# Shared Facts

Facts that more than one Fondue overlay states. Step 2 of
[SKILL.md](../SKILL.md) records each value from source, and Step 4 checks
every overlay against the recorded values.

Paths are relative to `{FONDUE}`. Read every value from source on each run.
The "Overlays" column names every overlay that states the fact. A **bold**
entry owns it: only the owner carries the full table, list or recipe, and the
others state what their own mechanics need and link to the owner.

| Fact | Authoritative source | Overlays |
|---|---|---|
| Variant x arch x torch matrix | `ci-job-definitions.yml` (Fondue's declared single source of truth for the CI matrix): `base_images.variants`, `builder_images.variants`, `rhai_pipeline.variants` / `collections` / `omit_jobs`, and the three `rhai_pipeline` torch levels (`torch_versions` map, `variants.<v>.torch_versions`, `collections.<c>.torch_versions.<v>`). `base_images.variants.*.torch_versions` is a separate image matrix. Built channels: the `promote-plan-<channel>` jobs in `.generated/rhai-promote-jobs.yml`, generated from the matrix, not from the catalog. `rhai-pipeline/publish_config.yml` drives only the legacy product-versioned publish. Job templates such as `images/builder/gitlab-ci/images.yml` and directory listings are not the matrix. | 0017 (image matrix), 0019 (builder variants), 0020 (per-collection coverage); **0030** (per-variant default torch lists) |
| Channel catalog and identity | `rhai-pipeline/channels.yml` (rows with `domain`, `maturity`, `adopted_by`, `namespace`, `labels`) and `rhai-pipeline/src/rhai_pipeline/channel.py` (name grammar, OS token pattern, default domain). A catalog row is not a built channel; compare both sets. | **0030**; 0017, 0019, 0020 name channels only |
| OS identity tokens | Channel `{os}` token: the catalog `os` field and the variant suffix (`compute_channel` in `bin/regen-ci.py`). Conf and GitLab CI image token: `base_images.variants.*.version` after `split_base_image_version` (`bin/regen-ci.py`). Konflux image name: the `NAME` build arg and `output-image` in `.tekton/*-on-push.yaml`. The tokens differ by design; record each one from its source. | **0030** (rule); 0017 (image names), 0019 |
| Torch pin and builder torch collections | `rhai_pipeline.torch_versions.<X.Y>.builder_collection` maps a torch version to a `builder/collections/` directory. In channel mode the torch pin comes from `builder/collections/<BUILDER_TORCH_COLLECTION>/<variant>/constraints.txt` (`builder/pipeline-api/prepare_constraints.sh`). For a (collection, variant) in `skip_builder_torch_constraints` (a list, or `true` for every variant), `BUILDER_TORCH_COLLECTION` is empty and the `constraints-rules.txt` files still apply. Rules files on variants that are not skipped are bypassed: never report them as the torch pin. Torch-linked packages (vLLM and similar) live in `rhai-pipeline/collections/<c>/<variant>/torch/{requirements,constraints}-torch-<X.Y>.txt`. | **0030** (map); 0019 (directories), 0020 (per-collection pins) |
| Channel index URL | Base path: an optional `{namespace}/` plus the channel name, plus `-test` for the test index (`Channel._names` in `channel.py`). Host by domain: `simple_index_url` in `bin/regen-ci.py` and `pulp_content_index_url` in `builder/pipeline-api/pulp_content_url.sh`. Record whether any catalog row sets `namespace`. `pulp channel apply --all` creates four distributions per catalog row (`Channel.indexes`; `rhai-pipeline/.gitlab/channel-apply-job.yml`), uploads go only to a built channel's `-test` index, and production indexes get content only from promote jobs. `pulp channel apply` only creates or updates and nothing deletes distributions, so a row removed from the catalog keeps them. A URL that resolves proves only that a distribution exists, not that the index has content: never infer content or availability from a URL resolving, and never put probe results in a Fact. | **0030**; 0017 (rendered conf URLs), 0020 (upload and promote targets) |
| Wheel index product version | `rhai-pipeline/product-version.yml` -> `PRODUCT_VERSION`; `images/base/build-args/argfile.conf` -> `INDEX_VERSION` should match. If they differ, report both; do not pick one. Neither selects a channel index path. `PRODUCT_VERSION` consumers: release tags (`RELEASE_VERSION_PREFIX` in `builder/pipeline-api/ci-wheelhouse.yml`), the `product_name`/`product_version` package labels (`pulp_upload.py`), `publish-pulp-repositories`, `update-publish-config-from-test`, the legacy index URL in `rhai-pipeline/.gitlab/trigger-autoqa-job.yml` and the push `changes:` trigger (`PRODUCT_VERSION_FILE`); grep `rhai-pipeline/.gitlab/` and `bin/regen-ci.py` for others. Not consumers: paths that hardcode the version (the `variant_overrides` `WHEEL_SERVER_PROJECT_PATH` values), `pulp copy` (`SOURCE_VERSION`/`DEST_VERSION`), `pulp delete` (manifest names) and the hand-maintained `supported_versions.yml`. Report where `INDEX_VERSION` is used in `images/base/`. | 0017, 0020 |
| Legacy product-versioned indexes | Upload mode precedence `CHANNEL`, then `PULP_BASE_PATH`, then `PRODUCT_VERSION` (`rhai-pipeline/bin/upload_to_pulp.sh`); grep `.generated/rhai-*.yml` for build jobs on `main` that upload without `CHANNEL`. Other writers and readers: the `publish_config.yml` publish, `pulp copy` and `pulp delete` jobs, and base confs whose `INDEX_BASE_URL` names a product path. Fondue release branches build their own product-versioned indexes, but this skill reads `main` only: say release branches are out of scope, and never call the legacy indexes frozen or retired. | **0030** (relationship); 0020 (publish, copy, delete), 0017 (confs) |
| Konflux base-image pipelines | `.tekton/*-on-push.yaml`: the `build-args-file` conf, `output-image`, `NAME` build arg and `on-cel-expression` trigger. `.tekton/` is generated by PMT from aipcc-product-management-configs (`.tekton/README.md`), so a new Konflux pipeline is a change there, not a `.tekton` edit. `bin/regen_tekton.py` rewrites only `pip-index-url`. | **0017**; 0030 (channel awareness) |
| Channel-awareness states | The checks listed under "Channel-awareness checks" in [channels.md](channels.md), each with its source: Konflux (`.tekton/*-on-push.yaml` `build-args-file`), image channel label (`compute_base_image_channel_label` in `bin/regen-ci.py` against the catalog `os`), bootstrap (the regex and fallback `case` list in `images/base/context/common/index-url.sh` against the built channels and catalog `os` tokens), deletion (`rhai-pipeline/src/rhai_pipeline/pulp_delete.py`, `rhai-pipeline/package-deletions/`, and whether `pulp_upload.py` and `builder/package_plugins/hooks/upload_after_build_wheel.py` read the manifests), images, catalog vs built, and legacy writers. Record one result per check. | **0030**; 0017 (label and bootstrap mechanics), 0020 (deletion mechanics) |
| Cross-component recipes and OS pins | The new torch version, new accelerator and new OS stream recipes, and the OS pin list built by the procedure under "OS Pins" in [channels.md](channels.md). | **0030**; 0017, 0019, 0020 (component-local steps only, link 0030) |
| Builder release tag | `releases/builder-release.yaml` -> `version`: the release declared on `main` (there is no `builder/release.yaml`). `main` sometimes declares a patch release and release branches tag others, so never describe a consumer's pinned tag as ahead of or behind the builder. | 0019, 0020 (context only) |
| Base OS (RHEL) version | `builder/product-version.yml` -> `PRODUCT_VERSION` (e.g. `0.0-el9.8`; the OS the builder targets, not a builder release; it drives builder-collection release tags and the builder cache path, per `builder_pipeline` in `ci-job-definitions.yml`), root `.gitlab-ci.yml` -> `BUILDER_PRODUCT_VERSION` (the `ci-<VERSION>-` builder image tags, through `builder-image-version.yml`), `images/builder/build-args/common.conf` -> `BASE_IMAGE`, `images/base/build-args/argfile.conf` -> `APP_BASE_IMAGE`. All four name the same RHEL minor; if not, report each value. | 0017, 0019, 0020, 0030 |
| How consumers get the builder | `rhai-pipeline/` uses the in-tree builder: `builder-image-version.yml` (included last by `.gitlab-ci.yml`) sets `BUILDER_IMAGE_VERSION` to `ci-${BUILDER_PRODUCT_VERSION}-${CI_MERGE_REQUEST_IID}`, so MR pipelines use that MR's builder images and non-MR pipelines use the branch's `ci-<VERSION>-` images. It is not a release tag. Which pipelines run `rhai-pipeline/` jobs is decided first by the rules on the `.generated/rhai-*.yml` includes in `.gitlab-ci.yml` (`RHAI_INCLUDE_RULES`, plus `RHAI_POST_MERGE_RULE` for collections with `enable_post_merge_jobs`, in `bin/regen-ci.py`), then by the job `rules` in `builder/pipeline-api/ci-wheelhouse.yml` (including the `changes:` paths that scope push builds); `build_on_all_pushes` only matters where those includes load. Derive what each pipeline source builds from those rules. `rhaiis/pipeline` is outside Fondue: say it pins a Fondue release ref and link overlay 0021; do not restate its pin. | 0019, 0020 |
| Public vs private index | Channel uploads: the catalog row `domain` (an omitted `domain` falls back to `DEFAULT_DOMAIN` in `channel.py`). Job and promote routing: `PULP_DOMAIN` after `rhai_pipeline.overrides._default` -> `overrides.<collection>` -> `variant_overrides.<collection>.<variant>`. Image side: the rendered `INDEX_URL_TEMPLATE` from `images/base/build-args/*.conf`. Classify by host (`packages.redhat.com` public, `private.console.redhat.com` private), not by `DISTRIBUTION_SCOPE` or `regen-skip` markers. Private-domain channels carry non-redistributable vendor wheels (AIPCC-28553). | **0030**; 0017, 0020 |
| Spyre IBM stack | SDK RPM pins: versioned package names in `images/base/context/spyre/rpms.in.yaml` (AIPCC-29839; there is no `SPYRE_VERSION` build arg). Wheel sourcing: `builder/overrides/settings/torch_sendnn.yaml` and `torch_nnpa.yaml` (pre-built, private index). Wheel version pins: the consuming collection's `requirements.txt` and its `torch/requirements-torch-<X.Y>.txt` overlay (vLLM and torch-linked packages live in the overlay). torch-sendnn tracks the SDK RPM version; torch-nnpa has its own version line. | 0017, 0019, 0020 |
| aiu-monitor | Not a wheel collection package; it ships as an RPM in the Spyre base image. The `aiu-monitor<0.0.0` / `ibm-aiu-monitor<0.0.0` guards were removed from `builder/collections/global-constraints.txt` (AIPCC-28729); grep that file before claiming any guard exists. Overlay 0017 must not mention `aiu-monitor` or `ibm-aiu-monitor` at all (see its reference), so skip this row when checking 0017. | 0019, 0020 |
