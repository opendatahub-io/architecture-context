## Purpose

**Short**: Kubernetes operator that manages OGX inference servers on RHOAI, reconciling OGXServer custom resources into fully configured deployments with autoscaling, network policies, monitoring, and a validating admission webhook. [source: main.go:101, api/v1beta1/ogxserver_webhook.go:54, config/rbac/role.yaml:2]

**Detailed**: ogx-k8s-operator ships two controller-runtime binaries. The root `ogx-k8s-operator` binary runs the OGXServerReconciler, which watches OGXServer CRs (ogx.io/v1beta1) and reconciles each into a Deployment, Service, HPA, PDB, NetworkPolicy, ConfigMap, and optional Ingress and PersistentVolumeClaim. It label-filters its informer caches to only track resources with `app.kubernetes.io/managed-by: ogx-operator` and applies the cluster's OpenShift TLS profile (with an Intermediate fallback on non-OpenShift clusters) to the webhook server. The `ogx-module` binary is a separate controller-runtime operator that manages the OGX platform component CRD (components.platform.opendatahub.io/OGX) and uses odh-platform-utilities for kustomize-based manifest rendering, condition management, garbage collection, and platform detection. A `configgen` CLI generates runtime configuration from distribution specifications. A validating webhook (`vogxserver.kb.io`) enforces OGXServer schema integrity on CREATE and UPDATE operations with a Fail failure policy. [source: main.go:101-106, main.go:108-136, main.go:156-198, ogx-module/internal/controller/ogx/reconciler.go:15-20, config/webhook/manifests.yaml:2-27, Dockerfile.konflux:29]

## Architectural Analysis

ogx-k8s-operator follows a dual-binary operator pattern common in the RHOAI platform. The root operator (`ogx-k8s-operator`) owns the user-facing OGXServer CR lifecycle, while `ogx-module` manages the platform-level OGX component CRD that the RHOAI operator uses to install and configure OGX itself. This separation keeps the user-facing reconciliation loop independent of the platform bootstrapping logic.

The OGXServerReconciler owns a broad set of child resources—Deployments, Services, ConfigMaps, HPAs, PDBs, NetworkPolicies, Ingresses, PVCs, and Secrets—and uses label-scoped informer caches (`app.kubernetes.io/managed-by: ogx-operator`) to reduce watch pressure on the API server. It also watches Secrets and ConfigMaps with a dedicated label selector rather than listing the entire namespace, which is a meaningful isolation boundary in multi-tenant clusters. A legacy adoption path exists for migrating pre-existing resources under operator management (controllers/legacy_adoption.go).

TLS configuration is delegated to the OpenShift platform: the operator fetches the APIServer TLS profile at startup via `controller-runtime-common/pkg/tls.FetchAPIServerTLSProfile` and applies it to the webhook server, falling back to the Intermediate profile on non-OpenShift clusters or transient API errors. This means cipher suite and minimum TLS version are platform-managed rather than hardcoded.

The ogx-module controller relies heavily on odh-platform-utilities for kustomize-based manifest rendering, controller condition helpers, garbage collection, and platform detection (ODH vs RHOAI). It manages ValidatingWebhookConfigurations, CRDs, RBAC resources, and Deployments as owned resources, providing full lifecycle management for the root operator's installation. Prometheus monitoring integration is established via RBAC grants on monitoring.coreos.com PrometheusRules and ServiceMonitors. ### FIPS Compliance

Both Konflux Dockerfiles build with `CGO_ENABLED=1` (dynamic linking), which satisfies the check-payload requirement for dynamically linked Go binaries. The runtime base image is `registry.access.redhat.com/ubi9/ubi-minimal`, which includes OpenSSL. However, neither Dockerfile specifies `GOEXPERIMENT=strictfipsruntime` or `-tags strictfipsruntime` in the build command, so the Go binaries do not use the strict FIPS runtime enforcement available in Go 1.24+.

At the application level, the root operator delegates TLS configuration to the OpenShift platform by fetching the APIServer TLS profile via `controller-runtime-common/pkg/tls.FetchAPIServerTLSProfile` and applying it to the webhook server. On non-OpenShift clusters, it falls back to the Intermediate TLS profile. This means cipher suites and minimum TLS version are determined by the platform's TLS security policy rather than hardcoded in the operator. The operator imports `crypto/tls` from the standard library, which on RHEL 9 with CGO delegates to OpenSSL at runtime. No non-FIPS crypto libraries or hardcoded cipher suites were detected.

## Data Flows

- **OGXServer reconciliation:** A user creates an OGXServer CR in a namespace. The OGXServerReconciler watches for these CRs and reconciles each into a Deployment running the inference server image, along with a Service, optional HPA, PDB, NetworkPolicy, ConfigMap, Ingress, and PVC. The reconciler reads Secrets (labeled with the watch label) for model credentials and ConfigMaps for runtime configuration. All child resources are owned by the OGXServer CR, enabling garbage collection on deletion. [source: main.go:101-106, main.go:108-136, config/rbac/role.yaml:6-30]
- **OGX platform component lifecycle:** The ogx-module Reconciler watches the OGX CR (components.platform.opendatahub.io) and renders kustomize-based manifests to install or update the root ogx-k8s-operator Deployment, its RBAC resources, CRDs, ValidatingWebhookConfiguration, and Services. It uses odh-platform-utilities for platform detection (ODH vs RHOAI overlay selection) and condition management. [source: ogx-module/internal/controller/ogx/reconciler.go:15-20, ogx-module/internal/controller/ogx/reconciler.go:44-52]
- **Admission control:** The ValidatingWebhookConfiguration routes CREATE and UPDATE operations on ogxservers to the `/validate-ogx-io-v1beta1-ogxserver` endpoint served by the ogx-k8s-operator webhook server on port 9443 with TLS. The webhook enforces schema validation with a Fail failure policy. [source: config/webhook/manifests.yaml:2-27, config/webhook/service.yaml:1, api/v1beta1/ogxserver_webhook.go:54]
- **Monitoring integration:** The operator's RBAC grants allow creating and managing PrometheusRules and ServiceMonitors via the monitoring.coreos.com API group, enabling Prometheus-based observability for managed OGX server instances. [source: config/rbac/role.yaml:2]
- **Egress:** Both binaries communicate with the Kubernetes API server (port 6443, HTTPS with ServiceAccount token authentication) for all resource operations. The root operator additionally fetches the OpenShift APIServer TLS profile at startup. [source: main.go:156-164, ogx-module/cmd/ogx-module/main.go:66]
