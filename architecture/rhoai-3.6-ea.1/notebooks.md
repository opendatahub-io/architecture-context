## Purpose

**Short**: Container image build repository producing JupyterLab, Code Server, and runtime workbench images for Red Hat OpenShift AI, with multiple accelerator variants (CPU, CUDA, ROCm) and pre-installed ML framework dependencies. [source: jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:49-50, manifests/rhoai/base/kustomization.yaml:4-29]

**Detailed**: The notebooks component is a container image factory that builds and ships the workbench images used by data scientists in Red Hat OpenShift AI. It produces multiple notebook image variants — JupyterLab (minimal, datascience, PyTorch, TensorFlow, TrustyAI, LLM Compressor) and Code Server — each available in CPU, NVIDIA CUDA, and AMD ROCm accelerator flavors. The images are built from UBI9 base images using Konflux pipelines with hermetic dependency prefetching (Cachi2/Hermeto). Each variant bundles a curated set of Python ML libraries (PyTorch, TensorFlow, scikit-learn, transformers, etc.) and platform integration SDKs (KubeFlow Pipelines, CodeFlare, MLflow) that users invoke from within their notebook sessions.

The repository also produces standalone runtime images (minimal, datascience, PyTorch, TensorFlow variants) that serve as lighter-weight execution environments for pipeline steps. Image metadata is delivered to the RHOAI platform via OpenShift ImageStream resources managed through kustomize manifests with ConfigMap-based parameter substitution. Authentication for notebook access is not handled within the container images themselves; it is delegated to the platform, where the odh-notebook-controller injects an oauth-proxy sidecar. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:47-50, manifests/rhoai/base/kustomization.yaml:4-29, jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:88-94]

## Architectural Analysis

The notebooks repository follows a layered container image build pattern where a shared UBI9 base stage (`cpu-base`) installs OS-level dependencies — including `compat-openssl11` for FIPS compliance scanning and `skopeo`/`openshift-clients` for platform tooling — and variant-specific stages layer Python dependencies from hermetically prefetched lockfiles. Each notebook variant uses the same `start-notebook.sh` entrypoint that launches JupyterLab with environment-variable-driven configuration for port, base URL, and root directory, keeping the image agnostic to its deployment context. [source: jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:9-30, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:16-50]

Authentication is architecturally absent from the notebook containers. The `jupyter_server_config.py` configures only PDF export disabling and Git extension timeouts — no token, password, or XSRF settings. In production, the odh-notebook-controller injects an oauth-proxy sidecar that gates access through OpenShift OAuth before requests reach JupyterLab. This separation means the notebook images are reusable across deployment contexts but depend on external enforcement for any access control. [source: jupyter/utils/jupyter_server_config.py:1-9, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:47-50]

The Go components (`buildinputs`, `check-payload`) are build-time utilities, not runtime services. They are compiled with `CGO_ENABLED=0` as statically linked binaries in their own Dockerfiles and are not included in the notebook container images. The check-payload tool validates FIPS compliance of built images; buildinputs is a Dockerfile dependency graph analyzer. [source: scripts/check-payload/Dockerfile:18-19, scripts/buildinputs/Dockerfile:17-18]

The kustomize manifests under `manifests/rhoai/base/` define ImageStream resources for each notebook and runtime variant, using ConfigMap-sourced parameter replacement to inject version-specific image references. The label `component.opendatahub.io/name: notebooks` enables the RHOAI operator and dashboard to discover these images as available workbench types. [source: manifests/rhoai/base/kustomization.yaml:4-47]

### FIPS Compliance

The notebook container images are Python-based workloads running on UBI9. FIPS compliance for cryptographic operations relies on the system-level OpenSSL provided by the UBI9 base image; when the host operating system has FIPS mode enabled, OpenSSL operates in FIPS mode. The `compat-openssl11` package is explicitly installed to provide `libcrypto.so.1.1`, which is required by the check-payload FIPS compliance scanner. [source: jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:27-30]

The Python `cryptography` library (==46.0.7) uses system OpenSSL as its backend, inheriting FIPS capability from the base image. However, `pycryptodome` (==3.23.0) is also a dependency; it is a self-contained crypto library that does not use OpenSSL and is not FIPS-validated. Its presence represents a potential non-FIPS crypto path if used by notebook workloads or upstream dependencies. [source: codeserver/ubi9-python-3.12/requirements.cpu.txt:92, codeserver/ubi9-python-3.12/requirements.cpu.txt:350]

The Go build utilities (`buildinputs`, `check-payload`) use `CGO_ENABLED=0` (static linking) and do not set `GOEXPERIMENT=strictfipsruntime`. These are build-time tools in separate container images, not shipped within notebook images, so they are outside the FIPS compliance scope of the notebook workloads. [source: scripts/check-payload/Dockerfile:18-19, scripts/buildinputs/Dockerfile:17-18]
## Data Flows

- **User access flow:** Users access notebook workbenches through the RHOAI Dashboard, which creates a Notebook CR. The odh-notebook-controller reconciles the CR into a StatefulSet pod containing the notebook container and an oauth-proxy sidecar. Incoming HTTPS requests hit the OpenShift Route, pass through the oauth-proxy for OpenShift OAuth authentication, and are forwarded to JupyterLab on the notebook container's configured port (default 8888, overridable via `NOTEBOOK_PORT`). [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:19-21]
- **Image delivery flow:** Notebook and runtime container images are built by Konflux pipelines using hermetically prefetched dependencies (Cachi2). The built images are referenced in ImageStream resources defined under `manifests/rhoai/base/`, with image tags injected via ConfigMap parameter replacement. The RHOAI Dashboard discovers available images through ImageStreams labeled `component.opendatahub.io/name: notebooks`. [source: manifests/rhoai/base/kustomization.yaml:4-47]
- **User-initiated integrations:** From within notebook sessions, users can programmatically interact with platform services using pre-installed client libraries: Kubernetes API (`kubernetes` client), KubeFlow Pipelines (`kfp`), MLflow tracking, CodeFlare SDK for distributed computing, S3-compatible storage (`boto3`), and various database connectors. These are user-driven data flows, not always-on service integrations. [source: codeserver/ubi9-python-3.12/requirements.cpu.txt:270, 468, 322]
