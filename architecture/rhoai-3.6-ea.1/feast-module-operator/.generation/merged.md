## Purpose

**Short**: Kubernetes operator that manages Feast feature store deployments on OpenShift as a module within the RHOAI platform, reconciling the FeastOperator custom resource to render, deploy, and lifecycle-manage Feast components via the opendatahub-operator reconciler framework. [source: cmd/main.go:29, internal/controller/feastoperator/feastoperator_controller.go:88, api/components/v1alpha1/feastoperator_types.go:20]

**Detailed**: feast-module-operator is a Go-based Kubernetes operator built on controller-runtime and the opendatahub-operator reconciler framework. It watches the cluster-scoped `FeastOperator` custom resource (components.platform.opendatahub.io/v1alpha1) and reconciles Feast feature store infrastructure by rendering kustomize manifests and deploying them into the applications namespace. The operator manages a broad set of child resources including Deployments, Services, ServiceAccounts, RBAC resources, Jobs, CronJobs, ConfigMaps, ServiceMonitors, and PodDisruptionBudgets. It implements a platform version handshake protocol via the `odh-feastoperator-config` ConfigMap, enabling coordinated upgrades with the RHOAI platform operator. The operator also watches Feast FeatureStore CRDs (feast.dev), Kubeflow Notebooks, OpenShift Routes, and Spark applications as part of its integration surface. [source: internal/controller/feastoperator/feastoperator_controller.go:88-135, internal/controller/feastoperator/feastoperator_platform_version.go:50-93, pkg/manager/manager.go:66-151]

## Architectural Analysis

feast-module-operator follows the ODH module operator pattern: a Cobra CLI entrypoint dispatches to an `operator` subcommand (with a secondary `chartgen` subcommand for offline manifest generation). The operator subcommand constructs a controller-runtime manager with namespace-scoped caching limited to the applications namespace, then registers a single reconciler for the FeastOperator CR. [source: cmd/main.go:31-43, cmd/operator/operator.go:40-54, pkg/manager/manager.go:86-111]

The reconciler is built using the opendatahub-operator's declarative action pipeline: `initialize → upgradeIfNeeded → setKustomizedParams → releases → reconcilePlatformVersion → kustomize render → migrateDeploymentSelector → deploy → deployments status → gc`. This pipeline renders kustomize manifests from a bundled manifests directory, applies them with ordering and caching, and garbage-collects stale resources. A finalizer cleans up cluster-scoped ClusterRoles and ClusterRoleBindings that cannot use owner references. [source: internal/controller/feastoperator/feastoperator_controller.go:88-143, internal/controller/feastoperator/feastoperator_controller.go:148-178]

A notable architectural feature is the platform version handshake: the operator watches a ConfigMap (`odh-feastoperator-config`) in the applications namespace and compares its `platformVersion` value against the version recorded in the FeastOperator status. When the platform version advances, the operator runs version-gated migration logic before updating the status record. This enables the RHOAI platform operator to coordinate upgrades across module boundaries. [source: internal/controller/feastoperator/feastoperator_platform_version.go:50-93]

The operator's RBAC footprint is broad, reflecting its responsibility for deploying the full Feast stack: it manages Deployments, Services, RBAC resources, Jobs, CronJobs, PVCs, HPAs, PDBs, and Spark applications. It also requires read access to Kubeflow Notebooks and OpenShift Routes, suggesting integration with workbench and dashboard components. The metrics endpoint uses controller-runtime's built-in authentication via TokenReview and SubjectAccessReview, with a dedicated metrics-auth ClusterRole. [source: config/rbac/role.yaml:2, config/rbac/metrics_auth_role.yaml:1-17, pkg/manager/manager.go:91-93]
