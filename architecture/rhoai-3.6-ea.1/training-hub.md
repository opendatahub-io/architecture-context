## Purpose

**Short**: Training Hub is a Python library that provides a unified, algorithm-focused interface for language model training techniques including supervised fine-tuning (SFT), LoRA adaptation, reinforcement learning (GRPO), and gradient-free prompt optimization (GEPA), delegating execution to pluggable backend implementations. **Detailed**: Training Hub is a pure Python library (not a deployed service) that unifies multiple LLM training and optimization algorithms behind a consistent Algorithm/Backend abstraction. It supports supervised fine-tuning via InstructLab Training (SFT) and Mini-Trainer (OSFT), parameter-efficient LoRA adaptation via Unsloth, reinforcement learning from verifiable rewards via ART/GRPO with optional VeRL distributed execution, and gradient-free prompt optimization via GEPA with optional MLflow experiment tracking. The library is consumed programmatically by RHOAI platform workloads and notebook environments; it has no HTTP endpoints, Kubernetes services, or container images of its own. Runtime network activity depends entirely on the algorithm and backend selected by the caller, such as LLM inference calls through litellm for GEPA or MLflow Tracking Server communication for the MLflow-backed GEPA backend. ## Architectural Analysis

Training Hub follows a Strategy pattern where each training algorithm is represented by an `Algorithm` subclass paired with one or more swappable `Backend` implementations, managed through a central `AlgorithmRegistry`. This design allows new training techniques (SFT, OSFT, LoRA, GRPO, GEPA) to be added independently and lets consumers select backend implementations at runtime without changing algorithm-level code. The separation is architecturally significant because different backends have fundamentally different execution models: InstructLab Training uses `torchrun` for distributed SFT, Unsloth provides memory-efficient LoRA in-process, ART manages co-located vLLM inference with time-shared GPU training for GRPO, and VeRL enables multi-node distributed GRPO. [source: src/training_hub/algorithms/__init__.py:6-97]

The library's most notable architectural characteristic is the absence of a service boundary. Training Hub runs entirely within the caller's process (typically a Jupyter notebook or a training job pod), which means its security, networking, and resource characteristics are inherited from the host environment rather than defined by the library itself. The GEPA algorithm is the exception to this in-process pattern: it makes outbound HTTP calls to OpenAI-compatible LLM endpoints via litellm and, when using the MLflow backend, to an MLflow Tracking Server. These outbound connections use environment variables (`OPENAI_API_BASE`, `OPENAI_API_KEY`) for configuration, with the library temporarily injecting and restoring these values during optimization runs. [source: src/training_hub/algorithms/gepa.py:63-97, src/training_hub/algorithms/gepa.py:150-179]

A recent architectural addition is the `TrainingHubCallback` abstraction with backend-specific adapters (Unsloth, InstructLab, Mini-Trainer), which provides a unified lifecycle hook interface across heterogeneous training backends. This pattern enables consumers to observe training progress, checkpoint state, and metrics without coupling to any specific backend's callback mechanism. [source: src/training_hub/adapters/__init__.py:1-8, src/training_hub/algorithms/sft.py:30-39]

## Data Flows

- **Training execution:** The caller invokes a top-level function (e.g., `sft()`, `lora_grpo()`, `gepa()`) which dispatches to the registered Algorithm and Backend. The Backend handles all execution-model details: InstructLab Training launches `torchrun` workers for distributed SFT, ART manages co-located vLLM inference and LoRA training on a single GPU with time-sharing, and GEPA calls `gepa.optimize()` directly. Results (checkpoints, metrics, optimized prompts) are returned to the caller or saved to a specified output directory. [source: src/training_hub/algorithms/__init__.py:82-96, src/training_hub/algorithms/sft.py:17-28, src/training_hub/algorithms/gepa.py:27-103]
- **GEPA inference flow:** The GEPA algorithm's prompt optimization sends outbound HTTP requests to OpenAI-compatible LLM endpoints via litellm, configured through `OPENAI_API_BASE` and `OPENAI_API_KEY` environment variables. The library temporarily sets and restores these environment variables during optimization runs. [source: src/training_hub/algorithms/gepa.py:63-97]
- **MLflow tracking flow:** The MLflowGEPABackend delegates prompt optimization to `mlflow.genai.optimize_prompts()`, which integrates with an MLflow Tracking Server for experiment logging and prompt registry. For SFT/OSFT algorithms, MLflow tracking is optionally configured via instructlab-training's native `mlflow_tracking_uri` parameter.
