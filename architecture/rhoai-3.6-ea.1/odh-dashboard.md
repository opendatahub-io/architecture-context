## Purpose

**Short**: odh-dashboard provides the web-based management console for Red Hat OpenShift AI, combining a React/PatternFly frontend with a Go operator and ten federated Go BFF sidecars to present a unified UI for managing notebooks, model serving, model registry, experiment tracking, and AI agent operations. [source: Dockerfile.konflux:52, Dockerfile.konflux.dashboard-operator:37, dashboard-operator/charts/dashboard/values.yaml:18]

**Detailed**: odh-dashboard is a multi-component platform console consisting of three tiers: (1) a React/PatternFly single-page application served via Webpack Module Federation that hosts domain-specific UI modules; (2) a Node.js Fastify backend that proxies Kubernetes API requests using user impersonation and serves static assets behind kube-rbac-proxy; and (3) a Go operator (dashboard-operator) built on controller-runtime v0.23.3 that reconciles Dashboard custom resources, managing the lifecycle of the console deployment including RBAC, routes, and sidecar BFF services. The federated architecture includes ten Go BFF (backend-for-frontend) sidecars — core-bff, gen-ai, model-registry, mlflow, eval-hub, maas, agent-ops, automl, autorag, and data-registry — each serving domain-specific API endpoints on dedicated TLS-encrypted ports with Bearer token authentication. The operator watches platform CRDs (DataScienceCluster, DSCInitialization, KServe InferenceService, ModelRegistry, MLflow, TrustyAI, Feast) to reflect platform state in the dashboard and manages Gateway API HTTPRoutes for request routing. A bundled Workspace controller reconciles kubeflow.org/v1beta1 Workspace and WorkspaceKind resources with validating and conversion webhooks. ## Architectural Analysis

The odh-dashboard follows a micro-frontend architecture using Webpack Module Federation, where a host React application dynamically loads domain-specific UI modules (gen-ai, model-registry, notebooks, eval-hub, agent-ops, automl, autorag, data-registry, maas, mlflow) at runtime via `/_mf/:name/*` paths. Each UI module is paired with a dedicated Go BFF sidecar that handles its backend operations, creating a vertically-sliced architecture where each domain owns its full request path from UI through BFF to Kubernetes API. The federation configuration (in `manifests/rhoai/base/federation-configmap.yaml`) maps path prefixes to sidecar ports, enabling a single ingress point to fan out to domain-specific backends. [source: manifests/rhoai/base/federation-configmap.yaml:15, backend/src/routes/module-federation.ts:1]

The dashboard-operator reconciles Dashboard custom resources created by the rhods-operator, deploying and configuring the console pod alongside its BFF sidecars. The operator implements a declarative ownership model where the parent Dashboard CR controls the lifecycle of Deployments, Services, Routes, NetworkPolicies, PodDisruptionBudgets, and RBAC resources via controller-runtime's `Owns()` watches. Controller watches on platform CRDs (DataScienceCluster, DSCInitialization, KServe InferenceService, ModelRegistry, MLflow, TrustyAI, Feast) enable the dashboard to reflect the real-time state of the AI platform without polling. The operator uses `odh-platform-utilities` for platform detection, manifest rendering, and deployment helpers. [source: dashboard-operator/charts/dashboard/values.yaml:15-18, dashboard-operator/go.mod:6, dashboard-operator/config/rbac/role.yaml:1]

Authentication follows a two-layer model: kube-rbac-proxy fronts the Node.js backend (port 8443) performing OpenShift OAuth validation and injecting identity headers (`x-forwarded-access-token`, `x-auth-request-user`, `x-auth-request-groups`), while each Go BFF sidecar independently validates Bearer tokens and performs SubjectAccessReviews against the Kubernetes API for fine-grained authorization. The agent-ops BFF extends this with per-agent RBAC via SubjectAccessReviews for agent-specific access control. The Node.js backend additionally proxies Kubernetes API calls (`/api/k8s/*`) by converting user tokens to impersonation headers, allowing the frontend to interact with the cluster API through the dashboard service boundary. [source: backend/src/utils/constants.ts:18-20, backend/src/utils/proxy.ts:39-42, packages/agent-ops/bff/internal/api/middleware.go:1]

The component packages a Workspace controller (reconciling kubeflow.org/v1beta1 Workspace and WorkspaceKind resources with validating and conversion webhooks) alongside the dashboard operator. Workspaces are managed via StatefulSets with associated Services and PodDisruptionBudgets. Cert-manager provisions TLS certificates for the webhook and metrics endpoints. All Go binaries (operator and BFF sidecars) are built with `CGO_ENABLED=1` and `-tags strictfipsruntime` for FIPS-compliant cryptographic operations through system OpenSSL. ## Data Flows

- **User request path:** Browser clients connect to the dashboard through an OpenShift Route that terminates TLS and forwards traffic to kube-rbac-proxy (port 8443). Kube-rbac-proxy validates the user's OpenShift OAuth token and injects identity headers (`x-forwarded-access-token`, `x-auth-request-user`, `x-auth-request-groups`) before forwarding to the Node.js Fastify backend. The backend serves the React SPA for UI requests at `/` and proxies `/api/k8s/*` requests to the Kubernetes API using user token impersonation. Module federation remotes are served at `/_mf/:name/*` paths, loading domain-specific UI bundles dynamically. [source: backend/src/utils/constants.ts:18-20, backend/src/utils/proxy.ts:39-42, backend/src/routes/root.ts:1, backend/src/routes/module-federation.ts:1]
- **BFF sidecar traffic:** Each federated module's API calls are routed by path prefix to the corresponding Go BFF sidecar (e.g., `/gen-ai/api/*` → port 8143, `/model-registry/api/*` → port 8043, `/agent-ops/api/*` → port 8843). BFF sidecars authenticate requests independently using Bearer tokens, perform SubjectAccessReviews for authorization, and issue Kubernetes API calls using either the user's forwarded token or an internal ServiceAccount token, depending on the configured `auth-method` flag. Two Kubernetes Service objects expose the operator's metrics (port 8443) and webhook (port 443→9443) endpoints internally. [source: manifests/rhoai/base/federation-configmap.yaml:15, packages/gen-ai/bff/internal/constants/api_constants.go:15, dashboard-operator/config/webhook/manifests.yaml:29]
- **Controller reconciliation:** The dashboard-operator watches the Dashboard CR (created by rhods-operator) and reconciles the deployment of the console pod, RBAC resources, routes, and services. It also watches platform CRDs (DataScienceCluster, DSCInitialization, KServe InferenceService, ModelRegistry, MLflow, TrustyAI, Feast) to propagate platform state changes into dashboard configuration. The Workspace controller reconciles Workspace and WorkspaceKind CRs, managing StatefulSets, Services, and PodDisruptionBudgets for notebook workspaces. [source: dashboard-operator/charts/dashboard/values.yaml:15-18, dashboard-operator/config/rbac/role.yaml:1]
- **External service interactions:** BFF sidecars proxy requests to external platform services: gen-ai BFF connects to Llama Stack servers, MLflow tracking servers, NeMo guardrails, and MCP servers (via SSE/streamable HTTP with `X-MCP-Bearer` authentication); eval-hub BFF queries TrustyAI and KServe InferenceServices; maas BFF communicates with MaaS API servers; and the core-bff proxies to Prometheus/Thanos for metrics dashboards. All external connections use TLS encryption with Bearer token or API key authentication. [source: packages/gen-ai/bff/internal/constants/mcp.go:5-16, packages/eval-hub/bff/internal/api/inferenceservices_handler.go:94]
