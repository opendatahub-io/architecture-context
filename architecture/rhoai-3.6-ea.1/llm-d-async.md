## Purpose

**Short**: llm-d-async is an asynchronous inference request processor that consumes requests from message queues (Redis or GCP Pub/Sub), dispatches them to model server backends via HTTP, and writes results back through the message broker. [source: cmd/main.go:14, pkg/server/runner.go:288-314]

**Detailed**: llm-d-async implements the asynchronous processing component of the llm-d (LLM Distributed) inference stack. It operates as a Kubernetes workload that bridges message queue transports with HTTP-based model serving backends. The processor supports three transport backends — Redis Pub/Sub, Redis Sorted Set, and GCP Pub/Sub — and uses configurable worker pools with concurrency limits and Prometheus-driven flow control gates to manage request dispatch. Incoming inference requests are consumed from named queues, optionally transformed via a plugin chain, forwarded to model servers over HTTP (with optional mTLS), and results are written back to the message broker. The component integrates with the gateway-api-inference-extension for logging utilities and uses controller-runtime for metrics serving with Kubernetes API-based authentication. Health probes are served on a dedicated HTTP port (default 8081) and Prometheus metrics on port 9090. The Konflux build produces a FIPS-compliant binary using `GOEXPERIMENT=strictfipsruntime` with dynamic linking on a UBI9 base. ## Architectural Analysis

llm-d-async follows a pipeline architecture centered on a pluggable transport layer. The `loadFlow` function in `runner.go` selects one of three message queue implementations — Redis Pub/Sub, Redis Sorted Set, or GCP Pub/Sub — based on runtime configuration, and each implementation satisfies the `pipeline.Flow` interface for consuming requests and publishing results. This transport abstraction allows the same worker pool machinery to operate across different messaging backends without code changes.

The worker pool design supports named pools with per-pool concurrency limits and optional Prometheus-metric-driven flow control gates. The `GateFactory` queries a configurable Prometheus endpoint to evaluate dispatch conditions, enabling backpressure based on model server load metrics. A request merge policy plugin system (defaulting to random-robin) determines how incoming queues map to worker pools, supporting multi-queue topologies.

The inference client is a plain HTTP client with optional mTLS support. TLS configuration accepts custom CA certificates and client certificate pairs, with a minimum TLS version of 1.2 enforced in `buildTLSConfig`. Request body transformations are handled by a plugin chain loaded from configuration, with a built-in GCS multipart transform registered at startup.

The metrics server uses controller-runtime's server implementation with Kubernetes API-based authentication and authorization enabled by default (`MetricsEndpointAuth: true`). This means the `/metrics` endpoint requires a valid Kubernetes bearer token and is protected by the same RBAC rules as the Kubernetes API. Health probes run on a separate unauthenticated HTTP server, consistent with Kubernetes kubelet probe requirements.

The component does not define its own CRDs, Kubernetes Services, or gRPC servers. It is a workload consumer that relies on external infrastructure (Redis, GCP Pub/Sub, Prometheus, model servers) and is deployed via operator-managed manifests or guide-provided YAML patches.
