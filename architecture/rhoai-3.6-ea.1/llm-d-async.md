## Purpose

**Short**: Asynchronous inference processor that dequeues LLM requests from a message broker (Redis or GCP Pub/Sub), dispatches them to model-serving backends over HTTP, and returns results through the same transport. [source: cmd/main.go:14, pkg/server/runner.go:288-314]

**Detailed**: llm-d-async is the async processing component of the llm-d inference stack. It runs as a long-lived Go process (`async-processor`) that connects to a configurable message transport—Redis Pub/Sub, Redis Sorted Sets, or GCP Pub/Sub—to consume inference requests from named queues. A pool of concurrent workers dispatches each request to a downstream model-serving endpoint (such as vLLM) over an HTTP client with optional TLS and mTLS support. Flow-control gates backed by Prometheus metrics allow request admission to be throttled based on real-time backend utilisation. The processor exposes a health server on port 8081 (`/healthz`, `/readyz`) and a metrics server on port 9090 with optional Kubernetes-delegated authentication. The Konflux build produces a FIPS-capable image using `GOEXPERIMENT=strictfipsruntime` and dynamic linking on a UBI 9 base. [source: cmd/main.go:14, pkg/server/runner.go:43-204, pkg/server/options.go:91-121, Dockerfile.konflux:30]

## Architectural Analysis

llm-d-async follows a pluggable pipeline architecture centred on a `Flow` abstraction that encapsulates transport-specific message consumption, result publication, and cancellation checking. Three transport backends are supported: `redis-pubsub` (default), `redis-sortedset` (adds priority-based ordering with flow-control gates), and `gcp-pubsub` (Google Cloud). The transport selection is a runtime configuration choice rather than a build-time decision, making the same binary deployable against different broker topologies. [source: pkg/server/runner.go:288-314, pkg/server/options.go:104-106]

Worker concurrency is managed through named worker pools loaded from a JSON configuration file. Each pool can optionally attach a Prometheus-backed gate that queries live metrics to throttle request admission before a worker dispatches to the inference backend. The gate factory uses a cached Prometheus client to avoid per-request scraping overhead. [source: pkg/server/runner.go:97-98, pkg/server/runner.go:139-157]

The inference client is a plain HTTP client wrapped with OpenTelemetry instrumentation and configurable TLS. When CA certificates and client key pairs are provided, the client establishes mTLS connections to the model-serving endpoint; otherwise it falls back to plaintext or server-TLS depending on the target. TLS minimum version is set to 1.2. [source: pkg/server/runner.go:357-375, pkg/server/runner.go:393-432]

The health subsystem is cleanly separated: a dedicated HTTP server on port 8081 serves `/healthz` (always-OK liveness) and `/readyz` (gate-aware readiness backed by a pluggable checker). The metrics server on port 9090 uses controller-runtime's metrics infrastructure with Kubernetes-delegated authentication and authorization enabled by default. [source: internal/health/health.go:33-49, pkg/server/runner.go:336-355, pkg/server/options.go:95-98]

A notable design trade-off is that the repository does not package Kubernetes Service or Ingress manifests for the async processor itself. The example deployment guide provides manifests only for the model-server sidecar (vLLM), implying that the async processor's network exposure is expected to be managed by a higher-level deployment orchestrator or Helm chart within the llm-d stack. [source: docs/guides/e2e-deploy/modelserver/base/kustomization.yaml:1-8]

## Data Flows

- **Request ingestion:** The async processor connects to a message broker (Redis or GCP Pub/Sub) at startup and continuously consumes inference request messages from configured topic/queue names. Messages are fanned into per-pool channels through a configurable merge policy (default: random-robin). [source: pkg/server/runner.go:288-314, pkg/server/runner.go:137]
- **Inference dispatch:** Worker goroutines in each pool dequeue requests, optionally gate them via a Prometheus-backed admission check, and forward them as HTTP POST requests to the downstream model-serving endpoint (e.g., vLLM on port 8000). The HTTP client supports TLS 1.2+ with optional mTLS and is instrumented with OpenTelemetry tracing. [source: pkg/server/runner.go:160-173, pkg/server/runner.go:357-375]
- **Result return:** Completed inference results are written back to the broker's result channel. Failed requests are routed to a retry channel for reprocessing within the same flow. [source: pkg/server/runner.go:170]
- **Health and metrics surface:** A health server on port 8081 exposes `/healthz` and `/readyz` (unauthenticated, kubelet-only). A metrics server on port 9090 exposes Prometheus metrics with optional Kubernetes-delegated authentication. [source: internal/health/health.go:40-41, pkg/server/runner.go:336-355, pkg/server/options.go:95-98]
- **Observability egress:** OpenTelemetry traces are exported via OTLP/gRPC to a configured collector endpoint. Redis operations may optionally include per-command tracing spans. [source: pkg/server/runner.go:82-85, pkg/server/options.go:148]
