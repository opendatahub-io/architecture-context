## Purpose

**Short**: ML Metadata (MLMD) is a gRPC metadata store service that records and retrieves metadata associated with ML workflows, including artifacts, executions, contexts, and their lineage relationships. [source: ml_metadata/proto/metadata_store_service.proto:1142, ml_metadata/tools/docker_server/Dockerfile.konflux:56-59]

**Detailed**: ML Metadata provides a gRPC-based metadata storage and retrieval service (`MetadataStoreService`) for tracking ML pipeline artifacts, executions, contexts, events, and lineage graphs. The server is a C++ binary (`metadata_store_server`) built with Bazel, exposing approximately 35 gRPC RPCs on a configurable port (default 8080). It supports MySQL/MariaDB, PostgreSQL, and SQLite as backend databases, with MySQL being the typical production choice in RHOAI. The repository also produces Python client bindings (`ml_metadata` package) for programmatic access. In RHOAI, the MLMD gRPC server is deployed as a supporting service for Data Science Pipelines, storing pipeline run metadata, artifact provenance, and execution lineage. [source: ml_metadata/proto/metadata_store_service.proto:1142-1546, ml_metadata/proto/metadata_store.proto:788-805, ml_metadata/tools/docker_server/Dockerfile.konflux:46-59]

## Architectural Analysis

ML Metadata follows a straightforward client-server architecture: a single C++ gRPC server binary manages all metadata operations against a relational database backend. The server implements the `MetadataStoreService` proto service, which provides CRUD operations for three core entity types (Artifacts, Executions, Contexts) along with their type schemas, relationship edges (Events, Attributions, Associations, ParentContexts), and lineage graph queries.

The server's database abstraction supports MySQL/MariaDB, PostgreSQL, and SQLite through a `ConnectionConfig` oneof in the protobuf configuration. Both MySQL and PostgreSQL backends support SSL-encrypted database connections via their respective `SSLOptions` messages. The gRPC server itself supports optional TLS and mutual TLS through `MetadataStoreServerConfig.SSLConfig`, though the default RHOAI container entrypoint does not configure TLS — authentication and encryption are delegated to the platform's service mesh and network policies.

The repository is structured as a build-only source tree with no Kubernetes deployment manifests (no kustomization.yaml). Deployment configuration is managed externally, typically by the Data Science Pipelines Operator which deploys the MLMD gRPC server as a sidecar or companion service alongside pipeline components. The build produces multiple container variants (Konflux, Red Hat, Fedora, upstream) from the same Bazel-compiled binary, with the Konflux variant using digest-pinned UBI9 base images for supply chain integrity. [source: ml_metadata/proto/metadata_store.proto:788-874, ml_metadata/tools/docker_server/Dockerfile.konflux:1-68]

## Data Flows

- **Metadata ingestion:** Pipeline components (primarily Data Science Pipelines) connect to the MLMD gRPC server on port 8080 and invoke Put RPCs (PutArtifacts, PutExecutions, PutContexts, PutExecution, PutEvents, PutAttributionsAndAssociations, PutParentContexts, PutLineageSubgraph) to record ML workflow metadata. The server persists these records to the configured database backend (MySQL/MariaDB in production). [source: ml_metadata/proto/metadata_store_service.proto:1192-1352]

- **Metadata retrieval and lineage:** Consumers query the MLMD gRPC server using Get RPCs (GetArtifacts, GetExecutions, GetContexts, and their filtered variants) and lineage-tracing RPCs (GetLineageSubgraph) to retrieve metadata records, relationships, and provenance graphs. [source: ml_metadata/proto/metadata_store_service.proto:1354-1546]
