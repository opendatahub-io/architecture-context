## Purpose

**Short**: ML Metadata (MLMD) is a gRPC metadata store server that records and retrieves metadata associated with ML workflows, including artifacts, executions, and their lineage relationships. [source: ml_metadata/proto/metadata_store_service.proto:1142, ml_metadata/tools/docker_server/Dockerfile.konflux:56-59]

**Detailed**: ml-metadata provides a gRPC-based metadata storage service (`MetadataStoreService`) for tracking ML pipeline artifacts, executions, contexts, and their lineage relationships. The server is a C++ binary (`metadata_store_server`) built with Bazel from protobuf service definitions, and shipped as a container image for RHOAI. It supports MySQL/MariaDB, PostgreSQL, and SQLite as backend databases, with the RHOAI deployment typically using MariaDB. The server listens on a configurable gRPC port (default 8080) and supports optional SSL/TLS with mutual authentication via `MetadataStoreServerConfig`. The repository also produces a Python client library (`ml_metadata` package) and a manylinux build artifact for cross-platform distribution. In the RHOAI platform, ml-metadata serves as the metadata backend for Data Science Pipelines, storing pipeline run metadata, artifact provenance, and execution lineage. ## Architectural Analysis

ml-metadata is Google's ML Metadata library, forked downstream for RHOAI as a gRPC server container. The primary deployed artifact is a statically linked C++ binary (`metadata_store_server`) built from protobuf definitions using Bazel, despite the repository also containing substantial Python client code. The Konflux Dockerfile (`Dockerfile.konflux`) performs a multi-stage build: the builder stage compiles the server binary on a UBI9 image with Bazel 5, and the runtime stage copies only the binary and third-party MariaDB connector libraries onto a `ubi9-minimal` base, running as non-root user 65534.

The server exposes a single gRPC service (`MetadataStoreService`) with approximately 40 RPCs covering CRUD operations for artifacts, executions, contexts, and types, along with lineage graph traversal. It supports three database backends—MySQL/MariaDB, PostgreSQL, and SQLite—configured via a protobuf-based `MetadataStoreServerConfig` file. The MariaDB connector (`libmysqlclient`) is bundled as a third-party dependency, confirming MySQL-family support as the primary production backend.

The server has no built-in authentication or authorization. Optional mTLS can be configured through `MetadataStoreServerConfig.SSLConfig`, which supports server key/cert, custom CA, and client certificate verification, but this is not enabled by default. In RHOAI deployments, network-level isolation (service mesh, NetworkPolicies) provides the access control boundary. The gRPC port defaults to 8080 and is configurable via the `GRPC_PORT` environment variable. No HTTP endpoints are exposed; all client interaction occurs through the gRPC protocol. No explicit FIPS build configuration or cipher suite restrictions are present in the Dockerfile or build commands. ## Data Flows

- **Pipeline metadata recording:** Pipeline orchestrators (e.g., Data Science Pipelines) call the MetadataStoreService gRPC API on port 8080 to record artifacts, executions, contexts, events, and their relationships. The server persists these records to the configured database backend (MariaDB/MySQL in RHOAI). [source: ml_metadata/proto/metadata_store_service.proto:1142-1282, ml_metadata/tools/docker_server/Dockerfile.konflux:47-48]
- **Lineage queries:** Clients query lineage relationships through `GetLineageSubgraph` and related RPCs, which traverse the artifact-execution-context graph stored in the database and return subgraphs satisfying the query constraints.
