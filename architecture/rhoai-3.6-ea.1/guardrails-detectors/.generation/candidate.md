## Purpose

**Short**: A collection of content-analysis microservices for the FMS Guardrails Orchestrator, providing regex-based, HuggingFace model-based, and LLM-as-Judge text detection capabilities, deployed as KServe ServingRuntimes on OpenShift. [source: detectors/pyproject.toml:1-6, detectors/llm_judge/deploy/servingruntime.yaml:1, detectors/huggingface/deploy/servingruntime.yaml:1]

**Detailed**: guardrails-detectors packages three detector families into FastAPI-based microservices for use with the FMS Guardrails Orchestrator. The **built-in detector** provides regex pattern matching, file-type validation, and custom detector support via a pluggable registry. The **HuggingFace detector** serves transformer-based classification models (AutoModelForSequenceClassification, GraniteForCausalLM) for content safety evaluation. The **LLM Judge detector** delegates content evaluation to an external vLLM inference server using the `vllm-judge` library, supporting configurable evaluation metrics such as safety, toxicity, and accuracy. Each detector type exposes a REST API on port 8000/8080 and is packaged as a KServe ServingRuntime for deployment in the RHOAI model serving infrastructure. The LLM Judge detector requires a running vLLM inference service configured via the `VLLM_BASE_URL` environment variable. None of the detectors implement application-level authentication; security is expected to be enforced at the network or platform level. [source: detectors/built_in/app.py:1-83, detectors/llm_judge/detector.py:1-37, detectors/pyproject.toml:1-6, detectors/Dockerfile.konflux.builtIn:1-30]

## Architectural Analysis

guardrails-detectors follows a plugin-oriented architecture with three independent detector families sharing a common FastAPI application base and a unified request/response schema. Each detector type runs as a separate container image with its own Dockerfile, requirements, and KServe ServingRuntime definition, allowing independent scaling and deployment.

The **built-in detector** is fully self-contained: it loads regex patterns, file-type validators, and user-supplied custom detectors at startup and processes requests synchronously without external service dependencies. The **HuggingFace detector** loads transformer models at container startup (sourced from MinIO object storage via a data connection secret) and runs inference locally within the container. The **LLM Judge detector** has a fundamentally different architecture—it delegates evaluation to an external vLLM inference server via HTTP, making it dependent on a co-deployed predictor service (e.g., `qwen2-predictor:8080`). [source: detectors/llm_judge/detector.py:25-37, detectors/llm_judge/deploy/servingruntime.yaml:33-35, detectors/built_in/app.py:17-27]

A notable security characteristic is the complete absence of application-level authentication across all detector endpoints. Neither app registers middleware, dependencies, or decorators for authentication or authorization. This is architecturally intentional for KServe-managed workloads where network-level isolation and platform-provided auth (via Istio/service mesh) are expected to protect the inference surface. However, it means that any network-level misconfiguration would expose unprotected content-analysis APIs. [source: detectors/llm_judge/app.py:32, detectors/built_in/app.py:30]

All three detector types use Prometheus instrumentation for observability, with the built-in detector using the multi-process collector pattern and the LLM Judge using `prometheus-fastapi-instrumentator` for automatic endpoint metrics. The Konflux build pipeline uses AIPCC base images for the built-in detector, inheriting FIPS-capable system cryptography, while the HuggingFace detector uses parameterized base images supporting multiple architectures (amd64/arm64/ppc64le/s390x). [source: detectors/Dockerfile.konflux.builtIn:1, detectors/Dockerfile.konflux.hf:1-9]

## Data Flows

- **Content analysis request flow:** The FMS Guardrails Orchestrator sends POST requests to `/api/v1/text/contents` (both built-in and LLM Judge detectors) or `/api/v1/text/generation` (LLM Judge only). Each detector processes the request according to its type: the built-in detector runs regex/file-type checks locally, the HuggingFace detector runs transformer inference locally, and the LLM Judge detector forwards the evaluation request to an external vLLM inference server via HTTP. Responses include detection results with scores and optional metadata. [source: detectors/built_in/app.py:42-65, detectors/llm_judge/app.py:36-76, detectors/llm_judge/detector.py:74-109]
- **LLM Judge evaluation chain:** The LLM Judge detector receives a content analysis request, constructs evaluation parameters (metric, content, optional scale), and calls `judge.evaluate()` via the `vllm-judge` library. This issues an HTTP request to the vLLM inference server at `VLLM_BASE_URL` (default example: `http://qwen2-predictor:8080`). The vLLM server returns an evaluation result with a decision, score, and reasoning. The detector translates this into the standard `ContentAnalysisResponse` format. [source: detectors/llm_judge/detector.py:25-37, 86-109, detectors/llm_judge/deploy/servingruntime.yaml:33-35]
- **Model loading (HuggingFace):** At startup, the HuggingFace detector loads transformer models from MinIO object storage via an S3-compatible data connection configured through the `aws-connection-minio-data-connection-guardrails-guardian` secret. The model is loaded into memory and reused for all subsequent inference requests. [source: detectors/huggingface/deploy/model_container.yaml:1, 94-117]
- **Observability:** All detector types expose Prometheus metrics. The built-in detector uses `prometheus_client` with multi-process collector at `/metrics`. The LLM Judge uses `prometheus-fastapi-instrumentator` for automatic endpoint instrumentation at `/api/v1/metrics`. [source: detectors/built_in/app.py:35-40, detectors/llm_judge/app.py:5, 33]
