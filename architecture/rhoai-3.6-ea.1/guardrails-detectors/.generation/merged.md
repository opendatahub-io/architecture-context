## Purpose

**Short**: Guardrails-detectors provides a collection of content safety detection microservices — built-in regex/file-type detectors, HuggingFace model-based classifiers, and an LLM-as-Judge evaluator — exposed as FastAPI REST APIs for the FMS Guardrails Orchestrator. [source: detectors/pyproject.toml:5, detectors/built_in/app.py:42, detectors/llm_judge/app.py:36, detectors/huggingface/detector.py:10-16]

**Detailed**: Guardrails-detectors is a multi-variant content safety detection service designed to be consumed by the FMS Guardrails Orchestrator within the RHOAI TrustyAI guardrails pipeline. The repository produces three distinct detector types, each packaged as a separate container image. The **built-in detector** runs local regex pattern matching, file-type validation, and custom detection logic against input text, requiring no external model inference. The **HuggingFace detector** loads transformer models locally using PyTorch for sequence classification, token classification, or causal language modeling, running inference on-device without external HTTP calls. The **LLM Judge detector** delegates content evaluation to a remote vLLM inference server, connecting via the `vllm_judge` library to the endpoint specified by `VLLM_BASE_URL`, and supports configurable evaluation metrics including safety, toxicity, accuracy, and helpfulness. All three detectors expose a common REST API surface (`/api/v1/text/contents`, `/api/v1/text/generation`) on port 8080 via FastAPI/uvicorn, with Prometheus metrics instrumentation. Two KServe ServingRuntime definitions are packaged for the HuggingFace and LLM Judge variants. [source: detectors/pyproject.toml:5, detectors/built_in/app.py:42, detectors/llm_judge/app.py:36, detectors/llm_judge/detector.py:25-37, detectors/huggingface/detector.py:10-16, detectors/Dockerfile.konflux.builtIn:22-27, detectors/common/app.py:64]

## Architectural Analysis

Guardrails-detectors follows a plugin-style architecture where three detector variants share a common FastAPI base class (`DetectorBaseAPI`) that provides health checks, Prometheus metrics instrumentation, and standardized error handling. Each variant is independently deployable as a container, but all implement the same `/api/v1/text/contents` request/response contract defined in `detectors/common/scheme.py`, enabling the upstream FMS Guardrails Orchestrator to invoke any detector interchangeably. [source: detectors/common/app.py:33-64, detectors/built_in/app.py:42, detectors/llm_judge/app.py:36]

The built-in and HuggingFace detectors are self-contained: they perform inference locally without external service calls. The LLM Judge detector is architecturally distinct because it introduces a runtime dependency on an external vLLM inference server configured via `VLLM_BASE_URL`, making it the only variant with an outbound HTTP integration point. The `vllm_judge` library wraps this dependency, initializing a `Judge` client at startup and using it for async content evaluation. [source: detectors/llm_judge/detector.py:25-37, detectors/huggingface/detector.py:10-16]

No authentication middleware is registered at the application level — all endpoints are unprotected within the FastAPI application boundary. Authentication enforcement is expected to be delegated to the platform layer (e.g., Istio/service mesh sidecar injection or network policies). The base application supports optional TLS configuration via `ssl_ca_certs` in `config.yaml`, but this is not enabled by default in the container entrypoints. [source: detectors/common/app.py:21-29, detectors/common/app.py:181-182, detectors/llm_judge/app.py:32]

The Konflux build images use the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0`), which provides a UBI-based Python environment with OpenSSL. No explicit FIPS configuration is present at the application level; cryptographic behavior is inherited from the base image's OpenSSL installation. [source: detectors/Dockerfile.konflux.builtIn:1]

## Data Flows

- **Orchestrator → Detector request flow:** The FMS Guardrails Orchestrator sends HTTP POST requests to `/api/v1/text/contents` or `/api/v1/text/generation` on port 8080. Each detector variant processes the request independently: the built-in detector applies regex and file-type rules locally, the HuggingFace detector runs transformer model inference locally via PyTorch, and the LLM Judge detector forwards evaluation requests to a remote vLLM server. All responses follow the same `ContentsAnalysisResponse` schema. [source: detectors/built_in/app.py:42, detectors/llm_judge/app.py:36-55, detectors/huggingface/detector.py:10-16, detectors/common/app.py:64]
- **LLM Judge → vLLM egress:** The LLM Judge detector makes outbound HTTP calls to a vLLM inference server at the URL specified by `VLLM_BASE_URL`. The `vllm_judge.Judge` client is initialized at application startup and used for async evaluation of content against configurable metrics (safety, toxicity, accuracy, etc.). [source: detectors/llm_judge/detector.py:25-37]
- **Metrics exposure:** All detector variants expose Prometheus metrics. The built-in detector uses a multi-process Prometheus collector at `/metrics`, while the LLM Judge and HuggingFace variants use `prometheus-fastapi-instrumentator` for automatic request instrumentation. Custom counters track detections, requests, errors, and runtime per detector kind and name. [source: detectors/built_in/app.py:35-40, detectors/llm_judge/app.py:33, detectors/common/app.py:37-58]
- **Security context:** No authentication middleware is registered at the application level. All 5 HTTP endpoints are accessible without credentials within the pod network. The HuggingFace deployment references 1 Opaque secret (`aws-connection-minio-data-connection-guardrails-guardian`) for MinIO storage access. TLS is configurable but not enabled in default container entrypoints. [source: detectors/common/app.py:21-29, detectors/common/app.py:181-182, detectors/llm_judge/app.py:32]
