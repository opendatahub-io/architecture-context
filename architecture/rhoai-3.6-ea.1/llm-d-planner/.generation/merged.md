## Purpose

**Short**: llm-d-planner is a multi-tier Kubernetes workload that provides a FastAPI-based capacity planning and deployment recommendation service for LLM workloads, integrating with OpenAI-compatible APIs, Ollama, PostgreSQL, and the Kubernetes cluster API for GPU detection. [source: src/planner/api/app.py:57-61, deploy/kubernetes/backend.yaml:1-4, src/planner/llm/openai_client.py:10-40]

**Detailed**: llm-d-planner is an LLM deployment planning tool that helps operators navigate the complexity of deploying large language models on Kubernetes. The backend service is a FastAPI application served by uvicorn on port 8000, exposing a comprehensive REST API for capacity planning (`/api/v1/calculate`), GPU estimation (`/api/v1/estimate`), model recommendations (`/api/v1/recommend`), and cluster deployment management (`/api/v1/deploy-to-cluster`). The system uses a pluggable LLM provider architecture (configurable via `LLM_PROVIDER`) supporting OpenAI-compatible APIs, Google Vertex AI, and local Ollama instances for intent extraction and structured data analysis. A PostgreSQL database stores benchmark data and deployment configurations. The backend reads NVIDIA GPU labels from cluster nodes via the Kubernetes Python client to detect available accelerators and inform hardware recommendations. A Streamlit-based UI on port 8501 and a simulator service provide the user-facing interface and testing capabilities. OpenShift Routes provide external HTTPS access with TLS termination, while the OpenShift Service CA injects a trust bundle for internal TLS verification. [source: src/planner/api/app.py:55-91, deploy/kubernetes/backend.yaml:1-163, src/planner/cluster/gpu_detector.py:78-168, src/planner/llm/openai_client.py:19-45, deploy/kubernetes/service-ca-configmap.yaml:1-12]

## Architectural Analysis

llm-d-planner follows a classic multi-tier web application pattern deployed as four Kubernetes Deployments within a `planner` namespace: a FastAPI backend, a PostgreSQL database, an Ollama LLM server, and a Streamlit UI. The backend is the central orchestration point — it hosts all `/api/v1/` business logic routes and coordinates with external LLM providers, the local database, and the Kubernetes API.

The LLM integration layer is notably flexible: the `LLM_PROVIDER` environment variable selects between OpenAI-compatible endpoints (which can be pointed at any OpenAI API-compatible service via `OPENAI_BASE_URL`), Google Vertex AI, and the co-deployed Ollama instance. This pluggability allows the same codebase to target cloud-hosted inference services or local GPU-backed models. The OpenAI client wraps the standard `openai` Python SDK and authenticates via API key, with no additional middleware or token exchange. [source: src/planner/llm/openai_client.py:19-40, deploy/kubernetes/backend.yaml:59-99]

A significant architectural observation is the complete absence of application-level authentication. The FastAPI application registers only CORS middleware with wildcard origins (`allow_origins=["*"]`) and no authentication or authorization middleware. All 37 backend API endpoints — including administrative operations like `/api/v1/db/reset` and `/api/v1/deploy-to-cluster` — are accessible without credentials at the application layer. Security depends entirely on network-level controls: the backend Service is ClusterIP (internal-only), and external access is mediated by two OpenShift Routes (`planner` and `planner-backend`) that provide TLS termination. However, no OpenShift OAuth proxy or similar edge authentication is configured in the analyzed manifests. [source: src/planner/api/app.py:64-71, deploy/kubernetes/backend.yaml:150-163]

The GPU detection subsystem uses the Kubernetes Python client with in-cluster authentication (via the `planner-backend` service account) to list cluster nodes and read `nvidia.com/gpu.product` labels. A ClusterRole `planner-gpu-reader` grants the minimal `list` verb on `nodes` resources. Results are cached with a configurable TTL (default 300 seconds) to reduce API server load. This is the only Kubernetes API interaction; the component does not create, modify, or watch cluster resources beyond node listing. [source: src/planner/cluster/gpu_detector.py:78-168, deploy/kubernetes/backend.yaml:23]

The OpenShift Service CA integration (`service.beta.openshift.io/inject-cabundle: "true"`) provisions a CA bundle at `/etc/pki/service-ca` in the backend container, enabling trust of service-serving certificates for internal TLS connections. This is a passive trust configuration — the application does not explicitly configure TLS listeners or certificate rotation. [source: deploy/kubernetes/service-ca-configmap.yaml:10-11, deploy/kubernetes/backend.yaml:119-122]
