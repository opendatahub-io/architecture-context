## Purpose

**Short**: llm-d-planner is a multi-component planning and recommendation service for LLM deployments on Kubernetes, providing GPU capacity planning, model recommendation, and deployment orchestration through a FastAPI backend, Streamlit UI, and configurable LLM provider integrations. [source: Dockerfile:57, 60, deploy/kubernetes/backend.yaml:1, 150, src/planner/api/app.py:59-63]

**Detailed**: llm-d-planner helps platform operators navigate LLM deployments from concept to production. The backend component is a FastAPI service (port 8000) that exposes a REST API for capacity planning, GPU estimation, model recommendation, and deployment management. It integrates with multiple LLM providers — OpenAI-compatible endpoints, a co-deployed Ollama service, and Vertex AI — for natural-language intent extraction and structured data analysis, and queries the Kubernetes API to detect available GPU types on cluster nodes via `nvidia.com/gpu.product` labels. [source: src/planner/llm/openai_client.py:10, 39-40, deploy/kubernetes/backend.yaml:54, src/planner/cluster/gpu_detector.py:39, 90-91]

A Streamlit-based UI (port 8501) provides the interactive frontend, and an embedded SQLite database on a PersistentVolumeClaim stores benchmark data. External access is secured by two OpenShift Routes providing TLS termination for both the UI and backend API surfaces. The backend service account (`planner-backend`) holds a cluster-scoped RBAC binding for listing node resources, and the deployment mounts an OpenShift Service CA bundle at `/etc/pki/service-ca` for platform TLS trust. [source: deploy/kubernetes/backend.yaml:24, 114-119, 141-148, deploy/kubernetes/route.yaml:1, 19, deploy/kubernetes/service-ca-configmap.yaml:11]

## Architectural Analysis

llm-d-planner follows a three-tier architecture: a Streamlit UI (port 8501), a FastAPI backend (port 8000), and an Ollama LLM inference sidecar (port 11434). External traffic enters through two OpenShift Routes providing TLS termination for both the UI and backend API. All three workloads are deployed as single-replica Deployments in the `planner` namespace. [source: deploy/kubernetes/backend.yaml:1, deploy/kubernetes/ollama.yaml:1, deploy/kubernetes/ui.yaml:1, deploy/kubernetes/route.yaml:1, 19]

The backend is the core component, implementing capacity planning algorithms, GPU recommendation logic, model catalog queries, and deployment orchestration across a REST API with 30+ endpoints organized into route modules (capacity_planner, configuration, database, gpu_recommender, intent, quality, recommendation, reference_data, specification). It uses a pluggable LLM provider pattern — the `LLM_PROVIDER` ConfigMap key selects among OpenAI-compatible endpoints, Ollama, and Vertex AI at runtime, with each provider authenticated independently via optional secrets from the `planner-secrets` Opaque secret. The OpenAI client constructs an `openai.OpenAI` instance with configurable `base_url`, making it compatible with any OpenAI API-compliant inference service including vLLM and other OpenAI-compatible backends. [source: src/planner/api/app.py:57-89, src/planner/llm/openai_client.py:19-45, deploy/kubernetes/backend.yaml:62-95]

GPU detection reads `nvidia.com/gpu.product` labels from cluster nodes via the Kubernetes Python client (`CoreV1Api.list_node()`), using a TTL-cached result (default 300 seconds) to minimize API calls. This requires the `planner-gpu-reader` ClusterRole granting `list` on `nodes`, bound to the `planner-backend` service account. The detection is toggleable via the `PLANNER_DETECT_CLUSTER_GPUS` environment variable and gracefully degrades when the kubernetes package is unavailable or no cluster is accessible. [source: src/planner/cluster/gpu_detector.py:19, 39, 78-91, 100-168, deploy/kubernetes/gpu-reader-rbac.yaml:9]

No authentication middleware is registered on the FastAPI application; the only middleware is `CORSMiddleware` with `allow_origins=["*"]`. All API endpoints are unauthenticated at the application level. Access control relies on network-level isolation (ClusterIP services) and TLS-terminated OpenShift Routes. Administrative database operations use a `DB_ADMIN_PASSWORD` environment variable for application-level password verification rather than standard authentication middleware. [source: src/planner/api/app.py:67-73, deploy/kubernetes/backend.yaml:103-107]

The application recently replaced PostgreSQL with an embedded SQLite database stored on a PersistentVolumeClaim (`planner-data-pvc`, 1Gi), simplifying deployment but limiting horizontal scaling to a single-writer replica. [source: deploy/kubernetes/backend.yaml:39-40, 141-148]

## Data Flows

- **User request flow:** Users interact with the Streamlit UI (port 8501), which communicates with the FastAPI backend (port 8000) over the internal ClusterIP service. External access enters through two OpenShift Routes (`planner` for the UI, `planner-backend` for the API) providing TLS termination. [source: deploy/kubernetes/route.yaml:1, 19, deploy/kubernetes/ui.yaml:56, deploy/kubernetes/backend.yaml:150]
- **LLM inference flow:** The backend dispatches LLM requests to a provider selected by the `LLM_PROVIDER` configuration: the co-deployed Ollama service at `http://ollama:11434` for local inference, an OpenAI-compatible endpoint via the `openai` Python SDK (configurable `OPENAI_BASE_URL`), or Google Vertex AI via GCP credentials. Each provider is authenticated independently via optional secrets. [source: deploy/kubernetes/backend.yaml:54, 84-95, src/planner/llm/openai_client.py:28-40]
- **GPU detection flow:** The backend queries the Kubernetes API (`CoreV1Api.list_node()`) to read `nvidia.com/gpu.product` labels from cluster nodes, mapping them to canonical GPU names for capacity planning. Results are cached with a configurable TTL (default 300s). This uses the `planner-backend` service account with a ClusterRoleBinding granting `list` on `nodes`. [source: src/planner/cluster/gpu_detector.py:39, 88-91, deploy/kubernetes/gpu-reader-rbac.yaml:9, 20]
- **Data persistence flow:** Benchmark data and deployment state are stored in an embedded SQLite database at `/app/db/planner.db`, backed by a PersistentVolumeClaim. Database uploads and resets are controlled via the `/api/v1/db/*` endpoints with `DB_ADMIN_PASSWORD` verification. [source: deploy/kubernetes/backend.yaml:39-40, 141-148]
- **Security context:** No authentication middleware is registered on the FastAPI application. The 6 secret references (HF_TOKEN, OPENAI_API_KEY, DB_ADMIN_PASSWORD, MODEL_CATALOG_TOKEN, Vertex AI credentials) are consumed as environment variables from the `planner-secrets` Opaque secret. The OpenShift Service CA bundle is mounted at `/etc/pki/service-ca` for platform TLS trust. [source: src/planner/api/app.py:67-73, deploy/kubernetes/backend.yaml:42-107, deploy/kubernetes/service-ca-configmap.yaml:11]
