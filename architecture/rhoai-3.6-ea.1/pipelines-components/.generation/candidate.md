## Purpose

**Short**: A Python init container and Kubeflow Pipelines component library that packages reusable ML pipeline stages (data processing, training, evaluation, deployment) and stages pre-compiled pipeline YAMLs for the KFP API server. [source: Dockerfile.konflux.pipelines-components:25, scripts/init_managed_pipelines/init_managed_pipelines.py:1-53, pyproject.toml:6-8]

**Detailed**: pipelines-components is a Python package (`kfp-components`) that provides a library of reusable Kubeflow Pipelines (KFP) components and pre-assembled pipelines for RHOAI managed pipeline workflows. The components span data processing (dataset download, document parsing and chunking, AutoML data loading), model training (fine-tuning with InstructLab, AutoGluon tabular training), evaluation (Eval Hub via KServe), and deployment (KServe model serving, Kubeflow Model Registry). The container entrypoint (`scripts.init_managed_pipelines.init_managed_pipelines`) runs as an init container that copies pre-compiled pipeline YAMLs from the image to a shared volume (`/config/managed-pipelines`) consumed by the KFP API server at startup. The repository is synced from the upstream `opendatahub-io/pipelines-components` via auto-merge, with downstream requirements pinned to the RHAI Python Package Index for supply chain control. [source: scripts/init_managed_pipelines/init_managed_pipelines.py:1-53, Dockerfile.konflux.pipelines-components:1-25, pyproject.toml:6-17, requirements.txt:1]

## Architectural Analysis

pipelines-components follows an init-container-plus-library pattern common in KFP-based platforms. At build time, the Konflux Dockerfile compiles pipeline definitions from Python DSL into portable YAML artifacts and bundles them into the container image. At runtime, the init container copies these pre-built YAMLs to a shared volume that the KFP API server mounts, enabling managed pipeline registration without requiring the API server to compile pipelines itself. When the `RELATED_IMAGE_*` environment variables are set (indicating an operator-managed deployment), the init container recompiles pipelines to substitute image references, ensuring disconnected or operator-pinned image registries are honored. [source: scripts/init_managed_pipelines/init_managed_pipelines.py:36-49, Dockerfile.konflux.pipelines-components:23-25]

The component library is organized by pipeline stage: data processing components handle dataset download, document parsing/chunking (with optional Ray-based distributed processing via CodeFlare SDK), and AutoML data loading from S3-compatible storage. Training components wrap InstructLab for supervised fine-tuning (SFT, LoRA, ORPO variants) and AutoGluon for tabular ML. Evaluation routes through Eval Hub with KServe-based model serving, and deployment components register models in the Kubeflow Model Registry. Each component is a KFP `@dsl.component` decorated function that runs inside a pipeline step container. [source: components/data_processing/parse_and_chunk/component.py:568-582, components/data_processing/automl/tabular_data_loader/component.py:1-10, pipelines/training/finetuning_evalhub/sft_minimal/pipeline.py:1-9]

Authentication is delegated to Kubernetes service account tokens: pipeline step containers call `load_incluster_config()` for K8s API access, and external storage credentials (AWS keys, HuggingFace tokens) are injected as environment variables from pipeline parameters or Kubernetes Secrets. The component does not expose HTTP endpoints or define Kubernetes Services — it is a batch-oriented init container and library, not a long-running service. [source: components/data_processing/parse_and_chunk/component.py:571-574, pipelines/training/finetuning_evalhub/sft_minimal/pipeline.py:87-92]

## Data Flows

- **Init container flow:** At pod startup, the init container reads pre-compiled pipeline YAMLs from `/app` and copies them to the shared volume at `/config/managed-pipelines`. When `RELATED_IMAGE_*` environment variables are present, it recompiles pipeline definitions to substitute operator-pinned image references before staging. The KFP API server then reads these YAMLs to register managed pipelines. [source: scripts/init_managed_pipelines/init_managed_pipelines.py:20-49]
- **Pipeline execution flow:** During pipeline runs, individual KFP component steps execute in separate containers. Data processing components fetch datasets from S3-compatible storage (via boto3) or HuggingFace Hub, writing intermediate artifacts to PVC-backed workspace volumes. The parse-and-chunk component optionally submits distributed RayJobs via CodeFlare SDK using in-cluster Kubernetes credentials. Training components produce model artifacts on the workspace PVC, which evaluation and deployment components consume. [source: components/data_processing/automl/tabular_data_loader/component.py:1-10, components/data_processing/parse_and_chunk/component.py:568-599, pipelines/training/finetuning_evalhub/sft_minimal/pipeline.py:30-44]
- **Credential flow:** S3 credentials (AWS_SECRET_ACCESS_KEY, S3_SECRET_KEY), HuggingFace tokens (HF_TOKEN), and LLM API keys (LLM_API_KEY) are injected as environment variables into pipeline step containers. Kubernetes API access uses in-cluster service account tokens via `load_incluster_config()`. [source: components/data_processing/parse_and_chunk/component.py:571-574, components/data_processing/automl/tabular_data_loader/component.py:90]
