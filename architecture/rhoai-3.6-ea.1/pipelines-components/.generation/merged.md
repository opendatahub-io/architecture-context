**Detailed**: pipelines-components provides a library of KFP (Kubeflow Pipelines) pipeline components covering data processing (document parsing, chunking, tabular data loading, synthetic data generation), model training (AutoML via AutoGluon, AutoRAG template optimization), model evaluation (lm-eval), model deployment, and dataset download. Each component is a Python function decorated with `@dsl.component` that runs as an individual pod in a KFP pipeline execution. Components interact with S3-compatible storage via boto3, the Kubernetes API for resource operations and in-cluster auth, and the CodeFlare SDK for distributed Ray job orchestration. ## Architectural Analysis

pipelines-components follows a library-of-components pattern where each pipeline step is a self-contained Python function decorated with `@dsl.component`. Components are organized by lifecycle stage: `data_processing` (tabular data loading, document parsing and chunking, synthetic data generation), `training` (AutoML, AutoRAG), `evaluation` (lm-eval), `deployment` (model deployment), and `dataset_download`. Each component runs in its own pod during KFP pipeline execution, receiving inputs and producing outputs through the KFP artifact system.

The repository's primary deployable artifact is an init container built from `Dockerfile.konflux.pipelines-components`. At build time, the image pre-compiles managed pipeline YAMLs via `scripts.generate_managed_pipelines`. At runtime, the init container copies these YAMLs to a shared volume at `/config/managed-pipelines` that the KFP API server mounts, enabling managed pipeline discovery without runtime compilation. This is a one-shot filesystem copy operation with no HTTP server, no long-running process, and no exposed network ports. [source: scripts/init_managed_pipelines/init_managed_pipelines.py:37-49, Dockerfile.konflux.pipelines-components:23-25]

The component library depends on three external platform services: S3-compatible object storage (via boto3 with credential-based auth from environment variables), the Kubernetes API (via the Python kubernetes client with in-cluster service account auth), and the CodeFlare SDK for submitting distributed Ray jobs from the parse-and-chunk, model training, evaluation, and deployment components. All outbound authentication is credential-based; the init container itself requires no inbound authentication as it performs only local filesystem operations. [source: components/data_processing/automl/tabular_data_loader/component.py:159-164, components/data_processing/parse_and_chunk/component.py:568-576, requirements.txt:1]
