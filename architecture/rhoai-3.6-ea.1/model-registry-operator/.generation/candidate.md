## Purpose

**Short**: Kubernetes operator that manages the lifecycle of ModelRegistry, Catalog, and AIHub custom resources, provisioning model-registry service instances with kube-rbac-proxy authentication, PostgreSQL storage, and Gateway API or OpenShift Route ingress. [source: cmd/modelregistry.go:169, internal/controller/modelregistry_controller.go:282, internal/controller/modelcatalog_controller.go:183]

**Detailed**: The model-registry-operator is a controller-runtime-based Kubernetes operator that reconciles three CRDs — ModelRegistry (v1alpha1/v1beta1), Catalog (v1alpha1), and AIHub (v1alpha1) — to provision and manage model registry service instances within the RHOAI platform. For each ModelRegistry CR, the operator creates a Deployment running the model-registry proxy backed by either PostgreSQL or MySQL storage, with an optional kube-rbac-proxy sidecar that enforces SubjectAccessReview-based authorization on the HTTPS port. The operator manages the full resource lifecycle including Services, ServiceAccounts, RBAC Roles/Bindings, Secrets, NetworkPolicies, and ingress resources (Gateway API HTTPRoutes or OpenShift Routes depending on cluster capabilities). The ModelCatalog reconciler similarly provisions a centralized catalog service with its own PostgreSQL instance. The operator detects cluster capabilities at startup — including OpenShift APIs, BYOIDC mode (where user.openshift.io is absent), Gateway API availability, and the platform Auth CRD — to conditionally create platform-specific resources. [source: internal/controller/util.go:36-39, internal/controller/config/defaults.go:197-211, internal/controller/config/templates/deployment.yaml.tmpl:220-272]

## Architectural Analysis

The model-registry-operator follows a multi-controller pattern with two primary reconcilers — `ModelRegistryReconciler` and `ModelCatalogReconciler` — sharing common resource-management utilities for proxy configuration, RBAC, and ingress. Both controllers use Go templates embedded in `internal/controller/config/templates/` to render Kubernetes manifests, enabling a declarative approach to managed workload configuration.

**Authentication architecture.** Each managed model-registry instance optionally deploys a kube-rbac-proxy sidecar container that terminates TLS and enforces Kubernetes SubjectAccessReview authorization. The proxy checks whether the caller has `get` access to the Service resource in the target namespace, effectively delegating access control to Kubernetes RBAC. This pattern allows namespace-scoped access control through standard RoleBindings (e.g., `registry-user-{registry-name}` grants the `{registry-name}-users` group access to endpoints and services). The operator also creates auth-delegator ClusterRoleBindings for each registry instance. [source: internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-config.yaml.tmpl:17-23, internal/controller/config/templates/deployment.yaml.tmpl:220-272]

**Platform-adaptive ingress.** The operator implements a dual ingress strategy: Gateway API HTTPRoutes for clusters with gateway-api support and OpenShift Routes for backward compatibility. HTTPRoutes reference a configurable Gateway (defaulting to `data-science-gateway`) with path-prefix-based routing and URL rewriting, while Routes provide direct TLS-terminated HTTPS access. The backend port selection is conditional — routing through the kube-rbac-proxy port (typically 8443) when configured, otherwise directly to the rest-container port. [source: internal/controller/config/templates/gateway/gateway-httproute.yaml.tmpl:16-38, internal/controller/modelregistry_oauth.go:73-76]

**Cluster capability detection.** At startup, the operator probes the Kubernetes discovery API to detect available platform features (OpenShift routes, user API, config API, platform Auth CRD), stored in a `ClusterCapabilities` struct. This enables graceful degradation across OpenShift, BYOIDC-enabled OpenShift 4.20+, and plain Kubernetes. The operator reads the cluster-level `config.openshift.io/v1/Ingress` resource to determine the default application domain for Route hostnames. [source: internal/controller/util.go:30-39, internal/setup/setup.go:80-91, internal/controller/config/defaults.go:196-211]

**TLS security posture.** The operator reads the OpenShift cluster TLS security profile via `controller-runtime-common` and applies it to webhook and metrics server TLS configuration, ensuring alignment with cluster-wide TLS policy. The Konflux build uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS-compliant dynamic linking against OpenSSL. [source: internal/setup/setup.go:93-129, Dockerfile.konflux:22]

**CRD version migration.** The operator manages CRD version migration from v1alpha1 to v1beta1 for ModelRegistry via a `StorageVersionMigration` strategy, ensuring backward compatibility during API evolution. The conversion webhook at `/convert` handles live request translation between API versions. [source: internal/migration/svm_strategy.go:122, config/crd/patches/webhook_in_modelregistries.yaml:3]

## Data Flows

- **API request path:** External clients access model-registry instances through Gateway API HTTPRoutes or OpenShift Routes. HTTPRoutes match path prefix `/model-registry/{registry-name}/` and rewrite URLs before forwarding to the backend Service, which targets either the kube-rbac-proxy sidecar (port 8443, TLS-terminated with SubjectAccessReview authorization) or the rest-container directly (port 8080). The kube-rbac-proxy proxies authorized requests to `http://127.0.0.1:{rest-port}/` on the loopback interface. [source: internal/controller/config/templates/gateway/gateway-httproute.yaml.tmpl:22-38, internal/controller/config/templates/deployment.yaml.tmpl:222-224]
- **Operator control plane:** The operator watches ModelRegistry and Catalog CRs and reconciles the full resource graph — Deployments, Services, ServiceAccounts, Secrets, ConfigMaps, RBAC bindings, NetworkPolicies, and ingress resources. It communicates exclusively with the Kubernetes API server over HTTPS/WSS using its ServiceAccount token, secured by the `model-registry-operator-manager-role` ClusterRole. [source: internal/controller/modelregistry_controller.go:282-304, internal/controller/modelcatalog_controller.go:1353-1361]
- **Data storage:** Each model-registry instance connects to a PostgreSQL or MySQL database with configurable connection parameters including SSL/TLS certificates, keys, and root CA bundles mounted from Secrets and ConfigMaps. Database credentials are injected via environment variables from referenced Secrets. [source: internal/controller/config/templates/deployment.yaml.tmpl:40-68, 107-131]
- **Webhook admission:** The operator serves three webhook endpoints — conversion (`/convert`), mutating, and validating — for ModelRegistry resources, enforced via Kubernetes admission webhook configurations with `fail` failure policy. [source: config/webhook/manifests.yaml:2-31, internal/webhook/modelregistry_webhook.go:57-110]
