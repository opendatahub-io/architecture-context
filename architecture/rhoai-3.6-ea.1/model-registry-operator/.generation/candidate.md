## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry and Model Catalog instances on RHOAI, provisioning per-instance deployments with PostgreSQL backends, kube-rbac-proxy authentication sidecars, Gateway API HTTPRoutes, and OpenShift Routes. [source: cmd/modelregistry.go:169, internal/controller/modelregistry_oauth.go:48-99, internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-config.yaml.tmpl:17-23]

**Detailed**: The model-registry-operator watches `ModelRegistry` custom resources (API group `modelregistry.opendatahub.io`, versions v1alpha1 and v1beta1) and reconciles per-instance deployments for both the Model Registry REST service and the Model Catalog. Each registry instance consists of a REST API deployment with a kube-rbac-proxy sidecar for authentication, a PostgreSQL deployment for metadata storage, and associated RBAC, networking, and ingress resources. The operator supports two ingress modes: OpenShift Routes (with TLS) and Gateway API HTTPRoutes through the `data-science-gateway`. Authentication on data-plane endpoints is enforced by kube-rbac-proxy using Kubernetes SubjectAccessReview, requiring `services:get` permission scoped to the registry's namespace and service name. The operator reads the OpenShift cluster Ingress configuration to discover the default domain for Route hostnames, and supports CRD version migration between v1alpha1 and v1beta1 via StorageVersionMigration resources. Admission webhooks validate and mutate `ModelRegistry` CRs, and a conversion webhook handles multi-version API serving. [source: api/v1alpha1/modelregistry_types.go:157, 440, internal/controller/modelregistry_oauth.go:48-99, internal/controller/config/defaults.go:196-211, internal/migration/svm_strategy.go:116-134]

## Architectural Analysis

The model-registry-operator follows a dual-reconciler architecture. The `ModelRegistryReconciler` watches the primary `ModelRegistry` CR and owns the per-instance resource graph: REST API deployment, PostgreSQL deployment, Services, ServiceAccounts, Roles, RoleBindings, NetworkPolicies, and ingress resources. The `ModelCatalogReconciler` manages a parallel set of resources for the Model Catalog component, including its own deployment, PostgreSQL backend, and RBAC configuration. Both reconcilers share proxy lifecycle methods for kube-rbac-proxy and OpenShift Route management. [source: internal/controller/modelregistry_oauth.go:32-99, internal/controller/modelcatalog_controller.go:183, 518]

Authentication is layered: health and readiness probes on ports 8081 and 8080 are intentionally unauthenticated, while data-plane access through port 8443 is protected by a kube-rbac-proxy sidecar. The proxy delegates authorization via Kubernetes SubjectAccessReview, checking whether the caller holds `services:get` permission for the specific registry service in its namespace. This design ties data-plane access to the existing Kubernetes RBAC model without introducing a separate identity provider. [source: internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-config.yaml.tmpl:17-23, internal/controller/modelregistry_oauth.go:48-70]

The operator integrates with platform-level infrastructure in several ways: it reads the `config.openshift.io/v1/Ingress` resource to discover the cluster's apps domain for Route hostname generation, manages Gateway API `HTTPRoute` resources against the `data-science-gateway` for Kubernetes-native ingress, and creates `StorageVersionMigration` resources to orchestrate CRD version upgrades from v1alpha1 to v1beta1. The operator is built with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS-compliant dynamic linking against the system OpenSSL provided by the UBI9 base image. [source: internal/controller/config/defaults.go:196-211, Dockerfile.konflux:22, internal/migration/svm_strategy.go:116-134]

## Data Flows

- **CR-to-workload reconciliation:** A `ModelRegistry` CR submission triggers the `ModelRegistryReconciler`, which provisions a REST API deployment (with kube-rbac-proxy sidecar on port 8443), a PostgreSQL deployment, Services, ServiceAccount, RBAC resources, and ingress objects (OpenShift Route and/or Gateway API HTTPRoute). The `ModelCatalogReconciler` follows a parallel pattern for the Model Catalog component. [source: internal/controller/modelregistry_oauth.go:48-99, internal/controller/modelcatalog_controller.go:183, 518]
- **Data-plane ingress:** External clients reach registry REST APIs through either OpenShift Routes (`{registry-name}-https` on `{registry-name}-rest.{domain}`) or Gateway API HTTPRoutes via the `data-science-gateway`. Both paths terminate at the kube-rbac-proxy sidecar on port 8443, which performs SubjectAccessReview authorization before proxying to the backend REST container on port 8080. [source: internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-config.yaml.tmpl:17-23, internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-https-route.yaml.tmpl:1, internal/controller/config/templates/gateway/gateway-httproute.yaml.tmpl:1]
- **Platform configuration reads:** The operator reads `config.openshift.io/v1/Ingress` to discover the cluster domain for Route hostnames, queries `components.platform.opendatahub.io/v1alpha1/ModelRegistry` and `services.platform.opendatahub.io/v1alpha1/Auth` for platform-level configuration, and creates `StorageVersionMigration` resources for CRD version upgrades. [source: internal/controller/config/defaults.go:196-211, internal/migration/svm_strategy.go:116-134]
- **Security context:** 7 authentication rules and 6 secret references describe enforcement and credential inputs. Health and readiness probes are unauthenticated by design; data-plane access requires kube-rbac-proxy SubjectAccessReview; webhook endpoints use Kubernetes admission authentication; and the operator authenticates to the Kubernetes API via in-cluster ServiceAccount token. [source: cmd/modelregistry.go:169, 287, 291, internal/controller/config/templates/kube-rbac-proxy/kube-rbac-proxy-config.yaml.tmpl:17-23]
