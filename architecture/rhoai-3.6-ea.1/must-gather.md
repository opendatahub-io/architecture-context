## Purpose

**Short**: RHOAI diagnostic data collection tool invoked via `oc adm must-gather` that gathers logs, resource definitions, and configuration from all RHOAI platform components across OpenShift and xKS distributions. [source: collection-scripts/gather.sh:1-246]

**Detailed**: must-gather is a container image built on the OpenShift `ose-must-gather-rhel9` base that packages shell-based collection scripts for every RHOAI platform component. When invoked through `oc adm must-gather`, it runs the `/usr/bin/gather` entrypoint which detects the Kubernetes distribution (OpenShift, AKS, EKS, or CoreWeave), then dispatches parallel collection jobs for each RHOAI component including Data Science Pipelines, KServe/model serving, workbenches, KubeRay, Kueue, training operators, Model Registry, TrustyAI, Feast, MLflow, Spark, AI Gateway, MCP Lifecycle Operator, OGX, and llm-d. [source: collection-scripts/gather.sh:127-217]

Each collection script uses `oc adm inspect` (on OpenShift) or equivalent `kubectl`-based collection (on xKS) to gather namespace resources, pod logs, custom resource instances, and Gateway API/Istio networking resources. The tool also collects cluster-scoped platform CRDs (DSCInitialization, DataScienceCluster, component and service CRs), webhook configurations, ValidatingAdmissionPolicies, and Helm release data. It authenticates using the caller's kubeconfig credentials inherited from the `oc adm must-gather` invocation. [source: collection-scripts/gather.sh:57-98, collection-scripts/common.sh:9-31]

## Architectural Analysis

must-gather follows the standard OpenShift must-gather pattern: a single container image with a `/usr/bin/gather` entrypoint that `oc adm must-gather` launches as a pod on the target cluster. The architecture is dispatch-based — the main `gather.sh` script detects the Kubernetes distribution using node metadata and API availability, then fans out to component-specific collection scripts that run in parallel. This parallel dispatch model allows the tool to collect diagnostic data from 14+ RHOAI components concurrently, with each component collector independently handling its own resource types and namespace discovery. [source: collection-scripts/gather.sh:186-216]

The tool supports two operational modes: OpenShift (using `oc adm inspect`) and xKS (using a custom `kubectl_inspect` function that replicates the inspect behavior). The xKS path includes auto-discovery of all API resources in target namespaces and parallel pod log collection, making it distribution-agnostic. The distribution detection logic in `xks_util.sh` examines infrastructure CRDs, kernel versions, provider IDs, and OS images to classify the cluster as OpenShift, CoreWeave, AKS, EKS, or generic Kubernetes. [source: collection-scripts/llm-d/xks_util.sh:138-179]

The tool has no persistent state, no network services, and no authentication mechanism of its own — it relies entirely on the kubeconfig credentials that the `oc adm must-gather` framework injects into the collection pod. Its security surface is limited to read-only Kubernetes API access for resource and log collection. [source: collection-scripts/common.sh:19-31]

## Data Flows

- **Collection flow:** An SRE or support engineer runs `oc adm must-gather --image=<must-gather-image>`. OpenShift launches a pod with the must-gather image, injecting the caller's kubeconfig. The `/usr/bin/gather` entrypoint detects the Kubernetes distribution, then dispatches parallel collection scripts that use `oc adm inspect` or `kubectl get` to read resource definitions, pod logs, events, and CRD instances from target namespaces. Collected data is written to a local filesystem directory (`/must-gather/`), which is then copied back to the caller's workstation by the must-gather framework.
