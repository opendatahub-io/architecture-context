**Detailed**: Data Science Pipelines is a multi-component Kubernetes application that manages ML pipeline definitions, executions, and artifacts. The central component is the `ml-pipeline` API server, a Go application that exposes both gRPC services (PipelineService, RunService, ExperimentService, and 7 others) and REST endpoints for pipeline upload, health checks, artifact retrieval, and webhook admission. The API server authenticates incoming requests via Kubernetes TokenReview (`authentication/v1`) and enforces per-resource authorization via SubjectAccessReview (`authorization/v1`), with each service account scoped to a dedicated RBAC role. Supporting controllers include the persistence agent (synchronizes workflow state), the scheduled workflow controller (manages cron-triggered pipeline runs), the cache server (mutating webhook for execution caching), and the viewer CRD controller (manages visualization deployments). Pipeline artifacts are stored in S3-compatible object storage via the AWS SDK v2, and pipeline metadata flows through an Envoy-proxied gRPC metadata store. The Konflux build for the API server uses Go's native FIPS 140 module (`GOFIPS140=v1.0.0`) with CGO dynamic linking and explicitly excludes OpenSSL (`-tags no_openssl`). ## Architectural Analysis

Data Science Pipelines follows a microservices pattern where the `ml-pipeline` API server acts as the central control plane, fronting 10 gRPC services behind a grpc-gateway reverse proxy and serving additional REST routes for pipeline upload and artifact retrieval. Request authentication is performed by a `TokenReviewAuthenticator` that extracts bearer tokens from request headers and validates them against the Kubernetes TokenReview API, with configurable audience validation. Authorization is enforced per-resource through `SubjectAccessReview` calls, ensuring that each API operation is checked against the caller's Kubernetes RBAC permissions. This two-layer authentication/authorization model delegates identity verification entirely to the Kubernetes API server rather than implementing application-level credential stores. [source: backend/src/apiserver/auth/authenticator_token_review.go:47-57, 77-89, backend/src/apiserver/resource/resource_manager.go:2310-2339]

The system relies on several supporting controllers, each deployed as a separate Deployment with its own service account and narrowly scoped RBAC role. The persistence agent watches Argo Workflow resources and synchronizes execution state back to the pipeline store. The scheduled workflow controller reconciles `ScheduledWorkflow` CRDs to trigger pipeline runs on cron schedules. The cache server implements a mutating admission webhook on port 8443 that intercepts pod creation to enable execution caching, backed by its own TLS certificate (`webhook-server-tls`). The viewer CRD controller manages `Viewer` custom resources by creating backing Deployments and Services for visualization workloads. [source: manifests/kustomize/base/pipeline/ml-pipeline-persistenceagent-deployment.yaml:1, manifests/kustomize/base/pipeline/ml-pipeline-scheduledworkflow-deployment.yaml:1, manifests/kustomize/env/cert-manager/platform-agnostic-k8s-native/patches/validating-webhook.yaml:1]

Object storage integration uses the AWS SDK v2 S3 client with configurable endpoints, path-style addressing, and static or default credential chains, making it compatible with MinIO, SeaweedFS, or any S3-compatible backend. The TLS configuration utility loads system certificate pools and supports custom CA bundles, but does not set explicit cipher suites or minimum TLS versions — relying on Go's defaults, which respect the FIPS module when `GOFIPS140` is active at build time. The Konflux build chain uses `GOFIPS140=v1.0.0` with `-tags no_openssl`, selecting Go's native FIPS 140 cryptographic module rather than OpenSSL for FIPS compliance. ## Data Flows

- **API request flow:** Clients submit pipeline operations via gRPC or REST to the `ml-pipeline` service (ports 8443, 8887, 8888). The API server authenticates each request by extracting a bearer token from the request header and validating it via a Kubernetes `TokenReview` call to `authentication/v1`. Once authenticated, per-resource authorization is enforced through `SubjectAccessReview` calls to `authorization/v1`, checking the caller's permissions against the requested pipeline resource. [source: backend/src/apiserver/auth/authenticator_token_review.go:47-57, 77-89, backend/src/apiserver/resource/resource_manager.go:2323-2332]
- **Pipeline artifact storage:** Pipeline artifacts and logs are stored in S3-compatible object storage via the AWS SDK v2 client, which constructs an S3 client with a configurable endpoint URL, path-style addressing, and either static credentials (from the `mlpipeline-minio-artifact` secret) or the default AWS credential chain. [source: backend/src/apiserver/client_manager/client_manager.go:1044-1057]
- **Metadata flow:** Pipeline metadata is served through a metadata-envoy-service (port 9090) proxying to a metadata-grpc-service (port 8080). A VirtualService routes metadata-grpc traffic to the envoy sidecar. The metadata-writer deployment watches Argo Workflow resources and writes execution metadata to the metadata store. [source: manifests/kustomize/base/metadata/base/metadata-envoy-service.yaml:1, manifests/kustomize/base/metadata/base/metadata-grpc-service.yaml:1, manifests/kustomize/base/metadata/options/istio/virtual-service.yaml:1]
- **Execution caching:** The cache-server deployment runs a mutating admission webhook on port 443 (targeting `webhook-api`) that intercepts pod creation to check whether a pipeline step's inputs match a cached result, enabling execution skipping. The webhook TLS is backed by the `webhook-server-tls` secret. [source: manifests/kustomize/base/cache/cache-service.yaml:1, manifests/kustomize/env/cert-manager/platform-agnostic-k8s-native/patches/mutating-webhook.yaml:1]
- **Controller reconciliation:** The viewer CRD controller watches `Viewer` custom resources and reconciles backing Deployments and Services. The scheduled workflow controller watches `ScheduledWorkflow` CRDs and creates Argo Workflow resources on cron schedules. Both controllers use in-cluster ServiceAccount tokens with scoped RBAC roles. [source: manifests/kustomize/base/pipeline/ml-pipeline-scheduledworkflow-deployment.yaml:1, manifests/kustomize/base/pipeline/ml-pipeline-viewer-crd-role.yaml:1]
