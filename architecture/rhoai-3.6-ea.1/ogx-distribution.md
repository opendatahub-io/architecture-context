## Purpose

**Short**: OGX distribution is a Red Hat-customized build of the OGX (formerly llama-stack) AI agent gateway that exposes multi-provider inference, RAG, and agentic APIs over HTTP on port 8321. [source: distribution/config.yaml:257, distribution/entrypoint.sh:79]

**Detailed**: ogx-distribution packages the OGX framework as a containerized Python service for RHOAI. It acts as a unified AI agent gateway that routes inference requests to configurable remote providers (vLLM, AWS Bedrock, IBM WatsonX, Azure, Vertex AI, OpenAI, Gemini, Anthropic), provides vector I/O through Milvus, PGVector, or Qdrant backends, and offers tool runtime capabilities including web search and file operations. The distribution uses PostgreSQL for both key-value and SQL-backed persistence of agent state, conversations, batches, and metadata. Authentication is handled via OAuth2 token validation with JWKS when configured. The container image is built on an AIPCC base image with Python dependencies installed from the RHEL AI Python Package Index via Hermeto-prefetched packages, and ships pre-fetched Docling and embedding model artifacts. [source: distribution/config.yaml:1-280, Dockerfile.konflux:1-58, distribution/entrypoint.sh:1-79]

## Architectural Analysis

OGX distribution follows a provider-plugin architecture where each API capability (inference, vector I/O, tool runtime, files, batches, responses, messages) is backed by one or more configurable providers. Providers are conditionally activated via environment variable guards (e.g., `${env.VLLM_URL:+vllm-inference}`), meaning the running configuration adapts to the deployment context without code changes. The distribution strips several inline providers (docling, faiss, milvus-inline, sentence-transformers) from the upstream build configuration, shipping only remote-capable providers suitable for production multi-worker deployments. [source: distribution/config.yaml:4-12, build/build.yaml:1-5]

The entrypoint resolves secret environment variables from `_FILE`-suffixed paths before launching the `ogx run` command, supporting Kubernetes secret volume mounts as an alternative to direct environment variable injection. This pattern avoids exposing secrets via `/proc/1/environ`. OpenTelemetry instrumentation is conditionally enabled when `OTEL_SERVICE_NAME` is set, exporting traces and metrics via OTLP. [source: distribution/entrypoint.sh:1-79]

Authentication is opt-in: when `AUTH_ISSUER` is configured, the server validates OAuth2 bearer tokens against a JWKS endpoint with configurable TLS verification and audience checking. The access policy implements resource-level authorization with owner-based isolation — authenticated users can create resources, and only owners can modify or delete them. System resources (unowned) are readable by all authenticated users. [source: distribution/config.yaml:259-280]

Storage is centralized on PostgreSQL with two backend types: `kv_postgres` for key-value stores (registry metadata, agent state, vector store namespaces) and `sql_postgres` for relational data (inference logs, conversations, batches, file metadata, connectors). This dual-backend pattern allows the framework to use the appropriate access pattern for each data type while sharing a single database instance. [source: distribution/config.yaml:198-235]
