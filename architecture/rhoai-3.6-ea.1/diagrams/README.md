## Diagram Descriptions

### Component Dependency Graph
Shows how platform components depend on each other based on the explicit dependency tree (rhods-operator as root, kserve as central serving node) and integration patterns (CRD-based orchestration, Gateway API routing, kube-rbac-proxy sidecar, Kuadrant policy integration). Color coding: red = platform root, blue = serving stack, green = ODH components, purple = llm-d inference, orange = auth infrastructure, gray = external dependencies.

### Platform Network Topology
Complete network architecture showing all ingress points (data-science-gateway, maas-default-gateway, OpenShift Routes), 7 namespace tiers, 4 authentication patterns, and the multi-generation ingress architecture (Gateway API primary, OpenShift Routes legacy, dual ingress for model-registry). Includes exact port numbers, protocols, encryption, and authentication mechanisms.

**Two formats provided**:
- **Mermaid (.mmd)**: Visual diagram with color-coded trust zones. Great for presentations and architecture discussions.
- **ASCII (.txt)**: Precise text format with no ambiguity. Required for SAR (Security Architecture Review) submissions and compliance documentation. Includes RBAC summary, Istio/service mesh details, TLS configuration, and FIPS posture.

Both formats contain the same information — use Mermaid for visual clarity, ASCII for security reviews.

### Cross-Component Workflows
Sequence diagrams showing 5 end-to-end user workflows:
1. **Model Deployment via Dashboard** — InferenceService creation through admission webhooks, kserve reconciliation, odh-model-controller platform additions, to production inference
2. **Models-as-a-Service API Request** — API key authentication through Kuadrant/Authorino, OPA authorization, maas-api processing, and background model route management
3. **LLM Disaggregated Inference (llm-d)** — LLMInferenceService reconciliation, prefill/decode deployment separation, EPP routing, ModelExpress gRPC KV cache coordination, and KEDA autoscaling
4. **Notebook Workspace Creation** — Notebook CR through workbenches-operator webhook mutation, kubeflow reconciliation, and kube-auth-proxy OIDC route creation
5. **Pipeline Execution** — Pipeline submission through DSP API server, Argo Workflow execution, artifact storage, and scheduled recurring runs

### Platform Security Overview
Visual representation of the 4-pattern authentication architecture: (1) kube-auth-proxy OIDC for dashboard, (2) Kuadrant/Authorino for MaaS and serving, (3) kube-rbac-proxy sidecar for pod-level SubjectAccessReview, (4) application-level TokenReview/SAR. Shows gateway authentication chains (up to 3 layers deep for dashboard), admission webhook inventory (210 total, all Fail policy), cross-component webhook targets, container security patterns (FIPS, UBI 9, TLS profile alignment, non-root), and TLS configuration per enforcement point.

### Platform Observability
Maps monitoring infrastructure deployed by rhods-operator Monitoring service controller. Shows Prometheus scrape targets with kube-rbac-proxy sidecars, ServiceMonitor/PodMonitor creation by odh-model-controller per InferenceService, autoscaling metrics sources (HPA, KEDA ScaledObjects, InferencePool metrics), and health probe patterns. Notes observability gaps: no distributed tracing evidence, no centralized logging pipeline, and incomplete per-component Prometheus endpoint inventory.

### Platform Maturity Dashboard
High-level metrics: 72 components, 19+ operators, 145 CRDs, 210 webhooks, 122 services, 1658 RBAC entries. CRD API maturity ranges from v1alpha1 (majority) through v1/v2 (DSC, DSCI). Security posture: FIPS-compliant builds, platform TLS alignment, conditional mTLS. Deployment readiness: leader election HA for all operators, but disconnected support and multi-architecture (beyond amd64) remain unresolved.
