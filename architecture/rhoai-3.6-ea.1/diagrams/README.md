## Diagram Descriptions

### Component Dependency Graph
Shows how 70 platform components depend on each other, organized into functional groups: Platform Orchestration (rhods-operator), Model Serving Control Plane (kserve, odh-model-controller, MaaS, AI Gateway), LLM Inference Stack (llm-d ecosystem - new in 3.6), ML Pipelines, Training, Development, and Infrastructure. Central components (rhods-operator, kserve) are highlighted with thicker borders. Color coding: red = orchestrator, blue = model serving, orange = LLM stack, green = platform components, teal = new 3.6 capabilities, gray = infrastructure.

### Platform Network Topology
Complete network architecture showing the multi-generation ingress architecture (Gateway API HTTPRoute, Istio VirtualService, OpenShift Routes, Envoy ExtProc) across trust boundaries: External, Ingress (DMZ), Platform Namespace (25+ controllers), User Namespaces (workloads), Mesh Infrastructure, and Egress (K8s API, S3, Container Registries, External LLM Providers).

**Two formats provided**:
- **Mermaid (.mmd)**: Visual diagram with color-coded trust zones. Great for presentations and architecture discussions.
- **ASCII (.txt)**: Precise text format with no ambiguity. Required for SAR (Security Architecture Review) submissions and compliance documentation.

Both formats contain the same information - use Mermaid for visual clarity, ASCII for security reviews.

### Cross-Component Workflows
Four sequence diagrams showing end-to-end user workflows:
1. **Model Deployment via Dashboard** - OAuth2 auth -> dashboard -> kserve webhook -> odh-model-controller mutation -> kserve controller -> model runtime -> gateway -> inference
2. **MaaS Multi-Tenant Model Access** - AIGateway CR -> gateway provisioning -> Kuadrant auth -> subscription governance -> model routing
3. **ML Pipeline Execution** - Pipeline submission -> DSPA stack -> Argo orchestration -> ml-metadata -> optional model deployment
4. **LLM Inference with Intelligent Routing** (new in 3.6) - LLMInferenceService -> vLLM pods + EPP -> KV-cache-aware routing -> disaggregated prefill/decode

### Platform Security Overview
Visual representation of the security architecture including:
- **5 authentication mechanisms**: ServiceAccount tokens (21+ components), OAuth2/OIDC reverse proxy, Kuadrant AuthPolicy, kube-rbac-proxy sidecar, direct bearer tokens
- **30+ admission webhooks** across 16 components (all Fail policy) with cross-component risks (kserve + odh-model-controller pod mutation conflict)
- **3 gateway authentication layers**: MaaS (Kuadrant), data-science-gateway (candidate EnvoyFilter), OpenShift Routes (kube-rbac-proxy)
- **FIPS compliance gap**: 16 Go operators compliant, data plane (vLLM, NeMo-Guardrails, llm-d-router) lacks FIPS signals
- **Container security**: UBI base images, non-root execution, TLS 1.2+ with NIST curves
- **Key RBAC scope**: ai-gateway-operator (57 rules), rhods-operator (19 CRDs), kserve (13 CRDs)

### Platform Observability
Maps all monitoring and observability endpoints:
- **22+ Prometheus scrape targets**: 5 via kube-rbac-proxy (8443/TCP), 17+ on controller-runtime default (8080/TCP)
- **Health probes**: Standard controller-runtime pattern (:8081 healthz/readyz) for 20+ components, custom ports for dashboard and model runtimes
- **Observability gaps**: No centralized trace aggregation, metadata fragmented across model-registry (PostgreSQL), pipelines (database), KServe CRDs (etcd), MLflow — cross-domain queries require manual correlation
- **Webhook health**: 16 webhook servers with Fail policy must be monitored; unavailability blocks K8s API operations

### Platform Maturity Dashboard
High-level metrics: 70 components, 128 CRDs across 30 components, 20+ operators, 25+ controller deployments, 110+ Service resources, mixed CRD API versions (v1alpha1 dominant), partial FIPS/multi-arch/Gateway API coverage, unresolved disconnected support, and inventory of new 3.6-ea.1 capabilities (llm-d ecosystem, AI Gateway, MCP services, feast, mlflow, trainer).
