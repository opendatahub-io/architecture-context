TLS Configuration:
- Server TLS: Optional; controlled by CLI flags (--tls-cert-path, --tls-key-path)
- Client mTLS: Optional; controlled by CLI flags (--tls-client-ca-cert-path)
- Downstream TLS: Per-service configurable via named TLS map in YAML config
  - Each downstream service can have independent cert/key/CA bundles
- Crypto stack: rustls + ring (NOT FIPS-validated)
- OpenSSL: Build stage only (protobuf-src), NOT in release image

RBAC Summary:
- No ClusterRoles or RoleBindings defined
- Orchestrator does NOT enforce authorization
- Authentication is passthrough-based (delegated to downstream services)

Secrets:
- TLS server cert/key (kubernetes.io/tls) - Server TLS, provisioned by platform operator / cert-manager, rotation: unknown
- TLS client CA cert (Opaque) - Server mTLS verification, provisioned by platform operator, rotation: unknown
- API tokens (Opaque / env var) - Downstream service authentication, provisioned by platform operator, rotation: unknown
- Downstream TLS certs (Opaque) - Downstream service TLS clients, provisioned by platform operator, rotation: unknown

Authentication & Authorization:
- /api/v1/*, /api/v2/* (POST): Header passthrough, application-level filtering
  - Configured headers forwarded to downstream services
  - X-Forwarded-Access-Token optionally rewritten to Authorization Bearer
- /health, /info (GET): Unauthenticated
- All endpoints: Optional TLS / mTLS via Rust TLS acceptor

FIPS Compliance:
- ⚠️  NOT FIPS COMPLIANT
- ring is explicitly selected as cryptographic provider (not FIPS-validated)
- OpenSSL present only in build stage, not in release image
- Service cannot claim FIPS compliance for TLS operations
