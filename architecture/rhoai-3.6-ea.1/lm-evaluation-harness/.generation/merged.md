## Purpose

**Short**: lm-evaluation-harness provides a batch-oriented evaluation runtime for language models within RHOAI, executing benchmarks against OpenAI-compatible model serving endpoints and reporting results through the EvalHub framework. [source: main.py:2, Dockerfile.konflux.lmes-job:47, pyproject.toml:11]

**Detailed**: lm-evaluation-harness is a Red Hat downstream fork of the EleutherAI lm-evaluation-harness framework, packaged as a container job image (`odh-ta-lmes-job-rhel9`) for the RHOAI platform. It provides a standardized, secure runtime for batch language model evaluation workloads. [source: Dockerfile.konflux.lmes-job:44-48, pyproject.toml:6-11]

The component operates as an EvalHub `FrameworkAdapter`, receiving job specifications that define a benchmark, a model endpoint, and evaluation parameters. It connects to OpenAI-compatible model serving endpoints (such as vLLM or KServe inference services) using the `local-completions` backend, sends prompts, and collects model responses for scoring. Evaluation results are computed using the lm-eval framework's pipeline with support for Unitxt task integration, few-shot prompting, and chain-of-thought reasoning. [source: main.py:619-764, main.py:532-616]

Authentication to model endpoints is resolved through the EvalHub credential framework (`resolve_model_credentials`), while HuggingFace Hub access for gated datasets uses `HF_TOKEN` sourced from model auth secrets. The job supports disconnected/air-gapped deployments through automatic offline mode detection when local tokenizer and dataset files are present under `/test_data`. [source: main.py:680-690, main.py:166-226]

## Architectural Analysis

lm-evaluation-harness follows a job-oriented batch architecture. The container image packages the EleutherAI lm-eval framework with Red Hat-specific adaptations, centered on an EvalHub adapter (`main.py:LMEvalAdapter`) that bridges the evaluation framework with the RHOAI platform's job orchestration infrastructure. The adapter translates EvalHub `JobSpec` configurations into lm-eval `simple_evaluate` calls, using the `local-completions` backend to communicate with OpenAI-compatible model endpoints via HTTP. [source: main.py:619-764, main.py:532-616]

The component does not expose any HTTP endpoints, gRPC services, or Kubernetes Services—it runs as a one-shot batch pod created by the platform's evaluation orchestration layer. All model inference is delegated to external serving endpoints, making the harness a pure evaluation client. Error messages are sanitized to prevent credential leakage in callback responses, with redaction covering Bearer tokens, API keys, passwords, and URL credentials. [source: main.py:289-333]

Two Dockerfiles produce the job image: `Dockerfile.konflux.lmes-job` (Konflux CI) and `Dockerfile.lmes-job` (development), both using parameterized base images (CUDA and CPU variants) and running as non-root user 65532. The container installs the `api`, `ifeval`, `math`, and `ibm_watsonx_ai` optional dependency groups, enabling support for API-based model evaluation, instruction-following evaluation (IFEval), mathematical reasoning, and IBM WatsonX AI integration. [source: Dockerfile.konflux.lmes-job:1-42, pyproject.toml:65-83]

The job supports disconnected operation: when `parameters.tokenizer` points to a local path under `/test_data` and co-located dataset bundles are detected, the adapter automatically sets HuggingFace offline environment variables to prevent network calls to the Hub. This air-gap pattern allows evaluations on clusters without external connectivity, provided models and datasets are pre-staged. [source: main.py:166-226]

## Data Flows

- **Evaluation job lifecycle:** The EvalHub service dispatches a `JobSpec` to the adapter. The adapter resolves model credentials, configures the `local-completions` backend with the target model endpoint URL, and executes `simple_evaluate` from the lm-eval framework. Status callbacks are reported through EvalHub SDK phases: INITIALIZING → LOADING_DATA → RUNNING_EVALUATION → POST_PROCESSING. Results are returned as `EvaluationResult` objects to the EvalHub callbacks. [source: main.py:643-773, main.py:228-241]
- **Model inference flow:** During evaluation, the harness sends prompts to an OpenAI-compatible completions endpoint via HTTP/HTTPS using the `local-completions` model backend. The completions URL is constructed from `job_spec.model.url`, appending `/v1/completions` as needed. Authentication uses an API key set via `resolve_model_credentials()`. [source: main.py:566-616, main.py:680-682]
- **External data access:** The harness accesses HuggingFace Hub for datasets and tokenizers (with `HF_TOKEN` for gated resources), and may use S3-compatible storage via boto3 for data retrieval. The `datasets-server.huggingface.co` endpoint is accessed for dataset metadata. In disconnected mode, all Hub access is disabled and local files under `/test_data` are used instead. [source: main.py:686-690, main.py:205-218, lm_eval/tasks/eus_exams/configs.py:10, scripts/s3_downloader.py:2]
- **Security context:** 5 secret references (HF_TOKEN, ANTHROPIC_API_KEY, WATSONX_API_KEY, OPENAI_API_KEY, AWS_SECRET_ACCESS_KEY) are used for outbound authentication to external services. No inbound authentication is required as the component does not expose any endpoints. Error messages are sanitized to redact credentials before callback reporting.
