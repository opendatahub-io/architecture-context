## Purpose

**Short**: lm-evaluation-harness is a batch-oriented Python framework for language model evaluation, packaged as a container image that runs one-shot evaluation jobs orchestrated by the RHOAI platform. [source: Dockerfile.konflux.lmes-job:44-49, pyproject.toml:6-11, 57]

**Detailed**: lm-evaluation-harness provides the EleutherAI lm-eval framework customized for Red Hat OpenShift AI. It is packaged as the `odh-ta-lmes-job-rhel9` container image, designed to be launched as a Kubernetes Job by the TrustyAI service operator. The harness evaluates language models by connecting to external LLM provider APIs (OpenAI, Anthropic, IBM watsonx) and data sources (Hugging Face, S3-compatible storage) using environment variable-based API key authentication. It supports the Unitxt evaluation framework for standardized task definitions and includes optional dependencies for specific evaluation types including ifeval, math verification, and watsonx integration. The component does not expose HTTP endpoints or gRPC services; it is a batch CLI application that produces evaluation results to a local output directory. Two Dockerfile variants exist: `Dockerfile.konflux.lmes-job` for Konflux CI with parameterized CUDA/CPU base images, and `Dockerfile.lmes-job` for development builds using UBI9. ## Architectural Analysis

lm-evaluation-harness is a downstream fork of the EleutherAI evaluation framework, synced from `opendatahub-io/lm-evaluation-harness` via auto-merge on the `stable` branch. The component serves as the evaluation runtime for the RHOAI TrustyAI stack: the TrustyAI service operator creates Kubernetes Jobs using the `odh-ta-lmes-job-rhel9` container image, passing model endpoints and evaluation parameters as environment variables and arguments. The harness itself is stateless and does not manage its own lifecycle within the cluster.

The architecture is plugin-based: LLM backends are registered as model types (`openai`, `anthropic-chat-completions`, `watsonx_llm`, `local-chat-completions`) and authenticate to their respective provider APIs via environment variable API keys (OPENAI_API_KEY, ANTHROPIC_API_KEY, WATSONX_API_KEY, HF_TOKEN). The `local-chat-completions` model type connects to arbitrary OpenAI-compatible endpoints, which in the RHOAI context typically means a model serving runtime (vLLM, Caikit) running within the same cluster. This makes the harness a consumer of the platform's serving infrastructure without direct compile-time coupling to it.

Two Dockerfile variants produce container images: `Dockerfile.konflux.lmes-job` for production Konflux CI builds with parameterized CUDA and CPU base images supporting multi-architecture (amd64, arm64, ppc64le, s390x), and `Dockerfile.lmes-job` for development builds from `ubi9/python-311`. Both install the same pip extras (`api`, `ifeval`, `math`, `ibm_watsonx_ai`) and configure the Unitxt evaluation catalog. The production image runs as non-root user 65532 with restricted permissions. No Kubernetes manifests, Services, or CRDs are defined in this repository; deployment is fully delegated to the operator that creates Jobs from this image.
