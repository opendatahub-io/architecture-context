## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.6-ea.1 is a comprehensive machine learning platform deployed on OpenShift Container Platform via the Operator Lifecycle Manager (OLM). The platform is orchestrated by rhods-operator, which manages a DataScienceCluster custom resource to provision and lifecycle-manage a layered stack of platform services, component operators, and user-facing capabilities spanning model serving, ML pipelines, distributed training, model registry, AI guardrails, and interactive development workbenches.

The platform's ingress architecture is in active transition. Model-serving endpoints primarily use Gateway API HTTPRoutes (via models-as-a-service and model-registry-operator), with conditional Istio VirtualService support for service mesh environments and OpenShift Routes for TLS termination. Authentication is layered: kube-auth-proxy provides OAuth2/OIDC reverse-proxy authentication at gateway ingress surfaces, kube-rbac-proxy sidecars enforce Kubernetes SubjectAccessReview authorization at the pod level for metrics and data-plane endpoints, and Kuadrant AuthPolicy resources provide API key and token validation at the Gateway API routing layer. The MaaS (Models-as-a-Service) subsystem introduces multi-tenant subscription governance with its own authentication policy CRDs.

The security posture is built on OpenShift conventions: most Go components are compiled with `GOEXPERIMENT=strictfipsruntime` for FIPS 140 compliance, containers use Red Hat Universal Base Images (UBI), and operators enforce TLS 1.2+ with NIST-approved cipher suites. The platform watches the OpenShift APIServer TLS security profile and propagates changes via pod restarts. Admission webhooks are pervasive — 16 components register a combined 30+ unique webhook configurations (mutating, validating, and conversion) to enforce CRD invariants and inject platform concerns such as hardware profiles and connection credentials.

### Central Components

**rhods-operator** is the platform orchestrator, managing 19 CRDs spanning DataScienceCluster, DSCInitialization, HardwareProfile, and per-component lifecycle CRDs (Kserve, Ray, Trainer, ModelRegistry, etc.). It is the root of the dependency tree and the sole OLM-installed operator; all other component operators are deployed as its operands.

**kserve** is the model-serving control plane, managing 13 CRDs including InferenceService, LLMInferenceService, InferenceGraph, LocalModelCache, and serving runtimes. It is the most webhook-dense component (6 mutating, 16 validating, 1 conversion) and integrates with Gateway API, kube-rbac-proxy, and llm-d for LLM-optimized serving.

**odh-model-controller** acts as the model-serving integration layer with 8 admission webhooks that intercept KServe InferenceService, LLMInferenceService, InferenceGraph, Pod, and NIM Account resources — creating cross-component coupling with kserve's CRDs.

**odh-dashboard** serves as the unified web console with a federated BFF (Backend-for-Frontend) architecture, providing 10+ domain-specific API sidecars (gen-ai, model-registry, mlflow, agent-ops, eval-hub, maas, automl, autorag) that integrate with nearly every platform component.

**models-as-a-service** provides the multi-tenant API gateway subsystem with 8 CRDs for subscription governance, tenant configuration, and authentication policy enforcement.

**ai-gateway-operator** orchestrates the AI Gateway infrastructure, provisioning Gateway API resources, cert-manager certificates, Kuadrant policies, and Istio configuration for the unified inference ingress.

### Ingress Analysis

The RHOAI 3.6-ea.1 platform exhibits a multi-generation ingress architecture reflecting active migration from Istio VirtualService and OpenShift Route patterns toward Gateway API.

The **MaaS gateway path** is the primary inference ingress for multi-tenant model access. The ai-gateway-operator provisions Gateway API infrastructure and the models-as-a-service controller creates HTTPRoute resources with Kuadrant AuthPolicy for API-key and token-based authentication. The exact Gateway resource, GatewayClass, and data-plane implementation could not be resolved because source checkouts are unavailable in the current generation environment.

The **KServe serving path** conditionally supports both Gateway API (HTTPRoute) and Istio (VirtualService) routing for InferenceService endpoints. The data-science-gateway is expected to be the central ingress point for model serving, with an EnvoyFilter-based ext_authz callout to kube-auth-proxy for user authentication. However, the EnvoyFilter creation, its exact target Service/port, and the kube-auth-proxy contract could not be verified via source inspection. The relationship between kserve's gateway provisioning and odh-model-controller's mutation of InferenceService resources creates a cross-component ingress dependency that is architecturally significant but only partially observable from the structured inventory.

The **OpenShift Route path** remains active for model-registry, TrustyAI, and kube-auth-proxy endpoints. These routes provide TLS termination at the OpenShift router and are directly observed in component manifests.

The **Istio VirtualService path** is used by data-science-pipelines for metadata-grpc service routing and by model-registry for internal service routing. These represent older integration patterns that may coexist with Gateway API routing.

Key unresolved joins: (1) The MaaS default gateway resource and its GatewayClass are not directly observed; they are expected to be created by ai-gateway-operator but source verification was not possible. (2) The EnvoyFilter -> ext_authz -> kube-auth-proxy chain for data-science-gateway is a candidate relationship based on component prose and dependency declarations but has not been source-verified. (3) The relationship between model-registry-operator HTTPRoutes and their parent Gateway is unresolved. Source checkouts were not available at generation time (paths under /data/checkouts are generation-environment artifacts).

## Deployment Architecture

### Deployment Topology

The platform follows a three-tier deployment model. The **operator tier** consists of rhods-operator installed via OLM in its own namespace, managing all component operator lifecycles. The **platform services tier** runs in the platform namespace (redhat-ods-applications) with 25+ controller deployments including kserve-controller-manager, odh-model-controller, kuberay-operator, model-registry-operator, models-as-a-service (maas-api), ai-gateway-operator, odh-dashboard, notebook-controller, and all other component operators. The **user workload tier** runs in user-created data science project namespaces, hosting InferenceService pods, notebook instances, pipeline runs, Ray clusters, training jobs, TrustyAI instances, and model registry instances.

Gateway infrastructure (Envoy proxies, Gateway API data planes) is expected to run in the openshift-ingress or istio-system namespace, though the exact deployment topology depends on the cluster's Gateway API and service mesh configuration.

## Platform Architectural Analysis

RHOAI 3.6-ea.1 is architecturally defined by three cross-cutting tensions that shape its design trade-offs and operational characteristics.

**Tension 1: Centralized orchestration vs. component autonomy.** The rhods-operator provides a single-pane DataScienceCluster CR for platform lifecycle, yet each component operator (kserve, data-science-pipelines-operator, model-registry-operator, etc.) maintains its own CRD hierarchy, RBAC requirements, and reconciliation loops. This creates a two-level control plane where the platform operator must encode knowledge of every component's configuration surface. The RBAC footprint is substantial — ai-gateway-operator alone declares 57 RBAC rules spanning Gateway API, cert-manager, Kuadrant, Istio, MaaS, llm-d, KServe, and OpenTelemetry. A missing or incompatible dependency can cascade through these broad RBAC requirements. The platform mitigates this through rhods-operator's FeatureTracker CRD and conditional component enablement, but the coupling remains architecturally significant.

**Tension 2: Webhook density vs. API server latency.** With 16 components registering 30+ unique webhook configurations, the admission control surface is the densest observed in any platform version. The cross-component webhook pattern — where odh-model-controller intercepts kserve's InferenceService, LLMInferenceService, InferenceGraph, and core Pod resources — creates runtime coupling that is invisible in the CRD dependency graph. Both kserve and odh-model-controller register pod-mutating webhooks, and their ordering (determined alphabetically by webhook name) could produce conflicting sidecar injection if not carefully coordinated. All webhooks use Fail failure policy, meaning webhook server unavailability blocks the affected API operations cluster-wide.

**Tension 3: Multi-generation ingress architecture.** The platform simultaneously supports Gateway API HTTPRoute (models-as-a-service, model-registry-operator, ai-gateway-operator), Istio VirtualService (data-science-pipelines, model-registry, kserve InferenceGraph), and OpenShift Routes (model-registry-operator, trustyai-service-operator, kube-auth-proxy). This reflects an active migration toward Gateway API as the primary ingress mechanism, but the coexistence creates operational complexity: different components use different authentication enforcement points (Kuadrant AuthPolicy at the Gateway layer, kube-rbac-proxy sidecars at the pod layer, kube-auth-proxy reverse proxy at the route layer), and the relationships between these layers are not consistently observable from the structured inventory.

**LLM inference stack evolution.** The 3.6-ea.1 release introduces a significant new inference architecture layer with llm-d and its ecosystem (llm-d-router, llm-d-kv-cache, llm-d-latency-predictor, llm-d-routing-sidecar, llm-d-async, llm-d-batch-gateway-operator, llm-d-inference-payload-processor). This stack implements disaggregated prefill/decode, KV-cache-aware routing, and latency-predicted endpoint selection — capabilities that operate alongside but architecturally distinct from the traditional KServe InferenceService model. The integration point is KServe's LLMInferenceService CRD and the gateway-api-inference-extension's InferencePool/InferenceModel CRDs, which bridge KServe's lifecycle management with llm-d's intelligent routing.

**AI Gateway consolidation.** The ai-gateway-operator, models-as-a-service, and ai-gateway-payload-processing components together form a unified AI Gateway subsystem that abstracts internal model serving (via KServe) and external provider access (via ExternalProvider/ExternalModel CRDs bridging OpenAI, Anthropic, AWS Bedrock, Azure, and Vertex AI APIs) behind a common Gateway API surface. This is a significant architectural investment in 3.6-ea.1, creating a single ingress point for all inference traffic with policy-based authentication and subscription governance.

**Observability and metadata fragmentation.** Each operator exposes Prometheus metrics independently (typically on port 8080 or 8443 via kube-rbac-proxy), but there is no platform-level trace aggregation or centralized metadata bus. Model metadata lives in model-registry (PostgreSQL-backed), pipeline metadata in data-science-pipelines (database-backed), serving state in KServe CRDs, and experiment tracking in MLflow. Cross-domain queries (e.g., "which pipeline produced the model currently serving in production?") require manual correlation across these systems.

**FIPS compliance gap.** While most Go operators achieve FIPS 140 compliance via strictfipsruntime, the model-serving data plane — vLLM images (upstream Ubuntu/CUDA/ROCm base), NeMo-Guardrails, guardrails-detectors, and the llm-d-router EPP — operates without FIPS signals. Since these components handle the actual inference request/response data path, this creates a compliance boundary between the FIPS-compliant control plane and the non-FIPS data plane.
