## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.6-ea.1 is a comprehensive AI/ML platform deployed on OpenShift Container Platform through the Operator Lifecycle Manager (OLM). The platform is orchestrated by rhods-operator, which manages the lifecycle of all platform components through a hierarchy of custom resources — DataScienceCluster, DSCInitialization, and per-component CRDs. Each major capability (model serving, pipelines, distributed workloads, notebooks, model registry, training, observability, guardrails, and models-as-a-service) is implemented by a dedicated module operator or controller that watches its component CR and reconciles downstream Kubernetes resources using kustomize-based manifest rendering through the shared odh-platform-utilities framework.

The platform ingress architecture is in active transition. The rhods-operator Gateway service controller provisions a central `data-science-gateway` using Gateway API (GatewayClass, Gateway, HTTPRoutes) while maintaining backward compatibility through OpenShift Routes. kube-auth-proxy provides OIDC-authenticated access to the dashboard, and the Gateway controller conditionally integrates with Istio by dynamically creating EnvoyFilter and DestinationRule resources when Istio CRDs are detected. Models-as-a-Service introduces a parallel ingress path through Kuadrant AuthPolicy enforcement with API key, TokenReview, and optional OIDC JWT authentication at the Gateway level. Model-registry-operator implements dual ingress (Gateway API HTTPRoutes and OpenShift Routes) with kube-rbac-proxy sidecar authentication on backend pods.

Security follows a defense-in-depth posture: all shipped Go binaries are built with `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` for FIPS-compliant cryptography through system OpenSSL, operators read the cluster APIServer TLS security profile to align their TLS configuration with platform-wide policy, admission webhooks validate and default CRD resources with fail-closed policies, and per-component RBAC is scoped through dedicated ServiceAccounts and ClusterRoles. Authentication is layered across gateway-level (kube-auth-proxy OIDC, Kuadrant AuthPolicy), pod-level (kube-rbac-proxy sidecar), and application-level (Kubernetes TokenReview, SubjectAccessReview) enforcement points.

### Central Components

**rhods-operator** is the platform root: it owns all component CRDs (DataSciencePipelines, Kueue, ModelRegistry, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI) and three service controllers (Auth, Gateway, Monitoring) that manage cross-cutting platform infrastructure. Every component operator depends on rhods-operator for activation and lifecycle management.

**kserve** is the most connected serving component with 13 CRDs, 4 independent controller binaries (manager, llmisvc, localmodel, kserve-module), and integration with Gateway API, KEDA, cert-manager, Istio, and the Gateway API Inference Extension. Both rhods-operator and model-registry depend on it.

**odh-model-controller** serves as the serving control plane companion to kserve, managing 10 reconcilers covering InferenceService, InferenceGraph, LLMInferenceService, and Gateway resources. It provides the model-serving-api REST endpoint and manages Kuadrant AuthPolicies and KEDA autoscaling for the serving layer.

**odh-dashboard** is the primary user interface, implementing a micro-frontend architecture with Webpack Module Federation. It watches platform CRDs (DataScienceCluster, DSCInitialization, KServe InferenceService, ModelRegistry, MLflow, TrustyAI, Feast) to reflect real-time platform state.

**models-as-a-service** is the multi-tenant model serving gateway, providing OpenAI-compatible API access with Kuadrant-based authentication and subscription governance.

### Ingress Analysis

RHOAI 3.6-ea.1 presents a multi-generation ingress architecture. The primary ingress path uses Gateway API through the `data-science-gateway`, provisioned by the rhods-operator Gateway service controller. This gateway serves as the central platform ingress node, with multiple independently owned components attaching HTTPRoutes to it. The rhods-operator creates the GatewayClass and Gateway resources, and conditionally integrates with Istio by dynamically owning EnvoyFilter and DestinationRule resources when Istio CRDs are detected on the cluster.

A parallel ingress path through OpenShift Routes persists for backward compatibility and for components that have not yet migrated to Gateway API. The model-registry-operator explicitly implements dual ingress, creating both HTTPRoutes (referencing data-science-gateway) and OpenShift Routes, with the backend port selection conditionally routing through kube-rbac-proxy when configured.

The Models-as-a-Service subsystem introduces a third ingress pattern: it references a `maas-default-gateway` in its HTTPRoute manifest and layers Kuadrant/Authorino authentication at the gateway level. The MaaSAuthPolicyReconciler programmatically constructs AuthPolicy resources with three authentication methods (API key, TokenReview, OIDC JWT) and OPA-based authorization. This is architecturally distinct from the dashboard's kube-auth-proxy OIDC pattern and from the pod-level kube-rbac-proxy pattern used by model-registry.

The EnvoyFilter -> ext_authz -> kube-auth-proxy chain for dashboard access is conditionally created by the rhods-operator Gateway controller when Istio CRDs are present. The specific filter configuration (selector, target service/port, auth-check path, route scope) is dynamically generated by the controller. Source inspection confirms that the Gateway controller owns EnvoyFilter and DestinationRule resources and deploys a kube-auth-proxy with OIDC support, but the exact ext_authz filter wiring details are rendered at reconciliation time from Go code rather than static manifests, making the full chain `derived` rather than `observed`. [source: rhods-operator internal/controller/services/gateway/gateway_controller.go:42-103]

The relationship between data-science-gateway and maas-default-gateway is unresolved from the structured inventory alone. Both are referenced in the `openshift-ingress` namespace, and they may be the same Gateway resource with different names used by different components, or they may be distinct Gateway resources. The models-as-a-service HTTPRoute explicitly references `maas-default-gateway` as its parentRef.

## Deployment Architecture

### Deployment Topology

The platform deploys across four namespace tiers. The operator namespace (redhat-ods-operator or opendatahub-operator-system) hosts rhods-operator and the platform-level admission webhooks. The applications namespace (redhat-ods-applications or opendatahub) hosts the dashboard, model controllers, and module operators. Per-component namespaces (kserve, models-as-a-service) isolate specific subsystems. User namespaces host workloads: inference service pods, notebook StatefulSets, pipeline workflow pods, training jobs, and Ray clusters.

The operator tier manages the control plane: rhods-operator reconciles DataScienceCluster and DSCInitialization CRs, triggering per-component operators to deploy their workloads. Module operators (kserve-module, ai-gateway-operator, trainer-operator, workbenches-operator, etc.) each run as separate processes with dedicated RBAC identities and leader election, following the ODH module operator pattern for standardized manifest rendering and lifecycle management.

Gateway infrastructure is deployed in the openshift-ingress namespace, where the data-science-gateway receives HTTPRoutes from multiple components. Monitoring infrastructure (Prometheus collectors and proxies with kube-rbac-proxy sidecars) is deployed in the applications namespace by the rhods-operator Monitoring service controller.

## Platform Architectural Analysis

RHOAI 3.6-ea.1 represents a platform in active architectural evolution across several dimensions. The most significant patterns and tensions observed across all 72 component analyses are:

**Module operator proliferation.** The platform has adopted a module operator pattern (via odh-platform-utilities framework) where each major capability runs its own operator process with independent RBAC, leader election, and lifecycle management. This provides clean separation of concerns and independent release cadences but results in a large number of operator pods (19+ controllers), each with substantial RBAC footprints. The ai-gateway-operator alone has 128 RBAC entries spanning 10+ API groups. This proliferation creates operational complexity in monitoring, debugging, and resource consumption.

**Authentication fragmentation.** The platform uses at least four distinct authentication patterns: (1) kube-auth-proxy OIDC at the gateway level for dashboard access, (2) Kuadrant/Authorino AuthPolicy for MaaS API access with API keys, TokenReview, and OIDC, (3) kube-rbac-proxy sidecars for pod-level SubjectAccessReview enforcement on metrics and API endpoints, and (4) application-level TokenReview/SubjectAccessReview in component code. While each pattern serves a valid use case, the lack of a unified authentication architecture means that different capabilities present different credential requirements and failure modes to users and operators.

**Gateway API transition.** The platform is mid-migration from OpenShift Routes to Gateway API. The rhods-operator provisions a central data-science-gateway, but not all components have migrated: model-registry-operator maintains dual ingress, some components still use Routes exclusively, and models-as-a-service references a separately-named gateway (maas-default-gateway). The conditional Istio integration (EnvoyFilter/DestinationRule created only when Istio CRDs are detected) adds complexity to the ingress story, as the authentication chain differs between Istio-present and Istio-absent clusters.

**KServe multi-controller complexity.** KServe ships 4 independent controller binaries (manager, llmisvc, localmodel/localmodelnode) plus the kserve-module operator, totaling 5 processes with separate RBAC identities. The llmisvc controller alone manages 13 resource types including HPA, KEDA ScaledObjects, LeaderWorkerSets, InferencePools, and Gateway resources. This reflects the rapid feature expansion of the LLM serving stack (disaggregated inference, multi-node serving, local model caching) but creates a large blast radius for any KServe upgrade.

**Shared infrastructure dependencies.** Multiple components independently depend on cert-manager, prometheus-operator, and Gateway API, each implementing their own conditional watch patterns. This means the platform has soft dependencies on these infrastructure components without a centralized dependency management mechanism — each component independently checks for CRD availability and degrades independently.

**Supply chain consistency.** All analyzed Go components use the FIPS-compliant build pattern (CGO_ENABLED=1 + GOEXPERIMENT=strictfipsruntime) on UBI 9 base images, providing strong build-time FIPS posture. However, the upstream KServe core manager Dockerfile uses CGO_ENABLED=0 (static linking, not FIPS-compliant), relying on the Konflux build pipeline to override these flags for downstream builds. Python components (KServe model servers, data-science-pipelines) inherit FIPS from the UBI base OpenSSL but have no explicit FIPS opt-in in their application code.

**Unresolved cross-cutting topics.** High availability, disconnected deployment, and supply chain evidence remain unresolved across the majority of components. While the platform architecture supports HA through leader election (operators) and horizontal scaling (workloads), no deterministic evidence of replica configuration, failover behavior, or disruption budgets was extracted at the platform level. Disconnected deployment support is architecturally expected through OLM and oc-mirror but was not confirmed from component source analysis.
