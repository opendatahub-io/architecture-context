## Purpose

**Short**: Kubernetes operator that manages the lifecycle of distributed training jobs (PyTorchJob, TFJob, JAXJob, MPIJob, PaddleJob, XGBoostJob) on OpenShift, with validating admission webhooks, OpenShift-aware TLS profile integration, and optional gang-scheduling support via Volcano or scheduler-plugins. [source: cmd/training-operator.v1/main.go:265-288, manifests/base/crds/kubeflow.org_pytorchjobs.yaml:2]

**Detailed**: The training-operator is a controller-runtime-based Kubernetes operator that reconciles six custom resource types under the `kubeflow.org/v1` API group: JAXJob, MPIJob, PaddleJob, PyTorchJob, TFJob, and XGBoostJob. Each CRD has a dedicated reconciler that manages Pod, Service, ServiceAccount, and ConfigMap lifecycle for distributed training workloads. The operator includes validating admission webhooks for all six CRD types, served on port 9443 with TLS certificates self-managed via the `open-policy-agent/cert-controller` library. At startup, the operator reads the OpenShift `config.openshift.io/v1/APIServer` resource to derive the cluster TLS profile for its webhook and metrics servers, falling back to hardened TLS 1.2 intermediate defaults on non-OpenShift clusters. It exposes a Prometheus-compatible metrics endpoint on port 8080 with TLS encryption, and health/readiness probes on port 8081. The PyTorch reconciler supports HorizontalPodAutoscaler integration, and the MPI reconciler manages kubectl-delivery init containers. The downstream RHOAI build uses `GOEXPERIMENT=strictfipsruntime` and dynamic linking for FIPS compliance. ## Architectural Analysis

The training-operator follows a standard controller-runtime multi-reconciler pattern, with one reconciler per training job CRD. All six reconcilers (JAX, MPI, Paddle, PyTorch, TensorFlow, XGBoost) share a common pod/service lifecycle management approach via the Kubernetes API, operating with a single ClusterRole that grants broad access to core resources, kubeflow.org CRDs, and scheduling APIs (Volcano and scheduler-plugins PodGroups). The MPI reconciler is notably more complex, additionally managing ConfigMaps, Roles, RoleBindings, and ServiceAccounts per job for the launcher/worker SSH pattern.

A distinctive architectural choice is the operator's OpenShift-aware TLS configuration: at startup, it reads the `config.openshift.io/v1/APIServer` cluster resource to extract the platform-mandated TLS profile (minimum version and cipher suites), then applies it uniformly to both the webhook server (port 9443) and the metrics server (port 8080). On non-OpenShift clusters or when the APIServer resource is unavailable, it falls back to a hardened TLS 1.2 intermediate profile with explicitly enumerated AEAD cipher suites. This ensures the operator's serving surfaces align with cluster-wide security policy without requiring external configuration.

Certificate management for the webhook server uses the `open-policy-agent/cert-controller` library for self-signed CA and serving certificate rotation, storing certificates in the `training-operator-webhook-cert` Secret. The readiness probe gates on certificate availability, preventing the operator from accepting traffic before webhook TLS is established. This ordering dependency means the operator's startup latency is bounded by cert generation.

The operator exposes a metrics endpoint with TLS encryption but without application-level authentication—access control for metrics scraping relies on network-level policies or Kubernetes RBAC on the Service. The health and readiness probes on port 8081 are intentionally unauthenticated for kubelet access. All five validating webhooks enforce a Fail policy, meaning API server unavailability of the operator blocks training job creation and updates. ## Data Flows

- **Training job reconciliation:** Users create kubeflow.org/v1 CRs (PyTorchJob, TFJob, etc.) via the Kubernetes API. The API server first routes CREATE/UPDATE requests through the operator's validating webhook (port 9443, TLS) for schema and semantic validation. Upon acceptance, the corresponding reconciler watches the CR and creates/manages Pods, Services, and (for MPI) ConfigMaps, Roles, RoleBindings, and ServiceAccounts in the job's namespace. Pod status changes are watched and reconciled back into the CR's status. [source: cmd/training-operator.v1/main.go:385-431, manifests/base/rbac/role.yaml:1-129]
- **TLS profile derivation:** At startup, the operator reads the `config.openshift.io/v1/APIServer` cluster singleton to extract the TLS profile (minimum version, cipher suites). This profile is applied to both the webhook server (port 9443) and the metrics server (port 8080). If the APIServer resource is not found (non-OpenShift), the operator applies TLS 1.2 intermediate defaults. [source: cmd/training-operator.v1/main.go:100-141]
- **Metrics and observability:** The operator serves Prometheus metrics on port 8080 with TLS encryption. The Service carries `prometheus.io/scrape`, `prometheus.io/port`, and `prometheus.io/path` annotations for autodiscovery. Health probes on port 8081 are unauthenticated HTTP for kubelet access. [source: manifests/base/service.yaml:4-7, cmd/training-operator.v1/main.go:280, 330-333]
- **Certificate lifecycle:** The `open-policy-agent/cert-controller` library generates a self-signed CA and serving certificate, stored in the `training-operator-webhook-cert` Secret. The readiness probe blocks until certificates are ready, ensuring the webhook server is functional before the operator advertises readiness.
