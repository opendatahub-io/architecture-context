## Purpose

**Short**: Model Registry is a metadata service that provides a central repository for ML model developers and platform operators to store, version, and manage model artifacts, serving as the integration point between model training and model serving on RHOAI. [source: Dockerfile.konflux:44-48, clients/ui/bff/cmd/main.go:32-56, cmd/controller/main.go:138-156]

**Detailed**: Model Registry provides a centralized metadata catalog for machine learning models, their versions, and associated artifacts within the RHOAI platform. The core service exposes an HTTP/REST API (via an OpenAPI-generated proxy) for registering and querying model metadata, backed by a relational database (PostgreSQL or MySQL via GORM). A Go-based BFF (Backend for Frontend) serves the UI with authentication-aware access to model registry data and Kubernetes resources, supporting multiple deployment modes (kubeflow, federated, standalone). A controller-runtime operator conditionally watches KServe InferenceService resources (when `INFERENCE_SERVICE_CONTROLLER=managed`) to synchronize model serving state with registry metadata, locating model-registry Service endpoints via Kubernetes API discovery. An async-upload Python job handles artifact upload operations to S3-compatible storage. The system integrates with Istio for service mesh-based authentication and authorization on its API and UI surfaces. [source: Dockerfile.konflux:24, 42, clients/ui/bff/cmd/main.go:32-88, cmd/controller/main.go:138-156, pkg/inferenceservice-controller/controller.go:248-303]

## Architectural Analysis

Model Registry follows a multi-tier architecture with distinct runtime components serving different concerns. The core registry service (`model-registry` binary) runs as an HTTP proxy exposing the OpenAPI-defined model metadata API on port 8080. The BFF layer (`bff` binary) mediates between the UI frontend and both the model registry API and Kubernetes API, implementing a pluggable authentication model: the `auth-method` flag selects between `internal` (ServiceAccount-based) and `user_token` (Bearer token passthrough) modes, with configurable token headers and prefixes. [source: clients/ui/bff/cmd/main.go:56-58, Dockerfile.konflux:42]

The controller component uses controller-runtime to reconcile KServe InferenceService resources with model registry metadata, but is conditionally activated only when `INFERENCE_SERVICE_CONTROLLER=managed`. When active, the controller discovers model registry instances by listing Kubernetes Services with the `component: model-registry` label, then constructs OpenAPI clients to update inference service URLs in the registry. This conditional activation pattern means the controller's RBAC permissions (watching InferenceServices and Services) are always deployed but the reconciliation loop only runs in managed mode. [source: cmd/controller/main.go:138-156, pkg/inferenceservice-controller/controller.go:248-310]

Security is layered: the controller's metrics endpoint uses controller-runtime's built-in TokenReview/SubjectAccessReview authentication with self-signed TLS certificates, and HTTP/2 is disabled by default to mitigate stream cancellation CVEs. The model registry API and UI surfaces are protected by Istio AuthorizationPolicies that enforce source principal and namespace restrictions. The BFF adds application-level authentication and performs SubjectAccessReview/SelfSubjectAccessReview checks against the Kubernetes API for fine-grained authorization decisions. The FIPS build configuration uses `GOEXPERIMENT=strictfipsruntime` with dynamic linking (`CGO_ENABLED=1`), ensuring that Go's crypto operations delegate to OpenSSL on the UBI base image. The TLS configuration enforces a minimum of TLS 1.2 with configurable cipher suites that are all FIPS-compatible. [source: cmd/controller/main.go:58-78, 99-104, Dockerfile.konflux:24, internal/platform/tls/config.go:64-68, 100-113]
