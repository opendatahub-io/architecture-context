## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines infrastructure, reconciling DataSciencePipelinesApplication custom resources into a full deployment stack including Argo Workflow engine, pipeline API server, and supporting services. **Detailed**: The data-science-pipelines-operator (DSPO) is a Go controller-runtime operator that manages Data Science Pipelines on Red Hat OpenShift AI. It watches DataSciencePipelinesApplication (DSPA) custom resources and reconciles them into a complete pipeline execution environment, deploying and managing Argo Workflow CRDs, pipeline API server deployments, database connections, object storage configurations, and supporting RBAC resources. The operator uses the manifestival library to apply declarative resource templates from its internal configuration directory, managing Deployments, Services, ConfigMaps, Secrets, Roles, RoleBindings, NetworkPolicies, Routes, and ServiceAccounts as owned resources. It integrates with multiple platform components including MLflow for experiment tracking, KServe for model serving state, Kubeflow Notebooks for workbench management, and prometheus-operator for monitoring. The operator dynamically adapts its TLS configuration to the cluster's OpenShift TLS security profile and restarts gracefully when the profile changes. [source: main.go:376, controllers/dspipeline_controller.go:28, tls_profile.go:22, config/manager/manager-service.yaml:1]

## Architectural Analysis

The data-science-pipelines-operator follows a single-controller reconciliation pattern centered on the DSPAReconciler, which owns the full lifecycle of Data Science Pipelines infrastructure within each namespace. When a user creates a DataSciencePipelinesApplication CR, the reconciler deploys and configures the complete pipeline stack—including Argo Workflow engine resources, pipeline API server, database connectivity, and object storage—using manifestival-based template rendering from bundled internal configurations. [source: controllers/dspipeline_controller.go:28, main.go:365]

The operator's RBAC footprint is notably broad, spanning 14 CRD types across 10+ API groups. This breadth reflects its role as an infrastructure orchestrator: it manages not only its own DSPA resources but also provisions Argo Workflow CRDs, creates ServiceMonitors for prometheus-operator, manages NetworkPolicies for workload isolation, and has CRUD permissions on Ray, CodeFlare AppWrappers, KServe InferenceServices, and Seldon deployments. The aggregate RBAC roles (aggregate-dspa-admin-edit and aggregate-dspa-admin-view) follow the OpenShift convention of composing into the platform's admin/edit/view ClusterRoles, giving namespace administrators self-service access to pipeline resources without cluster-admin intervention. [source: config/rbac/role.yaml:2, config/rbac/aggregate_dspa_role_edit.yaml:1, config/rbac/aggregate_dspa_role_view.yaml:1]

A distinctive architectural choice is the TLS profile adherence mechanism: the operator fetches the cluster's OpenShift APIServer TLS profile at startup and configures its webhook server accordingly, falling back to the Intermediate profile on non-OpenShift clusters. A SecurityProfileWatcher monitors for profile changes at runtime and triggers a graceful pod restart to reload TLS settings, ensuring the operator always aligns with the cluster's security posture without manual reconfiguration. [source: tls_profile.go:22-64, main.go:385-399]

The FIPS build strategy uses Go's native FIPS 140 module (`GOFIPS140=v1.0.0`) with static linking (`CGO_ENABLED=0`) and the `no_openssl` build tag, rather than the traditional OpenSSL-backed `strictfipsruntime` approach. This means the operator's cryptographic operations are handled by Go's certified FIPS 140 crypto module at runtime without depending on the container image's OpenSSL installation. [source: Dockerfile.konflux:28]

## Data Flows

- **Reconciliation loop:** The DSPAReconciler watches DataSciencePipelinesApplication CRs (primary resource) and reconciles a full stack of owned resources—Deployments, Services, ConfigMaps, Secrets, Roles, RoleBindings, NetworkPolicies, Routes, and ServiceAccounts—using manifest templates from `config/internal/`. Changes to any owned resource trigger re-reconciliation via controller-runtime's ownership watches. [source: controllers/dspipeline_controller.go:28, main.go:365]
- **Platform integrations:** The operator reads MLflow CR state (via `mlflowv1` Go types from the mlflow-operator API library), watches KServe InferenceService resources for model serving state, manages Kubeflow Notebook workbenches, creates ServiceMonitors for prometheus-operator, and provisions Argo Workflow CRDs. All platform API interactions traverse the Kubernetes API server over HTTPS with ServiceAccount token authentication. [source: controllers/dspipeline_controller.go:28, config/rbac/role.yaml:2]
- **Metrics exposure:** A ClusterIP Service on port 8080 exposes Prometheus metrics, scraped by a ServiceMonitor at `/metrics`. Health and readiness probes are served on port 8081 at `/healthz` and `/readyz` without authentication. [source: config/manager/manager-service.yaml:1, config/prometheus/monitor.yaml:1, main.go:376-380]
- **Security boundary:** Access to DSPA resources is governed by RBAC aggregation into OpenShift's admin/edit/view ClusterRoles. Argo Workflow resources use tiered aggregation roles (admin/edit/view) with a separate cluster role restricting secret access to the `argo-workflows-agent-ca-certificates` secret only. The operator's TLS configuration is dynamically aligned with the cluster's OpenShift TLS security profile. [source: config/rbac/aggregate_dspa_role_edit.yaml:1, config/argo/clusterrole.argo-cluster-role.yaml:1, tls_profile.go:22]
