## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Kubeflow Notebook workbenches on RHOAI, including notebook-controller deployment, connection-secret injection webhooks, and hardware-profile mutation. [source: cmd/main.go:67, internal/controller/workbenches_controller.go:110, internal/webhook/notebook/mutating.go:55]

**Detailed**: workbenches-operator is a controller-runtime operator that reconciles a cluster-scoped `Workbenches` custom resource to deploy and manage the Kubeflow notebook-controller stack. The reconciler owns Deployments, Services, ConfigMaps, Secrets, RBAC resources, and webhook configurations in a resolved applications namespace, applying upstream kustomize manifests with platform-specific parameters such as gateway domain, MLflow enablement, and section titles. Two mutating admission webhooks intercept Notebook CR create/update operations: `connection-notebook` validates referenced connection secrets exist and the submitting user has permission to read them (via SubjectAccessReview), then injects volume mounts; `hardwareprofile-notebook-injector` applies hardware-profile resource limits from HardwareProfile CRs. The operator bootstraps its TLS configuration from the OpenShift cluster APIServer TLS security profile, falling back to Mozilla Intermediate ciphers on non-OpenShift clusters, and watches for profile changes to trigger a pod restart. Webhook serving certificates are provisioned through OpenShift service-ca or cert-manager depending on cluster capabilities. [source: cmd/main.go:67-230, internal/controller/workbenches_controller.go:110-180, internal/webhook/notebook/mutating.go:55-99, internal/tlsconfig/tlsconfig.go:98-154]

## Architectural Analysis

The workbenches-operator follows a single-CR reconciliation pattern: one cluster-scoped `Workbenches` resource drives the entire notebook-controller stack. The `WorkbenchesReconciler` applies upstream Kubeflow notebook-controller manifests via kustomize, parameterized by platform type (ODH vs SelfManagedRhoai), gateway domain, and MLflow enablement state. It owns a broad set of Kubernetes resources (Deployments, Services, ConfigMaps, Secrets, RBAC, webhook configurations) and uses OwnerReferences for garbage collection on CR deletion, with an explicit finalizer for ordered cleanup of legacy workbench namespaces and ImageStreams. [source: internal/controller/workbenches_controller.go:110-180, cmd/main.go:189-197]

The operator's webhook architecture separates two admission concerns into distinct handlers. The `NotebookWebhook` enforces connection-secret governance: it validates that referenced secrets exist in the notebook's namespace and performs a SubjectAccessReview to confirm the submitting user can read them before injecting volume mounts. The `HardwareProfile Injector` resolves HardwareProfile CRs and mutates notebook containers with the specified resource limits. Both webhooks register on `kubeflow.org/notebooks` CREATE and UPDATE with `failurePolicy: Fail`, making them blocking for notebook lifecycle. [source: internal/webhook/notebook/mutating.go:55-99, internal/webhook/hardwareprofile/mutating.go:67]

TLS management is architecturally significant: the operator refuses to start without establishing its TLS posture. At bootstrap, it fetches the OpenShift APIServer TLS security profile and adherence policy via `controller-runtime-common/pkg/tls`, applying the cluster-mandated cipher suites and minimum TLS version to both the metrics server and the webhook server. On non-OpenShift clusters, it falls back to the Mozilla Intermediate cipher set with TLS 1.2 minimum. A `SecurityProfileWatcher` monitors the APIServer resource and cancels the manager context on profile changes, forcing a pod restart to adopt updated TLS settings. HTTP/2 is disabled by default as a hardening measure. [source: internal/tlsconfig/tlsconfig.go:41-154, cmd/main.go:119-127, 86-87]

Platform awareness is split between CR-level configuration and runtime config: the `Workbenches` CR spec carries `platform`, `gatewayDomain`, and `mlflowEnabled` fields projected by the platform orchestrator (DSC), while `odh-workbenches-config` ConfigMap provides distribution name and version metadata. The ConfigMap informer is scoped to the resolved applications namespace(s) to minimize cluster-wide watch pressure. [source: internal/platformconfig/config.go:69-103, cmd/main.go:166-181]

## Data Flows

- **Reconciliation flow:** The platform orchestrator creates or updates a cluster-scoped `Workbenches` CR with platform type, gateway domain, and MLflow enablement. The `WorkbenchesReconciler` reads the CR, resolves the applications namespace by platform, reads distribution metadata from `odh-workbenches-config` ConfigMap, then applies kustomize-rendered upstream notebook-controller manifests (Deployments, Services, RBAC, webhook configs) into the target namespace via server-side apply. [source: internal/controller/workbenches_controller.go:110-139, internal/platformconfig/config.go:69-103, cmd/main.go:189-197]
- **Webhook admission flow:** On Notebook CR create/update, the Kubernetes API server routes admission requests to port 9443 via `workbenches-operator-webhook-service` (ClusterIP 443 -> 9443). The `NotebookWebhook` handler validates connection-secret references exist and checks user permissions via SubjectAccessReview before injecting volume mounts. The `HardwareProfile Injector` reads the referenced HardwareProfile CR and mutates container resource limits. Both webhooks use TLS certificates provisioned by OpenShift service-ca or cert-manager. [source: internal/webhook/notebook/mutating.go:55-99, 322, internal/webhook/hardwareprofile/mutating.go:67, config/default/webhook_openshift_patch.yaml:1]
- **TLS bootstrap flow:** At startup, the operator fetches the OpenShift APIServer TLS security profile and adherence policy, configures cipher suites and minimum TLS version for both metrics and webhook servers, and registers a watcher that cancels the manager context on profile changes to force a restart. On non-OpenShift clusters, it falls back to Mozilla Intermediate ciphers with TLS 1.2 minimum. [source: internal/tlsconfig/tlsconfig.go:98-154, cmd/main.go:119-127]
- **Security context:** The metrics endpoint (port 8443) requires TokenReview and SubjectAccessReview via controller-runtime's authentication/authorization filter. Health and readiness probes (port 8081) are unauthenticated by design. All Kubernetes API interactions use the `workbenches-operator-controller-manager` ServiceAccount with RBAC enforced by `workbenches-operator-manager-role`. [source: cmd/main.go:144-146, 213, 218]
