## Purpose

**Short**: The mlflow-operator manages the lifecycle of MLflow Tracking Server instances on Red Hat OpenShift AI, orchestrating deployments, Gateway API routing, monitoring, and namespace-scoped RBAC through three Kubernetes controllers. [source: cmd/main.go:171, internal/controller/mlflow_controller.go:464, config/crd/bases/mlflow.opendatahub.io_mlflows.yaml:2]

**Detailed**: The mlflow-operator is a Go-based Kubernetes operator built on controller-runtime that manages MLflow Tracking Server instances within the RHOAI platform. It defines three CRDs — MLflow (cluster-scoped, `mlflow.opendatahub.io/v1`), MLflowOperator (cluster-scoped, `components.platform.opendatahub.io/v1alpha1`), and MLflowConfig (namespace-scoped, `mlflow.kubeflow.org/v1`) — and implements three controllers to reconcile them. The MLflowReconciler drives the primary lifecycle, creating and managing Deployments, Services, ServiceAccounts, PersistentVolumeClaims, Secrets, Jobs, CronJobs, NetworkPolicies, and ServiceMonitors for each MLflow instance using bundled Helm chart templates. It conditionally integrates with Gateway API (HTTPRoute), OpenShift Console (ConsoleLink), and prometheus-operator (ServiceMonitor) based on runtime CRD discovery. The MLflowOperatorReconciler handles the platform component lifecycle, and the NamespaceRBACReconciler manages per-namespace RoleBindings for MLflow access control. The operator enforces platform TLS profile adherence via OpenShift apiserver configuration and uses resourceNames-scoped RBAC for secret access. [source: cmd/main.go:171, 209-254, internal/controller/mlflow_controller.go:464-552, Dockerfile.konflux:37]

## Architectural Analysis

The mlflow-operator follows a multi-controller pattern where three distinct reconcilers share a single controller-runtime manager process. The MLflowReconciler is the primary controller, owning the full resource lifecycle for MLflow instances including Deployments, Services, Jobs, CronJobs, and NetworkPolicies. It uses Helm chart rendering (via `helm.sh/helm/v3`) to produce Kubernetes manifests from bundled chart templates at `charts/mlflow`, applying them through a reconcile loop that handles creation, updates, and ownership tracking. [source: cmd/main.go:171, internal/controller/mlflow_controller.go:464-552, Dockerfile.konflux:37]

A key architectural pattern is conditional CRD discovery at startup. Before registering watches, the operator probes the Kubernetes API for HTTPRoute (Gateway API), ConsoleLink (OpenShift Console), and ServiceMonitor (prometheus-operator) CRDs. Watches are only registered when the corresponding CRD is present, allowing the operator to run on clusters without these optional dependencies while still integrating with them when available. [source: internal/controller/mlflow_controller.go:528-550]

The operator implements a dual RBAC scoping strategy for cluster-scoped resources. Shared ClusterRole and ClusterRoleBinding objects use non-controller owner references to support multiple MLflow instances per cluster, with custom `Watches` handlers replacing the standard `Owns` pattern. A separate dedicated watch cache (`GCRBACWatchCache`) tracks garbage-collection RBAC objects under tight `resourceNames`-scoped field selectors, working around controller-runtime's single-selector-per-GVK constraint. [source: internal/controller/mlflow_controller.go:481-526]

TLS configuration is dynamically sourced from the OpenShift platform's `apiservers.config.openshift.io/cluster` resource, defaulting to the Intermediate TLS profile when the API is unavailable. A TLS profile watcher triggers graceful shutdown and reload when the cluster TLS policy or adherence setting changes, ensuring runtime adherence to platform-wide TLS standards. The metrics endpoint uses controller-runtime's `WithAuthenticationAndAuthorization` filter (TokenReview + SubjectAccessReview) with self-signed or externally provisioned TLS certificates. [source: cmd/main.go:209-254, 261-284]

Secret access is restricted to the named `mlflow-artifact-connection` Secret via `resourceNames`-scoped RBAC rules, limiting the blast radius of credential access. The operator also watches the platform trusted CA bundle ConfigMap, updating Deployment specs when its availability changes while relying on kubelet for content-change propagation via mounted ConfigMaps. A migration subsystem handles data migration between MLflow versions using batch Jobs with Pod lifecycle tracking. [source: config/rbac/role.yaml:2, internal/controller/mlflow_controller.go:487-496]
