## Purpose

**Short**: OGX distribution is a Python-based AI agent and inference gateway service that packages the upstream OGX framework (formerly llama-stack) as a Red Hat container image with configurable inference, vector storage, and tool runtime providers. [source: distribution/config.yaml:1-2, Dockerfile.konflux:9-10]

**Detailed**: ogx-distribution packages the upstream OGX framework into a Red Hat-branded container image for deployment as an AI service within the RHOAI platform. The distribution exposes eight API surfaces — responses, messages, batches, inference, tool_runtime, vector_io, files, and file_processors — on a configurable HTTP server (default port 8321). It supports pluggable inference backends including vLLM, AWS Bedrock, IBM WatsonX, Azure, Vertex AI, OpenAI, Gemini, and Anthropic, all configured via environment variables. Vector storage is delegated to remote providers (Milvus, pgvector, Qdrant), and persistent state is stored in PostgreSQL. Authentication is optional via OAuth2 token validation with JWKS key rotation, gated by the AUTH_ISSUER environment variable. The container entrypoint resolves file-mounted Kubernetes secrets before launching the `ogx run` command, with optional OpenTelemetry instrumentation. [source: distribution/config.yaml:13-280, distribution/entrypoint.sh:1-79, Dockerfile.konflux:58]

## Architectural Analysis

ogx-distribution follows a distribution-as-configuration pattern: the repository does not contain the OGX runtime source code itself, but rather a build pipeline and declarative configuration that assembles the upstream OGX Python package with provider-specific dependencies into a deployable container image. The `build.yaml` defines the full provider matrix including inline providers (sentence-transformers, docling, faiss, milvus-lite) that are stripped from the shipped `config.yaml` to reduce the default image footprint while remaining available via custom configuration. [source: distribution/config.yaml:4-11, build/build.yaml:37-39]

The authentication architecture uses conditional activation: the OAuth2 token provider is only enabled when `AUTH_ISSUER` is set, using the shell parameter expansion `${env.AUTH_ISSUER:+oauth2_token}`. When active, it validates JWT tokens against a configurable JWKS endpoint with a 3600-second key recheck period. The access policy enforces a resource-ownership model where unowned system resources are publicly readable, authenticated users can create resources, and only resource owners can update or delete their resources. [source: distribution/config.yaml:259-280]

The entrypoint implements a Kubernetes-aware secret resolution pattern, supporting `_FILE` variants for 18 secret environment variables (API keys, database passwords, and tokens). This prevents secret leakage through `/proc/1/environ` by reading credentials from mounted files rather than environment variables. The `--insecure` flag passed to `ogx run` disables TLS at the server level, delegating transport encryption to the platform ingress layer. [source: distribution/entrypoint.sh:5-10, 35-56, 79]

All persistent state flows through PostgreSQL via two storage backends: `kv_postgres` for key-value metadata and `sql_postgres` for relational data (conversations, batches, inference records, file metadata). The inference provider configuration uses environment-variable-gated conditional registration, allowing operators to enable only the providers relevant to their deployment by setting the corresponding environment variable. [source: distribution/config.yaml:198-235]

## Data Flows

- **Inference request flow:** Client requests arrive at the OGX server (port 8321), are authenticated via OAuth2 token validation when AUTH_ISSUER is configured, then routed to the appropriate API handler (responses, messages, inference, etc.). Inference requests are proxied to the configured remote provider (vLLM, Bedrock, WatsonX, Azure, OpenAI, Gemini, Anthropic, or Vertex AI) based on the provider_id. Conversation state, inference records, and batch results are persisted to PostgreSQL. [source: distribution/config.yaml:13-80, 198-234, 256-280]
- **Vector store flow:** Vector I/O operations are delegated to one of the configured remote vector backends (Milvus, pgvector, or Qdrant). Vector store metadata is persisted to the sql_default PostgreSQL backend. [source: distribution/config.yaml:81-121, 233-235]
- **Secret resolution flow:** On container startup, the entrypoint resolves `_FILE` variants for 18 secret environment variables by reading Kubernetes-mounted files, then launches the OGX server. [source: distribution/entrypoint.sh:35-56]
