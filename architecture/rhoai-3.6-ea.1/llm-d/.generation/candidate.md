## Purpose

**Short**: llm-d is a reference architecture repository providing multi-accelerator vLLM container images and kustomize-based deployment recipes for optimized LLM inference serving on Kubernetes. [source: docker/Dockerfile.cpu:142, docker/Dockerfile.cuda:630, guides/optimized-baseline/guide.yaml:1]

**Detailed**: llm-d provides two primary artifacts: (1) Dockerfiles that build vLLM-based model server container images for multiple hardware accelerators (NVIDIA CUDA, AMD ROCm, Intel XPU, CPU), and (2) kustomize overlays and Helm value files that compose deployment recipes for serving patterns including optimized-baseline single-model serving, prefill/decode (P/D) disaggregation, prefix-cache-aware routing, predicted-latency routing, multimodal serving, agentic serving, and workload autoscaling. The repository does not contain application source code; it packages the upstream vLLM inference engine into container images and provides declarative Kubernetes manifests that orchestrate the model server alongside the llm-d-router (EPP + Envoy proxy), Gateway API resources, and observability components. Each guide composes a stack from shared recipe components, enabling multi-accelerator, multi-model-server (vLLM, SGLang, TensorRT-LLM), and multi-cloud (GKE, AWS, CoreWeave, OpenShift) deployment topologies. [source: docker/Dockerfile.cpu:1-142, docker/Dockerfile.cuda:630, guides/optimized-baseline/guide.yaml:1-164, guides/recipes/router/base.values.yaml:1-55]

## Architectural Analysis

llm-d follows a composable recipe architecture where each deployment guide (optimized-baseline, pd-disaggregation, precise-prefix-cache-routing, etc.) assembles a stack from shared kustomize bases and components. The base recipe layer at `guides/recipes/modelserver/base/` defines the minimal decode Deployment with a vLLM OpenAI-compatible API server on port 8000/TCP, health and readiness probes, and a service account. Guide-specific overlays patch this base to add accelerator-specific images, P/D disaggregation topology (separate prefill and decode Deployments communicating via nixl on port 5600/TCP), routing sidecars, monitoring, and model caching.

The routing layer is provided by the external llm-d-router Helm chart, which deploys an Endpoint Picker Plugin (EPP) and an Envoy proxy. The EPP implements ext_proc gRPC at port 9002 with scheduling plugins (queue-scorer, kv-cache-utilization-scorer, prefix-cache-scorer, no-hit-lru-scorer) that perform load-aware and cache-aware request routing. Envoy listens on port 8081 and routes requests to model server backends using ORIGINAL_DST with the `x-gateway-destination-endpoint` header. The router integrates with the Gateway API Inference Extension (InferencePool and InferenceModel CRDs) for Kubernetes-native model routing.

The container image strategy uses upstream base images (Ubuntu 22.04 for CPU, NVIDIA CUDA for GPU, ROCm for AMD) rather than UBI. Each Dockerfile builds vLLM from source with hardware-specific dependencies. No FIPS compliance signals are present in the Dockerfiles. Authentication is not configured at the model server level; it is delegated to the gateway/mesh layer (Gateway API, Istio, kgateway, or AgentGateway), which is deployed separately via gateway recipes. [source: guides/recipes/modelserver/base/single-host/default/decode-deployment.yaml:1-39, guides/recipes/router/base.values.yaml:1-55, guides/no-kubernetes-deployment/router/envoy/envoy.yaml:1-136, guides/optimized-baseline/guide.yaml:42-94, docker/Dockerfile.cpu:1-142]

## Data Flows

- **Inference request flow:** Client requests arrive at the Gateway (port 80/HTTP) or standalone EPP service, are processed by the EPP ext_proc filter (port 9002/gRPC) for load-aware and cache-aware routing decisions, then forwarded by Envoy (port 8081) to the selected vLLM model server backend (port 8000/TCP) using the `x-gateway-destination-endpoint` header for ORIGINAL_DST routing. [source: guides/no-kubernetes-deployment/router/envoy/envoy.yaml:30-101, guides/recipes/gateway/base/gateway.yaml:1-10]
- **P/D disaggregation flow:** In prefill/decode disaggregation mode, prefill workers process the prompt and transfer KV cache data to decode workers via nixl on port 5600/TCP. Decode workers serve subsequent tokens from the transferred cache. Both prefill and decode Deployments expose port 8000/TCP for the vLLM API. [source: guides/recipes/modelserver/base/single-host/pd/base/prefill-deployment.yaml:1-42, guides/recipes/modelserver/base/single-host/pd/base/kustomization.yaml:11-27]
- **Observability flow:** The EPP exports distributed traces to an OpenTelemetry Collector at localhost:4317/gRPC using parentbased_traceidratio sampling. Prometheus monitoring is available via optional kustomize components. [source: guides/recipes/router/base.values.yaml:51-55]
