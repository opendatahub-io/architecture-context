## Purpose

**Short**: ai4rag is a Python library that automates the generation and hyperparameter optimization of Retrieval-Augmented Generation (RAG) patterns, designed to run as pipeline components within RHOAI Data Science Pipelines. [source: pyproject.toml:6-7, ai4rag/utils/event_handler/event_handler.py:47-55]

**Detailed**: ai4rag provides an end-to-end RAG optimization toolkit that orchestrates document ingestion from S3-compatible storage, text chunking (via Docling and LangChain strategies), embedding generation, vector store indexing (Milvus, PGVector, or Chroma), retrieval, LLM-based answer generation, and evaluation. It uses a hyperparameter optimization loop based on Generalized Additive Models (GAM) to search over chunking parameters, embedding models, foundation models, and retrieval strategies, producing ranked RAG pattern configurations. The library connects to an OpenAI-compatible Model-as-a-Service (MaaS) endpoint for both LLM inference and embedding generation, and includes a KFP event handler for integration with Data Science Pipelines. It is packaged as a Python library with no HTTP server or Kubernetes deployment manifests of its own. [source: pyproject.toml:6-7, 30-44, ai4rag/components/utils/maas_client.py:30-62, ai4rag/utils/event_handler/event_handler.py:47-55, ai4rag/core/hpo/gam_opt.py:1]

## Architectural Analysis

ai4rag is structured as a layered Python library organized around a RAG pipeline lifecycle: data ingestion, chunking, embedding, vector store management, retrieval, LLM generation, and evaluation. The optimization layer wraps this pipeline in a hyperparameter search driven by a GAM-based optimizer that explores combinations of chunking strategies (Docling hierarchical, LangChain recursive), embedding models, foundation models, and retrieval parameters to produce ranked RAG pattern configurations. [source: ai4rag/components/optimization/rag_templates_optimization.py:1-46, ai4rag/core/hpo/gam_opt.py:1]

All LLM and embedding interactions were recently consolidated onto a single OpenAI-compatible client (`create_maas_client`), replacing the previous OGX integration. This client connects to any OpenAI-compatible MaaS endpoint — in the RHOAI context, typically vLLM-based model serving — and includes a TLS fallback that disables certificate verification when self-signed certificates are encountered. This fallback (`verify=False`) allows operation against non-production endpoints but bypasses certificate validation, which is architecturally significant for FIPS and production security posture. [source: ai4rag/components/utils/maas_client.py:30-62]

The vector store layer supports three pluggable backends — Milvus (with gRPC TLS and PEM certificate materialization), PGVector (PostgreSQL with connection pooling), and Chroma (ephemeral, persistent, or client/server modes) — all configured via environment variables. Credentials for S3 storage, vector stores, and the MaaS endpoint are injected through environment variables, with no Kubernetes Secret manifests defined by the component itself. [source: ai4rag/rag/vector_store/config.py:1-258, ai4rag/components/utils/s3.py:10-31]

The library does not expose HTTP endpoints, define Kubernetes services, or ship deployment manifests. It is consumed as an embedded dependency within Kubeflow Pipeline components, with a dedicated `KFPEventHandler` that aggregates status changes and pattern results for post-experiment reporting. [source: ai4rag/utils/event_handler/event_handler.py:47-70]

## Data Flows

- **Document ingestion:** Source documents are read from S3-compatible storage via boto3 (authenticated with AWS_ACCESS_KEY_ID and AWS_SECRET_ACCESS_KEY), converted to structured text using Docling, and chunked into segments using configurable chunking strategies. [source: ai4rag/components/utils/s3.py:34-78, ai4rag/components/data/text_extraction.py:244, 262]
- **Embedding and indexing:** Chunked text is sent to an OpenAI-compatible MaaS endpoint for embedding generation, then indexed in the configured vector store (Milvus via gRPC with optional TLS, PGVector via PostgreSQL wire protocol, or Chroma via HTTP). [source: ai4rag/rag/embedding/openai_model.py:31-36, ai4rag/rag/vector_store/config.py:108-177, 181-249]
- **RAG query and evaluation:** Retrieval queries embed the question via the same MaaS endpoint, retrieve relevant chunks from the vector store, construct a prompt with context, and send it to the foundation model endpoint for LLM chat completion. Evaluation metrics (faithfulness, answer correctness, context correctness) are computed to score each RAG configuration. [source: ai4rag/rag/foundation_models/openai_model.py:25-96, ai4rag/components/optimization/rag_templates_optimization.py:39-46]
- **Security context:** 3 secret references (AWS_SECRET_ACCESS_KEY, MILVUS_TOKEN, PGVECTOR_PASSWORD) provide credential inputs for external service connections. All credentials are sourced from environment variables; no Kubernetes Secret manifests are defined by the component. [source: ai4rag/components/utils/s3.py:10, ai4rag/rag/vector_store/config.py:175, 248]
