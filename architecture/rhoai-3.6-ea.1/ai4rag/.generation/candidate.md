## Purpose

**Short**: ai4rag is a Python library that automates and optimizes Retrieval-Augmented Generation (RAG) pattern construction, using OGX inference services for embeddings, chat completions, and vector store operations, and S3-compatible storage for document ingestion. [source: pyproject.toml:6-7, ai4rag/components/utils/ogx_client.py:39, ai4rag/components/utils/s3.py:34]

**Detailed**: ai4rag provides an end-to-end Python framework for generating optimized RAG patterns. It orchestrates document text extraction from S3-compatible object storage via boto3, chunking through multiple strategies (Langchain, Docling), embedding generation and vector store management via the OGX inference platform (using the ogx-client SDK), and hyperparameter optimization of the RAG pipeline using Bayesian (GAM) and random search strategies. The library evaluates RAG quality through LLM-as-a-judge and Unitxt-based metrics, and produces deployment-ready Jupyter notebook artifacts. ai4rag is distributed as a Python package and does not expose HTTP endpoints or Kubernetes services; it acts as a client library that connects to external OGX inference and S3 storage services. ## Architectural Analysis

ai4rag follows a modular pipeline architecture centered on four composable stages: data ingestion, chunking, retrieval-augmented generation, and evaluation. Each stage is abstracted behind base classes that allow swapping implementations—for example, chunking supports Langchain text splitters and Docling-based chunkers, while vector stores can use either Chroma (local) or OGX (remote via the platform's inference service). The optimization layer uses a hyperparameter search framework (GAM-based Bayesian and random strategies via scikit-learn and pygam) to tune RAG parameters such as chunk size, overlap, and retrieval depth across experiments.

The library's external integration surface is narrow but safety-relevant. S3-compatible storage access uses AWS credentials from environment variables, with the boto3 SDK creating per-call sessions to avoid shared state across threads. OGX integration uses API-key authentication and includes an SSL verification fallback that downgrades to `verify=False` on self-signed certificate errors—a practical accommodation for development environments that weakens transport security when triggered. Both OGX embedding and foundation model clients implement timeout-based retry logic with a 20-minute fallback window for slow (CPU-deployed) models.

As a pure Python library with no container image, Kubernetes manifests, or HTTP server components, ai4rag delegates deployment concerns to its consumer. It does not define services, ingress, RBAC, or FIPS configuration. Cryptographic behavior inherits from the host Python runtime's OpenSSL linkage. The ogx-client dependency (>=1.1.0,<=1.1.3) pins the library to a specific OGX platform API contract, making this an implicit internal platform dependency. ## Data Flows

- **Document ingestion:** The user provides an S3 bucket reference and credentials. ai4rag connects to S3-compatible storage via boto3, downloads documents, and extracts text using Docling. Credentials are AWS access keys sourced from environment variables or explicit parameters. [source: ai4rag/components/utils/s3.py:10-78, ai4rag/components/data/text_extraction.py:240-273]
- **RAG pipeline:** Extracted text is chunked (Langchain or Docling strategies), embedded via OGX embedding models, and stored in an OGX-managed or Chroma vector store. Foundation model chat completions are obtained through the OGX API for generation and evaluation. [source: ai4rag/rag/embedding/ogx.py:31-261, ai4rag/rag/foundation_models/ogx.py:25-96, ai4rag/rag/vector_store/ogx.py:14-268]
- **Authentication:** S3 access uses AWS credential environment variables (AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY, AWS_S3_ENDPOINT). OGX access uses API key authentication. Both connections use HTTPS with TLS; the OGX client includes a verify=False fallback for self-signed certificates.
