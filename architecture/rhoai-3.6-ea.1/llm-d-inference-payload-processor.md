## Purpose

**Short**: llm-d-inference-payload-processor is an Envoy External Processor (ExtProc) that intercepts inference requests via gRPC callouts, applies a configurable plugin pipeline for payload transformation, model selection, and routing, and uses controller-runtime for lifecycle management and ConfigMap reconciliation. [source: pkg/server/runserver.go:76, cmd/runner/runner.go:227-244, cmd/main.go:27]

**Detailed**: llm-d-inference-payload-processor implements the Envoy External Processing (ExtProc) gRPC API to intercept and transform inference requests in the llm-d serving infrastructure. It runs as a controller-runtime managed process that registers an ExtProc gRPC server (port 9004, TLS by default) and a Health gRPC server (port 9005) alongside a Prometheus metrics HTTP endpoint (port 9090 with authentication). The processor operates through a configurable plugin framework supporting pre-processors, post-processors, response-headers processors, and a profile picker that selects processing profiles per request. Built-in plugins include model selection (with filtering, scoring, and picking strategies), body-field-to-header extraction, base-model-to-header mapping via ConfigMap reconciliation, request metadata and cost metadata extraction, and session affinity scoring. The component defines a PayloadProcessorConfig CRD (llm-d.ai/v1alpha1) and watches ConfigMaps for runtime reconfiguration. Its deployment manifests include dev/e2e infrastructure with Envoy proxy and vLLM model server simulators for integration testing. [source: pkg/server/runserver.go:38-81, cmd/runner/runner.go:122-310, pkg/server/options.go:27-69, Dockerfile:50-55]

## Architectural Analysis

llm-d-inference-payload-processor follows a plugin-oriented architecture built on controller-runtime. The central design pattern is a processing pipeline: incoming Envoy ExtProc gRPC callouts pass through configurable pre-processors, a profile picker, and post-processors before responses flow back through response-headers processors. This pipeline architecture enables flexible request transformation without modifying core server logic. [source: cmd/runner/runner.go:82-98, 293-309]

The component exposes three network surfaces: the ExtProc gRPC server (port 9004) with optional self-signed TLS, a plaintext Health gRPC server (port 9005) for liveness and readiness probes, and a controller-runtime managed HTTP metrics server (port 9090) with optional bearer-token authentication and authorization. TLS on the ExtProc server is enabled by default using a runtime-generated self-signed certificate via `internal/tls/tls.go`; a separate certificate reloader in `pkg/common/certs.go` supports hot-reloading from a filesystem path using fsnotify, though the default self-signed path does not use this mechanism. [source: pkg/server/runserver.go:61-70, pkg/server/options.go:59-68, internal/tls/tls.go:34-73, pkg/common/certs.go:39-98]

The plugin system uses a factory registration pattern where all in-tree plugins register their factory functions at startup via `plugin.Register`. Plugins span multiple concerns: request handling (body-field extraction, base-model-to-header mapping), model selection (group filtering, random/weighted-random/max-score picking, cost-guard and in-flight-request scoring, session affinity), and observability (request metadata, cost metadata, model-name-to-header). Plugin configuration is loaded from either a file (`--config-file`) or inline text (`--config-text`), parsed by the config loader into pre-processors, profiles, and post-processors. [source: cmd/runner/runner.go:293-309, 259-289]

The controller-runtime manager provides Kubernetes integration: it manages the process lifecycle, hosts the metrics server, and runs controllers including a ConfigMap reconciler that feeds base-model mapping data into the plugin pipeline. RBAC is scoped to ConfigMap read access (get, list, watch) via a ClusterRole bound to the `payload-processor` service account. The deployment manifests under `deploy/` include development and e2e testing infrastructure (Envoy proxy, vLLM simulators) that are not part of the production component but serve as integration test fixtures. [source: cmd/runner/runner.go:159-196, deploy/components/ipp/rbac.yaml:7-16]

## Data Flows

- **Envoy ExtProc request processing:** Envoy sends gRPC ExtProc callouts to the payload-processor on port 9004 (TLS by default via self-signed certificate). The ExtProc server processes each request through the plugin pipeline — pre-processors extract and transform request fields, the profile picker selects a processing profile, and post-processors modify response headers and body. Modified headers and routing decisions flow back to Envoy for downstream forwarding to model servers. [source: pkg/server/runserver.go:58-81, cmd/runner/runner.go:227-244]
- **ConfigMap reconciliation:** A controller-runtime reconciler watches ConfigMap resources in the configured namespace and updates the base-model-to-header mapping used by the pre-processor plugin pipeline. RBAC permits get, list, and watch operations on ConfigMaps via the `payload-processor-auth-reviewer` ClusterRole. [source: cmd/runner/runner.go:206-211, deploy/components/ipp/rbac.yaml:7-16]
- **Metrics collection:** A controller-runtime HTTP server on port 9090 exposes Prometheus metrics at `/metrics`. Authentication and authorization are enabled by default via the `MetricsEndpointAuth` flag, which validates bearer tokens against the Kubernetes API using `filters.WithAuthenticationAndAuthorization`. [source: cmd/runner/runner.go:173-182, pkg/server/options.go:47, 67]
- **Health probes:** A separate plaintext gRPC Health server on port 9005 provides liveness and readiness probes via the standard `grpc.health.v1.Health` protocol. This server has no TLS or authentication. [source: cmd/runner/runner.go:312-322, pkg/server/options.go:29]
