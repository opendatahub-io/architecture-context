## Purpose

**Short**: The RHOAI dashboard is a multi-component web application consisting of a Go-based Kubernetes operator, a Node.js/React frontend, and a suite of Go BFF (backend-for-frontend) sidecar services that provide domain-specific API surfaces for AI/ML platform features. **Detailed**: odh-dashboard serves as the unified web console for Red Hat OpenShift AI. It is composed of three principal architectural layers: (1) the dashboard-operator, a controller-runtime Go operator that reconciles the Dashboard custom resource and manages the lifecycle of all dashboard child resources including Deployments, Services, Routes, RBAC, and sidecar containers; (2) a Node.js (Fastify) backend that serves the React/PatternFly single-page application and proxies Kubernetes API requests on behalf of authenticated users via bearer token impersonation; and (3) a federated set of Go BFF sidecar services—one per platform domain (gen-ai, model-registry, mlflow, agent-ops, automl, autorag, eval-hub, maas)—each exposing a TLS-secured HTTP API on a dedicated port and authenticating requests via configurable bearer token or internal ServiceAccount token methods. The operator manages 3 custom resource definitions (Dashboard, Workspace, WorkspaceKind) and integrates with over 20 platform CRDs including DataScienceCluster, KServe InferenceService, ModelRegistry, TrustyAI, and MLflow. Each BFF sidecar uses SubjectAccessReview and SelfSubjectAccessReview calls for per-request RBAC enforcement against the Kubernetes API. The frontend uses Webpack Module Federation to dynamically load domain-specific UI plugins from the BFF sidecars. ## Architectural Analysis

The odh-dashboard employs a federated micro-frontend architecture where each platform domain (gen-ai, mlflow, model-registry, agent-ops, automl, autorag, eval-hub, maas) is packaged as an independent Go BFF sidecar with its own container image, TLS-secured port, and Kubernetes client. This design allows domain teams to develop and ship features independently while sharing a common authentication and authorization framework. The federation configmap (`manifests/rhoai/base/federation-configmap.yaml`) defines the path-to-port routing that maps each BFF's API prefix to its dedicated port, enabling the frontend to discover and route requests to the correct sidecar.

Authentication follows a layered model: the Node.js backend reads the `x-forwarded-access-token` header (set by kube-rbac-proxy or the OpenShift OAuth proxy) to identify the user, while each Go BFF sidecar supports a configurable `--auth-method` flag that selects between `user_token` (forwarded bearer token) and `internal` (in-cluster ServiceAccount token) authentication modes. The `InjectRequestIdentity` middleware in each BFF extracts the caller identity from request headers and injects it into the request context; requests to non-API paths (health checks, static files) bypass this middleware entirely. Fine-grained authorization is enforced through Kubernetes SubjectAccessReview and SelfSubjectAccessReview calls, with the agent-ops BFF additionally implementing per-agent RBAC via SubjectAccessReview against `agents.x-k8s.io` resources.

The dashboard-operator uses controller-runtime to reconcile Dashboard, Workspace, and WorkspaceKind custom resources. It is owned by the rhods-operator (or opendatahub-operator in ODH), which creates the Dashboard CR; the dashboard-operator then provisions the full deployment topology including Deployments, Services, Routes, RBAC, NetworkPolicies, PodDisruptionBudgets, and ConfigMaps. The operator's RBAC footprint is substantial (58 rules in the ClusterRole), reflecting its role as the lifecycle manager for all dashboard sub-resources across the platform.

The Go operator binary is built with `CGO_ENABLED=1` and `-tags strictfipsruntime`, establishing dynamic linking against OpenSSL for FIPS-compliant cryptographic operations in production. The Node.js frontend/backend image inherits FIPS-capable OpenSSL from the UBI 9 base image but has no explicit FIPS build configuration at the application level. Each BFF sidecar imports `crypto/tls` and configures TLS for both its own listener and its outbound HTTP clients, with TLS certificates managed via cert-manager Certificate CRs referenced in the webhook configuration.

The component's integration surface is broad: it watches or manages CRDs from KServe, TrustyAI, MLflow, ModelRegistry, Feast, Kubeflow Notebooks, OLM, and Gateway API, making it a central integration hub for the RHOAI platform. The gen-ai BFF additionally integrates with MCP (Model Context Protocol) servers via SSE or streamable-HTTP transport, using the `X-MCP-Bearer` header for authentication. ### FIPS Compliance

The odh-dashboard is a multi-component system with different FIPS postures per image:

**Dashboard Operator (Go):** The operator binary is built with explicit FIPS build flags: `CGO_ENABLED=1` ensures dynamic linking against system OpenSSL, and `-tags strictfipsruntime` enables the Go strict FIPS runtime mode that routes all cryptographic operations through the FIPS-validated OpenSSL module. The runtime base image is `ubi9/ubi-minimal`, which includes a FIPS-validated OpenSSL installation. This is the strongest FIPS posture in the component. [source: Dockerfile.konflux.dashboard-operator:18-20]

**Go BFF Sidecars:** Each BFF sidecar (gen-ai, maas, mlflow, eval-hub, automl, autorag, agent-ops, model-registry) is built from a separate Dockerfile.konflux file. The BFF sidecars import `crypto/tls` extensively for both server and client TLS configuration. FIPS compliance for these sidecars depends on their individual Dockerfile build flags, which were not exhaustively inspected in this analysis. Each BFF uses the Go `crypto/tls` package with standard configuration, which benefits from FIPS-mode OpenSSL when built with `CGO_ENABLED=1` and `strictfipsruntime`. [source: Dockerfile.konflux.dashboard-operator:18, packages/agent-ops/bff/cmd/main.go:42]

**Node.js Frontend/Backend:** The Node.js image (`Dockerfile.konflux`) uses `ubi9/nodejs-22` as its base image. There are no explicit FIPS build flags at the application level. FIPS compliance for the Node.js component relies entirely on the UBI 9 base image's system-level OpenSSL FIPS module. Node.js uses OpenSSL for TLS operations when running on UBI 9, so TLS connections inherit FIPS-validated cryptography from the system library. No non-FIPS crypto libraries or custom cipher suite configurations were detected. [source: Dockerfile.konflux:4, Dockerfile.konflux:34]

## Data Flows

- **User request flow:** Browser requests arrive at the OpenShift Route, pass through kube-rbac-proxy which injects `x-forwarded-access-token`, `x-auth-request-user`, and `x-auth-request-groups` headers, then reach the Node.js Fastify backend on port 8443. Static SPA assets are served directly; API requests under `/api/*` are proxied to Kubernetes or downstream services using the user's forwarded bearer token for impersonation. Module federation requests under `/_mf/:name/*` are routed to the appropriate BFF sidecar. [source: backend/src/utils/constants.ts:18-19, backend/src/app.ts:4, backend/src/routes/module-federation.ts:1]
- **BFF sidecar flow:** Each domain BFF sidecar listens on its dedicated TLS port (gen-ai:8143, maas:8243, mlflow:8343, eval-hub:8543, automl:8643, autorag:8743, agent-ops:8843, model-registry:8043). The `InjectRequestIdentity` middleware extracts the caller identity from the bearer token header, then downstream handlers create per-request Kubernetes clients using the caller's token for SubjectAccessReview-based authorization before proxying to platform services. [source: packages/agent-ops/bff/internal/api/middleware.go:34-56, manifests/rhoai/base/federation-configmap.yaml:15]
- **Operator reconciliation flow:** The rhods-operator creates a Dashboard CR; the dashboard-operator's `DashboardReconciler` watches for this CR and reconciles the full deployment topology including Deployments, Services, Routes, ConfigMaps, RBAC resources, NetworkPolicies, and PodDisruptionBudgets. The Workspace and WorkspaceKind controllers handle notebook workspace lifecycle, managing StatefulSets, Services, and VirtualServices as owned resources. [source: dashboard-operator/charts/dashboard/values.yaml:17-18, dashboard-operator/config/rbac/role.yaml:1]
- **Security context:** 16 authentication rules enforce bearer token, ServiceAccount token, or Kubernetes admission authentication across all API surfaces. The operator uses in-cluster ServiceAccount token authentication against the Kubernetes API, with RBAC enforced via the odh-dashboard-operator-role ClusterRole (58 rules). TLS certificates for the webhook and metrics endpoints are provisioned via cert-manager Certificate CRs. [source: backend/src/utils/constants.ts:18, dashboard-operator/cmd/manager/main.go:101, dashboard-operator/config/webhook/manifests.yaml:1]
