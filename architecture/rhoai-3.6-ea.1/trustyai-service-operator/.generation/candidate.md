## Purpose

**Short**: Kubernetes operator that manages TrustyAI explainability services, LM evaluation jobs, guardrails orchestration, and NVIDIA NeMo Guardrails deployments for the RHOAI platform. [source: cmd/main.go:92, controllers/dsc/config.go:17]

**Detailed**: The trustyai-service-operator is a multi-controller Kubernetes operator that provisions and manages several AI trustworthiness workloads within Red Hat OpenShift AI. It reconciles six custom resource types spanning three functional domains: TrustyAI explainability services (TrustyAIService, TrustyAI module CRD), LM evaluation (EvalHub, LMEvalJob), and guardrails (GuardrailsOrchestrator, NemoGuardrails). Each TrustyAIService instance is deployed as a two-container pod pairing a Quarkus-based TrustyAI service with a kube-rbac-proxy sidecar for authenticated, TLS-secured access. The operator reads platform-level configuration from the OpenDataHub operator's DSC ConfigMap and adapts its behavior based on cluster capabilities, including optional Kueue integration for workload queuing and OpenShift TLS profile adherence. [source: cmd/main.go:92-185, controllers/dsc/config.go:17-22, controllers/tas/templates/service/deployment.tmpl.yaml:1-241]

## Architectural Analysis

The trustyai-service-operator follows a multi-controller pattern within a single manager binary, using controller-runtime's service-selection mechanism to enable subsets of controllers at startup via the `--enable-services` flag. This design allows the same operator image to serve different roles depending on the deployment context. The operator manages three distinct functional domains—explainability (TrustyAIService), evaluation (EvalHub, LMEvalJob), and guardrails (GuardrailsOrchestrator, NemoGuardrails)—each with dedicated reconciliation loops and owned resource sets. [source: cmd/main.go:97-103, cmd/main.go:151-176]

A notable architectural pattern is the operator's defense-in-depth approach to TLS. At startup, the manager resolves the cluster's TLS security profile by reading the OpenShift APIServer configuration resource (`apiservers.config.openshift.io/cluster`), falling back to Mozilla Intermediate defaults (TLS 1.2+, FIPS-compatible ECDHE cipher suites) on non-OpenShift clusters or when the API server is unavailable. This resolved TLS configuration is applied to both the metrics server and the webhook server. Each TrustyAIService instance is fronted by a kube-rbac-proxy sidecar that enforces token-review-based authentication and TLS termination on port 8443, proxying to the Quarkus service on localhost:8080. [source: pkg/tls/tls.go:73-129, controllers/tas/templates/service/deployment.tmpl.yaml:153-208, cmd/main.go:119-156]

The operator integrates with platform capabilities through runtime API discovery rather than hard requirements. Kueue support is detected at startup by querying for the `kueue.x-k8s.io/v1beta1` Workload resource; when absent, EvalHub still operates without workload queuing. Similarly, platform-level configuration for LMEval online mode and code execution permissions flows through the `trustyai-dsc-config` ConfigMap created by the OpenDataHub operator, with graceful fallback when the ConfigMap is not present. The operator also disables controller-runtime's default caching for high-volume core resources (ConfigMap, Secret, Pod, Service) to prevent OOM from cluster-wide informer cache flooding, accepting higher API server latency for infrequent reads. [source: controllers/evalhub/kueue_workloads_discovery.go:21-36, controllers/dsc/config.go:37-53, cmd/main.go:133-148]

## Data Flows

- **TrustyAI service request path:** External clients connect to the TrustyAI service via an OpenShift Route or Istio VirtualService on port 443, which terminates TLS and forwards to the kube-rbac-proxy sidecar on port 8443. The proxy performs TokenReview and SubjectAccessReview authentication against the Kubernetes API server, then forwards authenticated requests to the TrustyAI Quarkus service on localhost:8080. The Quarkus service reads/writes data to either a PVC or an external database depending on the storage format configured in the TrustyAIService CR. [source: controllers/tas/templates/service/deployment.tmpl.yaml:153-161, controllers/tas/templates/service/deployment.tmpl.yaml:42-113]
- **Operator control plane:** The operator manager watches its six CRD types and owned resources (Deployments, Services, ConfigMaps) via the Kubernetes API server. At startup, it reads the OpenShift TLS security profile and the DSC ConfigMap from the OpenDataHub operator, then conditionally checks for Kueue API availability. Configuration changes in watched resources trigger reconciliation loops that create, update, or delete child resources in tenant namespaces. [source: cmd/main.go:118-185, controllers/dsc/config.go:37-53, controllers/evalhub/kueue_workloads_discovery.go:21-36]
- **Metrics and monitoring:** The operator exposes Prometheus metrics on port 8080 (metrics-service) and on port 8443 via the kube-rbac-proxy (controller-manager-metrics-service). The EvalHub controller conditionally creates ServiceMonitor resources when the prometheus-operator CRDs are available. [source: config/prometheus/metrics-service.yaml:1, config/rbac-base/auth_proxy_service.yaml:1]
- **Webhook conversions:** CRD version conversion for EvalHub (v1 ↔ v1alpha1) and TrustyAIService (v1 ↔ v1alpha1) is handled by a webhook server on port 9443 with TLS configured from the cluster TLS profile. [source: cmd/main.go:151-176]
