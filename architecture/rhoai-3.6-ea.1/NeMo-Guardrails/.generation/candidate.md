## Purpose

**Short**: NeMo-Guardrails is a Python-based guardrails server that intercepts and validates LLM interactions, enforcing programmable safety rails on input prompts and output responses before they reach or return from upstream LLM inference services. [source: pyproject.toml:2-3, nemoguardrails/server/api.py:190-196]

**Detailed**: NeMo-Guardrails provides a FastAPI-based HTTP server that sits between client applications and LLM inference endpoints, applying configurable guardrail policies to conversational interactions. The server exposes an OpenAI-compatible chat completions API (`/v1/chat/completions`, `/v1/completions`) alongside a dedicated guardrail checks endpoint (`/v1/guardrail/checks`) that evaluates messages against input and output rails without generating LLM responses. The toolkit supports pluggable rail types including jailbreak detection, fact-checking with AlignScore, prompt security via external services, and PII detection using Presidio. NeMo-Guardrails connects to upstream LLM providers (configurable via `MAIN_MODEL_ENGINE` and `MAIN_MODEL_BASE_URL` environment variables, defaulting to OpenAI-compatible endpoints) and forwards Authorization headers from incoming requests. The RHOAI distribution builds on the AIPCC CPU base image and includes OpenTelemetry instrumentation for observability. The server has no built-in authentication; access control is expected to be enforced at the platform level. [source: pyproject.toml:2-3, nemoguardrails/server/api.py:190-196, nemoguardrails/server/api.py:281-285, nemoguardrails/server/api.py:356-367, nemoguardrails/server/checks.py:479-491, Dockerfile.konflux:0-1]

## Architectural Analysis

NeMo-Guardrails follows a middleware-proxy architecture where the FastAPI server intercepts LLM-bound requests, applies a pipeline of configurable guardrail policies (input rails, output rails, and tool-input rails), and proxies validated requests to the upstream LLM provider. The server is stateless by default, though it supports an optional Redis-backed datastore for thread persistence. Configuration is directory-driven: the server scans a config path for YAML-based guardrail configurations, supporting both single-config and multi-config deployment modes. [source: nemoguardrails/server/api.py:69-81, nemoguardrails/server/api.py:132-196]

The guardrails toolkit is modular, with safety libraries (jailbreak detection, fact-checking, prompt security, PII detection) implemented as pluggable actions that can invoke external services. Each library may have its own standalone server (e.g., AlignScore on port 5000, jailbreak detection on port 1337), though the primary deployment model for RHOAI is the unified guardrails server on port 8000. The Konflux build uses the AIPCC CPU base image and includes pre-fetched ML models for offline operation. [source: Dockerfile.konflux:0-1, Dockerfile.konflux:33-38, Dockerfile.konflux:67]

A notable architectural characteristic is the absence of built-in authentication: the server forwards `Authorization` headers from incoming requests to upstream LLM providers but does not validate them for its own API surface. This design assumes platform-level access control (e.g., Kubernetes NetworkPolicy, service mesh, or API gateway). The server includes CORS middleware that is disabled by default and configurable via environment variables. [source: nemoguardrails/server/api.py:198-213, nemoguardrails/server/api.py:281-285]

## Data Flows

- **Client request ingestion:** Client applications send chat completion requests or guardrail check requests to the NeMo-Guardrails FastAPI server on port 8000. The server accepts OpenAI-compatible payloads at `/v1/chat/completions`, `/v1/completions`, and `/v1/guardrail/checks`. If an `Authorization` header is present, it is captured for forwarding to the upstream LLM provider. The server does not validate or enforce authentication on incoming requests. [source: nemoguardrails/server/api.py:190-196, nemoguardrails/server/api.py:281-285, nemoguardrails/server/checks.py:479-491]
- **Guardrail evaluation pipeline:** Incoming messages are routed through configurable rail pipelines: user and system messages pass through input rails, assistant messages through output rails, and tool messages through tool-input rails. Rails can invoke pluggable action libraries (jailbreak detection, fact-checking, PII detection, prompt security) which may call external services. [source: nemoguardrails/server/checks.py:484-491, pyproject.toml:45-80]
- **Upstream LLM proxy:** For chat completion requests that pass input rails, the server proxies the validated request to the upstream LLM provider configured via `MAIN_MODEL_ENGINE` (default: `openai`) and `MAIN_MODEL_BASE_URL`. The forwarded request includes any captured `Authorization` header. LLM responses pass through output rails before being returned to the client. [source: nemoguardrails/server/api.py:356-367, nemoguardrails/server/api.py:281-285]
- **External service integrations:** The guardrails toolkit integrates with external services via API keys stored in environment variables (16 secret references covering providers such as ActiveFence, AI Defense, Prompt Security, and others). The Azure OpenAI SDK client constructs outbound HTTPS connections on port 443. [source: nemoguardrails/embeddings/providers/azureopenai.py:49-53]
