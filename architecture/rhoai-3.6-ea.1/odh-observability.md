## Purpose

**Short**: odh-observability is a Kubernetes operator that deploys and manages a unified observability stack—Prometheus monitoring, distributed tracing via Tempo, and usage log collection via LokiStack—for the RHOAI platform through a singleton cluster-scoped `Monitoring` custom resource. [source: api/v1alpha1/monitoring_types.go:39-66, cmd/main.go:61-155, charts/odh-observability/crds/services.platform.opendatahub.io_monitorings.yaml:2]

**Detailed**: odh-observability implements a controller-runtime operator that reconciles a cluster-scoped `Monitoring` custom resource (`services.platform.opendatahub.io/v1alpha1`) to deploy and configure a complete observability stack for RHOAI. The operator manages Prometheus-based metrics collection with configurable storage and retention, distributed tracing through the Tempo operator with S3/GCS/PV storage backends, and usage log collection via LokiStack with OpenTelemetry collectors. It deploys kube-rbac-proxy sidecars for authenticated Prometheus access through SubjectAccessReview-based authorization and creates OpenShift Routes for external TLS exposure. The operator uses odh-platform-utilities for server-side-apply deployment via the `deploy.Deployer`, platform detection, and shared API types including the `PlatformObject` interface for standardized status and condition management across RHOAI services. A mutating admission webhook injects monitoring labels into PodMonitor and ServiceMonitor resources to ensure consistent metrics collection across data science workloads. [source: api/v1alpha1/monitoring_types.go:20-41, cmd/main.go:40-134, internal/controller/resources/data-science-prometheus-cluster-proxy.tmpl.yaml:58-93, Dockerfiles/Dockerfile.konflux:19]

## Architectural Analysis

odh-observability follows a reconciler pattern built on controller-runtime, with a single `MonitoringReconciler` watching the cluster-scoped `Monitoring` CR and managing a broad set of dependent resources through server-side apply. The operator uses odh-platform-utilities' `deploy.Deployer` configured with SSA mode and ordered apply, which renders Go templates into Kubernetes manifests and applies them declaratively without conflict with Helm or other field managers. [source: cmd/main.go:109-114]

The architecture has three functional tiers. The operator itself runs as a single manager process exposing health probes on port 8081 and an optional webhook on port 9443. The data plane consists of controller-managed Prometheus instances, kube-rbac-proxy sidecars for both cluster-scoped and namespace-scoped proxy access, prom-label-proxy for namespace-scoped metric filtering, and OpenTelemetry collectors for metrics processing and usage log forwarding to LokiStack. External access is provided through three OpenShift Routes—two for Prometheus proxy endpoints and one for Thanos Querier—all using TLS. [source: cmd/main.go:70-74, 86-101, internal/controller/resources/data-science-prometheus-cluster-proxy.tmpl.yaml:58-97]

Authentication at the proxy layer is enforced by kube-rbac-proxy, which performs SubjectAccessReview checks delegated via `system:auth-delegator` ClusterRoleBindings before proxying to the upstream Prometheus. The cluster proxy specifically restricts access to the `/metrics` path and requires `metrics.k8s.io/nodes/get` authorization. TLS is enforced end-to-end: the proxy uses its own serving certificate while connecting to Prometheus via mTLS with dedicated client certificates and CA verification. [source: internal/controller/resources/data-science-prometheus-cluster-proxy.tmpl.yaml:26-56, 82-91]

The CRD design enforces configuration invariants through CEL validation rules—requiring storage configuration when alerting is enabled, enforcing singleton semantics via the `default-monitoring` name constraint, and validating collector replica counts against storage configuration. The `Monitoring` type implements the `platformcommon.PlatformObject` interface from odh-platform-utilities, which standardizes status conditions and component release tracking across RHOAI platform services. [source: api/v1alpha1/monitoring_types.go:34-38, 197-200]

A notable design choice is the webhook self-enablement pattern: the reconciler checks for a cert-manager-provisioned TLS secret and, when found, patches its own Deployment to add the `--enable-webhook=true` argument, webhook port, volume mount, and cert volume via strategic merge patch. This defers webhook activation until TLS infrastructure is ready, avoiding startup failures in environments where cert-manager is not yet operational. [source: internal/controller/actions.go:580-614, 618-622]
