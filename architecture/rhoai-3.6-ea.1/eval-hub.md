## Purpose

**Short**: Evaluation orchestration service that manages evaluation job lifecycle, provider configurations, and result export for RHOAI, using a sidecar pattern for credential injection and model proxying. **Detailed**: eval-hub is a multi-binary Go application service that orchestrates model evaluation workflows within Red Hat OpenShift AI. The primary `eval-hub` binary serves a REST API on port 8080 for managing evaluation jobs, collections, and inference provider configurations, persisting state in PostgreSQL (production) or SQLite (development) via a pluggable SQL storage layer. The `eval-runtime-sidecar` binary runs alongside evaluation pods as a credential-injecting reverse proxy, resolving placeholder API key references from mounted Kubernetes Secrets before forwarding requests to model endpoints. The `eval-runtime-init` binary handles test data downloads from S3-compatible storage. The `evalhub-mcp` binary implements a Model Context Protocol server for AI tool integration, and `validate-configs` provides offline configuration validation. The service creates Kubernetes Jobs with sidecar containers for evaluation execution, manages ConfigMaps, Secrets, and HardwareProfile custom resources, and exports evaluation results to MLflow for experiment tracking and OCI registries via evalcards. ## Architectural Analysis

eval-hub follows a hub-and-spoke evaluation orchestration pattern. The central API server receives evaluation requests via a standard-library `net/http.ServeMux` router, creates Kubernetes Jobs with sidecar containers for credential injection and model proxying, and tracks job lifecycle through database state and Kubernetes resource operations. The architecture separates concerns across five binaries compiled from a single Go module, each with a distinct deployment role: API server, runtime sidecar proxy, init container, MCP server, and configuration validator. [source: internal/eval_hub/server/server.go:29-39, 441-485, Dockerfile.konflux:27-52]

Authentication is conditional and platform-delegated: in cluster mode, API endpoints enforce `X-User` and `X-Tenant` identity headers expected to be injected by an upstream gateway or kube-rbac-proxy, while local/development mode bypasses identity enforcement entirely. Health, documentation, and OpenAPI endpoints are explicitly exempt from identity checks. This design assumes correct perimeter authentication configuration in production. [source: internal/eval_hub/server/server.go:210-213, 430-438, 441-465]

The storage layer abstracts over PostgreSQL (via `pgx` driver, production) and SQLite (via `modernc.org/sqlite`, development/test) through a configurable driver selection pattern with OpenTelemetry SQL instrumentation. Tenant and user context are applied at the storage query level. [source: internal/eval_hub/storage/sql/sql.go:14-18, 33-37, 51-79]

The sidecar credential injection pattern is architecturally significant: `eval-runtime-sidecar` acts as a reverse proxy that reads model credentials from Kubernetes Secret mounts and injects them into proxied requests, preventing the evaluation adapter container from accessing raw API keys. TLS configuration is independently configurable per integration target (MLflow, OCI registry, eval-hub client, model endpoint) with custom CA certificate path support. [source: internal/eval_hub/config/sidecar_config.go:8-17, 24-29, 34-37, 39-47, 53-59]

Observability spans three pillars: Prometheus metrics via a dedicated MetricsServer on a separate port in cluster mode with request-ID correlation middleware, OpenTelemetry traces/metrics/logs exported via OTLP/gRPC, and structured `slog`-based logging with `X-Global-Transaction-Id` propagation. [source: internal/eval_hub/server/metrics_server.go:16-43, internal/eval_hub/server/server.go:41-43, 130-136, 197-208]

The build pipeline uses `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` on a UBI9 base image for all four shipped binaries, establishing FIPS 140 build-time compliance through dynamic linking to system OpenSSL. No Kubernetes Service or deployment manifests are present in this repository; the service is expected to be deployed by a parent operator or platform manifest system. ## Data Flows

- **Evaluation job lifecycle:** Clients submit evaluation requests to the eval-hub API (port 8080) with identity headers (`X-User`, `X-Tenant`) when cluster-mode enforcement is active. The API server validates the request, persists job state in the SQL database (PostgreSQL or SQLite), and creates a Kubernetes Job with an init container (`eval-runtime-init` for S3 test data download) and a sidecar container (`eval-runtime-sidecar` for model credential injection and proxying). The evaluation adapter runs as the primary container, communicating with the model endpoint through the sidecar's reverse proxy. [source: internal/eval_hub/server/server.go:441-485, internal/eval_hub/runtimes/k8s/k8s_helper.go:99-134, internal/eval_hub/storage/sql/sql.go:51-79, Dockerfile.konflux:27-52]
- **Result export:** Evaluation results flow from the evaluation runtime through the sidecar to the eval-hub API, which exports them to MLflow for experiment tracking and optionally to OCI registries via the evalcards publisher. The sidecar configures its upstream connections with independent TLS settings and optional custom CA certificates. [source: internal/eval_hub/server/server.go:87-101, internal/eval_hub/config/sidecar_config.go:8-17, 39-47, 49-59]
- **Kubernetes resource management:** The KubernetesHelper manages ConfigMaps (evaluation configuration), Secrets (credential references), Jobs (evaluation execution), and HardwareProfile CRs (hardware requirements) via typed and dynamic Kubernetes API clients over HTTPS/WSS to the kube-apiserver at port 6443. [source: internal/eval_hub/runtimes/k8s/k8s_helper.go:77-97, 99-151]
- **Observability pipeline:** Prometheus metrics are served on a dedicated MetricsServer port (cluster mode) or the main API port (local mode). When OpenTelemetry is enabled, traces, metrics, and logs are exported via OTLP/gRPC to an OpenTelemetry Collector. [source: internal/eval_hub/server/metrics_server.go:23-43, internal/eval_hub/server/server.go:467-474]
