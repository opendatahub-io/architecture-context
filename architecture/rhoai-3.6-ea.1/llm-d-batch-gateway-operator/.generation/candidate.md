## Purpose

**Short**: Kubernetes operator that manages the lifecycle of LLMBatchGateway custom resources, deploying batch inference gateway components via embedded Helm charts with optional cert-manager TLS, Gateway API routing, and Prometheus monitoring integration. [source: cmd/main.go:86, config/crd/bases/batch.llm-d.ai_llmbatchgateways.yaml:2, internal/controller/llmbatchgateway_controller.go:61-71]

**Detailed**: llm-d-batch-gateway-operator is a controller-runtime-based Kubernetes operator that reconciles `LLMBatchGateway` custom resources (batch.llm-d.ai/v1alpha1). On each reconciliation, it renders two embedded Helm charts — `batch-gateway` and `async-processor` — to deploy the batch inference gateway stack, which includes an API server, request processor, garbage collector, and optional async processor components. The operator manages the full lifecycle of chart-produced resources including Deployments, Services, ConfigMaps, ServiceAccounts, cert-manager Certificates, Gateway API HTTPRoutes, and Prometheus monitoring resources (ServiceMonitors, PodMonitors, PrometheusRules).

The operator supports cross-namespace Secret access via Gateway API ReferenceGrant verification, enabling secure credential sharing between namespaces. A separate MetricsController programmatically creates and maintains the operator's own metrics Service, ServiceMonitor, and PrometheusRule resources. Component images for the deployed stack are configured via environment variables, and the operator tracks deployment readiness through granular status conditions per component. [source: cmd/main.go:109-178, internal/controller/llmbatchgateway_controller.go:59-71, 544-571, internal/controller/secret_sync.go:50-118, internal/monitoring/controller.go:41-48, config/manager/manager.yaml:26-41]

## Architectural Analysis

The operator follows the Helm-rendering controller pattern: rather than constructing Kubernetes resources imperatively, it embeds two upstream Helm charts (`batch-gateway` and `async-processor`) and renders them with values derived from the `LLMBatchGateway` CR spec. This design delegates resource structure to the upstream charts while the operator manages lifecycle, drift detection (via a configurable sync period), and status reporting. The `managedGVKs` list declares every resource type the charts may produce, enabling the reconciler to prune orphaned resources when chart output changes. [source: internal/controller/llmbatchgateway_controller.go:59-71, cmd/main.go:95-96, 100]

Platform dependencies are handled conditionally: cert-manager Certificates, Gateway API HTTPRoutes, and prometheus-operator monitoring resources are only watched and owned when their respective CRDs are detected in the cluster's REST mapper at startup. This makes the operator deployable on clusters without cert-manager or the Prometheus stack, gracefully degrading TLS certificate provisioning and observability integration. The ReferenceGrant-gated cross-namespace Secret sync is particularly notable — it enforces Gateway API's reference authorization model to safely copy Secrets across namespace boundaries, with an immutability check that prevents mutation of established credential references. [source: internal/controller/llmbatchgateway_controller.go:554-569, internal/controller/secret_sync.go:53-118]

The operator deploys four downstream components (API server, processor, GC, and async processor) whose images are injected via environment variables at the operator Deployment level. The async processor is conditionally deployed only when `spec.processor.asyncConfig` is present on the CR. Each component's availability is tracked through dedicated status conditions, giving platform operators granular visibility into partial-ready states. [source: cmd/main.go:123-127, config/manager/manager.yaml:34-41, internal/controller/llmbatchgateway_controller.go:36-49]

## Data Flows

- **Reconciliation loop:** When a `LLMBatchGateway` CR is created or updated, the `LLMBatchGatewayReconciler` renders the embedded `batch-gateway` and `async-processor` Helm charts with values derived from the CR spec, then applies the resulting resources (Deployments, Services, ConfigMaps, ServiceAccounts, Certificates, HTTPRoutes, and monitoring resources) via server-side apply. Orphaned resources from previous chart renders are pruned. [source: internal/controller/llmbatchgateway_controller.go:59-71, 544-571]
- **Cross-namespace Secret sync:** When a `LLMBatchGateway` references a Secret in a different namespace, the controller verifies a matching `ReferenceGrant` exists in the source namespace, reads the source Secret, and creates a managed copy in the gateway's namespace. The Secret reference is immutable once established. [source: internal/controller/secret_sync.go:50-118]
- **Metrics service lifecycle:** The `MetricsController` creates and maintains a `llm-d-batch-gateway-operator-metrics` ClusterIP Service (port 8443/TCP), a ServiceMonitor, and a PrometheusRule with alerting rules. These are reconciled via server-side apply and watched for drift. The controller bootstraps on startup and re-reconciles on changes to the owned resources. [source: internal/monitoring/controller.go:93-117, 119-143, 146-171]
- **Operator probes:** The manager exposes health (`/healthz`) and readiness (`/readyz`) probes on port 8081 and a metrics endpoint on port 8443, both served by controller-runtime. The operator authenticates to the Kubernetes API via an in-cluster ServiceAccount token with RBAC governed by the `llm-d-batch-gateway-operator` ClusterRole. [source: cmd/main.go:97-98, 109-117, 152-156]
