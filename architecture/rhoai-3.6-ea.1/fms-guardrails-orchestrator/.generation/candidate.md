## Purpose

**Short**: REST API orchestrator that coordinates AI text generation with content safety guardrails, acting as middleware between clients and language models by routing requests through configurable detector and chunker services. [source: Cargo.toml:1-2, Dockerfile.konflux:71-72, src/server/routes.rs:70-108]

**Detailed**: The FMS Guardrails Orchestrator is a Rust service built on axum and tonic that provides a unified REST API for safe AI text generation. It accepts client requests on v1 and v2 API surfaces (port 8033/TCP), orchestrates content safety detection by forwarding text to configurable detector services via REST, chunks text via gRPC chunker services, and coordinates generation through a TGIS or caikit-nlp gRPC backend. A separate health server (port 8034/TCP) provides unauthenticated health and info endpoints. The service supports optional TLS and mTLS on its ingress surface, passthrough of configurable client headers to downstream services, and rewriting of X-Forwarded-Access-Token headers to Authorization Bearer for downstream authentication. Two additional v2 endpoints for OpenAI-compatible chat and text completions detection are conditionally enabled when an OpenAI-compatible generation backend is configured. The orchestrator is built for multi-architecture deployment (amd64, ppc64le, s390x) on UBI 9 minimal base images. [source: Cargo.toml:1-7, config/config.yaml:1-70, src/server/routes.rs:62-108, src/args.rs:31-47]

## Architectural Analysis

The orchestrator follows a middleware proxy pattern: it sits between API clients and multiple backend services (generation, detection, chunking), adding safety guardrails to the text generation pipeline. The axum HTTP framework handles inbound REST requests on port 8033, while tonic-generated gRPC clients communicate with downstream TGIS generation and caikit chunker services. Detector services are reached via reqwest REST clients. Each downstream service type supports independent TLS configuration through a named TLS map in the YAML config, allowing per-service certificate and CA bundles. [source: config/config.yaml:53-66, Cargo.toml:56-65, 85-89]

The service does not expose any gRPC server surface; `build.rs` explicitly sets `build_server(false)` when compiling proto definitions, generating only client stubs for chunker (caikit Chunkers API), NLP (caikit NLP API), generation (TGIS API), and health check protocols. [source: build.rs:9-21]

Authentication is passthrough-based rather than enforced: configurable header names are forwarded from client requests to downstream services, and an optional X-Forwarded-Access-Token rewrite converts forwarded access tokens into Authorization Bearer headers for downstream consumption. The orchestrator itself does not validate tokens or enforce authorization policies; it delegates authentication to the downstream services and to the platform's ingress layer. TLS and mTLS on the inbound surface are optional, controlled by CLI flags and environment variables. [source: src/server/routes.rs:452-480, src/args.rs:43-47, config/config.yaml:67-70]

The cryptographic stack uses rustls with the ring provider throughout (rustls, hyper-rustls, tokio-rustls, tonic TLS). Ring is not a FIPS-validated cryptographic provider, which means the service cannot claim FIPS compliance for its TLS operations. OpenSSL is present only in the build stage for protobuf compilation and is not installed in the release image. [source: Cargo.toml:33-34, 62-65, 81-83, 85-88, Dockerfile.konflux:17, 51-53]
