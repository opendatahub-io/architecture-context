## Purpose

**Short**: Rust-based guardrails orchestration service that intercepts LLM inference requests, applies configurable content detection and classification via downstream detector and chunker services, and forwards validated requests to text generation backends over gRPC and REST. [source: Cargo.toml:1-2, config/config.yaml:6-46, src/server/routes.rs:70-108]

**Detailed**: fms-guardrails-orchestrator is an application-level service that sits between API consumers and LLM generation backends, orchestrating content safety guardrails. It exposes a dual-port HTTP surface: port 8033 serves the guardrails API with 10 POST endpoints spanning v1 classification-with-generation and v2 detection/completions routes, while port 8034 hosts unauthenticated health and info endpoints. The service fans out to four categories of downstream dependencies over gRPC and REST: TGIS generation service (gRPC, port 8033), chunker services (gRPC, port 8085), detector services (REST, port 8080), and detector health services (REST, port 8081). TLS is optional on both inbound and outbound connections, configured per-service via named TLS blocks in the YAML configuration. Authentication is passthrough-based: configurable request headers are forwarded to downstream services, with optional X-Forwarded-Access-Token to Authorization Bearer rewrite. The service is built as a single Rust binary (`fms-guardrails-orchestr8`) using axum for HTTP routing and tonic for gRPC client communication, with multi-architecture container images for amd64, ppc64le, and s390x. [source: src/args.rs:32-47, src/server/routes.rs:62-108, config/config.yaml:1-70, build.rs:7-9, Cargo.toml:19-89]

## Architectural Analysis

The orchestrator follows a request-interception pattern: incoming HTTP requests on the guardrails API port (8033) are routed through axum handlers that coordinate content safety checks before or alongside text generation. Each detection endpoint orchestrates a fan-out to one or more downstream detector services over REST and chunker services over gRPC, then combines their results with generation output from a TGIS backend. The v2 API surface adds streaming content detection, chat-oriented detection, and context-document analysis alongside the original v1 classification-with-generation flow. Two v2 endpoints (`/api/v2/chat/completions-detection` and `/api/v2/text/completions-detection`) are conditionally registered only when an OpenAI-compatible generation backend is configured. [source: src/server/routes.rs:70-108, config/config.yaml:14-18]

The service uses tonic exclusively as a gRPC client; `build.rs` compiles proto definitions for TGIS generation, caikit NLP, chunker, and health-check services with `build_server(false)`, confirming that no gRPC server surface is exposed. [source: build.rs:8-9]

TLS is layered at two points: the inbound server surface supports optional TLS and mutual TLS via rustls (configured through CLI arguments for cert, key, and client CA paths), while outbound connections to detectors and chunkers use per-service TLS blocks defined in the YAML configuration with optional client certificates and an `insecure` toggle. The crypto provider is `ring` throughout—explicitly selected in Cargo.toml features for rustls, hyper-rustls, tokio-rustls, and rustls-webpki. Ring is not a FIPS-validated provider, which means the application's TLS does not use FIPS-validated cryptography regardless of the host platform. [source: Cargo.toml:33-34, 62-65, 81-83, 85-89, src/args.rs:43-47, config/config.yaml:53-66]

Authentication is delegated rather than enforced locally: the orchestrator forwards a configurable set of request headers to downstream services and optionally rewrites X-Forwarded-Access-Token into an Authorization Bearer header for downstream consumption. Health and info endpoints on port 8034 are intentionally unauthenticated. [source: src/server/routes.rs:451-480, config/config.yaml:67-70]

Observability is integrated via OpenTelemetry with configurable OTLP export for traces and metrics, supporting both gRPC and HTTP protocols. [source: src/args.rs:51-73, Cargo.toml:47-53]

### FIPS Compliance

#### Build-Time FIPS

This is a Rust binary, not a Go binary, so Go-specific FIPS build flags (GOEXPERIMENT, CGO_ENABLED) do not apply. The Konflux Dockerfile builds with `cargo build --release` without any FIPS-specific Rust compiler flags. The application uses rustls with the `ring` cryptographic provider, explicitly selected via Cargo.toml feature flags across all TLS-related dependencies.
