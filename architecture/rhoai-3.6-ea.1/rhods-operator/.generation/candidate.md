## Purpose

**Short**: rhods-operator is the RHOAI platform operator that orchestrates the lifecycle of all OpenShift AI components, managing their deployment, configuration, monitoring, and ingress through a set of custom resources and reconciliation controllers. [source: cmd/main.go:293, internal/controller/services/auth/auth_controller.go:57, internal/controller/services/gateway/gateway_controller.go:41]

**Detailed**: rhods-operator serves as the central control plane for Red Hat OpenShift AI (RHOAI). It defines and reconciles a hierarchy of custom resources—DataScienceCluster, DSCInitialization, and per-component CRDs such as DataSciencePipelines, Kueue, ModelRegistry, Ray, and KServe—that declaratively describe the desired state of the AI/ML platform. The operator deploys and manages each component's manifests via kustomize-based rendering and template actions, while a set of service controllers handle cross-cutting concerns: the Auth service controller manages RBAC group policies and watches for dependent namespaces (models-as-a-service, kuadrant-system), the Gateway service controller provisions a data-science gateway with kube-auth-proxy OIDC infrastructure and conditionally integrates with Istio (EnvoyFilter, DestinationRule) and OpenShift OAuth, and the Monitoring service controller deploys Prometheus proxies and collectors for platform-level observability. A companion cloudmanager binary handles cloud-provider Kubernetes engine resources (AWS, Azure, CoreWeave). The operator exposes 19 CRDs, serves admission webhooks on port 9443 with service-ca TLS, and reads the cluster APIServer TLS profile to align its own TLS configuration with the platform-wide security policy. ## Architectural Analysis

rhods-operator follows a layered controller-runtime reconciliation architecture with three distinct controller tiers: a top-level DataScienceCluster controller that owns the platform lifecycle, per-component controllers (DataSciencePipelines, Kueue, ModelRegistry, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI) that manage individual AI/ML workload components, and service controllers (Auth, Gateway, Monitoring) that handle cross-cutting platform infrastructure.

The Gateway service controller is the most architecturally complex service, provisioning a full ingress chain: it creates a GatewayClass and Kubernetes Gateway, deploys a kube-auth-proxy with OIDC support for authenticated dashboard access, manages OpenShift Routes for external exposure, and conditionally integrates with Istio by dynamically owning EnvoyFilter and DestinationRule resources when their CRDs are detected at runtime. On non-ROSA OpenShift clusters with integrated OAuth, it additionally owns OAuthClient resources. The controller watches the cluster APIServer resource to synchronize its TLS configuration (minimum TLS version and cipher suites) with the platform-wide TLS security profile. [source: internal/controller/services/gateway/gateway_controller.go:42-88, pkg/tls/profile.go:151-162]

The Auth service controller manages a template-driven RBAC system that provisions admin-group and allowed-group cluster roles and role bindings. It watches for the creation and deletion of the `models-as-a-service` and `kuadrant-system` namespaces to trigger reconciliation, establishing runtime coupling with the MaaS and Kuadrant subsystems without direct API dependency. [source: internal/controller/services/auth/auth_controller.go:56-88]

Security enforcement follows a defense-in-depth pattern: admission webhooks validate and default DataScienceCluster and DSCInitialization resources with a fail-closed policy, the metrics endpoint uses Kubernetes authentication and authorization filters when secure serving is enabled, and all webhook traffic is encrypted via OpenShift service-ca provisioned TLS certificates. The operator builds with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, ensuring FIPS-compliant cryptographic primitives on RHEL hosts. ## Data Flows

- **Admission and webhook flow:** The Kubernetes API server sends admission requests to the operator's webhook server on port 9443 (TLS via service-ca certificate `opendatahub-operator-controller-webhook-cert`). Mutating webhooks default DataScienceCluster v1/v2 resources, and validating webhooks enforce singleton constraints on DataScienceCluster and DSCInitialization resources. A mutating webhook injects monitoring labels into PodMonitor resources. [source: cmd/main.go:493-494, internal/webhook/datasciencecluster/v1/defaulting.go:22, internal/webhook/datasciencecluster/v1/validating.go:28]
- **Component reconciliation flow:** When a DataScienceCluster or DSCInitialization CR changes, the top-level controller reads the desired component states and triggers per-component controllers. Each component controller renders its manifests via kustomize/template actions, deploys them to the cluster via the Kubernetes API, and owns the resulting Deployments, Services, RBAC resources, and monitoring objects. [source: internal/controller/services/auth/auth_controller.go:57-87, internal/controller/services/gateway/gateway_controller.go:41-103]
- **Gateway ingress chain:** The gateway controller provisions a Gateway API chain: GatewayClass, Gateway, HTTPRoutes, and OpenShift Routes for external TLS-terminated access. A kube-auth-proxy deployment provides OIDC-authenticated access to the dashboard. On OpenShift clusters with integrated OAuth, an OAuthClient resource is created. The controller conditionally creates Istio EnvoyFilter and DestinationRule resources when detected. [source: internal/controller/services/gateway/gateway_controller.go:42-103]
- **Monitoring data flow:** The monitoring service controller deploys Prometheus proxies (cluster-proxy and namespace-proxy) with kube-rbac-proxy sidecars, a collector for MLflow trace export, and Routes for external Prometheus and Thanos querier access. All monitoring Routes use TLS. [source: internal/controller/services/monitoring/resources/data-science-prometheus-cluster-proxy.tmpl.yaml:59, internal/controller/services/monitoring/resources/data-science-prometheus-route.tmpl.yaml:1]
- **Security context:** 7 authentication rules and 11 secret references are documented in the Security section. The metrics endpoint enforces Kubernetes authentication and authorization when secure serving is enabled. The operator reads the cluster APIServer TLS security profile to configure its own TLS parameters. [source: cmd/main.go:483-485, pkg/tls/profile.go:151-162]
