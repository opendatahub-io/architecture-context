## Purpose

**Short**: rhods-operator is the central lifecycle operator for Red Hat OpenShift AI, managing deployment, configuration, and reconciliation of all AI/ML platform components through DataScienceCluster and DSCInitialization custom resources. **Detailed**: rhods-operator is a controller-runtime Kubernetes operator that orchestrates the full RHOAI platform stack. It exposes two primary cluster-scoped CRDs—DataScienceCluster (v1/v2) and DSCInitialization (v1/v2)—as the platform-level configuration surface. Per-component CRDs (DataSciencePipelines, Kueue, ModelRegistry, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI) let administrators enable and configure individual AI/ML capabilities. A services layer manages cross-cutting infrastructure: the Auth service reconciles RBAC and namespace-level permissions with integration points to Kuadrant and models-as-a-service namespaces [source: internal/controller/services/auth/auth_controller.go:63-75], the Gateway service manages ingress routing through Gateway API with conditional Istio support [source: internal/controller/services/gateway/gateway_controller.go:47-58], and the Monitoring service manages Prometheus observability resources. The operator produces two binaries—the main `manager` and a `cloudmanager` for multi-cloud Kubernetes engine management—both built with FIPS-compliant settings (GOEXPERIMENT=strictfipsruntime, CGO_ENABLED=1) on UBI 9 [source: Dockerfiles/Dockerfile.konflux:56-59]. ## Architectural Analysis

rhods-operator follows a layered controller architecture built on controller-runtime v0.24.1. The top layer consists of two platform-scoped reconcilers—DSCInitializationReconciler and DataScienceClusterReconciler—which drive cluster-wide initialization and component lifecycle. Beneath them, per-component controllers (one per AI/ML capability CRD) and per-service controllers (Auth, Gateway, Monitoring) handle fine-grained reconciliation. This separation allows individual components to be enabled, disabled, or upgraded independently while the platform services ensure consistent cross-cutting infrastructure. [source: cmd/main.go:527-565]

The gateway service controller implements a multi-mode ingress strategy. It owns Gateway API resources (GatewayClass, Gateway, HTTPRoute) and conditionally manages Istio service mesh resources (EnvoyFilter, DestinationRule) when their CRDs are available on the cluster, enabling transparent support for both Gateway API-native and Istio-backed deployments. The controller also deploys a kube-auth-proxy infrastructure for authentication at the gateway layer and handles ROSA-specific OAuth integration by conditionally creating OAuthClient resources when integrated OAuth is detected. [source: internal/controller/services/gateway/gateway_controller.go:40-109]

The auth service controller manages namespace-scoped RBAC policies and watches two external namespaces—"models-as-a-service" and "kuadrant-system"—to trigger reconciliation when those integration targets are created or removed. This enables the operator to dynamically provision or clean up authorization resources in response to the availability of dependent platform components. [source: internal/controller/services/auth/auth_controller.go:56-87]

TLS configuration is derived from the OpenShift cluster-wide TLS security profile (via the APIServer resource) rather than hardcoded, ensuring that both the webhook server (port 9443) and the metrics server follow the cluster's configured minimum TLS version and cipher suites. Unsupported TLS versions (1.0/1.1) are automatically floored to the Intermediate profile. The operator registers a SecurityProfileWatcher that cancels the manager context on TLS profile changes, causing a pod restart to pick up new settings. [source: cmd/main.go:468-469, pkg/tls/profile.go:137-148, cmd/main.go:597-599]

The admission webhook surface comprises 10 webhooks: conversion webhooks for DataScienceCluster and DSCInitialization multi-version support, mutating webhooks for v1/v2 DataScienceCluster defaulting and Prometheus monitor injection, and validating webhooks for DataScienceCluster (v1/v2), DSCInitialization (v1/v2), accelerator profiles, and hardware profiles. All webhooks are served on port 9443 with TLS from the OpenShift service-ca operator. [source: cmd/main.go:477-480, cmd/main.go:522-525]

## Data Flows

- **Admission and API surface:** The Kubernetes API server sends admission requests to the operator's webhook server (port 9443, TLS) for CRD validation, defaulting, and conversion. The operator exposes health probes on port 8081 (HTTP, unauthenticated) and a metrics endpoint on port 8443 (TLS, RBAC-protected via opendatahub-operator-metrics-reader ClusterRole). All webhook and metrics TLS configuration derives from the cluster-wide OpenShift TLS security profile. [source: cmd/main.go:476-480, cmd/main.go:588-592, config/rbac/auth_proxy_service.yaml:1]
- **Controller reconciliation:** DSCInitializationReconciler and DataScienceClusterReconciler watch their respective CRDs and cascade reconciliation to per-component controllers (DataSciencePipelines, Kueue, ModelRegistry, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI) and per-service controllers (Auth, Gateway, Monitoring). Each controller owns its downstream Kubernetes resources (Deployments, Services, RBAC, NetworkPolicies) and watches for cross-resource triggers such as ConfigMap changes, namespace events, and CRD availability.
