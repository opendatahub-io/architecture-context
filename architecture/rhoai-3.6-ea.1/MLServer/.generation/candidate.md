## Purpose

**Short**: MLServer is a Python-based model serving runtime implementing the KServe V2 Inference Protocol over both REST (FastAPI/uvicorn on port 8080) and gRPC (port 8081), deployed as a KServe ServingRuntime container in RHOAI. [source: mlserver/rest/app.py:60-162, mlserver/grpc/server.py:75-89, mlserver/settings.py:429-436]

**Detailed**: MLServer provides a pluggable model serving infrastructure that implements the V2 Inference Protocol (also known as the Open Inference Protocol). It exposes a dual-protocol API surface: REST endpoints via FastAPI/uvicorn on port 8080 and gRPC services on port 8081, plus a Prometheus metrics server on port 8082. The REST API includes model inference, streaming inference, model metadata, health probes, and model repository management endpoints. The gRPC surface mirrors this with GRPCInferenceService and ModelRepositoryService. MLServer ships with pluggable runtime backends for multiple ML frameworks including Scikit-Learn, XGBoost, LightGBM, ONNX, MLflow, HuggingFace, CatBoost, Spark MLlib, and Alibi (detect/explain). In RHOAI, MLServer runs as a KServe ServingRuntime container started via `mlserver start $MLSERVER_MODELS_DIR`, with authentication delegated to the platform's kube-rbac-proxy sidecar. The downstream Konflux builds use AIPCC base images (`quay.io/aipcc/base-images/cpu:3.5` for CPU, `quay.io/aipcc/base-images/cuda-12.9-el9.6:3.5` for CUDA). A trusted-runtimes allowlist mechanism restricts which model implementations can be loaded in production mode. [source: mlserver/rest/app.py:60-162, mlserver/grpc/server.py:75-89, mlserver/settings.py:429-451, Dockerfile.konflux:1-66, Dockerfile.konflux.cuda:1-4, mlserver/settings.py:42-74]

## Architectural Analysis

MLServer follows a multi-server architecture where a single process hosts three concurrent servers: a FastAPI/uvicorn REST server (port 8080), a gRPC async server (port 8081), and a Prometheus metrics server (port 8082). An optional Kafka consumer/producer server can also be enabled for asynchronous inference via message queues. All three primary servers share a common `DataPlane` handler layer that routes requests to loaded model instances, providing a unified inference interface regardless of transport protocol. [source: mlserver/rest/app.py:52-56, mlserver/grpc/server.py:22-31, mlserver/kafka/server.py:23-26]

The runtime plugin system is central to MLServer's design. Each ML framework backend (Scikit-Learn, XGBoost, LightGBM, ONNX, MLflow, HuggingFace, CatBoost, Spark MLlib, Alibi-Detect, Alibi-Explain) is a separate Python package that registers a model implementation class. In production mode, a trusted-runtimes allowlist baked into the container image at `/etc/mlserver/trusted-runtimes.json` restricts which implementations can be loaded, enforcing a security boundary against arbitrary code execution via model loading. Import paths are validated against a canonical pattern, and built-in aliases normalize legacy paths. [source: mlserver/settings.py:42-74, mlserver/settings.py:140-167, Dockerfile.konflux:44-61]

Neither the REST nor gRPC server implements application-level TLS or authentication. The gRPC server explicitly uses `add_insecure_port` for binding, and the REST server runs uvicorn without TLS configuration. All authentication and encryption are delegated to the platform: kube-rbac-proxy runs as a sidecar in the KServe pod, performing OpenShift OAuth/ServiceAccount token validation before traffic reaches MLServer. This is a standard pattern for KServe ServingRuntime containers in RHOAI. [source: mlserver/grpc/server.py:88-89, mlserver/rest/server.py:86-100]

Both REST and gRPC servers integrate OpenTelemetry for distributed tracing (with health endpoints excluded from trace collection) and Prometheus for metrics export. The REST server uses `starlette-exporter` middleware while the gRPC server uses `py-grpc-prometheus` interceptors. [source: mlserver/rest/app.py:192-205, mlserver/rest/app.py:225-236, mlserver/grpc/server.py:43-73]

## Data Flows

- **Inference request flow:** Client requests arrive at the KServe pod, where the kube-rbac-proxy sidecar validates OpenShift OAuth/ServiceAccount tokens. Authenticated requests are forwarded to MLServer on either port 8080 (REST) or port 8081 (gRPC). Both transports share a common DataPlane handler layer that routes to the appropriate loaded model runtime for inference execution. [source: mlserver/rest/app.py:52-58, mlserver/grpc/server.py:34-39, mlserver/grpc/server.py:88-89, mlserver/rest/server.py:86-90]
- **Model lifecycle:** Models are loaded via the V2 Model Repository API (REST POST `/v2/repository/models/{model_name}/load` or gRPC `RepositoryModelLoad`). The trusted-runtimes allowlist at `/etc/mlserver/trusted-runtimes.json` gates which model implementation classes can be instantiated. Custom REST handlers can be dynamically added per model. [source: mlserver/rest/app.py:164-181, mlserver/settings.py:140-167, mlserver/rest/server.py:38-47]
- **Observability:** Both REST and gRPC servers emit OpenTelemetry traces (with health endpoints excluded) and Prometheus metrics. The REST server uses starlette-exporter middleware; the gRPC server uses py-grpc-prometheus interceptors. Metrics are exposed on a separate port 8082 at `/metrics`. [source: mlserver/rest/app.py:192-236, mlserver/grpc/server.py:43-73, mlserver/settings.py:445-451]
- **Optional Kafka transport:** MLServer includes an optional Kafka consumer/producer server that consumes inference requests from a configured Kafka topic and publishes results, enabling asynchronous batch inference workflows. [source: mlserver/kafka/server.py:23-35]

## Integration Points

- **gRPC framework:** Python library; purpose: gRPC transport for V2 inference and model repository services. [source: mlserver/grpc/server.py:1, mlserver/grpc/interceptors.py:6]
- **KServe:** MLServer operates as a KServe ServingRuntime container, started via `mlserver start $MLSERVER_MODELS_DIR`. KServe manages the pod lifecycle, Service creation, and sidecar injection. [source: Dockerfile.konflux:66, mlserver/settings.py:14]
