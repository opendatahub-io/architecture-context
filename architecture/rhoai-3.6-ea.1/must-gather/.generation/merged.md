## Purpose

**Short**: RHOAI must-gather is a diagnostic data collection tool that runs as an ephemeral pod via `oc adm must-gather` to collect logs, resource manifests, and configuration from all RHOAI platform components across a cluster. [source: collection-scripts/gather.sh:1-247, Dockerfile.konflux:15]

**Detailed**: must-gather provides comprehensive diagnostic data collection for Red Hat OpenShift AI (RHOAI) installations. When invoked via `oc adm must-gather`, it launches an ephemeral pod that executes modular Bash collection scripts to inspect RHOAI operator namespaces, application namespaces, and component-specific resources. The tool supports both full collection (all RHOAI components in parallel) and targeted collection of individual components such as KServe, Data Science Pipelines, Model Registry, Notebooks, KubeRay, Kueue, TrustyAI, MLFlow, SparkOperator, AIGateway, MCP Lifecycle Operator, OGX, and LLM-d. [source: collection-scripts/gather.sh:127-217]

The tool supports cross-Kubernetes distribution deployment, automatically detecting the cluster type (OpenShift, AKS, EKS, CKS) and adapting its collection strategy accordingly. On OpenShift, it uses `oc adm inspect` for namespace-level collection; on non-OpenShift distributions, it provides a `kubectl`-based equivalent that auto-discovers and collects all namespaced and cluster-scoped resources. It also collects Helm release data, Gateway API resources, Istio resources, and platform-level CRDs including DSCInitialization, DataScienceCluster, and component-specific custom resources. [source: collection-scripts/llm-d/xks_util.sh:138-179, collection-scripts/gather.sh:14-121]

## Architectural Analysis

must-gather follows a modular, script-per-component architecture. The main entrypoint (`gather.sh`) orchestrates collection by first detecting the Kubernetes distribution, then dispatching to component-specific gather scripts either individually (when `COMPONENT` is set) or in parallel (default `all` mode on OpenShift). Each component gather script defines the Kubernetes resource types it needs to collect and uses shared utilities from `common.sh` to enumerate namespaces and run `oc adm inspect` or the equivalent `kubectl_inspect` fallback. [source: collection-scripts/gather.sh:127-217, collection-scripts/common.sh:19-31]

The cross-distribution support layer (`xks_util.sh`) abstracts the difference between OpenShift and vanilla Kubernetes clusters. On non-OpenShift platforms, the tool replaces `oc adm inspect` with `kubectl_inspect`, which auto-discovers all API resources in a namespace and collects pod logs in parallel. This makes the same must-gather image usable across OpenShift, AKS, EKS, and CoreWeave Kubernetes. [source: collection-scripts/llm-d/xks_util.sh:44-106, collection-scripts/llm-d/xks_util.sh:138-179]

The tool carries no persistent state, exposes no network services, and performs no writes to the cluster. All authentication is delegated to the service account provisioned by the `oc adm must-gather` framework, which grants the pod cluster-reader privileges. The collection output is written to a local `/must-gather` directory that the must-gather framework copies back to the user's workstation. [source: collection-scripts/common.sh:6, collection-scripts/gather.sh:219-221]

### FIPS Compliance

must-gather is a shell-based diagnostic tool with no application-level cryptographic operations. It does not perform TLS handshakes, hash computations, or key management directly. All network communication is delegated to `oc`/`kubectl` and `helm` CLI binaries bundled in the container image, which inherit FIPS-mode behavior from the host system's crypto policies. The base image is `ose-must-gather-rhel9` (UBI-based), which provides system-level OpenSSL and FIPS-capable crypto libraries. [source: Dockerfile.konflux:3]

No build-time FIPS flags (GOEXPERIMENT, CGO_ENABLED) are applicable — the component contains no compiled binaries of its own. The `oc` and `kubectl` binaries are copied from the `ose-cli-rhel9` builder image, which is independently validated for FIPS compliance. [source: Dockerfile.konflux:2, Dockerfile.konflux:7]
