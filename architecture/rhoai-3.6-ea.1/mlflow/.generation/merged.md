## Purpose

**Short**: MLflow tracking server for RHOAI, providing experiment tracking, model registry, and artifact serving with Kubernetes-native authentication and workspace isolation. [source: Dockerfile.konflux:80, pyproject.toml:128]

**Detailed**: MLflow is an open-source platform for the complete machine learning lifecycle. In the RHOAI deployment, it runs as a Python tracking server (Flask/Gunicorn) on port 5000, configured with the `kubernetes-auth` authentication plugin from `mlflow-kubernetes-plugins` and workspace isolation via a Kubernetes-backed workspace store (`kubernetes://`). The server exposes experiment tracking, model registry, and artifact serving APIs over HTTP. It ships as three installable Python packages (`mlflow`, `mlflow-skinny`, `mlflow-tracing`) plus the external `mlflow-kubernetes-plugins` for RHOAI-specific Kubernetes integration. The container image disables the AI Gateway and Assistant features (`MLFLOW_ENABLE_AI_GATEWAY=false`, `MLFLOW_ENABLE_ASSISTANT=false`) and telemetry (`MLFLOW_DISABLE_TELEMETRY=true`), focusing the deployment surface on core tracking and registry functionality with artifact serving enabled. ## Architectural Analysis

MLflow's RHOAI deployment follows a plugin-based architecture where Kubernetes-specific behaviors are injected at runtime rather than built into the core. The server entrypoint (`python3.12 -m mlflow server`) loads the `kubernetes-auth` authentication plugin via the `mlflow.app` entry point group, which is resolved by `_find_app()` in `mlflow/server/__init__.py:218`. This plugin is provided by the externally packaged `mlflow-kubernetes-plugins==1.5.0`, not by the MLflow source tree itself. The same plugin package provides the `kubernetes://` workspace store backend, registered through the `mlflow.workspace_provider` entry point group and resolved by `WorkspaceStoreRegistry` in `mlflow/tracking/_workspace/registry.py`. This separation means the authentication and workspace isolation mechanisms are opaque to static analysis of the MLflow codebase—their actual behavior depends on the plugin's implementation.

The Flask application in `mlflow/server/__init__.py` serves as the primary HTTP surface, with route handlers registered from `mlflow.server.handlers` and security middleware initialized conditionally when running as a server process (line 78-82). Gunicorn or Uvicorn acts as the production WSGI/ASGI server in front of Flask. The container image explicitly disables the AI Gateway and Assistant subsystems via environment variables, constraining the deployed API surface to the tracking server, model registry, and artifact serving paths. The gateway-related endpoints (e.g., `/gateway/`, `/v1/chat/completions`) present in the codebase are not active in this deployment configuration.

For Kubernetes integration beyond the plugins, MLflow includes a project execution backend in `mlflow/projects/kubernetes.py` that creates Kubernetes Jobs to run MLflow projects. This uses the `kubernetes` Python client library for direct API interaction including job creation, status polling, and cleanup. The broader dependency set includes pluggable artifact storage backends for S3, GCS, Azure, and SFTP, though the RHOAI deployment activates only the `--serve-artifacts` mode without prescribing a specific remote store.
