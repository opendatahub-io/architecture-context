## Purpose

**Short**: Asynchronous batch inference gateway for LLM workloads, providing an API server for batch job management, a processor for dispatching inference requests to llm-d gateways, and a garbage collector for expired job cleanup. [source: cmd/apiserver/main.go:34, cmd/batch-gc/main.go:48, cmd/batch-processor/main.go:44, internal/apiserver/server/server.go:86-101]

**Detailed**: batch-gateway implements an asynchronous batch inference pipeline for RHOAI. It consists of three independently deployable Go microservices: the **apiserver** accepts client HTTP requests for batch job CRUD operations (create, list, get, delete) with optional TLS and configurable security headers; the **batch-processor** polls for pending batch work and dispatches inference requests to llm-d inference gateways over HTTP; and the **batch-gc** periodically scans for expired batch jobs and files and removes them from the database and object storage. The system uses PostgreSQL for job state persistence, Redis/Valkey for async task queuing via the llm-d-async library, S3-compatible storage for batch input/output files, and exports traces via OTLP/gRPC to an OpenTelemetry Collector. All three binaries are built with `GOEXPERIMENT=strictfipsruntime` and dynamic linking for FIPS compliance. Authentication is not enforced at the application level and is expected to be delegated to the platform (gateway/service mesh). [source: internal/apiserver/server/server.go:86-101, internal/database/postgresql/db_postgresql.go:116, internal/util/redis/redis_client.go:144, internal/files_store/s3/client.go:119, docker/Dockerfile.apiserver.konflux:25]

## Architectural Analysis

batch-gateway implements an asynchronous batch inference pipeline decomposed into three single-responsibility Go binaries that share common internal libraries but are independently containerized and deployed.

**Request lifecycle.** The apiserver exposes a REST API surface for batch job management. The middleware chain applies panic recovery, request-scoped context (request ID, tenant identifier, structured logging, Prometheus metrics, and OpenTelemetry tracing), and security response headers — but no application-level authentication or authorization. When TLS is enabled via `SSLCertFile`/`SSLKeyFile` configuration, the server uses `crypto/tls` with configurable minimum version (TLS 1.2 default), cipher suites drawn exclusively from Go's FIPS-approved set (`tls.CipherSuites()`), and ALPN negotiation for h2 and HTTP/1.1. The observability server (health, readiness, metrics, optional pprof) always runs on a separate port in plain HTTP. [source: internal/apiserver/server/server.go:86-101, internal/apiserver/server/server.go:132-186, internal/tls/tls.go:109-140]

**Async processing.** The batch-processor polls for pending work using Redis/Valkey as a task queue, with the llm-d-async library providing the producer/consumer abstraction. Inference requests are dispatched to llm-d inference gateways over HTTP/HTTPS. Results and input files are stored in S3-compatible object storage. Job state is persisted in PostgreSQL via the pgx driver with connection pooling and OpenTelemetry instrumentation. [source: internal/util/redis/redis_client.go:144, pkg/clients/http/http_client.go:134, internal/database/postgresql/db_postgresql.go:116, internal/files_store/s3/client.go:119]

**Security posture.** Authentication is absent from the application layer; the middleware stack was fully inspected and contains no auth enforcement. This is architecturally intentional — the component expects platform-level authentication via a gateway or service mesh. All three Konflux Dockerfiles build with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` on UBI 9 base images, satisfying FIPS check-payload requirements. The TLS implementation uses only the standard library `crypto/tls` with FIPS-compatible configuration. [source: internal/apiserver/server/server.go:93-97, docker/Dockerfile.apiserver.konflux:25, docker/Dockerfile.processor.konflux:25, docker/Dockerfile.gc.konflux:25, internal/tls/tls.go:28-31]

**Deployment boundary.** This repository contains no Kubernetes Service, Ingress, or production kustomize manifests. The `benchmarks/manifests/` and `examples/deploy-demo/` directories contain demo and benchmarking resources (including a vLLM model server deployment) that are not production deployment artifacts. Service exposure and networking are managed by the deploying operator or platform tooling. [source: benchmarks/manifests/vllm/kustomization.yaml:1, examples/deploy-demo/llmd-sim/modelserver/kustomization.yaml:1]

## Data Flows

- **Batch job submission:** Clients submit batch inference requests to the apiserver REST API. The apiserver validates requests, stores job metadata in PostgreSQL, uploads input files to S3-compatible storage, and publishes async tasks to Redis/Valkey via the llm-d-async producer library. The API server optionally terminates TLS (TLS 1.2+ with FIPS-approved cipher suites) or relies on platform-level transport security. [source: internal/apiserver/server/server.go:86-101, internal/apiserver/server/server.go:169-186, internal/database/postgresql/db_postgresql.go:116, internal/files_store/s3/client.go:119]
- **Inference dispatch:** The batch-processor consumes pending tasks from Redis/Valkey, dispatches inference requests to llm-d inference gateways over HTTP/HTTPS, and writes results back to S3-compatible storage and PostgreSQL. [source: pkg/clients/http/http_client.go:134, internal/util/redis/redis_client.go:144]
- **Garbage collection:** The batch-gc periodically scans PostgreSQL for expired batch jobs and removes associated files from S3-compatible storage and job records from the database. [source: cmd/batch-gc/main.go:48]
- **Observability:** All three binaries export Prometheus metrics via `/metrics` endpoints and traces via OTLP/gRPC to an OpenTelemetry Collector. Health and readiness probes are served on a dedicated plain-HTTP observability port. [source: cmd/batch-gc/main.go:148-149, cmd/batch-processor/main.go:193-207, internal/util/otel/otel.go:124]
- **Security context:** No application-level authentication is enforced; the middleware chain provides request context, panic recovery, and security headers. Authentication is expected to be platform-delegated. [source: internal/apiserver/server/server.go:93-97]
