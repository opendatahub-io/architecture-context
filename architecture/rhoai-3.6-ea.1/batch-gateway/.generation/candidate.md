## Purpose

**Short**: Batch inference gateway for llm-d that accepts asynchronous batch inference requests, manages input/output files, dispatches work to inference backends, and garbage-collects expired jobs. [source: cmd/apiserver/main.go:34, cmd/batch-gc/main.go:48, cmd/batch-processor/main.go:44, charts/batch-gateway/values.yaml:97-207]

**Detailed**: batch-gateway provides an asynchronous batch inference API compatible with the OpenAI Batch API contract. It is deployed as three cooperating Go workloads: an **API server** that exposes REST endpoints for submitting batch jobs and uploading/downloading files, a **processor** that polls for pending batches, fans out inference requests to an llm-d inference gateway, and collects results, and a **garbage collector** that periodically removes expired jobs and their associated files. Persistent state is stored in PostgreSQL, files reside in either a local PVC or S3-compatible object storage, and Redis/Valkey serves as a work-exchange queue between the API server and processor. All three binaries share the same Go module, internal libraries, and a common Kubernetes Secret for credentials. The API server supports optional TLS termination with configurable TLS version, cipher suites, and ALPN, and can be exposed through a Gateway API HTTPRoute attached to an llm-d inference gateway. Authentication is not enforced locally; it is architecturally delegated to the platform gateway or service mesh. Observability is provided via Prometheus metrics, OpenTelemetry tracing (OTLP/gRPC), and structured logging. [source: cmd/apiserver/main.go:34, cmd/batch-gc/main.go:48, cmd/batch-processor/main.go:44, internal/apiserver/server/server.go:86-101, 131-210, charts/batch-gateway/values.yaml:19-27, 97-222]

## Architectural Analysis

batch-gateway follows a three-process split architecture where the API server, processor, and garbage collector are independently scaled Kubernetes workloads sharing a common data plane (PostgreSQL for batch/file metadata, Redis/Valkey for work exchange, and S3 or filesystem for file content). This separation allows the API surface to remain responsive while long-running inference fan-out is handled asynchronously by the processor, and expired-job cleanup runs on its own cadence without impacting either.

The API server uses a dual-mux HTTP design: a business API mux serves batch and file endpoints behind a middleware chain (panic recovery → request context with OTel tracing → security headers), while a separate observability mux serves health, readiness, and metrics endpoints without middleware. TLS is opt-in: when a certificate and key are provided, the API server terminates TLS with configurable minimum version (default TLS 1.2), cipher suites restricted to `tls.CipherSuites()` (IANA-approved, non-insecure), and ALPN negotiation. The observability server always runs as plain HTTP on a separate port. [source: internal/apiserver/server/server.go:86-101, 131-210, internal/tls/tls.go:109-140]

Authentication is not enforced within the batch-gateway process itself. The Helm chart supports an optional Gateway API HTTPRoute that attaches to an `llm-d-inference-gateway`, indicating that authentication and authorization are architecturally delegated to the platform ingress layer. The `Authorization` header is passed through to downstream inference requests, not validated locally. Tenant identity is extracted from the `X-MaaS-Username` request header for scoping batch operations, but this is an application-level tenant marker, not an authentication mechanism. [source: internal/apiserver/server/server.go:86-101, charts/batch-gateway/values.yaml:171-183, 190-201]

All three Konflux Dockerfiles build with `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` on a UBI 9 `go-toolset` builder, producing dynamically linked binaries that use OpenSSL for cryptographic operations in FIPS mode. Runtime images are based on `ubi9/ubi-minimal`, which ships OpenSSL. This configuration satisfies the check-payload FIPS gate for Konflux pipelines. [source: docker/Dockerfile.apiserver.konflux:4,25, docker/Dockerfile.gc.konflux:4,25, docker/Dockerfile.processor.konflux:4,25]

## Data Flows

- **Batch submission flow:** Clients submit batch inference requests and upload input files via the API server's REST endpoints on port 8000. The API server validates the request, persists metadata to PostgreSQL, stores input files to S3 or local filesystem, and enqueues work via Redis/Valkey. The processor polls Redis for pending batches, fans out individual inference requests to the llm-d inference gateway over HTTP/HTTPS, aggregates results, and writes output files back to the file store. [source: cmd/apiserver/main.go:34, cmd/batch-processor/main.go:44, charts/batch-gateway/values.yaml:97-207]
- **Observability flow:** Each workload exposes health, readiness, and Prometheus metrics on a dedicated observability port (default 8081) via plain HTTP. OpenTelemetry traces are exported to a configured OTLP/gRPC collector endpoint. The API server optionally enables pprof profiling endpoints on the observability mux. [source: internal/apiserver/server/server.go:103-119, 135-147, charts/batch-gateway/values.yaml:49-71, 189]
- **Credential distribution:** All three workloads mount a shared Kubernetes Secret (`batch-gateway-secrets`) containing connection URLs for Redis, PostgreSQL, inference API key, and S3 credentials. The secret is mounted read-only at `/etc/.secrets/`. [source: charts/batch-gateway/values.yaml:19-27]
- **Garbage collection flow:** The GC process runs on a configurable schedule, queries PostgreSQL for expired batch jobs and files past their TTL, removes associated file content from the file store, and deletes the metadata records. [source: cmd/batch-gc/main.go:48, charts/batch-gateway/values.yaml:198-205]
