## Purpose

**Short**: Garak red-teaming evaluation adapter that runs AI safety benchmarks as Kubernetes Jobs, integrating with eval-hub and Kubeflow Pipelines for orchestrated LLM security evaluation. [source: pyproject.toml:3-4, src/llama_stack_provider_trustyai_garak/evalhub/__init__.py:7-14]

**Detailed**: llama-stack-provider-trustyai-garak is a Python package that provides a FrameworkAdapter implementation integrating the Garak red-teaming framework with the eval-hub evaluation platform. It runs as a Kubernetes Job with two operational modes: simple mode (Garak executes within the same pod) and KFP mode (Garak runs in a separate Kubeflow Pipelines pod). The adapter reads evaluation configurations, resolves model API keys from environment variables or mounted Kubernetes Secrets, executes Garak probes against target LLM endpoints, and uploads results to S3-compatible storage. It does not expose HTTP endpoints or Kubernetes Services; instead, it authenticates outbound to KFP and S3 APIs using ServiceAccount tokens and AWS credentials respectively. ## Architectural Analysis

llama-stack-provider-trustyai-garak is a batch-oriented adapter that bridges the Garak AI safety red-teaming framework with eval-hub's evaluation orchestration platform. The component is deployed as a Kubernetes Job rather than a long-running service, and it exposes no HTTP endpoints or Kubernetes Services (confirmed by `io.openshift.expose-services=""` in `Dockerfile.konflux:25`).

The adapter operates in two modes. In simple mode, the Garak evaluation runs in the same pod as the adapter. In KFP mode, the adapter submits Garak evaluations as Kubeflow Pipelines runs, with two authentication models for KFP access: a legacy direct ServiceAccount token model (reading from `/var/run/secrets/kubernetes.io/serviceaccount/token`) and a newer sidecar proxy model (evalhub >= 0.4.4) where `AutomountServiceAccountToken=false` and a sidecar injects credentials on outbound requests. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:745-779]

Model API keys are resolved through a multi-layer cascade: role-specific environment variables, KFP-mounted secrets at `/mnt/model-auth/`, eval-hub model secrets at `/var/run/secrets/model/`, generic `API_KEY` fallback, and finally a `"DUMMY"` sentinel for unauthenticated local endpoints. S3 credentials are resolved from Data Connection environment variables (`AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`) or read from a Kubernetes Secret via the in-cluster K8s API. [source: src/llama_stack_provider_trustyai_garak/core/pipeline_steps.py:124-168, src/llama_stack_provider_trustyai_garak/evalhub/s3_utils.py:12-43, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:870-899]

The `cryptography` and `pyjwt` dependencies are present as transitive requirements. No explicit FIPS configuration is applied at the application level; cryptographic behavior is inherited from the container base image's OpenSSL installation. The uvicorn dependency is transitive (from garak or eval-hub-sdk) and does not indicate this component runs an ASGI server.

## Data Flows

- **Evaluation execution:** The adapter receives an eval-hub evaluation configuration, resolves the target model API key through a multi-layer credential cascade (environment variables, KFP-mounted secrets, eval-hub secrets), and executes Garak red-teaming probes against the target LLM endpoint. In KFP mode, the adapter submits the evaluation as a Kubeflow Pipelines run and polls for completion. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1198-1212, src/llama_stack_provider_trustyai_garak/core/pipeline_steps.py:124-168]
- **Results storage:** Evaluation results and sanitized configurations (API keys redacted) are uploaded to S3-compatible object storage using boto3, with credentials sourced from Data Connection environment variables or Kubernetes Secrets read via the in-cluster K8s API. [source: src/llama_stack_provider_trustyai_garak/evalhub/s3_utils.py:12-43, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:870-899]
- **Outbound authentication:** The adapter authenticates to external services using four credential mechanisms: Kubernetes ServiceAccount tokens for KFP API access (direct or sidecar-injected), AWS credentials for S3 operations, KFP_AUTH_TOKEN with Bearer auth for K8s API calls, and per-model API keys for LLM endpoint calls. The component exposes no inbound endpoints and has no inbound authentication requirements.
