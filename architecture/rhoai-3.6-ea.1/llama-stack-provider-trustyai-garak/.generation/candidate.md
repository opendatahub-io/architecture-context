## Purpose

**Short**: Garak red-teaming evaluation adapter that runs as a Kubernetes Job, integrating the Garak security scanning framework with the eval-hub evaluation platform. Supports simple (in-pod) and KFP (Kubeflow Pipeline) execution modes for AI model safety assessments. [source: pyproject.toml:2-4, src/llama_stack_provider_trustyai_garak/evalhub/__init__.py:7-13]

**Detailed**: llama-stack-provider-trustyai-garak is a batch-oriented adapter that bridges NVIDIA's Garak red-teaming framework with the eval-hub evaluation platform. It implements the eval-hub `FrameworkAdapter` interface and runs as a Kubernetes Job rather than a persistent HTTP service. The adapter supports two execution modes: **simple mode**, where Garak runs as a subprocess inside the same Job pod, and **KFP mode**, where scan execution is delegated to a Kubeflow Pipeline with S3 (via OpenShift AI Data Connection secrets) for artifact transfer between pods. The KFP pipeline includes six steps: validation, taxonomy resolution, SDG prompt generation, prompt preparation, Garak scan execution, and KFP output writing. Results are parsed from Garak's JSONL reports, persisted to OCI registries, and reported back to eval-hub via sidecar callbacks. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1-18, src/llama_stack_provider_trustyai_garak/evalhub/kfp_pipeline.py:1-25]

## Architectural Analysis

llama-stack-provider-trustyai-garak follows a batch-job architecture rather than the persistent-service pattern typical of most RHOAI components. The adapter implements the eval-hub `FrameworkAdapter` interface, receiving job specifications via a mounted ConfigMap (`/etc/eval-job/spec.json`) and reporting results back through sidecar callbacks. This design means the component does not expose HTTP endpoints, Kubernetes Services, or ingress resources; it is a consumer of platform APIs rather than a provider. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:13-17, src/llama_stack_provider_trustyai_garak/evalhub/__init__.py:7-13]

The dual execution-mode architecture (simple vs. KFP) introduces a significant split in the credential and integration surface. In simple mode, the adapter only needs outbound access to the target model endpoint and S3 storage. In KFP mode, it additionally requires a Kubeflow Pipelines client connection (authenticated via `KFP_AUTH_TOKEN`) and Kubernetes API access to read Data Connection secrets for S3 credentials. The KFP pipeline injects S3 credentials into pipeline pods via `kubernetes.use_secret_as_env`, while the eval-hub Job pod receives them via `envFrom`. [source: src/llama_stack_provider_trustyai_garak/evalhub/kfp_pipeline.py:7-11, 48-54, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:879-899]

Authentication to target model endpoints uses a cascading key resolution strategy: the adapter checks model-specific environment variables, mounted secret files, eval-hub secret storage, and falls back to generic `API_KEY` or `OPENAICOMPATIBLE_API_KEY` environment variables. API keys are redacted before persisting configurations to S3 to prevent credential leakage in artifact storage. The `pyjwt` and `cryptography` dependencies are transitive (from eval-hub-sdk and other dependencies) rather than directly consumed by this adapter's authentication logic. [source: src/llama_stack_provider_trustyai_garak/core/pipeline_steps.py:155-169, src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:1198-1204]

## Data Flows

- **Job execution flow:** The adapter receives a job specification via a mounted ConfigMap, resolves scan configuration and credentials, executes Garak either in-pod (simple mode) or via a Kubeflow Pipeline (KFP mode), parses JSONL scan results, persists artifacts to an OCI registry, and reports outcomes via eval-hub sidecar callbacks. [source: src/llama_stack_provider_trustyai_garak/evalhub/garak_adapter.py:12-17]
- **S3 artifact transfer:** In KFP mode, the adapter uses S3-compatible storage (via Data Connection secrets) as an intermediary for transferring scan configurations, SDG prompts, and Garak results between the adapter Job and KFP pipeline pods. Credentials are injected via `kubernetes.use_secret_as_env` in pipeline pods and `envFrom` in the Job pod. [source: src/llama_stack_provider_trustyai_garak/evalhub/kfp_pipeline.py:7-11, 48-54, src/llama_stack_provider_trustyai_garak/evalhub/s3_utils.py:30]
- **Outbound authentication:** The adapter authenticates to external services using environment-variable or file-mounted API keys for model endpoints, `KFP_AUTH_TOKEN` bearer tokens for the Kubernetes API (when not using in-cluster config), and AWS credentials for S3 access. Credentials are resolved through a cascading lookup chain and redacted before S3 persistence.
