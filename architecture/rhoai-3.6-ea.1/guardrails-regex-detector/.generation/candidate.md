## Purpose

**Short**: Rust-based regex detection microservice for the TrustyAI Guardrails framework that scans text content for PII patterns (email, SSN, credit card) and custom user-defined regular expressions. [source: src/main.rs:32-33, src/detectors.rs:38-72, Cargo.toml:2]

**Detailed**: guardrails-regex-detector is a lightweight, stateless Rust HTTP service that provides regex-based content detection as part of the RHOAI Guardrails system. It exposes a single POST endpoint (`/api/v1/text/contents`) that accepts text content and a set of regex patterns, then returns detection results with position, type, and score metadata. The service includes built-in detectors for common PII types—email addresses, Social Security numbers, and credit cards—and supports arbitrary user-supplied regex patterns. Built on the Axum web framework with Tokio async runtime, it listens on a configurable HTTP port (default 8080) with no application-level authentication or TLS; network-level isolation is expected from the platform. The container image is built from a Debian-based Rust builder stage and deployed on UBI 9 minimal. [source: src/main.rs:14-46, src/detectors.rs:96-137, Dockerfile:38-45, Cargo.toml:1-15]

## Architectural Analysis

guardrails-regex-detector follows a minimal microservice pattern: a single Rust binary serving one functional endpoint with no external dependencies, no persistent state, and no outbound connections. The Axum router registers only two routes—a health check and the detection endpoint—with a TraceLayer for request/response logging. The detection handler (`handle_text_contents`) dispatches to either built-in PII detectors or user-supplied regex patterns, returning results synchronously. This design makes the service horizontally scalable and side-effect-free, suitable for deployment as a sidecar or standalone pod behind a guardrails orchestrator. [source: src/main.rs:31-38, src/detectors.rs:96-137]

The service has no application-level security controls: no authentication middleware, no TLS termination, and no authorization logic. The Axum router directly accepts requests on plain HTTP. Security is entirely delegated to the platform layer (service mesh, NetworkPolicy, or similar). This is architecturally appropriate for an internal detection microservice that processes text payloads without accessing secrets or cluster resources, but operators should ensure network-level isolation is in place. [source: src/main.rs:31-45]

The container build uses a multi-stage Dockerfile with a Debian-based Rust 1.84.0 builder and a UBI 9 minimal release image. The `compat-openssl11` package is installed in the release image for glibc compatibility with the Debian-compiled binary, but the application itself does not perform any cryptographic operations or TLS termination. No Konflux Dockerfile is present on this branch. [source: Dockerfile:6, 38-45, rust-toolchain.toml:2]
