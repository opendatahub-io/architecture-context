## Purpose

**Short**: guardrails-regex-detector is a lightweight Rust HTTP microservice that scans text content for PII patterns (email addresses, social security numbers, credit card numbers) and custom regex matches, serving as a detection backend in the RHOAI guardrails pipeline. **Detailed**: guardrails-regex-detector is a single-purpose Rust microservice built on the Axum web framework that provides regex-based text content detection. It exposes a POST endpoint at `/api/v1/text/contents` that accepts JSON payloads containing text content and regex parameters, returning detection results with position, type, and score metadata. The service includes built-in detectors for common PII patterns—email addresses, social security numbers, and credit card numbers—and supports arbitrary custom regex patterns supplied at request time. [source: src/detectors.rs:96-137, src/detectors.rs:38-72]

The component is a stateless, self-contained service with no external dependencies or integration points at the application layer. It runs as a single Tokio async runtime serving both the detection API and a health check endpoint on a configurable HTTP port (default 8080, overridable via `HTTP_PORT` environment variable). The service is deployed as a container built from a UBI9-minimal base image and operates without TLS or authentication at the application layer, delegating those concerns to the platform infrastructure. It is synced from the upstream TrustyAI explainability project via auto-merge. [source: src/main.rs:14-46, Dockerfile:38-45]

## Architectural Analysis

guardrails-regex-detector follows a minimal microservice pattern: a single async Rust binary serving two HTTP routes on one port. The architecture is intentionally simple—text content arrives via POST, gets matched against built-in and custom regex patterns in-memory, and detection results are returned synchronously. There are no background workers, no persistent state, and no outbound network calls. [source: src/main.rs:31-45, src/detectors.rs:96-137]

The service exposes no authentication or authorization mechanisms at the application layer. The Axum router includes only a tracing middleware layer via `tower-http`; no header passthrough or filtering middleware is present in the router chain. Security enforcement is fully delegated to the deployment platform—typically a service mesh sidecar or API gateway in the RHOAI guardrails pipeline. [source: src/main.rs:31-38]

The built-in detector pattern uses a function registry (`HashMap`) mapping string keys ("email", "ssn", "credit-card") to detector functions, allowing straightforward extension of detection capabilities. Custom regex patterns bypass this registry and are compiled and matched directly. All detection is CPU-bound and stateless, making the service horizontally scalable without coordination. [source: src/detectors.rs:106-134]

From a build perspective, the Rust binary is compiled in a multi-stage Dockerfile using `rust:1.84.0`, with separate stages for tests, linting, and formatting checks. The release image is based on UBI9-minimal with `compat-openssl11` installed for system library compatibility, though the application itself performs no cryptographic operations. [source: Dockerfile:6-45]
