## Purpose

**Short**: rhoai-mcp is a Model Context Protocol (MCP) server that enables AI agents to interact with Red Hat OpenShift AI environments, providing tool-based access to workbenches, model serving, pipelines, training, and data connections via Kubernetes API operations. [source: pyproject.toml:4, src/rhoai_mcp/server.py:248-250, deploy/kustomize/base/clusterrole.yaml:1]

**Detailed**: rhoai-mcp implements the Model Context Protocol (MCP) to bridge AI agents with Red Hat OpenShift AI platform capabilities. It deploys as a single Python-based Kubernetes workload exposing an MCP server over configurable transports (stdio, SSE, or streamable HTTP on port 8000). The server uses a pluggy-based plugin architecture to register domain-specific tools, resources, and prompts that interact with RHOAI components including Kubeflow Notebooks, KServe model serving, Kubeflow Training jobs, Data Science Pipelines, and Model Registry. When OIDC authentication is enabled, an ASGI middleware validates Bearer JWT or OCP OAuth tokens and enforces per-user RBAC-based tool filtering via Kubernetes SubjectAccessReview. The server operates with a dedicated ClusterRole granting broad read and lifecycle access across RHOAI-managed CRDs and core Kubernetes resources. [source: pyproject.toml:4, 27-33, src/rhoai_mcp/server.py:227-274, 276-368, src/rhoai_mcp/config.py:22-28, 234-256, deploy/kustomize/base/clusterrole.yaml:1, deploy/kustomize/base/deployment.yaml:1-77]

## Architectural Analysis

rhoai-mcp follows a plugin-based architecture where domain capabilities are registered dynamically through the pluggy framework. The `RHOAIServer` class orchestrates server lifecycle: it eagerly connects a Kubernetes client at startup, loads core and external plugins via entrypoints, and registers their tools, resources, and prompts with the FastMCP runtime. Transport mode is configurable via the `RHOAI_MCP_TRANSPORT` environment variable or CLI argument, supporting stdio for local development and SSE or streamable-http for networked deployment behind Kubernetes Services. [source: src/rhoai_mcp/server.py:227-274, src/rhoai_mcp/config.py:22-28, deploy/kustomize/base/deployment.yaml:33-34]

The authentication design implements a dual-mode strategy. When OIDC is disabled (the default), the server operates with its service account identity and no per-request authentication on MCP endpoints. When OIDC is enabled, a pure ASGI middleware intercepts all HTTP requests except `/health` and the OAuth metadata endpoint, validates Bearer tokens via either JWKS-based JWT verification or Kubernetes TokenReview API, and sets a per-request `UserContext`. This context drives two isolation mechanisms: the Kubernetes client switches to user impersonation for all API calls, and a tool-level RBAC filter patches the MCP protocol handlers to enforce SubjectAccessReview-based tool access control per authenticated user. [source: src/rhoai_mcp/auth/middleware.py:25-93, src/rhoai_mcp/auth/oidc.py:36-62, src/rhoai_mcp/auth/token_review.py:20-58, src/rhoai_mcp/server.py:53-62, 276-368, 370-407]

The server holds a broad ClusterRole spanning core Kubernetes resources (namespaces, pods, secrets, persistent volumes) and RHOAI-specific CRDs (notebooks, inferenceservices, servingruntimes, trainjobs, datasciencepipelinesapplications). This reflects its role as an agent-facing control plane proxy that mediates access to the full RHOAI stack. The security posture relies on Kubernetes RBAC for authorization depth, with the optional OIDC layer providing user identity propagation at the MCP transport boundary. The container runs as non-root (UID 1000) with a read-only root filesystem, dropped capabilities, and seccomp RuntimeDefault profile. [source: deploy/kustomize/base/clusterrole.yaml:1, deploy/kustomize/base/deployment.yaml:19-54]

## Data Flows

- **Client entry:** AI agent clients connect to the rhoai-mcp server on port 8000/TCP via the configured MCP transport (SSE or streamable-http). When OIDC is enabled, the `OIDCAuthMiddleware` validates the Bearer token (JWT via JWKS or opaque token via Kubernetes TokenReview) before passing the request to the MCP handler. The `/health` endpoint is excluded from authentication and serves Kubernetes liveness and readiness probes. [source: deploy/kustomize/base/deployment.yaml:29-70, src/rhoai_mcp/auth/middleware.py:50-93, src/rhoai_mcp/server.py:331]
- **Tool dispatch:** MCP tool calls are routed through the plugin manager to domain-specific plugin handlers. When OIDC is enabled, the `ListToolsRequest` and `CallToolRequest` handlers are wrapped with RBAC filtering that performs SubjectAccessReview checks against the authenticated user's identity, restricting tool visibility and execution per user. [source: src/rhoai_mcp/server.py:259-261, 370-407]
- **Downstream interactions:** Plugin handlers interact with the Kubernetes API server via the Python kubernetes client library, using either the service account credential or user impersonation depending on OIDC mode. Named downstream systems accessed through CRD operations include Kubeflow Notebooks, KServe InferenceService, Kubeflow Training Operator, and Data Science Pipelines. Model Registry is accessed via HTTP at a configurable URL (default: `http://model-registry.odh-model-registries.svc:8080`). [source: src/rhoai_mcp/server.py:40-64, src/rhoai_mcp/config.py:183-212, deploy/kustomize/base/clusterrole.yaml:1]
