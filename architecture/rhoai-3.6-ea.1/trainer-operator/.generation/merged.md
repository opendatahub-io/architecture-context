## Purpose

**Short**: Kubernetes operator that manages the Kubeflow Trainer v2 lifecycle on RHOAI, reconciling a cluster-scoped Trainer CR to deploy training runtimes, JobSet-based training jobs, and associated monitoring resources. [source: cmd/main.go:68, api/v1alpha1/trainer_types.go:48, internal/controller/trainer_controller.go:179-211]

**Detailed**: trainer-operator is a controller-runtime-based Kubernetes operator that provides distributed model training capabilities in Red Hat OpenShift AI. It watches a singleton cluster-scoped `Trainer` custom resource (`components.platform.opendatahub.io/v1alpha1`, required name `default-trainer`) and reconciles the full Kubeflow Trainer v2 stack into a target application namespace. The reconciliation pipeline checks prerequisites (JobSetOperator availability on OpenShift, JobSet CRD on vanilla Kubernetes), ensures the target namespace, renders manifests from embedded templates (`/opt/manifests-template`, `/opt/runtimes-template`, `/opt/imagestreams-template`), deploys them via a declarative deploy action, monitors deployment health, and garbage-collects stale resources from previous versions. [source: cmd/main.go:68-196, internal/controller/trainer_controller.go:179-268, api/v1alpha1/trainer_types.go:30-60]

The operator integrates with the ODH platform utilities framework for reconciler construction, deployment actions, garbage collection, and platform detection (OpenShift vs. vanilla Kubernetes). It uses label-selector-scoped informer caches to limit memory consumption to trainer-managed resources only, and disables the Namespace cache to avoid cluster-wide informer overhead from namespace lookups. [source: cmd/main.go:82-130, internal/controller/trainer_controller.go:179-211]

## Architectural Analysis

trainer-operator follows the ODH platform reconciler pattern: a single controller watches a cluster-scoped component CR and drives a declarative reconciliation pipeline consisting of ordered action functions. The reconciler is built using `odh-platform-utilities/framework`, which provides the `ReconcilerFor` builder, deployment apply/GC actions, and deployment-health monitoring. This framework-driven approach means the operator itself contains minimal reconciliation boilerplate; the core domain logic is in the action chain: dependency checking, namespace provisioning, manifest rendering, deploy, health monitoring, and garbage collection. [source: internal/controller/trainer_controller.go:179-211, go.mod:9-10]

The operator's dependency management is platform-aware. On OpenShift clusters, it requires the JobSetOperator (operator.openshift.io) to be installed, CR-present, and healthy before proceeding with reconciliation. On vanilla Kubernetes, it only checks for the JobSet CRD. This conditional flow is implemented via `cluster.DetectClusterType` from odh-platform-utilities and a series of prerequisite checks that set degraded conditions with descriptive reasons when dependencies are not met. The operator dynamically watches the JobSetOperator resource (gated by CRD existence), allowing it to re-reconcile when the dependency status changes. [source: internal/controller/trainer_controller.go:184-187, 230-268]

The Trainer CRD embeds `common.Status` and `common.ComponentReleaseStatus` from odh-platform-utilities, implementing the `PlatformObject` interface. This enables the platform operator (odh-operator/rhods-operator) to manage the component lifecycle uniformly alongside other RHOAI components. The Trainer spec supports feature gates and per-controller resource overrides, providing operational tuning without manifest changes. [source: api/v1alpha1/trainer_types.go:20-95]

The informer cache is hardened against memory-exhaustion attacks: label selectors restrict cached Deployments, Services, ConfigMaps, and ValidatingWebhookConfigurations to trainer-managed resources only, and Namespace lookups bypass the cache entirely via `DisableFor`. The `StripUnusedFields` transform further reduces per-object memory. [source: cmd/main.go:98-130]

Metrics are served over plaintext HTTP on port 8080 with `SecureServing` explicitly disabled. No TLS or authentication protects the metrics endpoint; access control is expected to be enforced at the network layer or by the platform's metrics collection infrastructure. [source: cmd/main.go:93-96]
