## Purpose

**Short**: Kubernetes operator that manages Apache Spark workloads on OpenShift, providing CRD-based lifecycle management for SparkApplication, ScheduledSparkApplication, and SparkConnect resources with admission webhook validation and pod mutation. [source: cmd/operator/main.go:44, internal/controller/sparkapplication/controller.go:284, internal/controller/sparkconnect/reconciler.go:111]

**Detailed**: The spark-operator provides a Kubernetes-native interface for submitting, scheduling, and managing Apache Spark applications on Red Hat OpenShift AI. It consists of three principal runtime components: a controller deployment that reconciles SparkApplication, ScheduledSparkApplication, and SparkConnect custom resources; a webhook deployment that validates and mutates Spark workload submissions and injects Spark-specific pod configuration; and a spark-operator-module that integrates with the ODH platform through the `common.PlatformObject` interface from odh-platform-utilities, enabling the ODH Operator to manage the Spark operator's lifecycle via a cluster-scoped SparkOperator CR. The operator manages the full Spark workload lifecycle including driver and executor pod creation, service exposure, ingress management, PodDisruptionBudget creation, and monitoring configuration via ConfigMap-based Prometheus settings. TLS configuration for webhook endpoints is dynamically derived from the OpenShift APIServer TLS profile when available, with a hardened TLS 1.2 minimum fallback on non-OpenShift clusters. [source: cmd/operator/controller/start.go:352, cmd/operator/webhook/start.go:403, spark-operator-module/pkg/apis/v1alpha1/types.go:7, internal/controller/sparkapplication/controller.go:284]

## Architectural Analysis

The spark-operator follows a three-workload architecture: a controller deployment, a webhook deployment, and a module-level operator that bridges the component into the RHOAI platform. The controller and webhook run as separate Kubernetes Deployments under distinct service accounts (`spark-operator-controller` and `spark-operator-webhook`), each with scoped RBAC ClusterRoles that follow the principle of least privilege—notably, the webhook's secret access is restricted by `resourceNames` to `spark-operator-webhook-certs` only. [source: config/rbac/role.yaml:2, config/webhook/role.yaml:1, config/webhook/clusterrole.yaml:1]

The spark-operator-module acts as a meta-operator: it reconciles the cluster-scoped `SparkOperator` CR (from `components.platform.opendatahub.io/v1alpha1`) and manages the lifecycle of the controller and webhook Deployments, their RBAC resources, CRDs, NetworkPolicies, and cert-manager Certificates. The module implements the `common.PlatformObject` interface from odh-platform-utilities, which provides the ODH Operator a uniform status and condition interface across all managed components. [source: spark-operator-module/pkg/apis/v1alpha1/types.go:7-18, spark-operator-module/pkg/sparkoperatormodule/setup.go:22-32]

Webhook TLS is handled through two mechanisms: the webhook deployment self-manages certificate generation via `pkg/certificate/certificate.go` (creating and rotating a self-signed CA and server certificate stored in a named Secret), while the spark-operator-module provisions cert-manager Certificate and Issuer resources for production deployments. The webhook reads the OpenShift `APIServer` resource (`config.openshift.io/v1`) to align its TLS minimum version and cipher suites with the cluster-wide TLS profile, falling back to TLS 1.2 minimum when the profile is unavailable. [source: cmd/operator/webhook/start.go:399-418, pkg/certificate/certificate.go:94-113, pkg/tls/tls.go:26-51]

All seven admission webhooks (four mutating, three validating) use `failurePolicy: Fail`, meaning that webhook unavailability blocks Spark workload creation and updates. This is a deliberate safety choice that prioritizes correctness over availability—preventing unvalidated SparkApplications from running—but creates a hard dependency on webhook health for the Spark workload submission path. [source: config/webhook/mutatingwebhookconfiguration.yaml:7, config/webhook/validatingwebhookconfiguration.yaml:8]

## Data Flows

- **Spark workload submission:** Users create SparkApplication or ScheduledSparkApplication CRs, which are intercepted by the mutating and validating admission webhooks served on port 443 via `spark-operator-webhook-svc`. The webhooks validate resource specifications (including quota checks against ResourceQuota objects) and inject default values before the CR is persisted. The controller then reconciles the CR by creating driver Pods, executor Pods, Services, Ingress resources, and PodDisruptionBudgets. [source: config/webhook/service.yaml:3, internal/webhook/sparkapplication_validator.go:37, internal/controller/sparkapplication/controller.go:284]
- **SparkConnect flow:** The SparkConnect controller reconciles SparkConnect CRs by managing ConfigMaps and Services for persistent Spark sessions, providing a long-lived connection endpoint for interactive workloads. [source: internal/controller/sparkconnect/reconciler.go:111-198]
- **Platform lifecycle management:** The ODH Operator creates a SparkOperator CR, which the spark-operator-module reconciles by deploying the controller and webhook Deployments, their RBAC resources, CRDs, NetworkPolicies, cert-manager Certificates, and PodMonitors. Status flows back through the `common.PlatformObject` interface to the ODH Operator. [source: spark-operator-module/pkg/apis/v1alpha1/types.go:7-18, spark-operator-module/pkg/sparkoperatormodule/setup.go:22-32]
- **TLS configuration flow:** The webhook deployment reads the OpenShift APIServer TLS profile (`config.openshift.io/v1/APIServer` named `cluster`) at startup to configure TLS minimum version and cipher suites, aligning with the cluster-wide security policy. On non-OpenShift clusters, the operator falls back to TLS 1.2 minimum. [source: cmd/operator/webhook/start.go:399-418, pkg/tls/tls.go:26-51]
