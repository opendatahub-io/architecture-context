## Purpose

**Short**: GitOps configuration repository providing Helm charts and Kustomize manifests for deploying RHOAI/ODH platform dependencies and component configurations on OpenShift and non-OpenShift Kubernetes clusters. [source: charts/rhai-on-openshift-chart/Chart.yaml:3, charts/rhai-on-xks-chart/Chart.yaml:3]

**Detailed**: odh-gitops is the platform-level deployment orchestration repository for Red Hat OpenShift AI (RHOAI) and Open Data Hub (ODH). It ships two primary Helm charts: `rhai-on-openshift-chart` for OpenShift deployments using OLM-based operator subscriptions, and `rhai-on-xks-chart` for non-OpenShift Kubernetes distributions (AWS EKS, Azure AKS, CoreWeave) using direct Helm dependency installation. The OpenShift chart manages DataScienceCluster (DSC) and DSCInitialization (DSCI) custom resource configurations for platform components including KServe, AI Gateway, Kueue, Model Registry, Ray, Trainer, TrustyAI, Workbenches, Dashboard, and MLflow. A parallel Kustomize tree provides OLM Subscription manifests for nine dependency operators and post-install configuration CRs for operators such as Kueue, JobSet, LeaderWorkerSet, and RHCL/Kuadrant. [source: charts/rhai-on-openshift-chart/values.yaml:1-120, kustomization.yaml:1-7, dependencies/operators/kustomization.yaml:1-19]

## Architectural Analysis

odh-gitops follows a dual-delivery architecture: a Helm chart path for declarative platform installation and a Kustomize path for operator subscription management. The two paths are complementary — the Kustomize tree (`dependencies/` and `configurations/`) manages OLM Subscription lifecycle for dependency operators on OpenShift, while the Helm charts (`charts/rhai-on-openshift-chart/` and `charts/rhai-on-xks-chart/`) template the higher-level DataScienceCluster and DSCInitialization CRs that configure RHOAI component behavior.

The OpenShift chart uses a profile-based design (`default` vs `rhaii`) to control component `managementState` values, with explicit overrides available per component. Each component declares its own dependency toggles (e.g., KServe requires cert-manager and RHCL; Kueue requires cert-manager and its own operator), which the chart resolves into the appropriate operator subscriptions or Helm sub-chart installations depending on the `install-with-helm-dependencies` tag. The XKS chart targets non-OLM environments by bundling dependency operators as Helm sub-charts (cert-manager, gateway-api, lws-operator, rhcl-operator, sail-operator) and deploying the RHAI operator directly with container image references and resource specifications. Cloud-specific configurations for Azure, CoreWeave, and AWS are supported through dedicated value sections.

Gateway API is central to the ingress architecture: both KServe inference and Models-as-a-Service (MaaS) provision separate GatewayClass and Gateway resources using the `openshift.io/gateway-controller/v1` controller. TLS bootstrap for Authorino-based authentication is configured via the `security.opendatahub.io/authorino-tls-bootstrap` annotation on Gateway resources. The RHCL operator (Kuadrant) provides API policy management through a Kuadrant CR deployed in `kuadrant-system`.

This repository does not contain runtime code or compiled binaries — it is a pure configuration repository. All runtime behavior is delegated to the operators and controllers it deploys and configures. ## Data Flows

odh-gitops is a configuration repository and does not process runtime data flows. It produces Kubernetes manifests that are applied to clusters, establishing the deployment topology for RHOAI platform components. The deployment flow proceeds as: Helm chart values → templated Kubernetes resources (Subscriptions, DSC, DSCI, Gateways, Kuadrant CR) → applied to target cluster via Helm install or ArgoCD. The Kustomize path follows: base resources → component overlays → applied via `kubectl apply -k`. Both paths result in OLM-managed operators and platform CRs being created on the target cluster.
