## Purpose

**Short**: Eval-hub is an evaluation orchestration service for RHOAI that manages evaluation jobs, collections, and providers through a REST API, coordinating with Kubernetes batch Jobs, MLflow tracking, S3-compatible storage, and OpenTelemetry for observability. [source: internal/eval_hub/server/server.go:444, internal/eval_hub/mlflow/mlflow.go:24, cmd/eval_runtime_init/main.go:114, internal/otel/otel_sdk.go:174]

**Detailed**: Eval-hub provides a centralized evaluation orchestration service for Red Hat OpenShift AI. The primary server (`eval_hub`) exposes a REST API on port 8080 with endpoints for managing evaluation jobs, collections, and providers, protected by conditional identity header enforcement (X-User/X-Tenant) when enabled by configuration. A dedicated Prometheus metrics server runs on port 8081 in cluster mode. The service coordinates evaluation workloads by creating Kubernetes batch Jobs, ConfigMaps, and Secrets via client-go, and manages HardwareProfile custom resources for hardware-aware scheduling. It integrates with MLflow for experiment tracking via a TLS-configured HTTP client, S3-compatible storage for test data via AWS SDK, and exports traces/metrics to an OpenTelemetry Collector over OTLP/gRPC. The `eval_runtime_sidecar` acts as a proxy for evaluation runtime containers, `eval_runtime_init` handles S3 test-data downloads as an init container, and `evalhub_mcp` provides a Model Context Protocol (MCP) server interface. All Go binaries are built with `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` for FIPS compliance on UBI9. [source: Dockerfile.konflux:27-52, internal/eval_hub/server/server.go:444, internal/eval_hub/config/prometheus.go:4, internal/eval_hub/runtimes/k8s/k8s_helper.go:112-232]

## Architectural Analysis

Eval-hub follows a multi-process architecture where the main API server orchestrates evaluation workloads through Kubernetes batch primitives. The `setupRoutes` function at `server.go:444` registers route groups for evaluation jobs, collections, providers, health, and documentation, all behind a conditional identity enforcement middleware that checks `X-User` and `X-Tenant` headers when the `RequiresIdentityHeaders()` configuration flag is set—bypassed entirely in local/development mode (`server.go:430-441`). This configuration-gated authentication model means that identity enforcement depends on the deployment configuration rather than being structurally guaranteed, which is a meaningful security consideration for platform operators.

The Kubernetes interaction layer in `KubernetesHelper` (`k8s_helper.go`) provides CRUD operations across ConfigMaps, Secrets, Jobs, and HardwareProfile custom resources (`infrastructure.opendatahub.io/v1`). Evaluation workloads are dispatched as Kubernetes batch Jobs, with ConfigMaps carrying evaluation configurations and Secrets holding credentials. The HardwareProfile CRD integration enables hardware-aware scheduling of evaluation workloads.

The service maintains optional integrations with MLflow for experiment tracking (`mlflow.go:43-92`), constructing an HTTP client with TLS 1.2-1.3 enforcement and optional custom CA certificate loading. The MLflow client is nil-safe—when no tracking URI is configured, the server starts without MLflow integration. Storage uses pluggable SQL backends (SQLite for local development, PostgreSQL for production), with the database schema managed through the `internal/eval_hub/storage/sql` package.

No Kubernetes Service or ingress manifests exist in this repository; service exposure is platform-delegated, consistent with the `io.openshift.expose-services=""` label in the Dockerfile. The metrics server runs on a separate port (default 8081) in cluster mode, while in local mode `/metrics` is also served on the main API port for development convenience (`server.go:470-477`).

## Data Flows

- **API request flow:** Clients reach the eval-hub REST API on port 8080. Routes for evaluation jobs, collections, and providers pass through the conditional identity gate (`server.go:430-441`), which enforces X-User and X-Tenant headers when configuration enables it. Health, docs, and OpenAPI endpoints bypass this gate. In cluster mode, Prometheus metrics are served on a dedicated metrics server at port 8081; in local mode, `/metrics` is additionally registered on the main API port. [source: internal/eval_hub/server/server.go:444-488, internal/eval_hub/server/metrics_server.go:23-42, internal/eval_hub/config/prometheus.go:4]
- **Evaluation job orchestration:** When an evaluation is submitted, the server creates Kubernetes batch Jobs via `KubernetesHelper.CreateJob` (`k8s_helper.go:157-161`), with associated ConfigMaps for evaluation configuration and Secrets for credentials. The `eval_runtime_init` init container downloads test data from S3-compatible storage using the AWS SDK. The `eval_runtime_sidecar` proxies requests between the evaluation runtime and the main service. HardwareProfile CRs are queried to support hardware-aware scheduling of evaluation workloads. [source: internal/eval_hub/runtimes/k8s/k8s_helper.go:112-232, cmd/eval_runtime_init/main.go:114]
- **External integrations:** The service optionally connects to an MLflow Tracking Server over HTTPS with TLS 1.2-1.3 and custom CA certificate support for experiment tracking (`mlflow.go:43-92`). Traces, metrics, and logs are exported to an OpenTelemetry Collector over OTLP/gRPC (`internal/otel/otel_sdk.go:174`). The evalhub_mcp component exposes a Model Context Protocol server for AI agent integration. [source: internal/eval_hub/mlflow/mlflow.go:24-92, internal/otel/otel_sdk.go:174, internal/evalhub_mcp/server/server.go:223-228]
- **Security context:** 7 authentication rules describe enforcement across API endpoints and the Kubernetes API. Identity headers are conditionally required based on runtime configuration. Kubernetes operations use kubeconfig credential chains. TLS configuration imports are present across 10 source files for both HTTP and gRPC transports.
