## Purpose

**Short**: Preflight validation CLI for xKS clusters that verifies GPU availability, RDMA connectivity, network bandwidth, required CRDs, and operator health before AI workload deployment. [source: Dockerfile.konflux:19, cmd/agent/main.go:30-39]

**Detailed**: rhaii-cluster-validation is a Go CLI tool (also usable as a kubectl plugin via `kubectl-rhaii_validate`) that performs preflight validation of Kubernetes clusters before deploying AI/ML workloads. It validates GPU hardware (driver versions, ECC, memory), RDMA connectivity and bandwidth (ibv_rc_pingpong, ib_write_bw), TCP network performance (iperf3, custom TCP latency), and the presence of required platform CRDs (Gateway API, InferencePool, LeaderWorkerSet, cert-manager) and operators (cert-manager, Istio, LWS). The tool operates by deploying ephemeral Kubernetes Jobs to worker nodes under a dedicated ServiceAccount with privileged SCC access for hardware inspection. The controller process itself runs under the invoking administrator's kubeconfig credentials, not the workload ServiceAccount. Validation results are stored in a ConfigMap in the validation namespace. [source: cmd/agent/main.go:23-49, pkg/controller/controller.go:404-420, deploy/rbac.yaml:12-13, pkg/checks/crd/crd.go:50-79, pkg/config/platforms/ocp.yaml:37-45]

## Architectural Analysis

rhaii-cluster-validation follows a controller-agent architecture. The Cobra CLI entrypoint dispatches user-selected validation suites (gpu, network, rdma, deps, all) to a controller that orchestrates Kubernetes Jobs on target nodes. The controller creates a dedicated namespace (`rhaii-validation` by default), deploys an RBAC scaffold (ServiceAccount, empty ClusterRole, and a privileged SCC binding on OpenShift), and launches per-node agent Jobs that execute hardware and network checks. Agent pods run the same `rhaii-validator` binary in internal sub-commands (`run`, `tcp-lat-server`, `tcp-lat-client`) with host-level access to sysfs for PCI topology, GPU driver, and RDMA device discovery. [source: cmd/agent/main.go:42-55, pkg/controller/controller.go:935-962, deploy/rbac.yaml:12-19, Dockerfile.konflux:35-36]

A key design choice is the separation of authentication contexts: the controller process authenticates to the Kubernetes API using the invoking administrator's kubeconfig (via `client-go/tools/clientcmd`), while the workload Job pods use the `rhaii-validator` ServiceAccount solely for SCC privilege escalation — they never call the Kubernetes API themselves. This limits the blast radius of the privileged SCC binding to hardware-inspection operations within the validation Jobs. [source: deploy/rbac.yaml:12-13, pkg/controller/controller.go:404-420, pkg/controller/controller.go:2532-2556]

The dependency-check suite validates platform readiness by querying for required CRDs (Gateway API Gateways and HTTPRoutes, InferencePool, LeaderWorkerSet, cert-manager) and checking operator namespace presence (cert-manager, Istio, LWS). These are validation targets rather than runtime dependencies — the tool reports their presence or absence but does not consume their APIs. Platform configuration is loaded from embedded YAML profiles per target platform (OCP, EKS, CoreWeave), enabling platform-specific resource requests, GPU driver version thresholds, and network performance pass/warn criteria. [source: pkg/checks/crd/crd.go:50-79, pkg/config/platforms/ocp.yaml:23-45]

## Data Flows

1. **CLI invocation → Controller setup:** The administrator invokes `rhaii-validator` (or `kubectl rhaii-validate`) with a validation suite (gpu, network, rdma, deps, all). The controller loads kubeconfig credentials, builds a Kubernetes clientset, and ensures the validation namespace and RBAC resources exist. [source: cmd/agent/main.go:23-49, pkg/controller/controller.go:404-433]

2. **Controller → Kubernetes API:** The controller creates Namespace, ServiceAccount, ClusterRole, ClusterRoleBinding, and SCC binding resources via the Kubernetes API (HTTPS/WSS on port 6443). It then deploys per-node Jobs for hardware and network checks, and stores results in a ConfigMap. [source: pkg/controller/controller.go:309, 935-962, deploy/rbac.yaml:1-32]

3. **Agent Jobs → Host hardware:** Job pods run with privileged SCC access to inspect host sysfs paths (`/sys/class/infiniband`, PCI topology) for GPU driver status, RDMA device availability, and NIC topology. For network tests, agent pods use raw TCP (port 12865 echo server for latency) and iperf3 for bandwidth measurement between node pairs. [source: cmd/agent/tcplat.go:33-88, Dockerfile.konflux:24-30, pkg/controller/controller.go:2532-2534]

4. **Controller → CRD/Operator checks:** The deps suite queries the Kubernetes API for required CRDs and checks operator namespace presence. Results are aggregated into a validation report stored in a ConfigMap. [source: pkg/checks/crd/crd.go:50-79, pkg/config/platforms/ocp.yaml:23-45, pkg/controller/controller.go:300-320]
