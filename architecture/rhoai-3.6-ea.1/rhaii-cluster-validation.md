## Purpose

**Short**: Preflight validation CLI that verifies GPU availability, RDMA connectivity, network bandwidth, required CRDs, and operator health on Kubernetes clusters before AI workload deployment. [source: Dockerfile.konflux:17-22, cmd/agent/main.go:30-39]

**Detailed**: rhaii-cluster-validation is a Go CLI tool (`rhaii-validator`) distributed as a kubectl plugin and container image that performs preflight validation of Kubernetes clusters for AI/ML workload readiness. It orchestrates per-node validation Jobs to check GPU hardware (driver version, ECC status, memory), RDMA connectivity (device availability, NIC topology, pingmesh, bandwidth), and TCP network performance (bandwidth, latency via iperf3). A separate dependency-check mode validates the presence of required platform CRDs (Gateway API, InferencePool, LeaderWorkerSet, cert-manager) and operator health (cert-manager, Istio, LeaderWorkerSet) without creating cluster resources. The controller runs under the invoking administrator's kubeconfig credentials and creates temporary Namespaces, ServiceAccounts, ConfigMaps, Jobs, ClusterRoles, and ClusterRoleBindings for validation infrastructure, cleaning them up after checks complete. [source: cmd/agent/main.go:23-61, pkg/controller/controller.go:108-129, pkg/checks/crd/crd.go:50-81, pkg/checks/operator/operator.go:32-51]

## Architectural Analysis

rhaii-cluster-validation follows a controller-agent pattern where the CLI controller (running on the administrator's workstation or in a CI/CD pipeline) orchestrates per-node validation agents deployed as Kubernetes Jobs. The controller creates a dedicated `rhaii-validation` namespace with RBAC infrastructure, deploys agent pods to GPU nodes using tolerations and node selectors, collects results from pod logs and ConfigMap-based reports, and cleans up all temporary resources on completion. Agent pods run privileged (`securityContext.privileged: true`) to access GPU hardware and RDMA devices, using the `system:openshift:scc:privileged` SCC on OpenShift clusters. [source: deploy/node-check-job.yaml:28-29, deploy/rbac.yaml:12-14, pkg/controller/controller.go:84-101]

The tool supports platform-aware configuration via embedded YAML profiles (e.g., `ocp.yaml`) that define GPU driver version thresholds, RDMA resource names, CRD version requirements, operator namespace mappings, and network bandwidth pass/warn thresholds. Validation checks are organized into composable modes (gpu, network, rdma, rdma-node, rdma-ping, rdma-bandwidth, deps, all) that can be run independently or together. The dependency check mode (Tier 1) performs lightweight API-only validation of CRD presence and operator health without creating any cluster resources, making it suitable as a fast smoke test. [source: pkg/config/platforms/ocp.yaml:1-60, cmd/agent/main.go:42-55, pkg/controller/controller.go:120-122]

The component does not expose any HTTP or gRPC endpoints and does not define any Kubernetes Services — it is a run-to-completion CLI tool. All cluster interaction occurs through the Kubernetes API using client-go, authenticated via the invoking user's kubeconfig. Build-time FIPS compliance is enforced in Konflux Dockerfiles via `GOEXPERIMENT=strictfipsruntime` with dynamic linking, while local development builds use static linking without FIPS. [source: Dockerfile.konflux:11, Makefile:78]

## Data Flows

- **Validation orchestration:** The CLI controller connects to the Kubernetes API via kubeconfig, discovers GPU nodes by label or allocatable resources, creates a validation namespace with RBAC infrastructure, deploys per-node agent Jobs, streams pod logs for real-time progress, collects structured results from ConfigMap-based reports, and cleans up all temporary resources. [source: pkg/controller/controller.go:84-101, 108-129, deploy/node-check-job.yaml:1-51]
- **Agent execution:** Per-node agent pods run privileged GPU, RDMA, and network checks using host device access. Results are written to stdout (streamed by the controller) and optionally stored as ConfigMap reports. The agent does not call the Kubernetes API — `automountServiceAccountToken: false` is set on workload pods. [source: deploy/node-check-job.yaml:23, deploy/rbac.yaml:12-14]
- **Dependency validation:** The deps check mode queries the API server's apiextensions endpoint for required CRDs and lists pods in operator namespaces to verify health, without creating any cluster resources. [source: pkg/controller/controller.go:108-122, pkg/checks/crd/crd.go:50-81, pkg/checks/operator/operator.go:32-51]
