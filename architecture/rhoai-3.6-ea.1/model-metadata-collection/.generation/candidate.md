## Purpose

**Short**: Data container that ships pre-generated YAML catalogs of Red Hat AI models, MCP servers, and agents for consumption by other RHOAI platform components via volume mounts. [source: Dockerfile:53, Dockerfile.konflux:29, Dockerfile.konflux:9-22]

**Detailed**: model-metadata-collection is a data-only container that packages curated YAML catalog files describing Red Hat AI models, validated models, MCP servers (Red Hat, partner, and community), and agents. The container runs `sleep infinity` and exposes its catalog data at `/app/data` via a volume mount, allowing other platform components to access the catalog files without the container serving any network traffic. The repository also contains two Go CLI tools — `model-extractor` and `metadata-report` — that are used during CI/CD to generate the catalog files by fetching metadata from HuggingFace, GitHub, and container registries. These tools are not shipped in the production container image; only the generated YAML data files are copied into the final image. ## Architectural Analysis

model-metadata-collection follows a build-time generation, runtime data-serving pattern. The repository contains Go CLI tooling (`model-extractor`, `metadata-report`) that collects model metadata from external sources — HuggingFace collections API, GitHub repositories, and OCI container registries — and assembles curated YAML catalogs. These catalogs cover multiple domains: Red Hat AI models, validated models, partner and community MCP servers, and agents. CI/CD workflows run the extractor tools and commit the generated YAML files back to the repository.

The production container image is intentionally minimal: a `ubi9-minimal` (upstream) or `ubi9-minimal` (Konflux) base that copies only the pre-generated YAML files into `/app/data`. The container runs no processes of its own (`CMD ["sleep", "infinity"]`) and exposes no network endpoints. Other RHOAI platform components consume the catalog data by mounting the container's volume at `/app/data`. This design decouples catalog generation (which requires external API credentials and network access) from catalog consumption (which is purely filesystem-based).

The Go tools authenticate to external services via environment variables: `HF_TOKEN` for HuggingFace Bearer authentication and `GITHUB_TOKEN` for GitHub API access. Container registry access uses the `containers/image/v5` library's system credential chain. All external interactions are outbound HTTP client calls during build time only; no authentication is required or enforced at runtime.
