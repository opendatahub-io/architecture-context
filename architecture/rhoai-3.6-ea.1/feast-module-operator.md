## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Feast feature store deployments within the RHOAI platform, reconciling the `FeastOperator` CRD to deploy and configure upstream Feast components via kustomize-based manifests. [source: cmd/main.go:31, config/crd/bases/components.platform.opendatahub.io_feastoperators.yaml:2, internal/controller/feastoperator/feastoperator_controller.go:88]

**Detailed**: feast-module-operator is a Go-based Kubernetes operator built on controller-runtime and the opendatahub-operator/v2 reconciler framework. It watches the cluster-scoped `FeastOperator` custom resource (components.platform.opendatahub.io/v1alpha1) and reconciles the upstream Feast feature store operator into the RHOAI applications namespace. The reconciliation pipeline renders kustomize manifests, deploys resources with ordered apply and caching, manages cluster-scoped RBAC (ClusterRoles, ClusterRoleBindings) with explicit finalizer cleanup, and tracks deployment availability status. The operator also watches `ConfigMap` resources for platform version configuration and `CustomResourceDefinition` resources to detect component presence. It integrates with the Feast FeatureStore CRD (feast.dev), Kubeflow Notebooks (kubeflow.org) for workbench awareness, prometheus-operator for monitoring via ServiceMonitors, and OpenShift Routes for dashboard status. The binary is a Cobra CLI with two subcommands: `operator` (main controller loop) and `chartgen` (Helm chart generation utility). [source: cmd/main.go:31-43, internal/controller/feastoperator/feastoperator_controller.go:77-143, pkg/manager/manager.go:66-151]

## Architectural Analysis

The feast-module-operator follows the ODH module operator pattern, where a platform-level operator manages the lifecycle of a single component within the RHOAI ecosystem. Rather than implementing reconciliation logic from scratch, it delegates heavily to the opendatahub-operator/v2 reconciler framework — using its action pipeline for kustomize rendering (`kustomize.NewAction`), ordered deployment (`deploy.NewAction` with cache and apply ordering), garbage collection (`gc.NewAction`), deployment status tracking, and release management. [source: internal/controller/feastoperator/feastoperator_controller.go:113-134]

The operator's controller owns a broad set of Kubernetes resources (Deployments, Services, ServiceAccounts, ConfigMaps, RBAC resources, Jobs, and ServiceMonitors) and watches CustomResourceDefinitions and a platform-configuration ConfigMap to trigger reconciliation. A finalizer handles cleanup of cluster-scoped resources (ClusterRoles and ClusterRoleBindings) that cannot use standard owner references for garbage collection. [source: internal/controller/feastoperator/feastoperator_controller.go:88-131, 146-179]

Configuration is managed through a layered system using Viper: struct defaults, ConfigMap files from a mounted directory (`ODH_MODULE_OPERATOR_CONFIGURATION_PATH`), and environment variables with the `ODH_MODULE_OPERATOR_` prefix, in ascending order of precedence. This allows runtime configuration of controller parameters including metrics bind address, health probe address, leader election, and pprof without recompiling. [source: pkg/config/config.go:59-65, 140-155]

The metrics endpoint is served securely on port 8443 using controller-runtime's built-in HTTPS metrics server with RBAC-based authentication via TokenReview and SubjectAccessReview, enforced through dedicated ClusterRoles (`opendatahub-feast-metrics-auth-role` and `opendatahub-feast-metrics-reader`). Health and readiness probes are standard HTTP on port 8081 with no authentication. The operator uses namespace-scoped informer caches restricted to the applications namespace for resource types like Deployments, Services, and RBAC resources, while FeastOperator and CRD watches are cluster-scoped. [source: pkg/manager/manager.go:86-111, config/rbac/metrics_auth_role.yaml:1, config/rbac/metrics_reader_role.yaml:1]

FIPS compliance is addressed at build time through `GOEXPERIMENT=strictfipsruntime` and dynamic linking (`CGO_ENABLED=1`), built on a UBI9 go-toolset image and running on a UBI9-minimal runtime image that provides OpenSSL. [source: Dockerfile.konflux:7-25]
