**Detailed**: OpenVINO Model Server is a model inference engine built on Intel's OpenVINO toolkit that exposes KServe v1, v2, and gRPC v2 protocol endpoints for serving machine learning models. The repository packages two serving runtime definitions for the RHOAI platform: a `ClusterServingRuntime` (`kserve-openvino`) supporting OpenVINO, ONNX, TensorFlow, and Hugging Face model formats, and a namespace-scoped `ServingRuntime` (`kserve-ovms-2026-2`) that additionally supports Paddle, PyTorch, and vLLM formats with GPU capabilities. The core server binary (`/ovms/bin/ovms`) is built from C++ sources using Bazel/CMake on a UBI 9 base, linking against OpenSSL for TLS. An optional nginx-based mTLS authentication sidecar is provided in `extras/nginx-mtls-auth/` for deployments requiring client certificate verification. The repository also includes Go client libraries for KServe API and image classification demos. ## Architectural Analysis

OpenVINO Model Server follows a model-serving architecture where a single statically compiled C++ binary (`/ovms/bin/ovms`) handles both REST and gRPC inference requests using the KServe prediction protocol. The server is designed to be deployed as a container within a KServe `InferenceService`, where the KServe control plane manages the Kubernetes Service, routing, and scaling lifecycle. This means OVMS itself does not ship Kubernetes Service manifests — those are created dynamically by the KServe runtime reconciliation.

The repository provides two distinct serving runtime definitions targeting different deployment scopes. The `kserve-openvino` ClusterServingRuntime (REST on port 8080, gRPC on port 9000) is a cluster-wide runtime supporting four model formats with Prometheus metrics exposed at `/metrics` on the REST port. The `kserve-ovms-2026-2` ServingRuntime (REST on port 8888, gRPC on port 8001) is namespace-scoped with RHOAI dashboard integration via the `opendatahub.io/dashboard: "true"` label and supports seven model formats including GPU-accelerated inference via the `latest-gpu` image tag.

Security is architecturally layered: the core OVMS binary does not implement authentication, relying on the KServe/Istio service mesh for transport security in production deployments. For environments requiring explicit mTLS, the repository provides an nginx sidecar pattern (`extras/nginx-mtls-auth/`) that proxies both gRPC and REST traffic through nginx with TLSv1.2 client certificate verification, binding OVMS to localhost and exposing only the authenticated nginx ports externally. The sidecar uses a wrapper script that dynamically reassigns OVMS ports to avoid conflicts with the nginx listener ports.

The build pipeline is C++-centric, compiling against OpenSSL and Boost on a UBI 9 base with no explicit FIPS mode configuration. The Go code in the repository is limited to client-side demo libraries (kserve-api, ovmsclient) and does not participate in the serving runtime. ### FIPS Compliance

The OVMS binary is a C++ application compiled against `openssl-devel` on UBI 9, not a Go binary. Standard Go FIPS build flags (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) do not apply. The Go code in this repository is limited to client demo libraries and does not produce the serving runtime binary.

No explicit FIPS mode configuration was found in the Dockerfile build or runtime configuration. The server inherits system OpenSSL from the UBI 9 base image, which supports FIPS mode when the host system enables it, but the application does not enforce or validate FIPS mode at the application level.

The optional nginx-mtls-auth sidecar configures `TLSv1.2` with a restricted cipher suite (`AES256+EECDH`) that excludes several weak algorithms but does not explicitly configure nginx for FIPS mode. [source: Dockerfile.konflux:44-45, extras/nginx-mtls-auth/model_server.conf.template:34-35]
