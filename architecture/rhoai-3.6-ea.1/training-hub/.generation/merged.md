## Purpose

**Short**: Training Hub is a Python SDK providing a unified algorithm-focused interface for language model training techniques including SFT, OSFT, LoRA, GRPO, and GEPA prompt optimization, with pluggable backends for instructlab-training, rhai-innovation-mini-trainer, ART (OpenPipe), verl, and MLflow. [source: pyproject.toml:8-9, src/training_hub/__init__.py:1-51]

**Detailed**: Training Hub is a Python library that abstracts multiple LLM training paradigms behind a common Algorithm/Backend plugin architecture. It provides five algorithm families: supervised fine-tuning (SFT) via instructlab-training, orthogonal subspace fine-tuning (OSFT) via rhai-innovation-mini-trainer, LoRA-based fine-tuning via Unsloth, reinforcement learning from verifiable rewards (GRPO) via ART/OpenPipe with co-located vLLM inference, and gradient-free prompt optimization (GEPA) with optional MLflow integration. The library is consumed as a pip-installable package by data scientists in notebooks or by platform training jobs; it does not expose HTTP endpoints, define Kubernetes services, or ship container images itself. Optional dependency groups (cuda, lora, grpo, grpo-verl, gepa, dev) control which backends and accelerator support are installed. [source: pyproject.toml:7-97, src/training_hub/__init__.py:1-51, src/training_hub/algorithms/__init__.py:1-80]

## Architectural Analysis

Training Hub uses a registry-based plugin architecture with two extension axes: algorithms and backends. The `AlgorithmRegistry` class maps algorithm names to `Algorithm` subclasses and each algorithm to one or more `Backend` implementations, allowing callers to select both the training technique and the execution engine at runtime. [source: src/training_hub/algorithms/__init__.py:33-79]

The library delegates all heavy computation to backend packages rather than implementing training loops directly. SFT delegates to `instructlab.training.run_training`; OSFT delegates to rhai-innovation-mini-trainer; LoRA SFT uses Unsloth; GRPO uses the ART framework from OpenPipe with a co-located vLLM engine for inference during RL training; and GEPA uses the `gepa` library for evolutionary prompt search with an optional MLflow-backed variant that integrates with MLflow's prompt registry and experiment tracking. [source: src/training_hub/algorithms/sft.py:3-8, src/training_hub/algorithms/lora_grpo.py:1-43, src/training_hub/algorithms/gepa.py:150-179]

As a library without its own service entrypoint, Training Hub has no inbound network surface. Its outbound integrations are mediated by environment variables: GEPA's litellm-backed LLM calls use `OPENAI_API_BASE` and `OPENAI_API_KEY`, and SFT's optional MLflow logging uses tracking URI parameters. The library includes a `TrainingHubCallback` abstraction for training lifecycle hooks and memory/timing profiling estimators for pre-flight resource planning. [source: src/training_hub/algorithms/gepa.py:62-71, src/training_hub/__init__.py:9-11]

The GRPO algorithm supports single-turn tool-call verification with a built-in reward function and multi-turn agentic rollouts with custom rollout functions. A verl-based alternative backend (`VeRLLoRAGRPOBackend`) provides the same GRPO algorithm on the verl distributed RL framework with a custom `SingleTurnToolAgentLoop` that adds tool-call template support. [source: src/training_hub/algorithms/lora_grpo.py:1-43, src/training_hub/algorithms/verl_tool_agent.py:1-30]

## Data Flows

Training Hub operates as an in-process library with no inbound network surface. Data flows are caller-driven:

- **Training data ingestion:** Callers pass model paths, dataset paths (local or HuggingFace identifiers), and hyperparameters to algorithm entry points (e.g., `sft()`, `osft()`, `lora_grpo()`, `gepa()`). The library delegates execution to the selected backend. [source: src/training_hub/algorithms/sft.py:17-28, src/training_hub/algorithms/gepa.py:28-103]
- **GEPA prompt optimization:** The GEPA algorithm makes outbound HTTP calls to an LLM inference endpoint via litellm, configured by `OPENAI_API_BASE` and authenticated by `OPENAI_API_KEY`. The optional MLflow backend additionally communicates with an MLflow tracking server for prompt registry and experiment tracking. [source: src/training_hub/algorithms/gepa.py:62-71, 150-179]
- **GRPO reinforcement learning:** The ART backend co-locates a vLLM inference engine in the same process for generating rollouts during GRPO training. Communication is in-process (no network traffic). The verl backend uses verl's distributed rollout infrastructure. [source: src/training_hub/algorithms/lora_grpo.py:60-77, src/training_hub/algorithms/verl_tool_agent.py:15-17]
- **Checkpoint output:** All algorithms write model checkpoints and training artifacts to a caller-specified `ckpt_output_dir` on the local filesystem. [source: src/training_hub/algorithms/sft.py:34-37]
