**Detailed**: model-metadata-collection provides a catalog of Red Hat AI models, MCP servers, and agents as structured YAML files. The repository contains two Go CLI tools — `model-extractor` and `metadata-report` — that run during CI/CD to collect metadata from HuggingFace, GitHub, and OCI container registries, then generate catalog YAML files. The deployed container image (based on UBI9) packages only these pre-generated YAML files and runs `sleep infinity`, serving as a data volume mount point for other platform components such as the RHOAI dashboard. The container exposes no network ports, runs no application code at runtime, and has no inbound API surface. ## Architectural Analysis

model-metadata-collection follows a split architecture: a CI/pipeline-time data collection pipeline and a runtime data-only container. The `model-extractor` Go CLI orchestrates parallel metadata collection from three external sources — HuggingFace collections API, GitHub repository content API, and OCI container registries — merging results with static supplemental catalogs into structured YAML files covering models, MCP servers, and agents. The `metadata-report` CLI generates completeness reports from the extracted data. Both tools are build-time artifacts that do not ship in the deployed container.

The deployed container image uses a UBI9 base, copies the pre-generated YAML catalog files into `/app/data/`, and runs `sleep infinity` as a non-root user (UID 1001). It is designed exclusively as a volume mount source — other RHOAI components mount `/app/data` to read the catalog YAML files. The container exposes no ports, runs no application logic, and has no Kubernetes service, ingress, or RBAC configuration. There are no kustomize manifests in the repository; deployment is managed externally.

The external authentication for CI tools is optional and environment-variable-driven: `HF_TOKEN` for HuggingFace API Bearer authentication and `GITHUB_TOKEN` for GitHub API Bearer authentication. Both tokens are read lazily via `sync.Once` and, when absent, the tools fall back to unauthenticated requests with rate-limiting implications. OCI registry access uses the `containers/image` library's default authentication chain. ## Data Flows

### Flow 1: CI/CD Metadata Collection Pipeline

The `model-extractor` CLI runs during CI/CD to collect and generate catalog data. It fetches model metadata from HuggingFace collections, enriches it with OCI registry image metadata, fetches agent metadata from GitHub, merges results with static supplemental catalogs, and writes structured YAML catalog files to the `data/` directory. These files are then committed to the repository by CI automation. [source: cmd/model-extractor/main.go:102-239, internal/huggingface/client.go:54-59, internal/registry/registry.go:14-17]

### Flow 2: Container Volume Mount

The deployed container image copies the pre-generated YAML catalogs into `/app/data/` and exposes it as a volume mount point. Other RHOAI platform components mount this volume to read model, MCP server, and agent catalog data. No network communication occurs; data access is filesystem-based.
