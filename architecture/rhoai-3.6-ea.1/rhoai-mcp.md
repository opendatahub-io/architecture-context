## Purpose

**Short**: rhoai-mcp is a Python-based MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments, providing tools for managing workbenches, model serving, pipelines, and cluster resources via the Kubernetes API. [source: pyproject.toml:2-4, src/rhoai_mcp/server.py:300-305]

**Detailed**: rhoai-mcp implements a Model Context Protocol server using the FastMCP framework atop Starlette/uvicorn, exposing RHOAI platform operations as MCP tools to AI agents. The server supports three transport modes — stdio (default for Claude Desktop), SSE, and streamable-http — and uses a pluggy-based plugin system to organize domain-specific tools across workbenches (Kubeflow Notebooks), model serving (KServe InferenceServices, ServingRuntimes), training (Kubeflow TrainJobs), pipelines (DataSciencePipelinesApplications), and cluster management. Authentication is configurable via OIDC with JWT or TokenReview validation modes, enforced through ASGI middleware with per-tool RBAC filtering backed by Kubernetes SubjectAccessReview. The server authenticates to the Kubernetes API using either the user's forwarded token or impersonation, depending on the configured auth strategy. It is deployed as a single-replica Kubernetes Deployment with a ClusterIP Service on port 8000, using a broad ClusterRole that grants access to platform CRDs across multiple API groups. ## Architectural Analysis

rhoai-mcp adopts a plugin-oriented architecture where domain capabilities (workbenches, inference, pipelines, training, cluster management) are organized as pluggy plugins that register MCP tools, resources, and prompts with the central FastMCP server. This design allows selective enablement of plugins via the `RHOAI_MCP_ENABLED_PLUGINS` environment variable, supporting both full-featured and constrained deployments. The plugin manager also collects per-tool RBAC permission mappings that feed into the server's tool-level authorization filtering.

The security model has two distinct layers. At the transport layer, an ASGI middleware validates OIDC tokens on all MCP protocol endpoints (SSE and streamable-http), exempting only `/health` and the `/.well-known/oauth-protected-resource` metadata endpoint. At the tool layer, a patched `ListToolsRequest`/`CallToolRequest` handler performs Kubernetes SubjectAccessReview checks against the authenticated user's identity, filtering visible and callable tools based on RBAC permissions defined by each plugin. When OIDC is disabled (the default), all tools are accessible to any caller — this is the expected posture for single-user stdio deployments.

The server's Kubernetes API interaction is notable for its breadth: the ClusterRole grants access to 12 distinct resource rules spanning core resources (pods, namespaces, secrets, PVCs, nodes, PVs, events, services), Kubeflow resources (notebooks, trainjobs, trainingruntimes, clustertrainingruntimes), KServe resources (inferenceservices, servingruntimes), Data Science Pipelines, and storage classes. This broad scope reflects the MCP server's role as a general-purpose RHOAI management proxy for AI agents. The `rhoai-mcp` service account receives cluster-scoped access via a ClusterRoleBinding, which means namespace-level isolation depends on the OIDC/RBAC layer rather than on Kubernetes RBAC alone.

The AIPCC base image provides the Python runtime with pre-configured pip/uv package indexes. FIPS compliance is inherited from the base image's OpenSSL configuration; the application itself uses `cryptography` and `PyJWT[crypto]` for JWT operations but does not explicitly configure FIPS mode at the application level. ## Data Flows

- **Client ingress:** AI agents connect to the rhoai-mcp server via MCP protocol over one of three transports: stdio (direct process), SSE, or streamable-http. HTTP transports are served by uvicorn on port 8000 behind a ClusterIP Service. When OIDC is enabled, the OIDCAuthMiddleware validates Bearer tokens on all MCP protocol paths before requests reach the FastMCP handler. [source: src/rhoai_mcp/server.py:300-308, 382-417, deploy/kustomize/base/service.yaml:1]
- **Kubernetes API interactions:** The server uses the Python `kubernetes` client to perform CRUD operations against the Kubernetes API server. When OIDC is enabled, each request uses either the caller's forwarded token or impersonation headers, depending on the configured `oidc_kube_auth_strategy`. When OIDC is disabled, all operations use the `rhoai-mcp` service account. [source: src/rhoai_mcp/server.py:82-118, src/rhoai_mcp/config.py:61-65]
- **Platform CRD interactions:** The server reads and manages CRDs across multiple API groups — KServe InferenceServices and ServingRuntimes (`serving.kserve.io`), Kubeflow Notebooks (`kubeflow.org`), TrainJobs and TrainingRuntimes (`trainer.kubeflow.org`), and DataSciencePipelinesApplications (`datasciencepipelinesapplications.opendatahub.io`) — via the Kubernetes API, as authorized by the `rhoai-mcp` ClusterRole. [source: deploy/kustomize/base/clusterrole.yaml:1]
