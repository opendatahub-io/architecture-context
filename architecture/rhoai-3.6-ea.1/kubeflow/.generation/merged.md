## Purpose

**Short**: Kubeflow Notebooks controller pair that manages the lifecycle of Jupyter notebook workbenches on OpenShift, including workload creation, Gateway API routing, kube-rbac-proxy sidecar injection for authentication, and DSPA pipeline integration. [source: components/notebook-controller/main.go:58, components/odh-notebook-controller/main.go:142]

**Detailed**: The kubeflow repository ships two complementary controller-runtime operators for the RHOAI platform. The upstream **notebook-controller** reconciles `Notebook` custom resources (kubeflow.org CRD) into StatefulSets, Services, and Events, handling pod lifecycle and idle culling. The downstream **odh-notebook-controller** extends this with OpenShift-specific concerns: it injects a kube-rbac-proxy sidecar into every notebook pod for token-based authentication and TLS termination, manages Gateway API HTTPRoute and ReferenceGrant resources in a central namespace for secure ingress, reconciles NetworkPolicy resources for pod isolation, and optionally provisions Elyra pipeline runtime configuration by reading DataSciencePipelinesApplication CRs from the data-science-pipelines-operator API. Both controllers are built as FIPS-compliant Go binaries (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) on UBI9 base images, and the odh-notebook-controller fetches the cluster's TLS security profile from the OpenShift APIServer configuration at startup. [source: components/notebook-controller/controllers/notebook_controller.go:801, components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54, components/odh-notebook-controller/controllers/notebook_dspa_secret.go:49, components/notebook-controller/Dockerfile.konflux:29, components/odh-notebook-controller/Dockerfile.konflux:24, components/odh-notebook-controller/main.go:179]

## Architectural Analysis

The kubeflow component implements a two-controller architecture where the upstream notebook-controller handles core Kubeflow Notebook CRD reconciliation and the odh-notebook-controller layers OpenShift-specific platform integration on top. This split preserves upstream compatibility while enabling Red Hat-specific security, routing, and observability features.

**Controller coordination and reconciliation lock.** The odh-notebook-controller's mutating webhook injects a `kubeflow-notebook-controller-lock` stop annotation on every new Notebook to prevent the upstream controller from starting the pod before the ODH controller finishes its first reconciliation pass. This avoids a race condition where the pod could start before pull secrets, network policies, and auth sidecars are provisioned. The lock is removed after the ODH controller completes its initial reconciliation. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:106-121]

**Authentication via kube-rbac-proxy sidecar injection.** Rather than embedding authentication logic in the notebook application, the mutating webhook injects a kube-rbac-proxy sidecar container into every Notebook pod. The proxy listens on a secure port with TLS certificates, forwards authenticated requests to the notebook's localhost port, and propagates identity via `X-Auth-Request-User` and `X-Auth-Request-Groups` headers. Resource limits for the sidecar are configurable via Notebook annotations with validated defaults. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:183-244]

**Gateway API routing in a central namespace.** HTTPRoute resources are created in the controller's own namespace rather than the user's namespace for security isolation. Since cross-namespace owner references are not supported in Kubernetes, the controller uses label-based matching (`notebook-name`, `notebook-namespace`) and finalizers for cleanup instead of standard garbage collection. ReferenceGrant resources authorize cross-namespace backend references from the central namespace to the notebook's namespace. [source: components/odh-notebook-controller/controllers/notebook_route.go:142-193]

**DSPA pipeline integration.** The controller optionally reads `DataSciencePipelinesApplication` CRs via the data-science-pipelines-operator API types. When a DSPA instance named `dspa` exists in the notebook's namespace, the controller provisions an Elyra runtime configuration secret to enable pipeline submission from notebooks. The integration degrades gracefully: if the DSPA CRD is not installed or no instance exists, the feature is silently skipped. [source: components/odh-notebook-controller/controllers/notebook_dspa_secret.go:49-66]

**Platform TLS posture.** The odh-notebook-controller fetches the cluster-wide TLS security profile from `config.openshift.io/v1/APIServer` at startup and applies it to both the webhook server and metrics endpoint. On non-OpenShift clusters or when the API is transiently unavailable, hardened defaults are used. This ensures the controller's TLS configuration tracks the platform's cipher suite and protocol version policy. [source: components/odh-notebook-controller/main.go:179-209]
