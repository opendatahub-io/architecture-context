## Purpose

**Short**: Dual Kubernetes controller system that manages Kubeflow Notebook workbench lifecycle, injecting kube-rbac-proxy sidecars, Gateway API HTTPRoutes, and Elyra pipeline integration for RHOAI notebook workbenches. [source: components/notebook-controller/main.go:58, components/odh-notebook-controller/main.go:141, components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54]

**Detailed**: The kubeflow component ships two complementary controller-runtime operators. The upstream `notebook-controller` manages core Notebook CR lifecycle—creating StatefulSets, Services, and handling pod culling for idle workbenches. The downstream `odh-notebook-controller` extends this with OpenShift-specific concerns: it injects kube-rbac-proxy sidecar containers into notebook pods for authenticated access, manages Gateway API HTTPRoutes through the platform's `data-science-gateway` in `openshift-ingress`, creates NetworkPolicies for workbench isolation, and integrates with Data Science Pipelines by reading DataSciencePipelinesApplication CRs to generate Elyra runtime configuration secrets. Both controllers serve admission webhooks (mutating and validating) on port 8443 with TLS, and expose health/readiness probes on port 8081. The webhook server's TLS configuration follows the OpenShift APIServer TLS profile when available, falling back to hardened Mozilla Intermediate cipher defaults with TLS 1.2 minimum. ## Architectural Analysis

The kubeflow component follows a layered controller architecture where two independent controller-runtime managers partition responsibility across upstream and OpenShift-specific concerns.

**Controller separation.** The `notebook-controller` (upstream Kubeflow) owns the Notebook CRD lifecycle: it reconciles Notebooks into StatefulSets and Services, and runs a `CullingReconciler` that monitors pod activity metrics to stop idle workbenches. The `odh-notebook-controller` (downstream) extends the Notebook resource with platform integration—it injects kube-rbac-proxy sidecar containers for authentication, manages Gateway API HTTPRoutes for ingress routing, creates per-workbench NetworkPolicies, and handles cross-component secret propagation for Elyra pipeline runtimes. Both controllers ship as separate container images built from the same monorepo. [source: components/notebook-controller/controllers/notebook_controller.go:801-808, components/notebook-controller/controllers/culling_controller.go:580, components/odh-notebook-controller/main.go:141-246]

**Admission webhook chain.** The ODH controller registers both mutating and validating webhooks for the Notebook resource. The mutating webhook (`/mutate-notebook-v1`) is the primary injection point: it adds the kube-rbac-proxy sidecar container, injects proxy environment variables from the cluster-level OpenShift Proxy configuration, resolves ImageStream references, and sets the reconciliation-lock annotation that coordinates startup ordering with the upstream controller's culling logic. The validating webhook (`/validate-notebook-v1`) enforces update-time constraints. A conversion webhook (`/convert`) handles CRD version migration between v1alpha1, v1beta1, and v1. All webhook endpoints serve over TLS on port 8443. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54-104, components/odh-notebook-controller/controllers/notebook_validating_webhook.go:31, components/odh-notebook-controller/main.go:243-246]

**Gateway API ingress pattern.** Rather than using OpenShift Routes directly for notebook access, the ODH controller creates HTTPRoute resources in the controller's central namespace, referencing the platform-managed `data-science-gateway` Gateway in `openshift-ingress`. Each notebook gets a path-prefix route at `/notebook/{namespace}/{name}` with cross-namespace backend references and associated ReferenceGrant resources. Gateway and namespace names are configurable via `NOTEBOOK_GATEWAY_NAME` and `NOTEBOOK_GATEWAY_NAMESPACE` environment variables. [source: components/odh-notebook-controller/controllers/notebook_route.go:34-107]

**Data Science Pipelines integration.** The controller optionally integrates with the Data Science Pipelines operator by importing its v1 API types. When a `DataSciencePipelinesApplication` CR named `dspa` exists in a notebook's namespace, the controller generates an Elyra runtime configuration secret that enables pipeline submission from within the workbench. This dependency is graceful—the controller handles both missing CRDs and missing instances without error. [source: components/odh-notebook-controller/controllers/notebook_dspa_secret.go:26-60]

**TLS posture.** The controller fetches the OpenShift APIServer TLS profile at startup via `openshift/controller-runtime-common/pkg/tls` and applies it to both the webhook server and metrics endpoint. On non-OpenShift clusters or when the profile is unavailable, it falls back to a hardened default: TLS 1.2 minimum with Mozilla Intermediate cipher suites (ECDHE+AES-GCM and ECDHE+CHACHA20). The Konflux builds use `GOEXPERIMENT=strictfipsruntime` with dynamic linking (`CGO_ENABLED=1`) for FIPS runtime compliance. [source: components/odh-notebook-controller/main.go:42, 68-78, 178-221, components/notebook-controller/Dockerfile.konflux:29, components/odh-notebook-controller/Dockerfile.konflux:24]

## Data Flows

- **Notebook creation flow:** A user creates a Notebook CR → the mutating webhook intercepts the admission request and injects the kube-rbac-proxy sidecar container, proxy environment variables, and the reconciliation-lock annotation → the upstream NotebookReconciler creates a StatefulSet, Service, and begins watching the pod → the ODH OpenshiftNotebookReconciler creates an HTTPRoute in the controller namespace referencing the `data-science-gateway` Gateway, a NetworkPolicy for workbench isolation, and optionally an Elyra pipeline secret if a DSPA instance exists → the reconciliation lock is released and the pod starts. [source: components/odh-notebook-controller/controllers/notebook_mutating_webhook.go:54-62, components/odh-notebook-controller/controllers/notebook_route.go:48-107, components/odh-notebook-controller/controllers/notebook_dspa_secret.go:49-60]
- **Ingress routing:** External traffic enters through the platform's Gateway API `data-science-gateway` in `openshift-ingress` → the HTTPRoute matches on path prefix `/notebook/{namespace}/{name}` → traffic is forwarded to the notebook Service in the user's namespace via cross-namespace backend references with a corresponding ReferenceGrant. [source: components/odh-notebook-controller/controllers/notebook_route.go:90-107]
- **Idle culling:** The CullingReconciler periodically checks notebook pod activity timestamps → if a workbench has been idle beyond the configured threshold, the controller deletes the pod via the StatefulSet's scale mechanism and annotates the Notebook CR with a stopped status. [source: components/notebook-controller/controllers/culling_controller.go:580, 92, 122]
- **Admission security:** All webhook endpoints (mutating, validating, conversion) serve over TLS on port 8443 with certificates from a configurable directory. Health and readiness probes on port 8081 are unauthenticated by design. The webhook TLS configuration follows the OpenShift APIServer TLS profile or hardened Mozilla Intermediate defaults. [source: components/odh-notebook-controller/main.go:153-156, 207-221, 243-246]
