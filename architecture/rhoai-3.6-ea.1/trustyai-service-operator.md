## Purpose

**Short**: Kubernetes operator managing TrustyAI explainability services, EvalHub evaluation workloads, GuardrailsOrchestrator safety orchestration, NemoGuardrails guardrail deployments, and LMEvalJob language model evaluation jobs within RHOAI. [source: controllers/tas/trustyaiservice_controller.go:279, controllers/evalhub/evalhub_controller.go:341, controllers/gorch/guardrailsorchestrator_controller.go:410, controllers/lmes/lmevaljob_controller.go:341]

**Detailed**: The trustyai-service-operator is a multi-controller Kubernetes operator that manages the lifecycle of AI trustworthiness, evaluation, and safety infrastructure within Red Hat OpenShift AI. It reconciles six custom resource types across five controller domains: TrustyAIService for model explainability and bias monitoring (with kube-rbac-proxy sidecar for authenticated API access), EvalHub for centralized evaluation orchestration with multi-tenant namespace isolation, GuardrailsOrchestrator for safety guardrail deployment integrated with KServe InferenceService, NemoGuardrails for NVIDIA NeMo guardrails management, and LMEvalJob for language model evaluation job orchestration with Kueue integration. A separate trustyai-operator-module controller manages the platform-level TrustyAI component CRD (components.platform.opendatahub.io/TrustyAI) using odh-platform-utilities for platform detection and manifest rendering. The operator reads cluster TLS configuration from the OpenShift APIServer resource and enforces FIPS-compatible cipher suites, with DSC ConfigMap integration for evaluation policy configuration from the OpenDataHub operator. [source: controllers/tas/templates/service/deployment.tmpl.yaml:153-162, controllers/evalhub/evalhub_controller.go:338-367, pkg/tls/tls.go:78-129, controllers/dsc/config.go:37-67]

## Architectural Analysis

The trustyai-service-operator employs a multi-controller architecture under a single manager process (`cmd/main.go`), with a separate trustyai-operator-module binary for platform-level TrustyAI component management. The primary operator hosts seven reconciliation loops: TrustyAIService, EvalHub (with auxiliary job-failure and Kueue-workload controllers), GuardrailsOrchestrator, NemoGuardrails, and LMEvalJob. Each controller manages its own owned resources (Deployments, Services, ConfigMaps) and registers conditional watches—notably, ServiceMonitor ownership is gated on prometheus-operator API availability at startup, and Kueue Workload reconciliation activates only when the kueue.x-k8s.io/v1beta1 API is detected. [source: controllers/evalhub/evalhub_controller.go:348-364]

The TrustyAI service workload uses a sidecar authentication pattern: the Quarkus-based TrustyAI service container listens on port 8080 (localhost-only), while a kube-rbac-proxy sidecar enforces SubjectAccessReview-based authorization on the external port 8443 using TLS certificates from a Kubernetes Secret. The proxy configuration is loaded from a per-instance ConfigMap, and the proxy's own health endpoint at port 9443 uses HTTPS but is unauthenticated. This architecture ensures that all external API access passes through Kubernetes-native authorization without requiring the application to implement its own auth layer. [source: controllers/tas/templates/service/deployment.tmpl.yaml:153-168]

The operator integrates with the OpenShift platform TLS infrastructure by reading the cluster-wide APIServer TLS security profile (`apiservers.config.openshift.io/cluster`) at startup and applying the resolved cipher suites and minimum TLS version to the controller-runtime webhook server. On non-OpenShift clusters or when the API server is unavailable, it falls back to hardened Mozilla Intermediate defaults (TLS 1.2 minimum, FIPS-compatible AES-GCM and ChaCha20 cipher suites). This fail-closed design ensures secure defaults regardless of platform availability. [source: pkg/tls/tls.go:78-135]

The EvalHub controller implements multi-tenant namespace isolation: it watches Namespace resources filtered by a tenant label predicate and bootstraps a shared tenant namespace cache at startup. Evaluation policy (online evaluation and code execution permissions) is centrally configured via a `trustyai-dsc-config` ConfigMap provisioned by the OpenDataHub operator, creating a runtime dependency on the platform operator for policy propagation. [source: controllers/evalhub/evalhub_controller.go:345, controllers/dsc/config.go:17-22, 37-67]

## Data Flows

- **TrustyAI Service request path:** External clients connect to the kube-rbac-proxy sidecar on port 8443 (TLS); the proxy performs a Kubernetes SubjectAccessReview for authorization and forwards authenticated requests to the TrustyAI Quarkus service on localhost:8080. Health probes bypass the proxy via the dedicated proxy-healthz port 9443 (HTTPS, unauthenticated). The service exposes metrics at `/q/metrics` on the internal port for Prometheus scraping via annotated pod metadata. [source: controllers/tas/templates/service/deployment.tmpl.yaml:153-168, 37-39, 125-138]
- **Operator control plane:** The manager process watches six CRD types and creates/updates Deployments, Services, ConfigMaps, ServiceAccounts, Roles, RoleBindings, and Routes as owned resources. All Kubernetes API communication uses the in-cluster ServiceAccount token over TLS to the API server on port 6443. The operator reads the platform-provisioned `trustyai-dsc-config` ConfigMap for evaluation policy and the OpenShift APIServer resource for TLS profile configuration at startup. [source: controllers/evalhub/evalhub_controller.go:338-367, controllers/dsc/config.go:37-67, pkg/tls/tls.go:78-97]
- **Platform integrations:** The GuardrailsOrchestrator controller watches KServe InferenceService resources to read model serving state. The EvalHub controller conditionally owns ServiceMonitor resources when the prometheus-operator API is available. The trustyai-operator-module uses odh-platform-utilities for platform detection and manifest rendering. [source: controllers/gorch/guardrailsorchestrator_controller.go:449, controllers/evalhub/evalhub_controller.go:348-349, trustyai-operator-module/config/rbac/role.yaml:83-96]
- **Security context:** 5 authentication rules and 4 secret references describe enforcement and credential inputs. The kube-rbac-proxy sidecar provides the primary API authentication boundary, while the operator itself authenticates to the Kubernetes API via in-cluster ServiceAccount tokens. Health and readiness probes are unauthenticated by design. TLS is enforced with FIPS-compatible cipher suites derived from the cluster TLS profile.
