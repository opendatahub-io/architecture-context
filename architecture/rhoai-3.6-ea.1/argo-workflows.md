## Purpose

**Short**: Argo Workflows is the workflow execution engine for Data Science Pipelines in RHOAI, providing a Kubernetes-native workflow controller and API server that manage pipeline step orchestration via CRD-based workflow definitions. **Detailed**: Argo Workflows provides the underlying workflow execution runtime for Red Hat OpenShift AI Data Science Pipelines. The component consists of two primary deployments: the **workflow-controller**, which watches Workflow CRDs and orchestrates pod-based step execution, and the **argo-server**, which exposes a gRPC and HTTP API surface for workflow management, artifact access, and observability. A third binary, **argoexec**, runs as a sidecar or init container within workflow step pods to manage artifact I/O and container lifecycle.

The component defines 8 CRDs in the `argoproj.io/v1alpha1` API group, covering workflows, templates, cron scheduling, event bindings, artifact GC tasks, and task results. The API server registers 9 gRPC services and 18 HTTP endpoints, with authentication enforced through a configurable gatekeeper supporting client token delegation, server-mode service account auth, and SSO/OIDC integration. The Konflux production builds use Go 1.26 with `GOFIPS140=v1.0.0` for native FIPS 140-3 crypto. ## Architectural Analysis

Argo Workflows follows a controller-pattern architecture with two principal workloads. The **workflow-controller** Deployment runs as a reconciliation loop watching `Workflow`, `CronWorkflow`, and related CRDs, creating and managing Pods that execute individual workflow steps. Each step Pod runs an **argoexec** sidecar that handles artifact upload/download and container wait logic. The **argo-server** Deployment exposes a combined gRPC+HTTP gateway on port 2746, serving both programmatic clients and the optional web UI.

Authentication on the API server is enforced by a `Gatekeeper` that acts as both unary and stream gRPC interceptors. Three modes are supported: **Client** mode delegates the caller's bearer or basic token to the Kubernetes API for user-impersonated operations; **Server** mode uses the argo-server's own service account; **SSO** mode validates OIDC tokens and optionally maps them to namespace-scoped service accounts via annotation-based RBAC rules. An invalid or missing token results in a gRPC `Unauthenticated` error. The workflow-controller's `/healthz` endpoint is explicitly unauthenticated. [source: server/auth/gatekeeper.go:90-117, server/auth/gatekeeper.go:166-218, server/auth/mode.go:14-44]

The component interacts with the Kubernetes API to manage Pods, ConfigMaps, Secrets, PodDisruptionBudgets, and SelfSubjectAccessReviews. Within RHOAI, this component is deployed and managed by the Data Science Pipelines operator rather than being installed standalone — the Dockerfile labels explicitly identify it as "Argo Workflows used in Data Science Pipelines." [source: rhoai/Dockerfile.workflowcontroller:40, argo-workflowcontroller/Dockerfile.konflux:35]

The Konflux production builds use `GOFIPS140=v1.0.0` with `CGO_ENABLED=0` and `-tags no_openssl`, selecting Go 1.24+'s native FIPS 140-3 validated crypto module rather than linking against system OpenSSL. This produces statically linked binaries with FIPS-compliant cryptography without CGO dependencies. [source: argo-workflowcontroller/Dockerfile.konflux:25, argo-argoexec/Dockerfile.konflux:24]

### FIPS Compliance

The Konflux production builds use Go's native FIPS 140-3 crypto module (`GOFIPS140=v1.0.0`) introduced in Go 1.24+, with `CGO_ENABLED=0` and `-tags no_openssl`. This approach differs from the traditional `GOEXPERIMENT=boringcrypto` or `strictfipsruntime` path — it produces statically linked binaries that use Go's built-in FIPS-validated cryptographic primitives without linking against system OpenSSL.

## Data Flows

- **Pipeline submission flow:** The Data Science Pipelines operator submits workflow definitions as `Workflow` CRs. The workflow-controller watches these CRs via the Kubernetes API, creates step Pods with argoexec sidecars, and tracks completion via `WorkflowTaskResult` and `WorkflowTaskSet` CRs. [source: manifests/base/workflow-controller/workflow-controller-deployment.yaml:1, manifests/base/crds/minimal/argoproj.io_workflows.yaml:1]
- **API access flow:** Clients connect to the argo-server ClusterIP Service on port 2746. The gRPC Gatekeeper interceptor authenticates requests using bearer tokens (Client mode), the server's own SA (Server mode), or OIDC tokens (SSO mode) before dispatching to one of 9 gRPC services or the HTTP/gRPC-gateway endpoints. Artifact retrieval endpoints (`/artifacts/`, `/artifact-files/`) serve workflow outputs. [source: manifests/base/argo-server/argo-server-service.yaml:1, server/auth/gatekeeper.go:90-117, server/apiserver/argoserver.go:381-397]
- **Kubernetes resource management:** The workflow-controller creates and manages Pods for workflow steps, creates ConfigMaps for memoization caching, reads Secrets for SSO configuration, creates PodDisruptionBudgets for running workflow pods, and performs SelfSubjectAccessReview checks for authorization verification. [source: workflow/controller/agent.go:255, workflow/controller/cache/configmap_cache.go:164, server/auth/sso/sso.go:142, workflow/controller/operator.go:3928, util/auth/auth.go:16]
- **Observability:** The argo-server exposes a `/metrics` endpoint for Prometheus scraping and optional `/debug/pprof/` endpoints for profiling. The workflow-controller exposes a `/healthz` health check on port 6060. [source: server/apiserver/argoserver.go:397, util/pprof/pprof.go:16-20, cmd/workflow-controller/main.go:181]
