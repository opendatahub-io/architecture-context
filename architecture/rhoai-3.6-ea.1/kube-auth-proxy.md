## Purpose

**Short**: kube-auth-proxy is a FIPS-compliant authenticating reverse proxy that gates access to upstream services via OAuth2/OIDC, Kubernetes TokenReview, and basic authentication, deployed as a sidecar or standalone workload in RHOAI. [source: main.go:57-81, oauthproxy.go:145-288, Dockerfile.konflux:32-54]

**Detailed**: kube-auth-proxy is a Red Hat downstream fork of oauth2-proxy, adapted for OpenShift and RHOAI environments. It acts as a reverse proxy that intercepts incoming HTTP requests and enforces authentication before forwarding traffic to upstream services. The proxy supports multiple authentication methods: OAuth2/OIDC via configurable identity providers (including OpenShift OAuth), Kubernetes ServiceAccount token validation via the TokenReview API, JWT bearer token verification, and htpasswd-based basic authentication. Session state can be stored in cookies or in a Redis/Valkey backend with TLS support. The Konflux build produces a FIPS-compliant binary using `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` on a UBI9 base image. The proxy exposes a configurable set of authentication endpoints (sign-in, callback, sign-out, auth-only) under a configurable prefix, a health check endpoint at `/ping`, and a catch-all route that forwards authenticated requests to the configured upstream. [source: main.go:17-89, oauthproxy.go:47-65, 145-288, 342-380, Dockerfile.konflux:32-54, 59, pkg/http/server.go:142-183]

## Architectural Analysis

kube-auth-proxy implements a layered middleware architecture built on gorilla/mux and justinas/alice middleware chains. Every incoming request passes through a pre-authentication chain that handles health checks (`/ping`, `/ready`), request logging, metrics collection, and optional HTTPS redirection before reaching any authentication logic. The authentication session chain is composed dynamically at startup based on configuration: Kubernetes TokenReview validation runs first (when enabled), followed by JWT bearer token verification and OAuth2/OIDC session loading. This ordering ensures that service account tokens used for programmatic API access are validated before the interactive browser-based OAuth2 flow is attempted. [source: oauthproxy.go:342-380, 382-423, 425-438]

The proxy is designed for sidecar deployment in front of RHOAI dashboard components, model serving endpoints, and other platform services that require authentication gating. Its OpenShift provider handles `sha256~` prefixed OAuthAccessTokens natively, translating them into validated sessions via the OpenShift OAuth API. The configurable allow-list and API route patterns let operators selectively bypass authentication for specific paths or methods, supporting patterns like unauthenticated health probes behind an authenticated proxy. [source: oauthproxy.go:47-65, 78-87, 219-227, 266]

TLS termination is handled directly by the proxy when configured with certificate material, supporting TLS 1.2 and 1.3 with configurable cipher suites. The Redis session store integration supports TLS with custom CA certificates and connection authentication, enabling encrypted session persistence in multi-replica deployments. The FIPS-compliant build uses Go's `strictfipsruntime` experiment with dynamic linking against OpenSSL, ensuring that all cryptographic operations route through a FIPS-validated module at runtime. [source: pkg/http/server.go:142-183, pkg/sessions/redis/redis_store.go:160-207, Dockerfile.konflux:51-54]

## Data Flows

- **Inbound request flow:** Client requests arrive at port 4180 (HTTP) or a configurable HTTPS port. The pre-authentication middleware chain processes health checks, logging, and metrics before any authentication decision. Requests to `/ping` are answered directly by the health check middleware and never reach the authentication layer. Requests to the proxy prefix endpoints (`/sign_in`, `/start`, `/callback`) handle the OAuth2 authentication flow without requiring an existing session. [source: oauthproxy.go:342-380, 382-423]
- **Authentication decision:** Requests to the catch-all proxy path (`/*`) pass through the session chain: Kubernetes TokenReview validation (when enabled) checks for `Bearer` tokens against the kube-apiserver, JWT bearer token verification validates OIDC tokens, and OAuth2 session cookies are loaded from the cookie or Redis session store. If no valid session is found, the request is redirected to the sign-in page or denied with a 401/403. [source: oauthproxy.go:425-438, main.go:59-81, pkg/authentication/k8s/tokenreview.go:138-208]
- **Upstream forwarding:** Authenticated requests are forwarded to the configured upstream service(s) with request headers enriched by the headers chain (e.g., `X-Forwarded-User`, `X-Forwarded-Email`). The upstream proxy handles both HTTP and WebSocket connections. [source: oauthproxy.go:182-185, 363]
- **Session persistence:** When Redis is configured, session state is stored in a Redis/Valkey instance with optional TLS and custom CA certificates. The Redis client supports connection URL-based configuration with username/password authentication. [source: pkg/sessions/redis/redis_store.go:160-178]
- **Kubernetes API egress:** The proxy creates TokenReview resources via the kube-apiserver to validate Kubernetes ServiceAccount tokens. This uses in-cluster credentials with automatic TLS from the mounted CA certificate, or an external kubeconfig. [source: pkg/authentication/k8s/tokenreview.go:84-130, 219-237]
