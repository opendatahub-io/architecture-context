## Purpose

**Short**: Model Registry provides a central repository for storing and managing ML model metadata, versions, and artifacts, with an HTTP REST API proxied through Istio and a controller-runtime operator that synchronizes KServe InferenceService state. [source: Dockerfile.konflux:43-44, cmd/controller/main.go:138-156, pkg/inferenceservice-controller/controller.go:248-253]

**Detailed**: Model Registry is a multi-component system that serves as the metadata backbone for ML model lifecycle management within RHOAI. The core `model-registry` binary operates as an HTTP proxy backed by a relational database (PostgreSQL or MySQL via GORM), exposing a REST API for registering, versioning, and querying model artifacts. A separate controller-runtime operator (`controller`) watches KServe InferenceService resources and synchronizes their serving URLs back into the registry via the Model Registry OpenAPI client. The BFF (Backend-for-Frontend) component serves the Model Registry UI, providing authenticated API routes at `/api/v1/*` with configurable authentication methods (`internal` ServiceAccount tokens or `user_token` Bearer tokens). An async-upload Python job handles background model artifact uploads to S3-compatible storage. Ingress is managed through Istio VirtualServices and AuthorizationPolicies that enforce namespace-scoped and principal-based access control. [source: main.go:8, clients/ui/bff/cmd/main.go:56-58, 82-87, cmd/controller/main.go:138-156, pkg/inferenceservice-controller/controller.go:248-253, 268-293]

## Architectural Analysis

Model Registry follows a multi-process architecture with three principal runtime components sharing a common Go module: the hub proxy, the controller operator, and the BFF gateway.

The **hub proxy** (`model-registry` binary) fronts a relational database (PostgreSQL or MySQL, selected at deployment) and exposes an HTTP REST API for model metadata CRUD operations. It uses GORM for database abstraction and supports schema migrations via `golang-migrate`. The proxy is built with FIPS-compliant settings (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) and uses `crypto/tls` with a minimum of TLS 1.2 and configurable cipher suites that reject insecure algorithms. [source: Dockerfile.konflux:23, internal/platform/tls/config.go:64-68, 100-114, 121-125]

The **controller** is a controller-runtime operator that conditionally watches KServe InferenceService resources when the `INFERENCE_SERVICE_CONTROLLER` environment variable is set to `managed`. It reconciles InferenceService serving URLs back into the Model Registry by discovering the registry service via label selector (`component: model-registry`) and connecting through an OpenAPI-generated HTTP client. Leader election uses the `a7d60e25.kubeflow.org` lease identity. Metrics are served on port 8443 with TLS and authn/authz filtering via controller-runtime's `WithAuthenticationAndAuthorization` filter. [source: cmd/controller/main.go:99-104, 114-132, 138-156, pkg/inferenceservice-controller/controller.go:248-253, 306-310]

The **BFF** serves the Model Registry UI frontend and proxies authenticated API requests. It supports three deployment modes — kubeflow, federated, and standalone — and validates authentication via either internal ServiceAccount tokens or user-provided Bearer tokens, configurable through the `--auth-method` flag. The BFF performs SubjectAccessReview and SelfSubjectAccessReview calls for authorization decisions and manages ConfigMaps and Secrets for UI configuration state. Outbound TLS supports custom CA bundles via the `--bundle-paths` flag. [source: clients/ui/bff/cmd/main.go:47-48, 56-58, 61, 82-87]

Ingress is layered: three Istio VirtualServices expose the model-registry API, the model catalog, and the UI, while Istio AuthorizationPolicies enforce namespace-scoped access for the API server and principal-based access for the UI. The controller metrics endpoint uses a separate RBAC-protected surface with controller-runtime's self-signed TLS certificates. [source: manifests/kustomize/options/istio/istio-authorization-policy.yaml:1, manifests/kustomize/options/ui/overlays/istio/authorization-policy-ui.yaml:1]

No gRPC services are present in the current codebase; the component communicates exclusively over HTTP REST APIs. [source: Grep scan for grpc.Server, RegisterServer, and .proto files returned no results]

## Data Flows

- **Model metadata ingestion:** External clients or the UI submit model metadata through the Istio VirtualService to the model-registry HTTP proxy, which persists it to the backing database (PostgreSQL or MySQL). The proxy path `/api/model_registry/*` is protected by an Istio AuthorizationPolicy requiring Kubernetes JWT and source namespace/principal validation. [source: manifests/kustomize/options/istio/virtual-service.yaml:1, manifests/kustomize/options/istio/istio-authorization-policy.yaml:1, Dockerfile.konflux:41]
- **InferenceService reconciliation:** When the controller operator is enabled (`INFERENCE_SERVICE_CONTROLLER=managed`), it watches KServe InferenceService resources across labeled namespaces. On reconciliation, it discovers the model-registry service by label (`component: model-registry`), constructs an OpenAPI HTTP client to the registry, and synchronizes InferenceService serving URLs back into model metadata. [source: cmd/controller/main.go:138-156, pkg/inferenceservice-controller/controller.go:248-253, 268-293, 306-310]
- **UI access flow:** Users access the Model Registry UI through the `/model-registry/*` Istio VirtualService, which proxies to the BFF. The BFF authenticates requests using Bearer tokens or internal ServiceAccount tokens (configurable via `--auth-method`), then performs SubjectAccessReview checks against the Kubernetes API before serving data. The BFF manages ConfigMaps and Secrets for UI state. [source: clients/ui/bff/cmd/main.go:56-58, 82-87, manifests/kustomize/options/ui/overlays/istio/virtual-service.yaml:1, manifests/kustomize/options/ui/overlays/istio/authorization-policy-ui.yaml:1]
- **Async artifact upload:** The async-upload Python job handles background uploads of model artifacts to S3-compatible storage using boto3. It uses PyJWT and PyOpenSSL for authentication and TLS, and is deployed as a Kubernetes batch Job. [source: jobs/async-upload/Dockerfile.konflux:61, jobs/async-upload/requirements-aipcc.txt:222, 225]
- **Controller metrics:** The controller exposes a TLS-secured metrics endpoint on port 8443, protected by controller-runtime's TokenReview + SubjectAccessReview filter. The backing RBAC roles (`controller-metrics-auth-role`, `controller-metrics-reader`) scope access to authorized service accounts.
