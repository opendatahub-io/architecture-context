## Purpose

**Short**: Reverse-proxy sidecar for llm-d prefill/decode disaggregation that intercepts OpenAI-compatible inference requests, routes prefill operations to remote prefiller pods, and forwards decode requests to a co-located vLLM instance. [source: cmd/llm-d-routing-sidecar/main.go:30-84, internal/proxy/proxy.go:96-110]

**Detailed**: llm-d-routing-sidecar is a Go-based HTTP reverse proxy deployed as a sidecar container alongside a vLLM inference engine. It implements the prefill/decode (P/D) disaggregation pattern for the llm-d distributed inference stack. Incoming inference requests arrive at the sidecar on a configurable port (default 8000) and are inspected for P/D routing headers (`x-prefiller-url`, `x-prefiller-host-port`). When a prefill target is specified, the sidecar proxies the request to the remote prefiller pod; otherwise, it forwards the request to the co-located vLLM decoder at `localhost:<vllm-port>` (default 8001). The sidecar supports three P/D connector protocols—nixlv2 (default), the deprecated nixl v1, and lmcache—and offers optional TLS for both its inbound listener (self-signed or certificate-based) and its outbound connections to prefillers and the decoder. An optional SSRF protection mode watches Gateway API InferencePool resources (`inference.networking.x-k8s.io/v1alpha2`) via the Kubernetes API to maintain a dynamic allowlist of valid prefill targets. [source: cmd/llm-d-routing-sidecar/main.go:30-109, internal/proxy/proxy.go:37-146, internal/proxy/allowlist.go:40-44]

## Architectural Analysis

llm-d-routing-sidecar implements the sidecar proxy pattern for prefill/decode (P/D) disaggregated inference in the llm-d stack. Architecturally, it sits as a transparent reverse proxy between the inference gateway (or any OpenAI-compatible client) and a co-located vLLM decoder instance. The key design decision is to separate routing concerns from the inference engine itself: vLLM handles model execution while the sidecar handles P/D protocol negotiation and inter-pod request forwarding. [source: cmd/llm-d-routing-sidecar/main.go:30-109, internal/proxy/proxy.go:96-146]

The sidecar supports three connector protocols—nixlv2 (current default), the deprecated nixl v1, and lmcache—selected via a CLI flag at startup. Protocol selection determines how prefill/decode coordination headers are processed, but all three share the same reverse-proxy forwarding path. The catch-all `/` route on the mux forwards all traffic to the local vLLM decoder by default; the connector-specific handler intercepts requests containing P/D routing headers and redirects them to the appropriate remote prefiller. Prefiller proxy handlers are cached in an LRU cache (capacity 16) to avoid repeated URL parsing for recurring targets. [source: internal/proxy/proxy.go:107-114, internal/proxy/proxy.go:130-146, internal/proxy/proxy.go:276, internal/proxy/proxy.go:281-310]

The optional SSRF protection mode is a notable security architecture feature. When enabled, the AllowlistValidator watches Gateway API `InferencePool` custom resources (`inference.networking.x-k8s.io/v1alpha2`) and their backing Pods via Kubernetes informers. Only pods belonging to a specified InferencePool are added to the allowlist, preventing the sidecar from being abused to proxy requests to arbitrary cluster-internal endpoints. This protection is disabled by default and requires explicit opt-in with a namespace and pool name. [source: internal/proxy/allowlist.go:40-44, internal/proxy/allowlist.go:67-100, cmd/llm-d-routing-sidecar/main.go:43-77]

The proxy endpoint does not enforce caller authentication. TLS is the only inbound security control: when `--secure-proxy=true` (the default), the listener uses TLS 1.2+ with a curated cipher suite list. Certificate material can be provided via `--cert-path` or falls back to a runtime-generated self-signed certificate. Outbound connections to prefillers and the decoder have independent TLS settings, including opt-in `InsecureSkipVerify` flags. [source: internal/proxy/proxy.go:148-202, internal/proxy/proxy.go:297-310, internal/proxy/tls.go:33-72]

The upstream Dockerfile builds with `CGO_ENABLED=0`, producing a statically linked binary on a `ubi9/ubi-micro` base. This configuration uses pure-Go crypto rather than OpenSSL-backed FIPS-validated cryptography, which is relevant for downstream FIPS compliance requirements. [source: Dockerfile:24, Dockerfile:26]

## Data Flows

- **Inbound request path:** Inference requests enter through the OpenShift Route (`${PROJECT_NAME}-route`) over HTTPS, reach the Kubernetes Service (`${PROJECT_NAME}-service`) on port 8080/TCP, and arrive at the sidecar's listener on port 8000 (configurable). When `--secure-proxy=true` (default), the listener terminates TLS 1.2+ using either provided certificates or a self-signed certificate. No caller authentication is enforced at this layer. [source: deploy/common/patch-service.yaml:1, deploy/openshift/patch-route.yaml:1, internal/proxy/proxy.go:148-202, cmd/llm-d-routing-sidecar/main.go:31]
- **Decode forwarding (default path):** Requests without P/D routing headers (`x-prefiller-url`, `x-prefiller-host-port`) are forwarded unchanged via the catch-all `/` reverse proxy to the co-located vLLM decoder at `localhost:<vllm-port>` (default 8001). TLS to the decoder is optional via `--decoder-use-tls`. [source: internal/proxy/proxy.go:264-276, cmd/llm-d-routing-sidecar/main.go:32-35]
- **Prefill routing (P/D path):** When the connector-specific handler detects prefill routing headers, it extracts the target prefiller host:port, validates it against the SSRF allowlist (if enabled), and proxies the request to the remote prefiller pod. Prefiller proxy handlers are cached in an LRU cache (capacity 16). TLS to prefillers is configurable via `--prefiller-use-tls`. [source: internal/proxy/proxy.go:281-310, internal/proxy/proxy.go:107, cmd/llm-d-routing-sidecar/main.go:33-36]
- **SSRF protection control plane:** When `--enable-ssrf-protection=true`, the AllowlistValidator uses a Kubernetes dynamic client (kubeconfig-based authentication) to watch InferencePool resources (`inference.networking.x-k8s.io/v1alpha2`) and their backing Pods. The set of allowed target host:port pairs is maintained via informer callbacks and checked before each prefill proxy operation. [source: internal/proxy/allowlist.go:40-44, internal/proxy/allowlist.go:67-114, cmd/llm-d-routing-sidecar/main.go:43-77]
