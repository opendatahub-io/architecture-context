**Detailed**: kserve-autogluon-server is a downstream fork of the KServe project that packages the KServe controller-manager operator, the KServe Python SDK, and a catalog of serving runtimes for deployment in RHOAI. Its primary Konflux-built artifact is the AutoGluon model server container, which runs `python -m autogluonserver` on an AIPCC CPU base image and serves AutoGluon TabularPredictor and TimeSeriesPredictor models via the KServe model server framework. The repository also contains the Go-based KServe controller-manager that reconciles InferenceService, InferenceGraph, LLMInferenceService, LocalModelCache, and TrainedModel custom resources, managing their lifecycle through Deployments, Services, HTTPRoutes, and admission webhooks. The operator ships 14 ClusterServingRuntime definitions covering model formats including AutoGluon, HuggingFace, vLLM, TensorFlow, PyTorch/TorchServe, Triton, scikit-learn, LightGBM, XGBoost, PaddlePaddle, PMML, and MLServer. A kube-rbac-proxy sidecar enforces authentication on the controller-manager metrics endpoint. ## Architectural Analysis

The repository is a multi-role monorepo combining a Go operator, a Python SDK, multiple Python model servers, and Kubernetes manifest sets. The Go controller-manager (`cmd/manager`) is the primary operator binary, hosting six reconcilers (InferenceService, InferenceGraph, TrainedModel, and three LocalModel variants) plus admission webhooks for validation and defaulting of all KServe CRDs. A separate LLMInferenceService controller (`cmd/llmisvc`) manages the newer LLM serving abstraction through Gateway API HTTPRoutes, InferencePools, LeaderWorkerSets, and KEDA ScaledObjects, reflecting the emerging GenAI workload patterns. The `cmd/localmodel` and `cmd/localmodelnode` binaries handle pre-caching models to node-local storage via PersistentVolumes and Jobs.

The Python side ships the `kserve` SDK (FastAPI/uvicorn-based model server framework with V2 Inference Protocol support over both REST and gRPC) plus individual model server packages. The autogluon-specific container (`Dockerfile.konflux.autogluon`) builds on an AIPCC CPU base image (`registry.redhat.io/rhai/base-image-cpu-rhel9`), installs dependencies from the RHOAI PyPI index, and delegates to `kserve.ModelServer` for HTTP serving. The autogluon server itself contains no authentication middleware; all model server endpoints are unauthenticated at the application layer, with external enforcement expected from platform ingress or service mesh. The `pyjwt` dependency is present in the KServe SDK but is not wired into the autogluon server's request path.

The operator's metrics endpoint is proxied through kube-rbac-proxy on port 8443, which terminates TLS and enforces Kubernetes token authentication before forwarding to the manager's HTTP listener on port 8080. Prometheus scrapes metrics through this authenticated HTTPS endpoint. All webhook endpoints serve over TLS with certificates managed via the `kserve-webhook-server-cert` secret. The controller communicates with the Kubernetes API using in-cluster ServiceAccount tokens and maintains RBAC through five distinct ClusterRoles scoped to the manager, LLM ISVC, local model, local model node, and proxy workloads respectively.

The serving runtime catalog ships 14 ClusterServingRuntime manifests that define container images and model format auto-selection for the full range of supported inference backends. These are packaged within the `config/runtimes/` directory and deployed as cluster-scoped resources. The conditional Gateway API integration in the LLMInferenceService controller discovers Gateway resources at startup and only activates HTTPRoute management when the Gateway API CRDs are installed, reflecting a pluggable networking architecture that supports both traditional Kubernetes Ingress/Istio VirtualService and the newer Gateway API patterns. ## Data Flows

- **Model inference request flow:** Clients submit inference requests to model server pods (e.g., the autogluon server) via the V2 Inference Protocol over REST or gRPC. The KServe controller-manager creates the serving pod Deployments, Services, and ingress resources (Kubernetes Ingress, Istio VirtualService, or Gateway API HTTPRoute depending on configuration). The model server loads the model from storage (local path or remote via kserve-storage from S3, GCS, Azure Blob, or HDFS) and serves predictions through FastAPI/uvicorn endpoints. The inference router (`cmd/router`) handles traffic splitting and canary routing for A/B testing scenarios. [source: python/autogluonserver/autogluonserver/__main__.py:36-49, config/runtimes/kserve-autogluonserver.yaml:1]
- **Controller reconciliation flow:** The controller-manager watches KServe CRDs (InferenceService, InferenceGraph, ServingRuntime, TrainedModel) and reconciles the associated Kubernetes resources. InferenceService reconciliation creates or updates Deployments, Services, and networking resources. The LLMInferenceService controller additionally manages Gateway API resources, InferencePools, LeaderWorkerSets for multi-node inference, and KEDA ScaledObjects for autoscaling. All controller-to-API-server communication uses in-cluster ServiceAccount tokens over TLS. [source: cmd/llmisvc/main.go:230, 319, 323, config/rbac/role.yaml:2]
- **Metrics and monitoring:** The controller-manager exposes metrics through kube-rbac-proxy on port 8443 with TLS termination and Kubernetes token authentication. Prometheus scrapes this endpoint via the `prometheus.io/scrape: "true"` annotation on the metrics Service. [source: config/rbac/auth_proxy_service.yaml:1-21]
- **Admission control flow:** Webhook requests arrive from the Kubernetes API server over TLS on port 443 at the webhook service. The controller-manager validates and defaults InferenceService, InferenceGraph, ServingRuntime, LLMInferenceService, and LocalModelCache resources. The pod mutator webhook injects sidecar containers and configuration into inference pods at creation time. All webhook endpoints use `Fail` failure policy, making the controller a hard dependency for CRD mutations. [source: config/webhook/service.yaml:1, config/default/isvc_validatingwebhook_cainjection_patch.yaml:1]
