## Purpose

**Short**: Intel Gaudi (HPU) accelerator plugin for vLLM, providing hardware-optimized inference via the vLLM OpenAI-compatible API server. [source: vllm_gaudi/__init__.py:6-8, Dockerfile.konflux.gaudi:244]

**Detailed**: vllm-gaudi is an out-of-tree (OOT) platform plugin for the vLLM inference engine, enabling high-performance large language model serving on Intel Gaudi (Habana) accelerators. The `vllm_gaudi` Python package registers `HpuPlatform` as a vLLM platform backend, providing HPU-optimized implementations of attention mechanisms, fused MoE operations, quantization kernels (FP8, GPTQ, AWQ, compressed tensors), LoRA adapters, rotary embeddings, and distributed communication via HCCL. The container image packages both the upstream vLLM OpenAI-compatible API server (`vllm.entrypoints.openai.api_server`) and the Gaudi plugin on top of the Habana SynapseAI runtime stack, Intel Gaudi PyTorch modules, and a UBI 9 base. At runtime, it exposes the standard vLLM OpenAI-compatible HTTP API for completions, chat, embeddings, and model management. [source: vllm_gaudi/__init__.py:1-39, vllm_gaudi/platform.py:32-39, Dockerfile.konflux.gaudi:244, Dockerfile.konflux.gaudi:194-217]

## Architectural Analysis

vllm-gaudi follows the vLLM out-of-tree platform plugin architecture. The `vllm_gaudi` package implements a `register()` entry point that returns `vllm_gaudi.platform.HpuPlatform`, which extends `vllm.platforms.Platform` with `PlatformEnum.OOT` designation. This plugin registration model allows the upstream vLLM server to delegate device-specific operations — attention backends, kernel dispatch, quantization, and distributed communication — to the Gaudi-optimized implementations without modifying the vLLM core. [source: vllm_gaudi/__init__.py:5-8, vllm_gaudi/platform.py:32-34]

The build pipeline constructs a multi-stage container image on UBI 9 with the Habana SynapseAI runtime (version 1.23.0), Intel Gaudi PyTorch modules, upstream vLLM (pinned at `v0.16.0`), and the `vllm_gaudi` plugin itself. The image explicitly removes the OpenSSL FIPS provider (`rpm -e --nodeps openssl-fips-provider-so`), making it incompatible with FIPS-validated deployments. The container runs as a non-root user (UID 2000) for OpenShift compatibility. [source: Dockerfile.konflux.gaudi:7-8, 20-21, 26, 59-63, 234-238, 244]

The plugin provides extensive HPU-optimized operator coverage through `register_ops()`: attention backends (unified and MLA variants), fused MoE routing, FP8/GPTQ/AWQ quantization kernels, LoRA adapters, rotary embeddings, KV cache operations, and NIXL-based KV transfer connectors for disaggregated inference. Model-specific optimizations exist for architectures including DeepSeek V2, Qwen3 MoE, Gemma3, and multimodal models. [source: vllm_gaudi/__init__.py:16-38, vllm_gaudi/platform.py:39]

This repository does not define Kubernetes manifests, services, or deployment resources. The container image is deployed as a KServe ServingRuntime by the RHOAI platform, which manages service exposure, routing, and scaling. HTTP endpoints and authentication are provided by the upstream vLLM server and platform-level infrastructure respectively, not by this plugin repository. [source: Dockerfile.konflux.gaudi:244]

## Data Flows

The vllm-gaudi container serves as an OpenAI-compatible inference endpoint. Client requests arrive via HTTP to the vLLM API server, which dispatches model inference to Intel Gaudi HPU accelerators through the `vllm_gaudi` plugin's optimized backends. For distributed inference, the plugin uses Ray for worker orchestration and HCCL (Habana Collective Communications Library) for inter-device communication. KV cache transfer between disaggregated prefill and decode stages is handled via NIXL connectors when enabled. Model weights are loaded from a configured model path (typically a PVC or S3-compatible store mounted by the platform). [source: vllm_gaudi/__init__.py:21, vllm_gaudi/platform.py:37-38, Dockerfile.konflux.gaudi:244, requirements.txt:2]
