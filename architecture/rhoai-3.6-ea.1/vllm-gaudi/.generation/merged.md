## Purpose

**Short**: Intel Gaudi (HPU) plugin for vLLM that enables high-performance LLM inference on Habana Gaudi accelerators, packaged as a container image running the vLLM OpenAI-compatible API server. [source: pyproject.toml:13, Dockerfile.konflux.gaudi:244]

**Detailed**: vllm-gaudi is a Python plugin package (`vllm_gaudi`) that extends vLLM with Intel Gaudi (HPU) device support for large language model inference. The container image is built on UBI 9 with Intel Habana SynapseAI drivers, PyTorch for Gaudi, and the upstream vLLM inference engine. The Konflux production entrypoint runs `vllm.entrypoints.openai.api_server`, providing an OpenAI-compatible HTTP API for model inference. The plugin itself implements HPU-specific worker processes, model runners, memory management, speculative decoding, and scheduling optimizations that integrate with vLLM's device abstraction layer. The repository produces multiple Dockerfile variants for different build contexts (Konflux, CI, upstream development) but the Konflux variant (`Dockerfile.konflux.gaudi`) is the production artifact for RHOAI. [source: pyproject.toml:13, Dockerfile.konflux.gaudi:244, Dockerfile.konflux.gaudi:194-217, vllm_gaudi/v1/worker/hpu_dp_utils.py:1]

## Architectural Analysis

vllm-gaudi follows a plugin architecture pattern where the `vllm_gaudi` Python package registers as an HPU device backend for the upstream vLLM inference engine. The build process clones and installs both `vllm-project/vllm` (the core inference engine with OpenAI-compatible API server) and this plugin package, which provides HPU-optimized implementations of workers, model runners, schedulers, and speculative decoding modules. [source: Dockerfile.konflux.gaudi:194-217, pyproject.toml:13]

The container image follows a multi-stage build pattern: a base stage installs Habana SynapseAI drivers and system libraries from Intel's artifact repository, a second stage adds PyTorch for Gaudi, and the final stage installs vLLM and the vllm-gaudi plugin. The image explicitly removes the OpenSSL FIPS provider (`openssl-fips-provider-so`), indicating FIPS mode is not supported for this component. [source: Dockerfile.konflux.gaudi:59-64, Dockerfile.konflux.gaudi:134-167, Dockerfile.konflux.gaudi:170-217]

This repository does not define Kubernetes manifests, services, or RBAC resources. It is a pure container image that is consumed by the RHOAI platform via KServe ServingRuntime definitions managed in other components. HTTP endpoints, authentication, and service exposure are inherited from the upstream vLLM API server and the platform's serving infrastructure rather than being configured in this repository. ## Data Flows

- **Inference request flow:** Clients send OpenAI-compatible HTTP requests to the vLLM API server (port 8000 by default, inherited from upstream vLLM). The API server delegates model execution to HPU workers implemented by the `vllm_gaudi` plugin, which schedule and execute inference on Intel Gaudi accelerators via the Habana SynapseAI runtime. Model weights are loaded from a storage path provided at container startup (typically via KServe model serving configuration). [source: Dockerfile.konflux.gaudi:244, vllm_gaudi/v1/worker/hpu_dp_utils.py:1]

- **Build-time dependency flow:** The Dockerfile clones upstream `vllm-project/vllm` at a pinned commit (`v0.16.0`), installs it as the inference engine, then installs the `vllm_gaudi` plugin on top. SynapseAI drivers and PyTorch for Gaudi are fetched from Intel's Habana artifact repositories during image build. [source: Dockerfile.konflux.gaudi:194-217, Dockerfile.konflux.gaudi:94-127]
