## Purpose

**Short**: Python client SDK that provides a high-level interface for submitting and managing distributed compute workloads on Kubernetes via Ray, KubeRay, and Kueue. [source: pyproject.toml:2, src/codeflare_sdk/ray/client/ray_jobs.py:20, src/codeflare_sdk/common/kubernetes_cluster/auth.py:30]

**Detailed**: codeflare-sdk is a Python client library (v0.38.2) that enables data scientists and ML engineers to define, submit, and monitor distributed computing jobs on OpenShift and Kubernetes clusters. The SDK wraps the Ray Job Submission Client for workload dispatch, uses a vendored KubeRay Python client to manage RayCluster and RayJob custom resources, and integrates with Kueue for queue-aware batch scheduling. Authentication to the Kubernetes API is handled through kube-authkit with support for kubeconfig, in-cluster, and Bearer token strategies. The SDK also generates TLS certificates for securing Ray cluster communication using the `cryptography` library with RSA-3072 keys. The repository includes test infrastructure (minio Deployment, test Dockerfiles, and RBAC manifests) that is not part of the shipped SDK package. [source: pyproject.toml:2, 36-45, src/codeflare_sdk/common/kubernetes_cluster/auth.py:30, src/codeflare_sdk/ray/client/ray_jobs.py:20-67, src/codeflare_sdk/common/utils/generate_cert.py:21-58, src/codeflare_sdk/vendored/python_client/kuberay_cluster_api.py:9-46]

## Architectural Analysis

The codeflare-sdk is architected as a Python client library rather than a deployed service. Its primary function is to abstract the complexity of submitting distributed workloads on Kubernetes by composing three interaction layers: Kubernetes API access (via the `kubernetes` client and `kube-authkit` for authentication), Ray cluster management (via a vendored KubeRay Python client for CRD operations and the Ray Job Submission Client for workload dispatch), and Kueue integration (via CustomObjects API for queue-aware batch scheduling).

Authentication follows a layered strategy pattern. The SDK's `auth.py` module delegates to `kube-authkit` for auto-detection of credentials (kubeconfig files, in-cluster service account tokens), while preserving deprecated legacy classes (`TokenAuthentication`, `KubeConfigFileAuthentication`) for backward compatibility. A `set_api_client()` function allows callers to inject a pre-configured Kubernetes API client, enabling integration with external authentication workflows. TLS certificate verification is enforced by default, with optional CA certificate paths resolved through environment variables (`CF_SDK_CA_CERT_PATH`) or the OpenShift workbench trust bundle at `/etc/pki/tls/custom-certs/ca-bundle.crt`. [source: src/codeflare_sdk/common/kubernetes_cluster/auth.py:30-31, 40, 90-168, 225-268, 293-325, 346-370]

The SDK generates self-signed TLS certificates (RSA-3072, SHA-256) for securing Ray cluster head-to-worker communication. This certificate generation uses the `cryptography` library, which delegates to the platform's OpenSSL provider. FIPS compliance of the cryptographic operations is therefore inherited from the underlying OpenSSL configuration rather than being explicitly selected by the SDK. [source: src/codeflare_sdk/common/utils/generate_cert.py:21-24, 56-59]

A notable architectural characteristic is that several analyzer-detected components (minio Deployment, test Dockerfiles, RBAC manifests) are test infrastructure rather than shipped SDK artifacts. The RBAC roles (`test-user-kueue-admin`, `test-user-ray-admin`, `kueue-batch-user-role`) define the permissions that end users need when using the SDK on a cluster, but they are test fixtures with placeholder subjects, not production role bindings deployed by the SDK itself. [source: images/tests/rbac-test-user-permissions.yaml:58, 93, 127]

## Data Flows

- **Client authentication:** The SDK authenticates to the Kubernetes API server using kube-authkit's auto-detection strategy, which attempts kubeconfig, in-cluster service account tokens, and Bearer token mechanisms in priority order. Legacy `TokenAuthentication` and `KubeConfigFileAuthentication` classes remain available but are deprecated. TLS certificate verification is enforced by default with configurable CA certificate paths. [source: src/codeflare_sdk/common/kubernetes_cluster/auth.py:30-31, 225-268, 293-325]
- **Workload submission:** Users define Ray cluster configurations through the SDK's Python API, which the vendored KubeRay client translates into RayCluster and RayJob custom resources via the Kubernetes CustomObjects API. For direct job submission, the `RayJobClient` wrapper connects to the Ray Dashboard HTTP endpoint with configurable TLS verification, headers, and cookies. [source: src/codeflare_sdk/ray/client/ray_jobs.py:20-67, src/codeflare_sdk/vendored/python_client/kuberay_cluster_api.py:20-46]
- **Queue integration:** The SDK queries and manages Kueue LocalQueue and ClusterQueue resources through the Kubernetes API to enable queue-aware batch scheduling of workloads. [source: src/codeflare_sdk/common/kueue/__init__.py:1-6]
- **TLS certificate provisioning:** The SDK generates self-signed CA and server certificates (RSA-3072, SHA-256) using the `cryptography` library and stores them as Kubernetes Secrets for securing Ray cluster head-to-worker communication. [source: src/codeflare_sdk/common/utils/generate_cert.py:21-24, 56-59]
