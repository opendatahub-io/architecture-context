## Purpose

**Short**: Kubeflow Python SDK providing a high-level client interface for managing ML training workloads, hyperparameter tuning, and Spark jobs on Kubernetes via the Kubeflow Trainer, Katib, and Spark operator APIs. [source: pyproject.toml:10, kubeflow/trainer/backends/kubernetes/backend.py:27]

**Detailed**: kubeflow-sdk is the Python SDK for Kubeflow, providing the `TrainerClient` interface that orchestrates machine learning workloads on Kubernetes. The SDK wraps three Kubeflow API surfaces — Trainer (`kubeflow-trainer-api`), Katib (`kubeflow-katib-api`), and optionally Spark (`kubeflow-spark-api`) — into a unified client library. It authenticates to the Kubernetes API via the standard `kubernetes` Python client, supporting both kubeconfig and in-cluster service account authentication. The SDK includes a Red Hat AI (RHAI) module that adds transformers-specific training utilities including checkpoint injection and structured logging via `structlog`. As a client library, it does not deploy its own services or middleware; all authentication, authorization, and network security are delegated to the Kubernetes cluster and the Kubeflow control plane it connects to. [source: pyproject.toml:2-33, kubeflow/trainer/backends/kubernetes/backend.py:44-59, kubeflow/common/types.py:16-27]

## Architectural Analysis

kubeflow-sdk follows a backend-abstraction pattern where the `TrainerClient` dispatches ML workload operations to a pluggable `RuntimeBackend`. The primary backend is `KubernetesBackend`, which uses the `kubernetes` Python client to create, watch, and manage Kubeflow custom resources (TrainJobs, Katib experiments, SparkConnect jobs) via the Kubernetes CustomObjectsApi. A `LocalProcessBackend` exists for development workflows without a cluster. [source: kubeflow/trainer/backends/kubernetes/backend.py:44-59, kubeflow/trainer/api/trainer_client_test.py:23-44]

Authentication is entirely delegated to the Kubernetes client library. The `KubernetesBackend` initializes by calling `config.load_kube_config()` for external access or `config.load_incluster_config()` for pod-resident SDK usage, then constructs an `ApiClient` from the resulting configuration. No additional auth middleware, JWT validation, or token management is implemented in the SDK itself — the `pyjwt` dependency present in the lockfile is transitive and not directly imported by SDK code. [source: kubeflow/trainer/backends/kubernetes/backend.py:50-57, kubeflow/common/types.py:20-27]

The SDK's dependency architecture separates core API model packages (`kubeflow-trainer-api`, `kubeflow-katib-api`) from the SDK orchestration layer, allowing the API types to be versioned and released independently. Optional extras (`spark`, `hub`, `rhai`) add Spark operator integration, model registry access, and Red Hat AI-specific training utilities respectively. The RHAI module provides transformers-based training helpers including JIT checkpoint injection and structured logging, representing the primary downstream-specific value-add in this fork. [source: pyproject.toml:28-56]

### FIPS Compliance

kubeflow-sdk is a pure Python client library with no build-time FIPS enforcement applicable (no compiled binaries, no Konflux Dockerfile for the SDK package itself). The `cryptography` package (v46.0.5) appears in the lockfile as a transitive dependency but is not directly imported or used by the SDK source code. All TLS and cryptographic operations are delegated to the `kubernetes` Python client library, which uses the platform Python runtime's OpenSSL. FIPS compliance for SDK consumers depends on the host Python installation and its OpenSSL linkage, not on the SDK itself. No explicit FIPS configuration, cipher suite selection, or non-FIPS crypto risks were identified in SDK source code. [source: pyproject.toml:28-33, requirements.txt:416]
## Data Flows

- **SDK client to Kubernetes API:** The `TrainerClient` creates a `KubernetesBackend` that authenticates via `load_kube_config()` or `load_incluster_config()`, then issues CRUD operations on Kubeflow custom resources (TrainJob, Katib experiments, SparkConnect) through the Kubernetes CustomObjectsApi. All requests flow over the Kubernetes API server's TLS-protected endpoint using the credentials from the kubeconfig or service account token. [source: kubeflow/trainer/backends/kubernetes/backend.py:50-59, kubeflow/common/types.py:20-27]
- **Control plane verification:** On initialization, the `KubernetesBackend` reads the `kubeflow-trainer-public` ConfigMap from the `kubeflow-system` namespace to verify that a compatible Trainer control plane is available. This is a non-blocking check that does not enforce version compatibility. [source: kubeflow/trainer/backends/kubernetes/backend.py:66-79]
- **API model layer:** The SDK uses separate API packages (`kubeflow-trainer-api`, `kubeflow-katib-api`, and optionally `kubeflow-spark-api`) for custom resource model definitions. These packages provide Pydantic/dataclass models that the SDK serializes to Kubernetes API payloads. [source: pyproject.toml:28-33, kubeflow/trainer/backends/kubernetes/backend.py:26-27]
