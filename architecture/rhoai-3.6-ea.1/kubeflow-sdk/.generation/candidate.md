## Purpose

**Short**: Kubeflow Python SDK providing a unified client library for managing ML training workloads, pipeline definitions, Katib hyperparameter tuning, and Spark jobs on Kubernetes via the RHOAI platform. [source: pyproject.toml:10, kubeflow/pipelines/__init__.py:15-24, kubeflow/common/types.py:20-27]

**Detailed**: kubeflow-sdk is the primary Python SDK for the Kubeflow project, re-exported as the `kubeflow` package. It provides client-side abstractions for submitting and managing ML training jobs (via `kubeflow-trainer-api`), hyperparameter tuning experiments (via `kubeflow-katib-api`), Spark workloads (via `kubeflow-spark-api`), and ML pipelines (via `kfp`). The SDK includes RHAI (Red Hat AI) extensions under `kubeflow.trainer.rhai` that add instrumentation for Transformers-based training, including checkpoint management and progression tracking. It interacts with Kubernetes and Kubeflow control-plane components exclusively as a client, delegating authentication and authorization to the underlying `kubernetes` Python client and the platform's API servers. [source: pyproject.toml:2, 10, 28-35, 40-53, kubeflow/pipelines/__init__.py:15-24, kubeflow/pipelines/api/pipelines_client.py:17, kubeflow/common/types.py:16-27, kubeflow/trainer/rhai/instrumentation/__init__.py:15-25]

## Architectural Analysis

kubeflow-sdk is structured as a multi-module Python SDK that unifies several Kubeflow subsystem APIs under a single `kubeflow` namespace. The core package declares direct dependencies on `kubeflow-trainer-api` and `kubeflow-katib-api` for training and hyperparameter tuning, while `kubeflow-spark-api` and `kfp` (Kubeflow Pipelines) are available as optional extras (`[spark]` and `[pipelines]` respectively). [source: pyproject.toml:28-35, 44-53]

The SDK's Kubernetes interaction boundary is defined by the `kubernetes` Python client library, configured through `KubernetesBackendConfig` which accepts namespace, kubeconfig file, context, and a `client.Configuration` object for connection and authentication settings. This design delegates all Kubernetes API authentication to the standard Python client, which supports kubeconfig files, service account tokens, and OIDC providers. [source: kubeflow/common/types.py:16-27, pyproject.toml:29]

The Kubeflow Pipelines integration uses a lazy-loading pattern: `kubeflow.pipelines` re-exports `PipelinesClient` and KFP DSL modules (`compiler`, `components`, `dsl`, `kubernetes`) only when the optional `kfp` package is installed. The `PipelinesClient` itself is a thin re-export from `kfp.kubeflow_client`, meaning all pipeline API authentication and transport are handled by the upstream KFP library. [source: kubeflow/pipelines/__init__.py:72-95, kubeflow/pipelines/api/pipelines_client.py:17]

The RHAI extensions add Red Hat-specific instrumentation for Transformers-based trainers, including checkpoint management and progression tracking that are injected into training pods. These modules generate code and configuration for training pods but do not implement independent network services or authentication mechanisms. [source: kubeflow/trainer/rhai/instrumentation/__init__.py:15-25]

The SDK does not run as a server or controller in production. The `hack/Dockerfile.spark-e2e-runner` container entrypoint and the SparkConnect CRD in the `hack/crds` directory are CI/testing artifacts rather than production deployment components. Authentication is entirely platform-delegated: the SDK relies on the Kubernetes API server and Kubeflow control-plane services for enforcement. The `pyjwt` and `cryptography` packages present in the transitive dependency tree are pulled in by the `kubernetes` and `kfp` client libraries for their respective authentication flows. [source: pyproject.toml:28-35, requirements.txt:416, kubeflow/common/types.py:16-27]

## Data Flows

- **Client-to-platform interactions:** The SDK operates as a client library that issues requests to Kubernetes API servers and Kubeflow control-plane services. Users create training jobs, pipeline runs, Katib experiments, and Spark workloads by constructing API objects using the `kubeflow-trainer-api`, `kubeflow-katib-api`, `kubeflow-spark-api`, and `kfp` type packages, then submitting them through the `kubernetes` Python client or the `PipelinesClient`. [source: pyproject.toml:28-35, 44-53, kubeflow/common/types.py:16-27, kubeflow/pipelines/api/pipelines_client.py:17]
- **Kubernetes API boundary:** All cluster interactions pass through the `kubernetes` Python client configured via `KubernetesBackendConfig`, which supports kubeconfig files, context selection, and custom `client.Configuration` for authentication and TLS. The SDK does not implement its own transport or service mesh integration. [source: kubeflow/common/types.py:16-27, pyproject.toml:29]
- **RHAI instrumentation injection:** The RHAI extensions generate training instrumentation code (checkpoint management, progression tracking) that is injected into Transformers and TrainingHub training pods at job submission time. This is a code-generation data flow, not a runtime network interaction. [source: kubeflow/trainer/rhai/instrumentation/__init__.py:15-25]
- **Security context:** Authentication is delegated to the platform. The `kubernetes` client uses kubeconfig/service account tokens; the KFP `PipelinesClient` uses upstream kfp authentication. The SDK carries transitive dependencies on `pyjwt`, `cryptography`, and `requests-oauthlib` through these clients but does not configure independent authentication middleware. [source: pyproject.toml:28-35, requirements.txt:416, kubeflow/pipelines/api/pipelines_client.py:17]
