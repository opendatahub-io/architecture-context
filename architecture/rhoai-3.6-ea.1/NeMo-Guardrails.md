## Purpose

**Short**: NeMo-Guardrails is a Python-based FastAPI service that provides programmable guardrails for LLM-based conversational systems, exposing OpenAI-compatible chat completion and guardrail check APIs. [source: Dockerfile.konflux:69, nemoguardrails/server/api.py:231, pyproject.toml:2]

**Detailed**: NeMo-Guardrails is NVIDIA's open-source toolkit for adding input/output safety rails to LLM interactions, packaged as a FastAPI application served by uvicorn. The server exposes OpenAI-compatible endpoints (`/v1/chat/completions`, `/v1/checks`, `/v1/guardrail/checks`) that apply configurable guardrail policies—including jailbreak detection, fact-checking, prompt security, and content moderation—before and after LLM inference. The downstream RHOAI build uses a Konflux-managed container image based on the AIPCC CPU base image, with Python dependencies sourced from the RHAI Python Package Index. The service integrates with LLM providers (OpenAI, Azure OpenAI) via SDK clients, and supports runtime authentication forwarding where inbound `X-Authorization` headers are relayed to LLM backends. The server itself provides no built-in authentication middleware; access control is delegated to the Kubernetes infrastructure and ingress layer. ## Architectural Analysis

NeMo-Guardrails follows a modular guardrail pipeline architecture where incoming requests pass through configurable input rails, are optionally forwarded to an LLM provider, and then filtered through output rails before returning to the caller. The server is a single FastAPI application (`nemoguardrails/server/api.py`) that loads guardrail configurations from a directory of YAML/Colang files, each defining a named guardrail policy with its own set of rails, models, and action handlers. The Konflux container image (`Dockerfile.konflux`) packages the server with pre-fetched NLP models (spaCy, sentence-transformers, fastembed) to avoid runtime downloads.

The authentication architecture is notable: the server has no built-in authentication middleware at the FastAPI level. Inbound request authentication is expected to be handled by the Kubernetes infrastructure (ingress, service mesh, or proxy). For outbound LLM provider authentication, the `header_forwarding` module (`nemoguardrails/header_forwarding.py`) implements a pattern where `X-Authorization` headers from inbound requests are relayed as `Authorization` headers to LLM backends when no static API key is configured, while the inbound `Authorization` header (carrying K8s/proxy auth) is explicitly excluded from forwarding. This separation prevents accidental credential leakage between infrastructure and application auth domains. [source: nemoguardrails/server/api.py:29, 69-83, nemoguardrails/header_forwarding.py:16-25, 62-88]

The service exposes three distinct API surfaces: the main guardrails server (port 8000, OpenAI-compatible chat completions and guardrail checks), the AlignScore fact-checking server (port 5000), and the jailbreak detection server (port 1337). Each has its own Dockerfile and entry point, though the Konflux production build packages only the main guardrails server. External integrations are limited to LLM inference providers (OpenAI and Azure OpenAI via SDK clients); the service has no direct dependencies on other RHOAI platform components such as KServe or ModelMesh. ## Data Flows

- **Inbound request flow:** Clients send OpenAI-compatible requests to the FastAPI server on port 8000. The server loads the appropriate guardrail configuration, applies input rails (content filtering, jailbreak detection, prompt security), and routes valid requests to the configured LLM provider. No built-in authentication is enforced at the server level; authentication is delegated to the Kubernetes infrastructure layer. [source: nemoguardrails/server/api.py:29, 69, Dockerfile.konflux:68]
- **LLM provider interaction:** Outbound LLM calls use the OpenAI SDK with configurable authentication. When no static API key is configured, the `header_forwarding` module maps inbound `X-Authorization` headers to outbound `Authorization` headers. The inbound `Authorization` header (K8s/proxy auth) is explicitly excluded from forwarding to prevent credential leakage. [source: nemoguardrails/header_forwarding.py:62-88, nemoguardrails/embeddings/providers/azureopenai.py:49, 53-54]
- **Output processing:** LLM responses pass through output rails (fact-checking, content moderation, PII anonymization via Presidio) before being returned to the caller. The `/v1/guardrail/checks` endpoint applies role-based rail routing: user/system messages go through input rails, assistant messages through output rails, and tool messages through tool_input rails. [source: nemoguardrails/server/checks.py:479-491]
- **Security context:** 16 secret references (API keys for third-party guardrail providers such as ActiveFence, AI Defense, Prompt Security, and others) are sourced from environment variables at runtime. TLS certificate paths are configured via `REQUESTS_CA_BUNDLE` and `SSL_CERT_FILE` for outbound HTTPS connections. [source: Dockerfile.konflux:65-66, nemoguardrails/library/activefence/actions.py:74, nemoguardrails/library/ai_defense/actions.py:61]
