## Purpose

**Short**: Kubernetes operator that manages the lifecycle of distributed machine learning training jobs across six frameworks (PyTorch, TensorFlow, JAX, MPI, XGBoost, PaddlePaddle) via Kubeflow Training CRDs. [source: manifests/base/crds/kubeflow.org_pytorchjobs.yaml:2, manifests/base/crds/kubeflow.org_tfjobs.yaml:2, cmd/training-operator.v1/main.go:265]

**Detailed**: The training-operator is a controller-runtime-based Kubernetes operator that reconciles six namespaced CRDs — PyTorchJob, TFJob, JAXJob, MPIJob, XGBoostJob, and PaddleJob — each representing a distributed training workload. For each CRD, a dedicated reconciler manages the full lifecycle of worker Pods, Services, ServiceAccounts, and optional gang-scheduling PodGroups (via Volcano or scheduler-plugins). The operator exposes validating admission webhooks for all six job types, enforcing schema correctness at CREATE and UPDATE time over TLS on port 9443. A separate kubectl-delivery init container image copies kubectl into training Pods that require it (primarily MPI jobs). On OpenShift clusters, the operator reads the platform's `config.openshift.io/v1/APIServer` resource at startup to align its webhook TLS configuration with the cluster-wide TLS security profile, falling back to hardened TLS 1.2 defaults on non-OpenShift or when the resource is unavailable. The RHOAI Konflux build uses `GOEXPERIMENT=strictfipsruntime` with dynamic linking for FIPS-compliant crypto. [source: cmd/training-operator.v1/main.go:100-141, 265-287, build/images/training-operator/Dockerfile.konflux:17, manifests/base/rbac/role.yaml:1-303]

## Architectural Analysis

The training-operator follows a one-controller-per-CRD pattern built on controller-runtime v0.19.1, with each of the six reconcilers (JAXJobReconciler, MPIJobReconciler, PaddleJobReconciler, PyTorchJobReconciler, TFJobReconciler, XGBoostJobReconciler) watching its respective CRD and managing subordinate Pods, Services, and ServiceAccounts. The MPI reconciler additionally manages ConfigMaps for host-file distribution and Roles/RoleBindings for launcher-to-worker SSH access. The PyTorch reconciler uniquely supports HorizontalPodAutoscaler management for elastic training jobs. [source: manifests/base/rbac/role.yaml:1-303, cmd/training-operator.v1/main.go:265-287]

All six job types have validating admission webhooks registered via cert-controller (OPA cert-controller v0.12.0), with `failurePolicy: Fail` ensuring no invalid training jobs can be created. The webhook server listens on port 9443 with TLS certificates stored in the `training-operator-webhook-cert` Secret, while health and readiness probes are served on port 8081 without TLS. The readiness probe gates on webhook certificate availability, preventing the operator from accepting traffic before its admission surface is functional. [source: cmd/training-operator.v1/main.go:433-458, manifests/base/webhook/patch.yaml:1]

The operator integrates with optional gang schedulers — Volcano (`scheduling.volcano.sh`) and Kubernetes scheduler-plugins (`scheduling.x-k8s.io`) — to coordinate pod group scheduling for distributed jobs, selectable via the `--gang-scheduler-name` flag. NetworkPolicy management ensures per-job network isolation. On OpenShift, the operator queries the cluster's `APIServer` resource to derive TLS cipher suites and minimum version, enforcing platform-consistent cryptographic policy on the webhook server; on non-OpenShift clusters or transient API errors, it falls back to TLS 1.2 with an intermediate cipher suite list. [source: cmd/training-operator.v1/main.go:88-141, 288-289, manifests/base/rbac/role.yaml:260-303]

Prometheus metrics are exposed at `:8080/metrics` via service annotations (`prometheus.io/scrape: "true"`) with no authentication, relying on network-level access control. The operator supports namespace-scoped or cluster-wide operation, configurable via the `--namespace` flag with a filtered informer cache. [source: manifests/base/service.yaml:4-7, cmd/training-operator.v1/main.go:280, 290-291]

## Data Flows

### Flow 1: Training Job Reconciliation

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | User / Pipeline | kube-apiserver | 6443 | HTTPS | TLS 1.2+ | Bearer token / kubeconfig |
| 2 | kube-apiserver | training-operator (webhook) | 9443 | HTTPS | TLS | Kubernetes admission |
| 3 | training-operator | kube-apiserver | 6443 | HTTPS | TLS 1.2+ | ServiceAccount token |
| 4 | Prometheus | training-operator (metrics) | 8080 | HTTP | None | None |

A user or pipeline submits a training job CR (e.g., PyTorchJob) to the Kubernetes API server. The API server invokes the training-operator's validating webhook over TLS on port 9443 to validate the resource. Upon successful validation, the reconciler for that job type watches for the new CR, then creates and manages worker Pods, Services, ServiceAccounts, and optionally gang-scheduling PodGroups and NetworkPolicies through the Kubernetes API using its ServiceAccount token. Prometheus scrapes operator metrics from the `:8080/metrics` endpoint via service annotations. [source: cmd/training-operator.v1/main.go:265-294, 436-458, manifests/base/service.yaml:4-7, manifests/base/rbac/role.yaml:1-303]

### Flow 2: OpenShift TLS Profile Bootstrap

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|

At startup, the operator reads the `config.openshift.io/v1/APIServer` resource named `cluster` to retrieve the platform TLS profile. If found, the operator applies the profile's minimum TLS version and cipher suites to its webhook server. On non-OpenShift clusters or when the resource is unavailable, hardened defaults (TLS 1.2, intermediate cipher suites) are applied. [source: cmd/training-operator.v1/main.go:88-141]
