## Purpose

**Short**: odh-model-controller is the primary model-serving control plane for RHOAI, providing Kubernetes controllers and admission webhooks that manage the lifecycle of InferenceService, LLMInferenceService, InferenceGraph, and NIM Account resources, alongside a dedicated TLS-secured REST API (model-serving-api) for gateway discovery and sample retrieval. [source: cmd/main.go:86, server/main.go:27, config/crd/bases/nim.opendatahub.io_accounts.yaml:2]

**Detailed**: odh-model-controller ships as two cooperating deployments. The primary `odh-model-controller` deployment runs a controller-runtime operator that hosts nine reconcilers (InferenceService, LLMInferenceService, InferenceGraph, ServingRuntime, Gateway, Account, ConfigMap, Secret, and Pod) and eight admission webhooks covering resource mutation and validation. The secondary `model-serving-api` deployment provides a TLS-secured HTTP API that exposes gateway discovery (`/api/v1/gateways` with Bearer-token authentication and SelfSubjectAccessReview authorization) and static LLM-D sample templates. Both deployments use FIPS-compliant TLS configurations (TLS 1.2+, ECDHE+AES-GCM cipher suites, NIST curves) and are built with `GOEXPERIMENT=strictfipsruntime`. The controller integrates with platform CRDs (DataScienceCluster, DSCInitialization, HardwareProfile), networking resources (Gateway API, OpenShift Routes, Istio EnvoyFilters), security resources (Kuadrant AuthPolicy, NetworkPolicy, RBAC), and observability (prometheus-operator, OpenTelemetry Collector). NIM Account management is conditionally deployed based on the `NIM_STATE` environment variable, and an xKS mode disables standard reconcilers in favor of webhook-only operation for ConnectionsAPI and HardwareProfile. ## Architectural Analysis

odh-model-controller implements a dual-deployment architecture on RHOAI. The main `odh-model-controller` deployment hosts the controller-runtime operator that reconciles model-serving Kubernetes resources, while the separate `model-serving-api` deployment provides a REST API gateway for cluster introspection and template serving. [source: cmd/main.go:86, server/main.go:27, config/server/server.yaml:1, config/default/manager_webhook_patch.yaml:1]

The controller-runtime operator manages nine reconciliation loops with distinct responsibilities. The InferenceServiceReconciler is the most connected, owning or watching 15 resource types including Services, Routes, NetworkPolicies, ClusterRoleBindings, PodMonitors, ServiceMonitors, and ServingRuntimes. The GatewayReconciler manages Gateway API resources and owns AuthPolicies, PodMonitors, and EnvoyFilters. The LLMInferenceServiceReconciler integrates with Kuadrant for API authentication by watching AuthPolicy, Authorino, and Kuadrant resources. Controller startup is mode-sensitive: in xKS mode, only webhooks are registered for ConnectionsAPI and HardwareProfile, while all other modes include the full reconciler set. NIM Account management gates on the `NIM_STATE` environment variable, with a cleanup runner activated when set to "removed". [source: cmd/main.go:141-160, cmd/main.go:192-210]

The admission webhook surface enforces resource correctness through five mutating and three validating webhooks, all configured with FailurePolicy=Fail. These cover Pod injection, InferenceService defaults, InferenceGraph validation, LLMInferenceService connection configuration (v1alpha1 and v1alpha2), and NIM Account validation. [source: config/webhook/manifests.yaml:2-106]

The model-serving-api deployment runs independently of controller-runtime. It uses a Kubernetes client to discover Gateway resources via a label selector, exposes the results through a Bearer-token-protected REST endpoint (`/api/v1/gateways`), and delegates authorization via Kubernetes SelfSubjectAccessReview. The `/api/v1/samples/llm-d` endpoint serves static embedded YAML templates without authentication. Both deployments share TLS infrastructure through `common.NewTLSConfig`, which enforces FIPS-compliant cipher suites (ECDHE+AES-GCM) and NIST curves (P-256, P-384) at TLS 1.2 minimum, with certificate rotation supported via `CertReloader` using fsnotify-based directory watching. [source: server/server.go:16-44, server/main.go:63-98, server/middleware/auth.go:24-41, server/common/certreloader.go:97-115]

Observability spans both deployments. The controller operator exposes Prometheus metrics via controller-runtime's metrics server, defaulting to HTTP on port 8080 with `secureMetrics=false`; when enabled, the secure mode uses TokenReview and SubjectAccessReview via controller-runtime filters. The model-serving-api exposes metrics on a separate TLS-protected listener using `promhttp.Handler()` without additional authentication middleware, and optionally exports OTLP/gRPC traces to an OpenTelemetry Collector endpoint when configured. [source: cmd/main.go:95-101, cmd/main.go:229-245, server/observability/observability.go:53-104]

## Data Flows

- **Admission request flow:** Kubernetes API server sends admission requests to the webhook service (port 443 → target 9443) over TLS. The eight webhooks (five mutating, three validating) process Pod, InferenceService, InferenceGraph, LLMInferenceService, and NIM Account resources with FailurePolicy=Fail, returning admission decisions synchronously. [source: config/webhook/service.yaml:1, config/webhook/manifests.yaml:2-106]
- **Controller reconciliation flow:** Resource change events from the Kubernetes API (via controller-runtime watches) trigger reconciliation loops.
