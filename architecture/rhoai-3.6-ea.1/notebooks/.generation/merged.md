## Purpose

**Short**: Multi-variant container image build repository that produces JupyterLab notebook and code-server workbench images for RHOAI, each bundling a specific ML framework stack (PyTorch, TensorFlow, LLMCompressor) on UBI9. [source: jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:1, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:48, codeserver/ubi9-python-3.12/Dockerfile.konflux.cpu:367]

**Detailed**: The notebooks repository builds the container images that serve as RHOAI workbenches — interactive development environments for data scientists. It produces two IDE families: JupyterLab notebooks (started via `start-notebook.sh`) and code-server instances (started via `run-code-server.sh`), each available in multiple variants combining a base Python environment with accelerator-specific ML frameworks (CPU, NVIDIA CUDA, AMD ROCm). The images are built through Konflux pipelines using UBI9 base images with hermetic RPM and Python dependency management. Each image bundles a curated set of data science libraries including PyTorch, TensorFlow, scikit-learn, pandas, and platform SDKs such as codeflare-sdk and kfp. The workbench images are deployed as StatefulSets managed by odh-notebook-controller, which injects environment variables (`NOTEBOOK_ARGS`, `NB_PREFIX`) for routing and an oauth-proxy sidecar for authentication. The repository also includes Go-based build utilities (`buildinputs`, `check-payload`) used during the Konflux image build pipeline, and a comprehensive container test suite validating image correctness including idle culling API behavior. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:1-51, jupyter/minimal/ubi9-python-3.12/kustomize/base/statefulset.yaml:1-65, codeserver/ubi9-python-3.12/Dockerfile.konflux.cpu:367, tests/containers/workbenches/culling_api_test.py:32-33]

## Architectural Analysis

The notebooks repository follows a multi-variant image build pattern where a shared base layer is extended by framework-specific Dockerfiles. Each JupyterLab variant uses `start-notebook.sh` as its entrypoint, which reads platform-injected environment variables (`NOTEBOOK_PORT`, `NOTEBOOK_BASE_URL`, `NOTEBOOK_ROOT_DIR`, `NOTEBOOK_ARGS`) to configure the JupyterLab `ServerApp` at startup. [source: jupyter/minimal/ubi9-python-3.12/start-notebook.sh:16-51] The code-server variants use a parallel `run-code-server.sh` entrypoint with an nginx reverse-proxy and httpd CGI layer that exposes a `/api/kernels/` culling shim, enabling the platform's idle-detection mechanism to query workbench activity. [source: tests/containers/workbenches/culling_api_test.py:87-135]

Authentication is architecturally delegated: the kustomize StatefulSet template explicitly disables JupyterLab's built-in token and password authentication (`--ServerApp.token=''`, `--ServerApp.password=''`), expecting the platform to provide authentication via a sidecar proxy injected by odh-notebook-controller. [source: jupyter/minimal/ubi9-python-3.12/kustomize/base/statefulset.yaml:26-29] This design means the workbench images themselves contain no authentication enforcement — a deliberate architectural choice that makes them dependent on correct platform deployment.

The Go utilities (`buildinputs` and `check-payload`) are build-pipeline tools, not runtime components of the deployed workbench. Both are statically linked (`CGO_ENABLED=0`) and built from minimal base images (`scratch` and `ubi9-minimal` respectively), serving as Konflux pipeline helpers rather than as part of the deployed workbench pod. [source: scripts/buildinputs/Dockerfile:17, scripts/check-payload/Dockerfile:18]

For FIPS compliance, the notebook images install `compat-openssl11` to provide `libcrypto.so.1.1` required by FIPS-compliance scanning tools. [source: jupyter/minimal/ubi9-python-3.12/Dockerfile.konflux.cpu:27-30] The Python `cryptography` library (v49.0.0) uses the system OpenSSL backend on UBI9. However, `pycryptodome` (v3.23.0) is also present in the dependency tree and is not a FIPS-validated cryptographic provider. The Go build utilities use `CGO_ENABLED=0` static linking, which would not pass FIPS check-payload validation, but these are build-time tools not shipped in the runtime workbench images.

## Data Flows

- **User request flow:** Platform users access workbenches through an OpenShift Route managed by odh-notebook-controller. Requests pass through an oauth-proxy sidecar for authentication, then reach the JupyterLab server on port 8888/TCP or code-server via nginx on port 8787/TCP. The `NB_PREFIX` environment variable (e.g., `/notebook/<project>/<name>`) provides path-based routing. [source: jupyter/minimal/ubi9-python-3.12/kustomize/base/statefulset.yaml:24-34, jupyter/minimal/ubi9-python-3.12/start-notebook.sh:24-27]
- **Idle culling flow:** The odh-notebook-controller polls workbench activity via the `/api/kernels/` endpoint. For JupyterLab, this is served directly by the Jupyter server. For code-server, an nginx→httpd→CGI chain serves an `access.cgi` script that queries code-server's healthz endpoint on port 8787 and translates the heartbeat timestamp into a kernel-compatible JSON response. [source: tests/containers/workbenches/culling_api_test.py:87-135, tests/containers/workbenches/culling_api_test.py:145-161]
- **Build pipeline flow:** Konflux builds the notebook images using hermetic builds with prefetched RPMs and Python packages. The `buildinputs` Go utility generates build dependency metadata, and `check-payload` validates FIPS compliance of built artifacts. [source: scripts/buildinputs/Dockerfile:1-24, scripts/check-payload/Dockerfile:1-27]
