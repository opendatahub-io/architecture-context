## Purpose

**Short**: kube-auth-proxy is a FIPS-compliant authentication reverse proxy (fork of oauth2-proxy) that protects RHOAI services by enforcing OAuth2/OIDC, Kubernetes ServiceAccount token, and cookie-based session authentication before forwarding requests to upstream backends. [source: main.go:17-83, oauthproxy.go:89-128, Dockerfile.konflux:51-52]

**Detailed**: kube-auth-proxy sits in front of RHOAI platform services as a reverse proxy, intercepting all incoming requests and enforcing authentication before forwarding to upstream backends. It implements a layered authentication middleware chain: Kubernetes ServiceAccount tokens are validated first via the TokenReview API (enabling programmatic access), followed by OAuth2/OIDC bearer token validation, optional basic auth (htpasswd), and stored cookie sessions for browser flows. When configured with the OpenShift provider, it integrates with OpenShift OAuth for user authentication and performs OAuthAccessToken cleanup on sign-out. Sessions may be stored in Redis/Valkey with TLS support for horizontal scaling. The proxy exposes OAuth2 flow endpoints (`/oauth2/sign_in`, `/oauth2/callback`, `/oauth2/start`), an ext_authz-compatible auth-only endpoint (`/oauth2/auth`), and health/readiness probes. It is built with FIPS-compliant settings (`CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`) on a UBI9 base image. [source: main.go:17-83, oauthproxy.go:342-380, oauthproxy.go:425-464, Dockerfile.konflux:51-52]

## Architectural Analysis

kube-auth-proxy implements a multi-method authentication reverse proxy pattern using gorilla/mux routing and justinas/alice middleware chaining. The authentication chain is ordered by specificity: Kubernetes ServiceAccount token validation via the TokenReview API runs first, enabling programmatic API access without browser flows; JWT/OAuth bearer token validation follows for OIDC or OpenShift OAuth tokens; basic auth (htpasswd) provides a fallback mechanism; and stored cookie sessions handle returning browser users. This ordering ensures that service-to-service authentication (K8s tokens) is resolved before provider-specific browser flows are attempted. [source: oauthproxy.go:425-464]

The proxy serves two HTTP listeners: the primary application server on a configurable bind address (default port 4180) and a separate metrics server exposing Prometheus metrics via a dedicated handler. TLS is configurable on both servers with a minimum of TLS 1.2 and maximum of TLS 1.3, with optional custom cipher suite selection. [source: oauthproxy.go:310-340, pkg/http/server.go:136-184]

When the OpenShift provider is active, sign-out triggers an asynchronous background deletion of the OAuthAccessToken resource from the cluster via the OpenShift OAuth API (`oauth.openshift.io/v1/oauthaccesstokens`), matching the behavior of the OpenShift console. This is best-effort and does not block the logout response. [source: oauthproxy.go:857-899]

Redis/Valkey session storage enables horizontal scaling of proxy instances. The Redis client supports TLS with configurable CA certificates (loaded from the system trust store and optionally augmented with a custom CA path) and optional `InsecureSkipTLSVerify` for development environments. [source: pkg/sessions/redis/redis_store.go:26-36, 182-218]

The component has no internal RHOAI platform dependencies; it operates as a standalone proxy deployed alongside the services it protects. Its only external runtime dependencies are the Kubernetes API (for TokenReview validation and in-cluster configuration), the configured OAuth2/OIDC identity provider, and optionally Redis for session persistence. [source: main.go:60-74, pkg/authentication/k8s/tokenreview.go:47-69]

## Data Flows

- **Client request ingress:** Clients connect to the kube-auth-proxy Service (port 80 → target 4180) or via an OpenShift Route with TLS termination. The proxy's pre-auth middleware chain runs health checks and request logging before authentication. [source: examples/openshift/service-account/deployment.yaml:131, 208, oauthproxy.go:382-423]
- **Authentication flow:** Incoming requests pass through a layered middleware chain: (1) K8s ServiceAccount token validation via TokenReview API for programmatic access, (2) JWT/OAuth bearer token validation for OIDC or OpenShift OAuth tokens, (3) basic auth via htpasswd, (4) stored cookie session lookup and refresh. Unauthenticated browser requests are redirected to the OAuth2/OIDC sign-in flow. [source: oauthproxy.go:425-464, main.go:60-74]
- **Upstream proxying:** Authenticated requests are forwarded to the configured upstream backend with injected request/response headers (user identity, groups, access token). The upstream proxy handler manages connection pooling and request routing. [source: oauthproxy.go:182-185, 363]
- **Session persistence:** Sessions can be stored in Redis/Valkey via go-redis with optional TLS (configurable CA certificates and InsecureSkipTLSVerify). Session data is encrypted and stored with configurable expiration. [source: pkg/sessions/redis/redis_store.go:26-36, 178-218]
- **Sign-out flow:** On sign-out, the proxy clears the session cookie and, when the OpenShift provider is active, asynchronously deletes the OAuthAccessToken resource via the OpenShift OAuth API for session hygiene. [source: oauthproxy.go:809-850, 857-899]
