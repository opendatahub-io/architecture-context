## Purpose

**Short**: OpenShift operator that deploys and manages the Kueue job-queuing system, providing cluster-wide workload admission control and resource quota management for batch and ML training workloads. [source: bindata/assets/kueue-operator/deployment.yaml:1, cmd/kueue-operator/main.go:12, pkg/operator/starter.go:28]

**Detailed**: The kueue-operator is an OpenShift-specific operator that manages the lifecycle of the upstream Kueue job-queuing controller. The operator Deployment (`openshift-kueue-operator`) watches a cluster-scoped `Kueue` custom resource (`kueue.openshift.io/v1`) and reconciles the Kueue controller-manager Deployment along with its RBAC, webhooks, CRDs, and configuration. The managed `kueue-controller-manager` Deployment runs the upstream Kueue controller, which provides workload admission control through ClusterQueues and LocalQueues, enforcing resource quotas across namespaces. Kueue intercepts workload creation via 35 mutating and validating admission webhooks covering batch Jobs, Kubeflow training jobs (PyTorchJob, TFJob, MPIJob, XGBoostJob, PaddleJob), Ray clusters/jobs, JobSets, LeaderWorkerSets, AppWrappers, Deployments, StatefulSets, and Pods. A visibility API server on port 8082 exposes pending workload status. The operator also ships a must-gather container for diagnostic data collection. [source: bindata/assets/kueue-operator/deployment.yaml:1, bindata/assets/kueue-operator/mutatingwebhook.yaml:1, bindata/assets/kueue-operator/validatingwebhook.yaml:1, pkg/operator/starter.go:28]

## Architectural Analysis

The kueue-operator follows a two-tier operator architecture. The outer operator (`openshift-kueue-operator`, namespace `openshift-kueue-operator`) is a library-go-based static resource controller that renders and applies the inner Kueue controller-manager and all its supporting resources. The operator entrypoint at `cmd/kueue-operator/main.go` uses `controllercmd` from `openshift/library-go` to bootstrap the reconciliation loop in `pkg/operator/starter.go`, which creates a Kubernetes client, discovery client, dynamic client, and an OpenShift Route client, then delegates to a `TargetConfigReconciler` that manages the operand lifecycle. [source: pkg/operator/starter.go:28-80, cmd/kueue-operator/main.go:12]

The managed `kueue-controller-manager` Deployment runs as a single replica with three network surfaces: a webhook server on port 9443 serving 35 admission endpoints backed by TLS certificates from the `kueue-webhook-server-cert` Secret, a visibility API server on port 8082 registered as a Kubernetes API aggregation endpoint for `visibility.kueue.x-k8s.io`, and a metrics endpoint on port 8443 protected by RBAC-based authentication using TokenReview and SubjectAccessReview. Health and readiness probes are served on port 8081 at `/healthz` and `/readyz`. [source: bindata/assets/kueue-operator/deployment.yaml:41-50, bindata/assets/kueue-operator/webhook-service.yaml:1, bindata/assets/kueue-operator/visibility-server.yaml:1]

The RBAC model is extensive: the `kueue-manager-role` ClusterRole grants 36 rules spanning Kueue CRDs, batch Jobs, Kubeflow training operators (kubeflow.org), Ray (ray.io), JobSets, LeaderWorkerSets, AppWrappers (workload.codeflare.dev), and core resources such as Pods, Secrets, and Events. Complementary per-resource editor and viewer ClusterRoles provide fine-grained user-facing access control. The operator's own ClusterRole manages CRDs, webhooks, RBAC, Deployments, cert-manager resources, and ServiceMonitors for the managed operand. [source: bindata/assets/kueue-operator/clusterroles/clusterrole-manager-role.yaml:2, deploy/02_clusterrole.yaml:1]

All webhook configurations use `failurePolicy: Fail`, meaning that if the webhook server is unavailable, workload creation and updates are blocked. This is a deliberate safety choice ensuring that no workload can bypass quota enforcement, but it creates a hard dependency on the webhook server's availability for cluster workload operations. The operator uses cert-manager CRDs for TLS certificate lifecycle management of the webhook serving certificates. [source: bindata/assets/kueue-operator/mutatingwebhook.yaml:1, bindata/assets/kueue-operator/validatingwebhook.yaml:1, deploy/02_clusterrole.yaml:132-145]

The build uses `-tags strictfipsruntime` (Makefile:12) with the Red Hat Go 1.23 builder on a UBI9-minimal runtime base, indicating FIPS-compliant crypto enforcement at the Go runtime level. [source: Makefile:12, Dockerfile:1-6]

## Data Flows

- **Operator reconciliation:** The `openshift-kueue-operator` Deployment watches `Kueue` CRs (`kueue.openshift.io/v1`) and reconciles the `kueue-controller-manager` Deployment, its RBAC bindings, webhook configurations, CRDs, and cert-manager Certificate CRs. The operator uses the Kubernetes API via ServiceAccount token with the `openshift-kueue-operator` ClusterRole. [source: pkg/operator/starter.go:28-80, deploy/02_clusterrole.yaml:1]
- **Workload admission:** When a workload (Job, PyTorchJob, RayCluster, etc.) is created or updated, the kube-apiserver routes the admission request to the `kueue-webhook-service` (port 443 → target 9443) over TLS. The controller-manager's webhook server mutates the workload to inject queue labels and validates it against ClusterQueue/LocalQueue policies. All 35 webhook configurations use `failurePolicy: Fail`. [source: bindata/assets/kueue-operator/mutatingwebhook.yaml:1, bindata/assets/kueue-operator/validatingwebhook.yaml:1, bindata/assets/kueue-operator/webhook-service.yaml:1]
- **Metrics and monitoring:** The controller-manager exposes Prometheus metrics on port 8443, accessed through the `kueue-controller-manager-metrics-service`. Access is protected by RBAC-based authentication (TokenReview/SubjectAccessReview) via the `kueue-metrics-auth-role`. The operator creates ServiceMonitors for prometheus-operator scraping. [source: bindata/assets/kueue-operator/controller-manager-metrics-service.yaml:1, bindata/assets/kueue-operator/clusterroles/clusterrole-metrics-auth-role.yaml:2, deploy/02_clusterrole.yaml:93-104]
- **Visibility API:** A visibility API server on port 8082 (exposed via `kueue-visibility-server` Service at port 443) provides pending workload status as a Kubernetes API aggregation endpoint (`visibility.kueue.x-k8s.io`). Authentication is delegated to the kube-apiserver via the `extension-apiserver-authentication-reader` Role. [source: bindata/assets/kueue-operator/visibility-server.yaml:1, bindata/assets/kueue-operator/deployment.yaml:43-44]
