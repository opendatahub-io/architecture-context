## Purpose

**Short**: OpenShell is a sandboxed runtime platform for autonomous AI agents, providing secure container/VM lifecycle management, policy-enforced network egress, and credential-injected inference routing via gRPC/HTTP APIs.

**Detailed**: OpenShell provides a control-plane gateway and a multi-driver sandbox runtime that enables AI agents to execute code safely within isolated containers or virtual machines. The gateway server exposes a comprehensive gRPC API for sandbox lifecycle management (create, exec, stop, delete), provider credential management, inference route configuration, and policy enforcement. The platform enforces security at multiple layers: network isolation via OPA-compiled policy with L7 protocol inspection (REST, GraphQL, JSON-RPC, SQL, WebSocket), process sandboxing via seccomp and Landlock, and credential injection via placeholder substitution that prevents secret leakage.

The architecture is built around a pluggable driver model supporting Kubernetes, Docker, Podman, and KVM/QEMU VM compute backends, with credential storage via HashiCorp Vault, Kubernetes Secrets, or AES-256-GCM encrypted database. In Kubernetes deployments, the supervisor runs as a network sidecar alongside the sandbox container, enforcing egress policy via nftables rules and an HTTP CONNECT proxy. The gateway authenticates users via OIDC JWT tokens or mTLS certificates, and mints sandbox-scoped JWTs for supervisor-to-gateway communication. The system includes an SMT-based formal verification engine (Z3) for detecting data exfiltration paths in sandbox policies.

## Architectural Analysis

OpenShell's architecture is organized as a Rust workspace of 27 crates with clean separation between the control plane (gateway server), data plane (sandbox supervisor), and client tooling (CLI/SDK/TUI). The gateway multiplexes gRPC and HTTP on a single port using connection preface inspection, enabling both API access and health probes on the same listener.

The most significant architectural pattern is the descriptor-based authorization model: each gRPC method carries authorization requirements (auth mode, workspace role, global role, scope) as proto options, which are loaded into a runtime descriptor pool at startup and enforced before handler dispatch. This eliminates scattered auth checks and makes the authorization surface auditable from proto definitions alone.

The network supervisor implements a sophisticated proxy architecture where sandbox egress is intercepted via nftables rules that redirect traffic through an HTTP CONNECT proxy. The proxy performs binary identity attribution (via `/proc/<pid>/exe`) and OPA policy evaluation before allowing connections, with optional L7 inspection via TLS interception using dynamically generated leaf certificates. This design provides defense-in-depth: L4 filtering at the nftables layer, L7 inspection at the proxy layer, and credential injection only after policy evaluation passes.

A notable security boundary is the UID separation between the network sidecar (UID 1337) and the sandbox workload (UID 1000+). The sidecar holds gateway credentials and TLS material in directories with restrictive permissions (0o750/0o400), while nftables bypass rules prevent the sidecar's own traffic from being re-proxied. The IPC between sidecar and process supervisor uses Unix domain sockets with peer credential validation, providing PID/UID spoofing resistance.

The formal verification engine (Z3 SMT solver) is architecturally unique in this ecosystem — it enables static analysis of sandbox policies to detect potential data exfiltration paths before deployment, providing a provable security guarantee beyond runtime enforcement. The gateway builds with Z3 bundled from source via gcc-toolset-14 for C++20 support.

The Konflux build pipeline produces three separate container images (gateway, CLI, supervisor) using hermetic builds with Hermeto-prefetched dependencies. The gateway uses a glibc-linked binary on ubi9-minimal, while the CLI and supervisor produce fully-static binaries (glibc CRT-static). The supervisor image includes nftables and iproute runtime packages for network namespace management. All TLS is handled by rustls with the ring backend rather than OpenSSL, which is a significant FIPS compliance consideration.

_OpenShell uses rustls with the ring cryptographic backend exclusively — no OpenSSL dependency exists. While ring implements NIST-approved algorithms (AES-256-GCM, SHA-256, ECDSA, Ed25519), the ring library is not FIPS 140-2/3 validated. The aws_lc_rs backend used by jsonwebtoken has a FIPS module available but FIPS mode activation is not configured in the build. The absence of OpenSSL means the standard Konflux check-payload FIPS gate (which expects dynamically linked OpenSSL) may not pass without adaptation. This is architecturally significant for RHOAI deployment compliance._
