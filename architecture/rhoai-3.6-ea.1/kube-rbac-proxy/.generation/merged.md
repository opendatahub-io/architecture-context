## Purpose

**Short**: kube-rbac-proxy is a Kubernetes-aware reverse proxy deployed as a sidecar container that performs TLS termination and enforces authentication (via OIDC or Kubernetes TokenReview) and authorization (via SubjectAccessReview) on behalf of upstream services. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:328-331, Dockerfile.konflux:25]

**Detailed**: kube-rbac-proxy acts as a security sidecar in RHOAI component pods, intercepting inbound HTTPS requests on port 8443 and forwarding authenticated, authorized requests to the upstream application over HTTP on localhost. The proxy delegates authentication to configurable providers — either OIDC token validation or Kubernetes TokenReview — and authorization to Kubernetes SubjectAccessReview, allowing platform operators to enforce RBAC policies on any HTTP service without modifying the service itself. The proxy uses a handler chain (`WithAuthentication` → `WithAuthorization` → `WithAuthHeaders`) that can be selectively bypassed via configurable allow-paths for endpoints like health checks. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:326-338]

In RHOAI, the component is built with FIPS-compliant settings (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) from UBI9 base images and shipped as the `odh-kube-rbac-proxy-rhel9` container image. It connects to the Kubernetes API server using in-cluster ServiceAccount tokens or external kubeconfig credentials to perform TokenReview and SubjectAccessReview requests. TLS on the listener side supports configurable minimum version and cipher suites, with certificate hot-reloading for production deployments. [source: Dockerfile.konflux:8-10, cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:346-401, cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:506-522]

## Architectural Analysis

kube-rbac-proxy implements the sidecar proxy pattern for Kubernetes authentication and authorization enforcement. It sits in front of an upstream HTTP service within the same pod, terminating TLS on its secure listener (typically port 8443) and reverse-proxying authenticated requests to the upstream's localhost port (typically 8080). This architecture allows any HTTP service to gain Kubernetes-native RBAC protection without embedding authentication logic.

The proxy's request pipeline is structured as a composable handler chain. For each incoming request, the proxy first checks if the path matches a configured allow-list (`WithAllowPaths`); if so, the request bypasses authentication and is forwarded directly to the upstream. Otherwise, the chain applies `WithAuthentication` (validating credentials via OIDC or Kubernetes TokenReview), `WithAuthorization` (performing a SubjectAccessReview against the Kubernetes API), and `WithAuthHeaders` (injecting authenticated identity headers) before proxying the request. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:326-338]

The TLS configuration is production-grade: the proxy supports configurable minimum TLS version (normalized to accept both kube-rbac-proxy-style and k8s component-base-style version names), configurable cipher suites via Kubernetes apiserver flag utilities, and certificate hot-reloading via a file watcher. When no certificate files are provided, the proxy generates a self-signed certificate for development use. The upstream transport enforces TLS 1.2 minimum and supports optional mTLS with configurable CA and client certificates. A separate proxyEndpoints listener serves the `/healthz` health check endpoint using the same TLS configuration but without authentication. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:346-401, cmd/kube-rbac-proxy/app/transport.go:28-77]

The proxy relies on the Kubernetes API server for both TokenReview and SubjectAccessReview operations, connecting via in-cluster ServiceAccount credentials or an external kubeconfig. This makes the Kubernetes API server a critical dependency — if the API server is unreachable, authentication and authorization checks will fail, blocking all non-bypassed requests. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:506-522]

## Data Flows

### Flow 1: Authenticated Request Proxy

| Step | Source | Destination | Port | Protocol | Encryption | Auth |
|------|--------|-------------|------|----------|------------|------|
| 1 | Client | kube-rbac-proxy (secure listener) | 8443/TCP | HTTPS | TLS 1.2+ (configurable) | Bearer token (OIDC or SA token) |
| 2 | kube-rbac-proxy | Kubernetes API (TokenReview) | 6443/TCP | HTTPS | TLS 1.2+ | ServiceAccount token |
| 3 | kube-rbac-proxy | Kubernetes API (SubjectAccessReview) | 6443/TCP | HTTPS | TLS 1.2+ | ServiceAccount token |
| 4 | kube-rbac-proxy | Upstream service (localhost) | 8080/TCP | HTTP | None (localhost) | Auth headers injected |

The primary data flow is the authenticated reverse proxy path. Clients connect to the kube-rbac-proxy's TLS-secured listener (port 8443). The proxy validates the client's credentials by invoking either a Kubernetes TokenReview or an OIDC provider. If authentication succeeds, the proxy performs a Kubernetes SubjectAccessReview to verify the client is authorized for the requested resource. Authorized requests are forwarded to the upstream application on localhost with identity headers injected via `WithAuthHeaders`. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:326-338, cmd/kube-rbac-proxy/app/transport.go:28-77]
