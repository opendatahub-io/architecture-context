## Purpose

**Short**: kube-rbac-proxy is a TLS-terminating authentication and authorization reverse proxy deployed as a sidecar container to protect Kubernetes service endpoints using OIDC or Kubernetes TokenReview and SubjectAccessReview-based authorization. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:229-275, cmd/kube-rbac-proxy/main.go:27]

**Detailed**: kube-rbac-proxy sits in front of upstream HTTP services as a sidecar container, accepting HTTPS connections on a configurable secure listen address (typically port 8443) and reverse-proxying authenticated and authorized requests to a backend service (typically on localhost over HTTP). It supports two authentication modes: OIDC token validation and Kubernetes delegating authentication via TokenReview. Authorization is handled through a union chain comprising a hardcoded metrics authorizer, a static authorizer, and a SubjectAccessReview authorizer. Configurable ignore-paths allow specific URL patterns to bypass the authentication and authorization chain entirely. The proxy also exposes a separate `/healthz` endpoint on a dedicated port for liveness probing. The component is built with FIPS-compliant settings (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`) in its Konflux Dockerfile, producing a dynamically linked Go binary on a UBI 9 base. It is the RHOAI downstream fork of opendatahub-io/kube-rbac-proxy, synced via auto-merge. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:229-275, 326-341, 420-422, Dockerfile.konflux:8-10, cmd/kube-rbac-proxy/app/transport.go:28-77]

## Architectural Analysis

kube-rbac-proxy implements a handler-chain pattern that wraps a standard `httputil.ReverseProxy` with layered authentication and authorization filters. The core request flow is: incoming HTTPS request → optional ignore-path bypass → `WithAuthentication` (OIDC or Kubernetes TokenReview) → `WithAuthorization` (union of hardcoded metrics, static, and SubjectAccessReview authorizers) → `WithAuthHeaders` (identity propagation) → reverse proxy to upstream. This chain is registered on the root `/` route of the secure listener. Requests matching configured ignore-paths skip the authentication and authorization filters entirely and are forwarded directly to the upstream, which is a design trade-off that prioritizes flexibility for health and metrics paths but requires careful path configuration to avoid bypassing security. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:326-341]

The proxy's TLS configuration is notable for its flexibility: it supports configurable minimum TLS versions (accepting both kube-rbac-proxy-style `TLS1.2` and k8s component-base-style `VersionTLS12` names), configurable cipher suites via `k8sapiflag.TLSCipherSuites`, dynamic certificate reloading from file, and self-signed certificate generation as a fallback. The client authentication mode is `RequestClientCert`, meaning client certificates are requested but not required. The upstream transport independently enforces TLS 1.2 minimum and supports optional mutual TLS via client certificate configuration. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:345-401, cmd/kube-rbac-proxy/app/transport.go:28-77]

The authorization layer uses a union authorizer pattern: the hardcoded metrics authorizer is checked first (allowing OpenShift platform monitoring to always read metrics), followed by static file-based authorization rules, and finally Kubernetes SubjectAccessReview for dynamic RBAC evaluation. This layered approach allows both platform-level and user-level authorization without modifying application code. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:257-275]

## Data Flows

- **Inbound request flow:** External clients connect to kube-rbac-proxy over HTTPS (typically port 8443) via the Kubernetes Service. The proxy terminates TLS, then applies the authentication and authorization handler chain before forwarding the request to the co-located upstream service on localhost. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:326-341, 345-413]
- **Authentication delegation:** When using delegating authentication (non-OIDC mode), kube-rbac-proxy sends TokenReview requests to the Kubernetes API server to validate bearer tokens presented by clients. The token audiences are configurable. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:244-254]
- **Authorization evaluation:** For each authenticated request, the proxy evaluates authorization through a union chain: first checking the hardcoded metrics authorizer, then static file-based rules, and finally issuing SubjectAccessReview requests to the Kubernetes API server for dynamic RBAC evaluation against configurable resource attributes. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:257-275]
- **Upstream proxying:** Authenticated and authorized requests are forwarded to the upstream URL via a `httputil.ReverseProxy` with configurable transport (standard HTTPS, upstream CA bundle, mutual TLS via client certs, or forced H2C for unencrypted HTTP/2). [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:277-298, cmd/kube-rbac-proxy/app/transport.go:28-77]

## Integration Points

- **Kubernetes API:** REST + WebSocket; protocol: HTTPS/WSS; port: 6443; purpose: TokenReview and SubjectAccessReview for delegated authentication and authorization. The proxy constructs a typed Kubernetes clientset to call AuthenticationV1().TokenReviews and AuthorizationV1().SubjectAccessReviews at runtime. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:213, 247, 257]
- **Upstream service:** Sidecar (localhost); role: authentication gateway; protocol: HTTPS to HTTP (or HTTPS with upstream CA, or H2C when `--upstream-force-h2c` is set); port: 8443 inbound to configurable upstream; purpose: Reverse-proxies authenticated and authorized requests to the co-located application container. [source: cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:277-298]
- **kube-rbac-proxy (odh-kube-auth-proxy):** Sidecar Container; purpose: TLS termination and Kubernetes-delegated authentication/authorization enforcement for protected service endpoints. [source: cmd/kube-rbac-proxy/main.go:27-29, Dockerfile.konflux:27]
