## Purpose

**Short**: llm-d-kv-cache is a Go/Python toolkit that indexes KV cache blocks across distributed vLLM inference pods, enabling prefix-aware scheduling through Redis/Valkey-backed scoring and ZeroMQ event-driven cache tracking. **Detailed**: llm-d-kv-cache provides the KV cache indexing and scoring infrastructure for the llm-d distributed inference system. The Go core implements a KV block index that tracks which token prefix sequences are cached on which inference pods, using Redis or Valkey as the backing store. KV cache events from vLLM engines are received via ZeroMQ subscriptions, processed through a configurable worker pool, and indexed for prefix-aware lookup. The HTTP scoring API exposes `/score_completions` and `/score_chat_completions` endpoints that compute per-pod KV cache hit scores, enabling the llm-d routing layer to direct requests to pods that already have relevant context cached. A companion Python gRPC tokenization service (`services/uds_tokenizer`) provides tokenizer access over Unix Domain Sockets for co-located services. A controller-runtime PodReconciler tracks inference pod lifecycle via Kubernetes API watches. The deployment manifest is a placeholder template; actual deployment is orchestrated by parent components such as the llm-d operator. ## Architectural Analysis

llm-d-kv-cache follows an event-driven indexing architecture centered on tracking KV cache state across a fleet of vLLM inference pods. The core data path is: vLLM engines publish KV cache lifecycle events (store, delete, clear) via ZeroMQ, which the online service subscribes to and processes through a concurrent worker pool. These events update a Redis/Valkey-backed KV block index that maps token prefix hashes to pod identifiers and block metadata. When a new inference request arrives, the scoring API computes per-pod prefix match scores by traversing the index, enabling the upstream llm-d routing layer to select pods with maximum cache reuse. [source: examples/kv_events/online/main.go:45-58, pkg/kvcache/kvblock/redis.go:32-58, 60-120]

The Redis/Valkey backend supports both protocol-compatible backends through URL scheme detection (`redis://`, `rediss://`, `valkey://`, `valkeys://`), with TLS available when using the `rediss://` or `valkeys://` schemes. RDMA transport for Valkey is defined as a placeholder configuration but not yet functional in the Go client. [source: pkg/kvcache/kvblock/redis.go:73-90, 97-108]

The tokenization service is a standalone Python gRPC server that communicates exclusively over Unix Domain Sockets (`/tmp/tokenizer/tokenizer-uds.socket`) with filesystem-level access control (directory mode 0700). It exposes an HTTP health probe on port 8082 for Kubernetes liveness/readiness checks. The gRPC IndexerService example demonstrates prefix scoring as a service but uses no authentication interceptors. [source: services/uds_tokenizer/run_grpc_server.py:37-56, 87-91, examples/kv_cache_index_service/server/main.go:98-101]

No application-level authentication is configured on any endpoint in this component. The HTTP scoring API, gRPC IndexerService, and gRPC TokenizationService all run without auth middleware or TLS. The `pyjwt` dependency appears only in test requirements, not in production code paths. Authentication and encryption are expected to be enforced at the platform level through service mesh policies, network policies, or gateway configuration. ## Data Flows

- **KV cache event ingestion:** vLLM inference engines publish KV cache lifecycle events (block store, delete, clear) via ZeroMQ on a configurable endpoint (default `tcp://localhost:5557`, topic `kv@`). The online service subscribes to these events and processes them through a concurrent worker pool (default 4 workers) that updates the Redis/Valkey KV block index. [source: examples/kv_events/online/main.go:45-51, pkg/kvcache/kvblock/redis.go:110]
- **Prefix scoring requests:** External routing components (e.g., llm-d EPP) send HTTP POST requests to `/score_completions` or `/score_chat_completions` on port 8080. The scoring API computes per-pod KV cache hit scores by querying the Redis/Valkey index, then returns ranked pod scores as JSON. The `/metrics` endpoint exposes Prometheus metrics via the controller-runtime metrics registry. [source: examples/kv_events/online/main.go:244-316]
- **Tokenization flow:** Co-located services access the gRPC TokenizationService over a Unix Domain Socket (`/tmp/tokenizer/tokenizer-uds.socket`).
