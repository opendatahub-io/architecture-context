## Purpose

**Short**: llm-d-kv-cache provides KV cache indexing and prefix-aware scoring for LLM inference, enabling cache-aware request routing by tracking KV cache blocks in Redis/Valkey and scoring incoming prompts against cached prefix data. [source: pkg/kvcache/kvblock/redis.go:34-41, examples/kv_events/online/main.go:248-272]

**Detailed**: llm-d-kv-cache is a Go and Python system that manages KV cache state for distributed LLM inference. The core Go library indexes KV cache blocks in a Redis or Valkey backend, processes KV cache lifecycle events from vLLM engines via ZeroMQ pub/sub, and exposes scoring APIs that compute prefix cache hit ratios for incoming prompts. This enables an external router (such as llm-d's Endpoint Picker) to direct inference requests to vLLM instances that already hold relevant cached KV data, reducing time-to-first-token. The component includes a Python gRPC tokenizer sidecar (`uds_tokenizer`) that runs within KServe inference pods over a Unix domain socket to tokenize prompts for cache matching. A controller-runtime pod reconciler tracks vLLM engine pod lifecycle via Kubernetes watches to maintain cache index consistency. The system exports traces to an OpenTelemetry Collector and Prometheus metrics for observability. [source: pkg/kvcache/kvblock/redis.go:34-41, 60-120, examples/kv_events/online/main.go:44-58, 236-322, examples/kv_cache_index_service/server/main.go:34-107, services/uds_tokenizer/Dockerfile.konflux:57, 71, 81, pkg/telemetry/tracing.go:161-182]

## Architectural Analysis

llm-d-kv-cache is structured as a Go library with multiple example binaries, a Python tokenizer sidecar, and supporting connectors. The architecture centers on a KV block indexing layer (`pkg/kvcache/kvblock`) that abstracts Redis and Valkey as interchangeable backends via the `Index` interface, with address-scheme-based TLS selection (`rediss://` or `valkeys://` for TLS, plain `redis://` or `valkey://` for unencrypted TCP). The Redis client is configured through URL parsing with connection validation via `Ping`, and RDMA transport for Valkey is stubbed but not yet implemented in the Go client. [source: pkg/kvcache/kvblock/redis.go:34-41, 60-120]

The event processing pipeline (`pkg/kvevents`) consumes KV cache lifecycle events from vLLM engines via ZeroMQ pub/sub, with a configurable pool concurrency model. The `online` example demonstrates the complete runtime: a ZMQ subscriber receives cache events, an indexer scores prompts against cached blocks, and an HTTP server exposes `/score_completions` and `/score_chat_completions` endpoints (default port 8080) alongside Prometheus `/metrics`. No authentication or TLS is configured on these HTTP endpoints. [source: examples/kv_events/online/main.go:44-58, 236-322]

The gRPC `IndexerService` (protobuf-defined in `api/indexerpb`) listens on port 50051 with OpenTelemetry trace propagation via a stats handler interceptor but no TLS credentials or authentication interceptors. The tokenizer gRPC service (`tokenization.TokenizationService`) is designed to run as a UDS sidecar within KServe inference pods, communicating over a Unix domain socket at `/tmp/tokenizer` rather than a network port. This design delegates network-level security to the pod boundary and KServe's sidecar injection mechanism. [source: examples/kv_cache_index_service/server/main.go:34, 98-101, services/uds_tokenizer/Dockerfile.konflux:57, 71]

Observability is dual-stack: Go components export distributed traces to an OpenTelemetry Collector via OTLP/gRPC (currently configured with `WithInsecure()` for non-TLS transport) and expose Prometheus metrics via the controller-runtime metrics registry. The pod reconciler uses controller-runtime to watch `/v1/Pod` resources, maintaining cache index consistency when vLLM engine pods are created or removed. [source: pkg/telemetry/tracing.go:161-182, examples/kv_events/online/main.go:244-246]

The repository produces two container images: a Go binary (`/app/kv-cache-manager`) built on UBI9, and a Python tokenizer sidecar built on the AIPCC `cpu:3.4` base image. The Go Dockerfile does not include FIPS-specific build flags (`GOEXPERIMENT=strictfipsruntime` or explicit `CGO_ENABLED=1`), and no Konflux Dockerfile exists for the Go binary. The Python sidecar inherits any FIPS posture from the AIPCC base image's OpenSSL configuration. [source: Dockerfile:16-58, services/uds_tokenizer/Dockerfile.konflux:16, 32]

## Data Flows

- **KV cache event ingestion:** vLLM engines publish KV cache lifecycle events (block allocations, evictions, clears) via ZeroMQ pub/sub to the configurable endpoint (default `tcp://localhost:5557`, topic `kv@`). The event processing pool (`kvevents`) consumes these events with configurable concurrency and updates the KV block index in Redis/Valkey. [source: examples/kv_events/online/main.go:44-51, pkg/kvcache/kvblock/redis.go:60-120]
- **Scoring request flow:** External routers (such as llm-d Endpoint Picker) send HTTP POST requests to `/score_completions` or `/score_chat_completions` (port 8080). The handler decodes the prompt, queries the KV block index in Redis/Valkey for prefix cache hit scores, and returns scored pod rankings as JSON. The `/metrics` endpoint exposes Prometheus metrics via the controller-runtime registry. No authentication is applied to any HTTP endpoint. [source: examples/kv_events/online/main.go:248-298, 244-246, 306-316]
