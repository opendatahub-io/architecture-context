## Purpose

**Short**: OpenVINO Model Server (OVMS) is a high-performance C++ inference server that exposes TensorFlow Serving V1, KServe V2, and OpenAI-compatible V3 REST and gRPC APIs for serving machine learning models on OpenShift AI. **Detailed**: OpenVINO Model Server (OVMS) is a model inference server built primarily in C++ with Go client libraries, packaged as a container image for deployment as a KServe ServingRuntime on Red Hat OpenShift AI. It supports multiple model formats including OpenVINO IR, ONNX, TensorFlow, PaddlePaddle, PyTorch, and vLLM, exposed through three REST API protocol versions (TFS V1, KServe V2, and OpenAI-compatible V3) plus KServe V2 gRPC inference services. The repository ships two serving runtime definitions: a cluster-scoped `kserve-openvino` ClusterServingRuntime and a namespace-scoped `kserve-ovms-2026-2` ServingRuntime configured for OpenShift AI with GPU support. An optional nginx-based mTLS proxy sidecar (`extras/nginx-mtls-auth/`) provides client certificate authentication and TLS termination for both REST and gRPC traffic. The codebase originates upstream from `openvinotoolkit/model_server`, syncs through `opendatahub-io/openvino_model_server`, and is carried downstream in `red-hat-data-services/openvino_model_server` with Konflux CI integration. [source: Dockerfile.konflux:457-466, extras/openshift_AI/ServingRuntime.yaml:1-61, extras/kserve/kserve-openvino.yaml:1-63, extras/nginx-mtls-auth/model_server.conf.template:23-80]

## Architectural Analysis

OVMS is a C++ inference server (the analyzer classified the language as Go due to the client library modules in `client/go/`, but the primary server binary at `/ovms/bin/ovms` is C++) that implements three REST API protocol versions and gRPC inference services. The server architecture uses a handler-dispatch pattern: `HttpRestApiHandler` registers regex-based route handlers for TFS V1 (`/v1/models/...`), KServe V2 (`/v2/models/...`, `/v2/health/...`), OpenAI-compatible V3 (`/v3/...`), and Prometheus metrics (`/metrics`) endpoints, while `GRPCServerModule` hosts the `inference.GRPCInferenceService` proto service with `ModelInfer`, `ModelStreamInfer`, health, and metadata RPCs. [source: src/http_rest_api_handler.cpp:102-129, src/kfserving_api/grpc_predict_v2.proto:19-48]

The serving runtime integration follows the KServe pattern: OVMS ships as a container image referenced in `ServingRuntime` and `ClusterServingRuntime` CRDs. The RHOAI-specific `kserve-ovms-2026-2` runtime configures gRPC on port 8001 and REST on port 8888 with a `/v2/health/ready` startup probe, while the upstream `kserve-openvino` runtime uses ports 9000 (gRPC) and 8080 (REST). Both runtime definitions enable Prometheus metrics scraping via pod annotations. [source: extras/openshift_AI/ServingRuntime.yaml:17-24, extras/kserve/kserve-openvino.yaml:14-20]

The optional nginx-mtls-auth sidecar wraps the OVMS binary behind an nginx reverse proxy that terminates TLS 1.2 with mutual client certificate verification. The wrapper script intercepts `--port` and `--rest_port` arguments, reassigns OVMS to internal loopback ports, and configures nginx to listen on the original ports with mTLS. This sidecar enforces restricted cipher suites (`AES256+EECDH` excluding RSA, CAMELLIA, RC4, and weak hashes) and HSTS headers. The core OVMS binary itself does not enforce authentication; it relies on the platform (KServe, Istio, or the nginx sidecar) for transport security. [source: extras/nginx-mtls-auth/model_server.conf.template:27-44, extras/nginx-mtls-auth/ovms_wrapper:113-157]

The build pipeline uses a UBI 9 base image (`registry.access.redhat.com/ubi9/ubi-minimal:9.7`) and compiles against system OpenSSL (`openssl-devel`). No explicit FIPS build flags (such as `GOEXPERIMENT=strictfipsruntime` or FIPS-specific compile options) were found; FIPS compliance is inherited from the UBI base image's OpenSSL when the host node enables FIPS mode. [source: Dockerfile.konflux:17-49, Dockerfile.konflux:456-457]

## Data Flows

- **Model inference (REST):** Client sends HTTP request to OVMS REST port → `HttpRestApiHandler` dispatches to the appropriate protocol handler (V1 predict, V2 infer, or V3 OpenAI-compatible) → inference executes against the loaded model → response returned to client. The REST port is configurable via `--rest_port` (8888 in the RHOAI runtime, 8080 in the kserve-openvino runtime). [source: src/http_rest_api_handler.cpp:102-129, extras/openshift_AI/ServingRuntime.yaml:20]

- **Model inference (gRPC):** Client sends gRPC request to OVMS gRPC port → `GRPCInferenceService.ModelInfer` or `ModelStreamInfer` RPC → inference executes → response streamed or returned to client. The gRPC port is configurable via `--port` (8001 in the RHOAI runtime, 9000 in the kserve-openvino runtime). [source: src/kfserving_api/grpc_predict_v2.proto:43-48, extras/openshift_AI/ServingRuntime.yaml:19]

- **Model loading:** On startup, OVMS loads models from the path specified by `--model_path` (typically `/mnt/models`, provisioned by KServe's storage initializer from S3, PVC, or other storage backends). Model readiness is reported via `/v2/health/ready` and used as a KServe startup probe. [source: extras/openshift_AI/ServingRuntime.yaml:18-29]

- **mTLS proxy (optional):** When the nginx-mtls-auth sidecar is deployed, external clients connect to nginx on the originally requested ports with TLS 1.2 client certificate authentication → nginx proxies gRPC traffic via `grpc_pass` and REST traffic via `proxy_pass` to OVMS on internal loopback ports. [source: extras/nginx-mtls-auth/model_server.conf.template:49-78, extras/nginx-mtls-auth/ovms_wrapper:135-142]
