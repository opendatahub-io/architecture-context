## Purpose

**Short**: Argo Workflows is the workflow execution engine for Data Science Pipelines in RHOAI, providing a Kubernetes-native workflow controller and API server for defining and running DAG-based computational workflows. [source: rhoai/Dockerfile.workflowcontroller:40, rhoai/Dockerfile.argoexec:39, manifests/base/workflow-controller/workflow-controller-deployment.yaml:1, manifests/base/argo-server/argo-server-deployment.yaml:1]

**Detailed**: Argo Workflows provides the core workflow execution runtime for the Red Hat OpenShift AI Data Science Pipelines subsystem. It consists of two primary runtime components: a workflow controller that reconciles Workflow, CronWorkflow, and related custom resources through Kubernetes watch/reconcile loops, and an API server (argo-server) that exposes both gRPC and HTTP/REST interfaces for workflow management, artifact retrieval, and event handling. A third component, argoexec, runs as a sidecar or init container within workflow pods to manage artifact collection, script execution, and container lifecycle. The platform ships 8 CRDs under the argoproj.io API group for workflow definitions, templates, scheduling, and artifact garbage collection. Authentication on the API server is enforced by a gatekeeper interceptor supporting Bearer token, server-mode, and SSO/OIDC auth flows. [source: server/auth/gatekeeper.go:49-54, server/apiserver/argoserver.go:295-312, manifests/base/crds/minimal/argoproj.io_workflows.yaml:1, cmd/workflow-controller/main.go:181]

## Architectural Analysis

Argo Workflows follows a controller-pattern architecture with two cooperating Deployments. The **workflow-controller** watches Workflow and related CRDs, orchestrates pod creation for workflow steps, manages artifact garbage collection, and maintains ConfigMap-based memoization caches. The **argo-server** provides a unified API surface by co-hosting a gRPC server and an HTTP reverse proxy (grpc-gateway) on port 2746, routing `/api/` requests through the gRPC gateway while serving artifact download, OAuth2 callback, and static UI endpoints directly via HTTP handlers. [source: server/apiserver/argoserver.go:282-416, cmd/workflow-controller/main.go:181]

Authentication is centralized in a gatekeeper interceptor that chains into both gRPC unary/stream and HTTP request paths. The gatekeeper supports three modes—`client` (Bearer/Basic token creating per-request Kubernetes clients), `server` (using the server's own service account), and `sso` (OIDC tokens with optional RBAC delegation via annotated ServiceAccounts). A `hybrid` shorthand enables both client and server modes simultaneously. The `/metrics` endpoint has conditional authentication controlled by the `ARGO_SERVER_METRICS_AUTH` environment variable; the workflow-controller `/healthz` endpoint is unauthenticated by design. [source: server/auth/gatekeeper.go:90-218, server/auth/mode.go:14-44, server/apiserver/argoserver.go:397-411]

The Konflux build pipeline produces statically linked Go binaries with `CGO_ENABLED=0` and the Go 1.24+ `GOFIPS140=v1.0.0` native FIPS 140 cryptographic module. The `-tags no_openssl` flag explicitly excludes OpenSSL binding, meaning FIPS compliance relies entirely on Go's built-in FIPS 140 module rather than the traditional OpenSSL dynamic-linking approach. This is architecturally significant because traditional check-payload validation expects dynamically linked binaries with OpenSSL present in the image. [source: argo-workflowcontroller/Dockerfile.konflux:25, argo-argoexec/Dockerfile.konflux:24]

The component operates as part of the Data Science Pipelines subsystem—Dockerfile labels and Tekton pipeline names reference `odh-data-science-pipelines-argo-*`—but contains no direct code-level imports of other RHOAI platform components. The integration boundary is at the Kubernetes API level: the workflow controller creates Pods, ConfigMaps, PodDisruptionBudgets, and Secrets, and performs SelfSubjectAccessReviews for authorization checks, all via client-go typed and dynamic clients. [source: rhoai/Dockerfile.workflowcontroller:31, workflow/controller/agent.go:255, workflow/controller/cache/configmap_cache.go:164, util/auth/auth.go:16]

## Data Flows

- **Workflow submission and API access:** Clients (CLI, UI, or platform controllers such as DSP) submit workflow definitions through the argo-server gRPC or HTTP/REST interface on port 2746. Requests pass through the gatekeeper authentication interceptor which validates Bearer tokens, SSO/OIDC tokens, or falls back to server-mode ServiceAccount credentials before reaching the service handlers. [source: server/apiserver/argoserver.go:295-312, server/auth/gatekeeper.go:90-218, manifests/base/argo-server/argo-server-service.yaml:1]
- **Workflow orchestration:** The workflow-controller watches Workflow CRs via the Kubernetes API, creates workflow step Pods (via client-go), manages ConfigMap-based memoization caches, and creates PodDisruptionBudgets for running workflow pods. The argoexec sidecar runs inside each workflow pod to handle artifact collection, script execution, and container lifecycle signaling. [source: workflow/controller/agent.go:255, workflow/controller/cache/configmap_cache.go:164, workflow/controller/operator.go:3928, cmd/argoexec/main.go:18]
- **Artifact management:** Artifact endpoints (`/artifacts/`, `/artifact-files/`, `/input-artifacts/`) serve workflow artifacts via direct HTTP handlers on the argo-server, using the underlying artifact storage (S3, GCS, Azure Blob, HDFS, or other configured backends). [source: server/apiserver/argoserver.go:389-393]
- **Observability:** Prometheus metrics are exposed on `/metrics` with conditional authentication; pprof debug endpoints are available at `/debug/pprof/`. The workflow-controller exposes a health check on port 6060 at `/healthz`. [source: server/apiserver/argoserver.go:397-414, cmd/workflow-controller/main.go:181, util/pprof/pprof.go:16-20]
