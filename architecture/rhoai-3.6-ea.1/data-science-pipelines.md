## Purpose

**Short**: Data Science Pipelines is a Kubernetes-deployed ML pipeline orchestration platform providing gRPC/REST APIs, Argo Workflows-based execution, metadata tracking, step-level caching, and a web UI for managing machine learning workflows on RHOAI. [source: backend/src/apiserver/main.go:314, backend/src/apiserver/main.go:364-386]

**Detailed**: Data Science Pipelines is the RHOAI distribution of Kubeflow Pipelines, delivering end-to-end ML pipeline orchestration on OpenShift. The platform centers on the `ml-pipeline` API server, which exposes v1beta1 and v2beta1 REST/gRPC APIs for pipeline CRUD, execution, and artifact management. Ten gRPC services (ExperimentService, PipelineService, RunService, RecurringRunService, JobService, TaskService, ReportService, VisualizationService, ArtifactService, AuthService) are registered on a TLS-secured gRPC server with Prometheus metrics interceptors. Pipeline runs are orchestrated through Argo Workflows, with the driver and launcher-v2 components managing step execution within workflow pods. A persistence agent synchronizes pipeline run state between the workflow engine and the API server's database (MySQL). The scheduled workflow controller manages recurring pipeline runs via ScheduledWorkflow custom resources and exposes a Prometheus metrics endpoint. A cache server intercepts workflow pod creation via mutating/validating admission webhooks on PipelineVersion resources to enable step-level caching. ML Metadata (MLMD) provides artifact and execution lineage tracking through an Envoy-proxied gRPC service. The platform manages two custom resources—Pipeline and PipelineVersion (pipelines.kubeflow.org/v2beta1). Authentication is enforced per-request via Kubernetes TokenReview with SubjectAccessReview authorization, and all internal service accounts are bound to least-privilege RBAC roles. ## Architectural Analysis

Data Science Pipelines follows a microservices architecture with a central API server coordinating multiple specialized controllers and supporting services. The API server (`ml-pipeline`) is the primary control plane component, serving both gRPC (port 8887) and HTTP (port 8888) traffic through a gRPC-gateway proxy, with a separate TLS-secured webhook port (8443) for admission webhooks. The gRPC server is constructed with TLS credentials loaded from configurable cert paths and chains a Prometheus metrics interceptor with a logging/error-handling interceptor [source: backend/src/apiserver/main.go:314-339].

The authentication model is per-request rather than middleware-based: each API method extracts a user identity from a configurable request header (passed via gRPC metadata through a custom header matcher), validates it via a Kubernetes `authentication/v1/TokenReview`, and authorizes the operation via `authorization/v1/SubjectAccessReview` [source: backend/src/apiserver/auth/authenticator_token_review.go:47-58, backend/src/apiserver/resource/resource_manager.go:2317-2332]. This design delegates all identity verification and access control to the Kubernetes API server, ensuring that pipeline operations are subject to the same RBAC policies as direct Kubernetes API access.

The platform manages pipeline artifacts and outputs through an S3-compatible object storage interface. The storage client is constructed using the AWS SDK v2 with configurable endpoint, credentials (static key pair or default chain), region, and path-style addressing [source: backend/src/apiserver/client_manager/client_manager.go:1044-1056]. This abstraction supports MinIO, SeaweedFS (bundled for development), and any S3-compatible storage backend.

The FIPS compliance strategy uses Go 1.24+'s `GOFIPS140=v1.0.0` module with the `no_openssl` build tag, selecting Go's built-in FIPS 140-3 validated cryptographic module rather than the traditional OpenSSL/BoringCrypto approach. The API server builds with `CGO_ENABLED=1` (dynamic linking), while the driver and launcher build with `CGO_ENABLED=0` (static linking) for portability across workflow pod environments [source: backend/Dockerfile.konflux.api:29, backend/Dockerfile.konflux.driver:35]. Both build images are based on UBI9/go-toolset and the runtime images use UBI9/ubi-minimal.

Ten RBAC roles enforce least-privilege access across the platform's service accounts, with the `ml-pipeline` role being the most privileged (12 rules covering pipeline CRDs, Argo Workflows, Kubernetes secrets, TokenReview, and SubjectAccessReview). MySQL access is further protected by an Istio AuthorizationPolicy that restricts connections to named service account principals within the deployment namespace.

## Data Flows

- **Pipeline submission and execution:** Clients submit pipeline definitions and runs through the ml-pipeline API server (ports 8887 gRPC, 8888 HTTP via gRPC-gateway). Each request is authenticated via TokenReview and authorized via SubjectAccessReview against the Kubernetes API [source: backend/src/apiserver/main.go:314-339, backend/src/apiserver/auth/authenticator_token_review.go:47-58]. The API server creates Argo Workflow resources to orchestrate pipeline steps, with the driver component managing individual step execution and the launcher-v2 handling container launches within workflow pods.
- **State persistence and synchronization:** Pipeline metadata is persisted to MySQL (port 3306), with the persistence agent watching Argo Workflow status and synchronizing completed run state back to the API server. Pipeline artifacts are stored in S3-compatible storage via the AWS SDK v2 client [source: backend/src/apiserver/client_manager/client_manager.go:1044-1056]. ML Metadata (MLMD) tracks artifact lineage through the metadata-grpc-service (port 8080), fronted by an Envoy proxy (metadata-envoy-service, port 9090).
- **Admission and caching:** The cache server intercepts PipelineVersion resource mutations via mutating and validating admission webhooks on port 8443 (TLS). The cache-deployer manages webhook certificate lifecycle. Step-level caching enables skipping previously completed pipeline steps with matching inputs.
- **Observability and access:** Prometheus collects metrics from the API server (/metrics endpoint) and the scheduled workflow controller via service annotations. The ml-pipeline-ui service (port 80, target 3000) provides the web interface. Ten RBAC roles and their bindings enforce service account isolation across all components, with Istio AuthorizationPolicy providing additional network-level access control for MySQL [source: manifests/kustomize/third-party/mysql/options/istio/istio-authorization-policy.yaml:1].
