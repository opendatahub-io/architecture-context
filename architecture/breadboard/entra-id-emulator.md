## Purpose

entra-id-emulator is a Flask-based mock of Microsoft Entra ID (Azure AD) designed for local development and testing. It implements standard OIDC/OAuth2 endpoints (discovery, authorize, token, JWKS, userinfo, logout) supporting authorization code with PKCE, refresh token, and resource owner password grants, plus a hybrid flow. It issues RSA-signed JWTs, supports pairwise subject identifiers and groups claims with overage handling, and offers per-tenant/per-client token lifetime overrides. State is stored in SQLite with zero external dependencies, seeded from a YAML config, and a password-protected admin REST API and web UI manage tenants, users, groups, and clients.

## Architectural Analysis

The service is a single-process Flask application assembled by a factory (entra_mock/app.py:create_app) that loads YAML configuration, initializes and seeds a SQLite database, generates an RSA signing key, and registers route blueprints. Routes are split by concern: OIDC endpoints (discovery, authorize, token, jwks, userinfo, logout) expose tenant-prefixed paths mirroring real Entra ID URL shapes, while an admin blueprint under /admin provides a Basic-Auth-protected REST API and UI for CRUD over tenants, users, groups, and clients. Token issuance (tokens.py) signs JWTs with an RSA key persisted in SQLite and exposed via JWKS. There is no ingress, gRPC, or CRD surface; deployment is a simple Docker image running run.py on port 8080, with compose examples mounting source and config at runtime. Authentication exists only on the admin surface (HTTP Basic Auth against a configurable admin_password, optional); OIDC endpoints are intentionally unauthenticated as a test double. Tenants are a first-class data partition keyed into URLs and database rows, providing logical multi-tenancy within a shared SQLite instance.

## Security

- **Authentication:** OIDC endpoints are unauthenticated by design (test emulator). Admin API/UI uses optional HTTP Basic Auth against a plaintext admin_password from config. Users have seeded passwords for resource-owner-password grant testing.
- **Authorization:** Client credentials and redirect URI validation during OAuth flows; no RBAC beyond optional admin Basic Auth.
- **FIPS Compliance:** not applicable — local development emulator using standard cryptography libraries; no FIPS validation

**Secrets:**

- **admin_password** — HTTP Basic Auth password for admin console, set in config.yaml server section
- **client_secret** — OAuth client secrets seeded via config or admin API
- **user passwords** — Seeded user credentials hashed with werkzeug password hashing
- **signing keys** — RSA private keys stored unencrypted (PEM) in SQLite for JWT signing

## Multi-Tenancy

**Model:** Logical multi-tenancy: multiple tenants (each a mock Entra ID directory) coexist in one service and shared SQLite database, addressed via tenant-prefixed OIDC URL paths

**Isolation Mechanisms:**

- tenant ID path prefix on OIDC endpoints
- per-tenant rows in SQLite keyed by tenant_id
- per-tenant token lifetime overrides
- pairwise subject identifiers per tenant and client

**Shared Services:** single Flask process, shared SQLite database, shared RSA signing keys

## Data Flows

- **OIDC authorization flow**: Client redirects to /{tenant}/oauth2/v2.0/authorize; user authenticates with seeded credentials; code issued and exchanged at token endpoint for RSA-signed JWTs
- **token issuance**: token.py builds claims (including pairwise sub and groups with overage handling) and signs with the active RSA key from SQLite; public keys published via JWKS
- **admin management**: Admin API/UI performs CRUD on tenants, users, groups, clients persisted in SQLite
- **config seeding**: On startup, YAML config is loaded and seed data is written to the SQLite database
- **key lifecycle**: ensure_signing_key generates and persists an RSA keypair on first start if none exists

## Integration Points

- **OAuth2 clients / relying parties**: Any OIDC client (e.g., oauth2-proxy per examples/oauth2-proxy.cfg) can use discovery, authorize, token, JWKS, and userinfo
- **OpenShift / ODH BYO-IDC**: Documented configs (docs/ocp-byoidc-config.md, docs/odh-byoidc-config.md) integrate the emulator as an OIDC identity provider for OpenShift and OpenDataHub

## Concerns

- Admin authentication is optional and uses a plaintext password compared with ==; OIDC endpoints are entirely unauthenticated — acceptable for a local emulator, unsafe if exposed beyond localhost
- Flask development server is used rather than a production WSGI server
- RSA private keys stored unencrypted in SQLite; no key rotation mechanism documented
- No TLS by default (http scheme); encryption described as configurable but not enforced
- No HA or scaling story; single process with file-based SQLite state
- Hardcoded default admin password (changeme1234) risks accidental exposure in shared environments
