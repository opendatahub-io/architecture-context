## Purpose

**Short**: Python bindings to the TrustyAI Java explainability library, providing ML model explainability, fairness metrics, language detoxification, and an optional Kubernetes API client for the TrustyAI service.

**Detailed**: trustyai-explainability-python is a Python SDK that wraps the TrustyAI Java explainability library via JPype, a Python-to-Java bridge that runs a JVM within the Python process. The library provides several categories of functionality: explainers (LIME, SHAP, Counterfactual, Partial Dependence Plot), fairness metrics (Statistical Parity Difference, Disparate Impact Ratio, Average Odds Difference, Average Predictive Value Difference), language metrics (Levenshtein distance, Word Error Rate), and a language detoxification module (TMaRCo) based on the Hugging Face Transformers library.

The library also includes an optional Kubernetes API client (`trustyai[api]` extra) that discovers the TrustyAI service's OpenShift Route and provides methods to upload data, retrieve metrics, and query Thanos for time-series metric data. A Bokeh-based interactive dashboard (Tyrus) combines LIME, SHAP, and counterfactual explanations into a single visualization.

This is a pure Python library distributed via PyPI -- it has no Dockerfiles, no Kubernetes manifests, and no Konflux build configuration. It is consumed as a dependency by data scientists and ML engineers working within the RHOAI platform, either in Jupyter notebooks or in custom Python applications that interact with the TrustyAI service.

## Architectural Analysis

The trustyai-explainability-python library is architecturally distinctive in the RHOAI ecosystem because it bridges Python and Java via JPype, running an embedded JVM within the Python process. This design allows the library to leverage the mature TrustyAI Java explainability algorithms (which implement LIME, SHAP, Counterfactual search via OptaPlanner, and various fairness metrics) while presenting a Pythonic API familiar to data scientists. The JVM is lazily initialized on first import of any module that requires Java interop, via the `_default_initializer.py` pattern -- this means `import trustyai` itself is lightweight, but any use of explainers triggers JVM startup.

Performance-critical data paths use Apache Arrow for zero-copy data transfer between Python (Pandas DataFrames, NumPy arrays) and Java (PredictionInput/PredictionOutput objects). The `PredictionProviderArrow` class serializes Python predictions as Arrow IPC byte arrays, dramatically reducing the overhead of the thousands of model evaluations required by LIME and SHAP. A context manager pattern (`Model.ArrowTransmission`) transparently switches between Arrow and non-Arrow communication paths depending on whether the explainer benefits from batched evaluation.

The TMaRCo detoxification module (`trustyai.language.detoxify`) is architecturally separate from the core explainability functionality -- it uses Hugging Face Transformers and PyTorch rather than the Java library, and is guarded by a try/except import block that gracefully degrades when its heavy dependencies (`torch`, `transformers`, `datasets`, `scipy`) are not installed. This module implements a text detoxification pipeline combining expert/anti-expert language models with Jensen-Shannon divergence scoring and optional LLM self-reflection.

The optional Kubernetes API client (`trustyai.utils.api` and `trustyai.utils.extras.metrics_service`) provides a thin REST client for the TrustyAI Service deployed on RHOAI. It discovers service endpoints via OpenShift Route lookups using the Python kubernetes client, then communicates with the TrustyAI Service REST API and Thanos Querier for metric retrieval. This client uses a user-provided Bearer token for authentication and supports SSL verification toggling -- the `verify=False` option is a minor security concern that should be documented for users.

A notable architectural risk is the version divergence between `requirements.txt` and `pyproject.toml` -- the former pins `JPype1==1.4.1` and `pyarrow==14.0.1` while the latter specifies `JPype1==1.5.0` and `pyarrow==17.0.0`. Since `pyproject.toml` is the authoritative build configuration (used by `pip install .`), the `requirements.txt` appears to be stale. The bundled Java JAR (`explainability-arrow-999-SNAPSHOT.jar`) is built from source at development time via Maven, but the SNAPSHOT version string suggests this is not a release-quality artifact -- the build process clones the upstream `trustyai-explainability` Java repository and builds the shaded JAR locally.
