## Purpose

**Short**: TrustyAI is a Java-based Quarkus service providing AI model fairness metrics, data drift detection, and explainability algorithms for models served by KServe and ModelMesh on RHOAI.

**Detailed**: TrustyAI Explainability is a multi-module Maven project that provides a containerized REST service for responsible AI. The service consumes inference payloads (inputs and outputs) from model serving infrastructure — either via direct HTTP POST from ModelMesh or via Knative CloudEvents from KServe — and stores them for subsequent analysis.

The core capabilities are organized into three categories: (1) **Fairness metrics** (Statistical Parity Difference, Disparate Impact Ratio) that detect bias in model predictions across protected groups; (2) **Data drift detection** (Kolmogorov-Smirnov test, Meanshift, Fourier MMD, Approximate KS test) that compare production data against reference distributions; and (3) **Explainability algorithms** (LIME, SHAP, Counterfactual, Time Series Saliency, Partial Dependence Plots) that generate human-interpretable explanations of individual model predictions. All metrics can be scheduled for recurring computation, with results published as Prometheus gauges that are scraped by a ServiceMonitor.

The service supports two storage backends: PVC-based flat file storage (CSV) for simple deployments and Hibernate/MariaDB database storage for production workloads. The service is deployed per-namespace by the TrustyAI Operator (a separate repository: `trustyai-service-operator`), which manages the TrustyAIService CRD and creates the necessary Service, PVC, ConfigMap, and ServiceAccount resources. The RHOAI distribution disables explainability endpoints (LIME, SHAP, Counterfactual, TSSaliency, PDP) while keeping fairness and drift metrics enabled.

## Architectural Analysis

TrustyAI Explainability follows a multi-module Maven architecture where the core library (`explainability-core`) provides the algorithmic foundation, while the service layer (`explainability-service`) wraps these algorithms in a Quarkus REST API. This separation allows the core library to be used independently (e.g., by the TrustyAI Python library via the `explainability-arrow` module for cross-language communication). The `explainability-connectors` module provides KServe V2 gRPC client stubs generated from the `grpc_predict_v2.proto` protocol, enabling the explainability algorithms to make inference calls against live model serving endpoints.

The service uses a feature-flag pattern based on Quarkus profiles to control endpoint availability across distributions. The `%rhoai` profile disables all explainability endpoints (LIME, SHAP, Counterfactual, TSSaliency, global PDP) while keeping fairness and drift metrics enabled. This reflects a product maturity decision — explainability features remain available in ODH for community use but are not GA in RHOAI. The `@EndpointDisabled` annotation from Quarkus RESTEasy Reactive handles this at the framework level, completely removing disabled endpoints from the runtime.

The dual storage backend design (PVC flat-file vs. Hibernate/MariaDB) is noteworthy. The `@LookupIfProperty` annotation on storage implementations (`PVCStorage`, `HibernateStorage`, `MinioStorage`, `MemoryStorage`) enables runtime selection based on the `service.storage-format` config property. PVC storage persists data as CSV files in a mounted volume, while the database backend uses Hibernate ORM with JPA entities. A migration path exists (`HibernateMigrator`) for transitioning between storage backends. The init container pattern in the deployment manifest — which uses `oc apply` to create a `model-serving-config` ConfigMap pointing ModelMesh's payload processor at the TrustyAI service URL — is a coupling mechanism that requires the init container to have cluster-level ConfigMap write permissions (hence the ClusterRole).

The Prometheus scheduling system (`PrometheusScheduler`) is the operational core of the service. Users schedule recurring metric computations via REST POST requests, and the scheduler evaluates them at a configurable interval (default 5s). Each computation result is published as a Prometheus gauge with model-specific labels. This design means TrustyAI acts as both a metrics computation engine and a Prometheus exporter, with the ServiceMonitor filtering for `trustyai_*` metric names. The URL validation in `LocalServiceURLValidator` is a security control — it restricts explainability target URLs to local Kubernetes service names (no FQDNs, no external URLs), preventing the service from being used as an SSRF vector.

The Konflux build pattern for this repository is distinctive: rather than building from source in the Dockerfile, the Konflux Dockerfile extracts a pre-built Quarkus application from a PNC (Product Newcastle) build artifact. The `artifacts.lock.yaml` pins the exact PNC build artifact by SHA256 checksum, and the `rpms.lock.yaml` locks OS-level RPM dependencies. This two-tier hermeticity (PNC for Java + rpm-lockfile for OS packages) reflects RHOAI's supply chain security model where build reproducibility is enforced at the CI system level (PNC) rather than in the container build.
