## Purpose

**Short**: TrustyAI Explainability is a Java library and Quarkus-based REST service providing AI fairness metrics, explainability algorithms, and data drift detection for models served via KServe and ModelMesh on the RHOAI platform.

**Detailed**: TrustyAI is the responsible AI component of Red Hat OpenShift AI, providing model transparency and fairness monitoring capabilities. The service acts as an inference data consumer -- it intercepts model inference payloads (via REST endpoints and Knative CloudEvents) from KServe and ModelMesh inference services, stores the data in configurable backends (PVC, MinIO/S3, or relational database via Hibernate ORM), and computes fairness metrics (Statistical Parity Difference, Disparate Impact Ratio), drift detection metrics (Meanshift, Kolmogorov-Smirnov, Fourier MMD), and explainability analyses (LIME, SHAP, Counterfactual, Time Series Saliency) against the collected inference data.

The project is organized as a Maven multi-module build with four primary modules: `explainability-core` (the XAI algorithm library using OptaPlanner for counterfactual search), `explainability-connectors` (gRPC/HTTP connectors implementing the KServe V2 inference protocol), `explainability-arrow` (Apache Arrow data interchange for Python interoperability), and `explainability-service` (the Quarkus REST service that ties everything together). Scheduled metric computations are published as Prometheus gauges for integration with platform monitoring and alerting. The service supports distribution-specific feature profiles -- RHOAI disables the local explainer endpoints (LIME, SHAP, Counterfactual, Time Series Saliency) and global explainer endpoints while keeping fairness and drift metrics enabled.

## Architectural Analysis

TrustyAI's architecture follows a clean modular separation between the XAI algorithm library (`explainability-core`), the protocol layer (`explainability-connectors`), and the service layer (`explainability-service`). This separation enables the core algorithms to be consumed independently as a Java library (published to Maven Central) while the service module adds the REST API, storage, scheduling, and Kubernetes integration. The connector module's use of generated gRPC stubs from the KServe V2 proto definition ensures wire-compatible communication with any KServe-compliant inference server.

The storage layer uses Quarkus CDI's `@LookupIfProperty` annotation to select between four storage backends (Memory, PVC, MinIO, Database) at startup, making the storage choice a deployment-time configuration decision rather than a code change. The PVC backend is the most feature-complete with batch reading, tag filtering, and ID-based queries, while the MinIO backend is notably limited -- it does not support batch reading, slicing, or filtering operations, making it unsuitable for large-scale deployments. The Hibernate/database backend provides the strongest data management capabilities with transactional consistency and SQL-based filtering. A migration path from PVC to database storage exists via the `HibernateMigrator` class, which is triggered asynchronously on startup.

The inference payload reconciliation pattern is a key architectural element. Inference services send input and output payloads separately (partial payloads), and TrustyAI's reconcilers match them by ID before persisting. This decoupled ingestion model means TrustyAI never sits in the inference path -- it only observes inference data asynchronously. The reconciler also tags data as `SYNTHETIC` (generated by explainability algorithms) vs `UNLABELED` (organic inference data), which is critical for drift detection that must compare training data against production data without contamination from synthetic probes.

The feature flag system (`@EndpointDisabled` annotation driven by Quarkus profiles) is architecturally significant for RHOAI. The `%rhoai` profile disables all explainer endpoints (LIME, SHAP, Counterfactual, Time Series Saliency, Aggregated LIME, PDP) while keeping fairness metrics and drift detection enabled. This means the RHOAI-shipped service has a significantly smaller API surface than the ODH version -- only metrics computation and data ingestion endpoints are active. The gRPC client to model servers is unused in RHOAI deployments since the explainer endpoints that trigger gRPC calls are disabled.

A notable security gap is the complete absence of authentication in the application layer. TrustyAI has no `@RolesAllowed`, no JWT validation, no API key checks -- all authentication is delegated to the platform (kube-rbac-proxy sidecar or service mesh). The ClusterRoleBinding for ConfigMap access is cluster-scoped rather than namespace-scoped, which means the service account has ConfigMap CRUD permissions across all namespaces. In a multi-tenant environment, this is a potential privilege escalation vector if the service account token is compromised. The gRPC connections to model servers use `usePlaintext()`, meaning explainability computations send and receive model data without encryption -- though this is mitigated in RHOAI by disabling the explainer endpoints entirely.
