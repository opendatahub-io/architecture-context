## Purpose

**Short**: TrustyAI is a Quarkus-based Java service and library providing AI fairness metrics, drift detection, and model explainability for ML models served via ModelMesh and KServe on OpenShift AI.

**Detailed**: TrustyAI Explainability is a multi-module Java project that serves as the core fairness and explainability engine for Red Hat OpenShift AI. The primary deployable artifact is the `explainability-service`, a Quarkus 3.20.6.2 REST application that provides HTTP endpoints for computing fairness metrics (Statistical Parity Difference, Disparate Impact Ratio), drift detection (KS Test, Approximate KS Test, Fourier MMD, Meanshift), and local/global model explainers (LIME, SHAP, Counterfactual, TSSaliency, Partial Dependence Plots).

The service integrates with ML inference platforms through two payload ingestion mechanisms: a REST endpoint (`/consumer/kserve/v2`) for ModelMesh inference payloads, and a Knative CloudEvents consumer for KServe inference request/response events. It reconciles partial inference payloads into complete observations, stores them in configurable backends (PVC flat files, MinIO, or a relational database via Hibernate ORM), and exposes computed metrics to Prometheus via Micrometer gauges on a configurable schedule.

The RHOAI distribution profile disables explainer endpoints (SHAP, LIME, Counterfactual, TSSaliency, global explainers), retaining only fairness metrics and drift detection. The service is typically deployed per-namespace by the separate [TrustyAI Service Operator](https://github.com/trustyai-explainability/trustyai-service-operator), which manages lifecycle, configuration, and integration with the model serving infrastructure.

## Architectural Analysis

TrustyAI's architecture follows a scheduler-publisher pattern for metrics exposure. The `PrometheusScheduler` runs on a configurable interval (default 5s), iterating over registered metric requests, computing values against stored inference data, and publishing results as named Micrometer gauges (prefixed `trustyai_`). This design decouples metric computation from HTTP request handling, allowing Prometheus to scrape pre-computed values rather than triggering on-demand calculations.

The storage layer uses a strategy pattern with CDI conditional activation (`@LookupIfProperty`): `PVCStorage` for flat-file CSV on persistent volumes, `MinioStorage` for S3-compatible object storage, and `HibernateStorage` for relational databases (MariaDB/MySQL). The `DataSource` abstraction sits above storage, providing model-aware data access with schema metadata management. The service supports runtime migration between storage backends.

Payload ingestion is split by inference platform. ModelMesh payloads arrive as partial input/output pairs via the `/consumer/kserve/v2` REST endpoint, reconciled by `ModelMeshInferencePayloadReconciler`. KServe payloads arrive as CloudEvents via Knative Eventing, with separate `@Funq` handlers for request (`org.kubeflow.serving.inference.request`) and response (`org.kubeflow.serving.inference.response`) event types, reconciled by `KServeInferencePayloadReconciler`. Both reconcilers match input-output pairs by inference ID before persisting complete observations.

Feature gating is implemented via Quarkus `@EndpointDisabled` annotations controlled by profile-specific properties. The `rhoai` profile disables all explainer endpoints while keeping fairness and drift metrics enabled. This is a compile-time decision based on the active Quarkus profile, not a runtime toggle.

An init container using the OpenShift CLI (`oc`) creates a `model-serving-config` ConfigMap pointing the KServe payload processor URL at the TrustyAI service in the current namespace. This tightly couples deployment to the namespace where model serving runs and requires the service account to have ConfigMap write permissions (granted by the `trustyai-role` ClusterRole).

| Data storage | Per-namespace PVC or per-namespace database instance; data partitioned by model ID | Kubernetes (separate PVC per namespace) / Application (model ID partitioning) | Within a namespace, all models share the same storage; no per-user isolation |

| API scoping | All API responses scoped to local service instance's data (namespace-local) | Application | Per-namespace deployment inherently scopes data; no cross-namespace access possible |
