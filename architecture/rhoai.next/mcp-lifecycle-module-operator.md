## Purpose

**Short**: A Kubernetes module operator that manages the lifecycle of the MCP Lifecycle Operator operand within the ODH/RHOAI platform's modular architecture.

**Detailed**: The mcp-lifecycle-module-operator follows the ODH modular architecture pattern where the platform operator creates a cluster-scoped `MCPLifecycleOperator` custom resource, and this module operator reconciles it by deploying and managing the MCP Lifecycle Operator (MCPLO) as its operand. The operand itself manages MCPServer resources — Kubernetes-native representations of Model Context Protocol (MCP) servers.

The module operator embeds pre-rendered kustomize manifests for the operand and applies them via server-side apply (SSA) through the `odh-platform-utilities` deployer library. It handles the complete lifecycle: rendering manifests with platform-specific TLS configuration and image overrides, deploying operand resources, garbage-collecting stale resources, verifying operand deployment readiness, performing a conversion-health handshake (verifying stored MCPServer objects are convertible to the promoted v1beta1 API), and driving storage-version migration of stored MCPServer objects to v1beta1.

The operator integrates with the ODH platform by reading distribution metadata from a platform ConfigMap, reporting its version and the platform version back through status fields that the platform operator reads to track upgrade completion. It enforces a restricted network policy posture on the operand (deny-by-default ingress per ODH-ADR-Operator-0016) and propagates TLS configuration from the OpenShift APIServer's TLS profile.

## Architectural Analysis

This operator exhibits a two-tier controller pattern: the module operator (this repo) is a meta-operator that owns and deploys a second operator (the MCP Lifecycle Operator) as its operand. The module operator does not directly manage MCPServer or MCPGatewayBinding resources — those are the domain of the operand it deploys. This indirection means the module operator's RBAC is a superset of the operand's RBAC to satisfy Kubernetes RBAC escalation prevention: it must hold every permission it grants to the operand via the operand's ClusterRole.

The reconciliation flow has a carefully ordered sequence of gates. After applying operand manifests and verifying deployment readiness, a conversion-health check validates that stored MCPServer objects (originally stored at v1alpha1) are convertible to v1beta1 by listing them through the dynamic client, which forces the API server's conversion webhook to run. Only after this check passes does the operator advance `status.distribution` to signal upgrade completion to the platform operator. A durable `MCPServerConversionVerified` condition prevents the freshly rolled-out controller from skipping the check even if a previous (ungated) controller already advanced the distribution status during a rollout window.

The storage-version migration is a separate, non-blocking concern: it creates a `StorageVersionMigration` resource (provided by OpenShift's kube-storage-version-migrator) to re-encode stored MCPServer objects to v1beta1. This migration is deliberately excluded from operand readiness aggregation — a pending or failed migration never degrades the Ready condition. The migration includes self-healing with a bounded retry budget (5 attempts), after which it stops and requests manual intervention.

TLS configuration is dynamically resolved from the OpenShift APIServer's TLS profile (with hardened `Intermediate` defaults on non-OpenShift clusters) and injected into the operand's container as environment variables. The build uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS compliance, with an additional post-quantum crypto-policy stage (`DEFAULT:PQ`) in the Dockerfile.
