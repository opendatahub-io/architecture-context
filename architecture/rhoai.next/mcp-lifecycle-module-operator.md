## Purpose

**Short**: A Kubernetes module operator that manages the lifecycle of the MCP Lifecycle Operator as a deployable component within the ODH/RHOAI platform.

**Detailed**: The MCP Lifecycle Module Operator follows the ODH modular architecture pattern (v2 of the Onboarding Guide for ODH Operator Modules). It acts as a thin management layer: the platform operator (odh-operator / rhods-operator) creates a cluster-scoped `MCPLifecycleOperator` CR, and this module operator reconciles it by deploying the MCP Lifecycle Operator operand via server-side apply (SSA).

The module operator does not implement any MCP business logic itself. Its responsibilities are: (1) rendering and applying vendored operand manifests with runtime parameter injection (namespace, operand image, TLS settings), (2) garbage-collecting stale resources when the operand manifest set changes, (3) monitoring operand Deployment readiness and surfacing status conditions back to the platform, and (4) tearing down all owned resources when the CR's `managementState` is set to `Removed`. It also reads the cluster's TLS profile from the OpenShift `APIServer` CR and injects TLS configuration (minimum version, cipher suites) into the operand Deployment.

The operand it deploys is the [MCP Lifecycle Operator](https://github.com/opendatahub-io/mcp-lifecycle-operator), which manages `MCPServer` custom resources — the CRD for running Model Context Protocol servers in Kubernetes.

## Architectural Analysis

The MCP Lifecycle Module Operator exemplifies the ODH modular architecture pattern — a deliberately thin operator whose sole responsibility is lifecycle management of a single operand. This design separates platform concerns (when to deploy, what version, what namespace) from component concerns (what the MCP Lifecycle Operator actually does with MCPServer resources). The module operator has no knowledge of MCP protocol semantics; it only cares about rendering manifests, applying them, and confirming the operand Deployment is healthy.

The operand manifest vendoring strategy is noteworthy: rather than running kustomize at runtime, the manifests are pre-rendered via `make update-operand-manifests` (which clones the operand repo, runs its kustomize build, and copies the output to `internal/controller/resources/mcp-lifecycle-operator.yaml`). This 2167-line YAML file is embedded into the Go binary via `go:embed` and patched at runtime using manifestival transformers. The transformers inject: (1) the `platform.opendatahub.io/part-of` label for ownership tracking, (2) the target namespace, (3) the operand container image (from `RELATED_IMAGE_*` env var), and (4) TLS configuration (min version + cipher suites from the OpenShift APIServer TLS profile). This approach trades flexibility for reliability — the manifest set is deterministic and version-controlled, but requires a PR to update operand versions.

The garbage collection mechanism (using `odh-platform-utilities/pkg/controller/gc`) is sophisticated: it discovers all API resources in the cluster, lists objects matching the `platform.opendatahub.io/part-of: mcplifecycleoperator` label, and deletes any that are not in the current desired set. This handles manifest changes cleanly — if a resource is removed from the operand manifest, it gets cleaned up on the next reconciliation cycle rather than lingering as an orphan. The cache configuration in `cmd/main.go` is carefully scoped: namespace-scoped resources are restricted to the operator's own namespace, while cluster-scoped resources (ClusterRole, ClusterRoleBinding, CRD) are filtered by the managed-resource label to avoid caching every such object in the cluster.

The TLS integration is a good security pattern: the module operator reads the cluster-wide TLS profile from the OpenShift `APIServer` CR (or falls back to Intermediate profile defaults on non-OpenShift clusters), converts OpenSSL cipher names to IANA format using `library-go`, and injects the result as environment variables into the operand Deployment. This ensures the operand inherits the cluster's TLS policy without hardcoding cipher suites. The controller also watches the `APIServer` CR for changes and re-reconciles when the TLS profile is updated.

The platform version upgrade handshake (introduced in commit `d69b202`) reads a ConfigMap (`odh-mcplifecycleoperator-config`) to discover the platform version and includes it in the CR's `status.releases` list. This enables the platform operator to track which version of the module operator (and by extension, which operand version) is deployed, supporting coordinated platform upgrades.
