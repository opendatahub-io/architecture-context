## Purpose

**Short**: A Kubernetes module operator that manages the lifecycle of the MCP Lifecycle Operator as a component within the ODH/RHOAI platform.

**Detailed**: The MCP Lifecycle Module Operator follows the ODH modular architecture pattern where each platform component is managed by a dedicated module operator. The ODH platform operator creates a `MCPLifecycleOperator` custom resource, and this module operator reconciles it by deploying the MCP Lifecycle Operator operand via server-side apply (SSA).

The module operator embeds pre-rendered kustomize manifests for the operand (the MCP Lifecycle Operator itself) and applies them to the cluster with runtime transformations including namespace injection, image replacement, TLS configuration, and managed-resource labeling. It watches the `MCPLifecycleOperator` CR and owned resources (Deployments, Services, RBAC objects, CRDs) to detect drift and re-reconcile. When the CR's `managementState` is set to `Removed`, the operator garbage-collects all owned resources.

The operand it deploys -- the MCP Lifecycle Operator -- is a separate controller that manages `MCPServer` custom resources, which represent Model Context Protocol servers running in Kubernetes. This creates a two-tier operator architecture: platform operator -> module operator (this repo) -> operand (MCP Lifecycle Operator) -> user workloads (MCPServer instances).

## Architectural Analysis

The MCP Lifecycle Module Operator is a clean implementation of the ODH modular operator pattern. The two-tier architecture separates concerns: the module operator handles lifecycle management (deploy, upgrade, teardown) while the operand (MCP Lifecycle Operator) handles domain-specific logic (managing MCPServer CRs). This separation allows the platform operator to treat all components uniformly through the module operator interface.

The manifest management strategy is notable. Rather than using live kustomize rendering at runtime, the operator embeds pre-rendered manifests via `go:embed` (the `internal/controller/resources/mcp-lifecycle-operator.yaml` file, which is a single YAML stream containing all operand resources). These manifests are vendored from the upstream `mcp-lifecycle-operator` repo using `make update-operand-manifests`, which clones the operand repo and runs its kustomize build. At reconcile time, the `KustomizeProvider` applies runtime transformations using `manifestival`: namespace injection, image replacement (via `RELATED_IMAGE_*` env var), label injection (`platform.opendatahub.io/part-of`), and TLS environment variable injection. This approach eliminates the kustomize runtime dependency while preserving parameterization.

The TLS configuration is particularly well-designed. The operator reads the OpenShift `APIServer` CR's TLS profile (via `openshift/controller-runtime-common/pkg/tls`) to determine the cluster's minimum TLS version and cipher suites, then injects these as environment variables into the operand Deployment. On non-OpenShift clusters, it falls back to the Intermediate TLS profile defaults (TLS 1.2+). The cipher suite names are converted from OpenSSL to IANA format using `openshift/library-go`. This ensures the operand respects the cluster-wide TLS security policy without hardcoding cipher suites.

The garbage collection mechanism uses the `odh-platform-utilities` GC library. It identifies stale resources by comparing the desired state (rendered manifests) against live resources labeled with `platform.opendatahub.io/part-of: mcplifecycleoperator`, deleting any that are no longer in the desired set. This handles manifest evolution gracefully -- if a resource is removed from the operand manifests in an upgrade, the module operator will clean it up. The same GC mechanism handles the `Removed` management state, where all labeled resources are collected regardless of the desired set.

The controller watch setup is comprehensive: it watches the primary `MCPLifecycleOperator` CR plus all owned resource types (Deployments, Services, ServiceAccounts, Roles, RoleBindings, ClusterRoles, ClusterRoleBindings, CRDs), each filtered by the `platform.opendatahub.io/part-of` label. On OpenShift, it also watches `APIServer` CRs to re-reconcile when the cluster TLS profile changes. This ensures the operator reacts to both user-initiated changes and infrastructure drift.
