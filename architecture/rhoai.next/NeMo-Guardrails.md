## Purpose

**Short**: NeMo Guardrails is an open-source toolkit for adding programmable guardrails to LLM-based conversational systems, deployed as a FastAPI service that intercepts and validates LLM interactions.

**Detailed**: NeMo Guardrails provides a programmable safety layer for LLM applications. It implements input and output rails — configurable validation pipelines that inspect, filter, and transform messages flowing between users and LLM backends. The toolkit uses Colang, a domain-specific language with two runtimes (v1.0 and v2.x), to define guardrail logic as flows and actions.

The RHOAI distribution is a multi-hop fork (NVIDIA → TrustyAI → OpenDataHub → Red Hat Data Services) that adds Red Hat-specific integration: a Konflux-compatible container build with AIPCC base images, pre-baked ML models via modelcars, a fork-specific `/v1/guardrail/checks` endpoint for stateless guardrail evaluation, OpenTelemetry auto-instrumentation support via the entrypoint wrapper, and header forwarding for runtime LLM authentication in multi-tenant deployments.

The server exposes an OpenAI-compatible API surface (`/v1/chat/completions`, `/v1/models`) augmented with guardrail-specific endpoints (`/v1/checks`, `/v1/rails/configs`, `/v1/challenges`). Over 30 built-in guardrail library modules cover content safety, jailbreak detection, PII/sensitive data detection, fact-checking, hallucination detection, and integrations with third-party safety providers. A build-time profile system (`filter_guardrails.py`) selects between open-source and closed-source guardrail subsets.

## Architectural Analysis

NeMo Guardrails has a layered architecture centered on the `Guardrails` class, which dispatches to either the modern `IORails` engine (input/output rail pipelines evaluated through an engine registry) or the legacy `LLMRails` engine (full event-driven Colang pipeline). The choice is automatic based on configuration but defaults to `IORails` for new deployments. Both engines share `RailsConfig` as the user-facing configuration surface, loaded from YAML files that define models, rails, flows, and actions.

The Colang DSL is central to the guardrail logic: v1.0 provides a simpler flow model while v2.x adds richer state management and concurrent flow execution. Actions resolve through `ActionDispatcher`, and LLM access is abstracted behind a framework/provider layer supporting OpenAI-compatible clients and LangChain as alternative frameworks. Embedding providers (OpenAI, Azure OpenAI, SentenceTransformers, FastEmbed, NIM, Cohere, Google) power semantic similarity features used for topic detection and canonical form matching.

The fork introduces architectural patterns absent in upstream: (1) the header forwarding system uses context variables (`api_request_headers_var`) to propagate X-* headers from incoming requests to outgoing LLM calls, enabling runtime authentication without static API keys — the inbound `Authorization` header is never forwarded, while `X-Authorization` is mapped to the LLM provider's `Authorization`; (2) the entrypoint script conditionally wraps the server process with `opentelemetry-instrument` for automatic tracing when `OTEL_EXPORTER_OTLP_ENDPOINT` is set; (3) the HF classifier backend supports mTLS client authentication and custom CA bundles for connecting to model servers in enterprise environments.

A key architectural concern is the use of MD5 for content hashing in `utils.py` and `embeddings/cache.py`, with a FIPS-aware fallback to SHA-256 when MD5 is unavailable. This pattern is FIPS-tolerant but not FIPS-first — the code prefers MD5 and falls back only on failure. The `cryptography` library (v46.0.7) is present as a transitive dependency but no direct TLS configuration exists in the application code; TLS termination is delegated to the platform (OpenShift Routes/Ingress) or upstream proxy.

The container images use AIPCC CPU base images with six modelcar-sourced ML models baked in at build time (MiniLM, Snowflake Arctic Embed, spaCy en_core_web_lg, NLTK punkt, DeBERTa prompt injection, and Granite Guardian HAP). The runtime sets `HF_HUB_OFFLINE=1` and `TRANSFORMERS_OFFLINE=1` to prevent model downloads at runtime, ensuring air-gapped operation.
