## Purpose

**Short**: Reusable Tekton tasks, step actions, and pipelines that implement the RHOAI-specific CI/CD workflow within the Konflux build system.

**Detailed**: rhoai-konflux-tasks is a CI/CD infrastructure library that provides custom Tekton tasks, step actions, and pipeline definitions consumed by RHOAI component builds running on Konflux. The repository does not produce a deployable runtime service; instead, it defines build-time automation that other RHOAI component repositories reference via Tekton bundle resolvers or git resolvers in their `.tekton/` PipelineRun definitions.

The tasks cover the full lifecycle of an RHOAI Konflux build: pipeline initialization and metadata computation (`rhoai-init`), dependency prefetching for operator operand manifests, container image building with security scans (Clair, ClamAV, Snyk, SAST), image mirroring, operator and bundle build triggering across repositories, group testing orchestration, PR commenting with test results, Sealights instrumentation injection, and scan result evaluation. Two pipeline definitions (`container-build` and `container-build-remote`) compose upstream Konflux tasks with RHOAI-specific additions into complete build pipelines for single-arch and multi-arch container images.

The repository uses Renovate with Tekton manager support to keep upstream task bundle references automatically updated, and Pipelines-as-Code annotations in the `.tekton/` directory to manage its own CI via Konflux.

## Architectural Analysis

This repository functions as a shared CI/CD library rather than a deployable application. Its architecture follows the Tekton task composition pattern: each task is versioned independently (e.g., `rhoai-init/0.1`, `0.2`, `0.3`) and stored in a directory hierarchy that mirrors the Tekton Hub convention. Pipelines compose these custom tasks with upstream Konflux catalog tasks resolved via OCI bundles pinned to digest.

The `rhoai-init` task is central to the build workflow. It evolved through three versions: v0.1 added image output parsing and CPE ID computation; v0.2 introduced `pipeline-type` awareness for pull-request vs push builds and configmap-based Slack configuration; v0.3 added mandatory tag generation for PR builds. The CPE ID logic uses semantic version comparison to determine RHEL version targeting (RHEL 8 for versions below 2.20, RHEL 9 for 2.20+), which is a key versioning policy encoded directly in the task.

The `prefetch-operand-manifests-oci-ta` task is architecturally significant because it bridges the build system with the operator's component model. It clones the `RHOAI-Konflux-Automation` and `ODH-Build-Config` repositories, runs the `operator-processor` Python tool to process operand maps and manifest configs, then fetches individual component manifests via sparse git checkouts and stores them as trusted artifacts. This task creates a coupling between the build system and the operator's deployment topology.

The `evaluate-scan-results` task represents a policy enforcement point that is currently in report-only mode. It aggregates TEST_OUTPUT results from multiple scan tasks (Clair, ClamAV, Snyk, SAST shell/unicode checks, deprecated image check, RPM signature scan) and categorizes violations as gating or advisory. The code contains explicit comments about a planned transition to blocking mode, making this an intentional architectural decision to allow teams to address existing findings before enforcement.

Cross-repository orchestration is a notable pattern: `trigger-operator-build` triggers builds on the operator repo by posting commit comments; `trigger-bundle-build` dispatches GitHub Actions workflows on the ODH-Build-Config repo; and `trigger-group-testing` monitors all Konflux check runs on a PR and triggers group testing when all component builds complete. This creates an implicit dependency graph across the RHOAI build system that is not captured in any formal dependency manifest.

Security scanning of CI artifacts before external push is a consistent pattern across the step actions: `secure-git-push` and `secure-push-oci` both invoke `leaktk-scanner` to strip credentials and certificates before publishing artifacts to git repositories or OCI registries.
