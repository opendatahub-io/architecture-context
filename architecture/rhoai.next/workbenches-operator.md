## Purpose

**Short**: Kubernetes operator that manages the Workbenches component lifecycle — deploying and reconciling Kubeflow Notebook controllers, ODH notebook controller, and notebook image definitions for Open Data Hub and Red Hat OpenShift AI.

**Detailed**: The workbenches-operator is a module operator built with Kubebuilder v4 and controller-runtime. It owns the `Workbenches` cluster-scoped Custom Resource and reconciles the full Workbenches stack by rendering upstream kustomize manifests (kf-notebook-controller, odh-notebook-controller, and notebook ImageStreams) with platform-specific overlays and applying them via Server-Side Apply.

The operator acts as the single owner of the workbenches component within the Open Data Hub / RHOAI platform. It watches the `Workbenches` CR for spec changes, monitors a platform-managed ConfigMap (`odh-workbenches-config`) for distribution identity and version handshake signals, and tracks Deployment availability to compute a rich phase-based status (Pending → Initializing → Ready → Upgrading → Degraded → Failed). The operator supports both `Managed` and `Removed` management states, with full cleanup of all owned resources on removal.

In addition to the main reconciler, the operator hosts two mutating admission webhooks: a **notebook connection webhook** that validates and injects connection secrets (via `envFrom`) into Notebook pod specs based on the `opendatahub.io/connections` annotation, and a **hardware profile webhook** that injects resource requirements, node selectors, and tolerations from `HardwareProfile` CRs into Notebooks. Both webhooks enforce authorization checks (SubjectAccessReview) and provide graceful degradation on stale references.

## Architectural Analysis

The workbenches-operator represents a **module operator** pattern within the Open Data Hub platform architecture. Rather than being deployed via OLM as a standalone operator, it is embedded as a module managed by the platform orchestrator (rhods-operator or opendatahub-operator). The orchestrator creates the `Workbenches` CR and manages a sidecar ConfigMap (`odh-workbenches-config`) that carries distribution identity and version handshake signals. This two-phase handshake protocol — where the module reports `DistributionAligned` and `HandshakeComplete` in its status before being considered Ready — enables the orchestrator to coordinate multi-component upgrades across the platform.

The manifest rendering pipeline is notable for its approach to immutability. Upstream manifests are baked into the container image at `/opt/manifests` during build (fetched by `get_all_manifests.sh` from three upstream repos: kubeflow for kf-notebook-controller and odh-notebook-controller, and notebooks for ImageStreams). At reconcile time, the operator copies the entire manifest tree to a temp directory, patches kustomization files with the target namespace, injects runtime parameters (gateway URL, MLflow toggle, section title) into `params.env`, runs `kustomize build`, and applies the result via Server-Side Apply with `ForceOwnership`. This ensures the baked-in manifests stay immutable while allowing runtime parameterization.

The webhook architecture is a direct port from the monolithic opendatahub-operator, now scoped specifically to Notebook resources. The hardware profile webhook accesses `HardwareProfile` CRs as unstructured objects (avoiding an import dependency on the opendatahub-operator API types), and implements sophisticated merge-vs-replace logic when profiles change (clearing old scheduling settings before applying new ones). The connection webhook enforces a security boundary by performing SubjectAccessReview checks — ensuring the user creating/updating a Notebook actually has `get` permissions on the referenced secrets — which prevents privilege escalation through the webhook's elevated service account.

The TLS integration is architecturally significant. At startup, the operator bootstraps TLS configuration by reading the OpenShift APIServer's cluster-wide TLS profile, using it to configure cipher suites and minimum TLS version for both the metrics and webhook servers. A `SecurityProfileWatcher` (from `openshift/controller-runtime-common`) watches for TLS profile changes at runtime and triggers a graceful shutdown/restart to reload the new profile. On non-OpenShift clusters, the operator falls back to a hardened Mozilla Intermediate cipher set. This approach ensures the operator's TLS posture is always aligned with the cluster's security policy.

The cleanup logic is comprehensive and best-effort: on CR deletion or `Removed` management state, the operator iterates over all managed resource types (Deployments, ConfigMaps, Services, ServiceAccounts, Roles, RoleBindings, ImageStreams, ClusterRoles, ClusterRoleBindings, MutatingWebhookConfigurations, ValidatingWebhookConfigurations, CRDs) and deletes objects matching the `app.opendatahub.io/workbenches=true` component label. Errors are aggregated rather than short-circuiting, ensuring partial cleanup is possible even when some resource types are unavailable.
