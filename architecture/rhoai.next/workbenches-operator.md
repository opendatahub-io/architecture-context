## Purpose

**Short**: Kubernetes operator that reconciles a cluster-scoped `Workbenches` custom resource to deploy and manage the notebook controller stack (Kubeflow notebook controller, ODH notebook controller, and notebook manifests) on OpenShift.

**Detailed**: The workbenches-operator is a standalone module operator within the ODH/RHOAI platform orchestration model. It watches a singleton `Workbenches` CR (`default-workbenches`) and renders upstream Kustomize manifests — committed under `opt/manifests/` for hermetic builds — via the krusty engine, injecting `RELATED_IMAGE_*` environment variables and CR-derived parameters (`platform`, `gatewayDomain`, `mlflowEnabled`). Resources are applied using Server-Side Apply (SSA) with field manager `workbenches-operator`.

The operator manages three upstream operand stacks: the Kubeflow notebook controller (with OpenShift overlay), the ODH notebook controller, and notebook manifests (with platform-specific ODH or RHOAI overlays). It enforces drift reconciliation through `OwnerReferences` and `Owns()` watches on operand resources. Two mutating admission webhooks intercept `Notebook` resources to inject connection secrets and apply hardware profile settings (including Kueue integration for job scheduling).

The operator follows the platform ModuleStatus lifecycle model, reporting phase progression from `Pending` through `Ready`, with degradation detection when operand deployments regress. It integrates with the OpenShift cluster-wide TLS security profile, applying platform cipher/TLS-version settings to its metrics and webhook servers, and auto-detects the available webhook TLS provider (OpenShift service-CA, cert-manager, or none).

## Architectural Analysis

The workbenches-operator employs a layered architecture separating operator lifecycle management from operand manifest rendering. The central `WorkbenchesReconciler` acts as an orchestrator that reads the `Workbenches` CR spec, resolves the target applications namespace (from `APPLICATIONS_NAMESPACE` env or platform defaults), copies baked-in manifests to a temporary directory, renders them with platform-specific overlays and image parameter substitution, then applies the result via SSA.

A distinctive design choice is the **committed-manifest pattern**: upstream manifests are fetched at development time via `get_all_manifests.sh` and committed under `opt/manifests/`, then baked into the container image at build time. This enables fully hermetic builds suitable for Konflux and airgapped environments — the operator never fetches from GitHub at runtime. The `opt/manifest-sources.sh` file maps operand org/repo/ref entries per branch, with separate ODH and RHOAI source maps selected by `ODH_PLATFORM_TYPE`.

The webhook subsystem is architecturally notable for its **TLS provider auto-detection**: at startup, the operator probes Kubernetes API groups to determine whether OpenShift service-CA, cert-manager, or neither is available, configuring serving certs accordingly. A periodic retry (30s) handles resources that appear after startup. The operator also integrates with OpenShift's APIServer TLS security profile, fetching cipher/min-version settings and installing a watcher that triggers graceful shutdown on profile changes — ensuring TLS configuration stays aligned with cluster policy without requiring manual restarts.

The RBAC model carries broad cluster-level permissions because the operator must create, manage, and escalate (bind) operand ClusterRoles for the upstream notebook controllers and workspaces controller. The `manager-rbac-escalate-role` explicitly lists every upstream operand ClusterRole that the operator may need to bind, keeping escalation scoped rather than open-ended.

A current gap is the absence of a default-deny NetworkPolicy for the operator namespace (documented as a TODO in `config/manager/kustomization.yaml`, referencing CWE-284). Cross-pod communication within the operator namespace is currently unrestricted.
