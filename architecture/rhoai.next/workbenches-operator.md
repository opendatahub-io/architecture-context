## Purpose

**Short**: A Kubernetes operator that manages the lifecycle of workbenches (Kubeflow Notebooks) and their supporting controllers on the OpenDataHub and Red Hat OpenShift AI platforms.

**Detailed**: The workbenches-operator is a controller-runtime based Kubernetes operator that reconciles a cluster-scoped `Workbenches` Custom Resource to deploy and manage the notebook workbench stack. When the `Workbenches` CR is set to `Managed`, the operator renders upstream kustomize manifests (kf-notebook-controller, odh-notebook-controller, and platform-specific notebook ImageStreams) with parameter injection and applies them to the cluster via Server-Side Apply.

The operator serves as the component module for the workbenches vertical within the RHOAI/ODH modular architecture. It reads platform configuration from the `odh-workbenches-config` ConfigMap (projected by the orchestrator/rhods-operator), participates in a distribution version handshake protocol, and reports its status back through the `Workbenches` CR status subresource including phase, conditions, deployment availability, and release metadata.

In addition to manifest lifecycle management, the operator hosts two mutating admission webhooks: one that injects connection secrets into Notebook pods based on the `opendatahub.io/connections` annotation, and another that applies HardwareProfile resource requirements, node selectors, and tolerations to Notebooks based on the `opendatahub.io/hardware-profile-name` annotation. These webhooks intercept `kubeflow.org/v1 Notebook` CREATE and UPDATE operations.

## Architectural Analysis

The workbenches-operator follows the RHOAI modular operator pattern where a component-level operator owns a single vertical of functionality. Unlike the monolithic opendatahub-operator, this operator has a narrow scope: it manages exactly the notebook controller stack and notebook ImageStream definitions. The operator does not directly create workload infrastructure (no HTTPRoutes, no kube-rbac-proxy sidecars, no NetworkPolicies) — that responsibility falls to the upstream controllers it deploys (kf-notebook-controller and odh-notebook-controller). The operator's role is purely lifecycle management: render, apply, monitor, and report.

The manifest management approach is noteworthy. Rather than vendoring Go types or reimplementing upstream controller logic, the operator fetches raw kustomize manifests from `opendatahub-io/kubeflow` and `opendatahub-io/notebooks` repositories via `get_all_manifests.sh` and bakes them into the container image at `/opt/manifests/`. At reconcile time, the operator copies these manifests to a temporary directory, patches the kustomization namespace field, injects parameters via `params.env`, renders with the kustomize API, and applies via Server-Side Apply with `ForceOwnership`. This approach preserves upstream manifest fidelity while allowing platform-specific parameterization (gateway URL, MLflow toggle, image overrides). The trade-off is that the operator's RBAC must be a superset of everything the upstream manifests create — including CRDs, webhook configurations, and aggregated ClusterRoles requiring the `escalate` verb.

The distribution version handshake protocol (`odh-workbenches-config` ConfigMap → `status.distribution` → `status.releases[platform]`) is the mechanism by which the orchestrator coordinates upgrades across component operators. The operator will not report `Ready` until three conditions are met: (1) all Deployments have available replicas, (2) the distribution name/version aligns with what the orchestrator projected, and (3) the platform version handshake is complete. This three-phase readiness gate prevents the orchestrator from proceeding with the next component upgrade before the current component has fully stabilized.

The webhook architecture is well-isolated. The connection injection webhook performs strict security validation: it parses the `opendatahub.io/connections` annotation, verifies each referenced Secret exists in the same namespace as the Notebook, performs a SubjectAccessReview to confirm the requesting user has `get` permission on each Secret, and only then injects `envFrom` secretRef entries. The HardwareProfile webhook is more complex — it handles profile changes (clearing and reapplying scheduling settings), stale profile references (allowing updates with warnings when a referenced HardwareProfile is deleted), and container name matching to find the main notebook container in multi-container pods. Both webhooks use `failurePolicy: Fail`, meaning webhook unavailability blocks Notebook creation — a deliberate safety choice to prevent notebooks from being created without proper resource allocation or connection configuration.

The TLS bootstrap mechanism deserves attention. On startup, the operator fetches the OpenShift cluster-wide TLS profile from the `config.openshift.io/v1 APIServer` resource and configures its metrics and webhook servers accordingly. A `SecurityProfileWatcher` monitors for TLS profile changes and triggers a graceful shutdown + restart to reload the new profile. On non-OpenShift clusters, the operator falls back to Mozilla Intermediate cipher suite defaults with TLS 1.2 minimum. This is a security-conscious pattern that ensures the operator's TLS posture is always aligned with the cluster administrator's policy.
