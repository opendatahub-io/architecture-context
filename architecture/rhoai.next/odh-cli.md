## Purpose

**Short**: CLI tool and kubectl plugin for validating, diagnosing, migrating, and managing Red Hat OpenShift AI (RHOAI) deployments on Kubernetes clusters.

**Detailed**: odh-cli (`kubectl-odh` / `rhai-cli`) is a comprehensive command-line interface for RHOAI platform operators and administrators. It provides cluster health assessment, upgrade readiness validation (lint), automated migration actions for version transitions, workload backup, component lifecycle management, dependency tracking, log streaming, and event monitoring. The tool operates as a kubectl plugin using standard kubeconfig authentication and communicates exclusively with the Kubernetes API server.

The CLI also exposes all of its capabilities via the Model Context Protocol (MCP), allowing AI agents to invoke its tools programmatically. It bundles version-specific configuration data at compile time for offline/air-gapped operation of the lint command. The migration framework supports phased execution (pre-upgrade, post-upgrade, pre-enablement) with dry-run capability, hierarchical step recording, and structured output for CI/CD integration.

## Architectural Analysis

The odh-cli is architecturally a **platform management Swiss army knife** -- a single binary that consolidates diagnostics, migration automation, and operational tooling for RHOAI. Its design reflects several deliberate architectural choices worth noting.

**Command lifecycle consistency**: Every command follows a strict Complete() → Validate() → Run() lifecycle with AddFlags() for registration. This pattern enforces separation between flag parsing, client initialization, input validation, and execution. The pattern is enforced by the `Command` interface in `pkg/cmd/command.go` and consistently applied across all 13 commands. This makes the codebase predictable and new commands straightforward to add.

**Lint framework as a versioned policy engine**: The lint system is notable for its version-aware check framework. Checks implement `CanApply(target)` to declare which version transitions they apply to, and the `Target` struct carries both `CurrentVersion` and `TargetVersion` to distinguish between lint mode (current state validation) and upgrade mode (readiness assessment). The check registry uses glob pattern matching (`--checks "workloads/*"`) for selective execution. Sequential execution is a deliberate constraint to ensure deterministic output ordering for diff-based workflows. The framework registers 40+ checks across 5 categories (Platform, Component, Dependency, Workload, Service) with fluent builder APIs for composable validation logic.

**Migration framework with hierarchical recording**: The migration system uses an action/task/recorder pattern where each migration action produces a tree of steps with status tracking. The `StepRecorder` interface supports nested `Child()` calls for sub-step decomposition, and the `RootRecorder` builds a final `ActionResult` with recursive failure/skip detection. This is particularly sophisticated for a CLI tool and enables structured JSON/YAML output of migration progress for CI/CD integration. Phase detection (`DetectPhase()`) automatically determines whether to run pre-upgrade or post-upgrade actions based on the cluster's current version versus the target.

**FIPS compliance with a TLS gap**: The Konflux Dockerfile correctly sets `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for FIPS-compliant Go binaries. However, the TrustyAI metrics HTTP client (`pkg/migrate/actions/trustyai/metrics/http.go:60-63`) uses `InsecureSkipVerify: true`, which skips certificate validation. While the code documents this as intentional (matching `curl -sk` for in-cluster self-signed certs), it represents a deviation from strict FIPS posture. The `MinVersion: tls.VersionTLS12` setting is correct for FIPS compliance.

**MCP server as an integration surface**: The MCP (Model Context Protocol) integration is architecturally interesting -- it wraps all 12 CLI tools as MCP tool calls using a `toolAdapter` pattern that bridges the CLI's `Command` interface to MCP's `CallToolResult`. Each tool has explicit read-only/destructive annotations. The adapter clones `ConfigFlags` per invocation to preserve auth context across tool calls. This makes the CLI directly consumable by AI coding assistants for cluster troubleshooting.
