## Purpose

**Short**: CLI tool for diagnosing, auditing, and migrating Red Hat OpenShift AI (RHOAI) deployments on Kubernetes clusters.

**Detailed**: The odh-cli (shipped as `rhai-cli` in RHOAI containers) is a comprehensive command-line utility for RHOAI platform engineers and administrators. It provides three primary capabilities:

1. **Upgrade readiness assessment** (`lint`): A rules engine with 48 diagnostic checks that evaluates a running cluster's readiness for upgrade to a target RHOAI version. Checks span 5 categories — platform CRs, component configurations, dependency operators, service mesh/serverless state, and individual workloads (notebooks, inference services, pipelines, ray clusters, training jobs). Results are structured as Kubernetes-style CRs with severity levels (prohibited, blocking, advisory, informational).

2. **Automated migration actions** (`migrate`): An action framework with ~30 migration tasks organized into pre-upgrade and post-upgrade phases. Actions handle RHOAI 2.x→3.x transitions including workbench auth model migration (OAuth→RBAC), ModelMesh→RawDeployment conversion, embedded Kueue→RHBOK operator transition, AI Pipelines API version migration, TrustyAI data backup/restore, and RayCluster backup/migration. Each action has prepare (backup) and run (execute) stages with dry-run support.

3. **Cluster introspection** (`status`, `components`, `get`, `deps`, `events`, `logs`, `backup`): Read-only commands for inspecting platform health, component state, operator dependencies, Kubernetes events, pod logs, and exporting workload definitions. Also includes an MCP (Model Context Protocol) server that exposes all CLI commands as typed tools for AI agent integration.

## Architectural Analysis

The odh-cli is architected as a monolithic CLI binary with a highly modular internal structure. Each top-level command (`lint`, `migrate`, `status`, etc.) is implemented as a self-contained package under `cmd/` that delegates to a corresponding `pkg/` package. All commands follow a strict three-phase lifecycle: `Complete()` (populate options and create clients), `Validate()` (check invariants), and `Run(ctx)` (execute business logic). This pattern, borrowed from kubectl's plugin conventions, ensures consistent error handling and resource cleanup across the tool.

The lint engine is the tool's most sophisticated subsystem. It implements a registry of 48 diagnostic checks organized into 5 groups (dependency, service, platform, component, workload), each executed in a defined order. Checks use a fluent builder API (`ComponentBuilder`, `OperatorBuilder`, `WorkloadBuilder`, `DSCBuilder`, `DSCIBuilder`) that composes validation logic from reusable primitives. Results follow a Kubernetes CR convention with `apiVersion`, `kind`, `metadata`, `spec`, and `status` sections, including structured conditions with severity levels (`prohibited`, `blocking`, `advisory`, `informational`). This CR-style output is machine-parseable by downstream automation.

The migration framework follows an action registration pattern where each migration action implements an `Action` interface with `CanApply(version)` for version-gating and `Prepare/Run` tasks for two-phase execution. The RHBOK migration action is particularly complex — it performs RBAC preflight checks via `SubjectAccessReview`, backs up ClusterQueues and ConfigMaps, modifies the DataScienceCluster CR to switch from embedded Kueue to the standalone RHBOK operator, labels namespaces and workloads, and verifies the transition using exponential backoff polling. All destructive operations require interactive confirmation unless `--yes` is passed, and `--dry-run` is supported throughout.

The MCP server integration is a notable architectural choice — it wraps every CLI command as a typed MCP tool using an adapter pattern that clones kubeconfig flags and maps tool arguments to cobra command flags. This enables AI agents (Claude, etc.) to invoke the full CLI capabilities programmatically. The server supports both stdio (for direct agent integration) and SSE (for networked use, bound to localhost only). Input validation in the MCP layer includes path traversal protection for backup output directories.

A significant security consideration is the TrustyAI metrics HTTP client, which uses `InsecureSkipVerify: true` for TLS. This is documented as intentional for in-cluster self-signed routes (matching the original `curl -sk` behavior from the bash-based predecessor), but it does disable certificate chain validation. The build is FIPS-compliant at the check-payload level (dynamic linking, strictfipsruntime, OpenSSL in the base image), with no non-FIPS crypto algorithms (MD5, RC4, DES) used anywhere in the codebase.
