## Purpose

**Short**: CLI tool and kubectl plugin for interacting with, diagnosing, linting, and migrating Red Hat OpenShift AI (RHOAI) deployments on Kubernetes.

**Detailed**: odh-cli (distributed as `rhai-cli` in RHOAI builds) is a comprehensive command-line interface for OpenShift AI platform operations. It functions both as a standalone CLI and as a kubectl plugin (`kubectl odh`), providing cluster-aware commands for validating installations, assessing upgrade readiness, executing version migrations, backing up workloads, and diagnosing platform health issues.

The CLI implements a rich set of operational commands: `lint` validates current cluster state and assesses upgrade readiness against a target version; `diagnose` runs a 4-step diagnostic flow (triage, investigate, correlate, report); `migrate` manages version-aware cluster migrations with backup, prepare, and run phases; `backup` exports workloads and their dependencies as portable YAML; `status` shows platform health; `deps` manages operator dependency lifecycle via OLM; and `components`, `get`, `logs`, `events` provide resource introspection.

A notable architectural feature is the built-in Model Context Protocol (MCP) server (`mcp serve`), which exposes all CLI commands as typed tool calls accessible to MCP-capable AI agents (Claude, GPT, Cursor). The MCP server supports both stdio and SSE transports, enabling programmatic access to the full operational surface from agent-driven workflows.

## Architectural Analysis

odh-cli follows a clean command-adapter architecture: a Cobra command tree dispatches to package-level `Command` structs that implement a three-phase lifecycle (`Complete` / `Validate` / `Run`). This pattern is mirrored in the MCP server, where `toolAdapter` wrappers bridge MCP tool calls to the same `Command` implementations, ensuring behavioral parity between interactive CLI and agent-driven usage.

The client layer in `pkg/util/client` is a facade over multiple Kubernetes client types: dynamic, discovery, typed clientset, metadata, OLM, and controller-runtime. This multi-client approach is deliberate -- the CLI needs dynamic access for arbitrary GVRs (backup, get), typed access for RBAC pre-flight checks (SelfSubjectAccessReview), OLM access for operator lifecycle management, and controller-runtime for diagnostic health checks. Authentication is inherited from the kubeconfig credential chain with RBAC pre-flight validation before privileged operations.

The lint subsystem is architecturally significant: it implements a pluggable check framework with glob-based selectors, severity levels (prohibited, critical, warning, info), and version-aware gating. Checks span four categories -- components, services, dependencies, and workloads -- enabling comprehensive pre-upgrade validation.

The error handling system (`pkg/util/errors`) classifies all errors into structured categories with exit codes, retriable flags, and user-facing suggestions. It handles TLS certificate errors, DNS failures, authentication issues, and Kubernetes API errors through exhaustive classification tables, enabling both human-readable and machine-readable error reporting.

The TrustYAI metrics migration code uses `crypto/tls` with `MinVersion: tls.VersionTLS12` but sets `InsecureSkipVerify: true` for in-cluster route access to self-signed certificates. This is an intentional trade-off documented via a nolint directive, matching the original `curl -sk` behavior for cluster-internal routes.
