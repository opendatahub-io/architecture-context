## Purpose

**Short**: Asynchronous dispatch processor for llm-d that pulls batch inference requests from message queues, gates dispatch based on system capacity, and forwards requests to llm-d-router or another inference gateway.

**Detailed**: The Async Processor (AP) is a composable component in the llm-d inference platform that enables efficient processing of latency-insensitive LLM workloads. It functions as an asynchronous worker that consumes jobs from a message broker (Redis sorted sets, Redis pub/sub channels, or GCP Pub/Sub topics) and dispatches them to an inference gateway, decoupling job submission from immediate execution. This allows workloads such as bulk summarization, product classification, and near-realtime sentiment analysis to fill "slack" capacity on GPU accelerators without impacting real-time serving.

The processor implements a sophisticated flow control system with 11 dispatch gate types (including Prometheus-based saturation detection, Redis-backed quotas, endpoint scraping, and tier-priority admission), configurable worker pools with per-pool gating, and pluggable request merge policies that support multi-queue/multi-tenant deployments. The system uses a "Bring Your Own Queue" (BYOQ) design where prioritization, routing, retries, and scaling are decoupled from the message queue implementation.

The AP is deployed via a Helm chart as a single-replica Kubernetes Deployment. It provides comprehensive observability through 15 Prometheus metrics, OpenTelemetry distributed tracing, and Grafana dashboard integration. The producer library (a separate Go module) provides a programmatic API for submitting requests and retrieving results, enabling integration into batch processing pipelines.

## Architectural Analysis

The Async Processor implements a clean separation between message transport and dispatch logic through its plugin-based architecture. The `pipeline.Flow` interface abstracts the message queue backend, while `pipeline.Gate` and `pipeline.RequestMergePolicy` interfaces abstract flow control and multi-queue scheduling respectively. This means the same dispatch gates and worker pool configuration work identically across Redis and GCP Pub/Sub backends, and new queue backends can be added without touching the worker or gate logic.

The flow control system is notably sophisticated for what is fundamentally a queue consumer. The 11 gate types form a composable hierarchy — `composite` gates combine multiple inner gates with minimum-budget semantics, `wait-on-refuse` gates convert immediate rejections into in-memory parking, and `tier-priority-admission` gates implement three-way admission verdicts based on saturation, request tier, and quota classification. The `prometheus-budget` gate cascades two independent metric sources (EPP flow control queue size as primary, vLLM running requests as fallback) with automatic failover. The `endpoint-scrape` gate enables serverless monitoring by scraping raw `/metrics` endpoints directly, eliminating the need for a dedicated Prometheus server in simple deployments. This gate architecture allows fine-grained multi-tenant capacity management where different queues can have independent saturation thresholds and quota policies.

The multi-module Go repository structure (`api/`, `producer/`, `pipeline/`, root) enforces clean dependency boundaries. The `api` module has zero external dependencies, making it safe to import in any producer client. The `producer` module depends only on `api` and `go-redis`, keeping the client footprint minimal. The `pipeline` module depends only on `api`, defining interfaces that the root module implements. This layering prevents transitive dependency pollution — a producer client never pulls in Prometheus, OpenTelemetry, or GCP Pub/Sub libraries.

The cancellation mechanism uses a clever two-token pattern: when a request is submitted, a random 16-byte token is stored in `request-active:{ID}` with a TTL matching the request deadline. When cancellation is requested, a Lua script atomically copies this token to `request-cancel:{ID}` with a 7-day TTL. During dequeue, the processor checks both keys — if the cancellation marker exists and its token matches the active token, the request is dropped. This design handles race conditions between submission, cancellation, and processing without distributed locks.

A notable architectural decision is that the Helm chart creates no Kubernetes Service resource. The processor is a pure consumer — it pulls from queues and pushes to inference gateways. The only inbound connections are Prometheus metric scrapes via PodMonitor. This means the processor has zero attack surface for inbound HTTP traffic, reducing the security perimeter to outbound connections (inference gateway, message broker, Prometheus, OTLP collector). The pod security context enforces non-root execution, read-only root filesystem, and all capabilities dropped.

The request body transform plugin system (`pkg/asyncworker/transform/`) enables the processor to handle multi-modal inference endpoints. The `gcs_uri_multipart` plugin converts JSON payloads containing signed GCS URLs into `multipart/form-data` requests, with preflight validation that checks signed URL expiry against the request deadline before dispatch. This pattern avoids putting raw media bytes on the message broker while supporting endpoints like Whisper transcription that expect file uploads.
