## Purpose

**Short**: Asynchronous dispatch processor that pulls batch inference requests from a message queue, gates dispatch based on system capacity, and forwards them to an inference gateway (llm-d-router).

**Detailed**: The Async Processor (AP) is a Go service that enables efficient processing of latency-insensitive LLM inference workloads. It functions as an asynchronous worker that pulls jobs from a message queue (Redis Sorted Set, Redis Pub/Sub, or GCP Pub/Sub), applies configurable flow-control gating based on system capacity metrics, and dispatches them via HTTP to an inference gateway such as `llm-d-router`. This decouples job submission from immediate execution, allowing users to perform tasks such as bulk summarizations, product classification, or sentiment analysis without blocking real-time traffic.

The processor supports configurable worker pools with merge policies (random-robin or tier-priority), request body transforms via a plugin system, and sophisticated dispatch gating that integrates with Prometheus metrics, Redis budget keys, and endpoint scraping. It implements deadline-aware retry logic with exponential backoff and jitter, graceful shutdown with configurable drain timeout, and comprehensive observability through Prometheus metrics and OpenTelemetry tracing. The architecture follows a "Bring Your Own Queue" (BYOQ) principle — all prioritization, routing, retries, and scaling are decoupled from the message queue implementation.

## Purpose

**Short**: Asynchronous inference request pipeline for RHOAI that bridges Redis message queues with LLM Inference Gateways, enabling decoupled request submission, retry with exponential backoff, and batched result delivery.

**Detailed**: llm-d-async implements an asynchronous inference pipeline for the llm-d ecosystem within Red Hat OpenShift AI. The Go-based component acts as a message broker between external request submitters and the Inference Gateway (IGW), using Redis pub/sub channels and sorted sets as its transport layer. It subscribes to one or more configurable request queues in Redis, forwards inference requests to the IGW via HTTP (default path `/v1/completions`), and publishes results back through a Redis result channel. A retry mechanism backed by a Redis sorted set implements exponential backoff (1s-30s) for failed requests, with atomic Lua-script-based pop operations to prevent duplicate processing. The component deploys alongside a vLLM model server (e.g., Qwen3-0.6B with GPU acceleration) that provides OpenAI-compatible inference endpoints. Configuration supports both single-queue and multi-queue topologies via inline JSON or file-based queue configuration, with each queue mapping to a distinct inference objective and IGW endpoint path.

## Data Flows

- **Request ingestion:** External producers publish JSON-serialized `InternalRequest` messages to one or more Redis request queues via pub/sub. The `requestWorker` goroutine subscribes to each configured queue, deserializes incoming messages, and dispatches them to per-queue Go channels. Queue configuration is supplied via `--redis.queues-config` (inline JSON), `--redis.queues-config-file`, or individual flags (`--redis.request-queue-name`, `--redis.igw-base-url`, `--redis.request-path-url`, `--redis.inference-objective`).
- **Inference forwarding:** Each queue's channel feeds requests to the inference pipeline, which forwards them to the Inference Gateway (IGW) at the configured base URL and request path (default `/v1/completions`). The IGW is the `gateway-api-inference-extension` component that routes requests to vLLM model servers.
- **Result delivery:** Inference results flow back through the `resultChannel` (buffered to 64). The `resultWorker` batches up to 32 results and publishes them to the Redis result queue (`--redis.result-queue-name`, default `result-queue`) using pipelined `PUBLISH` commands to reduce Redis round-trips.
- **Retry flow:** Failed requests enter the `retryChannel` → `addMsgToRetryWorker` adds them to a Redis sorted set (`--redis.retry-queue-name`, default `retry-sortedset`) with a score of `current_unix_time + backoff_duration_seconds` → `retryWorker` polls the sorted set with exponential backoff (1s-30s, resetting on successful drain) using an atomic Lua script (`ZRANGEBYSCORE` + `ZREM`, batch size 100) to prevent duplicate processing → retried messages are re-dispatched to their original request queue channel.
- **Graceful shutdown:** On context cancellation, the result worker drains all remaining messages from the result channel. The retry worker requeues undelivered messages back to the sorted set. Redis operations during shutdown use `context.Background()` with up to 3 retries and exponential backoff (100ms, 200ms, 400ms) to maximize flush success before SIGKILL.
- **Model server:** The vLLM model server container runs alongside, serving the configured model (e.g., Qwen3-0.6B) with GPU acceleration (`nvidia.com/gpu`). Its `/health` and `/v1/models` endpoints are used exclusively as Kubernetes health probes with no authentication.

## Architectural Analysis

The Async Processor follows a clean pipeline architecture: message source → merge policy → worker pool → gate → dispatch → result/retry. Each stage is abstracted behind well-defined Go interfaces (`Flow`, `Gate`, `RequestMergePolicy`, `InferenceClient`), enabling the queue backend, gating strategy, and merge policy to be swapped independently. This composability is the system's key architectural strength — a single binary serves Redis Pub/Sub, Redis Sorted Set, GCP Pub/Sub, and GCP Pub/Sub with per-topic gating, all configurable at deploy time via CLI flags or Helm values.

The flow control system is particularly sophisticated. The `GateFactory` routes configuration-driven gate type strings to concrete implementations: `prometheus-saturation` and `prometheus-budget` gates query live Prometheus metrics (pool saturation or EPP flow control queue depth) to compute dispatch budgets in [0.0, 1.0]; `redis` gates read a single Redis key for external budget signaling; `redis-quota` gates enforce per-attribute concurrency or sliding-window rate limits; `local-max-concurrency` gates cap in-flight requests locally; `endpoint-scrape` gates hit raw `/metrics` endpoints with optional dynamic capacity from pod counts. These can be composed via `composite` gates (minimum budget) and wrapped with `wait-on-refuse` (converting refusal to deferral) or `tier-priority-admission` (class/tier-aware admission with 6-level priority). The cascade metric source with automatic fallback from EPP queue size to vLLM running requests ensures gating degrades gracefully when the preferred metric source is unavailable.

The multi-module repository structure (`api/`, `pipeline/`, `producer/`) provides clean API boundaries. The `api` module has zero external dependencies and defines the message contract; the `pipeline` module depends only on `api` and defines orchestration interfaces; the `producer` module is a standalone client library for submitting requests and retrieving results. This enables external services to import just `producer` or `api` without pulling in the full processor dependency tree. The `producer` module implements token-based request cancellation using Redis keys (`request-active:{ID}` and `request-cancel:{ID}`), enabling cooperative cancellation without modifying the message queue.

Security follows a defense-in-depth pattern appropriate for an internal service. The Konflux Dockerfile builds with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` on UBI 9, ensuring FIPS-compliant crypto via OpenSSL. The application-level TLS configuration enforces `MinVersion: tls.VersionTLS12` and supports full mTLS (CA cert + client cert/key) for communication with the inference gateway. The Helm chart deploys with hardened security context: read-only root filesystem, non-root user, all capabilities dropped, `RuntimeDefault` seccomp profile. Redis credentials are injected from Kubernetes Secrets via the `REDIS_URL` environment variable, avoiding hardcoded credentials. The `InsecureSkipVerify` option exists but is explicitly documented as dev/test only.

One notable design decision is the absence of a Kubernetes Service object in the Helm chart — the processor exposes health (8081) and metrics (9090) as pod ports only, with metrics scraped by PodMonitor rather than via a Service. This is appropriate since the processor is a consumer, not a server: it pulls work from queues rather than receiving inbound traffic. The only inbound connections are Kubernetes health probes and Prometheus scraping, both of which work with pod-level targeting.

## Architectural Analysis

llm-d-async follows a pipeline architecture with three concurrent worker goroutines — `requestWorker`, `retryWorker`, and `resultWorker` — coordinated through Go channels and Redis data structures. The use of Redis pub/sub for request ingestion and result delivery decouples producers and consumers, enabling horizontal scaling of both sides independently. The sorted-set-backed retry mechanism provides durable retry semantics with time-based scoring, and the atomic Lua script for pop-and-remove (`ZRANGEBYSCORE` + `ZREM` in a single `EVAL`) prevents duplicate retry processing under concurrent access, which is critical when multiple llm-d-async replicas share the same Redis instance.

The component integrates tightly with the `gateway-api-inference-extension` (Inference Gateway) ecosystem, importing its logging utilities (`sigs.k8s.io/gateway-api-inference-extension/pkg/epp/util/logging`) and targeting the IGW as its primary downstream HTTP dependency via the `--redis.igw-base-url` flag. The multi-queue configuration system allows a single llm-d-async instance to multiplex across multiple inference objectives and IGW endpoints, each with its own request path, queue name, and inference objective identifier. This maps directly to multi-model or multi-tenant serving scenarios where different queues serve different models or priority tiers.

The `golang.org/x/oauth2` dependency in `go.mod` indicates OAuth2-based authentication is available for outbound HTTP calls (likely to the IGW or Kubernetes API), though the specific token acquisition flow is configured at runtime and not visible in the analyzed source files. Redis connection authentication is similarly delegated to the `RedisOptions()` function. The vLLM modelserver probe endpoints (`/health`, `/v1/models`) are intentionally unauthenticated — they are Kubernetes health probes accessed only by the kubelet within the cluster network.

The result batching strategy (up to 32 messages per Redis pipeline call) and the exponential backoff on retry polling (1s-30s with reset on successful drain) demonstrate attention to Redis connection efficiency, avoiding the 1Hz fixed-rate polling that would otherwise hammer Redis with `ZRANGEBYSCORE` calls during idle periods. The graceful shutdown sequence is carefully ordered: the drain context is cancelled, result and retry workers flush remaining messages with `context.Background()` fallback and up to 3 retries, and undelivered retry messages are atomically requeued to prevent message loss during rolling deployments.
