## Purpose

**Short**: Asynchronous queue-based dispatch processor that drains batch inference requests from a message broker, gates dispatch based on real-time system capacity, and forwards requests to llm-d-router or another inference gateway.

**Detailed**: The Async Processor (AP) is a composable component within the llm-d inference platform designed for workloads where latency is not the primary constraint — bulk summarization, product classification, sentiment analysis, and other tasks with SLOs measured in minutes rather than milliseconds. It functions as an asynchronous worker that continuously pulls jobs from a message queue (Redis sorted-sets, Redis pub/sub channels, or GCP Pub/Sub topics), evaluates a configurable dispatch-gate pipeline to determine whether the inference pool has spare capacity, and then forwards qualifying requests to the llm-d-router or a model server endpoint via HTTP.

The dispatch-gate system is the core architectural differentiator. Gates operate at two levels — queue-level (admission gating per request source) and pool-level (shared capacity enforcement across all queues routed to a worker pool). Budget gates query Prometheus or scrape raw metrics endpoints for pool saturation, while admission gates enforce per-attribute quotas (rate limiting or concurrency caps) via Redis. Combinator gates compose these primitives. A tiered priority system with six strict lanes (reserved/overflow x interactive/async/batch) enables fine-grained workload prioritization.

The codebase is structured as a Go workspace with four modules: the root module (the processor binary), `api/` (message wire formats and client interfaces), `pipeline/` (flow abstractions and gate interfaces), and `producer/` (Redis-based message producer library). The processor integrates with the broader llm-d ecosystem through the Gateway API Inference Extension, sharing flow-control metric definitions with the EPP (Endpoint Picker Plugin) for coordinated capacity-aware dispatch.

## Architectural Analysis

The Async Processor follows a pipeline architecture centered on decoupling job submission from inference execution via a message broker. The design is deliberately broker-agnostic: the `pipeline.Flow` interface abstracts transport-specific concerns (Redis sorted-set polling, Redis pub/sub subscription, GCP Pub/Sub subscription) behind a uniform channel-oriented API. Each transport implementation produces `pipeline.EmbelishedRequestMessage` values onto per-queue Go channels, which a configurable merge policy then combines into per-pool merged channels consumed by worker goroutines.

The gate system implements a layered capacity-management architecture. The `GateFactory` constructs gates from declarative JSON configuration, supporting a rich combinator pattern — `composite` gates aggregate multiple budget or admission gates, while `wait-on-refuse` converts broker-redelivery semantics into in-memory parking. This composability enables sophisticated capacity policies without code changes: for example, a pool gate wrapping `redis-leased-rate` inside `wait-on-refuse` implements external rate control with bounded jittered backoff, matching the `llm-d.ai/v1alpha1` wire contract for drain-limit leases.

Observability is deeply integrated. The processor exposes a comprehensive Prometheus metric set under the `llm_d_async` subsystem, covering the full request lifecycle (ingestion, dispatch, success, shedding, retries, deadline expiry), latency distributions (inference latency, queue residence time), capacity gauges (queue depth, in-flight requests, broker backlog), and gate diagnostics (budget values, metric source availability, decision counters). OpenTelemetry distributed tracing propagates W3C trace context across the queue boundary, enabling end-to-end visibility from producer through broker to inference response.

The TLS configuration supports mutual TLS for outbound inference requests, with a minimum of TLS 1.2 enforced at the application level. The `InsecureSkipVerify` option is flagged as dev/test only and suppressed by gosec nolint directives. The Konflux build uses `GOEXPERIMENT=strictfipsruntime` with `CGO_ENABLED=1` for dynamic linking against OpenSSL, and targets `ubi9/ubi-minimal-pqc` (post-quantum cryptography variant) as the runtime base image.

A notable architectural decision is the absence of CRDs or operator patterns despite importing `controller-runtime`. The framework is used solely for its metrics server (with optional authentication/authorization via `kube-rbac-proxy` filters), signal handling, and structured logging — the processor is a long-running service, not a reconciliation controller.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-tenant auth; relies on producer-side authentication before messages reach the broker | Application (producer) / Platform | The processor trusts messages on the queue — any producer with broker access can submit requests claiming any tenant identity |
| Data storage | Per-queue message isolation; shared result queue/topic | Application (queue partitioning) | Results from different tenants share a single result queue unless per-queue `result_queue_name` overrides are configured |
| Network traffic | No per-tenant NetworkPolicy; single Deployment serves all queues | Kubernetes namespace isolation | No intra-queue network segmentation |
| Compute & resources | Worker pool partitioning via `worker_pool_id`; per-attribute quota via `redis-quota` gate | Application | Tenants sharing a worker pool compete for workers; `redis-quota` enforces rate limits or concurrency caps per tenant attribute |
| Configuration & secrets | Shared ConfigMap and Secret across all tenants | Kubernetes | Single Redis/Valkey connection shared across all queues |
| API scoping | Per-queue fairness identity header (`x-llm-d-inference-fairness-id`) stamped on dispatched requests | Application | Fairness enforcement delegated to downstream llm-d-router flow control; processor itself does not enforce fair scheduling beyond tier-priority lane ordering |
