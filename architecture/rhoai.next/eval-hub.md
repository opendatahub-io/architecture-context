## Purpose

**Short**: EvalHub is a lightweight REST API service for orchestrating LLM evaluations across multiple backend frameworks, tracking experiments via MLflow, and running natively on OpenShift.

**Detailed**: EvalHub provides a centralized evaluation orchestration platform for Large Language Model (LLM) assessment within the Red Hat OpenShift AI ecosystem. It exposes a versioned REST API (`/api/v1`) for managing evaluation jobs, benchmark collections, and evaluation providers. Evaluation providers — such as lm-evaluation-harness, RAGAS, Garak, GuideLLM, LightEval, and others — are declared as YAML configuration files and can be extended via a "Bring Your Own Framework" (BYOF) pattern using the eval-hub-sdk.

The service supports two runtime modes: a Kubernetes mode where evaluations run as K8s Jobs with sidecar containers for credential proxying and result export, and a local mode for development where evaluations run as subprocesses. In cluster mode, the eval-runtime-sidecar runs alongside each evaluation job pod, proxying requests to eval-hub, MLflow, OCI registries, and model endpoints with automatic credential injection. Results can be exported to MLflow as experiment artifacts or to OCI registries as evaluation cards. The service is managed on-cluster by the TrustyAI Service Operator via an `EvalHub` custom resource.

EvalHub also ships an MCP (Model Context Protocol) server (`evalhub-mcp`) that exposes evaluation tools, resources, and prompts for LLM integration, enabling AI agents to submit evaluations, poll status, and discover providers programmatically.

## Architectural Analysis

EvalHub follows a multi-binary, single-image architecture pattern where one container image (`odh-eval-hub-rhel9`) ships four Go binaries — the API server, runtime sidecar, init container, and MCP server — selected at deployment time via Kubernetes `command:` overrides. This reduces image maintenance overhead but means all components share the same dependency surface and security profile.

The evaluation execution model uses a **hub-and-spoke pattern**: the central eval-hub API creates Kubernetes Jobs that run evaluation framework adapters (Python, via the eval-hub-sdk). Each Job pod contains three containers: an init container (`eval-runtime-init`) that downloads test data from S3, the evaluation adapter (e.g., lm-evaluation-harness, RAGAS, Garak), and the sidecar proxy (`eval-runtime-sidecar`). The sidecar's role is critical — it acts as a transparent reverse proxy that injects credentials appropriate to each target service (SA tokens for eval-hub, bearer tokens for MLflow, OCI challenge-response for registries, and ref-token resolution for model endpoints). This design keeps credential management out of the evaluation SDK and centralizes auth logic in the sidecar.

The credential injection system in the sidecar is notably sophisticated. It supports a "ref-token" pattern where Bearer tokens ending in `:ref` trigger a secret cache lookup, resolving API keys and endpoint URLs from Kubernetes secret mounts. This enables multi-service credential injection without exposing credentials to the evaluation framework adapter. Token caching uses atomic operations with configurable TTL (default 5m) to minimize filesystem I/O for Kubernetes projected service account tokens.

Tenant isolation is implemented at the storage layer using header-based identity. In cluster mode, kube-rbac-proxy sits in front of eval-hub and injects `X-Tenant` and `X-User` headers after RBAC validation. The storage layer then scopes all queries to the tenant — system-provisioned resources (providers, collections shipped with the image) are visible to all tenants, while user-created resources are scoped. In local mode, identity enforcement is bypassed entirely.

The configuration system uses a layered approach: YAML config files (shipped with the image in `config/`) are the base, environment variables override specific fields via `env_mappings`, and Kubernetes secrets are mapped to config fields via `secrets.mappings`. A filesystem watcher monitors `config/providers/` and `config/collections/` directories for changes and hot-reloads provider/collection definitions without restart. This enables the TrustyAI Service Operator to update evaluation provider configurations via ConfigMap mounts.

The MCP server (`evalhub-mcp`) represents a forward-looking integration pattern — it wraps the eval-hub REST API as MCP tools, resources, and prompts, enabling AI agents to orchestrate evaluations programmatically. The MCP server supports three transports (stdio for local development, Streamable HTTP for production, and legacy HTTP+SSE for older clients) and can optionally enforce authentication via kube-rbac-proxy headers. The completion system caches provider/benchmark/collection ID lists for 30 seconds to reduce API calls during interactive use.
