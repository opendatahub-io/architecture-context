## Purpose

**Short**: Lightweight REST API service for orchestrating LLM evaluations across multiple backends, tracking experiments via MLflow, and exposing evaluation capabilities via the Model Context Protocol (MCP).

**Detailed**: EvalHub is the evaluation orchestration engine for Red Hat OpenShift AI. It provides a versioned REST API (`/api/v1`) that allows users to create, monitor, and cancel evaluation jobs against LLM models using pluggable evaluation frameworks such as lm-evaluation-harness, RAGAS, Garak, GuideLLM, LightEval, and MTEB. The service routes evaluation requests to framework-specific "adapter" containers and tracks experiments via optional MLflow integration.

In Kubernetes deployments, EvalHub is managed by the TrustyAI Service Operator via the `EvalHub` custom resource (`trustyai.opendatahub.io/v1alpha1`). Evaluation jobs run as Kubernetes Jobs with a three-container pod pattern: an init container (`eval-runtime-init`) that downloads test data from S3, the evaluation adapter container that runs the actual benchmark, and a sidecar container (`eval-runtime-sidecar`) that proxies traffic between the adapter and upstream services (EvalHub API, MLflow, OCI registries, and model endpoints) with credential injection and token caching.

EvalHub also includes an MCP server (`evalhub-mcp`) that exposes evaluation capabilities to AI agents via the Model Context Protocol, providing tools for submitting evaluations, monitoring jobs, and discovering providers, as well as resources for browsing providers, benchmarks, collections, and job results.

## Architectural Analysis

EvalHub follows a clean multi-binary architecture where a single container image (`Dockerfile.konflux`) produces four binaries from separate `cmd/` entry points. This design minimizes image sprawl while supporting distinct runtime roles: the primary API server, a reverse-proxy sidecar, an S3-downloading init container, and an MCP protocol server. The selection of which binary runs is determined by the Kubernetes pod spec's `command` override, a pattern that keeps the container image immutable across roles.

The sidecar proxy (`eval-runtime-sidecar`) is architecturally central to the Kubernetes runtime model. Rather than having evaluation adapter containers directly access upstream services (MLflow, OCI registries, model endpoints), all traffic is routed through the sidecar. This creates a single point for credential injection, token caching, TLS termination, and request ID propagation. The sidecar's route-matching logic uses URL prefix matching to determine the destination (EvalHub API, MLflow, OCI, or default model endpoint), and each destination has its own HTTP client with independent TLS configuration, timeout settings, and authentication mechanisms. The token caching layer (5-minute TTL with atomic pointer swap) avoids re-reading Kubernetes ServiceAccount tokens and file-based bearer tokens on every request.

The credential injection mechanism for model endpoints deserves special attention. The sidecar supports "ref tokens" — Bearer tokens of the form `Bearer api-key:ref` or `Bearer kfp_sa_token:ref` — where the suffix `:ref` signals that the token value should be resolved from the in-memory secret cache (populated at startup from mounted Kubernetes secrets). This indirection allows evaluation adapters to reference credentials symbolically without the actual secret values being passed through the adapter code. When no Authorization header is present, the sidecar falls back to injecting the Kubernetes ServiceAccount token, ensuring that adapters always have authenticated access to model endpoints. Error handling uses a sentinel header (`X-Model-Cred-Error`) to signal credential resolution failures, preventing malformed requests from reaching upstream.

The storage layer demonstrates thoughtful multi-tenancy design. Every SQL operation is scoped through `WithTenant()` and `WithOwner()` methods that add tenant/owner predicates to queries. This scoping is enforced at the storage interface level, meaning handlers cannot accidentally bypass tenant isolation. However, the isolation is purely application-level — there is no database-level row security or schema separation. The same database serves all tenants, relying on correct query construction. The storage layer supports both SQLite (for development) and PostgreSQL (for production) through a driver abstraction, with optional OpenTelemetry instrumentation that wraps the `database/sql` driver.

The MCP server (`evalhub-mcp`) represents a forward-looking integration point for AI agent workflows. It implements the full MCP specification with tools, resources, prompts, and completions. The tool set (submit, cancel, status, discover) maps directly to the most common evaluation API operations, while resources provide browsable access to the full data model. The three prompts (`edd_workflow`, `evaluate_model`, `compare_runs`) encode domain-specific evaluation guidance that helps AI agents use the evaluation system effectively. The MCP server supports three transport modes and can run alongside kube-rbac-proxy for authenticated deployment, making it suitable for both local development and cluster deployment.

The observability stack is comprehensive. EvalHub uses OpenTelemetry for distributed tracing, metrics, and log export, with conditional setup that avoids overhead when disabled. Prometheus metrics are exposed on a separate server (port 8081) in cluster mode, preventing metrics scraping from interfering with API traffic. Application-level metrics track job lifecycle events (created, cancelled, failed), benchmark errors, and HTTP request patterns. Every request gets a transaction ID (X-Global-Transaction-Id) that propagates through all downstream calls, enabling end-to-end trace correlation from the initial API request through sidecar proxying to upstream services.
