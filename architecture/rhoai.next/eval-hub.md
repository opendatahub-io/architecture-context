## Purpose

**Short**: A lightweight REST API service for orchestrating LLM evaluations across multiple backends, with MCP server support for AI agents, running natively on OpenShift.

**Detailed**: eval-hub is a Go-based evaluation orchestration platform that routes LLM evaluation requests to frameworks such as lm-evaluation-harness, RAGAS, Garak, and GuideLLM. It provides a REST API for managing evaluation jobs, providers (evaluation backends), and collections (evaluation presets), backed by SQL storage (PostgreSQL in production, SQLite for development). Experiment tracking is integrated through MLflow.

In an OpenShift cluster deployment, API requests arrive through kube-rbac-proxy which handles authentication and authorization, injecting `X-User` and `X-Tenant` headers for identity. The API server creates Kubernetes Jobs for evaluation runs; each job pod includes an init container (for downloading test data from S3, Git, or HuggingFace), a provider adapter container (the evaluation framework), and a sidecar container that proxies model inference, MLflow tracking, OCI registry, and API callback traffic. A separate MCP (Model Context Protocol) server exposes eval-hub functionality to AI agents via stdio or HTTP transports. Prometheus metrics are served on a dedicated port (8081) to allow scraping without authentication.

## Architectural Analysis

eval-hub follows a job-orchestration architecture where the central API server acts as a control plane that creates and monitors Kubernetes Jobs for each evaluation run. This decouples evaluation execution from the API server, allowing evaluations to run with their own resource profiles and failure isolation. The sidecar pattern is used extensively: every evaluation pod includes an eval-runtime-sidecar that acts as a reverse proxy, mediating all outbound traffic from the evaluation adapter container to model endpoints, MLflow, OCI registries, and back to the eval-hub API. This centralizes TLS configuration, authentication token management (with configurable caching), and observability instrumentation for job pods.

The multi-tenancy model is enforced at two levels: the kube-rbac-proxy boundary performs authentication and RBAC authorization, while the application layer implements tenant-scoped SQL queries using a `tenant_id` column on all core tables (evaluations, collections, providers). In local/development mode, the identity gate is bypassed, allowing unauthenticated access. This conditional enforcement pattern is security-relevant for deployment configuration.

The codebase has strong FIPS awareness: the Konflux Dockerfile uses `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` for dynamic linking against system OpenSSL, and the application code includes runtime FIPS detection (`/proc/sys/crypto/fips_enabled`) that blocks `InsecureSkipVerify` when FIPS mode is active. All HTTP servers configure TLS with MinVersion 1.2 and MaxVersion 1.3.

The configuration system uses a sophisticated layered approach with Viper: configuration file → environment variable overrides → secret file overrides. A file watcher enables hot-reload of provider and collection definitions without service restart. The service supports two database backends (PostgreSQL via pgx, SQLite via modernc.org/sqlite), with the database choice transparent to the application through a storage abstraction layer.

OpenTelemetry integration is comprehensive, covering traces, metrics, and logs across all components (API server, sidecar, and adapter containers), with OTLP/gRPC export to a collector. The MCP server, built on the `github.com/modelcontextprotocol/go-sdk`, provides an independent interface to eval-hub that operates behind the same kube-rbac-proxy authentication as the REST API.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy for inbound auth; X-User/X-Tenant headers for identity | Kubernetes (kube-rbac-proxy) + Application | Identity gate bypassed in local mode; no in-process TokenReview or SAR |
| Data storage | SQL tenant_id column on evaluations, collections, providers tables; queries filter by tenant | Application (SQL WHERE clauses) | Application-enforced, not Kubernetes-enforced; a SQL bug could leak cross-tenant data |
| Network traffic | No NetworkPolicy manifests in repo | Not enforced by this component | NetworkPolicy managed externally by operator/platform |
| Compute & resources | HardwareProfile CR per evaluation; Kueue LocalQueue for job scheduling | Kubernetes (ResourceQuota, Kueue) | Resource isolation delegated to platform; eval-hub itself does not create quotas |
| Configuration & secrets | Per-namespace secrets for test data and MLflow tokens; job-level ConfigMaps | Kubernetes (namespace scoping) | Secrets are namespace-scoped via job creation in tenant namespace |
| API scoping | All API queries include tenant_id filter; jobs created in tenant namespace | Application + Kubernetes | System providers/collections are shared across tenants (read-only) |
