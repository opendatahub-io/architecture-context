## Purpose

**Short**: REST-to-gRPC reverse proxy that translates KServe V2 REST Predict Protocol requests into gRPC V2 Predict Protocol calls for ModelMesh Serving inference endpoints.

**Detailed**: The rest-proxy component is a lightweight Go service built on [gRPC-Gateway](https://github.com/grpc-ecosystem/grpc-gateway) that acts as a protocol translation layer between RESTful HTTP clients and gRPC-based model inference servers. It enables clients that speak the KServe V2 REST Predict Protocol to interact with backend inference services (such as ModelMesh Serving) that only implement the gRPC V2 Predict Protocol.

The proxy accepts JSON-encoded inference requests over HTTP, performs custom marshaling/unmarshaling of tensor data (including multi-dimensional array flattening, BYTES/base64 encoding, and raw binary content handling), converts them into protobuf gRPC messages, forwards them to a co-located gRPC inference endpoint (typically on `localhost:8033`), and translates the gRPC response back to JSON for the REST client. It supports both plaintext and TLS-encrypted connections to the upstream gRPC service.

In the RHOAI deployment model, rest-proxy runs as a sidecar container within ModelMesh Serving pods, configured via the `restProxy.image` field in the `model-serving-config` ConfigMap. It is not independently deployed or exposed — it sits behind the same Service that fronts the ModelMesh pod.

## Architectural Analysis

The rest-proxy is architecturally simple by design — it is a single-purpose protocol translator that bridges the REST and gRPC worlds for the KServe V2 inference protocol. The entire application consists of approximately 400 lines of handwritten Go code (in `proxy/`) plus ~600 lines of generated protobuf gateway code (in `gen/`). This minimalism is a strength: the component has a small attack surface, few dependencies, and straightforward failure modes.

The custom JSON marshaling layer (`CustomJSONPb`, `transformRequest`, `transformResponse`) is the most complex part of the codebase. It handles edge cases that the standard gRPC-Gateway marshaler cannot: multi-dimensional tensor array flattening/nesting, raw binary tensor content decoding (little-endian byte array splitting with 4-byte size delimiters), base64-encoded BYTES tensors, and FP16 type rejection (explicitly unsupported with a TODO). The response transformation converts protobuf `InferTensorContents` and `RawOutputContents` into flat JSON arrays with proper type mapping. This custom marshaling is essential because the KServe V2 REST protocol allows nested JSON arrays matching tensor shape, while the gRPC protocol uses flat repeated fields.

A notable architectural detail is the `InsecureSkipVerify` toggle (`REST_PROXY_SKIP_VERIFY` env var). While this exists for development/testing scenarios where the co-located gRPC server uses self-signed certificates, it represents a configurable security weakening that should be disabled in production. The proxy's TLS handling has two independent dimensions: (1) client-facing TLS for the HTTP listener (controlled by `MM_TLS_KEY_CERT_PATH`/`MM_TLS_PRIVATE_KEY_PATH`), and (2) upstream gRPC TLS (controlled by `REST_PROXY_USE_TLS`). Both default to plaintext, relying on the enclosing pod's service mesh (Istio mTLS) for transport security.

The Konflux build pipeline demonstrates RHOAI's multi-architecture commitment: the Tekton PipelineRun builds for `linux/x86_64`, `linux/ppc64le`, `linux/s390x`, and `linux-m2xlarge/arm64`, matching the upstream GitHub Actions build matrix. The critical difference between the Konflux and upstream Dockerfiles is FIPS compliance: the Konflux build uses `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime -tags strictfipsruntime` (dynamic linking with FIPS crypto), while the upstream build uses `CGO_ENABLED=0` (static linking, pure Go crypto). The Konflux build also uses `ubi9/ubi-minimal` as the runtime base (which includes OpenSSL), versus `ubi9/ubi-micro` upstream.

The `controller-runtime` dependency (v0.14.1) is used solely for its `zap` structured logging package — no Kubernetes API interaction, reconciliation, or controller functionality is present. This is a lightweight usage that could theoretically be replaced with a direct `go.uber.org/zap` import to reduce the dependency footprint, though the current approach aligns with the broader KServe ecosystem's conventions.
