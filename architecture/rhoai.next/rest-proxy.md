## Purpose

**Short**: REST-to-gRPC reverse proxy that translates KServe V2 REST inference requests into gRPC calls for ModelMesh Serving backends.

**Detailed**: The rest-proxy component is a lightweight Go service that uses the gRPC-Gateway framework to create a reverse proxy translating RESTful HTTP API calls into gRPC messages. It enables clients to send inference requests using the KServe V2 REST Predict Protocol to inference platforms (specifically ModelMesh Serving) that natively speak the gRPC V2 Predict Protocol.

The proxy is deployed as a sidecar container within ModelMesh Serving pods. It listens for HTTP REST requests on a configurable port (default 8008/TCP), translates them to gRPC messages following the `grpc_predict_v2.proto` specification, and forwards them to a localhost gRPC endpoint (default port 8033/TCP). The proxy handles complex tensor data marshalling and unmarshalling, supporting multiple data types (BOOL, INT8-64, UINT8-64, FP16, FP32, FP64, BYTES) with both structured JSON and raw binary tensor formats. It also supports optional TLS for both the REST-facing listener and the gRPC backend connection.

The proxy is built and shipped through Konflux CI as part of RHOAI, with FIPS-compliant crypto enabled via `GOEXPERIMENT=strictfipsruntime`. It supports multi-architecture builds targeting x86_64, arm64, ppc64le, and s390x.

## Purpose

**Short**: gRPC-to-REST reverse proxy sidecar that translates KF Serving Predict V2 REST API calls into gRPC calls to a co-located ModelMesh inference runtime.

**Detailed**: rest-proxy is a lightweight Go service built on grpc-gateway v2 that runs as a sidecar container alongside ModelMesh serving runtime pods. It accepts incoming HTTP/REST requests conforming to the KF Serving Predict V2 inference protocol (model metadata and model inference endpoints) and translates them into gRPC calls forwarded to the inference runtime on localhost port 8033. ## Data Flows

1. **Inference request (REST to gRPC)**: An external client sends an HTTP POST to `/v2/models/{model_name}/infer` on port 8008. The grpc-gateway runtime deserializes the JSON body into a `ModelInferRequest` protobuf message. The proxy forwards the message as a gRPC `ModelInfer` call to `localhost:8033` (the co-located ModelMesh inference runtime). The gRPC response (`ModelInferResponse`) is serialized back to JSON via a custom marshaler that omits unpopulated fields, and returned to the HTTP client.
2. **Model metadata request**: An external client sends an HTTP GET to `/v2/models/{name}`. The grpc-gateway translates it to a gRPC `ModelMetadata` call to the backend. The response includes model name, versions, platform, and input/output tensor metadata.
3. **TLS negotiation (optional)**: When `MM_TLS_KEY_CERT_PATH` and `MM_TLS_PRIVATE_KEY_PATH` are set, the HTTP listener serves HTTPS. When `REST_PROXY_USE_TLS=true`, the gRPC client connection to the backend uses TLS credentials (with optional certificate verification skip via `REST_PROXY_SKIP_VERIFY`).

## Architectural Analysis

The rest-proxy is a focused, single-purpose component that bridges the gap between REST and gRPC inference protocols. Its architecture is deliberately minimal: a single Go binary using the well-established gRPC-Gateway framework to generate reverse proxy code from a protobuf service definition. The design choice to use gRPC-Gateway rather than a hand-written translation layer means the REST-to-gRPC mapping is declarative (defined in `grpc_predict_v2.proto` via `google.api.http` annotations) and automatically kept in sync with the proto specification.

The custom marshaling layer (`proxy/marshaler.go`, `proxy/bytes.go`, `proxy/request.go`) is the most architecturally significant part of the codebase. Rather than relying on gRPC-Gateway's default JSON marshaling, the proxy implements `CustomJSONPb` which intercepts both request decoding and response encoding. For requests, it performs custom tensor data unmarshalling that handles nested arrays, base64-encoded BYTES tensors, and multi-dimensional tensor flattening. For responses, it transforms gRPC `ModelInferResponse` messages into a REST-friendly format, converting raw binary output contents back into typed arrays. This custom marshaling is necessary because the KServe V2 REST protocol allows flexible tensor data representations (flat arrays, nested arrays, base64 strings) that don't map directly to protobuf's wire format.

A notable security observation is that the proxy itself implements no authentication or authorization. When deployed in RHOAI, authentication is provided externally by the platform's ingress infrastructure (kube-rbac-proxy sidecars in RHOAI 3.x, or oauth-proxy in 2.x). The proxy's TLS configuration has a potential concern: `InsecureSkipVerify` can be enabled via environment variable (`REST_PROXY_SKIP_VERIFY`), and no `MinVersion` is set on the TLS configuration, meaning TLS 1.0/1.1 are theoretically possible (though Go defaults to TLS 1.2 minimum). In a sidecar deployment where the gRPC connection is on localhost, this is low-risk, but it's worth noting for security audits.

The Konflux Dockerfile diverges from the upstream Dockerfile in important ways: it uses `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` for FIPS compliance (upstream uses `CGO_ENABLED=0` with static linking), and it uses `ubi9/ubi-minimal` as the runtime base instead of `ubi9/ubi-micro`. This is because FIPS-compliant Go binaries require dynamic linking to OpenSSL, which needs glibc and OpenSSL libraries present in the runtime image -- `ubi-micro` is too minimal for this.

The `controller-runtime` dependency in `go.mod` is used exclusively for its `zap` logging package, not for any Kubernetes controller functionality. This is a heavyweight dependency for just logging -- the component could potentially use `go.uber.org/zap` directly to reduce its dependency footprint.

## Architectural Analysis

The rest-proxy is a single-purpose sidecar container that implements the KF Serving Predict V2 REST-to-gRPC translation pattern. It is deployed as a sidecar alongside the ModelMesh serving runtime pod, enabling REST clients to interact with gRPC-only inference runtimes without modification.

The architecture is deliberately minimal: the entire proxy consists of a single `main.go` file plus generated protobuf/grpc-gateway code. The `grpc_predict_v2.proto` file defines the KF Serving Predict V2 inference protocol (`GRPCInferenceService`) with six RPCs, of which two (`ModelMetadata` and `ModelInfer`) have HTTP bindings via `google.api.http` annotations. The remaining four RPCs (`ServerLive`, `ServerReady`, `ModelReady`, `ServerMetadata`) are gRPC-only health and metadata endpoints with no REST mapping — they are accessible only through the gRPC interface on the backend runtime, not through the rest-proxy.

The proxy uses `grpc.WithBlock()` for its backend connection, meaning it will block at startup until the gRPC connection to `localhost:8033` is established. This is appropriate for a sidecar pattern where the proxy and runtime share a pod lifecycle, but means the proxy's readiness is coupled to the inference runtime's availability.

The `controller-runtime` dependency in `go.mod` is used only for its `zap` logging package (`sigs.k8s.io/controller-runtime/pkg/log/zap`), not for any controller or operator functionality. The rest-proxy is not a Kubernetes operator and does not watch or manage any Kubernetes resources.

The Konflux Dockerfile builds with `GOEXPERIMENT=strictfipsruntime` and `-tags strictfipsruntime` with `CGO_ENABLED=1`, indicating FIPS-compliant crypto for the Go binary. The runtime base image is `ubi9/ubi-minimal`. The `InsecureSkipVerify` option in the TLS configuration (controlled by `REST_PROXY_SKIP_VERIFY`) is a potential FIPS concern for environments requiring strict certificate validation.
