## Purpose

**Short**: Kubernetes operator that declaratively provisions and manages a complete observability stack (metrics, traces, logs, dashboards) for OpenShift AI / Open Data Hub.

**Detailed**: odh-observability is a controller-runtime operator that watches a singleton cluster-scoped `Monitoring` custom resource (`services.platform.opendatahub.io/v1alpha1`) and dynamically provisions an observability stack tailored to the prerequisite operators present on the cluster. It manages six subsystems: Prometheus metrics collection via MonitoringStack and ThanosQuerier (Cluster Observability Operator), distributed tracing via TempoMonolithic or TempoStack (Tempo Operator), telemetry pipelines via OpenTelemetry Collector (OpenTelemetry Operator), dashboarding via Perses (Perses Operator), alerting via PrometheusRules, and cluster log forwarding via ClusterLogForwarder (Loki/Logging Operators).

The operator uses an embedded Go template pattern with Server-Side Apply (SSA) to render and apply resources. Because the `Monitoring` CR is cluster-scoped but manages namespace-scoped resources, it cannot use standard OwnerReferences for garbage collection; instead, it uses label-based ownership (`platform.opendatahub.io/part-of=monitoring`) to track and garbage-collect stale resources. A mutating admission webhook conditionally injects scrape labels onto ServiceMonitor and PodMonitor resources in opted-in namespaces, gating injection on both the namespace label and the Monitoring CR's management state.

## Architectural Analysis

The operator's design centers on a single `MonitoringReconciler` that uses a declarative template-driven model: each subsystem is implemented as an "action function" that checks whether the prerequisite CRDs exist on the cluster and, if so, collects Go template sources from `//go:embed` resources. All template sources are rendered against a unified data map derived from the `Monitoring` CR spec, cluster TLS profile (fetched from the OpenShift APIServer resource), RELATED_IMAGE environment variables, and dynamically-resolved API versions (e.g., Perses v1alpha2 probing). The rendered resources are then applied in a single SSA batch via `odh-platform-utilities`'s deploy library with caching and apply ordering.

A notable security pattern is the TLS profile propagation: the operator reads the cluster-wide `APIServer` TLS security profile, resolves it to concrete min-version and cipher-suite strings via `openshift/library-go`, and injects these into kube-rbac-proxy and prom-label-proxy deployments. This ensures the observability proxies conform to the cluster's configured TLS posture (Intermediate by default, with TLS 1.0/1.1 floored to TLS 1.2).

The webhook is conditionally enabled via the `--enable-webhook` flag and requires cert-manager for TLS certificate provisioning. It intercepts CREATE and UPDATE operations on `monitoring.coreos.com/v1` PodMonitor and ServiceMonitor resources, injecting the `monitoring.opendatahub.io/scrape=true` label when the target namespace opts in and the Monitoring CR is in Managed state. This label selects which monitors the MonitoringStack's Prometheus instances scrape.

Network isolation is enforced through controller-managed NetworkPolicies: the collector monitoring ingress policy is the sole ingress gate for collector pods, permitting Prometheus scraping on `:8889`/`:8890` and OTLP ingestion on `:4317`/`:4318` restricted to the monitoring namespace. Separate policies guard the Prometheus instance, Prometheus proxies, Korrel8r, and Perses operator access.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy with SubjectAccessReview on both cluster and namespace proxies | Kubernetes RBAC | Cluster proxy grants cluster-wide metrics view; namespace proxy restricts to caller's namespace |
| Data storage | Shared MonitoringStack Prometheus instance; namespace filtering via prom-label-proxy | Application (prom-label-proxy) | Prometheus stores all tenants' metrics; isolation is query-time via label injection, not storage-time |
| Network traffic | NetworkPolicy per component (collector, Prometheus, proxies, Korrel8r, Perses); OTLP ingestion restricted to monitoring namespace | Kubernetes NetworkPolicy | NetworkPolicy enforcement depends on cluster CNI supporting it |
| Compute & resources | Shared collector and Prometheus instances; resource limits set via template defaults | Kubernetes resource limits | No per-tenant ResourceQuota; noisy-neighbor risk across tenants sharing the collector |
| Configuration & secrets | Per-namespace opt-in via namespace label; TLS secrets per service via service-CA | Kubernetes / OpenShift service-CA | Namespace opt-in label is not RBAC-protected by default |
| API scoping | Namespace proxy enforces `--label=namespace` filter; cluster proxy provides unfiltered access for admin use | prom-label-proxy | Users with cluster-monitoring-view can access all metrics via the cluster proxy Route |
