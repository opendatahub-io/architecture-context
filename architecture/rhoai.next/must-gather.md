**Detailed**: The `must-gather` component is a container image used with `oc adm must-gather` (on OpenShift) or as a Kubernetes Job (on non-OpenShift platforms like AKS, EKS, CKS) to collect diagnostic information from Red Hat OpenShift AI clusters. The tool detects the Kubernetes distribution at runtime (OpenShift, AKS, EKS, CKS) and adjusts its collection strategy accordingly. On OpenShift it uses `oc adm inspect` for namespace-level data collection; on non-OpenShift platforms it implements a `kubectl`-based equivalent (`kubectl_inspect`) that auto-discovers all API resources, collects pod logs, and gathers cluster-scoped resources. Component-specific gathering can be invoked in isolation via the `COMPONENT` environment variable, or the default `all` mode runs all component gatherers in parallel. The tool also collects Helm release information, Gateway API resources, Istio/Sail operator state, cert-manager certificates, and observability stack configuration.

## Purpose

**Short**: must-gather is a diagnostic data collection tool that gathers logs, resource definitions, and cluster state from Red Hat OpenShift AI (RHOAI) and Red Hat AI Inference (RHAII) deployments for troubleshooting and support case analysis.

**Detailed**: The must-gather image is invoked via `oc adm must-gather` on OpenShift or as a Kubernetes Job on non-OpenShift platforms (AKS, CKS, EKS). It extends the OpenShift base `ose-must-gather` image with component-specific collection scripts that enumerate RHOAI platform CRDs, namespace resources, pod logs, Helm release values, and cluster-scoped objects across all managed components.

The tool supports 15 individually selectable RHOAI components (dashboard, kserve, dsp, workbench, kuberay, kueue, kfto, modelregistry, trustyai, feastoperator, llamastack, mlflow, sparkoperator, maas, llm-d) via the `COMPONENT` environment variable. When run without a component filter on OpenShift, it collects all components in parallel. On non-OpenShift Kubernetes platforms, it defaults to llm-d collection only, with optional modules for workload-variant-autoscaler (WVA) and batch-gateway collection.

The collection scripts also gather dependency operator state (cert-manager, Sail/Istio, LeaderWorkerSet), Gateway API resources, Istio networking and security resources, Prometheus Operator monitoring resources, and detailed node information. The output directory structure follows the `oc adm must-gather` conventions, enabling integration with standard Red Hat support tooling. Multi-platform builds (x86_64, ppc64le, s390x, arm64) are produced via Konflux CI.

## Architectural Analysis

The must-gather component follows a hierarchical dispatch pattern where the main `gather.sh` script acts as an orchestrator. It first detects the Kubernetes distribution using node metadata heuristics (kernel version for CKS, provider ID prefix for AKS/EKS, OpenShift infrastructure API for OCP), then branches between OpenShift-specific and xKS-specific collection strategies. On OpenShift, it leverages the built-in `oc adm inspect` command which handles namespace-level resource serialization, pod log collection, and event gathering in a single operation. On non-OpenShift platforms, the `xks_util.sh` library implements an equivalent `kubectl_inspect` function that auto-discovers all API resource types via `kubectl api-resources` and iterates over them, collecting YAML representations and pod logs in parallel.

Component-specific collection is modular: each component has a dedicated `gather_*.sh` script that defines the CRD resource types it cares about, uses `get_all_namespace` to discover which namespaces contain those resources, and then calls `run_mustgather` (OpenShift) or `run_k8sgather` (xKS) to collect them. When no specific component is selected, all component gatherers run in parallel as background processes with PID tracking for error reporting. This parallel execution model significantly reduces collection time on large clusters. The `common.sh` library also collects a default set of Gateway API and Istio resources (`gateways`, `httproutes`, `grpcroutes`, `envoyfilters`, `destinationrules`) for every namespace inspected, reflecting the RHOAI 3.x ingress architecture.

The LLM-D collection path (`llm-d/gather_llmd.sh`) is notably more complex than other component gatherers. It runs dependency collection scripts (cert-manager, Sail/Istio, LeaderWorkerSet) in parallel, collects Gateway API Inference Extension resources (`inferencepools`, `inferenceobjectives`), and supports optional sub-components (WVA autoscaler via `ENABLE_WVA`, batch gateway via `ENABLE_BATCH_GATEWAY`). The observability collection (`gather_o11y.sh`) adapts to the monitoring stack -- Azure Managed Prometheus on AKS versus self-hosted kube-prometheus-stack elsewhere. This xKS awareness makes must-gather the most cross-platform component in the RHOAI ecosystem, supporting OpenShift, AKS, EKS, and CKS from a single codebase.

A significant design decision is the inclusion of `helm` and `kubectl` binaries directly in the image. The `helm` binary (v4.1.4) is checked into the repository via Git LFS, making the build hermetic but coupling the tool version to the repository. The `kubectl` binary (v1.33.3) is extracted from Red Hat's `ose-cli-rhel9` image in a multi-stage build for the Konflux Dockerfile, while the upstream Containerfile downloads it from `dl.k8s.io` at build time. The Tekton pipeline configuration builds multi-architecture images (x86_64, ppc64le, s390x, arm64), ensuring must-gather works across all supported RHOAI architectures.

## Architectural Analysis

The must-gather tool follows the standard OpenShift must-gather pattern: a container image that, when invoked via `oc adm must-gather`, runs collection scripts that enumerate cluster resources and write them to a structured directory tree. The output is then copied out of the pod by the `oc adm must-gather` framework. The RHOAI must-gather extends this pattern significantly by adding 15 component-specific collection scripts and a complete xKS (non-OpenShift Kubernetes) fallback path.

The architecture is organized as a hierarchical dispatch system. The main `gather.sh` entrypoint first detects the Kubernetes distribution using `xks_util.sh` (checking `infrastructures.config.openshift.io`, kernel version, provider ID, and OS image to distinguish OCP, AKS, CKS, and EKS). It then selects `oc` or `kubectl` as the primary CLI tool. On OpenShift, it collects platform-wide namespaces (`redhat-ods-operator`, `redhat-ods-applications`, `rhods-notebooks`, `redhat-ods-monitoring`, `rhoai-model-registries`, `openshift-ingress`, `kuadrant-system`, `rhai-gitops`) and platform CRs before dispatching to component scripts. On xKS, it skips OpenShift-specific resources and defaults to llm-d collection only.

A notable design decision is the parallel execution model for OpenShift "all components" collection. All 13 component gather scripts are launched as background processes with PIDs tracked in an associative array, enabling concurrent resource collection across components. Failed components are tracked and reported in the summary rather than aborting the entire collection. The llm-d path similarly parallelizes dependency operator collection (cert-manager, sail, lws). This parallel approach significantly reduces total collection time on clusters with many deployed components.

The xKS support path (`xks_util.sh` and `gather_llmd.sh`) is architecturally interesting because it implements a `kubectl`-based equivalent of `oc adm inspect` via the `kubectl_inspect` function. This function auto-discovers all namespaced or cluster-scoped API resources, collects their YAML, and gathers pod logs including previous container logs — replicating the core `oc adm inspect` behavior without depending on OpenShift tooling. This makes the must-gather usable on vanilla Kubernetes clusters running RHAII inference workloads.

The collection scripts use a shared `common.sh` library that provides resource discovery (`get_all_namespace`), namespace inspection (`run_mustgather`), operator namespace auto-detection (`get_operator_ns`), RHOAI version detection (`rhoai_version`), and Helm release value collection (`collect_helm_releases`). Each component script defines its relevant CRDs, discovers which namespaces contain those CRDs, and calls `run_mustgather` which also collects Gateway API resources (Gateways, HTTPRoutes, GRPCRoutes, ReferenceGrants) and Istio resources (EnvoyFilters, DestinationRules) as default per-namespace resources.
