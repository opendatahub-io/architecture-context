## Purpose

**Short**: Diagnostic data collector that gathers cluster state, logs, and custom resource snapshots from all RHOAI/RHAII components for support troubleshooting.

**Detailed**: must-gather is a diagnostic container image designed to run via `oc adm must-gather` on OpenShift or as a Kubernetes Job on non-OpenShift platforms (AKS, EKS, CKS). It collects namespace-level state (pod specs, logs, events), custom resource definitions, Helm release information, and cluster-scoped resources across all RHOAI components — KServe, LLM-D, AI Gateway, Data Science Pipelines, Workbench, KubeRay, Kueue, Training Operator, Model Registry, TrustyAI, Feast, MLflow, Spark, ModelExpress, MCP Lifecycle Operator, OGX, and their infrastructure dependencies (cert-manager, Sail/Istio, LWS).

The tool auto-detects the Kubernetes distribution at runtime (OpenShift, CKS, AKS, EKS) and adapts its collection strategy accordingly. On OpenShift it uses `oc adm inspect` for comprehensive namespace capture; on xKS platforms it uses a kubectl-based equivalent (`kubectl_inspect`) that auto-discovers all API resources, collects pod logs in parallel, and serializes resources to YAML. Components can be collected individually via the `COMPONENT` environment variable, or the default `all` mode runs all 14 component collectors in parallel on OpenShift. On xKS, the default collection is scoped to KServe and AI Gateway.

## Architectural Analysis

must-gather is a purely read-only diagnostic tool with no persistent state, no runtime services, and no API endpoints. Its architecture follows a dispatcher pattern: the main `gather.sh` entry point detects the Kubernetes distribution, sets up namespace defaults, and dispatches to per-component collector scripts. Each component script follows a consistent pattern — define a list of CRD resource types, discover namespaces where those resources exist via `get_all_namespace`, and use either `oc adm inspect` (OpenShift) or `kubectl_inspect` (xKS) to capture namespace state plus targeted custom resources.

A key design decision is the two-tier collection model. OpenShift's `oc adm inspect` captures everything in a namespace (pods, services, configmaps, events, logs) in a single operation, while the xKS `kubectl_inspect` function replicates this by calling `kubectl api-resources` to auto-discover all resource types, iterating over each, and collecting pod logs in parallel per container. This dual approach maintains feature parity across platforms while leveraging OpenShift-specific tooling when available.

The "all" component mode on OpenShift runs 14 component collectors as parallel background processes with PID tracking and failure reporting. Error handling is resilient — individual component failures are tracked in an associative array and reported in a summary but do not abort the overall collection. The `common.sh` library collects a default set of Gateway API and Istio resources (`gateways`, `httproutes`, `grpcroutes`, `envoyfilters`, `destinationrules`) for every namespace inspected on OpenShift, reflecting the RHOAI 3.x ingress architecture.

The LLM-D collection path is notably richer than other component collectors. It runs three dependency collectors (cert-manager, Sail/Istio, LWS), gathers Gateway API Inference Extension resources (`inferencemodelrewrites`, `inferenceobjectives`), and handles optional sub-components (Batch Gateway, MaaS) with feature flags. The observability collector (`gather_o11y.sh`) adapts to the monitoring stack — Azure Managed Prometheus on AKS versus self-hosted kube-prometheus-stack elsewhere.

The Dockerfile.konflux installs `crypto-policies-scripts` and sets the system crypto policy to `DEFAULT:PQ` (post-quantum), indicating forward-looking cryptographic posture. The helm CLI (v4.1.4) is included via Git LFS for collecting Helm release information. The kubectl binary comes from the `ose-cli-rhel9` builder stage, ensuring a Red Hat-built FIPS-compatible binary.
