## Purpose

**Short**: Diagnostic data collection tool for Red Hat OpenShift AI (RHOAI) and RHAII platforms that gathers cluster state, logs, and custom resource snapshots for support troubleshooting.

**Detailed**: The must-gather image is a specialized container that runs as a privileged diagnostic job on OpenShift clusters via `oc adm must-gather` or as a Kubernetes Job on non-OpenShift platforms (AKS, EKS, CKS). When executed, it collects comprehensive cluster state information — including namespace inspections (pod YAML, container logs, events), custom resource definitions across all RHOAI components, Helm release values, and Gateway API / Istio networking resources — and writes them to a tarball for Red Hat support analysis.

The tool supports both targeted single-component collection (via the `COMPONENT` environment variable, e.g., `COMPONENT=kserve`) and full-platform collection that runs all component gather scripts in parallel. It automatically detects the Kubernetes distribution (OpenShift, AKS, EKS, CKS) and adjusts its behavior accordingly — using `oc adm inspect` on OpenShift and a custom `kubectl_inspect` implementation on vanilla Kubernetes. For non-OpenShift platforms, collection is scoped to LLM-D inference workloads with their dependency operators (cert-manager, Sail/Istio, LeaderWorkerSet).

The must-gather covers 15+ RHOAI components including KServe, Data Science Pipelines, Dashboard, Workbenches, KubeRay, Kueue, Training Operator, Model Registry, TrustyAI, Feast, Llama-stack, MLflow, Spark Operator, AI Gateway (MaaS), and MCP Lifecycle Operator. Each component has a dedicated gather script that identifies relevant CRDs, discovers all namespaces containing those resources, and performs namespace-level inspection. The LLM-D subsystem additionally collects dependency operator state (cert-manager, Sail Operator, LeaderWorkerSet) and optional subsystems (workload-variant-autoscaler, batch-gateway).

## Architectural Analysis

The must-gather tool follows a well-structured modular architecture where each RHOAI component has a dedicated collection script that defines its own CRD resource list and namespace discovery logic. The main `gather.sh` orchestrator dispatches all component scripts in parallel using background processes with PID tracking, enabling efficient collection across the full platform in a single pass. This parallel execution pattern (lines 190-215 of `gather.sh`) is robust — it tracks individual job failures and reports them in a summary without aborting the entire collection.

The tool's multi-platform support is a significant architectural feature. The `xks_util.sh` library provides a complete `kubectl`-based reimplementation of `oc adm inspect` for non-OpenShift Kubernetes distributions. The `detect_k8s_distro()` function (lines 138-179 of `xks_util.sh`) uses a waterfall detection approach: first checking for OpenShift's `infrastructures.config.openshift.io` CRD, then falling back to kernel version strings (CoreWeave), provider IDs (Azure, AWS), and finally OS image strings. This is a pragmatic approach, though it may require updates as new xKS platforms are onboarded.

A notable design choice is the `DEFAULT_RESOURCES` array in `common.sh` (lines 9-16) which automatically collects Gateway API and Istio networking resources for every namespace that any component script inspects. This ensures that the RHOAI 3.x ingress infrastructure (Gateways, HTTPRoutes, GRPCRoutes, ReferenceGrants, EnvoyFilters, DestinationRules) is always captured alongside component state, without requiring each individual gather script to enumerate these resources. This is architecturally sound — it means ingress debugging data is always available regardless of which component triggered the collection.

The Helm integration (`collect_helm_releases` in `common.sh`, lines 77-86) collects both `helm get values` (user-supplied configuration) and `helm get manifest` (rendered templates) for the platform's Helm release. This is critical for RHAII deployments on xKS where Helm is the primary installation mechanism, and for RHOAI on OpenShift where Helm charts in the `rhai-gitops` namespace drive GitOps-based configuration.

The build infrastructure uses Konflux with digest-pinned base images and multi-architecture support (x86_64, ppc64le, s390x, arm64) as defined in the Tekton PipelineRun. The hermetic build flag is enabled, and the `helm` binary is vendored via Git LFS rather than downloaded at build time, which is a deliberate hermeticity choice. The `Containerfile` (for upstream/dev use) downloads `kubectl` and `helm` at build time via `curl`, which is not hermetic — this distinction between Konflux and upstream build paths is typical of RHOAI components.
