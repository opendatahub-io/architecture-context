## Purpose

**Short**: Latency prediction service for the llm-d ecosystem that trains and serves online ML models predicting TTFT (Time To First Token) and TPOT (Time Per Output Token) for LLM inference requests.

**Detailed**: The llm-d-latency-predictor is a dual-server architecture consisting of a training server and a prediction server. The training server collects request trace data (features like KV cache percentage, input token length, queue depth, prefix cache score, and tokens-in-flight), trains regression models (XGBoost, LightGBM, or Bayesian Ridge), and serves trained models via HTTP download endpoints. The prediction server periodically syncs trained models from the training server and serves low-latency TTFT/TPOT predictions via REST API, supporting both single and bulk (up to 10,000 requests) prediction modes.

The system supports configurable quantile regression (e.g., p90 predictions) or mean regression, a gated ensemble mode that uses separate sub-models for "noqueue" (idle) and "queued" request regimes, and disaggregated inference features via pod_type (prefill/decode) and tokens-in-flight tracking. Models are serialized as joblib files and downloaded over HTTP with checksum-based cache invalidation and atomic file replacement for safe multi-worker operation.

## Purpose

**Short**: Latency prediction microservice for the llm-d inference gateway ecosystem, providing TTFT and TPOT estimates via a dual-server architecture (training server + prediction server).

**Detailed**: llm-d-latency-predictor is a Python FastAPI service that provides real-time latency predictions (Time To First Token and Time Per Output Token) for LLM inference workloads within the llm-d ecosystem. It uses a dual-server architecture: a training server trains and serves ML regression models (XGBoost, LightGBM, or Bayesian Ridge), while one or more prediction server replicas periodically download trained models from the training server via HTTP and serve low-latency prediction requests. The prediction server exposes endpoints for single and bulk predictions (`/predict`, `/predict/bulk`, `/predict/bulk/strict`), accepting vLLM engine metrics (KV cache percentage, queue depth, token counts, prefix cache scores) and returning predicted latencies. The service supports a gated ensemble mode that uses separate sub-models for queued vs. non-queued inference requests. The prediction server is designed to run as a sidecar or auxiliary service consumed by the llm-d routing/scheduling layer to make latency-aware routing decisions.

## Data Flows

- **Model training pipeline:** The training server receives training data (vLLM engine metrics with observed latencies) via `POST /add_training_data_bulk`. It periodically retrains XGBoost/LightGBM/Bayesian Ridge regression models for TTFT and TPOT prediction, persisting them as joblib files to a PVC (`training-models-pvc`, 100Gi ReadWriteOnce).
- **Model distribution:** The prediction server's `ModelSyncer` background thread polls the training server at a configurable interval (`MODEL_SYNC_INTERVAL_SEC`, default 10s) via HTTP GET to `/model/{name}/info` (timestamp check) and `/model/{name}/download` (streaming download). Downloaded models are written atomically to local `emptyDir` storage, validated via `joblib.load()`, and hot-swapped into the `LightweightPredictor` under a lock. Each prediction server replica independently syncs its own copy of the models — no shared storage is needed.
- **Prediction serving:** External consumers (the llm-d routing/scheduling layer) send POST requests to `/predict` (single) or `/predict/bulk/strict` (batch, up to 10,000 requests) with vLLM engine metrics. The predictor constructs feature DataFrames, applies the loaded regression models, and returns predicted TTFT and TPOT in milliseconds. In gated ensemble mode, separate sub-models handle queued vs. non-queued inference requests.
- **Service surface:** 4 Kubernetes Service identities expose the runtime components: `training-service` (ClusterIP, 8000/TCP), `training-service-external` (LoadBalancer, 8080/TCP), `prediction-service` (LoadBalancer, 80→8001), and the application-level server on 8000/TCP and 8001/TCP.

## Architectural Analysis

The llm-d-latency-predictor follows a clean **dual-server architecture** separating training (stateful, single-replica) from prediction (stateless, horizontally scalable). This separation is a strong design choice: the training server accumulates data and performs expensive model fitting on a configurable interval (default 30 minutes), while prediction servers can scale to 10+ replicas to handle high request volumes. Each prediction worker independently syncs models via HTTP, using checksum-based cache invalidation to avoid redundant reloads -- only one worker "wins" the download race per cycle, but all workers reload from the local filesystem copy.

The **gated ensemble model** (`QueueGatedModel`) is a notable architectural pattern. Rather than training a single model for all traffic conditions, the system splits training data by queue regime (num_request_waiting == 0 vs > 0) and trains separate sub-models for each. At prediction time, the request's queue depth determines which sub-model is used. This improves accuracy because the relationship between features and latency fundamentally differs between idle and queued states -- an insight that a single model must learn implicitly but the ensemble handles explicitly.

The **bucketed sampling strategy** for training data is designed to prevent distribution skew. Training samples are stored in a 3-dimensional bucket grid (queue bucket × cache bucket × prefix bucket = 5×20×4 = 400 buckets), each with a configurable max size (default 500). This ensures the model sees representative samples from the full feature space rather than being dominated by the most common operating conditions. The `RandomDropDeque` data structure implements reservoir-like sampling by randomly evicting existing items when a bucket is full.

A significant **security gap** exists: neither server implements any form of authentication or authorization, and all inter-service communication uses plaintext HTTP. The model download flow between prediction and training servers lacks integrity verification beyond the joblib deserialization check. In production RHOAI deployments, the platform operator would need to layer network policies, mTLS, or kube-rbac-proxy to secure these services. The current manifests include GKE-specific nodeSelector and StorageClass configurations, indicating the base manifests were designed for a GKE development environment rather than production OpenShift.

The **bulk prediction fast path** (`predict_batch_fast`) demonstrates thoughtful performance optimization: it extracts features as numpy arrays via `np.fromiter` with pre-allocated counts, builds DataFrames from dict-of-arrays (avoiding Pandas' slow per-row type inference), and returns results via `ORJSONResponse` to bypass Pydantic serialization overhead. This path handles up to 10,000 predictions per request.

## Architectural Analysis

The llm-d-latency-predictor follows a train/serve split architecture where the training server and prediction server are deployed as separate Kubernetes Deployments but communicate via HTTP within the cluster. This design decouples model training (CPU/memory-intensive, single replica with PVC storage) from model serving (lightweight, horizontally scaled to 10 replicas using ephemeral `emptyDir` storage). The prediction server avoids needing `ReadWriteMany` PVCs by downloading models over HTTP from the training server, making the architecture simpler to deploy on clusters without shared filesystem support.

The prediction server implements a checksum-based reload mechanism that prevents redundant model deserialization. The `ModelSyncer` downloads models to a temporary file, validates them via `joblib.load()`, then performs an atomic `os.replace()` before the `LightweightPredictor` checks file checksums and hot-swaps model pointers under an `RLock`. This ensures predictions are never served from a partially written or corrupt model file, and the lock is held only for the pointer swap (microseconds) rather than during deserialization.

The gated ensemble mode (`LATENCY_ENSEMBLE_MODE`) is architecturally significant: it wraps two sub-models (noqueue and queued) inside a `QueueGatedModel` object, selecting the appropriate sub-model at prediction time based on `num_request_waiting`. This allows the system to use fundamentally different regression models for idle vs. queued inference servers, improving prediction accuracy across the full load spectrum.

The batch prediction path (`/predict/bulk/strict`) is heavily optimized for throughput: it builds DataFrames from `dict-of-numpy-arrays` rather than `list-of-dicts` to skip Pandas type inference, uses `ORJSONResponse` for fast serialization, and constructs response dicts directly rather than Pydantic objects. This design targets the latency-sensitive hot path where the llm-d scheduler needs predictions for many candidate pods within a tight latency budget.

The deployment manifest (`deploy/dual-server-deployment.yaml`) includes GKE-specific constructs (Hyperdisk StorageClass, node pool selectors) that will need adaptation for OpenShift/RHOAI deployment. The LoadBalancer Services for `prediction-service` and `training-service-external` suggest an interim development topology; production RHOAI deployment would likely use ClusterIP Services behind the platform's Gateway API ingress infrastructure.
