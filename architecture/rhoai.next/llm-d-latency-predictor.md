## Purpose

**Short**: Online ML service that predicts LLM inference latencies (TTFT and TPOT) for the llm-d request routing ecosystem.

**Detailed**: The llm-d-latency-predictor provides two cooperating FastAPI microservices that together form an online machine learning pipeline for predicting Large Language Model (LLM) inference latencies. The **training server** ingests real-time request telemetry (KV cache utilization, queue depth, input token length, prefix cache scores, etc.) and continuously retrains regression models (XGBoost, LightGBM, or Bayesian Ridge) to predict Time To First Token (TTFT) and Time Per Output Token (TPOT). The **prediction server** downloads trained model artifacts from the training server via HTTP and serves low-latency inference predictions to upstream routing components.

This component is part of the llm-d ecosystem, which provides intelligent request routing for LLM serving workloads. The latency predictor enables the routing layer to make informed scheduling decisions by providing per-pod latency estimates based on current system state. The system supports both quantile regression (e.g., p90 predictions) and mean regression, with an optional queue-gated ensemble mode that trains separate models for idle (no queue) and queued regimes.

## Architectural Analysis

The llm-d-latency-predictor implements a producer-consumer architecture for online machine learning. The training server acts as the "data plane" for model training while prediction servers form a horizontally scalable "serving plane." This separation allows the training workload (CPU-intensive model fitting) to run as a single replica with persistent storage while prediction serving scales independently across many replicas, each with its own local model copy.

The model synchronization mechanism is notable for its robustness in multi-worker environments. Each uvicorn worker process runs its own sync thread that downloads models independently. To avoid redundant in-memory reloads, the system uses MD5 checksums -- after any worker downloads a new model file, all workers detect the on-disk change via checksum comparison and reload the model. The reload path is carefully optimized: `joblib.load()` (the slow I/O operation) runs outside the prediction lock, and only the final pointer swap is protected by the lock, minimizing latency impact on in-flight predictions.

The queue-gated ensemble mode represents a sophisticated approach to handling bimodal latency distributions. When enabled, the system trains four sub-models (TTFT-noqueue, TTFT-queued, TPOT-noqueue, TPOT-queued) wrapped in `QueueGatedModel` objects. At prediction time, the system inspects `num_request_waiting` and routes to the appropriate sub-model. This mirrors the observation that LLM inference latency has fundamentally different characteristics when requests queue (dominated by queue wait time) versus when they don't (dominated by compute time).

A significant security gap exists: neither server implements authentication, authorization, or TLS. All endpoints are open, including the training data ingestion endpoint (`/add_training_data_bulk`) which could be exploited to poison the training data and manipulate routing decisions. In a production deployment, these services must be protected by network policies, service mesh mTLS, or an authentication proxy (e.g., kube-rbac-proxy or Istio PeerAuthentication). The deployment manifests currently expose the prediction service as a LoadBalancer, which would be externally accessible without additional network controls.

The bulk prediction fast path (`/predict/bulk/strict`) is heavily optimized for throughput: it constructs DataFrames from numpy arrays (bypassing Pandas type inference), skips Pydantic validation overhead for the response, and uses ORJSONResponse for serialization. This path is designed for the hot-path routing use case where thousands of predictions per second are needed.
