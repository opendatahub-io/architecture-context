## Purpose

**Short**: High-performance model weight transfer system that discovers the fastest available path to load LLM weights into GPU memory — via P2P RDMA, streaming, GPUDirect Storage, or host-staged POSIX I/O — and coordinates metadata across inference replicas.

**Detailed**: ModelExpress (MX) solves the cold-start bottleneck in LLM serving infrastructure. Before loading a model, it discovers where a compatible copy of the weights already lives and selects the fastest transport into GPU memory. In P2P mode, weights serving inference on one GPU transfer directly to another over NIXL/RDMA, achieving a 48× speedup over cold Hugging Face pulls for models like DeepSeek-V4-Pro. Beyond raw weights, it also transfers compatible JIT kernel caches (Triton, DeepGEMM, TileLang, CuTe DSL, FlashInfer) so new replicas skip compilation.

The system has two planes: a metadata control plane (the `modelexpress-server` gRPC service) that discovers sources and coordinates sharing, and a data plane where weight bytes move directly between storage and GPU without traversing the server. The Kubernetes operator (`modelexpress-operator`) manages server deployments declaratively through the `ModelExpressServer` CRD, handling TLS configuration, RBAC, NetworkPolicy, probe tuning, and cache PVC lifecycle. On OpenShift, the operator variant reads the cluster TLS security profile from `apiservers.config.openshift.io/cluster` so server deployments automatically follow platform-wide cipher policy.

ModelExpress integrates with vLLM (`--load-format modelexpress`), SGLang (`remote_instance` + `modelexpress` backend), TensorRT-LLM (`checkpoint_format="MX"`), NVIDIA Dynamo runtimes, and llm-d. Metadata backends include Redis and Kubernetes CRDs, with a decentralized `k8s-service` mode for coordinator-free discovery.

## Architectural Analysis

ModelExpress is architected as a Rust workspace with clear crate boundaries that separate concerns while sharing foundational types. The workspace produces two deployable binaries — a gRPC metadata coordinator (server) and a Kubernetes operator — plus client libraries for Rust, Python, and Go.

The **operator design** is notable for several deliberate choices. It uses CEL admission validation on the CRD schema instead of webhooks, making it OLMv1-compatible without a webhook certificate lifecycle. The operator creates per-CR RBAC (ServiceAccount, Role, RoleBinding) so each ModelExpressServer instance runs with least privilege scoped to its namespace. It renders NetworkPolicy resources when requested, restricting gRPC port access to named peers. The operator uses `kube-rs` Controller with metadata-only watches (`owns_stream` with `metadata_watcher`) on owned resources to minimize memory consumption in clusters with many ServiceAccounts and RoleBindings.

The **OpenShift variant** (`modelexpress-operator-openshift`) wraps the generic operator and adds two capabilities: it watches `apiservers.config.openshift.io/cluster` for TLS security profile changes (Old/Intermediate/Modern/Custom) and applies them as server defaults via the `TlsDefaults` trait, and it dynamically applies a `ServiceMonitor` for the operator's own metrics with the correct namespace-scoped server name for Prometheus certificate verification. Unknown `tlsAdherence` values fail secure by honoring the cluster profile.

The **gRPC server** exposes five service definitions — `ApiService` (generic request/response), `ModelService` (download coordination and file streaming), `HealthService` (status/uptime), `P2pService` (NIXL metadata publication, source discovery, and status coordination), and `RefitService` (RL weight version management) — all behind an optional `AuthLayer` that validates Kubernetes ServiceAccount tokens via TokenReview/SubjectAccessReview. The `WorkerService` and `RefitWorkerService` run on inference worker pods (not the coordinator server) for direct manifest exchange between peers.

The **TLS architecture** has two compile-time backends selected by Cargo feature flags: `tls-openssl` for FIPS-validated builds (linking against RHEL's system OpenSSL) and `tls-rustls` for upstream/development builds. The RHOAI Konflux Dockerfiles build with `--no-default-features --features openssl`, dropping `rustls` and the GCS feature (which hardcodes `rustls` via `google-cloud-auth`). Both the server and operator accept configurable minimum TLS version, cipher suites, and key exchange groups.

A design tension exists in metadata backend selection: the Kubernetes CRD backend (`ModelMetadata`, `ModelCacheEntry`) provides declarative, garbage-collected metadata but introduces apiserver load proportional to the number of inference workers, while the Redis backend avoids apiserver load but requires external state management and credential handling (the CRD supports `urlSecret` for Redis URLs with embedded credentials).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-CR ServiceAccount + Role + RoleBinding for server pods; operator itself uses a ClusterRole | Kubernetes RBAC | Server gRPC auth is opt-in (MODEL_EXPRESS_SECURITY_MODE=off by default); when disabled, any pod with network access can publish/query metadata |
| Data storage | Per-namespace PVC for model cache; per-namespace ModelMetadata/ModelCacheEntry CRs (when using kubernetes backend); shared Redis (when using redis backend) | Kubernetes (CRD backend) / Application (Redis backend) | Redis backend has no per-namespace isolation — all servers sharing a Redis instance see all metadata; CRD backend uses ownerReferences to garbage-collect metadata with pods |
| Network traffic | Optional per-CR NetworkPolicy restricting gRPC ingress to named peers | Kubernetes CNI (when spec.networkPolicy is set) | NetworkPolicy is opt-in (not set by default); worker-to-worker RDMA traffic bypasses CNI entirely (direct GPU-to-GPU over NIXL) |
| Compute & resources | Per-CR resource requests/limits on server pods; operator deployment has own resource spec | Kubernetes scheduler | No ResourceQuota or LimitRange created by the operator; resource isolation is the cluster admin's responsibility |
| Configuration & secrets | Per-CR Secrets for TLS certs and download credentials (HF_TOKEN, NGC_API_KEY, Redis URL); per-namespace scope | Kubernetes Secret RBAC | Secrets are namespace-scoped; no cross-namespace access |
| API scoping | Operator uses cluster-wide watch on ModelExpressServer CRs; owned resource watches are filtered by `managed-by` label | Kubernetes / Application | Cluster-wide CRD watch is expected for an operator; label-filtered owned resource watches reduce memory |
