## Purpose

**Short**: High-performance C++ model inference server that exposes OpenAI-compatible, KServe v2, and TensorFlow Serving REST/gRPC APIs for serving AI models optimized with OpenVINO.

**Detailed**: OpenVINO Model Server (OVMS) is an Intel-developed inference serving platform built in C++ for low-latency, high-throughput model serving. It provides a drop-in replacement for OpenAI API endpoints (chat completions, embeddings, reranking, image generation, audio transcription/synthesis) while using the OpenVINO runtime for inference execution, enabling efficient deployment on Intel CPUs and GPUs.

The server supports multiple model formats (OpenVINO IR, ONNX, TensorFlow SavedModel, PaddlePaddle, PyTorch, HuggingFace) and can load models from local storage, Amazon S3, Google Cloud Storage, Azure Blob Storage, or directly from HuggingFace Hub. Models can be served individually or composed into DAG pipelines and MediaPipe graphs for complex multi-model workflows. The server includes continuous batching for LLM text generation, OpenVINO GenAI integration for VLMs, and specialized servables for embeddings, reranking, image generation, and audio processing.

In the RHOAI platform, OVMS is deployed as a KServe-compatible serving runtime. Two ServingRuntime definitions ship with the repository: a ClusterServingRuntime (`kserve-openvino`) for general model serving and a namespace-scoped ServingRuntime (`kserve-ovms-2026-2`) tailored for OpenShift AI with GPU support and Prometheus metrics enabled.

## Architectural Analysis

OVMS follows a modular server architecture where the main `Server` singleton orchestrates independently startable/stoppable modules: `GRPCServerModule`, `HTTPServerModule` (backed by Drogon), `ServableManagerModule`, `MetricModule`, `HfPullModelModule`, and optionally `ProfilerModule`. Each module implements a lifecycle interface (`start`/`shutdown`) and is initialized in dependency order by the server.

The API surface is layered across three protocol generations. The TFS v1 API (`/v1/models/...`) provides backward compatibility with TensorFlow Serving clients. The KServe v2 API (`/v2/...`) implements the open inference protocol for cloud-native model serving with health, metadata, and inference endpoints. The OpenAI-compatible v3 API (`/v3/...`) routes requests through MediaPipe graph executors, supporting chat completions, text completions, embeddings, reranking, image generation, audio transcription, and the newer OpenAI Responses API — making OVMS a drop-in backend for applications built against the OpenAI SDK.

The model management layer supports hot-reloading via filesystem polling or config file changes, model versioning with configurable version policies, and dynamic shape/batch handling. The HuggingFace pull module can download and optionally convert models on startup using `optimum-intel`, enabling direct deployment from HuggingFace Hub without pre-conversion.

Security is handled externally by design. The gRPC server uses insecure credentials (`grpc::InsecureServerCredentials()`), and the Drogon HTTP server binds without TLS. The expectation is that TLS termination happens at the platform level (Kubernetes Service Mesh, Route, or the provided nginx-mTLS sidecar in `extras/nginx-mtls-auth/`). An optional API key mechanism (`--api_key_file` or `API_KEY` env var) provides Bearer token authentication on REST endpoints, but this is disabled by default.

A notable crypto concern is the use of OpenSSL MD5 (`openssl/md5.h`) in the filesystem abstraction layer for model file checksumming. While this is not a security-sensitive use (integrity checking, not authentication), MD5 is deprecated under FIPS 140-2/3 and could cause issues in strict FIPS enforcement modes.
