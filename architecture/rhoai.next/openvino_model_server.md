## Purpose

**Short**: High-performance C++ inference server for serving AI models via OpenAI-compatible, KServe, and TensorFlow Serving APIs using Intel OpenVINO for optimized execution.

**Detailed**: OpenVINO Model Server (OVMS) is a production inference server implemented in C++ for scalability and optimized for deployment on Intel architectures. It provides model serving through multiple API protocols: OpenAI-compatible REST APIs (chat completions, embeddings, reranking, image generation, audio), KServe v2 inference protocol (both gRPC and REST), and TensorFlow Serving prediction API. The server uses Intel OpenVINO as its inference backend, supporting models in OpenVINO IR, ONNX, TensorFlow, PaddlePaddle, and PyTorch formats.

Within the RHOAI platform, OVMS operates as a KServe ServingRuntime, deployed by KServe's InferenceService controller as the inference container within model-serving pods. It supports both single-model serving (via KServe) and multi-model serving (via its own configuration file). The server features continuous batching for LLM workloads, MediaPipe graph-based pipelines for complex inference workflows (DAGs), model hot-reloading, and a C API for embedded use cases. It can pull models from local storage, S3, Google Cloud Storage, Azure Blob Storage, and HuggingFace Hub.

The Konflux build produces a single container image (`odh-openvino-model-server-rhel9`) based on UBI 9 Minimal, compiled from source with Link-Time Optimization (LTO) enabled and GPU driver support (Intel GPU via OpenCL). The build fetches OpenVINO, OpenVINO Tokenizers, and OpenVINO GenAI from forked `opendatahub-io` repositories on release branches.

## Purpose

**Short**: OpenVINO Model Server (OVMS) is a high-performance C++ inference server that exposes TensorFlow Serving (v1), KServe Inference Protocol (v2), and OpenAI-compatible (v3) APIs over both gRPC and HTTP/REST for serving AI models optimized with the OpenVINO toolkit.

**Detailed**: OpenVINO Model Server (OVMS) is a C++ inference runtime built with Bazel that serves machine learning models using the Intel OpenVINO toolkit. It exposes three API generations: TensorFlow Serving v1 REST, KServe v2 (gRPC and REST), and OpenAI-compatible v3 (chat completions, embeddings, reranking, image generation, text-to-speech, speech-to-text). The server has a modular architecture with separately managed modules for gRPC, HTTP, servable management, metrics, Python interpreter, HuggingFace model pulling, and a C API shared library. It supports MediaPipe graph-based pipelines for composable inference workflows, model hot-reloading via filesystem polling, and dynamic model configuration. In the RHOAI platform, OVMS is deployed as a KServe/ModelMesh inference runtime container (`odh-openvino-model-server-rhel9`). It supports Azure Blob Storage, S3-compatible stores, Google Cloud Storage, and local filesystem as model repositories. The server provides Prometheus metrics, health/readiness probes (KServe v2 protocol), and optional API key authentication with CORS support.

## Data Flows

1. **Model Loading**: On startup or config reload, the Servable Manager Module reads model configuration (JSON config file or CLI args), resolves model paths from local filesystem or cloud storage (S3/Azure/GCS), downloads artifacts if needed, and loads models into OpenVINO runtime. The filesystem poller checks for changes every `--filesystem_poll_wait_seconds` (default 1s).
2. **gRPC Inference**: Client sends KFSRequest or TFS PredictRequest → gRPC server module dispatches to KFSInferenceServiceImpl or TFS PredictionService → request deserialized → model/pipeline looked up in Servable Manager → inference executed via OpenVINO → response serialized and returned. ModelStreamInfer provides streaming responses for generative models.
3. **REST Inference**: Client sends HTTP POST → HTTP server module routes via regex matching → HttpRestApiHandler dispatches to appropriate handler (TFS v1, KServe v2, or OpenAI v3) → request converted to internal gRPC-like format → same inference path as gRPC → JSON response returned. V3 endpoints support streaming via server-sent events.
4. **HuggingFace Pull**: When started in HF_PULL_AND_START_MODE, the HF Model Pull Module downloads a model from HuggingFace Hub (via git clone, Optimum CLI, or GGUF download), converts it with specified precision, generates a serving config, and starts the server.
5. **Health Probes**: KServe v2 health endpoints (`/v2/health/ready`, `/v2/health/live`) check module states — the server reports ready only when all modules (gRPC, HTTP, Servable Manager) are initialized.

## Architectural Analysis

OVMS is a monolithic C++ server with a modular internal architecture organized around a `Module` base class and a `Server` singleton that manages module lifecycle. The startup sequence is carefully ordered: the Metrics module initializes first to enable metric collection from the start, followed by the optional Python interpreter, then the Servable Manager (which loads models), the C API module, and finally the gRPC and HTTP server modules. This ordering ensures health probes respond correctly only after all infrastructure is ready. The server supports graceful shutdown with a 5-second deadline, using signal handlers for SIGINT/SIGTERM.

The GenAI serving stack (LLM, embeddings, reranking, image generation, audio) is built on MediaPipe's calculator framework rather than the traditional DAG scheduler. Each GenAI capability is implemented as a MediaPipe calculator (`HttpLLMCalculator`, `EmbeddingsCalculatorOv`, `RerankCalculatorOv`, etc.) configured via Protocol Buffer definitions. This allows complex inference graphs to be composed from reusable calculator nodes. The LLM module supports two execution modes: a legacy single-sequence pipeline (`LLMPipeline`) and a high-throughput continuous batching pipeline (`ContinuousBatchingPipeline`) from OpenVINO GenAI. The continuous batching mode is the production path for LLM serving, supporting multiple concurrent sequences with configurable KV cache, prefix caching, and speculative decoding.

The server exposes three API families on two ports: OpenAI-compatible REST endpoints under `/v3/`, KServe v2 endpoints under `/v2/`, and TensorFlow Serving endpoints under `/v1/`. The HTTP server uses Drogon (a high-performance C++ web framework) with configurable worker threads scaled to CPU cores and file descriptor limits. The gRPC server supports multiple instances via the `grpc_workers` setting, each with independent thread pools and resource quotas. Notably, neither the gRPC nor HTTP server implements TLS termination -- both use `InsecureServerCredentials` and plaintext HTTP respectively. TLS is expected to be handled by the platform's ingress layer (OpenShift Routes, Gateway API with Envoy, or kube-rbac-proxy sidecars).

The security model relies almost entirely on the deployment platform. OVMS itself provides only optional API key authentication (a single shared key, not per-user). In RHOAI deployments, the platform operator injects kube-rbac-proxy sidecars for proper authentication and authorization. The container runs as non-root user `ovms` (UID 5000) with restricted security context (no privilege escalation, all capabilities dropped). For image/media loading in VLM workloads, the server implements domain whitelisting (`allowed_media_domains`) and local path restrictions (`allowed_local_media_path`) to prevent SSRF and path traversal attacks.

The model storage abstraction supports four backends (local filesystem, S3, GCS, Azure Blob) with a common `FileSystem` interface. Model repositories can be polled for changes with configurable intervals (`file_system_poll_wait_seconds`), enabling model hot-reloading without server restart. The HuggingFace Pull module adds the ability to download models directly from HuggingFace Hub using libgit2, with support for authentication tokens and proxy configuration.

## Architectural Analysis

OVMS is a monolithic C++ inference server with a plugin-based module architecture. The `Server` class (singleton) owns a map of `Module` instances identified by name strings (`GRPC_SERVER_MODULE_NAME`, `HTTP_SERVER_MODULE_NAME`, `SERVABLE_MANAGER_MODULE_NAME`, etc.). Modules are started sequentially in dependency order and shut down in reverse. This design allows optional modules (Python interpreter, metrics, profiler) to be absent without affecting core serving.

The server exposes three generations of inference API simultaneously: TensorFlow Serving v1 (REST only, for backward compatibility), KServe v2 (both gRPC and REST, the primary production protocol), and OpenAI-compatible v3 (REST, for LLM/GenAI workloads including chat completions, embeddings, reranking, image generation, and speech). The v3 API is routed through MediaPipe graph executors, enabling composable multi-step inference pipelines (e.g., tokenization → generation → detokenization). The HTTP handler uses regex-based routing with a handler registry pattern, while gRPC uses standard protobuf service definitions.

The `ServerSettingsImpl` struct reveals that all network binding is fully configurable — gRPC and REST ports, bind addresses, worker counts, gRPC memory quota, and channel arguments are all runtime parameters. This allows the RHOAI platform operator (KServe/ModelMesh) to configure OVMS ports and resources per InferenceService. Authentication is limited to static API key comparison (optional) — in RHOAI deployments, platform-level authentication (kube-rbac-proxy sidecars or Gateway API) handles user authentication before traffic reaches OVMS.

The build is notably complex: Bazel orchestrates the C++ build with conditional feature flags (`--config=mp_on_py_on` for MediaPipe and Python support, `--config=mp_off_py_off` for a minimal build). The Konflux Dockerfile builds OpenVINO from source (or installs from binary), compiles OpenVINO Tokenizers and GenAI extensions, and produces both the main server binary and the C API shared library. The release image is based on UBI9 minimal with only runtime dependencies. The Go code in the repository (found by the analyzer) is exclusively for client libraries and demo applications — not part of the server architecture.

The `GraphExportType` enum in `server_settings.hpp` documents the supported GenAI graph types: text_generation, rerank, embeddings, image_generation, text2speech, and speech2text. Each maps to a MediaPipe graph template that orchestrates the inference pipeline for that modality. The HuggingFace integration (`HFSettingsImpl`) supports downloading models via git clone, Optimum CLI (for format conversion), or direct GGUF file download, with configurable precision, target device, and plugin settings.
