## Purpose

**Short**: High-performance C++ inference server implementing OpenAI-compatible, KServe, and TensorFlow Serving APIs for serving AI models optimized with the OpenVINO toolkit.

**Detailed**: OpenVINO Model Server (OVMS) is a production-grade model inference server developed by Intel, packaged for Red Hat OpenShift AI (RHOAI) as the `odh-openvino-model-server-rhel9` container image. It provides a standards-compliant serving layer for deploying deep learning and generative AI models with optimized inference on Intel architectures (CPUs and GPUs).

The server exposes a comprehensive multi-protocol API surface: gRPC and HTTP/REST endpoints supporting KServe inference protocol (v2), TensorFlow Serving protocol (v1), and OpenAI-compatible v3 endpoints for LLM chat/completions, embeddings, reranking, audio (speech-to-text, text-to-speech), and image generation. Models can be loaded from local storage, AWS S3, Google Cloud Storage, Azure Blob Storage, or pulled directly from HuggingFace Hub.

OVMS supports composable inference pipelines through two mechanisms: a built-in DAG (Directed Acyclic Graph) scheduler for chaining multiple models and custom processing nodes, and MediaPipe graph integration for streaming pipeline execution. The server also supports Python node execution via pybind11 embedding, custom C/C++ node libraries loaded via dlopen, and LoRA adapter management for efficient fine-tuned model serving.

## Architectural Analysis

OpenVINO Model Server follows a modular architecture where the main server binary orchestrates multiple independently startable modules. The module system (`src/module.hpp`) provides lifecycle management with ordered startup and shutdown. The startup sequence is critical: Python interpreter initializes first (for GIL management), followed by metrics, then the servable manager, gRPC server, HTTP server, and finally the model pulling module. This ordering ensures all infrastructure is ready before models are loaded and served.

The API surface has evolved through three generations. The v1 API provides TensorFlow Serving compatibility for legacy clients. The v2 API implements the KServe inference protocol with both gRPC and HTTP bindings, enabling standardized model serving across platforms. The v3 API adds OpenAI-compatible endpoints for generative AI workloads (chat completions, embeddings, reranking, audio, image generation). The v3 endpoints are implemented via MediaPipe calculators — each generative task is a MediaPipe graph with specialized calculators (LLM calculator, embeddings calculator, rerank calculator, etc.), allowing composable pipeline construction.

A notable design decision is that OVMS does not implement native TLS for its gRPC or REST endpoints. All connections are plaintext, with encryption delegated to the platform's ingress infrastructure (Gateway API + kube-rbac-proxy in RHOAI 3.x). This simplifies the server but means deployment outside a platform with TLS termination leaves traffic unencrypted. The only TLS usage is outbound — curl and libgit2 use system OpenSSL for HTTPS connections to cloud storage and HuggingFace.

The Konflux build (`Dockerfile.konflux`) compiles OpenVINO, OpenVINO Tokenizers, and OpenVINO GenAI from source using specific git commit SHAs pinned in `.konflux/build-args.conf`. The source repositories are forks under `opendatahub-io` (e.g., `opendatahub-io/openvino`, `opendatahub-io/openvino_tokenizers`) at the `releases/2026/2` branch. The build uses LTO (Link-Time Optimization) with `-flto=auto -ffat-lto-objects` and targets the Haswell microarchitecture (`-march=haswell`) for broad x86_64 compatibility. The build is GPU-enabled (`GPU=1`), including Intel OpenCL GPU drivers for inference acceleration.

The storage abstraction layer (`src/filesystem/`) enables model loading from four backends: local filesystem, AWS S3, Google Cloud Storage, and Azure Blob/File Storage. Each backend implements the same `FileSystem` interface with a factory pattern routing based on URL prefix (`s3://`, `gs://`, `azurefs://`, `azureblob://`). The model pulling module adds a fifth source — HuggingFace Hub — using libgit2 for authenticated git clone with LFS support, plus specialized downloaders for GGUF format models and Optimum-based model export.
