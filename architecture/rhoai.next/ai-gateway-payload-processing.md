## Purpose

**Short**: Envoy external processing (ext_proc) service that enables RHOAI's AI Gateway to route inference requests to external LLM providers (OpenAI, Anthropic, Azure, AWS Bedrock, Google Vertex AI) with API format translation, credential injection, usage metering, and content guardrails.

**Detailed**: AI Gateway Payload Processing is a pluggable Inference Payload Processor (IPP) built on the [llm-d](https://github.com/llm-d/llm-d-inference-payload-processor) framework. It runs as an Envoy ext_proc filter attached to the AI Gateway's Istio data plane, intercepting inference requests and responses to perform mutations on headers and body content.

The service introduces two Custom Resource Definitions -- `ExternalProvider` and `ExternalModel` -- in the `inference.opendatahub.io` API group. `ExternalProvider` defines a connection to an external LLM provider (endpoint, credentials, auth type), while `ExternalModel` maps a client-facing model name to one or more providers with weighted traffic distribution, API format translation configuration, and path templating.

Three controller-runtime controllers run inside the same process: the ExternalProvider controller creates Kubernetes ExternalName Services, Istio ServiceEntries, and DestinationRules for TLS origination to each provider endpoint; the ExternalModel controller creates Gateway API HTTPRoutes that route client traffic through the gateway to the appropriate provider backend; and a legacy migration controller watches deprecated `maas.opendatahub.io/v1alpha1` ExternalModel CRs and automatically creates equivalent `inference.opendatahub.io/v1alpha1` resources. The plugin pipeline (maas-headers-guard → model-provider-resolver → stream-usage-enforcer → api-translation → apikey-injection) handles request/response processing at runtime, including multi-provider weighted routing, format translation between OpenAI, Anthropic Messages, and Vertex AI APIs, credential injection (API key, AWS SigV4, GCP OAuth2), optional usage metering via an external metering service, and NeMo Guardrails content safety checks.

## Purpose

**Short**: Kubernetes controller that manages ExternalModel and ExternalProvider CRDs to route inference requests to external LLM providers (OpenAI, Anthropic, AWS Bedrock, Azure, Vertex AI) via Gateway API HTTPRoutes and Istio networking resources.

**Detailed**: ai-gateway-payload-processing is a controller-runtime operator built on top of the llm-d-inference-payload-processor runner framework. It registers three controllers: an ExternalProvider controller that creates Service, ServiceEntry, and DestinationRule resources for external LLM provider connectivity; an ExternalModel controller that creates Gateway API HTTPRoute resources mapping client-facing model names to provider backends through a configured Gateway; and a legacy migration controller that converts maas.opendatahub.io ExternalModel CRs into the current inference.opendatahub.io API. The operator also hosts a payload processing plugin pipeline (from llm-d) that handles request/response transformation including API key injection and model-provider resolution at inference time. Authentication to external providers is configured per-CR with support for simple header-based API keys, AWS SigV4 signing, and OAuth2 tokens, all sourced from Kubernetes Secrets.

## Data Flows

- **Control plane flows:** The operator watches ExternalProvider and ExternalModel CRs and reconciles Istio networking resources (Service, ServiceEntry, DestinationRule) and Gateway API resources (HTTPRoute) to establish routing paths from the platform Gateway to external LLM provider endpoints. The ExternalModel controller also watches ExternalProvider CRs via `MapProviderToModels` to re-reconcile dependent models when a provider changes.
- **Data plane flows:** At inference request time, the llm-d payload processing pipeline intercepts requests routed through the Gateway API HTTPRoute. The apikey-injection plugin reads the provider's Secret (containing the `api-key` data key) and injects the appropriate authentication header. The model-provider-resolver plugin resolves the client-facing model name to the correct upstream provider and target model.
- **Legacy migration:** The legacy migration controller watches unstructured `maas.opendatahub.io` ExternalModel CRs and creates equivalent `inference.opendatahub.io` ExternalProvider and ExternalModel CRs, enabling transparent migration from the older API group.
- **Security context:** Authentication to external LLM providers is configured per ExternalProvider CR with three supported auth types (simple, sigv4, oauth2). Credentials are stored in Kubernetes Secrets referenced by the CR. Four sample credential Secrets are documented (anthropic-credentials, openai-credentials, azure-credentials, vertex-credentials).

## Architectural Analysis

The AI Gateway Payload Processing service demonstrates a clean separation between the control plane (controller-runtime controllers managing Kubernetes resources) and the data plane (IPP plugin pipeline processing ext_proc gRPC calls). Both run in the same Go process, sharing CRD-backed state through in-memory stores. The `infoStore` in the model-provider-resolver plugin is populated by reconcilers watching ExternalModel and ExternalProvider CRDs, providing O(1) model name lookups at request time without Kubernetes API calls on the hot path. This design avoids latency spikes during inference but means the data plane operates on eventually-consistent state -- a provider deletion may take one reconcile cycle to propagate to the request path.

The plugin pipeline architecture (`maas-headers-guard → model-provider-resolver → stream-usage-enforcer → api-translation → apikey-injection`) uses a `CycleState` object (from the llm-d framework) as a per-request data bag that plugins write to and read from in sequence. This avoids direct plugin-to-plugin coupling: the model-provider-resolver writes the selected provider, auth type, endpoint, and credentials reference into CycleState; the api-translation plugin reads the input/output format pair to select the correct translator; and the apikey-injection plugin reads the Secret reference to look up credentials. The `external-metering` and `nemo-*-guard` plugins are optional additions to the pipeline, configured at the Helm values level rather than compiled in.

The multi-provider weighted routing design is noteworthy: an ExternalModel can reference multiple ExternalProviders with weights (0-100), and the model-provider-resolver plugin performs weighted random selection at request time. The selected provider name is written to the `x-ipp-selected-provider` header, and the ExternalModel controller creates per-provider HTTPRoute rules that match on this header, ensuring the Gateway routes to the correct backend Service. A fallback rule (no header match) routes to the first provider. This header-based routing means the ext_proc and the Gateway data plane must agree on the provider selection for each request -- a subtle correctness requirement.

The Istio networking integration follows a consistent pattern: each ExternalProvider creates three resources -- an ExternalName Service (for Kubernetes DNS resolution), a ServiceEntry (for Istio mesh-external resolution), and a DestinationRule (for TLS origination with SIMPLE mode). This triple ensures that traffic from the Envoy sidecar to external provider endpoints is properly encrypted without requiring the application to handle TLS directly. The `crypto/sha256` usage in the SigV4 auth generator and GCP OAuth2 token cache is FIPS-safe because the `strictfipsruntime` build experiment routes all crypto operations through OpenSSL.

The legacy migration controller is a pragmatic backward-compatibility mechanism: it watches the old `maas.opendatahub.io/v1alpha1` ExternalModel CRDs and creates corresponding `inference.opendatahub.io/v1alpha1` ExternalProvider + ExternalModel CRs, with owner references ensuring cleanup on legacy CR deletion. The migration controller gracefully skips registration if the legacy CRD is not installed on the cluster, making it safe to deploy on clusters that never had the old API group.

## Architectural Analysis

The ai-gateway-payload-processing operator bridges the RHOAI platform's internal Gateway API routing infrastructure with external commercial LLM providers. Its architecture follows a clear separation between control-plane reconciliation (creating Kubernetes and Istio networking resources) and data-plane request processing (the llm-d plugin pipeline that transforms payloads and injects credentials at inference time).

The operator is built on top of the `llm-d-inference-payload-processor` runner framework rather than a standalone controller-runtime manager. This design embeds the three custom controllers (ExternalProvider, ExternalModel, and legacy migration) into the llm-d runner's lifecycle via `WithCustomControllers()`, allowing the operator to share the runner's plugin infrastructure. The ExternalModel controller receives Gateway name and namespace from environment variables (`GATEWAY_NAME`, `GATEWAY_NAMESPACE`), creating HTTPRoutes that reference an externally-managed Gateway resource.

The CRD design supports multi-provider model routing with weighted traffic distribution. An ExternalModel CR can reference up to 64 ExternalProvider bindings, each with a weight (1-100) for weighted random selection. This enables A/B testing across providers or gradual migration between providers. The `apiFormat` field on each binding (supporting "openai-chat" and "messages" formats) drives request/response translation, allowing a single client-facing model name to be backed by providers with different API formats.

The authentication model is per-CR rather than cluster-wide. Each ExternalProvider specifies a required `spec.auth` block with a type discriminator (simple/sigv4/oauth2) and a Secret reference. ExternalModel bindings can optionally override the provider-level auth, enabling scenarios where the same provider endpoint requires different credentials for different model mappings. All credentials are stored in same-namespace Kubernetes Secrets with the `api-key` data key convention.

The legacy migration controller provides backward compatibility with the earlier `maas.opendatahub.io` API group by watching unstructured CRs and creating equivalent resources under `inference.opendatahub.io`. This enables zero-downtime migration for users who deployed ExternalModel CRs under the previous API group.
