## Purpose

**Short**: Envoy External Processing (ext_proc) gRPC service and Kubernetes controllers that enable multi-provider LLM inference routing through the AI Gateway.

**Detailed**: AI Gateway Payload Processing is the data-plane intelligence layer of the RHOAI AI Gateway. It runs as a gRPC External Processor (ext_proc) that Envoy invokes on every inference request, enabling a plugin pipeline to inspect and mutate request/response headers and bodies. This pipeline performs model-to-provider resolution, API format translation (OpenAI, Anthropic, Azure, Bedrock, Vertex), credential injection (API key, SigV4, OAuth2), NeMo guardrail enforcement, usage metering, and weighted provider selection.

The component also runs three Kubernetes controllers. The **ExternalProvider controller** reconciles `ExternalProvider` CRs into ExternalName Services, Istio ServiceEntry, and DestinationRule resources that establish network connectivity to external LLM providers. The **ExternalModel controller** reconciles `ExternalModel` CRs into Gateway API HTTPRoute resources that wire client-facing model names to their backing providers via the platform's ingress Gateway. A **legacy migration controller** watches the deprecated `maas.opendatahub.io/v1alpha1` ExternalModel CRDs and automatically creates equivalent `inference.opendatahub.io` resources, bridging the API transition. The ext_proc server and controllers share a single process managed by controller-runtime, with the ext_proc server wrapped by a dynamic-metadata interceptor that converts plugin-set pseudo-headers into Envoy DynamicMetadata for downstream filter consumption.

## Architectural Analysis

The component bridges two distinct architectural roles — a Kubernetes controller that manages declarative networking resources and a real-time gRPC request processor — within a single controller-runtime manager process. This single-process design keeps resource watches and ext_proc serving under one leader-election boundary and simplifies deployment (one Helm release, one ServiceAccount), but it means the ext_proc server's availability is tied to controller reconciliation health.

The plugin architecture is a key design decision: the upstream `llm-d-inference-payload-processor` framework provides the ext_proc handler, plugin registry, and configuration loader, while this repository registers its own "downstream" plugins (model-provider-resolver, api-translation, apikey-injection, nemo guardrails, external-metering, stream-usage-enforcer, maas-headers-guard) on top of the upstream in-tree plugins (body-field-to-header, model-selector, session-affinity, etc.). The `run()` function in `cmd/runner.go` is a hand-maintained copy of the upstream runner that exists solely to interpose the `dynamicmetadata.WrapServer` wrapper — a maintenance debt surface that must be re-diffed on every dependency bump.

Provider authentication is CRD-driven: `ExternalProvider.spec.auth` selects from `apikey`, `sigv4`, or `oauth2` types, each backed by a Secret reference. The apikey-injection plugin reconciles Secrets into an in-memory store and injects credentials at request time. A security-positive pattern is the `ValidateConnectionSecurity` check that rejects plaintext transport when auth is configured (CWE-319 mitigation).

The ExternalModel controller creates HTTPRoute resources with multiple rules per provider ref — header-matched rules for provider selection by the IPP's `x-ipp-selected-provider` header, plus fallback rules routing to the first provider. This enables the plugin pipeline to dynamically choose providers based on model configuration, weights, and scoring, with Envoy performing the actual traffic split via HTTPRoute backend refs.

Hub mode (cross-cluster routing) is supported through dual deployments with different plugin chains and EnvoyFilter anchor positions, enabling PROPOSE and TRANSFORM processing phases. Loop detection via `X-Origin-Cluster` / `CLUSTER_NAME` prevents infinite routing cycles.

| Dimension | Mechanism | Enforced By | Gaps / Risks |

| Data storage | Per-namespace CRs (ExternalModel, ExternalProvider) | Kubernetes | In-memory plugin stores (model-provider-resolver, apikey-injection) are process-wide, not namespace-partitioned |
| Network traffic | Per-provider Istio ServiceEntry + DestinationRule | Istio | No NetworkPolicy generated; relies on platform-level network policies |
| Compute & resources | Shared controller-runtime manager process | N/A | Single replica by default; no per-tenant resource quotas |
| Configuration & secrets | Per-namespace Secrets referenced by ExternalProvider CRs | Kubernetes | Cluster-scoped Secret watch required for multi-namespace mode |
