## Purpose

**Short**: Envoy ext_proc filter and Kubernetes controller that routes, translates, authenticates, and meters inference requests to external LLM providers via the AI Gateway.

**Detailed**: AI Gateway Payload Processing (internally called "BBR" — Body-Based Router) is the data-plane intelligence layer of the RHOAI AI Gateway. It runs as an Envoy external processing (ext_proc) filter attached to the platform's Istio Gateway, intercepting every inference request passing through the gateway.

The component has two complementary halves. The **controller half** watches `ExternalModel` and `ExternalProvider` custom resources and reconciles them into Gateway API `HTTPRoute` resources, Istio `ServiceEntry`/`DestinationRule` pairs, and Kubernetes `ExternalName` Services — wiring external LLM endpoints (OpenAI, Anthropic, Azure OpenAI, Vertex AI, AWS Bedrock) into the service mesh with TLS origination. The **plugin half** operates inside the ext_proc request/response pipeline, performing model-to-provider resolution with weighted traffic splitting, multi-format API translation (OpenAI ↔ Anthropic ↔ Vertex ↔ Bedrock ↔ Azure), credential injection (API keys, AWS SigV4, GCP OAuth2), token metering via an external metering service, and optional NeMo Guardrails content filtering.

The plugin framework is built on the upstream [llm-d Inference Payload Processor](https://github.com/llm-d/llm-d-inference-payload-processor) (IPP), which provides the ext_proc server, plugin lifecycle management, and CycleState request context. This component registers its domain-specific plugins into that framework and ships custom controllers alongside it.

## Architectural Analysis

The AI Gateway Payload Processing component employs a **dual-plane architecture** where Kubernetes controllers manage the routing infrastructure declaratively while an inline ext_proc plugin pipeline handles request-time decisions. This separation is deliberate: controllers reconcile networking resources (HTTPRoutes, ServiceEntries, DestinationRules) at the cluster control plane rate, while the plugin pipeline operates at request-per-second scale with in-memory stores that cache controller-produced state. The two planes synchronize through shared CRD watches — both the ExternalModel controller and the model-provider-resolver plugin watch ExternalModel CRs, but the controller materializes networking resources while the plugin caches resolved provider bindings for sub-millisecond lookups during request processing.

The **weighted provider selection** system is a standout design pattern. Each ExternalModel can reference up to 64 ExternalProviderRefs, each with a weight (0–100). The model-provider-resolver plugin performs cumulative-distribution weighted random selection at request time, enabling canary deployments across LLM providers (e.g., 80% OpenAI / 20% Azure) without any gateway configuration reload. A weight of 0 disables a provider ref entirely, providing a kill switch. The selected provider name is written to the `x-ipp-selected-provider` header, which the HTTPRoute rules then use for backend selection — a clean separation between selection logic (plugin) and routing enforcement (Envoy).

The **API translation layer** uses a registry pattern keyed by `(inputFormat, outputFormat)` tuples, supporting combinations like OpenAI→Anthropic, OpenAI→Vertex Gemini, OpenAI→Vertex Anthropic (for Claude on Vertex AI), and passthrough variants. The `ConfigAwareTranslator` interface extends the base translator for providers requiring per-model configuration — notably Vertex Anthropic, which needs the `anthropic_version` string injected from ExternalModel config. The Anthropic translator is the most complex, performing deep structural transformations including system message extraction, tool call format conversion, image content block mapping, and stop reason remapping. The field-stripping mechanism (used by Azure and Vertex OpenAI) handles provider-specific response noise via dot-notation path expressions with array iteration support.

The **credential management** architecture demonstrates defense-in-depth. The apikey-injection plugin's Secret informer is scoped by label selector (`inference.llm-d.ai/ipp-managed=true`), limiting the blast radius even though the RBAC grants broader Secret read access. Three auth generators cover the major cloud provider patterns: simple API key injection (with provider-specific header names — `Authorization: Bearer` for OpenAI, `x-api-key` for Anthropic, `api-key` for Azure), GCP OAuth2 with token caching and 5-minute refresh margin, and AWS SigV4 with full request signing including body hashing. The `none` auth type strips authorization headers entirely, supporting hub-to-spoke mTLS scenarios where no application-level credentials are needed.

The **external metering** plugin implements both budget enforcement (pre-request balance checking) and usage reporting (post-response CloudEvents emission). The streaming variant handles the complexity of token usage data split across Envoy chunk boundaries by accumulating raw response data and re-parsing on the final chunk. Metering defaults to fail-open — if the metering service is unavailable, requests proceed rather than blocking. This is a pragmatic choice for a data-plane component where availability typically outweighs strict budget enforcement. The NeMo Guardrails integration takes the opposite stance: fail-closed on unknown status codes, prioritizing content safety over availability.
