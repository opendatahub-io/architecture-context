## Purpose

**Short**: Container image repository that builds and maintains workbench (Jupyter, Code Server, RStudio) and pipeline runtime images for Red Hat OpenShift AI.

**Detailed**: The notebooks-downstream repository is a downstream fork of the upstream opendatahub-io/notebooks project. It produces approximately 35 distinct container images that serve as interactive data science environments (workbenches) and pipeline execution environments (runtimes) within the RHOAI platform. Workbench images include Jupyter Notebook (minimal, data science, PyTorch, TensorFlow, TrustyAI variants), VS Code-based Code Server, and RStudio Server. Runtime images provide stripped-down execution environments for Elyra and Kubeflow Pipelines (KFP).

Each image variant is built for multiple accelerator backends (CPU, NVIDIA CUDA 12.6, AMD ROCm 6.2.4) and Python versions (3.11, 3.12), producing a matrix of ~35 images. The repository uses OpenShift ImageStream resources to manage 6 historical versions (N through N-5) per image type, enabling users to select specific software versions. Images are built by Konflux via Tekton pipelines and published to quay.io registries. The ODH Notebook Controller (from the odh-notebook-controller component) is responsible for launching these images as Kubernetes Pods when users create Notebook CRs.

The build process uses a sandboxed Makefile system with a Go-based `buildinputs` tool that analyzes Dockerfile dependencies to create minimal build contexts. Dependency management is handled via Pipenv (Pipfile.lock) with micropipenv for deterministic in-container installation. Image digests and commit hashes are tracked in `params.env` and `commit.env` files, injected into ImageStream definitions via Kustomize replacements.

## Purpose

**Short**: notebooks-downstream produces pre-configured container images for Jupyter notebooks, RStudio, and Code Server workbenches, bundled with ML/data science frameworks and platform integration SDKs for use in RHOAI workbench environments.

**Detailed**: notebooks-downstream is the downstream build repository for Red Hat OpenShift AI notebook and workbench container images. It produces multiple image variants spanning different IDE environments (JupyterLab, RStudio, Code Server), ML frameworks (PyTorch with CUDA, TensorFlow, TensorFlow with ROCm), and Python runtime versions. Each image bundles pinned Python dependencies from `requirements.txt` files generated from `Pipfile.lock`, along with Go-based build tooling (`check-payload` for FIPS compliance validation, `buildkit` for container image analysis). The images are consumed by the ODH Notebook Controller, which deploys them as StatefulSet-managed workbench pods within user namespaces. The repository also contains CI test infrastructure (`ci/cached-builds/make_test.py`) that exercises the full deploy-test-undeploy lifecycle of each image variant against Kubernetes. Key platform integrations bundled in the runtime images include `codeflare-sdk` for distributed compute job submission, `boto3`/`minio` for S3-compatible storage access, `kubernetes`/`openshift-client` for cluster API interaction, and database clients (`psycopg`, `pymongo`, `mysql-connector-python`) for data source connectivity.

## Architectural Analysis

The notebooks-downstream repository is architecturally unusual compared to typical platform components -- it is not an operator or a service, but rather a container image factory. Its primary output is ~35 container images covering a matrix of workbench types (Jupyter, Code Server, RStudio) × accelerator backends (CPU, NVIDIA CUDA, AMD ROCm) × Python versions (3.11, 3.12). This matrix-driven design creates significant maintenance complexity: each new Python version or accelerator adds a row across all image types, and each new ML framework version must be coordinated across all variants that include it.

The build architecture uses a layered Dockerfile pattern where accelerator-specific stages (cuda-base, rocm-base) are shared across image types. CUDA images use multi-stage builds with architecture-conditional stages (`cuda-base-amd64` vs `cuda-base-arm64`) selected via `TARGETARCH`, enabling multi-architecture builds from a single Dockerfile. The ROCm images follow a simpler pattern since ROCm only targets x86_64. A notable optimization is the `scripts/sandbox.py` + `bin/buildinputs` Go tool that analyzes Dockerfile `COPY` directives to create minimal build contexts, avoiding sending the entire repository to the container engine.

The image versioning strategy uses OpenShift ImageStreams with 6 historical versions per image type (N through N-5), allowing users to pin to specific software versions (e.g., "2024.2" with CUDA 12.4 and PyTorch 2.4). This is managed through a sophisticated Kustomize replacement system: `params.env` and `commit.env` files contain image digests and commit hashes that are injected into ImageStream tag definitions via ~120 Kustomize replacements. The `ci/check-params-env.sh` script (781 lines) validates image references, sizes (with 10% / 100MB thresholds), and metadata consistency. This approach provides strong auditability -- every deployed image can be traced to a specific source commit.

The FIPS compliance story is interesting: the images are primarily Python interpreters running on UBI9, which inherit FIPS-compliant OpenSSL from the base image. The only explicitly FIPS-compiled component is `mongocli`, built in a multi-stage Dockerfile with `CGO_ENABLED=1 -tags strictfipsruntime`. The GitHub Actions workflow includes a check-payload FIPS validation step. However, the CUDA and ROCm vendor libraries are not FIPS-certified, which is an inherent limitation for GPU-accelerated workloads.

A significant gap identified in this analysis is the absence of AIPCC base image adoption. All images use standard UBI9 or CentOS Stream 9 base images with CUDA/ROCm installed from vendor repositories. Migration to AIPCC base images would provide standardized accelerator support, the RHEL AI Python Package Index for secure package builds, and consistent versioning across RHOAI components. Given that this repository produces the largest number of Python-heavy container images in the platform, it represents the most impactful AIPCC adoption candidate.

## Architectural Analysis

- **Multi-variant image strategy:** The repository produces a matrix of notebook images across three dimensions: IDE environment (JupyterLab, RStudio, Code Server), ML framework (datascience/minimal, PyTorch with CUDA, TensorFlow, ROCm variants for AMD GPUs), and base OS/Python version (UBI9 with Python 3.11). The CI test harness (`make_test.py`) maps each variant to appropriate deploy/test/undeploy make targets, with special handling for ROCm, RStudio, and CUDA variants. This multi-variant approach allows RHOAI to offer purpose-built workbench environments while sharing a common dependency management and testing strategy.
- **Dependency management approach:** Python dependencies are managed through `Pipfile.lock` and converted to hash-pinned `requirements.txt` files via `scripts/sync-requirements-txt.sh`. This ensures reproducible builds with cryptographic verification of every package. The PyTorch runtime additionally configures `https://download.pytorch.org/whl/cu126` as an extra index URL for CUDA 12.6-specific wheel packages. Go dependencies in `scripts/buildinputs/` and `scripts/check-payload/` are separate modules used for build-time tooling rather than runtime code.
- **Platform authentication delegation:** The notebook images themselves do not implement authentication. When deployed by the notebook controller, each pod receives a kube-rbac-proxy sidecar that enforces RBAC-based authentication before proxying requests to the notebook server. This is the standard RHOAI 3.x authentication pattern.
- **Platform integration via bundled SDKs:** Rather than building platform integrations into the images at the infrastructure level, the notebooks bundle client libraries (`codeflare-sdk`, `kubernetes`, `boto3`, `minio`, database drivers) that enable data scientists to interact with platform services from within their notebook sessions. The `codeflare-sdk` dependency is notable as a direct integration with another RHOAI platform component (CodeFlare/MCAD).
