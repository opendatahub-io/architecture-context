## Purpose

**Short**: Builds and publishes container images for data science workbenches (Jupyter, CodeServer, RStudio) and Elyra-compatible runtimes across multiple Python versions and GPU accelerator targets.

**Detailed**: The notebooks-downstream repository is a downstream productization of the OpenDataHub notebooks project. It defines Dockerfiles, build tooling, CI/CD pipelines, and Kubernetes manifests for approximately 32 container image variants that serve as the interactive development environments and pipeline runtimes for Red Hat OpenShift AI.

Each image variant is a combination of four axes: workbench type (Jupyter Minimal, Data Science, PyTorch, TensorFlow, TrustyAI, CodeServer, RStudio), Python version (3.11, 3.12), GPU accelerator (CPU, NVIDIA CUDA 12.6.3, AMD ROCm 6.2.4), and base OS (UBI9, CentOS Stream 9, RHEL9). The images are built using multi-stage Dockerfiles with a shared base layer pattern, ensuring consistent tooling (micropipenv, OpenShift CLI, skopeo) across all variants while layering in specialized libraries for each workbench type.

The repository does not contain application source code in the traditional sense. Instead, it defines the build recipes (Dockerfiles), dependency lock files (Pipfile.lock), deployment manifests (OpenShift ImageStreams via Kustomize), and CI/CD pipelines (GitHub Actions and Tekton/Konflux) that produce the final container images published to `quay.io/modh/` and `quay.io/opendatahub/workbench-images`.

## Architectural Analysis

The notebooks-downstream repository implements a **hierarchical container image factory** pattern where each workbench type builds upon a shared base layer. The `base` stage (UBI9 + Python + micropipenv + oc client + skopeo) is reused across all variants, with specialized stages layering in framework-specific dependencies. This multi-stage build strategy keeps the shared tooling consistent while allowing each variant to diverge only where needed. The CUDA variants add a particularly complex intermediate layer with multi-architecture support (`TARGETARCH` ARG switching between amd64 and arm64 CUDA packages), cuDNN, NCCL, and development tools.

A notable architectural decision is the **NGINX reverse proxy pattern** used by CodeServer and RStudio workbenches. Unlike Jupyter notebooks which expose their HTTP server directly on port 8888, CodeServer and RStudio run behind NGINX on port 8787. NGINX provides WebSocket upgrade support, custom JSON-formatted activity logging, and FastCGI endpoints (`access.cgi`, `probe.cgi`) that implement a Jupyter-compatible culling API. This allows the ODH Notebook Controller's pod culling system to work identically across all workbench types, despite CodeServer and RStudio having no native Jupyter kernel API. The 20-day proxy timeout (`proxy_read_timeout 20d`) is set to accommodate long-running interactive sessions. Supervisord manages the fcgiwrap process that bridges NGINX to the CGI scripts.

The **ImageStream versioning strategy** maintains 6 concurrent image versions (N through N-5) in each ImageStream, allowing platform operators to offer multiple release tracks simultaneously. Annotations on each tag carry structured metadata (`opendatahub.io/notebook-software`, `opendatahub.io/notebook-python-dependencies`) consumed by the ODH Dashboard to display software version information to users. The `opendatahub.io/image-tag-outdated: "true"` annotation marks older versions for deprecation warnings. Kustomize ConfigMapGenerator injects digest-pinned image references from `params.env`, ensuring reproducible deployments. The replacement mechanism uses over 1,290 field path replacements to wire ConfigMap values into ImageStream tag references.

The build system uses a **smart incremental build** approach: the `buildinputs` Go CLI tool performs static analysis of Dockerfiles to determine the minimal set of source files needed for each build, and `sandbox.py` creates isolated build directories containing only those dependencies. This prevents accidental inclusion of unrelated files in build contexts and enables efficient CI matrix builds where only images affected by a PR's changes are rebuilt. The CI matrix generation (`gen_gha_matrix_jobs.py`) parses the Makefile's `all-images` target and cross-references it with `git diff` to determine which images need rebuilding.

A key risk area is the **AIPCC gap**: all images install Python packages but none use AIPCC base images. The images use standard UBI9/C9S/RHEL9 Python base images with `micropipenv` for package deployment. While this works functionally, it means Python packages are sourced from the public PyPI index rather than the RHEL AI Python Package Index, which may not meet Red Hat's product security requirements for fully vetted package supply chains. Additionally, the absence of `rpms.lock.yaml` files on this branch means OS-level RPM dependencies are not hermetically locked, though downstream release branches likely add these.
