## Purpose

**Short**: Argo Workflows is a Kubernetes-native workflow engine that powers the Data Science Pipelines execution backend in RHOAI.

**Detailed**: Argo Workflows provides the core workflow execution engine for Data Science Pipelines in Red Hat OpenShift AI. It defines and manages Kubernetes Custom Resources (Workflow, CronWorkflow, WorkflowTemplate, ClusterWorkflowTemplate) that represent directed acyclic graph (DAG) workflows. The workflow controller watches these CRDs and creates Pods to execute each step, managing the full lifecycle from scheduling through completion, including artifact management, caching, retry logic, and garbage collection.

The system consists of three binaries built from a single Go module: the `workflow-controller` which reconciles workflow CRDs into pods, the `argo server` which provides a gRPC/HTTP API gateway and web UI, and the `argoexec` executor which runs as a sidecar/init container within workflow pods to manage artifacts and template execution. In the RHOAI context, only the workflow-controller and argoexec images are built via Konflux; the argo server is not shipped as a separate Konflux component (it is bundled into the Data Science Pipelines Operator deployment).

The RHOAI distribution uses UBI9-minimal base images and builds with Go 1.26 using native FIPS 140-3 cryptography (`GOFIPS140=v1.0.0`). The binaries are statically linked with `CGO_ENABLED=0` and use Go's native FIPS module rather than OpenSSL, enabled via `go.mod` directive `godebug fips140=on`.

## Architectural Analysis

Argo Workflows is a mature, feature-rich workflow engine that has been adapted for RHOAI's Data Science Pipelines use case. The architecture follows a classic Kubernetes operator pattern with a controller loop, but extends it significantly with three distinct execution models: standard Pod-per-step execution, agent-based execution for HTTP/plugin templates via WorkflowTaskSet CRDs, and the emissary executor pattern where argoexec acts as a process proxy inside workflow pods.

The controller's concurrency model is well-tuned for high-throughput scenarios. It uses separate work queues for different concerns (workflow reconciliation, pod cleanup, archival, cron scheduling) with configurable worker counts (32 workflow workers by default). Namespace-level parallelism (`namespaceParallelism`) and semaphore-based synchronization (`SyncManager`) provide multi-tenancy aware rate limiting. The health check at `/healthz` specifically monitors for stuck workflows (unreconciled beyond `HEALTHZ_AGE`), which is a practical liveness indicator for detecting controller deadlock.

The FIPS story in this repository is notable: it has recently transitioned from the OpenSSL-based FIPS approach (`GOEXPERIMENT=strictfipsruntime`) to Go 1.26's native FIPS 140-3 module (`GOFIPS140=v1.0.0` + `godebug fips140=on`). This is evidenced by commits `5363dfa59` ("Move FIPS 140 configuration from Dockerfiles to go.mod") and `736b2245c` ("Switch from OpenSSL FIPS to native Go FIPS 140-3 module"). The binaries are now statically linked (`CGO_ENABLED=0`) with `-tags no_openssl`, which represents a significant departure from the traditional check-payload requirement of dynamic linking with OpenSSL. This is only valid for Go 1.26+ on RHEL 10+ where native Go FIPS is accepted.

The authentication system in the argo server component is sophisticated, supporting three modes (client/server/SSO) with a clean interceptor chain. The SSO implementation uses go-jose for JWT encryption with RSA-2048 key wrapping and AES-256-GCM content encryption, storing the private key in a Kubernetes Secret. The RBAC delegation model allows SSO-authenticated users to be mapped to service accounts via annotation-based rules, which is a flexible but complex pattern that requires careful configuration. The `InsecureSkipVerify` usage is limited to the internal gRPC-gateway→gRPC loopback on localhost, which is architecturally acceptable.

In the RHOAI context, only two of the three binaries are shipped as Konflux images: workflow-controller and argoexec. The argo server (CLI binary with embedded UI) is not built as a separate Konflux component — it is deployed as part of the Data Science Pipelines stack. The `rhoai/` directory contains legacy UBI8-based Dockerfiles that have been superseded by the Konflux Dockerfiles in `argo-argoexec/` and `argo-workflowcontroller/`, which use UBI9-minimal base images.
