## Purpose

**Short**: Argo Workflows is a container-native workflow engine for orchestrating parallel jobs on Kubernetes, used as the execution backend for Data Science Pipelines in RHOAI.

**Detailed**: Argo Workflows implements a Kubernetes CRD-based workflow engine that allows users to define workflows where each step is a container. It supports both sequential (Steps) and parallel (DAG) execution patterns, making it suitable for machine learning pipelines, data processing, and CI/CD workflows. The component consists of two primary binaries: a workflow controller that watches Workflow CRDs and creates execution pods, and an API server (argo-server) that provides REST/gRPC APIs and a web UI.

In the RHOAI context, Argo Workflows serves as the execution engine underlying Data Science Pipelines (DSP). The DSP operator deploys and configures the workflow controller and argoexec executor to run ML pipeline steps. The Argo Server component (web UI and API) is typically not deployed in RHOAI — instead, DSP provides its own API layer. The two Konflux-built images (`argo-workflowcontroller` and `argo-argoexec`) are the only artifacts shipped for RHOAI.

## Architectural Analysis

Argo Workflows in the RHOAI context is a downstream fork of the upstream CNCF Argo Workflows project (`argoproj/argo-workflows`), adapted for Red Hat's Data Science Pipelines. The component ships two container images through Konflux: `argo-workflowcontroller` (the control plane) and `argo-argoexec` (the execution plane injected into workflow pods). The argo-server (API/UI) is not built via Konflux for RHOAI, as DSP provides its own API layer atop the Workflow CRDs.

The controller uses a direct client-go informer pattern rather than the controller-runtime framework common in other RHOAI operators. It maintains SharedIndexInformers for 8 resource types (Workflows, Pods, WorkflowTemplates, ClusterWorkflowTemplates, ConfigMaps, WorkflowTaskSets, WorkflowArtifactGCTasks, WorkflowTaskResults) with a 20-minute resync period. This design supports high-throughput workflow processing with configurable parallelism — 32 workflow workers by default, plus dedicated worker pools for TTL management (4), pod cleanup (4), cron scheduling (8), and archiving (8).

The FIPS compliance approach is notable: rather than using the traditional `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime` pattern with dynamic OpenSSL linking, this component uses Go 1.24+'s native FIPS 140-3 module via `GOFIPS140=v1.0.0` with `CGO_ENABLED=0` and `-tags no_openssl`. This produces statically linked binaries that implement FIPS cryptography through Go's built-in module rather than OpenSSL, which is a newer pattern. The `godebug fips140=on` directive in `go.mod` ensures FIPS mode is enabled at the module level. One crypto concern is the `InsecureSkipVerify: true` in the self-signed TLS configuration (`util/tls/tls.go:128`), though this is expected behavior for self-signed certificates and is only used when no external TLS secret is provided.

The argoexec binary operates as an "emissary" — it wraps user containers within workflow pods, intercepts their lifecycle signals, captures stdout/stderr, manages artifact collection to/from object storage, and reports exit codes and results back through the WorkflowTaskResult CRD. This sidecar-like pattern means argoexec has no network listeners of its own but requires access to the Kubernetes API (for status updates) and potentially to artifact storage (S3/GCS/Azure).

Build hermeticity is well-established with `rpms.lock.yaml` covering OS packages (mailcap across 3 architectures), `go.sum` for Go dependencies, and `yarn.lock` for UI dependencies. However, no Hermeto/cachi2 prefetch integration was detected in the Konflux Dockerfiles, which means Go module downloads during build are not fully hermetic. The `rhoai/` directory contains legacy UBI8-based Dockerfiles that appear to predate the Konflux migration and use `registry.redhat.io/ubi8/go-toolset:1.21` — these are not used by the current Konflux build pipeline.
