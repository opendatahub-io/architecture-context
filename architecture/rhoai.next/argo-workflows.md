## Purpose

**Short**: Argo Workflows is the workflow execution engine that powers Data Science Pipelines in Red Hat OpenShift AI, orchestrating container-native workflows as Kubernetes custom resources.

**Detailed**: Argo Workflows provides the core workflow orchestration layer for RHOAI's Data Science Pipelines component. It consists of two primary runtime binaries: the **workflow-controller**, which watches Workflow CRs and manages their lifecycle by creating pods, handling artifacts, and tracking state; and **argoexec**, a sidecar/init container injected into workflow pods to manage artifact collection, script execution, and container lifecycle within individual workflow steps.

The argo-server component (included in base manifests but not in the Konflux build pipeline) provides an optional API server with gRPC and REST endpoints for workflow management, artifact browsing, SSO authentication, and a web UI. In the RHOAI context, the Data Science Pipelines operator typically deploys the workflow-controller and argoexec images while the argo-server may be disabled or fronted by the DSP API server.

The repository is a downstream fork of [argoproj/argo-workflows](https://github.com/argoproj/argo-workflows) carrying Red Hat-specific build configuration (Konflux Dockerfiles, UBI base images, FIPS-compliant build flags, RPM lock files) while tracking upstream releases.

## Architectural Analysis

Argo Workflows follows a controller-pattern architecture where the workflow-controller acts as a reconciliation loop over Workflow CRs. When a Workflow is submitted, the controller decomposes the DAG/steps into individual nodes, creates pods for each step with argoexec as the wait container, and tracks completion through WorkflowTaskResult and WorkflowTaskSet CRs. The controller supports leader election via Kubernetes Lease objects, allowing multiple replicas for high availability — only the elected leader reconciles workflows, while standbys serve dummy Prometheus metrics.

The FIPS posture is notable: the Konflux builds use Go 1.26's native `GOFIPS140=v1.0.0` software FIPS module with `CGO_ENABLED=0` and `-tags no_openssl`, producing statically linked binaries that use Go's built-in FIPS 140 validated cryptographic module rather than the traditional CGO+OpenSSL approach. The `godebug fips140=on` directive in go.mod enforces FIPS mode at runtime. This approach differs from the check-payload expectation of dynamically linked binaries with OpenSSL — the Go 1.24+ FIPS software module path is a newer compliance mechanism that may require updated validation tooling.

The TLS implementation in `util/tls/tls.go` generates self-signed ECDSA P-256 certificates for the argo-server, with configurable minimum TLS version passed from server startup. The internal gRPC gateway proxy uses `InsecureSkipVerify: true` for the localhost loopback connection between the HTTP gateway and gRPC server — this is architecturally expected since both endpoints share the same process. The SSO subsystem also supports configurable `InsecureSkipVerify` for OIDC provider connections, which is a user-facing configuration option.

Artifact storage is pluggable through a repository abstraction supporting S3-compatible stores (MinIO, AWS S3), Google Cloud Storage, Azure Blob Storage, Alibaba OSS, and HDFS. Workflow archival uses optional SQL persistence (MySQL or PostgreSQL) configured via the workflow-controller ConfigMap, with SQLite used for the local workflow store in the argo-server.
