## Purpose

**Short**: Extends any Gateway API-compatible proxy (e.g. Envoy Gateway) into an inference-aware gateway that performs KV-cache-aware, LoRA-adapter-aware request scheduling for Kubernetes-hosted LLM serving.

**Detailed**: Gateway API Inference Extension (IGW) is an upstream Kubernetes SIG project that optimizes self-hosting generative AI models on Kubernetes. It works by leveraging Envoy's External Processing (ext-proc) filter to intercept inference requests at the gateway layer and make intelligent routing decisions based on real-time model server metrics—KV-cache utilization, queue depth, running requests, and LoRA adapter availability.

The project comprises two primary gRPC servers: the Endpoint Picker (EPP) and the Body Based Router (BBR). The EPP is the core intelligence, implementing a pluggable scheduling framework that selects the optimal model-serving endpoint for each request based on configurable scoring, filtering, and flow control plugins. The BBR is an optional upstream ext-proc that parses HTTP request bodies (e.g. OpenAI chat completion format) to extract routing metadata like model names into headers for gateway-level routing.

The project defines Kubernetes-native APIs through CRDs: `InferencePool` (GA, v1) groups model server pods for load balancing, `InferenceObjective` and `InferenceModelRewrite` (experimental, v1alpha2) enable SLO-driven scheduling and model name aliasing, and `EndpointPickerConfig` (v1alpha1) provides the pluggable configuration for scheduling profiles, data layer, and flow control. This fork under `red-hat-data-services` tracks the upstream `kubernetes-sigs/gateway-api-inference-extension` for inclusion in RHOAI.

## Architectural Analysis

The EPP architecture is fundamentally a plugin-based request processing pipeline. When Envoy receives an inference request, its ext-proc filter calls out to the EPP via gRPC. The EPP then: (1) parses the request using a configurable parser (OpenAI, vLLM gRPC, or passthrough), (2) runs request control plugins that can admit, annotate, or reject the request, (3) executes a scheduling pipeline of filter → score → pick to select the best backend endpoint, and (4) returns the routing decision to Envoy which forwards the request.

The scheduling framework supports multiple named profiles, each composed of ordered plugin chains. Built-in scorers assess endpoints on KV-cache utilization, queue depth, running requests, LoRA affinity, prefix cache affinity, and predicted latency. The flow control layer—gated behind the `flowControl` feature gate—adds fairness scheduling (global strict, round-robin), ordering (EDF, FCFS, SLO-deadline), saturation detection, and usage limits via InferenceObjective priorities.

A key architectural feature is the pluggable data layer, which decouples metric collection from scheduling. The data layer scrapes Prometheus-format metrics from model server pods at configurable intervals (default 50ms), maintaining a real-time view of endpoint health in an in-memory datastore. This datastore is shared between the scheduling pipeline and the controller reconciliation loops.

The BBR operates as an independent ext-proc server positioned before the gateway's routing layer. It extracts model names from request bodies and sets them as HTTP headers, enabling the gateway to route based on model name without requiring the full ext-proc round-trip for body parsing. The BBR also supports a base-model-to-header plugin that maps LoRA adapter model names to their base model names via a ConfigMap lookup.

Both servers integrate with controller-runtime for Kubernetes resource reconciliation. The EPP watches InferencePool, InferenceObjective, InferenceModelRewrite, and Pod resources; the BBR watches ConfigMaps for base model mapping configuration. TLS is enabled by default on all gRPC endpoints, using either provided certificates (with automatic reloading via fsnotify) or self-signed certificates generated at startup.

An optional latency predictor sidecar (Python-based) provides ML-driven latency estimation using XGBoost models, with separate training and prediction servers. This is deployed as a sidecar container alongside the EPP when enabled.
