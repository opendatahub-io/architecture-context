## Purpose

**Short**: Extends any Envoy-based Gateway API proxy into an inference gateway that provides intelligent, KV-cache-aware load balancing and request scheduling for self-hosted large language models on Kubernetes.

**Detailed**: Gateway API Inference Extension (also known as Inference Gateway / IGW) is a Kubernetes SIG project that optimizes serving generative AI models. It works by implementing Envoy's External Processing (ext-proc) gRPC protocol to intercept inference requests and responses flowing through any Gateway API-compatible proxy (Envoy Gateway, Istio, GKE Gateway, etc.), enabling intelligent endpoint selection based on real-time model server metrics.

The project consists of two primary components: the Endpoint Picker (EPP) and the Body Based Router (BBR). The EPP is the core scheduling engine that watches InferencePool CRDs to discover model server pods, scrapes their Prometheus metrics (queue depth, KV-cache utilization, running requests, LoRA adapter availability), and uses a pluggable framework of filters, scorers, and pickers to select the optimal backend for each request. The BBR is an optional ext-proc server that parses HTTP request bodies to extract model names and other routing metadata into headers that the gateway can use for routing decisions before the request reaches the EPP.

The project also defines the InferencePool CRD (GA in v1) along with experimental extensions: InferenceObjective (priority and fairness), InferenceModelRewrite (model name routing and traffic splitting), InferencePoolImport (multi-cluster federation), and EndpointPickerConfig (plugin configuration). An optional latency predictor subsystem (Python training/prediction servers + Go async sidecar client) provides TTFT/TPOT prediction capabilities for latency-aware scheduling.

## Architectural Analysis

The Gateway API Inference Extension employs a deeply layered plugin architecture that separates concerns across multiple processing phases. The EPP framework defines distinct plugin types for scheduling (Filter, Scorer, Picker, ProfileHandler), request control (AdmissionPlugin, PrepareDataPlugin, PreRequest, ResponseHeader, ResponseBody), flow control (FairnessPolicy, OrderingPolicy, UsageLimitPolicy, EvictionFilterPolicy, EvictionOrderingPolicy), and data layer (DataSource, EndpointExtractor, K8sNotificationExtractor). This design allows the scheduling algorithm to be fully customized via the EndpointPickerConfig CRD without modifying core code — the same mechanism that enables llm-d to integrate its disaggregated serving scheduler as a plugin.

The data layer subsystem represents a significant architectural evolution. Rather than having the EPP directly scrape model server metrics via hardcoded HTTP clients, the new data layer introduces a pluggable DataSource→Extractor→AttributeMap pipeline. DataSources (HTTP polling, Kubernetes notifications) feed raw data to Extractors that parse it into typed attributes (concurrency, latency, prefix cache state). These attributes are stored in a directed acyclic graph (DAG) with topological ordering that ensures data dependencies are resolved before plugins consume them. This architecture supports heterogeneous model servers and custom metrics without code changes.

The flow control subsystem (behind a feature gate) implements a sophisticated multi-priority queuing system. It uses sharded registries for lock-free hot paths, join-shortest-queue-by-bytes (JSQ-Bytes) distribution, and pluggable fairness/ordering policies. Priority bands are dynamically provisioned via JIT allocation, and each band can have its own fairness policy (global-strict or round-robin) and ordering policy (FCFS, EDF, or SLO-deadline). The eviction system uses a max-min heap for efficient request preemption when capacity is exhausted. This design mirrors production-grade API gateway rate limiting systems but is specialized for inference workloads where request cost (in tokens/bytes) varies dramatically.

The BBR component demonstrates clean separation of the body-parsing concern. By extracting model names from request bodies into headers before the EPP processes the request, the gateway can perform header-based routing (via HTTPRoute rules) without needing to buffer and parse request bodies itself. The BBR plugin framework mirrors the EPP's extensibility — custom request/response processors can be registered via factory functions and configured via CLI flags. The ConfigMap-based LoRA adapter mapping is a practical pattern for environments where adapter-to-base-model relationships change dynamically.

A notable architectural risk is the InsecureSkipVerify=true default for model server metrics scraping. While pragmatic for development environments where model servers don't typically serve TLS, this bypasses certificate validation in production. The configurable nature (via Helm values and plugin parameters) mitigates this, but the default-insecure stance should be documented for security reviews. Similarly, the ext-proc gRPC interface itself has no authentication — security relies entirely on network-level isolation between the gateway and the EPP/BBR pods, typically enforced by Kubernetes namespace boundaries and optional NetworkPolicies.
