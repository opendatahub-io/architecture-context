## Purpose

**Short**: Kubernetes-native inference gateway extension that provides intelligent request routing, model-aware load balancing, and flow control for LLM serving infrastructure via the Envoy ext-proc gRPC protocol.

**Detailed**: The Gateway API Inference Extension is a Kubernetes SIG project that extends Gateway API with inference-specific traffic management capabilities. It introduces custom resources (InferencePool, InferenceObjective, InferenceModelRewrite) that allow platform administrators and workload owners to define inference serving pools, priority-based scheduling objectives, and model name rewriting rules.

The extension operates as an Envoy external processor (ext-proc) filter deployed alongside a Gateway API-compatible ingress controller (Istio, GKE, etc.). It consists of two primary components: the Endpoint Picker (EPP), which performs intelligent request routing by scraping model server metrics (KV cache utilization, queue depth, LoRA adapter state) and applying scheduling algorithms (filter-score-pick pipeline with flow control); and the Body-Based Router (BBR), which inspects HTTP request bodies to extract routing metadata (model names) and set headers for upstream routing decisions.

The project is part of the Kubernetes SIG Network ecosystem and uses the `inference.networking.k8s.io` API group for its stable v1 CRDs. It supports multiple model server backends including vLLM, SGLang, Triton TensorRT-LLM, and trtllm-serve, and integrates with Gateway API providers including Istio and GKE.

## Architectural Analysis

The Gateway API Inference Extension follows a clean separation between control plane (CRD reconciliation) and data plane (ext-proc request processing). The EPP binary combines both roles: its controller-runtime manager watches InferencePool, InferenceObjective, and InferenceModelRewrite CRDs to maintain an in-memory datastore of available endpoints and their metadata, while simultaneously serving Envoy ext-proc gRPC requests using that datastore for scheduling decisions. This co-location avoids the latency of cross-process communication but means the EPP process is stateful -- it must maintain up-to-date views of both the Kubernetes state and real-time model server metrics.

The scheduling pipeline uses a three-phase Filter-Score-Pick pattern inspired by the Kubernetes scheduler. Plugins can be composed into named scheduling profiles, and the flow control layer adds priority-based queuing with fairness enforcement. The flow control system is particularly sophisticated: it uses a supervisor-worker pattern with sharded processing, JSQ-Bytes (Join-Shortest-Queue by bytes) distribution, just-in-time resource provisioning, and head-of-line blocking prevention. This design is critical for multi-tenant inference scenarios where workloads of different priorities share the same model server pool.

The BBR component operates as a separate ext-proc filter earlier in the Envoy filter chain. Its plugin framework is deliberately simpler than EPP's -- it provides RequestProcessor and ResponseProcessor interfaces for body field extraction and header mutation. The default plugins extract the `model` field from OpenAI-compatible JSON request bodies and resolve LoRA adapter names to base model names via ConfigMap-backed mappings. This separation allows BBR to run without the heavyweight scheduling state that EPP maintains.

A notable architectural decision is the metrics-driven endpoint selection. Rather than relying solely on Kubernetes readiness probes or connection-level load balancing, EPP actively scrapes Prometheus metrics from each model server pod (KV cache utilization, queue depth, running request count, LoRA adapter state). This gives the scheduler real-time visibility into model server capacity, enabling cache-aware routing and LoRA-aware endpoint selection that connection-level balancers cannot achieve. The tradeoff is the 50ms default scrape interval, which adds operational overhead but provides the granularity needed for latency-sensitive inference workloads.

The project's multi-provider architecture (Istio, GKE, standalone/sidecar mode) is well-abstracted through Helm chart parameterization. The standalone mode embeds an Envoy sidecar with the EPP container, providing a self-contained deployment that doesn't require a cluster-wide gateway. This is useful for development and for environments where modifying the cluster ingress is not feasible. The Envoy sidecar configuration in the standalone chart reveals the expected ext-proc integration pattern: an HTTP connection manager filter chain with ext_proc pointing to localhost:9002 with h2 ALPN and TLS, plus circuit breaker limits of 40,000 connections/requests.

The latency predictor subsystem is architected as an optional enhancement that brings ML-based scheduling. It uses a dual-server design where a single training server maintains models on persistent storage and multiple prediction servers download and serve them via HTTP. The coalescing dispatcher in the Go async client batches concurrent prediction requests into mega-batches, reducing per-request overhead. The system supports three model types (Bayesian Ridge for simplicity, XGBoost for accuracy, LightGBM for speed) with features including queue-gated ensemble models and quantile regression for p90 latency predictions.
