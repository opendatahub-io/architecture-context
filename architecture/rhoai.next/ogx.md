## Purpose

**Short**: OGX (Llama Stack) is a modular, plugin-based Python API server that provides a unified interface for AI/ML services including inference, agents, safety, RAG, evaluation, and post-training.

**Detailed**: OGX is Red Hat's downstream fork of Meta's Llama Stack project. It provides a standardized API layer that abstracts multiple AI/ML backend providers behind a consistent HTTP interface. The server exposes APIs for LLM inference (including OpenAI-compatible endpoints), agentic workflows with tool use, content safety via shields, vector-based retrieval-augmented generation (RAG), model evaluation and scoring, post-training (fine-tuning), dataset management, file management, and telemetry/observability.

The architecture follows a plugin/provider model where each API type (inference, safety, vector_io, etc.) can be backed by one or more provider implementations. Providers are classified as "inline" (running in-process, e.g., meta-reference GPU inference, FAISS vector store) or "remote" (calling external services, e.g., OpenAI, vLLM, Ollama, AWS Bedrock). The system supports 70+ providers across 11 API types and ships 23 pre-configured distribution templates for common deployment scenarios.

The server is built on FastAPI/Uvicorn with a sophisticated middleware stack including JWT/OAuth2 authentication, Cedar-like access control policies, rate limiting/quotas, distributed tracing (OpenTelemetry), and client version compatibility checking. It supports both HTTP and HTTPS (with optional mTLS), streaming via Server-Sent Events, and can be used as an in-process Python library without network overhead.

## Architectural Analysis

The OGX (Llama Stack) architecture exhibits a clean separation between API protocol definitions, routing logic, and provider implementations. Each of the 11 API types (inference, agents, safety, vector_io, tool_runtime, eval, scoring, post_training, datasetio, telemetry, files) is defined as a Python `Protocol` class with `@webmethod` decorators that declaratively specify HTTP routes, methods, and response types. This protocol-based design enables true duck-typing -- any class implementing the protocol can serve as a provider without inheritance, making the plugin system genuinely extensible.

The routing layer is a key architectural decision: rather than simple dispatch, routers like `InferenceRouter` add orchestration logic -- model type validation, token counting, telemetry metric logging, and streaming transformation. The router dispatches requests to providers via `routing_table.get_provider_impl(resource_id)`, which maps resource identifiers (model_id, shield_id, vector_db_id) to their registered provider implementations. This enables multi-provider configurations where different models can be served by different backends simultaneously.

The authentication and access control system is notably sophisticated for an open-source AI framework. It implements a Cedar-like policy language with permit/forbid rules, resource ownership tracking, and user attribute conditions. The JWT validation path supports both JWKS endpoint verification (with cached key refresh) and RFC 7662 token introspection. However, authentication is entirely optional -- the server operates in unauthenticated mode if no auth configuration is provided, which is a significant deployment consideration for production use.

A notable risk in the current architecture is the reliance on `python-jose` for JWT validation. This library uses pure Python `ecdsa` and `rsa` implementations that are not FIPS-validated. For RHOAI production deployments on OpenShift clusters requiring FIPS compliance, this needs to be addressed -- either by replacing `python-jose` with `PyJWT` backed by `cryptography` (which uses OpenSSL), or by delegating JWT validation to a sidecar like `kube-rbac-proxy`. Additionally, no Konflux Dockerfiles exist on this branch, indicating the component is likely in early stages of productization for RHOAI. The existing Containerfiles use `python:3.12-slim` (not UBI), which would not pass check-payload validation.

The dual storage strategy (KVStore for key-value access + SqlStore for relational data) with four pluggable backends each provides excellent flexibility but also operational complexity. The default SQLite backend is suitable for development but lacks the concurrent access guarantees needed for multi-replica production deployments. The PostgreSQL backend addresses this but requires additional infrastructure. The agent system specifically uses both stores -- KVStore for session/turn state persistence and SqlStore for structured OpenAI Responses API data -- which means production deployments need both storage backends properly configured.
