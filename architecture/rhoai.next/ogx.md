## Purpose

**Short**: OGX (formerly Llama Stack) is an application framework that standardizes building blocks for AI application development, providing unified APIs for inference, RAG, agents, tools, safety, evaluation, and telemetry with a pluggable provider architecture.

**Detailed**: OGX provides a unified API layer that abstracts over multiple AI service backends through a plugin-based provider system. The framework exposes REST APIs (both a native Llama Stack API and OpenAI-compatible endpoints) for inference, agents, safety, vector storage, dataset management, scoring, evaluation, post-training, telemetry, and tool execution. It uses a routing table architecture that maps resource identifiers (models, shields, vector DBs, etc.) to concrete provider implementations, enabling multi-provider deployments from a single server.

The server is built on FastAPI/Uvicorn with ASGI middleware for authentication (OAuth2 JWT/JWKS, token introspection, or custom HTTP delegation), request tracing (OpenTelemetry-compatible), quota enforcement, and client version compatibility checks. An attribute-based access control (ABAC) system enforces fine-grained permissions on resources using owner/role/team/project/namespace attributes. The framework ships pre-built distribution templates for various backends (vLLM, TGI, Ollama, NVIDIA, Fireworks, Together, etc.) and supports both inline (in-process) and remote (API-client) provider modes.

## Architectural Analysis

OGX's architecture centers on a clean separation between API protocol definitions and provider implementations. Each API domain (inference, safety, agents, etc.) is defined as a Python Protocol class decorated with `@webmethod` annotations that declare HTTP routes. At startup, the server dynamically registers these routes on the FastAPI application, binding each to the provider implementation resolved from the YAML run configuration. This design allows the same server binary to behave very differently depending on configuration -- from a lightweight local development server using SQLite and in-process models to a production deployment fronting remote vLLM clusters.

The provider system has two tiers: **inline providers** run within the server process (e.g., meta-reference inference, SQLite vector store, faiss) while **remote providers** are thin client wrappers that delegate to external services (vLLM, TGI, OpenAI, Anthropic, various cloud providers). The routing table layer sits between the API handlers and providers, maintaining a registry of resources (models, shields, datasets, etc.) and routing API calls to the correct provider based on the resource's `provider_id`. Each resource can optionally carry owner metadata for ABAC enforcement.

The authentication architecture is notably flexible: the server can run unauthenticated, with OAuth2 JWT/JWKS validation (supporting Kubernetes service account tokens), OAuth2 token introspection (RFC 7662), or custom HTTP endpoint delegation. When authentication is enabled, the ABAC engine evaluates a declarative policy (permit/forbid rules with conditions) against user attributes extracted from the token. This policy system was introduced in v0.2.10 and replaces the earlier attribute-matching model.

A significant architectural observation is the absence of Dockerfiles and Kubernetes manifests in this repository. OGX is primarily a Python library/framework distributed via PyPI (`llama_stack`). Containerization and Kubernetes deployment are handled by the separate `ogx-distribution` and `ogx-k8s-operator` companion components. This separation keeps the core framework focused on API and provider logic.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | ABAC policy with permit/forbid rules; per-resource owner attributes; auth middleware | Application (AuthenticationMiddleware + is_action_allowed) | Auth is configuration-conditional -- when disabled, all resources are accessible to all users |
| Data storage | Resources carry owner metadata (`ResourceWithOwner`); access filtered by ABAC at routing table layer | Application | No physical data isolation -- multiple tenants share the same KV store and vector databases; isolation is purely logical via ABAC policy |
| Network traffic | No tenant-level network isolation | N/A | Network isolation must be provided externally (Kubernetes NetworkPolicy, Istio) |
| Compute & resources | Quota middleware with per-client rate limiting (authenticated vs anonymous thresholds) | Application (QuotaMiddleware) | Rate limits are per-client, not per-tenant; no compute resource isolation between tenants |
| Configuration & secrets | Provider credentials shared across all tenants; per-request provider data via headers | Application | All tenants share the same provider configurations; credentials injected via environment variables are server-wide |
| API scoping | Routing table filters resources by owner attributes before returning to user | Application | Filter logic depends on correct ABAC policy configuration; misconfigured policy can expose cross-tenant resources |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| KV store (SQLite/PostgreSQL/Redis/MongoDB) | Shared store, key-prefixed per resource | Application-level ABAC filtering |
| Vector databases (SQLite-vec/Chroma/Milvus/PgVector/Qdrant/Weaviate) | Shared database | Application-level ABAC filtering on vector DB resources |
| Inference providers | Shared provider instances | No per-tenant isolation; all tenants use the same provider connection |
