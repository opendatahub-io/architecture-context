## Purpose

**Short**: OGX (Llama Stack) is a modular, plugin-based Python API server that provides a unified interface for AI/ML services including inference, agents, safety, RAG, evaluation, and post-training.

**Detailed**: OGX is Red Hat's downstream fork of Meta's Llama Stack project. It provides a standardized API layer that abstracts multiple AI/ML backend providers behind a consistent HTTP interface. The server exposes APIs for LLM inference (including OpenAI-compatible endpoints), agentic workflows with tool use, content safety via shields, vector-based retrieval-augmented generation (RAG), model evaluation and scoring, post-training (fine-tuning), dataset management, file management, and telemetry/observability.

The architecture follows a plugin/provider model where each API type (inference, safety, vector_io, etc.) can be backed by one or more provider implementations. Providers are classified as "inline" (running in-process, e.g., meta-reference GPU inference, FAISS vector store) or "remote" (calling external services, e.g., OpenAI, vLLM, Ollama, AWS Bedrock). The system supports 70+ providers across 11 API types and ships 23 pre-configured distribution templates for common deployment scenarios.

The server is built on FastAPI/Uvicorn with a sophisticated middleware stack including JWT/OAuth2 authentication, Cedar-like access control policies, rate limiting/quotas, distributed tracing (OpenTelemetry), and client version compatibility checking. It supports both HTTP and HTTPS (with optional mTLS), streaming via Server-Sent Events, and can be used as an in-process Python library without network overhead.

## Purpose

**Short**: Llama Stack distribution server — a FastAPI-based AI application service providing a unified API gateway for inference, safety, vector I/O, evaluation, scoring, and tool-runtime providers through a runtime-configurable plugin architecture.

**Detailed**: ogx is a downstream build of Meta's Llama Stack framework, packaged as a single FastAPI application service for RHOAI. It implements a provider-based plugin architecture where all backend capabilities (inference, safety, vector I/O, dataset I/O, scoring, evaluation, and tool runtime) are resolved at startup from a YAML `StackRunConfig` and dispatched through a common routing table (`CommonRoutingTableImpl`). The server exposes a dynamically-generated HTTP API surface derived from the configured provider set, with optional SSE streaming for inference responses. Authentication is layered via ASGI middleware supporting OAuth2 JWT/JWKS validation, RFC 7662 token introspection, and external custom HTTP auth delegation — all selectable at deployment time. Attribute-based access control (ABAC) enforces per-object authorization on routing table operations (create, read, delete) using the authenticated user's claims. A Streamlit-based UI module connects back to the server's own endpoint for interactive scoring workflows. The architecture has zero hard-coded internal platform dependencies; all inter-component interactions (e.g., connecting to vLLM for inference, or external vector databases) are injected through the provider configuration, making the component self-contained from a code perspective.

## Data Flows

- **Request lifecycle:** Inbound HTTP requests arrive at the uvicorn server (default port 8321) and pass through a middleware chain: `ClientVersionMiddleware` (version compatibility check) → `TracingMiddleware` (W3C trace context propagation, trace ID injection) → optional `AuthenticationMiddleware` (Bearer token extraction, provider-delegated validation) → optional `QuotaMiddleware` (rate limiting per principal) → FastAPI route handler. The route handler resolves the target API implementation through the routing table and dispatches the call, returning either a JSON response or an SSE stream for streaming inference.
- **Provider dispatch:** The `CommonRoutingTableImpl` maintains a registry of `RoutableObjectWithProvider` entries (models, shields, vector DBs, datasets, scoring functions, benchmarks, tool groups). Each API call is resolved to a specific provider implementation via the routing key and provider ID. The `DistributionRegistry` persists the object-to-provider mappings. ABAC checks gate every create, read, and delete operation against the authenticated user's attributes and the configured access policy.
- **Authentication flow:** When `config.server.auth` is set, the `AuthenticationMiddleware` extracts the Bearer token from the `Authorization` header and delegates validation to one of: (1) `OAuth2TokenAuthProvider` — validates JWT via JWKS public keys or introspects the token via RFC 7662 against a configured endpoint; (2) `CustomAuthProvider` — POSTs the token and request context to an external HTTP endpoint and parses the `AuthResponse`. Both providers return a `User` with principal and attributes, which are injected into the request scope for downstream ABAC decisions.
- **Downstream interactions:** The structured facts record 1 integration point and 1 egress destination (api.tavily.com for Tavily search tool runtime). All other downstream connections (inference providers, vector databases, etc.) are runtime-configured and not statically determinable from source code.
- **UI module:** The Streamlit UI module creates a `LlamaStackClient` pointed at `LLAMA_STACK_ENDPOINT` (default `http://localhost:8321`) and invokes the scoring API, forwarding provider API keys from environment variables.

## Architectural Analysis

The OGX (Llama Stack) architecture exhibits a clean separation between API protocol definitions, routing logic, and provider implementations. Each of the 11 API types (inference, agents, safety, vector_io, tool_runtime, eval, scoring, post_training, datasetio, telemetry, files) is defined as a Python `Protocol` class with `@webmethod` decorators that declaratively specify HTTP routes, methods, and response types. This protocol-based design enables true duck-typing -- any class implementing the protocol can serve as a provider without inheritance, making the plugin system genuinely extensible.

The routing layer is a key architectural decision: rather than simple dispatch, routers like `InferenceRouter` add orchestration logic -- model type validation, token counting, telemetry metric logging, and streaming transformation. The router dispatches requests to providers via `routing_table.get_provider_impl(resource_id)`, which maps resource identifiers (model_id, shield_id, vector_db_id) to their registered provider implementations. This enables multi-provider configurations where different models can be served by different backends simultaneously.

The authentication and access control system is notably sophisticated for an open-source AI framework. It implements a Cedar-like policy language with permit/forbid rules, resource ownership tracking, and user attribute conditions. The JWT validation path supports both JWKS endpoint verification (with cached key refresh) and RFC 7662 token introspection. However, authentication is entirely optional -- the server operates in unauthenticated mode if no auth configuration is provided, which is a significant deployment consideration for production use.

A notable risk in the current architecture is the reliance on `python-jose` for JWT validation. This library uses pure Python `ecdsa` and `rsa` implementations that are not FIPS-validated. For RHOAI production deployments on OpenShift clusters requiring FIPS compliance, this needs to be addressed -- either by replacing `python-jose` with `PyJWT` backed by `cryptography` (which uses OpenSSL), or by delegating JWT validation to a sidecar like `kube-rbac-proxy`. Additionally, no Konflux Dockerfiles exist on this branch, indicating the component is likely in early stages of productization for RHOAI. The existing Containerfiles use `python:3.12-slim` (not UBI), which would not pass check-payload validation.

The dual storage strategy (KVStore for key-value access + SqlStore for relational data) with four pluggable backends each provides excellent flexibility but also operational complexity. The default SQLite backend is suitable for development but lacks the concurrent access guarantees needed for multi-replica production deployments. The PostgreSQL backend addresses this but requires additional infrastructure. The agent system specifically uses both stores -- KVStore for session/turn state persistence and SqlStore for structured OpenAI Responses API data -- which means production deployments need both storage backends properly configured.

## Architectural Analysis

**Provider-based plugin architecture.** The core design pattern in ogx is a runtime-configurable provider registry. The `CommonRoutingTableImpl` (`routing_tables/common.py`) acts as a universal dispatcher: it maps routable objects (models, shields, vector DBs, datasets, scoring functions, benchmarks, tool groups) to provider implementations via a `DistributionRegistry`. Provider implementations are constructed at startup by `construct_stack()` from `StackRunConfig` YAML, and the server dynamically generates FastAPI routes for each configured API. This means the HTTP API surface is not statically defined — it varies by deployment configuration. The routing table supports seven API domains: inference, safety, vector_io, datasetio, scoring, eval, and tool_runtime.

**Zero hard-coded platform dependencies.** Unlike most RHOAI components that explicitly reference platform peers (KServe, vLLM, model registry), ogx has no code-level internal platform dependencies. All inter-component connections — inference backends, vector databases, auth providers — are injected via the provider configuration YAML. This makes the component highly portable but means that platform integration is entirely a deployment-time concern. Template configurations (e.g., `remote-vllm`) encode these choices, but the server binary is agnostic. The `Internal Platform Dependencies` table is correctly empty from a source-code evidence perspective.

**Layered authentication with ABAC.** Authentication is implemented as a composable middleware chain (`server.py` lines 447-450). The factory pattern in `auth_providers.py` (line 338-348) selects between OAuth2 JWT/JWKS, RFC 7662 token introspection, and custom HTTP delegation based on `AuthProviderType`. Once authenticated, the user principal and attributes flow into the request scope and are consumed by ABAC checks in the routing table (`common.py` lines 171, 178, 195). The ABAC model is operation-gated: `is_action_allowed()` evaluates policy rules against the action (create/read/delete), the target object, and the authenticated user's attributes. This provides fine-grained multi-tenant isolation without requiring per-resource RBAC roles.

**Middleware ordering is security-critical.** The server constructs its middleware stack in a specific order (`server.py` lines 444-479): version check → auth → quota → tracing. The `TracingMiddleware` is added last via `app.add_middleware()` but executes first (ASGI middleware wraps in reverse order). This means tracing captures the full request lifecycle including auth failures. The quota middleware depends on auth for principal identification; without auth, it falls back to anonymous rate limits (line 452-459). This coupling is documented in the code but represents a deployment consideration — quota enforcement is weaker without authentication.

**Self-referencing UI module.** The Streamlit UI (`api.py`) creates a `LlamaStackClient` pointed at the server's own endpoint, passing provider API keys from environment variables. This is an internal self-reference pattern, not a platform dependency. The UI module's purpose is interactive scoring via the `client.scoring.score()` API.
