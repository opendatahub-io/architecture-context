## Purpose

**Short**: OGX (Llama Stack) is a modular Python platform for serving LLM inference, agents, safety, evaluation, and tool execution via a unified REST API with pluggable provider backends.

**Detailed**: OGX is the Red Hat downstream fork of Meta's Llama Stack project. It provides a FastAPI-based server that exposes a comprehensive set of APIs for LLM operations — including inference (chat completions, embeddings), agentic workflows (multi-turn conversations with tool use), content safety (shield-based filtering), vector storage (RAG), evaluation/scoring, post-training (fine-tuning), and telemetry. The platform uses a protocol-based abstraction layer where each API is defined as a Python Protocol, allowing multiple interchangeable provider implementations.

The provider architecture supports both "inline" providers (running locally in-process, such as meta-reference inference, FAISS vector stores, or vLLM) and "remote" providers (delegating to external APIs like OpenAI, Anthropic, AWS Bedrock, NVIDIA, Google Gemini, and 20+ others). A routing table system maps resources (models, shields, vector DBs) to their backing providers, enabling multi-provider deployments where different models can be served by different backends simultaneously. The server includes enterprise features such as OAuth2/JWT authentication, attribute-based access control, per-client quota enforcement, TLS/mTLS support, and OpenTelemetry-based observability.

The platform ships with 25 deployment templates (pre-configured provider combinations for common scenarios like Ollama, vLLM, OpenAI, etc.) and maintains OpenAI API compatibility for inference and agent endpoints, allowing drop-in use with OpenAI client libraries.

## Architectural Analysis

OGX (Llama Stack) follows a **protocol-driven plugin architecture** that cleanly separates API definitions from implementations. Each of the 20+ APIs is defined as a Python `Protocol` class with `@webmethod` decorators that map methods to HTTP routes. The FastAPI server introspects these protocols at startup, dynamically registering routes — there is no static route table. This means adding a new API requires only defining a new Protocol and provider implementation, with zero changes to the server infrastructure. The `@webmethod` decorator (defined in `schema_utils.py`) annotates methods with route path, HTTP method, and experimental status.

The **routing table architecture** is the key abstraction that enables multi-provider deployments. Seven API pairs (models↔inference, shields↔safety, vector_dbs↔vector_io, etc.) use the `AutoRoutedApiInfo` pattern where a "routing table" API manages resource registration (e.g., which models exist) and a "router" API handles requests (e.g., chat completions). When a request arrives, the router looks up which provider owns the specified resource and delegates to that provider. This allows a single server to route `model-A` requests to vLLM and `model-B` requests to OpenAI. The `CommonRoutingTableImpl` class integrates access control checks into every resource lookup, ensuring ABAC policies are enforced before any provider code executes.

The **authentication stack** is layered: `AuthenticationMiddleware` (ASGI) extracts Bearer tokens and delegates to pluggable `AuthProvider` implementations. The OAuth2 provider handles JWKS key rotation with configurable refresh periods and supports both JWT verification and token introspection (RFC 7662). The custom provider enables integration with arbitrary auth systems by forwarding the token to an external endpoint. Importantly, authentication is optional — the server runs without auth by default, and access control policies (the `access_policy` field in `AuthenticationConfig`) are only enforced when auth is enabled. The `QuotaMiddleware` operates independently, tracking per-client request counts via a KV store backend.

For **RHOAI productization**, several architectural gaps need attention: (1) No Konflux Dockerfiles exist — the current Containerfiles use `python:3.12-slim`, not UBI base images, and lack FIPS-compliant crypto configuration; (2) The `python-jose` library used for JWT validation relies on pure-Python crypto (ecdsa, rsa) rather than OpenSSL bindings, which is a FIPS compliance concern; (3) No kustomize manifests or Kubernetes deployment resources exist — the platform operator would need to provide these; (4) The install.sh script deploys via Docker/Podman networking, which doesn't map to Kubernetes service mesh patterns. The extensive provider ecosystem (24+ remote inference providers) means the egress surface is very broad and would need careful NetworkPolicy configuration in a production deployment.

The **OpenAI API compatibility layer** is notable — endpoints under `/openai/v1/` mirror the OpenAI API surface for completions, chat completions, embeddings, models, files, and the newer Responses API. This enables existing OpenAI SDK users to point at a Llama Stack server with minimal code changes, which is strategically important for RHOAI adoption as it reduces migration friction from OpenAI-based applications.
