## Purpose

**Short**: A Kubernetes controller that performs intelligent autoscaling for LLM inference model servers based on saturation, queueing theory, and throughput analysis.

**Detailed**: The Workload Variant Autoscaler (WVA) is a global autoscaler for inference model servers in an llm-d / RHOAI environment. It works alongside Kubernetes HPA and KEDA to drive the scale subresource of inference deployments. WVA introduces the concept of "variants" -- multiple model servers in an InferencePool that serve the same base model but differ in hardware configuration (GPU type, tensor parallelism) or serving role (prefill vs. decode in P/D disaggregation).

WVA continuously monitors request rates and server performance via Prometheus, runs pluggable analyzers (saturation-based, queueing-model-based, throughput-based) to compute optimal replica counts, and emits `wva_desired_replicas` metrics that HPA/KEDA read to drive actual scaling. It supports GPU-constrained fair-sharing, cost-aware optimization, scale-to-zero with idle detection, scale-from-zero on pending requests, per-model SLO targets, and quota-based GPU allocation at cluster or namespace scope.

WVA is deployed as a single controller-runtime manager with multiple reconcilers (HPA, ScaledObject, InferencePool, ConfigMap) and two engine loops (saturation engine, scale-from-zero engine). Configuration is dynamic via labeled ConfigMaps, supporting namespace-local overrides for saturation thresholds, queueing model parameters, and scale-to-zero policies. An experimental coordinator with GPU rebalance plugin provides cross-namespace GPU quota management.

## Architectural Analysis

WVA's architecture implements a sophisticated multi-analyzer pipeline for LLM inference autoscaling. The central design decision is the separation of analysis (computing demand/supply signals) from optimization (allocating replicas under constraints). Three pluggable analyzers -- saturation V2 (token-based capacity), queueing model (SLO-driven Kalman filter), and throughput (ITL(k) OLS regression) -- can run simultaneously, with their results scored and weighted for fair-share allocation. This multi-signal approach provides robustness: if one analyzer's metrics are unavailable, the others continue to produce scaling decisions. The universal threshold post-processing step (`applyUniversalThreshold` in `engine_v2.go`) normalizes all analyzer outputs into a consistent RC/SC (required capacity / spare capacity) format before the optimizer sees them.

The optimizer layer offers two strategies: CostAwareOptimizer for unconstrained environments (sorts variants by cost/capacity ratio, scales cheapest first) and GreedyByScoreOptimizer for GPU-constrained environments (iterative mean-based fair-sharing across models). The GPU constraint system itself is pluggable -- the `Limiter` interface abstracts physical-capacity discovery (`TypeInventory`, which queries node GPU labels) from operator-declared quotas (`QuotaInventory`, which reads a static YAML file). A `CompositeLimiter` chains multiple limiters sequentially, enabling mixed cluster/namespace quota enforcement. This design means the optimization pipeline is identical regardless of whether constraints come from hardware discovery or administrative quotas.

The configuration system is notably dynamic. Three ConfigMap families (saturation-scaling, queueing-model, scale-to-zero) support both global defaults (in the system namespace) and namespace-local overrides (in watched namespaces). Namespace tracking is itself dynamic: the HPA and ScaledObject reconcilers track which namespaces contain managed resources, and the ConfigMap reconciler uses this tracking to decide which namespace-local ConfigMaps to watch. Labels (`llm-d.io/namespace-config-enabled=true`) and annotations (`llm-d.io/namespace-exclude=true`) provide fine-grained namespace filtering. This creates a system where configuration scope can change at runtime without controller restart.

The P/D (prefill/decode) disaggregation support is deeply integrated. Variants carry a "role" field, and the analysis/optimization layers sub-group variants by role for independent scaling within a model. The `allocateForModelPaired` function in `analyzer_helpers.go` implements joint role scaling: when allocating replicas to a prefill variant, the system also commits a proportional decode allocation to maintain role balance. This prevents scenarios where prefill scales up but decode remains starved (or vice versa).

A potential architectural risk is the in-memory decision cache. Scaling decisions are computed by the saturation engine and stored in a map keyed by `namespace/VA name`, then exposed via the `wva_desired_replicas` Prometheus metric. This cache is not persisted -- a controller restart loses all cached decisions until the next optimization cycle completes. The readiness probe gates on ConfigMap bootstrap completion but not on a successful optimization cycle, so there's a brief window after restart where the controller is ready but has no scaling decisions. The scale-from-zero engine mitigates one aspect of this (zero-replica variants with pending requests are immediately scaled) but non-zero variants rely on the saturation engine's next cycle.
