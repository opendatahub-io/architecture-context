## Purpose

**Short**: A Kubernetes controller that performs intelligent autoscaling for LLM inference model servers based on GPU saturation, queueing theory, and throughput analysis.

**Detailed**: The Workload Variant Autoscaler (WVA) is a controller-runtime based Kubernetes controller designed for the llm-d inference stack. It watches annotated HorizontalPodAutoscalers (HPAs) and KEDA ScaledObjects to discover managed model-serving workloads, collects real-time metrics from Prometheus (KV cache utilization, queue depth, token throughput, inter-token latency), and runs multi-engine scaling analysis to determine optimal replica counts for each model variant.

The controller supports three scaling engines: a percentage-based saturation analyzer (V1), a token-capacity-aware saturation analyzer (V2), and a queueing-model analyzer based on M/M/1/K theory. It emits `wva_desired_replicas` as a Prometheus gauge, which downstream autoscalers (HPA via prometheus-adapter, or KEDA ScaledObjects) consume to drive actual pod scaling. The controller also supports scale-to-zero for idle models and GPU-aware capacity limiting via either physical node inventory or operator-declared quotas.

WVA integrates with the Gateway API Inference Extension (GAIE) InferencePool CRD for endpoint discovery and supports both vLLM and SGLang inference engines. It deploys as a single-replica leader-elected controller with configurable namespace scoping, dynamic ConfigMap-driven configuration, and comprehensive observability via Prometheus metrics and PrometheusRule alerting.

## Architectural Analysis

The WVA follows an annotation-driven discovery pattern rather than a CRD-driven one. While the `PROJECT` file declares a `VariantAutoscaling` CRD (llmd.ai/v1alpha1), the actual production path discovers workloads through `llm-d.ai/managed: "true"` annotations on existing HPAs and KEDA ScaledObjects. This decoupled design means the WVA doesn't own the lifecycle of the autoscaling objects — it augments them by computing optimal replica counts and publishing the `wva_desired_replicas` Prometheus gauge. The downstream autoscaler (HPA via prometheus-adapter, or KEDA ScaledObject with a Prometheus trigger) reads this gauge and drives the actual scaling. This indirect scaling architecture provides safety: the WVA never directly mutates replica counts in the steady-state saturation path (only scale-from-zero uses direct patches), so existing HPA stabilization windows and KEDA cooldown periods still apply.

The multi-engine analysis pipeline is a key architectural strength. Three scaling engines (percentage-based saturation V1, token-capacity V2, and queueing-model M/M/1/K) can be configured per-model via namespace-aware ConfigMaps. The engine selection happens at the model level, not globally, so different models can use different scaling strategies. The pipeline follows an Analyzer → Optimizer → Limiter → Enforcer chain: analyzers produce raw scaling signals, the optimizer selects the best action (greedy or cost-aware), the limiter constrains based on GPU inventory/quotas, and the enforcer applies safety policies (minimum replicas, scale-to-zero eligibility). This separation of concerns makes each stage independently testable and extensible.

The metrics collection system is notably flexible, supporting both Prometheus (via PromQL queries) and direct pod scraping (via HTTP GET to `/metrics` endpoints). Query templates with parameterized placeholders enable per-engine metric name variants (vLLM uses bare names; SGLang gets engine-prefixed names). The pod-to-variant attribution uses ownerReference chain walking with an LRU cache (4096 entries, no TTL since ownerReferences are immutable) — this handles the Kubernetes topology of Pod → ReplicaSet → Deployment/LWS. The locator then matches the scale target to a managed scaler via the custom field indexes registered on HPAs and ScaledObjects.

The OpenShift integration layer is well-separated via kustomize components. The OpenShift overlay switches the Prometheus target from a self-hosted kube-prometheus-stack to OpenShift's built-in Thanos Querier, enables proper TLS verification via the service-ca operator, and configures user-workload-monitoring integration. The metrics endpoint uses service-ca signed certificates on OpenShift (vs self-signed on vanilla Kubernetes), and the ServiceMonitor drops pod/instance labels to ensure single-series per variant regardless of rolling updates — a critical detail for KEDA's scalar expectation of exactly one series per query.

The coordinator (experimental, disabled by default) represents a future direction for multi-model GPU rebalancing. Its plugin architecture (currently with a `gpurebalance` plugin) enables cluster-wide coordination across models sharing GPU pools. The coordinator operates on ScaledObjects/HPAs that are NOT managed by the saturation engine (they lack the `wva_desired_replicas` signal), writing `spec.maxReplicas` directly. This separation prevents conflicts between the saturation engine and the coordinator.
