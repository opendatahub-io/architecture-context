## Purpose

**Short**: Kubernetes operator that manages distributed training jobs for multiple ML/AI frameworks (PyTorch, TensorFlow, XGBoost, MPI, PaddlePaddle, JAX) on OpenShift and Kubernetes clusters.

**Detailed**: The Kubeflow Training Operator (KFTO) is a controller-runtime-based Kubernetes operator that orchestrates distributed machine learning training workloads. It defines Custom Resource Definitions (CRDs) for six training job types — PyTorchJob, TFJob, XGBoostJob, MPIJob, PaddleJob, and JAXJob — and implements reconciliation controllers that manage the complete lifecycle of each job type including pod creation, headless service provisioning for inter-replica communication, status tracking, and cleanup.

The operator supports advanced scheduling features through optional integration with Volcano and scheduler-plugins gang schedulers via PodGroup resources, enabling all-or-nothing scheduling for distributed training workloads that require multiple pods to start simultaneously. For PyTorch specifically, the operator supports elastic training with HorizontalPodAutoscaler integration and rendezvous-based dynamic scaling.

In the RHOAI distribution, the operator is deployed in the `opendatahub` namespace with FIPS-compliant builds, OpenShift TLS profile integration, and PodMonitor-based metrics collection. The RHOAI overlay applies a `kubeflow-` name prefix, configures webhook certificate management, and removes the public metrics port from the Service (relying on PodMonitor instead).

## Architectural Analysis

The training operator follows a framework-agnostic controller pattern where each ML framework (PyTorch, TensorFlow, etc.) implements a thin controller layer on top of a shared `JobController` base. The base controller in `pkg/controller.v1/common/` handles the generic reconciliation loop including pod lifecycle management, headless service creation, status tracking, and expectation-based consistency. Framework-specific controllers override methods like `GetDefaultContainerName()`, `GetDefaultContainerPortName()`, and `SetClusterSpec()` to inject framework-specific environment variables and topology logic. This design keeps the codebase DRY while supporting six distinct distributed training paradigms.

The MPI controller is architecturally distinct from the other five. While PyTorch, TensorFlow, XGBoost, PaddlePaddle, and JAX controllers create worker pods that communicate directly via headless services, the MPI controller creates a launcher/worker split where the launcher pod needs RBAC permissions to exec into worker pods via `kubectl exec`. This requires the controller to dynamically create ServiceAccounts, Roles, and RoleBindings per job — a significantly broader RBAC surface than the other controllers. The MPI controller also generates ConfigMaps containing `kubexec.sh`, `hostfile`, and `discover_hosts.sh` scripts that enable the Open MPI runtime to discover and communicate with worker pods.

The operator's TLS configuration is notably sophisticated for a component operator. Rather than hardcoding TLS settings, it reads the OpenShift cluster's TLS security profile (`config.openshift.io/v1/APIServer`) at startup and maps the profile (Intermediate, Modern, Custom, Old) to Go TLS constants. This ensures the webhook and metrics servers conform to cluster-wide TLS policy. For non-OpenShift clusters, it defaults to TLS 1.2 with intermediate cipher suites. The 11 supported cipher mappings cover modern ECDHE key exchange with AES-GCM and ChaCha20-Poly1305, with no legacy or known-weak ciphers.

The operator uses an expectation-based reconciliation pattern (similar to the Kubernetes ReplicaSet controller) to handle the gap between issuing create/delete requests and observing the results via informer watches. Each replica type tracks expected pod and service creations/deletions with a 5-minute TTL timeout, preventing reconciliation thrashing during high-latency watch scenarios. The informer cache is further optimized via label-based filtering (`training.kubeflow.org/operator-name` must exist), ensuring the operator only caches resources it owns rather than all pods/services cluster-wide.

The PyTorch controller has a unique downstream enhancement: it creates `NetworkPolicy` resources for each PyTorchJob that restrict ingress to pod-to-pod communication within the job, while explicitly allowing metrics scraping from the `openshift-monitoring` namespace on port 8080. This network isolation is not present in the upstream Kubeflow codebase and is an RHOAI-specific security hardening.
