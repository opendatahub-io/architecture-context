## Purpose

**Short**: Kubernetes operator that manages the lifecycle of distributed machine learning training jobs across multiple frameworks (PyTorch, TensorFlow, XGBoost, MPI, PaddlePaddle, JAX) on OpenShift.

**Detailed**: The training-operator is a controller-runtime-based Kubernetes operator forked from upstream Kubeflow Trainer v1.9.0. It defines six Custom Resource Definitions (CRDs) under the `kubeflow.org/v1` API group — PyTorchJob, TFJob, XGBoostJob, MPIJob, PaddleJob, and JAXJob — each representing a distributed training workload for its respective ML framework. For each job kind, a dedicated reconciler manages the full lifecycle: creating worker/master Pods, headless Services for inter-worker communication, and optional gang-scheduling PodGroups via Volcano or scheduler-plugins.

The operator includes a validating admission webhook for each CRD that enforces structural constraints (valid replica types, required container images, DNS-safe names, RunPolicy validation). Certificate rotation for the webhook TLS is handled internally via the OPA cert-controller library, writing to an in-cluster Secret and injecting the CA bundle into the ValidatingWebhookConfiguration. The RHOAI distribution deploys the operator in the `opendatahub` namespace with FIPS-compliant build flags, OpenShift TLS profile integration that reads the cluster APIServer resource to configure cipher suites dynamically, and label-filtered informer caches to bound memory consumption.

## Architectural Analysis

The training-operator follows a one-controller-per-framework pattern, with six independent reconciliation loops registered at startup via a scheme-based registry (`SupportedSchemeReconciler`). All controllers share a common `JobController` base that encapsulates Pod and Service lifecycle management, status aggregation, and gang-scheduling integration. This design allows each framework's controller to override framework-specific behavior (init containers for PyTorch's rendezvous, ConfigMap-based worker discovery for MPI, elastic scaling policies) without duplicating infrastructure code.

A notable architectural decision is the operator's memory management strategy. The controller-runtime cache is configured with label-selector filtering (`kubeflowv1.OperatorNameLabel` exists) on core resources (Pods, Services, ConfigMaps, Secrets, ServiceAccounts, Roles, RoleBindings), which constrains the informer cache to only operator-managed objects. This prevents unbounded memory growth in clusters with large numbers of unrelated Pods. Additionally, ConfigMaps and Secrets bypass the cache entirely for direct API reads via `DisableFor`, ensuring configuration lookups are never stale.

The TLS configuration is particularly mature: at startup, the operator reads the OpenShift `APIServer` cluster resource to extract the platform TLS security profile (Intermediate, Modern, Old, or Custom) and maps OpenSSL cipher names to Go's `crypto/tls` cipher suite constants. If the cluster resource is unavailable (non-OpenShift or transient errors), hardened defaults (TLS 1.2 minimum, intermediate cipher suite) are applied. This ensures the metrics and webhook servers inherit the cluster-wide TLS policy automatically.

The PyTorch controller also creates per-job NetworkPolicies that restrict ingress to only Pods within the same job plus the platform monitoring namespace, providing workload-level network isolation for distributed training traffic.
