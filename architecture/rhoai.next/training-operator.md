## Purpose

**Short**: Kubernetes operator for managing distributed AI/ML training jobs across multiple frameworks (PyTorch, TensorFlow, XGBoost, MPI, PaddlePaddle, JAX).

**Detailed**: The Training Operator (also known as Kubeflow Training Operator or KFTO) is a controller-runtime based Kubernetes operator that orchestrates distributed training workloads. It provides CRDs for six ML frameworks -- PyTorchJob, TFJob, XGBoostJob, MPIJob, PaddleJob, and JAXJob -- each representing a distributed training job with framework-specific semantics.

The operator creates and manages pods, headless services, and optionally PodGroups for gang scheduling via Volcano or scheduler-plugins. Each framework controller inherits from a shared `JobController` base that handles pod lifecycle, service creation, status tracking, and cleanup. Framework-specific logic (environment variable injection, init containers, elastic scaling) is isolated in per-framework packages.

In the RHOAI platform, the operator is deployed by the `rhods-operator`/`opendatahub-operator` into the `opendatahub` namespace with the `kubeflow-` name prefix. It integrates with the OpenShift API for TLS profile detection, supports FIPS-compliant builds via `GOEXPERIMENT=strictfipsruntime`, and provides validating webhooks for all training job types.

## Architectural Analysis

The Training Operator follows a well-structured plugin architecture where framework-specific controllers (PyTorch, TensorFlow, XGBoost, MPI, PaddlePaddle, JAX) inherit from a shared `JobController` base in `pkg/controller.v1/common/`. This design minimizes code duplication -- pod creation, service management, status tracking, cleanup policies, and gang scheduling are all handled centrally. Framework-specific logic (environment variable injection for distributed training, init containers for PyTorch, RBAC resources for MPI launcher) is cleanly isolated in per-framework packages.

The MPI controller stands out architecturally from the other five frameworks. While PyTorch, TensorFlow, XGBoost, PaddlePaddle, and JAX all create pods and headless services using the common controller's built-in pod/service reconciliation, MPI requires additional Kubernetes resources: ServiceAccounts, Roles, RoleBindings, and ConfigMaps for each job. This is because MPI's launcher-worker model requires the launcher pod to execute commands on worker pods via `kubectl exec`, which demands per-job RBAC. The MPI controller also handles its own pod reconciliation directly rather than fully delegating to the common framework, making it the most complex individual controller.

PyTorch's elastic training support via `ElasticPolicy` introduces HorizontalPodAutoscaler creation and NetworkPolicy management, which are unique among the six frameworks. The elastic policy supports rendezvous backends (c10d, etcd, etcd-v2) for worker discovery during scaling events, with `NprocPerNode` configuration for multi-GPU training. This makes PyTorchJob the most feature-rich CRD in the operator.

The operator's TLS configuration deserves attention. It dynamically detects OpenShift TLS profiles by reading `config.openshift.io/v1/APIServer`, with graceful fallback to hardened defaults (TLS 1.2 with intermediate cipher suites) when running outside OpenShift or when the API server is temporarily unavailable. The `fetchTLSOpts` function implements retry logic with `IsServerTimeout` handling for transient API errors, which is a recent fix (commit `e2bbd3bb`). Webhook TLS certificates are self-managed via the OPA cert-controller library, which rotates certificates and updates the ValidatingWebhookConfiguration automatically.

The RHOAI kustomize overlay applies several significant changes: it prefixes all resources with `kubeflow-`, deploys into the `opendatahub` namespace, removes the metrics port from the Service (relying on PodMonitor for metrics collection instead), and adds aggregated RBAC ClusterRoles (`training-edit`, `training-view`) that integrate with OpenShift's built-in RBAC aggregation via `rbac.authorization.k8s.io/aggregate-to-edit` and `aggregate-to-view` labels. The controller image parameter is injected via `configMapGenerator` and `replacements`, with the same image serving double duty as both the operator binary and the PyTorch init container image.
