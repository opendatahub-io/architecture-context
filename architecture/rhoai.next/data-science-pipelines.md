## Purpose

**Short**: Kubeflow Pipelines backend services for defining, scheduling, and executing ML/AI pipelines as Argo Workflows on Kubernetes.

**Detailed**: Data Science Pipelines (DSP) is the Red Hat downstream distribution of Kubeflow Pipelines (KFP), providing the complete backend infrastructure for ML pipeline orchestration within Red Hat OpenShift AI (RHOAI). It enables data scientists to define reproducible ML workflows as directed acyclic graphs (DAGs), compile them to Argo Workflow specifications, schedule recurring runs, cache intermediate results for efficiency, and track pipeline artifacts and metadata.

The platform consists of five deployable Go binaries: an API server exposing gRPC and REST APIs for pipeline CRUD operations, a persistence agent that watches Argo Workflow status and syncs it to the backend database, a scheduled workflow controller that manages cron-based recurring runs, a driver that orchestrates individual pipeline step execution within Argo Workflow DAG nodes, and a launcher that executes user container tasks with artifact I/O handling. The API server integrates with an external ML Metadata (MLMD) gRPC service for artifact lineage tracking, object storage (S3/MinIO) for pipeline spec and artifact persistence, and a relational database (MySQL or PostgreSQL) for pipeline metadata.

The component supports an extensible plugin architecture, with MLflow integration as the primary plugin, enabling automatic experiment and run tracking synchronization between KFP and MLflow. The upstream sync from kubeflow/pipelines occurs weekly via an automated GitHub Actions workflow, with downstream carries for Red Hat-specific Dockerfiles, FIPS compliance, and TLS hardening.

## Architecture Components

| Component | Type | Purpose |
|-----------|------|---------|
| API Server | Go Service | Central API gateway providing gRPC (8887/TCP) and REST (8888/TCP) endpoints for pipeline, run, experiment, and artifact management with multi-user RBAC |
| Driver | Go CLI (Argo step) | Orchestrates individual pipeline step execution within Argo Workflow DAG nodes — resolves inputs, checks cache, creates Kubernetes resources |
| Launcher | Go CLI (Argo step) | Executes user container tasks, handles artifact upload/download to/from object storage, reports metadata to MLMD |
| Persistence Agent | Go Service | Watches Argo Workflow and ScheduledWorkflow resources via informers, persists status and metrics to the API server database |
| Scheduled Workflow Controller | Go Controller | Kubernetes controller managing ScheduledWorkflow CRDs — triggers Argo Workflows on cron or periodic schedules |
| Cache Server | Go Webhook (not in Konflux) | Mutating admission webhook that intercepts pod creation to inject cached outputs when pipeline steps are reusable |
| Viewer Controller | Go Controller (not in Konflux) | Kubernetes controller managing Viewer CRDs — deploys TensorBoard instances as Deployments with Services |

## Architectural Analysis

Data Science Pipelines follows a distributed microservice architecture where each component has a clear separation of concerns. The API server acts as the central control plane, exposing both gRPC and REST APIs (via gRPC-Gateway) for all pipeline operations. The dual-protocol design allows the Python and Go SDKs to use gRPC for efficiency while web UIs and external integrations use REST. The persistence agent and scheduled workflow controller operate as independent Kubernetes controllers that watch cluster resources and synchronize state, following the operator pattern without being a full OLM operator.

The driver/launcher split is a particularly notable architectural pattern. Rather than running a single sidecar, DSP uses two distinct binaries injected into Argo Workflow steps: the driver runs as an init step to resolve inputs, check cache, and prepare the execution environment, while the launcher wraps the user's container to handle artifact I/O. This separation allows caching decisions to short-circuit execution before the user container even starts, and keeps artifact handling logic isolated from pipeline orchestration logic. The compiler translates the platform-independent KFP pipeline IR spec into Argo Workflow YAML, embedding driver and launcher containers as DAG node templates.

The plugin system demonstrates a well-designed extensibility pattern. The MLflow plugin hooks into run lifecycle events (before creation, on completion, on retry) to synchronize pipeline state with MLflow's experiment tracking. The plugin dispatcher uses a registry pattern with runtime enablement checks, and plugin failures are handled gracefully — they don't block run creation. The plugin configuration supports runtime reload via Viper's file watching, allowing operators to reconfigure MLflow integration without restarting the API server. Recent carry patches (`cbf6433dd`, `fd9107e9c`) show active hardening of the MLflow TLS configuration, removing `InsecureSkipVerify` and enforcing CA bundle paths.

The FIPS compliance approach uses Go 1.26's native `GOFIPS140=v1.0.0` build flag combined with the `godebug fips140=on` module directive. Notably, four of the five components (driver, launcher, persistence agent, scheduled workflow controller) are built with `CGO_ENABLED=0` (static linking) while still using `GOFIPS140=v1.0.0`. This is architecturally significant because Go 1.26's FIPS 140 module supports a pure-Go FIPS implementation that doesn't require CGO/OpenSSL, unlike the older `GOEXPERIMENT=boringcrypto` approach. Only the API server uses `CGO_ENABLED=1`, likely because it links against C libraries for database drivers (MySQL, SQLite).

Build hermeticity is strong: RPM lock files cover three architectures (x86_64, aarch64, ppc64le), Go dependencies are locked via go.sum across four modules, and Konflux Tekton pipelines use hermetic builds with gomod and RPM prefetch. The multi-architecture build support (x86_64, arm64, ppc64le) across all five Konflux components ensures broad hardware platform compatibility. The upstream sync workflow runs weekly, merging kubeflow/pipelines master with automatic conflict handling for downstream-only files (Dockerfiles, .tekton, OWNERS).
