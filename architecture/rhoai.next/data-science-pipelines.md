## Purpose

**Short**: Kubeflow Pipelines (KFP) backend providing a REST/gRPC API server, workflow execution engine, and supporting controllers for defining, scheduling, and running ML pipelines on Kubernetes.

**Detailed**: Data Science Pipelines is the RHOAI downstream of Kubeflow Pipelines, providing the core infrastructure for ML pipeline orchestration. The platform enables users to define pipelines as Python DSL, compile them to an intermediate representation (IR YAML), and submit them for execution on Kubernetes clusters via Argo Workflows as the execution engine.

The system is composed of several cooperating Go services: an API server that exposes both REST (via gRPC-gateway) and gRPC interfaces for pipeline CRUD and run management; a persistence agent that watches Argo Workflow status and reports it back to the API server; a scheduled workflow controller that manages recurring pipeline runs via ScheduledWorkflow CRDs; a driver that resolves pipeline task inputs and computes pod spec patches; and a launcher that handles artifact download/upload and executor invocation within task containers.

In the RHOAI distribution, these components are deployed and managed by the `data-science-pipelines-operator` (DSPO), which handles per-namespace DSPApplication CR reconciliation. The upstream repo also ships a Python SDK (`kfp`), a React frontend, and third-party dependencies (MySQL/MariaDB for metadata, S3-compatible object storage for artifacts, ML Metadata gRPC server for lineage tracking), though these are built and distributed separately.

## Architectural Analysis

The data-science-pipelines architecture follows a hub-and-spoke pattern centered on the API server (`ml-pipeline`), which acts as the central coordination point for all pipeline operations. The API server manages the lifecycle of pipelines, runs, experiments, and recurring runs, persisting state in a relational database (MySQL or PostgreSQL) and storing pipeline artifacts in S3-compatible object storage.

The execution flow illustrates a clear separation of concerns: the SDK compiles Python DSL to portable IR YAML; the API server compiles IR to Argo Workflow objects; the driver resolves runtime parameters and patches pod specs; the launcher handles artifact I/O within task pods. This layered design allows each component to be independently versioned and scaled, though in practice the components are tightly coupled through shared protobuf contracts and database schemas.

A notable architectural choice is the dual pipeline storage mode: pipelines can be stored either in the database (traditional) or as Kubernetes CRs (Pipeline/PipelineVersion CRDs). The Kubernetes-native storage mode is backed by admission webhooks that validate and mutate PipelineVersion resources, enabling the API server to act as both a traditional service and a Kubernetes controller.

The authentication model varies by deployment mode. In standalone mode, no authentication is enforced on the API surface. In multi-user mode, the API server performs TokenReview and SubjectAccessReview against the Kubernetes API server, and the system integrates with Istio for service-to-service mTLS and authorization policies. The MySQL database is further protected by an Istio AuthorizationPolicy restricting access to a named set of service account principals.

All RHOAI Konflux-built images use Go 1.26 with the native FIPS 140 crypto module (`GOFIPS140=v1.0.0` and `godebug fips140=on` in go.mod), running on UBI 9 minimal-pqc (post-quantum cryptography) base images. The API server uses `CGO_ENABLED=1` for dynamic linking (required for C dependencies), while the driver, launcher, persistence agent, and scheduled workflow controller use `CGO_ENABLED=0` with static linking. All builds use `-tags no_openssl`, relying on Go's built-in FIPS 140-3 validated crypto module rather than OpenSSL.

| Auth & AuthZ | TokenReview + SubjectAccessReview (multi-user); none (standalone) | API server / Kubernetes | Standalone mode has no auth; multi-user requires Istio for service mesh enforcement |
| Data storage | Per-namespace database instance (deployed by DSPO); shared within namespace | Kubernetes / Operator | Multiple users in the same namespace share the same database |
| Network traffic | Istio AuthorizationPolicy on MySQL; service mesh mTLS (multi-user) | Istio | Standalone mode has no network isolation between services |
| Compute & resources | Per-namespace deployments; no built-in ResourceQuota enforcement | Kubernetes | Resource limits delegated to platform-level quota policies |
| Configuration & secrets | Per-namespace Secrets (mysql-secret, mlpipeline-minio-artifact) | Kubernetes | Secrets are namespace-scoped |
| API scoping | Namespace-scoped watches; persistence agent filtered by NAMESPACE env | Application | pipeline-runner role has broad permissions (e.g., kubeflow.org/* verbs=*) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |

| Argo Workflows controller | Per namespace (namespaced mode) | Namespace-scoped workflow execution |
