## Purpose

**Short**: Kubeflow Pipelines v2 backend providing pipeline definition, scheduling, execution orchestration, and artifact management for ML workflows on Kubernetes via Argo Workflows.

**Detailed**: Data Science Pipelines is the core pipeline orchestration system within the Red Hat OpenShift AI platform, based on Kubeflow Pipelines v2. It enables users to define, upload, version, schedule, and execute reproducible ML workflows as directed acyclic graphs (DAGs) of containerized tasks.

The system consists of five deployable components built from this repository: (1) the API server, which exposes gRPC and REST APIs for pipeline CRUD, run management, experiment tracking, and artifact access; (2) the driver, an init container that orchestrates task execution within Argo Workflow pods by resolving inputs from ML Metadata (MLMD), managing caching, and generating pod spec patches; (3) the launcher, a main container companion that executes user code, handles artifact upload/download to object storage, and publishes execution metadata to MLMD; (4) the persistence agent, which watches Argo Workflow and ScheduledWorkflow resources and reports their state back to the API server's database; and (5) the scheduled workflow controller, which reconciles ScheduledWorkflow CRDs to trigger pipeline runs on cron or periodic schedules.

The platform stores pipeline metadata in a relational database (MySQL or PostgreSQL), tracks execution lineage and artifacts through ML Metadata (gRPC service), and persists artifacts in S3-compatible object storage (MinIO, AWS S3, or GCS). Pipeline execution is delegated to Argo Workflows, with the driver/launcher pattern providing a two-phase execution model within each task pod.

## Architectural Analysis

Data Science Pipelines implements a **two-phase execution model** within Argo Workflow task pods that cleanly separates orchestration from execution. The driver runs as an init container to resolve inputs from MLMD, check the execution cache, provision output paths, and generate Kubernetes pod spec patches. The launcher then runs as the main container, downloading input artifacts, substituting placeholders in user commands, executing the user code, uploading output artifacts, and publishing execution metadata back to MLMD. This separation means the driver can short-circuit execution on cache hits (by writing a cached decision file) without ever starting the user container, and the launcher operates independently of the scheduling logic.

The **plugin system** is a notable architectural feature, currently used for MLflow integration. The dispatcher invokes lifecycle hooks (`OnBeforeRunCreation`, `OnAfterRunCompletion`, `OnRetry`) at key points in the API server's run management flow. The MLflow plugin registers experiments and tracks runs in an external MLflow Tracking Server. The plugin architecture uses a factory pattern with Viper-based configuration, allowing runtime configuration changes without server restart. However, the MLflow plugin's TLS configuration includes a configurable `InsecureSkipVerify` option, which the codebase explicitly documents as an intentional design choice for environments where TLS validation is problematic -- this is a FIPS compliance risk worth noting.

The **persistence agent** acts as a bridge between Argo Workflows' native execution model and the DSP data model. It uses Kubernetes informers to watch Workflow and ScheduledWorkflow resources, then reports state changes to the API server via gRPC. This asynchronous reporting pattern decouples the execution engine from the API server's database, but introduces eventual consistency -- there's a window between workflow completion and database update where the API server may report stale run status. The agent uses exponential backoff with a 6-minute maximum delay for transient failures and a projected service account token (from `/var/run/secrets/kubeflow/tokens/persistenceagent-sa-token`) with hourly refresh for authentication.

The **FIPS posture is mixed across components**. The API server (CGO_ENABLED=1, GOFIPS140=v1.0.0) builds with dynamic linking and should pass check-payload validation. However, the driver, launcher, persistence agent, and scheduled workflow controller all build with CGO_ENABLED=0 (static linking) plus GOFIPS140=v1.0.0. While Go 1.26's native FIPS 140 module (`GOFIPS140=v1.0.0`) provides FIPS-compliant cryptography without requiring CGO, the `-tags no_openssl` build tag explicitly disables OpenSSL integration. This configuration uses Go's built-in FIPS 140 implementation rather than BoringCrypto or system OpenSSL, which may or may not satisfy Red Hat's check-payload requirements depending on the specific validation rules.

The **SSRF prevention** in the pipeline URL download path is well-implemented: `SafePipelineHTTPClient` validates domains against an allowlist, resolves DNS and checks IP ranges against blocked private/loopback/link-local/metadata CIDRs, and re-validates at connection time to prevent DNS rebinding attacks. The custom dialer intercepts the connection to verify the resolved IP hasn't changed between DNS lookup and actual connection establishment.
