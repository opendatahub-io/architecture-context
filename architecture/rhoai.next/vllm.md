## Purpose

**Short**: Konflux build-wrapper repository that produces the RHOAI vLLM CUDA inference serving container image with TGIS gRPC adapter support.

**Detailed**: This repository is a downstream build-definition wrapper in the Red Hat Data Services organization. It contains no application source code; instead, it defines a single Konflux Dockerfile (`Dockerfile.konflux.cuda`) that layers on top of the RHAIIS (Red Hat AI Inference Server) vLLM CUDA base image (`registry.redhat.io/rhaiis/vllm-cuda-rhel9`). The layer configures the container entrypoint to run the `vllm_tgis_adapter` Python module, which bridges vLLM's native OpenAI-compatible REST API with the TGIS (Text Generation Inference Service) gRPC protocol used internally by RHOAI model serving infrastructure.

The repository's role in the platform is purely build-time: it provides the Konflux pipeline definition (synchronized from `konflux-central`) and the Dockerfile needed to produce the `odh-vllm-cuda-rhel9` container image. All runtime behavior — the vLLM inference engine, model loading, GPU acceleration, the TGIS adapter, and API serving — is inherited from the RHAIIS base image. The upstream lineage traces from `vllm-project/vllm` (the open-source vLLM project) through `opendatahub-io/vllm` (the ODH fork) to this downstream RHOAI build repository.

## Architectural Analysis

This repository represents a pattern common in RHOAI's downstream distribution: a "Konflux build shim" that exists solely to own the container image build pipeline for a product component. The actual software stack — vLLM, the TGIS gRPC adapter, CUDA libraries, and Python dependencies — lives entirely within the RHAIIS base image (`registry.redhat.io/rhaiis/vllm-cuda-rhel9:3.2.2`). This separation means the build wrapper is intentionally minimal (a Dockerfile, Tekton pipeline definition, and gatekeeper workflow), while the RHAIIS team owns the substantive engineering of the base image.

The architectural significance of this repo lies in three areas. First, it defines the runtime contract: the entrypoint configures `vllm_tgis_adapter` as the process entry point, exposing dual protocols — an OpenAI-compatible HTTP API on port 8000 and a TGIS gRPC API on port 8033. This dual-protocol design allows the same container to serve both the standard OpenAI chat/completion API and the TGIS protocol expected by KServe and the RHOAI model serving stack. Second, it pins the RHAIIS version (`RHAIIS_VERSION=3.2.2`) as a build argument, controlling which upstream base image version flows into the RHOAI product build. Third, the non-root execution (UID 2000) and the speculative decoding logprobs override (`DISABLE_LOGPROBS_DURING_SPEC_DECODING=false`) are runtime configuration decisions made at this layer.

The build pipeline supports multi-architecture builds (linux/amd64 and linux/arm64) via Konflux with Tekton, and pipeline definitions are centrally managed in the `konflux-central` repository and automatically synchronized to this repo's `.tekton/` directory.
