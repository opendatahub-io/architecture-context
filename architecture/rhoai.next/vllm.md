## Purpose

**Short**: Downstream container image that wraps the RHAIIS vLLM CUDA product image with a TGIS adapter entrypoint for OpenShift AI inference serving.

**Detailed**: This repository produces a single container image (`odh-vllm-cuda-rhel9`) for GPU-accelerated LLM inference on NVIDIA CUDA hardware. The image is a thin layer on top of the Red Hat AI Inference Server (RHAIIS) `vllm-cuda-rhel9` base image, adding environment configuration and setting the entrypoint to the `vllm_tgis_adapter` Python module.

The TGIS adapter provides a gRPC-compatible API (port 8033) alongside the standard vLLM OpenAI-compatible HTTP API (port 8000), enabling backward compatibility with workloads originally written for IBM's Text Generation Inference Server. The adapter bridges the TGIS gRPC protocol to vLLM's internal engine.

This repo is intentionally minimal — it contains no application source code, no deployment manifests, no CRDs, and no controllers. All vLLM runtime code, Python dependencies, CUDA libraries, and the TGIS adapter module are inherited from the RHAIIS base image. The repo exists solely to define the Konflux build pipeline that produces the final shippable image with the correct entrypoint, labels, and non-root user configuration.

## Architectural Analysis

This repository exemplifies the "thin downstream wrapper" pattern used in Red Hat's AI inference product line. Rather than forking and maintaining the full vLLM codebase (~500k+ lines of Python/C++/CUDA), this repo contains only a single 25-line Dockerfile that layers the TGIS adapter entrypoint on top of the pre-built RHAIIS product image. This design separates concerns: the RHAIIS team (AIPCC Ecosystems) owns the vLLM build, CUDA integration, and Python dependency management, while this downstream repo focuses solely on the RHOAI-specific serving configuration.

The TGIS adapter (`vllm_tgis_adapter`) is architecturally significant — it bridges the IBM TGIS gRPC protocol to vLLM's internal engine, providing backward compatibility for workloads migrating from IBM's Watson NLP/TGIS serving infrastructure to vLLM. This adapter runs as the container's primary process and exposes both the TGIS gRPC API (port 8033) and the standard vLLM OpenAI-compatible HTTP API (port 8000) simultaneously. The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable override is notable — it ensures logprobs remain available even when speculative decoding is enabled, which is important for hosted model deployments where users expect consistent API behavior regardless of internal optimizations.

The build pipeline is managed entirely via Konflux with Tekton PipelineRuns synced from the `konflux-central` repository. The build is explicitly non-hermetic (`hermetic: false`) and targets both `amd64` and `arm64` architectures. The 10-hour pipeline timeout reflects the large image size typical of CUDA-based ML containers. The image is built in the `rhoai-tenant` namespace and published to `quay.io/rhoai/`. The pipeline includes Clair vulnerability scanning and Red Hat ecosystem certification preflight checks, with elevated compute resources (8-16 CPU, 16-32Gi RAM) allocated for these validation tasks.

A notable architectural gap is the absence of accelerator variants beyond CUDA in this repository. The branch history shows past support for ROCm (`rhoai-2.17` had `appstudio-vllm-rocm-217`), CPU, and Gaudi variants, but the current `main` branch only produces a CUDA image. Other accelerator variants may have been moved to separate repositories or are managed through different build pipelines. This is worth tracking for architects planning multi-accelerator inference deployments.
