## Purpose

**Short**: Downstream packaging image that wraps the RHAIIS vLLM CUDA product image with TGIS (Text Generation Inference Server) adapter configuration for GPU-accelerated LLM inference in RHOAI.

**Detailed**: This repository produces a container image for serving large language models (LLMs) on NVIDIA GPUs within the RHOAI model serving infrastructure. Rather than building vLLM from source, it extends the pre-built `registry.redhat.io/rhaiis/vllm-cuda-rhel9` image published by the RHAIIS (Red Hat AI Inference Server) team. The RHAIIS base image itself is built on AIPCC (AI Platform Common Components) CUDA base images and contains the full vLLM engine with NVIDIA CUDA support.

The image adds a thin configuration layer on top: it sets the entrypoint to the `vllm_tgis_adapter` Python module, which provides a gRPC interface compatible with the TGIS (Text Generation Inference Server) protocol alongside vLLM's native OpenAI-compatible HTTP API. This dual-protocol support allows the image to be used as a ServingRuntime in both KServe (OpenAI API) and legacy TGIS-based serving deployments. The image runs as non-root user (UID 2000) and exposes HTTP on port 8000 and gRPC on port 8033.

The repository contains no application source code — only a single Konflux Dockerfile, Tekton pipeline definitions (synced from `konflux-central`), and metadata files. All vLLM source, Python dependencies, CUDA libraries, and TGIS adapter code are inherited from the RHAIIS base image.

## Purpose

**Short**: Downstream container image wrapper that layers the vLLM TGIS gRPC adapter entrypoint onto the RHAIIS vLLM CUDA product image, producing the RHOAI inference serving runtime for NVIDIA GPU workloads.

**Detailed**: This repository is a thin downstream packaging layer in the Red Hat Data Services organization. It does not contain application source code. Instead, it provides a single Konflux Dockerfile (`Dockerfile.konflux.cuda`) that takes the pre-built RHAIIS (Red Hat AI Inference Services) vLLM CUDA image (`registry.redhat.io/rhaiis/vllm-cuda-rhel9`) as its base and configures it with the vLLM TGIS adapter entrypoint. The TGIS (Text Generation Inference Server) adapter exposes a gRPC interface on port 8033 that is compatible with the KServe/Caikit serving stack, while the underlying vLLM engine continues to expose its OpenAI-compatible HTTP API on port 8000.

The resulting container image (`rhoai/odh-vllm-cuda-rhel9`) is deployed as an inference serving runtime within Red Hat OpenShift AI. It is typically instantiated by the KServe `InferenceService` controller as a model server pod, where it loads a large language model (LLM) from a PersistentVolumeClaim or object storage and serves inference requests. The TGIS adapter provides backward compatibility with the TGIS gRPC protocol used by earlier versions of the serving stack, enabling a unified client interface across different model serving backends.

The repository also contains Tekton pipeline configuration (`.tekton/`) that is automatically synchronized from the `red-hat-data-services/konflux-central` repository. Builds target both `linux/amd64` and `linux/arm64` architectures. Other accelerator variants (ROCm, CPU, Gaudi) exist on separate branches but are not present on the `main` branch analyzed here.

## Architectural Analysis

This repository represents the thinnest possible downstream packaging pattern: a single Dockerfile with no source code that extends a pre-built product image. The `Dockerfile.konflux.cuda` is only 25 lines — it FROM's the RHAIIS vLLM CUDA image, sets three environment variables (`GRPC_PORT`, `PORT`, `DISABLE_LOGPROBS_DURING_SPEC_DECODING`), configures a non-root user (UID 2000), and overrides the entrypoint to launch the `vllm_tgis_adapter` module. All application code, Python dependencies, CUDA libraries, and the vLLM engine itself are inherited from the `registry.redhat.io/rhaiis/vllm-cuda-rhel9:3.2.2` base image.

The key architectural decision is the TGIS adapter entrypoint. The base RHAIIS vLLM image ships with both the native OpenAI-compatible HTTP server and the `vllm_tgis_adapter` module. This downstream image selects the TGIS adapter as the default entrypoint (`python3 -m vllm_tgis_adapter --uvicorn-log-level=warning`), which simultaneously exposes both the gRPC TGIS protocol (port 8033) and the OpenAI-compatible HTTP API (port 8000). This dual-protocol approach enables backward compatibility with existing TGIS-based clients while also supporting the standard OpenAI API that newer integrations expect.

The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable is noteworthy: vLLM normally disables logprobs when speculative decoding is active as a performance optimization, but this wrapper overrides that default. The comment in the Dockerfile explains this is because users of hosted models may not know speculative decoding is enabled and would find missing logprobs unexpected. This reflects the product's stance on predictable behavior over raw performance in a managed serving context.

Build infrastructure is fully managed by Konflux with pipeline definitions synced from `red-hat-data-services/konflux-central`. The Tekton pipeline builds for both `linux/amd64` and `linux/arm64` architectures. The build is explicitly non-hermetic (`hermetic: false`), which is acceptable because no dependencies are installed during the build — the Dockerfile only adds metadata and configuration to the pre-built base image. The `argfile.conf` referenced in the pipeline spec (`build-args-file: argfile.conf`) is not present on the `main` branch, suggesting it may be generated or present only on release branches.

The `RHAIIS_VERSION` build arg (currently `3.2.2`) pins the specific version of the pre-built vLLM CUDA image. Version updates are managed by commits like `562821ebc (chore): Update vllm-cuda to 3.2.2`, which simply bump this version string. This decouples the vLLM build lifecycle (managed by RHAIIS) from the RHOAI serving infrastructure lifecycle (managed by this repo and KServe).

## Architectural Analysis

This repository represents a minimal downstream packaging pattern used in RHOAI: a single-layer Dockerfile that takes a fully-built upstream product image (RHAIIS `vllm-cuda-rhel9`) and configures it with a specific entrypoint for platform integration. The repository contains no application source code, no deployment manifests, no RBAC definitions, and no Kubernetes resources. All inference logic, dependencies, and Python packages are inherited from the RHAIIS base image.

The key architectural decision is the TGIS adapter pattern. The entrypoint `python3 -m vllm_tgis_adapter --uvicorn-log-level=warning` wraps the vLLM OpenAI-compatible HTTP server with a gRPC interface that implements the TGIS (Text Generation Inference Server) protocol. This dual-protocol approach (HTTP on port 8000, gRPC on port 8033) enables backward compatibility with the Caikit+TGIS serving stack used in earlier RHOAI versions while also supporting the newer OpenAI-compatible API. The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable override indicates that RHOAI requires logprobs availability even when speculative decoding is active, which differs from upstream vLLM defaults.

The repository follows a branch-per-accelerator strategy. The `main` branch contains only the CUDA variant, while separate branches exist for ROCm (`appstudio-vllm-rocm-*`), CPU (`appstudio-vllm-cpu-*`), and experimental Gaudi variants. This branching model allows each accelerator variant to evolve independently with different base images and build configurations. The Tekton pipelines are centrally managed by `konflux-central` and auto-synchronized to this repository -- direct edits to `.tekton/` files are overwritten. The build pipeline explicitly sets `hermetic: false`, which is architecturally appropriate since this Dockerfile performs no dependency resolution. The migration from building vLLM and the TGIS adapter from source to consuming the pre-built RHAIIS image (commit `e927dff02`) significantly simplified this repository and moved supply-chain responsibility upstream.

The image runs as a non-root user (UID 2000), which differs from the AIPCC standard UID 1001 used by RHAIIS base images. This suggests the UID was chosen for compatibility with RHOAI's pod security context requirements. Security posture (authentication, authorization, TLS termination) is entirely delegated to the KServe serving stack and its associated sidecars (kube-rbac-proxy in RHOAI 3.x). The container itself listens on plaintext HTTP and gRPC ports, relying on the pod network boundary for isolation.
