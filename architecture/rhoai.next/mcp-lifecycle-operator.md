## Purpose

**Short**: A Kubernetes operator that provides a declarative API to deploy, manage, and safely roll out MCP (Model Context Protocol) Servers, handling their full lifecycle with production-grade automation and ecosystem integrations.

**Detailed**: The MCP Lifecycle Operator watches `MCPServer` custom resources and reconciles the desired state by creating and managing Deployment, Service, and NetworkPolicy resources for each MCP server instance. It supports deploying MCP servers from container images, configuring them with environment variables, arguments, ConfigMap and Secret volume mounts, and health probes.

The operator performs an MCP protocol handshake against each deployed server to verify it correctly speaks the Model Context Protocol, reporting server capabilities (tools, resources, prompts, logging, completions) in the CR status. It manages ownership and adoption of resources across MCPServer recreation, supports session affinity for stateful MCP servers, and provides Prometheus metrics for monitoring reconciliation health.

This is an upstream Kubernetes SIG Apps project (`kubernetes-sigs/mcp-lifecycle-operator`) that has been downstreamed into the Red Hat OpenShift AI platform. The downstream fork adds FIPS-compliant builds (`GOEXPERIMENT=strictfipsruntime`), Konflux CI pipelines, an ODH kustomize overlay with ServiceMonitor integration, and hermetic build support via cachi2 prefetch.

## Architectural Analysis

The MCP Lifecycle Operator follows a clean kubebuilder-scaffolded architecture with a single controller managing the full lifecycle of MCPServer custom resources. The controller decomposes reconciliation into four sequential phases -- validation, deployment, service, and network policy -- each instrumented with Prometheus histogram metrics for operational visibility. This phase-based approach enables precise failure attribution: if validation fails, the `Accepted` condition is set to False and deployment is skipped; if deployment succeeds but the service fails, the `Ready` condition identifies the exact failure point.

A distinctive design choice is the MCP protocol handshake verification. After the Deployment reports available replicas, the controller uses the `modelcontextprotocol/go-sdk` to perform an actual MCP `initialize` handshake against the deployed server. This goes beyond typical Kubernetes readiness -- it verifies the container is not just running, but actively speaking the MCP protocol. The handshake extracts server capabilities (tools, resources, prompts, logging, completions) and publishes them in the CR status, providing a protocol-level service registry. The handshake uses exponential backoff (10s, 20s, 40s, ... up to 2min) with a maximum of 10 retries before giving up, and treats HTTP 401/403 responses as "reachable" (the server is running, it just requires auth).

The config hash mechanism (`mcp.x-k8s.io/config-hash` annotation) provides automatic rolling updates when referenced ConfigMaps or Secrets change. The controller computes a SHA-256 hash of all referenced ConfigMap and Secret data and injects it as a pod template annotation. When external data changes, the hash changes, triggering a Deployment rollout without any spec change to the MCPServer CR. This is complemented by field indexes on ConfigMap and Secret references for efficient watch-to-reconcile mapping.

The ownership model is notably careful about resource lifecycle. The controller validates ownership before every update, rejecting operations on resources owned by different controllers and refusing to silently adopt unowned resources (preventing accidental overwrites of manually-created Deployments/Services). However, it does support cross-UID adoption when an MCPServer is deleted and recreated with the same name -- the orphaned resources are adopted seamlessly, even across API version upgrades. This design prevents the "name collision" class of bugs common in operators.

The TLS configuration system (`cmd/tlsconfig.go`) implements a propagation pattern where the operator's own TLS settings (`TLS_MIN_VERSION`, `TLS_CIPHER_SUITES`) can be forwarded to MCP server containers via the `PROPAGATE_TLS_ENV_VARS` environment variable. This enables platform-wide TLS policy enforcement without individual MCP server configuration, though it requires MCP server implementations to honor these environment variables.
