## Purpose

**Short**: A Kubernetes operator that provides a declarative API to deploy, manage, and safely roll out MCP (Model Context Protocol) servers, handling their full lifecycle with production-grade automation and gateway integrations.

**Detailed**: The mcp-lifecycle-operator translates MCPServer custom resources into a set of managed Kubernetes objects — Deployments, Services, and NetworkPolicies — that collectively run and protect user-supplied MCP server container images. It performs an MCP protocol handshake against each deployed server to verify reachability and protocol compliance before advertising readiness, providing a verification guarantee that the server is functioning correctly before traffic flows.

The operator implements a pluggable gateway integration architecture through MCPGatewayBinding resources. Two built-in providers — `httproute` (reference Gateway API HTTPRoute) and `kuadrant` (Kuadrant MCPGatewayExtension/MCPServerRegistration) — register themselves via Go `init()` and are reconciled by independent controllers. This design lets each MCPServer declaratively opt into external traffic exposure without coupling the core lifecycle logic to any specific ingress implementation.

The operator ships with a validating admission webhook that enforces policy on MCPServer create/update operations, including image allowlisting, digest-only image references, storage mount limits, and required labels. A CRD conversion webhook enables serving both v1alpha1 and v1beta1 API versions simultaneously, supporting rolling API migration. TLS configuration is environment-driven and supports post-quantum key exchange (X25519MLKEM768), with the operator propagating its validated TLS profile to managed MCP server containers when configured to do so.

## Architectural Analysis

The operator follows a standard kubebuilder/controller-runtime pattern with a single binary (`/manager`) hosting multiple controllers. The primary MCPServerReconciler owns the core lifecycle: it creates and reconciles a Deployment, Service, and NetworkPolicy for each MCPServer CR, then verifies the deployed server via an MCP protocol handshake using the `modelcontextprotocol/go-sdk`. The reconciler tracks three status conditions — Accepted (configuration valid), Available (workload running), and Verified (handshake passed) — providing a clear progression from spec validation through operational readiness.

The gateway integration uses a provider registry pattern (`internal/controller/providers/registry.go`) where providers self-register via blank imports and `init()` functions. Each provider runs its own controller watching MCPGatewayBinding resources filtered by provider name. The httproute provider creates Gateway API HTTPRoute resources pointing from a named Gateway to the MCPServer's Service. The kuadrant provider creates MCPServerRegistration and HTTPRoute resources coordinated with MCPGatewayExtension configuration. This separation means gateway-related reconciliation is fully decoupled from core lifecycle management.

NetworkPolicy management is notable: the operator supports two postures — "open" (default, allows all ingress) and "restricted" (denies unconfigured ingress by default). In restricted mode, the operator injects its own pod identity as an ingress peer so the verification handshake can still reach the managed server. Per-MCPServer ingress and egress rules are declarative via `spec.network`, with DNS egress always permitted. The operator also generates gateway-specific ingress peers when gateway integration is active.

TLS handling spans multiple concerns. The operator's own webhook and metrics endpoints use TLS configured via command-line flags and environment variables (`TLS_MIN_VERSION`, `TLS_CIPHER_SUITES`, `TLS_GROUPS`). The MCP handshake client supports per-MCPServer TLS transport configuration including custom CA bundles from Secrets and an opt-in `insecureSkipVerify` mode (with warning event emission). A TLS profile function propagated from the operator can optionally set min version, cipher suites, and named groups on managed server containers via environment variable injection (`PROPAGATE_TLS_ENV_VARS`).

The downstream Konflux build (`Dockerfile.konflux`) sets `GOEXPERIMENT=strictfipsruntime` and builds with `CGO_ENABLED=1` and `-tags=strictfipsruntime`, producing a dynamically-linked binary suitable for check-payload FIPS validation. A multi-stage build installs `crypto-policies-scripts` and sets the `DEFAULT:PQ` crypto policy, enabling post-quantum algorithm negotiation. The `rpms.lock.yaml` pins the crypto-policies-scripts package for hermetic builds across four architectures (x86_64, aarch64, ppc64le, s390x).
