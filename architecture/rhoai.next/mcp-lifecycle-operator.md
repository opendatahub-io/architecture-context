## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Context Protocol (MCP) servers by reconciling `MCPServer` custom resources into Deployments, Services, and NetworkPolicies.

**Detailed**: The MCP Lifecycle Operator is a Kubernetes operator built with kubebuilder (v4.11.1) and controller-runtime that automates the deployment and management of MCP servers on Kubernetes clusters. Users create `MCPServer` custom resources specifying a container image, port, environment variables, storage mounts, and runtime configuration; the operator then creates and manages a Deployment, ClusterIP Service, and NetworkPolicy for each MCPServer instance.

The operator performs an MCP protocol handshake against the deployed server endpoint to verify it speaks valid MCP (Streamable HTTP transport). On success, it populates the MCPServer status with the server's self-reported name, version, protocol version, instructions, and capabilities (tools, resources, prompts, logging, completions). The operator also computes a SHA-256 config hash of referenced ConfigMaps and Secrets, placing it as a pod annotation to trigger rolling updates when external configuration changes.

This is an upstream Kubernetes SIG project (`kubernetes-sigs`) being carried downstream for Red Hat OpenShift AI. The RHOAI build adds FIPS-compliant compilation (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`), Konflux CI/CD integration, and an ODH kustomize overlay with Prometheus ServiceMonitor.

## Architectural Analysis

The MCP Lifecycle Operator follows a clean kubebuilder v4 architecture with a single controller (`mcpserver`) managing three child resources per MCPServer CR: a Deployment, a ClusterIP Service, and a NetworkPolicy. The code is well-factored across focused files — deployment construction, service management, network policy, validation, condition management, ownership, config hashing, metrics, and MCP handshake are each in separate files. This decomposition keeps cyclomatic complexity low and makes the reconciliation flow easy to follow.

The MCP handshake verification is a distinctive architectural choice. After confirming the Deployment is available, the controller opens a real MCP session using the `modelcontextprotocol/go-sdk` client, performing an `initialize` handshake against the pod's service URL. This validates that the container actually speaks MCP protocol (not just that the port is open). The extracted `ServerInfo` — including capabilities like tools, resources, prompts, logging, and completions — is written back to the MCPServer status, making it queryable by platform-level tooling. The handshake uses exponential backoff (10s, 20s, 40s... up to 2min, max 10 retries) and treats HTTP 401/403 as "reachable" (auth-protected MCP servers are valid). A 15-second context timeout prevents the handshake from blocking the reconcile loop.

The ownership model is careful about resource adoption. Rather than silently overwriting existing resources, the controller validates ownership: resources with no controller owner are rejected (preventing accidental adoption of manually-created resources), resources owned by a different controller are rejected with an `OwnershipConflictError`, and orphaned resources from a deleted-and-recreated MCPServer (same name/namespace/group but different UID) are adopted. This prevents a class of bugs where operator restarts or CRD recreation could corrupt pre-existing resources.

The config hash mechanism (`mcp.x-k8s.io/config-hash` annotation) is a robust approach to triggering rolling updates when referenced ConfigMaps or Secrets change. The controller watches both resource types via field indexes and requeues affected MCPServers. The SHA-256 hash covers all data/binaryData keys in referenced ConfigMaps and all data keys in referenced Secrets, sorted deterministically. This ensures that configuration drift in external resources propagates to pods even though the Deployment spec itself hasn't changed.

The NetworkPolicy created per MCPServer is intentionally permissive on the source side — it allows ingress from any pod in the cluster on the MCP port but restricts to only that port. This is a practical default: MCP clients are diverse (AI agents, developer tools, orchestrators) and imposing source restrictions would require users to specify allowed client namespaces. The operator's own metrics endpoint has a stricter NetworkPolicy that limits access to namespaces labeled `metrics: enabled`.
