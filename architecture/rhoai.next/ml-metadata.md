## Purpose

**Short**: ML Metadata (MLMD) is a library and gRPC server for recording and retrieving metadata associated with ML workflows, providing lineage tracking for artifacts, executions, and contexts.

**Detailed**: ML Metadata is an open-source library originally developed by Google as part of the TFX (TensorFlow Extended) ecosystem. It provides a metadata store that records the relationships between ML pipeline components: artifacts (datasets, models, metrics), executions (training runs, transformations), and contexts (pipelines, experiments). The store supports SQLite, MySQL, and PostgreSQL backends.

In the RHOAI platform, MLMD is deployed as a gRPC server (`metadata_store_server`) that serves as the persistent metadata backend for ML pipelines. Components like Kubeflow Pipelines use MLMD to track experiment lineage -- which datasets were used to train which models, what parameters were used in each execution, and how artifacts flow between pipeline steps. The gRPC server exposes the `MetadataStoreService` API defined in Protocol Buffers, supporting CRUD operations on artifacts, executions, contexts, events, and lineage graph queries.

The repository also provides a Python client library (`ml_metadata` PyPI package) that can connect either directly to a database or to the gRPC server. The Red Hat fork adds RHEL-based container builds (UBI9) and Konflux CI integration for the gRPC server image, while keeping the core library unchanged from upstream.

## Architectural Analysis

ML Metadata follows a clean layered architecture with clear separation between the API layer (protobuf/gRPC), the business logic layer (MetadataStore C++ class), and the storage layer (MetadataSource implementations for SQLite, MySQL, and PostgreSQL). The proto definitions serve as the canonical data model, with the C++ gRPC service implementation being a thin wrapper around the core MetadataStore library. This design allows the Python client to bypass gRPC entirely and call the C++ library directly via pybind11 when co-located with the database.

The schema migration system is noteworthy. The `MetadataSourceQueryConfig` proto defines every SQL query as a parameterized template, with separate template sets for each database backend (SQLite, MySQL, PostgreSQL). Schema evolution is managed through a `migration_schemes` map keyed by schema version, with each version providing upgrade and downgrade query sequences and verification tests. This makes the component database-agnostic at the application level while supporting backend-specific optimizations.

From a security perspective, the FIPS compliance story has a gap. The gRPC server links against BoringSSL (bundled via Bazel from a pinned commit) for its TLS layer, rather than the system's FIPS-validated OpenSSL. While the database connections (PostgreSQL via libpq, MySQL via libmysqlclient) use the system SSL libraries, the primary client-facing gRPC TLS uses BoringSSL. The Dockerfile runs the server as non-root user (65534:65534), which is a positive security posture. The Konflux build targets three architectures (x86_64, arm64, ppc64le) per the Tekton pipeline configuration.

The build system is Bazel-based, which provides reproducibility through pinned dependencies with SHA256 checksums in the WORKSPACE file. However, the overall build is not hermetic -- the Tekton pipeline explicitly sets `hermetic: false`, and RPM packages in the builder stage are unpinned. The Konflux Dockerfile pins both base images by SHA256 digest, which is good practice for reproducibility. The 4-hour pipeline timeout and high compute resources (8-16 CPU, 16-32 GB RAM) reflect the heavy C++ compilation required by Bazel.

The Python client library (`ml_metadata` package) provides two operational modes: direct database connection (using the pybind11 C++ extension) and gRPC client mode. The gRPC client includes retry logic with exponential backoff for Aborted errors (configurable up to 5 retries by default). The client supports pagination for list operations with a maximum page size of 100 results, transparently handling multi-page fetches.
