## Purpose

**Short**: ML Metadata (MLMD) is a gRPC server and client library for recording and retrieving metadata associated with ML workflows, tracking artifacts, executions, contexts, and their lineage relationships.

**Detailed**: ML Metadata provides a centralized metadata store for machine learning pipelines. It defines a type system for three core entities -- Artifacts (datasets, models, metrics), Executions (training runs, transformations), and Contexts (experiments, pipelines) -- and records the events that connect them to form a lineage graph. This lineage tracking enables reproducibility, auditing, and debugging of ML workflows.

The component has two primary modes of operation: a standalone C++ gRPC server (`metadata_store_server`) that can be deployed as a containerized service, and a Python client library that can connect either directly to a database backend or to the gRPC server. The server supports MySQL, PostgreSQL, and SQLite as storage backends, with configurable SSL/TLS for both the gRPC channel and database connections.

In the RHOAI platform, MLMD serves as the metadata backbone for Kubeflow Pipelines, storing pipeline run metadata, artifact provenance, and execution lineage. The Red Hat downstream fork produces a Konflux-built container image (`odh-mlmd-grpc-server`) based on UBI 9 minimal (PQC variant) that runs the C++ gRPC server on port 8080.

## Architectural Analysis

MLMD follows a classic client-server architecture with a protobuf-defined API boundary. The server is a monolithic C++ binary built with Bazel that directly implements the `MetadataStoreService` gRPC service. The service layer delegates to a `MetadataStore` object, which in turn uses a pluggable `MetadataAccessObject` backed by SQL query templates specialized per database backend (MySQL, PostgreSQL, SQLite). This template-driven SQL approach allows the same business logic to work across databases with backend-specific query syntax.

The server's security model is configuration-driven rather than hardcoded. SSL/TLS for the gRPC channel is optional and controlled entirely through the `MetadataStoreServerConfig` protobuf configuration file. When no SSL config is provided, the server uses `InsecureServerCredentials`, which is the default posture in the Konflux Dockerfile. Database connections similarly support optional SSL through backend-specific configuration (MySQL SSL options with certificate paths and cipher selection; PostgreSQL sslmode with key/cert/password options).

A notable architectural characteristic is the use of BoringSSL (via gRPC's dependency chain) rather than system OpenSSL for the gRPC transport layer. The server binary is compiled with Bazel using C++17 and linked against the BoringSSL bundled with gRPC. The Konflux production image uses `ubi9/ubi-minimal-pqc` (a post-quantum cryptography UBI variant) as the runtime base, but the server binary itself carries its own crypto stack through the Bazel-built BoringSSL dependency.

The Python client library shipped in this repo provides both a direct-database access path (via C++ extensions compiled with Bazel) and a gRPC client path. The Python layer adds SSL channel credential support and exponential-backoff retry logic for transient `Aborted` errors. However, the Python package is not deployed as part of the RHOAI server image -- it is consumed as a pip package by other components like Kubeflow Pipelines SDK.

The component has no Kubernetes manifests, RBAC definitions, or CRDs of its own. It is a standalone gRPC server that relies on the deploying operator (typically the Data Science Pipelines operator) to manage its lifecycle, configure its database connection, and handle network exposure.
