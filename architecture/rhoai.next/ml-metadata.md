## Purpose

**Short**: ML Metadata (MLMD) is a gRPC server and Python client library for recording and retrieving metadata associated with ML workflows, tracking artifacts, executions, and their lineage.

**Detailed**: ML Metadata is a Google-originated library that provides a metadata store for machine learning pipelines. It defines a data model centered around three core entities -- Artifacts (data objects like datasets, models, metrics), Executions (pipeline steps that consume and produce artifacts), and Contexts (groupings that organize artifacts and executions) -- connected by Events, Attributions, and Associations.

In the RHOAI platform, the MLMD gRPC server (`metadata_store_server`) is deployed as a sidecar or standalone service to back pipeline metadata storage. It supports multiple database backends including MySQL, PostgreSQL, and SQLite. The server exposes a comprehensive gRPC API defined in Protocol Buffers for CRUD operations on all entity types, type management, and lineage graph queries. The Python client library (`ml-metadata` PyPI package) provides both a direct database connection mode and a gRPC client mode for interacting with the server.

The Red Hat downstream fork (`red-hat-data-services/ml-metadata`) adds Red Hat-specific build infrastructure (Dockerfile.konflux for Konflux CI, UBI9 base images, Tekton pipeline configurations) while maintaining the upstream Google codebase. The primary shippable artifact is the `odh-mlmd-grpc-server` container image built from C++ source using Bazel.

## Architectural Analysis

The ML Metadata server follows a clean layered architecture. At the top, the gRPC service layer (`MetadataStoreServiceImpl`) implements all RPCs defined in `metadata_store_service.proto`. Each RPC handler creates a fresh `MetadataStore` connection to the configured database, executes the operation, and returns the result. This per-request connection pattern (visible in `metadata_store_service_impl.cc` where every method calls `ConnectMetadataStore`) is simple but potentially expensive -- the code includes a TODO (`b/123039345`) acknowledging the need for a connection pool.

The data model is remarkably well-structured for lineage tracking. The three core entity types (Artifact, Execution, Context) are connected through three relationship types (Event links Artifact-Execution, Attribution links Artifact-Context, Association links Execution-Context, ParentContext links Context-Context). This graph structure enables the `GetLineageSubgraph` RPC, which performs bounded bidirectional graph traversal to reconstruct provenance chains. The newer `LineageSubgraphQueryOptions` replaces the deprecated `LineageGraphQueryOptions`, adding directional traversal (upstream/downstream/bidirectional) and ending node filters.

The type system uses extensible schemas with backward-compatible evolution. Each entity has a type (ArtifactType, ExecutionType, ContextType) with a `properties` map defining the schema. Type evolution is controlled by `can_add_fields` and `can_omit_fields` flags, preventing breaking changes to stored data while allowing forward evolution. System-defined base types (`mlmd.Dataset`, `mlmd.Model`, `mlmd.Train`, etc.) provide a standard vocabulary across ML platforms.

From a Red Hat integration perspective, the downstream fork adds minimal code changes. The primary additions are build infrastructure: `Dockerfile.konflux` for Konflux CI builds on UBI9 with multi-architecture support (x86_64, arm64, ppc64le per the Tekton pipeline), `Dockerfile.redhat` with ZetaSQL compatibility patches for UBI9, and Tekton PipelineRun configurations. The container runs as non-root (UID 65534) and exposes only gRPC on port 8080. The build is currently non-hermetic (`hermetic: false` in the Tekton config), which is a supply chain risk for production RHOAI releases.

A notable security consideration is that the MLMD server has no built-in authorization layer. While TLS and mTLS can be configured for transport security, there is no per-user, per-namespace, or per-pipeline access control within the metadata store. Any client that can reach the gRPC port can read or modify all metadata. In RHOAI deployments, isolation depends entirely on the platform operator deploying separate MLMD instances per Data Science Pipelines Application (DSPA) and using Kubernetes NetworkPolicy to restrict access.
