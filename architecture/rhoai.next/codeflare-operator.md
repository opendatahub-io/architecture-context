## Purpose

**Short**: Kubernetes operator that manages the lifecycle of RayCluster resources and optionally embeds an AppWrapper controller for Kueue-integrated batch workload management on RHOAI.

**Detailed**: The codeflare-operator is a Go-based Kubernetes operator built on controller-runtime that provides two core capabilities for the distributed AI compute layer of Red Hat OpenShift AI. Its primary controller, `RayClusterReconciler`, watches `RayCluster` CRs and creates supplementary resources needed for production operation on OpenShift: OAuth proxy sidecars for dashboard authentication, OpenShift Routes for external access, mTLS certificate infrastructure for inter-node encryption, NetworkPolicies for pod isolation, and ClusterRoleBindings for authorization delegation. Its secondary controller, embedded from the upstream `project-codeflare/appwrapper` library, manages `AppWrapper` CRs that provide a workload-agnostic grouping mechanism allowing Kueue to schedule and manage collections of Kubernetes resources (Jobs, PyTorchJobs, RayClusters, JobSets) as single queuing units with automatic fault detection and recovery.

The operator is deployed as a single Deployment (`codeflare-operator-manager`) in the `opendatahub` namespace, configured via a ConfigMap (`codeflare-operator-config`) that controls feature toggles for OAuth dashboard protection, mTLS enforcement, and AppWrapper enablement. It registers four admission webhooks — mutating and validating pairs for both `RayCluster` and `AppWrapper` resources — that inject security sidecars, enforce immutability of injected containers, and validate workload specifications at admission time.

## Architectural Analysis

The codeflare-operator demonstrates a dual-controller architecture where each controller serves a distinct purpose within the distributed AI scheduling stack. The RayCluster controller acts as a platform integration layer rather than a workload orchestrator — it does not manage Ray job execution, which is handled by the KubeRay operator, but instead enriches RayCluster resources with OpenShift-specific security and networking primitives. This separation of concerns means the codeflare-operator has an unusually broad RBAC surface (31 rules in the manager ClusterRole) spanning core resources, Ray CRDs, networking, RBAC, OpenShift routes, and multiple batch scheduling APIs, which reflects its role as a bridge between workload schedulers and the platform security model.

The mTLS implementation is notable: the operator generates a per-RayCluster CA key pair stored as a Kubernetes Secret, and the mutating webhook injects init containers that use `openssl` commands to generate node certificates at pod startup. This means certificate generation happens in the data plane (Ray pods) rather than the control plane, using the CA material provisioned by the controller. The CA key uses RSA-2048 with SHA-1 for the self-signed certificate — the SHA-1 usage is architecturally significant as it applies only to the internal CA certificate (not for external trust chains) but represents a crypto library choice worth tracking.

The AppWrapper controller is embedded as a Go library dependency rather than deployed separately, controlled by a runtime feature flag. When disabled (the default), the operator optimizes its informer cache to only watch resources labeled with `ray.openshift.ai/cluster-name`, reducing memory footprint. When enabled, it registers additional indexers and webhooks for AppWrapper lifecycle management. This conditional architecture means the operator's resource footprint and API surface change significantly based on configuration.

A key design decision is the use of OpenShift's OAuth proxy pattern: the mutating webhook injects an `oauth-proxy` sidecar container into every RayCluster head pod, which provides dashboard authentication by delegating to OpenShift's built-in OAuth server. The proxy uses `openshift-delegate-urls` to map pod-level `get` access to dashboard authorization, creating a tight integration with OpenShift's RBAC model. On vanilla Kubernetes, this pathway is skipped entirely and Ingress resources are created instead — the `isOpenShift` detection uses API group discovery to select the behavior at startup.
