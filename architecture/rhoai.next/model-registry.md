## Purpose

**Short**: Central repository for model developers to store and manage ML models, versions, artifacts metadata, and curated model/MCP/agent catalogs.

**Detailed**: Model Registry is a metadata service for the Kubeflow/OpenDataHub/RHOAI ecosystem that provides a REST API for registering, versioning, and tracking machine learning models across their lifecycle. It manages the relationships between registered models, model versions, model artifacts, inference services, and serving environments, enabling lineage tracking from training through deployment.

The component ships as a multi-service platform: (1) a Go REST API server backed by PostgreSQL or MySQL for model metadata CRUD operations, (2) a catalog service with plugin architecture for curating model catalogs (from HuggingFace), MCP server catalogs, and agent catalogs, (3) a Kubernetes controller that synchronizes KServe InferenceService CRDs with the Model Registry, (4) a CSI storage initializer that resolves `model-registry://` URIs for KServe model downloads, (5) a React/TypeScript UI with Go BFF for browsing and managing models, and (6) a Python async-upload Job for copying models between storage backends (S3/OCI) with Sigstore signing.

The Go module is `github.com/kubeflow/hub` and the OpenAPI spec defines the v1alpha3 REST API. The catalog service uses a plugin architecture with leader election (PostgreSQL pglock) for distributed deployments, supporting model, MCP server, and agent catalog plugins.

## Architectural Analysis

Model Registry is a multi-component Go monorepo with a well-defined separation between the metadata API server, catalog service, controller, storage initializer, UI, and async-upload job. All components share a single Go module (`github.com/kubeflow/hub`) but compile into distinct binaries via separate `cmd/` entry points. The API server and catalog server share the same container image but are invoked with different subcommands (`proxy` vs `catalog`), reducing image sprawl while maintaining deployment isolation.

The database architecture uses GORM as an ORM abstraction with pluggable drivers for MySQL and PostgreSQL. The schema is based on ML Metadata (MLMD) concepts -- contexts, artifacts, executions, and events -- mapped to domain entities (RegisteredModel, ModelVersion, ModelArtifact, InferenceService, ServingEnvironment). A migration framework (`golang-migrate`) handles schema evolution with retry logic (25 attempts with incremental backoff). The health endpoint detects migration "dirty" states and returns 503 until migrations complete cleanly, which is a thoughtful resilience pattern.

The catalog service's plugin architecture is notable -- it uses a registry pattern where model, MCP, and agent plugins register globally and are discovered at startup. Each plugin implements a well-defined interface (`Init`, `Start`, `Stop`, `Healthy`, `RegisterRoutes`, `Migrations`) with optional interfaces for leader-awareness and reconnection. Leader election uses PostgreSQL's `pglock` extension with configurable lock duration and heartbeat, ensuring only one catalog pod writes to the database in multi-replica deployments. The file monitor for YAML source configuration uses CRC32 hashing to detect actual content changes, avoiding false positives from Kubernetes ConfigMap symlink updates -- a detail that shows production-hardened awareness.

The inference-service controller is lightweight but architecturally significant: it bridges the KServe CRD world with the Model Registry REST API, creating ServingEnvironments per Kubernetes namespace and syncing InferenceService deployment state. Finalizer management ensures cleanup on deletion (best-effort -- removes finalizer even if Model Registry is unavailable, preventing InferenceService deletion from being blocked). The CSI storage initializer adds a critical integration point: it registers the `model-registry://` URI scheme with KServe via ClusterStorageContainer, resolves model artifact URIs through the Registry API, validates them against an allowlist (blocking cloud metadata endpoints like `169.254.169.254`), then delegates to KServe's native S3/GCS/HTTP providers for actual download.

The async-upload job is the only Python component and the only one using AIPCC base images. It supports three intent types (`update_artifact`, `create_model`, `create_version`) and performs the full cycle of download → sign → upload → register. Sigstore integration for model signing is auto-detected from environment variables, providing a good developer experience. The job writes results to `/dev/termination-log` for Kubernetes to surface in pod status.
