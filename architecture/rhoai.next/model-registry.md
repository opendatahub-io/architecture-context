## Purpose

**Short**: Model Registry provides a central metadata store for ML models, versions, and artifacts with a REST API, a UI with backend-for-frontend, a Kubernetes controller for InferenceService sync, a storage initializer for KServe, and a model catalog service for federated model discovery.

**Detailed**: Model Registry is a multi-component system originating from the Kubeflow Hub project. Its core is a Go REST API server that stores and manages model metadata (registered models, model versions, and model artifacts) in a relational database (PostgreSQL or MySQL). The server exposes an OpenAPI-defined REST interface on port 8080 for CRUD operations on model metadata.

The repository produces several deployable artifacts: (1) the model-registry proxy server — the primary data plane serving model metadata; (2) a UI backend-for-frontend (BFF) in Go that mediates between the React frontend and the model-registry API, plus Kubernetes resources like ConfigMaps and Secrets; (3) a controller-runtime operator that watches KServe InferenceService resources and synchronizes their state with registered models; (4) a CSI storage-initializer that downloads model artifacts from the registry for KServe serving; (5) a model catalog server that provides federated model discovery across sources like HuggingFace, MCP servers, and serving runtimes; and (6) a Python async-upload job that copies models between storage backends and registers them.

The system is designed for the Kubeflow and OpenShift AI platforms, with kustomize overlays for different deployment scenarios (standalone, Kubeflow-integrated, RHOAI). Authentication is layered: the model-registry service is protected by Istio AuthorizationPolicies in Kubeflow deployments, while the BFF supports both internal ServiceAccount tokens and user-forwarded Bearer tokens.

## Architectural Analysis

Model Registry's architecture reflects its evolution from a single-purpose metadata store into a multi-faceted ML lifecycle hub. The codebase is organized as a Go workspace with multiple `go.mod` files — the root module houses the REST proxy server and database layer, `clients/ui/bff` contains an independent BFF application, `cmd/controller` holds the controller-runtime operator, `pkg/inferenceservice-controller` is a reusable controller library, and `catalog/` implements the model catalog service. This module structure enables independent compilation and versioning of each component.

The data layer uses GORM with migration support for both PostgreSQL and MySQL via `golang-migrate`. Database schema evolution is handled through embedded SQL migrations under `internal/datastore/embedmd/`. The REST API is OpenAPI-generated (`api/openapi/`) with server stubs in `internal/server/openapi/` and client stubs in `pkg/openapi/`, while business logic lives in `internal/core/` with type conversion handled by `goverter`-generated converters.

A key architectural decision is the conditional controller pattern: the InferenceService controller is only activated when the `INFERENCE_SERVICE_CONTROLLER=managed` environment variable is set (cmd/controller/main.go:138). This lets the same controller binary serve environments with or without KServe installed. The controller watches `serving.kserve.io/v1beta1/InferenceService` resources and reconciles their state with model registry metadata, using configurable label names for flexible integration.

The BFF implements a sophisticated auth model with two modes (`internal` and `user_token`), configurable token headers and prefixes, and per-request Kubernetes client construction that impersonates the calling user's identity via `SelfSubjectAccessReview` and `SelfSubjectRulesReview`. This design delegates authorization decisions to the Kubernetes API server rather than implementing custom RBAC.

The model catalog is a plugin-based system — each data source (HuggingFace models, serving runtimes, MCP servers, agents, skills) is implemented as a catalog plugin that conforms to a common interface. The catalog server aggregates sources from YAML configuration files and exposes a unified query API. The RHOAI overlay adds a performance data init container for benchmark metadata.

The async-upload job (Python) is architecturally distinct: it runs as a Kubernetes Job, uses the AIPCC base image, and handles model transfer between storage backends with sigstore-based model signing. It carries its own requirements files and builds from a separate Dockerfile.

TLS is configured consistently across components: the core server's `internal/platform/tls/config.go` enforces TLS 1.2 minimum with configurable cipher suites and an explicit reject list for insecure ciphers; the BFF enforces TLS 1.3 minimum when TLS is enabled; the controller disables HTTP/2 by default to mitigate stream cancellation CVEs.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | manifests/kustomize/base/model-registry-deployment.yaml, manifests/kustomize/options/istio/istio-authorization-policy.yaml |
| **Deployment model** | per-namespace instance | Each model registry instance is deployed per namespace; the BFF discovers available registries |
| **Tenant identifier** | namespace name + model registry service name | clients/ui/bff/internal/api/app.go:38 (ModelRegistryId), Istio AuthorizationPolicy namespace constraint |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user RBAC via SelfSubjectAccessReview; Istio AuthorizationPolicy restricts registry access by namespace | Kubernetes API + Istio | BFF delegates all authz to Kubernetes RBAC; policies must be correctly configured per namespace |
| Data storage | Per-instance database (each registry has its own DB or schema) | Application deployment | No cross-tenant data leakage by design; separate DB per registry instance |
| Network traffic | Istio AuthorizationPolicy restricts source namespace to kubeflow; blocks kubeflow-userid header spoofing from non-gateway sources | Istio | Requires Istio sidecar injection; without Istio, registry endpoints are unprotected |
| Compute & resources | No built-in ResourceQuota or LimitRange; controller has resource limits (128Mi memory) | Kubernetes (manual) | Resource isolation depends on namespace-level Kubernetes configuration |
| Configuration & secrets | Per-namespace Secrets (DB credentials, HF API keys) | Kubernetes | Secrets must be provisioned per namespace |
| API scoping | BFF scopes queries to the selected model_registry_id; controller uses configurable namespace labels | Application + Kubernetes | Controller watches cluster-scoped InferenceServices but filters by label |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Model catalog server | Shared across tenants | Read-only federated catalog; no per-tenant write isolation |
