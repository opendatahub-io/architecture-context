## Purpose

**Short**: A central metadata repository for ML model lifecycle management, providing REST APIs for registering, versioning, and tracking models, artifacts, experiments, and serving environments.

**Detailed**: Model Registry is a multi-component platform service that provides a central repository for ML practitioners to store and manage model metadata throughout the AI/ML lifecycle. It exposes a REST API (OpenAPI v1alpha3) for CRUD operations on registered models, model versions, model artifacts, serving environments, inference services, experiments, experiment runs, datasets, metrics, and parameters. The service uses a relational database backend (MySQL or PostgreSQL) via GORM for persistent storage.

The repository contains six deployable components: (1) the core Model Registry REST API server, (2) a Catalog server for managing model, agent, and MCP server catalogs, (3) an InferenceService controller that synchronizes KServe InferenceService CRs with the registry, (4) a CSI storage initializer that enables KServe to download models via `model-registry://` URIs, (5) a UI Backend-for-Frontend (BFF) that serves the React frontend and proxies API calls, and (6) a Python async-upload job that copies models between storage backends (S3, OCI, HTTP) and registers them in the registry.

The component fits into the RHOAI platform as the metadata backbone for model governance: it tracks which models exist, their versions and artifacts, where they are served, and how experiments relate to model versions. It integrates with KServe for model serving, the RHOAI dashboard for UI access, and supports model signing via Sigstore for supply chain security.

## Architectural Analysis

Model Registry follows a hub-and-spoke architecture where the central REST API server acts as the metadata store, and satellite components (controller, CSI driver, UI, async-upload job) interact with it through its REST API. This design enables independent scaling and deployment of each component — the core server can run standalone, and optional components are added via kustomize overlays.

The database abstraction layer is well-designed with a factory/registry pattern supporting both MySQL and PostgreSQL through GORM. Connection retry logic (25 attempts with incremental backoff, ~5 minutes total) handles startup race conditions gracefully. The `DynamicRouter` pattern allows the HTTP server to start immediately and serve health checks while the database connection is established asynchronously — a smart approach for Kubernetes environments where probes must respond before the full service is ready.

The Go module structure reveals a clean separation of concerns but also reveals the repository's evolution. The top-level Go module (`github.com/kubeflow/hub`) was recently renamed from `model-registry`, and the repo contains five separate Go modules (`go.mod`, `gorm-gen/go.mod`, `cmd/controller/go.mod`, `cmd/csi/go.mod`, `pkg/inferenceservice-controller/go.mod`) with local `replace` directives. The controller and CSI driver have their own go.mod files because they depend on KServe v0.17.0-rc1, which has a large dependency tree that would bloat the core server. This multi-module approach keeps the core server lightweight.

The security architecture relies heavily on Istio for network-level access control. The Istio `AuthorizationPolicy` enforces a two-rule model: (1) traffic from the ingress gateway (authenticated users with `kubeflow-userid` header) and (2) service-to-service traffic from the kubeflow namespace with K8s authorization header but without `kubeflow-userid` header (restricting to the control-plane controller). This is a significant security improvement over allowing any in-mesh pod to reach the registry. The BFF adds a second authorization layer using K8s `SubjectAccessReview` to check namespace-scoped access before proxying requests.

The CSI storage initializer includes thoughtful security hardening: a hardcoded blocklist of cloud metadata endpoints (169.254.169.254, fd00:ec2::254, metadata.google.internal) and link-local IPv6 address detection prevents SSRF attacks through model artifact URIs. An optional allowlist (`ALLOWED_ARTIFACT_URI_PREFIXES`) provides defense-in-depth for restricting which storage backends are trusted. The async-upload job supports model signing via Sigstore/cosign, adding supply chain security to the model transfer workflow.

The catalog subsystem is architecturally notable as a plugin-based system. It supports three catalog types (model, agent, MCP server) through a plugin registry pattern, with each plugin providing its own entity types, service implementations, and data loaders. Catalog sources are configured via ConfigMaps mounted as YAML files, allowing dynamic catalog management without redeployment. The catalog uses its own PostgreSQL instance, separate from the main model registry database, enabling independent scaling and lifecycle management.
