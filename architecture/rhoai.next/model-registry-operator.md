## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry and Model Catalog instances on OpenShift AI, provisioning REST API deployments, database backends, authentication proxies, and ingress infrastructure for each registry.

**Detailed**: The model-registry-operator is a controller-runtime-based Go operator built with kubebuilder v4. It watches `ModelRegistry` custom resources (API group `modelregistry.opendatahub.io`, versions `v1alpha1` and `v1beta1`) and reconciles the full stack of Kubernetes resources needed to run a model registry instance: a Deployment running the model-registry REST API server, a Service, a ServiceAccount, RBAC roles and bindings, optional PostgreSQL or MySQL database backends (with auto-provisioning support for PostgreSQL), and an authentication proxy sidecar (kube-rbac-proxy).

The operator supports two ingress modes on OpenShift: the **Data Science Gateway** mode (Gateway API HTTPRoutes referencing a shared platform gateway) and **OpenShift Routes** (direct `reencrypt` TLS routes). Both modes can be active simultaneously for backward compatibility. The operator also manages a **Model Catalog** subsystem -- a singleton catalog service with its own PostgreSQL database, kube-rbac-proxy authentication, RBAC for admin groups, and labeled ConfigMap discovery for catalog sources.

The operator includes platform-aware capability detection that adapts to traditional OpenShift, BYOIDC-enabled OpenShift 4.20+ (where `user.openshift.io` APIs are absent), and plain Kubernetes clusters. It also performs CRD storage version migration from `v1alpha1` to `v1beta1` using either Kubernetes StorageVersionMigration or a manual fallback strategy.

## Architectural Analysis

The model-registry-operator exhibits a clean separation between its two controllers, each addressing different lifecycle patterns. The `ModelRegistryReconciler` follows a standard one-CR-per-instance pattern: each `ModelRegistry` CR triggers creation of an isolated resource set (Deployment, Service, RBAC, NetworkPolicy, Routes). The `ModelCatalogReconciler`, by contrast, manages a singleton -- all watched resources map to a fixed reconcile request via `mapToFixedCatalogRequest`, preventing reconcile storms when multiple ConfigMaps or Deployments trigger events simultaneously. This design difference is architecturally significant because it shows the team consciously chose different patterns for different scaling requirements.

The authentication migration path is noteworthy. The operator has undergone three generations of auth proxy: Istio service mesh (v1alpha1, fully removed), OAuth proxy (v1alpha1/early v1beta1, auto-migrated), and kube-rbac-proxy (current v1beta1). The `MigrateOAuthProxyToKubeRBACProxy()` method in the webhook and the `ReplaceIstioWithOAuthProxy()` in v1alpha1 conversion demonstrate a careful migration chain. The defaulting webhook ensures that on OpenShift clusters, registries without any auth proxy configured automatically get kube-rbac-proxy added -- a hardening measure that prevents accidental unauthenticated deployments. The reconciler also performs this defaulting as a safety net for registries modified outside the webhook path.

The Gateway API integration is implemented as an additive layer rather than a replacement. When `GATEWAY_DOMAIN` is set, the operator creates HTTPRoutes in a configurable namespace (default: `redhat-ods-applications`) with cross-namespace `ReferenceGrant` resources, while simultaneously maintaining OpenShift Routes for backward compatibility. The `ReferenceGrant` is intentionally created via `createIfNotExists` (not `createOrUpdate`) because it's namespace-scoped and shared across all registries -- updating it on every reconcile would cause unnecessary churn. This dual-ingress approach allows gradual migration from Route-based to Gateway API-based ingress.

The operator's cache strategy in `cmd/main.go` is deliberately fine-tuned for multi-tenancy. Most operator-created resources are filtered by the `app.kubernetes.io/created-by: model-registry-operator` label, keeping the informer cache small. Secrets, however, are excluded from the cache entirely (`DisableFor: []client.Object{&corev1.Secret{}}`) because user-provided database credentials and TLS secrets won't have operator labels, and caching them would leak across tenants. ConfigMaps use namespace scoping instead of label filtering because user-created catalog source ConfigMaps also lack operator labels. These decisions show awareness of the informer cache as a security boundary.

The platform capability detection (`DetectClusterCapabilities`) deserves attention for its handling of BYOIDC clusters. In OpenShift 4.20+ with BYOIDC, the `user.openshift.io` API is intentionally disabled, causing partial discovery failures. The operator distinguishes between "API not found" (expected BYOIDC behavior) and "API failed for other reasons" (transient errors that should block startup). This ensures the operator doesn't silently skip Group creation due to network blips while correctly adapting to BYOIDC environments where Groups are managed by external identity providers.
