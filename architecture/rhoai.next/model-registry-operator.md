## Purpose

**Short**: Manages the lifecycle of Model Registry and Model Catalog instances on OpenShift AI and Open Data Hub platforms.

**Detailed**: The Model Registry Operator is a Kubernetes operator built with controller-runtime that manages `ModelRegistry` custom resources. Each ModelRegistry CR represents a metadata store for ML models, backed by either PostgreSQL or MySQL. The operator reconciles the desired state by creating and managing Deployments, Services, ServiceAccounts, NetworkPolicies, OpenShift Routes, Gateway API HTTPRoutes, and kube-rbac-proxy sidecars for authentication.

The operator also includes a Model Catalog controller that deploys a centralized catalog service for discovering and browsing model metadata. The catalog has its own PostgreSQL backend (auto-provisioned), kube-rbac-proxy authentication, and Gateway API integration. Both controllers detect cluster capabilities at startup (OpenShift vs vanilla Kubernetes, BYOIDC mode, Gateway API availability) and adapt their resource creation accordingly.

A storage migration subsystem handles CRD version upgrades (v1alpha1 → v1beta1) using either the Kubernetes StorageVersionMigration API or a manual annotation-based fallback strategy. The operator also supports webhook-based defaulting and validation, including automatic migration from deprecated OAuth proxy and Istio configurations to the current kube-rbac-proxy pattern.

## Architectural Analysis

The Model Registry Operator follows a clean controller-runtime architecture with two reconcilers — ModelRegistryReconciler and ModelCatalogReconciler — sharing a common template engine and cluster capability detection system. The template-driven approach (30+ Go templates in `internal/controller/config/templates/`) keeps resource generation declarative while allowing the Go reconcilers to handle conditional logic around which templates to instantiate based on cluster capabilities, proxy configuration, and Gateway API availability.

The authentication architecture has undergone significant evolution visible in the codebase. The operator supports three auth proxy patterns in a migration chain: Istio (deprecated, auto-migrated at webhook defaulting time) → OAuth proxy (deprecated, auto-migrated) → kube-rbac-proxy (current). The webhooks handle this migration transparently — a v1alpha1 CR with Istio config gets converted to OAuth proxy, which then gets migrated to kube-rbac-proxy when stored as v1beta1. This conversion hub pattern (v1beta1 as storage version, v1alpha1 as spoke) is well-implemented but has explicit data loss: KubeRBACProxy and GenerateDeployment fields are dropped when converting to v1alpha1. The `MigrateOAuthProxyToKubeRBACProxy()` function in the reconciler handles in-place CR mutations during reconciliation for CRs that haven't been re-saved through webhooks.

The dual ingress strategy (OpenShift Routes + Gateway API HTTPRoutes) is conditional on the `GATEWAY_DOMAIN` environment variable. When set, the operator creates HTTPRoutes in a configurable namespace (defaulting to `openshift-ingress`) with path-based routing (`/model-registry/{name}/*`) and URL rewriting. ReferenceGrant CRs enable cross-namespace Service references. The operator creates both Routes and HTTPRoutes in parallel when both mechanisms are available, providing backward compatibility during the RHOAI 3.x Gateway API migration.

The cluster capabilities detection (`DetectClusterCapabilities`) runs once at startup and drives conditional resource creation throughout both reconcilers. The BYOIDC detection (OpenShift present but User API absent) is particularly noteworthy — it silently skips Group creation and adjusts RoleBinding subjects to reference external IdP groups instead of OpenShift Groups. The TLS security profile integration via `openshift/controller-runtime-common` fetches the cluster-wide TLS profile and applies it to both the webhook server and metrics server, with a watcher that triggers graceful pod restart on profile changes.

The Model Catalog controller is architecturally distinct from the registry controller despite sharing templates and infrastructure. It operates as a singleton (one catalog per namespace, fixed reconcile request mapping) rather than per-CR (multiple registries). It manages multiple ConfigMap sources (default catalog data, user catalog sources, MCP server sources, agent catalog sources) loaded via init containers, and integrates with the platform's Auth CR to determine admin groups for catalog access. The auto-provisioned PostgreSQL for the catalog uses a Recreate deployment strategy to avoid dual-write corruption during upgrades.

The storage migration subsystem demonstrates defense-in-depth: it first attempts the Kubernetes-native StorageVersionMigration API (which may not be available on all clusters), falling back to a manual strategy that lists all CRs, triggers conversion by reading/writing in the target version, and tracks progress via annotations. The migration monitor starts with a 30-second delay and checks every 30 seconds for SVM completion, making it resilient to transient API failures.
