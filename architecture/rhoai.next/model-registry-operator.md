## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry instances, a shared Model Catalog, and the AIHub platform component on OpenShift AI.

**Detailed**: The model-registry-operator is a kubebuilder-based Kubernetes operator that deploys and manages Model Registry instances from `ModelRegistry` Custom Resources. Each ModelRegistry CR is reconciled into a full deployment stack: the model-registry REST server, a PostgreSQL database (or external DB connection), a kube-rbac-proxy sidecar for authentication, OpenShift Routes or Gateway API HTTPRoutes for ingress, RBAC roles for per-registry user access control, and NetworkPolicies for traffic isolation.

Beyond individual registry instances, the operator manages two additional controllers. The CatalogReconciler deploys a shared Model Catalog service—a centralized catalog of model metadata sourced from configurable YAML-based catalog sources, backed by its own PostgreSQL instance, and exposed through the platform's ingress infrastructure. The AIHubReconciler manages the cluster-scoped AIHub component resource, orchestrating the Catalog lifecycle, admission webhooks, and platform-level RBAC.

The operator integrates with the broader RHOAI platform through the `odh-platform-utilities` library for platform detection and manifest rendering. It supports OpenShift-specific features (Routes, Groups, cluster TLS profile adherence, cluster proxy configuration) through runtime capability detection, and implements CRD storage version migration between v1alpha1 and v1beta1 API versions via the Kubernetes StorageVersionMigration API.

## Architectural Analysis

The operator follows a layered controller pattern with three reconcilers operating at different scopes. The AIHubReconciler is cluster-scoped and owns the Catalog lifecycle, creating and managing the Catalog CR and its associated webhooks. The CatalogReconciler operates in a designated namespace, deploying the catalog service with its PostgreSQL backend, kube-rbac-proxy sidecar, and ingress resources. The ModelRegistryReconciler is the most complex, managing per-instance deployments with template-based resource generation.

Resource creation relies heavily on embedded Go `text/template` files (`//go:embed`), organized under `internal/controller/config/templates/`. This design decouples Kubernetes resource structure from controller logic, with `TemplateApplier.Apply()` rendering each template using registry-specific parameters (name, namespace, spec values). The template approach enables consistent resource generation across the model-registry deployment, kube-rbac-proxy configuration, catalog deployment, and Gateway API routing resources.

The operator's cache strategy is noteworthy: it filters cached resources by the `app.kubernetes.io/created-by: model-registry-operator` label, keeping memory usage bounded. Secrets bypass the cache entirely (using direct API reads) because they are user-provided credentials (database passwords, TLS certificates) that lack operator labels. ConfigMaps are namespace-scoped in the cache to capture user-created catalog source ConfigMaps that also lack operator labels.

Security mode evolution is handled through automatic migration: the reconciler detects legacy OAuth Proxy configurations and migrates them to kube-rbac-proxy, the current authentication mechanism. The kube-rbac-proxy sidecar performs TokenReview and SubjectAccessReview against the Kubernetes API, enforcing RBAC-based access control at the service level.

The operator reads the cluster TLS security profile from the OpenShift APIServer resource at startup and configures both webhook and metrics servers accordingly. A `SecurityProfileWatcher` monitors for TLS profile changes at runtime and triggers a graceful pod restart when the profile is updated, ensuring the operator always operates within the cluster's TLS policy.

Gateway API support is conditional: when `GATEWAY_DOMAIN` is set, the operator creates HTTPRoute resources referencing a platform gateway (defaulting to `data-science-gateway` in `openshift-ingress`). Without it, the operator falls back to OpenShift Routes for ingress. Both paths produce HTTPS endpoints fronted by kube-rbac-proxy.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-registry kube-rbac-proxy sidecar with TokenReview/SAR; per-registry Role and RoleBinding scoped to `{registry-name}-users` OpenShift Group | Kubernetes RBAC + kube-rbac-proxy | Group membership managed via OpenShift Groups API; no automatic group creation for non-OpenShift clusters |
| Data storage | Per-registry PostgreSQL deployment (embedded mode) or per-registry database credentials (external mode) | Kubernetes (separate Pods/Secrets) | External database mode relies on user-provided credentials; no application-level row isolation if multiple registries share one external DB |
| Network traffic | Per-registry NetworkPolicy created by controller | Kubernetes NetworkPolicy | NetworkPolicy enforcement depends on cluster CNI supporting it |
| Compute & resources | Per-registry Deployment with configurable resource requests/limits (default: 100m CPU, 256Mi memory) | Kubernetes | No ResourceQuota enforcement by the operator; relies on namespace-level quotas if configured |
| Configuration & secrets | Per-registry Secrets for database credentials and TLS; per-registry ConfigMaps | Kubernetes namespace isolation | Secrets bypass operator cache (direct API reads), reducing risk of cross-tenant leakage |
| API scoping | ModelRegistry CRD is namespace-scoped; controller watches filtered by owner references | Kubernetes namespace scoping | Operator has cluster-wide permissions but creates resources only in target namespace |
