## Purpose

**Short**: AI Gateway control-plane controller that reconciles ExternalModel and ExternalProvider CRDs into per-tenant Envoy ExtProc dataplane configurations and routing overlays.

**Detailed**: ai-gateway-controller is the control-plane half of the AI Gateway's external-model architecture within Red Hat OpenShift AI. It is deployed by ai-gateway-operator as a sibling of maas-controller, replacing the dual control-plane/dataplane role that payload-processing (IPP) previously held.

The controller runs two reconciliation loops. The tenant reconciler (`pkg/tenant`) primarily watches `MaasTenantConfig` CRs owned by maas-controller, and for every tenant whose `maas.opendatahub.io/payload-processing-type` annotation is `praxis`, renders and SSA-applies a per-tenant copy of vendored praxis-extproc manifests (Deployments, Services, EnvoyFilters, NetworkPolicies, DestinationRules) into the tenant's Gateway namespace. The model reconciler (`pkg/controller`) watches `ExternalModel` and `ExternalProvider` CRDs defined in this repo, resolving multi-provider route sets and publishing content-addressed routing overlays, per-provider transport resources (ExternalName Services, ServiceEntries, DestinationRules, HTTPRoutes), and credential projections for the ExtProc dataplane.

The controller implements a race-free payload-processing backend swap handshake with maas-controller via annotation-based CAS on `MaasTenantConfig`, enabling incremental per-tenant migration from legacy IPP to the Praxis dataplane. It keeps its dependency graph deliberately minimal by reading maas-controller-owned CRDs (AITenant, MaasTenantConfig) via `unstructured.Unstructured` with hardcoded GVKs rather than importing their Go types.

## Architectural Analysis

ai-gateway-controller exhibits a two-plane separation where `pkg/tenant` owns dataplane lifecycle (install, cleanup, finalization of praxis-extproc manifests) and `pkg/controller` owns control-plane routing (ExternalModel → provider resolution, HTTPRoute generation, EnvoyFilter configuration, routing overlay publication). Both planes coordinate through shared tenant state: the model reconciler gates on `tenant.UsesPraxis` and `tenant.IsActive` before producing any transport or overlay resources, ensuring no routing state is applied for tenants that haven't completed their MaaS bootstrap or haven't opted into Praxis.

The backend swap handshake is architecturally significant. Because this controller and maas-controller share resource names (the `payload-processing` family), switching a tenant between backends requires a three-state CAS protocol on the `payload-processing-status` annotation: `cleanup-complete` → `steady` → back to `cleanup-complete` on switch-off. This avoids races where both controllers attempt to manage the same-named resources concurrently. The TOCTOU fence in `aiTenantStillValidForApply` (reading the AITenant live via APIReader immediately before SSA apply) addresses a further identity risk where a cached resolve could target a recreated or re-homed tenant.

Resource naming uses a `{base}-{tenantID}` convention, with the default/legacy tenant keeping unsuffixed names for backward compatibility. The 63-character Kubernetes name limit creates a bounded failure mode for tenants with very long names (logged and skipped, not retried). The controller uses server-side apply (SSA) with `ForceOwnership` and the field owner `ai-gateway-controller`, establishing clear ownership boundaries with maas-controller.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC via ClusterRoleBinding; per-provider API key Secrets scoped to tenant namespace | Kubernetes RBAC + Application | Provider Secret access is namespace-scoped; controller reads Secrets via APIReader to avoid cache-based credential leakage |
| Data storage | Per-namespace: ExternalModel/ExternalProvider CRs, routing overlay ConfigMaps, credential Secrets all namespace-scoped | Kubernetes | No shared data store; all state is Kubernetes-native |
| Network traffic | Per-tenant NetworkPolicy for praxis-extproc pods (skippable via `--skip-network-policy`); per-tenant DestinationRules with tenant-scoped naming | Kubernetes + Istio | NetworkPolicy can be opted out; no AuthorizationPolicy enforcement at controller level |
| Compute & resources | Per-tenant Deployment of praxis-extproc (separate pods per tenant) | Kubernetes | No ResourceQuota or LimitRange enforcement by this controller; delegated to platform |
| Configuration & secrets | Per-namespace Secrets for provider credentials; per-tenant plugins ConfigMaps | Kubernetes | Controller reads all Secrets in watched namespaces (read-only); no cross-tenant Secret access path |
| API scoping | Namespace-scoped watches with `InNamespace` list filters; `namespaceAllowed` guard on all reconcile paths | Application + Kubernetes | Model reconciler supports optional `--external-model-namespace` restriction; default watches all namespaces |
