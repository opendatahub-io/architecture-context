## Purpose

**Short**: Kubernetes operator that manages model serving infrastructure, admission webhooks, and serving runtime templates for OpenDataHub and RHOAI.

**Detailed**: The odh-model-controller is a controller-runtime based Kubernetes operator that orchestrates model serving on the OpenDataHub/RHOAI platform. It watches KServe InferenceService, LLMInferenceService, ServingRuntime, and NIM Account custom resources and dynamically creates the supporting infrastructure each model deployment requires — including OpenShift Routes, Kuadrant AuthPolicies, Istio EnvoyFilters, KEDA TriggerAuthentications, Prometheus ServiceMonitors/PodMonitors, NetworkPolicies, ClusterRoleBindings, and Ray TLS certificates.

The operator includes a comprehensive admission webhook system that mutates Pods (Ray TLS injection), InferenceServices, and LLMInferenceServices at admission time. The webhooks handle ConnectionsAPI credential injection (S3/URI/OCI), HardwareProfile resource and scheduling injection (including Kueue queue assignment), and InferenceGraph cross-namespace validation. It also validates NIM Account singleton constraints.

A companion API server (`model-serving-api`) provides a REST API for Gateway discovery, enabling the RHOAI dashboard to enumerate available inference gateways and serve sample LLMInferenceService configurations. The controller also manages a library of ServingRuntime templates (vLLM, OVMS, MLServer, Caikit, AutoGluon) across multiple accelerator variants (CUDA, ROCm, Gaudi, Spyre, CPU) with fast-track channels for rapid runtime updates.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-service AuthPolicy (LLMInferenceService), per-namespace RBAC for gateway discovery | Kuadrant/Authorino, Kubernetes RBAC | InferenceService Routes have no per-tenant auth — rely on OpenShift Route TLS only |
| Data storage | Per-namespace storage-config Secret aggregated from labeled data connection Secrets | Kubernetes namespace isolation | storage-config Secret aggregates ALL labeled secrets in namespace — no per-model isolation within a namespace |
| Network traffic | Dynamic NetworkPolicy creation per InferenceService | Kubernetes NetworkPolicy | NetworkPolicies are created per-ISVC but scope is per-namespace |
| Compute & resources | HardwareProfile injection sets resource requests/limits and Kueue queue labels | Kubernetes scheduler, Kueue | No ResourceQuota enforcement by controller — depends on cluster admin |
| Configuration & secrets | Per-namespace NIM Account (singleton per namespace), per-namespace Secrets | Kubernetes namespace isolation | NIM Account singleton enforced by webhook |
| API scoping | Controller watches cluster-wide but operates on namespace-scoped CRs | Kubernetes CRD scope | ClusterRoleBindings are created cross-namespace (for auth delegation) |

## Architectural Analysis

The odh-model-controller is a multi-faceted operator that serves as the bridge between KServe's model serving primitives and the RHOAI platform's security, monitoring, and networking infrastructure. Its design follows a reconciler-per-concern pattern: the InferenceServiceReconciler delegates to sub-reconcilers (Route, ClusterRoleBinding, MetricsService, MetricsServiceMonitor, MetricsDashboard, KEDA), each of which uses a delta processor (`internal/controller/processors/deltaProcessor.go`) to compute minimal resource changes. This pattern ensures that infrastructure updates are idempotent and that user customizations (annotations, labels) are preserved through merge semantics.

The webhook system is architecturally significant because it handles two cross-cutting concerns — ConnectionsAPI credential injection and HardwareProfile scheduling — that must be resolved at admission time before the resource reaches the KServe controller. The shared defaulter pattern (`LLMInferenceServiceCustomDefaulter` serving both v1alpha1 and v1alpha2) demonstrates version-bridging within a single webhook, with field pointers abstracting API version differences. The HardwareProfile injection (`internal/webhook/serving/hardwareprofile/injector.go`) has sophisticated merge/set/remove semantics: initial assignment merges with user-provided scheduling (preserving user tolerations, warning on nodeSelector conflicts), profile switches do a full clear-and-reapply, and removal surgically strips only the profile's contributions by matching exact key values.

The LLM inference stack introduces a second ingress path through Gateway API and Kuadrant. The `GatewayReconciler` (`internal/controller/serving/llm/gateway_controller.go`) watches Gateway resources and bootstraps auth by creating an EnvoyFilter (for Authorino TLS termination on the Gateway's Envoy proxy) and a gateway-level AuthPolicy. Individual LLMInferenceServices get per-HTTPRoute AuthPolicies via the `KserveAuthPolicyReconciler`. This two-layer auth model (Gateway-level filter + per-route policy) differs from the InferenceService path which uses simple OpenShift Routes with optional auth-delegation ClusterRoleBindings. The `MaaSRBACCleanupRunner` provides migration hygiene, deleting legacy Role/RoleBinding resources from the 3.3-era MaaS implementation.

The NIM Account controller (`internal/controller/nim/account_controller.go`) is a self-contained subsystem with its own handler chain pattern (`internal/controller/nim/handlers/`). Each handler (ValidationHandler → ConfigMapHandler → PullSecretHandler → TemplateHandler) runs sequentially, producing a `HandleResponse` that feeds status updates. The controller supports air-gapped mode by checking an annotation on the Account resource, bypassing NVIDIA API calls when set. The webhook enforces a singleton constraint (one Account per namespace), simplifying the handler logic which can assume a single Account context.

The model-serving-api server is deliberately minimal — it exposes only two functional endpoints (`/api/v1/gateways` and `/api/v1/samples/llm-d`) with a clean middleware chain (Recovery → SecurityHeaders → Logging → OpenTelemetry). Its Gateway discovery logic (`server/gateway/discovery.go`) performs a two-phase check: first a SelfSubjectAccessReview to verify the caller can create LLMInferenceServices in the target namespace, then a Gateway list filtered by listener AllowedRoutes configuration. This design delegates authorization to Kubernetes RBAC rather than implementing custom access control. The server's TLS configuration (`server/common/certreloader.go`) is explicitly FIPS-compliant with restricted cipher suites (ECDHE+AES-GCM only) and hot-reloads certificates via fsnotify, supporting Kubernetes Secret volume mount rotations.
