## Purpose

**Short**: Kubernetes controller that extends KServe model serving with platform-specific lifecycle management, admission control, networking, auth integration, and a model-serving API server for Red Hat OpenShift AI.

**Detailed**: odh-model-controller is the control-plane glue between KServe's model inference primitives and the RHOAI platform. It watches KServe InferenceService, InferenceGraph, LLMInferenceService, and ServingRuntime custom resources and reconciles the surrounding infrastructure that KServe does not manage: OpenShift Routes, NetworkPolicies, ServiceAccounts, RBAC RoleBindings, Prometheus ServiceMonitors/PodMonitors, KEDA TriggerAuthentications for autoscaling, Kuadrant AuthPolicies for authentication, and Istio EnvoyFilters for traffic management. The controller also manages NVIDIA NIM Account resources for GPU marketplace integration and ships 27 ClusterServingRuntime definitions spanning vLLM (CUDA, ROCm, Gaudi, CPU, Spyre across x86, s390x, ppc64le), OpenVINO Model Server, and MLServer.

A companion deployment, `model-serving-api`, exposes a TLS-secured REST API for gateway discovery and sample generation. This server authenticates requests with Bearer tokens, delegates authorization to Kubernetes SelfSubjectAccessReview, and provides OpenTelemetry-instrumented observability. The controller supports an xKS mode where it runs a minimal webhook-only profile for non-OpenShift Kubernetes distributions, disabling most reconcilers while retaining the LLMInferenceService ConnectionsAPI webhook.

## Architectural Analysis

The odh-model-controller follows a classic multi-reconciler Kubernetes controller pattern built on controller-runtime, with a notable separation into two deployment workloads. The primary `odh-model-controller` deployment runs the controller manager with 10 reconcilers covering the full model-serving lifecycle, while the `model-serving-api` deployment runs a standalone HTTP server for gateway discovery and sample serving. Both binaries are built from the same Go module but have independent entry points (`cmd/main.go` and `server/main.go`).

A key architectural decision is the TLS profile integration with OpenShift's cluster-wide APIServer configuration. At startup, the controller reads the `apiservers.config.openshift.io/cluster` resource, resolves the platform TLS profile (Intermediate/Modern/Old/Custom), and applies matching cipher suites and protocol versions to all TLS listeners. A ProfileWatcher controller monitors for profile changes and initiates graceful shutdown to reload. On non-OpenShift clusters, the controller falls back to Mozilla Intermediate defaults (TLS 1.2+, ECDHE+AES-GCM ciphers). This design ensures the controller always respects the cluster administrator's cryptographic policy without requiring per-component configuration.

The controller's RBAC footprint is broad — the `odh-model-controller-role` ClusterRole spans 15+ API groups and 30+ rules — reflecting its role as the integration layer between multiple platform subsystems. It manages resources across KServe, Gateway API, Kuadrant, KEDA, Istio, Prometheus Operator, and OpenShift-specific APIs. The controller selectively caches secrets and pods using label selectors (`opendatahub.io/managed: true` for secrets, `component: predictor` for pods) to limit memory consumption, and strips ConfigMap data from the informer cache to prevent OOM, falling back to direct API reads for ConfigMap payloads.

The admission webhook layer implements five mutating webhooks and three validating webhooks, covering pods, InferenceServices, InferenceGraphs, LLMInferenceServices, and NIM Accounts. The pod webhook injects model-serving-specific annotations and configuration. The InferenceService webhook applies defaulting and platform-specific mutations. In xKS mode, only the LLMInferenceService webhook is active, providing a minimal ConnectionsAPI+HardwareProfile surface for non-OpenShift deployments.

The Gateway controller integrates with the Gateway API to manage Kuadrant AuthPolicies for LLMInferenceService authentication, creating per-service auth policies backed by Kubernetes TokenReview. It also manages EnvoyFilters and PodMonitors for gateway-level observability. The LLMInferenceService controller orchestrates the full lifecycle of LLM deployments including ServiceAccount, Role, RoleBinding, Secret management, and KEDA TriggerAuthentication for Prometheus-based autoscaling.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | CRD scope: NIM Account is Namespaced; InferenceService, ServingRuntime, LLMInferenceService are Namespaced |
| **Deployment model** | multi-tenant (single controller instance manages all namespaces) | config/default/manager_webhook_patch.yaml:1, cmd/main.go:207 (cluster-scoped cache) |
| **Tenant identifier** | namespace name | Inferred from Namespaced CRD scope and namespace-scoped resource creation |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC Roles/RoleBindings created by InferenceService and LLMInferenceService reconcilers; SelfSubjectAccessReview for gateway API | Kubernetes RBAC + Application | Controller SA has cluster-wide access; tenant isolation depends on per-namespace Roles created dynamically |
| Data storage | Per-namespace Secrets (model credentials, serving runtime configs); no shared database | Kubernetes namespace isolation | None — Secrets are scoped per namespace with label selector filtering |
| Network traffic | Per-namespace NetworkPolicies created by InferenceService reconciler | Kubernetes NetworkPolicy | NetworkPolicy creation is per InferenceService; cluster-level gaps possible if controller fails to create policies |
| Compute & resources | Delegated to KServe and cluster administrator (ResourceQuota, LimitRange) | Kubernetes | Controller does not enforce compute isolation directly |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets with `opendatahub.io/managed: true` label | Kubernetes namespace isolation | Cluster-scoped ClusterServingRuntimes are shared across all namespaces by design |
| API scoping | Controller watches are cluster-wide; reconciliation creates resources in the target namespace of each CR | Kubernetes (namespace-scoped CRs) | Gateway API resources are namespace-scoped but controller has cluster-wide watch |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| ClusterServingRuntimes | Cluster-wide | Shared by design — cluster administrator controls which runtimes are available |
| Gateway (inference gateway) | Per-namespace auth policies | Kuadrant AuthPolicy created per LLMInferenceService with Kubernetes TokenReview |
