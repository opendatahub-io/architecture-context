## Purpose

**Short**: A FIPS-compliant authentication reverse proxy providing OIDC and OpenShift OAuth authentication for ODH/RHOAI applications, designed as a drop-in replacement for oauth-proxy sidecars.

**Detailed**: kube-auth-proxy is a focused authentication proxy derived from oauth2-proxy, streamlined to support only the authentication methods required for enterprise Kubernetes environments. It intercepts HTTP requests to upstream applications and enforces authentication through either external OIDC providers or OpenShift's internal OAuth service.

The proxy supports multiple authentication methods simultaneously: OAuth2/OIDC browser flows, OpenShift OAuth bearer tokens (sha256~ prefixed), JWT bearer tokens, htpasswd basic auth, and Kubernetes service account token validation via the TokenReview API. This last capability allows service accounts to authenticate alongside human users independently of the configured identity provider.

In the RHOAI platform, kube-auth-proxy serves as a sidecar authentication proxy for dashboard components and AI/ML workloads, replacing legacy oauth-proxy deployments. It integrates with Envoy's ext_authz framework for compatibility with the platform's Gateway API-based ingress architecture. The component includes an MLflow-specific auth-denied handler, indicating its role as the authentication layer for MLflow tracking server deployments within the platform.

## Architectural Analysis

kube-auth-proxy follows a middleware-chain architecture built on `gorilla/mux` for routing and `justinas/alice` for composable HTTP middleware. The authentication pipeline processes requests through three ordered chains: a pre-auth chain (logging, health checks, metrics, HTTPS redirect), a session chain (K8s token validation, JWT/OAuth token loading, basic auth, stored session loading), and a headers chain (request/response header injection for upstream services).

The session chain's ordering is architecturally significant: Kubernetes TokenReview validation runs first, enabling service account tokens to be validated before any provider-specific authentication. This design allows automated clients using `oc whoami -t` or mounted service account tokens to authenticate transparently regardless of whether the proxy is configured for OIDC or OpenShift OAuth.

The OpenShift provider implements on-demand OAuth endpoint discovery via `/.well-known/oauth-authorization-server`, protected by double-checked locking (`discoveryMu`). This means the proxy can auto-configure itself when deployed inside an OpenShift cluster with a service account, requiring minimal explicit configuration.

Session storage supports both cookie-based (default) and Redis/Valkey-backed sessions. The Redis store enables session sharing across multiple proxy replicas, which is essential for horizontally-scaled deployments behind a load balancer.

The TLS implementation is configurable with explicit minimum version support (TLS 1.2 or 1.3), cipher suite selection, and elliptic curve preferences. The server supports simultaneous HTTP and HTTPS listeners, with separate address bindings for the application and metrics servers.

A notable RHOAI-specific integration is the `authdeny.MLflowHandler`, which intercepts unauthenticated requests from the MLflow Python SDK (detected via User-Agent header) and returns structured JSON error responses with actionable guidance about OpenShift authentication setup, rather than the default HTML error page.
