## Purpose

**Short**: A FIPS-compliant authentication reverse proxy providing OIDC and OpenShift OAuth authentication for ODH/RHOAI platform components.

**Detailed**: kube-auth-proxy is a focused authentication proxy derived from oauth2-proxy that has been streamlined to support only OIDC and OpenShift OAuth providers. It serves as a drop-in replacement for existing oauth-proxy sidecars in OpenShift AI deployments, providing secure authentication for platform components without requiring configuration changes.

The proxy intercepts incoming HTTP requests and authenticates users through either external OIDC providers (Keycloak, Dex, etc.) or OpenShift's built-in OAuth service. Once authenticated, it forwards requests to upstream backend applications with injected identity headers (X-Forwarded-User, X-Forwarded-Email, X-Forwarded-Groups, X-Forwarded-Access-Token). It supports multiple session storage backends (cookie-based or Redis), Kubernetes service account token validation via TokenReview API, htpasswd basic authentication, and Envoy ext_authz compatibility for integration with the RHOAI 3.x Gateway API ingress stack.

The project is built with FIPS-compliant compilation flags (CGO_ENABLED=1, GOEXPERIMENT=strictfipsruntime) and runs automated check-payload validation in CI to ensure the binary meets Red Hat's FIPS requirements for OpenShift environments.

## Architectural Analysis

kube-auth-proxy is architecturally a stripped-down fork of oauth2-proxy, specifically tailored for the RHOAI/ODH authentication needs. The most significant architectural decision was removing all non-OIDC providers (Google, GitHub, Azure, Facebook, LinkedIn, etc.) and adding the OpenShift OAuth provider from openshift/oauth-proxy. This creates a focused codebase with exactly two authentication flows: generic OIDC and OpenShift OAuth. The provider interface (`Provider`) in `providers/providers.go` defines a clean contract with `GetLoginURL`, `Redeem`, `EnrichSession`, `Authorize`, `ValidateSession`, and `RefreshSession` methods, making the two implementations interchangeable.

The middleware chain architecture is the most complex part of the system. Requests flow through a five-layer pipeline: (1) pre-auth middleware (scope injection, HTTPS redirect, health checks, request logging, metrics), (2) session loading chain (K8s token validation, JWT/OAuth bearer token processing, basic auth, stored session retrieval), (3) authentication decision, (4) route handling (proxy, sign-in, callback, etc.), and (5) response header injection. The session loading chain is particularly noteworthy -- it tries multiple authentication mechanisms in sequence, with each handler gracefully passing to the next on failure. This allows a single proxy instance to simultaneously support cookie-based browser sessions, JWT bearer tokens from API clients, K8s service account tokens from pods, and htpasswd basic auth.

The Envoy ext_authz integration (via the `/oauth2/auth` endpoint) is critical for RHOAI 3.x. In this mode, kube-auth-proxy acts as an external authorization service called by Envoy for every request. The response is a simple 202 (allow) or 401 (deny), with authenticated user identity injected as response headers that Envoy forwards to the upstream application. This pattern replaces the sidecar proxy model used in RHOAI 2.x, where oauth-proxy sat directly in front of each application. The `authdeny` package includes an MLflow-specific handler that returns structured JSON error messages to MLflow Python clients, guiding users to authenticate via `oc login` -- a practical touch that reduces support burden.

The TLS and FIPS compliance architecture is well-considered. The server supports configurable TLS with minimum version (TLS 1.2 default), cipher suite selection, and HTTP/2 via ALPN negotiation. FIPS compliance is enforced at build time through `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime`, ensuring all cryptographic operations use OpenSSL via the Go crypto backend rather than pure-Go implementations. The CI pipeline runs check-payload validation on every PR. One architectural risk is the `InsecureSkipVerify` option, which is exposed as a configurable flag (`--ssl-insecure-skip-verify`) and propagated to TLS configs for upstream connections, Redis connections, and provider API calls. While disabled by default, misconfiguration could bypass TLS verification in production.

Session management supports both client-side (cookie) and server-side (Redis) storage. Cookie sessions use CFB cipher encryption with cookie splitting to handle browser size limits (4KB per cookie). Redis sessions support three topologies: standalone, Sentinel (HA), and Cluster (horizontal scale), with optional TLS and authentication. The file watcher system (`pkg/watcher/watcher.go`) enables hot-reload of htpasswd files and authenticated emails files using fsnotify, with special handling for Kubernetes ConfigMap/Secret symlink rotation patterns. This allows runtime credential updates without proxy restarts.
