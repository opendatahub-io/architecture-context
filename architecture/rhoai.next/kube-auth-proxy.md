## Purpose

**Short**: FIPS-compliant authentication reverse proxy that provides OIDC and OpenShift OAuth authentication for ODH/RHOAI component sidecars, serving as a drop-in replacement for oauth-proxy.

**Detailed**: kube-auth-proxy is a focused authentication proxy derived from oauth2-proxy but streamlined to support only the two authentication methods required for enterprise Kubernetes environments: external OIDC providers and OpenShift's internal OAuth service. It acts as a reverse proxy that intercepts requests to backend applications, handles the full OAuth2/OIDC authentication flow (login, token exchange, session management, token refresh), and forwards authenticated requests upstream with identity headers (X-Forwarded-User, X-Forwarded-Email, X-Forwarded-Access-Token).

The proxy is designed as a drop-in replacement for the existing oauth-proxy sidecars used throughout RHOAI. It adds Kubernetes service account token validation via the TokenReview API, Envoy ext_authz compatibility (returning 202/401 on its `/auth` endpoint for integration with Gateway API ingress), and an MLflow-specific auth denial handler that returns structured JSON error messages to the MLflow Python SDK. All non-OIDC providers (Google, GitHub, Azure, etc.) have been removed to reduce attack surface and simplify maintenance. FIPS compliance is a primary requirement, achieved through `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` build flags and UBI9 base images.

## Purpose

**Short**: kube-auth-proxy is an OAuth2-aware reverse proxy that provides authentication for RHOAI platform services, supporting OpenShift OAuth, OIDC providers, and Kubernetes ServiceAccount token validation via the TokenReview API.

**Detailed**: kube-auth-proxy is a Go-based authentication reverse proxy forked from oauth2-proxy and adapted for the OpenDataHub/RHOAI platform. It sits in front of upstream platform services and enforces authentication before proxying requests. The proxy supports multiple authentication mechanisms: OAuth2 Authorization Code flow with OpenShift OAuth or generic OIDC providers for interactive user sessions, and Kubernetes TokenReview API validation for ServiceAccount bearer tokens enabling programmatic access. Authenticated identity is forwarded to upstream services via HTTP headers (access token, user identity, groups). Session state is managed via encrypted cookies with configurable expiry and refresh intervals, with optional Redis/Valkey backing for distributed session storage. The proxy listens on port 4180 and is typically exposed through an OpenShift Route with TLS edge termination. Configuration is driven entirely by environment variables (OAUTH2_PROXY_* pattern), allowing the deploying operator (rhods-operator) to configure upstream targets and provider settings at deployment time.

## Data Flows

- **Inbound request flow:** External requests arrive via an OpenShift Route with TLS edge termination and are forwarded to the kube-auth-proxy Service (port 80 → targetPort 4180). The proxy intercepts all requests and enforces authentication before proxying to the upstream application.
- **Authentication decision paths:** Two parallel authentication paths are supported. (1) Interactive users: unauthenticated browser requests are redirected to `/oauth2/start`, which initiates an OAuth2 Authorization Code flow with the configured identity provider (OpenShift OAuth or OIDC). The `/oauth2/callback` endpoint completes the exchange, validates the authorization code, and sets an encrypted session cookie. Subsequent requests present this cookie for session validation. (2) Programmatic access: requests bearing a Kubernetes ServiceAccount bearer token in the Authorization header are validated via the `authentication/v1/TokenReview` API against the cluster's API server, bypassing the OAuth2 flow entirely.
- **Upstream proxying:** Authenticated requests are forwarded to the configured upstream service(s) with identity headers injected: access token (`X-Forwarded-Access-Token`), user identity (`X-Forwarded-User`, `X-Forwarded-Email`), and groups (`X-Forwarded-Groups`). The upstream target is runtime-configured via `OAUTH2_PROXY_UPSTREAMS`.
- **Session persistence:** Session state is stored in encrypted cookies by default. When Redis/Valkey is configured, sessions are stored server-side with the cookie containing only a session ticket, enabling distributed session sharing across proxy replicas.
- **Kubernetes API interaction:** The proxy communicates with the Kubernetes API server over TLS (auto-configured via InClusterConfig using the mounted ServiceAccount CA at `/var/run/secrets/kubernetes.io/serviceaccount/ca.crt`) for TokenReview validation and service account token retrieval.

## Architectural Analysis

kube-auth-proxy is a well-structured authentication proxy that follows a middleware-chain architecture using the `justinas/alice` library. The request processing pipeline is organized into three distinct chains: the pre-auth chain (scope injection, HTTPS redirect, health checks, logging, metrics), the session chain (K8s TokenReview → OAuth bearer → JWT bearer → Basic Auth → stored session), and the headers chain (request/response header injection). This layered design allows authentication methods to be composed flexibly -- each session loader in the chain checks for an existing session before attempting its own validation, and passes to the next loader on failure rather than rejecting immediately. This is critical for RHOAI's mixed authentication environment where human users authenticate via OIDC/OAuth while service accounts use Kubernetes tokens.

The OpenShift provider implementation is notable for its lazy-discovery pattern. Rather than requiring explicit `--login-url` and `--redeem-url` configuration, it discovers OAuth endpoints at first use via the Kubernetes API's well-known OAuth authorization server endpoint. This auto-detection extends to service account credentials -- when `--openshift-service-account` is set, the proxy reads the namespace and token from the pod's mounted service account secrets. The discovery logic is guarded by a `sync.Mutex` to prevent concurrent goroutines from racing on the shared provider state, and HTTP clients are cached by CA configuration key using `sync.Map`.

The ext_authz integration via the `/oauth2/auth` endpoint is architecturally significant for RHOAI 3.x. When used with Envoy Gateway, this endpoint receives subrequests with forwarded headers and returns 202 (Accept) with a `GAP-Auth` header containing the user's email on success, or 401/403 on failure. A special CSRF handling mode (`redirectOnCSRFError`) redirects to the sign-in page on callback CSRF failures rather than returning 403 directly, because Envoy returns raw non-200 responses to clients which would show unrendered HTML. The MLflow auth deny handler adds another integration concern -- it detects MLflow Python SDK requests via User-Agent header prefix and returns structured JSON errors with migration guidance, enabling a better developer experience for MLflow users transitioning to RHOAI authentication.

Session storage follows a two-tier design: cookie sessions use AES-CFB encryption with HMAC-SHA256 signing and automatic splitting at the 4KB browser limit, while Redis sessions use a ticket-based approach where each session gets a unique 16-byte ticket ID and 16-byte secret, with the session data encrypted using AES-GCM keyed by the per-session secret. This means even if the Redis store is compromised, individual session payloads cannot be decrypted without the ticket secret stored in the user's cookie. The Redis implementation supports all three Redis topologies (Standalone, Sentinel, Cluster) with optional TLS and custom CA certificates.

The FIPS compliance story is complete at both build-time and application level. Build-time compliance is achieved via `CGO_ENABLED=1` with `GOEXPERIMENT=strictfipsruntime` and `-tags strictfipsruntime`, which forces Go to use OpenSSL for all cryptographic operations. The UBI9-minimal base image provides the OpenSSL libraries. At the application level, all cryptographic operations use standard library primitives (AES-CFB, AES-GCM, HMAC-SHA256, SHA-256) that route through OpenSSL when the strictfipsruntime tag is active. The configurable `InsecureSkipVerify` flag is the only notable FIPS concern -- while it doesn't break FIPS compliance per se, it disables certificate validation which weakens the security posture. No non-FIPS algorithms (MD5, RC4, DES) were found in the codebase.

## Architectural Analysis

kube-auth-proxy is architecturally positioned as the RHOAI platform's authentication gateway, replacing both `oauth-proxy` and `kube-rbac-proxy` as the unified authentication sidecar/proxy for platform services. Its design as a fork of the upstream `oauth2-proxy` project provides a mature OAuth2/OIDC implementation, while the addition of the `TokenReviewValidator` (in `pkg/authentication/k8s/tokenreview.go`) extends it with Kubernetes-native ServiceAccount authentication — a critical capability for programmatic API access in a data science platform where notebooks, pipelines, and model serving components need to authenticate without interactive OAuth2 flows.

The dual authentication model is noteworthy: OAuth2 sessions use long-lived cookies (1h expiry, 30m refresh) with encrypted cookie state, while TokenReview-validated sessions use intentionally short 30-second expiry windows. This asymmetry reflects the different trust models — interactive users maintain persistent sessions, while ServiceAccount tokens are re-validated on every request cycle, ensuring that revoked tokens are detected promptly without relying on cached session state.

The proxy's configuration is entirely environment-variable-driven (`OAUTH2_PROXY_*` pattern), making it suitable for operator-managed deployment where the platform operator (rhods-operator) can inject the correct upstream targets, provider settings, and cookie secrets per component instance. The example deployment manifests show the ServiceAccount-based OpenShift OAuth integration pattern where the SA annotation (`serviceaccounts.openshift.io/oauth-redirectreference`) registers the OAuth redirect URI, enabling auto-discovery of the OAuth client without manual client registration.

The dependency on Redis/Valkey for distributed session storage is optional but architecturally significant — without it, each proxy replica maintains independent cookie-only sessions, which means session affinity is required. With Redis, session tickets enable stateless load balancing across replicas. The `go.mod` shows `redis/go-redis/v9` and `bsm/redislock` dependencies, indicating support for both session storage and distributed locking (likely for session garbage collection or leader election).

A notable gap is that the internal platform dependencies table remains empty because the proxy has no build-time Go module dependencies on other ODH/RHOAI components. Its relationships are purely deployment-time: rhods-operator deploys it, configures its upstream targets (dashboard, model registry, etc.), and manages its lifecycle. These deployment-time dependencies are not observable from the proxy's own source code — they are defined in the deploying operator's controller logic.
