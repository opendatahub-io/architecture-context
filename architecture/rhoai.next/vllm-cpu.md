## Purpose

**Short**: CPU-only build of vLLM, a high-throughput LLM inference and serving engine optimized for running without GPU hardware.

**Detailed**: vllm-cpu is a downstream variant of the vLLM project that produces a CPU-optimized container image for large language model inference and serving. It provides an OpenAI-compatible REST API server, a gRPC server, and a CLI for running LLM inference workloads on CPU-only infrastructure, including x86_64, ppc64le (IBM Power), and s390x (IBM Z) architectures.

The component is deployed as a containerized inference server within the RHOAI platform, typically fronted by KServe's model serving infrastructure. It supports the full vLLM feature set adapted for CPU execution: PagedAttention for efficient KV cache management, continuous batching, prefix caching, structured output generation, multi-LoRA serving, multimodal models (vision, audio, speech-to-text), speculative decoding, and OpenTelemetry-based observability. The V1 engine architecture provides a decoupled frontend/backend design with ZMQ-based IPC, supporting data parallelism and pipeline parallelism even on CPU.

The image is built by Konflux for the `linux/s390x` and `linux/ppc64le` platforms from a single `Dockerfile.konflux.cpu`, using UBI9-minimal as the base image. Architecture-specific build scripts (`build_vllm_ppc64le.sh`, `build_vllm_s390x.sh`) handle platform-dependent compilation of PyTorch, oneDNN, and native extensions.

## Purpose

**Short**: CPU-optimized build of the vLLM high-throughput LLM inference and serving engine, exposing OpenAI-compatible and custom HTTP APIs for text generation, embedding, reranking, and model management.

**Detailed**: vllm-cpu is the CPU-optimized variant of the vLLM inference engine, built specifically for RHOAI deployments where GPU hardware is unavailable or unnecessary. It provides a full OpenAI-compatible API surface (chat completions, completions, embeddings, audio transcription) alongside custom APIs for model lifecycle management (LoRA adapter loading/unloading, weight updates), disaggregated inference coordination (prefill/decode separation with KV cache transfer), and operational endpoints (health checks, profiling, sleep/wake). The server is built on FastAPI and supports optional Bearer Token authentication via the `VLLM_API_KEY` environment variable. Model weights and tokenizers are downloaded at startup from HuggingFace Hub (or optionally ModelScope), making external network access a deployment consideration. The CLI entrypoint (`vllm`) drives both the serving and offline inference modes.

_Python on UBI9 inherits FIPS-compliant OpenSSL from the base image. The Python ssl module delegates to system OpenSSL, so TLS operations use FIPS-validated crypto when the host is in FIPS mode. blake3 is not FIPS-validated but is used for content hashing (cache keys), not for security-critical operations. The gRPC server uses insecure_port binding (no TLS); in production, TLS is typically terminated at the ingress layer (KServe/Envoy)._

## Data Flows

- **Model loading:** At startup, the vLLM engine downloads model weights and tokenizer files from HuggingFace Hub (default) or ModelScope (when `VLLM_USE_MODELSCOPE=true`). This is an outbound HTTPS connection to external model registries, authenticated via `HF_TOKEN` or `MODELSCOPE_API_TOKEN` environment variables respectively. Downloaded artifacts are cached locally for subsequent restarts.
- **Inference request flow:** Clients send HTTP requests to the vLLM API server (FastAPI). The server validates optional Bearer Token authentication (when `VLLM_API_KEY` is configured), then routes to the appropriate handler — OpenAI-compatible endpoints (`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`) or custom endpoints (`/generate`, `/tokenize`, `/score`). Streaming responses use Server-Sent Events (SSE). The `/v1/realtime` endpoint uses WebSocket for bidirectional communication.
- **Disaggregated inference (optional):** vLLM supports a prefill/decode disaggregation mode where a proxy server coordinates between separate prefill and decode vLLM instances. The proxy sends the prompt to the prefill service (port 8100 default), which computes KV caches and transfers them via a dedicated KV transfer channel (ports 14579/14580), then streams the decode response from the decode service (port 8200 default). Request correlation uses a compound request ID encoding both KV socket addresses.
- **Security context:** Authentication is optional Bearer Token (API Key) on all endpoints. 11 environment variable secrets are referenced, including API keys for external services (OPENAI_API_KEY, VLLM_API_KEY), model registry tokens (MODELSCOPE_API_TOKEN, GH_TOKEN), and S3 credentials (S3_SECRET_ACCESS_KEY).

## Architectural Analysis

The vllm-cpu repository is a downstream fork of the upstream vllm project, carrying Red Hat-specific patches for CPU-optimized inference on UBI9. The architecture preserves the full upstream vLLM V1 engine while adapting it for CPU-only execution across three architectures: x86_64, ppc64le, and s390x. This multi-architecture support is notable -- each architecture has its own build script (`build_vllm_ppc64le.sh`, `build_vllm_s390x.sh`) that compiles platform-specific dependencies like oneDNN, numactl, and OpenBLAS from source where pre-built packages are unavailable.

The V1 engine architecture introduces a significant decoupling between the frontend API server and the backend engine core. The frontend (FastAPI/Uvicorn) handles HTTP request parsing, authentication, and response streaming, while the engine core runs in a separate process communicating via ZMQ sockets with msgspec serialization. This design enables the engine to maintain high throughput through continuous batching and PagedAttention-based KV cache management without being bottlenecked by HTTP I/O. For CPU deployment, the UniProcExecutor is typically used (single-process, no GPU parallelism), but the architecture supports multiprocess and Ray backends for multi-socket NUMA systems.

A notable architectural pattern is the platform abstraction layer (`vllm/platforms/`). The `CpuPlatform` class implements CPU-specific behavior including NUMA-aware memory allocation, architecture-specific dtype support (e.g., PowerPC supports only bf16/fp32, while x86_64 supports bf16/fp16/fp32), and CPU attention backend enforcement. The platform layer also handles the exclusion of certain features on specific architectures -- OpenTelemetry is disabled on s390x due to runtime segfaults (AIPCC-13600), and numba is excluded on s390x.

The FIPS and security posture has been actively maintained in the downstream patches. Several recent commits specifically address FIPS compliance: removing statically linked patchelf from the s390x runtime image, uninstalling maturin after outlines-core build to avoid FIPS violations from static Rust binaries. The gRPC server currently uses `insecure_port` binding (no TLS), which is acceptable in the RHOAI deployment model where TLS termination occurs at the platform ingress layer (Gateway API / Envoy), but this should be documented as a deployment assumption.

The Rust frontend (`rust/`) is an emerging architectural component -- a workspace of 12 crates providing high-performance tokenization, chat template rendering, tool call parsing, and reasoning parsing via PyO3 Python bindings. This represents a significant performance optimization over pure Python implementations for these latency-sensitive operations. The Rust code has its own gRPC proto definition (`rust/proto/vllm_grpc.proto`) defining a `Generate` service with unary and streaming RPCs, separate from the Python gRPC server's `VllmEngine` service. The Rust workspace is compiled into Python extension modules (`.so` files) during the build process.

Build hermeticity is a significant gap. The Tekton pipeline explicitly sets `hermetic: false`, and Python dependencies use version ranges rather than lockfiles. The Rust workspace has `Cargo.lock` for deterministic Rust builds, but the Python ecosystem lacks equivalent locking. The component also does not use AIPCC base images, instead building on raw UBI9-minimal with manual package installation. Migration to AIPCC base images would provide the RHEL AI Python Package Index for supply chain security and standardized accelerator runtime setup.

## Architectural Analysis

vllm-cpu is a CPU-only build of the vLLM inference engine that provides the same OpenAI-compatible API surface as its GPU counterparts but targets deployments where GPU acceleration is unavailable. The component exposes 59 HTTP endpoints spanning multiple API families: OpenAI-compatible chat/completions/embeddings, Anthropic-style messages, SageMaker inference protocol (`/invocations`, `/ping`), pooling operations (embed, rerank, score, classify), and operational management (profiling, sleep/wake, LoRA adapter hot-loading, weight updates).

The authentication model is intentionally simple — a single optional API key (`VLLM_API_KEY`) protects all endpoints uniformly via Bearer Token middleware. There is no per-endpoint or role-based access control within the vLLM server itself; in RHOAI deployments, fine-grained auth is typically enforced by the platform's ingress layer (kube-rbac-proxy sidecar or Gateway API HTTPRoute policies) rather than the application.

The disaggregated inference architecture (`benchmarks/disagg_benchmarks/disagg_prefill_proxy_server.py`) demonstrates a deployment pattern where the prefill and decode stages of LLM inference are split across separate vLLM instances. A lightweight Quart-based proxy coordinates the two stages, routing the initial prompt to the prefill service and streaming the generated tokens from the decode service. KV cache tensors are transferred directly between instances via a custom protocol on dedicated ports (14579/14580 by default), bypassing the proxy for the heavy data path. This architecture enables independent scaling of the compute-intensive prefill stage versus the memory-bandwidth-bound decode stage.

The external dependency on HuggingFace Hub (or ModelScope) for model downloads at startup means the component requires outbound HTTPS connectivity unless models are pre-cached in a persistent volume. This has implications for air-gapped deployments where model artifacts must be pre-staged.

Analyzer coverage is partial for manifests (Helm chart templates in `examples/deployment/chart-helm/` are templated YAML), platform semantics, and Python dynamic behavior (dynamic route composition, dependency injection, and call graphs are not resolved by static analysis). The 59 HTTP endpoints were extracted from literal FastAPI route decorators across the `vllm/entrypoints/` directory tree.
