## Purpose

**Short**: CPU-optimized build of vLLM providing high-throughput, memory-efficient LLM inference and serving with OpenAI-compatible, Anthropic Messages, and gRPC APIs.

**Detailed**: vllm-cpu is a Red Hat downstream fork of the vLLM project, specifically configured for CPU-only inference workloads. It provides an OpenAI-compatible HTTP API server built on FastAPI/Uvicorn that serves large language models without requiring GPU hardware. The server supports a broad API surface including chat completions, text completions, embeddings, reranking, scoring, classification, speech-to-text transcription, and the OpenAI Responses API, as well as an Anthropic Messages-compatible endpoint and an optional gRPC transport.

The component is designed to run as a containerized inference service within the RHOAI platform, deployed as a KServe/ModelMesh serving runtime. It supports multiple hardware backends through separate Dockerfile variants (CPU, CUDA/GPU, ROCm, HPU/Gaudi, TPU, ppc64le, s390x), though this specific component (`vllm-cpu`) focuses on the CPU build path. The Konflux CI pipeline produces the `odh-vllm-cpu-rhel9` container image from `Dockerfile.konflux.cpu` using a UBI 9 minimal base with PQC (post-quantum cryptography) support.

vLLM's core architecture centers on PagedAttention for efficient KV-cache management, continuous batching for high throughput, and a plugin-based system for model loading, LoRA adapters, and structured output generation. The serving layer uses a modular router pattern where API endpoint groups (OpenAI, Anthropic, pooling, disaggregated serving, etc.) are registered as FastAPI sub-applications.

## Architectural Analysis

The vllm-cpu repository is architecturally a monolithic inference server with a modular API surface. The codebase is organized around a central engine (`AsyncLLM` / `EngineClient`) that handles model loading, batching, and inference scheduling, while the entrypoints layer provides multiple protocol facades over this engine.

The API surface is notably broad — 47 HTTP endpoints spanning six distinct API families: OpenAI-compatible (completions, chat, models, responses), Anthropic Messages, pooling operations (embed, score, rerank, classify), disaggregated serving, SageMaker compatibility, and infrastructure/observability endpoints. This breadth reflects vLLM's ambition to be a universal inference server but creates a large authentication surface. The `AuthenticationMiddleware` only guards paths under `/v1`, `/v2`, and `/inference` prefixes, intentionally leaving health, load, and version endpoints unauthenticated — a reasonable design for Kubernetes probes but one that exposes operational metadata.

The SSL/TLS story is well-considered: the server accepts `--ssl-keyfile`, `--ssl-certfile`, and `--ssl-ca-certs` arguments passed through to Uvicorn, and includes an `SSLCertRefresher` that uses file-watching (`watchfiles`) to hot-reload certificates without restart. This is important for OpenShift environments where cert-manager rotates certificates on-disk. However, TLS is entirely opt-in; the default deployment listens on plain HTTP port 8000.

The gRPC server (`vllm.entrypoints.grpc_server`) is a separate entry point using `grpc.aio` with `add_insecure_port` — it does not configure TLS. It exposes a `VllmEngine` service plus standard gRPC health checking and reflection. This is a gap for production deployments requiring encrypted transport on all channels.

The disaggregated serving support (`vllm/entrypoints/serve/disagg/`) and data-parallel supervisor (`dp_supervisor.py`) indicate the architecture is evolving toward distributed inference topologies where prefill and decode phases can run on separate processes/nodes. The elastic expert-parallelism endpoints (`/scale_elastic_ep`, `/is_scaling_elastic_ep`) suggest support for dynamic scaling of Mixture-of-Experts workloads.

The build pipeline uses a multi-stage Dockerfile with architecture-specific build scripts (`build_vllm_*.sh`) and `uv` for Python dependency management. The Konflux Dockerfile does not use AIPCC base images — it builds directly from `registry.redhat.io/ubi9/ubi-minimal-pqc`, which is a supply-chain gap relative to RHOAI's standard for Python-based product containers.
