## Purpose

**Short**: CPU-only build of vLLM, a high-throughput LLM inference and serving engine optimized for running without GPU hardware.

**Detailed**: vllm-cpu is a downstream variant of the vLLM project that produces a CPU-optimized container image for large language model inference and serving. It provides an OpenAI-compatible REST API server, a gRPC server, and a CLI for running LLM inference workloads on CPU-only infrastructure, including x86_64, ppc64le (IBM Power), and s390x (IBM Z) architectures.

The component is deployed as a containerized inference server within the RHOAI platform, typically fronted by KServe's model serving infrastructure. It supports the full vLLM feature set adapted for CPU execution: PagedAttention for efficient KV cache management, continuous batching, prefix caching, structured output generation, multi-LoRA serving, multimodal models (vision, audio, speech-to-text), speculative decoding, and OpenTelemetry-based observability. The V1 engine architecture provides a decoupled frontend/backend design with ZMQ-based IPC, supporting data parallelism and pipeline parallelism even on CPU.

The image is built by Konflux for the `linux/s390x` and `linux/ppc64le` platforms from a single `Dockerfile.konflux.cpu`, using UBI9-minimal as the base image. Architecture-specific build scripts (`build_vllm_ppc64le.sh`, `build_vllm_s390x.sh`) handle platform-dependent compilation of PyTorch, oneDNN, and native extensions.

## Architectural Analysis

The vllm-cpu repository is a downstream fork of the upstream vllm project, carrying Red Hat-specific patches for CPU-optimized inference on UBI9. The architecture preserves the full upstream vLLM V1 engine while adapting it for CPU-only execution across three architectures: x86_64, ppc64le, and s390x. This multi-architecture support is notable -- each architecture has its own build script (`build_vllm_ppc64le.sh`, `build_vllm_s390x.sh`) that compiles platform-specific dependencies like oneDNN, numactl, and OpenBLAS from source where pre-built packages are unavailable.

The V1 engine architecture introduces a significant decoupling between the frontend API server and the backend engine core. The frontend (FastAPI/Uvicorn) handles HTTP request parsing, authentication, and response streaming, while the engine core runs in a separate process communicating via ZMQ sockets with msgspec serialization. This design enables the engine to maintain high throughput through continuous batching and PagedAttention-based KV cache management without being bottlenecked by HTTP I/O. For CPU deployment, the UniProcExecutor is typically used (single-process, no GPU parallelism), but the architecture supports multiprocess and Ray backends for multi-socket NUMA systems.

A notable architectural pattern is the platform abstraction layer (`vllm/platforms/`). The `CpuPlatform` class implements CPU-specific behavior including NUMA-aware memory allocation, architecture-specific dtype support (e.g., PowerPC supports only bf16/fp32, while x86_64 supports bf16/fp16/fp32), and CPU attention backend enforcement. The platform layer also handles the exclusion of certain features on specific architectures -- OpenTelemetry is disabled on s390x due to runtime segfaults (AIPCC-13600), and numba is excluded on s390x.

The FIPS and security posture has been actively maintained in the downstream patches. Several recent commits specifically address FIPS compliance: removing statically linked patchelf from the s390x runtime image, uninstalling maturin after outlines-core build to avoid FIPS violations from static Rust binaries. The gRPC server currently uses `insecure_port` binding (no TLS), which is acceptable in the RHOAI deployment model where TLS termination occurs at the platform ingress layer (Gateway API / Envoy), but this should be documented as a deployment assumption.

The Rust frontend (`rust/`) is an emerging architectural component -- a workspace of 12 crates providing high-performance tokenization, chat template rendering, tool call parsing, and reasoning parsing via PyO3 Python bindings. This represents a significant performance optimization over pure Python implementations for these latency-sensitive operations. The Rust code has its own gRPC proto definition (`rust/proto/vllm_grpc.proto`) defining a `Generate` service with unary and streaming RPCs, separate from the Python gRPC server's `VllmEngine` service. The Rust workspace is compiled into Python extension modules (`.so` files) during the build process.

Build hermeticity is a significant gap. The Tekton pipeline explicitly sets `hermetic: false`, and Python dependencies use version ranges rather than lockfiles. The Rust workspace has `Cargo.lock` for deterministic Rust builds, but the Python ecosystem lacks equivalent locking. The component also does not use AIPCC base images, instead building on raw UBI9-minimal with manual package installation. Migration to AIPCC base images would provide the RHEL AI Python Package Index for supply chain security and standardized accelerator runtime setup.
