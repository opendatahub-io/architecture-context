## Purpose

**Short**: CPU-optimized build of vLLM, a high-throughput inference and serving engine for large language models, providing OpenAI-compatible REST and gRPC APIs.

**Detailed**: vllm-cpu is the Red Hat downstream distribution of the vLLM project, specifically built and optimized for CPU-only inference without requiring GPU hardware. It serves as the inference runtime for deploying LLMs on CPU nodes in Red Hat OpenShift AI (RHOAI), supporting multiple CPU architectures including x86_64 (with AMD Zen optimizations), ppc64le (IBM POWER), and s390x (IBM Z).

The component implements an OpenAI-compatible HTTP API server (FastAPI/Uvicorn) and an alternative gRPC server, both backed by the vLLM async inference engine. The engine supports continuous batching, prefix caching, chunked prefill, speculative decoding, structured output generation (JSON schema, regex, grammar), LoRA adapter serving, multimodal inputs, and distributed tensor/pipeline/data parallelism. A Rust-based server component provides high-performance tokenization, tool parsing, and chat rendering via PyO3 bindings.

The image is built via Konflux pipelines for s390x and ppc64le architectures, with architecture-specific build scripts that compile LLVM, OpenBLAS, and numerical libraries from source. The container runs as a non-root user (UID 2000) and is optimized with tcmalloc memory allocation and OpenMP thread tuning for CPU workloads.

## Architectural Analysis

**Multi-Language Architecture**: vllm-cpu is an unusually complex component with a three-language build system — Python for the API layer and engine orchestration, Rust for high-performance tokenization and parsing (13 crates in a Cargo workspace producing 7 PyO3 extension modules), and C++ for CPU-optimized compute kernels (AVX-512, AVX2, BF16 ISA variants). This multi-language approach maximizes performance for each concern but creates significant build complexity, especially across CPU architectures.

**Engine Architecture (V1)**: The inference engine follows a clean pipeline architecture — InputProcessor → Scheduler → Executor → OutputProcessor — with configuration flowing from the composite `VllmConfig` object (20+ sub-configs covering model, cache, scheduler, parallelism, compilation, quantization, LoRA, multimodal, and observability). The engine supports continuous batching with chunked prefill, prefix caching for shared prompt prefixes, and speculative decoding. Inter-process communication between the engine core and workers uses ZeroMQ with MessagePack serialization, providing a language-agnostic IPC mechanism.

**CPU-Specific Optimizations**: The CPU build path includes significant platform-specific optimizations: AMD Zen CPUs get a dedicated `ZenCpuPlatform` with zentorch weight prepacking and AVX-512 acceleration; x86_64 builds auto-detect ISA capabilities (AVX2, AVX-512, BF16) and dispatch to architecture-specific kernel variants; tcmalloc is bundled and LD_PRELOAD'd for memory allocation performance; OpenMP thread binding is tunable via `VLLM_CPU_OMP_THREADS_BIND`. The s390x build compiles LLVM 15 from source due to big-endian architecture requirements, while ppc64le uses POWER9-optimized OpenBLAS with custom DevPI/IBM package indexes.

**Non-Hermetic Build Pipeline**: The Tekton pipelines explicitly set `hermetic: false`, meaning Konflux builds pull Python packages, Rust crates, and system libraries from external sources at build time. This is architecturally significant — while Python dependencies are version-pinned and Rust has Cargo.lock, there is no RPM lock file or cachi2/Hermeto prefetch integration. For the s390x and ppc64le architectures, many dependencies (LLVM, OpenBLAS, numba, llvmlite, OpenCV) are compiled from source in the builder stage, making full hermeticity extremely challenging. This represents a supply chain risk that should be tracked.

**Dual-Protocol Serving**: The component supports both HTTP (OpenAI-compatible REST API via FastAPI/Uvicorn on port 8000) and gRPC (via smg-grpc-servicer on port 50051), with the gRPC path requiring an optional dependency. The HTTP server includes comprehensive OpenAI API compatibility (chat completions, text completions, responses, models, embeddings), plus RHOAI-specific endpoints for SageMaker integration, disaggregated inference, and development/debugging. TLS is configurable with automatic certificate refresh support via watchfiles, though the gRPC server currently only supports insecure ports.
