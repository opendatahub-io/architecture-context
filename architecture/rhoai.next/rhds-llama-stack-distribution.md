## Purpose

**Short**: Builds and distributes a pre-configured Llama Stack server container image for Red Hat OpenShift AI, packaging the Llama Stack framework with RHOAI-specific providers, inference backends, vector stores, and evaluation tooling.

**Detailed**: rhds-llama-stack-distribution is a container image build repository that produces a deployable Llama Stack server for RHOAI. The Llama Stack framework (from the opendatahub-io fork at version v0.5.0+rhai0) provides a unified API server exposing multiple AI/ML capabilities: inference (via remote backends like vLLM, AWS Bedrock, Azure, Vertex AI, WatsonX, and OpenAI), vector I/O (Milvus, FAISS, pgvector, Qdrant), safety evaluation (TrustyAI FMS), LLM evaluation (TrustyAI LMEval, RAGAS, Garak), agent orchestration, batch processing, dataset I/O, scoring, file storage, and tool runtime (Brave Search, Tavily, MCP, RAG).

The repository does not contain the Llama Stack server source code itself. Instead, it maintains a distribution configuration (`distribution/config.yaml`) that declares which Llama Stack APIs and provider implementations to enable, a build script (`distribution/build.py`) that auto-generates a `Containerfile` with all required Python dependencies, and an entrypoint script with optional OpenTelemetry instrumentation. For Konflux (downstream RHOAI) builds, a separate `Dockerfile.konflux` uses an AIPCC CPU base image and installs pre-built Python wheels from a secure Konflux wheel release, rather than pulling packages from public PyPI. The resulting container listens on port 8321/TCP and runs the `llama stack run` command against the bundled configuration. Providers are conditionally enabled via environment variables, allowing the same image to serve different deployment scenarios. The image also bundles a pre-downloaded embedding model (`ibm-granite/granite-embedding-125m-english`) for inline sentence-transformer inference.

## Architectural Analysis

The rhds-llama-stack-distribution repository represents a "distribution-only" pattern: it contains no Llama Stack application source code, but instead defines a curated configuration, dependency set, and build pipeline that produces a deployable container image. The actual Llama Stack server code lives in the opendatahub-io/llama-stack fork, and is installed as a Python package during the container build. This separation allows the distribution to pin specific versions, add RHOAI-specific providers (TrustyAI, Garak), and control the build pipeline independently from upstream development.

The provider architecture is notably flexible. The `config.yaml` uses Llama Stack's conditional provider activation pattern (`${env.VAR:+provider-id}`) where a provider is only instantiated if the corresponding environment variable is set and non-empty. This means a single container image supports wildly different deployment topologies: a minimal deployment with just vLLM inference and Milvus, or a full deployment with cloud inference backends, remote vector stores, Kubeflow-based evaluation pipelines, and external search tools. The trade-off is that the image bundles all dependencies for all providers (PyTorch, milvus-lite, Google Cloud SDK, boto3, etc.), resulting in a large image even when most providers are disabled at runtime.

The dual-build architecture is significant from a security perspective. The upstream community build (`distribution/Containerfile`) pulls packages directly from public PyPI and the PyTorch CPU index, which is appropriate for development and open-source use. The Konflux build (`Dockerfile.konflux`) instead installs from pre-built, audited wheel releases via `install-wheel-release.sh`, using a GitLab PAT for authentication. This Konflux path integrates with the AIPCC base image toolchain (fromager RPM checks, self-tests, library scans) to produce images that meet Red Hat's product security requirements. However, the library scan (`scanlibs.py`) is currently disabled due to a milvus-lite build issue (AIPCC-3688), which represents a known gap in the build validation pipeline.

The storage architecture has been fully consolidated on PostgreSQL. The configuration uses `kv_postgres` for key-value storage and `sql_postgres` for structured data, with a single PostgreSQL instance serving as the backend for all state: metadata registry, inference logging, agent session persistence, file metadata, and conversation history. This simplifies deployment (one database dependency) but creates a single point of failure. The inline Milvus vector store uses a local SQLite database file, which is not persistent across pod restarts unless backed by a PVC.
