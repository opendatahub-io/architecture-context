## Purpose

**Short**: Praxis is a Rust-based framework for building cloud-native proxy servers, providing HTTP and TCP proxying with a composable filter pipeline, TLS termination, hot-reload, and FIPS 140-3 compliance.

**Detailed**: Praxis is a high-performance proxy server built on Cloudflare's Pingora library (maintained as a fork named "quixotic-plecostomus"). It processes HTTP and TCP traffic through configurable filter pipelines that handle routing, load balancing, rate limiting, security enforcement, payload transformation, and observability. The proxy supports TLS termination with SNI-based certificate selection, mutual TLS (mTLS) with SPIFFE identity, and hot-reload of both configuration and TLS certificates without restart.

Within the RHOAI platform, Praxis serves as the AI-native proxy layer. It includes specialized filters for AI workloads such as guardrails enforcement, policy evaluation via the Praxis Policy Engine (PPE), JSON body field promotion for model routing, and iterative request routing. The proxy's FIPS build, based on Red Hat UBI 9 with the system OpenSSL as its sole cryptographic provider, targets FIPS 140-3 compliance for deployment on FIPS-enabled RHEL hosts.

The architecture follows a strict crate dependency flow (`server -> protocol -> filter -> core -> tls`) with comprehensive lint enforcement, 96%+ test coverage, and a workspace of 5 production crates plus 7 test/tooling crates. Configuration is YAML-based with validation, conditional filter chains, branch pipelines, and dynamic config reload via filesystem watching.

## Architectural Analysis

Praxis is architecturally distinctive in its single-provider TLS design: all cryptography is delegated to the system OpenSSL through a rustls-openssl bridge, with no fallback provider compiled in. The Pingora fork's `custom-provider` feature removes rustls' implicit default, meaning the process fails loudly if no provider is installed rather than silently picking one. This design is purpose-built for FIPS 140-3 where the system `libcrypto.so` on a FIPS-enabled RHEL host is the validated module. The `PRAXIS_REQUIRE_FIPS` environment variable makes FIPS mode a hard startup requirement, checking both the kernel flag (`/proc/sys/crypto/fips_enabled`) and the provider's self-reported FIPS status.

The filter pipeline architecture uses a two-phase design: filter chains are resolved and validated at config load time into an immutable `FilterPipeline`, then swapped atomically via `ArcSwap` on hot-reload. This means in-flight requests see one consistent pipeline generation. Filter factories are registered in a `FilterRegistry` and instantiated from YAML config fragments. The system distinguishes routing (runtime path selection via the `router` filter) from pipelining (config-time filter chain composition), with branch chains adding conditional execution paths within a pipeline.

The FIPS build (`Containerfile.fips`) is architecturally separate from the standard Alpine build (`Containerfile`). It uses Red Hat's UBI 9 base images pinned by digest with signature verification, Red Hat's rust-toolset, and `cargo-auditable` for SBOM embedding. The FIPS feature set excludes the policy engine (whose `ppe` dependency tree carries `aws-lc-rs`, `sha2`, and `hmac`), and a `cargo xtask fips report` validates the binary's dependency graph against a FIPS-denied crate list. The workspace Cargo.toml carefully manages feature edges to prevent non-FIPS crypto from leaking into the FIPS build's graph through transitive dependencies.

Reserved header prefixes (`x-praxis-*`, `x-ext-protocol-*`, `x-ext-agent-*`) provide a client-unspoofable metadata channel: client requests carrying these are rejected with 400, they are stripped before forwarding, and stripped from backend responses. This enables secure body-to-header promotion patterns (e.g., `json_body_field` promoting a model name to `x-praxis-guard-model` for guardrails enforcement) without client bypass risk.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |

| **Deployment model** | Single-tenant (per-instance) | Containerfile, server.rs |

_Praxis is a proxy server without an inherent multi-tenancy model. Tenant isolation is delegated to the deployment topology: separate proxy instances per tenant, or namespace-scoped deployments in Kubernetes. Filter chains and routing rules can be configured per-listener to achieve logical separation, but the proxy itself does not enforce tenant boundaries. IP ACLs, mTLS client cert modes, and the policy engine can enforce access control boundaries at the request level._
