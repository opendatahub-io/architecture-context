## Purpose

**Short**: Kueue is a Kubernetes-native job queueing controller that manages resource quotas and fair scheduling for batch workloads, integrating with multiple job frameworks including Kubernetes Jobs, Kubeflow training operators, Ray, JobSet, and CodeFlare AppWrappers. [source: Dockerfile.rhoai:44, apis/config/v1beta1/configuration_types.go:31, config/rhoai/manager_role_patch.yaml:1]

**Detailed**: Kueue provides cluster-level resource quota management and fair scheduling for batch and AI/ML workloads on Kubernetes. It introduces a hierarchical queueing model using ClusterQueues and LocalQueues, where administrators define resource budgets at the cluster level and users submit workloads through namespace-scoped LocalQueues. The controller intercepts workload submissions via admission webhooks, creates internal Workload objects to track resource requests, and admits or queues them based on available quota and scheduling policies. [source: cmd/kueue/main.go:381, config/components/webhook/service.yaml:1, apis/config/v1beta1/configuration_types.go:31]

Kueue supports a broad set of job frameworks through its generic reconciler pattern: Kubernetes batch/v1 Jobs, Kubeflow training operators (PyTorchJob, TFJob, XGBoostJob, PaddleJob, MPIJob), Ray clusters and jobs, JobSets, LeaderWorkerSets, StatefulSets, Deployments, bare Pods, and CodeFlare AppWrappers. Each framework integration provides mutating and validating admission webhooks that inject queue labels and enforce quota semantics at submission time. Advanced features include MultiKueue for multi-cluster workload distribution, Topology-Aware Scheduling (TAS) for hardware-topology-aware placement, Cohorts for resource sharing between queues, and ProvisioningRequests for cluster autoscaler integration. [source: pkg/controller/jobs/job/job_webhook.go:72, pkg/controller/admissionchecks/multikueue/admissioncheck.go:66, pkg/controller/tas/topology_ungater.go:101]

## Architectural Analysis

Kueue follows a controller-runtime operator pattern centered on a single `kueue-controller-manager` Deployment that runs multiple reconcilers and a built-in scheduler in one process. The manager binary (`/manager`) hosts all controllers, the admission webhook server (port 9443), a Prometheus metrics endpoint (port 8443 with TLS), and health/readiness probes (port 8081). This single-process design keeps operational complexity low but makes the manager a single point of failure for all queue admission decisions. [source: cmd/kueue/main.go:381, config/rhoai/manager_metrics_patch.yaml:1, config/components/webhook/service.yaml:1]

The RHOAI distribution applies targeted patches to the upstream Kueue manifests. Webhook namespace selectors restrict mutating and validating webhooks for Pods and Deployments to namespaces with the `kueue-managed: "true"` label, while Job webhooks exclude OpenShift system namespaces (`kube-system`, `openshift-*`, etc.) to avoid interfering with platform-internal workloads. The manager role is extended with read access to CodeFlare AppWrappers (`workload.codeflare.dev`), enabling the AppWrapper job integration that is relevant to the RHOAI distributed workload stack. [source: config/rhoai/validating_webhook_patch.yaml:1, config/rhoai/mutating_webhook_patch.yaml:1, config/rhoai/manager_role_patch.yaml:1]

The admission webhook architecture is extensive: 17 mutating and 18 validating webhooks cover every supported job framework plus Kueue's own CRDs, all served through the `kueue-webhook-service` ClusterIP Service on port 443 (forwarded to container port 9443 with TLS). Webhooks uniformly use a `Fail` failure policy, meaning API server operations on managed resources will be rejected if the webhook is unavailable. The readiness check at `/readyz` gates on webhook certificate readiness (`certsReady` channel) before advertising the replica as ready, preventing early requests from being rejected during startup. [source: cmd/kueue/main.go:393, config/rhoai/validating_webhook_patch.yaml:1]

The controller watch topology is deep: the WorkloadReconciler alone watches ClusterQueues, LocalQueues, LimitRanges, and RuntimeClasses in addition to its primary Workload resource. The MultiKueue subsystem (ACReconciler, clustersReconciler, wlReconciler) watches AdmissionChecks, MultiKueueClusters, MultiKueueConfigs, Secrets, and Workloads to federate workloads across clusters. Topology-Aware Scheduling adds three more controllers (rfReconciler, topologyReconciler, topologyUngater) that watch Nodes, ResourceFlavors, Topologies, Pods, and Workloads. This dense watch graph means the manager maintains a large informer cache and requires careful RBAC scoping. [source: pkg/controller/core/workload_controller.go:797, pkg/controller/admissionchecks/multikueue/admissioncheck.go:181, pkg/controller/tas/topology_ungater.go:101]

The experimental `kueue-viz` component (under `cmd/experimental/`) provides a WebSocket-based visualization backend using the Gin framework, but it is not part of the RHOAI deployment manifests. Its HTTP endpoints (`/ws/*`) should not be considered production attack surface. [source: cmd/experimental/kueue-viz/backend/handlers/handlers.go:28]
