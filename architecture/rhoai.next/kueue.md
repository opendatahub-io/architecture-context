## Purpose

**Short**: Kueue is a Kubernetes-native job queueing system that manages when workloads should be admitted to start based on available quota, priorities, and fair sharing policies.

**Detailed**: Kueue provides a set of APIs and controllers for job-level resource management on Kubernetes clusters. It operates as a quota and admission control layer between users submitting batch workloads (Jobs, PyTorchJobs, RayJobs, etc.) and the Kubernetes scheduler. Rather than scheduling pods directly, Kueue decides *when* a job should be admitted to start (allowing its pods to be created) and *when* it should stop (suspending or deleting active pods).

The system introduces a hierarchy of resource management primitives: ClusterQueues define resource quotas and borrowing policies at the cluster level, LocalQueues provide namespace-scoped entry points for workload submission, ResourceFlavors map to different hardware profiles (GPU types, node pools), and Cohorts enable resource sharing between ClusterQueues. Kueue supports advanced scheduling features including fair sharing with preemption, topology-aware scheduling for optimizing pod placement on closely-located nodes, partial admission for running jobs with reduced parallelism, and MultiKueue for dispatching workloads across multiple clusters.

In RHOAI, Kueue is deployed as a single-replica controller in the `opendatahub` namespace. The RHOAI configuration disables VisibilityOnDemand and MultiKueue features while enabling LocalQueueMetrics. The controller manages workloads from 14 different job framework integrations including batch/Job, Kubeflow training jobs, Ray jobs, and CodeFlare AppWrappers.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC via separate editor/viewer ClusterRoles per resource type (clusterqueue_editor, localqueue_editor, etc.) | Kubernetes | Users with ClusterQueue editor access can affect all tenants' quota. No built-in per-namespace RBAC scoping for ClusterQueue management. |
| Data storage | Per-namespace Workloads and LocalQueues; ClusterQueues are cluster-scoped shared resources | Kubernetes | ClusterQueues are shared across namespaces -- a misconfigured namespaceSelector could grant unintended access. |
| Network traffic | NetworkPolicy for webhook port (RHOAI config); no per-tenant network isolation | Kubernetes (NetworkPolicy) | Kueue itself doesn't create per-tenant NetworkPolicies. Network isolation of actual workloads is the responsibility of the workload owner or platform. |
| Compute & resources | Quota enforcement via ClusterQueue nominalQuota, borrowingLimit, and lendingLimit per ResourceFlavor | Kueue (application-level) | Quota is enforced at admission time -- once a workload is admitted, actual resource consumption is not monitored by Kueue (delegated to Kubernetes scheduler and kubelet). |
| Configuration & secrets | Controller configuration is cluster-scoped (single ConfigMap). MultiKueueCluster secrets are cluster-scoped. | Kubernetes | Secrets for MultiKueue remote cluster kubeconfigs are readable by the controller SA. No per-tenant secret scoping. |
| API scoping | Workloads and LocalQueues are namespace-scoped. ClusterQueues use namespaceSelector to restrict which namespaces can submit. Watches use field indexes filtered by queue/clusterqueue. | Kubernetes + Kueue | A user with list permissions on Workloads across namespaces can see other tenants' workload details. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| ClusterQueue | Namespace (via namespaceSelector) | Label selector on namespace determines which namespaces can submit workloads to the queue |
| Cohort | ClusterQueue membership | Borrowing/lending limits control cross-queue resource sharing within a cohort |
| Scheduler | None (single instance) | Scheduler processes all ClusterQueues; isolation is through quota allocation, not scheduler partitioning |
| In-memory cache | None (single instance) | All workload and queue state is held in a single cache; no per-tenant partitioning |

## Architectural Analysis

Kueue implements a sophisticated quota management and job scheduling system using a layered architecture of Kubernetes CRDs. The core design separates *resource definition* (ClusterQueues, ResourceFlavors, Cohorts) from *workload submission* (LocalQueues, Workloads) and *admission control* (AdmissionChecks, ProvisioningRequestConfigs). This separation allows cluster administrators to define resource policies independently from the namespaces where workloads are submitted.

The controller architecture uses an event-driven notification pattern with Go channels to propagate state changes across controllers. When a ResourceFlavor or AdmissionCheck changes, the affected controller notifies the ClusterQueue controller via a channel, which then reconciles the ClusterQueue's Active status and triggers re-evaluation of pending workloads. This is more efficient than relying solely on Kubernetes watch events, as it allows the controllers to batch and deduplicate updates. The WorkloadReconciler implements a state machine with well-defined transitions (Pending -> QuotaReserved -> Admitted -> Finished, with Evicted as a side state), and uses an exponential backoff mechanism for requeuing evicted workloads.

The job framework integration is designed for extensibility. The `pkg/controller/jobframework` package provides a generic reconciler and webhook that handle the common logic (Workload creation, suspension management, finalizers, TAS annotation handling), while each job type implements a small interface (`GenericJob`) to provide type-specific behavior. The MultiKueue adapter pattern extends this further -- each job type implements a `MultiKueueAdapter` interface for cross-cluster job synchronization. This keeps the per-integration code minimal (typically ~100 lines per job type) while the framework handles the complexity. The RHOAI deployment disables MultiKueue, so the cross-cluster capabilities are not active.

The RHOAI-specific kustomize overlay makes several notable changes compared to upstream: it deploys into the `opendatahub` namespace rather than `kueue-system`, adds a NetworkPolicy restricting ingress to the webhook port (9443/TCP), includes a ServiceMonitor and PrometheusRule for monitoring integration, adds a dedicated ServiceAccount with a long-lived token for metrics authentication, and disables the VisibilityOnDemand and MultiKueue features via command-line flags. The feature gate configuration (`VisibilityOnDemand=false,LocalQueueMetrics=true,MultiKueue=false`) reflects RHOAI's focus on metrics observability over the on-demand visibility API and cross-cluster features.

One architectural observation is that Kueue's quota enforcement is purely at admission time -- once a workload is admitted and its pods are running, Kueue does not monitor actual resource consumption. If a pod uses more resources than requested (via limits > requests), Kueue's quota accounting won't reflect this. The `WaitForPodsReady` feature adds runtime monitoring of pod readiness with configurable timeouts and recovery windows, but this is about pod health rather than resource consumption accuracy. This design choice keeps Kueue focused on admission control and avoids overlap with kubelet's resource enforcement.
