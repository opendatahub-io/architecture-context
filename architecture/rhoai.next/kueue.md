## Purpose

**Short**: Kueue is a Kubernetes-native job queueing system that manages when workloads should be admitted to run on a cluster based on quotas, priorities, and fair sharing policies.

**Detailed**: Kueue implements a job-level resource management layer for Kubernetes clusters. Rather than allowing workloads to start immediately when submitted, Kueue intercepts job creation through admission webhooks and suspends workloads until cluster resources are available according to administrator-defined quotas and policies. The system introduces a two-tier queue hierarchy: ClusterQueues define cluster-wide resource quotas and borrowing policies, while LocalQueues provide namespace-scoped submission points that reference a ClusterQueue.

Kueue integrates with a broad set of batch and ML workload types through a pluggable framework architecture. The RHOAI distribution enables integrations for Kubernetes Jobs, Kubeflow training operators (PyTorchJob, TFJob, MPIJob, XGBoostJob, PaddleJob), Ray (RayJob, RayCluster), JobSet, and CodeFlare AppWrappers. Each integration registers mutating and validating webhooks that intercept workload creation, inject queue annotations, and enforce admission policies. The controller then creates internal Workload objects that track resource requirements and flow through the scheduling pipeline.

The scheduling engine evaluates pending workloads against ClusterQueue capacity, supports fair sharing across Cohorts (groups of ClusterQueues that can borrow resources from each other), priority-based preemption, and topology-aware scheduling for hardware locality. Advanced features include MultiKueue for federating workloads across multiple clusters and ProvisioningRequest integration with cluster autoscaler for dynamic capacity provisioning.

## Architectural Analysis

Kueue's architecture is centered on a separation between the workload submission plane and the resource admission plane. Users submit native Kubernetes workloads (Jobs, PyTorchJobs, etc.) to namespace-scoped LocalQueues. Admission webhooks intercept these submissions and suspend them by default. The Kueue controller creates a corresponding Workload CR that captures the resource requirements, then the scheduler evaluates Workloads against ClusterQueue quotas. When resources are available, the scheduler admits the Workload by updating its status, which triggers the job framework controller to unsuspend the original workload and allow pods to be created.

The RHOAI distribution makes several notable configuration choices. MultiKueue (multi-cluster federation) and VisibilityOnDemand are explicitly disabled via feature gates, while LocalQueueMetrics is enabled. The webhook configuration applies namespace selectors to exclude OpenShift system namespaces from job interception, preventing Kueue from interfering with platform-critical workloads. A NetworkPolicy restricts ingress to the webhook port (9443), and metrics are exposed via a dedicated service on port 8443 with kube-rbac-proxy-style authentication using TokenReview and SubjectAccessReview.

The RBAC model is extensive — the manager role requires cluster-wide access to 20+ API groups covering all supported workload types. User-facing roles follow a batch-admin/batch-user pattern where admin roles aggregate editor permissions for all resource types, and user roles aggregate viewer permissions plus job submission capabilities. This design allows platform administrators to grant coarse-grained access via a single role binding.

Internal certificate management handles webhook TLS certificates using the open-policy-agent cert-controller library, rotating certificates automatically without requiring cert-manager as a dependency. When internal cert management is disabled, the controller expects externally provisioned certificates at `/etc/kueue/metrics/certs`.
