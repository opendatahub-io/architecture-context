## Purpose

**Short**: Kueue is a Kubernetes-native job queueing system that manages quota and admission control for batch workloads, deciding when jobs should be admitted to start (creating pods) and when they should stop (evicting pods).

**Detailed**: Kueue provides a set of Custom Resource Definitions (CRDs) and controllers that implement job-level resource management for Kubernetes clusters. It operates by creating `Workload` objects that represent the resource requirements of batch jobs, then scheduling those workloads against quotas defined in `ClusterQueue` and `LocalQueue` resources. Users organize resources into `ResourceFlavor` objects that represent different hardware types (e.g., GPU models, CPU architectures) or pricing tiers.

The system supports sophisticated resource sharing through `Cohort` hierarchies, where multiple ClusterQueues can borrow unused resources from each other. Kueue integrates with multiple job frameworks including Kubernetes batch/Job, Kubeflow training operators (PyTorchJob, TFJob, MPIJob, etc.), Ray (RayJob, RayCluster), JobSet, CodeFlare AppWrapper, LeaderWorkerSet, and raw Pods/Deployments/StatefulSets. It also provides advanced features like Topology-Aware Scheduling (TAS) for placement-sensitive workloads, MultiKueue for multi-cluster federation, and integration with Cluster Autoscaler via ProvisioningRequests.

In the RHOAI platform, Kueue serves as the job queueing and resource management layer for AI/ML workloads, ensuring fair resource allocation across teams and projects while respecting cluster capacity constraints.

## Architectural Analysis

Kueue's architecture follows a clean separation of concerns through a layered controller design. The core scheduling loop operates through three primary controllers — ClusterQueue, LocalQueue, and Workload — coordinated by in-memory Cache and Queue Manager singletons. The Cache maintains a real-time view of resource allocation across all ClusterQueues and Cohorts, while the Queue Manager maintains ordered workload queues. The Scheduler, running as a separate goroutine managed by the controller-runtime manager, pulls workloads from the Queue Manager and makes admission decisions against the Cache. This design avoids distributed state and keeps all scheduling decisions local to a single leader replica.

The Job Framework layer (`pkg/controller/jobframework/`) provides a pluggable integration pattern that abstracts the differences between batch job types. Each job type registers callbacks for reconciliation, webhook setup, and workload construction through a central integration registry. The `BaseWebhook` provides common defaulting and validation (queue labels, suspend state management), while job-specific implementations extend it for custom behavior. This architecture makes adding new job types straightforward — implement the `GenericJob` interface and register callbacks — and the framework handles workload lifecycle, admission checks, and pod readiness tracking automatically.

The Admission Check system is a particularly well-designed extension point. Rather than hardcoding validation into the admission flow, Kueue defines `AdmissionCheck` CRDs that external or built-in controllers can satisfy. The Provisioning controller uses this to integrate with Cluster Autoscaler — it creates `ProvisioningRequest` CRs and watches for capacity provisioning outcomes. The MultiKueue controller uses the same mechanism to federate workloads across clusters. Both implement exponential backoff retry with configurable limits, keeping the Workload controller's core logic clean.

The RHOAI overlay makes conservative choices: MultiKueue and VisibilityOnDemand are disabled, but LocalQueueMetrics are enabled. Webhook namespace selectors exclude OpenShift system namespaces from Pod/Deployment/StatefulSet webhooks, preventing interference with platform components. The monitoring stack includes both a ServiceMonitor for metrics collection and PrometheusRules with alerts for pod health (KueuePodDown at critical severity), resource utilization (LowClusterQueueResourceUsage), quota violations (ResourceReservationExceedsQuota), and stale workloads (PendingWorkloadPods). A NetworkPolicy restricts ingress to only the webhook port (9443/TCP).

The Topology-Aware Scheduling (TAS) subsystem adds topology-aware pod placement without modifying the core scheduler. It uses scheduling gates on pods to delay Kubernetes scheduling until Kueue has determined topology domain assignments. The TopologyUngater controller implements two assignment strategies — rank-based (deterministic for distributed training) and greedy (balanced distribution for general workloads) — and patches pods with node selectors corresponding to assigned topology domains. This design leverages standard Kubernetes scheduling gates rather than requiring a custom scheduler.
