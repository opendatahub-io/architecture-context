## Purpose

**Short**: An out-of-tree Llama Stack evaluation provider that integrates the Ragas framework for RAG pipeline quality assessment via inline or Kubeflow-based remote execution.

**Detailed**: llama-stack-provider-ragas implements [Ragas](https://github.com/explodinggradients/ragas) as an external evaluation provider for the [Llama Stack](https://github.com/meta-llama/llama-stack) platform. It exposes RAG evaluation metrics (answer relevancy, context precision, faithfulness, context recall) through Llama Stack's standard eval API, bridging between the Ragas evaluation engine and Llama Stack's built-in inference, embeddings, datasets, and benchmarks APIs.

The component ships two provider variants. The **inline** provider executes Ragas evaluations in-process alongside the Llama Stack server, wrapping the server's own inference and embeddings APIs to satisfy Ragas' LLM and embedding requirements. The **remote** provider offloads evaluation to Kubeflow Pipelines: it compiles a KFP pipeline with two stages (data retrieval from Llama Stack, Ragas evaluation), submits it to a Kubeflow Pipelines server, and stores results in S3. The remote variant enables long-running evaluations on dedicated compute while keeping the Llama Stack server responsive.

The component is a Python package (not a standalone service) that plugs into a Llama Stack distribution at runtime. A Konflux Dockerfile builds a container image used as the KFP component base image for remote execution. The codebase includes a compatibility layer (`compat.py`) that supports both the legacy `llama_stack` and newer `llama_stack_api` package layouts, enabling forward-compatible upgrades.

## Architectural Analysis

This provider follows Llama Stack's plugin architecture with a clean separation between inline and remote execution paths. The inline path is tightly coupled to the Llama Stack server process via direct API object injection (`deps[Api.inference]`, `deps[Api.datasetio]`), while the remote path communicates exclusively through HTTP clients: `kfp.Client` for pipeline submission, `llama-stack-client` for data retrieval within KFP components, and `s3fs`/`pandas` for result storage and retrieval.

A notable architectural choice is the wrapper pattern: both variants bridge Ragas' LangChain-based LLM/embedding interfaces (`BaseRagasLLM`, `BaseRagasEmbeddings`) to Llama Stack's OpenAI-compatible completion and embedding APIs. The inline wrappers use the server's async inference API directly, while the remote wrappers instantiate separate HTTP clients pointing at the Llama Stack server URL. This means the remote variant's KFP pods must have network connectivity to both the Kubeflow Pipelines endpoint and the Llama Stack server.

The base image for KFP components is resolved through a three-tier fallback: environment variable `KUBEFLOW_BASE_IMAGE`, then a Kubernetes ConfigMap (`trustyai-service-operator-config` in `redhat-ods-applications` or `opendatahub` namespaces), then a hardcoded default image. This ties the remote provider to the TrustyAI operator's deployment topology.

Authentication for Kubeflow uses bearer tokens sourced either from explicit configuration (`KUBEFLOW_PIPELINES_TOKEN`) or from the local kubeconfig, with a manual healthz preflight check before client initialization. S3 credentials are injected into KFP pods via Kubernetes secrets. There is no TLS configuration in the application code; all HTTP connections use default transport settings from the underlying libraries.
