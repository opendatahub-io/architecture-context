## Purpose

**Short**: Out-of-tree Llama Stack Eval provider that integrates the Ragas evaluation framework, supporting both in-process (inline) and Kubeflow Pipelines-based (remote) evaluation execution modes.

**Detailed**: llama-stack-provider-ragas implements the Llama Stack `Eval` and `BenchmarksProtocolPrivate` provider interfaces to run Ragas-based LLM evaluation metrics (answer relevancy, context precision, faithfulness, context recall) against datasets registered in Llama Stack. It ships two provider modes: an **inline provider** (`RagasEvaluatorInline`) that executes evaluations in-process within the Llama Stack server by wrapping the Llama Stack Inference and DatasetIO APIs as Ragas-compatible LLM and embedding interfaces, and a **remote provider** (`RagasEvaluatorRemote`) that submits evaluation workloads as Kubeflow Pipeline runs with S3-backed result storage. The remote mode integrates with Data Science Pipelines (Kubeflow Pipelines), Kubernetes Secrets for S3 credentials, and the TrustyAI Service Operator ConfigMap for base image resolution. The provider is registered as type `trustyai_ragas` and is distributed as a standard Python package installable into Llama Stack distributions.

## Data Flows

- **Inline evaluation flow:** Client calls `run_eval` on the Llama Stack server → inline provider fetches dataset rows via DatasetIO API (`iterrows`) → wraps Llama Stack Inference API as Ragas-compatible LLM and embedding interfaces (`LlamaStackInlineLLM`, `LlamaStackInlineEmbeddings`) → calls `ragas.evaluate()` in a background thread → stores result in-memory keyed by job ID → client polls `job_status`/`job_result` to retrieve `EvaluateResponse` with per-metric scores.
- **Remote evaluation flow:** Client calls `run_eval` → remote provider authenticates to Kubeflow Pipelines API (Bearer token from config or kubeconfig) → submits a two-step KFP pipeline (`retrieve_data_from_llama_stack` → `run_ragas_evaluation`) with S3 credentials injected from a Kubernetes Secret → pipeline components call back to Llama Stack server for dataset retrieval and inference → results written to S3 as JSONL → client polls `job_status` which checks KFP run state → on completion, provider fetches results from S3 via pandas and converts to `EvaluateResponse`.

## Architectural Analysis

The provider follows the Llama Stack out-of-tree provider pattern: it implements the `Eval` and `BenchmarksProtocolPrivate` protocol interfaces and declares its API dependencies (`Inference`, `Files`, `Benchmarks`, `DatasetIO`) so the Llama Stack distribution wires them at startup. The provider never starts its own HTTP server—it is loaded as a plugin into the Llama Stack server process, which exposes the Eval API endpoints.

The dual inline/remote architecture addresses two deployment scenarios. The inline provider is simpler: it runs Ragas evaluation synchronously (via `asyncio.to_thread`) within the Llama Stack server process, using wrapper classes (`LlamaStackInlineLLM`, `LlamaStackInlineEmbeddings`) that translate Ragas's synchronous LLM/embedding interfaces into async Llama Stack Inference API calls. This mode is suitable for development and small-scale evaluations but ties up server resources during evaluation. The remote provider offloads evaluation to Kubeflow Pipelines, where each evaluation runs as a two-step pipeline: dataset retrieval from Llama Stack, then Ragas evaluation with results persisted to S3. This mode supports production-scale evaluation with proper resource isolation.

The remote provider's authentication strategy has two tiers: it first checks for an explicit `pipelines_api_token` (stored as a Pydantic `SecretStr`), falling back to extracting a Bearer token from the local kubeconfig (typically from `oc login`). The KFP client initialization includes a manual healthz preflight check because the KFP SDK's built-in health checking is reported as unreliable (see `ragas_remote_eval.py` line 86). S3 credentials are injected into pipeline pods via a Kubernetes Secret reference (`s3_credentials_secret_name`), keeping AWS credentials out of pipeline definitions.

A notable integration point is the TrustyAI Service Operator ConfigMap (`trustyai-service-operator-config`), which the remote provider reads to resolve the base container image for KFP pipeline components. This creates a runtime coupling to the TrustyAI operator's configuration, with candidate namespaces hardcoded to `redhat-ods-applications` and `opendatahub`. The default image falls back to `quay.io/trustyai/llama-stack-provider-ragas:latest` if the ConfigMap is unavailable.

The evaluation metrics are statically mapped in `constants.py` from Ragas metric function objects (`answer_relevancy`, `context_precision`, `faithfulness`, `context_recall`). The metric set is currently fixed at four RAG evaluation metrics with TODOs for additional metrics like `AnswerCorrectness` and `FactualCorrectness`. Both providers validate requested metrics against this static set during benchmark registration.
