## Purpose

**Short**: Kubernetes operator that manages the lifecycle of LLM-D batch gateway deployments, reconciling a single `LLMBatchGateway` custom resource into a full set of Kubernetes resources via Helm chart rendering at runtime.

**Detailed**: The LLM-D Batch Gateway Operator automates the deployment and lifecycle management of the batch inference gateway stack within Red Hat OpenShift AI (RHOAI). When a user creates an `LLMBatchGateway` custom resource, the operator renders the upstream `batch-gateway` Helm chart (and optionally the `async-processor` chart) into concrete Kubernetes resources — Deployments, Services, ConfigMaps, ServiceAccounts, HTTPRoutes, Certificates, and monitoring resources — and applies them via Server-Side Apply.

The batch gateway stack itself consists of four components managed by the operator: an **API server** that accepts batch job submissions via an OpenAI-compatible HTTP API, a **processor** that dispatches individual inference requests to inference gateways (synchronously or asynchronously via Redis message queues), a **garbage collector** that expires old jobs and files, and an optional **async-processor** for queue-based dispatch to inference pools. The operator reads component container images from environment variables (set by the platform operator via `params.env`), ensuring the platform controls which images are deployed rather than the CR author.

The operator implements cross-namespace secret resolution using Gateway API `ReferenceGrant` resources, supports TLS termination via cert-manager integration, creates Gateway API `HTTPRoute` resources for API server exposure, and provides Prometheus monitoring through ServiceMonitor, PodMonitor, and PrometheusRule resources. A dedicated metrics controller ensures the operator's own observability infrastructure (Service, ServiceMonitor, PrometheusRule) is always present.

## Architectural Analysis

The LLM-D Batch Gateway Operator follows a **Helm-as-library** pattern rather than the more common controller-runtime reconcile-from-scratch approach. Instead of imperatively constructing Kubernetes objects in Go code, the operator embeds two upstream Helm charts (`batch-gateway` and `async-processor`) at build time and renders them at reconcile time using the Helm v3 SDK (`engine.Render`). The CRD spec is mapped to Helm values via `specToBatchHelmValues()` and `specToAsyncHelmValues()`, and the rendered objects are applied via Server-Side Apply with force ownership. This design minimizes divergence between the upstream chart (maintained by the batch-gateway team) and the operator's deployment behavior — the operator is essentially a CRD-to-Helm-values translator with lifecycle management (owner references, orphan deletion, status tracking).

The **orphan detection** mechanism is noteworthy: the controller maintains a list of all GVKs the Helm chart can produce (`managedGVKs`) and, after each reconcile, lists all resources of those types in the CR's namespace, filtering by controller owner reference. Any resource owned by the CR but not in the current rendered set is deleted. This ensures that when chart configuration changes remove resources (e.g., disabling monitoring removes ServiceMonitors), those resources are cleaned up. The TODO comment in the code suggests this could be optimized with label-based filtering to reduce API server load.

The **cross-namespace secret resolution** pattern is sophisticated and security-conscious. When `spec.secretRef` points to a Secret in a different namespace, the operator enforces Gateway API `ReferenceGrant` semantics — it lists ReferenceGrants in the target namespace and verifies that one permits `batch.llm-d.ai/LLMBatchGateway` from the CR's namespace to reference the named Secret. If permitted, the Secret is copied into the CR's namespace under a managed name (`{gw-name}-credentials`). The `secretRef` is immutable after the first copy — changing it requires deleting and recreating the CR, which prevents credential-swapping attacks. The operator also watches the source Secret for rotation and re-syncs the copy.

The operator's **dual dispatch mode** (sync vs async) represents a significant architectural flexibility. In sync mode, the processor sends HTTP requests directly to inference gateways. In async mode, an additional async-processor Deployment is created that dequeues requests from Redis sorted sets and dispatches them to inference gateway EPPs (EndpointPickers). The async mode supports sophisticated dispatch gating mechanisms (prometheus-saturation, prometheus-budget, redis-quota) configured per worker pool, enabling fine-grained control over inference throughput. The `specToAsyncHelmValues()` function handles the complex mapping of per-queue configurations, worker pools, and gate parameters.

A **security gap** exists in the TLS configuration: the `InferenceGatewaySpec` type has a CRD-level validation rule that blocks `tlsInsecureSkipVerify` (`rule="!has(self.tlsInsecureSkipVerify) || !self.tlsInsecureSkipVerify"`), enforcing proper TLS verification for sync-mode inference connections. However, the `AsyncTLSSpec` type has an `InsecureSkipVerify` field with no equivalent CRD-level blocking, meaning async-mode TLS connections can bypass certificate verification. This inconsistency should be addressed.
