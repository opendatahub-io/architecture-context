## Purpose

**Short**: Kubernetes operator that manages the lifecycle of LLM-D batch gateway deployments, reconciling a single `LLMBatchGateway` custom resource into the full set of workload resources by rendering embedded Helm charts at runtime.

**Detailed**: The llm-d-batch-gateway-operator is a controller-runtime-based Kubernetes operator that declaratively manages batch inference gateway deployments on the RHOAI platform. Users create an `LLMBatchGateway` custom resource specifying database backends (PostgreSQL, Redis, Valkey), file storage (S3 or PVC), inference gateway endpoints, TLS settings, and monitoring configuration. The operator's reconcile loop translates the CR spec into Helm values, renders embedded Helm charts (batch-gateway and async-processor), and applies the resulting Kubernetes resources via Server-Side Apply with owner references for garbage collection.

The operator deploys up to four sub-components per CR: an API server that accepts OpenAI-compatible batch job submissions, a processor that dispatches inference requests (sync or async mode), a garbage collector for expired jobs and files, and an optional async-processor that dispatches via Redis message queues. It integrates with cert-manager for TLS certificate provisioning, Gateway API for HTTPRoute-based ingress, and Prometheus for monitoring. The operator manages its own metrics Service, ServiceMonitor, and PrometheusRule, and respects the cluster's TLS profile via the OpenShift `config.openshift.io/v1` APIServer resource.

## Architectural Analysis

The llm-d-batch-gateway-operator follows a Helm-rendering operator pattern: rather than templating Kubernetes manifests directly in Go, it embeds two upstream Helm charts (batch-gateway and async-processor) inside the container image and renders them at reconcile time using the Helm v3 SDK. This design decouples the operator's reconciliation logic from the chart's resource definitions, allowing upstream chart changes to propagate without modifying controller code — only the CRD-to-Helm-values mapping function (`specToHelmValues`) needs updating.

A notable architectural decision is the cross-namespace secret synchronization mechanism. When a user references a credentials Secret in a different namespace, the operator verifies a Gateway API `ReferenceGrant` exists in the source namespace, then copies the Secret into the CR's namespace under a managed name. The `secretRef` field is treated as immutable after the first copy to prevent credential rotation confusion — users must delete and recreate the CR to change the Secret reference. This is enforced at the application level through annotation checking rather than through a validating webhook, meaning it can be bypassed via direct API access.

The operator implements two distinct controllers: `LLMBatchGatewayReconciler` for the primary CRD lifecycle and `MetricsController` for the operator's own monitoring resources. The MetricsController is conditionally started only when `POD_NAMESPACE` is set, which means local development environments without this environment variable will lack operator-level monitoring reconciliation.

TLS configuration follows the OpenShift platform TLS profile pattern: at startup, the operator reads the cluster-wide `config.openshift.io/v1/APIServer` resource to determine TLS minimum version and cipher suites, and registers a watcher that triggers a graceful restart when the profile changes. This profile is also propagated to Helm chart values so that rendered workloads inherit the same TLS settings. On non-OpenShift clusters, it falls back to the Intermediate TLS profile.

The operator's RBAC surface is broad — managing Deployments, StatefulSets, Services, ConfigMaps, ServiceAccounts, Roles, RoleBindings, Secrets, cert-manager Certificates, Gateway API HTTPRoutes, and Prometheus monitoring resources — reflecting the wide variety of resources the Helm charts can produce. Optional resource types (HTTPRoute, Certificate, ServiceMonitor, PodMonitor, PrometheusRule) are handled via conditional watches that check CRD availability at startup, so the operator degrades gracefully on clusters without those CRDs installed.

The orphan detection mechanism lists all managed GVK types in the CR's namespace after each reconcile, filtering by controller owner reference, and deletes any resource owned by the CR but absent from the current rendered set. This ensures that configuration changes that remove resources (e.g., disabling monitoring) result in proper cleanup. The dual dispatch mode (sync vs. async) adds significant architectural flexibility — async mode introduces an additional Deployment, Redis message queues, worker pool configurations, and gate mechanisms (prometheus-saturation, prometheus-budget, redis-quota) for fine-grained inference throughput control.
