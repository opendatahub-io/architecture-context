## Purpose

**Short**: Kubernetes operator that manages the full lifecycle of LLM-D batch gateway deployments, consisting of an API server, request processor, garbage collector, and optional async processor for batch LLM inference workloads.

**Detailed**: The LLM-D Batch Gateway Operator watches `LLMBatchGateway` custom resources and renders Helm charts (batch-gateway and async-processor) into Kubernetes resources via server-side apply. A single `LLMBatchGateway` CR declaratively specifies the entire batch inference pipeline: an HTTP API server that accepts batch job submissions (`/v1/batches`, `/v1/files`), a processor that dispatches individual inference requests to inference gateways (either synchronously via HTTP or asynchronously via Redis message queues), and a garbage collector that expires old jobs and files.

The operator embeds two upstream Helm charts — `batch-gateway` (for the API server, processor, and GC) and `async-processor` (for the async dispatch worker). Component container images are injected via environment variables sourced from `params.env`, allowing the platform operator (`rhods-operator`/`opendatahub-operator`) to control which images are deployed rather than the end user. The operator supports cross-namespace secret references via Gateway API `ReferenceGrant` CRs, optional TLS termination via cert-manager, Gateway API `HTTPRoute` for ingress, and full observability integration (Prometheus ServiceMonitor, PodMonitor, PrometheusRule, Grafana dashboards, and OpenTelemetry tracing).

The operator also runs a `MetricsController` that ensures its own monitoring infrastructure (metrics Service, ServiceMonitor, PrometheusRule with operator-health alerts) is always present in the operator's namespace. Status is reported per-component (apiServer, processor, gc, asyncProcessor) with ready replica counts and conditions, providing a clear operational view.

## Architectural Analysis

The LLM-D Batch Gateway Operator follows a Helm-rendering operator pattern — rather than imperatively creating Kubernetes resources in Go code, the controller embeds upstream Helm charts and uses the Helm template engine to produce `Unstructured` objects, which are then applied via server-side apply (SSA). This design allows the operator to track upstream chart changes with minimal code modifications, while the CRD provides a curated API surface that maps user intent to Helm values. The operator maintains a `managedGVKs` list (Deployments, Services, ConfigMaps, ServiceAccounts, Certificates, HTTPRoutes, ServiceMonitors, PodMonitors, PrometheusRules) and garbage-collects orphaned resources when the rendered set changes — for example, when switching from async to sync dispatch mode.

The cross-namespace secret resolution is a notable security design. The operator implements Gateway API `ReferenceGrant` semantics: when `spec.secretRef.namespace` differs from the CR's namespace, the operator lists `ReferenceGrant` CRs in the target namespace and verifies that one permits `batch.llm-d.ai/LLMBatchGateway` from the CR's namespace to reference a `core/Secret`. If permitted, the operator copies the secret data into the CR's namespace under a managed name (`{name}-credentials`) with the CR as owner. The `secretRef` is enforced as immutable after the first copy to prevent credential confusion attacks. A `secretWatchFilter` predicate ensures the cluster-wide Secret informer only triggers reconciles for tracked cross-namespace secrets, minimizing unnecessary work.

The dual dispatch mode architecture (sync vs async) reflects two production deployment patterns. In sync mode, the processor directly calls inference gateways via HTTP with configurable per-endpoint concurrency control (including AIMD adaptive concurrency that backs off on 429/5xx responses). In async mode, the processor enqueues requests to Redis sorted-set queues, and a separate async-processor deployment polls queues and dispatches to inference gateways with flow-control gating (prometheus-saturation, redis-quota, or prometheus-budget). The `modelGateways` map allows per-model routing to different inference pools, each with its own `InferencePool` name and scheduling objective.

The operator's own observability is self-managed via the `MetricsController`, which bootstraps and self-heals a metrics Service, ServiceMonitor, and PrometheusRule with two built-in alerts: high reconcile error rate and leader election loss. Custom Prometheus metrics (`llmbatchgateway_controller_reconcile_errors_total`) partition errors by reason (ReferenceNotPermitted, SecretRefImmutable, Other) for operational debugging. The managed components expose their own metrics (API server on 8081/TCP, processor on 9090/TCP, GC on 9091/TCP) with optional ServiceMonitor/PodMonitor resources controlled by `spec.monitoring.enabled`.

One architectural concern is the FIPS gap in the async TLS configuration: while the primary `InferenceGatewaySpec` has a CEL validation rule that explicitly blocks `tlsInsecureSkipVerify`, the async-specific `AsyncTLSSpec` (`llmdasync_types.go:140`) allows `InsecureSkipVerify: true` without a validation guard. This inconsistency should be addressed to ensure uniform TLS security posture across both dispatch modes.
