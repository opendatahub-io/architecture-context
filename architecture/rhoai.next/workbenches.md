## Purpose

**Short**: Kubernetes operator, REST API, and web UI for managing interactive development environments (Workspaces) for AI/ML workloads.

**Detailed**: Workbenches implements Kubeflow Notebooks v2, providing a platform for running interactive development environments on Kubernetes. It introduces the Workspace and WorkspaceKind custom resources that decouple environment configuration (what images, resource profiles, and IDE types are available) from individual workspace instances (a user's running environment).

The component consists of three deployable services: a Kubernetes controller that reconciles Workspace CRs into StatefulSets, Services, and optionally Istio VirtualServices; a Go REST API backend that provides namespace-scoped CRUD operations with Kubernetes-native authorization via SubjectAccessReview; and a React/PatternFly frontend that offers workspace lifecycle management (create, edit, pause, delete) and administrative WorkspaceKind configuration. The architecture supports native JupyterLab, RStudio, and VS Code (code-server) environments.

Within RHOAI, this component is deployed into the `kubeflow-workspaces` namespace and integrates with the platform's Istio service mesh for ingress routing, network isolation, and authorization. The frontend communicates with the backend via Istio VirtualService routing, and the backend delegates authorization to the Kubernetes API server.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Workspace CRD is Namespaced (`workspaces/controller/api/v1beta1/workspace_types.go:295-327`); WorkspaceKind is Cluster-scoped (shared configuration) |
| **Deployment model** | multi-tenant (single controller, namespace-scoped workspaces) | Controller watches all namespaces; backend scopes API calls per namespace |
| **Tenant identifier** | namespace name + user identity (from `kubeflow-userid` header) | `workspaces/backend/internal/auth/authentication.go:29-70` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SubjectAccessReview checking user's namespace-scoped RBAC | Kubernetes API server (via backend SAR middleware) | `DISABLE_AUTH` flag defaults to `true` in code (overridden to `false` in deployment manifests); flag intended to be removed before GA |
| Data storage | Per-namespace PVCs for workspace home and data volumes | Kubernetes (PVC namespace scoping) | No cross-namespace data sharing restrictions beyond Kubernetes RBAC |
| Network traffic | NetworkPolicy default-deny-ingress in controller namespace; per-component NetworkPolicies allowing only Istio ingress | Kubernetes NetworkPolicy | Workspace pods in user namespaces have no default NetworkPolicy (must be configured separately) |
| Compute & resources | Per-workspace resource limits via WorkspaceKind podConfig (CPU, memory, GPU) | Kubernetes (resource requests/limits on StatefulSet pods) | No per-namespace ResourceQuota enforcement by this component |
| Configuration & secrets | Per-namespace Secrets attached to workspace pods | Kubernetes namespace scoping | Secrets API currently uses mock data (TODO in code) |
| API scoping | Namespace-scoped list operations; SAR checks per namespace/resource | Application middleware + Kubernetes RBAC | Cluster-wide workspace listing (`GET /api/v1/workspaces`) available -- access controlled by SAR |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|

## Architectural Analysis

The workbenches repository implements a clean three-tier architecture for managing interactive development environments on Kubernetes. The separation between WorkspaceKind (cluster-scoped templates) and Workspace (namespace-scoped instances) is a thoughtful design that allows platform administrators to define approved IDE configurations while giving users self-service workspace creation within their authorized namespaces. The WorkspaceKind CRD is notably rich -- it supports image configuration options with redirect chains for deprecation, pod configuration profiles with tolerations and GPU resources, activity-based culling for cost management, and customizable spawner UI metadata (icons, logos).

The controller's reconciliation logic translates Workspace CRs into StatefulSets rather than Deployments, which is correct for stateful workload environments that need persistent identity and storage. Each workspace gets its own ClusterIP Service and, when Istio is enabled, a VirtualService with path-prefix-based routing (`/workspace/connect/{namespace}/{name}/{portId}/`). The HTTP path prefix templating system in `extraEnv` allows workspace environments to be aware of their proxied path, which is essential for IDEs like JupyterLab that need to know their base URL. The controller also implements HTTP/2 disabling by default as a CVE mitigation (GHSA-qppj-fm5r-hxr3).

The backend's architecture follows a repository pattern with clear separation of concerns -- handlers, models, and repositories form distinct layers. The authentication system delegates to Kubernetes RBAC via SubjectAccessReview with a 10-second TTL cache, which is the correct pattern for multi-tenant Kubernetes-native services. However, several areas are still under development: the `DISABLE_AUTH` flag defaults to `true` in code (overridden to `false` in deployment manifests but flagged as "TODO: remove before GA"), the secrets repository uses mock data, and CORS allows all origins. The PVC repository notably tracks mount information by cross-referencing pods and workspaces in the namespace, providing users with visibility into which volumes are in use.

The frontend leverages Module Federation infrastructure (configured but not yet exposing modules) and the mod-arch framework packages for Kubeflow/RHOAI platform integration. The use of PatternFly 6 aligns with Red Hat's design system. The generated API client (via swagger-typescript-api) ensures type safety between frontend and backend. The nginx configuration includes security headers (X-Frame-Options, X-XSS-Protection, CSP) and static asset caching. One architectural concern is that user identity and admin status are currently hardcoded in the AppContext (userId: `kubeflow-user`, clusterAdmin: `true`), with TODOs to integrate real user settings.

The absence of Konflux Dockerfiles on this branch is notable -- all three Dockerfiles use upstream patterns (golang builder + distroless, node builder + nginx:alpine) with static Go linking (`CGO_ENABLED=0`). The downstream release branch will need to introduce Konflux-compatible Dockerfiles with UBI base images, dynamic linking for FIPS compliance, and Hermeto prefetch for hermetic builds.
