## Purpose

**Short**: Kubeflow Notebooks v2 — manages interactive development environments (JupyterLab, RStudio, VS Code) on Kubernetes through a three-tier architecture of controller, REST API backend, and web frontend.

**Detailed**: Workbenches is the RHOAI distribution of Kubeflow Notebooks v2. It provides a complete workspace management system for data scientists to run interactive development environments on Kubernetes. The system is built as three cooperating components: a Kubernetes controller that reconciles `Workspace` and `WorkspaceKind` custom resources into StatefulSets and supporting infrastructure, a Go REST API backend that proxies Kubernetes operations with per-user authentication and authorization, and a React frontend served via nginx.

The controller implements a template-based workspace model where cluster-scoped `WorkspaceKind` resources define reusable workspace types (e.g., JupyterLab, RStudio, VS Code configurations), and namespace-scoped `Workspace` resources represent individual user instances. The controller supports two mutually exclusive ingress strategies — Istio VirtualServices and Kubernetes Gateway API HTTPRoutes — and manages the full lifecycle of workspace pods including activity probing, pause/resume, and graceful shutdown. Validating webhooks enforce referential integrity between Workspaces and WorkspaceKinds.

The backend introduces a user-facing REST API that decouples the frontend from direct Kubernetes API access. It supports dual authentication modes: internal header-based identity (behind a trusted proxy) and Bearer token validation via Kubernetes TokenReview. Every API call is authorized through SubjectAccessReview, enforcing the same RBAC boundaries as direct kubectl access.

## Architectural Analysis

The workbenches architecture follows a clean separation of concerns across its three tiers, with the controller owning all Kubernetes resource lifecycle management and the backend serving as an authenticated API gateway. This design enables the frontend to operate without direct Kubernetes API access, centralizing authorization enforcement in the backend.

A notable design decision is the dual ingress strategy: the controller conditionally creates either Istio VirtualServices or Kubernetes Gateway API HTTPRoutes per workspace, selected at controller startup via configuration flags. The Gateway API path additionally injects a kube-rbac-proxy sidecar into workspace pods for authentication. These two strategies are mutually exclusive — the controller refuses to start if both are enabled. The RHOAI/ODH deployment overlay (`overlays/gateway/`) configures the Gateway API path by default, pointing to the platform's `data-science-gateway` in `openshift-ingress`.

TLS configuration is dynamically resolved from the OpenShift APIServer TLS profile (`apiservers.config.openshift.io/cluster`), with automatic fallback to Mozilla Intermediate defaults (TLS 1.2+, ECDHE cipher suites) on non-OpenShift clusters. A profile watcher triggers controller restart when the cluster TLS policy changes, ensuring the controller tracks platform-wide TLS requirements without manual intervention.

The multi-tenant model relies on Kubernetes namespace isolation reinforced by per-request SubjectAccessReview in the backend. The controller's aggregated ClusterRoles (admin/edit/view) integrate with the Kubeflow RBAC hierarchy, enabling platform-wide role composition. However, the controller watches Workspaces across all namespaces with a single cluster-scoped informer, relying on Kubernetes RBAC rather than application-level namespace filtering for tenant isolation.

Only the controller has a Konflux Dockerfile with FIPS build flags (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1`). The backend's upstream Dockerfile uses `CGO_ENABLED=0` with a distroless base — a FIPS compliance gap if the backend is deployed without a downstream Konflux build override.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SubjectAccessReview in backend; aggregated ClusterRoles (admin/edit/view) for fine-grained RBAC | Kubernetes (RBAC) + Application (backend SubjectAccessReview) | Controller service account has cluster-wide access; isolation relies on user-facing RBAC, not controller-level namespace scoping |
| Data storage | Per-namespace Workspaces; PVCs created per workspace in user namespace | Kubernetes (namespace isolation) | WorkspaceKind is cluster-scoped, shared across all tenants; ConfigMaps for image sources are cluster-wide |
| Network traffic | No NetworkPolicy resources in component manifests | N/A | Network isolation between workspace pods from different tenants is not enforced by this component; relies on platform-level NetworkPolicy |
| Compute & resources | Resource requests/limits on workspace pods (defined by WorkspaceKind podConfig) | Kubernetes (pod resource spec) | No per-tenant ResourceQuota or LimitRange created by this component |
| Configuration & secrets | Per-namespace Secrets managed via backend API; controller-level ConfigMaps filtered by label selector | Kubernetes (namespace isolation) | Backend service account has cluster-wide Secret read access |
| API scoping | Backend API routes are namespace-scoped for Workspaces, Secrets, PVCs; cluster-scoped for WorkspaceKinds and StorageClasses | Application (backend) + Kubernetes (SubjectAccessReview) | SubjectAccessReview enforcement is application-level; a bug could bypass namespace scoping |

| Controller metrics endpoint | Cluster-scoped | authn/authz FilterProvider |
