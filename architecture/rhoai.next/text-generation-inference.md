## Purpose

**Short**: Text Generation Inference Server (TGIS) provides high-performance model serving for large language models with gRPC and HTTP interfaces, continuous batching, and GPU-accelerated inference.

**Detailed**: TGIS is an early fork of HuggingFace Text Generation Inference (TGI), developed internally at IBM and significantly diverged from the original. It serves as a model inference runtime for text generation workloads in the RHOAI platform, supporting causal (decoder-only) and encoder-decoder (seq2seq) language models.

The system follows a multi-process architecture: a Rust launcher process manages one or more Python model shard processes and a Rust router process. The Python shards (`text-generation-server`) handle model loading, GPU memory management, and forward-pass inference via PyTorch, ONNX Runtime, or the IBM FMS engine. The Rust router (`text-generation-router`) accepts external gRPC requests via the `fmaas.GenerationService` API and HTTP requests for health and metrics, validates inputs, batches requests using a sophisticated continuous batching algorithm, and dispatches work to the Python shards over Unix domain socket gRPC connections.

Key features not in upstream HF TGI include a gRPC front-end interface, batch input support, independent tokenization API, configurable inference engine abstraction, tensor parallel (multi-GPU) sharding via NCCL, flash attention support, GPTQ quantization with Exllama V2 kernels, PyTorch 2 compile support, and tuned soft-prompt (PEFT) support.

## Architectural Analysis

TGIS uses a split-language architecture that leverages each language's strengths: Rust for high-throughput async I/O, request validation, tokenization, and continuous batching; Python for model loading and GPU inference via the PyTorch ecosystem. The launcher acts as a supervisor process -- it starts Python shard processes (one per GPU for tensor parallelism), waits for them to signal readiness via Unix domain socket files, then spawns the router process. This design allows clean process isolation and independent crash recovery.

The continuous batching system is architecturally notable. Two batch types -- `PaddedBatch` (for standard attention) and `FlashBatch` (for flash attention) -- implement different weight estimation models. The router queries the Python shard for memory scaling coefficients at startup, then uses these to dynamically size batches without exceeding GPU memory. This avoids OOM failures while maximizing throughput. The batch weight limit is auto-calibrated rather than user-configured.

The external gRPC API (`generation.proto`, package `fmaas`) is distinct from the internal shard-communication API (`generate.proto`, package `generate.v1`). The external API provides `Generate`, `GenerateStream`, `Tokenize`, and `ModelInfo` RPCs. The internal API provides lower-level `Prefill`, `NextToken`, `PruneBatch`, and `PrefixLookup` RPCs that the router orchestrates to implement continuous batching. This two-tier API design cleanly separates client-facing concerns from inference scheduling.

TLS is optional and applies only to the gRPC server (via tonic `ServerTlsConfig`). When enabled, it supports mutual TLS with client certificate authentication. The HTTP server (health/metrics on port 3000) does not support TLS independently. There is no built-in authentication mechanism -- the service relies on platform-level enforcement (e.g., Istio, service mesh, or KServe).

The Dockerfile uses a multi-stage build with UBI 9 as the final base image. The Rust components are compiled on `rust:1.78-bookworm` (Debian) and linked against system `libssl.so.3`. CUDA 12.1 development libraries are installed for building custom CUDA kernels (fused attention). The Python environment is managed via conda (Miniforge) rather than system Python. No Konflux Dockerfile exists on this branch.

From a security perspective, TGIS has notable gaps for FIPS compliance. The router's gRPC server TLS uses tonic with `rustls` (backed by the `ring` crate, which is not FIPS-validated). In production RHOAI deployments, TLS is typically terminated upstream by KServe or the platform's ingress layer. The Python server communicates exclusively over Unix Domain Sockets with `add_insecure_port`, avoiding network TLS entirely for shard communication.
