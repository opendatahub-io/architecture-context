## Purpose

**Short**: High-performance gRPC/HTTP inference server for serving large language models with multi-GPU tensor parallelism, continuous batching, and paged attention.

**Detailed**: Text Generation Inference Server (TGIS) is a model serving runtime that provides gRPC and HTTP endpoints for text generation using large language models. It is deployed as part of RHOAI's model serving stack, typically behind KServe or Caikit, to serve models like LLaMA, BLOOM, Falcon, T5, and GPT-NeoX families.

The system has a three-tier architecture: a **Launcher** (Rust) orchestrates the startup and lifecycle of one or more **Server shards** (Python) and a **Router** (Rust). Each server shard loads a portion of the model weights onto a dedicated GPU and communicates with the router via Unix Domain Sockets using an internal gRPC protocol. The router exposes the external gRPC API (`fmaas.GenerationService`) and an HTTP health endpoint, handles request validation, batching, and scheduling across shards.

TGIS supports multiple inference backends through a pluggable engine architecture including HuggingFace Transformers, TGIS-native (custom tensor-parallel models with Flash Attention), IBM FMS, HuggingFace Accelerate, Optimum BetterTransformer, Optimum ONNX Runtime, and DeepSpeed. It includes sophisticated memory management with paged KV cache, automatic memory estimation, prompt caching, speculative decoding, and custom CUDA kernels for fused attention on NVIDIA Ampere GPUs.

## Architectural Analysis

TGIS implements a sophisticated three-tier inference architecture that separates concerns between process lifecycle management (launcher), request routing and batching (router), and model execution (server shards). This design enables horizontal GPU scaling through tensor parallelism while maintaining a single external API surface. The launcher's role is particularly noteworthy — it resolves model configurations, converts tokenizers, sets up distributed training environment variables per shard, and provides robust failure detection including SIGBUS handling for NCCL shared memory exhaustion (a common operational issue in multi-GPU Kubernetes deployments).

The router's continuous batching implementation is a key performance differentiator. Rather than processing requests one at a time, the router maintains a queue and dynamically constructs batches that maximize GPU utilization. New requests can be concatenated into in-flight batches between generation steps, and the queue uses a multi-level fitting algorithm with weight-based limits, prefill padding constraints, and time-based cutoffs. The batch weight model is derived from the server's memory characterization — a startup process that profiles GPU memory consumption across varying batch sizes and sequence lengths, fitting linear and quadratic models to predict maximum safe batch configurations.

The pluggable inference engine architecture (`BaseInferenceEngine` → `get_inference_engine_class()` factory) allows the same serving infrastructure to support multiple backends without code changes. The TGIS-native engine is the most performance-critical path, implementing custom model classes with Flash Attention and tensor parallelism support for specific architectures (LLaMA, Falcon, BLOOM, T5, GPT-NeoX). The paged attention mode, built on IBM's `fms-extras` library, adds block-based KV cache management and optional speculative decoding for further throughput improvements.

From a security perspective, TGIS has notable gaps for FIPS compliance. The router's gRPC server uses `rustls` (backed by the `ring` crate) which is not FIPS-validated. In production RHOAI deployments, TLS is typically terminated upstream by KServe or the platform's ingress layer, making this less critical. However, if direct gRPC TLS is enabled via `TLS_CERT_PATH`/`TLS_KEY_PATH`, the connection uses non-FIPS crypto. The Python server communicates exclusively over Unix Domain Sockets, avoiding network TLS entirely for shard communication. The absence of Konflux Dockerfiles on this branch indicates the RHOAI build pipeline may use a separate branch or overlay for Konflux integration.

The deployment manifests follow a clean kustomize pattern with a minimal base (deployment + headless service) and strategic merge patches for different GPU configurations (1/2/8 GPU), optimization features (Flash Attention, PyTorch 2 compilation, shared memory for NCCL), and security hardening (read-only root filesystem). The headless service design is intentional — it enables DNS-based service discovery without load balancing, which is appropriate for dedicated model-serving pods where each pod serves a complete model instance.
