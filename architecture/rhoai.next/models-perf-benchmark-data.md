## Purpose

**Short**: Offline data-ingestion toolkit comprising a Kafka CDC consumer and a REST API client, both producing structured benchmark data files for the RHOAI model-validation ecosystem.

**Detailed**: models-perf-benchmark-data is a data pipeline repository that ingests model benchmark data from two sources and writes it to a structured on-disk format (JSON and NDJSON files organized by provider/model). The `kafka-processor` sub-application connects to a Kafka broker, subscribes to CDC (Change Data Capture) topics carrying model metadata, performance metrics, evaluations, validations, provider records, and variant groups, then deserializes Debezium or custom CDC envelopes into entity files with post-processing transforms (hardware configuration normalization, overall accuracy computation). The `api-client` sub-application fetches the same entity types from an HTTP REST API (model-validation v1) using paginated GET requests with configurable TLS verification, then serializes and writes the data in the same directory layout. Neither sub-application exposes inbound network services; both are batch consumers that authenticate outbound to their respective data sources via SASL/SSL (Kafka) or TLS (REST API).

## Data Flows

- **Kafka CDC ingest path:** External data producers publish model benchmark entities (model metadata, performance metrics, evaluations, validations, providers, variant groups) as CDC messages to Kafka topics. The `kafka-processor` sub-application connects to the Kafka broker using SASL/SSL credentials, consumes messages from configured topics, deserializes each message as either a Debezium CDC envelope or a custom CDC envelope (`{"op": "CREATE", "data": {...}}`), classifies the entity type by topic name or field heuristics, and writes the entity to the appropriate JSON or NDJSON file in a `provider/model/` directory hierarchy. After all messages are consumed, a post-processing pass deduplicates NDJSON files by record ID and applies registered transforms (hardware configuration normalization, overall accuracy computation) to each model's data. A `manifest.json` is generated as the final step.
- **REST API ingest path:** The `api-client` sub-application fetches the same entity types from a model-validation v1 REST API via paginated GET requests (`/api/v1/providers`, `/api/v1/models`, `/api/v1/performances`, `/api/v1/evaluations`, `/api/v1/validations`, `/api/v1/variant-groups`). Each entity type is serialized and written to the same on-disk format as the Kafka path. Post-processing (deduplication and transforms) is applied identically.
- **Security context:** Kafka authentication is handled via SASL credentials (username/password from environment variables) with optional SSL/TLS using client certificates. The REST API client uses configurable TLS verification with an option to supply a CA certificate and bypass hostname verification for internal service communication.

## Architectural Analysis

This repository is a data-pipeline toolkit, not a deployed service. It contains two independent sub-applications that share a common on-disk output format but use different ingest mechanisms (Kafka vs. HTTP API). Neither exposes inbound network services; the repository has no Dockerfiles, Kubernetes manifests, or deployment configuration, confirming its role as a batch processing tool run outside the cluster or in CI/CD pipelines.

The `kafka-processor` is the more complex sub-application. It implements a full CDC processing pipeline: the `KafkaDataProcessor` class manages a `confluent_kafka.Consumer` lifecycle with graceful signal handling (SIGINT/SIGTERM), processes messages in a poll loop with configurable batch limits, and delegates entity classification and file I/O to `EntityProcessor`. Entity type detection uses a priority chain: topic name pattern matching, explicit `entity_type`/`type` fields, then field-presence heuristics (e.g., `ttft_mean` implies performance data, `rhoai_version` implies validation data). The CDC envelope parser supports both a legacy Debezium format (`schema`/`payload` with `after`/`before` fields and operation codes `c`/`u`/`d`/`r`) and a simplified custom format, suggesting an ongoing migration from Debezium-based CDC to a lighter-weight event format.

The `api-client` is a simpler paginated REST client built on the `requests` library. It implements a custom `_CertNoHostnameAdapter` that creates an SSL context trusting a specific CA certificate while disabling hostname verification — a pattern typical of internal service communication where the server certificate's CN/SAN may not match the routing hostname. The pipeline fetches six entity types sequentially from `/api/v1/*` endpoints, with retry logic (3 retries, exponential backoff, retry on 429/5xx).

Both sub-applications produce the same output structure: a directory tree organized as `{provider}/{model}/` with `metadata.json`, `performance.ndjson`, `evaluations.ndjson`, `validation.ndjson`, and `provider.json` files, plus a top-level `variant-groups.ndjson` and `manifest.json`. The transform system (`HardwareConfigurationTransform`, `OverallAccuracyTransform`) enriches data after ingestion, operating on either metadata or performance records depending on the transform's target file declaration.

The SASL and SSL configuration in `kafka-processor/src/config.py` uses environment variables for all credentials (SASL_PASSWORD, SSL_KEY_PASSWORD, SSL_CA_LOCATION, SSL_CERTIFICATE_LOCATION, SSL_KEY_LOCATION), following the 12-factor app pattern. No credentials are hardcoded. The API client similarly externalizes its base URL and TLS settings via environment variables loaded through `python-dotenv`.
