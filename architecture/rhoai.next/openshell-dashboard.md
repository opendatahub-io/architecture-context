## Purpose

**Short**: Standalone web admin UI and Go backend-for-frontend (BFF) for managing OpenShell sandboxed AI agent runtimes through the NVIDIA OpenShell gateway.

**Detailed**: The OpenShell Dashboard is a two-tier web application that provides a browser-based administrative interface for the NVIDIA OpenShell agent sandboxing platform. It consists of a Go BFF server that proxies REST requests to the OpenShell gateway over gRPC using the official Go SDK, and a React (PatternFly 6) frontend that presents workspace, sandbox, provider, and policy management capabilities.

The BFF operates as a pure token relay — it never validates tokens, holds sessions, or runs OIDC flows. Authentication is delegated entirely to an external auth proxy (oauth2-proxy or the host platform's equivalent) which injects bearer tokens that the BFF forwards to the gateway. The gateway makes all RBAC decisions. This design enables the dashboard to be consumed both as a standalone deployment with oauth2-proxy and as an embedded component within downstream platforms like RHOAI via npm package exports and Module Federation.

The frontend exports self-contained page components, a slot injection system, i18n support, and API client hooks as an npm package (`openshell-dashboard/pages`, `openshell-dashboard/components`, etc.), allowing downstream platforms to import and wrap individual pages without forking the codebase.

## Architectural Analysis

The openshell-dashboard follows a strict BFF (Backend-for-Frontend) pattern where the Go server acts as a protocol translator between browser REST/WebSocket and the OpenShell gateway's gRPC API. The architecture is deliberately minimalist: the BFF holds no state, runs no OIDC flows, and validates no tokens. All authorization is deferred to the gateway, making the dashboard a thin relay layer.

The Go backend uses a handler-per-resource pattern with `go-chi/chi` for routing, organized through a `services` layer that wraps the OpenShell SDK client interfaces. This service layer serves as the downstream extension seam — consumers can substitute implementations without forking handlers. A notable escape hatch exists in `pkg/clients/rawexec.go` which bypasses the SDK for binary-safe file uploads via raw gRPC, because the SDK's exec API does not yet support non-TTY stdin with arbitrary bytes.

TLS is configured at three independent boundaries: inbound BFF HTTPS (optional, for production), outbound gateway TLS (server verification), and outbound gateway mTLS (client authentication). The inbound TLS configuration enforces TLS 1.3 minimum with HTTP/2 support, while the outbound gRPC connection to the gateway uses TLS 1.2+ with custom CA and client certificate support.

The frontend's architecture is designed for downstream consumption as a first-class concern. Pages are flat files in `src/pages/`, exported without any dashboard chrome, using navigation callbacks instead of direct routing. A slot system (`SlotProvider`) allows downstream wrappers to inject custom UI elements. Feature flags are BFF-side environment variables exposed via the `/api/v1/auth/config` endpoint, enabling per-deployment capability gating — particularly important for features like the WebSocket terminal that may not work through federation proxies.

Gateway compatibility is a first-class concern: the SDK and gateway are wire-coupled through protobuf field numbering, and the project maintains a formal compatibility testing regime with pinned gateway versions, automated sweep jobs, and ADR-documented upgrade procedures.
