## Purpose

**Short**: A lightweight REST API service for orchestrating LLM evaluations across multiple backends, tracking experiments via MLflow, and running natively on OpenShift.

**Detailed**: EvalHub (eval-hub-sobha) is a Go-based REST API service that routes evaluation requests to frameworks like lm-evaluation-harness, RAGAS, Garak, and GuideLLM. It provides CRUD endpoints for evaluation jobs, benchmark collections, and evaluation providers, and integrates with MLflow for experiment tracking. The service uses a pluggable storage layer (SQLite for development, PostgreSQL for production), structured logging with zap, Prometheus metrics, and full OpenTelemetry tracing.

On OpenShift, EvalHub is managed by the TrustyAI Service Operator via an `EvalHub` custom resource. The Kubernetes runtime mode creates evaluation workloads as batch/v1 Jobs in tenant namespaces, each paired with a sidecar proxy container and an init container that downloads test data from S3-compatible storage. The sidecar acts as a reverse proxy between evaluation adapter containers and the EvalHub API and MLflow, handling TLS and token-based authentication. Authentication and authorization are enforced via Kubernetes TokenReview and SubjectAccessReview (SAR), with authorization rules mapped from HTTP endpoints to `trustyai.opendatahub.io` and `mlflow.kubeflow.org` API group resources.

## Architectural Analysis

EvalHub's architecture is built around three cooperating Go binaries—`eval-hub` (the central API server), `eval_runtime_sidecar` (a reverse proxy injected into evaluation job pods), and `eval_runtime_init` (an init container for S3 data pre-fetch)—plus a Python-based `lighteval` evaluation adapter container.

The API server uses Go's standard `net/http.ServeMux` with a custom `ExecutionContext` pattern that threads request ID, tenant, user identity, and a request-scoped logger through every handler call. This avoids framework dependencies while providing structured observability. The middleware stack is layered: outermost Prometheus metrics, then authentication (Kubernetes TokenReview), then authorization (SubjectAccessReview mapped via `auth.yaml` endpoint rules), followed by CORS (development mode only).

Multi-tenancy is identity-driven: the `X-Tenant` header identifies the namespace boundary, and the authorization layer translates each API call into a SAR check against `trustyai.opendatahub.io` resources scoped to that namespace. The Kubernetes runtime creates Jobs in tenant namespaces, and the storage layer filters queries by tenant. This design means tenant isolation depends on correct Kubernetes RBAC being provisioned in each tenant namespace by the TrustyAI operator.

TLS is configurable at two levels: the API server supports optional TLS termination via cert/key files (typically fronted by kube-rbac-proxy in cluster), and all outbound HTTP clients (MLflow, eval-hub proxy, OCI registry) use a shared `buildTLSConfig` helper that enforces TLS 1.2–1.3, loads custom CA bundles from PEM files, and respects `InsecureSkipVerify` for development. The sidecar's TLS configuration is injected via `sidecar_config.json` mounted on job pods, not via ConfigMap.

The Konflux Dockerfile uses `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime`, ensuring the binary dynamically links against OpenSSL on the UBI 9 runtime image, satisfying check-payload FIPS validation requirements.
