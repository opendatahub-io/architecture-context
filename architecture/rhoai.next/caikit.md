## Purpose

**Short**: Caikit is a Python AI toolkit and runtime framework that provides a modular, task-oriented architecture for building, serving, and managing AI models through stable gRPC and HTTP APIs.

**Detailed**: Caikit serves as the foundational runtime framework for AI model serving in the Red Hat OpenShift AI platform. It provides a decorator-driven system where AI model authors define "tasks" (abstract interfaces like TextGeneration, Embedding, Reranking) and "modules" (concrete implementations backed by specific ML frameworks). The runtime automatically generates gRPC and HTTP/REST APIs from these task/module definitions at startup, without requiring hand-written service code.

The framework includes a dual-protocol server (gRPC on port 8085, HTTP/FastAPI on port 8080), a model management lifecycle (load, unload, train, predict), and native integration with IBM ModelMesh for multi-model serving at scale. It supports TLS/mTLS, OpenTelemetry tracing, Prometheus metrics, streaming inference (server-side and bidirectional), request batching, and abortable request contexts. The runtime is used by downstream libraries like `caikit-nlp` and `caikit-tgis-serving` which provide concrete module implementations for large language model inference.

Caikit is a pure Python library (no container images, no Kubernetes manifests). It is consumed as a pip dependency by other RHOAI components that build the actual deployable container images. The `red-hat-data-services/caikit` repository is a midstream fork of the upstream `caikit/caikit` project.

## Architectural Analysis

Caikit's architecture is built on a powerful decorator-driven registration pattern that enables dynamic service generation. The `@task` decorator defines abstract AI task interfaces (specifying input/output types for both unary and streaming modes), while the `@module` decorator registers concrete implementations with the task registry. At server startup, `ServicePackageFactory` introspects all registered modules and tasks to auto-generate gRPC service descriptors and HTTP routes — no hand-written service code is needed. This means adding support for a new AI task requires only defining the task interface and implementing a module, and the runtime automatically exposes inference endpoints for it.

The data model layer (`@dataobject` decorator and `DataBase` metaclass) provides a bidirectional bridge between Python dataclasses and Protocol Buffers. The metaclass (`_DataBaseMetaClass`) auto-generates property accessors, `__init__` methods, and proto serialization/deserialization from field annotations. The `py-to-proto` library dynamically compiles protobuf descriptors at runtime, enabling the entire gRPC service definition to be generated from Python type annotations without pre-compiled `.proto` files for the application-layer services (only the ModelMesh/Model-Train integration protos are static).

The model management subsystem uses a factory pattern (`ModelFinderBase`, `ModelInitializerBase`, `ModelTrainerBase`) with configurable implementations. The `LocalModelInitializer` iterates through backends in priority order, allowing the same module to have multiple backend implementations (e.g., LOCAL, TGIS, vLLM). The `ModelManager` provides singleton caching, lazy loading with configurable poll intervals, retry logic for partially-uploaded models, and write-detection to avoid loading models mid-upload. Training is managed asynchronously through `LocalModelFuture` objects that wrap either threads or subprocesses (configurable via `use_subprocess` setting), with a retention policy for completed training futures.

The gRPC server uses a distinctive interception pattern (`CaikitRuntimeServerWrapper`) that wraps the standard gRPC server to reroute all dynamically-generated RPC methods through a single `GlobalPredictServicer.Predict` handler. This handler extracts the model ID from gRPC metadata (the `mm-model-id` key set by ModelMesh), loads the appropriate model, and dispatches the request. The wrapper also adds a `safe_rpc_wrapper` around every RPC handler that provides consistent error handling, Prometheus gauge tracking (`rpc_in_progress_gauge`), and bidirectional streaming acknowledgment headers. The HTTP server achieves similar dispatch through FastAPI route registration with request-body-based model ID extraction.

A notable design decision is that caikit has no built-in authentication or authorization. All auth is delegated to the platform layer (kube-rbac-proxy sidecars, OAuth proxy, Gateway API, or Istio mTLS). Caikit's TLS support (both TLS and mTLS) is purely for transport-level encryption between the caikit process and its immediate callers (e.g., the ModelMesh sidecar or Kubernetes health probes). This clean separation means caikit can be deployed in diverse security contexts without code changes, but it also means that any deployment of caikit without platform-level auth enforcement exposes the inference and management APIs without protection.
