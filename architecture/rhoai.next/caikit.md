## Purpose

**Short**: Caikit is a Python AI toolkit and runtime framework that enables serving AI/ML models through task-specific gRPC and HTTP APIs with a modular, composable architecture.

**Detailed**: Caikit provides an abstraction layer between AI model implementations and application consumers. Rather than requiring applications to understand tensor-level model interfaces, Caikit defines task-oriented APIs (text generation, classification, embeddings, reranking, time series forecasting, etc.) that present data in domain-specific structures. Model authors implement "modules" that register against tasks, and Caikit's runtime dynamically generates gRPC and HTTP service endpoints for all registered modules.

The framework consists of three layers: (1) a **core** layer providing the module system, data model abstractions with automatic protobuf generation, task definitions, pluggable backends, and model lifecycle management; (2) an **interfaces** layer defining domain-specific tasks and data models for NLP, time series, and vision; and (3) a **runtime** layer that builds dual-protocol (gRPC + HTTP/REST) servers, integrates with ModelMesh for multi-model serving, provides health probes, Prometheus metrics, OpenTelemetry tracing, and request batching.

In the RHOAI platform, Caikit serves as the core runtime framework used by downstream components like `caikit-nlp` and `caikit-tgis-serving` to serve large language models behind KServe's model serving infrastructure. It is not deployed as a standalone container itself but is consumed as a Python library dependency.

## Purpose

**Short**: Caikit is a Python AI toolkit providing a modular framework for AI model serving and training, integrated with ModelMesh as a runtime sidecar via gRPC.

**Detailed**: Caikit is a Python-based AI toolkit that provides stable, task-specific model APIs for AI consumers while offering AI developers a modular and composable framework for building algorithms and models. In the RHOAI platform, caikit serves as the model runtime sidecar for ModelMesh, implementing the `mmesh.ModelRuntime` gRPC interface for model lifecycle management (loading, unloading, sizing, and status reporting). It also supports HTTP serving via FastAPI and gRPC serving with Prometheus metrics and OpenTelemetry tracing as optional runtime capabilities configured through extras in pyproject.toml (`runtime-grpc`, `runtime-http`, `runtime-trace`). The framework includes integration with Model-Train's Dynamic Workflow (DWF) system through the `processproto.Process` gRPC interface for training job execution. Caikit uses `alchemy-config` for runtime configuration, allowing deployment-time customization of TLS, authentication, and service parameters without code changes. Its interface surface comprises 13 gRPC service methods across 3 proto-defined services (ModelMesh, ModelRuntime, Process) with no proto-level authentication — external-facing auth is delegated to the RHOAI platform infrastructure.

| Data storage | Per-model directories on local filesystem | Application (model_manager) | Models share the same filesystem and process memory; no per-tenant storage isolation |
| Network traffic | Single-port serving (all models share gRPC/HTTP ports) | Application | No per-model network isolation; all models served on same ports |

- **ModelMesh → caikit (mmesh.ModelRuntime):** Model lifecycle operations flow from the ModelMesh controller to the co-located caikit runtime container via pod-local gRPC. ModelMesh calls `loadModel` to load a model into memory, `unloadModel` to release it, `predictModelSize`/`modelSize` for capacity planning, and `runtimeStatus` during startup to discover runtime capabilities and trigger purge of stale model state.
- **caikit → ModelMesh (mmesh.ModelMesh):** Model registration and management requests flow from caikit to the ModelMesh cluster. This includes `registerModel`/`unregisterModel` for model lifecycle, `ensureLoaded` to trigger on-demand loading, and `setVModel`/`deleteVModel`/`getVModelStatus` for virtual model aliasing that supports zero-downtime model updates.
- **Model-Train DWF → caikit (processproto.Process):** Training job execution requests flow from the Model-Train Dynamic Workflow orchestrator to caikit. The `Run` RPC receives training parameters, input/output directory paths, and COS storage references, returning training results and response parameters.
- **Inference clients → caikit runtime:** Client inference requests arrive via either gRPC or HTTP (FastAPI) transport, depending on which runtime extras are installed. The runtime dynamically generates service interfaces from registered caikit modules and task definitions.
- **caikit → observability (optional):** When runtime-trace is installed, traces are exported via OTLP to an OpenTelemetry Collector. When runtime-grpc is installed, Prometheus metrics are exposed for scraping via prometheus_client and py-grpc-prometheus.

## Architectural Analysis

Caikit's most distinctive architectural feature is its **dynamic service generation** system. Rather than defining API endpoints statically, the runtime introspects all registered modules and their task decorators at startup, then automatically generates gRPC service descriptors and HTTP route handlers for every module's inference and training methods. This means adding a new task (e.g., `@task` with `TextGenerationTask`) and a module implementing it (`@module` with `@TaskBase.taskmethod`) automatically exposes new API endpoints without changing any server code. The service generation machinery in `caikit/runtime/service_generation/` handles proto message construction, request/response type mapping, and streaming configuration based entirely on the task and module signatures.

The **dual-protocol architecture** (gRPC + HTTP) with shared servicer logic is well-designed for platform integration. The `GlobalPredictServicer` handles the core inference logic (model lookup, request unmarshalling, inference execution, response marshalling) while both the gRPC server and HTTP server delegate to it. This ensures consistent behavior across protocols. The HTTP server uses FastAPI with support for both `application/json` and `multipart/form-data` content types, and provides Server-Sent Events (SSE) for streaming responses — a pragmatic choice for HTTP streaming that avoids WebSocket complexity.

The **ModelMesh integration** via Unix socket gRPC follows the ModelMesh ServingRuntime contract (`model-runtime.proto`). Caikit implements the `ModelRuntime` service which ModelMesh calls to load/unload models and query runtime capacity. This integration is critical for RHOAI's multi-model serving architecture where ModelMesh orchestrates model placement across Caikit runtime pods. The `PredictModelSizeResponse` mechanism enables ModelMesh to make intelligent scheduling decisions based on model memory requirements.

The **data model system** with automatic protobuf generation from Python dataclasses (`@dataobject` decorator using `py_to_proto`) is architecturally significant. It eliminates the traditional workflow of maintaining `.proto` files separately from Python code, instead generating protobuf descriptors dynamically at import time. While this simplifies development, it means the gRPC API surface is determined at runtime rather than at build time, which has implications for API stability and contract testing. The `DataBase` metaclass (`_DataBaseMetaClass`) is complex — it auto-generates `__init__`, property getters, and `__slots__` from protobuf descriptors, and handles oneOf fields, nested messages, and enum mappings.

The **health probe architecture** is notable: Caikit ships a separate `caikit_health_probe` package (installed as the `caikit-health-probe` CLI entry point) that runs as an independent process. It performs readiness checks by making actual gRPC Health.Check and HTTP /health requests to the runtime, and performs liveness checks by detecting the Caikit process via `psutil`. This separation means the health probe doesn't share the runtime's event loop or thread pool, ensuring it can detect deadlocks or resource exhaustion in the main process. The probe supports TLS/mTLS certificate validation matching the runtime's configuration, including a creative fallback that extracts SANs from the server certificate to construct proper hostnames for TLS verification.

## Architectural Analysis

Caikit follows a modular plugin architecture where AI capabilities are organized as "modules" implementing task-specific interfaces. The core framework (`caikit` package) provides the module system, data model types, and configuration management via `alchemy-config`, while the runtime layer (`caikit.runtime`) provides transport options as optional extras. The separation of core framework from runtime extras (`runtime-grpc`, `runtime-http`, `runtime-trace`, `runtime-client`) in pyproject.toml demonstrates a clean dependency architecture — deployment configurations determine which transport and observability capabilities are active, and the core framework carries no transport dependencies beyond base `grpcio` and `protobuf`.

The ModelMesh integration is architecturally central: caikit acts as the model runtime sidecar in the ModelMesh serving pattern. ModelMesh handles model placement, scaling, and routing across a cluster of pods, while caikit handles the actual model loading, unloading, and inference execution within each pod. The proto files define this bidirectional relationship — ModelMesh calls `mmesh.ModelRuntime` RPCs on caikit (loadModel, unloadModel, runtimeStatus), and caikit can call `mmesh.ModelMesh` RPCs for model registration and virtual model management. The `runtimeStatus` RPC is particularly noteworthy: it is called only during startup and requires the runtime to purge any stale loaded models before returning READY, ensuring consistency after unexpected restarts. The virtual model (vmodel) API enables zero-downtime model updates by maintaining active/target model pairs with atomic transitions.

The `processproto.Process` proto reveals integration with IBM's Model-Train Dynamic Workflow (DWF) system for training pipelines. Caikit can serve as a process step in DWF, receiving training data via COS storage paths (both training-level and workflow-level) and returning results. This positions caikit as both a serving runtime and a training execution engine.

No authentication mechanism is defined at the protobuf level. The `mmesh.ModelRuntime` service is explicitly described as an "internal sidecar API for interfacing with a colocated model runtime container," indicating pod-local communication where network-level authentication is unnecessary. External-facing authentication for model inference endpoints exposed to users is handled by the RHOAI platform's ingress infrastructure (kube-rbac-proxy sidecars or gateway-level auth), not by caikit itself. The inclusion of `tls_test_tools` in dev-test dependencies confirms TLS is configurable at the transport level through caikit's runtime configuration, but the proto definitions carry no auth interceptors or token fields.

The entry points defined in pyproject.toml (`caikit-runtime`, `caikit-health-probe`, `caikit-render-interfaces`) show three distinct operational modes: the main runtime server, a health probe for Kubernetes liveness/readiness checks, and a utility for dumping generated service interface definitions. The health probe is a separate binary rather than an endpoint on the main server, which is a common pattern for gRPC services where HTTP health endpoints may not be available.
