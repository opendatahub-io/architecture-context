## Purpose

**Short**: Caikit is a Python AI toolkit and runtime framework that enables serving AI/ML models through task-specific gRPC and HTTP APIs with a modular, composable architecture.

**Detailed**: Caikit provides an abstraction layer between AI model implementations and application consumers. Rather than requiring applications to understand tensor-level model interfaces, Caikit defines task-oriented APIs (text generation, classification, embeddings, reranking, time series forecasting, etc.) that present data in domain-specific structures. Model authors implement "modules" that register against tasks, and Caikit's runtime dynamically generates gRPC and HTTP service endpoints for all registered modules.

The framework consists of three layers: (1) a **core** layer providing the module system, data model abstractions with automatic protobuf generation, task definitions, pluggable backends, and model lifecycle management; (2) an **interfaces** layer defining domain-specific tasks and data models for NLP, time series, and vision; and (3) a **runtime** layer that builds dual-protocol (gRPC + HTTP/REST) servers, integrates with ModelMesh for multi-model serving, provides health probes, Prometheus metrics, OpenTelemetry tracing, and request batching.

In the RHOAI platform, Caikit serves as the core runtime framework used by downstream components like `caikit-nlp` and `caikit-tgis-serving` to serve large language models behind KServe's model serving infrastructure. It is not deployed as a standalone container itself but is consumed as a Python library dependency.

## Architectural Analysis

Caikit's most distinctive architectural feature is its **dynamic service generation** system. Rather than defining API endpoints statically, the runtime introspects all registered modules and their task decorators at startup, then automatically generates gRPC service descriptors and HTTP route handlers for every module's inference and training methods. This means adding a new task (e.g., `@task` with `TextGenerationTask`) and a module implementing it (`@module` with `@TaskBase.taskmethod`) automatically exposes new API endpoints without changing any server code. The service generation machinery in `caikit/runtime/service_generation/` handles proto message construction, request/response type mapping, and streaming configuration based entirely on the task and module signatures.

The **dual-protocol architecture** (gRPC + HTTP) with shared servicer logic is well-designed for platform integration. The `GlobalPredictServicer` handles the core inference logic (model lookup, request unmarshalling, inference execution, response marshalling) while both the gRPC server and HTTP server delegate to it. This ensures consistent behavior across protocols. The HTTP server uses FastAPI with support for both `application/json` and `multipart/form-data` content types, and provides Server-Sent Events (SSE) for streaming responses — a pragmatic choice for HTTP streaming that avoids WebSocket complexity.

The **ModelMesh integration** via Unix socket gRPC follows the ModelMesh ServingRuntime contract (`model-runtime.proto`). Caikit implements the `ModelRuntime` service which ModelMesh calls to load/unload models and query runtime capacity. This integration is critical for RHOAI's multi-model serving architecture where ModelMesh orchestrates model placement across Caikit runtime pods. The `PredictModelSizeResponse` mechanism enables ModelMesh to make intelligent scheduling decisions based on model memory requirements.

The **data model system** with automatic protobuf generation from Python dataclasses (`@dataobject` decorator using `py_to_proto`) is architecturally significant. It eliminates the traditional workflow of maintaining `.proto` files separately from Python code, instead generating protobuf descriptors dynamically at import time. While this simplifies development, it means the gRPC API surface is determined at runtime rather than at build time, which has implications for API stability and contract testing. The `DataBase` metaclass (`_DataBaseMetaClass`) is complex — it auto-generates `__init__`, property getters, and `__slots__` from protobuf descriptors, and handles oneOf fields, nested messages, and enum mappings.

The **health probe architecture** is notable: Caikit ships a separate `caikit_health_probe` package (installed as the `caikit-health-probe` CLI entry point) that runs as an independent process. It performs readiness checks by making actual gRPC Health.Check and HTTP /health requests to the runtime, and performs liveness checks by detecting the Caikit process via `psutil`. This separation means the health probe doesn't share the runtime's event loop or thread pool, ensuring it can detect deadlocks or resource exhaustion in the main process. The probe supports TLS/mTLS certificate validation matching the runtime's configuration, including a creative fallback that extracts SANs from the server certificate to construct proper hostnames for TLS verification.
