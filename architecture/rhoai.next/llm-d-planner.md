## Purpose

**Short**: LLM deployment planning platform that guides users from business requirements to production-ready Kubernetes deployments through conversational intent extraction, SLO-driven GPU/model recommendations, and automated YAML generation.

**Detailed**: llm-d Planner is a full-stack web application that unifies three core capabilities for LLM deployment planning: (1) a **Planner** workflow that extracts deployment intent from natural language, maps it to traffic profiles and SLO targets, queries a benchmark database, and produces ranked model+GPU recommendations; (2) a **Capacity Planner** that estimates GPU memory requirements (model weights, KV cache for MHA/GQA/MQA/MLA attention, activation memory, CUDA graph overhead) for any HuggingFace model; and (3) a **GPU Recommender** that estimates inference performance (TTFT, ITL, throughput) across GPU types using BentoML's llm-optimizer roofline model.

The system is composed of a FastAPI backend exposing REST endpoints under `/api/v1/`, a Streamlit frontend for interactive use, a PostgreSQL database storing benchmark data, and an Ollama instance for LLM-powered intent extraction. It supports deploying generated KServe/vLLM configurations to Kubernetes clusters and includes a GPU-free vLLM simulator for development. The backend integrates with the RHOAI Model Catalog for benchmark data sourcing and supports multiple LLM providers (Ollama, Vertex AI, OpenAI-compatible) for intent extraction. It can generate deployment manifests for both standalone vLLM (KServe InferenceService) and the llm-d stack (kustomize overlay + Helm values).

## Purpose

**Short**: llm-d-planner is an LLM deployment planning tool that recommends GPU configurations, estimates performance, and manages deployments on Kubernetes clusters via a FastAPI backend, Streamlit UI, local Ollama inference, and PostgreSQL persistence.

**Detailed**: llm-d-planner provides an interactive capacity-planning and deployment-recommendation workflow for LLM workloads. The FastAPI backend (`backend`) exposes 33 HTTP endpoints covering intent extraction, GPU recommendation, cost estimation, SLO-aware ranking, deployment lifecycle management, and cluster status queries. It connects to a co-deployed PostgreSQL instance for persistent storage of deployment records and benchmark data, and to a co-deployed Ollama server (with GPU, running `granite3.3:2b`) for local LLM inference used in intent extraction and recommendation logic. The backend also integrates with external LLM providers (OpenAI-compatible APIs, Google Vertex AI, Anthropic) as configurable alternatives via environment variables and secrets. A `planner-gpu-reader` ClusterRole grants the backend read access to cluster nodes for GPU discovery. The Streamlit-based UI (`ui`) provides the user-facing dashboard. Two OpenShift Routes expose the UI and backend externally with TLS termination.

## Data Flows

- **User request path:** External users reach the Streamlit UI via the `planner` OpenShift Route (TLS-terminated). The UI calls the FastAPI backend through the `planner-backend` Route. All backend API endpoints are served on port 8000/TCP.
- **LLM inference chain:** When a user submits a planning request (e.g., `/api/v1/extract`, `/api/v1/recommend`), the backend routes inference to one of several configurable LLM providers: the co-deployed Ollama service at `ollama:11434` (default, using `granite3.3:2b`), an OpenAI-compatible API via `OPENAI_BASE_URL`, or Google Vertex AI via GCP credentials. The provider is selected by the `LLM_PROVIDER` ConfigMap key.
- **Data persistence:** The backend writes deployment records, benchmark data, and configuration state to the co-deployed PostgreSQL database at `postgres:5432` using the `psycopg2` driver. Database credentials come from `planner-secrets`.
- **Cluster introspection:** The backend queries the Kubernetes API (via the `kubernetes` Python client and `planner-gpu-reader` ClusterRole) to list cluster nodes and discover available GPU resources for capacity planning.
- **Model catalog:** The backend optionally retrieves model metadata from Hugging Face Hub using `HF_TOKEN` for model catalog lookups and parameter extraction.

## Architectural Analysis

llm-d Planner follows a clean **three-tier architecture** — Streamlit frontend, FastAPI backend, PostgreSQL database — with the backend acting as the sole integration point for all external services. The UI never communicates directly with Ollama, HuggingFace, or Kubernetes; everything is proxied through the backend API. This simplifies deployment security since only the backend pod needs network egress and RBAC permissions.

The **recommendation engine** is the system's intellectual core. It implements a multi-stage pipeline: (1) LLM-powered intent extraction converts natural language into structured `DeploymentIntent` schemas, (2) a traffic profile generator maps use cases to GuideLLM benchmark configurations with experience-class-driven SLO targets, (3) a `ConfigFinder` queries the benchmark database for exact matches on (model, GPU, traffic profile) tuples and fills gaps with BentoML roofline estimates, (4) a multi-criteria scorer evaluates each configuration on accuracy, price, latency, and complexity, and (5) an `Analyzer` produces five ranked views (balanced, best accuracy, lowest cost, lowest latency, simplest). This design makes the recommendation pipeline extensible — new scoring dimensions or estimation backends can be added without restructuring the workflow.

The **capacity planner** module is notably well-engineered, with accurate memory estimation that accounts for MHA/GQA/MQA/MLA attention types (including DeepSeek-V2/V3 compressed KV), quantization effects (GPTQ, FP8, MXFP4), multi-level parallelism (TP × PP × DP), and calibrated activation memory profiles from 49 empirical vLLM runs across 28 models. The constants are externalized in `vllm_memory_constants.json`, making recalibration possible without code changes.

The **LLM provider abstraction** uses Python's structural typing (`Protocol` class) to define a provider-agnostic interface, with factory-based selection via the `LLM_PROVIDER` environment variable. This allows swapping between Ollama (local, default), Vertex AI (Claude), and OpenAI-compatible endpoints without code changes — a pragmatic design for environments where GPU-based Ollama may not be available.

A significant **security gap** exists: the backend has no authentication on most endpoints and configures CORS to allow all origins (`allow_origins=["*"]`). In production, this relies entirely on OpenShift Route TLS termination and namespace-level NetworkPolicy for protection. The only authenticated endpoints are the database management routes (`/db/upload-benchmarks`, `/db/reset`), which use HMAC password comparison via the `X-Admin-Password` header. The RHOAI Model Catalog integration includes proper TLS handling with custom CA bundles and ServiceAccount token auto-discovery. Additionally, no Konflux Dockerfiles exist — the component uses standard `python:3.14-slim` base images rather than UBI, which is a prerequisite for RHOAI product shipping through Konflux pipelines.

## Architectural Analysis

llm-d-planner follows a classic multi-tier web application pattern deployed as a set of co-located Kubernetes workloads within a single `planner` namespace. The architecture separates concerns into four deployment units — a FastAPI backend for business logic, a Streamlit frontend for user interaction, a PostgreSQL database for persistence, and an Ollama server for local LLM inference — all connected via ClusterIP services.

The most architecturally significant aspect is the pluggable LLM provider design. The backend supports multiple inference backends (Ollama, OpenAI-compatible, Google Vertex AI, Anthropic) selected at runtime via the `LLM_PROVIDER` environment variable. This allows the planner to operate in air-gapped environments (using the co-deployed Ollama with `granite3.3:2b`) or leverage external cloud LLM services when available. The Ollama deployment requests a GPU (`nvidia.com/gpu: 1`) and uses a 20Gi PersistentVolumeClaim for model storage, making it the most resource-intensive component.

Security posture is minimal: the backend runs as non-root with `seccompProfile: RuntimeDefault` and drops all capabilities, but the API endpoints themselves have no authentication enforcement beyond the health probe exemption. The `planner-secrets` Opaque secret centralizes credentials for PostgreSQL, Hugging Face, OpenAI, GCP, and admin access, but several keys are optional. A `planner-service-ca` ConfigMap volume mount suggests integration with the OpenShift service CA operator for TLS trust, though its use within the application is not confirmed from manifest evidence alone.

The backend's `CORS_ORIGINS=*` setting permits cross-origin requests from any domain, which is appropriate for development but would need restriction for production deployments. The Kubernetes API access is tightly scoped — the `planner-gpu-reader` ClusterRole grants only `list` on `nodes`, sufficient for GPU discovery without broader cluster access.
