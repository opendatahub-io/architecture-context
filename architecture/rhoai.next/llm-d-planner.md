## Purpose

**Short**: An LLM deployment planning platform that guides users from business requirements to production-ready Kubernetes deployments through conversational AI, SLO-driven capacity planning, and GPU recommendation.

**Detailed**: llm-d-planner is an end-to-end LLM deployment planning service that unifies model selection, GPU sizing, performance estimation, and Kubernetes configuration into a single workflow. It exposes three core capabilities: a conversational planner that translates natural language use-case descriptions into SLO-driven deployment recommendations, a capacity planner that estimates GPU memory requirements for any HuggingFace model, and a GPU recommender that estimates inference performance across GPU types without running benchmarks.

The system deploys as a three-component architecture: a FastAPI backend (port 8000) that hosts the REST API and planning engines, a Streamlit UI (port 8501) providing a conversational chat interface with multi-tab recommendation display, and an Ollama LLM service (port 11434) used for intent extraction from natural language. The backend integrates with external services including the Kubernetes API for cluster GPU detection and deployment, OpenAI-compatible APIs for LLM inference, HuggingFace Hub for model metadata, and optionally the RHOAI Model Catalog for benchmark data. A vLLM simulator service supports GPU-free local development with realistic latency simulation.

The platform is also available as a Python library (`pip install llm-d-planner`) that exposes the full recommendation pipeline as method calls without requiring the web services infrastructure.

## Architectural Analysis

llm-d-planner follows a layered service architecture with clear separation between presentation (Streamlit UI), API gateway (FastAPI), core planning engines, and data access (Knowledge Base). The design centers on an SLO-driven pipeline that transforms conversational user input through four stages: intent extraction via LLM, specification generation with traffic profiles and SLO targets, multi-criteria recommendation scoring (quality/price/latency), and Kubernetes deployment generation with KServe/vLLM templates.

A notable architectural pattern is the dual data-source quality scoring system that composites Arena human preference rankings with Artificial Analysis automated benchmarks, normalized to percentile ranks and weighted per use case. This provides model quality assessment without requiring the user to run their own benchmarks.

The deployment model is straightforward: three Kubernetes Deployments in a dedicated `planner` namespace with OpenShift Routes for external access. The backend stores benchmark data in an embedded SQLite database on a PersistentVolumeClaim, and all configuration is externalized through ConfigMaps and Secrets. The optional Model Catalog integration uses the OpenShift service-serving CA for TLS trust, demonstrating awareness of the RHOAI platform environment.

Security-wise, the application has no authentication middleware on its FastAPI endpoints beyond a simple password check (via `hmac.compare_digest`) on database admin operations. All API routes are unauthenticated, with TLS termination delegated to OpenShift Routes at the edge. The CORS middleware is configured with `allow_origins=["*"]`, indicating the component is not yet hardened for multi-tenant production use. The README explicitly lists "Security Hardening" as a future enhancement.

The component has no Konflux Dockerfiles, no FIPS build signals, and uses upstream `python:3.14-slim` as the base image rather than UBI. This positions it as an incubation-stage project that has not yet completed productization for RHOAI downstream release.
