## Purpose

**Short**: LLM deployment planning service that recommends optimal model/GPU configurations based on use-case requirements, SLO targets, and benchmark data.

**Detailed**: llm-d-planner is a multi-component Python service that helps users navigate LLM deployments from concept to production. It provides an end-to-end workflow: users describe their deployment requirements in natural language (e.g., "I need a chatbot for 1000 users"), and the system extracts intent via an LLM, generates traffic profiles and SLO targets, queries a PostgreSQL benchmark database for configurations meeting those SLOs, scores each configuration across four criteria (accuracy, price, latency, complexity), and produces ranked recommendations with deployable Kubernetes YAML.

The system consists of three deployable images: a FastAPI backend API (port 8000) that orchestrates the recommendation workflow and generates KServe InferenceService manifests or llm-d kustomize overlays, a Streamlit UI (port 8501) that provides an interactive frontend for conversational deployment planning and GPU capacity analysis, and a vLLM simulator (port 8080) that provides a mock OpenAI-compatible API for GPU-free development and testing. The backend integrates with multiple LLM providers (Ollama, OpenAI-compatible APIs, Vertex AI) for intent extraction, queries HuggingFace for model metadata, uses BentoML's llm-optimizer for roofline performance estimation, and can optionally sync benchmark data from RHOAI's Model Catalog API.

The planner is designed to deploy into an OpenShift cluster alongside the RHOAI platform, where it can detect available GPU types from cluster nodes and deploy recommended configurations as KServe InferenceService resources or llm-d scheduler stacks. It supports both standalone PostgreSQL-backed benchmark data and live integration with the RHOAI Model Catalog for validated model performance metrics.

## Architectural Analysis

The llm-d-planner implements a layered architecture with clear separation between API presentation, orchestration, and domain logic. The `RecommendationWorkflow` class in `orchestration/workflow.py` acts as the central coordinator, composing five domain services: `IntentExtractor` for NLU, `TrafficProfileGenerator` for SLO/traffic derivation, `ConfigFinder` for capacity planning, `Scorer` for multi-criteria evaluation, and `Analyzer` for ranking. This composition pattern makes the workflow testable and allows each service to evolve independently.

The multi-criteria scoring engine is notably sophisticated for an incubation-stage project. It scores configurations on four axes — accuracy (from use-case-specific weighted CSV benchmarks sourced from Artificial Analysis data, with fuzzy model name matching and quantization discount factors), price (non-linear formula `100 * (1 - (cost/max_cost)^0.7)` that rewards cheaper configs disproportionately), latency (capped range scoring with separate TTFT/ITL/E2E components weighted 0.34/0.33/0.33), and complexity (predefined scores inversely proportional to GPU count). The balanced score uses configurable weights defaulting to 0.40/0.40/0.10/0.10 (accuracy/price/latency/complexity). The `ConfigFinder` includes a roofline fallback via BentoML's llm-optimizer: when PostgreSQL benchmarks don't cover a model/GPU combination, it runs analytical performance estimation and persists results back to the database as `estimated` confidence level records, creating a self-expanding knowledge base.

The deployment generation layer supports two output stacks: traditional KServe InferenceService YAML (with HPA and ServiceMonitor) generated via Jinja2 templates, and an llm-d kustomize overlay stack that references the upstream llm-d recipe repository and generates kustomization.yaml, patch-vllm.yaml, and scheduler values.yaml for the llm-d inference scheduler. The KServe templates include a simulator mode that swaps the vLLM container image for the built-in simulator image, enabling end-to-end testing without GPUs. The generated manifests include GPU-specific node selectors, tolerations, resource requests, and vLLM tuning parameters (max-model-len, tensor-parallel-size, gpu-memory-utilization) that are derived from the recommendation engine's analysis.

A significant architectural decision is the dual benchmark source model: the system can operate with a local PostgreSQL database loaded with pre-computed benchmark JSON files (BLIS, interpolated, estimated), or it can sync benchmark data live from the RHOAI Model Catalog API at startup. The Model Catalog integration uses a background thread with retry logic (exponential backoff with jitter) and TLS verification via OpenShift's service-serving CA. This dual mode enables both standalone development and production integration with the RHOAI platform. The Model Catalog client (`model_catalog_client.py`) implements connection pooling via httpx, client-level caching with 3600s TTL, and thread-safe initialization.

The security posture has notable gaps for a production RHOAI component. The base images are upstream `python:3.14-slim` rather than UBI, meaning no FIPS compliance or check-payload validation. The API has no authentication except optional HMAC password for database admin operations — all recommendation, deployment, and cluster management endpoints are unauthenticated. The `uv.lock` file is gitignored despite being required for hermetic builds. The Kubernetes integration uses kubectl subprocess calls rather than the Python client library for most operations, which is pragmatic but limits error handling granularity. The deployment manifests do apply good pod security practices (runAsNonRoot, drop ALL capabilities, RuntimeDefault seccomp). For RHOAI productization, the component would need Konflux Dockerfiles with UBI base images, committed lock files, and authentication on API endpoints.
