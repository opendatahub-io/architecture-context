## Purpose

**Short**: Sidecar container that bridges ModelMesh model lifecycle management with third-party ML inference runtime servers (Triton, MLServer, OVMS, TorchServe) and pulls model artifacts from cloud storage.

**Detailed**: ModelMesh Runtime Adapter is a multi-purpose sidecar image that runs inside every ModelMesh Serving model server pod. It contains five Go binaries — a model-serving puller and four runtime-specific adapters — all compiled into a single container image with no defined entrypoint; the consuming pod spec selects which binary to run.

The **puller** component implements the ModelRuntime gRPC interface on port 8084, intercepts model load/unload requests from ModelMesh, downloads model artifacts from cloud storage backends (S3, GCS, Azure Blob, HTTP, PVC) into a local directory, and then proxies the request to the downstream runtime adapter on port 8085. The **PullMan** library provides a plugin-based storage abstraction with client caching, credential management via mounted Kubernetes Secrets, and support for mTLS.

The four **runtime adapters** (Triton, MLServer, OVMS, TorchServe) each implement the same ModelRuntime gRPC interface on port 8085, adapting model layouts (symlinks, config files, directory structures) to each runtime's expected format before instructing the runtime to load models via its native API (gRPC for Triton/MLServer/TorchServe, REST for OVMS). The image also includes Python (3.11) and TensorFlow for Keras-to-SavedModel conversion used by the Triton adapter.

## Purpose

**Short**: modelmesh-runtime-adapter is a Go/Python sidecar adapter that bridges ModelMesh to multiple model serving runtimes (Triton, MLServer, TorchServe) via gRPC protocol translation and model artifact retrieval from cloud object storage.

**Detailed**: modelmesh-runtime-adapter implements the `mmesh.ModelRuntime` gRPC service interface so that ModelMesh can load, unload, and invoke models without runtime-specific knowledge. For each supported runtime—NVIDIA Triton Inference Server, Seldon MLServer, and TorchServe—the adapter maintains a dedicated gRPC client that translates the ModelMesh lifecycle commands into the runtime's native protocol (KServe Predict V2 for Triton and MLServer, TorchServe Management/Inference APIs for TorchServe). A companion "puller" component downloads model artifacts from cloud object storage (Azure Blob Storage, Google Cloud Storage, IBM Cloud Object Storage / S3-compatible) before the runtime loads them. The adapter runs as a sidecar container within the same pod as the model runtime, communicating over localhost gRPC. It is part of the KServe ecosystem (Go module `github.com/kserve/modelmesh-runtime-adapter`) and depends on the ModelMesh and KServe platform components for orchestration and inference protocol standardization.

## Data Flows

- **Inbound from ModelMesh:** ModelMesh invokes the adapter's `mmesh.ModelRuntime` gRPC service to issue model lifecycle commands—`loadModel`, `unloadModel`, `modelSize`, `predictModelSize`, and `runtimeStatus`. These calls arrive over localhost gRPC within the shared pod network namespace.
- **Model artifact retrieval:** When a `loadModel` request arrives, the puller component downloads the model artifact from the configured cloud object storage backend (Azure Blob Storage, Google Cloud Storage, or IBM Cloud Object Storage / S3-compatible) to local storage accessible by the runtime container.
- **Outbound to model runtimes:** After artifact retrieval, the adapter forwards runtime-specific gRPC commands to the co-located model serving process. For Triton, it calls `inference.GRPCInferenceService` (KServe Predict V2). For MLServer, it calls the MLServer variant of `inference.GRPCInferenceService` (also KServe Predict V2 with repository extensions). For TorchServe, it calls `InferenceAPIsService` and `ManagementAPIsService`.
- **Inference passthrough:** Inference requests routed by ModelMesh through the adapter are translated to the runtime's native gRPC protocol and forwarded, with responses returned back through the same chain.
- **Security context:** All gRPC services exposed by the adapter have no application-level authentication interceptors configured; security enforcement is expected to be provided by the enclosing ModelMesh pod-level network policies and the platform's ingress layer.

## Architectural Analysis

The ModelMesh Runtime Adapter follows a **multi-binary sidecar pattern** where five Go binaries are compiled into a single container image. The image has no default entrypoint; instead, the consuming pod spec selects which binary to execute via its `command:` field. This design minimizes image count and registry footprint while supporting four distinct inference runtimes. The puller and one adapter run as separate processes within the same pod, communicating exclusively over loopback gRPC — the puller on port 8084 receiving requests from ModelMesh, and the selected adapter on port 8085 managing the target runtime.

The **PullMan library** (`pullman/`) implements a clean plugin architecture for storage providers. Each provider registers itself and implements the `StorageProvider` interface with `GetKey` (credential hashing), `NewRepository` (client construction), and download methods. A cache layer (`pullman/cache.go`) reuses storage clients by credential hash with a 1-hour TTL and 4-hour cleanup cycle, which avoids reconnecting to cloud storage for every model load. Storage credentials flow from Kubernetes Secrets mounted at `/storage-config`, with per-request `storage_params` in the `ModelKey` JSON able to override or supplement the mounted config. This credential layering (mounted secret → per-request override) gives flexibility without hardcoding storage details.

The **OVMS adapter stands apart architecturally** from the other three adapters. While Triton, MLServer, and TorchServe adapters interact with their runtimes via gRPC, the OVMS adapter uses REST HTTP to communicate with OpenVINO Model Server. More significantly, it implements an **actor-based batching pattern** (`modelmanager.go`) where model load and unload operations are queued and batched within a configurable time window (100ms–3s). The actor writes a JSON config file (`model_config_list.json`) containing all models and calls OVMS's `/v1/config/reload` endpoint, then polls `/v1/config` to verify each model reaches its expected state. This batching is necessary because OVMS loads its model configuration from a single file rather than individual repository operations.

All inter-process communication within the pod uses **plaintext gRPC with insecure credentials**. This is architecturally intentional — the puller, adapter, and runtime all share a pod network namespace, so loopback traffic never leaves the pod boundary. Security is enforced at the pod level by Kubernetes network isolation, not within the adapter. The only encrypted traffic is outbound to cloud storage, where the SDKs use TLS by default. The HTTP provider additionally supports mTLS with client certificates for private model repositories. The FIPS posture is strong at build time (CGO_ENABLED=1, GOEXPERIMENT=strictfipsruntime, -tags strictfipsruntime) with no application-level non-FIPS crypto detected.

The inclusion of **Python 3.11 and TensorFlow 2.19.0** in the runtime image is solely for the Triton adapter's Keras-to-SavedModel conversion feature (`tf_pb.py`). This adds significant image size but enables users to serve Keras H5 models via Triton without manual conversion. The conversion runs as a subprocess with a concurrency semaphore (`MAX_CONC_KERAS_CONV_PROCS=2`) to prevent OOM. The Python dependencies are pinned via `requirements.txt` from `pip freeze` output, and the Konflux build uses prefetch for hermetic builds. The TensorFlow dependency does not currently use AIPCC base images, which is worth tracking for future security hardening.

## Architectural Analysis

The modelmesh-runtime-adapter follows a sidecar adapter pattern: it runs within the same pod as a model serving runtime and presents a uniform gRPC interface (`mmesh.ModelRuntime`) to ModelMesh while translating commands to the runtime's native protocol. This decouples ModelMesh from the specifics of each runtime (Triton, MLServer, TorchServe), allowing new runtimes to be supported by adding a new adapter implementation without modifying the core ModelMesh orchestration logic.

The repository is organized as a Go monorepo with separate adapter implementations under `model-mesh-triton-adapter/`, `model-mesh-mlserver-adapter/`, and `model-mesh-torchserve-adapter/`, plus a shared `model-serving-puller/` for artifact retrieval and `pullman/` for multi-provider storage abstraction (Azure, GCS, S3/IBM COS). Proto definitions are vendored from upstream projects—KServe Predict V2, MLServer, TorchServe, and ModelMesh—rather than imported as Go module dependencies, which pins the protocol definitions and avoids transitive dependency sprawl. The `go.mod` comment on the `controller-runtime` dependency (line 21: "controller-runtime dependency is only used for logging") indicates this is a pure application service, not a Kubernetes operator, despite importing controller-runtime.

The adapter has no application-level authentication or TLS configuration on its gRPC services. This is architecturally intentional: the adapter communicates exclusively over localhost within the pod network namespace, and all external access is mediated by ModelMesh and the platform's ingress and auth layers. The absence of network-level encryption on the adapter's own gRPC listeners is therefore a sidecar trust boundary decision rather than a security gap, though it means compromise of any process within the pod grants unauthenticated access to the model runtime.

The dual-language nature (Go for adapters and puller, Python for TensorFlow-related utilities in `requirements.txt`) reflects the need for TensorFlow protobuf generation tooling alongside the Go service binaries. The Python dependencies (TensorFlow, Keras, NumPy) are build-time utilities, not runtime service dependencies of the Go adapters.
