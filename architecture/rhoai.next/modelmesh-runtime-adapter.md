## Purpose

**Short**: Sidecar container providing model storage retrieval and runtime-specific adaptation for ModelMesh Serving pods.

**Detailed**: The ModelMesh Runtime Adapter is a multi-purpose sidecar image that runs alongside model serving runtime containers (Triton, MLServer, OVMS, TorchServe) in ModelMesh Serving pods. It contains two logical layers: a **model-serving-puller** that downloads ML models from cloud storage (S3, GCS, Azure Blob, HTTP, PVC) into the pod's local filesystem, and four **runtime adapters** that translate the generic ModelMesh `ModelRuntime` gRPC protocol into runtime-specific APIs.

Each adapter implements the `mmesh.ModelRuntime` gRPC service, receiving `LoadModel`/`UnloadModel`/`RuntimeStatus` RPCs from the ModelMesh controller. On load, it first pulls the model from remote storage (if the embedded puller is enabled), then adapts the model file layout into the format expected by the target runtime (e.g., creating `config.pbtxt` for Triton, `model-settings.json` for MLServer), and finally registers the model with the runtime server via the runtime's native API. This architecture decouples ModelMesh's model lifecycle management from the specifics of each inference server, allowing ModelMesh to treat all runtimes uniformly.

The single container image ships five Go binaries (`puller`, `triton-adapter`, `mlserver-adapter`, `ovms-adapter`, `torchserve-adapter`) with no defined entrypoint — the consuming deployment specifies which binary to run. Python 3.11 and TensorFlow are also installed in the image for Keras-to-TensorFlow model conversion used by the Triton adapter.

## Architectural Analysis

The modelmesh-runtime-adapter follows a **sidecar adapter pattern** that cleanly separates model lifecycle management from inference serving. ModelMesh Serving treats all runtimes identically through the `mmesh.ModelRuntime` gRPC contract (defined in `model-runtime.proto`), while each adapter handles the impedance mismatch between this generic protocol and each runtime's native API. This is an effective architectural choice — it allows ModelMesh to add support for new inference servers by adding a new adapter binary without modifying the core controller.

The **pullman storage framework** (`pullman/` package) is well-designed with a provider registration pattern (`init()` functions), client caching with TTL (1-hour default, 4-hour cleanup), and pluggable backends. However, the storage credential resolution chain (`storage_key` → filesystem → defaults) is complex and could be a source of misconfiguration. The PVC provider stands out as a zero-copy approach using symlinks rather than downloading files, which is efficient for models already on persistent storage.

A notable design decision is shipping **all five binaries plus Python/TensorFlow in a single container image** rather than separate images per adapter. This simplifies image management (one image to build, scan, and distribute) but results in a large image — TensorFlow 2.19.0 alone adds hundreds of megabytes, yet it's only used by the Triton adapter for Keras conversion. The `MAX_CONC_KERAS_CONV_PROCS` semaphore (default 2) suggests that Keras conversion is resource-intensive and must be throttled.

The OVMS adapter's **actor-based request batching** (`modelmanager.go`) is architecturally distinct from the other adapters. Rather than calling the runtime immediately on each load/unload request, it coalesces requests over a configurable window (100ms–3s), updates a single `model_config_list.json` file, and triggers a single reload via HTTP. This is necessary because OVMS reloads its entire configuration atomically — calling reload for every individual model would be inefficient. The tradeoff is increased latency for individual loads.

All internal communication (puller ↔ adapter, adapter ↔ runtime) uses **plaintext gRPC/HTTP on localhost**. This is acceptable because all processes run within the same pod and share the pod's network namespace — there is no cross-node traffic. Security is enforced at the pod boundary by ModelMesh Serving's network policies and Kubernetes RBAC. However, this means that any container compromise within the pod grants access to all model data and storage credentials.

The TorchServe adapter has a **deferred size computation** pattern that is unique: `LoadModel` returns `SizeInBytes: 0` to allow immediate model use, then ModelMesh later calls `ModelSize()` which polls TorchServe's `DescribeModel` up to 16 times (1-second interval) to get the actual worker memory usage. This accommodates TorchServe's asynchronous model loading behavior but introduces a window where ModelMesh's capacity tracking is inaccurate.
