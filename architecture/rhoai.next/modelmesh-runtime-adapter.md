## Purpose

**Short**: Sidecar container that bridges ModelMesh with third-party model serving runtimes by translating the ModelRuntime gRPC protocol and pulling model artifacts from cloud storage.

**Detailed**: modelmesh-runtime-adapter is a multi-purpose sidecar image that runs inside each ModelMesh Serving model server Pod. It contains two main functional layers: a **model-serving-puller** that downloads model artifacts from various cloud storage backends (S3/IBM COS, Azure Blob, GCS, HTTP, PVC) and a set of **runtime adapters** (for Triton Inference Server, MLServer, OpenVINO Model Server, and TorchServe) that implement the `mmesh.ModelRuntime` gRPC interface. Each adapter translates ModelMesh lifecycle commands—load, unload, predict size, runtime status—into the corresponding runtime-specific gRPC calls.

The puller and adapters are compiled into separate Go binaries and bundled into a single container image alongside a Python 3.11 runtime with TensorFlow for Keras-to-SavedModel conversion (used by the Triton adapter). At runtime, the ModelMesh controller selects which binary to execute as the Pod entrypoint via container command configuration. The puller sits in the gRPC request path as an intercepting proxy: ModelMesh calls the puller, which downloads the model from storage before forwarding the `LoadModel` request to the actual runtime adapter. All inter-process gRPC communication is localhost-bound and plaintext, with network-level security delegated to the ModelMesh service mesh and Kubernetes network policies.

## Architectural Analysis

The repository follows a monorepo adapter pattern where each supported inference runtime has its own top-level directory (`model-mesh-triton-adapter/`, `model-mesh-mlserver-adapter/`, `model-mesh-ovms-adapter/`, `model-mesh-torchserve-adapter/`) containing an independent `main.go` entrypoint and a `server/` package implementing the `mmesh.ModelRuntime` gRPC interface. This shared interface enables ModelMesh to treat all runtimes uniformly while each adapter handles the impedance mismatch with its target runtime's native gRPC API.

The `pullman/` library provides a pluggable storage abstraction with providers for S3 (via IBM COS SDK), Azure Blob, Google Cloud Storage, HTTP/HTTPS, and PVC mounts. The HTTP provider is notable for its explicit TLS support—custom CA certificates and client certificate authentication—while the cloud storage providers delegate TLS to their respective SDK implementations.

A key architectural decision is that all gRPC servers and clients bind exclusively to `localhost`, making this a process-to-process communication pattern within a single Pod. The adapters connect to the inference runtime container's gRPC port as an outbound client, while exposing their own `ModelRuntime` gRPC server for the puller (or ModelMesh) to call. No authentication interceptors are configured on the gRPC servers since all traffic is Pod-internal. This design delegates all external authentication and authorization to the ModelMesh infrastructure layer.

The Python dependency on TensorFlow (installed via `pip` from `requirements.txt`) is solely for the `tf_pb.py` Keras model conversion script used by the Triton adapter. This creates a relatively heavy image (TensorFlow, Keras, numpy) for what is functionally a simple format conversion utility. TensorFlow is not supported on ppc64le or s390x architectures, as noted in the Dockerfile.
