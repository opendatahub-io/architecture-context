## Purpose

**Short**: Standalone operator that reconciles the Trainer CR to deploy and lifecycle-manage upstream Kubeflow Trainer v2 resources on OpenShift via kustomize rendering and Server-Side Apply.

**Detailed**: The trainer-operator is a module controller in the ODH/RHOAI modular architecture. It watches a singleton cluster-scoped `Trainer` CR (`components.platform.opendatahub.io/v1alpha1`) named `default-trainer` and deploys the upstream Kubeflow Trainer v2 control plane — including CRDs, RBAC, the trainer controller-manager Deployment, admission webhooks, ClusterTrainingRuntimes, and ImageStreams — into a configurable applications namespace (default `opendatahub`).

The operator uses the `odh-platform-utilities` framework for reconciliation, condition management, garbage collection, and Server-Side Apply. At build time, upstream trainer manifests are fetched and baked into the container image at `/opt/manifests-template/`. At runtime, the reconciler copies these to a writable work directory, applies `RELATED_IMAGE` overrides from environment variables, renders kustomize overlays (manifests, runtimes, imagestreams), and applies the result with field-owner `trainer-module-controller`. The operator also checks for the JobSet operator as a prerequisite on OpenShift and degrades gracefully if it is missing.

TLS configuration is resolved from the OpenShift cluster TLS profile at startup, with a watcher that triggers a graceful restart when the profile or adherence policy changes. Metrics are served over HTTPS with authn/authz when secure mode is enabled.

## Architectural Analysis

The trainer-operator follows the ODH modular operator pattern: a single-purpose controller that owns a platform component CR and renders upstream manifests through kustomize. The design cleanly separates the operator's own CRD (`Trainer`) from the upstream Kubeflow Trainer CRDs it deploys (`TrainJob`, `TrainingRuntime`, `ClusterTrainingRuntime`, `OptimizationJob`), avoiding confusion between the lifecycle-management API and the training workload APIs.

Cache scoping is carefully hardened. The controller-runtime cache is label-filtered to only watch resources carrying `platform.opendatahub.io/part-of: trainer`, and optionally scoped to the applications namespace via the `APPLICATIONS_NAMESPACE` environment variable. Namespaces are explicitly excluded from the cache (`DisableFor`) to prevent an implicit cluster-wide informer from the `ensureNamespace()` Get call — a deliberate anti-pattern mitigation noted in the source.

The immutable-field recovery wrapper around the deploy action is architecturally significant: when Deployment selector changes are rejected by the API server's immutability check, the controller deletes the offending Deployment and requeues, relying on the next reconcile to recreate it with the new spec. This is necessary for smooth upstream version bumps that change selectors.

The operator's dependency-checking mechanism validates the presence and health of the JobSet operator on OpenShift clusters before proceeding with reconciliation. This is a prerequisite chain — the Kubeflow Trainer controller requires JobSet to function, and the trainer-operator gates its own readiness on this dependency.

A notable design choice is the dual cleanup strategy: garbage collection via label-based discovery handles most resources, but `ClusterTrainingRuntime` and `TrainingRuntime` are marked as "unremovable" by GC and instead cleaned up explicitly through the dynamic client during finalization. This handles a subtlety where the upstream trainer controller's resource-in-use finalizer would prevent deletion through normal GC. The operator also strips legacy finalizers from training runtimes after deploying a new control plane (Trainer 2.3+).

| Network traffic | NetworkPolicy restricts ingress to controller ports; unrestricted egress | Kubernetes NetworkPolicy | Egress is fully open for Kubernetes API access; no per-tenant network isolation within training namespace |

| Configuration & secrets | Per-namespace TrainingRuntime scoping; cluster-wide ClusterTrainingRuntimes shared | Kubernetes namespace isolation | ClusterTrainingRuntimes are shared; any authenticated user can read them |
| API scoping | TrainJob and TrainingRuntime are namespace-scoped; ClusterTrainingRuntime is cluster-scoped (read-only for users) | Kubernetes RBAC + CRD scope | training-view is aggregated to the default view ClusterRole, making training resources visible to all authenticated users |
