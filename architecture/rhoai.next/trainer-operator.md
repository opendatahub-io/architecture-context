## Purpose

**Short**: Component operator that deploys and manages the Kubeflow Trainer V2 controller and its associated ClusterTrainingRuntimes on RHOAI/ODH clusters.

**Detailed**: The trainer-operator is a Kubernetes operator that reconciles a cluster-scoped `Trainer` CR to deploy the Kubeflow Trainer V2 controller, validating webhooks, ClusterTrainingRuntimes, and OpenShift ImageStreams. It acts as a "module operator" within the ODH/RHOAI platform architecture -- the platform operator (rhods-operator or opendatahub-operator) creates the `Trainer` CR, and this operator provisions all downstream resources needed for distributed training workloads.

The operator uses a kustomize-based manifest rendering pipeline: at startup it loads manifest templates from `/opt/manifests-template/`, renders them through kustomize with parameter substitution (image references from RELATED_IMAGE env vars), and applies the resulting resources via server-side apply. It supports RHOAI-specific overlays that add PodMonitor metrics, RBAC aggregation roles for training-edit/training-admin/training-view, and parameterized training runtime images for CUDA, ROCm, and CPU variants.

The operator depends on the JobSet Operator being installed and healthy before it will provision Trainer resources. On OpenShift clusters, it performs a multi-step dependency check: verifying the JobSet Operator OLM subscription, the JobSetOperator CR existence, the CR's health conditions, and the JobSet CRD availability. On plain Kubernetes, it only checks for the JobSet CRD. When dependencies are missing, the operator enters a degraded state with descriptive status conditions and requeues reconciliation every 60 seconds.

## Architectural Analysis

The trainer-operator follows the ODH/RHOAI "module operator" pattern -- a component-specific operator that the platform operator activates by creating a singleton CR. This design isolates the Trainer lifecycle from the platform operator's reconciliation loop, allowing independent release cadence and failure isolation. The operator is lightweight (4 Go source files in `internal/controller/`) because it delegates all training job orchestration to the upstream Kubeflow Trainer V2 controller, which it deploys as a managed sub-component.

The manifest rendering pipeline is notable for its three-layer design. The operator ships with three embedded template directories (`/opt/manifests-template/`, `/opt/runtimes-template/`, `/opt/imagestreams-template/`), each rendered independently through kustomize with separate parameter maps. The RHOAI overlay is hardcoded as the default (`defaultOverlay = "rhoai"` in manifests.go:38), meaning this downstream repo always renders the RHOAI variant. Image references are parameterized through `params.env` files and overridable via `RELATED_IMAGE_*` environment variables -- a pattern that allows Konflux/OLM to inject digest-pinned images at build time without modifying the overlay.

The dependency management for the JobSet Operator is unusually thorough for a component operator. On OpenShift, the operator performs a four-step validation: (1) verify JobSet Operator OLM subscription exists, (2) verify JobSetOperator CR exists with name "cluster", (3) inspect the CR's status conditions for degraded state (checking `Degraded`, `TargetConfigControllerDegraded`, `JobSetOperatorStaticResourcesDegraded` condition types), and (4) verify the JobSet CRD is established. This defense-in-depth approach prevents the operator from deploying the Trainer controller into a cluster where its core dependency (JobSet) is broken, providing clear status conditions that propagate up to the platform operator's health rollup.

The informer cache hardening (cmd/main.go:100-131) demonstrates awareness of the Kubernetes operator OOMKill vulnerability described in the linked Red Hat Developers article. The operator uses label-scoped caches for Deployments, Services, ConfigMaps, and ValidatingWebhookConfigurations, ensuring only trainer-managed resources are cached. It also disables caching for Namespace objects to avoid implicit cluster-wide watches. The `APPLICATIONS_NAMESPACE` environment variable further restricts the cache to a single namespace when set by the platform operator.

The RHOAI overlay ships a comprehensive set of 15+ ClusterTrainingRuntimes covering CUDA 12.8/13.0, ROCm 6.4, and CPU variants across two Training Hub generations (TH05 and TH06). The ImageStreams provide versioned tags (3.4, 3.5) corresponding to RHOAI releases (2026.1, 2026.2), enabling the dashboard to present training runtime images as selectable workbench options.
