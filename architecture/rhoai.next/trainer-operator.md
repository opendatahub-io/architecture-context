## Purpose

**Short**: Manages the lifecycle of the Kubeflow Trainer (V2) component within Red Hat OpenShift AI, deploying and reconciling the upstream training controller, CRDs, ClusterTrainingRuntimes, and ImageStreams.

**Detailed**: The Trainer Operator is a Kubernetes operator built with controller-runtime that manages the deployment of the Kubeflow Trainer V2 ecosystem on RHOAI clusters. It watches a cluster-scoped `Trainer` CRD (named `default-trainer`) and reconciles the full training stack: the upstream Kubeflow Trainer controller-manager deployment, three Kubeflow CRDs (TrainJob, ClusterTrainingRuntime, TrainingRuntime), pre-configured ClusterTrainingRuntimes for PyTorch distributed training (with CUDA, ROCm, and CPU variants), and OpenShift ImageStreams for Training Hub workbench images.

The operator uses kustomize rendering to apply manifests from embedded templates (`/opt/manifests-template/`, `/opt/runtimes-template/`, `/opt/imagestreams-template/`), with image references resolved at runtime from environment variables (set by the RHOAI platform operator). It manages dependency checking — verifying that the JobSet Operator is installed and healthy before proceeding — and implements drift correction by watching downstream Deployments, Services, ConfigMaps, and ValidatingWebhookConfigurations for changes. On deletion, it performs garbage collection of all managed resources including ClusterTrainingRuntimes and TrainingRuntimes.

The operator integrates with the RHOAI platform via the `odh-platform-utilities` library, implementing the `PlatformObject` interface for standardized condition reporting, platform version handshake, and release metadata tracking. It communicates its health via Ready, ProvisioningSucceeded, and Degraded conditions on the Trainer CR status.

## Architectural Analysis

The Trainer Operator follows the RHOAI module pattern, implementing a "meta-operator" that deploys and manages an upstream operator (Kubeflow Trainer V2) as its operand. This is a two-layer operator architecture: the trainer-operator watches the platform-level `Trainer` CR and renders upstream manifests via kustomize, while the upstream kubeflow-trainer-controller-manager watches user-level `TrainJob` CRs and orchestrates distributed training via JobSets. This separation cleanly decouples platform lifecycle management from training workload orchestration.

The manifest rendering pipeline is notably sophisticated for a component operator. Rather than simple `kubectl apply`, the operator copies embedded manifest templates to a writable work directory (`/opt/manifests-work`), applies parameter overrides from `RELATED_IMAGE_*` environment variables (Konflux image pinning), renders via the `odh-platform-utilities/pkg/render/kustomize` library, stamps platform labels and instance annotations on every resource, and then applies via server-side apply with field ownership. The three resource sets (manifests, runtimes, imagestreams) are applied independently, with imagestreams conditionally applied only on OpenShift clusters. ConfigMaps generated by kustomize are filtered out from the runtimes and imagestreams sets to avoid conflicts.

The dependency checking is multi-layered and OpenShift-aware. On OpenShift, the operator checks: (1) JobSet Operator is installed via OLM, (2) the `JobSetOperator` CR exists with name `cluster`, (3) the JobSetOperator CR conditions are healthy (not degraded), and (4) the JobSet CRD itself is established. On vanilla Kubernetes, only the JobSet CRD check is performed. Failed dependency checks set the Trainer CR to Degraded with descriptive messages and requeue after 60 seconds. This ensures the operator does not attempt to deploy the training controller before its dependencies are ready.

Cache hardening deserves special mention. The operator scopes its informer caches using label selectors (`platform.opendatahub.io/part-of: trainer`) for Deployments, Services, ConfigMaps, and ValidatingWebhookConfigurations. This prevents OOMKill attacks where a user with edit permissions creates large objects to exhaust the operator's memory. The cache is also namespace-scoped to `APPLICATIONS_NAMESPACE` when set, and Namespace objects are excluded from caching entirely to avoid implicit cluster-wide informers. The `StripUnusedFields()` transform further reduces cached object sizes.

The runtime image matrix is extensive, covering three accelerator families (CUDA, ROCm, CPU) across two versioning tracks: pinned versions (e.g., `torch-distributed-cuda128-torch29-py312`) and floating "universal" versions (e.g., `torch-distributed` pointing at the latest CUDA 13.0 + PyTorch 2.10 image). The Training Hub variants add Jupyter notebook capabilities on top of the base distributed training images. ImageStreams provide the OpenShift-native mechanism for version-tagged image references across platform releases (3.4 and 3.5 tags). All runtime images are referenced in `params.env` and resolved at kustomize render time, enabling Konflux to pin them to SHA256 digests downstream.
