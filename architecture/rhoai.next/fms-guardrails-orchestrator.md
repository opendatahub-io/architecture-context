## Purpose

**Short**: A Rust-based REST API orchestrator that coordinates AI text generation with content safety guardrails, acting as middleware between clients and language models to enforce detection, filtering, and secure text generation.

**Detailed**: The FMS Guardrails Orchestrator sits between API consumers and backend AI services, intercepting text generation requests and routing them through configurable safety detector pipelines before returning results. It supports both unary and streaming request patterns across two API versions (v1 and v2), with v2 adding standalone detection endpoints for content, chat, context documents, and generated text analysis. The orchestrator also supports OpenAI-compatible chat completions and text completions endpoints with integrated detection.

The server manages connections to three categories of downstream services: text generation backends (TGIS via gRPC or caikit-nlp via gRPC), content chunker services (gRPC), and detector services (REST). Each downstream connection supports independent TLS configuration through a named TLS config system, allowing operators to reuse certificate bundles across multiple services. The orchestrator propagates configurable HTTP headers to downstream services and can rewrite `X-Forwarded-Access-Token` headers into `Authorization: Bearer` tokens for seamless integration with token-forwarding proxies.

The component is built as a single stateless binary deployed on UBI 9 minimal PQC base images, with multi-architecture support for amd64, ppc64le, and s390x. It uses the `ring` cryptographic provider with `rustls` for TLS, supports optional server TLS and mutual TLS (mTLS) for inbound connections, and exports OpenTelemetry traces and metrics for observability.

## Architectural Analysis

The orchestrator follows a task-based dispatch pattern where each API endpoint creates a typed task struct (e.g., `ClassificationWithGenTask`, `ChatCompletionsDetectionTask`) that is submitted to the `Orchestrator` core for execution. This design cleanly separates HTTP concerns (routing, serialization, error mapping) from orchestration logic (detector coordination, chunking, generation sequencing). The orchestrator initializes downstream gRPC and REST clients at startup from a YAML configuration file, validating hostnames, TLS references, and chunker-detector associations before accepting traffic.

A notable architectural choice is the explicit installation of `ring` as the default `rustls` crypto provider at process startup (`rustls::crypto::ring::default_provider().install_default()`). This means all TLS operations -- both inbound server TLS and outbound client connections via `reqwest` and `tonic` -- use the `ring` library rather than OpenSSL. While `openssl-devel` is installed in the builder image (needed for the `openssl-sys` crate that appears transitively in `Cargo.lock`), the runtime crypto path goes through `ring`. This is architecturally significant for FIPS compliance: `ring` is not a FIPS-validated cryptographic module, so despite the UBI 9 PQC base image providing system OpenSSL, the application's TLS stack does not use it.

The server runs two independent listeners on separate ports: the guardrails server (8033) handles API traffic with optional TLS/mTLS and request tracing, while the health server (8034) runs on plain HTTP without TLS. This separation ensures health probes from the Kubernetes kubelet are not blocked by TLS configuration. Both servers support graceful shutdown via SIGTERM and SIGINT, with a 10-second timeout for in-flight connections when TLS is enabled.

Streaming is a first-class concern: the v1 API uses Server-Sent Events (SSE) for streaming classification results, the v2 streaming content detection endpoint uses newline-delimited JSON (NDJSON) over a bidirectional stream, and the OpenAI-compatible endpoints support both unary and SSE streaming modes with `[DONE]` sentinel messages. The orchestrator uses Tokio channels (`mpsc`) to bridge between internal response streams and the HTTP response body.
