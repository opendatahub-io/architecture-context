## Purpose

**Short**: Deployment init container that bootstraps RHODS (Red Hat OpenShift Data Science) platform components by creating KfDef custom resources, CRDs, monitoring stack, network policies, and dashboard configurations.

**Detailed**: odh-deployer is a container image that runs as a deployment/init container alongside the RHODS operator. When executed, its `deploy.sh` script orchestrates the complete installation of the RHODS platform on an OpenShift cluster. It creates the required namespaces (`redhat-ods-applications`, `redhat-ods-monitoring`, `rhods-notebooks`), applies CRDs for the ODH Dashboard ecosystem, deploys KfDef custom resources that trigger the operator to install individual components (Dashboard, Notebook Controller, ModelMesh, Data Science Pipelines, Anaconda), and configures the monitoring stack (Prometheus, Alertmanager, Blackbox Exporter).

The deployer handles two distinct deployment modes: managed service (OpenShift Dedicated / OSD) and self-managed. In managed mode, it configures SRE alerting via PagerDuty, Dead Man's Snitch, SMTP email notifications, and Prometheus federation from the cluster monitoring stack. In self-managed mode, it applies a simpler configuration without SRE-specific alerting. The deployer also manages ISV (Independent Software Vendor) application tiles for the dashboard, serving runtime configurations for model serving, network policies across platform namespaces, and pod security RBAC for baseline SCC compliance.

This component represents the RHODS 1.x/2.x deployment model where a shell script orchestrated component installation. In RHOAI 3.x, this functionality has been largely superseded by the rhods-operator's built-in reconciliation logic, making odh-deployer a legacy component.

## Purpose

**Short**: A deployment container that bootstraps RHODS (Red Hat OpenShift Data Science) platform components by creating KfDef custom resources, applying CRDs, configuring monitoring infrastructure, and establishing network policies.

**Detailed**: odh-deployer is a self-contained UBI8-based container image that runs alongside the rhods-operator to perform the initial deployment and configuration of the RHODS platform. When executed, the `deploy.sh` entrypoint script orchestrates a multi-step deployment sequence: it creates and labels required namespaces (`redhat-ods-applications`, `redhat-ods-monitoring`, `rhods-notebooks`), applies Dashboard CRDs (`OdhApplication`, `OdhDocument`, `OdhQuickStart`, `OdhDashboardConfig`), and creates KfDef custom resources that trigger the Kubeflow operator to deploy individual RHODS components including the Dashboard, Notebook Controller, ModelMesh, Data Science Pipelines Operator, and Anaconda integration.

The deployer also provisions a comprehensive monitoring stack for managed-service (OSD) environments. This includes a Prometheus deployment with oauth-proxy sidecars, an Alertmanager with PagerDuty/SMTP/Dead Man's Snitch alerting channels, and a Blackbox Exporter for endpoint probing. SLO burn-rate recording rules and multi-window alerting are configured for all major RHODS components. The script differentiates between managed-service and self-managed installations, applying environment-specific configurations such as ISV (Independent Software Vendor) application tiles, RBAC policies for `dedicated-admins` vs `rhods-admins` groups, and alerting destinations.

Network policies for three namespaces (`redhat-ods-operator`, `redhat-ods-applications`, `redhat-ods-monitoring`) restrict ingress traffic to pods within namespaces labeled `opendatahub.io/generated-namespace=true`, establishing the RHODS security boundary. The deployer also creates an OpenShift ConsoleLink to surface the RHODS Dashboard in the OpenShift Application Launcher, and configures Segment.io analytics tracking.

## Architectural Analysis

The odh-deployer represents the legacy RHODS deployment model where a shell script run as an init container orchestrated the full platform bootstrap. This imperative approach has significant architectural implications: the deployment logic lives outside the operator's reconciliation loop, meaning drift detection and self-healing depend entirely on the operator's ability to reconcile the KfDef CRs that the deployer creates. The deployer itself is a one-shot execution -- it does not continuously reconcile, so any resources it creates directly (CRDs, ConfigMaps, Secrets, NetworkPolicies, monitoring stack) are not automatically repaired if manually modified or deleted.

The monitoring architecture is notably comprehensive for a deployment script. The Prometheus deployment includes four containers (prometheus, oauth-proxy, alertmanager-proxy, alertmanager) in a single pod, with init containers that block deployment until all monitored services are available. This creates a startup dependency chain: Prometheus cannot start until Dashboard, Notebook Controller, Model Controller, ModelMesh Controller, and DSPO are all healthy. The init container uses a polling loop with up to 230 iterations at 10-second intervals (approximately 38 minutes timeout), which could delay monitoring availability during slow component rollouts.

The SLO/alerting configuration demonstrates a mature observability model with multi-window burn rate alerting for Dashboard route errors, probe success rates, and component availability. Alert routing distinguishes between SRE-facing alerts (PagerDuty for critical), user-facing alerts (email for PVC usage warnings), and heartbeat monitoring (Dead Man's Snitch). The Prometheus configuration federates specific metrics from the cluster-level Prometheus rather than re-scraping targets directly, which is the correct pattern for RHODS managed service deployments on OSD.

A security concern is the static Segment.io analytics key stored in `monitoring/segment-key-secret.yaml` as a base64-encoded value committed to the repository. While this is a write-only analytics key (not a credential for accessing sensitive data), committing secrets to source control is a supply chain risk. The blackbox exporter's internal configuration (`blackbox-exporter-internal.yaml`) uses `insecure_skip_verify: true`, which is acceptable for internal cluster probes but should be documented as an intentional exception rather than a security gap.

The dual deployment mode (managed/self-managed) introduces significant code path complexity in `deploy.sh`. The managed service path configures PagerDuty, Dead Man's Snitch, SMTP, and Prometheus federation, while the self-managed path skips all SRE alerting. This bifurcation is managed through environment variable checks and `sed` substitutions in YAML templates, which is fragile and difficult to test. The approach of using `sed -i` to template monitoring configuration files at deploy time means the source YAML files contain placeholders (`<smtp_host>`, `<pagerduty_token>`, etc.) that are not valid Kubernetes resources until processed.

## Architectural Analysis

**Deployment Model and Lifecycle**: odh-deployer follows an imperative init-container pattern rather than a declarative operator pattern. The `deploy.sh` script runs sequentially, creating resources via `oc apply` commands. This design means the deployer is a one-shot execution — it does not reconcile drift. If resources are manually deleted or modified after deployment, the deployer will not detect or correct the change unless re-run. The script does include a primitive idempotency mechanism via `oc::object::safe::to::apply()`, which checks whether resources have been modified (using the `opendatahub.io/modified=false` label) before overwriting them, preventing accidental loss of user customizations.

**Environment Bifurcation**: The deployer has two distinct operational modes — managed-service (OSD/addon) and self-managed — determined by checking for the `addon-managed-odh-catalog` CatalogSource. Managed-service mode enables full monitoring (Prometheus, Alertmanager, Blackbox Exporter, PagerDuty, SMTP, Dead Man's Snitch), OSD-specific RBAC for `dedicated-admins`, and managed-service ISV tiles (Starburst Galaxy, NVIDIA, RHOAM). Self-managed mode skips monitoring infrastructure entirely, uses `rhods-admins` group for dashboard admin access, and offers a different ISV tile set (Starburst Enterprise). This bifurcation introduces significant operational differences that are not immediately apparent from the codebase.

**Monitoring Architecture**: The Prometheus deployment is notable for its init container pattern — it waits for ALL monitored services (dashboard, notebook controller, model controller, modelmesh controller, DSPO) to become available before starting, with a 2400-second (40 minute) progress deadline. This tight coupling means a delayed component startup can cause Prometheus to fail entirely. The Prometheus stack federates metrics from the cluster-level OpenShift Monitoring Prometheus, adding SLO burn-rate recording rules and multi-window alerting (5m/30m/1h/2h/6h/1d/3d windows) for all major components. The SLO target is 99.95% for dashboard route errors and probe success, and 98% for notebook spawner and controller probes.

**Security Boundary via Network Policies**: The three network policies establish a namespace-based trust boundary. The `redhat-ods-applications` policy allows ingress on ports 8443, 8080, 8081, 5432, 8082, 8099, and 8181 from namespaces with the `opendatahub.io/generated-namespace=true` label. The monitoring policy allows ports 443, 9115, 8443, 9091, and 10443. However, the policies use broad `podSelector: {}` (all pods in namespace) rather than targeting specific workloads, which means any pod in the namespace accepts traffic on those ports. The operator namespace policy is more restrictive, targeting only pods with `name: rhods-operator`.

**Legacy Architecture Note**: This repository uses the KfDef API (`kfdef.apps.kubeflow.org/v1`) for component deployment, which is the RHODS 1.x/2.x deployment pattern. In RHOAI 2.x+, the platform shifted to DSC (DataScienceCluster) and DSCI (DSCInitialization) CRDs managed by the rhods-operator/opendatahub-operator. The presence of KfDefs and the version tag `v1.20.1-5-rhods-64` indicate this is a legacy deployer from the RHODS 1.x era. Modern RHOAI installations no longer use odh-deployer; the operator handles all component lifecycle management directly.
