## Purpose

**Short**: Deployment container that bootstraps Red Hat OpenShift Data Science (RHODS/RHOAI) components by creating KfDef custom resources, configuring monitoring, network policies, and dashboard ISV tiles.

**Detailed**: odh-deployer is a container image designed to run as an init or job container alongside the opendatahub/rhods operator. When executed, it creates OpenShift projects (namespaces), applies KfDef custom resources to trigger component installations, configures Prometheus-based monitoring with alerting (PagerDuty, email, Dead Man's Snitch), sets up network policies across the platform namespaces, and deploys dashboard ISV (Independent Software Vendor) application tiles.

The deployer orchestrates the initial setup of the RHODS platform by creating KfDef resources for: the RHODS Dashboard, Notebook Controller, Model Mesh, Data Science Pipelines Operator, Notebooks ImageStreams, monitoring stack, Model Mesh monitoring, and Anaconda partner integration. It handles both managed service (OSD/addon) and self-managed deployment variants, adjusting alerting, RBAC, and ISV configurations accordingly.

This component represents a **legacy RHOAI 1.x/2.x deployment pattern** — the KfDef-based deployment mechanism used before the transition to the DSCInitialization/DataScienceCluster CRD-based operator model in RHOAI 2.x+. The repository's last commits reference RHODS version 1.33, indicating it is from the pre-operator refactoring era. In modern RHOAI (2.x+), these deployment responsibilities have been absorbed into the `rhods-operator`.

## Architectural Analysis

The odh-deployer represents a **first-generation deployment pattern** for Red Hat OpenShift Data Science. It uses a container image that runs a monolithic Bash script (`deploy.sh`) to bootstrap the entire RHODS platform. This approach predates the operator-native deployment model adopted in RHOAI 2.x+ where the `rhods-operator` directly manages all component lifecycle through DSCInitialization and DataScienceCluster CRDs. The KfDef-based approach relies on the opendatahub operator's KfDef controller to reconcile kustomize manifests from a pre-packaged tarball (`/opt/manifests/odh-manifests.tar.gz`), which introduces an indirection layer between the deployer and the actual component manifests.

The monitoring architecture is notably sophisticated for a deployment container. The deployer provisions a complete SRE monitoring stack including Prometheus with federation from the cluster Prometheus, Alertmanager with multi-channel alerting (PagerDuty, SMTP, Dead Man's Snitch), and a Blackbox Exporter for endpoint probing. The SLO-based alerting uses multi-window burn rate calculations (5m, 30m, 1h, 2h, 6h, 1d, 3d windows) following Google SRE best practices. This monitoring stack monitors the dashboard, notebook controller, model controller, ModelMesh controller, and Data Science Pipelines Operator.

A significant security concern is the use of **plaintext HTTP** for metrics scraping across all component services (ports 8080/TCP). While the Prometheus and Alertmanager UIs are protected by OAuth proxy sidecars with TLS, the actual metrics endpoints are scraped over unencrypted HTTP. The network policies mitigate this by restricting ingress to specific ports and labeled namespaces, but in-transit metrics data is not encrypted. Additionally, the blackbox-exporter-internal configuration explicitly disables TLS verification (`insecure_skip_verify: true`), which is acceptable for internal probes but should be noted.

The deployer's Dockerfile has several build hygiene issues: the base image is unpinned (no SHA digest), the `oc` CLI is downloaded from an external URL at build time (non-hermetic), and there is no Konflux Dockerfile, confirming this component has not been migrated to the Konflux build pipeline. The Dockerfile also references a `model-mesh` directory via `ADD model-mesh $HOME/model-mesh` that does not exist in the repository checkout, suggesting the build may rely on content that is injected externally or the reference is stale.

The managed-vs-self-managed branching in `deploy.sh` is controlled by checking for the `addon-managed-odh-catalog` CatalogSource in the operator namespace. This is the standard OSD addon detection pattern. When in managed mode, the deployer configures full SRE alerting with PagerDuty, Dead Man's Snitch, and SMTP; when self-managed, it creates an `rhods-admins` group and skips SRE-specific alerting.
