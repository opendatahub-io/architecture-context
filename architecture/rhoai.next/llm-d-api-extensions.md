## Purpose

**Short**: Pip-installable Python package that adds read-only server introspection HTTP endpoints to vLLM inference servers via its endpoint plugin framework, providing launch configuration, hardware device properties, and KV cache capacity data to the llm-d routing and scheduling layer.

**Detailed**: llm-d-api-extensions is a pure Python library that extends vLLM inference servers with additional HTTP API endpoints consumed by the llm-d intelligent routing system. The llm-d scheduler needs runtime metadata about each inference server -- how it was launched, what GPU hardware it sits on, and what its KV cache capacity looks like post-profiling -- to make informed routing and scheduling decisions. Rather than forking or patching vLLM, this repository packages those endpoints as plugins that integrate through vLLM's native extension points.

The repository is structured to be inference-server-agnostic at the top level. Currently only vLLM is supported via the `vllm/` sub-package, which registers three independent endpoint plugins through vLLM's `vllm.endpoint_plugins` entry point mechanism and one worker extension class via `--worker-extension-cls`. Each plugin is opt-in: installing the package changes nothing until a plugin is explicitly named in the `VLLM_PLUGINS` environment variable. This zero-footprint-by-default design lets operators enable exactly the introspection endpoints a deployment needs without side effects on other vLLM behavior.

The package has no container images, no Kubernetes manifests, and no CRDs. It is a library dependency consumed at the Python packaging layer -- typically installed into a vLLM container image at build time and activated via environment variables at runtime.

## Architectural Analysis

llm-d-api-extensions is architecturally notable for what it is *not*: it is not a service, operator, or sidecar. It is a pure in-process library that exploits vLLM's plugin architecture to inject FastAPI routes into a running inference server's HTTP surface. This is a deliberately minimal integration strategy -- the extensions share the server's process, event loop, and listening port, avoiding the networking and lifecycle complexity of a sidecar. The tradeoff is tight coupling to vLLM's internal configuration objects (`VllmConfig`, `CacheConfig`, `SchedulerConfig`, etc.), which are accessed directly rather than through a stable public API.

The plugin initialization model is "compute once, cache forever": each plugin's `init_state` builds a Pydantic response model at startup and stores it on FastAPI's `app.state`. Subsequent requests return the cached object with zero computation. This is sound because the data these endpoints expose (launch config, GPU properties, post-profiling KV cache dimensions) is immutable for the server's lifetime.

The `devices` plugin introduces a cross-process coordination requirement via `collective_rpc` -- it calls into every vLLM worker to collect per-rank GPU properties. This is the only plugin that uses `--worker-extension-cls` and the only one with a failure mode beyond "no engine": if the worker extension is not installed, `collective_rpc` raises and the plugin gracefully degrades to 503 rather than crashing the server. The config and kv-cache plugins operate entirely within the API server process.

The `kv_transfer` section of the config endpoint includes security-conscious handling: the `kv_connector_extra_config` dictionary (operator-controlled, free-form) is redacted by default, with values replaced by `"<redacted>"`. This can be overridden via `LLM_D_INTROSPECTION_EXPOSE_KV_EXTRA_CONFIG=1`, correctly placing the exposure decision on the operator.

A notable architectural gap is the feature-detection pattern in the KV cache plugin: it uses `hasattr(engine_client, "get_kv_cache_group_metadata")` to degrade gracefully against vLLM builds that predate the upstream PR (vllm-project/vllm#48121). This makes the package installable across vLLM versions but means the `groups` response field is silently empty on older builds, which could mislead consumers who do not check for emptiness.
