## Purpose

**Short**: MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments through programmatic tools.

**Detailed**: The RHOAI MCP Server is a Python-based service implementing the Model Context Protocol standard, allowing AI agents (such as Claude Desktop, Claude Code, or any MCP-compatible client) to manage RHOAI platform resources programmatically. It replicates and extends the capabilities of the OpenShift AI Dashboard through a tool-based API surface.

The server provides 50+ MCP tools organized into domain plugins covering project management, workbench (Jupyter notebook) operations, model serving via KServe, data connections, Data Science Pipelines, persistent storage, distributed training via Kubeflow Training Operator, model registry/catalog integration, and LLM deployment planning. It communicates with the Kubernetes API server to manage CRDs and core resources, and with external REST APIs for model registry and deployment planning services.

The architecture uses a pluggy-based plugin system that enables graceful degradation -- plugins that require unavailable CRDs are automatically disabled while the rest of the server continues operating. The server supports multiple transport modes (stdio, SSE, streamable-http), multiple authentication modes (kubeconfig, token, in-cluster, OIDC/TokenReview), and includes safety features such as read-only mode, dangerous operation gating, deletion confirmation patterns, and per-user RBAC-filtered tool visibility.

## Data Flows

- **Inbound:** MCP clients (AI assistants, IDE extensions) connect to the rhoai-mcp service on port 8000/TCP via SSE transport. All Kubernetes API calls use TLS 1.2+ (standard API server communication) with ServiceAccount token authentication.

## Architectural Analysis

The RHOAI MCP Server represents an AI-agent-native interface to the RHOAI platform, complementing the traditional web dashboard. Its architecture is notable for several design decisions that prioritize resilience, extensibility, and security.

**Plugin Architecture and Graceful Degradation**: The pluggy-based plugin system is central to the architecture. Each domain (notebooks, inference, training, etc.) is an independent plugin that declares its CRD requirements via `PluginMetadata.requires_crds`. During startup, the server runs health checks against the cluster -- if a CRD is missing (e.g., the Training Operator is not installed), that plugin is disabled while all other plugins continue operating. This is especially important for RHOAI's modular deployment model where components can be selectively enabled. The plugin system also supports external plugins via Python entry points (`rhoai_mcp.plugins`), enabling teams to extend the MCP server without modifying core code.

**Dual Authentication Models**: The server supports two fundamentally different security postures. In the default single-user mode (OIDC disabled), the service account's ClusterRole grants broad access and all MCP clients share that identity. In OIDC multi-user mode, the ClusterRole is replaced with impersonation and TokenReview/SubjectAccessReview permissions only. Every K8s API call is made with the authenticated user's identity via impersonation headers, and tools are filtered per-user via SubjectAccessReview checks. The OIDC middleware is implemented as a pure ASGI wrapper rather than Starlette's BaseHTTPMiddleware because BaseHTTPMiddleware wraps response bodies through `body_stream`, which breaks SSE streaming -- a subtle but critical architectural constraint documented in `auth/middleware.py`.

**Workflow Token Chaining**: The server implements HMAC-SHA256 signed workflow tokens that enforce multi-step tool call ordering. When a tool is decorated with `@workflow_step(produces="step_name")`, its output includes a signed token. The next tool in the sequence, decorated with `@workflow_step(requires="step_name")`, verifies this token before executing. This prevents AI agents from skipping prerequisite steps (e.g., running `deploy_model` without first calling `prepare_model_deployment`). Tokens have a configurable TTL (default 1 hour) and use constant-time comparison via `hmac.compare_digest()`. However, tokens are not user-scoped -- a gap in multi-user deployments.

**Context Window Optimization**: The server is explicitly designed for AI agent consumption, with several features targeting LLM context window efficiency: response verbosity levels (minimal/standard/full, with ~87% token savings at minimal), pagination with configurable limits, ResponseBuilder formatting, and compact resource status representations. The `suggest_tools` meta-tool provides intent-aware tool recommendations to help agents avoid trial-and-error tool discovery.

**Model Registry API Detection**: The Model Registry domain auto-detects whether the cluster runs the standard Kubeflow Model Registry or the Red Hat AI Model Catalog by probing API endpoints. It caches the detection result and routes subsequent calls to the appropriate client. This dual-API support with a single tool surface is architecturally significant -- it abstracts a platform evolution (Kubeflow → Red Hat AI catalog) behind a stable MCP tool interface. The domain also implements port-forward management for accessing in-cluster services from outside the cluster, with reference-counted subprocess lifecycle management.

## Architectural Analysis

rhoai-mcp is an MCP (Model Context Protocol) server that acts as a bridge between AI assistants and the Red Hat OpenShift AI platform. It translates high-level tool calls from MCP clients into Kubernetes API operations, enabling AI-driven management of data science workflows.

**Broad RBAC footprint:** The ClusterRole grants cross-namespace permissions spanning six API groups and core resources. This is by design — the MCP server needs to create and manage resources in arbitrary namespaces (Data Science Projects) on behalf of the AI assistant. However, the breadth of these permissions (namespace create/delete, secret create/delete, pod create, PV create) makes the ServiceAccount a high-value target. The ClusterRoleBinding scopes the ServiceAccount to the `rhoai-mcp` namespace, but the ClusterRole itself has no namespace restriction.

**Authentication gap in deployment manifests:** The deployment runs a single container with no auth sidecar (no kube-rbac-proxy, no oauth-proxy). The ClusterIP service type provides network-level isolation (only cluster-internal traffic can reach port 8000), but there is no manifest-level authentication enforcement. The `pyjwt` Python dependency in the package metadata strongly suggests JWT-based token validation is implemented in the application code, but this cannot be confirmed from manifests alone. Given the broad RBAC permissions granted to this service, the authentication mechanism — wherever it is enforced — is security-critical.

**SSE transport model:** The `--transport sse` argument selects Server-Sent Events as the MCP transport, which is a long-lived HTTP connection. This means connections persist and each client session maintains state over the SSE stream. The health probe configuration (liveness: 10s initial, 30s period; readiness: 5s initial, 10s period) is appropriately tuned for a stateful server process.

**Security hardening:** The deployment follows OpenShift best practices for pod security: non-root user (UID 1000), read-only root filesystem with an emptyDir for `/tmp`, all capabilities dropped, `RuntimeDefault` seccomp profile, and `allowPrivilegeEscalation: false`. This limits the blast radius of a container compromise despite the broad ServiceAccount permissions.
