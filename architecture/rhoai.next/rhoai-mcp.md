## Purpose

**Short**: MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments through a plugin-based tool system.

**Detailed**: RHOAI MCP is a Python-based MCP server that bridges AI agents (e.g., Claude Desktop, VS Code Copilot) with Red Hat OpenShift AI clusters. It exposes 55+ MCP tools organized into 7 domain plugins (projects, notebooks, inference, pipelines, connections, storage, training) and 4 composite plugins (cluster, training-composites, meta, planner) that let agents create data science projects, manage workbenches, deploy models, run training jobs, and explore cluster resources — all through the standardized MCP protocol.

The server supports three transport modes (stdio, SSE, streamable-http) and authenticates to Kubernetes via kubeconfig, service account token, or auto-detection. When deployed with the OIDC overlay, it supports multi-user authentication via JWT/TokenReview with per-user RBAC filtering — each user only sees and can invoke MCP tools they have Kubernetes permissions for, enforced via SubjectAccessReview. The plugin architecture uses pluggy hooks for extensibility, allowing external plugins to register new tools, resources, and prompts at runtime.

## Architectural Analysis

**Plugin-Based Extensibility**: The server's architecture centers on the pluggy hook system, which cleanly separates domain-specific logic from the core server infrastructure. Each domain (projects, notebooks, inference, etc.) is a self-contained plugin that registers its own MCP tools, resources, prompts, CRD definitions, and RBAC permissions through well-defined hook interfaces (`rhoai_register_tools`, `rhoai_get_tool_permissions`, `rhoai_health_check`, etc.). This design enables third-party plugins via the `rhoai_mcp.plugins` entry point group, and supports selective plugin loading via the `enabled_plugins` configuration. The composite plugins add a second layer that orchestrates across domains — for example, `cluster_summary` aggregates data from projects, notebooks, inference, and training clients in a single tool call, reducing the number of MCP roundtrips an AI agent needs.

**Two-Tier Auth Architecture**: The OIDC overlay implements a sophisticated multi-user authentication and authorization system. The ASGI middleware (`OIDCAuthMiddleware`) validates Bearer tokens via either JWT/JWKS verification or Kubernetes TokenReview API, extracting user identity into a `UserContext` context variable that propagates through async call chains. The server then creates impersonating Kubernetes clients (`create_impersonating_client`) that execute all API calls as the authenticated user rather than the server's service account. Additionally, `RBACChecker.filter_tools()` calls SubjectAccessReview before each MCP session to determine which tools the user is authorized to see. This means a user without `trainer.kubeflow.org/trainjobs:create` permission never sees the `train` tool. The security model is fail-closed: any validation failure results in a 401, and any missing permission hides the tool entirely.

**Model Registry Auto-Discovery**: The Model Registry integration demonstrates a discovery-first architecture. The `ModelRegistryDiscovery` class tries three strategies in order: (1) CRD-based discovery via the `components.platform.opendatahub.io/v1alpha1 ModelRegistry` component CR to find the registries namespace, (2) namespace scanning across common namespace patterns (`rhoai-model-registries`, `odh-model-registries`), (3) fallback to a configured URL. It then probes the discovered service to auto-detect whether it's a Kubeflow Model Registry (v1alpha3 API) or a Red Hat AI Model Catalog (v1alpha1 API), instantiating the appropriate client. When running outside the cluster, it transparently sets up `oc port-forward` subprocess connections with reference counting and lifecycle management.

**Workflow Token Chaining**: The server implements stateless workflow enforcement via HMAC-SHA256 signed tokens (`workflow_token.py`). Tools decorated with `@workflow_step(requires="step_a", produces="step_b")` enforce multi-step ordering — the output of one tool contains a signed token that the next tool must present. This prevents AI agents from skipping preparation steps (e.g., calling `train` without first calling `check_training_prerequisites`). The tokens carry embedded timestamps with configurable TTL (default 3600s) and use timing-safe comparison to prevent timing attacks.

**Response Optimization for AI Agents**: All tools support a `verbosity` parameter (MINIMAL/STANDARD/FULL) that controls response detail level. MINIMAL mode strips labels, annotations, and verbose fields for ~85% token savings, which is critical when AI agents need to process many resources in a single context window. The `PaginatedResponse` builder adds consistent offset/limit/has_more metadata across all list operations. Composite tools like `cluster_summary` further optimize by returning pre-aggregated counts rather than full resource lists.
