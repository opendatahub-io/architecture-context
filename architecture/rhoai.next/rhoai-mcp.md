## Purpose

**Short**: MCP (Model Context Protocol) server enabling AI agents to programmatically interact with Red Hat OpenShift AI environments for project, workbench, model serving, pipeline, storage, and training management.

**Detailed**: rhoai-mcp is a Python-based MCP server that replicates the capabilities of the OpenShift AI Dashboard through programmatic tools accessible to AI agents. It exposes approximately 30 MCP tools across seven domain modules (projects, notebooks, inference, connections, storage, pipelines, training), plus a model registry integration domain, composite cross-cutting tools, 18 workflow prompts, and MCP resources for cluster introspection.

The server uses a pluggy-based plugin architecture with a clear separation between "domain" modules (pure CRUD operations on individual Kubernetes resource types) and "composite" modules (cross-cutting orchestrators that combine multiple domains for agent efficiency). Each domain encapsulates its own Kubernetes client, Pydantic models, MCP tool definitions, and optionally CRD definitions, MCP resources, and prompts. Plugins are registered via a hook system and discovered at startup.

For multi-user deployments, rhoai-mcp supports OIDC authentication with two token validation modes (JWT via JWKS and OpenShift TokenReview) and two Kubernetes auth strategies (user-token forwarding for opaque OAuth tokens, and impersonation for audience-bound JWTs). Tool visibility is RBAC-filtered per user via SubjectAccessReview. The server also implements a stateless HMAC-signed workflow token system that enforces ordered multi-step tool execution, preventing agents from skipping prerequisite steps.

## Architectural Analysis

rhoai-mcp bridges the gap between AI agent harnesses (Claude Code, Codex, OpenCode, Pi) and the Kubernetes-native RHOAI platform. Rather than requiring agents to understand Kubernetes API semantics, the MCP server presents domain-oriented tools that map to user intents — "create a data science project," "deploy a model," "start a training job" — with appropriate safety rails.

The architecture follows a layered design: transport (stdio/SSE/streamable-http via FastMCP and uvicorn) → authentication middleware (OIDC/TokenReview) → tool/resource/prompt registration (pluggy hooks) → domain clients (Python Kubernetes SDK) → Kubernetes API. The plugin system enables domains to be loaded selectively via `RHOAI_MCP_ENABLED_PLUGINS`, which is useful for deployments where not all RHOAI components are installed.

The dual auth strategy (user-token vs. impersonation) is architecturally significant. In user-token mode, the service account holds minimal privileges (tokenreviews, subjectaccessreviews, users.user.openshift.io) while the caller's own token is forwarded to the K8s API — resource access is enforced by Kubernetes RBAC against the caller's identity. In impersonation mode, the service account requires elevated impersonate privileges but supports external IdPs whose JWTs are not natively trusted by the cluster. The config validator prevents combining JWT token mode with user-token strategy, avoiding confused-deputy risks.

The composite layer (cluster exploration, training orchestration, resource diagnostics, inference planning) reduces tool-call round-trips for AI agents, which is important for token budget and latency. The `prepare_training()` composite, for instance, validates storage, credentials, runtime availability, and resource estimation in a single call, returning parameters that can be passed directly to `train()`.

A notable security pattern is the workflow token system: HMAC-SHA256 signed tokens chain multi-step operations, preventing agents from skipping prerequisite verification. Tokens are stateless (no server-side session state), time-bounded via configurable TTL, and verified with constant-time comparison.

The RHOAI overlay defaults to read-only mode, reflecting a safer-by-default posture for production. The MCP Lifecycle Operator integration (MCPServer CR) enables operator-managed deployment where the operator handles Deployment, Service, and NetworkPolicy lifecycle.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user Bearer token validated via TokenReview or JWT; SubjectAccessReview filters tool visibility per user; K8s API calls use caller's credentials (user-token) or impersonation | Kubernetes API server + application middleware | In single-user mode (OIDC disabled), all operations use the shared SA identity — no user isolation |
| Data storage | Per-namespace (K8s native); resources are scoped to the namespace the user specifies; delete operations default to MCP-managed resources only | Kubernetes RBAC | No application-level namespace access control beyond K8s RBAC; users can access any namespace their K8s credentials allow |
| Network traffic | NetworkPolicy for Model Catalog access; Route with TLS edge termination | Kubernetes NetworkPolicy + OpenShift Router | No per-user network isolation — all users share the same Route and Service |
| Compute & resources | Single-replica Deployment with fixed resource requests/limits (100m-500m CPU, 256Mi-1Gi memory) | Kubernetes resource limits | No per-user compute isolation; a resource-intensive request from one user could impact others |
| Configuration & secrets | Per-process HMAC secret; per-user bearer tokens handled in-memory; ConfigMap for shared server configuration | Application (workflow tokens), Kubernetes (SA token, ConfigMap) | Workflow HMAC secret is shared across all users; a compromised secret would allow forging workflow tokens |
| API scoping | Tools operate on user-specified namespace; K8s API enforces access via caller's own token; RBAC-based tool filtering shows only tools the user has permissions for | Kubernetes RBAC + application RBAC filter | Tools without permission mappings are visible to all authenticated users by default |
