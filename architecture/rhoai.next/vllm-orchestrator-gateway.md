## Purpose

**Short**: An HTTP gateway that provides multiple OpenAI-compatible chat completion endpoints with configurable detector-based content filtering, routing requests to the FMS Guardrails Orchestrator.

**Detailed**: The vllm-orchestrator-gateway is a Rust-based HTTP reverse proxy that sits between clients and the FMS Guardrails Orchestrator. It enables controlled interaction with LLM inference services by enforcing configurable detector pipelines on chat completion requests. Each configured route exposes a unique `/{route-name}/v1/chat/completions` endpoint that maps to a specific set of content detectors (e.g., PII detection, regex-based filters).

When a request arrives, the gateway injects the route's detector configuration into the payload and forwards it to the orchestrator's `/api/v2/chat/completions-detection` endpoint. If the orchestrator reports a detection (e.g., PII found in output), the gateway replaces the response with a configurable fallback message. The gateway supports both streaming (SSE) and non-streaming chat completions, and it supports mTLS for secure communication with the orchestrator using OpenShift service-serving certificates.

The gateway is designed as a drop-in replacement for direct chat completion endpoints, allowing operators to add guardrails to any vLLM-served model without modifying client code. It is part of the TrustyAI ecosystem within RHOAI, working alongside the FMS Guardrails Orchestrator and various detector services.

## Data Flows

1. **Client → Gateway**: Client sends `POST /{route_name}/v1/chat/completions` with an OpenAI-compatible chat completion payload (and optional `Authorization` header) to the gateway on port 8090/TCP.
2. **Gateway route matching**: The gateway matches the route name to a configured `RouteConfig` which specifies a set of named detectors and an optional fallback message.
3. **Detector injection**: The gateway resolves the route's detector names against the global `DetectorConfig` list, building an `OrchestratorDetector` payload with separate `input` and `output` detector parameter maps. This is injected into the request payload under the `detectors` key.
4. **Gateway → Orchestrator**: The enriched payload is forwarded via `POST {scheme}://{orchestrator_host}:{orchestrator_port}/api/v2/chat/completions-detection` to the TrustyAI vllm-orchestrator. The connection uses HTTP or HTTPS depending on whether TLS certificates are mounted at `/etc/tls/private/`. The `Authorization` and `x-forwarded-*` headers from the original client request are forwarded.
5. **Orchestrator → Gateway**: The orchestrator performs the LLM inference and detector analysis, returning either a single JSON response or an SSE stream depending on the client's `stream` field.
6. **Detection check**: If the orchestrator response contains detections and the route has a `fallback_message` configured, the gateway replaces the response content with the fallback message.
7. **Gateway → Client**: The (possibly modified) response is returned to the client in the original format (JSON or SSE stream).

## Architectural Analysis

The vllm-orchestrator-gateway is architecturally simple by design — a stateless Rust HTTP proxy with a single responsibility: route-specific detector injection. Its entire codebase fits in three source files (~370 lines of application logic excluding tests), making it highly maintainable but also limited in scope.

**Configuration-driven routing**: The gateway's core pattern is elegant — each route in `config.yaml` generates a distinct `/{name}/v1/chat/completions` endpoint backed by a specific set of detectors. This allows operators to expose multiple guardrailed endpoints from a single gateway instance, each with different safety policies (e.g., `/pii/v1/chat/completions` with PII detection vs. `/passthrough/v1/chat/completions` with no detectors). The route configuration also supports per-route `fallback_message` strings, enabling different user-facing error messages when detections trigger.

**mTLS implementation**: The TLS code in `build_orchestrator_client()` (main.rs:351-406) demonstrates a carefully layered approach — it checks for the presence of service-serving certificates at well-known OpenShift paths and gracefully falls back to plaintext HTTP if they're absent. The `danger_accept_invalid_hostnames(true)` call when the orchestrator host is `localhost` is a development convenience that should be noted in security reviews but does not affect production deployments where the hostname will match the certificate's SAN. The PKCS12 identity construction is necessary because the `native-tls` crate requires DER-encoded PKCS12 bundles rather than separate PEM files.

**Security posture gap**: The gateway performs no authentication or authorization itself — it simply forwards `Authorization` and `X-Forwarded-*` headers. This means it relies entirely on network-level isolation (NetworkPolicy, service mesh) and the orchestrator's own auth enforcement. No RBAC manifests, ServiceAccount definitions, or admission webhook configurations are shipped with this repo, which is appropriate for a simple proxy but means the deployment must be carefully secured externally.

**Streaming architecture**: The streaming implementation (main.rs:259-349) processes orchestrator SSE responses chunk by chunk, parsing each for detection results. When a detection triggers on a streaming chunk, it replaces the content in that single chunk and sets `finish_reason: "stop"`, effectively truncating the stream. This is a pragmatic approach but means partial content may have already been streamed to the client before a detection is found in a later chunk — the gateway cannot retroactively redact earlier chunks.

**Build maturity**: The Konflux build pipeline is well-configured with full hermeticity (prefetched Cargo crates and RPMs, `rpms.lock.yaml` covering four architectures). The multi-arch build targets x86_64, arm64, ppc64le, and s390x. The repository has Tier 1 testing (unit tests, clippy, formatting) via GitHub Actions and Trivy filesystem security scanning.

## Architectural Analysis

The vllm-orchestrator-gateway follows a lightweight reverse-proxy pattern, purpose-built for the TrustyAI guardrails pipeline. Rather than implementing a general-purpose API gateway, it focuses on a single concern: injecting detector configurations into OpenAI-compatible chat completion requests before forwarding them to the vllm-orchestrator. The codebase is intentionally minimal — three source files totaling under 700 lines of Rust — which limits attack surface and maintenance burden.

The route configuration model is dynamic: routes are defined in a YAML config file read at startup, and each route maps to a subset of globally defined detectors. This means the gateway binary does not need to be rebuilt to add new filtering routes; only the ConfigMap needs updating and the pod restarted. The `/{route_name}/v1/chat/completions` path pattern allows clients to target different detector policies by choosing the appropriate route name, while the underlying orchestrator endpoint (`/api/v2/chat/completions-detection`) remains the same for all routes.

The gateway's authentication model is strictly pass-through: it forwards the `Authorization` header and `x-forwarded-*` headers to the orchestrator without inspecting or validating them. This design delegates all authentication and authorization decisions to the orchestrator backend. While this simplifies the gateway, it means the gateway itself has no access control — any client that can reach port 8090 can send requests. In a production deployment, a sidecar (e.g., kube-rbac-proxy) or network policy would need to provide ingress-level authentication.

The mTLS support for the outbound orchestrator connection is notable: the gateway reads TLS client certificates from well-known Kubernetes secret mount paths (`/etc/tls/private/`) and a CA certificate from `/etc/tls/ca/service-ca.crt`. When these files are present, the gateway automatically upgrades the orchestrator connection from HTTP to HTTPS with mutual TLS. When the orchestrator host is `localhost`, the gateway accepts mismatched hostnames in the server certificate (`danger_accept_invalid_hostnames`), which is a pragmatic choice for local development but requires careful configuration in production.
