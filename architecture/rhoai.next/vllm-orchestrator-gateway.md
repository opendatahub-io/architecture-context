## Purpose

**Short**: An OpenAI-compatible HTTP gateway that routes chat completion requests through configurable detector pipelines for content filtering, acting as a guardrails enforcement layer in front of the FMS Guardrails Orchestrator.

**Detailed**: The vllm-orchestrator-gateway is a lightweight Rust service that provides per-route OpenAI-compatible `/v1/chat/completions` endpoints, each bound to a specific set of content detectors (e.g., PII, toxicity). When a client sends a chat completion request to a named route, the gateway injects the route's detector configuration into the payload and forwards it to the FMS Guardrails Orchestrator's `/api/v2/chat/completions-detection` endpoint. If any detectors trigger, the gateway can substitute a configurable fallback response, shielding downstream consumers from unsafe or policy-violating content.

The gateway supports both synchronous and streaming (SSE) chat completions, forwarding Authorization and X-Forwarded-* headers to the orchestrator. It can establish mTLS connections to the orchestrator using certificates mounted at well-known paths (`/etc/tls/private/`) and custom CA bundles (`/etc/tls/ca/service-ca.crt`). Configuration is driven entirely by a YAML file that declares the orchestrator endpoint, available detectors with their parameters, and named routes that map detector combinations to exposed HTTP paths. This design enables drop-in replacement of an unguardrailed model endpoint with a guardrailed one, requiring no client-side changes beyond updating the URL.

## Architectural Analysis

The gateway follows a simple reverse-proxy pattern: a thin HTTP layer (Axum) that transforms incoming OpenAI-compatible requests into orchestrator-compatible requests by injecting detector specifications. The architecture is intentionally minimal -- no persistent state, no CRDs, no operator lifecycle. Routes are built dynamically at startup from the YAML config, making the gateway a stateless request transformer.

The mTLS implementation deserves architectural attention. The gateway uses the `openssl` crate to construct a PKCS#12 identity from PEM-formatted certificates and keys, then passes this to `reqwest`'s `native-tls` backend. This path through system OpenSSL (rather than pure-Rust `rustls`) is significant for FIPS compliance, as it delegates TLS operations to the platform's OpenSSL installation. The Konflux Dockerfile uses the `ubi9/ubi-minimal-pqc` base image (post-quantum cryptography variant), signaling forward-looking cryptographic posture. However, there is no explicit FIPS mode enablement at the application level -- TLS configuration relies entirely on system OpenSSL defaults.

A notable design choice is the `danger_accept_invalid_hostnames(true)` call when the orchestrator host is `localhost`, which disables hostname verification for local development. This is guarded by the hostname check and does not affect production deployments where the orchestrator hostname is a Kubernetes service DNS name.

The gateway has no Kubernetes manifests, RBAC definitions, or kustomize overlays in this repository. Deployment configuration is likely managed by the operator that deploys the TrustyAI stack (e.g., the trustyai-service-operator or the broader RHOAI operator).
