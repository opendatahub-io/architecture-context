## Purpose

**Short**: An HTTP gateway that provides route-specific OpenAI-compatible chat completion endpoints with configurable detector-based content filtering, routing requests to the FMS Guardrails Orchestrator.

**Detailed**: The vLLM Orchestrator Gateway is a lightweight Rust HTTP service that sits in front of the FMS Guardrails Orchestrator, enforcing stricter access to its exposed endpoints. It reads a YAML configuration file defining named routes, each with a set of detector pipelines and optional fallback messages. For each configured route, the gateway exposes a `/{route_name}/v1/chat/completions` endpoint that is OpenAI-compatible.

When a client sends a chat completion request to a route endpoint, the gateway injects the route's configured detector specifications (input and/or output detectors with their parameters) into the request payload, then forwards it to the FMS Guardrails Orchestrator's `/api/v2/chat/completions-detection` endpoint. If the orchestrator returns detection results (e.g., PII found in output), the gateway replaces the generated response with the route's configured fallback message. This enables drop-in replacement of an unguardrailed chat completions endpoint with a guardrailed one — clients use the same OpenAI chat completions API shape while the gateway transparently applies safety policies.

The gateway supports both streaming (SSE) and non-streaming chat completions, optional mTLS for orchestrator communication, and forwards authorization and `x-forwarded-*` headers to the backend.

## Architectural Analysis

The vLLM Orchestrator Gateway follows a straightforward reverse-proxy pattern implemented in Rust with the axum web framework. The architecture is intentionally simple — a single binary with three source files totaling ~770 lines of Rust code. The gateway is stateless; all configuration is loaded at startup from a YAML file and routes are registered once. There is no runtime reconfiguration, health check endpoint, or readiness probe exposed.

The gateway's core value proposition is route-level detector policy enforcement. Rather than requiring clients to understand the FMS Guardrails Orchestrator's detector configuration API, the gateway presents a clean OpenAI-compatible interface where each route name maps to a predetermined set of input/output detectors. This enables platform operators to define safety policies (e.g., "the `/pii` endpoint always checks for email and SSN patterns") while clients use a standard chat completions API. The fallback message mechanism provides a clean degradation path — when detections are triggered, the client receives a well-formed OpenAI response with the fallback text rather than an error.

The mTLS implementation is notable for its use of the OpenSSL crate directly (rather than relying solely on `native-tls` defaults). The gateway converts PEM certificates to PKCS#12 format in memory for use as a reqwest `Identity`. The `danger_accept_invalid_hostnames(true)` call when the orchestrator host is `localhost` is a development convenience that should not be exercised in production deployments. The TLS configuration is optional — the gateway falls back to plaintext HTTP when certificates are not mounted, which is the expected mode for development and some internal deployment scenarios.

A notable gap is the absence of health/readiness endpoints, metrics (no Prometheus integration), and graceful shutdown handling. The Dockerfile also runs as root (no `USER` directive), which is a security concern for production Kubernetes deployments. The configuration validation at startup is basic — it checks that route-referenced detectors exist in the detectors list and prevents duplicate server names per input/output direction, but does not validate orchestrator connectivity or detector availability.
