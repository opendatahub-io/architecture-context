## Purpose

**Short**: Downstream z-stream test fork of the OpenDataHub notebooks repository that builds workbench container images (Jupyter, Code Server, RStudio) and pipeline runtime images for Red Hat OpenShift AI.

**Detailed**: This repository is the furthest downstream fork in the notebooks lineage (opendatahub-io/notebooks → red-hat-data-services/notebooks → red-hat-data-services/notebooks-downstream-z-test). It serves as the z-stream build and test variant for RHOAI workbench images. The repository does not deploy services or controllers itself; instead, it produces container images that are consumed by the ODH Notebook Controller, which manages their lifecycle on OpenShift clusters.

The repository builds three categories of images across multiple accelerator variants (CPU, NVIDIA CUDA, AMD ROCm): (1) JupyterLab-based workbench images with varying levels of data science libraries (minimal, datascience, pytorch, pytorch+llmcompressor, tensorflow, trustyai), (2) Code Server (VS Code in browser) workbench images, and (3) headless pipeline runtime images used by Elyra for Kubeflow Pipelines execution. Each image is built from a layered Dockerfile hierarchy where accelerator-specific base images are injected via build args, and Python dependencies are locked via `pylock.toml` files with hash verification.

OpenShift ImageStream manifests managed via kustomize track multiple image generations (N through N-5) with parameterized image references, enabling the RHOAI dashboard to present versioned workbench selections to users.

## Architectural Analysis

The notebooks repository follows a matrix build architecture where each workbench type is cross-cut by accelerator variant. The Dockerfile hierarchy is carefully layered: a base stage installs OS packages and tooling (micropipenv, uv, oc client), then specialized stages add framework-specific Python packages. Datascience-level images build atop minimal images, and framework images (PyTorch, TensorFlow) build atop datascience. This layering keeps shared infrastructure consistent while allowing framework-specific customization.

A notable architectural choice is the mongocli builder stage present in datascience Dockerfiles, which compiles MongoDB CLI from source with FIPS-compliant build flags (`CGO_ENABLED=1 -tags strictfipsruntime`). This is the only Go binary produced by the image builds and represents the sole explicit FIPS build signal in the repository.

The non-Konflux runtime Dockerfiles (e.g., `runtimes/minimal/ubi9-python-3.12/Dockerfile.cpu`) reference AIPCC base images and inject UBI 9 repository configuration to enable package management. However, the Konflux Dockerfiles use generic `${BASE_IMAGE}` args that resolve to standard UBI 9 or ODH community base images, not AIPCC images. This divergence between the Konflux and non-Konflux build paths is architecturally significant for FIPS compliance tracking.

Python dependency management uses `pylock.toml` with `uv pip install --verify-hashes`, providing hash-verified, reproducible installs. Each variant directory maintains its own lock file. The JupyterLab addons system (`utils/addons/apply.sh`) provides an extension mechanism applied at build time. The Elyra bootstrapper (copied into runtime images) handles pipeline execution integration with Kubeflow Pipelines.
