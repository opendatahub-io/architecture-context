## Purpose

**Short**: Production-ready starter kits for building and deploying AI agents on Red Hat OpenShift AI, organized by framework (LangGraph, CrewAI, LlamaIndex, AutoGen, Google ADK, Langflow, A2A) with shared auth, tracing, and deployment infrastructure.

**Detailed**: agentic-starter-kits is a collection of self-contained agent templates and deployment recipes for Red Hat OpenShift AI. Each template provides a complete, deployable AI agent built on a specific framework (LangGraph, CrewAI, LlamaIndex, AutoGen, Google ADK, Langflow, or vanilla Python) with a standardized OpenAI-compatible API contract (`POST /chat/completions`, `GET /health`), Helm-based deployment, and optional MLflow tracing integration.

The repository is structured around three tiers: **templates** (reusable scaffolding for new agents), **examples** (business use-case demos like CI failure summarization and guardrailed banking agents), and **deployments** (pre-built tools like OpenClaw, Claude Code, Codex, and OpenCode deployed on OpenShift via Kustomize or Containerfiles). Shared infrastructure includes a reusable `agent-auth` middleware component for Kubernetes ServiceAccount token authentication, a shared Helm chart, a behavioral test harness, and llm-d deployment manifests for inference routing.

The repository does not produce a single deployable service. Instead, each agent template is independently containerized using UBI9 Python 3.12 base images, runs as a uvicorn-served FastAPI application on port 8080, and is deployed via a shared Helm chart that provisions OpenShift Routes with edge TLS termination.

## Architectural Analysis

agentic-starter-kits follows a **monorepo-of-templates** architecture rather than a traditional microservice or operator pattern. The key architectural decisions are:

**Standardized API contract**: All standard agents expose OpenAI-compatible `POST /chat/completions` (with JSON and SSE streaming) and `GET /health` endpoints. This uniformity enables a shared behavioral test harness that validates any agent through the same HTTP interface, regardless of the underlying framework. The `POST /v1/chat/completions` alias provides compatibility with clients that expect the versioned path.

**Shared Helm chart with per-agent values**: Rather than per-framework deployment infrastructure, a single Helm chart (`agents/<framework>/deployment/`) handles Deployment, Service, Route, Secret, ServiceAccount, and optional ClusterRoleBinding resources. Agent-specific configuration is injected through `values.yaml` overrides and `.env` files that feed Helm secrets. This design reduces chart drift but means all agents share the same deployment topology.

**Auth delegation pattern**: The `agent-auth` component implements ASGI middleware that validates Kubernetes ServiceAccount tokens via the TokenReview API. When `AUTH_ENABLED=true`, the agent's ServiceAccount is bound to `system:auth-delegator` via a ClusterRoleBinding, allowing it to verify caller tokens against an audience claim. The middleware is opt-in and imported lazily, so agents without the `auth` extra simply skip it.

**MLflow tracing as a cross-cutting concern**: Every template integrates MLflow tracing through a `tracing.py` module called during FastAPI lifespan startup. Tracing is opt-in (gated by `MLFLOW_TRACKING_URI`), supports ServiceAccount-based and token-based authentication to the MLflow server, and handles TLS configuration including self-signed certificates via `MLFLOW_TRACKING_SERVER_CERT_PATH` and `MLFLOW_TRACKING_INSECURE_TLS`.

**Non-standard agents diverge significantly**: The deployment-tier agents (OpenClaw, Claude Code, Codex, OpenCode) do not follow the FastAPI/Helm pattern. OpenClaw uses Kustomize with a pre-built upstream Node.js image. Claude Code uses a proprietary binary installer. Codex and OpenCode run as CLI tools inside OpenShell sandboxes with `sleep infinity` for interactive access. These represent integration recipes rather than agent templates.

**Security posture observations**: Agent containers run as non-root (UID 1001) with `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, and all Linux capabilities dropped. The OpenClaw deployment additionally pins container images by SHA256 digest. However, the TLS configuration across tracing modules supports disabling certificate verification (`MLFLOW_TRACKING_INSECURE_TLS`), which is a pragmatic accommodation for self-signed certificates in development/internal clusters but weakens the trust chain in production.
