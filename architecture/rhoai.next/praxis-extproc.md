## Purpose

**Short**: Envoy ExtProc gRPC server that runs Praxis filter pipelines as an external processor for header and body inspection, mutation, and rejection without replacing Envoy.

**Detailed**: praxis-extproc is a standalone gRPC server that implements the Envoy [External Processing](https://www.envoyproxy.io/docs/envoy/latest/configuration/http/http_filters/ext_proc_filter) (ExtProc) protocol. It translates Envoy ExtProc messages into [Praxis](https://github.com/praxis-proxy/praxis) filter pipeline invocations, enabling request/response header and body inspection, mutation, and rejection over gRPC without replacing Envoy itself.

Within RHOAI, praxis-extproc serves as the Inference Payload Processor (IPP) in the Model-as-a-Service (MaaS) data path. It is deployed in the `openshift-ingress` namespace alongside the Istio gateway, where EnvoyFilter resources inject it into the HTTP filter chain in two stages: a pre-auth stage that promotes body-level model identifiers to routing headers for KServe InferencePool selection, and a post-auth stage that runs the full processing pipeline. The component replaces the earlier Go-based Inference Payload Processor with a Rust implementation built on the Praxis filter framework.

All cryptography is delegated to the system OpenSSL library. The product image is the FIPS build by default, excluding features that carry pure-Rust cryptography (the policy engine and the Responses store). On a FIPS-enabled RHEL 9 host, the OpenSSL FIPS provider is the validated module, and the `PRAXIS_REQUIRE_FIPS` environment variable enforces fail-closed FIPS compliance.

## Architectural Analysis

praxis-extproc follows a clean single-binary architecture with three concurrent listeners: a gRPC ExtProc service (port 9004 in deployment), a gRPC health check service (port 50052), and an HTTP Prometheus metrics endpoint (port 9090). The binary's `main` function installs the OpenSSL-backed crypto provider as the first action, then loads YAML configuration, builds the filter pipeline from the Praxis filter registry, and starts all three listeners under a shared drain-signal supervisor. Graceful shutdown is bounded by a configurable drain timeout (default 20s), with a force-close latch that cancels hung streams when the deadline expires.

The FIPS compliance architecture is particularly thorough. Rather than a separate FIPS image variant, the product Containerfile builds the FIPS feature set by default. Features known to carry pure-Rust cryptography (`policy-engine`, `responses-store`, `responses-full`) are excluded at compile time via Cargo feature flags. At runtime, the `fips` module checks both the crypto provider's FIPS status and the kernel's `fips_enabled` flag, and an additional source-level check scans the filter registry for non-FIPS-safe filters (`policy`, `openai_response_store`), refusing to serve if any are registered while `PRAXIS_REQUIRE_FIPS` is set. The build embeds a cargo-auditable crate manifest so Red Hat's check-payload scanner can verify the absence of pure-Rust crypto crates.

TLS for the gRPC listener is handled directly by OpenSSL via `tokio-openssl`, supporting three modes: plaintext, self-signed (ephemeral P-256 cert), and provided (cert/key from disk with optional mTLS). The TLS configuration enforces TLS 1.2+ with ECDHE-only cipher suites, deliberately avoiding finite-field DH params that would import deprecated OpenSSL symbols outside the FIPS surface. Outbound TLS from Praxis filters uses rustls with the OpenSSL-backed crypto provider installed at startup, ensuring all crypto paths converge on the system library.

The deployment architecture in ODH/RHOAI positions the server in the gateway namespace (`openshift-ingress`), integrated via Istio EnvoyFilter resources that inject two ExtProc filter stages relative to the Kuadrant auth filter. The EnvoyFilter manifest accounts for four different auth anchor naming conventions across Istio versions (<=1.25, 1.26-1.29, >=1.30, and RHCL 1.4), ensuring correct filter ordering regardless of mesh version. Dedicated ExtProc upstream clusters bypass Istio's metadata exchange to avoid HTTP/2 protocol errors with the non-mesh Praxis server. A NetworkPolicy restricts ingress to gateway pods and monitoring scrapers, and egress to DNS and the Kubernetes API server.
