## Purpose

**Short**: Containerized distribution of OGX (formerly Llama Stack) providing a multi-provider AI/ML API server with pre-configured inference, vector storage, file processing, and agent capabilities for Red Hat OpenShift AI.

**Detailed**: The OGX Distribution is a build and packaging project that produces a multi-architecture (amd64/arm64/ppc64le) container image (`quay.io/opendatahub/odh-ogx-core`) running an OGX server. OGX is the opendatahub-io fork of the Llama Stack framework, which provides a unified API layer for AI/ML workloads including inference (via vLLM, OpenAI, Bedrock, Vertex AI, Azure, WatsonX, Gemini, Anthropic), vector storage (Milvus, pgvector, Qdrant, FAISS), file processing (Docling, pypdf, markitdown), web search (Brave, Tavily), and agent/responses workflows.

The project does not contain the OGX framework source code itself -- it is a distribution layer that: (1) defines provider configurations via `build/build.yaml`, (2) generates lock files for reproducible Python dependency resolution, (3) builds container images with pre-installed dependencies and pre-fetched ML model artifacts (Granite embedding, Docling layout, RapidOCR), and (4) runs comprehensive CI/CD including smoke tests, integration tests against multiple inference providers, and weekly Responses API test suites with published test reports.

The container image supports conditional provider activation via environment variables (e.g., setting `VLLM_URL` activates the vLLM inference provider), OAuth2 token-based authentication with JWKS validation, OpenTelemetry instrumentation, PostgreSQL-backed persistent storage, and secret mounting via `_FILE`-suffixed environment variables for Kubernetes-native secret management.

## Purpose

**Short**: Containerized distribution of OGX (the Open Data Hub fork of Llama Stack) that provides a multi-API AI inference gateway with configurable providers for LLM inference, vector storage, file processing, and tool execution.

**Detailed**: ogx-distribution packages the [opendatahub-io/ogx](https://github.com/opendatahub-io/ogx) framework — a fork of Meta's Llama Stack — into a production-ready container image for Red Hat OpenShift AI. The image ships as `quay.io/opendatahub/odh-ogx-core` and exposes a unified HTTP API surface on port 8321 that implements the OpenAI Chat Completions API (`/v1/chat/completions`), the Anthropic Messages API (`/v1/messages`), and the OGX Responses API (`/v1/responses`), among others.

The distribution uses a provider-based architecture where inference backends (vLLM, AWS Bedrock, IBM WatsonX, Azure OpenAI, Google Vertex AI, OpenAI, Gemini, Anthropic), vector stores (Milvus, pgvector, Qdrant), file storage (local filesystem, S3), file processors (Docling, MarkItDown, PyPDF), and tool runtimes (Brave Search, Tavily, MCP, file-search) are conditionally activated via environment variables at startup. A `build/build.yaml` manifest defines all available providers; `build/build.py` generates a stripped `distribution/config.yaml` and `distribution/requirements.txt` at build time. The container requires PostgreSQL for persistent state (kv store, SQL store for inference logs, batches, conversations, and file metadata).

The repository does not contain application source code — OGX is installed as a pip dependency from the upstream fork. The repository's purpose is to define the distribution configuration, build the container image (with pre-downloaded ML models for offline operation), and provide CI/CD infrastructure for testing and publishing. The Konflux build uses an AIPCC CPU base image for the downstream RHOAI product build, while the upstream ODH build uses `quay.io/opendatahub/odh-midstream-python-base-3-12`.

| Configuration & secrets | Shared configuration; per-user resources via ownership model | OGX application | All users share the same provider configurations and API keys |
| API scoping | Ownership-based filtering on resource CRUD operations | OGX application | System resources (models, unowned tool groups) are readable by all authenticated users |

## Architectural Analysis

The OGX Distribution represents a "distribution-as-code" pattern: the repository contains no application source code but rather a declarative build pipeline that assembles a container image from an upstream framework (OGX/Llama Stack), provider configurations, and pre-fetched ML model artifacts. The entire provider landscape is defined in a single `build/build.yaml` file, from which all other artifacts are generated -- `config.yaml`, `Containerfile`, lock files, and documentation. This centralized source-of-truth design makes it easy to add, remove, or reconfigure providers, but it means the repository must be regenerated whenever the upstream OGX version changes.

The conditional provider activation pattern (`${env.SOME_VAR:+provider-name}`) is architecturally significant: the same container image supports a wide variety of deployment scenarios (local vLLM, cloud-only, hybrid) without image variants. Providers that are not activated at startup (because their env var is unset) are simply skipped, with no runtime overhead. This is a clean separation of build-time (all dependencies pre-installed) and run-time (only activated providers consume resources) concerns. The 7 dependency-only providers (sentence-transformers, milvus-inline, faiss, docling, markitdown, pypdf, docling-serve) are installed in the image but stripped from the default `config.yaml`, requiring a custom config to activate them.

The build hermeticity is well-implemented for a Python project: the Konflux Tekton pipeline uses Hermeto prefetch for both pip packages (via the RHAI index) and generic artifacts (ML models, tokenizer caches) with SHA256 checksum verification in `artifacts.lock.yaml`. The `copy-artifacts.sh` script handles both Hermeto (Konflux) and `fetch_artifacts.py` (upstream CI) artifact sources, maintaining dual-path compatibility. However, there is no `rpms.lock.yaml` on the `main` branch, meaning OS-level package hermeticity depends on the downstream release branch adding RPM locks.

The authentication model has an important architectural characteristic: it is entirely optional and opt-in. When `AUTH_ISSUER` is not set, the OGX server runs with no authentication at all. When enabled, it implements a lightweight ownership model (read unowned, create any, manage own) that provides basic multi-tenant isolation. However, this is application-level isolation only -- all users share the same PostgreSQL instance, the same inference provider credentials, and the same vector stores. True tenant isolation would require platform-level enforcement (NetworkPolicies, separate deployments per tenant). The `--insecure` flag in the entrypoint confirms that TLS is expected to be provided by the platform's ingress layer (Gateway API / kube-rbac-proxy), not by the application itself.

The CI/CD pipeline is comprehensive and notable for its multi-provider testing approach: the `redhat-distro-container.yml` workflow builds multi-arch images and runs smoke tests against local vLLM, while the weekly `responses-weekly.yml` orchestrator runs full Responses API integration tests against OpenAI, Vertex AI, and vLLM MaaS, publishing interactive trend reports to GitHub Pages. This provides confidence that the distribution works across its supported inference backends, not just vLLM.

## Architectural Analysis

**Provider activation pattern:** The distribution's most distinctive architectural decision is its environment-variable-driven provider activation. The `build/build.yaml` config uses `${env.VAR:+provider-name}` syntax, which means providers are only instantiated when their corresponding environment variable is set. This allows a single container image to serve completely different deployment scenarios — from a minimal vLLM-only gateway to a multi-cloud inference hub connecting to Bedrock, WatsonX, Azure, Vertex AI, OpenAI, Gemini, and Anthropic simultaneously. The OGX server evaluates these templates at startup and skips providers whose activation variable is unset.

**Build pipeline with code generation:** The repository uses an unusual pattern where `build/build.py` serves as a code generator run via pre-commit hooks. It creates a temporary Python venv, installs OGX, runs `ogx stack list-deps` to discover all transitive Python dependencies, then generates three auto-generated files: `distribution/config.yaml` (stripped of dependency-only providers), `distribution/requirements.txt` (complete dependency list), and `Containerfile` (from `Containerfile.in` template with OCI labels). A second script `scripts/sync_labels.py` extracts the generated OCI labels and substitutes them into `Dockerfile.konflux.in` to produce `Dockerfile.konflux`. This two-template approach (upstream `Containerfile.in` + downstream `Dockerfile.konflux.in`) accommodates different base images and build processes for ODH vs RHOAI.

**Offline-ready container with pre-cached models:** The `distribution/install-common.sh` script downloads ML models at build time: the Granite embedding model (`ibm-granite/granite-embedding-125m-english`), Docling pipeline models (layout, tableformer, rapidocr, picture_classifier), tiktoken cl100k_base encoding, and the HybridChunker tokenizer. This ensures the container can operate in air-gapped environments without runtime model downloads, which is critical for RHOAI enterprise deployments.

**Dual-build architecture (ODH vs RHOAI):** The repository produces two container images from different Dockerfiles: `Containerfile` (generated from `Containerfile.in`) uses `quay.io/opendatahub/odh-midstream-python-base-3-12:latest` for ODH upstream builds, while `Dockerfile.konflux` (generated from `Dockerfile.konflux.in`) uses the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0-ea.2`) for RHOAI Konflux builds. The Konflux build adds AIPCC-specific tooling (fromager-rpm-check, selftest, scanlibs) and handles markitdown dependency limitations. The Tekton pipelines build for three architectures: x86_64, arm64, and ppc64le.

**Supply chain hermeticity gap:** While the Tekton pipeline declares `hermetic: true`, the `prefetch-input` is empty, meaning all Python packages are fetched at build time from the AIPCC-provided RHEL AI Python Package Index rather than being prefetched and cached. There are no hash-pinned lock files (`uv.lock`, `rpms.lock.yaml`, or `artifacts.lock.yaml`) on this branch. The `distribution/requirements.txt` specifies version ranges but not content hashes. This is a supply chain risk — the Konflux build depends on the availability and integrity of the RHEL AI PyPI at build time. Downstream release branches may add stricter pinning.
