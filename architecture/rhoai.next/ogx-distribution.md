## Purpose

**Short**: Containerized distribution of OGX (the opendatahub-io fork of Llama Stack) providing a pre-configured, multi-provider AI/ML API server for inference, agentic workflows, RAG, and file processing.

**Detailed**: The OGX Distribution repository produces a single container image (`quay.io/opendatahub/odh-ogx-core`) that packages the OGX server with pre-installed provider dependencies, pre-fetched model artifacts (embedding models, OCR models, document layout models), and a configuration-driven provider activation system. The image ships with support for 9+ inference backends (vLLM, OpenAI, Anthropic, AWS Bedrock, Azure, Google Vertex AI, Gemini, WatsonX, sentence-transformers), 4 vector storage backends (Milvus, pgvector, Qdrant, FAISS), file processing (docling, markitdown, pypdf), and tool runtime integrations (web search via Brave/Tavily, file search, MCP).

The repository is not a traditional application codebase — it contains no OGX server source code. Instead, it is a **distribution packaging layer** with build scripts (`build/`) that generate container build files, lock files, and configuration from a declarative source of truth (`build/build.yaml`). The build pipeline uses `pre-commit` hooks to regenerate auto-generated artifacts (Containerfile, config.yaml, distribution README) and CI-driven lock file generation (`gen_lockfile.py`). Providers activate at runtime based on environment variable presence, allowing a single image to serve any deployment scenario. The Konflux downstream build uses AIPCC base images (`quay.io/aipcc/base-images/cpu`) and hermetic dependency resolution via cachi2/Hermeto.

## Architectural Analysis

The OGX Distribution represents a **pure packaging layer** — it contains no OGX server source code, no controllers, and no CRDs. Its architectural significance lies in the build pipeline and the configuration system it produces. The `build/build.yaml` file is the single source of truth for the entire distribution: it defines all providers, their configuration schemas, environment variable bindings, and activation conditions. Four Python scripts (`gen_config.py`, `gen_containerfile.py`, `gen_lockfile.py`, `gen_distro_docs.py`) plus one verification script (`verify_secrets.py`) transform this declarative source into the set of artifacts needed for container builds. This code-generation approach ensures consistency — changing a provider in `build.yaml` automatically cascades to the Containerfile, runtime config, documentation, and secret validation.

The **provider activation pattern** (`${env.VAR:+provider-id}`) is the key architectural mechanism: all providers are baked into the image but only activate when their respective environment variables are set. This allows a single container image to serve diverse deployment scenarios — from a minimal vLLM-only setup to a full multi-cloud configuration with Bedrock, Vertex AI, and OpenAI simultaneously. The 7 "dependency-only" providers (sentence-transformers, milvus-local, faiss, docling, markitdown, pypdf, docling-serve) have their Python packages pre-installed but are stripped from the default `config.yaml` by `gen_config.py`, requiring a custom config mount to activate. This two-tier activation (env-var conditional vs. config-mount required) reflects a tradeoff between operational simplicity and image size.

The **secret management** design is notably robust for a container image. The entrypoint shell script implements `_FILE` variant resolution for all 18 secret environment variables, allowing Kubernetes operators to mount secrets as files rather than injecting them via environment variables. The `verify_secrets.py` pre-commit hook enforces that `build.yaml` secret fields and `entrypoint.sh` file-resolution loops stay in sync — a guard against drift between the configuration source of truth and the runtime secret handling.

The **build hermeticity** story is strong on the Python and ML artifact layers but has a gap at the RPM layer. The Konflux build uses Hermeto (cachi2) to prefetch both Python packages (from `requirements-lock-konflux.txt` with hashes) and generic artifacts (ML models from `artifacts.lock.yaml` with SHA-256 checksums). The lock file generator (`gen_lockfile.py`) resolves dependencies via `ogx stack list-deps` and OpenTelemetry bootstrap, then compiles platform-specific (Linux, Python 3.12) pinned requirements with hashes. The `artifacts.lock.yaml` pins 25 ML model files from HuggingFace and ModelScope with exact SHA-256 checksums, covering the Granite embedding model, Docling layout/figure/table models, RapidOCR models, and tiktoken tokenizer. The absence of `rpms.lock.yaml` on this branch is expected — RPM lock files are typically added on downstream release branches during Konflux release hardening.

The **multi-architecture support** (x86_64, arm64, ppc64le per the Tekton PipelineRun) is notable and aligns with the AIPCC CPU base image's architecture coverage. The CI pipeline (`redhat-distro-container.yml`) runs the full test suite on both amd64 and arm64, with MaaS endpoint overrides available for both architectures.
