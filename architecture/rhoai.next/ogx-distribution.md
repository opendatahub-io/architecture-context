## Purpose

**Short**: Builds and packages the OGX AI/ML API server as a production-ready container image with pre-configured inference, vector storage, and tool runtime providers for Red Hat OpenShift AI.

**Detailed**: ogx-distribution is the container packaging project for [OGX](https://github.com/opendatahub-io/ogx), the opendatahub-io fork of Llama Stack (renamed OGX circa 2026). It produces a single multi-arch (amd64/arm64/ppc64le) container image (`quay.io/opendatahub/odh-ogx-core`) that ships the OGX server (v1.4.0+rhaiv.1) with pre-installed Python dependencies for nine inference providers (vLLM, OpenAI, Anthropic, Azure, Bedrock, WatsonX, Vertex AI, Gemini, sentence-transformers), multiple vector store backends (Milvus, pgvector, Qdrant, FAISS), file processing (docling, markitdown, pypdf), tool runtimes (Brave Search, Tavily, MCP, file-search), and the Responses, Messages, and Batches APIs.

The repository contains no runtime application source code — that lives in `opendatahub-io/ogx`. Instead, ogx-distribution maintains build infrastructure: a `build/build.yaml` master provider manifest, Python scripts that generate the OGX `config.yaml`, lock files, and Containerfile from that manifest, and a comprehensive CI pipeline that builds images, runs smoke and integration tests against vLLM and PostgreSQL, and publishes weekly Responses API test reports across multiple cloud providers. Provider activation is environment-variable-driven: the same config.yaml works for all deployment scenarios, with providers enabling themselves when their corresponding env vars are set (e.g., `VLLM_URL` activates the vLLM inference provider). Pre-trained ML model artifacts (docling, HuggingFace embeddings, tiktoken) are sourced from a ProdSec-scanned "modelcar" OCI image at build time rather than downloaded from external model hubs.

## Architectural Analysis

ogx-distribution follows a code-generation pipeline architecture where the source of truth is `build/build.yaml` and all deployment artifacts (`distribution/config.yaml`, `Containerfile`, lock files, documentation) are machine-generated from it via pre-commit hooks. This design eliminates drift between the provider manifest and what ships in the image. Four generators run in sequence: `gen_config.py` strips dependency-only providers to produce the default config, `gen_containerfile.py` embeds the config as a base64 OCI label in the Containerfile, `verify_secrets.py` validates that every secret env var has `_FILE` support in the entrypoint, and `gen_distro_docs.py` produces the distribution README with the full API/provider table.

The modelcar pattern is architecturally significant: ML model and data artifacts are pre-packaged in a ProdSec-scanned OCI image (`registry.redhat.io/rhai/modelcar-redhatai-ogx-distribution:3.0`) rather than downloaded from external model hubs at build time. This provides supply chain control — the modelcar is scanned before being referenced as a build stage, and the `COPY --from=modelcar` stays hermetic within Konflux's network-isolated builds. A dual-mode system (`OGX_ARTIFACT_SOURCE=pull|cache`) handles the split: main/Konflux builds pull the modelcar directly from the stage registry, while fork CI builds use a GitHub Actions cache copy to avoid needing registry credentials.

The conditional provider activation pattern (`${env.SOME_VAR:+provider-name}`) is architecturally clean: the same container image supports a wide variety of deployment scenarios (local vLLM, cloud-only, hybrid) without image variants. Seven dependency-only providers (sentence-transformers, milvus-inline, faiss, docling, markitdown, pypdf, docling-serve) are installed in the image but stripped from the default config.yaml, requiring a custom config to activate them.

The entrypoint implements a security-conscious secret handling pattern: every secret env var (18 total) supports a `_FILE` variant that reads the secret from a mounted file at startup, avoiding exposure through `/proc/1/environ`. The entrypoint runs `ogx run --insecure`, which disables server-side TLS — TLS termination is expected at the platform level (OpenShift Route, Istio sidecar). Authentication is opt-in via OAuth2 JWT with JWKS validation and an ownership-based access policy engine.

The tenant isolation model is application-enforced: the OGX server's access policy provides per-user ownership filtering on resources (files, vector stores, conversations), with cross-user and cross-tenant isolation verified by the Praxis integration tests. However, all users share the same PostgreSQL instance, inference provider credentials, and vector store backends, making this a soft isolation boundary that depends on application correctness rather than Kubernetes-level enforcement.

_The Konflux build is hermetic for Python packages: cachi2 prefetches all packages declared in `distribution/requirements-lock-konflux.txt` (with SHA256 hash verification via --generate-hashes), and the Dockerfile installs with `--no-index --find-links "${PIP_FIND_LINKS}"`. ML model artifacts are sourced from the modelcar OCI image (a build stage), not downloaded at build time. However, there is no `rpms.lock.yaml` for OS package pinning, which is a hermeticity gap at the RPM layer. The downstream release branch likely adds RPM lock files. The lock files are compiled against the RHAI staging index (`cpu-ubi9-test/simple/`)._

### Tenant Model

| Aspect | Value | Source |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OAuth2 JWT validation with per-user ownership policy (read unowned, create any, manage own) | Application (OGX server) | Auth is optional (disabled when AUTH_ISSUER unset); no Kubernetes-level RBAC isolation |
| Data storage | Shared PostgreSQL database; resources tagged with owner identity | Application (OGX access policy engine) | All users share the same PostgreSQL tables; row-level isolation depends on OGX application correctness |
| Network traffic | None at the component level | Platform (expected: NetworkPolicy, Istio) | Component does not define NetworkPolicies; relies entirely on platform |
| Compute & resources | None at the component level | Platform (expected: ResourceQuota, LimitRange) | Single OGX server process handles all tenants; no per-tenant resource limits or rate limiting |
| Configuration & secrets | Shared configuration (config.yaml); per-user resource ownership | Application | All users share the same inference providers and backend credentials |
| API scoping | Owner-filtered queries (read/update/delete restricted to owner); system resources readable by all | Application (OGX access policy) | Cross-user and cross-tenant isolation verified by Praxis integration tests (tests/integration/praxis/test_tenant_isolation.py) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL (kv_default + sql_default) | Per-user ownership column | Application query filter (OGX access policy engine) |
| Inference providers (vLLM, OpenAI, etc.) | None — shared backend | No isolation; all users share the same provider endpoints and credentials |
| Vector stores (Milvus, pgvector, Qdrant) | Per-user ownership | Application query filter; underlying storage is shared |
