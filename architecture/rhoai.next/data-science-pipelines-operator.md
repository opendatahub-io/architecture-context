## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines (Kubeflow Pipelines v2) stacks on OpenShift, deploying and configuring all sub-components per namespace via the DataSciencePipelinesApplication custom resource.

**Detailed**: The Data Science Pipelines Operator (DSPO) is a controller-runtime operator that reconciles `DataSciencePipelinesApplication` (DSPA) custom resources. Each DSPA instance triggers the deployment of a complete Kubeflow Pipelines v2 stack within a namespace: API server, persistence agent, scheduled workflow controller, Argo Workflows controller, ML Metadata (MLMD) gRPC server with Envoy proxy, and optional MariaDB and MinIO instances for metadata storage and artifact persistence respectively.

The operator uses a manifest-templating pattern powered by manifestival, rendering Go templates from `config/internal/` with parameters resolved from the DSPA spec, operator-level configuration (via Viper), and Kubernetes secrets/configmaps. It performs health checks against configured databases and object stores before deploying workloads, and manages pod-to-pod TLS, OpenShift Route creation, NetworkPolicy enforcement, and webhook registration for PipelineVersion validation.

A second cluster-scoped CRD, `AIPipelines`, provides a platform-level module API for coordinated lifecycle management when deployed under the OpenDataHub/RHOAI operator umbrella. This controller manages Argo Workflows CRDs and cluster-scoped RBAC, handling the transition from legacy per-namespace ownership to centralized platform module control.

## Architectural Analysis

DSPO exhibits a hub-and-spoke operator pattern: a single operator deployment manages multiple independent pipeline stacks, one per DSPA CR, each fully contained within its target namespace. The operator does not share databases or object stores between DSPA instances — each stack receives its own storage backends, providing strong data isolation at the namespace boundary.

The reconcile loop follows a strict ordering: parameter extraction → health checks → component reconciliation (Common → Webhook → ManagedPipelines → APIServer → PersistenceAgent → ScheduledWorkflow → WorkflowController → MLMD). This ordering is architecturally significant because MLMD depends on TLS secrets provisioned by earlier components. Failure at any stage halts reconciliation with status conditions that surface the root cause.

The operator's cache optimization strategy is notable: ConfigMap and Secret data payloads are stripped from the informer cache and read via direct API calls, reducing memory footprint without sacrificing correctness. Watches are further scoped by the `dsp-version` label applied to all operator-managed resources via manifestival transforms.

TLS handling is sophisticated — the operator reads the cluster-wide TLS profile from the OpenShift APIServer CR at startup, falls back to the Intermediate profile on non-OpenShift clusters or when the API is unavailable, and registers a `SecurityProfileWatcher` that triggers a graceful restart when the profile changes. This ensures the metrics and webhook servers always honor the cluster's TLS posture without requiring manual reconfiguration.

The dual-CRD architecture (namespace-scoped DSPA + cluster-scoped AIPipelines) reflects an ongoing platform transition. The AIPipelines controller is gated behind the `ENABLEAIPIPELINESMODULECONTROLLER` flag and coexists with the legacy DSPA controller. When enabled, it manages Argo Workflows CRDs, cluster-scoped RBAC, and ServiceMonitor/PrometheusRule resources that were previously managed directly by the parent platform operator.

### DSPA-Managed MariaDB (Optional)

**Dockerfile**: Operator deploys via template `config/internal/mariadb/`
**Intent**: Default metadata database when no external database is configured. Includes TLS configuration, NetworkPolicy, and generated secrets.
**Language**: MariaDB

### DSPA-Managed MinIO (Optional)

**Dockerfile**: Operator deploys via template `config/internal/minio/`
**Intent**: Default object storage for pipeline artifacts when no external storage is configured. Primarily for development and testing.
**Language**: Go

### PipelineVersion Webhook

**Dockerfile**: Operator deploys via template `config/internal/webhook/`
**Intent**: Validating and mutating webhook for PipelineVersion resources when using the Kubernetes pipeline store. Cleaned up when no DSPA uses the Kubernetes store.
**Language**: Go

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregate RBAC ClusterRoles (admin/edit/view) for DSPA and Pipeline CRDs; per-namespace Roles for Argo controller | Kubernetes RBAC | Aggregate roles provide coarse-grained access; admin role grants full CRUD on all DSPAs in the cluster |
| Data storage | Per-namespace MariaDB deployment or per-DSPA external DB configuration; per-namespace MinIO or external object store | Kubernetes namespace isolation + application configuration | No cross-namespace database access; external DB credentials stored in namespace-scoped Secrets |
| Network traffic | Per-DSPA NetworkPolicy created for MariaDB; operator NetworkPolicy in operator namespace | Kubernetes NetworkPolicy | NetworkPolicy only covers MariaDB; other pipeline components rely on namespace isolation |
| Compute & resources | Each DSPA stack runs in its own namespace with independent deployments | Kubernetes namespace isolation | No ResourceQuota or LimitRange enforcement by the operator; resource limits configurable per DSPA CR |
| Configuration & secrets | Per-namespace Secrets for database credentials, object store keys, TLS certificates | Kubernetes namespace isolation | Operator service account has cluster-wide secret read access (used only within reconcile scope) |
| API scoping | Controller watches DSPA CRs across all namespaces; child resources are namespace-scoped with owner references | Kubernetes owner references + dsp-version label filtering | Cluster-scoped watches on Deployments, ConfigMaps, Secrets (filtered by labels in informer cache) |
