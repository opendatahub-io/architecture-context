## Purpose

**Short**: A batch-oriented language model evaluation harness that runs as a Kubernetes job, executing standardized benchmarks against LLM endpoints via the EvalHub framework.

**Detailed**: lm-evaluation-harness-sobha is a Red Hat downstream fork of EleutherAI's `lm-evaluation-harness` (v0.4.8), adapted for integration with the EvalHub evaluation orchestration platform. The component is packaged as a container image (`odh-ta-lmes-job-rhel9`) that runs as a one-shot Kubernetes job — it receives a job specification via a mounted ConfigMap at `/meta/job.json`, connects to a model inference endpoint using the OpenAI-compatible completions API, executes the configured benchmark tasks, and reports results back to EvalHub via callbacks. Results can optionally be persisted as OCI artifacts and logged to MLflow.

The harness supports over 150 benchmark task categories (from academic benchmarks like HellaSwag, ARC, MMLU to domain-specific evaluations), multiple model backends (HuggingFace, vLLM, OpenAI-compatible endpoints, Anthropic, IBM WatsonX), and offline/air-gapped operation. The Red Hat fork adds the `main.py` EvalHub adapter layer, multi-architecture container builds (amd64, s390x, ppc64le), Unitxt framework integration, and credential-safe error reporting with secret redaction.

## Architectural Analysis

The component's architecture is that of a batch execution wrapper: it receives configuration, executes a single evaluation run, persists results, and exits. There is no long-running service, no inbound API surface, and no persistent state beyond the output artifacts. The architectural complexity lies in three areas:

**Multi-architecture build pipeline**: The Konflux Dockerfile uses a 5-stage multi-stage build to support amd64, s390x, and ppc64le architectures. On s390x and ppc64le, PyArrow and PyTorch are compiled from source (stages 2-3), and on ppc64le OpenBLAS is built from source (stage 4). This creates significant build complexity and long build times for non-amd64 architectures.

**EvalHub adapter pattern**: The `main.py` adapter bridges lm-evaluation-harness with EvalHub's job lifecycle (JobSpec → LMEvalAdapter → JobResults). It handles credential resolution (OpenAI API key, HF token from model auth secrets), auto-detection of offline/disconnected environments via `/test_data` layout inspection, and sanitized error reporting that redacts secrets from error messages before sending them to EvalHub callbacks.

**Model endpoint integration**: Rather than loading models locally, the RHOAI deployment uses the `local-completions` backend to call remote OpenAI-compatible inference endpoints. The adapter constructs the completions URL from the job spec's model URL, configures tokenization via HuggingFace tokenizers, and supports concurrent request batching. TLS certificate verification is configurable with custom CA bundle support for internal endpoints.
