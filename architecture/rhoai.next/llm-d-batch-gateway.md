## Purpose

**Short**: High-performance OpenAI-compatible batch inference gateway for processing large-scale batch jobs in Kubernetes environments.

**Detailed**: llm-d-batch-gateway is a multi-component system that provides an OpenAI-compatible API for submitting, tracking, and managing batch inference jobs. It consists of three independently deployable services: an API server that exposes `/v1/batches` and `/v1/files` endpoints, a batch processor that pulls jobs from a priority queue and dispatches individual inference requests to downstream llm-d routers, and a garbage collector that periodically removes expired jobs and files while reconciling orphaned work from crashed processors.

The system is designed to coexist with interactive inference workloads by using AIMD-based adaptive concurrency control to dynamically adjust batch dispatch rates. The processor groups requests by model and system-prompt hash for prefix cache optimization. Storage is pluggable: PostgreSQL for job/file metadata, Redis/Valkey for the priority queue and event channels, and S3-compatible or filesystem storage for input/output files. Multi-tenancy is enforced at the application layer via tenant ID extraction from a configurable HTTP header (default `X-MaaS-Username`) and row-level isolation in PostgreSQL. Authentication and authorization are delegated to the gateway layer (Kuadrant/Authorino), with the batch gateway itself performing no authentication on its API routes.

## Architectural Analysis

The batch gateway follows a producer-consumer architecture with clear separation between the API surface (apiserver), work execution (processor), and maintenance (gc). The apiserver is stateless and horizontally scalable as a Deployment, while the processor runs as a StatefulSet to provide stable pod identities — essential for the gc's orphan reconciler, which watches processor pods to detect crashes and re-enqueue abandoned jobs.

A notable design decision is the three-way dispatch mode for the processor: "sync" mode with a global gateway URL, "sync" mode with per-model gateway mappings, and "async" mode via `llm-d-async` with Redis-backed queues. This flexibility lets the same codebase serve single-model deployments, multi-model platforms with model-specific routing (including tenant-scoped route keys), and asynchronous dispatch architectures.

The TLS posture is layered: the apiserver supports optional server-side TLS with configurable min version and cipher suites, while the processor supports custom CAs and mTLS for outbound connections to inference gateways. However, the API server exposes all business routes without authentication middleware — this is by design, as authentication is expected to be enforced by an external gateway (Kuadrant/Authorino) fronting the service.

The build configuration uses `CGO_ENABLED=0` with distroless static base images, producing statically-linked binaries. This is optimal for minimal container images but would not pass OpenShift check-payload FIPS validation, which requires dynamically-linked Go binaries with OpenSSL. No Konflux Dockerfiles exist on the analyzed branch, indicating FIPS-compliant builds are likely handled on downstream release branches.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to external gateway (Kuadrant/Authorino) | Gateway layer | The batch gateway itself performs no authentication; if deployed without a gateway, all API routes are unauthenticated |
| Data storage | Row-level isolation via `tenant_id` column in PostgreSQL; all queries include tenant ID filter | Application (PostgreSQL query filters) | Application-enforced: a bug in query construction could leak cross-tenant data. S3 file paths include file IDs but not explicit tenant prefixes |
| Network traffic | No per-tenant NetworkPolicy; relies on cluster-level network isolation | N/A | No network-level tenant isolation within the batch gateway namespace |
| Compute & resources | No per-tenant resource quotas; all tenants share processor workers | N/A | One tenant's large batch jobs could consume all processor workers, starving other tenants |
| Configuration & secrets | Shared secrets (DB URLs, API keys) across all tenants | Kubernetes | All tenants share the same database credentials and inference API key |
| API scoping | All API queries filtered by tenant ID extracted from HTTP header | Application | Tenant ID trusts the header value set by the external gateway; if the gateway is bypassed, any client can impersonate any tenant |
