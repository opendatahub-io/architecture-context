## Purpose

**Short**: OpenAI-compatible batch inference API gateway for the llm-d platform, providing high-performance batch job submission, processing, and lifecycle management.

**Detailed**: The batch-gateway is a multi-component Go service that implements the OpenAI `/v1/batches` and `/v1/files` API for large-scale batch inference workloads in Kubernetes environments. It is designed to process up to 50,000 requests per batch job while minimizing interference with interactive (real-time) inference traffic.

The system comprises three independently deployable components: an **API server** that accepts batch job submissions and file uploads, a **batch processor** that dequeues jobs from a priority queue and dispatches individual inference requests to downstream llm-d routers, and a **garbage collector** that reclaims expired jobs/files and recovers orphaned work from processor crashes. The processor implements AIMD-based adaptive concurrency control to dynamically adjust dispatch rates based on downstream backpressure signals (429, 5xx), protecting interactive workloads without manual tuning.

The batch-gateway integrates with PostgreSQL (metadata), Redis/Valkey (priority queue, events, status), and S3-compatible object storage (batch files). It supports two dispatch modes: synchronous HTTP dispatch directly to inference gateways, and asynchronous dispatch via the llm-d-async library for metrics-driven flow control. Authentication and authorization are delegated to the gateway layer (Kuadrant/Authorino), with tenant isolation enforced at every data access layer via header-based tenant extraction.

## Architectural Analysis

The batch-gateway demonstrates a clean separation of concerns across its three components. The API server is purely a stateless REST frontend -- it validates requests, writes metadata to PostgreSQL, enqueues jobs to Redis, and streams files to S3, but never processes inference requests itself. The processor is the compute-intensive component, implementing a sophisticated multi-stage pipeline (ingestion → execution → finalization) with per-model plan files that enable prefix-cache-aware request ordering. The garbage collector runs as a separate maintenance loop with its own reconciler that recovers orphaned jobs left by crashed processors. This separation allows independent scaling: API servers can be horizontally scaled for throughput, processors scaled for batch capacity, and the GC runs as a singleton.

The concurrency control system is particularly noteworthy. The processor implements a three-tier semaphore hierarchy: worker tokens (limiting concurrent jobs), global concurrency (limiting total in-flight inference requests), and per-endpoint adaptive semaphores managed by AIMD controllers. The AIMD pattern (Additive Increase / Multiplicative Decrease) automatically backs off on 429 (rate limit), 5xx (server error), and capacity-retry signals from downstream inference gateways, then slowly recovers. This protects interactive inference traffic from batch-induced overload without requiring manual concurrency tuning. The adaptive semaphore implementation uses `sync.Mutex + sync.Cond` rather than channels because Go channels cannot be dynamically resized -- a deliberate engineering trade-off documented in the code.

Security follows a defense-in-depth model with authentication delegated to the upstream gateway layer (Kuadrant/Authorino). The API server trusts the tenant identity header (`X-MaaS-Username`) from the gateway, extracts it via `LastHeaderValue()` (compatible with Envoy ext_authz which appends headers), and enforces tenant isolation at every database query by including the TenantID filter. Cross-tenant requests return 404 rather than 403 to hide resource existence. File storage uses SHA256-hashed tenant folder names for path isolation. Pod hardening is comprehensive: non-root execution (UID 65532), read-only root filesystem, all Linux capabilities dropped, seccomp RuntimeDefault profile, and no privilege escalation.

The dual dispatch mode (sync vs async) addresses different deployment scenarios. Sync mode provides direct HTTP dispatch to inference gateways with built-in retry and AIMD flow control -- suitable for single-cluster deployments. Async mode delegates to the llm-d-async library which uses Redis-backed request/result queues and external metrics-driven flow control via a dispatcher component -- suitable for multi-cluster or high-scale deployments where centralized flow control is preferred. The dispatch mode is selected at processor startup and cannot be changed at runtime. Both modes share the same pipeline infrastructure (source → pre-dispatch → AIMD → dispatch → collect), differing only in the final dispatch stage.

One notable gap is the absence of Konflux-specific Dockerfiles on this upstream branch. The existing Dockerfiles use `CGO_ENABLED=0` with distroless base images, producing statically linked binaries that would fail Konflux check-payload FIPS validation. The downstream RHOAI release branch is expected to add Konflux Dockerfiles with UBI base images, dynamic linking, and FIPS build flags. Additionally, no RPM lock files or Hermeto prefetch configuration exists on this branch, leaving OS-level dependency hermeticity to the downstream build process.
