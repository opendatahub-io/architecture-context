## Purpose

**Short**: Intelligent inference request router that provides LLM-aware load balancing, prefix-cache-aware routing, request prioritization, and disaggregated prefill/decode coordination for model-serving pools.

**Detailed**: The llm-d-inference-scheduler (upstream: llm-d Router) is the intelligent entry point for inference traffic in the llm-d ecosystem. It consists of two principal runtime components: the Endpoint Picker (EPP) and the Disaggregation Sidecar (pd-sidecar).

The EPP is a gRPC-based Envoy external processing (ext-proc) service that intercepts inference requests from an L7 proxy (Envoy) and selects the optimal model-serving pod based on KV-cache locality, current load, LoRA adapter availability, and configurable scheduling objectives. It watches Kubernetes resources (InferencePool, InferenceObjective, InferenceModelRewrite, Pods) to maintain a real-time view of the serving pool and scrapes metrics from model-serving endpoints to inform routing decisions. The EPP supports a pluggable architecture with configurable filters, scorers, data-layer sources, flow-control strategies, and protocol parsers, all driven by the EndpointPickerConfig CRD.

The Disaggregation Sidecar (pd-sidecar) runs alongside decode workers in Prefill/Decode (P/D) and Encode/Prefill/Decode (E/P/D) disaggregated inference topologies. It acts as an HTTP reverse proxy that intercepts incoming inference requests, orchestrates prefill on remote workers via KV-cache transfer protocols (NIXL v2, shared storage, SGLang, Mooncake), and forwards the decode phase to the local vLLM instance. It supports multiple KV connector types and optional encoder-connector protocols for multi-modal workloads.

## Architectural Analysis

The llm-d Router follows a separation-of-concerns design where request routing intelligence (EPP) is decoupled from the data plane (Envoy proxy) and the disaggregation coordination (sidecar). This allows the EPP to integrate with multiple proxy implementations -- standalone Envoy in the same pod, Istio service mesh, cloud-managed load balancers, or AgentGateway -- via the standard Envoy ext-proc gRPC protocol.

The plugin framework is the primary extension surface. The EndpointPickerConfig CRD drives plugin instantiation at startup: scheduling profiles compose filters and scorers into named pipelines, data-layer plugins provide endpoint metrics and model metadata, and flow-control plugins implement fairness, ordering, and saturation detection. This configuration-driven approach avoids code changes for common routing policy adjustments.

A notable FIPS compliance gap exists between the two binaries: the sidecar Dockerfile builds with `-tags strictfipsruntime` and `CGO_ENABLED=1`, while the EPP Dockerfile only sets `CGO_ENABLED=1` without the `strictfipsruntime` build tag. Both use UBI 9 minimal as the runtime base image (which includes OpenSSL), but the EPP binary may not enforce FIPS-approved cryptographic algorithms at the Go runtime level.

TLS is configurable but not enforced by default on either component. The EPP's gRPC server optionally loads certificates from a configurable path with filesystem-watch-based reload. The sidecar supports per-stage TLS configuration (prefiller, decoder, encoder) with independent InsecureSkipVerify toggles, and can generate self-signed certificates for its own serving endpoint. Neither component configures explicit TLS minimum version or cipher suite constraints in code -- they rely on Go's default TLS configuration, which inherits FIPS-appropriate settings when the `strictfipsruntime` tag is active.

The controller layer uses conditional watches: the InferenceModelRewrite and InferenceObjective controllers are registered only when the corresponding CRDs are detected via API discovery, allowing the EPP to run in environments where these optional APIs are not installed. The InferencePool controller integrates with the upstream Gateway API Inference Extension (GIE) types from `sigs.k8s.io/gateway-api-inference-extension`.
