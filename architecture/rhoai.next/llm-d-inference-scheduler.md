## Purpose

**Short**: Intelligent LLM inference request router that provides KV-cache-aware scheduling, disaggregated inference orchestration, and flow control for model server pools via the Kubernetes Gateway API Inference Extension.

**Detailed**: The llm-d Router is the intelligent entry point for inference traffic in the llm-d serving stack. It comprises two deployable components: the **Endpoint Picker (EPP)**, which integrates with Envoy proxy via the ext-proc gRPC protocol to make real-time routing decisions, and the **Disaggregation Sidecar (pd-sidecar)**, which coordinates multi-stage inference lifecycles (Prefill/Decode and Encode/Prefill/Decode) by managing KV-cache transfers between specialized model server pods.

The EPP implements a pluggable framework architecture with scheduling profiles, filters, scorers, and pickers that evaluate incoming requests against model server state — including KV-cache utilization, prefix cache locality, queue depth, active request counts, and LoRA adapter affinity — to make optimal endpoint placement decisions. It supports the Kubernetes Gateway API Inference Extension (`InferencePool`) for integration with any compliant L7 proxy, and defines its own CRDs (`InferenceObjective` for request prioritization, `InferenceModelRewrite` for model name-based traffic management including A/B testing and canary rollouts).

The router supports two deployment modes: **Gateway Mode** (recommended for production, where the EPP acts as a backend for an InferencePool referenced by HTTPRoutes on a shared Gateway) and **Standalone Mode** (where a self-managed Envoy proxy runs alongside the EPP in the same pod). It supports multiple inference API formats (OpenAI, Anthropic, VertexAI, vLLM HTTP/gRPC) and advanced flow control with per-priority-band fairness, request eviction, and saturation detection.

### Disaggregation Sidecar (pd-sidecar)

**Dockerfile**: `Dockerfile.sidecar.konflux`
**Intent**: A sidecar module deployed alongside decode model server pods to orchestrate disaggregated inference. Only deployed when disaggregated serving (P/D or E/P/D) is enabled for an InferencePool.
**Image**: `odh-llm-d-routing-sidecar`
**Language**: Go
**Port**: 8000/TCP (HTTP/HTTPS)

## Architectural Analysis

The llm-d Router implements a sophisticated plugin-based architecture that cleanly separates concerns across four layers: **request handling** (protocol parsing), **request control** (admission, data production, pre-request hooks), **scheduling** (filtering, scoring, picking), and **flow control** (queuing, eviction, fairness). Each layer is defined by Go interfaces with implementations registered as named plugins in the `EndpointPickerConfig`, allowing operators to compose different scheduling strategies without modifying code. This is conceptually similar to the Kubernetes scheduler framework, and the project explicitly draws on that pattern.

The ext-proc integration with Envoy is the primary architectural decision that distinguishes this from a standalone proxy: by operating as a gRPC sideband processor, the EPP avoids being in the critical data path for response streaming. The Envoy proxy handles the actual HTTP/gRPC proxying, TLS termination, and connection management, while the EPP only processes request headers/body to select an endpoint and response headers/body to collect metrics. This separation means the EPP can be upgraded or restarted without dropping existing connections, and Envoy's battle-tested connection handling provides reliability. The trade-off is latency: every request incurs a gRPC round-trip to the EPP before the proxy can forward it.

The disaggregation sidecar is architecturally distinct from the EPP — it runs as a separate binary (`pd-sidecar`) deployed as a sidecar container in decode worker pods. It implements a reverse proxy pattern with pluggable "connectors" (NIXL V2, Mooncake, SGLang, shared storage) that abstract the KV-cache transfer mechanism. The NIXL V2 connector is the recommended default, using remote KV reference passing where the prefill worker produces KV-cache metadata that the sidecar injects into the decode request. The MoRI-IO extension adds RDMA Write-mode support for zero-copy transfers. This multi-connector design allows operators to choose the transfer mechanism that matches their hardware capabilities (InfiniBand, shared filesystem, etc.) without changing the sidecar deployment.

A notable security concern is the default `InsecureSkipVerify: true` for model server metrics and models scraping. This means the EPP does not verify TLS certificates when scraping model server endpoints, which could allow MITM attacks in environments without network isolation. The sidecar addresses a related concern with optional SSRF protection — when enabled, it validates that prefill and encoder target addresses resolve to pods in the InferencePool's pod selector, preventing request forgery to arbitrary endpoints.

The FIPS compliance posture differs between the two components: the sidecar Dockerfile includes `-tags strictfipsruntime` for proper FIPS crypto linking, while the EPP Konflux Dockerfile uses `CGO_ENABLED=1` (required for dynamic linking) but omits the `strictfipsruntime` tag. This may represent a gap in the EPP's FIPS compliance story, though the UBI 9 base image provides OpenSSL which the Go runtime can use for crypto operations when dynamically linked. Both components generate self-signed certificates at startup when no certificates are provided, which is appropriate for development but should be replaced with properly provisioned certificates (via cert-manager or a secrets operator) in production.
