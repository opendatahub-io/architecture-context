## Purpose

**Short**: Intelligent LLM inference request router that provides KV-cache-aware scheduling, request prioritization, and disaggregated prefill/decode orchestration via the Envoy ext-proc protocol.

**Detailed**: The llm-d Router is the intelligent entry point for inference traffic in the llm-d platform. It consists of two deployable components: the **Endpoint Picker (EPP)** and the **Disaggregation Sidecar (pd-sidecar)**.

The EPP integrates with production-grade L7 proxies (primarily Envoy) via the ext-proc protocol, injecting real-time routing decisions into the data plane. It evaluates incoming requests against model server metrics (KV cache utilization, queue depth, active requests), prefix cache locality, and priority objectives to make optimal placement decisions. The EPP supports a pluggable framework with configurable filters, scorers, and pickers organized into scheduling profiles. It also implements flow control with priority-based queuing, eviction policies, and saturation detection.

The Disaggregation Sidecar runs alongside vLLM decoder instances and orchestrates complex multi-stage inference lifecycles. It supports Prefill/Decode (P/D) and Encode/Prefill/Decode (E/P/D) disaggregation strategies via multiple connector backends (NIXLv2 for RDMA-based KV transfer, SGLang room-based pooling, Mooncake engine ID bootstrap, and shared-storage cache-first decode). Both components integrate with the Kubernetes Gateway API Inference Extension ecosystem, consuming InferencePool CRDs to discover model server endpoints and InferenceObjective/InferenceModelRewrite CRDs for priority and traffic management.

## Architectural Analysis

The llm-d Router demonstrates a sophisticated plugin-based architecture inspired by the Kubernetes scheduler framework. The EPP's scheduling pipeline is organized as a three-stage process — Filter → Score → Pick — executed within named profiles. A ProfileHandler selects which profiles to run per request, enabling complex routing strategies like disaggregated P/D scheduling where separate prefill and decode profiles choose different endpoints based on different criteria (prefix cache locality for prefill, queue depth for decode). The plugin framework supports 13 extension points across scheduling, request control, and request handling layers, all resolved via a central plugin registry with factory-based instantiation.

The flow control system is particularly well-engineered, using a single-goroutine actor model (the Processor) for all state mutations to avoid lock contention on the hot path. The FlowRegistry uses `sync.Map` and atomic counters for lock-free request operations, while administrative operations (topology changes, priority band updates) are protected by a RWMutex. This hybrid concurrency model is critical for a component that sits in the request path of every inference call. The eviction system uses a min-heap for O(log n) eviction selection with pluggable ordering and filtering policies.

The data layer architecture implements a topological sort (Kahn's algorithm) for plugin dependency resolution, automatically ordering data producers so that each producer's dependencies are satisfied before it executes. This enables complex data pipelines — for example, a latency predictor producer can depend on a tokenizer producer, which in turn depends on a metrics source. The system even auto-instantiates missing producers from a default registry when a consumer declares a required data key with no explicit producer.

A notable architectural gap is the FIPS compliance asymmetry between the two Konflux Dockerfiles: the sidecar builds with `-tags strictfipsruntime` (full FIPS compliance), but the EPP Dockerfile uses `CGO_ENABLED=1` without the strictfipsruntime tag. While CGO_ENABLED=1 enables dynamic linking (required by check-payload), the missing tag means the EPP binary may not enforce FIPS-approved algorithms at the Go crypto layer. Both images use UBI 9 minimal as the runtime base, which provides OpenSSL, but the inconsistency should be resolved for production FIPS deployments. Additionally, the EPP's model server metrics scraping defaults to `insecureSkipVerify=true`, which is a practical choice for same-cluster communication but bypasses TLS certificate validation.

The sidecar's connector abstraction cleanly separates KV transfer mechanisms from routing logic. Each connector (NIXLv2, SGLang, Mooncake, shared-storage) implements a distinct KV cache transfer protocol while sharing the same E→P→D request flow orchestration. The NIXLv2 connector supports both serial (READ-mode: prefill reads from decode's allocated blocks) and parallel (WRITE-mode: prefill pushes via RDMA Write to decode) dispatch patterns, with Wide-EP fan-out for multi-pod tensor-parallel deployments. The SSRF protection via InferencePool allowlisting is well-designed — the sidecar watches the InferencePool's pod selector and maintains a live set of allowed pod IPs, rejecting any prefill/encoder target not in the set.
