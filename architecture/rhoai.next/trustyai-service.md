## Purpose

**Short**: Python REST API for Responsible AI workflows including drift detection, fairness monitoring, and model explainability, operating as a sidecar to KServe-based inference services on OpenShift AI.

**Detailed**: TrustyAI Service is a FastAPI-based Python service that provides real-time AI model monitoring capabilities within the Red Hat OpenShift AI platform. It consumes inference payloads from KServe and ModelMesh inference services via CloudEvents, stores the data in either PVC-backed HDF5 files or MariaDB, and computes statistical metrics on a configurable schedule that are published to Prometheus for alerting and dashboarding.

The service implements a comprehensive suite of drift detection algorithms (Kolmogorov-Smirnov, Jensen-Shannon divergence, Maximum Mean Discrepancy, Compare Means, streaming KS variants with Greenwald-Khanna quantile sketches) and fairness metrics (Statistical Parity Difference, Disparate Impact Ratio), with experimental explainability endpoints (LIME, SHAP, PDP, counterfactuals, time-series saliency) gated behind feature flags. The architecture separates traffic into two Hypercorn server instances: a health/consumer server on port 8080 (exposed to kubelet and KServe agents) and a metrics/API server on port 8081 (loopback-only, accessed via kube-rbac-proxy) with optional direct HTTPS on port 4443. This split ensures health probes and data ingestion remain accessible while the sensitive API surface is protected by the platform's authentication proxy.

The service represents a complete rewrite of the original Java/Quarkus-based TrustyAI service, maintaining wire compatibility with the KServe agent and operator-managed deployment model while gaining Python-native ML library access (scikit-learn, scipy, pandas, polars) and a modern async architecture.

## Architectural Analysis

TrustyAI Service employs a dual-server architecture that cleanly separates concerns between data ingestion and API exposure. The primary design decision is the split of Hypercorn into two independent server instances: a publicly-bound health/consumer server (port 8080, all interfaces) and a loopback-restricted API server (port 8081, 127.0.0.1 only). This split is security-critical -- the API server binds only to loopback because kube-rbac-proxy forwards authenticated requests to it, while the health server must be reachable by kubelet probes and KServe inference loggers that operate outside the authentication boundary. The optional HTTPS listener on port 4443 provides a direct-access path with TLS termination at the application layer.

The TLS implementation (`PolicyAwareConfig` in `service/tls.py`) is architecturally notable: it subclasses Hypercorn's `Config` to prevent the framework from overriding the system crypto policy. Rather than hardcoding cipher suites or TLS versions, it delegates to Python's `ssl.create_default_context()`, which inherits the cluster's crypto policy set by `update-crypto-policies`. This means the service automatically honors FIPS crypto policy when deployed on a FIPS-enabled cluster, without requiring application-level FIPS configuration. The upstream Containerfile additionally sets `DEFAULT:PQ` (post-quantum) crypto policy.

The feature flag system (`TRUSTYAI_ENABLE_*` environment variables) controls endpoint registration at startup time, not at request time. Disabled endpoints are never added to the FastAPI router, reducing attack surface and eliminating runtime overhead for unused features. Explainer endpoints default to disabled (experimental, computationally expensive), while drift and fairness metrics default to enabled. The two-level gating (group flag + individual metric flag) allows operators to disable entire metric families or fine-tune individual metrics.

The storage abstraction is clean but carries a significant architectural asymmetry: PVC storage is always available (using h5py for HDF5 files), while MariaDB support requires the optional `mariadb` extra and a native `libmariadb` connector. The MariaDB backend includes TLS support (via `DATABASE_TLS_CA_CERT`) and a migration path from PVC-to-database that runs at startup and integrates with readiness probes. The Containerfile installs MariaDB Connector/C with a CVE floor check (>= 3.4.9 for CVE-2026-44172) and sets the crypto policy to `DEFAULT:PQ` (post-quantum).

The Prometheus scheduler runs as an asyncio background task that periodically (default 30s) reads stored inference data, computes all registered metrics, and publishes results as Prometheus gauges. The scheduler uses thread-safe data structures for request registration and is resilient to per-model calculation failures -- errors are logged but do not crash the scheduler loop. This fire-and-forget design prioritizes availability over metric freshness, which is appropriate for drift detection workloads where delayed metrics are acceptable but service outages are not.

| Compute & resources | Per-deployment resource limits (operator-managed) | Kubernetes | No resource limits defined in the repo; background scheduler processes all models sequentially |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps | Kubernetes / Operator | Database credentials passed via environment variables; secret rotation not automated |
| API scoping | Single-namespace, single-instance; model_id parameter scopes data access | Application | No cross-namespace API access possible; each instance operates only on its own storage |
