## Purpose

**Short**: Platform operator that manages the full lifecycle of Red Hat OpenShift AI (RHOAI) components, services, and infrastructure on OpenShift and vanilla Kubernetes clusters.

**Detailed**: The rhods-operator is the central control plane for RHOAI. It manages two primary cluster-scoped singleton CRDs: DSCInitialization (DSCI) for platform-wide initialization (namespaces, monitoring, authentication, CA bundles, gateway infrastructure), and DataScienceCluster (DSC) for component lifecycle management. The operator deploys and manages 14+ AI/ML components (Dashboard, KServe, Kueue, Data Science Pipelines, Model Registry, Workbenches, TrustyAI, Ray, Training Operator, Trainer, Feast Operator, OGX, Spark Operator, Model Controller) and 4 out-of-tree module operators (AIGateway, MLflowOperator, MCPLifecycleOperator, Monitoring) through a DAG-based provisioning system with runlevel ordering.

The operator also deploys the platform's entire ingress infrastructure: a Gateway API-based ingress stack with Envoy proxy, EnvoyFilter CRs for authentication, kube-auth-proxy (OAuth2/OIDC), dashboard redirect services, and OpenShift Routes. It supports four platform types: ManagedRhoai (add-on), SelfManagedRhoai (customer-managed), OpenDataHub (community), and XKS (vanilla Kubernetes via Platform CR). The operator manages comprehensive observability (Prometheus, Tempo, OpenTelemetry, Perses), RBAC (admin/user group bindings), trusted CA bundle distribution, and hardware profiles for GPU scheduling.

## Purpose

**Short**: rhods-operator is the RHOAI platform operator that orchestrates the full lifecycle of 16 AI/ML components, 3 platform services, and multi-cloud Kubernetes engine integrations through a hierarchical CRD reconciliation model.

**Detailed**: rhods-operator is the central control-plane operator for Red Hat OpenShift AI (RHOAI). It implements a two-tier custom resource hierarchy: a cluster-scoped `DataScienceCluster` (DSC) CR serves as the top-level declaration of desired platform state, while `DSCInitialization` (DSCI) handles one-time cluster preparation such as namespace creation, RBAC setup, and platform service bootstrapping. The DSC controller reconciles user intent into individual component CRDs (Dashboard, DataSciencePipelines, FeastOperator, Kserve, Kueue, MLflowOperator, ModelController, ModelRegistry, ModelsAsService, OGX, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI, Workbenches) — each a cluster-scoped singleton that the corresponding component controller deploys via kustomize-based manifest rendering. Three platform service CRDs (Auth, GatewayConfig, Monitoring) manage cross-cutting infrastructure: Gateway API ingress with Envoy, authentication enforcement via kube-rbac-proxy, and Prometheus/Perses-based monitoring. A cloud manager subsystem introduces three additional CRDs (AWSKubernetesEngine, AzureKubernetesEngine, CoreWeaveKubernetesEngine) that abstract multi-cloud Kubernetes cluster lifecycle through a shared `KubernetesEngineInstance` interface with dependency tracking and readiness conditions. The Dashboard component CRD carries a `Gateway` spec field synced from GatewayConfig, linking per-component ingress configuration to the platform gateway. The operator exposes admission webhooks for DataScienceCluster validation, HardwareProfile defaulting, and Notebook mutation (sidecar injection, resource governance). Overall, rhods-operator manages 27 CRDs across 6 API groups, owns 132 integration points with the Kubernetes API, and coordinates with Gateway API, prometheus-operator, OpenShift cluster configuration, and the models-as-a-service library.

## Data Flows

- **User intent ingress:** A cluster administrator creates or updates a `DataScienceCluster` CR, declaring which AI/ML components should be enabled and their configuration. The DSC controller translates this into individual component CRDs. In parallel, `DSCInitialization` ensures the platform namespace exists, RBAC is configured, and platform services (Auth, GatewayConfig, Monitoring) are bootstrapped with defaults.
- **Hierarchical reconciliation:** Each component controller (Dashboard, Kserve, Kueue, etc.) watches its own singleton CRD and reconciles it into Kubernetes resources via kustomize manifest rendering, using the `k8s-manifest-kit/engine` and `renderer-helm` libraries. Controllers own Deployments, Services, ConfigMaps, Secrets, ClusterRoles, ClusterRoleBindings, NetworkPolicies, HTTPRoutes, and OpenShift Routes. The componentHandler and serviceHandler watch patterns propagate changes through owned and watched resources.
- **Gateway and ingress flow:** The GatewayConfig service controller manages the platform Gateway CR, Envoy proxy deployment, EnvoyFilter CRs, and kube-rbac-proxy sidecars. Individual component controllers create HTTPRoute CRs referencing the parent Gateway. The Dashboard component receives its gateway configuration through a `Gateway` spec field synced from GatewayConfig, ensuring consistent ingress across all components. Legacy redirect Routes and nginx services handle backward-compatible URL transitions.
- **Cloud manager flow:** The cloud manager subsystem reconciles AWSKubernetesEngine, AzureKubernetesEngine, and CoreWeaveKubernetesEngine CRDs. Each implements the `KubernetesEngineInstance` interface providing dependency configuration and readiness conditions (Ready, DependenciesAvailable). These singletons (e.g., "default-awskubernetesengine") abstract provider-specific cluster lifecycle.
- **Admission control:** Three webhook paths intercept resource creation and updates: a validating webhook prevents invalid DSC configurations, a mutating webhook defaults HardwareProfile resources (with 562 lines of defaulting logic), and a notebook mutating webhook injects sidecars and enforces resource policies using SubjectAccessReview authorization checks.
- **Monitoring egress:** The monitoring service controller creates PodMonitor, ServiceMonitor, and PrometheusRule CRs to wire component metrics into the cluster's Prometheus stack. The operator itself exposes a metrics service on port 8443.
- **Security context:** Webhook endpoints on port 9443 are secured with TLS certificates provisioned by the OpenShift service-ca operator. Health and readiness probes on port 8081 are intentionally unauthenticated. All Kubernetes API interactions use ServiceAccount-bound TLS 1.2+ connections.

## Architectural Analysis

The rhods-operator is architecturally the most complex component in the RHOAI platform. It functions as a meta-operator — an operator that manages other operators and platform services. The design centers on two complementary provisioning paths: **in-tree components** (deployed via kustomize manifests bundled in the operator image) and **out-of-tree modules** (deployed via Helm charts or kustomize as separate operator Deployments). Both paths share a unified DAG provisioning system that ensures correct ordering and readiness gating through runlevels.

The **DAG-based provisioning system** is a notable design choice. Components are assigned runlevels (RL(20) for core AI/ML, RL(31) for the serving stack, RL(32) for independent extensions, RL(33) for KServe-dependent components), and the `WalkBatches` function processes them in order, waiting for all components in a batch to reach Ready before advancing. A `StuckTracker` detects components that remain not-ready for too long (default 10 minutes) and can force advancement to prevent cascading blocks. This pattern provides deterministic, upgrade-safe provisioning while avoiding dependency deadlocks.

The **ingress architecture** is sophisticated and layered. The Gateway service controller deploys a full stack: a Kubernetes Gateway API Gateway CR with HTTPS listeners, an Istio EnvoyFilter for ext_authz-based authentication (calling kube-auth-proxy), a Lua filter for token extraction and header manipulation, kube-auth-proxy Deployments (OAuth2 or OIDC mode), DestinationRule for TLS to backends, and OpenShift Routes for backward-compatible URL redirects. The dashboard redirect subsystem deploys nginx pods that 301-redirect legacy dashboard and gateway URLs to the new Gateway API hostname. This multi-layer ingress design reflects the RHOAI 3.x migration from Route-based ingress to Gateway API while maintaining backward compatibility.

The **dual-mode architecture** (DSC mode for OpenShift, Platform CR mode for xKS) is cleanly implemented through the `PlatformContext` abstraction. Module handlers check which context object is present (DSC/DSCI vs Platform CR) and adapt their behavior — for example, on xKS the operator doesn't create module CRs (the Helm chart handles it), while on OpenShift it constructs the CR from DSC spec fields. This shared-code approach reduces divergence while supporting fundamentally different deployment models.

One notable risk area is the **singleton pattern enforcement**. Both DSC and DSCI are cluster-scoped singletons enforced by validating webhooks, with DSCI deletion blocked when a DSC exists. While this prevents orphaned resources, it means the entire platform configuration is a single point of failure — a corrupted DSC or DSCI can block all component operations. The operator mitigates this with leader election init bootstrapping that creates default CRs if missing.

The **observability subsystem** is comprehensive — the Monitoring service controller deploys Prometheus (via MonitoringStack CR), Tempo (traces), OpenTelemetry Collector (telemetry aggregation), Perses (dashboarding), and Thanos Querier (multi-cluster metrics) — but it introduces significant operator dependency on the Cluster Observability Operator, Tempo Operator, OpenTelemetry Operator, and Perses Operator. These are all conditionally deployed based on CRD availability, making the actual deployed stack dependent on which operators are installed. The monitoring multi-tenancy is enforced through prom-label-proxy, which restricts Prometheus queries to namespace-scoped metrics.

## Architectural Analysis

The rhods-operator is the architectural backbone of RHOAI, implementing a declarative platform-as-code model where a single `DataScienceCluster` CR drives the entire AI/ML platform state. Its design follows a hierarchical reconciliation pattern: the DSC controller fans out user intent into 16 component CRDs and 3 service CRDs, each reconciled by a dedicated controller with its own watch set, owned resources, and kustomize-based manifest pipeline. This separation allows individual components to be enabled, disabled, or reconfigured independently while maintaining a unified lifecycle through the parent DSC.

The operator's CRD surface spans 6 API groups reflecting clear architectural boundaries: `components.platform.opendatahub.io` for AI/ML workload components, `services.platform.opendatahub.io` for cross-cutting platform services (Auth, GatewayConfig, Monitoring), `datasciencecluster.opendatahub.io` and `dscinitialization.opendatahub.io` for top-level platform lifecycle, `infrastructure.opendatahub.io` for HardwareProfiles and cloud manager engine CRDs, and `features.opendatahub.io` for feature tracking. The cloud manager CRDs (AWSKubernetesEngine, AzureKubernetesEngine, CoreWeaveKubernetesEngine) are a notable addition, sharing a common `KubernetesEngineInstance` interface with dependency tracking and condition-based readiness. Each is a cluster-scoped singleton enforced via CEL validation rules — for example, `AWSKubernetesEngine` must be named `default-awskubernetesengine`. This pattern ensures exactly one cloud engine configuration exists per provider type, preventing conflicting state.

The Dashboard CRD illustrates how component-level ingress is coordinated: its spec includes an optional `Gateway` field of type `common.GatewaySpec`, which the DSC controller syncs from the platform-level GatewayConfig service CR. This design decouples per-component ingress requirements from the centralized gateway management, allowing the gateway controller to own the Envoy/Gateway API infrastructure while components declare their routing needs through HTTPRoute CRs. The Dashboard also exposes a URL in its status, providing a discoverable entry point for the RHOAI web console.

The integration footprint of 132 points reflects the operator's role as the platform's central nervous system. It watches and owns resources across nearly every Kubernetes API group: core resources (ConfigMaps, Secrets, Services, Namespaces), workload resources (Deployments, DaemonSets, Jobs), networking resources (NetworkPolicies, HTTPRoutes, Routes), security resources (ClusterRoles, ClusterRoleBindings, SecurityContextConstraints), and monitoring resources (ServiceMonitors, PodMonitors, PrometheusRules). The operator also reads OpenShift cluster configuration (APIServer, Authentication, ClusterVersion, Infrastructure) to adapt its behavior to the cluster environment, and accesses the IngressController resource to coordinate with OpenShift's ingress infrastructure.

A key architectural risk is the operator's breadth: a single controller-manager binary owns the reconciliation of 20+ CRDs and their transitive resource graphs. The 46 RBAC rules and wide API group access reflect this breadth. The v1-to-v2 API migration path (visible in both DataScienceCluster and DSCInitialization having v1 and v2 versions) indicates active API evolution, with the v2 APIs likely representing the current target schema. The presence of `k8s-manifest-kit/engine` and `renderer-helm` as dependencies suggests the operator is moving toward a more flexible manifest rendering pipeline that can consume both kustomize and Helm charts, consistent with the RHOAI 3.x architecture direction.
