## Purpose

**Short**: The central platform operator for Red Hat OpenShift AI (RHOAI) that orchestrates the lifecycle of all AI/ML platform components, manages platform ingress infrastructure, and enforces authentication and authorization policies across the data science cluster.

**Detailed**: rhods-operator is the top-level Kubernetes operator for RHOAI. It uses three cluster-scoped custom resources — `DSCInitialization` (platform bootstrapping and global settings), `DataScienceCluster` (component enablement and configuration), and `GatewayConfig` (ingress and authentication policy) — to declaratively manage the full AI/ML platform stack. The operator follows a modular architecture with separate controller domains: component controllers deploy downstream AI/ML components (dashboard, KServe, Ray, Kueue, TrustyAI, model registry, workbenches) by rendering and applying kustomize manifests fetched from component repositories; service controllers manage cross-cutting platform infrastructure including the Gateway API ingress stack, authentication (kube-auth-proxy with OIDC/OAuth), RBAC group management, certificate propagation, and Prometheus monitoring; and a module controller handles pluggable extensions like MLflow and the KServe module operator.

The operator deploys RHOAI's complete ingress infrastructure: a Kubernetes Gateway API `Gateway` CR as the platform entry point, `HTTPRoute` CRs for per-component routing, an Envoy proxy data plane, `EnvoyFilter` CRs for traffic shaping and auth integration, `kube-auth-proxy` deployments for OIDC/OAuth authentication, `DestinationRule` CRs for self-signed certificate TLS enforcement, `NetworkPolicy` for ingress isolation, and OpenShift `Route` CRs for legacy URL redirects. A secondary `cloudmanager` binary provides Cobra-based CLI tooling for cloud infrastructure management (AWS EKS, Azure AKE, CoreWeave) via additional cluster-scoped CRDs.

## Architectural Analysis

The rhods-operator's architecture reflects its role as the platform's control plane — it is the single point of orchestration for all AI/ML components, ingress infrastructure, and access control. Several patterns and design decisions are worth highlighting:

**Component lifecycle as a DAG.** Components and services are registered with explicit run-levels and organized into a directed acyclic graph. The reconciliation framework executes actions sequentially within each controller, stopping on first error, with garbage collection always last. This ensures deterministic ordering — for example, the gateway infrastructure must be ready before components that register HTTPRoutes against it. Component and service controllers can be individually suppressed via flags, enabling partial platform deployments.

**Dynamic resource creation.** The gateway controller exemplifies a pattern where significant Kubernetes resources (GatewayClass, Gateway, EnvoyFilter, DestinationRule, Deployment, HPA) are created programmatically during reconciliation rather than declared in static manifests. The controller detects cluster capabilities at runtime — checking for Istio CRDs before creating EnvoyFilter resources, checking for OpenShift before creating Routes, and checking for cert-manager before creating Certificate resources. This makes the operator adaptable across OpenShift, vanilla Kubernetes, and managed cloud environments (ROSA), but also means the full resource footprint is only visible through code analysis.

**TLS profile adherence.** The operator reads the cluster-wide TLS security profile from the OpenShift `APIServer` resource at startup and applies it to both the webhook server and metrics endpoint. A `SecurityProfileWatcher` monitors for profile changes and triggers a pod restart to pick up new settings. When the profile is unavailable (non-OpenShift or transient errors), the operator defaults to TLS 1.2 with Intermediate cipher suites. This same profile resolution flows into kube-auth-proxy template arguments.

**Auth delegation model.** Rather than implementing authentication directly, the operator deploys kube-auth-proxy as a separate Deployment fronting the platform gateway. Two authentication modes are supported: integrated OAuth (OpenShift OAuth via OAuthClient CR) and OIDC (external identity provider). The auth service controller dynamically creates per-group RBAC (admin groups get full CRD access, allowed groups get read-only) and watches specific namespaces (`models-as-a-service`, `kuadrant-system`) to react to MaaS and Kuadrant installations.

**Manifest rendering pipeline.** Component manifests are not stored in the operator repository. They are fetched from component repos at build time (pinned via `manifests-config.yaml` with SHA references), bundled into `/opt/manifests-template` in the container image, and rendered at runtime using kustomize APIs and Go templates. This decouples the operator release cadence from individual component releases while maintaining reproducibility through SHA pinning.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Group-based RBAC: admin groups get full CRD CRUD + namespace management; allowed groups get read-only platform access | Kubernetes RBAC (operator creates ClusterRoles, ClusterRoleBindings, Roles, RoleBindings per group) | Group membership from OpenShift `user.openshift.io` — no per-user tenant scoping |
| Data storage | Per-namespace PVCs, Secrets, ConfigMaps for data science projects | Kubernetes namespace isolation | Shared operator namespace holds platform-wide secrets |
| Network traffic | NetworkPolicy created per kube-auth-proxy deployment; ingress can be disabled via GatewayConfig.Spec.NetworkPolicy | Kubernetes NetworkPolicy | NetworkPolicy only covers kube-auth-proxy; component-level network isolation delegated to components |
| Compute & resources | Not enforced by operator; delegated to Kueue (job queuing) and namespace ResourceQuotas | Kubernetes / Kueue | Operator does not create ResourceQuotas — relies on cluster admin configuration |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps for component configuration | Kubernetes namespace scoping | Operator service account has broad cluster-wide access for component deployment |
| API scoping | Cluster-scoped operator watches (DSC, DSCI, GatewayConfig, Auth); namespace-scoped watches filtered by specific names | Kubernetes cache filters | Auth controller watches specific namespace names (`models-as-a-service`, `kuadrant-system`) |
