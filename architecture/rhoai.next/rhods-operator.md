## Purpose

**Short**: The rhods-operator is the platform operator for Red Hat OpenShift AI (RHOAI), managing the full lifecycle of all AI/ML platform components, ingress infrastructure, authentication, monitoring, and RBAC.

**Detailed**: The rhods-operator (also known as opendatahub-operator) is the central orchestration layer for the RHOAI platform. It implements a hierarchical controller architecture where two top-level Custom Resources — `DSCInitialization` (cluster initialization) and `DataScienceCluster` (component management) — drive the deployment of 16+ AI/ML components (Dashboard, KServe, Kueue, Ray, Model Registry, etc.) and 3 modules (AIGateway, MLflowOperator, MCPLifecycleOperator).

The operator deploys the platform's entire ingress infrastructure via the Gateway controller, which manages Kubernetes Gateway API resources (Gateway, HTTPRoute), Envoy proxy with EnvoyFilter CRs for ext_authz authentication, kube-auth-proxy (an OAuth2 proxy supporting OpenShift OAuth and external OIDC), dashboard redirect services, and OpenShift Routes. The Auth controller manages platform-wide RBAC with admin groups, allowed groups, and component-specific roles.

A comprehensive monitoring stack is deployed via the Monitoring service controller, including Prometheus (via MonitoringStack operator), Tempo for distributed tracing, OpenTelemetry collectors, Perses for dashboards, and Thanos for federated queries. The operator also includes a CloudManager subsystem for managing cloud-provider-specific Kubernetes engine configurations (AWS, Azure, CoreWeave) with Helm chart-based dependency management.

## Architectural Analysis

The rhods-operator is one of the most architecturally sophisticated operators in the RHOAI ecosystem. It implements a **three-tier controller hierarchy**: top-level controllers (DSCInitialization, DataScienceCluster) create service CRs (Auth, GatewayConfig, Monitoring) and component CRs (Dashboard, KServe, etc.), which are then reconciled by their own dedicated controllers. This design provides clean separation of concerns — each controller owns a single CRD and manages a well-defined set of resources.

The **DAG-based component provisioning** system (`pkg/controller/dag/`) assigns components to runlevels (20, 31, 32, 33) that determine deployment order. Core components deploy at level 20, the serving stack (KServe, ModelController, Kueue) at level 31, independent extensions at level 32, and KServe-dependent components (TrustyAI) at level 33. This ensures dependencies are satisfied before dependent components start reconciling.

The **Gateway controller** (`internal/controller/services/gateway/`) is the most complex single controller in the operator. It deploys a full multi-layer ingress stack: GatewayClass → Gateway → Envoy proxy (via Istio sidecar) → EnvoyFilter (ext_authz + Lua) → kube-auth-proxy (OAuth2 proxy) → backend applications. The controller supports two ingress modes (OcpRoute with ClusterIP, LoadBalancer with external IP) and three authentication modes (OpenShift OAuth, external OIDC, external auth bypass). The Lua filter in the EnvoyFilter performs sophisticated cookie stripping and token forwarding that bridges the gap between OAuth2 proxy session cookies and backend Bearer token expectations.

The **module handler pattern** (`internal/controller/modules/`) is a newer abstraction for components that run as separate operator pods (AIGateway, MLflowOperator, MCPLifecycleOperator). Unlike in-tree component controllers that apply kustomize manifests directly, module handlers deploy a module operator pod with its own reconcile loop and then project the DSC spec onto a module-specific CR. This enables independent release cycles for module operators while maintaining centralized lifecycle management.

The **monitoring stack** deployment is remarkably comprehensive — it deploys Prometheus via MonitoringStack CR, Tempo for distributed tracing (monolithic or stack mode), OpenTelemetry collectors with auto-instrumentation, Perses for dashboards with multiple datasource types, Thanos for federated queries, and a full set of NetworkPolicies for multi-tenant isolation. The atomic deployment pattern ensures all required CRDs exist before any monitoring resources are created, preventing partial stack deployments.
