## Purpose

**Short**: A module operator that manages AI Gateway sub-components (batch-gateway-operator, maas-controller, ai-gateway-controller) as part of the OpenDataHub modular architecture.

**Detailed**: ai-gateway-operator is a Kubernetes operator that runs as a "module operator" under the opendatahub-operator. It watches a single cluster-scoped `AIGateway` custom resource and, based on its spec, conditionally renders kustomize manifests for three sub-components and deploys them via server-side apply (SSA): the **batch-gateway-operator** (for LLM batch inference gateways), the **maas-controller** (for multi-tenant Models as a Service), and the **ai-gateway-controller** (for traffic routing via Praxis extproc). Each sub-component's manifests are vendored into the repository at pinned commit SHAs via `hack/scripts/get-manifests.sh`, ensuring reproducible builds.

The operator implements a two-level management model: the opendatahub-operator creates and manages the `AIGateway` CR, while ai-gateway-operator deploys the sub-component operators, which in turn manage their own workloads (e.g., `LLMBatchGateway` CRs for batch inference, `AITenant`/`MaaSSubscription` CRs for MaaS). Status is aggregated upward — each sub-component's Deployment readiness and operand health (e.g., MaaS Config Ready, TenantsHealthy conditions) are reflected on the `AIGateway` CR, which opendatahub-operator reads to update the `DataScienceCluster` status. A platform version handshake mechanism coordinates upgrades between the platform operator and this module operator via a shared ConfigMap.

## Architectural Analysis

ai-gateway-operator follows the ODH modular operator pattern: it is a single reconciler that acts as a lifecycle manager for multiple sub-component operators rather than directly managing end-user workloads. The reconciler pipeline is built on the opendatahub-operator's `reconciler.ReconcilerFor` framework, chaining actions for initialization, upgrade, kustomize rendering, deployment, status reporting, and garbage collection in a deterministic sequence.

The operator's most significant architectural decision is the conditional manifest inclusion model. The `initialize` action reads `spec.batchGateway.managementState` and `spec.modelsAsAService.managementState` from the `AIGateway` CR and appends the corresponding `ManifestInfo` entries to the reconciliation request. This means no sub-component manifests are rendered or deployed unless explicitly opted in via the CR. The ai-gateway-controller is implicitly tied to the MaaS toggle — it shares the same lifecycle as maas-controller and stays installed during MaaS teardown to allow in-flight traffic to drain.

The RBAC surface is notably broad because the operator must hold RBAC escalation privileges for every permission granted to its sub-components. The `manager-role` ClusterRole includes rules across 25+ API groups because it creates and patches the ClusterRoles that the sub-component operators (batch-gateway-operator, maas-controller) themselves need. This is an inherent constraint of the Kubernetes RBAC escalation model — the deploying operator must be a superset of what it deploys.

TLS is configured dynamically by fetching the OpenShift cluster TLS profile (`APIServer` CR) at startup. A `SecurityProfileWatcher` monitors for profile or adherence policy changes and triggers a graceful restart to reload the configuration. This design means the operator automatically aligns with cluster-wide TLS policy (e.g., Intermediate, Modern) without manual configuration, but on non-OpenShift clusters (xKS), it falls back to Intermediate defaults.

The namespace model uses a split between an "applications" namespace (e.g., `redhat-ods-applications`) where operators run and an "infrastructure" namespace (e.g., `redhat-ai-gateway-infra`) where maas-controller stores cross-namespace secrets like `maas-db-config`. The operator programmatically creates the infrastructure namespace and manages RBAC for secret migration during upgrades.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Metrics protected by TokenReview + SubjectAccessReview; AIGateway CR access via admin/editor/viewer ClusterRoles | Kubernetes RBAC, controller-runtime filters | No gaps — RBAC is Kubernetes-enforced |
