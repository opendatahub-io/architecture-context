## Purpose

**Short**: Kubernetes operator that declaratively provisions and manages the full inference serving stack (prefill/decode deployments, routing, RBAC) for a single base model using the ModelService custom resource.

**Detailed**: The llm-d-model-service is a Kubebuilder-based Kubernetes operator that manages `ModelService` custom resources in the `llm-d.ai` API group. When a user creates a ModelService CR, the controller reconciles the desired state by creating and managing a constellation of child Kubernetes resources: prefill and decode Deployments (for disaggregated inference), an Endpoint Picker (EPP) Deployment and Service for intelligent request routing, Gateway API HTTPRoutes for ingress, InferencePool and InferenceModel CRs from the Gateway API Inference Extension (GIE), ConfigMaps, ServiceAccounts, and RoleBindings.

The operator implements a two-layer configuration model: a platform-managed **BaseConfig** (stored as a ConfigMap) provides shared defaults across multiple models, while the **ModelService** CR provides per-model overrides. Both layers support Go template variable interpolation (using Sprig functions) that allows dynamic references like `{{.ModelServiceName}}` and `{{.InferencePoolName}}`. The controller merges these layers using the Mergo library with custom transformers for containers, environment variables, Gateway API ParentRefs, and BackendRefs.

Model artifacts can be loaded from three sources: HuggingFace (`hf://`), Kubernetes PVCs (`pvc://`), or OCI images (`oci://`). The controller handles each URI type differently — creating appropriate volumes, volume mounts, and environment variables (e.g., `HF_TOKEN`, `HF_HOME`). The operator also supports decoupled scaling, allowing external autoscalers (HPA or custom controllers) to manage replica counts independently.

**Note**: This project is now deprecated. The ModelService Helm chart proposal was accepted on June 10, 2025, and active development has moved to `llm-d-incubation/llm-d-modelservice`.

## Architectural Analysis

The llm-d-model-service implements a declarative operator pattern for inference infrastructure, but with a notable architectural distinction: rather than hardcoding the shape of managed resources, it uses a **two-layer template-and-merge system**. The BaseConfig ConfigMap acts as a fully serialized set of Kubernetes resource YAML (Deployments, Services, InferencePool, etc.) stored in ConfigMap data keys. The controller deserializes these, interpolates Go template variables (`{{.ModelServiceName}}`, `{{.InferencePoolName}}`, etc.), then performs a Mergo merge with fields from the ModelService CR. This design allows platform teams to define arbitrarily complex inference topologies without modifying the operator code — the controller is essentially a template engine plus a reconciler.

The merge system uses custom Mergo transformers (`containerSliceTransformer`, `envVarSliceTransformer`, `parentRefSliceTransformer`, `backendRefTransformer`) that implement name-based merge semantics. For example, containers are matched by `.name` and merged rather than appended. Arguments from the ModelService CR are prepended (not appended) to BaseConfig arguments via `stringSlicePrependTransformer`. This is important because vLLM and similar inference engines are sensitive to argument ordering. Environment variables are merged by name with override semantics. These transformers live in `internal/controller/merge_transformers.go` and represent the most complex logic in the codebase.

The controller manages an unusually broad set of resource types for a single-CRD operator: Deployments (prefill, decode, EPP), Services (prefill, decode, EPP), HTTPRoutes, InferencePools, InferenceModels, ConfigMaps, ServiceAccounts, and RoleBindings — all owned by a single ModelService CR via owner references. This breadth means a single ModelService deletion cascades to remove the entire inference stack. The `decoupleScaling` flag is architecturally significant: when enabled, the controller sets `Replicas: nil` during merges so that external autoscalers (HPA, KEDA, etc.) can manage replica counts without the reconciler reverting them.

The model artifact loading system (`internal/controller/utils.go`) handles three URI schemes with different volume strategies: `pvc://` creates a PVC volume (read-only), `hf://` creates an emptyDir volume with a size limit and injects `HF_TOKEN`/`HF_HOME` environment variables, and `oci://` support is partially implemented (constants defined but volume creation is TODO). The `mountModelVolume` field on `ContainerSpec` controls per-container opt-in to volume mounting, which is important for sidecar containers that don't need model access.

This project is officially deprecated as of June 2025 — the ModelService Helm chart proposal was accepted, and active development moved to `llm-d-incubation/llm-d-modelservice`. The operator pattern was replaced by a Helm chart approach. The codebase remains a valuable reference for understanding the inference topology and the relationship between ModelService, InferencePool, InferenceModel, and EPP components in the llm-d ecosystem.
