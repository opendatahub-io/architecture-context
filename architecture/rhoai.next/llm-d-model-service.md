## Purpose

**Short**: Kubernetes operator that declaratively provisions and manages the full inference serving stack for a base model via the ModelService custom resource.

**Detailed**: llm-d-model-service is a Kubernetes controller built with the Kubebuilder framework (controller-runtime v0.20.4) that reconciles `ModelService` custom resources in the `llm-d.ai` API group. When a user creates a ModelService CR specifying a base model, the controller automates the lifecycle of all child resources needed to serve that model for inference: prefill and decode Deployments (supporting disaggregated inference), an Endpoint Picker (EPP) Deployment and Service for intelligent request routing, InferencePool and InferenceModel resources from the Gateway API Inference Extension, HTTPRoute resources for Gateway API-based traffic routing, ServiceAccounts, RoleBindings, and ConfigMaps.

The controller supports a templating and merging system where platform operators define reusable `BaseConfig` presets (stored as ConfigMaps) containing default pod specs, container images, and routing configuration. Model owners then create lightweight ModelService CRs that reference a BaseConfig and overlay model-specific values. Template variables are interpolated at reconcile time, enabling dynamic naming of child resources. Model artifacts can be sourced from HuggingFace (`hf://`), Kubernetes PVCs (`pvc://`), or OCI images (`oci://`).

**Note**: This project is deprecated. The ModelService helm chart proposal was accepted by llm-d on June 10, 2025. The successor project is at [llm-d-incubation/llm-d-modelservice](https://github.com/llm-d-incubation/llm-d-modelservice).

## Architectural Analysis

The llm-d-model-service controller follows a single-CRD operator pattern where one custom resource (ModelService) acts as the declarative root for an entire inference serving stack. The controller's reconciliation loop performs three key phases: template interpolation, semantic merging of BaseConfig with ModelService overrides, and creation/update of child resources. This design cleanly separates platform concerns (BaseConfig presets managed by operators) from model-owner concerns (lightweight ModelService CRs).

A notable architectural choice is the use of ConfigMaps as the storage mechanism for BaseConfig presets rather than a dedicated CRD. The roadmap explicitly calls out migrating to a BaseConfig CRD, acknowledging this as a limitation. ConfigMaps lack schema validation, defaulting, and the status subresource that a CRD would provide.

The controller watches 10 resource types (ModelService, Deployments, Services, ServiceAccounts, ConfigMaps, RoleBindings, HTTPRoutes, InferenceModels, InferencePools) using owner-reference-based mapping functions. All watched resources except the primary ModelService use `requeueMsvcReq`, a shared function that checks owner references for `ModelService` ownership. This ensures the controller re-reconciles when any child resource changes.

The disaggregated prefill/decode architecture is a distinguishing feature: a single ModelService can independently configure and scale prefill and decode deployments with separate replica counts, resource requirements, parallelism settings, and accelerator affinity. The `DecoupleScaling` flag controls whether the controller manages replicas or defers to an external autoscaler (HPA or custom).

Security-wise, the metrics endpoint supports HTTPS with authn/authz via controller-runtime's `WithAuthenticationAndAuthorization` FilterProvider when `--metrics-secure=true` (the default). HTTP/2 is disabled by default to mitigate the Rapid Reset CVE. The Dockerfile builds with `CGO_ENABLED=0` (statically linked), which is a FIPS compliance concern for downstream RHOAI distribution. The Dockerfile CMD is `sleep infinity` rather than running the manager binary, indicating this image is not production-ready and the actual deployment uses kustomize patches to set the command.

The project is deprecated in favor of a Helm chart-based approach. This is architecturally significant: the successor moves from an operator pattern (controller watching CRDs) to a templating pattern (Helm rendering manifests), indicating that the operational overhead of maintaining a controller was not justified by the lifecycle management benefits for this use case.

The upstream Dockerfile uses `CGO_ENABLED=0` which produces a statically linked binary.
