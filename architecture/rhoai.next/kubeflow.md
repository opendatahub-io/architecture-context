## Purpose

**Short**: Manages the lifecycle of Jupyter notebook workspaces on Kubernetes, including per-notebook networking, authentication, idle culling, and integration with data science platform services.

**Detailed**: The kubeflow repository contains two cooperating Go controllers that together manage Notebook custom resources. The upstream **notebook-controller** (odh-kf-notebook-controller) handles core lifecycle — creating StatefulSets, ClusterIP Services, and optionally Istio VirtualServices for each Notebook CR. It also provides idle-notebook culling by querying the Jupyter kernel/terminal APIs and scaling notebooks to zero after configurable idle periods.

The downstream **odh-notebook-controller** extends the upstream controller with RHOAI/ODH-specific features. It injects kube-rbac-proxy sidecars for per-notebook authentication, creates Gateway API HTTPRoutes in a central namespace for ingress, manages per-notebook NetworkPolicies, creates ReferenceGrants for cross-namespace routing, integrates with Data Science Pipelines (DSPA) for Elyra runtime secrets, resolves notebook images from OpenShift ImageStreams, injects trusted CA bundles and cluster proxy environment variables, and supports MLflow and Feast integrations. Together, the two controllers provide a complete notebook-as-a-service platform layer.

Both controllers are deployed into the same namespace (typically `opendatahub`) and operate on the shared `kubeflow.org/Notebook` CRD. The upstream controller owns the StatefulSet and Service, while the ODH controller owns the networking, auth, and platform-integration resources.

**Dockerfile**: `components/notebook-controller/Dockerfile.konflux`
**Intent**: The upstream Kubeflow notebook controller. Deployed as a single-replica Deployment that reconciles Notebook CRs into StatefulSets (one pod per notebook), ClusterIP Services, and optionally Istio VirtualServices. ## Architectural Analysis

The kubeflow repository implements a layered controller architecture where the upstream Kubeflow notebook-controller handles core Kubernetes lifecycle (StatefulSet, Service) while the downstream ODH controller layers platform-specific concerns on top. This separation allows the upstream code to remain relatively clean and aligned with the Kubeflow community, while all RHOAI-specific logic — authentication, networking, platform integrations — lives in a separate controller binary that watches the same CRD. The two controllers coordinate through shared annotations and labels on the Notebook CR rather than through direct communication.

The RHOAI 3.x ingress pattern is clearly implemented here: HTTPRoutes are created in a central controller namespace (not the user's namespace) and reference backend Services cross-namespace via ReferenceGrants. This centralized HTTPRoute placement is architecturally significant — it means the platform operator controls the ingress topology while users only manage their Notebook CRs. The controller handles the complexity of cross-namespace references, name length constraints (63-char hostname limit), and cleanup via finalizers. Three finalizers (`httproute-cleanup`, `referencegrant-cleanup`, `kube-rbac-proxy-cleanup`) ensure that cluster-scoped and cross-namespace resources are properly garbage collected even though they cannot use standard Kubernetes owner references.

The kube-rbac-proxy sidecar injection is notable for its configurability — resource limits for the sidecar are set via annotations on the Notebook CR, allowing per-notebook tuning without changing the controller configuration. The proxy enforces SubjectAccessReview checks against the specific Notebook resource, meaning a user must have `get` permission on the exact Notebook CR to access its UI. This is a strong per-workspace auth model. However, the auth injection is opt-in via the `notebooks.opendatahub.io/inject-auth=true` annotation; notebooks without this annotation rely solely on NetworkPolicy (which only allows port 8888 from the controller namespace) for isolation.

The mutating webhook implements a "restart prevention" mechanism (`maybeRestartRunningNotebook`) that blocks webhook mutations that would force a running notebook to restart. Instead, it sets a `notebooks.opendatahub.io/update-pending` annotation with a human-readable diff of what changed. This is a UX-conscious design that prevents accidental data loss in running notebooks while still allowing the user to manually restart when ready.

The DSPA and MLflow integrations demonstrate a pattern of "ambient configuration" — the controller watches for platform resources (DSPA CRs, MLflow ClusterRoles) and automatically configures notebook workspaces to use them. The Elyra runtime secret construction is particularly complex, building a JSON configuration that includes S3 credentials, API endpoints, and gateway hostnames. This ambient approach means data scientists don't need to manually configure pipeline or experiment tracking connections, but it also creates implicit dependencies between the notebook controller and these platform services.
