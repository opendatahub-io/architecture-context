## Purpose

**Short**: Kubernetes controllers that manage the lifecycle of Jupyter Notebook workloads (workbenches) on OpenShift, providing per-notebook auth injection, network isolation, and Gateway API routing.

**Detailed**: The kubeflow repository is the Red Hat downstream fork of kubeflow/kubeflow, containing two cooperating Go controllers built with controller-runtime. The upstream **notebook-controller** (kf-notebook-controller) reconciles the `Notebook` CRD into StatefulSets, Services, and health probes, with an optional idle-culling controller that shuts down inactive notebooks after a configurable timeout. The downstream **odh-notebook-controller** extends this with OpenShift-specific capabilities: it injects a kube-rbac-proxy authentication sidecar into each notebook pod, creates per-notebook NetworkPolicies for traffic isolation, manages HTTPRoute resources against a central Gateway API gateway for external access, handles OAuthClient lifecycle, provisions DSPA (Data Science Pipelines) secrets, manages MLflow integration via RoleBindings, and assembles trusted CA bundles from platform ConfigMaps. A mutating webhook defaults notebook configurations on CREATE/UPDATE, while a validating webhook enforces pod security constraints and prevents unsafe MLflow annotation removal on running notebooks. Both controllers run as a single `odh-notebook-controller-manager` Deployment in the RHOAI operator namespace, with TLS configuration dynamically derived from the OpenShift APIServer TLS security profile.

## Architectural Analysis

The kubeflow notebook controllers exhibit a layered architecture where the upstream controller handles core Kubernetes lifecycle (Notebook → StatefulSet → Pod) and the downstream controller adds the OpenShift integration layer. The two controllers watch the same `Notebook` CRD but own distinct child resources — the upstream controller owns StatefulSets and Services, while the downstream controller owns ServiceAccounts, Secrets, ConfigMaps, NetworkPolicies, and RoleBindings. This separation preserves rebase compatibility with upstream Kubeflow while enabling deep platform integration.

A significant architectural decision is the use of a reconciliation lock: the mutating webhook injects a `kubeflow-notebook-controller/stoppedByController` annotation on CREATE to prevent the upstream controller from starting the pod before the downstream controller has finished provisioning auth sidecars, network policies, and route configuration. This coordination pattern prevents race conditions between the two controllers but couples them through a shared annotation contract.

The Gateway API integration is centralized — HTTPRoutes are created in the controller's namespace rather than the notebook's namespace, requiring ReferenceGrants in user namespaces to authorize cross-namespace backend references. This centralization simplifies gateway management but creates a fan-out pattern where changes to shared ReferenceGrants or ConfigMaps trigger reconciliation across all notebooks in affected namespaces.

TLS configuration follows a dynamic profile model: both controllers bootstrap from the OpenShift APIServer TLS profile (or fall back to Mozilla Intermediate cipher defaults for non-OpenShift clusters), and a SecurityProfileWatcher triggers graceful pod restarts when the cluster TLS profile changes. The metrics endpoint is secured with controller-runtime's built-in authentication and authorization filter, enforcing token review and subject access review at the metrics serving surface.

Cache optimization is notable: the odh-notebook-controller strips data payloads from cached ConfigMaps and Secrets via informer transforms, reading actual data through direct API calls. This reduces memory pressure from large ConfigMaps (trusted CA bundles, platform configs) that must be watched for changes but whose data is only needed during reconciliation.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar injected per notebook; per-notebook ServiceAccount; aggregated RBAC roles (notebooks-edit, notebooks-view) | Kubernetes RBAC + kube-rbac-proxy | OAuthClient resources are cluster-scoped (legacy path being deprecated) |
| Data storage | Per-notebook StatefulSet with user-specified PVCs in notebook namespace | Kubernetes namespace isolation | No cross-namespace data sharing enforced by controller; relies on namespace RBAC |
| Network traffic | Per-notebook NetworkPolicy allowing ingress only from controller namespace and kube-rbac-proxy port; per-notebook kube-rbac-proxy NetworkPolicy | Kubernetes NetworkPolicy | NetworkPolicies are controller-managed and reconciled; manual edits are overwritten |
| Compute & resources | Notebook pods run with user-specified resource requests/limits | Kubernetes (user-configured) | No controller-enforced ResourceQuotas; relies on platform-level namespace quotas |
| Configuration & secrets | Per-namespace trusted CA bundle ConfigMap; per-notebook DSPA secrets; per-namespace ReferenceGrants | Kubernetes namespace isolation | ConfigMaps like odh-trusted-ca-bundle are namespace-local copies |
| API scoping | Controller watches all namespaces; reconciliation scoped by notebook namespace | Kubernetes (namespace-scoped CRD) | Cluster-wide watch with per-namespace child resource creation |
