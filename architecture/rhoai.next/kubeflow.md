## Purpose

**Short**: Manages the lifecycle of Jupyter notebook workbenches on OpenShift, including creation, authentication, networking, idle culling, and integration with ML platform services.

**Detailed**: The kubeflow repository contains two complementary Kubernetes controllers that together manage notebook (workbench) instances on Red Hat OpenShift AI. The upstream **notebook-controller** (from the Kubeflow project) handles the core notebook lifecycle — creating StatefulSets and Services for each Notebook CR, managing status updates by mirroring Pod conditions, and optionally culling idle notebooks by polling the Jupyter kernel/terminal APIs.

The downstream **odh-notebook-controller** extends the upstream controller with OpenShift-specific and RHOAI platform features. It injects a kube-rbac-proxy sidecar for authentication, creates HTTPRoute resources (Gateway API) for external access, manages NetworkPolicies for per-notebook isolation, and integrates with platform services (MLflow, Data Science Pipelines via DSPA/Elyra, Feast). It also provides mutating and validating webhooks that handle image resolution from ImageStreams, CA bundle injection, cluster proxy configuration, and safe update semantics that prevent unintended pod restarts.

Both controllers run as a single combined deployment managed by the platform operator (rhods-operator / opendatahub-operator). The upstream controller watches Notebook CRs and manages the core workload (StatefulSet + Service), while the ODH controller adds the RHOAI-specific networking, security, and integration resources around each notebook. This layered design preserves upstream compatibility while enabling Red Hat-specific platform features.

## Architectural Analysis

The kubeflow repository implements a dual-controller architecture where the upstream Kubeflow notebook-controller handles the core workload lifecycle and a downstream ODH-specific controller layers platform integration on top. This design preserves upstream compatibility — the Notebook CRD schema and StatefulSet-based lifecycle management come directly from the Kubeflow project — while adding the authentication, networking, and service integration features required by RHOAI. The two controllers share the same Deployment but operate on different aspects of each Notebook CR: the upstream controller owns the StatefulSet and Service, while the ODH controller owns the HTTPRoute, NetworkPolicies, and integration resources.

The authentication architecture follows the RHOAI 3.x pattern, using kube-rbac-proxy as a sidecar injected into each notebook pod. When a user annotates a Notebook with `notebooks.opendatahub.io/inject-auth: "true"`, the mutating webhook injects a kube-rbac-proxy container that listens on port 8443 and proxies to the Jupyter server on port 8888. The proxy performs SubjectAccessReview checks against the Kubernetes API to verify the user has `get` access to the Notebook resource, providing fine-grained RBAC-based access control. TLS certificates for the proxy are auto-provisioned by the OpenShift Service CA operator via service annotations. The controller also creates a per-notebook ServiceAccount and ClusterRoleBinding to `system:auth-delegator` so the sidecar can perform token reviews.

The networking architecture uses Gateway API (HTTPRoute + ReferenceGrant) as the primary ingress mechanism, a key RHOAI 3.x migration from the older OpenShift Route pattern. HTTPRoutes are created in the controller's central namespace (not the user namespace), referencing the platform's `data-science-gateway` Gateway in `openshift-ingress`. ReferenceGrants in each user namespace explicitly permit this cross-namespace Service reference. Per-notebook NetworkPolicies restrict direct access to port 8888 to only the controller namespace, while the kube-rbac-proxy port 8443 is open to all (since the proxy itself enforces authentication). The legacy OAuthClient cleanup finalizer (`notebook-oauth-client-finalizer.opendatahub.io`) handles migration from the pre-3.0 OAuth proxy pattern.

The webhook design is notable for its "reconciliation lock" mechanism: on Notebook creation, the mutating webhook injects a `kubeflow-resource-stopped` annotation to prevent the pod from starting before the controller has finished creating all required resources (HTTPRoute, NetworkPolicy, kube-rbac-proxy resources). The controller removes this lock after reconciliation completes. The webhook also implements "update blocking" — it detects spec changes that would restart a running pod and instead sets an `update-pending` annotation, requiring the user to stop the notebook before the update takes effect. This prevents unexpected notebook restarts that would interrupt running computations.

The idle culling subsystem is architecturally isolated as a separate reconciler (CullingReconciler) within the upstream controller. It uses HTTP polling against the Jupyter kernel and terminal APIs to detect activity, with configurable idle thresholds (default 24 hours). When idle, it sets the `kubeflow-resource-stopped` annotation which the main reconciler uses to scale the StatefulSet to zero replicas. The notebook Service persists, allowing the notebook to be resumed by removing the annotation. This annotation-based coordination between the two reconcilers and the webhook is a recurring pattern throughout the codebase.
