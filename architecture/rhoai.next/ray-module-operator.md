## Purpose

**Short**: Module operator that manages the lifecycle of the KubeRay operator within the OpenDataHub/RHOAI platform's modular architecture.

**Detailed**: The ray-module-operator is a Kubernetes operator built on `controller-runtime` and the `odh-platform-utilities` framework. It reconciles a cluster-scoped `Ray` custom resource (`components.platform.opendatahub.io/v1alpha1`) and manages the full lifecycle of the KubeRay operator — install, upgrade, status reporting, and removal — as an operand within the ODH modular architecture.

When the platform operator enables the Ray module, it creates a singleton `Ray` CR named `default-ray`. The module operator then renders vendored KubeRay manifests (CRDs, RBAC, Deployment, webhooks) via kustomize with platform-specific overlays (ODH or RHOAI), applies them using server-side apply with force ownership, and continuously monitors the operand's deployment health. The operator reads distribution metadata from a platform-managed ConfigMap (`odh-ray-config`) to align version reporting and support future upgrade workflows.

The operand KubeRay operator in turn provides the `ray.io` CRD family (RayCluster, RayJob, RayService, RayCronJob), enabling users to run distributed Ray workloads on OpenShift. The module operator also creates a `ray` ClusterRole that Workbenches (Notebooks) bind to allow notebook service accounts to submit Ray jobs.

## Architectural Analysis

The ray-module-operator follows a two-tier architecture: a thin module operator manages the lifecycle of a heavier operand (KubeRay). This separation allows the platform operator to enable/disable Ray without bundling KubeRay's reconciliation logic into the monolithic operator.

The reconciliation pipeline is built using the `odh-platform-utilities` framework's action-chain pattern. Each reconcile pass executes a deterministic sequence: management state evaluation → release tracking → manifest initialization → image parameter injection → kustomize rendering → cert-manager dependency check → platform resource filtering → notebook RBAC → server-side apply deployment → deployment health monitoring → distribution status → degraded condition → observed generation → garbage collection. This pipeline design makes the reconciliation order explicit and testable.

A notable design decision is the writable-manifests pattern: because the container runs as a non-root user with a read-only root filesystem, the operator copies vendored manifests from `/opt/manifests` to a temp directory before rewriting `params.env` with RELATED_IMAGE environment variables. This accommodates Konflux/CSV image injection without requiring a writable image layer.

The operator handles platform-awareness through a ConfigMap watch on `odh-ray-config`. This ConfigMap carries distribution name, version, and a platform-version handshake key, allowing the module to report its alignment with the broader RHOAI release and to support future version-gated upgrade logic (currently a no-op hook).

The garbage collection strategy is split between managed and removed states. During normal operation, only owner-referenced resources are collected. On `Removed` management state or CR deletion, a broader sweep labels and owner-based sweep runs, including explicit deletion of cluster-scoped webhooks and SCCs — but CRDs are intentionally preserved to avoid data loss. The SCC filter action detects whether the `security.openshift.io` API is present, caching the result to skip SCC resources on non-OpenShift clusters.
