## Purpose

**Short**: Unified Python SDK for managing ML workloads across Kubeflow ecosystem projects without requiring Kubernetes expertise.

**Detailed**: The Kubeflow SDK (`kubeflow` PyPI package, version 0.4.1+rhai0 in this fork) provides a set of unified Pythonic APIs that abstract away Kubernetes complexity for AI/ML practitioners. It offers consistent client interfaces for multiple Kubeflow projects: Trainer (model training and fine-tuning), Optimizer (hyperparameter optimization via Katib), Spark (data processing via Spark Connect), Hub (model registry), and Pipelines (ML workflow orchestration via KFP).

The OpenDataHub/RHOAI midstream fork (`opendatahub-io/kubeflow-sdk`) extends the upstream `kubeflow/sdk` with a dedicated `kubeflow.trainer.rhai` subpackage that adds Red Hat AI-specific trainer implementations. These include `TransformersTrainer` (HuggingFace Transformers/TRL with auto-instrumentation for progression tracking and S3/PVC checkpointing), `TrainingHubTrainer` (RHAI Training Hub integration with SFT/OSFT/LoRA algorithms and user-defined callbacks), and `SpeculativeDecodingTrainer` (Eagle3/DFlash/MTP/PEAGLE draft model training for speculative decoding with multiple operational modes). The RHAI trainers inject instrumentation code into training pods at runtime via `inspect.getsource()` for checkpoint management, progression metrics, and distributed training coordination—all without adding SDK runtime dependencies to the training containers.

The SDK is a client-side library—it does not run as a server or operator. It communicates with the Kubernetes API to create and manage TrainJob, OptimizationJob, and SparkConnect custom resources, delegating actual workload execution to the corresponding Kubeflow operators running in the cluster.

## Architectural Analysis

The kubeflow-sdk follows a layered architecture with a clean separation between user-facing API clients and pluggable execution backends. Each Kubeflow project (Trainer, Optimizer, Spark, Hub, Pipelines) gets its own subpackage under `kubeflow/` with a consistent structure: `api/` for the client class, `backends/` for execution strategy implementations, `types/` for dataclass/Pydantic models, and `constants/` for configuration defaults.

The backend abstraction is the central design pattern: `TrainerClient` dispatches to `KubernetesBackend` (production), `ContainerBackend` (Docker/Podman local isolation), or `LocalProcessBackend` (subprocess prototyping). This allows the same training code to run locally during development and at scale on Kubernetes without API changes. The Container backend's auto-detection behavior (tries Docker first, then Podman) and its adapter pattern demonstrate clean extensibility.

The RHAI extensions introduce a distinctive code injection pattern. Rather than requiring the SDK as a runtime dependency in training containers, the RHAI trainers use `inspect.getsource()` to extract instrumentation functions as source code, which is then embedded into the training pod's command. This keeps training container images lean while still providing rich instrumentation (HTTP metrics servers on port 28080, S3/PVC checkpoint management with cloud upload queues, distributed barrier synchronization via `torch.distributed`). The trade-off is that the injected code must be self-contained—it cannot import from the SDK at runtime, leading to necessary code duplication between the instrumentation modules and the rest of the SDK.

The `SpeculativeDecodingTrainer` is architecturally notable for its multi-mode design: `DATA_ONLY` mode manages a vLLM sidecar container alongside the training pod for hidden state extraction, `TRAIN_ONLY` operates on pre-extracted data from PVC, `OFFLINE` uses an external vLLM endpoint, and `ONLINE` bundles everything into a single runtime image. This represents the most complex pod topology the SDK constructs, requiring coordination between the trainer container, optional vLLM sidecar (on port 8234), and shared PVC volumes.

The SDK uses RHAI-specific annotations (`trainer.opendatahub.io/progression-tracking`, `trainer.opendatahub.io/metrics-port`, `trainer.opendatahub.io/metrics-poll-interval`) on Kubernetes resources to communicate metadata to the Kubeflow Trainer operator, enabling the operator's controller to poll training progress from the injected HTTP metrics servers.

The midstream release process (documented in `odh-release.md`) produces versioned packages with a `+rhaiv.N` suffix and pins all dependencies to exact versions resolved from `uv.lock` on release branches, ensuring reproducible builds.
