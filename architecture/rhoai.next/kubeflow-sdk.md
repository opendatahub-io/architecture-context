## Purpose

**Short**: Unified Python SDK for managing ML workloads (training, hyperparameter optimization, Spark, model registry) across Kubeflow and Red Hat AI platforms.

**Detailed**: The Kubeflow SDK (`pip install kubeflow`) provides a high-level Python API for submitting and managing machine learning workloads on Kubernetes. It acts as a client library for Kubeflow's custom resources — primarily `TrainJob`, `TrainingRuntime`, and `ClusterTrainingRuntime` from the `trainer.kubeflow.org/v1alpha1` API group — as well as Katib (hyperparameter optimization), Spark Operator, and Model Registry.

The SDK implements a strategy/backend pattern with three pluggable execution backends: `KubernetesBackend` (creates CRs on a cluster), `ContainerBackend` (runs training in Docker/Podman containers locally), and `LocalProcessBackend` (runs training as local Python subprocesses). This allows the same training code to run across environments without modification.

The midstream fork (`opendatahub-io/kubeflow-sdk`) adds RHAI (Red Hat AI) extensions that are not present upstream. These include `TransformersTrainer` (HuggingFace Transformers integration with progression tracking, JIT SIGTERM-triggered checkpointing, and async S3 checkpoint upload) and `TrainingHubTrainer` (algorithm registry with SFT/OSFT/LoRA variants and HTTP-based progression metrics). The RHAI extensions use code injection — serializing Python functions via `inspect.getsource()` and embedding them into container commands — to instrument training pods with monitoring and checkpoint capabilities without requiring custom container images.

## Architectural Analysis

### Strategy/Backend Pattern

The SDK's most significant architectural decision is the strategy pattern for execution backends. The `RuntimeBackend` ABC (`kubeflow/trainer/backends/base.py`) defines the interface, and three concrete implementations (Kubernetes, Container, LocalProcess) provide pluggable execution environments. The `TrainerClient` dispatches to the appropriate backend based on the config type passed at construction — `KubernetesBackendConfig` routes to `KubernetesBackend`, `ContainerBackendConfig` to `ContainerBackend`, etc. This enables the same training code to run across environments without modification, which is critical for the development-to-production workflow.

### Code Injection Pattern

Both upstream and RHAI trainers use `inspect.getsource()` to serialize Python functions into strings that are embedded in container commands via shell heredocs. The `EXEC_FUNC_SCRIPT` constant in `constants.py` defines the template: the function source is written to a file inside the container, then executed via `python` (PlainML), `torchrun` (Torch), or `mpirun` (MPI). The RHAI extensions push this pattern further — `TransformersTrainer` serializes its entire progression tracking callback and checkpoint management code into the container command, effectively performing metaprogramming at job submission time. This avoids requiring custom container images for instrumentation but makes debugging harder since the code running in pods is generated, not directly readable from source files.

### RHAI Extensions as Midstream Differentiator

The `kubeflow/trainer/rhai/` directory contains the primary midstream-only code. Two trainer types extend the upstream `CustomTrainer` pattern:

1. **TransformersTrainer**: Integrates deeply with HuggingFace Transformers by monkey-patching `transformers.Trainer.__init__` to inject a `KubeflowProgressCallback`. It implements JIT checkpointing triggered by SIGTERM (with CUDA stream synchronization for GPU safety), async S3 upload via background worker threads, and periodic checkpoint configuration. The checkpoint management code is serialized via `inspect.getsource()` and injected into the training pod.

2. **TrainingHubTrainer**: Uses a centralized algorithm registry (`ALGORITHMS` dict in `algorithms.py`) that maps algorithm names (sft, osft, lora_sft, lora_grpo) to `AlgorithmSpec` frozen dataclasses containing entrypoint commands, metrics file patterns, and environment variables. It generates training scripts via `_render_algorithm_wrapper()` and injects an HTTP metrics server for progression tracking.

Both RHAI trainers annotate TrainJob CRs with `trainer.opendatahub.io/progression-*` annotations, enabling the platform to track training progress at the Kubernetes resource level.

### Output Directory Abstraction

The RHAI trainers introduce a URI-based output directory scheme (`pvc://volume-name/path` or `s3://bucket/prefix`) that abstracts storage backends. The `normalize_and_validate_output_dir()` function in `rhai/utils.py` parses these URIs and generates appropriate Kubernetes volume mounts (for PVC) or environment variables (for S3). This allows users to specify storage destinations without understanding Kubernetes volume semantics.

### Sync Workflow

The `rebase-upstream.yaml` workflow runs weekly (Monday at midnight UTC) to merge upstream `kubeflow/sdk` changes. It excludes `.github`, `CHANGELOG`, and `OWNERS` directories from upstream merges, preserving midstream CI configuration. Conflicts in excluded paths are auto-resolved to keep the midstream version. The workflow also regenerates `requirements.txt` from `uv.lock` after each merge.

### Risks and Limitations

1. **Code injection complexity**: The `inspect.getsource()` pattern for serializing trainer instrumentation is fragile — it breaks if functions reference closures, use decorators that alter source, or depend on module-level state that isn't serialized alongside. The RHAI trainers mitigate this by carefully structuring serializable functions as self-contained.

2. **No container images**: The SDK has no Konflux Dockerfiles and produces no container images. This means FIPS compliance, build hermeticity, and supply chain security are delegated entirely to the consumer's environment. For RHOAI, this means the notebook images or pipeline runners that install the SDK bear the responsibility.

3. **Version coupling**: The `kubeflow-trainer-api>=2.0.0` dependency pins the SDK to a specific CRD API version. Breaking changes in the trainer operator's CRD schema require coordinated SDK releases.
