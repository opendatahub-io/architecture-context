## Purpose

**Short**: Unified Python SDK for managing ML workloads across the Kubeflow ecosystem, providing consistent APIs for model training, hyperparameter optimization, Spark data processing, and model registry interactions without requiring Kubernetes expertise.

**Detailed**: The Kubeflow SDK is a Python client library that abstracts away Kubernetes complexity, providing a single `pip install kubeflow` entry point for data scientists and ML engineers to interact with multiple Kubeflow projects. It supports four major sub-packages: Trainer (distributed model training via TrainJob CRDs), Optimizer (hyperparameter tuning via Katib Experiments), Spark (data processing via SparkConnect CRDs), and Hub (model registry via the Model Registry API).

The SDK implements a pluggable backend architecture where each sub-package defines an abstract `RuntimeBackend` base class with concrete implementations. The Trainer sub-package supports three backends: Kubernetes (production training on clusters), Container (local Docker/Podman execution), and LocalProcess (quick prototyping via Python subprocesses). The Optimizer and Spark sub-packages currently support only the Kubernetes backend. The Hub sub-package connects directly to the Model Registry REST API without a Kubernetes backend.

The opendatahub-io fork adds RHAI (Red Hat AI) extensions in the `kubeflow/trainer/rhai/` module, including `TransformersTrainer` (HuggingFace Transformers with progress tracking and checkpoint management) and `TrainingHubTrainer` (integration with RHAI Training Hub algorithms like SFT, OSFT, LoRA). The midstream release process produces versioned packages with the `+rhai` suffix (e.g., `v0.3.0+rhai0`) and maintains upstream sync via the `rebase-upstream.yaml` workflow, which runs weekly and merges upstream changes while preserving midstream-specific paths (`.github`, `CHANGELOG`, `OWNERS`).

## Purpose

**Short**: Kubeflow Python SDK providing a unified client interface for managing ML training workloads, hyperparameter tuning, Spark analytics, and model registry operations on RHOAI/ODH platforms.

**Detailed**: kubeflow-sdk is a Python client library that provides a high-level programmatic interface to multiple Kubeflow platform components deployed on Red Hat OpenShift AI. The SDK unifies access to the Training Operator (via `kubeflow-trainer-api`), Katib hyperparameter tuning (via `kubeflow-katib-api`), Spark Operator (via `kubeflow-spark-api`), and Model Registry (via `model-registry`) through a single `kubeflow` Python package. It uses the `kubernetes` Python client to authenticate and interact with the Kubernetes API server, submitting and managing Custom Resources (such as TrainJob and SparkConnect) on behalf of data scientists. The SDK also includes an `rhai` (Red Hat AI) module that provides RHOAI-specific extensions, including JIT checkpoint injection for HuggingFace Transformers training and a training hub algorithm registry for reinforcement learning algorithms like LoRA-GRPO. The SDK is distributed as a pip-installable package and does not deploy its own services — it acts purely as a client-side library.

## Data Flows

- **Client-to-API-server flow:** Data scientists import the `kubeflow` package into their Python scripts or Jupyter notebooks. The SDK authenticates to the Kubernetes API server using the credentials available through the `kubernetes` Python client (typically a kubeconfig file or in-cluster service account token). All operations — creating TrainJobs, SparkConnect sessions, Katib experiments, or Model Registry entries — translate into Kubernetes API calls (create, get, list, patch, delete) against the respective Custom Resources.
- **CRD lifecycle:** When the SDK submits a TrainJob or SparkConnect CR, the corresponding platform operator (training-operator or spark-operator) reconciles the resource and manages the underlying workload pods. The SDK polls or watches the CR status to report progress back to the user.
- **Model registry flow:** For model registration, the SDK communicates with the Model Registry API (a separate platform service) to register model artifacts, manage versions, and query registered models. This flow uses the `model-registry` Python client library which connects to the Model Registry REST API.
- **RHAI extensions:** The `kubeflow.trainer.rhai` module provides RHOAI-specific training enhancements. The `transformers` submodule generates checkpoint injection code for HuggingFace Transformers trainers, enabling JIT checkpoint saving and periodic checkpoint configuration without modifying user training functions directly.

## Architectural Analysis

The Kubeflow SDK implements a layered architecture with a clear separation between user-facing API clients and pluggable backend implementations. Each sub-package (trainer, optimizer, spark, hub) follows the same pattern: a stateless `*Client` class delegates to an abstract `RuntimeBackend` whose concrete implementation handles Kubernetes-specific logic. This design enables the Trainer's distinctive multi-backend capability (Kubernetes, Docker/Podman, LocalProcess) while maintaining API consistency. The Container backend's adapter pattern (`BaseContainerClientAdapter` -> `DockerClientAdapter`/`PodmanClientAdapter`) demonstrates clean extensibility -- adding a new container runtime requires only implementing the adapter interface.

The RHAI extensions in `kubeflow/trainer/rhai/` represent the primary value-add of the opendatahub-io fork. `TransformersTrainer` adds three capabilities not present upstream: (1) progression tracking via HTTP metrics endpoints and OpenDataHub-specific annotations (`trainer.opendatahub.io/progression-tracking`), (2) checkpoint management supporting both PVC (`pvc://`) and S3 (`s3://`) URI schemes with just-in-time checkpointing on SIGTERM, and (3) storage credential injection from Kubernetes Secrets (data connection secrets). `TrainingHubTrainer` integrates RHAI Training Hub algorithms (SFT, OSFT, LoRA SFT, LoRA GRPO) as first-class trainer types, with each algorithm defined in the `AlgorithmSpec` registry including metrics file patterns and entrypoint commands. These extensions are integrated into the Kubernetes backend's `_get_trainjob_spec()` method via isinstance dispatch, keeping the core TrainerClient API unchanged.

A notable architectural characteristic is that the SDK is purely a client-side library -- it creates CRDs but does not reconcile them. The actual resource management (creating Pods, Services, JobSets) happens server-side in the respective operators (Trainer Operator, Katib Controller, Spark Operator). This means the SDK's network architecture is primarily egress-oriented: it makes API calls to the Kubernetes API server and external services (HuggingFace, S3, Model Registry) but does not expose any listening ports itself. The one exception is the RHAI `TransformersTrainer`, which configures training pods to expose an HTTP metrics endpoint on port 28080 that the Trainer controller polls for progress data.

The Optimizer sub-package demonstrates tight integration with the Trainer: `OptimizerClient.optimize()` internally uses `TrainerBackend._get_trainjob_spec()` to build the trial template, and each Katib Trial runs a TrainJob. This means optimization inherits all Trainer capabilities (initializers, custom trainers, RHAI extensions). The Spark sub-package is more standalone -- it manages its own CRD lifecycle and includes sophisticated local development support with automatic port-forwarding detection (in-cluster vs external) and kubectl-based port-forward subprocess management for local PySpark connections.

The midstream release process (`odh-release.md`, `.github/workflows/odh-release.yaml`) pins all dependencies to exact versions from `uv.lock` on release branches, producing deterministic builds. The upstream sync workflow (`rebase-upstream.yaml`) merges weekly, preserving midstream-specific paths (`.github`, `CHANGELOG`, `OWNERS`) and auto-resolving conflicts in those paths. This sync architecture is robust -- it handles conflict resolution, Snyk scanning of the sync branch, and automatic `requirements.txt` regeneration.

## Architectural Analysis

kubeflow-sdk is architecturally a client-side Python library, not a deployed service or operator. Despite the analyzer's classification as "Kubernetes Operator / Controller" (driven by the presence of CRD definitions in `hack/crds/`), the SDK does not run a reconcile loop or manage cluster state directly. Instead, it acts as a unified API client that data scientists use from notebooks or scripts to interact with multiple Kubeflow platform operators running on the cluster.

The SDK's dependency structure reveals its role as an integration hub across four distinct RHOAI platform components: training-operator, katib, spark-operator, and model-registry. Each is accessed through a dedicated API client library (`kubeflow-trainer-api`, `kubeflow-katib-api`, `kubeflow-spark-api`, `model-registry`), with the `kubeflow` package providing a cohesive namespace and shared configuration. The `kubernetes>=27.2.0` dependency provides the underlying transport layer for all CRD operations. The CRD YAML in `hack/crds/` (e.g., `sparkoperator.k8s.io_sparkconnects.yaml`) is included for local validation, testing, and smoke tests — not for deployment.

The `rhai` (Red Hat AI) module under `kubeflow.trainer.rhai` is a notable RHOAI-specific extension. The `transformers` submodule provides JIT checkpoint injection for HuggingFace Transformers training, generating code that wraps user training functions with checkpoint save/restore logic. The training hub algorithm registry (added in recent commits) allows registration of RL algorithms like LoRA-GRPO. These extensions demonstrate how the SDK adapts upstream Kubeflow abstractions for Red Hat's productized ML platform.

Authentication is delegated entirely to the `kubernetes` Python client, which supports kubeconfig-based authentication (bearer tokens, client certificates, OIDC tokens). The SDK does not implement its own auth layer. When running inside a cluster (e.g., from a Jupyter notebook pod), authentication uses the pod's service account token. Security posture for SDK operations is therefore governed by the RBAC permissions granted to the caller's identity on the target CRDs.
