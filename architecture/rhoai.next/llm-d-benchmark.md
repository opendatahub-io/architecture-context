## Purpose

**Short**: Automated benchmarking and performance evaluation framework for the llm-d LLM inference stack across multiple Kubernetes environments.

**Detailed**: llm-d-benchmark provides end-to-end automation for benchmarking LLM inference on the llm-d stack. It operates as a declarative lifecycle tool: a single `llmdbenchmark` CLI covers infrastructure standup, workload deployment, benchmark execution via pluggable harnesses (inference-perf, guidellm, vllm-benchmark, aiperf), result collection to local or cloud storage, and teardown. The system uses a deterministic configuration merge chain -- defaults.yaml through scenario files to CLI overrides -- so every experiment is reproducible from its inputs.

The framework supports multiple deployment methods (standalone Kubernetes Deployments, Helm-based modelservice with Gateway API), multiple cluster platforms (GKE, CoreWeave, OpenShift), and multi-model scenarios where N inference pools share a single gateway. It includes a Design of Experiments (DoE) engine for automated parameter sweeps across both infrastructure and workload configurations, plus a stack-discovery sub-tool that traces from an endpoint URL back through Gateway/Route/InferencePool resources to map the full deployed topology. Results are emitted in a universal Benchmark Report format and can be uploaded to GCS or S3.

## Architectural Analysis

llm-d-benchmark is architecturally a client-side orchestration tool rather than a long-running service. The Python CLI drives Kubernetes via kubectl/helm subprocess calls and the Python kubernetes SDK, following a phased step-executor pattern: each lifecycle command (standup, run, teardown, experiment) is decomposed into numbered steps executed by a shared `StepExecutor` framework that handles sequencing, parallelism across multi-model stacks, dry-run mode, and error aggregation.

The configuration system is notably layered: a Jinja2 template rendering pipeline merges `defaults.yaml` base values with scenario overrides, specification templates, cluster-config files, environment variables, and CLI `--set` overrides. This chain produces fully rendered Kubernetes manifests before any cluster interaction occurs, making the plan phase purely local and reviewable. The `--dry-run` flag exercises the entire render pipeline without touching the cluster.

The benchmark image itself is heavyweight -- it bundles multiple inference harnesses (inference-perf, vllm, guidellm, aiperf, lm-eval), the OpenShift CLI, gcloud/AWS CLI tools, and analysis scripts into a single container. This container runs as a StatefulSet pod on the cluster (or locally as the CLI), executing benchmark workloads against deployed inference endpoints. A separate lightweight `llm_d_stack_discovery` image provides runtime introspection of deployed stacks by tracing from an endpoint URL through Gateway API, OpenShift Routes, InferencePool, and InferenceModel CRDs.

The security posture is intentionally permissive for a benchmarking tool: the kustomize-based deployment grants `pods/exec` to all authenticated users in the namespace, and the Kubernetes client connection code has an explicit `verify_ssl = False` path for token-based auth. The HuggingFace token handling cascades through three environment variables (`HF_TOKEN`, `LLMDBENCH_HF_TOKEN`, `HUGGING_FACE_HUB_TOKEN`) and is rendered into Kubernetes Secrets for model download access.
