## Purpose

**Short**: KServe is a Kubernetes-native model inference platform that provides controllers, webhooks, and data-plane components for deploying, scaling, and routing traffic to machine learning models.

**Detailed**: KServe is the core model serving component in Red Hat OpenShift AI (RHOAI). It provides a declarative API for deploying ML models as `InferenceService` resources, with support for multiple deployment modes (raw Kubernetes, Knative serverless), multiple autoscaling backends (HPA, KEDA, WVA), and multiple ingress strategies (Gateway API HTTPRoute, Istio VirtualService, Kubernetes Ingress). The operator manages the full lifecycle of model serving workloads including storage initialization, sidecar injection, ingress routing, monitoring, and TLS configuration.

The repository also includes the `LLMInferenceService` controller (v1alpha2), a next-generation controller purpose-built for large language model workloads. It supports disaggregated prefill/decode architectures, multi-node serving via LeaderWorkerSet, Gateway API Inference Extension (GIE) InferencePools, workload variant autoscaling (WVA), and LoRA adapter hot-loading. Additionally, the `InferenceGraph` controller enables DAG-based inference pipelines, `LocalModel` controllers manage node-local model caching, and the `kserve-module` controller orchestrates KServe deployment within the ODH/RHOAI platform operator framework.

## Architectural Analysis

KServe's architecture is a multi-controller design where each major feature area is split into a separate binary and deployment. The main `kserve-controller` manages the original `InferenceService` API with its predictor/transformer/explainer component model, while the `llmisvc-controller` is a purpose-built controller for LLM workloads that takes a fundamentally different approach — managing scheduler (EPP) deployments, InferencePools, LoRA adapter volumes, disaggregated prefill/decode topologies, and multi-node LeaderWorkerSets. This separation allows the LLM controller to evolve rapidly without impacting the stable InferenceService API.

The repository uses Go build tags (`//go:build distro` vs `//go:build !distro`) extensively to separate ODH/RHOAI-specific behavior from upstream KServe. Platform-specific code includes: OpenShift Route watching for URL discovery, Istio DestinationRule creation for mTLS, SecurityContextConstraints RoleBindings for image volume and multi-node workloads, Kuadrant AuthPolicy precondition checks, and enhanced monitoring with PodMonitors/ServiceMonitors. This pattern allows maintaining a single codebase that compiles differently for upstream Kubernetes vs RHOAI, with the `GOTAGS="distro"` build argument in Konflux Dockerfiles activating the downstream path.

The `kserve-module` (in `kserve-module/`) represents the ODH/RHOAI platform integration layer. It implements the `components.platform.opendatahub.io/v1alpha1 Kserve` CR and uses a deployer pattern to apply prefetched kustomize manifests from `/opt/manifests-template/`. It validates external dependencies (Istio, cert-manager, LWS CRDs, operator subscriptions) before proceeding with deployment, and manages upgrades including HardwareProfile migrations. The module's dependency tracking system uses `crdDep()` declarations to check for optional CRDs (Istio, Gateway API, KEDA) and reports missing dependencies via status conditions.

The webhook architecture is notable for its pod mutating webhook, which intercepts all Pod creates in namespaces with InferenceService labels and injects multiple sidecars/init-containers: storage-initializer (model download), agent (logging, batching), batcher, metrics-aggregate, and accelerator-injector. For LLMInferenceService, a separate webhook defaults local model cache labels by matching model URIs against LocalModelCache/LocalModelNamespaceCache resources. The InferenceService validation webhook and defaulter handle spec validation, runtime auto-selection, and default value injection.

A key architectural pattern in the LLMISvc controller is the GIE (Gateway API Inference Extension) integration. The controller creates InferencePool resources (supporting both v1alpha2 and v1 API versions during migration), which enable the gateway to perform intelligent request routing to model serving pods. The HTTPRoute points to the InferencePool as a backend reference, and the scheduler (EPP) deployment performs the actual endpoint picking. This creates a two-level routing architecture: Gateway → HTTPRoute → InferencePool → Scheduler → Workload pods. The migration from v1alpha2 to v1 InferencePool is tracked via an annotation (`serving.kserve.io/inference-pool-migrated: v1`) that acts as a one-way lock.
