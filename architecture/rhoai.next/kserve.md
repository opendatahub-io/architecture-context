## Purpose

**Short**: KServe is a Kubernetes-native model serving platform that provides CRDs and controllers for deploying, scaling, and managing machine learning inference workloads including traditional ML models and LLM inference services.

**Detailed**: KServe provides the core model serving infrastructure for Red Hat OpenShift AI. It defines multiple custom resources -- InferenceService for traditional ML model serving, LLMInferenceService for large language model inference with features like disaggregated prefill/decode, multi-node serving via LeaderWorkerSets, and Gateway API integration via InferencePool. The platform also includes InferenceGraph for composing multi-step inference pipelines, LocalModelCache for node-local model caching with PV/PVC management, and ServingRuntime/ClusterServingRuntime for runtime configuration.

The repository produces nine distinct container images spanning controllers, sidecars, init containers, and inference routers. The kserve-module controller acts as the RHOAI platform integration layer, deploying KServe components via kustomize manifests and managing dependencies on Istio, cert-manager, and LeaderWorkerSet CRDs. A Python SDK provides the storage initializer for downloading models from S3, GCS, Azure, HuggingFace, and OCI sources, as well as server frameworks for custom model serving.

### kserve-agent

**Dockerfile**: `Dockerfiles/agent.Dockerfile.konflux`
**Intent**: Sidecar container injected into inference pods by the pod mutating webhook. Provides three capabilities: (1) model puller -- watches a config directory and downloads models on demand, (2) request/response logger -- intercepts inference traffic and sends CloudEvents to a configured log URL or blob storage, (3) request batcher -- batches inference requests for throughput optimization. Injected into every InferenceService pod that requires logging, batching, or dynamic model updates.
**Image**: odh-kserve-agent
**Language**: Go
**Port**: 9081/TCP (agent proxy), 9083/TCP (log marshaller)

### kserve-router

**Dockerfile**: `Dockerfiles/router.Dockerfile.konflux`
**Intent**: HTTP router for InferenceGraph that routes inference requests through a directed acyclic graph of inference steps. Supports splitter (weighted random), switch (condition-based), ensemble (parallel fan-out), and sequence (serial pipeline) routing patterns. Deployed as a per-InferenceGraph Deployment or Knative Service. Supports optional TLS and Bearer token authentication with Kubernetes TokenReview/SubjectAccessReview.
**Image**: odh-kserve-router
**Language**: Go
**Port**: 8080/TCP (HTTP/HTTPS inference endpoint)

### kserve-storage-initializer

**Dockerfile**: `Dockerfiles/storage-initializer.Dockerfile.konflux`
**Intent**: Init container injected into inference pods to download model artifacts before the main container starts. Supports multiple storage backends: S3, GCS, Azure Blob, HuggingFace Hub, HDFS, PVC, HTTP/HTTPS, and OCI. Includes confidential model serving support with JWE decryption via Confidential Data Hub (CDH). The runtime command is set by the consuming pod spec's init container args: `initializer-entrypoint <src_uri_0> <dest_path_0> ...`.
**Image**: odh-kserve-storage-initializer
**Language**: Python 3.11
**Port**: N/A (init container, no network listener)

## Architectural Analysis

KServe follows a multi-controller architecture where each major CRD group has its own controller binary. The main `kserve-controller-manager` handles InferenceService (v1beta1), InferenceGraph (v1alpha1), and TrainedModel, while `llmisvc-controller-manager` handles LLMInferenceService (v1alpha2) and LLMInferenceServiceConfig independently. This separation allows the LLM-specific controller to evolve rapidly without destabilizing the stable InferenceService API. The `kserve-module-controller` sits above both as the RHOAI platform integration layer, deploying the other controllers and their manifests via kustomize.

The codebase makes extensive use of Go build tags (`//go:build distro` vs `//go:build !distro`) to separate upstream KServe behavior from RHOAI-specific features. This includes OpenShift-specific RBAC (SCC bindings), Istio DestinationRule creation, OpenShift Route URL discovery, and kube-rbac-proxy sidecar injection. The build tag approach keeps the upstream codebase clean while allowing deep platform integration without forking. Files like `workload_permissions_odh.go`, `router_platform_networking_odh.go`, and `controller_setup_odh.go` contain RHOAI-specific logic that compiles only with the `distro` tag.

The LLMInferenceService controller is the most architecturally complex component, managing a full stack of resources per CR: workload Deployments or LeaderWorkerSets, scheduler (EPP) Deployments with RBAC, InferencePools (both GIE v1 and v1alpha2 for migration), HTTPRoutes, Services, TLS Secrets, HPA/KEDA/WVA autoscaling, PodMonitors/ServiceMonitors, Istio DestinationRules, and DRA ResourceClaimTemplates. The controller uses a strategic merge patch system where LLMInferenceServiceConfig resources are layered (well-known configs → user baseRefs → inline spec overrides) with Go template variable substitution. This allows platform operators to ship accelerator-specific presets (NVIDIA CUDA, AMD ROCm, Intel Gaudi, IBM Spyre) while users can override individual fields.

The InferencePool v1alpha2-to-v1 migration is managed via an annotation-based one-way lock (`serving.kserve.io/inference-pool-migrated: v1`). Once a workload's HTTPRoute backendRef is successfully migrated to v1 InferencePool, it never falls back to v1alpha2. The controller also performs version-gated scheduler config transformations (v0.6 through v0.9) to handle breaking changes in the EPP configuration format across versions, including plugin renames and parameter restructuring.

The local model caching system is a two-tier architecture: `LocalModelCache` (cluster-scoped) and `LocalModelNamespaceCache` (namespace-scoped) define what models to cache, while `LocalModelNode` CRs track per-node download status and `LocalModelNodeGroup` defines target node sets. The `localmodel-controller` creates PVs/PVCs for model storage, and the `localmodelnode-agent` creates batch Jobs on target nodes to download model artifacts. This separation allows models to be pre-cached on nodes before inference pods start, significantly reducing cold-start time for large models.
