## Purpose

**Short**: KServe provides a Kubernetes-native platform for deploying, scaling, and managing machine learning model inference services on OpenShift AI, supporting both traditional ML models and large language models (LLMs).

**Detailed**: KServe is the model serving backbone of Red Hat OpenShift AI (RHOAI). It defines a declarative API surface through Custom Resource Definitions—primarily `InferenceService` for traditional model serving and `LLMInferenceService` for LLM workloads—that lets users specify a model artifact, a serving runtime, and scaling policies, then reconciles the full deployment lifecycle: container scheduling, autoscaling (HPA and KEDA), ingress routing (Gateway API HTTPRoutes or OpenShift Routes), TLS termination, and observability (Prometheus ServiceMonitors, OpenTelemetry Collectors).

The repository ships as an ODH midstream fork of the upstream `kserve/kserve` project. ODH-specific behavior is isolated via Go build tags (`//go:build distro` in `*_odh.go` files, with `_default.go` no-op counterparts), enabling clean rebasing. The primary deployable is the `kserve-module-controller`, a single Go binary built with `controller-runtime` that bundles the `odh-model-controller` (managing InferenceService networking, RBAC, webhooks, and NIM account integration) and a model-serving API server. Alongside the Go controllers, KServe provides a Python SDK (`python/kserve/`) that implements the KServe Predict Protocol v2 over both REST (FastAPI/Uvicorn) and gRPC, plus a collection of model server implementations (HuggingFace, sklearn, LightGBM, XGBoost, PMML, Paddle, ART, AIF360, AutoGluon) that are packaged as separate container images.

KServe also includes a local model caching subsystem (`LocalModelCache`, `LocalModelNode`) that pre-stages model artifacts on cluster nodes via PersistentVolumes and download Jobs, a request router for InferenceGraph traffic splitting, and a queue proxy extension (`qpext`) for Prometheus metrics collection from model serving pods.

## Architectural Analysis

KServe's architecture follows a layered controller pattern with clear separation between the platform integration layer and the model serving data plane. The `kserve-module-controller` binary serves as the deployment unit for RHOAI: it runs the `KserveModuleReconciler` as the top-level controller that watches the platform `Kserve` component CR and reconciles all child resources—CRDs, webhooks, RBAC, deployments, DaemonSets, and NetworkPolicies—making KServe deployable as a self-contained ODH module.

Beneath this module controller sit four domain-specific controller binaries, each running as separate reconcile loops within the same process or independently: the core `InferenceServiceReconciler` (managing v1beta1 InferenceService lifecycle including Knative/Kubernetes deployments, autoscalers, and ingress), the `LLMISVCReconciler` (managing v1alpha2 LLMInferenceService with LeaderWorkerSets, InferencePools, and Gateway API integration for LLM-specific workloads), the `LocalModelReconciler` / `LocalModelNamespaceCacheReconciler` (coordinating model pre-caching across nodes), and the `LocalModelNodeReconciler` (running as a DaemonSet agent to manage per-node download jobs).

The distro build-tag pattern (`distro` / `!distro`) is a significant design decision. Every controller hook that adds OpenShift- or ODH-specific behavior (OpenShift Route creation, service-CA certificate injection, DataScienceCluster CR watches, NIM account management, HardwareProfile awareness) is isolated in `*_odh.go` files. This keeps the upstream codebase cleanly mergeable while allowing the downstream to layer on features like Kuadrant AuthPolicy integration, Istio DestinationRule/EnvoyFilter management, and OpenShift SecurityContextConstraints.

TLS handling is architecturally notable. The `pkg/tls` package provides configurable TLS version and cipher suite selection (defaulting to TLS 1.2+ with ECDHE AEAD ciphers). A `ProfileWatcher` controller monitors the OpenShift `config.openshift.io/v1/APIServer` resource to detect the cluster's TLS security profile and dynamically adjusts controller TLS settings. For the Konflux build pipeline, the `kserve-module-controller` Dockerfile uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` with a UBI 9 pqc (post-quantum cryptography) runtime base, ensuring FIPS-compliant dynamic linking.

The serving runtime registry is extensive, with 27 `ClusterServingRuntime` definitions covering vLLM across five accelerator variants (CUDA, ROCm, Gaudi, Spyre, CPU), each with three fast-channel cadences, plus MLServer, OpenVINO Model Server (OVMS), and specialized runtimes. Runtime images are parameterized through kustomize `configMapGenerator` replacements from `params.env`, allowing per-environment image pinning.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Inferred from CRD scope: all core serving CRDs (InferenceService, LLMInferenceService, ServingRuntime, etc.) are Namespaced |
| **Deployment model** | Single controller deployment, multi-tenant namespace scoping | `kserve-module/prefetched-manifests-rhoai/modelcontroller/manager/manager.yaml` |
| **Tenant identifier** | Namespace name | Controller reconciliation uses namespace-scoped watches and owner references |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC generated for InferenceService owners; admission webhooks validate tenant operations | Kubernetes (RBAC, admission) | Python model servers have no auth middleware; rely on network-level isolation |
| Data storage | Per-namespace PVCs for model caching; storage credentials scoped to namespace Secrets | Kubernetes | LocalModelCache uses cluster-scoped PVs which are shared across namespaces (by design, for node-local caching) |
| Network traffic | NetworkPolicy created per namespace for serving pods; Kuadrant AuthPolicy for ingress | Kubernetes (NetworkPolicy), Kuadrant | NetworkPolicy creation is conditional on platform configuration |
| Compute & resources | No ResourceQuota/LimitRange enforcement by KServe itself; delegates to platform | Platform administrator | Noisy-neighbor risk if platform does not set quotas |
| Configuration & secrets | Per-namespace Secrets for storage credentials, NIM accounts; ConfigMaps for controller config are in controller namespace | Kubernetes | ClusterServingRuntimes and ClusterStorageContainers are cluster-scoped (shared across all tenants) |
| API scoping | Namespace-scoped controller watches; InferenceService/LLMInferenceService are namespace-scoped | Kubernetes (namespace isolation) | ClusterServingRuntime changes affect all namespaces |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| kserve-module-controller | Cluster-wide singleton | Kubernetes RBAC; controller processes all namespaces |
| ClusterServingRuntimes | Cluster-wide | Shared runtime definitions; any namespace can reference them |
| LocalModelCache PVs | Node-level | PVs are cluster-scoped; PVCs per namespace provide namespace-level binding |
