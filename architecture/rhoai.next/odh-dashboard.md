## Purpose

**Short**: The RHOAI Dashboard is the web-based management console for Red Hat OpenShift AI, providing a unified UI for data scientists and administrators to manage ML/AI workloads, model serving, experiments, and platform resources.

**Detailed**: odh-dashboard is a TypeScript/Go monorepo that delivers the primary user interface for the Red Hat OpenShift AI platform. It is organized as a pnpm workspace with a React/PatternFly frontend served by a Node.js backend (Fastify), a Go-based Backend-for-Frontend (BFF) core service, and a dashboard-operator built with controller-runtime that manages the lifecycle and deployment of all dashboard components.

The repository implements a federated micro-frontend architecture using Webpack Module Federation. Each feature area (Gen AI, Model Registry, Notebooks, MLflow, MaaS, Eval Hub, AutoML, AutoRAG, Agent Ops, Data Connect Hub, Data Registry) is developed as an independent package under `packages/`, built into its own container image with a dedicated Go BFF sidecar, and deployed as a separate pod. The core dashboard pod runs three containers: the Node.js frontend/backend, a kube-rbac-proxy sidecar for TLS termination and authentication, and a Go core-bff service.

The dashboard-operator (a separate controller-runtime binary) reconciles the `Dashboard` custom resource created by the platform operator (rhods-operator/opendatahub-operator). It renders kustomize manifests for the core deployment, all federated module deployments, RBAC, networking (HTTPRoute via Gateway API), and monitoring resources. The operator also includes the Kubeflow Workspaces controller, which manages `Workspace` and `WorkspaceKind` CRDs for notebook workspace lifecycle.

## Architectural Analysis

The odh-dashboard architecture reflects a deliberate migration from a monolithic Node.js application to a federated micro-frontend platform. The legacy Node.js backend (`backend/`) serves the React SPA and proxies Kubernetes API calls using user token impersonation. The newer Go BFF layer (`distributions/core-bff/bff/` and `packages/*/bff/`) provides domain-specific APIs that aggregate calls to Kubernetes, external ML services (Llama Stack, MLflow, MaaS, NeMo Guardrails), and platform CRDs.

A notable design decision is the dual-auth architecture. The kube-rbac-proxy sidecar handles TLS termination and initial OpenShift authentication for the legacy Node.js backend on port 8443. The Go BFF services independently manage TLS using certificates from the OpenShift service-ca operator and enforce authentication via bearer tokens (either forwarded user tokens or internal service account tokens), configurable per-BFF via command-line flags. This creates two parallel authentication stacks within the same deployment.

The TLS configuration is notably mature: a shared `pkg/tls` package reads the cluster-wide TLS security profile from the OpenShift APIServer resource (`apiservers.config.openshift.io/cluster`) at startup and derives cipher suites and minimum TLS version accordingly, falling back to Mozilla Intermediate defaults (TLS 1.2, ECDHE-only ciphers) on non-OpenShift clusters. This ensures all Go BFF services honor the platform administrator's TLS policy. The runtime image for Go components uses `ubi9-minimal-pqc` (post-quantum cryptography variant), and the main dashboard image generates a `DEFAULT:PQ` crypto policy at build time.

The deployment strategy uses the dashboard-operator as the sole deployer — the platform operator creates a `Dashboard` CR, and the dashboard-operator reconciles all child resources (Deployments, Services, RBAC, HTTPRoutes, NetworkPolicies). Each federated module is deployed as a separate pod with its own service account and network policy, following the principle of least privilege. The operator manages image references via `params.env` ConfigMaps injected through kustomize replacements, enabling the platform operator to pin container images for each component independently.

A significant architectural risk is the breadth of RBAC permissions: the `dashboard-operator-role` ClusterRole contains 61 rules spanning core Kubernetes APIs, OpenShift-specific APIs, KServe, Kubeflow, Feast, MLflow, TrustyAI, ModelRegistry, NIM, MCP, OpenTelemetry, and Gateway API resources. While this breadth reflects the dashboard's role as a universal management console, a compromise of the operator's service account would grant extensive cluster access.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace + per-user | manifests/base/deployment.yaml (user impersonation), BFF auth middleware |
| **Deployment model** | single-tenant (one dashboard deployment per platform instance) | manifests/base/deployment.yaml:6 (replicas: 2 for HA, but single deployment) |
| **Tenant identifier** | OpenShift user identity + project/namespace | backend/src/utils/proxy.ts (impersonation), BFF token extraction |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy for initial auth; per-request SubjectAccessReview and SelfSubjectAccessReview in BFF services; user token impersonation for K8s API calls | Kubernetes + Application | BFF auth-method is configurable; `internal` mode uses SA token rather than user token, potentially bypassing user-level RBAC for internal operations |
| Data storage | Per-namespace Kubernetes resources (Secrets, ConfigMaps, CRDs); no shared database | Kubernetes | Data isolation relies on Kubernetes namespace RBAC; dashboard's broad ClusterRole could theoretically access cross-namespace data |
| Network traffic | Per-module NetworkPolicy in manifests/modules/*/networkpolicy.yaml | Kubernetes | Core pod does not have a dedicated NetworkPolicy in the base manifests |
| Compute & resources | Resource requests/limits per container; PodDisruptionBudget | Kubernetes | No per-user compute isolation; all users share the same dashboard pods |
| Configuration & secrets | Per-namespace Secrets; OdhDashboardConfig is namespace-scoped | Kubernetes | Some ConfigMaps (kube-rbac-proxy-config, federation-config) are shared across all users |
| API scoping | User token impersonation scopes K8s API calls to user's RBAC; BFF queries filter by namespace | Kubernetes + Application | SelfSubjectAccessReview queries in BFF are application-enforced |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Dashboard Node.js backend | per-user via token impersonation | Kubernetes RBAC via kube-apiserver |
| Core BFF and module BFFs | per-user via bearer token + SSAR | Application-level RBAC checks |
