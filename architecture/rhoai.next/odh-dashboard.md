## Purpose

**Short**: Web dashboard providing the primary user interface for Red Hat OpenShift AI (RHOAI), enabling data scientists and ML engineers to manage notebooks, model serving, pipelines, and platform configuration through a modular single-page application backed by Go BFF microservices and a Kubernetes operator.

**Detailed**: odh-dashboard is a large monorepo that produces the RHOAI/ODH web console. It uses a Module Federation architecture where a core React/TypeScript frontend shell loads feature-specific UI modules (Gen AI, Model Registry, MaaS, MLflow, Eval Hub, AutoML, AutoRAG, Agent Ops) at runtime. Each UI module is paired with a dedicated Go BFF (Backend-for-Frontend) server that handles Kubernetes API proxying, domain-specific business logic, and upstream service integration.

The repository produces 12 distinct container images via Konflux: one monolithic dashboard (Node.js backend + React frontend), one core-bff (Go BFF replacement for the Node.js backend), one dashboard-operator (Go operator managing deployment lifecycle), eight federated module images (each containing a Go BFF + webpack Module Federation UI bundle), and one Sealights-instrumented variant for test coverage tracking.

The dashboard-operator (`components.platform.opendatahub.io/v1alpha1 Dashboard` CRD) orchestrates deployment in two modes: **sidecar mode** (all modules as containers within a single pod behind kube-rbac-proxy) and **standalone mode** (each module deployed as a separate pod with its own Service, NetworkPolicy, and RBAC). The operator manages module lifecycle including dependency resolution, federation ConfigMap generation, observability integration via Perses, and platform-aware configuration for RHOAI vs ODH deployments.

## Architectural Analysis

The odh-dashboard monorepo implements a sophisticated modular architecture that is actively transitioning from a monolithic Node.js BFF to a distributed Go BFF model using webpack Module Federation. This transition is visible in the codebase: `Dockerfile.konflux` builds the legacy monolith (Node.js backend + React frontend), while `Dockerfile.konflux.core-bff` and the 8 module Dockerfiles build the next-generation Go-based architecture. The co-existence of both patterns reflects an incremental migration strategy.

**Module Federation Architecture**: The frontend shell (in `distributions/base/`) loads feature-specific UI modules at runtime via webpack Module Federation `remoteEntry.js` endpoints. Each module (gen-ai, maas, model-registry, etc.) is a separate webpack build that exposes React components and extension points. The federation config (`manifests/modular-architecture/federation-configmap.yaml`) maps module names to their BFF service endpoints and proxy routes (e.g., `/gen-ai/api` → port 8143 path `/api`). This allows independent development, testing, and deployment of UI features.

**Service Account Isolation**: The modular architecture implements deliberate SA isolation within the shared pod. The main dashboard container and kube-rbac-proxy share the `odh-dashboard` SA token (mounted from a projected volume), while BFF module containers receive a separate `odh-dashboard-modules` SA token (mounted from a Secret-based projected volume). This limits blast radius: module BFFs can impersonate users and access module-specific CRDs but cannot modify core dashboard resources. The modules SA has targeted permissions (MLflow, OTel, Sandbox CRDs) while the dashboard SA has broader platform access.

**Dual Deployment Modes**: The dashboard-operator supports two deployment modes managed via the Dashboard CR. **Sidecar mode** (default) packs all containers (dashboard + kube-rbac-proxy + 8 module BFFs) into a single pod with a shared Service exposing ports 8043-8843. **Standalone mode** deploys each module as a separate Deployment/Service/NetworkPolicy triplet with dedicated service accounts, enabling independent scaling, fault isolation, and more granular RBAC. The operator dynamically generates the federation ConfigMap with service discovery information appropriate to each mode.

**Security Architecture**: All external traffic enters through the Gateway API HTTPRoute and hits kube-rbac-proxy on port 8443, which validates the user's identity via TokenReview and checks they can list OpenShift projects (a permissive baseline authorization). The proxy then forwards to the dashboard backend on localhost:8080 with auth headers (X-Auth-Request-User, X-Auth-Request-Groups). BFF modules receive the user's token via the `x-forwarded-access-token` header and impersonate the user when making K8s API calls, ensuring all operations are scoped to the user's actual RBAC permissions. Inter-module communication (e.g., gen-ai → maas) also passes the user token through, maintaining the authentication chain.

**pgvector Auto-Provisioning**: The gen-ai BFF module has specialized RBAC to auto-provision a pgvector PostgreSQL deployment within user namespaces for vector storage. This creates Deployments, Services, PVCs, Secrets, ConfigMaps, and NetworkPolicies with deterministic names (prefixed `genai-pgvector-`), scoped to specific resourceNames in the ClusterRole to minimize privilege.
