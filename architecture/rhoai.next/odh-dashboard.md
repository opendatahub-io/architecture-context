## Purpose

**Short**: The RHOAI/ODH Dashboard is the web-based management console for Red Hat OpenShift AI, providing a unified UI for managing data science projects, model serving, notebooks, pipelines, and generative AI features.

**Detailed**: The odh-dashboard repository is a large TypeScript/Go monorepo that produces the primary user-facing web application for the RHOAI platform. It consists of three major architectural layers: (1) a React/PatternFly 6 frontend built with Webpack Module Federation that serves as the shell application, (2) a Node.js/Fastify backend (legacy monolithic BFF) that proxies Kubernetes API calls and manages authentication, and (3) a constellation of Go-based Backend-for-Frontend (BFF) modules that each serve a domain-specific micro-frontend and its corresponding API surface.

The monorepo also contains a Go-based dashboard-operator that reconciles a cluster-scoped `Dashboard` CRD to manage the deployment lifecycle of the dashboard and its BFF modules. The operator supports two deployment modes: **Sidecar** (all BFF modules run as containers in the main dashboard pod) and **Standalone** (each module gets its own Deployment, Service, and RBAC). Module enablement is driven by DSC (DataScienceCluster) component availability — when a platform component like KServe or Model Registry is enabled, the corresponding dashboard module is automatically deployed.

The dashboard integrates with nearly every RHOAI component: KServe for model serving, Kubeflow Pipelines for ML workflows, Model Registry for model catalog, TrustyAI for bias metrics, MLflow for experiment tracking, NeMo Guardrails for content moderation, Kueue for workload queuing, and many more. It serves as the single pane of glass for the entire platform.

## Architectural Analysis

The odh-dashboard is architecturally one of the most complex components in the RHOAI platform due to its dual role as both the user-facing frontend and a multi-protocol API gateway. The codebase has undergone a major architectural evolution from a monolithic React+Node.js application to a Webpack Module Federation-based micro-frontend architecture with Go BFF modules — and both patterns coexist in the current codebase.

**Module Federation Architecture**: The sidecar deployment mode co-locates up to 10 containers in a single pod (dashboard shell + kube-rbac-proxy + 8 BFF modules), all sharing a single `odh-dashboard` Service with different ports (8443, 8043, 8143, 8243, 8343, 8543, 8643, 8743, 8843). The legacy Node.js backend acts as the shell that proxies Module Federation remote entry points and API requests to the appropriate BFF container. Each BFF module serves its React micro-frontend as static files and exposes a Go-based API that proxies to domain-specific upstream services. The `federation-configmap.yaml` ConfigMap drives the routing: the dashboard backend reads it to know how to map URL prefixes (e.g., `/gen-ai/api` → port 8143, `/maas/api` → port 8243) to sidecar containers.

**Inter-BFF Communication**: The BFF modules form an internal service mesh. The gen-ai module calls the MaaS BFF for model catalog data and the MLflow BFF for experiment tracking. The eval-hub module calls the model-registry BFF for model lookups. These inter-BFF calls use TLS with forwarded user tokens, creating a chain of trust: user → kube-rbac-proxy → dashboard backend → BFF → upstream BFF. The service names and ports for inter-BFF communication are configurable per deployment mode (sidecar uses `odh-dashboard` service name; standalone uses per-module service names like `odh-dashboard-gen-ai`).

**SA Token Isolation**: The modular architecture deploys with careful service account token isolation. The dashboard shell and kube-rbac-proxy share the `odh-dashboard` SA token (broad permissions for K8s API proxy), while BFF modules use a separate `odh-dashboard-modules` SA token with restricted permissions. In sidecar mode, the pod disables `automountServiceAccountToken` and uses projected volumes to mount the appropriate token into each container. This limits blast radius — a compromised BFF module cannot escalate to full dashboard permissions.

**Dashboard Operator**: The operator introduces a second control plane layer. It reconciles a cluster-scoped `Dashboard` CR and dynamically renders kustomize manifests to deploy the dashboard. Module enablement follows a three-phase resolution: (1) read DSC component availability from the Dashboard CR's `spec.components` map, (2) apply per-module overrides from `spec.modules`, (3) resolve inter-module dependencies (e.g., MLflow requires the mlflow DSC component). The operator supports hot-switching between Sidecar and Standalone deployment modes via `spec.deploymentMode`. The singleton constraint (`default-dashboard` name validation) prevents accidental multi-instance deployments.

**Network Policy Design**: The NetworkPolicy configuration reflects the architectural complexity. In sidecar mode, a single NetworkPolicy opens all BFF ports (8043-8843) and allows broad egress. In standalone mode, each module gets its own NetworkPolicy with precise egress rules — for example, the gen-ai standalone deployment only allows egress to the MaaS pod (port 8243), MLflow pod (port 8343), K8s API (port 6443), DNS, and external HTTPS (port 443). This is notably more secure than the sidecar mode's catch-all egress policy.
