## Purpose

**Short**: A Caikit module backend that manages connections to TGIS (Text Generation Inference Service) servers for running large language models.

**Detailed**: caikit-tgis-backend is a Python library that provides a backend plugin for the [Caikit](https://github.com/caikit/caikit) AI runtime framework. It implements `BackendBase` from `caikit.core.module_backends` to manage connections between Caikit and TGIS, IBM's text generation inference server (based on the FMaaS gRPC protocol). The library enables Caikit-based inference runtimes to use TGIS as the model serving engine for large language models.

The backend supports two operational modes: **remote mode**, where it connects to an externally-managed TGIS server via gRPC (with optional TLS/mTLS), and **local mode**, where it launches and manages a TGIS subprocess directly. In remote mode, the backend provides client-side gRPC load balancing with DNS-based endpoint discovery and automatic channel reconnection when new endpoints appear. In local mode, it manages the TGIS process lifecycle including health polling, automatic failure recovery, and subprocess restart. The library also handles prompt artifact management, copying prompt tuning vectors to TGIS's prefix store.

This component is part of the Caikit ecosystem used in Red Hat OpenShift AI for model serving. It is consumed as a Python dependency by the `caikit-tgis-serving` runtime container and is not deployed as a standalone service. It provides the bridge between Caikit's module abstraction and TGIS's gRPC-based generation API.

## Architectural Analysis

The caikit-tgis-backend library follows a clean plugin architecture, implementing the `BackendBase` interface from the Caikit framework. The `register_backend_type(TGISBackend)` call at module level automatically registers the "TGIS" backend type when the library is imported, making it available for Caikit's backend configuration system. This pattern allows the consuming runtime to select TGIS as a backend through configuration without code changes.

The dual-mode architecture (remote vs. local TGIS) is a notable design decision. In remote mode, the library provides a sophisticated client-side load balancing implementation (`GRPCLoadBalancerProxy`) that polls DNS at configurable intervals (default 10 seconds) to discover new TGIS replicas. When new IP addresses appear in DNS resolution, the proxy transparently reconnects by re-initializing the gRPC client's channel without replacing the client object reference — this avoids forcing callers to update their references. The load balancing policy (default `round_robin`) is set via gRPC channel options. In local mode, the `ManagedTGISSubprocess` class implements a resilient process manager with health polling, bootup timeout enforcement, and auto-recovery: when an RPC call fails with specific error codes (ABORTED, DEADLINE_EXCEEDED, INTERNAL, UNAVAILABLE, UNKNOWN), a background thread checks health and restarts the process if needed. The `AutoRecoveringGenerationServiceStub` wraps every RPC method to intercept errors and trigger recovery.

The TLS implementation is straightforward but complete. The `TGISConnection` class supports three security levels: insecure (plaintext gRPC), server-TLS (CA cert only), and mutual TLS (CA cert + client cert/key pair). Validation logic enforces that client TLS cannot be set without a CA cert, and that client cert and key must be provided together. All certificate files are read from disk paths, with existence checks at configuration time. The library does not manage certificate rotation — it reads certificates once at connection time.

A notable limitation documented in code comments is that the local TGIS mode does not support multiple models concurrently. TGIS (at the time of this code) can only serve one model at a time, so attempts to load a second model in local mode will fail. The code includes TODO comments about supporting multi-model via per-model processes with dynamic port allocation. This limitation does not affect remote mode, where model-specific connection configurations allow routing to different TGIS instances per model.

The proto definition (`generation.proto`) defines the FMaaS (Foundation Model as a Service) gRPC interface under the `fmaas` package. It supports four RPCs: `Generate` (batched unary), `GenerateStream` (server-streaming for a single prompt), `Tokenize` (batched), and `ModelInfo`. The parameter space is rich: decoding method (greedy/sampling), sampling controls (temperature, top_k, top_p, typical_p), stopping criteria (max/min tokens, time limit, stop sequences), and response options (token details, logprobs, ranks, top-N candidates). This proto is a copy of the TGIS server's interface definition — it is compiled locally via `scripts/gen_tgis_protos.sh` using `grpc_tools.protoc`.
