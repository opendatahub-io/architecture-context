## Purpose

**Short**: Python library that provides a Caikit module backend for connecting to and managing TGIS (Text Generation Inference Service) instances.

**Detailed**: caikit-tgis-backend is a Python library that implements the `BackendBase` interface from the Caikit AI framework. It provides the `TGISBackend` class, which manages connections to TGIS servers -- either remote instances accessed over gRPC or locally-managed TGIS subprocesses. The backend handles model lifecycle (loading/unloading), connection management with TLS/mTLS support, and client-side gRPC load balancing with DNS-based endpoint discovery.

This library is not deployed as a standalone service. It is imported as a dependency by Caikit-based serving runtimes (such as `caikit-tgis-serving`) that run inside model serving pods in the RHOAI platform. The library communicates with TGIS inference servers over gRPC using the `fmaas.GenerationService` protocol, which supports text generation (unary and streaming), tokenization, and model info queries. It also supports prompt tuning via artifact loading to a shared filesystem directory.

The library provides auto-recovery capabilities for locally-managed TGIS subprocesses: if the subprocess becomes unhealthy, the `AutoRecoveringGenerationServiceStub` wrapper detects gRPC errors and triggers automatic subprocess restart. For remote connections, it includes a DNS-polling load balancer (`GRPCLoadBalancerProxy`) that periodically resolves the target hostname and reconnects the gRPC channel when new endpoints appear.

## Purpose

**Short**: Caikit backend module that bridges the Caikit AI runtime to TGIS (Text Generation Inference Server) via gRPC, supporting remote connections with TLS/mTLS and optional local TGIS subprocess management.

**Detailed**: caikit-tgis-backend is a Python backend plugin for the Caikit AI framework. It registers as a `TGIS` backend type via `caikit.core.module_backends` and provides model inference capabilities by acting as a gRPC client to TGIS servers. The module supports two operating modes: (1) remote mode, where it connects to one or more pre-existing TGIS instances identified by hostname, supporting TLS and mutual TLS for transport security; and (2) local mode, where it manages a TGIS subprocess lifecycle including launch, health polling, and automatic failure recovery. The gRPC client uses a custom load-balancing proxy (`GRPCLoadBalancerProxy`) that performs DNS-based service discovery with configurable polling intervals and reconnects channels when new endpoints appear. The proto definition (`generation.proto`) in this repository defines the `fmaas.GenerationService` interface that TGIS servers implement; this module consumes that interface as a client, it does not serve it.

## Data Flows

- **Inbound (from Caikit runtime):** The Caikit runtime framework invokes this backend module's Python API when a model backed by TGIS receives an inference request. There is no direct network ingress into this module — it is loaded in-process by the Caikit runtime.
- **Outbound to TGIS (gRPC):** The module establishes gRPC channels to TGIS servers (remote or local subprocess on port 50055/TCP by default). Channels pass through a `GRPCLoadBalancerProxy` that performs DNS-based endpoint discovery with configurable round-robin policy and reconnects when new IPs appear. - **Outbound health check (HTTP):** In local subprocess mode only, the module polls `http://localhost:{http_port}/health` (default port 3000/TCP) to determine when the TGIS process has finished loading a model and is ready for inference.
- **Prompt artifact flow:** When prompt tuning is enabled, the module copies prompt vector artifacts from the Caikit runtime's artifact paths to the TGIS instance's `prompt_dir` shared filesystem directory.

## Architectural Analysis

caikit-tgis-backend follows a clean separation between connection management and backend lifecycle. The `TGISBackend` class implements the Caikit `BackendBase` interface and handles the high-level concern of model-to-connection mapping, while `TGISConnection` manages the low-level gRPC channel setup including TLS credential loading and load balancer initialization. This separation allows the backend to support both remote multi-model scenarios (where each model can have its own connection config) and local single-model scenarios (where a subprocess is managed directly).

The load balancing implementation (`GRPCLoadBalancerProxy`) is notable for its approach to DNS-based service discovery. Rather than relying on Kubernetes service mesh or external load balancers, it polls DNS at a configurable interval (default 10 seconds) and reconnects the gRPC channel when new IP addresses appear. This is done by calling `client_class.__init__()` on the existing client instance to replace the underlying channel without requiring callers to obtain new client references -- a pragmatic but unusual pattern documented in the code with "spicy" emoji comments (load_balancing_proxy.py:176-178).

The auto-recovery mechanism for local TGIS subprocesses uses a thread-per-recovery design: when a gRPC error with specific status codes (ABORTED, DEADLINE_EXCEEDED, INTERNAL, UNAVAILABLE, UNKNOWN) is detected, a daemon thread is spawned to check health and restart the subprocess if needed. This is bounded by the `_TGISState` enum state machine (STOPPED → BOOTING → READY) with mutex-protected state transitions. The design handles the race condition where multiple concurrent requests detect failure simultaneously -- only the first thread to acquire the mutex triggers the restart.

The library has a notable limitation documented at `tgis_backend.py:46-50`: local mode does not support multiple models. TGIS itself is designed as a single-model server, so the local subprocess approach is inherently single-tenant. The remote mode partially addresses this by maintaining a `_model_connections` dict keyed by `model_id`, but all connections share the same TLS credentials from the base connection configuration. True multi-model support with per-model TLS would require extending the `remote_models` configuration.

From a security perspective, the TLS implementation is thorough for a library: it supports plaintext, TLS (server verification only), and full mTLS with separate CA, client cert, and client key files. Certificate validation is strict -- file existence is checked at configuration time (`tgis_connection.py:147-154`), and the library correctly enforces that mTLS requires both client cert and client key (not one without the other). However, there is no certificate rotation mechanism -- TLS files are read once at channel creation time.

## Architectural Analysis

This module is a **backend plugin**, not a standalone service. It has no network ingress of its own — it runs in-process inside the Caikit runtime and exposes no HTTP or gRPC servers. The `generation.proto` file in this repository defines the `fmaas.GenerationService` interface, but this module consumes that interface as a gRPC **client** (via `GenerationServiceStub`), not as a server. The TGIS binary that serves these RPCs is a separate component (`text-generation-launcher`).

The module supports two operating modes that reflect different deployment topologies. In **remote mode**, it connects to externally managed TGIS instances by hostname, supporting per-model connection configuration and model-ID templating in hostnames (e.g., `{model_id}-predictor:8033`). In **local mode** (when no remote connection is configured), it manages a TGIS subprocess lifecycle: launching `text-generation-launcher`, polling its HTTP health endpoint until the model is loaded, then creating an insecure gRPC channel to localhost. Local mode includes automatic failure recovery — when an RPC returns an error code indicating server failure (ABORTED, INTERNAL, UNAVAILABLE, UNKNOWN, DEADLINE_EXCEEDED), the `AutoRecoveringGenerationServiceStub` triggers a background thread that health-checks the subprocess and restarts it if needed.

The `GRPCLoadBalancerProxy` provides DNS-based client-side load balancing. It periodically resolves the target hostname via `socket.getaddrinfo`, and when new IP addresses appear (e.g., a Kubernetes headless Service scaling up), it replaces the gRPC channel to pick up the new endpoints. The load balancing policy defaults to `round_robin` and the DNS poll interval defaults to 10 seconds. This design enables the module to distribute inference requests across multiple TGIS replicas without requiring an external load balancer.

Transport security is configurable per-connection via `TGISConnection`: no TLS (insecure channel), server TLS (CA certificate only), or mutual TLS (CA certificate plus client certificate/key pair). The mTLS configuration requires both client cert and key to be provided together, and both require a CA cert. There is no application-level authentication (no tokens, no OAuth) — all authentication is at the gRPC transport layer.
