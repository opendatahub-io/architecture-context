## Purpose

**Short**: Operational utilities repository providing preflight diagnostics, network performance testing, and NIXL benchmarking tools for llm-d GPU-accelerated LLM serving deployments.

**Detailed**: llm-d-pd-utils ("Preflight Diagnostics Utilities") is a tooling repository in the llm-d ecosystem that provides scripts and AI agent skills for validating and diagnosing GPU networking and infrastructure health in llm-d deployments. Unlike most RHOAI components, this is not a deployable service — it is a collection of Python scripts, shell installers, and Claude Code skills that operators use to inspect, test, and benchmark the network fabric underlying llm-d model serving pods.

The repository centers on three capabilities: (1) **preflight checks** that run inside llm-d pods before vLLM starts, collecting GPU topology, NVLink status, and environment diagnostics with an optional pause mode that holds vLLM startup until operators signal readiness; (2) **networking tests** that drive perftest (RDMA), iperf3 (TCP), NCCL/RCCL collectives, and NIXL benchmarks between pod pairs to validate inter-pod bandwidth and latency; and (3) **NIXL benchmarking** that measures GPU VRAM-to-VRAM data transfer throughput via the NVIDIA Interconnect eXchange Library (NIXL) and UCX transport framework. These tools are packaged as Claude Code AI skills (`/llm-d-preflight-checks` and `/llm-d-networking-tests`) to enable AI-assisted operational workflows.

The repository also includes Kubernetes deployment manifests for NIXL benchmark client/server pods (with and without RoCE/RDMA), NIXL installation scripts for both root and non-root container environments, and a Dockerfile that builds an NVIDIA CUDA-based container image with NIXL, UCX, and gdrcopy pre-installed for benchmarking. The Makefile contains kubebuilder-scaffolded Go targets that are vestigial — no Go source code exists in the repository.

## Architectural Analysis

llm-d-pd-utils occupies an unusual position in the RHOAI component landscape: it is purely an operational tooling repository with no continuously running service, no CRDs, and no operator logic. Its architecture is best understood as three loosely coupled tool families sharing common infrastructure knowledge about llm-d's networking stack.

The **preflight checks** design is notable for its pod-intrusive approach — the script is injected into the vLLM container's startup command chain via `&&` sequencing, meaning it runs in the exact same environment (GPU bindings, RDMA devices, network namespace) that vLLM will use. In `pause` mode, it starts a minimal HTTP server on the vLLM inference port (default 8000) that satisfies Kubernetes health probes while blocking vLLM startup, allowing operators to `kubectl exec` into the pod for manual inspection. This design avoids sidecar complexity but couples the tool to the container entrypoint configuration.

The **networking test suite** is the largest component (~370K lines of Python) and follows a modular architecture: `run-tests-common.py` provides shared kubectl/SSH exec helpers and pod discovery logic, while specialized modules handle each test type (perftest, iperf3, NCCL/RCCL, nixlbench, topology discovery). The suite supports both direct pod execution and SSH-based remote execution, with optional ephemeral debug containers. Results include matplotlib-generated plots for visual analysis.

The **NIXL benchmark** operates in a client/server model using ZMQ for coordination and NIXL for data transfer. It creates GPU tensor datasets and measures transfer throughput between "creator" and "peer" agents across configurable thread counts. The deployment manifests define NodePort services for cross-node communication, with RoCE variants adding IPC_LOCK capabilities and multi-NIC network annotations (`k8s.v1.cni.cncf.io/networks`) for RDMA support.

A significant architectural observation is the presence of vestigial Go tooling scaffolding (Makefile with kubebuilder targets, `.golangci.yml`, `Dockerfile copy` referencing `cmd/main.go`, `api/`, `internal/`) despite the repository containing zero Go source files. The CI pipeline's Go lint and test steps are commented out, confirming this is leftover scaffolding from project initialization that was never cleaned up.
