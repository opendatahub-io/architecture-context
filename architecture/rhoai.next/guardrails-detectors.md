## Purpose

**Short**: A collection of detector microservices for the FMS Guardrails Orchestrator, providing text content analysis via regex/heuristic detectors, HuggingFace ML model-based detectors, and LLM-as-a-judge evaluation.

**Detailed**: Guardrails Detectors is a Python-based repository that produces multiple independently deployable detector microservices for use with the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator). The orchestrator invokes these detectors to analyze text generation input and output for safety, compliance, and quality concerns.

The repository produces three distinct detector types, each packaged as a separate container image: (1) a **built-in detector** that provides lightweight, heuristic detection functions including regex-based PII detection (email, credit card, SSN, phone numbers, IP addresses), file-type validation (JSON, XML, YAML with optional schema), and user-defined custom Python detectors; (2) a **HuggingFace detector** that loads and serves any `AutoModelForSequenceClassification`, `AutoModelForTokenClassification`, or `GraniteForCausalLM` model for ML-based content classification (deployed as a KServe InferenceService); and (3) an **LLM Judge detector** that integrates the [vLLM Judge](https://github.com/trustyai-explainability/vllm_judge) library to perform LLM-as-a-judge guardrailing against an external OpenAI-compatible LLM server.

All three detectors implement the same IBM Detector API contract (`/api/v1/text/contents`) and expose Prometheus metrics for observability. The HuggingFace and LLM Judge detectors are designed to be deployed as KServe ServingRuntimes/InferenceServices on Red Hat OpenShift AI, with Istio sidecar injection and platform auth support.

## Architectural Analysis

The guardrails-detectors repository follows a clean microservice architecture where each detector type is independently deployable as a separate container image, sharing a common Python package (`detectors.common`) for the FastAPI base application, Pydantic request/response schemas, and Prometheus instrumentation. This design allows each detector to scale independently and be deployed only when needed -- the built-in detector is lightweight and always-on, while the HuggingFace and LLM Judge detectors are heavier and deployed on-demand.

The common `DetectorBaseAPI` class (`detectors/common/app.py`) provides a consistent framework across all detectors, including a detector registry pattern, standardized error handling, and shared Prometheus counters (`trustyai_guardrails_detections`, `trustyai_guardrails_requests`, `trustyai_guardrails_errors`, `trustyai_guardrails_runtime`). The `InstrumentedDetector` base class adds per-function runtime measurement via a context manager, enabling fine-grained latency tracking per detection function.

The built-in detector's custom detector system (`custom_detectors_wrapper.py`) is architecturally notable for its security-conscious design. Before loading user-defined Python code, it performs static AST analysis to block dangerous imports (`os`, `subprocess`, `sys`, `shutil`) and function calls (`eval`, `exec`, `open`, `compile`, `input`). It also supports two decorator patterns for advanced use: `@use_instruments` for registering custom Prometheus metrics and `@non_blocking` for running detector logic asynchronously without blocking the API response.

The HuggingFace detector (`detectors/huggingface/detector.py`) is the most complex component, supporting three distinct model architectures (sequence classification, token classification, causal LM) through a unified API. The token classification path includes sophisticated span merging logic that groups adjacent tokens with the same label into contiguous detection spans with averaged confidence scores. The detector also implements a layered parameter resolution system (`_resolve_params`) that merges environment-level defaults, per-request `detector_params`, and model-level constraints (max length clamping).

A gap worth noting is that the LLM Judge detector has no Konflux Dockerfile, meaning it is not yet built through Red Hat's secure build pipeline and uses a generic `ubi9/python-312:latest` base image without AIPCC integration. This is a productization gap that needs to be addressed before the LLM Judge can ship as part of RHOAI. Additionally, the HuggingFace Konflux Dockerfile (`Dockerfile.konflux.hf`) installs packages via `pip install ".[huggingface]"` without hash-pinned requirements for the huggingface extras, unlike the built-in detector which has fully hash-pinned requirements. The `requirements-hf/cpu/` and `requirements-hf/cuda/` directories exist with compiled requirements but are not referenced by the Konflux Dockerfile.
