## Purpose

**Short**: A collection of detector algorithm microservices for the FMS Guardrails Orchestrator, providing text content analysis for safety, PII detection, file validation, and LLM-as-a-judge evaluation.

**Detailed**: Guardrails Detectors provides three independently deployable detector microservices that integrate with the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator), an IBM-led open source project for invoking detectors on LLM text generation input and output.

The three detectors serve distinct use cases: (1) a **built-in detector** offering lightweight regex-based PII detection (email, credit card, SSN, phone numbers, IP addresses), file-type validation (JSON, XML, YAML with optional schema), and user-defined custom detection functions; (2) a **HuggingFace detector** that loads any HuggingFace `AutoModelForSequenceClassification`, `AutoModelForTokenClassification`, or `GraniteForCausalLM` model for ML-based content classification including toxicity detection and prompt injection; and (3) an **LLM Judge detector** that uses the `vllm_judge` library to evaluate content against configurable metrics (safety, accuracy, helpfulness, etc.) via an external OpenAI-compatible LLM server.

All three detectors expose the same IBM Detector API contract (`/api/v1/text/contents`) and are designed to be deployed as KServe InferenceServices on RHOAI, with Prometheus metrics instrumentation for observability.

## Architectural Analysis

The guardrails-detectors repository follows a clean plugin architecture centered around the `BaseDetectorRegistry` abstract class. Each detector type (regex, file_type, custom, HuggingFace, LLM judge) implements this interface, providing a consistent `handle_request()` contract. The built-in detector composes multiple registries within a single process, while the HuggingFace and LLM judge detectors each run as standalone services. This design makes it straightforward to add new detector types -- implement `BaseDetectorRegistry`, register it in the app lifespan, and the existing API contract handles the rest.

The custom detector system (`custom_detectors_wrapper.py`) is architecturally notable for its security-conscious design. Before loading user-defined Python detector functions, it performs static code analysis via AST parsing to block dangerous imports (`os`, `subprocess`, `sys`, `shutil`) and function calls (`eval`, `exec`, `open`, `compile`, `input`). It also supports `@non_blocking` and `@use_instruments` decorators that let custom detectors run asynchronously and register Prometheus metrics without modifying the core framework. This suggests the platform intends for end users or operators to define custom guardrail logic at deployment time by mounting a `custom_detectors.py` file.

The HuggingFace detector demonstrates significant engineering depth around model flexibility. It auto-detects the model architecture at startup (sequence classification, token classification, or causal LM) and routes inference accordingly. The token classification path implements span merging -- grouping adjacent tokens with the same label into contiguous character spans with averaged scores. The causal LM path specifically supports IBM Granite Guardian models, iterating through a predefined set of risk categories (harm, social_bias, jailbreak, profanity, etc.) and parsing the model's generated "Yes"/"No" tokens with probability calibration. The `_resolve_params` method provides a layered parameter resolution system: environment variables set defaults, which can be overridden per-request via `detector_params`, with validation and clamping at each level.

A notable gap is that the LLM Judge detector has no Konflux Dockerfile, meaning it is not currently built via Red Hat's hermetic build pipeline. While the built-in and HuggingFace detectors are fully integrated with AIPCC base images and Konflux hermetic builds, the judge detector uses a plain UBI base image (`Dockerfile.judge`) and has no Tekton PipelineRun. This may indicate it is not yet GA for RHOAI, or that its Konflux integration is forthcoming. The `vllm_judge` library dependency (version 0.1.8) also suggests this component is relatively new.

All three detectors serve plaintext HTTP and delegate TLS/authentication entirely to the KServe platform infrastructure. The InferenceService example manifests include `security.opendatahub.io/enable-auth: 'true'` and `sidecar.istio.io/inject: 'true'` annotations, confirming the expected deployment pattern on RHOAI 3.x with Istio mTLS and kube-rbac-proxy authentication. The detectors are stateless beyond their loaded model, making horizontal scaling straightforward -- though the HuggingFace detector is limited to 1 worker due to GPU memory constraints (the ServingRuntime requests 18Gi memory).
