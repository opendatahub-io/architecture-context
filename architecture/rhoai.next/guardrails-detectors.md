## Purpose

**Short**: A collection of text detection microservices—regex/file-type built-ins, HuggingFace model classifiers, and LLM-as-a-judge evaluators—designed to run as detectors within the FMS Guardrails Orchestrator framework.

**Detailed**: guardrails-detectors provides three distinct detector microservices that integrate with the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator), the IBM-led open-source guardrails framework. Each detector is packaged as an independent container image exposing a FastAPI HTTP API on the standard Guardrails Orchestrator detector interface (`/api/v1/text/contents`, `/api/v1/text/generation`).

The **built-in detector** bundles lightweight heuristic functions: regex-based PII detection (email, credit card with Luhn validation, SSN, phone numbers, IP addresses), file-type validation (JSON, XML, YAML with optional schema enforcement), and user-defined custom Python detectors that are loaded dynamically at startup with basic static analysis sandboxing. The **HuggingFace detector** loads any `AutoModelForSequenceClassification`, `AutoModelForTokenClassification`, or `GraniteForCausalLM` model from disk and runs inference against text content, supporting GPU acceleration via CUDA. The **LLM Judge detector** wraps the [vllm_judge](https://github.com/trustyai-explainability/vllm_judge) library to perform LLM-as-a-judge evaluation against a remote vLLM-compatible inference server, supporting built-in metrics (safety, toxicity, accuracy, helpfulness) and custom criteria.

The HuggingFace and LLM Judge detectors are designed to be deployed as KServe InferenceServices using provided ServingRuntime definitions, integrating with the OpenDataHub/RHOAI model serving infrastructure. The built-in detector runs as a standalone microservice.

## Architectural Analysis

The codebase follows a clean plugin architecture centered on a shared `DetectorBaseAPI` FastAPI base class (in `detectors/common/app.py`) that provides health endpoints, Prometheus instrumentation counters (`trustyai_guardrails_{detections,requests,errors,runtime}`), and detector lifecycle management via the ASGI lifespan pattern. Each detector type registers itself into this framework at startup.

The built-in detector uses a registry pattern (`BaseDetectorRegistry`) to dispatch requests across three sub-registries: `RegexDetectorRegistry` (PII patterns with configurable timeout to prevent ReDoS), `FileTypeDetectorRegistry` (JSON/XML/YAML validation with optional schema enforcement), and `CustomDetectorRegistry` (dynamically loaded user Python functions). The custom detector system performs AST-based static analysis before loading user code, blocking dangerous imports (`os`, `subprocess`, `sys`, `shutil`) and calls (`eval`, `exec`, `open`). Users can also attach custom Prometheus counters via `@use_instruments` and run non-blocking background detections via `@non_blocking`.

The HuggingFace detector auto-detects model architecture at load time—token classification (with offset-mapping span merging), sequence classification (with per-label threshold support), or causal LM (specifically Granite Guardian with risk category iteration). It implements a layered parameter resolution: environment variable defaults can be overridden per-request via `detector_params`, with type validation and model-max-length clamping at each level.

The LLM Judge detector is stateless apart from its `Judge.from_url()` connection to a vLLM server. It defaults to the "safety" metric when no metric is specified and validates metrics against `vllm_judge.BUILTIN_METRICS`.

TLS support exists in `DetectorBaseAPI.main()` but is configuration-driven and not enabled in any Dockerfile or serving manifest. Encryption and authentication are delegated to the KServe/Istio service mesh, as confirmed by `security.opendatahub.io/enable-auth: 'true'` and `sidecar.istio.io/inject: 'true'` annotations on the example InferenceService manifests.

A notable gap: the LLM Judge detector has no Konflux Dockerfile and no Tekton PipelineRun, indicating it is not yet built via Red Hat's hermetic build pipeline.
