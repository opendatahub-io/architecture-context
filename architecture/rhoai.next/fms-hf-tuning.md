## Purpose

**Short**: Python library and container image for fine-tuning large language models using Hugging Face SFTTrainer with PyTorch FSDP for multi-GPU training.

**Detailed**: fms-hf-tuning provides a production-ready framework for supervised fine-tuning (SFT) of foundation models, primarily targeting the Hugging Face ecosystem. It wraps `trl.SFTTrainer` with Hugging Face Accelerate to orchestrate single-GPU and multi-GPU training via Fully Sharded Data Parallel (FSDP). The library supports multiple tuning techniques including full fine-tuning, LoRA, activated LoRA (aLoRA), GPTQ-LoRA, prompt tuning, and MXFP4 quantization, with pluggable acceleration backends (padding-free attention, fused LoRA kernels, ScatterMoE parallelism, and online data mixing).

The component is designed to run as a containerized batch job in Kubernetes environments. Configuration is supplied via JSON files or environment variables (not CLI arguments in the container entrypoint), and the container writes a `.complete` sentinel file to its output directory upon successful completion. It integrates with the broader RHOAI platform by providing the tuning runtime that the training operator schedules as Kubernetes Jobs. The library also supports experiment tracking via Aim, MLflow, ClearML, and file-based logging, and includes a trainer controller framework for policy-driven training loop control (e.g., early stopping based on loss thresholds).

## Architectural Analysis

fms-hf-tuning follows a layered architecture with a clear separation between the container entrypoint (`accelerate_launch.py`), the core training logic (`sft_trainer.py`), and pluggable subsystems for data preprocessing, acceleration, and experiment tracking. The entrypoint reads configuration from `SFT_TRAINER_CONFIG_JSON_PATH` or `SFT_TRAINER_CONFIG_JSON_ENV_VAR`, constructs accelerate launch arguments, and delegates to `accelerate launch` which spawns the training processes. This design allows transparent scaling from single-GPU to multi-node FSDP without changes to the training code.

The acceleration framework (`fms-acceleration` family of packages) is loaded dynamically based on configuration, providing an extensible plugin architecture for performance optimizations. Each acceleration plugin (PEFT quantization, fused ops, padding-free attention, MoE parallelism, online data mixing) is independently togglable and follows a consistent interface for model augmentation and custom callbacks. This modularity is a strength—operators can compose optimization strategies without code changes—but creates a complex configuration matrix where interactions between plugins must be carefully validated.

Error handling follows a structured exit-code convention: user errors (bad input, missing files) produce exit codes 1-127, while internal errors produce exit code 203. Errors are written to `/dev/termination-log` (or a configurable path), which integrates with Kubernetes termination message semantics, allowing the training operator to surface failure reasons.

The Dockerfile uses a multi-stage build with UBI9 as the base. CUDA 12.1 libraries are installed for GPU support, and a final `release-base` stage strips Python and dnf to reduce CVE surface. This is a notable security-hardening pattern: the runtime image contains only the pre-installed pip packages under the user's home directory, with no package manager or interpreter discovery tools.

Model loading follows a try-vision-then-language pattern: the trainer first attempts to load the model as a `AutoModelForVision2Seq` (for multimodal models like LLaVA/Granite Vision), and falls back to `AutoModelForCausalLM` for standard language models. This auto-detection approach simplifies configuration but means users cannot explicitly force one loader over the other.
