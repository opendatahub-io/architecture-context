## Purpose

**Short**: Python library and container image for fine-tuning large language models using Hugging Face SFTTrainer with PyTorch FSDP, designed to run as a batch training job in Kubernetes.

**Detailed**: fms-hf-tuning (Foundation Model Stack HF Tuning) provides a comprehensive fine-tuning framework for large language models. It wraps Hugging Face's `SFTTrainer` and PyTorch FSDP to support supervised fine-tuning (SFT) of decoder-style transformer models on single or multiple GPUs. The library supports multiple tuning techniques including LoRA, Activated LoRA (aLoRA), GPTQ-LoRA, Prompt Tuning, and full fine-tuning, with optional acceleration plugins for quantized LoRA, fused operations, padding-free attention, ScatterMoE, and online data mixing.

The component is deployed as a container image (`quay.io/modh/fms-hf-tuning`) that runs as a training job, typically orchestrated by the Kubeflow Training Operator (KFTO) as a `PyTorchJob` on Kubernetes. Configuration is passed via JSON config files or base64-encoded environment variables. The image includes an `accelerate_launch.py` entry point that wraps Hugging Face Accelerate's launch command, automatically configuring multi-GPU FSDP when multiple GPUs are detected. The library also provides a pluggable data preprocessing pipeline, a trainer controller framework for custom stopping criteria, and integrations with experiment trackers (Aim, MLflow, ClearML, file logger).

Within the RHOAI platform, fms-hf-tuning is the core fine-tuning engine consumed by the training operator. It does not run as a long-lived service -- it executes as a batch job that loads a model, processes training data, performs fine-tuning, saves checkpoints, and exits. The downstream repo (red-hat-data-services) adds Tekton pipeline definitions for Konflux CI/CD builds and synchronizes upstream tags automatically via GitHub Actions workflows.

## Purpose

**Short**: Python CLI/library for supervised fine-tuning (SFT) of HuggingFace language models, supporting LoRA, prompt tuning, aLoRA, and full parameter tuning with hardware acceleration via the fms-acceleration framework.

**Detailed**: fms-hf-tuning is a command-line tool and Python library that wraps HuggingFace's TRL SFTTrainer to provide a configurable supervised fine-tuning pipeline. It loads pre-trained language and vision models from HuggingFace Hub, processes training datasets through a flexible data preprocessing pipeline, and executes fine-tuning with optional PEFT methods (LoRA, activated LoRA, prompt tuning) and quantization (MXFP4). The tool integrates with the fms-acceleration framework for hardware-specific optimizations including padding-free attention, quantized LoRA, fused operations, ScatterMoE for mixture-of-experts models, and Online Data Mixing (ODM). Training metrics can be exported to external tracking services (MLflow, Aim, ClearML) via a pluggable tracker subsystem. In the RHOAI platform, fms-hf-tuning runs as a container within PyTorchJob pods managed by the training-operator, receiving its configuration via JSON environment variables or config files.

## Data Flows

- **Configuration ingestion:** The tuning job receives its configuration via one of three paths: command-line arguments parsed by HfArgumentParser, a base64-encoded JSON blob in the `SFT_TRAINER_CONFIG_JSON_ENV_VAR` environment variable, or a JSON file at `SFT_TRAINER_CONFIG_JSON_PATH`. In RHOAI, the training-operator typically injects configuration through the environment variable path.
- **Model loading:** The pipeline loads a pre-trained model and tokenizer from HuggingFace Hub (or a local path) via `AutoModelForCausalLM.from_pretrained()` or `AutoModelForVision2Seq.from_pretrained()` for multimodal models. Authentication to private model repositories uses the implicit HF_TOKEN environment variable via `huggingface_hub`.
- **Data preprocessing:** Training datasets are loaded via the HuggingFace `datasets` library from local files or remote sources. The data preprocessing pipeline supports multiple formats: pretokenized data, single-sequence with response templates, chat datasets with instruction/response templates, vision/multimodal datasets, and a default input/output format. Processed data passes through configurable data handlers and collators.
- **Training execution:** The SFTTrainer (or SumLossSFTTrainer for reduce-loss-sum mode) executes the training loop with optional fms-acceleration plugins for hardware optimization. PEFT adapters (LoRA, aLoRA, prompt tuning) or full parameter tuning are applied based on configuration.
- **Metric tracking:** During training, metrics and experiment metadata are exported to configured tracker services (MLflow, Aim, ClearML, or file-based logging) via the pluggable tracker subsystem. Each tracker reports run URIs/hashes for linking back to experiment dashboards.
- **Model output:** The fine-tuned model and tokenizer are saved to disk at the configured output directory. For LoRA adapters, additional metadata (added_tokens_info.json) is written alongside the model artifacts.

## Architectural Analysis

fms-hf-tuning follows a **layered library + container image** architecture pattern. The `tuning/` package provides the core Python library (installable via pip), while `build/accelerate_launch.py` provides the container entry point that wraps the library for Kubernetes deployment. This separation allows the library to be used standalone (e.g., in notebooks or development environments) while the container image adds GPU drivers, acceleration plugins, and operational configuration for production training jobs.

The **data preprocessing pipeline** is one of the most architecturally significant subsystems. It implements a flexible chain of `DataHandler` operations (map, filter, remove, select, rename) that process datasets through configurable pipelines defined in YAML/JSON config files (`DataConfig`). The pipeline supports five data formats: pretokenized data, single-sequence with Jinja templates, chat-format with instruction/response templates, vision-language multimodal data, and default input/output column format. This extensibility allows the same tuning image to handle diverse training data without code changes. The use of Jinja2 sandboxed templates (`SandboxedEnvironment`) for data formatting is a security-conscious design choice that prevents template injection attacks.

The **trainer controller framework** (`tuning/trainercontroller/`) implements a rule-based control system for the training loop. Users define metrics, operations, and controller rules in YAML configuration files. Rules are evaluated using `simpleeval` (a restricted expression evaluator) at specific trainer events (step end, epoch end, etc.), enabling custom stopping criteria, dynamic logging, and other loop controls without modifying code. The framework validates rules to prevent import attempts (`__` pattern rejection) and uses `EvalWithCompoundTypes` for safe evaluation. This is architecturally interesting because it provides a declarative way to express training policies.

The **acceleration framework integration** (`tuning/config/acceleration_configs/`) acts as a bridge to the separate `fms-acceleration` package ecosystem. It converts CLI arguments into a YAML configuration that the `AccelerationFramework` consumes, supporting plugins for quantized LoRA (AutoGPTQ, BitsAndBytes), fused operations/kernels, padding-free attention, ScatterMoE parallel training, and online data mixing (ODM). The annotation-based configuration system (`ConfigAnnotation` dataclass) elegantly maps CLI arguments to acceleration framework YAML paths, with standalone conflict detection to prevent incompatible plugin combinations.

A notable security improvement was the recent removal of unsafe pickle deserialization in the `txt_to_obj` function (commit b837608, CVE CWE-502), replacing it with JSON-only parsing via `base64.b64decode` + `json.loads`. The original code path could have allowed arbitrary code execution if an attacker could control the `SFT_TRAINER_CONFIG_JSON_ENV_VAR` environment variable.

The **Dockerfile build strategy** uses a multi-stage build with four stages: `base` (UBI9 + Python), `cuda-base` (adds CUDA runtime), `cuda-devel` (adds CUDA development tools + cuDNN + NCCL), and `python-installations` (builds/installs all Python packages). The final `release` stage is based on `release-base` which strips Python and dnf from the base image to minimize CVE surface. This is an aggressive hardening approach -- the Python runtime in the release image comes entirely from the pip user install (`/home/tuning/.local/`), not from the system Python that was used during build. The `PYTHONPATH` environment variable points to this user-local installation.

## Architectural Analysis

fms-hf-tuning is architecturally a batch-execution CLI tool rather than a long-running service. It has no inbound network surface — no HTTP endpoints, no gRPC services, no Kubernetes Services — which is appropriate for its role as a training job entry point. The tool is designed to run inside a container (typically a PyTorchJob pod managed by training-operator) where it executes a single training run and exits. This batch-job pattern means that network security concerns are limited to outbound connections rather than ingress protection.

The tracker subsystem demonstrates a clean plugin architecture: `tracker_factory.py` maintains a registry of available trackers (Aim, MLflow, ClearML, file_logger, hf_resource_scanner) with lazy registration on first use. Each tracker wraps the corresponding HuggingFace `TrainerCallback` and extends it with run URI/hash export functionality. The factory pattern allows optional tracker dependencies — if `aim` or `mlflow` packages are not installed, the tracker is simply not registered rather than causing an import error. This design supports the varying tracker requirements across deployment environments.

The fms-acceleration integration is tightly coupled to the training pipeline. The `AccelerationFrameworkConfig` is constructed from multiple optional config dataclasses (fast_moe, attention_and_distributed_packing, quantized_lora, fusedops_kernels, odm) and produces a framework object that can modify model loading (`requires_custom_loading`), augment the model before training (`requires_augmentation`), and inject additional trainer callbacks. The ODM (Online Data Mixing) plugin is particularly notable — it wraps the training dataset in an `OnlineMixingDataset` that dynamically adjusts dataset sampling weights during training based on reward signals.

Configuration handling uses two parallel paths: command-line arguments via HuggingFace's `HfArgumentParser` and JSON configuration via environment variables (`SFT_TRAINER_CONFIG_JSON_ENV_VAR` for base64-encoded JSON, `SFT_TRAINER_CONFIG_JSON_PATH` for file paths). The JSON path supports both JSON-decoded and Python pickle-decoded payloads in `txt_to_obj()`, which is a potential deserialization risk if the config source is untrusted. Error handling writes structured termination logs via `write_termination_log()` to communicate failure reasons back to the orchestrating training-operator, distinguishing between user errors (bad input) and internal errors (OOM, unexpected exceptions) via distinct exit codes.
