## Purpose

**Short**: Python library and container image for fine-tuning large language models using Hugging Face SFTTrainer with PyTorch FSDP, designed to run as batch GPU workloads on Kubernetes via Kubeflow Training Operator.

**Detailed**: fms-hf-tuning is a Foundation Model Stack (FMS) component that provides supervised fine-tuning (SFT) capabilities for large language models. It wraps Hugging Face's `SFTTrainer` and `transformers` libraries with an opinionated configuration layer, data preprocessing pipeline, and container image suitable for deployment as Kubernetes batch jobs via the Kubeflow Training Operator (`PyTorchJob`).

The library supports multiple tuning techniques including full fine-tuning, LoRA (Low-Rank Adaptation), activated LoRA (aLoRA), prompt tuning, and GPTQ-LoRA. It provides a pluggable acceleration framework (`fms-acceleration`) for optimizations like quantized LoRA (QLoRA), fused operations, padding-free attention, ScatterMoE, and online data mixing. Training can be distributed across multiple GPUs using PyTorch FSDP.

The container image is built on UBI 9 with CUDA 12.1 and is designed to be launched as a `PyTorchJob` workload. Configuration is passed via JSON files or base64-encoded environment variables (`SFT_TRAINER_CONFIG_JSON_PATH` or `SFT_TRAINER_CONFIG_JSON_ENV_VAR`). The entry point (`accelerate_launch.py`) wraps `accelerate launch` to automatically configure multi-GPU settings and invoke `tuning.sft_trainer` as the training module. An alternative NVIDIA NGC-based image (`nvcr.Dockerfile`) provides a variant optimized for NVIDIA environments.

## Architectural Analysis

The fms-hf-tuning library follows a clean layered architecture with clear separation between configuration, data preprocessing, training, and experiment tracking concerns. The entry point (`accelerate_launch.py`) acts as a thin orchestration layer that parses JSON configuration from files or environment variables, constructs `accelerate launch` arguments, and delegates to HuggingFace's `accelerate` CLI which spawns `tuning.sft_trainer` as the training module. This two-stage launch pattern (accelerate -> sft_trainer) is well-suited for Kubernetes deployments where configuration is injected via ConfigMaps.

The data preprocessing pipeline (`tuning.data`) is notably sophisticated. It supports five data formats: pretokenized, single-sequence with templates, chat-style with instruction/response templates, vision multimodal, and a default input/output masking format. The `DataHandler` abstraction provides a plugin system for data transformations (map, filter, remove, select, rename operations) that can be composed via YAML configuration files. The use of Jinja2 sandboxed templates for data formatting provides flexibility while maintaining security against template injection. Vision model support was recently added, with auto-detection of conversation columns and image token validation.

The acceleration framework integration (`tuning.config.acceleration_configs`) is implemented as a bridge pattern that converts user-facing dataclass configurations into the `fms-acceleration` YAML format. This design allows the acceleration framework to be completely optional — when `fms-acceleration` is not installed, the config layer gracefully degrades. The supported accelerations (QLoRA via AutoGPTQ or BitsAndBytes, fused LoRA operations, padding-free attention, multipack, ScatterMoE, and online data mixing) are each represented as standalone dataclasses with validation constraints (e.g., fused_lora requires a quantized base, multipack requires padding_free).

The trainer controller framework (`tuning.trainercontroller`) implements a rule engine that evaluates user-defined expressions (via `simpleeval`) against training metrics at configurable trainer events. This enables early stopping based on complex conditions like "loss increasing for last N steps" or "evaluation metric below threshold for M epochs." The framework uses YAML configuration files and supports pluggable metric handlers and operations, making it extensible without code changes. The architecture decisions are well-documented in `architecture_records/001-trainer-controller-framework.md`.

A notable security-relevant pattern is the error handling system: the code distinguishes between user errors (exit code 1) and internal errors (exit code 203), writing structured error messages to `/dev/termination-log` which Kubernetes surfaces in pod status. This is critical for the Kubeflow Training Operator to properly report job failures. The `txt_to_obj` function that was recently patched (commit b837608) previously used `pickle.loads()` for deserialization, which was a CVE (CWE-502) — it now uses only `json.loads()` after base64 decoding, eliminating the deserialization vulnerability.
