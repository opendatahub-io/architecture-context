## Purpose

**Short**: Caikit-NLP is a Python library providing Natural Language Processing (NLP) capabilities (text generation, embeddings, reranking, classification) built on top of the Caikit AI framework, designed to run as a model-serving runtime in Red Hat OpenShift AI.

**Detailed**: Caikit-NLP implements the Caikit framework's "task" and "module" abstractions to provide a pluggable NLP service layer. It wraps HuggingFace Transformers, PEFT (Parameter Efficient Fine-Tuning), and Sentence Transformers models behind a uniform gRPC and HTTP API surface. Modules support both local inference (loading models directly into GPU/CPU memory) and remote inference via TGIS (Text Generation Inference Server) over gRPC.

The library is deployed as a container image (`quay.io/modh/caikit-nlp`) within RHOAI's model-serving stack. When running as a service, the Caikit runtime auto-generates gRPC and HTTP endpoints from decorated Python task methods, exposing text generation, embedding, reranking, sentence similarity, sequence classification, token classification, and tokenization capabilities. The runtime supports multi-process deployment with a gRPC backend server and a REST gateway proxy, managed by `tini` as a process supervisor.

Caikit-NLP also provides training capabilities including prompt tuning (learning soft prompts without modifying base model weights), multi-task prompt tuning, and full fine-tuning with distributed training support via PyTorch FSDP and elastic launch. Trained prompt artifacts can be cached in TGIS for efficient multi-tenant inference where N prompt adapters share a single base model.

## Architectural Analysis

Caikit-NLP follows a modular architecture pattern centered around the Caikit framework's module abstraction. Each NLP capability (text generation, embeddings, reranking, classification) is implemented as a separate Caikit module with a unique UUID, registered via the `@module` decorator. This design enables the runtime to auto-discover capabilities and auto-generate gRPC service definitions and HTTP endpoints without explicit route configuration. The task method decorators (`@TextGenerationTask.taskmethod()`, `@EmbeddingTask.taskmethod()`) define the API contract, including streaming support via `output_streaming=True`.

The dual-path inference architecture is a notable design decision. Every text generation capability has both a local variant (e.g., `TextGeneration`) and a TGIS remote variant (e.g., `TextGenerationTGIS`). The remote variants use the `backend_type=TGISBackend.backend_type` registration to indicate they delegate inference to an external TGIS gRPC server. The `TGISAutoFinder` model finder enables automatic routing — when a model ID is requested, it probes the TGIS server for connectivity, and if successful, routes inference through the TGIS backend rather than loading the model locally. This supports the multi-tenant model serving pattern where one large base model in TGIS serves multiple prompt-tuned variants, each loaded as lightweight prompt vectors.

The embedding subsystem (`EmbeddingModule`) demonstrates several production optimization patterns: optional Intel IPEX acceleration, PyTorch 2.0 `torch.compile()` support, autocast mixed precision, and per-thread tokenizer caching to avoid Rust-level borrow conflicts in the tokenizers library. The `SentenceTransformerWithTruncate` wrapper adds controlled truncation with token counting, which is critical for production deployments where input sizes vary unpredictably. The retry logic around thread contention is a pragmatic concession to the sentence-transformers library's threading model.

The training architecture supports both parameter-efficient methods (prompt tuning, multi-task prompt tuning via PEFT) and full fine-tuning. Distributed training uses PyTorch's elastic launch with configurable master address/port and automatic GPU detection. The prompt tuning approach is architecturally significant because it produces small prompt vector artifacts (`.pt` files) rather than full model checkpoints, enabling the N-prompts-to-1-model serving pattern through TGIS's prompt caching mechanism.

A notable gap in the current build infrastructure is the absence of AIPCC base images in the Dockerfile.konflux. The image uses `ubi9/ubi-minimal` and installs Python packages via `pip install` of the built wheel, which pulls in PyTorch, Transformers, and other ML dependencies from public PyPI without the supply chain controls that AIPCC base images provide (pre-configured RHEL AI PyPI, vendor RPM repos, accelerator-specific builds). This represents a supply chain risk for the productized RHOAI offering and should be addressed by migrating to AIPCC base images.
