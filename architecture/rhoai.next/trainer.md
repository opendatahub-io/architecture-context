## Purpose

**Short**: Kubeflow Trainer is a Kubernetes operator that manages distributed ML training jobs by orchestrating JobSets based on user-defined TrainJob resources and reusable TrainingRuntime templates.

**Detailed**: Kubeflow Trainer (v2) is the next-generation training operator from the Kubeflow project. It introduces a declarative API built around three CRDs — `TrainJob`, `TrainingRuntime`, and `ClusterTrainingRuntime` — in the `trainer.kubeflow.org` API group. Users create a `TrainJob` that references a runtime template, and the operator builds and manages the underlying `JobSet` (from the `jobset.x-k8s.io` API) to orchestrate distributed training across multiple pods.

The operator supports multiple ML frameworks through a plugin-based runtime framework: PyTorch (torchrun), MPI (OpenMPI), TorchTune, and DeepSpeed. It integrates with gang-scheduling systems (Kubernetes scheduler-plugins coscheduling and Volcano) and supports elastic training with HPA-based auto-scaling for PyTorch.

In the RHOAI distribution, the operator includes downstream-specific features under the `pkg/rhai/` package: **progression tracking** (polls training pods for real-time metrics via HTTP and stores progress in TrainJob annotations) and **NetworkPolicy creation** (creates per-TrainJob NetworkPolicies restricting ingress to same-job pods and allowing controller access to metrics endpoints). The RHOAI overlay also ships pre-built `ClusterTrainingRuntime` resources for various accelerator/framework combinations (CUDA, ROCm, CPU) with pinned container images, plus OpenShift ImageStream resources for Training Hub universal workbench images.

## Architectural Analysis

The Kubeflow Trainer v2 represents a significant architectural evolution from the v1 Training Operator. The v1 operator managed framework-specific CRDs (PyTorchJob, MPIJob, TFJob, etc.) with separate controllers per framework. The v2 architecture consolidates around three generic CRDs (`TrainJob`, `TrainingRuntime`, `ClusterTrainingRuntime`) and delegates workload orchestration to `JobSet`, which handles the complexity of multi-pod job lifecycle management. This separation of concerns means the trainer controller only needs to build the correct JobSet specification from the runtime template and user overrides.

The runtime framework uses a plugin architecture (`pkg/runtime/framework/`) where each ML framework (PyTorch/torchrun, MPI, TorchTune, DeepSpeed) and infrastructure integration (JobSet, coscheduling, Volcano) is implemented as a plugin that satisfies well-defined interfaces (`ComponentBuilderPlugin`, `PodNetworkPlugin`, `WatchExtensionPlugin`, `CustomValidationPlugin`). Plugins compose through a core framework (`pkg/runtime/framework/core/framework.go`) that orchestrates plugin execution in a pipeline. This is a clean design that allows adding new frameworks without modifying the core controller logic.

The RHAI (Red Hat AI) extensions under `pkg/rhai/` add two significant downstream features. **Progression tracking** implements an active polling model — the controller makes HTTP GET requests to training pod metrics endpoints to collect real-time progress data (percent complete, steps, epochs, estimated time remaining) and stores it as a JSON annotation on the TrainJob. This is architecturally notable because controllers rarely make outbound HTTP calls to workload pods; the design uses the `APIReader` (direct API reads, no informer cache) to avoid setting up pod watches, which is a deliberate performance trade-off. The polling interval is configurable via annotation (default 30s, range 5-300s). **NetworkPolicy management** creates per-TrainJob NetworkPolicies that restrict ingress to same-job pods (for NCCL/MPI/gRPC inter-node communication) and optionally allow controller-to-pod access on the metrics port. This is defense-in-depth for multi-tenant clusters.

The TLS implementation (`pkg/tls/tls.go`) is particularly well-designed for the OpenShift ecosystem. Rather than hardcoding cipher suites, it dynamically reads the cluster's TLS security profile from the `config.openshift.io/v1 APIServer` resource using a dynamic client (avoiding an import dependency on `openshift/api`). It supports all four profile types (Intermediate, Modern, Old, Custom) and falls back to a hardened Intermediate profile if the API is unavailable. This ensures the operator respects cluster-wide TLS policy while degrading gracefully on non-OpenShift clusters. The cert-controller from `open-policy-agent/cert-controller` manages webhook certificate rotation without requiring cert-manager.

The RHOAI kustomize overlay is extensive — it configures 15 ClusterTrainingRuntime variants covering CUDA 12.8/13.0, ROCm 6.4, and CPU for both legacy torch-distributed and newer Training Hub runtimes. Images are pinned by SHA256 digest in `params.env` and injected via kustomize replacements. The overlay also creates OpenShift ImageStreams for Training Hub universal workbench images across two product versions (3.4 and 3.5), enabling version-tracked image management through the OpenShift image registry. The RHOAI overlay removes the upstream metrics port (8080) and replaces it with secure metrics on 8443, consistent with the RHOAI security posture.
