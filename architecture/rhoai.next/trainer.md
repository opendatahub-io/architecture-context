## Purpose

**Short**: Kubernetes operator that manages distributed ML training jobs on OpenShift, supporting PyTorch, MPI, and TorchTune workloads via a declarative TrainJob/TrainingRuntime API.

**Detailed**: The Kubeflow Trainer (formerly Kubeflow Training Operator v2) is a controller-runtime-based Kubernetes operator that orchestrates distributed machine learning training workloads. It introduces a two-level API: users create `TrainJob` CRs that reference `TrainingRuntime` or `ClusterTrainingRuntime` templates, and the operator reconciles these into concrete `JobSet` resources with the appropriate distributed training configuration.

The operator implements a plugin-based runtime framework supporting multiple ML frameworks (PyTorch/torchrun, TorchTune fine-tuning, MPI/OpenMPI) and multiple gang-scheduling backends (scheduler-plugins CoScheduling, Volcano). Each plugin enforces framework-specific policies: environment variable injection (PET_NNODES, PET_MASTER_ADDR for PyTorch), SSH key generation and hostfile management for MPI, and recipe/config selection for TorchTune fine-tuning.

In the RHOAI distribution, the operator includes Red Hat-specific extensions (pkg/rhai/) for progression tracking — HTTP polling of training pod metrics endpoints to capture real-time training progress — and NetworkPolicy management for metrics endpoint security. The RHOAI overlay also deploys pre-configured ClusterTrainingRuntimes with pinned container images for CUDA, ROCm, and CPU training environments, along with OpenShift ImageStreams for training hub workbench images.

## Architectural Analysis

The Kubeflow Trainer implements a sophisticated plugin-based architecture that cleanly separates concerns across ML framework-specific behavior, scheduling policies, and platform extensions. The core abstraction is the `Runtime` interface (`pkg/runtime/interface.go`), which exposes five methods for object creation, runtime info construction, status computation, event handler registration, and validation. Two runtime implementations — `TrainingRuntime` (namespaced) and `ClusterTrainingRuntime` (cluster-scoped) — share a singleton factory via a delegation pattern, eliminating code duplication.

The runtime framework (`pkg/runtime/framework/`) orchestrates seven plugin interfaces: `EnforceMLPolicyPlugin`, `EnforcePodGroupPolicyPlugin`, `PodNetworkPlugin`, `ComponentBuilderPlugin`, `TrainJobStatusPlugin`, `CustomValidationPlugin`, and `WatchExtensionPlugin`. Six concrete plugins (coscheduling, volcano, mpi, plainml, torch, jobset) are registered at startup. This design allows new ML frameworks or scheduling backends to be added without modifying controller code. The JobSet plugin is the foundation — all other plugins layer on top by modifying the `Info` structure before the JobSet plugin builds the final `JobSet` apply configuration.

The RHOAI-specific extensions (`pkg/rhai/`) represent a clean downstream fork pattern. The `progression` package implements a full metrics polling lifecycle: pod discovery via multiple label strategies (supporting both v2 JobSet labels and v1 legacy training-operator labels), HTTP metrics polling with JSON sanitization (handling Python's non-standard NaN/Infinity), three-tier final status capture (termination message → HTTP poll → existing annotation), and configurable poll intervals with bounds enforcement (5s-300s). The `networkpolicy` package creates per-TrainJob NetworkPolicies with two rules: unrestricted intra-job communication (required for NCCL/MPI/gRPC) and controller-only metrics access (restricted by pod labels and namespace selector). These RHOAI features are gated behind the `ENABLE_RHAI_FEATURES` environment variable and the `trainer.opendatahub.io/progression-tracking` annotation per TrainJob.

The TLS architecture demonstrates strong security posture. The controller reads the cluster-wide TLS security profile from the OpenShift APIServer (`config.openshift.io/v1/apiservers`) and applies it to both the webhook server and metrics endpoint. The fallback Intermediate profile enforces TLS 1.2 minimum with six modern ECDHE cipher suites. This integration means the operator automatically inherits cluster-level TLS hardening without manual configuration. The MPI SSH key generation uses ECDSA with P-521 curve (FIPS-approved), and generated secrets are marked immutable to prevent tampering.

The kustomize deployment structure in `manifests/rhoai/` uses a `configMapGenerator` with `params.env` to inject image references, supporting SHA256-pinned images from `registry.redhat.io`. The overlay adds RHOAI-specific RBAC (pods get/list for progression, networkpolicies CRUD), reconfigures the metrics port from 8080 to 8443 with TLS, and deploys pre-configured ClusterTrainingRuntimes with CUDA 12.8/13.0, ROCm 6.4, and CPU training images. The ImageStreams provide OpenShift-native image management for training hub universal workbench images across RHOAI release versions (2026.1 / 2026.2).
