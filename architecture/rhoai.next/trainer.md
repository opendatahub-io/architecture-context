## Purpose

**Short**: Kubernetes operator that orchestrates distributed machine learning training workloads by mapping user-facing TrainJob resources onto JobSet-based execution through a pluggable runtime framework.

**Detailed**: Trainer (formerly Kubeflow Training Operator) is a Kubernetes controller-runtime operator that provides a declarative API for distributed ML training on OpenShift AI. Users create `TrainJob` custom resources referencing a `TrainingRuntime` or `ClusterTrainingRuntime`, and the controller resolves the runtime's plugin chain to produce a `JobSet` workload with the correct distributed training topology (PyTorch, MPI, DeepSpeed, XGBoost, MLX, JAX, Flux).

The operator implements a plugin framework (`pkg/runtime/framework`) where each training backend (torch, mpi, jobset, coscheduling, volcano) is a plugin that can customize pod templates, inject sidecars, configure init containers, and set gang-scheduling policies. Runtimes compose plugins into a pipeline that transforms a TrainJob into concrete Kubernetes workloads. The controller also manages `OptimizationJob` resources that orchestrate hyperparameter tuning through Katib integration, spawning subordinate TrainJobs as trials.

An optional status server (`pkg/statusserver`), gated behind the `TrainJobStatus` alpha feature flag, provides an HTTPS endpoint for training pods to push runtime metrics and progress updates back to the controller. This endpoint uses projected service account tokens with OIDC verification for per-TrainJob authentication, ensuring that only pods belonging to a specific TrainJob can update its status.

## Architectural Analysis

The trainer controller follows the standard controller-runtime operator pattern but distinguishes itself with a composable runtime plugin framework. Rather than hard-coding behavior for each ML framework, the controller resolves a `TrainingRuntime` into an ordered chain of plugins -- each implementing well-defined extension points (EnforceMLPolicy, EnforcePodGroupPolicy, CustomValidation, etc.) -- that collaboratively build the final JobSet specification. This design enables adding new training backends (e.g., JAX, Flux) without modifying the core controller logic.

The RHOAI distribution adds several security hardening layers on top of the upstream Kubeflow project. TLS configuration is resolved from the OpenShift cluster's `TLSSecurityProfile` via `openshift/controller-runtime-common`, with a watcher that triggers controller restart when the profile or adherence policy changes. All three server surfaces -- metrics (`:8443`), webhook (`:9443`), and status server (`:10443`) -- use the same resolved TLS configuration. HTTP/2 is disabled by default across all servers to mitigate the Rapid Reset CVEs (CVE-2023-44487, CVE-2023-39325), falling back to HTTP/1.1.

The RHOAI overlay also adds NetworkPolicies restricting ingress to specific ports and source namespaces (API server for webhooks, training pods for status updates, openshift-monitoring for metrics scraping), plus egress is unrestricted to allow Kubernetes API access. RBAC includes tiered user-facing roles (training-view, training-edit, training-admin) aggregated via Kubernetes role aggregation, giving platform admins fine-grained control over who can view, create, or fully manage training resources.

Certificate management uses `open-policy-agent/cert-controller` to rotate webhook serving certificates, writing them to a shared cert directory consumed by the webhook, metrics, and status servers. The controller's readiness probe gates on webhook server readiness, ensuring no traffic is accepted before certificates are available.

The progression tracking subsystem (`pkg/rhai/progression`) is an RHOAI-specific addition that polls training pods for training loss metrics and progress percentage, enabling the RHOAI dashboard to display real-time training progress. This requires additional RBAC permissions to list pods and read secrets in user namespaces.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Tiered RBAC (training-view, training-edit, training-admin ClusterRoles); status server OIDC token validation with namespace binding | Kubernetes RBAC + Application (OIDC) | ClusterTrainingRuntime is cluster-scoped and shared across tenants; any tenant can reference any ClusterTrainingRuntime |
| Data storage | Per-namespace TrainJob resources; init container data downloaded to pod-local PVCs | Kubernetes namespace isolation | No cross-namespace data sharing by controller; data isolation depends on storage backend configuration |
| Network traffic | NetworkPolicy restricts ingress to controller pod; training pod network isolation delegated to platform | Kubernetes NetworkPolicy | Controller egress is unrestricted; tenant workload network isolation not enforced by this component |
| Compute & resources | Delegated to platform (Kueue, ResourceQuotas) | External | Controller does not enforce per-tenant compute limits; relies on external quota/scheduling systems |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; webhook cert shared only within controller namespace | Kubernetes namespace isolation | Controller ConfigMap (kubeflow-trainer-config) and public ConfigMap are in opendatahub namespace, read-only to all authenticated users |
