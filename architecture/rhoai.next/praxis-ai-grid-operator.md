## Purpose

**Short**: Distributed control plane operator that orchestrates multi-site AI inference routing across Kubernetes clusters, cloud providers, and third-party APIs by forming a peer-to-peer mesh, propagating provider state, and writing routing overlays for Praxis gateways.

**Detailed**: The AI Grid Network (AGN) operator (`grid-operator`) is a Rust-based Kubernetes controller that connects inference backends into a single routable mesh across sites. It manages four cluster-scoped CRDs—`GridNetwork`, `GridSite`, `InferenceProvider`, and `AgentToolProvider`—to define the mesh topology, peer sites, model-serving backends, and agentic tool endpoints respectively. The operator is an orchestrator, not a proxy: it discovers peers via the SWIM gossip protocol (through `foca`), propagates provider capabilities and health state with delta CRDTs, scores candidates using configurable strategies (`noMetrics`, `queueDepth`, `kvCachePressure`), and writes versioned routing overlay ConfigMaps that the Praxis AI gateway hot-reloads at request time.

The repository is organized as a Rust workspace containing 13 crates, compiled into three deployable binaries: the main `operator` (controllers, SWIM runtime, scoring, overlay rendering, metrics), an `enrollment` service (mTLS site-token onboarding backed by PostgreSQL), and a `grid-gateway` (Praxis-based data-plane gateway for inter-site traffic). Trust between sites is established via mTLS certificates managed through the enrollment workflow, with support for both the `rcgen`-based default path and an OpenSSL-based FIPS path via mutually exclusive Cargo features. The SWIM gossip layer uses AES-256-GCM encryption for all inter-site control-plane traffic.

## Architectural Analysis

AGN's architecture cleanly separates the control plane (what should be routable) from the data plane (actual request routing). The operator runs a reconciliation loop for each CRD kind alongside a live SWIM UDP runtime for peer-to-peer membership. The design is fundamentally distributed: each site runs its own operator instance that independently discovers peers, receives CRDT state deltas, scores providers, and renders a local overlay ConfigMap—there is no centralized coordinator. This makes the system resilient to partition but introduces eventual-consistency semantics for routing decisions.

The scoring engine deserves attention: it runs a single provider-level strategy per `GridNetwork`, not a per-request scoring model. The supported strategies (`noMetrics`, `queueDepth`, `kvCachePressure`) are intentionally constrained to signals the operator can collect from diverse backends (self-hosted llm-d pools, cloud APIs like Bedrock/Vertex/Anthropic/OpenAI). Request-level selection (e.g., prefix affinity) is delegated to the inference backend's own endpoint picker (llm-d EPP), keeping AGN's routing overlay coarse-grained and hot-reloadable.

The Recreate deployment strategy for the operator is architecturally significant: SWIM binds one identity per site, so a rolling update with two pods would gossip conflicting identities. The revision-lease mechanism (ConfigMap-backed CAS for SWIM transport revisions) ensures revision uniqueness across process restarts without coordination.

The FIPS/non-FIPS duality is implemented through mutually exclusive Cargo features (`tls-rustls` vs `fips`) that switch the entire TLS stack—`rustls` with `ring` for the default path, `openssl` for FIPS—with a compile-time error if both are selected. This is a cleaner model than runtime detection but means two distinct binaries for the two compliance postures. The current Konflux Dockerfiles build the default (rustls/ring) path; a FIPS build would require `--no-default-features --features fips` and an OpenSSL-linked base image.

The enrollment service is architecturally isolated as a separate binary and Dockerfile, with its own TLS and authorization path (Kubernetes TokenReview + SubjectAccessReview via the `sar` feature). It uses PostgreSQL (via `sqlx`) for durable token and enrollment state, which is notable as the only stateful database dependency in the entire AGN system.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | mTLS certificates per site; enrollment service gates site onboarding via single-use tokens with RBAC authorization | Application (enrollment) + TLS | No RBAC enforcement on CRDs themselves beyond Kubernetes native RBAC |
| Data storage | Per-site overlay ConfigMaps; enrollment uses PostgreSQL with per-site records | Application | Shared PostgreSQL for enrollment; row-level isolation, not schema-per-tenant |
| Network traffic | mTLS for all inter-site control-plane (signals) and data-plane (gateway) traffic; AES-256-GCM for SWIM gossip | Application (TLS/crypto) | No NetworkPolicy manifests in the repo; relies on cluster-level network policies |
| Compute & resources | Single operator pod per site; no ResourceQuota or LimitRange in manifests | Kubernetes (namespace) | No explicit resource limits in deployment manifest |
| Configuration & secrets | Per-site TLS secrets; per-provider credential secrets; SWIM key from GridNetwork.spec.tls.swimKeyRef | Kubernetes (Secret RBAC) | Operator has broad Secret get/create/patch permission in its namespace |
| API scoping | Cluster-wide CRD watches; provider access policy via `accessPolicy.siteSelector.matchLabels` | Application | InferenceProvider and AgentToolProvider use label-based access policy to restrict which sites can consume a provider |
