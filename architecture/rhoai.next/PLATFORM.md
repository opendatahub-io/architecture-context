## Platform Overview

Red Hat OpenShift AI (RHOAI) is a comprehensive AI/ML platform deployed on OpenShift Container Platform that provides end-to-end capabilities for model training, serving, monitoring, and lifecycle management. The platform is delivered as an OLM-managed operator (`rhods-operator`) that orchestrates 87 components spanning model serving infrastructure (KServe, vLLM, ModelMesh), distributed training (Training Operator, Kubeflow Trainer, KubeRay), data science workflows (notebooks, pipelines, feature stores), model governance (TrustyAI, guardrails), and a multi-tenant AI gateway (Models as a Service). The platform also includes emerging GenAI capabilities: LLM-specific inference routing (llm-d), agent orchestration (OGX/Llama Stack), and MCP lifecycle management.

The deployment model follows a three-tier operator hierarchy. The top-level `rhods-operator` creates cluster-scoped `DataScienceCluster` and `DSCInitialization` CRDs, which in turn generate per-component CRs (Dashboard, KServe, Kueue, etc.) and per-service CRs (Auth, GatewayConfig, Monitoring). Each component has its own dedicated controller — either embedded in the operator binary (14 component controllers) or deployed as separate module operator pods (AIGateway, MLflow, MCPLifecycle). A DAG-based provisioning system assigns components to runlevels (20–33) to ensure dependency ordering. The platform gateway (`data-science-gateway`) implements a multi-layer ingress stack: GatewayClass → Gateway → Envoy proxy → EnvoyFilter (ext_authz + Lua) → kube-auth-proxy (OAuth2) → backend applications, supporting both OpenShift Route and LoadBalancer ingress modes.

The security posture is defense-in-depth: kube-rbac-proxy sidecars enforce SubjectAccessReview authorization on metrics and API endpoints; the platform gateway handles OAuth2/OIDC authentication; NetworkPolicies restrict inter-component communication; 70% of container images run as non-root on UBI base images; and the MaaS gateway implements tenant-scoped API key authentication with SHA-256 hashing and Kuadrant AuthPolicy/TokenRateLimitPolicy enforcement. TLS is pervasive — the operator reads the cluster-wide TLS security profile from `apiservers.config.openshift.io/cluster` and propagates it to webhook servers and metrics endpoints.

### Central Components

**KServe** (17 reverse dependencies) is the gravitational center of the platform. Nearly every serving-related component — Model Registry, TrustyAI, odh-model-controller, MaaS, OGX, vLLM variants, and the dashboard — depends on KServe's InferenceService CRD for model deployment and serving. KServe's LLMInferenceService API is the primary entrypoint for LLM workloads, integrating with Gateway API Inference Extension for intelligent routing.

**rhods-operator** (15 reverse dependencies) is the platform control plane. All component and module operators depend on it for lifecycle management — it creates the CRs that trigger component deployment, manages the shared ingress gateway, and coordinates versioned upgrade handshakes with module operators.

**Kueue** (8 reverse dependencies) provides the shared job scheduling fabric. Training Operator, Kubeflow Trainer, TrustyAI (LMEvalJob), Spark, and the dashboard all submit workloads through Kueue's ClusterQueue/LocalQueue admission system.

**kube-rbac-proxy** (8 reverse dependencies) is the platform's standard authentication sidecar, used by KubeRay, odh-dashboard, KServe, TrustyAI, and multiple operators for metrics endpoint protection and SubjectAccessReview-based authorization.

**Model Registry** (5 reverse dependencies) serves as the shared model metadata store consumed by KServe, the dashboard, RHOAI MCP Server, and the eval-hub for model discovery and lifecycle tracking.

## Deployment Architecture

### Deployment Topology

The platform deploys across four namespace tiers. The **operator namespace** (`redhat-ods-operator`) hosts the platform operator and module operator pods (AIGateway, MLflow, MCPLifecycle). The **platform namespace** (`redhat-ods-applications`) hosts shared platform services: the dashboard (up to 10 containers per pod in sidecar mode), KServe controllers, odh-model-controller, monitoring stack (Prometheus, Tempo, Perses, OTel collectors), and the platform gateway (Envoy, kube-auth-proxy). #### Manifest Consumption Pipeline

Component manifests flow through a multi-stage pipeline. Upstream repositories are forked to `red-hat-data-services` or `opendatahub-io` organizations. A `get_all_manifests.sh` script (or per-component `get-manifests.sh`) fetches manifests at pinned commit SHAs into the operator repository. During operator image build, these manifests are embedded into the container image. At runtime, the operator applies kustomize rendering with distribution-specific overlays and substitutes `RELATED_IMAGE_*` environment variables (populated from the OLM CSV `relatedImages` section) to replace image tags with digest-pinned references. This pipeline ensures reproducible, disconnected-capable builds where every image reference is a content-addressable digest.

### Disconnected Support

The platform provides comprehensive air-gapped deployment support through the `RELATED_IMAGE` pattern. All container image references in operator CSVs use the `relatedImages` section, which OLM resolves to content-addressable digests. The `oc-mirror` tool can mirror the complete image set to a disconnected registry. Operators substitute `RELATED_IMAGE_*` environment variables into kustomize manifests at deploy time, ensuring no external registry pulls are needed at runtime. The manifest vendoring approach (pinned SHA fetches at build time) ensures operator images are self-contained. The `odh-deployer` component specifically handles bootstrapping in disconnected environments by extracting embedded manifests rather than fetching from remote repositories.

## Platform Architectural Analysis

RHOAI's architecture reveals several cross-cutting patterns and tensions that emerge only when viewing all 87 components together.

**The CRD explosion is the platform's defining architectural characteristic.** With 175 CRDs across 41 API groups, RHOAI has one of the highest CRD densities of any Kubernetes platform. The three-tier operator hierarchy (DSC → Component CR → workload CRDs) provides clean lifecycle management but creates a deep API surface that operators must understand. The `components.platform.opendatahub.io` group alone defines 22 component CRDs, each triggering a dedicated controller. This design trades API surface area for operational clarity — each component's state is independently observable and manageable — but increases the cluster's API server load and etcd storage requirements.

**Authentication is the platform's most fragmented domain.** Seven distinct authentication mechanisms coexist: kube-rbac-proxy sidecars (metrics/API protection), OAuth2/OIDC via kube-auth-proxy (platform gateway), Kuadrant AuthPolicy (MaaS per-route policies), API key hashing (MaaS tenant access), mTLS (Istio mesh), Bearer token forwarding (BFF inter-service), and SA token isolation (dashboard pod-level). While each mechanism serves a legitimate purpose, the lack of a unified auth abstraction means security auditing requires understanding all seven patterns. The `Auth` service CR in rhods-operator provides some centralization (admin groups, allowed groups), but per-component auth decisions are made independently.

**The serving stack bifurcation reflects the platform's evolution.** Two parallel model serving architectures coexist: ModelMesh (distributed LRU cache, multi-model per pod, etcd-backed state) and KServe (one-model-per-deployment, Knative/Gateway API routing). The LLMInferenceService API in KServe represents a third generation — purpose-built for LLM workloads with disaggregated prefill/decode, KV-cache-aware routing, and multi-node LeaderWorkerSet topologies. The llm-d routing stack (Router/EPP, inference-scheduler, kv-cache, routing-sidecar, latency-predictor) adds another layer of inference-specific infrastructure. This layering is necessary for the diversity of ML workloads but creates operational complexity: operators must choose between ModelMesh (legacy), KServe InferenceService (stable), and KServe LLMInferenceService (next-gen) for each model type.

**The ext_proc pattern is emerging as the platform's primary data-plane extension mechanism.** Three independent implementations — Gateway API Inference Extension (EPP/BBR), MaaS ai-gateway-payload-processing (pre/post-auth), and the llm-d Router — all use Envoy's ext_proc filter for request interception. Each implements its own plugin architecture, scoring algorithms, and metrics scraping. While the Gateway API Inference Extension is the most mature (Filter-Score-Pick scheduler, flow control with fairness), the MaaS implementation handles different concerns (API translation, credential injection). Converging these into a shared ext_proc framework would reduce operational surface area but is constrained by their different lifecycle requirements.

**The dashboard's Module Federation architecture is both innovative and operationally risky.** Deploying up to 10 containers (shell + kube-rbac-proxy + 8 BFF modules) in a single pod provides strong feature isolation and independent deployment cadence, but creates a blast radius problem: any single container failure takes down the entire dashboard. The inter-BFF communication chain (user → kube-rbac-proxy → shell → BFF → upstream BFF) adds latency and debugging complexity. The standalone deployment mode addresses this by deploying each BFF as its own pod with targeted NetworkPolicies, but at the cost of more cluster resources.

**Monitoring is exceptionally comprehensive but heterogeneous.** The platform deploys Prometheus (via MonitoringStack), Tempo (distributed tracing), OpenTelemetry collectors (auto-instrumentation), Perses (dashboards), and Thanos (federated queries). Most components expose `/metrics` endpoints protected by kube-rbac-proxy. However, the monitoring stack deployment is atomic — all CRDs must exist before any resources are created — which means partial observability is not possible during rollout. The 808 RBAC roles across all components reflect the monitoring integration tax: every operator needs permissions for ServiceMonitors, PodMonitors, and PrometheusRules.

**The dependency on optional external operators creates a combinatorial deployment matrix.** KServe alone has 8 optional dependencies (Istio, cert-manager, Knative, KEDA, LeaderWorkerSet, Gateway API, GIE, Kuadrant). Combined with Kueue's optional Cluster Autoscaler integration, the platform's full feature set requires coordinating with 10+ external operators. The module controller's CRD dependency checking system (`crdDep()` declarations) provides graceful degradation, but the number of valid deployment configurations is large and testing coverage for edge combinations is a persistent challenge.

**Container image security is mostly consistent with notable exceptions.** 70% of Dockerfiles specify non-root execution, 38% use UBI base images, and multi-stage builds are standard practice. However, several components default to `InsecureSkipVerify=true` for internal TLS connections (MaaS DestinationRule, llm-d metrics scraping), relying on mesh mTLS for identity verification. While pragmatic for cluster-internal traffic, this creates audit findings and should be explicitly documented as a conscious security trade-off rather than an oversight.
