## Platform Overview

Red Hat OpenShift AI (RHOAI) is a comprehensive AI/ML platform deployed on OpenShift Container Platform via a single top-level operator (`rhods-operator`). The operator uses two cluster-scoped custom resources — `DataScienceCluster` (component enablement) and `DSCInitialization` (platform bootstrapping) — to declaratively manage over 120 components spanning model serving (KServe, ModelMesh, vLLM across CUDA/ROCm/Gaudi/CPU/Spyre), distributed training (Kubeflow Trainer, Training Operator), interactive development (Workbenches/Kubeflow Notebooks), ML pipelines (Data Science Pipelines with Argo Workflows), experiment tracking (MLflow), feature stores (Feast), model registry, responsible AI (TrustyAI, NeMo Guardrails), distributed inference (llm-d), multi-tenant model consumption (Models-as-a-Service), and AI agent orchestration (agents-operator, OpenShell). Components follow a modular operator pattern where the platform operator delegates lifecycle management to per-domain module operators that watch their own component CRDs.

The platform's ingress architecture is built on Kubernetes Gateway API. The rhods-operator dynamically provisions a central `data-science-gateway` Gateway in the `openshift-ingress` namespace, backed by the OpenShift Gateway API controller (Envoy-based). All platform components register HTTPRoutes against this shared gateway. Authentication is enforced at the gateway level through an EnvoyFilter that invokes `kube-auth-proxy` via ext_authz, supporting both OpenShift OAuth and OIDC identity providers. A separate `maas-default-gateway` serves the Models-as-a-Service multi-tenant layer with Kuadrant/Authorino-based API key and bearer token authentication. Legacy OpenShift Routes provide backward-compatible URL redirects to the new Gateway API endpoints.

Security is enforced through multiple layers: TLS is mandatory with configuration derived from the cluster-wide OpenShift APIServer TLS profile (defaulting to TLS 1.2 Intermediate); container images use UBI 9 base images with non-root execution; FIPS compliance is achieved through `GOEXPERIMENT=strictfipsruntime` builds with post-quantum cryptography runtime bases; and per-component RBAC with principle-of-least-privilege service accounts. The platform supports 304 admission webhooks across 25 components, providing comprehensive validation and defaulting for all CRD types.

### Central Components

- **rhods-operator**: The root of the dependency tree. Orchestrates all component lifecycles, provisions the platform Gateway and authentication infrastructure, manages RBAC propagation, and deploys monitoring resources. Every platform component directly or transitively depends on it.
- **KServe (+ odh-model-controller)**: The model serving backbone. Defines InferenceService and LLMInferenceService CRDs consumed by vLLM, MLServer, OpenVINO, caikit, and ModelMesh runtimes. Manages 27 ClusterServingRuntime definitions. The embedded odh-model-controller extends KServe with networking, RBAC, Kuadrant AuthPolicy, KEDA autoscaling, and NIM account integration.
- **Kueue**: Central job queueing system integrated with CodeFlare (AppWrapper), KubeRay (RayJob), Kubeflow (Notebooks), and Trainer (TrainJob). Manages when workloads are admitted to run based on cluster resource availability.
- **gateway-api-inference-extension**: Provides the inference-aware Endpoint Picker (EPP) for KV-cache-aware, prefix-cache-aware, and LoRA-affinity-aware routing of LLM inference requests through Envoy.
- **odh-dashboard**: The primary user interface aggregating access to all platform capabilities. Implemented as a federated micro-frontend with 12+ independent module pods, each with its own Go BFF sidecar.

### Ingress Analysis

The RHOAI ingress architecture operates on two parallel generations with a clear migration path. The current-generation path uses Kubernetes Gateway API with two shared Gateways — the central `data-science-gateway` for platform services and the capability-specific `maas-default-gateway` for multi-tenant model consumption. The legacy path uses Istio Gateways and Knative for KServe InferenceService ingress, still operational for existing deployments.

The `data-science-gateway` is the platform's primary ingress surface. Created dynamically by rhods-operator's gateway service controller, it provisions a GatewayClass (`opendatahub-gateway` backed by `openshift.io/gateway-controller/v1` on OpenShift, `istio.io/gateway-controller` on XKS), a Gateway with HTTPS listeners, and supporting infrastructure (EnvoyFilter, DestinationRule, kube-auth-proxy Deployment, HPA, NetworkPolicy). The authentication chain is source-confirmed: an EnvoyFilter inserts `envoy.filters.http.ext_authz` before the router, calling `kube-auth-proxy.openshift-ingress.svc.cluster.local:8443/oauth2/auth` to validate sessions. A companion Lua filter forwards the authenticated token as `x-forwarded-access-token` and `Authorization: Bearer` headers to backends, stripping OAuth2 proxy cookies to prevent credential leakage. This design cleanly separates gateway-level authentication from backend authorization — backends receive a pre-validated identity and apply their own RBAC (typically via kube-rbac-proxy sidecar or application-level checks).

The `maas-default-gateway` implements a distinct authentication model for multi-tenant model consumption. Rather than ext_authz/kube-auth-proxy, it uses Kuadrant AuthPolicy resources created per-tenant by the maas-controller. Authorino evaluates two authentication methods with priority-based selection: MaaS-issued API keys (validated via HTTP callback to maas-api) and OpenShift tokens (validated via Kubernetes TokenReview). On successful authentication, Authorino strips the original Authorization header and injects identity headers (`X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription`), preventing credential exfiltration to model endpoints. A known gap exists in TLS validation: the DestinationRule for maas-api backend TLS uses `insecureSkipVerify: true` because the gateway proxy does not mount the service-ca bundle (tracked as RHOAIENG-61070).

Model serving ingress follows a third path through odh-model-controller. For each InferenceService or LLMInferenceService, the controller creates either OpenShift Routes or Gateway API HTTPRoutes (depending on platform configuration) and injects a kube-rbac-proxy sidecar into model serving pods. For LLMInferenceService, it additionally creates Kuadrant AuthPolicy resources for gateway-level token validation. The llm-d distributed inference stack adds another layer: the gateway-api-inference-extension EPP runs as an Envoy ext-proc filter that performs KV-cache-aware and prefix-cache-aware endpoint selection before requests reach model serving pods.

Legacy KServe ingress through Istio Gateways (knative-ingress-gateway, knative-local-gateway, kserve-local-gateway) remains operational for backward compatibility. These Gateways are provisioned by kf-poc-rhods-operator and use Istio mTLS for inter-service authentication. The platform is actively migrating from this Istio-based path to the Gateway API path.

## Deployment Architecture

### Deployment Topology

The platform deploys across four namespace tiers. The **operator tier** (`redhat-ods-operator`) runs the platform operator with a single leader-elected pod. The **application tier** (`redhat-ods-applications`) hosts all component controllers, dashboard pods (core + 12+ federated module pods), and operator infrastructure — typically 20-30 pods. The **ingress tier** (`openshift-ingress`) contains the Gateway infrastructure: the Envoy proxy pods backing the data-science-gateway and maas-default-gateway, kube-auth-proxy pods (autoscaled via HPA), and associated EnvoyFilters and DestinationRules. The **user tier** spans multiple namespaces where data science workloads run — model serving pods, notebook/workspace pods, pipeline runs, training jobs, and feature store instances.

Components that cross namespace boundaries include: kube-auth-proxy (deployed in openshift-ingress by rhods-operator), per-tenant maas-api (deployed in tenant infrastructure namespace by maas-controller), model serving pods (deployed in user namespaces by KServe), and monitoring resources (ServiceMonitors/PodMonitors created by operators in user namespaces and scraped by the platform Prometheus instance).

### Resource Summary

- **Operators**: 25+ controller-runtime operators managing component lifecycles
- **Gateway infrastructure**: 2 Gateway CRs (data-science-gateway, maas-default-gateway), 5+ Istio Gateways (legacy), EnvoyFilter + DestinationRule per gateway
- **Webhook servers**: 25 components serving 304 total webhooks (mutating, validating, conversion)
- **Container images**: 120+ distinct container images across all components
- **CRDs**: 236 CRD definitions across all components
- **ClusterServingRuntimes**: 27 definitions (vLLM x5 accelerators x3 channels + OVMS + MLServer x2)

#### Manifest Consumption Pipeline

Component manifests flow through a multi-stage pipeline. Component repositories define kustomize bases and overlays for their resources. At build time, `manifests-config.yaml` in rhods-operator pins each component to a specific repository SHA. The `get_all_manifests.sh` script fetches manifests from pinned SHAs and bundles them into the operator container image at `/opt/manifests-template`. At runtime, the operator renders manifests using kustomize APIs with runtime variable substitution (namespace, images, feature flags) and applies them via server-side apply. Module operators follow the same pattern independently, fetching their upstream component manifests at build time and rendering them at reconciliation time.

### Disconnected Support

Disconnected (air-gapped) deployment support is not fully resolved across all components for this generation cycle. The platform operator uses the `RELATED_IMAGE_*` environment variable pattern for image references, and OLM's `relatedImages` in the ClusterServiceVersion enables image mirroring via `oc-mirror`. Container images use digest-based references where available for supply chain integrity. However, the cross-cutting evidence shows that most components have `unresolved` disconnected deployment evidence, indicating that per-component disconnected testing and validation may not be uniformly complete. The platform relies on the operator-level `RELATED_IMAGE` pattern and OpenShift's cluster-wide image mirroring (ImageContentSourcePolicy / ImageDigestMirrorSet) as the primary disconnected deployment mechanism.

## Platform Architectural Analysis

RHOAI rhoai.next exhibits several cross-cutting architectural patterns and tensions that emerge only from reading all 130 component analyses together.

**Operator composition depth.** The platform follows a three-tier operator model: rhods-operator (tier 1) deploys module operators (tier 2, e.g., feast-module-operator, ray-module-operator, kueue-operator), which deploy upstream components (tier 3, e.g., Feast, KubeRay, Kueue). This creates clear lifecycle isolation but deep dependency chains — a change to a tier-3 component requires a SHA update in the tier-2 module operator's manifest config, which must then be referenced by the tier-1 operator. The manifest rendering pipeline (get_all_manifests.sh -> embedded kustomize -> runtime rendering) provides reproducibility but makes the full resource footprint visible only through code analysis, not static manifest inspection.

**Authentication fragmentation.** The platform employs four distinct authentication mechanisms depending on the ingress path: (1) ext_authz/kube-auth-proxy for the central data-science-gateway, (2) Kuadrant AuthPolicy/Authorino for MaaS and LLMInferenceService, (3) kube-rbac-proxy sidecar for pod-level authorization, and (4) Istio mTLS for legacy service mesh paths. While each mechanism serves a legitimate architectural purpose, the combination means that understanding the authentication chain for any given request requires knowing which gateway, which component, and which deployment era applies. The distinction between gateway-level ext_authz authentication and pod-level kube-rbac-proxy authorization is architecturally sound but operationally complex — a user accessing a model endpoint traverses both layers, and troubleshooting authentication failures requires understanding both.

**Parallel ingress generations.** The platform actively maintains two ingress architectures: the current-generation Gateway API path (data-science-gateway, maas-default-gateway) and the legacy Istio Gateway path (knative-ingress-gateway, knative-local-gateway). This dual-path maintenance is necessary for backward compatibility but creates confusion about which path applies to a given workload. The odh-model-controller's conditional logic — creating either OpenShift Routes or Gateway API HTTPRoutes depending on configuration — exemplifies this transitional complexity. The workbenches controller similarly selects between Istio VirtualServices and Gateway API HTTPRoutes at startup, refusing to enable both simultaneously.

**RBAC breadth risk.** Several central operators accumulate very broad ClusterRole permissions. The rhods-operator's manager role spans all component CRDs plus platform infrastructure. The odh-dashboard operator role contains 61 rules across 15+ API groups. The models-as-a-service controller spans 30+ API groups. While this breadth reflects each component's legitimate integration surface, it means a compromise of any single operator's service account grants extensive cluster access. The platform mitigates this through separate service accounts per component, but the central operators remain high-value targets.

**TLS profile convergence.** A notably consistent pattern across the platform is dynamic TLS profile resolution from the OpenShift APIServer resource. At least 7 controllers implement the same `ProfileWatcher` pattern — reading the cluster TLS profile at startup, defaulting to Mozilla Intermediate (TLS 1.2+, ECDHE ciphers), and restarting on profile changes. This convergence suggests the pattern should be factored into a shared library (it partially is via `odh-platform-utilities` and `openshift/controller-runtime-common`). The one gap is the MaaS DestinationRule using `insecureSkipVerify: true` for backend TLS validation.

**llm-d as a platform within the platform.** The llm-d distributed inference stack represents a significant architectural subsystem with its own controller (llm-d-model-service), router (llm-d-router), scheduling system (gateway-api-inference-extension EPP), KV-cache management (llm-d-kv-cache), disaggregated prefill/decode routing (llm-d-routing-sidecar), batch processing (llm-d-batch-gateway), async dispatch (llm-d-async), autoscaling (WVA), latency prediction, and performance tooling (llm-d-benchmark, llm-d-prism). This creates a deep integration stack that parallels the platform's own operator model but uses Helm charts, LeaderWorkerSets, and Gateway API InferencePools rather than OLM and kustomize.

**AI Gateway convergence.** The platform is developing three overlapping gateway solutions: (1) the inference-focused gateway-api-inference-extension (upstream Kubernetes SIG), (2) the multi-provider AI Gateway (ai-gateway-controller + ai-gateway-payload-processing using Praxis ext-proc), and (3) the Praxis proxy framework (praxis-ai, praxis-extproc, praxis-grid). These share Envoy ext-proc as a common integration point but have different CRD surfaces, authentication models, and lifecycle management. The ai-gateway-controller's backend swap handshake with maas-controller (coordinating ownership of payload-processing resources via annotations) illustrates the complexity of maintaining parallel gateway solutions.

**Webhook density.** With 304 total webhooks across 25 components, the platform has substantial admission control coverage. The kueue-operator alone contributes 70 webhooks covering most workload types (Pods, Jobs, Deployments, StatefulSets, and framework-specific CRDs). Multiple webhooks from different components may intercept the same resource type — for example, Pod creation is intercepted by KServe (sidecar injection), Kueue (scheduling gates), and spark-operator (Spark configuration). Webhook ordering depends on alphabetical name sorting, creating an implicit dependency on naming conventions for correct layering.
