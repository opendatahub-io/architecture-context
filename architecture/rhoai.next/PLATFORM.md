## Platform Overview

Red Hat OpenShift AI (RHOAI) is a comprehensive AI/ML platform that provides model training, serving, monitoring, and lifecycle management on OpenShift Container Platform and vanilla Kubernetes (xKS). The platform is deployed through a meta-operator architecture: the `rhods-operator` manages the entire platform lifecycle via two cluster-scoped singleton CRDs (`DataScienceCluster` and `DSCInitialization` on OpenShift, `Platform` CR on xKS). This operator orchestrates a DAG-based provisioning system with runlevels (RL20 for core AI/ML, RL31 for the serving stack, RL32 for independent extensions, RL33 for KServe-dependent components) that ensures deterministic, upgrade-safe deployment ordering across all platform components.

The platform's ingress architecture has migrated from OpenShift Routes to Kubernetes Gateway API with backward-compatible redirects. The gateway service controller deploys a full stack: Gateway CR with HTTPS listeners, Istio EnvoyFilter for ext_authz authentication (calling kube-auth-proxy), Lua filters for token extraction, and OpenShift Routes for legacy URL redirects. Individual components (notebooks, model serving, dashboard) create HTTPRoutes in a central controller namespace with cross-namespace ReferenceGrants, centralizing ingress topology management while allowing per-component routing control.

The security posture follows a defense-in-depth model. Authentication is layered through kube-rbac-proxy sidecars (SubjectAccessReview-based authorization), Kuadrant/Authorino policies (for LLM serving endpoints), and OAuth2/OIDC integration via kube-auth-proxy. TLS is pervasive: OpenShift service-serving certificates provide automatic provisioning, operators align their TLS configuration with the cluster-wide TLS security profile, and inter-component communication uses TLS 1.2+ with FIPS-compliant cipher suites. Container images are predominantly built on UBI9-minimal bases with FIPS-enabled Go builds (`GOEXPERIMENT=strictfipsruntime` or `GOFIPS140=v1.0.0`), non-root execution, and multi-stage builds.

### Central Components

**rhods-operator** is the platform's meta-operator and most depended-upon component. It manages the lifecycle of all other operators and platform services via a DAG-based provisioning system. Every operator and controller in the platform is deployed, configured, and version-managed by rhods-operator through either in-tree kustomize manifests or out-of-tree module Helm/kustomize deployments.

**KServe** is the serving backbone. It provides the InferenceService and LLMInferenceService CRDs that define the model serving API surface. Multiple components depend on KServe: odh-model-controller watches KServe CRs to create platform infrastructure (Routes, AuthPolicies, ServiceMonitors), Model Registry synchronizes deployment state with InferenceServices, TrustyAI patches InferenceServices for explainability payloads, and vLLM/MLServer/OpenVINO run as inference containers within KServe pods.

**odh-dashboard** is the user-facing web UI and the integration hub for the platform's user experience. It discovers and presents workbench images, model serving endpoints, pipeline statuses, model registry entries, feature stores, and MLflow experiments. Its modular architecture (webpack Module Federation with Go BFF modules) allows independent development of feature-specific UI surfaces.

**Kubeflow Notebook Controller** manages workbench pods (Jupyter, VS Code, RStudio) and performs ambient configuration — automatically injecting pipeline connections (DSPA), experiment tracking (MLflow), feature store configs (Feast), and authentication proxies (kube-rbac-proxy) into notebook environments without user intervention.

**kube-rbac-proxy** is the platform's authentication enforcement point, deployed as a sidecar across 15+ components. It terminates TLS and performs SubjectAccessReview authorization before proxying requests to application containers.

## Deployment Architecture

### Deployment Topology

The platform follows a three-namespace deployment model with user workspace isolation:

**Operator namespace** (`redhat-ods-operator`): Contains the platform meta-operator (rhods-operator), its webhooks, and leader election infrastructure. This namespace has minimal RBAC surface — the operator's ServiceAccount holds broad cluster permissions but the namespace itself is access-restricted.

**Applications namespace** (`redhat-ods-applications`): The primary platform services namespace containing 20+ operator/controller deployments, the dashboard, kube-auth-proxy, and shared infrastructure (Gateway, monitoring). Module operators deployed here manage their own sub-component namespaces (e.g., ai-gateway-operator manages `redhat-ai-gateway-infra`).

**User namespaces**: Individual or team namespaces where workloads run — notebooks, inference services, pipeline executions, training jobs, feature stores. Platform controllers create cross-namespace resources (HTTPRoutes, ReferenceGrants, ClusterRoleBindings) to connect user workloads to platform infrastructure. Namespace isolation is enforced via NetworkPolicies, kube-rbac-proxy per-resource authorization, and Kubernetes RBAC.

**Monitoring namespace** (`redhat-ods-monitoring`): Houses the observability stack — Prometheus (via MonitoringStack CR), Tempo for traces, OpenTelemetry Collector for telemetry aggregation, Perses for dashboarding, and prom-label-proxy for multi-tenant metrics isolation.

#### Manifest Consumption Pipeline

Component manifests flow through a multi-stage pipeline: (1) Component source repos contain kustomize bases and overlays with distribution-specific configurations. (2) Module operators and the platform operator use `get_all_manifests.sh` scripts to fetch manifests from component repos at pinned commit SHAs during their build process. (3) Fetched manifests are committed to the operator repo and baked into the container image via `COPY` directives. (4) At runtime, init containers copy manifests from the read-only image filesystem to writable emptyDir volumes. (5) Operator controllers render manifests using the kustomize API with runtime parameter injection (namespace, RELATED_IMAGE variables, feature flags) and apply via Server-Side Apply with force ownership. This pipeline ensures that all manifest changes are visible in PR diffs, deployments are reproducible without network access, and image references can be overridden for disconnected environments.

### Disconnected Support

The platform provides comprehensive air-gapped deployment support through the OLM `RELATED_IMAGE` pattern. All operator images reference their operand images via `RELATED_IMAGE_*` environment variables injected from the ClusterServiceVersion. Module operators (ai-gateway-operator, workbenches-operator, feast-module-operator) propagate these variables to sub-component kustomize manifests during rendering via `envsubst` or parameter injection. Image mirroring via `oc-mirror` uses digest-pinned references from the OLM catalog. The manifest vendoring pattern (fetching and committing manifests at build time rather than runtime) ensures operators can deploy without network access. The DSPO managed-pipelines feature adds a registry access requirement at reconciliation time (OCI manifest fetch), controlled by an `AllowedRegistries` allowlist. Notebook images use Cachi2-prefetched dependencies for hermetic builds, and AIPCC base images provide Red Hat's PyPI index for secure Python packaging.

## Platform Architectural Analysis

RHOAI's architecture reveals several cross-cutting patterns and tensions that only emerge when examining all 96 components together.

**The Meta-Operator Pattern at Scale**: The three-tier operator hierarchy (rhods-operator → module operators → workload operators) is the platform's most distinctive architectural feature. This pattern enables independent component evolution and clean API boundaries (the platform operator only knows about module CRDs like `AIGateway`, `Workbenches`, `Feast`), but it creates RBAC amplification: module operators like ai-gateway-operator must hold every permission their sub-components need, including escalation rights, because Kubernetes requires that a role-creating entity hold all granted permissions. The result is that 37 operator binaries collectively define 913 RBAC roles, with ai-gateway-operator, trainer-operator, and agents-operator each holding 30+ roles. The security surface is broad by necessity, not by design.

**Authentication Fragmentation**: The platform uses at least seven distinct authentication mechanisms, each appropriate for its context but collectively creating complexity. kube-rbac-proxy (SubjectAccessReview) dominates for operator metrics and service endpoints. Kuadrant/Authorino handles LLM serving auth. kube-auth-proxy provides OAuth2/OIDC at the Gateway level. OAuth proxy sidecars protect RayCluster dashboards. SPIFFE/mTLS secures agent-to-agent communication. Istio AuthorizationPolicy governs mesh-level access. API keys provide the simplest path for MaaS consumers. This heterogeneity is architecturally justified — each mechanism matches its service's requirements — but it means there is no single authentication audit point. A platform-wide auth policy change requires understanding and updating multiple distinct systems.

**TLS Configuration Drift**: While the platform has strong TLS coverage (service-serving certificates, cert-manager, self-signed certs, cluster TLS profile alignment), the configuration approaches diverge significantly across components. Some operators (trustyai-service-operator, model-registry-operator, workbenches-operator, feast-operator) dynamically read the OpenShift cluster TLS profile and restart on changes. Others use hardcoded TLS 1.2+ with fixed cipher suites. Several components contain `InsecureSkipVerify: true` — some intentionally (DSPO's MariaDB skip-verify opt-in, Feast's internal registry calls), some as development artifacts. The fms-guardrails-orchestrator includes a `NoVerifier` struct in production code. These inconsistencies are individually documented but collectively represent an area where platform-wide standardization would reduce security review burden.

**The Serving Stack Duplication**: The platform maintains three distinct model serving paths: (1) KServe with InferenceService for traditional ML models and LLMInferenceService for LLMs, using KNative for serverless scaling; (2) ModelMesh for multi-model serving with etcd-coordinated placement and scale-to-zero; (3) Models-as-a-Service (MaaS) for external provider routing via Envoy ext_proc. Each has its own deployment model, scaling mechanism, auth integration, and monitoring approach. The odh-model-controller acts as the bridge, watching KServe CRs to create platform infrastructure, but ModelMesh has its own independent infrastructure stack. This duplication reflects the platform's evolution from ModelMesh (traditional ML) to KServe (cloud-native ML/LLM) to MaaS (external providers), with backward compatibility requirements preventing consolidation.

**DAG-Based Provisioning as Risk Mitigation**: The rhods-operator's runlevel-based DAG provisioning (RL20→RL31→RL32→RL33) with StuckTracker timeout is an underappreciated architectural strength. It prevents the cascading failure mode common in operator-heavy platforms where component A waits for component B's CRD, which waits for component C's deployment, creating circular dependencies. The 10-minute StuckTracker threshold is a pragmatic choice that trades occasional force-advancement (potentially leaving a component in a degraded state) for guaranteed forward progress. The dual provisioning path (in-tree kustomize vs out-of-tree modules) adds flexibility but means upgrade behavior depends on whether a component has been migrated to the module path.

**Inference Routing Intelligence**: The llm-d stack introduces a sophisticated inference-aware routing layer that is architecturally distinct from traditional load balancing. The Endpoint Picker (EPP) runs as an Envoy ext_proc filter with scoring plugins that consider KV-cache state, prefix overlap, queued tokens, and expert parallelism — information that is invisible to standard L4/L7 load balancers. The composable plugin architecture (prefix-cache-affinity for baseline, token-load-scorer for disaggregated prefill/decode, expert-parallelism-aware for wide EP) allows deployment-specific routing without code changes. This represents a shift from infrastructure-level to application-level traffic management that is specific to LLM serving workloads.

**Container Image Supply Chain Complexity**: The platform's container image strategy spans four patterns: (1) Go binaries on distroless/scratch (20 components), (2) Python services on UBI9-minimal (64 components), (3) AIPCC ecosystem images with pre-built accelerator libraries (notebooks, vLLM variants), and (4) thin wrapper images that add only configuration to upstream base images (vllm downstream). The AIPCC dependency is particularly notable: notebook images use a 500-line `aipcc.sh` script to replicate the AIPCC system package layout on CentOS Stream for ODH builds, creating tight coupling between base images and the AIPCC package set. The llm-d CUDA Dockerfile compiles 10+ components from source with orchestrated dependency chains (GDRCopy→UCX→NVSHMEM→DeepEP), making it the most complex build artifact in the platform.

**Observability as a Conditional Stack**: The monitoring subsystem deployed by rhods-operator is comprehensive (Prometheus, Tempo, OpenTelemetry Collector, Perses, Thanos Querier, prom-label-proxy) but entirely dependent on CRD availability. Each observability component is conditionally deployed based on whether its operator CRD (MonitoringStack, Tempo, OpenTelemetryCollector, Perses) exists on the cluster. This means the actual deployed observability stack varies by cluster configuration, making monitoring coverage non-deterministic. The prom-label-proxy enforces multi-tenant metrics isolation (namespace-scoped queries), but the conditional deployment means some clusters may lack trace collection or dashboarding entirely.

**Emerging Agent Infrastructure**: The agents-operator introduces an entirely new trust model — SPIFFE-based workload identity with A2A protocol, JWS-signed agent cards, and OPA policy enforcement — that runs parallel to the platform's existing Kubernetes RBAC and OAuth2 infrastructure. This reflects the industry shift toward agentic AI workflows but creates a second identity and authorization plane that is not integrated with the existing kube-rbac-proxy or Kuadrant mechanisms. The AuthBridge sidecar's four deployment shapes (proxy-sidecar, envoy-sidecar, lite, waypoint) and three mTLS modes add configuration complexity that is unique to agent workloads.
