## Purpose

**Short**: Module operator that watches FeastOperator CRs and deploys the upstream Feast feature store operator via kustomize manifests on the ODH/RHOAI platform.

**Detailed**: The feast-module-operator is a satellite operator in the OpenDataHub modular architecture. Rather than being deployed directly by users, it is deployed by the central ODH Operator (opendatahub-operator) via a Helm chart. The ODH Operator then creates a `FeastOperator` CR (a cluster-scoped singleton named `default-feastoperator`), which this module operator reconciles to deploy the upstream feast-operator controller-manager and its associated resources.

The reconciliation pipeline follows a structured action chain: it resolves the bundled manifest path, writes runtime parameters (OIDC issuer URL, related images) into `params.env`, handles deployment selector migrations for upgrades, renders kustomize manifests through platform-specific overlays (ODH vs RHOAI), applies them to the cluster, and reports status conditions back to the CR. The operator also implements a platform version handshake protocol via the `odh-feastoperator-config` ConfigMap, enabling coordinated upgrades when the platform version advances.

The deployed feast-operator in turn manages `FeatureStore` CRs (namespaced, from the `feast.dev` API group), orchestrating feature store infrastructure including online/offline servers, registry services, and materialization jobs. The module operator's broad RBAC surface — covering Spark applications, CronJobs, HPA, PDB, Routes, and more — reflects permissions it delegates to the feast-operator it deploys.

## Architectural Analysis

The feast-module-operator exemplifies the ODH modular operator pattern, where component lifecycle management is factored out of the monolithic opendatahub-operator into independently-versioned module operators. It imports the opendatahub-operator's reconciler framework (`pkg/controller/reconciler`), action pipeline (`actions/deploy`, `actions/render/kustomize`, `actions/status`), and predicate/handler utilities rather than reimplementing controller machinery. This tight coupling to the opendatahub-operator library means the module operator's behavior is largely determined by the framework — the module-specific code is focused on parameterization and migration logic.

The architecture has a notable two-level operator pattern: this module operator deploys the feast-operator, which in turn manages FeatureStore CRs. The module operator's RBAC includes permissions for resources it never directly creates (Spark applications, CronJobs, PVCs, Routes) — these exist because the feast-operator it deploys needs them. The module operator holds these permissions as a superset to apply manifests containing RBAC rules for the inner operator.

The namespace-scoped cache configuration in `manager.go` is architecturally significant: informers for Deployments, Services, ServiceAccounts, Roles, and RoleBindings are restricted to the configured applications namespace, while FeastOperator CRs and CRDs use cluster-wide watches. ConfigMaps and Secrets are explicitly excluded from the cache (`DisableFor`) to ensure fresh reads during reconciliation — important because `params.env` values and the platform config ConfigMap are read directly rather than from cache.

The platform version handshake protocol (`reconcilePlatformVersion`) provides a coordination mechanism between the ODH platform operator and this module operator. The platform operator writes version information to the `odh-feastoperator-config` ConfigMap; this module operator watches that ConfigMap (via a named-resource predicate), compares versions, and runs any necessary migrations. The `upgradeIfNeeded` action provides a second upgrade path based on semver comparison of the release version, separate from the platform version handshake.
