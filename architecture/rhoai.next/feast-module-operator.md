## Purpose

**Short**: Module operator that deploys and manages the upstream Feast feature store operator and its CRDs on OpenShift as part of the ODH/RHOAI platform.

**Detailed**: The feast-module-operator is a Kubernetes operator that acts as a "module operator" within the ODH/RHOAI modular operator architecture. Rather than containing the Feast feature store logic itself, it deploys the upstream Feast operator (feast-dev/feast-operator) onto the cluster by rendering kustomize manifests that include the upstream operator's Deployment, CRDs (FeatureStore), RBAC, and supporting resources.

The operator watches a cluster-scoped `FeastOperator` custom resource (singleton named `default-feastoperator`) and reconciles the upstream Feast operator's deployment into the applications namespace. It selects between ODH and RHOAI kustomize overlays based on platform configuration, substitutes image references from `params.env`, and manages the full lifecycle including upgrades, deployment selector migration, and garbage collection of cluster-scoped resources.

The operator also implements a platform version handshake protocol — it reads the platform version from an `odh-feastoperator-config` ConfigMap (created by the parent platform operator) and tracks version changes in the FeastOperator CR status to coordinate platform-wide upgrades. Additionally, it supports OIDC issuer URL configuration for external OIDC authentication integration. The operator can be deployed both via kustomize (managed by rhods-operator/opendatahub-operator) and via a self-generated Helm chart for standalone development.

## Architectural Analysis

The feast-module-operator follows the ODH/RHOAI modular operator pattern, where a lightweight "module operator" is responsible for deploying and managing an upstream component's operator. This is a layer-of-indirection architecture: the module operator doesn't implement Feast logic itself but instead renders and applies kustomize manifests that install the upstream Feast operator. The upstream Feast operator then manages the actual FeatureStore custom resources. This two-tier design enables the platform to control lifecycle, versioning, and image pinning for upstream components without forking their controller logic.

The operator uses the ODH operator framework's reconciler pipeline pattern extensively. The reconciliation chain (`initialize → upgradeIfNeeded → setKustomizedParams → releases → reconcilePlatformVersion → kustomize.render → migrateDeploymentSelector → deploy → deployments.status → gc`) is a well-structured sequence of idempotent actions. Each action has a single responsibility, and the pipeline can be extended with new migration steps by inserting actions at the appropriate position. The `migrateDeploymentSelector` action is a noteworthy example — it handles the immutable `spec.selector` field by detecting stale selectors and deleting the Deployment for recreation, with a complementary `selector-migration` Job in the kustomize manifests as a belt-and-suspenders approach.

The platform version handshake protocol is architecturally significant. The platform operator writes a version to the `odh-feastoperator-config` ConfigMap, and the module operator reads it, performs any necessary migration logic, and records the acknowledged version in its CR status. This enables coordinated platform-wide upgrades where each module operator can gate on version transitions. Currently, no version-specific migrations exist (the `upgrade()` and `handlePlatformUpgrade()` methods are stubs), but the infrastructure is in place for future use.

The Helm chart generation capability (`chartgen` subcommand) is unusual for an operator — it reads kustomize output from stdin and produces a Helm chart with proper templating (namespace substitution, image reference injection, resource limit templating, ServiceAccount name templating). This enables standalone development and deployment outside the ODH/RHOAI operator ecosystem, which is valuable for testing and for users who want to deploy Feast without the full platform. The chart is stored in `config/chart/` and is auto-generated as part of the build process.

The RBAC scope is notably broad — the module operator has permissions for resources it doesn't directly manage (Routes, HorizontalPodAutoscalers, PodDisruptionBudgets, PersistentVolumeClaims, Notebooks, CronJobs). These permissions exist because the upstream Feast operator needs them, and the module operator must create the ClusterRole that grants them. The module operator's finalizer (`cleanupClusterResources`) handles deletion of cluster-scoped resources (ClusterRoles, ClusterRoleBindings) that can't use ownerReferences for garbage collection, which is a common pattern in operators that manage cluster-scoped resources from a namespaced context.
