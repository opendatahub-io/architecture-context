## Purpose

**Short**: Module operator that deploys and manages the upstream Feast feature store operator as a component within the OpenDataHub/RHOAI platform.

**Detailed**: The feast-module-operator is a second-level operator in the ODH/RHOAI modular operator architecture. It watches `FeastOperator` Custom Resources (API group `components.platform.opendatahub.io/v1`) and deploys the upstream [feast-operator](https://github.com/feast-dev/feast) using bundled kustomize manifests. The ODH platform operator creates a `FeastOperator` CR with platform configuration (including OIDC settings), and this module operator reconciles it by rendering kustomize manifests with distribution-specific overlays (ODH or RHOAI) and applying them to the cluster.

The operator follows the ODH modular handler framework pattern: the platform operator deploys this module operator via a Helm chart, then creates the `FeastOperator` CR. The module operator's reconciliation pipeline initializes manifests, sets OIDC parameters, handles version upgrades, renders kustomize, deploys resources, and reports deployment status. It manages the full lifecycle of the feast-operator controller-manager Deployment and its supporting RBAC, ServiceAccounts, Services, CRDs, and monitoring resources. A platform version handshake protocol synchronizes upgrade state between the platform operator and this module operator via a shared ConfigMap (`odh-feastoperator-config`).

## Architectural Analysis

The feast-module-operator exemplifies the ODH modular operator pattern -- a thin second-level operator that bridges the platform operator and an upstream Feast workload. Rather than embedding Feast deployment logic in the monolithic platform operator, the architecture delegates to this dedicated module operator deployed via Helm. This reduces the blast radius of Feast-related changes and allows independent release cadence. The operator binary serves dual purpose: at build time, the `chartgen` subcommand generates a self-contained Helm chart from kustomize output; at runtime, the `operator` subcommand runs the controller-runtime reconciler.

The reconciliation pipeline is structured as an ordered action chain: `initialize` → `upgradeIfNeeded` → `setKustomizedParams` → `releases` → `reconcilePlatformVersion` → `kustomize render` → `migrateDeploymentSelector` → `deploy` → `deployments status` → `gc`. The `migrateDeploymentSelector` action is notable -- it handles the immutable selector problem during upgrades by detecting stale `spec.selector.matchLabels` and deleting the Deployment for recreation. This is complemented by a selector-migration Job in the kustomize manifests that runs the same check using `oc` CLI, providing a belt-and-suspenders approach.

The platform version handshake (`reconcilePlatformVersion`) is a coordination protocol between the platform operator and module operators. The platform operator writes the current version to `odh-feastoperator-config` ConfigMap; the module operator watches it, runs any version-gated migrations, and records the acknowledged version in `status.releases[name="platform"]`. Currently no actual migrations exist (the `upgrade` and `handlePlatformUpgrade` methods are stubs), but the framework is ready for future version-gated changes.

The Helm chart generation (`chartgen`) is architecturally interesting -- it ingests raw kustomize YAML from stdin, groups resources by GVK, and applies kind-specific template transformations (namespace injection, image parameterization, serviceAccountName templating, imagePullSecrets). This allows the platform operator to deploy the module operator without requiring kustomize at runtime. The chart includes a JSON Schema (`values.schema.json`) auto-generated from the Go `Values` struct, and uses `missingkey=error` rendering which requires all values to be explicitly declared.

A potential risk is the breadth of the RBAC permissions. The module operator's ClusterRole grants full CRUD on CRDs, RBAC resources (ClusterRoles, ClusterRoleBindings), Deployments, and Routes. While these are required because the operator deploys the feast-operator workload (which itself needs these resources), the permissions are granted to the module operator's ServiceAccount rather than being scoped to only the resources it manages. The operator mitigates this partially through namespace-scoped informer caching (`ByObject` cache configuration restricts watches to the applications namespace for Deployments, Services, ServiceAccounts, Roles, and RoleBindings), but cluster-scoped resources like ClusterRoles and CRDs are watched cluster-wide.
