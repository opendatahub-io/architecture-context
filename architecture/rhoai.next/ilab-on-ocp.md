## Purpose

**Short**: Orchestrates the InstructLab LLM fine-tuning workflow on Red Hat OpenShift AI using Kubeflow Pipelines, KServe, and the Kubeflow Training Operator.

**Detailed**: ilab-on-ocp is the central pipeline application that automates the InstructLab large language model fine-tuning process on OpenShift clusters running Red Hat OpenShift AI. It defines and compiles multi-stage Kubeflow Pipelines that orchestrate the complete InstructLab workflow: synthetic data generation (SDG) using a teacher model, two-phase distributed training via PyTorchJobs, model evaluation (MT-Bench and MMLU), and output model publishing to OCI registries and Model Registry.

The pipeline is designed to run as a managed pipeline within Data Science Pipelines Application (DSPA). It does not deploy a long-running service; instead, it compiles pipeline definitions (YAML) that are uploaded to and executed by the Kubeflow Pipelines backend. Each pipeline stage runs as an ephemeral container task, using RHELAI images for InstructLab operations and a generic runtime image for utility tasks. The component coordinates GPU-intensive workloads across multiple nodes using the Kubeflow Training Operator for distributed PyTorch training.

The pipeline integrates with multiple RHOAI platform services: KServe for serving teacher and judge models during SDG and evaluation, the Training Operator for multi-node GPU training, Model Registry for registering output models, and S3-compatible object storage for artifact persistence. It supports both connected and disconnected OpenShift environments.

## Architectural Analysis

The ilab-on-ocp component is architecturally distinct from most RHOAI components because it is neither an operator nor a long-running service. It is a pipeline compiler and task library — a Python package that uses the KFP SDK to define pipeline DAGs that the Data Science Pipelines infrastructure executes. The compiled pipeline YAML (`pipeline.yaml`) is the deployable artifact, not the Python code itself. The runtime image (`odh-ml-pipelines-runtime-generic`) embeds the pipeline code and its dependencies so that individual pipeline steps can import the component modules at execution time.

The pipeline follows a strict sequential-with-parallelism pattern: prerequisites validation runs first (checking connectivity to teacher/judge models, Model Registry, Training Operator, and OCI registries), followed by SDG, data processing, two-phase distributed training, evaluation, and model output. Artifact data flows through ReadWriteMany PersistentVolumeClaims that are dynamically created and destroyed during each pipeline run.

A notable design choice is that the pipeline tasks directly call the Kubernetes API using service account tokens mounted at `/var/run/secrets/kubernetes.io/serviceaccount/` rather than relying on KFP's native secret handling. This is done because KFP v2 has limitations with optional secrets and dynamic secret names (noted as FIXMEs in the code). The TLS configuration is consistent across all components: `httpx.Client(verify=ssl.create_default_context())` is used for all HTTPS connections, leveraging OpenSSL's system CA bundle, and the Kubernetes CA certificate at the service account mount path is used for in-cluster API calls.

The distributed training architecture uses PyTorchJobs with FSDP (Fully Sharded Data Parallel) and explicitly disables Istio sidecar injection on training pods — a pragmatic choice to avoid interference with PyTorch's rendezvous protocol for inter-node communication. Training uses CPU offloading for both optimizer state and FSDP parameters, indicating the pipeline is designed for memory-constrained GPU configurations.
