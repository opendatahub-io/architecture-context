## Purpose

**Short**: Thin Dockerfile wrapper that extends the RHAIIS vLLM ROCm product image with a TGIS-compatible adapter entrypoint for AMD GPU inference serving on Red Hat OpenShift AI.

**Detailed**: The vllm-rocm repository produces a container image for serving large language models using AMD ROCm GPUs within RHOAI. It contains no application source code — the entire repository consists of a single Konflux Dockerfile, Tekton pipeline configuration, and upstream vLLM project files (README, LICENSE, pre-commit config) carried over from earlier iterations.

The Dockerfile uses the RHAIIS product image (`registry.redhat.io/rhaiis/vllm-rocm-rhel9`) as its base, which packages vLLM with AMD ROCm runtime libraries. This wrapper image adds a TGIS (Text Generation Inference Server) adapter entrypoint (`python3 -m vllm_tgis_adapter`), configuring default ports for both HTTP (8000) and gRPC (8033) protocols, and disabling the logprobs-during-speculative-decoding optimization that would be unexpected for hosted model users. The image runs as a non-root user (UID 2000) for security.

The repository was recently refactored (September 2025) to consume vLLM ROCm from RHAIIS releases via the AIPCC ecosystem, replacing a previous approach that built vLLM from source. This "integrate AIPCC" migration dramatically simplified the Dockerfile from a multi-stage build to a single-stage image extension.

## Architectural Analysis

The vllm-rocm repository exemplifies the "thin wrapper" pattern used across several RHOAI inference components. Rather than building vLLM from source (as the repository did historically), it now consumes a pre-built RHAIIS product image and adds only configuration — environment variables, a non-root user, and a TGIS adapter entrypoint. This architectural decision, implemented in the "Integrate AIPCC to consume vLLM ROCm from RHAIIS releases" commit (September 2025), collapses the build pipeline complexity from a multi-stage compilation with ROCm SDK dependencies to a single `FROM` + `ENV` + `ENTRYPOINT` layer. The tradeoff is that version control shifts from source-level (pinning vLLM commit) to image-level (pinning `RHAIIS_VERSION=3.2.1`).

The TGIS adapter (`vllm_tgis_adapter`) is the critical architectural bridge in this image. It exposes a gRPC interface on port 8033 that implements the TGIS (Text Generation Inference Server) protocol, which is the standard interface expected by KServe ServingRuntimes in RHOAI. Simultaneously, the underlying vLLM engine provides an OpenAI-compatible REST API on port 8000. This dual-protocol design allows the same pod to serve both KServe-managed inference (via gRPC/TGIS) and direct API access (via REST/OpenAI). The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` override is a notable product decision — upstream vLLM disables logprobs during speculative decoding for performance, but RHOAI overrides this because hosted model users expect logprobs to always be available.

The security posture of this image is entirely delegated — no TLS, no authentication, no authorization logic at the application level. This is architecturally correct for RHOAI 3.x where kube-rbac-proxy sidecars handle auth and Gateway API handles TLS termination. However, it means the image is not safe to expose directly without the platform ingress layer. The non-root user (UID 2000) provides basic container isolation. The absence of any FIPS-related configuration in this Dockerfile is expected since all crypto libraries come from the RHAIIS base image, which is built on RHEL 9 UBI with FIPS-capable OpenSSL.

The repository carries upstream vLLM artifacts (README.md, .pre-commit-config.yaml, LICENSE) from its earlier life as a source-building fork. These files are vestigial — the pre-commit config references Python/C++ source files that don't exist in this repo. The actual README for this wrapper image should be distinct from the upstream vLLM project README, as it can mislead contributors about the repository's scope and build process.

The Tekton pipeline (`hermetic: false`, `build-platforms: linux-extra-fast/amd64`) confirms this is an x86_64-only build with no hermeticity enforcement. The long pipeline timeouts (8h pipeline, 4h per task) are inherited from the build infrastructure rather than reflecting actual build duration — the wrapper Dockerfile should build in seconds. The pipeline is maintained centrally via `red-hat-data-services/konflux-central` and synced automatically, as documented in `.tekton/README.md`.
