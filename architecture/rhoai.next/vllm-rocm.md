## Purpose

**Short**: Thin Dockerfile wrapper that extends the RHAIIS vLLM ROCm product image with a TGIS-compatible adapter entrypoint for AMD GPU inference serving on Red Hat OpenShift AI.

**Detailed**: The vllm-rocm repository produces a container image for serving large language models using AMD ROCm GPUs within RHOAI. It contains no application source code — the entire repository consists of a single Konflux Dockerfile, Tekton pipeline configuration, and upstream vLLM project files (README, LICENSE, pre-commit config) carried over from earlier iterations.

The Dockerfile uses the RHAIIS product image (`registry.redhat.io/rhaiis/vllm-rocm-rhel9`) as its base, which packages vLLM with AMD ROCm runtime libraries. This wrapper image adds a TGIS (Text Generation Inference Server) adapter entrypoint (`python3 -m vllm_tgis_adapter`), configuring default ports for both HTTP (8000) and gRPC (8033) protocols, and disabling the logprobs-during-speculative-decoding optimization that would be unexpected for hosted model users. The image runs as a non-root user (UID 2000) for security.

The repository was recently refactored (September 2025) to consume vLLM ROCm from RHAIIS releases via the AIPCC ecosystem, replacing a previous approach that built vLLM from source. This "integrate AIPCC" migration dramatically simplified the Dockerfile from a multi-stage build to a single-stage image extension.

## Purpose

**Short**: Downstream Konflux build wrapper that produces the AMD ROCm variant of the vLLM inference server container image for Red Hat OpenShift AI.

**Detailed**: vllm-rocm is a minimal build-definition repository whose sole artifact is a container image (`odh-vllm-rocm-rhel9`) that packages the upstream vLLM inference engine with AMD ROCm GPU acceleration for deployment in RHOAI. The repository contains no application source code; instead, it pulls the pre-built `registry.redhat.io/rhaiis/vllm-rocm-rhel9` image produced by the Red Hat AI Inference Server (RHAIIS) team and layers on a custom entrypoint that starts vLLM through the `vllm_tgis_adapter` Python module.

The image exposes two network ports: an OpenAI-compatible HTTP API on port 8000 and a gRPC endpoint (TGIS-compatible) on port 8033. The `vllm_tgis_adapter` module provides both the standard vLLM OpenAI-compatible API and a TGIS (Text Generation Inference Server) gRPC adapter, allowing RHOAI model-serving infrastructure (KServe, ModelMesh) to communicate with vLLM using the TGIS protocol that is native to the platform.

The Konflux build pipeline is managed centrally from the `red-hat-data-services/konflux-central` repository and synced to the `.tekton/` directory. Builds run on `linux-extra-fast/amd64` and target `quay.io/rhoai/` for pull-request images. The image runs as non-root user 2000, and speculative decoding logprobs are explicitly enabled (`DISABLE_LOGPROBS_DURING_SPEC_DECODING=false`) for predictable behavior in hosted model scenarios.

## Architectural Analysis

The vllm-rocm repository exemplifies the "thin wrapper" pattern used across several RHOAI inference components. Rather than building vLLM from source (as the repository did historically), it now consumes a pre-built RHAIIS product image and adds only configuration — environment variables, a non-root user, and a TGIS adapter entrypoint. This architectural decision, implemented in the "Integrate AIPCC to consume vLLM ROCm from RHAIIS releases" commit (September 2025), collapses the build pipeline complexity from a multi-stage compilation with ROCm SDK dependencies to a single `FROM` + `ENV` + `ENTRYPOINT` layer. The tradeoff is that version control shifts from source-level (pinning vLLM commit) to image-level (pinning `RHAIIS_VERSION=3.2.1`).

The TGIS adapter (`vllm_tgis_adapter`) is the critical architectural bridge in this image. It exposes a gRPC interface on port 8033 that implements the TGIS (Text Generation Inference Server) protocol, which is the standard interface expected by KServe ServingRuntimes in RHOAI. Simultaneously, the underlying vLLM engine provides an OpenAI-compatible REST API on port 8000. This dual-protocol design allows the same pod to serve both KServe-managed inference (via gRPC/TGIS) and direct API access (via REST/OpenAI). The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` override is a notable product decision — upstream vLLM disables logprobs during speculative decoding for performance, but RHOAI overrides this because hosted model users expect logprobs to always be available.

The security posture of this image is entirely delegated — no TLS, no authentication, no authorization logic at the application level. This is architecturally correct for RHOAI 3.x where kube-rbac-proxy sidecars handle auth and Gateway API handles TLS termination. However, it means the image is not safe to expose directly without the platform ingress layer. The non-root user (UID 2000) provides basic container isolation. The absence of any FIPS-related configuration in this Dockerfile is expected since all crypto libraries come from the RHAIIS base image, which is built on RHEL 9 UBI with FIPS-capable OpenSSL.

The repository carries upstream vLLM artifacts (README.md, .pre-commit-config.yaml, LICENSE) from its earlier life as a source-building fork. These files are vestigial — the pre-commit config references Python/C++ source files that don't exist in this repo. ## Architectural Analysis

This repository exemplifies the RHOAI "thin wrapper" pattern for inference runtime images. The actual vLLM application, its Python dependencies, ROCm GPU libraries, and the TGIS gRPC adapter are all packaged in the upstream RHAIIS image (`registry.redhat.io/rhaiis/vllm-rocm-rhel9`). This repository's sole contribution is the final image layer: a custom `ENTRYPOINT` that starts `vllm_tgis_adapter` with appropriate defaults, environment variables configuring the HTTP and gRPC ports, and a non-root `USER 2000` directive for security.

The AIPCC integration (merged September 2025 via PR #77) transitioned this image from building vLLM from source to consuming the pre-built RHAIIS release. This is architecturally significant: the `RHAIIS_VERSION` build arg (currently `3.2.1`) pins the entire software stack — vLLM version, ROCm version, Python packages, and system libraries — to a specific RHAIIS release. This decouples the RHOAI model-serving team from the details of building vLLM with ROCm support, delegating that complexity to the AIPCC/RHAIIS teams.

The dual-port design (HTTP 8000 + gRPC 8033) reflects RHOAI's model-serving architecture: the OpenAI-compatible HTTP API on port 8000 serves direct consumer traffic (routed through KServe's Gateway API infrastructure), while the TGIS gRPC endpoint on port 8033 provides the internal protocol used by ModelMesh and KServe transformers. The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable is a deliberate override of vLLM's default optimization — in a platform context where users expect predictable API behavior regardless of backend optimizations like speculative decoding, disabling the logprob suppression ensures consistent API responses.

The build is explicitly non-hermetic (`hermetic: false` in the Tekton pipeline), which is acceptable because this Dockerfile installs no packages — it only extends the base image. Supply chain integrity relies entirely on the RHAIIS base image's own build process, which operates under AIPCC's secure build pipelines. The absence of lock files on the `main` branch is consistent with this pattern.
