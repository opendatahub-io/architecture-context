## Purpose

**Short**: Thin Dockerfile wrapper that layers the TGIS gRPC adapter entrypoint onto the RHAIIS vLLM ROCm base image, producing a GPU-accelerated LLM inference server for AMD GPUs.

**Detailed**: vLLM ROCm is a downstream Red Hat build artifact repository that contains no application source code. The entire repository consists of a single Konflux Dockerfile (`Dockerfile.konflux.rocm`) that takes the pre-built RHAIIS (Red Hat AI Inference Server) base image `registry.redhat.io/rhaiis/vllm-rocm-rhel9` and configures it to run the `vllm_tgis_adapter` — a Python wrapper that exposes both an OpenAI-compatible REST API (port 8000) and a TGIS (Text Generation Inference Server) gRPC interface (port 8033). The vLLM engine, ROCm runtime, AMD GPU support libraries, Python packages, and the TGIS adapter itself are all provided by the RHAIIS base image.

The resulting container image is consumed by RHOAI's model serving infrastructure through the `vllm-rocm-runtime-template` KServe ServingRuntime template defined in `odh-model-controller`. In the RHOAI platform, only the REST protocol is exposed through the template; the gRPC port is available in the image but is RHAII-scope and not wired into OOTB platform templates. The image is referenced by SHA256 digest in the RHOAI operator's `params.env`, ensuring deterministic deployments.

## Architectural Analysis

This repository represents the thinnest possible component pattern in the RHOAI ecosystem — a pure Dockerfile wrapper with no source code, no manifests, no tests, and no kustomize overlays. All application logic, GPU acceleration libraries, model loading, inference execution, and protocol handling are inherited from the RHAIIS base image. The repository's sole architectural purpose is to establish a Konflux build pipeline that produces a tagged and labeled container image with the correct TGIS adapter entrypoint for the RHOAI platform.

The RHAIIS base image (`registry.redhat.io/rhaiis/vllm-rocm-rhel9:3.2.1`) encapsulates the full vLLM engine with AMD ROCm support, meaning all FIPS compliance, crypto configuration, dependency management, and build hermeticity for the Python/C++ components are the responsibility of the RHAIIS team's upstream build process. This repository only adds the container metadata (labels, user, entrypoint) layer.

The TGIS adapter (`vllm_tgis_adapter`) is the critical architectural bridge in this image. It exposes a gRPC interface on port 8033 that implements the TGIS protocol, which is the standard interface expected by KServe ServingRuntimes in RHOAI. Simultaneously, the underlying vLLM engine provides an OpenAI-compatible REST API on port 8000. This dual-protocol design allows the same pod to serve both KServe-managed inference (via gRPC/TGIS) and direct API access (via REST/OpenAI). However, per overlay 0015, the RHOAI platform only exposes REST through the `vllm-rocm-runtime-template`; gRPC/TGIS remains RHAII-scope.

The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable override is a notable product decision. Upstream vLLM disables logprobs during speculative decoding as a performance optimization, but RHOAI overrides this because hosted model users expect logprobs to always be available regardless of the decoding strategy.

The build pipeline is non-hermetic (`hermetic: false` in the Tekton PipelineRun), which is architecturally appropriate since the Dockerfile performs no package installation — it is a pure base-image repackaging. Tekton pipeline definitions are synchronized from the `konflux-central` repository and should not be edited directly.

The security posture is entirely delegated — no TLS, no authentication, no authorization logic at the application level. This is architecturally correct for RHOAI where kube-rbac-proxy sidecars handle auth and Gateway API handles TLS termination, but means the image must never be exposed directly without the platform ingress layer. The non-root user (UID 2000) provides basic container isolation.

The repository carries upstream vLLM artifacts (README.md, .pre-commit-config.yaml, LICENSE) from its earlier life as a source-building fork. These files are vestigial — the pre-commit config references Python/C++ source files that don't exist in this repo.
