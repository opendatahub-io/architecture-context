## Purpose

**Short**: Container image build wrapper that produces the RHOAI vLLM inference server image for AMD ROCm GPUs.

**Detailed**: vllm-rocm is a minimal downstream repository that produces a single container image for running vLLM on AMD ROCm GPUs within Red Hat OpenShift AI. The repository contains only a Konflux Dockerfile, Tekton pipeline configuration, and upstream vLLM metadata files (README, LICENSE, pre-commit config).

The Dockerfile extends the RHAIIS (Red Hat AI Inference Server) product image `registry.redhat.io/rhaiis/vllm-rocm-rhel9`, which already contains the complete vLLM runtime with ROCm acceleration libraries. This repository's Dockerfile adds only configuration: environment variables for the gRPC and HTTP ports, a non-root user, the TGIS adapter entrypoint, and Red Hat container labels.

The resulting image serves LLM inference requests via two protocols: an OpenAI-compatible HTTP API on port 8000 and a TGIS (Text Generation Inference Server) gRPC adapter on port 8033. It is deployed as the serving runtime container within KServe InferenceService pods on OpenShift clusters with AMD Instinct GPUs.

## Architectural Analysis

The vllm-rocm repository is an extreme example of a "thin wrapper" pattern — the entire repository consists of a single 25-line Dockerfile, Tekton pipeline configuration, and upstream metadata files. All substantive software (vLLM, the TGIS adapter, ROCm libraries, Python runtime) lives in the RHAIIS base image `registry.redhat.io/rhaiis/vllm-rocm-rhel9:${RHAIIS_VERSION}`. This architectural decision pushes all build complexity and dependency management to the RHAIIS/AIPCC build pipeline, leaving this repository responsible only for configuration layering.

The Dockerfile's contribution is limited to: (1) setting environment variables for port configuration and a vLLM-specific optimization flag (`DISABLE_LOGPROBS_DURING_SPEC_DECODING=false`), (2) switching to a non-root user (UID 2000), (3) defining the ENTRYPOINT as the TGIS adapter, and (4) applying Red Hat container labels. Notably, no packages are installed, no files are copied, and no build stages exist beyond the single FROM. The version of the base image is controlled by the `RHAIIS_VERSION` build arg, currently defaulting to `3.2.1`.

The dual-protocol serving pattern (OpenAI HTTP on port 8000 + TGIS gRPC on port 8033) is significant. The TGIS adapter bridges the vLLM engine to the TGIS protocol used by Caikit and other Red Hat AI components, enabling backward compatibility with existing model serving infrastructure. The HTTP API provides the OpenAI-compatible interface expected by newer clients. Both protocols run in a single process via the `vllm_tgis_adapter` module.

The Tekton pipeline configuration (`.tekton/vllm-rocm-pull-request.yaml`) reveals that builds run non-hermetically (`hermetic: false`), use extended timeouts (8h pipeline, 4h per task) reflecting the heavyweight nature of GPU container builds, and target only `linux-extra-fast/amd64` architecture. The pipeline references `konflux-central` for the shared multi-arch container build pipeline definition, and the `.tekton/` directory is auto-synced from that central repository.

A key architectural risk is the tight coupling to the RHAIIS base image version. The `RHAIIS_VERSION` arg creates a single point of control for the entire runtime stack — changing it pulls in a new vLLM version, new ROCm libraries, and potentially new Python packages. There is no intermediate layer to decouple vLLM version from ROCm version from Python environment, which simplifies operations but limits flexibility for targeted updates.
