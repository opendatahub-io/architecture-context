## Purpose

**Short**: Preflight validation tool for GPU/RDMA-capable Kubernetes clusters, verifying hardware readiness, network bandwidth, RDMA connectivity, and required CRDs/operators before AI workload deployment.

**Detailed**: RHAII Cluster Validation is a kubectl plugin (`kubectl rhaii-validate`) and container-based agent that performs comprehensive preflight checks on Kubernetes clusters intended for AI/ML inference and training workloads. It validates GPU availability (NVIDIA and AMD), driver versions, ECC memory status, RDMA device topology (InfiniBand and RoCE), cross-node TCP bandwidth and latency, RDMA bandwidth (per-device and whole-endpoint), and pairwise RDMA connectivity via a full-mesh pingmesh test.

The tool operates in a controller-agent architecture: the controller runs locally under the user's kubeconfig and orchestrates validation by deploying Kubernetes Jobs onto GPU nodes. Each Job runs the validator agent in a privileged container to access GPU and RDMA hardware directly via sysfs and vendor CLI tools (nvidia-smi, rocm-smi, ibstat, ibv_devices). Multi-node bandwidth and connectivity tests use a separate tools image containing iperf3 and perftest (ib_write_bw, ibv_rc_pingpong) compiled with CUDA support.

The tool auto-detects the cloud platform (OpenShift, AKS, EKS, CoreWeave) and loads platform-specific configuration with tunable thresholds for bandwidth, latency, and driver versions. Results are stored in a ConfigMap for persistence and output as structured JSON or human-readable tables. It also validates platform dependencies — required CRDs (Gateway API, InferencePool, LeaderWorkerSet, cert-manager) and operators (cert-manager, Istio, LeaderWorkerSet) — ensuring the cluster meets RHOAI infrastructure prerequisites.

## Architectural Analysis

The RHAII Cluster Validation tool employs a **controller-agent split architecture** where the controller (running locally under the user's kubeconfig) orchestrates all Kubernetes API interactions, while agent pods on GPU nodes have zero API access. This is an intentional security design: the ClusterRole bound to the ServiceAccount has empty rules, and `automountServiceAccountToken: false` is set on all Job pods. The only reason the ServiceAccount exists is as an OpenShift SCC subject for privileged container access. This pattern minimizes the blast radius of a compromised validation pod — it can access local GPU/RDMA hardware but cannot escalate to Kubernetes API operations.

The tool implements a **multi-phase validation pipeline** with dependencies between phases: Tier 1 (API-level CRD and operator health checks) runs without any Jobs, Tier 2 (per-node GPU and RDMA topology checks) deploys Jobs to each GPU node, and Tier 3 (multi-node bandwidth and connectivity tests) depends on topology data from Tier 2 to determine GPU-NIC pairings and test configurations. The topology-driven job expansion is particularly sophisticated — it discovers the GPU-NIC-NUMA-PCIe topology on each node, selects a pairing strategy (NUMA affinity, PCIe distance, or measured loopback bandwidth), then expands bandwidth tests per GPU-NIC pair rather than per node. For flat PCIe topologies (common on cloud instances), it deploys an additional loopback bandwidth probe phase that measures actual GPU-NIC throughput and replaces the topology-based pairing with bandwidth-optimal assignments.

The pingmesh connectivity test uses a **round-robin tournament scheduling algorithm** to test all N-choose-2 node pairs efficiently. Disjoint pairs are scheduled concurrently in each round, maximizing parallelism while avoiding resource contention. Failed pairs are retried up to a configurable number of attempts, with results merged across attempts — a pair that succeeds on any attempt is considered passing. Failures are persisted to a dedicated ConfigMap with per-NIC-pair granularity, enabling detailed post-mortem analysis.

The **platform auto-detection** system reads Kubernetes node labels and provider IDs to identify the cloud environment, then loads platform-specific defaults for thresholds, resource requests, RDMA configuration, and operator namespaces. This is layered: embedded defaults → platform-specific YAML → optional ConfigMap override, with each layer partially merging over the previous one. The design supports heterogeneous environments where different node pools may have different hardware configurations.

A notable security trade-off: all validation pods run as **privileged containers** (`securityContext.privileged: true`) because GPU topology discovery requires direct access to sysfs (`/sys/class/infiniband/`, `/sys/bus/pci/devices/`), RDMA operations need `/dev/infiniband` access, and vendor CLI tools (nvidia-smi, ibstat) require elevated permissions. The `readOnlyRootFilesystem: true` constraint on check pods provides defense in depth. The universal toleration (`operator: Exists`) on all pods ensures scheduling succeeds on GPU nodes with arbitrary taints — the node selector on `kubernetes.io/hostname` is the actual scheduling constraint.
