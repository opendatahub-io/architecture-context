## Purpose

**Short**: kubectl plugin for validating GPU cluster readiness for AI/ML workloads by checking GPU hardware, RDMA connectivity, and cross-node network bandwidth.

**Detailed**: RHAII Cluster Validation is a preflight validation tool that runs on GPU clusters before deploying AI inference workloads. It ships as a kubectl plugin (`kubectl rhaii-validate`) and as a container image that can be run via podman. The tool auto-detects the target platform (AKS, EKS, CoreWeave, OpenShift), GPU vendor (NVIDIA/AMD), and cluster topology, then runs a series of validation checks.

The tool orchestrates validation by creating Kubernetes Jobs on GPU nodes. Per-node checks run privileged containers that access host hardware via `chroot /host` to validate GPU drivers, ECC memory errors, and GPU-NIC NUMA topology. Multi-node bandwidth tests use ring or star topologies with iperf3 (TCP) and ib_write_bw (RDMA) to measure cross-node bandwidth. RDMA connectivity is tested via ibv_rc_pingpong in a pairwise mesh across all GPU nodes. Results are stored in a ConfigMap as a structured JSON report.

The tool ships two container images: a validator image containing the Go binary with CLI commands and per-node check logic, and a tools image containing RDMA/network testing utilities (iperf3, perftest with CUDA support) used as workload containers for bandwidth Jobs.

## Purpose

**Short**: kubectl plugin that validates GPU and RDMA network readiness on OpenShift AI clusters by deploying per-node check Jobs, collecting structured results, and reporting cluster readiness status.

**Detailed**: rhaii-cluster-validation is a Go CLI tool distributed as a kubectl plugin (`kubectl rhaii-validate`) that performs multi-tier hardware and network validation for RHOAI GPU clusters. It uses a Controller pattern (not controller-runtime — pure client-go) to orchestrate ephemeral Kubernetes Jobs across GPU nodes. Tier 1 checks verify CRD presence and operator health via the Kubernetes API. Tier 2 deploys per-node Jobs that run inside privileged pods to inspect GPU driver versions, ECC status, RDMA device availability, NIC link status, and GPU-NIC PCIe/NUMA topology. For flat-topology nodes (no PCIe affinity), an intra-host loopback bandwidth probe measures all GPU×NIC combinations to determine optimal pairings. Tier 3 runs cross-node RDMA connectivity (pingmesh) and bandwidth tests (ib_write_bw) in ring or star topologies. Results are aggregated into a JSON report stored in a ConfigMap (`rhaii-validate-report`) and printed as a readiness assessment (READY / READY with warnings / NOT READY). The tool supports NVIDIA and AMD GPUs, InfiniBand and RoCE RDMA fabrics, and platform-specific configuration via an embedded config with user overrides.

RHAII Cluster Validation follows a controller-agent architecture where the CLI binary serves dual roles: as an orchestration controller (when invoked by the user) and as a per-node agent (when running inside Jobs it creates). The `run` hidden subcommand is the agent entry point — it executes GPU, RDMA, and topology checks directly on the scheduled node, writing structured JSON to stdout and progress to stderr. The controller parses pod logs to collect results. This two-stream output design (JSON on stdout, progress on stderr) enables the controller to reliably parse structured results without interference from human-readable progress messages.

The job runner subsystem implements three test topologies: ring (each node tested as both sender and receiver in sequential pairs), star (one server, all clients), and pairwise (N-choose-2 round-robin tournament for RDMA connectivity). The pairwise scheduler ensures disjoint pairs within each round to avoid GPU/RDMA resource conflicts when running concurrent tests. Each bandwidth job follows a server-first lifecycle: the controller creates the server Job, waits for its pod IP, then creates client Jobs that connect to that IP. This avoids race conditions between server readiness and client connection attempts, with a 3-second delay after pod IP assignment for the listening process to start.

GPU-NIC pairing is one of the most sophisticated subsystems, implementing four strategies based on hardware topology. On bare metal with clear PCIe hierarchy, PCIe distance pairing finds the shortest-path GPU-NIC assignment. On VMs with flat NUMA topology (all devices report NUMA -1), the system falls back to NUMA affinity or bandwidth probing — the latter runs loopback ib_write_bw tests across the full GPU×NIC matrix and uses measured bandwidth to greedily assign optimal pairs. This is critical for RDMA performance: a mismatched GPU-NIC pair can degrade bandwidth by 50% or more due to cross-NUMA PCIe traffic.

Security is deliberately minimal but carefully considered. All workload pods disable ServiceAccount token mounting (`automountServiceAccountToken: false`) since they never call the Kubernetes API — they are pure compute/test containers. The validator ServiceAccount's ClusterRole is intentionally empty; it exists only as an SCC subject on OpenShift. The actual Kubernetes API calls are made by the CLI binary using the invoking user's kubeconfig credentials, not the ServiceAccount. Privileged containers are used only where hardware access requires it (RDMA device access, GPU sysfs queries, chroot /host for host tools). Device name validation via regex (`^[a-zA-Z0-9][a-zA-Z0-9_-]*$`) prevents argument injection through RDMA device names that could start with `-`.

The CRD validation subsystem is notable for its version comparison sophistication. It supports both Kubernetes API version ordering (v1alpha1 < v1beta1 < v1) and semver comparison with pre-release handling (v1.4.0-rc1 < v1.4.0). CRD version requirements include a fallback name mechanism to handle API graduation (e.g., InferencePool moving from `inference.networking.x-k8s.io` to `inference.networking.k8s.io`). Release versions are extracted from CRD annotations via JSONPath expressions, enabling validation of the specific bundle version installed rather than just the API version served.

## Architectural Analysis

rhaii-cluster-validation is architecturally a **client-side orchestrator** — it has no long-running server component, no CRDs, no webhooks, and no inbound network surface. Its entire interaction with the cluster is through the Kubernetes API as a privileged client.

The Controller struct (`pkg/controller/controller.go`) is not a controller-runtime reconciler but a procedural orchestration engine. The `Run()` method (line 424) executes a fixed nine-step lifecycle: cleanup previous runs, ensure namespace, ensure RBAC, detect platform and create config, run CRD/operator health checks, discover GPU nodes, deploy per-node GPU check Jobs, deploy per-node RDMA node check Jobs (with optional bandwidth probe for flat topologies), run cross-node pingmesh and bandwidth tests, then aggregate and report. Each step is sequential and blocking — there is no watch/reconcile loop.

The tool's RBAC footprint is deliberately narrow: it can read nodes and CRDs, manage pods and jobs in its own namespace, and read pod logs. The `system:openshift:scc:privileged` ClusterRoleBinding (created at runtime for OpenShift clusters, line 2510-2533) grants the validation Job pods access to host devices (`/dev/infiniband/*`, GPU devices) and host filesystem (`/host` chroot) needed for hardware inspection. This is a significant privilege escalation scoped to the `rhaii-validation` namespace.

GPU vendor detection (line 778-835) uses a two-stage strategy: first label-based discovery (`nvidia.com/gpu.present=true` or `amd.com/gpu.present=true`), then fallback to scanning node allocatable resources. This determines the GPU resource name used in Job resource requests, ensuring the container runtime (e.g., NVIDIA Container Toolkit) injects the correct device libraries.

The bandwidth probe subsystem (line 1189-1332) is notable: when RDMA node checks detect a flat PCIe topology (no NUMA affinity between GPUs and NICs), the tool deploys additional privileged Jobs that run `ib_write_bw` loopback tests for every GPU×NIC combination. Results are parsed to determine bandwidth-optimal GPU-NIC pairings, replacing the default NUMA-affinity strategy. This is a computationally expensive operation (potentially N_GPUs × N_NICs tests per node) with configurable timeouts and a 15-minute floor.
