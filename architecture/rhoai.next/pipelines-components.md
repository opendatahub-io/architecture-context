## Purpose

**Short**: Centralized library of reusable Kubeflow Pipelines (KFP) components and managed pipelines for AI/ML workflows including fine-tuning, AutoML, AutoRAG, evaluation, data processing, and model deployment.

**Detailed**: The pipelines-components repository is the official Kubeflow Pipelines Components library used by Red Hat OpenShift AI (RHOAI). It provides a structured collection of Python-based KFP v2 components organized into four functional categories: data processing, training, evaluation, and deployment. Components are packaged as `@dsl.component` or `@dsl.container_component` decorators and execute as containerized tasks within Kubeflow Pipelines.

The repository produces three Konflux container images: `odh-pipelines-components` (the core init container that stages managed pipeline YAMLs for the KFP API server), `odh-automl` (AutoGluon-based AutoML training runtime), and `odh-autorag` (automated RAG pipeline runtime with Docling text extraction). Managed pipelines are pre-compiled Python pipeline definitions that are shipped as YAML specifications and loaded by the KFP API server at startup, enabling one-click pipeline execution from the RHOAI dashboard.

The component library covers the full ML lifecycle: dataset download from HuggingFace/S3/HTTP, synthetic data generation via SDG Hub, distributed PDF processing via RayJobs, fine-tuning with LoRA/OSFT/SFT backends via Kubeflow Trainer, model evaluation with lm-eval and Eval Hub, model registration to Kubeflow Model Registry, and model deployment via KServe InferenceServices with vLLM serving.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Pipeline ServiceAccount RBAC, per-namespace SA token | Kubernetes RBAC | Model Registry uses insecure HTTP with no auth — any pod that can reach the registry can register models |
| Data storage | Per-namespace PVC, per-namespace S3 credentials via Secrets | Kubernetes (Secret scoping), S3 server (bucket ACLs) | S3 credentials scoped to Secret but bucket ACLs managed externally |
| Network traffic | KFP task pods run in user namespace, subject to namespace NetworkPolicy | Kubernetes / Platform | Milvus connections may cross namespaces without NetworkPolicy enforcement |
| Compute & resources | KFP pipeline resource requests/limits defined per component (CPU, memory, GPU) | Kubernetes scheduler | No ResourceQuota enforcement within the components themselves |
| Configuration & secrets | Per-namespace Kubernetes Secrets for credentials (S3, HF, OGX, LLM) | Kubernetes | Secrets must be pre-created in each namespace by users/operators |
| API scoping | Pipeline SA reads own namespace; KServe resources scoped to pipeline namespace | Kubernetes RBAC | Eval Hub uses X-Tenant header for tenant scoping — relies on Eval Hub server to enforce |

## Architectural Analysis

The pipelines-components repository follows a modular, category-based architecture where each KFP component is a self-contained Python function decorated with `@dsl.component`. Components are grouped into four functional categories (data processing, training, evaluation, deployment) and composed into higher-level pipelines. This design enables maximum reuse — the same `dataset_download` component is used by all three fine-tuning pipelines (LoRA, OSFT, SFT), and the same `model_deployment` component serves both the RAG pipeline and standalone deployment workflows.

A significant architectural pattern is the **managed pipeline compilation flow**. The init container (`odh-pipelines-components`) runs `generate_managed_pipelines.py` which discovers pipelines with `managed: true` in their `metadata.yaml`, compiles them using the KFP compiler, and writes the resulting YAML specifications to a shared volume. The KFP API server then loads these at startup, making them available as one-click pipelines in the RHOAI dashboard. This decouples pipeline authoring (Python) from pipeline delivery (YAML staging), and the `RELATED_IMAGE_*` environment variables enable operator-controlled image substitution without recompiling pipelines.

The **fine-tuning stack** (LoRA, OSFT, SFT) uses a shared architecture pattern: all three variants share common utility modules (`data.py`, `training.py`, `setup.py`, `output.py`) for dataset resolution, Kubernetes initialization, training orchestration via the Kubeflow Trainer API, and model persistence. The key differentiator is the training backend — Unsloth for LoRA (single-node, with post-training adapter merge), mini-trainer for OSFT (multi-node FSDP), and instructlab-training for SFT (multi-node FSDP). The shared `wait_for_training_job()` function provides a common job monitoring pattern with log streaming and timeout handling.

The **AutoML and AutoRAG subsystems** represent two distinct managed pipeline families, each with their own container image and runtime dependencies. AutoML uses AutoGluon for tabular and time series model training with a two-stage selection-then-refit pattern that optimizes for evaluation metric quality. AutoRAG uses the ai4rag SDK for document-to-RAG-pipeline optimization, with a 6-stage pipeline (test data → discovery → extraction → indexing → search space → optimization) that explores chunking, embedding, and retrieval configurations. Both subsystems include `ComponentStatusTracker` for per-stage progress tracking, though they use different implementations (AutoML uses direct class instantiation; AutoRAG uses embedded artifact loading via importlib).

A security concern worth noting is the `verify=False` SSL fallback in the AutoML S3 client code. When the initial boto3 connection fails with an SSL error (common with self-signed MinIO certificates), the component retries with TLS verification disabled. This works in development clusters but bypasses certificate validation in production, which is a FIPS compliance gap. Additionally, the Model Registry integration uses insecure HTTP (`ModelRegistry(server_address, port)` without TLS), meaning model registration traffic is unencrypted within the cluster network. Both patterns should be hardened for production deployments.
