## Purpose

**Short**: A collection of reusable Kubeflow Pipelines components and pre-compiled managed pipelines for AI/ML workflows (training, evaluation, data processing, deployment) on Red Hat OpenShift AI.

**Detailed**: pipelines-components is the centralized repository for Kubeflow Pipelines (KFP) components and pipelines that ship as part of RHOAI. The repository is organized into four component categories — data processing, training, evaluation, and deployment — each containing KFP `@dsl.component`-decorated Python functions that execute as individual pipeline steps. These components handle tasks such as dataset downloading from multiple sources (HuggingFace, S3, HTTP), synthetic data generation (SDG), document parsing and chunking, model fine-tuning (SFT, LoRA, OSFT, LoRA-GRPO), model evaluation (lm-eval, EvalHub), and model deployment via KServe InferenceService CRs.

The repository produces four container images via Konflux Dockerfiles. The primary image (`pipelines-components`) functions as an init container for the KFP API server: at build time it compiles managed pipelines (those with `managed: true` in their `metadata.yaml`) into KFP YAML specs, and at runtime it copies these pre-compiled artifacts to a shared volume mounted by the API server. When `RELATED_IMAGE_*` environment variables are present (injected by DSPO), the init container recompiles pipelines at startup to substitute the correct downstream image references. Three additional images — `automl`, `autorag`, and `autorag-inference` — package specialized pipeline-specific dependencies built on AIPCC base images for AutoML (AutoGluon), AutoRAG (document processing with Docling, RAG optimization), and AutoRAG inference workloads respectively.

## Architectural Analysis

The architecture of pipelines-components follows the KFP component model: each component is a standalone Python function decorated with `@dsl.component`, packaged with its own base image and dependency requirements. Components communicate through KFP artifact passing (Input/Output datasets, models, metrics) and shared PVC storage rather than direct network calls. This design enables components to be composed into pipelines at compile time and execute as isolated Kubernetes pods at runtime.

A notable architectural decision is the dual-mode init container pattern. The `Dockerfile.konflux.pipelines-components` image pre-compiles managed pipeline YAML at build time using `generate_managed_pipelines`, embedding the compiled artifacts in the image. At runtime, `init_managed_pipelines` checks for `RELATED_IMAGE_*` environment variables — if present, it recompiles from source to inject operator-provided image overrides; otherwise, it simply copies the pre-built artifacts. This enables the Data Science Pipelines Operator (DSPO) to control runtime images without rebuilding the component image.

The deployment components (`model_deployment`, `deploy_embedding_model`, `evalhub_evaluator_kserve`) demonstrate tight integration with the RHOAI platform: they programmatically create KServe `ServingRuntime` and `InferenceService` custom resources using the Kubernetes Python client, matching the RHOAI dashboard deployment pattern including HardwareProfile annotations and opendatahub.io labels. These components use in-cluster service account authentication and properly validate TLS certificates via the mounted CA bundle.

The AIPCC-based images (automl, autorag, autorag-inference) use the RHEL AI Python Package Index for hermetic dependency resolution, while the main pipelines-components image uses a UBI9 Python base with `pip install` from the standard index. Pipeline-specific `requirements.txt` files are Hermeto-compatible (hash-pinned with `--index-url` pointing to the AIPCC package index), generated via the `scripts/refresh_pipeline_requirements` tooling.
