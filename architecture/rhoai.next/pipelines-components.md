## Purpose

**Short**: A centralized library of reusable Kubeflow Pipelines components and pre-composed pipelines for AI/ML workflows (training, evaluation, data processing, deployment) shipped as container images for Red Hat OpenShift AI.

**Detailed**: The pipelines-components repository provides the `kfp-components` Python package — a structured collection of KFP v2 pipeline components and pre-composed pipelines covering the full AI/ML lifecycle. Components are organized into four categories: **Training** (LoRA/SFT/OSFT fine-tuning via Training Hub, AutoGluon tabular/timeseries AutoML, AutoRAG optimization), **Evaluation** (lm-eval harness, Eval Hub via KServe), **Data Processing** (dataset download, synthetic data generation, PDF parsing/chunking via Ray+Docling, vector embedding into Milvus, AutoRAG document indexing via OGX), and **Deployment** (KServe InferenceService creation, Model Registry registration, embedding model deployment).

The repository produces three container images via Konflux: (1) `odh-pipelines-components` — an init container that generates compiled pipeline YAML files and stages them for the KFP API server to register as managed pipelines; (2) `odh-automl` — a runtime image based on AIPCC CPU base images containing the kfp-components wheel plus AutoGluon and its dependencies for AutoML pipeline execution; (3) `odh-autorag` — a runtime image based on AIPCC CPU base images containing ai4rag, Docling, and bundled Docling modelcar artifacts for AutoRAG pipeline execution. The init container is deployed as a sidecar to the Data Science Pipelines Operator (DSPO) and supports runtime RELATED_IMAGE overrides for container image substitution in air-gapped environments.

## Architectural Analysis

The pipelines-components repository follows a **library-first** architecture where Python components are defined as KFP v2 `@dsl.component` decorated functions, each packaged with standardized metadata (`metadata.yaml`), documentation, and tests. Pipelines compose these components declaratively using `@dsl.pipeline` decorators with typed parameters. This structure enables both standalone component use and pre-composed "managed pipelines" that are automatically compiled and registered by the init container.

A significant architectural pattern is the **dual execution model**: components specify their `base_image` at definition time (e.g., `AUTOML_IMAGE`, `RAY_RAG_BASE_IMAGE`), meaning the component code runs inside a purpose-built container during pipeline execution, not inside the init container. The init container only needs to compile pipeline definitions to YAML — it never runs the actual workloads. This separation allows the init container to be lightweight (UBI9 + kfp) while runtime images can be large and domain-specific (AutoGluon at ~4GB, Docling models at ~1GB).

The **RELATED_IMAGE mechanism** is a critical design pattern for RHOAI disconnected/air-gapped deployments. When DSPO sets `RELATED_IMAGE_*` environment variables on the init container, the `should_recompile_managed_pipelines()` function detects them and triggers a full recompilation from source, substituting container image references in the compiled YAML. This allows operators to override default image references with private registry mirrors without modifying the component code.

The fine-tuning pipeline family (LoRA, SFT, OSFT) demonstrates a well-factored **shared utilities pattern** via `components/training/finetuning/shared/`. Common concerns — Kubernetes client initialization, dataset resolution (supporting HuggingFace, S3, HTTP, OCI), training job lifecycle management, and metrics extraction — are centralized in helper modules. Each training variant (LoRA via unsloth, SFT via instructlab-training, OSFT via mini-trainer) differs only in its backend-specific parameters and `select_runtime()` call. The "minimal" pipeline variants hardcode safe defaults to reduce the parameter surface for users who don't need fine-grained control.

The AutoML and AutoRAG subsystems represent a **delegation pattern** where thin KFP component wrappers call into external libraries (AutoGluon, ai4rag). The AutoRAG components in particular use KFP's `embedded_artifact_path` feature to bundle the `component_status.py` tracker module into the component, avoiding workspace dependencies. The `component_stage_map_publisher` components in both AutoML and AutoRAG publish structured JSON manifests that drive dashboard progress visualization — a pattern for connecting pipeline execution state to platform UI.

Build hermeticity is enforced at the Python layer through hash-pinned requirements.txt files generated by `uv pip compile` against the RHEL AI Python Package Index. The `make pipeline-requirements` target automates regeneration using container-based resolution to ensure platform-accurate dependency resolution. However, RPM-level lock files (`rpms.lock.yaml`) and Hermeto/cachi2 prefetch integration are absent on this branch, representing a gap in full build hermeticity.
