## Purpose

**Short**: LMEval provides a secure, batch-oriented execution environment for language model evaluations using the lm-evaluation-harness framework, integrated with EvalHub for orchestrated benchmark execution.

**Detailed**: LM Evaluation Harness is a downstream fork of EleutherAI's lm-evaluation-harness, adapted for Red Hat OpenShift AI's TrustyAI evaluation pipeline. The component is deployed as a Kubernetes Job image (`odh-ta-lmes-job`) that receives a job specification from EvalHub, executes one or more LLM benchmarks against an OpenAI-compatible model endpoint, and reports results back via callbacks and OCI artifact persistence.

The adapter layer (`main.py`) wraps the upstream lm-eval `simple_evaluate()` function with EvalHub integration: it reads a job spec JSON from a mounted ConfigMap (`/meta/job.json`), resolves model credentials from Kubernetes secrets, configures the `local-completions` backend to call the model's OpenAI-compatible API, runs the benchmark, and reports status updates through EvalHub's callback protocol. Results are persisted as OCI artifacts via `skopeo` and optionally logged to MLflow.

The component supports air-gapped (disconnected) operation by auto-detecting when a tokenizer and dataset files are pre-staged under `/test_data`, automatically enabling Hugging Face offline mode. It includes Unitxt framework integration for custom evaluation tasks and supports over 200 built-in benchmark task configurations across multilingual, reasoning, safety, and domain-specific categories.

## Architectural Analysis

The lm-evaluation-harness component follows a clean adapter pattern: the upstream EleutherAI library provides the evaluation engine while a thin adapter layer (`main.py`, ~998 lines) bridges it to the RHOAI platform's EvalHub orchestration system. This separation means the evaluation logic itself is well-tested upstream open source code, while the platform integration is a focused ~600-line adapter that handles credential resolution, job lifecycle callbacks, error classification, and result persistence.

The adapter's credential handling is security-conscious. The `_sanitize_error_message()` function (lines 271-315) implements multi-layered secret redaction — stripping Authorization headers, key=value pairs, JSON-encoded secrets, URL userinfo, query parameters, and fragments before any error text reaches EvalHub callbacks. The job spec path is validated against a `/meta` root to prevent path traversal (CWE-22). Model credentials are resolved through the eval-hub-sdk's auth module rather than direct environment variable access.

The air-gapped operation pattern is architecturally notable. Rather than requiring an explicit `offline` flag, the adapter auto-detects disconnected clusters by examining whether `parameters.tokenizer` points to a local path under `/test_data` and whether co-located dataset directories contain `dataset_dict.json` files. This heuristic approach (`_infer_auto_offline_from_local_test_data`, lines 165-201) reduces configuration burden for air-gapped deployments. When detected, it sets six Hugging Face environment variables to prevent any outbound Hub calls.

The multi-architecture build strategy in `Dockerfile.konflux.lmes-job` is complex but necessary. PyTorch and Apache Arrow lack pre-built wheels for s390x and ppc64le, requiring from-source compilation in dedicated build stages (stages 2-4). OpenBLAS is also built from source for ppc64le. The `TARGETARCH` build argument drives conditional compilation — x86_64 and arm64 use pre-built wheels from PyPI, while s390x and ppc64le trigger the full source builds. This adds significant build time but ensures the same evaluation capabilities across all supported architectures.

The component's model interaction architecture is extensible but primarily uses the `local-completions` backend for RHOAI. The `build_lmeval_config()` function (lines 514-598) always configures OpenAI-compatible endpoint mode with a HuggingFace tokenizer for prompt encoding. This means the evaluation job connects to an already-deployed model serving endpoint (vLLM, TGI, or similar) rather than loading model weights directly — a clean separation that keeps the evaluation job lightweight and CPU-only while the model runs on GPU infrastructure.
