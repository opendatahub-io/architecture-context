## Purpose

**Short**: LMEval is a secure, batch-oriented execution environment for language model evaluations using the lm-evaluation-harness framework, integrated with the EvalHub platform.

**Detailed**: This component packages the EleutherAI lm-evaluation-harness library into a production-grade container image (`odh-ta-lmes-job-rhel9`) that runs as a Kubernetes batch job. It serves as the evaluation framework adapter for EvalHub -- Red Hat's model evaluation platform -- providing a standardized runtime for executing language model benchmarks against OpenAI-compatible inference endpoints.

The adapter (`main.py`) bridges EvalHub's job specification format with lm-evaluation-harness's `simple_evaluate()` API. It receives a `JobSpec` JSON file (mounted at `/meta/job.json`) containing the model endpoint URL, benchmark ID, evaluation parameters (few-shot count, batch size, concurrency), and output configuration. The adapter resolves model credentials, configures the evaluation backend (`local-completions`), executes the benchmark, and reports structured results back to EvalHub via callbacks. Results can optionally be persisted as OCI artifacts and logged to MLflow.

The container image supports multi-architecture builds (x86_64, ARM64, ppc64le, s390x) with architecture-specific compilation of PyTorch, PyArrow, and OpenBLAS. It includes over 200 built-in benchmark tasks (MMLU, HellaSwag, ARC, GPQA, IFEval, etc.) plus Unitxt framework integration for custom evaluation catalogs. An air-gapped mode auto-detects local test data and disables HuggingFace Hub connectivity for disconnected cluster deployments.

## Purpose

**Short**: A pluggable Python framework for evaluating language models against standardized benchmarks, used in RHOAI as the evaluation engine launched by the TrustyAI LMEval operator.

**Detailed**: lm-evaluation-harness is a CLI-driven Python application that evaluates language model quality across hundreds of benchmark tasks (MMLU, GSM8K, HellaSwag, etc.). It operates as a batch job with no persistent inbound API surface — it is invoked via `lm_eval` CLI entry point, sends prompts to configured LLM backends, collects completions, scores them against reference answers, and writes structured results to local files or HuggingFace Hub. The framework supports multiple LLM provider backends through a pluggable model registry including local HuggingFace transformers, OpenAI API, Anthropic API, and IBM WatsonX AI. Each backend authenticates to its respective external API using provider-specific API keys supplied through environment variables. In RHOAI, this component runs as a containerized Job orchestrated by the TrustyAI LMEval operator; it has no internal platform dependencies and communicates only outbound to external LLM inference endpoints and dataset servers.

## Data Flows

- **Evaluation request flow:** The CLI entry point (`lm_eval/__main__.py`) parses arguments, instantiates a `TaskManager` to load benchmark task definitions, and delegates to `evaluator.simple_evaluate()`. - **LLM backend communication:** Each model backend (Anthropic, OpenAI, WatsonX, local HuggingFace) authenticates to its external API using environment-variable-sourced credentials, sends prompt payloads over HTTPS, and receives completion responses. ## Architectural Analysis

The lm-evaluation-harness adapter follows a clean adapter pattern that decouples the EvalHub platform orchestration from the evaluation framework internals. The `LMEvalAdapter` class extends `FrameworkAdapter` and translates between EvalHub's `JobSpec` format and lm-eval's `simple_evaluate()` API. This separation means the adapter can be updated independently of the upstream lm-eval library, and the evaluation framework's extensive task catalog is available without modification.

The codebase implements a defense-in-depth security model for credential handling. The `_sanitize_error_message()` function (main.py:271-315) applies three layers of regex-based redaction before any error text reaches EvalHub callbacks: Authorization headers, key=value pairs for known secret names, and JSON-style credential objects. Path traversal protection (CWE-22) restricts job spec file access to the `/meta` directory. The model API key is never stored in the container image -- it flows from Kubernetes Secrets through `resolve_model_credentials()` to `OPENAI_API_KEY` at runtime.

The air-gapped deployment model is architecturally significant. Rather than requiring an explicit `offline` flag, the adapter auto-detects disconnected environments by checking whether `parameters.tokenizer` points to a local path under `/test_data` and whether dataset files (`dataset_dict.json`) are co-located there. When detected, it sets six HuggingFace environment variables to disable all network access to `huggingface.co`, enabling evaluation on clusters with no internet connectivity. This design means the same container image works in both connected and air-gapped environments without configuration changes.

The multi-architecture build strategy is notable for its complexity. The Konflux Dockerfile uses a 5-stage multi-stage build to handle architectures where pre-built Python wheels are unavailable: PyArrow is compiled from source for ppc64le and s390x (with an s390x-specific parquet patch), PyTorch is compiled from source for both architectures, and OpenBLAS is compiled for ppc64le. The final stage conditionally installs these architecture-specific wheels alongside the standard pip dependencies. This approach enables the same evaluation harness to run on IBM Power, IBM Z, ARM, and x86 hardware.

The evaluation pipeline itself delegates model inference to the `local-completions` backend, which sends string prompts (not token IDs, via `tokenized_requests=False`) to an OpenAI-compatible `/v1/completions` endpoint. This means the component never loads model weights -- it functions as a client-side evaluation harness. The `num_concurrent` parameter (capped at 128) controls async request parallelism via `aiohttp` with `TCPConnector` connection pooling and `tenacity` exponential backoff retries. The component runs on CPU only (`device="cpu"` is hardcoded in main.py:739), since it only needs the tokenizer, not the model.

## Architectural Analysis

The lm-evaluation-harness is architecturally a stateless batch-processing CLI application rather than a long-running service. It has no inbound API surface — no HTTP endpoints, no gRPC services, no Kubernetes Services or Ingress resources. Its entire network posture is outbound: it reaches out to external LLM inference APIs and dataset servers, performs evaluation computations locally, and writes results to files or external hubs.

The model backend system uses a plugin registry pattern (`@register_model` decorator) that maps short names like `"anthropic-completions"`, `"watsonx_llm"`, `"openai-completions"`, and `"local-completions"` to concrete LM implementation classes. Each backend handles its own authentication independently — there is no shared auth middleware or centralized credential management. The Anthropic chat backend (`AnthropicChat`) inherits from `LocalCompletionsAPI` and overrides the `api_key` and `header` properties to use Anthropic-specific authentication (`x-api-key` header with version pinning), while the OpenAI backends use the standard Bearer token pattern. The WatsonX backend has the most structured credential validation (`_verify_credentials`) requiring three environment variables (`WATSONX_API_KEY`, `WATSONX_URL`, `WATSONX_PROJECT_ID`) and explicitly fails fast with guidance on which variables to set.

All API key credentials are sourced from environment variables at class instantiation time, with no support for file-based secrets, Kubernetes Secret volume mounts, or secret rotation. In a RHOAI deployment context, the TrustyAI LMEval operator is responsible for injecting these environment variables into the Job pod specification. The harness itself has no awareness of the RHOAI platform — it treats its runtime environment as opaque and communicates only with the configured external LLM endpoints. This clean separation means the harness has zero internal platform dependencies; all platform integration is handled by the orchestrating operator.

The offline evaluation mode (`HF_EVALUATE_OFFLINE=1` in `__main__.py`) is significant for air-gapped RHOAI deployments. When enabled, it monkey-patches `evaluate.load` to prepend a configurable `LMEVAL_METRICS_PREFIX` path to metric lookups, allowing metrics to be pre-staged on a local or shared filesystem rather than fetched from the internet at evaluation time.
