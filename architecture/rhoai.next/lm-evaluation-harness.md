## Purpose

**Short**: A secure, batch-oriented execution environment for standardized language model evaluation benchmarks, integrated with the EvalHub platform.

**Detailed**: lm-evaluation-harness is a Red Hat downstream fork of EleutherAI's widely adopted LM Evaluation Harness framework. It provides a unified runtime for executing over 60 standard academic benchmarks against language models served via OpenAI-compatible API endpoints. The component runs as a one-shot Kubernetes Job — not a long-lived service — receiving evaluation specifications via a mounted JSON job spec and reporting results back to EvalHub through callback URLs.

The Red Hat fork adds a significant integration layer on top of the upstream evaluation engine. The `main.py` adapter implements the `evalhub.adapter.FrameworkAdapter` interface, handling job lifecycle phases (initialization, data loading, evaluation, post-processing, artifact persistence), error classification with secret redaction, OCI artifact creation via skopeo, and automatic detection of disconnected/air-gapped cluster environments through local `/test_data` layout inspection. The adapter exclusively uses the `local-completions` backend to communicate with model inference endpoints, meaning the evaluation container itself does not load model weights — it sends prompts to an externally-hosted model server and collects completions.

The component supports multi-architecture builds (amd64 with CUDA, arm64, ppc64le, s390x) and includes extensive support for the Unitxt evaluation framework, custom task definitions, and IBM watsonx.ai integration.

## Architectural Analysis

The architecture follows a client-adapter pattern where the lm-evaluation-harness container acts as a stateless, ephemeral evaluation client. The core design decision is to decouple model hosting from model evaluation: the container ships no model weights and forces `device="cpu"` in all evaluations, relying entirely on an external model endpoint for inference. This separation keeps the evaluation image portable across architectures and avoids GPU scheduling complexity in the evaluation pod itself.

The EvalHub adapter (`main.py`) wraps the upstream `simple_evaluate()` API with production hardening: error messages are sanitized via multi-pattern regex to strip tokens, credentials, and URL fragments before being sent to the callback endpoint. The adapter implements a path-traversal guard on job spec loading (files must resolve under `/meta`), an explicit allow-list for benchmarks that require `trust_remote_code` or code execution (humaneval, mbpp), and automatic HuggingFace offline mode detection from the `/test_data` mount layout.

A notable architectural risk is the Dockerfile.konflux's use of parameterized base images (`CUDA_BASE_IMAGE`, `CPU_BASE_IMAGE`) via build args. These are expected to be AIPCC base images but the values are not pinned in the Dockerfile itself — they are supplied at build time, meaning the actual base image provenance depends on the Konflux build pipeline configuration. The non-Konflux `Dockerfile.lmes-job` uses `registry.access.redhat.com/ubi9/python-311:latest` and includes a complex multi-stage build with from-source compilation of PyTorch, Apache Arrow, and OpenBLAS for ppc64le and s390x architectures.

The recent removal of `uv` from the Konflux image (RHOAIENG-99284) reflects ongoing attention to supply chain hygiene — uv was inherited from the base image as build tooling but its bundled cryptographic libraries were flagged as unnecessary runtime dependencies.
