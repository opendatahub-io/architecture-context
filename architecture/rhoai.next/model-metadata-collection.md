## Purpose

**Short**: CLI tool and data container that collects, enriches, and catalogs AI model metadata, MCP server metadata, and agent metadata from OCI registries, HuggingFace, and GitHub for consumption by the RHOAI dashboard.

**Detailed**: The model-metadata-collection component is a Go-based metadata pipeline that produces YAML catalog files describing Red Hat AI models, MCP servers, and agent starter kits. It consists of two CLI binaries -- `model-extractor` (the primary pipeline) and `metadata-report` (a reporting tool) -- along with a data-only container image built by Konflux.

The `model-extractor` binary fetches OCI container manifests from registries (e.g., `registry.redhat.io`), extracts modelcard content from annotated OCI layers (`io.opendatahub.modelcar.layer.type: modelcard`), parses YAML frontmatter and markdown to extract structured metadata (name, provider, license, tasks, languages), then enriches this data by cross-referencing with HuggingFace APIs (model details, README frontmatter, collection indices) and OCI registry metadata (architectures, timestamps). The enriched metadata is written to `data/` as YAML catalogs (`models-catalog.yaml`, `mcp-servers-catalog.yaml`, `agents-catalog.yaml`, etc.), which are then baked into a minimal UBI9 container image via the Konflux Dockerfile.

The resulting container image is consumed as an init container or volume mount by the RHOAI dashboard and other platform components, providing a pre-built catalog of available AI models, MCP servers, and agent definitions without requiring runtime API calls.

1. **Model metadata extraction pipeline** (`model-extractor`):

   - Writes aggregated MCP servers catalog YAML

## Architectural Analysis

The model-metadata-collection component follows a "build-time enrichment, runtime static" architecture pattern. All expensive operations -- registry fetches, API calls to HuggingFace and GitHub, metadata parsing, and enrichment -- happen during the CI/CD pipeline execution. The resulting container image is intentionally inert: a UBI9-minimal base with static YAML files and no executable code. This design eliminates runtime dependencies on external services, making the catalog data available in air-gapped environments.

The metadata enrichment pipeline implements a sophisticated multi-source provenance system. Each metadata field (name, provider, description, license, etc.) tracks its data source through a `MetadataSource` type with `Value` and `Source` fields. Sources are hierarchically prioritized: `huggingface.yaml` (YAML frontmatter from HuggingFace README) takes precedence over `huggingface.api` (API response), which beats `modelcard.yaml` (container modelcard frontmatter), which beats `modelcard.regex` (regex text extraction). This provenance tracking is written to separate `enrichment.yaml` files alongside each model's `metadata.yaml`, enabling the `metadata-report` tool to generate data quality audits with per-field source attribution.

The concurrent processing model is straightforward: `processModelsInParallelWithMetadata` uses a semaphore-based goroutine pool (default 5 workers) to process models in parallel. Each worker fetches an OCI manifest, extracts modelcard layers, and writes metadata independently. The enrichment phase runs sequentially after extraction is complete, cross-referencing each registry model against HuggingFace data using a fuzzy string similarity matcher (`CalculateSimilarity`) with a 0.5 threshold, filtered by model family to prevent cross-family matches (e.g., llama container matching a granite HuggingFace entry).

The Konflux build pipeline (`.tekton/odh-model-metadata-collection-pull-reques.yaml`) builds multi-architecture images for x86_64, ppc64le, s390x, and arm64. The build uses hermetic mode with gomod prefetch, even though the `Dockerfile.konflux` only copies static data files. This ensures that any future changes that add Go binaries to the container will automatically get hermetic dependency resolution. The Dockerfile.konflux uses `ubi9-minimal` as the base, which is significantly smaller than the development Dockerfile's `ubi9-micro`, and copies all `data/*.yaml` files rather than listing them individually -- a pragmatic choice for a rapidly evolving catalog that frequently adds new file types.

The component supports three distinct catalog types -- models, MCP servers, and agents -- each with its own index format, enrichment pipeline, and output structure. The model catalog is the most complex, with OCI registry interaction, HuggingFace enrichment, tool-calling config extraction, vLLM recommended configuration injection, and model deduplication/merging. The MCP catalog focuses on OCI image architecture and timestamp enrichment. The agent catalog fetches structured metadata from GitHub repositories (agent.yaml files) and enriches with README content and template artifacts.

## Architectural Analysis

**Deployment shape:** model-metadata-collection is a batch-processing CLI tool, not a long-running service or Kubernetes operator. It has no CRDs, no inbound network services, no RBAC requirements, and no runtime pods. The two CLI commands (`model-extractor` and `metadata-report`) are invoked during CI/CD or development workflows to regenerate the curated YAML catalogs committed to the `data/` directory. This makes the component architecturally simple — its integration surface is entirely outbound (HuggingFace API and OCI registries) and its output surface is filesystem-based (YAML files consumed by downstream components).

**OCI modelcar extraction pattern:** The `model-extractor` command implements a container-image-as-data-source pattern. It uses the `containers/image/v5` library to fetch OCI manifests and layer blobs, looking for layers annotated with `io.opendatahub.modelcar.layer.type=modelcard`. The modelcard layer is a tar (optionally gzipped) containing a single Markdown file with YAML frontmatter. This pattern treats container images as structured data packages rather than executable artifacts — the tool never runs the containers, only inspects their metadata and layer contents.

**Multi-source enrichment pipeline:** Metadata is assembled from multiple sources with explicit fallback logic. Primary data comes from OCI modelcard layers. When modelcard extraction fails, the tool falls back to fetching HuggingFace README content via fuzzy name matching (using string similarity scoring with a 0.5 threshold). Additional enrichment layers include HuggingFace API model details (downloads, likes, release dates), OCI registry manifest architecture lists, and curated vLLM configuration overrides from `input/models/vllm-config/`. Each metadata field tracks its provenance via `MetadataSource` structs, enabling downstream consumers to audit data origins.

**Concurrency model:** Model processing uses a bounded-concurrency fan-out pattern with `sync.WaitGroup` and a semaphore channel (default 5 concurrent goroutines). Each goroutine independently fetches an OCI manifest, extracts modelcard content, and returns results via a results channel. The `HF_TOKEN` environment variable enables optional authenticated requests to HuggingFace for higher rate limits and access to gated models. The `.env` file loading at startup supports developer convenience without requiring shell-level environment configuration.

**MCP server catalog:** In addition to model metadata, the tool generates MCP (Model Context Protocol) server catalogs. These aggregate curated YAML input files from `input/mcp_servers/` (organized by provider: `redhat/`, `partner/`, `community/`) into a single catalog, optionally enriching each entry with OCI image architecture data from container registries. This supports the RHOAI dashboard's MCP server discovery UI.
