## Purpose

**Short**: Extracts, enriches, and aggregates metadata for Red Hat AI model catalogs, MCP server catalogs, and agent starter kit catalogs, then packages the results as static YAML data files in a container image.

**Detailed**: The model-metadata-collection component is a Go-based data pipeline that produces curated catalog YAML files consumed by the RHOAI dashboard to display model, MCP server, and agent metadata. It runs as a batch CLI tool (`model-extractor`) that pulls model card content from OCI container registries (modelcar images), enriches extracted metadata with data from HuggingFace APIs and YAML frontmatter, merges supplemental static catalog entries, and writes the results to `data/*.yaml` files. These files are checked into the repository by CI/CD and then packaged into a minimal container image (`Dockerfile.konflux`) that serves as a data sidecar.

The tool supports three distinct catalog pipelines: (1) **Models catalog** -- extracts metadata from OCI modelcar images on `registry.redhat.io`, enriches with HuggingFace model details, tool-calling configuration, vLLM recommended configs, and supplemental data; (2) **MCP servers catalog** -- reads curated MCP server input files, enriches with OCI registry architectures and timestamps; (3) **Agents catalog** -- fetches agent starter kit metadata and READMEs from GitHub repositories. A companion `metadata-report` binary generates completeness reports tracking data provenance across sources (modelcard YAML, modelcard regex, HuggingFace API/YAML/tags, registry).

The output container image is consumed by the RHOAI dashboard component, which mounts the `/app/data` volume to access the pre-generated catalog files. The component does not run as a long-lived service -- it is a build-time data generator whose artifacts are baked into a container image at rest.

## Architectural Analysis

The model-metadata-collection component follows a **batch ETL (Extract-Transform-Load) pattern** rather than a traditional service architecture. The `model-extractor` CLI orchestrates three independent catalog generation pipelines (models, MCP servers, agents), each with distinct data sources and enrichment strategies. This design choice is driven by the static nature of model metadata -- catalogs change infrequently (on model releases or curation updates), so a build-time pipeline is far more efficient than a runtime service.

The metadata enrichment pipeline implements a **multi-source priority system** with source provenance tracking. Each metadata field records its origin (e.g., `modelcard.yaml`, `huggingface.api`, `huggingface.yaml`, `huggingface.tags`, `modelcard.regex`, `generated`). HuggingFace YAML frontmatter is treated as highest priority, followed by HuggingFace API data, then modelcard text parsing via regex. This approach provides auditability -- the `enrichment.yaml` sidecar file records which source populated each field, enabling the `metadata-report` tool to generate completeness reports. The `isCompatibleModelFamily()` guard prevents cross-family matching (e.g., a Llama container matching a Granite HuggingFace entry), using centralized model family definitions from `internal/config/model_families.go`.

The **data container pattern** (Dockerfile.konflux) is architecturally unusual -- it produces an image that runs `sleep infinity` and exists solely to provide a volume mount point. This pattern is used because Kubernetes init containers or sidecar containers can mount the `/app/data` volume, allowing the RHOAI dashboard to access catalog files without embedding them directly. The Konflux build pipeline builds multi-arch images (x86_64, ppc64le, s390x, arm64) with hermetic Go module prefetching, though the Dockerfile itself performs no Go compilation -- it only copies pre-generated YAML files from the repository's `data/` directory.

A notable risk is the **dependency on external APIs during build time**. The enrichment pipeline makes HTTP calls to HuggingFace (collections, model details, READMEs) and GitHub (agent metadata) during `make process`. If these services are unavailable, the pipeline gracefully degrades (`--skip-huggingface`, `--skip-enrichment`, `--skip-agent-enrichment` flags exist for offline operation), but the resulting catalog will lack enrichment data. The CI/CD workflow (`build-and-push-static-model-catalog-data.yml`) triggers on pushes to `data/` -- meaning the enrichment pipeline runs separately and its outputs are committed to the repo before the container image is built.

The OCI image inspection code (`internal/registry/registry.go`) uses the `containers/image` library to parse Docker Registry v2 manifests, manifest lists (multi-arch), and config blobs. It implements retry logic with exponential backoff for transient registry failures. Architecture information extracted from manifest lists is stored as JSON-encoded custom properties in the catalog output, enabling the dashboard to display supported platforms per model.
