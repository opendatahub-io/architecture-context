## Purpose

**Short**: A Go-based pipeline that extracts, enriches, and catalogs AI model metadata from container registries and HuggingFace, packaging the resulting YAML catalogs into a data-only container image for consumption by the RHOAI dashboard and other platform components.

**Detailed**: model-metadata-collection is a build-time data pipeline, not a running service. It produces a container image whose sole purpose is to carry pre-generated YAML catalog files—model metadata, MCP server definitions, agent catalogs, and serving runtime configurations—into the RHOAI platform at deployment time. The container runs `sleep infinity` so that other pods (typically the dashboard or operator) can mount its data volume or copy files from it.

The pipeline operates in three phases: (1) **Discovery and extraction** — fetching OCI container manifests from Red Hat container registries, scanning layers for ModelCar modelcard annotations, and discovering validated model collections from the HuggingFace API; (2) **Enrichment** — matching registry models to HuggingFace entries via name similarity scoring, merging metadata from YAML frontmatter, README content, OCI artifact timestamps, and vLLM recommended configurations; (3) **Catalog generation** — aggregating individual model metadata into validated-models, other-models, MCP servers (Red Hat, partner, community), agents, and serving runtime catalogs. The entire extraction pipeline uses bounded parallelism (semaphore pattern, default concurrency 5) for registry operations.

The component also curates serving runtime definitions for KServe-based inference (vLLM CUDA, vLLM-Omni CUDA, vLLM ROCm) and agent starter kit metadata sourced from GitHub repositories. All catalogs follow the index/input/catalog pattern: curated index files reference individual input YAML files that are assembled into aggregate catalogs.

## Architectural Analysis

model-metadata-collection follows an unusual architectural pattern for the RHOAI platform: it is a **data container** rather than a service or operator. The image contains no running application; it uses `CMD ["sleep", "infinity"]` to keep the container alive as a data volume source. This pattern allows catalog data to be versioned and distributed alongside container image releases, decoupling catalog updates from the dashboard or operator release cycles.

The Go CLI tools (`model-extractor`, `metadata-report`, `serving-runtime-catalog`) run during CI/CD to generate catalog data that is then checked into the repository and baked into the container image. This means the container image is essentially a static data artifact—the Go tools are build-time dependencies only, never shipped in the final container.

The enrichment pipeline demonstrates a careful priority hierarchy for metadata sources: HuggingFace YAML frontmatter takes highest priority, followed by extracted modelcard.md content, HuggingFace API data, and finally registry metadata with generated defaults. This multi-source merging is key to producing high-quality catalogs from inconsistent upstream data.

The Konflux Dockerfile (`Dockerfile.konflux`) uses `ubi9/ubi-minimal-pqc` (post-quantum cryptography variant) as the base image, while the development Dockerfile uses `ubi9-micro`. Since the final image contains only static YAML files and no Go binaries, the build-time Go tools' FIPS posture is irrelevant to the deployed artifact. The data-only nature of this component means it has minimal security surface area—no network listeners, no API endpoints, no RBAC requirements.

A notable design pattern is the serving runtime catalog, which carries KServe `ServingRuntime` template definitions referencing `serving.kserve.io/v1alpha1`. These are not CRDs owned by this component; they are data payloads consumed by odh-model-controller and the dashboard to configure model serving infrastructure.
