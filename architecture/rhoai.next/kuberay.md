## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Ray clusters, jobs, services, and scheduled jobs on OpenShift and Kubernetes.

**Detailed**: KubeRay is the Kubernetes operator for the Ray distributed computing framework. It defines four Custom Resource Definitions — RayCluster, RayJob, RayService, and RayCronJob — that allow users to declaratively manage Ray workloads. The operator handles pod lifecycle, autoscaling, network exposure, mutual TLS, and authentication for Ray clusters.

In the RHOAI distribution, KubeRay is enhanced with OpenShift-specific capabilities: Gateway API integration with HTTPRoute-based ingress, kube-rbac-proxy sidecar injection for OIDC-based authentication, NetworkPolicy enforcement for cluster isolation, OpenShift TLS security profile compliance, and SecurityContextConstraints for pod security. The operator creates cross-namespace HTTPRoutes in the platform namespace, referencing cluster-namespace Services via ReferenceGrants to enable centralized Gateway API authentication.

The operator supports batch scheduling integration (Volcano, Yunikorn, Kai-scheduler, scheduler-plugins), zero-downtime RayService upgrades via Gateway API traffic splitting, and optional mTLS via cert-manager for intra-cluster communication.

## Architectural Analysis

The KubeRay operator implements a hierarchical controller architecture where RayService owns RayClusters, and RayJob creates ephemeral RayClusters. This composition creates a clean ownership chain: `RayCronJob → RayJob → RayCluster → Pods/Services`. Each layer adds lifecycle management — RayCronJob adds scheduling, RayJob adds submission and cleanup, RayService adds serve application deployment and zero-downtime upgrades. The ownership model uses Kubernetes controller references for garbage collection, with finalizers for operations that require ordered cleanup (GCS Redis namespace cleanup, job stopping via dashboard API, authentication resource removal).

The RHOAI-specific authentication architecture is notable for its cross-namespace design. The authentication controller creates HTTPRoutes in the platform namespace (APPLICATION_NAMESPACE) that reference Services in user namespaces via Gateway API ReferenceGrants. This centralizes ingress through a single platform Gateway while maintaining per-cluster authentication via kube-rbac-proxy sidecars. The kube-rbac-proxy checks SubjectAccessReview against the head Service — effectively, access to the Ray dashboard requires Kubernetes RBAC permission to `get` the cluster's head Service. The ReferenceGrant is reference-counted (one per namespace, shared by all auth-enabled clusters) and cleaned up when the last authenticated cluster in a namespace is deleted. The mutating webhook enforces `enableIngress: false` on OpenShift to prevent unauthenticated Route creation, ensuring all external access flows through the authenticated Gateway API path.

The mTLS controller follows a cert-manager integration pattern: SelfSigned Issuer bootstraps a per-cluster CA, which then issues head and worker leaf certificates. Certificate names include a UID suffix to prevent conflicts during cluster recreation. The controller monitors certificate expiry and relies on cert-manager for automatic renewal. Pod IPs are included as SANs, requiring certificate updates when pods scale, which the controller handles by watching pod changes.

The operator's TLS configuration for its own metrics endpoint demonstrates defense-in-depth: it reads the OpenShift cluster-wide TLS security profile (`apiservers.config.openshift.io/cluster`), which can be Intermediate, Modern, Old, or Custom. This ensures the operator's TLS configuration matches the cluster's security posture. Non-OpenShift deployments get a hardened default (TLS 1.2+, ECDHE ciphers with ALPN).

The batch scheduler integration is pluggable via a manager interface, supporting Volcano, Yunikorn, Kai-scheduler, and scheduler-plugins. Each scheduler implementation modifies pod specs (annotations, labels) and optionally creates PodGroup CRDs for gang scheduling semantics. This ensures all Ray cluster pods are scheduled together, avoiding resource deadlock in shared clusters.
