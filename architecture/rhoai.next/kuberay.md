## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Ray clusters, jobs, and services on OpenShift via custom resources.

**Detailed**: KubeRay is a Kubernetes operator built on the controller-runtime framework that provides declarative management of Ray distributed computing infrastructure. It defines four core custom resource types — RayCluster, RayJob, RayService, and RayCronJob — enabling users to create and manage Ray clusters, submit jobs, deploy serving endpoints, and schedule recurring workloads entirely through Kubernetes-native APIs.

The RHOAI fork extends the upstream ray-project/kuberay with OpenShift-specific security features: an AuthenticationController that injects kube-rbac-proxy sidecars for OIDC-based dashboard authentication, a NetworkPolicyController that creates per-cluster network isolation, an mTLS controller that provisions cert-manager certificates for intra-cluster communication, TLS profile integration that reads the cluster-wide OpenShift TLS security profile from `apiservers.config.openshift.io/cluster`, and admission webhooks that enforce secure defaults (e.g., disabling ingress, enabling secure trusted networking). The operator deploys into the `redhat-ods-applications` namespace and is managed by the RHOAI operator via kustomize overlays.

## Architectural Analysis

KubeRay follows a multi-controller architecture where each CRD kind has its own reconciler, and cross-cutting concerns (authentication, network policy, mTLS) are handled by independent controllers that also watch RayCluster resources. This separation means the core reconciliation loop for cluster lifecycle management is decoupled from the OpenShift-specific security stack, which is a downstream carry.

The operator's RBAC footprint is notably broad: it manages pods, services, secrets, service accounts, roles, role bindings, ingresses, network policies, routes, Gateway API resources, cert-manager certificates, and batch jobs across all namespaces. This is architecturally necessary because Ray clusters are namespace-scoped but the operator watches cluster-wide, and it must create supporting resources (RBAC, networking, TLS) in each user namespace. The `kuberay-edit-role` and `kuberay-view-role` aggregate into the standard Kubernetes admin/edit/view roles, providing fine-grained user access without requiring cluster-admin.

The TLS subsystem demonstrates defense-in-depth: the operator reads the OpenShift APIServer TLS profile at startup, applies matching cipher suites and minimum TLS version to its own webhook server, and watches for profile changes via a dedicated `tls-profile-watcher` controller that triggers a graceful restart. When the APIServer resource is unavailable (non-OpenShift clusters, transient errors), it falls back to hardened Intermediate defaults (TLS 1.2+, AEAD cipher suites only). The mTLS controller provisions per-cluster CA hierarchies through cert-manager, creating self-signed issuers, CA certificates, and per-node certificates for head and worker nodes.

Feature gates control experimental functionality: RayCronJob and AsyncJobInfoQuery are alpha (default off), while RayClusterStatusConditions, RayJobDeletionPolicy, and RayMultiHostIndexing are beta (default on). The pluggable batch scheduler interface supports Volcano, YuniKorn, Kai, and scheduler-plugins for gang scheduling of Ray workers.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar injects OIDC auth for Ray dashboard; aggregated RBAC roles (edit/view) for CR access | Kubernetes RBAC + kube-rbac-proxy | Auth sidecar is OpenShift-specific; vanilla Kubernetes deployments lack dashboard auth |
| Data storage | Per-namespace Ray clusters with separate head/worker pods | Kubernetes namespace isolation | No shared storage isolation enforced by operator; users must configure storage per namespace |
| Network traffic | Per-RayCluster NetworkPolicy created by NetworkPolicyController | Kubernetes NetworkPolicy | NetworkPolicy controller is downstream carry; upstream deployments have no network isolation |
| Compute & resources | Delegated to namespace-level ResourceQuota / LimitRange | Kubernetes (not enforced by operator) | Operator does not create or enforce quotas; one namespace's Ray cluster can consume unbounded resources |
| Configuration & secrets | Per-namespace Secrets (mTLS certs) and ConfigMaps | Kubernetes namespace scoping | cert-manager CA is per-cluster, preventing cross-cluster cert reuse |
| API scoping | Controller watches cluster-wide but reconciles per-namespace CRs; edit/view roles are aggregated | Kubernetes RBAC | Operator SA has cluster-wide permissions; tenant isolation relies on Kubernetes RBAC for user access |
