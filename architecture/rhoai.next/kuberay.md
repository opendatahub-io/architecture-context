## Purpose

**Short**: Manages the lifecycle of Ray clusters, jobs, services, and cron jobs on Kubernetes/OpenShift via CRDs.

**Detailed**: The KubeRay operator is a Kubernetes controller-runtime based operator that manages the full lifecycle of Ray distributed computing workloads. It defines four CRDs — RayCluster, RayJob, RayService, and RayCronJob — and provides controllers that reconcile these custom resources into the underlying Kubernetes primitives (Pods, Services, Ingresses, Routes, HTTPRoutes, NetworkPolicies, etc.).

For Red Hat OpenShift AI (RHOAI), the operator is extended with OpenShift-specific security hardening: a mutating webhook that automatically enforces secure trusted network annotations on all RayClusters, an authentication controller that injects kube-rbac-proxy sidecars and creates Gateway API HTTPRoutes for authenticated dashboard access, a NetworkPolicy controller that restricts inter-pod traffic, and an mTLS controller that provisions cert-manager certificates for encrypted Ray node communication. The operator integrates with the OpenShift TLS security profile system to inherit cluster-wide cipher suite and minimum TLS version configuration.

The operator also supports batch scheduling integration with Volcano, Yunikorn, Kai-scheduler, and scheduler-plugins for gang scheduling of Ray workloads, and provides Gateway API support for RayService incremental (canary) upgrades with traffic weight management.

## Architectural Analysis

The KubeRay operator follows a standard controller-runtime architecture but with substantial OpenShift security hardening that creates a layered defense model. The most architecturally interesting aspect is the "secure by default" pattern enforced through the mutating webhook: on OpenShift, every RayCluster automatically receives the `odh.ray.io/secure-trusted-network=true` annotation and has `enableIngress` forced to `false`. This means no RayCluster can bypass the authenticated Gateway API path — the webhook is the enforcement point, not the controller. This is a defense-in-depth pattern where the admission layer prevents misconfigurations from reaching the controllers at all.

The authentication architecture has three distinct controllers that coordinate via annotations: the authentication controller injects kube-rbac-proxy sidecars and creates HTTPRoutes, the NetworkPolicy controller restricts network access to the head pod, and the mTLS controller provisions certificates for inter-node encryption. These controllers are loosely coupled — each watches RayCluster but acts on the `ray.io/enable-secure-trusted-network` annotation independently. This design allows each security layer to be enabled or disabled independently, though in RHOAI they are always enabled together. The authentication controller also manages ReferenceGrant resources using a shared-per-namespace pattern (one ReferenceGrant per namespace rather than per-cluster), which prevents resource proliferation.

The TLS integration with OpenShift is notable: the operator reads the cluster-wide TLS security profile from `apiservers.config.openshift.io/cluster` and applies it to both the metrics server and webhook server. The profile resolution has a 10-second timeout and falls back to the "intermediate" profile (TLS 1.2, ECDHE cipher suites) on non-OpenShift clusters. This means the operator's TLS posture automatically inherits any cluster-wide security policy changes without operator restarts — the profile is resolved at startup.

The RayService controller's incremental upgrade support via Gateway API is architecturally complex. It creates Gateway and HTTPRoute resources with traffic weight distribution across active and pending RayCluster serve services, enabling canary-style deployments. The traffic weight is managed through HTTPRoute backend refs with weight fields, and the controller progressively shifts traffic based on `stepSizePercent` and `intervalSeconds` configuration. This is gated behind the `RayServiceIncrementalUpgrade` feature gate (alpha, disabled by default).

The dashboard cache client uses an LRU cache (10,000 entries, 10-minute expiry) backed by an 8-worker goroutine pool querying at 3-second intervals. This asynchronous approach prevents the reconciliation loop from blocking on Ray Dashboard API calls while maintaining reasonably fresh job status data. The `AsyncJobInfoQuery` feature gate (alpha) further decouples job info queries from the main reconcile path.
