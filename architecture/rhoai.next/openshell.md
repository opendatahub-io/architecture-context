## Purpose

**Short**: OpenShell is a secure, policy-enforced runtime environment for autonomous AI agents, providing sandboxed execution with kernel-level isolation, formal policy verification, and credential injection.

**Detailed**: OpenShell provides the safe, private runtime for fleets of autonomous AI agents within the RHOAI platform. It enables agents to read files, install packages, call APIs, and use credentials without unrestricted access to data, secrets, or networks. Operators declare what each agent can touch in a policy, and OpenShell enforces it through two complementary mechanisms: kernel-level enforcement (seccomp, Landlock, network proxying) and formal policy verification using an embedded Z3 SMT solver.

The architecture follows a three-tier model: a **gateway** serves as the gRPC/HTTP control plane managing sandbox lifecycle, policy, authentication, and provider credentials; a **supervisor** runs alongside each sandbox enforcing policy, proxying network traffic, and injecting credentials at the L7 layer; and a **sandbox** runtime runs inside the agent workload as a statically-linked binary that mediates process execution, filesystem access, and system calls. This separation ensures the enforcement boundary is maintained even when the agent workload is compromised.

OpenShell is an NVIDIA-originated project (upstream at `github.com/NVIDIA/OpenShell`) forked into the OpenDataHub and Red Hat Data Services organizations for RHOAI integration. The Konflux Dockerfiles produce RHEL 9 UBI-based images with hermetic builds, cargo-auditable metadata for CVE scanning, and post-quantum cryptography policies (`DEFAULT:PQ`).

## Architectural Analysis

OpenShell's architecture is notable for its defense-in-depth approach to agent isolation. The gateway serves as a centralized control plane handling all external API interactions via multiplexed gRPC and HTTP on a single port (8080). The supervisor acts as a security boundary proxy — every network connection from a sandbox passes through the supervisor's L7 enforcement layer, which evaluates policy rules, performs DNS resolution, applies AWS SigV4 signing, and injects provider credentials only for approved endpoints. The sandbox binary itself is a fully-static glibc executable designed to be injected into arbitrary container images (Alpine, Debian, distroless, UBI), giving it the unique property of running in any Linux container environment without dependencies.

The provider model is a significant architectural decision. Rather than giving agents direct access to API keys, OpenShell stores encrypted credentials in the gateway (using AES-256-GCM with a key-encryption key) and injects them at the supervisor's network proxy layer. This means the agent workload never sees raw credentials — they are added to HTTP headers only on approved outbound requests. This is combined with OIDC-based user authentication, workspace-scoped RBAC, and optional SPIFFE integration for dynamic token grants.

The compute driver abstraction supports multiple isolation backends: Kubernetes (primary for RHOAI), Docker, Podman, MicroVM (libkrun), and Windows MXC. Each driver implements the `ComputeDriver` gRPC protocol, allowing the gateway to manage sandbox lifecycle uniformly. The Kubernetes driver is the most sophisticated, supporting shared, managed (auto-created per-workspace namespaces), and operator (pre-provisioned namespaces) workspace modes, with per-sandbox NetworkPolicy enforcement and optional user namespace isolation.

The formal verification layer (`openshell-prover`) uses Z3 to check proposed policy changes before they take effect, identifying newly granted access (e.g., reaching a new host with credentials, calling a new API method) and flagging them for human review. This proactive security model distinguishes OpenShell from runtime-only enforcement approaches.

The gateway interceptor and supervisor middleware frameworks provide extensibility points: interceptors transform gRPC requests at the gateway routing boundary, while middleware evaluates HTTP requests and WebSocket sessions at the supervisor layer. Both support external gRPC extensions, enabling third-party guardrails, content filtering, and audit logging.
