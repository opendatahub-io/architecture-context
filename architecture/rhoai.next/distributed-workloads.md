## Purpose

**Short**: E2E test suite and container image collection for distributed ML training workloads on Red Hat OpenShift AI.

**Detailed**: The distributed-workloads repository serves two primary functions within the RHOAI platform. First, it provides a comprehensive Go-based E2E test framework that validates distributed machine learning training across multiple orchestration frameworks — Kubeflow Training Operator v1 (PyTorchJob), Kubeflow Trainer v2 (TrainJob), KubeRay (RayJob/RayCluster), and Kueue (queue-based resource management). The test suites cover single-node and multi-node, single-GPU and multi-GPU scenarios for both NVIDIA CUDA and AMD ROCm accelerators.

Second, the repository builds and maintains container images used as training runtimes. These images span two categories: **runtime training images** (10 variants with Konflux Dockerfiles) providing PyTorch with CUDA or ROCm support for use in PyTorchJob/TrainJob workloads, and **universal training images** (3 variants) that serve dual purposes as both Jupyter Workbench environments and training runtimes. The universal images use the AIPCC (AI Python Component Container) Ecosystems base images and private PyPI index for hermetic, FIPS-friendly builds.

The repository also contains examples (Jupyter notebooks demonstrating distributed training patterns), benchmarks (OSU MPI micro-benchmarks and MPI DDP SFT training benchmarks), and dataset/model images for testing. It does not deploy any controllers, operators, or services — it is purely a testing and image-building repository.

**Note on non-AIPCC runtime images**: 8 of the 10 runtime training Konflux Dockerfiles use standard UBI9 Python base images (`registry.access.redhat.com/ubi9/python-3{11,12}`) rather than AIPCC base images. They install Python packages from public PyPI via micropipenv with no cachi2/hermeto prefetch. These images do not use the AIPCC Ecosystems and represent a gap — they must be migrated to AIPCC base images to comply with Red Hat's product security requirements for secure builds. The 2 OpenMPI-based runtime images have already migrated.

**Note on ROCm 6.4 retirement**: Per overlay 0017, ROCm 6.4 has been retired from the AIPCC base images. The runtime and universal images referencing `quay.io/aipcc/base-images/rocm-6.4-el9.6` and the universal ROCm images need to be updated to ROCm 7.14 (the current active version).

## Architectural Analysis

The distributed-workloads repository occupies a unique position in the RHOAI platform: it is not an operator or service but rather the quality gate for the entire distributed training stack. Every RHOAI release relies on this repository's test suites to validate that PyTorchJob, TrainJob, RayJob, and Kueue-managed workloads function correctly across NVIDIA and AMD GPU hardware. The test framework's three-level image resolution strategy (local env var → operator RELATED_IMAGE → hardcoded default) is particularly well-designed, as it enables the same tests to run against both development builds and release candidates without code changes.

The container image collection reveals a deliberate migration pattern within the team. The 8 "standard" runtime training images use the older approach: UBI9 base images + Pipfile/Pipfile.lock + public PyPI + no hermetic build support. The 2 OpenMPI runtime images and 3 universal training images represent the modern approach: AIPCC base images + requirements.txt/pyproject.toml + private AIPCC PyPI index + cachi2 hermetic builds. This migration is incomplete — the 8 non-AIPCC images represent a known gap in build hermeticity and FIPS compliance. The OpenMPI images serve as the template for what the remaining images should look like.

The universal training images are architecturally noteworthy for their dual-mode entrypoint design. A single image functions as both a Jupyter Workbench (interactive development) and a training runtime (headless computation). The `entrypoint-universal.sh` script detects `NOTEBOOK_ARGS` to switch modes. This reduces image proliferation but couples two distinct concerns into one artifact. The FIPS-friendly two-stage build pattern (builder stage for pip installs, final stage for runtime) is well-implemented and should be adopted by the remaining runtime images.

The test framework itself is substantial (~40 Go source files) and demonstrates strong engineering practices: gomega-based assertions, lazy client initialization, automatic namespace cleanup with comprehensive log capture, test tier tagging for selective execution, and proper GPU/accelerator abstraction supporting both NVIDIA and AMD. The periodic pod log capture (every 3 seconds with restart tracking) is particularly valuable for debugging distributed training failures where pods may crash and restart during long-running training jobs. The test suites cover both the legacy KFTO v1 (PyTorchJob) and the modern Trainer v2 (TrainJob) paths, ensuring that the platform's transition between training frameworks is validated.

One risk area is the ROCm 6.4 retirement documented in overlay 0017. Both the runtime OpenMPI image (`py312-rocm64-torch29-openmpi41`) and the universal ROCm image (`th06-rocm64-torch291-py312`) use AIPCC base images for ROCm 6.4, which has been retired. These need to be migrated to ROCm 7.14 base images. Additionally, the 4 standard ROCm runtime images (py311/py312) install ROCm 6.2/6.4 packages from AMD repos — these are not gated by AIPCC and will also need updating.
