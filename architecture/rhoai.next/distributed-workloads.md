## Purpose

**Short**: End-to-end test suite and training container images for distributed workloads on Red Hat OpenShift AI, covering Kubeflow Training Operator v1, Kubeflow Trainer v2, and KubeRay.

**Detailed**: The distributed-workloads repository serves two primary functions within RHOAI. First, it is the comprehensive end-to-end test suite for validating distributed training capabilities across three orchestration frameworks: Kubeflow Training Operator v1 (PyTorchJob), Kubeflow Trainer v2 (TrainJob/JobSet), and KubeRay (RayCluster/RayJob). The Go-based test suites (`tests/kfto/`, `tests/trainer/`, `tests/odh/`, `tests/fms/`) exercise training workloads across CPU, NVIDIA CUDA, and AMD ROCm accelerators, validating Kueue integration, model fine-tuning (SFT, LoRA, QLoRA), multi-node/multi-GPU configurations, and upgrade scenarios.

Second, the repository builds and maintains Universal Training Images — container images that serve as the runtime environment for ML training jobs on RHOAI. Three accelerator variants (CPU, CUDA, ROCm) are built via Konflux Dockerfiles, each layering a comprehensive ML Python stack (PyTorch, Transformers, TRL, DeepSpeed, vLLM, etc.) on top of UBI9-based Jupyter workbench base images. These images operate in a dual-mode architecture: as Jupyter workbenches when `NOTEBOOK_ARGS` is set (OpenShift workbench controller), or as headless training runtimes when a training controller overrides the entrypoint. The repository also provides Ray runtime images, example training workflows, and MPI benchmarks.

## Architectural Analysis

This repository is architecturally unusual within RHOAI: it is not a deployed service or operator, but rather a test-and-build artifact repository. Its primary deliverables are container images and test validation, not running workloads.

The Universal Training Image architecture deserves particular attention. Each variant (CPU, CUDA, ROCm) uses a two-stage Dockerfile pattern: a builder stage that installs Python dependencies via Hermeto/cachi2 prefetch, and a final stage that copies only site-packages — isolating build tools from the runtime image for FIPS friendliness. The images use a conditional `DOWNSTREAM` build arg to support both midstream builds (which install system packages directly) and downstream builds (where the AIPCC base image provides everything). The universal entrypoint script (`entrypoint-universal.sh`) implements the dual-mode switching: Jupyter notebook for interactive workbench use, or pass-through to whatever command a training controller provides.

The Go test infrastructure in `tests/common/support/` (~40 files) is a significant piece of engineering in its own right. It provides a lazy-initialized multi-client abstraction covering Kubernetes core, Kubeflow Training Operator, Kubeflow Trainer v2, KubeRay, Kueue, JobSet, OpenShift Machine API, and OLM. Each test suite (`kfto`, `trainer`, `fms`, `odh`) maintains strict import boundaries enforced by `depguard` in the linter config — shared code must go through the common support library.

A notable security pattern in the test code: TLS certificate verification is intentionally skipped (`InsecureSkipVerify: true`) in test helper clients (S3 provider, Ray cluster client, Prometheus client) — appropriate for ephemeral test environments but explicitly marked with `//nolint:gosec` comments. This is test-only code that never ships in production images.

The Python dependency stack is massive — the CUDA training image's `requirements.txt` has ~1389 lines of pinned dependencies, including ML/AI frameworks (PyTorch 2.13.0, Transformers 5.16.1, DeepSpeed 0.19.5, vLLM 0.28.0), the Kubeflow SDK (0.4.1+rhaiv.2), and Red Hat-specific packages (training-hub, rhai-innovation-mini-trainer, unsloth with rhaiv patches). All dependencies are resolved against the private AIPCC PyPI index, ensuring supply chain control.
