## Purpose

**Short**: End-to-end integration test suite, container image definitions, and reference examples for distributed ML training workloads on RHOAI.

**Detailed**: The distributed-workloads repository is a testing and container image repository — it does not deploy an operator or service. It provides three primary capabilities:

1. **Integration Test Framework**: A comprehensive Go-based test suite (built on Ginkgo/Gomega) that validates distributed training workloads across four domains: Kubeflow Training Operator v1 (PyTorchJob), Kubeflow Trainer v2 (TrainJob/JobSet), KubeRay (RayCluster/RayJob), and Foundation Model Services (fms-hf-tuning). Tests exercise GPU training (NVIDIA CUDA, AMD ROCm), multi-node distributed training, Kueue resource management, S3 storage integration, and upgrade scenarios.

2. **Training Runtime Container Images**: Defines and builds ~13 Konflux-managed container images and ~15 community container images providing GPU-accelerated Python environments for distributed training. Images span CUDA 12.1–13.0, ROCm 6.2–6.4, PyTorch 2.4.1–2.10.0, and include specialized ML libraries (Flash Attention, DeepSpeed, mamba-ssm, Training Hub). The "universal" image line combines Jupyter workbench and training runtime into a single image using AIPCC base images.

3. **Reference Examples and Workshops**: Jupyter notebooks and manifests demonstrating LLM fine-tuning (SFT, LoRA, DreamBooth), RAG pipelines, hyperparameter optimization, document processing with Docling, and multi-team GPU scheduling with Kueue.

## Architectural Analysis

The distributed-workloads repository occupies a unique position in the RHOAI ecosystem: it is neither an operator nor a service, but rather the **quality gate** for the entire distributed training stack. Its integration test framework validates that Kubeflow Training Operator v1, Kubeflow Trainer v2, KubeRay, Kueue, and the platform operator all work together correctly. This makes it architecturally significant despite producing no production services — a failure in this repository's tests blocks RHOAI releases.

The container image strategy reveals a **three-tier evolution** in build practices. The oldest tier (8 runtime training images) uses raw UBI9 Python base images and installs CUDA/ROCm directly from vendor repos — these lack RPM lock files and are not hermetic. The middle tier (2 OpenMPI images) has migrated to AIPCC base images (`quay.io/aipcc/base-images/cuda-13.0-el9.6` and `rocm-6.4-el9.6`) with `rpms.lock.yaml` files and `uv pip compile`-generated requirements. The newest tier (3 universal images) uses RHOAI workbench base images with full cachi2 hermetic builds. This progression shows active migration toward supply chain security, but the 8 UBI-based images remain a hermeticity gap.

A notable architectural pattern is the **universal image** concept: a single container image that serves as both a Jupyter workbench (for interactive development) and a training runtime (for batch jobs). The `entrypoint-universal.sh` script detects the `NOTEBOOK_ARGS` environment variable — when set by the OpenShift workbench controller, it starts Jupyter; otherwise it runs the provided command. This dual-mode design reduces image sprawl and ensures that the environment users develop in matches the environment their training jobs execute in, eliminating "works on my notebook but not in production" discrepancies.

The test framework's **multi-client abstraction** (`tests/common/support/client.go`) is worth noting for its breadth: it provides typed clients for 11 different Kubernetes API groups (core, dynamic, Kubeflow, Trainer, Ray, JobSet, Kueue, Kueue Operator, OpenShift Routes, OpenShift Images, OLM). This reflects the complexity of the distributed training stack — a single training job may involve PyTorchJob CRs, Kueue workload admission, JobSet management, and OpenShift-specific routing. The test framework uses namespace-scoped isolation with dynamic RBAC, creating fresh namespaces for each test and cleaning up afterward.

The ROCm 6.4 AIPCC base image used by `py312-rocm64-torch29-openmpi41/Dockerfile.konflux` is **Retired** per overlay 0017, which states that ROCm 7.14 is the current supported version. This image should be updated to use the ROCm 7.14 AIPCC base image when available. Similarly, the non-AIPCC runtime training images (CUDA 12.1, 12.4, ROCm 6.2) use older accelerator versions that may not align with the platform's current supported accelerator matrix.
