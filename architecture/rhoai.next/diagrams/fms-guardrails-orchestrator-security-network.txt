RBAC Summary:
  No RBAC resources -- standalone service, not a Kubernetes operator.
  RBAC is managed by the deploying operator.

Service Mesh Configuration:
  No service mesh resources defined in this repo.
  Network isolation delegated to platform operator.
  No NetworkPolicy defined -- ingress is managed by deploying operator.

Secrets:
  - TLS server cert/key (kubernetes.io/tls) - Server TLS for guardrails endpoint,
    provisioned by cert-manager or manual, rotation depends on provisioner
  - TLS client CA cert (Opaque) - mTLS client verification, manual provisioning,
    no auto-rotation
  - Named TLS configs (Opaque) - Per-service client TLS certs/keys for backend
    connections, manual provisioning, no auto-rotation
  - API tokens (Opaque) - Bearer tokens for OpenAI/detector services, via env var
    names in config, no auto-rotation

Authentication Flow:
  1. Client sends request with auth headers to orchestrator (8033/TCP)
  2. Orchestrator forwards configured passthrough_headers to backend services
  3. Optional: X-Forwarded-Access-Token is rewritten to Authorization: Bearer header
  4. Per-service api_token config injects Bearer tokens for detector/OpenAI backends
  5. gRPC backends authenticated via mTLS client certificates (per-service TLS config)

FIPS Compliance Assessment:
  - TLS Stack: rustls 0.23.36 with ring crypto backend (NOT FIPS 140-2/3 validated)
  - Build: openssl-devel installed but runtime TLS uses ring, not OpenSSL
  - Risk: NoVerifier struct in utils/tls.rs bypasses certificate validation (dev mode)
  - Risk: insecure: true per-service config disables cert verification
  - Gap: For strict FIPS compliance, service needs OpenSSL-backed TLS instead of ring
