Network Services:
- model-mesh: Headless ClusterIP (clusterIP: None), Port 8033/TCP
  Purpose: Direct pod-to-pod addressing for gRPC connections

NetworkPolicy:
- Ingress allowed on ports: 8033/TCP, 8080/TCP, 2112/TCP
- Ingress to 8033 (inference) allows ANY source (security gap)
- Intra-cluster limited to pods with matching app/component labels

RBAC Summary:
- ModelMesh does NOT define RBAC resources
- No direct Kubernetes API interaction
- RBAC managed by modelmesh-serving controller

Secrets:
- model-mesh-icd-etcd (Opaque/JSON) - etcd connection config (endpoints,
  credentials, TLS certs). Provisioned manually/operator. No auto-rotation.
- model-mesh-tls-secret (kubernetes.io/tls) - TLS cert/key for external gRPC
  and internal litelinks TLS. Provisioned manually/cert-manager. No auto-rotation.

Authentication & Authorization:
- gRPC external (8033): Optional mTLS (NONE/REQUIRE/OPTIONAL)
- gRPC litelinks (8080): Optional mTLS (MM_INTRACLUSTER_CLIENTAUTH)
- Health probes (8089): Unauthenticated (kubelet probes)
- Prometheus (2112): TLS server-auth only, no client auth

FIPS Compliance:
- *** CRITICAL GAP: Java FIPS mode DISABLED (-Dcom.redhat.fips=false) ***
- SunPKCS11 provider replaced in java.security (Dockerfile.konflux)
- BouncyCastle (non-FIPS) used for self-signed cert generation
- BoringSSL-static (netty-tcnative) used for TLS, NOT FIPS-validated
- Impact: ModelMesh does NOT use FIPS-validated crypto even on FIPS-enabled hosts

Multi-Tenancy:
- Tenant boundary: MM_SERVICE_NAME (logical ModelMesh cluster)
- No per-model or per-tenant authorization
- etcd isolation: Key prefix only (MM_KVSTORE_PREFIX), no etcd-level ACLs
- Any client with network access can manage any model in the cluster
