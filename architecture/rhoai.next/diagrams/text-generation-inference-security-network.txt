RBAC Summary:
  No RBAC resources defined. TGIS runs as a standalone inference server pod
  and does not interact with the Kubernetes API.

Service Mesh Configuration:
  No service mesh configuration defined in TGIS manifests.
  Service mesh integration (if any) is managed by the consuming platform
  (KServe / Caikit deployment).

Secrets:
  No Secrets defined in manifests. TLS certificates are provided via CLI flags:
  - TLS_CERT_PATH — Server TLS certificate
  - TLS_KEY_PATH — Server TLS private key
  - TLS_CLIENT_CA_CERT_PATH — Client CA certificate for mTLS validation
  These are mounted by the consuming deployment (e.g., KServe InferenceService).

FIPS Compliance Notes:
  - Router gRPC: Uses rustls (ring crate) — NOT FIPS-validated
  - Router HTTP: Uses axum with optional TLS
  - Python server: cryptography>=43.0.1 (OpenSSL-backed, FIPS-capable)
  - Shard communication: Unix Domain Sockets (no TLS needed — local IPC)
  - Risk: If direct gRPC TLS is enabled (TLS_CERT_PATH), uses non-FIPS crypto
  - Mitigation: In production, TLS is typically terminated upstream by KServe/platform

Multi-Tenancy:
  - Single-tenant: One TGIS pod serves one model
  - Tenant boundary: per-model instance
  - No per-user/per-tenant authorization
  - Relies on upstream (KServe) for multi-tenant auth enforcement

Container Security Context:
  - Read-only root filesystem (via kustomize patch)
  - GPU resources dedicated to single model instance
  - Model storage mounted read-only
