## Diagram Descriptions

### Component Dependency Graph
Shows how platform components depend on each other. The rhods-operator sits at the root, managing lifecycle of all 130 components through a three-tier operator model (platform → module → upstream). Color coding: red for platform root, blue for serving stack, orange for training/scheduling, green for development/MLOps, purple for agents, teal for model management.

### Platform Network Topology
Complete network architecture showing all trust zones: External, Ingress Tier (openshift-ingress with 2 primary Gateways), Operator Tier, Application Tier (20-30 pods), MaaS Tier (multi-tenant), User Tier (workloads), Legacy Mesh Tier (transitional Istio), and Egress.

**Two formats provided**:
- **Mermaid (.mmd)**: Visual diagram with color-coded trust zones. Great for presentations and architecture discussions.
- **ASCII (.txt)**: Precise text format with no ambiguity. Required for SAR (Security Architecture Review) submissions and compliance documentation. Includes complete auth chain details for both gateways.

Both formats contain the same information, just different representations.

### Cross-Component Workflows
Five sequence diagrams showing end-to-end user workflows:
1. **Model Deployment via Dashboard** — User deploys model through dashboard, KServe creates serving pod, odh-model-controller sets up ingress
2. **Multi-Tenant Model Consumption (MaaS)** — Admin creates AITenant, maas-controller bootstraps infrastructure, tenant authenticates with API key via Authorino
3. **Distributed Training Job** — TrainJob submitted, Kueue admits workload when quota available, distributed workers train across GPU nodes
4. **ML Pipeline Execution** — Pipeline DAG executed by Argo Workflows, steps register models and auto-deploy to KServe
5. **LLM-D Disaggregated Inference** — EPP scores endpoints by KV-cache utilization, routes to prefill worker, NIXL transfers KV-cache to decode worker

### Platform Security Overview
Visual representation of the platform's security architecture:
- **9 authentication mechanisms** (ext_authz, Kuadrant, kube-rbac-proxy, TokenReview, Istio mTLS, provider auth, controller-runtime, bearer middleware, unauthenticated probes)
- **5 most privileged ClusterRoles** with rule counts and API group coverage
- **304 admission webhooks** across 25 components with cross-cutting concerns (Pod mutation ordering, monitoring injection, workload scheduling)
- **TLS configuration** including ProfileWatcher pattern, service-ca, cert-manager, FIPS compliance, and the known insecureSkipVerify gap (RHOAIENG-61070)
- **Container security** patterns: UBI 9, non-root, capability drops, PQC, digest pinning, SCCs

### Platform Observability
Maps monitoring and observability coverage:
- **Prometheus scrape targets**: All operators expose :8443/TCP metrics via controller-runtime authn/authz or kube-rbac-proxy. Platform label injection via mutating webhooks.
- **Health probes**: All Go operators use :8081 healthz/readyz. Health endpoints are intentionally unauthenticated.
- **Inference metrics**: KServe request latency/throughput, EPP routing metrics, llm-d prefill/decode stats, vLLM token throughput and GPU utilization.
- **Monitoring infrastructure**: odh-observability provisions the declarative observability stack via Monitoring CR.

### Platform Maturity Dashboard
High-level metrics organized by category:
- **Component statistics**: 130 components, 25+ operators, 120+ images, 236 CRDs, 27 ClusterServingRuntimes
- **Security posture**: Gateway API primary path, MIXED mTLS, 304 webhooks, FIPS builds, non-root enforcement
- **API maturity**: Mostly v1alpha1 CRDs, 8 distinct serving paths, 2 primary + 3 legacy gateways
- **Deployment readiness**: Leader election HA, disconnected partially resolved, multi-arch partial for non-amd64
- **Architectural complexity**: 3-deep operator tiers, 9 auth mechanisms, 2 parallel ingress generations
