RBAC Summary:
- ClusterRole: rhaii-validator
  - Intentionally EMPTY — exists only as an SCC subject on OpenShift
  - Actual API calls use invoking user's kubeconfig credentials
- ClusterRoleBinding: rhaii-validator
  - Binds ClusterRole/rhaii-validator → SA rhaii-validation/rhaii-validator
- ClusterRoleBinding: rhaii-validator-scc-{namespace} (OCP only)
  - Binds ClusterRole/system:openshift:scc:privileged → SA rhaii-validation/rhaii-validator
  - Grants privileged SCC for sysfs/device access

Security Context:
- All workload pods: automountServiceAccountToken: false
  - SA tokens explicitly disabled — pods never call Kubernetes API
- Check Job pods: privileged security context
  - Required for chroot /host, sysfs access, GPU device queries
- Bandwidth pods: GPU and RDMA device resources requested
  - Not privileged — device access via device plugins

Secrets:
- (user-provided pull secret) kubernetes.io/dockerconfigjson
  - Image pull for registry.redhat.io
  - Provisioned by user via --pull-secret flag
  - No auto-rotation

FIPS Compliance:
- Go binary: GOEXPERIMENT=strictfipsruntime, CGO_ENABLED=1
- TLS: client-go default config, inherits system OpenSSL via FIPS runtime
- No custom TLS config, no InsecureSkipVerify, no weak ciphers detected

Network Security Notes:
- No NetworkPolicy applied to validation namespace
  - Bandwidth tests require unrestricted pod-to-pod communication
  - Acceptable for ephemeral validation workloads (Jobs are short-lived)
- All pod-to-pod traffic is plaintext (TCP) or RDMA (no encryption)
  - Expected for bandwidth measurement — encryption would skew results
- Only external connection is to Kubernetes API (TLS 1.2+)
- Device name validation: regex ^[a-zA-Z0-9][a-zA-Z0-9_-]*$
  - Prevents argument injection through RDMA device names
