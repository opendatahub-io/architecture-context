## Purpose

**Short**: Python SDK providing a high-level interface for requesting, managing, and interacting with Ray clusters and Ray jobs on Kubernetes (OpenShift AI / Open Data Hub).

**Detailed**: The CodeFlare SDK is a Python client library that simplifies the lifecycle management of distributed computing resources for data scientists. It abstracts the complexity of Kubernetes, KubeRay, and Kueue APIs behind intuitive Python objects (`Cluster`, `ClusterConfiguration`, `RayJob`, `RayJobClient`), enabling users to create, monitor, and tear down Ray clusters and submit Ray jobs from Jupyter notebooks or Python scripts.

The SDK integrates tightly with the RHOAI/ODH platform stack: it generates `RayCluster` and `RayJob` custom resources consumed by the KubeRay operator, interfaces with Kueue for queue-based scheduling and resource quotas, generates mTLS certificates for secure Ray client-to-cluster communication, and discovers ingress endpoints via Gateway API HTTPRoutes (RHOAI 3.x) or OpenShift Routes (legacy). Authentication is handled via `kube-authkit`, supporting auto-detection, OIDC, OpenShift OAuth, token-based, and kubeconfig methods.

The SDK is distributed as a PyPI package (`pip install codeflare-sdk`) and is pre-installed in RHOAI/ODH workbench notebook images. It also includes a vendored copy of the KubeRay Python client for RayJob management and an ipywidgets-based interactive UI for cluster management in Jupyter notebooks.

## Architectural Analysis

The CodeFlare SDK follows a well-structured layered architecture with enforced import boundaries defined in `.importlinter`. The architecture separates concerns into three tiers: a foundation layer (`common.utils`, `common.kubernetes_cluster`, `common.kueue`) that provides Kubernetes authentication, certificate management, and utility functions; a feature layer (`ray.cluster`, `ray.rayjobs`, `ray.client`) implementing the two primary user-facing workflows (interactive RayCluster management and batch RayJob submission); and a vendored layer containing the KubeRay Python client which is only importable from the `rayjobs` module. This layering is enforced at CI time via `import-linter` contracts, preventing circular dependencies and ensuring the foundation layer never depends on feature modules.

The SDK's ingress discovery mechanism is notable for its graceful degradation across platform versions. When resolving the Ray dashboard URL, it follows a four-step fallback chain: (1) HTTPRoute lookup by `ray.io/cluster-name` label (RHOAI 3.x with Gateway API), (2) OpenShift Route lookup by naming convention (pre-3.x), (3) Kubernetes Ingress lookup (non-OpenShift), (4) error message guiding users to run `cluster.apply()`. Within the HTTPRoute path, hostname resolution itself has a three-level fallback: Gateway spec listeners → OpenShift Route exposing the Gateway → GatewayConfig CR domain → Gateway status addresses. This multi-layered discovery ensures the SDK works across RHOAI versions, ODH deployments, and vanilla Kubernetes (Kind) without environment-specific configuration.

The mTLS certificate lifecycle is tightly integrated into the cluster apply/ready workflow. When `cluster.apply()` is called, the SDK polls for a KubeRay-provisioned CA Secret (labeled `ray.openshift.ai/cluster-name`), generates an RSA-3072 client certificate signed by that CA (with proper X.509v3 extensions including SAN entries for the head service DNS names), writes it to a user-local directory with restricted permissions, and sets `RAY_USE_TLS` environment variables. The certificate generation uses the `cryptography` library which delegates to the system OpenSSL, making it FIPS-compatible when the host's FIPS mode is enabled. Certificate cleanup is automatic when `cluster.down()` is called and manual cleanup utilities (`cleanup_expired_certificates`, `cleanup_old_certificates`) are available for maintenance.

The RayJob module introduces a dual-mode cluster targeting pattern: users can either reference an existing cluster by name (`cluster_name`) or define an ephemeral cluster inline (`cluster_config` with `ManagedClusterConfig`). The two modes have distinct Kueue integration behaviors — managed clusters get `kueue.x-k8s.io/queue-name` labels for admission control, while existing-cluster jobs intentionally skip Kueue labels. File handling for RayJobs uses Kubernetes Secrets as a transport mechanism: local Python scripts are read and stored as Secret data, working directories are zipped and base64-encoded, and an init container unzips them on the submitter pod. This approach has a 1MB size limit imposed by Kubernetes Secret constraints.

The SDK's authentication has been modernized with `kube-authkit` while maintaining backward compatibility through deprecated legacy classes (`TokenAuthentication`, `KubeConfigFileAuthentication`). The auto-detection mode (`AuthConfig(method="auto")`) tries kube-authkit first, then falls back to legacy `config.load_kube_config()` / `config.load_incluster_config()`, ensuring existing user code continues to work during migration. A workbench-specific CA cert path (`/etc/pki/tls/custom-certs/ca-bundle.crt`) is automatically detected, reflecting the SDK's primary deployment context within RHOAI workbench containers.
