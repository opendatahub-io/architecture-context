## Purpose

**Short**: Python SDK providing a high-level interface for creating, managing, and submitting jobs to Ray clusters on Kubernetes, with integration for Kueue scheduling and AppWrapper resource management.

**Detailed**: The CodeFlare SDK is a client-side Python library that simplifies the lifecycle management of Ray clusters on Kubernetes and OpenShift. It provides an intuitive API for data scientists and ML engineers to request batch compute resources, create Ray clusters via RayCluster custom resources, wrap them in AppWrappers for Kueue-based scheduling, monitor cluster status, and submit Ray jobs — all from within Jupyter notebooks or Python scripts.

The SDK is not deployed as a server-side component. Instead, it runs inside user workspaces (typically RHOAI/ODH notebook pods or local development environments) and communicates with the Kubernetes API server to manage RayCluster and AppWrapper custom resources. It also connects directly to Ray cluster head nodes via their dashboard endpoints (OpenShift Routes or Kubernetes Ingresses) for job submission and monitoring.

Key capabilities include: YAML-based RayCluster template generation with configurable CPU/memory/GPU resources, AppWrapper wrapping for Kueue queue integration, TLS certificate generation for secure Ray client connections, Jupyter notebook widgets for interactive cluster management, and a Ray Job Submission Client wrapper for job lifecycle operations.

## Architectural Analysis

The CodeFlare SDK follows a client-library architecture where all intelligence resides in the SDK code running inside the user's environment (typically a Jupyter notebook pod). The SDK has no server-side component — it acts as a sophisticated Kubernetes client that generates, submits, and monitors custom resources. This design means the SDK's security posture is entirely dependent on the user's service account permissions and the platform's RBAC configuration.

The SDK uses a template-based YAML generation approach (`base-template.yaml`) rather than programmatic construction of Kubernetes objects. The `generate_yaml.py` module reads a base RayCluster YAML template and mutates it in-place based on `ClusterConfiguration` fields. This approach provides flexibility but introduces risk: template drift between SDK versions and KubeRay API changes could produce invalid manifests. The template includes ODH-specific volume mounts for trusted CA bundles (`odh-trusted-ca-bundle`, `odh-ca-bundle.crt`), coupling the SDK to the ODH/RHOAI platform's certificate infrastructure.

The AppWrapper integration layer (`workload.codeflare.dev/v1beta2`) wraps RayCluster resources for Kueue scheduling. The SDK implements a two-mode deployment: direct RayCluster creation (when `appwrapper=False`) or AppWrapper-wrapped creation (when `appwrapper=True`, which is the default in RHOAI). The Kueue integration module discovers the default LocalQueue in the user's namespace and applies the `kueue.x-k8s.io/queue-name` label automatically.

The TLS certificate generation utility (`generate_cert.py`) is notable for its security implications. It generates RSA-2048 keys and X.509 certificates client-side, reads the cluster CA secret from Kubernetes, and creates signed client certificates stored in the user's local filesystem. The certificates use SHA256 signing and include Subject Alternative Names for `localhost` and `127.0.0.1`. This approach enables mTLS for the Ray client protocol (port 10001) but requires the user to have read access to the cluster's CA secret — a privilege that should be carefully scoped.

The SDK includes a comprehensive Jupyter widget system (`widgets.py`) that provides interactive cluster management UIs. The `RayClusterManagerWidgets` class creates toggle buttons for cluster selection, delete/view-jobs/dashboard buttons, and auto-refreshing cluster status tables. The `is_notebook()` function detects Jupyter environments via `PYDEVD_IPYTHON_COMPATIBLE_DEBUGGING` and `JPY_SESSION_NAME` environment variables, and automatically displays cluster up/down buttons when a `Cluster` object is instantiated in a notebook context. This tight integration with the notebook environment is a key differentiator from raw Kubernetes CLI workflows.

The SDK's image selection logic (`generate_yaml.py:96-108`) automatically selects Ray container images from `quay.io/modh/ray` based on the user's Python version (3.9 or 3.11), using SHA256 digest-pinned references for reproducibility. The `SUPPORTED_PYTHON_VERSIONS` dictionary hardcodes these mappings, which must be updated with each Ray version bump — a maintenance burden tracked in the codebase.
