## Purpose

**Short**: Intelligent LLM inference routing engine that provides KV-cache-aware endpoint selection, request prioritization, flow control, and disaggregated inference coordination for model-serving pods.

**Detailed**: The llm-d Router is the intelligent entry point for inference traffic in the llm-d ecosystem. Its core component, the Endpoint Picker (EPP), integrates with production-grade L7 proxies (primarily Envoy) via the ext-proc (external processing) gRPC protocol. The EPP evaluates incoming requests against real-time signals — KV-cache locality, queue depth, running request load, model availability, and priority — to make optimal endpoint placement decisions for model-serving pods organized into InferencePool resources.

The router supports two deployment modes: **Standalone Mode** (self-managed Envoy sidecar alongside EPP) and **Gateway Mode** (integrating with Kubernetes Gateway API infrastructure such as Istio or kGateway). It extends the Kubernetes Gateway API Inference Extension (GIE) with two custom CRDs — `InferenceObjective` (request priority/SLO configuration) and `InferenceModelRewrite` (model name rewriting for A/B testing and canary rollouts). The architecture is plugin-based: filters, scorers, data producers, parsers, and profile handlers are all pluggable, enabling extensibility across scheduling strategies, protocol formats (OpenAI, Anthropic, Vertex AI, vLLM gRPC), and data layer sources.

The repository also ships a **Disaggregation Sidecar** (pd-sidecar) that coordinates multi-stage inference lifecycles (Prefill/Decode, Encode/Prefill/Decode) by routing requests between specialized workers and managing KV-cache transfers via multiple protocols (NIXL, shared storage, SGLang, Mooncake). A **Coordinator** component provides centralized pipeline orchestration for more complex disaggregated inference topologies involving separate render, encode, prefill, and decode stages.

## Architectural Analysis

The llm-d Router exhibits a layered plugin architecture that separates concerns across four extension points. The **request control layer** handles parsing (OpenAI, Anthropic, Vertex AI, vLLM gRPC/HTTP, passthrough), data production (prefix cache computation, tokenization, session tracking, inflight load estimation), and admission control (saturation detection, latency SLO, probabilistic admission). The **scheduling layer** provides filters (by-label, prefix cache affinity, session affinity, SLO headroom tiers, endpoint attributes), scorers (KV-cache utilization, queue depth, running requests, load-aware, LoRA affinity, latency prediction, prefix cache, context-length-aware), pickers (max-score, random, weighted-random), and profile handlers (single, disaggregated P/D, data-parallel). The **flow control layer** (feature-gated) implements priority-based queuing with pluggable fairness policies (global-strict, round-robin, program-aware), ordering policies (FCFS, EDF, SLO-deadline), and usage limit policies (static, priority-holdback). The **data layer** provides pluggable sources (Prometheus metrics polling, DCGM GPU metrics, model server discovery, notification sources, file-based endpoint discovery) and extractors that populate the endpoint datastore with real-time signals.

The FIPS posture shows an inconsistency between the two Konflux images: the sidecar correctly uses `-tags strictfipsruntime` for FIPS-compliant crypto, while the EPP Konflux Dockerfile uses `CGO_ENABLED=1` (enabling dynamic linking) but omits the `strictfipsruntime` tag. Both images use UBI 9 minimal as the runtime base (which includes OpenSSL), so they will pass check-payload's basic linking validation. However, the EPP's omission of `strictfipsruntime` means its Go crypto operations may not route through the FIPS-validated OpenSSL backend. Additionally, several data layer source plugins default to `InsecureSkipVerify=true` when scraping model server metrics, which is appropriate for cluster-internal communication but should be documented as a conscious trade-off.

The disaggregation architecture supports five KV-cache transfer protocols (NIXLv2, shared storage, SGLang, Mooncake, offloading/P2P) and two encoder-cache transfer protocols (EC-Example, EC-NIXL), reflecting the diversity of hardware and networking environments in which LLM inference is deployed. The sidecar handles per-pod coordination while the coordinator handles centralized pipeline orchestration — these are complementary, not competing, deployment patterns. The coordinator is currently upstream-only (no Konflux Dockerfile), suggesting it is not yet shipping as part of RHOAI.

The EPP supports running without a Kubernetes cluster through its file-based endpoint discovery mode, enabling deployment on bare metal, Slurm, or Ray clusters. In this mode, InferenceModelRewrite and InferenceObjective CRD reconcilers are inactive, and static flow control configuration from the EndpointPickerConfig file is used instead. This dual-mode capability (Kubernetes-native vs. standalone) is a significant architectural feature that broadens the deployment surface.

The graceful shutdown mechanism is particularly sophisticated: on SIGTERM, the controller manager stops and releases the leader lease, health probes report NOT_SERVING (triggering Kubernetes endpoint removal), but the ext-proc gRPC server continues accepting requests for a configurable drain timeout (default 30s). This ensures in-flight and pre-DNS-refresh requests are served rather than rejected during rolling updates.
