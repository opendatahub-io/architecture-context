## Purpose

**Short**: Intelligent LLM inference request routing engine that provides KV-cache-aware endpoint selection, priority-based flow control, and disaggregated prefill/decode orchestration for model serving pools.

**Detailed**: The llm-d Router is the entry point for inference traffic in the llm-d serving architecture. It comprises three deployable components: the **Endpoint Picker (EPP)**, the **Disaggregation Sidecar (pd-sidecar)**, and the **Coordinator**. The EPP integrates with L7 proxies (primarily Envoy) via the ext-proc gRPC protocol to intercept inference requests and make optimal endpoint placement decisions based on KV-cache locality, load distribution, session affinity, request priority, and model compatibility. It watches Kubernetes CRDs -- `InferencePool` (from Gateway API Inference Extension), `InferenceObjective`, and `InferenceModelRewrite` -- to dynamically configure routing behavior.

The pd-sidecar runs alongside decode model server pods and orchestrates disaggregated inference workflows. In Prefill/Decode (P/D) mode, it routes prefill work to a selected prefiller pod and manages KV-cache transfer (via NIXL RDMA, shared storage, SGLang, or Mooncake connectors) before decode executes locally. In Encode/Prefill/Decode (E/P/D) mode, multimodal encoding is additionally offloaded to dedicated encoder workers. The Coordinator is an experimental HTTP service that implements the full E/P/D pipeline as a sequential step chain (replace-media-urls → render → encode → prefill → decode), forwarding requests through the inference gateway at each stage.

The router's plugin-based architecture supports 60+ built-in plugins for filtering, scoring, data collection, flow control, and request parsing, with support for OpenAI, Anthropic/Claude, Vertex AI, vLLM gRPC, and passthrough API formats.

## Architectural Analysis

The llm-d Router represents a sophisticated request routing system that has grown from a simple ext-proc endpoint picker into a multi-component platform with three distinct deployment targets. The architecture follows a plugin-based design with over 60 built-in plugins organized into clear categories: scheduling (filters, scorers, pickers), request control (data producers, admitters, response processors), data layer (sources, extractors), and flow control (fairness policies, ordering policies, saturation detectors). The plugin system uses a factory registry pattern where plugins self-register via Go `init()` functions, and a data dependency graph automatically resolves producer/consumer relationships between plugins. This design enables significant extensibility without modifying core scheduling logic.

The disaggregation architecture (P/D and E/P/D) is a key differentiator. The sidecar component implements five different KV-cache transfer connectors (NIXL v2 RDMA, shared storage, SGLang bootstrap, Mooncake, and offloading/P2P), reflecting the diverse hardware and network topologies encountered in production GPU clusters. The MoRI-IO WRITE mode for NIXL adds RDMA Write support with parallel dispatch, enabling sub-millisecond KV-cache transfers between prefill and decode workers. The coordinator component adds a separate HTTP-based orchestration path for the full E/P/D pipeline, which is useful when the Envoy ext-proc approach is insufficient (e.g., multimodal encoding requires media download and tokenization steps that don't map to ext-proc's filter model).

A notable FIPS asymmetry exists between the two Konflux-shipped images: `Dockerfile.konflux.sidecar` includes `-tags strictfipsruntime` for FIPS-compliant Go crypto, but `Dockerfile.konflux.epp` uses `CGO_ENABLED=1` without the strictfipsruntime tag. This means the sidecar binary will use OpenSSL-backed crypto in FIPS mode, while the EPP binary may fall back to Go's standard crypto library. Both images use UBI 9 bases (which include OpenSSL), so the EPP may still pass check-payload validation, but the absence of the explicit FIPS build tag is worth verifying with the build team. Additionally, several data source plugins (metrics, models, DCGM) default to `InsecureSkipVerify=true` when scraping model server metrics, which disables TLS certificate verification. While this is pragmatic for in-cluster communication where model servers may not have proper certificates, it should be documented as a security consideration.

The project's lineage traces to `kubernetes-sigs/gateway-api-inference-extension` (GIE), from which the EPP code was originally adapted (as noted in `cmd/epp/main.go`). The InferenceObjective and InferenceModelRewrite CRDs were merged into this repository from GIE, while the InferencePool CRD remains upstream. The `red-hat-data-services/llm-d-router` repository is a downstream fork of `llm-d/llm-d-router`, with the Konflux Dockerfiles (`.konflux.epp` and `.konflux.sidecar`) being the key downstream additions for RHOAI product builds. The coordinator component has no Konflux Dockerfile, indicating it is not yet shipped as a RHOAI product image.
