## Purpose

**Short**: Data Connect Hub is a middleware platform that centralises data connection management and exposes heterogeneous data sources through REST and Apache Arrow Flight APIs, deployed and managed by a Kubernetes controller.

**Detailed**: Data Connect Hub (DCH) provides a single integration point for ingesting data from multiple heterogeneous data sources—PostgreSQL, SQLite, S3, Milvus, Elasticsearch, Neo4j, and URI-based endpoints—so that consuming services do not each need to maintain their own client library stacks. The platform has three principal runtime components: a Go-based controller (`dc-controller`) that manages the lifecycle of the service deployments via the `DataConnectService` CRD, a Rust REST API (`rest-service`) built with actix-web that handles connection metadata CRUD and credential management, and a Rust gRPC service (`flight-service`) built with tonic that implements the Apache Arrow Flight protocol for high-throughput columnar data transfer.

The controller watches the `DataConnectService` custom resource and reconciles the desired state by creating or updating Deployments, Services, ConfigMaps, NetworkPolicies, RBAC bindings, and HTTPRoutes. It resolves container images from `RELATED_IMAGE_*` environment variables to support disconnected/air-gapped deployments, and integrates with the OpenShift APIServer resource to dynamically adopt the cluster's TLS security profile. Connection metadata is persisted in a shared PostgreSQL database, while actual data retrieval flows through the pluggable connector architecture in the flight service, using Apache Arrow RecordBatch as the universal interchange format.

## Architectural Analysis

Data Connect Hub follows a clear separation between control plane and data plane. The Go controller handles Kubernetes lifecycle orchestration—CRD reconciliation, resource creation, TLS profile watching, and Gateway API routing—while the Rust services handle all data-path operations. This split allows the controller to remain a lightweight operator (using controller-runtime patterns like leader election and health probes) while the data services can independently scale and be optimised for throughput.

The connector architecture is notably well-designed: each data source connector is a separate Rust crate implementing shared traits from `libs/commons`, compiled into the flight-service binary via Cargo feature flags. The `ConnectorsRegistry` pattern enables runtime-configurable connector enablement through TOML configuration, meaning the same binary can be deployed with different connector sets without recompilation.

Authentication follows a two-layer model. The REST API is fronted by a `kube-rbac-proxy` sidecar that intercepts all requests on port 8443, performs Kubernetes TokenReview and SubjectAccessReview checks scoped to the namespace extracted from the `X-Tenant-Id` header, and only then proxies authenticated traffic to the application on port 8080. The flight service implements its own Tower-based `AuthLayer` middleware that performs the same Kubernetes token validation directly, without a sidecar. This dual approach means the REST API's auth enforcement point is external to the application (Kubernetes-enforced via kube-rbac-proxy) while the flight service's is application-enforced—a notable asymmetry.

The cryptographic posture is split across languages. The Go controller uses `GOEXPERIMENT=strictfipsruntime` with `CGO_ENABLED=1` on a UBI 9 base, satisfying check-payload requirements. The Rust services use `rustls` with the `aws_lc_rs` cryptographic provider (a FIPS-capable library), though the `ring` provider is also present in `Cargo.lock`—the explicit `install_default()` call for `aws_lc_rs` at service startup ensures it is selected at runtime. All three Konflux container images use the `ubi9/ubi-minimal-pqc` (post-quantum cryptography) base image.

NetworkPolicies are deployed for both services but currently use allow-all rules (`ingress: [{}], egress: [{}]`), with comments indicating they are placeholders to be tightened once the gateway/client topology stabilises. This is a security gap worth tracking.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace SubjectAccessReview via X-Tenant-Id header | Kubernetes (kube-rbac-proxy for REST, application AuthLayer for Flight) | Flight service auth is application-enforced rather than sidecar-enforced; a bug in AuthLayer could bypass tenant isolation |
| Data storage | Shared PostgreSQL database with tenant_id column filtering | Application (pg-meta-store query filters) | Application-enforced data isolation; a query bug could leak data across tenants; no database-level row security |
| Network traffic | NetworkPolicy per service (currently allow-all) | Kubernetes (placeholder) | NetworkPolicies exist but are allow-all; no actual network isolation between tenants |
| Compute & resources | Shared service pods (no per-tenant compute isolation) | None | Single deployment serves all tenants; no ResourceQuota or LimitRange per tenant |
| Configuration & secrets | Per-namespace Secrets accessible via kube-rbac-proxy authorization | Kubernetes (SubjectAccessReview for secret export) | Database credentials are shared across all tenants in a single mounted Secret |
| API scoping | Namespace-scoped SubjectAccessReview for each API operation | Kubernetes (kube-rbac-proxy config maps HTTP methods to K8s verbs on per-namespace virtual resources) | Comprehensive path-to-resource mapping covers all API endpoints |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL metadata store | tenant_id column in database tables | Application query filter (pg-meta-store tenant_id parameter) |
