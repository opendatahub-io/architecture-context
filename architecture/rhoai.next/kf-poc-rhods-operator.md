## Purpose

**Short**: Platform operator that orchestrates the lifecycle of all Red Hat OpenShift AI data science components through cluster-scoped CRDs.

**Detailed**: kf-poc-rhods-operator is a proof-of-concept fork of the RHOAI/ODH platform operator (rhods-operator) built with controller-runtime. It serves as the central control plane for RHOAI, managing the deployment and configuration of 11 data science components — Dashboard, Workbenches, KServe, ModelMesh Serving, Data Science Pipelines, CodeFlare, Ray, Kueue, TrustyAI, Training Operator, and Model Registry — through a declarative `DataScienceCluster` custom resource.

The operator uses a two-phase initialization model: a `DSCInitialization` CR bootstraps shared platform infrastructure (applications namespace, monitoring, Service Mesh integration, trusted CA bundles, and network policies), while a `DataScienceCluster` CR controls which components are enabled (`Managed`) or disabled (`Removed`). Component manifests are fetched from upstream repositories at build time via `get_all_manifests.sh` and deployed using kustomize. The operator also runs a `SecretGenerator` controller for OAuth credential management and a `CertConfigmapGenerator` for distributing trusted CA certificates across namespaces.

This fork targets the `rhoai-2.14` branch of component manifests, pinning to `red-hat-data-services` organization repositories. It represents a KubeFlow-oriented proof-of-concept within the RHOAI operator lineage.

## Architectural Analysis

The operator follows a hub-and-spoke architecture pattern common to platform operators. A single operator binary hosts four controllers — `DSCInitializationReconciler`, `DataScienceClusterReconciler`, `SecretGeneratorReconciler`, and `CertConfigmapGeneratorReconciler` — that coordinate through shared Kubernetes API watches rather than direct in-process communication. The `DSCInitialization` controller runs first to establish namespace prerequisites and platform infrastructure, while the `DataScienceCluster` controller depends on DSCI state to deploy individual components.

The component abstraction layer (`components.ComponentInterface`) uses Go reflection to iterate over struct fields in `DataScienceClusterSpec.Components`, treating each as a pluggable reconciliation unit. Each component implements `ReconcileComponent`, `Cleanup`, and manifest override hooks. This design makes adding new components straightforward but creates a large RBAC surface — the operator's ClusterRole has 89 rules spanning nearly every API group in the cluster because each component's RBAC requirements accumulate in a single role.

The operator's cache configuration is platform-aware, scoping Secret and Deployment watches to specific namespaces based on the detected platform type (ManagedRhods, SelfManagedRhods, or community ODH). This reduces memory pressure but creates implicit coupling between namespace naming conventions and operator behavior.

Webhook enforcement is intentionally minimal: the validating webhook prevents creation of more than one DSC or DSCI instance (singleton pattern), and the mutating webhook sets default values for ModelRegistry's `registriesNamespace`. Both use a `failurePolicy: Fail` strategy, meaning webhook unavailability blocks these API operations.

The Service Mesh and Serverless integrations are configurable through the DSCI spec, with defaults pointing to `data-science-smcp` in `istio-system`. The operator creates Istio Gateway resources for KServe traffic routing, including both ingress and local gateway configurations with associated Kubernetes Services.
