## Purpose

**Short**: A pluggable gRPC service that inspects and mutates LLM inference request and response payloads in the llm-d data plane, enabling payload-aware routing and model selection via the Envoy External Processing (ext-proc) protocol.

**Detailed**: The Inference Payload Processor (IPP) sits alongside the inference gateway's proxy (Envoy) and is invoked over the Envoy ext-proc gRPC protocol for every HTTP lifecycle event -- request headers, request body, response headers, response body, and trailers. Because it sees the full payload, IPP can shape requests and responses in arbitrary ways through a configurable plugin pipeline.

IPP's flagship capability is multi-pool routing: extracting the model name from the request body and injecting routing headers so a single Gateway endpoint can front multiple base models and LoRA adapters. Each InferencePool serves one base model, and IPP's `base-model-extractor` plugin maps LoRA adapter names back to their base using labeled ConfigMaps. The `body-field-to-header` plugin copies the `model` field into `X-Gateway-Model-Name`, while `base-model-to-header` resolves adapters to their base model via ConfigMap-backed mappings and injects `X-Gateway-Base-Model-Name`. The proxy's HTTPRoute rules then match on these headers to select the correct InferencePool. This composes with the llm-d Router's Endpoint Picker (EPP) -- IPP decides which pool serves a request while the EPP decides which pod within that pool.

The component also provides a model selection framework (`Filter -> Score -> Pick`) that can choose which model to serve a request based on cost, load, session affinity, or any combination of pluggable scorers. A data layer maintains cross-request state through event-driven extractors and periodic collectors, decoupled from the latency-sensitive request path. All behavior is configured via a `PayloadProcessorConfig` YAML document; custom plugins can be added without forking the framework.

## Architectural Analysis

IPP is architecturally a stateless data-plane service built on controller-runtime for lifecycle management, but it does not reconcile CRDs in the operator pattern. It uses controller-runtime purely as a process manager for multiple gRPC servers and a metrics endpoint. The `PayloadProcessorConfig` type carries kubebuilder markers but is explicitly documented as not used as a real Kubernetes CRD -- it is deserialized from YAML config files or inline text, not from the Kubernetes API.

The processing pipeline follows a fixed stage ordering -- PreProcessors -> ProfilePicker -> Profile Request Plugins -> [Model Server] -> Profile Response Plugins -> PostProcessors -- with all concrete behavior delegated to plugins. The profile mechanism allows a single IPP deployment to apply different processing logic to different traffic classes (e.g. lightweight header extraction vs. full model selection). The data layer runs asynchronously: request/response events are delivered non-blocking on a buffered channel to extractors, while collectors poll on their own intervals with jittered startup.

The model selection pipeline directly adapts the Kubernetes scheduler's `Filter -> Score -> Reserve -> Bind` pattern, reducing it to three phases appropriate for stateless model selection. The CostGuard scorer implements an epsilon-greedy multi-armed bandit algorithm for cost-aware model routing, using t-digest data structures for efficient quantile estimation, demonstrating the framework's ability to support complex, statistically-grounded routing policies.

The ext-proc server supports optional TLS via self-signed certificates generated at startup (4096-bit RSA, 10-year validity). When deployed with Istio, a DestinationRule configures SIMPLE TLS with `insecureSkipVerify: true`, which is expected since the certificate is self-signed and communication is pod-local. The health server is a separate plaintext gRPC service on a distinct port, consistent with the Kubernetes health probe model.

A notable design trade-off is that request and response bodies are accumulated in memory without an upper bound (noted in a TODO in `pkg/handlers/server.go:181`), which poses an OOM risk for very large payloads. The codebase includes deduplication logic for Envoy's re-delivery of EndOfStream chunks in FULL_DUPLEX_STREAMED mode.

IPP's proxy integration strategy abstracts the provider: the Helm chart generates either an Istio `EnvoyFilter` (which inserts the ext-proc filter into the Gateway's HTTP filter chain), a GKE `GCPRoutingExtension` (which registers IPP as a native routing extension), or nothing (`none` mode) for custom wiring. This provider abstraction keeps the core service independent of any particular service mesh or cloud platform.
