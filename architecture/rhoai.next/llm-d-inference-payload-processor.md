## Purpose

**Short**: Pluggable Envoy ext-proc service that inspects and mutates inference request/response payloads for payload-aware routing and model selection in the llm-d data plane.

**Detailed**: The Inference Payload Processor (IPP) is a gRPC service implementing the Envoy External Processing (ext-proc) protocol. It runs alongside the inference gateway's proxy (Envoy) and is invoked on each HTTP lifecycle event — request headers, request body, response headers, and response body — enabling real-time, payload-aware processing of LLM inference traffic.

IPP's flagship capability is multi-pool routing: extracting signals from the request body (such as the model name) and injecting headers so a single Gateway endpoint can front multiple base models and LoRA adapters. The `body-field-to-header` plugin copies the `model` field into `X-Gateway-Model-Name`, while the `base-model-to-header` plugin maps LoRA adapter names to their base models via ConfigMap-backed mappings and injects `X-Gateway-Base-Model-Name`. The proxy's HTTPRoute rules then match on these headers to select the correct InferencePool.

Beyond routing, IPP provides a model selection framework (`Filter → Score → Pick`) that chooses which model serves a request based on cost, load, session affinity, or custom signals. The framework is fully pluggable — all behavior is implemented as plugins configured via a `PayloadProcessorConfig` YAML document. IPP complements the llm-d Router (EPP), which selects endpoints within a pool; IPP selects which pool serves the request.

## Architectural Analysis

The Inference Payload Processor demonstrates a well-designed plugin architecture that mirrors Kubernetes scheduling patterns. The `Filter → Score → Pick` model selection pipeline directly adapts the Kubernetes scheduler's `Filter → Score → Reserve → Bind` pattern, reducing it to three phases appropriate for stateless model selection. This design choice enables the same composability — multiple scorers with configurable weights, pluggable pickers for different selection strategies — while keeping the latency budget tight for the ext-proc request path.

The data layer architecture is particularly noteworthy for its separation of concerns. Request-path plugins (scorers, filters) never write to the datastore directly during request processing; instead, events are emitted asynchronously to a buffered channel (capacity 10,000) and processed by extractors in a dedicated goroutine. This eliminates datastore write contention from the request-critical path. The trade-off is eventual consistency — in-flight request counts and cost distributions lag behind reality by at most one event loop iteration plus extraction time. The `request-metadata-extractor` has a known limitation where counters leak if responses never arrive (e.g., context cancellation), which could skew the `inflight-requests-scorer` over time.

The CostGuard scorer (`pkg/framework/plugins/modelselector/scorer/costguard/plugin.go`) implements an epsilon-greedy multi-armed bandit algorithm for cost-aware model routing, using t-digest data structures for efficient quantile estimation. This is sophisticated optimization for balancing exploration (trying under-observed models) against exploitation (routing to known-cheap models), with configurable alpha/lambda parameters controlling tail cost sensitivity. The algorithm demonstrates the framework's ability to support complex, statistically-grounded routing policies through its plugin interfaces.

IPP's proxy integration strategy is notable for its provider abstraction. The Helm chart generates either an Istio `EnvoyFilter` (which inserts the ext-proc filter into the Gateway's HTTP filter chain) or a GKE `GCPRoutingExtension` (which registers IPP as a native routing extension), depending on `provider.name`. The `none` mode deploys IPP without any proxy integration, allowing custom wiring. The Istio path uses a `DestinationRule` with `insecureSkipVerify: true` for the TLS connection to IPP — acceptable for pod-local self-signed TLS but worth noting for security auditors.

The TLS implementation has two modes: self-signed certificates generated at startup (`internal/tls/tls.go`, 4096-bit RSA, 10-year validity) for the ext-proc gRPC endpoint, and a hot-reloadable `CertReloader` (`pkg/common/certs.go`) that watches certificate files via fsnotify with 250ms debouncing. The self-signed mode is clearly designed for development and Istio-meshed environments where the mesh provides the real TLS termination. For production RHOAI deployment, the CertReloader path with externally provisioned certificates would be the expected pattern.

A gap worth noting is the absence of Konflux Dockerfiles, RPM lock files, and Hermeto prefetch integration. The upstream Dockerfile uses `CGO_ENABLED=0` with a distroless base image, which is incompatible with FIPS requirements (check-payload requires dynamically linked Go binaries with OpenSSL). The downstream RHOAI integration would need to add Konflux build infrastructure with UBI base images, `CGO_ENABLED=1`, and `GOEXPERIMENT=strictfipsruntime` for FIPS compliance.
