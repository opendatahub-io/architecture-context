## Purpose

**Short**: Kubernetes operator that automates the deployment, discovery, security, and observability of AI agents and tools via the A2A protocol, SPIFFE identity, and OAuth2 authentication.

**Detailed**: The Kagenti Operator (shipped as `agents-operator` in RHOAI) manages AI agent workloads on Kubernetes and OpenShift. It provides two primary CRDs -- `AgentRuntime` for enrolling workloads into the Kagenti platform with identity, auth, and observability, and `AgentCard` for discovering and verifying agent metadata via the A2A (Agent-to-Agent) protocol. When an `AgentRuntime` CR is created, the operator applies labels, injects AuthBridge sidecar containers (for mTLS, token exchange, and protocol-aware request processing), and manages rolling updates on config change.

The operator implements a multi-layer trust model: JWS signature verification of agent cards, SPIFFE identity binding via SPIRE, Sigstore supply-chain attestation, and verification-driven NetworkPolicy enforcement. It integrates with Keycloak for OAuth2 client registration, MLflow for experiment tracking, cert-manager for TLS certificate management, Kuadrant for API management, and Tekton for CI/CD pipeline configuration. Controllers are conditionally registered based on CRD availability, making the operator adaptable to different cluster configurations.

The repository also contains the AuthBridge proxy (a sidecar providing forward/reverse proxy, mTLS, and token exchange), the Token Broker (an OAuth2 session broker for agent-to-resource-server authentication), and the Bundle Service (an OPA policy bundle distributor for AuthorizationPolicy CRs).

## Architectural Analysis

The Kagenti Operator implements a sophisticated layered trust architecture for AI agent workloads. At the core is a "trust chain" that progresses through four stages: (1) A2A agent card discovery, (2) JWS cryptographic signature verification using SPIRE X.509 certificates, (3) SPIFFE identity binding against a configured trust domain, and (4) enforcement via label-driven NetworkPolicies. Each stage builds on the previous one, and the operator supports an audit mode that logs failures without blocking -- critical for gradual rollout in production environments.

The sidecar injection system is the operator's most complex component. The AuthBridge mutating webhook implements a multi-layered configuration resolution chain: per-workload AgentRuntime CR fields override namespace-level ConfigMaps, which override cluster-level defaults. The webhook supports four deployment shapes (proxy-sidecar, envoy-sidecar, lite, waypoint), three mTLS modes (disabled, permissive, strict), two egress enforcement modes (enforce-redirect with iptables, none for cooperative HTTP_PROXY), and optional TLS bridge (decrypt agent egress HTTPS for transparent pipeline inspection). The `proxy-init` init container runs as root with NET_ADMIN capability to set up iptables rules, but drops all other capabilities and is NOT privileged -- it uses DNAT instead of route_localnet to avoid the security implications of privileged mode.

The operator demonstrates strong conditional registration patterns. Controllers for SPIRE, cert-manager, Kuadrant, Tekton, and MLflow are only registered when their respective CRDs are detected at startup (via Discovery API queries with retries). This makes the operator deployable on clusters without these optional dependencies. The tradeoff is that CRDs installed after operator startup require a pod restart to activate their controllers. Bootstrap runnables handle initial resource creation (ZTWIM CR, Kuadrant CR, Keycloak realm) with leader-election-guarded idempotent patterns.

The Sandbox workload type (agents.x-k8s.io/v1alpha1) receives special treatment throughout the codebase. Unlike Deployments and StatefulSets that can be mutated with rolling updates, Sandboxes require a two-phase restart: scale to 0, set a restart-pending annotation, then scale back to 1 after clearing stale pod-name annotations. This pattern is implemented in the AgentRuntime controller and appears to work around Sandbox controller semantics where the pod-name annotation becomes stale after scaling.

A notable security concern is the Token Broker's in-memory architecture: it stores all session state and cached tokens in-process memory with no replication. While this simplifies the deployment (no external state store), it means a Token Broker pod restart loses all active sessions. The Token Broker also has no Konflux Dockerfile variant and builds with `CGO_ENABLED=0` (static linking), which means it would not pass the check-payload FIPS gate. This is a gap for RHOAI productization.
