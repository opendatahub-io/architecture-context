## Purpose

**Short**: Kubernetes operator that automates deployment, discovery, identity, authentication, and observability for AI agents on OpenShift AI.

**Detailed**: The agents-operator (upstream: kagenti-operator) is the control-plane component that brings AI agent workloads into the RHOAI platform. It provides a declarative, Custom Resource-driven workflow: users create an `AgentRuntime` CR pointing at a Deployment or StatefulSet, and the operator applies labels, computes configuration hashes for rolling updates, and coordinates sidecar injection through a mutating admission webhook.

The webhook (AuthBridge injection) transparently adds authentication and identity sidecars — an OAuth2/OIDC-aware proxy (authbridge-proxy or authbridge-envoy), SPIFFE-based workload identity, and Keycloak client registration — into agent pods without application code changes. The operator also drives agent discovery: it watches labeled workloads, auto-creates `AgentCard` CRs, fetches A2A-protocol metadata from running agents, verifies JWS cryptographic signatures using SPIRE X.509 trust bundles, and enforces identity-binding policies via automatically managed NetworkPolicies.

Supporting subsystems include MLflow integration (auto-discovering MLflow instances, creating per-agent experiments, injecting tracing environment variables), Kuadrant API gateway integration, TektonConfig reconciliation, SPIRE zero-trust workload identity management, and a bundle-service for serving authorization policy bundles to AuthBridge sidecars. A separate token-broker service mediates OAuth2 token flows for interactive agent sessions.

## Architectural Analysis

The agents-operator follows a hub-and-spoke controller architecture centered on the `AgentRuntime` CR as the primary enrollment primitive. The AgentRuntime controller sits at the hub: when a user creates an AgentRuntime pointing to a workload, it applies canonical labels (`kagenti.io/type`), computes a config-hash annotation for rollout detection, and triggers sidecar injection. The spokes are a constellation of secondary controllers that react to the labeled workloads and injected resources.

The agent lifecycle is orchestrated through three phases. First, the AgentRuntime controller labels the target workload and the mutating webhook injects sidecars on the next pod creation. Second, the AgentCard sync controller detects the labeled Deployment/StatefulSet and auto-creates an AgentCard CR. Third, the AgentCard controller fetches the A2A agent-card.json from the running pod, performs JWS signature verification against SPIRE-issued X.509 trust bundles, evaluates SPIFFE identity binding, and sets status conditions that the NetworkPolicy controller reads to enforce permissive or restrictive network policies.

The AuthBridge sidecar architecture is notable for its zero-trust, transparent token management. The proxy-sidecar (or envoy-sidecar) handles both inbound JWT validation and outbound token exchange (RFC 8693) without application awareness. Credential provisioning is fully automated: the operator's ClientRegistrationReconciler registers each workload with Keycloak, provisions client secrets, and mounts them via shared volumes. SPIFFE workload identity is obtained in-process via `go-spiffe` X509Source rather than from sidecar files, avoiding per-handshake I/O. Three deployment shapes are supported: proxy-sidecar (default, HTTP forward+reverse proxy), envoy-sidecar (Envoy ext_proc gRPC), and lite (auth gates only, no protocol parsers).

A significant design decision is the conditional controller pattern: many secondary controllers (MLflow, Kuadrant, TektonConfig, SPIRE, SharedTrust) use runtime API discovery to determine whether their target CRDs exist before registering watches. This allows the operator to run on clusters without optional dependencies without failing at startup, at the cost of requiring a pod restart if CRDs are installed after operator startup.

The trust model is layered. At the transport level, mTLS can be configured per-agent (strict or permissive) using SPIRE-issued SVIDs. At the application level, JWT validation enforces per-request authentication. At the agent-to-agent level, AgentCard JWS signature verification provides cryptographic attestation of agent identity. NetworkPolicies provide Kubernetes-native network isolation based on verification status. The IBAC (intent-based access control) plugin in AuthBridge adds OPA-based per-request policy evaluation using bundles served by the bundle-service.

The RBAC surface is broad — the manager-role ClusterRole spans 20+ API groups — reflecting the operator's role as a platform orchestrator that must manage workloads, RBAC, networking, certificates, routes, Keycloak, SPIRE, MLflow, and Tekton resources across namespaces.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-workload Keycloak client registration with unique clientID; SPIFFE identity per ServiceAccount; mTLS between sidecars | Keycloak + SPIRE + Kubernetes | Single Keycloak realm for all tenants — realm isolation not enforced |
| Data storage | No persistent data — agent cards fetched live; token cache is in-memory per-session | Application | Token Broker is a single instance; pod restart loses all sessions |
| Network traffic | Auto-generated NetworkPolicies based on AgentCard signature verification status; namespace-level Istio ambient mesh enrollment | Kubernetes NetworkPolicy, Istio | NetworkPolicy enforcement is opt-in; without it, no network isolation between agents |
| Compute & resources | None — no ResourceQuota or LimitRange management | N/A | Compute isolation delegated to cluster admin |
| Configuration & secrets | Per-namespace ConfigMaps (authbridge-config); per-workload Keycloak credential Secrets; cluster defaults in operator namespace | Kubernetes | Namespace admin can modify authbridge-config to change auth behavior for their namespace |
| API scoping | Namespace-scoped CRD watches; AgentCard sync controller uses namespace-scoped field indices | Kubernetes RBAC | Operator SA has cluster-wide read on Deployments, StatefulSets, Pods |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Keycloak | Single realm (kagenti) | Per-client clientID scoped to namespace/workload; audience and token-exchange scope per client |
| SPIRE | Single trust domain | Per-workload SPIFFE ID (spiffe://{domain}/ns/{ns}/sa/{sa}); identity binding validates trust domain prefix |
| Token Broker | Single instance | Per-session keys tied to JWT subject; session ownership validated per request |
| Bundle Service | Single instance | Per-SPIFFE-ID bundle resolution; policy scoping via AuthorizationPolicy CRs |
| MLflow | Single instance (per cluster) | Per-agent experiment; RBAC Role scoped to single experiment via resourceNames |
