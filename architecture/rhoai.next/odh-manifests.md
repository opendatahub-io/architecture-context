## Purpose

**Short**: Central Kustomize manifest repository that packages and organizes the deployment definitions for all Open Data Hub and Red Hat OpenShift AI platform components.

**Detailed**: odh-manifests is a manifest aggregation repository that collects, organizes, and configures the Kubernetes deployment manifests for the entire ODH/RHOAI platform. It does not contain application source code — instead, it bundles CRD definitions, RBAC configurations, Deployment specs, Service definitions, and kustomize overlays for approximately 30 platform components including KServe, ModelMesh, the ODH Dashboard, Data Science Pipelines, Notebook Controllers, TrustYAI, Ray, Grafana, Prometheus, and others.

The repository uses KfDef custom resources to define deployment profiles (e.g., `odh-core`, `model-serving`) that compose subsets of components. Each component subdirectory contains its own kustomize base and overlays, parameterized via `params.env` files that primarily define container image references. The RHOAI distribution adds overlays (e.g., `odh-dashboard/overlays/rhods`) that rebrand and reconfigure components for the Red Hat productized offering. A root Dockerfile packages all manifests as a tar.gz archive in a UBI-based container image for distribution.

## Architectural Analysis

odh-manifests functions as the deployment "bill of materials" for the ODH/RHOAI platform. Its architecture is notable in several respects:

**Composition model**: The repository uses KfDef resources to define named deployment profiles. The `odh-core.yaml` profile includes 11 components (odh-common, odh-dashboard, prometheus, grafana, notebook-controller, model-mesh, modelmesh-monitoring, data-science-pipelines-operator), while `kfctl_openshift_model_serving.yaml` provides a minimal model-serving-only profile. This enables flexible installation topologies where operators can choose which components to deploy.

**Image parameterization strategy**: All container image references are externalized into `params.env` files consumed by kustomize `configMapGenerator` directives. This separation lets downstream builds (RHOAI) swap upstream community images for productized registry.redhat.io references without modifying deployment manifests. The data-science-pipelines-operator params.env demonstrates this pattern most clearly, mapping all pipeline component images including the oauth proxy.

**CRD bundling**: Rather than requiring separate CRD installation, odh-manifests bundles CRD definitions from multiple upstream projects. The kserve-built directory alone contains a 19,026-line monolithic manifest embedding all KServe CRDs (InferenceGraph, InferenceService, ServingRuntime, TrainedModel), RBAC, webhooks, and controller deployment. This bundling simplifies installation but creates a maintenance burden — CRD updates require regenerating or manually syncing this large file.

**Serving runtime templates**: The repository defines two categories of serving runtimes: (1) ClusterServingRuntime resources in `model-mesh/odh-modelmesh-controller/runtimes/` for multi-model serving via ModelMesh (Triton, MLServer, OVMS, TorchServe), and (2) OpenShift Template resources in `odh-dashboard/modelserving/` for single-model KServe serving (OVMS, Caikit-TGIS, TGIS standalone). This dual-path architecture reflects the platform's support for both multi-model (ModelMesh) and single-model (KServe) inference patterns.

**RHOAI differentiation**: The RHOAI overlay in `odh-dashboard/overlays/rhods` applies JSON patches to rename resources (e.g., `odh-dashboard` → `rhods-dashboard`), swap image references, and adjust RBAC bindings. The overlay also switches the dashboard image to `quay.io/opendatahub/odh-dashboard:main` and pins the OAuth proxy to a specific digest.

**Architectural risk**: The odh-model-controller deployment is configured with 3 replicas and pod anti-affinity for HA, but its RBAC grants extremely broad cluster-wide permissions including access to secrets, service accounts, network policies, Istio resources (VirtualServices, PeerAuthentications, ServiceMeshMembers), and KServe resources. The combination of kube-rbac-proxy for metrics authentication and leader election provides reasonable security posture, but the breadth of RBAC permissions represents a significant blast radius if the controller is compromised.
