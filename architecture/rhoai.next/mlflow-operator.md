## Purpose

**Short**: Kubernetes operator that manages the lifecycle of MLflow tracking server deployments on OpenDataHub and Red Hat OpenShift AI platforms.

**Detailed**: The MLflow Operator is a controller-runtime based Kubernetes operator that reconciles cluster-scoped `MLflow` custom resources into fully configured MLflow tracking server deployments. It uses an embedded Helm chart to render Deployment, Service, NetworkPolicy, ServiceAccount, RBAC, PVC, ServiceMonitor, and CronJob resources, then applies them via Server-Side Apply. The operator handles database migration orchestration (scaling down the deployment, running migration Jobs, scaling back up), Gateway API HTTPRoute creation for platform ingress, OpenShift ConsoleLink integration, CA bundle management (platform and custom), garbage collection CronJobs, and trace archival CronJobs.

The operator also implements a module handoff pattern via the `MLflowOperator` CRD (`components.platform.opendatahub.io/v1alpha1`), which allows the platform operator (opendatahub-operator/rhods-operator) to project gateway configuration and manage the component lifecycle. A NamespaceRBAC controller optionally manages per-namespace RoleBindings for workspace access control, reading group membership from the platform Auth CR (`services.platform.opendatahub.io/v1alpha1`).

## Architectural Analysis

The MLflow Operator follows a hybrid deployment pattern: the operator itself is deployed via kustomize (with ODH, OpenShift, and RHOAI overlays), while the operand (MLflow tracking server) is deployed by rendering an embedded Helm chart at reconciliation time. This separation allows the operator's deployment model to conform to platform operator conventions (kustomize + configMapGenerator for parameterization) while the operand's deployment model benefits from Helm's templating flexibility for complex conditional logic (CA bundle volumes, storage toggles, NetworkPolicy egress rules, garbage collection and trace archival CronJobs).

The migration orchestration is a distinctive architectural feature. Rather than letting the MLflow server self-migrate on startup (which risks race conditions with multiple replicas), the operator performs a controlled blue/green migration: it scales the Deployment to zero replicas, creates a one-shot Job using the same container image and volume mounts as the server, waits for the Job to complete, then restores the Deployment. The migration script uses explicit exit codes (10-15) to distinguish terminal failures (version mismatch, unsupported backend) from retryable failures, enabling the operator to make intelligent retry decisions. The operator-level retry delay is anchored to the Kubernetes Job's failure transition time rather than the reconcile timestamp, preventing retry drift.

The module handoff pattern (MLflowOperator CR) represents a coordinated ownership transfer between the platform operator and the component operator. When `ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER` is enabled, the MLflow operator waits for the platform operator to create and populate the MLflowOperator CR with gateway configuration before reconciling any MLflow CRs. This ensures the operator has the correct gateway domain, gateway name, and section title before creating HTTPRoutes and ConsoleLinks. The MLflowOperator controller also publishes release handshake status (platform version from the odh-mlflowoperator-config ConfigMap and MLflow version from the build-injected ldflags) back to the module CR status, enabling the platform operator to track component versions.

The NamespaceRBAC controller implements a label-driven workspace access model. Namespaces labeled with `opendatahub.io/global-mlflow-workspace=<mlflow-cr-name>` receive two RoleBindings: one granting `mlflow-view` to all Auth CR allowedGroups + adminGroups, and another granting `mlflow-edit` to adminGroups only. These RoleBindings are owned by the MLflow CR, so they are cleaned up when the CR is deleted. The controller watches for changes to the Auth CR, MLflow CRs, and labeled Namespaces to keep RoleBindings synchronized. The view/edit split leverages Kubernetes aggregate ClusterRoles, which also aggregate into the built-in admin/edit/view ClusterRoles for seamless RBAC integration.

Security is enforced at multiple layers: TLS encryption for the MLflow server (via OpenShift service-ca auto-provisioned certificates), SelfSubjectAccessReview-based authorization for every MLflow API request (using pseudo-resources like experiments, datasets, registeredmodels mapped to Kubernetes RBAC), NetworkPolicy restricting both ingress and egress, and CA bundle management that combines system CAs, platform CAs, and custom CAs for outbound TLS trust. The operator itself fetches the cluster TLS profile at startup and applies it to its metrics server, with a watcher that triggers operator restart if the profile changes.
