## Purpose

**Short**: Kubernetes operator that manages the lifecycle of MLflow tracking server deployments on OpenShift AI, including database migrations, ingress routing via Gateway API, and workspace-scoped RBAC.

**Detailed**: The MLflow Operator is a controller-runtime based Kubernetes operator that reconciles two custom resources: `MLflow` (the primary workload CR defining an MLflow tracking server instance) and `MLflowOperator` (a platform module CR used for handoff coordination with the ODH/RHOAI platform operator). The operator renders a bundled Helm chart to produce the MLflow server Deployment, Service, NetworkPolicy, ServiceAccount, ClusterRole, ClusterRoleBinding, PVC, ServiceMonitor, and CronJobs (for garbage collection and trace archival). It also dynamically creates HTTPRoute resources for Gateway API ingress and ConsoleLink resources for the OpenShift console.

A key feature is the operator-managed database migration orchestration: when the supported MLflow version changes or a force-migrate annotation is applied, the operator scales the MLflow Deployment to zero, runs a migration Job using an embedded Python script, and only restores replicas after the migration succeeds. The operator integrates with the RHOAI platform through the `MLflowOperator` module CR (which projects gateway domain, gateway name, and section title from the platform operator), the `Auth` CR (for workspace RBAC group resolution), and the OpenShift TLS profile API (for cluster-wide TLS cipher configuration). A dedicated NamespaceRBACReconciler manages workspace-scoped RoleBindings in namespaces labeled for MLflow workspace access, syncing view/edit permissions from the platform Auth CR's allowed and admin groups.

## Architectural Analysis

The MLflow Operator follows a Helm-driven reconciliation pattern: the controller renders an embedded Helm chart (`charts/mlflow`) with values derived from the `MLflow` CR spec and operator configuration, then applies the resulting Kubernetes objects via Server-Side Apply. This approach offers the composability of Helm templates (conditional GC CronJobs, conditional trace archival, CA bundle sidecars) while maintaining the lifecycle guarantees of a controller-runtime operator (watches, owner references, status reconciliation). The chart is not published as a standalone Helm release; it exists solely as an internal rendering engine.

The database migration orchestration is notable for its robustness. The operator implements a multi-phase migration flow: detect version mismatch → scale Deployment to zero → create migration Job (with the same container image, TLS certs, and CA bundles as the Deployment) → monitor Job status → retry on transient failures → mark terminal failures sticky → restore replicas only after success. The migration Job uses embedded Python script (`mlflow_db_migrate.py`) with explicit exit codes that the operator interprets to distinguish terminal failures (schema mismatch, unsupported backend) from retryable failures. A force-migrate annotation allows admins to manually trigger reruns after fixing issues.

The RBAC architecture has three distinct layers: (1) **Operator RBAC** — ClusterRole and namespace-scoped Role granting the operator permissions to manage resources; (2) **MLflow server RBAC** — a shared ClusterRole/ClusterRoleBinding granting the MLflow pod permissions to enumerate namespaces, read workspace secrets, and read MLflowConfig CRs; and (3) **Workspace RBAC** — the NamespaceRBACReconciler dynamically creates RoleBindings in labeled namespaces, binding platform Auth CR groups to aggregate ClusterRoles (mlflow-view, mlflow-edit). The aggregate roles use pseudo-resources (experiments, datasets, registeredmodels, gatewayendpoints, mcpservers) that are checked via SelfSubjectAccessReview by the MLflow kubernetes-auth plugin, not actual CRDs. This design enables fine-grained per-workspace authorization without dedicated admission webhooks.

The TLS configuration deserves attention: the operator fetches the OpenShift cluster TLS profile at startup and uses a SecurityProfileWatcher to restart if the profile changes. The MLflow server itself runs uvicorn with direct TLS termination (SSL keyfile/certfile from service-ca provisioned certs), and on OpenShift the operator injects `UVICORN_SSL_CIPHERS=PROFILE=SYSTEM` to align cipher selection with the cluster-wide profile. The CA bundle handling uses an init container to combine system CAs, platform trusted CAs, and custom CAs into a single PEM file, plus a sidecar watcher that regenerates the combined bundle when ConfigMap contents change.

Network isolation is enforced via NetworkPolicies on both the MLflow Deployment and migration Jobs. The Deployment NetworkPolicy allows ingress from any namespace (MLflow is a cluster-wide service accessed by the gateway, dashboard, and Prometheus from varying namespaces) but restricts egress to DNS, HTTPS, database ports, and S3-compatible storage ports. The migration Job NetworkPolicy is stricter — it blocks all ingress and only allows DNS and database egress. Users can customize egress rules via the CR spec's `networkPolicyEgressRules` (full replacement) and `networkPolicyAdditionalEgressRules` (append) fields.
