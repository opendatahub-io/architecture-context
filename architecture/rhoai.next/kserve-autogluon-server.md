## Purpose

**Short**: KServe model serving runtime for AutoGluon TabularPredictor and TimeSeriesPredictor models, providing REST v1/v2 inference endpoints.

**Detailed**: The KServe AutoGluon Server is a Python-based inference runtime that serves models trained with the AutoGluon ML framework. It supports two predictor types: **TabularPredictor** (for classification and regression on structured/tabular data) and **TimeSeriesPredictor** (for time series forecasting). The server auto-detects the predictor type at startup by attempting to load the model directory with each predictor class.

For tabular models, the server supports both KServe inference protocol v1 (JSON) and v2 (tensor-based), including optional probability output via `predict_proba()` for classification tasks. For time series models, only REST v1 JSON is supported, with structured history and known-covariates inputs. The server integrates with KServe's model storage system (supporting S3, GCS, Azure Blob, and local filesystem) for model downloading.

The AutoGluon server ships as a single container image built by Konflux, using an AIPCC CPU base image. It is deployed as part of RHOAI's KServe serving infrastructure — when a user creates an `InferenceService` CR with `modelFormat.name: autogluon`, the KServe controller provisions a pod running this image, pointed at the user's saved predictor artifact.

## Architectural Analysis

The AutoGluon server is architecturally a thin wrapper around AutoGluon's predictor classes, adapting them to the KServe inference protocol. The core design pattern is a **strategy pattern with auto-detection**: `AutoGluonDetectedModel` acts as a facade that detects whether a saved model is tabular or time series, then delegates all inference calls to the appropriate implementation (`AutoGluonTabularModel` or `AutoGluonTimeSeriesModel`). This auto-detection is implemented via a try-load approach in `predictor_detect.py` — it attempts `TimeSeriesPredictor.load()` first (because tabular models are more common and would fail faster as a fallback), then falls back to `TabularPredictor.load()`.

The tabular model implementation (`tabular_model.py`) is significantly more complex than time series, supporting both KServe v1 (JSON dict) and v2 (InferRequest tensor) protocols. The v2 support includes sophisticated DataFrame construction from per-feature tensors (`_infer_request_to_dataframe`), proper v2 datatype mapping from AutoGluon's internal type system (`_feature_to_v2_datatype`), and dynamic output schema generation based on problem type (regression returns FP64, classification returns class-specific datatypes, quantile returns multi-column FP64). The `predict_proba` mode (controlled by `PREDICT_PROBA` env var) generates per-class probability outputs with sanitized tensor names, which is essential for production use cases requiring confidence scores.

The `version_compat.py` module addresses a practical deployment challenge: AutoGluon enforces strict version matching when loading saved predictors, but downstream builds use patched versions (e.g., `1.5.0+rhaiv.3` vs upstream `1.5.0`). The compatibility layer reads the saved version file, compares only major.minor, and passes `require_version_match=False` for patch-level differences. This is critical for RHOAI where the `+rhaiv.N` local version suffix would otherwise prevent loading models trained with upstream AutoGluon.

The `runtime_paths.py` module handles a container-specific concern: AutoGluon's SeasonalNaive fallback (used for short time series) calls `setup_outputdir` under the process CWD, which defaults to `/` in containers — a non-writable path for non-root users (UID 1001). The module finds a writable directory (`/tmp`, `$HOME`, `/home/kserve`) and changes the process CWD at startup. The matplotlib cache directory is similarly redirected to `/tmp/matplotlib` to avoid home directory write failures.

The build architecture uses a multi-stage Dockerfile with the AIPCC CPU base image. All Python dependencies are installed from the RHEL AI Python Package Index (`console.redhat.com/api/pypi/public-rhai/rhoai/3.5-EA2/cpu-ubi9/simple/`), ensuring only Red Hat-built wheels are used. The `autogluon-all-requirements.txt` file is a comprehensive hash-locked requirements file generated by `uv export`, enabling fully hermetic builds via Hermeto pip prefetch in the Tekton pipeline. The AutoGluon packages themselves carry the `+rhaiv.3` local version suffix, indicating they are Red Hat-patched rebuilds of upstream 1.5.0.
