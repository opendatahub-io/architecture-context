## Purpose

**Short**: A KServe model server that serves AutoGluon TabularPredictor and TimeSeriesPredictor models via REST v1/v2 and gRPC inference protocols.

**Detailed**: The kserve-autogluon-server is a Python-based inference runtime for serving AutoGluon machine learning models within the KServe framework on Red Hat OpenShift AI. It packages AutoGluon's tabular and time series prediction capabilities into a container image that can be deployed as an `InferenceService` custom resource on Kubernetes.

The server auto-detects the model type (tabular vs. time series) at startup by attempting to load the `storageUri` artifact as each predictor type. Tabular models support both KServe v1 (JSON dict) and v2 (tensor) inference protocols, including optional probability output via `predict_proba()`. Time series models support REST v1 JSON only, accepting historical time series data and optional known covariates to produce forecasts.

This repository is a downstream fork of the upstream kserve/kserve monorepo, specifically focused on building and shipping the autogluon server container image for RHOAI. It contains the full kserve codebase (Go operator, Python SDK, multiple server implementations) but only builds the autogluon server via Konflux (`Dockerfile.konflux.autogluon`). The image is based on the AIPCC CPU base image, providing a RHEL 9-based runtime with Python 3.12 and the RHEL AI Python Package Index for hermetic builds.

## Architectural Analysis

The autogluon server follows the KServe model server pattern: a Python process that implements the KServe `Model` interface, delegates to a framework-specific predictor (here AutoGluon), and is served by the KServe `ModelServer` which provides FastAPI-based REST endpoints and a gRPC server. The server is a thin adapter layer — it translates between KServe inference protocol payloads (JSON dicts for v1, tensor-based `InferRequest` for v2) and AutoGluon's pandas DataFrame-based prediction API.

A notable design choice is the auto-detection pattern in `predictor_factory.py`. Rather than requiring users to specify whether their model is tabular or time series, the server tries loading the artifact as `TimeSeriesPredictor` first, then falls back to `TabularPredictor`. This is encapsulated in `AutoGluonDetectedModel`, which delegates all `predict()` calls to the correct underlying implementation once detection succeeds. This simplifies the `InferenceService` YAML — users just specify `modelFormat.name: autogluon` regardless of model type.

The version compatibility layer (`version_compat.py`) addresses a practical deployment challenge: AutoGluon models pickle the training-time version, and strict version matching would force users to retrain when the serving image gets a patch update. The `load_predictor_tolerating_patch_mismatch()` function reads the saved `version.txt`, compares major/minor versions (which must match), and allows patch-level or local label mismatches (e.g., `1.5.0` trained artifacts loading on `1.5.0+rhaiv.3` runtime). This is critical for RHOAI where the `+rhaiv.N` local version suffix is added for Red Hat's secure build variants.

The time series model (`timeseries_model.py`) is significantly more complex than the tabular model because it must handle multi-series time series data with configurable column names, known covariates for the forecast horizon, and metadata resolution from both the predictor object and an optional `predictor_metadata.json` file. Environment variables (`AUTOGLUON_TS_ID_COLUMN`, `AUTOGLUON_TS_TIMESTAMP_COLUMN`) provide runtime overrides for column names without requiring model retraining. However, v2 tensor protocol is explicitly not supported for time series — only REST v1 JSON is accepted. This is a deliberate scope limitation documented in the code via an `InferenceError` that explains which endpoint to use.

The `runtime_paths.py` module handles a specific OpenShift constraint: non-root containers running as arbitrary UIDs may have `/` as cwd and no writable `$HOME`. AutoGluon's `SeasonalNaive` fallback writes to the current working directory, so the server proactively `chdir`s to `/tmp` or `$HOME` at startup. This is called once before the event loop starts, as `os.chdir()` is process-wide and unsafe under concurrency.
