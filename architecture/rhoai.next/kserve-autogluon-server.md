## Purpose

**Short**: A KServe-compatible model serving container for AutoGluon TabularPredictor and TimeSeriesPredictor that provides v1 and v2 inference protocol endpoints for predictive AI workloads on RHOAI.

**Detailed**: kserve-autogluon-server is a Python model inference server built on the KServe SDK framework. It serves AutoGluon machine learning models — both tabular (classification, regression, quantile) and time series (forecasting) — via standardized REST and gRPC inference APIs. The server runs as a container within KServe's `InferenceService` pods, managed by a `ClusterServingRuntime` definition that registers AutoGluon as a first-class model format in the platform.

The server auto-detects whether a model directory contains a `TabularPredictor` or `TimeSeriesPredictor`, handles version compatibility between training and serving AutoGluon versions, and exposes both KServe v1 (JSON) and v2 (tensor-based) predict protocols. It supports predict-proba mode for classification, known covariates for time series, and publishes per-feature v2 model metadata contracts. The image is built from an AIPCC CPU base image with AutoGluon pinned to version 1.5.0+rhaiv.3 and ships on four architectures (x86_64, ppc64le, s390x, arm64).

This repository is a downstream fork of the upstream `kserve/kserve` monorepo. While the full repo contains the KServe operator, multiple model servers, and Python SDK, this Konflux component build targets **only** the autogluon server image via `Dockerfile.konflux.autogluon`.

## Architectural Analysis

The kserve-autogluon-server follows KServe's model server plugin architecture: a thin Python module (`autogluonserver`) implements the `kserve.Model` interface and registers with the KServe `ModelServer` entrypoint. At startup, `create_autogluon_model` returns an `AutoGluonDetectedModel` that defers predictor-type detection to load time — it tries `TimeSeriesPredictor.load()` first, then `TabularPredictor.load()`, delegating all subsequent predict calls to the appropriate implementation (`AutoGluonTimeSeriesModel` or `AutoGluonTabularModel`).

A notable design decision is the patch-version tolerance in `version_compat.py`: the server reads AutoGluon's saved `version.txt`, permits patch-level mismatches (e.g. `1.5.0+rhaiv.3` vs. `1.5.0`), and rejects major/minor mismatches at load time. This provides resilience for RHAI-patched builds without breaking model compatibility contracts.

The v2 tensor protocol implementation for tabular models is thorough — it maps AutoGluon's raw feature type metadata to v2 datatypes, enforces shape validation, and reports per-feature input/output metadata via the `/v2/models/{name}` endpoint. Time series remains v1-only (REST JSON), reflecting the DataFrame-oriented nature of time series payloads.

The `runtime_paths.py` module addresses a container runtime concern: AutoGluon's SeasonalNaive fallback writes to the current working directory, which defaults to `/` in containers. The entrypoint changes cwd to a writable directory (`/tmp` or home) before any model loading occurs.

The Dockerfile uses a multi-stage build from an AIPCC CPU base image, installing kserve SDK, storage, and autogluon dependencies via pip with the RHEL AI Python Package Index. The hermetic Tekton pipeline prefetches all pip dependencies.
