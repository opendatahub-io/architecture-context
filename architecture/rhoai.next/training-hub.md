## Purpose

**Short**: An algorithm-focused Python library providing a unified interface for common language model training, continual learning, and reinforcement learning techniques.

**Detailed**: training-hub abstracts the complexity of heterogeneous ML training frameworks behind a consistent Algorithm/Backend plugin architecture. Users call high-level convenience functions (`sft()`, `osft()`, `lora_sft()`, `lora_grpo()`, `grpo()`, `gepa()`) that internally resolve to registered backend implementations. This lets teams switch between training backends (instructlab-training, mini-trainer, Unsloth, ART/OpenPipe, verl, gepa) without rewriting training scripts.

The library covers three major training paradigms: supervised fine-tuning (SFT, OSFT, LoRA+SFT), reinforcement learning from verifiable rewards (GRPO via ART or verl backends), and gradient-free prompt optimization (GEPA). It also ships GPU memory/timing profiling estimators, reward functions for tool-calling agent verification, an ITS Hub rollout adapter for inference-time search during GRPO training, and a loss visualization module. A coding agent plugin (`codex-plugin/`, `claude-plugin/`) enables Claude Code and OpenAI Codex CLI to invoke training-hub skills directly.

training-hub is not a deployed service or Kubernetes operator. It is imported as a Python dependency by notebooks, scripts, and orchestration layers (e.g., InstructLab CLI, RHOAI workbench notebooks) that run on GPU-equipped compute nodes.

## Architectural Analysis

### Algorithm-Backend Plugin Architecture

training-hub's core design pattern is a two-level plugin system: `Algorithm` defines the training interface (required/optional parameters, `train()` method), while `Backend` encapsulates the execution engine. The `AlgorithmRegistry` maps `(algorithm_name, backend_name)` pairs to concrete classes, and `create_algorithm()` is the factory that wires them together. This separation allows the same algorithm (e.g., `lora_grpo`) to run on different backends (ART for single-GPU, verl for multi-GPU) without changing user-facing code.

Registration happens at module import time via top-level `AlgorithmRegistry.register_algorithm()` / `register_backend()` calls at the bottom of each algorithm module. The `__init__.py` imports all algorithm modules eagerly, so all registrations are available as soon as `import training_hub` completes.

### Parameter Translation Layer

Each backend translates training-hub's normalized parameter names into framework-specific names. For example, `InstructLabTrainingSFTBackend.execute_training()` maps `max_tokens_per_gpu` to `max_batch_len`, `beta1`/`beta2` to `adamw_betas`, and `eps` to `adamw_eps`. This insulates users from backend-specific naming conventions and allows switching backends without parameter changes.

### Subprocess Isolation for GPU Workloads

Both the ART and verl GRPO backends run training in subprocesses rather than in-process. The ART backend (`lora_grpo.py`) launches a subprocess to isolate vLLM's GPU memory management from the main process. The verl backend (`lora_grpo_verl.py`) launches verl as a CLI subprocess and parses its stdout for metrics. This pattern prevents GPU memory conflicts and allows clean process termination, though it requires workarounds for issues like the vLLM 0.21+ subprocess hang (addressed in commit `0864d60`).

### Defensive Dependency Management

The `pyproject.toml` demonstrates security-conscious dependency management: `litellm` versions 1.82.7 and 1.82.8 are explicitly excluded with a comment documenting the TeamPCP supply chain compromise date (2026-03-24). Dependencies are organized into optional extras (`cuda`, `lora`, `grpo`, `grpo-verl`, `gepa`, `dev`) to minimize the install footprint for users who only need specific algorithms.

### Memory Estimation Framework

The profiling module provides GPU memory estimators for each training paradigm. `BasicEstimator` (SFT) computes model parameters, gradients (2 bytes/param for bf16), optimizer states (12 bytes/param for AdamW with mixed precision), and activation memory. `OSFTEstimator`, `LoRAEstimator`, and `QLoRAEstimator` extend this with algorithm-specific calculations (e.g., QLoRA's 4-bit quantized weight storage). Results are cached to CSV for model parameter counts across architectures.

### Coding Agent Integration

The `codex-plugin/` and `claude-plugin/` directories implement a skills-first architecture for AI coding assistants. This allows Claude Code and OpenAI Codex CLI to invoke training-hub operations through natural language, bridging the gap between conversational AI and ML training workflows.
