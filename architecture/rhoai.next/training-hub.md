## Purpose

**Short**: An algorithm-focused Python library and CLI providing a unified interface across multiple LLM training backends for supervised fine-tuning, reinforcement learning, prompt optimization, and embedding fine-tuning.

**Detailed**: Training Hub is a Python package (`training-hub` on PyPI) developed by the Red Hat AI Innovation Team. It implements a Strategy + Registry pattern where seven training algorithms (SFT, OSFT, LoRA SFT, LoRA GRPO, full-parameter GRPO, GEPA prompt optimization, and Embedding SFT) are decoupled from their nine backend implementations (InstructLab Training, Mini-Trainer, Unsloth, ART/OpenPipe, verl with FSDP, GEPA direct, MLflow GEPA, and sentence-transformers). Users select an algorithm and optional backend; the registry dispatches to the correct implementation.

The library is consumed both as a Python API (`from training_hub import sft, lora_grpo, gepa`) and as a CLI tool (`thub sft --config config.yaml`). It supports single-GPU through multi-node distributed training via torchrun, with GPU-accelerated training for weight-modifying algorithms and CPU-only operation for gradient-free prompt optimization (GEPA). Training Hub does not deploy as a long-running service or Kubernetes operator — it is invoked as a library call or CLI command within a user's training environment (local machines, Kubeflow pipelines, or cloud GPU instances). It also ships with Claude Code and Codex CLI plugin manifests for use by AI coding agents.

## Architectural Analysis

Training Hub's core architecture is a **Strategy + Registry** pattern. The `AlgorithmRegistry` class acts as a central dispatch table, mapping algorithm names (strings) to `Algorithm` subclasses and each algorithm to one or more `Backend` implementations. Algorithm modules self-register at import time via `AlgorithmRegistry.register_algorithm()` and `AlgorithmRegistry.register_backend()` calls at module scope, avoiding a central configuration file but requiring module import for registration. The CLI uses lazy imports — each subcommand only imports its algorithm module when invoked — to avoid loading heavy dependencies (torch, transformers, vLLM) unnecessarily.

The most architecturally complex component is **LoRA + GRPO**, which has two fundamentally different backends. The **ART backend** (`lora_grpo.py`, ~2118 lines) runs training in a spawned subprocess via `mp.get_context("spawn")` to isolate the caller from vLLM's non-daemon threads. Results are communicated via JSON files on disk (`training_results.json`, `.training_error`), and `os._exit()` is used to force-exit the subprocess after training to avoid vLLM V1 shutdown hangs. The backend also creates a "seed LoRA checkpoint" — a zero-effect adapter with `lora_B` weights initialized to zero — to satisfy vLLM V1's eager validation of LoRA paths before the first real checkpoint exists. The **verl backend** (`lora_grpo_verl.py`, ~1140 lines) orchestrates training via a `subprocess.Popen` call to `verl.trainer.main_ppo`, passing configuration as Hydra-style CLI overrides and parsing stdout for real-time metrics. It supports FSDP for both LoRA and full-parameter training (`lora_r=0`), with weight syncing to vLLM for rollout generation. Both backends produce a uniform `training_metrics.jsonl` output for downstream consumption (e.g., Kubeflow progress tracking via `max_steps`).

The **callback system** (`TrainingHubCallback`) provides nine lifecycle hooks (on_train_begin/end, on_epoch_begin/end, on_step_begin/end, on_log, on_evaluate, on_save) that work across all backends. For torchrun-based backends (InstructLab, Mini-Trainer), callbacks are serialized across subprocess boundaries via class-source serialization, imposing constraints: module-level definitions, no closures, imports inside method bodies, and no instance state preservation. The `run_on_all_ranks` flag (default False) controls whether hooks fire only on rank 0 or on all distributed workers.

A notable supply chain consideration: the `litellm` dependency explicitly excludes versions 1.82.7 and 1.82.8 in `pyproject.toml`, which were compromised in the TeamPCP supply chain attack of March 2026 that harvested credentials at import time.

The CLI (`thub`, 728 lines) supports YAML config files with CLI argument override precedence, and dotted-path resolution for callable parameters (reward functions, rollout functions). The dotted-path resolution (`_resolve_callable` in `cli.py`) imports arbitrary Python modules at runtime — a security-relevant design choice that enables extensibility but means the CLI should not be exposed to untrusted input.

### SFT (Supervised Fine-Tuning)

**Intent**: Standard supervised fine-tuning on chat/instruction datasets. InstructLab Training backend translates Training Hub parameters (e.g., `max_tokens_per_gpu` to `max_batch_len`, AdamW params). Supports pretraining mode for document-style continual pretraining. Multi-GPU/multi-node via torchrun.

### OSFT (Orthogonal Subspace Fine-Tuning)

**Intent**: Continual learning that constrains weight updates to an orthogonal subspace, preserving prior model behavior without a replay dataset (Nayak et al. 2025). Uses InstructLab Training for data processing, Mini-Trainer for the training loop. Supports on-demand checkpointing via signal handling (SIGTERM, SIGUSR1/2) and auto-resume from latest checkpoint.
**Language**: Python
**Port**: N/A

### LoRA + GRPO (ART Backend)

**Intent**: Single-GPU reinforcement learning from verifiable rewards using LoRA adapters. Runs in a spawned subprocess with time-shared vLLM inference and Unsloth LoRA training. Three data modes: tool_call (tool-call verification rewards), generic (Q&A with custom reward), and custom rollout (user-provided rollout function). Creates seed LoRA checkpoint for vLLM V1 compatibility. Uses `os._exit()` to force clean subprocess exit after vLLM.
**Language**: Python
**Port**: N/A (vLLM runs as in-process engine, not a network service)

### LoRA + GRPO / Full GRPO (verl Backend)

**Intent**: Multi-GPU distributed GRPO training scaling to 70B+ models. Uses FSDP for distributed LoRA or full-parameter training (`lora_r=0`) and vLLM for parallel rollout generation. Launched as a subprocess running `verl.trainer.main_ppo` with Hydra config overrides. Supports Dr. GRPO variant, custom reward functions (including math verification), and custom agent loops for tool-calling. Data is prepared into Parquet format for verl consumption.
**Language**: Python
**Port**: N/A (Ray/NCCL for inter-process communication during distributed training)

### GEPA (Genetic-Pareto Prompt Optimization)

**Intent**: Gradient-free prompt optimization using evolutionary search with LLM-driven reflection. Optimizes prompts via API calls — no GPU required. Two backends: direct `gepa.optimize()` and MLflow prompt registry integration (`mlflow.genai.optimize_prompts`). Uses litellm for model routing.
**Language**: Python
**Port**: N/A

#### Upstream Dependencies

| MLflow Tracking | HTTPS | varies | None/Token | Experiment tracking and prompt registry (MLflow backend only) |

### Embedding SFT

**Intent**: Contrastive fine-tuning of sentence embedding models for semantic routing/classification. Supports three contrastive losses (batch_all_triplet, batch_hard_triplet, mnrl). Uses GROUP_BY_LABEL batch sampling for triplet losses. Auto-converts label datasets to pairs for MNRL loss. Supports custom loss functions.
**Language**: Python
**Port**: N/A
