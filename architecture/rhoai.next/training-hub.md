## Purpose

**Short**: Python library providing a unified Algorithm + Backend abstraction for LLM fine-tuning, reinforcement learning, and prompt optimization workflows.

**Detailed**: Training Hub is a pure Python library (published on PyPI as `training-hub`) that abstracts multiple LLM training methodologies behind a consistent API. It supports six training algorithms — SFT (Supervised Fine-Tuning), OSFT (Orthogonal Subspace Fine-Tuning), LoRA + SFT, LoRA + GRPO (Group Relative Policy Optimization), full-parameter GRPO, and GEPA (Genetic-Pareto prompt optimization) — each backed by one or more pluggable backend implementations that delegate to specialized training frameworks like InstructLab Training, Mini-Trainer, Unsloth, OpenPipe ART, verl, and GEPA.

The library is designed for use inside RHOAI training pipelines and coding agent environments. It ships with Claude Code and Codex CLI plugin manifests (`.claude-plugin/` and `.codex-plugin/`) so that AI coding agents can invoke training workflows directly. Additional utilities include GPU memory estimation for capacity planning, training loss visualization, reward functions for GRPO reinforcement learning, and ITS (Inference-Time Scaling) rollout adapters for advanced GRPO sampling strategies.

Training Hub is not a containerized service or Kubernetes operator — it is a library consumed by other components. Its distributed training support is handled via PyTorch's torchrun launcher, with multi-node/multi-GPU coordination parameters exposed through the algorithm API.

## Purpose

**Short**: Python library providing a unified algorithm/backend interface for language model training — SFT, OSFT, LoRA SFT, and LoRA GRPO — delegating execution to pluggable RHOAI ecosystem backends.

**Detailed**: training_hub is a Python package that provides an algorithm-focused interface for common language model training techniques. It implements a Strategy pattern with a central `AlgorithmRegistry` that maps algorithm names to `Algorithm` classes and backend names to `Backend` implementations. The package currently ships five algorithms: supervised fine-tuning (`sft`), orthogonal subspace fine-tuning (`osft`), LoRA-based SFT (`lora_sft`), LoRA-based GRPO reinforcement learning (`lora_grpo`), and full-parameter GRPO (`grpo`). The library is consumed as a Python dependency by research notebooks and training scripts; it does not expose HTTP endpoints, gRPC services, or Kubernetes-level resources. All training execution is local to the process (or subprocess for verl/art), using PyTorch distributed (torchrun) for multi-GPU coordination.

## Data Flows

- **User invocation:** A research notebook or script calls a top-level convenience function (`sft()`, `osft()`, `lora_sft()`, `lora_grpo()`, or `grpo()`), which resolves the algorithm and backend via `AlgorithmRegistry.create_algorithm()`.
- **Algorithm → Backend delegation:** The `Algorithm.train()` method translates user-facing parameter names to backend-specific parameter names, validates types and constraints, and calls `Backend.execute_training()`.
- **SFT flow:** `InstructLabTrainingSFTBackend` maps parameters and delegates to `instructlab.training.run_training()`, which handles torchrun-based distributed training.
- **OSFT flow:** `MiniTrainerOSFTBackend` first calls `instructlab.training.data_process` for data tokenization, then delegates to `mini_trainer.run_training()` with OSFT-specific configuration (unfreeze_rank_ratio, target_patterns).
- **LoRA SFT flow:** `UnslothLoRABackend` loads the model via Unsloth's `FastModel`/`FastLanguageModel`, applies PEFT LoRA configuration, and trains via TRL's `SFTTrainer`.
- **LoRA GRPO (ART) flow:** `ARTLoRAGRPOBackend` spawns a subprocess that registers the model with ART's `LocalBackend`, runs an iterative rollout-train loop (gather_trajectory_groups → model.train), and saves results to disk before shutting down vLLM.
- **LoRA GRPO (verl) flow:** `VeRLLoRAGRPOBackend` converts data to Parquet, writes reward functions to disk, and launches `verl.trainer.main_ppo` as a subprocess with Hydra-style configuration arguments. verl orchestrates Ray workers for distributed FSDP training and vLLM rollout generation.
- **Full GRPO flow:** The `grpo()` convenience function calls `lora_grpo()` with `lora_r=0, backend="verl"`, routing to the verl backend for full-parameter GRPO without LoRA adapters.

## Architectural Analysis

### Algorithm + Backend Pattern

Training Hub's core design pattern is a strategy-based abstraction where each training methodology (Algorithm) delegates execution to a pluggable Backend. The `AlgorithmRegistry` provides class-level registration and factory creation, enabling runtime backend selection. This pattern cleanly separates the training API surface from implementation details — for example, GRPO can use either the ART backend (single-GPU vLLM time-sharing) or the verl backend (multi-GPU FSDP via Ray) through the same `lora_grpo()` API.

The registry uses string keys for both algorithm and backend names, with each algorithm module self-registering at import time via `AlgorithmRegistry.register_algorithm()` and `AlgorithmRegistry.register_backend()` calls at module scope. This avoids a central configuration file but requires that algorithm modules be imported for registration to take effect.

### Subprocess Isolation for vLLM Compatibility

The ART GRPO backend (`lora_grpo.py`) uses a notable subprocess isolation pattern: training runs in a spawned subprocess rather than in-process. This is necessitated by vLLM's threading model — the vLLM engine spawns background threads that can hang if not explicitly shut down, preventing clean process exit. The backend includes `_shutdown_art_backend()` with explicit `gc.collect()` and engine destruction, plus `_create_seed_lora_checkpoint()` for vLLM V1 compatibility (which requires a zero-effect LoRA adapter to be present even before training begins).

The verl backend similarly uses subprocess execution with live log parsing, extracting training metrics from subprocess stdout into a `training_metrics.jsonl` file for consistent metric consumption across backends.

### Multi-Turn Trace Decomposition

The LoRA GRPO algorithm includes `_decompose_multiturn_traces()`, which converts N-turn conversation traces into N individual per-turn training samples. Each sample represents one assistant turn with its preceding context as the prompt. This is architecturally significant because it allows GRPO to train on tool-calling agent trajectories where the reward signal applies to the full trace but the model must learn from individual turns.

### VLM Detection and Mamba Kernel Compatibility

The LoRA module includes runtime model architecture detection (`_is_vlm_architecture`, `_is_vlm_model_id`) to handle Vision-Language Models differently from text-only models (Unsloth's FastModel vs FastLanguageModel). It also includes Mamba kernel compatibility logic (`_use_local_mamba_kernels`) that patches Mamba-architecture models to use locally compiled kernels when the installed version is incompatible.

### Memory Estimation

The profiling module provides analytical (non-empirical) GPU memory estimators for SFT, OSFT, LoRA, and QLoRA configurations. These use model metadata (parameter count, hidden dimensions, number of layers) to compute expected memory consumption across model weights, gradients, optimizer states, and intermediate activations. A CSV-based model metadata cache avoids repeated HuggingFace Hub queries. The `OSFTEstimatorExperimental` is marked deprecated in favor of `OSFTEstimator`, suggesting active refinement of memory models.

### Supply Chain Security Note

The `pyproject.toml` explicitly excludes `litellm` versions 1.82.7 and 1.82.8 with a comment citing a supply chain attack. This indicates the project actively monitors dependency security and uses version constraints as a mitigation mechanism.

### Coding Agent Plugin Support

The repository includes plugin manifests for Claude Code (`.claude-plugin/`) and Codex CLI (`.codex-plugin/`), positioning Training Hub as a library that AI coding agents can invoke directly. ## Architectural Analysis

Training Hub implements a clean Strategy pattern that decouples training algorithms from their execution backends. The `AlgorithmRegistry` acts as a service locator: algorithms register themselves and their compatible backends at import time via module-level `AlgorithmRegistry.register_algorithm()` and `register_backend()` calls. This design allows adding new training techniques (e.g., a DPO algorithm) or new backends (e.g., a DeepSpeed backend for SFT) without modifying existing code.

The backend implementations reveal distinct execution models. The `InstructLabTrainingSFTBackend` and `MiniTrainerOSFTBackend` operate in-process, calling the underlying library's `run_training()` function directly — training runs in the same Python process with torchrun handling multi-GPU coordination. By contrast, the `ARTLoRAGRPOBackend` spawns a subprocess via `multiprocessing.get_context("spawn")` to isolate ART/vLLM's non-daemon threads that prevent clean Python exit. The `VeRLLoRAGRPOBackend` goes further, launching verl as a fully external subprocess via `subprocess.Popen` because verl manages its own Ray cluster for FSDP-distributed training across multiple GPUs.

A notable design choice is the OSFT backend's cross-library dependency: `MiniTrainerOSFTBackend` uses `instructlab.training.data_process` for data tokenization even though it delegates training to `mini_trainer`. This is because mini-trainer does not implement its own data processing pipeline, so the OSFT backend composes capabilities from both RHOAI ecosystem libraries. The processed data path is then passed to mini-trainer's `run_training()` function.

The GRPO implementation handles a significant vLLM V1 compatibility challenge. vLLM V1 eagerly validates LoRA adapter paths when `add_lora` is called, but ART calls `add_lora` before training has produced a checkpoint. The backend solves this by monkey-patching ART's `convert_checkpoint_if_needed` function to create a zero-effect seed LoRA checkpoint (with all `lora_B` weights set to zero) if ART's own initialization does not produce one. This ensures the model behaves identically to the unmodified base model for the first rollout iteration while satisfying vLLM's validation requirements.
