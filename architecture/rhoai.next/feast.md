## Purpose

**Short**: Feast is a feature store platform that provides an operator and feature server for managing, storing, and serving ML features on Kubernetes/OpenShift.

**Detailed**: Feast (Feature Store) is an open-source feature management platform for machine learning. This repository contains two primary deployable components: a Go-based Kubernetes operator (`feast-operator`) and a Python-based feature server (`feature-server`). The operator manages the lifecycle of `FeatureStore` custom resources, orchestrating deployments of online stores, offline stores, registry servers, and UI servers. The feature server provides REST and gRPC APIs for online feature retrieval, feature pushing, and materialization.

The operator creates and manages Kubernetes Deployments, Services, ConfigMaps, ServiceAccounts, RBAC resources, CronJobs, HorizontalPodAutoscalers, PodDisruptionBudgets, and optionally OpenShift Routes and ServiceMonitors. It supports two authorization models: Kubernetes-native RBAC and OIDC-based authentication. The platform integrates with OpenDataHub/RHOAI through Notebook ConfigMap injection, namespace discovery labeling, and auto-access RBAC reconciliation based on Feast permission policies. It also integrates with Spark Operator for batch feature computation.

## Architecture Components

| Component | Type | Purpose |
|-----------|------|---------|
| feast-operator | Go Operator (controller-runtime) | Manages FeatureStore CRs, deploys and configures all Feast services (online/offline store, registry, UI), handles RBAC, TLS, scaling, and monitoring |
| feature-server | Python Service (FastAPI/Gunicorn/Uvicorn) | Serves online features via REST and gRPC, handles materialization, feature pushing, permissions enforcement, and MCP protocol |

## Architectural Analysis

The Feast repository follows a multi-language monorepo pattern with a clear separation between the infrastructure layer (Go operator) and the application layer (Python SDK and feature server). The operator is a controller-runtime based Kubernetes operator that manages a single CRD (`FeatureStore`) but creates a rich set of child resources. The Python feature server is built as a container image and injected by the operator into user namespaces as Deployment pods. This architecture allows the operator to run as a platform-level component while feature servers run in tenant namespaces.

The authorization model is notably sophisticated for a feature store. Feast implements its own permission framework with 8 distinct actions (CREATE, DESCRIBE, UPDATE, DELETE, READ_ONLINE, READ_OFFLINE, WRITE_ONLINE, WRITE_OFFLINE) enforced per-resource. The operator reconciles Kubernetes RBAC resources based on permission policies stored in the Feast registry — a bidirectional integration where the operator reads policies from the feature server's registry REST API and creates corresponding Kubernetes Roles and RoleBindings. The intra-communication token (a JWT with HS256 and an empty key) is used for operator-to-registry communication, bypassing the permission framework for trusted service-to-service calls. This pattern has a known weakness: `InsecureSkipVerify: true` is used for intra-cluster TLS connections (`registry/client.go`), which while pragmatic for cluster-internal traffic, means the operator does not validate the registry server's certificate identity.

The TLS architecture is well-integrated with OpenShift. On OpenShift clusters, the operator automatically provisions TLS via service serving certificates (annotating Services with `service.beta.openshift.io/serving-cert-secret-name`). The operator also fetches the cluster's TLS profile from the `apiservers.config.openshift.io/cluster` resource and applies it to its own webhook and metrics servers, ensuring alignment with cluster-wide TLS policy. A `SecurityProfileWatcher` monitors for TLS profile changes and triggers a graceful restart if the cluster policy changes. On non-OpenShift clusters, TLS must be manually configured via the CRD's `tls.secretRef` field.

The Notebook integration (`NotebookConfigMapReconciler`) demonstrates a pattern for dynamic controller registration. At startup, the operator checks whether the `notebooks.kubeflow.org` CRD exists. If absent, it starts a background polling loop and exits the process when the CRD appears, relying on Kubernetes to restart the pod so the controller registers during normal startup. This approach avoids the limitations of controller-runtime v0.18, which doesn't support dynamic controller registration on a running manager.

The scaling capabilities are comprehensive: the operator supports static replicas (`spec.replicas`), HPA-based autoscaling (with configurable metrics and behavior), PodDisruptionBudgets, topology spread constraints, and pod anti-affinity rules. When scaling is enabled, the operator auto-injects soft zone-spread constraints and pod anti-affinity to improve availability. CEL validation rules in the CRD enforce that scaling requires database-backed persistence for all stores (preventing file-based SQLite stores from being scaled, which would cause data corruption).
