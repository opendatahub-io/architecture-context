## Purpose

**Short**: Feast is a Kubernetes operator and feature store platform that manages the lifecycle of ML feature infrastructure, providing feature registration, storage, serving, and retrieval for training and real-time inference.

**Detailed**: Feast (Feature Store) is a dual-language platform consisting of a Go-based Kubernetes operator and a Python SDK/server ecosystem. The operator manages `FeatureStore` custom resources that declaratively define feature store deployments including registry, online store, offline store, and UI services. It creates and reconciles Deployments, Services, ConfigMaps, RBAC resources, CronJobs for materialization, and OpenShift Routes to expose these services.

The Python component provides the feature server (served via FastAPI/Starlette on port 6566), a comprehensive REST API for registry operations (entities, feature views, data sources, feature services, labels, lineage, monitoring), a gRPC interface for both serving and registry operations, and a CLI for local development. The feature server supports multiple online store backends (Redis, PostgreSQL, SQLite, DynamoDB, Bigtable, Milvus, and more) and offline store backends (BigQuery, Snowflake, Spark, Dask, DuckDB). It also provides OpenLineage integration for data lineage tracking, an MCP (Model Context Protocol) server, and active learning and annotation capabilities.

The Go feature server provides a high-performance online serving path for `GetOnlineFeatures` with HTTP and gRPC interfaces, connecting directly to online store backends (Redis, PostgreSQL, SQLite, DynamoDB, Bigtable, Cassandra) for low-latency retrieval. The operator integrates with the broader RHOAI platform by watching Kubeflow Notebook and MLflow CRDs to inject feature store configuration into notebooks.

## Architectural Analysis

Feast's architecture follows a declarative operator pattern where a single `FeatureStore` CR drives the deployment of an entire feature store stack. The operator (`FeatureStoreReconciler`) owns and watches 12 Kubernetes resource types including Deployments, Services, ServiceAccounts, PVCs, ConfigMaps, Roles, RoleBindings, Routes, CronJobs, HorizontalPodAutoscalers, and PodDisruptionBudgets. A secondary controller (`NotebookConfigMapReconciler`) watches FeatureStore CRs and ConfigMaps to automatically inject feature store client configuration into Kubeflow notebook environments.

The authorization model is CRD-driven and supports three modes: Kubernetes RBAC-based auth (where the operator creates namespace-scoped Roles), OIDC-based auth (referencing a Secret with provider configuration), or explicit no-auth mode. The OIDC issuer URL can be injected by the Open Data Hub operator from GatewayConfig. This design means the feature server itself does not enforce auth middleware at the application level -- authentication is expected to be configured declaratively through the CRD.

The operator uses the OpenShift `controller-runtime-common` TLS package to fetch the cluster's API server TLS profile, falling back to the Intermediate profile if the OpenShift `config.openshift.io/v1` API is unavailable (e.g., on vanilla Kubernetes). The Go feature server's TLS path includes post-quantum curve preferences (`X25519MLKEM768`), which is notable for forward-looking crypto readiness.

The Python feature server exposes a very large API surface (110+ HTTP endpoints plus gRPC services) covering registry CRUD, feature serving, monitoring, lineage, saved datasets, search, labels, and OpenLineage integration. This surface has no application-level authentication middleware -- it relies entirely on the operator's CRD-configured authorization at the Kubernetes/OIDC layer.

The Konflux build for the feature server uses AIPCC CPU base images with RHAI wheel index pre-configured, while the operator build uses UBI 9 minimal PQC with strict FIPS runtime flags. This split reflects the different security postures: the operator is a Go binary that must pass `check-payload` validation, while the feature server is a Python application that inherits its crypto from the AIPCC base image's OpenSSL.

| Data storage | Per-namespace PVCs; per-CR online/offline store configuration | Kubernetes (PVC namespace scoping) / Application (CR-level config) | Shared backend databases (e.g. shared PostgreSQL) could allow cross-tenant data access if not configured with separate schemas/databases |
| Network traffic | No NetworkPolicies created by operator | None | Cross-namespace network access not restricted by the operator; relies on platform-level NetworkPolicies |
| Compute & resources | Per-deployment resource limits (CPU: 1000m/10m, Memory: 256Mi/64Mi for operator); HPA and PDB per CR | Kubernetes | No ResourceQuota enforcement by the operator |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; TLS secrets per FeatureStore CR | Kubernetes (namespace scoping) | Operator has cluster-wide Secret read access (get verb) |
| API scoping | Namespace-scoped CRD watches; operator uses managed-by label filtering | Kubernetes / Application | Operator bypasses label-filtered cache for reads (DisableFor) to avoid upgrade deadlocks |
