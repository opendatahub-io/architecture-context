## Purpose

**Short**: Feast is an open-source feature store for machine learning that manages offline/online feature storage and serving for model training and real-time inference.

**Detailed**: Feast (Feature Store) provides a unified data access layer for ML features. It manages an offline store for historical data processing (batch scoring, model training), a low-latency online store for real-time feature serving, and a feature server for serving pre-computed features. The platform prevents data leakage by generating point-in-time correct feature sets and decouples ML workloads from underlying data infrastructure.

The Feast operator (`feast-operator`) is a Kubernetes controller-runtime operator that deploys and manages FeatureStore custom resources. It creates Deployments with multiple containers (offline server, online server, registry, UI), along with supporting Services, ConfigMaps, CronJobs, RBAC resources, and ServiceMonitors. The operator integrates with OpenShift for TLS certificate management, OpenDataHub/RHOAI for platform CA bundles, KubeFlow Notebooks for feature store discovery, and Prometheus for metrics collection.

The feature server (`feature-server`) is a Python FastAPI application that exposes REST and gRPC endpoints for online feature retrieval, feature materialization, and registry management. It supports multiple online store backends (Redis, PostgreSQL, DynamoDB, etc.), offline store backends (BigQuery, Snowflake, DuckDB, etc.), and authentication mechanisms (OIDC, Kubernetes RBAC).

## Architectural Analysis

The Feast architecture follows a multi-component pattern where a single Kubernetes Deployment hosts multiple containers (offline server, online server, registry, UI) that communicate internally via a shared intra-communication JWT token. This colocation model simplifies deployment and reduces network hops but creates a scaling bottleneck: all components scale together via a single HPA. The operator mitigates this somewhat through configurable per-container resource limits and by requiring DB-backed persistence when replicas exceed 1 (to avoid SQLite file locking conflicts).

The operator's reconciliation design is notably thorough in its OpenShift integration. It auto-detects OpenShift clusters at startup and configures TLS using service-serving certificates without user intervention. The TLS profile watcher monitors `config.openshift.io/v1 APIServer` for changes to the cluster's cipher suite policy and triggers operator restarts when the profile changes -- a pattern that ensures compliance with evolving cluster security policies. The Go feature server's TLS configuration explicitly sets `MinVersion: tls.VersionTLS12` with modern curve preferences including the post-quantum hybrid `X25519MLKEM768`, demonstrating forward-looking cryptographic posture.

The authorization system supports dual modes -- Kubernetes RBAC and OIDC -- that are mutually exclusive per FeatureStore CR. The auto-access RBAC feature is architecturally interesting: the operator queries the Feast Registry REST API at `/api/v1/permissions` to discover permission policies, then dynamically creates Kubernetes Roles and RoleBindings to grant read access to namespaces and ConfigMaps referenced by those policies. This creates a runtime dependency loop (operator → registry → operator-managed RBAC) that could delay reconciliation if the registry is slow to start.

One notable security consideration is the operator's use of `InsecureSkipVerify: true` when calling the registry REST API for permission discovery. While acceptable for cluster-internal service communication protected by network policies, this should be documented for security audits. The intra-communication token, while providing authentication between feast containers, is stored in a ConfigMap rather than a Secret, which means it's readable by anyone with ConfigMap read access in the namespace.

The NotebookConfigMap controller demonstrates a graceful degradation pattern for optional CRD dependencies. It validates the KubeFlow Notebook CRD at startup and, if missing, starts a background goroutine that polls every 5 seconds for CRD availability. When detected, it triggers a process restart rather than attempting dynamic controller registration -- a pragmatic choice given controller-runtime's architecture that avoids complex lifecycle management.
