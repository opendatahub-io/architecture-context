## Purpose

**Short**: vLLM hardware plugin that enables high-performance LLM inference on Intel Gaudi (Habana) accelerators.

**Detailed**: vllm-gaudi is a Python plugin package that integrates Intel Gaudi AI accelerators (Gaudi2, Gaudi3) with the vLLM inference engine. It follows vLLM's hardware-pluggable architecture (RFC #11162, #19161) to register the Gaudi HPU as an out-of-tree (OOT) platform, providing device-specific implementations of attention backends, model runners, workers, custom operations, and quantization methods.

The plugin replaces vLLM's GPU-centric code paths with HPU-optimized equivalents: paged attention with 128-token blocks, dynamic bucketing strategies to reduce graph recompilation, bfloat16-native compute, FP8 quantization (INC, compressed-tensors, ModelOpt), and Habana Collective Communications (HCCL) for distributed inference. It supports speculative decoding (Eagle3), LoRA adapters, MoE models (expert/data/tensor parallelism), KV cache offloading to CPU, and multimodal vision-language models.

In RHOAI, the plugin is shipped as a container image (`odh-vllm-gaudi-rhel9`) built on UBI 9.6 with Habana SynapseAI drivers, PyTorch for Gaudi, and the vLLM inference server. The container runs the OpenAI-compatible API server (`vllm.entrypoints.openai.api_server`) as its entrypoint, serving model inference requests over HTTP.

## Architectural Analysis

The vllm-gaudi plugin implements a comprehensive hardware abstraction layer that adapts vLLM's GPU-oriented inference engine to Intel Gaudi accelerators. The architecture is well-designed around vLLM's plugin system — it registers as an out-of-tree (OOT) platform via Python entry points (`vllm.platform_plugins`, `vllm.general_plugins`) and progressively overrides GPU-specific code paths with HPU equivalents. This means the plugin can evolve independently of vLLM's core, though it is tightly coupled to specific vLLM versions (pinned via `VLLM_STABLE_COMMIT` and `VLLM_PROJECT_COMMIT`).

A key architectural concern is the **graph compilation overhead** on Gaudi. Unlike CUDA GPUs where kernel dispatch is nearly instantaneous, Gaudi's SynapseAI compiler needs to compile compute graphs before execution. The plugin addresses this through an extensive **bucketing system** (`vllm_gaudi/extension/bucketing/`) that groups variable-length sequences into fixed-size buckets, enabling graph reuse across requests with similar shapes. The bucketing strategies (linear, exponential, vision-specific, file-configurable) represent significant engineering to avoid recompilation-induced latency spikes. The `unified_attn` mode further consolidates prefill and decode into a single graph path.

The **quantization support** is notably broad — the plugin implements HPU-specific backends for FP8 (INC, compressed-tensors, ModelOpt), GPTQ (2/3/4/8-bit), and AWQ (4-bit). Each quantization backend includes weight transformation logic to match HPU kernel layouts, with hardware-specific FP8 scale handling (Gaudi2 uses `float8_e4m3fnuz`, Gaudi3 uses `float8_e4m3fn`). The scale alignment code (`vllm_gaudi/extension/scales.py`) ensures that quantized weights produce deterministic graph shapes, critical for avoiding recompilation.

The **FIPS compliance gap** is the most significant security finding. The Dockerfile explicitly removes the OpenSSL FIPS provider (`rpm -e --nodeps openssl-fips-provider-so`), which means the container cannot operate in FIPS mode. Combined with the absence of AIPCC base images (the AIPCC Gaudi variant is currently disabled per AIPCC-3471), the lack of hermetic builds (`hermetic: false`), and no lock files for Python dependencies, this component has substantial supply chain and compliance gaps that need to be addressed before GA. The non-AIPCC build pipeline means Habana RPMs are pulled directly from an external artifactory server at build time, bypassing Red Hat's secure build infrastructure.

The **distributed inference** architecture supports tensor parallelism (TP), data parallelism (DP), and expert parallelism (EP) via HCCL collectives. The HPU communicator (`hpu_communicator.py`) works around Gaudi's lazy evaluation model by inserting explicit `mark_step()` synchronization barriers before collective operations. KV cache offloading between HPU and CPU memory is supported with async transfer handlers and heterogeneous block size conversion, enabling larger models to run with limited device memory.
