## Purpose

**Short**: Intel Gaudi (Habana) hardware plugin for vLLM that enables high-performance LLM inference on HPU accelerators.

**Detailed**: vllm-gaudi is a hardware plugin that integrates Intel Gaudi AI accelerators with the vLLM inference engine. It follows vLLM's pluggable hardware architecture (RFC #11162 and #19161), providing HPU-specific implementations of attention backends, model runners, workers, distributed communication, speculative decoding, quantization kernels, and memory management.

The plugin registers itself via Python entry points (`vllm.platform_plugins` and `vllm.general_plugins`) to inject HPU-optimized code paths into vLLM's execution pipeline. It replaces CUDA-specific operations with Habana equivalents — including HCCL for collective communication, FusedSDPA for attention, custom HPU kernels for MoE routing, FP8 quantization, and HPU Graph-based compilation for reduced overhead.

The downstream Red Hat build produces a container image (`odh-vllm-gaudi-rhel9`) based on UBI9 with Habana SynapseAI drivers, PyTorch for Gaudi, and the vLLM + vllm-gaudi stack pre-installed. The image serves an OpenAI-compatible API server as its default entrypoint, making it deployable as a KServe InferenceService runtime or standalone inference server within RHOAI.

## Purpose

**Short**: vllm-gaudi is an out-of-tree vLLM platform plugin that enables LLM inference on Intel Gaudi (HPU) accelerators, providing HPU-optimized workers, attention backends, custom ops, model implementations, and distributed communication.

**Detailed**: vllm-gaudi is a Python plugin package for vLLM that registers Intel Gaudi (HPU) as a supported accelerator platform via vLLM's plugin entry point system. It provides four plugin registrations: a platform plugin (`HpuPlatform`) that extends vLLM's `Platform` base class to configure HPU device management, memory, compilation, and quantization; a utility plugin for HPU-specific helper functions; a custom ops plugin registering 15+ HPU-optimized operations (attention, fused MoE, rotary embedding, layernorm, LoRA, quantization ops); and a model plugin that registers 11 HPU-optimized model architectures into vLLM's `ModelRegistry` (including Gemma3, Qwen2.5-VL, Qwen3-VL-MoE, DeepSeek v2, Pixtral, HunYuan, and others). The package also provides an `HPUWorker` that extends vLLM's `WorkerBase` for model execution on HPU devices, multiple attention backends (unified, MLA, v1), and distributed communication via HPU communicator and NIXL KV transfer connectors. ## Data Flows

- **Plugin registration flow:** When vLLM starts, it discovers vllm-gaudi via Python entry points. The `vllm.platform_plugins` entry point calls `vllm_gaudi:register()`, which configures torch.compile settings for HPU (lazy vs eager mode) and returns the `HpuPlatform` class path. Then `vllm.general_plugins` entry points are invoked in order: `register_utils` loads HPU utility functions, `register_ops` loads 15+ custom HPU-optimized operations (attention, fused MoE, rotary embedding, layernorm, LoRA, quantization ops, KV connectors), and `register_models` registers 11 HPU-optimized model architectures into vLLM's ModelRegistry.
- **Inference execution flow:** Once registered, the `HpuPlatform.check_and_update_config()` method configures vLLM for HPU execution: sets the worker class to `HPUWorker`, forces 128-block KV cache size, enables bfloat16 precision (HPU does not support float16/float32), and configures custom ops. The `HPUWorker` then manages model loading, KV cache allocation, and inference execution on HPU devices, with optional distributed execution via Ray for tensor parallelism.
- **KV cache transfer flow:** For disaggregated inference, the HPU NIXL KV transfer connector enables cross-device KV cache transfer between prefill and decode workers, supporting both CPU (DRAM) and HPU (VRAM) memory regions.

## Architectural Analysis

The vllm-gaudi plugin is structured as a clean hardware abstraction layer that injects itself into vLLM via Python entry points. The `setup.py` defines four entry points: `vllm.platform_plugins` for the `HpuPlatform` class, and three `vllm.general_plugins` for utilities, custom ops, and model overrides. This design allows the plugin to be installed alongside vLLM without modifying vLLM's source code. The plugin uses extensive monkey-patching to replace upstream implementations at runtime — for example, `vllm_gaudi/ops/hpu_attention.py` patches `Attention.forward`, and `vllm_gaudi/models/utils.py` patches `_merge_multimodal_embeddings`.

The plugin's extension subsystem (`vllm_gaudi/extension/`) implements a sophisticated configuration framework with lazy evaluation, hardware detection (Gaudi2 vs Gaudi3), feature flags, and kernel availability checking. The `Config` class uses dependency resolution to compute configuration values on demand, supporting environment variable overrides via `VLLM_*` prefixed variables (40+ documented). This is notably different from vLLM's own configuration — vllm-gaudi maintains a parallel config system tuned for HPU-specific concerns like contiguous paged attention, unified attention, and HPU Graph compilation.

The attention architecture is particularly complex, offering five distinct backends: `HPUAttentionBackendV1` (standard V1 paged attention), `HPUUnifiedAttentionBackend` (merged prefill/decode), `HPUMLAAttentionBackend` (multi-head latent attention for DeepSeek-style models), `HPUUnifiedMLABackend`, and legacy attention paths. The unified attention approach (`vllm_gaudi/extension/unified.py`, 1500+ lines in ops.py) merges prefill and decode batches into a single HPU Graph call, reducing compilation overhead at the cost of complexity. The bucketing system (`vllm_gaudi/extension/bucketing/`) manages tensor shape quantization to minimize HPU Graph recompilation — a critical performance concern since each unique tensor shape triggers a separate graph compilation.

A notable security concern is the explicit removal of `openssl-fips-provider-so` in the Dockerfile (line 63), which strips FIPS-validated OpenSSL modules from the image. Combined with the fully non-hermetic build (no lock files, `hermetic: false` in Tekton config, dependencies fetched from public internet at build time), this represents a gap in both FIPS compliance and supply chain security. The image also clones upstream vLLM and vllm-gaudi from GitHub during the build, pinned only to a tag (`v0.16.0`) rather than a content-addressable hash. These issues are expected to be addressed on downstream release branches where Konflux hardening is applied.

The model layer supports 14 architectures with HPU-optimized implementations, focusing on models with complex attention patterns: Qwen2.5-VL and Qwen3-VL (vision-language with 2D rotary embeddings), Pixtral (2D RoPE vision encoder), MiniMax M2 and DeepSeek V2 (MoE), Gemma3 multimodal, HunYuan (dense and MoE), and several OCR models. Each model override patches specific methods for HPU compatibility — typically replacing dynamic tensor operations with static-shape alternatives that compile efficiently to HPU Graphs. The quantization stack supports FP8 (per-tensor and channel-wise), INC (Intel Neural Compressor), AWQ, GPTQ, ModelOpt, and compressed-tensors formats, with special handling for INC's forced CPU loading to prevent OOM during weight quantization.

## Architectural Analysis

vllm-gaudi follows vLLM's out-of-tree (OOT) platform plugin architecture, which allows hardware vendors to add accelerator support without modifying vLLM core. The plugin uses Python `entry_points` for discovery, with four separate registration hooks that load platform configuration, utilities, custom operations, and model implementations in a defined order. This design cleanly separates the HPU-specific code from vLLM core while allowing deep integration at the worker, attention backend, and model registry layers.

The `HpuPlatform` class is the architectural anchor. It extends vLLM's `Platform` base class with `_enum = PlatformEnum.OOT`, signaling that this is an out-of-tree platform. The class overrides critical platform methods: device memory management, attention backend selection (choosing between unified, MLA, and v1 backends based on model configuration), configuration validation (forcing bfloat16 precision, 128-block KV cache, disabling torch.compile in favor of HPU-native compilation), and distributed communication (providing `HpuCommunicator` for inter-HPU communication and NIXL support for KV transfer).

The quantization support is notably broad for an accelerator plugin — `compressed-tensors`, `fp8`, `inc` (Intel Neural Compressor), `awq_hpu`, `gptq_hpu`, and `modelopt` are all listed as supported quantization methods. The INC quantization path includes a specific workaround that forces CPU weight loading to prevent OOM during quantization of large models, indicating mature handling of memory-constrained deployment scenarios.

The model registry contains 11 HPU-optimized model implementations, predominantly multimodal and MoE architectures (Gemma3, Qwen2.5-VL, Qwen3-VL-MoE, DeepSeek v2, Pixtral, HunYuan dense and MoE variants). These are registered as replacements for the standard vLLM model implementations, allowing HPU-specific optimizations in attention computation, memory layout, and operator fusion while maintaining API compatibility with vLLM's model loading pipeline.

As a plugin package, vllm-gaudi has no independent network surface — it does not expose HTTP or gRPC endpoints, manage authentication, or create Kubernetes resources. All network exposure is inherited from the vLLM server process that loads the plugin. This clean separation means the component's security posture is entirely determined by the vLLM deployment configuration, not by the plugin itself.
