## Purpose

**Short**: Hardware plugin that enables vLLM inference serving on Intel Gaudi accelerators, shipped as a container image running the OpenAI-compatible API server.

**Detailed**: vllm-gaudi is the Intel Gaudi (Habana) hardware plugin for the vLLM inference engine. It implements vLLM's plugin architecture to register a custom `HpuPlatform`, specialized attention backends, HPU-optimized custom ops (fused MoE, attention, FP8 quantization, rotary embedding, LoRA), and model-specific overrides for architectures that need HPU-tailored implementations (Gemma3, Qwen2.5-VL, Qwen3-VL-MoE, DeepSeek-v2, Pixtral, and others).

The Konflux container image (`Dockerfile.konflux.gaudi`) is a multi-stage build on UBI 9 that installs the Habana SynapseAI SDK, PyTorch for HPU, upstream vLLM (pinned to a verified commit), and the vllm-gaudi plugin. The container's entrypoint runs the vLLM OpenAI-compatible API server (`vllm.entrypoints.openai.api_server`), exposing standard `/v1/completions` and `/v1/chat/completions` endpoints. In RHOAI deployments, this image is instantiated by the model serving stack (KServe/ModelMesh) as a ServingRuntime container rather than being self-deployed.

The plugin supports Intel Gaudi 2 and Gaudi 3 hardware, with features like unified attention, MLA (Multi-head Latent Attention), NIXL-based disaggregated KV transfer, online memory defragmentation, and multiple quantization schemes (INC FP8, compressed-tensors, AWQ, GPTQ, ModelOpt).

## Architectural Analysis

vllm-gaudi follows a modular plugin architecture that cleanly separates hardware-specific concerns from the upstream vLLM framework. The plugin registers itself through Python entry points (`vllm.platform_plugins` and `vllm.general_plugins`), inserting HPU-specific implementations at four extension points: platform registration, utility functions, custom ops (attention, quantization, MoE, embedding operations), and model overrides.

The most architecturally significant pattern is the runtime configuration system (`vllm_gaudi/extension/`), which provides a lazy-evaluated, environment-variable-driven configuration framework. This system detects the hardware variant (Gaudi 2 vs Gaudi 3), selects appropriate attention backends (unified attention, FSDPA, MLA), and gates experimental features behind `VLLM_DEVELOPER_MODE`. The bucketing system for prompt/decode batch sizes enables HPU graph compilation by padding tensors to predictable shapes, a pattern unique to Habana's compiler infrastructure.

Distributed inference relies on Habana's HCCL collective communication library, wrapped by `HpuCommunicator`. The NIXL connector enables disaggregated prefill architectures where KV cache is transferred between workers, with an HPU-specific data pointer mapping workaround for the Habana PT bridge.

A notable security concern is the explicit removal of the OpenSSL FIPS provider in all Dockerfiles (`rpm -e --nodeps openssl-fips-provider-so`). This means the container actively opts out of FIPS-mode cryptography, which conflicts with Red Hat product security requirements for FIPS-capable images.

The container image does not use AIPCC base images despite installing substantial Python dependencies via pip. This represents a supply chain gap -- the image builds Python packages from upstream PyPI and Habana's own index rather than Red Hat's secure build pipelines.
