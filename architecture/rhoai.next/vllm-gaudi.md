## Purpose

**Short**: Intel Gaudi (Habana) hardware plugin for vLLM that enables high-performance LLM inference on HPU accelerators.

**Detailed**: vllm-gaudi is a hardware plugin that integrates Intel Gaudi AI accelerators with the vLLM inference engine. It follows vLLM's pluggable hardware architecture (RFC #11162 and #19161), providing HPU-specific implementations of attention backends, model runners, workers, distributed communication, speculative decoding, quantization kernels, and memory management.

The plugin registers itself via Python entry points (`vllm.platform_plugins` and `vllm.general_plugins`) to inject HPU-optimized code paths into vLLM's execution pipeline. It replaces CUDA-specific operations with Habana equivalents — including HCCL for collective communication, FusedSDPA for attention, custom HPU kernels for MoE routing, FP8 quantization, and HPU Graph-based compilation for reduced overhead.

The downstream Red Hat build produces a container image (`odh-vllm-gaudi-rhel9`) based on UBI9 with Habana SynapseAI drivers, PyTorch for Gaudi, and the vLLM + vllm-gaudi stack pre-installed. The image serves an OpenAI-compatible API server as its default entrypoint, making it deployable as a KServe InferenceService runtime or standalone inference server within RHOAI.

## Architectural Analysis

The vllm-gaudi plugin is structured as a clean hardware abstraction layer that injects itself into vLLM via Python entry points. The `setup.py` defines four entry points: `vllm.platform_plugins` for the `HpuPlatform` class, and three `vllm.general_plugins` for utilities, custom ops, and model overrides. This design allows the plugin to be installed alongside vLLM without modifying vLLM's source code. The plugin uses extensive monkey-patching to replace upstream implementations at runtime — for example, `vllm_gaudi/ops/hpu_attention.py` patches `Attention.forward`, and `vllm_gaudi/models/utils.py` patches `_merge_multimodal_embeddings`.

The plugin's extension subsystem (`vllm_gaudi/extension/`) implements a sophisticated configuration framework with lazy evaluation, hardware detection (Gaudi2 vs Gaudi3), feature flags, and kernel availability checking. The `Config` class uses dependency resolution to compute configuration values on demand, supporting environment variable overrides via `VLLM_*` prefixed variables (40+ documented). This is notably different from vLLM's own configuration — vllm-gaudi maintains a parallel config system tuned for HPU-specific concerns like contiguous paged attention, unified attention, and HPU Graph compilation.

The attention architecture is particularly complex, offering five distinct backends: `HPUAttentionBackendV1` (standard V1 paged attention), `HPUUnifiedAttentionBackend` (merged prefill/decode), `HPUMLAAttentionBackend` (multi-head latent attention for DeepSeek-style models), `HPUUnifiedMLABackend`, and legacy attention paths. The unified attention approach (`vllm_gaudi/extension/unified.py`, 1500+ lines in ops.py) merges prefill and decode batches into a single HPU Graph call, reducing compilation overhead at the cost of complexity. The bucketing system (`vllm_gaudi/extension/bucketing/`) manages tensor shape quantization to minimize HPU Graph recompilation — a critical performance concern since each unique tensor shape triggers a separate graph compilation.

A notable security concern is the explicit removal of `openssl-fips-provider-so` in the Dockerfile (line 63), which strips FIPS-validated OpenSSL modules from the image. Combined with the fully non-hermetic build (no lock files, `hermetic: false` in Tekton config, dependencies fetched from public internet at build time), this represents a gap in both FIPS compliance and supply chain security. The image also clones upstream vLLM and vllm-gaudi from GitHub during the build, pinned only to a tag (`v0.16.0`) rather than a content-addressable hash. These issues are expected to be addressed on downstream release branches where Konflux hardening is applied.

The model layer supports 14 architectures with HPU-optimized implementations, focusing on models with complex attention patterns: Qwen2.5-VL and Qwen3-VL (vision-language with 2D rotary embeddings), Pixtral (2D RoPE vision encoder), MiniMax M2 and DeepSeek V2 (MoE), Gemma3 multimodal, HunYuan (dense and MoE), and several OCR models. Each model override patches specific methods for HPU compatibility — typically replacing dynamic tensor operations with static-shape alternatives that compile efficiently to HPU Graphs. The quantization stack supports FP8 (per-tensor and channel-wise), INC (Intel Neural Compressor), AWQ, GPTQ, ModelOpt, and compressed-tensors formats, with special handling for INC's forced CPU loading to prevent OOM during weight quantization.
