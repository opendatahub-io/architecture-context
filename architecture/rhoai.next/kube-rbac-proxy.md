## Purpose

**Short**: An HTTP reverse proxy sidecar that enforces Kubernetes RBAC authorization via SubjectAccessReview before forwarding requests to an upstream service.

**Detailed**: kube-rbac-proxy is a small, single-upstream HTTP reverse proxy designed to run as a sidecar container alongside services that expose endpoints (typically metrics) which need access control. It intercepts incoming HTTPS requests, authenticates the caller using either delegating TokenReview, OIDC JWT validation, or client TLS certificates, then authorizes the request by submitting a SubjectAccessReview to the Kubernetes API server. Only authenticated and authorized requests are forwarded to the upstream service listening on localhost.

The proxy supports two authorization configuration formats: Format1, which applies top-level `resourceAttributes` and `rewrites` to all requests, and Format2, which provides path-scoped endpoint rules with per-method resource mappings, named path captures, and header/query parameter rewriting. This flexibility allows operators to map incoming HTTP requests to fine-grained Kubernetes RBAC policies. A hardcoded authorizer additionally allows the OpenShift monitoring Prometheus service account (`system:serviceaccount:openshift-monitoring:prometheus-k8s`) to scrape `/metrics` without explicit RBAC configuration.

In the RHOAI platform, kube-rbac-proxy is deployed as a sidecar container alongside platform components that need to expose authenticated metrics endpoints or protect internal APIs with Kubernetes-native RBAC. It terminates TLS, performs authentication and authorization, and proxies authorized requests to the upstream service over localhost HTTP.

## Architectural Analysis

kube-rbac-proxy follows a straightforward request-filter-proxy architecture. Every inbound request passes through a pipeline of HTTP handler middleware: path allow/ignore filtering, authentication (OIDC or delegating TokenReview), authorization (hardcoded metrics authorizer → static authorizer → SAR authorizer via `union.New`), optional auth header injection, and finally reverse-proxy forwarding to the upstream. This layered design makes the security enforcement chain explicit and auditable.

The TLS layer is notable for its support of certificate hot-reloading via a polling `CertReloader` that reads cert/key pairs at a configurable interval and swaps them atomically using `GetCertificate`. The server enforces configurable minimum TLS version, cipher suites, and curve preferences through `k8s.io/component-base/cli/flag` utilities. Upstream connections also enforce TLS 1.2+ minimum and support mutual TLS with custom CA bundles and client certificates.

The authorization subsystem has two distinct code paths. Format1 (top-level `resourceAttributes` and `rewrites` in `pkg/proxy`) handles the common case of mapping all requests to a single SAR template with optional query/header rewriting. Format2 (`pkg/authz/endpoints.go`) provides path-pattern matching with named captures (`{tenant}`), per-HTTP-method resource rule selection, and template expansion using `text/template`. The two formats coexist; Format2 endpoints take precedence when the request path matches, falling back to Format1 otherwise.

The hardcoded metrics authorizer (`pkg/hardcodedauthorizer`) is an OpenShift-specific accommodation that unconditionally allows the monitoring Prometheus service account to GET `/metrics`. This bypasses the SAR check and represents a coupling to OpenShift monitoring infrastructure.

The audit subsystem (`pkg/audit`) provides structured JSON audit logging at the metadata level, capturing user identity, authorization attributes, endpoint matching decisions, and upstream response status. It integrates as middleware around the authorization filter chain.
