## Purpose

**Short**: High-performance system for processing large-scale batch inference jobs in Kubernetes environments, providing an OpenAI-compatible API for submitting, tracking, and managing batch inference workloads.

**Detailed**: Batch Gateway is a multi-component Go service that implements the OpenAI Batch API (`/v1/batches` and `/v1/files` endpoints) for large-scale offline inference. It is designed to run alongside interactive inference workloads served by llm-d Router, minimizing interference with interactive traffic while satisfying batch jobs' service level objectives (SLOs). The system supports up to 50,000 requests per job, model-aware scheduling for prefix cache optimization, and adaptive concurrency control (AIMD) that dynamically adjusts dispatch rate based on downstream success/failure signals.

The system consists of three independently deployable components: an **API Server** that handles REST API requests, a **Batch Processor** that pulls jobs from a priority queue and dispatches inference requests to downstream llm-d Routers, and a **Garbage Collector** that cleans up expired jobs/files and recovers orphaned work items. All components share a common data layer backed by PostgreSQL (metadata), Redis/Valkey (queue, events, status), and S3-compatible or filesystem storage (input/output files). Authentication is delegated to an external gateway layer (Kuadrant/Authorino), and all data access is scoped to an authenticated tenant extracted from HTTP headers.

## Architectural Analysis

Batch Gateway is architecturally notable for its **composable pipeline pattern** in the processor component. The dispatch pipeline is built from interchangeable stages — `PreDispatcher → DirectDispatcher|AsyncDispatcher → AIMDDispatcher → ResultCollector` — where each stage implements a common interface. This allows the same job execution framework to support both synchronous HTTP dispatch (direct to llm-d Router) and asynchronous queue-based dispatch (via llm-d-async) by swapping a single pipeline stage. The AIMD wrapper is orthogonal and can wrap either dispatcher, providing adaptive concurrency control without modifying the dispatch logic itself.

The **multi-tenancy model** is application-enforced rather than infrastructure-enforced. Every database query includes a tenant ID filter, and file storage uses SHA256-based folder paths derived from the tenant ID. However, the API server has no built-in authentication — tenant identity is derived entirely from HTTP headers injected by an upstream auth gateway (Kuadrant/Authorino). This is a deliberate security architecture: the API server is designed to sit behind an auth proxy and must not be directly reachable. The security guide explicitly documents this as a hard prerequisite. Cross-tenant access returns 404 rather than 403, preventing tenant enumeration.

The **concurrency control** system is multi-layered and worth highlighting. At the job level, a worker semaphore limits concurrent jobs. At the request level, a global semaphore limits total in-flight inference requests across all jobs and endpoints, while per-endpoint semaphores add fine-grained control. On top of this, the AIMD (Additive Increase, Multiplicative Decrease) controller dynamically adjusts per-endpoint limits based on 429 and 5xx signals from downstream inference services. This means the processor automatically backs off when the inference tier is overloaded, protecting interactive traffic without manual tuning. The AIMD implementation uses three signal types for backoff: HTTP 429 (rate limit), HTTP 5xx (server error), and "capacity retry" (a synthetic signal from the llm-d Router indicating the request was queued but the server prefers it be retried later).

The **garbage collector's orphan reconciler** is an important resilience mechanism. When a processor pod crashes, its in-flight jobs become orphaned in non-terminal states. The reconciler periodically scans for jobs that are `in_progress` but have no active in-flight entry (or a stale one), and either transitions them to `failed`, re-enqueues them for retry, or marks them `expired` if the SLO has passed. This implements a compare-and-swap (CAS) pattern on the database to prevent race conditions when multiple GC instances or recovering processors compete to transition the same job.

The **secret management** pattern uses `os.OpenInRoot()` (Go 1.24+) to read secrets from the `/etc/.secrets/` mount path, which prevents path traversal attacks that could escape the mount directory. Secret key names are hardcoded (`redis-url`, `postgresql-url`, `inference-api-key`, `s3-secret-access-key`) and loaded at startup with fallback resolution: config file → secret file → mounted secret directory. This is a defense-in-depth approach where the application assumes a hostile environment even within the container.
