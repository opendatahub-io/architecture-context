## Purpose

**Short**: OpenAI-compatible batch API gateway for llm-d that accepts, queues, processes, and finalizes batch inference jobs against LLM backends.

**Detailed**: The batch-gateway implements the [OpenAI Batch API](https://platform.openai.com/docs/api-reference/batch) specification, enabling users to submit large sets of inference requests as batch jobs. It stores input/output files in S3 or filesystem storage, tracks job state in PostgreSQL (primary) or Redis/Valkey, and dispatches individual requests to LLM inference backends through either synchronous HTTP or asynchronous queue-based flows.

The system consists of three independently deployable binaries: the **apiserver** exposes RESTful endpoints for batch and file management with multi-tenant isolation; the **processor** polls a priority queue for pending jobs, downloads input files, dispatches requests to inference gateways with adaptive concurrency control (AIMD), and uploads result files; the **garbage collector** periodically removes expired batch jobs and files while a reconciler subsystem detects orphaned in-progress jobs from crashed processors and recovers them.

All three binaries are deployed via a single Helm chart and share the same database and file storage backends. The processor supports integration with the llm-d Gateway Inference Extension (GIE) via `x-gateway-inference-objective` headers and the llm-d-async producer library for asynchronous dispatch modes.

## Architectural Analysis

The batch-gateway follows a clean three-tier architecture with clear separation of concerns: the apiserver handles user-facing API operations, the processor handles compute-intensive batch execution, and the gc handles lifecycle maintenance. This separation allows each component to be scaled, upgraded, and debugged independently — for example, processor replicas can be scaled horizontally to handle queue depth while the apiserver and gc remain at low replica counts.

The processor's pipeline architecture is particularly well-designed. The composable dispatcher chain (PreDispatcher → AIMDDispatcher → DirectDispatcher for sync mode, or PreDispatcher → AsyncDispatcher for async mode) follows a chain-of-responsibility pattern that cleanly separates concerns: input filtering, concurrency control, and actual dispatch. The AIMD (Additive Increase Multiplicative Decrease) adaptive concurrency controller is a sophisticated feature that enables the processor to dynamically adjust its per-endpoint request rate based on backpressure signals (HTTP 429, 5xx, capacity retries), preventing overload of downstream inference servers while maximizing throughput during quiet periods. The semaphore hierarchy (global ceiling → per-endpoint adaptive → per-request goroutine) provides three layers of flow control.

The multi-tenant isolation model relies entirely on a trusted upstream proxy injecting the tenant identity header (default: X-MaaS-Username). The apiserver performs no authentication or API key validation itself — it trusts the header and enforces tenant-scoped visibility by filtering database queries. This is a deliberate architectural decision that offloads authn/authz to the platform's ingress layer (e.g., Envoy ext_authz, kube-rbac-proxy), but means the apiserver must never be exposed directly without an authenticating proxy in front.

The crash recovery mechanism is noteworthy: the processor writes intermediate artifacts (plan files, partial output JSONL) to a local emptyDir volume, and on restart it scans this directory to detect and recover stale jobs. Phase-aware recovery (finalizing → re-upload; in_progress with output → fail with partial results; in_progress without output → re-enqueue) ensures that no batch job is silently lost across container restarts. The GC reconciler complements this by detecting jobs that appear stuck (in-flight entries not refreshed within the heartbeat interval) after pod eviction (where emptyDir is destroyed).
