## Purpose

**Short**: High-performance batch inference gateway providing an OpenAI-compatible API for submitting, tracking, and managing large-scale batch inference jobs on Kubernetes.

**Detailed**: Batch Gateway is a multi-component system that bridges the gap between batch and interactive inference workloads in Kubernetes environments. It provides full schema parity with OpenAI's `/v1/batches` and `/v1/files` endpoints, enabling users to submit batch inference jobs of up to 50,000 requests, track progress in real-time, and retrieve results.

The system is decomposed into three independently deployable binaries: an API server that handles REST requests for batch and file management, a batch processor deployed as a StatefulSet that pulls jobs from a priority queue and dispatches inference requests to downstream llm-d gateways, and a garbage collector that periodically reclaims expired jobs and files while reconciling orphaned work from crashed processors. This separation enables independent scaling — API servers scale horizontally for request throughput while processors scale to match inference backend capacity.

The data layer uses PostgreSQL for job and file metadata, Redis/Valkey for priority queuing and event channels, and S3-compatible or filesystem storage for batch input/output files. The processor supports two dispatch modes: synchronous (direct HTTP to inference gateways) and asynchronous (via llm-d-async Redis queues). Model-aware scheduling groups requests by model and system-prompt hash for KV-cache optimization, while AIMD-based adaptive concurrency control protects interactive traffic from batch interference.

## Architectural Analysis

Batch Gateway follows a classic queue-driven worker architecture adapted for inference workloads. The API server and processor share no in-process state — all coordination flows through the database and queue layer, making the system crash-tolerant and horizontally scalable.

The authentication model is deliberately delegated: the API server itself does not enforce authentication on its endpoints. Instead, authentication and authorization are expected to be handled upstream by a gateway layer (Kuadrant/Authorino or similar), which injects a tenant identity header (`X-MaaS-Username`). The API server's request middleware extracts this tenant ID and propagates it through context, where every database query is scoped to the tenant. Cross-tenant access returns 404, providing application-level isolation even without per-request auth enforcement within the service itself. This is a conscious design choice documented in the security guide, but it means the batch gateway API is fully open if deployed without an upstream auth gateway.

The processor's inference dispatch architecture is notable for its flexibility. Three mutually exclusive dispatch modes are supported: a single global gateway URL, per-model gateway mappings, and async dispatch via llm-d-async. The per-model mode supports tenant-scoped route keys, enabling multi-tenant inference pool isolation. The AIMD concurrency controller dynamically adjusts dispatch rates based on 429/5xx signals, with a configurable floor to prevent starvation.

The GC component includes an orphan reconciler that watches processor pods via the Kubernetes API. When a processor pod disappears, the reconciler detects in-flight jobs assigned to it and either re-enqueues or expires them. This provides crash recovery without requiring distributed locks or consensus.

TLS is optionally available on the API server with configurable minimum version, cipher suites, and ALPN protocols. The processor supports custom CAs and mTLS for outbound connections to inference gateways, enabling secure communication within service mesh or zero-trust environments.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to upstream gateway (Kuadrant/Authorino); tenant ID injected via header | External gateway | If deployed without an upstream auth gateway, API endpoints are fully unauthenticated. Tenant identity relies on a trusted header that must not be spoofable by end users |
| Data storage | All database queries scoped by tenant ID; cross-tenant access returns 404 | Application (query filters) | Application-enforced: a bug in query scoping could leak data across tenants. No database-level isolation (shared PostgreSQL, shared Redis) |
| Network traffic | No per-tenant NetworkPolicies created by the component | N/A | All tenants share the same network path; isolation depends on the upstream gateway |
| Compute & resources | Shared workers process all tenants' jobs | N/A | No per-tenant resource quotas or priority within the batch processor; a tenant with many large jobs can consume all worker capacity |
| Configuration & secrets | Shared secrets (PostgreSQL URL, Redis URL, API key) mounted read-only | Kubernetes | Single set of credentials used for all tenants |
| API scoping | Tenant-filtered queries via context-propagated tenant ID | Application | Every API handler extracts tenant ID from context and passes it to database queries |

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|

| llm-d inference gateway | Shared endpoint(s), requests carry tenant's batch context | No tenant isolation at inference layer |
