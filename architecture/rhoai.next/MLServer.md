## Purpose

**Short**: MLServer is a multi-protocol machine learning inference server implementing the V2 Inference Protocol (KServe predict protocol v2) with pluggable ML framework runtimes.

**Detailed**: MLServer provides a production-grade inference serving layer that exposes trained ML models over REST (HTTP), gRPC, and optionally Apache Kafka transports. It implements the open V2 Inference Protocol (also known as the KServe/Triton predict protocol), enabling standardized model deployment regardless of the underlying ML framework. The server supports adaptive request batching, response caching, parallel multi-process inference workers, OpenTelemetry distributed tracing, and Prometheus metrics collection.

The project ships as a Python package (`mlserver`) along with a set of pluggable runtime adapters for popular ML frameworks including Scikit-learn, XGBoost, LightGBM, ONNX Runtime, HuggingFace Transformers, MLflow, Alibi Explain, Alibi Detect, CatBoost, and Spark MLlib. For RHOAI, the server is packaged into two Konflux-built container images: a CPU variant bundling sklearn, xgboost, lightgbm, and onnx runtimes, and a CUDA variant with GPU-accelerated ONNX runtime.

MLServer is deployed as a model serving container within KServe InferenceService pods. It functions as the model server that KServe's data plane routes inference requests to. A runtime security system enforces a trusted-runtimes allowlist in production images, preventing arbitrary code execution from user-supplied model configurations.

## Architectural Analysis

MLServer implements a clean multi-transport architecture where three protocol handlers (REST via FastAPI/uvicorn, gRPC via grpc.aio, Kafka via aiokafka) converge on a shared DataPlane core. The DataPlane orchestrates the inference pipeline: request middleware → cache lookup → model dispatch → response middleware → cache insert. This design means that all transports benefit from the same batching, caching, and metrics instrumentation without duplication.

The parallel inference subsystem is particularly well-architected for Python's GIL constraints. When `parallel_workers > 1`, MLServer spawns separate OS processes (via multiprocessing), each loading an independent copy of the model. The main process acts as a dispatcher, routing inference requests to worker processes via queues. Prometheus metrics use a MultiProcessCollector to aggregate counters and histograms across all workers. This is critical for CPU-bound ML inference where the GIL would otherwise serialize predictions.

The runtime security model introduces a production/development dichotomy controlled by the presence of `/etc/mlserver/trusted-runtimes.json`. In production images (built via Dockerfile.konflux), this file is generated at build time from the `TRUSTED_RUNTIMES` build argument, containing the exact list of allowed runtime import paths. The validation is enforced at two points: when ModelSettings are parsed and when the `implementation` property is accessed. This prevents arbitrary code execution from user-supplied `model-settings.json` files, which is a significant security boundary since model artifacts are typically user-controlled. The CORS policy is also restricted in production mode — wildcard origins and regex patterns are rejected. Custom Python environments (tarballs or sys.path extensions) are blocked entirely in production.

The codec system provides a bridge between V2 protocol tensors and Python ML framework types. NumpyCodec handles ndarray serialization with 14 data type mappings, PandasCodec maps DataFrame columns to individual tensors, and StringCodec handles text data. This layered codec architecture allows each runtime to declare its preferred input/output format while maintaining protocol compatibility.

One noteworthy architectural observation is that MLServer itself provides no TLS termination or authentication — it listens on plaintext HTTP and gRPC. This is intentional: in the RHOAI deployment model, KServe manages ingress (via Gateway API/HTTPRoute or OpenShift Routes), and authentication is enforced by kube-rbac-proxy sidecars or the platform's auth proxy. The batch_processing module's `ssl_context=False` for tritonclient calls is a local loopback optimization, not an external connection. The alibi-explain runtime's `ssl_verify_path` configuration is the only place where outbound TLS verification is configurable, used when the explainer needs to call a remote predictor.
