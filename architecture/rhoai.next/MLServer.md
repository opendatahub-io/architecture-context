## Purpose

**Short**: MLServer is a multi-model inference server implementing the KServe V2 Inference Protocol with REST and gRPC endpoints, supporting pluggable ML runtimes (scikit-learn, XGBoost, LightGBM, ONNX, HuggingFace, MLflow, CatBoost, Alibi, and MLlib).

**Detailed**: MLServer provides a production-grade, standards-compliant model serving runtime for the Red Hat OpenShift AI (RHOAI) platform. It exposes both a REST/HTTP API (via FastAPI/Uvicorn) and a gRPC API that implement the KServe V2 Inference Protocol (also known as the Open Inference Protocol), enabling any V2-compatible client to perform inference, manage model lifecycle, and query server/model metadata through standardized endpoints.

The server supports multi-model serving through a model registry that can load, unload, and version-manage multiple models concurrently. Performance features include adaptive request batching (grouping requests to improve throughput), parallel inference workers (multiprocessing for CPU-bound models), response caching, and gzip compression. Observability is built-in with Prometheus metrics exposition, OpenTelemetry distributed tracing, structured logging, and CloudEvents header injection for event-driven architectures. An optional Kafka integration enables asynchronous inference via message queues.

In the RHOAI platform, MLServer is deployed as a container within KServe `InferenceService` pods to serve traditional ML models (scikit-learn, XGBoost, LightGBM, ONNX). It ships in two Konflux-built image variants: a CPU image (`odh-mlserver`) with four runtimes (LightGBM, ONNX, scikit-learn, XGBoost) and a CUDA GPU image (`odh-mlserver-cuda`) with a single ONNX runtime configured for NVIDIA GPU acceleration. Both images use AIPCC base images from the Red Hat AI ecosystem and include a trusted runtimes allowlist mechanism that restricts model implementations to pre-approved import paths, preventing arbitrary code execution in production deployments.

## Purpose

**Short**: MLServer is a Python-based ML inference server providing V2 Inference Protocol endpoints over REST (FastAPI) and gRPC, deployed as a model serving runtime within KServe InferenceService pods on RHOAI.

**Detailed**: MLServer is an open-source inference server originally developed by Seldon Technologies and packaged for Red Hat OpenShift AI. It implements the V2 Inference Protocol (also known as the Open Inference Protocol) through dual REST (FastAPI/Starlette on uvicorn) and gRPC interfaces, exposing 11 RPCs on the `GRPCInferenceService` and 3 RPCs on the `ModelRepositoryService`. The server supports a pluggable runtime architecture with 10 ML framework-specific runtime packages (sklearn, xgboost, lightgbm, ONNX, MLflow, HuggingFace, Alibi-Detect, Alibi-Explain, CatBoost, and Spark MLlib). In RHOAI, MLServer runs as the inference container inside KServe InferenceService pods, where KServe manages lifecycle, scaling, and traffic routing. MLServer does not implement its own authentication — endpoint security is delegated to the platform infrastructure (kube-rbac-proxy sidecars in RHOAI 3.x). The server integrates with platform observability through OpenTelemetry (traces and metrics via OTLP gRPC) and Prometheus (starlette-exporter and py-grpc-prometheus), and supports event-driven inference via Kafka (aiokafka).

## Architectural Analysis

MLServer's architecture follows a clean layered design with protocol-agnostic business logic. The `DataPlane` handler class contains all inference logic (model lookup, caching, batching, CloudEvents middleware) and is consumed identically by both the REST server (FastAPI) and gRPC server (grpc.aio). This means protocol-specific concerns (HTTP routing, gRPC interceptors, SSE streaming, protobuf conversion) are isolated in their respective server modules while sharing the same model registry, metrics, and inference pipeline. The `handlers/` layer never imports protocol-specific types.

The runtime plugin system is one of MLServer's most significant architectural decisions. Rather than hardcoding ML framework support, each framework (scikit-learn, XGBoost, etc.) is a separate Python package (`mlserver-sklearn`, `mlserver-xgboost`) that extends the `MLModel` base class. Models are loaded via Python import string resolution (e.g., `mlserver_sklearn.SKLearnModel`), which enables the trusted runtimes security feature: in production mode, only import paths listed in `/etc/mlserver/trusted-runtimes.json` (baked into the container image at build time) can be loaded. This prevents arbitrary code execution via model-settings.json injection. The security hardening also disables custom Python environments (`environment_tarball`, `environment_path`) and wildcard CORS in production mode, closing two additional attack vectors.

The parallel inference worker system uses Python multiprocessing with "spawn" start method to avoid GIL limitations for CPU-bound models. Workers communicate via multiprocessing Queues with a round-robin dispatcher. Each worker loads its own copy of the model, enabling true parallelism. The worker pool integrates with the metrics system through a shared `PROMETHEUS_MULTIPROC_DIR` directory for cross-process metric aggregation. However, for GPU models (CUDA variant), parallelism is typically set to 1 since GPU inference is not CPU-bound and GPU memory cannot be easily shared across processes.

The build pipeline for RHOAI images uses a carefully designed requirements generation system (`hack/generate-pinned-requirements.py`) that resolves Python packages inside the AIPCC base image container against the RHEL AI Python Package Index, producing fully pinned requirements files with SHA256 hashes per target architecture. This ensures reproducible builds that use only Red Hat-approved packages. The Konflux Tekton pipelines enforce hermetic builds (`hermetic: true`), and the two image variants (CPU and CUDA) are defined declaratively in `hack/requirements-config.json` with per-variant root packages and platform targets.

A notable architectural pattern is the model readiness gating: during server startup, the registry tracks a `_startup_complete` flag that prevents the readiness endpoint from returning true until all initial models have finished loading (or failed). After startup, the `strict_readiness` setting controls whether ALL models must be ready or AT LEAST ONE. The `empty_registry_readiness` setting separately controls behavior when no models are loaded. This two-phase readiness model prevents Kubernetes from routing traffic to a partially-initialized server, which is critical for KServe's rolling update strategy.

## Architectural Analysis

MLServer implements the V2 Inference Protocol (Open Inference Protocol), which is the KServe community standard for model serving. It provides a dual-protocol surface — REST via FastAPI/Starlette and gRPC via grpcio — allowing clients to choose the transport that best fits their latency and throughput requirements. The gRPC interface supports streaming inference via `ModelStreamInfer`, enabling token-by-token streaming for generative models.

The runtime plugin architecture is a key design pattern: the core `mlserver` package provides the server infrastructure (HTTP/gRPC endpoints, model registry, lifecycle management), while each ML framework integration is packaged as a separate Python package (e.g., `mlserver-sklearn`, `mlserver-xgboost`). This separation allows RHOAI to ship only the runtimes relevant to each InferenceService configuration, reducing container image size and attack surface. The `odh-runtimes` dependency group in pyproject.toml (lines 114-121) defines the subset shipped for ODH/RHOAI: sklearn, xgboost, lightgbm, and ONNX.

MLServer delegates all authentication to the platform infrastructure. The proto definitions contain no authentication metadata or interceptors, and pyproject.toml includes no authentication libraries. In RHOAI 3.x, KServe deploys a kube-rbac-proxy sidecar alongside the MLServer container to enforce authentication before requests reach the inference endpoints. This design is consistent with the KServe model where the inference runtime is a pure computation component and security is handled at the pod level.

The `RuntimeSecurity` gRPC RPC (dataplane.proto:25-26) provides a distinct security surface: it reports whether the server operates in PRODUCTION or DEVELOPMENT mode and, in production mode, returns the list of allowed model implementation import paths. This is an application-level security control that restricts which Python classes can be loaded as model implementations, mitigating arbitrary code execution risks in production deployments.
