## Purpose

**Short**: IBM Spyre-accelerated vLLM inference server image for RHOAI, providing hardware-accelerated LLM serving via the TGIS adapter on RHEL 9.

**Detailed**: vllm-spyre is a thin Konflux Dockerfile that extends the RHAIIS product image `registry.redhat.io/rhaiis/vllm-spyre-rhel9` to produce the RHOAI-branded inference server container for IBM Spyre accelerators. The repository contains no application source code of its own — all vLLM, TGIS adapter, and Spyre SDK logic is inherited from the RHAIIS base image, which in turn builds on the AIPCC Spyre base image (overlay 0017).

The container runs the `vllm_tgis_adapter` Python module, which wraps vLLM's inference engine with the TGIS (Text Generation Inference Service) gRPC interface on port 8033, alongside vLLM's native OpenAI-compatible HTTP API on port 8000. This adapter pattern allows KServe/ModelMesh to route inference requests to the vLLM backend using the standard TGIS protocol while preserving access to vLLM's native API. The image is intended for deployment as a ServingRuntime container managed by KServe or the model controller within the RHOAI platform.

## Architectural Analysis

This component exemplifies the RHOAI "thin Dockerfile" pattern: the entire repository is a single Konflux Dockerfile that re-layers an RHAIIS product image with RHOAI-specific labels, a non-root user, and environment variable overrides. No application code, deployment manifests, tests, or build logic exists in the repo. All inference functionality, Spyre SDK integration, Python dependencies, and TGIS adapter code originate from the `rhaiis/vllm-spyre-rhel9` base image.

The architectural significance lies in the image layering chain: AIPCC Spyre base image (overlay 0017: Python 3.12, RHEL 9.8, IBM Spyre SDK 1.3.1, pip/uv configured for the Spyre content channel) provides the accelerator runtime and Python package index. The RHAIIS vllm-spyre-rhel9 image adds vLLM, the TGIS adapter, and model-serving dependencies. This repository's Dockerfile adds only RHOAI product metadata and runtime configuration (ports, user, spec-decoding optimization flag).

The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` override is notable: upstream vLLM disables logprobs during speculative decoding as an optimization, but this Dockerfile explicitly reverses that default to ensure users of hosted models get expected logprob behavior regardless of whether spec decoding is enabled.

Because the repository has a single commit and no deployment manifests, RBAC, or services, the operational surface is entirely determined by the RHAIIS base image and the platform's ServingRuntime/InferenceService definitions that reference this container image.

FIPS compliance, build hermeticity, and Python package provenance cannot be independently verified from this repository — they are inherited from the RHAIIS and AIPCC base image build pipelines. Architects evaluating this component's security posture must trace through those upstream layers.
