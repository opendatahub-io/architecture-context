## Purpose

**Short**: IBM Spyre-accelerated vLLM inference server container image for high-performance LLM serving on IBM Spyre hardware.

**Detailed**: vllm-spyre is a thin container image wrapper that extends the Red Hat AI Inference Server (RHAIIS) product image `registry.redhat.io/rhaiis/vllm-spyre-rhel9` with runtime configuration for the vLLM TGIS (Text Generation Inference Server) adapter. The base image provides vLLM pre-built with IBM Spyre accelerator support, and this Dockerfile adds environment variable defaults, a non-root user, and the entrypoint command.

The component exposes both an OpenAI-compatible HTTP API on port 8000 and a gRPC TGIS-compatible endpoint on port 8033, enabling drop-in compatibility with KServe ServingRuntime configurations. It is deployed as a model server pod within the RHOAI inference stack, typically managed by KServe or a ServingRuntime CR. The IBM Spyre accelerator provides hardware-accelerated inference for LLM workloads on ppc64le, s390x, and x86_64 architectures.

## Architectural Analysis

This repository exemplifies the "thin wrapper" container image pattern used in RHOAI for accelerator-specific inference variants. The entire intellectual content of the repository is a single 24-line Dockerfile that extends the RHAIIS (Red Hat AI Inference Server) product image with runtime configuration. There is no application source code, no manifests, no tests, and no CI configuration -- all of that complexity is handled by the upstream vLLM project, the AIPCC base image build pipeline, and the RHAIIS product image build.

The architectural significance of vllm-spyre lies in its position in the build chain: `AIPCC Spyre base image (quay.io/aipcc/base-images/spyre)` -> `RHAIIS vllm-spyre-rhel9 product image (registry.redhat.io/rhaiis/...)` -> `this Dockerfile (red-hat-data-services/vllm-spyre)`. This three-layer chain means that FIPS compliance, build hermeticity, Python package provenance, and IBM Spyre runtime correctness are all inherited from upstream layers and cannot be independently verified from this repository alone. Architects evaluating this component's security posture must trace through the RHAIIS and AIPCC base image pipelines.

The dual-port design (HTTP on 8000 for OpenAI-compatible API, gRPC on 8033 for TGIS protocol) enables this image to serve as a drop-in replacement for the standard vLLM inference server while also supporting legacy TGIS clients. The TGIS adapter (`vllm_tgis_adapter`) is the entrypoint, which wraps vLLM's engine to provide both API surfaces. The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable override is notable -- it ensures that speculative decoding (an optimization technique) does not silently disable logprobs, which would be unexpected for users of a hosted model service.

The repository carries the full upstream vLLM git history (the initial commit and all upstream commits) with only 4 Spyre-specific commits on top. This suggests the repo was created by forking vLLM and adding the Dockerfile, rather than being a standalone project. The upstream README is preserved as-is, which is slightly misleading since this repo doesn't contain vLLM source code that can be built -- it's purely a container image definition.

The non-root execution model (USER 2000) aligns with OpenShift security best practices and KServe's SecurityContext requirements. Authentication is entirely delegated to the platform-injected kube-rbac-proxy sidecar, meaning the vLLM server runs without any auth awareness -- a clean separation of concerns but one that requires the platform operator to correctly inject the sidecar for security to be enforced.
