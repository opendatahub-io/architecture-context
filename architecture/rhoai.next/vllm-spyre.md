## Purpose

**Short**: IBM Spyre-accelerated vLLM inference serving image with TGIS gRPC adapter for RHOAI model serving.

**Detailed**: vllm-spyre is a container image build repository that produces a specialized variant of the vLLM inference engine optimized for the IBM Spyre hardware accelerator. The repository contains no application source code — it consists of a single Konflux Dockerfile that layers configuration on top of the productized `registry.redhat.io/rhaiis/vllm-spyre-rhel9` base image from Red Hat AI Inference Server (RHAIIS).

The Dockerfile configures the `vllm_tgis_adapter` as the entrypoint, which wraps the vLLM engine to expose both an OpenAI-compatible HTTP REST API (port 8000) and a TGIS (Text Generation Inference Server) gRPC API (port 8033). The TGIS protocol is IBM's inference serving protocol compatible with KServe's v2 inference protocol, enabling integration with the KServe model serving stack deployed by RHOAI.

The repository is a downstream fork of the upstream vllm-project/vllm codebase, synced from the `nm/midstream-cuda-v0.9.1.0` branch. However, essentially all upstream vLLM source files have been removed — only the Dockerfile, README, and LICENSE remain. The actual vLLM runtime, Spyre acceleration libraries, and TGIS adapter are all inherited from the RHAIIS base image.

## Architectural Analysis

This repository exemplifies the "thin wrapper" container image pattern used in RHOAI for accelerator-specific inference variants. The entire intellectual content of the repository is a single 24-line Dockerfile that extends the RHAIIS (Red Hat AI Inference Server) product image with runtime configuration. There is no application source code, no manifests, no tests, and no CI configuration -- all of that complexity is handled by the upstream vLLM project, the AIPCC base image build pipeline, and the RHAIIS product image build.

The architectural significance of vllm-spyre lies in its position in the build chain: `AIPCC Spyre base image (quay.io/aipcc/base-images/spyre)` -> `RHAIIS vllm-spyre-rhel9 product image (registry.redhat.io/rhaiis/...)` -> `this Dockerfile (red-hat-data-services/vllm-spyre)`. This three-layer chain means that FIPS compliance, build hermeticity, Python package provenance, and IBM Spyre runtime correctness are all inherited from upstream layers and cannot be independently verified from this repository alone. Architects evaluating this component's security posture must trace through the RHAIIS and AIPCC base image pipelines.

The dual-port design (HTTP on 8000 for OpenAI-compatible API, gRPC on 8033 for TGIS protocol) enables this image to serve as a drop-in replacement for the standard vLLM inference server while also supporting legacy TGIS clients. The TGIS adapter (`vllm_tgis_adapter`) is the entrypoint, which wraps vLLM's engine to provide both API surfaces. The `DISABLE_LOGPROBS_DURING_SPEC_DECODING=false` environment variable override is notable -- it ensures that speculative decoding (an optimization technique) does not silently disable logprobs, which would be unexpected for users of a hosted model service.

The repository carries the full upstream vLLM git history (the initial commit and all upstream commits) with only 4 Spyre-specific commits on top. This suggests the repo was created by forking vLLM and adding the Dockerfile, rather than being a standalone project. The upstream README is preserved as-is, which is slightly misleading since this repo doesn't contain vLLM source code that can be built -- it's purely a container image definition.

The non-root execution model (USER 2000) aligns with OpenShift security best practices and KServe's SecurityContext requirements. Authentication is entirely delegated to the platform-injected kube-rbac-proxy sidecar, meaning the vLLM server runs without any auth awareness -- a clean separation of concerns but one that requires the platform operator to correctly inject the sidecar for security to be enforced.

## Architectural Analysis

This repository follows a "thin Dockerfile" pattern — the entire application stack (vLLM engine, IBM Spyre acceleration libraries, vllm_tgis_adapter, Python runtime) is inherited from the `registry.redhat.io/rhaiis/vllm-spyre-rhel9:3.2.2` base image. The Dockerfile's sole contribution is configuration: it sets the TGIS gRPC adapter as the entrypoint, configures port environment variables (HTTP 8000, gRPC 8033), disables logprob suppression during speculative decoding for user-facing model serving, and runs as non-root user 2000.

The dual-protocol exposure (HTTP + gRPC) is architecturally significant. The HTTP port (8000) serves the OpenAI-compatible REST API that vLLM natively provides. The gRPC port (8033) serves the IBM TGIS (Text Generation Inference Server) protocol, which is the standard inference protocol used by KServe within the RHOAI platform. The `vllm_tgis_adapter` module bridges these two worlds — it wraps vLLM's engine and translates TGIS gRPC requests into vLLM's internal API. This enables KServe to route inference requests to this container using its native gRPC path while also allowing direct HTTP access for debugging or alternative integration patterns.

The repository's minimal footprint creates an interesting supply chain dynamic: almost all security, FIPS compliance, and dependency management characteristics are inherited from the RHAIIS base image rather than being directly observable in this repository. Architecture reviews and vulnerability assessments must trace through to the base image's source repository.
