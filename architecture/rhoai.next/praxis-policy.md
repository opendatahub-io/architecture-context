## Purpose

**Short**: A typed policy enforcement runtime (Reference Monitor) for AI agent traffic, deciding who may call which tool, what data returns, and where it may flow next.

**Detailed**: The Praxis Policy Engine (PPE) is a deterministic reference monitor that sits between an untrusted LLM-driven agent and every capability the agent invokes: tools, prompts, resources, inference calls, and A2A methods. It is not a standalone service or operator -- it is an embeddable Rust library that a host process (such as the Praxis proxy gateway) links in. The host installs the engine, loads an APL (Authorization Policy Language) configuration, and dispatches every agent operation through a five-phase plugin pipeline.

Each operation runs through policy-defined phases that resolve identity (JWT/API-key verification against an IdP), make authorization decisions (delegated to Cedar, CEL, or OPA policy decision points), exchange and reduce credentials via RFC 8693 token delegation, redact or transform inputs and outputs, track information flow via session taint labels, and emit audit events. The engine evaluates policy against state the LLM cannot observe or forge -- verified tokens, delegation chains, taint labels, and the audit trail itself.

PPE ships as a Cargo workspace of 11 crates with a facade crate (`praxis-policy`) that re-exports the runtime. Nine bundled extension plugins (JWT identity, API-key identity, OAuth delegation, CIBA elicitation, Cedar/CEL/OPA decision points, Valkey session store, Vault secrets) are each behind individual Cargo features. The engine performs no HTTP itself; the host injects its own transport so PPE shares the process's connection pool, TLS trust store, and egress policy. A reference hyper-based transport is available behind the `http-hyper` feature for standalone use.

## Architectural Analysis

PPE's architecture is organized around a strict separation between the policy runtime (which never touches the network, the filesystem, or any external system directly) and the host that embeds it. The five-phase executor (sequential, transform, audit, concurrent, fire-and-forget) dispatches registered plugins against a config-driven pipeline, where scheduling decisions come from trusted configuration rather than from the plugin itself. This design makes the engine embeddable anywhere -- a proxy, a sidecar, a WASM host, or an in-process agent framework -- without carrying its own HTTP client, TLS stack, or connection pool.

The APL layer compiles routes at config load time, binding predicates and effects to the operations they govern. Three policy decision point dialects (Cedar, CEL, OPA) are pluggable through a `PdpFactory` trait, and a differential test harness (`ppe-pdp-diff`) ensures all three produce equivalent decisions for shared test corpora. This multi-dialect approach lets operators choose their preferred policy language without the engine taking an opinion.

The security model treats the LLM as a compromised principal. Identity is resolved from verified tokens (never from agent-supplied claims), delegation mints audience-scoped downstream credentials (never forwarding the caller's raw token), and session taint labels persist in a session store the model cannot reach. The `unsafe_code = "forbid"` lint and comprehensive panic-source denial (`unwrap_used`, `expect_used`, `panic`, `indexing_slicing` all denied) reflect a library-grade safety posture -- the engine must not abort the host process on recoverable input.

Egress safety is enforced at the transport layer: the bundled hyper transport blocks SSRF by refusing RFC 1918, link-local (including cloud metadata at 169.254.169.254), loopback, and CGNAT addresses, with a DNS resolver that checks resolved addresses rather than just IP literals. This closes the rebinding vector where a hostname initially resolves to a public address but later resolves to a private one.
