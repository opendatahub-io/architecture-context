## Purpose

**Short**: MLflow is an open-source ML experiment tracking, model registry, and model management server that provides a centralized platform for managing the complete machine learning lifecycle within Red Hat OpenShift AI.

**Detailed**: MLflow serves as the experiment tracking and model management backbone for RHOAI. It exposes REST and GraphQL APIs for logging experiment runs, parameters, metrics, and artifacts; managing model versions and their lifecycle through a model registry; and providing an AI gateway for LLM endpoint management with rate limiting and guardrails.

The RHOAI fork extends upstream MLflow with workspace-based multi-tenancy (mapping workspaces to Kubernetes namespaces), a Kubernetes-native authentication plugin (`kubernetes-auth`), module-federated UI components for embedding into the RHOAI dashboard, and MCP (Model Context Protocol) registry support. The server is deployed as a single Python process running on uvicorn/gunicorn behind a FastAPI application that wraps the legacy Flask app via WSGI middleware, serving both the REST API and a React-based web UI on port 5000.

The component is built hermetically via Konflux using the AIPCC Python Package Index for dependency resolution, and ships as a UBI9-minimal-based container image supporting amd64, arm64, ppc64le, and s390x architectures.

## Purpose

**Short**: MLflow is an open-source ML lifecycle platform providing experiment tracking, model registry, and an AI Gateway that proxies requests to configurable LLM provider endpoints with per-endpoint rate limiting.

**Detailed**: MLflow ships as three distributable Python packages: the full `mlflow` package (a FastAPI-based service encompassing the tracking server, AI Gateway, model serving, and experiment management), `mlflow-skinny` (a lightweight variant with the same FastAPI server core but reduced dependencies for environments that do not need the full ML library stack), and `mlflow-tracing` (a minimal instrumentation-only SDK for distributed tracing via OpenTelemetry without the server or tracking components). The AI Gateway (`mlflow/gateway/app.py`) provides an OpenAI-compatible API surface (`/v1/chat/completions`, `/v1/completions`, `/v1/embeddings`) that routes requests to configurable upstream LLM providers (OpenAI, Azure OpenAI, Anthropic, Cohere, and others) with per-endpoint rate limiting via slowapi. The deployment client architecture supports pluggable backends through Python entry points (`mlflow.deployments`), with built-in plugins for Databricks, OpenAI, and generic HTTP/HTTPS endpoints. The gateway enforces no application-level identity authentication; in RHOAI deployments, access control is expected to be provided by the platform ingress layer (e.g., kube-rbac-proxy or network policy). An optional basic-auth plugin for the tracking server is available via the `mlflow.app` entry point (`libs/skinny/pyproject.toml` lines 110-114).

## Architectural Analysis

MLflow's RHOAI fork follows a **hybrid application architecture** that bridges the upstream Flask-based server with a modern FastAPI wrapper. The `create_fastapi_app()` function in `fastapi_app.py` creates a FastAPI application with native async routes for performance-critical paths (OpenTelemetry trace ingestion, AI Gateway invocations, job management, MCP server registry) while mounting the entire Flask application at the root path via a custom `_EfficientWSGIMiddleware` that fixes Starlette's O(n²) body buffering. This dual-framework approach preserves 100% API compatibility with upstream MLflow while enabling incremental migration to async endpoints. The FastAPI layer also adds security middleware (CORS blocking, host header validation, security headers) that wraps both native and WSGI-proxied requests.

The **workspace system** is the most architecturally significant downstream addition. It introduces a logical tenant boundary by adding a `workspace` column to 11 workspace-aware ORM models (experiments, registered models, gateway endpoints, secrets, jobs, MCP servers, etc.) and enforcing workspace scoping through request middleware. The workspace store abstraction (`AbstractStore`) supports pluggable providers — the RHOAI deployment uses `kubernetes://` as the workspace store URI, which maps workspace CRUD operations to Kubernetes namespace operations via the `mlflow-kubernetes-plugins` package. Notably, the workspace table uses **no SQL foreign keys** to data tables; referential integrity is enforced at the application layer to support external providers like Kubernetes that manage workspace lifecycle outside the database.

The **security architecture** employs a layered approach: the FastAPI security middleware provides CORS protection and host header validation at the ASGI level; the `--app-name` plugin system provides authentication/authorization at the application level (with `kubernetes-auth` for RHOAI and `basic-auth` for standalone deployments); and gateway secrets are encrypted at rest using AES-GCM with a Key Encryption Key (KEK) derived from a server-admin-provided passphrase. The KEK rotation workflow is atomic and idempotent, with version tracking to support rolling updates. However, the single-process architecture means all workspaces share the same encryption key, and the auth cache (with configurable TTL) can allow stale credentials for a brief window after permission changes.

The **build pipeline** demonstrates exemplary Konflux hermeticity. Three separate requirements files partition dependencies by source: `konflux-aipcc-requirements.txt` (from the AIPCC Python Package Index, hash-pinned), `konflux-pypi-requirements.txt` (from upstream PyPI via Cachi2 prefetch, hash-pinned), and `konflux-build-aipcc-requirements.txt` (build-only deps from AIPCC). RPM dependencies are locked via `rpms.lock.yaml` across all four target architectures. The JavaScript UI build uses Yarn Berry with `--immutable` for deterministic dependency resolution, with Cachi2 providing offline packages when available. This three-layer hermeticity (RPM, Python, JavaScript) ensures reproducible builds across all supported architectures.

The **module federation** pattern for the React UI is a key integration point with RHOAI. The UI build produces both a standalone bundle and a federated module (built with `MLFLOW_API_BASE_URL=/mlflow yarn build:federated`), allowing the RHOAI dashboard to embed MLflow components (experiment views, trace detail panels, compare run pages) as remote modules. Environment flags (`MLFLOW_ENABLE_ASSISTANT=false`, `MLFLOW_ENABLE_AI_GATEWAY=false`) are set at build time in the Dockerfile to gate features that are not yet supported in the RHOAI product context.
