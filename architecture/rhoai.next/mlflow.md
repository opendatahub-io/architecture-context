## Purpose

**Short**: MLflow is the experiment tracking, model registry, and ML lifecycle management service for RHOAI, deployed as a shared multi-tenant server with Kubernetes-native authentication and workspace isolation.

**Detailed**: MLflow provides a centralized platform for managing the end-to-end machine learning lifecycle within Red Hat OpenShift AI. It covers experiment tracking (runs, metrics, parameters), model versioning and registry, artifact storage, LLM tracing and observability, prompt management, and an AI Gateway for proxying LLM provider requests.

In RHOAI, MLflow is deployed as a single shared instance managed by the MLflow Operator. Two Kubernetes-specific extensions differentiate the RHOAI deployment from upstream: a `kubernetes://` workspace provider that maps Kubernetes namespaces to MLflow workspaces, and a `kubernetes-auth` application plugin (provided by the `mlflow-kubernetes-plugins` package) that enforces Kubernetes RBAC via `SelfSubjectAccessReview` for every API request. This architecture lets data science project namespaces function as MLflow workspaces without requiring MLflow to manage its own user or tenant model.

The fork is maintained by rebasing onto upstream MLflow releases (currently v3.15.2), carrying a curated set of downstream patches for Konflux builds, PatternFly UI overrides, federated module support for ODH Dashboard embedding, and ODH-specific feature gating (e.g., AI Gateway and Assistant features are disabled by default in the container image).

## Architectural Analysis

MLflow's RHOAI deployment follows a gateway-authenticated, multi-tenant service pattern. A single Deployment runs the MLflow server with workspaces enabled, the `kubernetes-auth` app plugin active, and `kubernetes://` as the workspace store URI. The server exposes port 5000 and serves both REST APIs and the React-based UI from the same process.

The authentication flow is layered: users reach MLflow through the ODH data science gateway's `/mlflow` HTTPRoute, and SDK clients connect with Kubernetes bearer tokens. The `kubernetes-auth` plugin intercepts each request and performs `SelfSubjectAccessReview` calls against pseudo-resources in the `mlflow.kubeflow.org` API group, meaning authorization is entirely delegated to Kubernetes RBAC rather than maintained in a separate permission system. The `kubernetes` request auth provider on the client side reads tokens from the service account mount or kubeconfig and attaches `Authorization` and optional `X-MLFLOW-WORKSPACE` headers.

The workspace provider treats Kubernetes namespaces as read-only workspace sources. Namespace-scoped `MLflowConfig` custom resources can override artifact storage per workspace, while the shared `MLflow` CR defines defaults for the deployment. Artifact serving can be proxied through MLflow or configured for direct client-to-backend access.

The Helm chart shipped with the repository provides production deployment primitives including TLS termination at the pod level (via uvicorn SSL options), NetworkPolicy with pre-configured egress for DNS, HTTPS, Kubernetes API, PostgreSQL, MySQL, and S3-compatible storage, and optional Prometheus metrics via ServiceMonitor. The chart enforces restrictive security contexts by default: `readOnlyRootFilesystem`, `runAsNonRoot`, `allowPrivilegeEscalation: false`, and `seccompProfile: RuntimeDefault`.

The build pipeline uses a multi-stage Dockerfile: Node.js builds the React UI (with optional federated module output for ODH Dashboard embedding), Python builds the wheel artifacts from the monorepo's three packages (mlflow-tracing, mlflow-skinny, mlflow), and the final stage assembles everything on a UBI 9 minimal image. Dependencies are sourced from the RHOAI AIPCC PyPI index with hash verification and Hermeto/Cachi2 prefetch for supply chain hermeticity.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-workspace RBAC via SelfSubjectAccessReview against `mlflow.kubeflow.org` pseudo-resources | kubernetes-auth plugin (Kubernetes API) | Authorization is based on Kubernetes RBAC; requires proper role assignments per namespace |
| Data storage | Shared database with workspace-scoped queries (workspace column filtering) | Application (SQLAlchemy store with workspace-aware mixin) | Single database; logical isolation only — no physical per-tenant database separation |
| Network traffic | Optional NetworkPolicy via Helm chart | Kubernetes NetworkPolicy | NetworkPolicy disabled by default; must be explicitly enabled |
| Compute & resources | Shared server process; resource limits via Helm values | Kubernetes (pod resources) | No per-tenant compute isolation; all tenants share server capacity |
| Configuration & secrets | Per-namespace MLflowConfig CRs for artifact storage overrides | Kubernetes (workspace provider reads MLflowConfig) | Backend store URI is shared across all workspaces |
| API scoping | Workspace-scoped API queries; workspace header determines query scope | Application (workspace-aware SQLAlchemy store) | Workspace must be present in request headers; missing workspace context could leak cross-tenant data |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL backend store | Workspace column per row | Application query filter (workspace-aware mixin) |
| Artifact storage (S3/files) | Per-workspace artifact root (configurable via MLflowConfig) | Separate artifact paths per workspace; optionally separate buckets |
