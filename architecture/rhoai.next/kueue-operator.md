## Purpose

**Short**: OpenShift operator that deploys and manages the Kueue job queuing system for Kubernetes workload scheduling and resource management.

**Detailed**: The kueue-operator is an OpenShift-native operator built on the openshift/library-go controller framework that installs and manages the upstream Kueue project as an operand on OpenShift clusters. Kueue extends Kubernetes to manage access to resources for batch workloads by providing queue-based admission control — it integrates with the existing Kubernetes scheduler and cluster autoscaler rather than replacing them.

The operator follows a two-tier architecture: a parent operator deployment (`openshift-kueue-operator`) watches for a singleton `Kueue` CR and reconciles the complete operand stack — the kueue controller-manager deployment, CRDs, RBAC, webhook configurations, cert-manager certificates, network policies, and monitoring resources. The operand itself (the kueue controller-manager) handles the core queue scheduling logic, workload admission, preemption, and gang scheduling. The operator dynamically configures which workload frameworks Kueue manages (Jobs, RayJobs, PyTorchJobs, etc.) based on the CR spec, and implements an opt-in namespace model where only namespaces labeled `kueue.openshift.io/managed=true` have webhook enforcement applied.

The component requires cert-manager as a prerequisite and creates cert-manager Issuer and Certificate resources for webhook TLS. It ships with a comprehensive set of network policies following a deny-all-first pattern, and exposes a visibility API server plus Prometheus metrics with mTLS via cert-manager-issued certificates.

## Architectural Analysis

The kueue-operator exhibits a clean separation between the operator layer (lifecycle management) and the operand layer (queue scheduling logic). The operator uses embedded `bindata` assets to deploy the operand — all CRDs, RBAC, webhooks, services, and the operand deployment are stored as YAML in `bindata/assets/kueue-operator/` and applied via the `resourceapply` library from openshift/library-go. This approach gives the operator deterministic control over the exact manifests deployed but requires the bindata to be kept in sync with upstream Kueue releases.

The operator generates the kueue controller-manager's ConfigMap dynamically from the `Kueue` CR spec rather than using static configuration. This translation layer (in `pkg/configmap/`) converts the OpenShift API conventions (CamelCase enum values like `BatchJob`) to upstream Kueue's lowercase format (`batch/job`), allowing the operator to present a curated, API-reviewed surface while maintaining compatibility with upstream. The ConfigMap includes hardcoded feature gate decisions — notably `HierarchicalCohorts: false` and `VisibilityOnDemand: false` (with a comment noting the visibility API server is insecure).

The webhook architecture is notable: rather than deploying all webhooks unconditionally, the operator reads the enabled frameworks from the CR and dynamically filters the webhook configurations to include only relevant webhooks. Combined with the namespace opt-in label (`kueue.openshift.io/managed=true`) as a namespace selector, this provides a scoped, opt-in admission model that avoids interfering with workloads in unmanaged namespaces. All webhooks use `Fail` as their failure policy, meaning kueue unavailability will block managed resource creation.

The network policy design follows defense-in-depth: a deny-all policy applies to all pods with `app.openshift.io/name: kueue`, then selective policies permit only Kubernetes API egress, cluster DNS egress, webhook ingress from kube-apiserver, visibility API ingress, and metrics scraping. The operator and operand pods share the `openshift-kueue-operator` namespace, and a TODO comment in the deny-all policy notes the preference for namespace-level isolation.

A significant architectural dependency is cert-manager — the operator hard-gates on its availability, checking the discovery API for `cert-manager.io/v1/Issuer` before proceeding with reconciliation. The operator creates webhook and metrics TLS certificates via cert-manager CRs and injects CA bundles into webhooks via the `cert-manager.io/inject-ca-from` annotation. The cert-manager dependency is documented in the README and validated at runtime.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC roles per resource type (batch-admin, batch-user, editor, viewer roles) | Kubernetes RBAC | No per-tenant RBAC auto-generation; cluster admins must manually create role bindings for tenant namespaces |
| Data storage | Per-namespace LocalQueues and Workloads; cluster-scoped ClusterQueues | Kubernetes namespace isolation | ClusterQueues are shared across tenants; ResourceFlavors are cluster-scoped, visible to all |
| Network traffic | Deny-all NetworkPolicy + selective allow for API, DNS, webhook, visibility, metrics | Kubernetes NetworkPolicy | Network policies apply to operator/operand pods only, not to tenant workloads |
| Compute & resources | Kueue ResourceQuota-like semantics via ClusterQueue resource limits | Application (Kueue scheduling) | Compute isolation is application-enforced through queue admission, not Kubernetes ResourceQuota |
| Configuration & secrets | Operator ConfigMap and TLS secrets in operator namespace | Kubernetes namespace isolation | No tenant-specific configuration; all tenants share the same Kueue configuration |
| API scoping | Namespace-scoped webhooks via opt-in label; LocalQueues are namespaced | Kubernetes + Application (webhook namespace selector) | Cluster-scoped CRDs (ClusterQueue, ResourceFlavor, Cohort) are visible cluster-wide |
