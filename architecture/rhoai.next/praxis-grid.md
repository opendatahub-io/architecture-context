## Purpose

**Short**: AI Grid Network (AGN) is a distributed control plane that connects AI inference backends across Kubernetes clusters, cloud providers, and third-party APIs into a single routable mesh, orchestrating peer discovery, state propagation, scoring, and routing-overlay generation for Praxis AI gateways.

**Detailed**: AGN operates as a control-plane orchestrator—never in the request path. The grid-operator watches four custom resource definitions (GridNetwork, GridSite, InferenceProvider, AgentToolProvider) to model a mesh of sites, each running a Praxis AI gateway. Sites discover each other via a SWIM gossip protocol (backed by the `foca` library), propagate provider capability and health state using delta CRDTs (LWW registers, OR-Sets, G-Counters), and apply a configurable scoring strategy to rank inference providers. The operator renders scored routing decisions into a versioned ConfigMap (the "routing overlay") that Praxis hot-reloads without restarts.

An overlay-sync sidecar watches the ConfigMap through the Kubernetes API, validates a content-addressed envelope, and atomically writes the overlay to a shared `emptyDir` volume for Praxis to consume. An optional enrollment service provides a REST API for site registration, certificate signing, and identity rotation, backed by PostgreSQL. The fleet-dashboard crate offers an opt-in web UI (Axum + React) for fleet-wide visibility across sites.

The project ships as a Rust workspace of thirteen crates. The operator, enrollment server, and overlay-sync sidecar each build into separate container images. All inter-site and gateway-to-gateway communication is secured with mTLS, with a dual TLS backend: the default `tls-rustls` build uses ring as the cryptographic provider, while a mutually exclusive `fips` feature routes all TLS through the system OpenSSL for FIPS-validated deployments.

## Architectural Analysis

AGN embodies a clean separation between control plane and data plane. The operator is purely an orchestration daemon: it never proxies traffic. All routing decisions are pre-computed into a local overlay file, which means Praxis gateways make zero runtime calls to the operator during request processing. This architecture eliminates the operator as a latency bottleneck and single point of failure in the data path.

The SWIM membership protocol provides decentralized peer discovery without requiring a central registry. Each grid-operator instance maintains a SWIM identity (one per site, enforced by the `Recreate` deployment strategy) and gossips membership state over UDP port 7946. SWIM packets are optionally encrypted with AES-256-GCM using a shared symmetric key sourced either from an environment variable (development) or a Kubernetes Secret referenced by the GridNetwork CRD (production). The key value is explicitly excluded from logs and tracing spans.

State propagation uses delta CRDTs, which are mathematically guaranteed to converge without conflict resolution. This is architecturally significant because it means sites can temporarily partition and will automatically reconcile when connectivity resumes—a requirement for multi-cloud and edge deployments. The CRDT types (LWW registers for provider metadata, OR-Sets for membership, G-Counters for metrics) are purpose-built in the `crdt` crate.

The scoring engine supports three strategies: `noMetrics` (generic default for external APIs), `queueDepth` (shortest normalized queue for llm-d pools), and `kvCachePressure` (most available KV-cache). Strategy selection is per-GridNetwork, not per-provider, which keeps the overlay contract simple. The `signals` subsystem optionally serves and polls per-site metrics over mTLS (port 9091) when `signalTransport: poll` is configured, enabling cross-site metric propagation for informed scoring.

The dual TLS backend (`tls-rustls` vs `fips`) is enforced at compile time via mutually exclusive Cargo features with `compile_error!` guards. The `fips` build routes every cryptographic operation—SHA-256 hashing, TLS handshakes, certificate generation—through the system OpenSSL EVP API rather than pure-Rust implementations. This pattern propagates consistently across operator, enrollment, overlay-sync, and signals-client crates.

The enrollment service provides a certificate authority for the grid mesh. It issues site certificates with DNS SANs and dual EKU (client + server), handles identity rotation, and uses Kubernetes RBAC (TokenReview + SubjectAccessReview) for authorization. PostgreSQL stores enrollment state. The service supports both rustls and OpenSSL TLS backends via the same feature-flag pattern.

The codebase enforces unusually strict coding discipline: `unsafe_code = "forbid"`, `unwrap_used = "deny"`, `expect_used = "deny"`, `panic = "deny"`, `indexing_slicing = "deny"`, and `allow_attributes = "deny"` are all workspace-level lints. This level of strictness, combined with overflow checks in release builds (`overflow-checks = true`), reflects a security-conscious design appropriate for infrastructure operating at the trust boundary between clusters.
