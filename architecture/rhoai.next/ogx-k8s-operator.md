## Purpose

**Short**: Kubernetes operator that deploys and manages OGX (Open GenAI Stack) server instances on OpenShift, including workload lifecycle, networking, storage, autoscaling, and monitoring resources.

**Detailed**: ogx-k8s-operator is a two-binary Go operator built on controller-runtime that manages the full lifecycle of OGX server deployments on Kubernetes and OpenShift. The repository produces two distinct controller images: the root `ogx-k8s-operator` which reconciles user-facing `OGXServer` custom resources into Deployments, Services, PVCs, NetworkPolicies, PodDisruptionBudgets, HPAs, Ingresses, and Prometheus monitoring resources; and the `ogx-module` controller which integrates with the ODH/RHOAI platform operator to manage the root operator's own deployment and lifecycle through the platform-level `OGX` component CR.

The root operator uses an embedded kustomize pipeline with Go-based transformer plugins to render manifests at runtime, supporting distribution image resolution from an embedded registry (`distributions.json`) overridable via operator ConfigMap or per-CR spec. It supports legacy resource migration from the predecessor `LlamaStackDistribution` CRD (the project was renamed from LlamaStack to OGX), including PVC, Service, and Ingress adoption via annotations. The operator also manages CA bundle aggregation, validates OGXServer resources via an admission webhook, and integrates with OpenShift TLS profile configuration for platform-consistent security posture.

## Architectural Analysis

The operator follows a two-tier architecture pattern common in the ODH/RHOAI platform. The outer tier (`ogx-module`) runs inside the platform operator and manages the deployment of the inner tier (`ogx-k8s-operator`) through kustomize overlays with platform-specific parameterization. The inner tier is the workload-facing operator that users interact with through the `OGXServer` CRD.

A notable design choice is the runtime kustomize rendering in the reconciliation loop: rather than applying static manifests, the OGXServer controller builds a kustomize filesystem from embedded base manifests and applies Go-based transformer plugins (name prefix, namespace, field mutation, NetworkPolicy transformation) to generate the final resource set. Resources are applied via server-side apply with field owner `ogx-operator`, which provides clean conflict detection when multiple actors manage the same objects.

The operator's cache is deliberately filtered: ConfigMaps and Secrets require the `ogx.io/watch: "true"` label for cache inclusion, while other resource types are filtered by the `app.kubernetes.io/managed-by: ogx-operator` label. Resources not in cache (like the operator config ConfigMap) are read via a direct API client with 5-minute periodic requeue for eventual consistency. This design limits the operator's memory footprint while maintaining responsiveness for watched resources.

The TLS integration with OpenShift's cluster-wide TLS profile (`config.openshift.io/apiserver`) is comprehensive: the operator reads the profile at startup, configures both the metrics server and webhook server accordingly, and runs a `SecurityProfileWatcher` that triggers graceful shutdown and restart if the cluster TLS profile changes at runtime. This ensures the operator always aligns with the platform's security policy without manual intervention.

PVC lifecycle management is intentionally conservative: PVCs are excluded from owner references to prevent accidental data loss on CR deletion, and the operator uses `Recreate` deployment strategy to avoid ReadWriteOnce multi-attach deadlocks. Legacy resource adoption (from `LlamaStackDistribution`) implements a safety check preventing resource "stealing" — a resource can only be adopted if it is currently owned by the declared source CR.
