## Purpose

**Short**: Kubernetes operator that deploys and manages OGX (Open GenAI Stack) server workloads for generative AI inference, vector I/O, tool runtime, and agentic workflows.

**Detailed**: The OGX K8s Operator manages the lifecycle of OGX server instances on Kubernetes and OpenShift clusters. It provides a single Custom Resource Definition (`OGXServer`) through which users declare their desired AI stack configuration — including inference providers (vLLM, OpenAI, Azure, Bedrock, Vertex AI, Watsonx), vector databases (pgvector, Milvus, Qdrant), tool runtimes (Brave Search, Tavily, MCP), file storage (S3, local filesystem), and agentic response processing.

The operator uses a kustomize-based manifest rendering pipeline with Go-based transformer plugins to produce per-instance Kubernetes resources (Deployments, Services, PVCs, NetworkPolicies, PDBs, HPAs, Ingresses). It supports declarative configuration generation where providers and resources declared in the CRD spec are compiled into an OGX server `config.yaml`, as well as a "bring your own config" mode via ConfigMap references. The operator manages CA certificate bundles (including auto-detection of ODH trusted CA), secret references for provider credentials, and content-addressable immutable ConfigMaps for configuration rollouts.

The repository also contains an `ogx-module` sub-project — a separate controller that implements the ODH/RHOAI platform module contract. The module controller watches a cluster-scoped `OGX` CR (the platform's component enablement resource) and deploys the root OGX operator itself via staged kustomize manifests, enabling the platform operator (rhods-operator / opendatahub-operator) to manage OGX as a pluggable component. The module controller also aggregates health across all OGXServer instances for platform-level status reporting.

## Architectural Analysis

The OGX K8s Operator follows a well-structured Kubernetes operator pattern using controller-runtime with several notable architectural decisions. The operator uses **kustomize-as-a-library** to render per-instance manifests from a shared base (`controllers/manifests/base/`), with Go-based transformer plugins providing programmatic control over resource mutation. This approach avoids template sprawl while allowing fine-grained transformations like dynamic NetworkPolicy ingress rule generation, conditional metrics port injection, and field-level mutations via RFC 6901 JSON Pointers.

The **content-addressable ConfigMap** pattern for generated configuration is particularly well-designed. When the operator generates a `config.yaml` from the declarative spec, it creates an immutable ConfigMap named `{instance}-config-{sha256Hash}`, ensuring that configuration changes always trigger pod rollouts (since the ConfigMap name changes with content). The operator retains the 2 most recent ConfigMaps and protects any ConfigMap still referenced by active Deployments or ReplicaSets, preventing race conditions during rollouts. A similar hash-based rollout trigger mechanism exists for CA bundles and provider secrets — the operator computes hashes of these inputs and stores them as pod annotations, forcing Kubernetes to restart pods when credentials or certificates change.

The **legacy resource adoption** system demonstrates careful migration engineering. The operator can adopt PVCs, Services, and Ingresses from the deprecated LlamaStackDistribution CRD via annotations (`ogx.io/adopt-storage`, `ogx.io/adopt-networking`). This includes scaling down the legacy Deployment to zero, waiting for pod termination, detaching old ownerRefs, relabeling resources, and transferring ownership — all with safety checks to prevent adoption of resources owned by the same CR (which would cause naming conflicts). The adoption flow uses sentinel errors for controlled requeue during pod termination wait states.

The **two-tier deployment model** (ogx-module → root operator → OGXServer instances) is a deliberate architectural choice for the ODH/RHOAI platform. The ogx-module controller is a thin wrapper that implements the platform's component enablement contract: it watches a singleton cluster-scoped `OGX` CR, renders the root operator's manifests via kustomize with platform-appropriate overlays (ODH vs RHOAI namespace, image references from `params.env`), and deploys them using the shared `odh-platform-utilities` deployer. The module also aggregates health across all OGXServer instances, enabling the platform dashboard to show component-level health status. This separation allows the root operator to focus purely on OGXServer lifecycle management while the module handles platform integration concerns.

The operator's **TLS security posture** integrates deeply with OpenShift. On OpenShift clusters, it reads the `config.openshift.io/APIServer` CR to determine the cluster's TLS security profile (minimum TLS version, cipher suites) and applies it to both the webhook server and metrics endpoint. A `SecurityProfileWatcher` monitors for profile changes and triggers a graceful operator restart to reload TLS configuration. On non-OpenShift clusters, it falls back to the Intermediate TLS profile. This ensures the operator's TLS configuration always matches the cluster administrator's security policy.
