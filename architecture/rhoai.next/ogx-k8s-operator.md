## Purpose

**Short**: Kubernetes operator that manages the lifecycle of OGX (formerly Llama Stack) AI distribution servers on OpenShift and Kubernetes clusters.

**Detailed**: The OGX K8s Operator provides a declarative Kubernetes-native interface for deploying and managing OGX distribution servers. It introduces two CRDs: `OGXServer` (ogx.io/v1beta1, namespaced) for individual server instances, and a legacy `LlamaStackDistribution` (llamastack.io/v1alpha1, namespaced) that is being migrated away from. The operator handles the full server lifecycle including distribution image resolution via OCI labels, declarative configuration generation from typed provider specifications (inference, vector IO, tool runtime, files, batches, responses, file processors), secret management, storage backend configuration, and deployment with autoscaling, monitoring, and network policy support.

The repository also contains an `ogx-module` sub-component, which is a platform integration controller that manages the OGX operator as a module within the ODH/RHOAI platform. The ogx-module watches a cluster-scoped `OGX` CRD (components.platform.opendatahub.io/v1alpha1), renders the root OGX operator manifests via kustomize, and deploys them into the applications namespace. This two-tier architecture allows the platform operator (rhods-operator/opendatahub-operator) to manage the OGX operator lifecycle through the standard ODH component pattern.

## Architectural Analysis

The OGX K8s Operator follows a two-tier deployment architecture that cleanly separates platform lifecycle management from application-level concerns. The ogx-module acts as a "meta-operator" — it watches a single cluster-scoped OGX CR and renders the root OGX operator's kustomize manifests into the applications namespace. This pattern is standard across ODH/RHOAI component modules and allows the platform operator to enable/disable OGX without knowing its internal details. The root operator then handles the actual OGXServer lifecycle, creating per-instance resources (Deployment, Service, PVC, NetworkPolicy, HPA, PDB, ServiceMonitor, PrometheusRule) in the user's namespace.

The configuration generation pipeline is architecturally notable. Rather than requiring users to write raw config YAML, the operator accepts typed provider specifications in the CRD spec (e.g., `spec.providers.inference.remote.vllm[0]`) and expands them into a complete `config.yaml`. The pipeline supports seven API types (inference, vector_io, tool_runtime, files, batches, responses, file_processors) with 20+ concrete provider implementations. Base config is resolved from OCI image labels embedded in the distribution container, merged with user-provided provider/resource/storage configuration, and written to an immutable content-hashed ConfigMap. This design enables distribution images to ship default configurations while letting users override specific providers declaratively. The `configgen` CLI tool allows testing this pipeline outside Kubernetes.

Secret management follows a provider-aware pattern. Each provider type defines which fields can reference Kubernetes Secrets (e.g., API keys, connection strings). The operator collects all secret references across all configured providers, generates environment variable names following the `OGX_<PROVIDER_ID>_<FIELD>` convention, validates for naming collisions, and injects them into the Deployment's container spec. The config.yaml references these via `${env.<NAME>}` syntax, which the OGX server resolves at runtime.

The legacy migration system handles the rename from LlamaStackDistribution to OGXServer. Users annotate an OGXServer CR with `ogx.io/adopt-storage` and/or `ogx.io/adopt-networking` to transfer PVCs and Services from a legacy LLSD instance. The adoption flow scales the legacy Deployment to zero, waits for pod termination, detaches the PVC from the old controller, and updates Service selectors. PVCs are deliberately not given an ownerReference to the new OGXServer CR, preventing data loss if the CR is deleted. This design reflects careful consideration of stateful workload migration.

Network policy enforcement follows a sensible default: same-namespace and operator-namespace pods can reach the OGX server, with automatic OpenShift router and monitoring namespace integration. The NetworkPolicyTransformer kustomize plugin handles policy construction, adding monitoring ingress rules only when a metrics port is configured. Users can override with custom ingress/egress rules or disable NetworkPolicy entirely per instance. The feature flag system (`EnableNetworkPolicy`) provides a global toggle, though currently this is the only feature flag defined.
