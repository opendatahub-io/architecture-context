## Purpose

**Short**: llm-d is a Kubernetes-native distributed inference serving stack that provides well-lit-path deployment guides, container images, and Kustomize recipes for serving large language models at scale with intelligent routing, KV-cache management, and disaggregated serving across multiple hardware accelerators.

**Detailed**: llm-d is a CNCF sandbox project founded by Red Hat, Google Cloud, IBM Research, CoreWeave, and NVIDIA. It is not a single service or operator but rather an integration platform — a coordination repository that assembles multiple independently-developed components (llm-d-router, llm-d-kv-cache, llm-d-routing-sidecar, llm-d-async, llm-d-batch-gateway, llm-d-latency-predictor, llm-d-workload-variant-autoscaler) into tested, benchmarked deployment topologies on Kubernetes. The repository's primary deliverables are well-lit-path guides providing Kustomize overlays and Helm values for deploying optimized inference stacks, container images (vLLM builds for CPU, Intel XPU, AMD ROCm, plus RDMA tooling), and reusable recipes for model servers, routers, gateways, observability, and autoscaling.

The architecture centers on three core concepts: the llm-d Router (an Endpoint Picker / EPP + L7 proxy implementing the Gateway API Inference Extension for LLM-aware load balancing), the InferencePool (an API grouping model server pods serving the same base model), and Model Servers (vLLM or SGLang inference engines). These compose into advanced patterns including prefix-cache-aware routing, prefill/decode disaggregation, wide expert-parallelism, tiered KV-cache offloading, predicted-latency scheduling, flow control for multi-tenancy, and workload-variant autoscaling. The repository provides validated configurations for NVIDIA GPU, AMD GPU, Intel XPU, Google TPU, Rebellions NPU, Iluvatar GPU, MetaX GPU, and CPU-only deployments.

## Architectural Analysis

llm-d's architecture is distinctive because the main repository contains no Go or Python library source code — it is a pure coordination and deployment layer. The actual inference logic lives in upstream vLLM, while routing, caching, and scheduling logic live in sibling repositories (llm-d-router, llm-d-kv-cache, etc.). This design reflects principle #4 ("we respect our upstreams") and principle #6 ("vLLM-first but not vLLM-only"), keeping the core repo focused on composition rather than implementation.

The deployment model uses a layered Kustomize architecture: shared base manifests under `guides/recipes/` define skeleton Deployments, ServiceAccounts, and Gateway resources. Guide-specific overlays under `guides/<guide-name>/modelserver/<accelerator>/<engine>/` patch in accelerator-specific resource requests, model arguments, and image references. Image pinning is handled through Kustomize components under `guides/recipes/modelserver/components/images/`, centralizing version management so a single edit propagates across all guides. This three-layer composition (recipes → guide overlays → accelerator patches) means adding a new accelerator requires only a new overlay directory, not duplicating entire manifests.

The router is deployed via Helm charts (`llm-d-router-standalone` and `llm-d-router-gateway` from `oci://ghcr.io/llm-d/charts/`), while model servers are deployed via Kustomize. This split reflects the router's richer configuration surface (plugin configs, proxy settings, tracing) versus the model server's per-accelerator patching needs. Gateway API (`gateway.networking.k8s.io`) is the ingress mechanism, with recipes for Envoy, Istio, kgateway, Envoy AI Gateway, and Agent Gateway.

The container images implement a multi-accelerator strategy: the CPU Dockerfile builds vLLM entirely from source on Ubuntu 22.04 with UCX and NIXL; the ROCm Dockerfile layers UCX, UCCL, NIXL, and MORI onto the upstream vLLM ROCm image; the XPU Dockerfile is a thin pass-through adding only Intel oneAPI compiler and LMCache; and the RDMA tools image is a standalone diagnostic utility on UBI9. All images converge on the same entrypoint (`python -m vllm.entrypoints.openai.api_server`) and expose the same OpenAI-compatible API on port 8000.

A notable design risk for RHOAI productization is the absence of any Konflux-style downstream Dockerfiles. The upstream Dockerfiles build from Ubuntu 22.04 and upstream NVIDIA/vLLM base images with no UBI base, no FIPS enforcement, no RPM lock files, and no Hermeto prefetch. This is expected for a CNCF upstream project but means RHOAI productization would require significant downstream hardening including rebasing onto UBI/AIPCC images, adding FIPS build flags, creating lock files at all layers, and configuring Konflux pipelines.

The security posture is minimalist by design — vLLM endpoints are unauthenticated, relying on Gateway-level enforcement. No NetworkPolicy manifests are included in guides. The threat model document is a placeholder. For production RHOAI deployments, kube-rbac-proxy sidecars, TLS for internal traffic, and NetworkPolicies would need to be added.
