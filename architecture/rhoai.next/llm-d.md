## Purpose

**Short**: llm-d is a Kubernetes-native distributed LLM inference serving stack that provides container image builds, deployment guides, and reusable kustomize recipes for achieving state-of-the-art inference performance across multiple hardware accelerators.

**Detailed**: llm-d is a high-performance distributed inference serving stack optimized for production deployments on Kubernetes. It provides intelligent routing, advanced KV-cache management, prefill/decode disaggregation, and wide expert-parallelism for large Mixture-of-Experts models. The project is a CNCF sandbox project founded by Red Hat, Google Cloud, IBM Research, CoreWeave, and NVIDIA.

This repository serves as the project's central hub, containing: (1) Dockerfiles and build scripts for producing optimized model server container images across five accelerator platforms (CUDA, ROCm, XPU, CPU, RDMA-tools), (2) well-lit path deployment guides with tested, benchmarked kustomize manifests and Helm values for common inference topologies, and (3) reusable recipe components (gateway configurations, model server bases, image references, monitoring) that guides compose via kustomize overlays.

The repository itself does not contain Go or Python source code for the runtime components (router, EPP, sidecar, autoscaler) -- those live in sibling repositories (`llm-d-router`, `llm-d-kv-cache`, `llm-d-routing-sidecar`, etc.). This repo's role is to build the vLLM-based inference container images, define the deployment recipes, and serve as the integration point where all components are composed into deployable topologies.

## AIPCC Ecosystems Use

_No Konflux Dockerfiles exist in this repository. The images are built via standard Dockerfiles (`docker/Dockerfile.cuda`, `docker/Dockerfile.cpu`, etc.) using GitHub Actions CI, not Konflux. However, the Dockerfiles DO install Python packages extensively via `uv pip install`._

_This component does NOT use AIPCC Ecosystems base images. The CUDA image uses `nvcr.io/nvidia/cuda:13.0.2-{devel,runtime}-ubi9` as its base. The CPU image uses `ubuntu:22.04`. The ROCm image uses `vllm/vllm-openai-rocm:v0.23.0`. The XPU image uses a prebuilt vLLM XPU CI image from AWS ECR._

_As an upstream CNCF project, llm-d is not currently subject to Red Hat's AIPCC Ecosystems requirements. If/when llm-d images are consumed downstream in RHOAI, the downstream build system would need to rebase onto AIPCC base images for compliance._

## Architectural Analysis

The llm-d repository occupies an unusual architectural position: it is neither a traditional application source repository nor a pure deployment manifest collection. Instead, it functions as an integration layer that sits between the component source repositories (llm-d-router, vLLM, UCX, etc.) and production deployments. This dual role -- container image builder AND deployment recipe provider -- creates a clear separation of concerns but also means the repository's "architecture" is best understood through two lenses.

**Container Image Architecture**: The Dockerfile.cuda is the most architecturally significant artifact. It implements a sophisticated multi-stage build that compiles 10+ components from source with carefully orchestrated dependency chains (GDRCopy → UCX → NVSHMEM → DeepEP, and separately NIXL → vLLM). The build supports three installation modes for vLLM (prebuilt wheel, precompiled binaries + source, full source compilation), two OS bases (UBI9 and Ubuntu 24.04), two CPU architectures (amd64 and arm64), and a GB200-specific build target. The `docker/common-versions` file serves as the single source of truth for all component versions, and the `docker/scripts/` directory contains well-structured, testable shell scripts that handle the actual compilation. The use of UV as the Python package manager (rather than pip) across all images is a deliberate choice for faster, more deterministic builds. Build optimization is achieved through sccache (AWS S3-backed compilation cache), Docker layer caching, and the precompiled wheel strategy that avoids rebuilding CUDA kernels on every vLLM commit.

**Deployment Recipe Architecture**: The `guides/` directory implements a composable architecture using kustomize overlays and Helm charts. The key design pattern is a three-layer composition: (1) `guides/recipes/` provides reusable bases (gateway configs, model server deployments, image components), (2) each guide (`optimized-baseline/`, `pd-disaggregation/`, etc.) provides guide-specific overlays that reference the recipes, and (3) hardware-specific overlays (`gpu/`, `amd/`, `xpu/`, `tpu/`, `cpu/`) select accelerator-appropriate configurations. This composability means adding a new accelerator requires only a new overlay directory with patches, not duplicating the entire deployment manifest. The routing architecture consistently uses the Envoy + EPP (ext_proc) pattern across all guides, with the EPP's routing plugins being the primary differentiation point (prefix-cache-affinity for baseline, token-load-scorer for disaggregation, expert-parallelism-aware for wide EP).

**Security Observations**: The repository has minimal security hardening in its default deployment guides. The vLLM API is exposed without authentication, relying entirely on network isolation (internal ClusterIP services behind Envoy). No NetworkPolicy manifests are included. No TLS is configured between components. The container images run as a non-root user (UID 2000) with group 0 permissions for OpenShift compatibility. For RHOAI consumption, the security posture would need to be significantly hardened -- adding kube-rbac-proxy sidecars, TLS for internal traffic, NetworkPolicies, and potentially rebasing onto AIPCC Ecosystems images.

**CI/CD Integration**: The GitHub Actions CI pipeline implements a multi-gate approach: PR approval is required before image builds are triggered (protecting against fork-based supply chain attacks), and all images are scanned with Trivy for CRITICAL/HIGH/MEDIUM vulnerabilities before merge. The release process produces images tagged by git tag with a verify step that confirms all expected platform variants were successfully built. The kustomize dry-run workflow validates that guide manifests remain syntactically correct against a KinD cluster.
