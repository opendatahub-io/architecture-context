## Purpose

**Short**: Models as a Service (MaaS) is a Kubernetes-native platform that provides centralized inference model endpoint management with multi-tenant isolation, API key authentication, subscription-based access control, and policy-driven authorization through Gateway API and Kuadrant/Authorino.

**Detailed**: MaaS delivers a self-service model consumption layer for Red Hat OpenShift AI. Platform administrators define AI tenants via the AITenant CRD, which bootstraps dedicated namespaces, Gateway API routing, Kuadrant AuthPolicy enforcement, and RBAC for each tenant. Tenant users subscribe to models through MaaSSubscription resources and access them via OpenAI-compatible API endpoints, authenticated by either MaaS-issued API keys or OpenShift bearer tokens.

The system comprises three deployable components: the **maas-controller** (a controller-runtime operator that reconciles tenant lifecycle, model references, subscriptions, auth policies, and external model providers), the **maas-api** (a Gin-based REST service for API key management, model catalog, and subscription queries backed by PostgreSQL), and **maas-discovery** (a lightweight tenant discovery service that exposes tenant metadata through the platform gateway). The controller embeds kustomize manifests and renders per-tenant deployments of maas-api at runtime, creating a per-tenant instance model for the API service while maintaining a single controller deployment.

The architecture integrates deeply with Gateway API (HTTPRoute-based routing through a shared or per-tenant gateway), Kuadrant/Authorino (AuthPolicy for multi-method authentication and authorization), KServe (LLMInferenceService watches for model serving state), and Istio networking primitives (DestinationRules, EnvoyFilters, ServiceEntries) for traffic management and TLS enforcement.

## Architectural Analysis

MaaS follows a controller-driven reconciliation pattern where a single maas-controller operator manages the full tenant lifecycle across the cluster. The architecture separates concerns into three distinct Go modules with independent dependency trees: the controller handles all Kubernetes resource orchestration, the API service provides the HTTP interface for end-user operations, and the discovery service supports multi-tenant routing.

A key architectural decision is the **per-tenant maas-api deployment model**: when the controller reconciles an AITenant, it renders and deploys a dedicated maas-api instance into the tenant's infrastructure namespace using embedded kustomize manifests (the controller Dockerfile COPYs `maas-api/deploy` and `deployment/base/maas-api` into the image). This provides strong tenant isolation at the process level while centralizing lifecycle management through the single controller.

The authentication architecture is layered and worth noting for its complexity. External requests flow through Gateway API to the Istio-managed gateway proxy, where Kuadrant's Authorino evaluates authentication. Two authentication methods are supported with priority-based selection: MaaS API keys (`sk-oai-*` prefix, validated via HTTP callback to maas-api) and OpenShift tokens (validated via Kubernetes TokenReview). Authorino strips the original Authorization header and injects identity headers (`X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription`) before forwarding to backends, preventing credential exfiltration to model endpoints. The controller dynamically creates Kuadrant AuthPolicy resources per tenant that enforce this policy stack.

The controller's RBAC surface is broad, spanning 30+ API groups including core Kubernetes resources, MaaS CRDs, Gateway API, Kuadrant policies, Istio networking, KServe serving, cert-manager certificates, OpenTelemetry collectors, and monitoring resources. This breadth reflects the controller's role as the sole orchestrator for the entire MaaS stack. The supplemental ClusterRole for maas-api is narrower, restricted to read-only access for its CRDs and a named-resource restriction on the `maas-db-config` secret.

A notable gap exists in the TLS overlay: the DestinationRule for maas-api backend TLS uses `insecureSkipVerify: true` because the managed gateway proxy does not currently mount the OpenShift service-ca bundle needed to validate maas-api's serving certificate (tracked as RHOAIENG-61070). Traffic is encrypted but not certificate-validated on this hop.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant Kuadrant AuthPolicy with API key and OpenShift token auth; per-tenant RBAC roles | Kuadrant/Authorino + Kubernetes RBAC | None detected; AuthPolicy denies identity header injection from clients |
| Data storage | Per-tenant maas-api instance with shared PostgreSQL; tenant scoping via application query filter | Application (maas-api) | Shared database; isolation relies on application-level query filtering, not database-level separation |
| Network traffic | Per-tenant NetworkPolicies (egress, authorino, gateway, deployment-ns); controller manages NetworkPolicy lifecycle | Kubernetes NetworkPolicy | Default-deny enforced at gateway level (gateway-default-deny.yaml) |
| Compute & resources | Per-tenant Deployment with resource limits; HorizontalPodAutoscaler management | Kubernetes (resource limits) | No per-tenant ResourceQuota detected; tenants share cluster compute pool |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; controller creates per-tenant config | Kubernetes namespace isolation | Database connection secret (maas-db-config) is per-tenant (named per resourceNames restriction) |
| API scoping | Namespace-scoped CRD watches; per-tenant maas-api instance serves only its tenant's data | Kubernetes (namespace scoping) + Application | Controller watches cluster-wide but reconciles per-tenant |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | Application-level query filter | Per-tenant maas-api instances with separate connections; no schema-per-tenant |
| Gateway (Istio/Envoy) | Per-tenant HTTPRoute and AuthPolicy | Kuadrant AuthPolicy enforces authentication per route; Authorino injects tenant identity headers |
| maas-controller | Cluster-scoped single instance | Controller reconciles all tenants; namespace-scoped watches per CRD |
