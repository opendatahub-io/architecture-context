## Purpose

**Short**: Models as a Service (MaaS) is a multi-tenant platform for managing access to LLM inference endpoints with authentication, authorization, API key management, subscription-based rate limiting, and policy enforcement via Gateway API and Kuadrant.

**Detailed**: MaaS provides a comprehensive platform for offering large language model (LLM) inference as a managed service on OpenShift AI. It consists of two primary components: **maas-controller**, a Kubernetes operator that manages the lifecycle of tenants, model references, subscriptions, and authentication/authorization policies; and **maas-api**, a Go REST API service that handles API key management, model discovery, subscription selection, and user authentication.

The platform integrates deeply with Gateway API for traffic routing, Kuadrant/Authorino for authentication and authorization policy enforcement, Limitador for token-based rate limiting, KServe for model serving, and Istio for service mesh networking. MaaS implements a multi-tenant architecture where each tenant (AITenant) gets its own Gateway, namespace, and isolated set of subscriptions and policies.

The controller dynamically creates and manages Kuadrant AuthPolicies, TokenRateLimitPolicies, HTTPRoutes, EnvoyFilters, ServiceEntries, DestinationRules, NetworkPolicies, and observability resources (PodMonitors, ServiceMonitors, OpenTelemetry Collectors, Perses dashboards). It supports both internal KServe-served models (via LLMInferenceService) and external provider models (via ExternalModel with credential injection). A payload processing pipeline (ext_proc) handles body-based routing, API translation, credential injection, and usage enforcement at the Envoy level.

## Architecture Components

| Component | Type | Purpose |
|-----------|------|---------|
| maas-controller | Go Operator (controller-runtime) | Manages CRDs for tenants, model references, subscriptions, auth policies; deploys maas-api, networking, and observability resources via kustomize-based tenant reconciliation |
| maas-api | Go Service (Gin HTTP) | REST API for model listing, API key CRUD, subscription management, tenant info; validates tokens via Kubernetes TokenReview/SAR; stores API key hashes in PostgreSQL |
| payload-processing | External gRPC Service (ext_proc) | Envoy external processing filter for body-based model routing, API translation, credential injection, stream usage enforcement, and MaaS header guarding |

**Dockerfile**: `maas-controller/Dockerfile.konflux`
**Intent**: Primary operator component. Deployed as a single-replica Deployment in the platform namespace (e.g., `opendatahub`). ### maas-api

**Dockerfile**: `maas-api/Dockerfile.konflux`
**Intent**: User-facing REST API service deployed per-tenant by the maas-controller's Tenant reconciler into the infrastructure namespace. Provides OpenAI-compatible model listing, API key lifecycle management, subscription selection, and tenant discovery. Runs as a Deployment with a companion CronJob for expired key cleanup.
**Image**: `odh-maas-api-rhel9`
**Language**: Go (Gin framework)
**Port**: 8080/TCP (HTTP) or 8443/TCP (HTTPS), 9090/TCP (metrics)

## Architectural Analysis

The MaaS platform implements a sophisticated multi-tenant model serving gateway built on the Kubernetes Gateway API and Kuadrant policy engine. The architecture follows a clear separation of concerns: the **maas-controller** handles all declarative infrastructure management, while **maas-api** provides the user-facing REST interface. This separation allows the controller to manage the complete lifecycle of gateway infrastructure (HTTPRoutes, AuthPolicies, TokenRateLimitPolicies, EnvoyFilters) without the API service needing to understand policy mechanics.

The **tenant reconciliation pipeline** is particularly noteworthy. The controller renders deployment manifests via an embedded kustomize engine, applying overlays and parameter substitution at runtime. This allows a single controller binary to deploy all per-tenant infrastructure — maas-api Deployments, Services, CronJobs, NetworkPolicies, and monitoring resources — using the same kustomize bases that are also available for standalone deployment. The `INFRA_NAMESPACE=AUTO` pattern enables namespace separation where maas-api runs in a dedicated infrastructure namespace (e.g., `odh-ai-gateway-infra`), isolating it from the controller namespace.

The **Envoy ext_proc pipeline** is a critical architectural decision. Two payload processing instances — `ipp-pre` (before auth) and `ipp` (after auth) — are injected into the Gateway's Envoy filter chain via EnvoyFilter CRs. The pre-auth stage extracts the model name from the request body and sets the `X-Gateway-Model-Name` header for Authorino routing. The post-auth stage handles API translation (e.g., OpenAI ↔ native format), credential injection (replacing user credentials with model-specific API keys from Secrets), stream usage enforcement, and MaaS header guarding. This two-stage design is essential because auth must validate the user before credentials can be injected, but model routing must be resolved before auth can evaluate per-model policies.

The **governance model** (MaaSSubscription + MaaSAuthPolicy pairing) implements defense-in-depth access control. A model is only accessible when it has both an AuthPolicy (who can access it) and a Subscription (rate limits for access). The MaaSModelRef status tracks both `GovernanceAttached` and `RuntimeReady` conditions independently, allowing operators to distinguish between governance gaps and runtime failures. The gateway-level default deny TokenRateLimitPolicy ensures that any request reaching a model path without a per-route TRLP gets 0 tokens (429), preventing bypass via unconfigured routes.

The **API key security model** uses SHA-256 hashing with per-key salt (the key_id) and a null-byte delimiter to prevent length-ambiguity attacks. Keys are validated via an Authorino HTTP callback to maas-api's internal endpoint, which is protected by NetworkPolicy to allow only Authorino pods. The debounced last_used_at update pattern (using CAS for thread safety) is a pragmatic optimization that reduces PostgreSQL write contention while maintaining audit accuracy within a configurable window (default 60s).

A notable **risk area** is the DestinationRule for payload-processing which sets `insecureSkipVerify: true` for TLS origination within the mesh. While this is common for mesh-internal traffic where mTLS provides identity verification, it means the payload-processing service does not validate the server certificate of its upstream target, relying entirely on Istio mTLS for security.
