## Purpose

**Short**: Models-as-a-Service (MaaS) is a Kubernetes-native platform for exposing LLM inference endpoints with integrated policy management, API key authentication, subscription-based access control, and per-model token rate limiting.

**Detailed**: MaaS provides a comprehensive control plane for managing access to large language models deployed via KServe or external providers (OpenAI, Anthropic, etc.). The platform consists of two primary components: a **maas-controller** (Kubernetes operator) that reconciles custom resources defining tenants, model references, subscriptions, and auth policies into Gateway API HTTPRoutes and Kuadrant AuthPolicies/TokenRateLimitPolicies; and a **maas-api** (Go HTTP service) that handles API key lifecycle management, subscription selection for Authorino, model discovery, and tenant metadata.

The architecture follows a multi-tenant model where each AITenant gets a dedicated Gateway API Gateway, its own namespace, and isolated MaaS resources. Authentication is enforced at the gateway level via Kuadrant/Authorino with support for OpenShift tokens, external OIDC, and MaaS-issued API keys (sk-oai-* format). Token rate limiting is applied per-model per-subscription via Kuadrant TokenRateLimitPolicies. A payload processing service (EnvoyFilter-based ext_proc) handles request/response body inspection before and after authentication. The system integrates deeply with the OpenShift/Kubernetes ecosystem, using Gateway API for ingress, Istio EnvoyFilters for traffic shaping, and Prometheus/OpenTelemetry for observability.

## Architectural Analysis

The Models-as-a-Service architecture represents a policy-driven API gateway pattern built on top of Gateway API, Kuadrant, and KServe. Rather than implementing authentication, rate limiting, or routing directly, MaaS composes these capabilities from platform-level primitives: Kuadrant AuthPolicies handle authentication at the Envoy gateway, TokenRateLimitPolicies enforce per-model token budgets, and Gateway API HTTPRoutes provide per-model routing. The maas-controller acts as a "policy compiler" -- translating high-level MaaS CRDs (AITenant, MaaSModelRef, MaaSSubscription, MaaSAuthPolicy) into the lower-level Kuadrant and Gateway API resources that actually enforce the policies.

A distinctive design choice is the **governance pairing** model: a MaaSModelRef only becomes Ready when BOTH a MaaSSubscription AND a MaaSAuthPolicy reference it. This prevents models from being exposed without explicit access control and rate limiting. The controller enforces this by tracking GovernanceAttached and RuntimeReady conditions independently, and the model is only routable when both are satisfied. This fail-closed approach means accidental exposure of unprotected models is structurally impossible -- a model without governance is never routable.

The **multi-tenant isolation** model uses a combination of Kubernetes-level and application-level boundaries. Each AITenant gets its own namespace, dedicated Gateway, and per-tenant maas-api instance. However, the PostgreSQL database is shared across tenants with row-level tenant filtering (mandatory `WHERE tenant = $X` in all queries). This is a pragmatic choice that simplifies operations but creates a trust boundary at the application level -- a SQL injection or query construction bug could theoretically leak cross-tenant API key data. The gateway-claim ConfigMap mechanism (SHA256 hash-based) prevents concurrent AITenants from claiming the same Gateway, which is an elegant lock-free approach.

The **payload processing pipeline** uses Envoy External Processing (ext_proc) in a two-stage design: `ipp-pre` runs before authentication to extract the model name from request headers or body (enabling body-based routing), while `ipp` runs after authentication to process request/response bodies with full identity context. The EnvoyFilter configuration explicitly disables ext_proc on non-inference routes (maas-api management endpoints), preventing unnecessary processing overhead. The dual-anchor pattern in the EnvoyFilter (matching both WasmPlugin and wasm filter names) enables compatibility with both ODH/community Kuadrant and RHCL 1.4, which inject auth via different Envoy filter types.

The **API key system** follows security best practices: keys use a show-once pattern (plaintext returned only at creation), SHA-256 hashing with a null-byte delimiter between key_id and secret prevents length extension attacks, and last-used-at updates are debounced with CAS (compare-and-swap) to prevent row-lock storms under high concurrency. The key format (`sk-oai-*`) is OpenAI-compatible, allowing existing AI/ML tooling to work without modification.
