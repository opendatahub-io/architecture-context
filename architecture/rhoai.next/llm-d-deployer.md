## Purpose

**Short**: Deprecated monolithic Helm chart for deploying the llm-d distributed LLM inference framework on Kubernetes.

**Detailed**: llm-d-deployer provides a Helm chart that packages and deploys the entire llm-d ecosystem for high-performance distributed LLM inference. The chart installs a ModelService controller (which reconciles `ModelService` CRDs into prefill/decode vLLM deployments, endpoint picker instances, and Gateway API routing resources), a Kubernetes Gateway for ingress, Redis for KV-cache lookup coordination, and optional observability scaffolding via Grafana and Prometheus ServiceMonitors.

The chart follows a "preset" pattern where ConfigMaps define deployment templates for different configurations (basic GPU, GPU with NIXL, GPU with NIXL and Redis lookup, simulator). The ModelService controller reads these presets and stamps out the underlying Kubernetes resources (Deployments, Services, InferencePools, InferenceModels, HTTPRoutes) on behalf of the user. This allows a single `ModelService` CR to declare a model, and the controller materializes the entire prefill/decode inference stack.

As of 2025-07-25, this repository is **deprecated** in favor of [`llm-d-infra`](https://github.com/llm-d-incubation/llm-d-infra), which takes a more modular Helmfile-based approach. The charts are no longer updated, and new deployments should use `llm-d-infra`. The repository is preserved for historical reference and for users who wish to continue using the monolithic install pattern.

## Architectural Analysis

The llm-d-deployer chart is architecturally significant as the original "single-command" deployment surface for the llm-d ecosystem. Its design reveals several deliberate choices about how distributed LLM inference is orchestrated on Kubernetes.

The chart's central abstraction is the **preset ConfigMap pattern**: rather than embedding deployment specifications directly into the CRD or controller logic, deployment templates for prefill nodes, decode nodes, endpoint pickers, and services are stored as YAML strings inside ConfigMaps. The ModelService controller reads these templates at reconciliation time, interpolates model-specific values (model name, HF token, etc.), and creates the concrete Kubernetes resources. This decouples the controller's reconciliation logic from the specifics of vLLM configuration, NIXL connectivity, or LMCache setup. However, it also means the "real" deployment specification lives in templated-YAML-inside-templated-YAML (Helm renders ConfigMaps that contain Go-template strings for the controller), creating a double-templating layer that complicates debugging and auditing.

The **prefill/decode disaggregated architecture** is central to llm-d's design. Each model deployment can independently scale prefill and decode replicas, with NIXL providing direct GPU-to-GPU KV-cache transfer and LMCache enabling distributed cache lookup via Redis. The routing proxy sidecar intercepts traffic on decode nodes to redirect port 8000 to vLLM on port 8001 while managing NIXL connectivity on port 5557. This sidecar-based routing pattern is specific to disaggregated inference and would not be found in standard vLLM deployments.

The chart's **Gateway API integration** supports multiple backends (Istio, kGateway, GKE L7) through the `gatewayClassName` value. The endpoint picker (EPP) implements the Gateway API Inference Extension (GIE) `ExternalProcessor` gRPC interface, allowing the gateway to make intelligent routing decisions based on prefix-awareness, load-awareness, KV-cache state, and session affinity. The EPP exposes gRPC on ports 9002/9003 and metrics on 9090.

The deprecation in favor of `llm-d-infra` reflects a recognized limitation of the monolithic chart approach: the tight coupling between all components made it difficult for users to adopt individual pieces (e.g., using upstream GIE charts without the full llm-d stack) or to compose their own deployment topologies.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC ClusterRoles with admin/editor/viewer tiers | Kubernetes | Controller runs with cluster-wide permissions; no per-namespace restriction on which ModelService CRs it processes |
| Data storage | Per-namespace PVCs for model storage; per-namespace Secrets for HF tokens | Kubernetes | Redis is shared across all ModelService instances in the release namespace; no per-tenant data isolation in cache |
| Network traffic | No NetworkPolicy deployed by chart (redis.networkPolicy.enabled=false) | None | No network segmentation between tenants; relies on external network policy |
| Compute & resources | GPU resource requests on vLLM pods; tolerations for GPU nodes | Kubernetes scheduler | No ResourceQuota or LimitRange deployed by chart |
| Configuration & secrets | Per-namespace HF token secrets | Kubernetes | EPP default env vars are global (shared across all ModelService instances in the release) |
| API scoping | Controller has cluster-wide watches on ModelService CRs | Kubernetes | Single controller instance processes CRs across all namespaces |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Redis (LMCache lookup) | None — single instance per chart release | No tenant isolation; all vLLM instances share the same Redis for KV-cache lookup |
| Gateway | None — single gateway per chart release | All InferencePools route through the same gateway instance |
| EPP | Per InferencePool | EPP instances are created per ModelService but share the same ClusterRole |
