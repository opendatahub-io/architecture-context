## Purpose

**Short**: Kubernetes operator that manages the lifecycle of ModelMesh Serving custom resources and orchestrates multi-model inference serving infrastructure.

**Detailed**: ModelMesh Serving is a controller-runtime based Go operator that manages the deployment, scaling, and lifecycle of model serving infrastructure built on top of the ModelMesh model placement and routing layer. It watches for Predictor, ServingRuntime, ClusterServingRuntime, and InferenceService custom resources and reconciles them into Kubernetes Deployments, Services, and configuration resources.

The controller creates runtime Deployments from templates, injecting ModelMesh sidecar containers, REST proxy containers, and storage helper (puller) containers alongside the user-specified model server containers (Triton, MLServer, OVMS, TorchServe, or custom runtimes). It integrates with an etcd cluster for model registry and event coordination, and communicates with the ModelMesh gRPC API for virtual model (VModel) lifecycle management including model registration, loading, and status tracking.

The operator supports both cluster-scoped and namespace-scoped deployment modes, implements scale-to-zero functionality with configurable grace periods, manages HPA-based autoscaling, and handles TLS certificate configuration for secure gRPC communication. It serves as the control plane for the ModelMesh data plane, translating declarative CRD specifications into running inference infrastructure.

## Architectural Analysis

ModelMesh Serving implements a sophisticated multi-model serving architecture that separates the control plane (this controller) from the data plane (ModelMesh containers). The controller acts as a translation layer between Kubernetes-native declarative APIs (CRDs) and the ModelMesh imperative gRPC API. When a user creates a Predictor CR, the controller does not directly manage model loading — instead, it calls `SetVModel` on the ModelMesh gRPC service, which handles model placement, replication, and routing across the cluster. This decoupling allows ModelMesh to make intelligent placement decisions based on available memory and model usage patterns without the controller needing to understand the serving topology.

The deployment template pattern (`config/internal/base/deployment.yaml.tmpl`) is noteworthy: the controller dynamically generates Deployment manifests at runtime using Go templates, injecting the ModelMesh (`mm`) container, an optional REST proxy container, an oauth-proxy sidecar for authentication, and a storage helper/puller container alongside each user-specified model server container. This means each runtime Deployment is a multi-container pod with 4-5 containers, where inter-container communication happens over localhost (Unix domain sockets for gRPC, loopback for HTTP). The controller manages the full lifecycle of these Deployments, including rolling updates when configuration changes and scale-to-zero when no models are deployed to a runtime.

The etcd dependency is a defining architectural characteristic that distinguishes ModelMesh from KServe's single-model approach. While KServe uses Kubernetes-native CRDs for all state, ModelMesh uses etcd as a high-performance coordination layer for model registry state and cross-pod event propagation. The controller watches etcd for model lifecycle events (via `ModelEventStream`) and reconciles Predictor status accordingly. This means the system has two sources of truth — Kubernetes CRDs for declarative intent and etcd for actual model placement state — which the controller continuously reconciles. The etcd connection supports TLS and authentication, and the secret configuration (`model-serving-etcd`) is propagated to runtime pods as a mounted Secret.

The scale-to-zero implementation in `ServingRuntimeReconciler` is particularly interesting: when no Predictors reference a given runtime, the controller scales its Deployment to zero replicas after a configurable grace period. When a new Predictor targeting that runtime is created, the controller scales the Deployment back up before calling `SetVModel`. This provides cost efficiency for clusters with many configured runtimes but few active models. The HPA integration adds another autoscaling dimension — within the min/max replica range, the HPA can scale based on CPU/memory utilization, while scale-to-zero handles the zero-to-one transition.

The validation webhook enforces important safety constraints: it rejects ServingRuntime specs that use reserved container names (`mm`, `rest-proxy`, `puller`), reserved ports (8080, 8085, 8089, 8090, 11881-11899), or reserved volume names. This prevents user-defined runtimes from conflicting with the injected ModelMesh infrastructure containers. The webhook also validates autoscaler configuration, including HPA metrics and scaling parameters. The webhook runs on port 9443 with TLS certificates provisioned by cert-manager.
