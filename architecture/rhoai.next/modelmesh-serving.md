## Purpose

**Short**: Kubernetes controller that manages the lifecycle of ModelMesh model serving deployments, orchestrating model placement across shared inference runtime pods.

**Detailed**: ModelMesh Serving is the control-plane controller for the ModelMesh model serving system within Red Hat OpenShift AI. It watches Predictor, InferenceService, and ServingRuntime custom resources and reconciles them into Kubernetes Deployments that host ModelMesh sidecar containers alongside third-party inference runtimes (Triton, MLServer, OpenVINO Model Server, TorchServe). The controller manages the full serving lifecycle: it creates per-runtime Deployments with ModelMesh sidecars, configures gRPC connectivity to the ModelMesh orchestration layer, provisions TLS certificates for inter-component communication, and dynamically generates Kubernetes Services for inference traffic routing.

The architecture follows a multi-model serving pattern where a single runtime Deployment can host many models simultaneously, with ModelMesh handling intelligent model placement, caching, and routing across pods. The controller communicates with an etcd cluster for model metadata coordination and supports both namespace-scoped and cluster-scoped deployment modes. A built-in REST proxy translates KServe V2 REST requests into gRPC for inference. An HPA reconciler provides autoscaling, and a validating webhook enforces configuration constraints on ServingRuntime and ClusterServingRuntime resources.

## Architectural Analysis

ModelMesh Serving's architecture splits cleanly into three control loops implemented as controller-runtime reconcilers. The **ServiceReconciler** is the infrastructure controller: it watches Deployments and Namespaces, reconciles the headless Kubernetes Services that front inference traffic, manages TLS certificate secrets for ModelMesh gRPC connections, and creates ServiceMonitor resources for Prometheus integration. The **ServingRuntimeReconciler** is the workload controller: it watches ServingRuntime and ClusterServingRuntime CRs, generates runtime-specific Deployment manifests from an internal Go template (`config/internal/base/deployment.yaml.tmpl`), injects ModelMesh sidecars and storage-helper init containers, and configures per-runtime PVC mounts and environment variables. The **PredictorReconciler** handles the model lifecycle: it watches Predictor CRs (and optionally InferenceService CRs via the `ENABLE_ISVC_WATCH` toggle), translates them into ModelMesh internal model registrations, and updates status.

A notable design decision is the etcd dependency: ModelMesh uses etcd as a distributed coordination store for model placement metadata, tracked via the `model-serving-etcd` Secret. The controller maintains a `ModelEventStream` that watches etcd for model lifecycle events and feeds them back into the reconciler loop. This creates an external stateful dependency that is unusual for Kubernetes operators and represents a failure domain outside of the Kubernetes API.

The TLS architecture is layered. The controller-to-ModelMesh gRPC channel uses TLS configured from a user-provided Secret (read in `ServiceReconciler.tlsConfigFromSecret`), using the system CA pool augmented with the Secret's certificate. The webhook server uses a separate TLS certificate (`modelmesh-webhook-server-cert`). The etcd client independently configures TLS from its own Secret data. None of these paths explicitly set `MinVersion` or constrain cipher suites—they rely on Go's crypto/tls defaults, which default to TLS 1.2+.

The ServiceMonitor configuration sets `InsecureSkipVerify: true` with a TODO comment indicating this is a known gap pending CA certificate integration. This means Prometheus scraping of metrics endpoints does not validate the server certificate.

The pprof debug endpoint (port 9999) is conditionally enabled via the `ENABLE_PPROF` environment variable and protected by HTTP Basic Auth using credentials extracted from the etcd Secret. This is an internal debugging surface, not exposed via Kubernetes Services.
