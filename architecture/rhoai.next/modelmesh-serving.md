## Purpose

**Short**: Kubernetes controller that manages the lifecycle of ModelMesh model serving deployments, routing model inference requests to appropriate serving runtimes.

**Detailed**: ModelMesh Serving Controller is the management plane for ModelMesh, a general-purpose model serving management and routing layer. It watches for ServingRuntime, ClusterServingRuntime, Predictor, and InferenceService custom resources and reconciles the corresponding Kubernetes Deployments that host ModelMesh sidecar containers alongside model serving runtime containers (Triton, MLServer, OpenVINO, TorchServe).

The controller manages the full lifecycle of model serving pods: it generates Deployment manifests from templates, injects ModelMesh sidecars, storage puller sidecars, oauth-proxy sidecars, and REST proxy containers. It communicates with the ModelMesh gRPC API to register and manage virtual models (vModels) that provide blue-green model deployment semantics. The controller also manages supporting resources including Kubernetes Services, etcd Secrets (for inter-pod coordination), ConfigMaps (for type constraints), ServiceMonitors (for Prometheus metrics), and HorizontalPodAutoscalers.

The controller supports both cluster-scoped and namespace-scoped operation modes. In cluster scope mode, it watches namespaces with the `modelmesh-enabled=true` label and creates serving infrastructure in each. In namespace scope mode, it operates only within its own namespace. It includes a validating webhook for ServingRuntime and ClusterServingRuntime resources that enforces autoscaler configuration constraints.

## Architectural Analysis

ModelMesh Serving Controller employs a template-driven deployment model rather than the more common declarative reconciliation pattern. The controller renders runtime pod Deployments from a Go template (`config/internal/base/deployment.yaml.tmpl`) at reconcile time, then applies a series of transformation functions to inject sidecar containers, environment variables, volumes, and TLS configuration. This approach allows the controller to compose complex multi-container pods (ModelMesh sidecar, model server, puller, REST proxy, oauth-proxy) while keeping each concern modular, but it means the deployment spec is not directly visible in static manifests — it only materializes at runtime.

The controller's relationship with ModelMesh is notable: it manages ModelMesh as a sidecar but communicates with it as a service. After creating runtime Deployments, the controller establishes gRPC connections to the ModelMesh instances via the headless Kubernetes Service. Through this connection, it manages virtual models (vModels) that provide zero-downtime model updates — when a Predictor's spec changes, the controller creates a new concrete model and atomically transitions the vModel to point to it. This pattern decouples the Kubernetes CRD lifecycle from the model serving lifecycle, enabling features like model rollback and canary deployment.

The etcd dependency is architecturally significant: each ModelMesh cluster (a set of runtime pods sharing a serving runtime) uses etcd as a distributed coordination layer for model placement, load balancing, and event propagation. The controller manages per-namespace etcd secrets derived from the controller namespace's secret, modifying the root prefix to provide namespace-level isolation within a shared etcd cluster. The `ModelMeshEventStream` component watches etcd for model state changes and translates them into Kubernetes reconciliation events.

The scale-to-zero implementation is controller-managed rather than relying on Knative or KEDA. The controller tracks per-runtime predictor counts and, when a runtime has no associated predictors, starts a grace period timer. After the grace period elapses, it sets the Deployment replicas to zero. This coexists with HPA-based autoscaling — the two mechanisms are mutually exclusive per runtime, enforced by the validating webhook.

A security consideration: the deployment template includes an oauth-proxy sidecar for OpenShift authentication on port 8443, but the REST proxy on port 8008 and the gRPC endpoint on port 8033 are protected only by optional TLS/mTLS and NetworkPolicy. In deployments where NetworkPolicy is not enforced or is misconfigured, the inference endpoints could be accessible without authentication. The `InsecureSkipVerify: true` in the ServiceMonitor TLS configuration is flagged as a TODO in the code and represents a metrics-scraping-only risk.
