## Purpose

**Short**: Training Hub is an algorithm-focused Python library and CLI (`thub`) that provides a unified interface for common LLM post-training techniques including supervised fine-tuning, continual learning, LoRA adaptation, reinforcement learning from verifiable rewards (GRPO), gradient-free prompt optimization (GEPA), and contrastive embedding fine-tuning.

**Detailed**: Training Hub implements a Strategy + Registry design pattern that decouples training algorithms from their backend implementations. Seven algorithms are currently registered — SFT (InstructLab Training backend), OSFT (Mini-Trainer backend), LoRA SFT (Unsloth backend), LoRA GRPO (ART or verl backends), full-parameter GRPO (verl backend), GEPA (gepa or MLflow backends), and Embedding SFT (SentenceTransformers backend) — each accessible through both a Python convenience function and the `thub` CLI with YAML config support.

The library is published to PyPI as `training-hub` and is not deployed as a long-running service. Instead, it is consumed as a dependency by Kubeflow training pipelines and interactive notebook sessions within the RHOAI platform. It orchestrates GPU-intensive training workloads locally via torchrun (for distributed FSDP training), subprocess isolation (for ART's co-located vLLM + Unsloth training), and direct API calls (for GEPA's gradient-free prompt optimization). The library also ships as a plugin for Claude Code and Codex CLI coding agents, providing guided training setup through interactive skills.

## Architectural Analysis

Training Hub's core design revolves around a two-level abstraction: `Algorithm` defines the training contract (required/optional parameters, validation, orchestration), while `Backend` encapsulates the execution strategy. `AlgorithmRegistry` maps algorithm names to classes and backends, enabling runtime backend selection via a `backend=` parameter. This architecture explicitly anticipates multiple backends per algorithm — the GRPO path already demonstrates this with ART (single-GPU, in-process via spawned subprocess) and verl (multi-GPU, torchrun subprocess with FSDP + vLLM co-location).

The ART backend's subprocess isolation pattern is architecturally significant: training runs inside `mp.get_context("spawn")` to prevent vLLM's non-daemon threads from blocking the parent process. Results are serialized to disk rather than returned via IPC, and `os._exit()` is used to force-terminate after successful completion — a design forced by vLLM V1's shutdown behavior. The verl backend takes a different approach, launching training as a torchrun subprocess with Hydra-style CLI overrides.

The callback system (`TrainingHubCallback` / `TrainingHubContext`) provides cross-backend lifecycle hooks that survive torchrun's subprocess boundary via class-source serialization. This means callbacks must be defined at module level with no-arg constructors and inline imports — a constraint documented in the callback module but easy to violate.

A notable supply chain risk is explicitly managed: litellm versions 1.82.7-1.82.8 are excluded from the dependency spec due to a known credential-harvesting attack (TeamPCP, March 2026). The GEPA algorithm's use of `importlib.import_module()` to resolve dotted paths for `reward_fn`, `rollout_fn`, and similar callable parameters creates a trust boundary — YAML config files can trigger arbitrary code execution.
