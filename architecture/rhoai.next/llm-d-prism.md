## Purpose

**Short**: Prism is an interactive performance analysis dashboard for distributed AI inference systems that unifies benchmark data from multiple cloud sources into a single visualization experience.

**Detailed**: Prism is a full-stack web application that helps AI Platform Engineers and ML Engineers choose, configure, and optimize inference infrastructure by consolidating benchmark data from disparate sources—Google Cloud Storage, AWS S3, Google Drive, and local experiments—into interactive scatter plots, comparison charts, and data tables. The application covers multiple analysis domains: general inference benchmarks, prefix-cache offloading studies, prefill/decode (P/D) disaggregation ratio analysis, regression tracking, and a curated Results Store for community-submitted benchmark runs.

The application uses a Backend-for-Frontend (BFF) architecture. The React 19 single-page application communicates exclusively through the Node.js/Express backend, which proxies authenticated requests to Google Cloud APIs (GCS, GKE Recommender/GIQ), manages a Results Store with submission lifecycle (staging, validation, review, promotion), and enforces authorization via GitHub OAuth with organization membership and GCS-hosted IAM allowlists. The production deployment targets Google Cloud Run at https://prism.llm-d.ai, though the Docker image can be deployed to any container platform.

## Architectural Analysis

Prism's BFF pattern is the central architectural decision: the Express backend absorbs all cloud credential management (Application Default Credentials for GCS/GIQ, GitHub OAuth secrets) so the React frontend never touches cloud API keys or tokens. This simplifies the security model—the browser only sees a proxied API surface—but concentrates trust in the backend process. The GCS proxy enforces bucket-boundary checks (only configured buckets are accessible) and object-level authorization (Results Store items are filtered by submission state and ownership), which is a layered defense model beyond the OAuth gate.

The Results Store introduces a stateful submission lifecycle (`staged → submitted_pending_processing → submitted_pending_review → public/promoted`) backed entirely by GCS object metadata (custom `contexts` fields). There is no relational database; GCS serves as both the object store and the metadata layer. This is architecturally simple but means query flexibility is limited to what GCS listing and metadata filtering can provide. The IAM model (admin/user/none) is resolved by combining GitHub organization membership with GCS-hosted allowlists, creating a two-source permission system.

The Go module (`cmd/main.go`) is a placeholder stub containing only a "TODO" print statement and contributes no runtime functionality. The Python script (`tools/update_arena_scores.py`) is an offline data-fetching utility not part of the deployed application.

The frontend architecture is data-source-centric: dedicated React hooks (`useGCS`, `useGIQ`, `useAWS`, `useLLMD`) abstract data fetching per cloud provider, with a central `useDashboardData` hook that merges results. Specialized dashboard views (PrefixCacheOffloadingDashboard, PdDisaggregationDashboard, RegressionsAnalysisDashboard, AgenticWorkloadsDashboard) handle domain-specific analysis while sharing common UI primitives and chart components.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | GitHub OAuth + IAM allowlists (admin/user/none roles) + llm-d org membership | Application (Express middleware) | Playground mode bypasses all auth; token validation relies entirely on GitHub API availability |
| Data storage | GCS object metadata (`submission_state`, `github_user` custom contexts) gates visibility | Application (GCS proxy filter logic) | No bucket-level isolation between tenants; all users share same GCS bucket with object-level filtering |
| Network traffic | Cloud Run managed networking | Google Cloud Run | No network-level tenant isolation; single service instance serves all users |
| Compute & resources | Express rate limiting (50,000 req/min) | express-rate-limit middleware | Rate limit is per-IP, not per-user; effectively unlimited in current configuration |
| Configuration & secrets | OAuth tokens are client-side (hash fragment); server-side IAM allowlists in GCS | Application + GCS | GitHub tokens passed in request headers; IAM allowlists are plain text files in GCS |
| API scoping | Results Store items filtered by ownership and submission state | Application (server.js GCS proxy list handler) | Filtering happens at application layer, not storage layer — a GCS credential leak would expose all data |
