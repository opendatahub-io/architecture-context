## Purpose

**Short**: Kubernetes operator that manages TrustyAI AI/ML trustworthiness, evaluation, and guardrails services on Red Hat OpenShift AI.

**Detailed**: The TrustyAI Service Operator is a multi-CRD Kubernetes operator that manages five distinct AI/ML trustworthiness services within the RHOAI platform. It deploys and manages TrustyAI Service (bias/fairness monitoring for inference services), LM Evaluation Harness (language model evaluation jobs), EvalHub (multi-tenant evaluation platform with MCP server support), Guardrails Orchestrator (composable guardrails pipeline for LLM safety), and NeMo Guardrails (NVIDIA NeMo guardrails server with MCP gateway integration).

The operator integrates deeply with the RHOAI platform through a TrustyAI module CRD (`components.platform.opendatahub.io/TrustyAI`) that allows platform operators to selectively enable/disable each sub-service. It supports Kueue-based job scheduling for evaluation workloads, KServe InferenceService integration for model monitoring, Istio service mesh integration for traffic management, and OpenShift Routes for external access. All services are protected by kube-rbac-proxy sidecars and leverage OpenShift serving certificates for TLS. The operator uses a component-based kustomize architecture where each sub-service has independent CRDs, RBAC, and deployment manifests, composable via the `--enable-services` flag.

### ta-lmes-driver

**Dockerfile**: `Dockerfile.konflux.driver`
**Intent**: Init container and sidecar process that manages LM-Eval harness execution within evaluation job pods. Copied into the main container via an init container, then runs as a sidecar HTTP server (port 18080) that monitors progress, provides status via `/GetStatus`, and handles graceful shutdown via `/Shutdown`. **Image**: `odh-ta-lmes-driver-rhel9`

## Architectural Analysis

The TrustyAI Service Operator is architecturally distinctive among RHOAI operators in that it manages five independent sub-services through a single operator binary with selectable controller activation. The `--enable-services` flag and the TrustyAI module CRD work in concert: the platform operator creates a cluster-scoped TrustyAI CR with `enabledServices` toggles, which the rhods-operator translates into `--enable-services` flags on the controller-manager Deployment. This pattern allows fine-grained feature gating without deploying separate operator binaries for each sub-service, but it does mean the single binary imports and compiles all controller code regardless of which controllers are actually activated.

The operator's cache strategy is noteworthy. The manager explicitly disables informer caching for ConfigMaps, Secrets, Pods, and Services (`client.CacheOptions.DisableFor`) to prevent OOM from cluster-wide informer flooding. Additionally, both the GORCH and NemoGuardrails controllers use `OnlyMetadata` watches for ConfigMaps, caching ~1KB of metadata instead of full ConfigMap data. This is essential because these controllers watch for configuration changes across potentially large numbers of ConfigMaps, and full-content caching would be prohibitive. The trade-off is slightly higher API server load for direct reads (~50ms vs ~1ms cached), which is acceptable given the infrequent reconciliation cadence (30-60 second requeue).

The security architecture follows a consistent kube-rbac-proxy sidecar pattern across all externally exposed services. Each managed service (TAS, EvalHub, GORCH, NemoGuardrails) deploys a kube-rbac-proxy sidecar that terminates TLS and performs SubjectAccessReview authorization before proxying to the application container on localhost. The auth decision is gated by the `security.opendatahub.io/enable-auth=true` annotation for GORCH and NemoGuardrails, while TAS and EvalHub always use auth proxies. The operator reads the cluster TLS security profile from `apiservers.config.openshift.io/cluster` and applies it to its own webhook and metrics servers, ensuring consistency with the cluster-wide TLS policy. This integration with OpenShift's configurable TLS profiles is more sophisticated than most operators, which typically hardcode TLS settings.

The LMEvalJob controller implements a sophisticated pod-based execution model with a driver sidecar pattern. Rather than using Kubernetes Jobs, it creates bare Pods with an init container that copies the driver binary to a shared emptyDir volume, then runs the driver alongside the main evaluation container. The driver provides an HTTP status API (port 18080) for progress monitoring and graceful shutdown. Input validation is security-hardened with regex patterns that prevent shell injection, path traversal, and unauthorized remote code execution. The `allowOnline` and `allowCodeExecution` flags implement a hierarchical permission model: DSC-level global settings can restrict permissions, and job-level specs can further restrict (but never expand) them. This defense-in-depth approach is critical for an evaluation framework that executes arbitrary model evaluation code.

The GORCH controller's auto-configuration system represents a significant integration complexity. It watches InferenceServices with a configurable label selector (`trustyai/guardrails=true`), extracts connection information from InferenceService status URLs, discovers serving certificate secrets, and generates complete orchestrator configuration YAML with generation service, detector services, TLS settings, and passthrough headers. The change detection uses SHA256 hashes of InferenceService names and resourceVersions to avoid unnecessary redeployments. This auto-discovery pattern means that users only need to label their InferenceServices and create a GuardrailsOrchestrator CR—the operator handles the rest.
