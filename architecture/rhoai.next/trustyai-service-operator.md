## Purpose

**Short**: Multi-controller Kubernetes operator that manages the lifecycle of TrustyAI platform services including AI fairness monitoring (TAS), model evaluation (LMEvalJob/EvalHub), guardrails orchestration (GORCH), and NVIDIA NeMo Guardrails integration on OpenShift.

**Detailed**: The TrustyAI Service Operator is a controller-runtime based operator that provides five distinct controllers, each managing a different TrustyAI service type. The operator uses a pluggable service registration pattern — controllers register themselves at init time, and the `--enable-services` flag selects which controllers to activate at startup. In RHOAI deployments, all services (TAS, LMES, GORCH, NEMO_GUARDRAILS, EVALHUB) are enabled.

The TAS controller manages TrustyAI Service instances that provide AI fairness and explainability monitoring, integrating with KServe InferenceServices to intercept prediction payloads. The LMES controller manages LMEvalJob custom resources for language model evaluation using lm-evaluation-harness, with optional Kueue integration for workload queuing. The EvalHub controller provides a centralized evaluation hub with multi-tenant support, MCP (Model Context Protocol) server capabilities, and provider-based evaluation framework integration. The GORCH controller deploys the Guardrails Orchestrator with auto-discovery of KServe inference services for generator and detector configuration. The NemoGuardrails controller manages NVIDIA NeMo Guardrails deployments with Istio EnvoyFilter integration and MCP Gateway discovery.

A sixth controller (MODULE) reconciles the cluster-scoped `TrustyAI` CRD (`components.platform.opendatahub.io`), which is the DSC module registration point used by the platform operator to manage the TrustyAI component lifecycle.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy SAR per service instance; per-tenant RBAC Roles and RoleBindings in tenant namespaces (EvalHub) | kube-rbac-proxy sidecar, Kubernetes RBAC | TAS and GORCH rely on namespace-level RBAC; EvalHub adds fine-grained tenant roles |

| Network traffic | Relies on namespace NetworkPolicy from platform operator (redhat-ods-applications); EvalHub metrics port (8081) chosen to match existing NetworkPolicy allowlist | Platform operator NetworkPolicy | No component-level NetworkPolicies created by this operator |
| Compute & resources | Per-deployment resource requests/limits (configurable via operator ConfigMap); Kueue integration for LMES job queuing | Kubernetes resource limits, Kueue | No ResourceQuota or LimitRange created by this operator |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; EvalHub discovery ConfigMap injected into tenant namespaces | Kubernetes namespace isolation | Tenant provider/collection ConfigMaps mounted at separate /tenant/ sub-paths to prevent shadowing system configs |
| API scoping | Cluster-wide watches with per-namespace reconciliation; EvalHub tenant namespaces discovered via label selector | controller-runtime, Application (EvalHub) | Operator watches all namespaces but reconciles only owned CRs |

## Architectural Analysis

The TrustyAI Service Operator employs a distinctive multi-controller-in-one-binary architecture, where a single operator binary hosts six controllers, each selected by the `--enable-services` flag. This design consolidates operational overhead — one Deployment, one leader election lease, one set of RBAC bindings — while allowing selective controller activation for different deployment scenarios. The service registration pattern in `controllers/controllers.go` (lines 31-45) uses a global map populated by `init()` functions in each controller package's registration file (e.g., `controllers/evalhub.go`, `controllers/tas.go`), decoupling controller wiring from the main entrypoint.

The operator's image resolution strategy is sophisticated and operationally robust. The `controllers/images/resolver.go` (lines 80-109) implements a three-tier resolution chain: `RELATED_IMAGE_*` environment variables (injected by the platform operator's OLM-managed CSV) take precedence, followed by ConfigMap values (`trustyai-service-operator-config`), with an optional fallback. This enables disconnected/air-gapped deployments where image references are pinned in the CSV, while allowing override via ConfigMap for development or testing. The naming convention (`RELATED_IMAGE_ODH_*`) follows the OLM disconnected-mode pattern that enables automatic image mirroring.

The security model is consistent across all controllers: every user-facing service gets a kube-rbac-proxy sidecar that terminates TLS and enforces SubjectAccessReview authorization before proxying to the application container on loopback. The TLS certificate chain is managed entirely by OpenShift's service-serving-cert-signer via annotations, with no manual cert provisioning. The operator itself reads the cluster TLS security profile (`apiservers.config.openshift.io/cluster`) at startup to align its metrics server TLS configuration with cluster policy — falling back to Mozilla Intermediate (TLS 1.2, FIPS-compliant cipher suites) on non-OpenShift clusters or when the profile is unavailable. This is a strong FIPS posture: both Konflux Dockerfiles use `GOEXPERIMENT=strictfipsruntime`, and the application code explicitly avoids non-FIPS crypto (InsecureSkipVerify defaults to false, TLS MinVersion is explicitly TLS 1.2).

The EvalHub controller represents the most architecturally complex sub-component, with multi-tenant namespace management, MCP server support, provider/collection ConfigMap synchronization, and Kueue workload integration. Its tenant isolation model uses label-based namespace discovery (`controllers/evalhub/evalhub_tenant_namespaces.go`) where namespaces labeled with a discovery label are treated as tenant namespaces. The controller creates per-tenant RBAC (ServiceAccounts, Roles, RoleBindings), discovery ConfigMaps, and provider/collection ConfigMaps in each tenant namespace, with cleanup on label removal. The MCP server is deployed as an optional sidecar container (`evalhub-mcp`) that shares the kube-rbac-proxy authentication boundary with the main EvalHub container.

A notable architectural risk is the NemoGuardrails controller's cross-namespace EnvoyFilter creation — it discovers MCPGatewayExtension resources, resolves their target Gateway, and creates an EnvoyFilter (`mcp-sse-strip`) in the gateway's namespace (which may differ from the NemoGuardrails CR's namespace). This cross-namespace write requires elevated RBAC and creates an implicit dependency on the gateway namespace's security posture. The controller includes BBR plugin detection (`controllers/nemo_guardrails/envoy_filter.go:34-76`) to avoid creating conflicting EnvoyFilters.
