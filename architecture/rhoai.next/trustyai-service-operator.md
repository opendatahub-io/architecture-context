## Purpose

**Short**: Multi-service Kubernetes operator that manages AI/ML model trustworthiness, evaluation, and guardrail workloads across TrustyAI, EvalHub, LMEval, and NemoGuardrails service domains.

**Detailed**: The trustyai-service-operator is a controller-runtime-based operator that manages five distinct service controllers through a dynamic registration system. Each service can be independently enabled at startup via the `--enable-services` flag (TAS, EVALHUB, LMES, NEMO_GUARDRAILS, JOB_MGR). The operator provisions and manages per-namespace TrustyAI service instances with kube-rbac-proxy sidecars for authenticated access, orchestrates LM evaluation jobs via pod-based execution with driver containers, deploys EvalHub instances for centralized model evaluation with multi-tenant support, and manages NVIDIA NemoGuardrails deployments for model safety guardrails.

The operator also includes a companion component, the trustyai-operator-module, which acts as an ODH/RHOAI DataScienceCluster (DSC) component module controller. This module watches the `TrustyAI` CR (cluster-scoped, `components.platform.opendatahub.io/v1alpha1`) and renders the main operator's manifests into the target namespace using `odh-platform-utilities`. Together, the main operator and the module controller form a two-level deployment: the module controller handles component lifecycle within the platform, while the main operator handles workload-level CRDs within user namespaces.

## Architectural Analysis

The operator's most distinctive architectural pattern is its multi-service registration system. Controllers register themselves via `init()` functions in shim files under `controllers/`, and `SetupControllers` in `controllers/controllers.go` dispatches to each registered service's setup function. This enables a single operator binary to selectively activate subsets of its controllers, reducing resource consumption when only some services are needed.

TLS configuration is centrally resolved at startup by reading the OpenShift `apiservers.config.openshift.io/cluster` resource. The resolved TLS profile (cipher suites, minimum version, curve preferences) is propagated to three surfaces: the controller-runtime metrics server, the webhook server, and the kube-rbac-proxy arguments for all operator-created TrustyAI service deployments. A dedicated TLS ProfileWatcher controller monitors the APIServer resource and triggers a full manager restart when the cluster's TLS security profile changes, ensuring operand deployments are reconciled with the new profile without running an intermediate state.

The operator disables controller-runtime caching for ConfigMap, Secret, Pod, and Service types to prevent OOM from cluster-wide informer cache flooding. This trades sub-millisecond cache reads for ~50ms direct API server reads on these high-volume types, an intentional design choice documented in the source.

EvalHub's multi-tenancy model is noteworthy: a single EvalHub instance in a control-plane namespace serves multiple tenant namespaces identified by the label `evalhub.trustyai.opendatahub.io/tenant`. The operator provisions per-tenant ServiceAccounts, RBAC bindings, and discovery ConfigMaps across tenant namespaces, with a placement guard that prevents deploying a multi-tenant instance inside a namespace carrying the tenant label.

OpenTelemetry integration is opt-in: tracing and OTLP metrics export are activated via standard `OTEL_EXPORTER_OTLP_*` environment variables. Prometheus metrics are independently exported via a Prometheus exporter bridge registered on the controller-runtime metrics endpoint.

FIPS awareness extends beyond build flags. The runtime actively checks `crypto/fips140.Enabled()` and the kernel FIPS mode file (`/proc/sys/crypto/fips_enabled`), adjusting curve preferences (removing X25519 and X25519MLKEM768) when FIPS is active. This runtime-adaptive approach ensures correct cryptographic behavior on FIPS-enforcing nodes even when the binary itself is not built with FIPS-only curves.
