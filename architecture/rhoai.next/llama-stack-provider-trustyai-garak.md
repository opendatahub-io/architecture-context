## Purpose

**Short**: Garak red-teaming evaluation adapter for the eval-hub platform, enabling automated LLM vulnerability scanning on OpenShift AI.

**Detailed**: This component provides a `FrameworkAdapter` implementation that integrates NVIDIA's Garak red-teaming framework with the eval-hub evaluation platform. It runs as a Kubernetes Job (simple mode) or orchestrates Kubeflow Pipelines (KFP mode) to perform automated vulnerability assessments of Large Language Models, covering prompt injection, jailbreaks, toxicity, bias, and other attack vectors.

The adapter supports multiple benchmark profiles including OWASP LLM Top 10, AVID taxonomy (security, ethics, performance), CWE, and a custom intents-based risk assessment mode. In intents mode, the adapter performs Synthetic Data Generation (SDG) using sdg-hub to produce targeted adversarial prompts from a taxonomy of harm categories, then runs those prompts through an escalating pipeline of attack strategies (SPO, translation, TAP).

Results are reported back to eval-hub as `EvaluationResult` metrics, persisted to OCI registries, uploaded to S3 (in KFP mode), and optionally logged to MLflow. The component generates HTML reports including Vega-based visualizations for intents scans.

## Architectural Analysis

The component follows a clean layered architecture with three distinct tiers: a `core` module containing framework-agnostic business logic (config resolution, command building, garak subprocess execution, API key management), an `evalhub` module implementing the eval-hub `FrameworkAdapter` interface, and a top-level module providing Pydantic models for garak configuration. This separation enables code reuse -- the same core logic can drive both simple (subprocess) and KFP (distributed pipeline) execution modes without duplication.

The KFP pipeline design is notable for its six-step decomposition: validate, resolve_taxonomy, sdg_generate, prepare_prompts, garak_scan, and write_kfp_outputs. Each step is a self-contained `@dsl.component` using the same base image as the adapter itself. This enables KFP caching -- taxonomy resolution and SDG generation can be cached across multiple scan runs with identical inputs, significantly reducing execution time for repeated intents benchmarks. The pipeline wires secrets via `kubernetes.use_secret_as_env` (S3 data connection) and `kubernetes.use_secret_as_volume` (model auth), keeping credentials out of the pipeline definition.

API key management uses a sophisticated multi-layer resolution chain. In KFP mode, keys flow through placeholders (`__FROM_ENV__`) in the config that are resolved at pod runtime by `_resolve_config_api_keys()`, which reads from volume-mounted secret files (`/mnt/model-auth/{ROLE}_API_KEY`) or environment variables. This design supports both the legacy model (SA token auto-mounted) and the new sidecar-proxy model (evalhub >= 0.4.4 where `AutomountServiceAccountToken=false`). The sidecar proxy intercepts KFP API calls and injects authentication, while `k8s_sa_token:ref` placeholders trigger token resolution. All config files are redacted (`redact_api_keys`) before upload to S3 or OCI to prevent credential leakage.

The intents mode represents the most architecturally complex path. It orchestrates up to five LLM endpoints (target, judge, attacker, evaluator, SDG) with an escalating attack pipeline: baseline probes → SPO (augmented) → multilingual translation → TAP (tree-of-attack with model-as-judge). The `generate_intents_from_dataset` function creates Garak's CAS (Context Aware Scanning) topology files and intent stub JSONs from the SDG output, bridging the sdg-hub output format to garak's internal intent system. The ART HTML report (generated via Jinja2 with embedded Vega-Lite chart specifications) provides interactive visualizations of attack success rates across strategies and intents.

One notable design choice is the TLS verification flexibility. The `get_http_client_with_tls()` utility and KFP client configuration both support disabling TLS verification. While pragmatic for development and internal cluster communication, this creates a potential FIPS compliance gap in production -- there is no enforcement mechanism to prevent TLS verification bypass. The component inherits OpenSSL from its AIPCC base image but does not explicitly configure FIPS-compliant cipher suites.
