## Purpose

**Short**: Garak red-teaming evaluation adapter for the RHOAI eval-hub platform, enabling automated LLM vulnerability scanning via Kubernetes Jobs or Kubeflow Pipelines.

**Detailed**: This component provides a `FrameworkAdapter` implementation that integrates NVIDIA's [Garak](https://github.com/NVIDIA/garak) red-teaming framework with the RHOAI evaluation platform (eval-hub). It supports two execution modes: **simple mode**, where Garak runs as a subprocess inside an eval-hub Kubernetes Job pod, and **KFP mode**, where the adapter submits a six-step Kubeflow Pipeline (validate, resolve taxonomy, SDG, prepare prompts, scan, write outputs), polls for completion, and downloads results from S3.

The adapter supports predefined benchmark profiles covering OWASP LLM Top 10, AVID taxonomy, CWE, and quality assessments. A key feature is the **intents benchmark**, which combines Synthetic Data Generation (SDG) via sdg-hub with adversarial probes (TAPIntent, SPO, multilingual translation) for targeted risk assessment against custom policy taxonomies.

Results are reported as `EvaluationResult` metrics per probe with attack success rates, persisted to OCI registries and MLflow, and include JSONL, HTML, and AVID-format reports. The container image is built via Konflux using AIPCC CPU base images and ships all dependencies including the pinned Garak version (`0.15.0+rhaiv.5`).

## Architectural Analysis

The component follows a clean layered architecture with a `core/` package containing framework-agnostic business logic and an `evalhub/` package providing the eval-hub-specific adapter. This separation allows the same scan orchestration logic (config resolution, command building, process management, result parsing) to be reused across different integration points. The `core/pipeline_steps.py` module is particularly well-designed, providing all six KFP pipeline steps as pure functions that operate on local file paths and DataFrames, with I/O adapters (S3, OCI) handled at the evalhub layer.

The intents benchmark is the most architecturally complex feature, requiring up to four separate LLM model endpoints (target, judge, attacker, evaluator) plus an optional SDG model. The API key resolution system in `core/pipeline_steps.py` implements a sophisticated fallback chain: role-specific env var -> role-specific secret file -> generic env var -> generic secret file -> EvalHub SDK convention -> "DUMMY". This accommodates multiple deployment models: direct SA token auth (pre-sidecar), evalhub sidecar proxy (>= 0.4.4), and local development. The `__FROM_ENV__` placeholder pattern in `garak_config` is a security-conscious design that avoids embedding real keys in config files that may be persisted to S3 or OCI.

The KFP pipeline definition in `kfp_pipeline.py` uses `kubernetes.use_secret_as_env` for S3 credentials (Data Connection pattern) and `kubernetes.use_secret_as_volume` with `optional=True` for model auth. This allows KFP pods to operate independently of the adapter pod's auth context. The pipeline's six-step design with explicit caching annotations (taxonomy and SDG steps are cacheable, validation and scan steps are not) balances performance with correctness.

A notable design decision is the dual-mode base image resolution in `kfp_pipeline.py:_resolve_base_image()`, which checks KFPConfig, environment variables, and the `trustyai-service-operator-config` ConfigMap in two candidate namespaces (`redhat-ods-applications` and `opendatahub`). This creates a coupling with the trustyai-service-operator and opendatahub-operator components. The `KUBEFLOW_CANDIDATE_NAMESPACES` constant in `constants.py` hardcodes these namespace candidates, which could be fragile across different deployment topologies.

The result parsing system (`result_utils.py`) is comprehensive, supporting both standard AVID-based aggregation and intents-specific stub-level aggregation. The TBSA (Tier-Based Security Aggregate) scoring is computed when garak >= 0.14.0 is available, providing a standardized cross-scan comparability metric. The ART (Automated Red Teaming) HTML report generation uses Jinja2 templates with embedded Vega chart specifications for interactive visualization of attack success rates across probes and intents.
