## Purpose

**Short**: Garak red-teaming evaluation adapter that integrates NVIDIA's Garak LLM vulnerability scanner with the eval-hub evaluation platform, running as Kubernetes Jobs or Kubeflow Pipelines.

**Detailed**: This component provides a `FrameworkAdapter` implementation for the eval-hub SDK that orchestrates Garak-based security and safety assessments of Large Language Models. It supports two execution modes: **simple mode**, where Garak runs as a subprocess directly inside the eval-hub K8s Job pod, and **KFP mode**, where the adapter submits a six-step Kubeflow Pipeline (validate → resolve taxonomy → SDG → prepare prompts → scan → write outputs), polls for completion, and retrieves results from S3-compatible object storage.

The adapter ships predefined benchmark profiles covering OWASP LLM Top 10, AVID taxonomy (security, ethics, performance), CWE, and a policy-based intents workflow. The intents mode uses Synthetic Data Generation (SDG) via `sdg-hub` to produce adversarial prompts from a taxonomy of harm categories, then applies TAPIntent probes and MulticlassJudge detectors for targeted risk assessment. Results are reported as `EvaluationResult` objects back to eval-hub with per-probe attack success rates, TBSA (Tier-Based Security Aggregate) scoring, and optional HTML/AVID-format reports.

Despite the repository name referencing "llama-stack-provider," all Llama Stack provider code was removed in v0.5.0. The package no longer depends on or supports llama-stack/ogx.

## Architectural Analysis

This component follows a classic adapter pattern: it bridges two systems — eval-hub (the orchestration platform) and Garak (the scanning engine) — without owning either. The adapter's primary responsibility is configuration resolution, execution delegation, and result transformation.

The dual execution mode design (simple vs. KFP) is the central architectural decision. Simple mode keeps the blast radius small — Garak runs in the same pod, and failure is local. KFP mode trades simplicity for capability: the six-step pipeline enables the intents workflow (SDG → prompt normalization → scan → report), caching of taxonomy and SDG steps, and artifact persistence to S3 for later review. The cost is a hard dependency on Kubeflow Pipelines infrastructure, S3-compatible storage, and a more complex credential resolution chain.

Credential handling is deliberately layered: the adapter supports direct K8s API access (pre-sidecar model), KFP_AUTH_TOKEN environment variables, a sidecar proxy model (evalhub ≥ 0.4.4), model auth secrets, and kubeconfig fallback. This multi-path resolution makes the adapter resilient across deployment configurations but increases the surface area for misconfiguration. API keys are always redacted before persisting configs to S3 or OCI registries.

The dependency footprint is notably large — Garak pulls in torch, transformers, langchain, anthropic, openai, litellm, and many other ML/AI libraries. This is an inherent consequence of wrapping a general-purpose LLM red-teaming tool. The `requirements.txt` is generated via `uv pip compile` against the RHOAI package index, serving as the de facto lock file.
