## Purpose

**Short**: Praxis AI is an AI gateway proxy that provides provider-aware routing, protocol translation, stateful OpenAI APIs, and agentic traffic management for inference backends.

**Detailed**: Praxis AI is a high-performance reverse proxy built on the Praxis proxy framework (which itself is built on Cloudflare's Pingora). It sits between AI clients (OpenAI SDK, Anthropic SDK, MCP clients, A2A agents) and inference backends (vLLM, proprietary APIs), classifying requests by provider protocol, translating between API formats (e.g., Anthropic Messages to Chat Completions), and applying policy through a configurable filter pipeline.

The gateway implements stateful OpenAI Responses and Conversations APIs with pluggable persistence (PostgreSQL, SQLite), enabling response rehydration, context compaction, and durable agentic tool loops with MCP approval workflows. It supports intelligent request routing based on model, API format, or MCP tool name, and integrates with external services for guardrails (NeMo), credential injection (AWS SigV4, Azure AD, GCP ADC), metering, and prompt enrichment.

Praxis AI ships two container images: a standard Alpine-based image with the full feature set, and a FIPS 140-3 build on UBI 9 that restricts features to those whose cryptography runs entirely through the system OpenSSL. The FIPS build is designed for deployment on RHEL 9 hosts in FIPS mode, where the OpenSSL FIPS provider is the validated cryptographic module.

## Architectural Analysis

Praxis AI's architecture follows a layered filter-pipeline model inherited from the Praxis core proxy framework. Every request passes through a configurable chain of `HttpFilter` implementations that classify, transform, route, and persist traffic. The key architectural insight is the separation between the proxy runtime (Praxis core — listeners, TLS, load balancing, connection pooling) and the AI-specific logic (this repository — provider classification, protocol translation, response state management, agentic loops).

The crate dependency flow is strictly layered: `praxis-ai-proxy` (binary) → `praxis-ai-filters` (filter registration and cross-cutting concerns) → `praxis-ai-apis` (provider-specific protocol logic, store traits) → `praxis-core`/`praxis-filter` (proxy framework). This layering is enforced through Cargo features, with the `standard` feature set providing a lean proxy and `full` adding the stateful OpenAI groups and their database dependencies.

The filter pipeline uses a classify-then-route pattern: classifier filters examine request bodies and promote provider/model/operation facts to internal headers (`x-praxis-ai-*`), and routing filters (`intelligent_route`, `provider_route`) match those headers to select backend clusters. Security-critical filters (`credential_inject`, `provider_route`, `aws_sigv4_sign`, `state_owner`) are registered with a `Security` class that the framework enforces separately from general-purpose filters.

The response store architecture is notable for its tenant-scoped ownership model: every persisted record is bound to a `StateOwner` (tenant_id + issuer + subject), and the store trait enforces that queries can never cross ownership boundaries. The store lifecycle is managed through a `ResponseStoreRegistry` pipeline extension that supports hot-reload without dropping in-flight connections to the database. Store backend selection (PostgreSQL, SQLite, in-memory) is a compile-time feature gate, and the FIPS build excludes all store backends because sqlx's migration checksums use pure-Rust `sha2`.

The FIPS compliance architecture is unusually thorough for a Rust project. Rather than attempting to make all dependencies FIPS-compliant, the project defines a reduced feature set (`FIPS_FEATURES`) that excludes filters whose transitive dependencies carry non-OpenSSL cryptography. The `fips_blocker()` function at startup checks the filter registry against a denylist and refuses to start under `PRAXIS_REQUIRE_FIPS` if non-FIPS filters are registered. All application-level cryptography (SHA-256, HMAC-SHA256 for AWS SigV4 signing) is explicitly routed through OpenSSL's EVP API rather than using pure-Rust alternatives, ensuring the FIPS provider handles it on FIPS-mode hosts.

The llm-d ext_proc integration is architecturally isolated as an optional crate (`praxis-ai-llmd-ext-proc`) that provides Envoy external processing protocol compatibility specifically for the llm-d project. It is explicitly not a general-purpose ext_proc implementation and is documented as an anti-pattern relative to native Praxis filters.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request identity via `state_owner` filter (security-class); identity derived from trusted request headers or mTLS peer certificate | Application (filter pipeline, security-class enforcement) | Application-enforced: a misconfigured filter chain could skip the state_owner filter; security-class registration mitigates but does not prevent all misconfigurations |
