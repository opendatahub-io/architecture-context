## Purpose

**Short**: A lightweight Rust HTTP service that detects PII and custom patterns in text using regular expressions, designed to integrate with the FMS Guardrails Orchestrator.

**Detailed**: The guardrails-regex-detector is a stateless microservice built with the Axum web framework on a Tokio async runtime. It provides a single detection endpoint that accepts text contents and a list of regex patterns, returning matches with their positions, types, and confidence scores. The service ships with built-in detectors for common PII patterns (email addresses, Social Security numbers, and credit card numbers) and supports arbitrary user-supplied regular expressions for custom detection.

The component is part of the TrustyAI guardrails ecosystem within RHOAI. It acts as a downstream detection backend called by the FMS Guardrails Orchestrator, which routes content through multiple detectors before allowing responses from foundation models. The regex detector handles the deterministic, pattern-based detection class — complementing ML-based detectors that handle more nuanced content analysis.

The service is intentionally minimal (~200 lines of Rust) with no external dependencies beyond the web framework and regex engine. It has no persistent state, no database connections, and no TLS termination at the application layer, relying on the surrounding platform infrastructure (service mesh, sidecar proxies) for transport security.

## Architectural Analysis

The guardrails-regex-detector follows a clean single-responsibility pattern: it receives text, applies regexes, and returns structured match results. The architecture is notable for what it omits rather than what it includes — there is no authentication enforcement, no TLS configuration, no connection pooling, and no Kubernetes manifests in the repository. This positions it as a pure application container whose deployment, networking, and security are entirely managed by the platform operator that integrates it.

The detection model uses a two-tier approach: named built-in patterns (email, SSN, credit-card) are resolved from a hardcoded registry, while any unrecognized pattern string is compiled as a custom regex. All detections return a uniform response structure with start/end offsets, matched text, detection type, and a fixed score of 1.0. This fixed score is appropriate for regex matching (a pattern either matches or it doesn't) but means consumers cannot distinguish high-confidence from partial matches.

A design risk is that user-supplied regex patterns are compiled per-request without caching or complexity limits. A pathologically complex regex could cause excessive CPU consumption (ReDoS). The `regex` crate used here is designed to prevent catastrophic backtracking by using finite automaton-based matching, which mitigates this risk at the library level, but pattern compilation overhead remains per-request.

The repository contains only a standard Dockerfile — no Konflux-suffixed Dockerfile exists, suggesting this component may not yet be integrated into the Konflux CI/CD pipeline for production builds. The Dockerfile uses a Debian-based Rust builder (not UBI) for compilation, then copies the binary onto a UBI 9 minimal release image.
