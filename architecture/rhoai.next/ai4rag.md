## Purpose

**Short**: An optimization engine that automatically finds optimal hyperparameters for Retrieval-Augmented Generation (RAG) pipelines, producing tuned RAG Patterns from a configurable search space.

**Detailed**: `ai4rag` is a Python library that accepts a search space of RAG configuration parameters (foundation models, embedding models, chunking strategies, retrieval methods, vector store settings) and uses hyperparameter optimization (HPO) to find the best-performing combination for a given knowledge base and benchmark dataset. It is LLM and vector database provider-agnostic by design, with first-class integration with the OGX platform for embeddings, vector stores, and text generation.

The library implements a complete RAG evaluation pipeline: documents are chunked (via LangChain's RecursiveCharacterTextSplitter or Docling's structure-aware HybridChunker), embedded into a vector store (OGX-managed Milvus/Qdrant or in-memory ChromaDB), retrieved via similarity search, and used as context for foundation model generation. Each configuration is evaluated against a benchmark dataset using Unitxt metrics (answer correctness, faithfulness, context correctness) and optionally an LLM-as-a-Judge evaluator for answer relevance. A GAM-based (Generalized Additive Models) optimizer guides the search, with a random optimizer available as a fallback.

The library also provides pipeline-oriented orchestration modules (`ai4rag.components`) designed for integration with Kubeflow Pipelines (KFP). These modules handle S3-based document discovery, text extraction via Docling, document indexing into OGX vector stores, search space preparation with automatic model discovery, and full RAG optimization runs with artifact generation (pattern JSONs, Jupyter notebooks for indexing and inference).

## Purpose

**Detailed**: ai4rag is a Python library that automates the discovery of optimal RAG pipeline configurations. ## Architectural Analysis

The ai4rag library implements a clean separation between its optimization engine and its model/infrastructure integrations. The `BaseFoundationModel`, `BaseEmbeddingModel`, `BaseVectorStore`, `BaseChunker`, `BaseEvaluator`, and `BaseRAGTemplate` abstract base classes define contracts that allow swapping providers without modifying the optimization logic. However, in practice, the only production implementations target OGX (`OGXFoundationModel`, `OGXEmbeddingModel`, `OGXVectorStore`) while ChromaDB serves as a lightweight fallback for local development and model pre-selection. This means the library's "provider-agnostic" design is aspirational -- extending it to other platforms (e.g., direct OpenAI, Pinecone, or Weaviate integration) requires implementing these base classes.

The hyperparameter optimization layer is notably simple compared to full AutoML frameworks. The `GAMOptimizer` fits a `LinearGAM` model to evaluated configurations and uses its predictions to select promising candidates from the remaining search space. The search space itself is defined as a Cartesian product of categorical parameters with rule-based filtering (e.g., chunk overlap must be zero for hybrid chunking, chunk size must fit within embedding model context length). This approach is effective for the relatively small search spaces typical of RAG tuning (dozens to hundreds of combinations) but would not scale to thousands of dimensions. The `RandomOptimizer` provides a baseline comparison.

The evaluation system is extensible through the multi-evaluator dispatch pattern introduced in v0.10.0. The `UnitxtEvaluator` provides deterministic metrics (answer correctness, faithfulness, context correctness) while the `LLMaJEvaluator` uses a foundation model as an LLM judge for answer relevance scoring. Judge model selection is itself an optimization problem -- the `select_judge_model` function evaluates each candidate judge on a calibration subset and picks the one with the highest "spread and stability" score (standard deviation weighted by success rate). This ensures the selected judge produces discriminative, reliable scores rather than uniform ratings.

A notable security concern is the SSL verification fallback pattern used in both the OGX client and S3 client wrappers. When SSL certificate verification fails, both `create_ogx_client` and `_list_objects_with_ssl_fallback` silently retry with `verify=False`, logging only a warning. This is pragmatic for development environments with self-signed certificates but represents a man-in-the-middle risk in production. The library provides no mechanism to disable this fallback or enforce strict TLS.

The KFP-oriented components in `ai4rag.components` are designed as individual pipeline steps: document discovery (S3 listing with size-based sampling), text extraction (via Docling), document indexing (chunking + embedding into OGX vector stores), search space preparation (model discovery + constraint validation), and RAG optimization (full experiment with artifact generation). The `KFPEventHandler` collects all pattern results in memory for post-experiment processing, while the `LocalEventHandler` writes per-pattern JSON files for local development. These components assume a specific data flow (S3 -> Docling -> OGX) that aligns with the RHOAI pipeline architecture.

## Architectural Analysis

ai4rag follows a clean layered architecture with abstract base classes at each integration boundary. `BaseFoundationModel`, `BaseEmbeddingModel`, and `BaseVectorStore` define pluggable interfaces, with OGX implementations (`OGXFoundationModel`, `OGXEmbeddingModel`, `OGXVectorStore`) as the primary concrete classes and ChromaDB as an alternative vector store backend. This abstraction makes the library extensible to other LLM/embedding providers without modifying the core experiment logic.

The hyperparameter optimization layer is well-separated from the RAG pipeline. `AI4RAGSearchSpace` defines the parameter grid (chunk size, overlap, retrieval method, embedding model, foundation model, search mode, ranker parameters) with constraint rules that prune invalid combinations before optimization begins. The `GAMOptimizer` uses Generalized Additive Models to guide search, while a `RandomOptimizer` serves as a simpler alternative.

The library has no deployment footprint of its own — it is consumed as a pip-installable package. All network communication is delegated to `OgxClient`, which the consuming application must instantiate with appropriate credentials and endpoint configuration. This means authentication, TLS, and network security are entirely determined by the consumer's OGX client configuration, not by ai4rag itself.

A notable design pattern is the model pre-selection (MPS) stage: when more than 3 foundation models or 2 embedding models are provided, the experiment first evaluates them on a small data sample to narrow the candidate set before running full optimization. This reduces the cost of the combinatorial search space significantly.

The `ogx-client` dependency (`~=1.0.0`) is a recent migration from older OGX SDK patterns, as evidenced by the v0.6.1 release switching to `ogx 1.0.0` and updating vector store API calls from `vector_io.query()` to `vector_stores.search()`.
