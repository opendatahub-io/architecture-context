## Purpose

**Short**: ai4rag is a provider-agnostic RAG (Retrieval-Augmented Generation) optimization engine that automatically discovers optimal hyperparameters for RAG pipelines by searching over chunking, embedding, retrieval, and generation configurations.

**Detailed**: ai4rag is an IBM-developed Python library that treats RAG pipeline construction as a hyperparameter optimization problem. Given a set of knowledge-base documents, benchmark questions, and a search space of parameters (foundation models, embedding models, chunking methods, retrieval strategies), the engine evaluates candidate RAG configurations ("patterns") using automated metrics (unitxt, RAGAS, LLM-as-a-Judge) and a GAM-based optimizer to find the best-performing configuration.

The library is model-provider-agnostic: it reaches foundation and embedding models through the OpenAI SDK, so any OpenAI-compatible endpoint works — including OpenShift AI Models-as-a-Service (MaaS), vLLM, TGI, or Ollama. Vector store backends are pluggable: remote Milvus, embedded Milvus Lite, PostgreSQL/pgvector, and Neo4j (for graph-based RAG with knowledge-graph extraction). Each backend is selected via a frozen-dataclass config with a `.from_env()` constructor, keeping secrets in environment variables and out of generated artifacts.

Beyond optimization, ai4rag generates deployable artifacts from the best pattern: Jupyter notebooks for reproduction, a leaderboard of evaluated patterns, and an "agentic RAG starter kit" — a FastAPI service with an OpenAI Responses-API-compatible endpoint, Kubernetes TokenReview authentication, and an OpenShell Containerfile for sandbox deployment on OpenShift AI.

## Architectural Analysis

ai4rag's architecture separates clearly into three layers: a **core optimization engine**, a **pluggable RAG backend**, and an **artifact generation pipeline**.

The optimization engine (`ai4rag.core`) orchestrates hyperparameter search using a GAM (Generalized Additive Model) optimizer with optional warm-start candidates. Each trial instantiates a complete RAG pipeline — chunker, embedding model, vector store, retriever, and RAG template — evaluates it against benchmark data, and reports a composite score. Collection reuse across trials sharing the same indexing parameters is a key efficiency: the engine fingerprints `(chunking + embedding + optional KG extraction)` to skip redundant indexing.

The RAG backend (`ai4rag.rag`) implements a template pattern: `BaseRAGTemplate` subclasses (`AgenticRAG` for multi-turn retrieval with query rewriting, `SimpleRAG` for single-pass retrieve-then-generate) compose a foundation model with a retriever. Vector store backends share a common `BaseVectorStore` interface but differ substantially in implementation: `MilvusVectorStore` uses pymilvus's native server-side BM25 sparse fusion, `PGVectorStore` uses asyncpg with in-memory RRF/weighted fusion and a dedicated background event loop for thread safety, and `Neo4jGraphStore` uses neo4j-graphrag's `SimpleKGPipeline` for LLM-driven entity extraction with graph-aware retrieval via VectorCypherRetriever.

A **uniform URL trust policy** (`ai4rag.utils.network.ensure_safe_url`) enforces that every configurable external endpoint — MaaS, S3, Milvus, Neo4j, pgvector — must use HTTPS unless targeting localhost or a `*.cluster.local` in-cluster service. The library never falls back to unverified TLS; self-signed CA certificates are supported via explicit `ca_bundle`/`ca_cert` parameters.

The starter-kit generator (`ai4rag.assets_generator`) packages the optimized RAG configuration into a deployable FastAPI application with an optional `auth_wrapper.py` that authenticates requests via Kubernetes TokenReview against the K8s API, enforcing HTTPS for the K8s API URL and verifying the cluster CA certificate.
