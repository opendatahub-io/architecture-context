## Purpose

**Short**: ai4rag is an optimization engine for Retrieval-Augmented Generation (RAG) templates that automatically discovers optimal RAG pipeline parameters through hyperparameter optimization.

**Detailed**: ai4rag (AI for RAG) is a Python library that accepts RAG pipeline configurations — including foundation models, embedding models, chunking strategies, retrieval methods, and vector store settings — and systematically evaluates combinations to find the optimal RAG pattern for a given knowledge base and benchmark dataset. It is LLM and vector database provider-agnostic, with built-in integrations for OGX (the default inference and vector store backend) and ChromaDB (for local in-memory evaluation).

The library implements a full AutoML-style optimization loop: users define a search space of RAG parameters, provide benchmark question-answer pairs, and ai4rag explores the parameter space using Bayesian optimization (via Generalized Additive Models) or random search. Each iteration builds a complete RAG pipeline — chunking documents, embedding them, storing in a vector database, retrieving context, and generating answers — then evaluates quality using unitxt metrics (answer correctness, faithfulness, context correctness) and LLM-as-a-Judge scoring. The engine includes model pre-selection to efficiently narrow large model pools before full optimization.

ai4rag is designed for integration into Red Hat OpenShift AI as a component of the RAG optimization workflow. It uses docling-core for document parsing, ogx-client for inference and vector store operations, and supports event-driven result streaming through a pluggable event handler interface (including a Kubeflow Pipelines handler for KFP component integration).

## Architectural Analysis

ai4rag follows a clean layered architecture with clear separation between the optimization engine (`core/`), the RAG pipeline components (`rag/`), and the evaluation framework (`evaluator/`). The library uses abstract base classes extensively — `BaseChunker`, `BaseEmbeddingModel`, `BaseFoundationModel`, `BaseVectorStore`, `BaseEvaluator`, `BaseEventHandler` — making it straightforward to swap implementations. The OGX implementations are the primary production targets, while ChromaDB and local evaluators serve development use cases.

The hyperparameter optimization design is particularly well-structured. The `AI4RAGSearchSpace` class enforces constraint rules (chunk overlap must be less than half chunk size, hybrid chunking requires zero overlap, ranker parameters only apply to hybrid search mode, chunk size must fit within embedding model context length) through composable rule functions. The GAM optimizer uses scikit-learn's LabelEncoder for categorical parameter encoding and pygam's LinearGAM for Bayesian optimization, with a random exploration phase before model-guided search. Results caching avoids re-evaluating identical parameter combinations, and vector store collection reuse prevents redundant embedding operations when only retrieval/generation parameters change.

A notable security concern is the SSL verification fallback in `create_ogx_client()` — when the OGX server presents a self-signed certificate, the client silently falls back to `verify=False` after logging a warning. While pragmatic for development environments, this pattern could mask MITM vulnerabilities in production deployments. The S3 client similarly accepts a `verify` parameter defaulting to `True` but allowing disable. Additionally, the `hashlib.sha256` usage in `AI4RAGChunk` is for deterministic chunk ID generation (not security), so it does not represent a FIPS concern.

The event handler abstraction (`BaseEventHandler`) is the primary integration point for the broader platform. The `LocalEventHandler` writes JSON results to disk, while `KFPEventHandler` aggregates results for Kubeflow Pipelines components. The typed payload structures (`PatternPayload`, `EvaluationRecord`) define a stable contract for downstream consumers. The library also supports threaded parallel inference via `ThreadPoolExecutor` (default 10 threads) for RAG query evaluation, which is the primary concurrency mechanism.

The LLM-as-a-Judge evaluator (`LLMaJEvaluator`) adds a second evaluation dimension beyond traditional metrics. It uses structured JSON output (`response_format` with JSON schema) to extract scores from judge models, includes robust response parsing with markdown fence extraction and single-quote repair, and normalizes 1-5 rubric scores to [0,1]. This design allows evaluation quality to scale with judge model capability while maintaining consistent scoring semantics across evaluator types.
