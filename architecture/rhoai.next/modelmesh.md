## Purpose

**Short**: ModelMesh is a distributed LRU cache and routing layer for high-scale, high-density model serving that runs as a sidecar container alongside model runtime containers.

**Detailed**: ModelMesh acts as a mature, general-purpose model serving management and routing layer designed for high-scale, high-density, and frequently-changing model use cases. It works with existing or custom-built model servers and functions as a distributed LRU cache for serving runtime models. Each ModelMesh instance runs as a sidecar container within a pod, communicating with a colocated model runtime container via a local gRPC connection (TCP port 8085 or Unix Domain Socket).

ModelMesh provides model lifecycle management (register, unregister, load, unload) through a gRPC API, handles intelligent routing of inference requests to the correct model instance across a cluster of pods, manages model placement via an LRU cache eviction strategy, and coordinates state across instances using etcd as a distributed key-value store. Virtual models (vmodels) provide aliasing and zero-downtime model transitions. The framework uses the litelinks library for internal service discovery and inter-instance communication via Thrift RPC, while exposing a gRPC API externally for both management and inference requests.

For full Kubernetes-based deployment and management, ModelMesh is deployed through the [ModelMesh Serving](https://github.com/kserve/modelmesh-serving) controller, which manages ServingRuntimes and InferenceServices as Kubernetes custom resources.

## Architectural Analysis

ModelMesh implements a sophisticated distributed caching architecture for ML model serving that operates as a sidecar alongside model runtime containers. The core design is built around a **ConcurrentLinkedHashMap** (a fork/customization of the Google Guava concurrent LRU map) that serves as the local model cache. When the cache reaches capacity, least-recently-used models are evicted and unloaded from the colocated model runtime. This LRU cache strategy is well-suited for workloads with temporal locality in model access patterns but may underperform for uniform random access patterns.

The **dual-protocol architecture** is notable: externally, ModelMesh exposes a gRPC API (via `ModelMeshApi`) on port 8033 for both model management and transparent inference passthrough. Internally, inter-instance communication uses Thrift RPC via the IBM litelinks framework on port 8080. This split exists because litelinks provides mature service discovery and load balancing features (via etcd/ZooKeeper registration) that predate gRPC's native service mesh capabilities. The litelinks layer handles instance-to-instance routing when a model is loaded on a remote pod — the request is serialized, sent via Thrift to the remote instance, and re-invoked locally there. This adds a serialization/deserialization hop but enables transparent cross-instance routing without external service mesh dependencies.

The **inference passthrough mechanism** in `SidecarModelMesh` is architecturally interesting: ModelMesh acts as a transparent gRPC proxy that intercepts arbitrary inference RPCs (not just its own management API), extracts the model ID from headers or protobuf field paths (configured via `RuntimeStatusResponse.methodInfos`), performs the cache lookup and routing, then forwards the raw gRPC bytes to the model runtime. This is implemented via `ProtoSplicer` which can inject the model ID into specific protobuf field positions without fully deserializing the message, minimizing overhead. The `ByteBuf`-based zero-copy design throughout the inference path (using Netty reference-counted buffers) demonstrates significant optimization for low-latency, high-throughput inference workloads.

The **FIPS compliance gap** is the most significant security finding: Java FIPS mode is explicitly disabled via `-Dcom.redhat.fips=false` in start.sh, and the SunPKCS11 security provider (which enables FIPS on RHEL) is replaced in the JVM security configuration. This means that even on FIPS-enabled clusters, ModelMesh will use non-FIPS-validated cryptographic implementations. The Prometheus metrics endpoint uses a self-signed certificate generated via BouncyCastle (a non-FIPS-validated library). For RHOAI deployments in regulated environments (FedRAMP, FISMA), this gap requires either remediation or a documented exception.

The **model unload retry mechanism** (`UnloadFailure` queue in `ExternalModelLoader`) handles the edge case where the model runtime container becomes temporarily unavailable (e.g., restarts). Failed unloads are queued and retried up to 90 times (~15 minutes) with rate limiting, preventing capacity leaks where loaded models consume memory but are no longer tracked. This defensive design reflects production experience with sidecar container lifecycle races in Kubernetes.
