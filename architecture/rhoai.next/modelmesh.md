## Purpose

**Short**: ModelMesh is a distributed LRU cache and routing layer for serving machine learning models at high scale and density with frequently-changing model sets.

**Detailed**: ModelMesh is a Java-based model serving management and routing framework originally developed by IBM. It acts as a sidecar container that runs alongside model runtime containers (e.g., Triton, MLServer, custom runtimes) in Kubernetes pods. The framework provides distributed coordination via etcd or ZooKeeper, enabling intelligent model placement, loading, unloading, and caching across a cluster of instances.

The core value proposition is that ModelMesh manages far more models than can fit in memory simultaneously. It uses an LRU eviction policy to keep frequently-accessed models loaded while dynamically loading and unloading less-used models. It supports virtual models (vmodels) for zero-downtime model version transitions, multi-model parallelized inference, and detailed Prometheus metrics. The framework communicates with co-located model runtimes via an internal gRPC interface (ModelRuntime) and exposes an external gRPC API (ModelMesh service) for model lifecycle management and inference request routing.

In the RHOAI/ODH platform, ModelMesh is deployed by the modelmesh-serving component (via the modelmesh-controller) as a sidecar container within ServingRuntime pods. The modelmesh-controller manages the Kubernetes-level orchestration (CRDs, deployments, services), while ModelMesh handles the distributed runtime logic within each pod.

## Architectural Analysis

ModelMesh follows a sidecar architecture pattern where each instance runs alongside a model runtime container within the same Kubernetes pod. This design enables the framework to manage model lifecycle (loading, unloading, caching) independently of the specific runtime technology. The internal ModelRuntime gRPC interface provides a clean abstraction that allows any model server (Triton, MLServer, custom Java/Python servers) to participate in the distributed cache by implementing five simple RPCs: `loadModel`, `unloadModel`, `runtimeStatus`, `modelSize`, and `predictModelSize`. Communication between ModelMesh and the co-located runtime can use either TCP (port 8085) or Unix domain sockets (`/tmp/mmesh/grpc.sock`), with UDS being preferred for reduced latency in production.

The distributed coordination layer is built on LiteLinks, an IBM-internal Thrift-based service framework. Each ModelMesh instance registers itself with the KV store (etcd or ZooKeeper) and participates in leader election. The leader drives proactive model placement decisions, while all instances independently handle LRU eviction and request routing. Inter-instance communication uses Thrift on port 8080, with optional TLS/mTLS for secure intra-cluster traffic. The external gRPC API (port 8033) is layered on top via the `ModelMeshApi` class, which translates gRPC requests into the internal Thrift-based model routing system. This dual-protocol design (gRPC externally, Thrift internally) is a legacy of the framework's IBM Watson origins.

A notable architectural feature is the virtual model (vmodel) system, which enables zero-downtime model version transitions. A vmodel maps to an underlying concrete model and supports atomic target switching: the new model version is loaded to the same scale as the current one before traffic is redirected. This is critical for production model serving where version updates must not cause prediction outages. The multi-model parallelization feature (`MM_MULTI_PARALLELISM`, default 4) enables a single inference request to be dispatched to multiple models simultaneously, with results aggregated — useful for ensemble inference patterns.

The FIPS compliance posture has a notable gap: ModelMesh explicitly disables Java FIPS mode (`-Dcom.redhat.fips=false`) in the startup script because enabling FIPS breaks TLS functionality. The SunPKCS11 security provider is reconfigured to use NSS, but the explicit FIPS disable flag means the JVM does not enforce FIPS-validated cryptographic operations. Additionally, the Prometheus metrics server uses self-signed certificates generated via BouncyCastle at startup, and the truststore uses a hardcoded password (`watson15qa`). These represent areas where FIPS and security hardening should be improved for downstream productization. The build is hermetic via Hermeto/cachi2 for Maven artifacts and rpms.lock.yaml for OS packages, though there is no Maven-native lock file committed to the repository.

The payload processing framework (`PayloadProcessor` interface with `RemotePayloadProcessor`, `LoggingPayloadProcessor`, `MatchingPayloadProcessor`, `CompositePayloadProcessor`, and `AsyncPayloadProcessor` implementations) provides a flexible pipeline for intercepting inference request/response data. The `RemotePayloadProcessor` sends payloads to an external HTTP service, enabling centralized logging and audit trails. This is configurable at runtime via the `MM_PAYLOAD_PROCESSORS` environment variable.
