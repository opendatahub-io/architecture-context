## Purpose

**Short**: ModelMesh is a distributed LRU cache and routing layer for high-scale, high-density model serving that runs as a sidecar alongside model runtime containers.

**Detailed**: ModelMesh is a mature, general-purpose model serving management and routing framework originally developed by IBM. It acts as a distributed LRU cache that intelligently manages the loading, unloading, and routing of machine learning models across a cluster of pods. Each ModelMesh instance runs as a sidecar container alongside a model runtime container (e.g., Triton, TorchServe, MLServer), communicating with the runtime over a local gRPC connection (TCP or Unix Domain Socket).

The framework coordinates model placement across the cluster through a distributed key-value store (etcd or ZooKeeper), using leader election, distributed locking, and an eventually-consistent model registry. It handles model lifecycle operations — registration, loading, unloading, and status tracking — while providing transparent routing of inference requests to whichever pod currently has a given model loaded. This enables oversubscription: far more models can be registered than can fit in memory on any single node, with ModelMesh dynamically loading and evicting models based on demand (LRU policy).

ModelMesh also supports VModels (virtual models), which provide an alias/indirection layer enabling zero-downtime model updates by atomically switching the active backing model once a new version is fully loaded. In the RHOAI context, ModelMesh is deployed via modelmesh-serving, which provides Kubernetes-native management through ServingRuntime and InferenceService CRDs.

## Architectural Analysis

ModelMesh's architecture follows a sidecar-per-pod pattern where each pod runs two containers: the ModelMesh Java process (the `mm` container) and a model runtime container. The two communicate over a local gRPC channel — either TCP on port 8085 or a Unix Domain Socket at `/tmp/mmesh/grpc.sock`. This sidecar design means ModelMesh itself defines no CRDs; those are managed by the companion modelmesh-serving controller.

The distributed coordination layer is the most architecturally significant aspect. ModelMesh uses IBM's `litelinks` library for inter-pod RPC (Thrift-based) and service discovery, and IBM's `kv-utils` library for distributed state management backed by etcd or ZooKeeper. The model registry, instance table, VModel mappings, leader election latches, and dynamic configuration all reside in the KV store under a configurable prefix. This tight coupling to the KV store means etcd availability is critical for cluster health — without it, no new model loads or placements can occur, though in-flight inference to already-loaded models continues.

The headless ClusterIP service (`clusterIP: None`) is deliberate: ModelMesh instances discover each other via the KV store rather than DNS, and the Thrift-based litelinks layer handles direct pod-to-pod communication for model forwarding. The external gRPC service on port 8033 is the inference entry point; requests are either served locally (if the model is loaded on that pod) or forwarded to a peer pod that has it loaded.

The FIPS posture is notable: the start script explicitly disables Java FIPS mode (`-Dcom.redhat.fips=false`), and the `java.security` configuration modifies the NSS PKCS#11 provider ordering. The Dockerfile configures `SunPKCS11` provider placement. This is documented as a workaround for TLS breakage when FIPS is enabled, but it means the component does not operate in FIPS mode. The Prometheus metrics endpoint (port 2112) uses Netty with a self-signed certificate via BouncyCastle, adding a non-JDK crypto dependency.

A NetworkPolicy restricts ingress: intra-cluster ModelMesh traffic on ports 8033 and 8080 is limited to pods with matching `app: model-mesh` labels, while port 8033 (inference) and port 2112 (metrics) are open to any source. This is a reasonable baseline but relies on the deployer to further restrict inference access.
