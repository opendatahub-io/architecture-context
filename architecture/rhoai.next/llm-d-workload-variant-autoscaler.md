## Purpose

**Short**: GPU-aware global autoscaler for LLM inference model servers that optimizes replica counts across multiple hardware variants within a Kubernetes InferencePool.

**Detailed**: The Workload Variant Autoscaler (WVA) is a Kubernetes operator that provides intelligent autoscaling for LLM inference deployments. It introduces the concept of "variants" -- multiple model servers in an InferencePool that serve the same base model but differ in hardware configuration (GPU type), serving configuration (tensor parallelism, quantization, max batch size), or both. WVA works alongside standard Kubernetes HPA and KEDA external autoscalers by emitting Prometheus metrics (`wva_desired_replicas`) that drive the scale subresource of inference deployments.

WVA supports three scaling analysis paths: V1 saturation (percentage-based, deprecated), V2 saturation (token/capacity-based, default since v0.9.0), and queueing model (predictive M/M/1/K SLO-based). It computes optimal replica counts by considering GPU availability, KV cache utilization, queue depth, request arrival rates, and configurable cost models. The operator supports both unlimited mode (cost-aware optimization without resource constraints) and limited mode (fair-share GPU allocation with cluster-level or namespace-level quotas). It also supports scale-to-zero for idle models and prefill/decode disaggregated inference pipelines.

The system operates as a read-observe-emit loop: controllers watch HPA/ScaledObject annotations to discover managed workloads, a collector gathers metrics from Prometheus and direct pod scraping, scaling engines analyze metrics and produce decisions, and an actuator emits scaling signals back to Prometheus for external autoscalers (HPA/KEDA) to consume. For scale-from-zero, a separate fast-polling engine directly patches deployment replicas.

## Architectural Analysis

The WVA follows a distinctive read-observe-emit architecture rather than the typical Kubernetes operator pattern of directly reconciling desired state. Controllers are read-only: they watch HPAs, ScaledObjects, ConfigMaps, and InferencePools to populate an in-memory datastore and configuration, but never create or modify the watched resources themselves. Scaling decisions are computed by independent optimization engines running on fixed-interval polling loops, and the results are emitted as Prometheus metrics rather than applied directly. This design decouples the scaling brain (WVA) from the scaling muscle (HPA/KEDA), enabling integration with existing autoscaling infrastructure without replacing it. The only exception is the scale-from-zero engine, which directly patches the Deployment/LWS scale subresource because HPA/KEDA cannot act on zero-replica targets.

The VariantAutoscaling concept is notable for being an entirely in-memory construct. Despite being declared in the kubebuilder PROJECT file as a CRD, no VariantAutoscaling custom resource is installed on the cluster. Instead, VA objects are synthesized at runtime from HPA/ScaledObject annotations (`llm-d.ai/managed: "true"`, `llm-d.ai/variant-cost`, etc.). This annotation-driven discovery pattern avoids introducing a new CRD that users must manage, but it means the operator's state is entirely ephemeral -- a restart re-discovers all managed workloads from scratch. The datastore tracks namespace membership via a "track/untrack" pattern that enables efficient scoping of Prometheus queries and API list calls to only the namespaces with managed workloads.

The multi-analyzer pipeline is the core innovation. V2 saturation analysis uses token-level capacity math (KV cache blocks x block size = total capacity, tokens in use = demand) rather than percentage thresholds, enabling cross-variant comparisons when variants have different GPU memory. The queueing model path uses M/M/1/K queueing theory with online Kalman filter parameter tuning to predict required replicas from SLO targets (TTFT, ITL). Both paths feed into the same optimizer pipeline, which supports either cost-aware (unlimited GPU) or fair-share (constrained GPU) allocation strategies. The universal threshold post-step normalizes analyzer outputs so they can be combined when multiple analyzers are enabled simultaneously.

The GPU limiting subsystem is architecturally layered: an Inventory (TypeInventory for physical GPUs, QuotaInventory for declared quotas) tracks available resources, an AllocationAlgorithm (GreedyBySaturation) distributes GPUs across models prioritizing the most saturated variants, and a DefaultLimiter orchestrates the refresh-usage-allocate-metadata pipeline. The CompositeLimiter enables chaining multiple quota entries (e.g., cluster + namespace quotas) where each successive limiter tightens the constraint space. QuotaInventory supports namespace-scoped quotas with a closed allowlist model, meaning namespaces not listed in the quota config get zero GPU budget.

The OpenShift integration is well-structured through kustomize components. The `openshift` component patches the Prometheus source to point at Thanos Querier (OpenShift's built-in monitoring aggregation layer), mounts the service-ca certificate for proper TLS verification, provisions a long-lived SA token Secret for ServiceMonitor authentication, and labels the namespace for user-workload-monitoring discovery. This is cleanly separated from the base Kubernetes deployment, enabling the same codebase to deploy on vanilla Kubernetes or OpenShift with only a kustomize overlay selection.
