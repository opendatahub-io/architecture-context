## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying OpenDataHub/RHOAI operator dependencies and platform configurations on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: odh-gitops is the canonical infrastructure-as-code repository for the OpenDataHub and Red Hat OpenShift AI platform dependency stack. It provides two primary deployment paths: Kustomize-based layered manifests for installing operator prerequisites (cert-manager, Kueue, Leader Worker Set, RHCL/Kuadrant, observability operators, etc.) on OpenShift, and Helm charts for deploying the full RHAI operator stack on both OpenShift (`rhai-on-openshift-chart`) and non-OpenShift Kubernetes (`rhai-on-xks-chart`) environments including AWS, Azure, and CoreWeave.

The repository does not contain application source code — it is purely a deployment configuration artifact. It defines the complete dependency graph, OLM subscriptions, operator configurations, RBAC policies, CRDs, gateway infrastructure, and TLS provisioning needed to bootstrap the RHOAI/ODH platform. The Helm charts implement a tri-state dependency resolution system (`enabled: auto/true/false`) with profiles (default, rhaii, maas) that allow administrators to deploy purpose-built subsets of the platform (e.g., inference-only or Models-as-a-Service).

The repository is designed for use with GitOps tools (ArgoCD, Flux) and follows a branch-per-version release strategy with version-specific branches (e.g., `odh-3.x`, `rhoai-3.x`) and tags for z-stream releases.

## Architectural Analysis

odh-gitops occupies a distinctive architectural position as the deployment orchestration layer between platform operators and cluster administrators. Rather than implementing runtime behavior, it codifies the dependency graph and installation ordering that the RHOAI platform requires.

The most architecturally significant pattern is the dual-mode Helm chart design. The `rhai-on-openshift-chart` targets OLM-managed environments, generating Namespace, OperatorGroup, and Subscription resources and relying on OLM for operator lifecycle. The `rhai-on-xks-chart` targets vanilla Kubernetes (AWS EKS, Azure AKS, CoreWeave), where it directly deploys the RHAI operator binary, bundles CRDs, and uses post-install hook Jobs to create Platform and component CRs in the correct order. This fork represents a fundamental architectural decision: OLM-based lifecycle on OpenShift versus Helm-native lifecycle everywhere else.

The XKS chart's cloud provider abstraction is notable — a single `providerRegistry` template drives all provider-specific resources (CRDs, RBAC, cloud-manager deployments), and adding a new cloud target requires only one new entry in `_crs-definitions.tpl`. This registry pattern extends to component CRs and platform modules, keeping the chart extensible without template proliferation.

The Kustomize layer uses a component/overlay separation where `components/operators/` provides reusable Kustomize components (Namespace + OperatorGroup + Subscription) and `dependencies/operators/` composes them with patches. Configurations (`configurations/`) apply post-CRD resources that depend on OLM-installed CRDs being available, creating a two-phase installation ordering constraint.

A key risk area is the TLS/certificate infrastructure bootstrapping in the XKS chart. The `create-gateway.sh` and `create-maas-gateway.sh` scripts perform multi-step certificate provisioning through cert-manager, creating CA bundles, Certificates, and Gateway resources with wait loops. This imperative shell-script approach inside Helm hooks is fragile compared to declarative alternatives and creates upgrade complexity, as evidenced by the `pre-upgrade-migrate-certmanager.sh` migration hook for the 3.5→3.6 cert-manager management transition.

The RHAI operator deployment in the XKS chart explicitly disables most platform components via environment variables (`RHAI_DISABLE_*`), deploying a minimal operator that only manages KServe, AIGateway, and their dependencies. This selective-disable pattern means the same operator binary serves both full-platform and XKS deployments, with deployment-time configuration controlling scope.
