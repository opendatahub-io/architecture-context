## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying OpenDataHub/RHOAI platform dependencies and operator configurations on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: The odh-gitops repository serves as the single source of truth for deploying the entire RHOAI/ODH prerequisite stack. It contains two major deployment mechanisms:

1. **Kustomize manifests** (`components/`, `dependencies/`, `configurations/`): A layered kustomize structure for deploying operator subscriptions (cert-manager, Kueue, RHCL/Kuadrant, LeaderWorkerSet, JobSet, NFD, NVIDIA GPU, OpenTelemetry, Tempo, etc.) and their post-install configurations on OpenShift clusters. Each dependency is a kustomize component that can be installed independently or as part of a full stack. The manifests are designed for GitOps tools (ArgoCD, Flux) or direct `kubectl apply`.

2. **Helm charts**: Two Helm charts targeting different deployment environments. The `rhai-on-openshift-chart` installs the ODH/RHOAI operator via OLM and configures `DataScienceCluster` and `DSCInitialization` CRs with profile-based component management (KServe, Dashboard, Kueue, Trainer, Model Registry, etc.). The `rhai-on-xks-chart` deploys the RHAI operator directly (without OLM) on external Kubernetes services (AWS EKS, Azure AKS, CoreWeave), managing the operator Deployment, CRDs, RBAC, Gateway API infrastructure, TLS certificates, and cloud-provider-specific `KubernetesEngine` CRs.

The repository also includes a `contracts/schemas/` directory with JSON Schema definitions for CRDs consumed by the charts (Gateway API, Istio, Kuadrant, KServe, cert-manager, etc.), enabling Helm template validation. Five dependency sub-charts (cert-manager-operator, gateway-api, lws-operator, rhcl-operator, sail-operator) provide non-OLM Helm-based installation of operators for environments without OLM.

**Dockerfile**: N/A (Helm chart, no container image)
**Intent**: Primary Helm chart for deploying RHAI on external Kubernetes services (AWS EKS, Azure AKS, CoreWeave). ## Architectural Analysis

The odh-gitops repository occupies a unique position in the RHOAI/ODH platform architecture — it is not an operator or service, but rather the **deployment configuration layer** that orchestrates the installation and wiring of 12+ operators and their configurations. It bridges two fundamentally different deployment paradigms: OLM-based OpenShift installations and Helm-based vanilla Kubernetes installations.

**Dual-track deployment strategy.** The repository maintains three parallel deployment mechanisms (Kustomize, Helm-OpenShift, Helm-xKS) that all achieve the same end state but via different orchestration. The Kustomize path creates OLM Subscriptions and operator-specific CRs. The OpenShift Helm chart wraps the same OLM patterns in Helm templates with profile-based component management and tri-state dependency resolution. The xKS Helm chart bypasses OLM entirely, directly deploying the operator Deployment, CRDs, RBAC, and using Helm hooks to orchestrate the post-install sequence (KubernetesEngine CR → Platform CR → component CRs → Gateway infrastructure). This tri-modal approach creates a significant maintenance surface — any new dependency must be added in three places.

**Sophisticated dependency resolution in the OpenShift chart.** The `_helpers.tpl` for the OpenShift chart implements a tri-state dependency resolution system (`auto/true/false`) that automatically installs dependencies when components that need them are enabled. This cascades through component → dependency and dependency → dependency chains. Profile defaults (stored in YAML files under `profiles/`) provide baseline configurations (e.g., the `rhaii` profile enables KServe with its minimum required dependencies). This is a custom Helm-native dependency injection system that replaces what OLM's dependency resolution normally handles.

**Cloud-provider abstraction in the xKS chart.** The xKS chart uses a provider registry pattern (`_crs-definitions.tpl`) to abstract cloud-specific KubernetesEngine CRs. Adding a new cloud provider requires only adding an entry to the `providerRegistry` dict — all template logic (hook jobs, RBAC, cleanup) updates automatically. This is a well-designed extensibility pattern, though validation enforces exactly one provider being enabled at a time.

**Gateway API infrastructure as post-install hooks.** The xKS chart deploys substantial infrastructure via Helm hooks rather than static templates — Gateway CRs, TLS Certificates, CA bundle ConfigMaps, and Authorino CA trust configuration. This is architecturally necessary because these resources depend on CRDs and operators that are deployed by the chart itself. The hook-weight ordering (CRs at weight 1, inference Gateway at weight 2, MaaS Gateway at weight 3) ensures correct dependency sequencing. However, hook-based infrastructure is harder to inspect and debug than static resources, and the `before-hook-creation,hook-succeeded` delete policy means failed hooks leave no artifacts for troubleshooting.

**Contract schemas as a validation layer.** The `contracts/schemas/` directory (~85K lines of JSON Schema) provides validation for CRDs consumed by the Helm charts. This enables Helm template rendering to validate resource structures without requiring the CRDs to be installed in the cluster — particularly important for the xKS chart where CRDs are installed by the chart itself. The schemas cover Gateway API, Istio, Kuadrant, KServe, cert-manager, and cloud-provider KubernetesEngine resources.
