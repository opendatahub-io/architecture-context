## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying OpenDataHub/RHOAI dependencies and platform configuration on OpenShift and non-OpenShift Kubernetes (xKS).

**Detailed**: odh-gitops serves as the single source of truth for deploying the complete RHOAI/ODH dependency stack. It addresses administrator-owned prerequisite resources that must exist before the RHOAI/ODH operator can function -- operator subscriptions (via OLM), operator configurations (CRs), and infrastructure dependencies (Gateway API, Istio/SAIL, cert-manager, Kuadrant/RHCL, Kueue, NFD, NVIDIA GPU Operator, etc.).

The repository provides two deployment mechanisms: (1) a Kustomize-based approach for OpenShift clusters where dependencies are managed via OLM Subscriptions applied through `kubectl apply -k`, and (2) Helm charts for both OpenShift (`rhai-on-openshift-chart`) and non-OpenShift Kubernetes (`rhai-on-xks-chart`). The OpenShift Helm chart orchestrates OLM-based operator installation with a tri-state dependency resolution system (`auto`/`true`/`false`), profile-based configuration (`default`, `rhaii`), and automatic transitive dependency resolution. The xKS Helm chart bundles the RHAI operator deployment, cloud manager operators (AWS, Azure, CoreWeave), CRDs, RBAC, webhooks, and post-install lifecycle hooks -- providing a complete non-OLM installation path.

The repository also maintains 78 JSON contract schemas for CRD validation, extensive snapshot-based regression tests (38 snapshots across charts), E2E tests on kind clusters, and Tekton pipelines for OpenShift version validation. A daily GitHub Actions workflow (`update-rhai-xks-bundle.yaml`) automatically updates the xKS chart from the rhods-operator repository, and a sync workflow (`helm-sync.yml`) pushes chart changes to `RHOAI-Build-Config` on release branches.

## Architectural Analysis

**Three deployment paths, one truth**: The repository implements three distinct deployment mechanisms -- raw Kustomize (`kubectl apply -k`), Helm on OpenShift (`rhai-on-openshift-chart`), and Helm on vanilla Kubernetes (`rhai-on-xks-chart`) -- that converge on the same end state: a set of dependency operators installed and configured, plus an RHOAI/ODH operator with its CRs. The Kustomize path is the simplest (static YAML), the OpenShift Helm chart adds dynamic dependency resolution and profiles, and the xKS chart goes furthest by bundling the operator deployment itself since OLM is not available. This layering creates maintenance complexity -- the same operator configuration exists in three forms -- but the `extract-olm-bundle.sh` and `update-bundle.sh` scripts automate template generation from upstream sources to reduce drift.

**Tri-state dependency resolution is the OpenShift chart's key innovation**: The `shouldInstall` helper implements a cascading logic: each dependency can be `auto` (install only if a component needs it), `true` (always install), or `false` (never install). Dependencies can themselves depend on other dependencies (e.g., RHCL requires cert-manager), and the resolution walks the entire dependency graph. Combined with the profile system (`default` = all Removed, `rhaii` = KServe Managed), this allows the chart to serve both full-platform and inference-only installations from the same template set. The three-tier configuration priority (user values > operator-type defaults > profile defaults) ensures administrators can override any decision.

**The xKS chart is an operator-in-a-chart**: Unlike the OpenShift chart which relies on OLM to install the RHOAI operator, the xKS chart bundles the complete operator deployment (Deployment, ServiceAccount, ClusterRole, webhook Service) plus three cloud manager operators (AWS, Azure, CoreWeave). Post-install hooks use Kubernetes Jobs to create CRs (KubernetesEngine, Platform, KServe, AIGateway) and configure Gateway infrastructure (inference gateway + MaaS gateway). The hooks implement a staged approach: hook weight 1 creates CRs, weight 2 creates the inference gateway (with cert-manager CA wait), weight 3 creates the MaaS gateway. All hooks enforce security best practices (non-root uid 65534, read-only filesystem, no capabilities, RuntimeDefault seccomp).

**Contract schemas serve as a CRD validation layer**: The 78 JSON schemas in `contracts/schemas/` define the shape of every CR the charts might create or interact with -- Gateway API resources, Istio CRDs, Kuadrant CRDs, cloud engine CRDs, and more. Combined with the `skipCrdCheck` flag and `crdExists` helper, this enables the charts to gracefully handle CRD-before-CR ordering problems, which is critical for GitOps tools like ArgoCD where all resources are applied simultaneously.

**Release and sync automation**: The repository has two automated pipelines: (1) `update-rhai-xks-bundle.yaml` runs daily to clone rhods-operator, run `make manifests-all` + `make manager-kustomization`, pipe through helmtemplate-generator, and create a PR with updated xKS chart templates; (2) `helm-sync.yml` triggers on push to release branches (`rhoai-X.Y`) and syncs chart directories to `RHOAI-Build-Config/to-be-processed/helm/`. This ensures the xKS chart stays current with operator code changes and release engineering has the latest charts.
