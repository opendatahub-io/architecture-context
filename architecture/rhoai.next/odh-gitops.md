## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying OpenDataHub/RHOAI dependencies and platform configuration on OpenShift and non-OpenShift Kubernetes (xKS).

**Detailed**: odh-gitops serves as the single source of truth for deploying the complete RHOAI/ODH dependency stack. It addresses administrator-owned prerequisite resources that must exist before the RHOAI/ODH operator can function -- operator subscriptions (via OLM), operator configurations (CRs), and infrastructure dependencies (Gateway API, Istio/SAIL, cert-manager, Kuadrant/RHCL, Kueue, NFD, NVIDIA GPU Operator, etc.).

The repository provides two deployment mechanisms: (1) a Kustomize-based approach for OpenShift clusters where dependencies are managed via OLM Subscriptions applied through `kubectl apply -k`, and (2) Helm charts for both OpenShift (`rhai-on-openshift-chart`) and non-OpenShift Kubernetes (`rhai-on-xks-chart`). The OpenShift Helm chart orchestrates OLM-based operator installation with a tri-state dependency resolution system (`auto`/`true`/`false`), profile-based configuration (`default`, `rhaii`), and automatic transitive dependency resolution. The xKS Helm chart bundles the RHAI operator deployment, cloud manager operators (AWS, Azure, CoreWeave), CRDs, RBAC, webhooks, and post-install lifecycle hooks -- providing a complete non-OLM installation path.

The repository also maintains 78 JSON contract schemas for CRD validation, extensive snapshot-based regression tests (38 snapshots across charts), E2E tests on kind clusters, and Tekton pipelines for OpenShift version validation. A daily GitHub Actions workflow (`update-rhai-xks-bundle.yaml`) automatically updates the xKS chart from the rhods-operator repository, and a sync workflow (`helm-sync.yml`) pushes chart changes to `RHOAI-Build-Config` on release branches.

## Purpose

**Short**: GitOps repository providing Helm charts and Kustomize manifests for deploying RHOAI/ODH platform dependencies and configuring the DataScienceCluster stack on OpenShift and non-OpenShift Kubernetes environments.

**Detailed**: odh-gitops is a configuration-only repository that provides two primary deployment paths for the Red Hat OpenShift AI (RHOAI) and Open Data Hub (ODH) platforms. It contains no application source code — instead, it packages Helm charts and Kustomize manifests that install, configure, and wire together the platform's dependency operators (cert-manager, Kueue, RHCL/Kuadrant, Sail/Istio, Leader Worker Set, Job Set, NVIDIA GPU operator, Node Feature Discovery, and others) and the RHOAI/ODH operator itself.

The repository provides two Helm charts: `rhai-on-openshift-chart` for OpenShift clusters using OLM-based operator installation, and `rhai-on-xks-chart` for non-OpenShift Kubernetes (Azure AKS, CoreWeave, AWS EKS) where operators are deployed directly via Helm without OLM. Both charts manage the full lifecycle: operator namespaces, RBAC, Subscriptions or Deployments, DataScienceCluster and DSCInitialization CRs, Gateway API infrastructure (GatewayClass, Gateway, Certificate via cert-manager), cloud manager operators for XKS environments, and post-install hooks that create Kserve CRs and inference gateways. A parallel Kustomize-based path provides the same dependency operator installation for administrators who prefer `kubectl apply -k` or ArgoCD/Flux workflows. The repository also ships JSON schemas for Kubernetes CRDs (contracts/schemas/) used for chart validation, Tekton PipelineRuns for CI cluster validation, and shell scripts for dependency verification, Authorino TLS setup, and Helm chart snapshot testing.

The repository is version-branched per RHOAI/ODH minor release (e.g., `rhoai-3.4`, `odh-3.0`) with tags for z-stream releases. The `main` branch tracks the latest development. The current RHOAI version targeted is 3.5.0-ea.2.

## Architectural Analysis

**Three deployment paths, one truth**: The repository implements three distinct deployment mechanisms -- raw Kustomize (`kubectl apply -k`), Helm on OpenShift (`rhai-on-openshift-chart`), and Helm on vanilla Kubernetes (`rhai-on-xks-chart`) -- that converge on the same end state: a set of dependency operators installed and configured, plus an RHOAI/ODH operator with its CRs. The Kustomize path is the simplest (static YAML), the OpenShift Helm chart adds dynamic dependency resolution and profiles, and the xKS chart goes furthest by bundling the operator deployment itself since OLM is not available. This layering creates maintenance complexity -- the same operator configuration exists in three forms -- but the `extract-olm-bundle.sh` and `update-bundle.sh` scripts automate template generation from upstream sources to reduce drift.

**Tri-state dependency resolution is the OpenShift chart's key innovation**: The `shouldInstall` helper implements a cascading logic: each dependency can be `auto` (install only if a component needs it), `true` (always install), or `false` (never install). Dependencies can themselves depend on other dependencies (e.g., RHCL requires cert-manager), and the resolution walks the entire dependency graph. Combined with the profile system (`default` = all Removed, `rhaii` = KServe Managed), this allows the chart to serve both full-platform and inference-only installations from the same template set. The three-tier configuration priority (user values > operator-type defaults > profile defaults) ensures administrators can override any decision.

**The xKS chart is an operator-in-a-chart**: Unlike the OpenShift chart which relies on OLM to install the RHOAI operator, the xKS chart bundles the complete operator deployment (Deployment, ServiceAccount, ClusterRole, webhook Service) plus three cloud manager operators (AWS, Azure, CoreWeave). Post-install hooks use Kubernetes Jobs to create CRs (KubernetesEngine, Platform, KServe, AIGateway) and configure Gateway infrastructure (inference gateway + MaaS gateway). The hooks implement a staged approach: hook weight 1 creates CRs, weight 2 creates the inference gateway (with cert-manager CA wait), weight 3 creates the MaaS gateway. All hooks enforce security best practices (non-root uid 65534, read-only filesystem, no capabilities, RuntimeDefault seccomp).

**Contract schemas serve as a CRD validation layer**: The 78 JSON schemas in `contracts/schemas/` define the shape of every CR the charts might create or interact with -- Gateway API resources, Istio CRDs, Kuadrant CRDs, cloud engine CRDs, and more. Combined with the `skipCrdCheck` flag and `crdExists` helper, this enables the charts to gracefully handle CRD-before-CR ordering problems, which is critical for GitOps tools like ArgoCD where all resources are applied simultaneously.

**Release and sync automation**: The repository has two automated pipelines: (1) `update-rhai-xks-bundle.yaml` runs daily to clone rhods-operator, run `make manifests-all` + `make manager-kustomization`, pipe through helmtemplate-generator, and create a PR with updated xKS chart templates; (2) `helm-sync.yml` triggers on push to release branches (`rhoai-X.Y`) and syncs chart directories to `RHOAI-Build-Config/to-be-processed/helm/`. This ensures the xKS chart stays current with operator code changes and release engineering has the latest charts.

## Architectural Analysis

The odh-gitops repository represents a critical architectural layer in the RHOAI/ODH platform: the **deployment configuration plane**. It sits between raw operator source code and a running cluster, encoding the decisions about *how* operators are installed, *which* dependencies are wired together, and *what* infrastructure is provisioned. This makes it architecturally significant despite containing no application code.

The **dual Helm chart design** (`rhai-on-openshift-chart` vs `rhai-on-xks-chart`) reflects a key platform strategy: RHOAI's expansion from OpenShift-only to multi-cloud Kubernetes. The OpenShift chart leverages OLM for operator lifecycle management and assumes OpenShift-specific APIs (Routes, SecurityContextConstraints, ImageStreams). The XKS chart bundles operator CRDs, Deployments, and RBAC directly, because non-OpenShift clusters lack OLM. This duality introduces a consistency challenge — changes to operator RBAC or CRDs must be propagated to both charts. The XKS chart mitigates this with `update-bundle.sh` scripts that extract manifests from upstream OLM bundles.

The **tri-state dependency resolution** system (`auto`/`true`/`false`) in the OpenShift chart is a sophisticated design pattern. Rather than requiring administrators to manually track which operators are needed for which components, the chart automatically resolves transitive dependencies — enabling KServe automatically enables cert-manager, RHCL, and optionally Leader Worker Set. The `profile` system adds another layer, with `default` (all Removed) and `rhaii` (inference-only with KServe Managed) profiles that set baseline managementStates. This reduces configuration burden while preserving full override capability.

The **Gateway API infrastructure** in the XKS chart is notable for its complexity. The `create-gateway.sh` post-install hook orchestrates a multi-step process: waiting for Gateway API CRDs, extracting the CA certificate from cert-manager, creating a CA bundle ConfigMap, creating a cert-manager Certificate CR with appropriate DNS SANs, waiting for certificate issuance, and finally creating the Gateway CR with TLS termination. The hook includes cloud-specific annotations (Azure load balancer health probe protocol) and validates issuer readiness. This represents the XKS equivalent of the ingress infrastructure that `rhods-operator`'s gateway controller deploys dynamically on OpenShift.

The **Kustomize parallel path** serves a different audience than the Helm charts. Using Kustomize `Component` resources (not `base`/`overlay`), each operator is a self-contained unit (Namespace + OperatorGroup + Subscription) that can be composed independently via `kubectl apply -k`. This design supports ArgoCD and Flux workflows where Helm is not used. However, the Kustomize path only covers dependency operator installation — it does not generate DSC/DSCI CRs, Gateway API resources, or cloud manager infrastructure, which remain OpenShift or Helm-only concerns.

The **security boundary** between this repository and the operators it deploys is worth noting. This repository configures TLS termination, certificate issuance, webhook admission, and RBAC — but it does not implement any of these. FIPS compliance, for example, is entirely the responsibility of the operator container images. The XKS chart's RBAC (`rhai-operator-role`) grants extremely broad permissions (including `*` on RBAC resources), which is appropriate for a platform operator but represents a significant privilege surface. The mutating webhook intercepts InferenceService and LLMInferenceService creates/updates, providing a control point for platform policy enforcement.
