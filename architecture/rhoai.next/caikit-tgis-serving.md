## Purpose

**Short**: Caikit-TGIS-Serving is a model serving stack that enables Large Language Model (LLM) inference by combining the Caikit AI toolkit with the Text Generation Inference Server (TGIS) backend, deployed as KServe ServingRuntimes on OpenShift.

**Detailed**: Caikit-TGIS-Serving provides the container image and KServe ServingRuntime definitions for serving LLM models on the RHOAI platform. The primary container runs `python -m caikit.runtime` (the Caikit runtime), which provides both gRPC (port 8085) and HTTP (port 8080) inference APIs. In the TGIS-backed configuration, the Caikit runtime acts as a transformer container alongside a TGIS kserve-container that handles the actual model inference on port 8033. In standalone mode, the Caikit runtime uses caikit-nlp directly without TGIS.

The repository ships seven KServe ServingRuntime definitions covering two deployment topologies — caikit-tgis (multi-container with TGIS backend) and caikit-standalone (single-container using caikit-nlp) — each in both gRPC and HTTP variants. These ServingRuntimes are consumed by KServe InferenceService resources that specify model storage locations (typically S3-compatible storage) and route inference requests through the Knative/Istio service mesh. The component depends on the broader KServe, Knative Serving, and Istio Service Mesh stack for traffic routing, autoscaling, and security enforcement.

## Architectural Analysis

Caikit-TGIS-Serving occupies a narrow but critical role in the RHOAI model serving pipeline: it is the translation layer that exposes Caikit-format models through standardized inference APIs while delegating compute-intensive text generation to TGIS. The architecture is fundamentally a two-container sidecar pattern within a single KServe pod — the Caikit transformer container handles API formatting, model discovery (via TGIS-AUTO finder), and health probing, while the TGIS kserve-container manages GPU-bound inference.

The caikit.yml configuration reveals a key design decision: the model management system uses a MULTI finder with TGIS-AUTO priority, meaning model discovery is delegated to TGIS rather than relying on local filesystem scanning. The TGIS backend connection is configured to `localhost:8033` with test_connections enabled, confirming the co-located container architecture.

The repository is primarily a packaging and integration project — it contains minimal application code (a single `utils/convert.py` script for model format conversion) and instead depends on the `caikit`, `caikit-nlp`, and `caikit-tgis-backend` Python libraries for all runtime behavior. This means the architectural surface area of the repository itself is small, but it is the integration point where Caikit's model management, TGIS's inference engine, KServe's orchestration, and the Istio/Knative networking stack meet.

The Konflux Dockerfile uses `registry.redhat.io/ubi9/ubi-minimal-pqc` (Post-Quantum Cryptography UBI variant) with SHA256 digest pinning, indicating awareness of post-quantum security requirements. However, no FIPS build flags or explicit cryptographic configuration exists in the source code — the component inherits its crypto posture entirely from the UBI base image and the Python packages it installs via poetry.

Security enforcement is largely external: Istio PeerAuthentication provides STRICT mTLS between mesh services (with PERMISSIVE mode only on the metrics port 8086), Knative gateways handle TLS termination, and the container runs as non-root user (UID 1001). The repository's demo manifests illustrate the full deployment topology but should not be confused with production configurations — notably, the MinIO demo secret contains hardcoded credentials.
