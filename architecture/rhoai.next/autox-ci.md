## Purpose

**Short**: End-to-end integration test suite and benchmark orchestration framework for AutoX components (AutoRAG, AutoML) running on Red Hat OpenShift AI with Kubeflow Pipelines.

**Detailed**: autox-ci is not a deployed service or operator; it is a pytest-based test framework and benchmark tooling repository that validates AutoX product features against live RHOAI clusters. The test suites exercise AutoRAG (Documents RAG Optimization) and AutoML (tabular and time-series AutoGluon pipelines) by submitting KFP pipeline runs, polling for completion, and asserting on pipeline artifacts stored in S3-compatible object storage. The framework creates Kubernetes resources (DSPA CRs, namespaces, secrets, InferenceServices, ServingRuntimes) as part of test setup and tears them down afterward.

The benchmark side (`autox_benchmarks/`) provides orchestration for AutoRAG quality benchmarks — generating datasets from HuggingFace (BEIR, MKQA, SlideVQA, etc.), uploading them to S3, submitting benchmark pipeline runs, and computing pattern scores. Both halves share utility libraries for KFP client construction, Kubernetes API interaction, S3 data management, and environment-driven configuration.

## Architectural Analysis

autox-ci is structured as two cooperating Python packages — `autox_tests` (functional tests) and `autox_benchmarks` (benchmark orchestration) — sharing a common dependency base through the root `pyproject.toml`. The test package is the primary deliverable, designed to run from CI or as a git submodule in downstream repositories.

The architecture reflects three distinct interaction patterns. First, the test framework acts as a Kubeflow Pipelines API client, creating pipeline runs and polling for completion through the KFP SDK. Second, it acts as a Kubernetes API client, creating and managing OpenShift projects, DataSciencePipelinesApplication CRs, S3 connection secrets, and KServe InferenceServices directly via the Python Kubernetes client. Third, it acts as an S3 client through boto3, uploading test datasets, reading pipeline artifacts, and cleaning up after test sessions.

The DSPA auto-setup pattern is notable: when `RHOAI_KFP_URL` is unset, the test harness creates a DataSciencePipelinesApplication CR in the test namespace, waits for the DSPO operator to reconcile it, discovers the resulting OpenShift Route, and connects through that. This enables one-command test execution from a `.env` file without pre-existing pipeline infrastructure.

TLS verification is intentionally configurable (and defaults to insecure for some connections) because the test targets are typically lab clusters with self-signed certificates. The `score_inference_service` function explicitly disables hostname checking and certificate verification when scoring KServe InferenceServices, which is appropriate for a test harness but would be a vulnerability in production code.

The repository uses a RHEL AI Python Package Index (`console.redhat.com/api/pypi/public-rhai/rhoai/3.5/cpu-ubi9/simple/`) for AutoGluon packages via uv source configuration, tying the test environment to the same package versions shipped in the RHOAI product.

|-----------|-----------|-------------|--------------|
