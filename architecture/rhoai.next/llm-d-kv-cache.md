## Purpose

**Short**: KV-cache indexing and management library for KV-cache-aware routing and cross-node cache coordination in vLLM-based LLM inference platforms.

**Detailed**: The llm-d-kv-cache project provides a comprehensive suite of KV-Cache management capabilities for the llm-d distributed LLM inference platform. The core component is the **KV-Cache Indexer**, a high-performance Go library that maintains a global, near-real-time view of KV-Cache block locality across a fleet of vLLM pods. It is powered by KVEvents streamed from vLLM via ZeroMQ, which provide structured metadata as KV-blocks are created or evicted. This allows the indexer to track which blocks reside on which nodes and on which tier (GPU, CPU, or disk), enabling schedulers to make optimal KV-cache-aware placement decisions.

The repository also contains the **UDS Tokenizer** service, a Python gRPC sidecar that provides tokenization and chat template rendering over Unix Domain Sockets. Additionally, it includes two Python connectors: the **llmd-fs-backend** (a vLLM storage backend for offloading KV-cache blocks between GPU and shared storage, now upstreamed into vLLM v0.23+), and the **PVC Evictor** (a Kubernetes utility that automatically manages disk space for KV-cache storage on PersistentVolumeClaims).

The project serves as both a reusable library (consumed by the llm-d-router scheduler) and a set of deployable sidecar services that run alongside vLLM inference pods. It is a key component in the llm-d platform's architecture for optimizing Time To First Token (TTFT) and throughput through KV-cache reuse.

## Architectural Analysis

The llm-d-kv-cache repository implements a **distributed, event-driven KV-cache coordination system** designed to optimize LLM inference by maximizing cache reuse across a fleet of vLLM serving pods. The architecture follows a clear separation between the write path (event ingestion) and read path (scoring), with the kvblock.Index serving as the central data structure bridging both paths.

**Event Processing Architecture**: The write path uses a sharded worker queue pattern (FNV-1a hash-based routing in `kvevents.Pool`) to ensure ordered event processing per pod while parallelizing across pods. ZMQ PUB/SUB provides the transport layer, with 3-frame messages (topic, sequence number, msgpack payload) enabling reliable delivery. The system supports both vLLM and SGLang engine adapters, each implementing engine-specific msgpack deserialization. The recent addition of map-encoded vLLM event support (commit `7bfda47`) demonstrates active upstream compatibility maintenance.

**Multi-Backend Index Strategy**: The kvblock.Index interface supports four backends with a priority selection order: CostAwareMemory (Ristretto-based with memory-bounded eviction) > Valkey > Redis > InMemory (LRU). The Redis backend uses atomic Lua scripts for consistency, while the cost-aware memory backend tracks live keys separately from the cache to handle Ristretto's asynchronous eviction semantics. This design enables deployment flexibility from single-pod development setups to production clusters with shared state.

**Tokenization as a Sidecar**: The UDS Tokenizer service represents a deliberate architectural choice to move tokenization out of the main Go process into a Python sidecar. This enables using vLLM's OpenAIServingRender directly (which requires PyTorch and transformers), while the Go indexer remains lightweight. The Unix Domain Socket transport eliminates network overhead for pod-internal communication. The gRPC message size limit of 100MB and 2-hour keepalive timeout are tuned for large model tokenization workloads. The service uses lazy model initialization via the `InitializeTokenizer` RPC, allowing a single tokenizer container to serve multiple models.

**PVC Evictor Multi-Process Design**: The PVC Evictor uses an N+2 process architecture (N crawlers + activator + deleter) with inter-process communication via Python multiprocessing Events and Queues. The hex-modulo load balancing distributes cache directories across crawler processes (dividing 16 hex values evenly), while the activator implements hysteresis control (trigger at 85%, stop at 70%) to prevent oscillation. The design includes auto-restart of failed critical processes and graceful shutdown handling -- important properties for a long-running Kubernetes sidecar.

**Security Posture**: The current architecture has minimal security controls -- gRPC services use insecure credentials, ZMQ connections are unencrypted, and health check endpoints are open. This is appropriate for pod-internal communication patterns (UDS, localhost ZMQ) but would need hardening for any cross-node communication. The Konflux-built UDS tokenizer image inherits FIPS-capable crypto from the AIPCC base image, but the upstream Go binary (built via the non-Konflux Dockerfile) lacks FIPS build flags. No Konflux Dockerfile exists for the Go binary itself, suggesting it is consumed as a library rather than shipped as a standalone container in the RHOAI distribution.
