## Purpose

**Short**: Go library and Python sidecar services for KV-cache-aware routing in distributed LLM inference, tracking block residency across a fleet of model-server pods and scoring requests by prefix cache hit ratio.

**Detailed**: The llm-d-kv-cache project provides the core KV-cache indexing infrastructure for the llm-d distributed inference platform. Its primary component is a Go library (`pkg/kvcache`) that maintains a near-real-time, globally consistent view of KV-cache block locality across a fleet of vLLM or SGLang model-server pods. The library is designed to be embedded in a host process -- llm-d's Envoy Processing Plugin (EPP) is the reference consumer -- rather than deployed as a standalone service.

The library operates on two data paths: a **Write Path** that ingests KV-block lifecycle events (stored, evicted, cleared) from model servers via ZeroMQ, and a **Read Path** that scores candidate pods for a given prompt by computing how much of the request's KV-cache prefix each pod already holds. Block keys are derived from token sequences using chained FNV-64a hashes over CBOR-encoded content, with support for multimodal content hashes, LoRA adapter differentiation, and CPU-offloaded blocks.

The project also ships supporting services: a Python gRPC **UDS Tokenizer** sidecar that tokenizes and renders prompts via vLLM's tokenization engine, a **llmd-fs-backend** Python connector for offloading KV-cache blocks to shared storage (POSIX/GDS/S3), and a **PVC Evictor** utility for managing disk space on PVC-backed KV-cache storage. The fs-backend has been upstreamed into vLLM as of v0.23 and is in its final release.

## Purpose

**Short**: Source-backed analysis represents llm-d-kv-cache as Kubernetes Operator / Controller with 3 runtime components, 10 API identities, and 5 integration points.

**Detailed**: llm-d-kv-cache provides the KV cache indexing and tokenization infrastructure for the llm-d disaggregated inference stack. It maintains a real-time index of KV cache blocks stored across vLLM inference engine pods, enabling prefix-aware routing decisions. The component exposes two gRPC service interfaces: an IndexerService (indexer.v1) that scores pods based on KV cache prefix overlap for a given prompt and model, and a TokenizationService that handles tokenization, chat template rendering, and OpenAI-compatible completion rendering. The IndexerService receives KV cache lifecycle events from vLLM engines via ZMQ subscriptions, builds a token-tree index of cached prefixes per pod, and responds to GetPodScores queries from the llm-d routing layer with scores indicating how much of a prompt's prefix is already cached on each pod. The TokenizationService provides model-specific tokenization and chat template rendering via gRPC, supporting both plain text and multimodal content (image_url blocks). The component deploys as a StatefulSet with a Prometheus metrics HTTP server and integrates with Redis/Valkey for distributed KV block storage and OpenTelemetry for trace export.

## Data Flows

- **KV cache event ingestion:** vLLM inference engine pods publish KV cache lifecycle events (block allocations, evictions, clears) over ZMQ. The llm-d-kv-cache component subscribes to these events via a ZMQ events pool, processes them into a token-tree index keyed by pod identity, and stores KV block metadata in Redis/Valkey for distributed access.
- **Pod scoring query path:** When the llm-d routing layer needs to decide which inference pod to send a request to, it calls the IndexerService.GetPodScores gRPC RPC with the prompt text, model name, and candidate pod identifiers. The indexer tokenizes the prompt, walks the token-tree index to compute prefix overlap scores per pod, and returns ranked scores indicating cache hit potential. This enables prefix-aware routing that maximizes KV cache reuse.
- **Tokenization and rendering:** The TokenizationService accepts gRPC requests for tokenization (Tokenize), chat template rendering (RenderChatTemplate, RenderChatCompletion), and completion rendering (RenderCompletion). These RPCs support multimodal content including image_url blocks. The service initializes model-specific tokenizers on demand via InitializeTokenizer.
- **Observability:** The component exports distributed traces to an OpenTelemetry Collector via OTLP/gRPC, with trace context propagation through gRPC server and client calls using otelgrpc instrumentation. Prometheus metrics are exposed via an HTTP /metrics endpoint.
- **Kubernetes integration:** A PodReconciler watches Pod resources via controller-runtime to track pod lifecycle events relevant to KV cache index maintenance.

## Architectural Analysis

The llm-d-kv-cache project exhibits a clean separation between its library core and supporting services, following a **library-first architecture** where the primary value -- the KV-cache indexer -- is designed to be embedded rather than deployed independently. This pattern is unusual in the Kubernetes ecosystem, where most components are standalone services, but it's well-suited for the latency-sensitive scoring path where every network hop adds milliseconds to request routing decisions.

The **dual-key design** is the most architecturally significant pattern in the codebase. The indexer maintains two parallel key spaces -- engine keys (opaque hashes from vLLM/SGLang) and request keys (computed from tokens by the indexer itself) -- bridged by a mapping built during event ingestion. This decoupling means scoring never needs to round-trip to a model server, and the indexer's hash computation is independent of any engine-side hash seed. The downside is that eviction requires the reverse lookup (`engine_key → request_key`), which adds complexity to the index implementation and requires careful lifecycle management (e.g., keeping the mapping alive as long as any tier holds the block during CPU offloading).

The **sharded event processing pool** (`kvevents.Pool`) uses FNV-1a hashing on pod identifiers to route events to dedicated worker queues, guaranteeing per-pod ordering without global locks. This is critical for correctness: a CPU offload `BlockStored` event (which carries no tokens) depends on the preceding GPU `BlockStored` event (which does) having already been processed. The system degrades gracefully on message loss -- a CPU offload event for an unknown engine key is a no-op rather than a crash.

The **pluggable index backend** architecture (in-memory LRU, cost-aware Ristretto, Redis/Valkey) is well-designed but the in-memory backend dominates in practice. Redis/Valkey provides consistency across replicas but is rarely needed since each replica converges independently from the event stream. The Valkey RDMA transport support is experimental and signals a future direction for ultra-low-latency index lookups in HPC environments.

The **UDS tokenizer sidecar** pattern is notable for its use of Unix domain sockets rather than TCP. This avoids network overhead and kernel-level TCP processing for what is a pod-local communication path. The sidecar wraps vLLM's `OpenAIServingRender` to provide tokenization + multimodal feature extraction, which means the sidecar has a large dependency footprint (vLLM, PyTorch, transformers) relative to the simple tokenization task. The gRPC message size limits (100MB max) accommodate large multimodal inputs.

The **fs-backend upstreaming** (`llmd-fs-backend` → vLLM v0.23) is a significant architectural event: the connector that enables cross-node KV-cache sharing via shared storage is now part of vLLM itself. The version in this repo (v0.23) is the final release, and the NIXL-based object storage backend represents the last feature addition before the handoff. Future development continues in vLLM's `TieringOffloadingSpec`.

## Architectural Analysis

The llm-d-kv-cache component occupies a critical position in the llm-d disaggregated inference architecture. It bridges the gap between raw KV cache state scattered across vLLM inference pods and the routing decisions that determine request placement. The core abstraction is a per-pod token-tree index that maps tokenized prompt prefixes to cached KV blocks, enabling O(prefix-length) scoring queries. This design prioritizes lookup speed over storage efficiency, which is appropriate for the latency-sensitive scheduling path.

The component's dependency on ZMQ for event ingestion is notable. ZMQ provides low-latency pub/sub without the operational overhead of a message broker, but it also means events are fire-and-forget with no replay capability. The integration with Redis/Valkey for KV block metadata storage adds a persistence layer, but the index itself appears to be in-memory (using ristretto for caching), meaning pod restarts require re-indexing from incoming events. The StatefulSet deployment model (`deploy/common/statefulset.yaml`) provides stable network identity, which is important for ZMQ subscriptions and for the routing layer to maintain stable gRPC connections to the indexer.

The gRPC API surface is cleanly separated into two services: IndexerService for pod scoring (consumed by the routing layer) and TokenizationService for model-specific text processing (consumed by components that need tokenization without loading model weights). The TokenizationService proto definition supports multimodal content (image_url blocks in ChatMessage), chat template rendering with tool definitions, and OpenAI-compatible completion rendering, suggesting it serves as a shared tokenization sidecar for the inference stack.

A significant architectural observation is the complete absence of application-level authentication on the gRPC services. The example IndexerService server (`examples/kv_cache_index_service/server/main.go:98-101`) creates a gRPC server with only an OpenTelemetry stats handler — no TLS credentials, no auth interceptors, no token validation. The proto definitions carry no auth-related options. The StatefulSet manifest includes no auth sidecar (such as kube-rbac-proxy). This implies the component relies entirely on network-level isolation (Kubernetes NetworkPolicies or namespace boundaries) for access control, which is consistent with its role as an internal infrastructure service within the llm-d pod network but represents a gap if the services become reachable from outside the inference namespace.
