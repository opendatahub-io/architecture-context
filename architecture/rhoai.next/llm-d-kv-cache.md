## Purpose

**Short**: Go library and supporting services for KV-cache-aware routing in distributed LLM inference, maintaining a near-real-time global index of KV-cache block locality across vLLM/SGLang pod fleets.

**Detailed**: llm-d-kv-cache provides the core KV-Cache Indexer library that powers cache-aware routing in the llm-d distributed inference platform. It subscribes to KV-Events streamed from vLLM and SGLang model servers over ZeroMQ, maintaining a global index of which KV-cache blocks reside on which pods and device tiers (GPU, CPU). The indexer exposes a fast scoring API that ranks pods by prefix-cache hit ratio, enabling schedulers to route inference requests to pods that already have the prompt's KV-cache blocks.

The repository is primarily a Go library designed to be embedded in host processes (llm-d-router is the reference consumer). It also contains standalone service examples, a gRPC-based tokenization sidecar service, a PVC evictor for managing disk-based cache storage, and the llmd-fs-backend vLLM offloading connector (now upstreamed to vLLM). The block index supports multiple backends: in-memory LRU, cost-aware memory, Redis, and Valkey (API-compatible with Redis, with experimental RDMA support planned).

Note: As of the analyzed commit, the core KV-Cache Indexer libraries (kvcache, kvblock, kvevents) are being migrated to llm-d-router, and this repository is transitioning to focus on connectors and utilities.

## Architectural Analysis

llm-d-kv-cache is organized around a clean separation between event ingestion (write path) and scoring queries (read path). The write path uses a sharded worker pool that consumes ZMQ messages from model servers; events are routed to workers via FNV-1a hashing of the pod identifier to ensure in-order processing per pod. Engine-specific adapters (vLLM and SGLang) parse msgpack-encoded wire formats into domain events (BlockStored, BlockRemoved, AllBlocksCleared). The read path computes deterministic block keys from token sequences using chained FNV-64a over CBOR-canonical encoding -- reproducing vLLM's prefix caching algorithm -- then looks up which pods hold those blocks and scores them by longest-consecutive-prefix match weighted by device tier.

The pluggable Index interface is the architectural pivot point: the same Indexer orchestrator works against in-memory, Redis, or Valkey backends with no code changes. Redis/Valkey backends use pipelined operations and Lua scripts for atomic index maintenance, making the system suitable for multi-replica deployments without cross-process coordination. The cost-aware memory backend adds LRU-based eviction with per-entry cost tracking for standalone use cases.

The tokenization sidecar (UDS Tokenizer) is a Python gRPC service that wraps vLLM's tokenization and chat template rendering logic, communicating with the Go indexer over Unix Domain Sockets for low-latency intra-pod communication. This decouples the Python tokenization dependency from the Go binary.

A significant architectural decision is the use of ZeroMQ (SUB/PUB) rather than Kubernetes-native eventing for the high-throughput event path. ZMQ provides low-latency, topic-filtered delivery directly from model server pods to the indexer, avoiding the overhead of a message broker. The Kubernetes integration (controller-runtime PodReconciler) is limited to dynamic subscriber management -- discovering and connecting to new pods as they appear.
