## Purpose

**Short**: A reverse proxy sidecar that orchestrates disaggregated prefill/decode (P/D) inference by routing requests between prefiller and decoder vLLM instances.

**Detailed**: The llm-d-routing-sidecar is a lightweight HTTP/HTTPS reverse proxy designed to run as a sidecar container alongside vLLM decoder pods in a disaggregated LLM inference architecture. It intercepts OpenAI-compatible chat completion requests and, when the `x-prefiller-host-port` header is present, coordinates a two-phase prefill-then-decode protocol by first sending the request to a remote prefiller pod and then forwarding the result (with KV cache transfer metadata) to the local decoder.

The sidecar supports three connector protocols: NIXL v2 (default, using structured `kv_transfer_params`), NIXL v1 (deprecated, using flat fields for remote block/engine/host/port), and LMCache (deprecated, using max_tokens=1 truncation). It provides SSRF protection by watching Kubernetes `InferencePool` resources (Gateway API Inference Extension) and maintaining a dynamic allowlist of valid prefiller pod IPs. The proxy also supports TLS termination for its own listener and configurable TLS for upstream connections to both prefillers and the local decoder.

This component is experimental and is noted as planned for removal in a future iteration of the llm-d P/D disaggregation architecture. It ships as a single container image built via Konflux.

## Architectural Analysis

The llm-d-routing-sidecar implements a sidecar proxy pattern for disaggregated LLM inference, where the prefill (prompt processing) and decode (token generation) phases of inference are split across separate vLLM instances. This architecture enables independent scaling of compute-intensive prefill workers and memory-bound decode workers. The sidecar intercepts OpenAI-compatible API requests and transparently coordinates the two-phase protocol, making the disaggregation invisible to clients.

The connector protocol abstraction (`protocolRunner` function type in `proxy.go:93`) cleanly separates the protocol logic from the proxy infrastructure. Each connector (NIXL v1, NIXL v2, LMCache) implements a distinct request transformation flow: LMCache uses a simple max_tokens=1 truncation to force KV cache population, while NIXL v1 passes remote block/engine/host/port fields as flat JSON properties, and NIXL v2 wraps them in a structured `kv_transfer_params` object. The evolution from v1 to v2 reflects a maturing protocol that avoids polluting the top-level completion request schema. Both NIXL v1 and LMCache are marked deprecated in the code.

The SSRF protection mechanism (`AllowlistValidator` in `allowlist.go`) is architecturally notable: it uses Kubernetes SharedInformers with a two-level watch — first watching the InferencePool CR to extract its pod selector, then creating dynamic pod informers for each pool's selector. The allowlist tracks pod IPs and names (not ports), which is a deliberate simplification documented in the README. The 30-second resync period (`resyncPeriod` constant) provides eventual consistency. The validator uses a full allowlist rebuild on every pod change event rather than incremental updates, which is acceptable given the expected small pool sizes (tens of pods, not thousands).

TLS handling is thorough but has a notable asymmetry: the proxy's own listener defaults to TLS-enabled with a restricted cipher suite (six AEAD ciphers, no CBC), while connections to prefillers and the decoder default to plaintext HTTP and require explicit `--prefiller-use-tls` / `--decoder-use-tls` flags. The `InsecureSkipVerify` options for both upstream directions are present for development convenience but represent a security consideration in production. The self-signed certificate fallback (RSA 4096-bit, 10-year validity) is explicitly documented as "for testing" in the CLI help.

The component is explicitly marked as experimental in the README, with a note that it "will be removed in an upcoming iteration of the llm-d P/D disaggregation architecture." This suggests the P/D coordination logic may be absorbed into the EPP (Endpoint Picker Plugin) or the vLLM instances themselves. The Tekton pipeline builds for both `linux/x86_64` and `linux-m2xlarge/arm64` platforms, indicating multi-architecture support.
