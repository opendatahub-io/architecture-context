## Purpose

**Short**: A reverse proxy sidecar that routes disaggregated prefill/decode requests between vLLM workers in the llm-d prefill/decode (P/D) architecture.

**Detailed**: The llm-d-routing-sidecar is a Go-based HTTP/HTTPS reverse proxy designed to run as a sidecar container alongside a vLLM decoder instance. It intercepts incoming inference requests (OpenAI-compatible `/v1/chat/completions` and `/v1/completions` endpoints) and, when a prefiller target is specified via the `x-prefiller-host-port` HTTP header, orchestrates a two-phase prefill-then-decode flow using the NIXL v2 protocol (with deprecated support for NIXL v1 and LMCache).

The sidecar first forwards the request to the specified prefiller pod with modified parameters (e.g., `max_tokens=1`, `kv_transfer_params` with `do_remote_decode=true`), collects the KV cache transfer metadata from the prefiller's response, then forwards the original request augmented with the KV transfer parameters to the local decoder. Requests without a prefiller header are passed through directly to the local decoder.

The component includes optional SSRF (Server-Side Request Forgery) protection that watches Kubernetes `InferencePool` resources (from the `inference.networking.x-k8s.io` API group) to maintain a dynamic allowlist of valid prefill targets. This feature uses the Kubernetes dynamic client with informers to track pods matching the InferencePool's label selectors, restricting prefill forwarding to only pods within the same pool. The component is experimental and is planned to be removed in a future iteration of the llm-d architecture.

## Architectural Analysis

The llm-d-routing-sidecar implements a sidecar proxy pattern for disaggregated prefill/decode (P/D) in LLM inference. The design is intentionally simple: a single Go binary with no framework dependencies beyond the standard library's `net/http/httputil.ReverseProxy` and Kubernetes `client-go` for optional SSRF protection. The proxy intercepts only the OpenAI-compatible completion endpoints (`/v1/chat/completions`, `/v1/completions`) and passes all other traffic directly to the local decoder, making it transparent to non-P/D workloads.

The NIXL v2 protocol implementation (`connector_nixlv2.go`) reveals the core P/D orchestration pattern: the sidecar modifies the original request by injecting `kv_transfer_params` with `do_remote_decode: true`, sets `max_tokens: 1` and disables streaming, sends this to the prefiller, then extracts the KV cache transfer metadata from the prefiller's response and injects it into the decode request. This two-phase request modification is done entirely in-process with buffered response capture via `bufferedResponseWriter`, avoiding any external coordination service. The deprecated NIXL v1 and LMCache protocols follow similar patterns with different field naming conventions.

A notable security design is the SSRF protection via `AllowlistValidator`. Rather than a static configuration, the allowlist is dynamically maintained using Kubernetes informers that watch the `InferencePool` CRD (from the Gateway API Inference Extension project). When a pod matching the pool's label selector is added, its IP is added to the allowlist; when removed, the entire allowlist is rebuilt from the current pod state. This provides defense against request forgery attacks where a malicious `x-prefiller-host-port` header could redirect traffic to unauthorized endpoints. However, the allowlist only validates the host/IP portion and not the port, meaning any port on an allowed host is reachable -- this is documented as intentional in `README.md` but represents a residual risk surface.

The TLS configuration is thorough: the proxy supports TLS for its own listener (with self-signed cert fallback for development), for connections to the decoder, and for connections to prefillers -- each independently configurable. The cipher suite selection is consistent across all three TLS contexts, using only FIPS-approved algorithms (ECDHE + AESGCM/CHACHA20_POLY1305) with TLS 1.2 minimum. The `InsecureSkipVerify` options for decoder and prefiller connections are opt-in flags for development environments.

The component is explicitly marked as experimental (`README.md` line 6: "this project is experimental and will be removed in an upcoming iteration"). The prefiller proxy handlers are cached in an LRU cache (capacity 16) to avoid creating new `httputil.ReverseProxy` instances for repeated requests to the same prefiller. The lack of HTTP timeouts on read/write (`ReadTimeout` and `WriteTimeout` are intentionally unset per `proxy.go:171-172`) is a conscious design decision for LLM inference workloads that may take hours for large contexts, though `ReadHeaderTimeout` (30s) and `IdleTimeout` (5min) are set.

## Architectural Analysis

The llm-d-routing-sidecar follows a sidecar proxy pattern typical of service mesh architectures, but operates at the application layer specifically for LLM inference request routing rather than general-purpose traffic management. Its primary value is intelligent request distribution across inference model-server pods, using an LRU cache to maintain routing state that enables request affinity or balanced distribution strategies. The StatefulSet deployment type (rather than Deployment) ensures stable network identity via ordinal pod naming (`${PROJECT_NAME}-0-0`), which is architecturally relevant for both the RBAC `resourceNames` constraint and for maintaining consistent routing cache state across pod restarts.

A notable design coupling is the use of the platform operator's ServiceAccount (`operator-controller-manager`) rather than a dedicated ServiceAccount. This means the routing sidecar inherits the full Kubernetes API permissions of the platform operator, despite its own RBAC Role only granting `pods/exec` on a single named pod (`${PROJECT_NAME}-0-0`). In practice, the component's effective permissions are the union of its own Role and whatever ClusterRoles are bound to the `operator-controller-manager` SA. This simplifies deployment (no SA provisioning) but creates a tight identity coupling to the platform operator and an over-privileged runtime posture.

The deployment manifests are heavily parameterized with kustomize variables (`${PROJECT_NAME}`, `${IMAGE_TAG_BASE}`, `${VERSION}`, `${NAMESPACE}`), confirming the component is deployed as part of a larger kustomize composition managed by the platform operator rather than as a standalone workload. The OpenShift Route manifest is minimal — no TLS termination block, no authentication annotations, no rate limiting — which indicates that external traffic security is delegated upstream to the platform's Gateway or ingress infrastructure. This is consistent with the RHOAI 3.x pattern where individual component Routes may be supplementary or legacy, with the primary ingress path managed by the platform Gateway controller.
