## Purpose

**Short**: A reverse proxy sidecar that routes LLM inference requests between prefill and decode workers in a disaggregated prefill/decode (P/D) architecture.

**Detailed**: llm-d-routing-sidecar is a Go-based HTTP reverse proxy designed to sit alongside a vLLM decoder instance and orchestrate disaggregated prefill/decode inference. When a request arrives with an `x-prefiller-host-port` header, the sidecar intercepts it, forwards a prefill-only request to the designated remote prefill worker, extracts KV-cache transfer parameters from the prefill response, then constructs and forwards a decode request (with those parameters) to the co-located vLLM decoder. Requests without the prefill header pass straight through to the local decoder.

The component supports three connector protocols -- NIXL v2 (current), NIXL v1 (deprecated), and LMCache (deprecated) -- which differ in how KV-cache transfer metadata is exchanged between prefill and decode stages. An optional SSRF protection feature watches a Kubernetes InferencePool custom resource to build a dynamic allowlist of valid prefill targets (by pod IP and name), rejecting requests to unauthorized hosts with HTTP 403. The sidecar serves TLS by default (using either provided certificates or auto-generated self-signed certificates) and applies explicit AEAD-only cipher suites with a TLS 1.2 minimum version.

The project is marked as experimental and is expected to be removed in a future iteration of the llm-d P/D architecture.

## Architectural Analysis

The routing sidecar follows a straightforward intercepting-proxy pattern. The `http.ServeMux` registers three routes: a health endpoint (`GET /health`), OpenAI-compatible completion endpoints (`POST /v1/chat/completions` and `POST /v1/completions`), and a catch-all passthrough (`/`) that reverse-proxies everything else to the local decoder. The completion handler is the only non-trivial path: it inspects the `x-prefiller-host-port` request header, validates it against the SSRF allowlist (if enabled), then delegates to a connector-specific protocol handler that manages the two-phase prefill-then-decode sequence.

Prefiller reverse-proxy handlers are cached in a 16-entry LRU cache keyed by host:port, avoiding repeated URL parsing and proxy construction for repeat targets. The NIXL v2 protocol handler generates a UUID per request, rewrites the request body to force single-token non-streaming prefill (`max_tokens: 1, stream: false`) with KV transfer parameters, collects the prefill response in a `bufferedResponseWriter`, extracts the `kv_transfer_params` field, then builds the decode request with the original streaming/token settings restored and the KV transfer metadata injected.

The SSRF protection subsystem uses Kubernetes informers (via `client-go` dynamic client) to watch a specific InferencePool resource and the pods matching its label selector. Pod IPs and names are maintained in a thread-safe set; on any pod add/update/delete event, the entire allowlist is rebuilt from the informer stores. The allowlist checks only the host portion of the `host:port` header, meaning any port on an allowed host is permitted -- a design tradeoff documented in the README.

TLS is applied consistently across all three proxy surfaces (server, decoder client, prefiller client), each with the same cipher suite list of six AEAD ciphers and TLS 1.2 minimum. The decoder and prefiller TLS transports optionally support `InsecureSkipVerify` via flags, intended for development environments. The server's self-signed certificate fallback uses 4096-bit RSA keys with a 10-year validity, adequate for testing but not for production deployments where proper certificates should be mounted via the `-cert-path` flag.

The deployment topology uses a StatefulSet (single replica) rather than a Deployment, which is atypical for a stateless proxy. The existing service account (`operator-controller-manager`) suggests this was adapted from an operator scaffold rather than purpose-built for the sidecar pattern. In production, this sidecar would likely be injected as a container within the decoder pod rather than deployed as a standalone StatefulSet.
