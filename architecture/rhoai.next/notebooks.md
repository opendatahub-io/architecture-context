## Purpose

**Short**: Builds container images for interactive data science workbenches (Jupyter notebooks, Code-Server) and pipeline runtime environments used in OpenDataHub and Red Hat OpenShift AI.

**Detailed**: The notebooks repository produces 18 container images spanning three categories: Jupyter notebook workbenches (10 variants), pipeline runtime images (7 variants), and a Code-Server IDE workbench (1 variant). Each variant targets a specific accelerator profile — CPU, NVIDIA CUDA (12.9 or 13.0), or AMD ROCm (7.14) — and includes Python 3.12 with curated data science libraries.

The images are built using self-contained multi-stage Dockerfiles that start from AIPCC base images (`quay.io/aipcc/base-images/*`) and progressively layer JupyterLab, scientific computing libraries (NumPy, Pandas, SciPy, scikit-learn), and ML frameworks (PyTorch, TensorFlow, LLM Compressor, TrustyAI). All Konflux builds are fully hermetic, using cachi2-prefetched dependencies (RPMs and Python wheels) with no network access during build. The repository also maintains kustomize-based ImageStream manifests consumed by the ODH/RHOAI operator to deploy workbench images to OpenShift clusters.

The build system is driven by a Makefile with per-image targets, a `versions_config.yml` for centralized base image version management, and `pylock.toml` / `rpms.lock.yaml` lock files for reproducible builds. CI validation includes unit tests (pytest), container integration tests (testcontainers), and browser tests (Playwright).

## Architectural Analysis

The notebooks repository is architecturally distinctive as a pure container image build repository — it produces no running services, controllers, or operators. Instead, it defines 18 Dockerfile variants that produce workbench and pipeline runtime container images consumed by other platform components. The architecture is fundamentally a build system with deployment manifests.

**Image Hierarchy and Self-Containment**: Each Dockerfile is fully self-contained with no inter-image `FROM` dependencies. Conceptually, images follow a hierarchy (minimal → datascience → pytorch/tensorflow), but each Dockerfile rebuilds all ancestor stages internally from the AIPCC base image. This design ensures any single image can be rebuilt independently without cascading rebuilds, at the cost of duplicated Dockerfile content across variants. The `versions_config.yml` provides centralized version management to keep base image references consistent across all 18 Dockerfiles.

**Hermetic Build Architecture**: The repository demonstrates state-of-the-art supply chain security through fully hermetic Konflux builds. Every dependency layer is locked: RPMs via `rpms.lock.yaml` (rpm-lockfile-prototype), Python packages via `pylock.*.toml` (uv pylock format), npm packages via `package-lock.json` (code-server), and artifacts via `artifacts.lock.yaml` (Hermeto). The `uv pip install` commands use `--no-index --find-links /cachi2/output/deps/pip` to enforce zero network access during builds. This is a model implementation of hermetic builds across multiple dependency ecosystems.

**AIPCC Integration**: All images are built on AIPCC base images with SHA256 digest pinning, ensuring bit-for-bit reproducibility and alignment with Red Hat's secure build infrastructure. The pip/uv configuration is inherited from the AIPCC base layer, and the RHEL AI Python Package Index serves as the authoritative source for all Python wheels. The `base-images/` directory maintains upstream (ODH) variants of these base images for CentOS Stream 9.

**Code-Server Activity Tracking**: The code-server workbench has a notably complex architecture to support the platform's idle culling mechanism. Since code-server lacks JupyterLab's `/api/kernels/` endpoint, the image runs a three-process stack (nginx → httpd → CGI scripts) to synthesize Jupyter-compatible activity tracking responses. This is acknowledged as fragile in the ARCHITECTURE.md and planned for replacement with a single Go reverse proxy. This is the only image that runs multiple processes and exposes multiple ports (80, 8080, 8585).

**Multi-Accelerator Strategy**: The repository maintains three accelerator variants (CPU, CUDA, ROCm) with version-specific considerations. TensorFlow uses CUDA 12.9 while PyTorch uses CUDA 13.0, reflecting the different GPU driver compatibility requirements of these frameworks. ROCm builds include specialized de-vendoring scripts (`de-vendor-torch.py`) and glibc ABI compatibility shims for EL9, indicating significant engineering effort to make upstream AMD GPU libraries work on enterprise Linux.
