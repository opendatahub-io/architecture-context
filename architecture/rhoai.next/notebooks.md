## Purpose

**Short**: Builds containerized Jupyter, Code-Server, and Elyra pipeline-runtime images for the Red Hat OpenShift AI platform, providing interactive data science workbench environments with CPU, NVIDIA CUDA, and AMD ROCm accelerator variants.

**Detailed**: The notebooks component is a container image factory that produces the set of workbench and pipeline runtime images shipped with RHOAI. It is not a deployed service — it does not run controllers, operators, or long-lived daemons. Instead, it provides Dockerfiles, dependency lockfiles, kustomize manifests (ImageStream definitions), and CI tooling that together constitute the build pipeline for user-facing notebook environments.

Each image embeds a self-contained multi-stage Dockerfile that starts from a `${BASE_IMAGE}` build argument and rebuilds every ancestor stage internally. No notebook image inherits from another notebook image at the Docker layer. The repository produces three families of images: **Jupyter workbenches** (JupyterLab with data science libraries and optional GPU frameworks), **Code-Server workbenches** (VS Code in the browser with the same library stack), and **Elyra pipeline runtimes** (headless Python environments for KFP pipeline step execution). Each family comes in CPU, CUDA, and ROCm accelerator variants.

The repository also builds its own base images under `base-images/` (CentOS Stream 9 for ODH, RHEL 9.8 EUS for RHOAI), which configure the RHEL AI Python Package Index (`packages.redhat.com`) for hermetic, supply-chain-secured dependency installation. Images are published through Konflux CI to `quay.io/rhoai/` and `quay.io/opendatahub/` per-image repositories, and are surfaced to users via OpenShift ImageStream manifests consumed by the ODH Notebook Controller.

## Architectural Analysis

The notebooks repository's architecture is defined by three key design decisions: self-contained multi-stage Dockerfiles, accelerator-variant branching at the base image level, and hermetic build enforcement via Cachi2/Hermeto prefetch.

**Multi-stage self-containment.** Each leaf image (e.g., `jupyter/datascience`, `jupyter/pytorch`) embeds the build stages of its ancestors (minimal, baseline) within its own Dockerfile rather than depending on a pre-built parent image. This means changes to an earlier logical stage like `jupyter/minimal` must be propagated to every leaf Dockerfile that embeds that stage. The trade-off is explicit: images are fully reproducible from a single Dockerfile + base image, at the cost of duplicated build logic across ~23 Konflux Dockerfiles.

**Accelerator branching via `${BASE_IMAGE}`.** A single ARG — `BASE_IMAGE` — gates whether an image builds on CPU (CentOS Stream 9 / UBI9), CUDA 12.9/13.0, or ROCm 7.14 foundations. The `build-args/*.conf` files resolve this to a concrete INDEX_URL pointing at the appropriate RHEL AI Python Package Index channel (`cpu-ubi9`, `cuda13.0-ubi9`, `rocm7.14-ubi9`). This architecture means Python dependency sets diverge per accelerator: each variant has its own `requirements.{cpu,cuda,rocm}.txt` and `pylock.{cpu,cuda,rocm}.toml`.

**Hermetic builds.** All Konflux Dockerfiles run without network access. Python wheels, RPMs, and generic artifacts are prefetched by Cachi2 and mounted at `/cachi2/output/deps/`. RPM GPG keys are imported from prefetch output. Lock files (`rpms.lock.yaml`, `pylock.*.toml`) pin every dependency. The code-server image goes further, building VS Code from source using prefetched npm packages and patched build scripts that disable all network fetches.

**Deployment integration.** The repository does not deploy workloads directly. It emits OpenShift ImageStream manifests under `manifests/{odh,rhoai}/` that reference container image digests via kustomize `replacements` from `params.env` ConfigMaps. The ODH Notebook Controller (a separate component) reads these ImageStreams to present available workbench types to users and spawn StatefulSet-backed notebook pods. Version tagging follows the RHOAI release cadence (3.4, 3.5, 3.6, 2025.1, 2025.2), with each ImageStream carrying N through N-3 version tags for rollback support.

**Security posture.** The images run as UID 1001 (non-root), with GID 0 group-writable directories for OpenShift compatibility. Post-quantum cryptography is enabled in base images via `update-crypto-policies --set DEFAULT:PQ`. The `cryptography` (50.0.1) and `pycryptodome` (3.23.0) Python packages are present in workbench images. Authentication is not enforced at the image level — it is the responsibility of the ODH Notebook Controller and the platform's OAuth proxy sidecar.
