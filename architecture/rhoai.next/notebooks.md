## Purpose

**Short**: Builds and publishes container images for interactive data science workbenches (Jupyter notebooks, Code-Server) and Elyra pipeline runtime images for the OpenDataHub and Red Hat OpenShift AI platforms.

**Detailed**: The notebooks repository is a container image factory that produces the workbench images data scientists interact with daily on OpenShift AI. It produces three families of images: (1) Jupyter notebook workbenches in multiple flavors (minimal, data science, PyTorch, TensorFlow, TrustyAI, LLM Compressor) across CPU, NVIDIA CUDA, and AMD ROCm accelerators, (2) a Code-Server (VS Code in the browser) workbench, and (3) pipeline runtime images used by Elyra to execute notebook pipeline nodes remotely.

Each image is built via a self-contained multi-stage Dockerfile that starts from an external `${BASE_IMAGE}` and rebuilds every ancestor stage internally — no notebook image references another notebook image as a FROM source. For RHOAI, base images come from the AIPCC (AI Platform Container Components) pipeline providing RHEL 9.6 EUS with accelerator-specific libraries; for ODH, base images are built from the `base-images/` directory using CentOS Stream 9. The repository also contains the Kubernetes ImageStream manifests that the platform operator deploys to clusters, the Kustomize overlays for ODH and RHOAI distribution variants, and a comprehensive build/CI/test toolchain written in Python.

The images are consumed by the ODH Notebook Controller (which creates pods from Notebook CRs), the ODH Dashboard (which discovers images via ImageStream annotations), and the Elyra pipeline engine (which uses runtime images for pipeline node execution).

## Purpose

**Short**: Container image build definitions for Jupyter, code-server, and runtime notebook/workbench environments shipped in Red Hat OpenShift AI.

**Detailed**: The notebooks repository produces the container images that provide interactive data science workbench environments within RHOAI. It does not contain a running service or operator; instead, each directory tree defines a Dockerfile (or Konflux Dockerfile) plus locked Python requirements that produce a purpose-built OCI image. Image variants span a minimal JupyterLab environment, a full data-science stack with ML frameworks and platform SDKs (KFP, CodeFlare, Kubeflow Training, MLflow, TrustyAI), accelerator-specific builds for CUDA, ROCm, and Intel Gaudi, and a VS Code-based code-server alternative. At runtime these images are instantiated as StatefulSet pods by the odh-notebook-controller (a separate component), which also injects a kube-rbac-proxy sidecar for authentication. The repository's own Go code is limited to a small build-input utility; the architectural significance lies in the curated Python dependency sets and their integration points with the wider RHOAI platform. All packages are sourced from the Red Hat internal PyPI mirror (`packages.redhat.com/api/pypi/public-rhai/rhoai/3.5/…`) and pinned with SHA-256 hashes for supply-chain integrity.

## AIPCC Ecosystems Use

### Accelerator Build Variants

All 18 Konflux Dockerfiles install Python packages via `uv pip install`. The Dockerfiles use a `${BASE_IMAGE}` build arg that is resolved at build time — in RHOAI builds, this resolves to AIPCC base images; in ODH builds, it resolves to the in-house CentOS Stream 9 images from `base-images/`. The Dockerfiles themselves do not hardcode AIPCC image references, but the RHOAI build pipeline injects AIPCC base images via `build-args/konflux.*.conf` files.

The ODH base images in `base-images/` use `aipcc.sh` to replicate the AIPCC system package layout on CentOS Stream 9, providing API-compatible packages (same shared library versions) so that Python wheels built for AIPCC bases also work on ODH bases.

**Intent**: VS Code in the browser via code-server, with nginx reverse proxy for activity tracking. Provides a Jupyter-compatible `/api/kernels/` endpoint via CGI scripts so the notebook controller's idle culler works with non-Jupyter workbenches.

**Language**: TypeScript/JavaScript (code-server), Bash (CGI), Python
**Port**: 80/TCP (nginx → code-server 8888/TCP)

#### Architecture Stack
- **nginx** (port 80) — reverse proxy with JSON access logging for activity tracking
- **httpd** (port 8080) — Apache CGI gateway
- **bash CGI scripts** — `access.cgi` implements `/api/kernels/` by polling code-server heartbeat
- **code-server** (port 8888) — VS Code web IDE

#### Build Stages
1. `rpm-base` — builds code-server from prefetched source (npm ci --offline, release-standalone)
2. `cpu-base` — runtime base with OS packages, Node.js, openshift-clients
3. `codeserver` — final image with code-server, nginx, httpd, Python packages, VS Code extensions
4. `tests` — smoke test stage

These calls use in-cluster service account credentials or user-provided tokens.
- **Notebook → external storage:** The boto3, google-cloud-storage, and minio clients in the datascience and codeserver images enable notebook users to read/write data from S3-compatible and GCS object stores. Credentials are typically provided via environment variables or mounted secrets.

## Architectural Analysis

The notebooks repository has an unusual architecture for a platform component: it is not a running service or operator but rather a container image factory. Its "deployment" is the set of ImageStream manifests that the platform operator deploys to clusters, and its "API" is the set of container images that the notebook controller instantiates as pods. This means the repository's architecture is primarily defined by its build system and Dockerfile hierarchy rather than by runtime service interactions.

The image hierarchy follows a conceptual layer structure (minimal → datascience → pytorch/tensorflow/trustyai) but each leaf Dockerfile is self-contained — it rebuilds every ancestor stage from `${BASE_IMAGE}` rather than depending on a pre-built intermediate image. This design eliminates inter-image build dependencies at the cost of longer build times and duplicated Dockerfile logic across variants. The tradeoff is justified by the need for independent release cycles and the complexity of managing a build DAG across 18 Konflux pipelines.

The hermetic build system is particularly sophisticated. All 18 Konflux Dockerfiles run completely offline using Cachi2-prefetched dependencies (RPMs, Python wheels, npm packages, Go modules, generic artifacts). The `prefetch-input/` directory at the repo root is shared across images via symlinks, with separate RPM lockfiles for ODH (`odh/rpms.lock.yaml`) and RHOAI (`rhds/rpms.lock.yaml`). Python dependencies use a dual lockfile strategy: `pylock.*.toml` for metadata and resolution auditing, `requirements.*.txt` for actual installation. The CVE constraints file (`dependencies/cve-constraints.txt`) applies minimum version pins across all images during resolution, providing a centralized security response mechanism.

The Code-Server workbench has a notably complex architecture compared to the Jupyter variants. Because the ODH Notebook Controller's idle culler expects a Jupyter-compatible `/api/kernels/` API, the Code-Server image implements a three-process stack (nginx → httpd → bash CGI) to fake this API. The ARCHITECTURE.md acknowledges this as "fragile" and planned for replacement with a single Go reverse proxy. This is an architectural debt item worth tracking.

The AIPCC ecosystem integration is indirect but critical. The Dockerfiles use `${BASE_IMAGE}` as a build arg, and the RHOAI build pipeline injects AIPCC base images at build time. The ODH builds use CentOS Stream 9 base images from `base-images/` that replicate the AIPCC system package layout via `aipcc.sh` — a 500-line bash script that installs 100+ system packages to ensure API compatibility with AIPCC-built Python wheels. This creates a tight coupling between the ODH base images and the AIPCC package set that must be maintained in sync.

## Architectural Analysis

The notebooks repository is architecturally unusual within RHOAI: it is a build-time-only component that produces container images but contains no running service, operator, or controller of its own. Its architectural significance resides almost entirely in the curated Python dependency sets that create the user-facing data science workbench experience. The repository follows a matrix build pattern where each notebook variant (minimal, datascience, pytorch, tensorflow, rocm-pytorch, rocm-tensorflow, pytorch+llmcompressor, codeserver) is defined by a directory containing a Dockerfile and a locked `requirements.{cpu,cuda,rocm}.txt` file. This structure allows accelerator-specific images to diverge in ML framework packages while sharing a common Jupyter or code-server base.

The dependency pinning strategy is notable for its rigor. All requirements files use `--index-url` pointing to the Red Hat internal PyPI mirror at `packages.redhat.com/api/pypi/public-rhai/rhoai/3.5/cpu-ubi9/simple/`, and every package line includes one or more `--hash=sha256:` entries. This ensures reproducible, hermetic builds at the Python layer and allows Konflux to verify package integrity during image construction. The requirements files are effectively the component's architecture manifest — they define which platform SDKs, ML frameworks, and database connectors are available to notebook users.

The separation of concerns between this repository and the notebook controller is clean: this repo owns the image content (what runs inside the container), while odh-notebook-controller owns the deployment topology (how the container is scheduled, what sidecars are injected, what routes are created). Authentication is entirely delegated to the platform — the kube-rbac-proxy sidecar injected by the controller handles OAuth/OIDC enforcement before traffic reaches the Jupyter Server process. The Jupyter Server itself uses token-based authentication as a secondary defense layer, but the primary access control boundary is the platform's ingress and auth proxy chain.

The CI test infrastructure (`ci/cached-builds/make_test.py`) reveals the deployment pattern used in testing: each notebook variant is deployed as a StatefulSet in a dedicated namespace using `make deploy9-*` targets, with pod stability checks before validation. The test harness creates Kubernetes namespaces, waits for service accounts, deploys the notebook, waits for pod readiness, runs validation, and tears down — mirroring the lifecycle managed by odh-notebook-controller in production.

The analyzer-generated HTTP endpoint `time.sleep | PATCH` in the APIs Exposed section is a false positive from static analysis encountering `time.sleep()` calls in the CI test script; this repository does not define any HTTP API routes of its own. The actual HTTP surface is provided by Jupyter Server (bundled in the images) and code-server, both of which expose their standard endpoints at runtime. The secrets identified by the analyzer (RENOVATE_TOKEN, JIRA_API_TOKEN, JIRA_TOKEN, JIRA_OAUTH_CLIENT_SECRET) are CI/CD automation credentials used by the repository's Renovate bot and CVE tracking scripts, not runtime application secrets.
