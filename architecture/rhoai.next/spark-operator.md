## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Apache Spark applications on Kubernetes through CRDs for one-shot jobs, scheduled jobs, and interactive Spark Connect sessions.

**Detailed**: The Spark Operator automates submission, monitoring, and scaling of Apache Spark workloads on Kubernetes. Users declare Spark jobs as `SparkApplication` custom resources (one-shot batch), `ScheduledSparkApplication` resources (cron-based recurring jobs), or `SparkConnect` resources (persistent interactive Spark Connect servers). The controller watches these CRDs, creates and manages driver and executor pods, services, configmaps, ingresses, and PodDisruptionBudgets, and tracks application lifecycle through status updates and events.

The operator ships as two independently deployable components: a **workload operator** (controller + webhook in a single binary with separate Deployment manifests) and a **module controller** (`spark-operator-module`) that integrates with the ODH/RHOAI platform orchestrator. The module controller reconciles a cluster-scoped `SparkOperator` CR to manage the lifecycle of the workload operator itself — handling installation, upgrades, RBAC, CRD management, and webhook configuration as a self-contained ODH component module. A mutating webhook intercepts Pod and SparkApplication creation to inject Spark-specific configuration, volume mounts, and scheduling annotations.

## Architectural Analysis

The spark-operator follows a two-tier architecture pattern common in ODH/RHOAI modular components. The lower tier (the workload operator from upstream Kubeflow) handles the Spark-specific domain: reconciling `SparkApplication`, `ScheduledSparkApplication`, and `SparkConnect` CRDs into concrete Kubernetes workloads. The upper tier (the module controller, downstream-specific) wraps the workload operator behind a cluster-scoped `SparkOperator` platform CR, enabling the ODH operator to manage Spark as a pluggable component with uniform lifecycle semantics (`Managed`/`Removed` state, conditions, release status).

The controller and webhook run as separate Deployments from the same binary (`cmd/operator/main.go`), selected by subcommand (`controller start` or `webhook start`). This separation provides independent scaling and failure isolation: the webhook must remain highly available for pod admission while the controller can tolerate brief restarts during leader election transitions. Both components use leader election via Kubernetes Leases for HA.

TLS handling is notable for its OpenShift integration. The operator reads the cluster-wide `APIServer` TLS security profile (`config.openshift.io/v1`) at startup and applies its `minTLSVersion` and cipher suite configuration to both the webhook server and metrics endpoints. On non-OpenShift clusters, it falls back to hardened defaults (TLS 1.2 minimum with Intermediate cipher suite). The webhook self-generates certificates stored in a Kubernetes Secret (`spark-operator-webhook-certs`) unless cert-manager integration is enabled.

The RHOAI overlay deploys the operator in the `redhat-ods-applications` namespace and adds NetworkPolicy resources that restrict Spark pod ingress to internal cluster communication (driver-rpc port 7078, blockmanager port 7079, Spark UI port 4040) and SparkConnect gRPC access (port 15002) from workbench namespaces. The RHOAI overlay also patches the controller ClusterRole with `networkpolicies` verbs so the controller can manage per-application NetworkPolicy resources.

A feature-gated REST submission path (`RestSubmitter`) exists but is disabled by default. When enabled, it submits SparkApplications to an external `k8s-spark-submitter` service via HTTP POST rather than creating driver pods directly. This is a stateless, idempotent integration using client-generated submission IDs.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC aggregation roles (viewer/editor) per CRD type for user access; dedicated SA per operator component | Kubernetes RBAC | Users in allowed namespaces can see/modify all SparkApplications in those namespaces; no per-user scoping within a namespace |
| Data storage | Per-namespace PVCs and ConfigMaps created by Spark apps; no shared persistent storage | Kubernetes namespace isolation | None — data isolation follows namespace boundary |
| Network traffic | NetworkPolicy in RHOAI overlay restricts Spark pod ingress by port and source namespace | Kubernetes NetworkPolicy | NetworkPolicy only covers ingress to Spark pods; no egress restrictions on Spark workloads |
| Compute & resources | ResourceQuota awareness in webhook (lists quotas for validation); no operator-enforced LimitRange | Kubernetes (webhook validates against existing quotas) | Operator does not create or enforce ResourceQuotas; relies on cluster admin to set namespace quotas |
| Configuration & secrets | Per-namespace Secrets for Spark application configs; webhook certs in operator namespace | Kubernetes namespace isolation | None |
| API scoping | Configurable `--namespaces` flag limits watched namespaces; webhook filters by `sparkJobNamespaces` | Application (namespace filter) | Empty `--namespaces` flag means cluster-wide watch; `SparkOperator.spec.spark.jobNamespaces` controls webhook scope with safe default of `["default"]` |
