## Purpose

**Short**: Kubernetes operator that automates Apache Spark application lifecycle management -- submission, scheduling, monitoring, and cleanup -- on OpenShift/Kubernetes clusters.

**Detailed**: The Spark Operator provides three Custom Resource Definitions (SparkApplication, ScheduledSparkApplication, SparkConnect) that abstract away the complexity of running Spark workloads on Kubernetes. Users create CRs to submit Spark jobs, and the operator handles driver/executor pod creation, web UI exposure, Prometheus metrics integration, batch scheduler coordination (Volcano, YuniKorn, kube-scheduler-plugins), and automatic cleanup.

The operator runs as two separate deployments: a **controller** that watches CRs and manages the Spark lifecycle state machine, and a **webhook** server that validates/defaults CRs and mutates Spark pods at creation time to inject volumes, environment variables, sidecars, GPU resources, security contexts, and scheduling configuration from the SparkApplication spec.

For RHOAI/ODH integration, a separate **spark-operator-module** controller bridges the platform operator (rhods-operator/opendatahub-operator) with the Spark workload operator. The platform operator creates a `SparkOperator` CR, and the module controller renders and applies the Spark operator's kustomize manifests using server-side apply. This provides platform-managed lifecycle (install, upgrade, removal) without forking the upstream operator code.

## Architectural Analysis

The Spark Operator follows the Kubeflow upstream operator architecture closely, with a clean separation between the **workload operator** (upstream Spark operator managing SparkApplication CRs) and the **platform module** (spark-operator-module bridging ODH/RHOAI). This two-layer design allows the Red Hat fork to stay close to upstream while adding platform integration without modifying the core operator code. The module controller uses server-side apply with force ownership to deploy and adopt workload operator resources, enabling zero-downtime upgrades.

The workload operator's SparkApplication controller implements a 13-state state machine (`New -> Submitted -> Running -> Succeeding/Failing -> Completed/Failed`, plus suspension and retry states). Each state has a dedicated reconcile function, making the state transitions explicit and testable. The controller supports two submission strategies: **local spark-submit** (default, calls the spark-submit binary directly) and **REST submission** (behind the `RestSubmitter` feature gate, submits to an external k8s-spark-submitter service with mTLS and idempotency). The REST submitter pattern is notable for its full mTLS support, request body size limits (1MB DoS protection), and connection pool management.

The webhook server is architecturally significant -- it performs extensive pod mutation at create time, injecting 23 categories of configuration (volumes, env vars, sidecars, GPU resources, security contexts, scheduling hints, Prometheus config, etc.) from the SparkApplication spec into the driver and executor pods. This "spec-to-pod" translation is the core value proposition of the operator. The SparkConf validator enforces a deny list of restricted Spark configuration keys that could bypass operator-managed settings (e.g., `spark.kubernetes.authenticate.*`, `spark.master`, container image overrides).

The SparkConnect controller (v1alpha1, alpha) adds a new deployment model -- persistent Spark Connect server pods that clients connect to via gRPC on port 15002, rather than the traditional submit-and-wait pattern. The NetworkPolicy in RHOAI/ODH overlays specifically allows gRPC traffic on port 15002 from workbench namespaces labeled with `opendatahub.io/dashboard=true` and `opendatahub.io/workbenches=true`, indicating this is designed for notebook-driven interactive Spark usage. The SparkConnect server pod includes startup and readiness probes on the gRPC port, and tracks executor pods by phase for status reporting.

The AIPCC CPU base image usage in `Dockerfile.konflux` is noteworthy -- the operator image bundles PySpark 4.0.1 and a full Spark distribution (`/opt/spark`) alongside the Go operator binary. This dual-purpose image serves both as the operator runtime and as the Spark execution environment, which is unusual for operators. The image includes Java 17, podman (for catatonit init process), and the AIPCC Python package index. The FIPS build is properly configured with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, though the spark-operator-module-controller Dockerfile uses `CGO_ENABLED=0` without FIPS flags, which could be a check-payload compliance gap.
