## Purpose

**Short**: Kubernetes operator that automates the lifecycle of Apache Spark applications, scheduled Spark jobs, and Spark Connect servers on OpenShift/Kubernetes clusters.

**Detailed**: The Spark Operator watches for three custom resources -- SparkApplication, ScheduledSparkApplication, and SparkConnect -- and automates Spark job submission, monitoring, retry logic, and cleanup. For SparkApplication, the controller manages a 17-state state machine that handles spark-submit execution (locally or via a REST submitter service), driver/executor pod lifecycle tracking, web UI service and ingress creation, Prometheus monitoring configuration, and optional PodDisruptionBudget creation. For ScheduledSparkApplication, the controller implements cron-based scheduling with configurable concurrency policies (Allow, Forbid, Replace) and run history management. For SparkConnect (v1alpha1), the controller provisions a Spark Connect server pod with a gRPC endpoint, along with its ConfigMap (executor pod template) and Service (exposing gRPC, driver RPC, block manager, and web UI ports).

The operator ships as a single binary (`spark-operator`) with two subcommands: `controller` (runs the reconciliation controllers for all three CRDs) and `webhook` (runs mutating/validating admission webhooks for SparkApplication, ScheduledSparkApplication, SparkConnect, and Pod resources). In the RHOAI deployment, these run as separate Deployments in the `redhat-ods-applications` namespace with distinct ServiceAccounts and RBAC. The operator supports pluggable batch schedulers (Volcano, Yunikorn, kube-scheduler) and features configurable via Kubernetes feature gates (PartialRestart, LoadSparkDefaults, RestSubmitter).

## Architectural Analysis

The Spark Operator follows a clean separation between the controller plane and the webhook plane, deployed as two independent Deployments sharing a single binary. This design allows independent scaling and failure isolation -- the webhook must respond quickly to admission requests while the controller handles longer-running reconciliation loops. Both components use leader election to support HA deployment, and both enforce read-only root filesystems with dropped capabilities per OpenShift security best practices.

The SparkApplication controller implements a sophisticated 17-state state machine that handles the complete lifecycle from submission through completion, including retry logic, suspension/resumption, TTL-based garbage collection, and invalidation on spec changes. The state machine is particularly careful about idempotency -- it uses submission IDs to prevent duplicate spark-submit executions and employs merge patches for resource updates to handle filtered cache compatibility during upgrades. The introduction of the REST Submitter feature gate (alpha in v2.6.0) is architecturally significant: it decouples the spark-submit execution from the controller pod itself, enabling submission from a dedicated service with its own resource constraints and mTLS authentication.

The webhook system is comprehensive: it provides both defaulting (setting sensible defaults for Spark configuration) and validation (enforcing resource quotas, denying unsafe sparkConf keys, validating cron schedules) for all three CRDs plus pod mutation. The pod mutating webhook is particularly important -- it intercepts Spark driver and executor pod creation to inject operator-managed configuration (volumes, environment variables, labels, annotations) that couldn't be set through spark-submit alone. The webhook also manages its own TLS certificates, either self-signed (with automatic rotation via a dedicated controller) or delegated to cert-manager.

The RHOAI overlay adds platform-specific concerns: NetworkPolicy for Spark pod isolation (allowing internal Spark communication on ports 7078/7079/4040 and SparkConnect gRPC on 15002 from workbench namespaces), PodMonitor for Prometheus integration, and additional ClusterRole permissions for NetworkPolicy management. The `spark-rbac` configuration provides a separate ServiceAccount, Role, and RoleBinding that must be applied to each application namespace where Spark jobs will run -- this grants driver pods permission to create/manage executor pods without requiring cluster-wide privileges.

The `spark-operator-module` directory contains a separate Go module (`github.com/opendatahub-io/spark-operator-module`) that implements an ODH platform module controller. This controller manages the spark-operator component lifecycle via a `SparkOperatorModule` CRD, using `odh-platform-utilities` and `k8s-manifest-kit` for Helm-based resource rendering and reconciliation. It operates independently from the main spark-operator and is built separately.

One notable FIPS consideration: while the Konflux build correctly uses `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` for the Go binary, the codebase imports `crypto/md5` in `pkg/util/sparkapplication.go` for generating deterministic hash suffixes in pod names. This usage is not security-sensitive (it creates short identifiers, not cryptographic operations), but automated FIPS scanners may flag it. The webhook's TLS configuration is well-implemented -- it reads the OpenShift cluster's TLS profile from the `config.openshift.io/v1 APIServer` resource and applies the same minimum TLS version and cipher suites, falling back to TLS 1.2 with Intermediate ciphers on non-OpenShift clusters.
