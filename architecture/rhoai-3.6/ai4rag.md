## Purpose

**Short**: Provider-agnostic RAG optimization engine that finds optimal hyperparameters for Retrieval-Augmented Generation patterns and generates deployable starter kits.

**Detailed**: ai4rag is an optimization engine for RAG (Retrieval-Augmented Generation) templates, developed by IBM for inclusion in Red Hat OpenShift AI. It accepts a variety of RAG templates and a search space definition, then uses hyperparameter optimization (HPO) — via GAM-based or random search optimizers — to find the best combination of chunking, retrieval, and generation parameters for a given evaluation metric.

The component operates primarily as a Python library (`pip install ai4rag`) consumed by data scientists through notebooks or programmatic APIs. Its `AI4RAGExperiment` class orchestrates the full optimization loop: document ingestion (via docling), chunking, vector store indexing, retrieval, generation, and evaluation (using RAGAS or Unitxt). It supports four vector store backends (Milvus, Milvus Lite, PostgreSQL/pgvector, Neo4j) and reaches LLM and embedding models through the OpenAI SDK, making it compatible with any OpenAI-compatible endpoint including OpenShift AI Models-as-a-Service (MaaS).

After optimization, ai4rag generates deployable "starter kit" archives — self-contained FastAPI applications (the agentic RAG template) with an OpenAI-compatible Responses API, a Containerfile for OpenShell sandbox deployment, and Kubernetes auth integration. These starter kits carry the optimized configuration (model IDs, prompts, retrieval parameters) and can be deployed as inference services.

## Architectural Analysis

ai4rag has a two-layer architecture: a library layer for experimentation and optimization, and a generated application layer for serving optimized patterns.

**Library layer.** The core is `AI4RAGExperiment`, which orchestrates the optimization loop. It composes several pluggable subsystems: RAG templates (`SimpleRAG`, `AgenticRAG`), vector store backends (Milvus, Milvus Lite, pgvector, Neo4j), foundation models and embedding models (via the OpenAI SDK), chunking strategies (docling-based and LangChain-based), and evaluators (RAGAS, Unitxt, LLM-as-Judge). The HPO layer sits above the RAG pipeline, iterating over a search space of hyperparameters using either GAM-based Bayesian optimization or random search.

**Security model.** The library enforces a consistent URL trust policy through a central `ensure_safe_url()` function in `ai4rag.utils.network`: plaintext HTTP is only permitted against localhost or `*.cluster.local` addresses; all other endpoints must use HTTPS with certificate verification. This policy is applied uniformly across MaaS, S3, Milvus, Neo4j, and pgvector connections. The recent removal of unverified-TLS fallback in the vector store layer (commit 120e455) tightened this further. Custom CA certificates are supported for all backends (via `ca_cert` parameters or environment variables like `MAAS_CA_BUNDLE`), enabling disconnected/private-CA deployments without weakening verification.

**Starter kit layer.** The `generate_starter_kit()` function produces a zip archive containing a FastAPI application implementing the OpenAI Responses API (`/v1/responses`) with an optional Kubernetes TokenReview authentication wrapper. The auth wrapper (`auth_wrapper.py`) validates Bearer tokens via the Kubernetes `authentication.k8s.io/v1` TokenReview API and restricts access to protected paths. This is deployed as an OpenShell sandbox container.

**Provider agnosticism** is a deliberate design choice: all model interaction goes through the OpenAI Python SDK, so any OpenAI-compatible endpoint (vLLM, TGI, Ollama, MaaS) works without code changes. Vector store backend selection is driven by a `provider` discriminator with frozen dataclass configs that self-construct from environment variables, keeping secrets out of generated artifacts.
