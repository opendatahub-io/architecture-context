## Purpose

**Short**: Community-contributed evaluation framework adapters that integrate third-party LLM evaluation tools with the eval-hub service.

**Detailed**: eval-hub-contrib is a collection of 12 independent evaluation framework adapters, each packaged as a container image that runs as a Kubernetes Job orchestrated by the eval-hub service. Each adapter implements the `FrameworkAdapter` pattern from the evalhub-sdk, wrapping an external evaluation framework (LightEval, Inspect AI, DeepEval, RAGAS, SWE-bench, GuideLLM, MTEB, IBM CLEAR, RULER, WildGuard, IFBench, NeMo Guardrails) and translating its outputs into eval-hub's standardized `JobResults` format.

The adapters are not long-running services — they are ephemeral container workloads that execute a single evaluation job and terminate. The eval-hub service schedules them as Kubernetes Jobs, passing configuration via mounted ConfigMaps and receiving results through the evalhub-sdk callback mechanism. The repository also contains evaluation collections — pre-defined YAML files that group related benchmarks with scoring weights and pass criteria for composite evaluation workflows.

## Architectural Analysis

eval-hub-contrib follows a strict plugin architecture: every adapter is a self-contained Python application in its own `adapters/<name>/` directory with a `main.py` entry point, `requirements.txt`, `provider.yaml` (adapter registration manifest), and either a `Containerfile` (community build) or `Dockerfile.konflux` (production Konflux build). The adapters share no code between themselves — each is independently buildable, testable, and deployable.

The core contract is simple: each adapter subclass of `FrameworkAdapter` implements `run_benchmark_job(config, callbacks) -> JobResults`, reporting progress through a fixed lifecycle (`INITIALIZING` → `LOADING_DATA` → `RUNNING_EVALUATION` → `POST_PROCESSING` → optionally `PERSISTING_ARTIFACTS` → `COMPLETED`). The underlying evaluation frameworks are typically invoked via subprocess CLI calls or Python library APIs, and the adapter's role is to translate configuration, invoke the framework, and normalize results.

The SWE-bench adapter is architecturally distinct from the others: it creates child Kubernetes Jobs (one per evaluation instance) rather than running evaluation locally, which requires dedicated RBAC. The `anyuid` SCC binding is needed because SWE-bench container images require root for file permission fixups in init containers.

Only two adapters — Inspect AI and LightEval — have Konflux Dockerfiles for production builds; the remaining adapters use community Containerfiles. This means only these two are currently built through the Konflux/Tekton CI pipeline for RHOAI release integration. The Tekton pipeline definitions are externally managed by the `konflux-central` repository and synchronized automatically.

The Inspect AI adapter is the most feature-rich, exposing 75+ benchmarks across alignment auditing (Petri/Bloom from Meridian Labs), safety, coding, math, knowledge, telecom, and agent evaluation categories. It supports multi-model role assignment (target, auditor, judge, scenarios, realism) for adversarial alignment auditing scenarios.
