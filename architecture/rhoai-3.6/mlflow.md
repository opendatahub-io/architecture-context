## Purpose

**Short**: MLflow is an open-source ML lifecycle platform deployed in RHOAI as a shared experiment tracking, model registry, and artifact management service with Kubernetes-native workspace isolation and RBAC enforcement.

**Detailed**: MLflow provides experiment tracking, model versioning, LLM tracing, model evaluation, and artifact storage for the RHOAI platform. In the RHOAI deployment model, MLflow runs as a single shared service managed by the MLflow Operator. The server is configured with the `kubernetes-auth` application plugin (provided by `mlflow-kubernetes-plugins`) and the `kubernetes://` workspace store, which maps Kubernetes namespaces to MLflow workspaces and enforces RBAC via `SelfSubjectAccessReview` on `mlflow.kubeflow.org` pseudo-resources.

The server exposes a broad HTTP API surface covering experiment/run management, model registry, artifact upload/download, an AI gateway for LLM endpoint proxying, an assistant chat interface, MCP server federation, and job execution. The React-based UI is bundled into the container image and served from the same process. In RHOAI, users and SDK clients reach MLflow through the ODH data science gateway's `/mlflow` endpoint, with workspace context carried in the `X-MLFLOW-WORKSPACE` header.

## Architectural Analysis

MLflow's RHOAI deployment is architecturally notable for its plugin-based authentication model. The upstream codebase ships no authentication middleware on its FastAPI/Flask surfaces; instead, the `--app-name` CLI flag selects an application plugin at startup. The RHOAI Dockerfile hardcodes `--app-name kubernetes-auth`, which activates the `mlflow-kubernetes-plugins` package (v1.6.0, installed separately from PyPI via Konflux prefetch). This plugin registers a FastAPI middleware that extracts bearer tokens from incoming requests and performs Kubernetes `SelfSubjectAccessReview` checks against `mlflow.kubeflow.org` API group resources, delegating all authorization decisions to Kubernetes RBAC rather than maintaining a separate permission database.

The workspace model is the core multi-tenancy primitive. The `kubernetes://` workspace store URI causes MLflow to treat Kubernetes namespaces as workspaces: it list/watches namespaces via the Kubernetes API and optionally reads namespace-scoped `MLflowConfig` custom resources for per-workspace artifact storage overrides. This design means MLflow does not own namespace lifecycle — projects are created externally by the platform — and workspace isolation is enforced per-request through the combination of the `X-MLFLOW-WORKSPACE` header, Kubernetes RBAC checks, and workspace-scoped SQLAlchemy queries that filter experiments, runs, models, and artifacts by workspace.

The container image uses a multi-stage build: a Node.js stage compiles the React UI with Yarn Berry, a Python builder stage produces wheels for `mlflow`, `mlflow-skinny`, `mlflow-tracing`, and `mlflow-kubernetes-plugins`, and the final stage is based on `ubi9/ubi-minimal-pqc` (post-quantum cryptography variant). Python dependencies are installed from the RHOAI AIPCC package index with hash verification (`--require-hashes`). The image disables telemetry, job execution, the AI assistant, and the AI gateway by default via environment variables, reflecting the RHOAI-scoped feature set.

The Helm chart shipped in `charts/` provides a production-ready deployment template with configurable TLS (via `--ssl-keyfile`/`--ssl-certfile` passed to uvicorn), NetworkPolicy, ServiceMonitor, RBAC, PVC storage, and garbage collection CronJob. Probes hit `/health` on the configured port. The chart defaults to a single replica with `Recreate` strategy when using ReadWriteOnce storage, and supports `RollingUpdate` for multi-replica deployments with a PostgreSQL backend.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Bearer token + SelfSubjectAccessReview per workspace | Kubernetes (via kubernetes-auth plugin) | Authorization is Kubernetes-native; no application-level permission bypass possible without valid K8s credentials |
| Data storage | Workspace-scoped SQLAlchemy queries; all experiments, runs, and models filtered by workspace column | Application (SQLAlchemy ORM) | Application-enforced data isolation — a bug in workspace query filtering could leak cross-workspace data |
| Network traffic | Optional NetworkPolicy in Helm chart; no per-tenant network isolation | Kubernetes (when NetworkPolicy enabled) | NetworkPolicy not enabled by default; all tenants share the same pod network path |
| Compute & resources | Single shared deployment; no per-tenant resource limits | Kubernetes (Pod-level limits only) | One tenant's heavy API usage can impact others; no per-tenant rate limiting beyond optional slowapi |
| Configuration & secrets | Per-namespace MLflowConfig CRD for artifact storage overrides | Kubernetes (CRD per namespace) | Database credentials shared across all tenants (single backend store URI) |
| API scoping | Namespace-scoped workspace context from X-MLFLOW-WORKSPACE header; kubernetes-auth validates access | Kubernetes + Application | Workspace header is trusted after RBAC check; no secondary application-level access control |
