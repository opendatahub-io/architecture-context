## Purpose

**Short**: OpenShift operator that manages the lifecycle of the Kueue workload queuing system for Kubernetes-native job scheduling and resource quota management.

**Detailed**: The kueue-operator is an OpenShift-native operator that deploys and manages [Kueue](https://kueue.sigs.k8s.io/) (v0.10.2/release-0.11), a Kubernetes-native system for managing quotas and job scheduling. It follows the two-tier operator pattern: the operator itself (`openshift-kueue-operator` deployment) watches a singleton `Kueue` CR (`kueue.openshift.io/v1`) and reconciles the operand — the `kueue-controller-manager` deployment — along with all supporting resources (CRDs, RBAC, webhooks, services, network policies, cert-manager certificates, and monitoring).

Kueue provides cluster-level resource quota management through ClusterQueues, namespace-scoped LocalQueues, and Workload abstractions. The operator translates a high-level `Kueue` CR configuration — specifying which job frameworks to integrate with (BatchJob, PyTorchJob, RayJob, etc.), gang scheduling policy, preemption strategy, and workload management settings — into the full operand deployment. The operand uses extensive mutating and validating admission webhooks to intercept workload creation across 14 supported framework types, injecting Kueue queue labels and enforcing admission policies. An opt-in namespace labeling mechanism (`kueue.openshift.io/managed=true`) scopes webhook enforcement to designated namespaces.

The operator requires cert-manager as a prerequisite, using it to provision TLS certificates for webhook and metrics endpoints. It deploys a comprehensive set of NetworkPolicies implementing a default-deny posture with targeted allowances for API server egress, webhook ingress, DNS, metrics scraping, and the visibility API server.

## Architectural Analysis

The kueue-operator exhibits a clean separation between operator and operand concerns. The operator binary (`cmd/kueue-operator`) is built using OpenShift's `library-go` controller infrastructure (`controllercmd`, `v1helpers`), while the operand (kueue controller-manager) is the upstream Kueue controller image from `openshift/kubernetes-sigs-kueue`. The operator's `TargetConfigReconciler` (1372 lines) is the central reconciliation loop that materializes the entire operand stack from embedded `bindata/` assets, applying spec-driven parameterization (integration frameworks, gang scheduling mode, preemption policy) to a ConfigMap-based controller configuration.

The webhook surface is the most architecturally significant aspect: 17 mutating and 18 validating webhooks intercept creation and updates across all supported workload types (Jobs, JobSets, Pods, Deployments, StatefulSets, RayClusters, RayJobs, PyTorchJobs, MPIJobs, PaddleJobs, TFJobs, XGBoostJobs, AppWrappers, LeaderWorkerSets, ClusterQueues, ResourceFlavors, Workloads, and Cohorts). All webhooks use `Fail` failure policy, meaning Kueue unavailability blocks workload creation in managed namespaces — a deliberate correctness-over-availability trade-off. The namespace opt-in mechanism mitigates blast radius by limiting webhook scope to labeled namespaces.

The visibility API server (port 8082) exposes a Kubernetes-style aggregated API for querying pending workloads in ClusterQueues and LocalQueues, registered through an APIService resource. This provides operational visibility into queue depths without requiring direct CR listing. The metrics endpoint (port 8443) uses cert-manager-provisioned TLS with a ServiceMonitor configured for Prometheus scraping, including mTLS verification (`InsecureSkipVerify: false`, explicit CA, cert, and key references).

The network security posture is notably strict: a deny-all NetworkPolicy applies to both operator and operand pods (selected by `app.openshift.io/name: kueue`), with targeted allowances only for Kubernetes API egress (port 6443), cluster DNS (port 53), webhook ingress from the API server namespace, metrics ingress from the monitoring namespace, and visibility API ingress. This defense-in-depth approach limits the attack surface even in the event of pod compromise.

The operator deployment runs with 2 replicas and `system-cluster-critical` priority for high availability. The operand runs with 1 replica by default. Both deployments enforce strict security contexts: `runAsNonRoot`, `readOnlyRootFilesystem`, `RuntimeDefault` seccomp profile, and dropped capabilities.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC roles per workload type (batch-admin, batch-user, editor/viewer roles); namespace-scoped watches for workloads | Kubernetes RBAC | ClusterQueues and ResourceFlavors are cluster-scoped — admin access grants cross-tenant visibility |
| Data storage | No persistent data storage; state is in Kubernetes CRs scoped per namespace (Workloads, LocalQueues) | Kubernetes namespace isolation | None — stateless controller |
| Network traffic | Default-deny NetworkPolicy with explicit allowances for API server, DNS, webhook, metrics, and visibility | Kubernetes NetworkPolicy | Webhook traffic from API server to operand pod is intra-namespace |
| Compute & resources | ResourceQuota enforcement delegated to ClusterQueue/ResourceFlavor configuration by platform admin | Kueue application logic + Kubernetes scheduler | Misconfigured ClusterQueue can over-allocate resources |
| Configuration & secrets | TLS secrets scoped to operator namespace; operator ConfigMap per deployment | Kubernetes namespace isolation | None |
| API scoping | LocalQueues are namespaced; Workloads are namespaced; webhook opt-in via namespace label | Kubernetes + Kueue webhooks | Cluster-scoped CRDs (ClusterQueue, Cohort) require cluster-admin for modification |
