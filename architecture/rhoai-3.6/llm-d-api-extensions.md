## Purpose

**Short**: Python library providing read-only server introspection HTTP endpoints for vLLM, used by llm-d for routing and scheduling decisions.

**Detailed**: llm-d-api-extensions is a Python package that extends vLLM inference servers with introspection endpoints that expose server configuration, hardware device properties, and KV cache capacity. The llm-d inference gateway needs this data to make intelligent routing and scheduling decisions — knowing which model is served, what parallelism settings are active, how much KV cache headroom remains, and what GPU hardware each rank is running on.

The package integrates through vLLM's `vllm.endpoint_plugins` entry point framework and the `--worker-extension-cls` mechanism, requiring no fork or patch of vLLM core. Each plugin is opt-in: vLLM only loads plugins explicitly named in the `VLLM_PLUGINS` environment variable, so installing the package alone changes nothing about a server's behavior. The design is server-agnostic at the top level — the `vllm/` directory holds the vLLM-specific package, and sibling directories could be added for other inference servers (e.g., SGLang) once they expose comparable extension points.

All three endpoints are read-only GET routes that cache their responses at startup (the underlying data — launch config, device properties, post-profiling KV cache state — is immutable for the server's lifetime). This makes the endpoints essentially zero-cost at request time, serving pre-built Pydantic models from FastAPI application state.

## Architectural Analysis

The extension architecture is well-designed around two vLLM extension points. The `vllm.endpoint_plugins` entry point registers FastAPI routes, while `--worker-extension-cls` injects a mixin class into vLLM workers for cross-rank device introspection via `collective_rpc`. This layered approach cleanly separates the control plane (HTTP endpoints on the API server) from the data plane (per-worker device queries).

The plugin lifecycle follows a two-phase pattern: `attach_router` registers routes on the FastAPI app, then `init_state` runs once at startup to build and cache the response. The `required_tasks` field controls eligibility — the config plugin sets it to `None` (works everywhere, including the CPU-only render server), while the devices and KV cache plugins restrict to generation/pooling tasks that guarantee an engine is present. Graceful degradation is a first-class concern: missing worker extensions, absent engine clients, and pre-#48121 vLLM builds all result in 503 responses with specific error details rather than crashes.

The KV cache group schema is a discriminated union keyed on `kind`, modeling ten distinct attention/state group types (full attention, MLA, sliding window, Mamba, cross-attention, etc.). This forward-looking schema correctly handles hybrid models with heterogeneous layer types — architecturally significant for llm-d's capacity planning since different group types have different memory footprints.

A notable security consideration: `kv_connector_extra_config` may contain operator credentials. The config plugin redacts all values by default, requiring an explicit `LLM_D_INTROSPECTION_EXPOSE_KV_EXTRA_CONFIG=1` environment variable to expose them. This is documented but worth noting since the introspection endpoints are unauthenticated.
