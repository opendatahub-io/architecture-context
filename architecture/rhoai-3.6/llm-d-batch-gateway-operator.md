## Purpose

**Short**: A Kubernetes operator that manages the lifecycle of LLM batch gateway deployments by reconciling a single `LLMBatchGateway` custom resource into a full set of Kubernetes workloads rendered from embedded Helm charts.

**Detailed**: The llm-d-batch-gateway-operator is a controller-runtime-based operator that translates a declarative `LLMBatchGateway` CR into a complete batch inference gateway deployment. Each CR produces up to four sub-components: an API server (HTTP batch job submission), a request processor (sync or async dispatch to inference backends), a garbage collector (expired job/file cleanup), and an optional async-processor (Redis-queue-based async dispatch). The operator embeds two Helm charts (`batch-gateway` and `async-processor`) and renders them at runtime by converting the CR spec into Helm values, then applies the resulting Kubernetes objects via Server-Side Apply with owner references for lifecycle management.

The operator implements cross-namespace secret resolution using Gateway API `ReferenceGrant` resources, enabling credentials stored in a central namespace to be securely referenced by CRs in workload namespaces. It integrates with the OpenShift cluster TLS profile (`config.openshift.io/APIServer`) to enforce platform-consistent TLS settings across both the operator's own metrics endpoint and the Helm-rendered workloads. A dedicated `MetricsController` ensures the operator's own Service, ServiceMonitor, and PrometheusRule resources remain self-healing. The operator supports both ODH and RHOAI distributions via kustomize overlays that differ only in target namespace (`opendatahub` vs `redhat-ods-applications`).

## Architectural Analysis

The operator follows a Helm-rendering controller pattern rather than the more common template-per-resource approach. The `HelmRenderer` loads embedded charts at startup, and each reconciliation converts the CR spec into a Helm values map (`specToHelmValues()`), renders the chart into `unstructured.Unstructured` objects, sets owner references, and applies them via Server-Side Apply. This design delegates workload structure entirely to the upstream `batch-gateway` and `async-processor` Helm charts, meaning the operator's resource footprint is determined by chart templates rather than Go code. The `managedGVKs` list enumerates all possible resource types for orphan cleanup, which must be kept synchronized with the charts.

The cross-namespace secret pattern is noteworthy: when `secretRef.namespace` differs from the CR namespace, the controller checks for a `ReferenceGrant` in the source namespace, copies the Secret into the CR namespace under a managed name, and treats `secretRef` as immutable after the first copy. This prevents credential confusion after initial provisioning while enabling centralized secret management. The `secretWatchFilter` ensures the cluster-wide Secret watch only triggers reconciles for tracked cross-namespace secrets, reducing unnecessary reconciliation.

TLS configuration is cluster-aware: at startup the operator reads the OpenShift `APIServer` resource to resolve the cluster TLS profile (cipher suites, minimum version), falls back to Intermediate defaults on non-OpenShift or transient errors, and registers a `SecurityProfileWatcher` that triggers a graceful restart when the profile changes. This profile feeds both the metrics server TLS config and Helm chart values for workload TLS.

The `MetricsController` is conditionally created only when `POD_NAMESPACE` is set, making the operator deployable outside Kubernetes for testing. It self-heals three resources (Service, ServiceMonitor, PrometheusRule) in the operator namespace, separate from the per-CR resources managed by the main reconciler.

NetworkPolicy restricts metrics ingress (port 8443) to `redhat-ods-monitoring` and `openshift-monitoring` namespaces, while health probes (port 8081) are open to all sources to accommodate CNI-dependent kubelet access patterns.
