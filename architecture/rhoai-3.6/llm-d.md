## Purpose

**Short**: llm-d is the top-level orchestration repository for the llm-d distributed inference serving stack, providing deployment guides, Dockerfiles, Helm chart values, Kustomize overlays, and architecture documentation for serving LLMs at scale on Kubernetes.

**Detailed**: llm-d is a CNCF sandbox project, founded by Red Hat, Google Cloud, IBM Research, CoreWeave, and NVIDIA. This repository serves as the coordination point for a multi-repository distributed inference stack optimized for production Kubernetes deployments. It does not contain the runtime source code for any of its core components (router, KV cache, routing sidecar, etc.) — those live in dedicated repositories under the `llm-d` GitHub organization.

Instead, this repository provides: (1) architecture documentation describing how the core and ecosystem components compose into well-lit deployment paths; (2) Dockerfiles that build vLLM-based model server images for CPU, AMD ROCm, Intel XPU, and RDMA network diagnostics; (3) Kustomize-first deployment guides covering a matrix of accelerators (NVIDIA GPU, AMD GPU, Intel XPU, Google TPU v6/v7, Rebellions NPU, CPU, Iluvatar GPU, MetaX GPU) and model servers (vLLM, SGLang, TensorRT-LLM); (4) Helm chart values for the llm-d Router (standalone and gateway modes); and (5) proposals for new features and components. The v0.9.0 development version introduces intelligent routing, KV cache management with tiered offloading and P2P sharing, prefill/decode disaggregation over NIXL/RDMA, predicted-latency scheduling, batch inference, and KEDA-driven autoscaling.

The repository defines no CRDs or operators itself. Runtime APIs come from external dependencies — primarily the Kubernetes Gateway API Inference Extension (InferencePool, HTTPRoute) and PodSnapshot CRDs (from the pod-snapshot guide). Deployment manifests in `guides/` are reference configurations that compose reusable recipe components (router, model server, gateway, observability, autoscaling) into end-to-end "well-lit path" guides.

## Architectural Analysis

llm-d's architecture is organized around three primary abstractions: the **Router** (Proxy + Endpoint Picker), the **InferencePool**, and the **Model Server**. The Router is an L7 proxy (Envoy or agentgateway) that consults an Endpoint Picker (EPP) via the `ext-proc` protocol to make LLM-aware routing decisions. The EPP scores and selects model server pods based on real-time metrics (KV-cache utilization, queue depth, active requests), prefix-cache affinity, and configurable scheduling policies. The InferencePool is the Kubernetes resource that groups model server pods via label selectors and connects the EPP to the Gateway infrastructure.

A distinguishing design decision is the separation of concerns: this meta-repository owns no runtime code. Every core component — the router/EPP (`llm-d-router`), the KV cache scheduler (`llm-d-kv-cache`), the P/D routing sidecar (`llm-d-routing-sidecar`), the batch gateway (`llm-d-batch-gateway`), the async processor (`llm-d-async`), the latency predictor (`llm-d-latency-predictor`), and the workload variant autoscaler (`llm-d-workload-variant-autoscaler`) — lives in its own repository. Ecosystem components for planning, benchmarking, simulation, cost analysis, and semantic classification are similarly separate. This structure enforces Principle #2 ("composition over configurability, components connect at API boundaries") and Principle #6 ("vLLM-first but not vLLM-only") by keeping the model server layer pluggable.

The disaggregated serving architecture is noteworthy: prefill and decode phases are separated onto specialized model server instances, with the EPP selecting both endpoints and a routing sidecar (co-located with the decode pod) orchestrating the multi-step request flow. KV cache transfer between prefill and decode pods uses NIXL over RDMA (InfiniBand or RoCE), with GPUDirect bypassing CPU to achieve high throughput. Fallback to TCP is supported for development but is explicitly documented as non-production.

The Dockerfile strategy uses upstream base images (Ubuntu 25.10 for CPU, `vllm/vllm-openai-rocm` for AMD, `vllm/vllm-openai-xpu` for Intel) and builds vLLM from source against specific commit SHAs. There are no Konflux Dockerfiles on this branch, meaning this component currently follows the upstream build model rather than the RHOAI downstream release-engineering pipeline. The RDMA tools image uses NVIDIA CUDA UBI9 for network diagnostics (perftest, iperf3, NCCL tests, GDRCopy).

Multi-tenancy is addressed at the architecture level through Kubernetes namespace scoping — the InferencePool, EPP, and model servers are all namespace-scoped. Flow control features (documented in the flow-control guide) provide workload prioritization and fairness across tenants sharing a model server pool. However, the isolation mechanisms depend on the deployment's Gateway and RBAC configuration rather than being enforced by llm-d components directly.
