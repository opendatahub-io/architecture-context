## Purpose

**Short**: An MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments through programmatic tools.

**Detailed**: rhoai-mcp is a Python-based MCP server that replicates the capabilities of the OpenShift AI Dashboard through programmatic, agent-consumable tools. It provides a plugin-based architecture with domain modules covering Data Science Projects, Kubeflow Workbenches (Notebooks), KServe model serving, Data Science Pipelines, data connections (S3 secrets), storage (PVCs), Kubeflow Training Operator integration, and Model Registry access. Composite modules layer on top, providing cluster-wide summary tools optimized for AI agent context windows, training workflow orchestration, tool discovery/guidance, and a Planner integration for model recommendations.

The server runs on the FastMCP framework over uvicorn, supporting stdio, SSE, and streamable-http transports. It connects to the Kubernetes API using the official Python client, operating under a ServiceAccount with broad ClusterRole permissions spanning core resources, Kubeflow CRDs, KServe CRDs, and Data Science Pipelines CRDs. When deployed with OIDC authentication enabled, it validates bearer tokens (via JWT JWKS or Kubernetes TokenReview), sets per-request user context, and enforces tool-level RBAC filtering through SubjectAccessReview—allowing the same server instance to serve multiple users with individually scoped tool visibility. The MCP Lifecycle Operator can manage the deployment via an MCPServer CR, simplifying deployment and lifecycle management.

## Architectural Analysis

rhoai-mcp follows a **pluggy-based plugin architecture** where every functional domain is a self-contained plugin that registers MCP tools, resources, and prompts through a hook system. The plugin lifecycle includes health checks at startup—plugins whose required CRDs are absent in the cluster are gracefully skipped, allowing the server to degrade rather than fail. This makes the server adaptable to clusters running partial RHOAI installations (e.g., no Training Operator, no Model Registry).

The **authentication design** is notable for its layered approach. In single-user mode (the default), the server's ServiceAccount credentials are used for all Kubernetes API calls. When OIDC is enabled, an ASGI middleware intercepts all requests (except `/health` and the Protected Resource Metadata endpoint), validates tokens, and establishes a `UserContext` via Python `contextvars`. The K8s client then switches to either forwarding the user's bearer token directly or using impersonation headers, depending on the configured strategy. Tool-level RBAC filtering patches FastMCP's lowlevel request handlers to intercept `ListToolsRequest` and `CallToolRequest`, hiding tools the authenticated user lacks permissions for. This is a pure application-layer enforcement—no service mesh or sidecar proxies are involved.

The **kustomize overlay hierarchy** reveals how the component is deployed across environments: a generic base, an OpenShift overlay adding Routes and additional RBAC for OpenShift-specific APIs, ODH and RHOAI operator-managed overlays that set namespace and read-only defaults, an OIDC overlay that replaces the broad ServiceAccount ClusterRole with minimal TokenReview/SubjectAccessReview permissions, and an MCPServer overlay that delegates Deployment/Service lifecycle to the MCP Lifecycle Operator.

A notable design choice is the **dual-mode Planner integration**: the llm-d-planner library can run embedded (local mode) or as a remote REST API client. The local mode additionally supports syncing benchmark data from the RHOAI Model Catalog via its REST API, with TLS verified through the OpenShift service-serving CA bundle mounted into the pod.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user bearer token validation; tool-level RBAC filtering via SubjectAccessReview; user-token forwarding to K8s API | Application (OIDCAuthMiddleware + RBACChecker) | In SA mode (non-OIDC), all requests share the ServiceAccount's broad ClusterRole with no per-user isolation |
| Data storage | No server-side data storage; all state is in Kubernetes resources scoped by user's K8s permissions | Kubernetes RBAC | In SA mode, the ServiceAccount can access resources across all namespaces |
| Network traffic | NetworkPolicy for Model Catalog access; OpenShift Route with TLS edge termination | Kubernetes / OpenShift | No per-user network isolation; all users share the same pod and network identity |
| Compute & resources | Single pod with resource requests/limits (100m-500m CPU, 256Mi-1Gi memory) | Kubernetes | No per-user compute isolation; a single user's expensive operation could impact others |
| Configuration & secrets | Per-request UserContext via Python contextvars; session-level token stored in UserContext | Application | Workflow HMAC secret is process-global (not per-tenant) |
| API scoping | K8s API calls use the caller's bearer token (user-token strategy) or impersonation headers; K8s RBAC enforces namespace scoping | Kubernetes RBAC / Application | Unmapped tools (no permission mapping in plugin) are visible to all authenticated users by default |
