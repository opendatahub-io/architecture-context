## Purpose

**Short**: Kubernetes controller that manages the lifecycle of model serving resources — InferenceServices, LLMInferenceServices, InferenceGraphs, ServingRuntimes, and NVIDIA NIM Accounts — on the Red Hat OpenShift AI platform.

**Detailed**: odh-model-controller is the data plane orchestrator for model serving in RHOAI. It watches KServe InferenceService and LLMInferenceService custom resources and reconciles the surrounding ecosystem of supporting objects: networking (Routes, NetworkPolicies, Gateway API HTTPRoutes), security (RBAC Roles/RoleBindings, Kuadrant AuthPolicies), observability (ServiceMonitors, PodMonitors, KEDA TriggerAuthentications), and secrets (storage credentials, NIM API keys). The controller eliminates the manual steps users would otherwise perform when deploying models.

The component produces two independently deployable binaries. The primary controller (`/manager`) runs as a controller-runtime operator managing 8+ reconcilers and 8 admission webhooks. A companion `model-serving-api` server exposes an HTTPS REST API for gateway discovery and sample manifests, targeting the dashboard and CLI integration surfaces. Both binaries ship 27 ClusterServingRuntime definitions covering vLLM (CUDA, ROCm, Gaudi, CPU, Spyre), MLServer, and OpenVINO Model Server across multiple accelerator variants and "fast channel" release tiers.

## Architectural Analysis

odh-model-controller follows a hub-and-spoke controller design: a single operator deployment reconciles a wide surface of KServe and platform resources through a collection of focused reconcilers (InferenceService, LLMInferenceService, Gateway, ServingRuntime, Secret, ConfigMap, Pod, NIM Account, InferenceGraph). Each reconciler owns specific child resources and uses controller-runtime's `Owns()` / `Watches()` to trigger on related object changes.

A distinguishing pattern is the Gateway controller, which bridges the KServe data model with Kubernetes Gateway API. It reconciles Gateway resources, manages Kuadrant AuthPolicies for authentication, creates EnvoyFilters for traffic shaping, and wires PodMonitors for observability — all triggered by changes to LLMInferenceService or LLMInferenceServiceConfig resources. This positions the controller as the integration layer between KServe's inference abstractions and RHOAI's platform ingress infrastructure.

The controller supports an xKS (external KServe) mode for non-OpenShift deployments, activated via environment variable. In xKS mode, only the LLMInferenceService webhook runs — all reconcilers and other webhooks are disabled. This dual-mode design allows partial reuse of the webhook validation logic without the full RHOAI controller surface.

TLS configuration is cluster-aware: the controller reads the OpenShift APIServer TLS profile at startup and dynamically configures cipher suites and minimum TLS version to match the cluster policy. If the TLS profile changes at runtime, a watcher triggers a graceful restart to reload the configuration. On non-OpenShift clusters, hardened Mozilla Intermediate defaults apply.

The model-serving-api server enforces Bearer token authentication on the `/api/v1/gateways` endpoint and delegates authorization to Kubernetes SelfSubjectAccessReview. The `/api/v1/samples/llm-d` endpoint is intentionally unauthenticated as it serves static sample manifests.

The serving runtime definitions implement a "fast channel" model with three tiers per accelerator variant (base, fast-1, fast-2), allowing independent image pinning for staged rollouts of inference runtime updates. All runtime images are parameterized via kustomize ConfigMap replacements from `params.env`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC (Roles, RoleBindings created per InferenceService namespace); Kuadrant AuthPolicies per Gateway | Kubernetes + Kuadrant | Controller itself runs with cluster-wide permissions; tenant isolation relies on the child RBAC resources it creates |
| Data storage | Per-namespace Secrets and ConfigMaps (owned by InferenceService/Account CRs) | Kubernetes | No shared database; all state is Kubernetes resources |
| Network traffic | Per-namespace NetworkPolicies created by InferenceServiceReconciler | Kubernetes | NetworkPolicies are namespace-scoped; cross-namespace traffic depends on platform network policy baseline |
| Compute & resources | Delegated to KServe and cluster ResourceQuotas | Kubernetes | Controller does not create ResourceQuotas; relies on platform-level enforcement |
| Configuration & secrets | Per-namespace Secrets with `opendatahub.io/managed=true` label; Secret cache filtered by label | Kubernetes | ConfigMap cache is cluster-wide (metadata-only for efficiency) |
| API scoping | Controller watches cluster-wide but reconciles within CR namespace; model-serving-api enforces SelfSubjectAccessReview per request | Kubernetes + Application | Gateway discovery API validates per-namespace access before returning results |
