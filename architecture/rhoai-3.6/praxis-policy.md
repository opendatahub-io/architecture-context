## Purpose

**Short**: A typed, phased policy enforcement engine for AI agent traffic that decides who may call which tool, what data comes back, and where that data is allowed to go next.

**Detailed**: The Praxis Policy Engine (PPE) is a deterministic reference monitor that sits between an AI agent and every capability it invokes — tools, prompts, resources, inference providers, and A2A methods. It enforces authorization policy at a boundary the LLM cannot observe or forge, treating the LLM as fully untrusted (the adversary model assumes the model is compromised or steerable via prompt injection).

PPE evaluates operations through a five-phase plugin execution pipeline (sequential → transform → audit → concurrent → fire-and-forget). Policy is written declaratively in APL (Authorization Policy Language), which compiles to plugin dispatch. The engine resolves caller identity from verified tokens, evaluates authorization predicates through pluggable Policy Decision Points (Cedar, CEL, or OPA), exchanges credentials via RFC 8693 token delegation for downstream services, redacts fields in transit, tracks information flow across calls via Session Taint, supports out-of-band human approval (CIBA elicitation), and emits an audit event for every decision.

PPE is a pure Rust library (`unsafe_code = "forbid"`) published to crates.io, not a standalone service. It is embedded into host applications — primarily the Praxis proxy — which provide the HTTP serving layer, the deployment topology, and the connection between PPE's policy boundary and the wire. The same APL policy enforces identically whether PPE runs as a gateway fronting a tool server, an egress sidecar beside an agent, or inline within an agent framework.

## Architectural Analysis

PPE's architecture is organized as a layered Cargo workspace with strict dependency flow: the facade crate (`praxis-policy`) re-exports the runtime stack (`ppe-core` → `ppe-apl-runtime` → `ppe-apl-cmf` → `ppe-apl-core` → `ppe-orchestration`), giving hosts a single dependency that resolves the entire engine. The nine bundled extensions (JWT identity, API-key identity, OAuth delegation, CIBA elicitation, Cedar/CEL/OPA policy decision points, Valkey session store, and Vault secret provider) are consolidated into one crate (`praxis-policy-builtins`) behind individual Cargo features, so a consumer compiles only the extensions it enables.

The trust architecture is notable: plugin capabilities are declared in configuration, not claimed by plugins. The engine filters the request context each plugin sees based on its declared capabilities — a plugin that does not declare `read_subject` never receives identity attributes, even if it runs in the same pipeline as one that does. This is a capability-based access control model applied to the policy engine's own internals, preventing a compromised or poorly-written plugin from reading state it was not designed for.

The outbound HTTP transport (`HyperTransport`) enforces an egress table that refuses private-address destinations (RFC 1918, link-local, CGNAT, cloud metadata endpoints) at both DNS resolution time and pre-connect IP literal checks. This is a defense against SSRF through IdP or JWKS URLs, and the refusal is reported as a distinct error class (`Rejected`) that a caller cannot retry. The transport uses rustls with the `ring` crypto provider (explicitly selected, not a process default) and webpki root certificates.

The secret management model is fail-fast at startup and last-good on refresh: a declared secret that cannot be resolved stops initialization, while a failed refresh keeps the previous value rather than leaving a gap. Secret material is zeroized on drop, and the assertion system propagates secrets to HTTP headers without exposing them in plugin views, audit logs, or effective-policy artifacts.

A design risk worth noting: the library's Cargo.lock contains both `aws-lc-rs` (pulled by `jsonwebtoken` for JWT signature operations) and `ring` (used by the HyperTransport for TLS). Both are non-FIPS-validated in their default builds. A FIPS-compliant deployment would need to ensure the host application's crypto provider selection and linking strategy satisfies the target compliance regime — PPE itself makes no FIPS claims.

## Sub-Component Details

### praxis-policy-builtins: Identity Plugins

**Feature**: `jwt`, `api-key`
**Intent**: Resolve and validate caller identity from inbound credentials. The JWT resolver fetches JWKS, validates signatures (RS256/RS384/RS512, ES256/ES384, EdDSA, HS256/HS384/HS512 via `jsonwebtoken`), and maps claims to the identity model via configurable presets. The API-key resolver uses SHA-256 hash-indexed directories with bounded lookup caching.

### praxis-policy-builtins: Delegation Plugin

**Feature**: `oauth`
**Intent**: Exchange inbound credentials for audience-scoped downstream tokens via RFC 8693 token exchange. Uses HMAC-SHA256 cache-key derivation under a per-process `getrandom` secret, with a bounded coalescing cache (`moka`) that guarantees one exchange per uncached key under concurrent requests.

### praxis-policy-builtins: Elicitation Plugin

**Feature**: `elicitation-ciba`
**Intent**: Support out-of-band human approval via CIBA (Client Initiated Backchannel Authentication). Suspends the policy call for external sign-off and validates scope-bound approvals on resume.

### praxis-policy-builtins: Policy Decision Points

**Feature**: `cedar`, `cel`, `opa`
**Intent**: Pluggable authorization evaluation engines. Cedar uses `cedar-policy` v4 with stack-growth guards for musl. CEL uses `cel-rust` v0.14 with regex and chrono features (JSON/bytes features deliberately off). OPA uses `regorus` v0.12 (Microsoft's pure-Rust Rego interpreter) with restricted builtins — `http.send`, `net`, and `opa.runtime` are excluded to limit the attack surface of operator-authored Rego. All three run through a PDP decision cache (opt-in bounded TTL/entry-cap cache keyed by digest of inputs).

### praxis-policy-builtins: Session Store

**Feature**: `valkey`
**Intent**: Distributed session state persistence (Session Taint labels) via Valkey/Redis. Uses `redis` crate with rustls TLS (`tokio-rustls-comp`), `deadpool-redis` connection pooling, and SHA-256-derived session keys.

### praxis-policy-builtins: Secret Provider

**Feature**: `secrets-vault`
**Intent**: Vault KV v2 secret provider. Reads through the host HttpTransport, supports Kubernetes and AppRole auth, renews tokens lazily, and reauthenticates once after a 403.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request identity resolution + APL policy evaluation through PDP | PPE engine (in-process) | Identity resolution depends on host providing valid tokens; PPE validates signatures but does not authenticate users |
| Data storage | Session Taint labels keyed per session in Valkey; in-memory session store as fallback | PPE + Valkey | In-memory store is per-process only; Valkey store shares the backend across instances |
| Network traffic | Egress table refuses private addresses; host provides network-level isolation | PPE transport + host infrastructure | PPE cannot enforce network isolation between tenants at the infrastructure layer |
| Compute & resources | Plugin timeout (30s default), bounded decision cache, bounded routing cache (10,000 entries) | PPE engine | No per-tenant resource quotas within PPE; experimental quota plugin exists for per-consumer token budgets |
| Configuration & secrets | Secrets resolved per engine instance; zeroized on drop; capability-filtered plugin views | PPE engine | All tenants share the same engine configuration and secret store within one process |
| API scoping | Capability-based extension filtering per plugin (declared in config, not claimed by plugin) | PPE engine | Filtering is per-plugin, not per-tenant; all tenants' requests flow through the same plugin pipeline |
