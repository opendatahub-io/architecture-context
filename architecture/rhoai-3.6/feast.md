## Purpose

**Short**: Feast is a feature store operator and serving platform that manages the lifecycle of ML feature stores on Kubernetes, providing both online and offline feature serving for machine learning workloads.

**Detailed**: Feast (Feature Store) is a dual-language component that combines a Go-based Kubernetes operator with a Python SDK and feature server. The operator manages the full lifecycle of FeatureStore custom resources, creating and reconciling deployments for online/offline stores, a feature registry, and a UI. It handles TLS configuration, RBAC-based or OIDC-based authorization, horizontal pod autoscaling, pod disruption budgets, and CronJob-based materialization.

The Python feature server (served via FastAPI/uvicorn/gunicorn) exposes a rich REST API for online feature retrieval, registry management, data lineage tracking, monitoring, active learning, and vector store search. It supports multiple backend stores (Redis, PostgreSQL, BigQuery, Snowflake, DynamoDB, Bigtable, S3, and more) and integrates with MLflow for experiment tracking and OpenLineage for data lineage. A Go-based feature server provides a lightweight alternative for online feature serving with gRPC and HTTP interfaces.

Within RHOAI, the feast-operator is deployed into the `redhat-ods-applications` namespace by the platform operator, and each user-created FeatureStore CR provisions an isolated set of services in the user's namespace.

## Architectural Analysis

Feast's architecture follows a split-plane design: the operator (Go, controller-runtime) runs as a cluster-scoped controller that watches namespaced FeatureStore CRs, while the data plane consists of per-CR deployments of the Python feature server. This separation means the operator holds broad RBAC permissions (26 rules in the manager role spanning 12 API groups) but the feature server pods run with namespace-scoped service accounts that the operator provisions dynamically.

The operator implements a sophisticated TLS bootstrap sequence that reads the cluster-wide OpenShift APIServer TLS profile (`config.openshift.io/apiservers`) and applies the resulting cipher suite and minimum version to all managed TLS listeners. This means the operator automatically inherits any cluster-level TLS hardening. The Go feature server's TLS configuration explicitly sets TLS 1.2 as the minimum version and includes post-quantum key exchange support (X25519MLKEM768).

Authorization is configurable per FeatureStore CR with a three-way choice: Kubernetes RBAC, OIDC, or no auth. The CRD enforces exactly one selection via CEL validation. When Kubernetes auth is chosen, the operator creates Roles and RoleBindings in the feature store namespace. When OIDC is chosen, the operator reads credentials from a referenced Secret. The Python feature server implements JWT-based token validation via PyJWT, with OIDC token parsing that fetches and caches JWK signing keys.

A notable integration pattern is the NotebookConfigMapReconciler, which watches both FeatureStore CRs and Kubeflow Notebook resources to inject feature store client configuration into notebook workbenches via ConfigMaps. The operator also watches MLflow CRs to coordinate with experiment tracking.

The feature server's API surface is expansive, with 115+ HTTP endpoints and 69 gRPC services covering registry CRUD, online feature retrieval, materialization, monitoring, lineage, vector store search, active learning, and even chat endpoints. This breadth reflects Feast's upstream ambition as a full feature platform, though the RHOAI deployment may expose only a subset.
