## Purpose

**Short**: An SLO-driven deployment planning tool that guides users from business requirements to production-ready LLM deployments on Kubernetes, with capacity planning, GPU recommendation, and one-click KServe/vLLM deployment.

**Detailed**: llm-d-planner is a multi-component Python application that unifies LLM deployment concerns — model selection, GPU sizing, performance estimation, and Kubernetes configuration — into a single conversational workflow. Users describe their AI use case in natural language; the system extracts intent via an LLM, translates business requirements into technical SLO specifications (traffic profiles, latency targets, cost constraints), generates ranked GPU+model configuration recommendations backed by benchmarks and estimation, and produces deployable KServe/vLLM Kubernetes YAML with one-click deployment.

The system is built as three cooperating services: a FastAPI backend (port 8000) providing the core API pipeline, a Streamlit frontend (port 8501) for conversational UI and monitoring, and an Ollama sidecar (port 11434) for local LLM-powered intent extraction. The backend supports pluggable LLM providers (Ollama, OpenAI-compatible, Claude on Vertex AI) and can source benchmark data from either a local SQLite database or the RHOAI Model Catalog API. It also produces llm-d-specific deployment configurations via Jinja2 templates, and manages the full Kubernetes deployment lifecycle via kubectl and the Python Kubernetes client.

## Architectural Analysis

llm-d-planner follows a layered service architecture rather than the operator/controller pattern typical of RHOAI components. The core design centers on a four-stage pipeline — intent extraction, specification generation, recommendation scoring, and deployment configuration — where each stage's output feeds as input to the next. This pipeline is exposed both as a REST API and as a Python library (`Planner` facade class), enabling both interactive UI-driven workflows and programmatic integration.

The recommendation engine implements a multi-criteria scoring system across three dimensions (quality, price, latency) with per-use-case configurable weights. Quality scoring is particularly sophisticated, compositing human preference data from LMSYS Chatbot Arena with automated benchmark data from Artificial Analysis into percentile-normalized scores, weighted by use-case-specific category mappings (e.g., coding tasks weight coding benchmarks higher). This dual-source approach provides broader model coverage than either source alone.

A notable architectural choice is the pluggable benchmark data source. When `PLANNER_BENCHMARK_SOURCE=model_catalog`, the backend connects to the RHOAI Model Catalog API over HTTPS (port 8443) using OpenShift service-serving CA certificates for trust. A dedicated NetworkPolicy in the `rhoai-model-registries` namespace permits this cross-namespace traffic. This integration point ties llm-d-planner into the RHOAI platform data plane, though the component also operates standalone with local benchmark data.

The deployment configuration layer is also pluggable, supporting both KServe InferenceService YAML (for standard vLLM deployments) and llm-d-specific templates (kustomization + patch YAML). A simulator mode replaces real GPU-backed vLLM with a latency-simulating service for GPU-free development, which is how the KIND cluster development workflow operates.

From a security perspective, the backend API has no authentication middleware — all endpoints are unauthenticated at the application layer. The database admin endpoints use a simple environment-variable-based password checked via `hmac.compare_digest`, but this is optional and not RBAC-integrated. External exposure relies entirely on OpenShift Route TLS termination (edge mode). The CORS configuration allows all origins (`allow_origins=["*"]`), which is flagged in the code as needing production restriction. These gaps are consistent with the component's current beta/incubation status.
