## Purpose

**Short**: E2E test suite for distributed training workloads on RHOAI, plus universal training container images for CPU, CUDA, and ROCm accelerators.

**Detailed**: The distributed-workloads repository serves a dual purpose within the RHOAI platform. First, it provides comprehensive end-to-end integration tests written in Go that validate distributed training capabilities across three orchestration frameworks: Kubeflow Training Operator v1 (PyTorchJob), Kubeflow Trainer v2 (TrainJob/JobSet), and KubeRay (RayCluster/RayJob). These tests exercise multi-node/multi-GPU training, Kueue job queuing, SDK integrations, and foundation model fine-tuning (SFT, LoRA, QLoRA) via fms-hf-tuning.

Second, the repository produces three universal training container images — CPU, NVIDIA CUDA, and AMD ROCm variants — that function as both Jupyter workbenches and training runtimes. These images bundle PyTorch, Training Hub, Transformers, and the full ML stack needed for distributed training, sourced from the AIPCC PyPI index for RHOAI's secure supply chain. The images use a multi-stage build pattern with cachi2 prefetch for hermetic Konflux builds and support both midstream (RHOAI workbench base) and downstream (AIPCC base) build modes.

The repository also contains training examples (Ray Tune HPO, Stable Diffusion DreamBooth, LLM SFT) and MPI benchmarks, though these are supplementary materials rather than shipped product artifacts.

## Architectural Analysis

This repository is architecturally unusual among RHOAI components: it does not deploy an operator, controller, or long-running service. Instead, it produces container images consumed by other platform components and contains the integration test suite that validates the distributed training subsystem end-to-end.

The universal training images represent the key product artifacts. Their dual-mode design (workbench vs. runtime) is controlled by a shell entrypoint that checks for `NOTEBOOK_ARGS` — when present, it starts JupyterLab; otherwise, it executes the provided command (typically `torchrun`). This means the same image serves notebook users interactively and training controllers programmatically, reducing image sprawl. The `DOWNSTREAM` build argument controls whether system packages (CUDA/ROCm dev tools, RDMA/InfiniBand libraries) are installed from DNF or inherited from the AIPCC base image, enabling the same Dockerfile to work for both midstream and downstream builds.

The test suite architecture follows a well-structured pattern: a shared support library (`tests/common/support/`) provides Kubernetes client abstractions, resource helpers, and test lifecycle management (namespace isolation, cleanup, log collection), while four independent test suites consume it. Strict import boundaries enforced by `depguard` prevent cross-suite contamination. The Go code in this repo has no production deployment — its sole purpose is orchestrating Kubernetes resources to validate that the distributed training stack works correctly.

All Kubernetes manifests in the repository (minio deployments, Routes, Services, NFS server) exist solely within examples and workshop materials. They are not product manifests and are not deployed by any RHOAI installer or operator.
