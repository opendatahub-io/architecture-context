## Purpose

**Short**: An automated end-to-end benchmarking framework for LLM inference stacks, providing declarative lifecycle management of deployment, experiment execution, data collection, and teardown across multiple Kubernetes environments.

**Detailed**: llm-d-benchmark is the performance evaluation platform for the llm-d inference stack. It provides a single CLI (`llmdbenchmark`) that orchestrates the complete lifecycle of LLM benchmarking — from cluster standup and infrastructure provisioning through load generation, result collection, and teardown. The framework supports multiple Kubernetes environments (GKE, CoreWeave, OpenShift) and deployment styles (standalone vLLM, ModelService, kustomize, Fast Model Actuation).

The tool uses a declarative configuration model built on Jinja2 templates and a hierarchical merge chain (`defaults.yaml` → specification → scenario → CLI overrides) to render reproducible experiment definitions. Built-in Design of Experiments (DoE) support automates parameter sweeps across infrastructure and workload axes. Multiple benchmarking harnesses are supported — inference-perf, vllm-benchmark, guidellm, aiperf, inferencemax, and lm-eval — selectable with a CLI flag.

A companion sub-project, `llm_d_stack_discovery`, provides a separate CLI tool for live Kubernetes cluster introspection. Given an OpenAI-compatible endpoint URL, it traces the full llm-d serving stack (Gateway, HTTPRoute, Services, Pods, vLLM containers) and outputs structured configuration snapshots. Both tools interact heavily with the Kubernetes API and optionally with Google Cloud Storage for results persistence.

## Architectural Analysis

llm-d-benchmark follows a pipeline executor architecture organized around lifecycle phases: `plan → standup → smoketest → run → teardown`. Each phase is decomposed into numbered steps (e.g., `step_00_ensure_infra`, `step_02_admin_prerequisites`, up through `step_11_inference_test`) that are executed sequentially by a `StepExecutor`. The configuration system is notable for its depth — a `RenderPlans` engine processes Jinja2 templates through a deterministic merge chain that captures every parameter in a workspace, making experiments fully reproducible.

The harness container image (`build/Dockerfile`) bundles multiple third-party benchmarking tools (inference-perf, vllm-benchmark, guidellm, aiperf, lm-eval) into a single image with an entrypoint script (`llm-d-benchmark.sh`) that selects and dispatches to the appropriate harness. This image is deployed as a StatefulSet with a PVC for result persistence. The harness container runs the load generator, then runs an analysis script, and exits — it is a batch workload, not a long-running service.

The results store system uses a pluggable storage backend with two implementations: direct GCS (`google.cloud.storage`) and a GCS proxy client that routes through a Prism proxy (`https://prism.llm-d.ai`). The proxy fallback provides read access when direct GCS credentials are unavailable.

The `llm_d_stack_discovery` sub-project is architecturally independent — it has its own Dockerfile, requirements.txt, and package structure. It uses `pykube-ng` for Kubernetes API access and traces llm-d stacks by following the chain from Gateway → HTTPRoute → Service → Pod → container configuration, collecting vLLM runtime flags, model names, and resource allocations.

A security concern is that the RBAC configuration (deployed via `util/deploy/`) grants `pods/exec` permissions to all authenticated users (`system:authenticated`) scoped to the benchmark StatefulSet pod. This is a broad grant that allows any cluster user to exec into the benchmark pod.
