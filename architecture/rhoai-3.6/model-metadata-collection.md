## Purpose

**Short**: Go-based build-time pipeline that extracts, enriches, and catalogs AI model metadata from OCI container images, HuggingFace collections, MCP servers, agents, and serving runtimes into structured YAML catalogs, then packages the catalogs as a data-only container image for consumption by other RHOAI components.

**Detailed**: model-metadata-collection is a CI/CD build tool — not a runtime service. Its primary executable, `model-extractor`, orchestrates a multi-stage pipeline: it discovers Red Hat AI validated model collections from the HuggingFace API, fetches OCI container images from registries (e.g., registry.redhat.io), scans container layers for `io.opendatahub.modelcar.layer.type=modelcard` annotations, extracts structured metadata from embedded modelcards, and enriches that metadata with HuggingFace README content, vLLM recommended configurations, and tool-calling configuration from YAML frontmatter. The pipeline generates several YAML catalog files (validated-models, other-models, MCP servers in three tiers, agents, and serving runtimes) that are checked into the repository's `data/` directory.

The Konflux Dockerfile builds a minimal data container (`ubi9-minimal-pqc` base, `CMD sleep infinity`) that simply ships the pre-generated catalog YAML files at `/app/data/`. This container is designed to be mounted as a sidecar or init-container volume so that other platform components — such as the RHOAI dashboard — can consume the catalog data without needing direct access to the build pipeline or external APIs. The repository also produces two ancillary CLI tools: `metadata-report` (generates completeness/quality reports from catalog output) and `serving-runtime-catalog` (generates a normalized catalog of KServe ServingRuntime definitions from reviewed input files).

## Architectural Analysis

model-metadata-collection occupies a unique position in the RHOAI platform as an offline data generator rather than a deployed service. Its architectural significance lies in being the single source of truth for model, MCP server, agent, and serving runtime metadata surfaced to users through the RHOAI dashboard.

The build pipeline follows a fan-out/fan-in concurrency pattern: the main `model-extractor` CLI launches bounded goroutines (default 5, configurable) to process OCI images in parallel, collecting results through a channel before merging them into a unified catalog. The enrichment stage is sequential and layered — HuggingFace enrichment runs first, then OCI artifact metadata updates, with modelcard.md content given priority over external sources when both are available.

A notable design decision is the fallback strategy for missing modelcards: when a container image lacks the expected annotation-based modelcard layer, the tool creates a skeleton `metadata.yaml` and attempts to fetch the corresponding HuggingFace README as a fallback. This ensures every model in the catalog has at least minimal metadata, even when upstream container packaging is incomplete.

The serving runtime catalog pipeline (`cmd/serving-runtime-catalog`) is structurally independent — it reads reviewed YAML input files that reference `serving.kserve.io/v1alpha1 ServingRuntime` templates and generates a normalized output catalog. These input files contain embedded ServingRuntime manifests for vLLM variants (CUDA, ROCm, Omni-CUDA), establishing a data dependency on the KServe API without any runtime integration.

The data container pattern (UBI9-minimal-pqc base with `sleep infinity`) means the component has no network surface, no RBAC requirements, and no runtime security posture. Its security boundary is entirely at the build/CI layer where the Go tools authenticate to external APIs (HuggingFace, GitHub, container registries) using environment-variable tokens.
