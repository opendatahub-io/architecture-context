## Purpose

**Short**: A small HTTP reverse proxy that performs Kubernetes RBAC authorization via SubjectAccessReview before forwarding requests to a single upstream service.

**Detailed**: kube-rbac-proxy is a sidecar container that sits in front of an upstream HTTP service (typically a metrics endpoint) and enforces authentication and authorization using the Kubernetes API. On every incoming request it validates the caller's identity -- via bearer token (delegated TokenReview), client TLS certificate, or OIDC JWT -- and then performs a SubjectAccessReview to verify the caller holds the required RBAC permissions before proxying the request to the upstream.

The proxy was originally created to protect Prometheus metrics endpoints inside Kubernetes clusters where NetworkPolicies are unavailable or insufficient. In the RHOAI platform it is deployed as a sidecar container (image name `odh-kube-rbac-proxy`) alongside components whose HTTP endpoints need authentication and authorization enforcement without modifying the upstream application. It supports both a legacy Format1 authorization configuration (top-level resource attributes with query-parameter and header rewrites) and a newer Format2 configuration (path-scoped endpoints with per-HTTP-method SAR mappings, wildcard segments, and named path captures). It also provides OCSF 1.9.0-compliant AI inference audit logging for traceability of inference requests routed through the proxy.

## Architectural Analysis

kube-rbac-proxy follows a straightforward reverse-proxy architecture with a layered authentication/authorization filter chain. The request pipeline is: TLS termination -> optional path allow/ignore filtering -> authentication (delegating TokenReview, OIDC, or client-certificate) -> authorization (hardcoded OpenShift monitoring SA, static rules, then SAR) -> header injection -> upstream proxy. This chain is constructed at startup in `buildProtectedHandler` and wrapped with timeout enforcement that shares a single deadline between authentication and authorization.

A notable design decision is the hardcoded authorizer (`pkg/hardcodedauthorizer/metrics.go`) that unconditionally allows `system:serviceaccount:openshift-monitoring:prometheus-k8s` to GET `/metrics`. This is an OpenShift-specific carve-out that predates the static authorizer configuration and exists to ensure Prometheus monitoring always works regardless of RBAC policy. The codebase marks it with a TODO for removal once Cluster Monitoring Operator lands static authorizer configuration.

The Format2 endpoint authorization system in `pkg/authz/endpoints.go` adds significant expressiveness -- path-scoped SAR rules with named captures (`{tenant}`) and template expansion allow fine-grained per-path, per-method authorization. This supports multi-tenant patterns like TrustyAI's `trustyai.opendatahub.io` API group, where different URL paths map to different Kubernetes resource authorization checks.

TLS is handled carefully: the proxy defaults to TLS 1.2 minimum on both its listening socket and upstream connections. Certificate hot-reloading is supported via `pkg/tls/reloader.go` with configurable polling intervals. The proxy uses `crypto/tls` from the Go standard library, which under `GOEXPERIMENT=strictfipsruntime` routes through OpenSSL for FIPS-compliant cryptography. The upstream connection transport explicitly sets `MinVersion: tls.VersionTLS12` and supports HTTP/2.

The audit subsystem emits OCSF 1.9.0 API Activity events with an AI operation profile, designed for inference audit trails. It uses a bounded non-blocking queue to prevent audit logging from stalling request processing, with loss-detection and recovery summaries.
