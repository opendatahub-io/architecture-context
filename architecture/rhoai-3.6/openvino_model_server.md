## Purpose

**Short**: High-performance model inference server built on Intel OpenVINO, exposing KServe v2, TensorFlow Serving, and OpenAI-compatible APIs over gRPC and REST.

**Detailed**: OpenVINO Model Server (OVMS) is a C++-based inference serving system designed for high-throughput, low-latency model deployment on Intel architectures. It serves as the runtime engine behind KServe `ServingRuntime` definitions in Red Hat OpenShift AI, handling inference requests for models in multiple frameworks including OpenVINO IR, ONNX, TensorFlow, PaddlePaddle, and PyTorch formats.

The server exposes three API families: TensorFlow Serving v1 (predict, classify, regress), KServe Inference Protocol v2 (infer, health, metadata), and an OpenAI-compatible v3 API layer (chat/completions, completions, embeddings, rerank, images/generations, audio/transcriptions, audio/speech, responses). The REST server is built on the Drogon HTTP framework, while gRPC uses the standard gRPC C++ stack. Both protocols run concurrently with configurable ports and worker counts.

OVMS supports model loading from local filesystems, AWS S3, Google Cloud Storage, Azure Blob Storage, and HuggingFace Hub. It features a MediaPipe graph executor for generative AI workloads with continuous batching, DAG-based pipeline scheduling for multi-model inference chains, dynamic model management with versioning and hot-reload, and optional Python code execution for custom processing. The server runs as a stateless, single-binary container process (`/ovms/bin/ovms`) under a non-root user (UID 5000).

## Architectural Analysis

OVMS follows a monolithic server architecture where a single C++ binary hosts all protocol frontends (gRPC and REST), the model manager, and inference backends. The architecture is modular internally through a `Server` class that orchestrates independent modules: `GRPCServerModule` for gRPC transport, a Drogon-based HTTP server for REST, `ServableManagerModule` for model lifecycle, and `MetricModule` for Prometheus metrics.

The generative AI capabilities are built on MediaPipe graph execution rather than simple direct inference. The V3 (OpenAI-compatible) endpoints route through `MediapipeGraphExecutor` instances, enabling continuous batching via OpenVINO GenAI. This is a notable architectural choice: traditional inference (KServe v2, TFS) runs through a direct model-to-inference path, while LLM/generative workloads use a graph-based execution engine that manages streaming responses, token generation, and batching.

Model storage is abstracted through a filesystem factory pattern (`FilesystemFactory`) with pluggable backends for local, S3, GCS, and Azure. The HuggingFace Hub integration uses libgit2 for git-clone-based model downloads and curl for direct file downloads, both using system OpenSSL with native CA certificates (`CURLOPT_SSL_OPTIONS, CURLSSLOPT_NATIVE_CA`).

The gRPC server currently uses `InsecureServerCredentials` — there is no built-in TLS termination on the gRPC port. The REST server (Drogon) similarly runs without TLS. For mTLS-protected deployments, the repository includes an nginx-mtls-auth sidecar wrapper (`extras/nginx-mtls-auth/`) that fronts OVMS with nginx configured for mutual TLS. In RHOAI deployments, TLS termination is typically delegated to the KServe/Istio service mesh layer.

Authentication is handled via an optional API key mechanism: the server accepts a `--api_key_file` argument or `API_KEY` environment variable, and when configured, validates `Authorization: Bearer <key>` headers on V3 (OpenAI-compatible) endpoints. KServe v2 and TFS endpoints do not participate in this API key check — they rely on network-level access controls.

The build system uses Bazel for the C++ server and compiles OpenVINO, OpenVINO GenAI, and OpenVINO Tokenizers from source within the Dockerfile. This means the Dockerfile.konflux is a ~460-line multi-stage build that fetches and compiles substantial C++ dependencies including Boost, Azure SDK, OpenCV, pugixml, and the full OpenVINO toolkit. This source-build approach provides fine-grained control over compiler flags and security hardening (SDL flags) but makes the build non-hermetic — dependencies are fetched from git during build.
