## Purpose

**Short**: A reverse proxy sidecar that implements disaggregated prefill/decode routing for LLM inference in the llm-d platform, directing prefill requests to remote workers and decode requests to a co-located vLLM instance.

**Detailed**: The llm-d-routing-sidecar is a lightweight Go reverse proxy that enables disaggregated prefill/decode (P/D) serving for large language models. In the llm-d architecture, inference can be split between "prefill" workers (which process the input prompt and populate KV caches) and "decode" workers (which generate tokens). This sidecar sits alongside a local vLLM decoder instance and intercepts OpenAI-compatible completion requests. When a request arrives with an `x-prefiller-host-port` header, the sidecar orchestrates a two-phase protocol: it first sends a modified request to the specified remote prefill worker, captures KV transfer parameters from the response, then forwards the original request (enriched with those parameters) to the local decoder for token generation.

The sidecar supports multiple connector protocols (NIXL v1, NIXL v2, and LMCache), with NIXL v2 as the current default. It includes an optional SSRF protection mechanism that watches Kubernetes InferencePool resources (from the Gateway API Inference Extension) to maintain an allowlist of valid prefill targets based on pod IPs. TLS is enabled by default for the proxy's own listener, with configurable TLS settings for both prefill and decoder upstream connections.

**Note**: This repository is deprecated. The codebase has been moved to the [llm-d-inference-scheduler](https://github.com/llm-d/llm-d-inference-scheduler) repository under `cmd/pd_sidecar` and `pkg/sidecar`.

## Architectural Analysis

The routing sidecar follows a classic reverse proxy pattern with protocol-aware request transformation. Its architecture is shaped by three key design decisions:

**Two-phase request orchestration.** Rather than simply forwarding requests, the sidecar implements a stateful two-phase flow per completion request. For NIXL v2, it first sends a prefill-only request (with `stream=false`, `max_tokens=1`, and `kv_transfer_params` containing remote decode flags) to the prefill worker, captures the `kv_transfer_params` from the response, then constructs a decode request with those transfer parameters for the local vLLM instance. This means the sidecar buffers the entire prefill response in memory before forwarding to the decoder, which is acceptable since prefill responses are small (single-token completions with metadata).

**LRU-cached proxy handlers.** Prefill targets are dynamic (specified per-request via header), so the sidecar maintains an LRU cache of 16 `httputil.ReverseProxy` instances keyed by host:port. This avoids repeated proxy construction for commonly-targeted prefill workers while bounding memory usage.

**Optional SSRF protection via InferencePool watches.** When enabled, the sidecar uses client-go dynamic informers to watch a specific InferencePool custom resource and the pods matching its label selector. It maintains a host-only allowlist (pod IPs and names) and validates prefill targets against it before proxying. The allowlist is rebuilt on every pod add/update/delete event, which is straightforward but could become expensive with very large pod sets. The protection only validates the host portion of `host:port`, meaning any port on an allowed host is permitted.

**TLS posture.** The proxy listens on TLS by default (with `MinVersion: TLS 1.2` and an explicit FIPS-compatible cipher suite list), falling back to a self-signed certificate if no cert path is provided. Upstream connections to prefill and decode targets have independently configurable TLS with optional `InsecureSkipVerify` flags, creating a risk of disabled certificate validation in production if flags are misused. The build uses `CGO_ENABLED=0` (static linking), which means Go's pure-Go crypto is used rather than OpenSSL -- this is a FIPS compliance gap for check-payload validation.
