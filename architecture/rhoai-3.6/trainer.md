## Purpose

**Short**: Kubernetes operator that orchestrates distributed ML training jobs by reconciling TrainJob custom resources against pluggable TrainingRuntime templates, coordinating with JobSet and gang-scheduling systems.

**Detailed**: Kubeflow Trainer is the training orchestration component of the Red Hat OpenShift AI platform. It implements a two-tier API where users submit lightweight `TrainJob` custom resources that reference reusable `TrainingRuntime` or `ClusterTrainingRuntime` templates. The controller resolves these references, applies ML-framework–specific plugins (PyTorch, DeepSpeed, MPI, XGBoost, MLX, JAX), and materialises the underlying `JobSet` resources to run distributed training workloads across multiple pods and nodes.

The operator employs a plugin-based runtime framework (`pkg/runtime/framework`) where each distributed training paradigm is encapsulated as a plugin that mutates the JobSet spec — injecting entrypoint scripts, environment variables, ConfigMaps, Secrets, and sidecar containers appropriate to the framework. Gang scheduling is coordinated through optional integrations with either Kubernetes Scheduler Plugins (CoScheduling) or Volcano via PodGroup CRDs. An `OptimizationJob` controller provides hyperparameter search capabilities through integration with Katib.

The RHOAI distribution adds an `ENABLE_RHAI_FEATURES` environment variable that gates RHAI-specific progression tracking (`pkg/rhai/progression`), TLS hardening via the OpenShift cluster TLS security profile, secure metrics serving with authentication and authorization, NetworkPolicies restricting ingress and egress, and a feature-gated status server that allows training pods to report runtime status back to the controller over mTLS.

## Architectural Analysis

Trainer's architecture is centred on a controller-runtime operator that acts as a coordination layer between declarative training intent (TrainJobs) and the concrete workload execution substrate (JobSets). The plugin framework is the key architectural decision — rather than hard-coding each ML framework's distributed training topology, the controller delegates to a chain of plugins that incrementally build the final JobSet specification. This makes the system extensible: adding support for a new distributed framework requires implementing the plugin interface rather than modifying controller logic.

The TLS story is notably thorough for a component operator. The controller fetches the OpenShift cluster `TLSSecurityProfile` at startup and applies it uniformly across the webhook server, the metrics server, and the status server. A profile watcher triggers a graceful controller restart when the cluster-wide TLS policy changes. HTTP/2 is disabled by default to mitigate the Rapid Reset CVEs (CVE-2023-44487, CVE-2023-39325), with an opt-in path through the `Configuration` CRD's `TLSOptions.NextProtos` field.

The status server (`pkg/statusserver`) is an architecturally interesting addition — it provides an HTTPS endpoint where training pods report progress metrics back to the controller, gated behind the `TrainJobStatus` feature flag (alpha). It uses projected service account tokens for authentication, separate rate-limited API clients, and its own TLS certificate lifecycle, establishing a secure feedback channel from workload pods to the control plane.

RBAC is segmented into three tiers for platform consumers: `training-view` (read-only, aggregated to the default `view` ClusterRole), `training-edit` (create/manage TrainJobs, read runtimes), and `training-admin` (full CRUD on all Trainer resources). The controller's own ClusterRole is broad — it needs access to JobSets, PodGroups, Secrets, ConfigMaps, Services, Deployments, NetworkPolicies, and the Trainer CRDs — reflecting its role as the central orchestration point for training workloads.

NetworkPolicies restrict the controller pod's ingress to three specific ports: webhook (9443) from the API server, status-server (10443) from training pods identified by label, and metrics (8443) from the `openshift-monitoring` namespace. Egress is unrestricted because the controller must reach the Kubernetes API server.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC via training-view/edit/admin ClusterRoles; users bind these in their namespaces | Kubernetes RBAC | ClusterTrainingRuntimes are shared across all tenants; no per-namespace admission restriction on which runtimes can be referenced |
| Data storage | Per-namespace: Secrets and ConfigMaps for training data are namespace-scoped | Kubernetes | No persistent storage managed by the controller; data isolation delegated to PVC provisioning |
| Network traffic | NetworkPolicy restricts ingress to the controller pod; no per-tenant network isolation of training pods | Kubernetes NetworkPolicy (controller pod only) | Training pods in different namespaces are not isolated by the controller; relies on cluster-level NetworkPolicy |
| Compute & resources | PriorityClass and LimitRange awareness (controller reads these); ResourceQuota enforcement delegated to Kubernetes | Kubernetes | Controller does not enforce per-tenant compute quotas directly |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; controller accesses cross-namespace resources for reconciliation | Kubernetes | Controller SA has cluster-wide read on configmaps/secrets |
| API scoping | TrainJob controller watches TrainJobs across all namespaces; reconciliation scoped by TrainJob namespace | Kubernetes (namespace-scoped CRDs) | Cluster-wide list/watch by controller is expected for operator pattern |
