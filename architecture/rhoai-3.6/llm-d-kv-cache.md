## Purpose

**Short**: KV-cache management library and services for KV-cache-aware routing in llm-d distributed LLM inference platform.

**Detailed**: llm-d-kv-cache is a pluggable KV-cache management system that provides the indexing, scoring, and event processing libraries that power KV-cache-aware routing for the llm-d distributed inference platform. The core library maintains a global, near-real-time view of KV-cache block locality across a fleet of vLLM pods, enabling schedulers to make optimal placement decisions based on which pods already hold cached KV tensors for a given prompt.

The repository contains three major subsystems: (1) the Go `pkg/kvcache` and `pkg/kvevents` libraries that form the indexer core — consumed as a library by `llm-d-router`; (2) the Python `uds_tokenizer` sidecar service that provides gRPC-based tokenization using vLLM's rendering pipeline over a Unix Domain Socket; and (3) the Python `pvc_evictor` utility that manages disk space for offloaded KV-cache blocks on Persistent Volume Claims. The KV-cache indexer libraries (`kvcache`, `kvblock`, `kvevents`) have been migrated to `llm-d-router` and this repository is transitioning to a connector/utility role.

## Architectural Analysis

The architecture follows a two-path design: a **read path** for scoring prompts against cached blocks, and a **write path** for ingesting KV-cache events from vLLM engines. On the read path, the `Indexer` accepts a tokenized prompt, computes deterministic block hashes via `TokenProcessor`, looks up which pods hold matching blocks in the `kvblock.Index`, and returns weighted scores via `KVBlockScorer`. The scoring supports multi-tier backends (GPU weight 1.0, CPU weight 0.8) and multimodal content through per-block extra features.

On the write path, `kvevents.Pool` manages a fleet of ZMQ subscribers that consume `KVEvent` messages (BlockStored, BlockRemoved, AllBlocksCleared) from vLLM engine pods. Events flow through an `EngineAdapter` abstraction for format-specific parsing, then update the shared `kvblock.Index`. The index supports multiple backends: in-memory (for testing), Redis/Valkey (for production), and a cost-aware memory variant. Redis operations use pipelining for single-RTT batch lookups and Lua scripts for atomic pruning.

The primary production deployment of the indexer libraries is as a library bundled into `llm-d-router`, not as a standalone service. The standalone examples and gRPC `IndexerService` serve as reference implementations. The UDS tokenizer sidecar provides tokenization as a separate process communicating over Unix Domain Sockets, isolating the Python ML stack (vLLM, HuggingFace transformers) from the Go router. The PVC evictor runs as a sidecar alongside vLLM pods, using a multi-process architecture (crawler, activator, deleter, folder cleaner) to manage disk space based on configurable thresholds.

A notable architectural risk is the OTLP trace exporter's use of `WithInsecure()` for gRPC connections to the OpenTelemetry collector (pkg/telemetry/tracing.go:180), with an explicit code comment indicating TLS credentials should be used in production. The gRPC tokenization service also uses insecure ports for both UDS and optional TCP listeners.
