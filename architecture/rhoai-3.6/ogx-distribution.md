## Purpose

**Short**: Containerized distribution of OGX (the Open Data Hub fork of Llama Stack) that packages a pre-configured AI/ML API server with multi-provider inference, vector storage, file processing, and agentic workflow capabilities into a production-ready container image.

**Detailed**: ogx-distribution is a packaging and build repository — it does not contain OGX application source code itself. Instead, it assembles a container image that ships the `ogx` Python package (from the `opendatahub-io/ogx` fork of Llama Stack) along with pre-installed dependencies for a wide matrix of inference, vector-store, file-processing, and tool-runtime providers. The OGX server exposes Responses, Messages (Anthropic-compatible), Batches, Inference, Vector I/O, Files, File Processors, and Tool Runtime APIs on port 8321, backed by PostgreSQL for state management.

The distribution uses an environment-variable-driven provider activation pattern: all provider configurations ship in a single `config.yaml`, and providers activate at startup only when their corresponding environment variables are set (e.g., `VLLM_URL` enables the vLLM inference provider, `OPENAI_API_KEY` enables OpenAI). This design allows the same image to serve any deployment scenario without rebuilding. Pre-trained model artifacts (docling models, HuggingFace embeddings, tiktoken encodings) are sourced at build time from a ProdSec-scanned "modelcar" OCI image rather than downloaded from external model hubs, ensuring supply-chain integrity and hermetic builds.

## Architectural Analysis

ogx-distribution follows a **build-time composition** architecture where the primary artifact is a container image assembled from three layers: (1) an AIPCC Python base image providing the runtime and pre-configured package index, (2) Python dependencies installed from a pinned lock file via Hermeto prefetch in Konflux, and (3) model/data artifacts copied from a separate modelcar container image. This three-layer approach separates concerns: the base image handles OS-level security and Python runtime, the lock file controls application dependencies, and the modelcar handles ML artifact provenance.

The build pipeline is notable for its **code generation approach** — `config.yaml`, `Containerfile`, lock files, and documentation are all auto-generated from the source-of-truth `build/build.yaml` via pre-commit hooks and build scripts. Manual edits to generated artifacts are rejected. This eliminates drift between the provider manifest and the shipped container configuration.

The **conditional provider activation** pattern (`${env.VAR:+provider-name}`) is architecturally significant: it means the OGX server always loads the full configuration but only initializes providers whose environment variables are present. This has implications for startup time (only active providers initialize) and for secret management (secrets for inactive providers can be omitted entirely).

The repository includes a dedicated **multi-tenancy integration test suite** (`tests/integration/praxis/`) that validates cross-user and cross-tenant isolation for Files and Vector Store APIs via a Praxis proxy, suggesting this distribution is designed for shared multi-tenant deployments where identity-scoped resource isolation is critical.

Authentication is **conditionally enabled** via OAuth2 token validation (`${env.AUTH_ISSUER:+oauth2_token}`). When enabled, the server enforces JWKS-based token verification with a three-tier access policy: all users can read system resources, authenticated users can create resources, and only owners can read/update/delete their own resources. The `--insecure` flag passed to `ogx run` in the entrypoint does not disable auth — it disables TLS on the listener (auth is handled at the application layer).
