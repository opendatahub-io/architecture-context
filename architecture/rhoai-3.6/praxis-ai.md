## Purpose

**Short**: AI gateway proxy that classifies, routes, translates, and applies policy to provider-native AI traffic (OpenAI, Anthropic, MCP, A2A) through a configurable filter pipeline built on the Praxis proxy runtime.

**Detailed**: Praxis AI is a high-performance, Rust-based AI gateway built on the [Praxis](https://github.com/praxis-proxy/praxis) proxy framework. It sits between AI clients (OpenAI SDK, Anthropic SDK, MCP agents, A2A tasks) and inference backends (vLLM, cloud providers), performing request classification, protocol translation, intelligent routing, credential injection, guardrail enforcement, token metering, and stateful response management.

The proxy implements a filter pipeline architecture where each request passes through a configurable chain of `HttpFilter` implementations. Filters classify traffic by provider API format (OpenAI Responses, Chat Completions, Anthropic Messages), translate between protocols (e.g., Anthropic Messages to Chat Completions), route to backends by model or capability, inject upstream credentials, enforce guardrails (NeMo), count tokens, and persist OpenAI Responses state to PostgreSQL or SQLite. The `llm-d` ext_proc integration provides Envoy external processing compatibility for the llm-d inference platform via gRPC.

Praxis AI inherits its proxy runtime, TLS, load balancing, connection pooling, and hot-reload capabilities from the Praxis core crates (`praxis-proxy-core`, `praxis-proxy-filter`, `praxis-proxy-protocol`, `praxis-proxy-tls`). All cryptography is performed through the system OpenSSL, making the proxy eligible for FIPS 140-3 compliance when built on Red Hat UBI 9 with the FIPS provider active.

## Architectural Analysis

Praxis AI's architecture follows a layered separation of concerns: the **apis** crate defines provider-specific types, request classification, and response storage contracts; the **filters** crate implements cross-cutting AI behaviors as `HttpFilter` trait objects; and the **server** crate assembles the filter registry, provisions store backends, and delegates to Praxis's Pingora-based runtime.

The most architecturally significant pattern is the **classify → route → branch** model. Classifier filters promote request attributes (API format, model name, MCP tool) to internal headers (`x-praxis-ai-*`), and routing filters match those headers to select backend clusters. This avoids request body parsing at the routing layer and keeps classification and routing independently configurable. The `intelligent_route` filter extends this with weighted overlay routing across inference, agentic, and management traffic classes.

The **FIPS posture** is unusually rigorous for a Rust project. All cryptography — SHA-256 digests, HMAC-SHA256 for AWS SigV4, TLS via rustls — goes through the system OpenSSL's EVP API, never through pure-Rust implementations. The workspace explicitly disables `aws_lc_rs` and `ring` default features on `rustls` and `tokio-rustls` to prevent accidental compilation. The FIPS build (`Containerfile.fips` on UBI 9) further strips features whose dependency trees carry non-OpenSSL crypto (policy engine, general-purpose SQLx), substituting a certificate-only PostgreSQL profile via a forked SQLx that removes password-authentication crypto. `cargo-auditable` embeds a crate manifest into the binary for Red Hat's `check-payload` scanner, and `cargo xtask fips report` validates the dependency graph against a crypto denylist. The `PRAXIS_REQUIRE_FIPS` environment variable makes the process refuse to start unless both the provider and the kernel report FIPS mode.

The **response store** architecture uses a `ResponseStoreRegistry` pipeline extension that provides per-listener store backends. Backends are provisioned asynchronously at startup via a Pingora background service, with a readiness endpoint that gates orchestrator probes on store availability. The PostgreSQL backend supports both password and certificate-only authentication, and the SQLx fork tracks `praxis-proxy/sqlx` to isolate password-auth crypto from the FIPS build.

Hot reload is achieved through a file watcher (`notify` crate) that detects config changes, rebuilds filter pipelines and store generations, and atomically swaps them into the serving runtime. The `ServerState` holds `Arc`-wrapped pipelines and health registries that the watcher updates without restarting the process.
