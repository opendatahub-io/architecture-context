## Purpose

**Short**: MLServer is a Python-based inference server implementing the KServe V2 Inference Protocol, providing both REST and gRPC APIs for serving machine learning models.

**Detailed**: MLServer is a multi-protocol inference serving runtime originally developed by Seldon Technologies and forked into the Red Hat OpenShift AI ecosystem. It implements the KServe V2 (Open Inference Protocol) dataplane specification, exposing model inference through both a FastAPI-based REST server (port 8080) and an async gRPC server (port 8081), with a separate Prometheus metrics server (port 8082).

The server's architecture is built around a pluggable runtime system: the core `mlserver` package provides the protocol-compliant serving infrastructure (request routing, adaptive batching, parallel inference pools, model lifecycle management), while ML framework integration is handled by separate runtime packages (sklearn, xgboost, lightgbm, onnx, mlflow, huggingface, catboost, alibi-detect, alibi-explain, mllib). Each runtime implements a common `MLModel` interface for loading, unloading, and performing inference against models in a particular framework.

In RHOAI deployments, MLServer runs as a KServe `ServingRuntime` container, typically managed by the KServe controller. The downstream fork introduces a security-hardened "trusted runtimes" mechanism: production container images bake an allowlist of permitted model implementations into `/etc/mlserver/trusted-runtimes.json` at build time, preventing dynamic loading of arbitrary Python code. The images use AIPCC base images and install pre-built, hash-verified wheels from the Red Hat AI Python Package Index, with CPU and CUDA variants available.

## Architectural Analysis

MLServer's architecture follows a three-layer design: a transport layer (REST via FastAPI/uvicorn + gRPC via grpc.aio), a handlers layer (DataPlane and ModelRepositoryHandlers that implement protocol logic), and a model layer (pluggable runtimes behind a registry). The `MLServer` class in `server.py` orchestrates startup by creating all three servers (REST, gRPC, optional Kafka), loading models from a repository, and managing graceful shutdown via signal handlers.

A notable design decision is the dual-mode security model introduced in the downstream fork. The presence or absence of `/etc/mlserver/trusted-runtimes.json` switches behavior between "DEVELOPMENT" mode (any model implementation allowed, dynamic loading from model folders via `sys.path` injection) and "PRODUCTION" mode (only allowlisted implementations permitted, custom environments blocked, wildcard CORS rejected). This bifurcation is enforced at multiple layers: during `ModelSettings` validation, again at the `implementation` property accessor, and via `RuntimeSecurity` API endpoints that expose the current mode. The allowlist is generated at image build time from a `TRUSTED_RUNTIMES` build arg, validated against a regex pattern, and written to a read-only file.

The gRPC server uses `add_insecure_port` — no TLS is configured at the application level. Authentication is delegated to the platform: in RHOAI, a `kube-rbac-proxy` sidecar container handles OpenShift OAuth/ServiceAccount token validation in front of both ports. The OTLP tracing exporter similarly uses `insecure=True`. This is architecturally intentional — the inference container trusts the pod-level network boundary and platform-injected sidecars for transport security.

The server supports optional Kafka integration (disabled by default) for async inference via `aiokafka`, OpenTelemetry tracing (OTLP/gRPC export, with health-check endpoints excluded), and Prometheus metrics (via `starlette-exporter` for REST and `py-grpc-prometheus` for gRPC). Adaptive batching and parallel inference pools provide throughput optimization when enabled.
