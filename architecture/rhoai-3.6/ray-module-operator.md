## Purpose

**Short**: Module operator that manages the lifecycle of the KubeRay operator (install, upgrade, status, removal) as part of the ODH modular platform architecture.

**Detailed**: The ray-module-operator is a Kubernetes controller-runtime operator that reconciles a cluster-scoped `Ray` custom resource (`components.platform.opendatahub.io/v1alpha1`). It is deployed by the ODH/RHOAI platform operator when the Ray module is enabled. Its primary responsibility is lifecycle management of the KubeRay operand — the controller that actually runs Ray distributed compute clusters on OpenShift.

The operator follows the ODH modular architecture pattern: the platform operator creates the `Ray` CR with a projected `applicationsNamespace`, and the module operator renders and applies vendored KubeRay kustomize manifests into that namespace via server-side apply (SSA) with force ownership. The reconciliation pipeline includes management-state handling (Managed/Removed), release tracking, kustomize rendering, image parameter injection via `RELATED_IMAGE_*` environment variables, cert-manager dependency checking, platform-aware resource filtering (SCC on OpenShift, skipped on vanilla Kubernetes), notebook RBAC provisioning, deployment health monitoring, distribution/version tracking from a platform ConfigMap, and garbage collection of owned operands.

The operator uses the `odh-platform-utilities` framework library for its reconciler pipeline, condition management, and garbage collection, making it a lightweight delegating controller whose complexity is in orchestration rather than in direct resource management. It embeds two sets of KubeRay manifests — one for ODH and one for RHOAI — selected at image build time via the `ODH_PLATFORM_TYPE` build argument.

## Architectural Analysis

The ray-module-operator exemplifies the ODH modular decomposition pattern where each platform component gets its own module operator responsible for operand lifecycle. The operator never directly creates Ray clusters or jobs; instead it bootstraps the KubeRay operator that provides the `ray.io` CRDs (RayCluster, RayJob, RayService, RayCronJob) for end users.

The reconciliation pipeline is designed as a linear chain of framework actions, each producing side effects on a shared `ReconciliationRequest`. This design makes the pipeline easy to reason about but creates an implicit ordering dependency: the management-state check must precede manifest rendering, which must precede cert-manager validation, which must precede deployment. The `managementStateAction` sets a "removed" extension flag that downstream actions check to skip rendering and instead trigger garbage collection.

A notable design choice is how the operator handles platform-specific resources. The `filterPlatformResources` action performs a one-time REST mapper check for the `SecurityContextConstraints` API and caches the result for the process lifetime. This lets the same binary run on both OpenShift (with SCC) and vanilla Kubernetes (without) — but it means a cluster-type change requires a pod restart.

Image parameterization follows the ODH convention of `RELATED_IMAGE_*` environment variables injected by Konflux/CSV, with fallback to `params.env` defaults. The operator copies vendored manifests to a writable temp directory before rewriting parameters, since the container filesystem is read-only under restricted SCC.

The notebook RBAC action creates a cluster-scoped `ray` ClusterRole that Workbenches uses to bind Ray permissions to Notebook service accounts, addressing the cross-module authorization boundary documented in RHOAIENG-46748. This ClusterRole intentionally avoids ownerRefs to prevent the Ray CR from being pinned in Terminating state.
