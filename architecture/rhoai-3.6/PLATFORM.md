## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.6 is a comprehensive AI/ML platform deployed on OpenShift Container Platform through a single OLM-managed operator (`rhods-operator`). The operator uses three cluster-scoped CRDs — `DSCInitialization` (platform bootstrapping), `DataScienceCluster` (component enablement), and `GatewayConfig` (ingress and auth policy) — to declaratively manage the full platform lifecycle. Components are organized as modules that the operator deploys by rendering kustomize manifests fetched from component repositories at build time and bundled via SHA-pinned references.

The platform's ingress architecture is built on Kubernetes Gateway API with an Istio data plane. The central `data-science-gateway` Gateway (GatewayClass `data-science-gateway-class`, namespace `openshift-ingress`) provides the primary HTTPS entry point with TLS termination. An EnvoyFilter (`data-science-authn-filter`) injects an HTTP `ext_authz` filter that delegates authentication to a `kube-auth-proxy` deployment — a FIPS-compliant OAuth2/OIDC proxy supporting OpenShift OAuth, OIDC, Kubernetes TokenReview, and bearer token authentication. A companion Lua filter forwards access tokens and strips OAuth2 cookies. Models as a Service (MaaS) introduces a parallel ingress path through a separate `maas-default-gateway` Gateway with Kuadrant AuthPolicy enforcement for API key and OpenShift token authentication via Authorino. The AI Gateway controller adds a third pattern using Gateway API `EnvoyExtensionPolicy` resources to wire `praxis-extproc` (a Rust-based Envoy external processor) for payload processing and model routing.

Security posture is defense-in-depth: FIPS compliance through `GOEXPERIMENT=strictfipsruntime` builds on UBI 9 PQC base images, cluster-wide TLS profile adherence (reading `apiservers.config.openshift.io/cluster`), per-component `kube-rbac-proxy` sidecars for metrics endpoints, Kuadrant/Authorino policy enforcement for tenant isolation, and comprehensive RBAC with component-specific ClusterRoles. The platform ships 175 CRDs, 218 admission webhooks, and 183 services across its 95 components.

### Central Components

**rhods-operator** is the root orchestrator with the broadest dependency surface — it deploys and manages all platform components, creates the Gateway API ingress infrastructure, deploys kube-auth-proxy for authentication, and manages RBAC propagation for admin and allowed groups. Every other component depends on rhods-operator for lifecycle management.

**KServe** is the model serving backbone with the most reverse dependencies. It defines the `InferenceService` and `LLMInferenceService` CRDs that data-science-pipelines-operator, models-as-a-service, and the llm-d stack all reference. KServe provides 27 ClusterServingRuntime definitions covering vLLM (CUDA, ROCm, Gaudi, Spyre, CPU), MLServer, and OpenVINO Model Server.

**data-science-pipelines-operator** is the pipeline orchestration hub, depending on KServe for model deployment, KubeRay for distributed compute, MLflow/mlflow-operator for experiment tracking, and managing the full Kubeflow Pipelines V2 stack including Argo Workflows.

**models-as-a-service (MaaS)** is the multi-tenant model consumption layer, integrating with KServe for model serving, Kuadrant/Authorino for authentication and rate limiting, and Gateway API for per-tenant routing. It introduces the external provider pattern via `ExternalModel` CRDs.

**odh-model-controller** (now bundled into KServe as `kserve-module-controller`) bridges KServe primitives to the RHOAI platform, managing OpenShift Routes, NetworkPolicies, RBAC, Prometheus monitoring, KEDA autoscaling, Kuadrant AuthPolicies, and NIM account integration.

**odh-dashboard** provides the unified management console with a federated micro-frontend architecture, connecting to all platform services through domain-specific Go BFF sidecars.

### Ingress Analysis

RHOAI 3.6 operates three concurrent ingress generations reflecting the platform's evolution from monolithic model serving to multi-tenant AI services:

**The data-science-gateway** is the platform's central ingress surface, created programmatically by rhods-operator's gateway controller during `GatewayConfig` reconciliation. It uses GatewayClass `data-science-gateway-class` (controller `openshift.io/gateway-controller/v1` on OpenShift, `istio.io/gateway-controller` on vanilla Kubernetes) with a single HTTPS listener on port 443 with TLS termination. The Gateway allows routes from all namespaces via `NamespacesFromAll`, enabling downstream components to register HTTPRoutes without coordination. Authentication is enforced at the gateway level by the `data-science-authn-filter` EnvoyFilter, which inserts an HTTP `ext_authz` call to `kube-auth-proxy.<ns>.svc.cluster.local:8443` at path `/oauth2/auth` before the Envoy router. This filter is fail-closed (`failure_mode_allow: false`). A companion Lua filter forwards access tokens from kube-auth-proxy responses and strips OAuth2 proxy cookies to prevent credential leakage to backends. On OpenShift, an OCP Route with `reencrypt` TLS termination provides the external entry point, targeting the auto-created Istio Service.

Source references: `rhods-operator/internal/controller/services/gateway/gateway_support.go` (Gateway creation, lines 410-483), `gateway/resources/envoyfilter-authn.tmpl.yaml` (EnvoyFilter template), `gateway/resources/kube-auth-proxy-oauth-deployment.tmpl.yaml` (auth proxy deployment), `api/services/v1alpha1/gateway_types.go` (constants).

**The MaaS gateway** (`maas-default-gateway`) represents the second ingress generation for multi-tenant AI services. MaaS does not create the Gateway itself — it expects a pre-existing Gateway and creates HTTPRoutes with `parentRef` targeting it. Authentication is handled by Kuadrant AuthPolicy resources that the maas-controller creates per tenant, configured for dual authentication: MaaS API keys (validated via HTTP callback to maas-api's `/v1/api-keys/validate` endpoint) and OpenShift tokens (validated via Kubernetes TokenReview). Authorino strips the original Authorization header and injects identity headers (`X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription`) before forwarding to backends, preventing credential exfiltration. Rate limiting is enforced per subscription via Kuadrant `TokenRateLimitPolicy` resources through Limitador.

The relationship between `maas-default-gateway` and `data-science-gateway` is **candidate**: the MaaS controller configures the gateway name via the `GATEWAY_NAME` environment variable (default `maas-default-gateway`), and the two gateways may be the same physical resource or separate Gateways in the same namespace. The exact gateway sharing model depends on the deployment configuration and the presence of Kuadrant in the cluster. Source references: `models-as-a-service/maas-controller/` (controller logic), `deployment/base/maas-api/` (HTTPRoute and AuthPolicy templates).

**The praxis-extproc integration** adds a payload processing layer to the MaaS ingress path. Deployed in `openshift-ingress` alongside the Istio gateway, praxis-extproc receives Envoy ExtProc callouts at two stages: pre-auth (promoting body-level model identifiers to `X-Gateway-Model-Name` routing headers for KServe InferencePool selection) and post-auth (running the full Praxis filter pipeline for guardrails, usage metering, and response transformation). The EnvoyFilter resources account for four Istio version naming conventions to ensure correct filter ordering relative to the Kuadrant auth filter. Dedicated ExtProc upstream clusters bypass Istio metadata exchange. Source references: `praxis-extproc/deploy/overlays/odh/` (EnvoyFilter, NetworkPolicy, DestinationRule).

**The llm-d inference-gateway** is a capability-specific gateway for distributed LLM inference, created by the llm-d-deployer Helm chart. It uses the Gateway API Inference Extension (GIE) with InferencePool and InferenceModel CRDs. The llm-d-router EPP implements the Envoy `ext_proc` protocol for intelligent routing decisions based on KV-cache locality, queue depth, model load, and scheduling priorities.

**The AI Gateway controller** introduces a fourth ingress pattern for external model providers. It creates per-model HTTPRoutes with `parentRef` targeting `maas-default-gateway` (configurable), using path-based matching (`/<namespace>/<clientName>`) and header-based matching (`X-Gateway-Model-Name` for body-routed requests). The controller manages its own Istio EnvoyFilter resources (priority 20, higher than MaaS base priority 10) with `ExtProcPerRoute` overrides to selectively enable/disable ExtProc filters on specific ExternalModel routes. Two ExtProc stages run per ExternalModel: `external-model-pre` (pre-auth, buffers body to extract model name) and `external-model` (post-auth, streamed body for intelligent routing and credential injection). Both filters are globally disabled on all routes and selectively re-enabled, providing fail-closed security. Source references: `ai-gateway-controller/pkg/controller/reconciler.go`, `config/manifests/external-model/overlays/odh/external-model-envoy-filter.yaml`.

**odh-gitops Gateway provisioning** provides the Helm-based initial provisioning of Gateway resources. On OpenShift, the `rhai-on-openshift-chart` Helm chart creates both the `openshift-ai-inference` Gateway (GatewayClass `openshift-ai-inference`) for KServe inference and the `maas-default-gateway` (GatewayClass `maas-gateway-class`) for MaaS traffic, along with their corresponding GatewayClasses (both controller: `openshift.io/gateway-controller/v1`). On XKS (vanilla Kubernetes), post-install hook Jobs create Gateways using the `istio` GatewayClass with cert-manager TLS. The chart also installs RHCL (Kuadrant/Authorino) for API authentication and the Gateway API CRDs (v1.4.0). Source references: `odh-gitops/charts/rhai-on-openshift-chart/templates/dependencies/gateway/`.

**Unresolved relationships**: The exact relationship between rhods-operator's programmatic `data-science-gateway` creation and odh-gitops' Helm-based `openshift-ai-inference` Gateway provisioning requires deployment-specific verification — these may represent different deployment modes (OLM-managed vs. GitOps-managed) or different evolutionary stages of the platform's ingress infrastructure. The `maas-default-gateway` is provisioned by odh-gitops Helm charts and consumed by both the MaaS controller and the AI Gateway controller, confirming it is a shared ingress surface.

## Deployment Architecture

### Deployment Topology

The RHOAI 3.6 platform follows a three-tier namespace topology:

**Operator tier** (`redhat-ods-operator`): The platform operator runs as a single leader-elected pod managing the entire component lifecycle. It reads platform CRDs (DSCInitialization, DataScienceCluster, GatewayConfig) and reconciles component deployments across all tiers.

**Platform services tier** (`redhat-ods-applications`): Core platform services run here — module operators (KServe, kuberay, kueue, trainer, workbenches, feast, ray, mlflow, ai-gateway, mcp-lifecycle, trustyai), the dashboard operator and its federated micro-frontend pods, data-science-pipelines-operator, model-registry-operator, and observability stack. Each module operator reconciles its own component CR (e.g., `Kserve`, `Dashboard`, `Workbenches`) and deploys child resources.

**Ingress tier** (`openshift-ingress`): Gateway infrastructure runs in the OpenShift ingress namespace — Istio proxy pods for the data-science-gateway, kube-auth-proxy (2 replicas with HPA), praxis-extproc for payload processing, and MaaS infrastructure. This namespace is shared with OpenShift's built-in router.

**User workload tier** (user namespaces): Notebooks, pipeline runs, model serving pods, TrustyAI services, MLflow instances, and feature stores are deployed in user-owned namespaces. MaaS creates per-tenant infrastructure namespaces for maas-api instances and per-tenant RBAC.

#### Manifest Consumption Pipeline

Component manifests flow through a multi-stage pipeline: component repositories contain kustomize bases and overlays → the `get_all_manifests.sh` script (or equivalent) fetches manifests at operator build time using SHA-pinned references from `manifests-config.yaml` → manifests are bundled into the operator container image under `/opt/manifests-template` → at runtime, the operator renders manifests using kustomize APIs with runtime parameters (namespace, image references, feature flags) → rendered resources are applied via server-side apply (SSA) to the cluster. This pipeline decouples operator release cadence from individual component releases while maintaining reproducibility through SHA pinning.

### Disconnected Support

Disconnected/air-gapped deployment evidence was unresolved across all 91 component analyses for this generation cycle. The structured inventory did not extract complete deterministic evidence for `RELATED_IMAGE` patterns, OLM `relatedImages`, or `oc-mirror` configurations. Based on platform architecture patterns, RHOAI supports disconnected deployment through:

- **RELATED_IMAGE environment variables**: Operators reference container images via `RELATED_IMAGE_*` environment variables (observed in models-as-a-service, odh-dashboard), enabling OLM to populate `relatedImages` in the ClusterServiceVersion for image mirroring.
- **params.env image parameterization**: All component images are parameterized through kustomize ConfigMap generation, allowing operators to substitute mirrored registry references at deployment time.
- **OLM relatedImages**: The operator CSV declares all shipped images as `relatedImages`, enabling `oc-mirror` to discover and mirror the complete image set.
- **Digest pinning**: Production images use SHA256 digest references for reproducibility and mirror compatibility.

Targeted source/configuration review is required to confirm the completeness of disconnected deployment support for individual components.

## Platform Architectural Analysis

RHOAI 3.6 represents a platform at an inflection point between its origins as a model-serving and pipeline platform and its evolution into a comprehensive AI services infrastructure. Several cross-cutting architectural themes emerge from reading all 95 component analyses together:

**Ingress architecture proliferation.** The platform now operates three distinct ingress patterns: the original `data-science-gateway` with ext_authz-based OAuth2 authentication (Istio EnvoyFilter), the MaaS pathway with Kuadrant/Authorino policy-based multi-method authentication (AuthPolicy on HTTPRoutes), and the llm-d inference-gateway with GIE ext_proc for intelligent routing. A fourth pattern is emerging through the ai-gateway-controller's use of Gateway API `EnvoyExtensionPolicy`. While each pattern addresses a legitimate need (platform authentication, multi-tenant isolation, intelligent routing, payload processing), the coexistence of Istio EnvoyFilter, Kuadrant AuthPolicy, and Gateway API EnvoyExtensionPolicy creates operational complexity. The exact sharing model between `data-science-gateway` and `maas-default-gateway` remains a candidate relationship — they may be the same Gateway instance or separate instances depending on deployment configuration.

**Authentication fragmentation.** Authentication is implemented through at least five distinct mechanisms across the platform: (1) kube-auth-proxy ext_authz at the gateway level for OAuth2/OIDC, (2) Kuadrant/Authorino AuthPolicy for MaaS API key and token authentication, (3) kube-rbac-proxy sidecars for metrics and application port protection, (4) direct Kubernetes TokenReview for service-to-service authentication, and (5) application-level bearer token validation and impersonation. While each mechanism is well-implemented individually, the layered composition creates subtle security boundaries — for example, a request to a MaaS model endpoint passes through TLS termination at the OpenShift Route, ext_authz at the Envoy proxy level, Kuadrant AuthPolicy evaluation, and then kube-rbac-proxy at the pod level, with each layer potentially operated by a different team.

**FIPS compliance as a cross-cutting concern.** RHOAI 3.6 demonstrates mature FIPS compliance architecture across both Go and Rust components. Go components use `GOEXPERIMENT=strictfipsruntime` with `CGO_ENABLED=1` on UBI 9 PQC base images, ensuring all cryptography is delegated to the system OpenSSL FIPS provider. Rust components (praxis-extproc, praxis-praxis) exclude pure-Rust cryptography features at compile time via Cargo feature flags and enforce FIPS mode at runtime via `PRAXIS_REQUIRE_FIPS`. The cluster-wide TLS profile adherence pattern (reading `apiservers.config.openshift.io/cluster` and dynamically adjusting cipher suites) is implemented consistently across rhods-operator, KServe, odh-model-controller, odh-dashboard, and kube-auth-proxy.

**The llm-d distributed inference subsystem** represents a significant architectural expansion. With 16 sub-components (llm-d, llm-d-router, llm-d-deployer, llm-d-async, llm-d-autoscaling, llm-d-kv-cache, llm-d-model-service, llm-d-pd-utils, llm-d-planner, llm-d-prism, llm-d-routing-sidecar, llm-d-benchmark, llm-d-inference-sim, llm-d-inference-payload-processor, llm-d-batch-gateway, llm-d-batch-gateway-operator), llm-d introduces disaggregated prefill/decode inference with NIXL RDMA KV-cache transfer, intelligent routing via the EPP ext_proc plugin, and asynchronous inference via Redis queuing. The llm-d-deployer Helm chart is deprecated in favor of llm-d-infra, indicating active architectural iteration.

**The MaaS multi-tenancy model** is architecturally notable for its per-tenant deployment pattern. The maas-controller deploys a dedicated maas-api instance per AITenant, rendering embedded kustomize manifests at runtime. This provides process-level tenant isolation while centralizing lifecycle management. The authentication architecture is sophisticated — Authorino validates credentials, strips the Authorization header, and injects identity headers (X-MaaS-Username, X-MaaS-Group, X-MaaS-Subscription) before forwarding to backends, preventing credential exfiltration to model endpoints. A known TLS gap exists: the DestinationRule for maas-api backend uses `insecureSkipVerify: true` because the managed gateway proxy does not mount the OpenShift service-CA bundle (tracked as RHOAIENG-61070).

**Federated micro-frontend architecture** in odh-dashboard represents a significant UI architectural pattern. Each feature area (Gen AI, Model Registry, Notebooks, MLflow, MaaS, Eval Hub) is built as an independent Webpack Module Federation remote with its own Go BFF sidecar, deployed as a separate pod with independent RBAC and NetworkPolicy. This provides strong feature isolation but increases the deployment footprint — the dashboard may include 10+ pod deployments for a fully-featured installation.

**Operator RBAC breadth.** Several operators require exceptionally broad RBAC permissions due to their integration role. The rhods-operator, odh-dashboard operator, and odh-model-controller all span 15+ API groups and 30+ RBAC rules, reflecting their role as integration layers across multiple platform subsystems. While this breadth is architecturally justified by the operators' orchestration responsibilities, it creates a wide blast radius if any operator's service account is compromised.

**CRD API evolution.** The platform is actively evolving its API surface with multiple CRDs supporting multi-version APIs: DataScienceCluster (v2→v3), LLMInferenceService (v1alpha1→v1alpha2), Platform (v1alpha1→v1alpha2), EndpointPickerConfig (v1alpha1→v1). Conversion webhooks are deployed for smooth migration, but the active v1alpha1/v1alpha2 split across KServe and llm-d CRDs indicates API stability is still being established for newer features.
