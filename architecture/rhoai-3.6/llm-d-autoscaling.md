## Purpose

**Short**: Provides KEDA autoscaling manifest blueprints and an evaluation test bed for llm-d inference deployments, replacing the deprecated Workload-Variant-Autoscaler (WVA) controller.

**Detailed**: llm-d-autoscaling serves a dual role in the llm-d inference platform. Its primary function is to provide reviewed, recommended KEDA scaling strategies (ScaledObject configurations with metric triggers, scaling behavior policies, and min/max replica settings) for prefill/decode disaggregated inference topologies. These blueprints live under `benchmark/config/scenarios/` and are designed to be backend-agnostic — the same strategy applies whether the backend is a real GPU vLLM instance, a CPU simulation, or the llm-d-inference-sim latency simulator.

The repository's second function is the evaluation test bed under `benchmark/`, built on llm-d-benchmark. This test bed stands up a scaling scenario, drives load through a harness, and captures autoscaling behavior (replicas, HPA/KEDA trigger values, latency, throughput) so that blueprint variants can be compared quantitatively.

The repository also contains, under `legacy/`, the frozen Workload-Variant-Autoscaler (WVA) — a custom GPU-aware autoscaling controller built with controller-runtime. WVA is deprecated on the main branch (last supported release: v0.9.0 on the `release-0.9` branch), frozen in `legacy/`, and staged for removal. While the legacy controller's manifests, RBAC, and code are documented below for completeness, no new work should target it.

## Architectural Analysis

The llm-d-autoscaling repository represents a strategic architectural transition from a custom controller to a KEDA-native autoscaling approach. The legacy WVA controller was a sophisticated operator that combined Prometheus metric scraping, Kalman-filter-based prediction, GPU saturation analysis, and direct scale actuation into a single binary. It watched InferencePool resources (from the Gateway API Inference Extension), HorizontalPodAutoscalers, KEDA ScaledObjects, and ConfigMaps, using these inputs to make scaling decisions based on queue depth, KV-cache utilization, and throughput analysis.

The replacement architecture deliberately eliminates the custom controller from the scaling path. KEDA reads inference metrics (queue depth, KV-cache utilization) directly from Prometheus and manages Deployment replicas through the HPA it creates. This simplifies the operational model — KEDA is a well-established CNCF project with broad ecosystem support — while the repository's role shifts to curating and validating the KEDA configurations that produce good scaling behavior for LLM inference workloads.

The benchmark test bed is architecturally significant: it provides evidence-based validation of scaling strategies using real or simulated inference backends, allowing teams to compare queue-aggressive, KV-early, token-aware, and other trigger variants before promoting them to production blueprints. The test bed uses llm-d-benchmark's standup/teardown lifecycle and supports multiple cluster configurations (Kind with emulated GPUs, real GPU clusters).

The legacy WVA controller's architecture reveals several notable patterns: conditional CRD support (KEDA ScaledObjects and LeaderWorkerSets are registered at startup only if present, with optional auto-restart when they appear later), a plugin-based coordinator system (experimental GPU rebalancing across HPAs/ScaledObjects), and dual InferencePool API version support (both `inference.networking.k8s.io/v1` and `inference.networking.x-k8s.io/v1alpha2`). The Prometheus client connection supports full mTLS with CA validation, client certificates, bearer token authentication via file-mounted tokens, and enforces minimum TLS 1.2.
