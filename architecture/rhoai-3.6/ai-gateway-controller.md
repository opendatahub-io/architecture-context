## Purpose

**Short**: Kubernetes controller that reconciles ExternalModel/ExternalProvider CRDs and manages per-tenant Praxis ExtProc dataplane installations for the AI Gateway.

**Detailed**: ai-gateway-controller is the control-plane controller for the AI Gateway subsystem in RHOAI 3.6. It is deployed as a sibling of maas-controller by ai-gateway-operator, replacing the control-plane half of the legacy payload-processing (IPP) system. The controller has two primary responsibilities implemented by two independent reconcilers.

The tenant reconciler (`pkg/tenant`) primarily watches `MaasTenantConfig` (a MaaS-owned CR) and, for each tenant that opts into Praxis (the default when the `payload-processing-type` annotation is absent or set to `"praxis"`), renders and SSA-applies a per-tenant copy of the vendored praxis-extproc manifests (Deployments, Services, EnvoyFilters, DestinationRules, NetworkPolicies, RBAC) into that tenant's Gateway namespace. It implements a race-free backend-swap handshake with maas-controller using optimistic-concurrency CAS on a `payload-processing-status` annotation, allowing per-tenant migration between Praxis and legacy IPP.

The ExternalModel reconciler (`pkg/controller`) watches `ExternalModel` and `ExternalProvider` CRDs and publishes per-model transport resources (ExternalName Services, ServiceEntries, DestinationRules for provider TLS, HTTPRoutes with weighted multi-provider selection) and a content-addressed routing overlay ConfigMap consumed by the Praxis ExtProc process. This reconciler validates provider credentials by reading Secrets directly from the API server (bypassing the cache), and uses finalizers to guarantee cleanup of routing and transport state when models or providers are deleted.

## Architectural Analysis

ai-gateway-controller is architecturally notable for its strict separation of the control plane (this controller) from the dataplane (praxis-extproc, a separate image it installs). The controller itself never handles inference traffic; it produces the routing configuration that Envoy and ExtProc consume at runtime. This split is formalized in ADR ODH-ADR-MS-0005.

The two reconcilers share a single controller-runtime manager process but operate on different primary resources. The tenant reconciler is MaasTenantConfig-primary (mirroring maas-controller's own TenantReconciler), while the ExternalModel reconciler is ExternalModel-primary. Both read MaasTenantConfig and AITenant, creating a fan-out pattern where MaasTenantConfig changes trigger both tenant infrastructure re-evaluation and model routing re-evaluation.

A critical design choice is the avoidance of Go type imports from maas-controller. Both MaasTenantConfig and AITenant are watched via `unstructured.Unstructured` with hardcoded GVKs, keeping the dependency graph minimal (no transitive pulls of KServe, Knative, KEDA, or openshift/api). This trades compile-time type safety for deployment independence.

The TOCTOU fence pattern (`aiTenantStillValidForApply`, `livePraxisBeforeWrite`) is architecturally significant: both reconcilers re-read the API server live immediately before writing cluster state, preventing stale-cache decisions during AITenant delete+recreate, gateway rehoming, or generation skew. This is a deliberate defense against informer lag during watch disruptions.

The content-addressed overlay envelope (using SHA-256 JCS-canonicalized digests) provides a tamper-detection and distribution-attestation mechanism: Praxis ExtProc can verify that its routing configuration matches the controller's intended state without an additional API call. This enables eventual-consistency guarantees between the control plane and the ExtProc dataplane.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC (ClusterRoleBinding per tenant for payload-processing-reader); provider credentials scoped by namespace | Kubernetes RBAC + Application | Cross-namespace provider references are schema-accepted but resolver skips them until authorization is implemented |
| Data storage | Per-namespace: each tenant's routing overlay ConfigMap, ExtProc config, and transport resources are namespace-scoped | Kubernetes namespace isolation | None detected |
| Network traffic | Per-tenant NetworkPolicy (payload-processing) created in gateway namespace; configurable via `--skip-network-policy` | Kubernetes NetworkPolicy | NetworkPolicy can be skipped by installer flag; EnvoyFilter ACCEPT_UNTRUSTED for ExtProc upstream clusters |
| Compute & resources | Per-tenant Deployment (payload-processing, payload-pre-processing) with resource limits (256Mi/500m) | Kubernetes resource limits | No ResourceQuota enforcement; controller does not create per-tenant quotas |
| Configuration & secrets | Per-namespace Secrets (provider API keys); per-namespace ConfigMaps (plugins config, routing overlay) | Kubernetes namespace isolation | Secret data read via APIReader bypassing cache; no cross-namespace Secret access |
| API scoping | Namespace-scoped watches with `InNamespace` filtering; ExternalModel reconciler supports optional `--external-model-namespace` restriction | Application (namespace filter predicates) | When `--external-model-namespace` is empty (default), watches all namespaces |
