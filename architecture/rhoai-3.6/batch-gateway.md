## Purpose

**Short**: OpenAI-compatible batch inference API gateway that enables large-scale, cost-optimized batch processing of LLM inference requests in Kubernetes environments.

**Detailed**: Batch Gateway is a three-component system for processing batch inference jobs alongside interactive workloads in Kubernetes. It provides full schema parity with OpenAI's `/v1/batches` and `/v1/files` endpoints, enabling clients to submit JSONL files containing up to 50,000 inference requests per job.

The system separates concerns across an API server (REST endpoint management), a batch processor (job execution with adaptive concurrency control), and a garbage collector (lifecycle cleanup and orphan recovery). The processor supports multiple dispatch modes: synchronous HTTP to an llm-d inference gateway with AIMD-based flow control, per-model routing to separate inference pools, or asynchronous dispatch through Redis-backed llm-d-async queues. Model-aware scheduling groups requests by model and system-prompt hash for prefix cache optimization.

The data layer is pluggable: PostgreSQL for job and file metadata, Redis/Valkey for priority queuing and event channels, and S3-compatible or filesystem storage for batch input/output files. Authentication and authorization are delegated to an external gateway layer (Kuadrant/Authorino), while application-level multi-tenancy enforces per-tenant data isolation through header-based tenant ID extraction and database query scoping.

## Architectural Analysis

Batch Gateway follows a producer-consumer architecture centered on a shared PostgreSQL metadata store and a Redis/Valkey priority queue. The API server acts as the producer: it validates incoming requests, persists metadata, stores input files, and enqueues jobs. The processor acts as the consumer: it polls the queue, retrieves input files, builds per-model execution plans, and dispatches inference requests downstream. This decoupling allows independent horizontal scaling — API server replicas scale with request volume while processor replicas (deployed as a StatefulSet for stable network identities) scale with throughput requirements.

A notable design decision is the processor's AIMD-based adaptive concurrency control, which dynamically adjusts per-endpoint dispatch rates based on downstream success/failure signals (429 and 5xx responses). This protects interactive traffic without manual tuning. The system supports three dispatch modes — global gateway, per-model gateways, and async dispatch via llm-d-async — providing flexibility for different deployment topologies.

The GC component includes a reconciler subsystem that watches processor pods via the Kubernetes API. When a processor pod disappears unexpectedly, the reconciler detects orphaned in-progress jobs and either re-enqueues or expires them, providing fault tolerance. This is the only component that requires Kubernetes RBAC beyond the default service account.

Authentication is entirely delegated to an external gateway (Kuadrant/Authorino), which injects the authenticated tenant identity via the `X-MaaS-Username` header. The batch gateway itself performs no authentication — this is an intentional architectural boundary where the gateway layer handles admission, API key validation, and token verification. The application then enforces tenant isolation at the data layer, with all database queries scoped by tenant ID. The `LastHeaderValue` function specifically defends against tenant spoofing by taking the last header value, as Envoy ext_authz appends auth-injected values after client-supplied ones.

TLS is configurable at two boundaries: the API server supports optional TLS termination with configurable minimum version (TLS 1.2+) and cipher suites, while the processor supports custom CAs and mTLS for outbound connections to inference gateways. The observability servers (health, metrics, pprof) always run on plain HTTP on separate ports, keeping diagnostic endpoints off the API surface.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to Kuadrant/Authorino gateway; tenant header injected after auth | External gateway (Envoy ext_authz) | No in-process auth — if the gateway is bypassed (e.g., direct pod access), the API has no authentication. The `LastHeaderValue` function mitigates header spoofing when behind ext_authz. |
| Data storage | All database queries include `TenantID` filter; tenant ID stored on every BaseIndexes record | Application (database query scoping) | Application-enforced, not database-level row security. A code bug could leak cross-tenant data. |
| Network traffic | No per-tenant NetworkPolicy; relies on namespace-level isolation and gateway enforcement | Kubernetes namespace / External gateway | No in-cluster network isolation between tenants |
| Compute & resources | Shared processor workers across all tenants; no per-tenant resource limits | Application (global concurrency limits) | One tenant's large batch could consume all worker capacity. No fairness quotas. Optional `x-gateway-inference-fairness-id` header for downstream fairness. |
| Configuration & secrets | Shared secrets (PostgreSQL URL, Redis URL, S3 keys) across all tenants | Kubernetes | Shared credentials — appropriate for this architecture where tenant isolation is at the application layer |
| API scoping | All list/get/delete operations scoped by tenant ID from request context | Application | Correct: `TenantID` is set on every `BaseQuery` used in API handlers |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL | Row-level filtering by tenant_id column | Application query filter on every database operation |
| Redis/Valkey | Shared queues | Job metadata includes tenant ID; dequeued jobs carry tenant context |
| S3/filesystem | Shared bucket/directory | File paths include tenant-scoped IDs; access goes through tenant-filtered API |
