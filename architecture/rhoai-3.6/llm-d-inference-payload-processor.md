## Purpose

**Short**: Pluggable Envoy External Processing (ext-proc) service that inspects and mutates inference request/response payloads in the llm-d data plane, enabling payload-aware routing across multiple models and LoRA adapters behind a single gateway endpoint.

**Detailed**: The Inference Payload Processor (IPP) is a gRPC service that implements Envoy's External Processing (ext-proc) API. Deployed once per inference gateway, it intercepts every HTTP lifecycle event (headers, body, trailers for both requests and responses) streamed by the proxy, runs them through a configurable plugin pipeline, and returns mutations — rewritten headers, body edits, or routing signals — back to the proxy.

IPP's flagship capability is payload-aware routing: it reads the request body (e.g. the `model` field in an OpenAI-compatible chat completion request), resolves adapter-to-base-model mappings via ConfigMap-backed reconciliation, and injects routing headers so that the proxy can direct traffic to the correct InferencePool. This complements the llm-d Router's Endpoint Picker (EPP), which selects the optimal pod *within* a pool — IPP decides **which pool**, EPP decides **which pod**.

The framework is fully pluggable. All behavior — request processing, response processing, model selection (Filter → Score → Pick), profile picking, and data-layer collection — is expressed as plugins instantiated from a `PayloadProcessorConfig` YAML. In-tree plugins cover body-field extraction, base-model header injection, model-group filtering, cost-guard scoring, session affinity, and response-header mutation. Custom plugins can be registered without forking.

## Architectural Analysis

IPP follows a clear separation between framework and policy: the core defines five extension stages (PreProcessor → ProfilePicker → Profile Request → Profile Response → PostProcessor) and a parallel data-layer pipeline (Collectors, Extractors, DataSources), while all domain logic lives in plugins. The `PayloadProcessorConfig` CRD-like resource (read from YAML, not from the Kubernetes API server) declaratively wires plugins into profiles, making deployment-time composition straightforward.

The ext-proc integration is designed for full-duplex streaming: request and response bodies arrive in chunks, are accumulated until EndOfStream, then processed. The framework handles duplicate chunk suppression (observed with Envoy 1.35+) and SSE response body parsing. Each request carries a `CycleState` that plugins use to share typed data within a single request lifecycle, while cross-request state flows through the data-layer's event-driven processor.

TLS on the ext-proc gRPC port is opt-in via `--secure-serving` (default true). When enabled, IPP generates a self-signed certificate at startup using Go's `crypto/tls` and `crypto/x509` (4096-bit RSA). In the Istio provider path, a `DestinationRule` with `tls.mode: SIMPLE` and `insecureSkipVerify: true` connects the proxy to IPP — this is acceptable for same-namespace traffic but bypasses certificate validation. No `MinVersion` or cipher suite constraints are explicitly set in the TLS config, relying on Go's defaults (TLS 1.2+ with FIPS-safe cipher suites when linked with OpenSSL, though this binary is statically compiled with `CGO_ENABLED=0`).

The RBAC footprint is minimal: a single ClusterRole granting `get/list/watch` on ConfigMaps, used by the `base-model-to-header` plugin's ConfigMapReconciler to watch adapter mappings. Namespace scoping via the `NAMESPACE` environment variable constrains the controller-runtime cache to a single namespace by default, with a multi-namespace mode available via the Helm chart.

The health check server runs on a separate plaintext gRPC port (default 9005) with no authentication — appropriate for kubelet probes but exposed without access control. The metrics endpoint (default 9090) supports optional controller-runtime-based authentication and authorization via `--metrics-endpoint-auth`.
