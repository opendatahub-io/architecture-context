## Purpose

**Short**: An algorithm-focused Python library and CLI that provides a unified interface for common LLM training, continual learning, and reinforcement learning techniques.

**Detailed**: Training Hub abstracts away backend complexity to expose common training algorithms (SFT, OSFT, LoRA, GRPO, GEPA, Embedding SFT) through intuitive Python API functions and a `thub` CLI. Each algorithm follows a Strategy + Registry pattern: an `Algorithm` abstract base class defines the training interface, a `Backend` abstract base class encapsulates the actual training implementation, and an `AlgorithmRegistry` maps algorithm names to classes and backends. This decoupling allows multiple backend implementations per algorithm — for example, GRPO supports both the ART (OpenPipe) single-GPU backend and the verl multi-GPU distributed backend.

The library is designed for use within the RHOAI ecosystem, particularly for fine-tuning LLMs on OpenShift AI clusters. It integrates with InstructLab Training for SFT, Mini-Trainer for OSFT, Unsloth/TRL for LoRA, OpenPipe ART and verl for GRPO, the gepa library for gradient-free prompt optimization, and sentence-transformers for embedding fine-tuning. Training Hub also provides cross-cutting concerns including a unified callback system that works across all backends, JIT preemption checkpointing for Kubernetes pod eviction handling, remote checkpoint mirroring to S3-compatible storage, GPU memory estimation, and training loss visualization.

## Architectural Analysis

Training Hub's architecture is centered on a clean separation between algorithm semantics and backend execution through its Strategy + Registry pattern. This design allows the same user-facing API (`sft()`, `osft()`, `lora_grpo()`, etc.) to route training to different backend implementations transparently. The registry is populated at module import time via `AlgorithmRegistry.register_algorithm()` and `AlgorithmRegistry.register_backend()` calls at the bottom of each algorithm module.

The callback system (`TrainingHubCallback`) is a notable cross-cutting concern. Backends use fundamentally different training loop abstractions — HuggingFace Trainer (LoRA), InstructLab Training (SFT), Mini-Trainer (OSFT) — but Training Hub normalizes lifecycle events into a single interface via per-backend adapter modules (`adapters/instructlab.py`, `adapters/mini_trainer.py`, `adapters/unsloth.py`). For torchrun-based backends (SFT, OSFT), callbacks must cross a subprocess boundary, so they are serialized via class-source extraction rather than pickling.

The JIT checkpointing subsystem is architecturally sophisticated: it intercepts SIGTERM signals (Kubernetes pod eviction), coordinates across distributed ranks via `torch.distributed.all_reduce` so all ranks agree to stop at the same step boundary, and optionally mirrors the saved checkpoint to S3-compatible remote storage via a background LIFO upload worker. The SFT and OSFT backends delegate preemption handling to their native `on_demand_checkpointing` mechanism and mirror checkpoints from the launcher process after workers exit, while LoRA uses the hub's own `JITCheckpointCallback` and `RemoteCheckpointSyncCallback`.

A significant architectural decision is that Training Hub is distributed as a pure Python library (published to PyPI) with no container images, Dockerfiles, or Kubernetes manifests of its own. It is consumed as a dependency by other RHOAI components that provide the containerized training environment. This means it has no direct FIPS compliance surface, no RBAC, and no network exposure — all of those concerns belong to the consuming components.
