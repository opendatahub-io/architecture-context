## Purpose

**Short**: Kubernetes operator for managing Apache Spark applications, scheduled jobs, and Spark Connect sessions on OpenShift.

**Detailed**: The Spark Operator is a Kubeflow-originated Kubernetes operator that automates the lifecycle of Apache Spark workloads on OpenShift. It provides three CRDs — SparkApplication for one-shot Spark jobs, ScheduledSparkApplication for cron-scheduled Spark jobs, and SparkConnect (v1alpha1) for persistent Spark Connect sessions — along with mutating and validating admission webhooks that inject Spark-specific pod configuration and enforce resource constraints.

The operator follows a two-deployment architecture: a controller deployment that reconciles all three CRDs and manages Spark driver/executor pod lifecycles, and a separate webhook deployment that handles admission control. Both deployments share the same container image but run different subcommands (`controller start` vs `webhook start`). A third component, the spark-operator-module controller, acts as a meta-operator within the ODH/RHOAI platform, managing the installation and lifecycle of the Spark workload operator itself via the `SparkOperator` CRD (`components.platform.opendatahub.io/v1alpha1`).

The operator integrates with the OpenShift TLS profile API (`config.openshift.io/APIServer`) to dynamically configure TLS cipher suites and minimum versions, and uses the `odh-platform-utilities` library for platform detection and manifest rendering within the RHOAI deployment model.

## Architectural Analysis

The Spark Operator exhibits a three-tier architecture pattern. At the lowest tier, the core controller and webhook handle Spark workload lifecycle — creating driver pods, monitoring executor scaling, managing Spark UI services, and enforcing admission policies. The controller uses a label-based pod ownership model (`sparkoperator.k8s.io/launched-by-spark-operator`) to track Spark pods and implements custom event handlers for pod phase transitions rather than relying solely on controller-runtime's default reconciliation triggers.

The middle tier is the module controller (`spark-operator-module`), which implements the ODH/RHOAI component management pattern. It watches the cluster-scoped `SparkOperator` CR and reconciles the full set of resources needed to deploy the workload operator: Deployments, Services, CRDs, RBAC, webhooks, NetworkPolicies, and cert-manager resources. This two-level operator pattern — a module controller managing a workload operator — provides clean upgrade and configuration boundaries but requires elevated RBAC privileges including `bind` and `escalate` permissions on RBAC resources.

TLS handling is architecturally notable. The webhook server supports two certificate provisioning modes: self-signed certificates managed internally via a Kubernetes Secret (`spark-operator-webhook-certs`) with 180-day rotation checks, or cert-manager integration for automated certificate lifecycle management. The operator also fetches the cluster-wide OpenShift TLS profile to align cipher suite and TLS version configuration with platform security policy, falling back to an "Intermediate" profile (TLS 1.2 minimum with AEAD cipher suites) when the OpenShift API is unavailable.

The RHOAI overlay adds network segmentation through dedicated NetworkPolicies: one restricting Spark pod ingress to driver-RPC (7078), block-manager (7079), Spark UI (4040), and SparkConnect gRPC (15002) ports, and another allowing metrics scraping on port 8080 from monitoring namespaces. The SparkConnect gRPC policy also enables cross-namespace access from workbench namespaces labeled with `opendatahub.io/dashboard: "true"`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC via aggregated viewer/editor ClusterRoles; spark-operator-spark ServiceAccount for driver pods | Kubernetes | Viewer/editor roles use `aggregate-to-view` and `aggregate-to-edit` labels for automatic RBAC aggregation; no application-level auth |
| Data storage | Per-namespace pods and services; no shared persistent storage | Kubernetes | Spark applications manage their own storage (PVCs, S3) — isolation depends on application-level configuration |
| Network traffic | NetworkPolicy in RHOAI overlay restricts Spark pod ingress to specific ports; cross-namespace SparkConnect access limited by namespace labels | Kubernetes NetworkPolicy | Default overlay allows all pods in the same namespace to reach Spark ports; no egress NetworkPolicy |
| Compute & resources | Webhook validates ResourceQuota compliance before admission | Kubernetes (ResourceQuota) + Application (webhook validation) | No built-in per-tenant resource limits; depends on namespace-level ResourceQuota configuration |
| Configuration & secrets | Per-namespace Secrets for Spark applications; operator secrets scoped to operator namespace | Kubernetes | Webhook certs are shared across all tenant namespaces |
| API scoping | Controller supports namespace-scoped watches via `--namespaces` flag; default is all namespaces | Application | When watching all namespaces, a single controller instance processes all tenants' workloads |
