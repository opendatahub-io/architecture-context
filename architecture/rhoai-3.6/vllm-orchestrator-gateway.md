## Purpose

**Short**: An OpenAI-compatible HTTP gateway that routes chat completion requests through the FMS Guardrails Orchestrator with configurable per-route detector pipelines for content filtering and safety enforcement.

**Detailed**: The vllm-orchestrator-gateway is a Rust-based HTTP service that sits between clients and the FMS Guardrails Orchestrator, providing controlled access to guardrailed LLM inference. It exposes dynamically-configured `/{route-name}/v1/chat/completions` endpoints, each bound to a specific set of content detectors (e.g., PII detection, regex-based filtering). When a client sends a standard OpenAI-compatible chat completion request to a route, the gateway injects the route's configured detector specifications into the payload and forwards it to the orchestrator's `/api/v2/chat/completions-detection` endpoint. If a detection is triggered, the gateway substitutes the model's response with a configurable fallback message.

The gateway supports both streaming (SSE) and non-streaming chat completions. It can optionally establish mTLS connections to the orchestrator when TLS certificates are mounted at well-known paths (`/etc/tls/private/`), and it accepts a custom CA certificate for trust chain verification. The service is deployed as a single stateless binary configured via a YAML file that defines the orchestrator backend, detector definitions, and route-to-detector mappings. This enables platform operators to expose multiple guardrailed endpoints with different safety policies from a single gateway instance, providing a drop-in replacement for unguardrailed OpenAI-compatible model endpoints.

## Architectural Analysis

The gateway follows a straightforward reverse-proxy pattern with payload enrichment. At startup, it reads a YAML configuration that declares an orchestrator backend, a set of named detectors with their parameters and input/output scope, and routes that map URL paths to detector subsets. Each route is registered as a POST handler in an Axum router, creating a dynamic endpoint surface driven entirely by configuration.

The request path is simple: receive an OpenAI-compatible chat completion request, determine whether streaming is requested (via the `stream` boolean in the JSON payload), inject the route's detector configuration into the `detectors` field of the payload, and forward the enriched request to the orchestrator. The gateway forwards `Authorization` and `X-Forwarded-*` headers transparently, maintaining the client's identity context through to the orchestrator. For non-streaming responses, the gateway checks for detections in the orchestrator's response and replaces the generation with a route-specific fallback message when triggered. For streaming responses, the gateway parses each SSE chunk and applies the same detection-to-fallback logic per chunk.

The TLS architecture is notable: the gateway probes for certificate files at fixed well-known paths at startup and conditionally upgrades the outbound connection to mTLS. This is designed for OpenShift service-serving certificate integration, where the service CA and per-service certificates are automatically provisioned. The `danger_accept_invalid_hostnames(true)` call when the orchestrator hostname is `localhost` is a development convenience for local testing and does not affect production deployments where the orchestrator is reached via its Kubernetes service DNS name.

The configuration validation at startup catches misconfigured routes (referencing undefined detectors or having duplicate detector servers on the same input/output direction), which provides fail-fast behavior that prevents runtime routing errors. The gateway is entirely stateless — it maintains no session data, caches, or persistent storage — making horizontal scaling trivial.
