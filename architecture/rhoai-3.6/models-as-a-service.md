## Purpose

**Short**: Models as a Service (MaaS) provides a Kubernetes-native platform for managing multi-tenant inference model endpoints with real-time policy management, API key lifecycle, and Gateway API-based routing.

**Detailed**: MaaS is a multi-component system that enables platform administrators to expose AI/ML inference models to tenant users through a managed subscription model. The platform bootstraps isolated tenant environments via the AITenant CRD, which provisions per-tenant namespaces, Gateway references, RBAC, and network policies. Tenants subscribe to model endpoints via MaaSSubscription resources, and the system manages the full lifecycle of API keys, rate limiting (via Kuadrant TokenRateLimitPolicy), and authentication policy (via Kuadrant AuthPolicy with Authorino).

The system integrates with KServe's LLMInferenceService for on-cluster model serving and supports ExternalModel resources that route inference requests to external providers (OpenAI, Anthropic, etc.) with per-provider credential injection. Gateway API HTTPRoutes are dynamically reconciled for each model and subscription, providing a unified ingress surface. The controller embeds kustomize manifests and deploys the maas-api service per-tenant via its Tenant reconciler, creating a self-managing deployment topology. A discovery service provides tenant enumeration for cross-namespace visibility. The maas-controller also manages guardrails integration, allowing AIGuardrail policies to be attached at tenant and subscription scopes with additive semantics.

## Architectural Analysis

MaaS follows a three-tier architecture: a central controller (maas-controller) that manages the platform lifecycle, per-tenant API services (maas-api) that handle user-facing operations, and a discovery service (maas-discovery) that provides tenant enumeration. The controller operates as a self-deploying operator — it embeds kustomize manifests inside its container image and renders per-tenant deployments of maas-api at runtime, making the API service a controller-managed workload rather than an independently deployed component.

The tenant isolation model is architecturally significant. Each AITenant creates a dedicated namespace with its own maas-api Deployment, Service, HTTPRoutes, NetworkPolicies, and Kuadrant AuthPolicy. This per-namespace deployment provides strong isolation at the Kubernetes level — tenants cannot access each other's API services because NetworkPolicies restrict ingress to the Gateway and monitoring namespaces. The controller also provisions per-tenant RBAC and ClusterRoleBindings to scope the maas-api service account's access.

Authentication is layered: Kuadrant/Authorino sits at the Gateway level and validates requests using API keys, Kubernetes TokenReview, or optional OIDC JWT before traffic reaches maas-api. The controller programmatically creates Kuadrant AuthPolicy resources that strip the Authorization header before forwarding to model backends, preventing credential exfiltration — a design choice documented as a hard requirement for MaaS v0.1.0+. Internal cleanup routes use dedicated ServiceAccount tokens validated via TokenReview.

The integration with KServe is conditional — the controller watches LLMInferenceService resources only when the CRD is installed, enabling graceful degradation on clusters without KServe. Similarly, the InferenceObjective CRD from llm-d is conditionally watched to support inference scheduling priorities. This conditional watch pattern means the controller's RBAC surface adapts at runtime to the available APIs.

The use of a PostgreSQL database for API key storage introduces a stateful dependency that does not exist in most ODH/RHOAI controllers. The database connection secret (maas-db-config) is the only secret the maas-api ClusterRole can read, restricted by resourceNames in the RBAC definition. The controller also manages a separate database secret for the controller's own PostgreSQL needs.

OpenShift TLS security profile integration is notable: both maas-api and maas-discovery fetch the cluster-wide TLS profile from `config.openshift.io/v1/APIServer` and apply it to all TLS listeners, with a watcher that triggers process restart on profile changes. This ensures the components honor cluster-level TLS policy rather than hardcoding cipher suites.
