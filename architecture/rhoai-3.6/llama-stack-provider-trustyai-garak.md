## Purpose

**Short**: Garak red-teaming evaluation adapter for the eval-hub platform, enabling automated LLM vulnerability scanning via Kubernetes Jobs or Kubeflow Pipelines.

**Detailed**: This component provides a `FrameworkAdapter` implementation for the eval-hub evaluation SDK used by the RHOAI evaluation platform. It integrates NVIDIA's Garak red-teaming framework to perform automated vulnerability assessments against Large Language Models, covering prompt injection, jailbreaks, toxicity, bias, OWASP LLM Top 10, and AVID taxonomy benchmarks.

The adapter supports two execution modes: **Simple** mode runs garak as a subprocess directly inside the eval-hub Kubernetes Job pod, while **KFP** mode submits a six-step Kubeflow Pipeline (validate → taxonomy → SDG → prompts → scan → parse) that executes garak in a separate KFP pod with S3-based artifact transfer. KFP mode is required for the "intents" benchmark, which uses Synthetic Data Generation (SDG) and TAPIntent adversarial probes for policy-taxonomy-driven risk assessment.

Despite its name referencing "llama-stack-provider," all Llama Stack provider code was removed as of v0.5.0. The package is now exclusively an eval-hub adapter. The component is not deployed independently — it is packaged as a container image that eval-hub orchestrates as Kubernetes Jobs. Configuration is read from a mounted ConfigMap (`/etc/eval-job/spec.json`), and model API keys are injected via Kubernetes Secrets.

## Architectural Analysis

The adapter follows a plugin architecture centered on the eval-hub SDK's `FrameworkAdapter` interface. The `GarakAdapter` class implements `run_benchmark_job()` which dispatches to either local subprocess execution or KFP pipeline orchestration based on the resolved execution mode. A subclass `GarakKFPAdapter` hardcodes KFP mode for dedicated KFP orchestrator deployments.

Configuration resolution is layered: predefined benchmark profiles (OWASP, AVID, intents, etc.) in `config.py` serve as the base, user overrides from the JobSpec are deep-merged on top via `deep_merge_dicts`, and the intents model overlay fills empty model endpoint slots while always forcing API keys to `__FROM_ENV__` for Kubernetes Secret injection. This prevents accidental credential leakage — API keys are redacted from `config.json` before any persistence (S3 upload, OCI artifact, or Files API).

The KFP pipeline architecture uses `dsl.component` decorators with `install_kfp_package=False` and the component's own container image as the base, meaning all six pipeline steps run inside pods containing the full adapter code. S3 credentials are injected into every step via `kubernetes.use_secret_as_env`, and model auth secrets are volume-mounted at `/mnt/model-auth` with `optional=True`. The pipeline resolves its own base image from three sources: KFPConfig, environment variable, or a Kubernetes ConfigMap (`trustyai-service-operator-config`) looked up in the `redhat-ods-applications` or `opendatahub` namespaces.

The credential management strategy is noteworthy: `resolve_api_key()` implements a 13-step resolution chain that checks environment variables, KFP secret volume mounts, and evalhub SDK secret readers in priority order, with per-role overrides (target, judge, attacker, evaluator, SDG) falling back to a generic `api-key`. This allows single-key deployments to work without any role-specific configuration while supporting multi-model intents workflows that need distinct keys per role.

A significant design consideration is the S3 credential resolution in `_read_s3_credentials_from_secret()`, which implements five fallback strategies to handle the evolution of the evalhub auth model: direct K8s API, KFP auth token, sidecar proxy (evalhub >= 0.4.4), model auth secret, and local kubeconfig. The sidecar proxy model sets `AutomountServiceAccountToken=false`, so the adapter must handle both auth models transparently.
