## Purpose

**Short**: Kubernetes operator that deploys and manages the notebook workbench infrastructure (Kubeflow notebook controller, ODH notebook controller, and notebook manifests) on OpenShift for the Open Data Hub / Red Hat OpenShift AI platform.

**Detailed**: The workbenches-operator reconciles a cluster-scoped singleton `Workbenches` custom resource (`default-workbenches`) and deploys the complete notebook controller stack via server-side apply of upstream Kustomize manifests. It acts as a standalone module operator within the ODH platform orchestration model, where the platform orchestrator creates and updates the `Workbenches` CR and projects fields like `platform`, `gatewayDomain`, and `mlflowEnabled` from platform-level configuration.

When `managementState` is `Managed`, the operator renders upstream Kustomize manifests from `/opt/manifests` (baked into the container image for hermetic/airgapped builds), overlays `RELATED_IMAGE_*` environment variables onto image parameter files, merges CR-derived parameters, and applies resources to the cluster via server-side apply (SSA) with field manager `workbenches-operator`. The operator watches owned resources for drift reconciliation and monitors operand Deployment availability for status reporting. It uses the platform ModuleStatus lifecycle model to derive `status.phase`.

The operator also provides two mutating admission webhooks: one for injecting connection secrets into Notebook resources based on the `opendatahub.io/connections` annotation, and another for applying hardware profile resource constraints (CPU/memory/GPU), tolerations, nodeSelector, and Kueue queue-name labels based on the `opendatahub.io/hardware-profile-name` annotation on Notebooks.

## Architectural Analysis

The workbenches-operator exemplifies the ODH/RHOAI "module operator" pattern: a dedicated controller owns a single component CRD and is itself deployed by the platform orchestrator's Helm chart. The operator's primary reconciliation loop is manifest-driven — it reads Kustomize bundles from the filesystem, renders them with runtime parameters, and applies the result via SSA. This design decouples the operator from upstream manifest evolution; manifest updates are committed to `opt/manifests/` and baked into the container image, which ensures airgapped/disconnected deployment without network dependencies at runtime.

A notable architectural decision is the TLS bootstrap pipeline. At startup, the operator probes the cluster for OpenShift's APIServer TLS security profile and configures cipher suites and minimum TLS version for both the metrics server and webhook server. On non-OpenShift clusters, Mozilla Intermediate defaults are applied. A runtime watcher triggers graceful shutdown on TLS profile changes, forcing the pod to restart with updated settings. The webhook TLS provider is auto-detected (OpenShift service-CA → cert-manager → None), and a periodic ensurer handles late-appearing cert infrastructure.

The operator's RBAC footprint is broad because it must create the entire notebook controller stack (Deployments, Services, RBAC, CRDs, WebhookConfigurations, ImageStreams, NetworkPolicies, ServiceMonitors). The `rbac_escalate_role.yaml` grants `bind` and `escalate` verbs scoped to specific named ClusterRoles from the upstream manifests — a deliberate constraint to limit privilege escalation surface. The ConfigMap informer cache is namespace-scoped to the resolved applications namespace (or both platform defaults when unset), partially addressing the cluster-wide watch concern.

The optional workbenches-v2 submodule (Kubeflow Workspaces controller) is gated behind `spec.workbenchesV2.managementState` and defaults to `Removed`, indicating the Workspaces API is not yet GA.
