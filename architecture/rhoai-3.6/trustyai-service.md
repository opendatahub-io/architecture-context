## Purpose

**Short**: Python REST API for Responsible AI workflows providing drift detection, fairness monitoring, and model explainability on live inference streams within RHOAI and ODH.

**Detailed**: TrustyAI Service is a FastAPI-based microservice that serves as the runtime component for AI model monitoring in the Red Hat OpenShift AI platform. It consumes inference data from KServe and ModelMesh deployments via CloudEvents, stores the data in one of two backends (PVC/HDF5 or MariaDB), and computes statistical metrics on a configurable schedule. The computed metrics are published to Prometheus for alerting and dashboard integration.

The service exposes three categories of metrics: drift detection (Kolmogorov-Smirnov, Jensen-Shannon, Compare Means, Maximum Mean Discrepancy), fairness (Statistical Parity Difference, Disparate Impact Ratio), and explainability (LIME, SHAP, Counterfactuals, PDP — disabled by default). Endpoint availability is controlled by a feature flag system using `TRUSTYAI_ENABLE_*` environment variables, allowing operators to enable or disable metric categories per deployment.

The service runs a dual-server architecture: a main application server behind kube-rbac-proxy for authenticated API access, and a separate health/consumer server bound to all interfaces for Kubernetes probes and KServe inference payload ingestion. TLS is optional and delegates cipher/version selection to the operating system's crypto policy via a custom Hypercorn Config subclass, ensuring automatic compliance with cluster TLS profiles.

## Architectural Analysis

TrustyAI Service follows a layered architecture with clean separation between endpoint routing, metric computation, data persistence, and observability publishing. The core design choice is a **dual Hypercorn server** pattern: the main FastAPI application binds to `127.0.0.1:8081` (HTTP, for kube-rbac-proxy forwarding) and optionally `0.0.0.0:4443` (HTTPS, direct access), while a minimal health FastAPI application binds to `0.0.0.0:8080` for Kubernetes probes and KServe consumer endpoints. This split enables the service to receive unauthenticated health probes and inference payloads on port 8080 while protecting the metric computation and metadata API behind kube-rbac-proxy on port 8081.

The storage layer uses an abstract `StorageInterface` with two implementations: `PVCStorage` (HDF5 files on a PersistentVolumeClaim) and `MariaDBStorage` (relational, with TLS support via CA certificate). A built-in `PVCToDBMigrator` supports idempotent migration from PVC to MariaDB with per-file progress tracking and Prometheus counters for observability. The storage backend is selected at startup via the `SERVICE_STORAGE_FORMAT` environment variable, and MariaDB support is an optional dependency (`pip install trustyai-service[mariadb]`).

The Prometheus integration is more than a simple scrape endpoint. A `PrometheusScheduler` runs as a background `asyncio` task on a configurable interval (default 30s), iterating over registered metric requests, computing values against the latest inference data batch, and publishing them as Prometheus gauges. Each metric endpoint supports four operations: compute (one-shot), definition (metadata), request (register for scheduled computation), and requests (list registered). This design allows both ad-hoc metric queries and continuous monitoring without client polling.

A notable risk is the absence of application-level authentication middleware in the FastAPI application. The service relies entirely on kube-rbac-proxy as a sidecar for authentication and authorization. If deployed without kube-rbac-proxy (e.g., in development or misconfigured environments), all endpoints are accessible without authentication. The health port (8080) is intentionally unauthenticated for kubelet probes but also serves the KServe consumer endpoints, meaning inference data ingestion has no application-level auth gate.
