## Purpose

**Short**: A Kubernetes module operator that manages the lifecycle of AI Gateway sub-components (batch-gateway-operator, maas-controller, and ai-gateway-controller) within the OpenDataHub/RHOAI platform.

**Detailed**: The ai-gateway-operator is a module operator that runs under the opendatahub-operator framework, reconciling a singleton cluster-scoped `AIGateway` custom resource. Rather than implementing inference or routing logic itself, it acts as a lifecycle manager for three vendored sub-components: the batch-gateway-operator (for LLM batch inference via llm-d), the maas-controller (for Models as a Service multi-tenant model access), and the ai-gateway-controller (for gateway-level traffic routing and guardrails via Kuadrant and Praxis). Each sub-component is toggled independently via `spec.batchGateway.managementState` and `spec.modelsAsAService.managementState` fields on the AIGateway CR, with supported values of `Managed` or `Removed`.

The operator vendors its sub-component manifests at build time from upstream repositories (pinned by commit SHA via `hack/scripts/get-manifests.sh`), renders them through kustomize with image and namespace parameter substitution sourced from the opendatahub-operator's RELATED_IMAGE environment variables, and deploys them into the platform's applications namespace. It manages the full RBAC escalation chain needed to grant sub-components their required cluster permissions and implements a graceful teardown protocol for MaaS that coordinates with the maas-controller's self-cleanup before garbage-collecting its resources.

## Architectural Analysis

The ai-gateway-operator follows the ODH modular architecture pattern where the platform operator (opendatahub-operator) delegates component lifecycle to purpose-built module operators. This design isolates the AI Gateway domain's complexity — which spans batch inference, multi-tenant model access, and gateway routing — from the platform operator's codebase while maintaining a single upgrade and status reporting surface.

The most architecturally significant pattern is the two-phase teardown protocol for MaaS removal. When `modelsAsAService` transitions from `Managed` to `Removed`, the operator does not immediately delete the maas-controller's resources. Instead, it annotates the maas-controller Deployment with `maas.opendatahub.io/teardown-requested=true`, keeps the manifests rendered so the controller can execute its own self-teardown (deleting Config/default, cleaning up runtime resources), and only garbage-collects the bundle after the maas-controller signals completion via a `maas.opendatahub.io/teardown-completed=true` annotation on its own Deployment. This prevents data loss and ensures tenant resources are properly cleaned up. The ai-gateway-controller rides along on the same lifecycle toggle because the Praxis extproc may still be serving traffic that MaaS's teardown depends on.

A second notable pattern is the platform upgrade handshake. The platform operator maintains a ConfigMap (`odh-aigateway-config`) containing `data.platformVersion`. After all reconciliation actions succeed, the module operator echoes this version into `status.releases` on the AIGateway CR, allowing the platform to detect version alignment. The `withPreservedPlatformRelease` wrapper ensures that a failed reconcile cannot wipe a previously established handshake entry.

The operator resolves the cluster's TLS profile from the OpenShift APIServer resource at startup and registers a SecurityProfileWatcher that triggers a graceful restart when the profile or adherence policy changes, ensuring metrics serving always matches cluster policy.

The RBAC surface is wide (61 rules on the manager role) because the operator must hold escalation privileges for every permission granted within the vendored sub-component ClusterRoles (batch-gateway-operator, maas-controller, ai-gateway-controller). This is a deliberate tradeoff of the module operator pattern: the parent must be able to create and patch the children's RBAC without escalation errors.
