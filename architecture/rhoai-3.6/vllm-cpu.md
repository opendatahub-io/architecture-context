## Purpose

**Short**: CPU-optimized build of vLLM, a high-throughput inference and serving engine for large language models, providing OpenAI-compatible and multi-protocol API endpoints.

**Detailed**: vllm-cpu is a downstream fork of the vLLM project maintained by Red Hat Data Services for inclusion in Red Hat OpenShift AI. It provides a high-throughput, memory-efficient inference server for deploying LLMs on CPU hardware without GPU requirements. The server exposes an OpenAI-compatible REST API (chat completions, completions, embeddings, models) plus additional protocol support for Anthropic Messages, scoring/reranking, speech-to-text, and an optional gRPC interface.

The component is packaged as a container image built from a Konflux Dockerfile targeting multiple CPU architectures (x86_64, ppc64le, s390x). It uses FastAPI with Uvicorn as the HTTP server and supports optional TLS with runtime certificate refresh. Authentication is implemented via an optional API key middleware. vLLM supports advanced inference features including continuous batching, PagedAttention for memory management, LoRA adapter hot-loading, tensor parallelism, data parallelism, and disaggregated prefill/decode serving.

The repository also contains Dockerfiles for GPU accelerator variants (CUDA, ROCm, HPU/Gaudi, TPU) as non-Konflux builds. The Konflux pipeline builds only the CPU variant (`Dockerfile.konflux.cpu`).

## Architectural Analysis

vLLM's architecture follows a modular router-based pattern where API protocol surfaces (OpenAI, Anthropic, SageMaker, disaggregated inference) are implemented as independent FastAPI `APIRouter` instances composed into a single ASGI application. The server entry point (`vllm.entrypoints.openai.api_server`) dynamically includes routers based on the model's supported tasks (generate, embed, classify, score, speech-to-text, etc.), meaning the actual API surface varies per deployment.

The authentication layer is notably thin — a single optional ASGI middleware that validates bearer tokens against a static list. TLS is delegated to Uvicorn's built-in SSL support with an additional file-watcher (`SSLCertRefresher`) that reloads certificates on disk changes, enabling rotation without restarts. There is no mTLS enforcement at the application level; mutual TLS would need to be provided by the platform (e.g., Istio/Service Mesh).

A key FIPS concern is the default multimodal content hasher: `VLLM_MM_HASHER_ALGORITHM` defaults to `blake3`, which is not FIPS 140-3 compliant. The environment variable can be set to `sha256` or `sha512` for FIPS-compliant deployments, but this requires explicit operator configuration. The extensive use of `hashlib.sha256` throughout the codebase for compilation caching, model hashing, and content-addressable storage is FIPS-safe since Python's `hashlib` delegates to OpenSSL on UBI images.

The build does not use AIPCC base images, instead building directly on `ubi9/ubi-minimal-pqc`. Python packages are installed via `uv` from PyPI and the PyTorch CPU index without Hermeto/cachi2 prefetch, making the build non-hermetic at the Python package layer. This represents a supply chain gap for production builds.
