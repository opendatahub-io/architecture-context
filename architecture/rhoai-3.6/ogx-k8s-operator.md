## Purpose

**Short**: Kubernetes operator that deploys and manages OGX (Open GenAI Stack) server workloads, providing declarative lifecycle management for AI inference stacks with multiple distribution backends.

**Detailed**: ogx-k8s-operator is a two-level Kubernetes operator that manages the full lifecycle of OGX server deployments on OpenShift. The primary controller (`OGXServerReconciler`) watches `OGXServer` custom resources and reconciles Deployments, Services, PVCs, NetworkPolicies, PodDisruptionBudgets, HPAs, Ingresses, and monitoring resources for each server instance. It supports multiple distribution backends (starter, remote-vLLM, meta-reference-gpu, postgres-demo) via an embedded distribution registry with runtime image override capability.

The repository also contains a separate `ogx-module` controller that operates as an ODH/RHOAI platform module. This module-level controller watches the cluster-scoped `OGX` CR (from the `components.platform.opendatahub.io` API group) and manages the deployment of the root OGX operator itself, rendering kustomize manifests with platform-specific overlays (ODH vs RHOAI). This two-tier design separates platform component lifecycle management from the user-facing workload management, enabling the platform operator to control when and how the OGX operator is deployed while the OGX operator independently manages individual inference server instances.

The operator includes legacy adoption logic for migrating resources from the previous `LlamaStackDistribution` CRD (the project was renamed from LlamaStack to OGX), and supports Praxis-fronted mode where OGX servers operate as internal-only backends behind the Praxis Responses API.

## Architectural Analysis

The ogx-k8s-operator demonstrates a carefully layered architecture with clear separation between platform lifecycle management and workload management. The `ogx-module` controller acts as a bridge between the ODH/RHOAI platform operator and the OGX workload operator, using the `odh-platform-utilities` library for standardized manifest rendering, garbage collection, and condition management. This modular design allows the OGX operator to function independently on vanilla Kubernetes (via cert-manager overlay) or within the OpenShift platform (via service-serving-cert-signer overlay).

The reconciliation pipeline in `OGXServerReconciler` uses kustomize with Go-based transformer plugins rather than raw template rendering. Manifests are stored in `controllers/manifests/base/` and transformed at reconcile time with name prefixes, namespace injection, field mutations, and NetworkPolicy transformations. Resources are applied via Server-Side Apply with field owner `ogx-operator`, providing safe concurrent updates and ownership tracking. PVCs are intentionally excluded from ownerRef to prevent data loss on CR deletion, and a `Recreate` deployment strategy avoids RWO multi-attach deadlocks.

TLS configuration is notable: on OpenShift, the operator fetches the cluster-wide TLS profile from the `APIServer` resource and dynamically configures cipher suites and protocol versions for both the webhook server and metrics endpoint. A `SecurityProfileWatcher` monitors for TLS profile changes and triggers a restart. The fallback for non-OpenShift clusters is the Intermediate TLS profile. The operator cache is label-scoped — ConfigMaps require `ogx.io/watch: "true"` and managed resources use `app.kubernetes.io/managed-by: ogx-operator` — limiting watch scope and reducing API server load.

The validating webhook enforces distribution name validity, Praxis mode constraints, and immutability rules. When Praxis mode is enabled, the webhook emits warnings about Tech Preview status and warns (but does not reject) configurations that would weaken the internal-only network posture, preserving backward compatibility with existing CRs and GitOps workflows.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC aggregation roles (editor/viewer) scoped to ogx.io resources; platform RBAC for namespace access | Kubernetes | Operator itself has cluster-scoped access; per-tenant isolation relies on platform namespace RBAC |
| Data storage | Per-namespace PVCs with ownerRef exclusion (intentional, prevents data loss) | Kubernetes | PVCs persist after CR deletion by design; manual cleanup required |
| Network traffic | Operator-managed NetworkPolicy per OGXServer deployment; Praxis mode restricts to internal-only | Kubernetes / Application | NetworkPolicy can be disabled via CR spec; Praxis mode warns but does not reject insecure config |
| Compute & resources | HPAs and PDBs per OGXServer; no cross-namespace resource isolation | Kubernetes | No ResourceQuota or LimitRange enforcement; depends on platform-level quota |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; operator config is cluster-scoped | Kubernetes | Operator config ConfigMap is shared across all tenants; secret access is read-only (get, list, watch) |
| API scoping | OGXServerReconciler watches are scoped to the owning CR's namespace via ownerRef | Kubernetes | Operator cache uses label selectors (`ogx.io/watch`, `managed-by`), not namespace selectors |
