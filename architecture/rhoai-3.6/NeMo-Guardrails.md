## Purpose

**Short**: NeMo Guardrails is an open-source toolkit for adding programmable guardrails to LLM-based conversational systems, providing input/output rail enforcement, jailbreak detection, content safety, and fact-checking capabilities.

**Detailed**: NeMo Guardrails provides a programmable layer between application code and LLMs that enforces safety, topicality, and behavioral constraints on conversations. The toolkit supports two generations of the Colang domain-specific language (v1.0 and v2.x) for defining rails — declarative rules that control what an LLM can say, how it responds to specific topics, and which external tools it can invoke. The library ships over 30 built-in guardrail types (jailbreak detection, content safety, PII detection via Presidio, fact-checking via AlignScore, hallucination detection, prompt injection detection, and integrations with third-party moderation services).

The Red Hat fork adds a `/v1/guardrail/checks` endpoint for stateless message checking without LLM generation, header forwarding to upstream LLM providers, OpenTelemetry auto-instrumentation support, and a UBI9/AIPCC-based Konflux build with baked-in ML models (MiniLM, Snowflake Arctic, spaCy, NLTK punkt, DeBERTa for prompt injection, and Granite Guardian HAP). The server runs as a FastAPI application behind uvicorn, exposed on port 8000, and supports configuration-driven multi-rail pipelines loaded from YAML config directories.

## Architectural Analysis

NeMo Guardrails follows a pipeline-oriented architecture where incoming messages traverse a configurable chain of input rails, optionally invoke an LLM, and then pass through output rails before returning a response. The modern `Guardrails` class delegates to `IORails` for input/output rail dispatch or to the legacy `LLMRails` for the full event-driven Colang pipeline. Configuration is YAML-driven via `RailsConfig`, with each deployment mounting a config directory where subdirectories represent independent guardrail configurations selectable at request time.

The HTTP layer is built around a transport-neutral abstraction (`nemoguardrails/http/`) with configurable TLS (custom CA bundles and mutual TLS via `HTTPTLSConfig`) and retry policies. Outbound LLM calls route through a framework/provider abstraction supporting both a default OpenAI-compatible client and an optional LangChain framework. The codebase uses MD5 for cache key hashing with an automatic SHA-256 fallback when MD5 is unavailable (FIPS-mode environments), demonstrating awareness of FIPS constraints at the application level.

The Konflux build uses a multi-stage Dockerfile that sources an AIPCC CPU base image (`quay.io/aipcc/base-images/cpu-el9.8`), copies pre-trained models from six modelcar init containers (via `registry.redhat.io/rhai/modelcar-*`), creates a virtual environment with pinned dependencies, and produces a lean runtime image running as UID 1001. The entrypoint script validates configuration inputs, prevents command injection, and optionally wraps the server process with OpenTelemetry auto-instrumentation when `OTEL_EXPORTER_OTLP_ENDPOINT` is set.

A security-relevant design consideration is the large number of third-party guardrail integrations (ActiveFence, AI Defense, Pangea, Patronus, CrowdStrike, F5, and others), each requiring its own API key delivered via environment variables. These integrations are optional and lazily imported, but when deployed they establish outbound HTTPS connections to external SaaS services, expanding the network trust boundary.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-config authentication; bearer token forwarded to upstream LLM only | Application | No isolation between configurations; any client can use any config_id |
| Data storage | In-memory LLMRails instances keyed by config_id; no persistent state | Application | Conversation history cached per-instance in memory; no cross-config data leakage |
| Network traffic | All configurations share the same server process and port | Application | No network-level separation between configurations |
| Compute & resources | Shared process; no per-config resource limits | Application | One configuration's load can impact others |
| Configuration & secrets | Per-config YAML files mounted at `/app/config/<config_id>/` | Filesystem | Environment-variable API keys are shared across all configurations |
| API scoping | config_id parameter selects configuration at request time | Application | All configurations are accessible to all clients |
