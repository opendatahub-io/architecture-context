## Purpose

**Short**: Standalone operator that reconciles the Trainer CR to deploy and manage upstream Kubeflow Trainer v2 resources on OpenShift via kustomize rendering and Server-Side Apply.

**Detailed**: The trainer-operator is a module controller within the ODH/RHOAI modular architecture. It watches a singleton cluster-scoped `Trainer` CR (`components.platform.opendatahub.io/v1alpha1`) named `default-trainer` and deploys the complete upstream Kubeflow Trainer v2 stack — including the trainer controller-manager, CRDs for TrainJobs, ClusterTrainingRuntimes, TrainingRuntimes, and OptimizationJobs, along with RBAC, admission webhooks, network policies, and a ServiceMonitor.

The operator uses a build-time manifest pipeline: upstream Kubeflow Trainer manifests are fetched by `hack/get_trainer_manifests.sh` and baked into the container image under `/opt/manifests-template/`. At runtime, templates are copied to a writable work directory, `RELATED_IMAGE` environment variable overrides are applied to `params.env`, and the RHOAI kustomize overlay is rendered. Resources are deployed using Server-Side Apply with the field owner `trainer-module-controller`. The operator also manages ClusterTrainingRuntime definitions (torch-distributed, training-hub, openmpi, speculator, vllm-extract variants) and OpenShift ImageStream definitions for CUDA, ROCm, and CPU training images.

The operator builds on the `odh-platform-utilities` framework, which provides the reconciler lifecycle (action-based pipeline), condition management, garbage collection with label-based discovery, and kustomize rendering. A dependency check system validates that the JobSet Operator is installed and healthy on OpenShift before proceeding with reconciliation.

## Architectural Analysis

The trainer-operator follows the ODH modular operator pattern: a thin controller that renders upstream manifests through a kustomize overlay pipeline rather than imperatively constructing Kubernetes resources. This design separates concerns — upstream Kubeflow Trainer evolves independently, and the operator's role is confined to lifecycle management (deploy, upgrade, GC, finalize) and platform integration (RHOAI image overrides, TLS profile adherence, namespace scoping).

The reconciler uses the `odh-platform-utilities/framework` action pipeline, chaining `checkDependencies → ensureNamespace → updateReleases → renderManifests → deploy (SSA) → statusCheck → stripRuntimeFinalizers → GC` in sequence. The `withImmutableFieldRecovery` wrapper around the deploy action handles Deployment selector changes by deleting the offending Deployment and requeueing, which is a pragmatic workaround for the upstream trainer controller's occasional selector changes between versions.

Cache hardening is deliberately applied: the controller-runtime cache is scoped by `platform.opendatahub.io/part-of=trainer` label selectors for Deployments, Services, and ValidatingWebhookConfigurations, while ConfigMaps are excluded from this label filter because the platform config ConfigMap (`odh-trainer-config`) is created by the platform operator without the trainer label. Namespace scoping (`APPLICATIONS_NAMESPACE` env var) further bounds the cached set. The Namespace type is excluded from the cache entirely to prevent an implicit cluster-wide informer.

TLS profile integration is sophisticated: at startup, the operator resolves the OpenShift cluster TLS profile via `config.openshift.io/APIServer`, respects the TLS adherence policy, and configures controller-runtime's metrics server with the resulting cipher suites and protocol versions. A watcher triggers a graceful shutdown and restart when the cluster TLS profile or adherence policy changes, ensuring the operator always runs with the correct cryptographic configuration. On non-OpenShift clusters, the operator falls back to the Intermediate TLS profile.

The platform version tracking mechanism reads from an `odh-trainer-config` ConfigMap (set by the platform operator), stores the version in the Trainer CR status as component releases, and plumbs it into the framework's release tracking for deploy/GC annotation versioning. This enables version-aware upgrades and stale resource cleanup across platform version boundaries.

A notable design detail is the explicit handling of upstream Kubeflow Trainer's legacy `trainer.kubeflow.org/resource-in-use` finalizer on ClusterTrainingRuntimes and TrainingRuntimes. The `stripRuntimeFinalizers` action and the finalizer cleanup path both remove these finalizers, which were dropped in Trainer 2.3 but may persist on resources created by earlier versions. This prevents orphaned resources from blocking deletion during upgrades.
