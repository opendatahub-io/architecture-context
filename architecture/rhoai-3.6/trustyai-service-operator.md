## Purpose

**Short**: Multi-service Kubernetes operator managing TrustyAI model explainability, language model evaluation (LMEval/EvalHub), and NVIDIA NeMo Guardrails deployments for AI model trustworthiness and safety.

**Detailed**: The trustyai-service-operator is a controller-runtime-based Kubernetes operator that manages multiple AI trustworthiness and evaluation services within the RHOAI platform. It uses a dynamic service registration pattern where controllers register via `init()` functions and are selectively enabled at startup through the `--enable-services` flag, allowing a single operator binary to manage TrustyAIService (model bias and explainability monitoring), EvalHub (centralized LLM evaluation orchestration with multi-tenancy support), LMEvalJob (language model evaluation job lifecycle), and NemoGuardrails (NVIDIA NeMo safety guardrails).

The operator creates and manages secondary resources -- Deployments, Services, Routes, VirtualServices, NetworkPolicies, RBAC resources, and ServiceMonitors -- on behalf of each CR instance. It integrates with the OpenShift TLS security profile API to dynamically resolve TLS configuration for both the operator itself and the kube-rbac-proxy sidecars it deploys, and watches KServe InferenceServices to correlate model serving state with trustworthiness monitoring. The EvalHub controller implements a multi-tenant model where a single control-plane instance serves labeled tenant namespaces, provisioning per-tenant ServiceAccounts, RBAC bindings, and ConfigMap propagation.

## Architectural Analysis

The operator consolidates what were historically separate concerns -- model explainability (TrustyAIService), evaluation orchestration (EvalHub/LMEvalJob), and safety guardrails (NemoGuardrails) -- into a single operator binary. This design reduces operational overhead but creates a broad RBAC footprint, with the manager ClusterRole requiring 39 rules spanning 20+ API groups including Istio networking, Kueue workload management, MLflow experiments, and Gateway API.

A notable architectural pattern is the operator's TLS profile watcher: on startup, it reads the OpenShift `apiservers.config.openshift.io/cluster` resource to resolve the cluster TLS security profile, then configures both the operator's own metrics server and generates kube-rbac-proxy arguments for all managed workloads. Changes to the cluster TLS profile trigger a manager restart to propagate the updated configuration, making the restart boundary the refresh mechanism rather than in-place reconciliation.

The EvalHub controller's multi-tenancy implementation is substantive: it discovers tenant namespaces via label selectors, provisions job ServiceAccounts and ClusterRoleBindings per tenant, propagates system-level provider and collection ConfigMaps, and enforces placement guards that prevent a multi-tenant instance from being deployed in a tenant namespace. The operator also manages NetworkPolicy identity labels on Deployments it creates, enabling platform-level network isolation without requiring per-component NetworkPolicy resources.

Cache is deliberately disabled for high-volume core resources (ConfigMap, Secret, Pod, Service) to prevent OOM from cluster-wide informer flooding, accepting the latency trade-off of direct API server reads for these types.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant ServiceAccounts and ClusterRoleBindings; kube-rbac-proxy SAR per request for TrustyAIService | Kubernetes RBAC + kube-rbac-proxy | EvalHub tenant roles are namespace-scoped but bind to all service accounts in namespace via `system:serviceaccounts:{namespace}` |
| Data storage | Per-namespace PVCs for TrustyAIService; per-namespace evaluation jobs for EvalHub | Kubernetes namespace isolation | No cross-tenant data isolation within shared EvalHub control-plane namespace |
| Network traffic | NetworkPolicy identity labels on managed Deployments; relies on platform-level NetworkPolicies in redhat-ods-applications namespace | Kubernetes NetworkPolicy (platform-managed) | Operator does not create per-tenant NetworkPolicies; relies on platform allowlisting port 8081 |
| Compute & resources | No per-tenant ResourceQuotas or LimitRanges | N/A | Tenant workloads (evaluation jobs) compete for cluster resources; Kueue integration provides queue-level fairness |
| Configuration & secrets | System ConfigMaps copied to instance namespace; tenant ConfigMaps discovered in-place via labels | Kubernetes namespace isolation | Tenant-labeled ConfigMaps in instance namespace are accessible to all tenants of that instance |
| API scoping | Namespace-scoped CRDs; EvalHub watches labeled tenant namespaces only | Kubernetes + Application | Multi-tenant EvalHub has cluster-wide namespace list/watch to discover tenant namespaces |
