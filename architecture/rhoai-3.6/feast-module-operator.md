## Purpose

**Short**: Module operator that deploys and manages the upstream Feast feature store operator on the OpenDataHub / RHOAI platform via the ODH modular handler framework.

**Detailed**: The feast-module-operator is a Kubernetes operator that watches `FeastOperator` Custom Resources (API group `components.platform.opendatahub.io/v1alpha1`) and deploys the upstream [feast-operator](https://github.com/opendatahub-io/feast) using bundled kustomize manifests. It acts as a bridge between the ODH platform operator and the Feast ecosystem: the ODH Operator deploys this module operator via a Helm chart and creates a `FeastOperator` CR with platform configuration (e.g., OIDC settings), which this operator then reconciles to deploy the feast-operator workload into the applications namespace.

The operator implements the ODH module pattern — a single-purpose controller that manages one platform component's lifecycle. It uses `odh-platform-utilities` for platform detection and cache optimization, and embeds the `opendatahub-operator/v2` reconciler framework for action-based reconciliation. The reconciliation pipeline includes initialization, OIDC parameter injection, kustomize rendering, deployment selector migration, and garbage collection of cluster-scoped resources. Platform-aware overlays (ODH vs RHOAI) control namespace targeting and image parameterization. Related images for the feast-operator and feature-server are injected via `params.env` replacements at reconcile time.

## Architectural Analysis

The feast-module-operator follows the ODH modular operator pattern, where each platform component is managed by a dedicated module operator rather than being embedded in the monolithic ODH operator. This decomposition enables independent release cadences and isolated failure domains per component.

The reconciliation pipeline is built using the `opendatahub-operator/v2` action framework, which chains idempotent actions in sequence: `initialize → upgradeIfNeeded → setKustomizedParams → releases → reconcilePlatformVersion → kustomize.render → migrateDeploymentSelector → deploy → deployments.status → gc`. This design makes the reconciliation logic testable and extensible — new upgrade migrations or parameter injections can be added as new actions without modifying existing ones.

A notable architectural choice is the platform version handshake protocol. The operator reads a platform version from the `odh-feastoperator-config` ConfigMap (created by the ODH platform operator) and records it in the CR status. When the platform version advances, the operator runs version-gated migrations before updating the record. This enables coordinated upgrades across the platform without tight coupling between operators.

The operator manages cluster-scoped resources (ClusterRoles, ClusterRoleBindings) that cannot use standard Kubernetes ownerReferences for garbage collection. A dedicated finalizer (`cleanupClusterResources`) handles cleanup by listing and deleting these resources by label, which is important for clean component removal.

The RBAC footprint is broad — the operator needs permissions for `feast.dev/featurestores`, `kubeflow.org/notebooks`, `mlflow.opendatahub.io/mlflows`, `sparkoperator.k8s.io/sparkapplications`, and `route.openshift.io/routes`. These permissions are delegated to the feast-operator it deploys rather than exercised directly. The module operator also has `pods/exec` create permission, which warrants attention in security reviews.

The chartgen subcommand generates Helm charts from the kustomize manifests by transforming namespace references, image fields, and service account names into Helm template directives. This supports an alternative deployment path where the module can be installed via Helm without the ODH operator.
