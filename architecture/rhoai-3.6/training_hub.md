## Purpose

**Short**: Algorithm-focused Python library and CLI providing a unified interface for LLM training, continual learning, reinforcement learning, prompt optimization, and embedding fine-tuning.

**Detailed**: Training Hub is a Python package (`training-hub` on PyPI) developed by the Red Hat AI Innovation Team that abstracts multiple training backends behind a consistent Strategy + Registry pattern. It supports seven training algorithms: Supervised Fine-Tuning (SFT) via InstructLab Training, Orthogonal Subspace Fine-Tuning (OSFT) via RHAI Innovation Mini-Trainer, LoRA + SFT via Unsloth, LoRA + GRPO and full-parameter GRPO via OpenPipe ART and verl backends, GEPA gradient-free prompt optimization via the gepa library and MLflow, and contrastive embedding fine-tuning via sentence-transformers. Each algorithm may have multiple backend implementations.

The library exposes both a Python API (`from training_hub import sft, osft, lora_sft, lora_grpo, grpo, gepa, embedding_sft`) and a CLI (`thub`) that supports YAML config files and direct argument passing. It is designed for GPU-accelerated distributed training using torchrun for multi-GPU/multi-node setups, FSDP for distributed parameter sharding (verl backend), and co-located vLLM for inference during GRPO reinforcement learning. Training Hub is not a deployed service — it is a library consumed by other RHOAI components (e.g., Kubeflow training pipelines) and by end users directly. It also ships as a Claude Code and Codex CLI plugin for AI-assisted training workflows.

## Architectural Analysis

Training Hub follows a **Strategy + Registry** design pattern that cleanly separates algorithm definitions from backend implementations. The `Algorithm` abstract base class defines the `train()` interface, while `Backend` defines `execute_training()`. The `AlgorithmRegistry` maps algorithm names to classes and associates multiple backends per algorithm, enabling users to select a backend at runtime (e.g., `lora_grpo(..., backend="verl")` vs `backend="art"`).

The library manages two distinct execution models. Weight-training algorithms (SFT, OSFT, LoRA) launch torchrun subprocesses for distributed training, with callbacks serialized across the process boundary using source-code extraction and base64 encoding. The GRPO algorithms have two execution paths: the ART backend runs in a spawned subprocess with co-located vLLM inference and Unsloth LoRA training on a single GPU via time-sharing, while the verl backend launches full multi-GPU FSDP training via torchrun with a separate vLLM rollout engine. GEPA runs entirely CPU-side, calling remote LLM endpoints through litellm without any local GPU requirement.

A unified callback system (`TrainingHubCallback`, `TrainingHubContext`, `TrainingHubControl`) provides lifecycle hooks that work across all backends. Backend-specific adapters (`adapters/unsloth.py`, `adapters/instructlab.py`, `adapters/mini_trainer.py`) translate these into each trainer's native callback interface. The recently added JIT preemption checkpointing (`JITCheckpointCallback`) handles SIGTERM-based graceful shutdown with checkpoint saving, and the checkpoint manager supports remote mirroring to S3/GCS/Azure via fsspec.

Notable supply-chain consideration: the `litellm` dependency explicitly excludes versions 1.82.7 and 1.82.8 due to the TeamPCP supply chain compromise (March 2026) that harvested credentials at import time.
