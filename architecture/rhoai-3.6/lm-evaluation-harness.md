## Purpose

**Short**: A framework for evaluating language models against standardized benchmarks, packaged as a batch job container for the RHOAI platform's EvalHub service.

**Detailed**: lm-evaluation-harness is a fork of EleutherAI's open-source Language Model Evaluation Harness, adapted for Red Hat OpenShift AI. The upstream project provides a unified framework to test generative language models on over 60 standard academic benchmarks (HellaSwag, MMLU, GSM8K, HumanEval, etc.) with hundreds of subtasks, supporting models loaded via HuggingFace Transformers, vLLM, OpenAI-compatible APIs, and other backends.

The RHOAI downstream adds an EvalHub adapter (`main.py`) that integrates the harness into the EvalHub evaluation platform. This adapter receives job specifications as JSON files (mounted at `/meta/job.json`), drives evaluations against model inference endpoints using the `local-completions` backend (OpenAI-compatible API), reports status updates and results via callbacks, and optionally persists evaluation artifacts to OCI registries. The adapter includes security hardening such as path traversal protection (CWE-22 mitigation), error message sanitization to prevent secret leakage, controlled code execution gating for specific benchmarks, and automatic air-gapped/disconnected cluster support via HuggingFace offline mode detection.

The component is deployed as a Kubernetes batch Job container image (`odh-ta-lmes-job-rhel9`) that runs a single evaluation workload and exits. It does not expose any network services; instead, it acts as a client to model inference endpoints and reports results back to the EvalHub control plane.

## Architectural Analysis

The lm-evaluation-harness follows a batch-execution architecture where each evaluation is a one-shot process: the container starts, reads its job specification, runs the evaluation, reports results, and terminates. This pattern aligns with Kubernetes Job semantics and avoids the complexity of long-running service management.

The downstream adapter (`main.py`, ~1100 lines) is the key architectural addition over upstream. It wraps the upstream `simple_evaluate()` API with an `evalhub.adapter.FrameworkAdapter` integration layer. The adapter's design reflects several important architectural decisions:

1. **Disconnected cluster support**: The adapter probes the `/test_data` mount at startup to detect pre-staged tokenizers and datasets, automatically configuring HuggingFace offline mode. This avoids network calls to huggingface.co when running in air-gapped environments — a critical requirement for government and regulated deployments.

2. **Security-conscious error handling**: All error messages pass through `_sanitize_error_message()` before being sent to external callbacks, redacting Bearer tokens, API keys, OAuth secrets, URL credentials, and query parameters. This prevents credential leakage through error reporting channels.

3. **Controlled code execution**: Benchmarks like HumanEval that require executing model-generated Python code are gated by an explicit allowlist (`_BENCHMARKS_REQUIRING_CODE_EXECUTION`). The `HF_ALLOW_CODE_EVAL` environment variable is scoped per-benchmark execution and restored afterward.

4. **Multi-architecture build support**: The non-Konflux Dockerfile (`Dockerfile.lmes-job`) contains a complex multi-stage build that compiles PyTorch, Apache Arrow, and OpenBLAS from source for s390x and ppc64le architectures, reflecting RHOAI's commitment to IBM hardware platforms. The Konflux Dockerfile is simpler, relying on external base images (`CUDA_BASE_IMAGE`, `CPU_BASE_IMAGE`) that provide pre-built accelerator dependencies.

The model integration layer supports numerous LLM backends (HuggingFace, vLLM, OpenAI, Anthropic, WatsonX, TextSynth, SGLang) but the EvalHub adapter exclusively uses the `local-completions` backend, communicating with model endpoints via OpenAI-compatible HTTP APIs.
