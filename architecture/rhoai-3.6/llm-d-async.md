## Purpose

**Short**: Asynchronous queue-based dispatch processor that pulls batch inference requests from a message broker, gates dispatch based on system capacity metrics, and forwards them to llm-d-router or another inference gateway.

**Detailed**: The Async Processor (AP) addresses the problem of low GPU utilization in online-only LLM serving scenarios. It enables efficient processing of latency-insensitive workloads — product classification, bulk summarization, sentiment analysis — by decoupling request submission from execution through a message queue. Workers pull jobs from Redis or GCP Pub/Sub, evaluate dispatch gates that monitor inference pool saturation via Prometheus metrics, and forward eligible requests to the downstream inference gateway over HTTP.

The component is organized as a Go multi-module repository (root, `api/`, `pipeline/`, `producer/`) built on controller-runtime for logging and signal handling. The root module contains the processor binary; `api/` defines the public request/result wire format; `pipeline/` provides the flow, gate, and worker pool abstractions; and `producer/` implements the client-side SDK for enqueueing requests and receiving results. A composable dispatch gate system supports budget-based gates (Prometheus saturation/budget metrics, endpoint scraping, Redis-stored budgets), admission gates (concurrency limits, per-attribute quotas, tier-priority admission), and combinator gates. A configurable merge policy (random-robin or tier-priority with six strict lanes) controls how multiple queue sources are multiplexed into worker pools. The processor exposes comprehensive Prometheus metrics under the `llm_d_async` subsystem and supports OpenTelemetry distributed tracing with W3C trace context propagation across the queue boundary.

## Architectural Analysis

The Async Processor follows a pipeline architecture centered on the concept of a `Flow` — an abstraction over the message broker that encapsulates request ingestion, retry scheduling, and result publication. Three flow implementations exist: Redis Pub/Sub (deprecated), Redis Sorted Set (recommended for production, supporting persistence, priority sorting, and per-queue gating), and GCP Pub/Sub. The flow produces per-queue request channels that a `RequestMergePolicy` groups by worker pool, producing one merged channel per pool.

Each worker pool runs a fixed number of goroutine workers. A worker pulls a request from the merged channel, evaluates the pool-level dispatch gate (if configured), then dispatches to the inference gateway over HTTP. Gate evaluation follows a two-level model: queue-level gates run at admission (refuse returns the message to the broker immediately), while pool-level gates can park workers in-memory (`ActionWait`) to avoid redelivery overhead. The `wait-on-refuse` combinator converts refuse verdicts into waits for gates where in-memory parking is preferable.

The tier-priority system provides six strict priority lanes derived from `(classification × tier)`. A `redis-quota` gate in classifying mode tags messages as `reserved` or `overflow`, and the `tier-priority` merge policy dispatches reserved-interactive first through overflow-batch last. This enables mixing interactive and batch traffic on a shared inference pool with deterministic preemption semantics.

TLS is configured for outbound connections to the inference gateway with support for custom CA certificates and mutual TLS. The `buildTLSConfig` function enforces a minimum of TLS 1.2. The metrics endpoint supports optional authentication and authorization via controller-runtime's RBAC filter. Health probes (`/healthz` and `/readyz`) are unauthenticated by design, running on a separate port from metrics.

Graceful shutdown is carefully orchestrated: on SIGTERM the health server marks itself not-ready, message consumption stops, queue configuration watchers complete, and in-flight requests drain within a configurable timeout. Requests that cannot complete within the drain window are re-enqueued with a linked `re-enqueue` trace span.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-tenant authentication at the message queue level; relies on broker-level access control | Message broker (Redis ACLs / GCP IAM) | Tenants sharing a queue trust the broker for access control |
| Data storage | Per-queue result routing; per-request result keys with configurable TTL | Application (result routing in transport config) | Shared Redis/Valkey instance; no encryption-at-rest by default |
| Network traffic | No per-tenant network policies | N/A | All tenants share the processor's network context |
| Compute & resources | Per-attribute quota via `redis-quota` gate (rate-limit or concurrency); per-pool worker limits | Application (dispatch gates) | Quotas are best-effort; a single slow request occupies a worker for its full duration |
| Configuration & secrets | Per-queue transport configuration with separate gate params | Application (transport config) | Shared Prometheus/Redis connections across queues |
| API scoping | Per-queue/topic dispatching with separate `igw_base_url` and `inference_objective` | Application (merge policy) | All queues in a pool share workers |
