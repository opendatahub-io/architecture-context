## Purpose

**Short**: KServe serving runtime that serves AutoGluon TabularPredictor and TimeSeriesPredictor models via the KServe v1/v2 inference protocol.

**Detailed**: The kserve-autogluon-server is a Python model server built on the KServe SDK that serves AutoGluon machine learning models. It supports two predictor types from a single container image: TabularPredictor (for classification, regression, and quantile prediction on tabular data) and TimeSeriesPredictor (for time series forecasting). At startup, the server auto-detects whether the provided model artifact is tabular or time series by attempting to load each type in sequence.

The component registers as a `ClusterServingRuntime` with KServe under the `autogluon` model format, enabling users to deploy AutoGluon models via standard `InferenceService` custom resources. Tabular models support both KServe v1 (JSON) and v2 (tensor) inference protocols, including optional `predict_proba` output for classification models. Time series models support REST v1 JSON only. The server downloads models from cloud storage (S3, GCS, Azure Blob) via the KServe storage layer.

This component exists within the broader KServe mono-repository (which includes the KServe operator, Python SDK, and multiple serving runtimes), but the Konflux build pipeline produces only the autogluon server container image. The image ships a fixed Python ML stack including AutoGluon 1.5.0, LightGBM, XGBoost, PyTorch, and fastai, all pinned to specific versions to ensure model compatibility.

## Architectural Analysis

The autogluon server follows the standard KServe serving runtime pattern: a Python process that implements the `kserve.Model` interface and is launched by `kserve.ModelServer`. The entrypoint (`python -m autogluonserver`) parses CLI arguments for model name, model directory, and HTTP/gRPC ports, then delegates to the KServe SDK's FastAPI-based web server.

A notable design choice is the auto-detection mechanism in `predictor_detect.py`: the server first attempts to load the model directory as a `TimeSeriesPredictor`, and falls back to `TabularPredictor` if that fails. This means users do not need to specify the predictor type in their InferenceService YAML — the runtime determines it from the saved model artifact. The `version_compat.py` module adds a patch-level tolerance layer that allows loading models saved with a different AutoGluon patch version (e.g., 1.5.0 vs 1.5.0+rhaiv.3) while still rejecting major/minor mismatches.

The container image uses an AIPCC CPU base image from `registry.redhat.io/rhai/base-image-cpu-rhel9`, inheriting pre-configured pip/uv settings pointing at the RHEL AI Python Package Index. The build installs packages from a hermetic-style requirements file (`autogluon-all-requirements.txt`) with hash pinning, sourced from the Red Hat internal PyPI index. The result is a CPU-only image; there is no GPU variant for the autogluon server in this repository.

The runtime paths module (`runtime_paths.py`) handles a container-specific concern: AutoGluon's SeasonalNaive fallback writes to the current working directory, which in OpenShift containers may be the read-only `/`. The module changes cwd to a writable directory at startup and configures matplotlib's cache path to avoid permission errors under non-root UIDs.
