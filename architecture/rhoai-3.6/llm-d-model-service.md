## Purpose

**Short**: Kubernetes operator that declaratively provisions and manages the full inference-serving stack for LLM base models, including disaggregated prefill/decode workloads, Gateway API routing, and endpoint selection.

**Detailed**: llm-d-model-service is a Kubebuilder-scaffolded Kubernetes operator that reconciles `ModelService` custom resources (CRD group `llm-d.ai`, version `v1alpha1`). When a user creates a `ModelService` CR, the controller provisions and maintains the complete set of Kubernetes resources required to serve a base model for inference: separate prefill and decode Deployments, an Endpoint Picker (EPP) Deployment and Service, an InferencePool and InferenceModel from the Gateway API Inference Extension, an HTTPRoute for traffic routing, ConfigMaps for configuration, ServiceAccounts, and RoleBindings for RBAC.

The controller supports a composable configuration model via `BaseConfig` — a ConfigMap containing platform-managed presets that can be overlaid by per-model `ModelService` specs. Template variables in both BaseConfig and ModelService are interpolated at reconcile time, enabling dynamic name generation for child resources. Model artifacts can be sourced from HuggingFace (`hf://`), Kubernetes PVCs (`pvc://`), or OCI images (`oci://`). The operator also supports decoupled scaling, allowing external autoscalers (HPA or custom) to manage replica counts independently.

**Note**: This project is **deprecated** as of July 2025. The core functionality has been superseded by a Helm chart at [llm-d-incubation/llm-d-modelservice](https://github.com/llm-d-incubation/llm-d-modelservice). The repository carries a deprecation notice in its README.

## Architectural Analysis

The llm-d-model-service operator follows a single-controller architecture built on controller-runtime v0.20.4. A single `ModelServiceReconciler` watches the `ModelService` CRD as its primary resource and maintains ownership watches on ten resource types: Deployments, Services, ServiceAccounts, ConfigMaps, RoleBindings, HTTPRoutes, InferencePools, InferenceModels, and the ModelService itself (both `For` and `Owns`). All watched resources trigger reconciliation via owner-reference map functions, ensuring the controller re-converges when any child resource is externally modified or deleted.

The reconciliation flow is structured as a pipeline: (1) fetch and validate the ModelService CR, (2) interpolate template variables in both the ModelService and its referenced BaseConfig ConfigMap using Go `text/template`, (3) merge the ModelService spec onto the BaseConfig defaults using the `mergo` library, (4) create-or-update all child resources with controller-runtime's `controllerutil.CreateOrUpdate`, and (5) update the ModelService status with deployment readiness information from prefill, decode, and EPP workloads.

A notable architectural decision is the support for disaggregated prefill and decode deployments as separate Kubernetes Deployments, reflecting the KV-cache disaggregation pattern for LLM inference. The controller creates independent prefill and decode Deployments with separate scaling, node affinity, and accelerator type configurations. The `DecoupleScaling` flag allows operators to hand off replica management to external autoscalers — when set, the controller does not reconcile replica counts.

The CLI is Cobra-based with two subcommands: `run` (starts the controller manager) and `generate` (renders manifests to stdout without applying them, useful for dry-run validation). The `generate` command imports the same BaseConfig merging logic as the controller, ensuring manifest generation is consistent with runtime behavior.

The Gateway API integration is central: the controller creates HTTPRoute resources referencing a platform Gateway, and provisions InferencePool and InferenceModel resources from the `sigs.k8s.io/gateway-api-inference-extension` (v0.3.0, v1alpha2 API). The EPP (Endpoint Picker) deployment is a per-model instance that handles intelligent request routing within the inference pool; the controller creates a dedicated ServiceAccount and RoleBinding for the EPP, binding it to a configurable ClusterRole (`--epp-cluster-role` flag).

The operator's security posture is standard Kubebuilder: metrics are served over HTTPS on port 8443 with authentication and authorization filters (via `filters.WithAuthenticationAndAuthorization`) enabled by default. HTTP/2 is disabled by default to mitigate the Rapid Reset CVE. Health and readiness probes are unauthenticated on port 8081.

As a deprecated project, the primary architectural risk is that the operator will receive no further security patches or feature updates. Organizations still running this operator should plan migration to the Helm chart replacement.
