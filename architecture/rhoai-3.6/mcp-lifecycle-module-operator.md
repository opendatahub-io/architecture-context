## Purpose

**Short**: A module operator that manages the lifecycle of the MCP Lifecycle Operator as an operand within the OpenDataHub/RHOAI modular platform architecture.

**Detailed**: The MCP Lifecycle Module Operator follows the ODH modular architecture pattern where the platform operator creates a cluster-scoped `MCPLifecycleOperator` custom resource, and this module operator reconciles it by deploying the MCP Lifecycle Operator as its operand via server-side apply (SSA). The operand itself manages `MCPServer` and `MCPGatewayBinding` resources that enable Model Context Protocol (MCP) server lifecycle management on OpenShift AI clusters.

The module operator embeds the operand's full manifest set (CRDs, RBAC, Deployment, webhooks, network policies, cert-manager resources) as a Go `embed.FS` and renders them through a kustomize-based provider, injecting namespace, operand image, and TLS configuration at reconcile time. It implements garbage collection of stale resources, deployment readiness gating, a conversion-health handshake that validates stored MCPServer objects are convertible to v1beta1 before advancing the platform version, and a StorageVersionMigration to re-encode stored objects at the promoted API version. Gateway discovery detects `MCPGatewayExtension` and `Gateway` resources dynamically, registering watches at runtime when those CRDs become available.

## Architectural Analysis

This operator sits at a middle tier in the RHOAI platform's three-level operator hierarchy: the ODH platform operator creates the `MCPLifecycleOperator` CR, this module operator reconciles it, and the deployed operand (mcp-lifecycle-operator) manages the end-user-facing `MCPServer` resources. The module operator pattern — standardized through `odh-platform-utilities` — cleanly separates platform lifecycle concerns from component-specific logic.

The reconciliation flow is carefully staged: manifest rendering → SSA apply → garbage collection → deployment readiness check → conversion webhook health check → platform version handshake → storage version migration. The conversion-health gate is architecturally notable: it lists all stored `MCPServer` objects at v1beta1 to force the API server's conversion webhook, ensuring that no stored objects will fail conversion before reporting the operand as available. This prevents the platform operator from marking an upgrade complete when stored CRDs are in an unconvertible state.

TLS configuration is derived from the OpenShift `APIServer` resource's TLS profile on OpenShift clusters, with hardened Intermediate defaults on non-OpenShift clusters. The resolved min version, cipher suites, and key exchange groups are injected into the operand deployment as environment variables, ensuring the operand's webhook and metrics servers inherit the cluster's crypto policy.

The RBAC surface is broad because the module operator must hold a superset of the operand's permissions (Kubernetes RBAC escalation prevention): it applies the operand's ClusterRole, so its own service account must be authorized for every verb the operand needs. The operator's cache is carefully tuned — namespace-scoped for most resources, label-filtered for ClusterRoles/ClusterRoleBindings, and schema-stripped for CRDs to avoid holding every cluster CRD's OpenAPI schema in memory.

Metrics are disabled (bind address `"0"`) on the module operator itself; the operand exposes its own metrics endpoint on port 8443 with `kube-rbac-proxy`-style token/SAR authentication. The module operator's NetworkPolicy admits only health-probe traffic (port 8081) and allows all egress, conforming to the ODH-ADR-Operator-0016 contract.
