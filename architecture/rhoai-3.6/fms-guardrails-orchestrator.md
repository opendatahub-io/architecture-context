## Purpose

**Short**: A REST API orchestrator that coordinates AI text generation with content safety guardrails by routing requests through configurable detector, chunker, and LLM backend services.

**Detailed**: The FMS Guardrails Orchestrator is a Rust-based middleware service that sits between API clients and foundation model infrastructure to enforce content safety. When a client submits a text generation or detection request, the orchestrator fans out calls to one or more downstream services — text generation backends (TGIS via gRPC or caikit-nlp), content safety detectors (via HTTP REST), and text chunker services (via gRPC) — then aggregates and filters the results before returning them to the caller. This design keeps guardrail logic out of the model serving layer and allows detectors to be composed declaratively through a YAML configuration file.

The orchestrator exposes two HTTP servers: a primary guardrails API on port 8033 serving v1 and v2 detection and generation-with-detection endpoints, and a lightweight health/info server on port 8034. The guardrails server supports optional TLS and mutual TLS. It supports both unary and server-sent-event (SSE) streaming response patterns, and can optionally expose OpenAI-compatible chat completions and text completions endpoints when an OpenAI backend is configured. The service is built on the Tokio async runtime with Axum for HTTP routing and Tonic for gRPC client communication.

## Architectural Analysis

The orchestrator follows a task-handler pattern: each API endpoint creates a typed task struct (e.g., `ChatCompletionsDetectionTask`, `TextContentDetectionTask`) and submits it to the `Orchestrator` which dispatches to the appropriate handler. Handlers coordinate concurrent fan-out to detector and chunker services, with configurable concurrency limits (`detector_concurrent_requests`, `chunker_concurrent_requests` both default to 5). Generation client calls include exponential-backoff retry logic for transient failures (502, 503, 504).

A notable design decision is the use of a dynamic `ClientMap` with trait-object downcasting rather than static dispatch for client types. This allows the orchestrator to hold heterogeneous client types (generation, detector, chunker, OpenAI) in a single map while preserving type-safe access via `downcast_ref`. Client creation is driven entirely by the YAML configuration — unused service types are simply not instantiated.

The cryptographic posture deserves attention: the application explicitly installs `ring` as the rustls crypto provider at startup (`rustls::crypto::ring::default_provider().install_default()`). Ring is not a FIPS-validated cryptographic module. While OpenSSL development libraries are installed during the build (required for protobuf-src compilation and linkage), the application's TLS stack at runtime uses ring via rustls rather than OpenSSL. This means the service will not pass FIPS cryptographic validation at the application level, even though the UBI 9 base image provides a FIPS-capable OpenSSL. The outbound client TLS implementation includes a `NoVerifier` struct that disables all certificate verification when `insecure: true` is set in the per-service TLS configuration — architecturally appropriate for development but a potential risk if enabled in production.

Header passthrough is a first-class concern: the orchestrator accepts a configurable set of header keys and forwards them to all downstream service calls. It also supports rewriting `X-Forwarded-Access-Token` headers into `Authorization: Bearer` headers, enabling integration with platform authentication proxies. However, the orchestrator itself performs no authentication or authorization — it is a transparent proxy for credentials.
