## Purpose

**Short**: Kubeflow Notebooks v2 workspaces platform that manages interactive development environments (JupyterLab, RStudio, VS Code) on Kubernetes via CRDs, a REST API, and a web frontend.

**Detailed**: The workbenches component implements Kubeflow Notebooks v2 — a three-tier system for managing interactive development workspaces on Kubernetes. It defines two custom resources: `Workspace` (namespaced) represents a single interactive session, and `WorkspaceKind` (cluster-scoped) is a template that defines available IDE images, resource profiles, and activity rules. The controller reconciles these CRDs into StatefulSets, Services, ServiceAccounts, RoleBindings, and network routing resources (Istio VirtualServices or Kubernetes Gateway API HTTPRoutes).

A Go backend API server provides a RESTful interface (`/api/v1/*`) that proxies Kubernetes operations with per-request authentication (either Kubeflow request headers or Bearer token via TokenReview) and per-resource RBAC authorization (SubjectAccessReview). The TypeScript/React frontend (PatternFly 6) serves as the user interface, communicating exclusively through the backend API. In production, the backend can serve the frontend's static assets and TLS-terminate with configurable certificates.

## Architectural Analysis

The workbenches architecture follows a clear separation of concerns across three deployable components that share a single repository. The controller operates as a standard controller-runtime operator with leader election, managing the lifecycle of workspace pods through StatefulSets rather than Deployments — a deliberate choice that provides stable network identities and persistent storage semantics needed by interactive development environments.

A notable design decision is the dual networking support: the controller can provision either Istio VirtualServices or Kubernetes Gateway API HTTPRoutes for workspace access, controlled by mutually exclusive flags (`--use-istio` / `--use-kube-gateway`). When Gateway API mode is enabled, the controller also deploys kube-rbac-proxy sidecars for authentication, creates ReferenceGrants for cross-namespace HTTPRoute references, and manages ClusterRoleBindings for the auth-delegator pattern.

The backend API implements a resource-policy authorization model where every API endpoint maps to a specific Kubernetes resource verb (get/list/create/update/delete) and the backend performs SubjectAccessReviews against the user's identity before executing operations. This means the backend never bypasses Kubernetes RBAC — it impersonates authorization checks rather than operating under its own service account permissions. The backend supports two authentication modes: header-based identity injection from a trusted reverse proxy (the Kubeflow pattern), and direct Bearer token validation via TokenReview (the RHOAI/ODH pattern where the user's own token is forwarded).

The TLS configuration on both controller and backend is OpenShift-aware: the controller reads the cluster's `apiservers.config.openshift.io/cluster` TLS security profile at startup and watches for runtime changes, restarting when the profile is modified. The fallback for non-OpenShift clusters is a hardened Mozilla Intermediate profile (TLS 1.2+, ECDHE cipher suites). The backend supports optional TLS termination via `--cert-file` / `--key-file` flags with a minimum of TLS 1.3.

The WorkspaceKind webhook validation is particularly sophisticated: it prevents deletion or modification of image/pod configurations that are actively in use by existing Workspaces, implements redirect chain validation with cycle detection, and enforces activity probe configuration when pause rules are defined.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SubjectAccessReview against user identity for every backend API call; aggregated ClusterRoles (admin/edit/view) for namespace-scoped workspace access | Kubernetes RBAC via backend authorization middleware | Backend trusts the reverse proxy to inject validated identity headers; misconfigured proxy could allow header spoofing (mitigated by `user_token` mode) |
| Data storage | Per-namespace PVCs created alongside Workspaces; PVCs managed through backend API with per-resource authorization | Kubernetes (namespace isolation) | No cross-namespace PVC sharing enforced by the controller |
| Network traffic | Default-deny NetworkPolicy in controller namespace; optional Istio AuthorizationPolicy for backend | Kubernetes NetworkPolicy / Istio | Workspace pods in user namespaces do not have controller-managed NetworkPolicies |
| Compute & resources | Resource limits defined in WorkspaceKind pod configs; applied to StatefulSet pod specs | Kubernetes (LimitRange/ResourceQuota in namespace) | Resource enforcement depends on namespace-level quotas configured externally |
| Configuration & secrets | Per-namespace Secrets managed through backend API with per-resource RBAC authorization | Kubernetes RBAC | No encryption-at-rest enforcement by the component; relies on cluster etcd encryption |
| API scoping | Backend queries are namespace-scoped when namespace parameter is provided; cross-namespace listing authorized via SubjectAccessReview | Backend authorization + Kubernetes RBAC | Users with cluster-wide list permission can see workspaces across namespaces |
