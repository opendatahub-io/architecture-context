## Purpose

**Short**: Envoy ExtProc gRPC server that runs Praxis filter pipelines as an external processor for header and body inspection, mutation, and rejection.

**Detailed**: praxis-extproc is a standalone Rust gRPC server that implements Envoy's External Processing (ExtProc) protocol. It receives streaming ExtProc messages from Envoy, translates them into Praxis `FilterPipeline` invocations, and returns header/body mutations or immediate responses. This allows Praxis AI filters (model routing, request transformation, policy enforcement) to run alongside Envoy without replacing it.

In the RHOAI MaaS (Model as a Service) deployment, the component runs as two Deployment instances behind the Istio-managed gateway: a pre-auth `payload-pre-processing` stage that extracts the model name from request bodies and resolves model providers, and a post-auth `payload-processing` stage that runs the full processing pipeline. Both are wired into the gateway's HTTP filter chain via Istio EnvoyFilter resources that insert ExtProc filters before and after the Kuadrant auth layer.

The product image is the FIPS build: it links exclusively against system OpenSSL (never vendored), installs the OpenSSL-backed rustls crypto provider as the process-wide default, and deliberately excludes Cargo features (`policy-engine`, `responses-store`) that carry pure-Rust cryptography. The `PRAXIS_REQUIRE_FIPS` environment variable enforces fail-closed behavior when the host kernel's FIPS mode is not active.

## Architectural Analysis

praxis-extproc has a carefully layered internal architecture. The `server` module owns the gRPC `ExternalProcessor` service and the per-stream loop, dispatching each ExtProc phase (request headers, request body, response headers, response body, trailers) to dedicated `handlers`. The `pipeline` module executes the Praxis filter chain and assembles `ProcessingResponse` messages. The `protocol` module enforces ExtProc sequencing rules and parses Envoy's per-stream protocol configuration (body modes: None, Buffered, FullDuplexStreamed). Cross-phase filter state (branch iterations, executed filter indices, metadata) is parked in a `CarriedContext` and hydrated into each phase's `HttpFilterContext` through a compile-time-safe `HydratedContext` wrapper that prevents double-capture or forgotten restore.

The FIPS compliance story is the most architecturally significant design decision. Rather than a separate FIPS variant, the product Containerfile defaults to the FIPS feature set. The `fips` module installs `praxis-tls`'s OpenSSL-backed rustls `CryptoProvider` before any filter or TLS configuration is constructed, ensuring every cryptographic operation flows through the system OpenSSL (which is the FIPS-validated module on RHEL 9). The build embeds a crate manifest via `cargo-auditable` with `-Zsbom` so Red Hat's `check-payload` scanner can verify no pure-Rust crypto is present. Features carrying non-validated crypto (`policy-engine` with aws-lc-rs/sha2/hmac, `responses-store` with sqlx's sha2) are compiled out of the FIPS build but remain available for non-FIPS deployments.

The two-stage deployment pattern (pre-processing and post-processing) is notable: the pre-auth stage runs with `failure_mode_allow: true` (fail-open) and only inspects request headers/bodies to set routing headers, while the post-auth stage runs with `failure_mode_allow: false` (fail-closed) and processes both request and response headers/bodies. This separation keeps model-name extraction ahead of auth without exposing the full processing pipeline to unauthenticated traffic.

Graceful shutdown is bounded: a SIGTERM/SIGINT triggers a drain signal that flips health to `NotServing`, starts tonic's graceful drain, and arms a configurable deadline (default 20s) after which a force-close latch cancels any streams still running. A 5-second `preStop` sleep in the deployment gives Kubernetes time to stop routing before the drain begins.
