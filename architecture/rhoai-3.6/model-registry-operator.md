## Purpose

**Short**: Kubernetes operator that deploys and manages Model Registry instances, a shared Model Catalog, and the AI Hub module for the RHOAI platform.

**Detailed**: The model-registry-operator is a Kubebuilder-based operator that reconciles `ModelRegistry` custom resources into fully-configured Kubernetes deployments of the Model Registry server (a REST-based metadata service backed by PostgreSQL or MySQL). Each `ModelRegistry` CR produces a Deployment with the Model Registry server container and a kube-rbac-proxy sidecar for authentication, along with a Service, ServiceAccount, RBAC resources, NetworkPolicies, and optional OpenShift Routes or Gateway API HTTPRoutes for external access.

Beyond individual registries, the operator manages two additional domain controllers. The `CatalogReconciler` deploys a shared Model Catalog service that aggregates metadata across registries, backed by its own PostgreSQL instance and kube-rbac-proxy sidecar. The `AIHubReconciler` reconciles a cluster-scoped `AIHub` CR created by the platform operator (opendatahub-operator/rhods-operator), orchestrating the lifecycle of the Catalog CR and related webhook and RBAC infrastructure.

The operator integrates with OpenShift-specific APIs when available (Routes, user Groups, cluster TLS profiles, service-serving certificates) and falls back to vanilla Kubernetes primitives when running on non-OpenShift clusters. It supports CRD API version migration between v1alpha1 and v1beta1 via conversion webhooks and a storage version migration subsystem.

## Architectural Analysis

This operator exhibits a layered controller hierarchy: the platform operator (opendatahub-operator) deploys this operator via the `config/overlays/odh/` kustomize overlay, this operator's `AIHubReconciler` manages the catalog lifecycle, and the `ModelRegistryReconciler` and `CatalogReconciler` manage individual workloads. This design separates platform-level orchestration from component-level resource management.

A distinctive pattern is the template-based resource creation using Go's `text/template` with embedded YAML templates (`//go:embed`). Rather than constructing Kubernetes objects programmatically, the controllers render templates with `ModelRegistryParams` or `CatalogParams` structs, then apply the rendered resources via the `TemplateApplier`. This approach keeps resource definitions readable but introduces a gap between static analysis and runtime behavior — template branches for database type (PostgreSQL vs MySQL), auth mode (kube-rbac-proxy vs OAuth proxy vs none), and optional features (Routes, Gateway HTTPRoutes) produce different resource graphs depending on the CR spec.

The operator probes cluster capabilities at startup via the discovery API (`DetectClusterCapabilities`), adapting its behavior based on whether OpenShift Routes, User API, Config API, and Gateway API are available. This makes the same binary deployable across OpenShift and vanilla Kubernetes, but creates configuration branches that are not fully captured by static analysis.

The TLS configuration is notable: on OpenShift the operator reads the cluster-wide TLS security profile from the APIServer resource using `openshift/controller-runtime-common` helpers, and applies those cipher suites and protocol versions to the webhook and metrics servers. This ensures crypto configuration inherits from the platform rather than being hardcoded.

The OAuth proxy mode is legacy and auto-migrated to kube-rbac-proxy in the reconciler, indicating an ongoing transition in the authentication architecture. The operator manages per-registry RBAC dynamically — creating a `registry-user-{name}` Role and an OpenShift Group `{name}-users` for each registry instance, then cleaning them up on deletion.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-registry kube-rbac-proxy sidecar with TokenReview/SubjectAccessReview; per-registry Role (`registry-user-{name}`) and Group (`{name}-users`) | Kubernetes RBAC + kube-rbac-proxy | No fine-grained model-level access control within a registry |
| Data storage | Per-registry database (user-provided PostgreSQL/MySQL with separate credentials Secret per CR) | Application + Kubernetes Secrets | Operator-managed embedded PostgreSQL for catalog is shared; data isolation relies on database-level separation |
| Network traffic | Per-registry NetworkPolicy (`{name}-https-route`) restricting ingress; per-postgres NetworkPolicy (`{name}-postgres`) restricting database access | Kubernetes NetworkPolicy | NetworkPolicies are created per-CR; cross-namespace registry traffic is restricted |
| Compute & resources | Per-CR Deployment with configurable resource requests/limits (default 100m CPU, 256Mi memory) | Kubernetes resource management | No ResourceQuota or LimitRange created by operator; relies on namespace-level quotas |
| Configuration & secrets | Per-registry Secrets for database credentials and TLS; user-provided secrets referenced by name in CR spec | Kubernetes Secrets | Shared operator ServiceAccount has broad Secret access across registry namespace |
| API scoping | ModelRegistry CRs are namespace-scoped; operator watches with label filter (`app.kubernetes.io/created-by: model-registry-operator`) | Kubernetes namespace scoping + controller-runtime cache | Catalog is shared (single instance); all authenticated users get read access via `system:authenticated` group binding |
