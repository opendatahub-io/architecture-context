## Purpose

**Short**: Hardware plugin that enables vLLM large-language-model inference on Intel Gaudi (Habana) AI accelerators, exposing an OpenAI-compatible API server.

**Detailed**: vllm-gaudi is a Python hardware plugin for the vLLM inference engine that integrates Intel Gaudi accelerators (Gaudi 2 and Gaudi 3) into the vLLM serving stack. It follows vLLM's pluggable hardware architecture (RFC #11162 and RFC #19161), registering itself through setuptools entry points as both a platform plugin (`vllm.platform_plugins`) and a set of general plugins (`vllm.general_plugins`) that provide HPU-specific custom operations, attention backends, model implementations, and utility functions.

The component ships as a container image built on UBI 9 with the Habana SynapseAI stack (v1.23.0), PyTorch 2.9.0, and the vLLM core engine. At runtime, the container starts the vLLM OpenAI-compatible API server (`vllm.entrypoints.openai.api_server`), which accepts inference requests over HTTP. The plugin replaces GPU-targeted code paths with HPU-optimized implementations for attention computation, fused mixture-of-experts layers, rotary embeddings, quantization (FP8, INC, GPTQ, AWQ, ModelOpt, compressed-tensors), and distributed KV-cache transfer via NIXL. It also registers custom model implementations for architectures that require HPU-specific adaptations, including Gemma3, Qwen2.5-VL, Qwen3-VL-MoE, DeepSeek-V2, HunYuan, MiniMax-M2, Pixtral, and others.

## Architectural Analysis

vllm-gaudi's architecture centers on vLLM's plugin registration system. At Python import time, the `vllm_gaudi` package registers an `HpuPlatform` class that inherits from vLLM's `Platform` base, overriding device management, attention backend selection, compilation configuration, and worker class assignment. The platform steers the vLLM engine to use `HPUWorker` for model execution, which manages Habana-specific memory profiling, cache allocation, graph compilation, and online defragmentation of the KV cache.

The multi-stage Dockerfile builds a self-contained runtime environment: Stage 1 (gaudi-base) installs the Habana driver stack and system dependencies on UBI 9; Stage 2 (gaudi-pytorch) layers in Habana's PyTorch fork; Stage 3 (vllm-openai) clones and installs both upstream vLLM and the vllm-gaudi plugin, pinned to coordinated versions (v0.16.0). This build strategy creates tight coupling between the Habana SynapseAI runtime version, the PyTorch version, and the vLLM commit — all three must be mutually compatible.

A notable design decision is the explicit removal of the FIPS provider (`rpm -e --nodeps openssl-fips-provider-so`) early in the Dockerfile build. This is done because the Habana SynapseAI drivers are incompatible with the FIPS-mode OpenSSL provider on RHEL 9, and the component does not perform any application-level cryptographic operations itself — it delegates TLS termination and authentication to the surrounding platform infrastructure (KServe / Model Mesh ingress).

The Dockerfile performs network fetches at build time (git clone of upstream vllm and vllm-gaudi, pip install from PyPI, wget of Habana packages from vault.habana.ai), and there is no Hermeto/cachi2 prefetch or lock file hermeticity. This represents a supply-chain gap for reproducible builds in Konflux.
