## Purpose

**Short**: Standalone web admin UI and Go backend-for-frontend (BFF) for NVIDIA OpenShell, providing management of sandboxed AI agent runtimes, workspaces, providers, policies, and templates.

**Detailed**: openshell-dashboard is a two-tier web application that provides a management interface for the OpenShell sandboxing platform. The frontend is a React + PatternFly 6 single-page application, designed as a publishable npm package with exportable page components for downstream platform embedding (e.g., RHOAI). The Go BFF uses the `go-chi` HTTP router and acts as a relay between the frontend and the OpenShell gateway's gRPC API, using the official NVIDIA OpenShell Go SDK for most operations and three narrow direct gRPC clients for SDK gaps (binary file uploads, provider credential key reads, and provider profile endpoints).

The BFF follows a strict relay-only authentication model (ADR 0002): it never validates tokens, runs OIDC flows, or makes authorization decisions. A fronting auth proxy (oauth2-proxy or the host platform's proxy) owns login/sessions and injects the user's bearer token, which the BFF forwards to the OpenShell gateway for validation and RBAC enforcement. The architecture is explicitly designed for downstream consumption — the frontend exports pages, components, API clients, slots for UI injection, and an i18n layer, while the BFF's service interfaces allow downstream callers to substitute implementations without forking handlers.

## Architectural Analysis

The openshell-dashboard's architecture is shaped by two primary design constraints: relay-only authentication and downstream embeddability. The BFF sits between a React SPA and the OpenShell gateway and translates nothing — request and response bodies mirror the gateway's messages, minus secrets. This "stay in parity" principle means the BFF never renames fields, infers scopes, or coerces types, which keeps the translation layer thin but pushes API awareness into the frontend.

The component manages compatibility with a specific range of OpenShell gateway releases (currently 0.1.0–0.1.2), proven through a compat test suite that runs against digest-pinned gateway images. This is architecturally significant: the wire link (gateway ↔ SDK) is measured rather than assumed, and gateway version range metadata is baked into container image labels and environment variables at build time.

The three `pkg/clients` escape hatches — rawexec.go (binary file uploads via streaming gRPC with no TTY), rawprovider.go (credential key names the SDK drops), and rawprofile.go (full provider profile endpoints the SDK truncates) — represent intentional deviations from the SDK-only pattern, each documented with a specific SDK gap that would delete the workaround when closed.

The frontend's export architecture (pages, components, slots, i18n) allows RHOAI to wrap and embed the dashboard without forking, using the npm package as a dependency. Feature flags control capability exposure per deployment, addressing environments where WebSocket upgrades or specific gateway features aren't available.

TLS is configured at two boundaries: the inbound HTTP server enforces TLS 1.3 minimum when certificates are provided, while the outbound gRPC connection to the gateway supports TLS 1.2+ with optional mTLS client authentication. The BFF never sets `InsecureSkipVerify` — certificate validation is always enabled.
