## Purpose

**Short**: Production-ready starter kits for building and deploying AI agents on Red Hat OpenShift AI, spanning 12 frameworks with a shared Helm-based deployment model and OpenAI-compatible API contract.

**Detailed**: agentic-starter-kits is a collection of self-contained, production-ready agent templates organized by AI framework (LangGraph, CrewAI, LlamaIndex, AutoGen, Google ADK, Langflow, A2A, Claude Code, OpenClaw, Codex, OpenCode, and Vanilla Python). Each template provides a complete agent implementation with its own Dockerfile, Makefile, pyproject.toml, and deployment configuration. Standard agents expose a uniform OpenAI-compatible HTTP API (`POST /chat/completions` and `GET /health`) served via FastAPI/uvicorn, enabling consistent behavioral testing and deployment workflows across all frameworks.

The repository also includes shared components (the `agent-auth` ServiceAccount token auth middleware), a behavioral evaluation harness with MLflow integration, and infrastructure templates for llm-d model serving. Deployment to OpenShift is driven by per-framework Helm charts with edge-terminated TLS Routes, while the OpenClaw agent uses a Kustomize-based deployment with pre-built upstream images. All standard agent containers are built on Red Hat UBI9 Python 3.12 base images and run as non-root user 1001 with restricted security contexts.

## Architectural Analysis

The repository's architecture follows a "template collection" pattern rather than a traditional monolithic service or operator. Each agent under `agents/<framework>/templates/` is a self-contained, independently deployable unit with its own dependency tree (managed via `uv` lock files), Dockerfile, and Helm values — yet all standard agents converge on a shared API contract (`POST /chat/completions`, `GET /health`) and deployment topology (UBI9 container → Helm chart → OpenShift Route with edge TLS).

The shared `agent-auth` component in `components/auth/` provides a reusable ASGI middleware (`SATokenAuthMiddleware`) that authenticates callers via the Kubernetes TokenReview API, enforcing ServiceAccount identity-based access control. This is opt-in per deployment (controlled by `AUTH_ENABLED`), making it a clean cross-cutting concern that individual agents consume as a pip dependency without tight coupling.

A significant design decision is the separation between "standard" and "non-standard" agents. Standard agents (LangGraph, CrewAI, LlamaIndex, AutoGen, Google ADK, Vanilla Python) follow a uniform structure with shared Helm charts per framework, while non-standard agents (OpenClaw, Codex, OpenCode, Claude Code, Langflow, A2A) each have bespoke deployment patterns — Kustomize manifests, Containerfiles, podman-compose, or custom entrypoints. This divergence is documented explicitly in the repo's AGENTS.md, acknowledging the trade-off between template standardization and framework-specific requirements.

The behavioral evaluation infrastructure (under `evals/harness/` and `tests/behavioral/`) treats deployed agents as black boxes, testing them over HTTP against their shared API contract. This testing approach reinforces the architectural principle that agents are independently deployed services with a common interface.

An architectural risk is the use of pre-built upstream community images for OpenClaw (pinned by digest but not rebuilt or validated by Red Hat), which is explicitly flagged in the deployment manifests. Another consideration is that the MLflow tracing integration across multiple agents includes a configurable TLS verification bypass (`MLFLOW_TRACKING_INSECURE_TLS`), which is useful for development with self-signed certificates but could pose risks if left enabled in production.
