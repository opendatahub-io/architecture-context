## Purpose

**Short**: Envoy External Processing (ext-proc) filter and Kubernetes controller that enables the AI Gateway to route, authenticate, and translate requests across external LLM providers.

**Detailed**: AI Gateway Payload Processing is a combined gRPC service and Kubernetes controller that sits in the Envoy data path as an External Processing filter. It intercepts every inference request flowing through the AI Gateway, resolves which external LLM provider should handle the request (using ExternalModel and ExternalProvider CRDs), translates API formats between different provider conventions (OpenAI, Anthropic, Azure OpenAI, AWS Bedrock, Google Vertex), injects provider-specific credentials, and manages the Gateway API routing resources (HTTPRoute, Service, ServiceEntry, DestinationRule) that connect the gateway to external endpoints.

The component is built on the upstream `llm-d/llm-d-inference-payload-processor` framework and extends it with a downstream plugin suite that handles multi-provider model resolution, API format translation, credential injection (API key, SigV4, OAuth2), NeMo guardrail integration, usage metering, and routing loop detection. A `dynamicmetadata` wrapper intercepts ext-proc responses to inject Envoy dynamic metadata via pseudo-headers, enabling plugins to influence downstream Envoy routing decisions (e.g., provider selection, hub-mode cross-cluster routing).

The controller plane watches ExternalProvider CRs to create Istio networking resources (ExternalName Service, ServiceEntry for DNS resolution, DestinationRule for TLS origination) and watches ExternalModel CRs to create HTTPRoutes that bind client-facing model names to specific provider backends through the platform's Gateway. A legacy migration controller automatically converts `maas.opendatahub.io` CRs to the current `inference.opendatahub.io` API, preserving backward compatibility during the v1alpha1 transition.

## Architectural Analysis

The design fuses two runtime concerns into a single binary: a gRPC ext-proc server that intercepts live Envoy traffic and a set of controller-runtime reconcilers that manage Kubernetes networking resources. This co-location is deliberate---the ext-proc plugins need in-memory caches of ExternalModel/ExternalProvider state for sub-millisecond lookups during request processing, and the `model-provider-resolver` plugin shares reconciler informers with the controller plane, avoiding a separate data layer.

The plugin architecture is layered: the upstream `llm-d-inference-payload-processor` framework provides the core processing pipeline (profile pickers, body-field-to-header extraction, model selector with filter/scorer/picker stages), while the downstream `pkg/plugins/` package registers the ODH/RHOAI-specific plugins that handle real provider interactions. Plugin ordering is declarative via the Helm `customConfig.profiles` configuration, allowing operators to compose different request/response processing chains---for example, the hub-mode deployment splits processing into separate pre-auth (PROPOSE) and post-EPP (TRANSFORM) phases, each with its own EnvoyFilter anchor.

The component occupies a security-sensitive position in the architecture. It handles provider credentials (API keys, AWS SigV4 signatures, GCP OAuth2 tokens) at runtime. The ExternalProvider reconciler validates credential Secrets exist before marking the provider Ready, and the controller layer enforces TLS-only transport for any credentialed provider (CWE-319 prevention). The ext-proc gRPC server supports optional TLS with self-signed certificates for environments where Envoy-to-ext-proc traffic must be encrypted, though in typical mesh deployments the Istio sidecar provides mTLS.

A key architectural risk is the hand-maintained copy of the upstream runner (`cmd/runner.go`). The downstream wraps `handlers.NewServer` with `dynamicmetadata.WrapServer` to inject Envoy dynamic metadata, but upstream provides no hook for this, so the entire runner is forked. The file contains explicit "KEEP IN SYNC" comments noting that upstream changes to `handlers.NewServer`'s signature or `registerInTreePlugins` require manual re-diffing.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace Secrets for provider credentials; Kubernetes RBAC on CRDs | Kubernetes | Shared ClusterRole in multi-namespace mode grants cross-namespace read on Secrets (mitigated by label selector on apikey-injection plugin) |
| Data storage | Per-namespace CRs (ExternalModel, ExternalProvider, Secret) | Kubernetes | No persistent storage; in-memory caches are namespace-indexed |
| Network traffic | Per-ExternalModel HTTPRoute scoped to namespace path prefix (`/{namespace}/{model}`) | Gateway API / Envoy | Cross-namespace model name collisions prevented by path prefix namespace inclusion |
| Compute & resources | Single shared ext-proc pod processes all namespaces | Kubernetes | No per-namespace resource quotas on ext-proc processing; noisy neighbor possible |
| Configuration & secrets | Per-namespace Secrets referenced by ExternalProvider CRs | Kubernetes | Secret must be co-located with ExternalProvider in same namespace (enforced by reconciler) |
| API scoping | Namespace-scoped watches when NAMESPACE env is set; cluster-wide when multiNamespace=true | Application / Kubernetes | In multi-namespace mode, controller caches all namespaces; scoping controlled by RBAC |
