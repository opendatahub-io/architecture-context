## Purpose

**Short**: A Kubernetes operator that automates the deployment, lifecycle management, and multi-instance orchestration of MLflow tracking servers on OpenShift and Kubernetes clusters.

**Detailed**: The MLflow Operator manages the full lifecycle of MLflow deployments through a declarative Custom Resource API (`MLflow` CR). When a user creates an `MLflow` CR, the operator uses embedded Helm charts to render and reconcile all required Kubernetes resources — Deployments, Services, ServiceAccounts, PersistentVolumeClaims, CronJobs for garbage collection and trace archival, NetworkPolicies, and optionally a dedicated artifact-serving Deployment. The operator supports multiple concurrent MLflow instances within a single namespace, with each CR driving an independent stack of resources distinguished by name suffix.

The operator integrates with the OpenShift platform through several optional subsystems discovered at startup via the Kubernetes discovery API: Gateway API HTTPRoutes for ingress routing through the data-science gateway, OpenShift ConsoleLinks for dashboard integration, ServiceMonitors for Prometheus metrics collection, and a Namespace RBAC controller that propagates workspace-scoped RoleBindings based on the platform's Auth CR. It also fetches and watches the cluster's TLS security profile from `apiservers.config.openshift.io` to dynamically configure cipher suites and TLS versions, restarting itself if the profile changes. The operator additionally supports an MLflowOperator module controller path for coordinated ODH platform handoff via the `components.platform.opendatahub.io` API group.

## Architectural Analysis

The mlflow-operator follows a Helm-rendering operator pattern — rather than using raw client-go resource construction, it embeds Helm charts under `charts/mlflow/` and renders them through the Helm library at reconcile time, using values derived from the MLflow CR spec and operator configuration. This approach consolidates resource templates in standard Helm format while retaining controller-runtime's reconciliation loop and ownership model.

The operator uses a sophisticated resource-scoped caching strategy. The controller-runtime cache is configured with label selectors (`app=mlflow`) and field selectors (`metadata.name`) per GVK, rather than watching entire namespaces. This keeps RBAC aligned with `resourceNames`-scoped ClusterRole rules — Kubernetes only honors list/watch permissions with resourceNames when the request carries a matching field selector. Dedicated per-name caches (`GCRBACWatchCache`, `ViewRBWatchCache`, `EditRBWatchCache`) are created for singleton resources like the garbage-collection ClusterRole because controller-runtime allows only one field selector per GVK per cache.

The operator's TLS configuration is notable: at startup it fetches the cluster's `TLSProfileSpec` from the OpenShift `APIServer` resource, translates it into Go `tls.Config` cipher suites via `openshift/controller-runtime-common`, and installs a watcher that triggers a clean shutdown (and automatic restart via the Deployment) if the cluster TLS profile changes. This ensures the metrics endpoint always matches the cluster-wide security policy.

A key design decision is the optional activation of controllers via environment variables (`ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER`, `ENABLE_NAMESPACE_RBAC`). The operator waits for required CRDs (MLflowOperator, Auth) with configurable timeouts before proceeding, allowing graceful degradation when platform components are not yet installed.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregate ClusterRoles (mlflow-view, mlflow-edit) with RBAC aggregation labels; per-namespace workspace RoleBindings via NamespaceRBACReconciler | Kubernetes RBAC | Workspace RBAC requires `ENABLE_NAMESPACE_RBAC=true` and Auth CR; without it, namespace-level access is not automatically scoped |
| Data storage | Per-CR PVCs, per-CR backend store URIs (SQLite or PostgreSQL), per-CR artifact destinations | Application (operator renders per-CR resources) | Multiple CRs sharing the same external database URI would share metadata; no operator-level enforcement against this |
| Network traffic | Per-CR NetworkPolicy rendered via Helm chart; operator-level NetworkPolicy restricts ingress to monitoring namespaces only | Kubernetes NetworkPolicy | Egress rules configurable per CR; default allows DNS, HTTPS, PostgreSQL, MySQL, S3 ports |
| Compute & resources | Per-CR resource requests/limits, pod scheduling (nodeSelector, tolerations, affinity), DRA ResourceClaims | Kubernetes (resource limits on rendered Deployments) | No ResourceQuota or LimitRange enforcement; noisy-neighbor possible within shared namespace |
| Configuration & secrets | Per-CR env vars, envFrom, CABundleConfigMap; artifact-connection secret scoped by resourceNames RBAC | Kubernetes Secrets + Application | Operator SA can only read the single named secret `mlflow-artifact-connection`; per-CR secret references use envFrom |
| API scoping | Cluster-scoped MLflow CR; namespace-scoped cache with label/field selectors | Kubernetes + Application | MLflow CR is cluster-scoped; users with cluster-wide access can see all instances |
