## Purpose

**Short**: A centralized library of reusable Kubeflow Pipelines components and pre-compiled managed pipeline definitions for AI/ML workflows in RHOAI.

**Detailed**: The pipelines-components repository provides the building blocks for AI/ML workflows on Red Hat OpenShift AI. It contains reusable KFP (Kubeflow Pipelines) components organized into four categories — data processing, training, evaluation, and deployment — plus complete pipeline definitions that compose these components into end-to-end workflows such as LLM fine-tuning (SFT, LoRA, OSFT), AutoML (AutoGluon tabular and time series), and AutoRAG (document indexing, RAG optimization).

The repository produces four container images via Konflux Dockerfiles. The primary image (`pipelines-components`) runs as an init container that stages pre-compiled managed pipeline YAMLs into a shared volume for the KFP API server. Three additional images support AIPCC-based workloads: `automl` for AutoGluon tabular training, `autorag` for document processing with embedded Docling and Whisper models, and `autorag-inference` for deploying AutoRAG-generated agents. Components within this library are designed to run as KFP task containers — they are compiled into pipeline YAML specs and executed by the KFP backend, not deployed as standalone services.

## Architectural Analysis

The repository follows Kubeflow's component-pipeline separation pattern: leaf-level components (`components/`) define individual KFP steps as Python functions decorated with `@dsl.component`, while pipeline definitions (`pipelines/`) compose these components into directed acyclic graphs via `@dsl.pipeline`. This structure enables component reuse across multiple pipelines — for example, `dataset_download` and `kubeflow_model_registry` are shared across all fine-tuning pipeline variants.

A notable architectural pattern is the managed pipeline system. Pipelines marked `managed: true` in their `metadata.yaml` are compiled at image build time into YAML specs and bundled into the init container image. At runtime, the init container copies these pre-compiled YAMLs to a shared volume that the KFP API server reads. When `RELATED_IMAGE_*` environment variables are present (injected by DSPO), the init container recompiles pipelines on the fly to substitute operator-controlled image references — a key mechanism for ensuring air-gapped deployment support without modifying the pipeline sources.

Several components create Kubernetes custom resources at runtime rather than through static manifests. The `model_deployment` and `deploy_embedding_model` components create KServe `ServingRuntime` and `InferenceService` CRs using the in-cluster Kubernetes API, while the `evalhub_evaluator_kserve` component creates temporary KServe resources for model evaluation and cleans them up after completion. This pattern delegates resource lifecycle management to individual pipeline steps rather than to a centralized operator.

The AIPCC base image strategy is partially adopted: three of four Konflux Dockerfiles use `quay.io/aipcc/base-images/cpu-el9.8:3.6.0` for consistent Python packaging, while the primary `pipelines-components` image uses a UBI9/python-312 base with the RHOAI PyPI index configured directly. The primary image also sets post-quantum crypto policies (`DEFAULT:PQ`), a hardening measure not present in the AIPCC-based images since those inherit their crypto posture from the base image.
