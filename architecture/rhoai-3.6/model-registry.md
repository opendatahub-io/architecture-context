## Purpose

**Short**: Central metadata registry for ML models, versions, and artifacts with a federated catalog for cross-platform model discovery.

**Detailed**: Kubeflow Hub (formerly Model Registry) provides a REST API server that stores and manages ML model metadata — registered models, model versions, and model artifacts — backed by a relational database (MySQL or PostgreSQL). The project has evolved beyond a simple registry into an umbrella of related services.

The core model-registry server exposes an OpenAPI-defined REST API (v1alpha3) for CRUD operations on model metadata. An optional Kubernetes controller reconciles KServe InferenceService resources by annotating them with model registry labels and finalizers, linking deployed inference endpoints back to their registry entries. A UI Backend-For-Frontend (BFF) service bridges the React frontend to the model registry API and Kubernetes API, handling authentication delegation, Kubernetes RBAC checks, and UI-specific aggregation. A catalog service enables federated discovery across external model sources (HuggingFace, MCP servers, serving runtimes, skill catalogs). A Container Storage Interface (CSI) storage initializer allows KServe to download model artifacts using `model-registry://` URIs. A Python async-upload job runs as a Kubernetes Job to copy models between storage backends (S3, HuggingFace, OCI registries) with Sigstore signing integration.

## Architectural Analysis

Model Registry follows a multi-component architecture where each concern is a separate deployable artifact sharing a common Go module workspace. The core server is a contract-first REST proxy backed by GORM for database abstraction, supporting both MySQL and PostgreSQL. This design separates the OpenAPI contract from the storage layer, with code generation bridging the two through converters.

The controller component uses controller-runtime (kubebuilder scaffold) to watch KServe InferenceService resources and synchronize metadata between the registry and serving infrastructure. It is conditionally activated via the `INFERENCE_SERVICE_CONTROLLER=managed` environment variable, meaning the same binary can be deployed without the controller when KServe integration is not desired. The controller maintains finalizers on InferenceServices to ensure clean lifecycle management.

The BFF is architecturally interesting: it implements dual authentication modes — `internal` (using its own ServiceAccount) and `user_token` (forwarding the user's Bearer token). In `user_token` mode, it impersonates the requesting user for Kubernetes API calls by constructing per-request typed clients, which means authorization checks are delegated to the Kubernetes API server under the user's identity. The BFF also performs SubjectAccessReview and SelfSubjectAccessReview checks to determine what namespaces and registries the user can access.

The async-upload job is the only Python component that ships as a container image. It uses AIPCC base images, includes `rh-model-signing` for Sigstore-based model signature verification, and integrates with `olot` and `oras` for OCI artifact management. This job is noteworthy because it is the bridge between external storage (S3, HuggingFace Hub) and internal OCI registries.

Network isolation relies on Istio sidecar injection and AuthorizationPolicies. The model-registry server's AuthorizationPolicy enforces a two-rule pattern: ingress gateway traffic (user-facing, authenticated by oauth2-proxy) and internal control-plane traffic (service-to-service, scoped to the `kubeflow` namespace with JWT required and `kubeflow-userid` header explicitly blocked to prevent impersonation).

A notable risk is the TLS configuration for the InferenceService controller: the `SKIP_TLS_VERIFY` environment variable defaults to `false` but can be set to `true`, which would disable certificate verification for model registry API calls from the controller.

| Data storage | Per-namespace database instance (each registry deployment has its own DB) | Kubernetes (separate Deployments) | No shared database isolation needed since each namespace has its own deployment |
| Network traffic | Istio sidecar injection + AuthorizationPolicy per deployment | Istio | VirtualServices use wildcard host (*); relies on Istio for enforcement |
| Compute & resources | No ResourceQuota or LimitRange defined in manifests | N/A | Resource limits set per-container but no namespace-level quotas |
| Configuration & secrets | Per-namespace Secrets for database credentials | Kubernetes | mysql-secret must be provisioned per namespace |
| API scoping | BFF performs namespace-scoped operations using user's token; controller watches all namespaces | Kubernetes RBAC + Application | Controller has cluster-wide read access to InferenceServices |
