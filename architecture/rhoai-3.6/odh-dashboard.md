## Purpose

**Short**: ODH Dashboard provides the web UI for Red Hat OpenShift AI, enabling users to navigate and interact with the platform's AI/ML components through a modular, federated frontend architecture.

**Detailed**: ODH Dashboard is a pnpm-workspace monorepo containing the main dashboard application and over 25 feature packages. The frontend is built with React 18 and PatternFly v6, using Rspack Module Federation to allow independent feature modules (gen-ai, model-registry, maas, agent-ops, automl, autorag, eval-hub, mlflow, data-connect-hub, data-registry, notebooks) to be developed, built, and deployed independently as federated micro-frontends.

Each feature module pairs a TypeScript/React frontend with a Go Backend-for-Frontend (BFF) service that handles server-side API calls, Kubernetes resource operations, and domain-specific integrations. The core dashboard consists of a Node.js/Fastify backend proxying Kubernetes API requests on behalf of users, a kube-rbac-proxy sidecar for TLS termination and authentication, and a core-bff Go service handling shared backend operations. These three containers run in a single pod, while BFF modules are deployed as separate pods managed by the dashboard-operator.

The dashboard-operator is a Go controller-runtime operator that reconciles the `Dashboard` custom resource, managing the lifecycle of dashboard deployments, RBAC, networking (HTTPRoutes, NetworkPolicies), and module deployments. It also embeds the upstream Kubeflow Workspaces controller for managing Workspace and WorkspaceKind resources.

## Architectural Analysis

The ODH Dashboard's most distinctive architectural choice is its **federated modular architecture**. Rather than a monolithic frontend, the system uses Webpack Module Federation (via Rspack) to compose the UI from independently-deployed feature modules at runtime. Each module is a self-contained unit: a React frontend loaded as a federated remote, paired with a Go BFF sidecar that handles server-side logic. This architecture allows feature teams to develop, test, and release independently while sharing common UI components (plugin-core, k8s-core, foundation, ui-core) through workspace packages.

The **three-container pod pattern** for the core dashboard (Node.js app + kube-rbac-proxy + core-bff) establishes a consistent security boundary: all external traffic enters through kube-rbac-proxy on port 8443 with TLS and OpenShift authentication, then is proxied to the Node.js backend on localhost:8080. The core-bff sidecar on port 8943 serves its own TLS using certificates from the OpenShift serving-cert-secret mechanism.

The **TLS configuration** is notably sophisticated. A shared `pkg/tls` package reads the cluster-wide TLS security profile from `apiservers.config.openshift.io/cluster` and maps OpenSSL cipher names to Go's crypto/tls constants, supporting Intermediate, Modern, Old, and Custom profiles. This ensures all Go BFF services honor the cluster administrator's TLS policy. The main Dockerfile also sets `DEFAULT:PQ` crypto policies for post-quantum readiness.

A key architectural risk is the **breadth of RBAC permissions** granted to the dashboard's ClusterRole. The operator needs access to over 30 API groups spanning core Kubernetes, OpenShift, KServe, Kubeflow, Gateway API, Feast, MLflow, TrustyAI, NIM, agents, MCP, and observability resources. While this reflects the dashboard's role as a unified control plane for the platform, it creates a large blast radius if the service account is compromised. The dashboard mitigates this through user impersonation — the Node.js backend proxies Kubernetes API calls using the authenticated user's token rather than the service account, so the user's own RBAC applies for most operations.

The **Gateway API integration** represents the RHOAI 3.x ingress pattern. The operator creates HTTPRoute resources pointing to the `data-science-gateway` Gateway, replacing the legacy OpenShift Route mechanism. Each BFF module gets its own NetworkPolicy for network isolation.

### Tenant Model

| Aspect | Value | Source |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy (TLS + OpenShift auth), per-request token impersonation for K8s API, SubjectAccessReview in BFFs | Kubernetes (RBAC) + Application (middleware) | Service account has broad ClusterRole; mitigated by user token impersonation |
| Data storage | Per-namespace PVCs and Secrets; no shared database | Kubernetes | None — data is namespace-scoped by Kubernetes |
| Network traffic | Per-module NetworkPolicy; kube-rbac-proxy limits external access | Kubernetes | Module NetworkPolicies are operator-managed |
| Compute & resources | ResourceRequests/Limits on all containers; PodDisruptionBudget | Kubernetes | No per-tenant ResourceQuota (delegated to platform operator) |
| Configuration & secrets | Per-namespace Secrets; OdhDashboardConfig is a shared cluster-scoped ConfigMap | Kubernetes + Application | OdhDashboardConfig is shared — admin settings apply globally |
| API scoping | Node.js backend proxies K8s API with user's token (namespace-scoped access); BFFs use SelfSubjectAccessReview/SelfSubjectRulesReview | Kubernetes (RBAC) | BFF internal SA operations use operator SA, not user token |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Dashboard backend (Node.js) | per-user token | Kubernetes RBAC via impersonation |
| Core BFF (Go) | per-user token | SelfSubjectAccessReview per request |
| Module BFF pods | per-user token | SelfSubjectAccessReview / SelfSubjectRulesReview per request |
