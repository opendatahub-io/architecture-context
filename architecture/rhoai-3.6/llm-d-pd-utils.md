## Purpose

**Short**: Operational utility toolkit providing agentic skills, network performance testing, and NIXL benchmarking tools for llm-d prefill/decode disaggregated inference deployments.

**Detailed**: llm-d-pd-utils is a companion repository for the llm-d project that provides operational tooling for validating, diagnosing, and benchmarking GPU networking in disaggregated LLM inference deployments. It does not deploy as a standalone service; instead its scripts and skills are injected into llm-d model server pods or run externally against them via `kubectl exec`.

The repository contains two Claude Code agentic skills (`/llm-d-preflight-checks` and `/llm-d-networking-tests`) that automate multi-step operational workflows. The preflight checks skill gates vLLM startup by running a Python diagnostic script that collects GPU topology, NVLink status, and environment variables — optionally pausing with an HTTP server so operators can inspect the environment before the model loads. The networking tests skill orchestrates RDMA bandwidth/latency measurements (perftest, iperf3, NCCL/RCCL collectives, nixlbench) between pod pairs and generates tabular and visual reports of network performance.

Additionally, the repository includes NIXL installer scripts (supporting both root and non-root containers), a benchmark suite for measuring NIXL GPU VRAM-to-VRAM transfer throughput over UCX/RDMA, and sample Kubernetes Pod/Service manifests for deploying NIXL client-server pairs on GPU nodes.

## Architectural Analysis

llm-d-pd-utils occupies an unusual architectural niche: it is a toolkit rather than a deployed service. Its value lies in bridging the gap between Kubernetes pod scheduling outcomes and the networking performance that disaggregated inference requires. The core design insight is that GPU topology mismatches (GPUs on different NUMA nodes, PCIe root complexes, or NVSwitch domains) silently degrade performance — symptoms appear as elevated time-to-first-token rather than obvious errors.

The preflight checks pattern is architecturally significant because it uses a technique where the diagnostic script and vLLM are chained with `&&` in the container command, and in pause mode the script binds to the same port vLLM would use, satisfying Kubernetes health probes while blocking model loading. This allows operators to inspect the exact runtime environment — same GPU bindings, same RDMA devices, same UCX configuration — that vLLM will see.

The Makefile contains scaffolding from a Kubernetes operator template (controller-gen, go build targets, RBAC targets), but no Go source code exists in the repository. The actual functional code is entirely Python and shell scripts. The `Dockerfile copy` file similarly contains a Go builder Dockerfile that references non-existent Go source — this appears to be vestigial scaffolding.

The networking test suite has a modular architecture: `run-tests.py` is the unified entry point that dynamically imports specialized test modules (perftest, iperf3, NCCL/RCCL, nixlbench, discovery) via `importlib`. This design avoids circular dependencies and allows individual test types to be composed freely. The test framework supports both `kubectl exec` and SSH-based execution modes, enabling use inside and outside the cluster.
