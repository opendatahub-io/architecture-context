## Purpose

**Short**: OpenShell is a safe, private runtime for autonomous AI agents that enforces kernel-level isolation policies on sandboxed workloads.

**Detailed**: OpenShell provides a control plane and sandbox runtime that enables AI agents to read files, install packages, call APIs, and use credentials without unrestricted access to data, secrets, or network resources. Operators declare what each agent can touch in a policy, and OpenShell enforces it at the kernel level via isolated sandboxes with seccomp-mediated I/O and network proxying.

The architecture follows a three-tier model: a **gateway** (gRPC/HTTP control plane managing sandbox lifecycle, providers, and configuration), a **supervisor** (policy evaluation, credential injection, and L7 network enforcement running outside the agent workload), and a **sandbox** binary (injected into arbitrary container images to monitor processes and enforce filesystem/network/syscall constraints). SDKs in Rust, Python, Go, and TypeScript provide client access to the gateway API.

Within the RHOAI platform, OpenShell is deployed via Helm as a StatefulSet (or Deployment with an external database). The Kubernetes compute driver manages sandbox pods with per-sandbox identity, and a formal policy prover (backed by Z3) verifies policy changes before they are applied. The component originates from NVIDIA's upstream project and is forked through opendatahub-io to Red Hat Data Services for productization.

## Architectural Analysis

OpenShell's architecture separates trust boundaries cleanly across three binaries. The gateway is the only component that holds persistent state (SQLite by default, external PostgreSQL for multi-replica) and exposes the full gRPC API surface (109 RPCs across 5 protobuf service definitions). The supervisor is stateless and ephemeral — one instance per sandbox session — acting as a policy-aware reverse proxy for all network traffic leaving the sandbox. The sandbox binary is a fully-static glibc binary designed to be injected into arbitrary container images without depending on the host's libc or NSS, which required a custom NSS-pinning mechanism (pin-nss.c) to avoid RHAI-1927 crashes.

The driver abstraction is a notable design pattern: compute drivers (Docker, Podman, Kubernetes, MicroVM, Windows MXC) and credential drivers (Kubernetes Secrets, Vault, database) implement gRPC service contracts via Unix domain sockets. This allows the gateway to be composed with different backends at build time — the Konflux gateway image includes only the Kubernetes driver and disables telemetry, while upstream builds include all drivers.

The formal verification layer (openshell-prover, backed by Z3 SMT solver) is architecturally distinctive — it enables pre-approval review of policy changes by formally checking what new access a change would grant. This makes policy management audit-friendly in enterprise environments.

The TLS stack uses rustls with the aws-lc-rs cryptographic provider throughout, with post-quantum cryptography enabled at the OS level (RHEL `DEFAULT:PQ` crypto policy) on all Konflux-built images. The gateway and supervisor use dynamic linking to pick up system NSS and crypto, while the sandbox uses static linking with its own TLS stack. Gateway interceptors and supervisor middleware provide extension points for custom request transformation and enforcement logic.
