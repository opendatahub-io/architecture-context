## Purpose

**Short**: Diagnostic data collection tool that gathers logs, resource definitions, and configuration from Red Hat OpenShift AI (RHOAI) installations for support and troubleshooting.

**Detailed**: must-gather is a containerized diagnostic collection tool designed to capture comprehensive state snapshots from RHOAI deployments. It is invoked via `oc adm must-gather` on OpenShift or as a Kubernetes Job on non-OpenShift platforms (AKS, EKS, CKS). The tool collects namespace-scoped resources, pod logs, custom resource instances, Helm release information, cluster-scoped metadata, and observability data across all RHOAI components.

The collector is organized into 16 component-specific gathering scripts (dashboard, DSP, KServe, KubeRay, Kueue, KFTO, workbench, model registry, TrustyAI, Feast operator, MLflow, Spark operator, AI Gateway, MCP lifecycle operator, OGX, and a shared LLM-D/KServe module) that can run individually or in parallel during a full collection. Each script discovers relevant namespaces by querying the Kubernetes API for component-specific custom resources, then collects namespace dumps, resource YAML, pod logs, and events. The LLM-D subsystem adds dependency collection for cert-manager, Sail/Istio, and Leader Worker Set (LWS), as well as observability resources from Prometheus Operator or Azure Managed Prometheus.

The tool auto-detects the Kubernetes distribution (OpenShift, CKS, AKS, EKS) at startup and adapts its collection strategy accordingly — using `oc adm inspect` on OpenShift and a custom `kubectl_inspect` reimplementation on xKS platforms. On xKS, only KServe and AI Gateway are collected by default; additional resources (ModelExpress, MaaS, Batch Gateway) require explicit opt-in via environment variables.

## Architectural Analysis

must-gather follows a modular dispatcher pattern: a main `gather.sh` entry point detects the Kubernetes distribution, establishes default namespaces, and routes to component-specific scripts based on the `COMPONENT` environment variable. When `COMPONENT=all` (the OpenShift default), all 16 collectors run as background processes with PID tracking and failure reporting.

The architecture addresses multi-platform support through two layers of abstraction. First, `xks_util.sh` provides `detect_k8s_distro()` which fingerprints the cluster using node metadata, provider IDs, and API resource probes. Second, shared resource collection is split between `run_mustgather()` (OpenShift, using `oc adm inspect`) and `run_k8sgather()` / `kubectl_inspect()` (xKS, using native `kubectl`). The xKS path includes auto-discovery of all namespaced and cluster-scoped API resources, pod log collection with previous-container support, and event collection — effectively reimplementing the `oc adm inspect` workflow in portable shell.

A notable design choice is the LLM-D subsystem nested under `collection-scripts/llm-d/`, which acts as a dependency-aware meta-collector. It chains calls to cert-manager, Sail/Istio, and LWS dependency scripts, collects Gateway API resources, InferencePool/InferenceObjective CRDs, monitoring resources (ServiceMonitor, PodMonitor), and cluster-level diagnostics — all while deduplicating namespaces that the parent KServe collector already inspected. This nested structure reflects the tight coupling between KServe inference serving and the LLM-D disaggregated serving stack.

The Dockerfile configures a post-quantum-ready crypto policy (`DEFAULT:PQ`) via `update-crypto-policies`, which signals forward-looking TLS readiness at the system level. The image also bundles `helm` and `kubectl` CLIs alongside the OpenShift `oc` tooling, enabling Helm release value extraction across platforms.
