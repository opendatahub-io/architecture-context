## Purpose

**Short**: Distributed control plane that connects AI inference backends across Kubernetes clusters, cloud providers, and third-party APIs into a single routable mesh for the Praxis AI gateway.

**Detailed**: AI Grid Network (AGN) is a peer-to-peer orchestration daemon that manages multi-site AI inference routing. The operator watches Kubernetes CRDs (GridNetwork, GridSite, InferenceProvider, AgentToolProvider), discovers peer sites via the SWIM gossip protocol, propagates provider state using CRDTs (Last-Writer-Wins registers, OR-Sets, G-Counters), scores candidates using configurable strategies, and writes a versioned routing overlay as a ConfigMap that the Praxis AI gateway hot-reloads without restarts.

The repository produces three deployable binaries: the `operator` (control-plane daemon), the `enrollment` service (site onboarding with its own CA and Postgres-backed token store), and the `grid-gateway` (a Praxis/Pingora-based data-plane proxy with AGN-specific filter plugins). AGN handles the control plane — deciding what should be routable — while Praxis handles the data plane — proxying actual inference requests, translating API formats, and injecting credentials.

## Architectural Analysis

AGN's architecture separates concerns cleanly between a control plane (this operator) and a data plane (Praxis gateway). The operator is an orchestrator, never in the request path. All routing decisions are pre-computed into a local overlay file that each gateway reads independently, enabling zero-latency request routing with no control-plane dependency at request time.

The distributed state layer is built on three protocols: SWIM (via `foca`) provides fast, failure-tolerant peer discovery with bounded message complexity; delta CRDTs enable eventual consistency of provider capabilities and health metrics across sites without requiring consensus; and a scoring engine selects providers using pluggable strategies (`noMetrics` for opaque API backends, `queueDepth` and `kvCachePressure` for telemetry-rich backends like llm-d).

The trust architecture is certificate-based: the enrollment service operates as a site-private CA, issuing mTLS certificates for inter-site communication. Sites enroll through a token-based flow, receiving grid identity certificates. The operator manages certificate lifecycle, and gateways authenticate peers via mutual TLS. SWIM gossip packets are encrypted with AES-256-GCM using a shared key sourced from a Kubernetes Secret.

A notable design choice is the dual TLS backend: each crate exposes `tls-rustls` (default, using ring) and `fips` (using system OpenSSL) feature flags. This allows the same codebase to produce both upstream community builds and FIPS-compliant RHOAI builds by changing a single Cargo feature. The gateway workspace separately links OpenSSL via Praxis/Pingora.

The workspace enforces an unusually strict lint policy — `unsafe_code` is forbidden, `unwrap_used` / `expect_used` / `panic` / `indexing_slicing` are denied, arithmetic overflow is denied, and `allow` attributes require `#[expect(lint, reason = "...")]` instead. This policy significantly reduces the risk of runtime panics in production.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | mTLS for inter-site, Kubernetes RBAC for CRD access, SAR for enrollment API | Kubernetes + Application | CRDs are cluster-scoped; any user with CRD access can see all GridNetworks |
| Data storage | Routing overlays per gateway namespace ConfigMap; enrollment state in Postgres | Kubernetes (ConfigMap) + Application (Postgres) | Single Postgres instance shared by all enrollments |
| Network traffic | SWIM encryption (shared key per GridNetwork); mTLS for data plane | Application | No NetworkPolicy generated by the operator |
| Compute & resources | Single operator replica; no per-network resource quotas | Kubernetes (Deployment) | All networks share one operator instance |
| Configuration & secrets | Per-GridNetwork TLS secrets and SWIM keys | Kubernetes (Secrets) | Grid-operator SA can read secrets across namespaces |
| API scoping | InferenceProvider.spec.accessPolicy.siteSelector controls cross-site visibility | Application | Label-based selector; no Kubernetes-level enforcement |
