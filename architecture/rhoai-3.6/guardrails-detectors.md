## Purpose

**Short**: A collection of text detection microservices for the FMS Guardrails Orchestrator, providing regex-based PII detection, HuggingFace model-based content classification, and LLM-as-a-judge evaluation.

**Detailed**: guardrails-detectors provides three independently deployable detector microservices that integrate with the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator), an IBM-led open source project for applying guardrails to LLM input and output. Each detector implements the same content analysis API contract (`/api/v1/text/contents`) but uses different detection strategies.

The **built-in detector** ships lightweight heuristic detectors (regex-based PII detection for emails, credit cards, SSNs, phone numbers, IP addresses; file-type validation for JSON, XML, YAML with optional schema checking; and user-defined custom detectors loaded from a Python module). It runs on port 8080 with 4 uvicorn workers and requires no external model or service.

The **HuggingFace detector** loads a local HuggingFace model (sequence classification, token classification, or causal LM such as IBM Granite Guardian) and performs inference on text content. It deploys as a KServe InferenceService via a ServingRuntime, runs on port 8000, and supports CUDA GPU acceleration with optional CPU fallback. The **LLM Judge detector** delegates evaluation to an external vLLM-compatible LLM server via the `vllm_judge` library, supporting a catalog of built-in metrics (safety, accuracy, helpfulness, toxicity, etc.) and custom natural-language evaluation criteria.

All three detectors share a common FastAPI base class (`DetectorBaseAPI`) that provides health checks, Prometheus instrumentation (per-detector request/detection/error/runtime counters), and consistent error handling. The project is maintained by the TrustyAI team and integrated into the Red Hat OpenShift AI guardrails stack.

## Architectural Analysis

The guardrails-detectors architecture follows a plugin-oriented microservice pattern where three independent detector implementations share a common base framework but are packaged and deployed as separate container images. This design trades deployment simplicity for operational flexibility: each detector can be scaled, versioned, and resource-tuned independently based on its computational profile.

The shared `DetectorBaseAPI` class (extending FastAPI) centralizes cross-cutting concerns — health endpoints, Prometheus metrics with a `trustyai_guardrails_` prefix, and exception handling — creating consistency across detector types without tight coupling. The `InstrumentedDetector` mixin adds per-function timing and detection counters, enabling fine-grained observability across all detector registries.

A notable design decision in the built-in detector is the custom detector extension system: user-provided Python functions are loaded from `custom_detectors.py` via `importlib`, with best-effort static analysis blocking `os`, `subprocess`, `eval`, and `exec` calls. This is explicitly not a security sandbox — the AST-based check catches simple cases but cannot prevent determined exploitation. The `non_blocking` decorator pattern allows custom detectors to run asynchronously without blocking the API response, useful for logging or audit trail functions that should not add latency.

The HuggingFace detector supports three distinct model architectures (sequence classification, token classification, causal LM) behind a unified API, auto-detecting the model type from its HuggingFace config. Token classification produces span-level detections with character offsets and adjacent-token grouping, while sequence and causal LM modes produce document-level scores. The threshold system is layered: environment-variable defaults, per-label overrides, and per-request parameters, with max-length clamping to the model's actual capacity.

The LLM Judge detector is architecturally distinct as it performs no local inference — all evaluation is delegated to an external vLLM server via async HTTP calls. This makes it lightweight but introduces a runtime dependency and network latency that the other detectors avoid. The `vllm_judge` library handles prompt construction, metric resolution, and response parsing.

Security posture is minimal at the application layer: no authentication middleware is registered on any of the three FastAPI applications. The InferenceService manifests do include `security.opendatahub.io/enable-auth: 'true'` and Istio sidecar injection annotations, indicating that authentication is expected to be enforced at the platform layer (via KServe + Istio + OpenDataHub auth) rather than in the application code. The common app module supports optional TLS via config file (`ssl_ca_certs` triggers `ssl.CERT_REQUIRED`), but no Dockerfile or deployment manifest configures it.

The Konflux build for the built-in detector uses an AIPCC CPU base image (`quay.io/aipcc/base-images/cpu-el9.8`), while the HuggingFace detector uses multi-arch builds with both CUDA and CPU AIPCC base images. Both are built hermetically with pip prefetch. The LLM Judge detector has no Konflux Dockerfile on this branch, indicating it may be at an earlier stage of productization.
