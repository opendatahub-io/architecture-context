## Purpose

**Short**: Data Connect Hub is a middleware service that centralises data connection metadata management and exposes heterogeneous data sources through REST and Apache Arrow Flight gRPC APIs.

**Detailed**: Data Connect Hub (DCH) provides a single integration point for ingesting data from multiple heterogeneous data sources — PostgreSQL, SQLite, S3, Milvus, Elasticsearch, Neo4j, and URI-based endpoints — so consuming services do not need to maintain their own client library stacks for each backend. The system comprises three deployable components: a Go-based Kubernetes controller (`dc-controller`) that reconciles a `DataConnectService` custom resource and provisions the data plane, a Rust HTTP REST service that exposes connection metadata CRUD, credential testing, and binary data download, and a Rust Arrow Flight gRPC service that streams columnar data from configured connectors.

The controller deploys the two Rust services via kustomize manifests embedded in its container image and manages their lifecycle, networking (HTTPRoutes, NetworkPolicies), monitoring (ServiceMonitors), and RBAC. It watches the OpenShift APIServer resource to align TLS configuration with the cluster-wide TLS security profile. The REST service sits behind a `kube-rbac-proxy` sidecar that performs per-endpoint Kubernetes SubjectAccessReview authorization using the caller's `X-Tenant-Id` header as the namespace scope. The Flight service implements its own TokenReview-based authentication layer. Both services share a PostgreSQL metadata store and expose Prometheus metrics.

## Architectural Analysis

Data Connect Hub follows a two-tier architecture: a control plane (Go controller) and a data plane (Rust services). This separation keeps the reconciliation loop lightweight while the data-intensive work — Arrow RecordBatch streaming, format conversion, and connector pooling — runs in Rust with zero-copy where possible.

The connector model is trait-based: each data source implements `SQLReader<RecordBatch>` from the `commons` crate. Connectors are compiled as Cargo features and registered dynamically at startup based on TOML configuration, so disabled connectors carry no runtime cost. The `moka`-based connection pools are per-connector with configurable TTL and idle eviction.

Authorization is noteworthy for its dual-layer design. The REST service delegates authorization to `kube-rbac-proxy`, which maps HTTP paths and methods to Kubernetes `resourceAttributes` using the `X-Tenant-Id` header as the namespace. This produces fine-grained, per-namespace RBAC without application code changes. The Flight service, being gRPC, cannot use `kube-rbac-proxy` and instead implements a tonic middleware layer (`AuthLayer`) that performs TokenReview calls directly via the Kubernetes API.

The controller supports both OpenShift (service-CA certificates, OpenShift TLS profiles) and non-OpenShift Kubernetes (self-signed certificates, xKS overlay). It reads the cluster `APIServer` resource at startup and watches for profile changes, triggering a graceful restart if the TLS profile or adherence policy changes. The default TLS profile is Intermediate (TLS 1.2+) when no cluster profile is configured.

A significant architectural decision is the use of Apache Arrow Flight for the data transfer protocol. This enables columnar data streaming with schema negotiation and is designed for AI/ML workloads that process large datasets. The REST service can proxy binary data from Flight connections for clients that need simpler HTTP access.

The NetworkPolicies are currently allow-all placeholders, acknowledged in comments as awaiting a defined gateway/client topology to scope down. This is a gap to track for production hardening.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace SubjectAccessReview via kube-rbac-proxy (REST); TokenReview via AuthLayer (Flight) | Kubernetes (kube-rbac-proxy) / Application (AuthLayer) | Flight service auth is application-enforced; a bug could bypass tenant isolation |
| Data storage | Shared PostgreSQL database with tenant_id scoping | Application (pg-meta-store query filter) | Application-enforced row-level filtering; a query bug could leak cross-tenant data |
| Network traffic | NetworkPolicies present but currently allow-all | Kubernetes | NetworkPolicies are placeholders — no actual network isolation between tenants |
| Compute & resources | Shared pods (rest-service, flight-service) with resource limits | Kubernetes | No per-tenant resource quotas; one tenant's heavy queries could impact others |
| Configuration & secrets | Per-namespace credentials via X-Tenant-Id scoping; shared service config | Kubernetes / Application | dch-database-config secret is shared; per-tenant data source credentials are namespace-scoped |
| API scoping | kube-rbac-proxy maps each API path to namespace-scoped Kubernetes resources | Kubernetes | Authorization is per-namespace; no cluster-wide tenant isolation beyond namespace RBAC |
