## Purpose

**Short**: Provides the ML pipeline orchestration backend for Red Hat OpenShift AI, enabling users to define, compile, schedule, and execute reproducible machine learning workflows on Kubernetes.

**Detailed**: Data Science Pipelines is the RHOAI downstream fork of Kubeflow Pipelines (KFP). It delivers a complete pipeline orchestration platform composed of an API server, pipeline compiler, workflow execution engine (via Argo Workflows), artifact/metadata tracking (via ML Metadata), a web frontend, and a Python SDK for authoring pipelines as code.

The platform manages the full lifecycle of ML pipelines: compilation from Python DSL to intermediate representation (IR YAML), storage of pipeline definitions and versions (in MySQL or as Kubernetes-native CRDs), scheduling via cron-like recurring runs, execution through Argo Workflows with a driver/launcher pattern that resolves parameters and manages artifact I/O, and persistence of run state, metrics, and lineage metadata.

In RHOAI, the data-science-pipelines-operator (DSPO) deploys and manages instances of this component. The Konflux Dockerfiles in this repo produce the five core Go binaries (api-server, persistence-agent, driver, launcher, scheduled-workflow controller), while the UI, metadata services, and third-party dependencies (MySQL, object storage) are built or sourced separately.

## Architectural Analysis

Data Science Pipelines follows a microservices architecture centered on a Go API server that exposes both gRPC and REST APIs through a grpc-gateway pattern. The API server is the control plane: it compiles pipeline specs into Argo Workflow objects, manages CRUD operations on pipelines, experiments, runs, and recurring runs, and serves admission webhooks for the PipelineVersion CRD.

The execution model uses a driver/launcher split: the **driver** runs as an init container that resolves input parameters, computes pod spec patches, and prepares the execution environment, while the **launcher** runs alongside user code to handle artifact download/upload and executor invocation. This separation keeps the user container image clean and allows the platform to inject execution logic without requiring users to modify their containers.

A notable architectural pattern is the dual storage mode: pipelines can be stored either in MySQL (the traditional "database" mode) or as native Kubernetes CRDs ("kubernetes" mode, using Pipeline and PipelineVersion custom resources). The kubernetes-native mode is the path RHOAI favors, and it comes with validating and mutating webhooks on PipelineVersion resources to enforce schema validation at admission time.

Authentication is delegated to the Kubernetes API server via TokenReview and SubjectAccessReview — the API server extracts bearer tokens from incoming requests and validates them against the cluster's authentication/authorization infrastructure. In multi-user mode, namespace-based tenant isolation is enforced through the user's RBAC permissions. In standalone mode, no authentication is applied.

The TLS posture is configurable: the API server can run with or without TLS on its HTTP proxy, and the webhook server requires TLS certificates (typically provisioned by cert-manager). The `GetTLSConfig` utility loads system CA certificates plus optional custom CAs but does not explicitly set a MinVersion — relying on Go's default of TLS 1.2. The MLflow plugin has configurable InsecureSkipVerify for development scenarios.

All five Konflux-built Go binaries use `GOFIPS140=v1.0.0` with the `-tags no_openssl` build flag, indicating they use Go's built-in FIPS 140-3 module rather than linking against OpenSSL. The api-server is built with `CGO_ENABLED=1` (required for the SQLite driver), while the other four binaries use `CGO_ENABLED=0` for static linking. All runtime images use the post-quantum cryptography variant `ubi9/ubi-minimal-pqc`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | TokenReview + SubjectAccessReview for every API call in multi-user mode | Kubernetes (kube-apiserver) | Standalone mode has no auth; all users share everything |
| Data storage | Shared MySQL database with namespace-scoped queries; shared S3 bucket with namespace-prefixed keys | Application (query filters) | Application-enforced — a bug in namespace filtering could leak cross-tenant data |
| Network traffic | Istio AuthorizationPolicy for MySQL; optional NetworkPolicy for third-party services | Istio / Kubernetes | No per-tenant NetworkPolicies between pipeline namespaces by default |
| Compute & resources | Pipeline tasks run in user namespaces with user-defined resource requests | Kubernetes (namespace ResourceQuotas if configured) | No built-in ResourceQuota enforcement — depends on platform-level configuration |
| Configuration & secrets | Per-namespace Secrets for DB and S3 credentials (provisioned by DSPO per instance) | Kubernetes | Shared service credentials across tenants within a single DSP instance |
| API scoping | Namespace-scoped watches and queries; SubjectAccessReview before returning results | Kubernetes + Application | pipeline-runner Role uses wildcard verbs on pods, deployments, kubeflow.org resources |
