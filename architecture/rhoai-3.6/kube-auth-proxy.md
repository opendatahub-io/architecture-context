## Purpose

**Short**: FIPS-compliant authentication reverse proxy for ODH/RHOAI that intercepts requests and authenticates users via OIDC, OpenShift OAuth, or Kubernetes service account tokens before forwarding to upstream applications.

**Detailed**: kube-auth-proxy is a focused, FIPS-compliant authentication proxy derived from oauth2-proxy, specifically designed for OpenShift Data Hub (ODH) and Red Hat OpenShift AI (RHOAI) environments. It acts as a reverse proxy that sits in front of applications, intercepting all incoming requests and enforcing authentication before forwarding to upstream services. The proxy supports three authentication methods: external OIDC providers, OpenShift's built-in OAuth service, and Kubernetes service account tokens validated via the TokenReview API. All other authentication providers from the original oauth2-proxy have been intentionally removed to reduce attack surface and maintain focus.

The proxy is designed as a drop-in replacement for existing oauth-proxy sidecars in ODH/RHOAI deployments, maintaining argument and header compatibility. It supports Envoy ext_authz integration for use with Istio-based ingress architectures, session storage in Redis/Valkey for multi-replica deployments, and includes RHOAI-specific integrations such as MLflow client-aware error handling. The component operates purely as an authentication (authn) proxy — it does not include RBAC or SubjectAccessReview (SAR) authorization capabilities.

## Architectural Analysis

kube-auth-proxy implements a middleware-chain architecture centered around Go's `net/http` handler composition using the `alice` library. The processing pipeline consists of three distinct chains: a pre-auth chain (request logging, health checks, metrics, HTTPS redirect), a session chain (K8s token validation → JWT/OAuth bearer token validation → basic auth → stored session loading), and a headers chain (request/response header injection). This layered approach allows multiple authentication methods to coexist — the K8s TokenReview validator runs first, and if it fails, the request cascades to the next authentication method rather than being rejected.

The OpenShift provider implements on-demand OAuth endpoint discovery via the `.well-known/oauth-authorization-server` endpoint, with thread-safe caching guarded by a mutex. This allows the proxy to auto-configure when running inside an OpenShift cluster without explicit endpoint URLs. The provider also manages OAuthAccessToken lifecycle, deleting tokens on logout to match OCP console behavior.

A notable design choice is the `authdeny` handler framework, currently used to return MLflow SDK-specific JSON error responses instead of generic HTML error pages. This is implemented via a handler chain that inspects User-Agent headers and produces structured error responses with actionable remediation messages.

The TLS server implementation defaults to TLS 1.2 minimum with configurable cipher suites and curve preferences. Both the application server and a separate metrics server can independently bind to HTTP and/or HTTPS addresses. The Redis session store supports optional TLS with configurable CA certificates for the Redis connection itself.
