## Purpose

**Short**: Python SDK that simplifies the lifecycle management of Ray clusters, RayJobs, and Kueue integration on Kubernetes and OpenShift.

**Detailed**: CodeFlare SDK is a client-side Python library that provides a high-level, user-friendly interface for creating, configuring, and managing distributed computing resources on Kubernetes. It acts as the primary developer interface for the CodeFlare stack within Red Hat OpenShift AI, abstracting away the complexity of Kubernetes custom resources (RayCluster, RayJob), Kueue-based job queuing, and cluster authentication.

The SDK follows a single-entrypoint design centered on the `Codeflare` class, which authenticates to Kubernetes via the `kube-authkit` library and owns a Kubernetes API client. All objects created through a `Codeflare` instance — clusters and jobs — are bound to that specific client, enabling safe concurrent use of multiple instances targeting different clusters. The library constructs RayCluster and RayJob custom resource manifests from typed `ClusterConfiguration` dataclasses, applies them via server-side apply, and handles TLS certificate generation for mTLS connections to Ray head nodes.

The SDK is not deployed as a service — it runs in user workbenches (Jupyter notebooks), CI pipelines, or local development environments. It consumes the Kubernetes API, KubeRay operator CRDs, Kueue CRDs, OpenShift Routes, and Gateway API resources, but does not serve any endpoints itself. The only container image produced by this repository is a test runner image used for E2E testing.

## Architectural Analysis

CodeFlare SDK's architecture is organized around three principal concerns: authentication, cluster lifecycle, and job management, layered behind a facade pattern that enforces client isolation.

The `Codeflare` facade class owns a Kubernetes API client obtained through `kube-authkit`, which supports auto-detection, OIDC, OpenShift OAuth, and kubeconfig-based authentication. This client is propagated to all downstream operations through a `ContextVar`-based binding mechanism (`_active_api_client`), ensuring that concurrent `Codeflare` instances do not interfere with each other. Every method that touches the Kubernetes API is decorated with `@_bound_to_api_client`, which sets the context variable for the duration of the call. This pattern replaces a previous global-client design and is critical to multi-tenant workbench scenarios where a single notebook process may connect to multiple clusters.

The cluster layer (`ray/cluster/`) constructs RayCluster custom resource manifests from `ClusterConfiguration` dataclasses that support multi-worker-group heterogeneous clusters (multiple `WorkerGroup` specs with different resource profiles). The `build_ray_cluster` function translates configuration into Kubernetes manifests, while Kueue integration is handled by annotating resources with `kueue.x-k8s.io/queue-name` labels when a LocalQueue is configured. Autoscaling support is gated on the Kueue operator version — RHOAI-managed Kueue blocks autoscaling entirely, while standalone RHBOK >= 1.4 allows elastic Ray workloads.

Dashboard URL resolution reveals the SDK's multi-generation platform awareness: it first tries Gateway API HTTPRoutes (RHOAI v3.0+), including a GatewayConfig CR lookup in the `services.platform.opendatahub.io` API group, then falls back to OpenShift Routes, and finally to Kubernetes Ingresses for non-OpenShift environments (e.g., KinD). This layered resolution means the same SDK binary works across ODH, RHOAI, and vanilla Kubernetes clusters.

TLS certificate management is the SDK's most security-sensitive area. The `generate_cert` module creates self-signed CA certificates and TLS client certificates using RSA-3072 keys with SHA-256 signatures, RFC 5280-compliant extensions (BasicConstraints, KeyUsage, ExtendedKeyUsage with both serverAuth and clientAuth for mTLS), and proper SAN entries including the Ray head service's cluster DNS name. Certificates are stored with 0600 permissions in a user-private directory, and the module includes lifecycle management functions (refresh, cleanup, expiration scanning).

The vendored KubeRay Python client (`src/codeflare_sdk/vendored/`) is a notable architectural constraint: only the `ray/rayjobs/` layer may import from it (enforced by import-linter in CI), and it must not be modified. This boundary prevents tight coupling to the upstream KubeRay client API and centralizes its usage.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user Kubernetes credentials via kube-authkit; each Codeflare instance owns its client | Kubernetes RBAC | SDK forwards user credentials; authorization depends on cluster-side RBAC being correctly configured |
| Data storage | Per-namespace Kubernetes resources (RayCluster, RayJob CRs) | Kubernetes | No cross-namespace data sharing within the SDK |
| Network traffic | Ray cluster endpoints scoped to namespace; TLS certificates per cluster-namespace pair | Kubernetes / Ray mTLS | TLS certificates stored in user-local filesystem — multi-user workbench environments could expose certs if filesystem permissions are relaxed |
| Compute & resources | Delegated to Kueue (LocalQueue per namespace) and Kubernetes ResourceQuota | Kubernetes / Kueue | SDK does not enforce quotas directly |
| Configuration & secrets | Per-Codeflare-instance client binding via ContextVar (`_active_api_client`) | Application (Python ContextVar) | Legacy code paths without `@_bound_to_api_client` could leak to wrong client |
| API scoping | Namespace-scoped Kubernetes API calls for cluster/job operations | Kubernetes | Kueue operator version check (`list_cluster_custom_object`) requires cluster-wide read |
