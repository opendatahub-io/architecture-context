## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Ray clusters, jobs, and services through custom resources on OpenShift.

**Detailed**: KubeRay is a Kubernetes operator built on the controller-runtime framework that provides declarative management of Ray distributed computing workloads. It defines four core custom resources — RayCluster, RayJob, RayService, and RayCronJob — that allow users to deploy and manage Ray applications on Kubernetes without directly managing the underlying infrastructure.

The operator reconciles each custom resource type through dedicated controllers: the RayCluster controller provisions head and worker pods with appropriate networking and RBAC; the RayJob controller creates transient RayCluster instances, submits jobs, and cleans up on completion; the RayService controller manages zero-downtime upgrades of Ray Serve applications by orchestrating blue/green RayCluster transitions; and the RayCronJob controller (alpha, feature-gated) schedules recurring RayJob executions.

The RHOAI distribution includes significant OpenShift-specific hardening: an AuthenticationController injects kube-rbac-proxy sidecars and manages Gateway API HTTPRoutes for centralized authentication; a NetworkPolicyController creates per-cluster NetworkPolicies when the `odh.ray.io/secure-trusted-network` annotation is present; an mTLS controller provisions cert-manager Certificates for intra-cluster TLS between Ray head and workers; and a mutating webhook enforces Gateway-only access by disabling direct Route/Ingress creation. TLS configuration follows the cluster-wide OpenShift TLS security profile via `apiservers.config.openshift.io`.

## Architectural Analysis

KubeRay's architecture reflects a layered approach where upstream Ray lifecycle management is augmented with OpenShift-specific security controllers that operate independently. The core reconcilers (RayCluster, RayJob, RayService, RayCronJob) follow standard controller-runtime patterns with owned-resource watches, finalizers for cleanup, and status condition reporting. The RHOAI distribution adds three independent controllers — AuthenticationController, NetworkPolicyController, and RayClusterMTLSController — that each watch RayCluster resources and manage their own resource domain without coupling to the core reconcilers. This separation of concerns enables the security posture to be layered on without modifying upstream reconciliation logic.

The authentication model is particularly notable: the mutating webhook enforces that all RayClusters on OpenShift have ingress disabled and the secure trusted network annotation set, ensuring that external access is only possible through Gateway API HTTPRoutes with kube-rbac-proxy sidecar authentication. The AuthenticationController creates ServiceAccounts, RoleBindings, ConfigMaps for OAuth proxy configuration, and cross-namespace HTTPRoutes that reference the platform Gateway. This design centralizes authentication at the platform ingress layer rather than requiring per-application auth configuration.

TLS configuration demonstrates cluster-aware hardening: at startup, the operator reads the OpenShift APIServer TLS security profile (`apiservers.config.openshift.io/cluster`) and configures both the metrics server and webhook server to match. A watcher controller monitors the profile for changes and triggers a graceful restart if the profile is updated. When the profile is unavailable (non-OpenShift clusters or transient API errors), the operator defaults to an Intermediate profile with TLS 1.2 minimum and FIPS-compatible cipher suites.

The operator manages wide-ranging Kubernetes resources across many API groups: pods, services, secrets, service accounts, configmaps, jobs, ingresses, network policies, OpenShift routes, Gateway API resources (Gateways, HTTPRoutes, ReferenceGrants), and cert-manager resources (Certificates, Issuers). The RBAC footprint is correspondingly broad, with the main `kuberay-operator` ClusterRole granting access to 15+ API groups. Aggregate ClusterRoles (`kuberay-edit-role`, `kuberay-view-role`) provide user-facing RBAC for Ray resources that integrate with Kubernetes' built-in admin/edit/view aggregation.

The batch scheduler integration supports pluggable gang schedulers (Volcano, YuniKorn, Kai, scheduler-plugins) through an interface pattern, enabling resource-aware scheduling of Ray clusters that require all workers to be co-scheduled. Feature gates control experimental functionality, with RayCronJob and AsyncJobInfoQuery currently gated as alpha while RayClusterStatusConditions, RayJobDeletionPolicy, and RayMultiHostIndexing have graduated to beta with defaults enabled.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregate ClusterRoles (kuberay-edit-role, kuberay-view-role) mapped to admin/edit/view; kube-rbac-proxy sidecar for dashboard access | Kubernetes RBAC + kube-rbac-proxy | Operator runs with cluster-wide permissions; user isolation depends on Kubernetes RBAC for ray.io resources |

| Network traffic | NetworkPolicy per RayCluster (annotation-gated), Gateway API HTTPRoutes with per-cluster authentication | NetworkPolicyController + AuthenticationController | NetworkPolicy requires explicit annotation (`odh.ray.io/secure-trusted-network`); without it, Ray cluster pods have default-allow networking |
| Compute & resources | Resource limits/requests on operator pod; user-defined resource specs on RayCluster pods | Kubernetes scheduler + user-specified spec | No operator-enforced ResourceQuotas; tenants share cluster compute unless platform-level quotas are applied |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; mTLS secrets scoped to RayCluster namespace | Kubernetes namespace isolation | OAuth proxy ConfigMaps are per-namespace; CA secrets are per-cluster |
| API scoping | Controller watches can be scoped to specific namespaces via --watch-namespace flag; controller-runtime cache filters | Kubernetes API + controller-runtime | Default is cluster-wide watch; namespace scoping requires explicit configuration |
