## Purpose

**Short**: Intelligent LLM inference router that delivers KV-cache-aware request placement, priority scheduling, and disaggregated inference coordination via integration with Envoy proxies through the ext-proc protocol.

**Detailed**: The llm-d Router is the intelligent entry point for inference traffic in the llm-d ecosystem. It consists of three deployable components: the Endpoint Picker (EPP), the Coordinator, and the Disaggregation Sidecar. The EPP serves as the routing brain, integrating with production-grade proxies such as Envoy via the gRPC External Processing protocol to inject real-time signals into the data plane. It evaluates incoming requests against the current state of an InferencePool, considering factors like KV-cache locality, current load, LoRA adapter availability, and request priority to make optimal endpoint placement decisions. The EPP supports both standalone deployment (with a self-managed Envoy proxy) and Gateway Mode (as a backend for the Kubernetes Gateway API).

The Coordinator orchestrates complex multi-stage inference lifecycles for disaggregated serving, including Prefill/Decode (P/D) and Encode/Prefill/Decode (E/P/D) pipelines. It manages media URL replacement, tokenization via a rendering service, and KV-cache transfer coordination between specialized encode, prefill, and decode workers. The Disaggregation Sidecar runs alongside model servers (typically as a sidecar to decode workers) and proxies inference requests through the disaggregated pipeline, coordinating prefill-to-decode KV-cache transfers and supporting multiple KV connector protocols (NIXL RDMA, shared storage, SGLang).

The repository also defines three CRDs under the `llm-d.ai` API group: EndpointPickerConfig for plugin-driven EPP configuration, InferenceObjective for priority scheduling and multi-pool tier definitions, and InferenceModelRewrite for model name rewriting to enable A/B testing and canary rollouts.

## Architectural Analysis

The llm-d-router follows a plugin-based architecture for its core routing intelligence. The EPP's scheduling decisions are driven by an EndpointPickerConfig CRD that declares plugins (filters and scorers), scheduling profiles, data layer configuration, and flow control settings. This design separates the routing framework from the specific scoring logic, allowing new scheduling strategies to be added without modifying the core request processing path.

The three binaries share a common Go module but serve distinct roles in the inference serving topology. The EPP is the data-plane integration point, receiving per-request callbacks from Envoy's ext-proc filter and returning endpoint selection decisions. The Coordinator sits on the control path of disaggregated inference, orchestrating multi-stage pipelines where a single user request fans out to encode, prefill, and decode workers in sequence. The Sidecar is a per-pod component that handles the last-mile routing at the model server, including DNS-based service discovery and reverse proxy to prefill and decode endpoints.

TLS is uniformly supported across all three components. Each binary accepts certificate directory paths and supports configurable minimum TLS versions (1.2 or 1.3) and cipher suites. The EPP exposes separate TLS configurations for its gRPC serving endpoint and its Prometheus metrics endpoint, with optional mTLS for metrics scraping. The Coordinator loads TLS configuration from a YAML file with CLI flag overrides. Self-signed certificates are generated as a fallback when no certificate path is configured.

The asynchronous request broker in the Coordinator integrates with Redis-backed llm-d-async queues, enabling enqueue/wait/passthrough modes for async inference serving with per-tenant quota classification and reservation.
