## Purpose

**Short**: Kubernetes operator that declaratively provisions a complete observability stack (metrics, traces, logs, dashboards, alerting) for the RHOAI platform via a singleton cluster-scoped Monitoring custom resource.

**Detailed**: odh-observability is a controller-runtime operator that watches a singleton `Monitoring` CR (`services.platform.opendatahub.io/v1alpha1`) and dynamically provisions observability subsystems based on which prerequisite operators (Cluster Observability Operator, Tempo Operator, OpenTelemetry Operator, Perses Operator, cert-manager, Loki Operator) are installed on the cluster. It deploys MonitoringStack instances for Prometheus metrics, Tempo for distributed tracing, OpenTelemetry Collectors for telemetry pipelines, Perses for dashboards, LokiStack for usage logs, and PrometheusRules for alerting.

The operator uses a template-driven architecture: ~50 embedded Go templates in `internal/controller/resources/` are rendered against cluster-derived data and applied via Server-Side Apply through the `odh-platform-utilities` library. Because the Monitoring CR is cluster-scoped but manages namespace-scoped resources, the operator uses label-based ownership (`platform.opendatahub.io/part-of=monitoring`) instead of standard OwnerReferences, with a garbage collection loop that deletes stale resources not in the desired set. The operator also runs an optional mutating webhook that injects the `monitoring.opendatahub.io/scrape=true` label onto ServiceMonitor and PodMonitor resources in opt-in namespaces.

## Architectural Analysis

The odh-observability operator follows a hub-and-spoke pattern where a single controller manages the lifecycle of multiple observability backends. Its reconciliation loop consists of six stages: precondition checks (verifying OLM OperatorConditions), action functions (per-subsystem CRD existence checks), template rendering (Go text/template against cluster-derived data), Server-Side Apply (via odh-platform-utilities with caching), garbage collection (label-based stale-resource cleanup), and post-deploy syncs (TLS CA distribution and status URL discovery).

A notable design constraint is the cluster-to-namespace scope mismatch. The Monitoring CR is cluster-scoped (enforced as a singleton named `default-monitoring`), but it manages namespace-scoped resources. Standard Kubernetes OwnerReferences cannot cross scope boundaries, so the operator implements label-based ownership with explicit garbage collection. This introduces a risk surface: if the label selector drifts or a managed resource loses its label, the GC loop will not clean it up.

The metrics proxy architecture is layered. Three kube-rbac-proxy deployments (cluster-proxy, namespace-proxy, thanos-querier-proxy) sit in front of Prometheus and Thanos, enforcing RBAC-based access control via `cluster-monitoring-view` and `system:auth-delegator` roles. The namespace-proxy additionally uses prom-label-proxy to enforce per-namespace query scoping, enabling multi-tenant metrics access. All proxy services terminate TLS via OpenShift service-CA generated certificates.

The TLS configuration is dynamic: the operator watches the cluster `APIServer` resource and propagates TLS profile changes (minimum version, cipher suites) to all proxy deployments via template rendering. The `pkg/tls` package translates OpenShift TLS profiles to Go crypto/tls-compatible strings, with a floor of TLS 1.2 for unsupported legacy profiles.

The OpenTelemetry Collector's internal Prometheus telemetry is re-exported through a TLS-enabled pipeline on port 8890 because the Go SDK Prometheus exporter does not natively support TLS. NetworkPolicy `data-science-collector-monitoring-ingress` gates all collector ingress, permitting Prometheus scraping on 8889/8890 and OTLP on 4317/4318 restricted to the monitoring namespace.

Korrel8r is deployed as a correlation engine with broad read-only cluster access (pods, logs, deployments, events, Loki, Tempo traces) to enable cross-signal navigation between metrics, logs, and traces.
