## Purpose

**Short**: Lightweight REST API service for orchestrating LLM evaluations across multiple backends, with companion sidecar, init container, and MCP server components.

**Detailed**: eval-hub is the evaluation orchestration service for Red Hat OpenShift AI. It provides a REST API that routes evaluation requests to frameworks such as lm-evaluation-harness, RAGAS, Garak, and GuideLLM, tracks experiments via MLflow, and runs natively on OpenShift. The repository produces four deployable binaries from a single Go codebase: the primary API server (`eval-hub`), a reverse-proxy sidecar (`eval-runtime-sidecar`) injected into evaluation Job pods to proxy model, MLflow, OCI, and API callback traffic, an init container (`eval-runtime-init`) that downloads test data from S3, Git, or HuggingFace, and an MCP server (`evalhub-mcp`) that exposes eval-hub functionality to AI agents via the Model Context Protocol.

In cluster mode, API requests pass through kube-rbac-proxy, which handles authentication and authorization, injecting `X-User` and `X-Tenant` identity headers. The API creates Kubernetes Jobs for each evaluation; each Job pod runs a provider adapter container alongside the sidecar. The service supports PostgreSQL (production) and SQLite (development) for persistence, with full OpenTelemetry instrumentation (traces, metrics, logs) and a dedicated Prometheus metrics endpoint.

## Architectural Analysis

eval-hub follows a hub-and-spoke architecture where the central API server orchestrates evaluation work by creating Kubernetes Jobs. Each Job pod is a self-contained evaluation environment with an init container (test data download), a provider adapter (evaluation framework), and a sidecar (reverse proxy for all external traffic). This design isolates evaluation workloads from each other and from the control plane.

The security model is layered: kube-rbac-proxy handles authn/authz at the ingress boundary, the API enforces tenant and user scoping in the storage layer, and per-Job NetworkPolicies restrict network access for evaluation pods. The API server itself binds to `127.0.0.1` in cluster mode, only accessible through the proxy. A notable design choice is the FIPS-awareness at the application level — the server checks `/proc/sys/crypto/fips_enabled` at startup and refuses to start with `InsecureSkipVerify` in FIPS mode.

The MCP server is architecturally separate from the API: it runs as its own process and communicates with eval-hub through the same REST API (via kube-rbac-proxy in cluster mode), supporting stdio, Streamable HTTP, and legacy HTTP+SSE transports. The sidecar proxies are an interesting pattern — rather than giving evaluation Jobs direct credentials, the sidecar handles authentication to MLflow, OCI registries, and model endpoints via SA token injection and credential caching.

The Python packages (`python-server`, `python-mcp`) are thin shim distributions that wrap the compiled Go binaries for PyPI distribution; they do not contain Python application logic.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy (Bearer token authn + RBAC authz) → X-User/X-Tenant headers | kube-rbac-proxy (Kubernetes) | eval-hub trusts proxy headers without in-process SAR/TokenReview; direct access to API port bypasses auth in cluster |
| Data storage | Per-tenant scoping via tenant column in SQL storage | Application (sqlStorage carries tenant field) | Shared database; isolation relies on application-level query filtering, not database-level separation |
| Network traffic | Per-Job NetworkPolicy denying peer-Pod ingress | Kubernetes NetworkPolicy | Egress is annotated as "unmanaged-by-this-policy"; evaluation pods can reach external endpoints |
| Compute & resources | Evaluation Jobs support HardwareProfile and Kueue LocalQueue integration | Kubernetes (Kueue, ResourceQuota) | Resource limits depend on cluster-level Kueue and quota configuration, not enforced by eval-hub |
| Configuration & secrets | Per-evaluation secrets mounted from user-specified namespace | Kubernetes Secret mounts | Secrets are per-execution, not per-tenant; shared service config is cluster-wide |
| API scoping | Tenant-filtered storage queries; X-Tenant required on all evaluation API routes in cluster mode | Application | Local mode bypasses tenant enforcement entirely |
