## Purpose

**Short**: A lightweight Rust HTTP service that detects PII and custom patterns in text using regular expressions, designed as a detector backend for the FMS Guardrails Orchestrator.

**Detailed**: The guardrails-regex-detector is a focused, single-purpose HTTP service built in Rust with the Axum web framework. It accepts text content via a REST API and scans it against both built-in PII detection patterns (email addresses, Social Security numbers, credit card numbers) and arbitrary user-supplied regular expressions. Each match is returned with its position, matched text, detection type, and a confidence score.

The service is designed to be deployed as an internal backend detector within the TrustyAI guardrails ecosystem. It integrates with the FMS Guardrails Orchestrator, which routes text content through one or more detector services to identify sensitive or policy-violating content in LLM inputs and outputs. The regex detector handles the pattern-matching class of detections, complementing other detectors that may use ML-based approaches.

The codebase is intentionally minimal — two Rust source files totaling under 200 lines of application code — reflecting its role as a stateless, high-performance text scanner. It has no database, no persistent state, no CRDs, no RBAC requirements, and no outbound network dependencies beyond accepting HTTP requests.

## Architectural Analysis

The guardrails-regex-detector exemplifies a microservice sidecar pattern: a stateless, single-responsibility service that performs one task (regex matching) with high throughput and low latency. The architecture is deliberately flat — a single Axum router dispatches to one detection handler that iterates over content strings and regex patterns.

The detection system has a two-tier design. Three built-in detectors (email, SSN, credit card) are registered by keyword and use hardcoded regex patterns. Arbitrary custom regex patterns are also accepted; any regex string that doesn't match a built-in keyword is compiled and applied directly. This makes the service extensible without code changes — the orchestrator can pass new patterns at request time.

The service uses plain HTTP (no TLS termination in-process). The Dockerfile installs `compat-openssl11` as a runtime system dependency, but the application binary itself has no OpenSSL, rustls, or any TLS library in its dependency tree. TLS termination is expected to be handled by the platform (e.g., Istio sidecar proxy or OpenShift Route).

A notable risk is that the service compiles user-supplied regex patterns on every request without caching or complexity limits. Pathological regex patterns (e.g., catastrophic backtracking) could cause denial of service. The Rust `regex` crate mitigates this somewhat through its default size and nesting limits, but no explicit timeout or resource bound is applied at the application level.
