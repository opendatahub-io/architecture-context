## Purpose

**Short**: Unified Python SDK for managing ML workloads across the Kubeflow ecosystem, with RHOAI-specific trainer extensions for HuggingFace Transformers, speculative decoding, and Training Hub integration.

**Detailed**: The Kubeflow SDK (`kubeflow` PyPI package, version 0.4.1+rhai0) is a client-side Python library that provides unified Pythonic APIs for interacting with multiple Kubeflow projects — Trainer, Optimizer (Katib), Spark, Hub (Model Registry), and Pipelines — without requiring users to learn Kubernetes directly. It abstracts Kubernetes complexity through pluggable backends (Kubernetes, local process, container) and a consistent client interface.

The RHOAI-specific fork adds the `kubeflow.trainer.rhai` subpackage, which provides three specialized trainer types: `TransformersTrainer` for HuggingFace Transformers/TRL with auto-instrumented progression tracking and checkpoint management, `TrainingHubTrainer` for RHAI Training Hub algorithm integration (SFT, OSFT, LoRA-SFT, LoRA-GRPO), and `SpeculativeDecodingTrainer` for training draft models (Eagle3, DFlash, MTP, PEAGLE) used in speculative decoding inference acceleration. Each trainer includes instrumentation code that is serialized via `inspect.getsource()` and injected into training pods at runtime, providing HTTP-based metrics servers for real-time progression monitoring without runtime SDK dependencies.

The SDK does not itself deploy as a service — it is installed via `pip install kubeflow` and runs in user environments or CI pipelines, communicating with Kubernetes API servers and Kubeflow control-plane components to create and manage TrainJob, OptimizationJob, and SparkConnect custom resources.

## Architectural Analysis

The Kubeflow SDK's architecture is shaped by two design principles: unified client abstraction and code injection for in-pod instrumentation.

The unified client layer (`TrainerClient`, `OptimizerClient`, `SparkClient`, `PipelinesClient`, `ModelRegistryClient`) follows a backend-strategy pattern. Each client delegates to a runtime backend that handles the actual resource lifecycle. The `TrainerClient`, for example, supports `KubernetesBackend` (creates TrainJob CRs via the Kubernetes API), `ContainerBackend` (runs training locally via Docker/Podman), and `LocalProcessBackend` (subprocess execution for quick prototyping). This multi-backend approach enables the same training code to run from laptop to production cluster unchanged.

The RHAI instrumentation subsystem (`kubeflow.trainer.rhai.instrumentation`) uses a distinctive code-generation pattern: instrumentation functions are defined as normal Python in the SDK for syntax highlighting and testability, but at runtime their source is extracted via `inspect.getsource()` and embedded into the training pod's entrypoint script. This injects HTTP metrics servers (default port 28080) that expose training progression, checkpoint status, and evaluation metrics. The TrainJob controller polls these endpoints using OpenDataHub-specific annotations (`trainer.opendatahub.io/progression-tracking`, `trainer.opendatahub.io/metrics-port`). The HTTP servers bind to `0.0.0.0` without authentication — security relies on Kubernetes network isolation at the pod/namespace level rather than application-layer auth.

The checkpoint system supports two storage backends: PVC-based (direct mount to `/mnt/kubeflow-checkpoints`) and S3-based (ephemeral staging volume with async upload via `fsspec`/`s3fs`). The SpeculativeDecodingTrainer adds a vLLM sidecar pattern for DATA_ONLY mode, running a vLLM inference server on port 8234 alongside the training container to extract hidden states from the verifier model.

A notable risk is the `trust_remote_code=False` hardcoding in the speculator's `AutoConfig.from_pretrained` call — this is correct from a security standpoint but may limit model compatibility for custom architectures that require trusted remote code.
