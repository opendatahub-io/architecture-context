## Purpose

**Short**: Argo Workflows is a container-native workflow engine that orchestrates parallel jobs on Kubernetes using CRD-based workflow definitions, serving as the execution backend for Data Science Pipelines in RHOAI.

**Detailed**: Argo Workflows provides the core workflow orchestration layer for Red Hat OpenShift AI's Data Science Pipelines feature. It defines workflows as Kubernetes Custom Resources where each step runs as a container, supporting both sequential task chains and DAG-based dependency graphs. The system is well-suited for compute-intensive machine learning and data processing workloads.

The component consists of two primary runtime binaries: the **workflow-controller**, which watches for Workflow CRs and manages their lifecycle by creating and monitoring pods, and **argoexec**, which runs as a sidecar/init container within workflow pods to handle artifact collection, output capture, and container lifecycle management. An **argo-server** (API server + UI) exists in the upstream codebase but is not built or deployed in the RHOAI distribution — DSP provides its own API layer instead.

In the RHOAI context, this fork (downstream of `argoproj/argo-workflows` via `opendatahub-io/argo-workflows`) is purpose-built for Data Science Pipelines. The Konflux Dockerfiles produce two images — workflow-controller and argoexec — using Go 1.26 with the native FIPS 140-3 crypto module (`GOFIPS140=v1.0.0`) and UBI 9 minimal-pqc (post-quantum cryptography) base images. The builds are statically linked with `CGO_ENABLED=0` and the `no_openssl` build tag, relying entirely on Go's built-in FIPS-validated cryptographic module rather than system OpenSSL.

## Architectural Analysis

Argo Workflows follows a standard Kubernetes controller pattern with a clear separation between the control plane (workflow-controller) and the execution plane (argoexec pods). The workflow-controller uses leader election via Kubernetes Lease objects to ensure single-active-controller semantics, making it safe to run with multiple replicas for high availability. It exposes Prometheus metrics on port 9090 and a health check on port 6060.

The authentication architecture is notable for its flexibility: the argo-server supports three authentication modes — Client (pass-through Kubernetes bearer tokens), Server (use the server's own service account), and SSO (OpenID Connect via an external identity provider). The gatekeeper interceptor applies authentication uniformly across both gRPC and HTTP/REST APIs through grpc-gateway. However, in the RHOAI/DSP deployment, the argo-server is not used; workflow management is handled through the DSP API server.

The FIPS posture is distinctive for this RHOAI 3.6 build: rather than the traditional `GOEXPERIMENT=strictfipsruntime` with CGO-linked OpenSSL, the builds use Go 1.26's native `GOFIPS140=v1.0.0` module with static linking. This represents a transition to Go's own NIST-certified FIPS 140-3 module, eliminating the OpenSSL dependency. The `godebug fips140=on` directive in go.mod enables FIPS mode at runtime. The UBI 9 minimal-pqc base images provide post-quantum cryptography support at the OS layer.

A security consideration is the self-signed TLS certificate generation in `util/tls/tls.go`, where `InsecureSkipVerify: true` is set on the self-generated TLS config used for the argo-server's internal gRPC-gateway loopback connection (localhost only). This is an intentional design choice for the self-signed cert scenario and does not affect external connections. The `InsecureSkipVerify` option is also exposed as a user-configurable setting for CLI client connections and SSO provider connections, but is not enabled by default.
