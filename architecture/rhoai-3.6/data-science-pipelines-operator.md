## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines (Kubeflow Pipelines v2) stacks on OpenShift, deploying namespace-scoped pipeline infrastructure via the DataSciencePipelinesApplication custom resource.

**Detailed**: The Data Science Pipelines Operator (DSPO) is a controller-runtime-based operator that reconciles `DataSciencePipelinesApplication` (DSPA) custom resources on OpenShift. Each DSPA instance triggers the deployment of a complete Kubeflow Pipelines v2 stack within a single namespace, comprising: an API server, persistence agent, scheduled workflow controller, Argo workflow controller, ML Metadata (MLMD) server with Envoy proxy, and optionally MariaDB and MinIO for metadata storage and artifact persistence.

The operator uses Go templates rendered through manifestival to produce Kubernetes manifests for each sub-component, applying owner references and version labels to all managed resources. It performs health checks against the configured database and object store before deploying workloads, ensuring backend connectivity. The operator also manages Argo Workflows CRDs and RBAC, integrates with the ODH platform's AIPipelines module controller for coordinated lifecycle management, and enforces OpenShift TLS security profiles across its webhook and metrics servers.

DSPO integrates with multiple platform services including KServe (for inference), MLflow (for experiment tracking), Prometheus (for monitoring), and the OpenShift route system (for external pipeline API access). It supports configurable proxy settings, custom CA bundles, and pod-to-pod TLS between DSPA components.

## Architectural Analysis

DSPO follows a single-reconciler-per-CRD pattern with the `DSPAReconciler` as the primary workhorse. The reconciler's `ExtractParams` phase merges CR spec fields, operator configuration (via viper), secrets, and configmaps into a `DSPAParams` struct that drives all downstream template rendering. This centralized parameter resolution is a strength for consistency but creates a single point of failure — any parameter extraction error blocks the entire reconcile cycle.

The operator exhibits a layered controller architecture: `DSPAReconciler` handles per-namespace DSPA lifecycle, while the `AIPipelinesReconciler` and `AIPipelinesArgoReconciler` manage the platform-level AIPipelines module when enabled via the `ENABLEAIPIPELINESMODULECONTROLLER` feature flag. This dual-path design supports the transition from standalone DSPA management to coordinated platform module ownership under the ODH operator framework.

A notable cache optimization strategy strips managed fields, ConfigMap data, and Secret data from the informer cache, forcing direct API reads for sensitive payloads. This reduces operator memory footprint but introduces additional API server load for every Secret/ConfigMap read. Operator-managed resources are filtered by the `dsp-version` label in the cache, reducing watch scope.

The TLS posture is well-implemented: the operator fetches the OpenShift APIServer TLS profile at startup, falls back to Intermediate when unavailable, and registers a `SecurityProfileWatcher` that triggers a graceful restart on profile changes. The webhook and metrics servers both honor the cluster's TLS policy. Database connections support optional TLS with custom CA bundles, though TLS is not enforced by default — it must be enabled per-DSPA via the `podToPodTLS` field.

The broad RBAC surface of the `manager-role` ClusterRole (39 rules spanning 15+ API groups) reflects the operator's responsibility to create entire pipeline stacks. This is architecturally necessary but represents a significant blast radius if the operator's service account is compromised.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC via aggregate ClusterRoles; namespace-scoped DSPA resources | Kubernetes | Aggregate roles allow any admin/edit user in a namespace to manage DSPAs |
| Data storage | Per-namespace MariaDB and MinIO/S3; each DSPA deploys its own database and object store or references external ones | Kubernetes (PVC per namespace) + Application (DSPA spec) | External database/object store credentials are stored in namespace-scoped Secrets; no cross-namespace isolation enforcement for external stores |
| Network traffic | Per-DSPA NetworkPolicy created by operator | Kubernetes (NetworkPolicy) | NetworkPolicies are template-rendered; specifics depend on config/internal templates |
| Compute & resources | No ResourceQuota or LimitRange enforcement by operator | N/A | Operator does not create resource quotas; tenants share cluster compute unless platform-level quotas exist |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps | Kubernetes | Operator reads secrets via direct API calls (cache bypass); no cross-namespace access |
| API scoping | Namespace-scoped watches for owned resources; dsp-version label filtering | Kubernetes + Application | Operator has cluster-wide RBAC but scopes watches to namespace-specific resources |
