## Purpose

**Short**: Builds containerized Jupyter, Code-Server, and Elyra runtime images for data science workbenches in Red Hat OpenShift AI.

**Detailed**: The notebooks repository is a container image factory that produces the full catalog of interactive workbench and pipeline runtime images shipped with RHOAI. It does not deploy a running service itself — instead it produces container images that the workbenches-operator (via the ODH Notebook Controller) launches as per-user StatefulSet pods on OpenShift.

The repository builds three families of images: **Jupyter workbenches** (JupyterLab-based interactive environments with framework-specific libraries), **Code-Server workbenches** (VS Code in the browser with data science tooling), and **Elyra pipeline runtimes** (headless Python environments for Data Science Pipelines execution). Each family ships CPU, NVIDIA CUDA, and AMD ROCm variants using AIPCC base images for RHOAI downstream builds. All images target Python 3.12 on UBI 9 / RHEL 9.8.

Images are built hermetically via Konflux (Cachi2 prefetch for Python deps, `rpms.lock.yaml` for OS packages) and published to `registry.redhat.io/rhoai/`. OpenShift `ImageStream` manifests in `manifests/rhoai/` provide version-tagged references that the dashboard and operator consume to present notebook image choices to end users.

## Architectural Analysis

The notebooks component is architecturally unusual in the RHOAI platform: it is a **pure build-time artifact** that produces no controllers, operators, or running services of its own. Its entire output is a matrix of container images consumed by downstream platform components (workbenches-operator, Data Science Pipelines).

The key architectural pattern is a **multi-stage Dockerfile per image variant**, where each notebook image is self-contained — no image `FROM`s another notebook image. Instead, each Dockerfile embeds the full build chain from base image through every logical layer (OS packages → Python venv → framework libraries → IDE/notebook server → extensions and configuration). This design avoids image inheritance diamonds but means that changes to shared logical layers (e.g., the "minimal" stage) must be propagated across all leaf Dockerfiles that embed it.

Hermetic build support is comprehensive: every Konflux Dockerfile sources prefetched dependencies from `/cachi2/output/deps/` (pip wheels via `uv pip install --no-index --find-links`) and verifies RPM GPG keys against imported prefetch keys. Lock files exist at both the OS layer (`rpms.lock.yaml` in `prefetch-input/odh/` and `prefetch-input/rhds/`) and the Python layer (`pylock.*.toml` per image variant under `uv.lock.d/`). Build-args configuration files (`build-args/konflux.*.conf`) pin AIPCC base images by SHA256 digest, ensuring reproducible builds.

The manifest delivery model uses OpenShift `ImageStream` resources with kustomize `replacements` from `params.env` — a ConfigMap-driven parameterization pattern that allows the operator to resolve digest-pinned image references at deploy time. Each ImageStream carries multiple version tags (N through N-3) to support the dashboard's version-selection UX and rolling upgrade compatibility.

A notable risk is the large dependency surface: each full-featured workbench image (e.g., Code-Server data science) bundles hundreds of Python packages spanning ML frameworks, cloud SDKs, database connectors, and visualization libraries. This creates a wide CVE exposure surface that the team manages through automated Renovate-driven dependency updates and Quay vulnerability scanning.
