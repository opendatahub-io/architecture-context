## Purpose

**Short**: TrustyAI Explainability is a Java/Quarkus REST service that provides fairness metrics, model explainability algorithms, and data drift detection for ML models served through KServe and ModelMesh on OpenShift AI.

**Detailed**: TrustyAI Explainability is a multi-module Java library and Quarkus-based service that brings Explainable AI (XAI) capabilities to the RHOAI platform. The core library (`explainability-core`) implements fairness metrics such as Statistical Parity Difference (SPD) and Disparate Impact Ratio (DIR), local explainability algorithms (LIME, SHAP, Counterfactual, Time-Series Saliency), global explainability (Aggregated LIME, Partial Dependence Plots), and data drift detectors (KS Test, Fourier MMD, Meanshift).

The `explainability-service` module wraps the core library as a Quarkus REST service that integrates with the model serving infrastructure. It consumes inference payloads from ModelMesh and KServe (via both HTTP and CloudEvents), stores them for later analysis, and computes fairness and drift metrics on a configurable schedule. Computed metrics are published to Prometheus for alerting and dashboard integration. The service supports multiple storage backends: PVC-backed flat files (CSV), MinIO object storage, and MariaDB/MySQL via Hibernate ORM.

The `explainability-connectors` module provides KServe v1/v2 HTTP and gRPC client implementations, enabling the service to invoke model inference endpoints for on-demand explainability computations. The `explainability-arrow` module facilitates data exchange between the Java library and the companion TrustyAI Python library via Apache Arrow.

## Architectural Analysis

TrustyAI follows a layered, multi-module Maven architecture where core algorithmic logic is cleanly separated from the serving infrastructure. The `explainability-core` module is a pure library with no framework dependencies, while `explainability-service` adds the Quarkus runtime, storage backends, and REST API surface. This separation allows the core algorithms to be consumed independently (e.g., by the Python library via Arrow bridging).

The service employs Quarkus profile-based feature flags to differentiate the RHOAI distribution from ODH. In the RHOAI profile, local explainer endpoints (SHAP, LIME, Counterfactual, TSSaliency) and global explainer endpoints are disabled via `@EndpointDisabled` annotations, limiting the RHOAI API surface to fairness metrics and drift detection. This is an intentional scoping decision, likely reflecting GA readiness of different feature categories.

The inference payload pipeline is a key architectural pattern: ModelMesh sends partial inference payloads (inputs and outputs) to `/consumer/kserve/v2`, where a `ModelMeshInferencePayloadReconciler` matches and reconciles partial payloads into complete records. KServe uses a separate path via Knative CloudEvents (`org.kubeflow.serving.inference.request` and `.response`), handled by `CloudEventConsumer` with a `KServeInferencePayloadReconciler`. This dual-path consumer architecture reflects the platform's support for both ModelMesh and KServe serving runtimes.

Storage is pluggable via Quarkus CDI with `@LookupIfProperty` annotations. The default configuration uses PVC-backed CSV storage, but MinIO and Hibernate (MariaDB/MySQL) backends are available. The deployment manifest configures storage parameters via the `trustyai-config` ConfigMap.

A notable risk is the init container pattern in the deployment manifest: it uses `oc apply` to write a `model-serving-config` ConfigMap that embeds the current namespace into a payload processor URL. This creates a runtime dependency on the `oc` CLI binary and requires the service account to have ConfigMap write permissions cluster-wide via the `trustyai-role` ClusterRole.

The service configures TLS with certificate files at `/etc/tls/internal/tls.crt` and `/etc/tls/internal/tls.key` on the HTTPS port (4443), but the primary HTTP port (8080) and the OpenShift Route are configured without TLS termination, indicating that encryption is handled at the Route or mesh layer in production deployments.
