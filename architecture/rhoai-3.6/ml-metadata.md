## Purpose

**Short**: ML Metadata (MLMD) is a gRPC server and client library for recording and retrieving metadata associated with ML workflows, tracking artifacts, executions, contexts, and their lineage relationships.

**Detailed**: ML Metadata provides a persistent metadata store for machine learning pipelines. It implements Google's MLMD specification, offering a typed metadata schema that tracks three core entity types — Artifacts (datasets, models, metrics), Executions (training runs, transforms, evaluations), and Contexts (pipelines, experiments, runs) — along with the relationships between them (Events, Attributions, Associations, and ParentContexts). This lineage graph enables pipeline orchestration systems like Kubeflow Pipelines to record what happened during each step of an ML workflow.

In the RHOAI distribution, the primary deliverable is the `metadata_store_server` — a C++ gRPC server binary compiled with Bazel and shipped in a UBI9-minimal-pqc container image. The server supports MySQL, PostgreSQL, and SQLite as metadata storage backends, with PostgreSQL being the typical production configuration in OpenShift AI. The repository also contains a Python client library (`ml-metadata` PyPI package) that can connect to the server over gRPC or directly to a database via embedded C++ bindings.

## Architectural Analysis

The ml-metadata architecture is split into two distinct operational modes: a standalone gRPC server for production deployment, and an embedded Python library for direct database access. In the RHOAI context, only the gRPC server mode is relevant — it is built as a single statically-linked C++ binary from the Bazel build system and shipped in a minimal container.

The server is architecturally simple: a single-threaded gRPC service implementation (`MetadataStoreServiceImpl`) that serializes all operations through one `MetadataStore` instance. The TODO comment in the source (`b/123039345`) noting the need for a connection pool indicates that concurrent request handling is sequential, which is a potential throughput bottleneck under load. The server delegates all persistence to a pluggable `MetadataSource` backend (MySQL, PostgreSQL, or SQLite), with schema migration support built into the initialization path.

A notable security observation is that the gRPC server provides **no application-level authentication**. It supports optional TLS (via `SSLConfig` in the server configuration protobuf) for transport encryption, including mutual TLS with client certificate verification, but there is no user identity, authorization, or multi-tenant access control. All authentication and authorization must be provided by the deployment infrastructure (e.g., Kubernetes NetworkPolicy, Istio AuthorizationPolicy, or sidecar proxies). This is consistent with its role as an internal data plane service consumed by Kubeflow Pipelines components within the cluster.

The Konflux build uses the `ubi9/ubi-minimal-pqc` base image (post-quantum cryptography variant), which is notable as an early adopter of Red Hat's PQC-ready UBI images. The server runs as non-root user (UID 65534), and multi-architecture builds are produced for amd64, arm64, and ppc64le.

## APIs Exposed

### gRPC Services

| Service | Port | Protocol | Encryption | Auth | Purpose |
|---------|------|----------|------------|------|---------|
| MetadataStoreService | 8080/TCP | gRPC | Optional TLS (SSLConfig) | None (infrastructure-delegated) | Full CRUD for ML metadata: artifacts, executions, contexts, types, events, lineage |

The `MetadataStoreService` exposes approximately 45 RPC methods organized into these categories:

**Type Management**: PutArtifactType, PutExecutionType, PutContextType, PutTypes, GetArtifactType(s), GetExecutionType(s), GetContextType(s), and by-ID/by-external-ID variants.

**Entity CRUD**: PutArtifacts, PutExecutions, PutContexts, PutExecution (atomic execution+artifacts+contexts), PutLineageSubgraph (batch insert). GetArtifacts/Executions/Contexts by ID, type, type+name, URI, external ID, and context.

**Relationship Management**: PutEvents, PutAttributionsAndAssociations, PutParentContexts, GetEventsByExecutionIDs/ArtifactIDs, GetContextsByArtifact/Execution, GetParentContextsByContext, GetChildrenContextsByContext.

**Lineage Queries**: GetLineageSubgraph (graph traversal with filtering, direction, and hop control). GetLineageGraph (deprecated).
