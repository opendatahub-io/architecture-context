## Purpose

**Short**: The central control-plane operator that installs, configures, and lifecycle-manages the full Red Hat OpenShift AI (RHOAI) platform and its constituent AI/ML components on OpenShift clusters.

**Detailed**: rhods-operator (downstream of opendatahub-operator) is the single entry-point for deploying the RHOAI platform. Cluster administrators create two singleton cluster-scoped CRs — `DSCInitialization` for platform-wide settings (monitoring, service mesh, trusted CA bundles) and `DataScienceCluster` for component enablement — and the operator reconciles the desired state across ~16 managed components including Dashboard, KServe, Ray, Kueue, Model Registry, TrustyAI, Workbenches, Data Science Pipelines, and others.

The operator implements a modular controller architecture where each platform component has a dedicated handler (component or module pattern) that renders kustomize manifests from prefetched sources, deploys them, and garbage-collects removed resources. The operator also manages cross-cutting platform services: a Gateway API-based ingress stack with kube-auth-proxy for OIDC authentication, a centralized auth service for RBAC group management, monitoring integration with Prometheus, and certificate lifecycle management. A separate `cloudmanager` binary manages cloud-provider Kubernetes engine CRs (AWS EKS, Azure AKS, CoreWeave) for the RHAII (Red Hat AI Infrastructure) deployment model.

## Architectural Analysis

rhods-operator follows a **reconciler-builder pattern** where each managed component implements either the `componentHandler` interface (for in-tree components like Kueue) or the `ModuleHandler` interface (for externally-operated components like KServe, Ray, Dashboard). The reconciler builder constructs an ordered chain of **actions** — precondition checks, manifest rendering via kustomize, deployment, status updates, and garbage collection — executed sequentially with short-circuit on error. The GC action is always last in the chain to avoid premature resource deletion.

The operator's **ingress architecture** is a critical design surface. In RHOAI 3.x, the gateway controller deploys a full Gateway API stack: a platform Gateway CR, HTTPRoute CRs for per-component routing, a kube-auth-proxy deployment for OIDC authentication (with HPA for scaling), EnvoyFilter CRs for traffic shaping and auth header injection, DestinationRule CRs for TLS enforcement with self-signed certificates, and nginx-based redirect deployments for legacy URL migration from Routes to Gateway API. This dual-path ingress (Gateway API primary, OpenShift Routes for legacy redirects and OAuth callbacks) is intentional and architecturally significant.

The operator reads the cluster's TLS security profile from the OpenShift APIServer configuration (`configv1.APIServer`) and propagates it to all managed components, ensuring consistent TLS policy across the platform. The `pkg/tls/profile.go` module resolves named profiles (Intermediate, Modern, Custom) to concrete cipher suites and minimum TLS versions, with a safety floor that prevents TLS 1.0/1.1 configuration.

Platform detection at startup determines whether the operator runs in ODH or RHOAI mode via build tags (`-tags rhoai`), influencing default component sets, namespace naming, and feature gates. The operator also conditionally creates OpenShift-specific resources (Routes, ConsoleLinks, OAuthClients) using a three-way branch pattern (found / IsNotFound|IsNoMatchError / other error) that makes it resilient on non-OpenShift Kubernetes distributions.

Admission webhooks enforce structural invariants: singleton CRs for DSCInitialization and DataScienceCluster, field validation for hardware profiles and accelerator profiles, version conversion between API versions (v2↔v3 for DSC, v1↔v2 for DSCI), and Prometheus PodMonitor mutation for metrics namespace injection.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Group-based RBAC with admin and allowed groups; per-component editor/viewer ClusterRoles; kube-auth-proxy OIDC for ingress | Kubernetes RBAC + kube-auth-proxy | Group membership is the primary tenant boundary; no per-user isolation within a group |
| Data storage | Per-namespace PVCs and Secrets for user workloads; operator delegates storage to component controllers | Kubernetes namespace isolation | Operator itself does not create per-tenant storage; delegated to components |
| Network traffic | NetworkPolicy created per component (controller watch on NetworkPolicy); AuthorizationPolicy possible via Istio integration | Kubernetes NetworkPolicy | Network isolation policy is component-specific, not centrally enforced by the operator |
| Compute & resources | HardwareProfile CRDs (Namespaced) for workload scheduling; ResourceQuota read access for admin groups | Kubernetes + Application | Operator does not enforce compute quotas directly; provides HardwareProfile abstraction |
| Configuration & secrets | Per-namespace Secrets for component credentials; operator namespace for platform secrets | Kubernetes namespace isolation | Platform secrets (OAuth, TLS) are in the operator namespace |
| API scoping | Component CRs are Cluster-scoped singletons; user-facing resources (HardwareProfile, ServingRuntime) are Namespaced | Kubernetes API scope | Cluster-scoped CRs mean any authorized user can view platform configuration |
