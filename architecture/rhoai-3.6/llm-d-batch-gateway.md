## Purpose

**Short**: OpenAI-compatible batch inference gateway that processes large-scale batch jobs alongside interactive workloads in Kubernetes environments.

**Detailed**: llm-d-batch-gateway is a multi-component system for submitting, processing, and managing batch inference jobs against llm-d inference endpoints. It exposes a REST API with full schema parity with OpenAI's `/v1/batches` and `/v1/files` endpoints, enabling users to upload JSONL input files, create batch jobs targeting specific models, track progress in real time, and retrieve results.

The system is decomposed into three independently scalable Go binaries. The **API server** handles all client-facing REST traffic for batch and file operations. The **batch processor** runs as a StatefulSet, pulling jobs from a Redis/Valkey priority queue, building per-model execution plans, dispatching individual inference requests to downstream llm-d gateways with AIMD-based adaptive concurrency control, and writing output files. The **garbage collector** periodically removes expired jobs and files and includes an orphan reconciler that watches processor pods via the Kubernetes API to detect and recover stuck jobs after processor crashes.

The architecture relies on PostgreSQL for job and file metadata, Redis or Valkey for priority queuing and event channels, and S3-compatible object storage (or local filesystem) for input/output files. Authentication and authorization are deliberately not implemented in the gateway itself — they are delegated to the external gateway layer (Kuadrant/Authorino) — while multi-tenancy isolation is enforced at the application level through tenant-scoped database queries keyed to the `X-MaaS-Username` header.

## Architectural Analysis

The batch gateway follows a clean producer-consumer pattern with clear separation of concerns. The API server is stateless and horizontally scalable — it writes metadata to PostgreSQL, enqueues jobs to Redis, and stores files in S3, then returns immediately. The processor is stateful (deployed as a StatefulSet for stable network identity) and acts as the work consumer, pulling jobs from the priority queue and driving them through ingestion, execution, and result upload phases.

A notable design decision is the dual dispatch mode architecture: processors can operate in "sync" mode (sending inference requests directly to llm-d gateway endpoints via HTTP) or "async" mode (queuing requests through llm-d-async via Redis). This flexibility allows deployment configurations ranging from simple single-gateway setups to complex multi-pool deployments where different models route through separate InferencePool instances with distinct priority bands.

The concurrency control system is layered: a global semaphore caps total in-flight requests across all endpoints, per-endpoint semaphores limit concurrency to individual inference gateways, and AIMD (Additive Increase Multiplicative Decrease) dynamically adjusts the per-endpoint limit based on 429/5xx feedback signals. This protects interactive traffic from batch pressure without requiring manual tuning.

The GC component's orphan reconciler is architecturally significant — it watches processor pods via the Kubernetes API and detects when a processor crashes with in-flight jobs, recovering them by re-enqueueing or expiring depending on state. This uses a CAS-based approach to avoid races with live processors.

Security follows a defense-in-depth model, but the upstream Dockerfiles use `CGO_ENABLED=0` with distroless base images, which is incompatible with FIPS check-payload validation. The downstream RHOAI build likely requires Konflux-specific Dockerfiles with UBI base images and dynamic linking for FIPS compliance — these are not present in this branch.

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-tenant via HTTP header | internal/apiserver/common/config.go:44 |
| **Deployment model** | Multi-tenant (shared instance serving all tenants) | internal/apiserver/server/server.go:69 |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to external gateway (Kuadrant/Authorino); tenant ID extracted from header | External gateway + Application | If the external gateway is misconfigured, unauthenticated requests reach the API server; tenant ID is trusted from the header without cryptographic verification |
| Data storage | Tenant ID stored with every batch job and file record; all DB queries filtered by tenant ID | Application (PostgreSQL query filters) | Application-enforced — a bug in query construction could leak cross-tenant data; no database-level row security policy |
| Network traffic | No per-tenant NetworkPolicy | N/A | All tenants share the same network path; isolation depends on the external gateway layer |
| Compute & resources | No per-tenant resource limits | N/A | All tenants share processor workers and concurrency limits; a single tenant's large batch could consume all worker slots |
| Configuration & secrets | Shared Kubernetes Secret for all tenants | Kubernetes | All tenants use the same database credentials and inference API keys |
| API scoping | Tenant ID injected into context from header; API responses filtered by tenant | Application | Cross-tenant requests return 404 (not 403), preventing tenant enumeration |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL | Row-level tenant_id column | Application query filter on every operation |
| Redis/Valkey | Shared queues | Job metadata contains tenant ID; processor inherits tenant from job |
| S3-compatible storage | Shared bucket | File IDs are UUIDs — no path-level tenant separation; access controlled via DB metadata lookups |
