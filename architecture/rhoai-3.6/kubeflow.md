## Purpose

**Short**: Kubernetes controllers that manage the lifecycle of Jupyter Notebook workbench pods on OpenShift AI, including idle culling, authentication sidecar injection, and Gateway API routing.

**Detailed**: The kubeflow repository contains two complementary Go controllers for managing interactive notebook workbenches in the RHOAI platform. The upstream **notebook-controller** reconciles `Notebook` custom resources into StatefulSets, Services, and supporting resources, providing core lifecycle management including a configurable idle-culling reconciler that stops notebooks after a period of inactivity. The **odh-notebook-controller** extends this with OpenShift-specific capabilities: it injects kube-rbac-proxy authentication sidecars into notebook pods via a mutating webhook, manages Gateway API HTTPRoute resources to expose notebooks through the platform ingress gateway, creates per-notebook NetworkPolicies for network isolation, handles OpenShift OAuth integration, manages DSPA (Data Science Pipelines Application) secrets for pipeline connectivity, and supports MLflow experiment tracking configuration.

Together these controllers form the workbench subsystem of RHOAI. The Notebook CRD wraps a PodSpec to define the user's compute environment, and the controllers handle everything from workload creation through authentication, routing, network isolation, and eventual idle-based shutdown. The architecture follows a layered design where the upstream controller handles Kubernetes-portable notebook lifecycle while the ODH controller adds platform-specific security, networking, and integration concerns.

## Architectural Analysis

The kubeflow workbench subsystem exhibits a clear upstream/downstream layering pattern. The notebook-controller is a mostly-unmodified Kubeflow upstream controller that handles the Notebook CRD → StatefulSet reconciliation loop and idle culling, while the odh-notebook-controller runs as a separate binary that extends Notebook semantics with OpenShift-specific side effects. Both controllers watch the same Notebook CRD but operate on different resource dimensions—the upstream controller owns the StatefulSet and Services, while the ODH controller owns NetworkPolicies, RoleBindings, Secrets, ConfigMaps, and ServiceAccounts attached to each notebook.

A notable architectural decision is the mutating webhook's role as the primary injection point for security infrastructure. On every Notebook CREATE/UPDATE, the webhook injects a kube-rbac-proxy sidecar container, associated TLS certificate volumes, and service account configuration. This webhook-driven injection pattern means authentication infrastructure is configured at admission time rather than during reconciliation, creating a tight coupling between the webhook's availability and the ability to create notebooks (failure policy is `Fail`).

Both controllers read the OpenShift APIServer TLS security profile at startup and apply the cluster's TLS policy to their metrics and webhook endpoints. If the TLS profile changes at runtime, a watcher triggers a graceful restart to pick up the new configuration. This self-healing TLS profile adherence pattern avoids configuration drift but means TLS policy changes cause brief controller unavailability.

The Gateway API integration in the ODH controller represents a migration from OpenShift Routes to Kubernetes-native ingress. The controller creates HTTPRoute resources per notebook, manages ReferenceGrants for cross-namespace gateway references, and reads the platform gateway configuration to construct routes. This coexists with legacy OAuthClient management that is being phased out.

The DSPA secret reconciliation (notebook_dspa_secret.go) imports types directly from the data-science-pipelines-operator Go module, creating a compile-time dependency between the workbench and pipeline subsystems. This coupling means pipeline API changes require coordinated workbench controller updates.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Notebook CRD is Namespaced; all owned resources (StatefulSet, Service, NetworkPolicy, HTTPRoute, RoleBinding) scoped to notebook's namespace |
| **Deployment model** | single controller instance, multi-tenant | Both controllers run as single cluster-wide deployments watching all namespaces |
| **Tenant identifier** | namespace name | Controller scopes operations using the Notebook CR's namespace |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-notebook kube-rbac-proxy sidecar; per-namespace RoleBindings; aggregated ClusterRoles (admin/edit/view) | Kubernetes RBAC + kube-rbac-proxy | OAuthClient resources are cluster-scoped — naming collisions theoretically possible across namespaces |
| Data storage | Per-notebook StatefulSet with PVCs inherited from PodSpec; no shared storage | Kubernetes | Storage isolation depends on user-provided PodSpec configuration |
| Network traffic | Per-notebook NetworkPolicy created by ODH controller | Kubernetes NetworkPolicy | NetworkPolicy enforcement depends on cluster CNI plugin support |
| Compute & resources | Resource limits from user-provided PodSpec; kube-rbac-proxy sidecar resources set by webhook | Kubernetes | No enforced ResourceQuota by controller; depends on namespace-level quotas |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; per-notebook DSPA secrets | Kubernetes | odh-config ConfigMap is read from controller namespace (shared across all tenants) |
| API scoping | Cluster-wide watch with per-namespace reconciliation; OwnedBy handler maps child events to parent Notebook in same namespace | Kubernetes controller-runtime | No namespace allow/deny list in controllers; watches all namespaces |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Platform Gateway (Gateway API) | Per-notebook HTTPRoute | Each notebook gets its own HTTPRoute with unique hostname; gateway handles TLS termination |
| Metrics endpoint | Controller-wide | Single metrics endpoint serves all notebook metrics; no per-tenant scoping |
