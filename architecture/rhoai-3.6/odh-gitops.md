## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying and configuring OpenDataHub/RHOAI platform dependencies on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: odh-gitops is the infrastructure-as-code repository that codifies the deployment of all prerequisite operators and configurations needed by the OpenDataHub (ODH) and Red Hat OpenShift AI (RHOAI) platforms. It does not contain application source code or container images; instead, it provides declarative manifests that install, configure, and wire together the operator ecosystem that the AI/ML platform relies on — including cert-manager, Kueue, Leader Worker Set, Red Hat Connectivity Link (Kuadrant/Authorino), observability operators, GPU operators, and more.

The repository serves two deployment paradigms. First, a **Kustomize-based approach** with reusable components (`components/operators/`) composed into overlays (`dependencies/operators/`) with post-install configurations (`configurations/`), suitable for GitOps tools like ArgoCD or Flux. Second, a **Helm chart approach** with two charts: `rhai-on-openshift-chart` for OLM-based OpenShift deployments (using OLM Subscriptions) and `rhai-on-xks-chart` for non-OpenShift Kubernetes (AWS, Azure, CoreWeave) where it bundles the RHAI operator deployment, CRDs, RBAC, and cloud-provider-specific resources directly. The Helm charts implement a tri-state dependency resolution system (`auto`/`true`/`false`) that automatically installs only the operators required by enabled platform components, with profile-based defaults for inference-only or full-platform configurations.

## Architectural Analysis

odh-gitops occupies a critical infrastructure layer: it is the bridge between the platform operators and the cluster. While it deploys no runtime workloads of its own, it defines the entire dependency graph of the RHOAI platform and controls how operators are installed, namespaced, configured, and wired together.

The most architecturally significant pattern is the **tri-state dependency resolution** in the Helm charts. Each RHOAI component (KServe, Kueue, Ray, Trainer, etc.) declares its operator dependencies, and each dependency has an `enabled` tri-state. When set to `auto` (the default), the chart walks the component graph at render time to determine which dependencies are actually required, including transitive dependencies. This allows a single chart to generate manifests ranging from a minimal inference-only stack (cert-manager + LWS + RHCL) to a full platform with GPU support, observability, and pipelines — all driven by values overrides and profiles.

The **dual-chart architecture** (`rhai-on-openshift-chart` vs. `rhai-on-xks-chart`) reflects a fundamental platform split. On OpenShift, operator lifecycle is delegated to OLM via Subscriptions, and the chart generates Namespace + OperatorGroup + Subscription resources. On non-OpenShift Kubernetes, the chart takes on the responsibility of deploying the RHAI operator itself (Deployment, RBAC, webhook Service, CRDs) plus cloud-provider-specific resources (AWS/Azure/CoreWeave KubernetesEngine CRDs and cloud-manager operators). The XKS chart also uses post-install hook Jobs to create Gateway resources and DataScienceCluster/DSCInitialization CRs, since these require the operator and CRDs to be running first.

The **TLS and certificate management** architecture spans both charts and the Kustomize layer. The OCP chart configures Authorino TLS through Kustomize patches or direct CR patching. The XKS chart generates cert-manager Certificate resources with appropriate SANs for inference gateways and MaaS API serving, distributes CA bundles via ConfigMaps to gateway proxy sidecars, and patches Authorino deployments to trust the internal CA. This represents a tightly coupled but necessary integration between cert-manager, Istio/Gateway API, and Authorino.

A notable design decision is the **profile system**. The `default` profile sets all components to `Removed`, requiring explicit opt-in. The `rhaii` profile enables only KServe for inference-only deployments. The `maas` profile adds Models-as-a-Service capabilities. This prevents accidental deployment of unneeded components and their transitive dependency chains.

The separation of Kustomize `components/` (reusable, composable) from `dependencies/` (overlay compositions with patches) from `configurations/` (post-CRD custom resources) creates a clean three-phase deployment model: install operators → wait for CRDs → configure operators. This maps directly to the inherent ordering constraint of OLM-based operator deployment.
