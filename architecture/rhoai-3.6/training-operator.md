## Purpose

**Short**: Kubernetes operator that manages distributed training jobs across multiple ML frameworks (PyTorch, TensorFlow, XGBoost, MPI, PaddlePaddle, JAX) on OpenShift.

**Detailed**: The training-operator is a Kubeflow-originated controller-runtime operator that defines six Custom Resource Definitions — PyTorchJob, TFJob, XGBoostJob, MPIJob, PaddleJob, and JAXJob — allowing users to declaratively specify distributed training workloads. For each job type, a dedicated reconciler manages the full lifecycle: creating worker/master pods and headless services, tracking replica status, handling restarts and failures, and cleaning up completed jobs. The operator exposes validating admission webhooks for five of the six job types (all except MPIJob) to reject malformed job specs before they enter the cluster.

The RHOAI distribution adds OpenShift-specific hardening: TLS configuration is derived from the cluster's APIServer TLS security profile (with hardened intermediate defaults as fallback), FIPS-compliant builds use `GOEXPERIMENT=strictfipsruntime` and dynamic linking via CGO, and webhook TLS certificates are self-managed using the OPA cert-controller rotator. The PyTorchJob controller creates per-job NetworkPolicies to isolate training pod traffic, and the operator supports optional gang scheduling via Volcano or scheduler-plugins for coordinated pod startup.

## Architectural Analysis

The training-operator follows a per-framework reconciler pattern: each of the six supported ML frameworks has its own controller in `pkg/controller.v1/` sharing a common `JobController` base that handles pod and service lifecycle. This factoring keeps framework-specific logic (e.g., PyTorch elastic training, MPI launcher/worker topology) isolated while the common layer manages replica counting, status tracking, and gang scheduling integration.

A notable design choice is the cache-filtering strategy implemented in `newCacheOptions()`: the operator restricts its informer cache to only operator-labeled resources (Pods, Services, ConfigMaps, Secrets, ServiceAccounts, Roles, RoleBindings), preventing unbounded memory growth that would occur from watching all cluster resources. ConfigMaps and Secrets are additionally excluded from the cache client to force direct API reads, avoiding stale configuration data.

The TLS configuration is adaptive: on OpenShift clusters, the operator reads the cluster-wide `config.openshift.io/v1/APIServer` resource to discover the TLS security profile and applies it to both the metrics server and webhook server. On non-OpenShift clusters or when the APIServer resource is unavailable, it falls back to a hardened intermediate profile (TLS 1.2 minimum with AEAD cipher suites only). This design ensures the operator's security posture aligns with cluster policy without requiring manual configuration.

The webhook certificate lifecycle is fully self-managed: the OPA cert-controller rotator generates a CA and server certificate, stores them in a Kubernetes Secret, writes them to disk for the webhook server, and patches the ValidatingWebhookConfiguration's `caBundle`. This eliminates any dependency on cert-manager. The readiness probe delays advertising the pod as ready until certificates are generated and the webhook server is listening, preventing request rejection during startup.

The PyTorchJob controller is the most feature-rich of the six, adding NetworkPolicy creation for per-job pod isolation (allowing only intra-job traffic and monitoring scrapes from `openshift-monitoring`), HorizontalPodAutoscaler management for elastic training, and init container injection for distributed coordination.
