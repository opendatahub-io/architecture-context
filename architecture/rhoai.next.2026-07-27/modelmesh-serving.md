## Purpose

**Short**: ModelMesh Serving is a Kubernetes controller that manages multi-model serving runtimes, providing model placement, scaling, and lifecycle management through CRD-based APIs.

**Detailed**: modelmesh-serving is a Kubernetes Operator / Controller comprising 8 architecture components. The principal controllers are the ServingRuntime controller (reconciles ServingRuntime and ClusterServingRuntime resources to manage model serving deployments), the Predictor controller (reconciles Predictor resources to manage individual model lifecycle), the Service controller (reconciles Deployments to manage headless services and monitoring), and the HPA reconciler (manages HorizontalPodAutoscaler resources for autoscaling serving runtimes). A validating webhook enforces autoscaler configuration, replica constraints, and HPA metric validation on ServingRuntime and ClusterServingRuntime CREATE/UPDATE operations. The controller communicates with ModelMesh runtime pods via gRPC and uses etcd for model mesh coordination. Its API surface includes 4 CRDs (ClusterServingRuntime, ServingRuntime, Predictor, InferenceService), 5 HTTP endpoints, and admission webhooks for validation and CRD conversion.

## Data Flows

- **Entry and service surface:** The controller exposes a single ClusterIP Service (modelmesh-webhook-server-service) on port 9443 for admission webhook traffic. Health and readiness probes are served on port 8081. The controller does not expose ingress routes.
- **Webhook validation flow:** On ServingRuntime or ClusterServingRuntime CREATE/UPDATE, the Kubernetes API server sends an admission review to the validating webhook on port 9443. The webhook checks if the runtime is multiModel; if so, it validates autoscaler class (HPA supported), target utilization percentage (1-100), and replica/scaling constraints (autoscaler and explicit replicas cannot coexist). Non-multiModel runtimes bypass validation entirely (source: apis/serving/v1alpha1/servingruntime_webhook.go:38-93).
- **Controller reconciliation:** The ServingRuntime controller watches ServingRuntime, ClusterServingRuntime (conditional), Predictor, InferenceService (conditional), Namespace (conditional), Secret (conditional), and ConfigMap resources. It owns Deployment resources for serving runtime pods. The Predictor controller watches Predictor and InferenceService resources. The Service controller watches Deployments, owns Services, and conditionally watches ServiceMonitors.
- **gRPC client communication:** The controller communicates with ModelMesh sidecar containers in serving runtime pods via gRPC using generated stubs (model-mesh-external_grpc.pb.go). Service discovery uses a custom Kubernetes Endpoints-based gRPC resolver (grpc_resolver.go) that watches Endpoints resources for target pod resolution.
- **etcd coordination:** The controller uses etcd client v3 for ModelMesh model placement coordination, including range watching for model state changes (etcdrangewatcher.go).
- **Downstream interactions:** The structured facts record 30+ integration points, 4 internal dependencies, and 3 egress destinations. Named destinations include Kubernetes API, etcd, ModelMesh runtime pods, and prometheus-operator.
- **Security context:** 6 authentication rules and 1 secret reference describe the enforcement and credential inputs. The webhook server uses TLS certificates from the modelmesh-webhook-server-cert secret mounted at /tmp/k8s-webhook-server/serving-certs.
