## Purpose

**Short**: Python SDK library for managing Kubeflow ML workloads (training, hyperparameter tuning, Spark, model registry) via Kubernetes API interactions.

**Detailed**: kubeflow-sdk is a Python client library that provides a unified interface for data scientists and ML engineers to manage ML workloads on Kubernetes-based Kubeflow platforms. The SDK does not deploy as a standalone service or controller; instead, it is consumed as a Python package (`kubeflow`) by user code and notebooks. It integrates with Kubeflow Trainer (for model training orchestration), Kubeflow Katib (for hyperparameter optimization), Spark Operator (for distributed Spark workloads via SparkConnect), and Model Registry (for model artifact management). All Kubernetes interactions are performed through the `kubernetes` Python client with configurable authentication via `KubernetesBackendConfig`. The SDK includes optional dependency groups for container runtimes (Docker, Podman), RHAI storage (fsspec, s3fs), Spark (pyspark-connect), and hub (model-registry).

## Data Flows

- **Client library model:** kubeflow-sdk is a Python package imported by user applications, notebooks, or pipeline steps. It does not run as a long-lived service. Data flows originate from user code invoking SDK methods.
- **Kubernetes interactions:** The SDK uses the `kubernetes` Python client to perform CRUD operations on Kubeflow CRDs (TrainJob, Experiment, SparkConnect, etc.) against the Kubernetes API server. Authentication is configured per-session via `KubernetesBackendConfig` (namespace, kubeconfig file, context, or explicit `client.Configuration`).
- **API package layer:** The `kubeflow-trainer-api`, `kubeflow-katib-api`, and `kubeflow-spark-api` packages provide protobuf-generated Python types and gRPC stubs. The SDK uses these for type-safe interaction with the corresponding operators' CRDs.
- **Optional storage:** When the `rhai` extra is installed, the SDK uses `fsspec`/`s3fs` for reading/writing checkpoints and datasets to S3-compatible storage.
- **Optional container runtimes:** The `docker` and `podman` extras enable local container-based training workflows without requiring a Kubernetes cluster.

## Architectural Analysis

- **Deployment shape:** kubeflow-sdk is a pure Python client library (PyPI package `kubeflow`) consumed by user applications and notebooks. It does not deploy as a Kubernetes workload, operator, or controller. The analyzer's classification as "Kubernetes Operator / Controller" is corrected based on source evidence: the repository contains no controller-manager, no Deployment manifests, and no controller watches.
- **SDK module structure:** The package is organized into five functional subpackages — `trainer` (training orchestration with multiple backends), `optimizer` (Katib-based hyperparameter tuning), `spark` (SparkConnect workload management), `hub` (model registry integration), and `common` (shared types including `KubernetesBackendConfig`). Optional dependency groups (`docker`, `podman`, `rhai`, `spark`, `hub`) allow selective installation.
- **CRD relationship:** The SparkConnect CRD (`sparkoperator.k8s.io/v1alpha1`) in `hack/crds/` is a reference copy from the Spark Operator repository, used for SDK development and testing. This SDK is a client of that CRD, not its owner.
- **API surface:** The SDK exposes no inbound HTTP endpoints and no gRPC services. All network communication is outbound — to the Kubernetes API server and optionally to S3-compatible storage. The `grpcio` and `protobuf` dependencies are consumed transitively through the Kubeflow API packages for type serialization.
- **Authentication model:** The SDK delegates all authentication to the `kubernetes` Python client. `KubernetesBackendConfig` (defined in `kubeflow/common/types.py`) accepts namespace, config_file, context, and `client.Configuration`, supporting kubeconfig files, in-cluster service account tokens, and explicit client configurations.
- **RHOAI integration:** The dev dependency for `kubeflow-trainer-api` pins to the `opendatahub-io/trainer` fork (commit `095d52e`), and the `trainer.rhai` subpackage provides Red Hat AI-specific extensions including transformers integration and training hub functionality.
- **Evidence boundary:** Analyzer coverage is partial for `platform_semantics`, `python`, and `webhooks_source`. The SDK's runtime behavior depends on the Kubeflow operators and platform services it connects to; those are documented in their respective component architectures.
