## Purpose

**Short**: LLM deployment planning service providing GPU capacity estimation, model recommendation, and deployment configuration for Kubernetes clusters via a FastAPI backend and Streamlit UI.

**Detailed**: llm-d-planner is a multi-component planning tool that helps users navigate LLM deployments from concept to production. It consists of 5 architecture components: a FastAPI backend API server providing capacity planning, GPU recommendation, deployment management, and database operations (port 8000); an Ollama LLM inference server running the Granite 3.3 2b model on GPU (port 11434); a PostgreSQL 16 database for benchmark and deployment data persistence (port 5432); a Streamlit web UI for interactive planning workflows (port 8501); and the planner Python service core. The backend connects to external LLM providers (OpenAI-compatible, Vertex AI, Ollama) for AI-assisted planning, queries HuggingFace Hub for model metadata, and interacts with the Kubernetes API for cluster GPU detection and KServe-based model deployment. External access is provided via two OpenShift Routes with TLS edge termination. No application-level authentication middleware is registered on any endpoint.

## Data Flows

- **External entry:** Users access the Streamlit UI via the `planner` OpenShift Route (HTTPS, TLS edge termination on port 8501). The UI communicates with the backend API internally at `http://backend:8000` (plaintext HTTP within the cluster).
- **Backend API surface:** The `planner-backend` Route exposes the backend API externally (HTTPS, TLS edge termination on port 8000). The backend serves 30 REST API endpoints covering capacity planning, GPU recommendation, deployment configuration, database management, intent extraction, and reference data.
- **Internal data path:** UI → backend (HTTP :8000) → postgres (PostgreSQL :5432, password auth) for benchmark and deployment persistence. Backend → ollama (HTTP :11434) for local LLM inference using Granite 3.3 2b model.
- **External LLM providers:** Backend connects to one of three configurable LLM providers: Ollama (local, HTTP), OpenAI-compatible API (external, HTTPS with API key), or Vertex AI (external, HTTPS with GCP service account credentials). Provider selection is controlled by the `LLM_PROVIDER` environment variable from `planner-config` ConfigMap.
- **External data sources:** Backend optionally connects to HuggingFace Hub (HTTPS, bearer token) for model metadata and to a Model Catalog service (HTTPS, bearer token) for benchmark data.
- **Cluster interaction:** Backend uses the Kubernetes Python client with the `planner-backend` ServiceAccount to list cluster nodes for GPU detection (via `planner-gpu-reader` ClusterRole) and to create/manage KServe InferenceService resources for model deployment.
- **TLS trust:** Backend mounts the OpenShift Service CA bundle at `/etc/pki/service-ca` for verifying TLS certificates of cluster-internal services.
- **Security context:** No application-level authentication middleware is registered on any endpoint. CORS is configured to accept all origins (`CORS_ORIGINS=*`). Database admin operations are optionally gated by `DB_ADMIN_PASSWORD`.

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Kubernetes Workload, represented by 4 Deployments (backend, ollama, postgres, ui), 4 ClusterIP Services, and 1 Python service core (planner). All components deploy to the `planner` namespace.
- **Multi-provider LLM architecture:** The backend supports three LLM providers (Ollama local, OpenAI-compatible, Vertex AI) selected at runtime via the `LLM_PROVIDER` ConfigMap key, enabling flexible deployment across cloud and on-premises environments.
- **GPU dependency:** The ollama Deployment requests `nvidia.com/gpu: 1` for local LLM inference. The backend uses ClusterRole `planner-gpu-reader` to detect available GPU nodes in the cluster.
- **Storage:** Two PersistentVolumeClaims: `ollama-pvc` (20Gi, ReadWriteOnce) for LLM model storage and `postgres-pvc` (5Gi, ReadWriteOnce) for database persistence. Both deployments use Recreate strategy to avoid PVC access conflicts.

- **Security posture:** Only the backend Deployment has restricted pod security context (runAsNonRoot, RuntimeDefault seccomp, drop ALL capabilities). No application-level authentication middleware is registered. CORS accepts all origins. TLS is terminated at the OpenShift Router; internal pod-to-pod traffic is plaintext HTTP/PostgreSQL. Database admin endpoints are optionally gated by `DB_ADMIN_PASSWORD`.
