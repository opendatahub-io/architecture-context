## Platform Overview

Red Hat OpenShift AI (RHOAI) is an enterprise machine learning platform built on OpenShift Container Platform that provides a comprehensive, operator-managed stack for the full ML lifecycle — from interactive development through model training, serving, and monitoring. The platform is deployed via OLM through the `rhods-operator`, which acts as a meta-operator orchestrating 20+ component operators and controllers through a layered CRD model. A singleton `DataScienceCluster` CR drives component reconciliation, with each component (Dashboard, KServe, Kueue, CodeFlare, etc.) represented by its own component CRD under the `components.platform.opendatahub.io` API group.

Ingress is architected around the Kubernetes Gateway API, with a centralized `data-science-gateway` in the `openshift-ingress` namespace providing TLS termination and routing via HTTPRoute resources. Authentication is enforced at the gateway level through Kuadrant AuthPolicy (supporting API key, TokenReview, and optional OIDC JWT mechanisms) and at the component level through kube-rbac-proxy sidecars, OAuthProxy injection, and native Kubernetes RBAC. The platform uses cert-manager for TLS certificate lifecycle management across 6 components and prometheus-operator for unified observability across 23 components.

The security posture follows defense-in-depth principles: UBI9-minimal base images, non-root container execution with dropped capabilities, FIPS-compliant Go builds (GOEXPERIMENT=strictfipsruntime) for critical components like models-as-a-service, OpenShift cluster TLS profile adherence for webhook and metrics endpoints, and comprehensive admission webhook coverage with 218 webhook registrations across 24 components — all configured with `Fail` failure policy to enforce strict admission control.

## Deployment Architecture

### Deployment Topology

The platform follows a three-tier namespace architecture. The **operator tier** (`redhat-ods-operator`) hosts the meta-operator and module operators that reconcile platform state. The **platform services tier** (`redhat-ods-applications`) hosts controllers, the dashboard, and shared services. ## Platform Architectural Analysis

The RHOAI rhoai.next platform reveals several cross-cutting architectural patterns and tensions that emerge from analyzing all 87 components together.

**Converging on Gateway API as the universal ingress model.** The platform is migrating from a mix of OpenShift Routes, Istio VirtualServices, and direct Service exposure toward a unified Gateway API architecture. The centralized `data-science-gateway` provides a single ingress point with HTTPRoute-based routing, but the migration is incomplete: KServe still carries Istio VirtualService and Knative Serving dependencies (`istio.io/api`, `knative.dev/serving` in go.mod), reflecting the transition from the previous Istio-based service mesh to Gateway API. This dual-stack networking creates operational complexity during the transition period.

**The llm-d disaggregated inference stack represents a significant architectural investment.** With 12 llm-d-related components (llm-d, llm-d-async, llm-d-batch-gateway, llm-d-inference-scheduler, llm-d-router, llm-d-kv-cache, llm-d-planner, llm-d-latency-predictor, llm-d-routing-sidecar, llm-d-model-service, llm-d-batch-gateway-operator, llm-d-workload-variant-autoscaler), the platform is building a sophisticated prefill-decode separation architecture with NIXL-based KV-cache transfer. This stack introduces its own Envoy ext_proc pipeline, scheduling, and routing layers that run parallel to the core KServe serving path. The InferencePool abstraction from gateway-api-inference-extension bridges these two serving models.

**Kueue is the most aggressive cross-component webhook integrator.** With 31 webhook registrations spanning 14 mutating and 16 validating webhooks, Kueue intercepts resources from 10 different workload frameworks (batch/Job, JobSet, 5 Kubeflow training operators, 2 Ray operators, AppWrapper, Deployment, StatefulSet, LeaderWorkerSet, and pods). This creates tight runtime coupling — a Kueue outage blocks admission for all workload types across the platform. The `Fail` failure policy on all webhooks is the correct security choice but amplifies the blast radius.

**Authentication inconsistency across the serving stack.** The platform employs at least 5 distinct authentication mechanisms: kube-rbac-proxy sidecars (Dashboard, metrics endpoints), OAuthProxy injection (KServe inference services), Kuadrant AuthPolicy (MaaS API), direct TokenReview/SubjectAccessReview (MaaS API server, InferenceGraph router), and cert-manager mTLS (webhook endpoints). While defense-in-depth is valuable, the lack of a unified authentication framework means each component implements its own token validation, creating potential policy gaps and operational complexity. The kube-rbac-proxy approach is being phased out in favor of controller-runtime's native authn/authz filters in newer components.

**The operator hierarchy creates a deep reconciliation chain.** The rhods-operator orchestrates module operators (kserve-module, dashboard-operator, ai-gateway-operator), which in turn deploy and manage component controllers (kserve controller, odh-model-controller), which then manage workload resources (InferenceServices, Deployments, Pods). This 3-4 level deep reconciliation chain means a single DataScienceCluster spec change can trigger cascading reconciliation across dozens of controllers. The layered CRD model (DataScienceCluster → component CRDs → workload CRDs) provides clean separation of concerns but adds latency to configuration propagation.

**Model serving has the richest ecosystem with the most duplication.** The platform ships 7 distinct model serving runtimes (vllm, vllm-cpu, vllm-gaudi, vllm-rocm, vllm-spyre, openvino_model_server, MLServer) plus the Caikit stack (caikit, caikit-nlp, caikit-tgis-backend, caikit-tgis-serving), text-generation-inference, and modelmesh. Each runtime has its own container image, gRPC endpoint configuration, and monitoring setup, but they share the common KServe V2 Inference Protocol. The modelmesh path (multi-model serving) coexists with the KServe single-model path, creating two parallel serving architectures.

**Observability is the most uniformly adopted cross-cutting concern.** With 23 of 87 components integrating with prometheus-operator via ServiceMonitor/PodMonitor CRDs, and the rhods-operator injecting podmonitor-injector webhooks, metrics collection is the most consistent platform-wide pattern. However, the metrics transport is not uniformly secured — some components expose metrics on HTTP while others use HTTPS via kube-rbac-proxy, and the transition to controller-runtime's built-in metrics HTTPS is ongoing.

**The MCP (Model Context Protocol) integration is emerging.** Three components (mcp-lifecycle-operator, mcp-lifecycle-module-operator, rhoai-mcp) provide MCP server lifecycle management, and the rhods-operator includes `github.com/mark3labs/mcp-go` as a dependency with an embedded MCP server CLI (`cmd/mcp-server`). The agents-operator adds AgentCard and AgentRuntime CRDs. This represents a new surface area for AI agent orchestration that is still in early integration with the core platform.
