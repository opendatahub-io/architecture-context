## Purpose

**Short**: Source-backed analysis represents agents-operator as Kubernetes Operator / Controller with 17 runtime components, 25 API identities, and 62 integration points.

**Detailed**: agents-operator is a Kubernetes operator for managing AI agent runtimes within the RHOAI platform. It defines the AgentCard and AgentRuntime CRDs (agent.kagenti.dev/v1alpha1) and reconciles agent deployments, TLS certificates, network policies, RBAC, and platform integrations (MLflow, Tekton, Kuadrant, SPIRE). The operator ships an AuthBridge subsystem — a pluggable authentication/authorization proxy available in three deployment modes (authbridge-envoy for Envoy ext_proc sidecar, authbridge-proxy for full proxy-sidecar, authbridge-lite for size-optimized proxy-sidecar) — that intercepts agent-to-agent communication to enforce JWT validation, OPA policy, token exchange, SPIFFE mTLS, and protocol-aware session tracking for A2A, MCP, and inference protocols. A mutating admission webhook (inject.kagenti.io) injects the AuthBridge sidecar into agent Pods. A companion token-broker service manages OAuth2 session tokens, and an agentcard-signer signs agent cards using sigstore. The operator integrates with cert-manager for TLS, DataScienceCluster for platform feature gating, and optional SPIRE for workload identity. Its documented interface surface contains 25 API identities, including 21+ HTTP endpoints, 2 gRPC services, and 3 custom resource identities. The extracted dependency view records 11 internal platform dependencies and 62 integration points.

## Data Flows

- **Entry and service surface:** The operator exposes 2 Kubernetes Services (webhook on 443→9443, metrics on 8443→8443) and manages 21+ HTTP endpoints and 2 gRPC services across its components. AuthBridge sidecars are injected into agent Pods via the mutating webhook (inject.kagenti.io) and intercept all agent inbound/outbound HTTP traffic through reverse proxy and forward proxy listeners.
- **AuthBridge request pipeline:** Inbound requests flow through a configurable plugin chain: jwt-validation verifies Bearer tokens against configured JWKS endpoints, OPA evaluates Rego authorization policies, and protocol parsers (a2a-parser, mcp-parser, inference-parser) extract session context for observability. Outbound requests flow through token-exchange (resolves credential placeholders to real tokens, performs audience-scoped exchange) and the same parser chain. Session state is tracked in an in-memory store with configurable TTL.
- **mTLS and SPIFFE:** When the mTLS block is configured, authbridge-proxy/lite use SPIFFE X.509-SVIDs from the SPIRE Workload API for mutual TLS on both inbound (reverse proxy, byte-peek detection) and outbound (forward proxy) paths. authbridge-envoy relies on Envoy's native TLS termination with SVID files mirrored to disk by the SPIFFE Provider.
- **TLS bridge:** authbridge-proxy supports a TLS bridge mode where outbound TLS is terminated using a cert-manager-issued CA, allowing the outbound pipeline to inspect decrypted HTTPS before re-encrypting to the upstream. Configurable port set (defaults to 443, 8443) and passthrough hosts.
- **Runtime inventory:** The extracted deployment and source facts identify 17 runtime components: 8 controllers, 3 authbridge variants, abctl CLI, and 4 supporting executables (manager, agentcard-signer, bundle-service, token-broker). The operator reconciles agent lifecycle, certificates, network policies, RBAC, and platform integrations.
- **Downstream interactions:** The structured facts record 62 integration points, 11 internal dependencies, and 2 egress destinations. Named destinations include cert-manager, DataScienceCluster CR, MLflow, Envoy proxy, SPIFFE/SPIRE, Keycloak, Kuadrant, Tekton, and OpenShift Routes.
- **Security context:** 15 authentication rules and 3 secret references describe the extracted enforcement and credential inputs. AuthBridge sidecar endpoints (stat server, session API, health) are explicitly unauthenticated; the session API carries raw user content and must not be exposed via ingress.
