## Purpose

**Short**: GPU-aware autoscaler controller for LLM inference workloads that optimizes replica counts across hardware variants using saturation analysis, queueing models, and cost-based scaling decisions.

**Detailed**: The Workload Variant Autoscaler (WVA) is a Kubernetes controller-runtime based application that observes LLM inference serving workloads and makes intelligent scaling decisions across multiple hardware variants (e.g., different GPU types). It watches HorizontalPodAutoscalers, KEDA ScaledObjects, and InferencePool resources to discover managed workloads, then runs a continuous optimization loop that collects per-replica metrics from Prometheus (KV cache utilization, queue lengths, throughput), analyzes saturation levels using pluggable analyzers (percentage-based V1, token/capacity-based V2, throughput, queueing model), and emits `wva_desired_replicas` metrics that HPA or KEDA consume to drive actual scaling.

The controller supports disaggregated inference topologies via LeaderWorkerSet integration, multi-model GPU quota rebalancing through an experimental coordinator subsystem with plugin architecture, and scale-to-zero capabilities with configurable retention periods. It operates in either cluster-scoped (watching all namespaces) or namespace-scoped mode, and supports both inventory-based (physical GPU capacity discovery) and quota-based (operator-declared per-GPU-type quotas) GPU limiting strategies.

## Architectural Analysis

The Workload Variant Autoscaler follows a control-loop architecture built on controller-runtime, but extends the typical operator pattern with continuous optimization engines that run alongside Kubernetes reconcilers. Rather than owning custom resources, WVA acts as a sidecar autoscaler that observes existing HPA/KEDA/InferencePool resources via annotation-based discovery (`llm-d.ai/managed: "true"`) and emits scaling recommendations as Prometheus metrics (`wva_desired_replicas`). This decoupled design means WVA does not directly mutate replica counts on managed Deployments for the saturation engine path — instead, it publishes metrics that HPA or KEDA consume, preserving the native Kubernetes scaling chain.

The architecture has a notable CRD gap: the PROJECT file declares a `VariantAutoscaling` CRD (group `llmd.ai`, version `v1alpha1`), but no CRD YAML or generated API types exist on this branch. The current discovery mechanism relies entirely on HPA/ScaledObject annotations and ConfigMap-based configuration, suggesting the CRD is planned but not yet implemented.

The GPU limiter subsystem supports two modes: inventory-based (physical GPU capacity from node labels across NVIDIA, AMD, Intel vendors) and quota-based (operator-declared quotas per GPU type). The experimental coordinator with its GPU rebalance plugin represents a step toward cluster-wide multi-model optimization, but carries documented risks including potential queue metric cross-namespace inflation, lack of optimistic locking on patches, and scaling thrash from queue fluctuations.

Security-wise, the metrics endpoint uses controller-runtime's TokenReview + SubjectAccessReview filter for authentication, and supports both self-signed and externally provided TLS certificates. The upstream Dockerfile uses `CGO_ENABLED=0` with distroless/static, which would not pass FIPS check-payload validation — downstream builds would need to use CGO with a UBI base. The default Prometheus connection uses `InsecureSkipVerify: true`, which is documented as a dev/test setting.

The ConfigMap-based dynamic configuration system is sophisticated: global configs apply cluster-wide, namespace-local configs can override per-model settings, and namespaces opt in via labels or opt out via annotations. The readiness probe blocks until all ConfigMaps are bootstrapped, ensuring the controller does not make scaling decisions with incomplete configuration.
