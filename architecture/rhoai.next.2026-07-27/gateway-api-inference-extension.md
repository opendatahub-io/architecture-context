## Purpose

**Short**: Gateway API Inference Extension implements an Endpoint Picker (EPP) gRPC service and Kubernetes controllers for intelligent request routing to model-serving inference pools, with plugin-based scheduling, flow control, and priority-aware traffic management.

**Detailed**: gateway-api-inference-extension provides the Gateway API Inference Extension for Kubernetes, enabling intelligent routing of inference requests to model-serving backends. The core component is the Endpoint Picker (EPP), a gRPC-based Envoy External Processor that receives per-request callouts and selects optimal backend endpoints using configurable scheduling profiles, plugins, and flow control policies. The extension defines 5 CRDs: InferencePool (groups model-serving Pods by label selector and exposes target ports with an endpoint picker reference), EndpointPickerConfig (configures the EPP's plugin pipeline including scheduling profiles, data layer sources, flow control with priority bands, and parser selection), InferenceModelRewrite (defines model name rewriting rules with weighted traffic distribution), InferenceObjective (assigns priority levels to workloads for flow control within a pool), and InferencePoolImport (enables multi-cluster pool federation). Five controllers reconcile these resources and watch Pods to maintain a live backend datastore. The component integrates with Gateway API (gateway.networking.k8s.io) as a backend referenced by HTTPRoute resources, scrapes metrics from model-serving endpoints, and communicates with the Kubernetes API for resource operations.

## Data Flows

- **Entry and service surface:** The EPP receives gRPC ExtProc callouts from an Envoy proxy sitting behind a Gateway API gateway. HTTPRoute resources reference InferencePool as a backendRef, causing the gateway to route inference requests to the pool's model-serving Pods after EPP endpoint selection. The EPP itself exposes 2 gRPC services (ExternalProcessor and Health) but no HTTP endpoints.
- **Request processing pipeline:** On each ExtProc callout, the EPP executes its EndpointPickerConfig-driven plugin pipeline: (1) parse the request (default: openai-parser), (2) extract data-layer signals from configured sources, (3) evaluate saturation detection (default: utilization-detector), (4) apply flow control with priority bands, fairness policies, and ordering policies, (5) score/filter endpoints using the scheduling profile's plugins, and (6) select a backend endpoint (podIP:port) from the InferencePool's matched Pods.
- **Runtime inventory:** 6 runtime components maintain the system: 5 controllers (InferencePool, InferenceObjective, InferenceModelRewrite, Pod, ConfigMap) keep the in-memory datastore synchronized with cluster state, while the EPP gRPC service processes per-request routing decisions.
- **Downstream interactions:** The EPP scrapes metrics from model-serving endpoints via HTTP to feed saturation detection and scheduling. Controllers watch Kubernetes resources through the API server. InferenceModelRewrite and InferenceObjective resources reference their parent InferencePool via poolRef. InferencePoolImport enables cross-cluster pool federation.
- **Security context:** No application-level authentication is enforced on the gRPC services; transport TLS is optional and configuration-dependent. Kubernetes API access uses standard ServiceAccount authentication. No Secret resources are referenced by the component.
