## Purpose

**Short**: Kubernetes operator managing distributed machine learning training jobs (PyTorch, TensorFlow, MPI, XGBoost, PaddlePaddle, JAX) on OpenShift and Kubernetes clusters via the Kubeflow Training v1 API.

**Detailed**: training-operator is a Kubernetes operator built on controller-runtime v0.19.1 that manages the lifecycle of distributed ML training workloads through 6 CRDs in the `kubeflow.org` API group: PyTorchJob, TFJob, MPIJob, XGBoostJob, PaddleJob, and JAXJob. Each CRD type has a dedicated reconciler and validating admission webhook. The operator supports optional gang scheduling via Volcano (`scheduling.volcano.sh/v1beta1/PodGroup`) or scheduler-plugins (`scheduling.x-k8s.io/v1alpha1/PodGroup`). It exposes Prometheus metrics over TLS on port 8080, serves validating webhooks on port 9443 with TLS, and integrates with the OpenShift `config.openshift.io/v1/APIServer` TLS profile system for cluster-consistent TLS configuration with a hardened Intermediate default (TLS 1.2, AEAD cipher suites). Certificate rotation for the webhook server is managed by the OPA cert-controller library. The PyTorch controller additionally supports elastic training via HorizontalPodAutoscaler integration.

## Data Flows

- **Entry and service surface:** The operator exposes 2 Kubernetes Service ports: port 443→9443 for validating admission webhooks (TLS) and port 8080 for Prometheus metrics (TLS). Health probes are served on port 8081 without TLS. The 5 validating webhook endpoints and 1 metrics endpoint are all TLS-secured using the cluster TLS profile. No ingress resources are defined; all endpoints are cluster-internal.
- **Startup sequence:** On startup, the operator fetches the OpenShift TLS profile from `config.openshift.io/v1/APIServer` (with a 10-second timeout and hardened fallback defaults), initializes the controller manager with TLS-configured metrics and webhook servers, starts certificate rotation via cert-controller, and then registers per-CRD-type reconcilers and webhooks after certificates are ready. The readiness probe gates on both certificate readiness and webhook server availability.
- **Runtime inventory:** The operator runs a single Deployment (kubeflow-training-operator) with one container that hosts 6 reconcilers (one per CRD type) and 5 validating webhooks. Controllers watch their respective CRD types plus Pods, Services, ConfigMaps, ServiceAccounts, Roles, and RoleBindings with label-selector filtering (`OperatorNameLabel` exists requirement) to restrict cache scope.
- **Downstream interactions:** Reconcilers interact with the Kubernetes API to manage Pods, Services, ServiceAccounts, Roles, RoleBindings, ConfigMaps, and NetworkPolicies for training job workloads. The PyTorch controller additionally manages HorizontalPodAutoscalers. When gang scheduling is enabled, the operator creates Volcano or scheduler-plugins PodGroups.
- **Security context:** TLS is enforced on both externally-reachable ports (metrics 8080, webhooks 9443) using cluster-derived or hardened-default TLS profiles. Health probes (8081) are intentionally unauthenticated and unencrypted. Webhook certificates are auto-rotated by cert-controller. RBAC is enforced via the kubeflow-training-operator ClusterRole with scoped permissions. The operator also provides aggregate ClusterRoles (kubeflow-training-edit, kubeflow-training-view) for user-facing RBAC.

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Kubernetes Operator / Controller, represented by 1 architecture component (kubeflow-training-operator Deployment) with 6 internal reconcilers and 5 validating webhooks. The operator runs as a single-replica Deployment with optional leader election (`--leader-elect` flag, election ID `1ca428e5.training-operator.kubeflow.org`).
- **Control-plane surface:** The operator manages 6 CRDs in the `kubeflow.org/v1` API group, has 20 RBAC rules across 4 roles (1 operator ClusterRole, 2 aggregate ClusterRoles for user RBAC, 1 namespace-scoped webhook Role), and 2 role bindings. The aggregate roles (`kubeflow-training-edit`, `kubeflow-training-view`) are designed for RBAC aggregation via standard Kubernetes labels.
- **TLS and security:** Both externally-reachable service ports (metrics 8080, webhook 9443) are TLS-secured using the OpenShift cluster TLS profile with a hardened Intermediate fallback (TLS 1.2, AEAD cipher suites). Health probes on port 8081 are intentionally unencrypted. Webhook certificates are managed by the OPA cert-controller library with automatic rotation. The `--webhook-secret-name` and `--webhook-service-name` flags configure the certificate Secret name and DNS name.
- **Cache optimization:** The operator uses label-selector filtered informer caches (via `OperatorNameLabel` exists requirement) for Pods, Services, ConfigMaps, ServiceAccounts, Secrets, Roles, and RoleBindings to avoid unbounded memory growth from cluster-wide informers. ConfigMaps and Secrets are additionally excluded from the client cache (`DisableFor`) for direct API reads.
- **Gang scheduling:** The operator supports optional gang scheduling via Volcano (`scheduling.volcano.sh`) or scheduler-plugins (`scheduling.x-k8s.io`) through the `--gang-scheduler-name` flag. When enabled, the operator validates the corresponding PodGroup CRD exists at startup and creates PodGroups for coordinated scheduling of training job pods.
