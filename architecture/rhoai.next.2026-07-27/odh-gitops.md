## Purpose

**Short**: GitOps repository providing Helm charts and Kustomize overlays for deploying RHOAI/ODH platform dependencies, operator subscriptions, and infrastructure configuration on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: odh-gitops is a configuration-only repository that provides standardized, repeatable deployment templates for the Red Hat OpenShift AI (RHOAI) / Open Data Hub (ODH) stack. It does not run workloads itself but manages operator subscriptions, dependency charts, gateway infrastructure (Istio/Gateway API), TLS certificate provisioning (cert-manager), and authentication plumbing (Kuadrant/Authorino). The repository ships two primary Helm charts: `rhai-on-openshift-chart` (v3.4.0) for OLM-based OpenShift deployments and `rhai-on-xks-chart` (v3.5.0-ea.2) for non-OLM Kubernetes services (AWS, Azure, CoreWeave). It works with GitOps tools (ArgoCD, Flux) and supports layered Kustomize composition for granular or grouped installation.

## Data Flows

- **Inference traffic (xKS)**: Client → inference-gateway (port 80/443, Istio proxy with TLS termination) → KServe InferenceService via HTTPRoute. CA trust distributed via rhai-ca-bundle ConfigMap mounted into istio-proxy containers.
- **MaaS traffic (xKS)**: Client → maas-default-gateway (port 80/443, Istio proxy) → MaaS API services. Authorino patched with rhai-ca-bundle for callback TLS trust (SSL_CERT_FILE=/etc/pki/tls/custom/ca.crt).
- **Certificate issuance**: cert-manager watches Certificate CRs → issues TLS certificates → stores in Secrets → referenced by Gateway TLS listeners.
- **Operator lifecycle (OpenShift)**: OLM Subscriptions → InstallPlans → Operator Deployments → CR reconciliation (DataScienceCluster, DSCInitialization).
- **GitOps delivery**: Repository → ArgoCD/Flux Application → kubectl apply -k / helm install → Cluster resources.

## Architectural Analysis

- **Deployment shape:** odh-gitops is a configuration-only repository with no runtime workloads. It produces Kubernetes manifests (Helm charts + Kustomize overlays) consumed by GitOps tools or direct kubectl application. The two primary Helm charts target different platforms: `rhai-on-openshift-chart` uses OLM for operator lifecycle, while `rhai-on-xks-chart` bundles dependency charts for non-OLM environments.
- **Multi-cloud support:** The xKS chart supports AWS, Azure, and CoreWeave via cloud-specific sections in values.yaml. Each cloud provider has a dedicated CloudManager operator deployment and KubernetesEngine CR with dependency management policies (Managed/Unmanaged for cert-manager, gateway-api, lws, sail-operator).
- **Component architecture:** The OpenShift chart configures 14 RHOAI components (KServe, Dashboard, Ray, Trainer, Kueue, TrustyAI, Workbenches, ModelRegistry, AI Pipelines, FeastOperator, OGX, MLflow, Spark, TrainingOperator) through DataScienceCluster CR managementState control, plus 12 dependency operators with tri-state enablement (auto/true/false).
- **TLS architecture:** Both charts use cert-manager with an internal CA (rhai-ca-issuer) by default, with support for external ClusterIssuers. Certificates are created for inference-gateway, maas-gateway, and maas-api-serving endpoints. CA trust is distributed via ConfigMaps (rhai-ca-bundle) mounted into Istio proxy sidecars.
- **Evidence boundary:** Analyzer coverage is partial for platform_semantics and webhooks_source. The repository contains no Go/Python/Rust source code; all logic resides in Helm templates (Go template language) and shell scripts executed as post-install hooks.
