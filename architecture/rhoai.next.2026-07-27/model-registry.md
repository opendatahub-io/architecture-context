## Data Flows

- **Entry and service surface:** The BFF exposes a comprehensive REST API at `/api/v1/` on port 8080 with 50+ route registrations organized into model registry CRUD, model catalog browsing, agent catalog, MCP server catalog, model transfer jobs, and settings management (clients/ui/bff/internal/api/app.go:250-401). The catalog server exposes plugin-registered routes plus `/healthz` and `/readyz` on port 8080 (catalog/internal/plugin/server.go:99-120). The controller manager exposes health probes on port 8081 (Analyzer-seeded).
- **Authorization flow:** The BFF implements a layered authorization model: (1) `InjectRequestIdentity` extracts user identity from incoming requests, (2) `AttachNamespace` resolves the target namespace, (3) `RequireAccessToMRService` or `RequireListServiceAccessInNamespace` performs Kubernetes SubjectAccessReview (SAR) via the internal Kubernetes client to verify the user has access to the specific service or namespace. The `InternalKubernetesClient` performs SAR checks using the pod's service account credentials, with optimizations including cluster-admin detection via ClusterRoleBinding inspection and a 10-worker parallel SAR pool for namespace enumeration (clients/ui/bff/internal/integrations/kubernetes/internal_k8s_client.go:160-296).
- **Proxy pattern:** The BFF acts as a reverse proxy for Model Registry and Model Catalog APIs. Requests that pass SAR authorization are forwarded to the upstream services via REST clients attached by `AttachModelRegistryRESTClient` and `AttachModelCatalogRESTClient` middleware. Custom CA bundles can be configured for TLS connections to these upstream services (clients/ui/bff/internal/api/app.go:132-164).
- **Downstream interactions:** The structured facts record 17 integration points including Kubernetes API resources (SubjectAccessReview, SelfSubjectAccessReview, SelfSubjectRulesReview, ConfigMap, Secret, Service, Job, Namespace, ClusterRoleBinding), KServe InferenceService watches, S3-compatible storage, OCI registries, and upstream Model Registry/Catalog APIs.
- **Deployment modes:** The BFF supports two deployment modes: standalone and Kubeflow integration. In Kubeflow mode (`DeploymentMode.IsKubeflowMode()`), namespace selection, settings, and catalog management endpoints are disabled as these are provided by the Kubeflow Central Dashboard (clients/ui/bff/internal/api/app.go:306-363).

- **Multi-tier architecture:** The system follows a BFF (Backend-for-Frontend) pattern where the UI BFF acts as a secure gateway, performing Kubernetes SAR authorization before proxying requests to backend Model Registry and Model Catalog services. The BFF supports custom CA bundles for upstream TLS connections (clients/ui/bff/internal/api/app.go:132-164).
- **Plugin system:** The catalog server uses a plugin-based architecture (`catalog/internal/plugin/server.go`) where catalog plugins register routes dynamically, support lifecycle management (init/start/stop), leader election notification (`NotifyLeader`), and reconnection after database schema recreation (`Reconnect`).
- **Authorization model:** The BFF enforces authorization through Kubernetes-native mechanisms: SubjectAccessReview (SAR) for server-side checks via the internal client's service account, and SelfSubjectAccessReview (SSAR) for token-based user-scoped checks. A notable gap is that agent catalog endpoints (`/api/v1/agent_catalog/*`) lack explicit SAR authorization, relying only on namespace attachment (clients/ui/bff/internal/api/app.go:346-349).
- **Security and network evidence:** 12 authentication rules across BFF, catalog server, and controller manager; 6 secret/credential references; 0 ingress identities; 3 egress destinations (Kubernetes API, S3 storage, OCI registries). The model-registry binary is built with FIPS compliance (`GOEXPERIMENT=strictfipsruntime`). The BFF runs as nonroot (65532) on distroless, and model-registry runs as user 1001 on UBI9-minimal.
