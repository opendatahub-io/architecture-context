## Purpose

**Short**: Envoy External Processing (ExtProc) gRPC server that provides a plugin-based pipeline for pre-processing, profile-based routing, and post-processing of LLM inference requests in the llm-d inference stack.

**Detailed**: llm-d-inference-payload-processor implements an Envoy ExtProc gRPC service that intercepts inference requests flowing through an Envoy proxy. It uses a configurable plugin framework with 15 in-tree plugins organized into pre-processing, profile picking, per-profile request/response handling, and post-processing stages. The PayloadProcessorConfig type (uses kubebuilder markers for YAML deserialization but is not registered as a live CRD) defines the plugin pipeline: plugins are instantiated from factory registrations, organized into named profiles, and executed in order. Plugin categories include request processors (body-field-to-header, base-model-extractor), model selectors (model-group filter, random/max-score/weighted-random pickers, inflight-requests/session-affinity/cost-guard scorers), response processors (model-name-to-header), and datalayer components (request-metadata extractor, request-cost-metadata extractor, model-config-collector datasource). A controller-runtime manager watches ConfigMaps labeled `inference.llm-d.ai/ipp-managed: "true"` to resolve base model to adapter mappings. The dev/e2e deployment includes an Envoy proxy that routes requests to model server simulators based on the `X-Gateway-Base-Model-Name` header set by the payload processor.

## Data Flows

- **Entry and service surface:** Client HTTP requests enter through the Envoy proxy on port 8081. Envoy's `ext_proc` filter sends gRPC callouts to the payload-processor on port 9004 for request processing before routing to backend model servers.
- **ExtProc processing pipeline:** The payload-processor executes a configurable plugin pipeline: pre-processing plugins (e.g., body-field-to-header, base-model-extractor) run first, then a profile picker selects a named profile, the profile's request plugins (including model-selector with filter/scorer/picker stages) execute, and finally post-processing and response-headers plugins process the response path.
- **Model routing:** After ExtProc processing, Envoy routes the request to a model server cluster based on the `X-Gateway-Base-Model-Name` header (set by the base-model-extractor plugin). In the dev/e2e configuration, this routes to either the llama_cluster (vllm-llama3-8b-instruct:8000) or deepseek_cluster (vllm-deepseek-r1:8000), with llama_cluster as the default fallback.
- **Control plane:** The controller-runtime manager maintains a cache of ConfigMaps (filtered by NAMESPACE env var when set) and reconciles changes to ConfigMaps labeled `inference.llm-d.ai/ipp-managed: "true"` to update base model to adapter mappings used by the base-model-extractor plugin.
- **Observability:** Prometheus metrics are served on port 9090 via the controller-runtime metrics server. OpenTelemetry tracing (when enabled via --tracing flag) exports spans via OTLP gRPC or stdout.
- **Security context:** 5 authentication rules, 0 secret references describe the enforcement surface. The ExtProc gRPC port supports optional TLS; the metrics endpoint supports optional Kubernetes-native auth. Dev deployments disable both. No secrets are referenced.
