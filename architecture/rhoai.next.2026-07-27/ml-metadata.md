## Purpose

**Short**: ML Metadata (MLMD) is a gRPC metadata store server that tracks artifacts, executions, contexts, and lineage for ML pipelines in RHOAI.

**Detailed**: ml-metadata provides a gRPC-based metadata store service (`MetadataStoreService`) for recording and querying ML workflow metadata. The server binary (`metadata_store_server`) exposes ~45 RPCs for managing typed artifacts, executions, contexts, events, and lineage subgraphs. It supports MySQL, PostgreSQL, and SQLite database backends with optional TLS/mTLS transport security. The Python package provides client bindings (`MetadataStore` class) for programmatic access. In RHOAI, the server is deployed as the `odh-mlmd-grpc-server` container on port 8080, built from UBI9 base images via Bazel and Konflux pipelines.

## Data Flows

- **Runtime inventory:** The server binary `metadata_store_server` listens on gRPC port 8080 (default, configurable via `--grpc_port`). Clients connect via gRPC to perform metadata CRUD operations. The server connects to a configured database backend (MySQL, PostgreSQL, or in-memory fake) for persistence.
- **Startup sequence:** On startup, the server parses command-line flags to determine database backend configuration (`--metadata_source_config_type`: default, config_file, mysql, postgresql), creates a `MetadataStore` to initialize the schema (with retry logic up to `--metadata_store_connection_retries` attempts), then starts the gRPC server with either insecure or SSL credentials.
- **Database migration:** The server supports schema upgrade (`--enable_database_upgrade`) and downgrade (`--downgrade_db_schema_version`) via `MigrationOptions`.

## Architectural Analysis

- **Deployment shape:** The component is a single gRPC server binary (`metadata_store_server`) with a Python client library. The server is stateless beyond its database connection; all metadata is persisted in the configured database backend.
- **gRPC API surface:** The `MetadataStoreService` exposes ~45 RPCs organized into: type management (Put/Get ArtifactType, ExecutionType, ContextType), entity CRUD (Put/Get Artifacts, Executions, Contexts), event tracking (Put/Get Events), relationship management (Attributions, Associations, ParentContexts), and lineage queries (GetLineageSubgraph). The deprecated `GetLineageGraph` RPC is retained for backward compatibility.
- **Database backends:** Three backends are supported: MySQL (via libmysqlclient/MariaDB Connector), PostgreSQL, and SQLite/in-memory (fake, for testing). Backend selection is via `--metadata_source_config_type` flag or a protobuf config file.
- **Security posture:** Transport security is optional TLS with optional mutual TLS (mTLS). No application-level authentication or authorization is implemented in the server; access control is delegated to network-level policies and the platform deployment configuration.
- **Build system:** Built with Bazel 5 on UBI9, requiring C++17 for ZetaSQL compatibility. The Konflux Dockerfile pins base image digests.
- **Container identity:** Runs as non-root user 65534:65534. Container label `odh-mlmd-grpc-server`.
- **Evidence boundary:** Analyzer coverage is partial for agent_baseline, platform_semantics, python, and webhooks_source. The C++ source was classified as unsupported by the analyzer's language-specific extractors.
