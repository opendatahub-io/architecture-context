## Purpose

**Short**: Container image definitions for RHOAI Jupyter Notebook and Workbench environments with 10 runtime components, platform SDK integrations (KFP, CodeFlare, MLflow, TrustyAI), and 14 integration points.

**Detailed**: notebooks provides the source definitions and build infrastructure for Red Hat OpenShift AI (RHOAI) Jupyter Notebook and Workbench container images. It produces a family of layered notebook images—from a minimal JupyterLab environment to specialized variants pre-loaded with data science libraries (scikit-learn, pandas, matplotlib), deep learning frameworks (PyTorch, TensorFlow), LLM tooling (LLMCompressor, Transformers), TrustyAI explainability, and AMD ROCm GPU support. Each image bundles platform SDKs for Kubeflow Pipelines, CodeFlare/Ray distributed computing, MLflow experiment tracking, and OpenShift/Kubernetes API interaction. Two Go executables (buildinputs, check-payload) support the Konflux build pipeline. Authentication is delegated to the RHOAI platform (OAuth Proxy sidecar); notebook images themselves do not enforce inbound authentication.

## Data Flows

- **Entry and service surface:** Notebook pods expose JupyterLab on port 8888 (HTTP). The RHOAI Notebook Controller creates an OpenShift Route with an OAuth Proxy sidecar that terminates TLS and enforces OpenShift OAuth before forwarding requests to the Jupyter server. Users access notebooks through the RHOAI Dashboard, which manages notebook lifecycle.
- **Runtime inventory:** The repository produces 8 Python notebook image variants (minimal, datascience, pytorch, pytorch+llmcompressor, tensorflow, rocm-pytorch, rocm-tensorflow, trustyai) plus a code-server variant. Two Go build utilities (buildinputs, check-payload) support the Konflux CI pipeline but are not part of the runtime notebook images.
- **Platform integration:** Notebook images bundle SDKs that make outbound connections to platform services: Kubeflow Pipelines API (pipeline submission), Kubernetes/OpenShift API (resource management), S3-compatible storage (data/artifact access), MLflow (experiment tracking), and Ray/CodeFlare (distributed compute). These connections use the pod's ServiceAccount token or user-configured credentials.
- **Security context:** Authentication is platform-delegated (OAuth Proxy sidecar). 4 secret references exist in CI scripts only; runtime notebook images rely on ServiceAccount tokens and user-provided credentials for platform service access.

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Application Service. The repository produces container images (not an operator or controller). Each notebook variant is a standalone JupyterLab server pod managed by the RHOAI Notebook Controller. The 8 Python notebook variants form a layered hierarchy: minimal → datascience → specialized (pytorch, tensorflow, trustyai, etc.).
- **Image layering:** Notebook images are built on UBI9 with Python 3.12. Variants extend the minimal base with additional ML frameworks and SDKs. GPU-accelerated variants add CUDA or ROCm runtime libraries. All production dependencies are sourced from the Red Hat internal PyPI mirror (`packages.redhat.com/api/pypi/public-rhai/rhoai/3.5/cpu-ubi9/simple/`).
- **Platform integration pattern:** Notebooks are consumers (not providers) of platform services. They bundle client SDKs for multiple RHOAI components (KFP, CodeFlare, Training Operator, TrustyAI, MLflow) enabling data scientists to interact with the platform from within JupyterLab. The ODH Elyra extension adds a visual pipeline editor.
- **Security and network evidence:** Authentication is platform-delegated to the OAuth Proxy sidecar injected by the RHOAI Notebook Controller. 4 secret references exist in CI scripts only (Renovate, JIRA). No RBAC, ingress, or egress resources are defined in this repository — these are managed by the Notebook Controller and Dashboard.
- **Build infrastructure:** Two Go executables (buildinputs, check-payload) are build-time utilities for the Konflux CI/CD pipeline, not runtime components. CI testing deploys notebook pods to Kubernetes via kustomize, validates behavior, and undeploys (source: ci/cached-builds/make_test.py).
- **Evidence boundary:** Analyzer coverage is partial for kustomize, platform_semantics, python, and source surfaces. Integration points are inferred from bundled SDK dependencies in requirements files, not from runtime code analysis. Actual ports, protocols, and encryption for outbound connections depend on runtime configuration. Dynamic behavior outside the extracted literal and manifest evidence is not asserted.
