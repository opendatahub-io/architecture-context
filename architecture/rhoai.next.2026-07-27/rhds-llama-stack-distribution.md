## Purpose

**Short**: Red Hat distribution of Meta's Llama Stack framework, providing a containerized AI/ML inference server with pluggable providers for inference, safety, evaluation, and vector storage on RHOAI.

**Detailed**: rhds-llama-stack-distribution packages the Llama Stack framework (version 0.5.0+rhai0 from opendatahub-io/llama-stack) as a RHEL 9-based container image for Red Hat OpenShift AI. It exposes a unified HTTP API on port 8321 that serves 10 API surfaces — agents, batches, datasetio, eval, files, inference, safety, scoring, tool_runtime, and vector_io — backed by a configurable matrix of inline and remote providers. The distribution integrates with vLLM, AWS Bedrock, IBM WatsonX, Azure OpenAI, Google Vertex AI, and OpenAI for inference; Milvus, PgVector, Qdrant, and FAISS for vector storage; TrustyAI for safety guardrails, LM evaluation, RAGAS evaluation, and Garak security benchmarking; PostgreSQL for persistent state; and optional OpenTelemetry instrumentation for observability. Provider activation is environment-variable-driven and all are conditionally enabled.

## Data Flows

1. **Client → Llama Stack Server (port 8321)**: Clients send HTTP requests to the Llama Stack API (OpenAI-compatible or native Llama Stack endpoints).
2. **Llama Stack Server → Inference Providers**: Inference requests are routed to the configured provider (vLLM, Bedrock, WatsonX, Azure, Vertex AI, OpenAI, or inline sentence-transformers).
3. **Llama Stack Server → Safety Provider**: Content is optionally routed through TrustyAI FMS orchestrator for safety guardrail evaluation.
4. **Llama Stack Server → PostgreSQL**: Agent state, inference records, file metadata, conversations, and registry metadata are persisted to PostgreSQL via KV and SQL storage backends.
5. **Llama Stack Server → Vector DB**: Vector embeddings are stored/queried via inline Milvus (default) or remote Milvus/PgVector/Qdrant/FAISS.
6. **Llama Stack Server → Evaluation**: Evaluation workloads are dispatched to TrustyAI LMEval, RAGAS, or Garak providers, optionally via Kubeflow Pipelines.
7. **Llama Stack Server → OTLP Collector** (optional): When `OTEL_SERVICE_NAME` is set, traces and metrics are exported via OpenTelemetry.

## Architectural Analysis

- **Deployment shape:** Single-container server process running `llama stack run` with a configuration-driven provider architecture. The container image is built for RHEL 9 CPU on both x86_64 and aarch64.
- **Provider model:** All APIs use a pluggable provider pattern activated by environment variables. Providers are categorized as `inline::` (in-process) or `remote::` (HTTP/gRPC clients to external services). External provider modules are installed via pip as versioned packages.
- **Storage architecture:** Dual-backend PostgreSQL storage — `kv_postgres` for key-value state (registry, vector_io persistence, agent state) and `sql_postgres` for structured records (inference_store, files_metadata, agent responses, conversations). Both point to the same PostgreSQL instance by default.
- **Configuration model:** Single `config.yaml` with environment variable interpolation using `${env.VAR:=default}` syntax and conditional provider activation via `${env.VAR:+provider_id}` patterns.
- **Telemetry:** Built-in telemetry support (`telemetry: enabled: true`) with optional OpenTelemetry instrumentation for OTLP export of traces and metrics.
- **Security boundary:** The server itself does not configure endpoint authentication — this is expected to be enforced by the platform layer. Remote provider credentials are passed as environment variables.
- **Evidence boundary:** Analyzer coverage is partial for platform_semantics and webhooks_source. HTTP endpoints beyond `/v1/health`, `/v1/models`, and `/v1/chat/completions` are inferred from the `apis:` list in config.yaml; exact path routing is defined by the upstream llama-stack framework and was not directly observed in this distribution's source.
