## Purpose

**Short**: ai-gateway-operator is a Kubernetes module operator that manages the AIGateway platform component, orchestrating batch inference gateway and Models-as-a-Service sub-components with integrated API governance, service mesh, and observability.

**Detailed**: ai-gateway-operator is a standalone module operator for the RHOAI platform, built on controller-runtime v0.24.1 and the opendatahub-operator/v2 reconciler framework. It reconciles a singleton cluster-scoped `AIGateway` custom resource (`default-aigateway`) that controls the lifecycle of two sub-components: the batch-gateway operator (for `batch.llm-d.ai/llmbatchgateways`) and the MaaS controller (for external model/provider management via `maas.opendatahub.io` and `inference.opendatahub.io` APIs). Each sub-component is independently toggled via `managementState` (Managed/Removed, default Removed). The operator manages kustomize-rendered manifests, integrates with Kuadrant for API governance (AuthPolicies, RateLimitPolicies), Istio for service mesh networking, cert-manager for TLS certificates, Gateway API for HTTP routing, prometheus-operator and OpenTelemetry for observability, and Perses for dashboarding. Its documented interface surface contains 4 API identities (1 CRD, 2 HTTP health endpoints, 1 metrics endpoint), and 36+ integration points across the platform.

- **Downstream interactions:** The operator interacts with 36+ integration points spanning Kubernetes API resources, platform CRDs (cert-manager, Gateway API, Kuadrant, Istio, OpenTelemetry, Perses, Authorino), and ODH/RHOAI platform components (DSCInitialization, KServe, opendatahub-operator). - **Security context:** 4 authentication rules describe the enforcement boundaries: ServiceAccount token for Kubernetes API, unauthenticated health probes, and RBAC-protected metrics. ConfigMaps and Secrets are read fresh (not cached) per `cmd/operator/operator.go:116-119`.

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Kubernetes Operator / Controller, represented by 1 Deployment and 2 managed sub-components (batch-gateway and models-as-a-service), each independently controlled via `managementState` fields on the singleton `AIGateway` CR.
- **Module operator pattern:** The operator implements the ODH module operator pattern: it wraps the controller-runtime manager with `odhmanager.New()` to provide manifests base path resolution, uses kustomize rendering for sub-component deployment, and reports module version and manifest source status through the `AIGateway.status.module` field.
- **Control-plane surface:** The document contains 1 CRD identity, 130 RBAC rules, and 6 role bindings, exposing the extracted Kubernetes API and authorization footprint. Delegated RBAC roles (admin/editor/viewer) are provided for cluster administrators to manage `AIGateway` CR access for users.
- **Security and network evidence:** 4 authentication rules describe enforcement across Kubernetes API (ServiceAccount), health probes (unauthenticated), and metrics (TokenReview/RBAC). The metrics service uses TLS on port 8443. ConfigMaps and Secrets are excluded from the client cache for freshness and security (`cmd/operator/operator.go:116-119`). Cache scope is restricted to the applications namespace and cluster-scoped resources.
- **Platform integration depth:** The operator's RBAC footprint spans 20+ API groups covering API governance (Kuadrant), service mesh (Istio), TLS (cert-manager), observability (prometheus-operator, OpenTelemetry, Perses, Istio Telemetry), authorization (Authorino), network policy, and inference serving (KServe), reflecting a deep platform integration role.
- **Evidence boundary:** Analyzer coverage is partial for kustomize, platform_semantics, source, and webhooks_source. Dynamic behavior outside the extracted literal and manifest evidence is not asserted. Kustomize configMapGenerator, image transforms, and replacements are not resolved.
