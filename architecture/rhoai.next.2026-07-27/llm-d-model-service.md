## Purpose

**Short**: Kubernetes operator that declaratively provisions and maintains the resources needed to serve a base model for disaggregated prefill/decode inference, including workloads, Gateway API routing, and RBAC.

**Detailed**: llm-d-model-service is a Kubernetes operator built with controller-runtime (Kubebuilder v4 scaffold) that reconciles `ModelService` custom resources in the `llm-d.ai` API group. When a user creates a ModelService CR, the controller dynamically provisions a complete inference serving stack: separate prefill and decode Deployments, an Endpoint Picker (EPP) Deployment, Services, ServiceAccounts, RoleBindings, HTTPRoutes, InferencePools, InferenceModels, and ConfigMaps. All dynamically created resources are set as owned children of the ModelService CR for garbage collection.

The operator supports a two-tier configuration model: platform operators define reusable `BaseConfig` presets via ConfigMaps that establish shared defaults (container images, resource requirements, routing templates), while model owners create ModelService CRs that reference these presets and override model-specific fields. A Go template interpolation engine (powered by Sprig) enables dynamic value substitution in both the BaseConfig and ModelService specs. The merging is performed using the `mergo` library with custom transformers for container slices, Gateway API ParentRefs, and BackendRefs.

The operator integrates with the Kubernetes Gateway API Inference Extension (v0.3.0) for routing, creating InferencePool and InferenceModel resources that connect to an EPP deployment for endpoint selection. It supports three model artifact storage backends: HuggingFace (`hf://`), PVC (`pvc://`), and OCI images (`oci://`, partially implemented). The project is deprecated as of July 2025 in favor of a Helm chart approach at `llm-d-incubation/llm-d-modelservice`.

## Architectural Analysis

### Controller Reconciliation Pattern

The ModelServiceReconciler follows a declarative reconciliation pattern with a two-phase approach: first, it resolves and interpolates templates, then it creates or updates all child resources. The controller uses Sprig-powered Go templates for value substitution in both the BaseConfig ConfigMap and ModelService specs, enabling platform operators to define reusable templates with variables like `{{.ModelServiceName}}`, `{{.ModelName}}`, and `{{.MountedModelPath}}`. Custom template functions include `getPort` for named port resolution.

### Merge Strategy

The merge between BaseConfig (platform defaults) and ModelService (user overrides) uses the `mergo` library with custom transformers. Container slices are merged by name (not appended), environment variables within containers are also merged by name with override semantics, and string slices (like container args) are prepended rather than appended. Gateway API ParentRefs and BackendRefs use similar name-based merge transformers. This ensures that user-specified values override platform defaults at a granular level.

### Dynamic Child Resources

The controller dynamically creates up to 13 different Kubernetes resource types per ModelService. All resources are set with owner references for automatic garbage collection. The `invokeCreateOrUpdate` method uses `controllerutil.CreateOrUpdate` with mergo-based mutate functions to achieve idempotent reconciliation. For prefill/decode Deployments, a special path handles `decoupleScaling`: when enabled, the controller does not manage replica counts, allowing HPA or other autoscalers to control scaling.

### Model Artifact Support

Three URI schemes are supported for model loading:
- **`pvc://`**: Mounts an existing PVC as a read-only volume at `/model-cache`
- **`hf://`**: Creates an EmptyDir volume with configurable size limit; injects `HF_TOKEN` env var from a referenced Secret and sets `HF_HOME` to the mount path
- **`oci://`**: Partially implemented (constants defined but volume creation not complete)

### Deprecation Status

The project is deprecated as of July 2025 (commit 403e983). The core functionality is being replaced by a Helm chart at `llm-d-incubation/llm-d-modelservice`. This is architecturally significant as it represents a shift from operator-based to Helm-based lifecycle management for the ModelService abstraction.

### Security Observations

- The controller has broad cluster-wide RBAC permissions including write access to Deployments, Services, HTTPRoutes, InferencePools, InferenceModels, and RoleBindings across all namespaces.
- HTTP/2 is disabled by default as a mitigation for CVE-2023-44487 (HTTP/2 Rapid Reset) and CVE-2023-39325 (HTTP/2 Stream Cancellation).
- The metrics endpoint is protected by controller-runtime's `WithAuthenticationAndAuthorization` filter, which delegates authentication and authorization to the kube-apiserver via TokenReview and SubjectAccessReview.
- The upstream Dockerfile uses `CGO_ENABLED=0` which would fail FIPS compliance checks. No Konflux Dockerfile exists; downstream builds would need modification.
- BaseConfig ConfigMaps support cross-namespace reads (when `baseConfigMapRef.namespace` is set), which could be a security consideration in multi-tenant environments.
