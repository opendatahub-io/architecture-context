## Purpose

**Short**: Kubernetes operator that manages ModelRegistry custom resources, provisioning model registry REST services, PostgreSQL/MySQL databases, kube-rbac-proxy sidecars, Gateway API HTTPRoutes, OpenShift Routes, and a centralized model catalog with associated RBAC and network policies.

**Detailed**: model-registry-operator is a controller-runtime-based Kubernetes operator that reconciles ModelRegistry custom resources (v1alpha1, deprecated; v1beta1, storage version) to deploy and manage model registry instances in RHOAI. The operator runs two controllers: ModelRegistryReconciler (manages per-registry Deployments with rest-container and kube-rbac-proxy sidecar, PostgreSQL databases, Services, Routes, HTTPRoutes, RBAC, and NetworkPolicies) and ModelCatalogReconciler (manages a centralized model-catalog Deployment with kube-rbac-proxy, PostgreSQL backend, and catalog source ConfigMaps). The operator supports kube-rbac-proxy (current default in v1beta1) performing TokenReview/SubjectAccessReview, with automatic migration from deprecated OAuthProxy and Istio configurations. It integrates with Gateway API for platform ingress via a configurable data-science-gateway, OpenShift Routes for direct HTTPS exposure, and OpenShift TLS security profiles for webhook and metrics server hardening. A StorageMigrationManager handles CRD storage version migrations between v1alpha1 and v1beta1. Source: `cmd/main.go:303-342,386-387`

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Kubernetes Operator / Controller, represented by 5 architecture components (1 operator deployment, 2 catalog components, 2 per-registry components) and 7 service identities.
- **Controller architecture:** Two independent controllers run within the same manager: ModelRegistryReconciler (reconciles ModelRegistry CRs into per-instance deployments) and ModelCatalogReconciler (reconciles a singleton model-catalog deployment). Both share the same template engine for resource generation. Source: `cmd/main.go:303-342`
- **CRD version strategy:** v1beta1 is the storage version (implements conversion.Hub). v1alpha1 is deprecated with a deprecation warning. A conversion webhook at /convert handles bidirectional conversion. StorageMigrationManager monitors migration.k8s.io StorageVersionMigration resources. Source: `api/v1beta1/modelregistry_types.go:368,393`, `cmd/main.go:386-387`
- **Authentication proxy evolution:** The operator implements a three-stage migration chain: Istio (v1alpha1, fully removed) -> OAuthProxy (v1alpha1 default on OpenShift) -> KubeRBACProxy (v1beta1 default on OpenShift). Migrations are automatic in the mutating webhook. v1beta1 spec enforces mutual exclusion: `!(has(self.oauthProxy) && has(self.kubeRBACProxy))`. Source: `api/v1beta1/modelregistry_types.go:303`, `api/v1beta1/modelregistry_webhook.go:179-199`
- **Database provisioning:** v1beta1 adds PostgreSQL auto-provisioning via `spec.postgres.generateDeployment=true`, with CEL validation rules ensuring host/hostAddress are not set when auto-provisioning is enabled. v1alpha1 auto-provisions when no host is specified (legacy behavior). MySQL requires explicit external host. Source: `api/v1beta1/modelregistry_types.go:46-48`
- **TLS hardening:** On OpenShift, the operator fetches the cluster's TLS security profile (TLSProfileSpec) and TLS adherence policy, applies them to both the webhook server and metrics server, and registers a SecurityProfileWatcher that triggers graceful pod restart when profiles change.
