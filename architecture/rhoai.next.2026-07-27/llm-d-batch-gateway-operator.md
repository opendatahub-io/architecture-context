## Purpose

**Short**: Kubernetes operator that manages LLMBatchGateway custom resources, deploying and reconciling a multi-component batch inference gateway consisting of an API server, request processor, garbage collector, and optional async processor via Helm chart rendering.

**Detailed**: llm-d-batch-gateway-operator is a controller-runtime-based Kubernetes operator that watches `LLMBatchGateway` custom resources (batch.llm-d.ai/v1alpha1) and renders two embedded Helm charts (batch-gateway and async-processor) to deploy and manage four child workloads: an HTTP API server for batch job submission, a request processor that dispatches inference requests (sync via HTTP or async via Redis message queue), a garbage collector for expired jobs and files, and an optional async processor (deployed when `dispatchMode=async`). The operator requires four pinned component images injected via environment variables (`LLM_D_BATCH_GATEWAY_APISERVER_IMAGE`, `LLM_D_BATCH_GATEWAY_PROCESSOR_IMAGE`, `LLM_D_BATCH_GATEWAY_GC_IMAGE`, `LLM_D_ASYNC_IMAGE`) and manages associated Services, ConfigMaps, ServiceAccounts, Secrets (cross-namespace sync via ReferenceGrant), HTTPRoutes, cert-manager Certificates, and Prometheus monitoring resources. A separate MetricsController reconciles operator-level ServiceMonitors, PodMonitors, and PrometheusRules when `POD_NAMESPACE` is set.

## Data Flows

- **Operator reconciliation loop:** The operator controller manager watches LLMBatchGateway CRs (primary) and owned resources (Deployments, Services, ConfigMaps, ServiceAccounts). On reconciliation, it renders embedded Helm charts (`/charts/batch-gateway` and `/charts/async-processor`) with values derived from the CR spec and pinned component images to produce child Deployment manifests. The operator also watches Secrets (for credential sync) and conditionally watches ReferenceGrants (for cross-namespace Secret authorization) and Prometheus monitoring resources.
- **Managed component topology:** Each LLMBatchGateway CR produces up to 4 Deployments: API Server (batch job HTTP API), Processor (inference dispatch), GC (job/file cleanup), and optionally Async Processor (Redis queue-based dispatch). These workloads connect to external database (PostgreSQL/Redis/Valkey), file storage (S3/PVC), and inference gateways as configured in the CR spec.
- **Cross-namespace secret sync:** When `spec.secretRef.namespace` references a Secret in a different namespace, the operator checks for a ReferenceGrant authorizing the reference, then copies the Secret into the CR's namespace as `<gateway-name>-credentials` for workload pod mounting.
- **Monitoring pipeline:** The MetricsController (started when `POD_NAMESPACE` is set) reconciles ServiceMonitors, PodMonitors, and PrometheusRules in the operator's namespace for Prometheus scraping of both operator and managed workload metrics.
- **Security context:** 4 authentication rules describe the enforcement applied around operator endpoints and API access. Managed workload authentication to downstream services (database, storage, inference) is configured via the CR's `spec.secretRef` Secret; exact mechanisms depend on the child workload implementations.

## Architectural Analysis

- **Deployment shape:** The normalized deployment type is Kubernetes Operator / Controller. The operator itself runs as a single Deployment (`manager` container) and dynamically creates up to 4 child Deployments per LLMBatchGateway CR via Helm chart rendering. Two embedded Helm charts (`batch-gateway` and `async-processor`) produce the child workload manifests.
- **Multi-component orchestration:** The operator uses a Helm-rendering pattern rather than static manifest embedding. Component images are pinned via environment variables (`LLM_D_BATCH_GATEWAY_APISERVER_IMAGE`, `LLM_D_BATCH_GATEWAY_PROCESSOR_IMAGE`, `LLM_D_BATCH_GATEWAY_GC_IMAGE`, `LLM_D_ASYNC_IMAGE`), decoupling image lifecycle from operator releases. The `syncPeriod` (default 5m) ensures drift detection for out-of-band changes.
- **Dispatch modes:** The processor supports two dispatch modes: `sync` (direct HTTP to inference gateway) and `async` (Redis sorted-set queues with the async-processor handling dequeue and dispatch via inference gateway EPP). Async mode is gated by CRD validation (`spec.processor.asyncConfig` required when `dispatchMode=async`).
- **Control-plane surface:** The document contains 1 CRD identity, ClusterRole rules spanning 11 API groups/resources, aggregate roles for admin/edit/view RBAC, and leader election via coordination.k8s.io leases.
- **Security and network evidence:** 4 authentication rules cover health probes (unauthenticated), metrics (controller-runtime authn/authz), and Kubernetes API (ServiceAccount RBAC). Cross-namespace Secret access requires explicit ReferenceGrant authorization. The CRD enforces `tlsInsecureSkipVerify` is disallowed via CEL validation rules.
- **Evidence boundary:** Analyzer coverage is partial for kustomize (configMapGenerator, replacements not resolved), platform_semantics, source (dynamic routes/watched expressions not resolved), and webhooks_source. Managed workload internal behavior is described from CRD spec structure; runtime behavior of child workloads is not directly inspected.
