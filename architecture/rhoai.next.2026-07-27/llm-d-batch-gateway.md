## Purpose

**Short**: Batch Gateway is a multi-component Go service that provides an OpenAI-compatible API for submitting, tracking, and processing large-scale batch inference jobs in Kubernetes environments.

**Detailed**: The llm-d-batch-gateway implements a high-performance batch inference processing system composed of three independently deployable components: an API server, a batch processor, and a garbage collector. The API server exposes OpenAI-compatible `/v1/batches` and `/v1/files` REST endpoints for job submission, status tracking, and file management. The batch processor dequeues jobs from a Redis/Valkey priority queue, builds per-model execution plans, dispatches inference requests to downstream llm-d inference gateways with adaptive AIMD-based concurrency control, and writes results to S3-compatible or filesystem storage. The garbage collector periodically removes expired jobs and files, and includes an orphan reconciler that recovers batch jobs left in non-terminal states after processor crashes.

The system uses a pluggable data layer with PostgreSQL for job and file metadata persistence, Redis/Valkey for priority queuing, event channels, in-flight tracking, and ephemeral status updates, and S3-compatible or local filesystem for batch input/output file storage. Each component is deployed as a separate Kubernetes Deployment via Helm charts, with shared configuration for database and storage backends. The system supports both synchronous (direct HTTP dispatch) and asynchronous (llm-d-async via Redis queues) inference dispatch modes. Tenant isolation is enforced at the application level through HTTP header-based tenant extraction and per-request tenant ID validation on all API operations.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Tenant ID extracted from HTTP header; every CRUD operation validates resource's TenantID matches request context TenantID | Application (batch_handler.go, file_handler.go) | No authentication within the application itself; relies on upstream proxy to authenticate and inject tenant header. Spoofable if no upstream auth proxy is deployed. |
| Data storage | Tenant ID stored as column/field in PostgreSQL and Redis; all queries filtered by tenant ID | Application (database layer) | Shared database instances across tenants; tenant isolation relies on application-level query filtering |
| Network traffic | No per-tenant NetworkPolicy | N/A | All tenants share the same network path |
| Compute & resources | No per-tenant resource limits | N/A | All tenants share the same processor workers and concurrency limits |
| Configuration & secrets | Shared Secret (batch-gateway-secrets) across all tenants | Kubernetes | Single set of database and storage credentials |
| API scoping | Tenant-filtered queries at database level; SHA256-hashed tenant ID for filesystem paths | Application | File storage uses SHA256(tenant_id) as directory prefix for isolation |

## Architectural Analysis

The batch gateway follows a producer-consumer architecture with clear separation of concerns across three independently deployable components. The API server (producer) accepts client requests and enqueues batch jobs, while the processor (consumer) dequeues and executes them. The GC handles lifecycle cleanup and crash recovery.

**Dispatch architecture**: The processor supports two dispatch modes. In synchronous mode, the DirectDispatcher (or AIMDDispatcher when AIMD is enabled) sends HTTP POST requests directly to inference gateways. In asynchronous mode, the AsyncDispatcher submits requests to llm-d-async Redis queues and polls for results. The AIMD dispatcher implements per-endpoint adaptive concurrency control that backs off on 429/5xx responses and additively increases on success, protecting interactive traffic from batch burst.

**Concurrency control**: Three-level semaphore hierarchy — worker tokens (limits concurrent jobs), global semaphore (limits total in-flight requests), and per-endpoint adaptive semaphores (AIMD-controlled). This layered approach prevents any single dimension from overwhelming the system.

**Fault tolerance**: The processor implements crash recovery at startup by scanning the local work directory for stale job directories, cross-referencing with database state, and applying appropriate recovery actions (re-enqueue, fail with partial results, or mark expired). The GC reconciler provides secondary recovery by detecting orphaned non-terminal jobs whose processor has not heartbeated within the staleness threshold.

**Status update patterns**: The system uses CAS (Compare-And-Swap) for persistent status transitions in PostgreSQL, preventing race conditions between multiple processors and the GC reconciler. Lightweight progress updates use Redis with TTL for fast read access without PostgreSQL write amplification.

**Security boundary**: The application does not perform authentication. It extracts a tenant identifier from a configurable HTTP header (default X-MaaS-Username), which is expected to be injected by an upstream authentication proxy (e.g., Envoy ext_authz). All data access is then filtered by this tenant ID. The README documents that batch API admission and per-model inference authorization should be enforced on separate routes at the gateway level.

**Build considerations for RHOAI**: The current Dockerfiles use `CGO_ENABLED=0` with distroless/static base images, which would not pass FIPS check-payload validation. No Konflux-specific Dockerfiles exist on this branch. The downstream RHOAI release branch would need Konflux Dockerfiles with UBI base images, `CGO_ENABLED=1`, and GOEXPERIMENT=strictfipsruntime for FIPS compliance.
