## Purpose

**Short**: GPU-accelerated text generation inference server for serving large language models (LLMs) with gRPC and HTTP interfaces, continuous batching, and tensor parallelism.

**Detailed**: Text Generation Inference Server (TGIS) is an early fork of Hugging Face's text-generation-inference, developed internally at IBM and significantly diverged from the original. It provides a high-performance inference serving layer for large language models in the RHOAI platform.

The server uses a multi-process architecture: a Rust **launcher** spawns N Python **shard** processes (one per GPU for tensor parallel inference) and a Rust **router** process. The router exposes both a gRPC API (for model inference, tokenization, and management) and an HTTP API (for health checks and Prometheus metrics). It implements continuous dynamic batching, request queuing, and validation before forwarding inference requests to the Python shards via Unix domain sockets.

The Python server implements a pluggable inference engine abstraction supporting seven backends: HuggingFace Transformers, HuggingFace Accelerate, Optimum BetterTransformer, Optimum ONNX Runtime, IBM Foundation Model Stack (FMS), TGIS Native (custom optimized kernels), and DeepSpeed. It supports Flash Attention v2, Paged Attention, PyTorch 2.0 compilation, GPTQ and BitsAndBytes quantization, and distributed tensor parallelism via NCCL/GLOO.

## Architectural Analysis

TGIS follows a sophisticated multi-process, multi-language architecture optimized for GPU inference serving:

**Process Model**: The Rust launcher orchestrates the system by spawning N Python shard processes (one per GPU) and one Rust router process. Each shard binds a gRPC server to a Unix domain socket. The launcher monitors all processes via channels and implements graceful shutdown on SIGTERM, writing termination reasons to `/dev/termination-log` for Kubernetes observability.

**Batching Strategy**: The router implements continuous dynamic batching — incoming requests are queued and assembled into batches that maximize GPU utilization. The batcher supports both padded (rectangular) and flash-attention (packed) batch formats. Requests can "overtake" others in the queue if they fit within a 1-second cutoff window, improving throughput for short requests. A configurable max prefill padding ratio (default 20%) prevents excessive padding waste.

**Inference Engine Abstraction**: The Python server's pluggable engine architecture (`BaseInferenceEngine`) allows seven backends without changing the serving logic. The `tgis_native` engine is required for advanced features (Flash Attention, Paged Attention, tensor parallelism) and uses custom model implementations with optimized kernels. Engine selection cascades through model type, attention mode, and shard count to determine the appropriate backend automatically.

**Memory Management**: GPU memory is managed through per-process memory fraction limits, automatic memory scaling estimation (quadratic/linear models fitted from probe runs), and optional batch compaction before prefill. Paged attention manages KV cache slots with explicit allocation and deallocation, while a prompt prefix cache (LRU, 512MB default) stores reusable prompt embeddings on disk and in memory.

**Upstream Divergence**: This repo is an early fork of HuggingFace TGI that diverged significantly. Key differences include: gRPC instead of REST API, batch input support, independent tokenization API, configurable inference engine abstraction, and more sophisticated dynamic batch sizing. Upstream changes after TGI v1.0 are not incorporated due to license changes (post-v1.0 uses a non-Apache license).

**Operational Considerations**: The Deployment manifests configure generous startup probes (12-minute timeout with 24 retries at 30s intervals) to accommodate large model loading times. The headless Service (ClusterIP: None) suggests use within a StatefulSet-like pattern or direct pod addressing by the model serving platform. GPU resource requests default to 8 NVIDIA GPUs with 512Gi memory, reflecting the large model workloads this service targets.

**Risk: rustls vs OpenSSL for FIPS**: The Rust router uses rustls (pure-Rust TLS) rather than OpenSSL-backed TLS. While the binary is dynamically linked and OpenSSL is present in the UBI9 base image, the Rust TLS stack does not use OpenSSL at runtime. This may create a FIPS compliance gap for the gRPC/HTTP endpoints if FIPS-validated cryptography is required. The Python server communicates over local Unix sockets only (no TLS).
