## Diagram Descriptions

### Component Dependency Graph
Shows how platform components depend on each other across 6 groups: meta-operator, core platform services, inference serving, llm-d disaggregated inference, ML workflow, distributed training, and trust/safety. Central components (most dependencies) are highlighted: rhods-operator (orchestrates all), KServe (11 components reference), gateway-api-inference-extension (root of dependency tree), and odh-dashboard (18 outgoing dependencies). Useful for understanding blast radius of changes and planning upgrades.

### Platform Network Topology
Complete network architecture showing the 5-tier namespace model: external ingress (Gateway API with data-science-gateway), operator tier (redhat-ods-operator), platform services tier (redhat-ods-applications), user workload tier (project namespaces), and observability tier (redhat-ods-monitoring). Includes exact port numbers, protocols, encryption, and authentication mechanisms. Documents all 218 admission webhook endpoints and the cert-manager/OPA cert-controller TLS provisioning.

**Two formats provided**:
- **Mermaid (.mmd)**: Visual diagram with color-coded trust zones. Great for presentations and architecture discussions.
- **ASCII (.txt)**: Precise text format with no ambiguity. Required for SAR (Security Architecture Review) submissions and compliance documentation.

Both formats contain the same information — use Mermaid for visual clarity, ASCII for security reviews.

### Cross-Component Workflows
5 sequence diagrams showing end-to-end user workflows:
1. **Model Deployment via Dashboard** — Dashboard → KServe → odh-model-controller → Gateway API → inference
2. **Distributed Training Job Submission** — Dashboard → Kueue quota admission → training-operator/kuberay → gang scheduling
3. **ML Pipeline Execution** — Dashboard → DS Pipelines → Argo Workflows → ml-metadata → Model Registry → KServe
4. **LLM Disaggregated Inference (llm-d)** — Gateway → EPP ext_proc → llm-d-inference-scheduler → prefill → NIXL KV-cache transfer → decode
5. **Models-as-a-Service API Key Flow** — Gateway → Kuadrant AuthPolicy (API key + TokenReview + OIDC JWT) → MaaS → KServe → EPP routing

### Platform Security Overview
Visual representation of security architecture including:
- **8 authentication mechanisms**: SA tokens, kube-rbac-proxy, OAuthProxy, Kuadrant AuthPolicy, TokenReview, OpenShift cluster TLS profile, cert-manager CA injection, OPA cert-controller
- **218 admission webhooks** across 24 components, all with failurePolicy: Fail
- **RBAC**: 1903 entries across 39 operator/controller components
- **Container security**: UBI9-minimal, non-root, capability drop ALL, FIPS (selective), filtered informers
- **TLS configuration**: 9443 (webhooks), 8443 (metrics), 443 (gateway), 5600 (NIXL)
- **Cross-component coordination risks**: 3-way pod mutation, 3-way RayCluster admission, dual notebook injection

### Platform Observability
Maps all monitoring and observability endpoints:
- **23 Prometheus scrape targets** via ServiceMonitor/PodMonitor CRDs, all on :8443/TCP HTTPS
- **Health probes**: Liveness and readiness on :8080 or :8081 for all operator components
- **Monitoring infrastructure**: Prometheus + Thanos + alerting rules in redhat-ods-monitoring namespace
- **Metrics auth transition**: Moving from kube-rbac-proxy sidecars to controller-runtime native authn/authz
- **PodMonitor injection**: rhods-operator webhook injects PodMonitors for prometheus-operator

### Platform Maturity Dashboard
High-level metrics: 87 components, 39 operators, 127 CRD kinds, 218 webhooks, 1903 RBAC entries, 815 HTTP endpoints, 191 gRPC services, 102 container images. Security posture: all webhooks failurePolicy Fail, selective FIPS, UBI9-minimal, non-root. Deployment: leader election HA, disconnected support (RELATED_IMAGE + digest pinning), multi-architecture (amd64 full, arm64/ppc64le/s390x partial). Key rhoai.next changes: LLMInferenceService CRDs, MaaS multi-tenant CRDs, agents-operator, MCP integration, llm-d disaggregated inference (12 components).
