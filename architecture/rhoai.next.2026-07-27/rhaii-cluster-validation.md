## Purpose

**Short**: CLI validation tool that deploys ephemeral check Jobs to GPU nodes and validates cluster readiness for AI/ML workloads on RHOAI.

**Detailed**: rhaii-cluster-validation is a Cobra CLI (`kubectl-rhaii_validate`) that validates GPU cluster readiness for AI/ML workloads. It operates as a controller that connects to the Kubernetes API via kubeconfig, creates ephemeral RBAC and namespace resources, then deploys per-node Job pods to execute hardware and network validation checks. Supported check modes include GPU hardware (driver version, ECC status for NVIDIA and AMD), TCP bandwidth/latency (iperf3), RDMA node checks (device discovery, NIC status, GPU-NIC-NUMA-PCIe topology), RDMA connectivity mesh (pingmesh via ibv_rc_pingpong), and RDMA bandwidth (ib_write_bw). A separate `deps` subcommand validates that prerequisite CRDs (Gateway API, InferencePool, LeaderWorkerSet, cert-manager) and operators (cert-manager, Istio, LeaderWorkerSet) are healthy. The controller creates all cluster resources ephemerally and performs deferred cleanup on exit. Platform auto-detection supports OCP, EKS, AKS, and CoreWeave.

## Data Flows

- **Runtime model:** The CLI controller runs locally (or as a pod) and connects to the Kubernetes API via kubeconfig. It creates an ephemeral namespace (`rhaii-validation` by default), deploys per-node check Job pods, waits for completion, collects results from pod logs and report ConfigMaps, then cleans up all created resources via deferred cleanup.
- **Check execution:** Per-node Job pods run the internal `run` subcommand with GPU vendor (`GPU_VENDOR`), check mode (`CHECK_MODE`), and node name (`NODE_NAME`) passed via environment variables. Results are written to stdout (collected via pod logs) and stored in a report ConfigMap (`rhaii-validate-report`) for cross-node coordination.
- **Multi-node tests:** Network and RDMA bandwidth tests use ring or star topology (configurable via `--server-node`/`--client-nodes`). The controller creates paired server/client Jobs and coordinates via the report ConfigMap and pingmesh failure ConfigMap (`rhaii-validate-pingmesh-failures`).
- **Downstream interactions:** 9 Kubernetes API integration points: ConfigMap, Namespace, ServiceAccount, Node, Pod, Job, ClusterRole, and ClusterRoleBinding CRUD operations, plus the primary client-go API connection.
- **Security context:** 2 authentication contexts (admin kubeconfig for controller, ServiceAccount for workload pods with token mount disabled). No secrets created (optional pull secret reference). On OpenShift, the privileged SCC is granted for host sysfs access and cleaned up on exit.

Creates ephemeral cluster resources during validation runs and performs deferred cleanup. The controller deploys two container images: a validator image (self-reference for per-node `run` subcommand) and a tools image (iperf3, RDMA tools).
- **Control-plane surface:** No CRDs defined. 1 ClusterRole (empty rules), 2 ClusterRoleBindings (1 static for SA, 1 dynamic OpenShift SCC). Controller operates under the invoking user's kubeconfig with admin-level permissions.
