## Purpose

**Short**: Garak red-teaming evaluation adapter for eval-hub that provides AI safety evaluation via two execution modes (simple subprocess and Kubeflow Pipelines), with 6 integration points and multi-layer authentication.

**Detailed**: llama-stack-provider-trustyai-garak is a Python package (v0.5.1) that implements the eval-hub `FrameworkAdapter` interface to integrate NVIDIA's Garak red-teaming framework with the eval-hub evaluation platform. It supports two execution modes: **simple** (runs garak as a subprocess inside the K8s Job pod) and **kfp** (delegates scan execution to a Kubeflow Pipeline using S3 for artifact transfer). The adapter reads job specifications from mounted ConfigMaps, builds and executes Garak CLI commands or submits KFP pipelines, parses results from Garak's JSONL reports, persists artifacts to OCI registries, and reports results back to eval-hub via sidecar callbacks. It supports AI safety intents (ART) with synthetic data generation (SDG) via sdg-hub, translation via HuggingFace or LLM models, and role-based API key resolution for multi-model evaluation scenarios.

## Data Flows

- **Runtime inventory:** The adapter runs within eval-hub K8s Job pods. In **simple mode**, it executes garak as a subprocess, reads results from local filesystem, and reports via eval-hub sidecar callbacks. In **KFP mode**, it submits a Kubeflow Pipeline, uploads configuration and data to S3, polls for completion, downloads results from S3, and reports via callbacks.
- **Artifact flow (KFP mode):** Config JSON and intent prompts -> S3 upload -> KFP pipeline execution -> S3 result download -> JSONL parsing -> OCI artifact persistence -> eval-hub callback.
- **ART intents flow:** Taxonomy data (from S3 or built-in) -> SDG generation via sdg-hub -> prompt normalization -> intent stub generation -> Garak scan with intents probes -> AVID report conversion -> result aggregation.
- **Credential flow:** API keys are resolved per-role (TARGET, SDG, JUDGE, ATTACKER, EVALUATOR, TRANSLATION) via a priority chain: role-specific env var -> role-specific secret file -> generic API_KEY -> api-key secret file -> DUMMY fallback. Keys are redacted (replaced with `***`) before config upload to S3/OCI.
- **Downstream interactions:** The structured facts record 6 integration points, 3 internal dependencies, and 6 egress destinations. Named destinations include Kubeflow Pipelines, S3-compatible storage, Kubernetes API, target model endpoint, evalhub sidecar proxy, and OCI registry.
- **Security context:** Multi-layer authentication with role-based API key resolution (6 roles), SA token-based KFP auth (with sidecar proxy support for evalhub >= 0.4.4), and AWS credential resolution from Data Connection secrets. API keys are always redacted before persistence. 11 secret references describe the credential inputs applied around these interactions.

- **Deployment shape:** The component is a Python library/adapter (v0.5.1) that runs within eval-hub K8s Job pods. It does not deploy its own workloads, services, or ingress -- those are managed by the eval-hub platform. The adapter implements the `FrameworkAdapter` interface from eval-hub-sdk.
- **Execution modes:** Two modes are supported: **simple** (subprocess garak execution within the pod) and **kfp** (Kubeflow Pipeline delegation with S3-based artifact transfer). Mode selection is driven by `execution_mode` in the benchmark configuration.
