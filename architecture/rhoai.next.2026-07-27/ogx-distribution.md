## Purpose

**Short**: Container distribution image that packages the OGX AI agent framework (v1.2.1+rhaiv.0) with pre-installed inference providers, vector stores, tool runtimes, and file processors for deployment as the RHOAI OGX server on port 8321.

**Detailed**: ogx-distribution builds an OpenShift-compatible container image (`quay.io/opendatahub/odh-ogx-core`) from the upstream OGX framework. The image ships a pre-configured OGX server exposing eight HTTP APIs (responses, messages, batches, inference, tool_runtime, vector_io, files, file_processors) on port 8321. It supports nine remote inference providers (vLLM, Bedrock, WatsonX, Azure, Vertex AI, OpenAI, Gemini, Anthropic, sentence-transformers), three vector store backends (Milvus, pgvector, Qdrant), PostgreSQL for state persistence, S3 for file storage, web search tools (Brave, Tavily), file processors (docling, markitdown, pypdf), and Model Context Protocol integration. Authentication is via optional OAuth2/JWKS token validation with owner-based access policies. The entrypoint resolves Kubernetes-mounted `_FILE` secret variants to avoid `/proc` exposure. Pre-fetched model artifacts (IBM Granite embedding) and OpenTelemetry instrumentation are built into the image. The repository contains no Go or Python runtime code — it is purely a build/distribution wrapper around the upstream OGX binary.

## Data Flows

1. **Inference request flow**: Client → OGX server (port 8321) → configured inference provider (vLLM/Bedrock/WatsonX/Azure/VertexAI/OpenAI/Gemini/Anthropic) → response back to client. The Messages API translates between Anthropic and OpenAI Chat Completions format when the underlying provider requires it — `distribution/config.yaml:136-144`.
2. **Vector search flow**: Client → OGX vector_io API → configured vector store (Milvus/pgvector/Qdrant) with persistence metadata in PostgreSQL — `distribution/config.yaml:81-121`.
3. **File processing flow**: Client → OGX files API → local filesystem (`/opt/app-root/src/.ogx/distributions/rh/files`) or S3 storage, with metadata stored in PostgreSQL `files_metadata` table — `distribution/config.yaml:167-183`.
4. **Tool execution flow**: Client → OGX tool_runtime API → web search (Brave/Tavily) or file search (backed by files API) or MCP server — `distribution/config.yaml:145-166`.
5. **Secret resolution flow**: Container start → `entrypoint.sh` resolves `_FILE` variants for 18 secret variables from Kubernetes-mounted files → exports as environment variables → launches OGX server — `distribution/entrypoint.sh:35-57`.
6. **Telemetry flow**: When `OTEL_SERVICE_NAME` is set, `opentelemetry-instrument` wraps the OGX process to export traces and metrics via OTLP — `distribution/entrypoint.sh:69-77`.

## Architectural Analysis

- **Deployment shape**: ogx-distribution is a container image (`quay.io/opendatahub/odh-ogx-core`) that runs the OGX AI agent server. It is not a Kubernetes operator and defines no CRDs, controllers, or RBAC roles. Deployment and lifecycle management are handled externally by the RHOAI platform operator.
- **Provider architecture**: The image uses a pluggable provider model where inference backends, vector stores, tool runtimes, and file processors are conditionally enabled via environment variables. Providers with the `${env.VAR:+id}` pattern activate only when their trigger variable is set; providers without this pattern are always active.
- **State management**: All persistent state is stored in PostgreSQL via two backend types: `kv_postgres` for key-value data (metadata, agent state, vector store metadata) and `sql_postgres` for relational data (inference logs, conversations, batches, file metadata, responses). PostgreSQL is a hard runtime dependency.
- **Security model**: Authentication is optional (disabled by default) and uses OAuth2 token validation against a JWKS endpoint. Access control follows an owner-based model: all users can read unowned resources, authenticated users can create, and only owners can update/delete. Secrets support file-mounted injection to avoid `/proc` exposure.
- **Build architecture**: The repository is a build wrapper — it contains no runtime source code. `build/build.yaml` defines the full provider manifest, from which `gen_config.py` strips dependency-only providers to produce the default `config.yaml`. Lock files ensure hermetic dependency resolution.
- **Evidence boundary**: Analyzer coverage is partial for platform_semantics and webhooks_source. The OGX server binary is upstream code not present in this repository; exact HTTP path patterns, request methods, and internal API contracts are determined by the upstream OGX framework and are not inspected here. Port 8321 and the 8 API families are confirmed from the distribution config.
