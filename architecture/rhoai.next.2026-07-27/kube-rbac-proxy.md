## Purpose

**Short**: Kubernetes-aware HTTP reverse proxy sidecar that enforces RBAC authorization via SubjectAccessReview, with OIDC and TokenReview authentication, TLS termination, and configurable upstream forwarding.

**Detailed**: kube-rbac-proxy is a small HTTP reverse proxy designed to run as a sidecar container alongside upstream services (typically metrics endpoints). It accepts incoming HTTPS requests on a secure listen address (default port 8443), authenticates them using either OIDC or Kubernetes delegating TokenReview, authorizes them through a union authorizer chain (hardcoded metrics authorizer, static authorization rules, and SubjectAccessReview against the Kubernetes API), and forwards authenticated/authorized requests to a configured upstream URL over localhost. It supports TLS with configurable minimum version and cipher suites, certificate hot-reloading, HTTP/2 including h2c for upstream connections, configurable allow/ignore paths that bypass the auth chain, and a separate proxy endpoints port serving an unauthenticated `/healthz` endpoint. The CLI is built with Cobra and uses oklog/run for lifecycle management of concurrent listeners (`cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:65-123`, `cmd/kube-rbac-proxy/main.go:27-31`).

## Data Flows

- **Entry and service surface:** External clients connect to the kube-rbac-proxy secure listen address (typically port 8443) over TLS. The proxy exposes 2 HTTP endpoints: `/` (all methods, authenticated and authorized) and `/healthz` (GET only, unauthenticated, on a separate proxy endpoints port). There are no gRPC services.
- **Authentication chain:** For non-ignored paths on `/`, requests pass through `filters.WithAuthentication`. When OIDC is configured (`--oidc-issuer`), an OIDC authenticator validates tokens; otherwise, a delegating authenticator uses the Kubernetes TokenReview API (`authentication.k8s.io/v1`) via the `kubeClient.AuthenticationV1()` client (`cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:234-255`).
- **Authorization chain:** Authenticated requests pass through `filters.WithAuthorization` using a `union.New` authorizer combining: (1) hardcoded metrics authorizer allowing well-known OpenShift metrics users, (2) static authorizer from config file rules, and (3) SAR authorizer creating SubjectAccessReview requests via `kubeClient.AuthorizationV1()` (`cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:257-275`).
- **Upstream forwarding:** Authorized requests are proxied via `httputil.NewSingleHostReverseProxy` to the configured upstream URL (typically `http://127.0.0.1:<port>/` on localhost). Upstream connections support optional h2c forcing, custom CA bundles, and client certificates (`cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:277-298`).
- **Downstream interactions:** The structured facts record 5 integration points, 1 internal dependency, and 1 egress destination. Named destinations include Kubernetes API (TokenReview + SubjectAccessReview), upstream service (reverse proxy), and kube-rbac-proxy (odh-kube-auth-proxy) as sidecar.
- **Security context:** 5 authentication rules and 0 secret references describe the extracted enforcement and credential inputs. The TLS configuration supports configurable minimum version (normalized from both "TLS1.2" and "VersionTLS12" formats), cipher suite selection, HTTP/2 with ALPN negotiation, and certificate hot-reloading via `pkg/tls.CertReloader` (`cmd/kube-rbac-proxy/app/kube-rbac-proxy.go:369-401`).
