## Purpose

**Short**: OAuth2/OIDC authentication reverse proxy for Kubernetes, providing OpenShift OAuth and Kubernetes TokenReview-based access control in front of upstream services.

**Detailed**: kube-auth-proxy is a Kubernetes-native authentication reverse proxy (fork of oauth2-proxy under the `github.com/opendatahub-io/kube-auth-proxy/v1` module path). It intercepts HTTP requests to upstream services and enforces authentication via OpenShift OAuth, OIDC providers, or Kubernetes TokenReview API validation of service account tokens. The proxy listens on port 4180, manages user sessions via encrypted cookies backed by Redis (standalone, Sentinel, or cluster modes with optional TLS), and forwards authenticated identity headers and access tokens to upstream applications. It exposes an OpenShift Route with TLS edge termination for external access and integrates with OpenShift ServiceAccount-based OAuth clients. The repository contains 2 architecture components: the kube-auth-proxy Deployment itself and an example-app Deployment used for integration testing. The extracted dependency view records 0 internal platform dependencies and 3 analyzer-sourced integration points (Kubernetes API, Redis/Valkey, authentication/v1/TokenReview), extended with 2 source-backed integration points (OpenShift OAuth Server, upstream service).

## Data Flows

- **Entry and service surface:** External HTTPS traffic arrives at the OpenShift Route `kube-auth-proxy` with TLS edge termination (insecure requests redirected to HTTPS). The Route forwards to the `kube-auth-proxy` ClusterIP Service on port 80, which targets port 4180 on the proxy container. The proxy exposes 7 HTTP endpoints including OAuth2 flow endpoints, health checks, and metrics.
- **Authentication flow:** Unauthenticated requests are redirected to the identity provider (OpenShift OAuth or OIDC) via `/oauth2/start`. After authentication, the provider redirects to `/oauth2/callback` with an authorization code. The proxy exchanges the code for tokens, creates an encrypted session cookie, and optionally stores the session in Redis. Service account tokens bypass the OAuth flow and are validated directly via the Kubernetes TokenReview API (`authentication/v1`).
- **Proxy forwarding:** Authenticated requests are forwarded to the configured upstream service (e.g., `http://example-app:8080`) with identity headers (access token, user headers) injected. The upstream receives pre-authenticated requests with user identity information.
- **Session persistence:** Sessions are stored as encrypted cookies on the client. When Redis is configured, session data is persisted to Redis (standalone, Sentinel, or cluster mode) with optional TLS and custom CA certificate support. Redis distributed locking (`redislock`) provides session concurrency control.
- **Downstream interactions:** The structured facts record 3 analyzer-sourced integration points extended with 2 source-backed points, 0 internal dependencies, and 4 egress destinations. Named destinations include Kubernetes API (TokenReview), OpenShift OAuth Server, Redis/Valkey, and the configurable upstream service.
- **Security context:** 6 authentication rules and 1 secret reference describe the extracted enforcement and credential inputs applied around these interactions. The proxy enforces authentication at the reverse proxy layer before any request reaches the upstream service. Container security context enforces `runAsNonRoot`, `allowPrivilegeEscalation: false`, and drops all capabilities.
