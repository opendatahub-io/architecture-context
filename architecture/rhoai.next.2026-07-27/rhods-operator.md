## Purpose

**Short**: rhods-operator is the central lifecycle-management operator for Red Hat OpenShift AI (RHOAI), orchestrating 16 component CRDs, 3 service CRDs, 3 cloud-manager CRDs, and platform-level resources (DataScienceCluster, DSCInitialization, Platform) across multi-cloud environments.

**Detailed**: rhods-operator is the platform operator for RHOAI, managing the full lifecycle of AI/ML platform components through a layered CRD hierarchy. At the top level, DataScienceCluster (v1/v2) and DSCInitialization (v1/v2) provide cluster-scoped orchestration of all sub-components. The operator manages 16 component CRDs under `components.platform.opendatahub.io/v1alpha1` (Dashboard, DataSciencePipelines, FeastOperator, Kserve, Kueue, MLflowOperator, ModelController, ModelRegistry, ModelsAsService, OGX, Ray, SparkOperator, Trainer, TrainingOperator, TrustyAI, Workbenches), 3 service CRDs under `services.platform.opendatahub.io/v1alpha1` (Auth, GatewayConfig, Monitoring), and 3 cloud-manager CRDs under `infrastructure.opendatahub.io/v1alpha1` (AWSKubernetesEngine, AzureKubernetesEngine, CoreWeaveKubernetesEngine) for multi-cloud Kubernetes engine management. Each component CR is a singleton with XValidation-enforced naming (e.g., `default-dashboard`, `default-kserve`). The operator provides 12 admission webhooks (validating and mutating) for resource integrity, gateway/ingress configuration via GatewayConfig, OIDC integration for external authentication, OAuth proxy sidecar management for inference services, and Argo Workflows controller lifecycle management. It runs as a single Deployment with a webhook server on port 9443 and health/readiness probes on port 8081. (Source: api/components/v1alpha1/*_types.go, api/cloudmanager/*/v1alpha1/*_types.go, component-architecture.json)

## Data Flows

- **Entry and service surface:** The operator exposes 2 Kubernetes Services: a metrics service on port 8443 and a webhook service on port 443 (targeting container port 9443). All 14 HTTP endpoints are either admission webhooks (TLS-secured, Kubernetes admission authenticated) or health/readiness probes (unauthenticated by design).
- **Runtime inventory:** The operator runs as a single Deployment (`rhods-operator`) with a companion CLI tool (`v2` for cloud manager operations). The operator manages 27 CRD kinds across 7 API groups, each representing a platform component, service, or infrastructure resource.
- **Component lifecycle:** Component CRs (Dashboard, DataSciencePipelines, FeastOperator, Kserve, Kueue, etc.) are created as singletons by the DSCInitialization/DataScienceCluster controllers. Each component controller watches its own CR and manages owned resources (Deployments, Services, RBAC, NetworkPolicies, etc.) through the componentHandler/serviceHandler pattern.
- **Gateway and authentication chain:** GatewayConfig CR provides centralized gateway and OIDC configuration that is synced to component CRs: Dashboard receives GatewaySpec for ingress routing (source: api/components/v1alpha1/dashboard_types.go:47), FeastOperator receives GatewayOIDCSpec for external OIDC issuer URL propagation (source: api/components/v1alpha1/feastoperator_types.go:74). Kserve manages OAuthProxy sidecar injection for inference service authentication (source: api/components/v1alpha1/kserve_types.go:57-63).
- **Multi-cloud infrastructure:** Cloud manager CRDs (AWSKubernetesEngine, AzureKubernetesEngine, CoreWeaveKubernetesEngine) implement a common KubernetesEngineInstance interface with shared dependency management, enabling multi-cloud Kubernetes engine lifecycle management (source: api/cloudmanager/*/v1alpha1/*_types.go).
- **Downstream interactions:** The structured facts record 132 integration points, 7 internal dependencies, and 1 egress destination. Named destinations include Gateway API, prometheus-operator, OpenShift Cluster Configuration, models-as-a-service, Cloud Manager, OpenShift OAuth, Kubeflow Notebooks, and additional destinations listed in the tables.
- **Security context:** 8 authentication rules (including source-enriched OIDC and OAuthProxy entries) and 1 secret reference describe the extracted enforcement and credential inputs applied around these interactions; unknown values remain explicit in the tables.
