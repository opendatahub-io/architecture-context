## Purpose

**Short**: Guardrails orchestration server (v0.18.3) that intercepts LLM generation requests, applies configurable content detection and classification via downstream detector/chunker services, and returns safety-annotated responses over HTTP/HTTPS.

**Detailed**: fms-guardrails-orchestrator is a Rust-based application service built on axum (HTTP) and tonic (gRPC client) that orchestrates safety guardrails for foundation model interactions in RHOAI. It operates as a proxy between API consumers and backend generation services (TGIS via gRPC, NLP via caikit-nlp, or OpenAI-compatible via REST), routing requests through configurable detector and chunker pipelines. The server exposes 12 HTTP endpoints across two API versions (v1 and v2) on port 8033, covering classification-with-generation, content detection, chat detection, context document detection, and OpenAI-compatible chat/text completions with detection. A separate health server on port 8034 provides unauthenticated health and info endpoints. Authentication is header-passthrough based, with configurable header allowlists and optional X-Forwarded-Access-Token to Bearer token rewriting. All downstream service connections support optional TLS with named, reusable TLS configurations, and the server itself supports optional TLS and mTLS for inbound connections.

## Data Flows

- **Entry and service surface:** The orchestrator exposes two independent servers: a guardrails API server on port 8033 (12 HTTP endpoints, optional TLS/mTLS) and a health server on port 8034 (2 HTTP endpoints, no TLS). The guardrails server handles all content detection, classification, and generation orchestration requests.
- **Conditional endpoint enablement:** Two v2 endpoints (/api/v2/chat/completions-detection and /api/v2/text/completions-detection) are conditionally registered only when an OpenAI-compatible generation service is configured (src/server/routes.rs:97-109). All other endpoints are always available.
- **Request flow:** Each API endpoint validates the inbound request, filters headers through the configured passthrough_headers allowlist, optionally rewrites X-Forwarded-Access-Token to Authorization: Bearer, constructs a typed task object, and delegates to the orchestrator handler. The handler coordinates concurrent calls to generation, chunker, and detector services.
- **Streaming protocols:** v1 streaming and chat/text completions-detection endpoints use SSE (Server-Sent Events) with JSON data payloads and keep-alive. The stream-content endpoint (v2) uses ND-JSON (application/x-ndjson) for both input and output, enforcing content-type validation.
- **Downstream interactions:** The orchestrator acts as a gRPC client to TGIS/NLP generation and chunker services (via tonic), and as a REST client to detector and OpenAI-compatible generation services (via reqwest). Each downstream service connection supports optional TLS through named, reusable TLS configurations. Detector requests are sent concurrently with a configurable limit (default: 5 concurrent requests per task).
- **Security context:** 6 authentication rules and 4 secret references describe the extracted enforcement and credential inputs. Inbound TLS uses rustls with the ring crypto provider. Downstream API tokens are loaded from environment variables at config time.
