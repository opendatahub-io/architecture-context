## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines (Kubeflow Pipelines v2) deployments on OpenShift via the DataSciencePipelinesApplication custom resource.

**Detailed**: The Data Science Pipelines Operator (DSPO) is a kubebuilder-based operator that reconciles `DataSciencePipelinesApplication` (DSPA) custom resources to deploy namespace-scoped Kubeflow Pipelines v2 stacks on OpenShift. Each DSPA instance creates a complete pipelines environment including: API server, persistence agent, scheduled workflow controller, Argo workflow controller, ML Metadata (MLMD) service, and optional MariaDB and MinIO instances for metadata storage and artifact storage respectively.

The operator uses a manifest-templating architecture via the manifestival library: Go templates in `config/internal/` are rendered with parameters extracted from the DSPA CR spec, operator configuration (viper), and cluster state (secrets, configmaps, TLS profiles). The rendered Kubernetes resources are applied with owner references and `dsp-version` labels for lifecycle tracking. The operator also manages Argo Workflows CRDs and RBAC, and integrates with the modular AIPipelines platform API for coordinated deployment within the broader RHOAI platform.

A secondary controller path — AIPipelinesReconciler and AIPipelinesArgoReconciler — implements the modular ownership model where the cluster-scoped `AIPipelines` CR coordinates component deployment within the RHOAI platform operator hierarchy. This path is feature-gated by the `ENABLEAIPIPELINESMODULECONTROLLER` environment variable.

## Architectural Analysis

DSPO exhibits a layered reconciliation architecture with careful separation between parameter resolution and resource application. The `ExtractParams` phase (in `dspipeline_params.go`) is a pre-flight step that resolves all CR fields, operator configuration, secrets, configmaps, and TLS certificates into a `DSPAParams` struct — any failure here blocks the entire reconcile, ensuring the operator never applies partially-resolved templates. Health checks against the database and object store backends run after parameter resolution but before workload deployment, providing fast feedback on infrastructure readiness.

The operator's cache optimization strategy is architecturally notable. It strips `managedFields` from all cached objects via `DefaultTransform`, further strips data payloads from ConfigMaps and Secrets (reading them via direct API calls instead), and scopes informers to operator-managed resources using the `dsp-version` label selector. This reduces memory consumption significantly in clusters with many resources. Pod watches are additionally scoped to the `component=data-science-pipelines` label.

TLS security is handled by fetching the cluster's TLS security profile from the OpenShift `config.openshift.io` API at startup. The profile drives cipher suite and protocol version configuration for both the webhook server (port 9443) and the metrics endpoint. A `SecurityProfileWatcher` monitors for profile changes at runtime and triggers a graceful shutdown to reload — trading availability of a single controller pod for correct TLS posture without hot-reloading complexity.

The dual-controller architecture (legacy DSPAReconciler + modular AIPipelines controllers) allows DSPO to operate standalone or as a managed component within the RHOAI platform operator. The DSPA controller remains active in both modes, while the AIPipelines controllers only activate when `ENABLEAIPIPELINESMODULECONTROLLER=true`. This design supports the platform's incremental migration from monolithic operator ownership to modular component ownership.

**Language**: Go (external component)

**Dockerfile**: Deployed via operator templates

**Dockerfile**: Deployed via operator templates

**Language**: Go (external component)

### ml-metadata (MLMD)

**Dockerfile**: Deployed via operator templates
**Intent**: ML Metadata gRPC server with Envoy sidecar for TLS termination. Stores pipeline artifact lineage and metadata. Deployed per DSPA instance, reconciled last due to TLS secret dependencies.
**Image**: Configured via `IMAGES_MLMDGRPC` (gRPC server) and `IMAGES_MLMDENVOY` (Envoy proxy)
**Language**: C++ (gRPC server), Go (Envoy proxy)

### mariadb (optional)

**Dockerfile**: Deployed via operator templates
**Intent**: Optional in-namespace MariaDB instance for pipeline metadata storage. Deployed when DSPA does not specify an external database. Includes operator-generated credentials secret.
**Image**: Configured via `IMAGES_MARIADB` env var

### minio (optional)

**Dockerfile**: Deployed via operator templates
**Intent**: Optional in-namespace MinIO instance for pipeline artifact storage. Deployed when DSPA does not specify external S3-compatible storage. Includes operator-generated credentials secret.
**Image**: Not configurable via params.env (defined in DSPA CR spec)

#### Build-Time FIPS (check-payload gate)

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | GOFIPS140=v1.0.0, CGO_ENABLED=0, -tags no_openssl | Dockerfile.konflux:30 |
| **Go module FIPS** | godebug fips140=on | go.mod:5 |
| **Linking** | Static (CGO_ENABLED=0, no OpenSSL) | Dockerfile.konflux:30 |
| **OpenSSL in image** | Not required — uses Go 1.26 native FIPS 140 crypto module | Dockerfile.konflux:30 |

| **OLM FIPS annotation** | Not present in repo (set by platform operator) | N/A |

_Go 1.24+ introduced the `GOFIPS140` build variable and `godebug fips140=on` runtime directive. This replaces the older `GOEXPERIMENT=boringcrypto`/`GOEXPERIMENT=strictfipsruntime` + `CGO_ENABLED=1` approach. With `GOFIPS140=v1.0.0`, Go downloads and uses its own FIPS 140-3 validated cryptographic module (pure Go, no OpenSSL dependency). The `-tags no_openssl` build tag explicitly disables the OpenSSL backend. The `ubi9/ubi-minimal-pqc` base image provides post-quantum cryptography support at the OS level._

|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregate RBAC ClusterRoles (admin/edit/view) for DSPA and pipeline resources; per-namespace Roles and RoleBindings created by operator | Kubernetes | Argo aggregate ClusterRoles grant cluster-wide access to Argo resources; DSPA access is namespace-scoped |
