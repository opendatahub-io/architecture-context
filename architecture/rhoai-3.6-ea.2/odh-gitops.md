## Purpose

**Short**: GitOps repository providing Kustomize manifests and Helm charts for deploying OpenDataHub/RHOAI platform dependencies and operator configurations on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: odh-gitops is the standardized deployment configuration repository for the OpenDataHub (ODH) and Red Hat OpenShift AI (RHOAI) platform stack. It does not contain application source code or produce container images; instead, it provides declarative infrastructure-as-code that orchestrates the installation, configuration, and lifecycle management of the 13+ operator dependencies that underpin the RHOAI/ODH platform.

The repository supports two distinct deployment paths: a Kustomize-based path for OpenShift environments using OLM (Operator Lifecycle Manager) subscriptions, and a Helm chart-based path available in two variants — `rhai-on-openshift-chart` for OCP clusters and `rhai-on-xks-chart` for non-OpenShift Kubernetes environments (AWS EKS, Azure AKS, CoreWeave). The Helm charts implement a sophisticated tri-state dependency resolution system (`auto`/`true`/`false`) that automatically determines which operators to install based on which platform components (KServe, Kueue, Trainer, Dashboard, etc.) are enabled, with profile-based presets (default, rhaii, maas) for common deployment patterns.

The XKS chart is architecturally distinct in that it bundles the RHAI operator deployment directly (rather than relying on OLM), deploys cloud-provider-specific cloud manager operators (AWS, Azure, CoreWeave), and uses Helm hooks with shell scripts to orchestrate multi-step operations like Gateway creation, TLS certificate provisioning via cert-manager, and Authorino TLS bootstrap for API authorization.

## Architectural Analysis

odh-gitops occupies an unusual position in the RHOAI architecture — it is not a runtime component but rather the orchestration layer that brings all other components into existence. Its architecture reflects two distinct eras of platform deployment: the original Kustomize-based approach designed for single-cluster OpenShift deployments with OLM, and the newer Helm-chart approach designed for multi-cloud portability.

The Kustomize path follows a three-layer composition model: reusable `Component` resources in `components/operators/` define individual operator installations (Namespace, OperatorGroup, Subscription), overlays in `dependencies/operators/` compose these into installable bundles, and `configurations/` contains post-install CRs (e.g., Kueue, LeaderWorkerSetOperator, Kuadrant) that require OLM-installed CRDs to exist first. This two-phase application (dependencies first, configurations second) is a deliberate design choice to handle CRD chicken-and-egg ordering.

The Helm charts introduce a component-dependency graph that is the most architecturally significant feature of the repository. Components (KServe, Trainer, Dashboard, etc.) declare their dependency requirements, and the `shouldInstall` helper template traverses this graph to determine which operators to install. Transitive dependency resolution ensures that, for example, enabling Kueue (which depends on cert-manager) will automatically enable cert-manager if it is set to `auto`. The three deployment profiles (default, rhaii, maas) encode common configurations: `default` starts with all components Removed, `rhaii` enables KServe for inference-only deployments, and `maas` enables the AI Gateway with Models-as-a-Service.

A key architectural tension exists in the TLS and Gateway setup for the XKS chart. The `create-gateway.sh` and `create-maas-gateway.sh` scripts perform multi-step, order-dependent operations (wait for CRDs, create CA bundles, create Certificates, wait for Certificate readiness, create Gateways, patch Authorino) that cannot be expressed purely in Helm templates. These scripts run as Helm post-install hooks and contain the actual TLS orchestration logic, including cert-manager Certificate creation, CA bundle distribution across namespaces, and Authorino CA trust injection.

The cloud provider abstraction in the XKS chart uses a registry pattern (`providerRegistry`, `componentCRRegistry`, `moduleCRRegistry`) where adding a new cloud provider or component requires only a single entry in `_crs-definitions.tpl`. The `activeProvider` helper resolves the enabled provider at render time, and all templates consume its output — achieving genuine extensibility without template duplication.
