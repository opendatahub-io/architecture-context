## Platform Overview

RHOAI 3.6-ea.2 is a comprehensive AI/ML platform deployed on OpenShift Container Platform via the Operator Lifecycle Manager (OLM). At its center, the `rhods-operator` acts as a meta-operator that manages platform lifecycle through two cluster-scoped CRDs — `DataScienceCluster` (which components to enable) and `DSCInitialization` (platform initialization, monitoring, and service mesh integration). Rather than running 16+ separate OLM subscriptions, the operator uses a module system that fetches component kustomize manifests at build time and renders them at runtime with image overrides from `RELATED_IMAGE_*` environment variables set in the OLM ClusterServiceVersion. This keeps a single operator binary while centralizing lifecycle management for the entire platform.

The platform's ingress architecture centers on the Kubernetes Gateway API. The `rhods-operator` creates a `data-science-gateway` Gateway in the `openshift-ingress` namespace using the OpenShift Gateway API controller. Components attach HTTPRoutes to this shared gateway for external access. Authentication at the gateway is enforced via an Envoy `ext_authz` filter that calls a `kube-auth-proxy` deployment at `/oauth2/auth`, supporting both OpenShift integrated OAuth and external OIDC providers. A companion Lua filter handles token forwarding and cookie stripping after authentication. A separate `maas-default-gateway` serves the Models-as-a-Service (MaaS) subsystem, using Kuadrant/Authorino for API key and OAuth token authentication with Envoy ExtProc filters (praxis-extproc) for request payload processing. For LLM serving, `odh-model-controller` manages per-gateway EnvoyFilters and Kuadrant AuthPolicies independently.

The security posture is anchored in several layers: FIPS-compliant builds using `GOEXPERIMENT=strictfipsruntime` on UBI 9 minimal-pqc base images; dynamic TLS configuration derived from the cluster's `APIServer` TLS security profile; `kube-rbac-proxy` sidecars on metrics endpoints performing TokenReview and SubjectAccessReview; and per-component RBAC with least-privilege ClusterRoles. Certificate management is split between OpenShift's service-CA operator (for internal services) and cert-manager (for webhooks and gateway TLS on non-OpenShift clusters).

### Ingress Analysis

The platform operates three distinct ingress generations that coexist in a single deployment:

**Gateway API (primary):** The `data-science-gateway` is the platform's central ingress node, created by the `rhods-operator` gateway service controller in `openshift-ingress`. It uses the OpenShift Gateway API controller (`openshift.io/gateway-controller/v1`) with an Istio revision label (`istio.io/rev: openshift-gateway`). Authentication is enforced by an EnvoyFilter (`data-science-authn-filter`) that inserts an `ext_authz` HTTP filter calling `kube-auth-proxy` at `https://kube-auth-proxy.openshift-ingress.svc.cluster.local:8443/oauth2/auth`. The kube-auth-proxy supports two modes: OpenShift integrated OAuth (using the platform's OAuth server with auto-discovery) and external OIDC (configurable via the `GatewayConfig` CR's `.spec.oidc` field). A companion Lua filter handles OAuth-mode token forwarding (promoting `x-auth-request-access-token` to `Authorization: Bearer` and `x-forwarded-access-token`) and strips `_oauth2_proxy` cookies from authenticated requests to prevent credential leakage to backends. Source: `rhods-operator/internal/controller/services/gateway/resources/envoyfilter-authn.tmpl.yaml`.

**MaaS Gateway:** The `maas-default-gateway` serves the Models-as-a-Service subsystem with a fundamentally different authentication model. Instead of kube-auth-proxy, it uses Kuadrant/Authorino with a dual authentication path: API keys (prefixed `sk-oai-`) are validated via an HTTP callback to the maas-api's internal endpoint (`/internal/v1/api-keys/validate`), while OpenShift tokens use Kubernetes TokenReview. Authorino strips the original Authorization header to prevent credential forwarding to model backends and injects identity headers (`X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription`). Request payload processing is handled by two `praxis-extproc` instances deployed as Envoy ExtProc filters: a pre-auth instance (fail-open) that extracts model names from request bodies and promotes them to routing headers, and a post-auth instance (fail-closed) that performs full request/response processing including provider resolution for external models. Source: `models-as-a-service/maas-controller/pkg/controller/maas/`, `praxis-extproc/deploy/overlays/odh/`.

**Legacy OpenShift Routes:** Several components still create OpenShift Routes for backward compatibility or specific use cases: the dashboard redirect route (forwarding legacy `rhods-dashboard` hostnames), observability proxy routes (Prometheus namespace and cluster proxies), and model-registry Routes in non-gateway mode. These coexist with Gateway API resources.

An important architectural transition is visible in the LLM serving path: `odh-model-controller`'s `GatewayReconciler` creates EnvoyFilters and Kuadrant AuthPolicies for LLM-specific Gateways independently of the `data-science-gateway`'s kube-auth-proxy chain. This separation allows the LLM serving gateway to use Kuadrant-based auth (which supports per-service policies and rate limiting) while the platform dashboard gateway uses the simpler kube-auth-proxy + ext_authz pattern.

## Deployment Architecture

### Deployment Topology

The platform follows a three-tier namespace deployment model. The operator tier runs in `redhat-ods-operator` and contains only the `rhods-operator` pod (with leader election for HA). The platform services tier runs in `redhat-ods-applications` and hosts all component operators, controllers, dashboards, API servers, and management services. The gateway tier runs in `openshift-ingress` and hosts the Istio-powered data-science-gateway, kube-auth-proxy authentication pods, and praxis-extproc payload processing pods. User workloads (InferenceServices, Notebooks, RayClusters, TrainJobs, Pipelines) run in user-owned namespaces with per-workload RBAC. MaaS tenant resources are isolated in per-tenant namespaces created by the maas-controller, with infrastructure services (maas-api, PostgreSQL) in a dedicated `odh-ai-gateway-infra` namespace.

On non-OpenShift (XKS) clusters, the architecture adapts: gateway resources move to `rh-ai-gateway`, the operator is deployed directly (not via OLM), and the cloud manager binary provisions cloud-provider-specific infrastructure (AWSKubernetesEngine, AzureKubernetesEngine, CoreWeaveKubernetesEngine CRDs).

#### Manifest Consumption Pipeline

Component manifests flow from individual component repositories through a centralized consumption pipeline. Each component repository contains its own kustomize manifests (base + overlays). The `rhods-operator`'s `manifests-config.yaml` declares which component repos to fetch, and a build-time script downloads their manifests into the operator image. At runtime, the module reconciler renders these manifests with kustomize, injecting image overrides from `RELATED_IMAGE_*` environment variables defined in the OLM ClusterServiceVersion. This pipeline means that a component image update requires only a CSV change (new digest in `RELATED_IMAGE_*`), not a new operator build — unless the component's manifests have also changed.

For the GitOps deployment path (`odh-gitops`), a parallel pipeline exists: OLM subscriptions install dependency operators, then post-install kustomize manifests or Helm values create the `DataScienceCluster` and `DSCInitialization` CRs that trigger the `rhods-operator` to deploy the platform.

### Disconnected Support

The platform supports air-gapped/disconnected deployment through the `RELATED_IMAGE_*` pattern mandated by OLM. All component container images are declared as `relatedImages` in the ClusterServiceVersion, enabling `oc-mirror` to automatically discover and mirror the complete image set to a local registry. At runtime, `RELATED_IMAGE_*` environment variables provide the resolved (potentially mirrored) image references. The module operator system extends this: module manifests reference images via kustomize `params.env` variables that are overridden by `RELATED_IMAGE_*` values from the CSV. Supply chain evidence for this topic is `unresolved` across all 88 components in the structured inventory — the component-level analyzers did not extract RELATED_IMAGE patterns, so this assessment is derived from the operator architecture rather than per-component evidence.

## Platform Architectural Analysis

RHOAI 3.6-ea.2 reveals a platform at a significant inflection point, with three major architectural evolutions underway simultaneously: the transition from single-model serving to disaggregated LLM inference, the emergence of a dual-gateway ingress architecture, and the expansion from an OpenShift-native platform to a multi-cloud deployment target.

**The Module Operator Pattern as Scaling Strategy.** The most distinctive architectural decision in the platform is the module system. Rather than managing 16+ separate OLM subscriptions (each with its own lifecycle, version constraints, and upgrade risk), `rhods-operator` bundles module operator manifests at build time and deploys them as subordinate controllers at runtime. This trades deployment flexibility (individual component versions are locked to the operator release) for operational simplicity (a single CSV upgrade updates the entire platform). The tradeoff becomes visible in the component analyses: some module operators (kserve-module, feast-module-operator) are thin lifecycle wrappers that primarily render kustomize manifests, while others (models-as-a-service, odh-model-controller) are substantial controllers with their own CRDs and reconciliation logic. The distinction matters because module operators share the `rhods-operator`'s release cadence even when their development velocity differs.

**Dual Authentication Architecture.** The platform runs two fundamentally different authentication models through two gateway instances. The `data-science-gateway` uses a monolithic auth proxy (kube-auth-proxy) with an Envoy ext_authz integration — a pattern optimized for human users with browser-based sessions. The `maas-default-gateway` uses Kuadrant/Authorino with API key validation — a pattern optimized for programmatic API access. This dual model is architecturally sound: human and machine clients have different authentication needs, and collapsing them into a single mechanism would compromise either usability or security. However, it means the platform carries two authentication stacks, two gateway configurations, and two sets of TLS certificates, increasing the operational surface area.

**The LLM-D Ecosystem.** The llm-d family (llm-d, llm-d-router, llm-d-deployer, llm-d-model-service, llm-d-kv-cache, llm-d-async, llm-d-routing-sidecar, llm-d-latency-predictor, llm-d-benchmark, llm-d-inference-sim, llm-d-inference-payload-processor, llm-d-planner, llm-d-prism, llm-d-api-extensions, llm-d-autoscaling, llm-d-pd-utils, llm-d-batch-gateway, llm-d-batch-gateway-operator) represents a significant expansion of the platform's inference capabilities. This ecosystem introduces disaggregated prefill/decode serving with RDMA-based KV-cache transfer, plugin-based request routing through the Gateway API Inference Extension, and multi-accelerator support (NVIDIA, AMD ROCm, Intel XPU, Google TPU, IBM Spyre). The architectural risk is complexity: the disaggregated serving path involves 4-5 separate components (EPP, Coordinator, Sidecar, model servers, KV-cache manager) communicating over multiple protocols (gRPC ext-proc, HTTP, NIXL/RDMA, ZeroMQ).

**The Praxis Gateway Processing Stack.** A new gateway processing layer has emerged through the Praxis family (praxis-extproc, Praxis proxy, Praxis AI, praxis-grid, Praxis Policy Engine). The `praxis-extproc` component bridges the gap between Envoy's routing layer and AI-specific request processing needs — extracting model names from request bodies, resolving external provider configurations, and performing response transformations. Its dual-deployment model (pre-auth fail-open + post-auth fail-closed) is a careful security design that prevents authentication bypass while ensuring routing headers are available for auth policy evaluation.

**TLS Configuration Consistency.** A positive cross-cutting observation: all major Go controllers (rhods-operator, kserve, odh-model-controller, odh-dashboard, models-as-a-service, model-registry-operator) follow the same TLS profile derivation pattern — reading the cluster's `APIServer` TLS security profile and dynamically configuring cipher suites. This consistency ensures platform-wide TLS policy compliance from a single cluster configuration knob. The Rust components (praxis-extproc, fms-guardrails-orchestrator) achieve equivalent FIPS compliance through runtime OpenSSL FIPS provider probing rather than build-time flags.

**Multi-Cloud Expansion.** The XKS (non-OpenShift Kubernetes) deployment path, visible in `odh-gitops`'s Helm charts and the `rhods-operator`'s cloud manager binary, represents a significant architectural expansion. On XKS, the platform replaces OpenShift-specific primitives (service-CA, OAuth, Routes, OLM) with portable alternatives (cert-manager, Istio Gateway controller, Authorino, direct Deployment). The cloud manager introduces `AWSKubernetesEngine`, `AzureKubernetesEngine`, and `CoreWeaveKubernetesEngine` CRDs for infrastructure provisioning. The conditional compilation pattern (`//go:build distro` vs `//go:build !distro`) in KServe cleanly separates upstream from downstream behavior without source forks.
