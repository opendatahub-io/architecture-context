## Purpose

**Short**: An algorithm-focused Python library and CLI providing a unified interface for LLM training, continual learning, reinforcement learning, and prompt optimization techniques.

**Detailed**: Training Hub is a Python package (`training-hub` on PyPI) developed by the Red Hat AI Innovation Team that provides a Strategy + Registry abstraction over multiple training backends. It exposes seven training algorithms—SFT, OSFT (Orthogonal Subspace Fine-Tuning), LoRA + SFT, LoRA + GRPO, full-parameter GRPO, GEPA (Genetic-Pareto prompt optimization), and Embedding SFT—each backed by one or more pluggable backend implementations (InstructLab Training, RHAI Innovation Mini-Trainer, Unsloth, OpenPipe ART, verl, GEPA, MLflow, SentenceTransformers).

The component is not an operator, service, or controller—it is a library consumed by other RHOAI components (such as Kubeflow training pipelines and coding agent plugins) that need to execute LLM fine-tuning workloads. It ships a CLI (`thub`) for direct invocation with YAML config files or CLI arguments. Training Hub adds infrastructure-aware features on top of the raw backends: JIT preemption checkpointing via SIGTERM handling (critical for Kubernetes pod eviction), remote checkpoint mirroring to S3/GCS/Azure Blob via fsspec, distributed training coordination via torchrun, and a unified callback system that works across all backends.

## Architectural Analysis

Training Hub's architecture follows a clean **Strategy + Registry** pattern that decouples algorithm definitions from backend implementations. The `AlgorithmRegistry` is a class-level singleton that maps algorithm names to `Algorithm` subclasses and backend names to `Backend` subclasses. Each algorithm defines required and optional parameters; each backend implements `execute_training()` with backend-specific parameter translation. Convenience functions (`sft()`, `osft()`, `lora_grpo()`, etc.) wrap the registry lookup and provide the primary public API.

The callback system (`TrainingHubCallback` / `TrainingHubContext`) is a notable design decision: it provides a normalized view of training state across backends that have fundamentally different execution models. Unsloth runs in-process with HuggingFace Trainer, while InstructLab Training and Mini-Trainer run inside torchrun subprocesses. The adapter layer (`adapters/`) bridges this gap—torchrun backends use class-source serialization to cross the subprocess boundary, which imposes constraints (module-level definitions, no closure state, imports inside method bodies).

The checkpoint infrastructure is the most complex subsystem. JIT checkpointing (`JITCheckpointCallback`) intercepts SIGTERM signals and requests a save at the next step/epoch boundary, coordinating across distributed ranks via `torch.distributed.all_reduce`. The `RemoteCheckpointSyncCallback` mirrors checkpoints to remote storage via a background LIFO uploader thread with hardlink-based staging to avoid race conditions with HuggingFace's `save_total_limit` rotation. The restore path downloads remote checkpoints atomically (temp directory + move) and validates completeness via upload markers.

A significant architectural split exists between the ART and verl GRPO backends. ART runs in a spawned subprocess (`mp.get_context("spawn")`) with co-located vLLM inference and Unsloth training on a single GPU via time-sharing. verl launches training as a torchrun subprocess with Hydra-style CLI overrides, using FSDP for distributed training and vLLM for parallel rollout generation across multiple GPUs. This means the same `lora_grpo()` API can target single-GPU fast iteration (ART) or multi-GPU scaled training (verl), but the execution paths are entirely different.

The CLI (`thub`) uses lazy imports—each algorithm's module is imported only when its subcommand is selected—because the transitive dependency graph is enormous (torch, transformers, vLLM, etc.). This prevents one algorithm's missing optional dependency from breaking every other subcommand.
