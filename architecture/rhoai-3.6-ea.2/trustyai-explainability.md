## Purpose

**Short**: TrustyAI is a Java library and Quarkus REST service providing fairness metrics, model drift detection, and explainable AI algorithms for ML models served via KServe/ModelMesh on OpenShift.

**Detailed**: TrustyAI Explainability is a multi-module Maven project that provides AI trustworthiness capabilities at both a library and service level. The core library (`explainability-core`) implements fairness metrics such as Statistical Parity Difference (SPD) and Disparate Impact Ratio (DIR), model drift detection algorithms (KS Test, Fourier MMD, Meanshift), and local/global explainability methods (LIME, SHAP, Counterfactual, TSSaliency, Partial Dependence Plot).

The service module (`explainability-service`) wraps this library as a Quarkus 3.8.5 REST application that integrates with the RHOAI platform. It consumes inference payloads from ModelMesh and KServe model servers, stores them in configurable backends (PVC flat files, MinIO, or MariaDB/MySQL via Hibernate), and computes fairness and drift metrics on a scheduled basis. These metrics are exposed as Prometheus gauges and scraped by the platform's monitoring stack. The connectors module provides both KServe v1 HTTP and v2 gRPC client adapters for querying model inference endpoints, while the arrow module facilitates data exchange with the TrustyAI Python library.

In the RHOAI distribution, the service operates in a reduced feature mode: local explainer endpoints (LIME, SHAP, Counterfactual, TSSaliency) and global explainer endpoints are disabled via Quarkus profile configuration, leaving only fairness metrics and drift detection active. The service is deployed per-namespace by the TrustyAI Service Operator and receives inference payloads via a payload processor callback URL injected into the model-serving-config ConfigMap.

## Architectural Analysis

TrustyAI follows a sidecar-adjacent deployment pattern where an instance is deployed per data science project namespace by the TrustyAI Service Operator. Rather than intercepting traffic inline, the service registers itself as a KServe v2 payload processor via a ConfigMap injected by an init container (`config-map-overrider`). This init container uses the `oc` CLI to write a `model-serving-config` ConfigMap containing the service's own URL (`http://trustyai-service.<namespace>/consumer/kserve/v2`), enabling ModelMesh to forward inference payloads asynchronously.

The storage architecture is pluggable with three production backends: PVC-mounted flat files (CSV format, the default), MinIO for S3-compatible object storage, and Hibernate ORM for relational databases (MariaDB or MySQL). The choice of backend is driven by the `SERVICE_STORAGE_FORMAT` environment variable. The Hibernate path supports a separate payload reconciliation pipeline with both in-memory and database-backed variants for buffering partial inference payloads before they are reconciled into complete predictions.

The metrics scheduling system is notable: fairness and drift metrics are computed periodically (configurable via `SERVICE_METRICS_SCHEDULE`, default 5 seconds) and published as Prometheus gauges. A ServiceMonitor selects the service by label and scrapes `/q/metrics` with specific metric name filters (`trustyai_spd`, `trustyai_dir`), using bearer token authentication from the pod's service account.

The Konflux build pipeline uses a pre-built artifact approach: the Java application is compiled by Red Hat's PNC (Product Node Catalog) build system and distributed as a zip archive referenced in `artifacts.lock.yaml`. The Konflux Dockerfile simply extracts these pre-built artifacts rather than compiling from source, using Hermeto/cachi2 for dependency prefetching.

TLS is configured at the application level with certificate files mounted at `/etc/tls/internal/tls.crt` and `/etc/tls/internal/tls.key` on port 4443, alongside the plaintext HTTP port 8080. The operator is responsible for provisioning these certificates.
