## Purpose

**Short**: Module operator that manages the lifecycle (install, upgrade, status, removal) of the KubeRay operator as part of the ODH/RHOAI modular architecture.

**Detailed**: The ray-module-operator reconciles a cluster-scoped `Ray` custom resource (`components.platform.opendatahub.io/v1alpha1`) and is deployed by the ODH platform operator when the Ray module is enabled. It carries vendored KubeRay operand manifests inside the container image under `/opt/manifests/kuberay` and uses kustomize to render and server-side-apply them into the target `applicationsNamespace`.

The operator follows the ODH platform utilities framework reconciler pattern: a pipeline of composable actions processes the Ray CR through management state evaluation, release tracking, manifest rendering, image parameter injection (via `RELATED_IMAGE_*` environment variables), cert-manager prerequisite validation, platform-specific resource filtering, notebook RBAC provisioning, server-side-apply deployment, deployment health monitoring, distribution status synchronization, and garbage collection. A finalizer ensures owned operands (webhooks, SCCs, ClusterRoles) are cleaned up on Ray CR deletion while CRDs are deliberately retained.

The controller watches a platform ConfigMap (`odh-ray-config`) in the applications namespace to detect distribution name and version changes. It uses this to maintain `status.distribution` on the Ray CR and to participate in the platform version handshake protocol. When the management state is set to `Removed`, the operator tears down all KubeRay operands and their supporting RBAC and webhook resources.

## Architectural Analysis

The ray-module-operator is a thin lifecycle wrapper around KubeRay, following the ODH modular operator pattern where each platform component gets a dedicated module operator that the central platform operator coordinates via a component CR. The architecture is intentionally constrained: the operator does not define its own webhooks or serve user-facing APIs — its sole job is deploying and managing the KubeRay operator.

A notable design decision is the copy-on-write manifest strategy: since the container image runs as a non-root user with a read-only filesystem, the operator copies vendored manifests from `/opt/manifests` to a writable temp directory before rewriting `params.env` with RELATED_IMAGE values and adjusting kustomize namespace directives. This avoids mutating the image filesystem while still supporting dynamic image and namespace parameterization at reconcile time.

The operator's RBAC footprint is deliberately broad — it holds the same verbs on Ray API resources (`ray.io/rayclusters`, `rayjobs`, `rayservices`, `raycronjobs`) as the KubeRay operator itself, because Kubernetes privilege-escalation rules require the SSA applier to hold at least the verbs it grants. Similarly, it manages admission webhook configurations, CRDs, and SecurityContextConstraints because these are part of the KubeRay deployment surface.

The `notebookClusterRole` action creates a stable `ray` ClusterRole that Workbenches binds to Notebook ServiceAccounts, granting them ability to submit RayJobs and read RayCluster status. This ClusterRole is explicitly managed outside the SSA/ownerRef tree to avoid blocking Ray CR deletion.

Platform portability is handled at reconcile time: on clusters without the `security.openshift.io` API group, the `filterPlatformResources` action strips SecurityContextConstraints from the rendered manifest set before deployment.
