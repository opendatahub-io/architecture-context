## Purpose

**Short**: Manages interactive development workspaces (JupyterLab, RStudio, VS Code) on Kubernetes through a controller that reconciles Workspace and WorkspaceKind CRDs, a REST API backend, and a web frontend.

**Detailed**: Workbenches (Kubeflow Notebooks v2) provides a platform for running interactive development environments for AI/ML workloads on Kubernetes. The component defines two custom resources — `Workspace` (namespaced) and `WorkspaceKind` (cluster-scoped) — that together model user workspaces and their templates (notebook types, container images, resource presets). The controller reconciles these CRDs into StatefulSets, Services, ServiceAccounts, and network routing (Istio VirtualServices or Kubernetes Gateway API HTTPRoutes with kube-rbac-proxy sidecars), creating a complete per-workspace deployment with appropriate RBAC and ingress.

The Go backend provides a REST API (`/api/v1/`) that exposes workspace CRUD operations, workspace kind management, PVC management, secret management, and pod log streaming. It delegates authentication to either Kubeflow identity headers (internal mode) or Kubernetes TokenReview (user_token mode for RHOAI/ODH deployments), and authorization to Kubernetes SubjectAccessReview, ensuring all API operations respect the caller's RBAC permissions. The frontend is an nginx-served React/TypeScript SPA that can also be served directly by the backend via Module Federation static asset serving.

## Architectural Analysis

The workbenches architecture separates concerns into three independently-deployable components: a controller (operator pattern), an API backend, and a frontend. This separation allows the controller to operate purely on CRD reconciliation while the backend handles user-facing API requests with full authentication and authorization.

The controller implements a dual-mode ingress strategy — Istio VirtualServices or Kubernetes Gateway API HTTPRoutes — selected at deployment time via `USE_ISTIO` or `USE_KUBE_GATEWAY` flags (mutually exclusive). In Gateway API mode, the controller injects a kube-rbac-proxy sidecar into each workspace's StatefulSet, creates an HTTPRoute in the gateway namespace, and a cross-namespace ReferenceGrant to allow the HTTPRoute to reference the workspace's kube-rbac-proxy Service. This pattern integrates with RHOAI's platform-level Gateway (`data-science-gateway`) for centralized ingress.

TLS configuration on the controller is OpenShift-aware: it reads the cluster's TLS security profile from `apiservers.config.openshift.io/cluster` at startup and applies the appropriate cipher suites and minimum TLS version. A profile watcher triggers graceful restarts when the cluster TLS policy changes. On non-OpenShift clusters, it defaults to Mozilla Intermediate TLS (min TLS 1.2, AEAD cipher suites).

The controller's RBAC footprint is notable: it requires `pods/exec` create permission for workspace activity probing (detecting idle workspaces), and `clusterroles` bind permission on `system:auth-delegator` for creating kube-rbac-proxy ClusterRoleBindings. The backend similarly requires SubjectAccessReview create permission and broad read access across namespaces, secrets, pods, PVCs, and storage classes.

Caching strategy is deliberate: both the controller and backend disable controller-runtime's global cache for ConfigMaps and Secrets (to avoid memory pressure in large clusters) and instead use label-filtered caches for the specific `notebooks.kubeflow.org/image-source=true` ConfigMaps they need.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SubjectAccessReview; Kubernetes RBAC via aggregated ClusterRoles (admin/edit/view) | Kubernetes (RBAC) + Application (SAR) | Backend enforces SAR on every API call. Controller operates with its own SA, not user identity. |
| Data storage | Per-workspace PVCs in the workspace's namespace | Kubernetes (namespace isolation) | PVCs are namespace-scoped; cross-namespace access prevented by Kubernetes RBAC |
| Network traffic | Default-deny NetworkPolicy in controller namespace; per-workspace kube-rbac-proxy sidecar (Gateway mode); Istio AuthorizationPolicy restricts backend to gateway SA (Istio mode) | Kubernetes (NetworkPolicy) + kube-rbac-proxy / Istio | Full per-tenant network isolation depends on deployment mode |
| Compute & resources | Per-workspace StatefulSet with configurable resources; no ResourceQuota enforcement by the controller | Kubernetes (StatefulSet isolation) | Resource limits set per workspace via WorkspaceKind presets; no controller-enforced quota — relies on external ResourceQuota |
| Configuration & secrets | Per-namespace Secrets; Secrets and ConfigMaps cache disabled to avoid cross-namespace data in memory | Kubernetes (namespace) + Application (cache design) | Image source ConfigMaps filtered by label selector |
| API scoping | Backend delegates all operations through user's RBAC (SubjectAccessReview) | Kubernetes (RBAC) | User can only see/modify resources they have Kubernetes RBAC access to |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Controller (single instance) | Cluster-wide, operates across all namespaces | Controller uses its own SA; does not impersonate users |
| Backend API | Cluster-wide, but per-request SAR enforcement | Every API call authorized via SubjectAccessReview against caller's identity |
