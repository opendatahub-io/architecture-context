## Purpose

**Short**: ODH Dashboard is the unified web UI for Red Hat OpenShift AI, providing a React-based SPA with a modular micro-frontend architecture backed by domain-specific Go BFF services and managed by a Kubernetes operator.

**Detailed**: ODH Dashboard is a monorepo that produces the primary user-facing web interface for the Red Hat OpenShift AI (RHOAI) platform. It delivers a React 18 / PatternFly v6 single-page application that serves as the hub for data scientists and ML engineers to manage notebooks, model serving, model registry, pipelines, experiments, and generative AI workloads across OpenShift clusters.

The architecture follows a modular micro-frontend pattern using Webpack Module Federation (via Rspack). The host application (core-bff distribution) loads feature packages as federated remotes at runtime, enabling independent development, build, and deployment of feature verticals such as gen-ai, model-registry, maas, notebooks, eval-hub, mlflow, automl, autorag, agent-ops, data-connect-hub, and data-registry. Each feature package that requires backend integration ships its own Go-based Backend-for-Frontend (BFF) service, which proxies Kubernetes API calls, handles authentication token forwarding, and implements domain-specific business logic.

A co-located Kubernetes operator (`dashboard-operator`) manages the full lifecycle of the dashboard deployment. It reconciles a cluster-scoped `Dashboard` custom resource created by the parent `rhods-operator` / `opendatahub-operator`, rendering kustomize manifests, deploying the core dashboard and federated module pods via server-side apply, and managing per-module RBAC, services, network policies, and Gateway API HTTPRoutes. The operator also manages `Workspace` and `WorkspaceKind` CRDs from the Kubeflow Notebooks project for notebook workbench lifecycle management.

## Architectural Analysis

ODH Dashboard's most distinctive architectural decision is the combination of Webpack Module Federation with per-module Go BFF services, creating a true micro-frontend platform where each feature vertical is independently deployable as a separate container image. The core-bff distribution serves as the shell application and reverse proxy: it hosts the React SPA, proxies API calls to upstream platform services, and routes `/_mf/:name/*` requests to the appropriate federated module's static assets. Each BFF module runs as a separate Deployment with its own ServiceAccount, TLS certificates, and RBAC permissions, communicating with the Kubernetes API using either user token impersonation or internal service account credentials.

The operator follows the odh-platform-utilities patterns for manifest rendering and SSA-based deployment, including platform detection (ODH vs RHOAI), kustomize variable injection from `params.env` files, and condition-based status reporting. A notable design choice is that the operator manages not just the core dashboard but all module deployments — including their RBAC, network policies, and service resources — through a module registry that maps module definitions to kustomize overlays.

TLS handling is centralized in the `pkg/tls` package, which dynamically reads the OpenShift cluster-wide TLS security profile (`apiservers.config.openshift.io/cluster`) and configures Go `crypto/tls` accordingly. This means all BFF services inherit the cluster's TLS policy (Intermediate by default: TLS 1.2+, ECDHE cipher suites, ALPN h2/http/1.1) and support the post-quantum cryptography policy via the `ubi9/ubi-minimal-pqc` base image and `update-crypto-policies --set DEFAULT:PQ` in the Node.js frontend image.

Authentication is layered: the Node.js legacy backend uses `kube-rbac-proxy` as a sidecar for OpenShift OAuth-based authentication, while the Go BFF services implement their own authentication middleware with configurable token source (`--auth-method=user_token` or `--auth-method=internal`). User-scoped API calls use the forwarded access token for Kubernetes API impersonation, enforcing the user's native RBAC. Several BFF modules implement additional authorization gates via `SubjectAccessReview` and `SelfSubjectAccessReview` checks for fine-grained per-resource access control.

The admission webhook surface includes three validating webhooks (Dashboard CR, Workspace CR, WorkspaceKind CR) and one conversion webhook (WorkspaceKind) served by the operator on port 9443 with cert-manager-provisioned TLS.

| Data storage | Per-namespace resources (notebooks, PVCs, secrets) | Kubernetes namespace isolation | Cluster-scoped CRDs (WorkspaceKind, Dashboard) are admin-only |
| Network traffic | NetworkPolicy per module deployment | Kubernetes NetworkPolicy | Module pods have per-module network policies |

| Configuration & secrets | Per-namespace Secrets for user workloads; shared ConfigMap for dashboard config | Kubernetes / Application | OdhDashboardConfig is namespace-scoped but shared |
| API scoping | User-scoped K8s API calls via token impersonation; namespace filtering in BFF handlers | Application / Kubernetes RBAC | Namespace access validated via SelfSubjectAccessReview |
