## Purpose

**Short**: Kubernetes operator that reconciles a cluster-scoped singleton `Workbenches` CR and deploys the notebook controller stack (Kubeflow notebook controller, ODH notebook controller, and notebook manifests) on OpenShift.

**Detailed**: The workbenches-operator is a module operator within the ODH/RHOAI platform orchestration model. When the `Workbenches` CR's `managementState` is `Managed`, the operator renders committed upstream Kustomize manifests from `/opt/manifests`, overlays `RELATED_IMAGE_*` environment variables and CR-derived parameters (gateway domain, MLflow state, platform identity), and applies the resulting resources to the cluster via Server-Side Apply. It watches operand deployments for availability changes and computes a `ModuleStatus` lifecycle phase (`Pending` → `Initializing` → `Ready` → `Upgrading` → `Degraded` → `Failed`).

The operator also serves two mutating admission webhooks for Kubeflow `Notebook` resources: one injects connection secrets referenced by annotation, and another applies `HardwareProfile` settings (resources, nodeSelector, tolerations) and integrates with Kueue for workload scheduling. Webhook TLS is auto-detected at startup — OpenShift service-CA is preferred, falling back to cert-manager, and disabling webhooks when neither is available. The operator integrates with the OpenShift cluster-wide TLS security profile, applying its cipher and protocol version settings to both the metrics and webhook servers and performing a graceful shutdown when the profile changes.

## Architectural Analysis

The workbenches-operator follows a clean module-operator pattern where the platform orchestrator creates the singleton `Workbenches` CR and projects platform state (gateway domain, MLflow toggle, platform identity) into its spec fields. This decouples the operator from direct platform API dependencies — it reads only its own CRD plus a platform ConfigMap for version handshake, receiving all coordination indirectly.

The manifest rendering pipeline is notable: upstream operand manifests are fetched at development time and committed under `opt/manifests/` for hermetic container builds. At runtime the operator copies this immutable tree to a temporary directory, overlays image references from `RELATED_IMAGE_*` environment variables onto `params.env`/`params-latest.env`, merges CR-derived parameters, selects platform-specific overlays (ODH vs RHOAI notebooks), and applies via SSA with field manager `workbenches-operator`. This design ensures airgapped/disconnected builds work without network access at build or runtime.

The webhook architecture introduces an interesting dynamic TLS provisioning pattern. Rather than requiring a fixed TLS provider, the operator probes the cluster API at startup to detect available providers (OpenShift service-CA, cert-manager, or none) and configures itself accordingly, with a 30-second periodic retry for resources that appear after startup. This makes the operator deployable across vanilla Kubernetes (with cert-manager) and OpenShift without configuration changes.

The RBAC escalation role is architecturally significant: because the operator deploys upstream notebook controllers that define their own ClusterRoles, the workbenches-operator needs `bind` and `escalate` verbs on those specific role names. This creates a maintenance coupling — any upstream ClusterRole rename requires a corresponding update in `rbac_escalate_role.yaml`.

The ConfigMap informer cache is namespace-scoped to the applications namespace (or both ODH/RHOAI defaults when unset), reducing the operator's watch footprint while ensuring the platform version handshake works before the CR's platform field is known.
