## Purpose

**Short**: A batch-oriented evaluation framework that runs standardized language model benchmarks as Kubernetes jobs, reporting results to the EvalHub platform.

**Detailed**: lm-evaluation-harness is a downstream fork of EleutherAI's Language Model Evaluation Harness, adapted for Red Hat OpenShift AI. The upstream project provides a unified framework for testing generative language models across 60+ standard academic benchmarks (MMLU, HellaSwag, GSM8K, BBH, etc.) with support for multiple model backends including HuggingFace Transformers, vLLM, OpenAI-compatible APIs, and others.

The RHOAI adaptation wraps the upstream harness in an EvalHub adapter (`main.py`) that runs as a Kubernetes batch job. The adapter receives a job specification (mounted as `/meta/job.json`), configures the lm-eval harness to use `local-completions` (OpenAI-compatible) backends to evaluate a model served elsewhere in the cluster, and reports results back to EvalHub via callbacks. It also supports OCI artifact persistence via skopeo and MLflow experiment tracking.

The component includes support for disconnected/air-gapped deployments through automatic detection of local test data under `/test_data`, which triggers Hugging Face offline mode so that no external network calls are made to huggingface.co during evaluation.

## Architectural Analysis

The component follows a classic adapter pattern: the upstream lm-evaluation-harness library is the evaluation engine, while `main.py` implements the `FrameworkAdapter` interface from the `evalhub` SDK. The adapter's `run_benchmark_job` method orchestrates a five-phase lifecycle (Initialization → Loading Data → Running Evaluation → Post-Processing → Persisting Artifacts), with status updates sent to EvalHub at each transition.

A notable architectural decision is that model inference is never performed locally. The adapter always uses the `local-completions` backend, which sends prompts as HTTP requests to an external OpenAI-compatible API endpoint (typically a vLLM or other serving runtime running elsewhere in the cluster). This means the job container itself requires only CPU resources; GPU resources are allocated to the model serving infrastructure.

The disconnected-deployment detection (`_infer_auto_offline_from_local_test_data`) inspects the job spec's `parameters.tokenizer` field: if it points to a local path under `/test_data` and a sibling directory contains `dataset_dict.json`, the adapter sets all Hugging Face offline environment variables before the `lm_eval` library is imported. This import-order sensitivity is called out explicitly in the source as a constraint.

Security-wise, the adapter implements credential redaction for error messages (`_sanitize_error_message`) to prevent API keys, tokens, and other secrets from leaking into EvalHub callbacks. The job spec path is constrained to `/meta` via resolved path validation to prevent path traversal (CWE-22).

The Konflux build uses AIPCC base images (CPU and CUDA variants) and hermetic prefetch with separate pip requirements for CUDA (x86_64, aarch64) and CPU (ppc64le, s390x) architectures, plus RPM lockfiles. A dedup script (`scripts/dedup_prefetch_requirements.py`) handles hash conflicts between AIPCC-rebuilt pure-Python packages across the two indexes.
