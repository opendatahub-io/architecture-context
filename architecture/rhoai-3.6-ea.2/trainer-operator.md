## Purpose

**Short**: Kubernetes operator that reconciles the Trainer Module CR to deploy and manage upstream Kubeflow Trainer v2 resources on OpenShift AI.

**Detailed**: The trainer-operator is the ODH modular architecture controller for the Trainer component within Red Hat OpenShift AI. It watches a singleton cluster-scoped `Trainer` custom resource (`components.platform.opendatahub.io/v1alpha1`) and manages the full lifecycle of upstream Kubeflow Trainer v2 infrastructure — including CRDs, controller deployment, RBAC, webhooks, ClusterTrainingRuntimes, and ImageStreams.

The operator follows a manifest-rendering pipeline: at build time, upstream Kubeflow Trainer manifests are fetched into the container image; at runtime, these templates are copied to a writable work directory, RELATED_IMAGE environment variables are applied to override container image references, and kustomize rendering produces the final resource set. Resources are applied via Server-Side Apply (SSA) with field ownership, and garbage collection removes stale resources from previous versions using label-based discovery.

The operator integrates with the ODH platform utilities framework (`odh-platform-utilities`) for reconciliation actions, condition management, GC, and deployment status tracking. It validates the JobSet Operator as a hard dependency on OpenShift clusters, checking for OLM installation, the JobSetOperator CR health, and the JobSet CRD before proceeding with reconciliation. TLS configuration is dynamically resolved from the OpenShift cluster TLS profile, and a watcher triggers operator restart when the profile changes.

## Architectural Analysis

The trainer-operator embodies the ODH modular architecture pattern: a thin controller layer that acts as a deployment wrapper around upstream Kubeflow Trainer, rather than reimplementing training orchestration logic. The `odh-platform-utilities/framework` reconciler provides the structural skeleton — action chaining, condition management, finalizers, and GC — while the operator contributes domain-specific actions: dependency checking, namespace provisioning, manifest rendering, and legacy finalizer cleanup.

The manifest pipeline is the architectural centerpiece. Three independent resource sets (trainer core manifests, ClusterTrainingRuntimes, ImageStreams) are rendered from separate kustomize trees. The RHOAI overlay (`manifests/trainer/rhoai/`) adds namespace scoping, label selectors, ServiceMonitor, TLS RBAC, and progression-tracking RBAC on top of upstream bases. RELATED_IMAGE environment variables enable Konflux-compatible image pinning without modifying the manifest source, a critical requirement for disconnected and air-gapped deployments.

The dependency validation for JobSet Operator is notably thorough: on OpenShift, it checks OLM subscription presence, JobSetOperator CR existence, CR health via conditions (Degraded, Available), and the JobSet CRD itself. On non-OpenShift clusters it checks only the CRD. This graduated checking avoids startup failures on platforms where the operator lifecycle differs.

Cache scoping is tightly controlled. Label selectors restrict cached Deployments, Services, and ValidatingWebhookConfigurations to `platform.opendatahub.io/part-of=trainer`, and the APPLICATIONS_NAMESPACE environment variable bounds namespace watches. ConfigMaps are excluded from label filtering because the platform config ConfigMap (`odh-trainer-config`) is created by the platform operator without the trainer label. Namespace objects bypass the cache entirely (direct API reads) to prevent cluster-wide informers — a deliberate optimization against anti-pattern 3 documented in the codebase.

The TLS architecture resolves the cluster's TLS profile from `APIServer` resources at startup, constructs a `tls.Config` with appropriate cipher suites and protocol versions, and registers a watcher that cancels the manager context on profile changes — forcing a clean restart. This pattern ensures the operator always serves metrics with the cluster-mandated TLS profile, including support for the TLS adherence policy introduced in OpenShift 4.22+.

The GC strategy handles a subtle ownership challenge: cluster-scoped ClusterTrainingRuntimes cannot have owner references to the namespace-scoped Trainer CR. These are marked as "unremovable" in the normal GC cycle and instead cleaned up explicitly in the finalizer path via the dynamic client, which also strips the legacy `trainer.kubeflow.org/resource-in-use` finalizer that older Trainer versions added to runtime resources.
