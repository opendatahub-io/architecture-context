## Purpose

**Short**: Operational utilities and AI-agent-driven skills for diagnosing, benchmarking, and validating GPU networking and topology in llm-d prefill/decode disaggregated inference deployments.

**Detailed**: llm-d-pd-utils is a collection of Python scripts, shell installers, and Claude Code agentic skills that support operators running llm-d (the LLM disaggregated inference system). The repository provides three primary capabilities: (1) preflight checks that run before vLLM starts inside model server pods to gather GPU topology, NVLink status, CPU layout, and environment diagnostics — with an optional HTTP-server pause mode that gates vLLM startup until operators confirm the environment is ready; (2) automated networking test suites that discover pods, validate RDMA/RoCE connectivity, and measure inter-pod bandwidth and latency using perftest, iperf3, NCCL/RCCL collectives, and nixlbench (GPU VRAM-to-VRAM transfer via NIXL/UCX); and (3) a NIXL benchmarking tool with Kubernetes deployment manifests for measuring GPU-direct data transfer throughput between pods.

The repository does not deploy a long-running service or operator. Instead, it provides ephemeral diagnostic and benchmarking tooling that integrates with llm-d deployments via kustomize overlays, ConfigMaps, and `kubectl exec`. The agentic skills are designed to be invoked from Claude Code to guide operators through multi-step workflows (deploying configs, running tests, interpreting results) with minimal manual intervention.

## Architectural Analysis

llm-d-pd-utils occupies a unique position in the llm-d ecosystem as an operational diagnostics toolkit rather than a runtime component. Its architecture reflects this role: instead of controllers or long-running services, the repo delivers self-contained Python scripts that are injected into existing pods via ConfigMap mounts or run externally via `kubectl exec`.

The preflight checks system (`llm-d-preflight-checks.py`) implements a clever gating pattern: the script is chained before `vllm serve` using `&&` in the container command, so vLLM only starts if preflight exits 0. In `pause` mode, the script starts an HTTP server on the same port vLLM would use (typically 8000 or 8200), which satisfies Kubernetes health probes while keeping vLLM blocked. This allows operators to inspect the pod environment and run network tests with full GPU memory available (since vLLM hasn't allocated it yet). The `/exit` endpoint releases the port, allowing vLLM to bind and start normally.

The networking test suite (~9,000 lines of Python) is the most substantial component. It follows a modular architecture: `run-tests-common.py` provides shared utilities for pod discovery, `kubectl exec` wrappers, and SSH-based remote execution; specialized modules (`run-tests-perftest.py`, `run-tests-iperf3.py`, `run-tests-nccl-rccl.py`, `run-tests-nixlbench.py`) implement protocol-specific tests; and `run-tests-discovery.py` (~3,000 lines) handles GPU topology analysis including NVLink status, PCIe hierarchy, NUMA topology, and UCX transport configuration validation.

The NIXL benchmark (`benchmark.py`) uses PyTorch tensors for GPU memory allocation, the NIXL Python API for GPU-direct data transfer, and ZMQ for control-plane coordination between creator and peer agents. It supports multi-threaded transfer tests across multiple GPUs and measures throughput in GB/s.

The Kubernetes resources are intentionally minimal: raw Pods plus one NodePort Service, with no Deployment controller, reconciliation loop, CRD, operator RBAC, or kustomize composition. The server Pod is kept alive with `sleep infinity`, and the actual benchmark process is started interactively by `benchmarks/benchmark_deployment.sh`. The RoCE variants add Multus network attachment annotations, `IPC_LOCK` capability, shared memory mounts, and `nvidia.com/roce_gdr` resource requests.

A notable architectural artifact is that the Makefile contains extensive Go/kubebuilder scaffolding (controller-gen, kustomize, envtest targets) and a `Dockerfile copy` references a Go builder with `cmd/main.go`, `api/`, and `internal/` directories — but no Go source code, `go.mod`, or `config/` directory exists. The Go infrastructure is vestigial, likely leftover from an initial project scaffold.
