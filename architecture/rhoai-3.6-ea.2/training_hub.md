## Purpose

**Short**: Training Hub is an algorithm-focused Python library and CLI that provides a unified interface for common LLM training, continual learning, and reinforcement learning techniques.

**Detailed**: Training Hub (`training-hub` on PyPI) is a pure Python library developed by the Red Hat AI Innovation Team that abstracts multiple training backends behind a Strategy + Registry design pattern. It exposes seven training algorithms — Supervised Fine-Tuning (SFT), Orthogonal Subspace Fine-Tuning (OSFT), LoRA + SFT, LoRA + GRPO, full-parameter GRPO, GEPA gradient-free prompt optimization, and contrastive embedding fine-tuning — each backed by one or more swappable backend implementations (InstructLab-Training, Mini-Trainer, Unsloth, ART/OpenPipe, verl/Volcano Engine, GEPA, MLflow, SentenceTransformers).

The library is consumed as a Python package or via the `thub` CLI. It is not a deployed service and has no Kubernetes manifests, Dockerfiles, or container images of its own. It is designed to run inside GPU-equipped training pods (managed by components like Kubeflow or the Trainer Operator) and integrates with the RHOAI platform at the workload level — receiving training jobs and producing model checkpoints. Recent additions include JIT preemption checkpointing with SIGTERM handling, remote checkpoint mirroring to S3-compatible storage via fsspec, a unified callback abstraction that works across all backends, and a `thub` CLI for YAML-driven training workflows.

## Architectural Analysis

Training Hub's central design decision is the **Strategy + Registry** pattern: `Algorithm` and `Backend` are abstract base classes; `AlgorithmRegistry` maps string names to classes and backends to algorithms. Convenience functions (`sft()`, `osft()`, `lora_sft()`, etc.) wrap the registry lookup into a single call. This means adding a new training algorithm or a new backend for an existing algorithm is a two-line registration plus one class implementation, with no changes to the core dispatch code.

The codebase splits into three layers: (1) the algorithm/backend core (`algorithms/`), (2) backend-specific adapter bridges (`adapters/`) that translate TrainingHubCallback lifecycle hooks into each trainer's native callback interface, including serialization across the torchrun subprocess boundary, and (3) infrastructure concerns — JIT preemption checkpointing (`jit_checkpoint.py`, `checkpoint_manager.py`, `checkpoint_utils.py`), GPU memory estimation (`profiling/`), loss visualization, and the CLI.

A notable architectural risk is the **torchrun subprocess boundary**: SFT and OSFT backends launch training via `torchrun`, which spawns new processes where Python closures and instance state do not survive. Callbacks are serialized via `inspect.getsource` + base64 encoding, requiring them to be defined at module level with no closure captures. The GRPO/ART backend uses `mp.spawn`, which imposes similar pickling constraints. The verl backend delegates entirely to a subprocess (`verl.trainer.main_ppo`) orchestrated via Hydra CLI overrides, meaning parameter forwarding must be manually maintained.

Checkpoint management is layered: HuggingFace-style `checkpoint-{step}` dirs for LoRA, Mini-Trainer `full_state_checkpoints/step_{n}` for OSFT, and InstructLab `full_state/epoch_{n}` for SFT. The JIT system intercepts SIGTERM, coordinates across ranks via `all_reduce`, and saves at the next step boundary. Remote mirroring uses a background LIFO uploader with hardlink staging to avoid data races with `save_total_limit` rotation.

### SFT Algorithm

**Intent**: Supervised fine-tuning of language models on instruction/chat datasets. Primary algorithm for full-parameter fine-tuning.
**Backend**: `instructlab-training` (InstructLab-Training library)
**Features**: Multi-GPU/multi-node via torchrun, continual pretraining mode, on-demand checkpointing

### OSFT Algorithm

**Intent**: Orthogonal Subspace Fine-Tuning — fine-tune models while controlling how much existing behavior to preserve via unfreeze_rank_ratio.
**Backend**: `mini-trainer` (RHAI Innovation Mini-Trainer)
**Features**: FSDP distributed training, AdamW post-step re-projection, Liger kernel support, on-demand checkpointing

### LoRA + GRPO / GRPO Algorithm

**Intent**: Reinforcement learning from verifiable rewards using Group Relative Policy Optimization. Supports both LoRA adapter training and full-parameter fine-tuning.
**Backend**: `art` (OpenPipe ART, single-GPU) and `verl` (Volcano Engine RL, multi-GPU FSDP + vLLM)
**Features**: Tool-call verification, custom reward functions, multi-turn agentic rollouts, Dr. GRPO variant

### GEPA Algorithm

**Intent**: Gradient-free prompt optimization using evolutionary search with Pareto-based selection and LLM-driven reflection. No GPU required — optimizes prompts via API calls.
**Backend**: `gepa` (direct `gepa.optimize()`) and `mlflow` (MLflow prompt registry, scorers, tracking)

### Embedding SFT Algorithm

**Intent**: Contrastive fine-tuning of sentence embedding models for semantic routing, classification, retrieval, and deduplication.
**Backend**: `sentence-transformers` (SentenceTransformers >=5.0)
**Features**: Three contrastive losses (batch_all_triplet, batch_hard_triplet, MNRL), GROUP_BY_LABEL batch sampling
