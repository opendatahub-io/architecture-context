## Purpose

**Short**: A typed, phased policy engine library for AI agent traffic that decides who may call which tool, what data comes back, and where that data is allowed to go next.

**Detailed**: The Praxis Policy Engine (PPE) is a Rust library crate (`praxis-policy`) that implements authorization, identity resolution, credential delegation, data-flow control, and audit for AI agent traffic. It is embedded by the Praxis proxy and potentially other host processes — it is not a standalone service but a library linked into a host binary. The host places it at an enforcement boundary (gateway, egress sidecar, or in-framework) and PPE evaluates Authorization Policy Language (APL) rules at that boundary for every operation an agent attempts.

PPE treats the LLM driving an agent as a compromised actor: it sits between the model's decisions and every capability, evaluating policy against cryptographically verified identity, PDP decisions, and session taint state that the model cannot forge. The engine ships nine bundled extension plugins (JWT identity, API-key identity, OAuth delegation, CIBA elicitation, Cedar/CEL/OPA decision points, Valkey session store, Vault secrets), each behind a Cargo feature. Additional plugins can be written against the `PluginFactory` trait in `praxis-policy-core`. The library publishes to crates.io and is versioned together across all workspace crates at v0.4.1.

## Architectural Analysis

PPE's architecture follows a Reference Monitor design: every operation crosses a single enforcement boundary, and the engine evaluates a declarative policy at that boundary. The architecture is structured as a layered Cargo workspace with strict dependency ordering — the facade crate (`praxis-policy`) re-exports the core runtime and optionally the builtin extensions, while internal crates flow in one direction: `ppe → ppe-apl-runtime → ppe-apl-cmf → ppe-apl-core`, plus `ppe → ppe-core` and `ppe → ppe-orchestration`.

The plugin runtime uses a five-phase execution model (sequential → transform → audit → concurrent → fire_and_forget) with strict invariants: sequential and concurrent plugins can block, transform and audit cannot, and fire-and-forget runs after the verdict is returned. Every degraded path (plugin panic, error, timeout) resolves to deny in blocking phases, never fail-open — a critical safety property backed by a fault-injection test catalog documented in `docs/safety-invariants.md`.

The three bundled policy decision points (Cedar, CEL, OPA) are held to semantic equivalence by a differential test suite (`ppe-pdp-diff`) that detects disagreements across their shared boolean, integer, string, and string-set subset. This means policy can be expressed in any of the three languages with the same authorization semantics, and migrating between them is a policy change rather than a behavioral change.

The engine's TLS stack (via the optional `http-hyper` feature) is rustls-based, using `ring` as the cryptographic provider. The `jsonwebtoken` crate uses `aws-lc-rs` for JWT operations. Both crypto providers are present in the dependency graph — `ring` for TLS and `aws-lc-rs` for JWT — with the deliberate choice of `aws-lc-rs` for JWT to avoid pulling the `rsa` crate (which carries RUSTSEC-2023-0071) into the runtime tree. The library forbids `unsafe` code workspace-wide and denies all panic-sourcing clippy lints (`unwrap_used`, `panic`, `expect_used`, `indexing_slicing`), enforcing an unusually strict safety posture for a Rust crate.

The audit subsystem is architecturally distinctive: it records both decisions (how the pipeline ruled) and effects (irreversible external acts like token minting), with effects written ahead of the act via `fsync` to provide crash-recovery guarantees. Content provenance uses HMAC-SHA256 digests under an operator-supplied key rather than recording payload content, preserving redaction guarantees. The audit stream supports tamper-evident sequencing with per-epoch, per-stream monotonic counters and W3C trace context integration.

The secrets subsystem supports three provider kinds (`file`, `env`, `vault`), with values resolved at startup and refreshable via `refresh_secrets()`. Secret values are named indirectly through declared values, never raw references, keeping the addressable set finite and auditable from the policy document.
