## Purpose

**Short**: Envoy ExtProc server that runs Praxis filter pipelines for HTTP request/response inspection, mutation, and rejection alongside Envoy proxy in the MaaS gateway.

**Detailed**: praxis-extproc is a Rust-based gRPC service that implements the Envoy External Processing (ExtProc) protocol. It translates bidirectional ExtProc gRPC messages from Envoy into Praxis `FilterPipeline` invocations, allowing filter chains to inspect and mutate HTTP headers and bodies, rewrite request paths, or reject requests with immediate responses — all without replacing Envoy as the data plane.

The component is deployed as two instances in the MaaS gateway namespace (`openshift-ingress`): a **pre-auth processor** (`payload-pre-processing`) running before Kuadrant/RHCL authentication that promotes model names to routing headers, and a **post-auth processor** (`payload-processing`) running after authentication for full request/response processing. Both are injected into the Envoy filter chain via Istio `EnvoyFilter` resources positioned relative to the auth plugin.

praxis-extproc supports three body processing modes (buffered, streamed, and full-duplex streamed) with proper end-of-stream tracking, 10 MiB body accumulation limits, and 62 KiB chunk splitting for streamed responses. It includes runtime FIPS approved-mode detection via OpenSSL provider probing, a gRPC health check service for Kubernetes readiness probes, and a Prometheus metrics endpoint.

## Architectural Analysis

praxis-extproc follows a clean sidecar-service architecture where Envoy owns networking and routing while this component owns request/response processing logic. The design separates concerns into well-defined modules: the `server` module implements the `ExternalProcessor` gRPC trait with per-stream `StreamState` tracking, the `adapter` module translates between Envoy protobuf types and Praxis filter types, and the `response` module builds well-formed `ProcessingResponse` messages with proper body chunking.

A notable architectural pattern is the dual-instance deployment model. The pre-auth instance runs a lightweight filter chain (`model_to_header` + `llmisvc_model_provider_resolver`) for extracting AI model identifiers from request bodies and promoting them to HTTP headers before authentication. This enables the gateway to route based on model name without having parsed the full request body. The post-auth instance runs a configurable filter chain for full request/response processing. Both instances share the same binary and differ only in their YAML configuration.

The FIPS approach is distinctive for a Rust component: rather than compile-time linking against a specific crypto provider, the code uses the `openssl` crate bound to system OpenSSL and probes at startup whether the FIPS provider is active (MD5 refusal + FIPS provider load). The `fips` cargo feature gates this as a hard requirement, refusing to serve traffic if FIPS is required but not detected. This design delegates FIPS enforcement to the host OS configuration rather than build-time flags.

The stream handler maintains careful per-direction phase ordering (request and response phases progress independently through Headers → Body → Trailers, allowing full-duplex interleaving) and per-phase end-of-stream tracking via `EosTracker`. Filter state is preserved across request-to-response phase boundaries via `StreamState`, enabling filters that store typed state during request processing to read it back during response processing.

TLS termination uses the `openssl` crate directly with `tokio-openssl` for async I/O, supporting plaintext, self-signed (ephemeral P-256 cert), and provided certificate modes, plus optional mTLS client verification. The Dockerfile forces system OpenSSL via `OPENSSL_NO_VENDOR=1`, ensuring the runtime binary links against UBI9's `libssl.so.3`. The self-signed mode uses `PkeyCtx::new_id(Id::EC)` with `NID_X9_62_prime256v1` — the EVP keygen path that is compatible with the OpenSSL FIPS provider, unlike the legacy `EcKey::generate` path.

The EnvoyFilter configuration in the ODH overlay handles four different Istio version ranges (≤1.25, 1.26–1.29, ≥1.30 with TrafficExtension, and RHCL 1.4 with WASM), with the pre-auth filter using `failure_mode_allow: true` (fail-open) and the post-auth filter using `failure_mode_allow: false` (fail-closed). Per-route disabling prevents ExtProc from running on non-inference routes (models, subscriptions, api-keys, maas-api).
