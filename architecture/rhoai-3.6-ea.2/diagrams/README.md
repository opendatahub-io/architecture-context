## Diagram Descriptions

### Component Dependency Graph
Shows how platform components depend on each other. Central components (most dependencies) are highlighted. Organized by tier: Core Platform Services (prometheus-operator, cert-manager, Gateway API), Meta-Operator (rhods-operator), Model Serving (KServe, odh-model-controller, llm-d), MaaS (models-as-a-service, ai-gateway-controller, praxis-extproc), ML Workflows (Pipelines, Feast, MLflow), User-Facing (Dashboard, Workbenches, Model Registry), and Gateway Infrastructure. Useful for understanding blast radius of changes and planning upgrades.

### Platform Network Topology
Complete network architecture showing all ingress points, service mesh communication, and egress destinations. Covers the dual-gateway architecture (data-science-gateway with kube-auth-proxy ext_authz, maas-default-gateway with Kuadrant/Authorino + praxis-extproc), LLM serving gateways, and legacy OpenShift Routes. Includes exact port numbers, protocols, encryption, and authentication mechanisms.

**Two formats provided**:
- **Mermaid (.mmd)**: Visual diagram with color-coded trust zones. Great for presentations and architecture discussions.
- **ASCII (.txt)**: Precise text format with no ambiguity. Required for SAR (Security Architecture Review) submissions and compliance documentation.

Both formats contain the same information — use Mermaid for visual clarity, ASCII for security reviews.

### Cross-Component Workflows
Sequence diagrams showing four end-to-end workflows:
1. **Model Deployment via Dashboard** — InferenceService creation through KServe with storage-initializer and gateway routing
2. **MaaS External Model Access** — AITenant setup, API key authentication, praxis-extproc payload processing, external provider routing
3. **LLM-D Disaggregated Inference** — EPP routing, prefill/decode split, NIXL KV-cache transfer, streaming response
4. **Data Science Pipeline Execution** — Pipeline run through Argo Workflows with ml-metadata lineage tracking

### Platform Security Overview
Visual representation of security architecture including:
- **Authentication mechanisms**: 7 patterns (ext_authz, Kuadrant, kube-rbac-proxy, SA tokens, controller-runtime, OpenShift OAuth, TokenReview)
- **Gateway auth chains**: Detailed filter chain composition for each gateway type
- **Webhook attack surface**: 213 total webhooks across 17 components, including cross-component mutation targets
- **TLS configuration**: Webhook TLS, metrics TLS, gateway TLS, cluster-derived TLS profiles, self-signed certificate validation
- **Container security**: UBI 9 pqc, strictfipsruntime, Rust FIPS probe, non-root, digest-pinned, RPM lockfiles
- **Service mesh security**: Istio revision labeling, DestinationRules, EnvoyFilters, VirtualServices

### Platform Observability
Maps all monitoring and observability endpoints:
- **Prometheus scrape targets**: 12 components with kube-rbac-proxy or controller-runtime auth on metrics endpoints
- **Health probes**: Liveness and readiness probes per component (controller-runtime standard :8081, dashboard :8080)
- **Monitoring injection**: odh-observability mutating webhooks for platform label injection into ServiceMonitor/PodMonitor resources
- **Webhook health**: 213 admission webhooks with Fail policy — any certificate expiry blocks API operations

### Platform Maturity Dashboard
High-level metrics about platform health:
- **93 components**, 28 operator-based, 599 container images, 166 CRDs across 37 API groups
- **Gateway architecture**: 2 primary gateways + on-demand LLM serving + XKS gateway + legacy Routes
- **Security**: MIXED mTLS, FIPS via strictfipsruntime + UBI 9 pqc, cluster-derived TLS profiles
- **API maturity**: v1 (stable core), v1beta1 (near-stable serving), v1alpha1/v1alpha2 (evolving LLM + MaaS)
- **Deployment**: Disconnected support, multi-arch (amd64 full, arm64/ppc64le/s390x partial), XKS multi-cloud
- **Serving evolution**: 5 serving paths from single-model to disaggregated to batch inference
