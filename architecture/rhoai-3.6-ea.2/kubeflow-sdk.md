## Purpose

**Short**: A unified Python SDK that provides high-level APIs for managing ML workloads across Kubeflow projects — Trainer, Optimizer, Spark, Hub (Model Registry), and Pipelines — without requiring users to learn Kubernetes.

**Detailed**: The Kubeflow SDK (`kubeflow` Python package) is a client-side library that abstracts Kubernetes-native ML infrastructure behind Pythonic APIs. It supports multiple execution backends: a Kubernetes backend that creates and manages CRs (TrainJob, Experiment, SparkConnect) via the Kubernetes Python client, a container backend (Docker/Podman) for local development, and a subprocess backend for quick prototyping. The SDK is not itself deployed as a service — it runs in user environments (notebooks, CI pipelines, local machines) and communicates with cluster-side operators and services.

The opendatahub-io fork extends the upstream kubeflow/sdk with an RHAI-specific module (`kubeflow.trainer.rhai`) that adds three trainer implementations: `TransformersTrainer` for HuggingFace/TRL with auto-instrumented progression tracking and checkpointing to PVC or S3, `TrainingHubTrainer` for Red Hat AI Training Hub integration, and `SpeculativeDecodingTrainer` for Eagle3/DFlash/MTP/PEAGLE draft model training via the speculators library. These trainers generate code that is injected into training pods via `inspect.getsource()`, including HTTP metrics servers and checkpoint managers, ensuring the SDK itself never runs inside the cluster.

## Architectural Analysis

The kubeflow-sdk follows a backend-abstraction pattern where each subproject (Trainer, Optimizer, Spark, Hub, Pipelines) exposes a stateless client class (`TrainerClient`, `OptimizerClient`, `SparkClient`, `ModelRegistryClient`, `PipelinesClient`) backed by pluggable execution backends. The Kubernetes backend is the primary production path, constructing CRs from user-provided dataclass configurations and submitting them via the `kubernetes` Python client. The container and localprocess backends provide development-time parity.

A distinguishing architectural choice is the code-injection pattern used by the RHAI trainers. Rather than shipping training instrumentation as a separate container image or sidecar, the SDK serializes Python functions and instrumentation callbacks via `inspect.getsource()` and embeds them directly into the pod's entrypoint command. This keeps the SDK's RHAI extensions self-contained within the library — no additional images or deployed components are needed — but creates a tight coupling between the SDK version and the generated training code.

The RHAI module's progression tracking injects an HTTP metrics server (default port 28080) into training pods, exposing training progress via a JSON API endpoint. This allows cluster-side controllers to poll training status without log parsing. The checkpoint instrumentation similarly injects code that handles PVC volume mounts, S3 cloud storage uploads with configurable SSL verification, and SIGTERM-based just-in-time checkpointing.

The SDK references several Kubeflow API groups (`trainer.kubeflow.org/v1alpha1`, `kubeflow.org/v1beta1`, `sparkoperator.k8s.io/v1alpha1`) and OpenDataHub annotations (`trainer.opendatahub.io/*`) but does not define or install CRDs itself — it is a consumer of APIs provided by server-side operators (Kubeflow Trainer, Katib/Optimizer, Spark Operator, Model Registry).
