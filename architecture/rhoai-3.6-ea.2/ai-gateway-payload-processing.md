## Purpose

**Short**: Envoy External Processor (ext-proc) that intercepts AI Gateway inference traffic to resolve model-to-provider mappings, translate API formats, inject credentials, and enforce guardrails — with Kubernetes controllers that reconcile the routing and networking resources needed to reach external LLM providers.

**Detailed**: ai-gateway-payload-processing is the payload processing layer of the RHOAI AI Gateway (MaaS). It runs as a gRPC External Processor attached to an Envoy-based Gateway via an Istio EnvoyFilter. On every inference request, the ext-proc pipeline resolves the client-facing model name to an external LLM provider (OpenAI, Anthropic, Azure, AWS Bedrock, Vertex AI, or a remote MaaS cluster), rewrites the request path and body to the provider's native API format, injects API credentials from Kubernetes Secrets, and optionally enforces NVIDIA NeMo guardrails on request and response content. The processing pipeline is built on the upstream `llm-d-inference-payload-processor` (IPP) framework, extended with downstream-only plugins and a dynamic-metadata wrapper that converts pseudo-headers into Envoy DynamicMetadata for inter-filter communication.

Two Kubernetes controllers complement the ext-proc server. The **ExternalProvider controller** reconciles `ExternalProvider` CRs into ExternalName Services, Istio ServiceEntries, and DestinationRules that give the Envoy data plane reachability to external provider endpoints. The **ExternalModel controller** reconciles `ExternalModel` CRs into Gateway API HTTPRoutes that route client traffic — keyed on the `x-ipp-selected-provider` header set by the ext-proc — to the correct provider backend. A **legacy migration controller** watches deprecated `maas.opendatahub.io/v1alpha1 ExternalModel` CRs and creates corresponding `inference.opendatahub.io` resources, enabling zero-downtime CRD migration. The component also supports a **hub mode** for cross-cluster routing, where a hub cluster proposes eligible spoke endpoints via DynamicMetadata and a spoke cluster transforms the request for the final provider.

## Architectural Analysis

The component's architecture splits cleanly between a data-plane gRPC service (the ext-proc) and a control-plane set of Kubernetes controllers, both running in a single process managed by controller-runtime.

The ext-proc pipeline follows a plugin architecture inherited from the upstream `llm-d-inference-payload-processor` framework. Upstream provides the IPP server skeleton, plugin lifecycle, CycleState for inter-plugin data passing, and a library of model-selection plugins (weighted random, max-score, session affinity). Downstream adds the domain-specific plugins: `model-provider-resolver` (the core plugin that watches ExternalModel/ExternalProvider CRDs and drives routing), `api-translation` (OpenAI ↔ Anthropic format conversion), `apikey-injection` (reads Secrets and injects Authorization headers), `maas-headers-guard` (validates required headers), `stream-usage-enforcer` (ensures streaming responses include usage data), `nemo` request/response guardrails, and `external-metering`. The downstream `dynamicmetadata.WrapServer` interceptor is the key architectural divergence from upstream: it intercepts every ext-proc response to extract a JSON pseudo-header and convert it into Envoy `ProcessingResponse.DynamicMetadata`, because the upstream framework has no hook for this.

The controller architecture is straightforward: ExternalProvider creates networking plumbing (ExternalName Service, ServiceEntry, DestinationRule), ExternalModel creates HTTPRoutes with per-provider match rules on the `x-ipp-selected-provider` header. The model-provider-resolver plugin also runs its own reconcilers to build an in-memory store of model-to-provider mappings, separate from the controller reconcilers. This dual-reconciler pattern means the ext-proc and controllers share CRD watches but serve different purposes.

A notable security consideration is that the ext-proc gRPC server has no application-level authentication — it relies on network-level isolation (same namespace as the Gateway, Istio mesh). The metrics endpoint optionally enables controller-runtime's authentication and authorization via a `--metrics-endpoint-auth` flag. The NeMo guardrail integration enforces HTTPS-only with TLS 1.2 minimum, and the ExternalProvider controller validates that credentials are never sent over plaintext (CWE-319).

Hub mode introduces cross-cluster routing complexity: in PROPOSE phase the plugin advertises eligible spoke endpoints via DynamicMetadata for the EPP to filter; in TRANSFORM phase on the spoke cluster, the request is rewritten for the final provider. Routing loop detection (comparing `X-Origin-Cluster` against the local `CLUSTER_NAME`) prevents A→B→A cycles.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-provider credentials via namespace-scoped Secrets | Application (apikey-injection plugin reads Secret from CR's namespace) | ext-proc runs with ClusterRole and can read Secrets across namespaces when multiNamespace=true |
| Data storage | No persistent storage; in-memory model-provider store | Application | In-memory store is shared across all namespaces in multi-namespace mode |
| Network traffic | Istio ServiceEntry/DestinationRule per provider, namespace-scoped | Istio + Application | No NetworkPolicy generated by the chart |
| Compute & resources | Single shared ext-proc process for all namespaces | Kubernetes (Pod resource limits via Helm values) | No per-tenant resource quotas |
| Configuration & secrets | Per-namespace ExternalProvider with namespace-scoped SecretRef | Kubernetes + Application | ValidateConnectionSecurity prevents plaintext credential transmission |
| API scoping | NAMESPACE env var can restrict cache to single namespace; default is cluster-wide | Application | Cluster-wide mode processes all namespaces' CRDs in a single process |
