## Purpose

**Short**: Asynchronous queue-based processor that pulls latency-insensitive inference requests from message brokers and dispatches them to llm-d-router or other inference gateways, using capacity-aware gating to fill slack GPU capacity.

**Detailed**: llm-d-async (the "Async Processor" or AP) is a composable Go service designed for processing inference workloads where latency is not the primary constraint (SLOs on the order of minutes). It functions as an asynchronous worker that pulls jobs from a message queue (Redis sorted sets, Redis pub/sub, or GCP Pub/Sub), evaluates dispatch gates based on real-time system capacity metrics from Prometheus or direct endpoint scraping, and forwards requests to `llm-d-router` or another inference gateway. This decouples job submission from immediate execution, enabling use cases such as bulk summarization, product classification, and near-realtime sentiment analysis without blocking real-time serving traffic.

The architecture follows a "Bring Your Own Queue" (BYOQ) principle where all prioritization, routing, retries, and scaling are decoupled from the message queue implementation. The processor does not expose a user-facing API; instead, it interacts solely with message queues via a `Producer` interface, making it composable with offline batch processing and asynchronous workflows. When real-time traffic spikes or errors occur, the system performs intelligent retries with exponential backoff and deadline-based expiration. The component is organized as a multi-module Go repository (root, `api/`, `pipeline/`, `producer/`) with a Helm chart for Kubernetes deployment.

## Architectural Analysis

llm-d-async's core design centers on a pipeline-based flow architecture with three transport implementations behind a unified `Flow` interface (`pipeline.Flow`). Each transport (Redis pub/sub, Redis sorted set, GCP Pub/Sub) implements the same lifecycle methods — `Start`, `StopConsuming`, `Shutdown` — enabling transport selection at startup without changing application logic.

The dispatch gate system is the most architecturally significant subsystem. Gates come in two flavors — budget gates (returning a capacity fraction in [0,1]) and admission gates (issuing per-message verdicts) — and operate at two levels: queue-level gates that refuse or continue individual messages at admission, and pool-level gates that regulate capacity shared by all queues routed to a worker pool. The `composite` and `wait-on-refuse` combinator gates allow assembling complex gating policies from primitives. The `redis-leased-rate` gate implements an external control plane contract (`llm-d.ai/v1alpha1`) where controllers write rate-limit leases as Redis hash transactions, enabling the llm-d-planner to dynamically cap batch dispatch rates without direct API coupling.

Worker concurrency is managed through named worker pools, where each pool has a fixed number of workers and its own merged request channel. The merge policy (random-robin or tier-priority) merges messages from multiple queues per pool, providing backpressure isolation — a saturated pool blocks only its own merged channel. The tier-priority policy implements six strict priority lanes from (reserved, interactive) to (overflow, batch), enabling fine-grained traffic differentiation.

The codebase uses `controller-runtime` not as an operator framework but for its signal handling, structured logging (via `logr`), and authenticated metrics server infrastructure. The component creates no CRDs, watches no Kubernetes resources, and runs no reconciliation loops.

TLS for outbound connections to inference gateways is configurable via CLI flags with CA certificate validation, mTLS support, and a minimum protocol version of TLS 1.2. The `InsecureSkipVerify` option exists for dev/test only. Redis connection URLs support TLS via the `rediss://` scheme.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-tenant auth — trusts queue-level access control | Message broker (Redis ACLs, GCP IAM) | Tenants with queue write access can submit requests as any userid |
| Data storage | Per-request results keyed by request ID; optional per-request result queues | Application (Redis sorted set) | Result IDs are caller-assigned; collision causes cross-tenant result leakage |
| Network traffic | None at the AP level — delegates to broker-level isolation | Message broker / Kubernetes NetworkPolicy | No network-level tenant isolation within the AP |
| Compute & resources | Per-attribute rate limiting via redis-quota gate; worker pool concurrency caps | Application (dispatch gates) | Rate limits are advisory within the processor; no hard resource isolation |
| Configuration & secrets | Shared configuration across all tenants | Application | Single transport config serves all tenants |
| API scoping | Fairness identity header (x-llm-d-inference-fairness-id) stamped per tenant for downstream flow control | Application (merge policy) | Fairness stamping relies on metadata attribute presence |
