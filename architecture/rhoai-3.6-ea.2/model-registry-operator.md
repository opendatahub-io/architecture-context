## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry instances, Model Catalog, and AIHub resources on the RHOAI platform.

**Detailed**: The model-registry-operator is a kubebuilder-based operator that deploys and manages Model Registry instances from `ModelRegistry` custom resources. Each ModelRegistry CR is reconciled into a full deployment stack including a REST API server (backed by the model-registry container image), a PostgreSQL database, a kube-rbac-proxy authentication sidecar, Kubernetes Services, OpenShift Routes, and Gateway API HTTPRoutes for ingress.

The operator also manages the Model Catalog subsystem through a `Catalog` CR and the higher-level `AIHub` CR that composes catalog and other AI platform services. The Catalog controller deploys a catalog service with its own PostgreSQL database, kube-rbac-proxy sidecar, and networking configuration. The AIHub controller orchestrates the lifecycle of child Catalog resources and associated RBAC, webhooks, and deployment infrastructure.

At startup the operator probes the Kubernetes discovery API to detect cluster capabilities (OpenShift, User API, Config API, Auth API) and conditionally enables OpenShift Routes, user group management, and TLS profile adherence. It supports both Gateway API (via the platform's `data-science-gateway`) and legacy OpenShift Route ingress patterns, with kube-rbac-proxy replacing the deprecated oauth-proxy for authentication.

## Architectural Analysis

The model-registry-operator follows a three-controller architecture where each controller manages a distinct CRD at a different abstraction level. The ModelRegistryReconciler handles individual registry instances, creating per-registry deployments, databases, services, RBAC, NetworkPolicies, and ingress resources. The CatalogReconciler manages a single shared model catalog deployment with its own database and ingress. The AIHubReconciler sits above both, managing the cluster-scoped AIHub CR that orchestrates Catalog lifecycle and platform-wide RBAC and webhook infrastructure.

A key design pattern is template-based resource creation using Go `text/template` files embedded via `//go:embed`. All Kubernetes resources created by the controllers (Deployments, Services, Routes, NetworkPolicies, RBAC) are rendered from `.yaml.tmpl` templates parameterized with CR spec values. This separates resource structure from controller logic and makes the resource shapes auditable without reading Go code.

The operator employs a label-filtered controller-runtime cache (`app.kubernetes.io/created-by: model-registry-operator`) to minimize API server load -- only operator-created resources are cached. Secrets bypass the cache entirely (`DisableFor`) because they are user-provided (database credentials, TLS certificates) and lack operator labels. ConfigMaps in the target namespace are cached without label filtering to support user-created catalog source ConfigMaps.

TLS configuration is cluster-aware: on OpenShift, the operator fetches the cluster TLS security profile via `openshift/controller-runtime-common` and applies it to both webhook and metrics servers. A `SecurityProfileWatcher` monitors for TLS profile changes and triggers graceful pod restart to reload the configuration. This pattern ensures the operator tracks cluster-wide TLS policy changes without manual intervention.

The CRD storage version migration subsystem (`internal/migration/`) handles v1alpha1-to-v1beta1 migration using a strategy pattern that supports both manual CR rewriting and the Kubernetes StorageVersionMigration API. A conversion webhook at `/convert` handles runtime conversion between API versions.

Security enforcement follows a sidecar proxy pattern: each model registry and catalog deployment includes a kube-rbac-proxy container (port 8443) that fronts the application container (port 8080), performing TokenReview and SubjectAccessReview against the Kubernetes API before proxying authenticated requests. Per-registry user access is controlled through OpenShift Groups -- the operator creates a `{registry-name}-users` group and binds it to a `registry-user-{registry-name}` role scoped to that registry's namespace. The legacy OAuth proxy mode is detected and auto-migrated to kube-rbac-proxy during reconciliation.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-registry kube-rbac-proxy with dedicated ServiceAccount; per-registry OpenShift Group for user access | Kubernetes (kube-rbac-proxy, RBAC) | Group-based access control depends on OpenShift User API availability (HasUserAPI capability) |
| Data storage | Per-registry PostgreSQL deployment in the registry namespace; separate database credentials per registry | Kubernetes (namespace isolation) | No cross-registry data access possible by design |
| Network traffic | Per-registry NetworkPolicy (`{registry-name}-https-route`, `{registry-name}-postgres`) restricts traffic to authorized sources | Kubernetes (NetworkPolicy) | NetworkPolicy enforcement depends on CNI plugin |
| Compute & resources | Default ResourceRequirements (100m CPU, 256Mi memory requests) applied to registry and catalog containers | Application (controller defaults) | No per-tenant ResourceQuota enforcement by the operator |
| Configuration & secrets | Per-registry Secrets for database credentials and TLS; user-provided Secrets for external DB not cached (direct API reads) | Kubernetes (namespace scoping) | Secrets bypass cache; direct API reads add latency |
| API scoping | Operator cache filtered by `app.kubernetes.io/created-by` label; watches scoped to operator-created resources | Kubernetes (controller-runtime cache) | ConfigMaps cached per-namespace without label filter for user-created catalog sources |
