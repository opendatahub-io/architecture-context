## Purpose

**Short**: AI Grid Network (AGN) is a distributed control plane that connects AI inference backends across Kubernetes clusters, cloud providers, and third-party APIs into a single routable mesh, producing routing overlays that the Praxis AI gateway consumes at request time.

**Detailed**: AGN is an orchestration daemon — never in the request path — that manages multi-site AI inference routing. The grid-operator watches four Cluster-scoped CRDs (`GridNetwork`, `GridSite`, `InferenceProvider`, `AgentToolProvider`) and uses the SWIM gossip protocol (via the `foca` crate) for peer discovery across clusters. Provider state is propagated through delta CRDTs (LWW registers, OR-Sets, G-Counters), scored by a pluggable scoring engine (strategies: `noMetrics`, `queueDepth`, `kvCachePressure`), and rendered into a versioned ConfigMap routing overlay that each site's Praxis AI gateway hot-reloads without restarts.

The project is structured as a Rust workspace (edition 2024, resolver 3) containing 14 crates. The core `operator` crate implements the Kubernetes controllers, SWIM runtime, and overlay renderer. Supporting crates handle certificate lifecycle and mTLS (`certs`), CRDT replication (`crdt`), gossip protocol wrapping (`swim`), scoring logic (`scoring`), overlay delivery as a sidecar (`overlay-sync`), site enrollment with a CA-pinned enrollment server (`enrollment`), metrics signal scraping (`signals`, `signals-client`), an opt-in fleet dashboard (`fleet-dashboard`), mock provider backends for testing (`mock-providers`), and development tooling (`forge`, `xtask`, `version`). All binaries support feature-flag TLS backend switching between `tls-rustls` (ring crypto, the default) and `fips` (OpenSSL) for FIPS compliance.

## Architectural Analysis

AGN follows a strict control-plane/data-plane separation. The operator computes routing decisions and materializes them as ConfigMap overlays; the Praxis gateway (a separate repository and deployment) handles all request proxying, API translation, and credential injection. This separation means the operator is never latency-critical at request time, and its unavailability does not disrupt in-flight traffic — gateways continue serving from the last-written overlay.

The SWIM membership layer gives the system eventually-consistent distributed membership without a centralized registry. Each operator instance maintains a local view of the mesh, discovers peers through seed endpoints, and propagates site identity and provider metadata via CRDT replication over the same gossip channel. AES-256-GCM encrypts all SWIM traffic when a key is configured (sourced from a Kubernetes Secret in production, an environment variable in development). The `foca` library provides the protocol implementation, with the `swim` crate wrapping it with encryption and serialization.

Certificate management is a central concern. The `certs` crate provides a `CertificateProvider` trait with two implementations: `rcgen`-based generation for the default path and OpenSSL for the FIPS path. Site certificates include DNS SANs and dual Extended Key Usage (client + server) for mTLS. The enrollment subsystem (`enrollment` crate) handles automated site registration with a CA-pinned enrollment server, including one-time token validation, identity persistence, and certificate rotation under SPIFFE-compatible peer trust modes.

The scoring engine operates at the provider level, not the request level. It selects one strategy per `GridNetwork` — the generic `noMetrics` default for external APIs and cloud providers, or metric-driven strategies (`queueDepth`, `kvCachePressure`) for instrumented backends like llm-d. Request-specific decisions like prefix-cache affinity are delegated to the backend's own routing layer (e.g., llm-d EPP), which operates after AGN has selected a provider pool.

A notable architectural risk is the Recreate deployment strategy, necessary because SWIM requires a single identity per site — a surge pod would gossip a second identity. This means the operator has a brief unavailability window during upgrades. The `replicaCount` must remain 1 until multi-replica operation is qualified. The startup probe configuration allows up to 16 minutes (96 failures × 10-second period) to accommodate the enrollment deadline of 15 minutes.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | mTLS between sites; SWIM key for gossip; enrollment token for site registration; optional SAR for enrollment API | Application (certs, swim, enrollment crates) | No per-request user-level auth within the operator; relies on upstream gateway and platform RBAC |
| Data storage | Per-site ConfigMap overlays in configured namespace; enrollment state in PostgreSQL per site | Kubernetes (ConfigMap) / Application (sqlx) | Enrollment database is shared across sites; row-level isolation by site_name |
| Network traffic | NetworkPolicy restricts metrics port to monitoring namespaces; SWIM and signals ports open to peers | Kubernetes (NetworkPolicy) | SWIM and signals are open to any peer that knows the SWIM key; no IP-level peer verification beyond loadBalancerSourceRanges |
| Compute & resources | No built-in ResourceQuota or LimitRange; resources configurable via Helm values | Kubernetes (if configured by admin) | No default compute isolation; a misbehaving site could generate excessive overlay writes |
| Configuration & secrets | Per-site identity secrets; grid CA shared; SWIM key shared across all sites in a GridNetwork | Kubernetes (Secrets) | Grid SWIM key is a shared secret; compromise of one site's key access compromises all sites' gossip |
| API scoping | InferenceProvider.spec.accessPolicy.siteSelector controls which sites can route to a provider; AgentToolProvider has equivalent siteSelector | Application (operator scoring/overlay renderer) | Access policy enforcement is application-level (overlay generation), not Kubernetes RBAC; a site could bypass if it directly reaches a provider endpoint outside the grid |
