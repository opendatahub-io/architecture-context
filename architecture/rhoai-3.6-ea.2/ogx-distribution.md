## Purpose

**Short**: Containerized distribution of OGX (the OpenDataHub fork of Llama Stack) that packages an AI/ML inference and agentic API server into a multi-arch container image with pre-configured providers for inference, vector storage, file processing, and tool integration.

**Detailed**: ogx-distribution is a build-and-packaging repository that produces the `odh-ogx-core` container image — the Red Hat-supported distribution of OGX. The image ships a Python-based HTTP server (port 8321) that exposes eight APIs: responses, messages, batches, inference, tool_runtime, vector_io, files, and file_processors. Providers for each API are conditionally activated at runtime via environment variables, enabling a single image to serve diverse deployment scenarios — from a local developer setup with a single vLLM endpoint to a production deployment backed by PostgreSQL, multiple inference providers (vLLM, OpenAI, Anthropic, Azure, Bedrock, WatsonX, Vertex AI, Gemini), vector databases (Milvus, pgvector, Qdrant), and tool runtimes (web search, file search, MCP).

The repository contains no application source code. Instead, it maintains a build pipeline (Python build scripts, Containerfile templates, and lock file generators) that assembles the OGX distribution from upstream packages (`ogx` v1.4.0+rhaiv.0 from the opendatahub-io fork), pre-scanned model artifacts from a modelcar OCI image, and AIPCC base images. The build pipeline auto-generates `distribution/config.yaml`, lock files, the Containerfile, and documentation from a single source-of-truth `build/build.yaml`. Konflux Tekton pipelines produce hermetic, multi-arch (x86_64, arm64, ppc64le) images for RHOAI downstream consumption.

## Architectural Analysis

ogx-distribution follows a **configuration-driven distribution pattern** rather than containing application logic. The architectural centerpiece is the provider activation mechanism: each provider in `config.yaml` uses conditional `${env.SOME_VAR:+provider-name}` syntax so that an unset environment variable causes the provider to be silently skipped at OGX server startup. This design allows a single container image to serve all deployment profiles without rebuilding.

The build pipeline is template-based with strict separation: `build/build.yaml` is the single source of truth for the full provider manifest (including dependency-only providers), while `build/gen_config.py` strips dependency-only providers to produce the runtime `config.yaml`. The Containerfile template (`Containerfile.in` / `Dockerfile.konflux.in`) is processed by `build/gen_containerfile.py`, which embeds the entire config.yaml as base64-encoded OCI labels — enabling runtime tools to inspect the image's configuration without starting the container.

Model and data artifacts (docling models, HuggingFace embeddings, tiktoken encodings) are sourced from a ProdSec-scanned **modelcar OCI image** rather than being downloaded at build time. The modelcar is referenced as a multi-stage build source, and the build validates that expected model trees exist before completing — failing hard on a broken or empty modelcar. Two artifact source modes exist: `pull` (direct modelcar pull, used by Konflux and non-fork builds) and `cache` (cached artifacts in the build context, used by fork/Dependabot CI).

The entrypoint implements a **secret file resolution** pattern: for each supported secret environment variable, a corresponding `_FILE` suffix allows mounting Kubernetes secrets as files rather than injecting them as environment variables, reducing exposure through `/proc/1/environ`. The entrypoint then dispatches to `ogx run` with optional OpenTelemetry wrapping when `OTEL_SERVICE_NAME` is set.

Storage is externalized to PostgreSQL with two backend types: `kv_postgres` (key-value store for metadata, agent state, prompts) and `sql_postgres` (relational store for inference logs, conversations, files metadata, batches). There is no in-container persistent storage — the image is stateless by design.

Authentication is conditionally enabled via the `AUTH_ISSUER` environment variable, activating OAuth2 JWT token validation with JWKS-based key discovery. The access policy implements owner-based resource isolation: all users can read unowned system resources, authenticated users can create resources, and only resource owners can update or delete their own resources.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OAuth2 JWT with owner-based access policy | Application (OGX server) | Auth is optional (disabled when AUTH_ISSUER is unset); when disabled, all API access is unauthenticated |
| Data storage | Shared PostgreSQL with application-level owner filtering | Application (OGX) | All users share the same database tables; isolation is at the application query level, not at the database schema level |
| Network traffic | None (single service endpoint) | N/A | No per-tenant network isolation; all requests go through the same endpoint |
| Compute & resources | None | N/A | No per-user resource quotas or rate limiting at the distribution level |
| Configuration & secrets | Shared configuration; per-user resource ownership | Application (OGX) | Provider credentials (API keys) are shared across all users |
| API scoping | Owner-based resource filtering for created resources; system resources readable by all | Application (OGX) | Inference requests and model access are not per-tenant scoped |
