## Purpose

**Short**: AI Gateway control-plane controller that reconciles ExternalModel/ExternalProvider CRDs and installs per-tenant praxis-extproc dataplane resources.

**Detailed**: ai-gateway-controller is the control-plane half of the AI Gateway subsystem in RHOAI 3.6. It is deployed by ai-gateway-operator as a sibling of maas-controller, both governed by the shared `AIGateway.spec.modelsAsAService.managementState` toggle. The controller has two primary responsibilities: (1) watching `MaasTenantConfig` resources and, for tenants annotated with `payload-processing-type: praxis`, rendering and SSA-applying per-tenant copies of the vendored praxis-extproc manifests (Deployments, Services, EnvoyFilters, NetworkPolicies, RBAC) into each tenant's Gateway namespace; and (2) watching `ExternalModel` and `ExternalProvider` CRDs to create per-model HTTPRoutes through Gateway API, per-provider ExternalName Services, Istio ServiceEntries and DestinationRules, and a content-addressed routing-overlay ConfigMap that the praxis-extproc dataplane reads at runtime.

The controller replaces the control-plane half of the legacy payload-processing (IPP) component. It coordinates a race-free backend swap handshake with maas-controller via status annotations on `MaasTenantConfig`, allowing tenants to migrate individually between legacy IPP and Praxis backends. It deliberately avoids importing maas-controller's Go types — reading `MaasTenantConfig` and `AITenant` as unstructured objects to keep its dependency graph minimal.

## Architectural Analysis

ai-gateway-controller is a two-reconciler controller-runtime manager with a clear separation of concerns. The `tenant.Reconciler` implements per-tenant dataplane lifecycle (kustomize build → placeholder post-render → per-tenant rename → SSA apply/cleanup) with a `PraxisCleanupFinalizer` that guarantees resource removal when tenants switch backends or are deleted. The `controller.Reconciler` implements the model control plane, resolving ExternalModel/ExternalProvider pairs into a unified route set that feeds both the Envoy transport plane (HTTPRoutes, ServiceEntries, DestinationRules) and the Praxis routing overlay (a content-addressed JSON envelope published to a ConfigMap).

The routing overlay uses RFC 8785 (JCS) canonicalization with SHA-256 content addressing, enforcing monotonic generation numbers and tamper detection (re-digesting published bytes on read-back). This design means the praxis-extproc dataplane can independently verify the overlay's integrity without trusting the ConfigMap transport. The envelope wire format is cross-validated against Rust-side golden vectors to guarantee byte-compatible digest computation.

The multi-tenant architecture piggybacks on maas-controller's existing `MaasTenantConfig`/`AITenant` tenancy model. Both controllers watch the same `MaasTenantConfig` object, with backend selection driven by a single annotation — no cross-object propagation lag. The backend swap handshake uses an optimistic-concurrency CAS pattern on a status annotation, with three states (absent → cleanup-complete → steady) that prevent both controllers from deploying simultaneously. A bounded deletion timeout prevents cleanup failures from blocking `MaasTenantConfig` deletion indefinitely.

The ExternalModel reconciler creates owner-referenced transport resources (HTTPRoute per model, ExternalName Service + ServiceEntry + DestinationRule per provider), with stale resource cleanup by label selector. Only the `apikey` auth type for `openai-chat` API format is currently qualified for the routing overlay credential path; other auth types (`sigv4`, `oauth2`) are declared in the CRD enum but fail closed at reconcile time with `ErrUnsupportedCredential`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-tenant RBAC (ClusterRoleBinding per tenant for praxis-extproc ServiceAccount); controller uses cluster-scoped ClusterRole | Kubernetes RBAC | Controller has broad cluster-scoped permissions; tenant isolation relies on correct resource naming and namespace targeting |
| Data storage | Per-namespace resources (Services, Deployments, ConfigMaps in tenant's Gateway namespace); per-namespace routing-overlay ConfigMap | Kubernetes namespace isolation | Routing overlay ConfigMap is per-namespace; no cross-tenant data leakage path |
| Network traffic | Per-tenant NetworkPolicy for praxis-extproc pods (unless --skip-network-policy); per-tenant DestinationRule for provider egress | Kubernetes NetworkPolicy, Istio | NetworkPolicy can be skipped by flag; when active, scopes ingress to the Gateway namespace |
| Compute & resources | Per-tenant Deployment (payload-processing, payload-pre-processing) with resource limits; no per-tenant ResourceQuota | Kubernetes | No ResourceQuota enforcement; tenant workloads share node resources. Resource limits set in the vendored overlay. |
| Configuration & secrets | Per-namespace ExternalProvider Secrets; per-tenant plugins ConfigMap | Kubernetes namespace isolation | Secret reads use APIReader (direct API server read, not cached) to avoid caching credentials |
| API scoping | ExternalModel/ExternalProvider are namespace-scoped CRDs; controller filters by namespace when --external-model-namespace is set | Kubernetes CRD scope + application filter | When --external-model-namespace is empty, controller watches all namespaces — namespace RBAC is the isolation boundary |
