## Purpose

**Short**: A lightweight REST API service for orchestrating LLM evaluations across multiple backends (lm-evaluation-harness, RAGAS, Garak, GuideLLM, LightEval, MTEB), tracking experiments via MLflow, with pluggable storage (SQLite/PostgreSQL) and Kubernetes-native job orchestration.

**Detailed**: EvalHub is a Go-based REST API service that orchestrates LLM evaluation workflows on the OpenShift AI platform. It provides a unified interface for running evaluation benchmarks through configurable provider backends, managing benchmark collections, and tracking evaluation experiments via MLflow integration. The service operates in two modes: a Kubernetes cluster mode where evaluation jobs are scheduled as Kubernetes Jobs with sidecar containers for proxy, readiness, and telemetry, and a local mode where evaluations run as subprocess processes for development and testing.

The architecture follows a three-tier pattern: an HTTP API layer using Go's standard `net/http.ServeMux` with per-request `ExecutionContext` threading for identity and observability; a pluggable storage layer abstracting SQLite and PostgreSQL backends; and a runtime layer that delegates job execution to either local processes or Kubernetes Jobs. In cluster mode, authentication and authorization are delegated to kube-rbac-proxy, which sets `X-User` and `X-Tenant` headers -- eval-hub enforces these headers on evaluation API routes but does not validate Bearer tokens itself. The component is managed by the TrustyAI Service Operator via an `EvalHub` custom resource and integrates with the broader OpenShift AI platform through HardwareProfile CRDs for GPU/accelerator scheduling.

The repository also produces an MCP (Model Context Protocol) server binary that exposes eval-hub functionality to AI agents via stdio and HTTP transports, a runtime sidecar container for Kubernetes job pods, and an init container for downloading test data from S3, Git, or HuggingFace.

## Architectural Analysis

EvalHub's architecture is shaped by a clean separation between its control plane (the API server) and its data plane (evaluation job pods). The API server accepts evaluation requests, persists them, and delegates execution to a runtime abstraction -- either local subprocess management or Kubernetes Job orchestration. This two-tier runtime design enables the same API surface to serve both development and production workloads without code duplication.

The Kubernetes runtime constructs Job resources with a sidecar pattern: the main container runs the evaluation framework adapter (via the Python eval-hub-sdk), while the sidecar container proxies callbacks to the eval-hub API and MLflow, handles service account token refresh, and writes termination messages. Configuration for the sidecar flows through `sidecar_config.json` injected as a ConfigMap, not through the main `evalhub-config` ConfigMap -- a deliberate isolation that prevents job pods from accessing the full server configuration.

The identity model is notable: eval-hub explicitly does not perform in-process authentication. It trusts kube-rbac-proxy headers (`X-User`, `X-Tenant`) in cluster mode and bypasses identity checks in local mode. This is architecturally clean (single enforcement point) but creates a hard dependency on the proxy sidecar being correctly configured for all inbound traffic paths.

The TLS configuration is consistently set to TLS 1.2 minimum / TLS 1.3 maximum across the main server, MLflow client, and sidecar proxy clients. The server additionally checks `/proc/sys/crypto/fips_enabled` at startup and rejects `InsecureSkipVerify` when FIPS mode is active -- a runtime-level enforcement that complements the build-time FIPS signals (GOEXPERIMENT=strictfipsruntime).

Observability is thorough: OpenTelemetry provides traces, metrics, and log export via OTLP/gRPC or OTLP/HTTP, while Prometheus metrics are served on a dedicated port (8081) to avoid passing through kube-rbac-proxy authentication. The dual-port design (API on 127.0.0.1:8080, metrics on 0.0.0.0:8081) reflects the cluster deployment topology where API traffic arrives through the proxy while metrics are scraped directly.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy performs Bearer token auth and RBAC; X-User/X-Tenant headers forwarded | Kubernetes (kube-rbac-proxy) | eval-hub trusts proxy headers without validation; if proxy is bypassed, no auth is enforced |
| Data storage | Tenant column in SQL storage; queries scoped via `WithTenant` chain on Storage interface | Application | Application-enforced; a bug in tenant scoping could leak data across tenants |
| Network traffic | No per-tenant NetworkPolicy defined in this repository | Platform (TrustyAI Operator) | Network isolation delegated to operator deployment |
| Compute & resources | HardwareProfile CRs provide per-evaluation resource requests/limits; no per-tenant ResourceQuota | Kubernetes / Application | Resource contention possible if quotas not configured at namespace level |
| Configuration & secrets | Provider and collection configs are system-scoped (shared); tenant-created providers are per-tenant | Application | System providers are visible to all tenants; tenant providers scoped via storage |
| API scoping | API routes gated by `canContinueRequest` which requires X-Tenant in cluster mode; storage queries filter by tenant | Application | Health, docs, and metrics endpoints are tenant-agnostic (intentional) |
