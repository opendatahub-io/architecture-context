## Purpose

**Short**: Kubernetes controller that performs intelligent, saturation-aware autoscaling for LLM inference model servers deployed via llm-d.

**Detailed**: The Workload-Variant-Autoscaler (WVA) is a controller-runtime operator that watches HorizontalPodAutoscalers, KEDA ScaledObjects, and Gateway API InferencePool resources to drive autoscaling decisions for inference workloads. It queries Prometheus for runtime metrics — KV-cache utilization, queue depth, and throughput signals from vLLM and the Endpoint Picker (EPP) — and applies a saturation-based optimization engine to compute desired replica counts. The controller then actuates scaling via the Kubernetes Scale subresource on Deployments and LeaderWorkerSets.

The WVA is deprecated on the upstream `main` branch (llm-d/llm-d-autoscaling), where KEDA-native autoscaling has replaced it. In this RHOAI distribution, the controller code lives under the `legacy/` directory and is staged for removal in a future release. The `release-0.9` branch represents the last supported WVA version upstream. Despite the deprecation status, the downstream RHOAI fork continues to build and ship the controller image for the 3.6-ea.2 release.

## Architectural Analysis

WVA follows a collect–analyze–actuate pattern common to custom autoscalers but distinguishes itself through its saturation engine. Rather than scaling on raw request rate or CPU, it collects per-model metrics from Prometheus (KV-cache saturation, token throughput, queue depth), feeds them through a configurable analysis pipeline that includes Kalman filtering for noise reduction, and computes target replicas via a saturation curve. This approach is better suited to GPU-bound inference workloads where CPU utilization is a poor scaling proxy.

The controller architecture is plugin-oriented: metrics sources are registered in a source registry, scaling analyzers (throughput, saturation) are pluggable, and the GPU limiter can operate in either physical-inventory mode (discovering available GPUs via Node API) or quota mode (reading operator-supplied YAML caps). An experimental coordinator loop dispatches cluster-wide GPU rebalancing across namespaces when enabled.

Configuration follows a layered precedence model (flags > environment > config file > ConfigMap > defaults) managed by Viper, with live reload for ConfigMap-backed settings. The ConfigMapReconciler bootstraps initial settings at startup using an uncached API reader and watches for live changes. A readiness gate blocks traffic until the initial ConfigMap bootstrap is complete.

The namespace-scoped deployment variant restricts the controller's watch to a single namespace (set via `--watch-namespace`), while the cluster-scoped variant uses label-selector-filtered caching on ConfigMaps to limit memory consumption across namespaces. Both variants deploy to OpenShift via kustomize overlays that wire up Thanos Querier integration, service-ca TLS certificates, and user-workload-monitoring ServiceMonitor configuration.

CRD dependencies (KEDA ScaledObject, LeaderWorkerSet) are conditionally detected at startup. A CRD watcher can automatically restart the controller when an optional CRD is installed post-startup, unless disabled via `--disable-crd-auto-restart`.
