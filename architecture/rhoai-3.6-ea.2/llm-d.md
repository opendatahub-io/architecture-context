## Purpose

**Short**: llm-d is a high-performance distributed LLM inference serving stack for Kubernetes that provides optimized model-server images, intelligent routing, KV-cache management, and production deployment guides across multiple hardware accelerators.

**Detailed**: llm-d is a CNCF sandbox project that accelerates distributed inference by composing industry-standard components — primarily vLLM and the Kubernetes Gateway API Inference Extension — into tested, production-ready deployment patterns. The project does not contain its own Go or Python services in this repository; instead, it provides Dockerfiles that build optimized vLLM model-server container images (for CPU, ROCm, XPU, and RDMA tooling), along with a comprehensive library of kustomize-based deployment guides ("well-lit paths") covering patterns such as prefix-cache-aware routing, prefill/decode disaggregation, tiered KV-cache offloading, wide expert-parallelism, batch serving, and workload-variant autoscaling.

The core runtime components (router, KV-cache scheduler, routing sidecar, batch gateway, latency predictor, autoscaler) live in separate repositories within the `llm-d` GitHub organization. This repository serves as the integration point: it defines the container images that run vLLM with llm-d optimizations, publishes kustomize overlays and Helm values that wire the components together, and provides GKE pod-snapshot support code for fast model actuation. For RHOAI, llm-d is consumed as a reference architecture and container image source for distributed inference workloads.

## Architectural Analysis

llm-d follows a composition-over-configuration philosophy: components connect at well-defined API boundaries (OpenAI-compatible HTTP, Kubernetes Gateway API, Prometheus metrics) rather than through tightly-coupled internal interfaces. The repository itself is a deployment orchestration layer, not a runtime service — it produces container images and kustomize manifests that other llm-d components consume.

The Dockerfile strategy is notable: each accelerator variant builds vLLM from source (or layers on a prebuilt vLLM image) with accelerator-specific optimizations. The CPU image compiles vLLM from a pinned commit with NIXL and UCX for high-performance networking. The ROCm image adds ROCm-specific UCX, UCCL, NIXL, and MORI (AMD's runtime optimizer). The XPU image extends the official vLLM XPU image with LMCache for SYCL-based caching. The RDMA-tools image is a diagnostic sidecar rather than a model server.

The guide system is architecturally significant: each guide is a self-contained deployment recipe defined by a `guide.yaml` manifest that declares environment variables, prerequisites, accelerator/model-server support matrices, and kustomize overlay paths. The guides compose reusable recipe components (model-server base deployments, gateway configurations, monitoring stacks) through kustomize overlays. This design allows the same base deployment (a vLLM Deployment with health probes on port 8000) to be customized for different accelerators, model servers (vLLM, SGLang, TensorRT-LLM), and infrastructure providers (GKE, OpenShift, bare-metal).

The router integration uses Helm charts published to `ghcr.io/llm-d/charts/` with a plugin-based scheduling architecture. The EndpointPickerConfig custom resource defines plugin chains (prefix-cache affinity, inflight-load, token-load scoring) that the router evaluates per-request to select optimal model-server replicas.

A notable feature is the GKE Fast Pod Snapshotting support (`docker/scripts/snapshot/`), which hooks into vLLM's FastAPI lifespan to checkpoint a fully-initialized model server (after weights are loaded and graphs compiled), then restores it on demand — reducing cold-start latency from minutes to seconds.

**Dockerfile**: N/A (Python module in `docker/scripts/snapshot/`)
**Intent**: GKE Fast Pod Snapshotting integration. Hooks vLLM's FastAPI lifespan to perform engine.sleep() → gVisor checkpoint → engine.wake_up() cycle, enabling warm-start restoration of fully-initialized model servers. Only activates when `SNAPSHOT_PROVIDER=gke_gvisor`.
