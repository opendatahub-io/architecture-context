## Purpose

**Short**: Kubernetes operator that deploys and manages OGX (Open GenAI Stack) servers, providing declarative lifecycle management for AI inference endpoints with configurable distributions, network policies, and Praxis-fronted multi-tenant operation.

**Detailed**: The ogx-k8s-operator is a two-layer operator system for the OGX (Open GenAI Stack) platform within Red Hat OpenShift AI. The primary layer is the OGXServer controller (`controllers/ogxserver_controller.go`), which reconciles `OGXServer` custom resources (API group `ogx.io`, version `v1beta1`) to deploy and manage inference server workloads. It renders manifests via an embedded kustomize pipeline (`controllers/manifests/base/`), applies them with server-side apply (field owner `ogx-operator`), and manages the full lifecycle: Deployments, Services, PVCs, NetworkPolicies, PodDisruptionBudgets, HPAs, Ingresses, ServiceMonitors, and PrometheusRules. Distribution images are resolved from an embedded `distributions.json` registry, overridable at runtime via an operator ConfigMap or per-CR `spec.distribution.image`.

The second layer is the OGX module controller (`ogx-module/`), which operates as a component within the ODH platform operator pattern. It reconciles the cluster-scoped `OGX` CR (API group `components.platform.opendatahub.io`, version `v1alpha1`) to deploy the root OGX operator itself, managing its CRDs, RBAC, webhooks, and deployment via the `odh-platform-utilities` library. This two-layer design allows the ODH/RHOAI platform operator to install and lifecycle-manage the OGX operator as a managed component.

The operator supports a "Praxis-fronted" mode (`spec.praxisMode`), in which OGX servers are internal-only backends fronted by the Praxis (MaaS Gateway) service. In this mode, the operator enforces network-level isolation via locked-down NetworkPolicies admitting only Praxis pods and the operator namespace, disables the Responses/Conversations APIs (served by Praxis instead), and configures upstream-header authentication with tenant-aware access rules. Legacy LlamaStackDistribution resources can be adopted into OGXServer CRs via annotation-based migration.

## Architectural Analysis

The ogx-k8s-operator follows a two-tier operator pattern that separates platform lifecycle management from workload management. The OGX module controller (ogx-module) is a platform-level component that deploys and manages the root OGX operator's resources using ODH platform utilities for kustomize rendering, garbage collection, and deployment ordering. The root OGX operator then manages individual OGXServer workloads per namespace.

The reconciliation pipeline is architecturally notable for its kustomize-in-process approach: rather than shelling out to the `kustomize` binary, the operator embeds kustomize base manifests under `controllers/manifests/base/` and applies Go-based transformer plugins (`pkg/deploy/plugins/`) for name prefixing, namespace injection, field mutation, and NetworkPolicy transformation. This provides deterministic manifest rendering without external tool dependencies.

The Praxis-fronted mode represents a significant architectural decision for multi-tenant inference serving. When enabled, the operator enforces a defense-in-depth isolation model: Kubernetes NetworkPolicies restrict ingress to the OGX service port (8321) to only Praxis pods and the operator namespace, the generated OGX config injects `x-user-id`/`x-tenant-id` upstream-header authentication with ownership-based access rules, and `server.tenancy.mode` is set to `multi`. This shifts the trust boundary from per-user authentication at OGX to per-request header injection at Praxis, with OGX as an internal-only backend.

TLS configuration is dynamically derived from the OpenShift APIServer TLS profile via `openshift/controller-runtime-common`, with automatic restart on profile changes via a SecurityProfileWatcher. On non-OpenShift clusters, the operator falls back to the Intermediate TLS profile. Metrics serving uses conditional HTTPS with controller-runtime's FilterProvider for authentication and authorization when a cert path is configured.

The operator cache is intentionally restrictive: ConfigMaps and Secrets are filtered by the `ogx.io/watch: "true"` label, and all managed resources are filtered by the `app.kubernetes.io/managed-by: ogx-operator` label. This limits informer memory usage but requires the operator config ConfigMap (which lacks the watch label) to be read via a direct API client with 5-minute periodic requeue for eventual consistency.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC via aggregated ClusterRoles (viewer/editor); in Praxis mode, upstream-header authentication (`x-user-id`/`x-tenant-id`) with ownership-based access rules | Kubernetes (RBAC), Application (Praxis header injection) | In Praxis mode, tenant identity depends on Praxis correctly injecting headers; compromised Praxis would bypass tenant isolation |
| Data storage | Per-CR PersistentVolumeClaim; PVCs excluded from ownerRef to prevent data loss | Kubernetes (namespace-scoped PVCs) | No cross-namespace data access possible |
| Network traffic | Per-CR NetworkPolicy; in Praxis mode, ingress locked to Praxis pods + operator namespace only | Kubernetes (NetworkPolicy) | Legacy mode allows all same-namespace pods + OpenShift router; Praxis mode is significantly more restrictive |
| Compute & resources | Per-CR Deployment with optional HPA; per-CR PodDisruptionBudget | Kubernetes (Deployment, HPA, PDB) | No ResourceQuota enforcement by the operator itself; relies on namespace-level quotas |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; watch label `ogx.io/watch: "true"` scopes cache | Kubernetes (namespace-scoped resources) | Operator ConfigMap (`ogx-operator-config`) is cluster-wide and read via direct client |
| API scoping | OGXServerReconciler watches namespace-scoped OGXServer CRs; cache filtered by `app.kubernetes.io/managed-by: ogx-operator` label | Kubernetes (namespace-scoped CRD), Application (label selector on cache) | Cluster-scoped ClusterRoles mean the operator SA can access all namespaces |
