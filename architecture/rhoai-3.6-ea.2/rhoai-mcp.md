## Purpose

**Short**: An MCP (Model Context Protocol) server that enables AI agents to programmatically interact with Red Hat OpenShift AI environments, replicating the capabilities of the OpenShift AI Dashboard through tool-based APIs.

**Detailed**: rhoai-mcp is a Python-based MCP server that bridges AI coding assistants (such as Claude Desktop and Claude Code) to the full lifecycle of RHOAI platform operations. It exposes over 30 MCP tools across eight domain modules—projects, workbenches, model serving, data connections, pipelines, storage, training, and model registry—plus composite tools for cluster exploration, training orchestration, and model recommendation via the llm-d-planner library.

The server uses a pluggy-based plugin architecture where each domain (projects, notebooks, inference, etc.) is a self-contained plugin that registers its own MCP tools, resources, and prompts. Plugins are health-checked at startup to gracefully degrade when CRDs they depend on (e.g., Notebook, InferenceService, TrainJob) are unavailable in the cluster. The architecture separates domain plugins (CRUD operations on specific Kubernetes resource types) from composite plugins (cross-cutting tools that orchestrate multiple domains).

rhoai-mcp supports three MCP transport modes (stdio, SSE, and streamable-http) and three Kubernetes authentication modes (auto, kubeconfig, and token). When deployed in multi-user mode, it implements OIDC/OAuth2 authentication with two token validation strategies (JWT via JWKS discovery and OpenShift TokenReview API), per-user RBAC filtering that shows each user only the MCP tools they are authorized to use, and user-scoped Kubernetes API calls via either token forwarding or impersonation headers. Safety features include read-only mode, a dangerous-operations gate, HMAC-signed workflow tokens that enforce multi-step tool ordering, and credential masking for S3 secrets.

## Architectural Analysis

The rhoai-mcp server is architecturally notable for being the platform's agent-interaction surface — it translates high-level natural-language-driven tool calls from AI assistants into structured Kubernetes API operations against RHOAI CRDs. Rather than exposing a traditional REST API, it uses the Model Context Protocol, which means its primary consumers are LLMs and AI agent frameworks.

The plugin system is the central design pattern. Each domain module (projects, notebooks, inference, pipelines, connections, storage, training, model_registry) follows an identical internal structure: `client.py` for Kubernetes operations, `models.py` for Pydantic data structures, `tools.py` for MCP tool definitions, and optional `crds.py`, `resources.py`, and `prompts.py`. This consistency enables new RHOAI capabilities to be added as drop-in plugins. External plugins can be loaded via Python entry points. A set of composite plugins (cluster, training, meta, planner) layer cross-domain orchestration on top. The planner composite integrates `llm-d-planner` for model recommendation based on hardware availability and use-case requirements.

The multi-user authentication layer is sophisticated: OIDC middleware validates tokens at the ASGI transport level (using raw ASGI rather than Starlette's BaseHTTPMiddleware to avoid SSE streaming incompatibility), then sets a contextvars-based `UserContext` for the request lifetime. The server dynamically patches the FastMCP low-level request handlers to inject per-user RBAC filtering — each plugin can declare permission mappings between tool names and required Kubernetes RBAC verbs, and the server uses the Kubernetes SubjectAccessReview API to check whether the authenticated user holds the necessary permissions. The OIDC RBAC layer is additive to Kubernetes-native RBAC: in user-token mode, the caller's bearer token is forwarded to the Kubernetes API, so all resource access is naturally scoped to that user's permissions.

The workflow token mechanism addresses a unique challenge of LLM tool use: ensuring that multi-step operations (e.g., "validate prerequisites → create training job") execute in the correct order. Each step signs its output with an HMAC token using SHA-256, and the next step verifies the token before proceeding. This provides stateless, tamper-proof ordering without requiring server-side session state.

Security hardening is evident throughout: the deployment runs as non-root with a read-only root filesystem, capabilities are dropped, seccomp profiles are applied, header injection is prevented via CWE-113 validation, JWKS refresh is rate-limited against CWE-400, and identity claims are sanitized against CWE-20 injection.

| Configuration & secrets | Per-namespace secrets; workflow HMAC secret is process-global | Kubernetes (namespace) / Application (HMAC) | Workflow tokens use a shared HMAC key — tokens from one user could theoretically be replayed by another (mitigated by short TTL and step-specific validation) |
