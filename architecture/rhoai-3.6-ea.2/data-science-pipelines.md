## Purpose

**Short**: Kubeflow Pipelines (KFP) fork providing end-to-end ML workflow orchestration on Kubernetes with pipeline compilation, scheduling, execution, artifact management, and a web UI.

**Detailed**: Data Science Pipelines is the Red Hat downstream of Kubeflow Pipelines, providing a platform for building, deploying, and managing reusable end-to-end machine learning workflows on OpenShift. The platform follows a multi-tier architecture: a Python SDK compiles pipeline definitions into IR YAML specifications, the Go-based API server persists pipeline definitions and compiles them into Argo Workflow objects, a driver resolves runtime inputs and computes pod specifications, and a launcher manages artifact I/O and executor invocation within user containers.

The system comprises approximately a dozen microservices coordinated through Kubernetes APIs, including the central API server (exposing both REST and gRPC interfaces), persistence agent (synchronizing workflow state back to the API server), scheduled workflow controller (managing recurring pipelines via CronWorkflow-like semantics), cache server (implementing pipeline step caching via mutating admission webhook), metadata services (ML Metadata store with Envoy proxy), and a React-based frontend. All services share a MySQL database for metadata persistence and connect to S3-compatible object storage for pipeline artifacts. The v2 engine introduces Kubernetes-native CRDs (Pipeline and PipelineVersion) with validating and mutating admission webhooks for pipeline version lifecycle management.

In RHOAI, this component is not deployed via its own kustomize manifests directly; rather, the **data-science-pipelines-operator (DSPO)** manages the lifecycle of Data Science Pipelines instances per-namespace. The kustomize manifests in this repo serve as reference for upstream Kubeflow Pipelines and as the base that DSPO consumes.

## Architectural Analysis

Data Science Pipelines follows a hub-and-spoke architecture centered on the API server, which orchestrates pipeline lifecycle from submission to completion. The API server is the only component that exposes external-facing APIs (HTTP on port 8888, gRPC on port 8887, webhook admission on port 8443), while all other services are internal consumers that interact through the Kubernetes API or direct service-to-service calls.

The security model layers Kubernetes RBAC with application-level authorization. The API server implements TokenReview and SubjectAccessReview for per-request authentication and authorization, enabling multi-user isolation. Each microservice runs under a dedicated ServiceAccount with a narrowly-scoped Role, following least-privilege principles. The MySQL database is additionally protected by an Istio AuthorizationPolicy that restricts access to specific service identities. A notable exception is the `pipeline-runner` Role, which has wildcard access to `kubeflow.org` resources and broad permissions on pods, PVCs, and jobs -- this wide grant is necessary because pipeline steps can create arbitrary Kubernetes resources but represents the largest RBAC attack surface in the component.

A notable architectural tension exists between the v1/v1beta1 Argo Workflow-based execution model and the v2 engine's introduction of Pipeline/PipelineVersion CRDs. The v2 driver and launcher operate as sidecar/init containers within Argo Workflow pods, bridging the two models. The CRD webhooks (validating and mutating) enforce pipeline version constraints at the Kubernetes API level, independent of the API server's own validation logic.

The FIPS compliance strategy uses Go 1.24+'s native FIPS 140 module (`GOFIPS140=v1.0.0`) with the `no_openssl` build tag and module-level `godebug fips140=on` in go.mod, relying on Go's built-in FIPS-validated cryptographic implementations rather than linking against OpenSSL. This is a deliberate choice -- the API server uses `CGO_ENABLED=1` (for database drivers like go-sqlite3) while all other components are statically compiled with `CGO_ENABLED=0`. With FIPS mode enabled, Go automatically restricts cipher suites and TLS versions to FIPS-approved values without requiring explicit configuration, which is why no hardcoded cipher suites or TLS version pins appear in the codebase. TLS is configurable but optional for all services (API server, persistence agent, webhooks), meaning the operator deploying DSP is responsible for ensuring TLS is enabled in production. The runtime base image (`ubi9/ubi-minimal-pqc`) provides post-quantum cryptography support at the OS level.

|-----------|-----------|-------------|--------------|
| Auth & AuthZ | TokenReview + SubjectAccessReview per API request; projected SA token for service-to-service auth | Application (API server) + Kubernetes | Standalone mode has no auth -- all users share full access |
| Data storage | Shared MySQL database (logical separation by namespace in queries) | Application | Single database instance; tenant isolation depends on correct query scoping in application code |
| Network traffic | Istio AuthorizationPolicy for MySQL; NetworkPolicy for SeaweedFS | Istio / Kubernetes | No NetworkPolicy for inter-service traffic beyond MySQL and SeaweedFS |
| Compute & resources | Namespace-scoped controllers (--namespace flag) | Kubernetes | No ResourceQuota or LimitRange enforced by the component itself |
| Configuration & secrets | Per-namespace Secrets for DB and S3 credentials | Kubernetes | Shared Secret names across all workloads in namespace |
| API scoping | Namespace-scoped CRDs; controllers watch single namespace | Kubernetes | pipeline-runner Role has wildcard access to kubeflow.org resources |
