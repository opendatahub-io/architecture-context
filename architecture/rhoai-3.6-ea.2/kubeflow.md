## Purpose

**Short**: Kubernetes controllers that manage the lifecycle of Jupyter Notebook workbenches on OpenShift, including pod creation, authentication sidecar injection, idle culling, and Gateway API routing.

**Detailed**: The kubeflow repository is a Red Hat Data Services fork of the upstream Kubeflow project, containing two cooperating Go controllers for notebook workbench management. The **notebook-controller** (upstream Kubeflow) reconciles `Notebook` custom resources into StatefulSets, Services, and manages idle notebook culling by probing kernel activity. The **odh-notebook-controller** (OpenDataHub extension) layers OpenShift-specific functionality on top: it injects `kube-rbac-proxy` authentication sidecars, creates per-notebook Gateway API HTTPRoutes and ReferenceGrants for ingress, manages NetworkPolicies for pod isolation, handles DSPA (Data Science Pipelines) secret mounting, MLflow tracking integration, Feast configuration, OAuth client cleanup, and ImageStream resolution through mutating and validating admission webhooks.

Both controllers run as separate binaries in separate deployments but operate on the same `kubeflow.org/Notebook` CRD. The upstream controller handles core lifecycle (StatefulSet reconciliation, stop/start via annotations, culling), while the ODH controller handles platform integration concerns. This separation allows the ODH layer to evolve independently of upstream Kubeflow while preserving core notebook semantics.

## Architectural Analysis

The kubeflow component follows a two-controller architecture that cleanly separates upstream Kubeflow notebook lifecycle from OpenShift platform integration. This design enables independent development cycles and cleaner rebase workflows against the upstream Kubeflow repository.

The upstream notebook-controller is a straightforward CRD controller that maps Notebook CRs 1:1 to StatefulSets. It uses the v1beta1 API version internally for backwards compatibility while supporting v1 and v1alpha1 through CRD conversion. The CullingReconciler is conditionally enabled via the `ENABLE_CULLING` environment variable and polls notebook kernels over HTTP to detect idle instances, setting the `kubeflow-resource-stopped` annotation to scale replicas to zero.

The odh-notebook-controller is architecturally more complex, acting as both a controller and an admission webhook server. Its mutating webhook intercepts every Notebook CREATE and UPDATE to inject the kube-rbac-proxy sidecar container, resolve OpenShift ImageStream references to concrete image digests, set cluster proxy environment variables, and configure volumes for TLS certificates and trusted CA bundles. This webhook-driven approach ensures that security sidecars and platform configuration are injected before the upstream controller ever sees the pod spec.

For ingress, the ODH controller creates HTTPRoute resources in its own controller namespace (not the user's namespace) and uses ReferenceGrants to allow cross-namespace backend references. This centralized routing model means all notebook routes go through the platform's `data-science-gateway` Gateway in the `openshift-ingress` namespace, providing a single point of TLS termination and policy enforcement.

Both controllers implement a TLS security profile watcher that reads the OpenShift APIServer TLS configuration at startup and restarts the process on profile changes. When the OpenShift config API is unavailable (non-OpenShift clusters), they fall back to Mozilla Intermediate cipher suites with TLS 1.2 minimum. The metrics endpoints are served over HTTPS with controller-runtime's built-in authentication and authorization filters.

A notable architectural risk is the broad RBAC surface of the `manager-role` ClusterRole used by the ODH controller: it has write access to OAuthClients, ClusterRoleBindings, NetworkPolicies, and RBAC resources across all namespaces. This is necessary for its cross-namespace resource management (HTTPRoutes, ReferenceGrants, kube-rbac-proxy RBAC) but represents a high-privilege footprint.
