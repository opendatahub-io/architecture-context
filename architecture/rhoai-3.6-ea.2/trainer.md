## Purpose

**Short**: Kubernetes-native distributed AI training operator that orchestrates large-scale model training and fine-tuning across PyTorch, DeepSpeed, MPI, JAX, XGBoost, and other frameworks via declarative TrainJob and TrainingRuntime CRDs.

**Detailed**: Kubeflow Trainer is the training orchestration component of Red Hat OpenShift AI, providing a Kubernetes-native platform for distributed AI model training and LLM fine-tuning. Users submit `TrainJob` CRDs that reference `TrainingRuntime` or `ClusterTrainingRuntime` templates, and the controller materializes the appropriate distributed training topology using JobSet as the underlying workload primitive.

The controller operates through a plugin-based runtime framework. Built-in plugins handle framework-specific concerns: the JobSet plugin creates replicated training jobs, the MPI plugin configures hostfile-based multi-process launch, the Flux plugin provides HPC-style workload orchestration, and scheduling plugins (CoScheduling via scheduler-plugins, Volcano) coordinate gang scheduling so all workers are co-scheduled. The architecture supports extensibility—new training frameworks can be added as plugins without modifying core controller logic.

RHOAI-specific features include progression tracking (polling training pods for step/epoch metrics and writing them back to TrainJob status annotations), NetworkPolicy creation for per-job pod isolation, and a TLS-secured status server (feature-gated, alpha) that allows training pods to push real-time status updates back to the controller via OIDC-authenticated HTTPS POST requests.

## Architectural Analysis

Kubeflow Trainer follows the controller-runtime operator pattern with a single-binary deployment running the controller manager, webhook server, metrics server, and an optional status server. The design separates concerns through a plugin framework (`pkg/runtime/framework/`): each training framework (PyTorch, MPI, DeepSpeed, Flux, JAX, XGBoost) is a plugin implementing a standard interface, and plugins compose to build the final workload specification. The controller doesn't directly create Pods—it delegates to the JobSet API, which handles replicated Job creation and lifecycle management.

The RHOAI downstream fork adds three significant capabilities on top of upstream Kubeflow: (1) **TLS profile adherence** via `pkg/tls/`, which reads the OpenShift cluster `APIServer` TLS profile and applies it to metrics, webhook, and status servers, then watches for profile changes and triggers controller restart; (2) **RHAI progression tracking** via `pkg/rhai/progression/`, which polls training pods' HTTP metrics endpoints for step/epoch progress and annotates TrainJob status; and (3) **NetworkPolicy creation** via `pkg/rhai/networkpolicy.go`, which creates per-TrainJob ingress rules allowing same-job pod communication (for NCCL/MPI/gRPC) and optionally controller-to-pod metrics access.

The controller's RBAC footprint is broad (14 cluster role rules) because it must create and manage JobSets, PodGroups (for both scheduler-plugins and Volcano), NetworkPolicies, ConfigMaps, Secrets, and its own webhook configurations. Three user-facing aggregate ClusterRoles (`training-view`, `training-edit`, `training-admin`) provide tiered access to trainer resources.

A notable architecture decision is HTTP/2 is disabled by default across all TLS servers (metrics, webhook, status) to mitigate the Rapid Reset CVEs (CVE-2023-44487, CVE-2023-39325), falling back to HTTP/1.1 unless explicitly configured via the Configuration CRD's TLS options.
