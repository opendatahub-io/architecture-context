## Purpose

**Short**: Diagnostic data collection tool that gathers logs, resource definitions, and cluster state from Red Hat OpenShift AI and RHAII deployments for troubleshooting.

**Detailed**: must-gather is a diagnostic container image designed to collect comprehensive cluster state and logs from RHOAI (Red Hat OpenShift AI) and RHAII (Red Hat AI Inference) deployments. It is invoked via `oc adm must-gather` on OpenShift or deployed as a Kubernetes Job on non-OpenShift platforms (AKS, EKS, CKS). The tool collects namespace-scoped resources, pod logs, Custom Resource instances, Helm release values, and cluster-scoped configuration for all RHOAI components.

The image bundles per-component collection scripts covering 16 platform components: Dashboard, Data Science Pipelines, KServe, KubeRay, Kueue, Kubeflow Training Operator, Model Registry, TrustyAI, Feast Operator, MLflow, Spark Operator, AI Gateway, MCP Lifecycle Operator, OGX, LLM-D, and Workbenches. Collection can target a single component via the `COMPONENT` environment variable or run all collectors in parallel. For non-OpenShift Kubernetes (xKS) platforms, the tool auto-detects the cluster distribution and adjusts its collection strategy, defaulting to LLM-D-specific resource gathering.

## Architectural Analysis

must-gather follows the standard OpenShift must-gather pattern: a container image based on `ose-must-gather-rhel9` that replaces the base `/usr/bin/gather` entrypoint with a custom orchestration script. The architecture is a shell-script-based dispatcher that routes collection to per-component scripts based on the `COMPONENT` environment variable.

The main `gather.sh` orchestrator first detects the Kubernetes distribution (OCP, AKS, EKS, CKS) via node metadata and API server probes in `xks_util.sh`, then branches into OpenShift-specific or xKS-specific collection paths. On OpenShift, it inspects core RHOAI operator namespaces (`redhat-ods-operator`, `redhat-ods-applications`, `rhods-notebooks`, `redhat-ods-monitoring`, `rhoai-model-registries`) and platform-level CRs (DSCInitialization, DataScienceCluster, and 20+ component module CRs across `components.platform.opendatahub.io`, `services.platform.opendatahub.io`, and `infrastructure.opendatahub.io` API groups). On xKS, it restricts collection to LLM-D-specific resources and Helm release metadata, with platform-specific CRs for AKS/CKS/EKS infrastructure.

When collecting all components (the default on OpenShift), the orchestrator launches all 14 component gather scripts as background processes in parallel, tracking PIDs for failure reporting. Each component script follows a consistent pattern: define the CRD resource types to collect, discover namespaces where those resources exist via `get_all_namespace`, then call `run_mustgather` to run `oc adm inspect` across those namespaces along with Gateway API and Istio resources collected by default.

The LLM-D collection path is the most complex, adding a layer of dependency collection scripts (cert-manager, Sail/Istio, LeaderWorkerSet) that run in parallel, followed by Gateway API, inference extension, and monitoring resource collection. The xKS utility layer provides a `kubectl_inspect` function that emulates `oc adm inspect` for non-OpenShift clusters, including auto-discovery of all namespaced API resources via `kubectl api-resources` and parallel pod log collection with both current and previous container logs.

A notable post-quantum crypto hardening step is applied at build time: the Konflux Dockerfile installs `crypto-policies-scripts` and sets the system crypto policy to `DEFAULT:PQ`, enabling post-quantum key exchange algorithms for any TLS connections made by the `oc`, `kubectl`, and `helm` tools within the image.
