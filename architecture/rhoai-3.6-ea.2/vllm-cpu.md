## Purpose

**Short**: CPU-optimized build of the vLLM inference engine, providing OpenAI-compatible and multi-protocol serving for large language models without GPU hardware.

**Detailed**: vllm-cpu is the CPU-only variant of vLLM, a high-throughput and memory-efficient inference and serving engine for large language models. It runs as a FastAPI-based HTTP server (with optional gRPC) exposing an OpenAI-compatible API surface that supports chat completions, text completions, embeddings, reranking, scoring, classification, speech-to-text, and the newer OpenAI Responses API. The server also implements Anthropic Messages API compatibility and SageMaker-compatible endpoints.

The CPU build targets x86_64, ppc64le, and s390x architectures. It uses PyTorch 2.11.0 (CPU variant) with Intel Extension for PyTorch on x86_64 for optimized inference. The codebase includes C/C++ custom kernels compiled for CPU execution, Rust-based chat template rendering and tool-call parsing, and Python-level optimizations including PagedAttention, continuous batching, and speculative decoding. The engine supports disaggregated prefill/decode, elastic expert parallelism, LoRA adapter hot-loading, and structured output generation via multiple grammar backends.

## Architectural Analysis

vLLM's architecture follows a modular router pattern: a single FastAPI application dynamically composes API routers based on the model's supported tasks. The `api_server.py` entrypoint builds the ASGI application, wires middleware (authentication, CORS, scaling, request-ID tracking), and delegates to Uvicorn for HTTP serving. Each API domain (OpenAI chat/completions, embeddings, scoring, Anthropic messages, etc.) lives in its own `api_router.py` module, registered conditionally based on model capabilities.

The engine itself runs in-process via `AsyncLLM` (the V1 engine), which manages the scheduler, KV cache, and worker processes. Multi-process parallelism uses fork-based workers by default (`VLLM_WORKER_MULTIPROC_METHOD=fork`), with tensor-parallel and data-parallel modes available. The data-parallel supervisor (`dp_supervisor.py`) runs a separate HTTP proxy that aggregates health checks across multiple vLLM worker processes.

A notable design decision is the conditional authentication middleware: bearer token auth is applied only to paths prefixed with `/v1`, `/v2`, or `/inference`, leaving health and operational endpoints unauthenticated by design. Token comparison uses constant-time digest comparison (`secrets.compare_digest` on SHA-256 hashes) to prevent timing attacks.

TLS is supported via Uvicorn's native SSL integration with configurable certificate/key paths. The `SSLCertRefresher` watches certificate files via `watchfiles` and hot-reloads them without server restart, supporting Kubernetes cert-manager rotation patterns. However, the default `ssl_cert_reqs` is `CERT_NONE` (no client certificate verification), meaning mTLS is opt-in rather than default.

The Konflux build uses `ubi9-minimal-pqc` (post-quantum cryptography variant) as the base image, but the application itself does not use AIPCC base images — it builds from bare UBI and installs Python via system packages. This represents a gap in the AIPCC migration story.
