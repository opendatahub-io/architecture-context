## Purpose

**Short**: A REST API orchestrator that coordinates AI text generation with content safety guardrails by routing requests through configurable detector, chunker, and generation backend services.

**Detailed**: The FMS Guardrails Orchestrator (binary name `fms-guardrails-orchestr8`) acts as middleware between clients and large language models, intercepting text generation requests to enforce content safety. It exposes a REST API surface on two ports: a guardrails server (port 8033) for orchestrated detection and generation endpoints, and a health server (port 8034) for liveness and service information.

The orchestrator is configuration-driven via a YAML file that defines downstream service connections for generation backends (TGIS via gRPC, caikit-nlp via gRPC, or OpenAI-compatible via HTTP), content detector services (via REST), and text chunker services (via gRPC). Each detector can be associated with a chunker for input segmentation and a threshold for score filtering. The orchestrator supports both unary and streaming response patterns across its v1 and v2 API families.

The component provides flexible TLS support: optional server-side TLS and mTLS on the guardrails port, and per-service client TLS configuration for downstream connections including support for mutual TLS, custom CA certificates, and insecure mode. Header passthrough allows forwarding of configured request headers (including X-Forwarded-Access-Token rewriting to Bearer authorization) to downstream services for authentication delegation.

## Architectural Analysis

The orchestrator follows a task-handler architecture pattern where each API endpoint creates a typed task object (e.g., `ClassificationWithGenTask`, `CompletionsDetectionTask`) that the `Orchestrator` struct dispatches to the appropriate handler. This design cleanly separates routing from business logic and allows each handler to compose its own pipeline of chunker, detector, and generation calls.

A notable design decision is the dual-server architecture: the health server runs on a separate port (8034) with no TLS, while the guardrails server (8033) supports configurable TLS/mTLS. This separation ensures health probes work regardless of TLS configuration, which is critical for Kubernetes liveness/readiness probes when mTLS is enforced.

The TLS implementation uses `rustls` with `ring` as the cryptographic provider throughout the stack. This is explicitly configured in `main.rs` via `rustls::crypto::ring::default_provider().install_default()`. While `ring` provides good performance and memory safety, it is not a FIPS-validated cryptographic module. The Cargo.lock also shows an `openssl` crate dependency (likely pulled in transitively), but the application's active TLS paths all use `ring`-backed `rustls`. This creates a gap between the build-time FIPS signals (OpenSSL installed in the UBI image, which may satisfy `check-payload` scanning) and the runtime crypto posture (non-FIPS `ring` provider).

The client-side TLS module (`src/utils/tls.rs`) implements a `NoVerifier` struct that completely bypasses certificate verification when `insecure: true` is configured. While this is gated behind explicit configuration, its availability represents a potential security concern in production deployments if misconfigured.

The orchestrator's v2 API conditionally enables OpenAI-compatible endpoints (`/api/v2/chat/completions-detection` and `/api/v2/text/completions-detection`) only when an `openai` backend is configured. This means the API surface is dynamic based on runtime configuration.

Observability is well-integrated via OpenTelemetry (traces and metrics) with OTLP export support for both gRPC and HTTP protocols, plus configurable log format options (full, compact, pretty, JSON).
