## Purpose

**Short**: A FIPS-compliant authentication reverse proxy for RHOAI that provides OIDC and OpenShift OAuth authentication, serving as a drop-in replacement for oauth-proxy sidecars.

**Detailed**: kube-auth-proxy is a focused authentication reverse proxy derived from oauth2-proxy, streamlined specifically for OpenDataHub and Red Hat OpenShift AI environments. It intercepts requests to upstream applications and enforces authentication through either external OIDC providers or OpenShift's built-in OAuth service, forwarding authenticated requests with user identity headers.

The proxy supports multiple authentication mechanisms in a layered middleware chain: Kubernetes service account token validation via the TokenReview API, OIDC JWT bearer tokens, OpenShift OAuth bearer tokens (sha256~ format), htpasswd basic authentication, and cookie-based session management. Sessions can be stored in cookies or externally in Redis/Valkey for horizontal scaling. It is designed as a drop-in replacement for the legacy oauth-proxy sidecar, maintaining argument and header compatibility while removing all providers except OIDC and OpenShift OAuth to reduce attack surface.

A key architectural feature is the Envoy ext_authz compatibility mode, where the proxy returns HTTP 200 with identity headers on successful authentication (via the `/auth` endpoint), enabling integration with Envoy-based service meshes and RHOAI's Gateway API ingress infrastructure. The proxy also includes an MLflow-specific auth denial handler that returns structured JSON error messages for the MLflow Python SDK client.

## Architectural Analysis

kube-auth-proxy follows a middleware-chain architecture (via `justinas/alice`) that cleanly separates pre-authentication concerns (logging, health checks, metrics, HTTPS redirect) from the authentication pipeline itself. The authentication chain is ordered deliberately: Kubernetes TokenReview validation runs first (allowing service accounts to bypass provider-specific auth), followed by provider-specific bearer token loaders (JWT for OIDC or OAuth for OpenShift), then htpasswd basic auth, and finally cookie-based stored sessions. This ordering ensures service accounts are validated quickly and independently of the configured provider.

The codebase shows careful attention to the dual-use pattern where the proxy operates both as a traditional reverse proxy (forwarding to upstreams) and as an Envoy ext_authz endpoint (returning 200/401/403 to Envoy). The `AuthOnly` endpoint and `redirectOnCSRFError` flag are specifically designed to support the ext_authz pattern, where Envoy cannot handle HTML error pages or redirect-based login flows gracefully.

The OpenShift provider implements on-demand OAuth endpoint discovery through the `/.well-known/oauth-authorization-server` endpoint, with thread-safe double-checked locking to handle concurrent discovery attempts. This allows the proxy to auto-configure when deployed inside an OpenShift cluster without explicit login/redeem URL configuration.

Token caching in the TokenReview validator uses a singleflight-inspired pattern (custom implementation rather than `golang.org/x/sync/singleflight`) with SHA-256 hashed keys to avoid holding raw tokens in memory. The cache has configurable TTL (default 10s) and sweeps expired entries lazily on writes.

The build system produces FIPS-compliant binaries using `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1`, with the runtime image based on `ubi9/ubi-minimal-pqc` (post-quantum cryptography variant). The proxy configures TLS with a minimum of TLS 1.2, supports configurable cipher suites and curve preferences, and properly handles custom CA certificates for OpenShift API communication.
