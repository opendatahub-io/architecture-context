## Purpose

**Short**: Builds containerized Jupyter notebook, Code-Server, and Elyra pipeline runtime images for Red Hat OpenShift AI workbenches, providing interactive data science environments with CPU and GPU accelerator support.

**Detailed**: The notebooks component is a container image factory — it does not deploy a running service itself but produces the workbench and runtime images that data scientists interact with on OpenShift. The repository contains multi-stage Dockerfiles for Jupyter notebooks (minimal, data science, PyTorch, TensorFlow, TrustyAI, LLM Compressor), Code-Server (VS Code in the browser), and Elyra pipeline runtime images across CPU, NVIDIA CUDA, and AMD ROCm accelerator variants. Each image is self-contained: no image references another as a FROM source, and every Dockerfile rebuilds all ancestor stages from the external AIPCC base image upward.

For RHOAI 3.6, all images target Python 3.12 on RHEL 9.8 EUS via AIPCC base images (`quay.io/aipcc/base-images/`). The build system uses `uv` for hermetic Python dependency resolution with pylock.toml lock files, RPM lockfiles for OS packages, and Cachi2/Hermeto prefetching for Konflux builds. Images are published to `registry.redhat.io/rhoai/` and deployed to clusters via OpenShift ImageStreams managed by the ODH Operator. The ODH Dashboard discovers these images through ImageStream annotations and presents them as selectable workbench types to users.

## Architectural Analysis

The notebooks repository follows a **matrix build architecture**: each image flavor (minimal, datascience, pytorch, etc.) is crossed with each accelerator variant (cpu, cuda, rocm) to produce a combinatorial set of container images. Despite the conceptual layer hierarchy (minimal → datascience → pytorch), there are no inter-image dependencies — each Dockerfile inlines all ancestor stages. This design trades Dockerfile duplication for build independence, avoiding diamond dependency problems and enabling per-image base image selection (critical when different accelerators require different CUDA/ROCm SDK versions).

The integration model is indirect: notebooks produces images consumed by other platform components. The ODH Operator deploys ImageStream manifests from `manifests/rhoai/base/` via kustomize, with image digests injected through `params.env` and kustomize replacements. The ODH Dashboard reads ImageStream annotations (`opendatahub.io/notebook-image-name`, etc.) to populate its workbench picker. The ODH Notebook Controller injects OAuth proxies, CA certificate bundles, and Elyra pipeline runtime ConfigMaps into workbench pods at creation time.

A notable architectural pattern is the Code-Server idle culling workaround: since Code-Server lacks Jupyter's `/api/kernels/` endpoint, the repo implements a three-process stack (nginx → httpd → bash CGI scripts) to fake Jupyter-compatible activity reporting. This is acknowledged as fragile and planned for replacement with a single Go reverse proxy.

The hermetic build pipeline is comprehensive: RPM lockfiles (`rpms.lock.yaml`), Python lockfiles (`pylock.*.toml`), and Hermeto/Cachi2 prefetching ensure reproducible builds. The AIPCC base images provide pre-configured `pip.conf` and `uv.toml` pointing to Red Hat's Python Package Index, and the Dockerfiles install packages with `--no-index --find-links /cachi2/output/deps/pip`.
