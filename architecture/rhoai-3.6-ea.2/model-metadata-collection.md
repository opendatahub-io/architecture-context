## Purpose

**Short**: A Go-based pipeline that extracts, enriches, and catalogs metadata from Red Hat AI model container images, MCP servers, and AI agents into structured YAML catalogs consumed by the RHOAI dashboard.

**Detailed**: model-metadata-collection is a build-time data pipeline that produces YAML catalog files describing AI models, MCP (Model Context Protocol) servers, and AI agents available in the Red Hat OpenShift AI ecosystem. The pipeline operates in several stages: it discovers models from HuggingFace collections, extracts model cards from OCI container image layers (ModelCar format), enriches metadata with HuggingFace API data, and aggregates everything into structured catalogs. The tool also processes MCP server definitions and agent metadata from index files, enriching them with OCI registry data and GitHub content.

The final output is a set of static YAML catalog files (`models-catalog.yaml`, `validated-models-catalog.yaml`, `other-models-catalog.yaml`, `*-mcp-servers-catalog.yaml`, `redhat-agents-catalog.yaml`) that are baked into a minimal container image. This container runs as a data sidecar (`sleep infinity`) — it exposes no network services and serves purely as a volume mount source. Other RHOAI platform components (notably the dashboard) mount the `/app/data` volume to read model and MCP server metadata at runtime. The catalog data references KServe `serving.kserve.io` API resources, linking models to their serving runtime configurations.

## Architectural Analysis

model-metadata-collection follows an unusual "data-only container" architecture pattern. The Go CLI tooling (`model-extractor`, `metadata-report`) runs at build/CI time to generate catalog data, but none of this Go code executes at runtime. The Konflux container image simply copies pre-generated YAML files into a UBI 9 minimal-pqc image that sleeps forever, acting as a sidecar data volume. This separation means the runtime security surface is essentially zero — no ports, no network, no running code — while the build-time surface involves external API calls to HuggingFace and container registries.

The codebase is well-modularized into internal packages: `catalog/` handles catalog generation for models, MCP servers, and agents; `enrichment/` handles HuggingFace metadata merging; `huggingface/` manages collection discovery and API interaction; `registry/` handles OCI registry queries; `config/` manages model family definitions and configuration loading; `metadata/` parses model cards; and `report/` produces completeness reports. Public types and utilities live in `pkg/`.

The pipeline uses concurrent processing with configurable parallelism (`--max-concurrent`, default 5) for model extraction, employing goroutines with a semaphore pattern. It supports multiple catalog types (Red Hat models, validated models, other models, MCP servers by tier, and agents) with independent processing pipelines that can be selectively enabled or disabled via CLI flags.

A notable architectural dependency is the reference to `serving.kserve.io` resources in generated catalog data files (`validated-models-catalog.yaml`, `other-models-catalog.yaml`), establishing a data-plane linkage between the catalog metadata and the KServe serving infrastructure without any code-level dependency.
