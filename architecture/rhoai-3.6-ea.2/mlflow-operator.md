## Purpose

**Short**: Kubernetes operator that automates the deployment and lifecycle management of MLflow tracking servers on OpenShift and Kubernetes clusters.

**Detailed**: The MLflow Operator provides a declarative API for managing MLflow deployments through Custom Resources (`MLflow`, `MLflowOperator`, `MLflowConfig`). It uses Helm charts internally to render and apply Kubernetes manifests for MLflow tracking server instances, including their backing storage, network exposure, and monitoring configuration.

The operator supports two deployment modes — RHOAI (targeting `redhat-ods-applications` namespace) and OpenDataHub (targeting `opendatahub` namespace) — and integrates with the platform's Gateway API for external routing via HTTPRoute resources, OpenShift Console for ConsoleLink integration, and Prometheus for metrics collection via ServiceMonitor resources. Key features include built-in Kubernetes auth with self-subject access review, automatic TLS certificate provisioning via OpenShift service-ca-operator, flexible storage backends (local PVC, PostgreSQL, S3), read-replica routing for metadata reads, and operator-managed database migrations during upgrades.

The operator employs a three-controller architecture: `MLflowReconciler` manages individual MLflow instances and their child resources; `MLflowOperatorReconciler` handles the platform-level component lifecycle when integrated with the ODH operator module system; and `NamespaceRBACReconciler` manages per-namespace workspace RoleBindings for multi-tenant access control based on the platform Auth CR.

## Architectural Analysis

The mlflow-operator follows a Helm-rendering operator pattern where the primary controller (`MLflowReconciler`) translates `MLflow` CR specifications into Helm chart values and applies the rendered manifests as owned resources. This design provides flexibility — the same Helm chart can be used standalone or via the operator — while keeping the operator's reconciliation logic focused on lifecycle management, status aggregation, and platform integration rather than resource templating.

A notable architectural choice is the conditional controller activation pattern. The `MLflowOperatorReconciler` and `NamespaceRBACReconciler` are gated behind environment variables (`ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER` and `ENABLE_NAMESPACE_RBAC`), with startup CRD-wait loops that block until required CRDs become available. This supports a staged rollout where the operator works in standalone mode initially and gains platform-integrated capabilities (module ownership, workspace RBAC) when the platform operator is ready. The RHOAI overlay enables namespace RBAC by default while keeping the module controller disabled, indicating the RHOAI 3.6 EA2 deployment has not yet migrated to the full module ownership model.

The operator's cache configuration is carefully scoped: owned resources are filtered by `app: mlflow` label selectors and restricted to the target namespace, while cluster-scoped RBAC resources use exact metadata.name field selectors aligned with resourceNames-scoped RBAC permissions. A separate `GCRBACWatchCache` handles the garbage collection RBAC singleton without broadening the main cache's watch scope — an effective pattern for managing multiple named singletons with tight RBAC.

TLS configuration is derived from the OpenShift APIServer TLS profile at startup via `controller-runtime-common/pkg/tls`, with a `SecurityProfileWatcher` that triggers a graceful restart when the cluster's TLS profile changes. This ensures the operator's metrics endpoint always reflects the cluster-wide cryptographic policy. The fallback to Intermediate profile defaults ensures correct operation on non-OpenShift Kubernetes clusters.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RoleBindings (mlflow-view, mlflow-edit) bound to platform Auth CR groups | Kubernetes RBAC via NamespaceRBACReconciler | RoleBindings only created when `ENABLE_NAMESPACE_RBAC=true` and Auth CR exists |
| Data storage | MLflow instances share the operator namespace; data isolation relies on separate backend databases per MLflow CR | Application (backend store URI per CR) | No enforced isolation at the storage layer if CRs share the same database |
| Network traffic | NetworkPolicy on operator pod restricts ingress to health probes and monitoring namespaces | Kubernetes NetworkPolicy | MLflow instance network policies rendered via Helm chart, not documented in operator manifests |
| Compute & resources | Resource limits on operator pod (1 CPU / 4Gi); MLflow instance resources controlled via CR spec | Kubernetes | No ResourceQuota enforcement by the operator itself |
| Configuration & secrets | Secret access scoped to named `mlflow-artifact-connection` via resourceNames RBAC | Kubernetes RBAC | User-provisioned secrets; operator cannot enforce rotation |
| API scoping | Aggregate ClusterRoles (mlflow-view, mlflow-edit) for RBAC aggregation to admin/edit/view roles; cluster-scoped MLflow CR | Kubernetes RBAC | Cluster-scoped MLflow CR means any user with edit ClusterRole can affect all instances |
