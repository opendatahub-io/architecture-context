## Purpose

**Short**: Multi-tenant platform for managing AI model endpoints as a service, providing API key management, subscription-based access control, and Gateway API integration for model inference routing.

**Detailed**: Models-as-a-Service (MaaS) is a Kubernetes-native platform that exposes AI inference models as managed API endpoints with multi-tenant isolation, subscription-based access control, and policy enforcement. The platform consists of three independently deployable Go services: a controller that reconciles tenant, model, subscription, and auth policy CRDs into Gateway API routing and Kuadrant/Authorino enforcement resources; an API service that provides REST endpoints for model discovery, API key lifecycle management, and subscription operations backed by a PostgreSQL database; and a discovery service that provides tenant metadata for multi-cluster environments.

The controller operates as the central orchestration component, managing the lifecycle of per-tenant infrastructure including namespaces, networking (HTTPRoutes, NetworkPolicies), RBAC, and Kuadrant AuthPolicies with TokenRateLimitPolicies. It embeds the maas-api deployment manifests and renders them at runtime through its Tenant reconciler, enabling a single controller deployment to bootstrap the entire API tier. Authentication flows support both OpenShift bearer tokens (via Kubernetes TokenReview) and MaaS-issued API keys (validated via HTTP callback to the API service), with Kuadrant/Authorino acting as the gateway-level policy enforcement point. The component integrates conditionally with KServe's LLMInferenceService for model serving state and manages ExternalModel resources for third-party model provider integration.

## Architectural Analysis

MaaS follows a multi-service architecture with clear separation between the control plane (controller), data plane proxy (API service behind Kuadrant/Authorino), and discovery tier. The controller is the single source of truth for tenant lifecycle: when an AITenant CR is created, the controller creates per-tenant namespaces, deploys MaasTenantConfig resources, generates Kubernetes Secrets for database credentials, provisions HTTPRoutes against a shared Gateway, and creates Kuadrant AuthPolicy resources that wire up the authentication and authorization chain. This design means the controller manages resources across multiple namespaces (its own namespace, tenant namespaces, the gateway namespace in openshift-ingress, and an infrastructure namespace), requiring broad cluster-scoped RBAC.

A distinguishing architectural choice is the dual authentication path at the gateway: API keys (prefixed `sk-oai-`) are validated via an HTTP callback to the API service's internal endpoint, while OpenShift tokens use Kubernetes TokenReview. Authorino evaluates these in priority order, strips the original Authorization header to prevent credential forwarding to model backends, and injects identity headers (`X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription`) for downstream consumption. This credential isolation pattern — requiring Kuadrant 1.4.2+ for header stripping — is a security-critical dependency documented explicitly in the README.

The LifecycleReconciler (self-deployment controller) watches its own Deployment and associated infrastructure resources (ConfigMaps, ClusterRoleBindings, NetworkPolicies, CRDs) to perform self-healing and coordinated upgrades. This is unusual for a component operator and indicates the controller acts as an autonomous deployment unit rather than relying solely on an external operator for lifecycle management.

TLS configuration follows the OpenShift TLS Security Profile pattern: both the API service and discovery service read the cluster's APIServer TLS profile at startup and configure their crypto/tls settings accordingly, using the `openshift/library-go` helper to determine whether strict adherence is required. This ensures cipher suite and minimum TLS version decisions are cluster-policy-driven rather than hardcoded.

The PostgreSQL dependency for API key storage introduces a stateful external dependency that requires a pre-existing database Secret (`maas-db-config`). The controller supports both an infrastructure namespace separation model (for production, deriving `odh-ai-gateway-infra` from the controller namespace) and a collapsed namespace model (for ROSA/restricted environments), controlled via the `INFRA_NAMESPACE` environment variable.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kuadrant AuthPolicy per HTTPRoute with API key + TokenReview; per-tenant identity headers injected by Authorino; client-supplied identity headers rejected | Kuadrant/Authorino (Gateway-level) + Application (TokenReview for /v1/tenants) | Internal endpoints (/internal/v1/*) rely on NetworkPolicy for isolation; compromised pod in allowed namespace could access internal API |
| Data storage | Per-tenant data isolation via tenant column in shared PostgreSQL database; tenant name scoped in API key operations | Application (query filter by tenant name) | Application-enforced: a bug in tenant scoping could leak data across tenants; no database-level row security |
| Network traffic | NetworkPolicies per namespace: maas-authorino-networkpolicy, maas-gateway-networkpolicy, maas-deployment-ns-networkpolicy, cleanup-ingress networkpolicy | Kubernetes NetworkPolicy | NetworkPolicies created by controller; coverage depends on correct reconciliation |
| Compute & resources | Per-tenant resource allocation via MaaSSubscription rate limits (TokenRateLimitPolicy); shared controller and API service | Kuadrant Limitador | No per-tenant ResourceQuota or LimitRange; tenants share controller compute |
| Configuration & secrets | Per-tenant MaasTenantConfig CR in tenant namespace; shared maas-db-config secret in infrastructure namespace | Kubernetes (CR per namespace) + Application | Database connection secret shared across all tenants |
| API scoping | Controller uses namespace-scoped watches for tenant resources; API key operations scoped by tenant name | Kubernetes (namespace-scoped CRDs) + Application | MaaSSubscription and MaaSModelRef are namespace-scoped; tenant isolation depends on correct namespace assignment |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL database | Tenant name column | Application query filter (tenant name parameter) |
| maas-api service | Per-request tenant context from identity headers | Authorino identity injection (X-MaaS-Username, X-MaaS-Group, X-MaaS-Subscription) |
| Gateway (data-science-gateway) | Per-HTTPRoute + AuthPolicy | Gateway API routing rules with per-tenant auth policies |
