## Purpose

**Short**: Python plugin library that adds read-only server introspection HTTP endpoints to vLLM inference servers, exposing launch configuration, hardware properties, and KV cache capacity for llm-d routing and scheduling decisions.

**Detailed**: llm-d-api-extensions provides API extensions for inference servers consumed by the [llm-d](https://github.com/llm-d/llm-d) distributed LLM serving platform. The llm-d routing and scheduling layer needs runtime metadata from inference servers — how a server was launched, what GPU hardware it runs on, KV cache capacity after profiling — to make intelligent routing decisions. Rather than forking or patching inference server code, this repository packages those endpoints as external plugins that integrate through each server's own extension points.

The current implementation targets vLLM exclusively, using its [endpoint plugin framework](https://docs.vllm.ai/en/latest/design/endpoint_plugins/) (`vllm.endpoint_plugins` entry points) and `--worker-extension-cls` mechanism. The architecture is server-agnostic at the top level — each supported server gets its own directory with an independently installable Python package. All plugins are opt-in via the `VLLM_PLUGINS` environment variable; installing the package alone does not alter server behavior.

The three introspection endpoints expose: (1) operator-supplied configuration (model, scheduler, parallelism, KV transfer/disaggregation settings), (2) per-rank GPU device properties collected via `collective_rpc`, and (3) post-profiling KV cache capacity and attention group structure. Responses are computed once at startup and cached immutably for the server's lifetime. Plugins degrade gracefully — returning HTTP 503 rather than crashing — when dependencies (engine, worker extensions, unreleased vLLM APIs) are absent.

## Architectural Analysis

llm-d-api-extensions follows a clean plugin architecture that separates concerns well. Each endpoint is an independent plugin class implementing `attach_router` (FastAPI route registration) and `init_state` (one-time data collection at server startup). The init-once-serve-forever pattern means these introspection endpoints add negligible ongoing overhead to the inference server — responses are Pydantic model instances cached on `app.state` and returned directly on each request.

The `config` plugin stands apart from `devices` and `kv-cache` by setting `required_tasks = None`, meaning it works even on the CPU-only render server where no engine exists. The other two plugins restrict to `ENGINE_TASKS` and return 503 when no engine is available.

A notable design decision is the redaction of `kv_connector_extra_config` values by default in the config endpoint. Since this field is free-form and operator-controlled, it may contain credentials or other sensitive data. Values are replaced with `"<redacted>"` unless `LLM_D_INTROSPECTION_EXPOSE_KV_EXTRA_CONFIG=1` is explicitly set, striking a balance between observability and security.

The KV cache plugin includes a forward-compatibility pattern: it feature-detects `engine_client.get_kv_cache_group_metadata()` via `hasattr`, falling back to capacity-only fields when running against a vLLM build that predates the upstream PR (vllm-project/vllm#48121). The group schema is a discriminated union over 10 `kind` values, correctly representing hybrid attention architectures (full attention, MLA, sliding window, Mamba, cross-attention, etc.).

As a library with no Dockerfiles, no container images, no CRDs, and no deployment manifests, this component has an unusually light infrastructure footprint. It is consumed by installing the Python package into a vLLM container image at build time. Security, FIPS compliance, and deployment topology are all inherited from the host vLLM image rather than managed by this repository.
