## Purpose

**Short**: CLI tool for inspecting, diagnosing, linting, and migrating Red Hat OpenShift AI (RHOAI) deployments on Kubernetes clusters.

**Detailed**: odh-cli (shipped as `rhai-cli` in RHOAI) is a kubectl-plugin-style command-line tool that gives cluster administrators and SREs a single entry point for RHOAI operational tasks. It connects to a live Kubernetes cluster via kubeconfig credentials and provides subcommands for platform health status, upgrade-readiness lint checks, component inspection, log retrieval, event monitoring, workload backup, dependency management (via OLM), and version-to-version migration actions. The CLI covers the full RHOAI upgrade lifecycle: pre-upgrade lint checks identify blocking issues, migration actions execute schema and resource transformations, and post-upgrade diagnostics verify platform health.

The tool also exposes its entire command surface as a Model Context Protocol (MCP) server, allowing AI agents (Claude, GPT, Cursor, etc.) to invoke every CLI operation programmatically over stdio or HTTP SSE transports. Diagnostic tools from the opendatahub-operator's `clusterhealth`, `failureclassifier`, and `mcptools` packages are integrated directly, enabling platform health triage, failure classification, and component status correlation without separate tooling.

## Architectural Analysis

odh-cli follows a clean command/package architecture where each top-level Cobra subcommand (`lint`, `status`, `migrate`, `diagnose`, `get`, `deps`, `backup`, `logs`, `events`, `components`, `mcp`, `api`, `version`, `completion`) delegates to a corresponding `pkg/` package that encapsulates domain logic. The `pkg/cmd.Command` interface provides a unified execution contract that the MCP adapter layer reuses to expose every CLI operation as a typed MCP tool without duplicating business logic.

The client layer (`pkg/util/client`) abstracts Kubernetes API access behind `Reader`, `Writer`, and `Client` interfaces, with the `Reader` interface deliberately restricting lint checks to read-only operations. Under the hood, six distinct Kubernetes client types are constructed from a single REST config: dynamic, discovery, apiextensions, OLM, metadata, and typed clientset. This gives the CLI fine-grained access patterns ranging from unstructured resource listing (dynamic) through OLM subscription/CSV inspection to metadata-only queries for efficient large-scale enumeration.

The lint engine is the most architecturally complex subsystem. It organizes checks into four tiers — components (per-RHOAI-component validation), dependencies (operator prerequisite verification), platform (DSC/DSCI configuration), and workloads (per-resource-type validation) — with checks targeting specific RHOAI components like KServe, Ray, Kueue, ModelMesh, Dashboard, AI Gateway, AI Pipelines, LlamaStack, and Training Operator. Checks are severity-gated (prohibited, critical, warning, info) and version-aware for upgrade assessment.

The migration system (`pkg/migrate`) follows an action/registry pattern where individual migration actions (covering AI Pipelines RBAC, Kueue, LlamaStack, model serving, Ray clusters, TrustYAI, and workbenches) are registered with version ranges and lifecycle phases (pre-upgrade, post-upgrade, pre-enablement). Each action implements a standard interface with dry-run capability, allowing safe preview before cluster modification.

Error handling uses a structured classification system (`pkg/util/errors`) that maps Kubernetes API errors, TLS errors, DNS failures, filesystem errors, and context cancellations to user-facing categories with exit codes and actionable suggestions — a design that improves both CLI and MCP consumer experience.

A notable design decision is the Post-Quantum (PQ) crypto policy: the Konflux Dockerfile explicitly sets the system crypto policy to `DEFAULT:PQ` via `update-crypto-policies --set DEFAULT:PQ`, preparing the container for post-quantum TLS negotiation ahead of broader ecosystem adoption.
