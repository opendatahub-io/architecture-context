## Purpose

**Short**: A Kubernetes operator that manages the complete lifecycle of LLM-D batch gateway deployments by reconciling a single `LLMBatchGateway` custom resource into the full set of Kubernetes workloads using embedded Helm chart rendering.

**Detailed**: The llm-d-batch-gateway-operator automates deployment and day-2 management of the LLM-D batch inference gateway stack on OpenShift. When a user creates an `LLMBatchGateway` CR, the operator translates its spec into Helm values, renders two embedded Helm charts (batch-gateway and async-processor) at runtime using the Helm v3 Go library, and applies the resulting Kubernetes resources via Server-Side Apply. The rendered stack consists of up to four components: an API server that accepts batch job submissions, a processor that dispatches inference requests to inference gateways (either synchronously via HTTP or asynchronously via Redis queues), a garbage collector that expires completed jobs and files, and an optional async-processor that bridges the Redis queue to inference gateway endpoints.

The operator follows a chart-rendering pattern rather than managing a Helm release: it owns all generated resources via controller references, detects and deletes orphaned resources on spec changes, and reports fine-grained status conditions (Ready, APIServerAvailable, ProcessorAvailable, GCAvailable, AsyncProcessorAvailable) derived from replica health. Component container images are injected by the platform operator via environment variables sourced from `params.env`, ensuring the user CR controls configuration but not image provenance. Cross-namespace secret references are authorized through Gateway API ReferenceGrant resources, and TLS configuration is derived from the cluster-wide OpenShift TLS profile with automatic restart on profile changes.

## Architectural Analysis

The operator's architecture is shaped by three key design decisions. First, using the Helm Go library for in-process chart rendering (rather than deploying Helm releases) gives the operator full control over the resource lifecycle — it can set owner references, detect orphans, and apply via Server-Side Apply without relying on Helm's release tracking. This also means the operator embeds prefetched Helm charts in its container image, avoiding runtime network dependencies.

Second, the strict separation between platform-controlled and user-controlled configuration is enforced at the architecture level. The four component images (apiserver, processor, gc, async) are read from environment variables set by the parent platform operator (opendatahub-operator/ai-gateway-operator) via `params.env`, not from the `LLMBatchGateway` CR. This prevents users from deploying unauthorized images while still allowing full control over scaling, storage, and inference gateway configuration.

Third, the operator integrates deeply with the OpenShift security model. It resolves the cluster-wide TLS profile from the `config.openshift.io/APIServer` resource at startup and propagates the resulting minimum TLS version, cipher suites, and ALPN protocols both to its own metrics server and to the rendered workloads via Helm values. A `SecurityProfileWatcher` monitors the APIServer resource and triggers a graceful operator restart on profile changes, ensuring crypto configuration stays synchronized without manual intervention. The metrics endpoint uses controller-runtime's authentication and authorization filter (TokenReview/SubjectAccessReview), and the serving certificate is provisioned by the OpenShift service-ca operator via an annotation on the metrics Service.

The cross-namespace secret handling is notable: when `secretRef.namespace` differs from the CR namespace, the operator verifies authorization through a Gateway API `ReferenceGrant` in the source namespace, copies the secret into the CR namespace as a managed resource, and makes the secret reference immutable after first sync. This prevents credential hijacking while supporting shared-secret deployment patterns.
