## Purpose

**Short**: Pluggable Go library and service suite for KV-Cache-aware routing in distributed LLM inference platforms, maintaining a near-real-time global view of KV-Cache block locality across vLLM pod fleets.

**Detailed**: llm-d-kv-cache provides the foundational KV-Cache management layer for the llm-d distributed inference platform. Its core is a Go library (`pkg/kvcache`, `pkg/kvevents`) that tracks which KV-Cache blocks reside on which vLLM pods and on which device tier (GPU, CPU, disk), enabling schedulers to make optimal cache-aware placement decisions. The library subscribes to KV-Events streamed from vLLM engines over ZeroMQ and maintains a block index backed by either in-memory LRU, Redis, or Valkey stores.

The library is designed to be embedded in a host process — the reference consumer is `llm-d-router` (the inference gateway/EPP). The repository also ships standalone example services (an HTTP scoring service, a gRPC IndexerService), sidecar utilities (a Python UDS tokenizer for chat template rendering, a PVC evictor for disk-based KV offloading), and a Python/C++ filesystem storage connector (`llmd-fs-backend`) for moving KV blocks between GPU and shared storage. The KV-Cache Indexer libraries (`kvcache`, `kvblock`, `kvevents`) have been migrated into `llm-d-router` as of PR #1886; this repository retains the connectors, utilities, and legacy library code.

## Architectural Analysis

llm-d-kv-cache follows a library-first, modular architecture with clearly separated concerns across its module hierarchy. The `kvcache.Indexer` acts as an orchestrator coordinating three internal pipelines: token processing (converting token sequences into deterministic block keys via chained FNV-64a over CBOR-encoded content hashes), index lookup (querying the block index for pod-to-block mappings), and scoring (computing per-pod cache-hit ratios using a longest-consecutive-prefix algorithm weighted by device tier).

The write path is event-driven: ZMQ subscribers receive msgpack-encoded event batches from vLLM/SGLang engines, which a sharded worker pool (`kvevents.Pool`) routes to per-pod worker shards using FNV-1a hashing on pod ID — guaranteeing in-order processing per engine. Three event types drive index state: `BlockStored`, `BlockRemoved`, and `AllBlocksCleared`. The block index supports multiple backends through a common `kvblock.Index` interface, with Redis/Valkey connectivity leveraging the `go-redis` client and supporting both plaintext (`redis://`) and TLS (`rediss://`) connection URLs.

A notable design pattern is the multi-language composition: the core routing library is Go, but peripheral services are Python-based. The UDS tokenizer service runs as a gRPC sidecar (Unix Domain Socket for low-latency intra-pod communication), wrapping vLLM's Python tokenizer for chat template rendering and multimodal processing. The PVC evictor is a Python multi-process utility (N+2 architecture: N crawlers, 1 activator, 1 deleter) managing disk space for offloaded KV-Cache blocks. The llmd-fs-backend is a Python/C++ hybrid (with CUDA extensions via pybind11) that implements vLLM's offloading connector interface — though it has been fully upstreamed into vLLM as of v0.23.

The OTLP tracing connection uses `WithInsecure()` (no TLS) by default in examples, with a comment noting that production should use `WithTLSCredentials()`. HTTP and gRPC endpoints carry no authentication middleware — these are designed for cluster-internal use and depend on network-level isolation in production.
