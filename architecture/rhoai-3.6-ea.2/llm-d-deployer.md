## Purpose

**Short**: Deprecated monolithic Helm chart for deploying the llm-d distributed LLM inference stack on Kubernetes, including a ModelService controller, inference gateway, endpoint picker (EPP), and Redis-backed KV-cache routing.

**Detailed**: llm-d-deployer is a Helm chart packaging repository that provides a single `helm install` entry point for the entire llm-d ecosystem — a Kubernetes-native high-performance distributed LLM inference framework. The chart deploys a Gateway API-compatible inference gateway (supporting Istio, kGateway, and GKE L7), a ModelService CRD and controller that reconciles desired model deployments into prefill and decode pod pairs with sidecar routing proxies, an endpoint picker (EPP) running as a gRPC external processor for intelligent request routing, and an optional Redis instance used for LMCache KV-cache lookup coordination.

As of July 2025 this repository is officially deprecated in favor of the more modular `llm-d-infra` repository, which uses Helmfile to compose individual per-component Helm charts. The charts here remain usable but receive no further updates. The repository does not contain source code for any of the deployed components — it references external container images (llm-d-model-service, llm-d-inference-scheduler, llm-d, llm-d-routing-sidecar, llm-d-inference-sim) built from separate repos. A quickstart installer script wraps Helm with namespace creation, HF token secrets, CRD application, optional model download, and Prometheus/Grafana provisioning.

## Architectural Analysis

llm-d-deployer is an opinionated composition layer that orchestrates five independently-developed components into a single coherent deployment. Its architecture follows the Kubernetes Gateway API Inference Extension (GAIE) pattern: an inference Gateway receives HTTP requests, routes them through an EPP (external processor) that uses scoring algorithms (prefix-aware, load-aware, KV-cache-aware, session-aware) to select optimal backends, and forwards them to prefill or decode vLLM instances organized by a ModelService controller.

The chart uses a "preset" pattern where deployment templates for prefill, decode, EPP, and services are stored as ConfigMap data fields rather than direct Kubernetes manifests. The ModelService controller reads these ConfigMaps and stamps out the actual Deployments, Services, InferencePools, and InferenceModels. This two-level templating — Helm rendering ConfigMaps that contain Go-template-bearing YAML consumed by the controller — enables runtime model deployment through `ModelService` CRs without additional Helm operations, but creates complexity in tracing the actual deployed configuration.

The default preset (`basic-gpu-with-nixl-and-redis-lookup-preset`) configures NixL + LMCache multi-connector KV transfer between prefill and decode pods, with a routing proxy sidecar on decode pods that intercepts traffic on port 8000 and proxies to vLLM on port 8001. Redis serves dual duty as LMCache lookup backend and optional KV-cache indexer for the EPP scorer.

Security posture is minimal: no TLS termination is configured at the application level (the Gateway listens on HTTP port 80 by default), no authentication enforcement exists on the inference path, and the controller pod drops all capabilities with `runAsNonRoot`. The chart relies on external infrastructure (Istio, kGateway, or a cloud L7 LB) for TLS and on Kubernetes RBAC for API authorization. No Dockerfiles or compiled source code exist in this repository — it is purely a packaging artifact.

|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC ClusterRoles with admin/editor/viewer tiers for ModelService CRs | Kubernetes | ClusterRoles are not namespace-scoped; manager role has cluster-wide access to create deployments, services, and RBAC bindings |
| Data storage | Per-PVC model storage; Redis per-release (standalone mode) | Kubernetes | Redis auth disabled by default; no data isolation within Redis if shared |
| Network traffic | None | N/A | No NetworkPolicy templates in chart; relies on external network policy |
| Compute & resources | NVIDIA GPU tolerations; per-container resource requests/limits configurable | Kubernetes | No ResourceQuota or LimitRange templates; compute isolation is user-configured |
| Configuration & secrets | Per-namespace HF_TOKEN secret; per-release ConfigMap presets | Kubernetes | HF_TOKEN shared across all ModelService CRs in the namespace |
| API scoping | ModelService controller watches namespace-scoped CRs | Kubernetes | Manager ClusterRole has cluster-wide permissions; controller scope depends on --leader-elect and namespace filtering in the controller binary |
