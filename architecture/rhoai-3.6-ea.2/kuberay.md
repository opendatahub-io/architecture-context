## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Ray clusters, jobs, and services on OpenShift, providing CRDs for declarative Ray workload management with integrated authentication, mTLS, and network isolation.

**Detailed**: KubeRay is a controller-runtime-based Kubernetes operator that provides four Custom Resource Definitions — RayCluster, RayJob, RayService, and RayCronJob — enabling declarative lifecycle management of Ray distributed computing workloads. The operator reconciles these CRDs into Kubernetes-native resources (Pods, Services, Jobs, Ingresses) and manages the full lifecycle from cluster creation through autoscaling and teardown.

The RHOAI distribution extends the upstream KubeRay operator with significant OpenShift-specific hardening. An AuthenticationController injects kube-rbac-proxy sidecars into Ray head pods and creates Gateway API HTTPRoutes for centralized authentication, replacing direct Route/Ingress access. A NetworkPolicyController creates per-cluster network policies based on annotation triggers. An mTLS controller uses cert-manager to provision self-signed CA certificates and per-node TLS certificates, enabling encrypted communication between Ray head and worker nodes. A mutating webhook enforces secure defaults on OpenShift by enabling the secure trusted network annotation and disabling direct ingress creation to enforce Gateway-only access.

The operator reads the cluster-wide OpenShift TLS security profile from `apiservers.config.openshift.io/cluster` and applies it to both the metrics server and webhook server, with a watcher that triggers graceful restart on profile changes. It supports pluggable batch schedulers (Volcano, YuniKorn, Kai) for gang scheduling of Ray worker pods.

## Architectural Analysis

KubeRay follows a multi-controller architecture where each CRD kind has a dedicated reconciler, supplemented by three cross-cutting OpenShift-specific controllers. The RayClusterReconciler is the primary controller, managing head and worker pods, services, ingresses, and RBAC resources. RayJobReconciler orchestrates job submission by creating a child RayCluster, submitting the job via the Ray dashboard API, and managing a Kubernetes batch Job for the submitter process. RayServiceReconciler implements a blue-green deployment pattern with pending and active RayCluster instances, managing service endpoints and traffic routing between versions.

The AuthenticationController is the most architecturally significant downstream addition. It watches RayCluster resources annotated for secure networking, then creates a ServiceAccount with OAuth redirect annotations, injects a kube-rbac-proxy sidecar container into the head pod's service, creates HTTPRoutes in the platform namespace (controlled by `APPLICATION_NAMESPACE` env var) pointing to the authenticated endpoint, and manages ReferenceGrants for cross-namespace routing. The sidecar image is resolved from `RELATED_IMAGE_ODH_KUBE_RBAC_PROXY_IMAGE`, injected via the operator's CSV relatedImages for disconnected environment support.

The TLS architecture has three distinct concerns: (1) the operator's own metrics endpoint uses the OpenShift serving cert mechanism via the `service.beta.openshift.io/serving-cert-secret-name` annotation, (2) webhook TLS uses cert-manager self-signed certificates, and (3) Ray inter-node mTLS uses a separate cert-manager CA chain managed by the RayClusterMTLSController. All three read the cluster TLS security profile to align cipher suite and protocol version selection.

The operator uses controller-runtime's cache with label selectors to reduce watch scope — batch Jobs are filtered to only those created by KubeRay. Namespace scoping is configurable via `--watch-namespace`, supporting single-namespace, multi-namespace, or cluster-wide operation.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC via aggregated ClusterRoles (edit, view); kube-rbac-proxy sidecar per RayCluster | Kubernetes + Application | Aggregated roles grant access to all Ray resources in namespaces where bound; no per-CR access control |
| Data storage | Per-namespace Pods and PVCs; no shared database | Kubernetes | Data isolation relies entirely on namespace-level Kubernetes RBAC |
| Network traffic | Per-cluster NetworkPolicy (annotation-activated) | Application (NetworkPolicyController) | NetworkPolicy is opt-in via annotation, not enforced by default |
| Compute & resources | No ResourceQuota enforcement by operator; delegates to platform quota | Kubernetes | One tenant's large RayCluster can consume cluster resources unless platform-level quotas are set |
| Configuration & secrets | Per-namespace Secrets for mTLS certificates; per-namespace ConfigMaps | Kubernetes | mTLS CA is per-namespace, preventing cross-namespace certificate reuse |
| API scoping | Namespace-scoped CRD watches; configurable `--watch-namespace` | Kubernetes + Application | Cluster-wide watch mode (default) gives operator visibility into all namespaces |
