## Purpose

**Short**: Hardware plugin that enables vLLM to run large language model inference on Intel Gaudi (HPU) accelerators, exposing an OpenAI-compatible API server.

**Detailed**: vllm-gaudi is the Intel Gaudi hardware plugin for vLLM, providing the platform abstraction layer, attention backends, custom operations, and worker infrastructure needed to run LLM inference on Intel Gaudi 2 and Gaudi 3 accelerators. It follows vLLM's plugin architecture (RFC #11162 and #19161) and registers itself via Python entry points as a platform plugin (`vllm.platform_plugins`) and general plugin (`vllm.general_plugins`), allowing vLLM's core engine to dispatch work to HPU devices without modification to the upstream codebase.

The plugin implements HPU-optimized attention backends (unified attention, MLA variants, and v1 backends), custom fused operations (MoE, rotary embeddings, layer normalization, quantization), LoRA adapters, and distributed inference support including KV cache transfer via the NIXL protocol. It ships a comprehensive quantization stack supporting compressed-tensors, FP8, INC (Intel Neural Compressor), AWQ, GPTQ, and ModelOpt formats, along with HPU-specific model overrides for architectures requiring specialized handling (DeepSeek, Qwen, Gemma3, Pixtral, HunYuan, and others). The container image bundles Habana SynapseAI drivers, PyTorch for HPU, and vLLM itself, running the OpenAI-compatible API server as its entrypoint under a non-root user for OpenShift compatibility.

## Architectural Analysis

vllm-gaudi follows a clean plugin separation pattern where all HPU-specific logic is isolated from upstream vLLM. The `HpuPlatform` class (inheriting from vLLM's `Platform` base) serves as the central dispatch point, configuring attention backends, worker classes, compilation settings, and device management. This design allows the plugin to track vLLM releases independently — the `VLLM_STABLE_COMMIT` file pins the last validated upstream commit, and the Dockerfile clones and installs both vLLM and the plugin at build time.

The runtime configuration system (`vllm_gaudi.extension`) implements a sophisticated lazy-evaluation mechanism where features, environment variables, and hardware capabilities are resolved on demand through a `Config` class with functional composition primitives (`All`, `Any`, `Not`, `Enabled`). This enables feature flags that adapt to detected hardware (Gaudi 2 vs Gaudi 3) and user-selected compilation modes (lazy vs eager PyTorch bridge).

A notable architectural tension exists in the build: the Dockerfile explicitly removes the FIPS provider (`rpm -e --nodeps openssl-fips-provider-so`) from the UBI base image due to incompatibility with Habana's driver stack. This creates a FIPS compliance gap that is accepted for the Gaudi accelerator use case. The image also installs packages from Habana's external artifactory (`vault.habana.ai`), introducing a supply chain dependency on Intel's infrastructure that is not present in other RHOAI inference components.

The KV cache architecture supports multiple configurations: contiguous page attention for Gaudi 3 (avoiding costly gather operations), hybrid KV cache with mixed dtypes, and distributed KV transfer via NIXL for disaggregated prefill-decode deployments. The online defragmentation system manages memory compaction during inference to mitigate HPU memory fragmentation.
