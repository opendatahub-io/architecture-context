## Purpose

**Short**: Provides online machine-learning prediction and training services for llm-d time-to-first-token (TTFT) and time-per-output-token (TPOT) latency.

**Detailed**: The component is a two-service FastAPI application. The training service accepts request traces, maintains bounded training/test data, periodically retrains regression models, persists model and scaler artifacts, and exposes model download and diagnostic APIs. The prediction service loads those artifacts locally, periodically synchronizes newer artifacts from the training service, and serves single or bulk latency predictions.

The prediction deployment is horizontally scaled (10 replicas in the base manifest) and uses per-pod `emptyDir` model storage. The single-replica training deployment is the model-authority component; prediction pods retrieve models over the internal `training-service` HTTP service. Kubernetes ConfigMaps provide runtime configuration, while the GKE overlay adds persistent model storage and optional external LoadBalancer services.

## Architectural Analysis

This is a data-plane workload rather than a Kubernetes operator: it has no CRDs, controllers, webhooks, RBAC objects, or platform API integration. Its architectural boundary is two independently packaged Python containers sharing the `common` type definitions. Prediction is optimized for read-heavy horizontal scale; training is intentionally singleton-oriented because it owns mutable model artifacts and retraining state.

The model distribution path is pull-based. Each prediction worker polls the training service, downloads a newer joblib artifact to a temporary file, validates that it can be deserialized, and atomically replaces the local file before loading it. This avoids shared model storage for prediction but makes model availability and freshness dependent on the training service and on unauthenticated internal HTTP. The default configuration also uses HTTP rather than HTTPS, so encryption and service identity are delegated to the deployment environment rather than implemented by the application.

The Konflux path is substantially more reproducible than the legacy Dockerfiles: it uses a digest-pinned AIPCC CPU image and a hashed, compiled requirements file. The repository nevertheless contains legacy `python:3.11-slim` Dockerfiles that install from unpinned requirements and Debian packages; consumers should use the Konflux images for RHOAI delivery.
