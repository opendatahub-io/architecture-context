## Purpose

**Short**: Provides KEDA autoscaling manifest blueprints and an evaluation test bed for llm-d inference deployments, with a deprecated custom controller (WVA) staged for removal.

**Detailed**: llm-d-autoscaling serves two roles in the llm-d inference platform. Its primary, current function is to provide reviewed, recommended KEDA `ScaledObject` scaling strategies — configuring trigger thresholds for queue depth, KV-cache utilization, and vLLM/EPP signals — as manifest blueprints under `benchmark/config/scenarios/`. These blueprints are layered with backend-specific cluster configs to produce complete autoscaling configurations for prefill/decode disaggregated topologies.

The repository also hosts the autoscaling evaluation test bed (`benchmark/`), built on llm-d-benchmark. This test bed stands up KEDA scaling scenarios against either simulated (llm-d-inference-sim) or real GPU vLLM backends, drives load, and captures autoscaling behavior metrics (replica counts, HPA/KEDA trigger values, latency, throughput) for evidence-based comparison of blueprint strategies.

The `legacy/` directory contains the deprecated Workload-Variant-Autoscaler (WVA), a custom Go controller-runtime operator that performed GPU-aware autoscaling using Prometheus metrics, Kalman-filter-based prediction, and direct scaling of Deployments and LeaderWorkerSets. WVA is frozen on `main`, last released as v0.9.0 on the `release-0.9` branch, and staged for deletion. KEDA replaces WVA as the autoscaling engine, eliminating the need for a custom controller in the scaling path.

## Architectural Analysis

The repository is in architectural transition. The active surface is entirely declarative — KEDA ScaledObject YAML blueprints that configure Prometheus-based autoscaling triggers, and Jinja2-templated benchmark specifications that drive the evaluation harness. No custom controller sits in the production scaling path; KEDA reads inference metrics directly from Prometheus and manages HPA scaling.

The legacy WVA controller, though deprecated, reveals the prior design intent: a sophisticated autoscaling pipeline with pluggable engines (saturation detection, scale-from-zero, throughput analysis), a coordinator with GPU rebalancing plugins, and ConfigMap-driven runtime configuration. It watches InferencePool resources from the Gateway API Inference Extension, HPA objects, KEDA ScaledObjects (conditionally), and ConfigMaps, using a Prometheus HTTP API client for metrics collection and a Kalman filter for signal smoothing. The controller supports both cluster-scoped and namespace-scoped deployment modes.

A key architectural risk for RHOAI integration is that the legacy Dockerfile uses `CGO_ENABLED=0` (statically linked Go binary) on a distroless base image — incompatible with FIPS check-payload validation. No Konflux Dockerfile exists, so the legacy controller lacks RHOAI build pipeline readiness. However, since WVA is deprecated and KEDA is the production path, this is a documentation concern rather than a blocking issue — the RHOAI integration relies on KEDA (which has its own FIPS posture) and the blueprint YAMLs rather than the WVA binary.

The Prometheus TLS configuration in the legacy controller is well-engineered: it enforces TLS 1.2 minimum, supports CA certificate validation, mutual TLS with client certificates, and rejects credentials embedded in URLs. The OpenShift kustomize overlay integrates with the cluster's Thanos Querier and service-ca certificates for proper metrics TLS verification.
