## Purpose

**Short**: Kubernetes controller that extends KServe with RHOAI-specific model serving capabilities, managing inference service lifecycle, gateway routing, admission webhooks, serving runtime templates, and NVIDIA NIM integration.

**Detailed**: odh-model-controller is a controller-runtime based Kubernetes controller that serves as the model serving control plane for Red Hat OpenShift AI. It bridges KServe's core inference serving infrastructure with RHOAI-specific concerns: OpenShift Route/Gateway API integration, platform-aware TLS configuration, multi-accelerator serving runtime provisioning, NVIDIA NIM account management, and admission-time validation/mutation of inference resources.

The controller produces two deployable artifacts. The primary `odh-model-controller` binary runs as a controller manager with 10 reconciliation loops and 8 admission webhooks covering InferenceService, LLMInferenceService, InferenceGraph, ServingRuntime, NIM Account, Pod, Secret, ConfigMap, and Gateway resources. The secondary `model-serving-api` binary provides a standalone HTTPS REST API for gateway discovery and LLM-D sample template retrieval, supporting the RHOAI dashboard and CLI tooling.

The component ships 27 ClusterServingRuntime definitions that cover vLLM (CUDA, ROCm, Gaudi, CPU, Spyre across x86, s390x, and ppc64le), OpenVINO Model Server, and MLServer, each versioned across three release channels (GA, fast-1, fast-2). It also supports an xKS (external Kubernetes) mode where only the LLMInferenceService webhook runs, enabling deployment on non-OpenShift clusters with cert-manager for TLS.

## Architectural Analysis

The controller's architecture follows a hub-and-spoke reconciliation model where the InferenceServiceReconciler is the central orchestrator. It watches InferenceService resources and manages a constellation of owned sub-resources: Services, Routes, NetworkPolicies, RBAC Roles/RoleBindings, ClusterRoleBindings, ServiceAccounts, Secrets, ConfigMaps, and monitoring resources (ServiceMonitors, PodMonitors). This design concentrates lifecycle ownership in a single controller while delegating auxiliary concerns (secret rotation, config propagation, pod labeling, runtime template management) to specialized reconcilers.

The LLM serving path introduces a parallel control surface. The LLMInferenceServiceReconciler and GatewayReconciler work together to manage Gateway API resources, Kuadrant AuthPolicies, and KEDA TriggerAuthentications for LLM workloads. The GatewayReconciler owns the shared Gateway resource and attaches EnvoyFilters and PodMonitors, while the LLMInferenceServiceReconciler manages per-service Secrets, ServiceAccounts, Roles, RoleBindings, and AuthPolicies. This split means LLM autoscaling and auth policy lifecycle are decoupled from the legacy InferenceService path.

TLS handling is notable for its OpenShift-awareness. The controller reads the cluster-wide TLS profile from `apiservers.config.openshift.io/cluster` at startup and maps it to Go `crypto/tls` configuration, defaulting to Mozilla Intermediate ciphers when the APIServer resource is unavailable. A ProfileWatcher controller continuously monitors the APIServer resource and triggers a graceful restart when the TLS profile changes, ensuring the controller's served endpoints always reflect the cluster policy. The model-serving-api binary takes a similar approach with its own FIPS-compliant TLS configuration and certificate hot-reloading via fsnotify.

The xKS mode represents an interesting architectural decision: the same binary supports two fundamentally different deployment profiles. In xKS mode, all reconcilers and most webhooks are disabled, leaving only the LLMInferenceService webhook active. This allows the ConnectionsAPI and HardwareProfile webhook functionality to run on non-OpenShift clusters where cert-manager replaces OpenShift's service-CA for certificate provisioning.

The informer cache is tuned aggressively for memory efficiency. ConfigMap data is stripped from the cache via a custom transform function (only metadata is retained), with payload reads bypassing the cache entirely via direct API calls. Secrets are filtered by the `opendatahub.io/managed=true` label, and Pods are filtered by `component=predictor`, significantly reducing the informer's memory footprint in clusters with many resources.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace | Inferred from namespace-scoped CRDs (InferenceService, ServingRuntime, Account) and namespace-based resource ownership |

| **Tenant identifier** | namespace name | Controller watches cluster-wide, reconciles per namespace |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC roles created by InferenceServiceReconciler; Kuadrant AuthPolicies for LLM services; SelfSubjectAccessReview for gateway API access | Kubernetes RBAC, Kuadrant, Application | Controller SA has broad cluster-wide permissions (inherent to multi-tenant controllers) |
| Data storage | Per-namespace Secrets and ConfigMaps for model serving configuration | Kubernetes | Secrets filtered by label selector in cache; label absence could miss resources |
| Network traffic | Per-namespace NetworkPolicies created by InferenceServiceReconciler | Kubernetes | NetworkPolicy creation is controller-managed; no tenant-initiated network isolation |
| Compute & resources | Delegated to InferenceService resource requests/limits; HardwareProfile CRD for hardware targeting | Kubernetes / KServe | No explicit ResourceQuota or LimitRange enforcement by this controller |
| Configuration & secrets | Per-namespace Secrets with `opendatahub.io/managed=true` label; NIM API keys per Account CR | Kubernetes | Secrets are namespace-scoped and label-filtered |
| API scoping | Cluster-wide watches with namespace-based reconciliation; each reconciler processes only the owning namespace's resources | Kubernetes / Application | No tenant-level rate limiting or quota at the controller level |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Gateway (LLM serving) | Shared across namespaces | Single Gateway CR managed by GatewayReconciler; per-service HTTPRoutes and AuthPolicies provide request-level isolation |
| ClusterServingRuntime templates | Shared across cluster | Cluster-scoped templates; namespace-scoped ServingRuntime overrides possible |
