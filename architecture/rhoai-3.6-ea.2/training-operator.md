## Purpose

**Short**: Kubernetes-native operator for orchestrating distributed training and fine-tuning of ML models across multiple frameworks including PyTorch, TensorFlow, JAX, XGBoost, PaddlePaddle, and MPI.

**Detailed**: The Training Operator (also known as Kubeflow Training Operator or KFTO) is a controller-runtime-based Kubernetes operator that manages the lifecycle of distributed training jobs. It provides six Custom Resource Definitions — PyTorchJob, TFJob, JAXJob, XGBoostJob, PaddleJob, and MPIJob — each modeling a framework-specific distributed training topology. The operator reconciles these CRs by creating and managing the underlying Pods, Services, ConfigMaps, and RBAC resources needed for distributed training, including handling pod group scheduling via Volcano or scheduler-plugins for gang scheduling.

The operator is deployed as a single-replica Deployment in the `opendatahub` namespace within RHOAI. It runs a validating webhook server (port 9443) to enforce structural correctness of training job specifications at admission time, and self-manages its own TLS certificates using the OPA cert-controller library. The RHOAI distribution adds a PodMonitor for Prometheus metrics collection and applies kustomize overlays that configure namespace scoping, image references, and webhook naming conventions specific to the OpenShift AI platform.

## Architectural Analysis

The Training Operator follows the standard controller-runtime reconciler pattern but with a distinctive multi-controller architecture: each framework (PyTorch, TensorFlow, etc.) has its own dedicated reconciler and webhook, all registered dynamically at startup based on the `--enable-scheme` flag. By default, all six frameworks are enabled.

A significant architectural choice is the label-filtered informer cache (introduced to prevent unbounded memory growth). The operator only watches Pods, Services, ConfigMaps, ServiceAccounts, Secrets, Roles, and RoleBindings that carry the `training.kubeflow.org/operator-name` label, which the operator itself sets on resources it creates. ConfigMaps and Secrets are additionally excluded from the cache for direct API reads, avoiding stale data for configuration lookups.

The TLS configuration is actively managed rather than relying on static certificates. On startup, the operator reads the OpenShift APIServer resource to discover the cluster's TLS security profile (Intermediate, Modern, Custom, or Old) and applies the corresponding minimum TLS version and cipher suite selection to both the metrics server and webhook server. This means the operator's TLS posture automatically follows cluster-wide security policy changes. When running on non-OpenShift clusters, it falls back to hardened TLS 1.2+ defaults with an intermediate cipher suite.

The MPI controller is architecturally distinct from the other five frameworks: it creates additional ConfigMaps (for hostfile generation), ServiceAccounts, Roles, and RoleBindings per job, and uses a kubectl-delivery init container for distributing kubectl to launcher pods. The PyTorch controller also has unique capabilities including HorizontalPodAutoscaler management for elastic training and support for the `torch.distributed.run` elastic launch mode.

NetworkPolicy management is part of the operator's RBAC scope, indicating the operator can create per-job network policies for tenant isolation, though this behavior is framework-dependent.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregated ClusterRoles (training-edit, training-view) for per-namespace RBAC | Kubernetes RBAC | Users with cluster-admin can see all jobs; no application-level authorization beyond Kubernetes RBAC |
| Data storage | Per-namespace: Pods, Services, ConfigMaps, Secrets scoped to job's namespace | Kubernetes namespace isolation | No persistent storage managed directly; users configure their own volumes |
| Network traffic | NetworkPolicy CRUD in RBAC scope; operator can create per-job NetworkPolicies | Kubernetes NetworkPolicy | NetworkPolicy creation is capability-based, not enforced by default for all jobs |
| Compute & resources | No built-in ResourceQuota or LimitRange; users set resource requests/limits per replica spec | User configuration / Kubernetes | No operator-enforced compute isolation between tenants; relies on cluster-level quotas |
| Configuration & secrets | Per-namespace Secrets (webhook cert in operator namespace only) | Kubernetes namespace scoping | MPI controller creates per-job Roles/RoleBindings within the job's namespace |
| API scoping | Label-filtered informer cache watches only operator-labeled resources cluster-wide | Kubernetes + Application (label selector) | Operator has cluster-wide list/watch; label filter prevents cache bloat but is not a security boundary |
