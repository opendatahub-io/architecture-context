## Purpose

**Short**: End-to-end test suite and container image definitions for distributed training workloads on RHOAI, covering Kubeflow Training Operator v1, Kubeflow Trainer v2, and KubeRay.

**Detailed**: The distributed-workloads repository serves two primary functions within the RHOAI platform. First, it contains a comprehensive Go-based end-to-end test suite that validates distributed training capabilities across multiple frameworks: KFTO v1 (PyTorchJob), Kubeflow Trainer v2 (TrainJob, ClusterTrainingRuntime, JobSet workflows), KubeRay (RayCluster, RayJob, RayTune HPO), and fms-hf-tuning GPU fine-tuning. Tests exercise Kueue integration for workload scheduling, multi-node/multi-GPU scenarios, upgrade resilience, and notebook-driven SDK workflows.

Second, the repository defines container images for distributed training runtimes. Two image families exist: "runtime training" images built on AIPCC base images (CUDA 13.0 and ROCm 6.4 with OpenMPI 4.1) for MPI-based distributed training, and "universal training" images built on Jupyter workbench bases that combine notebook interactivity with the full ML runtime stack (PyTorch, DeepSpeed, Transformers, TRL, vLLM). The repository also builds Ray cluster images across CPU, CUDA, and ROCm variants. Examples and benchmarks (Stable Diffusion DreamBooth, LLM fine-tuning with Ray+DeepSpeed, MPI OSU benchmarks) complement the test suite.

## Architectural Analysis

This repository is architecturally unusual within RHOAI: it produces no deployed services or operators of its own, but instead functions as the integration test harness and image factory for the distributed workloads subsystem. The Go test code exercises platform components (Kubeflow Training Operator, KubeRay, Kueue, the RHOAI Dashboard) through their Kubernetes APIs, creating ephemeral namespaces, CRDs, and workloads to validate end-to-end behavior.

The image build strategy reveals a deliberate split between two dependency management regimes. Runtime training images inherit the AIPCC Python Package Index from their AIPCC base images (`quay.io/aipcc/base-images/cuda-*`, `quay.io/aipcc/base-images/rocm-*`), installing pinned `requirements.txt` via `uv pip install --no-index`. Universal training images extend Jupyter workbench bases and use Hermeto (cachi2) prefetch for fully hermetic builds in Konflux, sourcing `PIP_FIND_LINKS` from `/cachi2/cachi2.env`. This two-track approach reflects the transition from traditional PyPI-sourced dependency management to AIPCC's secure build pipeline.

The test architecture enforces strict suite isolation via depguard rules: `tests/kfto/`, `tests/trainer/`, `tests/fms/`, and `tests/odh/` cannot import from each other. Shared infrastructure lives in `tests/common/support/`, providing Kubernetes client abstractions, Ray/Kueue/PyTorchJob helpers, and Gomega-based assertion patterns. Every test creates its own namespace and uses `GenerateName` for Kubernetes resources to enable parallel execution.

The `InsecureSkipVerify: true` usage in three test helper files (Prometheus API client, Ray cluster client, cloud storage provider) is test-only and does not affect production images. The Python images ship `cryptography==46.0.5` and `pyopenssl==26.4.0` as transitive dependencies of the ML stack, inheriting FIPS compliance from the UBI/AIPCC base image's OpenSSL.
