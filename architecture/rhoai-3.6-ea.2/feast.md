## Purpose

**Short**: Feast is a feature store operator that manages the lifecycle of feature store instances on Kubernetes, providing feature serving, registry, and materialization for ML workloads.

**Detailed**: Feast (Feature Store) is a machine learning feature platform that enables teams to define, store, and serve features consistently for both model training and real-time inference. The RHOAI distribution ships two primary artifacts: a Go-based Kubernetes operator (`feast-operator`) that reconciles `FeatureStore` custom resources, and a Python-based feature server that exposes online features via HTTP and gRPC APIs.

The operator watches `FeatureStore` CRs and provisions a complete feature store stack per instance — including deployments for the registry server, online feature server, offline store, UI dashboard, and scheduled materialization CronJobs. It manages all associated RBAC, services, persistent storage, HPA scaling, and PodDisruptionBudgets. The operator integrates with OpenShift routes for external access and supports configurable authorization via Kubernetes RBAC, OIDC, or explicit no-auth mode.

The Python feature server (built on FastAPI/Starlette) provides a comprehensive REST API surface for feature retrieval, registry management, data lineage tracking, monitoring, label management, and an OpenAI-compatible vector search endpoint. It supports multiple online store backends (Redis, PostgreSQL, DynamoDB, SQLite, Milvus) and offline store backends (BigQuery, Snowflake, Spark, DuckDB) through a pluggable architecture. A Go feature server binary provides a high-performance alternative for online feature retrieval specifically.

## Architectural Analysis

Feast follows a split-plane architecture where the operator (control plane) and the feature server (data plane) are built in different languages and deployed as separate images. The operator uses controller-runtime and reconciles a single CRD (`FeatureStore`) that encodes the full desired state of a feature store instance — registry backend, online/offline store backends, auth mode, TLS configuration, scaling parameters, and image references. This single-CRD design keeps the user-facing API simple but pushes considerable complexity into the reconciler, which must map the CRD spec into 8+ owned Kubernetes resource types (Deployments, Services, ConfigMaps, ServiceAccounts, Roles, RoleBindings, PVCs, CronJobs, HPAs, PDBs, Routes).

The auth model is noteworthy: the operator supports three mutually exclusive modes selected via a CEL-validated union in the CRD (`kubernetes`, `oidc`, `noAuth`). When Kubernetes auth is selected, the operator provisions per-namespace RBAC roles that the Python feature server checks at request time via TokenReview. OIDC mode references a Secret containing the identity provider configuration. The operator also reads the OpenShift `APIServer` resource to inherit the cluster's TLS profile, using `openshift/controller-runtime-common` to derive cipher suites and minimum TLS version — a pattern that ensures the operator's metrics endpoint respects cluster-wide TLS policy.

The Python feature server is a large, feature-rich application with 100+ REST endpoints spanning feature retrieval, registry CRUD, OpenLineage integration, monitoring metrics, active learning, label management, saved datasets, and vector store search. The Go feature server is deliberately narrower — it exposes only `/get-online-features`, `/health`, and `/metrics` — and is used as the high-performance online serving path. Both servers share protobuf-defined gRPC service interfaces (`ServingService`, `RegistryServer`, `TransformationService`) defined in the `protos/` directory.

A secondary controller (`NotebookConfigMapReconciler`) watches `FeatureStore` CRs and Kubeflow `Notebook` resources to automatically inject feature store client configuration into notebook workspaces, tightening the integration between Feast and the RHOAI notebook environment.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-instance RBAC roles or OIDC; configurable via CRD AuthzConfig | Kubernetes / Application | noAuth mode explicitly disables all auth — documented as dev/test only |
| Data storage | Per-instance deployments and PVCs; backend credentials per-namespace Secrets | Kubernetes / Application | Shared backend databases (e.g., shared PostgreSQL) may require row-level isolation at the application layer |
| Network traffic | Per-namespace Services; optional Routes for external access | Kubernetes | No NetworkPolicy resources created by the operator; cross-namespace access depends on cluster network policy |
| Compute & resources | Per-instance Deployments with resource limits; HPA and PDB per instance | Kubernetes / Application | No ResourceQuota enforcement by the operator; depends on namespace-level quotas |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; client config auto-injected per namespace | Kubernetes | None identified |
| API scoping | Namespace-scoped CRD watches; operator watches across namespaces for its own CRD | Kubernetes | Operator has cluster-wide RBAC; individual feature server instances are namespace-scoped |
