## Purpose

**Short**: ML Metadata (MLMD) is a gRPC server and client library for recording and retrieving metadata associated with ML workflows, tracking artifacts, executions, contexts, and their lineage relationships.

**Detailed**: ML Metadata provides a metadata store service that captures the provenance and lineage of machine learning pipelines. The core is a C++ gRPC server (`metadata_store_server`) built with Bazel, which exposes a comprehensive API for managing ML metadata entities: artifact types, execution types, context types, and their instances. It tracks relationships between these entities through events (artifact-execution links), attributions (artifact-context links), associations (execution-context links), and parent-child context hierarchies.

The server supports three production database backends -- MySQL, PostgreSQL, and SQLite -- plus an in-memory fake database for testing. Database schema migrations are built in, supporting both upgrades and downgrades. The Python client library wraps the C++ implementation via SWIG bindings for local access, and also provides a gRPC client for remote server access. In the RHOAI platform, MLMD serves as the metadata backbone for ML pipeline orchestration, enabling experiment tracking, artifact lineage, and reproducibility.

## Architectural Analysis

MLMD follows a straightforward stateless-server-with-external-database pattern. The C++ gRPC server creates a new database connection per RPC call (`MetadataStoreServiceImpl` connects on each request in `metadata_store_service_impl.cc`), which means it carries no in-process state between requests. This simplifies horizontal scaling but makes the database the single point of failure and the performance bottleneck.

The server binary is configured entirely through command-line flags or a protobuf text-format config file (`MetadataStoreServerConfig`). SSL/TLS for the gRPC channel is optional and configurable, including mutual TLS with client certificate verification. Database connections to MySQL and PostgreSQL also support SSL with configurable certificates and cipher suites.

The Konflux Dockerfile uses a multi-stage build: a UBI 9 builder stage compiles the C++ binary with Bazel 6.3.2, then copies only the server binary and MariaDB connector source (for license compliance) into a `ubi9/ubi-minimal-pqc` runtime image. The server runs as a non-root user (65534:65534) and exposes port 8080 for gRPC. The post-quantum crypto (PQC) base image variant in the Konflux build indicates forward-looking cryptographic posture, though the application itself does not explicitly configure post-quantum algorithms.

A notable design aspect is the dual-use Python library: it can operate both as a direct in-process metadata store (via SWIG-wrapped C++ code accessing SQLite/MySQL directly) and as a gRPC client to a remote metadata store server. This flexibility allows both embedded and client-server deployment models.
