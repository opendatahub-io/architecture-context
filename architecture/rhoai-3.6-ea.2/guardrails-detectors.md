## Purpose

**Short**: A collection of text detection microservices for the FMS Guardrails Orchestrator, providing regex/heuristic, HuggingFace ML-model, and LLM-as-a-judge based content analysis.

**Detailed**: guardrails-detectors provides three distinct detector implementations that integrate with the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator) to perform safety and content analysis on LLM inputs and outputs. Each detector type runs as an independent FastAPI microservice behind uvicorn.

The **built-in** detector bundles lightweight, heuristic detection functions — regex-based PII detection (email, credit card, SSN, phone numbers, IP addresses), file-type validation (JSON, XML, YAML with optional schema checking), and a custom detector framework that allows users to define arbitrary Python detection functions at deploy time. The **huggingface** detector wraps HuggingFace Transformers models (sequence classification, token classification, and Granite CausalLM) to perform ML-based content detection, deployed as a KServe InferenceService with model storage on S3-compatible storage (MinIO). The **llm_judge** detector uses the vllm_judge library to perform LLM-as-a-judge evaluations against a remote vLLM-compatible inference server, supporting built-in metrics like safety, toxicity, accuracy, and helpfulness.

All three detectors conform to the IBM Detector API specification, exposing `/api/v1/text/contents` as their primary detection endpoint, with the huggingface and llm_judge detectors deployed via KServe ServingRuntime definitions.

## Architectural Analysis

The guardrails-detectors repository follows a shared-base/specialized-variant pattern. A common application framework (`DetectorBaseAPI`) in `detectors/common/app.py` extends FastAPI with a detector registry, Prometheus instrumentation counters (detections, requests, errors, runtime), custom error handling, and a `/health` endpoint. Each detector variant (`built_in`, `huggingface`, `llm_judge`) builds on this base with its own `app.py` entry point and detector implementation.

The built-in detector is notably different from the other two in its extensibility model: it dynamically loads user-supplied Python files (`custom_detectors.py`) at startup via `importlib`, performing a best-effort static code analysis pass to block dangerous imports (`os`, `subprocess`, `sys`, `shutil`) and function calls (`eval`, `exec`, `open`, `compile`, `input`). This is explicitly not a security sandbox — it reduces accidental misuse but does not provide isolation.

The huggingface detector demonstrates a multi-architecture build strategy. The Konflux Dockerfile (`Dockerfile.konflux.hf`) uses build args to select between AIPCC CPU and CUDA base images depending on `TARGETARCH`, enabling a single build definition to produce images for amd64 (CUDA-accelerated), arm64 (CUDA), and ppc64le/s390x (CPU fallback). Model weights are loaded from a mount path (`/mnt/models`) configured via KServe's model storage mechanism, with the model architecture auto-detected from HuggingFace config to select the appropriate inference pipeline (sequence classification, token classification, or causal LM).

A notable security gap is the complete absence of authentication middleware across all three detector services. The FastAPI applications register no auth middleware, meaning all HTTP endpoints are unauthenticated when accessed directly. In a production KServe deployment, the InferenceService manifests include `security.opendatahub.io/enable-auth: 'true'` and Istio sidecar injection annotations, indicating that authentication is expected to be enforced at the mesh/platform layer rather than within the application itself.

The deploy manifests under `detectors/huggingface/deploy/` include a development-oriented MinIO deployment with hardcoded access keys in a Kubernetes Secret. These manifests serve as example deployment templates rather than production configurations.
