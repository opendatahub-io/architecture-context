## Purpose

**Short**: OpenAI-compatible batch inference API gateway that manages large-scale batch job submission, processing, and lifecycle in Kubernetes environments.

**Detailed**: Batch Gateway is a high-performance system for processing large-scale batch inference jobs alongside interactive workloads. It exposes OpenAI-compatible `/v1/batches` and `/v1/files` REST endpoints for submitting, tracking, and managing batch inference jobs containing up to 50,000 requests per job. The system is designed to minimize interference with interactive workloads while satisfying batch jobs' service level objectives through AIMD-based adaptive concurrency control.

The component is decomposed into three independently deployable binaries: an **API server** that handles REST API requests and file management, a **batch processor** (deployed as a StatefulSet) that pulls jobs from a priority queue and dispatches individual inference requests to downstream llm-d inference gateways, and a **garbage collector** that periodically removes expired jobs and files. The data layer uses PostgreSQL for metadata storage, Redis/Valkey for the priority queue and event channels, and S3-compatible or filesystem storage for batch input/output files.

Batch Gateway integrates tightly with the llm-d ecosystem. The processor sends inference requests to llm-d Router endpoints (one global gateway or per-model gateways) and can optionally use llm-d-async for metrics-driven dispatch flow control. Multi-tenancy is enforced at the application layer through header-based tenant identification (`X-MaaS-Username`), with all database queries scoped by tenant ID and cross-tenant requests returning 404. Authentication and authorization are delegated to an external gateway layer (Kuadrant/Authorino).

## Architectural Analysis

Batch Gateway follows a clean separation-of-concerns architecture with three stateless (or minimally stateful) binaries sharing a common data layer. The API server is a standard HTTP service deployed as a Kubernetes Deployment, while the processor uses a StatefulSet with emptyDir working storage for local input file copies and plan files during execution. The garbage collector runs as a single-replica Deployment to avoid concurrent deletes.

The system's multi-tenancy model is notable for being entirely application-enforced rather than Kubernetes-enforced. Tenant identity flows in via an HTTP header (`X-MaaS-Username`, configurable), is injected into context by middleware, and propagated to every database query. The database layer (both PostgreSQL and Redis backends) filters by tenant ID on all read operations and stores tenant ID with every record. This provides strong logical isolation but relies on correct application behavior — a bug in tenant propagation could leak data across tenants.

Authentication is deliberately absent from the batch gateway itself. The README and Helm chart documentation describe a security boundary model where authentication/authorization is enforced at the gateway layer (Kuadrant/Authorino) before traffic reaches the batch API. The batch gateway trusts the tenant identity header set by the upstream gateway. The observability endpoints (`/health`, `/ready`, `/metrics`) are served on a separate port (8081 for apiserver, 9090 for processor, 9091 for GC) and are always plain HTTP without authentication — appropriate for cluster-internal scraping.

The processor's inference dispatch supports two modes: synchronous (direct HTTP to llm-d Router) and asynchronous (via llm-d-async Redis queues). The sync path includes sophisticated retry logic with status-code-aware backoff (different strategies for 429 vs. 502/503/504), Retry-After header honoring, and capacity-retry tracking. The async path uses the llm-d-async producer library to enqueue requests and poll for results. Both paths support custom TLS configuration including mTLS for outbound inference connections.

Pod security is well-hardened: non-root execution, read-only root filesystem, all Linux capabilities dropped, seccomp enabled, and secrets mounted read-only via projected volumes with `os.OpenInRoot()` for path traversal prevention. The Helm chart validates TLS configuration and supports cert-manager integration for automated certificate lifecycle.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to upstream gateway (Kuadrant/Authorino); no internal auth enforcement | External gateway | If gateway is misconfigured or bypassed, batch gateway has no authentication; tenant header can be spoofed if traffic reaches the service directly |
| Data storage | All database queries filter by tenant ID; Redis Lua scripts and PostgreSQL queries include tenant ID predicates; cross-tenant retrieval returns 404 | Application (database layer) | Application-enforced isolation — a bug in tenant ID propagation could leak data across tenants |
| Network traffic | No per-tenant NetworkPolicies defined in Helm chart | Not enforced | No network-level tenant isolation; all tenants share the same service endpoints |
| Compute & resources | No per-tenant ResourceQuotas or compute isolation | Not enforced | All tenants share the same processor workers and concurrency limits; one tenant's large batch could consume all workers |
| Configuration & secrets | Shared secrets for database URLs and API keys; no per-tenant secrets | Kubernetes (single shared Secret) | All tenants use the same database credentials and inference API key |
| API scoping | Tenant ID extracted from request header and used in all database queries; batch handler explicitly checks `item.TenantID != tenantID` and returns 404 on mismatch | Application | Correct implementation — explicit tenant check in retrieval handlers (batch_handler.go:379) |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL | Row-level tenant ID column | Application query filter (all queries include tenant ID WHERE clause) |
| Redis/Valkey | Hash field tenant ID | Redis Lua scripts filter by tenantID field in hash entries |
| S3-compatible storage | No explicit tenant boundary in file keys | File IDs are UUIDs scoped through database tenant query; no S3-level bucket or prefix isolation |
