## Purpose

**Short**: Multi-domain Kubernetes operator that manages AI trustworthiness, evaluation, and guardrails services on Red Hat OpenShift AI.

**Detailed**: The trustyai-service-operator is a Go-based Kubernetes operator built on controller-runtime that manages six distinct service domains within the RHOAI platform: TrustyAI model explainability (TrustyAIService), language model evaluation (LMEvalJob), centralized evaluation hub (EvalHub), guardrails orchestration (GuardrailsOrchestrator), NVIDIA NeMo guardrails (NemoGuardrails), and a platform integration module (TrustyAI). Controllers are registered via a dynamic service registry and selectively enabled at startup via the `--enable-services` flag.

The operator provisions complete workload stacks for each service domain: Deployments with kube-rbac-proxy sidecars for TrustyAIService, multi-tenant evaluation infrastructure for EvalHub (including per-namespace RBAC, ConfigMap propagation, and ServiceMonitor creation), batch Job orchestration for LMEvalJob with Kueue integration, and Deployment management for GuardrailsOrchestrator and NemoGuardrails. A separate `trustyai-operator-module` sub-module acts as a DSC (DataScienceCluster) component controller that manages the operator's own lifecycle within the RHOAI platform operator.

## Architectural Analysis

The operator exhibits a hub-and-spoke architecture centered on a single manager binary that houses all six controller domains. This design simplifies deployment (one Pod, one image) but creates a broad RBAC surface — the manager ClusterRole spans 39 distinct rules covering 15+ API groups. The dynamic controller registration pattern (`registerService`/`SetupControllers`) is a clean separation that allows individual controllers to be enabled or disabled without code changes, but it means the single binary carries the weight of all domains regardless of which are active.

TLS handling is notably well-designed: the operator reads the cluster-wide `apiservers.config.openshift.io/cluster` TLS security profile at startup via `pkg/tls/tls.go` and applies the resolved cipher suites and protocol versions to both the metrics server and webhook server. A dedicated `ProfileWatcher` controller monitors the APIServer resource and triggers a graceful manager restart when the profile changes. When running on non-OpenShift clusters, the operator falls back to hardened Intermediate defaults — fail-safe rather than fail-open.

The EvalHub controller is the most architecturally complex domain, implementing true multi-tenancy with namespace-based tenant isolation, cross-namespace ConfigMap propagation for providers and collections, and a dedicated metrics surface on port 8081 separate from the API surface. The tenant model supports both multi-tenant (one EvalHub serving labeled namespaces) and single-tenant modes, with a placement guard that prevents invalid configurations.

Cache is deliberately disabled for ConfigMap, Secret, Pod, and Service types to prevent OOM from cluster-wide informers. This trades latency (~50ms direct API reads vs ~1ms cached) for memory safety, which is appropriate given the operator's broad watch surface.

The repo produces three distinct container images via Konflux: the main operator (`Dockerfile.konflux`), the LMES evaluation driver (`Dockerfile.konflux.driver`), and the trustyai-operator-module (`trustyai-operator-module/Dockerfile.konflux`). Two additional non-Konflux Dockerfiles exist for the LMES evaluation job runner (Python-based, `Dockerfile.lmes-job`) and the guardrails orchestrator (Rust-based, `Dockerfile.orchestrator`).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC Roles (evalhub-tenant-admin, evalhub-user) in single-tenant mode; per-namespace ClusterRoleBindings in multi-tenant mode | Kubernetes RBAC | Roles are provisioned by the operator; no external policy enforcement |
| Data storage | Per-namespace ConfigMaps for providers and collections; system vs tenant separation | Kubernetes namespace isolation | System ConfigMaps are copied into instance namespace; tenant ConfigMaps stay in-place |
| Network traffic | Cluster-internal Services; no cross-namespace NetworkPolicy created by operator | Kubernetes (default) | No explicit NetworkPolicy created; relies on platform-level policies |
| Compute & resources | No ResourceQuota or LimitRange created by operator | N/A | Resource limits delegated to platform; no operator-level enforcement |
| Configuration & secrets | Per-namespace Secrets provisioned per TrustyAIService instance | Kubernetes namespace isolation | Secrets are templated by controller; no cross-tenant access possible |
| API scoping | Namespace-scoped CRD watches; tenant namespace discovery via label selector | Kubernetes + Application | Multi-tenant EvalHub has placement guard preventing control-plane namespace from being a tenant |
