## Purpose

**Short**: An LLM deployment planning platform that guides users from business requirements to production-ready Kubernetes deployments through conversational AI, capacity planning, and SLO-driven recommendations.

**Detailed**: llm-d Planner is a multi-component Python application that addresses the complexity of deploying LLMs in production. It unifies model selection, GPU sizing, performance estimation, and Kubernetes configuration generation into a single platform. The system implements a four-stage conversational flow: (1) extract business intent via LLM-powered natural language analysis, (2) generate deployment specifications with SLO targets mapped from use-case templates, (3) produce ranked GPU+model recommendations scored across quality, price, and latency dimensions, and (4) generate and deploy KServe/vLLM configurations to Kubernetes clusters.

The architecture comprises three deployable components: a FastAPI backend service exposing a REST API pipeline at port 8000, a Streamlit frontend at port 8501 providing a conversational UI with recommendation visualization, and an Ollama sidecar at port 11434 for local LLM inference (intent extraction). The backend supports pluggable LLM providers (Ollama, OpenAI-compatible, Vertex AI) and can connect to the RHOAI Model Catalog for benchmark data. Quality scoring combines dual-source data from Arena human preferences and Artificial Analysis automated benchmarks, normalized to percentile ranks with per-use-case category weighting. A vLLM simulator enables GPU-free development and testing.

## Architectural Analysis

llm-d Planner follows a layered service architecture centered on a FastAPI backend that coordinates multiple domain engines. The backend acts as both a REST API gateway and an orchestration layer, routing requests through a sequential pipeline: intent extraction → specification generation → recommendation scoring → deployment configuration. Each stage has a dedicated service module (`intent_extraction/`, `specification/`, `recommendation/`, `configuration/`) with clean facade classes, enabling both API-driven and library-style (pip-installable) usage via the `Planner` class.

The recommendation engine is the core differentiator. It implements multi-criteria scoring across three dimensions (quality, price, latency) with configurable priority weights (default 45/45/10). Quality scoring is notably sophisticated: it composites Arena human-preference Elo ratings across 27 categories with Artificial Analysis automated benchmarks, applying per-use-case category weights. Results are presented as four ranked views (best quality, lowest cost, lowest latency, balanced), enabling different decision perspectives.

The cluster interaction layer (`cluster/`) uses two strategies: the Kubernetes Python client for read-only node inspection (GPU detection via nvidia.com/gpu.product labels), and kubectl subprocess calls for deployment lifecycle management (apply, delete, status). This dual approach means the component needs both Python SDK access and kubectl in the container PATH. GPU detection results are cached with a 5-minute TTL to minimize Kubernetes API load.

Security-wise, the application has notable gaps typical of an incubation-stage project. The FastAPI backend has no authentication middleware — all 31 API endpoints are unauthenticated. The CORS configuration uses `allow_origins=["*"]`, which is explicitly noted as needing production hardening. OpenShift Routes provide edge TLS termination for external access, but internal service-to-service communication within the `planner` namespace is unencrypted HTTP. The backend does mount the OpenShift service-CA bundle for TLS verification when connecting to the Model Catalog API, showing awareness of the pattern even if not fully generalized.

The project uses multiple external API keys (HuggingFace, OpenAI, Vertex AI, Artificial Analysis, Model Catalog) managed as environment variables sourced from the `planner-secrets` Kubernetes Secret. All are marked `optional: true` in the deployment manifest, reflecting the modular LLM-provider architecture where only the active provider's credentials are required.
