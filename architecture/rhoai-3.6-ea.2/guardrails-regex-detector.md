## Purpose

**Short**: A lightweight Rust HTTP service that detects PII and custom patterns in text using regular expressions, designed for integration with the FMS Guardrails Orchestrator.

**Detailed**: The guardrails-regex-detector is a single-purpose detection microservice in the TrustyAI guardrails ecosystem. It accepts text content via a REST API and scans it against both built-in PII detectors (email addresses, Social Security numbers, credit card numbers) and arbitrary user-supplied regular expressions. Each match is returned with character offsets, a detection type classification, and a fixed confidence score of 1.0 (deterministic regex matching).

The service is built on Axum (an async Rust web framework backed by Tokio) and runs as a stateless HTTP server with no persistent storage, no TLS termination, and no authentication of its own. It is intended to sit behind the FMS Guardrails Orchestrator, which handles routing, auth, and policy decisions. The detector itself is a pure compute function: text in, detections out.

The codebase is minimal (~170 lines of Rust across two source files), reflecting its role as a focused leaf service in a larger guardrails pipeline rather than a standalone platform component.

## Architectural Analysis

The guardrails-regex-detector follows a deliberately narrow architectural pattern: a single async HTTP server with no external dependencies, no state, and no configuration files. The entire detection logic is compiled into one static binary that ships inside a UBI 9 minimal container.

The design delegates all cross-cutting concerns to the surrounding infrastructure. There is no TLS termination in the application -- it binds a plain TCP listener (`tokio::net::TcpListener`) and expects the orchestrator or service mesh to handle encryption. There is no authentication middleware -- the analyzer identified "header passthrough" semantics, but source inspection confirms the application does not read, validate, or forward any headers for auth purposes. It simply deserializes the JSON body and returns results. Any auth enforcement must occur upstream in the Guardrails Orchestrator or at the network level.

The built-in detectors (email, SSN, credit card) compile their regex patterns on every request rather than caching them. For a service expected to handle high-throughput guardrails checking, this is a potential performance concern -- the `regex` crate compiles patterns to deterministic finite automata, so compilation cost is non-trivial for complex patterns like the SSN detector. Custom regex patterns supplied by callers are also compiled per-request by design, but the built-in patterns could be pre-compiled at startup.

Error handling is asymmetric: an empty `detector_params.regex` list returns HTTP 400, but an invalid custom regex is silently skipped with a tracing warning rather than failing the request. This means a caller could receive an empty detection list for a valid input if all supplied patterns are malformed, with no indication of failure in the response body.

The Dockerfile uses a multi-stage build with a Debian-based Rust builder (`rust:1.84.0`) and a UBI 9 minimal release image. The `compat-openssl11` RPM is installed in the release image for system library compatibility, but the application code contains no TLS or cryptographic operations. There is no Konflux-specific Dockerfile on this branch, suggesting the Konflux build pipeline may add one on downstream release branches or use the existing Dockerfile directly.

A notable operational concern: the handler at `src/detectors.rs:100` logs the full deserialized request payload at `info` level, which could expose sensitive PII data (the very content being scanned for PII) in application logs.
