## Purpose

**Short**: An OpenAI-compatible HTTP gateway that routes chat completion requests through the FMS Guardrails Orchestrator with configurable per-route detector pipelines for content filtering.

**Detailed**: The vllm-orchestrator-gateway is a Rust-based HTTP service that sits between clients and the FMS Guardrails Orchestrator, providing a simplified OpenAI-compatible chat completions interface with configurable safety guardrails. It reads a YAML configuration file that defines detector pipelines (e.g., PII detection via regex) and exposes dynamically generated routes of the form `/{route_name}/v1/chat/completions`, each associated with a specific set of input/output detectors.

When a request arrives, the gateway injects the route's detector configuration into the payload and forwards it to the orchestrator's `/api/v2/chat/completions-detection` endpoint. If detectors flag content in the response, the gateway substitutes a configurable fallback message. The gateway supports both streaming (SSE) and non-streaming response modes, forwarding authorization and `x-forwarded-*` headers transparently.

The gateway optionally establishes mTLS connections to the orchestrator using service-mesh-provisioned certificates, with automatic protocol selection (HTTP vs HTTPS) based on certificate availability. This design enables drop-in replacement of an unguardrailed chat completions endpoint with a guardrailed one, requiring no client-side changes beyond updating the URL.

## Architectural Analysis

The gateway follows a thin routing proxy pattern: it has no business logic of its own beyond route-to-detector mapping and fallback message substitution. The entire behavior is driven by a single YAML configuration file loaded at startup, making it operationally simple but also meaning configuration changes require a restart.

The mTLS implementation in `build_orchestrator_client` uses OpenSSL to construct PKCS#12 identity bundles from PEM certificates at well-known service-mesh paths (`/etc/tls/private/`). The `danger_accept_invalid_hostnames(true)` call is gated behind `hostname == "localhost"`, limiting the relaxation to development scenarios. TLS is correctly auto-detected: the client upgrades to HTTPS only when both client cert and key exist on disk.

The streaming path deserializes each SSE chunk to check for detections before re-serializing, which adds latency proportional to chunk size. The non-streaming path has a subtle error handling asymmetry: on success it constructs a JSON response, but on error it discards the typed error and re-unwraps `response_result.err()`, which could panic if the error has been consumed. This is mitigated by the match arm structure but represents a code quality concern.

Config validation runs synchronously at startup and panics on invalid configurations (unresolved detector references, duplicate server bindings). This fail-fast behavior is appropriate for a deployment where misconfiguration should prevent pod readiness.
