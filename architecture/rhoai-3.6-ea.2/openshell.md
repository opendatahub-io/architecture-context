## Purpose

**Short**: OpenShell is the safe, private runtime for autonomous AI agents, providing sandboxed execution environments governed by declarative YAML policies that prevent unauthorized file access, data exfiltration, and uncontrolled network activity.

**Detailed**: OpenShell provides isolated, policy-enforced execution environments for AI agents such as Claude Code, OpenCode, Codex, and GitHub Copilot. The system follows a gateway–supervisor–sandbox architecture: a Gateway control-plane API manages sandbox lifecycle through pluggable compute drivers (Docker, Podman, Kubernetes, MicroVM, Windows MXC), a Supervisor enforces policy and manages upstream networking per sandbox, and a Sandbox runtime runs inside the agent workload container as a minimal, statically-linked process monitor.

The platform enforces defense-in-depth across four policy domains: filesystem access control (locked at creation), network egress filtering with L7 enforcement (hot-reloadable), process constraints including seccomp and privilege escalation prevention (locked at creation), and provider credential injection with endpoint-bound scoping (hot-reloadable). Provider profiles define credential bundles, endpoints, and authorized client binaries; credentials are injected at runtime and never written to the sandbox filesystem.

OpenShell ships client SDKs for Python (PyPI), TypeScript (GitHub Packages), Go, and Rust. The RHOAI distribution builds four Konflux container images—gateway, supervisor, sandbox, and CLI—from UBI 9 base images with Hermeto-prefetched dependencies.

## Architectural Analysis

OpenShell's architecture is structured as a Rust-native, multi-binary system with clear process isolation boundaries. The gateway (axum + tonic server) exposes a multiplexed gRPC/HTTP API on port 8080 and coordinates sandbox lifecycle through an internal driver registry. Each compute driver (Docker, Podman, Kubernetes, VM, MXC) is an in-process gRPC `ComputeDriver` backend selected at build time via Cargo feature flags. The Kubernetes driver uses the `agents.x-k8s.io/v1` Sandbox CRD for pod lifecycle and supports three workspace modes: shared (single namespace), managed (auto-created per-workspace namespaces), and operator (pre-provisioned namespaces).

The security architecture is notable for its layered design. TLS is handled by `rustls` with the `aws-lc-rs` cryptographic provider—a FIPS-capable backend, though FIPS validation status depends on runtime configuration. The gateway supports optional mTLS for sandbox callbacks and OIDC for user authentication. The supervisor implements an L7 proxy that intercepts HTTP requests and CONNECT tunnels, applying per-endpoint policy decisions and injecting provider credentials only for policy-admitted destinations. OPA integration (`regorus` crate) provides policy evaluation for network decisions.

The sandbox binary is unique in the architecture: it is compiled as a fully-static glibc binary (`-C target-feature=+crt-static`) so it can be injected into arbitrary agent workload containers regardless of their base OS. It uses a custom isolation protocol (RFC 0012 `IsolationBackend` trait) to communicate with the supervisor across the process boundary. The formal policy verification layer uses Z3 SMT solving to prove policy boundary correctness before sandbox creation.

Post-quantum cryptography support (`DEFAULT:PQ` crypto policy) is configured in the gateway, supervisor, and CLI runtime images, positioning the platform for future quantum-resistant requirements.
