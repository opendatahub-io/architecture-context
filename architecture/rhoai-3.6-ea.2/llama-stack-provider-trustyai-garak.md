## Purpose

**Short**: Garak red-teaming evaluation adapter for the eval-hub platform, enabling automated LLM vulnerability scanning as Kubernetes Jobs or Kubeflow Pipelines.

**Detailed**: llama-stack-provider-trustyai-garak provides a `FrameworkAdapter` implementation for the eval-hub evaluation platform that integrates NVIDIA's Garak red-teaming framework with OpenShift AI. The adapter enables automated vulnerability assessment of Large Language Models for prompt injection, jailbreaks, toxicity, bias, and other security risks, with benchmark profiles aligned to OWASP LLM Top 10, AVID taxonomy, and CWE standards.

The component operates in two execution modes. In **simple mode**, garak runs as a subprocess directly inside the eval-hub Kubernetes Job pod — suitable for standard scans. In **KFP mode**, the adapter submits a six-step Kubeflow Pipeline (validate → resolve taxonomy → SDG → prepare prompts → garak scan → write outputs), polls for completion, and retrieves results via S3-compatible storage. KFP mode additionally supports **intents-based testing**, which uses synthetic data generation (SDG) with policy taxonomies and TAPIntent probes to perform targeted risk assessment against custom security policies.

Despite the repository name referencing "llama-stack-provider," all Llama Stack provider code was removed as of v0.5.0. The package is exclusively an eval-hub adapter with no llama-stack/ogx dependency.

## Architectural Analysis

The component follows the eval-hub `FrameworkAdapter` pattern, where the adapter reads a `JobSpec` from a mounted ConfigMap (`/etc/eval-job/spec.json`), resolves benchmark configuration via a deep-merge strategy (profile defaults → user overrides), and reports results back to eval-hub via sidecar callbacks. This design decouples the scanning framework from the orchestration platform.

The API key management architecture is notably sophisticated. A multi-layer resolution chain supports per-model-role keys (TARGET, JUDGE, ATTACKER, EVALUATOR, SDG, TRANSLATION) with fallback semantics: environment variables → KFP volume-mounted secret files → evalhub sidecar secret → generic `API_KEY` → `"DUMMY"`. This accommodates both the older direct-auth model and the newer sidecar-proxy model (evalhub ≥ 0.4.4) where `AutomountServiceAccountToken=false` and authentication is injected transparently. All API keys are redacted from config files before upload to S3 or OCI storage.

The KFP pipeline image resolution uses a three-tier fallback: `KFPConfig.base_image` → `KUBEFLOW_GARAK_BASE_IMAGE` env var → ConfigMap lookup in `trustyai-service-operator-config` across candidate namespaces (`redhat-ods-applications`, `opendatahub`) → hardcoded default digest. This allows the TrustyAI operator to control the pipeline component image centrally.

A key architectural risk is the broad dependency surface. The `[inline]` optional dependency set pulls in garak and its full transitive closure (torch, transformers, langchain, litellm, anthropic, openai, cohere, mistralai, ollama, replicate, etc.), resulting in ~200 PyPI packages. While this is necessary for garak's multi-provider probe support, it creates a large attack surface and complicates FIPS compliance assessment.
