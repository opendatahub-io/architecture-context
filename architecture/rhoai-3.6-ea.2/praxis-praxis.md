## Purpose

**Short**: Praxis is a Rust-based framework for building high-performance, composable proxy servers with a filter-first architecture, used as an AI and cloud-native gateway.

**Detailed**: Praxis is a cloud-native proxy server built in Rust on top of Cloudflare's Pingora engine. It provides a filter-first architecture where every behavior — routing, load balancing, rate limiting, body-based routing, observability, and security enforcement — is implemented as a composable filter plugged into named chains. Listeners bind to addresses and reference filter chains, which are resolved and concatenated into pipelines at startup and can be swapped atomically at runtime via config hot-reload.

The project targets multiple deployment patterns: ingress (API gateway, edge proxy), egress (workload-to-upstream), east/west (sidecar), and security gateway (guardrails). AI-specific features are maintained in a separate repository (`praxis-proxy/ai`). Praxis performs all cryptography through the system OpenSSL library via a `rustls-openssl` provider, enabling FIPS 140-3 compliance on Red Hat Enterprise Linux hosts in FIPS mode. The FIPS build ships on UBI 9 and excludes the policy engine (whose dependencies carry their own cryptography).

The codebase is organized as a Rust workspace with five core crates (`server`, `protocol`, `filter`, `core`, `tls`) following a strict dependency flow, plus test crates for conformance, integration, security, resilience, and benchmarking. The standard container build uses Alpine; the FIPS build uses UBI 9 with Red Hat's `rust-toolset`.

## Architectural Analysis

Praxis's architecture is built around two orthogonal concepts: **pipelining** (config-time composition of named filter chains into per-listener pipelines) and **routing** (runtime selection of upstream clusters by the `router` filter based on path, host, and headers). This separation keeps the filter system simple — filters write results without knowing about routing decisions, while the pipeline executor handles branching logic.

The crate dependency flow (`server → protocol → filter → core → tls`) enforces clear layering. Protocol adapters (`praxis-protocol`) translate Pingora's callback model into pipeline invocations, keeping Pingora responsible for HTTP framing, connection pooling, and request-smuggling prevention while Praxis owns business logic, filtering, and observability. The `praxis-tls` crate installs a single process-wide cryptographic provider (OpenSSL-backed rustls) at startup, with no fallback — if no provider is installed, the process fails loudly rather than picking one silently.

Dynamic configuration reload is achieved through `Arc<ArcSwap<FilterPipeline>>`: each request loads a snapshot pinned for its lifetime, and a file watcher (500ms debounce via the `notify` crate) validates, rebuilds, and swaps pipelines atomically. Changes that cannot be applied dynamically (listener topology, protocol type, TLS toggle) are logged as warnings and rejected.

The FIPS build deserves architectural attention: it uses `--no-default-features` to exclude the policy engine (and its `ppe`, `sha2`, `hmac`, `aws-lc-rs` dependency tree), compiles with Red Hat's `rust-toolset` on UBI 9, and dynamically links against the system `libcrypto.so.3`. The `OPENSSL_NO_VENDOR=1` environment variable ensures the system library is used rather than a vendored copy. At runtime, Praxis checks both the kernel FIPS flag (`/proc/sys/crypto/fips_enabled`) and the provider's own FIPS status, and can be configured to refuse startup if either is missing (`PRAXIS_REQUIRE_FIPS`).

Reserved header prefixes (`x-praxis-*`, `x-ext-protocol-*`, `x-ext-agent-*`) are enforced at both ingress and egress: client requests carrying them are rejected with 400, and they are stripped from backend responses. This makes header-based routing decisions tamper-proof for internal metadata promoted from request bodies by filters like `json_body_field`.
