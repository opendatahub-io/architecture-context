## Purpose

**Short**: Module operator that manages the lifecycle of the upstream Feast feature store operator within the OpenDataHub/RHOAI platform.

**Detailed**: The feast-module-operator is a meta-operator built on the ODH modular handler framework. It watches a singleton cluster-scoped `FeastOperator` custom resource (API group `components.platform.opendatahub.io/v1alpha1`) and reconciles it by rendering bundled kustomize manifests to deploy the upstream feast-operator (`feast-operator-controller-manager`). The ODH Operator deploys this module operator via a Helm chart, creates the `FeastOperator` CR with platform configuration (e.g. OIDC issuer URL), and this operator handles the full deployment lifecycle including image parameterization, platform version handshake, deployment selector migration, and garbage collection of cluster-scoped resources.

The operator embeds manifests for the upstream feast-operator (Feast v0.66.0) and uses kustomize overlays to configure them for ODH or RHOAI environments. It manages a rich set of Kubernetes resources on behalf of the feast-operator including CRDs (`feast.dev/FeatureStore`), RBAC, deployments, services, jobs, and monitoring resources.

## Architectural Analysis

The feast-module-operator follows the ODH modular operator pattern: a lightweight Go controller that delegates reconciliation logic to a pipeline of composable actions provided by `opendatahub-operator/v2/pkg/controller`. The reconciliation pipeline is: `initialize` (resolve manifest path from `ODH_MODULE_OPERATOR_MANIFESTS_PATH`) &rarr; `upgradeIfNeeded` (semver-gated migration, currently a stub) &rarr; `setKustomizedParams` (inject `OIDC_ISSUER_URL` into params.env) &rarr; `releases` (track component release metadata from `component_metadata.yaml`) &rarr; `reconcilePlatformVersion` (handshake with ODH operator via `odh-feastoperator-config` ConfigMap) &rarr; `kustomize.Render` (render manifests with component and part-of labels) &rarr; `migrateDeploymentSelector` (delete-and-recreate feast-operator Deployment if selector changed between releases) &rarr; `deploy` (apply rendered resources with caching and apply-order) &rarr; `deployments.Status` (report deployment health to CR conditions) &rarr; `gc` (garbage-collect stale resources in the applications namespace). A finalizer handles cleanup of cluster-scoped ClusterRoles and ClusterRoleBindings labeled with the component label that cannot use ownerReferences.

The operator uses namespace-scoped informer caches for most resources (Deployments, Services, ServiceAccounts, Roles, RoleBindings), scoped to the configured applications namespace, which limits its watch scope. Cluster-scoped resources (FeastOperator CR, CustomResourceDefinitions) use unscoped watches with `k8slabels.Everything()`. ConfigMaps and Secrets are excluded from the cache entirely to ensure reads are always fresh from the API server.

Platform detection drives overlay selection: RHOAI platforms (`SelfManagedRhoai` or `ManagedRhoai`) use `overlays/rhoai` (namespace `redhat-ods-applications`), while ODH uses `overlays/odh` (namespace `opendatahub`). Both overlays share identical kustomize replacement logic; they differ only in target namespace and potentially image references. Image parameterization maps `RELATED_IMAGE_FEAST_OPERATOR` and `RELATED_IMAGE_FEATURE_SERVER` environment variables from the operator's environment to the feast-operator deployment via `params.env`, enabling disconnected/air-gapped installations via operator catalog overrides.

The controller watches two external resources beyond its owned resources: `CustomResourceDefinition` objects labeled with the component label (`opendatahub.io/component.<componentName>=true`) to detect when the feast.dev CRDs are available, and a named `ConfigMap` (`odh-feastoperator-config`) for platform version coordination. Both watches route events to the singleton FeastOperator CR via `handlers.ToNamed`.
