## Purpose

**Short**: A small HTTP reverse proxy that enforces Kubernetes RBAC authorization (via SubjectAccessReview) and authentication (via TokenReview or OIDC) on requests to an upstream service, typically deployed as a sidecar container.

**Detailed**: kube-rbac-proxy sits in front of a service endpoint—most commonly a Prometheus metrics endpoint—and gates access using Kubernetes-native authentication and authorization. On each incoming request, it authenticates the caller via TokenReview against the Kubernetes API (or via OIDC JWT validation or client TLS certificates) and then authorizes the request by submitting a SubjectAccessReview. Only authorized requests are forwarded to the upstream service listening on localhost.

This component is central to the RHOAI security posture because multiple platform operators inject it as a sidecar to protect their metrics and API endpoints. The proxy terminates TLS on the external-facing port (8443 by default), forwards authenticated requests over plain HTTP to the co-located upstream container, and exposes user identity to the upstream via configurable HTTP headers. It supports two authorization configuration formats: Format1 (top-level resourceAttributes with optional query/header rewrites) and Format2 (path-scoped endpoint rules with per-method resource mappings, named path captures, and template expansion). Format2 enables AI-inference-specific audit logging with OCSF 1.9.0 API Activity events, purpose-built for KServe sidecar deployments.

A hardcoded authorizer unconditionally permits the OpenShift `system:serviceaccount:openshift-monitoring:prometheus-k8s` service account to `GET /metrics`, ensuring that Prometheus monitoring always works regardless of SubjectAccessReview configuration. This integration with OpenShift monitoring is a key platform coupling.

## Architectural Analysis

kube-rbac-proxy follows a classic transparent reverse-proxy pattern with a layered authentication/authorization middleware chain. The `Run` function constructs a middleware pipeline: request → path allow/ignore filter → authentication (TokenReview or OIDC) → authorization (hardcoded metrics authorizer → static rules → SubjectAccessReview) → upstream proxy. This pipeline is clean and deterministic—each middleware layer either rejects the request or enriches the context for the next layer.

The dual authorization format (Format1 and Format2) is a significant design decision. Format1 applies global resource attributes with optional query/header rewrites, suitable for simple metrics endpoints. Format2 introduces path-scoped rules with named captures and per-method mappings—this was added to support multi-endpoint services like TrustyAI, where different paths require different authorization policies. The `EndpointAttributesFromRequest` function checks Format2 first; if the path matches any endpoint, Format1 is entirely bypassed for that request. This is a one-way gate: a Format2 path match commits the request to Format2 rules even if the HTTP method isn't matched (returning 403 rather than falling back to Format1).

The audit subsystem (OCSF 1.9.0) is architecturally notable: it uses a bounded non-blocking queue to avoid request stalls from slow sinks, aggregates loss events into summaries, and handles graceful drain on shutdown. The `--audit-ai-provider` flag explicitly positions this proxy as an inference audit point for KServe sidecars.

TLS handling is robust. The server supports hot-reloading of certificates via a polling-based `CertReloader` (configurable interval, defaulting to 1 minute). Upstream connections enforce TLS 1.2 minimum and support mTLS to the upstream. The `--tls-min-version` flag accepts both Go constant names and short names (e.g., "TLS1.2" or "VersionTLS12"). Curve preferences are validated numerically against the running Go version rather than maintaining a hardcoded list.

The hardcoded metrics authorizer (`system:serviceaccount:openshift-monitoring:prometheus-k8s`) is a tight OpenShift coupling that should eventually move to static authorizer configuration (the code contains a TODO for this). Until then, it represents an implicit platform dependency that isn't visible in RBAC manifests.

## Security

### RBAC - Cluster Roles

| Role Name | API Group | Resources | Non-Resource URLs | Verbs |
|-----------|-----------|-----------|-------------------|-------|
| kube-rbac-proxy | authentication.k8s.io | tokenreviews | | create |
| kube-rbac-proxy | authorization.k8s.io | subjectaccessreviews | | create |

_The `kube-rbac-proxy` ClusterRole is the operationally significant one — it grants the proxy's ServiceAccount the ability to delegate authentication (TokenReview) and authorization (SubjectAccessReview) to the Kubernetes API. The `metrics` ClusterRole grants clients permission to GET /metrics through the proxy. Other roles (cluster-writer, cluster-reader, named-captures-*, verb-override-*) exist only in examples and test fixtures._
