## Purpose

**Short**: A pluggable Envoy External Processing (ext-proc) service that inspects and mutates inference request and response payloads in the llm-d data plane, enabling payload-aware routing across multiple model pools.

**Detailed**: The Inference Payload Processor (IPP) is a gRPC service that sits alongside the inference gateway's proxy (Envoy) and is invoked via the ext-proc protocol on each HTTP lifecycle event. It provides a general framework for request and response shaping through a plugin pipeline, where behavior is composed from configurable plugins organized into named profiles. Each request flows through PreProcessors, a ProfilePicker, profile-specific request plugins, and then response plugins and PostProcessors.

IPP's flagship capability is multi-pool routing: extracting signals from the request body (such as the model name or LoRA adapter identifier) and injecting routing headers so a single Gateway endpoint can serve many base models and adapters. This complements the llm-d Router (EPP), which handles endpoint-level pod selection within a pool. IPP decides *which pool* serves a request; the EPP decides *which pod* within that pool.

The component also includes a ModelSelector framework implementing a Filter-Score-Pick pipeline for model selection, a data layer for cross-request state management (supporting event-driven extractors, periodic collectors, and watch-based datasources), and OpenTelemetry tracing integration. It is deployed once per Gateway via a Helm chart that supports Istio, GKE, and standalone integration modes.

## Architectural Analysis

IPP is architecturally notable for its separation between the framework and the opinions encoded in plugins. The core runtime manages the ext-proc lifecycle, gRPC transport, profile dispatch, and data layer plumbing, while all payload processing logic lives in registered plugins. This design allows the same binary to serve radically different use cases (routing-only, model selection with cost/load scoring, response mutation) purely through YAML configuration changes via `PayloadProcessorConfig`.

The use of controller-runtime is pragmatic rather than CRD-driven: IPP is not a Kubernetes operator in the traditional sense. It uses controller-runtime as a lifecycle manager (signal handling, metrics serving, pprof, graceful shutdown) and leverages its cache/informer machinery for watching ConfigMaps that supply model-to-base-model mappings. The `PayloadProcessorConfig` type carries kubebuilder markers but is explicitly not registered as a CRD -- it is deserialized from a file or CLI flag, not reconciled from the API server.

The plugin architecture follows a registration-factory pattern. Each plugin type registers a factory function keyed by a string type identifier; the config loader instantiates plugins from the configuration and wires them into the pipeline. The ModelSelector framework uses a three-phase pipeline (Filter, Score, Pick) that mirrors the Gateway API Inference Extension's scheduler architecture, but operates at the model level rather than the endpoint level.

TLS for the ext-proc gRPC server is optional and when enabled uses self-signed certificates generated at startup. A `CertReloader` mechanism exists for hot-reloading externally provisioned TLS certificates via filesystem watching. The health gRPC server runs on a separate port without TLS. The metrics endpoint optionally supports controller-runtime's authentication and authorization filter.

A key architectural risk is the unbounded request/response body accumulation in the `FULL_DUPLEX_STREAMED` mode handler, which is acknowledged with a TODO comment but not yet capped. This could lead to OOM under adversarial or unusually large payloads.
