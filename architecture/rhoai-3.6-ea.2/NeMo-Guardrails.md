## Purpose

**Short**: NeMo Guardrails is an open-source toolkit for adding programmable guardrails to LLM-based conversational systems, providing input/output filtering, jailbreak detection, fact-checking, and topic control.

**Detailed**: NeMo Guardrails is NVIDIA's framework for controlling LLM behavior through a programmable "rails" abstraction. It sits between application code and LLM providers, intercepting and filtering both user inputs and model outputs. The toolkit supports two generations of its Colang domain-specific language (v1.0 and v2.x) for defining conversational flows and guardrail rules.

The Red Hat fork (`red-hat-data-services/NeMo-Guardrails`) extends the upstream NVIDIA codebase with several RHOAI-specific capabilities: a `/v1/guardrail/checks` endpoint for evaluating messages against rails without invoking LLM generation, HTTP header forwarding for runtime authentication passthrough to LLM providers, UBI9-based container builds with baked-in ML models via modelcar images, OpenTelemetry auto-instrumentation support, and a guardrail profile filtering system that enables open-source vs. closed-source guardrail selection at build time.

The server exposes an OpenAI-compatible API surface (`/v1/chat/completions`, `/v1/models`, `/v1/checks`) backed by FastAPI and uvicorn, operating on port 8000. It bundles pre-downloaded embedding models (MiniLM, Snowflake Arctic, spaCy, NLTK, DeBERTa, Granite Guardian HAP) to support offline inference for content classification and jailbreak detection without requiring external model downloads at runtime.

## Architectural Analysis

NeMo Guardrails follows a layered architecture where the FastAPI server (`server/api.py`) delegates to `LLMRails` instances, each bound to a named configuration (a `config.yaml` plus Colang `.co` files). Configurations are loaded lazily and cached per config-id, with optional model override. The Colang runtime evaluates guardrail rules through an event-driven pipeline that chains input rails, dialog management, and output rails.

The fork introduces a clean separation between upstream and fork-specific code. Fork additions — the `/v1/guardrail/checks` endpoint, header forwarding, and the entrypoint script — are isolated into dedicated modules (`server/checks.py`, `header_forwarding.py`, `scripts/entrypoint.sh`) to minimize merge conflicts during upstream syncs. The header forwarding mechanism uses `contextvars` to thread inbound HTTP request headers through async contexts, enabling runtime authentication passthrough to LLM providers without static API key configuration.

The Dockerfile.konflux build uses an AIPCC CPU base image and a multi-stage pattern: a build stage installs dependencies into a virtual environment and copies pre-trained models from six Red Hat modelcar images, while the runtime stage copies only the assembled `/app` directory. The runtime runs as UID 1001 in offline mode (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`), ensuring no outbound model downloads occur from within the cluster. This is architecturally significant — it means the guardrails service is self-contained for its built-in detection capabilities, though it still requires network access to upstream LLM providers for generation tasks.

The HTTP transport layer (`http/types.py`, `http/transport.py`) provides a structured `HTTPTLSConfig` abstraction supporting TLS verification, custom CA bundles, and mutual TLS client certificates. This is used by the HF classifier backend for connecting to remote classification endpoints with configurable TLS posture, though TLS verification defaults to enabled.

A notable design choice is the hashlib usage pattern: `utils.py` attempts MD5 first (faster) and falls back to SHA-256 when MD5 is unavailable (as on FIPS-enabled systems), making the cache key generation FIPS-tolerant without requiring FIPS-only operation.
