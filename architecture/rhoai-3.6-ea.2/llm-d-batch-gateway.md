## Purpose

**Short**: High-performance OpenAI-compatible batch inference API gateway for processing large-scale batch jobs in Kubernetes environments with llm-d.

**Detailed**: llm-d-batch-gateway provides a three-component system (API server, batch processor, garbage collector) that enables batch inference workloads alongside interactive inference in llm-d deployments. The API server exposes OpenAI-compatible `/v1/batches` and `/v1/files` endpoints for submitting, tracking, and managing batch inference jobs supporting up to 50,000 requests per batch. The batch processor pulls jobs from a Redis/Valkey priority queue, builds per-model execution plans with prefix-cache-optimized ordering, and dispatches inference requests to llm-d gateway endpoints using AIMD-based adaptive concurrency control that protects interactive traffic. The garbage collector runs periodic cleanup of expired jobs and files, with an optional reconciler that watches processor pod lifecycle via the Kubernetes API to recover orphaned jobs after processor crashes.

The system uses PostgreSQL for job and file metadata, Redis/Valkey for priority queuing and event channels, and S3-compatible or filesystem storage for batch input/output files. All components are deployed via a Helm chart with OpenShift compatibility, non-root execution, read-only filesystems, and optional TLS with configurable cipher suites.

## Architectural Analysis

The batch gateway follows a clean separation-of-concerns pattern with three independently scalable components sharing a common data layer. The API server is stateless and horizontally scalable as a Deployment, while the processor runs as a StatefulSet to provide stable pod identities needed for job ownership tracking and crash recovery. The garbage collector runs as a single-replica Deployment to avoid concurrent deletion races.

A notable design decision is the dual-mux HTTP server pattern in the API server: business endpoints (batches, files) are served on the main port (8000) with a full middleware chain (recovery, request tracking, OTel tracing, security headers), while observability endpoints (health, readiness, metrics, pprof) are served on a separate port (8081) with no middleware — ensuring health checks never fail due to application middleware issues and are always served over plain HTTP even when TLS is enabled on the API port.

The processor supports three dispatch modes: sync-global (single inference gateway for all models), sync-per-model (model-specific gateway routing), and async (Redis-backed queues via llm-d-async). The AIMD concurrency control is a significant reliability feature — it backs off aggressively on 429/5xx responses (multiplicative decrease by 0.5) and recovers slowly (additive increase of 1 per successful window), protecting downstream inference services from batch traffic overload.

The tenant isolation model relies on an HTTP header (`X-MaaS-Username`) for tenant identification, with database queries filtered by tenant ID. There is no built-in authentication or authorization on API routes — the architecture assumes external enforcement (e.g., Envoy ext_authz, gateway-level auth) is in place. The `LastHeaderValue` helper explicitly takes the last header value to work with Envoy ext_authz's pattern of appending auth-injected values after client-supplied ones.

From a FIPS compliance perspective, the upstream Dockerfiles use `CGO_ENABLED=0` (static linking) with `gcr.io/distroless/static:nonroot` base images that lack OpenSSL. This configuration would not pass Konflux check-payload validation. The downstream RHOAI build likely uses different Dockerfiles with UBI base images, CGO_ENABLED=1, and GOEXPERIMENT=strictfipsruntime, but those were not present in this checkout. No Konflux Dockerfiles were found.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | None built-in; tenant ID from HTTP header trusted without validation | External (gateway/proxy expected) | No built-in auth means a misconfigured gateway could allow tenant spoofing via header injection |
| Data storage | Shared PostgreSQL with tenant column filtering | Application (database query layer) | All tenants share the same database; no schema-per-tenant or row-level security policies |
| Network traffic | No tenant-level network isolation | N/A | All tenant traffic flows through the same API server instance |
| Compute & resources | No per-tenant resource limits | N/A | A single tenant's large batch could consume all processor workers |
| Configuration & secrets | Shared secrets across all tenants | Kubernetes (single secret mount) | All tenants use the same inference API key and database credentials |
| API scoping | Tenant-filtered database queries | Application | Batches and files are filtered by tenant ID in all list/get/delete queries |
