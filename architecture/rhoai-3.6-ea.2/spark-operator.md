## Purpose

**Short**: Kubernetes operator for managing Apache Spark application lifecycles, scheduled Spark jobs, and Spark Connect sessions on OpenShift.

**Detailed**: The Spark Operator manages the complete lifecycle of Apache Spark applications on Kubernetes through three Custom Resource Definitions: SparkApplication for one-shot Spark jobs, ScheduledSparkApplication for cron-scheduled recurring jobs, and SparkConnect (v1alpha1) for persistent Spark Connect gRPC sessions. The operator automates pod creation for Spark driver and executor processes, manages Spark UI services, handles monitoring configuration, and enforces resource quotas through admission webhooks.

The repository ships two independently deployable controllers. The workload operator (built from `Dockerfile.konflux`) runs as both the controller and webhook server, using the same binary in two separate Deployment configurations. The module controller (built from `Dockerfile.konflux.module-controller`) is an ODH platform module that manages the lifecycle of the workload operator itself — it watches a cluster-scoped `SparkOperator` CR and reconciles the complete deployment stack (CRDs, RBAC, Deployments, webhooks, network policies) using templated manifests bundled into its container image. This two-tier architecture allows the RHOAI operator to install, upgrade, and configure the Spark workload operator through a single declarative API.

## Architectural Analysis

The spark-operator follows the ODH modular component pattern with a clear separation between the platform management layer (module controller) and the workload layer (spark controller + webhook). The module controller imports `odh-platform-utilities` for platform detection and manifest rendering, implementing the `common.PlatformObject` interface so the ODH operator can manage it through a uniform lifecycle API.

The webhook architecture is noteworthy: a dedicated webhook Deployment runs the same binary as the controller but in webhook mode, with its own ServiceAccount and RBAC policies. The webhook server self-provisions its TLS certificates via `pkg/certificate/certificate.go`, storing them in the `spark-operator-webhook-certs` Secret. Seven admission webhooks (four mutating, three validating) cover all three CRD types plus a pod mutator that injects Spark-specific configuration (volumes, environment, tolerations) into driver and executor pods identified by the `sparkoperator.k8s.io/launched-by-spark-operator` label.

TLS configuration is OpenShift-aware: the operator reads the cluster's TLS security profile from `config.openshift.io/v1/APIServer` and applies it to webhook and metrics servers, falling back to a hardened Intermediate profile (TLS 1.2+ with ECDHE-only cipher suites) on non-OpenShift clusters or when the API is unavailable. A dedicated `spark-operator-tls-profile` ClusterRole grants both controller and webhook ServiceAccounts read access to the APIServer resource.

The RHOAI overlay deploys into `redhat-ods-applications` namespace, adds NetworkPolicies for Spark pod internal communication (driver-rpc 7078, blockmanager 7079, Spark UI 4040, SparkConnect gRPC 15002), and configures Prometheus PodMonitor with `opendatahub.io/monitoring` labels. Image injection uses a ConfigMap-based parameterization pattern where `params.env` values are substituted into Deployment specs via Kustomize replacements.

The runtime image is built on AIPCC `cpu-el9.8` base and bundles Java 17, PySpark 4.0.4, and catatonit (from podman) as init process. The entrypoint script handles OpenShift's arbitrary UID assignment via NSS wrapper before exec-ing the operator binary through catatonit for signal forwarding.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC via aggregated viewer/editor ClusterRoles | Kubernetes | Editor/viewer roles use label-based aggregation (`aggregate-to-admin/edit/view`); namespace-level RBAC must be configured per tenant |
| Data storage | Per-namespace PVCs created by Spark driver pods | Kubernetes | No cross-namespace data access enforcement beyond Kubernetes RBAC |
