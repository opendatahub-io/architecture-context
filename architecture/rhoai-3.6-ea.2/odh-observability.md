## Purpose

**Short**: A Kubernetes operator that declaratively provisions and manages a full observability stack (metrics, traces, logs, dashboards, and alerting) for the RHOAI platform via a single cluster-scoped Monitoring custom resource.

**Detailed**: The odh-observability operator watches a singleton `Monitoring` CR (`services.platform.opendatahub.io/v1alpha1`) and dynamically detects which prerequisite operators are installed on the cluster — Cluster Observability Operator, Tempo Operator, OpenTelemetry Operator, Perses Operator, Loki Operator, and cert-manager — deploying only the subsystems whose CRDs are present. This design allows the observability stack to degrade gracefully when optional operators are absent.

The operator manages six subsystems: MonitoringStack + ThanosQuerier for Prometheus metrics collection, TempoMonolithic/TempoStack for distributed tracing, OpenTelemetry Collector for the telemetry pipeline, Perses for dashboarding, LokiStack + ClusterLogForwarder for log collection, and PrometheusRules for alerting. All resources are rendered from embedded Go templates at reconciliation time and applied via Server-Side Apply (SSA) through the odh-platform-utilities deploy library. Because the Monitoring CR is cluster-scoped but manages namespace-scoped resources, the operator uses label-based ownership (`platform.opendatahub.io/part-of=monitoring`) with API-discovery-based garbage collection instead of standard OwnerReferences. A mutating admission webhook optionally injects monitoring labels on ServiceMonitor and PodMonitor resources in opted-in namespaces. The operator also deploys a Korrel8r correlation engine for cross-signal log-metrics-traces correlation.

## Architectural Analysis

The operator follows a template-driven reconciliation pattern that is architecturally distinctive. Rather than directly constructing Kubernetes objects in Go code, all managed resources are defined as Go template files (`*.tmpl.yaml`) embedded via `//go:embed`. The reconcile loop collects template sources from per-subsystem "action functions" (e.g., `deployMonitoringStackWithQuerierAndRestrictions`, `deployTracingStack`), renders them against cluster-derived template data, and applies the full desired set via SSA. A garbage collector then deletes any labeled resources not in the desired set — this is the operator's drift correction mechanism.

The TLS posture is notably thorough for a monitoring component. The operator reads the cluster-wide OpenShift APIServer TLS profile at reconcile time and propagates the cluster's minimum TLS version and cipher suites into kube-rbac-proxy and prom-label-proxy arguments in its templates. This ensures all proxy sidecars respect the cluster administrator's TLS policy. The Prometheus metrics scraping path uses a re-export pattern: because the Go OpenTelemetry SDK's Prometheus pull exporter doesn't support TLS natively, the collector re-exports its internal telemetry through a TLS-enabled pipeline exporter on port 8890, letting Prometheus scrape over HTTPS.

Network isolation is enforced through multiple NetworkPolicy resources — one per subsystem — with the collector ingress policy acting as the sole ingress gate for collector pods. OTLP ingestion (ports 4317/4318) is intentionally restricted to the monitoring namespace via NetworkPolicy rules.

The CRD design enforces a singleton pattern via CEL validation (`self.metadata.name == 'default-monitoring'`) and uses cross-field CEL rules for configuration consistency (e.g., alerting requires metrics storage, collector replicas require at least one data pipeline). The `Removed` management state triggers full cleanup via the label-based garbage collector.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy with SubjectAccessReview on both Prometheus proxies and Korrel8r | kube-rbac-proxy + Kubernetes RBAC | Namespace-proxy uses aggregated ClusterRole (data-science-metrics-view) auto-granted to admin/edit/view roles |
| Data storage | Shared Prometheus/Thanos instance; prom-label-proxy injects namespace label on queries | Application (prom-label-proxy) | Cluster-proxy provides unscoped access to users with cluster-monitoring-view role |
| Network traffic | Per-subsystem NetworkPolicies (collector, Prometheus, namespace-proxy, Korrel8r, Perses) | Kubernetes NetworkPolicy | OTLP ingestion restricted to monitoring namespace; no cross-namespace NetworkPolicy for tenants |
| Compute & resources | Resource limits set on controller-created Deployments via template defaults | Application (template defaults) | No per-tenant ResourceQuota; all monitoring resources share one namespace |
| Configuration & secrets | Per-subsystem Secrets and ConfigMaps in monitoring namespace | Kubernetes namespace scoping | All secrets in a single monitoring namespace; no per-tenant secret isolation |
| API scoping | Namespace proxy uses prom-label-proxy `--label=namespace --enable-label-apis` to force-inject namespace label | Application (prom-label-proxy) | Application-enforced; a prom-label-proxy bypass would expose cross-tenant metrics |
