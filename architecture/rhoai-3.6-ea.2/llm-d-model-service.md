## Purpose

**Short**: Kubernetes operator that declaratively provisions and maintains the resources needed to serve a base model for inference via the ModelService CRD.

**Detailed**: llm-d-model-service is a Kubernetes controller built with kubebuilder (go.kubebuilder.io/v4) and controller-runtime v0.20.4 that watches ModelService custom resources and reconciles the full inference serving stack for each base model. When a user creates a ModelService CR, the controller provisions prefill and decode Deployments for disaggregated inference, an Endpoint Picker (EPP) Deployment and Service, Gateway API InferencePool and InferenceModel resources for request routing, HTTPRoutes for Gateway integration, ServiceAccounts, RoleBindings, and ConfigMaps — all set with owner references to the ModelService for garbage collection.

The controller supports a BaseConfig pattern where platform operators define reusable presets as ConfigMaps that are merged with ModelService-specific overrides using the mergo library and Go text/template variable interpolation. Model artifacts can be loaded from HuggingFace (`hf://`), Kubernetes PVCs (`pvc://`), or OCI images (`oci://`). The controller supports decoupled scaling for HPA integration, GPU affinity via accelerator type labels, and tensor parallelism configuration for vLLM. **This project is deprecated** — the functionality has been replaced by a Helm chart in [llm-d-incubation/llm-d-modelservice](https://github.com/llm-d-incubation/llm-d-modelservice) as of June 2025.

## Architectural Analysis

The ModelService controller follows a single-controller, multi-resource-owner pattern. A single `ModelServiceReconciler` watches the primary ModelService CRD and 8 additional resource types (Deployment, Service, ConfigMap, ServiceAccount, RoleBinding, HTTPRoute, InferenceModel, InferencePool) via owner-reference-based map functions. On each reconcile, the controller reads an optional BaseConfig ConfigMap, interpolates template variables (model name, namespace, derived resource names), deep-merges the BaseConfig with ModelService spec overrides, then creates or updates all child resources using controller-runtime's CreateOrUpdate pattern. Status is populated by reading back the Deployment conditions from the cluster and mirroring them with prefixed condition types (PrefillAvailable, DecodeProgressing, etc.).

A notable design choice is the Cobra CLI structure with two subcommands: `run` starts the controller manager, while `generate` performs offline manifest generation from ModelService + BaseConfig YAML files without a running cluster. This dual-mode approach allows platform teams to preview the full resource graph before applying it.

The development Dockerfile sets `CMD ["sleep", "infinity"]` — the actual binary entry point (`/manager run`) is injected via the kustomize deployment patch. The Dockerfile uses `CGO_ENABLED=0` for static linking, which is incompatible with FIPS check-payload validation. No Konflux Dockerfile exists on this branch, indicating this component has not yet been onboarded to the Konflux build pipeline.

The controller manages RBAC dynamically: it creates per-ModelService ServiceAccounts for prefill/decode pods and EPP pods, and binds the EPP ServiceAccount to a configurable ClusterRole via the `--epp-cluster-role` flag. This delegation pattern allows the EPP ClusterRole to be defined externally (e.g., by the Gateway API Inference Extension) while the ModelService controller handles the per-namespace binding.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace ServiceAccounts created for PD and EPP pods; RBAC admin/editor/viewer ClusterRoles for ModelService resources | Kubernetes | Controller itself runs with broad ClusterRole; no namespace restriction on which namespaces it watches |
| Data storage | Per-namespace PVCs or HuggingFace downloads per ModelService; no shared data store | Kubernetes | Model cache not shared between ModelService instances |
| Network traffic | Optional NetworkPolicy for metrics access (config/network-policy/); no per-ModelService NetworkPolicy | Kubernetes | No automatic NetworkPolicy isolation between ModelService workloads in different namespaces |
| Compute & resources | Per-deployment resource limits configurable via ModelService spec; GPU affinity via accelerator type labels | Kubernetes | No automatic ResourceQuota enforcement per tenant |
| Configuration & secrets | Per-namespace ConfigMaps and Secrets; BaseConfig references scoped to ModelService namespace | Kubernetes | BaseConfig ConfigMap can reference cross-namespace if ObjectReference.Namespace is set |
| API scoping | Controller watches all namespaces; owner-reference-based filtering maps events to correct ModelService | controller-runtime | Cluster-wide list-watch means controller caches all Deployments/Services across all namespaces |
