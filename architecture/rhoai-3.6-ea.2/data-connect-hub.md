## Purpose

**Short**: Data Connect Hub is a middleware service providing a unified integration point for ingesting data from heterogeneous data sources (PostgreSQL, S3, Elasticsearch, Milvus, Neo4j, SQLite, URI) via REST and Apache Arrow Flight gRPC APIs.

**Detailed**: Data Connect Hub (DCH) centralises data connection metadata management and provides two purpose-built data access APIs: a REST API (actix-web) for connection CRUD, credential testing, and binary data download, and an Apache Arrow Flight gRPC service (tonic) for high-throughput columnar data transfer. Rather than consuming services each maintaining their own client library stacks for multiple data backends, DCH abstracts the connection lifecycle into a uniform set of APIs backed by pluggable connector libraries.

The system comprises three deployable components: a Go-based Kubernetes controller (`dc-controller`) that reconciles `DataConnectService` CRDs and manages the lifecycle of the rest-service and flight-service Deployments, networking (HTTPRoutes, NetworkPolicies), and RBAC; the Rust REST service that handles connection metadata via a PostgreSQL meta-store and proxies audit/readiness checks to the flight service; and the Rust flight service that performs actual data ingestion against backend data sources using a feature-gated connector registry.

DCH is designed for multi-tenant operation on OpenShift AI. Tenancy is scoped by namespace, with kube-rbac-proxy enforcing per-request SubjectAccessReview authorization on the REST API using the `X-Tenant-Id` header (mapped to Kubernetes namespace), and the flight service performing its own bearer token authentication and authorization via TokenReview/SubjectAccessReview against the `X-Tenant-Id` namespace. The controller deploys the data plane services into namespaces managed by `DataConnectService` CRs and exposes them through the platform's Gateway API infrastructure.

## Architectural Analysis

Data Connect Hub follows a clean separation between control plane (Go controller) and data plane (Rust services). The controller is a standard kubebuilder operator using controller-runtime v0.25.1 that watches a singleton `DataConnectService` CR and reconciles the complete application stack — Deployments, Services, ConfigMaps, ServiceAccounts, ClusterRoles, ClusterRoleBindings, NetworkPolicies, and HTTPRoutes — by rendering kustomize manifests embedded in the controller image. This gives the operator full declarative control over the deployed topology and allows image references to be injected via `RELATED_IMAGE_*` environment variables for disconnected/air-gapped installations.

The Rust data plane uses a workspace monorepo pattern with clear layering: shared types and traits in `libs/commons`, each data source connector as a separate library crate under `connectors/`, and two binary crates under `services/`. The connector architecture follows a trait-based plugin model (`SQLReader<RecordBatch>`) that converts source-specific types into Apache Arrow `RecordBatch` streams. Feature flags in the flight-service Cargo.toml control which connectors are compiled in, allowing build-time customisation of the connector set.

TLS handling is notable for its dual-language approach. The Go controller reads the cluster-wide OpenShift `APIServer` TLS profile and configures controller-runtime's TLS accordingly, with a `ProfileWatcher` controller that triggers graceful shutdown on profile changes. The Rust services use `rustls` with the `aws_lc_rs` cryptographic provider (explicitly installed at startup) and receive TLS certificates via OpenShift service-ca annotations. The REST service binds on plaintext HTTP (port 8080) behind kube-rbac-proxy (port 8443), while the flight service terminates TLS directly (port 8443).

The kube-rbac-proxy configuration for the REST service is architecturally significant: it maps every API endpoint to a SubjectAccessReview against virtual `dataconnecthub.opendatahub.io` resources (data-connections, data-connection-types, data-store), scoped to the namespace carried in the `X-Tenant-Id` header. This transforms standard Kubernetes RBAC into per-tenant API authorization without requiring the REST service itself to perform auth checks.

NetworkPolicies are deployed for both services but currently allow all ingress/egress — the manifests include a comment noting they exist as placeholders to be tightened once the gateway/client topology is defined. This is an acknowledged security gap.

The Rust services use `ubi9/ubi-minimal-pqc` (post-quantum cryptography) as the runtime base image in Konflux builds, suggesting forward-looking cryptographic posture. The Go controller uses standard `ubi9/ubi-minimal`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy SubjectAccessReview per namespace (REST); Tower AuthLayer with TokenReview + SAR per namespace (Flight) | kube-rbac-proxy sidecar / Application (KubeAuthClient) | Authorization is scoped to namespace via X-Tenant-Id header; if header is spoofed before kube-rbac-proxy, isolation breaks — mitigated by kube-rbac-proxy terminating external TLS and validating the SAR |
| Data storage | Shared PostgreSQL database with tenant_id column filtering | Application (pg-meta-store) | All tenants share one database instance; row-level tenant filtering in application code. No database-level isolation. |
| Network traffic | NetworkPolicy resources deployed per service (currently allow-all placeholders) | Kubernetes NetworkPolicy | NetworkPolicies are allow-all; no inter-tenant network isolation enforced yet. Explicitly noted as placeholder in manifests. |
| Compute & resources | Shared rest-service and flight-service Deployments with resource limits per container | Kubernetes | No per-tenant resource quotas; one tenant's heavy queries could starve others of CPU/memory within the shared service |
| Configuration & secrets | Database secret shared across tenants (dch-database-config); TLS secrets per service | Kubernetes Secrets | Shared database credential means a compromised pod has access to all tenants' metadata |
| API scoping | kube-rbac-proxy maps X-Tenant-Id to namespace for SAR; flight auth middleware validates against tenant namespace | kube-rbac-proxy / Application | API operations are scoped to the tenant namespace via SAR; tenant cannot access another's data without RBAC grants in that namespace |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL metadata store | tenant_id column | Application query filter (pg-meta-store passes tenant_id to all queries) |
| Connection cache (moka) | Per-connector instance | In-memory cache keyed by connection ID; shared across tenants within a connector |
