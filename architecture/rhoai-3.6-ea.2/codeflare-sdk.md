## Purpose

**Short**: Python SDK that provides an intuitive interface for requesting, managing, and monitoring distributed compute resources (Ray clusters and RayJobs) on Kubernetes within the RHOAI platform.

**Detailed**: CodeFlare SDK is a client-side Python library — not a deployed service — that abstracts the complexity of managing distributed computing workloads on Kubernetes. Its primary role is to let data scientists and ML engineers create, configure, and submit Ray clusters and RayJobs without writing Kubernetes manifests directly.

The SDK's `Codeflare` class serves as the single entrypoint, authenticating to Kubernetes via the `kube-authkit` library and providing namespace-accessor handlers for clusters (`cf.clusters`) and jobs (`cf.jobs`). Each `Codeflare` instance owns its own Kubernetes client, enabling multiple authenticated sessions to coexist without interfering — a design enforced through `ContextVar`-based client isolation.

The SDK bridges three platform subsystems: **KubeRay** (by constructing RayCluster and RayJob custom resource manifests and applying them via the Kubernetes API), **Kueue** (by resolving local queues, validating priority classes, and attaching queue labels to workloads), and the **RHOAI networking layer** (by discovering Ray dashboard URLs via Gateway API HTTPRoutes, OpenShift Routes, or the `GatewayConfig` CR from `services.platform.opendatahub.io`). It also generates mTLS certificates locally for secure client-to-Ray-cluster communication, using the `cryptography` library with RSA-3072 keys and SHA-256 signatures.

## Architectural Analysis

CodeFlare SDK follows a layered architecture with enforced import boundaries (CI-checked via `import-linter`). The top layer is the `Codeflare` facade, which delegates to two handler classes — `ClusterHandler` and `JobHandler` — that wrap the lower-level `Cluster` and `RayJob` classes respectively. This dual-path design exists because both standalone RayCluster resources and RayJob-managed ephemeral clusters share the same `ClusterConfiguration` dataclass, ensuring a single description format across the SDK.

A notable architectural decision is the `ContextVar`-based client isolation (RHOAIENG-98754). Rather than threading a Kubernetes client through every function, the SDK uses `_active_api_client` as a context variable. The `@_bound_to_api_client` decorator activates the correct client for the duration of each method call, and helper functions that transitively reach the Kubernetes API — including cert generation, Kueue lookups, and manifest building — automatically pick up the scoped client. This avoids a wide-reaching parameter-threading refactor while preventing silent cross-talk between concurrent `Codeflare` instances.

The vendored KubeRay Python client (`src/codeflare_sdk/vendored/`) is frozen and import-guarded: only the `ray.rayjobs` layer may import it directly. This contains the blast radius of upstream KubeRay API changes. The two builder paths — `build_ray_cluster.py` for standalone clusters and `ray/rayjobs/config.py` for job-embedded clusters — must be kept in parity when `ClusterConfiguration` fields change, as divergence causes silent field drops.

Dashboard URL discovery illustrates the SDK's platform-awareness: it first attempts HTTPRoute lookup (Gateway API, RHOAI v3.0+), falls back to OpenShift Routes, and finally tries the `GatewayConfig` cluster-scoped CR from `services.platform.opendatahub.io/v1alpha1` to resolve the gateway hostname. This multi-strategy approach allows the same SDK to function across RHOAI, ODH, and plain Kubernetes (KinD) environments.

The autoscaling-with-Kueue validation logic (`validate_autoscaling_with_kueue`) checks whether the cluster runs RHOAI-managed Kueue (blocked) or standalone RHBOK ≥ 1.4 (allowed), reflecting a real platform constraint where elastic Ray workloads under RHOAI-managed Kueue have not yet been validated.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user Kubernetes credentials via kube-authkit; each Codeflare instance owns its client | Kubernetes RBAC | SDK trusts Kubernetes RBAC for authorization; no application-level access control |
| Data storage | Per-namespace Kubernetes secrets for TLS certs; local cert files in user-private directory (0700/0600 perms) | Kubernetes / Filesystem | Local TLS certs stored in `~/.local/share/codeflare/tls/` are user-private but not encrypted at rest |
| Network traffic | Inherited from cluster NetworkPolicy; SDK connects through existing Routes/HTTPRoutes | Kubernetes / RHOAI platform | SDK does not create NetworkPolicy; relies on platform networking |
| Compute & resources | Per-namespace Kueue LocalQueues, ResourceFlavors, WorkloadPriorityClasses | Kueue | Quota enforcement delegated entirely to Kueue |
| Configuration & secrets | Per-namespace secret access; credentials scoped to authenticated user | Kubernetes | No cross-namespace operations by design |
| API scoping | All Kubernetes API calls are namespace-scoped (except cluster-level CRD discovery) | Kubernetes API server | Cluster-scoped reads (DataScienceCluster, GatewayConfig, OperatorCondition) are read-only discovery |
