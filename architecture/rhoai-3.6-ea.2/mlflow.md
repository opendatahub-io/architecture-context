## Purpose

**Short**: MLflow is an experiment tracking and model registry service providing multi-tenant ML lifecycle management on OpenShift with Kubernetes-native authentication and workspace isolation.

**Detailed**: MLflow serves as the experiment tracking, model registry, and artifact management backbone within RHOAI. The downstream fork of `mlflow/mlflow` (v3.15.2) carries significant customizations for Kubernetes-native deployment: authentication via Kubernetes bearer tokens (the `kubernetes-auth` app plugin, provided by `mlflow-kubernetes-plugins`), multi-tenant workspace isolation mapped to Kubernetes namespaces, and a module-federated React UI adapted for embedding within the RHOAI dashboard (PatternFly overrides, feature-flag gated AI Gateway and Assistant features).

The server exposes a rich HTTP API surface spanning experiment tracking (runs, metrics, parameters, artifacts), model registry (registered models, model versions, aliases, tags), an AI Gateway for proxying LLM provider requests, an MCP (Model Context Protocol) server and registry, an assistant/chat interface, job execution, and distributed tracing. In RHOAI, the AI Gateway and Assistant features are disabled by default via environment variables (`MLFLOW_ENABLE_AI_GATEWAY=false`, `MLFLOW_ENABLE_ASSISTANT=false`). Artifacts can be stored locally (server-proxied) or in remote object stores (S3, GCS, Azure Blob Storage). The backend metadata store supports SQLite (for single-node) or PostgreSQL (for production).

## Architectural Analysis

MLflow's downstream architecture centers on three key design decisions that differentiate it from upstream.

**Kubernetes-native identity and tenancy.** Rather than adopting MLflow's built-in `basic-auth` plugin (username/password over HTTP Basic), the RHOAI deployment uses `--app-name kubernetes-auth`, which loads the `mlflow-kubernetes-plugins` package as a server-side auth middleware. On the client side, `KubernetesRequestAuthProvider` reads Kubernetes ServiceAccount tokens (from `/var/run/secrets/kubernetes.io/serviceaccount/token` or kubeconfig) and injects `Authorization: Bearer <token>` headers. Workspace isolation maps each Kubernetes namespace to an MLflow workspace via the `X-MLFLOW-WORKSPACE` header, with the server storing workspace metadata in a Kubernetes-backed workspace store (`--workspace-store-uri kubernetes://`). This design avoids maintaining a separate user database and delegates identity to the cluster's existing RBAC infrastructure.

**Feature-flag gating of upstream capabilities.** Several upstream features — the AI Gateway (LLM provider proxy), the Assistant (AI chat interface), and job execution — are disabled by default in the RHOAI container via environment variables. The UI code also gates Playground and Gateway routes behind `shouldEnableAIGateway()`. This pattern allows the RHOAI team to control feature exposure without maintaining a separate codebase, and features can be enabled per-deployment when appropriate.

**Multi-stage hermetic build.** The Dockerfile.konflux uses three stages: a Node.js stage building the React UI with Yarn Berry (including a federated build for dashboard embedding), a Python stage building wheel artifacts from pinned AIPCC-sourced dependencies, and a UBI9-minimal-pqc runtime stage. All dependency installation uses `--require-hashes --no-deps` for supply chain integrity, and Hermeto (cachi2) prefetch is supported. The base image is UBI9-minimal-pqc (post-quantum-cryptography variant) rather than an AIPCC Ecosystems base image.

**Fork maintenance model.** The codebase follows a disciplined rebase-and-squash model against upstream tags (documented in `FORK_HISTORY.md`), with downstream changes organized into scaffolding, backend, and UI categories. The `mlflow-kubernetes-plugins` package is version-pinned and bumped with each rebase to maintain auth compatibility.
