## Purpose

**Short**: The primary platform operator for Red Hat OpenShift AI (RHOAI) that orchestrates the deployment, configuration, and lifecycle management of the entire AI/ML platform stack on OpenShift.

**Detailed**: rhods-operator is the central control plane for RHOAI. It manages the platform through two primary cluster-scoped custom resources: `DataScienceCluster` (DSC) defines which AI/ML components are enabled and their configuration, while `DSCInitialization` (DSCI) handles platform-wide initialization including namespace creation, monitoring setup, and service mesh integration. The operator has been significantly rearchitected in the 3.x generation, transitioning from monolithic reconciliation to a modular DAG-based architecture with three reconciler tiers: in-tree components (e.g., Kueue), services (auth, gateway, monitoring), and modules (dashboard, kserve, workbenches, etc.) that deploy external operator manifests fetched at build time.

The operator deploys the platform's entire ingress infrastructure, including Gateway API resources, Envoy proxy data plane, EnvoyFilter CRs for traffic shaping, kube-auth-proxy OIDC deployments for per-component authentication, and OpenShift Routes for legacy URL redirects. It also manages cross-cutting concerns like RBAC for admin/user groups, hardware profiles, TLS certificate rotation tracking, and Prometheus monitoring rules. A separate `cloudmanager` binary handles cloud-specific Kubernetes engine provisioning for AWS (EKS), Azure (AKS), and CoreWeave environments, enabling the RHAII (Red Hat AI Infrastructure) multi-cloud deployment model.

## Architectural Analysis

The rhods-operator's architecture centers on a three-tier reconciler design that separates concerns between platform services, in-tree components, and externally-fetched module operators. Each tier uses a declarative action chain pattern: controllers define an ordered sequence of actions (render templates, deploy resources, garbage-collect stale objects) that execute sequentially, stopping on first error, with GC always last. This design prevents resource leaks even during partial reconciliation failures.

The gateway service controller (`internal/controller/services/gateway/`) is architecturally the most complex subsurface. It orchestrates the complete RHOAI 3.x ingress stack: a Kubernetes Gateway API `Gateway` CR as the entry point, `HTTPRoute` CRs per component, `EnvoyFilter` CRs for authentication header injection and CORS, `DestinationRule` CRs for self-signed certificate TLS enforcement, and `kube-auth-proxy` OIDC deployments that authenticate users via OpenID Connect before proxying to backend services. The gateway controller dynamically detects Istio CRDs at startup and conditionally creates Envoy/Istio resources, making the ingress stack adaptable to clusters with or without a service mesh.

A notable architectural decision is the TLS profile watcher (`pkg/tls/profile.go`): the operator reads the cluster-wide `APIServer` TLS security profile and derives cipher suites and minimum TLS versions for both the webhook server and the kube-auth-proxy deployments. When the cluster TLS profile changes, the operator triggers a graceful self-restart to reload the new profile, ensuring the data plane stays aligned with cluster security policy without manual intervention.

The module system (`internal/controller/modules/`) deserves attention as a scaling strategy. Rather than building all component operators into the rhods-operator binary, modules are external operator repos whose kustomize manifests are fetched at build time via `manifests-config.yaml` and bundled into the container image under `/opt/manifests-template`. At runtime, the module reconciler renders these manifests with image overrides from `RELATED_IMAGE_*` environment variables (set in the OLM ClusterServiceVersion) and deploys them. This keeps the operator binary lean while centralizing lifecycle management — a pragmatic tradeoff that avoids the operational complexity of running 16+ separate OLM subscriptions.

The cloudmanager subsystem (`cmd/cloudmanager/`) introduces a separate binary and Cobra CLI for managing cloud-specific Kubernetes engines. Its controllers watch for `AWSKubernetesEngine`, `AzureKubernetesEngine`, and `CoreWeaveKubernetesEngine` CRDs and provision infrastructure accordingly, extending the operator's reach beyond OpenShift into the RHAII multi-cloud scenario.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-group RBAC via data-science-admingroup and data-science-allowedgroup ClusterRoles and namespace-scoped Roles | Kubernetes RBAC (operator creates bindings) | Group membership managed externally via OpenShift identity providers |
| Data storage | Per-namespace PVCs and Secrets (delegated to component operators) | Kubernetes namespace isolation | Operator itself does not manage user data storage directly |
| Network traffic | NetworkPolicy per component namespace (created by component controllers) | Kubernetes NetworkPolicy | Operator creates NetworkPolicies via kueue controller; other components manage their own |
| Compute & resources | HardwareProfile CRs define per-namespace resource constraints | Application (via HardwareProfile CRD) | No built-in ResourceQuota enforcement by the operator itself |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps for component configuration | Kubernetes namespace isolation | Shared ConfigMaps (e.g., tier-to-group-mapping) cross namespace boundaries by design |
| API scoping | Namespace-scoped watches for user resources; cluster-wide watches for platform CRs | Kubernetes informer cache with namespace filtering | Operator watches all namespaces for some resources (Deployments, Secrets) to detect managed components |
