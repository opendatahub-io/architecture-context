## Purpose

**Short**: A reverse proxy sidecar that orchestrates disaggregated prefill/decode (P/D) for LLM inference by routing requests between remote prefiller pods and the local vLLM decoder.

**Detailed**: llm-d-routing-sidecar sits alongside a vLLM decoder as a sidecar container, intercepting OpenAI-compatible completion requests and implementing the disaggregated prefill/decode pattern. When a request arrives with an `x-prefiller-host-port` header, the sidecar first forwards the prompt to the specified remote prefiller pod for KV-cache population, then passes the decode request (enriched with KV transfer parameters) to the co-located vLLM decoder. This two-phase approach allows separating compute-intensive prefill from latency-sensitive decode across different GPU workers.

The sidecar supports multiple connector protocols: NIXL V2 (current default), NIXL V1 (deprecated), and LMCache (deprecated). It includes optional SSRF protection that maintains a dynamic allowlist of valid prefill targets by watching Kubernetes InferencePool resources and their matching pod IPs. Requests without the prefiller header are transparently proxied to the local decoder.

**Note**: This repository is deprecated. The code has been migrated to the [llm-d-inference-scheduler](https://github.com/llm-d/llm-d-inference-scheduler) repository under `cmd/pd_sidecar` and `pkg/sidecar`. No new development is expected here.

## Architectural Analysis

The routing sidecar implements a purpose-built HTTP reverse proxy with a clear two-phase request lifecycle. For disaggregated inference requests, the sidecar clones the incoming request, modifies the JSON body to constrain the prefiller (setting `max_tokens=1` and disabling streaming), forwards to the remote prefiller, extracts KV transfer parameters from the response, then constructs a second request to the local decoder with those parameters injected. This serialized prefill-then-decode flow is synchronous within a single HTTP request context, meaning the client sees a single response after both phases complete.

The SSRF protection layer is architecturally notable: rather than a static configuration, it uses Kubernetes informer watches on InferencePool custom resources (from the `inference.networking.x-k8s.io/v1alpha2` API group) to dynamically discover which pod IPs belong to valid prefiller targets. The allowlist tracks host IPs only (not ports), rebuilt on every pod add/update/delete event. When disabled (the default), all prefiller targets are permitted for backward compatibility.

TLS is configured at three levels with distinct trust models: the proxy server itself serves TLS by default (with self-signed certs as fallback), while outbound connections to both prefiller and decoder have independent TLS and certificate verification controls. All three use the same hardcoded cipher suite list limited to AEAD ciphers with TLS 1.2 minimum. The `InsecureSkipVerify` options for prefiller and decoder connections are a pragmatic concession to environments where service mesh or platform-level mTLS handles authentication at a different layer.

The deployment as a StatefulSet (rather than Deployment) with `replicas: 1` reflects its sidecar nature -- it is tightly coupled to a single decoder instance and maintains an LRU cache of prefiller proxy handlers that should not be load-balanced across replicas.

The `InsecureSkipVerify` flags for prefiller and decoder TLS are disabled by default but available -- their use bypasses certificate validation._
