## Purpose

**Short**: MLServer is a Python-based inference server implementing the KServe V2 Inference Protocol over REST and gRPC, supporting multiple ML framework runtimes.

**Detailed**: MLServer provides a standardized model serving runtime compliant with the KServe V2 Dataplane specification. It exposes both REST (HTTP on port 8080 via FastAPI/uvicorn) and gRPC (port 8081 via grpcio) interfaces for inference, model management, health checking, and repository operations. A separate metrics server runs on port 8082 for Prometheus-compatible observability.

The server supports a pluggable runtime architecture where ML frameworks are loaded as separate Python packages. In the RHOAI distribution, the CPU variant ships with scikit-learn, XGBoost, LightGBM, and ONNX runtimes, while the CUDA variant ships with only the ONNX runtime configured for GPU execution via CUDAExecutionProvider. A trusted-runtimes allowlist mechanism enforces which model implementations can be loaded in production mode, preventing arbitrary code execution through model configuration. Additional runtimes (HuggingFace, MLflow, CatBoost, Alibi Detect/Explain, Spark MLlib) exist in the codebase but are not included in the Konflux container images.

MLServer is deployed as a container within KServe InferenceService pods in RHOAI, where authentication is delegated to a kube-rbac-proxy sidecar that validates OpenShift OAuth/ServiceAccount tokens.

## Architectural Analysis

MLServer's architecture centers on a dual-protocol serving pattern: every inference endpoint is exposed over both REST and gRPC simultaneously, sharing a common DataPlane handler layer. This design ensures protocol parity and means that model runtimes need only implement a single Python interface (`MLModel`) to be accessible on both transports.

The trusted-runtimes security model is a distinctive design decision for the RHOAI distribution. At container build time, the Dockerfile generates a `/etc/mlserver/trusted-runtimes.json` allowlist baked into the image, which restricts which `model_settings.implementation` values the server will accept. This controls model loading at two checkpoints: settings validation (during repository discovery) and implementation property access (defense-in-depth at import time). In development mode (no allowlist file), any runtime can be loaded and `sys.path` injection is permitted for dynamic model loading from disk. Production mode additionally blocks custom environments (`environment_tarball`, `environment_path`) and wildcard CORS origins to tighten the attack surface.

The gRPC server uses `add_insecure_port` exclusively (no TLS at the application layer), relying on the platform (KServe + kube-rbac-proxy sidecar, Istio service mesh) for transport encryption and authentication. The OpenTelemetry tracing exporter similarly uses `insecure=True` for its OTLP gRPC connection. This is an intentional pattern for in-cluster communication where the service mesh handles mTLS.

The multi-model serving capability allows multiple models to coexist in a single process, with parallel inference workers available via Python multiprocessing. Adaptive batching can group requests to amortize per-request overhead. An optional Kafka consumer/producer integration allows asynchronous inference via message queues, though this is disabled by default.
