## Purpose

**Short**: Kubeflow Hub provides a central repository for ML model metadata (models, versions, artifacts), federated catalog discovery, and Kubernetes-native model serving integration for the RHOAI platform.

**Detailed**: The Model Registry (now part of Kubeflow Hub) is the RHOAI platform's metadata backbone for ML models. It exposes a contract-first REST API defined by OpenAPI specifications, allowing model developers and automated pipelines to register, version, and query model metadata. The server persists data to PostgreSQL or MySQL via GORM with embedded schema migrations, supporting both standalone and platform-integrated deployment modes.

Beyond the core registry, the project delivers several companion components: a Kubernetes controller that watches KServe InferenceService CRDs and synchronizes model serving state back into the registry; a Backend-for-Frontend (BFF) Go service that proxies UI requests, performs Kubernetes authorization checks (SubjectAccessReview, SelfSubjectAccessReview), and manages model registry settings; a federated Catalog service supporting plugin-based discovery across external catalogs (including MCP servers); a CSI-compatible storage initializer for downloading models from the registry into serving containers; and a Python-based async upload Job that copies models between storage backends with sigstore-based model signing.

The project is the downstream Red Hat productization of the upstream Kubeflow Hub (formerly kubeflow/model-registry) project and follows a contract-first API design. All API traffic within the platform flows through Istio service mesh with AuthorizationPolicy enforcement, while the BFF supports both Kubernetes-native and bearer token authentication modes.

## Architectural Analysis

Model Registry's architecture reflects its evolution from a focused metadata store into a multi-component platform service. The core design splits along three axes: data persistence, Kubernetes integration, and user-facing API layers.

The persistence layer uses GORM as a database abstraction over PostgreSQL and MySQL, with schema migrations embedded directly in the binary (`internal/datastore/embedmd/`). This avoids external migration tooling at the cost of coupling the schema lifecycle to the binary release. The server uses `golang-migrate` for migration execution and `pglock`/`pgx` for PostgreSQL advisory locking, suggesting distributed deployment scenarios where migration races must be prevented.

The Kubernetes integration layer is conditional: the InferenceService controller only activates when `INFERENCE_SERVICE_CONTROLLER=managed`, allowing the registry to run without KServe dependencies. This controller uses a dual implementation pattern — an outer `InferenceServiceReconciler` (in `cmd/controller/`) delegates to an inner `InferenceServiceController` (in `pkg/inferenceservice-controller/`), which handles the actual label-based synchronization between InferenceService CRDs and registry entries. The controller reads model metadata from the registry's REST API using configurable labels (`NAMESPACE_LABEL`, `NAME_LABEL`, `INFERENCE_SERVICE_ID_LABEL`, etc.) and annotates InferenceServices with registry URLs.

The BFF layer acts as both an API proxy and an authorization gateway. It performs SubjectAccessReview and SelfSubjectAccessReview checks against the Kubernetes API using the end user's token, enforcing namespace-scoped access to model registry instances. This is a critical security boundary: the BFF creates Kubernetes resources (ConfigMaps, Secrets, Jobs) on behalf of users, making its authorization checks the primary defense against cross-tenant access.

A notable design tension exists between the Istio-based security model (AuthorizationPolicy requiring namespace-scoped principals and JWT authorization headers) and the BFF's own token-based authentication (configurable between `internal` and `user_token` modes). In Kubeflow deployments, both mechanisms are active, creating a defense-in-depth posture but also requiring careful coordination to avoid configuration drift.

The async upload Job introduces a Python runtime dependency alongside the Go components. It uses `sigstore`, `rh-model-signing`, and `cosign` for supply chain security, signing uploaded models during transfer. This job runs as a Kubernetes batch Job created by the BFF's SharedClientLogic, establishing a control flow from UI → BFF → Job → model registry → storage backend.

| Auth & AuthZ | Per-user SubjectAccessReview and SelfSubjectAccessReview via BFF; Istio AuthorizationPolicy | Kubernetes (RBAC) + Istio | BFF performs authorization checks using user tokens — a misconfigured auth-method could weaken isolation |
| Data storage | Per-instance database (each model registry namespace gets its own deployment with dedicated DB credentials) | Kubernetes (separate Deployments) | Database isolation depends on operational deployment; nothing prevents sharing a database if configured that way |
| Network traffic | Istio AuthorizationPolicy restricts access by namespace and service principal | Istio | VirtualServices use wildcard host (*), relying on AuthorizationPolicy for actual access control |
| Compute & resources | No ResourceQuota or LimitRange defined in manifests | N/A | Tenant resource isolation delegated to platform operator (model-registry-operator) |
| Configuration & secrets | Per-namespace Secrets for database credentials | Kubernetes | Shared ConfigMap (pipeline-install-config) within namespace |
| API scoping | BFF uses SelfSubjectRulesReview to determine namespace-level access; controller uses REGISTRIES_NAMESPACE env | Kubernetes + Application | Controller reads from a single REGISTRIES_NAMESPACE, limiting cross-namespace awareness |
