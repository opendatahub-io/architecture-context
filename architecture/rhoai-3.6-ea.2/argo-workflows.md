## Purpose

**Short**: Container-native workflow engine for orchestrating parallel jobs on Kubernetes, used as the execution backend for Data Science Pipelines in RHOAI.

**Detailed**: Argo Workflows is a CNCF-graduated, open-source workflow engine that defines and executes workflows as Kubernetes Custom Resources. Each workflow step runs as a container, enabling DAG-based and sequential orchestration of compute-intensive jobs for machine learning, data processing, and CI/CD pipelines.

Within RHOAI, argo-workflows provides the core execution engine for Data Science Pipelines (DSP). The DSP operator deploys two components from this repository: the **workflow-controller** (which reconciles Workflow CRDs and manages pod lifecycle) and the **argoexec** executor (which runs as a sidecar inside workflow pods to manage artifact I/O and container lifecycle). The upstream argo-server API/UI component exists in this repo but is not deployed in the RHOAI DSP context — pipeline API access is handled by the DSP server instead.

This is a fork of argoproj/argo-workflows maintained through opendatahub-io for ODH and red-hat-data-services for RHOAI, with downstream customizations including Konflux-compatible Dockerfiles, GOFIPS140 FIPS compliance, UBI-based container images, and RHOAI-specific build variants.

## Architectural Analysis

Argo Workflows follows a controller pattern where a single workflow-controller deployment watches Workflow CRDs across configured namespaces and drives pod creation, status tracking, cron scheduling, and artifact garbage collection. The controller uses informer-based watches against the Kubernetes API with a work-queue reconciliation loop, leader election via coordination/v1 Leases, and optional workflow archiving to SQL databases (PostgreSQL or MySQL). The argoexec binary runs inside each workflow pod as a sidecar, managing artifact upload/download (supporting S3, GCS, Azure Blob, HDFS, Alibaba OSS, and Minio backends), container output capture, and resource cleanup.

The argo-server component multiplexes gRPC and HTTP/1.1 on a single port (2746) using a grpc-gateway proxy pattern, serving 9 gRPC services with a matching REST API facade. Authentication is layered through a gatekeeper interceptor supporting three modes — client-token passthrough, server-side ServiceAccount token validation, and SSO via OIDC with encrypted JWT cookies. Rate limiting is applied at both the gRPC and HTTP layers. TLS is configurable with a minimum version parameter, and the server can generate self-signed ECDSA P-256 certificates for development use.

A notable FIPS architecture decision in this fork uses Go 1.24+'s native FIPS 140 module (`GOFIPS140=v1.0.0`) with the `-tags no_openssl` build tag instead of the legacy `GOEXPERIMENT=boringcrypto` approach. Combined with `CGO_ENABLED=0` and static linking, this produces binaries that use Go's stdlib FIPS 140 crypto module without requiring system OpenSSL. The runtime images use `ubi9/ubi-minimal-pqc` — the post-quantum cryptography variant — signaling forward-looking cryptographic resilience.

_Note: This fork uses Go 1.24+'s native FIPS 140 module (`GOFIPS140=v1.0.0`) rather than the legacy `GOEXPERIMENT=boringcrypto`. The `-tags no_openssl` flag disables any OpenSSL bindings, relying entirely on Go's stdlib FIPS 140 crypto implementation. With `CGO_ENABLED=0`, binaries are fully statically linked. This approach differs from the typical RHOAI pattern of dynamically linked binaries using system OpenSSL, and may affect check-payload validation which traditionally expects dynamic linking and OpenSSL presence._
