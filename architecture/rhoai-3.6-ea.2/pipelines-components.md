## Purpose

**Short**: A collection of reusable Kubeflow Pipelines components and pre-compiled managed pipelines for AI/ML workflows on RHOAI, packaged as a Python library and init container image.

**Detailed**: pipelines-components is the centralized repository of reusable KFP (Kubeflow Pipelines) components and complete pipeline definitions for RHOAI. Components span four categories — data processing, training, evaluation, and deployment — and are organized as a single Python package (`kfp-components` v1.11.0) that pipeline authors import. The repository covers LLM fine-tuning (SFT, LoRA, OSFT, LoRA-GRPO), automated ML (AutoGluon tabular and timeseries), AutoRAG (document discovery, text extraction, indexing, RAG template optimization), synthetic data generation (SDG Hub), model evaluation (lm-eval harness, Eval Hub with KServe), and model deployment/registration (KServe InferenceService, Kubeflow Model Registry).

The primary deployable artifact is an init container image (`Dockerfile.konflux.pipelines-components`) that compiles pipelines marked `managed: true` into YAML specs at build time, then copies them to a shared volume at pod startup for the KFP API server to discover. Three additional Konflux container images serve as runtime environments for AutoML, AutoRAG, and AutoRAG-inference pipeline steps. The `RELATED_IMAGE_*` environment variable pattern enables DSPO (Data Science Pipelines Operator) to inject digest-pinned images at runtime, supporting disconnected/air-gapped deployments.

## Architectural Analysis

The repository follows a library-plus-init-container pattern rather than deploying a long-running service. Components are Python functions decorated with `@dsl.component`, each specifying a `base_image` and `packages_to_install` so that KFP can execute them in isolated containers at pipeline runtime. The init container (`scripts.init_managed_pipelines`) bridges build-time and run-time: during `docker build`, `generate_managed_pipelines` discovers all pipelines with `managed: true` in their `metadata.yaml`, compiles each to a KFP YAML spec, and bundles the results into the image. At container start, the init script either copies pre-built YAMLs directly or, when `RELATED_IMAGE_*` environment variables are set, recompiles on the fly to substitute operator-supplied image references — a critical mechanism for disconnected cluster deployments.

The component architecture reveals a clear layered dependency: deployment components (model_deployment, deploy_embedding_model, evalhub_evaluator_kserve) create KServe ServingRuntime and InferenceService CRs programmatically via the Kubernetes Python client using in-cluster service account tokens. This means the component code has deep integration with the RHOAI serving stack — constructing vLLM GPU-based ServingRuntimes with RHOAI-specific annotations (`opendatahub.io/*`), hardware profile lookups (`infrastructure.opendatahub.io/v1` HardwareProfile CRs), and dashboard integration labels. The evalhub evaluator is particularly sophisticated: it creates ephemeral KServe deployments, submits evaluation jobs to Eval Hub via REST, polls for completion, and cleans up both the ServingRuntime and InferenceService after evaluation completes.

A notable security consideration is that several components handle credentials through environment variables (AWS keys, HF tokens, Kubernetes auth tokens, LLM API keys, OCI pull secrets) that are expected to be injected by the pipeline runtime or Kubernetes secrets. The evalhub component has a `verify_tls: bool = False` default, meaning TLS certificate verification is disabled by default for Eval Hub API calls. The tabular and timeseries data loader components also retry S3 downloads with `verify=False` after SSL errors — both patterns that weaken transport security guarantees.

The four managed pipelines (autogluon-tabular-training, autogluon-timeseries-training, documents-indexing, documents-rag-optimization) are all at `beta` stability. The remaining finetuning and evaluation pipelines are `experimental` and not yet managed, meaning they are not shipped via the init container to the KFP API server.
