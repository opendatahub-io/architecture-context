## Purpose

**Short**: AI-native gateway proxy built on the Praxis runtime that provides provider-aware routing, protocol translation, stateful OpenAI APIs, and agent traffic management for inference backends.

**Detailed**: Praxis AI is an AI gateway that sits between clients (OpenAI, Anthropic, MCP, A2A) and inference backends (vLLM, commercial providers). It classifies incoming requests by provider format, model, and protocol; routes them to appropriate backends through configurable filter pipelines; and applies cross-cutting policy (guardrails, credential injection, metering, token usage tracking).

The gateway implements protocol translation between provider-native APIs — for example, serving Anthropic Messages clients from Chat Completions-compatible backends, or translating OpenAI Responses into Chat Completions for native vLLM endpoints. It also manages stateful OpenAI Responses and Conversations endpoints, persisting session history in PostgreSQL or SQLite, and supports agentic tool loops with MCP, web search, and file search dispatch.

Praxis AI builds on top of the separate Praxis core proxy runtime, which provides listeners, TLS, load balancing, health checks, and the `HttpFilter` framework. The AI-specific layer packages all provider-aware filters and the server binary on top of it. A dedicated FIPS 140-3 build on UBI 9 performs all cryptography through the system OpenSSL, and the standard build uses Alpine with dynamically linked OpenSSL.

## Architectural Analysis

Praxis AI follows a **classify → route → transform** architecture where every request passes through a configurable filter pipeline. The filter framework, inherited from Praxis core, allows dynamic pipeline composition at startup and hot-reload at runtime without process restart.

The most significant architectural choice is the separation between the AI gateway (praxis-ai) and the proxy runtime (praxis-proxy/praxis). This lets AI-specific protocol support evolve independently while the core proxy handles connection management, TLS termination, and HTTP/2 backpressure through a forked Pingora engine ("quixotic-plecostomus"). The dependency flows in one direction: `server → filters → apis → praxis-filter`, with all praxis-core crates taken as versioned workspace dependencies.

The Rust workspace is structured as a multi-crate workspace producing a single binary (`praxis-ai`). The `apis` crate owns provider-specific type definitions and protocol parsers; the `filters` crate implements cross-cutting filter logic; and the `server` crate assembles everything into the runnable binary with auto-discovered external filters via build.rs codegen. Cargo feature flags gate optional capabilities — the `full` feature set includes all stable filters plus the PostgreSQL response store, while the FIPS build strips features whose dependencies carry non-OpenSSL cryptography (the policy engine, response stores, file resolve).

The response store subsystem is notable for its lifecycle-managed backend architecture: `store` defines persistence traits, `store-backends` provides PostgreSQL and SQLite implementations, and `store-lifecycle` manages pool provisioning across config reloads. The `ResponseStoreRegistry` is injected as a pipeline extension, so filters share backend connections through the filter context rather than constructing their own.

Cryptographic design is disciplined: all hashing (SHA-256, HMAC-SHA256) routes through `openssl` crate bindings to the system library, and the `secrecy` crate wraps sensitive values. The `hash.rs` module explicitly documents why each digest goes through OpenSSL — even non-security digests (cache keys, bucket identifiers) — because Red Hat's check-payload scanner fails on the presence of pure-Rust crypto crate names, regardless of usage.

The llm-d ext_proc integration provides a gRPC-based compatibility layer for external processing, compiled from protobuf definitions and gated behind the `llmd-ext-proc` feature. This allows the gateway to interoperate with Envoy's external processing protocol for LLM workloads.
