## Purpose

**Short**: Intelligent inference traffic router that provides LLM load-aware and prefix-cache-aware request routing, request prioritization, and disaggregated inference coordination via Envoy ext-proc integration.

**Detailed**: The llm-d Router is the entry point for inference traffic in the llm-d platform. It comprises three deployable components: the Endpoint Picker (EPP), which integrates with Envoy proxy via the gRPC ext-proc protocol to make real-time routing decisions based on KV-cache locality, endpoint load, and priority; the Coordinator, which orchestrates multi-stage disaggregated inference lifecycles (Encode/Prefill/Decode) through a configurable pipeline of steps to specialized worker pods; and the Disaggregation Sidecar, which runs alongside model-serving decode workers to coordinate prefill/decode handoff and KV-cache transfer.

The EPP watches Kubernetes CRDs (InferenceObjective, InferenceModelRewrite, InferencePool) to configure scheduling profiles, priority bands, and model name rewriting for A/B testing and canary rollouts. Its plugin architecture supports extensible filters and scorers that evaluate endpoints against configurable scheduling objectives. The router supports two deployment modes: Standalone Mode with a self-managed Envoy proxy, and Gateway Mode using the Kubernetes Gateway API for production environments.

## Architectural Analysis

The llm-d-router follows a separation-of-concerns architecture across three distinct binaries that can be deployed independently. The EPP operates as a controller-runtime application that both watches Kubernetes resources and serves the Envoy ext-proc gRPC protocol; this dual role means it maintains an in-memory datastore of pod states, model objectives, and scheduling profiles populated by reconciliation loops, which the gRPC request path queries to score and select endpoints without additional API server round-trips. The plugin system (EndpointPickerConfig CRD) allows runtime reconfiguration of scoring and filtering logic without redeployment.

The Coordinator uses a pipeline architecture where each step (replace-media-urls, render, encode, prefill, decode, async-broker) is a composable unit that transforms or routes the request. The pipeline is configured via YAML and can be tailored per deployment. The async-broker step bridges to a Redis-backed queue system (llm-d-async) for deferred request processing, adding an asynchronous serving mode alongside synchronous streaming.

The Sidecar acts as a local reverse proxy on each decode worker pod, intercepting inference requests and orchestrating the multi-hop coordination needed for disaggregated serving. It maintains LRU caches of proxy handlers for prefill, decode, and encoder backends, and supports multiple KV-transfer protocols (NIXL RDMA, shared storage, SGLang bootstrap) and EC-transfer protocols for multimodal embeddings.

TLS is configurable at every boundary: the EPP gRPC server, the Coordinator HTTP server, the Coordinator metrics endpoint, and the Sidecar serving and proxying layers all support minimum TLS 1.2 with configurable cipher suites and certificate reloading. However, no application-level authentication is enforced on the gRPC ext-proc surface; the EPP relies on the deployment topology (Envoy sitting in front) for access control.
