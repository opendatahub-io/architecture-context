## Purpose

**Short**: KServe model serving platform providing the AutoGluon TabularPredictor and TimeSeriesPredictor inference runtime as a containerized KServe-compatible server, alongside the full KServe controller stack for managing InferenceServices, LLMInferenceServices, and local model caching on Kubernetes.

**Detailed**: This repository is a Red Hat downstream fork of the KServe project that produces the AutoGluon model server container image for RHOAI. The autogluon server is a Python-based KServe model server that serves AutoGluon TabularPredictor and TimeSeriesPredictor models via the KServe v1 REST and v2 Open Inference Protocol. It auto-detects the model type at load time, dispatching to either tabular or time-series inference logic. The server integrates with KServe's storage subsystem for model download from S3, GCS, Azure Blob, and other backends.

The broader repository also contains the full KServe Go operator stack: the core `kserve-controller-manager` that reconciles InferenceService, InferenceGraph, ServingRuntime, and TrainedModel CRDs; the `llmisvc` controller that manages LLMInferenceService resources with Gateway API, KEDA, and LeaderWorkerSet integration; the `localmodel` and `localmodelnode` controllers that cache models to node-local PVs; and the `router` component for InferenceGraph traffic routing. However, this build artifact (`Dockerfile.konflux.autogluon`) targets specifically the Python autogluon model server.

## Architectural Analysis

The architecture separates concerns between the Go operator plane and the Python model-serving plane. The Konflux build (`Dockerfile.konflux.autogluon`) produces only the autogluon server image, which runs as a standalone model server container inside KServe-managed pods. The server inherits KServe's Python SDK infrastructure (FastAPI/Starlette on uvicorn, gRPC via grpcio, Prometheus metrics on port 8080) and layers AutoGluon-specific model loading and inference logic.

A notable design decision is the `AutoGluonDetectedModel` class, which acts as a runtime strategy selector: it attempts to load the model directory as a `TabularPredictor` first, then falls back to `TimeSeriesPredictor`. This enables a single ClusterServingRuntime definition to serve both model types transparently. The v2 inference protocol support for tabular models is thorough — the server correctly maps AutoGluon's per-feature column model to v2's per-tensor input contract, returning typed model metadata via `get_input_types()` and `get_output_types()`. Time-series models are currently REST v1 only.

The Go operator side runs four separate binaries (`manager`, `llmisvc`, `localmodel`, `localmodelnode`) each with their own controller-runtime manager. The `llmisvc` controller is particularly notable: it manages the full lifecycle of LLM inference services including Gateway API HTTPRoutes, KEDA/WVA autoscaling, LeaderWorkerSets for multi-node inference, and InferencePool resources from the Gateway API inference extension. The `localmodel` system enables pre-caching models to node-local PersistentVolumes, reducing cold-start latency.

Security is enforced through kube-rbac-proxy sidecars for metrics endpoints, cert-manager for webhook TLS, and Kubernetes admission webhooks with FailurePolicy=Fail for all CRD validation. The TLS configuration in the logger worker allows configurable `InsecureSkipVerify` (runtime-controlled via log request settings), while the LLMInferenceService controller has a `tlsInsecureSkipVerify` config option for Prometheus connections used in KEDA autoscaling — both are explicit opt-in patterns, not defaults.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | RBAC via ClusterRoles scoping SA to specific resource verbs; kube-rbac-proxy for metrics | Kubernetes | Model server endpoints have no application-level auth — relies on platform ingress (Istio/Gateway API) |
| Data storage | Per-namespace PVCs for local model cache; model artifacts from external storage per-CR config | Kubernetes | LocalModelCache PVs are node-scoped, shared across namespaces via LocalModelNode |
| Network traffic | Delegated to platform (Istio AuthorizationPolicy, NetworkPolicy) | Platform | No built-in NetworkPolicy manifests in the repository |
| Compute & resources | Resource requests/limits in ServingRuntime definitions (1 CPU, 2Gi per container) | Kubernetes | No built-in ResourceQuota or LimitRange enforcement |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps via controller watches | Kubernetes | ClusterServingRuntime and ClusterStorageContainer are cluster-scoped, shared across tenants |
| API scoping | Controllers use namespace-scoped watches for namespaced resources | Kubernetes | ClusterServingRuntime watches are cluster-wide |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
