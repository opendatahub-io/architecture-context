## Purpose

**Short**: MCP (Model Context Protocol) server that enables AI agents to interact with Red Hat OpenShift AI environments, managing workbenches, model serving, pipelines, training, and data connections through a plugin-based tool interface.

**Detailed**: The RHOAI MCP server implements the Model Context Protocol specification, providing a standardized interface through which AI assistants (Claude, ChatGPT, etc.) can discover and operate RHOAI platform resources. It exposes MCP tools for managing the full lifecycle of data science workflows -- creating Data Science Projects (namespaces), launching Jupyter/VS Code workbenches (Kubeflow Notebooks), deploying models via KServe InferenceServices, configuring Data Science Pipelines, managing training jobs via the Kubeflow Training Operator, and handling storage (PVCs) and data connections (S3 secrets).

The server uses a pluggy-based plugin architecture with 14 plugins (10 domain plugins + 4 composite plugins) that register MCP tools, resources, and prompts at startup. Domain plugins handle individual RHOAI components (notebooks, inference, pipelines, training, connections, storage, projects, model-registry, prompts, quickstarts), while composite plugins provide cross-domain orchestration tools (cluster exploration, training workflows, tool discovery, model recommendation via a Planner backend). The server connects to the Kubernetes API using in-cluster service accounts, kubeconfig files, or explicit tokens, and exposes its MCP interface over stdio, SSE, or streamable-http transports.

Multi-user access is supported via OIDC authentication with two token validation modes: JWT (JWKS-based validation against an OIDC issuer) and TokenReview (OCP OAuth token validation via the Kubernetes TokenReview API). When OIDC is enabled, the server uses Kubernetes user impersonation and SubjectAccessReview-based RBAC to filter MCP tools per user based on their Kubernetes permissions.

## Architectural Analysis

The RHOAI MCP server is a well-structured, plugin-based Python service that acts as an intermediary between AI agents and the RHOAI platform. Its architecture follows several notable patterns:

**Plugin Architecture with Graceful Degradation**: The pluggy-based plugin system allows the server to start even when not all RHOAI components are available. Each domain plugin declares its CRD requirements (e.g., notebooks requires `kubeflow.org/v1 Notebook`), and health checks at startup mark unavailable plugins as unhealthy without preventing the server from serving other domains. This is critical for RHOAI environments where not all components are always installed. The 10 domain plugins + 4 composite plugins provide comprehensive coverage of the RHOAI platform surface.

**Composite Pattern for Cross-Domain Orchestration**: The composite plugins layer higher-level operations on top of domain plugins. The `cluster_summary` tool aggregates data from 7 domain clients in a single call, reducing token usage for AI agents. The `training` unified tool consolidates 14 different training actions behind a single tool interface with an `action` parameter. The `diagnose_resource` tool combines status checks, event analysis, log retrieval, and common failure pattern detection (ImagePullBackOff, OOMKilled, etc.) into automated troubleshooting. These composites demonstrate intentional design for AI agent consumption -- minimizing the number of tool calls needed for common workflows.

**Multi-User Security Model**: The OIDC auth implementation is thoughtfully designed with defense-in-depth. The pure ASGI middleware avoids Starlette's BaseHTTPMiddleware (which breaks SSE streaming). User impersonation via `Impersonate-User`/`Impersonate-Group` headers ensures that all K8s API calls execute with the authenticated user's permissions, not the server's SA permissions. Per-tool RBAC filtering uses deduplicated SubjectAccessReview checks to hide tools the user cannot use. Security hardening includes CWE-113 header injection prevention, CWE-20 identity value validation, CWE-269 inherited impersonation header clearing, and CWE-400 rate-limited JWKS refresh. However, when OIDC is disabled (the default), all users share the server's broad SA permissions -- a significant gap that should be documented for operators.

**Model Registry Dual-Client Architecture**: The model_registry domain supports both the standard Kubeflow Model Registry API (v1alpha3) and the Red Hat Model Catalog API (v1alpha1) through automatic API type detection. Discovery cascades through CRD lookup → namespace scan → port-forward (for outside-cluster access), with results cached. Benchmark extraction differs by API: structured custom properties for Model Registry vs. markdown README parsing for Model Catalog. This dual-client approach allows the MCP server to work across RHOAI versions as the Model Registry evolves.

**Operation Safety**: The server implements a multi-layer safety model: `read_only_mode` disables all writes, `enable_dangerous_operations` gates delete operations independently, and destructive tools require explicit `confirm=True` parameters. The RHOAI kustomize overlay defaults to read-only mode, requiring intentional opt-in for write operations in production. All create/update/delete tool handlers check `server.config.is_operation_allowed()` before proceeding.
