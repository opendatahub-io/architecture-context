## Purpose

**Short**: A collection of text detection microservices for the FMS Guardrails Orchestrator, providing regex-based PII detection, HuggingFace model-based content analysis, and LLM-as-a-judge evaluation capabilities.

**Detailed**: Guardrails Detectors is a repository that produces multiple detector microservices used by the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator) to perform safety, content moderation, and data protection checks on text generation input and output. The repository is maintained by the TrustyAI team.

The repository produces three distinct detector types: (1) a **built-in detector** that bundles lightweight, heuristic detection functions (regex-based PII detection for emails, credit cards, SSNs, phone numbers, IP addresses; file-type validation for JSON/XML/YAML with optional schema validation; and user-defined custom detectors with static code analysis sandboxing), (2) a **HuggingFace detector** that wraps `AutoModelForSequenceClassification`, `AutoModelForTokenClassification`, and `GraniteForCausalLM` models for ML-based content analysis (toxicity, prompt injection, etc.), and (3) an **LLM Judge detector** that integrates the `vllm_judge` library for LLM-as-a-judge evaluations using configurable metrics. All detectors expose the IBM Detector API (`/api/v1/text/contents`) and are designed to be deployed as KServe InferenceServices.

Each detector is packaged as an independent container image, with Konflux Dockerfiles for the built-in and HuggingFace variants. The built-in detector runs standalone, while the HuggingFace detector requires a pre-downloaded model directory and the LLM Judge requires a running vLLM-compatible inference server.

## Architectural Analysis

The guardrails-detectors repository follows a clean modular architecture with a shared `common` library providing the base FastAPI application class, Pydantic request/response schemas, and Prometheus instrumentation. Each detector type (built-in, HuggingFace, LLM Judge) is a self-contained Python module that extends the common base, implementing its own `handle_request` or `run` method. The `DetectorBaseAPI` class centralizes health endpoint registration, exception handling (with structured error responses for missing parameters and type mismatches), and Prometheus counter management (requests, detections, errors, runtime per detector function). This design allows adding new detector types with minimal boilerplate.

The built-in detector uses a registry pattern (`BaseDetectorRegistry`) where detector functions are organized into registries (regex, file_type, custom). The custom detector subsystem is particularly notable: it dynamically loads user-supplied Python code from `custom_detectors/custom_detectors.py` and applies static code analysis (`ast.parse`) to block forbidden imports (`os`, `subprocess`, `sys`, `shutil`) and dangerous calls (`eval`, `exec`, `open`). This provides a sandboxing layer for user-defined detection logic, though it is AST-based and not a true sandbox -- determined attackers could potentially bypass it through indirect dynamic imports or obfuscation. The custom detector framework also supports decorator-based features: `@use_instruments` for custom Prometheus counters and `@non_blocking` for asynchronous background execution of non-critical detections.

The HuggingFace detector supports three distinct model architectures auto-detected from `config.architectures` in the model config: `AutoModelForSequenceClassification` (text-level classification with per-label thresholds), `AutoModelForTokenClassification` (token-level entity detection with span grouping via adjacent-token merging), and `GraniteForCausalLM` (IBM's causal LM guardian model with multi-risk assessment across 7 risk categories). The detector includes sophisticated parameter resolution through `_ResolvedParams` that validates and clamps threshold, label_thresholds, safe_labels, and max_length from environment variables and per-request `detector_params`, with proper type checking and fallback defaults. CUDA support is auto-detected at initialization with graceful fallback to CPU.

From a deployment perspective, there is an asymmetry between the two Konflux-shipped components: the built-in detector pipeline (`.tekton/odh-built-in-detector-v3-5-push.yaml`) sets `hermetic: false`, while the HuggingFace detector pipeline enables `hermetic: true` with Hermeto pip prefetch for both CPU and CUDA architectures. This means the built-in detector build can fetch dependencies at build time from external registries, creating a supply chain gap compared to the fully hermetic HF build. The LLM Judge detector has no Konflux pipeline at all -- it uses only the upstream `Dockerfile.judge` and is not currently shipped as part of the RHOAI product build. The HuggingFace Konflux Dockerfile uses a multi-architecture pattern with `FROM --platform` directives to select CUDA base images for x86_64/arm64 and CPU base images for ppc64le/s390x, ensuring GPU acceleration is used where available.
