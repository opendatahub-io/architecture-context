## Purpose

**Short**: A Kubernetes operator that manages the lifecycle of workbenches (Jupyter Notebooks) infrastructure for the OpenDataHub and Red Hat OpenShift AI platforms.

**Detailed**: The workbenches-operator is a controller-runtime-based Go operator responsible for deploying, configuring, and managing the Kubeflow Notebook Controller ecosystem on OpenShift. It reconciles a cluster-scoped `Workbenches` custom resource (CR) and applies upstream kustomize manifests for three sub-components: the Kubeflow notebook controller (kf-notebook-controller), the ODH notebook controller, and notebook image definitions (ImageStreams).

The operator supports dual-platform deployment (ODH and RHOAI) with platform-specific kustomize overlays, distribution-aware status reporting, and a version handshake protocol with the platform orchestrator via a ConfigMap (`odh-workbenches-config`). It also registers two mutating admission webhooks: one for injecting HardwareProfile settings (resource requests/limits, tolerations, nodeSelectors) into Notebook CRs, and another for injecting connection secrets as `envFrom` references into Notebook containers.

The operator integrates with the OpenShift cluster TLS security profile, dynamically bootstrapping its TLS configuration from the `APIServer` resource and watching for profile changes to trigger graceful restarts. All manifests are applied via Server-Side Apply (SSA) with field ownership, enabling clean upgrades and conflict resolution.

## Architectural Analysis

The workbenches-operator follows the emerging RHOAI 3.x "module operator" pattern, where individual component operators are factored out from the monolithic rhods-operator into standalone controllers with well-defined CRD contracts. The Workbenches CR serves as a component-level contract, receiving orchestrated configuration (platform identity, gateway domain, MLflow state) from the parent operator and reporting distribution alignment and deployment health back through status conditions and the phase field.

The manifest application strategy is notable: rather than encoding deployment logic in Go, the operator embeds upstream kustomize manifests at build time (via `get_all_manifests.sh` into `/opt/manifests/`) and renders them at reconcile time with dynamic parameter injection. This preserves upstream manifest fidelity while allowing the operator to inject platform-specific values (gateway URL, image references, namespace) via kustomize's `configMapGenerator` and `replacements`. The operator copies manifests to a temp directory before rendering, keeping the baked-in `/opt/manifests` immutable. This approach means the operator manages three distinct manifest groups per reconcile: kf-notebook-controller (OpenShift overlay), odh-notebook-controller (base), and notebooks (platform-specific base -- ODH or RHOAI).

The TLS security posture is well-designed: the operator bootstraps its TLS configuration from the OpenShift cluster's APIServer TLS profile at startup, using `openshift/controller-runtime-common` to fetch the profile and construct cipher suites. On non-OpenShift clusters, it falls back to a hardened Mozilla Intermediate cipher set (6 AEAD ciphers, TLS 1.2 minimum). A `SecurityProfileWatcher` monitors for TLS profile changes and triggers a graceful shutdown to reload, ensuring the operator always aligns with cluster policy. The webhook server (port 9443) and metrics server (port 8443) both inherit this TLS configuration.

The webhook architecture implements two admission handlers with different security models. The connection-notebook webhook performs SubjectAccessReview checks to verify that the requesting user has `get` permission on the referenced connection secrets -- a defense-in-depth measure preventing privilege escalation through the webhook. The hardware-profile webhook, by contrast, does not perform SAR checks; it reads HardwareProfile CRs using the operator's service account. This is architecturally intentional (HardwareProfiles are cluster-level resources meant to be visible to workbench users) but worth noting as a design decision. Both webhooks are fail-closed (`failurePolicy: Fail`) with 5-second timeouts.

The platform version handshake protocol (`odh-workbenches-config` ConfigMap with `platformVersion` key) gates the Ready condition, ensuring the operator doesn't report readiness until it has reconciled against the target platform version. This enables coordinated upgrades: the platform operator writes the target version, waits for the module operator to acknowledge it in `status.releases`, and only then considers the module upgrade complete. The Workbenches CR uses a singleton pattern (`default-workbenches` enforced by CEL validation rule) with an immutable `workbenchNamespace` field, preventing accidental namespace migration after initial setup.
