## Purpose

**Short**: Kubernetes operator that manages Jupyter notebook server lifecycle on OpenShift, including pod creation, idle culling, Gateway API ingress, kube-rbac-proxy authentication, and data science pipeline/MLflow/Feast integrations.

**Detailed**: The kubeflow repository contains two complementary Go operators that together manage Jupyter Notebook workspaces on Red Hat OpenShift AI. The upstream **notebook-controller** (from Kubeflow) handles the core lifecycle: it watches `Notebook` custom resources and reconciles them into StatefulSets and Services, with optional Istio VirtualService routing and idle notebook culling via Jupyter kernel/terminal API polling.

The **odh-notebook-controller** extends the upstream controller for OpenShift/RHOAI environments. It injects kube-rbac-proxy sidecar containers for RBAC-enforced authentication (RHOAI 3.x pattern), creates Gateway API HTTPRoutes for notebook ingress in a central namespace with cross-namespace ReferenceGrants, manages NetworkPolicies per notebook, and integrates with Data Science Pipelines (Elyra runtimes), MLflow tracking, Feast feature store config, and OpenShift ImageStreams. Both controllers run as a single deployment managed by the platform operator (rhods-operator/opendatahub-operator).

The component also handles migration from RHOAI 2.x patterns (OAuth proxy + OpenShift Routes) to the 3.x pattern (kube-rbac-proxy + Gateway API HTTPRoutes), including cleanup of legacy OAuthClient resources on notebook deletion.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar performs SubjectAccessReview per request; user must have GET on notebooks.kubeflow.org in notebook namespace | kube-rbac-proxy / Kubernetes RBAC | Auth only enforced when `notebooks.opendatahub.io/inject-auth: "true"` annotation is present; without it, notebook is accessible to any pod in the cluster |
| Data storage | Per-namespace Notebook CRs; DSPA secrets created per namespace | Kubernetes namespace isolation | No cross-namespace data isolation enforcement beyond Kubernetes RBAC |
| Network traffic | Two NetworkPolicies per notebook: controller-access (port 8888 from controller namespace only) and kube-rbac-proxy-access (port 8443 open to all) | Kubernetes NetworkPolicy | kube-rbac-proxy NetworkPolicy allows all ingress on port 8443; relies on kube-rbac-proxy SubjectAccessReview for access control rather than network-level restriction |
| Compute & resources | None (delegated to namespace-level ResourceQuota) | Kubernetes | Controller does not enforce per-tenant compute limits |
| Configuration & secrets | Per-namespace Secrets (ds-pipeline-config, kube-rbac-proxy-config) and ConfigMaps (workbench-trusted-ca-bundle) | Kubernetes namespace isolation | workbench-trusted-ca-bundle is aggregated from cluster-wide CAs; not tenant-specific |
| API scoping | Controller watches Notebooks cluster-wide; HTTPRoutes created in central namespace with labels for tenant association | Kubernetes controller-runtime | HTTPRoutes in central namespace use labels (notebook-namespace, notebook-name) for association; ReferenceGrant per user namespace |

## Architectural Analysis

The kubeflow repository implements a two-layer operator architecture: the upstream Kubeflow notebook-controller handles the fundamental Notebook-to-StatefulSet lifecycle, while the ODH notebook-controller adds RHOAI-specific capabilities through an extension pattern rather than forking. The ODH controller imports the upstream Notebook API types as a Go dependency (`replace` directive points to the sibling directory) and registers its own watches on the same CRD, effectively running as a companion reconciler in the same process. This design preserves upstream compatibility while enabling deep OpenShift integration.

The ingress architecture has fully migrated to the RHOAI 3.x Gateway API pattern. HTTPRoutes are created in the central controller namespace (e.g., `openshift-ingress`) rather than the user's namespace, which requires ReferenceGrant CRs to permit cross-namespace Service references. Each user namespace gets one shared ReferenceGrant (created on first notebook, cleaned up when last notebook is deleted using finalizers). The kube-rbac-proxy sidecar performs SubjectAccessReview authentication, forwarding the upstream user identity via X-Auth-Request-User and X-Auth-Request-Groups headers. Legacy RHOAI 2.x resources (OAuthClient CRs) are cleaned up via finalizers during notebook deletion, supporting live migration scenarios.

The mutating webhook is architecturally critical -- it performs 10+ operations including kube-rbac-proxy injection, CA bundle mounting, ImageStream resolution, pipeline runtime image sync, Elyra config secret creation, Feast config mounting, MLflow env var injection, and cluster proxy env injection. Several of these operations (DSPA secret sync, runtime images sync) were added to the webhook to fix race conditions (RHOAIENG-24545) where the controller hadn't yet created the required ConfigMaps/Secrets when the pod started. The webhook pre-syncs these resources during admission, ensuring they exist before the pod is scheduled.

The TLS configuration deserves note: the controller reads the OpenShift APIServer CR to obtain the cluster TLS security profile, then configures both its own webhook server and the kube-rbac-proxy sidecar with the same cipher suite restrictions. This ensures the component automatically adapts when cluster administrators change the TLS policy (e.g., from Intermediate to Modern profile). The TLS watcher (from openshift/controller-runtime-common) monitors the APIServer CR and dynamically updates the server's TLS config without restart.

The idle notebook culling mechanism is noteworthy for its direct Jupyter API integration. Rather than relying on proxy-level metrics or pod-level activity signals, the CullingReconciler makes HTTP calls to each notebook's `/api/kernels` and `/api/terminals` endpoints, parsing the `last_activity` timestamps from each kernel and terminal session. This provides accurate idle detection that accounts for active computations (running kernels) even when the user's browser is disconnected.
