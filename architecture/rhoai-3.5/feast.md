## Purpose

**Short**: Feast is a feature store for machine learning that provides a Kubernetes operator and feature serving infrastructure for managing, storing, and serving ML features at scale.

**Detailed**: Feast (Feature Store) is an open-source feature store that bridges the gap between data engineering and machine learning by providing a centralized platform for managing feature definitions, storing feature data in online and offline stores, and serving features for model training and inference. The repository contains the complete Feast platform: a Python SDK with CLI tools, a Go-based high-performance feature server, a Kubernetes operator for declarative deployment, and a React-based UI for feature exploration.

In the RHOAI distribution, the Feast operator (`feast-operator`) manages the lifecycle of `FeatureStore` custom resources, automatically provisioning feature serving infrastructure including online stores, offline stores, registry servers, and UI components. The operator handles TLS auto-configuration on OpenShift, OIDC and Kubernetes RBAC-based authorization, horizontal pod autoscaling, CronJob-based materialization, and integration with OpenDataHub notebooks via automatic ConfigMap injection.

The feature server component (`feature-server`) is a Python-based service that exposes REST and gRPC APIs for online feature retrieval, feature pushing, materialization, and an embedded MCP (Model Context Protocol) server. It supports pluggable online store backends (Redis, PostgreSQL, DynamoDB, SQLite, and 15+ others) and offline store backends (DuckDB, Snowflake, BigQuery, Spark, and others) for comprehensive feature management.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-FeatureStore ServiceAccount; OIDC or K8s RBAC with feature-level permissions; auto-access RBAC bindings from registry permissions | Kubernetes RBAC + Feast SecurityManager | InsecureSkipVerify=true on operator→registry calls bypasses TLS verification for cluster-internal traffic |
| Data storage | Per-FeatureStore PVCs for file-based stores; separate DB credentials via per-CR Secrets | Kubernetes PVC isolation + credential-based DB access | Shared database instances rely on credential separation, not schema isolation |
| Network traffic | ClusterIP services (not exposed externally by default); OpenShift Route only for UI | Kubernetes Service networking | No NetworkPolicy resources created by operator; relies on namespace-level policies if any |

## Architectural Analysis

The Feast architecture in RHOAI follows a clean operator pattern where a single Go-based operator manages multiple `FeatureStore` instances across namespaces, each resulting in a consolidated Deployment that runs all Feast services (online store, offline store, registry, and optionally UI) as separate processes within one pod. This single-pod-per-FeatureStore approach simplifies networking and TLS configuration but limits independent scaling of individual services — the HPA scales the entire pod, not individual components.

The authorization model is notably sophisticated, implementing a two-tier system: Kubernetes-level RBAC for cluster access control (via TokenReview and SubjectAccessReview APIs) and application-level permissions for fine-grained feature access (via Feast's registry-stored permission policies). The operator bridges these tiers by reading permission policies from the running registry and automatically creating corresponding Kubernetes RBAC bindings — a pattern that keeps authorization declarative while enabling per-feature access control. The auto-access RBAC reconciliation, which creates ClusterRoleBindings for namespace discovery and namespace-scoped RoleBindings for ConfigMap access, runs on every 30-second requeue cycle.

The TLS architecture on OpenShift is well-integrated: the operator auto-detects OpenShift clusters, fetches the cluster's TLS profile from `apiservers.config.openshift.io/cluster`, and configures service annotations for automatic certificate provisioning. The OIDC CA certificate resolution follows a priority chain (CR-specified → ODH auto-detected bundle → system CA) that enables seamless integration with both self-managed and platform-managed identity providers. However, there is a notable security gap: the operator uses `InsecureSkipVerify=true` when calling the in-cluster registry to fetch permissions, which bypasses TLS verification even when TLS is configured. While this is cluster-internal traffic, it weakens the security posture and could be improved.

The Go feature server (under `go/`) provides a high-performance alternative to the Python feature server for online feature retrieval only. It supports HTTP and gRPC serving with OpenTelemetry tracing, TLS 1.2+ with post-quantum key exchange (X25519MLKEM768), and pluggable online store backends (SQLite, Redis, DynamoDB, PostgreSQL). The Go server is not currently used as the primary serving path in the Konflux-built feature server image — the Python-based feature server is the deployed component.

The notebook integration via `NotebookConfigMapReconciler` is an ODH-specific feature that watches for Kubernetes Notebooks (kubeflow.org GVK, discovered dynamically) labeled with `opendatahub.io/feast-integration=true` and automatically creates ConfigMaps containing Feast client configuration. This enables zero-configuration Feast access from ODH notebooks, with the reconciler handling ConfigMap lifecycle as FeatureStore CRs and Notebooks are created, updated, or deleted.
