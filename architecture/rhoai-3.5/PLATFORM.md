## Platform Overview

Red Hat OpenShift AI (RHOAI) 3.5 is a comprehensive AI/ML platform built on OpenShift Container Platform that provides end-to-end capabilities for data science workflows: interactive development via JupyterLab workbenches, ML pipeline orchestration via Kubeflow Pipelines, model serving via KServe with multi-framework support, distributed training via Kubeflow Trainer and KubeRay, model evaluation and fairness monitoring via TrustyAI, experiment tracking via MLflow, and LLM-optimized inference via the llm-d distributed serving stack. The platform ships 162 container images across 69 analyzed components, spanning Go operators, Python services, Rust gateways, Java monitoring services, and TypeScript/Node.js frontends.

RHOAI is deployed via OLM (Operator Lifecycle Manager) through a hierarchical operator model. The platform operator (`rhods-operator`) manages component lifecycle through a DAG-based runlevel system, deploying components either as traditional kustomize-based controllers or as Helm-based module operators. A CloudManager subsystem extends deployment support beyond OpenShift to AWS EKS, Azure AKS, and CoreWeave Kubernetes clusters. The platform's ingress architecture centers on a centralized Gateway API stack deployed by the platform operator: traffic flows through an OpenShift Route or LoadBalancer to a Gateway API Gateway backed by an Envoy data plane, with EnvoyFilter-based ext_authz calling kube-auth-proxy for OAuth2/OIDC authentication before routing to component backends via HTTPRoutes. This replaces the RHOAI 2.x per-component OAuth-proxy sidecar pattern.

The security posture is defense-in-depth: FIPS 140-compliant cryptography via Go's native FIPS module or strictfipsruntime build tags, UBI-based container images (177 of 442 Dockerfiles), kube-rbac-proxy sidecars for RBAC-enforced HTTPS termination on 11+ components, Kuadrant AuthPolicies for Gateway API-level authorization, mTLS within the Istio service mesh, and network segmentation via NetworkPolicies. The platform supports disconnected (air-gapped) deployments through the `RELATED_IMAGE_*` environment variable pattern and OLM relatedImages, with digest-pinned image references throughout.

### Central Components

**rhods-operator** (24 reverse dependencies) is the platform's root operator, managing the lifecycle of all other components through a DAG-based runlevel system. It deploys the centralized Gateway API ingress stack, authentication infrastructure, and monitoring configuration. Every operator and service in the platform depends on rhods-operator for deployment, configuration injection, and image reference resolution.

**KServe** (16 reverse dependencies) is the model serving foundation. It provides InferenceService and LLMInferenceService CRDs that are consumed by the AI Gateway (MaaS), Data Science Pipelines (model deployment), TrustyAI (fairness monitoring), Model Registry (metadata linking), odh-dashboard (serving UI), and the llm-d stack (LLM routing). KServe's LLMInferenceService controller orchestrates resources across 10+ API groups including Gateway API, GIE InferencePools, LeaderWorkerSets, and DRA ResourceClaimTemplates.

**kube-rbac-proxy** (7 reverse dependencies) serves as the platform's standard authentication enforcement sidecar. It is injected into KubeRay Operator, Kubeflow Notebook Controller, odh-dashboard, TrustyAI Service Operator, EvalHub, and multiple other components, providing SubjectAccessReview-based RBAC checks with FIPS-compliant TLS termination.

**Kueue** (8 reverse dependencies) provides workload scheduling and resource quota management consumed by distributed training, pipeline execution, and inference workload components.

**Model Registry** (5 reverse dependencies) acts as the central metadata catalog for ML models, versions, and artifacts, consumed by KServe, odh-dashboard, odh-model-controller, RHOAI MCP Server, and pipeline components.

## Deployment Architecture

### Deployment Topology

The platform deploys across four namespace tiers. The **operator namespace** (`redhat-ods-operator`) hosts the platform operator, webhook configurations, and CRD definitions. The **applications namespace** (`redhat-ods-applications`) contains platform-wide services: the dashboard (with 10+ BFF module containers in sidecar mode), KServe controllers, odh-model-controller, the centralized Gateway API stack (Gateway + Envoy + kube-auth-proxy), and module operators (AI Gateway, MLflow, MCP Lifecycle, Feast, Trainer, Workbenches). An optional **infrastructure namespace** (`redhat-ai-gateway-infra`) hosts MaaS shared database configuration.

#### Manifest Consumption Pipeline

Component manifests flow through a multi-stage pipeline from source to cluster. Component repositories maintain kustomize manifests in their `config/` directories with distribution-specific overlays. The `get_all_manifests.sh` script (run during rhods-operator builds) fetches component manifests at pinned commit SHAs and stores them in `prefetched-manifests/` (for component controllers) or `prefetched-charts/` (for module operators using Helm). At reconcile time, the rhods-operator renders these manifests with runtime parameters (namespace, image references, feature flags) and applies them via server-side apply. Module operators follow a similar pattern but use Helm chart rendering with values derived from their CRs. For disconnected deployments, all image references are resolved from `RELATED_IMAGE_*` environment variables injected by OLM, overriding manifest-embedded defaults.

### Disconnected Support

RHOAI supports fully disconnected (air-gapped) deployments through multiple mechanisms. All operators implement the `RELATED_IMAGE_*` environment variable pattern, where OLM injects digest-pinned image references from the operator bundle's `relatedImages` list. Image resolution follows a three-tier precedence: `RELATED_IMAGE_*` env vars > ConfigMap entries > hardcoded defaults, ensuring the correct images are used without manifest changes. Container images are mirrored to local registries via `oc-mirror` using ImageContentSourcePolicy/ImageDigestMirrorSet CRDs. All 162 shipped images use SHA256 digest references rather than tags. The NVIDIA NIM integration provides an explicit `airGapped` mode that disables all NGC API calls. CA bundle management aggregates platform, user-provided, and service-ca certificates into unified ConfigMaps consumed by all components requiring outbound TLS.

## Platform Architectural Analysis

RHOAI 3.5 represents a platform in active architectural transition, with several cross-cutting patterns revealing both deliberate design choices and evolutionary tensions.

**Dual deployment model (Components vs. Modules)**: The platform operator manages components through two coexisting deployment models. The traditional component controller pattern uses kustomize overlays from `prefetched-manifests/`, while the newer modules framework uses Helm charts from `prefetched-charts/` and deploys separate operator CRs managed by their own controllers. Newer components (AI Gateway Operator, MLflow Operator, MCP Lifecycle Operator, Feast Module Operator, Trainer Operator, Workbenches Operator) use exclusively the modules pattern, while KServe uniquely exists as both a component controller and a module. This dual model creates operational complexity but enables independent versioning and lifecycle management for module operators. The platform version upgrade handshake mechanism (used by AI Gateway Operator and module operators) coordinates version alignment between the platform operator and module operators via ConfigMap-based signaling.

**Ingress architecture evolution (2.x to 3.x)**: The platform is transitioning from per-component OAuth-proxy sidecars (RHOAI 2.x pattern) to a centralized Gateway API stack (RHOAI 3.x pattern). Both patterns coexist: the rhods-operator deploys the centralized Gateway with kube-auth-proxy for OAuth2/OIDC authentication, while odh-model-controller still creates OpenShift Routes for InferenceServices (2.x path) alongside Kuadrant AuthPolicies on HTTPRoutes (3.x path). The 3.x path is activated when LLMInferenceService CRs are used, while InferenceService CRs follow the 2.x path. This coexistence means the platform currently maintains two complete ingress stacks, with the Gateway API path adding Istio EnvoyFilters, Kuadrant AuthPolicies, and ReferenceGrants that the Routes path does not require.

**Authentication heterogeneity**: Despite the standardization on kube-rbac-proxy (used by 11+ components) and Gateway-level ext_authz, the platform exhibits multiple authentication mechanisms at different layers. Gateway-level auth uses kube-auth-proxy (OAuth2/OIDC) via ext_authz. Service-level auth uses kube-rbac-proxy (SubjectAccessReview). API-level auth uses Kuadrant AuthPolicies (Authorino-backed) for fine-grained route authorization. Application-level auth uses bearer tokens (MaaS API keys). The odh-dashboard adds another layer with its BFF auth modes: `user_token` (pass-through) vs. `internal` (ServiceAccount impersonation). This layered approach provides defense-in-depth but means operators must configure auth at multiple levels, and a misconfiguration at any layer could create gaps.

**TLS and FIPS compliance inconsistencies**: While the platform broadly targets FIPS compliance, the implementation varies across components. Go operators use either `GOEXPERIMENT=strictfipsruntime` (older pattern) or `GOFIPS140=v1.0.0` (newer Go 1.26 pattern). The DSPO explicitly uses `CGO_ENABLED=0` with `GOFIPS140`, leveraging Go 1.22+'s embedded FIPS module without dynamic linking, while KServe and llm-d Router use `CGO_ENABLED=1`. The llm-d Router's EPP Dockerfile notably omits the `strictfipsruntime` build tag despite enabling CGO, creating a potential FIPS compliance gap. Several components default to `InsecureSkipVerify=true` for internal TLS connections (rhods-operator Gateway DestinationRule to kube-auth-proxy, DSPO database connections with `tls=skip-verify`, llm-d Router data source clients), mitigated by mesh-level mTLS but still representing certificate validation bypasses.

**LLM-native architecture layer (llm-d stack)**: RHOAI 3.5 introduces a substantial LLM-optimized inference stack alongside the traditional KServe model serving path. The llm-d ecosystem (Router, KV Cache, Latency Predictor, Routing Sidecar, Async, Planner, Batch Gateway) adds GPU-aware routing with prefix-cache affinity, disaggregated prefill/decode inference with five KV-cache transfer mechanisms (NIXL v2, Shared Storage, SGLang, Mooncake, P2P Offloading), variant-aware autoscaling based on queueing theory, and batch inference processing. This layer operates largely independently from the traditional KServe InferenceService path, connected primarily through the LLMInferenceService CRD. The architectural split creates two inference stacks with different operational models, scaling characteristics, and debugging approaches.

**Multi-tenant operator composition**: Several operators compose multiple independent controllers in a single binary with service-registry patterns. TrustyAI Service Operator manages six domains (TAS, LMES, EvalHub, GORCH, NemoGuardrails, Module) selectable via `--enable-services` flags. odh-dashboard's operator manages sidecar vs. standalone deployment modes with 10+ BFF modules. This pattern enables flexible deployment profiles but creates large blast-radius binaries where a bug in one controller's reconciliation loop can affect all controllers. EvalHub's multi-tenant model is the most sophisticated, discovering tenant namespaces via labels and provisioning per-tenant RBAC, ServiceAccounts, and discovery ConfigMaps.

**Reactive configuration pipelines**: Multiple components implement hash-based reactive configuration that automatically responds to cluster state changes. The TrustyAI GORCH controller watches KServe InferenceServices and ServingRuntimes, hashing their combined state and regenerating orchestrator/gateway ConfigMaps only when the hash changes. The AI Gateway Operator's MaaS teardown protocol uses annotation-based signaling (`maas.opendatahub.io/teardown-requested`, `maas.opendatahub.io/teardown-completed`) for coordinated multi-resource cleanup. These patterns reduce manual configuration but create implicit coupling where changes in one component's resources can trigger reconciliation cascades in unrelated controllers.

**Dashboard as a federation platform**: The odh-dashboard has evolved from a monolithic web application into a Webpack Module Federation platform with independently deployable BFF modules (gen-ai, MaaS, MLflow, eval-hub, automl, autorag, agent-ops, model-registry). Inter-BFF communication creates a service mesh within the dashboard layer, where the gen-ai BFF calls MaaS and MLflow BFFs directly via HTTP. The sidecar deployment mode places all modules in a single pod with 10+ containers, creating a monolithic operational unit despite the architectural decomposition. This trade-off simplifies networking but means a failing BFF module can impact all dashboard functionality.
