## Purpose

**Short**: Lightweight REST API service for orchestrating LLM evaluations across multiple backends on OpenShift.

**Detailed**: EvalHub is a Go-based REST API server that orchestrates large language model (LLM) evaluations across multiple evaluation frameworks including lm-evaluation-harness (188 benchmarks), RAGAS, Garak, GuideLLM, LightEval, DeepEval, IBM CLEAR, and MTEB. It provides a unified API for submitting evaluation jobs, tracking their progress, managing benchmark collections and providers, and exporting results to MLflow and OCI registries.

On OpenShift, EvalHub is deployed and managed by the TrustyAI Service Operator via an `EvalHub` custom resource (`trustyai.opendatahub.io/v1alpha1`). The service creates Kubernetes Jobs for each benchmark evaluation, injecting a sidecar proxy container (`eval-runtime-sidecar`) and an init container (`eval-runtime-init`) that downloads test data from S3. The sidecar acts as a reverse proxy, routing traffic from evaluation adapters to the eval-hub API, MLflow tracking server, model inference endpoints, and OCI registries with appropriate authentication.

The service also provides an MCP (Model Context Protocol) server (`evalhub-mcp`) that exposes evaluation capabilities as AI-native tools, resources, and prompts, enabling LLM agents and IDE integrations to submit evaluations, discover providers, and compare results programmatically.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar injects X-User and X-Tenant headers; eval-hub rejects requests without these headers in cluster mode | kube-rbac-proxy (Kubernetes RBAC) + Application | Auth is header-based; if kube-rbac-proxy is bypassed (e.g., pod-to-pod without NetworkPolicy), headers could be spoofed |
| Data storage | Shared database with tenant column; all queries scoped by tenant from X-Tenant header; system resources (providers, collections) are shared across tenants | Application (SQL query filtering) | Single shared database; no schema-level isolation |
| Network traffic | No NetworkPolicy defined by eval-hub itself; relies on platform operator to create per-namespace policies | Platform operator (external) | If platform operator doesn't create NetworkPolicies, cross-namespace access is possible |
| Compute & resources | Evaluation jobs created in the tenant's namespace; resource requests/limits set on job pods via HardwareProfile CRD | Kubernetes (namespace ResourceQuota) | No built-in quota enforcement; depends on cluster-level ResourceQuota |
| Configuration & secrets | Per-namespace Secrets for model credentials, S3 credentials, OCI credentials; ConfigMaps for provider/collection configs | Kubernetes (RBAC on Secrets) | Secrets referenced by name; if user has access to the namespace, they can read secrets of other users' jobs in the same namespace |
| API scoping | All list/query operations filter by tenant (X-Tenant header); system resources visible to all tenants; owner field for user-level scoping | Application | System-scoped providers/collections shared across tenants (by design); no fine-grained per-user RBAC beyond owner field |

| Shared Service | Tenant Boundary | Isolation Mechanism |

## Architectural Analysis

EvalHub follows a **sidecar proxy pattern** for evaluation job execution. Rather than requiring evaluation framework adapters to handle authentication, TLS, and service discovery directly, the service injects a reverse proxy sidecar (`eval-runtime-sidecar`) into each evaluation job pod. The adapter sees only `http://localhost:8080` and the sidecar handles credential injection, token caching, and TLS termination for all upstream services (eval-hub API, MLflow, OCI registries, model endpoints). This pattern significantly reduces the complexity of the Python-based eval-hub-sdk and the individual framework adapters. The sidecar uses KEP-753 init container promotion (`restartPolicy: Always`), which ensures it starts before the main container and remains running throughout the job lifecycle.

The **credential management** approach uses multiple isolation layers. Model API keys are injected via ephemeral Kubernetes Secrets that are created per-job and deleted after completion. The sidecar resolves `ref-token` patterns (e.g., `Bearer api-key:ref`) by loading secrets from a projected volume mount, avoiding static credential embedding. K8s ServiceAccount tokens use projected volumes with 1-hour expiry for ROSA/STS compatibility. All token types are cached in-memory with configurable TTL (default 5 minutes) using atomic pointer operations for thread safety.

The **storage layer** uses a pluggable SQL abstraction supporting both SQLite (development/local mode) and PostgreSQL (production). All entities are serialized as JSON and stored alongside tenant-scoped metadata columns. The service distinguishes between "system" resources (providers and collections shipped with the container image) and "tenant" resources (user-created). System resources are immutable and loaded at startup from YAML files in `config/providers/` and `config/collections/`, with a hot-reload watcher (500ms debounce) for configuration updates. PostgreSQL uses Read Committed isolation with `FOR UPDATE` locks for job state transitions, while SQLite uses WAL mode with a single-writer mutex.

The **MCP server** (`evalhub-mcp`) represents a modern integration pattern for AI-native tooling. It exposes the full evaluation lifecycle as MCP tools (`submit_evaluation`, `cancel_job`, `get_job_status`, `discover_providers`), resources (`evalhub://` URI scheme), and prompts (`edd_workflow`, `evaluate_model`, `compare_runs`). The server supports three transports: stdio for local CLI usage, Streamable HTTP for remote access, and legacy HTTP+SSE for backwards compatibility with older MCP clients. It includes a 30-second completion cache for provider/benchmark/collection IDs to improve interactive response times.

The **observability stack** is comprehensive. OpenTelemetry integration spans traces, metrics, and logs with support for OTLP gRPC and HTTP exporters. The service bridges Go's `slog` logger to OTEL's log provider for unified log export, and can export evaluation job container logs as OTEL log records with benchmark-level attributes. Prometheus metrics include both standard HTTP semconv counters and custom evaluation lifecycle counters (`evalhub.evaluation_jobs`, `evalhub.evaluation_job_completions`, `evalhub.benchmark_runtime_errors`). A dedicated metrics server runs on port 8081, separate from the API server.
