## Purpose

**Short**: Kubernetes operator that manages the lifecycle of OGX AI server deployments, providing declarative configuration of inference providers, vector databases, tool runtimes, and file storage backends.

**Detailed**: The OGX K8s Operator is a controller-runtime based Kubernetes operator that watches `OGXServer` custom resources and reconciles a complete application stack for each instance: a Deployment running the OGX distribution image, a ClusterIP Service, optional Ingress for external access, NetworkPolicy for network segmentation, HPA for autoscaling, PDB for disruption tolerance, PVC for persistent storage, and Prometheus monitoring resources (ServiceMonitor and PrometheusRule).

The operator implements a declarative provider configuration system where users specify inference providers (vLLM, OpenAI, Azure, Bedrock, VertexAI, Watsonx), vector I/O providers (PGVector, Milvus, Qdrant), tool runtime providers (Brave Search, Tavily, MCP), and file storage providers (S3, LocalFS) through the CRD spec. The operator generates a `config.yaml` from these declarations, resolving base configurations from OCI image labels and injecting secret references as environment variables. An override mode allows users to supply a complete config.yaml via ConfigMap instead.

The repository also contains an **OGX Module** (`ogx-module/`), a separate Go binary that integrates with the RHOAI/ODH platform operator. The module controller watches an `OGX` platform CR (cluster-scoped, in the `components.platform.opendatahub.io` API group) and deploys the root OGX operator using kustomize overlays. It handles platform-specific concerns: namespace targeting, image injection via `RELATED_IMAGE` environment variables, health aggregation across all OGXServer instances, and lifecycle management (Managed/Removed states). The module is the entry point when OGX is deployed as a managed RHOAI component.

## Architectural Analysis

The OGX K8s Operator employs a **two-tier deployment architecture** that is characteristic of RHOAI managed components. The outer tier is the OGX Module (`ogx-module/`), which integrates with the platform operator through the `components.platform.opendatahub.io/v1alpha1` API group. The module controller renders kustomize overlays (RHOAI or ODH) to deploy the inner tier -- the root OGX Operator -- into the platform applications namespace. This separation allows the platform operator to manage component lifecycle (enable/disable, image updates, version tracking) without understanding OGX-specific business logic, while the root operator focuses entirely on OGXServer reconciliation.

The **provider configuration system** is the operator's most architecturally distinctive feature. Rather than requiring users to write raw config.yaml, the CRD exposes a strongly-typed provider hierarchy (inference, vector_io, tool_runtime, files, batches, responses, file_processors) with per-provider-type validation via CEL rules and webhook logic. The operator resolves a base config from OCI image labels embedded in the distribution image, then merges user-specified providers on top. Secret references are converted to environment variables following the `OGX_<PROVIDER_ID>_<FIELD>` convention, with `${env.OGX_...}` substitution in the generated config.yaml. This design enables GitOps workflows where CRs are committed to git while secrets remain in Kubernetes.

The **legacy adoption system** (`controllers/legacy_adoption.go`) handles migration from the deprecated `llamastack.io/v1alpha1` CRD to the current `ogx.io/v1beta1` CRD. Adoption is annotation-driven: setting `ogx.io/adopt-storage` or `ogx.io/adopt-networking` on an OGXServer CR triggers the operator to scale down the legacy Deployment, detach its PVC (removing the old ownerRef), transfer Service/Ingress ownership, and relabel resources for the new instance. PVCs are deliberately not given a new ownerRef so they survive OGXServer deletion -- a deliberate design choice for data safety.

The **network architecture** follows a defense-in-depth pattern. Each OGXServer instance gets a dedicated NetworkPolicy with default-deny ingress except from the same namespace and the operator namespace. OpenShift ingress router access is automatically added when external access is enabled. Egress is unrestricted by default but can be locked down with explicit rules (DNS egress is auto-injected when any egress rules are configured). The operator supports optional TLS termination at the server level (via TLS Secret reference) and outbound mTLS to providers (via spec.tls with trust anchors and client certificates).

The **monitoring integration** is comprehensive: ServiceMonitor targets the OGX server metrics port (default 9464) with a 60s scrape interval, and PrometheusRule defines recording rules that produce binary API usage indicators (`ogx:api_info:max`) for inference, vector_io, responses, RAG, and agentic APIs. These recording rules enable platform-level telemetry aggregation without requiring Prometheus to query raw high-cardinality metrics.
