## Purpose

**Short**: NeMo Guardrails is a Python server that applies programmable guardrails to LLM-based conversational applications, enforcing safety, content moderation, and controllable dialog policies.

**Detailed**: NeMo Guardrails is an open-source toolkit from NVIDIA for adding programmable safety controls ("rails") between application code and large language models. It provides input rails (validating user prompts), output rails (checking LLM responses), retrieval rails (filtering RAG results), and tool rails (governing tool use). The system supports two Colang versions: Colang 1.0 (a declarative dialog language) and Colang 2.x (a flow-based programming model).

The downstream RHOAI build packages the guardrails library as a FastAPI server container image with an OpenAI-compatible API surface. It uses the AIPCC CPU base image for RHEL-hardened builds, pre-downloads ML models for offline operation, and applies a profile filter (`opensource`) to strip closed-source guardrail integrations (ActiveFence, AI Defense, Autoalign, etc.) before shipping. The fork adds several downstream-specific features: a `/v1/guardrail/checks` endpoint for per-message rail evaluation, runtime LLM authentication via header forwarding (`X-Authorization` → `Authorization`), and OpenTelemetry auto-instrumentation support in the entrypoint.

The server acts as a proxy layer in the RHOAI inference stack: clients send OpenAI-compatible chat completion requests, the guardrails engine applies configured rails, and the request is forwarded to an upstream LLM model server (vLLM, NIM, OpenAI-compatible, etc.). It does not host models itself — it proxies to them after applying safety policies.

## Architectural Analysis

NeMo Guardrails follows a **proxy-with-policy** architecture: it sits between clients and LLM providers, applying configurable safety policies defined in the Colang domain-specific language. The FastAPI server exposes an OpenAI-compatible API surface, making it a drop-in safety layer for any application already using the OpenAI chat completions API. The server caches `LLMRails` instances per config_id, so the first request for a given configuration incurs model loading overhead while subsequent requests reuse the cached instance.

The **fork-specific additions** are carefully isolated to minimize upstream merge conflicts. Header forwarding (`header_forwarding.py`), the `/v1/guardrail/checks` endpoint (`server/checks.py`), and the guardrail profile filter (`scripts/filter_guardrails.py`) are each in dedicated files not present in the upstream NVIDIA repository. This separation is explicitly called out in code comments (e.g., "Fork-specific, extracted to reduce conflict surface during upstream syncs"). The entrypoint script adds OpenTelemetry auto-instrumentation wrapping when `OTEL_EXPORTER_OTLP_ENDPOINT` is set, providing observability without code changes.

The **build hermeticity strategy** is notable: requirements are compiled from the RHEL AI Python Package Index with full hash pinning, and ML model artifacts (sentence-transformers/all-MiniLM-L6-v2 for semantic similarity, qdrant/all-MiniLM-L6-v2-onnx for ONNX embedding, and NLTK punkt tokenizer) are locked via `artifacts.lock.yaml` with SHA-256 checksums. The `setup_prefetched_models.sh` script reconstructs HuggingFace cache directory layouts from Hermeto-prefetched generic artifacts during the build, enabling fully air-gapped operation. This is a significant improvement over the upstream `Dockerfile.server` which downloads models from HuggingFace during build.

The **guardrail library filtering** mechanism deserves attention: the `filter_guardrails.py` script at build time removes closed-source guardrail integrations (ActiveFence, AI Defense, Autoalign, Clavata, Cleanlab, CrowdStrike, Fiddler, GCP, jailbreak_detection, Pangea, PatronusAI, PolicyAI, PrivateAI, Prompt Security, Trend Micro) from the image when built with the `opensource` profile. This ensures the RHOAI-shipped image contains only Apache-2.0 licensed guardrail code. The remaining open-source guardrails include self_check, content_safety, regex, hallucination, sensitive_data_detection, llama_guard, gliner, factchecking, attention, context_bloat_detection, f5, guardrails_ai, hf_classifier, injection_detection, polygraf, and topic_safety.

A **security consideration** is that the server does not enforce any inbound authentication — it relies entirely on the RHOAI platform to front it with kube-rbac-proxy or an equivalent auth sidecar. The `header_forwarding.py` module carefully filters infrastructure headers (X-Forwarded-*, X-Real-IP, X-Request-Id) and maps `X-Authorization` to `Authorization` for upstream LLM calls, preventing the Kubernetes/proxy auth bearer token from leaking to the LLM provider. When no static API key is configured, a `"runtime-provided"` sentinel is used as a placeholder, and real auth comes from the forwarded request headers at call time.
