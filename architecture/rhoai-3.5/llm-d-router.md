## Purpose

**Short**: Intelligent routing engine for LLM inference traffic that provides load-aware, prefix-cache-aware endpoint selection, request prioritization, flow control, and disaggregated prefill/decode orchestration.

**Detailed**: The llm-d Router is the entry point for inference traffic in the llm-d platform, delivering intelligent request routing across pools of LLM model servers. It consists of three deployable components: the **Endpoint Picker (EPP)**, which integrates with Envoy proxy via the ext-proc protocol to make real-time endpoint selection decisions based on KV-cache locality, queue depth, and priority; the **PD-Sidecar (Disaggregation Sidecar)**, which runs alongside decode model servers to orchestrate multi-stage inference lifecycles (Encode/Prefill/Decode) with KV-cache transfer coordination; and the **Coordinator**, an HTTP pipeline service that handles multimodal content downloading, tokenization, and multi-stage request orchestration for complex inference workflows.

The router supports two primary deployment modes: **Standalone Mode** where a self-managed Envoy proxy runs alongside the EPP in the same pod, and **Gateway Mode** where the EPP acts as a backend for the Kubernetes Gateway API InferencePool resource. The EPP watches Kubernetes CRDs (InferencePool, InferenceObjective, InferenceModelRewrite) to dynamically configure routing behavior, priority levels, and model name rewriting for A/B testing and canary rollouts.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-tenant auth; EPP serves all requests routed by Envoy | Platform (Envoy/Gateway routing) | EPP itself does not authenticate callers; relies on upstream proxy for tenant-level access control |
| Data storage | Per-namespace CRDs (InferenceObjective, InferenceModelRewrite scoped to pool) | Kubernetes RBAC | No cross-tenant data leakage risk; each EPP instance watches only its configured pool namespace |
| Network traffic | No NetworkPolicy defined | None | EPP accepts gRPC connections from any source within the cluster; recommend NetworkPolicy restricting to Envoy pod |

| Configuration & secrets | Per-namespace InferencePool, InferenceObjective, InferenceModelRewrite CRDs | Kubernetes RBAC | CRD-level isolation is effective; namespace RBAC prevents cross-tenant configuration changes |
| API scoping | Namespace-scoped controller-runtime cache; watches filtered to pool namespace | controller-runtime | Effective namespace scoping prevents listing resources across namespaces |

## Architectural Analysis

The llm-d Router represents a sophisticated inference routing system that bridges the gap between Kubernetes-native resource management and real-time ML serving optimization. Its architecture centers on three key design decisions that shape the entire system.

**Plugin-driven extensibility**: The EPP's architecture is fundamentally built around a plugin framework with five extension point categories: scheduling plugins (filters, scorers, pickers, profile handlers), request control plugins (data producers, admitters, response receivers), flow control plugins (ordering, fairness, saturation detection, usage limits), data layer plugins (data sources, extractors, attributes), and request handling plugins (protocol parsers). This design enables the routing logic to be customized without modifying core code. The plugin DAG builder (`pkg/epp/config/loader/configloader.go:229-282`) topologically sorts plugins by dependencies, allowing complex composition. Default configuration ships with queue-depth, KV-cache utilization, and prefix-cache scorers -- a reasonable starting point for most LLM serving workloads. The plugin system also supports multiple scheduling profiles via ProfileHandlers, enabling disaggregated inference patterns (data-parallel, prefill/decode split) where different endpoint subsets serve different stages of inference.

**Disaggregation as a first-class pattern**: The PD-Sidecar implements five distinct KV-cache transfer mechanisms (NIXL v2, Shared Storage, SGLang, Mooncake, P2P Offloading), reflecting the reality that disaggregated LLM inference requires different transfer protocols depending on hardware, network topology, and serving framework. The NIXL v2 connector is the most sophisticated, supporting both serial and parallel (MoRI-IO) dispatch modes, wide Expert Parallelism across multiple pods, and configurable RDMA Write semantics. The sidecar's architecture as an HTTP reverse proxy with cached per-host handlers (`pkg/sidecar/proxy/proxy.go:312-334`) is elegant -- it avoids creating new connections for each request while maintaining per-prefiller/encoder isolation. The SSRF protection via InferencePool-based allowlisting (`pkg/sidecar/proxy/allowlist.go`) is a notable security feature that validates all upstream targets against the set of pods in the watched InferencePool.

**FIPS compliance gap in EPP**: While the Sidecar Konflux Dockerfile correctly includes `-tags strictfipsruntime` with `CGO_ENABLED=1` for FIPS compliance, the EPP Konflux Dockerfile uses `CGO_ENABLED=1` but omits the strictfipsruntime build tag. This means the EPP binary may not use FIPS-validated cryptographic implementations despite being dynamically linked. Additionally, all data source clients (metrics scraper, DCGM exporter, models discovery) default to `InsecureSkipVerify=true` for TLS connections to model servers, which is pragmatic for development but represents a certificate validation gap in production. The self-signed TLS certificates generated with 10-year expiry and RSA 4096-bit keys (`internal/tls/tls.go:34-73`) are suitable for development but should be replaced with cert-manager-provisioned certificates in production.

**Coordinator pipeline architecture**: The Coordinator's sequential pipeline with step registry and factory pattern (`pkg/coordinator/pipeline/registry.go`) provides clean separation between pipeline stages. The SSRF protection in the replace-media-urls step is particularly thorough -- it includes dial-time IP checks (blocking loopback, link-local, CGNAT, private ranges), optional hostname allowlisting, and DNS rebinding defense via `dialControl` callback. The `ErrPipelineDone` sentinel for early exit (used by conditional-decode on cache hit) is an elegant pattern that avoids complex control flow. However, the Coordinator currently lacks a Konflux Dockerfile, meaning it is not built through the Red Hat Konflux pipeline and may not be shipped as a product component in RHOAI 3.5.
