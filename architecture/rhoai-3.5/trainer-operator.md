## Purpose

**Short**: Kubernetes operator that manages the lifecycle of the Kubeflow Trainer (V2) component within the Red Hat OpenShift AI platform, provisioning training infrastructure including CRDs, ClusterTrainingRuntimes, webhooks, and ImageStreams.

**Detailed**: The trainer-operator is a modular component operator that watches for a cluster-scoped `Trainer` CR (named `default-trainer`) and reconciles the full Kubeflow Trainer V2 training stack. When the Trainer CR is created, the operator verifies that the JobSet Operator dependency is installed and healthy (on OpenShift), ensures the target namespace exists, then renders and applies kustomize manifests from embedded templates to deploy the upstream Kubeflow Trainer controller, its validating webhooks, ClusterTrainingRuntimes, and (on OpenShift) ImageStreams for training workbench images.

The operator follows the ODH platform modular architecture pattern: it is deployed by the platform operator (rhods-operator) as a module, reads a `Trainer` CR for configuration, and reports status with structured conditions (Ready, ProvisioningSucceeded, Degraded). It uses the `odh-platform-utilities` library for cluster type detection, kustomize rendering, label management, garbage collection, and condition handling. The operator deploys pre-configured ClusterTrainingRuntimes for PyTorch (CPU, CUDA, ROCm), DeepSpeed, MLX, and TorchTune fine-tuning, each pinned to specific container images via params.env image references. It also manages OpenShift ImageStreams that expose versioned training-hub workbench images (CPU, CUDA, ROCm) for use in the RHOAI dashboard.

## Architectural Analysis

The trainer-operator follows the ODH modular operator pattern, acting as a thin lifecycle manager rather than implementing training logic itself. The operator's primary job is dependency validation, kustomize rendering, and server-side apply of the upstream Kubeflow Trainer V2 controller and its associated resources. The actual training orchestration (TrainJob → JobSet → Jobs → Pods) is handled entirely by the deployed Kubeflow Trainer controller. This separation is architecturally clean: the operator manages the "control plane" lifecycle while the deployed controller manages the "data plane" of training workloads.

The dependency checking system is particularly sophisticated for a modular operator. On OpenShift, the operator performs a four-stage dependency gate: (1) verifies the JobSet Operator is installed via OLM, (2) checks the JobSetOperator CR exists with name "cluster", (3) inspects the JobSetOperator CR's status conditions for degraded state (checking `Degraded`, `TargetConfigControllerDegraded`, `JobSetOperatorStaticResourcesDegraded` conditions), and (4) verifies the JobSet CRD itself is established. If any check fails, the operator sets degraded conditions with specific error messages and requeues after 60 seconds. On vanilla Kubernetes, only the CRD existence check is performed. This graceful degradation pattern prevents the operator from deploying a controller that would immediately fail due to missing infrastructure.

The cache hardening in `cmd/main.go` demonstrates security-aware design. The operator uses label-selector scoped informer caches (filtering on `platform.opendatahub.io/part-of: trainer`) to prevent OOM attacks where a user with edit permissions could create large objects that inflate the operator's memory. The cache is also namespace-scoped when `APPLICATIONS_NAMESPACE` is set, and direct API reads bypass the cache for resources like Namespaces to avoid implicit cluster-wide informers. This follows the guidance from the referenced Red Hat developer article on protecting operators from OOMKill.

The kustomize rendering pipeline uses an interesting work-directory pattern: manifests are copied from the embedded `/opt/manifests-template` to a writable `/opt/manifests-work` directory before rendering, allowing params.env overrides via environment variables (RELATED_IMAGE_* pattern). This supports Konflux's image pinning workflow where release-specific image digests are injected at build time through environment variables. The operator manages three independent resource sets (manifests, runtimes, imagestreams), each with its own params.env and rendering path. The `filterConfigMaps` flag on runtimes and imagestreams ensures the synthetic ConfigMaps generated by kustomize's `configMapGenerator` are stripped before apply, since they serve only as kustomize parameterization vehicles.

The RHOAI overlay adds several production-hardening features beyond the base manifests: a RBAC progression patch that grants the Kubeflow Trainer controller pod-list/get permissions and NetworkPolicy management for metrics endpoint security hardening during training workload progression tracking, a PodMonitor for Prometheus integration with TLS scraping, aggregated ClusterRoles (training-edit/admin/view) that integrate with Kubernetes standard RBAC aggregation labels, and a secretGenerator for the webhook TLS certificate. The `ENABLE_RHAI_FEATURES=true` environment variable on the deployed controller activates RHOAI-specific features in the upstream Kubeflow Trainer code.
