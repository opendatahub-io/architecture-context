## Purpose

**Short**: TrustyAI Service is a REST API for AI model monitoring that provides drift detection, fairness metrics, explainability, and LLM evaluation capabilities for models served by KServe and ModelMesh on OpenShift AI.

**Detailed**: TrustyAI Service is a Python-based FastAPI application that serves as the runtime component of the TrustyAI responsible AI stack within Red Hat OpenShift AI (RHOAI). It consumes inference data from KServe and ModelMesh model serving platforms, stores observations in either PVC-backed HDF5 files or MariaDB, and computes fairness and drift metrics both on-demand via REST endpoints and on a recurring schedule via a Prometheus metrics publisher.

The service supports multiple metric families: **fairness metrics** (Statistical Parity Difference, Disparate Impact Ratio, Average Odds Difference, Average Predictive Value Difference, Individual Consistency), **drift metrics** (Kolmogorov-Smirnov test, Jensen-Shannon divergence, Compare Means, Fourier MMD), **explainability** (LIME and SHAP via upstream libraries, currently WIP), and **LLM evaluation** (via the lm-evaluation-harness library). The service is deployed per-namespace by the TrustyAI Operator and integrates with the platform's monitoring stack by exposing computed metrics as Prometheus gauges that can be scraped by the cluster's monitoring infrastructure.

The architecture follows a three-layer design: a pure algorithm core (`src/core/`) intended for future upstream extraction to the `trustyai-explainability-python` library, a service layer (`src/service/`) handling storage, scheduling, and data management, and an endpoint layer (`src/endpoints/`) implementing the REST API. The service runs behind a kube-rbac-proxy sidecar in RHOAI 3.x for authentication and supports dual HTTP/HTTPS protocol binding via Hypercorn.

## Architectural Analysis

The TrustyAI Service represents a complete rewrite from Java (Quarkus) to Python, targeting RHOAI 3.5. This migration brings the service closer to the Python-native ML ecosystem, enabling direct use of scikit-learn, scipy, and pandas for metric computation rather than maintaining Java equivalents. The three-layer architecture (`core/` → `service/` → `endpoints/`) is deliberately designed for future extraction: the `core/` layer enforces a strict boundary — no imports from `service/` or `endpoints/` are permitted — so the pure algorithm implementations can be upstreamed to the `trustyai-explainability-python` library without modification.

The dual-protocol binding pattern (HTTP on 127.0.0.1:8080, HTTPS on 0.0.0.0:4443) reflects the RHOAI 3.x authentication architecture. The loopback-only HTTP binding ensures that the kube-rbac-proxy sidecar is the sole entry point for unauthenticated traffic — the application never accepts external HTTP connections directly. The HTTPS binding on 4443 provides an alternative direct-access path with TLS but without kube-rbac-proxy mediation, primarily for operator-to-service communication. Certificate auto-detection at startup allows the service to gracefully degrade to HTTP-only mode when TLS certificates are not provisioned, which is useful for local development.

The storage abstraction supports two fundamentally different backends: PVC-backed HDF5 files (the default, using h5py with async locks per dataset) and MariaDB (optional, with a v2 schema that auto-migrates from v1). The HDF5 backend stores data in per-dataset files with column names and aliases as HDF5 attributes, while MariaDB uses LONGBLOB columns with JSON+gzip serialization per cell. The serialization layer explicitly avoids Python pickle (replaced for CWE-502 mitigation), using JSON+gzip throughout. This design choice trades some performance for security — all deserialized data passes through JSON parsing rather than arbitrary code execution.

The LM Evaluation Harness integration is architecturally notable for its security hardening. It dynamically generates a Pydantic request model from lm-eval's argparse specification, runs evaluations as isolated subprocesses with a minimal environment (blocking `LD_PRELOAD`, `PYTHONPATH`, `PATH`, and proxy variables to prevent CWE-426/427 attacks), and manages job concurrency with configurable limits (`MAX_CONCURRENCY=4`). Server secrets (database passwords, TLS keys) are never passed to subprocess environments. The subprocess executable path is server-side only and not user-controllable.

The FIPS compliance approach is UBI10-native rather than application-level: the Dockerfile sets the system crypto policy to FIPS via `update-crypto-policies --set FIPS`, which configures OpenSSL system-wide. The Python `cryptography` library (>=48.0.1) uses the OpenSSL backend and inherits FIPS restrictions from the system policy. The only non-standard crypto usage is `hashlib.md5` with `usedforsecurity=False` for deterministic UUID generation (matching Java's `UUID.nameUUIDFromBytes()` for cross-platform compatibility) — this is FIPS-compliant as Python 3.9+ allows non-security MD5 calls even in FIPS mode.
