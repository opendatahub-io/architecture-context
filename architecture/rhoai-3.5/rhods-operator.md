## Purpose

**Short**: Platform operator that manages the lifecycle of all Red Hat OpenShift AI (RHOAI) components, including ingress infrastructure, authentication, monitoring, and cloud-provider integrations.

**Detailed**: The rhods-operator is the central control plane for RHOAI 3.5. It implements a controller-runtime based operator that manages 18+ component CRDs (Dashboard, KServe, Kueue, ModelRegistry, Workbenches, TrustyAI, etc.) through two primary custom resources: DataScienceCluster (DSC) for component orchestration and DSCInitialization (DSCI) for platform initialization. Components are provisioned using a DAG-based runlevel system that ensures correct ordering and readiness gating.

The operator deploys the platform's entire ingress infrastructure via the Gateway service controller, which creates Gateway API resources (Gateway, HTTPRoute), an OAuth2-Proxy-based authentication proxy (kube-auth-proxy), Istio EnvoyFilters for L7 authentication, OpenShift Routes for legacy redirects, and NetworkPolicies. This ingress stack provides the single entry point for all RHOAI component traffic with configurable authentication modes (OAuth, OIDC, external auth).

Additionally, the operator manages a monitoring service (Prometheus, OpenTelemetry, Perses, Tempo, Thanos), an auth service for RBAC group management, a CloudManager subsystem for AWS/Azure/CoreWeave hosted deployments, and a modules framework for deploying out-of-tree operators (AIGateway, KServe module, MLflowOperator, MCPLifecycleOperator). The operator also registers admission webhooks for HardwareProfile injection, serving connection validation, monitoring label injection, and singleton enforcement.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Admin groups (ClusterRole + namespaced Role bindings) + allowed groups (ClusterRole); kube-auth-proxy enforces OAuth/OIDC at ingress | Kubernetes RBAC + kube-auth-proxy + EnvoyFilter | Auth proxy is a single shared instance; compromised proxy affects all tenants |
| Data storage | Per-namespace PVCs for workloads; shared platform namespace for operator state | Kubernetes namespace isolation | Platform secrets (OAuth creds, TLS) stored in openshift-ingress namespace |
| Network traffic | NetworkPolicy for kube-auth-proxy (restrict ingress to Gateway pods + monitoring); per-component NetworkPolicies in prefetched manifests | Kubernetes NetworkPolicy | No default inter-component NetworkPolicy at platform level |
| Compute & resources | HardwareProfile CR defines resource requests/limits and scheduling (Queue or Node based); Kueue auto-creates ClusterQueue + LocalQueues per managed namespace | Kubernetes ResourceQuota (via Kueue) + HardwareProfile webhook | No default ResourceQuota without Kueue enabled |
| Configuration & secrets | Per-namespace Secrets for component connections; platform-level ConfigMaps in application namespace | Kubernetes namespace isolation | Operator ServiceAccount has broad cluster-wide RBAC |
| API scoping | Component CRDs are cluster-scoped singletons; workload CRDs (InferenceService, Notebook) are namespace-scoped | Kubernetes API server + admission webhooks | DSC/DSCI singletons mean single platform tenant per cluster |

## Architectural Analysis

The rhods-operator is one of the most architecturally complex operators in the RHOAI ecosystem. It manages the full platform lifecycle through a layered controller architecture: the DSC controller orchestrates components via a DAG-based runlevel system, the DSCI controller bootstraps platform infrastructure, and specialized service controllers handle ingress, auth, and monitoring. This design enables independent evolution of each subsystem while maintaining correct dependency ordering.

The Gateway controller deserves particular attention as it deploys a multi-layer ingress stack that is unique to RHOAI 3.x. The traffic path flows through an OpenShift Route or LoadBalancer → Gateway API Gateway → Envoy data plane → EnvoyFilter ext_authz (calling kube-auth-proxy for OAuth2/OIDC authentication) → Lua filter (token forwarding and cookie stripping) → HTTPRoute routing to component backends. This design replaces the RHOAI 2.x pattern of per-component OAuth-proxy sidecars with a centralized authentication proxy, reducing resource overhead and simplifying auth configuration. The controller handles three authentication modes (integrated OAuth, external OIDC, external auth/none) and two ingress modes (OcpRoute, LoadBalancer), with runtime auto-detection when not explicitly configured.

The modules framework introduces a second deployment model alongside the traditional component controller pattern. While component controllers use kustomize overlays from `prefetched-manifests/`, modules use Helm charts from `prefetched-charts/` and deploy separate operator CRs that are managed by their own controllers. This dual model creates some complexity—modules like KServe exist as both a component controller (managing legacy kustomize manifests) and a module (managing the KServe module operator via Helm). The transition from components to modules appears to be ongoing, with newer components (AIGateway, MLflowOperator, MCPLifecycleOperator) using only the modules pattern.

The CloudManager subsystem is architecturally isolated from the main operator: it has its own binary (`cloudmanager`), its own CRDs (`*KubernetesEngine`), and manages cloud-provider-specific dependencies (cert-manager, Sail/Istio, LWS) via Helm charts. This design enables RHOAI to run on non-OpenShift Kubernetes clusters (AWS EKS, Azure AKS, CoreWeave) without modifying the core operator logic. The Platform CR (`config.opendatahub.io/v1alpha1`) provides an alternative to DSC for these xKS environments, using the same modules framework but without DSCI (no monitoring namespace, no OpenShift-specific features).

A notable security design decision is the use of `insecureSkipVerify: true` in the DestinationRule for kube-auth-proxy traffic. This is mitigated by the fact that the traffic is within the Istio service mesh (mTLS between sidecars) and the kube-auth-proxy uses service-ca-generated certificates that are not in the mesh's trust domain. The operator also derives TLS settings from the OpenShift APIServer TLS profile, ensuring that the auth proxy's cipher suites and minimum TLS version align with the cluster's security policy—a pattern that maintains FIPS compliance without hardcoding cipher suites.
