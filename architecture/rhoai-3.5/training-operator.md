## Purpose

**Short**: Kubernetes operator for managing distributed ML training jobs across multiple frameworks (PyTorch, TensorFlow, XGBoost, JAX, MPI, PaddlePaddle).

**Detailed**: The Kubeflow Training Operator is a Kubernetes-native project for fine-tuning and scalable distributed training of machine learning models. It manages the lifecycle of distributed training jobs by creating and reconciling Pods, headless Services, and optional resources (NetworkPolicies, HPAs, PodGroups, RBAC resources) based on Custom Resource Definitions (CRDs) for each supported ML framework.

The operator provides a unified control plane that abstracts framework-specific distributed training patterns. For PyTorch, it handles elastic training with rendezvous configuration, init containers for master readiness, and HPA-based autoscaling. For TensorFlow, it generates the TF_CONFIG JSON environment variable for cluster specification. For MPI, it creates per-job RBAC (ServiceAccount, Role, RoleBinding) and ConfigMaps containing hostfiles and bootstrap scripts. Each framework controller extends a common job controller that handles pod/service reconciliation, gang scheduling integration (Volcano and scheduler-plugins), clean pod policies, backoff limits, and TTL-based cleanup.

In the RHOAI distribution, the operator runs in the `opendatahub` namespace with `kubeflow-` name prefix, uses ConfigMap-driven image injection for the training operator container, aggregated RBAC roles for edit/view access, and PodMonitor for Prometheus Operator integration. The operator builds with FIPS-compliant Go crypto (strictfipsruntime) on UBI9 base images for OpenShift compliance.

## Architectural Analysis

The Training Operator follows a clean **template method pattern** where a common `JobController` provides the reconciliation skeleton (pod lifecycle, service management, gang scheduling, status tracking) while each framework controller overrides specific hooks (`SetClusterSpec`, `UpdateJobStatus`, `IsMasterRole`, `GetDefaultContainerName`). This design enables consistent behavior across all six frameworks while allowing framework-specific environment variable injection, init container setup, and completion semantics. The common controller handles approximately 70% of the reconciliation logic, with each framework adding only 200-400 lines of specialization.

The operator's **informer cache is label-filtered** (`training.kubeflow.org/operator-name` exists selector) for Pods, Services, ConfigMaps, ServiceAccounts, Secrets, Roles, and RoleBindings. This is a critical performance optimization -- without it, the cache would load all cluster Pods and Services, causing unbounded memory growth in large clusters. ConfigMaps and Secrets are additionally configured with `DisableFor` on the client, bypassing the cache for direct API reads to avoid stale configuration data.

The **TLS configuration** is notably robust for a Kubeflow component. Rather than hardcoding TLS settings, the operator reads the OpenShift cluster's TLS security profile (`config.openshift.io/v1 APIServer`) at startup and applies the appropriate cipher suites and minimum TLS version. It handles three profile types (Intermediate, Custom, Modern) with graceful fallback to Intermediate defaults on non-OpenShift clusters or transient API errors. This ensures the operator's webhook and metrics endpoints comply with whatever TLS policy the cluster administrator has configured.

The **MPI controller** is architecturally distinct from the other five frameworks. It creates per-job RBAC resources (ServiceAccount, Role, RoleBinding) because the launcher pod needs `pods/exec` and `configmaps` access to manage worker pods via `kubectl exec`. It overrides `ReconcileServices` to be a no-op (MPI uses direct pod exec, not DNS-based discovery) and generates a ConfigMap containing the hostfile, `kubexec.sh`, and `discover_hosts.sh` scripts. This makes MPIJob the most complex in terms of dynamic resource creation.

The **RHOAI overlay** applies several important customizations. The `kubeflow-` name prefix ensures all resources are prefixed for namespace sharing with other components. The ConfigMap-driven image replacement injects the container image from `params.env` into both the Deployment container and the PyTorch init container argument, allowing the platform operator to control the image version centrally. Aggregated RBAC roles (`training-edit`, `training-view`) with `aggregate-to-admin/edit/view` labels integrate with OpenShift's role hierarchy so that namespace admins automatically get training job management permissions.
