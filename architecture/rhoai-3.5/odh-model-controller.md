## Purpose

**Short**: Extends KServe controller behavior with RHOAI-specific capabilities including ingress integration, authentication policy management, NVIDIA NIM account lifecycle, metrics collection, and a model-serving API server for gateway discovery.

**Detailed**: The odh-model-controller is a Kubernetes operator that augments the upstream KServe serving stack with Red Hat OpenShift AI (RHOAI) platform integration. It watches InferenceService, InferenceGraph, LLMInferenceService, and ServingRuntime custom resources to create and manage supplementary Kubernetes resources such as OpenShift Routes, Gateway API AuthPolicies, Istio EnvoyFilters, Prometheus ServiceMonitors, KEDA TriggerAuthentications, and RBAC bindings.

The controller manages the full NVIDIA NIM account lifecycle -- validating NGC API keys, fetching model metadata, creating pull secrets, and generating OpenShift Templates for NIM-based ServingRuntimes. It also implements admission webhooks that inject data connection credentials (S3, URI, OCI), hardware profile scheduling constraints (Kueue queue labels, node selectors, tolerations), and Ray TLS certificates into model serving pods.

A separate model-serving-api server component provides an HTTPS API for discovering available Gateway API gateways, enabling the RHOAI dashboard to display gateway options when users deploy LLM inference services. The server performs per-request RBAC checks using the caller's bearer token and SelfSubjectAccessReview to ensure users only see gateways in namespaces where they have permission to create LLMInferenceServices.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-ISVC ClusterRoleBindings (auth-delegator); per-Gateway/HTTPRoute AuthPolicies via Kuadrant; per-request SelfSubjectAccessReview in API server | Kubernetes RBAC + Kuadrant/Authorino | ClusterRoleBindings are cluster-scoped -- a compromised SA in one namespace has auth-delegator power cluster-wide |
| Data storage | Per-namespace Secrets (storage-config, NIM pull secrets, Ray TLS); per-namespace ConfigMaps (NIM config, CA bundles, metrics dashboards) | Kubernetes namespace isolation | storage-config Secret is auto-generated from all data connection secrets in the namespace -- no cross-namespace data leakage |
| Network traffic | No NetworkPolicies created by this controller (NetworkPolicy RBAC exists but is unused for tenant isolation) | N/A | Network isolation between tenant namespaces depends on platform-level NetworkPolicies created by rhods-operator |
| Compute & resources | HardwareProfile webhook injects Kueue queue labels or node selectors/tolerations per ISVC | Kueue (when used) or Kubernetes scheduler | No ResourceQuota enforcement by this controller; relies on platform or cluster-level quotas |
| Configuration & secrets | Per-namespace NIM Account (singleton enforced by webhook); per-namespace ConfigMaps and Secrets | Kubernetes namespace isolation + validating webhook | NIM Account singleton is per-namespace only (webhook allows one Account per namespace) |
| API scoping | model-serving-api filters gateways by namespace RBAC (SelfSubjectAccessReview); controllers use namespace-scoped watches for Secrets/Pods | Kubernetes RBAC + Application code | Gateway list is cluster-wide (filtered by RBAC); controller cache filters by label not namespace |

## Architectural Analysis

The odh-model-controller serves as a critical integration layer between the upstream KServe serving stack and the RHOAI platform. Its architecture reflects two distinct generations of the RHOAI ingress model. The InferenceService controller creates OpenShift Routes (the RHOAI 2.x pattern) with configurable TLS termination (Reencrypt when auth is enabled, Edge otherwise), while the LLMInferenceService and Gateway controllers implement the RHOAI 3.x pattern using Gateway API resources -- creating Kuadrant AuthPolicies on HTTPRoutes and Gateways, and Istio EnvoyFilters to route traffic through Authorino for authentication. Both patterns coexist in the codebase, with the 3.x path activated when LLMInferenceService CRs are used.

The controller's reconciliation architecture follows a sub-reconciler pattern where the top-level InferenceService controller delegates to specialized reconcilers (Route, ClusterRoleBinding, KEDA, Metrics Service, ServiceMonitor, Dashboard ConfigMap, ServiceAccount, Model Registry). Each sub-reconciler uses a delta processor with pluggable comparators to compute desired-vs-actual state differences. This design enables clean separation of concerns but means that a single InferenceService creation triggers 8+ sub-reconcilers in sequence, each performing its own API server round trips. The LLMInferenceService controller uses a similar but simpler pattern, delegating only to the AuthPolicy reconciler.

The webhook subsystem is notably rich. The Pod mutating webhook injects Ray TLS volumes and an init container for distributed training. The InferenceService and LLMInferenceService mutating webhooks inject ConnectionsAPI credentials (S3 ServiceAccounts, URI storage specs, OCI pull secrets) and HardwareProfile scheduling constraints (Kueue queue labels or node selectors/tolerations). The InferenceGraph validating webhook enforces same-namespace service URL references to prevent cross-namespace data exfiltration. The NIM Account validating webhook enforces a singleton pattern -- only one Account per namespace.

The NVIDIA NIM integration demonstrates a well-designed air-gapped mode: when DSC specifies `nim.airGapped=true`, the controller skips all NGC API calls (validation, model metadata fetching) and creates resources without external network access. This is critical for disconnected environments. The NIM Account controller manages the full lifecycle -- API key validation, model metadata ConfigMap, NVCR.io pull secrets, and OpenShift Template wrapping a ServingRuntime.

The model-serving-api server component is architecturally separate from the controller, deployed as its own Deployment with its own ServiceAccount and RBAC. It implements a FIPS-compliant TLS configuration with restricted cipher suites (ECDHE+AES-GCM only) and NIST curves (P-256, P-384). Its gateway discovery flow performs per-request RBAC checks by creating SelfSubjectAccessReviews with the caller's bearer token, ensuring users only see gateways in namespaces where they can create LLMInferenceServices. This is a security-by-design pattern -- the server never returns more data than the user is authorized to see.
