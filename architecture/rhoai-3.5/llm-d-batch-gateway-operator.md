## Purpose

**Short**: A Kubernetes operator that manages the lifecycle of LLM-D batch gateway deployments by reconciling `LLMBatchGateway` custom resources into Kubernetes resources via Helm chart rendering at runtime.

**Detailed**: The LLM-D Batch Gateway Operator provides a declarative interface for deploying and managing the [batch-gateway](https://github.com/opendatahub-io/batch-gateway) system, which enables batch inference processing for large language models. The operator watches `LLMBatchGateway` CRs and translates their spec into Helm values, renders the upstream batch-gateway Helm chart in-memory, and applies the resulting Kubernetes resources (Deployments, Services, ConfigMaps, ServiceAccounts, HTTPRoutes, Certificates, monitoring resources) via server-side apply with owner references for lifecycle management.

The operator manages four workload components: an **API server** (HTTP endpoint for batch job submission and file management), a **processor** (dispatches individual inference requests to inference gateways with AIMD-based adaptive concurrency control), a **garbage collector** (expires completed jobs and orphaned files), and an optional **async-processor** (dispatches inference requests asynchronously via Redis message queues to inference gateway EndpointPicker services). It supports both synchronous and asynchronous dispatch modes, S3 or filesystem-based file storage, PostgreSQL or Redis/Valkey database backends, optional TLS via cert-manager, Gateway API HTTPRoute exposure, and comprehensive Prometheus monitoring with Grafana dashboards and alerting rules. The operator also manages cross-namespace Secret references using Gateway API ReferenceGrant authorization and creates its own metrics Service, ServiceMonitor, and PrometheusRule for self-monitoring.

## Architectural Analysis

The LLM-D Batch Gateway Operator follows a **Helm-as-library pattern** rather than the typical controller-runtime pattern of imperatively constructing Kubernetes resources in Go code. The operator embeds two upstream Helm charts (batch-gateway and async-processor) at build time, loads them via `helm.sh/helm/v3/pkg/chart/loader`, and renders them in-memory using `helm.sh/helm/v3/pkg/engine`. This design has significant architectural implications: the operator's Go code is primarily a **CRD-to-Helm-values translator** (the `specToBatchHelmValues` and `specToAsyncHelmValues` functions in `helm_batch.go` and `helm_async.go`), with the actual resource topology defined in the Helm chart templates. This means the operator's behavior is tightly coupled to the upstream chart's template structure, and changes to the chart require careful synchronization of the CRD spec, the values mapping functions, and the `managedGVKs` list that drives orphan cleanup.

The operator's **orphan resource deletion** strategy (in `deleteOrphanedResources`) is comprehensive but coarse-grained: it lists all resources of each managed GVK in the CR's namespace, checks owner references, and deletes any owned resource not in the current render output. This handles config changes that remove optional resources (e.g., disabling HTTPRoute or monitoring) but requires the `managedGVKs` list to be kept in sync with every resource type the charts can produce. Missing a GVK from this list would leave orphaned resources on spec changes.

The **cross-namespace Secret handling** via Gateway API ReferenceGrant is a notable security design. Rather than requiring all Secrets to be in the same namespace as the CR, the operator supports referencing Secrets in other namespaces -- but only if a ReferenceGrant in the Secret's namespace explicitly permits the reference. The operator copies the Secret into the CR's namespace under a managed name (`{gateway-name}-credentials`) with an immutability constraint: once a managed copy is created, the `secretRef` cannot be changed without deleting and recreating the CR. This prevents credential-swap attacks while still supporting centralized secret management patterns.

The **dual dispatch mode architecture** (sync vs async) introduces significant complexity. In sync mode, the processor directly calls inference gateways via HTTP with AIMD-based adaptive concurrency control. In async mode, an additional async-processor Deployment is created that polls Redis sorted-set queues, dispatches to inference gateway EPP (EndpointPicker) services, and supports sophisticated gating mechanisms (prometheus-saturation, prometheus-budget, redis-quota) for flow control. The CRD validation ensures mutual exclusivity (`globalInferenceGateway` XOR `modelGateways`) and requires `asyncConfig` when `dispatchMode` is "async". This is enforced both in CRD CEL rules and in the controller's `validateSpec` function, providing defense-in-depth validation.

The **image management pattern** is notable: component images (apiserver, processor, gc, async) are NOT specified in the LLMBatchGateway CR. Instead, they are injected into the operator container as environment variables (`LLM_D_BATCH_GATEWAY_APISERVER_IMAGE`, etc.) by the platform operator via kustomize `configMapGenerator` replacements from `params.env`. This ensures the platform -- not the end user -- controls which container images are deployed, which is critical for supply chain security in a productized distribution. The operator fails to start if any of these four env vars is missing.
