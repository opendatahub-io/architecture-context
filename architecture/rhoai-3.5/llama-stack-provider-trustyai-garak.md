## Purpose

**Short**: Garak red-teaming evaluation adapter that integrates NVIDIA's Garak LLM vulnerability scanner with the eval-hub evaluation platform, running as Kubernetes Jobs or Kubeflow Pipelines on OpenShift AI.

**Detailed**: This component provides a `FrameworkAdapter` implementation for the eval-hub platform that orchestrates Garak red-teaming scans against LLM inference endpoints. It supports two execution modes: "simple" mode where Garak runs as a subprocess in the same K8s Job pod, and "KFP" mode where scans are delegated to a six-step Kubeflow Pipeline (validate, resolve taxonomy, SDG generation, prepare prompts, scan, write outputs) with S3-based artifact transfer via Data Connection secrets.

The adapter supports predefined benchmark profiles aligned to security frameworks (OWASP LLM Top 10, AVID taxonomy, CWE), a quality profile for toxicity/hate speech detection, and an intents-based risk assessment mode that uses Synthetic Data Generation (SDG) to produce adversarial prompts from a policy taxonomy. Results are parsed from Garak's JSONL reports into structured `EvaluationResult` metrics, persisted to OCI registries, and optionally logged to MLflow. The component also generates interactive HTML reports (ART reports) for intents scans with heatmaps and probe-level breakdowns.

The package is designed to run in containerised environments on Red Hat OpenShift AI. It reads job specifications from mounted ConfigMaps, authenticates to model endpoints via Kubernetes Secrets, and communicates scan progress back to eval-hub via sidecar callbacks. The KFP mode supports caching of taxonomy and SDG steps across multiple scan runs.

## Architectural Analysis

The component follows a clean layered architecture with a framework-agnostic `core` package and framework-specific adapters. The `core` package (config_resolution, pipeline_steps, garak_runner, command_builder) contains pure business logic that operates on local paths, content strings, and DataFrames. The `evalhub` package adds eval-hub-specific concerns: JobSpec parsing, sidecar callbacks, OCI persistence, and S3-based KFP artifact transfer. This separation means the same pipeline logic could be reused by alternative execution frontends without modification.

The API key resolution system is notably sophisticated, implementing a multi-tier fallback chain that adapts to three different deployment topologies: direct K8s API access (pre-sidecar evalhub), sidecar proxy model (evalhub >= 0.4.4 with AutomountServiceAccountToken=false), and local development (kubeconfig). The `_read_s3_credentials_from_secret` method alone has five resolution strategies that cascade gracefully. While this flexibility supports diverse deployment scenarios, it creates a complex failure surface where misconfigurations may silently fall through to a "DUMMY" key, potentially running scans against unauthenticated endpoints without warning.

The KFP pipeline design uses Konflux-built container images as the `base_image` for all six pipeline steps, resolved dynamically via `_resolve_base_image()` which checks KFPConfig, env vars, a Kubernetes ConfigMap, and a hardcoded default. This means every KFP pod runs the same image as the adapter pod, ensuring version consistency. The pipeline leverages KFP caching for taxonomy resolution and SDG generation steps (the most expensive operations), while validation, prompt preparation, scanning, and output writing are never cached.

The intents mode represents the most architecturally complex execution path, involving up to seven distinct model endpoints (target, judge, attacker, evaluator, SDG, translation, and the built-in HuggingFace models). The `_apply_intents_model_config` method enforces a "1 or 3" rule for judge/attacker/evaluator roles to prevent ambiguous configurations. API keys use `__FROM_ENV__` placeholders in the serialised config, resolved at pod level by `_resolve_config_api_keys` which maps config paths to model roles (e.g., `detector_model_config` -> JUDGE, `attack_model_config` -> ATTACKER). This deferred resolution pattern is necessary because the config is serialised and passed as a KFP pipeline argument, crossing pod boundaries.

The config redaction pattern (`redact_api_keys`) is applied defensively before any config is persisted to S3, OCI, or the Files API, recursively walking the config dict to replace `api_key` values with `"***"`. This ensures secrets never escape to object storage even if the serialisation pipeline has bugs, though the redaction is best-effort and depends on the key being named exactly `api_key`.
