## Purpose

**Short**: A Go CLI application that extracts, enriches, and catalogs metadata from Red Hat AI container images and produces structured model, MCP server, and agent catalogs for the RHOAI dashboard.

**Detailed**: model-metadata-collection is a data pipeline tool that discovers AI models from HuggingFace collections, processes OCI container images from Red Hat registries, and generates structured YAML catalogs. The tool operates in a multi-stage pipeline: first discovering models from HuggingFace's RedHatAI collections, then extracting model cards from OCI container image layers (using the `io.opendatahub.modelcar.layer.type` annotation to identify model card layers), enriching the extracted metadata with data from HuggingFace APIs and YAML frontmatter, and finally producing aggregated catalog YAML files.

The tool handles three distinct catalog types: (1) Model catalogs (validated, other, and combined) that describe AI models available as OCI "modelcar" containers in `registry.redhat.io`, (2) MCP (Model Context Protocol) server catalogs (Red Hat, partner, and community tiers) that describe tool-calling servers, and (3) Agent catalogs that describe agentic starter kits fetched from GitHub repositories. The final container image produced by this component is a minimal data-only image (based on `ubi9-minimal`) that packages the pre-generated catalog YAML files and benchmark data for consumption by the RHOAI dashboard and model registry.

The tool also includes a metadata-report CLI that analyzes catalog completeness, tracking data source provenance (YAML frontmatter, regex extraction, HuggingFace API, registry metadata) for each metadata field across all models.

## Architectural Analysis

The model-metadata-collection tool implements a sophisticated multi-stage metadata extraction and enrichment pipeline with a clear data prioritization hierarchy. The enrichment system follows a strict priority order: (1) HuggingFace YAML frontmatter (highest priority), (2) container modelcard.md content, (3) HuggingFace API data, (4) repository tags, and (5) generated fallbacks. This priority system is implemented through the `MetadataSource` type which tracks both values and their provenance (source field), enabling the enrichment.yaml files to provide full data lineage for each metadata field. The `enrichment.go` file at 604 lines is the most complex piece, orchestrating matching between OCI registry model names and HuggingFace model identifiers using a similarity scoring algorithm with a 0.5 threshold and a model family compatibility check that prevents cross-family matching (e.g., preventing a Llama container from matching a Granite HuggingFace entry).

The container image architecture is deliberately minimal -- the Dockerfile.konflux does not build Go binaries; it only copies pre-generated YAML catalogs and benchmark data into a `ubi9-minimal` base image that runs `sleep infinity`. This means the Go CLI tools execute only during CI/CD (via the `build-and-push-static-model-catalog-data.yml` workflow), and the shipped container is purely a data volume. Other components (dashboard, model registry) mount or copy data from this container at runtime. This pattern decouples the metadata generation pipeline from the serving infrastructure.

The tool handles three distinct catalog types that share infrastructure but have different data sources. Model catalogs derive from OCI container images in `registry.redhat.io` with enrichment from HuggingFace. MCP server catalogs derive from manually curated input YAML files in `input/mcp_servers/` with OCI enrichment for architecture and timestamp data. Agent catalogs derive from GitHub repositories (fetching `agent.yaml` files and READMEs), with support tier classification. Each catalog type has its own input index format, processing pipeline, and output format, but they share utility code for YAML marshaling, retry logic, and model name normalization.

Concurrent processing is a key architectural feature -- the model extraction pipeline processes multiple models in parallel using a semaphore-based concurrency limiter (default 5 goroutines). Each goroutine independently fetches the OCI manifest, reads container image layers searching for the `io.opendatahub.modelcar.layer.type: modelcard` annotation, extracts the model card from tar/gzip layers, parses metadata from the markdown content, and writes output files. The retry mechanism (`pkg/utils/retry.go`) provides exponential backoff with configurable limits for all registry and API operations, essential for dealing with rate limits and transient failures.

The tool-calling configuration support (`pkg/types/toolcalling.go`) demonstrates deep integration with the vLLM serving runtime. The system extracts tool-calling metadata (parser type, chat template paths, CLI args) from HuggingFace YAML frontmatter and transforms them for RHOAI deployment -- notably converting `examples/` paths to `opt/app-root/template/` paths to match the container filesystem layout used in RHOAI serving deployments. This path transformation is hard-coded and specific to the RHOAI deployment model.
