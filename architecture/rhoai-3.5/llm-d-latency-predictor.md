## Purpose

**Short**: Latency prediction service for the llm-d ecosystem that provides ML-based TTFT (Time To First Token) and TPOT (Time Per Output Token) latency predictions for LLM inference routing.

**Detailed**: The llm-d-latency-predictor is a dual-server architecture consisting of a training server and a prediction server. The training server ingests real-time request trace data (KV cache utilization, queue depth, input token length, prefix cache scores, tokens in flight) and trains online ML models (XGBoost, LightGBM, or Bayesian Ridge) using quantile or mean regression objectives. Trained models are serialized as joblib files and served over HTTP.

The prediction server periodically downloads trained models from the training server and serves low-latency TTFT/TPOT predictions via a FastAPI REST API. It supports single predictions, batch predictions, and a "strict" bulk mode optimized for high-throughput use cases (up to 10,000 requests per batch). The service employs a gated ensemble architecture that routes predictions through specialized sub-models based on queue state (noqueue vs. queued), improving accuracy for both idle and congested scenarios.

This component is part of the llm-d ecosystem and is designed to feed latency predictions into the Gateway API Inference Extension's routing decisions, enabling intelligent request routing to LLM inference pods based on predicted latency characteristics.

## Architectural Analysis

The llm-d-latency-predictor employs a clean separation of concerns between training and prediction workloads. The training server is a singleton (single replica) that accumulates request traces in a stratified bucketed sampling system -- samples are partitioned by queue depth, KV cache utilization, and prefix cache score into a 3D grid of bounded deques. This reservoir sampling approach prevents the training set from being dominated by any single operating regime while keeping memory usage bounded.

The prediction server is horizontally scalable (default 10 replicas) and deliberately stateless with respect to training data. Each replica runs an independent background sync thread that polls the training server for model updates every 10 seconds. Model downloads use a write-to-temp-then-atomic-replace pattern with joblib validation before swap, ensuring prediction pods never serve corrupt models. The checksum-based reload skip mechanism (`_file_checksum`) avoids redundant model reloads when the on-disk file hasn't changed, which is important in multi-worker (8 uvicorn workers per pod) configurations where only one worker wins the download race per cycle.

The gated ensemble architecture is a notable design decision. Rather than using a single model for all predictions, the system trains separate "noqueue" (queue_depth=0) and "queued" (queue_depth>0) sub-models for each metric (TTFT and TPOT). At prediction time, `num_request_waiting` is used as the gating signal. The rationale is that idle-server predictions and congested-server predictions have fundamentally different distributions -- an XGBoost tree that has to handle both regimes wastes splits on partitioning them. The ensemble is wrapped in `QueueGatedModel` instances that are atomically serialized/deserialized via joblib, keeping the sync protocol simple.

A significant security observation is that **no authentication or authorization exists on any endpoint**. Training data can be injected by any network-reachable caller, model files can be downloaded by anyone, and the `/flush` endpoint can wipe all training data without credentials. All inter-service communication is plaintext HTTP. The service relies entirely on network-level isolation (e.g., Kubernetes NetworkPolicies or platform-level controls) for security. This is a gap that should be addressed before production deployment -- at minimum, the training data ingestion and flush endpoints should be protected.

The Konflux Dockerfiles all use the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0`), pinned by SHA256 digest. The requirements are compiled with `uv pip compile --generate-hashes` from the RHEL AI Python Package Index, providing hermetic Python dependency resolution. RPM dependencies are also locked via `rpms.lock.yaml` (only `jq` for the test image). However, there is no Hermeto/cachi2 prefetch integration in the Dockerfiles, so the pip install step fetches packages at build time rather than from a pre-fetched cache.
