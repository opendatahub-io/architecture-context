## Purpose

**Short**: A Kubernetes controller that performs intelligent autoscaling for inference model servers based on GPU saturation, KV cache utilization, and queueing theory models.

**Detailed**: The Workload Variant Autoscaler (WVA) is a global autoscaler for LLM inference model servers deployed in Kubernetes. It works alongside standard Kubernetes HPA and external autoscalers like KEDA by emitting optimization metrics (e.g., `wva_desired_replicas`) to Prometheus, which HPA/KEDA then reads to drive the scale subresource of inference deployments.

WVA introduces the concept of **variants** — multiple model server configurations within an InferencePool that all serve the same base model but differ in hardware configuration (GPU type), serving configuration (tensor parallelism, max batch size, quantization), or role in a disaggregated pipeline (prefill vs decode). The controller continuously monitors request rates, KV cache utilization, and queue depths via Prometheus metrics, then applies pluggable scaling algorithms (V1 percentage-based, V2 token/capacity-based, queueing model, or throughput-based) to determine optimal replica counts while considering constraints such as GPU availability, energy budget, and performance SLOs.

The controller also supports scale-from-zero for idle models (detecting pending requests via EPP metrics), a coordinator plugin system for experimental features like GPU quota rebalancing across inference pools, and namespace-scoped configuration overrides for per-model tuning.

## Architectural Analysis

The Workload Variant Autoscaler is architecturally distinctive in that it does **not** directly scale workloads. Instead, it operates as a **metrics sidecar** to Kubernetes-native autoscalers (HPA and KEDA). WVA computes optimal replica counts and emits them as Prometheus metrics (`wva_desired_replicas`), which HPA or KEDA then reads via standard external metric sources. This design preserves the Kubernetes autoscaling control plane's stabilization, rate limiting, and status reporting while WVA focuses purely on the optimization decision logic. The sole exception is scale-from-zero, where WVA directly patches the scale subresource because HPA/KEDA cannot observe metrics from zero-replica deployments.

The **analyzer pipeline** is the core intellectual property. Three analyzer implementations compete or compose: (1) the legacy V1 percentage-based analyzer (deprecated), (2) the V2 token/capacity-based analyzer that models KV cache tokens as a finite resource with compute-bound (k2) and memory-bound (k1) constraints, and (3) a queueing model analyzer based on M/M/1 queueing theory that uses a Kalman filter to learn per-variant parameters (alpha, beta, gamma) online. A throughput analyzer based on ITL (inter-token latency) modeling provides an additional signal. Each analyzer produces a `VariantCapacity` struct containing `PerReplicaCapacity`, which feeds into either a `CostAwareOptimizer` (unlimited GPU mode) or a `GreedyByScoreOptimizer` (GPU-limited mode with fair-share allocation across models).

The **engine-aware metrics collection** system is notable. WVA dynamically detects whether model servers are vLLM or SGLang and registers different PromQL query templates for each engine's metric naming conventions (`vllm:*` vs `sglang/*`). The `SourceRegistry` pattern allows pluggable metrics sources — Prometheus API for aggregated queries and direct pod HTTP scraping for EPP (Endpoint Picker Proxy) metrics. A two-layer caching system (LRU cache with configurable TTL in the source layer + in-memory decision cache for controller-to-engine communication) minimizes Prometheus query load.

The **coordinator** represents an experimental extension point. While the main saturation engine handles `wva_desired_replicas`-consuming scalers, the coordinator discovers managed HPAs/ScaledObjects that do NOT use WVA's metrics and dispatches them to plugins. The `gpu-rebalance` plugin redistributes GPU quota across inference pools proportional to their queue depths by patching HPA `maxReplicas` or ScaledObject `maxReplicaCount`. This is gated behind `EXPERIMENTAL_COORDINATOR_ENABLED` and operates independently of the main optimization loop.

A significant architectural risk is the **cluster-wide RBAC surface**. The controller requires read access to nodes, pods, namespaces, and services cluster-wide for GPU inventory discovery and pod-to-variant attribution. The pod locator's ownership chain walk (Pod → ReplicaSet → Deployment → HPA/ScaledObject) requires broad `get/list/watch` permissions across multiple API groups. While this is necessary for the controller's function, it means a compromised controller pod could enumerate significant cluster state.
