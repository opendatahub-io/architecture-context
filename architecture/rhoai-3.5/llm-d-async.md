## Purpose

**Short**: Asynchronous dispatch processor that pulls batch inference requests from message queues and forwards them to llm-d-router (or another inference gateway), decoupling job submission from execution.

**Detailed**: The Async Processor (AP) is a composable component in the llm-d inference platform that enables efficient processing of latency-insensitive workloads. It consumes requests from message queues (Redis Pub/Sub, Redis Sorted Set, or GCP Pub/Sub), applies capacity-aware dispatch gating to avoid overwhelming backend inference servers, and forwards requests to the inference gateway (llm-d-router). This allows users to run batch workloads such as bulk summarizations, product classification, and sentiment analysis without impacting real-time serving traffic.

The processor implements a sophisticated flow control system with multiple gate types (Prometheus-based saturation/budget gates, Redis-based dispatch/quota gates, local concurrency gates, and endpoint-scrape gates) that can be composed per-queue or per-worker-pool. It supports configurable request merge policies (random-robin, tier-priority with 6-level priority scheduling) for multi-queue deployments. Results are published back to the message queue for consumer retrieval. The system is designed around the "Bring Your Own Queue" (BYOQ) principle, keeping all prioritization, routing, retries, and scaling logic decoupled from the queue implementation.

## Architectural Analysis

The llm-d-async processor is a well-structured Go service that follows the "Bring Your Own Queue" (BYOQ) principle. The architecture cleanly separates concerns into four Go modules: `api/` (message types and contracts), `pipeline/` (flow control abstractions), `producer/` (client SDK), and the root module (server, workers, queue implementations). This modular design allows the producer SDK to be imported independently by client applications without pulling in the full server dependency graph.

The flow control system is the most architecturally significant subsystem. The `GateFactory` (in `pkg/async/inference/flowcontrol/gate_factory.go`, 601 lines) acts as a strategy router that creates gate instances from JSON configuration. Gates are composable -- the `composite` type chains multiple gates with minimum-budget semantics, and the `wait-on-refuse` decorator converts rejection into parking. The `CascadeMetricSource` provides graceful degradation by falling back from EPP metrics to vLLM metrics when the primary source is unavailable. The `CachedMetricSource` reduces Prometheus load with a configurable TTL (default 5 seconds). This layered approach means the processor can operate in environments ranging from fully-instrumented (EPP + Prometheus) to minimal (direct endpoint scrape without a Prometheus server).

The multi-queue architecture supports sophisticated workload prioritization. The `tier-priority` merge policy implements a 6-level priority scheduler (3 tiers × 2 classifications) using condition variables and mutex-protected buckets. Combined with the `tier-priority-admission` gate (which drops overflow-interactive requests with 429 while deferring reserved requests), this enables differentiated service levels within a single processor instance. The alternative `random-robin` policy uses `reflect.Select()` for fair multiplexing across queues, which is simpler but does not differentiate by priority.

From a security perspective, the processor is FIPS-compliant at build time (`GOEXPERIMENT=strictfipsruntime`, `CGO_ENABLED=1` in `Dockerfile.konflux`) and uses `tls.VersionTLS12` as the minimum TLS version. The `InsecureSkipVerify` option exists but is explicitly documented as "dev/test only." Redis credentials are properly handled through Kubernetes Secrets (never stored in Helm values for production), and the `--redis.url` flag is redacted in startup logs. The processor runs as non-root (UID 1001) with a read-only root filesystem and dropped capabilities. However, the Helm chart does not include NetworkPolicy resources, so network-level isolation between the processor and other workloads must be configured externally.

The retry system uses exponential backoff via Redis sorted sets. Failed requests are re-enqueued with a score of `now + backoff_duration`, and a polling worker dequeues them when their score falls below the current timestamp. The sorted set implementation also supports request cancellation through a token-based mechanism: each request gets a random 16-byte token stored in `request-active:{ID}`, and cancellation is signaled by writing the token to `request-cancel:{ID}`. This is a best-effort mechanism -- a request already in-flight cannot be aborted, but it will not be retried.
