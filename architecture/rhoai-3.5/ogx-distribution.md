## Purpose

**Short**: Containerized distribution of OGX (formerly Llama Stack) providing a multi-provider AI/ML inference, agent, and RAG server for RHOAI.

**Detailed**: The ogx-distribution repository produces a multi-architecture (amd64, arm64, ppc64le) container image that packages the OGX server with pre-configured providers for inference (vLLM, Bedrock, WatsonX, Azure, Vertex AI, OpenAI, Gemini, Anthropic), vector storage (Milvus, pgvector, Qdrant, FAISS), file processing (docling, pypdf, markitdown), tool runtime (Brave Search, Tavily Search, file-search, MCP), and the Responses/Messages/Batches APIs. The image ships with pre-fetched ML model artifacts (Granite embedding model, docling layout models, RapidOCR models, tiktoken tokenizer data) and uses PostgreSQL as its persistent storage backend for both key-value and SQL stores.

The repository contains no application source code -- it is a distribution packaging project. The OGX server itself comes from the `opendatahub-io/ogx` fork (version v1.2.1+rhaiv.0) and is installed as a Python package. The repo's value lies in its build pipeline: Python scripts that generate the distribution configuration (`config.yaml`) from a master `build.yaml`, compile pinned lock files with hashes for hermetic builds, generate the Containerfile with embedded OCI labels, verify secret environment variable sync, and produce documentation. Pre-commit hooks enforce that all auto-generated artifacts stay in sync.

For RHOAI, the downstream Konflux build uses the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu:3.5.0`), installs Python dependencies from the RHEL AI Package Index via Hermeto (cachi2) prefetch, and copies pre-fetched model artifacts from the Hermeto generic cache. The image exposes the OGX HTTP API on port 8321 and supports optional OAuth2 token authentication with JWKS validation.

## Architectural Analysis

The ogx-distribution repository represents an interesting architectural pattern: a **distribution-only packaging project** that contains zero application source code. The OGX server framework is consumed as a pip package (`ogx==v1.2.1+rhaiv.0`), and this repo's entire value proposition is the packaging layer -- configuration generation, dependency pinning, model artifact pre-fetching, and container image construction. This separation of concerns is clean but means that application-level security analysis (e.g., FIPS crypto behavior, input validation, injection vulnerabilities) must be performed against the upstream `opendatahub-io/ogx` repository, not this one.

The **provider activation pattern** is architecturally notable. The `build.yaml` defines all possible providers (31 providers across 8 API categories), but the runtime `config.yaml` strips 7 "dependency-only" providers (sentence-transformers, milvus-inline, faiss, docling, markitdown, pypdf, docling-serve). The remaining providers use conditional `${env.VAR:+name}` syntax that evaluates at OGX startup time: if the env var is set, the provider activates; if unset, it is silently skipped. This means a single container image serves all deployment scenarios -- from a minimal setup with just vLLM to a full-featured deployment with multiple cloud providers, vector databases, and search tools. The trade-off is container image size: all dependencies for all providers are pre-installed regardless of which are activated.

The **build pipeline** is heavily automated via pre-commit hooks and Python code generation. The chain is: `build/build.yaml` (source of truth) → `build/gen_config.py` (strips dependency-only providers) → `distribution/config.yaml` → `build/gen_containerfile.py` (embeds config as base64 OCI label) → `Containerfile`. Lock files are generated separately via `build/gen_lockfile.py` which creates temp venvs, runs `ogx stack list-deps` to discover transitive dependencies, runs `opentelemetry-bootstrap` for auto-instrumentation packages, then compiles everything with `uv pip compile --generate-hashes`. The `build/verify_secrets.py` script enforces that every secret field in `build.yaml` has a corresponding `_FILE` variant in `entrypoint.sh`, preventing secret handling regressions. This level of automation is excellent for maintainability but creates a fragile dependency chain -- a bug in any generator script cascades through all generated files.

The **security model** has a significant gap: the entrypoint.sh always passes `--insecure` to the OGX server, even when AUTH_ISSUER is set. The `--insecure` flag may disable TLS at the application level (the server binds plaintext HTTP on port 8321), relying entirely on the platform's ingress infrastructure (kube-rbac-proxy sidecar, Gateway API with TLS termination) for transport security. This is a defensible architecture on RHOAI where the platform provides these layers, but it means the OGX container itself never handles TLS, making it vulnerable in non-standard deployment scenarios (e.g., direct port-forward access, network-adjacent attackers within the cluster). The `_FILE` secret resolution pattern in the entrypoint is a positive security feature that avoids exposing credentials in `/proc/1/environ`.

The **artifact pre-fetching** mechanism (`distribution/artifacts.lock.yaml` + `distribution/fetch_artifacts.py` + `distribution/copy-artifacts.sh`) is a well-designed supply chain control. Each artifact has a SHA-256 checksum, download URL, and deterministic cache path. In Konflux hermetic builds, Hermeto deposits these at `/cachi2/output/deps/generic`; in standard builds, `fetch_artifacts.py` downloads them with checksum verification. The artifacts include the Granite embedding model (125M parameters), docling layout models, RapidOCR models, and tiktoken tokenizer data.
