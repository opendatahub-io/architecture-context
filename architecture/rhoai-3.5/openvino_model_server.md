## Purpose

**Short**: High-performance C++ inference server that hosts AI models and exposes them via gRPC and REST APIs compatible with KServe, TensorFlow Serving, and OpenAI protocols.

**Detailed**: OpenVINO Model Server (OVMS) is an Intel-developed inference serving system that enables remote AI model inference over standard network protocols. It is built in C++ for maximum performance and optimized for Intel hardware architectures. The server supports multiple inference APIs -- KServe (v2 inference protocol), TensorFlow Serving (v1), and OpenAI-compatible chat/completions -- allowing clients in any programming language to run inference remotely.

OVMS supports a wide variety of AI workloads including traditional model inference, large language model text generation with continuous batching and streaming, text embeddings generation, document reranking, image generation (Stable Diffusion/FLUX), speech-to-text transcription, and text-to-speech synthesis. Models can be loaded from local storage, Amazon S3, Azure Blob Storage, Google Cloud Storage, or pulled directly from HuggingFace Hub.

Within the RHOAI platform, OVMS serves as the primary inference runtime for Intel-optimized model serving. It is deployed as a container managed by KServe's InferenceService controller, running as a model server pod that receives inference requests through the platform's ingress infrastructure. The server integrates MediaPipe for graph-based pipeline composition and supports Python custom nodes for extensible processing workflows.

## Architectural Analysis

OVMS is a monolithic C++ inference server designed for high throughput and low latency. Its architecture follows a modular plugin pattern: a core server hosts gRPC and HTTP frontends, while specialized AI capabilities (LLM, embeddings, reranking, image generation, audio) are implemented as MediaPipe calculator plugins. This design allows new inference modalities to be added without modifying the core serving infrastructure. The MediaPipe integration provides a graph-based execution model where processing nodes can be composed into pipelines with configurable side packets -- for example, the LLM pipeline chains request parsing, tokenization, continuous batching inference, and streaming response serialization as graph nodes.

The server's API surface has evolved from TensorFlow Serving compatibility (v1 API) through KServe inference protocol (v2 API) to a modern v3 API that provides OpenAI-compatible endpoints for chat completions, completions, embeddings, reranking, image generation, and audio transcription. The v3 API is where authentication (optional API key bearer tokens) and CORS support are enforced at the application level. The v1/v2 APIs have no application-level authentication, relying entirely on infrastructure-level enforcement via kube-rbac-proxy sidecars or service mesh. This mixed authentication model means security depends heavily on proper platform deployment configuration.

A notable architectural choice is that OVMS does not terminate TLS at any endpoint. Both the gRPC frontend (using `InsecureServerCredentials`) and the Drogon HTTP frontend operate in plaintext mode. The nginx-mtls-auth extra (in `extras/nginx-mtls-auth/`) provides a separately-built nginx wrapper for mTLS but is not part of the standard RHOAI deployment. This design delegates all transport security to the platform infrastructure -- Envoy Gateway for ingress TLS, kube-rbac-proxy for component auth, and Istio for pod-to-pod mTLS. While architecturally sound for a platform-managed service, it means OVMS is completely unprotected if deployed without these infrastructure layers.

The build system uses Bazel for C++ compilation with OpenVINO built from source (pinned git SHA `c01cd93e24d1cd78bfbb401eed51c08fb93e0816` on the `opendatahub-io/openvino` fork). The Konflux build configuration enables LTO (Link Time Optimization) with `-flto=auto -ffat-lto-objects -march=haswell`, targeting Haswell and newer Intel CPUs. The build produces two main artifacts: the `ovms` binary (with MediaPipe and Python support enabled) and the `libovms_shared.so` C API library (with MediaPipe and Python disabled). The CAPI library enables embedding OVMS inference capabilities directly in other applications without network overhead. The build requires 8+ hours in Konflux due to compiling OpenVINO from source, making it one of the most resource-intensive builds in the RHOAI platform.

The filesystem abstraction layer (`src/filesystem/`) supports four storage backends -- local filesystem, S3, Azure Blob Storage, and Google Cloud Storage -- auto-selected by URL prefix (`s3://`, `az://`/`abfs://`, `gs://`). Model repositories can be configured to poll for updates at configurable intervals (default 1000ms), enabling hot-reloading of model versions without server restart. The server also supports direct HuggingFace Hub integration for model download and export via optimum-intel, with support for GGUF model format.
