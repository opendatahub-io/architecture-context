## Purpose

**Short**: Kubeflow Pipelines (KFP) v2 backend providing ML pipeline orchestration, scheduling, artifact management, and metadata tracking for Red Hat OpenShift AI.

**Detailed**: Data Science Pipelines is the RHOAI distribution of Kubeflow Pipelines v2. It provides an end-to-end ML pipeline orchestration platform that enables users to define, compile, schedule, and execute multi-step ML workflows on Kubernetes. The system compiles pipeline definitions into Argo Workflows, manages pipeline versions and artifacts via an API server backed by a relational database and S3-compatible object storage, and tracks execution metadata through ML Metadata (MLMD).

The repository produces five distinct container images: the API server (central REST/gRPC service for pipeline and run management), the driver (DAG orchestration within Argo Workflow pods), the launcher (user container execution with artifact I/O), the persistence agent (syncs workflow status back to the API server), and the scheduled workflow controller (manages cron/periodic pipeline schedules). Each image is built via Konflux with FIPS-compliant Go crypto using GOFIPS140. The component is deployed by the Data Science Pipelines Application (DSPA) operator, which is managed by the rhods-operator platform operator.

The rebase process merges upstream Kubeflow Pipelines tags into the opendatahub-io fork, then carries Red Hat-specific patches (FIPS, UBI base images, Konflux build configs, MLflow integration) downstream to the red-hat-data-services organization for RHOAI releases.

## Architectural Analysis

Data Science Pipelines follows a disaggregated architecture where the API server acts as the central control plane, while pipeline execution is fully delegated to Argo Workflows with two specialized sidecar-style components (driver and launcher) injected into each workflow step. This separation means the API server never directly executes user code — it compiles pipeline IR to Argo Workflow CRDs and manages lifecycle state through the persistence agent's informer-based sync loop. The driver/launcher split mirrors a sidecar pattern but runs as sequential Argo steps: the driver resolves DAG topology, evaluates CEL conditions, and generates pod spec patches, while the launcher handles the actual container execution with artifact I/O.

The FIPS strategy is notable for its heterogeneity across sub-components. The API server uses CGO_ENABLED=1 with GOFIPS140=v1.0.0, allowing dynamic linking against OpenSSL — the standard pattern for check-payload compliance. However, the driver, launcher, persistence agent, and scheduled workflow controller use CGO_ENABLED=0 (static linking) with the same GOFIPS140=v1.0.0 flag plus the `no_openssl` build tag. This relies on Go 1.24+'s native FIPS 140 module, which provides FIPS-validated cryptography without requiring OpenSSL or dynamic linking. This is a valid FIPS approach for Go 1.24+ but is newer than the traditional CGO/OpenSSL pattern and may need verification against check-payload's current validation rules.

The authentication model has a significant gap between single-user and multi-user modes. In single-user mode (the default), there is no authentication or authorization — all API requests are treated as anonymous. Multi-user mode adds HTTP header-based user identification and Kubernetes SubjectAccessReview authorization, but the transition is a deployment-time configuration rather than a gradual capability. The projected ServiceAccount token pattern used by the persistence agent and scheduled workflow controller (with `audience: pipelines.kubeflow.org` and 3600s expiry) is well-designed — it avoids long-lived secrets and integrates with Kubernetes token rotation.

The database schema is shared across tenants in multi-user mode, with isolation enforced at the application layer through namespace-column filtering in SQL queries. This is a common pattern but creates a risk surface — a bug in query construction could leak cross-tenant data. The same applies to object store isolation, which relies on path-prefix conventions rather than bucket-level or IAM-level tenant boundaries. In RHOAI deployments, the DSPA operator mitigates this by deploying per-namespace DSP instances, each with its own database and object store, effectively converting the shared-database design into a per-tenant deployment model.

The cache server webhook intercepts pod creation to inject caching metadata, operating as a Kubernetes MutatingAdmissionWebhook on port 443→8443 with TLS from the `webhook-server-tls` Secret. The PipelineVersion webhooks (validating and mutating) run on the API server itself (port 8443) and enforce spec immutability, label injection, and owner-reference management — ensuring that Pipeline→PipelineVersion ownership chains support cascading deletes.
