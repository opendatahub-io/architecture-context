## Purpose

**Short**: ML Metadata (MLMD) is a gRPC server and Python client library for recording and retrieving metadata associated with ML workflows, including artifacts, executions, contexts, and their lineage relationships.

**Detailed**: ML Metadata provides a metadata store service that tracks the full lifecycle of ML pipeline components. It manages three core entity types -- Artifacts (datasets, models, metrics), Executions (training runs, transformations, evaluations), and Contexts (pipelines, experiments, sessions) -- along with the relationships between them (Events linking Artifacts to Executions, Attributions linking Artifacts to Contexts, Associations linking Executions to Contexts, and hierarchical Parent-Child Context relationships).

The server exposes a comprehensive gRPC API (`MetadataStoreService`) with ~45 RPC methods for CRUD operations on these entities and their relationships, plus lineage graph traversal capabilities. It supports multiple backend databases: MySQL, PostgreSQL, and SQLite (including an in-memory fake database for testing). The C++ gRPC server binary is built from source using Bazel 5 and deployed as a container image (`odh-mlmd-grpc-server`) on Red Hat UBI 9 minimal.

In the RHOAI platform, MLMD serves as the metadata backbone for ML Pipelines (Kubeflow Pipelines), storing pipeline run metadata, artifact provenance, and execution history. The Python client library (`ml-metadata` PyPI package) provides a high-level API consumed by pipeline orchestrators and components.

## Architectural Analysis

ML Metadata is a Google-originated library that serves as the metadata backbone for ML pipeline systems. The Red Hat downstream fork (`red-hat-data-services/ml-metadata`) is a thin downstream layer focused almost entirely on containerization and CI/CD integration -- the core C++ and Python code remains unchanged from upstream. The downstream modifications consist of Red Hat-specific Dockerfiles (`Dockerfile.redhat`, `Dockerfile.konflux`, `Dockerfile.fedora`), Tekton pipeline configurations for Konflux, and a ZetaSQL version patch for UBI9 compatibility.

The architecture follows a clean separation between the storage layer and the API layer. The `MetadataStore` C++ class provides the core business logic, while `MetadataStoreServiceImpl` wraps it as a gRPC service. The storage abstraction (`MetadataSource`) supports pluggable backends through concrete implementations: `MySQLMetadataSource`, `PostgreSQLMetadataSource`, and `SqliteMetadataSource`. Each backend has its own SQL query configuration (`MetadataSourceQueryConfig`) with templated queries, enabling dialect-specific SQL while maintaining a unified API. Schema migration is built-in via `MigrationOptions`, supporting both upgrade and downgrade migrations across schema versions.

The Python client library provides two access modes: a gRPC client mode (connecting to the standalone server) and an embedded mode using pybind11 C++ extensions (`metadata_store_extension`). The embedded mode bypasses the network stack entirely, linking directly against the C++ metadata store library. This dual-mode architecture allows the same Python API to work both as a remote client and as an in-process library, which is particularly useful for testing and local development.

The Konflux container image (`Dockerfile.konflux`) builds the C++ server binary on UBI9 using Bazel 5 with the Galileo COPR repository, then produces a minimal runtime image on UBI9-minimal containing only the server binary, MariaDB connector third-party notices, and the `tzdata` package (required by ZetaSQL timezone operations). The server runs as non-root user 65534:65534. The build is explicitly non-hermetic (`hermetic: false` in the Tekton PipelineRun), meaning Bazel fetches dependencies from the internet during build. This is a notable supply chain gap compared to hermetic Konflux builds that use cachi2/Hermeto prefetching. The multi-arch build targets `amd64`, `arm64`, and `ppc64le`.

A security consideration is that the MLMD server has no built-in application-level authentication or authorization beyond optional mTLS. All clients that can reach the gRPC port have full read/write access to the entire metadata store. In production RHOAI deployments, the platform operator typically fronts this service with network policies or auth proxies. The database connection supports SSL/TLS with full certificate chain configuration for both MySQL (cert, key, CA, CA path, cipher, verify_server_cert) and PostgreSQL (sslmode, sslcert, sslkey, sslpassword, sslrootcert), but these are optional and disabled by default.
