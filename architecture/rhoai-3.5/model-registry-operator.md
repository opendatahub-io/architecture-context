## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Model Registry and Model Catalog instances, deploying and configuring the model registry REST service, authentication proxies, database backends, and network exposure for the RHOAI platform.

**Detailed**: The Model Registry Operator is a controller-runtime-based Kubernetes operator that watches `ModelRegistry` custom resources (CRD group `modelregistry.opendatahub.io`) and reconciles the full deployment stack for each instance. For every ModelRegistry CR, the operator creates a Deployment running the model-registry REST service container, optionally paired with a kube-rbac-proxy sidecar for authentication. It also provisions the associated Service, ServiceAccount, RBAC Role/RoleBinding, NetworkPolicy, and OpenShift Route or Gateway API HTTPRoute for external access.

The operator has two primary controllers: the **ModelRegistryReconciler** which manages per-instance model registry deployments, and the **ModelCatalogReconciler** which manages a single shared model catalog instance (including its PostgreSQL database, catalog data ConfigMaps, and kube-rbac-proxy authentication). The operator supports both PostgreSQL and MySQL backends for model registries, with an option to auto-provision a PostgreSQL deployment for simple setups. It includes webhook-based defaulting and validation, CRD version conversion (v1alpha1 ↔ v1beta1), and automated storage version migration.

The operator detects cluster capabilities at startup to adapt its behavior: on OpenShift it creates Routes, Groups, and uses the cluster TLS security profile; on plain Kubernetes it operates with reduced features. It supports the RHOAI 3.x Data Science Gateway pattern by creating HTTPRoutes referencing the platform's shared Gateway, and it includes an automatic migration path from OAuth proxy to kube-rbac-proxy authentication.

## Architectural Analysis

The Model Registry Operator follows a mature kubebuilder-based design with two distinct reconciliation domains: per-instance model registries and a singleton model catalog. The dual-controller architecture is noteworthy because the catalog controller uses a fixed-key reconciliation pattern (all watched resources map to a single reconcile request via `mapToFixedCatalogRequest`) to prevent reconcile storms from multiple ConfigMap or RBAC changes. This is a deliberate design choice documented in the code that provides workqueue deduplication.

The operator employs a sophisticated template-based resource generation system. All Kubernetes resources (Deployments, Services, Routes, NetworkPolicies, etc.) are defined as Go templates in `internal/controller/config/templates/` and rendered at reconcile time with registry-specific parameters. This approach keeps the resource definitions declarative while supporting conditional features (kube-rbac-proxy sidecars, database SSL, Gateway API). The templates are embedded via `go:embed` and parsed once at startup. Resource updates use `k8s-objectmatcher` for patch calculation, avoiding unnecessary API calls when resources haven't changed.

The authentication architecture has undergone a significant migration from OAuth proxy to kube-rbac-proxy. The operator includes automatic migration logic: existing ModelRegistry CRs with OAuthProxy config are transparently converted to KubeRBACProxy during reconciliation (lines 186-209 of `modelregistry_controller.go`) and via the defaulting webhook. On OpenShift, registries without any auth proxy configured are automatically defaulted to kube-rbac-proxy. The kube-rbac-proxy sidecar performs SubjectAccessReview authorization checking for `get` access on the registry's Service resource, providing Kubernetes-native RBAC integration. The operator also supports BYOIDC (Bring Your Own Identity Provider) mode on OpenShift 4.20+, where it skips creating `user.openshift.io/v1/Group` resources and instead references external IdP groups in RoleBindings.

The networking architecture supports three access modes simultaneously: (1) direct ClusterIP Service access within the cluster, (2) OpenShift Route with TLS reencrypt for external HTTPS access, and (3) Gateway API HTTPRoutes referencing the platform's shared `data-science-gateway` for the RHOAI 3.x ingress pattern. The operator creates cross-namespace ReferenceGrants to allow HTTPRoutes in the platform namespace to reference Services in the registry namespace. All three modes can coexist — the Route is maintained alongside HTTPRoutes for backward compatibility.

The TLS security implementation is thorough: the operator fetches the OpenShift cluster TLS security profile at startup and applies it to both the webhook server and metrics server. A SecurityProfileWatcher continuously monitors for profile changes and triggers a graceful restart when the TLS configuration changes. This ensures the operator always respects cluster-wide TLS policy, including cipher suite restrictions and minimum version requirements.
