## Purpose

**Short**: FIPS-compliant authentication reverse proxy that handles OIDC and OpenShift OAuth authentication for RHOAI component sidecars, serving as a drop-in replacement for oauth-proxy.

**Detailed**: kube-auth-proxy is a focused authentication proxy derived from the oauth2-proxy project, streamlined to support only the two authentication methods required by Red Hat OpenShift AI: external OIDC providers and OpenShift's internal OAuth service. All other providers (Google, GitHub, Azure, etc.) have been intentionally removed to reduce the attack surface and maintenance burden.

The proxy runs as a sidecar container alongside RHOAI component pods, intercepting incoming requests and authenticating users before forwarding traffic to the upstream application. It supports multiple session stores (cookies or Redis), configurable header injection for passing user identity to upstreams, and an `ext_authz`-compatible `/auth` endpoint for use with Envoy's external authorization framework. The proxy also supports Kubernetes service account token validation via the TokenReview API, enabling machine-to-machine authentication alongside user-facing OIDC/OAuth flows.

A key design requirement is FIPS compliance -- the proxy is built with `GOEXPERIMENT=strictfipsruntime` and `CGO_ENABLED=1` to ensure all cryptographic operations use OpenSSL rather than Go's native crypto. It also includes an MLflow-specific auth deny handler that returns structured JSON error responses to guide MLflow Python clients toward proper Kubernetes-native authentication.

## Architectural Analysis

kube-auth-proxy implements a middleware chain architecture derived from oauth2-proxy, using the `alice` library for composable HTTP middleware. The authentication flow is layered: Kubernetes ServiceAccount token validation runs first (via the TokenReview API), followed by JWT bearer token verification for OIDC, then OAuth sha256~ token validation for OpenShift, and finally stored session loading from cookies or Redis. This ordering ensures that machine-to-machine (SA token) auth is attempted before falling back to user-facing session auth, with each layer passing through to the next if it cannot authenticate the request. The chain is critical for ext_authz integration -- the `/oauth2/auth` endpoint must handle both human users (with session cookies) and service accounts (with bearer tokens) in a single request path.

The OpenShift OAuth provider is the most complex component, implementing auto-detection of ServiceAccount credentials from the pod's mounted service account files (`/var/run/secrets/kubernetes.io/serviceaccount/`). It constructs a client ID from the namespace and SA name, discovers OAuth endpoints dynamically from `.well-known/oauth-authorization-server`, and manages a cached pool of HTTP clients keyed by CA configuration. The provider also handles sign-out by deleting the OAuthAccessToken resource from the cluster -- mirroring the behavior of the OpenShift web console. This delete operation runs asynchronously in a goroutine to avoid blocking the logout response.

A notable design choice is the MLflow-specific auth deny handler (`pkg/authdeny/mlflow.go`), which detects requests from the MLflow Python client via User-Agent header inspection and returns structured JSON error responses guiding users toward Kubernetes-native authentication (`oc login`, `MLFLOW_TRACKING_AUTH=kubernetes-namespaced`). This is an application-specific integration point that wouldn't exist in generic oauth2-proxy -- it reflects RHOAI's need to support ML workloads that use client libraries with their own authentication expectations.

Session management supports distributed deployments through Redis with Sentinel or Cluster modes, including a distributed lock mechanism for session refresh. When multiple proxy instances share a Redis-backed session store, only one instance refreshes a session at a time (5-second lock timeout, 2-second hold duration, 10ms retry period). Cookie-based sessions use AES-GCM (authenticated encryption) or AES-CFB encryption with HMAC signing, and automatically split large sessions across multiple cookies (4000-byte limit per cookie to stay under browser limits). The proxy supports session cookie minimization mode (`--session-cookie-minimal`) that strips access/ID/refresh tokens from cookies to reduce size -- useful when only the session identity matters and token-based operations are not needed.

The FIPS compliance architecture is straightforward but critical: the Dockerfile.konflux builds with `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime` on a UBI9 Go toolset base image, ensuring all Go crypto operations delegate to OpenSSL rather than Go's native crypto. The application code itself uses `crypto/tls` with a minimum version of TLS 1.2 and configurable cipher suites. No weak cryptographic algorithms (MD5, RC4, DES) are used anywhere in the codebase. The only potential FIPS concern is the configurable `--ssl-insecure-skip-verify` flag, which disables TLS certificate verification -- this is a deliberate escape hatch for development/testing and defaults to `false`.
