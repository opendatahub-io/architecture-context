## Purpose

**Short**: Module operator that manages the lifecycle of the upstream Feast (Feature Store) operator within the OpenDataHub/RHOAI platform.

**Detailed**: The Feast Module Operator is a Kubernetes operator that follows the ODH "module operator" pattern -- a lightweight wrapper that deploys and manages a third-party operator (in this case, the upstream Feast operator from feast-dev/feast) as a component of the OpenDataHub or RHOAI platform. It does not directly manage FeatureStore custom resources; instead, it deploys the upstream feast-operator Deployment, CRDs, RBAC, and ServiceMonitor resources via kustomize manifests, and the upstream feast-operator then handles FeatureStore CR reconciliation.

The operator watches a single cluster-scoped `FeastOperator` CR (singleton named `default-feastoperator`) and reconciles the upstream feast-operator's deployment manifests using the ODH kustomize rendering pipeline. It supports platform version handshakes with the parent platform operator via a ConfigMap (`odh-feastoperator-config`), OIDC issuer URL injection for external identity providers, deployment selector migration for upgrades, and semantic-versioned upgrade gates.

The operator is deployed either via Helm chart (standalone) or via the platform operator (opendatahub-operator/rhods-operator) which creates the `FeastOperator` CR. The module operator pattern decouples the Feast component lifecycle from the monolithic platform operator, enabling independent versioning and release cadence.

## Architectural Analysis

The Feast Module Operator exemplifies the ODH "module operator" pattern -- a thin reconciliation wrapper that decomposes what was previously a monolithic platform operator into independently deployable, independently versioned components. The operator itself contains minimal domain logic; its primary function is to render and apply kustomize manifests that deploy the upstream feast-operator, while providing platform integration points (version handshake, OIDC injection, upgrade migration).

The reconciliation pipeline follows the ODH framework's action chain pattern: `initialize → upgradeIfNeeded → setKustomizedParams → releases → reconcilePlatformVersion → kustomize.Render → migrateDeploymentSelector → deploy → deployments.Status → gc.Action`. Each action is a discrete step with single responsibility. The `migrateDeploymentSelector` action is particularly noteworthy -- it handles the case where the upstream feast-operator changed its Deployment's `spec.selector.matchLabels` between versions, which is an immutable field in Kubernetes. The operator detects the stale selector and deletes the Deployment so it can be recreated with the correct selector, complemented by a Job-based migration in the RHOAI overlay for robustness.

The platform version handshake mechanism (`reconcilePlatformVersion`) reads a `platformVersion` from the `odh-feastoperator-config` ConfigMap written by the parent platform operator. When the version changes, the module operator runs upgrade logic (currently a no-op stub) and records the acknowledged version in the FeastOperator CR's `status.releases` list. This enables coordinated platform-wide upgrades where the platform operator can gate further actions on module acknowledgment.

The operator's RBAC footprint is notably broad -- it inherits permissions needed by the upstream feast-operator (pods/exec, PVCs, Routes, HPA, PDB, CronJobs) because it deploys and manages those resources. This is a design trade-off of the module operator pattern: the module operator needs permissions to create the RBAC resources that the upstream feast-operator will use, resulting in a high-privilege ClusterRole. The finalizer cleanup (`cleanupClusterResources`) handles cluster-scoped resource deletion (ClusterRoles, ClusterRoleBindings) that cannot use ownerReferences for garbage collection, preventing orphaned RBAC resources on FeastOperator CR deletion.

The Helm chart generation (`chartgen` subcommand) is a build-time tool, not a runtime component. It reads kustomize build output from stdin and produces a Helm chart with templated values for image references, replicas, namespace, and resource limits. This dual deployment model (kustomize via platform operator + Helm for standalone) enables both integrated platform deployment and independent testing/development.
