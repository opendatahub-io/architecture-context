## Purpose

**Short**: KubeRay is a Kubernetes operator that manages the lifecycle of Ray clusters, jobs, services, and scheduled cron jobs on OpenShift / RHOAI.

**Detailed**: KubeRay provides four Custom Resource Definitions — RayCluster, RayJob, RayService, and RayCronJob — that enable users to deploy and manage Ray-based distributed computing workloads on Kubernetes. The operator handles head and worker pod orchestration, service creation, autoscaling, batch scheduling integration (Volcano, Yunikorn, Kai-scheduler, scheduler-plugins), and GCS fault tolerance with Redis.

On RHOAI / OpenShift, the operator adds authentication via kube-rbac-proxy sidecars injected into Ray head pods, Gateway API HTTPRoutes for dashboard access, mTLS certificate management through cert-manager, and NetworkPolicy creation for workload isolation. A mutating webhook enforces OpenShift-specific security defaults by enabling the secure trusted network annotation and disabling raw Ingress in favour of Gateway API. The operator also integrates with OpenShift's cluster-wide TLS security profiles to align cipher suites and minimum TLS versions with platform policy.

## Architectural Analysis

The KubeRay operator follows a modular controller architecture where the primary RayCluster controller handles core lifecycle (pods, services, RBAC) while specialized satellite controllers — authentication, mTLS, and NetworkPolicy — extend functionality through annotation-gated activation. This design allows features like mTLS and network isolation to be opt-in without adding complexity to the core reconciliation loop. The controllers coordinate through Kubernetes objects rather than direct function calls, which provides clean separation of concerns at the cost of slightly delayed convergence (multiple reconciliation cycles may be needed for all resources to reach desired state).

The authentication architecture on OpenShift represents a significant RHOAI-specific enhancement. The mutating webhook is the critical entry point: it forces `enableIngress: false` and sets the secure trusted network annotation on every RayCluster, which disables direct Ingress/Route access and activates the authentication controller. The authentication controller then creates an HTTPRoute in the platform namespace (using a ReferenceGrant to allow cross-namespace Service references) that routes through the platform Gateway to a kube-rbac-proxy sidecar injected into the head pod. This ensures all external dashboard access goes through OIDC/OAuth validation via Kubernetes TokenReview and SubjectAccessReview. The path scheme `/ray/{namespace}/{cluster}/` with URL rewriting provides namespace-scoped access control inherent in the URL structure.

The RayService controller's incremental upgrade strategy (alpha feature) leverages Gateway API HTTPRoutes with weighted backends to implement canary-style traffic migration between active and pending RayCluster instances. The `stepSizePercent` and `intervalSeconds` fields allow fine-grained control over traffic shifting. During upgrades, the HTTPRoute is updated to include two backends (active and pending serve services), and traffic is gradually shifted by adjusting weights. This is architecturally distinct from the simpler NewCluster strategy which performs a hard cutover.

The operator's TLS handling is noteworthy for its integration with OpenShift's cluster-wide TLS security profile. At startup, the operator reads the `apiservers.config.openshift.io/cluster` resource to determine the active TLS profile (Intermediate, Modern, Old, or Custom) and configures both the webhook server and its own HTTP clients accordingly. The fallback to Intermediate (TLS 1.2+ with modern cipher suites) on non-OpenShift clusters ensures reasonable defaults. The ALPN configuration (`h2`, `http/1.1`) enables HTTP/2 connections where supported.

Build hermeticity shows a gap at the RPM and artifact layers. While Go dependencies are locked via `go.sum`, there is no `rpms.lock.yaml` for OS packages and no Hermeto/cachi2 prefetch integration in the Konflux Dockerfile. The Dockerfile uses digest-pinned base images (`ubi9/go-toolset@sha256:...` and `ubi9/ubi-minimal@sha256:...`), which provides image-level reproducibility, but individual RPM versions within those base images are not locked.
