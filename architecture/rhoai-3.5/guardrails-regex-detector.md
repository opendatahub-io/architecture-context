## Purpose

**Short**: A lightweight HTTP service that detects PII and custom patterns in text using regex matching, integrated with the FMS Guardrails Orchestrator for AI/ML content safety.

**Detailed**: The Guardrails Regex Detector is a Rust-based microservice that provides text content scanning via regular expressions. It exposes a single POST endpoint (`/api/v1/text/contents`) that accepts text content and a set of regex patterns, returning structured detection results with match positions and scores.

The service ships with three built-in detection patterns for common PII types: email addresses, Social Security Numbers (SSN), and credit card numbers. Users can also supply arbitrary custom regex patterns in each request. All matches are returned with position information (start/end offsets), detection type classification (`pii` for built-in or `custom` for user-supplied patterns), and a confidence score (always 1.0 for regex matches).

This component is designed to work as a downstream detector within the FMS Guardrails Orchestrator ecosystem. The orchestrator routes text content to this service for regex-based scanning as part of a broader content safety pipeline that may include other detection methods (e.g., ML-based classifiers). The service is stateless, has no persistent storage requirements, and is designed for horizontal scaling behind the orchestrator.

## Architectural Analysis

The Guardrails Regex Detector is an intentionally minimal Rust microservice. Its entire surface area is two HTTP endpoints served by the axum framework on a single port. The design prioritizes simplicity and performance -- Rust's `regex` crate provides fast, compiled regex execution, and the `tokio` multi-threaded runtime allows concurrent request processing without requiring external state.

The built-in detector pattern (email, SSN, credit card) uses a function-pointer dispatch table (`HashMap<&str, fn>`) rather than a trait-based plugin architecture. This keeps the codebase small (~170 lines across two source files) but limits extensibility. Adding new built-in detectors requires code changes and redeployment. The custom regex escape hatch (any pattern string not matching a built-in name is treated as a raw regex) provides runtime flexibility, though it shifts the regex correctness burden to callers.

A notable architectural gap is the complete absence of security controls at the application level. There is no TLS, no authentication, no authorization, and no input validation beyond checking for non-empty regex parameters. The service trusts that network-level isolation (via Kubernetes NetworkPolicy or service mesh) and the orchestrator's own auth layer prevent unauthorized access. This is a reasonable design for an internal microservice within a trusted pod network, but it means the service has zero defense-in-depth if network boundaries are breached. The Dockerfile also runs the service as root (no `USER` directive), which is a container security concern.

The absence of a Konflux Dockerfile is significant for RHOAI 3.5. Without Konflux build integration, the component cannot participate in Konflux's supply chain security features (check-payload FIPS validation, Hermeto prefetch for hermetic builds, SLSA provenance attestation). The standard `Dockerfile` uses an unpinned `ubi9/ubi-minimal:latest` base image, which creates reproducibility concerns. This suggests the component may be in an early integration stage or may be deployed via a different mechanism than the standard Konflux pipeline.
