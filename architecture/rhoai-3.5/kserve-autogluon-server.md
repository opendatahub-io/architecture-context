## Purpose

**Short**: Python inference server that serves AutoGluon TabularPredictor and TimeSeriesPredictor models via the KServe model serving protocol (v1 REST and v2 Inference Protocol).

**Detailed**: The KServe AutoGluon Server is a single-image inference runtime for the KServe model serving framework. It auto-detects whether a model artifact is an AutoGluon TabularPredictor or TimeSeriesPredictor at load time and delegates to the appropriate handler. The server supports KServe v1 REST JSON for both predictor types and additionally supports the v2 Inference Protocol (Open Inference Protocol) tensor payloads for tabular models. For tabular classification, an optional `PREDICT_PROBA` mode returns per-class probabilities instead of hard labels.

The server is deployed as a container within KServe `InferenceService` pods on OpenShift. It uses the `kserve` Python SDK to register as a model server, which provides the REST/gRPC transport layer, model repository management, health checks, and protocol compliance. Model artifacts are downloaded from cloud storage (S3, GCS, Azure Blob, or HuggingFace) via the `kserve-storage` module. The server image is built from an AIPCC CPU base image with a hermetic Konflux pipeline and ships a pinned ML stack: AutoGluon 1.5.0+rhaiv.3, LightGBM, XGBoost, CatBoost, PyTorch, and fastai.

The KServe AutoGluon Server follows a clean separation of concerns: the `autogluonserver` package handles only AutoGluon-specific model loading and prediction logic, while all serving infrastructure (REST/gRPC transport, health checks, model repository management, metrics) is delegated to the `kserve` Python SDK. This pattern is shared across all KServe runtime servers (sklearn, xgboost, lgb, huggingface, etc.) and allows the autogluon-specific code to remain small (~850 lines across 7 modules).

The auto-detection pattern in `predictor_factory.py` and `predictor_detect.py` is noteworthy: the server tries `TimeSeriesPredictor.load()` first, then falls back to `TabularPredictor.load()`. This means users deploy a single `modelFormat: autogluon` in their InferenceService CR without specifying the predictor type. The detection is robust but has an ordering bias -- if a directory could theoretically load as both types (unlikely in practice), time series wins. The `AutoGluonDetectedModel` wrapper class delegates all calls to the detected implementation, avoiding runtime type-checking overhead after initial load.

Version compatibility handling in `version_compat.py` adds resilience: the server tolerates patch-level AutoGluon version mismatches (e.g., model saved with 1.5.0 loaded by 1.5.0+rhaiv.3) by reading `version.txt` from the predictor directory and comparing major.minor only. This is important because the downstream RHOAI build uses custom AutoGluon releases (`+rhaiv.3` local version label) that differ at the patch/local level from upstream releases. Major or minor mismatches cause an immediate `InferenceError` rather than a subtle prediction failure.

The `runtime_paths.py` module addresses an OpenShift-specific operational concern: AutoGluon's SeasonalNaive fallback model calls `setup_outputdir` under the current working directory, which fails when the container's cwd is `/` (the default for many base images) and the process runs as an arbitrary UID. The module probes writable directories (`/tmp`, `$HOME`, `/home/kserve`) and `chdir`s to the first usable one at startup. This is a process-wide side effect and is explicitly documented as unsafe to call per-request.

The time series model (`timeseries_model.py`) only supports v1 REST JSON, not v2 tensor payloads. This is an intentional design choice documented in the code -- time series data has inherent structure (id columns, timestamps, known covariates) that maps poorly to flat tensors. The tabular model fully supports both v1 and v2 protocols with bidirectional DataFrame/tensor conversion. The v2 tabular path includes careful feature name mapping: when the v2 client sends integer-named columns (0, 1, 2...), the server remaps them to the predictor's feature names in order, enabling clients that lack column semantics to still produce correct predictions.
