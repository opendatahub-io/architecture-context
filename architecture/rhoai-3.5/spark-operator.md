## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Apache Spark applications on OpenShift, including submission, monitoring, scheduling, and cleanup of Spark driver and executor pods.

**Detailed**: The Spark Operator (also known as the Kubeflow Spark Operator) automates Apache Spark application lifecycle management on Kubernetes/OpenShift. It provides three Custom Resource Definitions — `SparkApplication` for one-shot Spark jobs, `ScheduledSparkApplication` for cron-scheduled recurring jobs, and `SparkConnect` for persistent Spark Connect server sessions — enabling users to declaratively submit and manage Spark workloads without direct interaction with `spark-submit` or pod management.

The operator consists of two deployments: a **controller** that reconciles CRDs and manages Spark driver/executor pods, services, ingresses, and monitoring configuration; and a **webhook** server that validates and mutates SparkApplication CRs and their associated pods. It integrates with batch schedulers (Volcano, YuniKorn, kube-scheduler with scheduler-plugins) for gang scheduling, supports Prometheus-based metrics collection, and provides configurable TLS with OpenShift TLS profile detection.

For RHOAI deployment, a companion **spark-operator-module** controller manages the operator's own lifecycle via a `SparkOperator` CRD (`components.platform.opendatahub.io`), handling kustomize-based manifest rendering, platform detection (RHOAI vs ODH), image parameter substitution, and deployment readiness monitoring. The module controller is deployed by the platform operator (rhods-operator) and manages the spark-operator controller and webhook deployments.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace RBAC via spark-role ServiceAccount; webhook validation blocks dangerous SparkConf keys | Kubernetes RBAC, ValidatingWebhookConfiguration | Users in the same namespace share the spark-operator-spark ServiceAccount; no per-user isolation within a namespace |
| Data storage | Per-namespace PVCs and ConfigMaps; secrets referenced by name within namespace | Kubernetes namespace isolation | No cross-namespace data access controls beyond Kubernetes namespace boundaries |
| Network traffic | NetworkPolicy restricts Spark pod ingress to same-namespace and OpenShift ingress; SparkConnect gRPC restricted to same-namespace and workbench-labeled namespaces | NetworkPolicy (RHOAI overlay) | NetworkPolicy only applied in RHOAI/ODH overlays; base deployment has no NetworkPolicy |
| Compute & resources | Optional ResourceQuota enforcement via webhook; configurable executor instance limits; max tracked executors per app (default 1000) | Webhook validation (optional), operator flags | ResourceQuota enforcement is off by default; no per-tenant compute limits enforced by operator itself |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; Spark configs scoped to SparkApplication CR | Kubernetes namespace isolation | Shared ServiceAccount (spark-operator-spark) across all apps in a namespace |
| API scoping | Namespace-scoped CRD watches; configurable namespace list or label selector | controller-runtime cache, operator flags | If `--namespaces` is empty (default), operator watches all namespaces cluster-wide |

## Architectural Analysis

The Spark Operator follows a multi-binary-from-single-image pattern: the same Go binary (`spark-operator`) serves both the controller and webhook roles via Cobra subcommands (`controller start`, `webhook start`). This simplifies image management but means a single Konflux Dockerfile produces an image used in two distinct Deployments with different arguments and RBAC profiles. The AIPCC CPU base image is used because the operator image also serves as a Spark runtime — it bundles Java 17 and PySpark 4.0.1 for `spark-submit` execution, making it significantly larger than a typical operator image.

The SparkApplication controller implements a sophisticated state machine with 13 states (New, Submitted, Running, Succeeding, Completed, Failing, Failed, FailedSubmission, PendingRerun, Invalidating, Suspending, Suspended, Resuming, Unknown). This state machine manages the full lifecycle from submission through monitoring to cleanup, with support for suspension/resumption, retry policies with configurable backoff, and spec-change detection that triggers invalidation and resubmission. The event filter is notably intelligent — it exempts executor-level fields that are patched by the webhook (PriorityClassName, NodeSelector, Tolerations, Affinity, SchedulerName) from triggering invalidation, preventing unnecessary restarts when webhook mutations update running applications.

The webhook system implements a 13-step pod mutation pipeline that transforms bare Spark pods into fully configured workloads with environment variables, volume mounts, security contexts, GPU resources, Prometheus monitoring, and sidecars. The SparkConf validator blocks 13 dangerous configuration keys that could allow users to override service accounts, inject OAuth tokens, change the Kubernetes master, or swap container images — enforcing that these security-sensitive parameters are managed exclusively through the CRD spec. This is a critical security boundary for multi-tenant deployments.

The three batch scheduler integrations (Volcano, YuniKorn, kube-scheduler with scheduler-plugins) each implement the same `scheduler.Interface` but create resources differently: Volcano and kube-scheduler create PodGroup CRDs with resource requirements, while YuniKorn uses annotations for gang scheduling configuration. The registry pattern allows runtime selection via `--default-batch-scheduler` and per-app override via `spec.batchScheduler`. This extensible design supports adding new schedulers without controller code changes.

The spark-operator-module is architecturally distinct from the main operator — it's a separate Go module in `spark-operator-module/` with its own `go.mod`, CRD (`components.platform.opendatahub.io/SparkOperator`), and deployment lifecycle. It acts as a level-of-indirection: the platform operator creates a SparkOperator CR, and the module controller renders kustomize manifests (selecting between RHOAI and ODH overlays based on `ODH_PLATFORM_TYPE`), injects images via `RELATED_IMAGE_*` environment variables, and monitors deployment readiness. This pattern decouples the spark-operator's deployment from the platform operator's reconcile loop.
