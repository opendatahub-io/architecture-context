## Purpose

**Short**: A Kubernetes operator that automates deployment, lifecycle management, and database migration orchestration for MLflow on OpenShift and Kubernetes clusters.

**Detailed**: The MLflow Operator provides a declarative API for managing MLflow deployments through Custom Resources. It uses Helm charts internally to render Kubernetes manifests and applies them via Server-Side Apply. The operator manages the full lifecycle including: persistent storage (PVC or remote S3/PostgreSQL), TLS certificate provisioning via OpenShift service-ca, Gateway API HTTPRoute creation for external access through the RHOAI data science gateway, Kubernetes-native authentication via `self_subject_access_review`, operator-managed database migration orchestration with automatic retry and version tracking, garbage collection CronJobs, trace archival CronJobs, namespace-scoped workspace RBAC via the Auth CR, and OpenShift ConsoleLink integration.

The operator supports two deployment modes — RHOAI mode (deploying to `redhat-ods-applications`) and OpenDataHub mode (deploying to `opendatahub`). It implements a module handoff pattern via the `MLflowOperator` CRD (`components.platform.opendatahub.io/v1alpha1`) which allows the platform operator to project gateway configuration into the MLflow operator. The operator creates a comprehensive set of resources dynamically: Deployment, Service, ServiceAccount, PVC, NetworkPolicy, ClusterRole/ClusterRoleBinding (for the MLflow server pod's cluster-wide namespace enumeration and secret access), CronJobs for garbage collection and trace archival, HTTPRoute for Gateway API integration, ConsoleLink for OpenShift console, ServiceMonitor for Prometheus, and migration Jobs.

## Architectural Analysis

The MLflow Operator follows a Helm-based rendering pattern that is uncommon among Kubernetes operators. Rather than constructing Kubernetes resources programmatically in Go, the operator loads a vendored Helm chart (`charts/mlflow/`), maps the MLflow CR spec to Helm values via `mlflowToHelmValues()`, renders templates through the Helm SDK, and applies the resulting unstructured objects via Server-Side Apply with field ownership. This approach gives the operator the templating power of Helm while maintaining the reconciliation semantics of controller-runtime. The trade-off is that debugging requires understanding both the Go controller logic and the Helm template logic.

The migration orchestration is the most sophisticated subsystem. When a version upgrade or forced migration is triggered, the operator: (1) scales the MLflow Deployment to zero replicas, (2) waits for all pods to quiesce, (3) builds a migration Job by cloning the rendered Deployment's pod spec with the main container replaced by an embedded Python migration script (`mlflow_db_migrate.py` via `//go:embed`), (4) monitors the Job for success/failure with specific exit codes for different failure modes (version mismatch, unsupported backend, revision conflicts), (5) automatically retries retryable failures after a 2-minute delay while treating terminal failures as sticky until an admin adds the `mlflow.opendatahub.io/force-migrate` annotation, and (6) only records `status.version` after the post-migration rollout is fully ready. The migration NetworkPolicy is built programmatically (not via Helm) and restricts migration Jobs to DNS and database egress only.

The operator uses a dual-cache architecture for RBAC watches. The main controller manager cache uses `metadata.name` field selectors for the shared `mlflow` ClusterRole/ClusterRoleBinding (required by resourceNames-scoped RBAC). A secondary `GCRBACWatchCache` watches the singleton `mlflow-gc` ClusterRole/ClusterRoleBinding, since controller-runtime only allows one field selector per GVK per cache. Similarly, the namespace RBAC controller uses two dedicated caches (`ViewRBWatchCache` and `EditRBWatchCache`) for watching the `odh-group-mlflow-view` and `odh-group-mlflow-edit` RoleBindings across all namespaces.

The RHOAI 3.x ingress pattern is implemented via Gateway API HTTPRoute. The operator creates an HTTPRoute with two rules: one for `/mlflow/v1/*` paths (with URL rewrite to strip the prefix) and one for `/mlflow/*` paths, both pointing to the MLflow Service on port 8443. The HTTPRoute references the `data-science-gateway` Gateway in the `openshift-ingress` namespace as its parent. TLS termination happens in-process within the MLflow container using uvicorn options with certificates from the `mlflow-tls` Secret. On OpenShift, uvicorn SSL ciphers default to `PROFILE=SYSTEM` to follow the platform crypto policy.

The platform module handoff via the `MLflowOperator` CRD represents a transitional architecture. When `ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER` is enabled, the MLflow controller blocks on the singleton `MLflowOperator` CR being ready before reconciling MLflow CRs, reads gateway domain/name/sectionTitle from the module spec (overriding environment variables), and the `MLflowOperatorReconciler` tracks release metadata (platform version + MLflow version) in the module's status. This allows the platform operator (odh-operator/rhods-operator) to project configuration into the MLflow operator without direct env-var coupling. A finalizer on the MLflowOperator CR prevents deletion while MLflow instances still exist.
