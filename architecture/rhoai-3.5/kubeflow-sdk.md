## Purpose

**Short**: Unified Python SDK providing Pythonic APIs for managing AI/ML training, hyperparameter optimization, Spark data processing, and model registry operations on Kubernetes via Kubeflow components.

**Detailed**: The Kubeflow SDK is a Python library that abstracts away Kubernetes complexity, enabling data scientists to run distributed AI workloads using familiar Python APIs. It provides client interfaces for four Kubeflow projects: Trainer (distributed training with PyTorch, MPI, TorchTune), Katib-based Optimizer (hyperparameter tuning), Spark Operator (Spark Connect data processing), and Model Registry (model artifact management).

The SDK supports three execution backends: `KubernetesBackend` (production training on Kubernetes clusters via TrainJob CRDs), `ContainerBackend` (local Docker/Podman isolation), and `LocalProcessBackend` (pure Python subprocesses for prototyping). When targeting Kubernetes, the SDK creates and manages `TrainJob` custom resources in the `trainer.kubeflow.org/v1alpha1` API group and Katib `Experiment` CRs for optimization workflows.

The RHOAI midstream fork (version `v0.3.0+rhai0`) adds the `kubeflow.trainer.rhai` module, which provides two RHAI-specific trainer types: `TrainingHubTrainer` (for SFT, OSFT, LoRA SFT, and LoRA GRPO algorithms with automatic progression tracking via HTTP metrics servers) and `TransformersTrainer` (HuggingFace Transformers/TRL integration with JIT checkpointing, S3/PVC checkpoint storage, and auto-resume). These trainers inject instrumentation code into training pods at runtime via `inspect.getsource()` extraction, providing real-time training progress monitoring and fault-tolerant checkpointing without requiring changes to user training scripts.

## Architectural Analysis

The Kubeflow SDK follows a **backend abstraction pattern** where the `TrainerClient`, `OptimizerClient`, and `SparkClient` classes delegate all operations to pluggable backend implementations. The `KubernetesBackend` is the production path, using the `kubernetes` Python client library with async threading (`async_req=True`) for parallel API calls. This design enables seamless switching between local development (ContainerBackend, LocalProcessBackend) and production Kubernetes clusters with no code changes.

The RHAI module (`kubeflow.trainer.rhai`) is architecturally the most sophisticated part of the SDK. It uses **source code extraction via `inspect.getsource()`** to inject instrumentation into training pods. Rather than requiring training images to ship with SDK dependencies, the RHAI trainers extract entire Python functions as source code strings, substitute runtime parameters, and embed them into the pod's `command`. This is a deliberate design choice that keeps the training container images decoupled from the SDK -- the injected code is fully self-contained and uses only stdlib imports (plus `transformers` when using `TransformersTrainer`). The TrainingHubTrainer supports four algorithms (SFT, OSFT, LoRA SFT, LoRA GRPO), each registered in a centralized `ALGORITHMS` registry (`kubeflow/trainer/algorithms.py`) with algorithm-specific metadata (metrics file patterns, entrypoint commands, validation functions).

The **progression tracking system** deserves attention for its three-layer reliability design: (1) an HTTP metrics server on port 28080 serves real-time training progress as JSON, polled by the Kubeflow Trainer controller via annotations (`trainer.opendatahub.io/progression-tracking`, `trainer.opendatahub.io/metrics-port`); (2) a termination message written to `/dev/termination-log` captures final metrics even if the HTTP server becomes unreachable during pod shutdown; (3) algorithm-specific metrics schema transformers normalize heterogeneous backend output (SFT uses `avg_loss`/`overall_throughput`, OSFT uses `loss`/`time_per_batch`, LoRA uses `loss`/`learning_rate`) into a controller-compatible schema with `progressPercentage`, `estimatedRemainingSeconds`, and standardized `trainMetrics`/`evalMetrics` dicts.

The **TransformersTrainer's JIT checkpointing** system is another notable design: it registers a SIGTERM handler (`CheckpointManager`) that defers the checkpoint to the next training callback (on_step_end/on_epoch_end) to avoid reentrancy deadlocks during periodic checkpoints. For S3 storage, it uses a background upload worker thread with a LIFO queue (latest checkpoint first), per-rank incomplete markers for distributed training, and automatic checkpoint resume via `_find_latest_checkpoint()` which skips checkpoints with stale markers. This design ensures fault tolerance without requiring the platform operator to manage checkpoint lifecycle.

The SDK's **namespace scoping model** is straightforward: all operations target a single namespace determined by kubeconfig context or explicit configuration. The one exception is `ClusterTrainingRuntime` listing (cluster-scoped), where the SDK implements a priority rule: namespace-scoped `TrainingRuntime` with the same name shadows the cluster-scoped version. This prevents unintentional use of shared runtimes when a team has customized their own.
