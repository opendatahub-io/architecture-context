## Purpose

**Short**: KServe is a Kubernetes-native model serving platform that provides serverless inference, model lifecycle management, and LLM-optimized serving for RHOAI.

**Detailed**: KServe is the core model serving component of Red Hat OpenShift AI, providing a standardized way to deploy, serve, and manage machine learning models on Kubernetes. It defines Custom Resource Definitions (InferenceService, LLMInferenceService, ServingRuntime, InferenceGraph, LocalModelCache, TrainedModel) that abstract the complexities of model deployment into declarative configurations.

The component is a multi-controller architecture with several entry points: (1) the main KServe controller manager handling InferenceService reconciliation with support for Knative serverless, raw Kubernetes deployments, and Gateway API ingress; (2) the LLMInferenceService controller optimized for LLM workloads with features like prefill/decode disaggregation, group routing, InferencePool integration, managed DRA for accelerator provisioning, and LoRA adapter routing; (3) the LocalModel controller and node agent for pre-caching models on cluster nodes; (4) the kserve-module controller that acts as a platform module deploying KServe as part of the ODH/RHOAI platform. Pod-level mutation webhooks inject storage initializers, inference agents, batchers, and metrics aggregators into serving pods.

The Python SDK (`kserve`) provides a framework for building custom model servers, and the storage library handles model downloading from S3, GCS, Azure, HuggingFace, PVC, and OCI sources with support for confidential model decryption.

## Architectural Analysis

KServe in RHOAI 3.5 is a multi-controller, multi-language component with significant architectural complexity. The repository contains three distinct Go modules (`kserve`, `kserve-module`, `qpext`), a Python SDK and storage library, and multiple Python serving runtimes. The `distro` build tag system (`//go:build distro` vs `!distro`) creates a clean separation between upstream KServe behavior and RHOAI/ODH customizations—OpenShift-specific features like kube-rbac-proxy injection, serving certificate management, OpenShift Route creation, and SCC management are compiled in only for downstream builds.

The LLMInferenceService controller (`v1alpha2`) represents a major architectural evolution beyond the original InferenceService pattern. While InferenceService follows a traditional Kubernetes operator model (watch CR → create Deployment + Service + Ingress), the LLMInferenceService controller operates as a meta-controller orchestrating resources across 10+ API groups: Gateway API HTTPRoutes, GIE InferencePools for model-based routing, LeaderWorkerSets for distributed multi-node inference, DRA ResourceClaimTemplates for accelerator provisioning, Prometheus Operator PodMonitors/ServiceMonitors for observability, and WVA VariantAutoscaling for variant-aware scaling. The controller's conditional CRD availability checks (`controller.go:438-478`) allow graceful degradation when optional APIs are not installed.

The kserve-module controller adds a platform management layer that does not exist upstream. It deploys the entire KServe stack—multiple controllers, webhooks, CRDs, RBAC, serving runtimes, monitoring, and model cache infrastructure—via kustomize rendering from `/opt/manifests-template`. Its dependency tracking is sophisticated: it monitors cert-manager, Istio, LeaderWorkerSet, and KEDA via OLM Subscription watches and CRD availability checks, with per-dependency severity levels that determine whether failures are blocking (cert-manager on XKS) or degraded-only (Istio, LWS). The fast-variant filtering logic and version-prefixed LLMInferenceServiceConfig management are unique downstream features.

The pod mutation webhook chain (`pkg/webhook/admission/pod/`) is a critical architectural component that transforms vanilla model server pods into production-ready inference endpoints. The injection chain (storage initializer → agent → batcher → metrics aggregator → accelerator selector → OCI storage mutator) adds sidecars, init containers, credential injection, and platform-specific security contexts. The ODH-specific `InjectImageVolume` path leverages Kubernetes 1.33+ image volumes as an alternative to the upstream modelcar sidecar pattern, demonstrating the downstream's willingness to adopt cutting-edge Kubernetes features.

The LocalModel subsystem (`LocalModelCache → LocalModelController → LocalModelNode → LocalModelNode Agent → batch Jobs`) implements a sophisticated model pre-caching pipeline. Storage deduplication via SHA256 hash of the model URI prevents redundant downloads when multiple CRs reference the same model. The ODH-specific node agent code handles SELinux MCS context management and launches permission-fix Jobs when filesystem permissions are incorrect—a level of platform-specific operational concern not present upstream.
