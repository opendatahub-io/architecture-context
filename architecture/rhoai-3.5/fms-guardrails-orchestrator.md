## Purpose

**Short**: REST API orchestrator that coordinates AI text generation with content safety guardrails, acting as middleware between clients and language models.

**Detailed**: The FMS Guardrails Orchestrator is a Rust-based middleware service that sits between clients and large language model (LLM) inference backends to enforce content safety policies. It intercepts text generation requests, routes content through configurable detector services for classification and filtering, and coordinates chunker services for text segmentation before detection.

The orchestrator supports multiple generation backends including TGIS (via gRPC), Caikit NLP (via gRPC), and OpenAI-compatible APIs (via HTTP). It exposes a REST API surface with both legacy v1 endpoints (classification with text generation) and modern v2 endpoints (content detection, chat completions detection, completions detection, context document detection). Both unary and streaming response modes are supported, with sophisticated detection batching logic to correlate streaming chunks with their detection results.

The service is designed as a stateless middleware that can be horizontally scaled. It manages no persistent state of its own — all configuration is provided via a YAML config file at startup, and all content safety logic is delegated to external detector and chunker services. The orchestrator's primary value is in orchestrating the flow: input detection → generation → output detection, with early-exit patterns when input content is deemed unsuitable.

## Architectural Analysis

The FMS Guardrails Orchestrator implements a sophisticated middleware architecture built around the concept of "orchestrated safety." Rather than implementing content detection logic directly, it acts as a routing and coordination layer that composes external detector, chunker, and generation services into safety-aware pipelines. This design follows a clear separation of concerns: the orchestrator handles request routing, response aggregation, and streaming coordination, while content safety intelligence resides in the detector services.

The streaming architecture is particularly noteworthy. For streaming endpoints, the orchestrator employs an actor-based detection batching system (`DetectionBatcherManager`) that runs in a spawned Tokio task and coordinates multiple concurrent detector streams via `tokio::select!` with biased polling. Two batching strategies are implemented: `CompletionBatcher` for OpenAI-compatible chat/completions (batches by choice index for multi-choice responses) and `MaxProcessedIndexBatcher` for content detection streams (ensures all detectors have processed up to an index before emitting a batch). This allows the orchestrator to stream generation results to clients while concurrently running detection on the generated content, with detections attached to the appropriate response chunks.

The TLS architecture deserves scrutiny. The service uses **rustls with the ring crypto backend** rather than OpenSSL for all TLS operations. While this provides memory-safe TLS, the ring crate is not FIPS-certified, which creates a gap for FIPS-regulated deployments. Additionally, the client-side TLS code includes a `NoVerifier` implementation (`src/utils/tls.rs:39-91`) that completely bypasses certificate verification when `insecure: true` is set in the per-service TLS configuration. While useful for development, this is a significant security risk if inadvertently enabled in production. The server side properly implements mTLS via `WebPkiClientVerifier` when a client CA certificate path is provided.

The service implements comprehensive observability through OpenTelemetry with support for both gRPC and HTTP OTLP exporters. Every inbound request generates spans with structured fields (method, path, duration, status), and outbound client calls are instrumented with `TraceLayer` (HTTP) and `OtelGrpcLayer` (gRPC). W3C trace context propagation (`traceparent` header) is automatically injected into all downstream calls, enabling end-to-end distributed tracing across the orchestrator, detectors, chunkers, and generation services. Metrics include counters for incoming requests, responses by status class (2xx/4xx/5xx), and histograms for request duration.

A notable architectural pattern is the header passthrough mechanism. The orchestrator supports configurable header forwarding from inbound requests to downstream service calls via `passthrough_headers` in the config. It also supports rewriting `X-Forwarded-Access-Token` headers into standard `Authorization: Bearer` headers (`rewrite_forwarded_access_header` config flag), which enables integration with platforms that use forwarded access token patterns (common in OpenShift environments with OAuth proxy sidecars). This design allows the orchestrator to remain authentication-agnostic while still propagating credentials to downstream services.
