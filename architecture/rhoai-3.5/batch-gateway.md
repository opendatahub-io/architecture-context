## Purpose

**Short**: High-performance batch inference gateway providing an OpenAI-compatible API for submitting, tracking, and processing large-scale batch inference jobs against llm-d inference routers.

**Detailed**: Batch Gateway is a multi-component Go service that enables large-scale batch inference processing in Kubernetes environments. It provides OpenAI-compatible `/v1/batches` and `/v1/files` REST endpoints for submitting batch inference jobs containing up to 50,000 requests per job. The system is designed to coexist with interactive workloads by using adaptive concurrency control (AIMD) to minimize interference while satisfying batch SLO deadlines.

The system comprises three independently deployable components: an **API Server** that handles REST requests for job submission, tracking, and file management; a **Batch Processor** that dequeues jobs from a priority queue, pre-processes them into per-model execution plans, dispatches inference requests to downstream llm-d routers with flow control, and uploads results; and a **Garbage Collector** that periodically removes expired batch jobs, files, and orphaned resources.

The data layer supports pluggable backends — PostgreSQL for metadata storage, Redis/Valkey for priority queues, event channels, status tracking, and in-flight job coordination, and S3 or local filesystem for batch input/output file storage. The architecture emphasizes fault tolerance through automatic crash recovery, idempotent cancellation, and distributed orphan reconciliation.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to gateway layer (Kuadrant/Authorino); application enforces tenant isolation via header validation returning 404 on cross-tenant access | Gateway (Kuadrant) + Application | Tenant ID from HTTP header — if gateway is misconfigured or bypassed, any caller can impersonate tenants by setting the header |
| Data storage | Tenant-scoped DB queries (TenantID in all BaseQuery filters); tenant-scoped file storage (SHA256-hashed tenant folder names) | Application (query filters, folder partitioning) | Application-enforced — a bug in query construction could leak cross-tenant data; no database-level row security |
| Network traffic | No per-tenant NetworkPolicy; all components share the same network namespace | None (shared) | No network-level tenant isolation; relies entirely on application-level scoping |
| Compute & resources | Shared processor pool across all tenants; no per-tenant quotas or priority classes | None (shared) | One tenant's large batch job could consume all processor capacity; priority queue orders by SLO, not tenant |
| Configuration & secrets | Single shared secret mount for all tenants; per-model API keys are global, not per-tenant | Application | All tenants share the same inference API keys and storage credentials |
| API scoping | All DB queries include TenantID filter; batch/file retrieval validates tenant ownership (returns 404 on mismatch) | Application (`batch_handler.go:417-426`, `file_handler.go:150-159`) | Effective but application-enforced — relies on correct implementation in every handler |

## Architectural Analysis

The batch-gateway follows a clean multi-component service architecture where three independently deployable binaries (apiserver, processor, gc) share a common codebase in `internal/` and coordinate through shared external state stores rather than direct inter-component communication. This design enables independent scaling — the processor can be scaled horizontally to handle more concurrent batch jobs while the apiserver scales for API throughput, with no direct coupling between them. The garbage collector runs as a single instance and handles both TTL-based cleanup and distributed orphan reconciliation.

The adaptive concurrency control system is architecturally notable. The processor implements a multi-layered semaphore hierarchy — a global ceiling (default 100 in-flight requests), per-endpoint limits (default 10), and per-endpoint AIMD controllers that dynamically adjust limits based on downstream signals (HTTP 429 → multiplicative decrease by 0.5, success → additive increase by 1). This creates backpressure that protects interactive workloads on shared inference infrastructure without requiring manual tuning. The dispatcher chain pattern (PreDispatcher → AIMDDispatcher → DirectDispatcher/AsyncDispatcher) cleanly separates concerns: validation, flow control, and execution.

The multi-tenancy model is entirely application-enforced, which is both a strength (simple, no external dependencies) and a risk. Tenant identity is extracted from a configurable HTTP header (default `X-MaaS-Username`) and propagated through request context. Every database query includes a tenant filter, and file storage uses SHA256-hashed tenant folder names. However, there is no Kubernetes-level enforcement (no per-tenant NetworkPolicies, RBAC, or namespace isolation). If the upstream gateway (Kuadrant/Authorino) is misconfigured or bypassed, tenant impersonation is trivial by setting the header. The README explicitly documents that authentication is delegated upstream.

The fault tolerance design uses several sophisticated patterns. Crash recovery scans the processor's work directory on startup to find incomplete jobs and either re-enqueues or fails them based on SLO status. The GC reconciler uses in-flight heartbeats (Redis hash with `{ProcessorID, LastSeen}`) to detect orphaned jobs — if a processor crashes, its jobs' `LastSeen` timestamps go stale, and the reconciler triages them (re-enqueue if SLO permits, expire or fail otherwise). CAS (compare-and-swap) updates via Lua scripts in Redis and conditional UPDATE in PostgreSQL prevent race conditions during concurrent status transitions. The context hierarchy in `job_runner.go` is particularly well-structured — separate context branches for SLO deadlines, user cancellation, SIGTERM, and polling ensure clean shutdown semantics without mixing concerns.

The pluggable backend architecture uses Go interfaces (`BatchFilesClient`, `DBClient[T, Q]`) with wrapper patterns (base → tracing → retry) for cross-cutting concerns. However, while the database and file storage backends are pluggable (PostgreSQL/Redis, S3/filesystem), the exchange layer (queue, events, status, in-flight) is hardcoded to Redis — there's a TODO in `clientset.go` noting this limitation. The Redis implementation uses embedded Lua scripts for atomic operations (store, CAS update, priority queue management), which provides correctness guarantees but creates a hard dependency on Redis semantics.
