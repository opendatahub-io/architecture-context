## Purpose

**Short**: Python SDK that provides an intuitive interface for creating, managing, and interacting with Ray clusters and Ray jobs on Kubernetes (via KubeRay) within OpenShift AI / Open Data Hub.

**Detailed**: The CodeFlare SDK is a client-side Python library that data scientists use from Jupyter notebooks or local development environments to manage distributed computing resources on Kubernetes. It abstracts the complexity of Kubernetes resource management by providing high-level Python APIs for creating RayCluster custom resources (via the KubeRay operator), submitting RayJob CRs, monitoring cluster status, and managing job lifecycles.

The SDK interacts with the Kubernetes API server to create and manage `ray.io/v1` custom resources (RayCluster, RayJob), integrates with Kueue (`kueue.x-k8s.io/v1beta1`) for batch job queuing and resource management, and generates mTLS certificates for secure communication with Ray clusters. It supports multiple authentication methods through `kube-authkit` (OIDC, OpenShift OAuth, kubeconfig, in-cluster service accounts) and provides Jupyter notebook widgets (via `ipywidgets`) for interactive cluster management.

The SDK also handles RHOAI platform-specific patterns including Gateway API (HTTPRoute) dashboard URL resolution for RHOAI v3.0+, OpenShift Route-based dashboard access for legacy deployments, and automatic ODH trusted CA certificate bundle mounting in Ray pod specifications.

## Architectural Analysis

The CodeFlare SDK follows a layered architecture with strict import boundaries enforced by `import-linter`. The foundation layer (`common/`) provides Kubernetes authentication, API error handling, Kueue integration, and utility functions. The feature layer (`ray/`) is split into three sub-modules: `cluster` for interactive RayCluster management, `rayjobs` for batch RayJob submission, and `client` for direct Ray dashboard interaction. The `client` module is deliberately isolated — it has no imports from `common/` or other `ray/` sub-modules, serving as a thin, dependency-free wrapper around Ray's `JobSubmissionClient`. This isolation ensures it can be used independently without pulling in the full SDK dependency chain.

The mTLS certificate management (`generate_cert.py`) is a significant security feature. The SDK generates RSA 3072-bit client certificates signed by the KubeRay operator's CA, with proper RFC 5280 extensions (BasicConstraints, KeyUsage, ExtendedKeyUsage for both serverAuth and clientAuth, and SANs including the head service DNS names). Certificates are stored in a user-private directory (`~/.local/share/codeflare/tls/`) with 0600 permissions, and are automatically cleaned up when clusters are deleted. The cert generation polls for the CA secret after cluster creation, which creates a temporal coupling — the SDK must wait for KubeRay to create the head pod before certificates can be generated.

The dashboard URL resolution logic in `cluster.py` (lines 612-1419) implements a multi-strategy pattern that reflects the platform's evolution from OpenShift Routes (RHOAI 2.x) to Gateway API (RHOAI 3.x). The resolution tries HTTPRoute first (searching by `ray.io/cluster-name` label), then falls back to OpenShift Routes, then Kubernetes Ingresses. For HTTPRoute resolution, it cascades through four hostname sources: Gateway spec listeners, OpenShift Routes exposing the Gateway, GatewayConfig CR domain configuration, and finally Gateway status addresses. This cascading fallback ensures backwards compatibility across RHOAI versions but introduces complexity — there are multiple code paths that could diverge.

The `rayjobs` module introduces a declarative job submission model that differs from the interactive `cluster` module. While `Cluster.apply()` creates a long-lived RayCluster and the user manages its lifecycle, `RayJob` creates a RayJob CR that can optionally provision its own ephemeral cluster via `ManagedClusterConfig`. The RayJob module handles local file packaging (zipping working directories, base64-encoding into Kubernetes Secrets with 1MB size limits, creating submitter pod templates with init containers for unzipping), runtime environment processing, and Kueue integration. File Secrets are created with owner references to the RayJob CR, ensuring automatic garbage collection.

The vendored KubeRay Python client (`vendored/python_client/`) is imported only by the `rayjobs` module (enforced by import-linter contract #4). This vendored code provides lower-level RayJob and RayCluster CRUD operations that the SDK wraps with higher-level abstractions. The vendoring approach isolates the SDK from KubeRay client API changes but requires manual updates when the upstream client evolves.
