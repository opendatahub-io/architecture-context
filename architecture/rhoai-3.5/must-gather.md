## Purpose

**Short**: Diagnostic data collection tool for Red Hat OpenShift AI and LLM-D inference workloads across OpenShift and non-OpenShift Kubernetes platforms.

**Detailed**: The must-gather component is a utility container image that collects diagnostic data from Red Hat OpenShift AI (RHOAI) clusters and non-OpenShift Kubernetes (xKS) environments running LLM-D inference workloads. It is invoked via `oc adm must-gather` on OpenShift or as a Kubernetes Job on CKS, AKS, and EKS platforms. The tool collects namespace-level resources (pods, logs, events, deployments, services), custom resources for every RHOAI component (KServe, Data Science Pipelines, Notebooks, Dashboard, Kueue, KubeRay, Training Operator, Model Registry, TrustyAI, Feast, LlamaStack, MLflow, Spark, AI Gateway, MCP Lifecycle Operator), and platform-level resources (DSCInitialization, DataScienceCluster, Gateway API resources, Istio networking, Helm release values).

The tool supports component-scoped collection via the `COMPONENT` environment variable, allowing engineers to gather data for a single subsystem (e.g., `COMPONENT=kserve`). When no component is specified on OpenShift, all component gatherers run in parallel for maximum collection speed. The LLM-D collection path is the primary xKS flow, with optional sub-collectors for workload-variant-autoscaler (WVA), batch-gateway, and observability (Prometheus Operator or Azure Managed Prometheus). The tool also collects dependency operator state for cert-manager, Sail/Istio, and LeaderWorkerSet.

## Architectural Analysis

The must-gather component follows a modular collector pattern: a main `gather.sh` orchestrator dispatches to per-component shell scripts that each define a list of CRD resource types and use shared library functions to discover namespaces containing those resources and collect them. This design allows component teams to independently add or update their collection logic by editing a single script (e.g., `gather_aigateway.sh`) without touching the orchestrator. The shared `common.sh` library provides `get_all_namespace` (discover namespaces where given CRDs exist) and `run_mustgather` (iterate namespaces and call `oc adm inspect`), while the `xks_util.sh` library provides equivalent xKS functions (`kubectl_inspect`, `auto_discover_resources`, `run_k8sgather`) that replace OpenShift-specific tooling with standard kubectl commands.

The xKS platform support (CKS, AKS, EKS) is a significant architectural extension. The `detect_k8s_distro` function uses multiple heuristics -- OpenShift infrastructure CRDs, kernel version (CoreWeave), provider ID prefix (azure://, aws://), and node OS image -- to determine the platform. On non-OpenShift platforms, the tool constrains collection to LLM-D resources only (`component="llm-d"`), since the full RHOAI stack is not deployed on xKS. The xKS path includes its own namespace inspection implementation (`kubectl_inspect`) that mirrors `oc adm inspect` by collecting namespace YAML, auto-discovering all namespaced resources via `kubectl api-resources`, and gathering pod logs for each container in parallel. This is a faithful reimplementation of OpenShift tooling for vanilla Kubernetes.

The parallel execution model in `gather.sh` is worth noting: when collecting all components on OpenShift, the orchestrator spawns 14 component collector scripts as background processes and tracks their PIDs in an associative array for error reporting. This can generate significant Kubernetes API server load, as each collector independently discovers namespaces and calls `oc adm inspect` or `kubectl get`. Similarly, within `kubectl_inspect`, pod log collection runs in parallel with one subshell per pod. The tool does not implement rate limiting or API server back-pressure, which could be problematic on large clusters with many RHOAI-managed namespaces.

The Helm integration (`collect_helm_releases`) reflects the architectural shift in RHOAI 3.x where both OpenShift deployments (via `rhoai` release) and xKS deployments (via `rhaii` release) use Helm charts for installation. This allows must-gather to capture the actual configuration values used during deployment, which is essential for debugging configuration-related issues.

The DEFAULT_RESOURCES array in `common.sh` automatically collects Gateway API resources (Gateways, HTTPRoutes, GRPCRoutes, ReferenceGrants) and Istio resources (EnvoyFilters, DestinationRules) for every namespace inspected, reflecting the RHOAI 3.x ingress architecture. This ensures that per-component networking configuration is captured even when the component-specific gatherer doesn't explicitly list these resource types.
