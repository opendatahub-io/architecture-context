## Purpose

**Short**: End-to-end test suite and container image collection for distributed training workloads on Red Hat OpenShift AI, covering Kubeflow Training Operator, Kubeflow Trainer v2, KubeRay, and Kueue.

**Detailed**: The distributed-workloads repository serves as the primary integration test suite for the Distributed Workloads stack on RHOAI. It validates that distributed training frameworks (PyTorchJob via KFTO v1, TrainJob via Kubeflow Trainer v2, RayJob/RayCluster via KubeRay) work correctly on OpenShift clusters with GPU acceleration (NVIDIA CUDA, AMD ROCm) and job scheduling via Kueue.

The repository also produces a substantial matrix of container images: runtime training images (10 Konflux-built variants spanning CUDA 12.1–13.0 and ROCm 6.2–6.4), universal training images (3 variants for CPU/CUDA/ROCm with Training Hub integration), Ray runtime images, benchmark images, and utility images. These images are the primary training runtime for RHOAI users — they are referenced by the rhods-operator's `RELATED_IMAGE_*` environment variables and deployed into user namespaces when distributed training workloads are submitted.

Beyond testing and images, the repository provides example notebooks and benchmarks demonstrating distributed training patterns (LLM fine-tuning, Stable Diffusion DreamBooth, RAG pipelines, MPI benchmarks) that serve as reference implementations for RHOAI users.

## Architectural Analysis

The distributed-workloads repository occupies a unique position in the RHOAI platform: it is simultaneously a test suite, a container image factory, and a reference implementation library. This dual nature creates an unusual architectural footprint where the Go code never ships to production (it's purely test infrastructure), but the container images it co-locates with are critical production artifacts referenced by the platform operator.

**Two-tier image strategy with migration gap.** The repository maintains two distinct image families with fundamentally different build approaches. The "runtime" training images (10 Konflux variants) use plain UBI base images and install GPU toolchains from vendor repositories — a pattern that pre-dates AIPCC and lacks RPM-level hermeticity. The newer "universal" training images (3 variants) use AIPCC workbench bases and cachi2 prefetch for full hermeticity. The OpenMPI runtime variants (2 images) sit in between — they use AIPCC base images but with a simpler single-stage build. This migration from vendor-repo-based builds to AIPCC-hermetic builds is incomplete: 8 of 10 runtime training images still build without AIPCC. The ROCm 6.4 base images used by the OpenMPI ROCm variant and the universal ROCm variant are flagged as "Retired" in overlay 0017, creating an immediate supply chain concern.

**Test infrastructure is deeply coupled to the platform.** The Go support library (`tests/common/support/`) initializes 13 distinct Kubernetes API clients spanning 6 CRD groups (Kubeflow, Trainer, Ray, Kueue, JobSet, and OpenShift-specific APIs). It auto-detects whether it's running on ODH or RHOAI via CSV prefix inspection, resolves training images through a three-level fallback (env var → `RELATED_IMAGE_*` from rhods-operator pod → hardcoded defaults), and adapts networking behavior (Route vs Ingress) based on OpenShift API availability. This makes the test suite a de facto integration validator for the entire distributed workloads stack, but also means it is fragile to platform API changes.

**GPU variant matrix creates combinatorial complexity.** The repository manages training images across 2 Python versions (3.11, 3.12), 5 CUDA versions (12.1, 12.4, 12.8, 12.8, 13.0), 2 ROCm versions (6.2, 6.4), 2 PyTorch version ranges (2.4.x–2.5.x and 2.8.x–2.10.x), and 2 build systems (Pipfile/pipenv for runtime, pyproject.toml/uv for universal). Each combination produces a separate Dockerfile and Tekton pipeline (49 Tekton pipeline YAML files in `.tekton/`), creating significant maintenance burden. The Tekton pipelines are managed externally via `konflux-central` and synced automatically.

**Benchmark infrastructure demonstrates Trainer v2 patterns.** The benchmarks directory showcases the ClusterTrainingRuntime + TrainJob pattern that is replacing PyTorchJob in RHOAI 3.5. The MPI DDP SFT benchmark (`benchmarks/kftv2-mpi-ddp-sft/`) documents real production constraints: MPI's int32 count limit caps model size at ~2.1B float32 parameters, and the MPI backend lacks half-precision datatype mappings. These constraints inform the platform's recommended training configurations.
