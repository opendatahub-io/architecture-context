## Purpose

**Short**: TrustyAI is a Java library and Quarkus-based REST service providing AI model fairness metrics, bias tracking, drift detection, and explainability algorithms for models served via KServe/ModelMesh on OpenShift AI.

**Detailed**: TrustyAI Explainability is a multi-module Java project that provides the core AI explainability and fairness measurement capabilities for Red Hat OpenShift AI. The primary deliverable is the `explainability-service`, a Quarkus-based microservice that consumes inference data from KServe and ModelMesh model servers (via REST payloads and CloudEvents), stores the data persistently (on PVC, in a database, or in MinIO), computes fairness and drift metrics on configurable schedules, and publishes results to Prometheus for monitoring and alerting.

The core library (`explainability-core`) implements multiple explainability algorithms including LIME, SHAP, Counterfactual, and Partial Dependence Plots, along with group and individual fairness metrics (Statistical Parity Difference, Disparate Impact Ratio), drift detection methods (KS Test, Fourier MMD, Meanshift, Jensen-Shannon), and NLP metrics (BLEU, ROUGE, WER). The `explainability-connectors` module provides KServe V1 HTTP, V2 HTTP, and V2 gRPC connectors for querying model servers during explainability analysis. The `explainability-arrow` module enables efficient data exchange via Apache Arrow IPC for Python interoperability.

In the RHOAI distribution, the service operates with a reduced feature set compared to ODH: fairness and drift endpoints are enabled, but explainer endpoints (LIME, SHAP, Counterfactual, TSSaliency, global explainers) are disabled by default via Quarkus profile-based feature flags. The service is deployed per-namespace by the TrustyAI Service Operator and integrates with ModelMesh/KServe via a `model-serving-config` ConfigMap that routes inference payloads to TrustyAI for bias monitoring.

## Architectural Analysis

TrustyAI Explainability follows a multi-module Maven architecture where the core library (`explainability-core`) is framework-agnostic, the connectors module provides protocol adapters for inference servers, and the service module wraps everything in a Quarkus REST application. This layering is clean and allows the core algorithms to be consumed independently as a Java library (published to Nexus) or embedded in the Quarkus service. The Arrow module adds a fourth integration path for Python interoperability, though its usage in the deployed RHOAI service is unclear -- it appears primarily intended for the [TrustyAI Python library](https://github.com/trustyai-explainability/trustyai-explainability-python).

The inference data reconciliation pattern is a key architectural decision. Inference requests and responses arrive asynchronously (often as separate CloudEvents from KServe) and must be correlated by inference ID before they can be stored as complete prediction records. The `InferencePayloadReconciler` acts as a stateful join buffer, holding unmatched halves until a pair is found. This design handles the asynchronous nature of KServe's logging pipeline but introduces a risk: unmatched payloads accumulate in memory if one side (request or response) fails to arrive. The reconciler implementations for KServe and ModelMesh handle this differently, reflecting the two integration paths.

The RHOAI profile configuration (`%rhoai.*` in application.properties) reveals a significant product decision: in RHOAI, all explainer endpoints (LIME, SHAP, Counterfactual, TSSaliency, global explainers) are disabled, leaving only fairness metrics (SPD, DIR) and drift detection (KSTest, FourierMMD, Meanshift, ApproxKSTest) active. This means the deployed RHOAI service is primarily a bias monitoring and drift detection tool, not a full explainability service. The explainability algorithms remain in the codebase and are available in ODH, but RHOAI ships them disabled. This is likely a support scope decision -- fairness metrics are passive (computed on stored data), while explainers require active model queries that introduce latency and failure modes.

The storage abstraction supports four backends (PVC, DATABASE, MINIO, MEMORY) through a `DataSource` abstraction, but the default and most common deployment uses PVC-backed CSV files at `/inputs`. The database backend adds Hibernate ORM with JPA entities, supporting MariaDB, MySQL, and PostgreSQL. The migration config (`storage.migration-config.*`) suggests a path for migrating from PVC to database storage, which is architecturally significant for the platform's evolution toward a shared database model.

Security-wise, the service itself has no authentication or authorization. In RHOAI 3.x, the TrustyAI Service Operator injects a `kube-rbac-proxy` sidecar container that enforces Kubernetes RBAC before proxying requests to the application container. The service's OpenShift Route in the static manifests has `tls: null`, meaning no TLS termination -- this is likely overridden by the operator at deployment time with proper TLS configuration. The gRPC connector to KServe inference servers uses `usePlaintext()` without TLS, which is acceptable for cluster-internal communication but would not satisfy strict FIPS requirements for all network traffic.

The build pipeline is notable for its PNC (Product Newcastle) integration. Unlike most RHOAI components that build from source in Konflux, TrustyAI uses PNC to pre-build Maven artifacts, producing a zip archive pinned by SHA256 digest in `artifacts.lock.yaml`. The Konflux Dockerfile simply extracts the pre-built Quarkus application from these PNC artifacts rather than running `mvn package`. This provides strong build reproducibility for Java dependencies at the cost of an additional build system dependency.
