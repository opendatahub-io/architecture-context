RBAC Summary:
  RBAC roles and bindings are managed by the TrustyAI Operator, not by this
  service directly. The operator creates necessary ServiceAccount, Roles, and
  RoleBindings for each per-namespace TrustyAI Service deployment.

Authentication & Authorization:
  - External access (8443/TCP): kube-rbac-proxy enforces Bearer Token auth
    via Kubernetes SubjectAccessReview. All external API calls must pass RBAC.
  - Direct HTTPS (4443/TCP): TLS client certificate validation (optional).
    Primarily for operator-to-service communication.
  - Internal HTTP (8080/TCP): No auth. Bound to 127.0.0.1 only — accessible
    exclusively from kube-rbac-proxy sidecar within the same pod.

Secrets:
  - TLS certificates (kubernetes.io/tls) — HTTPS endpoint encryption
    - Mounted at /etc/tls/internal/tls.crt, /etc/tls/internal/tls.key
    - Provisioned by: TrustyAI Operator / cert-manager
    - Auto-rotate: Yes
  - Database credentials (Opaque) — MariaDB authentication
    - Env vars: DATABASE_USERNAME, DATABASE_PASSWORD
    - Provisioned by: TrustyAI Operator
    - Auto-rotate: No
  - Database TLS CA (Opaque) — MariaDB connection encryption
    - Mounted at /etc/tls/db/ca.crt
    - Provisioned by: Cluster admin
    - Auto-rotate: No

FIPS Compliance:
  - System crypto policy set to FIPS via update-crypto-policies --set FIPS
  - Python cryptography library (>=48.0.1) uses OpenSSL FIPS backend
  - MD5 usage: hashlib.md5 with usedforsecurity=False (FIPS-compatible)
  - TLS: Hypercorn ssl_version=2 (TLS 1.2+), inherits FIPS cipher suites

Multi-Tenancy:
  - Tenant boundary: per-namespace (one TrustyAI Service per namespace)
  - Data isolation: per-namespace PVC or per-namespace DB credentials
  - Network isolation: relies on platform NetworkPolicy (not defined here)
  - Compute isolation: per-namespace Deployment with resource limits
