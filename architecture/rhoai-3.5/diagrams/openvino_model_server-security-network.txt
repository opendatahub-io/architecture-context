RBAC Summary:
- OVMS does not define its own RBAC resources (ClusterRoles, RoleBindings).
- RBAC is managed entirely by the deploying operator (KServe InferenceService).
- Access control relies on:
  - kube-rbac-proxy sidecar (platform-injected)
  - Kubernetes NetworkPolicy
  - Istio AuthorizationPolicy (if service mesh enabled)

Authentication Summary:
- OpenAI-compatible endpoints (/v1/chat/completions, /v1/completions, /v1/tokenize, /v3/*):
  - Bearer Token via Authorization header
  - Optional: disabled if no --api_key_file or API_KEY env var set
  - Enforcement: Application-level (http_rest_api_handler.cpp)
- KServe v2 / TFS v1 endpoints (/v1/*, /v2/* non-OpenAI):
  - No application-level auth
  - Relies on platform sidecar (kube-rbac-proxy)
- gRPC (all services):
  - No application-level auth (InsecureServerCredentials)
  - Relies on platform sidecar

Secrets:
- OVMS does not define Kubernetes Secrets.
- Cloud storage credentials passed via environment variables or CLI flags:
  - AWS_ACCESS_KEY_ID, AWS_SECRET_ACCESS_KEY (S3)
  - Azure Storage account keys
  - GCP service account JSON
  - HF_TOKEN (HuggingFace)
- API key file specified via --api_key_file flag or API_KEY env var

Crypto Summary:
- Server endpoints: Plaintext only (no TLS termination)
- Outbound connections: System libcurl → System OpenSSL (UBI9 FIPS-validated)
- Certificate trust: System trust store (ca-bundle.crt)
- No custom crypto implementations
- C++ binary (FIPS Go checks not applicable)

Multi-Tenancy:
- Tenant boundary: per-pod (one OVMS instance per KServe InferenceService)
- No multi-tenant auth within OVMS
- All loaded models accessible to any client on the same endpoint
- Isolation enforced by Kubernetes pod boundaries, not by OVMS
