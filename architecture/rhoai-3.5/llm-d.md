## Purpose

**Short**: llm-d is a Kubernetes-native distributed inference serving stack that provides intelligent routing, KV-cache management, prefill/decode disaggregation, and autoscaling for production LLM deployments.

**Detailed**: The `llm-d/llm-d` repository is the central meta-repository for the llm-d project — a CNCF sandbox project founded by Red Hat, Google Cloud, IBM Research, CoreWeave, and NVIDIA. This repository does not contain application source code (Go, Python, Rust); instead, it serves three critical roles:

1. **Container image build definitions**: Dockerfiles and build scripts for producing vLLM-based model server images across five accelerator platforms (NVIDIA CUDA, AMD ROCm, Intel XPU, CPU, and RDMA tools). These images bundle vLLM with additional optimizations including NIXL (GPU-to-GPU KV-cache transfer), UCCL transport, NVSHMEM shared memory, DeepEP/DeepGEMM kernels, LMCache, FlashInfer, and OpenTelemetry tracing.

2. **Well-lit path deployment guides**: Kustomize-based recipes and Helm values files for deploying the complete llm-d stack on Kubernetes. Guides cover optimized baseline serving, prefix-cache-aware routing, prefill/decode disaggregation, wide expert parallelism, tiered KV-cache offloading, predicted latency routing, workload autoscaling, batch inference, and multi-model routing — all tested across multiple cloud providers (IBM, CoreWeave, GKE, AMD, Intel).

3. **Project governance and documentation**: Architecture documentation, API references, SIG charters, contributing guidelines, proposals, and release process for the multi-repository llm-d ecosystem. The actual inference router logic lives in `llm-d/llm-d-inference-scheduler`, KV-cache management in `llm-d/llm-d-kv-cache`, and autoscaling in `llm-d/llm-d-workload-variant-autoscaler`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Delegated to Gateway layer (Istio AuthorizationPolicy, GKE IAP, etc.) | Gateway/Proxy | Model server itself has no auth — if Gateway is misconfigured, model server is exposed |
| Data storage | Per-pod model weights and KV-cache; PVC per deployment | Kubernetes | Shared model storage (HuggingFace cache) may be shared across pods in same namespace |
| Network traffic | Namespace-scoped InferencePool; NetworkPolicy not defined by default | Kubernetes namespace isolation | No NetworkPolicy defined in guide manifests — relies on cluster-level defaults |
| Compute & resources | GPU resource requests per pod; no ResourceQuota defined | Kubernetes scheduler | No built-in multi-tenant resource quotas |
| Configuration & secrets | Per-namespace Secrets (hf-token); per-InferencePool EPP config | Kubernetes | Shared cluster-wide CRDs (GAIE CRDs are cluster-scoped) |
| API scoping | InferencePool discovery is namespace-scoped | EPP (namespace-scoped watches) | No cross-namespace isolation at API level beyond Kubernetes RBAC |

## Architectural Analysis

The `llm-d/llm-d` repository is architecturally unique among inference platform components because it functions as a meta-repository rather than a source code repository. Its primary build artifacts are container images — not compiled binaries or libraries — that bundle the vLLM inference engine with a curated stack of GPU communication, caching, and kernel optimization libraries. The Dockerfile.cuda is the most complex artifact at over 630 lines, implementing a multi-stage build that compiles NVSHMEM, UCX, UCCL, gdrcopy, DeepEP, DeepGEMM, FlashInfer, and LMCache from source before assembling them with a vLLM installation in a minimal CUDA runtime image. This build-from-source approach allows llm-d to ship patches and optimizations (such as the NVSHMEM zero-ibv-ah-attr patches in `patches/`) that are not yet available upstream.

The repository's version management strategy is centralized in `docker/common-versions`, which pins every dependency to a specific commit SHA or version tag. This acts as a "bill of materials" for each release. The constraints files (`docker/constraints.txt`, `docker/build-constraints.txt`) pin torch and nixl at the Python level to prevent version drift during `uv pip install`. However, the absence of a comprehensive lock file (like `uv.lock`) means builds are not fully hermetic — transitive dependencies can float between builds unless the uv cache is warm.

The well-lit path guides represent a composable deployment architecture. Each guide provides a kustomize overlay on a common base (`guides/recipes/modelserver/base/`), adding accelerator-specific patches, EPP configuration, and optional components. The base/overlay structure is consistent: a `kustomization.yaml` references the base deployment and applies patches for the model server flags, resource requests, and sidecar containers needed for each use case. This kustomize-first approach (adopted in v0.7) replaced earlier Helm-only configurations and enables more fine-grained composition. Gateway selection is similarly overlayable — users choose from Istio, AgentGateway, Envoy AI Gateway, kgateway, or cloud-managed options by applying the appropriate gateway recipe.

The project's governance model through SIGs (11 active SIGs) and proposals (`proposals/` directory with 16 proposals covering autoscaling, batch, disaggregation, observability, and more) reflects the multi-organization nature of the CNCF project. The nightly E2E testing matrix in `release/README.md` shows comprehensive cross-platform validation across 5 hardware vendors (IBM, CoreWeave/CKS, GKE, AMD, Intel) for all major guides. The CI infrastructure uses GitHub Actions with a `pull_request_target` model for fork PR testing, with nightly dispatch workflows for hardware-specific validation.

A notable gap for RHOAI integration is the absence of Konflux build infrastructure. The upstream Dockerfiles use NVIDIA NGC CUDA images as base (`nvcr.io/nvidia/cuda:*`) rather than AIPCC base images, and there are no Konflux-suffixed Dockerfiles, no `rpms.lock.yaml`, and no Hermeto prefetch configuration. The RHOAI downstream will need to add these to meet Red Hat's product security requirements. The model server images also run as a non-root user (UID 2000, GID 0) which is compatible with OpenShift's restricted SCC.
