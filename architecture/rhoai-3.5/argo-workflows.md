## Purpose

**Short**: Argo Workflows is the workflow execution engine that powers Data Science Pipelines in RHOAI, providing container-native workflow orchestration on Kubernetes.

**Detailed**: Argo Workflows is an open-source container-native workflow engine for orchestrating parallel jobs on Kubernetes. In the RHOAI context, it serves as the backend execution engine for Data Science Pipelines, executing DAG-based and step-based workflows that represent ML pipeline runs.

The component consists of two primary binaries shipped for RHOAI: the **workflow-controller** that watches Workflow CRDs and orchestrates pod creation/lifecycle, and the **argoexec** executor that runs as a sidecar within workflow pods to manage artifact I/O, container lifecycle, and result reporting. A third binary (argo CLI / argo-server) exists upstream but is not shipped as a separate Konflux image for RHOAI — the Data Science Pipelines operator manages its own API server deployment.

The workflow controller implements a sophisticated state machine that creates Kubernetes Pods for each workflow step, manages artifact storage across multiple backends (S3, GCS, Azure Blob, HDFS), handles workflow scheduling via CronWorkflows, provides workflow archival to SQL databases, and supports distributed locking via semaphores for concurrency control. The executor binary coordinates with the controller through the Kubernetes API using WorkflowTaskResult and WorkflowTaskSet CRDs as communication channels.

## Architectural Analysis

Argo Workflows in the RHOAI context is a fork of the upstream argoproj/argo-workflows project, tailored for the Data Science Pipelines use case. The RHOAI distribution ships only two of the three upstream binaries — the workflow-controller and argoexec — as separate Konflux-built container images. The argo CLI / argo-server binary is not shipped as a standalone RHOAI image because the Data Science Pipelines operator manages API access through its own API server layer.

The controller's architecture follows the standard Kubernetes operator pattern but with notable complexity. It manages eight different CRD types through a single controller binary using informer-based watches with a 20-minute resync period. The reconciliation loop operates as a state machine in `operator.go`, walking the workflow DAG/step graph and creating pods for each node. The controller supports multiple concurrent worker pools (32 workflow workers, 8 cron workers, 8 archive workers, 4 TTL workers, 4 pod cleanup workers by default), which is significantly more parallelism than typical operators. Leader election uses Kubernetes Leases with a 15-second lease duration, and non-leaders run a "dummy" metrics server to maintain Prometheus scrape targets.

The argoexec emissary executor implements a file-based coordination protocol through the `/var/run/argo/` shared EmptyDir volume. The executor binary is copied into the volume during init, and it replaces the user container's entrypoint to intercept execution. Exit codes, signals, stdout capture, and artifact staging all use filesystem primitives rather than network calls, which avoids the need for a long-running sidecar container. This design is particularly efficient for workflow steps that run quickly, as it eliminates the overhead of a persistent sidecar process.

The FIPS compliance approach is notable: the project recently migrated (commits `5363dfa59`, `736b2245c`) from the traditional OpenSSL-based FIPS approach (`GOEXPERIMENT=strictfipsruntime` + `CGO_ENABLED=1`) to Go 1.26's native FIPS 140-3 module (`GOFIPS140=v1.0.0` + `godebug fips140=on` in go.mod + `-tags no_openssl`). This produces statically linked binaries (`CGO_ENABLED=0`) that use Go's built-in FIPS-certified cryptographic module rather than linking against OpenSSL. This is a newer approach that may require updated check-payload validation rules. The TLS implementation uses ECDSA P-256 for self-signed certificates and supports configurable minimum TLS version (default 1.2). However, several `InsecureSkipVerify: true` settings exist — most are opt-in (SSO config) or constrained (HTTP template executor), but the self-signed cert TLS config unconditionally sets it, which is a minor security observation.

Build hermeticity is well-addressed at the Go and RPM layers — `go.sum` locks all Go dependencies, `rpms.lock.yaml` locks the single `mailcap` RPM across three architectures (aarch64, ppc64le, x86_64), and `yarn.lock` locks the UI JavaScript dependencies. The absence of Hermeto/cachi2 prefetch integration means the Go module download during build is not hermetically cached, though `go.sum` verification provides integrity guarantees. The UI (yarn/Node.js) is not shipped in the Konflux images — only the Go binaries are packaged.
