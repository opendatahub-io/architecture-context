## Purpose

**Short**: LMEval is a secure, batch-oriented execution environment for language model evaluations using the lm-evaluation-harness framework, integrated with EvalHub for orchestrated benchmark execution on RHOAI.

**Detailed**: LM Evaluation Harness (LMEval) is a downstream fork of EleutherAI's `lm-evaluation-harness` library, adapted for use within the Red Hat OpenShift AI (RHOAI) platform as a batch evaluation job. The component runs standardized language model benchmarks (e.g., MMLU, HellaSwag, GPQA, BBH) against models served via OpenAI-compatible inference endpoints. It ships as a container image (`odh-ta-lmes-job`) designed to run as a one-shot Kubernetes Job, processing a job specification from a mounted ConfigMap.

The Red Hat adaptation adds an EvalHub adapter layer (`main.py`) that integrates the upstream framework with the EvalHub orchestration platform. This adapter reads a job specification JSON from `/meta/job.json`, configures the `local-completions` backend to target an OpenAI-compatible model endpoint, runs the evaluation, and reports results back via EvalHub callbacks. It also supports OCI artifact persistence (via `olot` and `skopeo`), air-gapped/offline execution (auto-detecting local HuggingFace datasets under `/test_data`), credential redaction in error messages, and HuggingFace gated dataset authentication.

The component includes 157+ benchmark task definitions (6,500+ YAML configurations), 56 offline metric modules, and supports multiple model backends including HuggingFace Transformers, vLLM, GGUF, IBM watsonx.ai, Anthropic, and OpenAI-compatible APIs. In the RHOAI deployment context, the `local-completions` backend is the primary model interface, connecting to model serving endpoints via HTTP.

## Architectural Analysis

The LM Evaluation Harness is a downstream fork of EleutherAI's widely-adopted evaluation framework, adapted to function within the RHOAI platform's EvalHub orchestration system. The most significant architectural addition over upstream is `main.py`, which implements the `LMEvalAdapter` class — a `FrameworkAdapter` subclass from the `eval-hub-sdk`. This adapter transforms the upstream CLI-oriented tool into a service-oriented batch processor that reads structured job specifications, manages lifecycle callbacks, and produces machine-readable evaluation results.

The adapter's OpenAI-compatible endpoint integration is the primary model backend for RHOAI deployments. The `build_lmeval_config()` function constructs `local-completions` model arguments from the job spec, building a completions URL from the model's base URL and configuring concurrent request limits (capped at 128). This design allows LMEval to evaluate any model exposed via an OpenAI-compatible API — including vLLM, TGI, and other serving frameworks deployed on RHOAI — without requiring direct model loading into the evaluation pod. The evaluation pod runs on CPU only (line 739: `device="cpu"`), keeping GPU resources dedicated to model serving.

The credential handling architecture in `main.py` implements defense-in-depth: the `_sanitize_error_message()` function redacts authorization headers, bearer tokens, API keys, and URL credentials from error messages before they're sent to EvalHub callbacks. The `_resolve_job_spec_path_for_read()` function mitigates path traversal (CWE-22) by resolving the job spec path and verifying it stays under `/meta`. The `_evaluation_failure_for_evalhub()` function maps HTTP error codes from model endpoints to semantic error codes (e.g., `gated_dataset_auth_required`, `model_authentication_failed`) that EvalHub can display to users.

The offline/air-gapped execution support is implemented via the `_seed_hf_offline_before_lm_eval_import()` function, which runs at module import time (before `lm_eval` is imported) to configure HuggingFace environment variables that prevent outbound Hub calls. Auto-detection is sophisticated: it checks that the tokenizer path exists under `/test_data`, is not the mount root itself, and that a sibling directory contains a `dataset_dict.json` file. The `lm_eval/api/task.py` file contains complementary offline support with `_offline_datasetdict_bundle_dir()` that resolves HuggingFace dataset bundles from local paths.

The repository carries a substantial multi-architecture build footprint: the Konflux Dockerfile includes four build stages dedicated to compiling PyTorch, Apache Arrow, and OpenBLAS from source for s390x and ppc64le architectures. These source builds account for the majority of build time and complexity. Migration to AIPCC base images would potentially simplify this by using pre-built wheels from the RHEL AI Python Package Index, though coverage for all three architectures (x86_64, s390x, ppc64le) would need to be verified.
