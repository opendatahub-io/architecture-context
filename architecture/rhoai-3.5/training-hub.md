## Purpose

**Short**: Python library providing an algorithm-focused interface for LLM fine-tuning, continual learning, and reinforcement learning.

**Detailed**: Training Hub (`training-hub` on PyPI) is a pure Python library that abstracts the complexity of LLM training behind a unified, algorithm-centric API. It supports multiple training paradigms -- Supervised Fine-Tuning (SFT), Orthogonal Subspace Fine-Tuning (OSFT), LoRA-based parameter-efficient fine-tuning (including QLoRA/DoRA), Group Relative Policy Optimization (GRPO) for reinforcement learning from verifiable rewards (RLVR), and Genetic-Pareto prompt optimization (GEPA) -- each with interchangeable backend implementations.

The library uses a registry pattern where algorithms declare their required and optional parameters, and backends handle the actual training execution. This design allows the same algorithm (e.g., LoRA+GRPO) to run on different engines (ART/OpenPipe vs. verl/Volcano Engine) without changing user code. Training Hub integrates with PyTorch distributed training (torchrun), experiment tracking (W&B, MLflow, TensorBoard), and GPU memory estimation for capacity planning.

Training Hub is not a deployed service -- it is a client-side library consumed by notebooks, scripts, and training pipelines within the RHOAI ecosystem. It ships as a pip-installable package with optional extras for CUDA acceleration, LoRA support, GRPO backends, and development dependencies.

## Architectural Analysis

### Algorithm-Backend-Registry Pattern

Training Hub's core design is a three-layer abstraction: **Algorithms** define training semantics and parameter schemas, **Backends** handle execution against specific engines, and a **Registry** connects them. This pattern enables adding new algorithms or swapping backends without changing the user-facing API. For example, `grpo()` is an alias for `lora_grpo()` with `lora_r=0` and defaults to the verl backend -- a single convenience function bridging two different algorithm configurations.

The registry's `create_algorithm()` factory function resolves algorithm names to classes and attaches the appropriate backend. Each algorithm class exposes `get_required_params()` and `get_optional_params()` for self-documenting parameter discovery, which the coding agent plugins use to generate accurate tool schemas.

### Subprocess Isolation for RL Backends

Both GRPO backends (ART and verl) run training in subprocesses rather than in-process. This is a deliberate architectural choice driven by two constraints: (1) vLLM's inference server initialization conflicts with the parent process's GPU memory management, and (2) ART and verl each have complex dependency trees that can conflict with each other. Subprocess isolation prevents GPU memory leaks, avoids import conflicts, and allows clean process termination after training completes. The `_force_exit_subprocess()` utility specifically addresses vLLM 0.21+ hang issues where background threads prevent clean shutdown.

### Type Validation System

OSFT's algorithm implementation includes a custom type validation system (`_validate_param_type()`) that handles Python typing generics (Union, Optional, Literal, list, dict) for runtime parameter checking. This is unusual for a training library and reflects the team's focus on developer experience -- providing clear error messages when parameters are misconfigured, rather than failing deep in the training loop.

### Memory Estimation as Architecture

The profiling module models GPU memory consumption analytically rather than empirically. It decomposes memory usage into model parameters, gradients, optimizer states (AdamW = 2 state tensors), activations, and outputs, with low/mid/high bounds. This is architecturally significant because it enables capacity planning before committing GPU resources -- a user can estimate whether a model fits in available VRAM without downloading the model weights.

### No Deployment Footprint

Training Hub is notable among RHOAI components for having zero deployment infrastructure. No Dockerfiles, no Kubernetes manifests, no CRDs, no RBAC, no network services. It is consumed as a transitive dependency by notebooks and training pipelines. This means its security posture is entirely inherited from the consuming environment -- FIPS compliance, network policies, and tenant isolation are all the responsibility of the platform layer.

### Supply Chain Considerations

The `litellm` dependency explicitly excludes version 1.82.0 (`!=1.82.0`), which was identified as containing a supply chain issue. The library also pins floor versions for critical dependencies (torch>=2.6.0, transformers>=4.51.0) to ensure compatibility with RHOAI's tested configurations. Optional extras (cuda, lora, grpo, grpo-verl, gepa) keep the base installation lightweight while allowing users to opt into specific training capabilities.

### Multi-Turn RLVR Decomposition

The LoRA+GRPO algorithm supports multi-turn conversational training through trace decomposition (`_decompose_multiturn_traces()`). This converts multi-turn conversation histories into individual turn-level training examples, enabling GRPO to optimize each assistant response independently while maintaining conversational context. This is architecturally important for tool-calling agent training where each tool invocation in a conversation needs separate reward evaluation.
