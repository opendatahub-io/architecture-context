## Purpose

**Short**: Module operator that manages AI Gateway sub-components (batch-gateway-operator and maas-controller) for the OpenDataHub/RHOAI platform.

**Detailed**: ai-gateway-operator is a Kubernetes operator that runs as a module operator under the opendatahub-operator (or rhods-operator in RHOAI). It reconciles a single cluster-scoped `AIGateway` custom resource to deploy and manage two sub-components: the batch-gateway-operator (for batch LLM inference) and the maas-controller (for Models as a Service multi-tenant model management).

The operator follows the ODH modular architecture pattern: it vendors kustomize manifests from its sub-component repositories at pinned commit SHAs via `hack/scripts/get-manifests.sh`, embeds them in its container image, and renders/deploys them via server-side apply (SSA) based on the `AIGateway` CR's `managementState` fields. Each sub-component can be independently set to `Managed` or `Removed`. The operator reports per-sub-module ready conditions (`BatchGatewayReady`, `ModelsAsAServiceReady`) and implements a coordinated teardown protocol for MaaS that waits for the maas-controller to complete its self-cleanup before garbage-collecting its resources.

The operator also manages cross-namespace infrastructure RBAC, creating a dedicated infrastructure namespace (`redhat-ai-gateway-infra` for RHOAI, `odh-ai-gateway-infra` for ODH) with Role/RoleBinding resources that allow the maas-controller service account to migrate database connection secrets across namespaces during upgrades.

## Architectural Analysis

The ai-gateway-operator follows the ODH modular architecture pattern, where a "module operator" acts as a lifecycle manager for a family of related sub-components. This is a two-tier operator hierarchy: the platform operator (opendatahub-operator) creates the AIGateway CR, and ai-gateway-operator reconciles it by rendering vendored kustomize manifests and deploying them via server-side apply. This pattern cleanly separates platform-level concerns (which components are enabled) from component-level concerns (how to deploy and configure each sub-component).

The vendored manifest approach (pinned commit SHAs in `hack/scripts/get-manifests.sh`) provides strong reproducibility but creates a coupling between the operator release and its sub-component versions. The `batchgateway` manifests come from `llm-d-batch-gateway-operator` and the `maascontroller` manifests come from `models-as-a-service`, each pinned to specific commits for both ODH and RHDS repositories. The init container pattern (`copy-manifests`) copies vendored manifests from the image to a writable emptyDir at startup, ensuring the operator has mutable access to manifest files for kustomize rendering while the container image remains read-only.

The MaaS teardown protocol is notably sophisticated: rather than simply deleting the maas-controller Deployment when `modelsAsAService.managementState` transitions to `Removed`, the operator annotates the Deployment with `maas.opendatahub.io/teardown-requested=true`, keeps the controller running while it performs self-cleanup (deleting the Config/default anchor, cleaning up runtime resources), and only garbage-collects the MaaS resources after the controller reports completion via `maas.opendatahub.io/teardown-completed=true`. The `maasAwareGCPredicate` augments the default generation-based garbage collection to recognize this out-of-band completion signal. This prevents orphaned resources that would result from premature deletion.

The RBAC configuration is extensive because the operator must hold escalation permissions for both sub-components' ClusterRoles — it creates ClusterRoles that grant permissions the operator itself must also have. This is documented explicitly in the kubebuilder markers in `aigateway_controller.go`. The scope of RBAC touches a large number of API groups including Gateway API, Kuadrant, Istio, OpenTelemetry, Perses, and cert-manager, reflecting the breadth of infrastructure that the MaaS controller manages at runtime. The infrastructure namespace RBAC (`redhat-ai-gateway-infra`) is tightly scoped: the Role only permits `create` on secrets generally and `get` on the specific `maas-db-config` secret, minimizing the blast radius of the cross-namespace secret migration capability.

The platform version upgrade handshake mechanism (reading `data.platformVersion` from the `odh-aigateway-config` ConfigMap and echoing it into `status.releases`) enables coordinated version alignment between the platform operator and the module operator. The `withPreservedPlatformRelease` wrapper ensures that a failed reconcile cannot wipe the existing platform handshake entry, which would cause the platform operator to incorrectly detect a version mismatch.
