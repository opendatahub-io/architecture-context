## Purpose

**Short**: Pluggable Go library and sidecar services for KV-cache-aware routing and cross-node cache coordination in vLLM-based LLM inference platforms.

**Detailed**: The llm-d-kv-cache project provides the core KV-cache indexing library used by llm-d to enable intelligent request routing based on KV-cache block locality. It maintains a near-real-time, globally consistent view of KV-cache block residency across a fleet of vLLM (or SGLang) pods by subscribing to KV-Events emitted over ZeroMQ. The library exposes a fast scoring API that ranks pods by how much of a request's prefix they already have cached, enabling the scheduler to route requests to pods with the highest cache hit ratio, reducing Time To First Token (TTFT) and improving throughput.

The repository also provides companion components: a UDS tokenizer sidecar service (the only Konflux-built image), a filesystem storage backend for KV-cache offloading (llmd-fs-backend, now upstreamed into vLLM), and a PVC evictor utility for automated disk space management of offloaded cache blocks. The Go library is designed to be embedded in a host process (llm-d's Envoy Processing Policy is the reference consumer) rather than deployed as a standalone service.

## Architectural Analysis

The llm-d-kv-cache project follows a modular library architecture where the core KV-cache indexing logic is designed to be embedded rather than deployed as a standalone service. This is an unusual pattern in the RHOAI ecosystem — most components are operators or services — but it is appropriate here because the indexer must operate on the critical path of every inference request with sub-millisecond latency. The design avoids network hops by running inside the host process (llm-d's EPP/router).

The **dual-key design** is the most architecturally significant pattern in the codebase. The indexer maintains two independent hash spaces: "engine keys" (content hashes from vLLM/SGLang) and "request keys" (the indexer's own hashes computed from token sequences). On ingestion, `BlockStored` events carry token chunks that let the indexer build a bridge between the two spaces. On eviction, `BlockRemoved` events only carry engine keys, so the bridge is essential. On scoring, only request keys are used — the indexer computes them from the prompt's tokens without needing to contact the engine. This separation enables the indexer to score pods without a round-trip to any engine and makes the design engine-agnostic.

The **sharded event processing pool** uses FNV-1a hashing on pod identifiers to assign each pod's event stream to a dedicated worker queue. This ensures per-pod event ordering (critical for the dual-key bridge consistency) while enabling parallel processing across pods. The pool supports two delivery modes: centralized (single ZMQ endpoint) and pod-discovery (Kubernetes label selector-based per-pod subscriptions), with the latter enabling active-active multi-replica deployments.

The **index backend abstraction** allows plugging in different storage strategies: in-memory LRU (lowest latency, default), Ristretto cost-aware cache (memory-bounded, better for multimodal workloads with variable entry sizes), and Redis/Valkey (persistent but adds network latency). The in-memory backend is recommended for most deployments since each replica converges independently from the event stream. The factory pattern with instrumentation (Prometheus) and tracing (OpenTelemetry) wrappers applied via the decorator pattern keeps observability concerns separate from storage logic.

The **UDS Tokenizer** is the only Konflux-built artifact in this repository. It runs as a sidecar communicating over a Unix Domain Socket to avoid network overhead. The service wraps vLLM's `OpenAIServingRender` for chat template application and tokenization, supporting multimodal inputs with image placeholder tracking. The gRPC interface is designed with a 100MB message size limit to accommodate large multimodal payloads. The tokenizer's in-process tokenization pool is deprecated in favor of external tokenization — new consumers should call `ScoreTokens` directly with pre-tokenized input.

The **PVC Evictor** implements a sophisticated multi-process architecture with N crawlers (load-balanced by hex bucket modulo distribution), an activator (monitoring disk usage against configurable thresholds), a deleter (batched file removal via `xargs rm -f`), and an optional folder cleaner. The processes coordinate through multiprocessing Events and Queues, with the main process monitoring and auto-restarting dead children. This design handles the high file count and I/O contention of KV-cache storage on shared PVCs effectively.

A notable security gap is the lack of encryption and authentication on ZMQ event streams and the gRPC tokenizer service. The ZMQ transport relies entirely on network-level isolation (pod networking), and the gRPC tokenizer uses insecure credentials with no TLS. While appropriate for pod-internal UDS communication, the TCP fallback mode for testing and the ZMQ TCP subscriptions to remote pods are unprotected. Redis/Valkey connections optionally support TLS via the `rediss://` URL scheme.
