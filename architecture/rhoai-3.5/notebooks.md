## Purpose

**Short**: Builds container images for interactive data science workbenches (JupyterLab, Code-Server) and Elyra pipeline runtime images, spanning CPU, NVIDIA CUDA, and AMD ROCm accelerator variants.

**Detailed**: The notebooks repository produces the complete set of workbench container images used by Red Hat OpenShift AI (RHOAI) for interactive data science work. It defines 18 Konflux-built container images across three image families: Jupyter notebook workbenches (10 variants), Elyra pipeline runtime images (7 variants), and Code-Server (VS Code in the browser, 1 variant). Each variant targets a specific accelerator (CPU, NVIDIA CUDA 12.9/13.0, or AMD ROCm 7.14) and Python version (3.12).

The images are not standalone services — they are launched by the ODH Notebook Controller as pods on OpenShift clusters. The repository also produces OpenShift ImageStream manifests consumed by the platform operator (`rhods-operator`/`opendatahub-operator`) via kustomize. These manifests define how the dashboard discovers and presents workbench images to users. Each ImageStream carries up to four version tags (N, N-1, N-2, N-3) enabling rolling upgrades while preserving backward compatibility.

All RHOAI builds use AIPCC (AI Practices and Controls) base images from `quay.io/aipcc/base-images/`, with hermetic builds enforced via Konflux and Cachi2 prefetching. The repository includes a comprehensive CI/testing infrastructure (pytest, testcontainers, Playwright browser tests), dependency management via `uv` with per-variant lock files, and CVE-constraint-driven dependency pinning.

## Architectural Analysis

The notebooks repository follows a **multi-stage Dockerfile pattern** where each image variant embeds all ancestor stages rather than referencing parent images. For example, the PyTorch CUDA Dockerfile chains `cpu-base` → `cuda-jupyter-minimal` → `cuda-jupyter-datascience` → `cuda-jupyter-pytorch`, all in one file. This design eliminates inter-image build dependencies at the cost of code duplication across Dockerfiles. The duplication is managed through shared utility scripts in `jupyter/utils/` and `base-images/utils/`, with the `scripts/dockerfile_fragments.py` tool suggesting the team is exploring automated fragment management.

The **AIPCC base image integration** is thorough — every RHOAI Konflux Dockerfile uses digest-pinned AIPCC images, with base image versions centrally managed in `versions_config.yml` and propagated via `make sync-build-args-from-versions`. This ensures atomic updates of base images across all 18 variants. The per-variant `build-args/konflux.{cpu,cuda,rocm}.conf` files serve as the single source of truth for each image's base and product configuration.

The **Code-Server idle culling architecture** is notably complex: nginx (port 8888) reverse-proxies to code-server (port 8787) while also hosting an httpd CGI gateway (port 8080) that runs `access.cgi` — a bash script that polls code-server's healthz endpoint and translates heartbeat timestamps into Jupyter-compatible `/api/kernels/` JSON. This three-process stack exists because the notebook controller's culler expects a Jupyter API. The existing `ARCHITECTURE.md` acknowledges this is fragile and planned for replacement with a single Go reverse proxy.

The **dependency management** strategy uses `uv` with per-variant lock files (`pylock.{cpu,cuda,rocm}.toml`), CVE-constraint-driven minimum versions (`dependencies/cve-constraints.txt`), and meta-packages (`dependencies/odh-notebooks-meta-*-deps/`) that aggregate dependency groups. This enables centralized CVE patching while maintaining per-image flexibility. The `FIPS: exclude py-spy` comment in multiple `pyproject.toml` files reveals a practical FIPS concern: the `py-spy` profiler is a statically linked Rust binary that would fail check-payload validation.

The **kustomize manifest pipeline** is sophisticated: `params.env` / `params-latest.env` contain parameterized image references that are injected into ImageStreams via kustomize `replacements` (not the older `vars` mechanism). Each ImageStream carries up to 4 version tags (N, N-1, N-2, N-3), enabling the dashboard to show both current and previous workbench versions. The replacement rules in `kustomization.yaml` constitute over 1300 lines, reflecting the combinatorial complexity of 18 images × 4 version tags × 2 ConfigMaps (params + commit hashes).
