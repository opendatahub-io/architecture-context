## Purpose

**Short**: LLM deployment planning service that guides users from business requirements to production-ready Kubernetes configurations through capacity analysis, GPU performance estimation, and SLO-driven recommendations.

**Detailed**: llm-d Planner is a multi-tier web application that unifies LLM deployment planning into a single workflow. It provides three core capabilities: (1) a conversational Planner that extracts deployment intent from natural language, maps it to traffic profiles and SLO targets, queries benchmark databases, and produces ranked model+GPU recommendations; (2) a Capacity Planner that estimates GPU memory requirements (model weights, KV cache for MHA/GQA/MQA/MLA attention types, activation memory, system overhead) for any HuggingFace model; and (3) a GPU Recommender that estimates inference performance (TTFT, ITL, throughput) across GPU types using BentoML's roofline model without running actual benchmarks.

The service is deployed as a FastAPI backend with a Streamlit UI frontend, backed by PostgreSQL for benchmark storage and Ollama (or OpenAI/Vertex AI) for LLM-powered intent extraction. It integrates with the RHOAI Model Catalog for benchmark data synchronization and can deploy generated KServe InferenceService manifests directly to Kubernetes clusters. The architecture supports both a standard vLLM deployment stack and the llm-d stack (via kustomize overlays and Helm values).

## Architectural Analysis

The llm-d Planner follows a classic three-tier architecture (UI → API → DB) but with significant computational depth in the API tier. The FastAPI backend is not just a CRUD service; it embeds a full GPU memory estimation engine implementing vLLM's KV cache math, a multi-criteria recommendation scoring system, and an LLM-powered intent extraction pipeline. The decision to run these computations server-side rather than in a separate computation service keeps the deployment simple but means the backend is CPU-intensive during capacity calculations.

The LLM provider abstraction (`llm/client.py` Protocol + `llm/factory.py` factory) is well-designed, using Python's structural typing to allow plug-in of Ollama, OpenAI, and Vertex AI backends without inheritance. However, the intent extraction pipeline is tightly coupled to a specific prompt format (`llm/prompts.py`) with hard-coded rules for 9 use cases, which means adding new use cases requires code changes rather than configuration. The `_clean_llm_output()` method in `extractor.py` contains extensive hallucination correction logic (alias maps, fuzzy matching), suggesting the LLM's raw output quality is variable and the system compensates at the application layer.

The Kubernetes integration layer uses `kubectl` subprocess calls rather than the native `kubernetes` Python SDK for deployment operations (`cluster/manager.py`). While the SDK is used for GPU detection (`cluster/gpu_detector.py`), the deployment path shells out to `kubectl apply`, `kubectl delete`, and `kubectl get`. This is a reliability concern: subprocess calls are harder to test, have less structured error handling, and depend on `kubectl` being available in the container image. The per-namespace `KubernetesClusterManager` caching with a 32-entry limit and `asyncio.Lock` is a reasonable pattern but could become a bottleneck under concurrent multi-namespace usage.

The benchmark data pipeline has two distinct paths: (1) static JSON files loaded via `scripts/load_benchmarks.py` for BLIS/estimated/interpolated data, and (2) dynamic synchronization from the RHOAI Model Catalog via a background daemon thread (`_sync_model_catalog_async`). The ETL process in `model_catalog_sync.py` is destructive -- it deletes all rows with `source='model_catalog'` before inserting fresh data, which creates a brief window where queries may return incomplete results. The `config_id` hash-based deduplication prevents duplicate inserts across different loading mechanisms.

Security is minimal for an incubation-stage project. CORS is wide open (`allow_origins=["*"]`), the DB admin password is optional, and there is no authentication on API endpoints that can deploy workloads to Kubernetes clusters. The `trust_remote_code=True` flag in HuggingFace's `AutoConfig.from_pretrained()` is an acknowledged security risk that executes arbitrary Python code from model repositories. These gaps are expected at this stage but must be addressed before productization. The deployment manifests do include security context constraints (runAsNonRoot, drop ALL capabilities, seccompProfile: RuntimeDefault) and the service-ca integration for Model Catalog TLS is properly configured.
