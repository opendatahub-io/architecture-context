## Purpose

**Short**: A curated library of reusable Kubeflow Pipelines (KFP) components and pre-assembled pipelines for AI/ML workflows on Red Hat OpenShift AI, packaged as both a Python SDK and container images.

**Detailed**: The pipelines-components repository provides the building blocks for AI/ML pipelines on RHOAI. It contains 27+ individual KFP components spanning data processing, model training, evaluation, and deployment, plus 18+ pre-assembled pipelines that compose these components into end-to-end workflows. Components cover domains including AutoML (AutoGluon tabular and time-series), AutoRAG (automated RAG pattern optimization via ai4rag), LLM fine-tuning (SFT, LoRA, OSFT via instructlab-training), model evaluation (lm-eval, EvalHub), data ingestion (Milvus, S3, OGX), and model deployment (KServe InferenceService, vLLM).

The repository also produces three container images via Konflux: an init container (`odh-pipelines-components`) that compiles "managed" pipeline YAML at build time and copies it to the KFP API server's shared volume at startup, and two runtime images (`odh-automl`, `odh-autorag`) that provide pre-installed Python dependencies for AutoML and AutoRAG pipeline steps. The init container enables the RHOAI operator to register curated pipelines automatically when a DataSciencePipelinesApplication CR is created, while the runtime images use AIPCC base images to ensure supply-chain compliance and accelerator support.

## Architectural Analysis

The pipelines-components repository implements a **library-first architecture** where reusable KFP components serve as building blocks composed into higher-level pipelines. This design enables both curated "managed" pipelines (shipped with the platform) and user-authored custom pipelines using the same component primitives. The distinction between managed and non-managed pipelines is a key architectural decision: managed pipelines (`managed: true` in `metadata.yaml`) are compiled at build time, embedded in the init container image, and automatically registered with the KFP API server, while non-managed pipelines exist as reference implementations or experimental offerings.

The **init container pattern** is noteworthy: `generate_managed_pipelines.py` compiles pipeline Python definitions to KFP YAML at image build time, and `init_managed_pipelines.py` copies them to a shared PVC at container startup. The system includes a recompilation mode triggered by `RELATED_IMAGE_*` environment variables, allowing the RHOAI operator to override runtime container images without rebuilding the init container. This decouples pipeline logic from runtime image references, enabling independent lifecycle management.

The repository's **two-tier image strategy** separates concerns effectively. The init container (`odh-pipelines-components`) is built on plain UBI9 and contains the pipeline compilation toolchain (KFP compiler, all component source). The runtime images (`odh-automl`, `odh-autorag`) are built on AIPCC CPU base images and contain heavy ML dependencies (AutoGluon at 1.5.0+rhaiv.5 with Red Hat patches, ai4rag with 1000+ transitive dependencies). This separation means the init container stays lightweight (~200MB of Python deps) while runtime images can be large (multi-GB with ML frameworks) without affecting platform startup time.

A significant supply-chain architecture choice is the use of the **RHEL AI Python Package Index** (`console.redhat.com/api/pypi/public-rhai/rhoai/3.5/cpu-ubi9/simple`) rather than public PyPI. All locked requirements files pin to this index with SHA256 hashes, and the `make pipeline-requirements` target uses container-based `pip-compile` against this index to ensure platform-consistent resolution. The `refresh_pipeline_requirements` script runs `pip-compile` inside a UBI9 container to guarantee `manylinux_2_34` wheel compatibility, preventing host-OS contamination. Combined with hermetic Tekton builds (`hermetic: true` in all three Tekton PipelineRuns), this creates a reproducible and auditable build pipeline.

The **AutoRAG architecture** deserves attention: the `odh-autorag` container embeds pre-downloaded docling models from Red Hat modelcar OCI images (`registry.redhat.io/rhai/modelcar-docling-project-docling-layout-heron:3.0` and `modelcar-docling-project-docling-models`). These models are copied at build time via multi-stage Docker builds, enabling fully offline text extraction during pipeline execution. The `DOCLING_ARTIFACTS_PATH` environment variable points the docling library to these embedded models, avoiding runtime downloads. This is a thoughtful design for air-gapped or network-constrained environments, though it significantly increases the AutoRAG image size.

Component stability follows a three-tier model (Alpha → Beta → Stable/Experimental) with `lastVerified` freshness tracking. Currently, managed pipelines are exclusively Beta-stability (AutoML tabular/timeseries, AutoRAG optimization, documents indexing), while fine-tuning pipelines are Alpha, and EvalHub variants are Experimental. The `generate_managed_pipelines` script enforces that only Alpha/Beta/Stable pipelines can be marked as managed — Experimental is excluded. This gating mechanism ensures platform-shipped pipelines meet a minimum quality bar.
