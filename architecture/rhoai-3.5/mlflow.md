## Purpose

**Short**: MLflow is an open-source ML experiment tracking, model registry, and artifact management platform, adapted for multi-tenant Kubernetes deployment in Red Hat OpenShift AI.

**Detailed**: MLflow provides a comprehensive platform for the complete machine learning lifecycle including experiment tracking (runs, metrics, parameters), model registry (versioning, staging, production promotion), artifact storage (models, datasets, logs), and an interactive web UI for visualization and comparison. The RHOAI fork extends upstream MLflow with workspace-based multi-tenancy backed by Kubernetes namespaces, a pluggable authentication system with RBAC, and a React frontend with PatternFly CSS integration and module federation for embedding within the RHOAI dashboard.

The server is a Python application built on Flask (WSGI) and FastAPI (ASGI), fronted by uvicorn. It exposes REST, GraphQL, and gRPC-compatible APIs for experiment tracking, model registry, AI Gateway (LLM proxy with rate limiting and guardrails), and an MCP (Model Context Protocol) server registry. The Helm chart packages the server for Kubernetes deployment with optional TLS, NetworkPolicy, Prometheus metrics, garbage collection CronJob, and persistent storage. In RHOAI, the platform operator deploys MLflow via this chart and injects workspace-scoped auth via the `kubernetes-auth` app plugin and `mlflow-kubernetes-plugins` package.

## Architectural Analysis

MLflow's architecture in RHOAI represents a substantial fork of the upstream Databricks-originated project, adapted for multi-tenant Kubernetes deployment. The most significant architectural decision is the workspace-based multi-tenancy model, where Kubernetes namespaces map directly to MLflow workspaces. This is implemented through column-based tenant isolation in a shared database (every tracking table includes a `workspace` column) rather than database-per-tenant separation. The `mlflow-kubernetes-plugins` package bridges the gap by auto-detecting the pod's namespace from the service account mount and injecting it as the `X-MLFLOW-WORKSPACE` header. This approach is pragmatic but carries the inherent risk of application-level isolation: a bug in query filtering could leak cross-workspace data, and the workspace header is trusted after authentication without server-side namespace verification against the Kubernetes API.

The server architecture layers Flask (WSGI) inside FastAPI (ASGI) via a custom `_EfficientWSGIMiddleware` that avoids the O(n^2) body buffering of the standard Starlette WSGIMiddleware. Native FastAPI routers handle newer subsystems (AI Gateway, MCP server registry, OpenTelemetry, Assistant, Jobs) while the Flask app handles the legacy tracking and model registry APIs. This dual-framework approach allows incremental migration of endpoints from Flask to FastAPI without a rewrite, but it creates a split where some endpoints benefit from async ASGI handling while others remain synchronous.

The gateway secrets subsystem uses envelope encryption (AESGCM via the `cryptography` library) with a server-wide Key Encryption Key (KEK) derived from a passphrase via PBKDF2 with 600,000 iterations. The fixed salt is an intentional design decision documented in `mlflow/utils/crypto.py` -- since the passphrase is an admin-controlled server credential (not user passwords), per-deployment random salts would add complexity without meaningful security benefit. However, the default passphrase (`mlflow-default-kek-passphrase-for-development-only`) means installations that don't set `MLFLOW_CRYPTO_KEK_PASSPHRASE` share the same encryption key, which is a deployment hygiene concern rather than a code defect.

The Helm chart demonstrates thoughtful Kubernetes-native design: automatic strategy selection (Recreate for ReadWriteOnce PVC or SQLite, RollingUpdate otherwise), comprehensive security context (non-root, read-only root filesystem, all capabilities dropped, seccomp RuntimeDefault), and a NetworkPolicy that precisely scopes egress to DNS, Kubernetes API, databases, and S3. The garbage collection CronJob adds operational hygiene for long-running deployments. The chart does not create RBAC by default, requiring explicit configuration when the server needs Kubernetes API access (e.g., for workspace namespace operations).

The fork maintenance process documented in `FORK_HISTORY.md` reveals a rebase-based workflow where upstream releases are periodically rebased onto the ODH fork, with commits categorized as "keep" (Red Hat-specific) or "drop" (already upstreamed). This creates a clear provenance trail but requires manual conflict resolution on each rebase, particularly around the UI (i18n keys, PatternFly CSS overrides, module federation configuration) and CI tooling.
