## Purpose

**Short**: CPU-only build of vLLM, a high-throughput inference engine for large language models optimized for running without GPU hardware.

**Detailed**: vLLM CPU is the CPU-only variant of the vLLM inference and serving engine, packaged as a container image for Red Hat OpenShift AI (RHOAI). It provides an OpenAI-compatible HTTP API server and an optional gRPC server for serving LLM inference requests on CPU hardware, supporting architectures including x86_64, ppc64le (IBM POWER), and s390x (IBM zSystems).

The component is a downstream fork of the upstream vllm-project/vllm repository, rebased onto the `rhoai-3.5` branch with RHOAI-specific patches for multi-architecture builds, FIPS-aware hashing, and Red Hat container standards. It supports a wide range of model architectures, quantization formats (AWQ, GPTQ, compressed-tensors), continuous batching, prefix caching, LoRA adapters, tool calling, structured output via grammar-constrained decoding, multimodal inputs (images, audio, video), and OpenTelemetry-based observability.

In the RHOAI platform, vLLM CPU is deployed as an InferenceService via KServe, running as a model-serving container in user namespaces. It is the inference runtime for CPU-based model serving workloads and integrates with the platform's model registry, dashboard, and monitoring infrastructure.

## Architectural Analysis

vLLM CPU is architecturally a single-process Python inference server with optional Rust and C/C++ acceleration components. The primary entry point (`python -m vllm.entrypoints.openai.api_server`) launches a FastAPI application on Uvicorn, exposing an OpenAI-compatible API surface. The engine core uses PyTorch for model execution, with CPU-specific optimizations via Intel Extension for PyTorch (x86_64), OpenMP thread binding, and custom C/C++ attention kernels compiled through CMake (AVX2 and AVX512 variants for x86_64). The architecture follows a producer-consumer pattern: the API server accepts requests, the scheduler batches them for continuous processing, and the model executor runs inference on the CPU. KV cache management uses blocked memory allocation with configurable block sizes and prefix caching.

The Rust frontend (`vllm-rs`) is a significant architectural element -- it implements high-performance tokenization, chat template rendering (via minijinja), tool call parsing, and reasoning output parsing as compiled Rust code exposed to Python via PyO3 bindings. The Rust workspace contains 12 crates organized by function: `chat`, `cmd`, `engine-core-client`, `llm`, `managed-engine`, `metrics`, `mock-engine`, `reasoning-parser`, `server`, `text`, `tokenizer`, and `tool-parser`. For the CPU container image, the Rust frontend is built from source during the Docker build process using the 1.95 stable toolchain.

Multi-architecture support is a first-class concern in this component. The `Dockerfile.konflux.cpu` uses architecture-conditional logic (`uname -m` checks) to install different system packages and apply different build procedures for x86_64, ppc64le, and s390x. Dedicated build scripts (`build_vllm_ppc64le.sh`, `build_vllm_s390x.sh`) handle architecture-specific dependency resolution, including building PyTorch components and system libraries (numactl, protobuf) from source where prebuilt wheels are unavailable. The s390x build path is notably more complex, requiring source compilation of numactl, TorchVision, and hf-xet.

The FIPS compliance posture is nuanced: the application layer has explicit FIPS awareness (configurable hash algorithms with sha256/sha512 options, md5 fallback to sha256 via `safe_hash()`), but the default configuration uses non-FIPS algorithms (blake3 for multimodal hashing). The Dockerfile does not apply FIPS build flags (since this is a Python service, not a Go binary), but does use system OpenSSL for gRPC (`GRPC_PYTHON_BUILD_SYSTEM_OPENSSL=1`). A key FIPS risk is that `opencv-python-headless` may bundle its own non-FIPS OpenSSL, which could fail the kernel FIPS self-test. Production FIPS deployments require explicit configuration overrides.

The component does not use AIPCC base images -- it builds from generic UBI 9 Minimal. This means it does not benefit from the RHEL AI Python Package Index or the pre-configured pip/uv environment that AIPCC base images provide. Migration to the AIPCC CPU base image (`quay.io/aipcc/base-images/cpu`) would align it with Red Hat's secure build requirements and simplify dependency management for the ppc64le and s390x architectures that currently use custom build scripts with external package indices.
