## Purpose

**Short**: Kubernetes operator that manages the lifecycle of Data Science Pipelines (DSP) infrastructure — deploying and reconciling the API server, database, object storage, ML metadata service, workflow controller, and associated components per DataSciencePipelinesApplication (DSPA) custom resource.

**Detailed**: The Data Science Pipelines Operator (DSPO) is a controller-runtime based Kubernetes operator that watches `DataSciencePipelinesApplication` (DSPA) custom resources and reconciles the full stack of Kubeflow Pipelines V2 components within each namespace. When a user creates a DSPA CR, DSPO deploys up to seven sub-components: a KFP API Server (REST/gRPC), a Persistence Agent, a Scheduled Workflow controller, an Argo Workflow Controller, an ML Metadata (MLMD) gRPC server with Envoy proxy, and optionally MariaDB and MinIO for metadata storage and artifact storage respectively. Each component is deployed as a separate Deployment with its own ServiceAccount, RBAC, and network policies.

DSPO supports both internal (MariaDB, MinIO) and external (user-provided SQL database, S3-compatible storage) backends. It manages pod-to-pod TLS using OpenShift service CA certificates, deploys kube-rbac-proxy sidecars for API authentication, creates OpenShift Routes for external access, and integrates with the platform's trusted CA bundle. The operator also manages a PipelineVersion admission webhook (validating and mutating) when the Kubernetes pipeline store mode is enabled, and supports managed pipelines that are automatically imported from OCI container images. DSPO integrates with the MLflow operator to configure the MLflow tracking plugin on the API server.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar on API Server and MLMD Envoy; ds-pipeline-user-access-{name} Role grants namespace-scoped access to DSPA API subresource | kube-rbac-proxy + Kubernetes RBAC | Users with namespace access can access all pipelines in that namespace; no per-user pipeline isolation within a namespace |
| Data storage | Per-DSPA MariaDB instance (separate PVC) or external DB; per-DSPA MinIO instance (separate PVC) or external S3 with configurable basePath | Kubernetes (separate Deployments/PVCs) | External DB/S3 shared across DSPAs requires user-managed credential separation |
| Network traffic | NetworkPolicy per component: ds-pipelines-{name} restricts API server ingress; mariadb-{name} restricts DB access to API server and MLMD only; ds-pipeline-metadata-grpc-{name} restricts MLMD to v2_component and data-science-pipelines pods | Kubernetes NetworkPolicy | No egress NetworkPolicies — components can reach any cluster-internal endpoint |
| Compute & resources | Optional resource limits/requests per component via DSPA spec (Resources field on each sub-component) | Kubernetes (resource requests/limits) | No ResourceQuota or LimitRange enforcement by the operator; relies on namespace-level quotas set by administrators |
| Configuration & secrets | Per-DSPA Secrets for DB and storage credentials; per-DSPA ConfigMaps for server config, CA bundles | Kubernetes (namespace-scoped resources) | system:auth-delegator ClusterRoleBinding is cluster-scoped — one per DSPA instance |

## Architectural Analysis

The Data Science Pipelines Operator follows a single-CRD, multi-component deployment pattern. Each `DataSciencePipelinesApplication` CR triggers the deployment of up to seven Kubernetes Deployments (API server, persistence agent, scheduled workflow, workflow controller, MLMD gRPC, MLMD Envoy, and optionally a webhook) plus supporting database and storage infrastructure. The operator uses `manifestival` for template-based resource deployment, reading Go template files (`.yaml.tmpl`) from `config/internal/` and rendering them with parameters extracted from the DSPA spec and operator configuration. This approach decouples resource definitions from controller logic, making it straightforward to audit what gets deployed per DSPA instance.

The TLS architecture is particularly well-designed. DSPO integrates with the OpenShift cluster's TLS security profile via `openshift/controller-runtime-common/pkg/tls`, ensuring the webhook and metrics servers use cluster-mandated cipher suites and minimum TLS versions. A `SecurityProfileWatcher` triggers a graceful pod restart when the cluster TLS profile changes. For pod-to-pod encryption, DSPO leverages OpenShift's service-ca controller through `service.beta.openshift.io/serving-cert-secret-name` annotations, which auto-generates and rotates TLS certificates per Service. The `PodToPodTLS` flag (defaulting to true) controls whether component Deployments mount these certificates and configure TLS listeners. CA bundle management aggregates three sources — the platform's `odh-trusted-ca-bundle` ConfigMap, user-provided CA bundles from the DSPA spec, and service-ca certificates — into a single `dsp-trusted-ca-{name}` ConfigMap consumed by all components.

The FIPS compliance posture uses Go 1.26's native `GOFIPS140=v1.0.0` build flag with `godebug fips140=on` in `go.mod`, which is the modern replacement for the older `GOEXPERIMENT=strictfipsruntime` pattern. Notably, `CGO_ENABLED=0` produces a static binary — this works with `GOFIPS140` because Go 1.22+ embeds the FIPS 140 module directly in the Go runtime without requiring dynamic linking to OpenSSL. The `-tags no_openssl` flag explicitly opts out of OpenSSL linkage. One crypto concern: the database controller sets `InsecureSkipVerify: true` when the user configures `tls=skip-verify` in CustomExtraParams, which bypasses certificate validation. This is a user-controlled opt-in, but it could weaken FIPS posture if used in production.

The operator's memory optimization is noteworthy. It strips `managedFields` from all cached objects via `DefaultTransform`, strips `Data` payloads from cached ConfigMaps and Secrets (reading them via direct API calls when needed), and scopes informer watches using label selectors (`dsp-version` label on operator-managed resources) and field selectors (webhook configurations by name). The `GOMEMLIMIT=3600MiB` setting prevents OOM kills while allowing the Go runtime to use available memory efficiently.

The managed pipelines subsystem introduces an OCI registry dependency: the operator pulls `managed-pipelines.json` manifests from container images at reconcile time to validate pipeline names declared in the DSPA spec. A per-digest cache with 10-minute TTL reduces registry traffic, and an optional registry allowlist (`MANAGED_PIPELINES_ALLOWED_REGISTRIES`) restricts which registries the operator will contact. This is a supply chain consideration — the operator executes OCI manifest pulls during reconciliation, not just at build time.
