## Purpose

**Short**: An HTTP reverse proxy that enforces Kubernetes RBAC authorization via SubjectAccessReview before forwarding requests to an upstream service.

**Detailed**: kube-rbac-proxy is a small HTTP/HTTPS reverse proxy designed to sit in front of a single upstream service and perform authentication and authorization checks against the Kubernetes API before proxying requests. It authenticates incoming requests using either Kubernetes TokenReview (delegating authentication) or OIDC JWT validation, then authorizes them by issuing SubjectAccessReview requests to the Kubernetes API server.

In the RHOAI 3.x platform, kube-rbac-proxy is deployed as a sidecar container alongside component pods (e.g., TrustyAI, Model Registry, KServe). It replaces the legacy `oauth-proxy` pattern from RHOAI 2.x. The platform operator (`rhods-operator`) injects kube-rbac-proxy containers into component deployments, typically listening on port 8443/TCP with TLS, and proxying authenticated/authorized requests to the application container on its internal port. This provides a uniform authentication and authorization layer across all RHOAI components without requiring each component to implement its own auth logic.

The proxy supports two authorization configuration formats: Format1 (top-level `resourceAttributes` with optional `rewrites` for templated SubjectAccessReview fields) and Format2 (path-scoped `endpoints` with per-method resource rules). Format2 enables fine-grained, per-endpoint authorization policies — for example, allowing different RBAC resources to be checked for different API paths within the same upstream service. A hardcoded authorizer also grants `system:serviceaccount:openshift-monitoring:prometheus-k8s` read access to `/metrics` without a SubjectAccessReview, ensuring Prometheus can always scrape metrics.

## Architectural Analysis

kube-rbac-proxy follows a classic sidecar proxy pattern, acting as an authentication and authorization gateway that sits in the request path between external clients and the application container. Its design is intentionally minimal — it is a single statically-compiled Go binary with no CRDs, no controllers, and no persistent state. This simplicity is its architectural strength: every RHOAI component gets the same auth enforcement without implementing auth themselves.

The proxy's authorization model supports two complementary formats. Format1 (top-level `resourceAttributes` with optional `rewrites`) provides a simple way to map all proxied requests to a single SubjectAccessReview check, optionally parameterized by HTTP headers or query parameters. Format2 (`endpoints` with per-path/method `mappings`) enables fine-grained, per-endpoint authorization — for instance, checking different Kubernetes resources for GET vs POST on the same API path. This dual-format system is particularly important for components like TrustyAI that expose multiple API endpoints requiring different RBAC checks. The `TemplateData` struct in Format2 supports `{{.FromHeader}}`, `{{.FromQueryString}}`, and `{{.FromMethod}}` template variables, enabling dynamic namespace and resource scoping from request metadata.

The hardcoded metrics authorizer (`pkg/hardcodedauthorizer/metrics.go`) is a notable design choice — it unconditionally allows the `system:serviceaccount:openshift-monitoring:prometheus-k8s` service account to GET `/metrics` without any SubjectAccessReview. This ensures Prometheus can always scrape metrics even if RBAC is misconfigured, which is critical for platform observability. The comment in the code notes this should eventually be replaced by static authorizer configuration.

The TLS implementation is thorough: the server listener enforces configurable `MinVersion` (default TLS 1.2) and cipher suites, the upstream transport also enforces `MinVersion: tls.VersionTLS12`, and HTTP/2 ALPN is configured on both sides. Certificate hot-reloading (`pkg/tls/reloader.go`) polls cert files on a configurable interval (default 1 minute) with a goroutine-safe read-lock pattern. Client CA certificates for both X.509 client auth and OIDC issuer verification use `DynamicFileCAContent` from the Kubernetes API server library, which watches the file for changes. The token sanitization filter (`cmd/kube-rbac-proxy/app/sanitazion.go`) intercepts all klog output and masks bearer tokens in TokenReview JSON payloads, preventing credential leakage to logs.

A recent downstream change (`b2190792`) added support for accepting both TLS version name formats (`TLS1.2`/`TLS1.3` and `VersionTLS12`/`VersionTLS13`) for the `--tls-min-version` flag via a `normalizeTLSVersion()` function, improving compatibility across different deployment configurations. Another notable change (`736eec87`) removed the `--http2-disable` flag to always enable HTTP/2 with ALPN negotiation, aligning with Kubernetes best practices and ensuring gRPC proxying works correctly. The upstream transport was also hardened (`209423f3`, `a05924ef`) to unconditionally set `MinVersion: tls.VersionTLS12` and configure `NextProtos` for ALPN, closing a gap where the default Go transport could negotiate TLS 1.0/1.1.
