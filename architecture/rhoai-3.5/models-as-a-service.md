## Purpose

**Short**: Models as a Service (MaaS) provides a managed platform for exposing LLM inference endpoints with API key management, subscription-based rate limiting, and multi-tenant isolation on OpenShift AI.

**Detailed**: MaaS consists of two primary components -- a Kubernetes controller (`maas-controller`) and an HTTP API service (`maas-api`) -- that together enable platform administrators to offer LLM inference as a self-service capability. The controller manages the lifecycle of tenants, model references, authorization policies, and subscriptions by reconciling custom resources into Gateway API HTTPRoutes, Kuadrant AuthPolicies and TokenRateLimitPolicies, and Istio networking resources. The API service provides user-facing endpoints for API key CRUD operations, model discovery, subscription listing, and tenant information, backed by a PostgreSQL database.

A third component, `payload-processing`, runs as a gRPC external processor integrated into the Envoy gateway via EnvoyFilter. It handles pre-authentication model name extraction from request bodies and post-authentication API translation, token counting, and model routing. The platform leverages Kuadrant/Authorino for authentication and authorization, Gateway API for ingress routing, and Istio for service mesh networking including TLS origination to external model providers.

## Architecture Components

| Component | Type | Purpose |
|-----------|------|---------|
| maas-controller | Go Operator (controller-runtime) | Reconciles MaaS CRDs (AITenant, MaasTenantConfig, MaaSModelRef, MaaSAuthPolicy, MaaSSubscription, ExternalModel, Config) into Kubernetes resources including HTTPRoutes, AuthPolicies, TokenRateLimitPolicies, NetworkPolicies, and Deployments |
| maas-api | Go HTTP Service (Gin) | API key management, model discovery, subscription selection, and tenant info; authenticates via Authorino-injected headers |
| payload-processing | gRPC External Processor | Envoy ext_proc filter for request/response payload processing (model extraction, API translation, token counting, credential injection) |

### maas-api

**Dockerfile**: `maas-api/Dockerfile.konflux`
**Intent**: User-facing REST API for MaaS. Deployed per-tenant by the TenantReconciler as a Deployment in the infrastructure namespace. ## Architectural Analysis

The MaaS platform implements a sophisticated multi-tenant model-serving gateway that sits between users and LLM backends (both internal KServe models and external providers like OpenAI). The architecture is notable for its deep integration with the Kuadrant policy engine, which provides a clean separation between routing (Gateway API HTTPRoutes), authentication (Authorino via AuthPolicy), and rate limiting (Limitador via TokenRateLimitPolicy). Each MaaS CRD maps to one or more Kuadrant resources, creating a layered abstraction where platform users interact with MaaS-specific concepts (subscriptions, auth policies, model refs) while the controller translates these into the underlying policy engine primitives.

The payload-processing component represents an innovative use of Envoy's External Processing (ext_proc) API to solve a chicken-and-egg problem in AI gateway routing: the model name is embedded in the request body (JSON), but auth policy evaluation needs to know the model to check access. The solution splits processing into two stages -- `ipp-pre` runs *before* the Kuadrant WasmPlugin to extract the model name from the request body and set an `X-Gateway-Model-Name` header, then `ipp` runs *after* auth to handle API format translation, token counting, and credential injection for external models. The EnvoyFilter manifests include dual anchor patterns (WasmPlugin for ODH/community Kuadrant, `envoy.filters.http.wasm` for RHCL 1.4) ensuring compatibility across policy engine versions.

The API key system uses a well-designed cryptographic model: keys follow an `sk-oai-{key_id}_{secret}` format where the `key_id` serves as a per-key salt, and only `SHA-256(key_id + "\x00" + secret)` is stored in PostgreSQL. The null delimiter prevents length-ambiguity attacks, and validation uses `subtle.ConstantTimeCompare` to prevent timing side-channels. The debounced `last_used_at` updates (atomic CAS with configurable interval) prevent row-lock storms under high concurrency -- a practical optimization for shared API keys in load-testing scenarios.

Multi-tenancy is implemented through AITenant CRs, each of which provisions a dedicated namespace, maas-api Deployment, and set of network policies. The TenantReconciler uses a kustomize-based pipeline: it renders a base overlay with tenant-specific parameters (namespace, gateway reference, TLS configuration), then applies a post-render step that injects tenant-suffixed resource names, per-tenant DestinationRules, and default-deny TokenRateLimitPolicies. Server-Side Apply (SSA) with `Config` as the field manager ensures idempotent reconciliation. The shared PostgreSQL database provides row-level tenant isolation via a mandatory `tenant` column filter, though schema-per-tenant isolation is not implemented.

The security model features defense-in-depth: NetworkPolicies restrict which namespaces can reach maas-api's internal endpoints, Kuadrant AuthPolicy enforces authentication at the gateway, group name validation at API key creation time prevents CEL injection in AuthPolicy expressions, and the maas-api returns 404 (not 403) for unauthorized key access to prevent enumeration. The webhook validators ensure AITenant gateway uniqueness (preventing two tenants from claiming the same gateway) and namespace enablement (requiring MaasTenantConfig before allowing subscription/policy creation).
