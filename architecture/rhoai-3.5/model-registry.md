## Purpose

**Short**: Central metadata repository for ML models, versions, artifacts, and serving configurations in the RHOAI/ODH platform.

**Detailed**: Model Registry provides a REST API server for recording and retrieving metadata associated with ML developer and data scientist workflows. It stores information about registered models, model versions, model artifacts, serving environments, inference services, experiments, and experiment runs. The service replaces the legacy C++ gRPC service provided by the MLMD (ML Metadata) project with a Go-native implementation that exposes a higher-level OpenAPI-based REST API.

The component ships as four deployable images: (1) the primary REST API proxy server backed by MySQL or PostgreSQL, (2) a Kubernetes controller that watches KServe InferenceService CRs and synchronizes their state into the registry, (3) a custom storage initializer (CSI) that enables KServe to pull model artifacts using `model-registry://` URIs, and (4) an async-upload Python job that copies models between storage backends (S3, OCI) and registers them. The controller and CSI components integrate Model Registry into the KServe serving infrastructure, enabling bidirectional metadata flow between model serving and model governance.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Istio AuthorizationPolicy restricts access to istio-ingressgateway SA and kubeflow namespace | Istio | No application-level auth; if Istio is misconfigured, API is open. The AuthorizationPolicy allows any pod in the `kubeflow` namespace with an authorization header to access any Model Registry instance. |
| Data storage | Per-instance database (each Model Registry instance has its own DB) | Deployment architecture | Complete isolation -- each instance has its own database |
| Network traffic | Istio mTLS (ISTIO_MUTUAL DestinationRule) + AuthorizationPolicy | Istio | Requires Istio sidecar injection; without it, traffic is plaintext HTTP |
| Compute & resources | No resource quotas defined in base manifests | None | Resource limits not set in base deployment; must be added by platform operator |
| Configuration & secrets | Per-instance ConfigMap and Secret (database credentials) | Kubernetes | Secrets are per-namespace; no cross-namespace Secret sharing |
| API scoping | No namespace-scoped API filtering within a single registry instance; all data visible to any authorized client | Application | Within a single instance, no row-level tenant filtering; isolation relies entirely on separate instances per namespace |

## Architectural Analysis

The Model Registry follows a multi-module monorepo pattern with four distinct deployable components that share common Go packages. The primary REST API server (`model-registry proxy`) is a stateless Go service built around OpenAPI code generation: the `api/openapi/model-registry.yaml` spec drives both the server stubs in `internal/server/openapi/` and the client library in `pkg/openapi/`. This code-generation approach ensures API consistency but means the server-side route handlers are generated code -- the actual business logic lives in `internal/core/` (service layer) and `internal/db/` (repository layer using GORM). The EmbedMD datastore connector in `internal/datastore/embedmd/` replaces the legacy MLMD gRPC service with a direct SQL backend, eliminating the need for a separate metadata server process.

The controller component demonstrates thoughtful integration with KServe: rather than requiring users to manually register InferenceServices in the registry, it watches KServe CRs and automatically creates/updates corresponding metadata entries. The controller uses labels (`modelregistry.kubeflow.org/*`) to associate InferenceServices with Model Registry instances and manages finalizers to clean up registry state when ISVCs are deleted. Notably, the controller discovers Model Registry endpoints dynamically by listing Services with `component: model-registry` labels, allowing it to support multiple per-namespace registry instances. One architectural concern is the `SKIP_TLS_VERIFY` option, which sets `InsecureSkipVerify: true` -- while defaulted to false, its presence in the API surface creates a risk if inadvertently enabled in production.

The async-upload job is the newest component, implementing a model lifecycle pattern where models flow from source storage (S3/OCI/HuggingFace) through a signing pipeline (Sigstore/cosign) to destination storage, with metadata automatically registered in the Model Registry. The job supports three intents (`update_artifact`, `create_model`, `create_version`), enabling both updating existing artifacts and creating entirely new model+version+artifact hierarchies from ConfigMap metadata. This is the only component using AIPCC base images (CPU variant), as it needs Python for the model-registry client SDK and sigstore libraries. The job's hermeticity story is strong: `requirements-aipcc.txt` with hash verification for Python deps, `rpms.lock.yaml` for OS packages, and `poetry.lock` for development.

The security architecture relies heavily on Istio service mesh for transport security (mTLS) and access control (AuthorizationPolicy). The application itself has no authentication mechanism -- the REST API is completely open at the application layer, with all authN/authZ delegated to the mesh and platform. The Istio AuthorizationPolicy restricts access to traffic from the istio-ingressgateway (external users authenticated by OAuth) and from the kubeflow namespace with a Kubernetes JWT (control-plane components like the controller). The deployment manifest includes `sidecar.istio.io/inject: "true"` to ensure mesh enrollment. Without Istio, the service would be accessible without authentication, which is an important operational consideration.

The database schema uses an MLMD-compatible structure (types, artifacts, contexts, executions, properties) managed via golang-migrate migrations. Both MySQL and PostgreSQL are supported, with PostgreSQL being the newer addition. The code uses GORM as the ORM layer with generated model structs from `gorm-gen/`. The `internal/platform/db/` package provides a pluggable connector factory pattern that allows registering database drivers at initialization time. TLS support for database connections is comprehensive, with configurable cipher suites and explicit rejection of insecure ciphers.
