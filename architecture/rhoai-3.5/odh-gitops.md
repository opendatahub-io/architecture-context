## Purpose

**Short**: GitOps repository providing Helm charts and Kustomize manifests for deploying Red Hat OpenShift AI (RHOAI) / Open Data Hub (ODH) and its dependency operators on OpenShift and non-OpenShift Kubernetes clusters.

**Detailed**: odh-gitops is a configuration-only repository (no compiled source code) that serves as the standardized deployment vehicle for the RHOAI/ODH platform. It provides two primary Helm charts — `rhai-on-openshift-chart` for OLM-based OpenShift deployments and `rhai-on-xks-chart` for non-OLM Kubernetes services (AWS EKS, Azure AKS, CoreWeave) — alongside Kustomize manifests for granular dependency operator installation.

The repository addresses the "day-1" installation challenge: orchestrating the deployment of 12+ dependency operators (cert-manager, Kueue, RHCL/Kuadrant, Sail/Istio, LWS, JobSet, NFD, NVIDIA GPU, etc.), creating the platform operator (rhods-operator), configuring DataScienceCluster (DSC) and DSCInitialization (DSCI) custom resources, and provisioning Gateway API infrastructure (GatewayClass, Gateway, Certificates) for model inference. It implements a sophisticated dependency resolution system where components declare their dependencies and a tri-state (`auto`/`true`/`false`) mechanism determines which operators to install.

The Helm charts also support deployment profiles (e.g., `default`, `rhaii` for inference-only), multi-cloud provider selection (AWS, Azure, CoreWeave) with cloud-specific KubernetesEngine CRs, TLS certificate provisioning via cert-manager, and Authorino-based authentication integration. Charts are synced to RHOAI-Build-Config via the `helm-sync.yml` workflow for downstream release processing.

## Architectural Analysis

The odh-gitops repository implements a sophisticated multi-layer deployment architecture. At the Kustomize layer, it uses the Kustomize Component pattern (not the more common base/overlay model) — each dependency operator is defined as a `Component` kind with its own Namespace, OperatorGroup, and Subscription resources. This allows fine-grained composition: administrators can include or exclude individual operators by commenting components in the `dependencies/operators/kustomization.yaml` file. The post-install configurations (Kueue CR, Kuadrant CR, LWS CR, etc.) are separated into their own directory, requiring a two-phase installation where operators must be installed and their CRDs registered before configuration CRs can be applied.

The Helm charts implement an advanced dependency resolution engine via Go template helpers in `_helpers.tpl`. The tri-state `enabled` flag (`auto`/`true`/`false`) on each dependency, combined with component-to-dependency mappings (e.g., KServe requires cert-manager, RHCL, and optionally LWS), allows the chart to calculate the minimum set of operators to install. Transitive dependencies are resolved: enabling Kueue auto-enables cert-manager because the `kueue.dependencies.certManager` flag is set to `true`. The profile system (`default`, `rhaii`) provides deployment presets by setting component `managementState` defaults — the `rhaii` profile enables only KServe for inference-only deployments.

The xKS chart introduces cloud provider abstraction through a provider registry pattern (`_crs-definitions.tpl`). Each cloud provider (AWS, Azure, CoreWeave) is registered with its KubernetesEngine CR metadata (kind, resource name, API group). A validation template enforces that exactly one provider is enabled. Post-install hooks (Kubernetes Jobs with the `ose-cli` image) handle the multi-step orchestration: first creating the KubernetesEngine CR to trigger dependency deployment, then the Platform CR to enable module operators, and finally component CRs after their CRDs are established. The gateway creation scripts (`create-gateway.sh`, `create-maas-gateway.sh`) implement a robust wait-loop pattern with configurable timeouts, handling the complex sequence of waiting for Gateway API CRDs, cert-manager CA secrets, Certificate readiness, and GatewayClass availability before creating the inference Gateway.

A notable security consideration is the `rhai-operator-role` ClusterRole, which grants wildcard (`*`) permissions on all RBAC resources (`clusterrolebindings`, `clusterroles`, `rolebindings`, `roles`). This is necessary because the platform operator must create per-component RBAC resources dynamically, but it represents a broad privilege grant. The xKS chart also disables most operator components via `RHAI_DISABLE_*` environment variables, running only the KServe reconciler — this is an important security hardening measure that limits the blast radius on non-OpenShift clusters. The `helm-sync.yml` workflow uses GitHub App tokens for cross-repo push access, with unpinned action versions flagged as medium-severity security annotations in the component-architecture.json.
