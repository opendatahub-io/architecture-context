## Purpose

**Short**: Kubernetes-native operator for managing distributed machine learning training jobs, supporting PyTorch, MPI, DeepSpeed, MLX, and TorchTune frameworks.

**Detailed**: Kubeflow Trainer is a controller-runtime based Kubernetes operator that manages the lifecycle of distributed ML training workloads. It introduces three CRDs — `TrainJob`, `TrainingRuntime`, and `ClusterTrainingRuntime` — that provide a declarative API for specifying training jobs and reusable runtime templates. The operator converts `TrainJob` specifications into `JobSet` objects using a plugin-based runtime framework, supporting PyTorch distributed training (torchrun), TorchTune fine-tuning, MPI-based training, DeepSpeed, and MLX.

The RHOAI distribution extends the upstream Kubeflow Trainer with Red Hat AI-specific features including training progression tracking (real-time metrics polling from training pods), NetworkPolicy enforcement for pod isolation, TLS security profile integration with OpenShift cluster configuration, and pre-configured ClusterTrainingRuntimes for CUDA, ROCm, and CPU accelerator variants. The operator deploys into the `opendatahub` namespace and ships pre-built training images via OpenShift ImageStreams for the Training Hub ecosystem.

## Architectural Analysis

The Kubeflow Trainer v2 architecture represents a significant redesign from the v1 Training Operator. Where v1 had separate controllers for each ML framework (PyTorchJob, MPIJob, etc.), v2 unifies everything behind a single `TrainJob` CRD with a plugin-based runtime framework. The `TrainJob` → `TrainingRuntime` → `JobSet` chain provides clean separation of concerns: users define *what* they want to train via TrainJob, platform administrators define *how* training runs via TrainingRuntime templates, and the runtime plugins translate both into concrete Kubernetes resources via JobSet. This three-tier model closely mirrors the Kubernetes Pod → ReplicaSet → Deployment pattern.

The plugin framework (`pkg/runtime/framework/`) implements a pipeline pattern with well-defined extension points: `EnforceMLPolicyPlugin`, `EnforcePodGroupPolicyPlugin`, `PodNetworkPlugin`, `ComponentBuilderPlugin`, and `TrainJobStatusPlugin`. Each plugin interface handles a specific concern — the Torch plugin configures distributed training environment variables (`PET_NNODES`, `PET_NPROC_PER_NODE`, `PET_MASTER_ADDR`), the MPI plugin generates SSH keys and hostfiles, the CoScheduling/Volcano plugins create PodGroup CRs for gang-scheduling, and the JobSet plugin orchestrates everything into a single JobSet apply configuration. The framework enforces that only one `TrainJobStatusPlugin` exists (preventing status conflicts), and plugins register additional watchers via `ReconcilerBuilders` to react to changes in the resources they create.

The RHAI (Red Hat AI) integration layer adds three capabilities not present in upstream Kubeflow: (1) training progression tracking via HTTP polling of a `/metrics` endpoint on the primary training pod, with structured status written to TrainJob annotations including loss, accuracy, epoch progress, and estimated time remaining; (2) per-TrainJob NetworkPolicy creation that restricts training pod ingress to same-JobSet peers and the controller's metrics scraping; and (3) OpenShift TLS security profile integration that dynamically configures the webhook and metrics server TLS based on the cluster's `config.openshift.io/v1/APIServer` resource, with a hardened Intermediate fallback (TLS 1.2+, ECDHE cipher suites). The progression tracking uses a separate API reader (`mgr.GetAPIReader()`) for pod lookups to avoid adding pods to the controller cache, which would dramatically increase memory usage.

The TorchTune integration (`pkg/runtime/framework/plugins/torch/torchtune.go`) implements fine-tuning workflow support with model-specific validation — it validates against a set of supported pre-trained models (Llama 3.2 1B/3B, Llama 3.3 70B, Qwen 2.5 1.5B) and enforces constraints like multi-node restrictions per model. Recipe/config selection is automated based on numNodes and numProcPerNode settings, with QLoRA fine-tuning support for reduced memory scenarios. The data cache component (`pkg/data_cache/`) is an experimental Rust service built on Apache Arrow Flight, DataFusion, and Apache Iceberg that provides distributed dataset caching with head/worker topology — it is not yet part of the Konflux build pipeline (no Konflux Dockerfile) and uses a plain `Dockerfile` with `debian:bookworm-slim` base.

The operator's finalizer strategy prevents orphaned resources: `TrainingRuntime` and `ClusterTrainingRuntime` objects receive a `trainer.kubeflow.org/resource-in-use` finalizer when any TrainJob references them, preventing deletion until all referencing TrainJobs are removed. The runtime controller uses a 1-second debounce on TrainJob notification events to batch updates efficiently. The RHOAI kustomize overlay (`manifests/rhoai/`) uses 21 ConfigMap-based image replacements to inject SHA-pinned training images for multiple accelerator/framework combinations, supporting CUDA 12.8, CUDA 13.0, ROCm 6.4, and CPU-only variants across PyTorch 2.9 and 2.10 with Python 3.12.
