## Purpose

**Short**: A Kubernetes module operator that manages the lifecycle of the MCP Lifecycle Operator as a component within the ODH/RHOAI platform.

**Detailed**: The MCP Lifecycle Module Operator follows the ODH modular architecture pattern (v2 of the Onboarding Guide for ODH Operator Modules). It does not implement business logic itself; instead, the ODH platform operator creates a `MCPLifecycleOperator` custom resource, and this module operator reconciles it by deploying the MCP Lifecycle Operator operand via Server-Side Apply (SSA). The operand is the actual MCP Lifecycle Operator that manages `MCPServer` resources.

The reconciliation flow is: the platform operator creates a `MCPLifecycleOperator` CR → this module operator renders pre-vendored kustomize manifests → applies them via SSA with label-based ownership → garbage-collects stale resources → monitors operand Deployment readiness. When `managementState` is set to `Removed`, all owned resources are deleted. The operator reads the cluster's TLS configuration from the OpenShift `APIServer` resource and propagates it as environment variables to the operand Deployment.

Platform configuration (operand image reference, target namespace) is provided via environment variables (`RELATED_IMAGE_ODH_MCP_LIFECYCLE_OPERATOR_IMAGE`, `SYSTEM_NAMESPACE`) injected by the platform into the module operator's pod spec, not through the CR spec.

## Architectural Analysis

The MCP Lifecycle Module Operator is a clean implementation of the ODH v2 modular architecture pattern. It serves as a thin lifecycle management layer between the platform operator and the MCP Lifecycle Operator operand. The architectural separation is clear: this module operator handles deployment, configuration propagation, and health monitoring, while the operand handles the actual MCPServer business logic.

The manifest management approach is notable: operand manifests are pre-rendered via `make update-operand-manifests` (which clones the upstream `mcp-lifecycle-operator` repo, runs `make build-installer`, and copies the output into `internal/controller/resources/`). These manifests are then embedded into the Go binary via `//go:embed`. At runtime, the `KustomizeProvider` transforms the embedded manifests using `manifestival` -- injecting the `platform.opendatahub.io/part-of` label, targeting the correct namespace, replacing the operand image, and injecting TLS environment variables. This is a vendor-and-transform pattern, not a live-kustomize pattern.

The TLS configuration propagation is well-designed for OpenShift environments. The operator reads the cluster's `APIServer` resource to determine the active TLS profile, converts OpenSSL cipher suite names to IANA names using `library-go`, and injects `TLS_MIN_VERSION`, `TLS_CIPHER_SUITES`, and `PROPAGATE_TLS_ENV_VARS` environment variables into the operand's Deployment. On non-OpenShift clusters, it falls back to the OpenShift Intermediate profile defaults (TLS 1.2+), ensuring reasonable security even outside OpenShift.

The garbage collection mechanism is label-based rather than owner-reference based. It uses the `platform.opendatahub.io/part-of: mcplifecycleoperator` label to identify managed resources, then deletes any labeled resource that is not in the current desired set. This allows the operator to manage both namespaced and cluster-scoped resources (CRDs, ClusterRoles) without owner-reference limitations across namespaces. The GC runs on every successful reconciliation pass.

The operator deploys a substantial set of resources for the operand: the MCPServer CRD, 7 RBAC resources (ClusterRoles for admin/editor/viewer, leader election Role, manager ClusterRole, plus their bindings), a ServiceAccount, a Deployment, a metrics Service, a ServiceMonitor, and a NetworkPolicy. The NetworkPolicy restricts ingress to the operand metrics port (8443) to only namespaces labeled with `metrics: enabled`, and allows kubelet health probes on port 8081.
