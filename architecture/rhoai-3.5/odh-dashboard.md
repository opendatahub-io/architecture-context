## Purpose

**Short**: Web-based management console for Red Hat OpenShift AI providing a unified UI for ML workflows, model serving, notebooks, pipelines, and AI-assisted features through a modular architecture.

**Detailed**: odh-dashboard is the primary user interface for the OpenShift AI platform. It provides a React-based single-page application (SPA) served by a Node.js (Fastify) backend that proxies Kubernetes API calls and upstream ML services. The dashboard manages workbench notebooks, model serving configurations, model registries, data science pipelines, hardware profiles, and connection types through a rich set of API endpoints and a responsive UI built on PatternFly.

The architecture follows a modular federation pattern where the core dashboard acts as a host application that dynamically loads federated UI modules (remotes) at runtime. Each module consists of a React frontend and a Go Backend-for-Frontend (BFF) service, packaged as independent container images. Modules include gen-ai (AI studio with LlamaStack integration), model-registry (artifact management), maas (model-as-a-service), mlflow (experiment tracking), eval-hub (model evaluation), automl (automated ML pipelines), autorag (RAG optimization), and agent-ops (AI agent lifecycle management).

A companion Go operator (`dashboard-operator`) manages the lifecycle of the dashboard deployment, handling module enablement based on DSC component availability, deployment mode switching (sidecar vs standalone), federation configuration, RBAC, and observability integration with Perses. The operator reconciles a singleton `Dashboard` CR and dynamically provisions per-module Deployments, Services, NetworkPolicies, and RBAC resources.

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user Bearer token forwarded to K8s API; admin check via Auth CR groups; SelfSubjectAccessReview for resource access | kube-rbac-proxy + backend middleware + K8s RBAC | Admin group membership is stored in a custom Auth CR, not standard K8s RBAC |

| Configuration & secrets | Per-namespace Secrets for workbench credentials; cluster-wide OdhDashboardConfig shared | Kubernetes + dashboard backend | Dashboard config is global; no per-tenant config overrides |
| API scoping | K8s API calls use user's token (namespace-scoped); backend validates namespace ownership | K8s RBAC + backend route-security.ts | Module BFFs use internal SA with impersonation; impersonation scope covers users, groups, serviceaccounts |

## Architectural Analysis

The odh-dashboard repository represents a sophisticated multi-component architecture that has evolved from a monolithic Node.js+React application into a modular federation platform. The core architectural innovation is the use of Webpack Module Federation to decompose the dashboard into independently deployable feature modules, each with its own React frontend and Go BFF service. This allows feature teams to develop, build, and ship UI modules independently while sharing core dependencies (React, PatternFly, plugin SDK) through singleton sharing.

The deployment model supports two modes managed by the dashboard-operator: **sidecar mode** (default), where all BFF modules run as containers within a single pod alongside the main dashboard and kube-rbac-proxy, and **standalone mode**, where each module gets its own Deployment, Service, NetworkPolicy, and RBAC resources. The sidecar mode simplifies networking (all modules accessible via localhost) but creates a monolithic pod with 10+ containers. The standalone mode provides better isolation and independent scaling but requires more infrastructure. The operator's reconcile logic handles the complete lifecycle of both modes, including federation ConfigMap generation, module readiness tracking, and degraded-state management.

Authentication follows a multi-hop proxy chain: the browser authenticates via OpenShift OAuth, the token is forwarded through the Gateway API HTTPRoute to kube-rbac-proxy (port 8443), which performs RBAC checks and forwards to the backend (port 8080) with `x-forwarded-access-token` and `x-auth-request-user` headers. The backend then delegates to BFF modules, which can operate in two auth modes: `user_token` (passing the user's token directly) or `internal` (using the modules ServiceAccount with impersonation). This impersonation pattern allows BFF modules to make K8s API calls on behalf of users without direct token forwarding, but it requires broad impersonation RBAC (users, groups, serviceaccounts).

The inter-BFF communication pattern is notable: the gen-ai BFF calls the MaaS and MLflow BFFs directly via HTTP, configured through environment variables (`BFF_MAAS_SERVICE_NAME`, `BFF_MLFLOW_SERVICE_NAME`). This creates a service mesh within the BFF layer where modules depend on each other's APIs. The eval-hub BFF similarly calls a model catalog BFF. These inter-service dependencies are managed through the operator's module dependency graph, which determines enablement based on DSC component availability.

The kustomize manifest structure uses a layered composition pattern: `core-bases/base` provides the foundational deployment, `modular-architecture` adds federation containers via JSON6902 patches, and the distribution variants (RHOAI/ODH) apply naming, labeling, and app-specific customizations. The parameterization system injects image references and configuration through ConfigMapGenerator + vars, enabling image replacement without manifest editing. The NetworkPolicy configuration is carefully scoped, allowing ingress on all module ports from the OpenShift ingress controller and same-namespace pods, with egress restricted to K8s API (6443), HTTPS (443), and HTTP (80).
