## Purpose

**Short**: Kubernetes operator that manages TrustyAI Service deployments, LM evaluation jobs, guardrails orchestrators, NeMo guardrails servers, and a centralized evaluation hub (EvalHub) on OpenShift AI.

**Detailed**: The TrustyAI Service Operator is a multi-controller operator built with controller-runtime that manages five distinct service domains within the Red Hat OpenShift AI (RHOAI) platform. Each domain is enabled via CLI flags and has its own controller, CRDs, and RBAC.

The first domain, **TrustyAI Service (TAS)**, deploys model explainability and fairness monitoring services alongside KServe/ModelMesh inference endpoints. It patches InferenceServices to add TrustyAI as an inference logger, supports PVC and database storage backends, and integrates with Istio for traffic management. The second domain, **LMEvalJob (LMES)**, provides a job-based architecture for running LM evaluations using EleutherAI's lm-evaluation-harness, with Kueue integration for queue-based scheduling. The third domain, **EvalHub**, deploys a centralized evaluation hub with multi-tenant support, MCP (Model Context Protocol) server integration, and comprehensive provider/collection management. The fourth domain, **GuardrailsOrchestrator (GORCH)**, manages FMS guardrails deployments with auto-configuration from KServe InferenceServices and optional built-in detectors. The fifth domain, **NemoGuardrails**, manages NVIDIA NeMo Guardrails server deployments with MCP gateway integration and Istio EnvoyFilter support.

All controllers share a common pattern of kube-rbac-proxy sidecars for authentication, OpenShift Route creation for external access, and CA bundle management for TLS. The operator resolves container images from a central ConfigMap populated by the platform operator via `RELATED_IMAGE_*` environment variables.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy sidecar with SubjectAccessReview on per-instance RBAC resources (e.g., evalhubs/proxy) | Kubernetes RBAC + kube-rbac-proxy | Relies on correct RBAC propagation to tenant namespaces |
| Data storage | TAS: per-namespace PVC or per-namespace database credentials Secret; EvalHub: per-instance database (SQLite in-memory or PostgreSQL via Secret) | Kubernetes namespace isolation | SQLite mode shares memory within pod; PostgreSQL isolation depends on separate DB credentials |
| Network traffic | No per-tenant NetworkPolicies created by operator; relies on platform-level network isolation | Platform (if configured) | No operator-created NetworkPolicies; cross-namespace traffic not restricted by this operator |
| Compute & resources | LMEvalJob pods run in tenant namespaces; Kueue provides queue-based scheduling and resource quotas | Kueue + Kubernetes scheduler | No operator-created ResourceQuotas; relies on Kueue or external quota mechanisms |
| Configuration & secrets | Per-namespace Secrets and ConfigMaps; EvalHub propagates service CA and discovery ConfigMaps to tenant namespaces | Kubernetes namespace isolation | Shared operator ConfigMap (trustyai-service-operator-config) is cluster-wide |
| API scoping | All controllers use namespace-scoped watches; EvalHub multi-tenant mode discovers namespaces by label and provisions resources per-namespace | Kubernetes namespace + application label selector | EvalHub controller watches all namespaces for the tenant label (cluster-wide namespace list permission required) |

## Architectural Analysis

The TrustyAI Service Operator follows a modular multi-controller architecture where each domain (TAS, LMES, EvalHub, GORCH, NemoGuardrails, Module) is a self-contained controller registered via a service registry pattern (`controllers/controllers.go`). The operator binary accepts `--enable-services` flags that determine which controllers are instantiated, allowing the same binary to serve both focused deployments (e.g., LMES-only) and full-stack deployments (all services). This design is unusual for Kubernetes operators and enables the RHOAI/ODH platform to compose different deployment profiles via kustomize overlays.

The security model is consistently implemented across all controllers: every deployed service gets a kube-rbac-proxy sidecar for HTTPS termination and SubjectAccessReview-based authentication. The proxy configs enforce TLS 1.2 minimum with FIPS 140-2 approved cipher suites, and the operator reads the cluster's TLS security profile from the OpenShift APIServer CR to align with platform-wide crypto policy. This approach means no deployed service exposes plaintext HTTP externally -- all external traffic traverses kube-rbac-proxy. The operator itself uses GOEXPERIMENT=strictfipsruntime for FIPS-compliant cryptography in both the operator and driver binaries.

The EvalHub controller introduces the most sophisticated multi-tenancy model in the operator. It supports two modes: "multi" (default) deploys EvalHub in a control-plane namespace and discovers tenant namespaces via the `evalhub.trustyai.opendatahub.io/tenant` label, provisioning per-tenant ServiceAccounts, RBAC, service CA ConfigMaps, and discovery ConfigMaps; "single" mode runs everything in one namespace with convenience Roles. The tenant namespace provisioning is particularly notable -- it creates a well-known `evalhub-discovery` ConfigMap in each tenant namespace containing the EvalHub service URL, enabling job pods to resolve their control plane without cross-namespace API calls. The EvalHub also has two auxiliary controllers: one watches batch/v1 Jobs for failure detection (pod scheduling failures, init container failures) and another watches Kueue Workloads for admission failures, both reporting events back to the EvalHub API via HTTPS with service CA trust.

The GORCH controller's auto-configuration system is architecturally distinctive: it watches KServe InferenceServices and ServingRuntimes, hashes their combined state, and regenerates orchestrator/gateway ConfigMaps only when the hash changes. This creates a reactive configuration pipeline where adding a new InferenceService with the `trustyai/guardrails=true` label automatically reconfigures the guardrails orchestrator without manual intervention. The NemoGuardrails controller similarly auto-discovers MCPGatewayExtension resources and manages Istio EnvoyFilters for SSE response transformation, bridging the NeMo Guardrails server with the Kuadrant MCP Gateway infrastructure.

Image resolution follows a three-tier precedence: `RELATED_IMAGE_*` environment variables (injected by the platform operator for disconnected environments) take priority over ConfigMap entries, which fall back to hardcoded defaults. This pattern ensures the operator works in air-gapped environments where images must be resolved from a local registry. The operator disables informer caching for high-volume core resources (ConfigMaps, Secrets, Pods, Services) to prevent OOM conditions in clusters with many namespaces, accepting the latency tradeoff of direct API reads.
