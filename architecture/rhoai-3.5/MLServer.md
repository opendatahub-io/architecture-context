## Purpose

**Short**: MLServer is a multi-framework machine learning inference server implementing the KServe V2 Inference Protocol (dataplane API) over REST and gRPC.

**Detailed**: MLServer provides a standards-compliant inference serving runtime for machine learning models. It implements the KServe V2 Dataplane protocol (formerly the Open Inference Protocol), exposing both REST (HTTP/1.1 via FastAPI/uvicorn) and gRPC interfaces for model inference, health checks, model metadata, and model repository management.

The server supports a plugin-based runtime architecture where each ML framework (scikit-learn, XGBoost, LightGBM, ONNX Runtime, HuggingFace Transformers, MLflow, CatBoost, Alibi Explain, Alibi Detect) is implemented as a separate Python package that extends the base `MLModel` class. In RHOAI, two container image variants are shipped: a CPU variant bundling sklearn, XGBoost, LightGBM, and ONNX runtimes, and a CUDA variant bundling only the ONNX runtime with GPU execution provider support.

MLServer also provides adaptive batching, parallel inference workers (multi-process), response caching, Prometheus metrics, OpenTelemetry tracing, Kafka streaming integration, and a CLI for model serving, Docker image building, and batch inference. A trusted runtimes allowlist mechanism enforces production security by restricting which model implementation classes can be loaded.

## Architectural Analysis

MLServer follows a clean layered architecture separating protocol handling from inference logic. The `DataPlane` class (`mlserver/handlers/dataplane.py`) serves as the central handler shared by both REST and gRPC servers, implementing the KServe V2 protocol semantics. Protocol-specific code in `mlserver/rest/` (FastAPI) and `mlserver/grpc/` (grpc.aio) handles serialization and transport, delegating all business logic to the shared DataPlane. This design ensures protocol parity: any feature available via REST is automatically available via gRPC.

The runtime plugin architecture is well-designed for extensibility. Each runtime (sklearn, ONNX, XGBoost, etc.) is a separate Python package with its own `pyproject.toml` and `poetry.lock`, extending the `MLModel` base class. The trusted runtimes allowlist mechanism (`mlserver/settings.py:140-251`) provides a production security boundary: the `/etc/mlserver/trusted-runtimes.json` file, baked into the container image at build time, restricts which Python import paths can be loaded as model implementations. This prevents arbitrary code execution via model-settings.json in production deployments. In development mode (no allowlist file), any runtime can be loaded, including custom ones from model folders via dynamic sys.path injection.

The ONNX runtime plugin deserves special attention for RHOAI. The CPU variant installs `onnxruntime` with CPU execution providers, while the CUDA variant installs `onnxruntime-gpu` with `CUDAExecutionProvider` as the primary execution provider and `CPUExecutionProvider` as fallback. The ONNX runtime has the most complex settings surface (`runtimes/onnx/mlserver_onnx/settings.py`) with provider selection, session options, and run options -- critical for GPU performance tuning.

A notable security consideration is that MLServer runs all three servers (REST, gRPC, metrics) on plaintext/insecure ports. The gRPC server explicitly uses `add_insecure_port()` (`mlserver/grpc/server.py:88`), and the REST server has no TLS configuration. This is by design: TLS termination and authentication are handled externally by KServe's ingress infrastructure. The production-mode CORS validation (`mlserver/settings.py:537-562`) prevents wildcard CORS origins when the trusted runtimes allowlist is present, and the environment-path/tarball injection is blocked in production mode (`mlserver/settings.py:620-648`), preventing model-folder sys.path attacks.

The Prometheus metrics implementation is split across REST and gRPC: REST uses `starlette-exporter` PrometheusMiddleware (`mlserver/rest/app.py:226-236`), while gRPC uses a custom async wrapper around `py-grpc-prometheus` (`mlserver/grpc/interceptors.py:46-253`). Both export to a dedicated metrics server on port 8082 with a `/metrics` endpoint. Application-level inference metrics (success/failure counters, duration summary) are registered in the DataPlane handler (`mlserver/handlers/dataplane.py:44-58`).
