## Purpose

**Short**: An OpenAI-compatible HTTP gateway that routes chat completion requests through the FMS Guardrails Orchestrator with configurable per-route detector-based content filtering.

**Detailed**: The vLLM Orchestrator Gateway is a Rust-based HTTP service that sits between clients and the FMS Guardrails Orchestrator. It provides multiple OpenAI-compatible `/v1/chat/completions` endpoints — one per configured route — each with its own detector pipeline configuration. This enables operators to expose guardrailed LLM endpoints as drop-in replacements for ungurdrailed ones.

The gateway reads a YAML configuration file that defines: (1) the backend orchestrator endpoint, (2) named detector services with input/output classification and parameters, and (3) routes that bind a subset of detectors to a named endpoint path. When a client sends a chat completion request to a route endpoint (e.g., `/{route_name}/v1/chat/completions`), the gateway injects the route's detector configuration into the payload and forwards it to the orchestrator's `/api/v2/chat/completions-detection` endpoint. If the orchestrator's response contains detections and the route has a fallback message configured, the gateway replaces the generated content with the fallback message.

The gateway supports both synchronous (non-streaming) and streaming (SSE) chat completion modes, and can communicate with the orchestrator over mTLS when TLS certificates are mounted at well-known paths. It is part of the TrustyAI guardrails stack within RHOAI and is designed to be deployed as a sidecar or standalone service alongside vLLM inference servers.

## Architectural Analysis

The vllm-orchestrator-gateway follows a clean reverse-proxy pattern with request enrichment. Rather than implementing guardrails logic itself, it acts as a routing and configuration injection layer in front of the FMS Guardrails Orchestrator. Each route defined in the YAML config maps to a distinct endpoint that automatically injects a specific set of detectors into the request payload. This design allows platform administrators to expose multiple guardrail-policy variants as separate OpenAI-compatible endpoints without requiring clients to understand detector configuration.

The TLS implementation (`build_orchestrator_client` in `main.rs:351-406`) demonstrates a thoughtful approach to in-cluster mTLS. The gateway probes for certificate files at well-known OpenShift paths (`/etc/tls/private/` for client certs, `/etc/tls/ca/` for CA bundle) and gracefully degrades to plaintext HTTP when they are absent. The PKCS#12 conversion through the `openssl` crate is necessary because `reqwest`'s `native-tls` Identity API requires PKCS#12 format, while Kubernetes typically provides PEM files. One concern is the `danger_accept_invalid_hostnames(true)` call when the orchestrator hostname is `localhost` — while intended for local development, this code path exists in the production binary and could be triggered by a misconfigured `orchestrator.host` value.

The streaming implementation (`handle_streaming_generation` in `main.rs:259-349`) handles SSE protocol translation: it reads chunked HTTP responses from the orchestrator, parses each chunk's `data:` lines, applies fallback message logic per chunk if detections are found, and re-emits as SSE events. This is more complex than the non-streaming path because detection checking must happen per-chunk rather than on a complete response. The fallback message replaces the delta content and sets `finish_reason: "stop"` on the first detection, effectively terminating the stream with the safety message.

The configuration validation (`validate_registered_detectors` in `config.rs:64-108`) catches two classes of misconfiguration at startup: (1) routes referencing detectors not defined in the detector list, and (2) routes with multiple input or output detectors pointing at the same server name. Both result in a panic, preventing the gateway from starting with an invalid config. This fail-fast approach is appropriate for a service that would silently misbehave with bad detector mappings.

The header forwarding logic (`orchestrator_post_request` in `main.rs:420-433`) selectively forwards `Authorization` and `X-Forwarded-*` headers from the client to the orchestrator. This is important for two reasons: it preserves the client's identity for downstream authorization, and it carries proxy metadata for observability. Other headers are intentionally dropped, providing a minimal attack surface for header injection.
