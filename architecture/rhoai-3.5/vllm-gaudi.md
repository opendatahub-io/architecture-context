## Purpose

**Short**: vLLM hardware plugin that enables high-performance large language model inference on Intel Gaudi (Habana) accelerators, packaged as a container image for RHOAI serving runtimes.

**Detailed**: vllm-gaudi is an out-of-tree (OOT) platform plugin for the vLLM inference engine that provides Intel Gaudi HPU (Habana Processing Unit) support. It extends vLLM's plugin architecture to register HPU-optimized implementations of attention backends, custom operators, model runners, workers, and distributed communication primitives. The plugin enables vLLM's OpenAI-compatible API server to run on Gaudi2 and Gaudi3 accelerators with hardware-specific optimizations including unified attention, dynamic shape bucketing for graph compilation, FP8 quantization (via Intel Neural Compressor), and heterogeneous multi-device KV cache transfer via NIXL.

The downstream repository (red-hat-data-services/vllm-gaudi) takes upstream releases from vllm-project/vllm-gaudi and packages them into a Konflux-built RHEL UBI9 container image (`odh-vllm-gaudi-rhel9`). The container bundles the Habana Synapse AI software stack (drivers, runtime, PyTorch modules), upstream vLLM, and the vllm-gaudi plugin, producing a self-contained inference server image. This image is consumed by KServe `ServingRuntime` CRs to deploy vLLM model servers on Gaudi-equipped OpenShift clusters as part of the RHOAI model serving stack.

## Architectural Analysis

### Plugin Architecture and vLLM Integration

vllm-gaudi follows vLLM's out-of-tree (OOT) platform plugin architecture, which enables hardware-specific optimizations without modifying vLLM core. The plugin registers itself through Python entry points defined in `setup.py` (lines 66-72): `vllm.platform_plugins` for the HPU platform class, and `vllm.general_plugins` for utilities, custom ops, and model registrations. This is a clean integration pattern -- the plugin can evolve independently of vLLM releases, with version compatibility managed through the `VLLM_STABLE_COMMIT` file that pins the tested upstream vLLM commit. The `HpuPlatform` class (334 lines) overrides 20+ methods from vLLM's `Platform` base class, covering device management, attention backend selection, configuration validation, distributed communication, and LoRA support.

### Unified Attention: A Novel Algorithm

The most architecturally significant contribution is the unified attention system (`extension/unified.py`, 931 lines; `extension/unified_batch.py`, 949 lines). This implements a novel 3-path attention algorithm that processes causal (unfrozen), shared block, and unique block attention independently, then merges results using flash-attention-style online softmax. This avoids materializing the full attention matrix and enables efficient prefix caching. The algorithm has a chunked variant for memory-constrained scenarios that generates bias on-the-fly from dense block_usages tensors. A dedicated `HPUAsyncScheduler` (22 lines) extends vLLM's async scheduler to handle spurious tokens that the unified attention path may generate before the scheduler expects output. This tight coupling between attention algorithm and scheduler is a potential maintenance risk as vLLM evolves.

### Dynamic Bucketing for Graph Compilation

HPU accelerators require static shapes for efficient graph compilation, but LLM inference has highly variable sequence lengths. The bucketing system (`extension/bucketing/`, 6 files, ~1,150 lines) solves this by mapping variable shapes to a set of pre-determined "buckets." Three strategies are available: exponential (for high-range values), linear (for low-range), and vision-specific (for multimodal encoder outputs). A file-based strategy allows production tuning without code changes via `VLLM_BUCKETING_FROM_FILE`. This is a pragmatic solution to a fundamental hardware constraint, but it introduces a tuning surface that operators must understand for optimal performance.

### FIPS Provider Removal and Security Implications

The Dockerfile explicitly removes the OpenSSL FIPS provider (`rpm -e --nodeps openssl-fips-provider-so`, line 63). This is done because the Habana software stack (Synapse AI, PyTorch HPU modules) may not be compatible with FIPS-mode OpenSSL. While vllm-gaudi itself does not perform TLS (the platform ingress handles encryption), this means all Python libraries in the container (requests, urllib3, etc.) operate with non-FIPS OpenSSL. This is a deliberate trade-off documented in the Dockerfile comment as "System setup - Remove FIPS provider." For RHOAI deployments in FIPS-mandated environments, this represents a compliance gap that must be tracked.

### Non-Hermetic Build Pipeline

The build is explicitly non-hermetic (`hermetic: false` in Tekton pipeline). During image build, the Dockerfile clones two GitHub repositories (`vllm-project/vllm` and `vllm-project/vllm-gaudi`), downloads RPMs from `vault.habana.ai`, and installs Python packages from PyPI. While the build args pin specific versions (`VLLM_GAUDI_COMMIT=v0.16.0`, `VLLM_PROJECT_COMMIT=v0.16.0`), there are no lock files for Python dependencies, RPMs, or artifacts. This means builds are not fully reproducible and are vulnerable to supply chain attacks via dependency confusion or upstream package tampering. The absence of Hermeto/cachi2 prefetch integration and `rpms.lock.yaml` files are supply chain risks worth tracking.

### Quantization and Model Support

The plugin supports a rich set of quantization methods: FP8 (with Gaudi2/Gaudi3 format differences -- `float8_e4m3fnuz` vs `float8_e4m3fn`), GPTQ, AWQ, ModelOpt, compressed-tensors, and Intel Neural Compressor (INC). The calibration pipeline (`calibration/`, 8 files) provides a 6-step process for FP8 quantization including device detection, dataset preparation, scale measurement, postprocessing, quantization, and measurement unification across tensor parallel ranks. Model-specific handling exists for Mixtral (blocking self_attn/lm_head) and DeepSeek (block quantization with expert parallelism). The plugin registers 15+ model families including multimodal models (Qwen2.5-VL, Gemma3-MM, Pixtral) with HPU-specific optimizations.
