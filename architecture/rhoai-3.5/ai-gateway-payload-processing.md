## Purpose

**Short**: Envoy ext_proc service that provides payload processing plugins for the RHOAI AI Gateway, enabling multi-provider LLM routing with API translation, credential injection, metering, and content guardrails.

**Detailed**: AI Gateway Payload Processing is a pluggable Inference Payload Processor (IPP) built on the llm-d framework. It runs as an Envoy External Processing (ext_proc) filter attached to the platform's Gateway, intercepting inference requests and responses in the Envoy data plane. The service resolves client-facing model names to external LLM providers (OpenAI, Anthropic, Azure, AWS Bedrock, Vertex AI), translates API formats between OpenAI Chat Completions, Anthropic Messages, and Vertex AI protocols, injects provider-specific authentication credentials (API keys, AWS SigV4, GCP OAuth2), and enforces token metering with balance checks.

The component defines two custom CRDs — `ExternalProvider` and `ExternalModel` — in the `inference.opendatahub.io` API group. Controllers reconcile these CRDs to create Istio networking resources (Service, ServiceEntry, DestinationRule) for TLS origination to external endpoints, and Gateway API HTTPRoutes for per-model routing through the platform's ingress gateway. The plugin pipeline is configurable via profiles, with the default profile chaining: maas-headers-guard → model-extractor → model-provider-resolver → stream-usage-enforcer → api-translation → apikey-injection. A legacy migration controller watches `maas.opendatahub.io` ExternalModel CRs and creates corresponding `inference.opendatahub.io` resources for backward compatibility.

## Architectural Analysis

The AI Gateway Payload Processing component implements a dual-personality architecture: it is simultaneously an Envoy ext_proc sidecar (data plane) and a Kubernetes controller (control plane). The ext_proc personality handles real-time request/response mutations through a configurable plugin pipeline, while the controller personality reconciles CRDs to maintain the networking infrastructure that routes traffic to external providers. Both run in the same Go process, sharing in-memory stores (infoStore, secretStore) that bridge the two domains — controllers populate the stores from CRD watches, and plugins read from them during request processing.

The plugin pipeline follows the Chain of Responsibility pattern, with each plugin reading from and writing to a shared CycleState object. The ordering is significant: `maas-headers-guard` captures and strips internal headers first, `model-provider-resolver` resolves the model to a provider and writes routing metadata, `stream-usage-enforcer` ensures usage data will be available, `api-translation` rewrites the request body to the provider's native format and sets the `:path` pseudo-header, and `apikey-injection` adds the final authentication headers. This design means each plugin is loosely coupled but the pipeline as a whole has implicit ordering dependencies.

The multi-provider routing design is notable: an ExternalModel can reference up to 64 ExternalProviderRefs with independent weights, API formats, auth configs, and path templates. The model-provider-resolver plugin performs weighted random selection at request time and sets the `x-ipp-selected-provider` header, which the HTTPRoute rules match on to route to the correct backend. This achieves provider-level A/B testing and failover without any Envoy configuration changes — the controller generates the HTTPRoute rules statically, and the plugin drives the selection dynamically per-request.

The credential management approach uses defense-in-depth: while the RBAC ClusterRole grants broad Secret access (required for cross-namespace watches in multiNamespace mode), the apikey-injection plugin creates a separate label-filtered informer cache that only lists Secrets with `inference.llm-d.ai/ipp-managed: "true"`. This means the process never caches or processes unrelated Secrets, even though the RBAC would allow it. The credentials are stored in-memory (never written to disk) with namespace/name keying for tenant isolation.

The legacy migration controller provides a backward-compatible upgrade path from the older `maas.opendatahub.io` API group to the current `inference.opendatahub.io` API group. It uses unstructured client access to watch CRDs that may not exist on the cluster (gracefully skipping registration if the legacy CRD is not installed). Migrated resources are owned by the legacy CR, so deletion cascades correctly.
