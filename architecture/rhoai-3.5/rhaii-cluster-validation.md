## Purpose

**Short**: kubectl plugin for preflight validation of GPU cluster readiness for AI/ML inference workloads.

**Detailed**: RHAII Cluster Validation is a Go CLI tool that runs as a kubectl plugin (`kubectl rhaii-validate`) to verify that a Kubernetes cluster is ready for GPU-accelerated AI workloads. It deploys ephemeral validation Jobs onto GPU nodes to check hardware health (GPU driver version, ECC memory errors), RDMA connectivity, network topology (GPU-NIC NUMA affinity, PCIe distance), TCP bandwidth (iperf3), TCP latency, RDMA bandwidth (ib_write_bw), and RDMA connectivity mesh (ibv_rc_pingpong).

The tool auto-detects the cloud platform (AKS, EKS, CoreWeave, OpenShift), GPU vendor (NVIDIA, AMD), and cluster topology. It produces a structured pass/fail report stored in a ConfigMap for persistence. The architecture follows a controller pattern: the CLI binary acts as a controller that creates Kubernetes Jobs on each GPU node, collects their JSON output from pod logs, and aggregates results into a final report. Two container images are shipped -- the validator (Go binary with nvidia-smi/ibstat tools) and the tools image (iperf3, perftest/ib_write_bw with CUDA support for GPUDirect RDMA testing).

The component supports multi-platform clusters and validates five CRD dependencies (Gateway API, InferencePool, LeaderWorkerSet, cert-manager) and three operator dependencies (cert-manager, Istio, LeaderWorkerSet) as prerequisites for llm-d inference deployment.

## Architectural Analysis

The architecture follows a **hub-and-spoke controller pattern** where the CLI binary acts as a centralized controller that communicates exclusively through the Kubernetes API. Rather than deploying a persistent operator, the tool creates ephemeral Batch Jobs for each validation phase and collects results by streaming pod logs. This is an intentional design choice -- the tool creates no persistent cluster state beyond two ConfigMaps (configuration and report), making it safe to run in production clusters without long-lived footprint.

The **GPU-NIC topology discovery** is the most architecturally interesting subsystem. The tool builds a complete model of each node's PCIe tree by walking `/sys/bus/pci/` and `/sys/class/` hierarchies on the host via `chroot /host`. Three pairing strategies are implemented: PCIe distance (preferred, uses shortest tree hops), NUMA affinity (fallback when PCIe paths are flat or missing), and bandwidth probe (measures actual intra-host loopback ib_write_bw to determine optimal GPU-NIC pairs on flat-topology VMs). The bandwidth probe phase deploys a separate set of privileged Jobs that test all GPU x NIC combinations on each node, then uses the measured bandwidth to override the topology-based pairing. This three-tier pairing strategy handles the heterogeneity of GPU VM topologies across AKS, EKS, CoreWeave, and bare-metal OpenShift.

The **security model** is worth noting for its minimalism. The ServiceAccount's ClusterRole has zero rules -- the pods never call the Kubernetes API (automountServiceAccountToken: false). All API interaction happens through the invoking user's kubeconfig. The only elevated privilege is the `privileged: true` SecurityContext on check pods, which is required for host sysfs access and GPU driver interaction via `chroot /host`. On OpenShift, this is gated by the SCC system. The tool creates and cleans up its own RBAC resources, with a deferred cleanup that runs even after SIGINT.

The **image resolution system** uses a three-tier hierarchy: embedded defaults (via `//go:embed` of `image-references.yaml`), environment variable overrides (`RELATED_IMAGE_*`), and CLI flag overrides. This follows the RHOAI pattern where Konflux and OLM pipelines inject digest-pinned image references via environment variables, while developers can use mutable tags during development. The tool warns when non-digest-pinned images are used.

The **CRD validation** goes beyond simple existence checks -- it discovers served API versions, validates minimum API version requirements, and extracts release versions via JSONPath from CRD annotations (e.g., Gateway API bundle-version). This provides version-specific validation that catches cases where a CRD is installed but at an incompatible version. The fallback CRD name mechanism (e.g., `inference.networking.x-k8s.io` to `inference.networking.k8s.io`) handles the Gateway API graduation pattern where experimental APIs drop the `x-` prefix.
