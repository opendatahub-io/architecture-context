## Purpose

**Short**: A multi-command Go operator. The AIHub module operator installs two child operators: one deploys per-namespace Model Registry REST services from `ModelRegistry` CRs, and one runs a single shared Model Catalog service from the `Catalog` CR.

**Detailed**: The `model-registry-operator` image (`odh-model-registry-operator-rhel9`) contains one Cobra binary, `/manager`, that runs as three independent operator processes, selected by subcommand (`cmd/root.go`). The **AIHub operator** (`manager aihub`) is the module entry point that the RHOAI platform operator (rhods-operator) deploys through `config/overlays/aihub`. It reconciles the cluster-scoped singleton `AIHub` CR (`components.platform.opendatahub.io/v1alpha1`, named `default-aihub`). It renders the embedded kustomize bundle at `/opt/manifests-template/modelregistry/overlays/odh` and applies it with server-side apply through `odh-platform-utilities`' Deployer. That bundle installs the two child operators, their CRDs, RBAC, webhooks and NetworkPolicies. AIHub also creates the instances namespace (default `rhoai-model-registries`), creates the singleton `Catalog` CR, creates its own ServiceMonitor, and reports child readiness up to the DataScienceCluster (DSC) as `AIHubReady`.

The **ModelRegistry operator** (`manager` / `manager modelregistry`, Deployment `model-registry-operator-controller-manager`) reconciles namespaced `ModelRegistry` CRs (`modelregistry.opendatahub.io` v1alpha1/v1beta1, with v1beta1 as the storage version). For each CR it deploys a Model Registry REST server (`rest-container`) with a `kube-rbac-proxy` sidecar. It can also deploy a PostgreSQL 16 pod. Around those it creates a Service, ServiceAccount, RBAC (a Role, an OpenShift Group and an auth-delegator ClusterRoleBinding), NetworkPolicies, an OpenShift reencrypt Route, and a Gateway API `HTTPRoute` that attaches to the platform `data-science-gateway`. It also serves the ModelRegistry mutating, validating and conversion webhooks.

The **Catalog operator** (`manager catalog`, Deployment `catalog-controller-manager`) reconciles the singleton namespaced `Catalog` CR (`aihub.opendatahub.io/v1alpha1`, which must be named `catalog`). It deploys the shared `model-catalog` service: the model-registry image run in catalog mode, plus a kube-rbac-proxy sidecar, init containers that copy and validate catalog and benchmark data images, and a PVC-backed PostgreSQL. On OpenShift it manages scheduled-import ImageStreams (`model-catalog-data:stable`, `model-catalog-benchmark-data:stable`) so catalog data can update independently of operator releases. Image selection, validation and rollout readiness are tracked as detailed Catalog conditions that AIHub aggregates into `CatalogDataReady`.

## Architectural Analysis

**One image, three operators, two tiers.** In RHOAI 3.x the old "component" (which the platform operator rendered directly) became a "module". The platform operator now deploys only the AIHub operator plus the AIHub and Catalog CRDs. AIHub then owns the child-operator lifecycle: it renders kustomize at runtime from manifests baked into the image by `hack/get_aihub_manifests.sh` (`Dockerfile.konflux:22`). It stamps child Deployments with `RELATED_IMAGE_*` values and the namespaces and gateway domain from the AIHub spec, and applies everything in CRD-first SSA order. This makes the operator self-contained for upgrades. It also means AIHub's ClusterRole has to cover the union of everything the child bundles contain, including `customresourcedefinitions` create/patch, `mutating/validatingwebhookconfigurations` create/delete, `clusterroles` create/delete, and `namespaces` create. AIHub is therefore one of the most privileged service accounts in the module. `deploy.WithLegacyOwners` adopts resources previously owned by the in-tree opendatahub-operator ModelRegistry component, and `reconcileIncompatibleSelectors` deletes and recreates child Deployments whose immutable selectors changed. Together these give an explicit upgrade migration path.

**Ingress is dual-path.** Each registry and the catalog are exposed through two paths:

- A Gateway API `HTTPRoute` in `HTTPROUTE_NAMESPACE` (default `redhat-ods-applications`). It attaches to `data-science-gateway` in `openshift-ingress`, uses path prefixes `/model-registry/{name}/` and `/catalog/`, and rewrites the URL. A `ReferenceGrant` permits the cross-namespace backend reference.
- An optional OpenShift `Route` with `reencrypt` termination to the kube-rbac-proxy `https-api` port. It is enabled by default when kube-rbac-proxy is configured (`api/v1beta1/modelregistry_types.go:227`).

kube-rbac-proxy is the only authentication and authorization point for data-plane traffic. It performs a TokenReview, then a SubjectAccessReview for `get` on the instance's own Service (`kube-rbac-proxy-config.yaml.tmpl`). So "can call the registry" is modelled as Kubernetes RBAC on a Service object, and the operator creates a `registry-user-{name}` Role and an OpenShift `{name}-users` Group to make granting access easy. The ModelRegistry defaulter migrates legacy `oauthProxy` specs to `kubeRBACProxy`, and defaults to kube-rbac-proxy on OpenShift when no proxy is configured (`api/v1beta1/modelregistry_webhook.go:66-74`). On non-OpenShift clusters a ModelRegistry can therefore run with no auth proxy at all, which leaves the REST API unauthenticated on port 8080.

**TLS follows the cluster profile.** All three managers read `APIServer/cluster.spec.tlsSecurityProfile` at startup through `odh-platform-utilities/framework/tls` and apply it to the webhook and metrics servers (`internal/tls/tls.go`). They also watch the APIServer so a profile change triggers a controlled restart. For kube-rbac-proxy sidecars the operator converts the profile into `--tls-min-version`, `--tls-cipher-suites` and curve flags (`internal/tls/proxy.go`). It drops X25519 and X25519MLKEM768 and non-FIPS ciphers when FIPS mode is detected (`crypto/fips140.Enabled()` or `/proc/sys/crypto/fips_enabled`). Profiles below TLS 1.2 fall back to Intermediate, and unusable Custom profiles fail closed. One nuance: the operator's own servers accept whatever minimum version the cluster profile allows (`minTLSVersion` maps TLS 1.0 and 1.1). They also advertise `h2` in ALPN (`internal/tls/tls.go:68`), unlike the common Kubebuilder scaffold, which disables HTTP/2.

**Database security is opt-in.** User-provided PostgreSQL defaults to `sslMode: disable` (`api/v1beta1/modelregistry_types.go:80`). The auto-provisioned PostgreSQL pods (registry and catalog) are reachable only through in-namespace NetworkPolicies that restrict port 5432 to the owning app pods, and they talk over plaintext. Passwords are generated with `crypto/rand` (`internal/utils/io.go:55`) and stored in operator-created Secrets.

**Risks and observations:**

- Registry names must be unique across the cluster. The validating webhook lists every ModelRegistry cluster-wide (`api/v1beta1/modelregistry_webhook.go:244`) because the derived cluster-scoped objects (Group `{name}-users`, ClusterRoleBinding `{name}-auth-delegator`) would otherwise collide.
- Both the ModelRegistry and Catalog webhooks force CRs into `REGISTRIES_NAMESPACE` when it is set. This is also what keeps the namespace-scoped informer caches correct.
- The webhooks use `failurePolicy: Fail`. AIHub deliberately waits for the Catalog operator Deployment to be Available before creating the Catalog CR (`internal/controller/aihub_controller.go:386-390`).
- Egress NetworkPolicies are allow-all for the operators, the registry pods and the catalog pod (RHOAIENG-90747).
- Data image rollout uses scale-down as "temporary containment" for import or validation failures. The README states this does not guarantee old content stops being served.
- The registry ingress NetworkPolicy also admits `automl-ui` pods from any namespace labelled `opendatahub.io/generated-namespace: "true"` (`ingress-network-policy.yaml.tmpl`). This cross-namespace allowance is worth tracking.

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-registry instance (ModelRegistry CR); all instances share one namespace (`REGISTRIES_NAMESPACE`, RHOAI default `rhoai-model-registries`) | `api/v1beta1/modelregistry_webhook.go:202-212` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-registry kube-rbac-proxy SAR on `services/{name}`; per-registry Role + OpenShift Group | Kubernetes RBAC (via kube-rbac-proxy) | Authorization is all-or-nothing per registry (no read/write split); catalog access granted to every authenticated user |
| Data storage | Separate DB per registry (user-provided or auto-provisioned pod); catalog has its own PVC-backed DB | Application config / Kubernetes | Users may point multiple registries at the same external DB; DB TLS off by default |
| Network traffic | Per-registry ingress NetworkPolicy (router/gateway ns + `automl-ui` pods); per-DB NetworkPolicy (owning app only) | Kubernetes NetworkPolicy | Egress allow-all; 8080 plaintext reachable inside pod only when proxy present |
| Compute & resources | Per-Deployment resource requests/limits; Catalog `spec.resources` | Kubernetes | No ResourceQuota created |
| Configuration & secrets | All instances' Secrets in one shared namespace | Kubernetes RBAC | Any principal with Secret read in the instances namespace sees every registry's DB credentials |
| API scoping | Informer caches scoped to `REGISTRIES_NAMESPACE`; webhooks deny CRs elsewhere | Kubernetes + Application (webhook) | Name-uniqueness check lists cluster-wide; AIHub cache scoped by `platform.opendatahub.io/part-of=aihub` label |

| Shared Service | Tenant Boundary | Isolation Mechanism |
