## Purpose

**Short**: Builds the RHOAI workbench images (JupyterLab and code-server) and the Elyra/Data Science Pipelines runtime images, and publishes them to the platform as OpenShift ImageStreams.

**Detailed**: The `notebooks` repository produces the user-facing IDE containers that run inside a Data Science Project when a user creates a workbench. Each image is a self-contained multi-stage Dockerfile. It starts `FROM ${BASE_IMAGE}`, which for RHOAI is an AIPCC base image pinned by digest, and rebuilds its conceptual layers internally: minimal → datascience → pytorch / pytorch+llmcompressor / tensorflow. No image uses another notebook image as its `FROM`. On the `rhoai-3.7-ea.1` branch, Konflux builds 15 images hermetically: 10 workbenches (Jupyter minimal CPU/CUDA/ROCm, datascience, pytorch CUDA, pytorch+llmcompressor CUDA, tensorflow CUDA, universal CPU; code-server datascience and minimal) and 5 pipeline runtimes (minimal, datascience, pytorch, pytorch+llmcompressor, tensorflow). They are pushed to `quay.io/rhoai/<name>-rhel9`.

The repository also ships `manifests/rhoai/`, a kustomize bundle with 24 `ImageStream` resources. A `configMapGenerator` turns `params.env`, `params-latest.env`, `commit.env` and `commit-latest.env` into the ConfigMaps `notebook-image-params` and `notebook-image-commithash`. Kustomize `replacements` then inject image digests and build-commit annotations into each ImageStream tag. `rhods-operator` (workbenches component) consumes this directory and patches `params-latest.env` with its own `RELATED_IMAGE_*` values from the CSV. In the repo, the N version (`3.7`) carries `dummy` placeholders. The N-1..N-5 tags (`3.6`, `3.5`, `3.4`, `2025.2`, `2025.1`) point to released `registry.redhat.io/rhoai/...@sha256` digests. The Dashboard reads ImageStreams labelled `opendatahub.io/notebook-image: "true"` to offer workbench images, and Elyra/AI Pipelines read `opendatahub.io/runtime-image` streams as pipeline-node runtimes.

At runtime, the images are passive workloads. The ODH notebook controller (in `kubeflow`) creates a `Notebook` CR → StatefulSet/Pod. It injects `NOTEBOOK_ARGS` (port 8888, empty token/password, base URL `NB_PREFIX`), mounts the Elyra runtime config and PVC, and puts the container behind a Gateway API `HTTPRoute` with a `kube-rbac-proxy` sidecar. The image's job is to serve all content under `${NB_PREFIX}` on port 8888, answer culler probes on `${NB_PREFIX}/api/kernels`, and provide the SDK/client stack for the rest of the platform: KFP, Elyra, Kale, CodeFlare/Ray, Feast, MLflow, Kubeflow Trainer via `universal`, `oc`, database connectors, and S3/MinIO clients.

## Architectural Analysis

**Images, not services.** Most of the analyzer's inventory is incidental to this repo's architecture. The "HTTP endpoint `PATCH time.sleep`" and the "Service `notebooks`" both come from a CI helper, `ci/cached-builds/make_test.py:183`. The FastAPI/uvicorn/gunicorn/flask entries are dependencies installed inside images for users. They are not services the repo runs. The real runtime surfaces are the processes the entrypoint scripts start:

- **Jupyter images**: `start-notebook.sh` → `jupyter lab` on `NOTEBOOK_PORT`/8888. It always passes `--ServerApp.ip=""` and `--ServerApp.allow_origin="*"` and appends controller-supplied `NOTEBOOK_ARGS`.
- **code-server images**: `run-code-server.sh` starts three processes. nginx on 8888 is the public listener and rewrites `${NB_PREFIX}/codeserver/` to the backend. code-server runs with `--auth none` on 8787. httpd on 8080 runs a CGI (`/api/kernels/`) that turns code-server `/healthz` into a Jupyter-style kernel-activity JSON for the idle culler.
- **`jupyter-universal`**: `entrypoint-universal.sh` is a dual-mode entrypoint. With no command it runs JupyterLab (workbench mode). With `runtime` as the first argument, or a command override, it runs the Elyra `bootstrapper.py` or the supplied command (pipeline/trainer runtime mode). The same digest therefore backs both `jupyter-universal-notebook` and `runtime-universal` ImageStreams. This matches the dual-purpose pattern in overlay 0013, but here it is a CPU Jupyter/Elyra image built in this repo.

**Security is delegated to the platform.** None of the in-pod listeners authenticates. Jupyter runs with token and password disabled by the controller contract (see `jupyter/minimal/ubi9-python-3.12/kustomize/base/statefulset.yaml`), code-server runs with `--auth none`, and both serve plain HTTP. The whole authentication model rests on the notebook controller's `kube-rbac-proxy` sidecar plus the Gateway/HTTPRoute. The controller's NetworkPolicies limit direct pod access (not in this repo). Two details widen the attack surface if those controls are missing:

1. code-server binds `[::]:8787` / `0.0.0.0:8787` (`run-code-server.sh:197-200`) rather than loopback, so the unauthenticated backend is reachable on the pod IP, not only through nginx.
2. Jupyter's `allow_origin="*"` turns off origin checks.

Neither is exploitable through the supported ingress path. Both depend on network isolation that sits outside this repo.

**Supply chain.** Every RHOAI pipeline sets `hermetic: 'true'`. RPMs come from `prefetch-input/rhds/rpms.lock.yaml` (shared by Jupyter and runtimes) or per-code-server `prefetch-input/rhds/` locks. Python wheels come from hash-pinned `requirements.<flavor>.txt` files resolved against the AIPCC channel index `https://packages.redhat.com/api/pypi/public-rhai/<channel>/simple/`. code-server's npm graph (~70 `package-lock.json` roots) and generic artifacts (`artifacts.lock.yaml`) are prefetched too. `mongocli` is built from a git submodule with `gomod` prefetch. Inside the Dockerfiles, `uv pip install` runs with `--no-index --no-config --find-links /cachi2/output/deps/pip`, plus `--no-verify-hashes` and `--index-strategy=unsafe-best-match`. Hash integrity is therefore enforced at Hermeto prefetch time, not re-checked at install time. `--no-config` also deliberately ignores the base image's `pip.conf`/`uv.toml`.

**AIPCC "à la carte" channel adoption.** Base images and indexes are selected per image family by channel, not by product version (ADR `docs/architecture/decisions/0016-adopt-a-la-carte-content-delivery-for-aipcc-notebooks.md`, status *Proposed* but already applied):

- CPU images: `cpu-torch2.13-el9.8`
- CUDA PyTorch/LLM Compressor: `cuda13.0-torch2.13-el9.8`
- TensorFlow: `cuda12.9-torch2.13-el9.8`
- ROCm minimal: `rocm7.14-torch2.12-el9.8`

`versions_config.yml` → `make sync-build-args-from-versions` is the single control point for these `BASE_IMAGE` pins.

**Lifecycle signals in 3.7-ea.1.** The manifests show a large catalog transition:

- **Deprecated ImageStreams.** Nineteen of the 24 RHOAI ImageStreams carry `opendatahub.io/deprecated: "true"`. That covers all the classic Jupyter streams, `code-server-notebook`, and every flavour runtime stream, including the `-2025-2` copies. Only `code-server-minimal-notebook`, `jupyter-universal-notebook` and `runtime-universal` are not marked. In the Dashboard this shows a "Deprecated" badge for the whole stream (`docs/workbench-imagestreams.md:31`). Together with the new `universal` and `code-server-minimal` images, this points to a consolidation of the workbench catalog.
- **Streams with no 3.7 tag.** `jupyter-rocm-pytorch`, `jupyter-rocm-tensorflow` and `odh-trustyai-notebook` stop at `3.6`, and no ROCm PyTorch/TensorFlow or TrustyAI images are built on this branch.
- **Python 3.11.** Python 3.11 images survive only as the `2025.1` tags.

**ODH-only artefacts in the tree.** `baseline` images (Jupyter, code-server, runtime) use the CentOS Stream 9 `odh-base-image-cpu-py312-c9s` base. They are not in `manifests/rhoai/base` and appear only through an opt-in `manifests/rhoai/overlays/additional/baseline` overlay that an admin must apply manually. The `che-code` (Dev Spaces VS Code) variant is built only by an ODH `main`-branch, non-hermetic pipeline.

**Risks worth tracking:**

- Unauthenticated in-pod listeners that rely entirely on platform proxies and NetworkPolicy.
- Non-FIPS crypto libraries (`pycryptodome`, `pynacl`) shipped in most images, which is consistent with the images being explicitly outside "Designed for FIPS".
- The Elyra bootstrapper downgrades to plain HTTP when the object-storage endpoint uses `http://`.
- Most of the catalog is being deprecated in an EA release while still receiving N-version builds.

## Multi-Tenancy

The images do not implement tenancy themselves. Each workbench is a single-user pod in the user's Data Science Project namespace. Tenancy is fully delegated to the notebook controller, Kubernetes RBAC and the Gateway/kube-rbac-proxy layer.

| Aspect | Value | Source |
