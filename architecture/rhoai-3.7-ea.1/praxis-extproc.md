## Purpose

**Short**: A Rust gRPC Envoy External Processing (ExtProc) server that runs [Praxis](https://github.com/praxis-proxy/praxis) filter pipelines to inspect, change, or reject HTTP headers and bodies for the Models-as-a-Service (MaaS) AI gateway.

**Detailed**: praxis-extproc is a standalone `envoy.service.ext_proc.v3.ExternalProcessor` gRPC server. Envoy's `ext_proc` HTTP filter opens one bidirectional gRPC stream per HTTP request. The server turns each ExtProc message (request headers, request body, response headers, response body) into a Praxis `HttpFilterContext`. It then runs a `FilterPipeline` that is built once at startup from YAML, and sends back `ProcessingResponse` mutations or an `ImmediateResponse`, for example a 413 for oversized bodies. Envoy still owns listeners, routing, upstream connections and load balancing. praxis-extproc only adds policy. The filter catalogue comes from `praxis-proxy-filter` (core filters such as `headers`, `json_body` and `request_id`) and `praxis-ai-filters` (AI filters such as `llmisvc_model_provider_resolver`, OpenAI Responses, AWS SigV4 signing and guardrails), both pulled from crates.io or git.

In RHOAI it replaces the Go "Inference Payload Processor" (IPP, `ai-gateway-payload-processing`); see `docs/migration-ipp-to-praxis.md`. The ODH/MaaS kustomize overlay deploys **two instances of the same image** next to the MaaS Istio gateway (`maas-default-gateway` in `openshift-ingress`):
- **`payload-pre-processing`** (pre-auth, "BBR" chain). It runs before the Kuadrant auth/rate-limit Wasm filter. It strips any caller-supplied `X-Gateway-Model-Name` header, copies the JSON body's `/model` into that header, and resolves the model provider/publisher for KServe `LLMInferenceService` routing.
- **`payload-processing`** (post-auth, "IPP" chain). It runs after Kuadrant. It strips credentials and internal `x-maas-*` identity headers before requests reach model backends (except on maas-api management routes), adds a request ID, and processes buffered responses.

The image is a FIPS build. The Konflux `CARGO_FEATURES` are `responses,aws-sigv4,store-postgres-cert-auth`. The build deliberately leaves out the Praxis Policy Engine and the SQLite/password-auth Postgres response stores, because those carry pure-Rust crypto. All primitives go through the system OpenSSL on a UBI 9 minimal PQC runtime.

## Architectural Analysis

**Sidecar-free policy plane bolted onto Istio via EnvoyFilter.** This component has no CRDs, controller or reconcile loop. Its integration with the platform is entirely declarative. An Istio `EnvoyFilter` (`deploy/overlays/odh/envoy-filter.yaml`) inserts two `ext_proc` HTTP filters into the gateway's HTTP connection manager, anchored before and after the Kuadrant Wasm plugin. The filter is written against four alternative subfilter names, including a misspelled `extenstions.istio.io/...` variant, to cover different Istio/OSSM and Kuadrant naming. The EnvoyFilter also defines its own `CLUSTER`s (`payload-pre-processing-extproc` and `payload-processing-extproc`) instead of Istio `outbound|*` clusters. The reason: Istio's metadata-exchange filter injects frames that the non-mesh Praxis HTTP/2 server rejects as `protocol_error`. These clusters pin TLS with SNI and SAN matching, use the OpenShift service-CA bundle as the trust anchor, set ALPN `h2`, and limit concurrency with circuit breakers (8 connections, pending, requests and streams). The design depends on Istio internals. A block of the EnvoyFilter removes Istio's own `envoy.filters.http.ext_proc`, used for the Gateway API Inference Extension EPP, and re-inserts it in front of the router, so that a per-route `ExtProcPerRoute` override and `envoy.lb` metadata forwarding keep working. The comments say this copies what Istio renders up to 1.31. Upgrading Istio/OSSM is therefore a known coupling risk.

**Fail-closed security posture.** Both ext_proc filters set `failure_mode_allow: false`. If praxis-extproc is unavailable or slow (300 s timeout), inference requests fail. This is deliberate because the pre-auth chain is a trust boundary: routing identity must come from the body, not from a forged header. The post-auth chain is a confidentiality boundary: it removes `authorization`, `x-api-key` and around 20 `x-maas-*` identity/tenant/subscription headers before traffic leaves for model servers. The trade-off is availability. Each instance runs `replicas: 1` with no PodDisruptionBudget or HPA in the repo, so pod restarts block inference traffic until readiness returns. Mitigations are a 5 s preStop sleep and a gRPC readiness probe that reports NOT_SERVING during drain. TLS certificates are loaded only at startup, so service-CA rotation relies on Stakater Reloader (`secret.reloader.stakater.com/reload`) being installed.

**Memory-bounded buffering.** Both chains use BUFFERED body modes. The design couples three limits: `max_body_bytes` (10 MiB), `GRPC_MAX_RECV_MSG_SIZE=11Mi`, and the Envoy cluster `max_requests: 8`. Together they keep peak RSS (measured at about 50 MiB per 10 MiB body, RHAIENG-8104) under the 512 Mi pod limit. Oversized bodies are rejected by tonic before allocation, or answered with a 413 `ImmediateResponse`. The config warns operators never to set `insecure_options.allow_unbounded_body`. Operators can tune these values through ai-gateway-controller `MaasTenantConfig` annotations such as `maas.opendatahub.io/experimental-extproc-max-requests`. The limits have to be kept in step across the ConfigMap, Deployment env and EnvoyFilter, or the guarantee breaks.

**FIPS by construction, enforced at runtime only on request.** The crypto design is unusually explicit:
- One OpenSSL-backed rustls `CryptoProvider` is installed before any filter or connector is built (`src/fips.rs`).
- The ExtProc listener terminates TLS directly with `tokio-openssl`.
- The cipher list is ECDHE-only for TLS 1.2, built from `mozilla_modern_v5` so that deprecated finite-field DH symbols are not linked.
- `fips::blocker()` refuses to serve when `PRAXIS_REQUIRE_FIPS` is set and the binary registers a non-FIPS filter (`policy`, or a non-cert-auth response store).

However, the deployment manifests in this repo do **not** set `PRAXIS_REQUIRE_FIPS`, so the hard gate depends on the consumer. `Cargo.lock` still contains `ring` (via `rustls-webpki` and the dev-only `rcgen`) and `aws-lc-rs` (via `jsonwebtoken`, which only the excluded `policy-engine` feature uses). Whether these get linked into the release binary under the FIPS feature set should be checked with the repo's `make fips-check` / `cargo xtask fips` rather than assumed.

**Observability with in-process auth.** The metrics HTTP listener (9090) serves `/healthz` without auth. When `metrics_auth.enabled` is true, it guards `/metrics` with Kubernetes `TokenReview` plus a `SubjectAccessReview` on the non-resource URL `/metrics`. This does the same job as kube-rbac-proxy, but inside the process using the `kube` client, so no sidecar is needed. The ODH overlay grants the matching cluster roles to the pod SA and to `prometheus-k8s` in `redhat-ods-monitoring`.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | No per-tenant auth; shared SA `payload-processing`. Identity headers stripped post-auth | Application (filter chains) + Kuadrant upstream | Correctness depends on the strip list staying in sync with MaaS header names |
| Data storage | None in the FIPS ODH config (the stateful response store is optional and not configured) | — | If the Responses store is enabled, tenant scoping happens in praxis-ai (`x-maas-responses-owner` is stripped here) |
| Network traffic | NetworkPolicy: ingress only from gateway pods (9004) and monitoring namespaces (9090) | Kubernetes | Server-side TLS only; no mTLS client auth on the gRPC listener |
| Compute & resources | Shared pod limits (512Mi/500m), Envoy circuit breaker of 8 concurrent requests | Kubernetes + Envoy | One tenant's large bodies or bursts can use up the shared 8-request budget and, with fail-closed mode, delay or fail other tenants' requests |
| Configuration & secrets | One shared ConfigMap and TLS Secret per instance | Kubernetes | Per-tenant tuning only through ai-gateway-controller `MaasTenantConfig` annotations, which apply to the whole gateway |
| API scoping | Cluster-wide TokenReview/SAR only for metrics | Kubernetes | — |
