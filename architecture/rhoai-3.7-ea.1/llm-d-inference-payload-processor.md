## Purpose

**Short**: The Inference Payload Processor (IPP) is a pluggable Envoy `ext_proc` gRPC service. It inspects and mutates inference request and response payloads in the llm-d data plane, mainly to inject payload-derived routing headers such as the model name and the base model of a LoRA adapter.

**Detailed**: The Inference Payload Processor runs as a standalone Deployment next to an inference Gateway's L7 proxy (Envoy, Istio Gateway, or a GKE Gateway). The proxy streams each HTTP request and response (headers, body and trailers) to IPP over the Envoy External Processing API (`envoy.service.ext_proc.v3.ExternalProcessor`) on gRPC port 9004. IPP buffers the body until end-of-stream and then runs a configured plugin pipeline:
- pre-processors
- a profile picker that selects one named profile
- the profile's request plugins
- response post-processors

It returns header and body mutations to the proxy. Its main use is payload-aware, multi-pool routing. The `body-field-to-header` plugin copies the OpenAI `model` field into `X-Gateway-Model-Name`, and the `base-model-to-header` plugin maps LoRA adapter names to `X-Gateway-Base-Model-Name`. With those headers, one OpenAI-compatible Gateway endpoint can front many InferencePools and adapters. IPP picks the pool; the llm-d Router's Endpoint Picker (EPP) then picks the pod.

All behaviour comes from plugins declared in a YAML `PayloadProcessorConfig` (`apiVersion: llm-d.ai/v1alpha1`), loaded from `--config-file` or `--config-text`. The in-tree plugins include:
- request and response header injectors
- a `Filter → Score → Pick` ModelSelector framework: model-group filter; in-flight, session-affinity and cost-guard scorers; max-score, random and weighted-random pickers
- datalayer plugins for request metadata, request cost, and a `models.json` model/pricing config collector

The binary hosts a controller-runtime manager. The manager provides the Kubernetes client, the metrics/pprof server, and the ConfigMap reconciler that the base-model plugin uses to read adapter→base-model mappings from ConfigMaps labelled `inference.llm-d.ai/ipp-managed=true`.

In RHOAI 3.7 EA1, this upstream repo is the framework behind the downstream `ai-gateway-payload-processing` component (MaaS AI Gateway). That component imports IPP as a Go library and Helm subchart and adds its own plugins and controllers. Upstream ships a Helm chart (`config/charts/payload-processor`) with three proxy integrations: Istio (`EnvoyFilter` + `DestinationRule`), GKE (`GCPRoutingExtension` + `HealthCheckPolicy`), or none. There are no Konflux Dockerfiles, Tekton pipelines or kustomize overlays on this branch. The image is built by GitHub Actions and pushed to `ghcr.io/llm-d`.

## Architectural Analysis

**A data-plane service shaped like a controller.** `cmd/main.go` → `cmd/runner/runner.go` builds a controller-runtime `Manager`. The manager is mostly used as a lifecycle container. The ext-proc gRPC server (9004) and gRPC health server (9005) are registered as manager `Runnable`s with leader election disabled (`runnable.NoLeaderElection`, `cmd/runner/runner.go:244`, `:317`). Every replica therefore serves traffic, and there is no leader-gated work. The manager is still needed for the controller-runtime metrics server (9090), the optional pprof handlers on that server, and the shared informer cache behind plugin reconcilers. The only in-tree controller is the `base-model-to-header` plugin's `ConfigMapReconciler` (`For(&corev1.ConfigMap{})` with a label predicate, `base_model_to_header.go:66`). The runner also exposes `WithCustomControllers` / `WithCustomCollectors` hooks. These let downstream consumers such as `ai-gateway-payload-processing` add control-plane controllers to the same process. The analyzer labels this an operator, but the component has no CRDs and reconciles nothing into the cluster; it only reads ConfigMaps.

**Configuration is a schema, not an API.** `PayloadProcessorConfig` is defined with kubebuilder markers in `apix/config/v1alpha1`. The source says explicitly: "the CRD JSON Schema validation is NOT used as we don't have a real CRD" (`payloadprocessorconfig_types.go:17-21`). It is only a YAML file format, usually delivered through a ConfigMap mounted at `/config`. No CRD manifest exists in the repo, and nothing watches this config. Changing the plugin pipeline needs a pod restart. The `model-config-datasource` plugin is the exception: it watches its `modelsPath` file with fsnotify.

**Plugin pipeline and failure posture.** Requests are buffered in memory until `EndOfStream` before request plugins run (`pkg/handlers/server.go`). The Istio integration requests `FULL_DUPLEX_STREAMED` body modes and sets `failure_mode_allow: false` (`istio.yaml:31-37`). IPP is therefore a hard dependency in the Gateway request path: if it is down or slow, inference requests on that Gateway fail closed. The chart defaults to `replicas: 1` with no PodDisruptionBudget, HPA, resource requests or anti-affinity, so the default install is a single point of failure for the Gateway. The GKE integration sets a 1s extension timeout (`gke.yaml:18`).

**Transport security is "encrypted but unauthenticated".** `--secure-serving` defaults to `true` (`pkg/server/options.go:67`). When it is on, the ext-proc server generates a fresh self-signed RSA-4096 certificate at every start. The cert is valid for 10 years, kept only in memory, and served with stdlib default TLS parameters (`internal/tls/tls.go:34-72`, `pkg/server/runserver.go:61-70`). The Istio chart path pairs this with a `DestinationRule` (`mode: SIMPLE`, `insecureSkipVerify: true`, `istio.yaml:44-54`). Gateway→IPP traffic is encrypted, but the Gateway does not authenticate the server. No gRPC interceptor authenticates the client either. Any pod that can reach port 9004 can open ext-proc streams. `pkg/common/certs.go` contains a `CertReloader` for mounted `tls.crt`/`tls.key` files, but nothing in the binary uses it, so certificates from cert-manager or service-ca cannot be plugged in. The gRPC health server is always plaintext and always reports `SERVING` (`cmd/runner/health.go:42`).

**Metrics authentication has a latent RBAC gap.** `--metrics-endpoint-auth` defaults to `true`, which installs controller-runtime's `filters.WithAuthenticationAndAuthorization` (`cmd/runner/runner.go:173-182`). That filter needs the pod's ServiceAccount to `create` `tokenreviews` and `subjectaccessreviews`. Neither the Helm chart RBAC (`rbac.yaml`) nor `deploy/components/ipp/rbac.yaml` grants those permissions. The deploy ClusterRole is even named `payload-processor-auth-reviewer` but only grants ConfigMap read. A default chart install therefore serves `/metrics` and `/debug/pprof/*` behind an auth filter whose authorizer calls will fail, so scrapes will most likely be rejected. The e2e manifests avoid this with `--metrics-endpoint-auth=false`. The metrics server never sets `SecureServing`, so it runs plain HTTP on 9090. With auth enabled, scrapers send bearer tokens in cleartext. With auth disabled, `/metrics` and pprof (`--enable-pprof` defaults to `true`) are open to anyone with network reachability. The chart's Service also does not expose 9090.

**Tenancy is namespace-by-default, cluster-wide by opt-in.** If `NAMESPACE` is set (the chart sets it from the downward API unless `multiNamespace: true`), the manager cache is limited to that namespace (`cmd/runner/runner.go:185-190`), and RBAC is a namespaced `Role`. If `multiNamespace: true`, the chart grants a ClusterRole for cluster-wide ConfigMap `get/list/watch` and IPP caches every ConfigMap in the cluster. Inside the process, the `ipp-managed` label predicate decides which ConfigMaps feed the adapter store. That filter is applied by the application, not by Kubernetes, so anyone who can label a ConfigMap in a watched namespace can inject adapter→base-model mappings that affect routing.

**Observability.** Prometheus metrics are registered into the controller-runtime registry: `info`, `success_total`, body-field counters, `plugin_duration_seconds`, model-selector latency and attempts, and `request_ttft_seconds`. The binary default is `--tracing=true`, but both the chart and the e2e manifests pass `--tracing=false`. When tracing is on, the default exporter is `console` (stdout). With `OTEL_TRACES_EXPORTER=otlp`, spans go over OTLP gRPC with `WithInsecure()` (`telemetry.go:156`), so trace export is always plaintext. Trace context is propagated from incoming W3C `traceparent` headers on the proxied request.

**Supply chain and FIPS.** The only Dockerfile builds a static binary: `CGO_ENABLED=0`, no `GOEXPERIMENT=strictfipsruntime`, on `golang:1.27`, copied into `gcr.io/distroless/static:nonroot`. That image fails the Konflux check-payload FIPS gate, which requires a dynamically linked binary and OpenSSL in the image. This branch has no `.konflux` Dockerfile, `rpms.lock.yaml` or Hermeto prefetch, and the builder image tag (`golang:1.27`) is not pinned to match go.mod (`go 1.26.6`). A downstream fork such as `ai-gateway-payload-processing` must supply FIPS-compliant packaging. The Helm chart's default image tag (`v0.1.0`) also lags the chart `appVersion` (`0.2.0`).
