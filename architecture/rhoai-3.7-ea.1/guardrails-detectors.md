## Purpose

**Short**: A set of Python REST microservices ("detectors") that classify text for safety, PII, and format violations, using the IBM/FMS Detector API. The service is deployed as KServe model-serving runtimes that act as a guardrails layer next to LLM inference endpoints.

**Detailed**: guardrails-detectors is the TrustyAI team's set of detector algorithms for the [FMS Guardrails Orchestrator](https://github.com/foundation-model-stack/fms-guardrails-orchestrator). Each detector is a FastAPI app built on a shared base class (`DetectorBaseAPI` in `detectors/common/app.py`) and exposes the FMS "Detector API" contract: `POST /api/v1/text/contents` takes a list of text strings plus `detector_params` and returns, for each input string, a list of detection spans (`start`, `end`, `text`, `detection`, `detection_type`, `score`). The repo contains three detector families:

1. **Hugging Face runtime** (`detectors/huggingface/`). Loads any `AutoModelForSequenceClassification`, `AutoModelForTokenClassification` or `GraniteForCausalLM` (Granite Guardian) model from `MODEL_DIR` and runs inference on CPU or CUDA.
2. **Built-in detectors** (`detectors/built_in/`). Regex PII detectors (email, credit card with Luhn check, SSN, phone, and others), JSON/YAML/XML file-type and schema validators, and a "custom" registry that runs user-supplied Python functions.
3. **LLM-as-a-judge detector** (`detectors/llm_judge/`). Wraps the `vllm-judge` library and sends evaluation prompts to an external OpenAI-compatible LLM endpoint.

In RHOAI 3.7.0-ea.1, Konflux builds **only the Hugging Face runtime** from this repo. The image is `quay.io/rhoai/odh-guardrails-detector-huggingface-runtime-rhel9` (`.tekton/odh-guardrails-detector-huggingface-runtime-v3-7-ea-1-push.yaml:35`). It ships to customers in two ways:
- rhods-operator lists it as the related image `RELATED_IMAGE_ODH_GUARDRAILS_DETECTOR_HUGGINGFACE_RUNTIME_IMAGE`.
- odh-model-controller references it from the OOTB template `guardrails-detector-huggingface-serving-template` (`config/runtimes/hf-detector-template.yaml`).

Users deploy it per namespace as a KServe `InferenceService` on top of that ServingRuntime, supplying a model from S3/PVC storage. The repo also contains a Konflux Dockerfile for the built-in detector (`Dockerfile.konflux.builtIn`, image label `rhoai/odh-built-in-detector-rhel9`), but this release branch has no Tekton PipelineRun for it. The LLM-judge detector has only an upstream (non-Konflux) Dockerfile.

## Architectural Analysis

**Shared detector framework, three deployables.** All three detectors subclass `DetectorBaseAPI`, a `FastAPI` subclass (`detectors/common/app.py:33-136`). The base class provides:
- an in-process detector registry in `app.state.detectors`;
- four Prometheus counters with the prefix `trustyai_guardrails_*` (detections, requests, errors, runtime), labelled by `detector_kind` and `detector_name`;
- uniform 422/HTTP error mapping to `{code, message}`;
- a `GET /health` liveness route that every detector inherits.

Each detector builds its model or registry in a FastAPI `lifespan` hook. The Hugging Face detector loads model weights at startup and fails fast if `MODEL_DIR` is unset (`huggingface/detector.py:132-134`). The LLM judge fails fast if `VLLM_BASE_URL` is unset (`llm_judge/detector.py:25-28`). Model loading is synchronous at startup, so readiness depends on model size; neither the repo examples nor the downstream template configure startup or readiness probes.

**Hugging Face runtime: a model-agnostic classifier.** `Detector.initialize_model()` picks the model class from `config.architectures`:
- Token classifiers require a fast tokenizer, because they need offset mapping.
- Granite causal LMs go through a safe/unsafe logprob comparison path.
- Everything else falls through to sequence classification.

Detection thresholds are set per deployment through environment variables (`THRESHOLD`, `LABEL_THRESHOLDS`, `SAFE_LABELS`, `MAX_LENGTH`). They can be overridden per request through `detector_params`. `MAX_LENGTH` is clamped to the model's maximum length. Inference runs in Starlette's threadpool (`run_in_threadpool`), with **one uvicorn worker** (`Dockerfile.konflux.hf:36`). GPU throughput is therefore bounded by a single process. `DETECTOR_NAME` is injected from `metadata.name` through the downward API, and the code strips the `-predictor` suffix to recover the user's InferenceService name, which becomes the metric label (`huggingface/detector.py:207-215`).

**Metrics in multiprocess mode.** The HF and built-in Dockerfiles set `PROMETHEUS_MULTIPROC_DIR`. Their `/metrics` handlers build a fresh `CollectorRegistry` with `MultiProcessCollector`, so counters from multiple uvicorn workers get aggregated. Two inconsistencies:
- `Dockerfile.konflux.builtIn` does **not** set `PROMETHEUS_MULTIPROC_DIR`, while the upstream `Dockerfile.builtIn:16` does. `MultiProcessCollector` raises when the variable is unset, so `/metrics` on a Konflux-built built-in image would likely return 500. The image is not built on this branch, so this is a latent risk only.
- The LLM judge uses `prometheus_fastapi_instrumentator` without multiprocess mode, with 4 workers (`Dockerfile.judge:19`). Each scrape therefore sees one worker's counters.

**Built-in custom detectors run arbitrary Python.** `CustomDetectorRegistry` loads `built_in/custom_detectors/custom_detectors.py` with `importlib` and runs it in-process (`custom_detectors_wrapper.py:155-201`). Users are expected to overwrite that file, for example through a mounted ConfigMap. Before loading, a best-effort AST scan rejects imports of `os`, `subprocess`, `sys` and `shutil` (with an exception for `from os import environ/getenv`) and calls to `eval`, `exec`, `open`, `compile` and `input`. The code says explicitly that this is "Not a security sandbox" (`custom_detectors_wrapper.py:113`); it is trivially bypassed, for example with `importlib` or `__import__`. Custom functions can also ask for the **full inbound HTTP request headers** (`built_in/app.py:46`, `custom_detectors_wrapper.py:189,209`), which may include `Authorization` bearer tokens forwarded by the orchestrator or a proxy. Whoever controls `custom_detectors.py` therefore gets code execution inside the detector pod and can see caller credentials. Regex evaluation is ReDoS-hardened with the third-party `regex` module and a per-match timeout (`REGEX_TIMEOUT`, default 1.0 s, `regex_detectors.py:12`). XML schema validation uses `xmlschema` with `defuse='always'` (`file_type_detectors.py:145`). Plain XML well-formedness checking uses stdlib `xml.etree.ElementTree.fromstring` (`file_type_detectors.py:126`).

**No in-application authentication.** None of the apps registers auth middleware or dependencies (`dependencies=[]` everywhere). Authentication is fully delegated to the platform. The example InferenceServices set `security.opendatahub.io/enable-auth: 'true'` and `sidecar.istio.io/inject: 'true'` in RawDeployment mode, which in RHOAI 3.x tells KServe/odh-model-controller to front the predictor with an auth proxy and Gateway routing. When a predictor is reached directly on its ClusterIP Service (port 8000), there is no authentication and no TLS: uvicorn listens in plaintext on `0.0.0.0`. The common `main()` helper supports uvicorn `ssl_*` settings from a config file, but no shipped entrypoint calls it. All Dockerfiles invoke `uvicorn` directly.

**Supply chain and build posture.** The Konflux HF build:
- is **hermetic** (`hermetic: true`) and multi-arch (x86_64, arm64, ppc64le, s390x);
- uses digest-pinned AIPCC base images: the CUDA 13.0 + torch 2.13 image for amd64/arm64 and the CPU + torch 2.13 image for ppc64le/s390x (`.konflux/base-images.conf`, `Dockerfile.konflux.hf:1-9`);
- gets Python wheels from Hermeto pip prefetch of hash-pinned `requirements-hf/{cuda,cpu}/requirements.txt`. The CPU file keeps only native wheels, so it does not collide with checksums in the CUDA prefetch (`detectors/scripts/extract_native_requirements.py`).

Both Konflux Dockerfiles explicitly uninstall `uv` from the AIPCC base to remove its bundled (non-system) crypto (RHOAIENG-97373). One thing to watch: the requirements are compiled against the **legacy product-versioned RHOAI 3.6 indexes** (`rhoai/3.6/cpu-ubi9`, `rhoai/3.6/cuda13.0-ubi9`, `Makefile:1-8`), while the base images are **torch-2.13 channel** images (overlay 0017). The two indexes could drift apart. The pinned `torch==2.13.0` currently matches the base image's torch version.

**Example manifests are demos, not product manifests.** `detectors/*/deploy/` contains sample ServingRuntimes, InferenceServices and a MinIO model store. They use `:latest` and personal-namespace images, hardcoded placeholder MinIO credentials (`THEACCESSKEY`/`THESECRETKEY`, plaintext in the Deployment env and base64 in the Secret), and a `user-one` ServiceAccount bound to the `view` ClusterRole. The MinIO Deployment also has a mis-indented top-level `labels:` key (`model_container.yaml:31`). The LLM-judge sample ServingRuntime tells Prometheus to scrape port `8080`, but the container listens on `8000` (`llm_judge/deploy/servingruntime.yaml:12,30`). The product ServingRuntime comes from odh-model-controller's template, not from these files.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Platform auth proxy/Gateway on InferenceServices with `enable-auth` | Platform (KServe / odh-model-controller) | No in-app auth; in-cluster callers reaching the predictor Service directly bypass auth unless NetworkPolicy restricts them |
| Data storage | Model weights in a per-InferenceService volume; the service is otherwise stateless (no persistence of request text) | Kubernetes | The root logger is at DEBUG (`log_conf.yaml`), and built-in logs `detector_params`; request content could reach logs |
| Network traffic | None defined in repo | Platform | No NetworkPolicy shipped |
| Compute & resources | Requests/limits in ServingRuntime (sample: 18–20 Gi memory, 1–2 CPU) | Kubernetes | Single worker per pod; no concurrency limit configured on the uvicorn CLI path |
| Configuration & secrets | Env vars per ServingRuntime/InferenceService; S3 data-connection Secret per namespace | Kubernetes | Sample manifests embed placeholder credentials |
| API scoping | n/a (no Kubernetes API access) | n/a | None |
