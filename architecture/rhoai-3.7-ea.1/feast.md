## Purpose

**Short**: Feast is the feature store for RHOAI. The Feast Operator reconciles `FeatureStore` custom resources into per-namespace Feast registry, online, offline, UI, lineage, and MCP servers.

**Detailed**: Feast (Feature Store) manages the ML feature lifecycle: it defines features, materializes them from offline stores into online stores, and serves them at low latency for training and inference. In RHOAI the repository produces three Konflux images. `odh-feast-operator` is a Go controller-runtime operator deployed into `redhat-ods-applications`. `odh-feature-server` is the Python Feast runtime. The operator runs it as the registry (gRPC + REST), online feature server, offline (Arrow Flight) server, UI, OpenLineage server, and MCP server. `odh-feast-mcp` is a standalone `feast mcp` Model Context Protocol server image.

The operator watches namespaced `FeatureStore` CRs (`feast.dev/v1`; storage version, with `v1alpha1` still served). For each CR it creates a Deployment with one container per enabled Feast service, plus Services, an optional OpenShift Route (UI only), PVCs, a CronJob for scheduled `feast apply`/`materialize`, HPA/PDB, ServiceMonitor, NetworkPolicies, and per-CR RBAC. It also renders `feature_store.yaml` client configs. A second controller, `NotebookConfigMapReconciler`, watches Kubeflow `Notebook` CRs and writes `notebook-feast-config` ConfigMaps so labeled workbenches get client configs for the Feast projects they reference.

The operator integrates with the wider platform in several ways. It discovers MLflow (`mlflow.opendatahub.io`) and OpenLineage endpoints. On RHOAI it admits traffic from the dashboard (`rhods-dashboard`) through NetworkPolicy. It can run one cluster-wide "data registry" FeatureStore that fronts a Feast REST registry with `kube-rbac-proxy` and serves the `dataregistry.opendatahub.io` API family (namespaces, tables, volumes, generic-tables). It takes the cluster TLS profile from `apiservers.config.openshift.io/cluster`.

## Architectural Analysis

**Operator-as-renderer with a single operand image.** Every Feast server type (registry, online, offline, ui, lineage, mcpserver, data-registry) is the same `RELATED_IMAGE_FEATURE_SERVER` container started with different CLI verbs: `serve`, `serve_offline`, `serve_registry [--rest-api]`, `ui`, `serve_lineage`, `mcp` (`infra/feast-operator/internal/controller/services/services_types.go:59-106`). Configuration reaches the containers as base64 `feature_store.yaml` in env vars (`FEATURE_STORE_YAML_BASE64`), not as mounted files. Secrets referenced by the CR (DB credentials, OIDC client secrets) are therefore read by the operator and inlined into pod env. Anyone who can read the Deployment spec or exec into the pod can see them. The operator's cluster-wide `secrets: get/list/watch` permission exists to support this rendering.

**Two different auth planes.** Feast's own authorization is applied inside the Python servers (Kubernetes TokenReview, or OIDC/JWKS JWT validation) using the Feast `Permission` objects stored in the registry. Platform-style auth (`kube-rbac-proxy` + SubjectAccessReview) is used only in data-registry mode. In that mode the operator forces Feast to `no_auth`, because the proxy already authenticates the caller and Feast's TokenReview would reject valid SA tokens (`repo_config.go:53-60`). The upstream fallback `127.0.0.1:6572` is bound to localhost, so the proxy cannot be bypassed from the pod network. The v1 CRD requires exactly one of `kubernetes`, `oidc`, or `noAuth` when `authz` is set. If `authz` is omitted, the rendered config defaults to Kubernetes auth (`repo_config.go:969`), which is a secure default. `noAuth: true` is an explicit opt-out with no other platform guard.

**Intra-communication token.** Feast servers authenticate to each other with a shared token from a per-CR ConfigMap (`INTRA_COMMUNICATION_BASE64`). The Kubernetes token parser checks this token before calling TokenReview (`sdk/python/feast/permissions/auth/kubernetes_token_parser.py:44`). It is a static bearer credential stored in a ConfigMap rather than a Secret, and it is not rotated by any visible mechanism.

**Network posture is NetworkPolicy-driven.** The operator creates up to six NetworkPolicies per FeatureStore. Same-namespace catch-all, dashboard, workbench, ingress controller, remote registry, and monitoring policies are built in `network_policy.go:83-220`. The workbench policy admits pods labeled `opendatahub.io/feast-integration=true` from **any** namespace (`network_policy.go:468-480`). The cross-namespace boundary therefore relies on who can set that pod label, plus Feast-level auth.

**TLS by default on OpenShift.** When running on OpenShift and no TLS is configured, the operator requests service-serving certificates (`service.beta.openshift.io/serving-cert-secret-name`) per service and switches containers to their HTTPS ports (6567, 8816, 6571/6573, 8443, 6581, 8101) (`services.go`, `tls.go:50-114`). The UI Route uses `reencrypt` with an HTTP→HTTPS redirect (`services.go:895-897`). The operator's own metrics/webhook TLS follows the cluster APIServer TLS profile via `openshift/controller-runtime-common`. A `SecurityProfileWatcher` restarts the operator when that profile changes (`cmd/main.go:141-158, 292-313`; `internal/tls/bootstrap.go`).

**Elevated operator privileges.** `feast-operator-manager-role` is broad for a component operator. It includes cluster-wide `secrets` read, `pods/exec create`, `clusterroles create/update/delete/bind`, `clusterrolebindings` CRUD, `namespaces create/update`, `routes/custom-host`, and `sparkoperator.k8s.io` and `dataregistry.opendatahub.io` access. The `bind` and ClusterRole CRUD permissions support the aggregated data-registry ClusterRoles and per-CR authz roles. The CronJob runs `kubectl exec deploy/<feast> -- bash -c "<feast apply/materialize>"` with a per-CR Role granting `pods/exec` (`cronjob.go:198-206, 289`). This makes scheduled work depend on exec into the long-running pod.

**Upstream monorepo, partial downstream build.** The checkout is the full upstream Feast monorepo (Go feature server, Java serving, React UI, Python SDK). The Konflux pipelines build only the Go operator and the Python images. The Go feature server (`go/`), Java serving (`java/`), and standalone UI (`ui/`) Dockerfiles are not part of the RHOAI build, so their endpoints (e.g., Go `/get-online-features`) are not RHOAI-shipped surfaces. Python dependencies come from the AIPCC RHAI index through a hash-pinned `requirements-rhai.txt`.

**Index/base version skew.** The Konflux Python images use the `cpu-el9.8:3.6.0` AIPCC base, and `requirements-rhai.txt` is compiled against the `rhoai/3.6/cpu-ubi9` RHAI index, while the build targets RHOAI `3.7.0-ea.1`. This is consistent with an EA branch, but it should be tracked for GA.

**Default images not pinned to downstream.** `config/overlays/rhoai/params.env` still sets `RELATED_IMAGE_FEAST_OPERATOR` and `RELATED_IMAGE_FEATURE_SERVER` to upstream `quay.io/feastdev/*:0.67.0`, and `DefaultImage` in code falls back to upstream. Downstream images are expected to be injected by the RHOAI platform operator or bundle. If they are not, operands would pull community images.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace / per-FeatureStore CR (one Feast project per CR) | `FeatureStore` is Namespaced (`config/crd/bases/feast.dev_featurestores.yaml`) |
| **Deployment model** | Single cluster-wide operator; per-CR operand Deployment in the tenant namespace; one cluster-wide data-registry singleton | `services.go`; `data_registry.go:111-116` |
| **Tenant identifier** | Namespace + Feast project name; Feast `Permission` policies on Kubernetes groups/namespaces/roles or OIDC roles | `kubernetes_token_parser.py`; `api/v1/featurestore_types.go` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-CR SA + Role; Feast authz (TokenReview/OIDC + Feast Permissions); kube-rbac-proxy SAR in data-registry mode | Application (Feast) + Kubernetes | Feast permissions are application-enforced; `noAuth` opt-out; UI server has no auth middleware; shared static intra-communication token in a ConfigMap |
| Data storage | Per-CR PVCs or user-configured backends (DB/S3) | Kubernetes (PVC) / user config | Multiple CRs pointing at the same DB/bucket share data with no tenant column |
| Network traffic | Up to six NetworkPolicies per CR (same-ns, dashboard, workbench, ingress controller, remote registry, monitoring) | Kubernetes NetworkPolicy | Workbench policy admits `opendatahub.io/feast-integration=true` pods from **any** namespace |
| Compute & resources | Per-CR resource requests/limits, HPA, PDB; no ResourceQuota created | Kubernetes | Relies on namespace quotas set elsewhere |
| Configuration & secrets | Per-namespace Secrets/ConfigMaps; secrets inlined into pod env | Kubernetes | Operator reads secrets cluster-wide; anyone with Deployment read sees inlined credentials |
| API scoping | Operator watches cluster-wide; `feast-configs-registry` ConfigMap readable by `system:authenticated` | Kubernetes | Namespace registry discloses FeatureStore names/namespaces to all authenticated users |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Feast operator | Cluster | Per-CR reconciliation; cluster-scoped RBAC |
| Data-registry FeatureStore (singleton, `rhoai-data-registry`) | Kubernetes RBAC on `dataregistry.opendatahub.io` resources | kube-rbac-proxy SAR; aggregated viewer/editor/admin ClusterRoles |
| Namespace registry ConfigMap (`feast-configs-registry`) | None (cluster-readable) | RoleBinding to `system:authenticated` |
