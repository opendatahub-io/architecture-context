## Purpose

**Short**: A Rust REST service that runs AI safety guardrails. It sends LLM inputs and outputs to configured detector, chunker, and generation services, then returns generated text with detection results attached.

**Detailed**: The FMS Guardrails Orchestrator (binary `fms-guardrails-orchestr8`) sits between client applications and large language models. A request names one or more *detectors* by ID, such as HAP, PII, or regex detectors. The orchestrator then runs a task-specific workflow: it chunks the text through caikit chunker gRPC services and fans the chunks out to detector REST services (Detector API `/api/v1/text/{contents,chat,context/doc,generation}`). It calls a generation backend when needed, which is TGIS gRPC, caikit-nlp gRPC, or an OpenAI-compatible HTTP server such as vLLM. Finally it merges the detections into the response. Streaming variants return Server-Sent Events, and a detection batcher keeps per-chunk detections in order across streams.

The service exposes two API generations on its main port (8033). The legacy `/api/v1/task/*classification-with-text-generation` endpoints run input/output detection around TGIS or caikit-nlp generation. The `/api/v2/text/detection/*` endpoints offer standalone detection over content, chat, context documents, or generated text. Two more v2 endpoints, `/api/v2/chat/completions-detection` and `/api/v2/text/completions-detection`, are OpenAI-compatible guardrailed endpoints. They are only registered when an `openai` backend is configured. A separate unauthenticated health server (8034) serves `/health` and `/info`. `/info` reports the health of every configured downstream client.

In RHOAI the orchestrator is part of the TrustyAI guardrails stack. It is the central coordinator for detector runtimes (for example `guardrails-detectors`, `guardrails-regex-detector`, and the HF detector ServingRuntime template in overlay 0014) and for KServe- or vLLM-hosted LLMs. Every downstream service is declared in one YAML file (`ORCHESTRATOR_CONFIG`, default `/app/config/config.yaml`). In practice an operator or user renders this file per deployment. This repository ships only the binary and image. No Kubernetes manifests are included.

## Architectural Analysis

**Config-driven fan-out orchestrator.** The service is stateless and does not talk to the Kubernetes API. Its topology comes entirely from `OrchestratorConfig` (`src/config.rs:210-237`): an optional `generation` backend (TGIS or caikit-nlp, gRPC), an optional `openai` backend (HTTP), named `chunkers` (gRPC), named `detectors` (HTTP, each tied to a chunker and a default threshold), a reusable named `tls` map, `passthrough_headers`, and concurrency limits. At startup, `Orchestrator::new` builds one client per entry. With `START_UP_HEALTH_CHECK=true` it probes all clients and logs any that are unhealthy (`src/orchestrator.rs:60-93`). gRPC clients use a patched fork of `ginepro` (`gkumbhat/ginepro`) for DNS-based client-side load balancing across headless Service endpoints (`src/clients.rs:272-357`). This matters when detectors or generators are scaled horizontally behind a headless Service.

**Dual-listener pattern.** `server::run` starts two axum servers (`src/server.rs:31-97`). The guardrails router on 8033 can use TLS or mTLS. The health router on 8034 is always plain HTTP and has no auth. Both listeners bind `0.0.0.0` (`src/main.rs:41-44`) and shut down gracefully on SIGTERM or Ctrl+C. The TLS path has a 10-second drain timeout (`src/server/tls.rs:131-141`). `/info` can trigger fan-out health calls to every downstream service, so leaving it unauthenticated is a small amplification risk if port 8034 is reachable from outside the pod.

**Auth is delegated, not enforced.** The orchestrator does no authentication or authorization of callers. Its only inbound control is optional mTLS client-certificate verification (`WebPkiClientVerifier`, `src/server/tls.rs:39-53`). Identity reaches downstream services in two ways:
1. An allow-list of request headers (`passthrough_headers`, lower-cased, empty by default) is copied onto downstream requests (`src/server/routes.rs:452-467`).
2. If `rewrite_forwarded_access_header: true`, an `X-Forwarded-Access-Token` header (normally set by an OAuth or kube-auth proxy in front of the pod) is rewritten to `Authorization: Bearer <token>` (`src/server/routes.rs:469-481`).

Separately, each HTTP service can carry a static `api_token`. The config value is the *name of an environment variable*, which is resolved at load time (`src/utils.rs:38-50`) and injected as a Bearer header (`src/clients/http.rs:151-160`). Authorization therefore depends on the platform ingress (Route plus auth proxy) and on the detector and LLM services themselves.

**TLS design and risks.**
- The server side uses rustls with the `ring` provider, installed as the process default (`src/main.rs:30-32`). It sets no explicit protocol versions or cipher suites, so the rustls defaults apply (TLS 1.2 and 1.3; `hyper-rustls` enables `tls12`).
- HTTP clients build a rustls `ClientConfig` per service. When `insecure: true` is set, a custom `NoVerifier` turns off server certificate *and* handshake signature verification, and advertises SHA-1 schemes (`src/utils/tls.rs:42-90, 237-240`).
- If a service has no TLS config, the HTTP connector is still built with the `NoVerifier` config (`src/clients.rs:237-238`). The base URL is `http://` in that case, so the config only takes effect if the downstream redirects or is reached over HTTPS. Still, a certificate-verification bypass is the default in that code path.
- The gRPC client TLS path calls `unwrap()` on both `cert_path` and `key_path` (`src/clients.rs:322-324`). A gRPC backend configured with server-only TLS (CA but no client keypair) panics at startup, so in practice gRPC TLS means mTLS.
- In the gRPC path, `client_ca_cert_path` is used as the CA for verifying the server. In the server path, the CLI flag of the same name means the CA for verifying *clients*. Same name, two meanings.

**Dual crypto providers.** Application TLS (axum server, hyper and tonic clients) runs entirely on rustls plus `ring`, which is not a FIPS-validated module. `reqwest` is pulled in with its default features (`native-tls`) for the OpenTelemetry HTTP exporter. That brings in `openssl`/`openssl-sys` (`Cargo.lock:1323,1354`), so the binary also links the system OpenSSL dynamically for OTLP-over-HTTP. The Konflux build uses the `ubi9/ubi-minimal-pqc` base and OpenSSL RPMs. Even so, the main data-plane TLS does not go through OpenSSL. FIPS posture is therefore **not established**, and the default provider is likely non-FIPS.

**Supply chain.** The Konflux build is hermetic. Tekton sets `hermetic: true` and prefetches `cargo` plus `rpm` via Hermeto (`.tekton/odh-fms-guardrails-orchestrator-pull-request.yaml:38-41`), `rpms.lock.yaml` pins OS packages, and `Cargo.lock` pins crates. `protoc` is compiled from source through the `protobuf-src` build dependency (`build.rs:5`) instead of being downloaded, unlike the non-Konflux `Dockerfile.{amd64,ppc64le,s390x}`, which `curl` protoc from GitHub. Two git-sourced crates are in the dependency graph: `ginepro` (runtime) and `mocktail` (dev only). The Tekton PR pipeline in this branch is still labelled `rhoai-v3-6` / `rhoai-version: 3.6.0`, a stale label carried over from the previous release.

**Observability.** OpenTelemetry traces and metrics can be exported over OTLP gRPC (default `http://localhost:4317`) or HTTP (`:4318`) via `OTLP_EXPORT=traces,metrics` and the standard `OTEL_EXPORTER_OTLP_*` variables (`src/args.rs:50-73`, `src/utils/trace.rs:40-41`). Trace context is propagated on outgoing HTTP and gRPC requests (`src/clients/otel_grpc.rs`, `http_trace_layer`).
