## Purpose

**Short**: Module operator that reconciles the cluster-scoped `Ray` module CR (`components.platform.opendatahub.io/v1alpha1`) and installs, upgrades, reports on, and removes the KubeRay operator (the operand) as part of the ODH/RHOAI modular platform architecture.

**Detailed**: ray-module-operator is the "Ray module" in the ODH/RHOAI modular-platform design (Epic RHOAIENG-62503, Feature RHAISTRAT-1064). The platform operator (rhods-operator/opendatahub-operator) deploys this module operator when the Ray component is enabled. It then creates or projects a singleton `Ray` CR named `default-ray`, with `spec.managementState` and `spec.applicationsNamespace` set. The module operator does not run Ray workloads. It owns the lifecycle of the **KubeRay operator** deployment and its supporting resources in the applications namespace. These include the four `ray.io` CRDs (RayCluster, RayJob, RayService, RayCronJob), the KubeRay ClusterRoles/bindings, the mutating and validating admission webhooks for RayCluster, cert-manager Issuer/Certificate for webhook serving, a NetworkPolicy, and the `run-as-ray-user` SecurityContextConstraints.

The KubeRay operand manifests are vendored into the repository as kustomize snapshots under `opt/manifests/{odh,rhoai}/kuberay`. The Dockerfile copies the distribution-appropriate snapshot into the image at `/opt/manifests/kuberay`. The Konflux build sets `ODH_PLATFORM_TYPE=rhoai`. At reconcile time the operator copies that tree to a writable temp directory. It rewrites `params.env` with `RELATED_IMAGE_*` values injected by the platform, forces the overlay `namespace:` to `applicationsNamespace`, renders with kustomize, and server-side-applies the result with field owner `ray`.

The operator reports module health back to the platform through a standard status contract: `Ready`, `ProvisioningSucceeded`, `DeploymentsAvailable` and `Degraded` conditions, plus `status.releases` and `status.distribution`. `status.releases` advertises the KubeRay version, taken from the image tag or the params.env default. `status.distribution` is read from the per-module ConfigMap `odh-ray-config` in the applications namespace. It also maintains a stable ClusterRole named `ray`, which the Workbenches component binds to Notebook ServiceAccounts so notebooks can submit RayJobs (RHOAIENG-46748).

## Architectural Analysis

**A thin, pipeline-style module operator.** The whole controller is one `reconciler.ReconcilerFor(...)` chain from `odh-platform-utilities/framework` (`internal/controller/ray_controller.go:92-145`). It runs as an ordered list of actions: management state → releases → manifest init → image-param rewrite → kustomize render → cert-manager prerequisite check → OpenShift SCC filter → notebook ClusterRole → SSA deploy (`WithApplyOrder`) → deployment status → distribution → platform release → Degraded → observedGeneration → GC. A separate finalizer action handles deletion. The design deliberately mirrors the in-tree component controllers of the monolithic opendatahub-operator. The same `params.env`/`RELATED_IMAGE_*` substitution pattern and the `platform.opendatahub.io/part-of` GC label are reused. The difference is that it runs as an independently built and shipped image. Most real behavior, including SSA, GC, condition aggregation and dynamic ownership, lives in the shared framework library (`odh-platform-utilities` v0.5.0 / framework v0.3.1). This repository is mostly configuration and lifecycle glue.

**Platform contract surface.** The integration with the platform operator is narrow and explicit:
- (a) The `Ray` CR is cluster-scoped, its name is pinned to `default-ray` by a CEL rule, and `applicationsNamespace` is immutable once set (CEL, `api/v1alpha1/ray_types.go:63-68`).
- (b) Until the platform projects `applicationsNamespace`, the reconciler parks in a PreApply gate with reason `ApplicationsNamespaceNotProjected`. It also drops its own finalizer so the CR cannot get stuck (`ray_controller.go:169-185`).
- (c) The ConfigMap `odh-ray-config` (keys `distribution.name`, `distribution.version`, `platformVersion`) is the handshake channel. It is watched with a name predicate and mapped back to `default-ray` only when it lives in the applications namespace (`configmap.go:20-50`).
- (d) `upgrade()` is an explicit no-op hook that waits for the platform contract to define an upgrade workflow (`status.go:58`). Version transitions are therefore currently "re-apply new manifests" only.

**Image-embedded operand manifests (hermetic, disconnected-friendly).** Operand manifests ship inside the module image, not fetched at runtime. Disconnected installs therefore need no Git access, and image references are resolved only from `RELATED_IMAGE_ODH_KUBERAY_OPERATOR_CONTROLLER_IMAGE` and `RELATED_IMAGE_ODH_KUBE_RBAC_PROXY_IMAGE`. Because the image root filesystem is read-only and runs as an arbitrary UID under restricted SCC, the operator copies the tree to `$TMPDIR/ray-module-manifests` (an `emptyDir` on `/tmp`) before mutating it (`params.go:35-44,111-122`). Two observations:
- The writable copy is created once and reused for the life of the pod (`os.Stat(dst)` short-circuit). A namespace change cannot happen because the field is immutable, but a later reconcile re-applies params on the already-mutated copy.
- The RHOAI snapshot's committed `params.env` still points at `quay.io/opendatahub/kuberay-operator:v1.7.1`. Correct RHOAI images therefore depend entirely on the platform injecting `RELATED_IMAGE_*`.

**ODH and RHOAI snapshots are currently byte-identical.** `hack/manifests-sources.yaml` declares different provenance for the two snapshots: `opendatahub-io/kuberay@dev 49b93bc` for ODH and `red-hat-data-services/kuberay@main 54d25df` for RHOAI. Even so, `diff -rq opt/manifests/odh/kuberay opt/manifests/rhoai/kuberay` reports no differences on this branch. Both overlays default `namespace: opendatahub`. `forceNamespacedResources()` and `setOverlayNamespace()` exist specifically because RHOAI operand YAML may hardcode `redhat-ods-applications` (`render.go:69-71`, `params.go:97-99`).

**Very broad RBAC by design (privilege-escalation mirroring).** The module ServiceAccount holds cluster-wide create/update/delete on RBAC objects, admission webhook configurations, SCCs, Secrets, Pods, Routes, Gateway API, Ingress and NetworkPolicies. It also holds create/update/patch on CRDs. The kubebuilder markers say why (`ray_controller.go:57-63`): Kubernetes RBAC escalation prevention requires the applier to already hold every verb it grants in the KubeRay operand ClusterRoles. In practice, the module operator's effective privilege is a superset of KubeRay's. This makes it one of the more highly privileged components in the platform, even though its own code only touches a handful of resource types.

**Deletion and GC are hardened against stuck finalizers.** The code has several defensive layers:
- A custom `deletionTimestampSetPredicate` makes delete-only updates trigger the finalizer path.
- Owned-only GC runs while `Managed`.
- Full label-based GC plus a direct ownerRef/label sweep (`deleteOwnedOperands`) runs on `Removed` and on CR deletion.
- Cluster-scoped objects such as the `ray` ClusterRole are kept free of controller ownerRefs so `blockOwnerDeletion` cannot pin `default-ray` in Terminating (`notebook_rbac.go:28-34`).

CRDs are intentionally never deleted, so user RayClusters/RayJobs survive a `Removed` transition. CRDs are excluded from the part-of label and from the cluster GC list (`render.go:100-104`, `owned_gc.go:31-35`).

**Optional platform dependencies are checked at runtime, with different outcomes.** When the rendered set contains cert-manager `Issuer`/`Certificate`, the operator fails reconcile with an explicit error if those CRDs are missing (`dependencies.go:21-42`). This makes cert-manager a hard prerequisite for the Ray module on RHOAI. SCC objects are silently filtered out on non-OpenShift clusters after a one-time RESTMapper probe (`platform_filter.go:26-58`). This lets the same image run on Kind in CI.

**TLS posture is centrally governed.** The operator's own metrics server follows the OpenShift cluster `APIServer` TLS profile via `odh-platform-utilities/framework/tls`. The adherence policy controls whether that profile is honored. Otherwise the code falls back to the Intermediate profile (TLS 1.2 + ECDHE AEAD). Loading fails closed on error, and the pod restarts when the profile changes, through a watcher that cancels the manager context (`cmd/main.go:108-191`). HTTP/2 is disabled by default (rapid-reset CVE mitigation). The KubeRay operand is configured separately: HTTPS metrics on 8443 with service-ca certs, webhooks on 9443 with cert-manager certs, and its own `kuberay-tls-profile-role` to read the same APIServer TLS profile.

**Risks / observations:**
- `--leader-elect` is set in the deployment, but `replicas: 1` and `LeaderElectionReleaseOnCancel` is not enabled. Failover therefore waits out the full lease duration.
- The scaffolded `config/network-policy` for the module operator's metrics endpoint is not included in `config/default` (it is commented out), so the module pod has no NetworkPolicy. The operand does get one (RHOAIENG-96339).
- The scaffolded `ServiceMonitor` in `config/prometheus` uses `insecureSkipVerify: true` but is not included in the default/openshift kustomization.
- `distributionAction` silently skips status updates when the ConfigMap carries an invalid semver. It only logs, and no condition is raised.
