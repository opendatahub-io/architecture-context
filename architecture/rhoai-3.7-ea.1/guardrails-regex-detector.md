## Purpose

**Short**: A lightweight Rust/Axum HTTP server that scans text for PII (SSN, credit card, email) or caller-supplied regular expressions and returns match spans, acting as a detector for the FMS Guardrails Orchestrator.

**Detailed**: `guardrails-regex-detector` implements the FMS Guardrails detector "text contents" API (`POST /api/v1/text/contents`). A caller — normally the FMS Guardrails Orchestrator — sends a batch of text strings plus a list of detector parameters. Each parameter is either the name of a built-in pattern (`ssn`, `credit-card`, `email`) or an arbitrary regular expression. The service runs every pattern against every input string and returns one list of detections, each with `start`/`end` offsets, the matched text, a `detection_type` (`pii` or `custom`), a detection label (`EmailAddress`, `SocialSecurity`, `CreditCard`, `custom`) and a fixed `score` of 1.0.

The service keeps no state. It has no persistence, no outbound network calls and no Kubernetes API usage. The repo ships one multi-stage `Dockerfile` that builds a single binary (`/app/bin/regex-detector`) on `rust:1.84.0` and copies it into a UBI 9 minimal runtime image. The repo has no kustomize manifests, CRDs, RBAC or Konflux-specific Dockerfile. Any deployment (Deployment/Service, sidecar to the orchestrator) has to be defined somewhere else.

In the RHOAI 3.7 EA1 workspace, nothing found references this repo's image. `rhods-operator/manifests-config.yaml:461-468` ships `RELATED_IMAGE_ODH_BUILT_IN_DETECTOR_IMAGE` (`quay.io/rhoai/odh-built-in-detector-rhel9`), and `guardrails-detectors/README.md:14` says that image provides regex-based PII detection with custom regexes. This suggests the `guardrails-detectors` built-in detector has replaced or absorbed this standalone Rust detector as the supported regex path in RHOAI. Treat this repo as a lightweight or legacy alternative implementation unless a deployment reference turns up.

## Architectural Analysis

**Design.** The whole component is two source files. `src/main.rs` reads `HTTP_PORT` (default `8080`) and `HOST` (default `0.0.0.0`) from the environment. It builds an Axum `Router` with two routes (`/health`, `/api/v1/text/contents`) plus a `tower_http` `TraceLayer` for INFO-level request/response logging, then serves plain HTTP on a Tokio TCP listener (`src/main.rs:15-46`). `src/detectors.rs` holds the request/response types and the detection logic. The built-in detectors are function pointers in a `HashMap` that is rebuilt on every request. Any unrecognised `detector_params.regex` entry is compiled as a custom regex (`src/detectors.rs:96-137`).

**Analyzer corrections.** The analyzer marked the endpoints as "TLS 1.2+ (optional)" with "Passthrough headers" auth, and listed `/info` and `/api/v2/*` routes plus an optional mTLS service. None of this is in the source. The server binds a plain `tokio::net::TcpListener` with no TLS acceptor. There is no auth middleware and no header forwarding, because the service makes no downstream calls. Only the two routes above are registered. The analyzer's "OpenSSL" signal comes from `compat-openssl11` being installed in the runtime image (`Dockerfile:42`). The binary does not link OpenSSL: `Cargo.lock` has no `openssl`, `rustls` or `ring` crate.

**Risks and observations.**
- **Sensitive data in logs.** `handle_text_contents` logs the whole incoming payload at INFO level (`info!("incoming payload: {:?}", payload)`, `src/detectors.rs:100`). That payload is exactly the text being screened for PII, so SSNs, card numbers and emails end up in container logs. There is also a leftover `println!("hi")` debug statement (`src/detectors.rs:99`).
- **Untrusted regex input.** Callers can submit arbitrary regex patterns. The Rust `regex` crate guarantees linear-time matching, so catastrophic-backtracking ReDoS is not possible. However, regexes are compiled per request (both built-in and custom), and the code sets no request body limit beyond Axum's default, no pattern-size limit and no timeout. Large or many patterns could still use a lot of CPU and memory.
- **Silent errors.** If a built-in detector fails, the error is dropped. An invalid custom regex only produces a `warn!` log, and the response is still 200 with no indication that the pattern was ignored (`src/detectors.rs:118-131`). The only client error returned is `400 empty regex`.
- **Response shape.** Detections for all input strings are flattened into one list and wrapped in a single outer array (`json!([detections])`, `src/detectors.rs:136`). Detections are therefore not grouped per input string, and the caller cannot reliably map a detection back to its source string (offsets are relative to each individual string). This differs from the per-content list-of-lists shape that the orchestrator's contents API normally expects.
- **No transport security.** The server only speaks plain HTTP. Encryption and authentication have to come from the platform, for example by running it as a localhost sidecar of the orchestrator, behind a service mesh, or behind NetworkPolicy.
- **Supply chain.** `Cargo.lock` pins Rust dependencies, but the builder image (`rust:1.84.0`, Debian-based Docker Hub image) and the runtime tag (`ubi9/ubi-minimal:latest`) are mutable references. There is no `rpms.lock.yaml`, Hermeto prefetch or `.konflux` Dockerfile on this branch.
