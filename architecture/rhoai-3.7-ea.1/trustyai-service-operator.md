## Purpose

**Short**: Kubernetes operator that deploys and manages RHOAI's AI trust, safety and evaluation workloads (TrustyAI Service, LM-Eval jobs, EvalHub and NeMo Guardrails) from namespaced custom resources.

**Detailed**: The repository ships one multi-controller operator binary (`/manager`, built from `cmd/main.go`). Startup flag `--enable-services` selects which controllers run. The RHOAI overlay enables `TAS,LMES,NEMO_GUARDRAILS,EVALHUB`, and the Kueue job manager (`JOB_MGR`) is left off. Each controller reconciles its own namespaced CRD into workloads in the user's namespace:
- `TrustyAIService` → TrustyAI explainability/fairness/drift service. It also patches KServe InferenceServices so inference payloads reach TrustyAI.
- `LMEvalJob` → a single evaluation Pod running lm-evaluation-harness/Unitxt, with an injected Go "driver" that reports status.
- `EvalHub` → a multi-tenant evaluation-orchestration REST API, with an optional MCP server, Postgres storage and MLflow integration.
- `NemoGuardrails` → an NVIDIA NeMo Guardrails server.

Every network-facing operand except LMES pods sits behind controller-injected `kube-rbac-proxy` sidecars. Those sidecars terminate TLS with OpenShift service-serving certificates and authorize callers with Kubernetes TokenReview/SubjectAccessReview.

The repository also contains `trustyai-operator-module/`, a separate Go module and image (`odh-trustyai-module-operator-rhel9`). It is the platform-facing "component module" controller for the cluster-scoped `TrustyAI` resource (`components.platform.opendatahub.io/v1alpha1`, singleton `default-trustyai`). When that resource is `Managed`, the module does the following:
- checks prerequisites (a Prometheus instance must exist; KServe is optional);
- does a one-time server-side-apply adoption of resources created by the previous in-tree rhods-operator integration;
- renders the bundled `config/overlays/rhoai` (or `odh` / `mcp-guardrails`) kustomize overlay with `odh-platform-utilities`, and substitutes `RELATED_IMAGE_*` values into `params.env`;
- applies the result, which installs the workload operator itself.

The deployment chain is therefore rhods-operator → `TrustyAI` CR → module controller → trustyai-service-operator Deployment → per-namespace operand CRs.

Three images are built by Konflux from this repo: `quay.io/rhoai/odh-trustyai-service-operator-rhel9` (`Dockerfile.konflux`), `quay.io/rhoai/odh-ta-lmes-driver-rhel9` (`Dockerfile.konflux.driver`) and `quay.io/rhoai/odh-trustyai-module-operator-rhel9` (`trustyai-operator-module/Dockerfile.konflux`). Operand images (TrustyAI service, EvalHub, NeMo Guardrails server, LMES job, kube-rbac-proxy, EvalHub provider images) are built elsewhere. They come in through the `trustyai-service-operator-config` ConfigMap and `RELATED_IMAGE_*` environment variables.

## Architectural Analysis

**Plugin-style controller registry in one binary.** `controllers/controllers.go` registers each service's setup function under a key (`TAS`, `LMES`, `EVALHUB`, `NEMO_GUARDRAILS`, `JOB_MGR`). The kustomize overlay chooses which ones start. Every controller shares one manager, one ServiceAccount (`trustyai-service-operator-controller-manager`) and one config ConfigMap, but RBAC is split into one ClusterRole per component under `config/components/*/rbac`. The operator's effective permissions are the union of the enabled components. That union is broad and cluster-wide: secrets CRUD (TAS, NeMo), `pods/exec` (LMES), ClusterRoleBinding create/update (TAS, EvalHub, NeMo), and `bind` on a fixed list of named EvalHub ClusterRoles. To limit memory, the manager disables the informer cache for ConfigMaps, Secrets, Pods and Services (`cmd/main.go:158-167`), so reads of these types go straight to the API server instead of building cluster-wide caches.

**Two-tier operator (module → operator).** `trustyai-operator-module` is a thin, platform-contract controller with no operand logic. It packages the top-level `config/` tree into the image at `/opt/manifests-template` (`trustyai-operator-module/Dockerfile.konflux:28-30`) and applies it at runtime. Its own ClusterRole (`trustyai-operator-module/config/rbac/role.yaml`) is a superset of everything the workload operator needs, plus CRD CRUD, ClusterRole create and `bind`, and webhook-configuration CRUD. It has to hold that much because Kubernetes RBAC escalation prevention requires the applier to hold every permission it grants. This makes the module the most privileged identity in this component.

**Consistent operand security pattern.** Every HTTP operand (TAS, EvalHub API, EvalHub MCP, NeMo Guardrails with auth enabled) is fronted the same way:
- the application listens on loopback or an internal port;
- `kube-rbac-proxy` exposes 8443/TCP with a `service.beta.openshift.io/serving-cert-secret-name` certificate;
- an OpenShift Route uses `reencrypt` termination with HTTP→HTTPS redirect;
- the operator generates NetworkPolicies for the operand pods.

EvalHub's proxy config is the most elaborate. kube-rbac-proxy rewrites each request into a namespaced SubjectAccessReview against virtual resources (`evaluations`, `collections`, `providers`, `status-events` in `trustyai.opendatahub.io`, and `mlflow.kubeflow.org/experiments`). The namespace comes from the `X-Tenant` header (`controllers/evalhub/configmap.go:339-520`), so tenant authorization reuses Kubernetes RBAC instead of application code.

**Cluster TLS profile propagation.** `pkg/tls` reads `apiservers.config.openshift.io/cluster` at startup. It retries bounded transient errors, refuses to start on permission errors, and falls back to Intermediate on non-OpenShift clusters. It applies the result to the operator's metrics and webhook listeners, and publishes matching `--tls-min-version`, `--tls-cipher-suites` and `--tls-curve-preferences` arguments for every kube-rbac-proxy sidecar it creates. A `ProfileWatcher` cancels the manager when the profile or `tlsAdherence` changes, so the pod restarts and re-reconciles all operands with the new profile (`cmd/main.go:233-246`). The curve list defaults to the PQC hybrid `X25519MLKEM768` and drops plain X25519 in FIPS mode (`pkg/tls/proxy.go:132-186`). Not every operand follows the profile:
- The NeMo Guardrails kube-rbac-proxy ConfigMap template hardcodes TLS 1.2 and a static cipher list (`controllers/nemo_guardrails/templates/kube-rbac-proxy-config.tmpl.yaml`).
- The EvalHub failure-reporter HTTP client pins `MinVersion: TLS 1.2` (`controllers/evalhub/evaluation_job_failure_reconciler.go:1130-1133`).
- The module controller serves metrics on plain HTTP `:8080` with no authn/authz filter (`trustyai-operator-module/cmd/trustyai-operator-module/main.go:36,62`). Its NetworkPolicy only opens 8081, which limits but does not remove this exposure.

**Operator as a data-plane client.** Most operator traffic goes to the Kubernetes API, with two exceptions:
- The LMES controller uses `pods/exec` to run `/opt/app-root/src/bin/driver --get-status` and `--shutdown` inside job pods (`controllers/lmes/lmevaljob_controller.go:368-433`). Job progress is pulled over the exec channel, not over the network.
- The EvalHub failure reconcilers watch Jobs, Pods and Kueue Workloads in tenant namespaces. When an evaluation pod cannot start (unschedulable, init failure, Kueue `Inadmissible`), they POST a `benchmark_status_event` to `https://<evalhub>.<ns>.svc:8443/api/v1/evaluations/jobs/{id}/events`, authenticating with the operator's own ServiceAccount token. The client trusts the OpenShift service CA. The EvalHub NetworkPolicy explicitly allows the operator pod as an ingress peer (`controllers/evalhub/network_policy.go:98-105`).

**KServe coupling (TAS).** The TAS controller watches InferenceServices in its namespace and wires TrustyAI in according to each InferenceService's deployment mode:
- ModelMesh: patches the `MM_PAYLOAD_PROCESSORS` environment variable on ModelMesh Deployments.
- RawDeployment: sets an HTTPS `spec.predictor.logger` URL (`https://<tas>.<ns>.svc/consumer/kserve/v2` via port 4443). If Istio is present, it also creates a DestinationRule (`SIMPLE` TLS on 443) and a VirtualService (rewrites port 80→443).
- Serverless (only when `kServeServerless=enabled`): sets an HTTP logger URL that reaches pod port 8080 directly.

TAS's `internal-tls-proxy` sidecar passes `/consumer/kserve/v2` and the health paths through without authentication (`--ignore-paths`, `controllers/tas/templates/service/deployment.tmpl.yaml:246`). Inference payload ingestion is therefore authorized only by NetworkPolicy peer selection, not by a token.

**Observed risks.**
1. Operator RBAC is cluster-wide (secrets, `pods/exec`, ClusterRoleBindings), so a compromised operator pod can read secrets in every namespace.
2. NeMo Guardrails without the `security.opendatahub.io/enable-auth: "true"` annotation runs with no kube-rbac-proxy. Its Route then uses `edge` termination and plaintext to pod port 8000 (`controllers/nemo_guardrails/nemoguardrail_controller.go:236-246`).
3. The EvalHub metrics port 8081 and the TAS service port 80→8080 are plaintext and unauthenticated inside the cluster.
4. kube-rbac-proxy reads the EvalHub auth config through a `subPath` mount, so rule changes do not reach running pods until they restart (documented in `README.md`).
5. In the RHOAI overlay, LMES online access and code execution are disabled by default (`lmes-allow-online=false`, `lmes-allow-code-execution=false`). The upstream base allows both.
