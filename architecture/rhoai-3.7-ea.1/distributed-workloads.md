## Purpose

**Short**: Builds the RHOAI universal training images (CPU / CUDA / ROCm) and Ray runtime images, and hosts the Go E2E test suite that validates Kubeflow Training Operator v1, Kubeflow Trainer v2, KubeRay and Kueue on RHOAI.

**Detailed**: `distributed-workloads` does not deploy a long-running platform service. It has two jobs. First, it is the source of the **universal training images** (`odh-th-torch-{cpu,cuda,rocm}-py312-rhel9`). Each image works as a Jupyter workbench image and as a headless runtime image for Kubeflow Trainer `ClusterTrainingRuntime`s (see overlay 0013). The images bundle Training Hub, the Kubeflow SDK, InstructLab Training, the RHAI mini-trainer, PEFT/TRL/Transformers, DeepSpeed, Flash-Attention and (CUDA only) vLLM on top of the RHOAI Jupyter minimal workbench images. The repo also builds Ray runtime images (`quay.io/modh/ray:*`) and a test-runner image.

Second, it holds the platform's **distributed-workloads E2E test suite** (`tests/`). The suite is written in Go with gomega and covers the `kfto` (PyTorchJob), `trainer` (TrainJob/JobSet/MPI), `odh` (RayCluster/RayJob) and `fms` (fms-hf-tuning) suites. Each test creates a namespace, builds Kueue queues, RBAC and workloads, and checks status through the Kubernetes, Kubeflow, KubeRay, Kueue, JobSet, OpenShift and OLM clients.

The repo also ships example notebooks and manifests (`examples/`): Ray Tune HPO, Stable Diffusion DreamBooth, KFTO SFT and Feast/RAG. It also has MPI benchmarks (`benchmarks/`) and workshops. Those examples bring their own sample MinIO, NFS and KServe manifests. They are user-applied demo content, not platform deployments.

## Architectural Analysis

**Build repository, not a runtime component.** Every Service, Route, Secret, Deployment and ServingRuntime the analyzer found comes from `examples/` or `workshops/`. They include MinIO with a hardcoded `minio/minio` credential, an NFS server with an `anyuid`/`privileged` SCC, and a TorchServe ServingRuntime. None is installed by the RHOAI operator, so this document treats them as demo artifacts and does not count them as platform network surface. What reaches customers is the set of container images from the hermetic Konflux pipelines in `.tekton/`. The platform consumes them through the `trainer` component's ClusterTrainingRuntime manifests and the notebooks ImageStreams.

**Dual-purpose image via entrypoint switching.** `entrypoint-universal.sh` starts Jupyter only when `NOTEBOOK_ARGS` is set, which the workbench controller does. In any other case it runs the supplied command. The Trainer SDK overrides the container command, so the entrypoint never runs on training pods. The CUDA and CPU images also turn `mpirun` and `mpiexec` into symlinks to `openshift-uid-exec.sh`. That wrapper adds the random OpenShift UID to `/etc/passwd`, which is group-writable on purpose (`chmod g=u /etc/passwd`). It waits up to 60 s for the TrainJob hostfile names to resolve in DNS and caps `ulimit -n` before handing off to OpenMPI. The images also install `openssh-server` with a user-level sshd config: port 2222, pubkey-only, no root login, no forwarding. This is how OpenMPI launcher-to-worker SSH works under the restricted SCC.

**Variant asymmetry.** The ROCm image has no `openssh-server` install, no MPI wrapper and no `rpms.lock.yaml`/RPM prefetch. It also removes `uv` from the final image, while the CUDA image keeps it for `openpipe-art`. So MPI-based TrainJobs (`benchmarks/osu-benchmarks`, `kftv2-mpi-ddp-sft`) are only supported on the CUDA and CPU images.

**Version label drift.** All three Konflux Dockerfiles label the image "PyTorch 2.11.0", and the CUDA header comment says the same. The lockfiles pin `torch==2.13.0` (CPU/CUDA) and `torch==2.12.0` (ROCm). Overlay 0013 lists the image names as `*-torch210-*` / `*-torch291-*`, so the overlay naming is stale too. The `pyproject.toml`/`requirements.txt` index URLs point at the **RHOAI 3.6** AIPCC index (`console.redhat.com/api/pypi/public-rhai/rhoai/3.6/...`) on a 3.7 branch.

**CI pipeline hygiene risks.** The push pipeline `ray-2.58.0-py312-cu130-th0112-push.yaml` builds from `images/runtime/ray/cuda/2.58.0-py312-cu129-th081` and tags `...cu129-th081`, but only `2.58.0-py312-cu130-th0112` exists in the tree. Both `odh-training-*-openmpi41` pull-request pipelines point at `images/runtime/training/py312-cuda130-torch210-openmpi41`, which does not exist. The ROCm one also points at the CUDA path. All three pipelines would fail or are stale.

**FIPS posture.** The images are "FIPS-friendly by construction" rather than FIPS-validated. They use a multi-stage build so build tools stay out of the final image, and they inherit OpenSSL from the RHEL9 workbench base. They delete TensorBoard's Rust `tensorboard_data_server` binary because its bundled crypto is not FIPS compliant, then smoke-test the pure-Python fallback during the build. They also drop `uv` from the CPU and ROCm runtime images. Many Python wheels with native crypto ship in the image anyway: `cryptography`, `pyOpenSSL`, `blake3`, `grpcio` (BoringSSL) and `sigstore`. Their FIPS behaviour depends on whether they link system OpenSSL, and this repo does not verify that.

**Test suite trust shortcuts.** Several E2E clients disable TLS verification (`InsecureSkipVerify: true`) for the Ray dashboard, S3 storage and Trainer metrics endpoints. This is acceptable for test code, but it is not a pattern for product code.

## AIPCC Ecosystems Use

The three Konflux Dockerfiles install Python packages with `pip`/`uv`. They do **not** reference `quay.io/aipcc/base-images/*` or the `rhaipcc` tooling directly. Their `BASE_IMAGE` is the RHOAI Jupyter minimal workbench image. Per overlay 0013, that workbench image is itself layered on an AIPCC base image. The dependency on AIPCC is therefore **indirect through the notebooks image** plus **direct through the AIPCC PyPI index**: the lockfiles are compiled against `console.redhat.com/api/pypi/public-rhai/rhoai/3.6/<variant>/simple/` with the comment "Strict AIPCC-only: all packages must be available in AIPCC index". The Dockerfile comments say "AIPCC base image has everything pre-configured" when `DOWNSTREAM=true`. The Ray runtime images use `registry.access.redhat.com/ubi9/python-312` and do **not** use AIPCC bases or the AIPCC index. That is a gap to track against product security build requirements.
