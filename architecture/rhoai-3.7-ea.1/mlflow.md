## Purpose

**Short**: Multi-tenant MLflow tracking server, model/prompt registry and web UI for RHOAI. It maps Kubernetes namespaces to MLflow workspaces and checks every request against Kubernetes RBAC.

**Detailed**: This repository is the Red Hat downstream of upstream MLflow (via `opendatahub-io/mlflow`). It produces one Konflux container image, `quay.io/rhoai/odh-mlflow-rhel9`, which contains the MLflow Python packages (`mlflow-tracing`, `mlflow-skinny`, `mlflow`) and the compiled React UI. The UI is built twice: once standalone and once as a module-federated bundle with `MLFLOW_API_BASE_URL=/mlflow` so the ODH Dashboard can embed it. The image starts `mlflow server` on port 5000 with the `kubernetes-auth` application plugin, workspaces enabled, the `kubernetes://` workspace store and server-side artifact proxying (`--serve-artifacts`).

In RHOAI the MLflow Operator deploys MLflow as one shared tracking service. The operator reconciles a cluster-scoped `MLflow` CR and renders a Helm chart from the operator repository. It sets the backend, registry and artifact store URIs and the TLS options. Users and SDK clients reach the service through the data science gateway at `/mlflow`. Each data science project namespace appears as an MLflow workspace. The `kubernetes-auth` plugin checks each request with a `SelfSubjectAccessReview` against pseudo-resources in the `mlflow.kubeflow.org` group, using the caller's own token. An optional namespace-scoped `MLflowConfig` resource can override artifact storage for one workspace. Both plugins come from the external `mlflow-kubernetes-plugins` package (kubeflow/mlflow-integration), pinned at 2.1.1. They are not in this repository.

The downstream fork also carries RHOAI-specific changes:
- feature guards that turn off the AI Gateway, the MLflow Assistant, server-side job execution and telemetry in the image
- a `mlflow db fix-migration-gap` command that repairs databases upgraded from RHOAI 3.3 to 3.4
- prompt model filtering, PatternFly UI styling, embedded-dashboard routing and session-expiry handling
- downstream CI and Konflux scaffolding

## Architectural Analysis

**Runtime shape.** By default `mlflow server` starts uvicorn with 4 workers (`mlflow/server/__init__.py`, `_build_uvicorn_command(..., workers or 4, ...)`). Uvicorn serves a FastAPI app (`mlflow/server/fastapi_app.py:384-434`). Native FastAPI routers handle OTLP ingest, jobs, the gateway, the assistant (only when enabled), streaming artifact upload/download, MCP-server and Skills Registry APIs, and server-info. The legacy Flask app, which holds the core REST API `/api/2.0/mlflow/*`, `/ajax-api/*`, GraphQL, the UI static assets and `/health`, is mounted at `/` through a WSGI adapter. Because the routers are registered first, FastAPI routes take precedence. OpenAPI/docs are disabled on purpose (`docs_url=None`). When `--app-name kubernetes-auth` is given, the plugin's app factory, loaded from the `mlflow.app` entry point, wraps this application and adds authorization. The Dockerfile loads that entry point and the `mlflow.workspace_provider/kubernetes` entry point at build time (`Dockerfile.konflux:77-81`), so a broken plugin fails the build instead of the running pod.

**Tenancy is delegated to Kubernetes.** MLflow does not create workspaces. The workspace provider treats namespaces as the source of truth and resolves the active workspace from the `X-MLFLOW-WORKSPACE` header (`mlflow/utils/workspace_utils.py:9`, `mlflow/server/workspace_helpers.py:30`). Authorization is a per-request SSAR with the caller's bearer token. This means MLflow needs no separate permission database, and access follows the platform's normal RoleBindings. One cost is that every API call depends on the Kubernetes API server, unless the plugin caches results. The plugin is not in this repo, so its caching behavior is unknown. A second point: all tenants share one metadata database and, by default, one artifact root. Isolation therefore depends entirely on the application filtering every query by workspace. A bug in workspace scoping, in upstream MLflow or in the plugin, would expose data across tenants.

**Feature surface reduced by environment flags.** The upstream server now includes an LLM AI Gateway, a "MLflow Assistant" that can run tools, a Huey-based job runner and telemetry. The RHOAI image turns these off with `MLFLOW_ENABLE_AI_GATEWAY=false`, `MLFLOW_ENABLE_ASSISTANT=false`, `MLFLOW_SERVER_ENABLE_JOB_EXECUTION=false` and `MLFLOW_DISABLE_TELEMETRY=true`, and blanks `MLFLOW_MODEL_CATALOG_URI` (`Dockerfile.konflux:39-45`). The guards are enforced in code: the assistant router is only included when its flag is set (`fastapi_app.py:417`), and the gateway routes return errors when disabled (`gateway_api.py:110`, `handlers.py:1471`). The code for these features, including LLM provider clients for OpenAI, Anthropic, Bedrock, Gemini and others, is still installed. A deployment that sets these variables to true can turn it back on. Many of the analyzer's HTTP endpoints and secret env vars belong to these disabled features or to separate processes not started by the image CMD: the standalone gateway (`mlflow/gateway/app.py`), the pyfunc scoring server and the GenAI agent server.

**Security posture notes.**
- The image enables the upstream host-validation and CORS middleware (`mlflow/server/fastapi_security.py`). The operator has to set `--allowed-hosts` correctly for the gateway hostname.
- `mlflow/utils/crypto.py:30` has a hardcoded `DEFAULT_KEK_PASSPHRASE` that is used whenever `MLFLOW_CRYPTO_KEK_PASSPHRASE` is unset. It protects the gateway secrets store, which uses AES-GCM envelope encryption with PBKDF2-HMAC-SHA256. That store is idle while the AI Gateway is off, but it becomes a risk if the gateway is enabled.
- Model-registry webhook secrets use Fernet with a key from `MLFLOW_WEBHOOK_SECRET_ENCRYPTION_KEY`. If that variable is unset, a random key is generated per process (`mlflow/store/model_registry/dbmodels/models.py:300`), so stored secrets can no longer be decrypted after a restart and differ across workers.
- The TLS server certificate is supplied by the operator through uvicorn options. This repo has no TLS configuration of its own.

**Supply chain.** The build is hermetic (`hermetic: 'true'`). Cachi2/Hermeto prefetches pip packages from two sources: hash-locked `konflux-aipcc-requirements.txt` files from the Red Hat AI PyPI index, plus a 4-package PyPI side channel (`mlflow-kubernetes-plugins`, `psycopg2`, `prometheus-flask-exporter`, `starlette==1.3.1` for CVE-2026-54283). Yarn packages and RPMs (`requirements/rpms.lock.yaml`) are prefetched too. The build targets amd64, arm64, ppc64le and s390x. Two things stand out:
1. The runtime base is `ubi9/ubi-minimal-pqc`, not an AIPCC base image. Python 3.12 is installed from RPMs.
2. The AIPCC index URL in the lock files is `.../rhoai/3.6/cpu-ubi9/simple`, although this branch is 3.7-ea.1. The lock was probably not refreshed for the release.

**Release-coupled risk.** The `kubernetes-auth` app and workspace store come from an external package whose versions must match MLflow's server internals. FORK_HISTORY records a Skills Registry authorization failure that was fixed only by bumping the plugin. Any upstream rebase that adds routes needs the plugin's route-authorization audit, which covers 66 registry and 147 native route/method pairs, to be re-run. Otherwise new endpoints could be left without authorization.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SSAR with caller token on `mlflow.kubeflow.org` pseudo-resources | Application (`kubernetes-auth` plugin) + Kubernetes RBAC | Plugin is external; new upstream routes need explicit authorization mapping |
| Data storage | Shared DB with workspace column/filtering; default shared artifact root with per-workspace prefix; optional `MLflowConfig` artifact override | Application | No DB-level isolation; a workspace-scoping bug crosses tenants |
| Network traffic | None at tenant level (single shared service) | Platform gateway | NetworkPolicy, if any, is operator-owned |
| Compute & resources | Shared pods/workers | None | Noisy-neighbor risk; no per-tenant quotas or rate limits in the image |
| Configuration & secrets | Shared server config; per-namespace `MLflowConfig` | Kubernetes + application | Shared artifact-store credentials unless overridden |
| API scoping | Workspace-filtered queries; workspace list filtered by RBAC | Application | — |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL backend/registry store | workspace (row-level) | Application query filtering |
| Artifact object store | workspace path prefix / `MLflowConfig` override | Application artifact-root resolution |
| MLflow server process | request context | Per-request workspace resolution + SSAR |
