## Purpose

**Short**: A Python REST service built on FastAPI and Hypercorn. It receives KServe/ModelMesh inference payloads, stores them, and computes model drift and fairness metrics. It publishes those metrics to Prometheus on a schedule.

**Detailed**: The TrustyAI Service is the runtime backend for Responsible AI monitoring in RHOAI. It runs one instance per namespace. Model-serving inference loggers send it request and response payloads: KServe CloudEvents arrive at `/`, and ModelMesh flat payloads arrive at `/consumer/kserve/v2`. The service matches each request with its response (by inference id) and persists the joined rows. Storage is pluggable: HDF5 on a PVC, MariaDB, PostgreSQL, or SQLite. Users and the dashboard register recurring metric requests through the REST API:
- fairness: Statistical Parity Difference and Disparate Impact Ratio
- drift: Compare Means (t-test), KS test, streaming KS, Jensen–Shannon, and MMD
- batch mean

A background task recomputes every registered metric each `SERVICE_METRICS_SCHEDULE` interval (default 30s) and exposes the results as Prometheus gauges on `/q/metrics`.

This repository is the Python rewrite of the original Java/Quarkus TrustyAI service. It keeps the Quarkus-era API: `/q/health`, `/q/metrics`, and `QUARKUS_DATASOURCE_*` environment variables. It also keeps deprecated route aliases: `/dir`, `/spd`, `/metrics/identity`, `/metrics/drift/meanshift`, `/metrics/drift/fouriermmd`, and `/metrics/drift/approxkstest`. A `trustyai-migrate` console script moves data from the legacy Java formats (PVC HDF5/CSV, Java-serialized MariaDB rows) into the new canonical SQL schema.

Explainer endpoints (LIME, SHAP, counterfactual, TSSaliency, PDP) exist in the API but are off by default. When enabled, they return HTTP 501 Not Implemented, so they are placeholders only.

## Architectural Analysis

**One process, three listeners, split trust model.** `main.py` runs two Hypercorn servers in a single asyncio loop (`asyncio.gather`):
1. **Main app, plain HTTP on `127.0.0.1:8081`.** Bound to loopback only, so the pod's kube-rbac-proxy sidecar is the intended authenticated entry point.
2. **Main app, HTTPS on `0.0.0.0:4443`.** Only bound when serving certificates are mounted at `/etc/tls/internal/tls.{crt,key}`.
3. **Second FastAPI app `health_app`, plain HTTP on `0.0.0.0:8080`.** Serves health probes and also the two KServe/ModelMesh consumer POST routes.

The application has no authentication middleware. Its only middleware is wildcard CORS with `allow_credentials=True`, gzip request decompression, and trailing-slash stripping. All authentication is therefore external, which means:
- The data-ingest routes on 8080 accept unauthenticated plaintext writes from anything that can reach the pod port.
- Direct HTTPS on 4443 likewise has no auth unless the deployer adds network controls.

The deployer (the TrustyAI operator) must use NetworkPolicy to limit who can reach 8080 and 4443. `docs/server-tls.md` says this explicitly ("Network exposure and plaintext exceptions must be evaluated by the deployer").

**TLS is policy-aware but stays inside Python's limits.** `service/tls.py`:
- Wraps Hypercorn's `Config` (`PolicyAwareConfig`).
- Supports `TLS_POLICY=system`, which defers to the OS/OpenSSL crypto policy.
- Supports `TLS_POLICY=configured`, which sets an explicit min version (TLSv1.2/1.3), exact OpenSSL cipher names for TLS 1.2, and a single ECDH curve.

Invalid or unrepresentable settings stop the service at startup instead of being silently weakened. Python cannot configure TLS 1.3 suites or a list of multiple key-exchange groups. For cluster TLS profiles that need those, the docs recommend fronting the service with a capable terminator and removing the direct 4443 listener.

**Storage abstraction and a DB-TLS gap.** `GlobalStorageInterface` is a process-wide singleton chosen by `SERVICE_STORAGE_FORMAT` (`PVC` | `DATABASE` | `MARIA` | `POSTGRESQL` | `SQLITE`). For `DATABASE`, the database kind comes from `QUARKUS_DATASOURCE_DB_KIND`. Database TLS uses a CA mounted at `/etc/tls/db/ca.crt`:
- PostgreSQL uses `sslmode=verify-full`.
- MariaDB uses `ssl_verify_cert=True`.

However, `DATABASE_ALLOW_INSECURE_TLS` is treated as **true when unset**. If no CA is mounted and `DATABASE_TLS_CA_CERT` is not explicitly set, the connection is made without certificate verification. A configured-but-missing CA does fail closed. Treat this default as a security risk.

**Hermetic AIPCC build.** The Konflux image:
- Uses the AIPCC `cpu-torch2.13-el9.8` base.
- Installs strictly from a hash-locked `.konflux/requirements.txt` resolved against the RHEL AI PyPI channel.
- Swaps `psycopg[binary]` for `psycopg[c]`, because the AIPCC index ships no binary wheel; it links against the base image's `libpq`.
- Removes the inherited `uv` binary to drop its bundled crypto (RHOAIENG-97373).

The pip index used is the `-test` channel (`.../cpu-torch2.13-el9.8-test/simple/`). This matches the overlay 0017 channel convention but is worth tracking for GA.

**Other observations:**
- Feature flags (`TRUSTYAI_ENABLE_*`) are read once at import time. Routes they disable are never registered, so they return 404 rather than a policy error.
- Both servers advertise HTTP/2 through ALPN (`h2`, `http/1.1`).
- The ingest path's `GzipRequestMiddleware` caps decompressed size at 16 MB (zip-bomb guard). Hypercorn `h11_max_incomplete_size` is also 16 MB.
- Legacy `.proto` (KServe gRPC predict v2) bindings are present only for payload parsing. No gRPC server is started.
