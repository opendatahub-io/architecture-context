## Purpose

**Short**: KServe is the RHOAI model-serving control plane. It reconciles `InferenceService`, `LLMInferenceService`, `InferenceGraph` and model/kernel-cache CRs into scalable inference workloads. A `kserve-module` operator installs and configures the whole serving stack from a single `Kserve` platform CR.

**Detailed**: In RHOAI 3.7-ea.1 this repository produces nine Konflux images. Four are Go controller-runtime managers: `kserve-module-controller`, `kserve-controller` (`cmd/manager`), `llmisvc-controller` (`cmd/llmisvc`) and `localmodel-controller` (`cmd/localmodel`). The rest are a node DaemonSet agent (`localmodelnode-agent`), two data-plane binaries injected into model pods (`agent` and `router`), the Python `storage-initializer` init container, and one Python model-server runtime (`autogluonserver`). The predictive `InferenceService` path (v1beta1) supports RawDeployment/Standard mode, plus Knative/Serverless where installed. Its networking runs through Gateway API `HTTPRoute`, Kubernetes `Ingress`, OpenShift `Route` or Istio `VirtualService`, and autoscaling uses HPA or KEDA. The generative-AI path (`LLMInferenceService` v1alpha1/v1alpha2) integrates llm-d. It creates Deployments or LeaderWorkerSets, `InferencePool`/`InferenceObjective`, Gateway API routes, an EPP scheduler, prefill/decode disaggregation (`DisaggregatedSet`) and per-service NetworkPolicies, Roles and ServiceAccounts.

The biggest architectural change on this branch is the `kserve-module` sub-project (`kserve-module/`). It reconciles the cluster-scoped singleton `components.platform.opendatahub.io/v1alpha1 Kserve` (name pinned to `default-kserve`) and implements the `odh-platform-utilities` `PlatformObject` contract, so the RHOAI operator can delegate the whole serving stack to it. Manifests are baked into its image at build time: `config/` goes to `/opt/manifests-template/kserve/`, and `kserve-module/prefetched-manifests-rhoai/{modelcontroller,modelexpress,wva}` go to `/opt/manifests-template/`. At runtime the module renders kustomize overlays and server-side-applies them. The rendered components are KServe, odh-model-controller, Workload Variant Autoscaler (Removed by default), ModelExpress (Removed by default), the model cache (LocalModel), LLMISVC Perses dashboards and OpenShift console dashboards. The module also manages cert-manager resources, versioned `LLMInferenceServiceConfig` presets (overlay 0022), hardware-aware accelerator presets driven by node allocatable and DRA `ResourceSlice`s, NIM `Account` CRs, OCSF audit `TelemetryPolicy` (Kuadrant), and `ClusterServingRuntime`s for vLLM (CUDA/ROCm/Gaudi/Spyre/CPU/Omni), OVMS and MLServer.

The branch also carries newer node-local caching subsystems. **LocalModel** (`LocalModelCache`, `LocalModelNamespaceCache`, `LocalModelNode`, `LocalModelNodeGroup`) pre-downloads model artifacts to node PVs/PVCs through Jobs run by a node agent. **KernelCache** (`KernelCache`, `KernelCacheCapture`, `KernelCacheNode`, `KernelCacheNodeGroup`) captures and distributes compiled GPU kernel caches as OCI artifacts. Its source code and RBAC are present, but no Konflux Dockerfile builds `kernelcachenode` or `kernelcache-agent` on this branch. Confidential model serving is also present: a `kserve-decrypt` CLI inside the storage initializer decrypts JWE-encrypted models with keys fetched from the CoCo Confidential Data Hub, and a privileged SCC covers the bare-metal LUKS disk-formatting path.

## Architectural Analysis

**Module-operator pattern (new control-plane layer).** `kserve-module` turns KServe from "manifests that the RHOAI operator applies" into "an operator that applies its own manifests". The upside is that serving owns its configuration surface. `Kserve.spec` exposes raw-service headless/headed mode, OAuth proxy resources, confidential containers defaults, NIM air-gap, WVA, ModelExpress, LLMISVC TLS, console dashboards, an opt-in monitoring NetworkPolicy, hardware-aware presets, audit logging profile, model cache and model registry. Upgrades handle differential versioning and `LLMInferenceServiceConfig` cleanup inside serving code (`differential_versioning.go`, `upgrade.go`, `llmisvcconfig_cleanup.go`). The cost is a large blast radius in one ServiceAccount. `kserve-module-manager-role` has 47 rules, including `bind`/`escalate` on ClusterRoles/Roles, full CRUD on `securitycontextconstraints`, `mutating/validatingwebhookconfigurations`, `customresourcedefinitions` (including delete), namespaces, DaemonSets and cluster RBAC. In practice this ServiceAccount is cluster-admin-equivalent, so a compromise of the module pod is a cluster compromise. Secret access is partly constrained by `resourceNames` (webhook secret plus WVA tokens), but create/delete/patch on Secrets is still granted. Because manifests ship inside the image (`/opt/manifests-template`), operator image and runtime manifests always move together. Changing a runtime image or preset requires a module image rebuild, which removes the drift risk of `make get-manifests`.

**Two serving control planes in one repo.** `kserve-controller` (InferenceService/InferenceGraph/TrainedModel/ServingRuntime) and `llmisvc-controller` (LLMInferenceService/Config) are separate Deployments, each with its own webhook Service. The ODH overlay applies `llmisvcconfig/` last on purpose. During 3.3→3.4-style upgrades the cluster can briefly run a stale ValidatingWebhookConfiguration against the split controllers, which would block DSC readiness (`config/overlays/odh/kustomization.yaml` comment). Every admission webhook uses `failurePolicy: Fail`, including the pod mutators on `pods` CREATE. If the KServe webhook server is unavailable, pod creation for labelled inference pods fails cluster-wide. This availability coupling deserves the attention of HA and upgrade designs.

**TLS posture is centrally derived from the cluster.** `pkg/tls/distro` reads `apiservers.config.openshift.io/cluster` `TLSSecurityProfile` and `TLSAdherence`. Explicit flags win; otherwise the code falls back to Intermediate, with a hardened TLS 1.2 floor on non-OpenShift clusters. It then applies the resolved profile to controller webhook and metrics servers. Through `InjectPythonTLSProfile` it also pushes the profile into HTTPS-serving Python model containers (`KSERVE_TLS_PROFILE_PROVIDER=openshift`, `KSERVE_TLS_MIN_VERSION`, OpenSSL cipher names), and it filters curve IDs for FIPS approval (`CurveIDsFromNames(..., fipsMode)`). This is a strong pattern, because cluster-wide TLS policy changes propagate into inference workloads. `ProfileWatcher` reconciles on APIServer changes.

**Data-plane injection is webhook-driven.** The `/mutate-pods` handler builds a fixed chain: GKE accelerator selector → storage-initializer init container → Istio CNI security context → agent (logger/batcher/model-puller) → metrics aggregator, with an OCI model mutator for modelcar/OCI sources (`pkg/webhook/admission/pod/mutator.go:137-150`). The ODH build adds OVMS auto-versioning and OpenShift config hooks (`*_odh.go`). The KernelCache mutator only acts on pods labelled as InferenceService pods with `KernelCacheSupportedAnnotationKey=true`.

**Auth is mostly delegated.** Inference endpoints carry no built-in auth. Model servers are FastAPI/Starlette or gRPC with no auth middleware, so auth comes from Gateway or Kuadrant policies created by odh-model-controller or from kube-rbac-proxy sidecars. The exception is the InferenceGraph router, which does its own Bearer-token TokenReview followed by a SubjectAccessReview for `get inferencegraphs/<name>` in the pod's namespace (`cmd/router/main.go:505-600`).

**Risks and observations.**
- The ODH NetworkPolicies for `kserve-controller-manager` and `llmisvc-controller-manager` are `ingress: [{}]` (allow-all). They exist only so the controllers stay reachable under namespace default-deny; they do not restrict anything. Per-LLMISVC restrictive ingress policies are opt-in (`EnableLLMMonitoringIngressNetworkPolicy`, default false).
- `InsecureSkipVerify` is reachable on two opt-in paths: logger sink TLS (`logReq.TlsSkipVerify`, `pkg/logger/worker.go:120`) and the kernel-cache registry `registry.insecure` option (`pkg/kernelcache/registry/transport.go:39`).
- The confidential bare-metal path grants `allowPrivilegedContainer: true` with RunAsAny to SA `coco-cc-storage` (`config/overlays/odh/confidential/scc.yaml`).
- The source still contains WVA wiring (`WVASpec`, `wva.go`, WVA token secrets in module RBAC). Overlays 0028 and 0029 say WVA is removed from the `rhoai.next` serving path, and `Kserve.spec.wva.managementState` defaults to `Removed`, so do not treat WVA as active.
- The storage-initializer builder stage uses an unpinned `ubi9/ubi-minimal:latest`; its final stage is digest-pinned.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace (data science project); InferenceService / LLMInferenceService / InferenceGraph / ServingRuntime / LocalModelNamespaceCache are Namespaced | CRD scopes (`pkg/apis/serving/*`) |
| **Deployment model** | Single shared control plane (cluster-wide controllers and webhooks in the applications namespace) serving all tenant namespaces; per-CR data-plane workloads in tenant namespaces | `config/overlays/odh/kustomization.yaml` (namespace `opendatahub`, cluster-scoped bindings) |
| **Tenant identifier** | Namespace name | inferred from CRD scope and controller ownership |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC on namespaced CRs; per-LLMISVC ServiceAccounts/Roles/RoleBindings; router SAR scoped to namespace | Kubernetes / Application (router) | Model endpoints have no app-level auth; isolation depends on Gateway/Kuadrant policies from odh-model-controller |
| Data storage | Per-namespace PVCs and storage secrets; LocalModelCache is cluster-scoped and shared across namespaces, LocalModelNamespaceCache is namespace-scoped | Kubernetes | Cluster-wide model cache PVs are shared; namespace caches mitigate |
| Network traffic | Per-LLMISVC NetworkPolicies (opt-in restrictive monitoring/gateway policy); controller NetworkPolicies are allow-all | Kubernetes | Default-allow for ISVC workloads; restrictive LLMISVC policy disabled by default |
| Compute & resources | Pod resources from runtime/ISVC spec; HardwareProfile, DRA ResourceClaims, accelerator selectors | Kubernetes | No ResourceQuota created by KServe |
| Configuration & secrets | `inferenceservice-config` and `LLMInferenceServiceConfig` presets are global (system namespace); user secrets per-namespace | Kubernetes / Application | Global config shared across tenants; `ClusterServingRuntime`/`ClusterStorageContainer` are cluster-wide |
| API scoping | Controllers use cluster-wide watches; webhooks intercept all matching pods cluster-wide | Kubernetes / Application | Controller SAs hold cluster-wide Secret/ServiceAccount/RBAC permissions |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| kserve / llmisvc controllers + webhooks | namespace | Kubernetes RBAC on CRs; `failurePolicy: Fail` |
| Platform Gateway (data-science / inference gateway) | HTTPRoute per namespace | Gateway API + Kuadrant/Authorino (external to repo) |
| LocalModelCache node storage | cluster | Shared PVs per node group; namespace cache variant available |
| Global LLMInferenceServiceConfig presets | cluster (system namespace) | Read-only references via `spec.baseRefs` |
