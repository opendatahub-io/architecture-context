## Purpose

**Short**: KubeRay operator that manages the lifecycle of Ray clusters, Ray jobs, Ray Serve services and scheduled Ray jobs on OpenShift. In RHOAI it also adds Gateway API dashboard routing, kube-rbac-proxy authentication, cert-manager mTLS and per-cluster NetworkPolicies.

**Detailed**: This repository is the Red Hat downstream fork of KubeRay. RHOAI ships one artifact from it: the `ray-operator` controller manager (`/manager`). Konflux builds it from `ray-operator/Dockerfile.konflux` as `quay.io/rhoai/odh-kuberay-operator-controller-rhel9`. The operator reconciles four `ray.io` custom resources: `RayCluster`, `RayJob`, `RayService` and `RayCronJob`. A `RayCluster` becomes a head pod, worker pods, Services, optional autoscaler RBAC and optional batch-scheduler PodGroups. A `RayJob` creates a RayCluster and then submits a Ray job, either through a Kubernetes `batch/v1` Job submitter pod or through the Ray dashboard HTTP API. A `RayService` runs Ray Serve applications, with zero-downtime cluster upgrades and optional Gateway/HTTPRoute-based incremental upgrades. A `RayCronJob` (alpha feature gate) creates RayJobs on a cron schedule.

The fork carries a substantial OpenShift/RHOAI security layer that is not in upstream:
- **Default security on OpenShift.** A mutating admission webhook (`mraycluster.kb.io`) marks every RayCluster as a "secure trusted network" (`odh.ray.io/secure-trusted-network: "true"`), enables mTLS (`spec.tlsOptions.enabled`), injects a platform NetworkPolicy profile, and forces `enableIngress: false`. Plain Routes and Ingresses are therefore never used for dashboard access.
- **AuthenticationController.** Injects a `kube-rbac-proxy` sidecar (8443/TCP) into Ray head pods, with a SubjectAccessReview config (`get services/<cluster>-head-svc`). It also creates a cross-namespace `HTTPRoute` in the platform namespace that attaches to the shared `data-science-gateway` in `openshift-ingress`, plus a `ReferenceGrant` in the user namespace.
- **RayClusterMTLSController.** Builds a per-cluster cert-manager PKI (self-signed issuer → CA certificate → CA issuer → head and worker leaf certificates) and sets `RAY_USE_TLS` for Ray's internal gRPC traffic.
- **NetworkPolicyController.** Creates head and worker NetworkPolicies that admit traffic only from the same cluster, the same namespace, the operator, the monitoring namespace and the Gateway.

The operator is deployed as a component of the RHOAI platform operator (rhods-operator / opendatahub-operator) from `ray-operator/config/openshift`. That operator substitutes the image, the namespace and the kube-rbac-proxy image through `params.env`. The Ray workloads it creates are consumed by Data Science Projects (workbenches, CodeFlare SDK users and Kueue-admitted RayJobs). The repository also contains upstream-only sub-projects that RHOAI does not build: `apiserver` (gRPC/REST KubeRay API server), `apiserversdk`, `historyserver` (history server and collector), `dashboard` (Node.js UI), `kubectl-plugin`, `podpool` and `proto`.

## Architectural Analysis

**One shipped binary, many controllers behind feature gates.** The RHOAI image contains only `ray-operator/main.go`. One controller-runtime manager hosts:
- the core reconcilers: RayCluster, RayJob and RayService;
- RayCronJob, enabled when its gate is on;
- three downstream controllers: AuthenticationController (always registered), RayClusterMTLSController (gate `RayClusterMTLS`) and NetworkPolicyController (gate `RayClusterNetworkPolicy`);
- LegacySecurityController, registered only when the cluster is OpenShift and both the mTLS and NetworkPolicy gates are on;
- a TLS-profile watcher.

Upstream defaults most of these gates to off (alpha). The OpenShift overlay enables them with `--feature-gates=RayClusterStatusConditions=true,RayClusterNetworkPolicy=true,RayClusterMTLS=true` (`config/openshift/feature-gates-patch.yaml`). So the RHOAI security posture is a deployment-time choice, not a compile-time one. `RayCronJob`, `KubernetesWAS`, `RayClusterHistoryServer` and `GCSFaultToleranceEmbeddedStorage` stay disabled in RHOAI.

**Security is applied by the operator, with a migration path.** The downstream security contract has one entry point, `EnsureOpenShiftRayClusterSecurity` (`controllers/ray/utils/openshift.go`). It is applied in two places:
- at admission, by the mutating webhook, for new or updated objects;
- after the fact, by LegacySecurityController, which patches pre-existing clusters that carry only the legacy annotation onto the upstream-native `tlsOptions` and `networkPolicy` fields.

The NetworkPolicyController deliberately keeps legacy OpenShift policies until that migration finishes, so clusters are not left without isolation during upgrade. The validating webhook (`vraycluster.kb.io`) then stops users of managed OpenShift clusters from weakening the contract. It forbids custom egress rules, extra ingress rules beyond the platform-allowed set, unmanaged `managedBy` values and invalid managed port overrides. This makes the webhook pair a hard dependency: both use `failurePolicy: Fail`. If the operator pod or the cert-manager-issued webhook certificate is unavailable, all RayCluster CREATE/UPDATE requests are rejected.

**Gateway-only dashboard access, but the auth sidecar is not on the Gateway path.** On OpenShift, dashboard exposure goes through Gateway API: `HTTPRoute` `<ns>-<cluster>` in the platform namespace, path prefix `/ray/<ns>/<cluster>`, a URL rewrite to `/`, and a cross-namespace backend reference to `<cluster>-head-svc:<dashboard-port>`, which a per-namespace `ReferenceGrant` `kuberay-gateway-access` permits. The backend port is the Ray dashboard port (8265 by default), not the kube-rbac-proxy port 8443. The source code says so explicitly: "The Gateway data path targets the dashboard Service/port, not this Ray head port" (`controllers/ray/utils/openshift.go`). The `kube-rbac-proxy` sidecar with its per-cluster SubjectAccessReview check is therefore *not* on the Gateway data path. End-user authentication and authorization for Gateway traffic depends on the platform Gateway's own auth layer (kube-auth-proxy / EnvoyFilter, owned by rhods-operator, outside this repo). The NetworkPolicy keeps a source-less 8443 ingress rule "until direct 8443 callers are ruled out". Architects should treat per-RayCluster authorization at the Gateway as **unverified from this repository**.

**TLS profile compliance.** `ray-operator/pkg/tls` reads `apiservers.config.openshift.io/cluster` and turns the cluster `TLSSecurityProfile` into the Go `tls.Config` used by the metrics server and the webhook server. It also produces kube-rbac-proxy `--tls-min-version` / `--tls-cipher-suites` flags for injected head sidecars (RHOAIENG-95575). CBC, 3DES and RC4 suites are refused under any profile, including Old and Custom. If the profile cannot be read, a hardened Intermediate set (TLS 1.2+, ECDHE-GCM/ChaCha20) is used. A watcher cancels the manager context so the pod restarts when the profile changes. Head pods are stamped with the proxy TLS args and are recreated when those args drift.

**Operational risks and observations.**
- **Single replica.** `replicas: 1`, `strategy: Recreate`, and leader election is commented out in `config/manager/manager.yaml`. Webhooks with `failurePolicy: Fail` plus a single replica means that operator restarts (including the automatic TLS-profile-change restart) briefly block RayCluster admission.
- **Possible metrics port mismatch.** The OpenShift overlay moves the metrics Service and container port to 8443/HTTPS (`tls-metrics-patch.yaml`, `tls-service-json-patch.yaml`), but does not pass `--metrics-addr`. The binary default stays `:8080` (`apis/config/v1alpha1/defaults.go:8`), still with secure serving. Unless the platform operator overrides the bind address, Prometheus scrapes on 8443 would find no listener. Verify this in a deployed environment.
- **Broad cluster-wide privileges.** The operator ClusterRole grants create/delete on Secrets, Pods, Services, Roles, RoleBindings, NetworkPolicies, Routes, Ingresses, Gateways and HTTPRoutes in all namespaces. This is necessary because it watches all namespaces by default (`--watch-namespace` unset), but it is a high-value service account.
- **Ray dashboard traffic is plaintext.** Operator→Ray dashboard calls (job submission/status, Serve status) use plain HTTP to `<head-svc>:8265` (`controllers/ray/utils/util.go:1103`). Ray mTLS covers Ray's gRPC/GCS plane, not the dashboard HTTP API.
- **Upstream sub-projects are not shipped.** The `apiserver`, `historyserver` and `dashboard` endpoints in the analyzer inventory are present in source but are not built by Konflux for RHOAI.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy SAR on `services/<cluster>-head-svc`; per-cluster OAuth/OIDC proxy ServiceAccount | Kubernetes (SAR) / sidecar | Gateway path targets dashboard port 8265, bypassing per-cluster SAR; relies on platform Gateway auth |
| Data storage | Per-RayCluster PVCs/volumes in user namespace | Kubernetes | Ray object storage / GCS FT Redis are user-configured |
| Network traffic | Per-RayCluster head/worker NetworkPolicies (same-cluster, same-namespace pods on 8265/10001, operator, Gateway, monitoring ns); mTLS between Ray nodes | Kubernetes NetworkPolicy / Ray TLS | Any pod in same namespace can reach dashboard/client ports; source-less 8443 ingress rule retained |
| Compute & resources | Delegated to Kueue / ResourceQuota / batch schedulers | Platform | Operator itself has no quota enforcement |
| Configuration & secrets | Per-cluster CA and leaf certs, auth token Secrets in user namespace, owned by RayCluster | Kubernetes | Operator SA can read/write Secrets cluster-wide |
| API scoping | Cluster-wide informers (label-filtered for Pods/Jobs); HTTPRoutes centralized in platform namespace; ReferenceGrant per user namespace | Application | HTTPRoutes for all tenants live in one namespace; route naming `<ns>-<cluster>` truncated with hash |
