## Purpose

**Short**: OpenAI-compatible batch inference gateway that accepts `/v1/files` and `/v1/batches` jobs, queues them in PostgreSQL, and drives them through llm-d inference gateways with adaptive concurrency so batch traffic does not crowd out interactive traffic.

**Detailed**: llm-d-batch-gateway provides an asynchronous, OpenAI-schema-compatible batch API on top of llm-d. Users upload JSONL input files (up to 50,000 lines / 200 MB by default) through the API server and create batch jobs that reference them. Job and file metadata, a priority queue (ordered by SLO deadline), job events and status live in PostgreSQL; file content lives in S3-compatible object storage or a filesystem/PVC backend.

A horizontally scaled batch processor StatefulSet polls the PostgreSQL priority queue, downloads the input file, groups requests by model and system-prompt hash (to keep prefix/KV-cache hot), writes per-model plan files to local disk, and dispatches individual inference requests to the configured llm-d inference gateway (global or per-model URL) under global and per-endpoint semaphores. An AIMD controller shrinks concurrency on 429/5xx and grows it on success. Optionally (`dispatchMode=async`) requests are pushed onto Redis/Valkey sorted sets (or an experimental PostgreSQL SQL transport) for the external llm-d-async dispatcher to consume. Results are checkpointed, assembled into output/error files, uploaded to storage, and the job status is updated.

A garbage collector Deployment periodically deletes expired batches and files and runs a reconciler that watches the processor StatefulSet via the Kubernetes API so jobs owned by dead processor pods can be reclaimed (orphan recovery). In RHOAI the component sits behind the platform Gateway (Kuadrant/Authorino AuthPolicy) which performs authentication and injects the tenant identity header; the gateway itself performs no authentication.

## Architectural Analysis

**Three-binary split with PostgreSQL as the coordination plane.** The repository builds three independent binaries (`cmd/apiserver`, `cmd/batch-processor`, `cmd/batch-gc`) that never call each other directly. All coordination happens through PostgreSQL: the API server inserts batch rows (with `priority` derived from SLO), processors dequeue by claiming rows (`processor_id`, `epoch`, lease expiry for resumable jobs), cancellation is delivered via PostgreSQL events/`LISTEN` (`internal/database/postgresql/pg_listen.go`), and GC/reconciler sweeps rows. This makes the API server stateless and independently scalable, while processors are a StatefulSet so each pod has a stable identity used as `processor_id` and for orphan detection. PostgreSQL is therefore a single point of failure and the primary scaling bottleneck; HA is delegated entirely to the operator-supplied database.

**Delegated security boundary.** The API server has no authentication or authorization code. The middleware chain is only Recovery → RequestMiddleware (request ID, tenant extraction, metrics, OTel) → SecurityHeaders (`internal/apiserver/server/server.go:94-98`). Tenant identity comes from a configurable header (`X-MaaS-Username` by default) and the *last* header value is used so that a gateway-appended value wins over a client-spoofed one. The project's own security guide states direct access to the API server bypasses all tenant isolation. The Helm chart ships no NetworkPolicy, so in RHOAI the protection depends on the platform Gateway/Kuadrant AuthPolicy being the only reachable path to the `ClusterIP` Service on port 8000. The documented topology uses two gateways: an External Gateway (`batch-route`, TokenReview auth + RateLimitPolicy) and a ClusterIP-only Internal Gateway (`batch-llm-route`, AuthPolicy with SubjectAccessReview on `inferencepools`, no TokenRateLimitPolicy) that the processor uses for inference.

**User bearer tokens persisted and replayed.** With `passThroughHeaders: [Authorization]` (the Helm default), the API server copies the caller's `Authorization` header into the batch row's `tags` JSONB column under a `pth:` prefix (`internal/apiserver/batch/batch_handler.go:193-198`). The processor reads it back (`internal/shared/batch_utils/job_info_builder.go:46-50`) and replays it on every inference request, and in async mode it is also placed in Redis queue messages. This gives per-request model authorization on the Internal Gateway, but means long-lived user credentials are stored at rest in PostgreSQL (and Redis) in plaintext for the life of the batch row. Jobs that run longer than the token's validity will also see per-line 401/403 failures. Database and Redis access control and encryption at rest are therefore security-relevant.

**Pluggable storage, application-enforced isolation.** Storage backends are abstracted behind `internal/database/api` and `internal/files_store/api` interfaces (PostgreSQL; S3 or filesystem), with retry and tracing decorators layered around file clients. Tenant isolation is purely application-level: every DB row carries `tenant_id` (indexed), queries filter on it, files are stored under `t-<sha256(tenant)[:61]>` prefixes (`internal/util/com/common.go:84-94`), and cross-tenant reads return 404. A single shared S3 bucket, PostgreSQL database and processor pool serve all tenants.

**Resilience design.** Processors support resumable jobs (lease-based ownership, checkpointed result lines with SHA-256 integrity, `finalizer_resumable.go`), startup recovery with bounded concurrency, and AIMD concurrency control (`internal/util/semaphore/aimd.go`). The GC reconciler only acts when the StatefulSet is stable (`readyReplicas == replicas`), which avoids reclaiming jobs during rolling updates.

**Observability surfaces are unauthenticated.** Each binary exposes plain-HTTP `/health`, `/ready` and `/metrics` on a separate port (apiserver 8081, processor 9090, gc 9091). Optional `/debug/pprof/*` (`enablePprof`, default false) is mounted on the same unauthenticated listener; enabling it in production exposes profiling and command-line data to anything that can reach the pod. OTLP trace export defaults to `insecure: true` in Helm values.

**Upstream build artifacts only on this branch.** The checked-out branch contains only upstream `docker/Dockerfile.*` files (no `.konflux` variants, no Tekton pipelines, no RPM lock files). These build `CGO_ENABLED=0` static binaries on `gcr.io/distroless/static:nonroot`, which would fail the Konflux check-payload FIPS gate as-is. The RHOAI productized build is expected to come from a downstream Konflux configuration that is not present here.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | External AuthPolicy injects identity. The application trusts the header. | Platform (Kuadrant/Authorino) + Application | No in-process auth or NetworkPolicy. Any in-cluster caller that reaches Service port 8000 can impersonate any tenant by setting the header. Missing header falls back to the shared `default` tenant. |
| Data storage | Shared PostgreSQL with `tenant_id` column filters; shared bucket/FS with `t-<sha256>` prefixes | Application | Isolation depends on every query filtering correctly. Stored pass-through bearer tokens are readable by anyone with DB access. |
| Network traffic | None shipped | — | No NetworkPolicy in the Helm chart. Observability and pprof ports are open in-cluster. |
| Compute & resources | Shared processor pool. Global/per-endpoint semaphores plus AIMD. SLO-ordered priority queue. | Application | No per-tenant quotas or fairness at the gateway (optional `sendFairnessHeader` only). One tenant can fill the queue, limited only by gateway RateLimitPolicy. |
| Configuration & secrets | Single shared app Secret and inference API key | Kubernetes | Shared credentials across tenants. Per-model API keys are not per-tenant. |
| API scoping | All list/get/delete operations filtered by tenant; cross-tenant access returns 404 | Application | Relies on correct header injection |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL (batch_items, file_items) | Row-level `tenant_id` | Application query filter |
| S3 bucket / filesystem PVC | Key prefix `t-<sha256(tenant)>` | Application path derivation |
| Redis/Valkey async queues | None (keyed by inference pool) | Per-request user token carried in the message, authorized at Internal Gateway |
| llm-d inference gateway | Per-request identity | AuthPolicy SubjectAccessReview on inferencepools |
