## Purpose

**Short**: An OpenAI-compatible batch inference gateway for llm-d. It accepts `/v1/files` and `/v1/batches` jobs, sends each request to llm-d inference gateways under adaptive concurrency control, and writes the results back to object storage.

**Detailed**: batch-gateway brings the OpenAI Batch API to llm-d-based model serving in RHOAI. Users upload a JSONL file of inference requests through the `/v1/files` API, then create a job with `/v1/batches`. The API server (`batch-gateway-apiserver`) stores job and file metadata in PostgreSQL, which also serves as the priority queue, event channel and status store. It stores the file content in S3-compatible object storage or on a filesystem/PVC. Every job and file is tagged with a tenant ID, taken from a configurable header (default `X-MaaS-Username`) that an upstream gateway authentication layer sets.

The batch processor (`batch-gateway-processor`) runs as a StatefulSet. Each replica pulls jobs from the PostgreSQL priority queue and downloads the input file. It groups requests by model and system-prompt hash (to keep the prefix/KV cache warm) and writes a per-model plan to local disk. It then sends the requests either **synchronously** over HTTP(S) to one global or several per-model llm-d inference gateway / EPP endpoints, or **asynchronously** through llm-d-async request/result queues (Redis/Valkey sorted sets or experimental PostgreSQL SQL transport). Concurrency is limited by global and per-endpoint semaphores, and an AIMD controller backs off on 429/5xx responses so batch traffic does not crowd out interactive traffic. Results are checkpointed (resumable pipeline with ownership leases held in PostgreSQL), assembled into output and error files, uploaded, and the job status is updated.

The garbage collector (`batch-gateway-gc`) runs as a single replica. It periodically deletes expired jobs and files from the database and file store. It also runs an orphan reconciler: it watches the processor StatefulSet through the Kubernetes API and recovers jobs that crashed processor replicas left in non-terminal states. In RHOAI 3.x this component sits behind the platform's Gateway API ingress (batch-route → API server). The processor calls model endpoints through an internal gateway route, where per-model authorization (SubjectAccessReview on `inferencepools`) runs against the end user's forwarded bearer token.

## Architectural Analysis

**Split control/data plane with PostgreSQL as the coordination backbone.** All three binaries share one PostgreSQL database for job and file metadata, the priority queue, events (e.g. cancellation), progress updates, resumable-pipeline checkpoints and ownership leases. The API server and GC are effectively stateless. The processor is a StatefulSet because it needs a stable replica identity: async result queue names are suffixed with that identity, and the GC orphan reconciler matches ready pod names against job ownership to tell live processors from dead ones. This makes PostgreSQL a single point of failure and a hard dependency for every component. The design document set (`docs/design/resumable-jobs.md`, `orphan-recovery.md`) describes the lease/reconcile protocol that replaces a separate message broker.

**Authentication is delegated entirely to the platform gateway.** The API server has no authentication middleware. Its chain is Recovery → RequestMiddleware (request ID, tenant extraction, logging, metrics, OTel) → SecurityHeaders (`internal/apiserver/server/server.go:93-97`). Tenant identity is read from a header (`X-MaaS-Username` by default). The middleware takes the *last* header value (`common.LastHeaderValue`), which works around Envoy ext_authz *appending* rather than replacing headers. A client could add a spoofed value, and the authenticated value appended later by the gateway wins. This only holds if (a) every request goes through a gateway whose auth policy always sets this header and (b) nothing can reach the API server Service directly. The chart ships no NetworkPolicy, and a request with no tenant header silently falls back to tenant `default`. Any in-cluster workload that can reach `<apiserver>:8000` can therefore act as any tenant by setting the header itself.

**End-user bearer tokens are persisted at rest.** `batchAPI.passThroughHeaders` defaults to `[Authorization]` (`charts/batch-gateway/values.yaml:196-197`). At batch creation the API server copies each pass-through header into the job's database `tags` with a `pth:` prefix (`internal/apiserver/batch/batch_handler.go:193-198`). The processor later rebuilds them (`internal/shared/batch_utils/job_info_builder.go:46-50`) and attaches them to every inference request, so the internal gateway can run per-model authorization as the original caller. As a result, user Kubernetes/OIDC bearer tokens sit in PostgreSQL for the life of the job record (event TTL defaults to 30 days). Long-running or queued jobs can also fail midway when the stored token expires. Database access controls and encryption at rest therefore matter for platform security.

**Two TLS stacks with different defaults.** The API server listener can serve TLS when a cert/key pair is supplied (optionally provisioned by a cert-manager `Certificate`). Min version, cipher suites and ALPN are injectable from a platform TLS profile through `internal/tls/tls.go`, which rejects cipher lists combined with TLS 1.3. If no min version is supplied it defaults to TLS 1.2. The observability listener (8081/9090/9091) is always plaintext. The outbound HTTP client used for inference (`pkg/clients/http/http_client.go`) supports custom CA, mTLS client certs, min TLS version and an `InsecureSkipVerify` escape hatch that is documented as testing-only. TLS to PostgreSQL, Redis and S3 is driven by the URL/endpoint scheme (`sslmode=`, `rediss://`, `https://`), not by code-level config. The chart's OTel default is `insecure: true` (plaintext gRPC to the collector).

**Pluggable storage, tenant-hashed paths.** File content is stored under a tenant folder derived from `sha256(tenantID)` (`internal/util/com/common.go:84-93`, `t-` + 61 hex chars). This gives deterministic per-tenant S3 key prefixes or filesystem subdirectories without exposing raw user names in object paths. All tenants still share a single bucket, a single set of S3 credentials (`s3-secret-access-key`) and a single database, so isolation is enforced only by the application (tenant equality checks in `file_handler.go:153`, `batch_handler.go:345` and `tenant_id` filters in `db_core.go:193-195`).

**Operational posture.** The containers are hardened (non-root, all capabilities dropped, read-only root FS, RuntimeDefault seccomp). Images are built FIPS-ready (CGO + `GOEXPERIMENT=strictfipsruntime` on `ubi-minimal-pqc`), hermetically, for four architectures. pprof endpoints exist on the observability listeners but are off by default. The repository has no kustomize manifests and no operator. RHOAI integration (DataScienceCluster component wiring, Gateway/AuthPolicy, platform TLS profile injection) is expected to come from the platform operator and the deployment guides, not from this repo. The `benchmarks/manifests/vllm` Deployment (`vllm-qwen3-8b-decode`) is benchmark tooling, not part of the shipped component.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Upstream gateway sets the tenant header; app trusts it | Platform gateway + Application | No in-app authentication. Direct in-cluster access to Service 8000 allows header spoofing, and a missing header maps to the shared `default` tenant |
| Data storage | Shared PostgreSQL with `tenant_id` column; shared bucket/FS with `t-<sha256>` prefix per tenant | Application | Single DB and S3 credentials for all tenants; isolation depends on query filters and equality checks |
| Network traffic | None shipped (no NetworkPolicy) | — | API and observability ports reachable from any pod that network policy allows |
| Compute & resources | Shared processor pool; global/per-endpoint semaphores + AIMD; API rate limits at gateway | Application + Gateway | No per-tenant concurrency quota inside processor; one tenant's large batch can delay others in the priority queue |
| Configuration & secrets | Single shared secret | Kubernetes | Per-user bearer tokens stored in shared DB tags |
| API scoping | List queries filtered by tenant; GET/DELETE/cancel return 404 on tenant mismatch | Application | Correctness relies on every handler applying checks |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL | Row-level `tenant_id` | Application query filter |
| S3 bucket / filesystem PVC | Key prefix `t-<sha256(tenant)>` | Application path derivation |
| Redis/Valkey async queues | Per-model/pool queue (not per-tenant) | None per tenant |
| llm-d inference gateway | Per-request user bearer token | Internal gateway SubjectAccessReview on `inferencepools`; optional `routeKeyMethod: tenant` for tenant-specific model routes |
