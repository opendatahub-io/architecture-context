## Purpose

**Short**: The Kubeflow Training Operator (KFTO, v1 API) reconciles framework-specific distributed training jobs (PyTorchJob, TFJob, MPIJob, XGBoostJob, PaddleJob, JAXJob) into Pods, headless Services and supporting resources in user namespaces.

**Detailed**: training-operator is a single Go binary (`/manager`, built from `cmd/training-operator.v1/main.go`) that runs one controller-runtime manager. The manager hosts six job reconcilers (`pkg/controller.v1/register_controller.go:37-56`), a validating admission webhook server on port 9443, and health/readiness probes on 8081. It also exposes Prometheus metrics on 8080. For each `kubeflow.org/v1` job CR, the operator creates replica Pods and per-replica Services. It also injects framework-specific environment, such as `MASTER_ADDR`/`WORLD_SIZE` for PyTorch, `TF_CONFIG` for TensorFlow, and the JAX coordinator address. Other job resources depend on the framework:

- PyTorch elastic jobs get a HorizontalPodAutoscaler.
- PyTorch jobs get a per-job NetworkPolicy.
- MPI launchers get a ConfigMap, ServiceAccount, Role and RoleBinding.
- Gang-scheduling PodGroups are created when Volcano or scheduler-plugins are configured.

In RHOAI, the Red Hat OpenShift AI operator deploys the component from the `manifests/rhoai` kustomize overlay into the `opendatahub` application namespace with the `kubeflow-` name prefix. It watches jobs cluster-wide (no `--namespace` flag is set). Data scientists submit jobs from workbenches, either directly or through the Kubeflow Training Python SDK. The operator's own image doubles as the PyTorch "wait for master" init container image, which is why `bind-utils` (`nslookup`) is installed in the runtime image. This is the legacy v1 Training Operator line. Upstream has since been renamed to `kubeflow/trainer` and moved to the v2 TrainJob/TrainingRuntime API, but this branch ships only the v1 API.

## Architectural Analysis

**Single-process, multi-framework controller.** All six frameworks share a common `JobController` in `pkg/controller.v1/common` (pod/service reconciliation, expectations, status conditions, run-policy/cleanup). Each framework adds only env-var injection, the master/worker topology and success semantics. You can limit which reconcilers start with `--enable-scheme`, but RHOAI does not set it, so all six run. Controllers are registered in a goroutine only after the webhook certificate rotator signals `certsReady`. Readiness also blocks on certificate generation and webhook server startup (`cmd/training-operator.v1/main.go:372-374, 448-455`). This prevents admission failures during startup, because webhook `failurePolicy` is `Fail`.

**Self-managed webhook PKI.** The operator does not depend on cert-manager or the OpenShift service-CA. `open-policy-agent/cert-controller`'s rotator (`pkg/cert/cert.go:53-70`) generates a self-signed CA and serving certificate. It stores them in the `kubeflow-training-operator-webhook-cert` Secret, which RHOAI kustomize creates empty via `secretGenerator`. It then patches the CA bundle into the `kubeflow-validator.training-operator.kubeflow.org` ValidatingWebhookConfiguration. Secret access is limited to a namespaced Role. The ClusterRole only grants `get/list/watch/update` on ValidatingWebhookConfigurations, so the operator can patch any VWC in the cluster.

**Cluster TLS profile adherence (partial).** At startup, `fetchTLSOpts` reads `config.openshift.io/v1 APIServer/cluster` and maps `spec.tlsSecurityProfile` (Intermediate, Modern, Old or Custom) to Go `tls.Config` options (`main.go:86-224`). If the profile is unavailable, it falls back to TLS 1.2 with Intermediate ECDHE-AEAD ciphers. If the custom cipher list maps to zero Go ciphers, the operator exits rather than run with unrestricted ciphers. The profile is read only once at startup, so profile changes need a pod restart. The same `tlsOpts` are passed to the metrics server, but `SecureServing` is not set (`main.go:330-333`). As a result, the metrics endpoint serves **plain HTTP without authentication** on :8080, and only the webhook server actually applies the TLS profile. RHOAI removes port 8080 from the Service and scrapes through a `PodMonitor` on the pod port instead.

**Memory-bounded informer cache.** Informers for Pods, Services, ConfigMaps, ServiceAccounts, Secrets, Roles and RoleBindings use a label selector that requires the operator-name label (`main.go:229-263`). ConfigMap and Secret reads skip the cache entirely. This stops cluster-wide caching of every Pod and Secret. Without it, a cluster-wide watch would grow memory without limit (`GOMEMLIMIT=460MiB`, limit 512Mi).

**Privilege surface and risks.**
- The ClusterRole is broad. It includes cluster-wide `create/delete` on Pods, `pods/exec`, Roles, RoleBindings and ServiceAccounts, which the MPI launcher flow needs. In practice, the operator can create a namespaced Role granting `pods/exec` in any namespace.
- MPIJob has no validating webhook. Its registration is a no-op scaffold (`pkg/webhooks/webhooks.go:37,43-45`).
- The MPI launcher's `kubectl-delivery` init image defaults to `ghcr.io/kubeflow/training-v1/kubectl-delivery:latest` (`pkg/config/config.go:35`), and the RHOAI overlay does not override it. That is a mutable, non-Red Hat image reference, which is a problem for disconnected and supply-chain-sensitive installs.
- The RHOAI aggregate role `training-edit` (aggregated into `admin`/`edit`) still lists the removed `mxjobs` and omits `jaxjobs`. Namespace editors therefore cannot manage JAXJobs through the default aggregated roles (`manifests/rhoai/kubeflow-training-roles.yaml:13-20`).
- The PyTorchJob NetworkPolicy allows ingress only from the job's own pods, plus TCP 8080 from `openshift-monitoring` (`pkg/controller.v1/pytorch/pytorchjob_controller.go:540-563`). This gives PyTorch jobs default-deny isolation from other workloads. The other five frameworks get no NetworkPolicy.

**Build posture.** The Konflux build is hermetic. It uses `prefetch-input` for both `gomod` and `rpm`, a pinned `rpms.lock.yaml` for `bind-utils`, and digest-pinned builder and runtime bases. It builds with `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime -tags strictfipsruntime`, which matches the RHOAI FIPS build pattern. The PR pipeline builds `linux/x86_64` only, while the rpm lock covers x86_64, aarch64 and ppc64le.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | User access via aggregated `edit`/`view` roles; the operator acts with one shared cluster-wide SA | Kubernetes | The operator SA can create Pods, Roles with `pods/exec`, and RoleBindings in any namespace, so any compromise has cluster-wide impact. JAXJob is missing from the aggregated roles |
| Data storage | Job pods mount user-specified PVCs in their own namespace | Kubernetes | None introduced by the operator |
| Network traffic | Per-PyTorchJob NetworkPolicy (intra-job + openshift-monitoring:8080 only) | Kubernetes | TFJob, MPIJob, XGBoostJob, PaddleJob and JAXJob get no NetworkPolicy, so their pods are reachable from other namespaces unless a namespace policy exists |
| Compute & resources | None from the operator. Optional gang scheduling; Kueue (external) provides quota | Kubernetes / Kueue | No ResourceQuota enforcement by the operator |
| Configuration & secrets | Job ConfigMaps and SAs created in the job namespace with owner refs | Kubernetes | Secret informer is label-filtered |
| API scoping | Cluster-wide watches, label-filtered caches for core objects | Application (controller-runtime) | Single reconcile queue shared across tenants; one tenant's job volume can slow reconciliation for others (`controller-threads=1`) |
