SCOPE NOTE
  llm-d is a meta-repository of deployment recipes, guides, and auxiliary images.
  It runs no service of its own. The topology below is what the upstream guides
  deploy using external components: the llm-d-router chart, vLLM, and a Gateway API provider.
  In RHOAI, KServe's LLMInferenceService controller renders the llm-d topology
  (overlay 0011) using RHAIIS AIPCC vLLM images and downstream llm-d-router
  images (overlay 0019). The upstream defaults shown here are a REFERENCE BASELINE
  ("reference, not hardened"), not necessarily what RHOAI ships.

Service Mesh Configuration:
- Istio mTLS: ONLY for ModelExpress (PeerAuthentication STRICT + AuthorizationPolicy)
- All other hops (Gateway → router → vLLM, sidecar → prefill, NIXL KV transfer)
  are plaintext in the upstream guides
- No NetworkPolicies are shipped by any guide

Authentication & Authorization:
- Gateway / router inference APIs (POST): NONE in guides; delegated to platform
- Routing sidecar → vLLM: NONE (--secure-serving=false)
- Router /metrics (GET): DISABLED (prometheus.auth.enabled: false)
- modelexpress-server :8001: Istio mTLS + AuthorizationPolicy ALLOW-list
- Thanos Querier (OCP): Bearer SA token, cluster-monitoring-view
- x-llm-d-epp-profile header route: NONE, client-controlled → documented bypass

Secrets:
- llm-d-hf-token (Opaque, HF_TOKEN) - HuggingFace download; manual; no rotation;
  referenced by about 135 manifests
- keda-epp-metrics-reader-token (kubernetes.io/service-account-token) - KEDA →
  Thanos bearer + service-ca.crt; long-lived SA token; no rotation
- wva-epp-metrics-token (kubernetes.io/service-account-token) - WVA EPP metrics read
- agentic-api-postgres (Opaque: password, database-url) - openssl rand -hex 16
- prometheus-tls-cert / prometheus-web-tls (kubernetes.io/tls) - self-signed CA,
  RSA 2048, SHA-256, generated by generate-prometheus-tls-certs.sh; no rotation
- squid-ca-public-cert (CA bundle) - coordinator egress proxy; manual

Multi-Tenancy:
- Boundary: one guide instance per namespace; within a pool, logical tenants via
  x-llm-d-inference-fairness-id and InferenceObjective priority bands
- Fairness and priority only, NOT isolation; tenant/priority headers are
  client-controlled and unauthenticated (any caller can claim premium priority)
- Shared prefix KV cache across tenants in one pool (timing side-channel potential)
- No ResourceQuota / LimitRange shipped

FIPS / Build Posture (upstream images - NOT used in RHOAI, overlay 0019):
- Dockerfile.cpu: ubuntu:25.10 system OpenSSL (not FIPS-validated); uv via curl | sh;
  UV_INDEX_STRATEGY=unsafe-best-match (dependency-confusion exposure)
- Dockerfile.xpu: thin layer on vllm/vllm-openai-xpu:v0.30.0 + LMCache v0.5.0
- Dockerfile.rdma-tools: nvcr.io CUDA 13.0.2 UBI9, diagnostics only
- No Konflux, no rpms.lock.yaml, no Hermeto: all build layers non-hermetic
- No TLS server code in repo

Key Security Observations:
1. Plaintext everywhere by default: Gateway :80, sidecar --secure-serving=false,
   NIXL 5600 over fabric.
2. failureMode: FailOpen keeps traffic flowing when EPP is down (availability
   over LLM-aware routing).
3. Gateway allows routes from all namespaces; no NetworkPolicies.
4. OCP P/D overlay adds IPC_LOCK, SYS_RAWIO, NET_ADMIN, NET_RAW + hostPath.
5. interactive-pod Role can read Secrets and write RBAC in its namespace.
6. Good patterns: modelserver SA token automount disabled; ModelExpress mTLS
   allow-list; agentgateway OCP params drop ALL caps, read-only rootfs,
   runAsNonRoot, RuntimeDefault seccomp; KEDA → Thanos over HTTPS + bearer.
