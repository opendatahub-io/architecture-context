## Purpose

**Short**: A Python package of opt-in vLLM endpoint plugins that add read-only `GET /plugins/llm-d-server-introspection/{config,devices,kv-cache}` endpoints to a vLLM server. llm-d uses these endpoints to learn how a server was launched, what hardware it runs on, and how big its KV cache is.

**Detailed**: llm-d makes routing and scheduling decisions based on facts about each inference server: launch configuration, parallelism, accelerator properties, and KV cache capacity after profiling. This repo does not add those endpoints to vLLM core. It packages them as **extensions** that vLLM loads through its own extension points. The package `llm-d-api-extensions-vllm` registers three classes under the `vllm.endpoint_plugins` entry-point group: `ServerConfigPlugin`, `ServerDevicesPlugin` and `ServerKVCachePlugin`. vLLM attaches their FastAPI routers to its OpenAI-compatible API server at startup. A fourth class, `DeviceInfoWorkerExtension`, is mixed into vLLM's GPU worker processes with `--worker-extension-cls`. It adds a `get_device_properties` method that the devices plugin calls over `engine_client.collective_rpc`.

The plugins are off by default. vLLM loads only the plugins named in the `VLLM_PLUGINS` environment variable, so installing the package changes nothing until an operator enables it. Each plugin collects its data once, in `init_state` during server startup, caches the response on `app.state`, and serves that cached copy for the life of the server. The plugins open no network listeners or outbound connections of their own. They run inside the vLLM API server process and share its port, TLS and auth settings.

At the top level the repo does not depend on any one inference server: each server gets its own sibling package directory. Only `vllm/` exists today, and the README says SGLang or similar could be added later. In RHOAI 3.7 EA1 this component is expected to be consumed as a pip dependency of the vLLM/llm-d model-server images. This repo contains no Dockerfile, so how it gets into an image is decided elsewhere.

## Architectural Analysis

**Extension-point integration, not a fork.** The design relies on two vLLM extension mechanisms. The first is the `vllm.endpoint_plugins` entry-point group (`vllm/pyproject.toml:27-30`), which supplies `attach_router(app)` and `init_state(engine_client, state, args)` hooks. The second is `--worker-extension-cls`, which mixes a class into the concrete `Worker` bases (`device_worker_ext.py:2-15`). With these two mechanisms llm-d gets server-introspection APIs without patching vLLM. The cost is that every value comes from vLLM *internals* (`VllmConfig`, `EngineClient`, `current_platform`), which are not a stable contract.

**Defense against vLLM interface drift is the main design concern.** vLLM calls `init_state` without exception handling, so if a plugin raises there, server startup aborts (`common.py:4-7`). The package handles this in three layers:
1. `read_attr` (`common.py:116-129`) is a `getattr` wrapper that returns a default and records a "drift" event when an attribute is missing.
2. `build_tolerant` (`common.py:132-144`) builds the Pydantic model. If a field fails validation, it drops that field to its default (null) instead of failing the whole response.
3. `guarded_init_state` (`common.py:158-188`) catches any remaining exception, logs it, and makes that endpoint return `503` with a reason while the rest of the server keeps running.
Every field in the response schemas is nullable (`schemas.py:6-8`). The `kv-cache` group union has a catch-all `UnknownGroupSpec` for KV-cache kinds the package doesn't know yet. CI runs the contract tests (`test_vllm_contract.py`) against the released vLLM and against vLLM nightly, both on every PR and on a daily schedule (`.github/workflows/ci-test.yaml:11-31`). This catches upstream renames early. The trade-off is that llm-d consumers must treat `null` as "unknown" and not as "false/zero".

**Dependency on an unmerged upstream API.** The `kv-cache` endpoint gets attention-group structure from `EngineClient.get_kv_cache_group_metadata()`. That method is proposed in vllm-project/vllm#48121 and is not in a released vLLM (`kv_cache_plugin.py:11-18`). The plugin detects the method with `getattr`. If the method is missing, it falls back to capacity-only fields computed from `cache_config` (`num_gpu_blocks * block_size`, and `max_concurrency` = tokens / `max_model_len`) and returns an empty `groups` list. Unless the vLLM build shipped in RHOAI carries that patch, llm-d will only see capacity data.

**Engine vs. render-server split.** The `config` plugin sets `required_tasks = None`, so it also loads on vLLM's CPU-only "render" frontend, which has no engine (`config_plugin.py:7-9`, `:188`). The `devices` and `kv-cache` plugins set `required_tasks = ENGINE_TASKS` (generation + pooling tasks, without `render`), so they load only where an engine exists. Without an engine they return 503.

**Information exposure is the main security consideration.** The endpoints have no authentication of their own. They inherit whatever the vLLM API server enforces (for example `--api-key`, or a gateway/auth proxy in front of it). The data returned is operational metadata, but the `config` response includes KV-transfer topology: connector name, `kv_port`, `engine_id`, and the NIXL side-channel host/port (`config_plugin.py:100-129`). That information is useful for reconnaissance of the P/D-disaggregation data plane. The free-form `kv_connector_extra_config` can hold credentials, so by default its values are replaced with `"<redacted>"` and only the keys are kept. Values are returned verbatim only when `LLM_D_INTROSPECTION_EXPOSE_KV_EXTRA_CONFIG=1` (`config_plugin.py:50-63`). Operators should leave that flag unset in production.

**Supply chain and release posture.** The package has no lock file. Runtime dependencies are unpinned (`vllm`, `fastapi`, `pydantic>=2`). There is no Konflux Dockerfile, no RPM or artifact lock, and no Tekton pipeline. Hermeticity and FIPS posture therefore come entirely from whatever image installs this package. The git tag `v1.0.0` and the package version `0.1.0` do not match. Dependabot covers pip and GitHub Actions.
