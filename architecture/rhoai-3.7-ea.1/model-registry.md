## Purpose

**Short**: Gives RHOAI a central metadata store and REST API for registered models, versions, artifacts and experiments, plus a Model/MCP/Agent/Skill/Serving-Runtime catalog API server. Both servers ship in one Go image. A separate Python Job image copies, registers and optionally signs models.

**Detailed**: The model-registry repo (upstream `kubeflow/hub`, Go module `github.com/kubeflow/hub`) builds one Go binary, `/model-registry`, with two cobra subcommands:

- `proxy` (`cmd/proxy.go`) is the Model Registry REST server. It serves the OpenAPI-generated `/api/model_registry/v1` and deprecated `/api/model_registry/v1alpha3` APIs on port 8080. Its data goes into MySQL or PostgreSQL through the "embedmd" GORM datastore.
- `catalog` (`catalog/cmd/catalog.go`) is the Model Catalog API server. A plugin framework serves model, MCP-server, agent, skill and serving-runtime catalogs. It is backed by PostgreSQL and uses `pglock`-based leader election.

In RHOAI, the model-registry-operator deploys both roles from the same `quay.io/rhoai/odh-model-registry-rhel9` image. Per overlay 0018, the odh-dashboard model-registry module (BFF and frontend) proxies to them.

The second Konflux artifact is `odh-model-registry-job-async-upload-rhel9`, a Python Kubernetes Job built on the AIPCC CPU base image. It downloads a model from S3, OCI or a URI, then uploads it to S3 or packages it as an OCI ModelCar (via `olot` and `skopeo`). It registers the result in the Model Registry through the `model-registry` Python client. If signing is enabled, it signs the model and image with Sigstore/`rh-model-signing` and the `cosign` binary.

The repository also contains code that RHOAI ships elsewhere or only uses as a library:

- `pkg/inferenceservice-controller`, a Go library that syncs KServe InferenceServices back to the registry. The model-registry-operator imports it, and `cmd/controller` wraps it as a standalone upstream controller.
- The `clients/ui` frontend and BFF.
- The `cmd/csi` storage initializer.
- Python clients (`clients/python`, `catalog/clients/python`).
- Upstream kustomize manifests (`manifests/kustomize`) that target Kubeflow/Istio. RHOAI does not use these directly: the model-registry-operator renders RHOAI deployments, apart from the catalog `overlays/rhoai` variant.

## Architectural Analysis

**One image, two runtime roles.** `Dockerfile.konflux` builds a single FIPS-mode Go binary. The default `CMD` runs `proxy`, and the catalog deployment overrides the command to `/model-registry catalog`. The two roles share platform code under `internal/platform/*`: datastore connectors, DB TLS config, validation and deprecation middleware, and health checkers. They do not share a database. The registry supports MySQL (default `--embedmd-database-type=mysql`) or PostgreSQL. The catalog is PostgreSQL-only, configured through libpq environment variables (`PGHOST`, `PGUSER`, `PGPASSWORD`). Because of this coupling, every catalog change ships a new registry image and the reverse, and both roles share one CVE/FIPS surface.

**No in-process authentication on the data APIs.** Neither `proxy` nor `catalog` installs any authentication or authorization middleware. `proxy` wraps routes with request logging, optional CORS and deprecation headers, and schema validation (`middleware.WrapWithValidation`). `catalog` wraps them with `ValidationMiddleware`. Both listen with plain `http.ListenAndServe` and no TLS. All access control is external:

- In upstream Kubeflow, an Istio `AuthorizationPolicy` allows the ingress gateway principal, plus `kubeflow`-namespace callers that present an `Authorization` header without `kubeflow-userid`.
- In RHOAI, the model-registry-operator is expected to place each instance behind kube-rbac-proxy or a Gateway HTTPRoute. That wiring lives outside this repo.

If a deployment exposes the registry or catalog Service without that proxy, any in-cluster caller with network reach gets unauthenticated read/write access to model metadata.

**Catalog server design.** The catalog loads multiple `--catalogs-path` source YAMLs: model, MCP and skill sources, plus `/default-sources` in the ODH/RHOAI overlays. Plugins self-register with a blank import (`_ "…/plugins/model"`, `mcp`, `agent`, `skill`, `serving_runtime`). Only the leader runs ingestion. Every replica holds a Postgres advisory lock (`catalog-leader`, default 60 s lease with a 15 s heartbeat), and readiness reports leader-election health. On becoming leader, a replica re-initializes the datastore. Model sources can pull from Hugging Face (`https://huggingface.co`, optional `HF_API_KEY` secret) and from YAML files seeded by init containers:

- ODH uses `odh-model-metadata-collection`.
- RHOAI adds `registry.redhat.io/rhoai/odh-model-performance-data-rhel9:v3.0.0` to supply `/shared-data/performance` benchmark data.

The skill catalog's `git-skills-plugin` source type runs the `git` CLI (`exec.CommandContext(ctx, "git", …)`) and allows `https`, `http` and `git` transports by default. `Dockerfile.konflux` does not install `git` on its `ubi-minimal-pqc` runtime base. Unless the operator adds it, git-backed skill sources will likely fail in the RHOAI image. The default `skill-sources.yaml` is empty (`skill_catalogs: []`).

**API versioning in transition.** The registry serves both `v1alpha3` and `v1` routes from the same service layer. `--alpha-sunset-date` adds RFC 8594 `Deprecation`/`Sunset` headers to v1alpha3. The catalog plugins still mount `v1alpha1` base paths for model, MCP and agent, while `serving_runtime` and `skill` are already `v1`. `api/openapi/catalog-v1.yaml` defines v1 paths for all five catalogs. `CATALOG_ALPHA_SUNSET_DATE` controls catalog deprecation headers.

**Async upload Job and supply chain.** The Job is the only Python runtime artifact and the only one on an AIPCC base (`quay.io/aipcc/base-images/cpu-el9.8`). Its Konflux build is the most hermetic in the repo: RPM lockfile for `skopeo`, pip prefetch from `requirements-aipcc.txt` against the RHOAI AIPCC index, multi-arch binary wheels. After install it deletes `uv`/`uvx` because their bundled aws-lc fails FIPS scanning. It handles cloud credentials (S3 access keys, OCI registry passwords, the registry bearer token) as CLI args or environment variables. These have to arrive through mounted Secrets in the Job spec, which the BFF/operator creates (`batch/v1/Job` and `/v1/Secret` creation in `clients/ui/bff/internal/integrations/kubernetes/shared_k8s_client.go`).

**TLS posture risks.**

- DB client TLS (`internal/platform/tls/config.go`) sets `MinVersion: TLS 1.2` but sets `InsecureSkipVerify: !VerifyServerCert`, and `--embedmd-database-ssl-verify-server-cert` defaults to `false`. When MySQL TLS is enabled without that flag, the server certificate is not verified.
- The InferenceService controller library hard-codes `InsecureSkipVerify: true` when `skipTLSVerify` is set. It validates the registry over HTTPS otherwise.
- The upstream BFF reads the OpenShift `APIServer` `tlsSecurityProfile`, falling back to Intermediate on transient errors. This is a good pattern that the core servers lack, since they serve plain HTTP.

**Kubeflow vs. RHOAI manifests.** `manifests/kustomize` describes the upstream Kubeflow topology: Istio `VirtualService` on `kubeflow-gateway`, `DestinationRule` with `ISTIO_MUTUAL`, `kubeflow` namespace, MySQL/Postgres dev databases with public images (`mysql:8.3.0`, `postgres:17.6`). Only `options/catalog/overlays/rhoai` is RHOAI-specific. The RBAC, Services and VirtualServices the analyzer extracted come from these upstream manifests. They do not show how RHOAI actually exposes the component.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per registry instance. Each ModelRegistry instance is its own `proxy` Deployment with its own database; the catalog is a single shared platform instance | Inferred from `cmd/proxy.go` (single DSN per process) and `options/catalog` (single deployment) |
| **Deployment model** | Registry: one instance per ModelRegistry CR (operator-managed). Catalog: single shared instance with leader election across replicas | `catalog/cmd/catalog.go:220-248` |
| **Tenant identifier** | None in application; access determined by external proxy/RBAC on the instance | `cmd/proxy.go` (no identity handling) |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | External proxy (kube-rbac-proxy/Gateway in RHOAI; Istio AuthorizationPolicy upstream) | Platform | No in-process auth; direct Service access bypasses all checks. Upstream policy was hardened to restrict header-less JWT callers to the `kubeflow` namespace |
| Data storage | Separate DB per registry instance; shared Postgres for catalog | Application / operator | All users of one registry share all its data (no row-level tenancy). Catalog data is global by design |
| Network traffic | Istio mTLS + AuthorizationPolicy (upstream); NetworkPolicy only for controller metrics | Istio / Kubernetes | No NetworkPolicy for registry/catalog Services in this repo |
| Compute & resources | None defined in manifests | -- | No ResourceQuota/limits in base manifests |
| Configuration & secrets | Per-instance DB Secret; catalog Secrets in catalog namespace | Kubernetes | Job credentials passed via env/args; must be Secret-backed by the caller |
| API scoping | Controller watches InferenceServices cluster-wide; maps them to registries by labels (namespace/name labels, URL annotation) | Application | Cluster-wide ISVC get/list/watch/patch |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Model Catalog server + PostgreSQL | None (platform-global catalog) | Read-mostly API; access control by fronting proxy |
| Registry database (per instance) | Registry instance | Separate DSN/database per instance |
