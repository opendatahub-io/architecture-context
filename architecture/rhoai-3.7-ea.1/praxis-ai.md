## Purpose

**Short**: Praxis AI is an AI gateway built on the Praxis proxy (Pingora-based). It classifies, translates, routes and applies policy to OpenAI, Anthropic, MCP and A2A traffic sent to inference and agent backends.

**Detailed**: praxis-ai packages a set of AI-specific HTTP filters and a server binary on top of the upstream [Praxis](https://github.com/praxis-proxy/praxis) proxy runtime. Praxis provides listeners, TLS, load balancing, health checks and the `HttpFilter` framework. Clients keep their provider-native API shape (OpenAI Chat Completions or Responses, Anthropic Messages, MCP JSON-RPC, A2A), and the gateway picks a backend based on API format, model name or MCP tool name. It can translate between protocols, including streaming: Anthropic Messages to Chat Completions, Chat Completions to AWS Bedrock Converse, Azure AI and Vertex Gemini, and Responses to Chat Completions.

Beyond routing, the gateway handles policy and cost: credential injection, prompt enrichment, external guardrails (NeMo Guardrails, Lakera), token counting, token rate limits and ceilings (with an optional Valkey/Redis backend), metering callouts, time-to-first-token metrics and OpenTelemetry. It can also run the experimental stateful OpenAI surfaces itself: Responses persistence and rehydration, the Conversations API, context compaction and an agentic tool loop. This state is stored in PostgreSQL or SQLite. For RHOAI, the notable integrations are the `llmisvc_model_provider_resolver` filter, which rewrites publisher-style model IDs for KServe LLMInferenceService routing, and an optional `llm-d` Envoy `ext_proc` compatibility layer that calls the llm-d Endpoint Picker (EPP) over gRPC.

The project is alpha (pre-1.0). Two images are produced: a standard Alpine image and a FIPS 140-3 build on UBI 9. The FIPS build turns off feature groups whose dependencies carry their own cryptography. Pipelines are defined entirely in a YAML config with filter chains, which can be hot-reloaded. The repo ships no Kubernetes manifests, so whatever deploys it (an operator, a Helm chart or llm-d) supplies the Deployment, Service and config.

## Architectural Analysis

**Layered on an upstream proxy core.** praxis-ai owns only the AI layer. Listener, TLS, load-balancer, admin API and config-reload behaviour come from the `praxis-proxy-*` 0.8.0 crates (Cargo.toml:126-130), which wrap Cloudflare Pingora. So most of the network-facing security surface — TLS termination, mTLS, SNI and the admin endpoints `/healthy`, `/ready` and `/metrics` — is inherited, and has to be assessed together with the Praxis repository. The server crate adds:
- build-time filter auto-discovery: `build.rs` uses `cargo metadata` through `praxis-ai-build-support`
- registration of about 60 AI filters (`filters/src/register.rs`)
- store provisioning and readiness gating
- a filesystem watcher for hot reload

**Features are gated at compile time.** Most capabilities are Cargo features (server/Cargo.toml:24-81). `full` is the default and includes standard filters plus the policy engine. Experimental groups such as `openai-responses`, `openai-conversations`, `openai-agentic-loop`, `store-*`, `azure-ad-filter` and `gcp-adc-filter` are opt-in. This drives the image matrix: standard, `-experimental` (Responses plus SQLite/Postgres stores) and `-fips` (`aws-sigv4-filter` only). If a config names a filter that was not compiled in, startup rejects it. Architects need to know which image variant RHOAI ships, because the available API surface (for example `/v1/responses` and `/v1/conversations`) depends entirely on it.

**One crypto provider, deliberately.** The workspace pins `rustls` and `tokio-rustls` without default features, so aws-lc-rs is not pulled in (Cargo.toml:67-70, 95-98). It uses the `openssl` crate without `vendored` (Cargo.toml:53-55). `praxis_tls::provider::install()` installs a single rustls provider backed by OpenSSL (server/src/lib.rs:150). All TLS, digest and HMAC work therefore goes through the system `libcrypto`. The analyzer saw `ring` and `aws-lc-rs` in Cargo.lock. Per docs/fips.md they are test-only (`rcgen` with ring) or come in with the policy engine. The FIPS build excludes both and checks the result with `cargo auditable` plus Red Hat's `check-payload` scanner. `PRAXIS_REQUIRE_FIPS=1` makes startup fail closed: it refuses to start unless the provider, the kernel and the system crypto policy all report FIPS, and the standard build refuses the variable outright.

**Trust boundaries are defined by headers.** Identity and tenancy are not authenticated by praxis-ai itself (except the experimental `basic_auth` filter). The `state_owner` filter consumes assertions such as `x-auth-tenant` and `x-auth-user` from a trusted upstream authenticator and strips the inbound copies (apis/src/state_owner.rs:1-8). `identity_header_guard` prevents spoofing. Deployments must make sure untrusted clients cannot reach the listener directly — a significant integration risk when it sits behind a Gateway or kube-rbac-proxy. Provider-route chains require downstream mTLS with SPIFFE peer identity (`peer_identity_trust`) as the first filter.

**Outbound callouts are hardened against SSRF.** Every callout — guardrails, metering, web or file search, MCP, Azure AD and GCP ADC token fetch, `http_callout` — resolves the target once and rejects any private, loopback or link-local address unless a filter-specific opt-in is set. Cloud metadata addresses are always rejected (GCP ADC excepted). Redirects are not followed and URL userinfo is rejected (docs/architecture/outbound-callouts.md). Production callouts use the shared Pingora `SubRequestClient`, so they inherit the same TLS provider. `reqwest` is dev/test-only (Cargo.toml:61-65).

**Risks and observations.**
1. Alpha software. APIs, config and the store schema may change before 1.0.
2. The certificate-only Postgres store depends on a temporary fork pin of SQLx (`praxis-proxy/sqlx@637e7025`, Cargo.toml:88). This is a supply-chain item to track.
3. The `llm-d` ext_proc layer adds a gRPC hop and a separate failure domain. Its own crate documentation calls it an anti-pattern, kept only because the llm-d EPP speaks ext_proc.
4. The default config binds `127.0.0.1` for both the proxy and the admin port (server/src/default.yaml:14,18). Any real deployment must supply a config that binds externally.
5. No Konflux Dockerfile, RPM lockfile or Hermeto configuration exists on this branch. The downstream build definition lives elsewhere.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Trusted-header identity via `state_owner`; `identity_header_guard` strips spoofed headers | Application (relies on upstream authenticator) | If clients can bypass the authenticator and reach the listener, identity can be forged |
| Data storage | Shared DB; all rows keyed by `tenant_id`, `owner_issuer`, `owner_subject` (primary keys and indexes) | Application | Single shared Postgres/SQLite; isolation relies on query filtering |
| Network traffic | None in-repo; SSRF guards on outbound callouts | Application | NetworkPolicy left to the deployer |
| Compute & resources | Token rate limits and ceilings keyed by header, IP or model; inflight tracking | Application | Shared process; no per-tenant compute isolation |
| Configuration & secrets | Single process config; credentials per chain/route | Application | Config is shared across tenants |
