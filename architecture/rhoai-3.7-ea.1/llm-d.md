## Purpose

**Short**: llm-d is the top-level repository of the llm-d distributed inference stack. It holds the "well-lit path" deployment guides, reusable Kustomize/Helm recipes, auxiliary container images, and architecture docs for serving LLMs with vLLM/SGLang behind the llm-d Router on Kubernetes.

**Detailed**: llm-d is a CNCF Sandbox project, founded by Red Hat, Google Cloud, IBM Research, CoreWeave, and NVIDIA. It adds LLM-aware orchestration on top of model servers (vLLM, SGLang, TensorRT-LLM, Atom): prefix-cache and load-aware routing, tiered and precise KV-cache management, prefill/decode (P/D) disaggregation, wide expert parallelism, flow control and multi-tenant QoS, autoscaling, and batch/async processing. The runtime code for each piece lives in separate repositories (`COMPONENTS.md`): `llm-d-router` (EPP, coordinator, disaggregation sidecar), `llm-d-kv-cache`, `llm-d-routing-sidecar`, `llm-d-async`, `llm-d-batch-gateway`, `llm-d-latency-predictor`, and `llm-d-workload-variant-autoscaler`. This repository contains none of that runtime source.

What this repository provides:

1. **`guides/`**: about 30 guides (optimized-baseline, pd-disaggregation, wide-ep, precise-prefix-cache-routing, tiered-prefix-cache, flow-control, workload-autoscaling, fast-model-actuation, agentic-api, batch-serving, rollouts, and others). Each guide covers a matrix of accelerators and model servers, with overlays for providers such as base Kubernetes, GKE, OpenShift (`ocp`), CoreWeave, and AMD CI.
2. **`guides/recipes/`**: shared building blocks. These include router Helm values, Gateway variants, modelserver bases (Deployment, LeaderWorkerSet, DisaggregatedSet), image-pin Kustomize components, monitoring/tracing/alerting, and the KEDA metrics-reader auth bundle.
3. **`docker/`**: three Dockerfiles for CPU vLLM, Intel XPU vLLM+LMCache, and RDMA/NCCL network diagnostics, plus build helper scripts and a GKE pod-snapshot launcher.
4. **`helpers/`**: an interactive debug pod, Mooncake store/client manifests, and client setup docs.
5. **`docs/`, `proposals/`**: architecture and API reference docs, and feature proposals.

In RHOAI, KServe's `LLMInferenceService` controller deploys llm-d (overlay 0011). It uses RHAIIS AIPCC-built vLLM images and the downstream `llm-d-router` images; the upstream images built here are not used (overlay 0019). For RHOAI architects, this repo matters as the reference for llm-d topology, the default flags, ports, and header contracts that KServe mirrors, and as the upstream source for the `llm-d.ai` and InferencePool resource shapes.

## Architectural Analysis

**Composition, not code.** The repository applies llm-d's principle that components connect at API boundaries. Every guide follows the same three-layer structure. (1) A **Router** is installed from an external Helm chart (`oci://ghcr.io/llm-d/charts/llm-d-router-standalone` or `llm-d-router-gateway`, `guides/env.sh:36-37`) and configured with `guides/recipes/router/base.values.yaml` plus a guide-specific values file. (2) A **model server** is applied with `kubectl apply -k` from a provider/accelerator/engine overlay that patches a shared base from `recipes/modelserver/base`. (3) An optional **Gateway** comes from `recipes/gateway/<provider>`. Model-server pods are joined to the router's InferencePool by labels (`llm-d.ai/guide`, `llm-d.ai/role`, `llm-d.ai/inference-serving`). Placeholder images such as `REPLACE_MODEL_SERVER_IMAGE` are resolved by Kustomize components under `recipes/modelserver/components/images/*`. This keeps image pins in one place: GPU vLLM is `docker.io/vllm/vllm-openai:v0.31.0`, and the routing sidecar and coordinator are `ghcr.io/llm-d/...:v1.0.0`.

**Two router modes.** In *standalone* mode, the EPP pod carries an Envoy sidecar (default; `--concurrency 8 --log-level warn`) or an agentgateway sidecar that receives client traffic directly and calls the EPP via ext-proc over localhost. In *gateway* mode, a Gateway API implementation (Istio, agentgateway, GKE, NGINX Gateway Fabric, Envoy AI Gateway, or the deprecated kgateway) fronts an HTTPRoute whose backend is an `InferencePool`. `inferencePool.failureMode: FailOpen` is the base default, so if the EPP is unavailable the gateway still forwards traffic and routing degrades to non-LLM-aware rather than failing (`recipes/router/base.values.yaml:18-19`). On OpenShift, only Istio is a supported GatewayClass (overlay 0023). The kgateway and agentgateway OpenShift recipes exist but are not support statements. The kgateway recipe is marked deprecated in-tree.

**Disaggregation topology.** For P/D, the shared base is a `DisaggregatedSet` (`disaggregatedset.x-k8s.io/v1`, LWS-backed) with prefill and decode roles (`recipes/modelserver/base/single-host/pd-disaggregatedset/base/disaggregatedset.yaml`). On decode pods, the routing proxy runs as a native sidecar (an init container with `restartPolicy: Always`) on port 8000 and fronts vLLM on 8200. KV transfer uses NIXL on port 5600/TCP, in practice over RDMA/RoCE. The OpenShift P/D overlay requests SR-IOV VFs and `rdma/roce_gdr`, adds the `IPC_LOCK`, `SYS_RAWIO`, `NET_ADMIN`, and `NET_RAW` capabilities, and mounts a node hostPath model cache (`guides/pd-disaggregation/modelserver/gpu/vllm/ocp/kustomization.yaml`). These are significant privilege escalations compared with the aggregated baseline. Multi-host serving uses `LeaderWorkerSet`. An experimental Coordinator alternative replaces the per-pod sidecar with a standalone service on 8080/TCP.

**Security posture is "reference, not hardened."** Several defaults in the guides favor ease of use over defense in depth:
- The routing sidecar consistently runs with `--secure-serving=false`, so prefill/decode hops are plaintext HTTP.
- The base Gateway listens on plain HTTP port 80 with `allowedRoutes.namespaces.from: All`.
- Router Prometheus scraping disables auth (`monitoring.values.yaml`).
- The Kimi K3.1 guide sets `insecureSkipVerify: true` for metrics scraping.
- No NetworkPolicies are shipped.
- The coordinator HTTPRoute documents a header-spoofing bypass (`x-llm-d-epp-profile`).

The repo does show good patterns in places. ModelExpress uses strict Istio mTLS plus an AuthorizationPolicy allow-list. Modelserver ServiceAccounts set `automountServiceAccountToken: false`. The OpenShift agentgateway parameters drop all capabilities and use a read-only root filesystem with `runAsNonRoot` and a RuntimeDefault seccomp profile. On OpenShift, KEDA authenticates to Thanos over HTTPS with a bearer token, and service-ca injects the CA. Because KServe generates the RHOAI deployment, these upstream defaults are not necessarily what RHOAI ships, but they are the baseline KServe starts from.

**Image strategy and productization gap.** On this branch there are no Konflux Dockerfiles, no `rpms.lock.yaml`, and no Hermeto configuration, so the repo follows a purely upstream GitHub Actions build (`.github/workflows/build-image.yaml`, Trivy SARIF scan). `Dockerfile.cpu` builds vLLM v0.30.0 from source on `ubuntu:25.10`. Its line 1 comment still says "Ubuntu 22.04", which is stale. It installs `uv` with `curl | sh` and uses `UV_INDEX_STRATEGY=unsafe-best-match` against the PyTorch CPU index. `Dockerfile.xpu` is a thin layer over `vllm/vllm-openai-xpu:v0.30.0` that adds the Intel oneAPI compiler and LMCache v0.5.0. `Dockerfile.rdma-tools` uses NVIDIA CUDA UBI9 images. Compared with the RHOAI 3.6 snapshot, `Dockerfile.rocm` has been removed: vLLM image builds were moved upstream, and guides now consume `docker.io/vllm/vllm-openai*` images directly. None of these images is used downstream. RHOAI substitutes RHAIIS AIPCC images (overlay 0019), so FIPS and hermeticity gaps here do not apply to RHOAI's runtime images.

**Multi-tenancy is application-level QoS inside a namespace.** Each guide deploys into one namespace, such as `llm-d-optimized-baseline`. Tenancy within a shared pool is handled by EPP flow control. Requests are classified by `x-llm-d-inference-fairness-id` and `x-llm-d-inference-objective`, and `InferenceObjective` priorities set the priority bands. That gives fairness and priority, not isolation, and the headers are client-controlled. Cluster-scoped objects, such as the `keda-epp-metrics-reader-monitoring-view` ClusterRoleBinding and the `fma-node-viewer` ClusterRole, collide when the same guide is deployed to multiple namespaces. The recipe calls this out explicitly (`recipes/autoscaling/metrics-reader/clusterrolebinding.yaml:5-9`).

### Tenant Model

| Aspect | Value | Source |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | None on inference path in guides; namespace-scoped SAs with token automount disabled | Platform (delegated) | Tenant and priority headers are client-controlled and unauthenticated; any caller can claim premium priority |
| Data storage | Per-namespace PVCs (model cache), emptyDir caches; shared KV cache across tenants in one pool | Kubernetes / Application | Prefix-cache sharing across tenants within a pool (timing side-channel potential) |
| Network traffic | No NetworkPolicy; Gateway `allowedRoutes.from: All`; Istio mTLS only for ModelExpress | Kubernetes / Istio (partial) | Any namespace can attach routes to the shared Gateway; plaintext P/D traffic |
| Compute & resources | Pod requests/limits per model server; EPP priority bands and fairness policy | Application (EPP) | No ResourceQuota/LimitRange; fairness is scheduling-level only |
| Configuration & secrets | Per-namespace `llm-d-hf-token` and other Secrets | Kubernetes | Cluster-scoped bindings (metrics-reader, fma-node-viewer) collide across multi-namespace installs |
| API scoping | InferenceObjective looked up in the InferencePool namespace | Application (EPP) | Interactive-pod Role can read Secrets and write RBAC in its namespace |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| vLLM model-server pool (InferencePool) | Fairness ID / priority band | EPP flow-control queues (application-level) |
| llm-d-inference-gateway | None (all namespaces) | None beyond Gateway API route attachment |
| Redis (async multitenant), PostgreSQL (agentic-api) | Guide namespace | Application keys; no per-tenant DB isolation |
| OTel collector / Prometheus | Namespace labels | Query-level filtering only |
