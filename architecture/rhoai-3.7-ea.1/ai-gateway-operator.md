## Purpose

**Short**: A module operator that reconciles the cluster-scoped `AIGateway` singleton CR and installs, upgrades, tears down and reports status for four AI Gateway sub-components: llm-d batch gateway, Models-as-a-Service (maas-controller), ai-gateway-controller, and Praxis AI Grid.

**Detailed**: ai-gateway-operator is a "module operator" in the ODH/RHOAI modular-operator design (RHAISTRAT-1064). The platform operator (opendatahub-operator / rhods-operator) deploys it from this repo's own kustomize tree (`config/manifests/ai-gateway-operator/overlays/rhoai`) into `redhat-ods-applications`. From then on it owns the `AIGateway` CR (`components.platform.opendatahub.io/v1alpha1`, cluster-scoped, which must be named `default-aigateway`). The spec has three toggles, `batchGateway`, `modelsAsAService` and `aiGrid`. Each is `Managed` or `Removed` and defaults to `Removed`.

The operator does no data-plane work and serves no traffic apart from probes and metrics. Its job is lifecycle orchestration. It reuses the opendatahub-operator reconciler framework (`reconciler.ReconcilerFor`, kustomize render, server-side-apply deploy, GC and status actions). The image bundles each sub-component's manifests, vendored and pinned under `config/manifests/<component>/`. At startup the operator substitutes `RELATED_IMAGE_*` values into each tree's `params.env`, and it renders only the trees whose toggle is `Managed`. With `modelsAsAService` enabled it deploys maas-controller and its sibling ai-gateway-controller. Those vendored manifests bring a large set of Kuadrant, Istio, Gateway API, cert-manager, monitoring and OpenTelemetry resources, plus a ValidatingWebhookConfiguration. With `batchGateway` enabled it deploys the llm-d-batch-gateway-operator. With `aiGrid` enabled it installs the five `grid.praxis.fast` CRDs and runs grid-operator in its own namespace (`redhat-ai-grid` on RHOAI).

The operator reports status back to the platform. It sets per-sub-module conditions (`ModelsAsAServiceReady`, `BatchGatewayReady`, `AIGridReady`, `TenantsHealthy`, `DeploymentsAvailable`) and fills `status.module` (version, build source, platform, rendered sources). It also implements the platform upgrade handshake: it echoes `data.platformVersion` from the `odh-aigateway-config` ConfigMap into `status.releases[name=platform]`, and only after a reconcile succeeds.

## Architectural Analysis

**A module operator that mostly deploys other operators.** Nearly all of the reconcile behaviour comes from the opendatahub-operator library pipeline (`internal/controller/aigateway/aigateway_controller.go:183-263`). The pipeline runs, in order: initialize, infra-RBAC, upgrade, releases, kustomize render, AI Grid render, annotate, selector migration, deploy (SSA, ordered), deployment status, sub-module status, condition override, report status, and GC. Repo-specific code is mainly the `initialize` action (picks manifest trees by toggle), MaaS teardown coordination, selector migration for maas-controller Deployments created by the old standalone `modelsasservice` component, and per-sub-module status aggregation. The `upgrade()` hook is currently a no-op (`aigateway_upgrade.go`).

**The RBAC is very broad, and that is by design.** Kubernetes prevents RBAC escalation: an operator cannot create a ClusterRole that grants more than it already holds. So ai-gateway-operator's `manager-role` must hold the union of every rule in every vendored sub-component ClusterRole. The kubebuilder markers say this explicitly ("Cluster-wide rules (no resourceNames) are required for escalation", `aigateway_controller.go:121-123`). The result is a cluster-wide grant of about 76 rules. It covers secrets (create/delete/get/list/patch/watch), cluster-wide ClusterRole/ClusterRoleBinding update/patch/delete (`aigateway_controller.go:164`), `serviceaccounts/token` create, ValidatingWebhookConfigurations, CRDs, and Kuadrant/Istio/Gateway API policy objects. Some rules are narrowed with `resourceNames`, for example the CRDs and named ClusterRoles. The unrestricted ClusterRole update rule cancels out much of that narrowing. Treat this operator's ServiceAccount as highly privileged: compromising it effectively grants cluster-admin-equivalent RBAC manipulation.

**Vendored manifests are a supply-chain and drift boundary.** Sub-component manifests are fetched by `hack/scripts/get-manifests.sh` and committed. Each component pins an ODH ref (`main` or `stable`) and an RHDS ref (`rhoai-3.6@...`). The README says nothing in the repo sets `ODH_PLATFORM_TYPE`, so in practice the vendored trees come from the ODH refs, even on this RHOAI branch. Downstream-only manifest fixes on `rhoai-3.x` branches therefore do not reach this image. The RHDS pins still point at `rhoai-3.6` while this branch is `rhoai-3.7-ea.1`. Several `params.env` defaults use `odh-stable` tags or an upstream `ghcr.io/praxis-proxy/grid-operator:v0.3.0-rc.4` image. These are expected to be replaced at runtime by `RELATED_IMAGE_*` env vars injected by the platform operator (`aigateway.go:100-125`). If a variable is missing, the upstream default stays in place.

**MaaS teardown is a cooperative protocol.** Setting `modelsAsAService: Removed` does not delete MaaS straight away. The operator annotates the maas-controller Deployment with `maas.opendatahub.io/teardown-requested=true`. It keeps the MaaS and ai-gateway-controller manifests rendered until maas-controller sets `maas.opendatahub.io/teardown-completed=true` on its own Deployment. Only then do GC and the infra-namespace RBAC cleanup proceed (`aigateway_remove.go`, `aigateway_infra_rbac.go`). The infra namespace (`redhat-ai-gateway-infra`) and the `maas-db-config` secret are intentionally kept so MaaS can be re-enabled without reprovisioning. AI Grid CRDs are never deleted on `Removed` (no delete verb; the GC predicate skips `*.grid.praxis.fast`).

**Namespaces span several tenancy domains.** The operator itself runs in the applications namespace. It also creates and labels the infra namespace (MaaS API and Postgres secrets) and the AI Grid namespace. The vendored MaaS policy `gateway-default-deny` targets `openshift-ingress` / `maas-default-gateway`, although per the kustomization comment it is applied separately by deploy.sh and is not part of the `default` render. The manager cache watches the applications namespace plus all namespaces (`cmd/operator/operator.go:114-119`), so its informers are effectively cluster-wide.

**Network exposure of AI Grid.** The vendored grid-operator overlay contains two `LoadBalancer` Services, `grid-operator-swim` (7946/UDP, SWIM gossip) and `grid-operator-signals` (9091/TCP). Their annotations ask for *internal* load balancers on GKE, AWS and Azure. No such annotation exists for bare-metal or other OpenShift providers, so on those platforms these Services could get externally reachable addresses. This needs review whenever `aiGrid: Managed`.

**TLS posture is a strength.** Metrics are served over HTTPS (`:8443`) with controller-runtime authn/authz filters (TokenReview/SubjectAccessReview). TLS settings come from the OpenShift APIServer TLS profile and adherence policy (`internal/tls/profile.go`), with Intermediate as the fallback. RC4 and TLS 1.3 IDs are filtered out of the explicit cipher list. A `SecurityProfileWatcher` restarts the process gracefully when the profile changes. The Konflux build is FIPS-oriented (CGO + `strictfipsruntime`, `ubi-minimal-pqc`) and hermetic for Go modules.

### FIPS Compliance

FIPS compliance has two layers: **build-time enforcement** (check-payload validation in Konflux) and **application-level crypto correctness** (what the code actually does with cryptography). Both must be documented.

#### Build-Time FIPS (check-payload gate)

Konflux validates images via [check-payload](https://github.com/openshift/check-payload), which enforces:
- Go binaries must be **dynamically linked** (CGO_ENABLED=1, no static linking)
- **OpenSSL must be installed** in the container image
- No statically linked Go crypto (pure-Go crypto / BoringCrypto static gets rejected)

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | `CGO_ENABLED=1` (ARG default) + `GOEXPERIMENT=strictfipsruntime`. No `-tags strictfipsruntime`; `make build-bin` is plain `go build -ldflags`. | Dockerfile.konflux:4,34-36; Makefile:138-142 |
| **Linking** | Dynamic (CGO) in the Konflux build. The upstream `Dockerfile` builds static `CGO_ENABLED=0` on ubi10-micro, which is not FIPS-suitable and not used by Konflux. | Dockerfile.konflux:34; Dockerfile:41 |
| **OpenSSL in image** | Yes, via `registry.redhat.io/ubi9/ubi-minimal-pqc:9.8` base | Dockerfile.konflux:40 |
| **OLM FIPS annotation** | Not present (no CSV/bundle in repo; delivered via platform operator) | N/A |

#### Application-Level Crypto

check-payload is the bare minimum -- it validates build artifacts but not runtime behavior. Document what the application actually does with cryptography:

| Aspect | Value | Source |
|--------|-------|--------|
| **TLS configuration** | `crypto/tls` metrics server configured from the OpenShift APIServer TLS profile via `controller-runtime-common`. Intermediate profile when unavailable or when adherence is `NoOpinion`/`LegacyAdheringComponentsOnly`. Min TLS 1.2 default. | **Non-FIPS crypto risks** | None detected. `hash/fnv` is used only to shorten derived namespace names (not security-relevant). No InsecureSkipVerify, MD5, SHA1 or JWT usage. ### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | One shared operator SA with a broad cluster-wide ClusterRole. AIGateway admin/editor/viewer roles for users. | Kubernetes | The SA can modify any ClusterRole/Binding and any Secret cluster-wide (needed for RBAC escalation), so compromise breaks every tenant boundary. |
| Data storage | None in the operator. MaaS DB secret lives in a separate infra namespace with narrowly scoped migration RBAC. | Kubernetes | `maas-db-config` survives MaaS removal by design. |
| Network traffic | No NetworkPolicy shipped for the operator in the platform deploy tree (only `config/network-policy` for standalone dev). Sub-components ship their own metrics NetworkPolicies. | Kubernetes | AI Grid LoadBalancer Services may be externally reachable on providers without internal-LB annotations. |
| Compute & resources | Operator limits 500m CPU / 512Mi (GOMEMLIMIT 410MiB). No quotas. | Kubernetes | N/A |
| Configuration & secrets | Operator config ConfigMap in the applications namespace. Secrets/ConfigMaps read uncached. | Kubernetes / Application | N/A |
| API scoping | Cache scoped to the applications namespace plus all namespaces (cluster-wide). GC limited to the applications namespace (`gc.InNamespace`). | Application | Cluster-wide informers. AI Grid resources live in a separate namespace, outside GC namespace scoping (handled by the explicit grid render). |
