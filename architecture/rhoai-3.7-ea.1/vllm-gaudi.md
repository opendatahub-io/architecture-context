## Purpose

**Short**: Intel Gaudi (HPU) hardware plugin for vLLM, packaged by RHOAI as the `odh-vllm-gaudi-rhel9` model-serving runtime image.

**Detailed**: `vllm-gaudi` is the out-of-tree vLLM hardware plugin for Intel Gaudi AI accelerators (HPUs). It follows vLLM's pluggable-hardware RFC: the Python package `vllm_gaudi` registers itself through setuptools entry points (`vllm.platform_plugins` → `hpu = vllm_gaudi:register`, plus `vllm.general_plugins` for custom utils, ops and models). When vLLM starts, it discovers the plugin and loads `HpuPlatform` (`device_name="hpu"`, `dispatch_key="HPU"`). The plugin provides HPU attention backends, fused MoE, quantization kernels (FP8, GPTQ, AWQ, compressed-tensors, ModelOpt), LoRA, Mamba/SSM ops, a device communicator, NIXL KV-transfer connectors for disaggregated prefill/decode, and CPU↔HPU KV offload.

In RHOAI the repo builds one product image, `rhoai/odh-vllm-gaudi-rhel9`, from `Dockerfile.konflux.gaudi`. The image runs `python3 -m vllm.entrypoints.openai.api_server`, the upstream vLLM OpenAI-compatible HTTP server, on Gaudi hardware. KServe deploys it as a model-serving runtime. The repo itself has no Kubernetes manifests, CRDs, Services or RBAC; ServingRuntime templates for this image are owned by other platform components (e.g. KServe or the ODH model controller / dashboard templates).

The downstream fork tracks upstream `vllm-project/vllm-gaudi` (Intel). The README states that version 0.16.0 is built on vLLM 0.16.0 and is compatible with Intel Gaudi software 1.23.0, which matches the Dockerfile defaults (`SYNAPSE_VERSION=1.23.0`, `SYNAPSE_REVISION=695`, `PT_VERSION=2.9.0`).

## Architectural Analysis

**Plugin, not fork-of-vLLM.** The code in this repository is purely an accelerator backend. All network-facing behaviour (HTTP API, auth flags, TLS options, metrics) comes from upstream vLLM, which the image installs at build time with `VLLM_TARGET_DEVICE=empty`. vllm-gaudi is then layered on top with `VLLM_TARGET_DEVICE=hpu`. The plugin hooks in via entry points (`setup.py:63-70`). Op registration is mostly unconditional; the heterogeneous-layout NIXL connector is only imported when `VLLM_HPU_HETERO_KV_LAYOUT=true` (`vllm_gaudi/__init__.py:22-23`).

**The Konflux image does not build from the checked-out source.** `Dockerfile.konflux.gaudi` (byte-identical to `Dockerfile.hpu.ubi`) runs `git clone https://github.com/vllm-project/vllm-gaudi.git` and `git clone https://github.com/vllm-project/vllm.git` at build time (lines 196, 206), then checks out tags `v0.16.0` (from `.konflux/build-args.conf`). The shipped plugin code is therefore upstream Intel `v0.16.0`, not the contents of this downstream branch. Downstream patches committed here would not reach the product image. This is a significant provenance and supply-chain observation.

**Non-hermetic, multi-origin build.** The build pulls from: UBI 9.6 (`registry.access.redhat.com/ubi9/ubi:9.6`), CentOS Stream 9 mirrors (AppStream/CRB/BaseOS), EPEL, Habana's `vault.habana.ai` artifactory (RPMs, GPG key, PyTorch modules tarball and `install.sh`), public PyPI (`https://pypi.org/simple/`) and GitHub. The Tekton pipeline sets `hermetic: false` and there are no `rpms.lock.yaml`, Python lock files or Hermeto prefetch configs. The image does not use AIPCC base images, even though overlay 0017 lists an Active AIPCC Intel Gaudi variant (1.24.1, x86_64).

**FIPS is explicitly disabled.** Stage 1 runs `rpm -e --nodeps openssl-fips-provider-so` (line 63; commented "Remove FIPS provider"). The resulting image cannot operate in FIPS mode. This is the most important security finding for this component.

**Runtime posture.** The image runs as UID 2000, GID 0, with group-writable `/workspace`, `/home/vllm`, `/usr/src` and `/var/log/habana_logs`, which suits OpenShift's arbitrary-UID model. Build is `linux/x86_64` only. There are no probes, Service or port declarations in-repo; the vLLM server defaults to port 8000/TCP over plain HTTP unless the deployer passes `--ssl-*` and `--api-key` flags.

**Other Dockerfiles** under `.cd/` (Ubuntu/RHEL dev and benchmark images, NIXL variant, docker-compose) and `tests/pytorch_ci_hud_benchmark/Dockerfile.hpu` are upstream developer/CI artifacts and are not built by Konflux.
