## Purpose

**Short**: A collection of containerized evaluation-framework adapters (LightEval and Inspect AI are productized in RHOAI) that eval-hub launches as Kubernetes Jobs to benchmark OpenAI-compatible model endpoints.

**Detailed**: eval-hub-contrib holds community-contributed "framework adapters" for the eval-hub evaluation service (TrustyAI / EvalHub in RHOAI). Each adapter under `adapters/<framework>/` implements the `FrameworkAdapter` pattern from `eval-hub-sdk` (`evalhub.adapter`). An adapter consists of a `main.py` entrypoint, a `provider.yaml` catalog entry (benchmarks, metrics, primary scores, runtime resource requests) and a container build. The upstream repo carries 17 adapters (LightEval, Inspect AI, GuideLLM, MTEB, RAGAS, DeepEval, RULER, SWE-bench, ToolEval, promptfoo, WildGuard, IFBench, FollowBench, NeMo Guardrails, IBM CLEAR, DataBench, ATIF) plus an eval-hub post-processor and example `collections/`.

On the RHOAI `rhoai-3.7-ea.1` branch only **two adapters are productized**. Both have Konflux Dockerfiles and Tekton push pipelines: **LightEval** (`odh-eval-hub-lighteval-rhel9`) and **Inspect AI** (`odh-eval-hub-inspectai-rhel9`). The other adapters build only from upstream `Containerfile`s on `ubi9/python-31x` for `quay.io/evalhub/community-*`. They are present in the source tree but are not RHOAI deliverables on this branch.

At runtime, the eval-hub service creates a Job pod for each benchmark run. The pod mounts the job spec at `/meta/job.json`, optionally mounts staged test data at `/test_data` and model credentials at `/var/run/secrets/model`, and runs alongside an eval-hub sidecar on `localhost:8080`. The adapter reads the job spec and runs the framework (LightEval CLI / `inspect eval` subprocess) against the model endpoint, which is usually reached through the sidecar. It then reports `JobPhase` status and final results back through SDK callbacks. Where configured, it also saves metrics and artifacts to MLflow and pushes result files as OCI artifacts.

## Architectural Analysis

**Job-per-benchmark adapter pattern, no server surface.** The productized images expose no listener (`io.openshift.expose-services=""`). Each container is a one-shot process: `python main.py` loads the `JobSpec`, emits `INITIALIZING → LOADING_DATA → RUNNING_EVALUATION → POST_PROCESSING → [PERSISTING_ARTIFACTS]` through `callbacks.report_status()`, and ends with `callbacks.report_results()`, which emits `COMPLETED`. The process exits 0 on success and 1 on failure. All control-plane concerns sit in eval-hub, outside this repo: scheduling, RBAC, secret projection, sidecar injection, the result store and the MLflow/OCI credentials. This repo is pure workload code plus catalog metadata (`provider.yaml`). The adapters' contract with eval-hub runs through `eval-hub-sdk` 1.0.7 (`DefaultCallbacks`, `resolve_model_credentials`, `read_model_auth_key`, `MlflowFileArtifact`, `OCIArtifactSpec`).

**Sidecar-mediated credentials.** The adapters avoid holding real model credentials where possible. LightEval points LiteLLM at the sidecar (`model.url`, normally `http://localhost:8080`, with `/v1` appended). It passes a *reference token* from `resolve_model_credentials()` as `api_key`, or `dummy` when none is set, and the sidecar swaps in the real key or the pod's ServiceAccount token (`adapters/lighteval/main.py:520-536`). Inspect AI uses the same approach for judge credentials (`judge_api-key`, `judge_url` via `read_model_auth_key`). It explicitly ignores sidecar placeholder tokens when resolving `HF_TOKEN` from `/var/run/secrets/model/hf-token` (`adapters/inspect/_hf_auth.py`). Some paths still put raw keys into subprocess environment variables: `OPENAI_API_KEY`, `ANTHROPIC_API_KEY`, and `OPENAI_JUDGE_API_KEY` for StrongREJECT. The `api_key` / `anthropic_api_key` job parameters are also accepted as fallbacks, which means credentials can end up persisted in the job spec. The code redacts `"api_key"` in logged command strings (`_API_KEY_RE` in `adapters/inspect/_execution.py:47`).

**Disconnected-environment posture is partial.** Both adapters can run Hugging Face in offline mode when eval-hub stages data under `/test_data`: `HF_HUB_OFFLINE=1`, with a writable cache at `/data/huggingface` (`_hf_offline.py`). Inspect adds a fail-fast network pre-flight that probes `huggingface.co`, GitHub raw URLs (BFCL, CyberSecEval) and any extra hosts before starting. This turns silent retry loops into clear errors (`adapters/inspect/_preflight.py`). However, the Konflux Inspect build runs with `NLTK_AIRGAP=true` and an empty `nltk-data-airgap/`, deliberately, because the Punkt models carry no redistribution licence. As a result the RHOAI Inspect image ships **without** NLTK data, and the `makemesay` benchmark needs runtime egress or a volume mount. Many inspect-evals tasks also download datasets at runtime. Telemetry is disabled (`INSPECT_NO_TELEMETRY=1`).

**Supply chain.** Both Konflux builds are hermetic (`hermetic: true`) and Hermeto-prefetch pip wheels for four architectures (x86_64, aarch64, ppc64le, s390x). They build FROM digest-pinned AIPCC CPU base images, and Renovate keeps the digests current. Both lockfiles resolve from the Red Hat curated AI Python index, but they differ in rigor:
- Inspect's `requirements-rhoai.txt` is fully hash-pinned (244 `--hash` entries) against the **production** `console.redhat.com/.../rhoai/3.6/cpu-ubi9` index. Its header documents a sha256 divergence on `packages.redhat.com` for four packages.
- LightEval's `requirements-rhoai.txt` pins versions but carries **no hashes**. It installs with `--no-deps` to keep an NLTK security override that conflicts with `lighteval==0.13.0`'s own pin.

Neither Dockerfile installs RPMs, so the absence of an `rpms.lock.yaml` is not a gap here. Both images remove `uv` after install, because it is build-only tooling inherited from the base.

**Hardening observations.** Both Konflux Dockerfiles run `chmod -R 777 /tmp` and make `/opt/app-root`, including site-packages, group-writable (`chown -R 1001:0`, `g+rwX`). This lets LightEval and Inspect write caches at runtime, but a compromised evaluation, for example via a malicious dataset or untrusted model-generated code, could modify installed packages for the rest of that pod's life. The impact is bounded because pods are short-lived Jobs. LightEval wraps code-execution benchmarks with a memory cap (`lighteval_memory_cap.py`). It also patches LiteLLM's loglikelihood path and turns off LiteLLM's response cache (`lighteval_logprob_patch.py`).

**Non-productized manifests in the tree.** The only Kubernetes manifests in the repo are *examples* for non-productized adapters. They are not installed by the operator.
- `adapters/swebench/rbac.yaml`: a Role allowing `batch/jobs` create/get/list/delete and `pods`, `pods/log` get/list, bound to `evalhub-evalhub-opendatahub-job`, plus a ClusterRoleBinding to the `anyuid` SCC.
- `adapters/tooleval/tool-server/deploy.yaml`: a `toolbench-server` Deployment, ClusterIP Service and NetworkPolicy.

The SWE-bench example is architecturally notable. It requires granting the shared eval-hub job ServiceAccount `anyuid` SCC and the ability to spawn child Jobs, which is a privilege escalation that admins apply by hand per tenant namespace.

**Upstream flow.** Lineage is `eval-hub/eval-hub-contrib` → `opendatahub-io/eval-hub-contrib` (an hourly `sync-upstream.yml` merges upstream `main`) → `red-hat-data-services/eval-hub-contrib` (release branches with `Dockerfile.konflux`, `requirements-rhoai*.txt` and Tekton pipelines synced from `konflux-central`).

| Compute & resources | `runtime.k8s` requests/limits per provider; LightEval code-exec memory cap | Kubernetes / Application | -- |
| Configuration & secrets | Per-job projected secret at `/var/run/secrets/model`; per-job JobSpec ConfigMap | Kubernetes (eval-hub) | Job-param API keys may persist in JobSpec |
| API scoping | N/A (adapters do not call the Kubernetes API, except the SWE-bench example) | -- | -- |
