## Purpose

**Short**: ModelExpress is a model-weight distribution control plane. A gRPC coordinator server brokers model-cache and P2P (NIXL/RDMA) source metadata so that inference replicas can load weights from peers or shared caches instead of cold-pulling them. A Rust operator deploys and secures that server through the `ModelExpressServer` CR.

**Detailed**: ModelExpress ("Dynamo ModelExpress", upstream `ai-dynamo/modelexpress` by NVIDIA) targets LLM cold-start latency. When an inference runtime (vLLM, SGLang, TensorRT-LLM, NVIDIA Dynamo, llm-d) starts, its ModelExpress client library asks the coordinator where a compatible copy of the weights already lives. If a serving peer has one, weights move GPU-to-GPU over NIXL RDMA. Other paths are a server-coordinated shared disk cache, ModelStreamer, GPUDirect Storage, or the engine's native loader. The coordinator handles metadata only. Weight bytes stay on the data plane between peers, storage and GPUs.

The repository is a Cargo workspace. `modelexpress-server` is a tonic gRPC server exposing Model, P2P, Refit, RefitCollective, Api and Health services. It persists source and cache metadata in either Redis or Kubernetes CRDs (`ModelMetadata`, `ModelCacheEntry` in `modelexpress.nvidia.com`), and can download models from HuggingFace, NGC, or S3 into a PVC-backed cache. `modelexpress-operator` and its OpenShift build, `modelexpress-operator-openshift`, reconcile a namespaced `ModelExpressServer` CR (`modelexpress.opendatahub.io/v1alpha1`). From it they produce a Deployment, a Service, an optional PVC, a NetworkPolicy, a per-instance ServiceAccount/Role/RoleBinding, and, when ServiceAccount auth is enforced, a `system:auth-delegator` ClusterRoleBinding.

In RHOAI 3.7.0-ea.1, Konflux builds two images: `odh-modelexpress-rhel9` (server) and `odh-modelexpress-operator-rhel9` (operator). Both are FIPS-oriented builds linked against RHEL OpenSSL. The operator is deployed by kustomize manifests in `config/manifests/` into `modelexpress-operator-system` or the ODH applications namespace. Users then create `ModelExpressServer` CRs in their own namespaces, which the operator turns into a coordinator instance for that namespace's inference workloads.

## Architectural Analysis

**Two-tier control plane: operator → per-namespace coordinator.** The operator is cluster-wide. It watches `ModelExpressServer` and owned Deployments, Services, PVCs, NetworkPolicies, ServiceAccounts, Roles and RoleBindings across all namespaces (`Api::all`, operator/src/controller.rs:78-86) and applies children with server-side apply under field manager `modelexpress-operator`. Each CR yields an independent coordinator in its own namespace. The coordinator's Kubernetes metadata backend stores CRs and tensor-descriptor ConfigMaps in the pod's own namespace (`POD_NAMESPACE`). So the default isolation unit is "one MX server per namespace". Validation uses CEL rules on the CRD schema rather than an admission webhook, explicitly to stay OLMv1-clean (CRD description, config/manifests/crd/modelexpressservers…yaml:38).

**RBAC escalation surface.** Under Kubernetes RBAC escalation prevention, the operator's ClusterRole must hold every permission it grants. The ClusterRole therefore includes cluster-wide CRUD on `configmaps`, `roles`, `rolebindings`, `clusterrolebindings`, `networkpolicies`, `serviceaccounts` and the upstream CRDs (config/manifests/rbac/clusterrole.yaml). `clusterrolebindings` create/update/delete is a powerful grant. The operator only uses it to bind instance ServiceAccounts to `system:auth-delegator`, with digest-suffixed names and a finalizer for cleanup (operator/src/rbac.rs:38-87, operator/src/controller.rs:335-372). The code does not restrict it beyond that convention. The server's per-namespace Role grants CRUD on *all* ConfigMaps in its namespace (operator/src/rbac.rs:139-147). The source comment advises a dedicated namespace on shared clusters.

**Security defaults are off; the operator makes them easy to turn on.** The server ships with `security.mode=off` and `tenant_isolation=off` (modelexpress_server/src/config.rs:199-206), so the gRPC API is unauthenticated unless the CR sets `spec.security.mode: enforce`. In enforce mode, a Tower `AuthLayer` wraps every non-health service. It validates the Bearer ServiceAccount token via `TokenReview` (with audience checks) and matches the caller against an allowlist (`ns:sa` or `ns:*`), caching decisions in a `moka` cache keyed on zeroized token copies (modelexpress_server/src/auth.rs, server.rs:443-458). With `tenant_isolation: enforce`, the P2P service and model cache are further scoped to the caller's verified namespace. That is application-enforced tenancy inside a shared server. gRPC TLS is likewise optional: it is off unless `spec.tls.secretName` is set. On OpenShift, TLS parameters follow the cluster `APIServer` TLS profile when `tlsAdherence` is `StrictAllComponents`, otherwise the Intermediate profile (operator-openshift/src/apiserver.rs).

**FIPS engineering is deliberate and enforced at build time.** The upstream default feature set uses rustls (which pulls `ring`) and a GCS provider that hardcodes rustls. The Konflux Dockerfiles build `--package <crate> --no-default-features --features openssl`, then run `ci/check-fips-crypto.sh`. That script fails the build if the shipped binary carries any `ring`, `rustls` or `aws-lc` symbols, lacks `openssl::` symbols, or lists check-payload-denied crates in its cargo-auditable data. It is a gate stricter than check-payload alone. The trade-off is that the RHOAI server image cannot pull models from GCS (docker/Dockerfile.konflux:13-15). SHA-256 hashing is routed through OpenSSL under `tls-native` and only falls back to pure-Rust `sha2` otherwise (modelexpress_common/src/digest.rs).

**Observability hardening on the operator, not the server.** The operator's `/metrics` endpoint on OpenShift is served over TLS on 8443, using a service-ca-issued cert. It is gated by TokenReview + SubjectAccessReview (`get` on non-resource URL `/metrics`), mirroring controller-runtime's `WithAuthenticationAndAuthorization` (operator/src/metrics_auth.rs). The operator also self-applies its own ServiceMonitor with the namespace from the downward API. The coordinator's `/metrics` on 9401 is plain HTTP/1.1 with no auth (modelexpress_server/src/metrics/exposition.rs). Its exposure depends only on the operator-generated NetworkPolicy, which restricts ingress only when `spec.networkPolicy.allowFrom` is set. Otherwise ingress on the gRPC, HBONE (15008) and metrics ports is allowed from any source.

**Broad repo, narrow shipped surface.** The repo also contains a Helm chart, many example/CI Dockerfiles (Ubuntu/CUDA-based client images for vLLM, SGLang, TRT-LLM, Dynamo, RL refit), a Python client package and Go stubs. Only the two `docker/Dockerfile.konflux*` images are built by RHOAI Konflux pipelines on this branch. The Python client, which runs inside inference engine images, is not packaged here for RHOAI.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Optional TokenReview + `ns:sa` / `ns:*` allowlist; per-CR ServiceAccount, Role, RoleBinding | Application (server) + Kubernetes RBAC | Auth is off by default. Any pod that can reach port 8001 can publish or read P2P metadata and trigger downloads unless `security.mode=enforce`. |
| Data storage | CRD backend stores in the server's own namespace; per-CR optional PVC; Redis backend is an external shared store | Kubernetes (namespace) / Application | Redis shared across servers has no built-in key namespacing beyond what `tenantIsolation` provides. With tenant isolation off, a shared server mixes all callers' sources. |
| Network traffic | Operator-generated NetworkPolicy per CR; operator NetworkPolicy limits ingress to monitoring namespaces | Kubernetes | Without `spec.networkPolicy.allowFrom`, server ingress on 8001/15008/9401 is open to all. Egress is unrestricted. |
| Compute & resources | `spec.resources`, nodeSelector, tolerations, affinity per CR | Kubernetes | No ResourceQuota/LimitRange created; relies on namespace quotas. |
| Configuration & secrets | Per-namespace Secrets referenced by CR (Redis URL, HF/NGC tokens, TLS) | Kubernetes | The server Role grants CRUD on all ConfigMaps in its namespace, so MX should run in a dedicated namespace on shared clusters. |
| API scoping | Operator watches all namespaces (`Api::all`); server CRD backend scoped to `POD_NAMESPACE` | Kubernetes / Application | Operator holds cluster-wide ClusterRoleBinding/Role/ConfigMap write permissions. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| modelexpress-server (when shared by multiple namespaces) | Caller namespace | Application-level filtering when `tenantIsolation: enforce` (P2P sources and model cache) |
| Redis metadata backend (external) | None inherent | Application filtering only; user-supplied Redis instance |
| Model cache PVC | Per server instance | Kubernetes PVC; shared by all callers of that server |
