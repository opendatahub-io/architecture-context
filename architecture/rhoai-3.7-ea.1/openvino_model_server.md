## Purpose

**Short**: OpenVINO Model Server (OVMS) is a high-performance C++ inference server that serves OpenVINO IR, ONNX, TensorFlow, PaddlePaddle, PyTorch and generative (LLM/VLM/embeddings/image) models over the KServe v2, TensorFlow Serving and OpenAI-compatible APIs.

**Detailed**: In RHOAI, OVMS is one of the out-of-the-box predictive serving runtimes owned by the Model Runtimes team (overlay 0014). It is not an operator. The platform ships the `odh-openvino-model-server-rhel9` container image, and ODH Model Controller registers it with KServe through a ServingRuntime template (`kserve-ovms`). Each InferenceService that selects that template gets a pod running the `ovms` binary. The binary loads models from `/mnt/models` (fetched by the KServe storage initializer, or read directly from S3/GCS/Azure) and serves inference over REST (Drogon HTTP server) and gRPC.

The server has several API surfaces. It implements the KServe v2 REST and gRPC (`inference.GRPCInferenceService`) protocols, the TensorFlow Serving v1 REST and gRPC (`PredictionService`, `ModelService`) protocols, Prometheus metrics, and an OpenAI-compatible `/v3` API (chat/completions, completions, responses, embeddings, rerank, image generation, audio) driven by MediaPipe graphs and OpenVINO GenAI. It also supports DAG pipelines, custom nodes, Python nodes (`pyovms`) and stateful (sequence) models.

On this downstream release branch the repository no longer builds OVMS from source in Konflux. `Dockerfile.konflux` assembles the runtime image from prebuilt Red Hat AI RPMs (`openvino_model_server`, `openvino`, `openvino-genai`, `openvino_tokenizers` and the `ovms-*` third-party libraries from the `rhelai-3.6` CDN channel) on top of the AIPCC `cpu-el9.8` base image. It adds a hash-pinned Python environment (`openvino`, `torch` CPU) from the RHOAI RHEL AI PyPI index. The C++ source tree (`src/`, Bazel `WORKSPACE`) is upstream code kept for reference and for RPM provenance. It is not what the Konflux pipeline compiles.

## Architectural Analysis

**Build model changed: from a source build to packaged-binary assembly.** The single Konflux Dockerfile is a one-stage "install RPMs + wheels" image. Every input comes from Hermeto prefetch (`/cachi2/output/deps/rpm` and `/cachi2/output/deps/pip`), and the Tekton push pipeline sets `hermetic: true`. This makes OVMS a fully hermetic build on this branch, for both RPMs (`rpms.lock.yaml`, 22 packages from `cdn.redhat.com/.../rhelai/3.6`) and pip wheels (`requirements.txt`, `--require-hashes --only-binary=:all: --no-index`). Overlay 0014 still describes OVMS as "UBI9 + upstream Bazel build — Not hermetic". That statement is stale for `rhoai-3.7-ea.1`, and the overlay should be updated. The trade-off is that build provenance for the server binary now lives in the RPM build system (`openvino_model_server-2026.4.0-3.el9ai`), not in this repository. Patches in `src/` therefore do not reach the image unless the RPM is rebuilt. `rpms.in.yaml` sets `noSources: true`, so source-RPM provenance is handled outside this repository.

**Entrypoint path inconsistency.** The final sanity check runs `/usr/bin/ovms --version`, but `ENTRYPOINT` is `/ovms/bin/ovms` (`Dockerfile.konflux:73,75`). The image only works if the RPM also provides `/ovms/bin/ovms` (for example as a compatibility symlink). Nothing in this repository proves that, so it should be verified against the RPM file list. A ServingRuntime that overrides `command` would avoid the issue.

**Single-arch, CPU-only image.** The build platforms are `linux-extra-fast/amd64` only, and the lock covers `x86_64` only. The base is AIPCC CPU, and the pip index is `rhoai/3.6/cpu-ubi9`. The only GPU path left is Intel GPU through the OpenVINO GPU plugin, if the RPMs pull it in (the user is added to the `video`(39) and `video1`(44) groups for `/dev/dri` access). Overlay 0014 confirms that NVIDIA/CUDA is unsupported. `.konflux/build-args.conf` (`GPU=1`, `BASE_OS=redhat`) is explicitly marked as a stub that is no longer used.

**Version skew between the repo templates and the product.** The in-repo `extras/openshift_AI/ServingRuntime.yaml` is labelled `2026.2` and references `docker.io/openvino/model_server:latest-gpu`. The in-repo `extras/kserve/kserve-openvino.yaml` is an upstream KServe Helm ClusterServingRuntime with the placeholder image `openvino/model_server:replace`. Neither is the template the product deploys. That template is `ovms-kserve-template.yaml` in odh-model-controller, with the image pinned through the operator CSV `relatedImages`. The repo examples are documentation artifacts. The image actually built here is OVMS 2026.4.0.

**Security posture is delegated to the platform.** OVMS has no native TLS. The gRPC listener always uses `grpc::InsecureServerCredentials()` (`src/grpcservermodule.cpp:138`), and the Drogon REST server is plain HTTP. The only built-in authentication is an optional static Bearer API key (`--api_key_file` or the `API_KEY` env var). It is checked **only** on the `/v3` generative/OpenAI endpoints (`src/http_rest_api_handler.cpp:745`). KServe v2, TFS v1, metrics and gRPC are unauthenticated in-process. The key comparison is a plain `==` string compare, not a constant-time comparison. CORS defaults to `*` for origins, methods and headers. In RHOAI, encryption and authentication therefore come from the platform: KServe RawDeployment, the ODH Model Controller Route or Gateway, and optional auth (kube-rbac-proxy / Authorino) per overlays 0014 and 0023. `extras/nginx-mtls-auth` (nginx sidecar with TLS 1.2 mTLS) is an upstream example and is not shipped.

**gRPC port is not declared in the RHOAI template.** The template passes `--port=8001` but declares only the `rest` port 8888. KServe therefore cannot route gRPC externally (overlay 0023). OVMS also does not implement `ModelStreamInfer`.

**FIPS considerations.** The image inherits system OpenSSL from the RHEL 9.8 AIPCC base. The server dynamically links distro-packaged gRPC, protobuf and Azure SDK RPMs. However, model-config change detection computes MD5 with OpenSSL's legacy `MD5()` API (`src/filesystem/filesystem.hpp:273`). In a FIPS-enabled OpenSSL 3 runtime, that call can fail when `--config_path` multi-model mode is used. Whether the packaged RPM patches this is not visible from this repository.
