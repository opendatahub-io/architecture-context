## Purpose

**Short**: The RHOAI platform operator. It reconciles the `DataScienceCluster`, `DSCInitialization`, `Platform` and service CRs, then installs, configures and garbage-collects every Red Hat OpenShift AI component, plus the shared platform ingress and authentication layer.

**Detailed**: `rhods-operator` is the Red Hat downstream of `opendatahub-io/opendatahub-operator`. It is built with the `rhoai` Go build tag, which selects RHOAI defaults:
- application namespace `redhat-ods-applications`
- monitoring namespace `redhat-ods-monitoring`
- notebooks namespace `rhods-notebooks`
- operator namespace `redhat-ods-operator`

OLM installs it from the `rhods-operator` CSV. The CSV initialization resource is a `DataScienceCluster` v3 named `default-dsc`. Administrators declare the components they want in the DSC. Platform-wide settings go in `DSCInitialization`: namespaces, monitoring, trusted CA bundle and the default NetworkPolicy. The operator then renders and applies the matching manifests.

In this release the operator is mostly a **module orchestrator**:
- **Kueue** is the only in-tree component controller.
- The other component capabilities are "built-in modules": out-of-tree module operators the platform operator deploys from bundled Helm charts or Kustomize manifests (`internal/controller/modules/builtin/handlers.go`). Modules are ordered by runlevel:
  - Runlevel 20: aipipelines, dashboard, databaseservice, mcplifecycleoperator, aihub, ray, trainer, workbenches, monitoring.
  - Runlevel 31: kserve.
  - Runlevel 32: aigateway, data, mlflowoperator, ogx, sparkoperator, trustyai.
- The operator propagates platform configuration (`injectPlatformConfig`) and per-module environment into those modules. It gates upgrades on acknowledgements in the `odh-upgrade-acks` ConfigMap, and cleans up disabled modules in two phases.
- Manifests and charts are baked into the image (`/opt/manifests-template`, `/opt/charts`). An init container copies them to `/opt/manifests` at startup, so the operator works in disconnected clusters.

The operator also owns the **platform ingress and authentication plane** through its "services" controllers:
- **gateway**: a Gateway API `GatewayClass` and `Gateway` (`data-science-gateway` in `openshift-ingress`), an oauth2-proxy-based `kube-auth-proxy` deployment, an Istio `EnvoyFilter` for ext_authz, and legacy dashboard redirect Routes.
- **auth**: admin and allowed group RBAC.
- **certconfigmapgenerator**: trusted CA bundle distribution.
- **setup**.

Validating, mutating and conversion webhooks protect the platform CRs. A separate `cloudmanager` binary (CCM) reconciles `AWSKubernetesEngine`, `AzureKubernetesEngine` and `CoreWeaveKubernetesEngine`. On non-OpenShift Kubernetes (XKS) it installs prerequisite stacks: Gateway API, LWS, Sail/Istio, RHCL and cert-manager.

## Architectural Analysis

**From component operator to module orchestrator.** The operator used to hold a controller per component. Most of those now live in standalone module operators. The platform operator's job is to render each module's operator chart, inject platform-wide settings, apply the result with server-side apply, and read the module's status back into the DSC.

This shrinks the reconcile surface of the platform operator, but the RBAC footprint does not shrink with it. The manager still carries 315 kubebuilder RBAC markers. Several of them grant cluster-wide write on core workload kinds in wildcard API groups: deployments, services and statefulsets, all `"*"` group with full CRUD (`internal/controller/datasciencecluster/kubebuilder_rbac.go:94-151`). Two forces keep it broad:
- It must install arbitrary module operators, CRDs and their RBAC.
- Kubernetes RBAC escalation rules require the installer to hold any permission it grants.

So the operator remains the highest-privilege identity in the RHOAI control plane. Compromising its service account (`redhat-ods-operator-controller-manager`) is effectively cluster-admin.

**Build-time manifest pinning drifts from the release branch.** `manifests-config.yaml` pins all 21 component and chart refs, and the `buildConfig` ref (`red-hat-data-services/RHOAI-Build-Config`), to `rhoai-3.6@<sha>` branches. Nothing points at a `rhoai-3.7` ref, yet this is the `rhoai-3.7-ea.1` branch with Konflux `rhoai-version: 3.7.0-ea.1`. Either the EA build intentionally reuses 3.6 component content, or the 3.7 ref bump has not landed. Anyone validating component versions for 3.7 EA should treat the bundled manifests as 3.6-sourced until proven otherwise. The only commit in this shallow clone is `Updating the operator repo with latest images and manifests` (2026-11-10), so the history here does not show when the refs last moved.

**Gateway-centric ingress and auth.** Every user-facing RHOAI UI and API now goes through one platform `Gateway` (`data-science-gateway`, HTTPS 443, TLS Terminate). Authentication happens centrally at the gateway, through Envoy ext_authz to `kube-auth-proxy`. kube-auth-proxy is an oauth2-proxy fork that runs in OpenShift OAuth mode (`--provider=openshift`, OAuthClient `data-science`) or in OIDC mode for external IdPs. After a user logs in, the Lua filter turns the `_oauth2_proxy` session into an `Authorization: Bearer <token>` header and strips the cookie before forwarding upstream. Backends receive a real user token and do their own Kubernetes RBAC (SubjectAccessReview).

This design has two risks:
- **Envoy-to-proxy hop is not verified.** The `DestinationRule` `data-science-tls-rule` sets `insecureSkipVerify: true` for the Envoy → kube-auth-proxy hop on ports 8443/443 (`gateway_controller_actions.go:687`). That traffic is encrypted but the certificate is not checked. Within the gateway namespace, anything that can spoof the service endpoint could see bearer tokens.
- **Proxy egress is open.** The kube-auth-proxy NetworkPolicy restricts ingress to gateway pods on 8443 but allows all egress. That is needed for arbitrary OIDC issuers, but nothing further limits it.

**Two ingress modes and a legacy compatibility layer.**
- `IngressMode=OcpRoute`: the Gateway sits behind a ClusterIP Service with service-ca TLS, and a reencrypt OpenShift Route exposes it.
- LoadBalancer mode is used on XKS.
- Additional Gateways and Routes (`AdditionalIngresses`) get ownership and conflict checks.
- An nginx `dashboard-redirect` deployment keeps old `rhods-dashboard` and `data-science-gateway.<domain>` URLs working. It returns 301 redirects, or a deprecation page for browsers. It is the only workload the DSCI default NetworkPolicy explicitly carves out (`app!=dashboard-redirect`), so router traffic can reach it.

**TLS profile adherence is first-class.**
- The manager reads the cluster `APIServer` TLS profile at startup. It applies the profile to the metrics server (8443) and webhook server (9443), and also propagates it to kube-auth-proxy flags.
- `SecurityProfileWatcher` restarts the manager when the profile or the adherence policy changes.
- When the cluster does not require honouring its profile, the fallback is TLS 1.2+ with an "intermediate" AEAD list that includes CHACHA20-POLY1305, which is not FIPS-approved (`cmd/main.go:108-117`).
- The CSV advertises `features.operators.openshift.io/tls-profiles: "true"`.

**FIPS posture is internally inconsistent.**
- The manager binary is built correctly for FIPS: `CGO_ENABLED=1 GOEXPERIMENT=strictfipsruntime`, on a UBI9 `ubi-minimal-pqc` runtime that carries OpenSSL.
- The `cloudmanager` binary in the same image is built with `CGO_ENABLED=${CGO_ENABLED}`, but that ARG is never declared, so it expands to empty and Go uses its default. It uses only `-tags strictfipsruntime`, without `GOEXPERIMENT`.
- The RHOAI CSV declares `features.operators.openshift.io/fips-compliant: "false"`.

check-payload may accept the image, but the published OLM metadata says it is not FIPS-compliant, and the second binary may not get the strict FIPS runtime.

**Asymmetric metrics hardening.** The main manager serves metrics with `SecureServing` and controller-runtime `WithAuthenticationAndAuthorization` (TokenReview/SAR) when `--metrics-secure=true`, which the RHOAI patch sets. The cloudmanager's metrics endpoint is plain HTTP with no authn filter (`cmd/cloudmanager/app/run.go`). That matters mainly on XKS clusters, where there is no OpenShift service-ca and no default NetworkPolicy.

**Dead or dormant code paths.** The serving "connection" mutating webhook (`internal/webhook/serving`) is still in the tree. It is not registered: the comment defers to odh-model-controller (#3777). Webhook registration is conditional on which services and modules are enabled (gateway, monitoring, dashboard, DSC/DSCI flags). The admission surface therefore varies with configuration, so reviewers should not assume every manifest-declared webhook path is live.

**Naming divergence in generated config.** The upstream `config/default` tree uses `opendatahub-operator-*` names. The RHOAI overlay (`config/rhoai/*`) renames them:
- Deployment → `rhods-operator`
- Service account → `redhat-ods-operator-controller-manager`
- Metrics service → `redhat-ods-operator-controller-manager-metrics-service`
- Webhook cert → `redhat-ods-operator-controller-webhook-cert`
- Metrics TLS → `rhods-operator-metrics-tls`
- Namespace → `redhat-ods-operator`

The tables below use the RHOAI names and give the upstream names where they help.
