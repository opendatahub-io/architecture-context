## Platform Overview

Red Hat OpenShift AI 3.7-ea.1 is an AI/ML platform on OpenShift. It covers interactive workbenches, data science pipelines, distributed training (Ray, Kubeflow Trainer, Kueue, Spark), model registry and catalog, experiment tracking (MLflow), generative-AI serving (KServe with llm-d disaggregated inference), governed model access (Models-as-a-Service), guardrails and evaluation (TrustyAI, NeMo Guardrails, EvalHub, lm-evaluation-harness), feature store (Feast), agent tooling (MCP lifecycle, OGX/Llama Stack, OpenShell) and a technical-preview cross-cluster AI Grid (Praxis). The analyzed set has 95 components, 216 CRDs in 51 API groups, 282 Services, 747 endpoints and 225 admission-webhook entries.

The platform is deployed by OLM-packaged `rhods-operator` (3 replicas, leader election, namespace `redhat-ods-operator`). It initializes `DataScienceCluster` v3 `default-dsc` and now acts mainly as a **module orchestrator**. Most capabilities ship as separately built *module operators*, each with manifests baked into its own image and image references injected via `RELATED_IMAGE_*`: kserve-module, ray-module, trainer, workbenches, aipipelines, dashboard, databaseservice (rhai-db), mcplifecycle, aihub (model registry), aigateway, mlflow, ogx, sparkoperator, trustyai and feast. Run levels order them: 20 for core, 31 for kserve, 32 for gateway and dependent modules. Only Kueue remains an in-tree component. The model relies on shared conventions from `odh-platform-utilities`: SSA deploy, `platform.opendatahub.io/part-of` GC labels, a `params.env` handshake, and cluster TLS-profile propagation with restart-on-change.

Ingress has three separate Gateway API front doors in `openshift-ingress` plus a long tail of OpenShift Routes:
- **`data-science-gateway`** is created by the rhods-operator GatewayConfig controller and hosts the dashboard, workbenches, MLflow, model registry and Ray dashboards. Authentication is an operator-generated `EnvoyFilter` that performs an HTTP `ext_authz` call to `kube-auth-proxy` (an OAuth2/OIDC proxy) on 8443. A Lua filter then converts the session into a Bearer token for the backend's own `kube-rbac-proxy` or application authorization.
- **`openshift-ai-inference`** is created by the odh-gitops chart, not by rhods-operator code. It carries KServe `LLMInferenceService` routes to llm-d InferencePools, with a Kuadrant/Authorino `AuthPolicy` from odh-model-controller doing TokenReview and SubjectAccessReview.
- **`maas-default-gateway`** is created by the odh-gitops chart or the MaaS deployment manifests. It carries Models-as-a-Service API-key traffic with an Authorino `AuthPolicy`, TokenRateLimitPolicies, and payload-processing `ext_proc` filters (Praxis ExtProc by default, legacy IPP as an alternative).

Security posture is uneven:
- **Strengths:** cluster TLS-profile propagation is broad and consistent, internal TLS uses service-ca, most Go operators use FIPS-oriented Konflux builds (`strictfipsruntime`, `ubi-minimal-pqc`), and all admission webhooks fail closed.
- **Weaknesses:** gateway-to-backend TLS commonly uses `insecureSkipVerify` DestinationRules; several surfaces rely only on NetworkPolicy or are unauthenticated; the CSV declares `fips-compliant: "false"`; and the Rust components (Praxis, AI Grid, OpenShell) ship non-FIPS crypto.

### Ingress Analysis

**Three generations of ingress coexist.**
- **OpenShift Routes.** Component operators still create reencrypt Routes to kube-rbac-proxy sidecars: DSPO, TrustyAI, observability, Feast, model registry, odh-model-controller for raw InferenceServices. They also create edge Routes and Ingresses for MCP, planner, OGX and Spark.
- **Platform Gateway.** `data-science-gateway` is the shared, authenticated front door for user-facing UIs. rhods-operator creates the GatewayClass, the Gateway (`gateway_support.go:374-480`) and, in the default OpenShift `OcpRoute` mode, a ClusterIP Service with a reencrypt Route in front of the Envoy gateway. The old dashboard hostnames survive only as nginx redirect Routes (`dashboard_redirects.go`).
- **Capability gateways.** `maas-default-gateway` and `openshift-ai-inference` use Kuadrant/Authorino instead of kube-auth-proxy, and neither is created by rhods-operator Go code. Both come from the odh-gitops chart; the MaaS gateway alternatively comes from MaaS deployment manifests. rhods-operator only reports that `maas-default-gateway` "must be created" (`internal/controller/modules/aigateway/maas.go`).

**data-science-gateway authentication chain (source-resolved).**
- *The filter.* `gateway/resources/envoyfilter-authn.tmpl.yaml` creates EnvoyFilter `data-science-authn-filter`. It selects `gateway.networking.k8s.io/gateway-name: data-science-gateway` and inserts `envoy.filters.http.ext_authz` (http_service) before the router. The target is `https://kube-auth-proxy.<ns>.svc.cluster.local:8443/oauth2/auth`. It forwards `cookie`, `authorization` and `user-agent`, and allows `x-auth-request-*` and `authorization` upstream and `set-cookie` downstream.
- *Failure behavior.* The filter sets no `failure_mode_allow` and no per-route disable, so it fails closed for every route. It is created even in `AuthModeNone`, where traffic is rejected until a provider is configured (`gateway_auth_targets.go:193-272`).
- *Session conversion.* A Lua filter turns the access token into `Authorization: Bearer` and strips `_oauth2_proxy*` cookies.
- *kube-auth-proxy.* It runs in OpenShift mode (`--provider=openshift --scope=user:full --upstream=static://200 --skip-jwt-bearer-tokens --enable-k8s-token-validation`) or OIDC mode. It answers `/oauth2/auth` via `AuthOnly` with 202/401/403. Every other path goes through `Proxy`, returning the static 200 or an OAuth 302 (`oauthproxy.go:342-361, 1205-1281`). Bearer tokens are checked with a TokenReview (10s cache) before cookies.
- *Two candidate behaviors (not runtime-verified).* Because `path_prefix` is unset, Envoy sends the original request path, so the catch-all `Proxy` handler probably answers rather than `/oauth2/auth`. Because `Accept` is not forwarded, API clients without a session may get a 302 instead of a 401.
- *Separation of concerns.* The gateway does **authentication only**. Authorization stays with each backend: kube-rbac-proxy `get notebooks/<name>` for notebooks with `inject-auth: "true"` (otherwise the route goes straight to 8888), kube-rbac-proxy in workspaces gateway mode, MLflow workspace SSAR, model-registry SAR on the Service. The gateway-to-backend hop uses DestinationRule `data-science-tls-rule` (host `"*"`, `insecureSkipVerify: true`).

**MaaS chain.** Requests to `maas-default-gateway` follow this sequence:
1. The `ipp-pre` ext_proc runs before the Kuadrant wasm and extracts the model from the body into a header.
2. Authorino applies `maas-gateway-auth`: an API key validated by maas-api, or TokenReview, or OIDC, then an OPA subscription check. It injects `X-MaaS-*` headers and denies client-supplied ones.
3. Limitador enforces per-route TokenRateLimitPolicies built from MaaSSubscriptions, with a zero-limit `gateway-default-deny` backstop.
4. The `ipp` ext_proc runs after the wasm for provider resolution, API translation, usage enforcement and API-key injection.
5. The request reaches the backend: an LLMISVC through InferencePool/EPP, or an external provider through an ExternalName Service, ServiceEntry and a DestinationRule doing SIMPLE TLS origination with SNI.

Praxis ExtProc (ai-gateway-controller) and the legacy IPP (maas-controller / ai-gateway-payload-processing) are **alternatives per tenant**, selected by `maas.opendatahub.io/payload-processing-type` with a `payload-processing-status` handover. Praxis is the default. Both own EnvoyFilter `payload-processing` with `failure_mode_allow: false` for the main filter. The legacy IPP's `ipp-pre` is fail-open. The internal maas-api endpoints (`/internal/v1/api-keys/validate`, `/subscriptions/select`) are protected only by NetworkPolicy, and the maas-api DestinationRule uses `insecureSkipVerify` until BackendTLSPolicy is available (OCP 4.22).

**Inference chain.** KServe's ODH overlay points `kserveIngressGateway` at `openshift-ingress/openshift-ai-inference` and disables Gateway API for raw InferenceServices (`enableGatewayApi: false`). The two KServe APIs therefore reach users differently:
- *LLMInferenceService* uses Gateway API: HTTPRoute → InferencePool → llm-d EPP `ext_proc` → vLLM pods.
- *Predictive InferenceService* uses Routes created by odh-model-controller.

On the inference gateway, odh-model-controller's EnvoyFilter is **not** an `ext_authz` filter. It is a CLUSTER patch that adds TLS to Authorino. The real `ext_authz` wiring comes from Kuadrant compiling the odh-model-controller AuthPolicy (TokenReview + SAR). odh-model-controller deliberately skips Gateways owned by the platform GatewayConfig, which keeps the kube-auth-proxy and Authorino models from overlapping on one gateway.

## Deployment Architecture

### Deployment Topology

**Operator tier.** `rhods-operator` runs in `redhat-ods-operator` with 3 replicas, leader election `07ed84f7.opendatahub.io` and anti-affinity. It installs DSC/DSCI and per-module CRs and deploys module operators into `redhat-ods-applications`.

**Module and controller tier.** Each module operator in `redhat-ods-applications` deploys its operand controllers into the same namespace: kserve and llmisvc controllers, odh-model-controller, DSPO, kuberay, the Trainer controller, the notebook controllers, model-registry/catalog, MLflow, TrustyAI, Feast, the MCP lifecycle operator, the OGX root operator, rhai-db, maas-controller and ai-gateway-controller. odh-observability deploys its monitoring stack into `redhat-ods-monitoring`. #### Manifest Consumption Pipeline

rhods-operator's `manifests-config.yaml` lists component manifest sources. On the `rhoai-3.7-ea.1` branch, 21 refs and the buildConfig are pinned to `rhoai-3.6@<sha>`, so several operands ship 3.6-sourced manifests. At build time these are prefetched into `prefetched-manifests/` and `prefetched-charts/` and baked into the operator image under `/opt/manifests` and `/opt/charts`, which replaces runtime git fetching (the legacy `get_all_manifests.sh` role). `build/operands-map.yaml` supplies the 132 digest-pinned `relatedImages`, which become `RELATED_IMAGE_*` env vars on the operator. When rhods-operator deploys a module operator, it passes the relevant `RELATED_IMAGE_*` values and projects `applicationsNamespace` plus an `odh-<module>-config` ConfigMap. Each module operator then repeats the pattern: it renders its own image-embedded operand manifests with substituted images and applies them with SSA and part-of GC labels. Some components, such as ai-gateway-operator and odh-gitops, add a further layer by vendoring other components' manifests or charts, which creates multi-hop version pinning that can drift (for example 3.6 pins inside a 3.7 build).

## Platform Architectural Analysis

**From monolith to module federation.** 3.7-ea.1 completes the shift from an in-tree monolith to a federation of module operators built on `odh-platform-utilities`. The benefits are independent release cadence, image-embedded hermetic manifests and consistent GC/condition semantics. The costs:
- **Privilege multiplication.** Kubernetes RBAC escalation prevention forces each module SA to hold every verb its operand grants, so the platform now has many cluster-admin-adjacent identities: kserve-module, ray-module, trainer-operator, ogx-module, data-connect-hub, ai-gateway-operator and rhods-operator.
- **Multi-hop version pinning.** The operator pins 21 manifest refs to `rhoai-3.6`; ai-gateway-operator and workbenches-operator vendor 3.6 manifests; module images carry upstream default images. What actually runs depends on `RELATED_IMAGE_*` injection succeeding at every hop.
- **Inconsistent HA.** rhods-operator runs 3 leader-elected replicas, but most module operators and several request-path components (maas-api, praxis-extproc, workbenches-operator with Fail webhooks) run a single replica.

**Fragmented authentication models across gateways.** Three gateways in the same `openshift-ingress` namespace use different identity stacks:
- `data-science-gateway` uses an operator-templated Envoy `ext_authz` → kube-auth-proxy (OAuth/OIDC sessions, authentication only) chain, with authorization pushed to kube-rbac-proxy sidecars or application SAR.
- `openshift-ai-inference` uses Kuadrant AuthPolicy → Authorino with TokenReview and SAR at the gateway.
- `maas-default-gateway` uses Authorino with API keys, OPA subscriptions and token rate limits, with payload processing around the auth filter.

odh-model-controller deliberately avoids platform-owned Gateways, which keeps the stacks separate. A feature that crosses gateways, such as a dashboard calling a model, must handle both identity models. The data-science-gateway chain fails closed and is enforced for every route. Its authorization guarantees are only as strong as each backend: notebooks without `inject-auth` route directly to 8888, and DSPO, MaaS internal endpoints and TrustyAI expose ports protected only by NetworkPolicy.

**TLS without verification is a platform-wide pattern.** Cluster TLS-profile propagation is a real strength. It is implemented consistently across Go operators, with restart-on-change and projection into operands. Yet gateway-to-backend hops repeatedly use `insecureSkipVerify` DestinationRules:
- rhods-operator `data-science-tls-rule` with host `"*"`, which affects every backend of the platform gateway
- the MaaS maas-api rule, pending BackendTLSPolicy on OCP 4.22
- the payload-processing self-signed certificate
- the llm-d EPP when the istio provider is used
- kserve sidecars without cert rotation

ServiceMonitors in mlflow-operator and mcp-lifecycle also use `insecureSkipVerify`. Encryption is in place, but these hops have no server authentication. Adopting BackendTLSPolicy is the clear consolidation path.

**Fail-closed everywhere means availability coupling.** All 225 webhook entries are Fail, and the gateway `ext_authz` and MaaS `ipp` ext_proc filters are fail-closed. Four Pod mutators (kserve, odh-model-controller, spark-operator, kueue) and single-replica webhook servers (workbenches-operator) make control-plane component health a precondition for user workload creation. This is a sound security choice, but it raises the importance of HA. The structured `high_availability` evidence is fully unresolved for this generation.

**Supply-chain and FIPS posture are inconsistent across language ecosystems.** Go components converge on `strictfipsruntime` + `ubi-minimal-pqc` Konflux builds with digest-pinned images. The Rust-based newcomers are different:
- praxis-ai-grid-operator ships rustls/ring because the Konflux build does not enable its `fips` feature.
- praxis-grid's analyzed checkout has no Konflux files.
- openshell has non-blocking FIPS checks and vendored aws-lc-rs.
- praxis-extproc does not require FIPS.

These components arrive together with the new GenAI and agent capabilities, and some run on the request path (Praxis ExtProc on the MaaS gateway). The structured `supply_chain` evidence and the Dockerfile inventory are empty or unresolved, so these conclusions rest on component prose.

**Multi-tenancy is built from shared primitives with application-enforced edges.** Tenancy relies on namespace RBAC via SAR (kube-rbac-proxy templated SARs, Authorino SAR, EvalHub/DCH header SARs). Several boundaries are application-enforced:
- data-connect-hub `X-Tenant-Id` row filtering and the REST → Flight confused-deputy boundary
- MaaS tenant headers, guarded by AuthPolicy denial of client `x-maas-*`
- praxis-ai `x-auth-tenant`
- mcp-lifecycle gateway allowlists that are empty by default

Payload processing can shadow model names across namespaces, and several operators cache all cluster Secrets. AI Grid explicitly disclaims tenant isolation.

**Ingress joins that remain open.** data-connect-hub targets `odh-gateway`/`opendatahub`, and batch-gateway defaults to `llm-d-inference-gateway`. Neither has an identified RHOAI creator: they are upstream defaults without an observed RHOAI override, and should be treated as candidate misconfigurations rather than missing features. `openshift-ai-inference` and `maas-default-gateway` are created by the odh-gitops chart, or by MaaS manifests for the MaaS gateway, not by rhods-operator. Platform behavior for non-GitOps installs therefore depends on an out-of-band step, which rhods-operator surfaces as a status message.

**Coverage gaps in this generation.** odh-dashboard has no component document. rhods-operator webhooks are missing from the structured webhook inventory. NetworkPolicy and Dockerfile inventories are empty. Supply chain, disconnected and HA topics have no deterministic evidence family. Duplicate repositories (`training-hub`/`training_hub`, `batch-gateway`/`llm-d-batch-gateway`) and deprecated repositories (`llm-d-routing-sidecar`, `llm-d-model-service`, `llm-d-deployer` at 2025-07) are in the analyzed set and inflate component counts.
