## Purpose

**Short**: Reconciles a cluster-scoped singleton `MLflow` custom resource into a TLS-secured, Kubernetes-auth-enabled MLflow tracking server (plus optional artifact server, migration Job, and maintenance CronJobs) that is exposed through the RHOAI platform Gateway at `/mlflow`.

**Detailed**: The mlflow-operator is the supported way RHOAI deploys the shared MLflow service. It watches the cluster-scoped `MLflow` CR (`mlflow.opendatahub.io/v1`, name pinned to `mlflow` by CEL validation). It renders an embedded Helm chart (`charts/mlflow`, copied into the image) into Deployments, Services, ServiceAccounts, PVCs, ClusterRoles/Bindings, NetworkPolicies, ServiceMonitors, and CronJobs in the applications namespace (`redhat-ods-applications` for RHOAI). The operator then server-side applies those objects. It also creates the Gateway API `HTTPRoute`, which attaches to `data-science-gateway` in `openshift-ingress`, and an OpenShift `ConsoleLink` application-menu entry.

The operator does not implement MLflow request handling. Instead, it starts the MLflow server with `--app-name=kubernetes-auth`, `--enable-workspaces`, and the `kubernetes://` workspace store. That configuration makes the MLflow runtime map workspaces to Kubernetes namespaces and authorize each request with a `SelfSubjectAccessReview` against the caller's own token. The operator also ships the namespaced `MLflowConfig` CRD (`mlflow.kubeflow.org`) used by the runtime for per-namespace artifact-root overrides. It also ships aggregate ClusterRoles (`mlflow-view`, `mlflow-edit`, `mlflow-integration`) on virtual `mlflow.kubeflow.org` resources (experiments, registeredmodels, gatewayendpoints, and so on) that MLflow's SAR checks evaluate against.

Two more controllers complete the picture. `MLflowOperatorReconciler` handles the cluster-scoped `MLflowOperator` module CR (`components.platform.opendatahub.io/v1alpha1`). This is the ODH modular-architecture handoff path, gated by `ENABLE_MLFLOW_OPERATOR_MODULE_CONTROLLER` (default `false`). `NamespaceRBACReconciler` is enabled in the RHOAI overlay through `ENABLE_NAMESPACE_RBAC=true`. It binds the platform `Auth` CR's allowed/admin groups to the view/edit ClusterRoles in every namespace labeled `opendatahub.io/global-mlflow-workspace`.

## Architectural Analysis

**Helm-as-template inside an operator.** Instead of building Kubernetes objects in Go, the reconciler renders the in-image Helm chart (`internal/controller/helm.go`) with values derived from the `MLflow` spec and operator config. It applies the rendered objects with owner references. Only routing (`HTTPRoute`, `ConsoleLink`), migration Jobs, and namespace RoleBindings are constructed in Go. This gives one deployment shape for direct Helm installs and for the operator. The trade-off is that the chart (`charts/mlflow/templates/*`) is part of the operator's effective API surface. Changes to chart defaults, such as the NetworkPolicy and ServiceMonitor TLS defaults, ship with operator releases.

**Singleton, cluster-wide service with namespace-derived tenancy.** The CRD enforces `metadata.name == 'mlflow'` (`api/v1/mlflow_types.go:652`), so there is exactly one MLflow deployment per cluster. Code paths for suffixed instances (resource suffix, URL-rewrite route filters in `routing.go`) exist but the CRD blocks them. Tenancy lives in the MLflow runtime (Kubernetes workspace provider + SSAR authorization), not in separate deployments. All tenants therefore share one metadata database, one artifact store (unless `MLflowConfig` overrides the artifact root per namespace), and one set of server pods.

**Split tracking/artifact serving and migration safety.** When `artifactsServer.enabled` is set, a second metadata-aware Deployment/Service (`mlflow-artifacts`) serves `/mlflow-artifacts` plus legacy artifact-proxy paths. A dedicated artifacts HTTPRoute uses URL rewrites to direct that traffic. Both Deployments touch the metadata store, so database schema migrations (`internal/controller/migration.go`) scale both to zero and wait for live replicas to drain before creating a migration Job. The Job is cloned from the rendered tracking Deployment's pod spec. The Job's exit code is classified as retryable or terminal and surfaced as a status condition. A force-migrate annotation can re-trigger it. Extensive CEL rules on the CRD (`api/v1/mlflow_types.go:28-62`) block unsafe topologies at admission time: SQLite with split serving, multiple replicas on RWO storage, and the forbidden `MLFLOW_SERVER_DISABLE_SECURITY_MIDDLEWARE` and `MLFLOW_SERVER_ENABLE_JOB_EXECUTION` env vars. Storage access modes are also immutable.

**Capability-gated optional integrations.** At startup, the operator uses discovery to check for HTTPRoute, ConsoleLink, ServiceMonitor, MLflowOperator, and Auth APIs (`routing.go:47-180`). It registers `Owns()` watches only for APIs that exist (`mlflow_controller.go:723,731`). The namespace RBAC controller waits for the Auth CRD before setup. Because RBAC on RoleBindings and ClusterRoles is `resourceNames`-scoped, RoleBinding watches use dedicated per-name caches with field selectors. Without them, a general informer would be rejected.

**Security posture observations.**
- The operator itself exposes no data-plane API. Metrics on `:8443` use controller-runtime authn/authz filters (TokenReview + SubjectAccessReview), with TLS following the cluster `APIServer` TLS profile through `odh-platform-utilities` (Intermediate fallback). Health probes on `:8081` are unauthenticated.
- The operator ServiceAccount holds broad cluster permissions. These include create/patch on ClusterRoles/ClusterRoleBindings and `bind` on ClusterRoles, which it needs to install the MLflow server's cluster-scoped RBAC and the namespace RoleBindings. This is an escalation-sensitive grant, mitigated by `resourceNames` scoping in `config/rbac/role.yaml`.
- The chart-rendered ServiceMonitor defaults to `insecureSkipVerify: true` when `metrics.tlsConfig` is not set (`charts/mlflow/templates/servicemonitor.yaml`).
- The MLflow pod NetworkPolicy allows ingress on the server port from all namespaces (`namespaceSelector: {}`). It relies on token-based auth rather than network segmentation. Egress is open on ports 443, 6443, 8443, 5432, 3306, 9000, 8333, and 8334 to any destination.

**Admission policy.** RHOAI and ODH overlays add a `ValidatingAdmissionPolicy` (`config/admission/trace-rollups-schedule-warning.yaml`). It has `failurePolicy: Ignore` and a `Warn` binding, and warns when SQL trace rollups are enabled without an explicit schedule and timezone. It never denies requests. No admission webhooks are present.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace (MLflow workspace = Kubernetes namespace) | `charts/mlflow/templates/deployment.yaml:161-209` (`--workspace-store-uri=kubernetes://`) |
| **Deployment model** | Single shared multi-tenant MLflow instance per cluster | `api/v1/mlflow_types.go:652` (name must be `mlflow`) |
| **Tenant identifier** | Namespace name; optional `workspaceLabelSelector`; `opendatahub.io/global-mlflow-workspace` label for group RBAC | `api/v1/mlflow_types.go:249`, `internal/controller/namespace_rbac_controller.go:116` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-request SSAR with caller token against namespace RBAC; aggregate view/edit ClusterRoles; operator-managed group RoleBindings | Application (MLflow plugin) + Kubernetes RBAC | Enforcement lives in the MLflow runtime. A plugin bug could leak across workspaces |
| Data storage | Shared metadata DB with workspace column; shared default artifact store unless `MLflowConfig` overrides the per-namespace artifact root | Application | No physical separation by default |
| Network traffic | Operand NetworkPolicy allows ingress from all namespaces on 8443 | Kubernetes | No per-tenant network segmentation (relies on token auth) |
| Compute & resources | Shared server pods | — | Noisy-neighbor risk; no per-tenant quotas |
| Configuration & secrets | Per-namespace `MLflowConfig` and `mlflow-artifact-connection` Secret | Kubernetes + Application | MLflow SA can read the named secret in every namespace |
| API scoping | Operator watches cluster-scoped CRs; operand lists/watches namespaces cluster-wide | Kubernetes | Cluster-wide namespace visibility for MLflow SA |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| MLflow tracking/artifact server | Workspace (namespace) | Application SSAR authorization |
| Metadata database (PostgreSQL/MySQL/SQLite) | Workspace column | Application query filtering |
| Default artifact storage | Path/workspace prefix | Application; optional per-namespace override via MLflowConfig |
