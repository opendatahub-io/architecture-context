## Purpose

**Short**: Provides KEDA-based autoscaling blueprints and an evaluation test bed for llm-d inference deployments, and carries the deprecated Workload-Variant-Autoscaler (WVA) controller in a frozen `legacy/` tree.

**Detailed**: llm-d-autoscaling used to host the Workload-Variant-Autoscaler (WVA), a GPU- and saturation-aware controller for LLM inference workloads. On the analyzed branch (`main` at `b6be439`), the README says WVA is deprecated. Its last supported release is `v0.9.0` on the `release-0.9` branch. All WVA code, manifests and docs have moved, unchanged, into `legacy/`, which is "staging for removal": frozen, with no CI wired up. The top-level `Makefile` says the repository "is not a Go project". It only creates Kind clusters with emulated GPUs and lint-checks shell scripts.

The current architecture puts KEDA in the scaling path. KEDA reads inference metrics (vLLM queue depth, KV-cache utilization, EPP signals) straight from Prometheus and scales model-server Deployments through the HPA it manages. No custom controller sits in that path. The repository supplies two things for this model. First, reviewed `ScaledObject` blueprints per serving role (prefill/decode) under `benchmark/config/scenarios/guides/`, with experimental variants under `scenarios/staging/`. Second, an evaluation harness under `benchmark/`, built on llm-d-benchmark, that compares blueprints using measured replicas, trigger values, latency and throughput.

The WVA controller in `legacy/` is still the only runnable artifact the repo can build (`legacy/Dockerfile`). It is a controller-runtime manager that defines no CRDs of its own. It discovers workloads through annotations (`llm-d.ai/managed: "true"`, `llm-d.ai/model-id`, `llm-d.ai/variant-cost`) on HPAs and KEDA ScaledObjects. It watches Gateway API Inference Extension `InferencePool` objects to locate Endpoint Picker (EPP) metrics. Each optimization cycle reads vLLM/EPP metrics from Prometheus, scrapes EPP pods directly, computes a desired replica count per variant, and publishes it as the `wva_desired_replicas` gauge, which HPA (via prometheus-adapter) or KEDA consumes. A scale-from-zero engine writes the `scale` subresource of target workloads directly when EPP flow-control queues show pending requests.

## Architectural Analysis

**The repository has changed role.** On this branch, llm-d-autoscaling is mostly a configuration and evaluation repository, not a controller. Scaling is done by KEDA (an external dependency) using Prometheus queries defined in blueprint ScaledObjects. The repo itself contributes no runtime. Anyone consuming this for RHOAI 3.7 EA should treat the WVA controller as legacy. It is not built by Konflux on this branch: there are no `.konflux` Dockerfiles, no `.tekton/` pipelines and no lock files. The upstream `legacy/Dockerfile` targets distroless, not UBI. If RHOAI ships WVA, it is built from another branch or a downstream fork (e.g. `release-0.9` or an opendatahub-io/red-hat-data-services mirror), which this analysis does not cover.

**WVA design (legacy).** WVA works as a "metric producer" autoscaler, not an actuator. The saturation engine (`internal/engines/saturation`) runs on a leader-elected loop (`GLOBAL_OPT_INTERVAL`, default 15s, 60s on OpenShift). It gets data from a pluggable source registry: a Prometheus source plus per-InferencePool `PodScrapingSource`s that scrape EPP pods. Analyzers (saturation, an optional throughput analyzer, a Kalman-filter-based queueing model) turn this into desired replicas. Optional GPU limiters (inventory mode uses Node GPU labels via GPU-operator discovery; quota mode uses `ResourceQuota`) cap the result. The engine then exports Prometheus gauges. The HPA or KEDA object that opted in reads `wva_desired_replicas` back from Prometheus. So the control loop goes through Prometheus twice (inputs and output), and staleness and scrape intervals directly affect scaling latency. The ServiceMonitor drops `instance|pod|container|node` labels so that rolling updates still give KEDA a single scalar series.

**Annotations instead of CRDs.** The kubebuilder `PROJECT` file still declares a `VariantAutoscaling` (`llmd.ai/v1alpha1`) CRD, but no CRD manifest is shipped under `legacy/config/`. Annotation-sourced objects are built in memory and marked `llm-d.ai/synthetic`, so they are never written to the API server. The opt-in surface is just annotations on HPA/ScaledObject objects, and any user who can annotate an HPA in a watched namespace can put a workload under WVA control.

**Direct actuation path.** Most scaling goes through HPA/KEDA. The scale-from-zero engine (`internal/engines/scalefromzero`) and `DirectActuator` are the exception: they update `deployments/scale` and `leaderworkersets/scale` directly with a dynamic/scale client. The experimental Coordinator (`EXPERIMENTAL_COORDINATOR_ENABLED`, off by default) also writes `spec.maxReplicas` on HPAs and ScaledObjects through its `gpurebalance` plugin. That is why the ClusterRole includes `patch/update` on deployments, HPAs, ScaledObjects and LeaderWorkerSets.

**Optional CRDs.** KEDA `ScaledObject` and LWS `LeaderWorkerSet` are detected at startup through discovery (`internal/utils/crd`). If either CRD is installed after startup, a CRD watcher returns `ErrRestartRequired` and the process exits so the pod restarts with support enabled. `--disable-crd-auto-restart` turns this off.

**Security observations (legacy manifests).**
- The base `manager-config` sets `PROMETHEUS_TLS_INSECURE_SKIP_VERIFY: "true"` and the ServiceMonitor sets `insecureSkipVerify: true`. Only the OpenShift component fixes both, using the service-ca bundle and a service-ca-issued metrics serving cert.
- EPP pods are scraped at `http://<podIP>:<metrics-port>/metrics`. The scheme defaults to `http` because `datastore.PoolSet` never sets `MetricsScheme`, and the request still carries the `epp-metrics-reader` service-account token as a Bearer header. That token goes over plaintext pod-to-pod traffic. The Prometheus client, by contrast, refuses to send bearer tokens over HTTP.
- With no cert path configured, the metrics server uses a controller-runtime self-signed certificate.
- The webhook server is scaffolded, but no admission webhooks are registered.

**Tenancy.** By default the controller is cluster-scoped (all namespaces, ClusterRole). A namespace-scoped overlay adds `--watch-namespace=$(POD_NAMESPACE)`, but the RBAC is still ClusterRole/ClusterRoleBinding, so the controller's permissions stay cluster-wide even in namespace-scoped mode.

| Data storage | None (in-memory datastore) | Application | N/A |

| API scoping | All-namespace watches (default) or `DefaultNamespaces` cache restriction | Kubernetes / Application | Prometheus queries filter by namespace label in app code |
