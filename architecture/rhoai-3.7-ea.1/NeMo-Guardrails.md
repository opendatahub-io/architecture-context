## Purpose

**Short**: An OpenAI-compatible HTTP proxy/server that sits in front of LLM inference endpoints and applies programmable input, output, dialog, retrieval and tool guardrails defined in YAML + Colang configuration.

**Detailed**: NeMo-Guardrails is NVIDIA's open-source toolkit for adding programmable "rails" to LLM-based conversational systems. RHOAI ships the TrustyAI fork (`trustyai-explainability/NeMo-Guardrails`) as the container image `odh-trustyai-nemo-guardrails-server-rhel9`. At runtime the image starts `nemoguardrails server` on port 8000 against one or more rails configurations mounted under `/app/config/<CONFIG_ID>` (`scripts/entrypoint.sh`). Clients call an OpenAI-shaped `/v1/chat/completions` endpoint; the server runs configured input rails (jailbreak/injection heuristics, sensitive-data detection via Presidio, content safety, topic control, regex, HF classifiers, etc.), forwards the request to the configured main LLM (`MAIN_MODEL_ENGINE` / `MAIN_MODEL_BASE_URL`, typically a vLLM/KServe endpoint in-cluster), then runs output rails before returning the response.

The fork adds Red Hat/TrustyAI-specific behavior on top of upstream: a guardrail-only check API (`/v1/guardrail/checks`, now deprecated in favour of upstream's `/v1/checks`), request header forwarding (`X-*` headers and `X-Authorization` → `Authorization`) for per-request LLM authentication, a build-time profile filter that strips closed-source/third-party SaaS guardrail integrations, and a Konflux build that bakes Red Hat "modelcar" models (MiniLM, Snowflake Arctic embed, spaCy `en_core_web_lg`, NLTK punkt, Wolf Defender prompt-injection, Granite Guardian HAP) into the image so it can run fully offline (`HF_HUB_OFFLINE=1`, `TRANSFORMERS_OFFLINE=1`).

Within RHOAI, this repo only produces the server image; the Kubernetes lifecycle (Deployment, Service, Route, ConfigMaps holding rails config, auth proxy) is owned by the TrustyAI service operator, which is not part of this repository.

## Architectural Analysis

**Shape of the runtime.** The deployable artifact is a single FastAPI application (`nemoguardrails/server/api.py`) served by uvicorn bound to `0.0.0.0:<PORT>` with plain HTTP (`nemoguardrails/cli/__init__.py:212`). There is no TLS termination, authentication, or authorization in the application itself — the only middleware is exception handling, opt-in CORS (`NEMO_GUARDRAILS_SERVER_ENABLE_CORS`, default origins `*` with `allow_credentials=True` when enabled), and the legacy-checks deprecation header injector. All perimeter security therefore must come from the deploying operator (Route/Gateway TLS, kube-rbac-proxy or similar sidecar, NetworkPolicy). The analyzer's "Bearer token or API key" auth finding is sourced from `nemoguardrails/library/prompt_security/actions.py`, which is an *outbound* call to a third-party SaaS and, moreover, is removed from the RHOAI image by the `opensource` build profile — it does not describe inbound auth.

**Configuration is code.** Rails configurations are loaded from the mounted config directory per request (`_get_rails`, cached per `config_ids`+`model` key in a process-global dict). Configurations may include Python `actions.py`/`config.py` modules; in multi-config mode a root-level `config.py` is `exec`'d at startup with a reference to the app (`api.py:182-193`). Anyone who can write the mounted ConfigMap/volume has code execution in the guardrails pod — the trust boundary is the configuration source, not the HTTP API. Path traversal on `config_id` is defended by regex and `commonprefix` checks (`api.py:440-447`).

**Credential flow is mixed and partly inconsistent.** The fork's `header_forwarding.py` explicitly states the inbound `Authorization` header (K8s/proxy token) must never be forwarded to the LLM; instead clients send `X-Authorization`, which is mapped to `Authorization` only when the model has no static API key. However, `/v1/models` (`api.py:318-332` → `server/schemas/utils.py:fetch_models`) does forward the inbound `Authorization` header as the provider bearer token when no `OPENAI_API_KEY`-style env var is set. If the server sits behind an auth proxy that passes the user's OpenShift token through, that token can be sent to the upstream model provider. This is worth flagging to the TrustyAI operator owners.

**Build-time feature filtering.** `scripts/filter_guardrails.py` with `GUARDRAILS_PROFILE=opensource` (the Konflux default) deletes 15 library directories at build time (activefence, ai_defense, autoalign, clavata, cleanlab, crowdstrike_aidr, fiddler, gcp_moderate_text, jailbreak_detection, pangea, patronusai, policyai, privateai, prompt_security, trend_micro). As a result most of the third-party API-key secrets the analyzer enumerates (`ACTIVEFENCE_API_KEY`, `AI_DEFENSE_API_KEY`, `PANGEA_API_TOKEN`, …) are dead in the shipped image, and the `jailbreak_detection` and `align_score` sidecar servers (with their own upstream Dockerfiles) are not shipped. Retained third-party SaaS integrations include `f5`, `polygraf`, and `guardrails_ai`. Note that `/v1/challenges`, `/v1/actions/*` (separate actions server CLI) and the benchmark mock LLM server are present in code but are not part of the RHOAI runtime path.

**Offline / disconnected posture.** The Konflux image pre-stages all embedding/NLP models from Red Hat modelcar images and the tldextract public-suffix cache, sets HF/Transformers offline flags and `DO_NOT_TRACK=1` (which disables NVIDIA usage telemetry to `events.telemetry.data.nvidia.com`, `nemoguardrails/telemetry.py:41,374`). This makes the image suitable for disconnected clusters, as long as the main LLM endpoint is in-cluster.

**Dependency/base-image drift.** The image is built on AIPCC `cpu-torch2.13-el9.8`, but the app creates a fresh venv (no `--system-site-packages`) and installs `requirements.txt`, which pins `--index-url .../public-rhai/rhoai/3.5/cpu-ubi9/simple/` and `torch==2.11.0`. The torch shipped by the base image is thus not used; the venv carries its own torch 2.11 wheel from an older product-versioned index, roughly doubling torch footprint and diverging from the base image channel. The build also uninstalls `uv` from the base to remove its bundled crypto (RHOAIENG-97373).

**Observability.** OpenTelemetry auto-instrumentation is enabled only when `OTEL_EXPORTER_OTLP_ENDPOINT` is set (`entrypoint.sh`), wrapping the server with `opentelemetry-instrument` (FastAPI and httpx instrumentation, OTLP gRPC/HTTP exporters).

**State.** The server is effectively stateless: the rails instance cache and events-history cache are in-process; the optional thread datastore (memory or Redis via `aioredis`) is only registered programmatically and not wired by the RHOAI entrypoint. Horizontal scaling is safe, but there is no shared cache across replicas.
