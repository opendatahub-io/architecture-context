## Purpose

**Short**: The Red Hat build of Kueue Operator installs and lifecycle-manages the upstream Kueue job-queueing controller (`kueue-controller-manager`) on OpenShift from a single cluster-scoped `Kueue` custom resource.

**Detailed**: kueue-operator is an OpenShift-style operator built on `openshift/library-go` (`controllercmd` + a single `TargetConfigReconciler`). It watches one cluster-scoped `kueue.openshift.io/v1` `Kueue` CR named `cluster`. From that CR it renders and applies all operand resources: the 11 upstream `kueue.x-k8s.io` CRDs, the `kueue-manager-config` ConfigMap (Kueue `Configuration` v1beta1), the `kueue-controller-manager` Deployment, three Services (metrics, visibility, webhook), Mutating and ValidatingWebhookConfigurations, about 40 ClusterRoles and their bindings, cert-manager `Issuer`/`Certificate` objects, a Prometheus `ServiceMonitor`, and a set of default-deny NetworkPolicies. The static operand manifests are embedded as `bindata/assets/kueue-operator/*`. The operand image comes from the `RELATED_IMAGE_OPERAND_IMAGE` env var (`registry.redhat.io/kueue/kueue-rhel9`).

Kueue itself provides quota-based admission, fair sharing, preemption and gang scheduling for batch and AI/ML workloads: batch Jobs, JobSets, Kubeflow training jobs (PyTorch/TF/XGBoost/Paddle/MPI), KubeRay RayJob/RayCluster, CodeFlare AppWrappers, LeaderWorkerSets, and plain Pods/Deployments/StatefulSets. In RHOAI, this operator is the supported install path for Kueue that backs the platform's Kueue integration capability (overlay 0007). rhods-operator and the workload components rely on the `kueue.x-k8s.io` APIs and the `kueue.x-k8s.io/queue-name` label. They do not install Kueue themselves.

The operator has a hard dependency on cert-manager. On every sync it checks discovery for `cert-manager.io/v1 Issuer` and refuses to reconcile if it is missing. Kueue's internal cert management is disabled, and a self-signed Issuer provides the webhook and metrics serving certificates.

## Architectural Analysis

**Single-CR, render-and-apply operator.** The operator does not use controller-runtime. It uses library-go's `resourceapply` helpers in one sync loop (`pkg/operator/target_config_reconciler.go:143`) that applies every resource in a fixed order on each event. Resource versions of the ConfigMap, ServiceAccount, Role/RoleBinding and Services are copied into Deployment pod-template annotations. Any config change therefore triggers a rolling restart of the operand. Status is reported through the standard `operatorv1.OperatorStatus` conditions on the `Kueue` CR. A finalizer drives ordered cleanup on deletion: webhooks, then certs and issuers, then ClusterRoles, then ClusterRoleBindings, then namespaced resources. Cluster-scoped objects carry an ownerReference to the cluster-scoped `Kueue` CR.

**Opinionated configuration surface.** The `Kueue` CR does not expose the raw Kueue `Configuration`. It exposes a curated subset: `integrations.frameworks` (enum of 14 frameworks), `externalFrameworks`, `labelKeysToCopy`, `workloadManagement.labelPolicy`, `gangScheduling`, and `preemption.preemptionPolicy` (Classical/FairSharing). `pkg/configmap/configmap.go` hard-codes the rest: metrics on `:8443`, webhook on `9443`, health on `:8081`, OCP-recommended leader-election timings, QPS 50/burst 100, `InternalCertManagement.Enable=false`, and disabled feature gates `HierarchicalCohorts` and `VisibilityOnDemand`. The code comment says the visibility API server is disabled because "apiserver is insecure". The bundled `apiservice.yaml` sets `insecureSkipTLSVerify: true` and is never applied by the operator. The `kueue-visibility-server` Service and its ingress NetworkPolicy are still created, so they point at a port with no listener.

**Opt-in namespace model.** Kueue's `managedJobsNamespaceSelector` is pinned to `kueue.openshift.io/managed=true`. The operator rewrites every namespaced webhook's `namespaceSelector` by merging that opt-in label with the upstream `NotIn [kube-system, openshift-kueue-operator]` exclusion (`pkg/webhook/pod_webhook.go:166`). As a result, Kueue's Pod/Deployment/StatefulSet/Job webhooks only intercept workloads in labelled namespaces, which limits the blast radius of the `failurePolicy: Fail` webhooks. This label (`kueue.openshift.io/managed`) differs from the `kueue.x-k8s.io/managed` label referenced in overlay 0007 for RHOAI platform activation. Architects should confirm which label RHOAI tooling applies.

**Framework-filtered webhooks, with a likely gap.** Webhooks are filtered to the frameworks enabled in `spec.config.integrations.frameworks`. The filter maps webhook names to frameworks via `webhooksList`. The Kueue-native webhooks (`clusterqueue`, `workload`, `resourceflavor`, `cohort`) are keyed by annotation-style strings (`kueue.x-k8s.io/clusterqueue`, etc.) that the CRD enum does not allow in `frameworks`. Reading the source (`pkg/webhook/pod_webhook.go:62-102`), these core-API webhooks look like they are always dropped, which would leave ClusterQueue, Workload, ResourceFlavor and Cohort objects without admission defaulting or validation. This is inferred from source and was not verified on a running cluster. The unit tests only cover pod/deployment/statefulset/job/rayjob filtering. Separately, `getFrameworkForValidatingWebhook` panics on an unregistered webhook name, so a new upstream webhook in bindata without a matching `webhooksList` entry would crash the operator.

**HA and placement.** Both the operator (`deploy/07_deployment.yaml`, 2 replicas) and the operand (forced to 2 replicas, RollingUpdate maxUnavailable 1, preferred hostname anti-affinity) use leader election and `system-cluster-critical` priority. The operator forces `readOnlyRootFilesystem` on the operand container as a downstream hardening ahead of upstream Kueue 0.12.

**High-privilege operator identity.** The `openshift-kueue-operator` ClusterRole grants `bind` and `escalate` on all RBAC kinds, full CRUD on cluster-wide Secrets/ConfigMaps/Pods/Services, CRDs, and webhook configurations. This lets it mint the operand's broad `kueue-manager-role`, which can update Secrets cluster-wide and patch every supported job kind. Compromise of either service account is cluster-significant.

**Version skew signals.** go.mod vendors `sigs.k8s.io/kueue v0.10.2` for the config API, while the README targets Kueue 0.11.z on OCP 4.19–4.20. Dockerfile labels say `com.redhat.openshift.versions=v4.17-v4.18` (operator) and `v4.18-v4.19` (bundle, must-gather). A legacy `operator.openshift.io/v1alpha1 Kueue` CRD remains in `manifests/` but is not shipped in the OLM bundle (`bundle/manifests/` only contains `kueue.openshift.io_kueues.yaml`).

**Dead client.** `starter.go` builds an OpenShift Route clientset (`osrClient`) and passes it to the reconciler, but nothing in the reconciler uses it. No Routes are created.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Editor/viewer ClusterRoles for Kueue and job CRDs, bound by admins per namespace | Kubernetes | Operand SA can read/update Secrets and patch jobs cluster-wide |
| Data storage | None (state stored in Kubernetes objects) | Kubernetes | — |
| Network traffic | Default-deny NetworkPolicies on operator and operand pods only | Kubernetes | Does not isolate tenant workloads. Metrics and visibility ingress allowed from any source. |
| Compute & resources | ClusterQueue quotas, Cohort borrowing, preemption (Classical/FairSharing) | Application (Kueue) | Enforced only in opt-in namespaces and only for workloads carrying `queue-name` (per `labelPolicy`) |
| Configuration & secrets | Single cluster-wide ConfigMap | Application | Tenants cannot customize Kueue config |
| API scoping | Webhooks scoped by namespace selector; Kueue watches cluster-wide | Kubernetes + Application | ClusterQueue/Workload admission webhooks are probably not installed (see Architectural Analysis) |
