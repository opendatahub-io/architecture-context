## Purpose

**Short**: A downstream fork of vLLM. It builds the `odh-vllm-cpu-rhel9` container image, which serves LLM inference on CPUs without a GPU through vLLM's OpenAI-compatible HTTP API server. The RHOAI Konflux pipeline builds it for IBM Power (ppc64le) and IBM Z (s390x).

**Detailed**: `vllm-cpu` is a fork of upstream `vllm-project/vllm` maintained in `red-hat-data-services`. Per overlay 0014, IBM teams own it, and they use it to build CPU variants of the vLLM engine image (x86, Power and Z). The repository contains the full vLLM source tree: the Python engine, the OpenAI/Anthropic-compatible FastAPI front end, C++ CPU kernels and Rust helpers. The downstream part is mainly the build layer: `Dockerfile.konflux.cpu`, `build_vllm_ppc64le.sh` and `build_vllm_s390x.sh`, plus the legacy `Dockerfile.*.ubi` files.

On this branch the Konflux push pipeline (`.tekton/odh-vllm-cpu-v3-7-ea-1-push.yaml`) builds `Dockerfile.konflux.cpu` only for `linux/s390x` and `linux/ppc64le`. It publishes the result as `quay.io/rhoai/odh-vllm-cpu-rhel9:rhoai-3.7-ea.1`. The image runs `python -m vllm.entrypoints.openai.api_server` as UID 2000 and listens on port 8000 by default.

In the platform, this image is the engine behind the KServe `ServingRuntime` templates that `odh-model-controller` ships: `vllm-cpu-runtime-template` and `vllm-cpu-x86-runtime-template` (overlays 0014 and 0015). Those templates own the Kubernetes Service, Route/Gateway exposure and auth. This repository supplies only the engine and its HTTP API.

## Architectural Analysis

**A fork whose deliverable is a build recipe.** Almost all of the code is upstream vLLM. What RHOAI adds is a per-architecture build strategy. Neither Power nor Z has a usable upstream wheel ecosystem for vLLM's dependency tree, so `Dockerfile.konflux.cpu` delegates the builder stage to `build_vllm_$(uname -m).sh` (`Dockerfile.konflux.cpu:44-45`), and the two scripts diverge sharply:
- **ppc64le** (`build_vllm_ppc64le.sh`) pulls prebuilt torch, torchvision and opencv from IBM's DevPI (`wheels.developerfirst.ibm.com`). It gets torchaudio and other packages from the RHOAI public index, pinned to the stale `rhoai/3.5-EA2/cpu-ubi9` path. It builds protobuf from source.
- **s390x** (`build_vllm_s390x.sh`) installs `torch==2.11.0+cpu` from `download.pytorch.org` with `pypi.org` as an extra index. It builds a large set of packages from source via `git clone`: torchvision, xet-core, LLVM 15.0.7, llvmlite and numba, outlines-core, opencv-python and numactl. It also installs Rust through `curl https://sh.rustup.rs`.

The builder venv `/opt/vllm` is then copied wholesale into the runtime stage (`Dockerfile.konflux.cpu:138`).

**Non-hermetic supply chain.** The Konflux pipeline sets `hermetic: false`. The builds resolve packages from several non-Red Hat indexes using `--index-strategy unsafe-best-match`: IBM DevPI, PyPI, the PyTorch CDN, and GitHub sources cloned at build time. EPEL RPMs are installed from `dl.fedoraproject.org`. No AIPCC base image or AIPCC content channel is used. `UV_EXTRA_INDEX_URL` (IBM DevPI) and `UV_INDEX_STRATEGY=unsafe-best-match` are also baked into the **runtime** image environment (`Dockerfile.konflux.cpu:85-86`). As a result, any `uv pip install` run inside a serving pod would consult the IBM index with dependency-confusion-prone resolution. This is the most significant architectural risk in the component.

**Post-quantum UBI base.** Both stages use `registry.redhat.io/ubi9/ubi-minimal-pqc`, pinned by digest (`Dockerfile.konflux.cpu:8,63`). This gives the image the RHEL 9 system OpenSSL with PQC-enabled crypto policy. Python's `ssl` and `hashlib` link against that OpenSSL, so TLS (when enabled) and hashing inherit the RHEL crypto stack. vLLM has no explicit FIPS opt-in.

**Optional, path-scoped API-key auth.** `AuthenticationMiddleware` is added only when `--api-key` or `VLLM_API_KEY` is set (`vllm/entrypoints/openai/api_server.py:257-261`). Even then it guards only paths starting with `/v1`, `/v2` or `/inference` (`vllm/entrypoints/serve/utils/server_utils.py:40,91`). Root-level routes stay unauthenticated, including `/tokenize`, `/detokenize`, `/pooling`, `/classify`, `/score`, `/rerank`, `/generate`, `/invocations`, `/scale_elastic_ep`, `/start_profile`, `/stop_profile`, `/metrics` and `/health`. Some of these routes are compute-bearing or operational (scaling, profiling). In RHOAI the expected enforcement point is therefore the platform layer (KServe/Gateway/auth proxy), not vLLM itself. The middleware compares SHA-256 digests with `secrets.compare_digest`, which is a sound constant-time comparison. CORS defaults are fully permissive (`allowed_origins=["*"]`, `cli_args.py:258-263`).

**Optional engine-side TLS.** Uvicorn TLS is available through `--ssl-keyfile`, `--ssl-certfile`, `--ssl-ca-certs`, `--ssl-cert-reqs` (default `CERT_NONE`), `--ssl-ciphers` and `--enable-ssl-refresh` (`vllm/entrypoints/openai/cli_args.py:268-279`). It is off by default. No minimum TLS version is configured in vLLM, so the Python `ssl` defaults and system crypto policy apply.

**gRPC server is present in source but not in the image.** `vllm/entrypoints/grpc_server.py` provides a `VllmEngine` gRPC server (`--grpc`, documented port 50051). It uses `server.add_insecure_port` with reflection enabled (`grpc_server.py:107-118`). It depends on the `grpc` extra (`smg-grpc-servicer[vllm]`, `setup.py:1272`). The Konflux image installs only the `[tensorizer]` extra (`Dockerfile.konflux.cpu:57`), so the gRPC entrypoint would fail with an ImportError unless the servicer is added separately. This matches overlay 0014: the gRPC server is not wired into the OOTB templates.

**Build quirks worth noting.**
- `ARG VLLM_VERSION` is `0.24.0` in the builder stage but `0.21.0` in the runtime stage. Only the builder value is consumed, so the runtime ARG is stale noise.
- `LD_PRELOAD=/usr/lib64/libtcmalloc.so.4` is set for all architectures, but `gperftools-libs` is installed only on the ppc64le path. On s390x the preload is likely ignored with a loader warning.
- `VLLM_WORKER_MULTIPROC_METHOD=fork` and `VLLM_NO_USAGE_STATS=1` are set in the image. Usage telemetry is disabled.

## AIPCC Ecosystems Use

`Dockerfile.konflux.cpu` installs Python packages with pip and uv, but it does **not** use AIPCC base images, AIPCC content channels or AIPCC tooling. Both stages are based on `registry.redhat.io/ubi9/ubi-minimal-pqc`. Python packages come from IBM DevPI, PyPI, the PyTorch CDN, GitHub source builds, and (for some ppc64le packages) a stale RHOAI 3.5-EA2 public index path. To comply with Red Hat's product security requirements for secure builds, this component must be migrated to AIPCC base images; per overlay 0017, the CPU variant supports both ppc64le and s390x.
