## Purpose

**Short**: Builds and configures the RHOAI OGX (formerly Llama Stack) server container image (`odh-ogx-core-rhel9`). The image has pre-configured, env-var-activated providers for inference, vector storage, files, file processing, responses, messages, batches and tool runtime.

**Detailed**: `ogx-distribution` is a packaging repository, not an application codebase. It assembles a runnable OGX server image. OGX is the opendatahub-io fork of Llama Stack (`ogx==1.4.1+rhaiv.0`). The repo does three things: it pins the OGX Python package and its provider dependencies, it supplies a default run configuration (`distribution/config.yaml`), and it supplies a small shell entrypoint that execs `ogx run`. The repo contains no OGX server source code. All HTTP API behaviour comes from the upstream `ogx`/`ogx-api` packages.

The single source of truth is `build/build.yaml`. Generator scripts in `build/` turn it into several outputs:
- the runtime `config.yaml`, with dependency-only providers stripped
- the `Containerfile` and `Dockerfile.konflux`, with `config.yaml` embedded as a base64 OCI label (`com.ogx.config.config.yaml`)
- the hashed lock files
- the provider table in `distribution/README.md`

Every remote provider is gated by the `${env.VAR:+provider-id}` syntax. As a result, one image and one config serve every deployment scenario, and the operator or user enables backends by setting environment variables.

In RHOAI, the image is built hermetically by Konflux (`.tekton/odh-ogx-core-v3-7-ea-1-push.yaml`) into `quay.io/rhoai/odh-ogx-core-rhel9`. The OGX operator deploys it. The included `ServiceMonitor` selects pods labelled `app.kubernetes.io/managed-by: ogx-operator`. The OGX operator also nudges image references through `build-nudge-files`. At runtime the server listens on port 8321 and needs PostgreSQL for all KV/SQL state. It forwards inference to vLLM (KServe), MaaS, or public LLM APIs (OpenAI, Anthropic, Azure, Bedrock, Vertex AI, Gemini, watsonx), and uses remote vector stores (Milvus, pgvector, Qdrant).

## Architectural Analysis

**Configuration-as-artifact pattern.** The repository's main design choice is that `build/build.yaml` drives everything else. Generated files (`distribution/config.yaml`, `Dockerfile.konflux`, `Containerfile`, `distribution/README.md`, lock files) are regenerated by pre-commit hooks, and CI verifies them (`verify-konflux-dockerfile.yml`). Embedding the full `config.yaml` as a base64 OCI label (`Dockerfile.konflux:29`) means a consumer such as the operator can discover the default config, APIs and distribution name (`com.ogx.distribution.name="rh"`) from image metadata without running the image.

**Conditional provider activation.** Each remote provider's `provider_id` resolves to empty unless a trigger variable is set, for example `${env.VLLM_URL:+vllm-inference}` (`distribution/config.yaml:25`). OGX skips providers with an empty id. Local providers that are always on:
- `inline::builtin` for responses and messages
- `inline::localfs` files
- `inline::file-search`
- `remote::model-context-protocol`
- `inline::auto` file processors
- `inline::reference` batches

Seven provider types (`inline::docling`, `inline::faiss`, `inline::milvus`, `inline::pypdf`, `inline::markitdown`, `inline::sentence-transformers`, `remote::docling-serve`) are "dependency only". Their wheels are installed, but they need a user-supplied `config.yaml` (`distribution/config.yaml:4-11`). The result is a large image (torch 2.13, docling, sentence-transformers, pymilvus) with a narrow default runtime surface.

**State externalised to PostgreSQL.** Both storage backends (`kv_default` → `kv_postgres`, `sql_default` → `sql_postgres`) point at the same PostgreSQL instance (`distribution/config.yaml:198-214`). Responses, conversations, inference logs, prompts, connectors, vector-store metadata, file metadata, batches and the provider registry all live there. Files are on a local path (`/opt/app-root/src/.ogx/distributions/rh/files`) unless S3 is enabled. This split matters: blob data on local disk without a shared PVC prevents multiple replicas from sharing state, while all metadata is in Postgres.

**Secret hygiene in the entrypoint.** `distribution/entrypoint.sh` adds a `_FILE` indirection for 18 secret variables. It reads mounted secret files into the env at startup, rejects ambiguous configuration when both forms are set, and unsets the `_FILE` variable. A pre-commit check (`build/verify_secrets.py`) keeps this list in sync with `build.yaml`. Note that the values still end up in the exec'd `ogx` process environment. The mechanism avoids putting secrets in the Pod spec, not in process memory.

**Auth is opt-in and in-process.** `server.auth.provider_config.type` is `${env.AUTH_ISSUER:+oauth2_token}` (`distribution/config.yaml:261`). With no `AUTH_ISSUER`, the server runs unauthenticated. When it is set, OGX validates JWT bearer tokens against a JWKS endpoint and applies an owner-based ABAC policy: unowned resources are readable by everyone, any authenticated user can create, and only owners can read, update or delete their own resources. The entrypoint always passes `--insecure` to `ogx run`, so the server speaks plain HTTP. TLS termination is expected from the platform (Route, Gateway or service mesh) that the operator configures.

**Hermetic, AIPCC-based downstream build.** The Konflux Dockerfile uses AIPCC `cpu-torch2.13-el9.8` as its base and installs only from the Cachi2/Hermeto prefetch (`--no-index`, `Dockerfile.konflux:39-41`). It pulls models from a ProdSec-scanned "modelcar" image used as a build stage (`Dockerfile.konflux:12,65`), so no HuggingFace download happens at build time. The upstream `Containerfile.in` instead uses `odh-midstream-python-base-3-12` and `uv pip sync --verify-hashes`.

**Risks and observations:**
- **Plain HTTP.** The server is unauthenticated by default and always runs plain HTTP (`--insecure`). Security depends entirely on how the operator or platform deploys it.
- **`tls_verify` is configurable.** Outbound `tls_verify` for vLLM and the auth JWKS fetch defaults to `true` but can be turned off with env vars.
- **Fake default token.** `VLLM_API_TOKEN` defaults to the literal `fake` (`distribution/config.yaml:30`).
- **No RPM lockfile.** No `rpms.lock.yaml` is present. The Dockerfile runs `public-repos.sh` as root (`Dockerfile.konflux:50`), but the actual RPM installation step is commented out.
- **Dangling nudge reference.** `.tekton/...-push.yaml` references `build/operator-nudging.yaml`, which does not exist on this branch.
- **Debt markers.** Scanning for missing libraries is disabled (AIPCC-3688, `Dockerfile.konflux:54-55`). A comment says `uv` is uninstalled "to please FIPS gods" (`Dockerfile.konflux:43-44`).
- **Unverified tenant isolation.** The Praxis tenant-isolation tests (`tests/integration/praxis/`) use `x-tenant-id` and `x-user-id` headers set by a Praxis proxy in front of OGX. This points to an emerging multi-tenant front-door pattern, but this repo neither configures nor enforces it.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OAuth2 JWT + owner ABAC | Application (OGX) | Disabled unless `AUTH_ISSUER` is set. Unowned resources (models, providers) are world-readable. |
| Data storage | Shared PostgreSQL with ownership metadata; localfs files on the pod filesystem | Application | All users share tables. Isolation is by application query filtering only. |
| Network traffic | None defined in the repo | n/a (operator/platform) | No NetworkPolicy. The plain-HTTP server relies on platform TLS. |
| Compute & resources | None defined | n/a (operator) | A noisy user can saturate a shared instance. |
| Configuration & secrets | Process-wide env and provider credentials | Application | All users share the same upstream provider API keys. |
| API scoping | Owner-filtered list/read/delete for files and vector stores | Application | Verified by Praxis tests (403/404 cross-user and cross-tenant). Not verified in this repo for other APIs. |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| PostgreSQL (kv_default / sql_default) | Resource owner | Application query filter (ABAC) |
| Upstream inference providers | none | Shared credentials per instance |
| Remote vector stores (Milvus/pgvector/Qdrant) | Resource owner (metadata) | Application ABAC on vector-store metadata |
