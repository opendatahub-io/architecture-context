## Purpose

**Short**: A web admin UI and Go backend-for-frontend (BFF) for one NVIDIA OpenShell gateway, the open-source sandboxing platform for AI agents.

**Detailed**: openshell-dashboard is a standalone web application for one OpenShell gateway. It ships as a single container image (`quay.io/rhoai/odh-openshell-dashboard-rhel9`) that holds a Go HTTP server and the built React/PatternFly 6 single-page app. The BFF serves a REST API under `/api/v1` and the static UI. It turns each REST call into a gRPC call to the OpenShell gateway, mostly through the OpenShell Go SDK (`github.com/NVIDIA/OpenShell/sdk/go`). In three places it makes raw gRPC calls instead, to fill gaps in the SDK: binary-safe stdin exec for file upload, reading provider credential key names, and reading and writing whole provider profiles.

From the UI you can manage workspaces and their members, sandboxes (create, start, stop, delete, create from a template), and what happens inside a sandbox: logs (polled and streamed), an interactive WebSocket terminal, file upload and download, exposed services, settings, and attached providers. You can also manage per-sandbox security policies with revision history, review proposed policy changes ("drafts"), and edit the gateway-wide global policy and settings. Further screens cover credential providers and provider profiles, and give admins a gateway overview with lists across all workspaces.

The BFF keeps no state, runs no OIDC flows and makes no authorization decisions (ADR 0002). The Helm chart runs it with an oauth2-proxy sidecar that signs users in against an OIDC provider (Keycloak in the reference setup) and forwards the user's access token. The BFF sends that token to the gateway as `authorization: Bearer` on every gRPC call, and the gateway validates it and enforces roles and workspace membership. Releases follow the gateway's minor release line: this branch targets gateway `0.1.x` and was tested on `0.1.6`.

## Architectural Analysis

**Relay-only BFF and trust boundary.** The main design choice is that the BFF trusts the token header it receives (`x-forwarded-access-token`, else `Authorization: Bearer`) and never validates it (`backend/pkg/auth/proxy.go:75-98`). That is only safe when nothing but the auth proxy can reach the BFF. The Helm chart enforces this in three layers:
1. `LISTEN_ADDRESS=127.0.0.1`, so the BFF listens only inside the pod network namespace.
2. The Service exposes only the oauth2-proxy port (4180).
3. A NetworkPolicy admits ingress only on 4180, and only from the ingress namespace (default `openshift-ingress`).

Running the image any other way without these controls, for example with the BFF port 8080 published, lets any client present any token header. The token is still validated by the gateway, so the risk is mainly impersonation through header injection by anyone who can reach the BFF and who already holds a token. The `AUTH_DISABLED=true` dev mode turns token relay off completely (requests run as `dev-user`). It is hard-coded to `false` in the chart.

**Gateway is the source of truth.** The BFF adds no RPCs, objects or lifecycle states (ADR 0003). The role-based UI (platform admin / workspace admin / user) and the six `FEATURE_*` flags only hide parts of the UI and are not access control. Every route is always served, and the gateway enforces authorization. So the dashboard's security posture depends on the OpenShell gateway's OIDC and RBAC setup: the issuer, audience (`openshell-api`), roles claim and workspace membership keyed by `sub`.

**Transport security is split across three hops**, each configured on its own:
- **Browser → proxy.** TLS ends at the ingress: either an OpenShift Route (edge or reencrypt, with an insecure-to-Redirect policy) or a Gateway API HTTPRoute on an HTTPS listener. oauth2-proxy can also serve HTTPS itself when `authProxy.tls.secretName` is set.
- **Proxy → BFF.** Plain HTTP on loopback inside the pod.
- **BFF → gateway.** gRPC over TLS by default: `grpcs://openshell.<ns>.svc.cluster.local:8080`, verified against the `openshell-client-tls` CA. mTLS client certificates are optional.

When the BFF serves HTTPS itself it requires TLS 1.3 or newer (`inbound_tls.go:62-63`). The raw gRPC client sets a minimum of TLS 1.2 (`rawexec.go:69`). A plaintext gateway URL (`grpc://` / `http://`) is still accepted: `ContextAuthProvider.RequireTransportSecurity()` then returns false, and user bearer tokens travel unencrypted. The chart permits this when `gateway.tls.enabled=false` and no CA or client certificate secrets are set.

**Long-lived connections.** The terminal is the only WebSocket. It relays the gateway's interactive exec stream through `gorilla/websocket`, with a same-origin `CheckOrigin` check as defense-in-depth against cross-site WebSocket hijacking (`terminal_handler.go:286-294`). Handshakes with no Origin header are allowed, because they come from non-browser clients. Log streaming is a long-lived HTTP GET. `WriteTimeout` is deliberately left unset for these streams and for large uploads (up to 64 MiB, `app.go:64`). The OpenShift Route annotations set a 300 s timeout and a 1 h tunnel timeout to match.

**Packaging and lifecycle.** The component is installed with its own Helm chart (`deploy/helm/openshell-dashboard`), in the gateway's namespace (`openshell`). It does not use operator-managed kustomize manifests. No CRDs, controllers, webhooks or Kubernetes API calls exist: the pod runs with `automountServiceAccountToken: false` and needs no RBAC. Scaling is horizontal and stateless, with an optional HPA (1–4 replicas). Sessions live in oauth2-proxy's encrypted cookie, so no sticky sessions are needed. The extension hook (`pkg/server/extensions.go`) lets a downstream build add or override authenticated `/api/v1` routes without forking the router. `cmd/server` passes no extensions.

**Supply chain.** The Konflux build is hermetic, with npm and gomod prefetch, on digest-pinned UBI9 base images. The Go build uses `CGO_ENABLED=1` and `GOEXPERIMENT=strictfipsruntime`, which fits the check-payload FIPS gate. The oauth2-proxy sidecar image (`oauth2-proxy/oauth2-proxy:v7.15.2`) is an upstream image that this repo neither builds nor pins by digest by default. For RHOAI it would normally be replaced with a Red Hat-built proxy image. This is a gap to track.

**Version coupling.** Each dashboard release supports one gateway minor line (ADR 0005). The release line is compiled in (`models.BuiltInGatewayReleaseLine`), and `/api/v1/gateway/compatibility` reports whether the connected gateway matches. A mismatch is reported but never blocks requests. CI pins the gateway release, the SDK commit and the gateway image digests in `deploy/ci/gateway-pins.json`.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per OpenShell workspace (gateway concept), plus a platform scope for admins | `backend/pkg/server/app.go:198-266` |
| **Deployment model** | One dashboard instance per OpenShell gateway, in the gateway's namespace; shared by all users of that gateway | `README.md`, `docs/architecture.md` |
| **Tenant identifier** | Workspace name in the URL path (`/workspaces/{workspace}`); user identity = token `sub` | `backend/pkg/server/app.go:198`, `docs/authentication.md` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user token relayed to gateway; gateway enforces roles and workspace membership | OpenShell gateway (Application) | The BFF does no checks. The UI hides admin features by role only as a convenience. Isolation depends fully on the gateway |
| Data storage | None in dashboard (stateless); data lives in the gateway | Gateway | N/A |
| Network traffic | NetworkPolicy: only the ingress namespace can reach 4180; BFF bound to loopback | Kubernetes | No egress policy; no per-workspace network separation (not applicable to a UI) |
| Compute & resources | Single shared pod/Deployment; optional HPA | Kubernetes | A noisy user (large uploads up to 64 MiB, long WebSockets/log streams) can use shared BFF capacity; no per-user rate limiting |
| Configuration & secrets | One OIDC client secret, cookie secret and gateway CA/client cert for the instance | Kubernetes | The optional mTLS client cert identifies the BFF, not the user. The user token is still required per call |
| API scoping | Workspace in path; cross-workspace lists answered by the gateway only for platform admins | Gateway | — |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| OpenShell gateway (gRPC) | Workspace | Gateway-side token validation, roles and membership checks |
| BFF process / shared gRPC connection | Per-request token | `ContextAuthProvider` attaches each request's own token to every RPC |

| 6 | OpenShell gateway | OIDC issuer JWKS | 443/TCP | HTTPS | TLS | None (public keys) |
