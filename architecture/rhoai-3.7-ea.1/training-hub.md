## Purpose

**Short**: Training Hub is a Python library and CLI (`thub`). It gives one algorithm-focused API for LLM post-training: SFT, OSFT, LoRA, GRPO, GEPA prompt optimization and embedding fine-tuning. Each algorithm can run on more than one training backend.

**Detailed**: Training Hub is published to PyPI as `training-hub`. Users call one function per algorithm, such as `sft()`, `osft()`, `lora_sft()`, `lora_grpo()`/`grpo()`, `gepa()` and `embedding_sft()`, or the matching `thub <algorithm>` subcommand. Each call goes to a pluggable training backend: InstructLab-Training for SFT, RHAI Innovation Mini-Trainer for OSFT (continual learning), Unsloth for LoRA, OpenPipe ART or verl for GRPO, GEPA or MLflow for prompt optimization, and SentenceTransformers for embedding models. The library also includes GPU memory and runtime estimators, a loss-plotting utility, a callback framework, and JIT preemption checkpointing that can mirror checkpoints to S3-compatible object storage.

In RHOAI, Training Hub has no Kubernetes footprint of its own. It ships pre-installed in the `distributed-workloads` universal training images (`odh-th-torch-{cpu,cuda,rocm}-py312-rhel9`, which pin training-hub 0.11.2 in rhoai-3.7-ea.1). Those images run as Jupyter workbenches and as runtimes for Kubeflow Trainer v2 TrainJobs and legacy KFTO PyTorchJobs. The Kubeflow SDK's `TrainingHubTrainer` generates scripts that call Training Hub inside those pods (overlay 0009). Kubernetes integration happens only at runtime, through the environment the orchestrator injects: torchrun/`PET_*` rendezvous variables, `SIGTERM` on preemption, mounted PVCs and S3 credentials.

The repository is the RHAI Innovation Team's upstream. RHOAI consumes it as a pinned pip dependency, not as a separately built container. The repo has no Dockerfiles, kustomize manifests, CRDs or Konflux pipelines.

## Architectural Analysis

**Registry and adapter design.** The core abstraction (`src/training_hub/algorithms/__init__.py`) is an `AlgorithmRegistry` that maps algorithm names to `Algorithm` classes and maps each algorithm to named `Backend` implementations. `create_algorithm()` picks the first registered backend when none is given. Every algorithm module registers itself at import time and exposes a convenience function. Most heavy dependencies (Unsloth, ART, verl, GEPA, MLflow, sentence-transformers, s3fs) are imported lazily and declared as optional extras (`[lora]`, `[grpo]`, `[grpo-verl]`, `[gepa]`, `[embedding]`, `[s3]`, `[cuda]`). So the base install supports only SFT/OSFT, and the rest of the matrix depends on what the runtime image installed. The universal images resolve this by installing a curated superset.

**Distributed execution comes from the environment.** Training Hub does not create pods or talk to the Kubernetes API. `utils.get_torchrun_params()` reads `PET_NNODES`, `PET_NODE_RANK`, `PET_NPROC_PER_NODE`, `PET_MASTER_ADDR`, `PET_MASTER_PORT` and similar variables, which Kubeflow Trainer and KFTO inject, and falls back to the standard torchrun names. The InstructLab and Mini-Trainer backends launch torchrun workers. Because live Python callback objects cannot cross that process boundary, `adapters/serialize.py` writes each callback's class source to a base64 JSON payload file (mode 0600). The path goes in `TRAINING_HUB_CALLBACKS_PATH`, and workers rebuild the classes with `exec()`. This is a deliberate code-execution channel. Its integrity depends on the payload directory, which defaults to the checkpoint output dir on a shared PVC, being writable only by the job.

**Preemption-aware checkpointing.** `jit_checkpoint.py` installs a flag-only `SIGTERM` handler, deliberately avoiding logging inside the handler to prevent deadlocks. The flag is all-reduced (MAX) across ranks, so every rank saves at the next step boundary before the pod is killed. `checkpoint_manager.py` adds optional remote mirroring. With `checkpoint_storage="pvc"` (the default), checkpoints stay on the filesystem. With an fsspec URI such as `s3://bucket/prefix`, node 0 / local-rank 0 stages each checkpoint and uploads it from a background pool (4 workers, 3 attempts, `.upload_complete` marker). On restart it can restore from the remote copy. Storage access is checked by a write/read/delete probe at `train()` entry, so credential problems fail fast and don't surface hours into the run. This makes Training Hub suitable for Kueue-preemptible or spot-backed TrainJobs.

**Outbound integrations come from user configuration.** All network egress goes through third-party libraries, driven by user parameters or environment variables: Hugging Face Hub (model/dataset download via transformers/datasets), S3-compatible storage (s3fs/botocore with `AWS_ENDPOINT_URL_S3`), MLflow (`MLFLOW_TRACKING_URI`), Weights & Biases (`WANDB_*`), and LiteLLM-routed LLM endpoints for GEPA/GRPO (`OPENAI_API_BASE`/`OPENAI_API_KEY`). If an `api_base` is given without a key, GEPA sets `OPENAI_API_KEY="dummy"` so LiteLLM accepts local OpenAI-compatible endpoints such as vLLM. Training Hub sets no TLS policy itself: certificate validation and protocol versions are whatever requests, aiohttp and botocore default to.

**Risks and observations.**
- *CLI config is a code-execution trust boundary.* `thub` parameters marked `callable` (`--reward-fn`, `--rollout-fn`, `--evaluator`, `--adapter`, and others) are resolved with `importlib.import_module()` with no allowlist (`cli.py:386-433`). A YAML config from an untrusted author can run arbitrary code. The source documents this risk explicitly.
- *Supply-chain sensitivity.* The `litellm` dependency explicitly excludes compromised releases 1.82.7, 1.82.8 and 1.107.0 (credential-stealer/backdoor incidents). Dependencies use only lower bounds and the repo has no lock file. Reproducibility for RHOAI therefore depends on the downstream `distributed-workloads` image lock files, not on this repo.
- *`trust_remote_code`* is passed through to Hugging Face loaders in the LoRA path and memory estimators. It defaults to `False`.
- *No AIPCC/Konflux build here.* The repo produces only an sdist/wheel through GitHub Actions (`pypi.yaml`), with pinned-SHA actions and step-security harden-runner in audit mode. AIPCC base-image compliance belongs to the consuming image (`distributed-workloads`).
