## Purpose

**Short**: Container image and Python package that runs NVIDIA Garak LLM red-teaming scans (prompt injection, jailbreak, toxicity, OWASP/AVID/CWE profiles, intents-based risk assessment) as eval-hub evaluation jobs, either in the job pod or through a Kubeflow Pipeline.

**Detailed**: The component is a TrustyAI-maintained `FrameworkAdapter` for the eval-hub evaluation platform (`eval-hub-sdk[adapter]~=1.0.4`). eval-hub launches the image as a Kubernetes Job. The adapter reads a `JobSpec` (default path `/meta/job.json`, overridable with `EVALHUB_JOB_SPEC_PATH`) that names a benchmark profile (`quick`, `owasp_llm_top10`, `avid*`, `quality`, `cwe`, `intents`), a target model endpoint, and parameters. It resolves the profile, deep-merges user overrides into a Garak config, runs Garak, parses the JSONL/AVID reports into per-probe `EvaluationResult`s (attack success rate, TBSA aggregate), and reports status and results back to eval-hub through the SDK's sidecar callbacks. It can also push artifacts to an OCI registry and MLflow.

There are two execution modes. In **simple** mode (the default), the adapter runs the `garak` CLI as a subprocess inside the Job pod. In **KFP** mode (`execution_mode=kfp`, or the `evalhub.kfp_adapter` entrypoint), the Job pod only orchestrates. It submits a six-step Kubeflow pipeline (`validate → resolve_taxonomy → sdg_generate → prepare_prompts → garak_scan → write_kfp_outputs`) to Data Science Pipelines, polls it until it finishes, and pulls results from S3 storage set up through an OpenShift AI Data Connection secret. Only KFP mode supports the `intents` benchmark, which uses sdg-hub synthetic data generation (via LiteLLM) and Garak TAPIntent probes with a MulticlassJudge detector. Intents runs need four model roles: target, attacker, judge, and evaluator, plus an optional SDG model.

The repo name is historical. Versions up to 0.4.x were a Llama Stack eval provider, and 0.5.0 removed Llama Stack entirely (COMPATIBILITY.md). The downstream image is `quay.io/rhoai/odh-trustyai-garak-lls-provider-dsp-rhel9`. It is wired into the platform through the `garak-provider-image` key of the `trustyai-service-operator-config` ConfigMap, which the KFP pipeline reads to choose its component image.

## Architectural Analysis

**Stateless batch worker, not a service.** No code path opens a listening socket. The image has no `EXPOSE`, `io.openshift.expose-services=""` is set, and there are no Service, Route, or manifest definitions. The analyzer reports `uvicorn` as an entrypoint, but `requirements.txt:736` shows it is only a transitive dependency of `mcp` (pulled in by Garak). It is not used as a server. The repo has no kustomize manifests or RBAC. eval-hub (and the TrustyAI/ODH operator configuration) provides the Job spec, ServiceAccount, mounted secrets, and sidecar. This repo only supplies the workload image and the KFP pipeline definition.

**One image, two roles.** `Dockerfile.konflux` has no `CMD`. The downstream image is generic: eval-hub supplies `python -m llama_stack_provider_trustyai_garak.evalhub` (or `.evalhub.kfp_adapter`) for the Job, and KFP `@dsl.component(base_image=_resolve_base_image())` reuses the same image for every pipeline step. `_resolve_base_image()` resolves the image in this order: `KFPConfig.base_image`, then env `KUBEFLOW_GARAK_BASE_IMAGE`, then the `trustyai-service-operator-config/garak-provider-image` ConfigMap in `redhat-ods-applications` or `opendatahub`, then a hard-coded upstream `quay.io/trustyai/...@sha256` digest. Because this runs in a decorator, it is evaluated at module import time and needs Kubernetes API access to read ConfigMaps in the operator namespace. If that read is denied, the pipeline silently falls back to the upstream (non-RHOAI) image, which is a supply-chain and disconnected-install risk.

**Layered credential resolution with compatibility shims.** Much of `garak_adapter.py` exists to support several generations of eval-hub auth:
- **KFP client token:** taken from `KFP_AUTH_TOKEN`, then the auto-mounted SA token file, and otherwise left unset so the eval-hub sidecar proxy injects it. The sidecar model (evalhub >= 0.4.4) has `AutomountServiceAccountToken=false`.
- **S3 credentials:** five fallbacks are tried in order: in-cluster `read_namespaced_secret`, then `KFP_AUTH_TOKEN` against `KUBERNETES_SERVICE_HOST`, then the sidecar at `http://localhost:8080/api/v1/...` with the `Bearer k8s_sa_token:ref` placeholder, then S3 keys inside the model-auth secret, then a local kubeconfig.
- **Model API keys:** resolved through a 13-step chain per role (`core/pipeline_steps.py:resolve_api_key`) that ends in the literal `"DUMMY"`.

This makes the adapter work across environments, but it hides misconfiguration because failures are logged at debug level and the next path is tried. The `KFP_AUTH_TOKEN` path also turns off Kubernetes API TLS verification when the CA file is missing (`garak_adapter.py:898`).

**Secrets hygiene.** Intents configs force `api_key` to `__FROM_ENV__` so keys come from Kubernetes Secrets rather than the request. `config.json` is redacted (`redact_api_keys`) before OCI export and S3 upload. Garak runs with `shell=False` in its own process group, with SIGTERM/SIGKILL timeout handling (`core/garak_runner.py`).

**Build posture.** The downstream build is hermetic. Konflux sets `hermetic: true` and Hermeto prefetches pip wheels from a fully pinned `requirements.txt` compiled against the RHOAI 3.6 `cpu-ubi9` RHEL AI index. The build is multi-arch (x86_64, arm64, ppc64le, s390x) on an AIPCC `cpu-torch2.13-el9.8` base. The build removes `uv` from the base image to drop its bundled crypto (RHOAIENG-97373). However, `Dockerfile.konflux` switches to `USER root` and never switches back, so the image's default user is root. The upstream `Containerfile` does drop to 1001. In practice, OpenShift's restricted SCC assigns an arbitrary UID, which reduces the impact. Garak pulls in a very large dependency set, including torch, transformers, and many LLM-provider SDKs (OpenAI, Anthropic, Cohere, Mistral, Google, Replicate, Ollama, NVIDIA Riva). This widens the image's CVE surface well beyond what the adapter itself uses.

**Egress depends on the scan.** Network destinations depend on the scan config: the target/judge/attacker model endpoints (OpenAI-compatible HTTP), S3, the KFP API, the eval-hub sidecar, and optionally the OCI registry and MLflow through eval-hub callbacks. `NLTK_ALLOW_PROXIED_URLOPEN=1` and Hugging Face downloads (which can be pre-seeded from S3 via `hf_cache_path`) suggest that some Garak probes fetch corpora or models at runtime. That needs mirroring in disconnected clusters. A disconnected-readiness CI check exists (`.github/workflows/disconnected-readiness.yml`).
