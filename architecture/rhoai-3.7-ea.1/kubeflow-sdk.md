## Purpose

**Short**: A unified Python SDK (`kubeflow` package) that lets data scientists submit and manage Kubeflow Trainer TrainJobs, Katib optimization experiments, Spark Connect sessions and SparkApplications, Model Registry entries, and KFP pipelines from notebooks or scripts.

**Detailed**: The Kubeflow SDK is the developer entry point to the RHOAI training and data-processing stack. It exposes high-level client classes: `TrainerClient`, `OptimizerClient`, `SparkClient`, `ModelRegistryClient`, and `PipelinesClient`, the last re-exported from `kfp`. Each client turns Python calls into Kubernetes API operations, usually creating namespaced custom resources such as `TrainJob`, `Experiment`, `SparkConnect`, and `SparkApplication`. Some clients call REST APIs instead, as with Model Registry. The SDK authenticates with the caller's kubeconfig or the in-cluster service account. All authorization is therefore Kubernetes RBAC on the user's identity, and the SDK adds no server-side component.

The trainer package has pluggable backends. The Kubernetes backend creates TrainJob CRs. A container backend runs jobs locally through Docker or Podman, and a local-process backend runs them as subprocesses. The SDK serializes a user's Python training function into the TrainJob's container command, together with an optional `pip install` step. The trainer controller then runs that code inside the selected `ClusterTrainingRuntime` image. In RHOAI that image is typically the universal training image (overlay 0013).

The midstream fork (`opendatahub-io/kubeflow-sdk`) adds Red Hat AI extensions under `kubeflow/trainer/rhai/` that are not upstream:

- `TransformersTrainer`: HuggingFace/TRL with progress tracking and JIT checkpointing to PVC or S3.
- `TrainingHubTrainer`: integration with Training Hub algorithms (SFT, OSFT, LoRA) and user callbacks.
- `SpeculativeDecodingTrainer`: Eagle3 draft-model training with a vLLM sidecar.

These trainers inject instrumentation code into the training pod. That code runs a small HTTP metrics server and reports TrainJob progress to the Trainer controller over an authenticated HTTPS status endpoint. The fork tracks upstream `kubeflow/sdk` through daily merge-based sync (`.github/workflows/rebase-upstream.yaml`).

## Architectural Analysis

**A client library, not a service.** Nothing in this repository is deployed as a long-running workload. It has no kustomize manifests, no Konflux Dockerfile, no RBAC, and no Service. The analyzer reported an HTTP endpoint (`PATCH kubeflow.trainer.rhai.transformers.get_jit_checkpoint_injection_code`), a "kubeflow" Service, and a "FastAPI/Starlette, no auth" rule. All three are false positives from a `@patch(...)` mock decorator in `kubeflow/trainer/rhai/transformers_test.py:1607`, so they are left out of the tables below. The CRD under `hack/crds/` (SparkConnect) is a test fixture for Kind-based E2E. Its owner is the Spark Operator, so it is listed as a consumed API rather than one this repo defines. The only Dockerfile is `hack/Dockerfile.spark-e2e-runner`, an upstream test runner (`python:3.11-slim`) that is not shipped.

**Delivery is transitive.** Overlay 0012 describes the delivery chain. Upstream `kubeflow/sdk` feeds the midstream `opendatahub-io/kubeflow-sdk`, tagged `vX.Y.Z+rhaiv.N` by `.github/workflows/odh-release.yaml`. The AIPCC Python indexes then rebuild the wheel, which ends up in workbench and universal training images. The SDK's version, CVE posture, and FIPS behavior are therefore set by the consuming image's Python and OpenSSL, not by anything built here. The release workflow pins all dependencies to `==` versions from `uv.lock` and regenerates a hash-locked `requirements.txt` (2,267 `sha256` hashes).

**Identity and authorization belong to the caller.** Every Kubernetes interaction goes through `kubernetes.config.load_kube_config()` or `load_incluster_config()` (`kubeflow/trainer/backends/kubernetes/backend.py:54-56`). Tenancy and authorization are therefore exactly the caller's RBAC in their own namespace. When no namespace is configured, the default comes from the kube context or the service-account namespace file. One sensitive operation is RHAI cloud-storage support. It reads a "Data Connection" Secret (`read_namespaced_secret`, `kubeflow/trainer/rhai/utils.py:398`) only to list its keys, then injects `secretKeyRef` env vars into the TrainJob. Secret values are never copied into the CR, but the user still needs `get` permission on Secrets.

**Code generation is the main architectural pattern, and a risk to manage.** The trainer APIs, both upstream and RHAI, work by serializing Python source into container commands. They use `inspect.getsource`, AST-validated callbacks (`traininghub_callbacks.py`), and templated scripts such as `_render_speculator_training_script`. This makes the SDK effectively a remote code-execution client. Whatever the user's function contains runs in the training pod under that pod's service account. By default the generated scripts also run `pip install` against `https://pypi.org/simple` (`DEFAULT_PIP_INDEX_URLS`, `kubeflow/trainer/constants/constants.py:133`; overridable by env var). This matters for disconnected and air-gapped clusters and for supply-chain posture.

**In-pod servers created by the SDK.** The RHAI instrumentation starts `http.server.HTTPServer(("0.0.0.0", metrics_port))` inside training pods. The default port is 28080, validated to the range 1024-65535 for restricted SCC compatibility. The server is plain HTTP and has no authentication. The Trainer controller polls it based on the pod annotations `trainer.opendatahub.io/progression-tracking` and `trainer.opendatahub.io/metrics-port`. The speculator flow adds a `vllm-sidecar` container on `localhost:8234` (plain HTTP, loopback only). Separately, `update_trainjob_status()` POSTs progress to `KUBEFLOW_TRAINER_SERVER_URL` over HTTPS. That call uses a projected SA bearer token and a controller-supplied CA (`kubeflow/trainer/backends/kubernetes/utils.py:744-850`), with a 5 s minimum update interval, a 300 s token-cache TTL, and at most 256 metrics.

**Spark Connect locality.** Inside a cluster, `SparkClient` connects to the SparkConnect server's in-cluster address (`sc://...svc.cluster.local:15002`) over gRPC. Outside a cluster, it shells out to `kubectl port-forward` and connects to `sc://127.0.0.1:<port>`. Both paths are plaintext gRPC from the SDK's point of view. Outside a cluster, the port-forward tunnel through the API server is TLS-protected.

**Upstream-overlay drift.** Overlay 0012 states that `kubeflow.pipelines` is "planned but not yet available". In this version it exists: `kubeflow/pipelines/api/pipelines_client.py` re-exports `kfp.kubeflow_client.PipelinesClient`, behind the `pipelines` extra (`kfp[kubernetes]>=2.17,<2.18`). Overlay 0012 also lists v0.3.0 as the shipped version, while this branch is at 0.5.0.
