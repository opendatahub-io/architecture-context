## Purpose

**Short**: A Kubernetes operator that deploys and manages OGX (Open GenAI Stack, formerly Llama Stack) servers from `OGXServer` custom resources. It also ships an ODH/RHOAI module operator that installs the OGX operator itself, driven by a cluster-scoped `OGX` component CR.

**Detailed**: The root operator (`main.go`, image `rhoai/odh-ogx-operator-rhel9`) watches namespaced `OGXServer` (`ogx.io/v1beta1`) resources. For each one it renders an embedded kustomize base (`controllers/manifests/base`) into a per-instance Deployment, ClusterIP Service (default port 8321), ServiceAccount, a RoleBinding to `system:openshift:scc:nonroot-v2`, NetworkPolicy, and, when requested, PVC, PodDisruptionBudget, HorizontalPodAutoscaler, ServiceMonitor/PrometheusRule and Ingress. It also generates the OGX runtime `config.yaml` from declarative CR fields (`spec.providers`, `spec.resources`, `spec.storage`, `spec.disabledAPIs`, optional `spec.baseConfig`). The result goes into an immutable, content-hashed ConfigMap mounted at `/etc/ogx/config.yaml`. Provider and storage credentials are injected as Secret-backed environment variables. The operator then polls each server's `/v1/providers` and `/v1/version` endpoints to fill in status. A validating admission webhook (`vogxserver.kb.io`) enforces distribution, provider, volume and external-access rules.

The operator also implements the RHOAI 3.6+ "Praxis-fronted" topology. With `spec.praxisMode.enabled: true`, OGX is an internal-only backend: the NetworkPolicy only admits Praxis gateway pods and the operator namespace, no Ingress is created, the Responses and Conversations APIs are disabled in the generated config, and `server.auth` is rewritten to trust upstream `x-user-id`/`x-tenant-id` headers. An optional migration Job moves Responses/Conversations data to the Praxis database. The operator also supports adopting storage and networking from legacy `LlamaStackDistribution` (`llamastack.io/v1alpha1`) deployments through annotations.

The `ogx-module/` subtree (image `rhoai/odh-ogx-module-operator-rhel9`) is a separate Go module and manager. It reconciles the singleton cluster-scoped `OGX` CR (`components.platform.opendatahub.io/v1alpha1`, instance `default-ogx`). Its image bundles the root operator's `config/` kustomize tree under `/manifests/ogx/`. The module picks the `overlays/rhoai` or `overlays/odh` overlay from the platform name, renders it into the applications namespace with `odh-platform-utilities`, and applies the root operator's CRDs, RBAC, Deployment, webhook and monitoring resources. It reports readiness and an aggregate `OGXServer` health summary on the `OGX` status. This lets the ODH/RHOAI platform operator manage OGX as a pluggable module.

## Architectural Analysis

**Two-tier operator layout.** The repo holds two operators. The platform operator creates the `OGX` CR. `ogx-module` reacts by deploying the root OGX operator from manifests baked into its own image: an init container copies `/manifests` to an `emptyDir`, then the manager renders them. The root operator then reconciles user `OGXServer` CRs. So the root operator's manifests and image are the deployment contract between the two layers. Image overrides come in through `RELATED_IMAGE_ODH_OGX_K8S_OPERATOR_IMAGE` and `RELATED_IMAGE_ODH_OGX_CORE_IMAGE`, which `ogx-module` rewrites into `params.env` before rendering (`ogx-module/internal/controller/ogx/reconciler.go:72-80`). The module filters out the Namespace object, makes CRDs cluster-scoped, and only applies ServiceMonitor/PrometheusRule objects when `monitoring.coreos.com/v1` is discoverable.

**Label-scoped informer caches.** The root operator restricts its informer cache: ConfigMaps and Secrets are only cached when labeled `ogx.io/watch: "true"`, and owned workload types only when labeled `app.kubernetes.io/managed-by: ogx-operator` (`main.go:107-136`). This reduces memory use and limits which user Secrets the controller sees. However, the ClusterRole still grants cluster-wide `get/list/watch` on Secrets, so the restriction is an application-level choice, not an RBAC boundary. User-referenced Secrets and ConfigMaps (provider keys, CA bundles, base/override configs) must carry the watch label or the operator won't see changes to them.

**Config generation pipeline.** When `spec.baseConfig` is absent, the operator reads OCI image config labels (`com.ogx.distribution.default-config`, `com.ogx.config.<file>`) straight from the distribution image's registry using a bare `net/http` client. It probes HTTPS first and silently falls back to plain HTTP (`pkg/config/oci_fetcher.go:145-170`). It sends no registry credentials, so this only works for anonymously pullable images. It is also an egress path that matters for disconnected clusters and a downgrade risk on untrusted networks. The `configgen` CLI (`cmd/configgen`) runs the same pipeline offline for validation and debugging. It is not deployed.

**Network posture differs by mode.** Praxis mode is opt-in per CR: `isPraxisModeEnabled` requires `spec.praxisMode.enabled` to be explicitly `true` (`api/v1beta1/ogxserver_webhook.go:148`). In legacy mode the NetworkPolicy admits all pods in the namespace plus the OpenShift router, and `spec.network.externalAccess` can create a `networking.k8s.io/v1` Ingress. The webhook requires a hostname and TLS secret for that Ingress, so TLS terminates at the ingress controller and traffic to the 8321 backend is plain HTTP. In Praxis mode the operator reports `PraxisReachable` and `TLSConfigured` conditions instead of rejecting the CR. On this branch, `spec.network.tls.secretName` is only checked for existence (`controllers/praxis_preflight.go:76-106`); no code was found that mounts that Secret into the OGX Deployment. The operator's own status polling uses `http://<svc>.<ns>.svc.cluster.local:<port>` with a 5-second timeout (`controllers/ogxserver_controller.go:1128-1137, 1899`). Server-side mTLS for OGX is therefore expected to come from the distribution image or platform, not from this operator.

**TLS follows the OpenShift cluster profile.** Both managers read the `config.openshift.io/v1 APIServer` TLS profile and adherence policy at startup through `openshift/controller-runtime-common` (`pkg/tls/tls.go`, `ogx-module/pkg/tls/tls.go`). The resulting `tls.Config` options apply to the webhook and metrics servers. A watcher restarts the process when the profile changes. Off OpenShift, or when the APIServer object is missing, they fall back to the Intermediate profile. If strict adherence is set without usable ciphers, startup fails.

**Metrics auth is uneven.** In the OpenShift overlay, the root operator's metrics server uses HTTPS with service-CA certificates and `filters.WithAuthenticationAndAuthorization`, i.e. TokenReview/SubjectAccessReview (`main.go:202-213`, `config/overlays/openshift/manager_metrics_patch.yaml`). The vanilla `config/default` path still references a kube-rbac-proxy sidecar patch, but that patch isn't listed in the kustomization, so metrics bind according to the manager's own flags. `ogx-module` always serves metrics over TLS (`SecureServing: true`) but never sets a `FilterProvider` (`ogx-module/cmd/ogx-module/metrics.go:11-24`). Its `/metrics` on 8443 therefore needs no authentication, even though `metrics-auth-role` (TokenReview/SubjectAccessReview) is bound to its ServiceAccount.

**Privilege concentration in `ogx-module`.** `manager-cluster-role` can create, update and delete ClusterRoles, ClusterRoleBindings, CRDs and ValidatingWebhookConfigurations cluster-wide, because it has to install the root operator. That makes the module ServiceAccount effectively cluster-admin-adjacent. Its cache is limited to the operator and applications namespaces (`ogx-module/cmd/ogx-module/main.go:101-111`), and its garbage collector deletes all managed objects in the applications namespace (`InNamespace(cfg.ApplicationsNamespace)`).

**Legacy API surface.** `config/crd/bases/llamastack.io_llamastackdistributions.yaml` and `api/v1alpha1` are still in the tree, but the CRD is not in `config/crd/kustomization.yaml` and the type is not registered in the manager scheme. The operator only deals with legacy LlamaStackDistribution resources by adopting their PVCs, Services and Ingresses and scaling down their Deployments (`controllers/legacy_adoption.go`). At startup it also deletes legacy ClusterRoleBindings from earlier operator versions (`pkg/cluster/cluster.go:48-90`).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-OGXServer ServiceAccount + nonroot-v2 SCC RoleBinding; Praxis header auth in OGX | Kubernetes / Application | Header-based identity trusts whoever can reach port 8321, so it relies on the NetworkPolicy; legacy mode has no operator-enforced server auth |
| Data storage | Per-CR PVC in CR namespace; external SQL/KV via user Secrets | Kubernetes | Shared external DBs are user-managed |
| Network traffic | Per-CR NetworkPolicy (Praxis: Praxis pods + operator namespace; legacy: same namespace + router) | Kubernetes | Legacy mode allows all pods in the namespace; NetworkPolicy can be disabled (warning only in Praxis mode) |
| Compute & resources | Per-CR resources, HPA, PDB, topology spread | Kubernetes | No ResourceQuota/LimitRange created |
| Configuration & secrets | User Secrets/ConfigMaps in CR namespace, label-gated (`ogx.io/watch`) | Kubernetes / Application | Operator SA holds cluster-wide Secret `get/list/watch`; label filtering only restricts the cache |
| API scoping | OGXServer namespaced; operator watches cluster-wide; ogx-module cache scoped to operator + applications namespace | Kubernetes / Application | Operator has cluster-wide reach by design |
