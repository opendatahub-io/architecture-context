## Purpose

**Short**: This is the AI Gateway control plane. It installs a Praxis ExtProc dataplane for each MaaS tenant, and reconciles `ExternalModel`, `ExternalProvider` and `AIGuardrail` resources into Gateway API, Istio and ExtProc configuration that routes inference requests to external LLM providers.

**Detailed**: `ai-gateway-controller` is a sibling of `maas-controller`. `ai-gateway-operator` deploys both under the shared `AIGateway.spec.modelsAsAService.managementState` toggle (`DESIGN.md:237-281`). It replaces the control-plane half of the legacy `payload-processing` (IPP) component, which used to watch `ExternalModel`/`ExternalProvider` and also run the Envoy ExtProc dataplane. The dataplane role moves to **Praxis** (`praxis-extproc`). This controller installs Praxis and generates its configuration.

The binary runs four reconcilers (`cmd/manager/main.go:188-246`):
1. **Tenant reconciler** (`pkg/tenant`). Its primary watch is `MaasTenantConfig`. For each tenant whose `maas.opendatahub.io/payload-processing-type` annotation selects Praxis (the default when the annotation is absent), it renders the vendored `praxis-extproc` kustomize manifests, post-renders the placeholders, renames the resources per tenant, and server-side-applies them into the tenant's Gateway namespace. A dedicated ExternalModel ExtProc copy goes into the tenant namespace. A compare-and-swap annotation handshake (`payload-processing-status`) hands off with maas-controller's IPP deployment.
2. **ExternalModel / ExternalProvider reconcilers** (`pkg/controller`). They publish content-addressed routing overlays, per-model `HTTPRoute`s, provider transport (`ExternalName` Service, `ServiceEntry`, `DestinationRule`), and reference-only credential projections. They also handle Gateway attachments (`spec.gatewayRefs`), cross-namespace providers gated by `ReferenceGrant`, and staged withdrawal with request draining.
3. **Consumer portal reconciler** (`pkg/consumerportal`). It deploys a `kube-auth-proxy` OIDC auth proxy, `HTTPRoute`s, Kuadrant `AuthPolicy`s and TLS `DestinationRule`s so the MaaS consumer portal can be reached through the default tenant Gateway in OIDC mode.
4. **AIGuardrail reconciler** (`pkg/guardrail`). It validates `AIGuardrail` policies that reference TrustyAI `NemoGuardrails` services. The tenant reconciler compiles accepted policies into NeMo callout filters in the post-auth ExtProc chain and opens NetworkPolicy egress to the NeMo pods.

The controller does not serve request traffic itself. Its only listeners are the health probe and metrics endpoints. All of its effects go through Kubernetes API writes that configure the Istio/Envoy Gateway (`openshift-ingress`), the Praxis ExtProc pods, and Kuadrant policy.

## Architectural Analysis

**A control plane that writes into infrastructure namespaces.** The controller is deployed in `opendatahub`, but almost everything it creates lives elsewhere. The Praxis ExtProc Deployments, Services, NetworkPolicies, ServiceMonitors, HPAs, `EnvoyFilter`s and `DestinationRule`s go into the Gateway namespace (`openshift-ingress` by default). ExternalModel ExtProc copies, `HTTPRoute`s, provider Services/ServiceEntries and `agc-cred-<hash12>` credential copies go into tenant or model namespaces. The consumer portal proxy goes into `MaasTenantConfig.status.infraNamespace`. Because of this the controller has a single, broad ClusterRole (`config/self/rbac/clusterrole.yaml`) with cluster-wide `secrets` create/patch/delete, `clusterroles`/`clusterrolebindings` create/patch, `roles`/`rolebindings`, `envoyfilters` and `authpolicies` CRUD. The repo's own comments say the safety boundary here is ownership labels and field-manager checks (`pkg/tenant/ownership.go`), not RBAC: "RBAC cannot scope verbs by label ... the agc-cred- name and ownership labels are controller safeguards, not RBAC restrictions" (`clusterrole.yaml:110-116`). Compromising this ServiceAccount would therefore give an attacker cluster-wide Secret and Gateway filter-chain control.

**No Go dependency on its sibling.** `MaasTenantConfig`, `AITenant`, `MaaSSubscription`, `MaaSModelRef`, `NemoGuardrails` and `DSCInitialization` are all read as `unstructured.Unstructured` against hardcoded GVKs, so `models-as-a-service` (with its kserve/knative/KEDA graph) is never imported (`DESIGN.md:758-772`). The dependency footprint stays small (controller-runtime, client-go, kustomize `krusty`). The cost is that the controller is coupled to maas-controller's object schemas and annotation state machine (`payload-processing-type`/`payload-processing-status`, `aitenant-name`/`aitenant-namespace`) only through string contracts. A schema drift in MaaS fails at runtime, not at compile time.

**Two controllers share resource names.** Legacy IPP and Praxis use the same Gateway-namespace resource names (`payload-processing`, `payload-pre-processing`, `payload-processing-plugins`). Ownership is coordinated by a CAS-claimed status annotation on `MaasTenantConfig` (`cleanup-complete` → `steady`), mirrored in `pkg/tenant/migration.go`. Defensive gates sit on top of the handshake:
- an IPP-shaped plugins ConfigMap blocks Praxis apply unless `force-payload-processing-migration=true` is set (`DESIGN.md:385-395`);
- the field-manager/label ownership checks keep cleanup from deleting foreign objects;
- `--deletion-timeout` (default 10m) force-removes the `PraxisCleanupFinalizer` if cleanup cannot be confirmed.

**Manifests vendored and baked into the image.** The `praxis-extproc` `deploy/overlays/odh` tree is vendored at a pinned commit (`hack/scripts/get-manifests.sh`) and `COPY`'d into the image under `/config/manifests` (`Dockerfile.konflux:33-35`). It is rendered at runtime with `krusty` plus a placeholder post-render step (`pkg/render`). The dataplane manifest version therefore follows the controller image, while the dataplane container image comes from `RELATED_IMAGE_ODH_PRAXIS_EXTPROC_IMAGE`. A related design choice makes upgrades tolerant: the operator vendors the controller's Deployment args at a different commit than the image, so `dropUnknownFlags` (`cmd/manager/flags.go:50-94`) drops unrecognised flags instead of crash-looping (RHAI-15815). For the same reason the manifest deliberately avoids restating defaults (`config/self/manager/manager.yaml:27-42`).

**Fail-closed request path with staged withdrawal.** Every injected ExtProc filter sets `failure_mode_allow: false`. The ExternalModel ExtProc filters are installed Gateway-wide but disabled per route, and the controller re-enables them only on its own routes, so ordinary MaaS/KServe routes are unaffected (`config/manifests/external-model/overlays/odh/external-model-envoy-filter.yaml:256-278`). Provider removal is staged:
1. A reduced overlay is published.
2. The controller confirms the serving ExtProc revision by tailing pod logs (`pods/log` get, `pkg/controller/reconciler.go:130`).
3. After a drain interval, routes, credential copies and transports are deleted.

If revision evidence is missing, cleanup is blocked rather than allowed. Reading pod logs as a correctness signal is unusual. It ties control-plane progress to the ExtProc log format, and the design notes accept that both quoted and unquoted revision log forms must be supported.

**Secrets stay as references.** Overlays and HTTPRoute annotations carry Secret names, never key material (`pkg/controller/reconciler.go:2998-3003`). Credentials reach the tenant ExtProc as Secret mounts, and secrets from other namespaces are copied into the tenant namespace as `agc-cred-<hash12>`. The design documents that a copy is "exposure, not isolation": anyone who can read Secrets or create pods in the tenant namespace can read it. It also notes that a `ReferenceGrant` for a cross-namespace provider trusts the model namespace's Service/HTTPRoute writers with the provider namespace's credential (`DESIGN.md:540-567`).

**Risks and observations.**
- The default `--kube-auth-proxy-image` fallback is the mutable tag `quay.io/opendatahub/odh-kube-auth-proxy:odh-stable` (`cmd/manager/main.go:287`), and so is `kube-auth-proxy-image` in `params.env`. RHOAI builds are expected to override both with a digest-pinned `RELATED_IMAGE_*`.
- `config/self` hardcodes namespace `opendatahub` and the monitoring NetworkPolicy allow-list (`redhat-ods-monitoring`, `openshift-monitoring`). RHOAI namespace substitution happens in `ai-gateway-operator` and is not visible here.
- Leader election is enabled (`--leader-elect`) but `replicas: 1`, so there is no HA for the control plane.
- The EnvoyFilters match multiple Istio filter-name variants (the `extenstions` typo in Istio ≤1.25, `wasmplugin`, `trafficextension` in ≥1.30, RHCL `envoy.filters.http.wasm`). They are brittle against future Istio/RHCL filter renames.
- `DESIGN.md` still records open questions about end-to-end RBAC sufficiency of the `ai-gateway-operator` wiring.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | MaaS auth on Gateway (Kuadrant); one shared controller SA with cluster-wide ClusterRole; cross-namespace provider use requires ReferenceGrant | Platform (Kuadrant) / Application | Controller SA can read/write Secrets cluster-wide; ownership labels are not an authorization boundary (stated in `DESIGN.md`) |
| Data storage | No persistent storage; credentials as Secrets in provider/model/tenant namespaces; copies `agc-cred-*` in tenant namespace | Kubernetes / Application | Credential copies are readable by anyone with Secret read or pod create in the tenant namespace |
| Network traffic | Per-tenant ExtProc NetworkPolicy (ingress only from Istio gateway pods; egress DNS/API + NeMo); portal proxy NetworkPolicy (Gateway + Authorino only) | Kubernetes | `--skip-network-policy` removes them; NeMo egress widens to the whole NeMo namespace when the Service selector is unreadable |
| Compute & resources | Per-tenant ExtProc Deployments with requests/limits; optional HPA from `MaasTenantConfig` | Kubernetes | Shared Gateway Envoy across tenants within a Gateway namespace; Gateway-wide 10 MiB listener buffer limit |
| Configuration & secrets | Per-tenant plugins ConfigMap and overlay ConfigMaps; Gateway-namespace DestinationRules carry tenant identity labels | Application | Gateway namespace (`openshift-ingress`) is shared; tenants cannot read it (CA errors deliberately do not disclose Secret names) |
| API scoping | Cluster-wide watches by default; optional `--external-model-namespace` scope; per-namespace provider status ownership following the tenant's selected dataplane | Application | Tenant attribution derived from namespace and annotations; bugs in attribution would cross tenants |
