## Purpose

**Short**: OpenShell is a policy-enforced sandbox runtime for autonomous AI agents. A central gateway creates, governs, and brokers access to isolated agent sandboxes on Kubernetes.

**Detailed**: OpenShell (upstream NVIDIA/OpenShell, now moving to CNCF governance) gives AI agents controlled access to files, packages, network endpoints, and credentials. Operators declare what each agent may touch in a sandbox policy. OpenShell enforces that policy at runtime using kernel-level controls (filesystem and syscall confinement inside the sandbox) and an L7 network proxy with OPA/Rego evaluation in the supervisor. A Z3-backed prover (`openshell-prover`) checks proposed policy changes before they are approved, so risky new access can wait for human review. Agents never see real provider credentials. The supervisor adds credentials only to requests bound for approved endpoints.

The RHOAI 3.7 EA1 distribution ships four Konflux-built images: **gateway** (`odh-openshell-gateway`), **supervisor** (`odh-openshell-supervisor`), **sandbox runtime** (`odh-openshell-sandbox`), and **CLI** (`odh-openshell-cli`). The gateway is the control plane. It exposes the `openshell.v1.OpenShell` gRPC API (sandboxes, workspaces, providers, policies, SSH/exec sessions, TCP forwarding, logs) and a small HTTP surface for auth discovery, health, and metrics, all on one multiplexed TLS port. Through the in-tree Kubernetes compute driver, the gateway creates `agents.x-k8s.io` `Sandbox` resources (Kubernetes SIG Agent Sandbox) and supervisor Pods. Supervisors register back to the gateway and enforce policy for the workloads they host. The statically linked sandbox binary is injected into arbitrary agent images.

In RHOAI, OpenShell is installed per namespace through an ODH-fork installer (`deploy/rhoai/install.py`). The installer deploys two Helm releases: the gateway chart from this repo and `openshell-dashboard` (a separate repo). Prerequisites are Agent Sandbox CRDs and controller, a customer-managed OIDC issuer (validated with Red Hat build of Keycloak), and a NetworkPolicy-enforcing CNI. The repo's README states this is "an initial installer, not a qualified RHOAI deployment". It is not operator-managed in this release.

## Architectural Analysis

**Three-tier trust model.** The architecture separates three trust tiers:

1. **Gateway**: trusted control plane. Holds the database, credential storage, signing keys, and Kubernetes RBAC.
2. **Supervisor**: trusted policy enforcer, running outside the agent workload. Holds the network proxy, OPA, credential injection, and process/session runtime.
3. **Sandbox workload**: untrusted agent code, confined by the sandbox runtime binary.

Supervisors authenticate to the gateway with gateway-minted Ed25519 sandbox JWTs. These are bootstrapped by exchanging a projected Kubernetes ServiceAccount token (`IssueSandboxToken`, validated with `TokenReview` plus pod name/UID lookup). User clients authenticate with OIDC bearer tokens, mTLS client certificates, or both. A configurable listener can accept bearer-only clients while still validating any client certificate presented. Gateway replicas authenticate to each other the same way, using projected-token `TokenReview` (`peer-role.yaml`).

**Shared vs dedicated supervisors.** The chart can deploy a shared supervisor pool (StatefulSet `supervisor.yaml`, Service on runtime port 5500, HPA, PDB). The gateway assigns sandboxes to supervisor instances (`openshell-supervisor-control`). Without the pool, each sandbox gets a dedicated supervisor Pod created directly by the Kubernetes driver. A supervisor NetworkPolicy limits ingress on the runtime port to workload pods (`openshell.ai/boundary-role: workload`). Supervisor egress is unrestricted at the Kubernetes layer (`egress: - {}`) because policy-approved sandbox egress flows through it. Egress control is therefore an application-layer property of the supervisor proxy, not of Kubernetes.

**Pluggable drivers, many compiled in.** The Rust workspace has 40+ crates. Compute drivers cover Kubernetes, Docker, Podman, MicroVM/VFIO, and Windows MXC. Credential drivers cover the default encrypted DB store (AES-256-GCM with a KEK Secret), Kubernetes Secrets, and Vault. Extension points include gateway interceptors and supervisor middleware, both exposed as gRPC contracts (`proto/gateway_interceptor.proto`, `proto/supervisor_middleware.proto`, `proto/compute_driver.proto`, `proto/credential_driver.proto`). The Konflux gateway build uses `--no-default-features --features defaults-without-telemetry,vendored-z3`. The in-tree compute drivers are still compiled in, but anonymous telemetry is compiled out. The Helm value `server.telemetryEnabled: true` is therefore inert in RHOAI images.

**State and HA.** The default backend is SQLite (WAL) on a per-pod PVC, so the default workload is a single-replica StatefulSet. Multi-replica HA requires `server.externalDbSecret` (PostgreSQL URI) plus `workload.kind=deployment`. Replicas coordinate through a headless peer Service and `Peer*` RPCs (`PeerRelay`, `PeerNotifyConfigUpdate`, and others). The HPA is disabled by default.

**Workspace isolation modes.** `drivers.kubernetes.workspaceMode` sets how much cluster privilege the gateway needs:

- **`shared`** (default): all sandboxes run in one namespace using a namespaced Role.
- **`managed`**: the gateway creates and deletes per-workspace namespaces. This requires a ClusterRole with namespace create/delete, cluster-wide pod/sandbox CRUD, and Secret create/delete.
- **`operator`**: uses pre-provisioned namespaces labelled for discovery, granted through the separate `openshell-workspace` chart.

Choosing `managed` widens the gateway's blast radius considerably.

**Risks and observations.**

- **FIPS:** Konflux FIPS checks are explicitly non-blocking on all four pipelines (`fips-check-blocking: false`, citing OCPEXCEPT-75/76). The Rust TLS stack is rustls with the `aws-lc-rs` provider (vendored, not system OpenSSL). `openshell-crypto::verify_posture(require_fips=true)` deliberately returns `UnsupportedPosture`. `ring` is also present in `Cargo.lock` through transitive dependencies (`hickory-proto`, `quinn-proto`). The sandbox binary is statically linked (`+crt-static`) and does not read the system crypto policy. Runtime images use `ubi-minimal-pqc` with the `DEFAULT:PQ` crypto policy (post-quantum hybrid key exchange). That is a hardening signal, not FIPS validation.
- **Discrepancies with the analyzer:** the analyzer reported a `guardrails-server` service and an `/api/v1/*, /api/v2/*` "header passthrough" auth rule. Neither has any source support in this repository, so both are omitted below.
- **Kubernetes Secrets credential driver:** when enabled, its Role grants read/write on *all* Secrets in the credential namespace, because Secret names are runtime SHA-256 hashes. The chart warns that a dedicated namespace is recommended.
- **Unsafe flags:** these exist, are off by default, and are documented as dev-only: `server.auth.allowUnauthenticatedUsers`, `server.disableTls`, `oidc.dangerouslyAllowInsecureHttp`, and CLI/SDK `--insecure` (skips TLS verification).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | OIDC roles (platform admin/user) + workspace membership and workspace roles | Application (gateway) | Single gateway SA holds all Kubernetes permissions for all workspaces. `allowUnauthenticatedUsers` (off) bypasses user auth |
| Data storage | Shared SQLite/PostgreSQL with workspace-scoped records. Per-sandbox workspace PVCs | Application / Kubernetes | Logical (row-level) isolation only in the DB |
| Network traffic | NetworkPolicy: sandbox SSH only from gateway. Supervisor runtime only from workload pods. Supervisor L7 proxy enforces per-sandbox egress policy | Kubernetes + Application | Supervisor pod egress unrestricted at the Kubernetes level. Requires a NetworkPolicy-enforcing CNI |
| Compute & resources | Per-sandbox Pods. Optional RuntimeClass (e.g. kata), user namespaces (`enableUserNamespaces`), shared vs dedicated supervisors | Kubernetes | Shared mode puts all workspaces' sandboxes in one namespace. Shared supervisor pool hosts many sandboxes |
| Configuration & secrets | Provider credentials encrypted (AES-256-GCM) per record, injected only to approved endpoints | Application | KEK shared across workspaces. Kubernetes Secrets driver Role covers all Secrets in its namespace |
| API scoping | `shared`: single namespace Role. `managed`: per-workspace namespaces (cluster-wide RBAC). `operator`: pre-provisioned labelled namespaces | Kubernetes | Managed mode grants namespace create/delete and cluster-wide pod/sandbox CRUD |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Gateway database (SQLite/PostgreSQL) | Workspace | Application query filtering and authz |
| Shared supervisor pool | Sandbox generation | Routing preface + pinned TLS identity per generation. Per-sandbox policy |
| Credential store / KEK | Workspace/provider record | AES-256-GCM with AAD record binding |
