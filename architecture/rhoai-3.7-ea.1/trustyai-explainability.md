## Purpose

**Short**: TrustyAI's Java explainability library plus the Quarkus "TrustyAI Service", which ingests model inference payloads and computes fairness, drift, and explainability metrics that it publishes to Prometheus.

**Detailed**: This repository is the Java core of the TrustyAI project. It is a Maven multi-module build. `explainability-core` contains the XAI algorithms (LIME, SHAP, counterfactuals via OptaPlanner, PDP, TSSaliency) plus fairness and drift metrics. `explainability-connectors` holds the KServe v1/v2 HTTP and gRPC prediction-provider clients. `explainability-arrow` bridges to the TrustyAI Python library over Apache Arrow. `explainability-integrationtests` holds the Kogito DMN/PMML/OpenNLP tests. `explainability-service` is the deployable REST service, branded `odh-trustyai-service` in container labels (`Dockerfile.konflux:44-52`).

At runtime the TrustyAI Service is a passive data sink and metrics engine. ModelMesh payload processors POST partial request/response payloads to `/consumer/kserve/v2`. KServe InferenceService loggers send CloudEvents (`org.kubeflow.serving.inference.request|response`), which arrive through Quarkus Funqy Knative Events. The service reconciles each request with its response into a dataframe and persists it to memory, a PVC flat file (CSV), MinIO, or a MariaDB/MySQL database via Hibernate ORM. Users register recurring metric requests (SPD, DIR, identity, Mean-shift, KS-test, Fourier MMD). A Quarkus scheduler recomputes them every `service.metrics-schedule` and publishes them as `trustyai_*` Micrometer gauges at `/q/metrics` for Prometheus to scrape. In ODH builds, explainer endpoints call back into the model server over KServe v2 gRPC to generate local and global explanations.

In RHOAI the service is not deployed from this repo's kustomize manifests. trustyai-service-operator reconciles `TrustyAIService` CRs and puts kube-rbac-proxy sidecars in front of the service container. In the RHOAI 3.7-ea.1 build configuration, however, the operator and the platform bundle reference `RELATED_IMAGE_ODH_TRUSTYAI_SERVICE_PY_IMAGE` (`odh-trustyai-service-py-rhel9`, from the separate Python `trustyai-service` repo). Neither `RELATED_IMAGE_ODH_TRUSTYAI_SERVICE_IMAGE` nor `odh-trustyai-service-rhel9` appears in `RHOAI-Build-Config/bundle/bundle-patch.yaml`. The last konflux-central pipeline reference for this repo is a 3.6-ea-2 push pipeline. For 3.7-ea.1, this Java service image looks superseded by the Python reimplementation, and the repo's main ongoing value is as the upstream source of the Java library and as the legacy service.

## Architectural Analysis

**Library-plus-service monorepo with a decoupled downstream build.** Only `explainability-service` (and the core and connector modules it embeds) ships in the image. `.syft.yaml` excludes tests and demos from the SBOM. The Konflux Dockerfile does not compile anything. It unzips a prebuilt Quarkus fast-jar produced by Red Hat PNC (Project Newcastle), which is pinned by URL and SHA-256 in `artifacts.lock.yaml` and fetched by Hermeto/cachi2 into `./cachi2/output/deps/generic`. It then copies the four Quarkus layers onto a digest-pinned `ubi9/openjdk-17-runtime`. As a result, the Konflux image build is hermetic (RPM lock, artifact lock, digest-pinned bases), but the build provenance of the Java bytecode sits in PNC, outside this repo. The `trigger-pnc-build.yaml` workflow that kicks off PNC builds is scoped only to branches matching `rhoai-2.1[6-9]+` (line 7). On the 3.x branch, the artifact `999.0.0.managedsvc-redhat-01483` may therefore be stale relative to the source at this commit, so the latest Quarkus/Vert.x bump (`a5533dc`) may not be in the shipped jar.

**Profile-gated feature surface.** All XAI endpoints are wrapped with Quarkus REST `@EndpointDisabled`. The `%rhoai` profile keeps fairness and drift enabled and disables SHAP, LIME, counterfactual, TSSaliency, and global explainers (`application.properties:111-118`). `/data/download` is disabled by default everywhere except tests. The RHOAI product surface is therefore limited to metrics, data ingestion/upload, and metadata, and the outbound gRPC path to model servers exists only when explainers are enabled. Which profile the PNC artifact was built or launched with cannot be verified from this repo: the upstream `Dockerfile` builds with `-Dquarkus.profile=odh`, and `Dockerfile.konflux` sets no `QUARKUS_PROFILE`.

**Security is delegated to the platform.** The service has no authentication or authorization code (no quarkus-oidc, quarkus-security, or JWT dependencies). It serves plain HTTP on 8080 and optionally HTTPS on 4443 with a cert mounted at `/etc/tls/internal` (`application.properties:1-7`). Access control depends entirely on the operator-injected kube-rbac-proxy sidecars. In the operator template, the "internal" proxy on 4443 deliberately bypasses auth for `/`, `/consumer/kserve/v2`, and health paths so that ModelMesh and KServe can push payloads. As a consequence, any in-cluster client that can reach the service can inject inference data, and so influence fairness and drift metrics, unless NetworkPolicies restrict it. Outbound gRPC to model servers uses `usePlaintext()` with a new channel per request (`KServeV2GRPCPredictionProvider.java:128-130`). SSRF risk on the explainer `target` is reduced by `LocalServiceURLValidator`, which only accepts dot-less short hostnames, effectively restricting targets to same-namespace Services.

**Legacy in-repo manifests overreach.** `explainability-service/manifests` dates from 2023 (KfDef, `odh-manifests` era). It grants a cluster-wide ClusterRole with full CRUD on `configmaps` to `trustyai-serviceaccount`. The Java service has no Kubernetes client, so the only consumer of that permission is an `ose-cli` init container that runs `oc apply` to write a `model-serving-config` ConfigMap pointing ModelMesh at the service (`trustyai-deployment.yaml:62-81`). The Route uses `tls: null` (plaintext), and the ServiceMonitor scrapes over HTTP. These manifests should be treated as historical and not representative of the RHOAI deployment.

**Data-plane risks.** Storage defaults to a 1 Gi RWO PVC with a single replica, so there is no HA. The DB credentials default to `quarkus/quarkus` when environment variables are absent (`application.properties:69-70`), and `hibernate-orm.database.generation` defaults to `update`. CloudEvent payload decompression is capped at 100 MB to guard against gzip bombs (`CloudEventConsumer.java:77`). A `HibernateMigrator` supports one-shot migration from PVC CSV storage to a database.
