## Purpose

**Short**: A standalone Kubernetes operator that reconciles a singleton, cluster-scoped `Monitoring` CR into the RHOAI observability stack: metrics, traces, usage logs, log forwarding, dashboards, signal correlation and alerting.

**Detailed**: odh-observability is the observability module that was split out of the opendatahub-operator. It can run standalone through its Helm chart, or the platform operator (rhods-operator/opendatahub-operator) can drive it using the ModuleHandler pattern, typically through `DSCInitialization.spec.monitoring`. It watches a single `Monitoring` resource (`services.platform.opendatahub.io/v1alpha1`, required name `default-monitoring`). For each configured capability it renders embedded Go `text/template` YAML into operand CRs owned by other operators, then applies them with Server-Side Apply. Those operand CRs are:

- MonitoringStack and ThanosQuerier (Cluster Observability Operator)
- TempoMonolithic or TempoStack (Tempo Operator)
- OpenTelemetryCollector and Instrumentation (OpenTelemetry Operator)
- LokiStack (Loki Operator)
- ClusterLogForwarder (Cluster Logging Operator)
- Perses, PersesDatasource and PersesDashboard (Perses / COO)

It does not ship Prometheus, Tempo, Loki or an OTel Collector itself. Instead it checks which prerequisite operators are installed, using OLM OperatorConditions and ClusterExtensions plus CRD discovery, and deploys only the subsystems whose CRDs are present.

The operator also deploys several pieces of its own around those operands:

- **Namespace-scoped query proxies.** These are Deployments with three containers: kube-rbac-proxy, then a "method-gate" sidecar (the operator's own binary), then prom-label-proxy. They sit in front of the Data Science Prometheus and Thanos Querier, so tenants can query only series labelled with namespaces they are authorized for.
- **A Korrel8r Deployment** for correlating metrics, traces and logs.
- **NetworkPolicies** for every operand.
- **A ValidatingAdmissionPolicy.**
- **PrometheusRules** for operator alerting.
- **Accelerator (DCGM) recording rules.**

A mutating admission webhook in the same binary adds the `monitoring.opendatahub.io/scrape=true` label to ServiceMonitors and PodMonitors created in opted-in namespaces. That label is what lets the OTel TargetAllocator and the Prometheus pipeline discover workload monitors.

In RHOAI, the operator writes operand resources into the monitoring namespace given by `spec.namespace` (for example `redhat-ods-monitoring`). The operator itself runs in the operator namespace. Its image is `quay.io/rhoai/odh-observability-rhel9`, built from `Dockerfiles/Dockerfile.konflux` for x86_64, arm64, ppc64le and s390x.

## Architectural Analysis

**Template-rendering operator with capability gating.** `MonitoringReconciler` runs a fixed sequence of "action functions": webhook readiness, operator monitoring, admission policies, MonitoringStack/Thanos, tracing, OTel collector, alerting, node metrics endpoint, Korrel8r, Perses and Perses datasources. Usage logs and log forwarding are handled through `deployLokiStacks`. Each action checks the spec trigger, verifies its required CRDs exist, sets a feature condition and adds template sources to a shared list. The whole set is rendered and applied in one Server-Side Apply pass using the `odh-platform-utilities` deployer (field owner `monitoring`, ordered apply, cached). After the apply, label-based garbage collection (`platform.opendatahub.io/part-of=monitoring`) deletes anything that was not rendered. That is how removing a capability, or setting `managementState: Removed`, tears down its operands.

Features that are not configured are marked with Info severity, so they do not make the operator look Degraded. Missing prerequisites set `MonitoringDependenciesReady=False` and stop reconciliation without retrying. Recovery relies on the CRD watch, which re-triggers reconciliation when the missing operator is installed. All watches feed a singleton handler (`default-monitoring`).

**Main risk: cluster-wide informer footprint.** The controller caches cluster-scoped informers for Secrets, ConfigMaps, Namespaces, CRDs, EndpointSlices, Routes, Deployments, Jobs, Services, ServiceAccounts and ClusterRoles/Bindings. The Helm values document about 1.7 GiB steady state on a small cluster, with a 3 GiB limit (`charts/odh-observability/values.yaml:30-42`). Memory therefore grows with cluster size, not with the number of CRs. The analyzer also reports that the named-resource filtering of the watch predicates cannot be resolved statically (`monitoring_reconciler.go:1274-1303`).

**Defence-in-depth tenancy on metrics.** The most security-relevant design is the namespace-scoped query path:

1. kube-rbac-proxy (:8443) authenticates the caller with TokenReview. It then runs a SubjectAccessReview `get metrics.k8s.io/pods` for every `namespace=` value in the URL.
2. The method-gate (:9092, loopback) runs `/manager method-gate`. For Prometheus it allows only GET/HEAD. For Thanos it also allows URL-encoded form POSTs, but only to read-only query APIs, and it rejects any POST whose body contains a `namespace` field (`cmd/main.go:315-384`).
3. prom-label-proxy (:9091, loopback) adds the namespace matcher to the PromQL query.

The method-gate closes a known bypass: without it, prom-label-proxy would merge a namespace from the POST body into a label matcher that was only authorized for the URL namespace. Reusing the operator image for the sidecar means no extra image has to be mirrored for disconnected installs. The trade-off is that `OPERATOR_IMAGE` is required, and reconciliation fails if it is unset (`templatedata.go:851-860`).

The external routes are `data-science-prometheus-route`, `data-science-thanos-querier-route` and `data-science-prometheus-cluster-proxy`. All three are `reencrypt` and point at the proxies, never at the raw Prometheus or Thanos Services. Thanos on port 10902 stays internal, and NetworkPolicy limits it to the proxy and in-cluster consumers.

**Cluster TLS profile propagation.** TLS settings are not hard-coded:

- **Webhook listener (:9443).** The operator reads the OpenShift `APIServer` TLS profile and adherence policy using `odh-platform-utilities/framework/tls`. Under Strict adherence it applies the profile's minimum version and cipher suites, and forces HTTP/1.1 ALPN. If the APIServer object cannot be read, it falls back to a "Strict Intermediate" stand-in, exposes the `odh_observability_webhook_tls_degraded` gauge, and polls every 30 s for recovery. When the profile changes it exits with code 0 so the pod restarts with the new settings (`cmd/tls.go`).
- **kube-rbac-proxy operands.** The operator converts the resolved profile into `--tls-min-version`, `--tls-cipher-suites` and `--tls-curve-preferences` flags. When the cluster is in FIPS mode, it drops curves that are not FIPS-approved. If the cluster's FIPS status cannot be determined, reconciliation fails closed (`internal/controller/proxy_tls.go:48-140`).

This makes the operator a good example of honouring the platform TLS profile.

**Operational trade-offs worth noting.**

- **Webhook failure policy.** The webhook uses `failurePolicy: Fail` by default. If the operator is unavailable, creating or updating a PodMonitor or ServiceMonitor in an opted-in namespace is rejected. To catch this, an in-process admission probe writes a canary PodMonitor every 5 minutes into a dedicated probe namespace. The result drives the `webhook_admission_probe_*` metrics and the `MonitoringWebhookAdmissionPathDown` alert.
- **API-server-to-webhook traffic.** NetworkPolicy cannot reliably express this traffic, which originates on the host network. The chart therefore uses machine, pod and service CIDR `ipBlock` rules that default to OpenShift/ROSA install values (`values.yaml:85-88`). Clusters with a non-default machine CIDR must override them, or admission will fail.
- **Cluster-wide monitor discovery.** The TargetAllocator selects labelled monitors across the whole cluster, because KServe creates monitors in workload namespaces. Secret access is limited to a `secretNamespaces` allowlist with namespace-scoped Roles. `denyFSAccessThroughSMs` blocks file-backed credentials in selected monitors.
- **Broad operator RBAC.** The operator ClusterRole includes `*` on `monitoring.coreos.com` podmonitors/servicemonitors and create/update/delete on core Secrets cluster-wide. Updates and deletes on RBAC objects are restricted to named resources. Much of this breadth exists because the operator must hold every permission it grants to collector, Korrel8r and proxy ServiceAccounts.

**Test fixtures in analyzer inventory.** The analyzer lists `lgtm` (`docker.io/grafana/otel-lgtm`) and `oauth-proxy` (`quay.io/openshift/origin-oauth-proxy`) Deployments, Services and a binding. They come from `tests/e2e/prerequisites/inference/lgtm.yaml` and are e2e test prerequisites, not shipped operands. They are listed below for completeness and marked as test-only.
