## Purpose

**Short**: A library of reusable Kubeflow Pipelines (KFP) components and pipelines. It also builds the init-container image that stages RHOAI "managed pipelines" for the Data Science Pipelines API server, plus the runtime images that AutoML and AutoRAG pipeline tasks run in.

**Detailed**: `pipelines-components` (Python package `kfp-components`) is the downstream RHOAI fork of `kubeflow/pipelines-components`. It holds KFP v2 components (`@dsl.component`) and pipelines (`@dsl.pipeline`) grouped by category: data processing (dataset download, parse/chunk, SDG, AutoML data loaders, AutoRAG document discovery/extraction/indexing, Milvus ingestion), training (SFT/OSFT/LoRA/LoRA-GRPO fine-tuning via the Kubeflow Trainer, speculator training, AutoGluon AutoML, AutoRAG template optimization), evaluation (lm-eval, EvalHub, GRPO eval, speculator), and deployment (KServe InferenceService/ServingRuntime deployment, embedding model deployment, speculative-decoding serving, Model Registry registration). Each asset has a `metadata.yaml`. Assets marked `managed: true` are compiled and shipped as platform-managed pipelines.

Konflux builds four images from this repo. `odh-pipelines-components-rhel9` is a one-shot init container. At image build time it compiles every `managed: true` pipeline (currently AutoGluon tabular, AutoGluon timeseries, AutoRAG documents-indexing, and AutoRAG documents-RAG-optimization) into KFP IR YAML plus a `managed-pipelines.json` manifest. At runtime it copies them to `/config/managed-pipelines` for the KFP API server deployed by the Data Science Pipelines Operator (DSPO). If DSPO passes any non-empty `RELATED_IMAGE_*` environment variables, the init container recompiles the pipelines so they reference the operator-pinned runtime image digests. `odh-automl-rhel9` and `odh-autorag-rhel9` are the task images those pipelines run in; both are AIPCC CPU torch 2.13 based and carry AutoGluon, or ai4rag/Docling/LangChain plus bundled Docling and Whisper modelcar weights. `odh-autorag-inference-rhel9` is a placeholder runtime image for serving AutoRAG-generated agents.

The component does not run a long-lived service itself. It runs inside the platform's Data Science Pipelines (Argo/KFP) stack. Pipeline task pods call the Kubernetes API (KServe, Kubeflow Trainer, ODH HardwareProfiles, TokenReview), S3-compatible object storage, Hugging Face, MaaS/OpenAI-compatible LLM endpoints, Milvus/PGVector vector stores, MLflow, and Model Registry. Credentials reach the task pods as Kubernetes Secrets mounted as environment variables.

## Architectural Analysis

**Build-time compilation with a runtime override.** The managed-pipeline design moves KFP compilation into the image build: `RUN python -c "... generate_managed_pipelines import main ..."` in `Dockerfile.konflux.pipelines-components:27`. At runtime the init container only copies files, so it is fast and needs no network. For relocation, `should_recompile_managed_pipelines()` (`scripts/generate_managed_pipelines/generate_managed_pipelines.py:233-235`) switches to a full recompile when any `RELATED_IMAGE_*` variable is set. Image pinning therefore spans three repos: this repo's `utils/consts.py`, the ODH operator `imageParamMap`, and DSPO `params.env`/manager env (documented in `docs/CONTRIBUTING.md:1113-1180`). If those three drift apart, compiled pipelines fall back to mutable defaults such as `quay.io/opendatahub/odh-automl:odh-stable` (`utils/consts.py:3-4`). That is a disconnected-install and reproducibility risk whenever the operator does not set the variable. The init script guards against path traversal when reading the manifest (`init_managed_pipelines.py:25-27`).

**Components are code that runs on someone else's image.** Most components declare `base_image=` and run in pipeline task pods. The image references are mixed: AIPCC-derived AutoML/AutoRAG images, digest-pinned `odh-pipeline-runtime-datascience-cpu-py312-rhel9` for Ray RAG, and tag-only community or upstream images such as `quay.io/opendatahub/odh-th06-cpu-torch291-py312:odh-3.4`, `quay.io/opendatahub/odh-th-torch-cpu-py312:odh-3.6-ea.2`, and `registry.access.redhat.com/ubi9/python-311:latest` (`components/deployment/speculative_decoding_serving/component.py:10`). Only the AutoML and AutoRAG images are built and shipped from this repo, so the supply-chain posture of non-managed components depends on images outside this repo's Konflux control. Several components also use `packages_to_install`, which resolves pip packages at pod start time.

**Privileged-ish actions from pipeline pods.** The deployment and fine-tuning components act as Kubernetes clients from within a pipeline run. They create or patch KServe `InferenceService`/`ServingRuntime` objects, read ODH `HardwareProfile`s (`components/deployment/model_deployment/component.py:106-327`), and submit Kubeflow Trainer jobs through `TrainerClient` (`components/training/finetuning/sft/component.py:153-166`). The fine-tuning setup requires an explicit `KUBERNETES_SERVER_URL` + `KUBERNETES_AUTH_TOKEN` (a `kubernetes-credentials` secret) and verifies TLS against the in-cluster CA (`components/training/finetuning/shared/setup.py:41-60`). The effective authority of a pipeline is therefore whatever that token, or the pipeline runner ServiceAccount, can do in the user's namespace. This repo ships no RBAC manifests.

**AutoRAG starter-kit artifact.** `components/training/autorag/shared/assets_generator/starter_kit_templates/agentic_rag/` is a template that AutoRAG emits for users. It is not deployed by this repo. It is a FastAPI app (`POST /v1/responses`, `GET /health`, default port 8000) with an optional `auth_wrapper.py` that enforces Kubernetes TokenReview authentication on `/v1/responses` and can pin a single allowed ServiceAccount username. The OpenShell sandbox Containerfile binds uvicorn to `127.0.0.1:8080` behind the sandbox supervisor and uses proxychains to tunnel DB sockets through an HTTP CONNECT proxy. The analyzer reports "no auth middleware" because it only inspected `main.py`. Auth exists in the wrapper, but only if the wrapper is used.

**Risks observed.**
- The Model Registry component hardcodes plain HTTP (`is_secure=False`, `http://` scheme prefixing) in `components/deployment/kubeflow_model_registry/component.py:109-118`.
- The AutoRAG Dockerfile patches an installed `docling_core` file in place with `sed` (`Dockerfile.konflux.autorag:20-24`). This is fragile across docling-core upgrades.
- The Python requirement files point at the AIPCC **staging** index (`.../cpu-torch2.13-el9.8-test/simple`) even on this release branch.
- The init container base is UBI `python-312`, not AIPCC, and sets the crypto policy to `DEFAULT:PQ` (`Dockerfile.konflux.pipelines-components:6`).
- `PROTOCOL_BUFFERS_PYTHON_IMPLEMENTATION=python` and an `os._exit` workaround for an s390x segfault (`Dockerfile.konflux.pipelines-components:10,27`) show multi-arch fragility in the protobuf C extension.

## AIPCC Ecosystems Use

Three of the four Konflux Dockerfiles use the AIPCC CPU torch 2.13 base image. `Dockerfile.konflux.pipelines-components` installs Python packages on a **non-AIPCC** base (`registry.redhat.io/ubi9/python-312`). It still resolves packages from the AIPCC `cpu-torch2.13-el9.8` channel index through `requirements.txt` and the Hermeto pip prefetch. To comply with Red Hat product security requirements for secure builds, it must migrate to an AIPCC base image, even though it uses no accelerator-specific libraries.
