## Purpose

**Short**: A Python CLI (`llmdbenchmark`) and harness container image. It stands up an llm-d inference stack on Kubernetes or OpenShift, runs repeatable LLM inference benchmarks against it, collects results in a standard Benchmark Report format, and tears the stack down afterwards.

**Detailed**: llm-d-benchmark is the performance-evaluation toolkit of the llm-d project. Its `llmdbenchmark` CLI (`llmdbenchmark/cli.py`) has the subcommands `plan`, `standup`, `update`, `smoketest`, `run`, `teardown`, `experiment` and `results`. Configuration is merged deterministically: `config/templates/values/defaults.yaml`, then a scenario/specification (`config/scenarios`, `config/specification`), then `LLMDBENCH_*` environment variables, then CLI flags. The merged configuration is rendered through the Jinja2 templates in `config/templates/jinja/` into reviewable Kubernetes manifests and helmfiles. The CLI then applies them with `kubectl`/`helm`/`helmfile` subprocesses. Supported deployment methods are standalone vLLM (Deployment + Service), modelservice (Helm + Gateway API + GAIE EPP + LWS), kustomize-based well-lit-path guides, and Fast Model Actuation (FMA).

In the run phase the CLI does the following:
1. Discovers or accepts the model-serving endpoint.
2. Renders workload profiles into ConfigMaps.
3. Launches one or more harness pods in a harness namespace. The pods use the `ghcr.io/llm-d/llm-d-benchmark` image, built from `build/Dockerfile`.
4. Collects results from a workload PVC through a data-access pod.
5. Optionally uploads results to GCS or S3.

The harness image bundles several load generators: inference-perf v0.7.0, vllm-benchmark (vLLM v0.32.0), guidellm v0.8.1, InferenceMAX `bench_serving`, aiperf v0.13.0, lm-eval 0.4.13, and a `nop` harness. It also bundles the analysis scripts that turn raw outputs into Benchmark Report v0.2 documents (`benchmark-report/`, published separately as the `llmd-benchmark-report` package).

Two auxiliary deliverables live in the same repo:
- **`llm_d_stack_discovery`**: a read-only tool with its own Dockerfile and a ClusterRole manifest. Starting from an OpenAI-compatible URL, it walks Routes, Gateways, HTTPRoutes, InferencePools and vLLM pods, and emits the stack configuration in Benchmark Report format.
- **`benchmark-report`**: a library of schemas, validators and converters.

Within RHOAI, the component is a benchmarking and validation client for llm-d-based serving (KServe LLMInferenceService / llm-d stacks). It is not a runtime service in the serving data path.

## Architectural Analysis

**Client-side orchestrator rather than an in-cluster controller.** All control logic runs on the operator's workstation or a CI runner. The CLI is a step-based pipeline: `executor/step_executor.py` runs numbered steps from `standup/steps`, `run/steps` and `teardown/steps`, either sequentially or in parallel per stack. Cluster mutations go through two routes: the Kubernetes Python client (`utilities/cluster.py`), and shell-outs to `kubectl`, `oc`, `helm` and `helmfile` (`executor/command.py`). Nothing in the repo watches cluster state continuously. This is why the analyzer found no CRDs, webhooks, HTTP servers or gRPC services: the tool *creates* resources owned by other components (Gateway API, GAIE InferencePools, LWS, KEDA ScaledObjects, WVA, FMA, PodMonitors) but defines none itself.

**Declarative render-then-apply design.** The `plan` phase renders every manifest to a workspace before anything is applied. This gives reproducibility (each result traces back to its exact rendered inputs) and reviewability. It also means the security posture of the deployed stack is mostly decided by template defaults in `config/templates/values/defaults.yaml`. Two examples:
- Namespaces are labelled `pod-security.kubernetes.io/audit|warn: privileged`.
- The harness ServiceAccount is bound to `system:openshift:scc:restricted`. Harness pods can be switched to `privileged: true` through `harness.privileged`, which defaults to false.

**Harness image is upstream-oriented, not product-hardened.** `build/Dockerfile` has the following properties:
- It starts from `docker.io/library/python:3.13.5-slim-bookworm` (Debian).
- It installs the `oc`/`kubectl` binaries from mirror.openshift.com, the Google Cloud SDK GKE auth plugin, and AWS CLI v2, all fetched with `curl`/`wget` and no checksum verification.
- It clones the harness repos by tag with `git clone` and installs CPU torch from download.pytorch.org.
- It runs `install.sh` inside the image.
- It configures an rsync daemon on port 20873.

The s390x variant (`build/Dockerfile.s390x`) is the only one that uses UBI9 (`ubi9/ubi-minimal:9.6`). The repo has no `Dockerfile.konflux*`, no `.tekton/` pipelines, and no hermetic lock files (`rpms.lock.yaml`, `uv.lock`, `requirements.txt` with hashes). Images are published to `ghcr.io/llm-d` by GitHub Actions (`.github/workflows/ci-release.yaml`, `ci-nightly-benchmark-build-image.yaml`). For a RHOAI distribution this is a significant supply-chain gap: a downstream fork or Konflux pipeline would be needed to produce a supportable image, and none is visible on this branch.

**TLS verification is deliberately relaxed in several paths.** The code favours "works on any cluster" over strict verification:
- Token-based cluster login sets `verify_ssl = False` (`llmdbenchmark/utilities/cluster.py:99`) and passes `--insecure-skip-tls-verify=true` to `oc login` (`cluster.py:565`).
- Thanos/Prometheus queries use `curl -k` (`run/steps/step_09a_capture_cluster_state.py:60,402`).
- Endpoint smoke tests use `curl -sk` from ephemeral pods (`utilities/endpoint.py:810`).
- The vLLM pod preprocess script falls back to `ssl.CERT_NONE` when the kubeconfig has no CA (`standup/preprocess/set_llmdbench_environment.py:960`).

These are acceptable for a benchmarking tool, but the tool should not be treated as a reference for secure client behaviour.

**Unused generic kustomize template.** `util/deploy/` is a generic StatefulSet + Service + Route + RBAC kustomization with placeholder variables (`${PROJECT_NAME}`, `${NAMESPACE}`, `${IMAGE_TAG_BASE}`). No code in the repo references it. It has two latent defects:
- The Service selector `app: ${PROJECT_NAME}-service` does not match the StatefulSet's pod label `app: ${PROJECT_NAME}-statefulset`.
- The exec RoleBinding grants `pods/exec` to the `system:authenticated` group.

It references a ServiceAccount `operator-controller-manager` that it does not create. The analyzer reported these resources as the component's Service and Route. In practice they are scaffolding and not part of the benchmark workflow.

**Results and telemetry egress.** Results leave the cluster through several routes:
- `kubectl cp` from the data-access pod.
- `gcloud storage cp` / `aws s3 cp` (`utilities/cloud_upload.py`).
- The google-cloud-storage SDK (`results_store/client/gcs.py`), with an HTTP fallback through the Prism proxy (`results_store/client/gcs_proxy.py`, default `https://prism.llm-d.ai`).
- Optional HTTP telemetry POSTs with a Google OIDC bearer token (`telemetry/http.py`, `telemetry/google_auth_provider.py`). Telemetry is off unless `LLMDBENCH_TELEMETRY_ENABLED` is set.

Default egress to llm-d-operated infrastructure (Prism) matters in disconnected or regulated RHOAI environments.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-namespace SA + Role; secret access scoped by resourceName | Kubernetes | Standup of shared infrastructure (CRDs, Gateway, LWS, ClusterRoles) needs cluster admin. The unused `util/deploy` RoleBinding grants exec to `system:authenticated`. |
| Data storage | Per-namespace workload PVC and model PVC | Kubernetes | rsync daemon exposes results without auth to any pod that can reach the ClusterIP Service |
| Network traffic | None (no NetworkPolicies rendered) | — | Harness, data-access and model pods are reachable cluster-wide |
| Compute & resources | Optional resource requests/limits; capacity validator checks GPU availability | Application | No ResourceQuota/LimitRange; namespaces labelled PSA `privileged` (audit/warn) |
| Configuration & secrets | Per-namespace HF token Secret and profile ConfigMaps | Kubernetes | HF token may be rendered as plaintext `stringData` into workspace manifests on disk |
| API scoping | Namespaced operations except admin prerequisites and teardown of ClusterRoles | Application | `llm-d-stack-discovery` uses a cluster-wide read ClusterRole |
