## Purpose

**Short**: An Envoy `ext_proc` gRPC service attached to the MaaS AI Gateway. It runs a chain of Inference Payload Processor (IPP) plugins, which route, translate and add credentials to inference requests bound for external LLM providers. It also runs controllers that reconcile `ExternalProvider` and `ExternalModel` CRs into Istio and Gateway API networking resources.

**Detailed**: This repository is the downstream (opendatahub-io / RHOAI) build of the llm-d Inference Payload Processor (`github.com/llm-d/llm-d-inference-payload-processor`). The binary (`/bbr`, from its Gateway API Inference Extension "body-based routing" lineage) is a hand-maintained copy of the upstream IPP runner (`cmd/runner.go:85-96`). The copy exists so the ext-proc server can be wrapped with a dynamic-metadata interceptor. It registers the upstream in-tree plugins plus downstream plugins (`pkg/plugins/plugins.go`):
- `maas-headers-guard`: strips spoofable routing/auth headers.
- `model-provider-resolver`: maps the body `model` field to an ExternalModel and its provider.
- `api-translation`: translates between OpenAI Chat and Anthropic Messages, and to Vertex, Bedrock or Azure formats.
- `apikey-injection`: injects an API key, AWS SigV4 or GCP OAuth2 credential from a labeled Secret.
- `stream-usage-enforcer`.
- `external-metering`.
- NeMo guardrail request/response guards.
- `passthrough-profile-picker`.

Istio's Gateway (default `maas-default-gateway` in `openshift-ingress`) forwards headers and full-duplex streamed bodies to this service through an EnvoyFilter. The plugins mutate them so Envoy can route the request to the selected provider backend.

The same process hosts three controller-runtime controllers. The **ExternalProvider controller** turns each provider (an external FQDN plus auth Secret) into an `ExternalName` Service, an Istio `ServiceEntry` (MESH_EXTERNAL) and a `DestinationRule` that does TLS origination (`SIMPLE`, on by default). The **ExternalModel controller** creates an `HTTPRoute` attached to the configured Gateway. The route matches on `X-Gateway-Model-Name` / `x-ipp-selected-provider` and rewrites `Host` to the provider endpoint. The **legacy-migration controller** converts `maas.opendatahub.io/v1alpha1` ExternalModel CRs into the new `inference.opendatahub.io/v1alpha1` ExternalProvider and ExternalModel pairs. It is only registered if the legacy CRD exists.

The component is installed into the Gateway's namespace, using a Helm chart that wraps the upstream `payload-processor` chart, or by MaaS when MaaS owns the Deployment. It is the external-provider path of RHOAI Models-as-a-Service. The code coordinates ownership with a newer **AI Gateway Controller (AGC / "Praxis")**:
- IPP stops reconciling ExternalModels that use `spec.gatewayRefs` or carry AGC's finalizer, and withdraws their routes.
- IPP removes transport for ExternalProviders that carry AGC's finalizer.
- IPP suppresses provider status when only AGC-managed models reference the provider.

## Architectural Analysis

**Two planes in one process.** A single `ctrl.Manager` hosts both the data plane (ext-proc gRPC on 9004, gRPC health on 9005) and the control plane (the three controllers, plus informer-backed in-memory stores that the plugins read at request time). The gRPC runnables are wrapped with `noLeaderElection` (`cmd/runner.go:230,237`), so every replica serves traffic. The controllers use the manager's leader-election settings (`ctrl.Options` sets no `LeaderElection`, so by default every replica reconciles). The chart defaults to `replicas: 1`. Running more replicas without leader election would make the controllers race on the same Services and HTTPRoutes. Their create/update logic is idempotent, so the effect is churn rather than corruption. You can set `DISABLE_EXTERNAL_MODEL_CONTROLLER=true` to run the binary as a pure data-plane processor (`cmd/main.go:35-46`).

**Two controller wiring paths.** Production wiring is in `cmd/controllers.go`. That `providerController` registers only `For(ExternalProvider)` and `Watches(ExternalModel)`. It does **not** register the `Owns(Service)` and ServiceEntry/DestinationRule watches that `externalprovider.Reconciler.SetupWithManager` declares (`pkg/controller/externalprovider/reconciler.go:388-414`). Likewise, `modelController` does not `Owns(HTTPRoute)`, unlike `externalmodel.SetupWithManager` (`reconciler.go:317-321`). As a result, drift or deletion of generated networking objects is only corrected on the next CR event or resync, not immediately. The analyzer reports both paths. Only the `cmd/` path runs in the shipped image.

**Request pipeline (default profile, `deploy/payload-processing/values.yaml:30-62`).**
1. `maas-headers-guard` captures and strips `x-maas-*`, captures and strips `X-Origin-Cluster`, removes client `authorization`/`x-api-key`, and optionally strips inbound routing headers.
2. `body-field-to-header` copies body `model` to `X-Gateway-Model-Name`.
3. `model-provider-resolver` looks up the model in its in-memory store. It picks a provider by weight using `math/rand/v2`, which is non-cryptographic and only used for traffic splitting. It then sets `x-ipp-selected-provider` and `Host`, rewrites the body `model` to the provider's target model, and writes provider, format, path and credential references to CycleState. It returns 403 on a routing loop when `X-Origin-Cluster` equals `CLUSTER_NAME`.
4. `stream-usage-enforcer`.
5. `api-translation` rewrites the body and `:path` into the provider's format.
6. `apikey-injection` signs or injects credentials from the labeled-Secret store.

On the response, `api-translation` reverses the translation. Envoy then routes the mutated request with the HTTPRoute that the ExternalModel controller generated. That route targets the ExternalName Service, which resolves through the ServiceEntry and is TLS-originated by the DestinationRule. The upstream EnvoyFilter uses `failure_mode_allow: false`, so if IPP is unavailable, requests on that gateway fail closed.

**Hub mode.** Cross-cluster routing works with `hubMode: true` and two chart releases (pre-EPP "PROPOSE" and post-EPP "TRANSFORM"). In PROPOSE, the resolver emits `envoy.lb.subset_hint` dynamic metadata through a pseudo-header, which `dynamicmetadata.WrapServer` converts into `ProcessingResponse.DynamicMetadata` (`pkg/dynamicmetadata/metadata.go`). In TRANSFORM, it selects the provider ref matching `x-gateway-destination-endpoint`. This wrapper is the only reason `cmd/runner.go` diverges from upstream. The file carries a "KEEP IN SYNC" maintenance burden against IPP releases.

**Ownership hand-off to AGC.** Much of the controller and resolver logic arbitrates ownership with ai-gateway-controller:
- `IsAGCManaged`: the model has `gatewayRefs`, or all of its provider refs are foreign.
- `IsAGCAttached`: the model has `gatewayRefs`.
- `IsAGCServed`: the model carries AGC's finalizer `inference.opendatahub.io/external-model-cleanup`.

The ExternalProvider finalizer `inference.opendatahub.io/external-provider-cleanup` marks AGC's claim. IPP never resolves cross-namespace provider refs. Mixed-shape models keep serving through their local refs. The CRDs already carry AGC-oriented fields (`gatewayRefs`, `status.gateways`, `overlayDigest`/`overlayGeneration`). IPP itself does not populate them.

**Risks and observations.**
- **Secret cache scope.** The `apikey-injection` plugin builds a separate label-filtered cache (`inference.llm-d.ai/ipp-managed=true`) and documents it as defense-in-depth (`pkg/plugins/apikey-injection/plugin.go:205-241`). However, the ExternalProvider reconciler's `validateSecretRef` calls `r.Get(ctx, …, &corev1.Secret{})` through the manager's default cache-backed client (`pkg/controller/externalprovider/reconciler.go:301-313`). That cache has no Secret label selector. With `multiNamespace: true` (the chart default, which leaves `NAMESPACE` unset) this probably starts an unfiltered, cluster-wide Secret informer in the manager. If so, every Secret's data is held in process memory, which defeats the stated defense-in-depth.
- **Secret validation is looser than injection.** `validateSecretRef` only checks that the Secret exists. It does not check for the `ipp-managed` label or the `api-key` field. A provider can therefore report `Ready` while the injection store ignores an unlabeled Secret, and requests then fail at runtime.
- **Global model namespace.** The resolver store keys models only by client-facing `modelName` (`pkg/plugins/model-provider-resolver/store.go:98-103`). The last writer wins. The ExternalModel controller can also create HTTPRoutes in different namespaces that match the same `X-Gateway-Model-Name` on the shared Gateway. Two namespaces that use the same model name can therefore shadow each other.
- **Plaintext guard.** `ValidateConnectionSecurity` refuses a provider that sets `inference.opendatahub.io/tls: "false"` while also configuring an auth type. That case would send credentials in cleartext (`pkg/controller/common/annotations.go`). Because `spec.auth` is required, the TLS-disabled path is effectively limited to providers whose auth type is empty, which the CRD enum does not allow. In practice TLS origination is always on.
- **Self-signed ext-proc TLS.** With `--secure-serving` (default true), the ext-proc server generates a self-signed RSA-4096 certificate valid for 10 years at every start (`cmd/runner.go:355-390`). The upstream chart's DestinationRule for the IPP Service uses `insecureSkipVerify: true`, so Gateway→IPP traffic is encrypted but not authenticated.
- **Message size.** The gRPC per-message receive limit defaults to 32 MiB, configurable with `GRPC_MAX_RECV_MSG_SIZE`, and fails closed on invalid values (`cmd/grpcmaxrecv.go`). Cumulative streamed-body size is not bounded here.
- **pprof on by default.** Upstream `EnablePprof` defaults to true. Its handlers are added to the controller-runtime metrics server, which uses authn/authz filters when `--metrics-endpoint-auth` is true (the default).

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | per-namespace (ExternalProvider/ExternalModel and their Secrets are namespaced; cross-namespace provider refs not served by IPP) | `api/inference/v1alpha1/common_types.go:28-64`, `pkg/controller/externalmodel/reconciler.go:146-152` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Single shared ServiceAccount with cluster-wide ClusterRole | Kubernetes | Cluster-wide Secret get/list/watch; client auth is delegated to Gateway policies (Kuadrant/MaaS) |
| Data storage | In-memory stores only (models, providers, credentials) | Application | Model store keyed by `modelName` globally, so cross-namespace name collisions are last-writer-wins |
| Network traffic | Shared Gateway; HTTPRoutes created per model namespace | Istio / Gateway API | Routes from different namespaces can match the same model header on the shared Gateway; no NetworkPolicy shipped |
| Compute & resources | Shared IPP Deployment | Kubernetes | No per-tenant quotas; one tenant's large bodies (up to 32 MiB/message) share capacity |
| Configuration & secrets | Credential Secret resolved in provider namespace (or model namespace for override) | Application | Manager cache may hold all cluster Secrets (unfiltered `r.Get` in provider reconciler); injection store is label-filtered |
| API scoping | Cluster-wide watches unless `NAMESPACE` set | Kubernetes / Application | Cross-namespace provider refs rejected by IPP and handed to AGC |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| IPP ext-proc server (all Gateway traffic) | namespace (via resolved ExternalModel) | Application-level lookup in in-memory store |
| MaaS Gateway (Envoy) | HTTPRoute per model namespace | Gateway API header matching; upstream Kuadrant policies |
