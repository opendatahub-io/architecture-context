## Purpose

**Short**: An OpenAI-compatible HTTP gateway that exposes one `/{route}/v1/chat/completions` endpoint for each configured guardrail policy. It injects a fixed set of detectors into each request and forwards it to the FMS Guardrails Orchestrator.

**Detailed**: The vLLM Orchestrator Gateway is part of the TrustyAI Guardrails stack. The FMS Guardrails Orchestrator exposes a general `/api/v2/chat/completions-detection` API where each caller chooses which detectors run on input and output. The gateway restricts that choice. Operators pin detector pipelines in a YAML config (`orchestrator`, `detectors`, `routes`), and the gateway publishes one endpoint per route, for example `/pii/v1/chat/completions` or `/passthrough/v1/chat/completions`. Clients see a normal OpenAI chat-completions API. Behind it, the gateway adds the route's `detectors` map (input/output detector → `detector_params`) to the JSON body and POSTs it to the orchestrator. This makes a guardrailed model a drop-in replacement for an unguardrailed one.

When the orchestrator reports detections and the route defines a `fallback_message`, the gateway replaces the generated choices with a canned assistant reply such as "I'm sorry, I'm afraid I can't do that." It does this for both non-streaming JSON responses and streaming (SSE) responses. The `detections` and `warnings` from the orchestrator are passed through to the client.

The service is a single Rust binary (axum + tokio + reqwest) with no Kubernetes API usage, no CRDs and no persistence. On the outbound side it supports TLS and mTLS to the orchestrator using certificates mounted at fixed paths (`/etc/tls/private`, `/etc/tls/ca`). The listener is plain HTTP on port 8090, so inbound TLS and authentication are expected to come from a fronting proxy supplied by whatever deploys it. Historically that was the TrustyAI operator's GuardrailsOrchestrator controller.

## Architectural Analysis

**Design: a policy-pinning adapter, not a general proxy.** The gateway's main job is access restriction. Routes are fixed at startup from `GATEWAY_CONFIG` (`src/main.rs:60-109`). There is no dynamic routing, and clients cannot override detectors: the route's `detectors` key overwrites any client-supplied value in the body (`src/main.rs:233-236`). Every other field of the client payload goes to the orchestrator unchanged (model, messages, tools, `stream`). Detector config is resolved per request from the cloned `GatewayConfig` (`get_orchestrator_detectors`, `src/main.rs:32-56`). A detector's `server` field, which defaults to its name (`src/config.rs:39-46`), becomes the orchestrator's detector key. This lets several gateway "detectors" share one orchestrator detector server with different `detector_params`.

**Auth is pass-through.** The gateway does no authentication or authorization of its own. It forwards only the `Authorization` header and any `x-forwarded-*` headers to the orchestrator (`src/main.rs:423-433`, `493-502`). User identity and policy enforcement are therefore delegated to (a) whatever proxy sits in front of port 8090 and (b) the orchestrator or its upstream model server. Without such a proxy, anyone who can reach the pod can call any route.

**TLS posture is selected implicitly by file presence.** `build_orchestrator_client` (`src/main.rs:351-406`) switches the URL scheme to `https` only when *both* `/etc/tls/private/tls.crt` and `tls.key` exist. In that case it also presents them as a client identity (mTLS), converting PEM to an in-memory PKCS#12 with an empty password via the `openssl` crate. If only the CA (`/etc/tls/ca/service-ca.crt`) exists, the CA is trusted but the scheme stays `http`, so the CA has no effect. When the orchestrator host is `localhost`, hostname verification is turned off (`danger_accept_invalid_hostnames(true)`, line 373). The in-code comment says this is because the orchestrator's serving cert covers only its service DNS name, which fits a same-pod sidecar deployment that uses an OpenShift service-ca certificate. If the cert files are missing, the gateway quietly falls back to plaintext HTTP and only logs a warning (line 402).

**Logging leaks sensitive data.** The tracing subscriber is hard-coded to `DEBUG` (`src/main.rs:67-71`) with no environment override. At that level, every request header is logged, including the full `Authorization` bearer token (`src/main.rs:425`, `494`), along with complete request payloads and orchestrator response bodies (lines 163, 237, 414-418, 461). Prompts and completions, which may contain the PII the guardrails are meant to catch, end up in container logs. This is the most significant security risk in the component. The subscriber is also initialized *after* config loading, so the early config debug lines (60-65) are never printed.

**Robustness gaps.** Several code paths panic instead of returning errors: config read/parse (`src/config.rs:56-62`), invalid `HOST` (`src/main.rs:128`), bind failure (132), and an unexpected orchestrator JSON shape (`expect` at line 475). A malformed orchestrator response therefore aborts the request task. An unparsable `HTTP_PORT` is logged and the gateway keeps using 8090. In the streaming path, each SSE chunk from the orchestrator that carries `detections` has its first choice's delta replaced with the fallback message. Content chunks emitted *before* a detection have already reached the client, so output guardrails on streams are best-effort. The SSE parser also assumes each network chunk contains whole `data:` lines (`src/main.rs:518-544`).

**Config validation bug.** `validate_registered_detectors` (`src/config.rs:64-109`) checks for duplicate *output* servers only inside the `if detector_cfg.input` branch (lines 96-101). Output-only detectors that share a server are therefore never flagged, and an input detector is recorded in both sets. The unit test `test_validate_multiple_same_server_output_detectors` expects a panic for that output-only case, so it would likely fail. Either way, two output detectors on one server would be sent to the orchestrator as a single map key, and the last one written would silently win.
