## Purpose

**Short**: An operator that gives RHOAI platform components a shared, declarative Kubernetes API for getting PostgreSQL access. It manages database providers, either an operator-run PostgreSQL instance or one an administrator manages, and writes per-claim connection Secrets.

**Detailed**: rhai-db-operator is the RHOAI downstream build of `opendatahub-db-operator`, the "shared database infrastructure service" described in ODH-ADR-Operator-0017. It runs as an RHOAI platform module. The platform operator (rhods-operator) turns it on through the `databaseservice` component of the `DataScienceCluster`, which creates the cluster-scoped singleton `DatabaseService/default-db-operator` (`services.platform.opendatahub.io/v1alpha1`). The module then owns the lifecycle of the database "supply" and "demand" APIs in `infrastructure.opendatahub.io/v1alpha1`.

On the supply side, a cluster-scoped `DatabaseProvider` describes one of two backends. An **Internal** provider is a single-instance PostgreSQL StatefulSet that the operator renders from embedded templates (`registry.redhat.io/rhel9/postgresql-16` by default), with a PVC, a cert-manager TLS certificate, a NetworkPolicy and an SCC binding. An **External** provider is an administrator-managed PostgreSQL that the operator reaches through an admin connection Secret. When default-provider management is on, `DatabaseService` creates a well-known Internal provider called `rhai-db`, so components get a working database without any administrator setup.

On the demand side, namespace-scoped `DatabaseClaim` (database-scoped role, optionally a dedicated database) and `SchemaClaim` (a dedicated schema plus login role) resources select a provider by name or label selector. The operator then provisions the database or schema, a unique login role and password, grants and extensions over a pgx connection. It writes an `Opaque` Secret with the `opendatahub.io/connection-type-protocol: postgres` annotation into the claim's namespace. The Secret has fixed keys: `host`, `port`, `user`, `password`, `dbname`, `sslmode`, plus optional `schema` and `ca.crt`. Consuming components (for example model registry, feature store or other platform services) mount that Secret and connect with whatever driver they use. The operator also installs the infrastructure CRDs itself as operands of `DatabaseService`, so the module can start before those CRDs exist.

## Architectural Analysis

**Module pattern and CRD bootstrapping.** The operator is built on the `odh-platform-utilities` reconciliation framework (`reconciler.ReconcilerFor`, actions, dynamic watches). Only the `DatabaseService` reconciler is registered unconditionally. The `DatabaseProvider`, `DatabaseClaim` and `SchemaClaim` reconcilers are registered lazily through `NewInfrastructureRegistration` once their CRDs exist (`pkg/manager/manager.go:69-147`). The `DatabaseService` reconciler applies those three CRDs from embedded operand manifests (`internal/controller/databaseservice/operands/manifests/`). To support this, the manager role has `create` on all CRDs, but `patch` only on the three named infrastructure CRDs (`config/rbac/role.yaml:41-58`). Watches on the infrastructure kinds use `reconciler.Dynamic(reconciler.CrdExists(...))`, so they turn on only after the CRD appears. This is why the analyzer flagged the named-watch predicates as "unresolved": they are dynamic CRD-existence gates plus event mappers back to the singleton, not filters on resource names (`internal/controller/databaseservice/databaseservice.go:116-138`).

**Supply/demand separation.** Providers are cluster-scoped and claims are namespace-scoped. That split is the core tenancy decision. Any principal allowed by Kubernetes RBAC to create a claim in a namespace can get credentials from any matching cluster-scoped provider. Selecting a provider is deterministic: highest `db.infrastructure.opendatahub.io/selection-priority`, ties broken by name, and a bound claim stays with its provider. The operator itself does no authorization beyond Kubernetes RBAC on the claim CRs, so access to a provider is governed entirely by who can create claims.

**Internal backend as a convenience service, not HA.** The Internal provider deploys a single-replica StatefulSet with an RWO PVC and no backup/restore (ARCHITECTURE.md). The pod runs as UID/GID 26 under a dedicated install-time SCC, `odh-db-internal-postgres`. Because the SCC is pre-created, the operator only needs `use` on it, not `create` (`config/openshift/internal_postgres_scc.yaml`). Its service account has `automountServiceAccountToken: false`. Ingress to PostgreSQL goes through a generated NetworkPolicy that admits only the operator pod and the namespaces that currently hold bound claims (`assets/manifests/internal/networkpolicy.yaml.tmpl`, `internal/controller/databaseprovider/databaseprovider_internal_support.go:79-114`). That allow-list changes as claims come and go, which is a meaningful data-plane control. Removing the provider keeps the PVC and admin Secret: owner references are detached (`databaseservice_default_provider.go:184-190`).

**Secret-cache hardening.** The operator needs cluster-wide Secret read/write: claim Secrets in any namespace, and External admin Secrets referenced by `corev1.SecretReference` with a namespace. To avoid caching every Secret in the cluster (RHOAIENG-96275), the informer is label-scoped to operator-managed Secrets, and the client bypasses the cache for all Secret reads (`pkg/manager/cache.go:43-72`). This keeps memory use down and shrinks the blast radius. RBAC is unchanged, though: `secrets` still carries `create, delete, get, list, patch, update, watch` cluster-wide.

**Two-tier RBAC for the Internal backend.** The cluster-wide manager role is mostly read/watch for workload resources. Write verbs (`create, get, patch`) on StatefulSets, Services, PVCs, ConfigMaps, ServiceAccounts, RoleBindings, NetworkPolicies and cert-manager Issuers/Certificates come from the `internal-provider-writer` ClusterRole. Kustomize binds it through a namespaced RoleBinding only in the operator namespace (`config/rbac/internal_provider_writer_rolebinding.yaml`). This is good least-privilege design. One risk: `spec.internal.namespace` lets a provider put its backend in another namespace (`pkg/controller/names.go:120-125`), and that only works if an equivalent RoleBinding exists there. Without one, reconciliation fails with RBAC errors instead of silently escalating.

**Metrics and webhook surfaces.** The metrics server always runs with `SecureServing: true` and `filters.WithAuthenticationAndAuthorization`, i.e. TokenReview/SubjectAccessReview (`pkg/manager/manager.go:109-119`). This answers the analyzer's "unresolved conditional-metrics-enforcement" gap: there is no conditional branch. The serving cert comes from OpenShift service-ca (`metrics-server-cert`), with a lazily generated self-signed fallback if the Secret is missing (`pkg/manager/metrics_certificate.go:63-79`). A webhook server is enabled by default on port 9443 with a cert-manager certificate (`webhook-server-cert`), but **no admission or conversion handlers are registered and no `*WebhookConfiguration` manifests ship**. The webhook Service, port and NetworkPolicy rule are scaffolding with no admission behavior today.

**PostgreSQL client TLS.** `pkg/postgres/client_tls.go` builds pgx TLS configs per connection. If a CA is supplied, `require` is upgraded to `verify-ca`. `verify-ca` sets `InsecureSkipVerify=true` together with a custom `VerifyPeerCertificate` that checks the chain against the provided CA but skips the hostname check, which is the libpq-compatible meaning. `verify-full` validates the hostname. No MinVersion or cipher suites are set, so Go/pgx defaults apply. Connections to Internal backends use `verify-full` when TLS is on. External admin connections default to `require`.

**Credential hygiene.** Passwords come from `crypto/rand` (`pkg/postgres/support.go:46-50`) and are wrapped in a `secret.SecretString` type. A redacting pgx trace logger strips them out (`pkg/postgres/tracelog_redact.go`), and SQL identifiers and literals are quoted before DDL. There is no rotation workflow; a new password is issued only when lost credentials are repaired.

**Downstream build divergence.** The Konflux image is FIPS-capable (`CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, `ubi9/ubi-minimal-pqc`). The dev `Containerfile` builds a static `CGO_ENABLED=0` binary on `ubi10/ubi-micro:latest` and must not be used for production. The image labels say `rhai-db`, but chart and RBAC names keep the `odh-db-operator-*` prefix (`Dockerfile.konflux:2`).

**Analyzer false positive.** The analyzer listed a "HardwareProfile CR" internal dependency sourced from `config/rbac/role.yaml`. Neither `config/`, `pkg/` nor `internal/` contains any HardwareProfile rule or reference, so it is left out of the dependency tables below.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace (claims and their Secrets); providers are shared, cluster-scoped supply | CRD scopes in `config/crd/bases/` |
| **Deployment model** | Single cluster-wide operator; one or more shared PostgreSQL backends serving many namespaces | `config/manager/manager.yaml`, ARCHITECTURE.md |
| **Tenant identifier** | Claim namespace + claim name (unique PostgreSQL role per claim) | `pkg/controller/claimhelpers.go:71-94` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Kubernetes RBAC on claim CRs; unique PostgreSQL role per claim with grants limited to the claim's database or schema | Kubernetes + PostgreSQL (application-issued grants) | No per-provider authorization: any namespace allowed to create claims can bind to any matching cluster-scoped provider |
| Data storage | Separate database (DatabaseClaim) or schema (SchemaClaim) per claim in a shared PostgreSQL instance | PostgreSQL grants issued by the operator | Shared default-database DatabaseClaims share one database. Isolation depends on correct DDL and grants; `ReadOnly` is read-only only within the granted scope |
| Network traffic | Internal: generated NetworkPolicy restricts 5432 to the operator pod and namespaces with bound claims | Kubernetes NetworkPolicy | All admitted namespaces reach the same instance, so isolation inside it is at PostgreSQL level only. External network policy is the administrator's responsibility |
| Compute & resources | Single shared PostgreSQL pod; optional `resources` on the Internal spec | Kubernetes | No per-tenant quotas or connection limits; one noisy claim consumer can degrade others |
| Configuration & secrets | Connection Secret written only into the claim's namespace; Secret informer label-scoped, reads uncached | Kubernetes + operator | Operator SA holds cluster-wide Secret CRUD. External admin Secrets may live in any namespace |
| API scoping | Cluster-wide watches on claims/providers; provider selection by name/label | Application | Selection-priority labels on providers are cluster-wide policy set by whoever can edit providers |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Internal PostgreSQL (`rhai-db` default provider) | Database or schema + role per claim | PostgreSQL grants + NetworkPolicy namespace allow-list |
| External PostgreSQL providers | Database or schema + role per claim | PostgreSQL grants; network isolation owned by administrator |
