## Purpose

**Short**: Praxis Policy Engine (PPE) is an embeddable Rust library that enforces identity, authorization, delegation, data-control, approval, and audit policy on AI agent and tool traffic for the Praxis proxy.

**Detailed**: praxis-policy is the policy layer of [Praxis](https://github.com/praxis-proxy/praxis). It is a typed, phased plugin runtime plus a policy evaluator (APL, the Authorization Policy Language) that decides who may call which tool, resource, prompt, LLM, or HTTP route, what data comes back, and where that data may go next. A host process links the `praxis-policy` facade crate, loads a YAML policy document of routes (`- tool:`, `resource:`, `prompt:`, `llm:`, `http:`), and calls the engine at each hook point (pre-invocation, args, result, and so on) for every request.

The engine resolves and checks user, agent, and workload identities (JWT with optional DPoP, or API keys). It evaluates APL predicates and pluggable Policy Decision Points (Cedar, CEL, and OPA/Rego through the embedded `regorus` interpreter). It exchanges credentials using RFC 8693 token exchange or Vault, so each upstream gets a token scoped to that service. It redacts fields in results, carries Session Taint across calls (state stored in Valkey), supports out-of-band approval through OIDC CIBA, applies experimental quota and rate limits (Limitador), and emits an audit event for every decision. Each bundled extension sits behind its own Cargo feature (`jwt`, `api-key`, `oauth`, `delegator-vault`, `elicitation-ciba`, `cedar`, `cel`, `opa`, `valkey`, `secrets-vault`). The `builtins` umbrella feature turns on all of them.

The repository produces no container image, Kubernetes manifest, Service, or CRD. Where it runs is up to the host: as a gateway in front of a tool server, as an egress sidecar beside an agent, or inside an agent framework (docs/content/deployment.md). In RHOAI it ships inside the Praxis proxy, which supplies the network listener, the HTTP transport (Praxis injects its own pingora-backed transport), and the process-level FIPS configuration.

## Architectural Analysis

**Library, not service.** All network exposure comes from the host. The engine has no listener of its own. Every outbound call (JWKS fetch, token exchange, CIBA, Vault, Limitador, HTTP API-key directory) goes through an `HttpTransport` trait defined in `praxis-policy-core`, which the host injects. The optional `http-hyper` feature adds a default hyper/rustls transport for hosts that have none. Praxis does not use it. This makes the host responsible for TLS trust, proxying, and mTLS on outbound traffic, and the analyzer's empty Service/Ingress/Endpoint tables are accurate for this repo.

**Layered crates.** Dependencies run in one direction: `ppe` (facade) → `ppe-apl-runtime` → `ppe-apl-cmf` → `ppe-apl-core`, plus `ppe-orchestration` and `ppe-core`. `ppe-core` holds the PolicyEngine, executor, hook definitions (defined with a `define_hooks!` macro), config, identity/delegation/elicitation abstractions, and the shared crypto backend. `ppe-apl-core` compiles and evaluates APL. `ppe-apl-cmf` maps the Common Message Format onto attribute bags. `ppe-apl-runtime` holds the per-hook plugin invokers, PDP router, decision cache, and session resolver. Bundled extensions live in a single `builtins` crate with one feature each, partly because crates.io publishing is serial and rate-limited. Hosts can replace any extension by implementing `PluginFactory` and registering it under a `kind:`. An unknown `kind` makes policy loading fail at startup.

**Fails closed.** Almost every plugin defaults to denying. Plaintext endpoints are refused unless `insecure_http: true` is set (JWT JWKS, OAuth token endpoint, Vault, Limitador). Valkey refuses plaintext to non-localhost endpoints, and refuses `tls: true` combined with a `redis://` scheme. Limitador `on_error` defaults to `deny`. Unknown config keys fail plugin construction. Session ids are bound to the authenticated principal, so one principal cannot address another's session state (crates/ppe-apl-runtime/src/session_resolver.rs:91). The library is built without `panic = "abort"` so that a policy panic cannot bring down the host.

**Two crypto backends.** Crypto is selected at compile time, and the two backends cannot be combined. `crypto-rustcrypto` is the default (sha2/hmac). `fips` routes SHA-256 and random-byte generation through system OpenSSL, using the private DRBG. `jwt` verifies signatures with AWS-LC (through `jsonwebtoken/aws_lc_rs`), while `jwt-openssl-fips` verifies RS/PS/ES signatures with OpenSSL. `crypto_capability_report().fips_profile_is_safe()` lets the host refuse to serve unless the compiled crypto graph is FIPS-safe. `make check-fips-graph` fails the build if a FIPS feature selection links `sha2`, `hmac`, `ring`, `rustls`, `aws-lc-rs`, or `aws-lc-sys`. The FIPS profile covers only a subset of features. OAuth delegation, Vault delegation, Valkey (rustls/ring through redis-rs), ordinary `jwt` (AWS-LC), and `http-hyper` (ring) all fall outside it, and HMAC (keyed content provenance, HS* JWTs) is refused under FIPS. Whether the RHOAI Praxis build actually uses the FIPS selection is decided by the host's Cargo features. This repo does not decide it.

**Risks and observations.**
- The `Cargo.lock` graph contains `ring`, `aws-lc-rs`, and `openssl` together. Which one is used depends on features. A host that turns on `builtins` gets non-FIPS providers.
- The `http-hyper` transport trusts the compiled-in `webpki-roots` Mozilla bundle, not the system trust store. Internal or OpenShift service CAs will not validate through it.
- Token quota is a soft cap with an overrun window, and its pending-debit state is per-replica and in-process (crates/builtins/src/plugins/quota/README.md).
- The public API is pre-1.0 and changes between minor versions. Quota and ratelimit are experimental and not covered by semver.
