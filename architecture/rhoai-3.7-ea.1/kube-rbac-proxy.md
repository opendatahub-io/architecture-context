## Purpose

**Short**: A small HTTP(S) reverse proxy for one upstream. It authenticates callers with Kubernetes TokenReview, OIDC, or client certificates, and authorizes them with SubjectAccessReview before forwarding the request.

**Detailed**: kube-rbac-proxy runs as a sidecar container next to an application container. It terminates TLS on a public port (usually 8443/TCP) and forwards only authenticated and authorized requests to the application. The application listens on localhost or a cluster-internal port (usually 8080/TCP). Callers are identified from a bearer token, which is validated with a Kubernetes `TokenReview` or an OIDC issuer's JWKS, or from an X.509 client certificate signed by a configured CA. Each request is then mapped to Kubernetes authorization attributes: either a non-resource URL/verb, or a templated resource such as `namespace/metrics` or `services/proxy`. Those attributes are checked with a hardcoded Prometheus-metrics allow rule, an optional static allow-list, and finally a `SubjectAccessReview` sent to the kube-apiserver. If the request is allowed, the proxy can add `x-remote-user` / `x-remote-groups` headers so the upstream knows who the caller is.

In RHOAI 3.x, kube-rbac-proxy is the main auth sidecar for workloads exposed through Gateway API `HTTPRoute`s. Component operators (notebook controller, model serving, TrustyAI, and others) inject it in front of their workloads, replacing the oauth-proxy sidecar used in RHOAI 2.x. This repository builds the `odh-kube-rbac-proxy-rhel9` image (`quay.io/rhoai/odh-kube-rbac-proxy-rhel9`) with Konflux, as a FIPS-enabled, multi-arch build (x86_64, ppc64le, s390x, arm64). The repo deploys nothing itself. Its only Kubernetes manifests are examples and e2e test templates.

The downstream fork adds features beyond upstream `brancz/kube-rbac-proxy`:
- "Format2" path- and method-scoped authorization endpoints with named path captures and header- or query-based templating, for example TrustyAI `status-events`.
- An OCSF 1.9.0 audit log with an "AI Operation" profile (`--audit-log-profile=metadata`, `--audit-ai-provider`).
- Combined authentication/authorization and upstream timeouts.
- TLS curve preferences, and TLS version flags in the format the operator passes from the cluster TLS profile.

## Architectural Analysis

**A single-binary filter chain.** `cmd/kube-rbac-proxy/app/kube-rbac-proxy.go` builds one `http.ServeMux` with a single catch-all `/` handler. All requests go through these layers in order:
1. `WithAllowPaths`. Paths not on the list get 404.
2. `--ignore-paths` bypass. Matching paths skip authentication entirely.
3. `withRequestTimeouts`.
4. `WithAuthentication`.
5. `WithAuthorization`. A request can produce several attribute sets, and every one must be allowed.
6. `WithAuthHeaders`.
7. `httputil.NewSingleHostReverseProxy`.

There are no other application routes. Every path that isn't ignored or rejected is proxied to the upstream as-is. When `--proxy-endpoints-port` is set, `/healthz` is served on a separate TLS listener that reuses a clone of the main TLS config (lines 433-470). The audit logger is wired in as extra decorators only when the `metadata` profile is on, so with audit disabled the hot path stays exactly as upstream.

**Authorization is a union with a hardcoded first rule.** The authorizer is `union.New(hardcodedMetricsAuthorizer, staticAuthorizer, sarAuthorizer)`. The hardcoded authorizer always allows `GET /metrics` for `system:serviceaccount:openshift-monitoring:prometheus-k8s` (`pkg/hardcodedauthorizer/metrics.go:295`), whatever the cluster RBAC says. The source carries a `TODO: remove this, once CMO lands static authorizer configuration` comment. That is an OpenShift-specific implicit grant worth knowing about. The rule only covers the exact `/metrics` non-resource path. SAR decisions are cached for 5 minutes (allow) and 30 seconds (deny), and TokenReview results for 2 minutes (`pkg/authz/auth.go:103`, `pkg/authn/delegating.go`). So when a RoleBinding is revoked, the change can take up to 5 minutes to reach the proxy.

**Templated SARs are the multi-tenancy primitive.** Format1 (`rewrites` + `resourceAttributes`) and Format2 (`endpoints[].mappings[].resources[]`) both turn request data into SAR attributes through Go `text/template`. The inputs are a query parameter, an HTTP header, or a named path segment, for example `namespace: '{{ index .PathParams "tenant" }}'`. This is how RHOAI scopes a shared service per namespace: the caller has to hold the target verb on a resource in the namespace named in the request. Two things carry the risk here. A mistake in the config (for example, a template that resolves to an empty namespace, which makes the SAR cluster-wide) or a too-broad `--ignore-paths` goes straight into authorization decisions. And if an endpoint's method isn't mapped, the request gets 403 (`ErrEndpointMethodNotAllowed`), so a Format2 endpoint denies unmapped methods by default.

**TLS policy comes from the caller.** Server TLS settings are deliberately empty by default (`&tls.Config{}`) and filled in by `applyTLSConfig` from `--tls-min-version` (default `VersionTLS12`), `--tls-cipher-suites` and `--tls-curve-preferences`. The code comments say these are set by "the component operator from the resolved cluster TLS profile". The proxy therefore relies on the injecting operator to follow the OpenShift `APIServer` TLS security profile. If no cipher list is passed, Go defaults apply. The server certificate comes from mounted files that are hot-reloaded (`pkg/tls/reloader.go`). In OpenShift these are usually service-serving certificates. If no certificate is given, the proxy generates a self-signed one in memory, a deprecated mode that logs a warning. `--insecure-listen-address` (plain HTTP plus h2c) is still supported but deprecated. The `examples/oidc` sample still uses it.

**Upstream hop.** By default, the proxy talks to the upstream over plain HTTP on localhost (sidecar pattern). With `--upstream-ca-file` and optionally `--upstream-client-cert-file`/`--upstream-client-key-file`, it can use TLS or mTLS to the upstream. Certificate verification is never disabled, and TLS 1.2 is the minimum (`transport.go:176-192`). `--upstream-force-h2c` supports gRPC upstreams that speak only cleartext HTTP/2. Identity headers are only safe on that localhost hop: the code warns `WithAuthHeaders ... Must not be used, if connection is not encrypted with TLS`.

**Operational hardening.** The downstream branch adds several defenses against resource exhaustion:
- `ReadHeaderTimeout` (10s) and `IdleTimeout` (60s).
- A shared auth timeout (30s) and an upstream timeout (30s) that covers the time up to response headers.
- HTTP/2 stream and frame limits (100 streams, 256 KiB).
- A klog `SanitizingFilter` that masks `TokenReview.spec.token` in logs.
- A bounded, asynchronous audit queue that writes OCSF "gap" events when audit records are dropped, instead of blocking requests.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace, as defined by the SAR attributes in each sidecar's config (static `namespace`, or templated from header/query/path) | `pkg/authz/endpoints.go:17-75`, `pkg/authz/auth.go:32-73` |
| **Deployment model** | One sidecar instance per workload pod; the proxy itself is stateless and single-upstream | `kube-rbac-proxy.go:321` |
| **Tenant identifier** | Caller identity (user/groups from TokenReview/OIDC/x509) checked against a namespace from config or the request | `pkg/filters/auth.go` |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | TokenReview/OIDC/x509 plus SubjectAccessReview per request | Application (kube-rbac-proxy) delegating to Kubernetes RBAC | Templated namespaces come from caller-controlled headers/query/path. Correctness depends on the config. Up to 5 min SAR allow cache delays revocation. Hardcoded Prometheus `/metrics` grant. `--ignore-paths` bypasses all checks. |
| Data storage | None (stateless) | N/A | None |
| Network traffic | None in the proxy; relies on consumer NetworkPolicies and on the upstream binding only to localhost | Kubernetes / consumer | If the upstream listens on a pod IP, the proxy can be bypassed inside the cluster |
| Compute & resources | Per-pod sidecar; HTTP/2 stream/frame limits and timeouts | Application / Kubernetes | Resource requests/limits set by consumers |
| Configuration & secrets | Per-pod mounted config file and certs | Kubernetes | None in this repo |
| API scoping | Only TokenReview/SAR create calls; no list/watch | Kubernetes | SA needs cluster-scoped create on tokenreviews/subjectaccessreviews |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Upstream service fronted by the proxy (for example, a shared TrustyAI or metrics API) | Namespace derived from request (Format2 path capture / header) | SubjectAccessReview against the derived namespace |
