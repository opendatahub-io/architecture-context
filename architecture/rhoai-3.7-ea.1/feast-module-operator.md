## Purpose

**Short**: A cluster-scoped module operator that reconciles the singleton `FeastOperator` CR (`components.platform.opendatahub.io/v1alpha1`) and deploys the upstream Feast operator (`feast-operator-controller-manager`) and its `FeatureStore` CRD from kustomize manifests baked into the image.

**Detailed**: feast-module-operator splits the Feast component out of the monolithic opendatahub-operator / rhods-operator. Under the platform's modular handler framework, the platform operator installs this operator with a generated Helm chart (`config/chart/`). It then creates the singleton `FeastOperator` CR named `default-feastoperator`, which carries platform settings: optional OIDC issuer settings and optional per-capability management states. This operator reconciles that CR. It renders the bundled Feast kustomize manifests (`config/manifests/feastoperator`, copied from `opendatahub-io/feast` or `red-hat-data-services/feast` `infra/feast-operator/config` at source commit `5abb1bc3`) and applies them into the applications namespace (`redhat-ods-applications` on RHOAI). Those manifests contain the Feast operator Deployment, the `feast.dev` `FeatureStore` CRD, RBAC, the metrics Service and the ServiceMonitor. The operator then reports `Ready` / `DeploymentsAvailable` conditions and the platform release version back on the CR status.

Besides plain manifest delivery, the operator also controls two **capabilities** for the Feast operator: **Feature Store** and **Data Registry**. It writes them into a `feast-capabilities-config` ConfigMap that the Feast operator reads. It also creates and labels the fixed `rhoai-data-registry` namespace when Data Registry is Managed. When capability values change, it patches the Feast operator Deployment's pod template with a `feast.dev/capabilities-hash` annotation, which forces a rollout so the Feast operator picks up the new values. On uninstall, a finalizer protocol makes sure the Feast operator has torn down its Data Registry workloads before the ConfigMap disappears. The platform-version handshake reads `platformVersion` from the `odh-data-config` ConfigMap and records it in `status.releases`.

The operator does not serve feature data and does not reconcile `FeatureStore` instances; the deployed upstream Feast operator does that. Its ClusterRole is very broad: it includes `feast.dev`, `dataregistry.opendatahub.io`, `sparkoperator.k8s.io`, `pods/exec`, ClusterRole/Binding CRUD and `bind` on `system:auth-delegator`. This is mostly because Kubernetes RBAC escalation prevention requires the module operator to hold every permission it grants to the Feast operator's ClusterRole.

## Architectural Analysis

**Module-operator pattern, not a feature operator.** The controller (`internal/controller/feastoperator/feastoperator_controller.go:238-288`) is built entirely from the opendatahub-operator reconciler builder. The action pipeline is: `initialize` → `upgradeIfNeeded` → `setKustomizedParams` → `reconcileDataRegistryNamespace` → `reconcileCapabilitiesConfigMap` → `releases` → `reconcilePlatformVersion` → `kustomize` render → `migrateDeploymentSelector` → `deploy` (cached, ordered apply) → `triggerCapabilityRolloutIfNeeded` → `deployments` status → `gc` in the applications namespace. Most behavior therefore comes from the shared `opendatahub-operator/v2/pkg/controller/actions/*` and `odh-platform-utilities/framework` libraries. Upgrades to those modules can change this operator's behavior without any local code change. `upgrade()` and `handlePlatformUpgrade()` are currently no-op hooks (`feastoperator_upgrade.go:54-58`, `feastoperator_platform_version.go:112-116`).

**Manifests baked into the image, copied at startup.** `Dockerfile.konflux` copies `config/manifests/` to `/manifests` in the image. The pod's `copy-manifests` init container copies them into an `emptyDir` at `/opt/manifests`, because the main container runs with a read-only root filesystem. At startup the operator rewrites `params.env` image references from `RELATED_IMAGE_ODH_FEAST_OPERATOR_IMAGE`, `RELATED_IMAGE_ODH_FEATURE_SERVER_IMAGE` and `RELATED_IMAGE_ODH_KUBE_RBAC_PROXY_IMAGE` env vars (`feastoperator.go:41-45, 78`). On every reconcile it writes `OIDC_ISSUER_URL`, which must be an `https` URL with a host (`feastoperator_actions.go:125-137`). The platform type picks the overlay: `SelfManagedRhoai` / `ManagedRhoai` → `overlays/rhoai`, otherwise `overlays/odh` (`feastoperator.go:58-67`). Because the manifests are vendored, the Feast operator version (0.67.0) is pinned to the image build. Note that the checked-in RHOAI `params.env` still points at upstream `quay.io/feastdev/*:0.67.0` images. Production images are expected to come from the `RELATED_IMAGE_ODH_*` env vars that the platform operator injects, and `RELATED_IMAGE_CRON_JOB` (`ose-cli`) is not remapped.

**Capability ConfigMap finalizer handshake.** This is the most intricate logic in the repo (`feastoperator_capabilities.go`, `feastoperator_controller.go:330-399`). The module adds its own finalizer `components.platform.opendatahub.io/feast-capabilities` to `feast-capabilities-config`. The Feast operator adds `feast.dev/capabilities-config-cleanup`. On CR deletion the module:
1. Writes both capabilities as `false` and stamps a cleanup-start annotation.
2. Rolls the Feast Deployment.
3. Deletes the ConfigMap.
4. Waits up to 5 minutes (`feastOperatorReleaseTimeout`) for the Feast operator to drop its finalizer. On timeout it emits a `CapabilitiesCleanupTimeout` Warning event and carries on.
5. Releases its own finalizer and removes labelled ClusterRoles/ClusterRoleBindings.

The `rhoai-data-registry` namespace is never deleted, so its data is preserved; only its `dataregistry.opendatahub.io/enabled` label is removed. A custom watch predicate on the owned ConfigMap reacts to the update that sets `deletionTimestamp`, so the module finalizer can be released and the ConfigMap recreated (`feastoperator_controller.go:303-319`).

**Capability precedence.** When `spec.capabilities` is set it overrides startup config. Otherwise the `feature-store-enabled` / `data-registry-enabled` config keys apply, and both default to `true` (`feastoperator_capabilities.go:156-166`, `pkg/config/config.go`). So with an older platform operator that doesn't write `spec.capabilities`, Data Registry is enabled by default and the `rhoai-data-registry` namespace is created. Overlay 0031 says end-to-end DSC capability wiring is "in review", so check the platform operator version before assuming this path is shipped.

**Narrowed informer cache.** `pkg/manager/manager.go:106-145` limits informers for Deployments, Services, ServiceAccounts, Roles and RoleBindings to the applications namespace. FeastOperator and CRD informers stay cluster-wide. ConfigMaps and Secrets bypass the cache (direct API reads), and `StripUnusedFields` trims cached objects. This keeps memory down even though the ClusterRole grants cluster-wide read on Secrets.

**Cluster TLS-profile adherence.** On startup the operator reads `config.openshift.io/v1 APIServer cluster` with a 10s bootstrap client (`pkg/manager/tls.go:127-171`). It honours `tlsSecurityProfile`/`tlsAdherence` for the metrics server when adherence is not `NoOpinion`/`LegacyAdheringComponentsOnly`. A `SecurityProfileWatcher` makes the manager exit and restart when the profile or adherence policy changes. Off OpenShift (no `APIServer` kind) it falls back silently to controller-runtime defaults.

**Risks and observations:**
- *Metrics bind-address env mismatch (likely defect).* The Helm chart (`config/chart/templates/apps_v1_deployment.yaml:45-46`) and the kustomize patch (`config/default/manager_metrics_patch.yaml:6`) set `ODH_MODULE_OPERATOR_METRICS_BIND_ADDRESS=:8443`. The config loader binds keys with the `ODH_MODULE_OPERATOR` prefix and the full dotted key path, so the env var it reads is `ODH_MODULE_OPERATOR_CONTROLLER_METRICS_BIND_ADDRESS` (`pkg/config/config.go:39,71`). The chart also passes no `--metrics-bind-address` flag. Unless the platform supplies `controller.metrics.bind-address` through the `odh-data-config` ConfigMap or `extraEnvs`, the metrics server probably listens on the default `:8080`. Meanwhile `opendatahub-feast-metrics-service` and the NetworkPolicy target 8443. Verify on a live cluster.
- *Self-signed metrics certificate.* No `--metrics-cert-path` is configured in the chart, and `cert_metrics_manager_patch.yaml` is not included in `config/default`. controller-runtime therefore serves metrics with an auto-generated self-signed certificate.
- *Broad ClusterRole.* It includes `pods/exec create`, `secrets get/list/watch` cluster-wide, `clusterroles bind` (scoped by kubebuilder marker to `system:auth-delegator`), CRD CRUD and Namespace create/patch. A compromised module-operator pod gives significant cluster-wide privilege.
- *Upgrade migration.* `migrateDeploymentSelector` deletes the Feast operator Deployment when its selector does not match `app.kubernetes.io/name=feast-operator`, because selectors are immutable. Expect a short Feast operator outage on the first reconcile after upgrading from monolith-managed installs.
- *Stale scaffolding.* `config/webhook/kustomization.yaml` refers to files that don't exist and is not included in `config/default`. No admission webhooks are served.
