## Purpose

**Short**: KV-cache support for llm-d. It provides a Go KV-block indexing library for KV-cache-aware routing, a gRPC tokenizer sidecar that serves requests over a Unix domain socket, and a PVC evictor that keeps offloaded KV-cache volumes below a disk-usage threshold.

**Detailed**: The core of the repository is a Go library: `pkg/kvcache`, `pkg/kvcache/kvblock`, `pkg/kvevents` and `pkg/tokenization`. It keeps a near-real-time view of which vLLM pods hold which KV-cache blocks. vLLM pods publish `KVEvents` (BlockStored/BlockRemoved) over ZeroMQ, and the `kvevents.Pool` subscribes, decodes them (msgpack) and updates a `kvblock.Index`. The index backend is in-memory LRU, cost-aware Ristretto, or Redis/Valkey. A scheduler calls `kvcache.Indexer.GetPodScores(prompt, model, pods)` to score pods by prefix-cache hit. The prompt is tokenized first, then hashed into block keys (FNV-64a over CBOR-canonical encoding, which must match vLLM's `PYTHONHASHSEED`). The library is linked into the llm-d EPP/inference scheduler (`precise-prefix-cache-scorer` plugin) and is not deployed as its own process. The README says the indexer libraries have moved upstream to `llm-d/llm-d-router` and only deprecated imports remain here.

In RHOAI, this repository produces two container images. **`odh-llm-d-kv-cache-rhel9`** is the Python **UDS tokenizer** service (`services/uds_tokenizer`). It runs as a sidecar next to the EPP scheduler. It exposes `tokenization.TokenizationService` over gRPC on `unix:///tmp/tokenizer/tokenizer-uds.socket`, which the Go `UdsTokenizer` client in `pkg/tokenization` dials. It downloads tokenizer files from Hugging Face (or optionally ModelScope) and uses vLLM's `OpenAIServingRender` to render chat/completion requests into token IDs. KServe's LLMInferenceService controller wires this socket into the scheduler config through the `WithUdsTokenizerConfig` migration (overlay 0011).

**`odh-llm-d-kv-pvc-evictor-rhel9`** is the Go **PVC evictor** (`kv_connectors/pvc_evictor/go`). It is a single-replica Deployment that mounts the shared PVC holding vLLM's offloaded KV-cache files. Those files are written by the `llmd_fs_backend`/vLLM `OffloadingConnector` file-system tier. The evictor deletes cold `.bin` block files when usage passes `CLEANUP_THRESHOLD` (85%) and stops at `TARGET_THRESHOLD` (70%). It can optionally publish ZeroMQ `BlockRemoved` events so that indexers drop the evicted blocks. It does not use the Kubernetes API.

## Architectural Analysis

**This is a library repo with sidecars, not an operator.** The analyzer labels it "Kubernetes Operator / Controller", but that comes from `examples/kv_events/pod_reconciler`, a demo controller-runtime reconciler that watches Pods. RHOAI does not ship it. The root `Dockerfile` builds `examples/kv_events/online` as `/app/kv-cache-manager`, an HTTP demo (`/score_completions`, `/score_chat_completions`, `/metrics` on `:8080`). That Dockerfile is upstream-only: no Konflux pipeline references it. Likewise, `deploy/kustomization.yaml` is a template stub. It references `common/service.yaml`, `openshift/route.yaml` and RBAC files that do not exist in the tree, plus an `operator-controller-manager` ServiceAccount, so it is not a usable deployment. The architecturally relevant RHOAI surfaces are: (1) the Go indexer library, consumed at build time by the llm-d scheduler; (2) the UDS tokenizer sidecar image; and (3) the Go PVC evictor image.

**Konflux build coverage on this branch is asymmetric.** `.tekton/` has a push pipeline (`odh-llm-d-kv-pvc-evictor-v3-7-ea-1-push.yaml`) only for the Go PVC evictor, which produces `quay.io/rhoai/odh-llm-d-kv-pvc-evictor-rhel9:rhoai-3.7-ea.1`. The UDS tokenizer (`services/uds_tokenizer/Dockerfile.konflux`) has only a pull-request pipeline, which publishes to `quay.io/rhoai/pull-request-pipelines` with a 5-day expiry. A release-branch push build of `odh-llm-d-kv-cache-rhel9` for 3.7-ea.1 is therefore not defined in this repository. Either it comes from elsewhere, or the image is carried over from a previous release. Platform aggregation should confirm this.

**Hot path versus side path.** The tokenizer sidecar sits on the request hot path for precise-prefix-cache scoring. Every scoring call that needs tokenization becomes a gRPC call over UDS, bounded by a 100 MB message limit, run on an asyncio server with a thread pool (`THREAD_POOL_SIZE`). Using UDS instead of TCP is a deliberate security and latency choice. The gRPC port is unauthenticated and plaintext (`add_insecure_port`), and the only boundary is the pod-local filesystem: the socket directory is created with mode `0700` inside an emptyDir shared between containers. A TCP gRPC listener exists only when `GRPC_PORT` is set, and the code marks it "FOR TESTING ONLY". The PVC evictor is fully off the request path. It is a storage-hygiene control loop that relies on file `atime`, so `relatime` mounts can make warm files look cold. It also does not coordinate with writers except through a directory-cleanup TTL.

**Security observations.**
- **Remote code from model repos:** The tokenizer loads tokenizers with `trust_remote_code=True` (`tokenizer_service/tokenizer.py`), and the renderer passes it to vLLM's `AsyncEngineArgs`. The `InitializeTokenizer` RPC takes a caller-supplied model identifier. Any principal that can reach the socket can therefore cause Python code from a Hugging Face repository to execute in the sidecar. Today only containers in the same pod can reach the socket. This is the most significant trust assumption in the shipped artifacts.
- **Plaintext telemetry and Redis by default:** In the Go library, the OTLP exporter is hard-coded to `WithInsecure()`. The Redis/Valkey index uses TLS only when the address uses the `rediss://` or `valkeys://` scheme.
- **Low-privilege evictor:** The PVC evictor has a minimal footprint: no API access, `automountServiceAccountToken: false`, all capabilities dropped, non-root, RuntimeDefault seccomp. Its ZeroMQ publisher (when enabled) has no CURVE authentication.

**Duplication and drift risks.**
- **Two evictor implementations:** The Python evictor (`Dockerfile.konflux`, AIPCC `cpu-el9.8:3.6.0-ea.2`, unpinned `pip install msgpack pyzmq`) and the Go evictor share the image name `odh-llm-d-kv-pvc-evictor-rhel9`, but only the Go one is wired into Tekton.
- **Index and base mismatch:** The tokenizer's `requirements.txt` pins its index to `rhoai/3.4/cpu-ubi9-test` while its base image is AIPCC `cpu:3.5`.
- **Stale README:** The tokenizer README documents a `/config` endpoint that `run_grpc_server.py` no longer implements. Only `/healthz` exists.
- **Upstreamed connector:** `llmd_fs_backend` is marked as upstreamed into vLLM (final release `llmd-fs-connector==0.23`). The evictor still copies `event_publisher.py` from it in the Python image.
