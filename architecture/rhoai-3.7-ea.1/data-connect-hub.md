## Purpose

**Short**: Data Connect Hub (DCH) is a central service for data-source connections. It stores connection and connection-type metadata in PostgreSQL, serves a REST API for managing connections, and serves an Apache Arrow Flight gRPC API that streams data from external sources (PostgreSQL, S3, Milvus, Elasticsearch, Neo4j, SQLite, URI/HuggingFace) as Arrow record batches.

**Detailed**: Without DCH, every consuming service would carry its own client libraries for S3, relational databases, vector stores, and so on. DCH replaces that with one integration point. The **rest-service** (Rust, actix-web) handles CRUD for *connections*, *connection types* and *Flight service registrations*. It can also test credentials without saving them, run readiness audits, stream binary objects (S3/URI), and export a connection's credentials into a Kubernetes Secret in the tenant namespace. The **flight-service** (Rust, tonic + arrow-flight) is the data plane. It loads connection metadata from the shared PostgreSQL metastore, resolves credentials from Kubernetes Secrets, and uses pluggable connector crates that implement a common `SQLReader<RecordBatch>` trait to stream columnar data.

The **dc-controller** (Go, controller-runtime) is the ODH/RHOAI module operator. It reconciles a namespaced `DataConnectService` CR. To do that it renders the kustomize tree under `config/`, which is baked into its image at `/manifests`. It applies the REST and Flight Deployments, Services, NetworkPolicies, RBAC, the Gateway API `HTTPRoute` and (on OpenShift with prometheus-operator) a `ServiceMonitor`. It seeds built-in connection types as `InitDataConnectionType` CRs, pushes them to REST, and registers Flight instances with REST. Two migration controllers handle the move from ODH: they watch legacy dashboard connection-type ConfigMaps (`opendatahub.io/connection-type`) and connection Secrets (`opendatahub.io/dashboard`) and promote them into DCH. Migrated connections store only a `secret_ref`, never a copy of the credentials.

On the platform, user traffic enters through the shared `odh-gateway` (Gateway API). REST is fronted by a `kube-rbac-proxy` sidecar that maps each request to a SubjectAccessReview against synthetic resources (`data-connections`, `data-connection-types`, `data-store`, `flight-services`) in the namespace named by the `X-Tenant-Id` header. Flight runs its own TokenReview + SubjectAccessReview middleware. The tenant is therefore a Kubernetes namespace, and access is granted through ordinary RoleBindings to the shipped `read` / `read-write` / `admin` / `secret-export` ClusterRoles.

## Architectural Analysis

**Operator-renders-kustomize pattern.** dc-controller does not hand-build resources. It copies `/manifests` (the repo-root `config/` tree, copied in by `dc-controller/Containerfile.konflux:24`) into an in-memory filesystem. It then merges image and gateway parameters into `params.env`, adds strategic patches built from `spec.restService` / `spec.flightService` overrides, runs krusty, and applies the result with owner references and spec-hash annotations (`dc-controller/internal/controller/resources.go:72-224, 813-923`). It selects the `overlays/openshift` root, which adds the ServiceMonitor, only when it detects the prometheus-operator API (`dataconnectservice_controller.go:551`). Deployment manifests therefore live in the repo once, shared by standalone `kustomize build` and the operator. The cost is that the operator's behaviour depends on the image content, so the controller image must be rebuilt for any manifest change.

**Cluster-scoped side effects of a namespaced CR.** `DataConnectService` is namespaced (`scope: Namespaced`). AGENTS.md describes it as a cluster-scoped singleton, but the CRD on this branch says namespaced. The rendered manifests include ClusterRoles and ClusterRoleBindings (`flight-auth-delegator` → `system:auth-delegator`, `kube-rbac-proxy-auth-review`, `rest-service-data-access`, user roles). The controller rewrites ClusterRoleBinding subjects to the CR namespace (`patchClusterRoleBindingSubjects`, `resources.go:942`) and deletes them in a finalizer by owner UID (`deleteClusterScopedResources`, `dataconnectservice_controller.go:735`). As a result the controller needs `create/delete` on `clusterroles` and `clusterrolebindings`, which is a powerful privilege-escalation-capable grant. The two watchers also list every `DataConnectService` to detect deletion (`migration_watcher.go`), so the design effectively assumes one DCS per cluster.

**Two auth enforcement points with different mechanisms.** REST trusts kube-rbac-proxy. The Rust service listens only on `127.0.0.1:8080` (`config/base/rest-service/configmap.yaml`), never sees bearer tokens, and takes identity from `x-remote-user`. It deliberately ignores `x-remote-groups` because group names can contain the delimiter (`services/rest/src/rest/middleware.rs:195-203`), so per-request audit/identity is username-only. Authorization still happens in the proxy SAR, where groups are honoured. Flight does its own SAR (`get` on `data-store` in the `X-Tenant-Id` namespace). There is one exception: the controller's discovery ServiceAccount may call `DoAction` without a tenant header (`services/flight/src/flight/auth.rs`). REST calls Flight with its own SA token, which holds a cluster-wide `get data-store` grant (`rest-service-data-access`). After the proxy has authorized a REST caller, REST is therefore trusted to pass the correct tenant to Flight. That makes REST a confused-deputy boundary worth reviewing.

**Tenant identity is caller-supplied.** Both data planes take the tenant from the `X-Tenant-Id` header and authorize against that namespace. The shared PostgreSQL metastore filters rows by `tenant_id` in JSON metadata, plus a "global" tenant (`opendatahub`) that holds built-in connection types visible to everyone (`libs/pg-meta-store/src/store/meta.rs:99-105`). Isolation is correct only if every REST/Flight path both authorizes and filters on the same header value. Kubernetes enforces the SAR; the row filtering is application-enforced.

**TLS profile propagation.** The controller reads the OpenShift `APIServer` TLS security profile through `odh-platform-utilities/framework/tls` and applies it to its own metrics/webhook servers. It restarts on profile or adherence-policy change, and stops serving if it loses read access to `APIServer` (`dc-controller/internal/tls/profile.go`, `authorization.go`). It also projects the profile into kube-rbac-proxy args and the Flight ConfigMap (`setKubeRbacProxyTLSOpts`, `setConfigMapFlightTLSProfile`, `resources.go:1023-1147`). Flight then builds a rustls acceptor restricted to TLS 1.2/1.3 with the projected cipher list. It fails closed if a policy is projected but no cert is configured (`services/flight/src/lib.rs:69-195`). This is a well-engineered posture, but the Go side admits `tls.InsecureCipherSuites()` (all except RC4) when the profile lists them (`profile.go:100-104`).

**Release-branch build gap.** `.tekton/` on this branch only defines push/PR pipelines for `odh-data-connect-hub-rest` and `odh-data-connect-hub-flight`. `dc-controller/Containerfile.konflux` exists, but no controller pipeline is present in this repo for 3.7-ea.1, so the controller image is presumably built elsewhere or not yet onboarded. The Rust images are hermetic (cargo + RPM prefetch). The controller Containerfile runs `go mod download` with no Hermeto sourcing.

**Documentation drift.** README lists `POST /api/v1alpha1/audit/data-connection-types`, but no such route is registered in `services/rest/src/main.rs:49-77`. The `/flights` routes exist but are not exposed via the HTTPRoute; only the controller reaches them, and the NetworkPolicy allows that. AGENTS.md says the DCS is cluster-scoped, which disagrees with the CRD.

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | SAR on synthetic resources in tenant namespace; tenant RoleBindings to `dch-read`/`read-write`/`admin`/`secret-export` | Kubernetes (kube-rbac-proxy, Flight SAR) | REST→Flight uses REST SA with cluster-wide `get data-store`, so Flight trusts REST to forward the correct tenant (confused-deputy surface). REST identity drops groups (audit only) |
| Data storage | Shared PostgreSQL; rows filtered by `tenant_id` JSON field | Application | Application-enforced row filtering; one bug crosses tenants. No per-tenant schema/DB |
| Network traffic | NetworkPolicies: REST 8443 only from gateway pods and controller; Flight 8443 only from REST and gateway; metrics 9090 open to all | Kubernetes | Not per-tenant (shared service). Metrics port open cluster-wide |
| Compute & resources | Single shared Deployments with limits (1 CPU / 512Mi); no per-tenant quota | Kubernetes | Noisy-neighbour risk; Flight `max_rows` 1,000,000 cap is global |
| Configuration & secrets | Credentials stay in tenant-namespace Secrets referenced by `secret_ref`; REST/Flight need a per-tenant RoleBinding to `dch-rest-service-secret-access` | Kubernetes | Manual per-tenant binding; controller SA has cluster-wide Secret CRUD and watches all labelled Secrets for migration |
| API scoping | Every `/data/*` request needs a tenant header and namespace SAR; built-in types are global | Kubernetes + Application | Global-tenant types are readable by all tenants by design |

|----------------|----------------|---------------------|
| PostgreSQL metastore | `tenant_id` in row JSON | Application query filter |
