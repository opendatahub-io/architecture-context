## Purpose

**Short**: Extends KServe on OpenShift AI by reconciling InferenceServices, LLMInferenceServices, ServingRuntimes, InferenceGraphs, and NVIDIA NIM Accounts into the OpenShift/RHOAI-specific resources they need (Routes, RBAC, NetworkPolicies, monitoring, auth policies, certificates), and by enforcing RHOAI-specific admission rules.

**Detailed**: odh-model-controller is the RHOAI "glue" controller for model serving. Upstream KServe owns the core serving lifecycle; this controller watches the same KServe resources and adds platform behaviour that KServe does not provide: OpenShift Routes for raw-deployment InferenceServices, ServiceMonitors/PodMonitors and metrics dashboards, KEDA TriggerAuthentications for Prometheus-based autoscaling, per-ISVC ServiceAccounts/ClusterRoleBindings for auth, custom CA bundle and storage-config propagation into user namespaces, Ray TLS certificates for multi-node vLLM, and optional Model Registry registration (when `MODELREGISTRY_STATE=managed`).

For the llm-d / LLMInferenceService stack it reconciles Gateway API Gateways into Istio EnvoyFilters and Kuadrant AuthPolicies (so Authorino TLS configuration exists even before any model is deployed), watches Kuadrant/Authorino state, and publishes cluster-scoped `grid.praxis.fast/InferenceProvider` objects with matching Roles, RoleBindings, and NetworkPolicies for LLMInferenceServices attached to Gateways. It also owns the only CRD in the repo, `nim.opendatahub.io/v1 Account`, which validates an NVIDIA NGC API key against NVIDIA endpoints and materialises NIM ServingRuntime Templates, ConfigMaps, and pull Secrets.

The repo produces a second image, `odh-model-serving-api`, a small HTTPS service for the RHOAI dashboard/UI. It provides user-scoped Gateway discovery (`/api/v1/gateways`, filtered per namespace with SelfSubjectAccessReview using the caller's token) and static llm-d sample manifests. The repo also ships 30 ClusterServingRuntimes (vLLM for CUDA/ROCm/Gaudi/Spyre/CPU, vLLM-Omni, MLServer, OVMS) plus OpenShift Templates for serving runtimes. The opendatahub/rhods operator deploys all of them through kustomize parameters.

## Architectural Analysis

**Two-binary design with a deliberate trust split.** The manager (`cmd/main.go`) runs with a broad ClusterRole (create/delete on Secrets, RBAC objects, NetworkPolicies, EnvoyFilters, AuthPolicies, Routes), while `model-serving-api` (`server/`) runs under a separate ServiceAccount whose ClusterRole only allows listing Gateways, getting Namespaces, and reading `config.openshift.io/apiservers`. The API server does not use its own identity to authorize users. `middleware.Auth` only extracts a Bearer token, then the Gateway discoverer issues a `SelfSubjectAccessReview` *as the caller* (per-request rest.Config with the user token) before returning namespace-scoped Gateways (server/gateway/discovery.go:120-171). Authorization is therefore delegated to kube-apiserver RBAC. The middleware itself does no token validation; that happens when the SSAR call fails for a bad token.

**Cluster TLS-profile awareness is a first-class concern.** `pkg/tls` resolves the OpenShift `APIServer` TLS security profile and the new `TLSAdherence` policy. The manager always applies the profile to its webhook and metrics servers and fails fast on a malformed profile (cmd/main.go:119-130). The API server keeps a TLS 1.2 + ECDHE-AES-GCM baseline (with X25519MLKEM768 PQC curve preference) under `NoOpinion`/`LegacyAdheringComponentsOnly`, and applies the cluster profile under `StrictAllComponents` or unknown values (server/tlspolicy.go). Both binaries watch the APIServer object and restart themselves when the profile changes (`ProfileWatcher`, `watchTLSPolicy`) instead of hot-swapping cipher config.

**Deployment modes.** `ODH_PLATFORM_TYPE=xKS` (internal/platform/platform.go:13) switches the manager to a webhook-only profile: no reconcilers, only the LLMInferenceService webhook (ConnectionsAPI injection plus HardwareProfile DRA checks). This supports non-OpenShift Kubernetes (`config/overlays/xks`, which uses cert-manager instead of service-ca). Feature toggles `NIM_STATE`, `MODELREGISTRY_STATE`, `KSERVE_STATE`, and `ENABLE_WEBHOOKS` gate whole subsystems at startup rather than at runtime.

**Admission webhooks are fail-closed and in the hot path of every pod creation.** All 10 webhooks use `failurePolicy: Fail`. The Pod mutating webhook intercepts *all* Pod CREATEs (filtered in code to pods with `RAY_USE_TLS`), so webhook-service availability directly affects cluster-wide pod scheduling in watched namespaces. The webhook NetworkPolicy allows all ingress to the manager pod (`ingress: [{}]`, config/webhook/networkpolicy.yaml), so network-level protection of the webhook and metrics ports comes only from TLS plus metrics authn/authz.

**Credential-bearing mutation.** The ISVC and LLMISVC mutating webhooks implement the ConnectionsAPI: an `opendatahub.io/connections` annotation naming a Secret causes the webhook to inject storage URIs/credentials (and create ServiceAccounts) into the workload spec. The SecretReconciler likewise builds a namespace `storage-config` Secret from data-connection Secrets. Users who can annotate a serving resource can only reference Secrets in their own namespace, but the webhook runs with the controller's privileges.

**Risks and observations.**
- NIM integration makes outbound HTTPS calls to `api.ngc.nvidia.com`, `authn.nvidia.com`, and `nvcr.io` from the controller pod, which matters in disconnected/air-gapped installs (`NIM_STATE=removed` disables it).
- `MR_SKIP_TLS_VERIFY` (default false) can disable TLS verification for Model Registry calls (cmd/main.go:372).
- The controller generates self-signed RSA-4096 CA and leaf certificates in-process for Ray TLS (internal/controller/utils/cert.go:65). These have no rotation path outside the controller.
- `params.env` on this branch still points to `quay.io/opendatahub/*:odh-stable` and `quay.io/vllm/*:latest` images. The RHOAI operator is expected to override these with digest-pinned RHOAI images at deploy time.
- A `MaaSRBACCleanupRunner` removes legacy tier-based MaaS Roles/RoleBindings at startup, which shows that MaaS RBAC ownership has moved out of this component.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-ISVC ServiceAccount + ClusterRoleBinding; Kuadrant AuthPolicy for LLMISVC; SSAR-as-user in model-serving-api | Kubernetes / Platform (Authorino) / Application | Controller holds a cluster-wide escalation-capable SA. | Data storage | Per-namespace `storage-config` Secret built from that namespace's data connections | Kubernetes / Application | Webhooks read Secrets with controller privileges. Namespace scoping is enforced in code, not by RBAC |
| Network traffic | Per-ISVC and per-Grid-provider NetworkPolicies; Gateway AuthPolicies | Kubernetes / Istio | Webhook NetworkPolicy allows all ingress to the controller pod |
| Compute & resources | HardwareProfile injection/DRA validation | Kubernetes / Application | No ResourceQuota management by this component |
| Configuration & secrets | Per-namespace CA bundle ConfigMap, NIM Account singleton per namespace | Kubernetes / Application (webhook) | Global CA bundle is copied into every serving namespace |
| API scoping | Cluster-wide watches; protected application namespace rejected for ISVCs | Application | All namespaces are watched; there is no namespace allow-list in the manager |
