## Purpose

**Short**: EvalHub is a multi-tenant REST API service that catalogs evaluation providers/benchmark collections and orchestrates LLM evaluation runs as Kubernetes Jobs, tracking status and results.

**Detailed**: eval-hub (image `odh-eval-hub-rhel9`) is the server side of the EvalHub evaluation platform. Clients (the `eval-hub-sdk`, the RHOAI dashboard, or an MCP-capable AI assistant via `evalhub-mcp`) submit evaluation jobs against a catalog of **providers** (lm-evaluation-harness, lighteval, garak, guidellm, inspect, ragas, deepeval, mteb, nemo-guardrails, etc. — `config/providers/*.yaml`) and curated **collections** of benchmarks (`config/collections/*.yaml`). The server validates the request, persists it as a JSON document in SQL (SQLite or PostgreSQL), optionally creates an MLflow experiment, and hands it to a pluggable **Runtime** — `local` (subprocesses, dev) or `k8s` (production).

The Kubernetes runtime builds, per evaluation, a job-spec ConfigMap, an optional rewritten model-credential Secret, an ingress-deny NetworkPolicy, and a `batch/v1` Job. The Job pod contains: an **init container** (`eval-runtime-init`) that stages test data from S3, Git, or Hugging Face; a native **sidecar** (`eval-runtime-sidecar`, run as a restartable init container) that proxies adapter traffic to eval-hub, MLflow, OCI registries and model endpoints while injecting credentials; and the **adapter** container (provider image from the catalog) that runs the benchmark and posts status events back to `/api/v1/evaluations/jobs/{id}/events` through the sidecar. Jobs honour Kueue queue / priority-class labels and ODH `HardwareProfile` resources.

In RHOAI the service is deployed by the TrustyAI service operator (the repo carries a CI check that the operator's ConfigMap stays in sync with `config/`), fronted by **kube-rbac-proxy** which authenticates callers and forwards `X-Tenant` (namespace) and `X-User` headers. A single Konflux image ships all four runtime binaries (`eval-hub`, `eval-runtime-sidecar`, `eval-runtime-init`, `evalhub-mcp`); the operator selects the binary per container.

## Architectural Analysis

**One image, four roles.** `Dockerfile.konflux` compiles four binaries into a single image with `CMD ["/app/eval-hub"]`. The same image therefore serves as the API server, the job init container, the job sidecar and the MCP server. This simplifies release/versioning (sidecar protocol always matches server version) but means the job pods pull the full server image, and any CVE in one binary's dependency tree affects all roles.

**Authentication is fully delegated.** eval-hub does not validate tokens. In cluster mode `canContinueRequest` (`internal/eval_hub/server/server.go:512`) only checks that `X-Tenant` and `X-User` headers are non-empty; in `--local` mode it skips even that. The security of the whole API therefore rests on (a) kube-rbac-proxy being the only network path to the backend listener and (b) the proxy stripping client-supplied identity headers. The service binds `127.0.0.1` by default (`config/config.yaml:3`), which is the intended guard when kube-rbac-proxy runs as a sidecar in the same pod. The separate metrics listener on `0.0.0.0:8081` is intentionally unauthenticated. `evalhub-mcp` defaults to `auth_type: none` and offers `rbac-proxy` (header trust) as the only alternative.

**Tenant = namespace, and tenancy drives placement.** The `X-Tenant` value scopes every SQL query (`storage/sql/shared/statements.go` passes `api.Tenant` to all CRUD statement builders) *and* is used as the namespace in which the Kubernetes runtime creates the Job, ConfigMap, Secret and NetworkPolicy (`runtimes/k8s/job_config.go:185`). The upstream docs explicitly note that tenant-membership authorization ("can this user submit into that namespace?") is a separate boundary that eval-hub does not itself verify — it is expected to be enforced by kube-rbac-proxy's SubjectAccessReview configuration and by the operator-provisioned RoleBindings.

**Job pod hardening.** Job pods set `AutomountServiceAccountToken: false` (`job_builders.go:262`), so the adapter has no Kubernetes API credential; the sidecar obtains eval-hub/MLflow tokens from mounted files and injects them, keeping secrets out of the adapter process. Model credentials are copied into a per-job "reference" Secret with rewritten values (`secret_builder.go`) so the adapter sees placeholders that the sidecar resolves. The per-job NetworkPolicy denies all peer-pod ingress but deliberately does **not** select egress (`network_policy.go:18-21`); egress isolation is an acknowledged open gap (`docs/network-policies.md`).

**Workload registry.** Post-processing (e.g. confidence intervals over a finished evaluation) is modelled as an internal workload type stored in the same `evaluations` table with a `workload_type` column, reusing the same runtime and status-event path. This is the extension point for future server-managed workloads.

**Native TLS is optional.** The API and MCP HTTP listeners share `internal/servingtls`, which defaults to plaintext unless certificate files are provided, and enforces TLS 1.2+ when enabled with optional `TLS_MIN_VERSION`, `TLS_CIPHERS`, `TLS_CURVES` (including PQC hybrid groups `X25519MLKEM768` etc.). The managed topology expects kube-rbac-proxy to terminate TLS. The runtime image is `ubi9/ubi-minimal-pqc`, signalling post-quantum readiness.

**Observability.** Prometheus metrics on a dedicated port, optional OpenTelemetry traces/metrics/logs over OTLP gRPC or HTTP, including export of adapter container logs at job completion (`internal/otel/job_logs.go`).

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy authn/authz; eval-hub trusts headers | Platform (kube-rbac-proxy) | eval-hub only checks header presence; any path bypassing the proxy can spoof tenant. `--local` disables checks. Tenant-membership authorization is explicitly out of eval-hub scope |
| Data storage | Shared SQL DB, tenant column filtering on all CRUD statements | Application | Single DB for all tenants; isolation relies on correct query construction |
| Network traffic | Per-job ingress-deny NetworkPolicy | Kubernetes | Egress not restricted (documented gap); API/metrics network isolation is operator-defined |
| Compute & resources | Jobs created in tenant namespace; Kueue queues, PriorityClass, HardwareProfiles | Kubernetes / Kueue | Relies on namespace ResourceQuota/Kueue config owned elsewhere |
| Configuration & secrets | Per-job ConfigMap/Secret in tenant namespace; reference-Secret rewriting; no SA token in pod | Kubernetes / Application | Server SA needs secret read/create across all tenant namespaces it serves |
| API scoping | Tenant-filtered queries; namespace-scoped K8s calls | Application | System-scoped providers/collections are shared read-only catalog |

### Shared Services

|----------------|----------------|---------------------|
| eval-hub SQL database (SQLite/PostgreSQL) | tenant column | application query filter |
| Provider/collection system catalog | none (shared, read-only) | system vs tenant scope in storage |
| MLflow | MLflow workspace (`MLFLOW_WORKSPACE`) | MLflow server |
