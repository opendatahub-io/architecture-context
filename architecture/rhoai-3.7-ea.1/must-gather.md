## Purpose

**Short**: Container image of Bash collection scripts. It snapshots RHOAI/RHAII cluster state (namespaces, CRs, pod logs, Helm releases) into a `must-gather/` directory for support diagnostics.

**Detailed**: `odh-must-gather` is the RHOAI-specific diagnostics image. Cluster admins run it with `oc adm must-gather --image=registry.redhat.io/rhoai/odh-must-gather-rhel9:<ver>`. The image is based on `ose-must-gather-rhel9:v4.22`. It keeps the stock OpenShift gather as `/usr/bin/gather_original` and replaces `/usr/bin/gather` with `collection-scripts/gather.sh`. The script detects the Kubernetes distribution (OCP, CKS, AKS, EKS, or other) and resolves platform namespaces. On OCP it reads the operator namespace from the `rhods-operator` Subscription. It writes a `version` file, then inspects the core RHOAI namespaces and platform CRs: DSCI, DSC, `*.components.platform.opendatahub.io`, `*.services.platform.opendatahub.io`, webhook configurations and admission policies.

After that it dispatches per-component collectors. On OCP the default (`COMPONENT=all`) runs 15 collectors in parallel: DSP, KServe (plus LLM-D and ModelExpress), Workbench, KubeRay, Kueue, KFTO, Model Registry, TrustyAI, Feast, Data Registry, MLflow, Spark, AI Gateway (plus MaaS, Grid and Batch Gateway), MCP Lifecycle Operator and OGX. Each collector lists every namespace that holds its CR kinds and inspects those namespaces in full. On non-OpenShift Kubernetes ("xKS": CoreWeave CKS, AKS, EKS) `oc` is not available. The image instead uses a kubectl-based re-implementation of `oc adm inspect` (`kubectl_inspect` in `llm-d/xks_util.sh`) and by default collects only KServe/LLM-D and AI Gateway. It also collects the infrastructure CR for the detected cloud distribution (`azure|coreweave|aws kubernetesengines.infrastructure.opendatahub.io`).

The component has no long-running process, Service, CRD, or network listener. All of its interaction goes through the user's or ServiceAccount's Kubernetes API credentials. It is architecturally important because it is the platform's support data-plane: whatever it collects leaves the cluster in support cases. Its resource list therefore acts as a de-facto inventory of the CRDs that RHOAI 3.7 ships or depends on (see Dependencies).

## Architectural Analysis

**Wrapper-over-upstream pattern.** The Konflux image does not fork OpenShift's must-gather. It layers on top of it. The base image's `gather` is preserved as `gather_original` but is never called by `gather.sh`, so OpenShift core data is not collected unless the user also runs the default must-gather image. `oc adm must-gather` expects `/usr/bin/gather`, and the Dockerfile renames `gather.sh` to that path (`Dockerfile.konflux:12-14`). The image adds `kubectl` (from `ose-cli-rhel9`) and a Helm v4.1.4 binary. The Helm binary is committed via Git LFS (`bin/helm` is an LFS pointer, sha256 `210d576a…`). Helm is used only for `helm get values` and `helm get manifest` on the RHAII Helm chart release (`rhai-gitops/rhoai` on OCP, `rhaii` on xKS) and on the `batch-gateway` release.

**Two collection back-ends with different safety properties.** On OCP most collection goes through `oc adm inspect`. That command elides Secret data and writes the directory layout that must-gather tooling expects. The newer LLM-D/xKS code path (`llm-d/xks_util.sh`) replaces this with `kubectl_inspect`. That function enumerates **every** namespaced `api-resources` type and runs `$KUBECTL get <type> -o yaml` (`xks_util.sh:15-41`). It also dumps every cluster-scoped type (`collect_cluster_scoped_resources`, called from `llm-d/gather_cluster.sh:32`). There is no deny-list, so `secrets` are included with their base64 `data`, along with any other sensitive kinds. The xKS path is not the only one affected. On OCP, `gather_kserve.sh` → `llm-d/gather_llmd.sh` also calls `kubectl_inspect "namespace/…"` (with `KUBECTL=oc`) for these namespaces:
- `cert-manager` and `cert-manager-operator` (`dependency/cert-manager.sh:31-33`)
- `istio-system` (`dependency/sail.sh:58`)
- `openshift-lws-operator` (`dependency/lws.sh:61`)
- the monitoring namespace (`gather_o11y.sh:74`, which resolves to `redhat-ods-monitoring` because `gather.sh:47` exports it)
- `batch-gateway` (`gather_batch_gateway.sh:18`)

`gather_cluster.sh` also runs on OCP. Because of this, a default OCP must-gather can capture Secrets from these namespaces (for example cert-manager CA keys and Istio CA material) and cluster-scoped objects that hold credentials. That is a real data-handling risk for support bundles and is the main finding of this analysis. `helm get values` output is also written unfiltered and can contain chart-supplied credentials (`common.sh:84`).

**Parallelism and robustness.** On OCP, the `all` mode forks one background job per component, tracks their PIDs and reports failed components in a summary (`gather.sh:180-238`). Within LLM-D, namespaces and pod logs are also collected in nested background subshells. Errors are swallowed broadly (`2>/dev/null`, `|| true`, `|| echo`), so a gather is "SUCCESS" even when individual inspections fail. The same namespace can be inspected more than once. `run_mustgather` re-inspects the full namespace for each component, and the README's own CR-to-namespace mapping overlaps across components. Collection time grows with the number of namespaces that hold any watched CR kind. `get_operator_ns` builds a Go-template command string and runs it through `eval` (`common.sh:93-94`). The operator name is a hard-coded literal, so it is not exploitable today, but the pattern is fragile.

**Distribution detection** is heuristic (`xks_util.sh:138-180`). The order is: `infrastructures.config.openshift.io/cluster` → node kernel string containing "coreweave" → `azure://` providerID → `aws://` providerID plus `-eks-` server version → RHCOS osImage fallback. Only the first node is inspected. The detected distribution drives the defaults for namespaces, components and the optional collectors (`ENABLE_MAAS`, `ENABLE_GRID`, `ENABLE_BATCH_GATEWAY`, `ENABLE_MODELEXPRESS`).

**Supply chain.** The Konflux build is hermetic (`hermetic: true`, RPM prefetch). Its single extra RPM (`crypto-policies-scripts`) is pinned in `rpms.lock.yaml` for four architectures. Both base images are digest-pinned. The upstream `Containerfile` (developer build via `make build-must-gather`) is a different and weaker recipe. It uses unpinned `quay.io/openshift/origin-must-gather:4.21.0`, `kubectl` v1.34.7 fetched with `curl` without checksum verification, and Helm downloaded from `get.helm.sh` without verification. The `Containerfile` also hard-codes `amd64`. The image switches the system crypto policy to `DEFAULT:PQ` (post-quantum hybrid) at build time (`Dockerfile.konflux:16-17`). This affects TLS from `oc`, `kubectl` and `helm` to the API server.

**Drift signals.** The README examples still reference the `v3.6.0` image tag and RHOAI 3.6. The `rhoai_version` function reads the CSV whose name contains `rhods` and falls back to the operator deployment's `olm.owner` label. On Helm-installed (non-OLM) RHAII on OCP, the version file will report `Unknown`.
