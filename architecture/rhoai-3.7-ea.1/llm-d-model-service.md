## Purpose

**Short**: A kubebuilder controller that reconciles `ModelService` (`llm-d.ai/v1alpha1`) custom resources into a complete llm-d inference stack: prefill/decode vLLM Deployments, an Endpoint Picker (EPP), Gateway API Inference Extension `InferencePool`/`InferenceModel`, an `HTTPRoute`, and supporting ServiceAccounts/RoleBindings.

**Detailed**: A `ModelService` declares the desired state for serving one base model. The controller reads an optional **BaseConfig**, which is a ConfigMap holding platform-defined YAML templates for child resources. It renders Go templates (with Sprig functions) in both the BaseConfig and the ModelService against the ModelService spec. It then semantically merges the ModelService values over the BaseConfig with `mergo`, plus custom slice transformers. Finally it creates or updates each child resource with `controllerutil.CreateOrUpdate`. Every child carries an owner reference back to the ModelService, so Kubernetes garbage collection handles cleanup. Status is populated with child-resource names, ready/available replica counts for prefill, decode and EPP, and `metav1.Condition`s.

Model artifacts can come from HuggingFace (`hf://`, with an optional `authSecretName` injected as `HF_TOKEN`), a PVC (`pvc://`), or an OCI image (`oci://`). Prefill and decode can be scaled separately (`decoupleScaling`), constrained to accelerator node labels, and configured with tensor/data parallelism. The controller binds the EPP ServiceAccount it creates to an operator-supplied ClusterRole (`--epp-cluster-role`) through a namespaced RoleBinding. Image pull secrets for PD and EPP pods are injected through the `--pd-pull-secrets` and `--epp-pull-secrets` flags.

**Lifecycle status:** the upstream README marks the project **deprecated and no longer actively maintained**. The llm-d project accepted a Helm-chart replacement (`llm-d-incubation/llm-d-modelservice`) on 2025-06-10. The checkout's HEAD commit (2025-07-02) is the deprecation notice itself. This repo is tracked in the RHOAI 3.7 EA1 llm-d checkout set, but no Konflux build artifacts exist on the analyzed branch. That strongly suggests it is carried as legacy/lineage context rather than shipped as an RHOAI product image.

## Architectural Analysis

**Templated composition controller.** The core design is "BaseConfig + overrides". Platform teams write a ConfigMap whose data keys (`decodeDeployment`, `prefillDeployment`, `eppDeployment`, `eppService`, `inferencePool`, `inferenceModel`, `httpRoute`, `configMaps`, …) hold YAML fragments that may contain Go template expressions. Model owners write a small ModelService. The controller does three things per reconcile (`internal/controller/modelservice_controller.go:171-230`):

1. Interpolate both documents (`template.go`, Sprig plus custom funcs such as `getPort`).
2. Merge them (`MergeChildResources`, `child_resources.go:308`).
3. Push them to the cluster (`invokeCreateOrUpdate`, `child_resources.go:959`).

The controller has no finalizer logic. Deletion relies entirely on owner references and Kubernetes GC.

**Event fan-in via owner-reference mapping.** The reconciler uses `For(ModelService)` and `Watches(...)` with `EnqueueRequestsFromMapFunc` on Deployments, Services, RoleBindings, ConfigMaps, HTTPRoutes, InferenceModels, InferencePools and ServiceAccounts (`modelservice_controller.go:233-247`). Each map function walks owner refs looking for `llm-d.ai/v1alpha1 ModelService`. These watches are **cluster-wide** (no namespace restriction in `ctrl.Options`), so the informer cache holds every Deployment, Service, ConfigMap and RoleBinding in the cluster. That is a memory and scale cost, and it is why the RBAC is a ClusterRole. Edits to a BaseConfig ConfigMap only trigger a reconcile if the ConfigMap is owned by a ModelService. Shared BaseConfig presets are normally not owned, so changing a preset does not re-reconcile its ModelServices until something else triggers them.

**Gateway API Inference Extension integration.** The controller is an early consumer of GIE `v1alpha2`. It registers `inference.networking.x-k8s.io` types in its scheme and creates `InferencePool` (selecting decode pods by label) and `InferenceModel` objects. It also creates an `HTTPRoute` whose `parentRefs` come from `spec.routing.gatewayRefs` and whose backendRef is the InferencePool (`child_resources.go:844-905`). Request routing at runtime is therefore delegated to whatever Gateway implementation is installed, plus the EPP (`llm-d-inference-scheduler` in the samples, ext-proc gRPC on 9002). The controller itself is never on the data path.

**RBAC escalation surface by design.** To let EPP pods watch pods and InferencePools, the controller writes RoleBindings in tenant namespaces that point to the ClusterRole named by `--epp-cluster-role`. Kubernetes only allows creating a binding to a role you already hold (or with `bind`), so the deployment also ships a ClusterRoleBinding granting the controller SA that same `$EPP_CLUSTER_ROLE` (`config/rbac/epp_role_binding.yaml`). The controller's effective permissions are therefore manager-role ∪ EPP ClusterRole, cluster-wide.

**Cross-namespace BaseConfig risk.** `spec.baseConfigMapRef` is a full `corev1.ObjectReference`, and its `namespace` is honoured (`child_resources.go:234-242`). Any user who can create a ModelService can make the controller read a ConfigMap from **any** namespace using the controller's cluster-wide `configmaps get`, and have its rendered contents materialized into their own namespace. Similarly, `mergeConfigMaps` keeps an explicit `namespace` on BaseConfig-declared ConfigMaps (`child_resources.go:372-374`). Cross-namespace owner references are rejected by `controllerutil.SetOwnerReference`, but that error is only logged (`child_resources.go:378-381`), after which `CreateOrUpdate` still runs with cluster-wide `configmaps create/update`. A BaseConfig author can therefore create or overwrite unowned ConfigMaps in other namespaces. All other child kinds have their namespace forced to the ModelService's namespace.

**Packaging quirks.** The only Dockerfile builds a **static** binary (`CGO_ENABLED=0`) on `quay.io/projectquay/golang:1.24` and copies it into the full `ubi9/ubi:latest` image. Its default `CMD` is `sleep infinity` (`Dockerfile:34`), so the image is inert unless the Deployment overrides the command; `config/manager/manager.yaml` does this with `/manager run`. The `generate` sub-command (`cmd/generate.go`) runs the same interpolate-and-merge pipeline offline and prints manifests. That is useful for debugging BaseConfigs and was a stepping stone toward the Helm-chart replacement. The `deploy/` tree is an unrelated generic scaffold (StatefulSet + edge Route + `pods/exec` granted to `system:authenticated`) with placeholder values. It is not wired to this binary.

**Metrics and probes.** Probes listen on `:8081` (`/healthz`, `/readyz`, unauthenticated). Metrics are disabled by default (`--metrics-bind-address=0`), but the default kustomize overlay enables them on `:8443`. With `--metrics-secure=true` (default), controller-runtime serves HTTPS and protects `/metrics` with TokenReview/SubjectAccessReview (`filters.WithAuthenticationAndAuthorization`, `cmd/run.go:156-162`). Unless `--metrics-cert-path` is set, the certificate is controller-runtime's self-signed one. HTTP/2 is disabled by default as a Rapid Reset mitigation (`cmd/run.go:103-112`). A webhook server object is constructed but no webhooks are registered.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-ModelService EPP SA + RoleBinding to a shared ClusterRole; PD SA per ModelService | Kubernetes RBAC | Controller SA is highly privileged cluster-wide (RoleBindings, Deployments, ConfigMaps everywhere plus the EPP ClusterRole); a controller compromise affects all tenants |
| Data storage | Model PVCs referenced by `pvc://` in the tenant namespace | Kubernetes | No checks beyond Kubernetes; PVC must be in the same namespace |
| Network traffic | None created by the controller; optional metrics NetworkPolicy for the controller only | — | Model-server and EPP Services are open within the cluster unless the platform adds NetworkPolicies |
| Compute & resources | Per-PD resources/accelerator node affinity from spec | Kubernetes scheduler | No ResourceQuota/LimitRange created |
| Configuration & secrets | `baseConfigMapRef.namespace` honoured; BaseConfig `configMaps[].namespace` honoured | Application (none) | **Cross-namespace read**: a tenant can make the controller read any namespace's ConfigMap and project it into theirs. **Cross-namespace write**: BaseConfig-declared ConfigMaps with explicit namespaces are created/overwritten elsewhere (the owner-ref error is only logged) — child_resources.go:234-242, 372-381 |
| API scoping | Cluster-wide watches/cache of Deployments, Services, ConfigMaps, SAs, RoleBindings, HTTPRoutes, GIE objects | Application (owner-ref mapping) | Large cache footprint; isolation depends on owner-ref filtering in map funcs |
