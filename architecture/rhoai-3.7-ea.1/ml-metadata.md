## Purpose

**Short**: ML Metadata (MLMD) is a C++ gRPC service and Python library that records and queries lineage metadata (artifacts, executions, contexts, events) for ML workflows. RHOAI ships it as the `odh-mlmd-grpc-server` image.

**Detailed**: MLMD comes from Google's TFX ecosystem. It defines a typed metadata model: ArtifactTypes, ExecutionTypes, ContextTypes and their instances, plus Events, Attributions, Associations and parent/child Context links. It also provides a storage abstraction that persists this model in a relational database. The repo contains the `MetadataStoreService` gRPC API definition (`ml_metadata/proto/metadata_store_service.proto`), the C++ implementation (`ml_metadata/metadata_store/`), backends for MySQL/MariaDB, PostgreSQL, SQLite and an in-memory fake database, and the `ml-metadata` Python client package (`setup.py`).

In RHOAI 3.7-ea.1, Konflux builds exactly one artifact from this repo: the `metadata_store_server` binary, packaged as `quay.io/rhoai/odh-mlmd-grpc-server-rhel9` from `ml_metadata/tools/docker_server/Dockerfile.konflux`. The server is a stateless gRPC front end. On startup it connects to an external database, creates or migrates the MLMD schema, and then serves `ml_metadata.MetadataStoreService` on port 8080 (default). The repo itself has no Kubernetes manifests. The platform (in practice the Data Science Pipelines operator; inferred, not shown in this repo) deploys the image and supplies the database connection flags.

In the platform, MLMD is the lineage and artifact-tracking backend for Kubeflow Pipelines v2 / Data Science Pipelines. The pipeline driver and launcher record executions and artifacts in it, and the UI reads lineage graphs from it. That integration is inferred from the platform role and the component's history, not proven by code in this repo.

## Architectural Analysis

**A stateless gRPC façade over a pluggable RDBMS.** `metadata_store_server_main.cc` parses gflags, builds a `MetadataStoreServerConfig`, calls `CreateMetadataStore()` once to initialize or migrate the schema (retrying up to `--metadata_store_connection_retries` on `Aborted`), then starts a `grpc::ServerBuilder` bound to `0.0.0.0:<grpc_port>` (`metadata_store_server_main.cc:575-627`). `MetadataStoreServiceImpl` opens connections per request from the stored `ConnectionConfig`. All state lives in the database, so the server can scale horizontally provided the backend can take the load. Concurrent replicas racing on schema migration is a risk worth noting.

**Four backend selection modes.** `--metadata_source_config_type` accepts `default`, `config_file`, `mysql` or `postgresql`. In `default` mode the server tries the textproto config file first, then the `--mysql_config_*` flags. If neither is set it **silently falls back to an in-memory fake database** and logs only a warning (`metadata_store_server_main.cc:~460`). A misconfigured deployment can therefore look healthy while losing all metadata on restart.

**Inbound transport is plaintext by default.** The image sets `METADATA_STORE_SERVER_CONFIG_FILE=""`, and server credentials default to `grpc::InsecureServerCredentials()`. TLS (and optional mTLS through `client_verify`) is enabled only when the config file supplies an `ssl_config` block (`metadata_store_server_main.cc:45-61, 609-613`). The server has no authentication or authorization of its own. Any client that can reach the port can read and write all metadata. Isolation depends entirely on network placement and any fronting proxy, such as the DSP Envoy/kube-rbac-proxy (inferred).

**The crypto supply chain bypasses system OpenSSL, which is the most significant architectural risk.** The Bazel build fetches pinned third-party sources: gRPC v1.58.3, abseil, protobuf, upb, zlib, SQLite 3.47.2, PostgreSQL 12.17 sources, the MariaDB connector, ZetaSQL and glog. It also fetches **BoringSSL** at commit `648cbaf…` (`WORKSPACE:54-61`). gRPC's TLS and the MariaDB connector's TLS (`libmysqlclient.BUILD:49-50, 92, 110` → `@boringssl//:ssl`) are both statically linked against that non-validated BoringSSL. The runtime base is `ubi9/ubi-minimal-pqc` and the builder installs `openssl-devel`, but neither leads the binary to use system OpenSSL. libpq is compiled **without** SSL (`postgresql.BUILD:715, 736, 1306` — `HAVE_LIBSSL`/`USE_OPENSSL` undefined). The `--postgres_config_ssl*` flags are therefore exposed, but encrypted PostgreSQL connections likely cannot actually be established.

**Large, slowly-moving upstream fork.** The branch tracks upstream `google/ml-metadata` 1.15.0.dev. Downstream changes are limited to build fixes: a multi-arch Bazel 6.3.2 bootstrap for ppc64le/aarch64, `-Wno-error` workarounds (`Dockerfile.konflux:22-57`), tzdata reinstall, a non-root UID 65534, and a PQC base image. The Python client (`grpcio`, `protobuf<4`) and Go SWIG bindings are present but not shipped by Konflux in this release.
