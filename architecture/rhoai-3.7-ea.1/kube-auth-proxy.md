## Purpose

**Short**: kube-auth-proxy is a FIPS-built authentication reverse proxy, forked from oauth2-proxy. It authenticates users through OpenShift OAuth or any OIDC provider, and can also validate Kubernetes bearer tokens through TokenReview. It is the authentication layer for RHOAI's platform ingress.

**Detailed**: kube-auth-proxy is a disconnected fork of upstream `oauth2-proxy/oauth2-proxy`. It strips every identity provider except generic OIDC, and it adds an OpenShift OAuth provider ported from `openshift/oauth-proxy` (`DESIGN.md`, `providers/openshift.go`). The fork was created to replace the legacy `oauth-proxy` sidecars in ODH/RHOAI with a single proxy that supports both the in-cluster OpenShift OAuth server and external "bring your own OIDC" (BYOIDC) identity providers. It also had to pass Konflux `check-payload` FIPS validation.

The proxy can run in two ways. As a classic reverse proxy, it serves `/oauth2/*` login, callback, and sign-out pages, keeps an encrypted session cookie (or a Redis-backed session ticket), and forwards authenticated requests upstream with identity headers. As an auth-only endpoint, `/oauth2/auth` returns 202/401 for Envoy `ext_authz` or nginx `auth_request` subrequests. In RHOAI 3.x the platform operator (rhods-operator) deploys kube-auth-proxy behind the `data-science-gateway` Gateway and calls it from Envoy through ext_authz EnvoyFilters (see `rhoai-ingress-patterns.md`). The manifests that do this live in the operator, not in this repo.

Beyond the upstream feature set, the RHOAI fork adds:

- optional Kubernetes `TokenReview` validation of `Authorization: Bearer` tokens, so CLIs and SDKs (`oc whoami -t`, ServiceAccount tokens) can authenticate without a browser session (`pkg/authentication/k8s/tokenreview.go`, `pkg/middleware/k8s_token_session.go`)
- deletion of the OpenShift `OAuthAccessToken` on sign-out, matching the OCP console (`oauthproxy.go:854`)
- OIDC RP-initiated (front-channel) logout
- configurable TLS curve preferences (`pkg/tls/curves.go`)
- a pluggable "auth deny" handler that returns a structured JSON 401 to MLflow Python clients (`pkg/authdeny/mlflow.go`)

The proxy handles authentication only. It performs no RBAC or SubjectAccessReview authorization; that is left to downstream components such as kube-rbac-proxy (README "Migration from oauth-proxy").

## Architectural Analysis

**Fork lineage defines the shape.** Almost all of the code structure (`oauthproxy.go`, `pkg/middleware`, `pkg/sessions`, `pkg/apis/options` with legacy and alpha config) is inherited from oauth2-proxy. Most behavior therefore matches upstream: the cookie/session model, the `alice` middleware chain, the `gorilla/mux` router, the separate metrics server, the `skip-auth-routes` allow-list, and Redis session storage (standalone, Sentinel, or Cluster). The RHOAI-specific code is concentrated in a few files: `providers/openshift.go`, `pkg/authentication/k8s/`, `pkg/middleware/k8s_token_session.go`, `pkg/authdeny/`, `pkg/tls/curves.go`, and the sign-out additions in `oauthproxy.go`. Reviewers judging RHOAI-specific risk should focus there.

**Request pipeline.** Every request first passes the pre-auth chain: request scope/ID, optional HTTPS redirect, health checks on `/ping` and `/ready`, and request logging (`oauthproxy.go:382`). It is then routed:

- `/robots.txt` is served unauthenticated.
- `{prefix}/auth` runs the session chain. It is registered outside the no-cache subrouter so nginx/Envoy can briefly cache auth decisions.
- `{prefix}/sign_in`, `/start`, `/callback`, and `/static/` run without a session.
- `{prefix}/userinfo` and `/sign_out` load the session first.
- All other paths go through the session chain to `Proxy`, which either forwards upstream or returns a static 200 in ext_authz mode (`oauthproxy.go:342-380`).

The session chain tries, in order: a JWT bearer session (if configured), a Kubernetes TokenReview bearer session (if `EnableK8sTokenValidation`), the stored cookie/Redis session, and basic auth (`oauthproxy.go:425-431`).

**TokenReview validator design.** The validator deduplicates concurrent reviews of the same token with a hand-rolled singleflight. It caches successful reviews for `KubeAPICacheTTL` (default 10s), keyed by the SHA-256 of the token so raw tokens are never map keys. Each review has a 30s timeout, and client-go QPS/Burst are configurable (`tokenreview.go:63-208`). Sessions built from TokenReview get the synthetic email `<username>@cluster.local` and a 30-second expiry (`tokenreview.go:239-246`). The in-code comment notes a known limitation: client-go does not reload the cluster CA after CA rotation, so pods must restart (`tokenreview.go:81-83`).

**OpenShift provider.** The provider reads the pod's ServiceAccount namespace, token, and CA (`/var/run/secrets/kubernetes.io/serviceaccount/*`). It discovers OAuth endpoints from `https://kubernetes.default.svc/.well-known/oauth-authorization-server`. It can run as a ServiceAccount OAuth client (`system:serviceaccount:<ns>:<sa>`), and it looks up identity at `/apis/user.openshift.io/v1/users/~` (`providers/openshift.go:36-45, 553, 638`). On sign-out it issues `DELETE /apis/oauth.openshift.io/v1/oauthaccesstokens/<name>`, hashing `sha256~` tokens into the object name (`oauthproxy.go:854-912`).

**Risks and observations.**

- *Configurable TLS weakening.* `--ssl-insecure-skip-verify` and `--ssl-upstream-insecure-skip-verify` disable certificate checks for IdP and upstream traffic (`pkg/validation/options.go:33-35`, `pkg/upstream/http.go:151-154`). Redis `InsecureSkipTLSVerify` does the same for Redis (`redis_store.go:184-190`). The server cipher parser accepts names from `tls.InsecureCipherSuites()` (`pkg/http/server.go:150`). The secure defaults are TLS 1.2 minimum and Go default ciphers, but an operator-supplied flag can override them.
- *Cookie encryption mode.* Session-cookie and CSRF-cookie payloads are encrypted with AES-CFB (`pkg/sessions/cookie/session_store.go:159`, `pkg/cookies/csrf.go:319`) and integrity-protected by an HMAC-SHA256 signature (`pkg/encryption/utils.go:75-121`). Redis session tickets use AES-GCM (`pkg/sessions/persistence/ticket.go:252`). AES-CFB is FIPS-approved (SP 800-38A), but it is unauthenticated on its own and Go has deprecated it (hence the `//nolint:staticcheck`).
- *Legacy SHA-1 htpasswd.* `pkg/authentication/basic/htpasswd.go:163` supports `{SHA}` htpasswd entries using SHA-1. This only applies if `--htpasswd-file` is configured, which is not part of the RHOAI deployment pattern.
- *Default bind address.* The default `--http-address` is `127.0.0.1:4180` (`legacy_options.go:15`). Deployments must explicitly set `0.0.0.0:4180` (or an HTTPS address) for the Service to reach it.
- *Repository examples are not production manifests.* `examples/openshift/*` and `examples/oidc/*` are sample deployments in `default` with an `http-echo` backend. The analyzer's Services and Route come from these files. The real RHOAI deployment (ports, TLS, Gateway/EnvoyFilter wiring) is owned by rhods-operator.
- *Stale design doc.* `DESIGN.md` still lists FIPS Dockerfiles and dual-org sync as pending, but both exist on this branch (`Dockerfile.redhat`, `Dockerfile.konflux`, `.github/workflows/fips-compliance.yml`).
