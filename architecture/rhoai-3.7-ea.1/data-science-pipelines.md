## Purpose

**Short**: The Red Hat downstream of Kubeflow Pipelines v2. It supplies the pipeline API server, the run persistence agent, the scheduled-workflow controller, and the v2 driver/launcher binaries that run ML pipelines on Argo Workflows inside RHOAI.

**Detailed**: data-science-pipelines (DSP) is the RHOAI build of Kubeflow Pipelines (KFP) 2.16.x. It comes from `kubeflow/pipelines` through `opendatahub-io/data-science-pipelines`. On the `rhoai-3.7-ea.1` branch, Konflux builds five container images from this repo: the **API server** (`odh-ml-pipelines-api-server-v2`), the **persistence agent**, the **ScheduledWorkflow controller**, the v2 **driver**, and the v2 **launcher**. The API server stores pipelines, pipeline versions, experiments, runs and recurring runs. It exposes them over gRPC (8887) and over REST through grpc-gateway (8888). It compiles pipeline IR (PipelineSpec) into Argo `Workflow` objects. It keeps run metadata in MySQL or PostgreSQL and artifacts in S3-compatible object storage.

At run time, Argo Workflows (a separate RHOAI component) schedules the compiled workflow. Each pipeline task runs the **driver**, which resolves inputs, caching and Kubernetes task config, and records executions in ML Metadata (MLMD). The task pod then runs the **launcher**, which wraps the user container, moves artifacts to and from object storage, and publishes outputs and logs. The **persistence agent** watches Argo Workflows and ScheduledWorkflows and reports their state to the API server's ReportService. The **ScheduledWorkflow controller** reconciles `kubeflow.org/v1beta1 ScheduledWorkflow` CRs into periodic or cron runs.

In RHOAI, DSPO deploys these images into each user Data Science Project namespace, together with MariaDB/external DB, MLMD gRPC/Envoy, object storage and an auth proxy. That makes DSP a per-namespace, single-tenant-per-instance service. The `manifests/kustomize` tree here is the upstream KFP standalone and multi-user packaging. It documents the default topology and RBAC, but RHOAI does not consume it directly. Newer capabilities on this branch include Kubernetes-native pipeline storage (`Pipeline`/`PipelineVersion` CRDs with validating and mutating admission webhooks) and an MLflow plugin that creates MLflow experiments and runs for KFP runs.

## Architectural Analysis

**Control plane and data plane split.** The long-running control plane is small: one API server deployment plus two lightweight controllers (persistence agent and ScheduledWorkflow). The data plane runs inside user pods. The driver and launcher run with the namespace's `pipeline-runner` service account and call back into the API server (gRPC 8887) and MLMD (gRPC 8080). They also go straight to object storage with S3 credentials. Pipeline execution therefore spreads trust widely. Every task pod holds object-store credentials and network access to the API server and MLMD. The `pipeline-runner` Role is very broad (`*` on pods, pods/exec, PVCs, services, deployments, jobs and all `kubeflow.org` resources; `manifests/kustomize/base/pipeline/pipeline-runner-role.yaml`). Within a namespace it can do almost anything to workloads.

**Two storage modes for pipelines.** By default, pipelines and pipeline versions live in the SQL database. When `--pipelinesStoreKubernetes` is set, they are stored as `pipelines.kubeflow.org/v2beta1` `Pipeline`/`PipelineVersion` CRs. The API server then also starts an admission webhook server on 8443 (`backend/src/apiserver/main.go:86-88, 540-580`). The validating webhook parses the PipelineSpec, checks the pipeline name, and keeps the spec immutable after creation: only `displayName` and `tags` may change. The mutating webhook adds `pipelines.kubeflow.org/pipeline-id` and `pipelines.kubeflow.org/pipeline` labels and an owner reference to the parent `Pipeline` (`backend/src/apiserver/webhook/pipelineversion_webhook.go:86-204`). Both webhooks use `failurePolicy: Fail`. An unavailable API server pod therefore blocks PipelineVersion CR writes.

**Authentication is pluggable and conditional.** Authorization only runs when `MULTIUSER=true`. Otherwise `ResourceManager.IsAuthorized` returns nil for every request (`backend/src/apiserver/resource/resource_manager.go:2330-2334`). In multi-user mode, identity comes from one of two authenticators, tried in order (`backend/src/apiserver/auth/auth.go`):

- A trusted header (`KUBEFLOW_USERID_HEADER`, which defaults to the Google IAP header). This assumes an upstream proxy strips and re-sets the header.
- A Bearer token validated with a `TokenReview` against audience `pipelines.kubeflow.org`.

Authorization is a Kubernetes `SubjectAccessReview` on synthetic `pipelines.kubeflow.org` resources (for example `runs` with verbs `readArtifact` and `reportMetrics`, or `workflows` with verb `report`). `MULTIUSER_SHARED_READ` lets anyone get and list. Under DSPO each namespace gets its own instance, and an auth proxy in front of the API server and UI handles authentication. Whether `MULTIUSER` is enabled depends on DSPO configuration, which this repo does not show.

**TLS is opt-in and uses Go defaults.** The API server enables TLS on gRPC and REST only when both `--tlsCertPath` and `--tlsCertKeyPath` are set. `initCerts` builds a `tls.Config` with only `ServerName` and `Certificates` set, so no MinVersion and no cipher list (`backend/src/apiserver/main.go:106-126`). The webhook server logs a warning and serves plain HTTP when it finds no cert (`main.go:566-572`). In-cluster clients (driver, launcher, persistence agent) have matching `*_tls_enabled` and `ca_cert_path` flags. DSPO supplies the service-serving certificates.

**FIPS posture moved to the native Go FIPS 140-3 module.** All Konflux builds compile with `GOFIPS140=v1.0.0 -tags no_openssl`. That selects the Go Cryptographic Module v1.0.0 instead of the older `strictfipsruntime`/OpenSSL (CGO) approach. Only the API server builds with `CGO_ENABLED=1`. The driver, launcher, persistence agent and ScheduledWorkflow controller build with `CGO_ENABLED=0`, and the launcher passes `-extldflags "-static"` explicitly. The traditional check-payload rules require dynamic linking and OpenSSL, so these four statically linked binaries conflict with them. They either rely on a check-payload exception or policy update for Go native FIPS, or they would fail the gate. The repo does not show which.

**MLflow integration crosses a new trust boundary.** The API server's MLflow plugin (`backend/src/apiserver/plugins/mlflow/`, `backend/src/common/plugins/mlflow/`) has two jobs. It creates MLflow experiments and parent runs; the API server Role grants `mlflow.kubeflow.org/experiments` create/get/list/update. It also injects `MLFLOW_TRACKING_*` environment variables into task pods from a namespace secret `kfp-mlflow-credentials`, and the API server's secret access is limited to that name via `resourceNames`. Its HTTP client honors a configurable `insecureSkipVerify` and an optional CA bundle (`backend/src/common/plugins/mlflow/config.go:213-235`). Driver and launcher receive only the `InsecureSkipVerify` flag.

**Upstream baggage.** The repo still carries the KFP v1 components: cache server/deployer, viewer CRD controller, visualization server (Python), metadata-writer, frontend, and AWS/GCP/KServe component images. RHOAI does not build any of them in Konflux. Even the upstream OpenShift kustomize env patches several of them out (`manifests/kustomize/env/openshift/base/kustomization.yaml`). Treat analyzer rows for them as upstream inventory, not RHOAI runtime surface.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | SAR per request in MULTIUSER mode; per-namespace instance + auth proxy in RHOAI | Application + Kubernetes RBAC | Authz is fully skipped when `MULTIUSER=false`, so any caller that reaches the Service can use the API. The trusted-header authenticator needs a proxy that strips spoofed headers |
| Data storage | Separate DB and bucket per DSPA (RHOAI); shared DB with namespace columns in upstream multi-user | Deployment topology / Application query filters | Upstream multi-user mode depends on application-level namespace filtering |
| Network traffic | No NetworkPolicy in base manifests (seaweedfs only); DSPO adds policies in RHOAI | Kubernetes (DSPO) | Upstream API server 8887/8888 is reachable cluster-wide without DSPO policies |
| Compute & resources | Task pods run in the user namespace and inherit namespace quotas | Kubernetes | `pipeline-runner` has `*` on pods/deployments/jobs in its namespace |
| Configuration & secrets | Per-namespace Secrets (DB, object store, `kfp-mlflow-credentials`) | Kubernetes | Every task pod gets object-store credentials, so any task can read any run's artifacts in that namespace |
| API scoping | Persistence agent/scheduledworkflow `--namespace` flag (empty = all namespaces) | Application | Empty namespace makes controllers watch cluster-wide (upstream default); DSPO scopes them per namespace |
