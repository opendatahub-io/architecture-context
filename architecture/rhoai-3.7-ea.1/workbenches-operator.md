## Purpose

**Short**: A standalone module operator that reconciles the cluster-scoped singleton `Workbenches` CR and deploys the notebook (workbench) controller stack, while serving mutating admission webhooks for Kubeflow `Notebook` CRs.

**Detailed**: workbenches-operator is the module operator for the RHOAI/ODH **Workbenches** component. It is part of the platform's modular operator model: the platform orchestrator (opendatahub-operator / rhods-operator) renders this operator's Helm chart, creates the `Workbenches` CR named `default-workbenches`, and fills in fields such as `platform`, `gatewayDomain`, `ingresses`, and `mlflowEnabled` from platform configuration (GatewayConfig, the DSC MLflow component). The operator does not decide how the platform is set up. It turns that projected configuration into running operands.

When the CR is `Managed`, the operator copies the Kustomize bundles baked into the image at `/opt/manifests` to a temporary directory. It overlays `RELATED_IMAGE_*` environment variables onto `params.env` image keys, merges CR-derived parameters (`section-title`, `mlflow-enabled`, `gateway-url`), renders with the krusty engine, and applies the results with Server-Side Apply (field manager `workbenches-operator`). The operands are the Kubeflow notebook controller (OpenShift overlay), the ODH notebook controller (ODH or RHOAI overlay), and the notebook image manifests (ImageStreams, ODH or RHOAI variant). When `spec.workbenchesV2.managementState` is `Managed`, it also deploys the Workbenches v2 `workspaces-controller` (gateway overlay) and `WorkspaceKind` resources. Status follows the platform ModuleStatus model (`Pending/Initializing/Ready/Upgrading/Degraded/Failed`) and records `status.releases` from upstream `component_metadata.yaml`. A finalizer (`components.platform.opendatahub.io/workbenches-cleanup`) deletes labelled operands on `Removed` or on CR deletion.

The same binary also runs a webhook server on port 9443 with two mutating webhooks on `kubeflow.org/v1` `Notebook` objects. One injects data-connection secrets referenced by the `opendatahub.io/connections` annotation and checks the requesting user's access with a SubjectAccessReview. The other applies HardwareProfile settings (resources, node selectors, tolerations, Kueue queue label, DRA resource claims) referenced by the `opendatahub.io/hardware-profile-*` annotations. The operator provisions the webhook serving certificates itself, preferring OpenShift service-CA, then cert-manager. If neither is present, webhooks are disabled.

## Architectural Analysis

**Thin orchestration over committed upstream manifests.** The operator holds very little operand knowledge in Go. Operand definitions are upstream Kustomize trees from `red-hat-data-services/kubeflow`, `red-hat-data-services/notebooks`, and `red-hat-data-services/workbenches`. They are fetched by `get_all_manifests.sh`, committed under `opt/manifests/`, and copied into the image (`Dockerfile.konflux:23`), which allows hermetic and disconnected Konflux builds. The Go code selects overlay paths by platform (`internal/controller/manifests.go:67-95`), injects images and parameters, adds component labels (`app.opendatahub.io/workbenches=true`, `app.kubernetes.io/part-of=workbenches`) to metadata and to Deployment/Service selectors, and runs SSA. The trade-off is that operand behavior (RBAC, NetworkPolicies, webhooks, CRDs of the notebook controllers) is defined in separate repositories, and changes there reach the cluster without passing through this repo's Go review. The bundled tree carries further webhooks of its own, for example the `notebooks.kubeflow.org` conversion webhook (`/convert`) declared in `opt/manifests/workbenches/kf-notebook-controller/crd/patches/webhook_in_notebooks.yaml:4`. Those are served by the operand controllers, not by this operator.

**Branch pinning risk.** On this `rhoai-3.7-ea.1` branch, `opt/manifest-sources.sh` pins the RHOAI operand manifests to `rhoai-3.6` refs of `red-hat-data-services/kubeflow`, `notebooks`, and `workbenches`. The README says downstream release branches are refreshed by a separate rhods-devops-infra job. Until that job runs, the 3.7-ea.1 operator ships 3.6 operand manifests. Architects should confirm the committed `opt/manifests/` content matches the intended release.

**Broad but bounded privilege.** Because it applies arbitrary upstream manifests, the manager ClusterRole has full CRUD on ClusterRoles/ClusterRoleBindings/Roles/RoleBindings, webhook configurations, CRDs (no delete), Deployments, Secrets, and NetworkPolicies cluster-wide. The `bind`/`escalate` verbs are deliberately split into a hand-maintained ClusterRole (`config/rbac/rbac_escalate_role.yaml`) restricted by `resourceNames` to the operand ClusterRoles (notebook-controller-*, odh-notebook-controller-*, workspaces-*). This limits privilege escalation to known role names. The cost is that the role must be updated by hand when upstream renames ClusterRoles. The analyzer table does not capture this `resourceNames` restriction.

**Secure-by-default TLS that follows the cluster profile.** At startup the operator reads the OpenShift `APIServer` TLS security profile and adherence policy (`internal/tlsconfig/tlsconfig.go:193`). It applies that profile to both the metrics server (8443) and the webhook server (9443). It filters cipher suites to those Go can negotiate and refuses to start if the profile is unusable or the adherence policy cannot be read (`cmd/main.go:127-130`). On non-OpenShift clusters it falls back to TLS 1.2 minimum with the Mozilla Intermediate ECDHE/AEAD suites. A `SecurityProfileWatcher` cancels the manager context when the profile changes so the pod restarts with the new settings (`cmd/main.go:307-329`). HTTP/2 is off by default (`--enable-http2=false`), which mitigates the HTTP/2 rapid-reset class of attacks.

**Self-provisioned webhook PKI.** `internal/webhook/tls` detects the provider by API group: `route.openshift.io`/`security.openshift.io` means OpenShift, then `cert-manager.io`, otherwise none. The operator then annotates the webhook Service and MutatingWebhookConfiguration (service-CA), or creates a self-signed `ClusterIssuer` and a `Certificate` (cert-manager). With no provider it **deletes** its own MutatingWebhookConfiguration so that `failurePolicy: Fail` webhooks never point at a server that is not listening. A background ensurer re-applies this every 30s (`internal/webhook/tls/ensurer.go:160`). Both webhooks use `failurePolicy: Fail` and a 5s timeout, so operator unavailability blocks Notebook CREATE/UPDATE cluster-wide. With `replicas: 1` and leader election disabled by default in the Helm chart, this is a single point of failure for workbench creation.

**Confused-deputy protection in connection injection.** The connection webhook reads Secrets in any namespace with the operator's own identity. Before injecting a Secret as `envFrom`, it issues a `SubjectAccessReview` for the *requesting user* (`internal/webhook/notebook/mutating.go:350-368`). This stops a user from mounting Secrets they cannot `get` into their own notebook. The annotation value is capped at 4096 bytes (`mutating.go:50`).

**Scoped caching.** The ConfigMap informer cache is limited to the resolved applications namespace, or to both `opendatahub` and `redhat-ods-applications` when it is unset (`cmd/main.go:168-185`). Deployment and owned-resource watches stay cluster-scoped, and a mapper filters them. ImageStream watches are filtered to managed `part-of` labels so that unrelated churn does not trigger reconciles.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Per-user SubjectAccessReview before cross-referencing Secrets; shared operator SA with cluster-wide Secret read | Application + Kubernetes | Operator SA can read all Secrets cluster-wide. Isolation for connection injection depends on the SAR check being correct |
| Data storage | None owned by operator | N/A | N/A |
| Network traffic | NetworkPolicy on operator pod; operand NetworkPolicies from upstream manifests | Kubernetes | Egress allow-all; webhook port open to any peer |
| Compute & resources | HardwareProfile/Kueue label injection on Notebooks | Application (webhook) + Kueue | HardwareProfile namespace taken from annotation, so users may reference profiles in other namespaces, subject only to the operator's `get` access |
| Configuration & secrets | Connection Secrets referenced by namespace/name; SAR-gated | Application | See Auth row |
| API scoping | ConfigMap cache namespaced to apps NS; Deployment/owned watches cluster-wide | Kubernetes (cache) | Cluster-wide informers for several kinds |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Webhook server (single pod) | Notebook namespace / requesting user | Per-request SAR; `failurePolicy: Fail` means an outage affects all tenants |
| Notebook controllers (operands) | Namespace | Upstream operand RBAC/NetworkPolicies |
