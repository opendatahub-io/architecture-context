## Purpose

**Short**: Python SDK that lets data scientists create, manage, and submit jobs to KubeRay `RayCluster` and `RayJob` resources (optionally queued through Kueue) from notebooks or scripts.

**Detailed**: The CodeFlare SDK is a client-side library. It runs only in the user's process, usually a Jupyter workbench in RHOAI, and has no controller, service, or CRD of its own. Users build a `Codeflare` facade (`src/codeflare_sdk/codeflare.py`) from an `SDKConfig` that holds a kube-authkit `AuthConfig` and a default namespace. The facade gives access to `cf.clusters` and `cf.jobs`. These turn a `ClusterConfiguration` (head/worker resources, accelerators, heterogeneous worker groups, volumes, image, labels, Kueue local queue) into `ray.io/v1` `RayCluster` or `RayJob` custom resources and apply them to the Kubernetes API server with the user's credentials. The KubeRay operator, shipped by RHOAI as a separate component, reconciles those resources.

After a cluster is applied, the SDK finds the Ray dashboard URL. On RHOAI 3.x it looks for a Gateway API `HTTPRoute` labelled for the cluster. It falls back to OpenShift `Route`s and then Kubernetes `Ingress`. It talks to the dashboard over HTTPS with Ray's `JobSubmissionClient`, sending the user's bearer token, to submit, list, inspect and stop jobs. For direct Ray client (`ray://...:10001`) connections it creates client mTLS material locally: it reads the cluster CA secret that KubeRay/RHOAI creates and signs a short-lived client certificate.

It also includes Kueue integration (default LocalQueue lookup, priority classes, elastic/autoscaling compatibility checks against Red Hat Build of Kueue and the RHOAI `DataScienceCluster`), ipywidgets UI helpers for notebooks, demo notebooks, and a standalone RHOAI 2.x → 3.x RayCluster migration script. It reaches RHOAI through PyPI releases. The `odh-notebooks-sync.yml` workflow opens PRs that bump the SDK version pinned in the ODH workbench images.

## Architectural Analysis

**A thin client over CRDs.** codeflare-sdk is a convenience layer that builds and submits Kubernetes resources. The facade (`codeflare.py`), the RayCluster spec builder (`ray/cluster/build_ray_cluster.py`, `ray/cluster/raycluster_spec.py`) and the RayJob builder (`ray/rayjobs/rayjob.py`) generate `ray.io/v1` objects. These go out through the `kubernetes` Python client's `CustomObjectsApi` or the `DynamicClient`, using server-side apply in `Cluster.apply()`. The SDK has no server, port or Service. It acts entirely as the calling user, so its permissions are whatever the user's token allows in the target namespace. This makes the SDK's security posture identical to the user's RBAC. That is the right model for a multi-tenant data science platform, and it means the SDK adds no privilege of its own. The analyzer's "HTTP endpoint" (`builtins.print PATCH`) and the `codeflare-sdk` "Service" both come from a unit test file (`test_kube_api_helpers.py:62`) and are false positives. The `minio` Deployment and the RBAC manifests are e2e and test-image fixtures, not shipped artifacts.

**Vendored KubeRay client.** `src/codeflare_sdk/vendored/` holds a copy of the upstream KubeRay `python_client` (cluster/job APIs plus a builder/director). Tests and examples are excluded from the wheel (`pyproject.toml:12-18`). Vendoring decouples the SDK from KubeRay client releases, but a KubeRay API change has to be pulled in by hand.

**Multiple ways to find the dashboard.** `_get_dashboard_url_from_httproute` (`ray/cluster/cluster.py:1639-1796`) records how the RHOAI ingress model has changed. RHOAI 3.x exposes Ray dashboards through the platform data-science Gateway at `https://{host}/ray/{namespace}/{cluster}`. The SDK first lists `HTTPRoute`s cluster-wide by label. If that is forbidden, it probes a hard-coded list of namespaces (the cluster's own, `redhat-ods-applications`, `opendatahub`, `default`, `ray-system`). It resolves the hostname from the Gateway listener, then an OpenShift Route that fronts the Gateway, then the ODH `GatewayConfig` CR (`services.platform.opendatahub.io`, default subdomain `data-science-gateway`), then the Gateway status address. Only after all of that does it fall back to per-cluster `ray-dashboard-<name>` Routes or Ingresses (the RHOAI 2.x model). The SDK sets `enableIngress: False` on the RayCluster head (`build_ray_cluster.py:108`), so exposure is left to the platform (KubeRay + RHOAI networking). The hard-coded namespace list and the dependency on read access to platform-owned CRs (`GatewayConfig`, `DataScienceCluster`, `OperatorCondition`) are a coupling risk: lookups quietly degrade when users lack those permissions.

**The client holds the cluster CA private key.** `generate_tls_cert` (`common/utils/generate_cert.py:202-380`) reads the `<cluster>-ca-secret-*` Secret (label `ray.openshift.ai/cluster-name`), including the CA private key (`tls.key`/`ca.key`). It then mints an RSA-3072, SHA-256 client/server certificate in the user's process and writes it under `~/.local/share/codeflare/tls/<cluster>-<namespace>/` with 0600 permissions. This works and the files are protected, but it means any user who can read Secrets in the namespace can mint certificates trusted by that Ray cluster. The trust boundary is therefore namespace Secret-read RBAC, not a dedicated identity. Certificates are not rotated automatically. `refresh_certificates()` and `force_regenerate` exist for CA rotation. The cert directory key leaves out the API server, which can cause cross-cluster collisions (the code documents this).

**TLS verification depends on the platform.** `Cluster._client_verify_tls` returns `_is_openshift_cluster() and config.verify_tls` (`cluster.py:146-147`). On non-OpenShift clusters the dashboard `JobSubmissionClient` is built with no auth headers and Ray's default verification (`cluster.py:163-165`). The Kubernetes API client always forces `verify_ssl = True` and picks up a workbench CA bundle at `/etc/pki/tls/custom-certs/ca-bundle.crt` or `CF_SDK_CA_CERT_PATH` (`auth.py:77, 159-188`). The restored deprecated `TokenAuthentication(skip_tls=True)` path turns off certificate verification and silences urllib3 warnings (`deprecated_auth.py:156-167`). This is a user-chosen opt-out, but it is still in the public API with no removal date.

**RayJob file shipping.** When local files are given in a RayJob runtime env, the SDK zips them into an Opaque Secret owned by the `RayJob` (ownerReference, `controller=true`) and mounts it into the `submitterPodTemplate` (`ray/rayjobs/runtime_env.py:340-405`, `rayjob.py:458-520`). Kubernetes garbage collection handles cleanup. Users should know that code and data travel through Secrets, which have size limits enforced by `validate_secret_size`.

**Supply chain and packaging.** The repo has no Konflux Dockerfile, so RHOAI does not build a container image from it. The only Dockerfiles are a test-runner image (`images/tests/Dockerfile`, Debian `python:3.12-slim` with Google Chrome and `oc` fetched at build time) and a pre-commit toolchain (`.github/build/Containerfile`). Neither ships as a product. The AIPCC base-image requirement therefore does not apply to this repo, but it does apply to the workbench images that pip-install `codeflare-sdk`. The default Ray runtime images are digest-pinned `quay.io/modh/ray` images (`common/utils/constants.py:7-8`), and `ray==2.58.0` is pinned so client and cluster versions match.

**Note on invocation arguments:** the pipeline passed `--component-name=claude-opus-5-5`. That looks like a pipeline argument error, so this document uses the repository and package name `codeflare-sdk`.
