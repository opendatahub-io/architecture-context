## Purpose

**Short**: Models-as-a-Service (MaaS) is a governance layer for model serving. It exposes LLM endpoints (KServe LLMInferenceService and external providers) through a shared Gateway API gateway and adds API-key management, subscriptions, per-tenant token rate limiting, and usage telemetry, all enforced through Kuadrant/RHCL policies.

**Detailed**: MaaS is a Go monorepo with three deployables and a shared module (`maas-common`). **maas-controller** is a controller-runtime operator. It reconciles the `maas.opendatahub.io/v1alpha1` APIs: MaaSModelRef, MaaSAuthPolicy, MaaSSubscription, ExternalModel, AITenant, Tenant/MaasTenantConfig, and the cluster-scoped Config anchor. From these it generates platform resources: Kuadrant `AuthPolicy`, `TokenRateLimitPolicy`, `RateLimitPolicy` and `TelemetryPolicy`, Gateway API `HTTPRoute`s, Istio `DestinationRule`/`ServiceEntry`/`EnvoyFilter`/`Telemetry`, llm-d `InferenceObjective`, NetworkPolicies, and observability resources (OpenTelemetryCollector, Perses dashboards, Loki wiring). The controller image bundles the kustomize manifests for maas-api, the gateway policies, payload-processing and maas-discovery. A `TenantReconciler` renders and server-side-applies these manifests, so the controller deploys its own data-plane services.

**maas-api** is a gin HTTP service with a PostgreSQL backend. It implements the user-facing MaaS REST API: model listing filtered by entitlement, subscriptions, `/v1/me`, API key lifecycle, and an org-scoped Loki log proxy. It also implements the internal callbacks Authorino calls during request authorization: API key validation and subscription selection. API keys use the format `sk-oai-{id}_{secret}` and only SHA-256 hashes are stored. **maas-discovery** is an optional TokenReview-authenticated service that returns tenant and gateway metadata (`GET /v1/tenants`). The controller's LifecycleReconciler deploys it only when `maas-discovery-enabled=true`.

In RHOAI, maas-controller is deployed by the RHOAI operator (DataScienceCluster `modelsAsService` component) into the applications namespace. Inference traffic enters through the shared `maas-default-gateway` (in `openshift-ingress`, gatewayClass `openshift-default`). Authorino authenticates each request with an API key or a Kubernetes TokenReview/OIDC token and calls maas-api to validate keys and select subscriptions. Limitador enforces token quotas. The payload-processing ext_proc filters (an operand image from a separate repo) handle body-based routing and API translation before traffic reaches KServe or external model backends.

## Architectural Analysis

**Controller as meta-operator.** maas-controller does more than reconcile its own CRs. It translates a small, opinionated API surface (subscriptions, auth policies, model references) into a large set of third-party CRs owned by Kuadrant, Istio, Gateway API, llm-d, the OpenTelemetry operator and Perses. It also deploys its own data plane by rendering kustomize trees embedded in its image (`maas-controller/Dockerfile.konflux:25-30`) and applying them with SSA (`maas-controller/pkg/platform/tenantreconcile/pipeline.go`). This keeps operator-level orchestration in the RHOAI operator thin, but it concentrates privilege in maas-controller. Its ClusterRole can create and delete `clusterroles`, `clusterrolebindings`, `roles` and `rolebindings`, read Secrets cluster-wide, create namespaces, and manage EnvoyFilters and NetworkPolicies. Compromising the controller is close to compromising the gateway data plane. The cluster-scoped `Config` CR is the ownerReference anchor, so deleting it garbage-collects the entire operand graph.

**Gateway-centric security model with trusted headers.** maas-api does not authenticate end-user inference traffic itself. Authorino (via the generated AuthPolicy) authenticates, then injects `X-MaaS-Username`, `X-MaaS-Group`, `X-MaaS-Subscription` and a verified identity envelope, which maas-api trusts. Several layers protect that trust. The AuthPolicy denies requests that already carry `x-maas-*` headers. `RejectTrustedIdentityHeaders` middleware guards direct-call endpoints. NetworkPolicies restrict maas-api ingress to gateway pods, Authorino pods, the controller/dashboard pods and cleanup pods. The identity envelope parser is defensively bounded (`maas-api/internal/token/identity.go`: 16KB, depth 6, duplicate-key rejection). The design holds only as long as every one of these layers stays in place. In particular, the internal callbacks `/internal/v1/api-keys/validate` and `/internal/v1/subscriptions/select` have no caller authentication and rely entirely on NetworkPolicy. Because the API-key validate endpoint is a hash-lookup oracle, a weakened NetworkPolicy (for example, a custom CNI without enforcement) would expose it in-cluster. Authorino strips the `Authorization` header before forwarding to model backends, so the platform's API keys never leak to upstream providers.

**Known transport-security compromises.** The gateway-to-maas-api hop uses an Istio `DestinationRule` with `tls.mode: SIMPLE` and `insecureSkipVerify: true` (`deployment/base/networking/maas/destination-rule.yaml`, TODO RHOAIENG-61070, because BackendTLSPolicy is unavailable before OpenShift 4.22). The payload-processing DestinationRule does the same. Traffic is encrypted, but the server identity is not verified on that hop. The base `maas-api-cleanup` CronJob also calls `http://maas-api:8080`, which the TLS overlay used by the Tenant reconciler patches to HTTPS 8443. The base manifests are therefore not secure-by-default on their own.

**Default egress is permissive.** The controller manages a NetworkPolicy named `maas-api-egress-restrict`, but unless the operator supplies explicit `networkPolicyEgressRules` in `Config`, the reconciler appends an allow-all `{}` egress rule (`maas-controller/pkg/platform/tenantreconcile/params.go:799-827`). In practice maas-api egress is unrestricted by default, despite the policy name.

**Fail-open vs fail-closed ext_proc.** The payload-processing EnvoyFilter inserts two ext_proc filters around the Kuadrant wasm plugin. `ipp-pre` runs before auth with `failure_mode_allow: true` and `ipp` runs after auth with `failure_mode_allow: false`. The pre-auth stage can therefore be bypassed if it fails, while the post-auth stage (which sees credentials and does translation) fails closed. This seems intentional, because the pre-auth stage only shapes requests for routing, but it should be reviewed as part of any change that moves security-relevant logic into it.

**Default-deny gateway.** A `TokenRateLimitPolicy` named `gateway-default-deny` puts a zero limit on every path except the MaaS control endpoints, portal and oauth2. Model traffic is denied unless a MaaSSubscription produces a matching rate-limit policy. This is a good fail-safe posture.

**Multi-tenancy is in transition.** The API surface carries migration debris. `Tenant` is deprecated in favor of `MaasTenantConfig`, with platform context moving to `AITenant`. The legacy `maas.opendatahub.io` ExternalModel is migrated to `inference.opendatahub.io` ExternalModel/ExternalProvider; when the new kind exists, the IPP controller owns networking and legacy children are torn down (`maas-controller/pkg/controller/externalmodel/reconciler.go:155-175`). AITenant names are capped at 41 characters so per-tenant resource names such as `maas-api-auth-policy-<tenant>` fit within 63 characters. Tenant isolation in PostgreSQL is application-enforced: each maas-api instance is constructed with `TENANT_NAME` and scopes queries by it. AITenant revocation spawns Jobs that call maas-api's internal DELETE endpoints with the `maas-api-cleanup` ServiceAccount token, verified by TokenReview.

**Operational observations.** The controller runs 1 replica with leader election (`maas-controller.models-as-a-service.opendatahub.io`). maas-api runs 1 replica with no HPA, so key validation (on the hot path of every inference request through Authorino) depends on a single pod plus Authorino's caching. maas-api restarts itself when the OpenShift APIServer TLS profile changes, which keeps TLS settings consistent across the cluster at the cost of brief restarts. The controller's Self-deployment controller hard-codes the Loki datasource URL against `redhat-ai-gateway-infra` (`self_deployment_controller.go:76`), which couples that path to the RHOAI infra namespace naming.

### FIPS Compliance

FIPS compliance has two layers: **build-time enforcement** (check-payload validation in Konflux) and **application-level crypto correctness** (what the code actually does with cryptography). Both must be documented.

#### Build-Time FIPS (check-payload gate)

Konflux validates images via [check-payload](https://github.com/openshift/check-payload), which enforces:
- Go binaries must be **dynamically linked** (CGO_ENABLED=1, no static linking)
- **OpenSSL must be installed** in the container image
- No statically linked Go crypto (pure-Go crypto / BoringCrypto static gets rejected)

| Aspect | Value | Source |
|--------|-------|--------|
| **Build flags** | `CGO_ENABLED=1`, `GOEXPERIMENT=strictfipsruntime`, `go build -a -trimpath -ldflags="-s -w"` | `maas-api/Dockerfile.konflux:15`; `maas-controller/Dockerfile.konflux:5-6,16`; `maas-discovery/Dockerfile.konflux:5-6,16` |
| **Linking** | Dynamic (CGO) | Same Dockerfiles; builder `registry.access.redhat.com/ubi9/go-toolset@sha256:0e3894ce…` |
| **OpenSSL in image** | Yes (via UBI base `registry.redhat.io/ubi9/ubi-minimal-pqc@sha256:d638f3b4…`) | Runtime stage of all three Dockerfiles |
| **OLM FIPS annotation** | not present (no CSV in this repo; shipped via RHOAI operator bundle) | N/A |
