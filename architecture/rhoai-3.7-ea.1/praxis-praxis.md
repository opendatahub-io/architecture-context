## Purpose

**Short**: Praxis is a Rust framework and ready-to-use binary for building fast, secure-by-default HTTP/TCP proxy servers in which every behavior is a composable filter.

**Detailed**: Praxis ships a single `praxis` binary (crate `praxis-proxy`) that loads a YAML configuration describing named **listeners**, reusable **filter chains**, and upstream **clusters**. At startup, each listener's referenced chains are concatenated into one filter pipeline. Routing, load balancing, rate limiting, header and path rewriting, CORS/CSRF, IP ACLs, guardrails, credential injection, gRPC and JSON-RPC handling, access logging and tracing are all filters that implement the same `HttpFilter`/`TcpFilter` traits as user-written extensions. Protocol handling is handed to Cloudflare's Pingora, used through a Praxis-maintained fork published as `quixotic-plecostomus-*`. An experimental hyper backend can be selected at build time instead.

Praxis can also be used as a library. The `praxis-proxy-core`, `-filter`, `-protocol` and `-tls` crates let downstream binaries compose their own proxies. The README notes that the AI Gateway features (inference routing, LLM policies) live in the separate `praxis-proxy/ai` repository, which builds a `praxis-ai` binary on top of this framework. In RHOAI this repository is the base proxy engine that those AI gateway capabilities sit on. The primary deployment shapes are ingress/API gateway, egress, east/west sidecar, and security gateway.

The repository has no Kubernetes operator, CRDs or kustomize manifests. It produces a container image (`Containerfile` on Alpine and `Containerfile.fips` on UBI 9) configured by a mounted YAML file. A Kubernetes rollout acceptance harness (`tests/rollout`, kind-based) exercises pod loss, rollouts, config reloads and TLS rotation under traffic, but it is test-only.

## Architectural Analysis

**Filter-first pipeline model.** All behavior goes through one abstraction. HTTP filters run request hooks in declared order and response hooks in reverse, and any filter can short-circuit. Body hooks are opt-in through `BodyAccess` declarations. The most recent breaking change requires filters to declare whether body processing is `Optional` or `Required`, so a transport that bypasses body hooks (such as an upgraded connection) can be admitted or refused deterministically. Pipelining (chain concatenation per listener, fixed at load or reload time) is kept separate from routing (the `router` filter choosing a cluster per request). Pipelines are swapped atomically on hot reload (`arc-swap`, `notify` file watcher). Certificates hot-reload too, behind the `config-reload` feature.

**Pluggable network backends behind a contract.** `praxis-core` defines the `ServerRuntime`, egress connector and session traits. `praxis-protocol` adapts backend callbacks into pipeline calls. Exactly one backend is chosen by cargo feature: `pingora` (default) or `hyper` (experimental), and a build with neither refuses to compile. This keeps protocol correctness in upstream libraries, though Pingora is consumed through a fork pinned to v0.11.4. The fork also pins tokio to `~1.53.3` because Pingora 0.11 creates zero-capacity BufStreams that tokio 1.54 rejects (`Cargo.toml` comment). That tokio pin is real dependency debt.

**Cryptography is deliberately single-provider.** rustls is built with `default-features = false` so neither aws-lc-rs nor ring is linked as a provider. `praxis-proxy-tls` installs one OpenSSL-backed rustls provider (`rustls-openssl`, also vendored from the Pingora fork) at bootstrap, and there is no fallback: a missing provider fails startup. Every primitive goes through the system `libcrypto.so`, which on a FIPS-enabled RHEL host is the validated module. `PRAXIS_REQUIRE_FIPS` makes listener and upstream TLS config construction fail if rustls does not report FIPS mode. Extended Master Secret is enforced on TLS 1.2. The analyzer noticed `ring` and `aws-lc-rs` in `Cargo.lock`. That reflects the whole-workspace lock: ring comes in through weak features and test/dev crates. The FIPS build uses `cargo auditable -Zsbom` specifically so the embedded crate manifest lists only what was compiled, and `cargo xtask fips report` checks the result.

**The Policy engine is the main FIPS boundary.** The default feature set includes `policy-builtins`, which pulls in the external `praxis-policy` (PPE 0.6.0) engine with its RustCrypto backend. RustCrypto is not FIPS-validated. The FIPS image (`Containerfile.fips`) builds with `--no-default-features --features pingora,config-reload,admin-api` and leaves Policy out entirely. Separate FIPS profiles (`policy-crypto-fips`, `policy-jwt-fips`, `policy-api-key-fips`) route Policy cryptography through OpenSSL. So the published standard image and the FIPS image have different security features: JWT, API-key and DPoP policies are absent from the default FIPS image.

**Secure-by-default configuration.** Development-only relaxations go under `insecure_options` (`allow_root`, `allow_public_admin`, `allow_unbounded_body`, `allow_tls_without_sni`, `allow_private_health_checks`, `skip_pipeline_validation`), all defaulting to false. Upstream and health-check destinations are screened for SSRF-sensitive ranges (loopback, link-local, cloud metadata). Admin listeners bound to loopback reject non-loopback `Host` headers with 421 to defeat DNS rebinding. The admin API itself has **no authentication**. Its protection depends entirely on loopback binding, and the KV store API (`/api/kv/*`, PUT/DELETE) and `/api/log-level` are mutating endpoints. In Kubernetes, anyone who sets `allow_public_admin` or exposes 9901 opens an unauthenticated control plane.

**Risks / observations.** (1) The fork dependency (`quixotic-plecostomus-*`) carries both the HTTP engine and the TLS provider, so security fixes depend on fork maintenance. (2) There are no Konflux Dockerfiles, `rpms.lock.yaml` or Tekton pipelines on this branch, so downstream productization (image build, hermetic prefetch) must happen elsewhere. (3) The standard `Containerfile` uses Alpine/musl, which is not a FIPS-capable base; only `Containerfile.fips` qualifies for RHOAI. (4) The health/metrics listener (9902) may bind to non-loopback addresses for Kubernetes probes and has no auth, so `/metrics` exposure has to be controlled with NetworkPolicy.
