## Purpose

**Short**: MLServer is a Python inference server that serves classical ML models (scikit-learn, XGBoost, LightGBM, ONNX) over the Open Inference Protocol (KServe V2) using REST and gRPC.

**Detailed**: MLServer is Seldon's open-source inference server, which Red Hat forks and ships in RHOAI as the `odh-mlserver-rhel9` and `odh-mlserver-cuda-rhel9` images. Inside a pod it runs three listeners in one process: a FastAPI/uvicorn REST server on 8080, a `grpc.aio` server on 8081, and a Prometheus metrics server on 8082. The REST and gRPC servers implement the KServe V2 / Open Inference Protocol dataplane (health, metadata, infer, stream infer) and a model repository extension (index, load, unload). Models are loaded from `MLSERVER_MODELS_DIR=/mnt/models`. KServe's storage initializer populates that directory. Each model's `model-settings.json` names the runtime class that handles it, for example `mlserver_sklearn.SKLearnModel`.

The repository holds the core `mlserver` package and ten runtime plugin packages under `runtimes/`. The RHOAI Konflux images install only a subset, as pinned and hashed wheels from the RHEL AI Python package index:
- **CPU image**: `mlserver`, `mlserver-sklearn`, `mlserver-xgboost`, `mlserver-lightgbm`, `mlserver-onnx[cpu]`
- **CUDA image**: `mlserver`, `mlserver-onnx[cuda]`, using the ONNX Runtime CUDA execution provider

The images do not build the source tree directly. They consume wheels that AIPCC builds from this source (`requirements/requirements-cpu.txt:1-14`, `hack/requirements-config.json:7-21`).

In the RHOAI platform, MLServer is one of the predictive model-serving runtimes that KServe can deploy. The ServingRuntime definitions, Services, routing (Gateway API / Routes) and authentication sidecars are created by KServe and the RHOAI operator, not by this repository. The repository contains no Kubernetes manifests.

## Architectural Analysis

**A runtime image, not a controller.** MLServer has no reconcile loop, no CRDs and no RBAC of its own. Its deployable output is two container images, and everything about how it runs on the cluster is decided outside this repo by the KServe ServingRuntime / InferenceService machinery. So the network, auth and multi-tenancy sections below mostly describe what MLServer does *not* enforce, and what it relies on the platform to provide.

**Single process, three listeners, all plaintext.** `mlserver start` starts the REST server (uvicorn, `0.0.0.0:8080`), the gRPC server (`add_insecure_port` on `0.0.0.0:8081`, `mlserver/grpc/server.py:88-90`) and the metrics server (`0.0.0.0:8082`) in one process. Optionally it also starts a Kafka consumer/producer and a parallel inference worker pool. No listener has TLS or authentication code. The gRPC interceptor chain only does access logging, Prometheus metrics and OpenTelemetry tracing (`mlserver/grpc/server.py:41-73`). Transport security and authentication are entirely platform-delegated. In RHOAI 3.x that means the kube-rbac-proxy sidecar KServe injects when token auth is enabled on an InferenceService, plus any service-mesh/Gateway TLS. When auth is not enabled for an InferenceService, the plaintext ports are reachable by anything that can reach the pod network.

**Unauthenticated model management surface.** Two surfaces let callers change server state, and MLServer itself does not authenticate either:
- The model repository API: REST `POST /v2/repository/models/{name}/load|unload` and the gRPC `RepositoryModelLoad`/`RepositoryModelUnload` RPCs, exposed both on `GRPCInferenceService` and on a separate `ModelRepositoryService`.
- `/v2/docs` and the per-model OpenAPI pages.

Any client that gets past the platform auth layer (or reaches the pod directly) can load and unload models from the model repository root. That makes NetworkPolicy and auth-sidecar configuration important for this runtime.

**Downstream hardening: the trusted runtimes allowlist.** The RHOAI fork adds a "runtime security" mode that is not upstream:
- `Dockerfile.konflux:35-52` bakes `/etc/mlserver/trusted-runtimes.json` (mode 0444, directory 0555) at build time. It lists only the runtime classes installed in that image: four for CPU, `mlserver_onnx.OnnxModel` for CUDA.
- When this file exists, the server runs in PRODUCTION mode. `_assert_trusted_runtime_import_path` rejects any `model-settings.json` `implementation` not on the list (`mlserver/settings.py:140-165`). This closes the upstream arbitrary-code-execution path, where a model directory could name any importable Python class or add itself to `sys.path`.
- PRODUCTION mode also forbids wildcard CORS origins and origin regexes (`mlserver/settings.py` `validate_no_wildcard_cors_in_production_mode`).
- The mode is reported through a new `/v2/runtimes` REST endpoint and a `RuntimeSecurity` gRPC RPC added to `proto/dataplane.proto:26`. This makes the RHOAI dataplane proto a strict superset of the KServe V2 proto.
- When the file is absent (the upstream `Dockerfile` / `Dockerfile.cuda`, local development), every implementation is allowed.

**Supply chain posture is strong at the Python layer.**
- Both Konflux builds are `hermetic: true` with a pip Hermeto prefetch.
- Both install with `pip install --no-deps --require-hashes` from fully pinned, hashed requirements files generated by `hack/generate-pinned-requirements.py` against the RHEL AI index (`https://packages.redhat.com/api/pypi/public-rhai/rhoai/3.6/...`).
- Both start from digest-pinned AIPCC base images: `cpu-el9.8:3.6` and `cuda-12.9-el9.8:3.6`.

There are no `rpms.lock.yaml` or `artifacts.lock.yaml` files, but the Dockerfiles install no RPMs, so the OS layer is whatever the AIPCC base ships. Two observations:
- The base images and the package index are on the AIPCC **3.6** channel even though this is the RHOAI 3.7-ea.1 branch.
- `Dockerfile.konflux.cuda:12-13` has a comment that says `el9.9` while the image is `el9.8`. The comment is stale; the build is not affected.

**Observability and outbound connections.**
- Prometheus metrics are served on their own port. In parallel-worker mode they are aggregated through a shared multiprocess directory.
- OpenTelemetry tracing, when `tracing_server` is set, exports over OTLP/gRPC with `insecure=True` hard-coded (`mlserver/tracing.py:22`). Trace export can't use TLS without code changes.
- The optional Kafka server (`kafka_enabled`, default off) uses `aiokafka` with only `bootstrap_servers`: no SASL or SSL options are wired up (`mlserver/kafka/server.py:29-35`).

**Build variants and architectures.**
- CPU image: x86_64, arm64, ppc64le.
- CUDA image: x86_64, arm64.

Both match the AIPCC CPU and CUDA 12.9 base image architecture matrix in overlay 0017. The upstream `Dockerfile` and `Dockerfile.cuda` (multi-stage builds that compile wheels from source) are still in the repo but are not used by Konflux.
