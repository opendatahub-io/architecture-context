## Purpose

**Short**: The AI Grid Network (AGN) operator is a control plane that discovers participating sites and inference/tool providers across clusters, gossips their state over SWIM/CRDT, scores them, and publishes versioned routing overlays that Praxis AI gateways use to route inference requests.

**Detailed**: The AI Grid Network (AGN) is a technical-preview, multi-site inference routing control plane. Each site runs one `grid-operator` that watches five cluster-scoped `grid.praxis.fast/v1alpha1` CRDs: `GridNetwork`, `GridSite`, `InferenceProvider`, `AgentToolProvider` and `SiteInvite`. It records local provider state as delta-CRDT entries and exchanges membership and state with peer site operators over an encrypted SWIM gossip protocol (`foca`, UDP 7946). From its merged local view, the operator applies lifecycle, trust, freshness, placement and access-policy checks, scores candidates (`noMetrics`, `queueDepth`, `kvCachePressure`), and writes a content-addressed routing overlay ConfigMap for each gateway that a `GridNetwork` references.

The operator stays out of the request path. A Praxis AI gateway reads the overlay. Either an `overlay-sync` sidecar delivers it as a file, or the project-owned `grid-gateway` mounts a serving ConfigMap. The gateway then routes each request to a local backend, an external API, or, over gateway-to-gateway mTLS, a remote provider gateway. The operator also serves a per-provider "signals" exporter (`/v1/site/signals`, TCP 9091, mTLS with certificate pinning). Peers and gateways read scraped provider telemetry from it without holding provider credentials. It also manages site trust material: site identity Secrets, the SWIM mesh key reference, and trust bundles.

This repository produces three Konflux images for RHOAI: `odh-praxis-ai-grid-operator` (the controller), `odh-praxis-ai-grid-enrollment` (an optional site-identity bootstrap CA/signer service that issues site certificates against one-time enrollment tokens) and `odh-praxis-ai-grid-gateway` (a Praxis/Pingora-based data-plane gateway in a separate Cargo workspace). The repo also contains Helm charts (`grid-operator`, `grid-enrollment`, `grid-site`, `praxis-gateway`, `grid-mock-providers`), Kustomize manifests generated from the charts, an optional fleet dashboard, mock LLM providers for qualification, and Go API types published as `github.com/praxis-proxy/grid/go`.

## Architectural Analysis

**Control plane vs. data plane split.** AGN deliberately keeps its operator off the request hot path. The README and `docs/architecture/overview.md` describe the boundary as "AGN decides what should be routable; Praxis AI performs the actual request routing." The operator's output is a ConfigMap with two keys: a versioned envelope (`routing-overlay.json`) and a bare payload (`routing-config.json`). The envelope carries a SHA-256 content digest, a semantic revision, and scope binding (network, gateway, namespace, local site). Gateways validate the envelope and keep a last-known-good snapshot. So an unavailable operator degrades freshness, not availability. `GridNetwork.status.routingMapStatus` reports rendered and distributed revisions separately for this reason. Overlays contain credential *references* (Secret name, namespace, key), never token bytes. Credentials stay with the gateway that makes the final backend hop.

**Eventually consistent multi-site state.** Each site is a single SWIM member. Pods, gateways and providers are not SWIM members, so a single-site install is a valid one-node mesh. Provider and site state travel as delta-CRDT broadcasts (`crdt` crate). Every operator renders from its own merged view, so views converge but are never guaranteed to be identical. The default deployment sets `GRID_SWIM_REQUIRE_KEY=true`: all gossip is held until a `GridNetwork` loads the shared AES-256-GCM mesh key (Secret `grid-swim-key`) or declares that none is used. The shared key gives confidentiality, not per-site origin authentication. Per-site ECDSA P-256 signing of state broadcasts exists behind `peerTrust.signedState: enforce`. The README still states that the publication path does not fully wire origin pins (upstream issue praxis-proxy/grid#75). This is the main residual trust gap: any holder of the mesh key can inject state, which is then filtered only by routing-eligibility and access-policy checks.

**Leader-held Service endpoints.** The SWIM (UDP 7946) and signals (TCP 9091) Services are selector-less `LoadBalancer` Services with `externalTrafficPolicy: Local`. The OpenShift overlay adds internal-NLB annotations for AWS, GCP and Azure. The leader replica (Lease `grid-operator`) writes "holder" EndpointSlices (`grid-operator-swim-holder`, `grid-operator-signals-holder`) so that only the leader is reachable by peers. This explains the unusual `endpointslices` and `endpointslices/restricted` RBAC. Two ValidatingAdmissionPolicies (CEL, not webhooks) constrain the operator's own ServiceAccount. It may delete only controller-managed EndpointSlices of its own two Services, and it may never update its operator-config ConfigMap (`grid-operator-config`). This is a defense-in-depth pattern against a compromised operator.

**Gap between FIPS design and shipped Konflux build.** The codebase has a carefully designed opt-in `fips` cargo feature (`docs/fips.md`). It routes TLS, certificate keygen/signing, SWIM AES-GCM/ECDSA, and digest operations through dynamically linked system OpenSSL. FIPS binaries refuse to start unless the OpenSSL default context has `fips=yes`, a SHA-256 KAT passes, and `/proc/sys/crypto/fips_enabled=1` (`grid-fips`, `grid-openssl-fips` crates). However, the RHOAI Konflux Dockerfiles on this branch do not enable that feature:
- The operator builds with default features: `tls-rustls`, i.e. rustls + ring, `swim/rust-crypto` and rcgen.
- Enrollment builds with `--features sar,bootstrap` only.
- The gateway's `CARGO_FEATURES` build arg defaults to empty. Its Dockerfile comment says this "bundles aws-lc and fails check-payload", and the `.tekton/*-push.yaml` PipelineRuns pass no build args.

As a result, the shipped images use statically linked pure-Rust crypto (ring is listed as non-FIPS by the analyzer) despite running on the `ubi9/ubi-minimal-pqc` base. This is the most significant architectural risk for an RHOAI component. It is also internally inconsistent with the Dockerfile comment's claim that "the RHOAI pipelines pass it as a build arg".

**Deployment shape and platform vendoring.** `deploy/operator/` is the platform base. It is generated from `charts/grid-operator` by `scripts/generate-deployment-operator.sh` and carries no Namespace. The image and namespace are parameterized through a `params.env` → ConfigMap → `replacements` chain, the RHOAI vendoring pattern. `deploy/overlays/openshift/` adds a NetworkPolicy, a ServiceMonitor scraped over HTTPS with the OpenShift service CA, and service-ca serving-cert TLS for the metrics listener. Note that the arch-analyzer extracted Services and RBAC from `deploy/overlays/kind/`. That overlay omits the signals Service and uses ClusterIP for SWIM, so the tables below are corrected from the base and OpenShift manifests. The default image in `params.env` is still upstream `ghcr.io/praxis-proxy/grid-operator:v0.3.0`. The platform operator is expected to override it with `quay.io/rhoai/odh-praxis-ai-grid-operator-rhel9`.

**Observability endpoint exposure.** The metrics/health listener (TCP 9090) serves `/metrics`, `/healthz` and `/readyz` with no application-level authentication. A `grid-operator-metrics-scraper` ClusterRole for the `/metrics` non-resource URL exists, but the operator uses it to mint a token (`serviceaccounts/token`) for scraping *gateway* metrics, not to protect its own endpoint. TLS on 9090 is optional and falls back to plaintext when neither cert files nor a site-identity Secret are configured. Both shipped manifests configure TLS, and on OpenShift the NetworkPolicy restricts 9090 to the monitoring namespaces and the Helm test pod.

**Enrollment as a CA.** The enrollment service is the production certificate signer for site identities (`/v1alpha1/enrollments`, `/v1alpha1/rotations`). Grid-admin calls (mint and revoke tokens) need a Bearer token. In RHOAI builds (`sar` feature) the token is checked with a Kubernetes TokenReview plus a SubjectAccessReview against the virtual resource `grid.praxis.fast/enrollmenttokens`. Site enrollment uses one-time tokens, stored only as SHA-256 digests. Renewal uses optional client certificates chained to the Grid CA. Storage is in-memory or Postgres. The Postgres hop enforces `sslmode=verify-full`, and the FIPS guidance requires client-certificate authentication because sqlx's SCRAM/MD5 password auth runs outside the validated module.

**Technical-preview posture.** The CRD API group moved from `grid.praxis-proxy.io` to `grid.praxis.fast` and requires a fresh install. There is no mixed-version gossip compatibility guarantee. `AgentToAgentProvider` is schema-only, with no controller. AGN explicitly disclaims tenant isolation, billing and identity-provider roles.

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Single operator SA. Site-level mTLS and pins for peers. Enrollment uses K8s RBAC via SAR. | Kubernetes / Application | No per-user or per-tenant authorization. Shared SWIM key lets any key holder inject state. |
| Data storage | ConfigMaps and Secrets in the operator namespace. Optional shared Postgres for enrollment. | Kubernetes / Application | Enrollment Postgres may be shared with MaaS |
| Network traffic | NetworkPolicy on the operator pod (OpenShift overlay). Internal LBs for SWIM and signals. | Kubernetes | SWIM and signals ports are open to any source that can reach the LB |
| Compute & resources | None defined (no requests/limits in manifests) | — | No resource requests or limits on the operator Deployment |
| Configuration & secrets | Secret refs only in overlays. Provider credentials stay in the provider gateway namespace. | Application | `secrets get/create/patch` in the operator namespace |
| API scoping | Cluster-wide CRD watches; namespace-limited resource RBAC via RoleBinding | Kubernetes | Cluster-scoped CRDs mean any CRD editor affects the whole site |
