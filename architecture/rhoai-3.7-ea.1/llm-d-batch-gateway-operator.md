## Purpose

**Short**: Kubernetes operator that reconciles a namespaced `LLMBatchGateway` custom resource into a full llm-d Batch Gateway deployment (API server, processor, garbage collector, and async processor) by rendering embedded Helm charts at runtime and applying the results with Server-Side Apply.

**Detailed**: The llm-d Batch Gateway gives RHOAI an OpenAI-compatible Batch and Files API (`/v1/batches`, `/v1/files`). Users submit batch jobs, and the gateway sends the individual inference requests to llm-d inference gateways in the background. This operator manages the gateway's lifecycle. A user creates one `LLMBatchGateway` CR (`batch.llm-d.ai/v1alpha1`, short name `lbg`) in a workload namespace. The CR points to PostgreSQL (job metadata), S3-compatible or PVC file storage, a Redis/Valkey or PostgreSQL async queue transport, and one or more model gateways. The operator turns the CR spec into Helm values (`specToBatchHelmValues`, `specToAsyncHelmValues`) and renders two charts baked into the image: `batch-gateway` (from `opendatahub-io/batch-gateway`) and `llm-d-async` (from `opendatahub-io/llm-d-async`). Each rendered object gets a controller owner reference and is applied with SSA.

Within the platform, this is a third-level operator. opendatahub-operator / rhods-operator deploys ai-gateway-operator when the DataScienceCluster sets `aigateway.batchGateway.managementState: Managed`. ai-gateway-operator then deploys this operator from the `config/base` kustomize path into `redhat-ods-applications`. Users create `LLMBatchGateway` CRs in their own namespaces (docs/odh-installation.md:10-21). Operand container images are pinned by the platform through operator environment variables populated from `params.env`, not by the CR author. This keeps image selection under platform control (internal/controller/helm.go:27-35, cmd/main.go:35-70).

The operator also manages its own observability. A secondary `MetricsController` server-side applies the operator's metrics Service (with a service-ca serving-cert annotation), a ServiceMonitor, and a PrometheusRule with reconcile-error and leader-election-lost alerts in its own namespace. The operator reads the cluster TLS security profile from `config.openshift.io/APIServer`. It applies that profile to its own metrics listener and passes min version, ciphers, and ALPN to the batch-gateway API server through Helm values. If the profile changes, it restarts itself.

## Architectural Analysis

**Helm-as-library reconciliation.** The operator does not hand-code operand manifests. It loads the upstream Helm charts once at startup (`helm.sh/helm/v3` `loader.Load` + `engine.Render`) from `/charts/batch-gateway` and `/charts/llm-d-async`, and renders them in memory on every reconcile (internal/controller/helm.go:43-96). It never creates Helm releases or release Secrets. Helm is only a templating engine, and the operator owns lifecycle through owner references and SSA (field owner `llmbatchgateway-controller`, `ForceOwnership`) (internal/utils/utils.go:14-21). To clean up drift, the operator lists every GVK in `managedGVKs` in the CR namespace and deletes controller-owned objects that the latest render no longer produces (internal/controller/llmbatchgateway_controller.go:90-104, 334-396). As a result, the operator's behavior depends on the chart commit pinned in the Makefile (`BATCH_GATEWAY_REF=0947400…`, `LLM_D_ASYNC_REF=1408854…`) or, for Konflux, the copies in `prefetched-charts/`. Chart drift is an operand-behavior change without any Go code change. `managedGVKs` has to be kept as a manual superset of every kind the chart can emit, or orphan cleanup silently misses resources.

**Optional-CRD tolerance.** HTTPRoute, cert-manager Certificate, ServiceMonitor, PodMonitor, PrometheusRule, and ReferenceGrant are watched only if their CRDs are present at startup (llmbatchgateway_controller.go:565-580, internal/monitoring/controller.go:105-115). During apply and orphan cleanup, `NoMatch`/`NotFound` errors are logged and skipped (llmbatchgateway_controller.go:253-257, 362-366). The operator therefore runs on vanilla Kubernetes ("xKS", where `--metrics-secure=false` is the documented escape hatch) as well as OpenShift. The trade-off: a CRD installed after the operator starts is not watched until the operator restarts. Its resources are still applied on the next periodic resync (`--sync-period`, default 5m).

**Cross-namespace credential copy guarded by ReferenceGrant.** `spec.secretRef` may point to a Secret in another namespace. The operator then requires a Gateway API `ReferenceGrant` in the source namespace that permits `batch.llm-d.ai/LLMBatchGateway` from the CR namespace to reach `Secret` (by name or wildcard). It then copies the Secret's data into `<cr-name>-credentials` in the CR namespace, owned by the CR and annotated `batch.llm-d.ai/copied-from` (internal/controller/secret_sync.go:43-195). The annotation enforces immutability: changing the reference after a copy exists fails permanently with `SecretRefImmutable`. This pattern lets a central team hold database and S3 credentials for many tenant namespaces. It also means the operator's ClusterRole includes cluster-wide `get/list/watch/create/patch` on `secrets`, and the controller starts a cluster-wide Secret informer. A dynamic predicate (`secretWatchFilter`) limits which events trigger reconciles, but the informer still caches every Secret in the cluster in operator memory (GOMEMLIMIT is 200MiB, memory limit 256Mi). The filter also has a `remove` method that is never called, so tracked keys pile up for the life of the process (internal/controller/secret_watch_filter.go:22-26). This does not affect correctness because the map function re-checks live CRs, but it is a small leak.

**Platform-controlled images and TLS posture.** Component images come only from `LLM_D_BATCH_GATEWAY_{APISERVER,PROCESSOR,GC}_IMAGE` and `LLM_D_ASYNC_IMAGE`. All four are required at startup (cmd/main.go:47-70; the log message on line 147 incorrectly says "3 component images"). For the TLS profile, `tlsinit.Resolve` reads the APIServer CR. On non-OpenShift clusters or transient errors it falls back to the Intermediate profile. A `SecurityProfileWatcher` cancels the manager context when the profile or adherence policy changes, so the pod restarts and picks up the new settings (internal/tls/profile.go:132-223). The converted profile is passed to the batch-gateway chart as `apiserver.tls.{minVersion,cipherSuites,nextProtos}`. Only TLS 1.2 and 1.3 minimums are accepted. Cipher names that Go/Batch Gateway does not support are dropped and logged (internal/tls/profile.go:45-127, internal/controller/helm_batch.go:131-155).

**Deployment-surface constraint.** The metrics args/volume patches and the NetworkPolicy live in `config/base` because ai-gateway-operator deploys only from `SourcePath "base"`. Anything placed in the `odh`/`rhoai` overlays never reaches the cluster (config/base/manager_metrics_patch.yaml:1-3). The overlays only change the namespace.

**Risks and observations.**
- The `spec.processor.asyncConfig.tls.insecureSkipVerify` CRD field is passed straight to the async processor, letting any CR author turn off TLS verification to inference gateways (api/v1alpha1/llmdasync_types.go:200-202, internal/controller/helm_async.go:152).
- The operator creates per-instance Roles/RoleBindings from the chart (for example the GC role), so it needs cluster-wide `roles`/`rolebindings` create/update. Escalation is bounded by Kubernetes RBAC escalation checks, but the operator SA is still a high-value identity.
- The operator does not create NetworkPolicies for operands. Isolation between operand pods and other namespaces is left to the platform or the user.
- `prefetched-charts/async-processor/` is a stale copy of the async chart. Dockerfile.konflux consumes only `prefetched-charts/batch-gateway` and `prefetched-charts/llm-d-async`.
- Sync dispatch has been removed. Async dispatch (Redis sorted-set or experimental SQL transport) is mandatory and is enforced by CEL validation on `ProcessorSpec` (api/v1alpha1/llmbatchgateway_types.go:299). See docs/async-default-migration.md.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace / per-CR at the Kubernetes level. Within one instance, the upstream gateway also has application-level tenants (identified by header, isolated by S3 key prefix) | config/crd/bases/batch.llm-d.ai_llmbatchgateways.yaml (`scope: Namespaced`); api/v1alpha1/llmbatchgateway_types.go:141, 242-243, 476-483 |
| **Deployment model** | Single cluster-wide operator, one operand stack per CR, deployed in the CR's namespace | internal/controller/llmbatchgateway_controller.go:244-262 |
| **Tenant identifier** | Namespace of the CR. Inside the gateway, a request header (e.g. `X-MaaS-Username`) mapped via `apiServer.config.batchAPI.inputHeaders` | api/v1alpha1/llmbatchgateway_types.go:242-243 |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | Aggregated admin/edit/view ClusterRoles for CRs. Operator SA is cluster-wide. Cross-namespace Secret use requires a ReferenceGrant | Kubernetes RBAC + operator | The operator SA can read and create Secrets in every namespace. Correct ReferenceGrant checking is the only thing stopping a CR author from copying another namespace's Secret |
| Data storage | User-provided PostgreSQL/S3/Redis per CR. Tenants within an instance share the bucket and are separated by key prefix | Application (upstream) | Several CRs can point to the same backends; the operator does not enforce separation |
| Network traffic | Operator pod only: NetworkPolicy limiting 8443 ingress to monitoring namespaces | Kubernetes | No NetworkPolicies for operand pods |
| Compute & resources | Per-component `resources` in the CR. No quotas created | Kubernetes | Relies on namespace ResourceQuota set by admins |
| Configuration & secrets | Per-CR Secret (local or copied `<cr>-credentials`), per-instance ConfigMaps | Kubernetes / operator | `secretRef` immutable after copy. Cluster-wide Secret informer cache |
| API scoping | Cluster-wide watches on CRs, owned kinds, Secrets (dynamically filtered), and ReferenceGrants. All writes go to the CR's namespace | controller-runtime | Cluster-wide list/watch footprint |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| Operator manager (single instance) | Namespace | Owner references; writes limited to the CR namespace |
| External PostgreSQL / S3 / Redis (if shared across CRs) | Per CR configuration; per tenant prefix inside an instance | Application-level (upstream batch-gateway) |
| Inference gateways / model servers | Tenant via fairness header / `routeKeyMethod: tenant` | Application-level (llm-d EPP flow control) |
