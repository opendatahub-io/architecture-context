## Purpose

**Short**: This repo builds and ships a static container image of curated YAML catalogs: validated models, other models, MCP servers, agents and KServe serving runtimes. The RHOAI model catalog reads these catalogs.

**Detailed**: model-metadata-collection has two parts. The first is a set of Go command-line tools that generate catalog YAML. They run offline, from a developer workstation or CI, and are never deployed to a cluster:

- `model-extractor` finds Red Hat AI validated models through the HuggingFace Collections API. It then pulls OCI ModelCar image manifests and layers from `registry.redhat.io` and scans the layers for modelcard annotations. Next it adds metadata from HuggingFace READMEs and vLLM recommended configs. Finally it writes `validated-models-catalog.yaml` and `other-models-catalog.yaml`. The same binary also builds the MCP server catalogs (Red Hat, partner and community), adding OCI image architectures and timestamps. It builds the agents catalog by fetching `agent.yaml` and `README.md` files from GitHub.
- `serving-runtime-catalog` renders KServe ServingRuntime OpenShift Templates. It takes them from RHOAI controller source images or checkouts, using `skopeo`, `kustomize` and `cosign` SBOM attestations, and writes `redhat-serving-runtimes-catalog.yaml`.
- `serving-runtime-validate` checks that catalog against model-registry API schemas pinned into the binary.
- `metadata-report` produces reports on how complete the metadata is.

The second part is what actually ships in RHOAI: the image `quay.io/rhoai/odh-model-metadata-collection-rhel9`, built from `Dockerfile.konflux`. It contains no binaries. It holds only the checked-in `data/*.yaml` files, copied to `/app/data`, and runs `sleep infinity` so other workloads can mount or copy the data. The current snapshot has 100 validated models, 44 other models, 4 Red Hat, 5 partner and 3 community MCP servers, 14 agents, and 24 serving runtimes.

The README tells maintainers to coordinate the metadata image rollout with an "operator configuration update" that points catalog sources at paths under `/app/data/`. This means the model-registry catalog service, deployed by the platform operator, mounts this data as catalog sources for the Model Catalog and MCP Catalog. Overlay 0018 says those catalog UIs and APIs belong to model-registry. This repo is the data supplier for them, not a runtime service.

## Architectural Analysis

**Data-only image built from offline tooling.** The architecture is a static content pipeline. Catalog generation needs credentials (`HF_TOKEN`, `GITHUB_TOKEN`, registry auth files), talks to the internet, and must be deterministic. All of it happens before the image is built. The generated YAML is committed to git and reviewed through PRs (the README says catalogs are "checked in by CI/CD"). The Konflux build then copies the committed YAML onto a digest-pinned `ubi9/ubi-minimal-pqc` base. As a result, the shipped artifact has no network listeners, no credentials, no Kubernetes API access and no executable code paths beyond `sleep`. The image label `io.openshift.expose-services=""` (Dockerfile.konflux:38) states this explicitly. The runtime attack surface is close to zero. The supply-chain trust boundary moves to the git review of `data/*.yaml` and to the integrity of the inputs the tools pull: HuggingFace content, GitHub raw files, and registry manifests and SBOMs.

**Generation pipelines.** There are four independent pipelines, all driven by the Makefile:

1. **Models.** HuggingFace collections lead to version-specific index files under `input/models/collections/`. These are merged with the curated `data/validated-models-index.yaml` and `data/other-models-index.yaml`. Each OCI ModelCar reference is then processed in parallel (a semaphore bounds concurrency, default 5) through `containers/image/v5`, with platform pinned to `linux/amd64`. Modelcards are extracted from layers, parsed into structured metadata, and enriched from HuggingFace and vLLM configs. The output is the two model catalogs. Validated status comes only from curated index membership and the `validated` label. Enrichment never promotes a model between catalogs, which is a deliberate governance decision documented in the README.
2. **MCP servers.** Per-server YAML under `input/mcp_servers/{redhat,partner,community}` is aggregated into three catalogs. OCI image architecture and timestamp enrichment can be turned off.
3. **Agents.** An index of GitHub repos and branches is resolved to commit SHAs through the GitHub API. Using the SHA, rather than a floating branch, keeps raw.githubusercontent.com fetches stable. The tool then fetches `agent.yaml` and `README.md`, capped at 5 MiB per response.
4. **Serving runtimes.** `input/serving_runtimes/generator-config.yaml` lists RHOAI controller images, for example `odh-kserve-llmisvc-controller-rhel9:v3.6-ea.1`. The tool pulls templates out of those images with `skopeo` and replaces image parameters in a temporary copy of `params.env`. It renders with `kustomize build` and resolves floating tags to `tag@sha256` digests. It discovers upstream vLLM versions from SPDX SBOM attestations through `cosign download attestation`. Validation requires every rendered image to come from `registry.redhat.io/rhoai/`, `rhaii/`, `rhaii-early-access/` or `rhaii-fast/`. Every serving-runtime image in the shipped catalog is digest-pinned.

**Cross-component coupling.** The serving-runtime catalog embeds full OpenShift `Template` JSON for `serving.kserve.io/v1alpha1` ServingRuntime objects, carrying odh-dashboard labels and annotations. So this repo effectively republishes runtime definitions owned by the KServe and model-runtimes teams. Drift between this snapshot and the operator-shipped runtimes is possible whenever controller images move. The generator config pins the EA source to rhods-operator 3.6.0-ea.1 bundle images, even though this is the 3.7-ea.1 branch. In other words, the 3.7-ea.1 data image currently carries 3.6-ea.1 runtime templates (`minimumRHOAIVersion: "3.6"`). The `minimumRHOAIVersion` field is a local catalog extension that the pinned model-registry loader ignores, as the validator itself notes.

**Upstream vs. downstream image divergence.** The upstream `Dockerfile` (GitHub Actions, `quay.io/opendatahub/...`) uses `ubi9-micro:latest`, an unpinned floating tag. It copies a named list of catalogs plus `sample-data/` into `/app/benchmarks`. The downstream `Dockerfile.konflux` uses a digest-pinned PQC base and copies `data/*.yaml`. That glob also picks up the index files and `redhat-agents-index.yaml`, and the image has no `/app/benchmarks`. Consumers should rely only on `/app/data`.

**Risks and observations.**
- The Konflux pipeline sets `hermetic: true` with a `gomod` prefetch, but the image build compiles no Go. The prefetch is unnecessary but harmless. Hermeticity holds because the Dockerfile runs no package installs.
- The Konflux image is built for x86_64, ppc64le, s390x and arm64, but metadata extraction always resolves `amd64` manifests. That is acceptable because the output is architecture-neutral metadata.
- `CMD ["sleep", "infinity"]` means a pod running this image never exits. Consumers are presumably expected to mount `/app/data` as a volume from an init container or a long-running sidecar. Wiring it as a short-lived init container would need a command override.
