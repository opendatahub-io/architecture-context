## Purpose

**Short**: llm-d Planner turns business requirements (use case, user count, SLOs) into sized LLM deployment recommendations and generates KServe or llm-d deployment manifests, which it can apply to a cluster.

**Detailed**: llm-d-planner is a capacity planning and recommendation tool for LLM serving. A user describes a workload in natural language or through structured forms. The backend uses an LLM (Ollama by default, or Claude on Vertex AI, or any OpenAI-compatible endpoint) to extract a structured `DeploymentIntent`. It then derives SLO targets and a traffic profile from bundled use-case templates, and scores candidate model/GPU/tensor-parallel configurations. Scoring uses benchmark data, quality scores (LMArena leaderboard and Artificial Analysis), and analytical memory/throughput estimates (HuggingFace model configs plus the BentoML `llm-optimizer`).

Benchmark data comes from an embedded SQLite database (`PLANNER_DB_PATH`, default `/app/db/planner.db` on a PVC) or, in RHOAI mode (`PLANNER_BENCHMARK_SOURCE=model_catalog`), from the RHOAI Model Catalog service (`model-catalog.rhoai-model-registries.svc:8443`, source `redhat_ai_validated_models`). Recommendations become Jinja2-rendered manifests: a KServe `InferenceService` (RawDeployment), HPA/autoscaling, a `ServiceMonitor`, or an llm-d kustomize/Helm-values bundle. With `kubectl` available, the backend can apply these to a target namespace and report status.

The repo produces three container images (backend, UI, simulator). The same code is also published to PyPI as the `llm-d-planner` library, with a `planner` CLI. In RHOAI it is a standalone helper app deployed into its own `planner` namespace. It reads from the Model Catalog and node GPU labels, and the manifests it generates target KServe/llm-d.

## Architectural Analysis

**Layering.** The code is a library first. `src/planner/planner.py` (`Planner` class, `PlannerConfig`) runs the pipeline: intent extraction → specification → recommendation → configuration generation. `src/planner/api/` is a thin FastAPI shell over it: `app.py` registers 10 routers, and `dependencies.py` builds singletons on `app.state` at startup. The Streamlit UI (`ui/`) only talks to the backend over HTTP (`API_BASE_URL`, default `http://backend:8000`). It copies a few data-resolver modules into its image to avoid pulling in backend dependencies. `src/quality_scoring/` is a separate package for the Arena/AA quality score engine.

**Pluggable external dependencies.** Each external integration is optional and selected by env var:
- LLM provider: `LLM_PROVIDER` = `ollama` | `vertex` | `openai`
- Benchmark source: `PLANNER_BENCHMARK_SOURCE` = `database` | `model_catalog`
- GPU detection: in-cluster Kubernetes client listing node labels `nvidia.com/gpu.product`, cached with `PLANNER_CLUSTER_GPU_CACHE_TTL`
- Quality data refresh: HuggingFace datasets + Artificial Analysis API

Python extras in `pyproject.toml` (`server`, `llm`, `openai`, `vertex`, `kubernetes`, `estimation`, `quality-sync`) mirror these choices. The backend image installs all of them.

**Security posture: the main architectural risk.** The backend API has no authentication or authorization middleware (`src/planner/api/app.py:57-89`). It sets CORS to `allow_origins=["*"]` with `allow_credentials=True` (`app.py:67-73`, plus `CORS_ORIGINS="*"` in `deploy/kubernetes/backend.yaml:112-113`). The reference manifests expose the backend directly through an edge-TLS OpenShift Route (`deploy/kubernetes/route.yaml:19-35`), with no oauth-proxy or kube-rbac-proxy in front. Three endpoint groups are sensitive:
- `POST /api/v1/deploy-bundle-to-cluster` (`src/planner/api/routes/configuration.py:155-227`) accepts arbitrary YAML and a caller-chosen namespace, then runs `kubectl create namespace` and `kubectl apply -f -` (`src/planner/cluster/manager.py:53-154`). This is effectively unauthenticated cluster write access, bounded only by the backend's kube credentials. In the shipped manifests that impact is mostly limited: the backend image does not install `kubectl` (`Dockerfile:8-12`), and the `planner-backend` SA only has `list nodes`. The control is accidental, though. A kubeconfig-mounted or local `make start` deployment would expose it fully.
- `PUT /api/v1/deployment-mode` and `PUT /api/v1/quality/auto-update` change global server state for every user.
- `/api/v1/db/upload-benchmarks` and `/api/v1/db/reset` are protected only by an optional shared `X-Admin-Password` header (`src/planner/api/routes/database.py:23-34`). It is compared in constant time with `hmac.compare_digest`. If `DB_ADMIN_PASSWORD` is unset (the shipped Secret has `db-admin-password: ""`), these destructive endpoints are open.

**State and scaling.** The backend is stateful: SQLite on a ReadWriteOnce PVC (`backend.yaml:142-178`), deployment mode held in memory, and an `asyncio.Lock` around the cluster manager (`app.py:51`). uvicorn runs `--workers 2` in one pod (`Dockerfile:65`), so in-memory settings such as deployment mode can differ between the two worker processes. All Deployments are `replicas: 1`, and Ollama uses `strategy: Recreate` with a 20Gi model PVC and one `nvidia.com/gpu` (`deploy/kubernetes/ollama.yaml:10-12,62-88`). Nothing in the design targets HA.

**Model Catalog integration.** This is the main RHOAI touchpoint. `ModelCatalogClient` (`src/planner/knowledge_base/model_catalog_client.py`) calls `https://model-catalog.rhoai-model-registries.svc:8443/api/model_catalog/v1alpha1`. It authenticates with `MODEL_CATALOG_TOKEN` or falls back to the pod's ServiceAccount token, and verifies TLS against the OpenShift service-CA bundle injected into the `planner-service-ca` ConfigMap. If the CA file appears after startup, the client recreates its httpx client. A NetworkPolicy installed into `rhoai-model-registries` (`deploy/kubernetes/networkpolicy-model-catalog.yaml`) lets planner backend pods reach port 8443.

**Supply chain and productization gaps.**
- Images build from `python:3.14-slim` (Debian, not UBI or AIPCC), with `apt-get` packages and `uv` copied from `ghcr.io/astral-sh/uv:latest`.
- The backend installs `llm-optimizer` straight from an unpinned GitHub URL (`Dockerfile:29`).
- `uv.lock` is listed in `.gitignore:30`, yet the backend `Dockerfile:18,28` COPYs it and runs `uv sync --frozen`. The image cannot be built from a clean checkout without first generating a lock file.
- Manifests reference `:latest` tags on quay.io/llm-d-planner and Docker Hub `ollama/ollama`.
- There are no Konflux Dockerfiles, Tekton pipelines, or RPM/artifact lock files on this branch. The checkout is an upstream incubation project, not yet a hermetic RHOAI build.
