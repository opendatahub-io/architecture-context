## Purpose

**Short**: Kubeflow Notebooks v2 "Workspaces" controller. It reconciles the `Workspace` and `WorkspaceKind` CRDs into per-user interactive IDE StatefulSets (JupyterLab, code-server, RStudio), and exposes them through the RHOAI Gateway API behind per-workspace kube-rbac-proxy sidecars.

**Detailed**: This repository is the downstream RHOAI fork of `kubeflow/notebooks` (the `notebooks-v2` codebase), carried through `opendatahub-io/workbenches`. It holds three upstream workloads under `workspaces/`: a controller-runtime operator (`controller`), a Go REST API (`backend`) and a React UI served by nginx (`frontend`). On the `rhoai-3.7-ea.1` branch only the **controller** has a Konflux Dockerfile and PipelineRun. It ships as `quay.io/rhoai/odh-workbenches-controller-rhel9`. The backend and frontend Dockerfiles are upstream-only (`golang`/distroless and `node`/`nginx` bases), with no downstream build.

An admin defines a cluster-scoped `WorkspaceKind`: a template of image configs, pod configs, ports, probes and activity rules. Users create namespaced `Workspace` CRs that pick a kind plus image/pod options. For each Workspace the controller creates:
- a StatefulSet, a Service, a ServiceAccount and RoleBindings
- either an Istio VirtualService (upstream mode) or, in the RHOAI `gateway` overlay, a set of Gateway API resources:
  - an `HTTPRoute` in the controller namespace, attached to `data-science-gateway` in `openshift-ingress`
  - a `ReferenceGrant` in the user namespace
  - a kube-rbac-proxy sidecar, its Service, its ConfigMap and a TLS secret issued by the Service CA
  - a per-workspace `system:auth-delegator` ClusterRoleBinding

The controller also probes workspace activity, either over HTTP against Jupyter's `/api/status` or by running a script via `pods/exec`. It uses the result to auto-pause idle workspaces according to `WorkspaceKind` activity rules.

In RHOAI 3.x this is the next-generation workbench engine. It sits beside the legacy `odh-notebook-controller` (Kubeflow `Notebook` CRD) and deliberately mirrors that component's OpenShift patterns: Service CA serving certs, `inject-cabundle`, and aggregation into the `admin`/`edit`/`view` roles. Downstream, the `workbenches-operator` deploys it from `manifests/kustomize/overlays/gateway` and rewrites the namespace to the applications namespace (for example `redhat-ods-applications`).

## Architectural Analysis

**Single binary, two reconcilers, two webhooks.** `cmd/main.go` starts one manager. It hosts `WorkspaceReconciler` and `WorkspaceKindReconciler`, the `vworkspace.kb.io` and `vworkspacekind.kb.io` validating webhooks on port 9443, health probes on 8081 and optional metrics. Leader election uses the ID `kubeflow-workspace-controller` and runs with `replicas: 1`. `MaxConcurrentReconciles` defaults to 10, so that a slow activity probe on one Workspace does not stall the others. Caching is turned off for ConfigMaps and Secrets to bound memory on large clusters; image-source ConfigMaps get a dedicated label-filtered cache instead (`cmd/main.go:191-203`, `:276`).

**Three ingress modes, chosen by flags.** The controller runs in one of three modes:

| Mode | How it is enabled | Resources created per Workspace |
|------|-------------------|---------------------------------|
| No ingress | default | none |
| Istio | `USE_ISTIO` | VirtualService (Owns watch) |
| Gateway API | `USE_KUBE_GATEWAY` | HTTPRoute + ReferenceGrant + kube-rbac-proxy |

Istio and Gateway API cannot both be on, and Gateway API mode requires `KUBE_RBAC_PROXY_IMAGE` (`cmd/main.go:137-144`). RHOAI uses Gateway API mode through `overlays/gateway/params.env`.

Each workspace route has a deterministic name `ws-<ns>-<name>` and is created in the **controller namespace**. It points across namespaces at the workspace's kube-rbac-proxy Service on 8443, which is why the controller also creates a ReferenceGrant in the user namespace. Neither the HTTPRoute nor the auth-delegator ClusterRoleBinding can carry an ownerReference, because both cross namespace boundaries. They are deleted explicitly when the Workspace disappears (`workspace_controller.go:203-221`). Only the **first** HTTP-protocol port of the image config is routed (`generateGatewayV1HTTPRoute` returns on the first match).

**Authorization lives at the sidecar.** Each workspace pod gets a kube-rbac-proxy listening on 8443, plus a health endpoint on 8444. Its static authorization config requires the caller to be allowed `get` on `workspaces.kubeflow.org/<name>` in `<namespace>`. Verified identity is forwarded upstream as `X-Auth-Request-User`/`X-Auth-Request-Groups`. Consequences:
- Access to a workspace is exactly Kubernetes RBAC on the Workspace object. The `workspaces-edit` and `workspaces-view` ClusterRoles aggregate into OpenShift `admin`/`edit`/`view`.
- The controller needs `bind` on `system:auth-delegator` so it can grant each workspace ServiceAccount TokenReview/SubjectAccessReview without holding those permissions itself. This is a deliberate, narrowly scoped escalation path, commented in `components/gateway/role_gateway_patch.yaml`.
- The controller's own Jupyter activity probe calls the pod IP and app port directly over plaintext HTTP (`probe.go:256`, `workspace_activity.go:214`), bypassing the sidecar. The controller's network position is effectively trusted.

**TLS follows the cluster profile.** `pkg/tls` reads `config.openshift.io/v1 APIServer/cluster` at startup. It maps `tlsSecurityProfile` (Old, Intermediate, Modern or Custom) onto the webhook and metrics `tls.Config`, and separately builds `--tls-min-version`, `--tls-cipher-suites` and `--tls-curve-preferences` arguments for every kube-rbac-proxy sidecar. A `ProfileWatcher` cancels the manager context when the profile or `tlsAdherence` changes, so the pod restarts to pick up new settings (`cmd/main.go:323-338`).

The proxy path is FIPS-aware. It detects FIPS through `crypto/fips140.Enabled()` or `/proc/sys/crypto/fips_enabled` and filters out ciphers and curves that are not FIPS-approved: ChaCha20, X25519 and the ML-KEM hybrids. The in-process path (`tls.go` `IntermediateCiphers`) still lists the two ECDHE-CHACHA20-POLY1305 suites and does not filter. Under `strictfipsruntime` those suites cannot be negotiated, but the two paths are inconsistent. If the cluster profile is "Old", the in-process minimum drops to TLS 1.0.

**Risks and observations**
- **Broad controller privileges.** The cluster-wide `pods/exec create` (for activity probes), `bind` on `system:auth-delegator`, cluster-wide ConfigMap CRUD (gateway patch) and ClusterRoleBinding CRUD make the controller ServiceAccount high-value.
- **No workload network isolation.** The controller creates no NetworkPolicy for workspace pods. Isolation relies on the user namespace's own policies; the app port is reachable on the pod network unauthenticated.
- **Cluster-scoped objects grow with Workspaces.** There is one `ws-<name>-rbac-<ns>-auth-delegator` ClusterRoleBinding per Workspace.
- **CRD conversion webhook is defined but off.** `/convert` patches exist under `base/crd/`, but they are commented out in `base/crd/kustomization.yaml`. The CRDs still carry `cert-manager.io/inject-ca-from` cainjection patches, which have no effect on OpenShift.
- **No high availability.** The Deployment runs `replicas: 1` even though leader election is enabled.
- **Image wiring.** The controller image is set through the `WORKBENCH_CONTROLLER_IMAGE` replacement from the gateway `params.env`, which defaults to `quay.io/opendatahub/odh-workbenches-controller:v2.0.2`. `workbenches-operator` overrides it at deploy time.

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | kube-rbac-proxy SAR on `get workspaces/<name>`; Workspace RBAC aggregated into OpenShift project roles; per-Workspace ServiceAccount | Kubernetes RBAC + sidecar | Per-workspace auth-delegator ClusterRoleBinding gives every workspace SA cluster-wide TokenReview/SAR create; controller holds cluster-wide `pods/exec` |
| Data storage | Per-namespace PVCs/secrets referenced by Workspace spec | Kubernetes | None beyond namespace RBAC |
| Network traffic | Controller pod: NetworkPolicy (9443/8081 ingress, metrics from monitoring ns only); workspace pods: none created | Kubernetes NetworkPolicy (controller only) | No NetworkPolicy for workspace pods; app port reachable unauthenticated on pod network, bypassing sidecar |
| Compute & resources | Pod config values from WorkspaceKind (requests/limits, affinity, tolerations) | Application (WorkspaceKind template) | No ResourceQuota created; relies on namespace quotas |
| Configuration & secrets | kube-rbac-proxy ConfigMap and TLS secret in user ns; WorkspaceKind cluster-scoped and shared | Kubernetes | WorkspaceKind is cluster-wide; any admin change affects all tenants (webhook protects in-use values) |
| API scoping | Cluster-wide watches on Workspaces, Pods, Services, etc.; HTTPRoutes centralized in controller ns | Kubernetes / Application | All routes in one namespace; isolation between routes relies on deterministic names and labels |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| workspaces-controller | namespace | Cluster-scoped SA; reconciles per-Workspace objects into owning namespace |
| data-science-gateway (Envoy) | path prefix `/workspace/connect/{ns}/{name}/` | HTTPRoute per Workspace + kube-rbac-proxy SAR at backend |
| WorkspaceKind templates | cluster | Admin-only RBAC (`kubeflow-workspaces-admin`); validating webhook |
