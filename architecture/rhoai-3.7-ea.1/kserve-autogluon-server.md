## Purpose

**Short**: A KServe model-serving runtime image that serves AutoGluon `TabularPredictor` and `TimeSeriesPredictor` models over the KServe v1/v2 inference protocols.

**Detailed**: `kserve-autogluon-server` is a downstream Red Hat fork of the full upstream KServe monorepo. The Go controller, webhooks, LLMInferenceService, router, local-model agents, Helm charts and the other Python model servers are all still in the tree. This branch builds only one Konflux artifact: `Dockerfile.konflux.autogluon`, which produces `quay.io/rhoai/odh-kserve-autogluon-server-rhel9` (component `odh-kserve-autogluon-server-v3-7-ea-1` in Konflux application `rhoai-v3-7-ea-1`). The rest of the tree is inherited context. The KServe controller and CRDs ship to RHOAI from the separate `kserve` component, not from here.

The runtime is the `autogluonserver` Python package (`python/autogluonserver/`) layered on the KServe Python SDK (`python/kserve`) and the `kserve-storage` model download library (`python/storage`). At startup it downloads the model directory given by `--model_dir` (normally `/mnt/models`, already populated by the KServe storage-initializer). If `Storage.download` is given a remote URI, it resolves S3/GCS/Azure/HDFS/HTTP/Git itself. The server then picks the predictor type by trying to load it: first `TimeSeriesPredictor.load`, then `TabularPredictor.load`. Users write a single `modelFormat: autogluon` in their InferenceService and never declare the predictor type.

Tabular models are served over KServe REST v1 and v2 (and over the v2 gRPC service the SDK provides). If `PREDICT_PROBA=true`, tabular models return class probabilities instead of labels. Time-series models accept REST v1 JSON only (`instances` history plus optional `known_covariates`) and return mean/quantile forecasts. Before loading, the server checks the AutoGluon version the model was saved with. A different patch or local label (for example `+rhaiv.1` vs `+rhaiv.3`) is tolerated. A different major or minor version is rejected.

## Architectural Analysis

**Fork-of-monorepo packaging.** The repository is a full KServe checkout (`cmd/`, `pkg/`, `config/`, `charts/`, 20+ Dockerfiles), so the arch-analyzer reports 50 runtime components, 12 CRDs and dozens of webhooks. Almost none of that ships from this repo. The deliverable is set by `.tekton/odh-kserve-autogluon-on-pull-request.yaml`: Docker build context `python/`, hermetic build, pip prefetch of `python/autogluonserver/autogluon-all-requirements.txt`, and four platforms (x86_64, ppc64le, s390x, arm64). This summary covers that image and lists the inherited KServe surface only where the runtime depends on it: the SDK's HTTP/gRPC server, storage, and the `ClusterServingRuntime` definition.

**Build/pipeline inconsistencies (risk).** Several build details don't line up:
- The PipelineRun names `dockerfile: Dockerfiles/autogluon.Dockerfile.konflux` with `path-context: python`. Neither `python/Dockerfiles/` nor that file exists on this branch. The real Konflux Dockerfile is `Dockerfile.konflux.autogluon` at the repo root. Its `COPY kserve`, `COPY storage`, `COPY autogluonserver` and `COPY third_party/...` lines only work with `python/` as the context. Expect the build to fail at Dockerfile resolution until the path is corrected, or until konflux-central resolves it some other way.
- Only an `on-pull-request` pipeline exists (triggered by PR or by the `/build-konflux-autogluon` comment). This branch has no `on-push` pipeline to produce release images.
- The pip index is pinned to `https://console.redhat.com/api/pypi/public-rhai/rhoai/3.5-EA2/cpu-ubi9/simple/`, both in the Dockerfile and in the requirements header. The branch targets RHOAI 3.7-ea.1 and the AIPCC `base-image-cpu` legacy index is at `rhoai/3.6` (overlay 0017), so the Python content channel lags the base image.
- `RUN uv venv -p 3.12 && source .venv/bin/activate` (line 11) has no lasting effect, because activation doesn't carry over to later `RUN` steps. Packages are installed with the base image's preconfigured `pip` into `/opt/app-root`, and the unused `.venv` is copied along with everything else.
- The OpenMP runtime install (`microdnf install -y libgomp`) is commented out (line 45). LightGBM/XGBoost therefore depend on the AIPCC base image already shipping `libgomp`.

**Dependency drift vs README.** The README's "supported stack" table lists `torch 2.9.1` and `catboost 1.2.8`. The hermetic requirements file actually pins `torch==2.11.0` and has no `catboost` at all. `pyproject.toml` installs `autogluon.tabular[lightgbm,xgboost,tabm,fastai]` without the catboost extra. Models trained with CatBoost will fail to load in this image. Backend versions are never checked at runtime (README and `version_compat.py` both say so), so a predictor trained against a different LightGBM/XGBoost/torch may load and then behave differently.

**Model loading = deserialization of untrusted pickles.** AutoGluon `*.load()` unpickles `predictor.pkl` and per-model artifacts. Anyone who can write to the model storage location can therefore execute code inside the serving pod. The only mitigations are the restricted pod security context (`runAsNonRoot`, `drop: [ALL]`, no privilege escalation) and RHOAI's normal controls over who can set `storageUri`. Loading is also brute force: a failed time-series load is caught and the tabular loader is tried, and both error messages are put in the `InferenceError`.

**Container-hardening accommodations.** `runtime_paths.ensure_autogluon_runtime_paths()` runs once at startup. It sets `MPLCONFIGDIR=/tmp/matplotlib` and `chdir`s into the first writable directory among `$TMPDIR`/`/tmp`, `$HOME` and `/home/kserve`. This exists because AutoGluon's SeasonalNaive fallback writes `./AutogluonModels` under the current working directory, and under OpenShift arbitrary UIDs the default cwd `/` is read-only.

**Fallback to model repository.** If `model.load()` raises `ModelMissingError`, `__main__` starts `ModelServer` with an `AutoGluonModelRepository`. That repository treats each subdirectory of `--model_dir` as a separate model, which enables multi-model loading via the v2 repository load/unload APIs.

**Two upstream-style Dockerfiles coexist.** `python/autogluon.Dockerfile` is the upstream Debian (`python:3.12-slim-bookworm`), `uv sync`, UID 1000 build. It is not used by Konflux, but it explains the `/home/kserve` and `MPLCONFIGDIR` conventions in the runtime code.
