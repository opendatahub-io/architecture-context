## Purpose

**Short**: The Async Processor (AP) pulls latency-insensitive inference requests from a message queue (Redis, GCP Pub/Sub or Postgres), applies capacity and admission gates, sends them over HTTP to llm-d-router or another inference gateway, and writes the results back to a result queue.

**Detailed**: llm-d-async lets batch and asynchronous inference work use spare accelerator capacity without hurting online serving. Users never call the processor directly. Producers (batch jobs, workflows, or RHOAI's `batch-gateway`) put request messages on a broker. The processor consumes those messages, decides when each one may be dispatched, POSTs it to the inference gateway's OpenAI-compatible endpoint (for example `/v1/completions`), and writes a result message keyed by request `id` to a result queue or topic. The README calls this "Bring Your Own Queue": prioritisation, retries, and scaling stay separate from the broker. Four transports are available: `redis-pubsub` (deprecated), `redis-sortedset` (recommended), `gcp-pubsub`, and `sql` (experimental, Postgres).

Flow control is the core of the processor. **Dispatch gates** run at two levels: per queue at admission, and per worker pool inside the worker loop. Budget gates (`prometheus-budget`, `prometheus-saturation`, endpoint scrape) query Prometheus or scrape EPP `/metrics` to estimate how much capacity the inference pool has free. Admission gates (`redis-quota`, `sql-quota`, `redis-leased-rate`, `tier-priority-admission`) enforce per-attribute quotas, for example per `userid`. **Merge policies** (`random-robin`, `tier-priority`) combine messages from many queues into one channel per worker pool, so a saturated pool only blocks its own traffic. Six strict priority lanes come from combining quota classification (reserved/overflow) with SLA tier (interactive/async/batch). Every message has a mandatory deadline. Failures are retried with exponential backoff until that deadline, after which a `DEADLINE_EXCEEDED` error result is written.

In RHOAI, overlay 0011 lists llm-d-async with `batch-gateway` as the batch-inference capability of the llm-d serving stack: `batch-gateway` provides the OpenAI `/v1/batches` API and llm-d-async does the asynchronous queue processing. The values file shows the two can share the batch gateway's Postgres when the `sql` transport is used. The processor sends requests to the llm-d-router/EPP (gateway-api-inference-extension) and stamps the `x-llm-d-inference-fairness-id` and `x-llm-d-inference-objective` headers so the gateway's flow control can arbitrate between tenants.

## Architectural Analysis

**Pull-based, API-less design.** The processor serves only health (`:8081`) and metrics (`:9090`). It has no request API, so its attack surface is mostly outbound: the broker connection, the inference gateway, Prometheus, and the OTLP collector. The upstream chart creates no Service, Route, or NetworkPolicy, and Prometheus scrapes the pod directly through a PodMonitor. Access control therefore depends on who can write to the broker. Anyone who can enqueue messages can make the processor send inference requests to whatever `igw_base_url` is configured for that queue. Queue-to-gateway URLs come from operator-controlled transport config, not from messages, which limits SSRF exposure. Per-message `metadata` can still choose body-transform plugins: `gcs_uri_multipart` passes a signed object URL through to the backend but never fetches it.

**Gate hierarchy and backpressure.** Admission happens in layers. Queue-level gates return `Refuse` (nack to broker) or `Drop` (write an error result). Pool-level gates can also return `Wait`, which parks the worker in memory for up to `--gate-wait-timeout` instead of sending the message back through the broker. Each worker holds one in-flight request, so pool size caps concurrency (the README points to Little's Law). Budget gates rely on Prometheus or EPP metrics. A cascade/cached metric source (default cache TTL configurable via `--prometheus-cache-ttl`) avoids overloading Prometheus, and fallback behaviour handles ambiguous pools (release note #489).

**State and consistency.** The processor itself is stateless. Durable state lives in the broker:
- Redis sorted sets hold deadline/priority-ordered requests, with claim leases (default 300 s TTL).
- Postgres holds the experimental `sql` transport: `async_requests`, `async_partitions`, `async_dispatchers`, `async_results`, and quota tables. Dispatchers lease hash partitions, and **schema migrations run automatically at processor startup** (`sqlqueue.WithMigrate()`).

Running several replicas therefore depends on the broker's semantics (sorted-set claims, Pub/Sub ack deadlines, SQL partition leases). The chart hardcodes `replicas: 1`, and there is no leader election.

**Graceful drain.** On SIGTERM, readiness flips to false, consumption stops, and in-flight requests get up to `--drain-timeout` (default 2 m) to finish before being cancelled. The chart sets `terminationGracePeriodSeconds: 130` to match.

**Security posture observations (risks):**
- The `/metrics` endpoint runs controller-runtime's `WithAuthenticationAndAuthorization` filter (TokenReview + SubjectAccessReview) only when `--metrics-endpoint-auth=true`. The binary defaults to `true`, but the Helm chart sets `ap.metrics.secure: false`, so **metrics are served unauthenticated over plain HTTP by default**. Turning auth on also needs `tokenreviews`/`subjectaccessreviews` RBAC, which the chart does not ship.
- `ctrl.GetConfigOrDie()` runs unconditionally at startup, so the pod must reach the Kubernetes API (or have a kubeconfig) even when metrics auth is disabled.
- Credentials are passed as connection URLs (`REDIS_URL`, `SQL_URL`) taken from a Kubernetes Secret through env vars. If an inline `url` is put in `transportConfig`, the chart renders it into pod args, where it is visible through `kubectl get pod` (the chart warns against this).
- The default OTLP export is plaintext gRPC (`ap.otel.insecure: true`).
- `--tls-insecure-skip-verify` exists for dev/test use and turns off gateway certificate validation.
- The upstream Dockerfile builds a static `CGO_ENABLED=0` binary on `gcr.io/distroless/static`. That would **fail the Konflux check-payload FIPS gate**. This repo has no `.konflux` Dockerfile, so the downstream RHOAI build must supply its own.

**Plugin/registry pattern.** Merge policies and body transforms register as plugins (`pkg/plugins`) using a TypedName/handle model copied from gateway-api-inference-extension's EPP plugin framework. The Go workspace (`go.work`) splits into reusable modules: `api`, `pipeline`, `producer` (Redis), and `producer-sql`. External producers import those client libraries to enqueue requests.
