## Purpose

**Short**: Red Hat downstream of EleutherAI's lm-evaluation-harness. It ships as the `odh-ta-lmes-job-rhel9` batch image, which runs language model benchmark evaluations for TrustyAI LMEval jobs and as an EvalHub framework adapter.

**Detailed**: lm-evaluation-harness (`lm_eval`) is a Python framework that evaluates language models against a large catalog of benchmark tasks (YAML task definitions under `lm_eval/tasks/`). It supports many model backends: local Hugging Face/vLLM/SGLang models, plus remote OpenAI-compatible, Anthropic, IBM watsonx.ai and other APIs. It exposes the `lm-eval` / `lm_eval` console scripts (`lm_eval.__main__:cli_evaluate`) and the `simple_evaluate` Python API.

In RHOAI the repository's only Konflux deliverable is the container image `quay.io/rhoai/odh-ta-lmes-job-rhel9`, built from `Dockerfile.konflux.lmes-job`. The image labels call it "a secure, batch-oriented execution environment for language model evaluations" with Unitxt integration and support for custom tasks and metrics. The image's default command is just the Python interpreter (`CMD ["/opt/app-root/bin/python"]`). The launcher supplies the real command, which runs one of two entrypoints:
1. **`python -m lm_eval ...`**: the classic CLI. The TrustyAI service operator's LMEvalJob path uses it (the `odh-ta-` prefix and the `my_tasks`/`my_catalogs`/`output`/`hf_home` directories in the image match that runtime contract).
2. **`python main.py`**: a downstream-only **EvalHub adapter** (`LMEvalAdapter(FrameworkAdapter)` from `eval-hub-sdk`). It reads a job spec from `/meta/job.json`, evaluates an OpenAI-compatible model endpoint through the `local-completions` backend, and reports status and results back to EvalHub. It can also save results to MLflow and push an OCI artifact.

The component is a pure evaluation client. It exposes no network endpoints, defines no CRDs, and creates no Kubernetes resources. Its network footprint is entirely egress: to the model inference endpoint under test, Hugging Face Hub (datasets, tokenizers, metrics) unless running offline, the EvalHub callback API, MLflow, OCI registries, and optionally S3-compatible storage.

## Architectural Analysis

**Two personalities in one image.** The upstream harness is a general CLI/library. The downstream fork adds a thin integration layer: `main.py` (about 1,265 lines) and `scripts/oci.py`/`scripts/s3_downloader.py`. This layer turns the harness into a managed job runtime. The EvalHub adapter narrows the model surface deliberately. `build_lmeval_config()` always picks `local-completions` (an OpenAI-compatible `/v1/completions`) with `tokenized_requests=False`, so the job sends string prompts to a remote inference server. It needs only a Hugging Face tokenizer locally ("Device: cpu (forced)"). The CUDA/torch base image therefore mostly serves the `lm_eval` CLI path, where in-process HF/vLLM backends are possible, rather than the EvalHub path.

**Job contract with EvalHub.** EvalHub mounts the job spec under `/meta` (default `/meta/job.json`, overridable via `EVALHUB_JOB_SPEC_PATH`). The adapter refuses paths that resolve outside `/meta` (CWE-22 guard, `main.py:95-116`). The adapter reports progress phases through `JobCallbacks.report_status()`, writes results to MLflow (`callbacks.mlflow.save`), then calls `callbacks.report_results()`. When `exports.oci` is set in the job spec, it also creates an OCI artifact. Model credentials come from the SDK (`resolve_model_credentials()`, `read_model_auth_key("hf-token")`) and are injected into `OPENAI_API_KEY`/`HF_TOKEN` for the harness.

**Disconnected / air-gapped support.** Before `lm_eval` and the Hugging Face libraries are imported, the adapter checks for a staged tokenizer plus a `dataset_dict.json` bundle under `/test_data`. If it finds them, it sets `HF_HUB_OFFLINE`, `HF_DATASETS_OFFLINE`, `HF_EVALUATE_OFFLINE` and `TRANSFORMERS_OFFLINE`, and pins the HF caches to `/test_data` (`main.py:206-275`). An EvalHub init container fills `/test_data` (via `test_data_ref`). On the CLI path, `lm_eval/__main__.py:16-33` redirects `evaluate.load` to a local metrics folder (`LMEVAL_METRICS_PREFIX`) when `HF_EVALUATE_OFFLINE=1`. The repo also carries a `metrics/` directory.

**Security hardening in the adapter.**
- Model-generated code runs only for an allow-list of benchmarks (`humaneval`, `humaneval_instruct`, `mbpp`): `HF_ALLOW_CODE_EVAL` is forced to `0` for everything else (`main.py:65-92`).
- `trust_remote_code` is limited to an allow-list (`ethics_cm`).
- `num_concurrent` is capped at 128.
- Error messages are scrubbed of bearer tokens, key=value secrets, JSON secrets and URL userinfo/query strings before they go to EvalHub callbacks (`_sanitize_error_message`, `main.py:440-485`). `tests/test_evalhub_error_sanitize.py` covers this.
- The `uv` binary from the base image is removed to drop its bundled crypto (RHOAIENG-99284).
- The image runs as UID 65532.

**Risks and observations.**
- **Remote code and secrets on the CLI path.** The classic CLI path keeps upstream behaviour. It can append `trust_remote_code=True` (`lm_eval/__main__.py:396`) and passes `HF_TOKEN` into `hf_hub_log_args` (`lm_eval/__main__.py:307-308`).
- **TLS verification can be turned off.** `verify_certificate` on API models can be disabled. `scripts/s3_downloader.py` honours `S3_VERIFY_SSL=false`, and `scripts/oci.py` can pass `--tls-verify=false`.
- **Stale root `requirements.txt`.** The root file is a Poetry export with CUDA 12 NVIDIA wheels and older pins. The real build input is the hash-pinned `requirements/{cuda,cpu}/requirements.txt`. Architects should treat the root file as non-authoritative.
- **Lock index version lag.** The Python locks are compiled against the legacy `rhoai/3.6` RHAI package index. Meanwhile the base images are `torch2.13` AIPCC images (with their own channel indexes), so the dependency pins and the base image index may drift.
- **Unpinned base on the non-Konflux path.** `Dockerfile.lmes-job` is a legacy, non-Konflux, source-building Dockerfile. It uses `ubi9/python-311:latest` and compiles Arrow/PyTorch/OpenBLAS for ppc64le/s390x. Konflux does not use it.
