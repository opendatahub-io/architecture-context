## Purpose

**Short**: Training Hub is a Python library and CLI (`thub`) that gives one algorithm-focused API for LLM post-training (SFT, OSFT, LoRA-SFT, GRPO/LoRA-GRPO, GEPA prompt optimization and embedding fine-tuning), with pluggable training backends underneath.

**Detailed**: Training Hub (`training-hub` on PyPI) hides the different training libraries behind one abstraction: an *Algorithm* (what to do) and a *Backend* (which engine runs it), both kept in an `AlgorithmRegistry`. Callers use simple functions (`sft()`, `osft()`, `lora_sft()`, `lora_grpo()`, `grpo()`, `gepa()`, `embedding_sft()`) or the `thub <algorithm>` CLI. Each call is handed to a backend: InstructLab Training (SFT), RHAI Innovation Mini-Trainer (OSFT), Unsloth/TRL (LoRA-SFT), OpenPipe ART with co-located vLLM, or verl (GRPO), the `gepa` library or MLflow (GEPA), and sentence-transformers (embedding SFT). The library also includes memory and runtime estimators, loss plotting, a single callback interface that works across all backends, and just-in-time (JIT) preemption checkpointing. That checkpointing can mirror checkpoints to any fsspec object store (S3 is the tested path).

In RHOAI, Training Hub is not deployed by itself. It has no CRDs, operator, Service, or ingress. It is pre-installed as a pip dependency in the Kubeflow "universal training" images built in `opendatahub-io/distributed-workloads` (overlays 0009, 0013). Those images serve two roles: a Jupyter workbench, and the training runtime that Kubeflow Trainer v2 (TrainJob / ClusterTrainingRuntime) or the legacy Kubeflow Training Operator (PyTorchJob) launches. Inside those pods, Training Hub reads the torchrun / PyTorch elastic environment (`PET_*`, `WORLD_SIZE`, `LOCAL_RANK`, `NODE_RANK`) to set up distributed launches. It then writes checkpoints to the pod filesystem (usually a PVC) and, optionally, to remote object storage.

Training Hub sits next to fms-hf-tuning as an algorithm library within the RHOAI fine-tuning stack, while Trainer v2 and KFTO handle orchestration. The Red Hat AI Innovation team owns its release cadence, which feeds the universal-image release process each RHOAI cycle (overlay 0013).

## Architectural Analysis

**Algorithm/Backend registry pattern.** Each algorithm module registers itself and its backends when imported (for example `sft.py:384-385`, `osft.py:656-657`, `lora.py:1133-1134`, `lora_grpo.py:1754-1758`, `lora_grpo_verl.py:1136-1137`, `gepa.py:613-615`, `embedding_sft.py:558-559`). Heavy backend dependencies are imported lazily inside backend methods, and the optional extras (`cuda`, `lora`, `grpo`, `grpo-verl`, `gepa`, `embedding`, `s3`) gate which backends can run. As a result, the base install is fairly small, but the full feature set pulls in a very large ML dependency graph: torch, vLLM via ART/verl, flash-attn, mamba-ssm, unsloth, xformers, and litellm. Keeping these extras compatible with each other is pushed onto the universal-image build (overlay 0013), not managed in this repo.

**Process model.** Training Hub mostly launches other processes rather than doing the compute itself. SFT and OSFT run through torchrun via InstructLab Training and Mini-Trainer, and `utils.get_torchrun_params` resolves rendezvous settings from the `PET_*` variables that Kubeflow Trainer injects. verl GRPO runs as a `subprocess.Popen` child whose stdout is parsed live for metrics (`lora_grpo_verl.py:993-1030`). ART GRPO starts an in-process LocalBackend with a co-located vLLM engine. Multi-GPU and multi-node communication (NCCL/Gloo, torchrun rendezvous) therefore runs pod-to-pod inside the training job. That traffic is set up by the backends, and Training Hub adds no TLS or auth to it.

**Callback serialization across the torchrun boundary.** To make user `TrainingHubCallback` subclasses work inside torchrun workers, `adapters/serialize.py` captures each class's source with `inspect.getsource`, writes it base64-encoded to a JSON payload file (mode 0600), passes the file path in `TRAINING_HUB_CALLBACKS_PATH`, and rebuilds the class in the worker with `exec()` (`serialize.py:82-92`). This is a deliberate trust boundary: anyone who can write to the payload directory can run code in every rank. That directory defaults to a temp dir, but the code recommends the checkpoint `output_dir` (often a shared PVC) for multi-node jobs. The CLI has a similar boundary: `importlib.import_module` runs for callable parameters named in YAML configs (`cli.py:391-410, 702`). YAML itself is loaded with `yaml.safe_load` (`cli.py:450`).

**Preemption-aware checkpointing.** `jit_checkpoint.py` installs a SIGTERM handler that only sets flags (it avoids logging, which could deadlock in a signal handler). The flag is then combined across ranks with an all-reduce (MAX) so every rank saves and stops at the same step boundary. `checkpoint_manager.py` mirrors checkpoints to `TRAINING_HUB_CHECKPOINT_UPLOAD_URI` through fsspec. It uses a write/read/delete probe at `train()` entry to fail fast, a 4-worker background upload pool with 3 attempts per upload, `.upload_complete` markers so only finished uploads are ever restored, and node-0 / local-rank-0 election so only one node uploads. Its docs warn that for SFT/OSFT the full upload happens during the pod termination grace period, so the default 120 s is too short for multi-GB checkpoints. This is an operational risk that Kubernetes job specs need to account for.

**External credentials come from the environment.** The library opens no network listeners. Its egress (S3-compatible storage, MLflow, Weights & Biases, OpenAI-compatible LLM endpoints via litellm for GEPA, and the HuggingFace Hub for model and dataset downloads) uses credentials taken from the pod environment by the underlying SDKs. Training Hub defines no Secrets itself. GEPA temporarily overwrites `OPENAI_API_BASE` and `OPENAI_API_KEY` in the process environment (setting `"dummy"` when no key exists) and restores them afterwards (`gepa.py:63-97`). Because this mutates environment state for the whole process, it is not thread-safe.

**Supply-chain posture.** The repo has no lockfile, no Dockerfile and no Konflux configuration. Dependencies are lower-bound ranges only. `litellm` excludes versions known to be compromised (1.82.7, 1.82.8, 1.107.0; `pyproject.toml:77-78, 87-89`), which shows supply-chain incidents in this dependency graph are being tracked by hand. GitHub Actions are SHA-pinned and PyPI publishing uses trusted publishing (OIDC). The hardened-runner egress policy is still `audit`, not `block`. Any hermetic or FIPS guarantees must come from the downstream universal image build, not from this repo.
