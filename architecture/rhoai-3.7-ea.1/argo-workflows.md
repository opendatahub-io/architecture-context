## Purpose

**Short**: A Kubernetes-native workflow engine. RHOAI ships its workflow controller and `argoexec` executor as the execution backend for Data Science Pipelines (Kubeflow Pipelines v2).

**Detailed**: This repository is the Red Hat downstream fork of upstream `argoproj/argo-workflows`. It defines the `argoproj.io/v1alpha1` CRDs, including `Workflow`, `WorkflowTemplate`, `ClusterWorkflowTemplate`, `CronWorkflow` and the internal `WorkflowTaskResult`, `WorkflowTaskSet` and `WorkflowArtifactGCTask` types. The `workflow-controller` reconciles these resources by creating one pod per workflow step, plus PDBs and ConfigMaps. Inside each step pod, the `argoexec` binary runs as the init, wait and emissary process. It moves input and output artifacts to and from object stores (S3, GCS, Azure, OSS, HDFS, Git, HTTP) and reports step results back as `WorkflowTaskResult` objects.

In RHOAI, only two images are built from this repo by Konflux: `odh-data-science-pipelines-argo-workflowcontroller-rhel9` and `odh-data-science-pipelines-argo-argoexec-rhel9`. They are not deployed by this repo's kustomize manifests. The Data Science Pipelines Operator (DSPO) deploys a `workflow-controller` Deployment per `DataSciencePipelinesApplication` (DSPA) namespace with `--namespaced`, `--configmap ds-pipeline-workflow-controller-<dspa>` and `--executor-image <argoexec>`. The KFP API server submits compiled pipeline runs as Argo `Workflow` CRs into that namespace.

The upstream `argo-server` (UI and gRPC/REST API on 2746/TCP), the `argo` CLI, SSO, and the SQL workflow archive are present in source. However, RHOAI does not build or ship them: there is no Konflux pipeline for the `argocli` image. They are described below for completeness and marked as not shipped.

## Architectural Analysis

**Two-binary runtime, one-controller-per-tenant deployment.** The RHOAI footprint is a controller and a per-step executor. The workflow controller is a classic informer/workqueue controller (`workflow/controller/controller.go`). It has tunable worker pools: `--workflow-workers` 32, `--cron-workflow-workers` 8, `--pod-cleanup-workers` 4, `--workflow-ttl-workers` 4 and `--workflow-archive-workers` 8. It also has client-side throttling (`--qps` 20, `--burst` 30) and Lease-based leader election (`LEADER_ELECTION_IDENTITY`, `coordination.k8s.io/leases`). With `--namespaced`, the controller scopes all informers to the managed namespace, which defaults to its own namespace (`cmd/workflow-controller/main.go:106-111`). DSPO relies on this to run one isolated controller per DSPA namespace instead of a shared cluster-wide controller. The upstream cluster-install manifests still bind a broad `argo-cluster-role` (pods, pods/exec and PVCs create/delete; workflows CRUD; secrets get). DSPO replaces that with its own namespace Role template (`data-science-pipelines-operator/config/internal/workflow-controller/role.yaml.tmpl`).

**Executor as privileged data mover.** `argoexec` runs inside user workload pods. It reads artifact repository credentials from Secrets referenced in the workflow and pushes or pulls artifacts. The `agent` mode executes HTTP templates directly. HTTP templates use `http.DefaultClient` unless `insecureSkipVerify: true` is set on the template, which selects a shared `InsecureSkipVerify` client (`workflow/executor/agent.go:301-310`). This lets a pipeline author disable TLS verification for outbound HTTP steps per template.

**Controller listeners.** The controller exposes `/healthz` on `:6060` through the default `http` mux with no authentication (`cmd/workflow-controller/main.go:181-184`). It serves Prometheus/OTel metrics on 9090. Metrics TLS defaults to on (`MetricsConfig.Secure`, `config/config.go:286`) and uses a self-signed ECDSA P-256 certificate generated at startup (`util/tls/tls.go:47-127`). DSPO's NetworkPolicy restricts 9090 ingress to the OpenShift and RHOAI monitoring namespaces. pprof handlers (`util/pprof/pprof.go`) are registered only when `ARGO_PPROF` is enabled.

**FIPS posture diverges from check-payload expectations.** Both Konflux Dockerfiles build with `CGO_ENABLED=0 GOFIPS140=v1.0.0 -tags no_openssl`, and argoexec also builds with `-ldflags '-extldflags -static'`. The binaries are therefore statically linked and use Go's native FIPS 140-3 cryptographic module, not dynamically linked OpenSSL. The runtime base is `ubi9/ubi-minimal-pqc`. This deliberately departs from the "dynamic CGO plus OpenSSL" pattern that check-payload has historically enforced. Whether Konflux accepts it depends on check-payload's handling of `GOFIPS140` binaries, so it should be tracked.

**Legacy and duplicate Dockerfiles.** `rhoai/Dockerfile.*` (ubi8, go-toolset 1.21, `make dist/...`) and `argo-*/Dockerfile.ODH` are stale alternatives. Only `argo-*/Dockerfile.konflux` is referenced by `.tekton/*-v3-7-ea-1-push.yaml`. The upstream root `Dockerfile` and `Dockerfile.windows` are not used for RHOAI builds.

**Unshipped surfaces.** The source still contains the upstream argo-server and its supporting features: 9 gRPC services with a grpc-gateway REST facade, artifact download endpoints, OAuth2/OIDC SSO with JWE-encrypted session cookies (`server/auth/sso/sso.go:182`, RSA-OAEP-256 + A256GCM) and webhook event intake (`argo-workflows-webhook-clients` secret). The SQL archive and offload support (MySQL/Postgres via `upper/db`) is also present. DSP uses its own KFP API server, so none of these surfaces reach the RHOAI attack surface unless someone deploys `argocli` manually.
