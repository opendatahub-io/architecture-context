## Purpose

**Short**: A Model Context Protocol (MCP) server that lets AI agents work with Red Hat OpenShift AI resources (projects, workbenches, model serving, pipelines, storage, connections, training, model registry/catalog) through MCP tools, resources, and prompts.

**Detailed**: rhoai-mcp is a Python FastMCP application. It exposes about 97 MCP tools and 18 workflow prompts that cover what the OpenShift AI Dashboard can do. Agents can create and manage Data Science Projects (namespaces), Kubeflow Notebook workbenches, KServe InferenceServices and ServingRuntimes, Data Science Pipelines Applications, PVCs, S3 data-connection Secrets, and Kubeflow Trainer v2 TrainJobs. The server talks directly to the Kubernetes API through the `kubernetes` Python client and its dynamic client. It also calls the Model Registry and Model Catalog REST APIs over HTTP(S) with `httpx`.

The server can run over three transports: `stdio` (local agents such as Claude Desktop; the container default), `sse`, and `streamable-http`. In cluster deployments it listens on port 8000. The base kustomize config sets transport to `sse`, and the OIDC overlay switches it to `streamable-http`. A "Navigator"/planner composite embeds the `llm-d-planner` library in-process (local mode). It can also call a remote Planner REST backend. It gives GPU and deployment recommendations, using benchmarks synced from the RHOAI Model Catalog.

Within the platform, rhoai-mcp is an agent-facing control plane over existing RHOAI CRDs. It defines no CRDs of its own. It ships kustomize overlays for the ODH (`opendatahub` namespace) and RHOAI (`redhat-ods-applications` namespace) operator-managed deployments. The ODH/RHOAI operator rewrites `params.env` with the `RELATED_IMAGE` value at deploy time.

## Architectural Analysis

**Plugin architecture with domains and composites.** Features are pluggy plugins (`src/rhoai_mcp/plugin.py`, `plugin_manager.py`). *Domains* (`src/rhoai_mcp/domains/*`) are self-contained CRUD modules, each with its own client, models, tools, and CRD definitions. *Composites* (`src/rhoai_mcp/composites/*`) orchestrate across domains for agent efficiency, for example `explore_cluster`, `diagnose_resource`, `prepare_training`, and the planner/Navigator flow. Dependencies flow one way: composites import domains, never the reverse. `RHOAI_MCP_ENABLED_PLUGINS` filters which plugins load at startup. By default, the `notebooks`, `pipelines`, `training`, and `prompts` domains are **not** enabled (`config.py:250-263`), so the default deployment exposes a narrower tool set than its ClusterRole would allow.

**There are two very different security postures, chosen at deploy time.**
1. *ServiceAccount-as-actor (base, `openshift`, `odh`, `rhoai` overlays).* Every MCP caller acts through the `rhoai-mcp` ServiceAccount. A ClusterRoleBinding gives it cluster-wide create/delete on namespaces, Secrets, PVCs, Notebooks, TrainJobs, InferenceServices, and DSPAs. It can also create Pods and PersistentVolumes. The MCP HTTP endpoint itself has **no authentication** in this mode: `OIDCAuthMiddleware` is attached only when `oidc_enabled` is true (`server.py:373-465`). The overlays expose it through an edge-terminated OpenShift Route. So anyone who can reach the Route or Service gets the SA's cluster-wide privileges, limited only by application-level guards. Those guards are `read_only_mode`, which the RHOAI overlay sets to `true`, `enable_dangerous_operations=false`, which blocks deletes, and a `app.kubernetes.io/managed-by=rhoai-mcp` ownership check before deleting resources (`clients/base.py:381,500,597,679`). This is the main architectural risk in this component.
2. *Multi-user OIDC (`openshift-oidc` and `openshift-oidc-mcpserver` overlays).* The ClusterRole is replaced so it grants only `create tokenreviews`, `create subjectaccessreviews`, and `get users.user.openshift.io`. A pure-ASGI middleware validates each caller's Bearer token. It uses either the Kubernetes TokenReview API (OpenShift opaque tokens) or JWKS-verified JWTs (RS256/ES256, with `exp`/`iss`/`aud` required). The validated identity is stored in a contextvar (`UserContext`). Downstream Kubernetes calls then use either the caller's own token (`user-token`, `clients/base.py:248`) or SA credentials with `Impersonate-User`/`Impersonate-Group` headers (`impersonation`, `clients/base.py:211`). The server refuses `user-token` combined with `jwt` at startup, because audience-bound JWTs cannot be forwarded (`config.py:399-407`). Tool listing and invocation are also filtered per user with SubjectAccessReview against per-tool permission mappings that plugins supply (`server.py:157-204, 467-547`). The design is fail-closed: an RBAC check error returns an empty tool list. Tools with no permission mapping are allowed by default.

**Lifecycle notes.** The server connects to Kubernetes eagerly in `create_mcp()` so `/health` answers before the first MCP session (`server.py:256-275, 337`). Port-forward connections, used when discovering the Model Registry from outside the cluster, are cleaned up by wrapping the Starlette lifespan (`server.py:285-320`). Workflow continuation tokens are HMAC-SHA256 signed (`utils/workflow_token.py`). The secret is random per process unless `RHOAI_MCP_WORKFLOW_HMAC_SECRET` is set, so tokens do not survive a restart and are not shared across replicas.

**Session affinity and scaling.** `streamable-http` sessions are stateful, so the OIDC overlay sets `sessionAffinity: ClientIP` (3h timeout). All overlays run `replicas: 1`. Nothing in the repo provides HA (no PDB, no HPA).

**TLS posture for in-cluster HTTP calls.** In-cluster calls to Model Registry service URLs (`*.svc`, `*.svc.cluster.local`) **skip TLS verification** (`domains/model_registry/auth.py:55-80`), because the OpenShift service-serving CA is not in the SA bundle. The OIDC overlay already mounts an injected service-CA ConfigMap at `/etc/pki/service-ca` and passes it to the Model Catalog client through `MODEL_CATALOG_CA_BUNDLE`. Using that bundle for Model Registry calls as well would close this gap. Model Registry discovery also prefers plain HTTP on port 8080 over kube-rbac-proxy on 8443 (`domains/model_registry/discovery.py:53-56, 228-229`).

**Deployment evolution.** The `openshift-oidc-mcpserver` overlay replaces the Deployment and Service with a `mcp.x-k8s.io/v1alpha1` `MCPServer` CR, annotated with the catalog entry `com.redhat/rhoai-mcp-server`. The MCP Lifecycle Operator then reconciles the workload, and the Service port name becomes `mcp`. This points to a move toward operator-managed MCP server lifecycle across the platform.

## AIPCC Ecosystems Use

The repo builds a single image from `Containerfile`; there is no `.konflux`-suffixed Dockerfile. Konflux uses it in `.tekton/odh-rhoai-mcp-push.yaml`. The image installs Python packages with `uv sync --frozen --no-dev` (`Containerfile:22`). The base image is `quay.io/opendatahub/odh-midstream-python-base-3-12`, which is **not** an AIPCC base image (`quay.io/aipcc/base-images/*`), and overlay 0017 does not list it. The image does not use AIPCC accelerator variants or AIPCC tooling. To meet Red Hat product-security requirements for secure builds, this component should migrate to AIPCC base images, even though it uses no accelerator-specific libraries. Separately, `requirements-cpu.txt` is compiled against the Red Hat AI Python index (`https://packages.redhat.com/api/pypi/public-rhai/cpu-torch2.13-el9.8-test/simple/`), but the Containerfile installs from `uv.lock` and does not use that file.

### Isolation Mechanisms

| Auth & AuthZ | SA mode: shared SA with cluster-wide ClusterRole. | Data storage | No local persistence (emptyDir `/tmp` only); user data lives in per-namespace PVCs and Secrets | Kubernetes | None in the component |
| Network traffic | No NetworkPolicy for the rhoai-mcp pod in repo (only an optional ingress policy in the model-registries namespace) | — | Pod reachable from any namespace on 8000 |
| Compute & resources | Pod requests/limits (100m/256Mi – 500m/1Gi) | Kubernetes | Single replica shared by all users; no per-user rate limiting |
| Configuration & secrets | Single ConfigMap; HMAC secret per process | Application | Workflow tokens are not bound to a user identity (signature only) |
| API scoping | Cluster-wide list/watch; projects filtered by `opendatahub.io/dashboard=true` label | Application / Kubernetes | In SA mode the label filter is a convenience, not a security boundary |
