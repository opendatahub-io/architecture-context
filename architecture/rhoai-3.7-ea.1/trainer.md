## Purpose

**Short**: Kubeflow Trainer v2 for RHOAI. It provides the TrainJob/TrainingRuntime APIs for distributed training and fine-tuning on Kubernetes, plus a small RHOAI operator that installs and manages the Trainer controller through a `Trainer` platform CR.

**Detailed**: The repository is the Red Hat downstream of `kubeflow/trainer` (by way of `opendatahub-io/trainer`). The core deliverable is the **Kubeflow Trainer controller-manager** (`cmd/trainer-controller-manager`, image `odh-trainer-rhel9`). It reconciles `TrainJob` objects against `TrainingRuntime` / `ClusterTrainingRuntime` templates and turns each TrainJob into a JobSet (`jobset.x-k8s.io/v1alpha2`), along with ConfigMaps, Secrets (MPI SSH keys, Flux CURVE certs), Services and optional gang-scheduling PodGroups (scheduler-plugins CoScheduling or Volcano). A plugin framework (`pkg/runtime/framework/plugins`) implements the framework-specific behaviour: Torch, MPI, JAX, XGBoost, Flux, PlainML, JobSet, CoScheduling, Volcano and TrainJobStatus. The controller-manager also serves admission webhooks for all trainer APIs. It manages its own webhook certificates with `open-policy-agent/cert-controller`. Behind feature gates it can run a TrainJob status server and an alpha `OptimizationJob` hyperparameter-tuning controller that talks gRPC to an Optuna/Katib suggestion service.

The RHOAI build adds midstream-only features in `pkg/rhai/`. Progression tracking polls training pods over HTTP for progress metrics and writes them into a TrainJob annotation. The controller also creates a NetworkPolicy for every TrainJob to isolate the training pods. These features are switched on in the RHOAI manifest overlay with `ENABLE_RHAI_FEATURES=true` (`manifests/rhoai/manager_config_patch.yaml:13`).

The **trainer-operator** (`rhoai/operator`, image `odh-trainer-operator-rhel9`) is a standalone module operator built on `opendatahub-io/odh-platform-utilities`. It reconciles the cluster-scoped `Trainer` CR (`components.platform.opendatahub.io/v1alpha1`, singleton `default-trainer`). On each reconcile it checks that the OpenShift JobSet Operator is installed and healthy. It then renders the bundled kustomize manifests (`/opt/manifests-template`: the `manifests/rhoai` overlay, the curated ClusterTrainingRuntimes and the training-hub ImageStreams) with `RELATED_IMAGE_*` overrides, translates the cluster TLS profile into the operand's `Configuration`, and applies everything with Server-Side Apply into the applications namespace. The platform (rhods-operator) drives this operator by creating the `Trainer` CR and the `odh-trainer-config` ConfigMap.

## Architectural Analysis

**Two-tier operator pattern.** RHOAI no longer has the platform operator deploy Kubeflow Trainer manifests directly. A dedicated module operator owns that job. The operator image bakes in the operand manifests at build time (`rhoai/operator/Dockerfile.konflux:32-36`), so operand and manifests ship together as one versioned unit and nothing is fetched at runtime. Image references are substituted at runtime from `RELATED_IMAGE_*` environment variables (`rhoai/operator/internal/controller/params.go:30-57`), which suits disconnected and OLM relatedImages use. The operator's own manager cache is scoped to `APPLICATIONS_NAMESPACE` with label filters (`rhoai/operator/cmd/main.go:103-145`). Its RBAC is still cluster-wide, though, because it has to install CRDs, ClusterRoles, webhook configurations and cluster-scoped ClusterTrainingRuntimes.

**Spec fields the reconciler does not use.** `TrainerSpec` declares `featureGates` and `controllers[].resources` (`rhoai/operator/api/v1alpha1/trainer_types.go`), but nothing in `rhoai/operator/internal` reads them. Operand feature gates come entirely from the bundled `manifests/rhoai/controller_manager_config.yaml`, where only `TrainJobDynamicResourceAllocation: true` is set. As a result, alpha features such as `TrainJobStatus` (status server) and `OptimizationJob` stay off in RHOAI. Users cannot turn them on through the CR.

**Dependency gating instead of bundling.** On OpenShift the operator does not install JobSet itself; the bundled third-party JobSet resource is commented out in `manifests/rhoai/kustomization.yaml`. Instead it requires the Red Hat JobSet Operator: an OLM `jobset-operator` subscription, a `JobSetOperator` CR named `cluster`, a healthy status and an existing JobSet CRD. If any of these is missing, it marks the `Trainer` CR `Degraded` (`rhoai/operator/internal/controller/trainer_controller.go:271-309`, `dependencies.go:35-93`). This follows the platform policy of not auto-installing external operators.

**TLS profile propagation.** Both managers resolve the OpenShift `APIServer` TLSSecurityProfile at startup through `odh-platform-utilities/framework/tls`. If the adherence policy says not to honour the cluster profile, they fall back to the Intermediate profile. They also restart themselves when the profile or adherence policy changes (`rhoai/operator/internal/tls/profile.go:47-118`, `pkg/tls/tls.go`). The operator additionally writes the effective profile into the operand's `Configuration.tls` as `minVersion` and cipher suites (`rhoai/operator/internal/tls/operand.go:91`), so the operand's metrics, webhook and status servers stay consistent with the cluster.

**Security observations.**
- *Cluster-wide Secret access.* The operand ClusterRole grants `create/get/list/patch/update/watch` on `secrets` and `configmaps` cluster-wide (`manifests/base/rbac/role.yaml`). This is how it materialises MPI and Flux secrets in user namespaces, but it means the controller can read every Secret in the cluster.
- *Deterministic Flux CURVE key.* The Flux plugin builds the ZeroMQ CURVE secret key as `sha256(TrainJob.UID)` (`pkg/runtime/framework/plugins/flux/flux.go:509-516`). Anyone who can read the TrainJob's UID can recompute the key. X25519 is also not a FIPS-approved key agreement. Flux is an upstream runtime; no Flux runtime ships among the RHOAI curated ClusterTrainingRuntimes (`rhoai/operator/manifests/runtimes/`), but the plugin is compiled in. MPI SSH keys, by contrast, are random ECDSA P-521 keys (`pkg/runtime/framework/plugins/mpi/mpi.go:316`).
- *Webhook validation opt-out.* The validating webhooks for ClusterTrainingRuntime and TrainingRuntime have an `objectSelector` that skips validation when an object carries the label `trainer.kubeflow.org/webhook-validation=disabled` (`manifests/base/webhook/patch_validating.yaml`). Anyone allowed to create TrainingRuntimes can bypass webhook validation; only CRD CEL rules remain.
- *Cleartext progression polling.* Progression tracking fetches `http://<podIP>:<port>/metrics` without TLS or authentication (`pkg/rhai/progression/progression.go:263`). The per-TrainJob NetworkPolicy limits who can reach that port: only the controller pods and same-JobSet peers (`pkg/rhai/networkpolicy.go:58-118`).
- *Operator NetworkPolicy.* The operator's metrics NetworkPolicy admits port 8443 from `podSelector: {}`, which means any pod in the operator namespace, plus three monitoring namespaces (`rhoai/operator/config/network-policy/allow-metrics-traffic.yaml`). Metrics are still behind controller-runtime authn/authz (TokenReview/SubjectAccessReview) because `--metrics-secure=true`.

**Image and version drift.** `manifests/rhoai/params.env` pins the controller image tag `rhoai-3.6`, and the ImageStream parameters only have keys up to `-3-6`, with the 3-4 and 3-5 tags defaulting to `quay.io/opendatahub/...:odh-3.5-ea1`. Only the `-3-6` ImageStream keys and the runtime images are mapped to `RELATED_IMAGE_*` overrides. Older ImageStream tags therefore keep their upstream `quay.io/opendatahub` defaults unless something else patches them, which is a risk for disconnected clusters. The operator's PR pipeline still declares `rhoai-version: "3.6.0"`, and `.tekton/` has no push pipeline for the operator image on this branch.

**Unused artifacts.** The Python initializers, runtimes (`cmd/runtimes/*`), the torchtune trainer and the Rust data-cache all have upstream Dockerfiles but no Konflux pipelines on this branch. RHOAI ships only the two Go images. Training images come from the separately built universal training-hub images (overlay 0013).

## Multi-Tenancy

### Tenant Model

| Aspect | Value | Source |
|--------|-------|--------|
| **Tenant boundary** | Per-namespace (TrainJob, TrainingRuntime are namespaced; ClusterTrainingRuntime shared) | CRD scopes in `manifests/base/crds` |
| **Deployment model** | Single shared controller per cluster (cluster-wide watches) serving all tenant namespaces; one operator per cluster | `manifests/base/rbac/role_binding.yaml` (ClusterRoleBinding) |
| **Tenant identifier** | Namespace name | `pkg/statusserver/auth.go` (namespace claim check) |

### Isolation Mechanisms

| Dimension | Mechanism | Enforced By | Gaps / Risks |
|-----------|-----------|-------------|--------------|
| Auth & AuthZ | training-edit/admin/view ClusterRoles bound per namespace; status server checks token namespace and audience | Kubernetes RBAC / Application | `training-edit`/`training-admin` lack aggregate-to-edit/admin labels (only view aggregates), so they must be bound explicitly; the controller SA has cluster-wide Secret read |
| Data storage | Per-namespace PVCs/initializers defined in runtimes | Kubernetes | Controller does not mediate storage |
| Network traffic | Per-TrainJob NetworkPolicy (ingress only from same JobSet + controller metrics port) | Kubernetes NetworkPolicy (RHAI) | Ingress-only; no egress restriction for training pods |
| Compute & resources | Optional gang scheduling (PodGroups), Kueue integration, LimitRange-aware defaults | Kubernetes / Kueue | Quotas rely on platform (Kueue/ResourceQuota), not this component |
| Configuration & secrets | MPI/Flux secrets created in the TrainJob namespace | Kubernetes | Flux CURVE secret key predictable from UID |
| API scoping | Cluster-wide watches; TrainJob may only reference a TrainingRuntime in its own namespace or a ClusterTrainingRuntime | Application (runtime resolution) | ClusterTrainingRuntimes are global; admins of any namespace can create TrainingRuntimes that skip webhook validation via label |

### Shared Services

| Shared Service | Tenant Boundary | Isolation Mechanism |
|----------------|----------------|---------------------|
| kubeflow-trainer-controller-manager (webhooks, reconcilers) | namespace | Kubernetes RBAC on CRs; webhook validation |
| Status server (gated, off in RHOAI) | namespace + TrainJob | Audience-bound projected token, namespace claim check |
| Curated ClusterTrainingRuntimes | cluster-wide (read-only to users) | RBAC (training-edit read-only) |
