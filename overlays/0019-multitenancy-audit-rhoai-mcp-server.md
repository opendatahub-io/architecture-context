## Fact

Structured multi-tenancy audit of the RHOAI MCP Server component for RHOAIENG-74880. The MCP server has a **bifurcated security architecture**: with the OIDC overlay (`openshift-oidc` kustomize) it provides strong per-user isolation via K8s impersonation, SubjectAccessReview-based tool filtering, and fail-closed auth middleware. Without OIDC (the default), it is effectively single-tenant with a broadly privileged ServiceAccount. The primary recommendation is to make the OIDC overlay the default or only supported deployment configuration for any multi-user environment.

## Impact on Strategies

- The generated architecture doc (`architecture/rhoai.next/rhoai-mcp.md`) is missing the `openshift-oidc` overlay from its Kustomize Structure and Distribution Variants tables — any strategy referencing MCP server deployment variants will miss the only multi-tenant-ready configuration
- ~~Subprocess execution in the downstream quickstart domain bypasses OIDC impersonation entirely~~ — **Historical (ec1157a):** quickstart domain removed from downstream codebase; no longer an active risk
- Tools without explicit permission mappings are allowed by default (`server.py:403`) — new tools risk being unscoped until permissions are added
- No NetworkPolicy restricts ingress to or egress from the MCP server pod beyond a single model-catalog ingress rule

## Context

This overlay captures the full multi-tenancy audit findings. The generated architecture doc covers the MCP server's general architecture comprehensively but does not analyze tenancy boundaries, isolation gaps, or the security implications of the OIDC-off default. This audit fills that gap for the cross-component aggregation matrix (RHOAIENG-76375).

## 1. Tenancy Definition & Implementation

| Aspect                                                               | Details                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         |
|----------------------------------------------------------------------|-------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------|
| **What does "tenant" mean in this component?**                       | An authenticated user identity (OIDC JWT or OCP OAuth token) whose K8s API calls are scoped via impersonation. Without OIDC enabled, all MCP clients share a single ServiceAccount identity — effectively single-tenant.                                                                                                                                                                                                                                                                                                                        |
| **Implementation Model** (per cluster/namespace/user/customer/other) | Per-user (via OIDC/TokenReview) mapped to per-namespace K8s RBAC. Without OIDC: per-cluster (single SA identity).                                                                                                                                                                                                                                                                                                                                                                                                                               |
| **Primary K8s Primitives Used**                                      | RBAC (ClusterRole, ClusterRoleBinding), Namespaces, ServiceAccounts, SubjectAccessReview, TokenReview, User Impersonation                                                                                                                                                                                                                                                                                                                                                                                                                       |
| **Enforcement Split** (% K8s vs % App Logic)                         | With OIDC: 90% K8s (impersonation + RBAC + SubjectAccessReview) / 10% App Logic (tool filtering, safety gates, credential masking). Without OIDC: 30% K8s (namespace boundaries) / 70% App Logic (safety flags only).                                                                                                                                                                                                                                                                                                                           |
| **Has Shared Services/Data Planes** (Yes/No)                         | Yes                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                             |
| **If shared, how are boundaries preserved?**                         | Single MCP server pod serves all users. With OIDC: per-request `UserContext` via contextvars, K8s impersonation client created per request (server.py:53-63), tool visibility filtered via SubjectAccessReview (server.py:370-450). Without OIDC: no boundaries — all requests use the shared SA client. **Downstream note**: the planner composite domain uses unauthenticated HTTP to the Planner Backend. ~~Quickstart domain subprocess execution (helm, oc, kubectl)~~ — **removed at ec1157a**; no longer present in downstream codebase. |

**Aggregation Notes:** RHOAI MCP Server has a bifurcated security architecture. With the OIDC overlay (openshift-oidc kustomize), it provides strong per-user isolation via K8s impersonation, SubjectAccessReview-based tool filtering, and fail-closed auth middleware. Without OIDC (the default), it is effectively single-tenant with a broadly privileged ServiceAccount. The primary recommendation is to make the OIDC overlay the default or only supported deployment configuration for any multi-user environment.

The downstream codebase introduces additional risk surface not present upstream: an unauthenticated Planner Backend integration (confirmed). Quickstart tools that execute helm/oc/kubectl subprocesses were documented in the generated architecture doc (2026-06-30) but the quickstart domain (`src/rhoai_mcp/domains/quickstarts/`) has since been removed from the downstream codebase — all quickstart-related subprocess bypass findings are stale as of HEAD ec1157a (see Downstream Verification Results).
