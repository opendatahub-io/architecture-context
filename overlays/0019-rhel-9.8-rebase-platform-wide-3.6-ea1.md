## Fact

For RHOAI 3.6 EA1, the AIPCC base image rebase from RHEL 9.6 to RHEL 9.8
(referenced in overlay [0017](0017-aipcc-base-images.md), which documents
RHEL 9.6 as the base for the current 3.5 accelerator images) is a
**platform-wide AIPCC effort**, not owned by any single accelerator
strategy. This is confirmed across every AIPCC accelerator variant, not
just CUDA: CUDA 12.9, CUDA 13.0.2, CPU, ROCm 7.14, IBM Spyre, Google TPU
(once Active), and Intel Gaudi (Technical Preview, pending base image
status reconfirmation) all rebase to RHEL 9.8 together for 3.6 EA1.

The compiler toolchain for building AIPCC packages remains **gcc14**
across all accelerator variants, unchanged from prior releases.

The following fact is scoped to vLLM CUDA 12.9 only, not platform-wide:
the speculators package used for vLLM speculative decoding is locked to
version **0.6.0** for the CUDA 12.9 / 3.6 EA1 stack, confirmed by the
owning team.

## Impact on Strategies

- Strategies for any AIPCC accelerator variant (CUDA, CPU, ROCm, Spyre,
  TPU, Gaudi) should treat the RHEL 9.8 rebase as a platform-wide AIPCC
  dependency, not something the strategy itself owns or drives — this
  resolves an open question raised independently in RHAISTRAT-2366 ("Is
  the RHEL 9.8 rebase a platform-wide AIPCC effort or per-variant?") and
  confirmed again in six other 3.6 EA1 accelerator strategies.
- Build/test/CI assumptions for any accelerator variant should continue
  to assume gcc14 as the compiler toolchain — no change from prior
  releases.
- Strategies referencing speculators for the CUDA 12.9 / 3.6 EA1 stack
  specifically should cite version 0.6.0 as locked, rather than leaving
  the version unpinned. This does not apply to non-CUDA-12.9 strategies.

## Context

RHAISTRAT-2366 ("CUDA 12.9 Support for Red Hat AI 3.6 EA1") independently
identified the RHEL 9.8 rebase scope as an open question and left the
speculators version unpinned. This overlay originally recorded that as a
CUDA-12.9-specific fact (`affects: [vllm]`), but the same RHEL 9.8 rebase
and gcc14 continuity were independently confirmed while refining
RHAISTRAT-2141 (CUDA 13.0.2), RHAISTRAT-2161 (CPU), RHAISTRAT-2170 (ROCm
7.14), RHAISTRAT-2172 (Spyre), RHAISTRAT-2149 (Google TPU), and
RHAISTRAT-2150 (Intel Gaudi) — none of which reference `vllm` as an
affected component in a way the original scoping would reliably match.
`affects` was broadened to `platform` to ensure every accelerator
strategy picks up the rebase and toolchain facts, so future strategies
touching any AIPCC accelerator variant don't have to re-derive or re-ask
the same questions.
