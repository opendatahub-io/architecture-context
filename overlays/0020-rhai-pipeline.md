## Fact

`rhai/pipeline` is the **package index management system** for all Red Hat AI
(RHAI) products. It does not compile wheels -- compilation is fully delegated to
the `redhat/rhel-ai/wheels/builder` system, which provides global constraints,
security constraints, and variant-specific build requirements. Constraint files
in this repo must not conflict with the builder's constraints. This repo declares
which packages to build per collection x variant x architecture, and publishes
approved wheels to the customer-facing Pulp index.

Some products (notably RHAIIS) also maintain their own dedicated pipeline repos
(`rhaiis/pipeline`), though certain variants and collections are duplicated
across both repos.

- **Product name:** `rhoai`
- **Product version (3.6-EA1):** `3.6-EA1`
- **Builder version pinned:** `v39.1.0`
- **Pulp domain:** `public-rhai`
- **Public index base URL:** `https://packages.redhat.com/api/pypi/public-rhai/rhoai/`

Publishing to Pulp is controlled per **variant** in `publish_config.yml`, not
per collection. All collections' wheels for a published variant end up in the
same Pulp index. For 3.6-EA1, the published variants are: cpu-ubi9, cuda12.9-ubi9,
cuda13.0-ubi9, rocm7.14-ubi9, and spyre-ubi9.

`model-opt` and `ogx` have `ENABLE_MULTI_VERSION_BOOTSTRAP: true` with a 30-day
maximum release age, allowing builds against multiple simultaneous product versions.

**Explicit exclusions from the build matrix (OMIT_JOBS):**
- `ogx` — excluded from `cpu-ubi9/s390x` (no s390x index)
- `rhaiis` — excluded from `cpu-ubi9/s390x` and `cpu-ubi9/ppc64le` (no s390x/ppc64le index)

Note: `OMIT_JOBS` also contains entries for `docling` and `sdg-hub` referencing
`cpu-ubi9/s390x`, but these are **dead code** — those strings are package names
inside the `rhai-innovation` collection, not collection names. The set is checked
against the collection name in the iteration loop, so these entries never match
and have no effect. The `rhai-innovation/cpu-ubi9/s390x` job still runs.

**Test jobs** (`ENABLE_TEST_JOBS: true`) are enabled only for `ogx` and
`onboarding` collections.

**Upcoming: `vllm-deps` collection** — A `COLLECTION_OVERRIDES` entry for
`vllm-deps` is pre-wired (AIPCC-19939) to publish to
`https://private.console.redhat.com` with product name `vllm-deps` and version
`torch2.11`. The collection directory does not yet exist and it is absent from
`COLLECTIONS`; the override will take effect once the directory is created and

### Onboarding Pipeline

New dependency requests land in `collections/onboarding/{variant}/` first.
Test builds are enabled, giving teams CI feedback before production. A weekly
scheduled GitLab job (`move-onboarded-packages`, triggered by
`SCHEDULE_TYPE=move-onboarded`) runs `./bin/move-onboarded-packages.sh`, which
calls the `migrate-onboarding` CLI tool, moves graduated packages to
`collections/rhai/*/requirements/onboarded.txt`, and creates a bot MR. All new
top-level dependencies must go through onboarding before appearing in the `rhai`
collection.

### Pipeline Flow

**Stages:** checks → lint → bootstrap → build → release → package-deletion →
publish → pre-notify → notify

**Trigger types:**
- Push to branch: standard CI (cancels concurrent interruptible jobs, except on
  main)
- Nightly schedule (`SCHEDULE_TYPE=nightly`): main branch builds only
- Weekly `move-onboarded` schedule: runs `move-onboarded-packages.sh`
- CVE scan schedule: runs `bin/cve_scanner.py`
- AutoQA trigger: fires HTTP POST to AutoQA when `publish_config.yml` changes

**Key checks-stage gates:**
- `variant-linter` — validates variant names in `.gitlab-jobs.yml` on every MR
- `verify-publish-config` — on `publish_config.yml` changes, queries Pulp API
  to compare old vs new versions; saves `publish-delta/index-delta.md` as 90-day
  artifact
- `validate-package-deletion-manifests` — validates deletion YAML on MR; on
  merge, executes actual deletion

### Pulp Publishing Mechanics

**Two-stage workflow:**

1. **Upload** (`bin/pulp_ops.py upload`): Discovers wheel/sdist artifacts, filters
   packages listed in deletion manifests, uploads via mTLS to Pulp, creates or
   updates a `-test` distribution (auto-increment pointer for QE). Labels each
   artifact: accelerator, rhel_version, variant, product_version, ci_commit_sha.

2. **Publish** (`bin/pulp_ops.py publish`): Reads per-variant
   `WHEEL_REPO_VERSION`/`SDIST_REPO_VERSION` HREFs from `publish_config.yml`;
   updates the production distribution to point to the specified, tested, immutable
   repository version. Customers access packages only after this stage.

**Repository naming (ADR 065):**
- Wheels repo: `rhoai-{version}-{variant}` → path `rhoai/{version}/{variant}/simple/`
- SDists repo: `rhoai-{version}-{variant}-sdists`
- Test distributions append `-test` suffix

**Authentication:** All Pulp operations use mTLS (`PULP_CERT_BASE64` /
`PULP_KEY_BASE64` CI/CD variables). Builder cache deletion requires `BOT_PAT`.

### Package Deletion System

YAML manifests in `package-deletions/{release}.yaml` declare packages to remove.
Deletion is enforced at upload time (packages matching deletion patterns are
skipped before upload, preventing re-introduction even if builds re-run). MR
validation runs a dry-run; on merge the job executes actual Pulp deletion and
purges the GitLab PyPI cache. The system is idempotent.

### Version Branching

`bin/copy_wheels.py` copies existing Pulp repositories to new repository names
when creating a new product version (e.g., EA1 → GA). This is a fast
promotion path that does not require re-running builds; requires no package
changes between EA and GA.

## Impact on Strategies

- This is the authoritative publish gate for all RHAI Python packages. No package
  reaches the customer-facing Pulp index without going through this pipeline.
- Adding a new collection or variant requires: (1) entry in `COLLECTIONS`/`VARIANTS`
  in `bin/regen-gitlab-jobs.py`, (2) creating `collections/{name}/{variant}/`
  directory structure, (3) running `tox -e regen`, (4) merging. The
  `variant-linter` CI job blocks any unrecognized accelerator type. The
  `tpu-ubi9` variant is already defined in `VARIANTS` — adding a collection for
  it only requires steps 2–4.
- All jobs use `ENABLE_REPEATABLE_BUILD_MODE: true`. On a release branch, adding
  or updating a package requires explicit version pinning — the locked dependency
  graph will not re-resolve.
- Two CUDA versions (12.9 and 13.0) are maintained simultaneously. Adding a third
  is structurally straightforward but doubles builder resource consumption for
  that variant. Note: `cuda12.9-ubi9` is excluded from the `rhaiis` collection
  and therefore does not receive vLLM packages via this pipeline.
- ROCm 7.1 has been fully retired: it is no longer present in `VARIANTS`,
  `COLLECTIONS`, or `publish_config.yml`. Only ROCm 7.14 is built and published.
  RFEs referencing ROCm no longer need to specify a version — there is exactly
  one ROCm variant.
- All published variants for 3.6-EA1 pin torch 2.11.0 in their
  `constraints-rules.txt`. Spyre carries IBM-proprietary packages:
  `sendnn-inference==2.3.1` (IBM inference runtime, compiled from source),
  `torch-sendnn==1.2.5` (pre-built, x86_64 and ppc64le, private Pulp index),
  `torch-nnpa==1.5.0` (pre-built, s390x only, private Pulp index),
  `ibm-fms==1.11.1` (Foundation Model Stack, built from source via GitLab mirror;
  both pinned and unpinned `ibm-fms` are listed per AIPCC-27741), and a separate
  IBM vLLM fork (`vllm[tensorizer]==0.24.0+rhaiv.3.spyre`) — all despite sharing
  the same torch 2.11.0 pin as other variants. `aiu-monitor`/`ibm-aiu-monitor`
  are blocked from all wheel collections (`aiu-monitor<0.0.0` in
  `global-constraints.txt`) and live in the base image instead. RFEs touching
  Spyre must account for this separate stack.
- The public index URL structure (`rhoai/{version}/{variant}/simple/`) is treated
  as a stable contract for air-gapped mirroring (`wget`-based). Breaking this
  structure requires coordinating all downstream consumers.
- Package deletion is idempotent and enforced at upload time. RFEs proposing
  package removal must go through the deletion manifest process; simply removing
  a package from `requirements.txt` does not remove it from Pulp.
- New packages must go through the `onboarding` collection first. The weekly
  graduation automation handles promotion to `rhai`, but it runs weekly, not on
  demand.

### ROCm Work Breakdown Patterns

When a strategy involves a ROCm variant update in the pipeline (e.g., new ROCm
version or ROCm package changes), the pipeline-side work decomposes into these
epics:

- **Update ROCm variant constraints** — torch pin, vllm pin, and ROCm-specific
  package versions in `constraints.txt` and `constraints-rules.txt` for the
  `rocm{version}-ubi9` variant.
- **Add or update ROCm-specific packages in collections** — `amd-quark`,
  `amd-aiter`, `flash-attn`, `flydsl`, and any new AMD ecosystem packages in
  `collections/rhaiis/rocm{version}-ubi9/requirements.txt`.
- **Validate build and publish for the ROCm variant** — CI pipeline green, wheels
  uploaded to Pulp, customer-facing index updated, `publish_config.yml` updated
  to point to the new Pulp repository version.

Strategies referencing ROCm pipeline updates should structure their Technical
Approach around these epics rather than describing the work as prose.

## Context

This overlay was created to capture the state of the RHAI wheel pipeline at the
3.6-EA1 release boundary. The pipeline repo is purely declarative — it contains
no application code. Its architecture (collection structure, variant matrix, Pulp
publishing contract) shapes what RHAI customers receive and constrains what RFEs
can realistically propose. This overlay allows the feasibility reviewer to
evaluate whether a proposed change is compatible with the existing index
structure, build infrastructure, and publishing workflow. Updated 2026-07-30 by
running the `update-rhai-pipeline-overlay` skill.
